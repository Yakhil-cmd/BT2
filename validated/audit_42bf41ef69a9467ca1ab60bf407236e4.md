### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while the acted-upon repository is bound to a different, unchecked `repository.full_name` field, allowing signature-bypass forgery of events for protected repositories in multi-organization deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The engine supports configuring several GitHub organizations, each with its own (optional) `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to verify the incoming HMAC against using the attacker-controlled JSON fields `repository.owner.login` / `organization.login`. However, the handlers that actually act on the payload (e.g. `PushHandler`, and other handlers derived from `Shipit::Webhooks::Handlers::Handler`) resolve the target `Repository`/`Stack` using a completely independent, also attacker-controlled field: `repository.full_name`. Nothing enforces that the organization used to select the verification secret matches the organization that owns the repository being written to.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to verify against based on the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` only respects this `organization` argument when the installation is running in the documented multi-organization configuration mode (`github_default_organization` non-nil); each organization can have its own, independently-configured `webhook_secret`, which the setup docs explicitly mark as **optional**: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` fully bypasses HMAC checking whenever the selected organization has no secret configured: [5](#0-4) 

Once `verify_signature` passes (or is bypassed this way), event handlers resolve which `Repository`/`Stack` to act on using an entirely different, also-unverified field of the same payload: [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization_used_for_secret_selection == owner_of(repository.full_name)`

but this is never checked. An attacker can set `repository.owner.login` (or `organization.login`) to any configured organization that has no `webhook_secret` set (satisfying signature verification trivially since `verify_webhook_signature` returns `true` when `webhook_secret` is blank), while setting `repository.full_name` to `some-other-org/protected-repo` that is tracked by Shipit under a *different*, secret-protected organization. The handler will process the forged event against that protected repository, because `repository_name` (used for the actual DB lookup) is never cross-checked against `repository_owner` (used for authentication).

### Impact Explanation
This is an authentication bypass of the webhook endpoint for any tracked repository, as long as the Shipit installation is configured with at least two organizations and at least one of them lacks a `webhook_secret` (an explicitly supported/optional configuration per `docs/setup.md`). With this bypass an unprivileged, unauthenticated network attacker can forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) against repositories belonging to a *different*, properly-secured organization:
- Forged `push` events trigger `GithubSyncJob` against arbitrary tracked stacks.
- Forged `membership` events create/delete `Team`/`Membership`/`User` records, which back `User#authorized?` (`Shipit.github_teams` authorization) — see `app/models/shipit/webhooks/handlers/membership_handler.rb` and `app/models/shipit/user.rb`.
- Forged `status`/`check_suite`/`pull_request` events can influence merge-queue and deploy-readiness signals that other parts of Shipit rely on being authentic.

This matches the "authentication bypass" and "escalation into `Shipit.github_teams` authorization" impact categories called out in scope.

### Likelihood Explanation
Requires a specific but documented and plausible configuration: multiple GitHub organizations configured in `secrets.github`, with at least one organization missing `webhook_secret` (explicitly optional per the setup docs). No credentials, tokens, or prior access are required by the attacker — only the ability to POST to the public `/webhooks` endpoint with a crafted `X-Github-Event` header and JSON body.

### Recommendation
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret` in `verify_webhook_signature`).
- Cross-validate that the organization used to select the verification secret matches the owner segment of `repository.full_name` (and `organization.login` where applicable) before dispatching to handlers.
- Consider verifying the signature using a secret keyed off of the resolved `Repository`/`Stack` rather than an unauthenticated payload field.

### Proof of Concept
1. Admin configures Shipit with two organizations in `secrets.github`, e.g. `open-org` (no `webhook_secret` set) and `secure-org` (with `webhook_secret` set), both with tracked repositories/stacks.
2. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/protected-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid signature required.
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name("secure-org/protected-repo")` and enqueues `GithubSyncJob` for that stack, even though the attacker never produced a signature valid for `secure-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
