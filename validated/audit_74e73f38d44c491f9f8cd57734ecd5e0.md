### Title
Webhook Organization/Secret Verification Not Bound to Acted-Upon `repository.full_name` — Cross-Organization Stack Manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a GitHub webhook using `repository_owner`, a value read directly out of the (still-unverified) JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, the actual event handlers (e.g. `PushHandler`, `Handler#stacks`) resolve which `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name`. Because the signature only proves "this payload was signed with the secret belonging to the organization named in `repository.owner.login`," and nothing ties that organization to the `repository.full_name` that is subsequently trusted to select the target stack, an attacker who legitimately possesses a webhook secret for one organization configured in this Shipit instance can forge a payload whose `owner.login` matches their own org (so it passes signature verification) but whose `repository.full_name` points at a stack belonging to a completely different, unrelated organization also hosted on the same Shipit instance.

### Finding Description
- `verify_signature` picks the `github_app`/secret via `repository_owner`, itself parsed from the raw, not-yet-verified body: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` is derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [2](#0-1) 
- Once the signature is accepted, the generic `Handler` base class (used by `PushHandler` and all other GitHub event handlers) resolves the affected stacks purely from `repository.full_name`, with no re-validation against the organization that was used for signature verification: `Repository.from_github_repo_name(repository_name)&.stacks`, `repository_name = payload.dig('repository', 'full_name')`. [3](#0-2) 
- `PushHandler#process` then directly triggers `stack.sync_github(expected_head_sha: params.after)` for every matching stack. [4](#0-3) 

This is structurally identical to the reported bug class: a value that is *acted upon* (`stake.value`/`totalTaxInGoldPerRank` in the Halborn report; here, `repository.full_name`) is never actually covered by the check that is supposed to authorize the action (`SafeCast`-worthy bounds check in the report; here, the webhook signature, which only binds the *organization* identity, not the *repository* field used downstream). The engine explicitly supports multiple organizations configured behind one Shipit instance with independent webhook secrets (as shown by the two-org fixture `test/dummy/config/secrets_double_github_app.yml`), so this is not a theoretical multi-tenancy scenario but a supported configuration.

### Impact Explanation
An attacker who is a legitimate, low-privilege owner/administrator of Organization A's GitHub App/webhook registration on a shared Shipit instance can forge a `push` (or other) webhook payload that is validly signed with Org A's secret, but whose `repository.full_name` names a repository/stack belonging to Organization B. Because signature verification never re-checks that the signed organization matches the repository the handler subsequently mutates, the forged event causes `GithubSyncJob`/deploy-triggering logic to run against Organization B's stack — a cross-repository/cross-organization action the attacker was never authorized to perform. This matches the "cross-repository writes" / "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Exploitation only requires:
1. A Shipit deployment configured with more than one GitHub organization/app (an explicitly supported and documented configuration).
2. The attacker to control a valid webhook secret for their own (low-privilege) organization entry — something they would normally have as the person who set up Shipit integration for their own repo.

No compromise of `GITHUB_TOKEN`, `api_clients_secret`, or any `ApiClient` token is required, and no privileged Shipit account is needed — only crafting an HTTP POST to the shared `/webhooks` endpoint with a body signed by a secret the attacker legitimately controls.

### Recommendation
After signature verification, cross-check that the organization/app used to validate the signature matches the owner organization implied by `repository.full_name` (or `repository.owner.login`) before resolving `Repository.from_github_repo_name`. Reject the event if these two identities diverge, analogous to how the original report fixed the cast mismatch by tying the checked type/value to the value actually used.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an operator with legitimate access to `OrgA`'s webhook secret, craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already present in OrgB/target-repo>",
  "repository": {
    "full_name": "OrgB/target-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to the Shipit `/webhooks` endpoint with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `github_app`, and successfully verifies the signature (since it was signed with `OrgA`'s secret). [1](#0-0) 
5. `PushHandler` resolves stacks via `repository.full_name = "OrgB/target-repo"`, entirely unrelated to `OrgA`, and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stack. [3](#0-2) [4](#0-3)
