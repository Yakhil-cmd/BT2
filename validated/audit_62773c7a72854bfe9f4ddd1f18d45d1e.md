### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the stack derived from `repository.full_name` - allowing cross-repository writes when Shipit is configured for multiple GitHub organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports a multi-organization GitHub App configuration where each organization has its own `webhook_secret` [1](#0-0) . The webhook signature is verified using the secret belonging to the organization read from `repository.owner.login` (or `organization.login`) in the JSON body [2](#0-1) [3](#0-2) . However, the event handlers that actually mutate state (sync commits, create statuses, etc.) resolve the target `Repository`/`Stack` using a completely different field of the same payload: `repository.full_name` [4](#0-3) .

### Finding Description
This mirrors the Royco bug class: a check is performed on one field/binding while the consequential action is performed on a different, unlinked field. In `WrappedVault.sol`, the rate check used one comparison operator while the actual reward allocation depended on the opposite boundary, letting the two diverge. Here, the "authentication" binding (organization → webhook secret, taken from `repository.owner.login`) and the "write target" binding (stack → repository, taken from `repository.full_name`) are two independently attacker-suppliable strings inside the same JSON body, with no code that asserts `full_name.split('/').first == owner.login`.

Concretely:
- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [2](#0-1) .
- `Shipit.github(organization:)` looks up a per-organization config entry (and secret) keyed by that string [1](#0-0) .
- If the signature validates (i.e., the request was legitimately signed by GitHub for the organization identified by `owner.login`), the controller dispatches the whole parsed JSON body to handlers [5](#0-4) .
- The handler base class then determines which `Stack`s to touch using `repository_name = payload.dig('repository', 'full_name')` and `Repository.from_github_repo_name(repository_name)` [4](#0-3) , e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) .

Because GitHub computes the HMAC over the raw request body, and the body itself is fully attacker-controlled content when the attacker owns *some* org onboarded to the same Shipit instance, an org administrator (or anyone who compromises that org's webhook secret/delivery, which they legitimately possess for their own org) can craft a payload where `repository.owner.login` = their own organization (so the signature check passes using their own secret) while `repository.full_name` = `"other-org/other-repo"` for a *different* organization/repository configured on the same Shipit deployment. The signature check would succeed (correctly signed for the attacker's org), but the handler logic would sync commits / create statuses for a stack belonging to an entirely different organization/repository.

### Impact Explanation
This breaks the equality "organization that authenticated the webhook == repository being written to." If exploitable, it enables a webhook impersonation / cross-repository write: an org that legitimately controls its own webhook secret can force `GithubSyncJob` to run against another organization's stack, potentially corrupting its commit history tracking, injecting fake commit statuses (`StatusHandler`), or manipulating pull-request/merge-status state for a repository the attacker does not own. This matches the "cross-repository writes" Critical-impact category in scope, contingent on the deployment actually being configured with multiple organizations sharing one Shipit instance (as supported by `github_organizations`/`github_app_config`) [7](#0-6) .

### Likelihood Explanation
Likelihood is conditional and not fully provable from static code alone: it requires (a) the operator to run Shipit in the multi-org configuration mode with distinct `webhook_secret`s per org (the default/legacy single-org mode uses one shared secret across the whole instance, in which case there is no privilege boundary to cross), and (b) that GitHub, when delivering a webhook for org A's repository, does not itself constrain the JSON body's `repository.full_name` to match org A (which it does not — GitHub simply forwards whatever the event payload naturally contains, and this analysis cannot fully verify whether GitHub webhooks for a given org could ever legitimately carry a `full_name` referencing a different org's repo, e.g. via forks/transfers, versus this requiring the attacker to directly POST a forged-but-validly-signed body using their own known secret to the shared endpoint). Given `verify_signature` only checks that *some* valid signature exists for the org named in `owner.login`, and never cross-checks it against `full_name`, a webhook relay/replay crafted by anyone in possession of one org's secret is sufficient — no session, no `ApiClient` token, and no privileged Shipit account is required, only ordinary control over one GitHub organization's webhook configuration in a multi-tenant Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler#repository_name`), enforce that the organization used to select the webhook secret is the same organization referenced by `repository.full_name` (and `organization.login`, where present). Concretely, derive `repository_owner` from `full_name.split('/').first` (or explicitly compare it against `repository.owner.login`/`organization.login` and reject on mismatch) before verifying the signature, so a single payload cannot be signed under one organization's secret while addressing a stack belonging to another organization.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (multi-org config per `lib/shipit.rb#github_app_config`).
2. As an administrator of `org-a`'s GitHub App/webhook (who legitimately knows `org-a`'s `webhook_secret`), craft a JSON body: `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/some-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen-sha>"}`.
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(org-a-webhook-secret, body)`.
4. POST to `/shipit/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature [2](#0-1) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/some-repo")` [4](#0-3) [6](#0-5)  and triggers `GithubSyncJob` for `org-b`'s stack, even though the request was only authenticated for `org-a`.

Note: I could not fully verify from the indexed code/tests whether the host deployment ever runs in this multi-org mode in practice, or whether any additional validation exists elsewhere in the request pipeline (e.g., Rack middleware) that cross-checks `owner.login` against `full_name` before reaching `Webhooks.for_event`; the tests reviewed (`test/controllers/webhooks_controller_test.rb`) only exercise the single-org fixture scenario and do not cover this cross-org case.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
