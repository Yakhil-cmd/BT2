### Title
Webhook signature is bound to `repository.owner.login`, but events are applied to `repository.full_name` — cross-organization forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit's multi-organization GitHub App support (`Shipit.github(organization:)`) resolves a distinct `webhook_secret` per GitHub organization. `WebhooksController#verify_signature` picks which organization's secret to use for HMAC verification based on the attacker-supplied JSON field `repository.owner.login` (or `organization.login`), while the handlers that actually act on the request use a *different* attacker-supplied field, `repository.full_name`, to look up the target `Repository`/`Stack`. Nothing ties these two fields together, so the org whose secret authenticates the webhook is not necessarily the org whose repository gets mutated.

### Finding Description
`verify_signature` derives the signing organization purely from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` config (with its own `webhook_secret`) via `github_app_config`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only proves that the requester knows *that organization's* secret — it says nothing about which repository the payload describes: [4](#0-3) 

After signature verification succeeds, `create` dispatches the *entire raw payload* to handlers unmodified: [5](#0-4) 

Every handler resolves its target `Repository`/`Stack` from a completely different field, `repository.full_name`: [6](#0-5) 

e.g. `PushHandler`, which triggers `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack for the branch: [7](#0-6) 

or `MembershipHandler`, which adds/removes members of a `Team` looked up from `params.organization.login` while trusting `params.member.login` verbatim: [8](#0-7) 

**Binding broken:** `organization authenticated by verify_signature (repository.owner.login)` ≠ `repository/organization acted on by the handler (repository.full_name / organization.login inside handler params)`. The signature covers the raw bytes, but the controller's choice of *which secret* to validate against is itself taken from an unauthenticated field of the same payload, and the field used for authorization-scoping (`owner.login`) is never cross-checked against the field used for the actual write action (`full_name`).

This is the same class of bug as the referenced WLFI report: a status/flag is enforced in the code path that authenticates the identity (`_excludedVotingPower` checked in `getVotes`), but a sibling path that performs the actual mutating action (`_delegate`/`_update`) never re-validates that same identity, letting the excluded actor's effect reach an unauthorized destination. Here, the "verification" gate (organization secret) and the "mutation" gate (which repository's stacks/teams get modified) are decoupled the same way.

### Impact Explanation
An attacker who legitimately controls (or has compromised the webhook secret of) **any one** organization/repository configured in a multi-org Shipit deployment can craft a payload whose `repository.owner.login` names their own organization (so `verify_signature` selects and validates against their own known secret) while `repository.full_name` (and, for `membership` events, `organization.login`) names a **victim** repository/organization also hosted on the same Shipit instance. Because the handler layer trusts `full_name`/`organization.login` independently of what was used for signing, this can:
- Force `GithubSyncJob`/`stack.sync_github` to run with an attacker-chosen `expected_head_sha` against a victim stack (`PushHandler`), potentially causing a deploy of attacker-controlled/unreviewed refs — an unauthorized deploy.
- Add/remove arbitrary GitHub users from a victim `Team` used for `Shipit.github_teams` authorization (`MembershipHandler`) — escalation into Shipit's team-based authorization.
- Archive/unarchive victim review stacks or trigger check-suite driven merges via `PullRequest`/`CheckSuite` handlers.

This satisfies the "High" bar (escalation into `Shipit.github_teams` authorization) and can reach "Critical" (unauthorized deploy) depending on which handler is abused.

### Likelihood Explanation
Requires the attacker to control the webhook secret for at least one organization already onboarded to the same multi-tenant Shipit instance — a realistic scenario for shared/hosted Shipit deployments serving multiple orgs/teams, and no different in privilege level from a normal webhook-sending GitHub App owner (not a Shipit session, API token, or repo-write privilege on the victim repo). Because `repository_owner` and `repository_name` are read from two unrelated JSON paths with no cross-validation, exploitation only requires crafting a JSON body and computing one HMAC with a secret the attacker already legitimately possesses.

### Recommendation
Bind the two values together: derive the organization used for `Shipit.github(organization:)` lookup from the *same* field used by handlers to resolve the target repository (`repository.full_name`'s owner segment), and additionally, after signature verification succeeds, assert that the verified organization matches the owner portion of `repository.full_name` (and `organization.login` for membership-style events) before dispatching to handlers. Reject the request (422) on mismatch.

### Proof of Concept
1. Configure two organizations in `secrets.github`, e.g. `attacker-org` (secret known to the attacker) and `victim-org` (hosts the real stack).
2. Craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own known secret [1](#0-0) .
6. `PushHandler` resolves stacks via `repository.full_name == "victim-org/victim-repo"` [6](#0-5)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [9](#0-8) , despite the request never having been signed by `victim-org`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
