Based on my research, I found a plausible structural analog to the reported "stale authority not revoked" vulnerability class in `pallets/remote-proxy/src/lib.rs`, used by Asset Hub Kusama (and referenced from `relay/kusama/constants/src/lib.rs` / `relay/polkadot/constants/src/lib.rs`). [1](#0-0) 

### Title
Stale remote-proxy authorization window allows use of a revoked delegate proxy - (File: `pallets/remote-proxy/src/lib.rs`)

### Summary
`pallet_remote_proxy` authorizes an account to act as a proxy for a "real" account based on a Merkle proof that a `ProxyDefinition` (delegate relationship) existed at *some retained historical block* on a remote chain (typically the relay chain), rather than checking the *current* state of that relationship. Because a sliding window of `MaxStorageRootsToKeep` historical storage roots is kept, a delegate whose proxy rights were revoked on the remote chain can still successfully execute `remote_proxy` / `remote_proxy_with_registered_proof` using a proof anchored to an older, still-retained root from before the revocation.

### Finding Description
`do_remote_proxy` resolves proxy authority purely from a proof matched against one of the roots in `BlockToRoot`, a bounded ring buffer of the last `MaxStorageRootsToKeep` (block, storage_root) pairs: [2](#0-1) 

The lookup does a `binary_search_by` against this list, reads the proxy definition from the supplied proof at that historical root, and — as long as the caller's `delegate == who` and `delay.is_zero()` — dispatches the call as the `real` account: [3](#0-2) 

There is no re-verification against the *current* state of the proxy relationship on the remote chain (e.g., via the most recent root). If the `real` account removes `delegate` as a proxy on the relay chain (e.g., because the delegate's key was compromised), the removal only updates the *current* relay-chain state. Any of the previously retained storage roots in `BlockToRoot` — up to `MaxStorageRootsToKeep` blocks old — still contain a valid Merkle proof showing the delegate relationship as it existed *before* revocation, and this pallet has no mechanism to reject a proof anchored to a root older than the revocation. This directly mirrors the reported pattern: on-chain state records an authorization (operator / delegate) at time-of-action, and stale authorization is honored later without re-checking whether it has since been revoked.

### Impact Explanation
An attacker holding a compromised or since-revoked delegate key can still dispatch arbitrary calls filtered only by `ProxyType` on behalf of the `real` account, for as long as a pre-revocation storage root remains in the retained window. Because `pallet_proxy` proxy types (e.g. `Any`, `StakingOperator`, governance-related types) can permit balance transfers, staking operations, or other privileged calls, this can result in direct loss of funds or unauthorized privileged actions attributable to the victim account — the same class of impact ("previous operator... can still finalize... with an untruthful outcome") described in the reference report.

### Likelihood Explanation
Exploitation requires: (1) a delegate proxy relationship to have existed and been provable via Merkle proof, (2) the `real` account to revoke it, and (3) the (former) delegate to act before all roots predating the revocation are evicted from `BlockToRoot`. This is a narrow, real-time race window bounded by `MaxStorageRootsToKeep`, and the doc comments in the pallet acknowledge storage-root retention is deliberately limited for proof-freshness reasons — suggesting the retention window may be a known, accepted design trade-off rather than an overlooked bug. I was not able to confirm the exact configured value of `MaxStorageRootsToKeep` for Asset Hub Kusama/Polkadot before running out of tool iterations, which is needed to assess how wide this race window actually is in production.

### Recommendation
When validating a remote-proxy proof, additionally track/require that the proof's anchor block is no older than the block at which the most recent revocation-relevant state change (if any) is known, or reduce `MaxStorageRootsToKeep` to the minimum viable for cross-chain proof latency. Alternatively, require the proof to be anchored to the *latest* available root only, forcing proxy revocations to take effect immediately once the newest root is available locally.

### Proof of Concept
1. On the relay chain, account `A` adds `B` as an `Any` (or otherwise powerful) proxy with `delay = 0`.
2. Parachain observes this relay block via `on_validation_data`, storing `(block_n, root_n)` in `BlockToRoot`.
3. `B` obtains a Merkle proof of this `ProxyDefinition` at `block_n`.
4. `A` detects `B`'s key compromise and calls `remove_proxy` on the relay chain to revoke `B`.
5. As long as `block_n` is still within the last `MaxStorageRootsToKeep` roots retained by `BlockToRoot`, `B` calls `pallet_remote_proxy::remote_proxy` with the stale proof from step 3; `do_remote_proxy` succeeds because it only checks the historical root, not current relay-chain state, and dispatches an arbitrary call as `A`. [4](#0-3) 

**Caveat:** I could not fully verify how `MaxStorageRootsToKeep` is configured in the live Asset Hub Kusama runtime (last query was cut off before confirming this value), nor whether any other runtime-level mitigation (e.g., very small window, or additional freshness checks elsewhere in the runtime) narrows or eliminates this window in practice. This should be independently confirmed before treating this as a confirmed exploitable finding rather than a design-tradeoff observation.

	impl<T: Config<I>, I: 'static> Pallet<T, I> {
		fn do_remote_proxy(
			who: T::AccountId,
			real: T::AccountId,
			force_proxy_type: Option<T::ProxyType>,
			call: <T as pallet_proxy::Config>::RuntimeCall,
			proof: RemoteProxyProof<RemoteBlockNumberOf<T, I>>,
		) -> DispatchResult {
			let Some(real_remote) = T::RemoteProxy::local_to_remote_account_id(&real) else {
				return Err(Error::<T, I>::CouldNotConvertLocalToRemoteAccountId.into());
			};

			let def = match proof {
				RemoteProxyProof::RelayChain { proof, block } => {
					let roots = BlockToRoot::<T, I>::get();

					let Ok(storage_root) = roots
						.binary_search_by(|(b, _)| b.cmp(&block))
						.map(|pos| roots[pos].1.clone())
					else {
						return Err(Error::<T, I>::UnknownProofAnchorBlock.into());
					};

					let key = T::RemoteProxy::proxy_definition_storage_key(&real_remote);

					let db =
						sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>();
					let value = sp_trie::read_trie_value::<sp_trie::LayoutV1<_>, _>(
						&db,
						&storage_root,
						&key,
						None,
						None,
					)
					.ok()
					.flatten()
					.ok_or(Error::<T, I>::InvalidProof)?;

					let proxy_definitions = alloc::vec::Vec::<
						ProxyDefinition<
							RemoteAccountIdOf<T, I>,
							RemoteProxyTypeOf<T, I>,
							RemoteBlockNumberOf<T, I>,
						>,
					>::decode(&mut &value[..])
					.map_err(|_| Error::<T, I>::ProxyDefinitionDecodingFailed)?;

					let f = |x: &ProxyDefinition<
						T::AccountId,
						T::ProxyType,
						BlockNumberFor<T>,
					>|
					 -> bool {
						x.delegate == who &&
							force_proxy_type.as_ref().is_none_or(|y| &x.proxy_type == y)
					};

					proxy_definitions
						.into_iter()
						.filter_map(T::RemoteProxy::remote_to_local_proxy_defintion)
						.find(f)
						.ok_or(Error::<T, I>::DidNotFindMatchingProxyDefinition)?
				},
			};

			ensure!(def.delay.is_zero(), Error::<T, I>::Unannounced);

			Self::do_proxy(def, real, call);

			Ok(())
		}
