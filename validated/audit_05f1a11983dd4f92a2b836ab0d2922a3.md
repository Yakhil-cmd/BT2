### Title
Unvalidated `creator` identity field in `InitializeWithPermission` allows permanent freezing of creator trading fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`InitializeWithPermission` accepts a `creator` account that is declared as `UncheckedAccount<'info>` rather than `Signer<'info>`, and its raw pubkey is written directly into `PoolState.pool_creator` without any proof that the entity controlling that pubkey ever authorized or signed the transaction. This mirrors the RaptorCast root cause: an identity field carried in a message/instruction (`creator`) is never checked against the actual signer/key that produced the transaction.

### Finding Description
In `InitializeWithPermission`, only `payer` is a `Signer`; `creator` is unchecked: [1](#0-0) 

The unvalidated `creator.key()` is then persisted as the pool's permanent `pool_creator` identity: [2](#0-1) 

This is different from the sibling `initialize` instruction, where the equivalent identity (`creator`) *is* required to be a `Signer`, so `pool_creator` there is always the transaction's own key: [3](#0-2) [4](#0-3) 

`pool_creator` subsequently gates who may withdraw accrued `creator_fees_token_0/1`:
- `CollectCreatorFee` requires `creator` to match `pool_state.pool_creator` **and** be a `Signer`: [5](#0-4) 
- `CollectCreatorFeePermissionless` lets *anyone* trigger a payout, but the destination ATA authority is fixed to `pool_state.pool_creator`: [6](#0-5) [7](#0-6) 

Because `initialize_with_permission`'s `creator` field is never checked to be on-curve or to match any signing key, a permissioned caller (the `payer`, who only needs a valid `Permission` PDA — see `programs/cp-swap/src/instructions/admin/create_permission_pda.rs`) can set `creator` to an arbitrary 32-byte value, including an off-curve pubkey for which no private key exists and which is not a genuine PDA any program can sign for.

### Impact Explanation
Once `pool_creator` is permanently fixed to such an unsignable address:
- `CollectCreatorFee` can never succeed, because no keypair can produce a valid signature for that address (the `Signer` constraint can never be satisfied).
- `CollectCreatorFeePermissionless` will still succeed in moving funds, but it creates/transfers into an associated token account whose `authority` is the unsignable address, so the tokens become permanently unmovable — nobody can ever authorize a transfer out of that ATA.

`creator_fees_token_0/1` accrue from real swap volume via the constant-product fee split (`AmmConfig.creator_fee_rate`, `PoolState.creator_fees_token_0/1`): [8](#0-7) 

This means a fraction of every swapper's trade fee routed to the "creator" bucket for that pool is permanently and irrecoverably frozen — a concrete permanent freezing of user-derived funds, not merely a best-practice issue.

### Likelihood Explanation
Any account holding a `Permission` PDA (an unprivileged, explicitly in-scope pool-creation persona for this entry point) can trigger this in a single transaction by supplying an off-curve/unsignable pubkey as the `creator` account — no cost beyond normal pool-creation fees, no cooperation from a victim required, and no special program privilege beyond what `initialize_with_permission` already grants to permissioned callers.

### Recommendation
Require `creator` in `InitializeWithPermission` to be a `Signer` (mirroring `Initialize`), or, if delegated creator assignment is intentionally supported, explicitly validate that the supplied `creator` pubkey is on the ed25519 curve (rejecting PDA-shaped/unsignable addresses) before persisting it into `PoolState.pool_creator`, and/or require an explicit co-signed consent (e.g., the designated creator must also sign) before it is accepted as the fee-collection identity.

### Proof of Concept
1. Attacker (or any account with a valid `Permission` PDA) calls `initialize_with_permission`, supplying:
   - `payer` = attacker's own signer key.
   - `creator` = a deliberately generated off-curve 32-byte value (no corresponding private key exists), passed as the `creator` `UncheckedAccount`.
2. The instruction succeeds; `pool_state.initialize(..., ctx.accounts.creator.key(), ...)` writes this unsignable address into `PoolState.pool_creator`.
3. As swaps occur on the pool, `creator_fees_token_0/1` accumulate normally per the fee split logic.
4. Any attempt to call `CollectCreatorFee` fails permanently because the `Signer` constraint `address = pool_state.load()?.pool_creator` can never be satisfied by any real signer.
5. Calling `CollectCreatorFeePermissionless` succeeds in transferring the accrued fees into an ATA whose `associated_token::authority = creator` is the unsignable address — the funds land in an account nobody can ever move out of, permanently freezing that portion of trading fees.
