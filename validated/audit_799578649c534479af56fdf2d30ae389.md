## Confirmed multi-tenant Shipit setup analysis

The multi-tenant GitHub App configuration is exactly what makes this analog exploitable. `Shipit.github(organization:)` looks up a *per-organization* config keyed by the organization name and instantiates a distinct `GitHubApp` (with its own `webhook_secret`) for each org: [1](#0-0) [2](#0-1) . Each organization onboarded onto the Shipit GitHub App has its own webhook secret, which the org owner (or anyone able to configure a repo's webhook under an org they administer) legitimately possesses.

The webhook signature check binds the HMAC verification to `repository_owner`, derived straight from the untrusted JSON body (`repository.owner.login` or `organization.login`): [3](#0-2) [4](#0-3) . This only proves "the payload was signed with organization X's secret" — it does **not** constrain which repository the payload's handlers subsequently act on.

Every webhook handler resolves the target `Stack`/`Repository` from a *different, independently-controlled* field of the same payload: `payload.dig('repository', 'full_name')`, with no cross-check against `repository.owner.login`: [5](#0-4) , and identically in `PushHandler` [6](#0-5) , and all `PullRequest` handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `EditedHandler`, `LabelCapturingHandler`, etc.) [7](#0-6) [8](#0-7) . `Repository.from_github_repo_name` splits `owner/name` straight from that untrusted `full_name` string to find the DB row: [9](#0-8) .

### Title
Webhook signing organization is not bound to the repository the payload acts on, allowing cross-tenant forged GitHub events - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
In a multi-organization Shipit deployment, the webhook signature is verified against the secret of the organization named in `repository.owner.login` (or `organization.login`), but the handler that mutates state trusts a *separate* payload field, `repository.full_name`, to pick the `Stack`/`Repository` to act on. Because these two fields are never compared, an attacker who legitimately controls org `alice-org` (and thus its Shipit-configured `webhook_secret`) can craft and correctly sign a webhook whose `repository.full_name` names a victim org's repository (e.g. `victim-org/prod`), and Shipit will accept it as authentic for that victim repository.

### Finding Description
The binding that should hold is: `organization that authenticated (repository_owner used for verify_webhook_signature) == organization of the repository the handler writes to (repository.full_name owner)`. This equality is never enforced.

- `WebhooksController#verify_signature` selects the `GitHubApp`/secret using `repository_owner`, a value taken directly from the JSON body, and validates the HMAC against that secret: [10](#0-9) .
- Once verification passes, `create` dispatches the full raw payload to all registered handlers for the event, with no additional binding checks: [11](#0-10) .
- Every handler resolves its target purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`: [5](#0-4) .

Since Alice, as an onboarded org admin, knows (or can obtain, via the Shipit config for her own org) the `webhook_secret` used to sign requests for `alice-org`, she can POST a webhook payload directly to `/webhooks` (this endpoint is unauthenticated by design — GitHub calls it) where:
- `repository.owner.login` = `"alice-org"` (used only for HMAC secret selection),
- `repository.full_name` = `"victim-org/victim-repo"` (used by the handler to find the target stack).

She signs this payload with `alice-org`'s webhook secret. `verify_signature` passes because it only checks the secret belonging to `alice-org`. The handler then acts on `victim-org/victim-repo`.

### Impact Explanation
This crosses the "cross-repository writes" boundary called out as Critical impact. Concretely, using `push` events, Alice can trigger `GithubSyncJob` for a victim's stack with an attacker-chosen `expected_head_sha` [12](#0-11) , forcing spurious re-syncs / commit ingestion against another tenant's repository state on demand. Using `pull_request` events (`opened`, `closed`, `reopened`, `labeled`/`unlabeled`), she can forge provisioning/archival actions against victim `ReviewStack`s she has no access to — e.g. force-archiving or force-unarchiving a victim's review stack: [13](#0-12) [14](#0-13) . This is state manipulation across a tenant boundary using an identity/secret that was never supposed to authorize writes to that repository — a direct analog of the TrueFi report's core flaw (an entity permitted to act in one context is trusted to act in a different, unauthorized context because the two are never checked for equality).

### Likelihood Explanation
Likelihood is High in any deployment that uses the per-organization GitHub config keyed by `Shipit.github_app_config`/`TOP_LEVEL_GH_KEYS` (i.e., more than one org onboarded) [15](#0-14) . Any org admin able to view/manage their own org's Shipit webhook configuration already possesses the necessary secret; no elevated Shipit privilege, GitHub App private key, or `ApiClient` token is required — only the standard admin capability of the attacker's own onboarded organization, which is an unprivileged position relative to the victim's repositories.

### Recommendation
Bind the two identities together: after resolving `repository_owner` for secret selection, require that the exact same value equals the owner segment parsed from `payload.dig('repository', 'full_name')` before dispatching to handlers, rejecting the request (422) on mismatch. Equivalently, thread the already-verified `repository_owner` into `Webhooks::Handlers::Handler` and have `Repository.from_github_repo_name`/lookups reject repositories whose owner does not match.

### Proof of Concept
1. Shipit is configured with two orgs, `alice-org` and `victim-org`, each with distinct `webhook_secret` values under `secrets.github`.
2. Alice, an admin of `alice-org`, knows her org's `webhook_secret` (she configured or was given it to set up the GitHub webhook).
3. Alice crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "alice-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. She computes `X-Hub-Signature: sha1=HMAC-SHA1(alice-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "alice-org")` and validates successfully against the `alice-org` secret: [3](#0-2) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [5](#0-4)  and enqueues `GithubSyncJob` for the victim's stack with the attacker-supplied `expected_head_sha`, despite Alice never having presented `victim-org`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
