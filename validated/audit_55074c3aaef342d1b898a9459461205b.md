### Title
`provision?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` due to operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` is written as `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...) || (...)`. Ruby's `&&` binds tighter than `||`, so `review_stacks_enabled` is only ANDed into the first disjunct (`allow_all`) and is never consulted for the `allow_with_label` or `prevent_with_label` branches. Any repository configured with `provisioning_behavior: prevent_with_label` (a common, safe-seeming default) will provision a review stack for a PR opened by an untrusted fork owner even when `review_stacks_enabled` is `false`.

### Finding Description
Binding claimed: `provision? == true` should require `repository.review_stacks_enabled == true` for every `provisioning_behavior` value. Actual code: [1](#0-0) 

Due to precedence, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So for `provisioning_behavior_prevent_with_label?` (the presumed-safe default gate), `provision?` is true whenever the PR lacks the provisioning label, entirely independent of `review_stacks_enabled`. Similarly for `allow_with_label?`, it only requires the label, not `review_stacks_enabled`.

`respond_to_pull_request_opened?` gates only on `params.action == "opened" && provision?` — there is no check on `params.pull_request.user.login` or `params.sender.login` anywhere in the handler: [2](#0-1) 

When true, `process` immediately calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` using attacker-controlled `params.pull_request.head.ref` as the `branch`, and enqueues it for provisioning: [3](#0-2) 

**Attacker request**: any external GitHub user opens a real pull request against a repository tracked by Shipit (this is a completely ordinary, unprivileged GitHub action — no fork/PR restriction bypass needed, since accepting external PRs is the normal open-source workflow). GitHub sends a legitimately-signed `pull_request` `opened` webhook to `POST /webhooks`; the existing HMAC signature check passes because it is a genuine GitHub-originated webhook, not a forgery — the vulnerability is not in signature verification but in the authorization logic downstream of a valid webhook.

**Root cause**: a missing set of parentheses collapses the intended "review stacks must be enabled AND (one of the behavior conditions holds)" into "review stacks enabled only gates `allow_all`; the other two behaviors are unconditionally live." This exactly matches what the question describes and I confirmed it by reading the raw source.

Existing guards do not close this gap: webhook signature verification only authenticates that the event came from GitHub, not that the PR author is trusted; there is no `User#authorized?`/`require_permission!`/team-membership check anywhere in this handler or `ReviewStackAdapter`.

### Impact Explanation
Any unprivileged external GitHub user who can open a PR against a Shipit-tracked repository configured with `provisioning_behavior: prevent_with_label` (without adding the opt-out label) or `allow_with_label` (by adding a label they control on their own PR) can force creation and provisioning of a `ReviewStack` tied to their fork's branch — even when the maintainer has explicitly set `review_stacks_enabled: false`, believing review-stack provisioning is off. Provisioning queues run tasks that check out the PR branch and execute build/deploy commands on the deploy host, i.e., attacker-controlled code execution reachable purely from opening a PR — meeting the Critical bar (RCE-capable provisioning triggered by content the attacker fully controls). This is repeatable against every repository sharing that configuration, and each PR creates an independent stack, so the blast radius scales with the number of PRs the attacker opens.

### Likelihood Explanation
Preconditions: a Shipit-tracked repository with `provisioning_behavior` set to `prevent_with_label` or `allow_with_label` (both are non-`allow_all` "restricted" settings a maintainer would pick specifically to keep `review_stacks_enabled` meaningful for stricter control), and that repository accepting external pull requests (standard for open source). No secrets, tokens, or privileged roles are required — only the ability to open a PR, which is the exact attacker capability granted in scope. This makes the bug highly likely to be exploitable wherever it's misconfigured this way, with zero attacker cost beyond opening a PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three behaviors:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest plan (mirrors existing `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` structure):
1. Create a `Repository` fixture with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label`.
2. Build `params` via `payload_parsed(:pull_request_opened)`, setting `pull_request.user.login` and `sender.login` to a novel external login never seen before, and ensuring `pull_request.labels` does not include the provisioning label.
3. Assert binding before: `repository.review_stacks_enabled == false` and `repository.provisioning_behavior_prevent_with_label? == true`.
4. Call `OpenedHandler.new(...).process` (or trigger via webhook dispatch).
5. Assert `Shipit::ReviewStack.find_by(environment: "pr#{params.number}")` is **not nil** — proving a stack was created despite `review_stacks_enabled == false`, i.e., `provision?` returned `true` when it should have returned `false` per the intended binding.
