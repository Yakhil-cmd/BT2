### Title
Undeclared `flash_position` callback assets are permanently locked in the controller - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
`flash_position` snapshots and processes only the explicitly declared `collaterals` and `refund_assets`. Any other tokens transferred to the controller by the receiver callback are left uncredited and unrefunded, with no generic recovery endpoint.

### Finding Description
`flash_position` is an unprivileged controller entrypoint accepting a caller, flash-borrowed debt market, receiver contract, callback data, declared collateral list, and declared refund-asset list. [1](#0-0) 

After forwarding the borrowed tokens, the controller snapshots only the declared collateral assets and declared refund assets before invoking `execute_flash_position`. [2](#0-1) 

After the callback, the controller measures deposits only for entries in `collaterals`, then refunds only entries in `refund_assets`; an asset omitted from both lists is never inspected. [3](#0-2) 

`collect_collateral_deposits` iterates exclusively over the declared collateral list, while `refund_listed_assets` iterates exclusively over the declared refund list. [4](#0-3) [5](#0-4) 

The refund helper transfers only the measured positive balance delta for the supplied asset, so it cannot recover an undeclared token accidentally left in the controller. [6](#0-5) 

### Impact Explanation
A user or integrating contract can permanently lose tokens by returning an undeclared asset, returning extra borrowed debt without listing it for refund, or omitting a delivered collateral asset from `collaterals`. The funds remain owned by the controller while the transaction can still satisfy all collateral minimums and account-risk checks. [7](#0-6) 

The protocol explicitly has no controller sweep endpoint for undeclared callback assets, so the transferred balance remains stranded rather than becoming account collateral or protocol revenue. [8](#0-7) 

### Likelihood Explanation
This requires the caller’s own receiver or integration to send an asset that was not included in either list, so it is a user/integration error rather than a remote theft primitive. It is plausible because the API separates collateral declarations from refund declarations and does not reject undeclared controller balance increases. [9](#0-8) [3](#0-2) 

### Recommendation
Reject callbacks that increase the controller balance of any token absent from `collaterals` and `refund_assets`, or provide a bounded allowlist/snapshot mechanism that refunds all callback-delivered assets. At minimum, return excess debt tokens to the caller or apply them to the flash-created debt instead of leaving them in controller custody. [3](#0-2) 

### Proof of Concept
1. Configure a flash-loanable debt market `D`, a supplyable collateral market `C`, and an additional listed token `E` in the same hub/spoke.
2. Deploy a receiver whose `execute_flash_position` callback transfers enough `C` to meet its declared minimum and also transfers a positive amount of `E` to the controller.
3. Call `flash_position(caller, 0, spoke_id, PositionMode::Multiply, D, amount, receiver, data, [(C, min)], [])`.
4. The transaction snapshots only `C` because `refund_assets` is empty and `E` is not in `collaterals`. [10](#0-9) 
5. The callback’s `E` transfer succeeds; the controller then deposits only `C` and performs no refund iteration for `E`. [3](#0-2) 
6. Finalization succeeds because the account retains debt and collateral, leaving `E` held by the controller without an accessible recovery path. [11](#0-10) [12](#0-11)

fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
    deposits

Pool supply measures receipts again. Borrow and supply caps are checked when each pool result merges into the account. Supply and the declared debt position must remain open after finalization.

Refund assets must be unique, listed in the debt hub and account spoke, disjoint from collateral declarations, and bounded by the maximum supply-position count. Refund eligibility requires an active spoke and an existing listing; it does not check collateralizable, borrowable, paused or frozen flags. Only positive balance changes above pre-callback balances return to the caller. The debt token can be a refund asset, but refunding it does not repay the minted debt.

Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint. Refunds produce token transfer events, without a dedicated controller refund event.
