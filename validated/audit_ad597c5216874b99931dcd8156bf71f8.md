### Title
Webhook signature verification is scoped to `repository.owner.login`, but the target repository/stack acted upon is resolved from the independent `repository.full_name` field, allowing spoofed events for repositories under a different GitHub organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App configuration (and therefore the `webhook_secret` used to validate the HMAC) using the `repository.owner.login`/`organization.login` field of the *unverified* JSON body. The event handlers, however, resolve the actual `Repository`/`Stack` that the webhook acts on from a separate, independently-controlled field: `repository.full_name`. Nothing in the code enforces that these two values refer to the same organization, so the "organization that authenticated" and the "repository that is written" are not bound together.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and asks `Shipit.github(organization: repository_owner)` for the app config used to check the signature: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` fails open whenever the resolved organization has no configured `webhook_secret` (a supported, documented configuration state, as shown by the shipped example configs and templates that leave `webhook_secret:` blank): [3](#0-2) [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, every registered `Webhooks::Handlers::Handler` resolves the repository/stack to act on using `payload.dig('repository', 'full_name')` — a value never checked against `repository.owner.login`: [6](#0-5) 

For the `push` event, this repository is used to look up all non-archived stacks matching the branch and unconditionally trigger a GitHub sync with an attacker-chosen `after` (head) SHA: [7](#0-6) 

Root cause: the equality that should hold — `organization that signed/authenticated == organization owning the repository/stack acted upon` — is never enforced. `repository_owner` (used to select the verifying secret) and `repository.full_name`'s owner segment (used to select the acted-upon `Repository`) are two independent, attacker-supplied strings in the same JSON body.

### Impact Explanation
If any GitHub organization configured on the Shipit instance has no `webhook_secret` set (a state the shipped configuration templates explicitly support), an unprivileged attacker can send a forged webhook with `repository.owner.login` set to that unsecured organization (making `verify_webhook_signature` return `true` unconditionally) while setting `repository.full_name` to `victim-org/victim-repo`. This lets the attacker drive `GithubSyncJob`/stack state for a repository/organization that never authorized or signed the request, without possessing that organization's `webhook_secret`. This crosses the "organization authenticated vs repository written" trust boundary the engine is supposed to enforce at the webhook boundary.

### Likelihood Explanation
Requires only that the Shipit deployment has at least one GitHub organization/app entry configured without a `webhook_secret` — a state explicitly supported and shown as a valid example in the repo's own configuration templates, so it is a realistic multi-tenant misconfiguration rather than a purely theoretical one. No GitHub credentials, session, or API token are needed by the attacker; the request is a plain unauthenticated HTTP POST to `/webhooks`.

### Recommendation
Bind the two identities together: verify that `repository.owner.login` (or `organization.login`) used to select the verifying app/secret matches the owner segment of `repository.full_name` used by handlers before dispatching to `Shipit::Webhooks.for_event`. Additionally, make `GitHubApp#verify_webhook_signature` fail closed (reject) rather than return `true` when no `webhook_secret` is configured, unless that behavior is an intentionally-accepted risk that operators are warned about in the setup docs.

### Proof of Concept
1. Deploy Shipit with two configured organizations: `unsecured-org` (no `webhook_secret`) and `victim-org` (real stacks, has repos synced from GitHub).
2. POST to `/webhooks` with header `X-Github-Event: push`, a `X-Hub-Signature` of any value, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus signature header.
4. `PushHandler#process` resolves the target stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (from `repository.full_name`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on `victim-org`'s stack despite the request never being authenticated as `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
