### Title
Cross-Organization Webhook Trust Confusion — Signature Verified Against `repository.owner.login`/`organization.login`, But Payload Processing Trusts Unrelated Fields (`repository.full_name`, `sha`) — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate an inbound webhook's HMAC using only `repository.owner.login` (falling back to `organization.login`) from the attacker-controlled JSON body. Once that check passes, `WebhooksController#create` hands the *entire same JSON body* to event handlers that select which local records to mutate using **different, unvalidated fields** of that body (`repository.full_name`, or in the case of `StatusHandler`, nothing more than a bare `sha`). Nothing ties the field used for signature-secret-selection to the field(s) used for target-selection, so a party who legitimately owns a webhook secret for *one* configured GitHub organization can forge a validly-signed payload that is processed against a completely different organization's repository/stack.

### Finding Description
`Shipit` supports multiple GitHub Apps, one per organization, each with its own `webhook_secret` [1](#0-0) [2](#0-1) .

The signature check picks the app/secret to verify against using only the `repository.owner.login` (or `organization.login`) field of the untrusted JSON body: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` only proves the raw body was HMAC-signed with *that organization's* secret — it says nothing about which repository/commit the body's other fields should be trusted to act on: [5](#0-4) 

Once `verify_signature` passes, `create` re-parses the same raw body and dispatches it, unmodified, to the registered handlers for the event type: [6](#0-5) 

Handlers pick their operating scope from **other** fields of the identical body, with no cross-check against the field that was used to select the signing secret:
- The generic `Handler` base class resolves the target `Repository` via `repository.full_name`, a field independent from `repository.owner.login`/`organization.login`: [7](#0-6) 
- `StatusHandler`, used for the `status` event, is even less scoped: it looks up commits **globally by `sha` alone**, with no repository/organization filter at all: [8](#0-7) 
- `PushHandler` likewise operates on `stacks` derived from `repository.full_name` via the shared `stacks` helper, not from the value used to pick the webhook secret: [9](#0-8) 

This is structurally identical to the reported bug class: one function (`_updateNthByte`/here, `verify_signature`) treats a "position" (here, `repository.owner.login`) as the authority-selecting key, while a different function (`_decodeNthByte`/here, the event handlers) treats an unrelated field of the same encoded blob (`repository.full_name`, `sha`) as the effective target, breaking the intended binding between "the organization that authenticated" and "the repository that is written."

### Impact Explanation
Any party who has legitimately created/administers a GitHub App for **their own** organization configured in Shipit (i.e., who knows only their own org's `webhook_secret` — not a privileged Shipit secret) can:
1. Craft a JSON body with `repository.owner.login` (or `organization.login`) set to their own org, so `verify_signature` selects their own `GitHubApp` and the HMAC they compute with their known secret passes.
2. Set unrelated payload fields — `repository.full_name` for push/PR/membership events, or simply `sha` for status events — to values belonging to a victim organization's stack/commit that they do not administer.
3. Have the forged event processed against the victim's data: e.g., forging a `status` event to attach a fabricated **successful CI status** to an arbitrary commit SHA in someone else's stack, which can satisfy `ci.require`/`merge.require` gating and enable an unauthorized deploy or merge [8](#0-7) ; or forging a `push`/`membership` event to trigger syncs, team membership changes, or PR-driven review-stack provisioning against a repository outside the attacker's authorized organization.

This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope, and the CI-status-forgery path can produce an unauthorized deploy/rollback — a Critical-tier impact per the given rules.

### Likelihood Explanation
Exploitation only requires: (a) Shipit configured with multiple GitHub organizations (a documented, supported configuration [1](#0-0) ), and (b) the attacker being a legitimate administrator/owner of any one of those configured organizations' GitHub Apps — not a privileged Shipit operator, GITHUB_TOKEN holder, or Shipit `ApiClient`. No repository write access or Shipit session is needed; only knowledge of one's own already-issued webhook secret and the ability to send an HTTP POST to the public `/webhooks` endpoint. The `status` event path (`StatusHandler`) is trivial to exploit because it requires guessing/knowing only a commit SHA (often public), with zero repository scoping at all.

### Recommendation
Bind webhook target-resolution to the same identity used for signature verification:
- Reject/ignore any handler processing where `repository.full_name`'s owner segment (or `organization.login`) does not match the organization whose secret validated the signature.
- In `StatusHandler`, scope the `Commit.where(sha:)` lookup by the repository/stack derived from the verified organization, not by a bare, globally-unscoped SHA.
- Consider passing the verified organization identity from `WebhooksController#verify_signature` down into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` and have `Handler` assert consistency before mutating any record.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with its own webhook secret (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the legitimate owner/admin of `OrgA`'s GitHub App (who knows `OrgA`'s `webhook_secret`), craft a `status` event JSON body:
```json
{
  "sha": "<commit sha belonging to a stack under OrgB>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `OrgA`, fetches `Shipit.github(organization: 'OrgA')`, and the HMAC validates successfully (attacker legitimately knows this secret) [3](#0-2) .
5. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, matching the OrgB commit globally, and creates a forged successful status on it [8](#0-7) , potentially unblocking `ci.require`/`merge.require` gates for OrgB's stack despite the attacker never having any credential or access tied to OrgB.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
