### Title
Cross-tenant CI status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook event, once authenticated against the sending organization's GitHub App webhook secret, is applied to **every** `Commit` record in the entire Shipit database that matches the raw `sha` field, with no check that the commit's stack/repository belongs to the organization the signature was verified for. This mirrors the reported bug class: a value (the sha-addressed commit) is *acted upon* by the handler, but the *binding* that was actually cryptographically verified (the sending organization's identity) is never checked against the object being mutated.

### Finding Description
Signature verification and event dispatch are two separate steps in `WebhooksController`:
- `verify_signature` derives `repository_owner` from the payload (`params.dig('repository','owner','login')`) and validates `X-Hub-Signature` using only that organization's `webhook_secret`: [1](#0-0) 
- After the signature check passes, `create` blindly hands the full, attacker-influenced `params` to every registered handler for the event: [2](#0-1) 

`StatusHandler`, the handler for the `status` event, then updates commit CI status purely by matching `sha` across the whole `Commit` table, with **no scoping to the repository/organization whose secret validated the request**: [3](#0-2) 

The equality the code implicitly assumes is:
`organization whose webhook_secret verified the signature == repository that owns the commit being mutated`

This equality does not hold: verification only proves "this payload came from GitHub for organization X" (based on `repository.owner.login` in the same untrusted JSON body), while the write (`commit.create_status_from_github!`) touches any `Shipit::Commit` row with a matching `sha`, regardless of which stack/repository owns it. Because git commit SHAs are content-addressed and identical commits routinely exist across multiple repositories tracked by the same Shipit instance (forks, mirrors, shared subtree history, multiple orgs pointing to the same upstream, per the documented multi-org support in `docs/setup.md`), an organization/repo that is legitimately onboarded to a shared Shipit instance can produce a validly-signed `status` webhook (from its own GitHub App installation, entirely within its rights) whose `sha` happens to also identify a commit tracked under a different organization's stack.

### Impact Explanation
`Commit#create_status_from_github!` writes the reported CI state (`success`/`failure`/`pending`) that stack safety machinery relies on to determine whether a commit is deployable and mergeable (via merge-queue `required_statuses`/`StatusChecker`). If a low-privilege, cross-tenant actor (an org owner of any org configured on the shared Shipit instance) can inject a forged `success` status onto a commit belonging to a *different* organization's stack, they can flip that commit to "deployable"/"mergeable" without it ever having passed the victim's actual CI, directly leading to an unauthorized deploy or unauthorized auto-merge of unreviewed/failing code in a repository they do not control. This satisfies the Critical bar of "an unauthorized deploy, rollback or merge," because the write is cross-repository despite passing signature verification legitimately for the attacker's own tenant.

### Likelihood Explanation
Exploitation does not require a stolen `webhook_secret`, GitHub App key, or Shipit session — the attacker only needs legitimate GitHub write access to a repository/organization that is one of possibly many tenants configured in the multi-org `github:` section documented in `docs/setup.md`, and they need a commit sha collision with the victim stack. Real-world sha collisions across tenants occur through forks, shared upstream history, or copied commits (cherry-pick preserving identical trees, or a victim occasionally re-pushing a public commit also present in the attacker's fork) — not requiring a SHA1 preimage break. Likelihood is therefore moderate: it requires a specific multi-tenant deployment topology and a shared/forked commit history between the attacker's and victim's repositories, but no privileged credential.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed webhook handler) to commits whose `stack.repository` matches the `repository`/`organization` that the signature was verified against, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner_from_verified_payload })`, rather than a bare `Commit.where(sha: ...)` lookup across the entire instance.

### Proof of Concept
1. Configure a shared Shipit instance for two GitHub organizations, `victim-org` and `attacker-org`, per the multi-org `github:` config in `docs/setup.md`.
2. `attacker-org` forks (or shares history with) a repository that also exists as `victim-org/app`, so a commit with sha `abc123...` is tracked as a `Shipit::Commit` under both stacks.
3. From `attacker-org`'s legitimately configured GitHub App, send a real `status` webhook event (validly signed with `attacker-org`'s `webhook_secret`) reporting `state: success` for sha `abc123...`.
4. `WebhooksController#verify_signature` succeeds because the signature is valid for `attacker-org`. `StatusHandler#process` (`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }`) then updates the CI status on **both** the attacker's and the victim's `Commit` row for that sha, including `victim-org/app`'s commit — even though the webhook was never signed by `victim-org`'s webhook secret.
5. If `victim-org/app`'s deploy/merge-queue gating depends on this status becoming green, the victim stack now considers the commit deployable/mergeable despite no CI ever running for it in `victim-org`.
