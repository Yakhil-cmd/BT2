## Title
Webhook signature verified against an attacker-chosen `repository.owner`/`organization` login while handlers act on a different `repository.full_name` — cross-repository status/write forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and thus which `webhook_secret`) to validate a webhook against using a field the attacker controls, while the event handlers act on a different, unrelated field from the same payload. This breaks the intended binding "the organization whose secret verified this request" == "the repository the handler subsequently writes to."

### Finding Description
`verify_signature` derives the organization used to select the verifying secret purely from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GithubApp`/`GithubOrganizationApp` instance configured per-organization, and `verify_webhook_signature` intentionally treats an unconfigured secret as automatically valid: [3](#0-2) 

This "no secret configured -> always verified" behavior is a supported, documented configuration state, not a hardening bypass — the shipped example config explicitly ships `webhook_secret: # nil` for an organization, including in the documented multi-organization schema: [4](#0-3) 

Meanwhile, every webhook handler resolves the target `Repository`/`Stack`/`Commit` using a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

So the equality the code implicitly assumes — `organization authenticated by verify_signature == organization that owns the repository being written` — does not hold: `repository_owner` (used to pick the secret) and `repository.full_name` (used to pick the target Stack/Commit) are independent, attacker-controlled fields inside the same JSON body being forged.

### Impact Explanation
If a Shipit deployment manages multiple GitHub organizations (a documented, supported configuration) and any one of them has no `webhook_secret` configured — which the shipped example config explicitly demonstrates as a valid state — an unauthenticated attacker can:
1. Set `repository.owner.login` (or `organization.login`) to the org with no configured secret, so `verify_webhook_signature` returns `true` unconditionally.
2. Set `repository.full_name` to any other repository tracked by the Shipit instance, including ones belonging to organizations that *do* have secrets configured.
3. Have the corresponding handler (e.g. `StatusHandler`) act on that unrelated repository's data — for instance forging a passing commit `Status` via `Commit#create_status_from_github!`, which Shipit's deploy-safety mechanisms consult when deciding whether a commit is deployable.

This can enable an unauthorized deploy by satisfying commit-status-based safety gates on a repository the attacker has no legitimate relationship with, without possessing any secret, session, or API token for that repository's organization — a direct violation of the "organization authenticated vs. repository written" binding called out in scope.

### Likelihood Explanation
Exploitability depends entirely on host configuration: it requires at least one configured GitHub organization in the Shipit instance to have `webhook_secret` unset. This is not a hypothetical edge case — it is the documented default/example configuration shipped in the repo, and organizations without any need for GitHub-side webhook signing (e.g. quickly bootstrapped ones) are realistically left with a blank secret. Given that, the attack requires no credentials at all: only knowledge of a second, target repository's `full_name` tracked by the same Shipit instance, which is discoverable via the public Shipit UI/API endpoints.

### Recommendation
Bind webhook trust to the repository actually acted upon rather than to an attacker-supplied organization login:
- Resolve the target repository first (via `repository.full_name`), then look up that repository's actual owning organization from Shipit's own `Repository` records (not from the payload) to select the verifying `webhook_secret`.
- Refuse to treat a missing `webhook_secret` as automatically "verified" for organizations that have other repositories under management with configured secrets, or require an explicit opt-in flag for "signature verification disabled" instead of silently trusting an unset secret.
- Reject any webhook where `repository.owner.login` does not match the owner segment implied by the resolved repository/organization.

### Proof of Concept
Assume Shipit tracks `secure-org/protected-repo` (organization `secure-org` has a `webhook_secret` configured) and also has organization `no-secret-org` configured with `webhook_secret: nil` (per the documented example config).

```
POST /github_webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": {
    "full_name": "secure-org/protected-repo",
    "owner": { "login": "no-secret-org" }
  },
  "sha": "<sha of a commit pending on protected-repo>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "created_at": "2026-09-01T00:00:00Z"
}
```

- `WebhooksController#verify_signature` resolves `repository_owner` = `"no-secret-org"`, calls `Shipit.github(organization: "no-secret-org")`, and `verify_webhook_signature` returns `true` because that org has no `webhook_secret` set — no `X-Hub-Signature` header needed at all.
- `StatusHandler#process` (via `Handler#stacks`/`Commit.where(sha:)`) is completely independent of `repository_owner` and instead operates on the commit identified by `sha`, which belongs to `secure-org/protected-repo`, forging a successful CI status for that commit without ever possessing `secure-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
