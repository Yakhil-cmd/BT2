### Title
Webhook signature is verified against the org named in the payload, but `StatusHandler` never checks that the payload's repository matches any stack — allowing a holder of *any* configured org's `webhook_secret` to forge CI status for commits belonging to a different repository/org - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify a request against using a field taken from the same untrusted JSON body it is supposed to authenticate (`repository.owner.login`, falling back to `organization.login`), and never re-checks that this "authenticating org" is the same org that owns the repository the handler subsequently mutates. `StatusHandler`, unlike `PushHandler`/`CheckSuiteHandler`, doesn't even scope by repository at all — it looks up commits by bare SHA across the whole install. This breaks the same "who authenticated" vs "what gets written" binding that made the reward-token report analogous.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to check the HMAC against based on `repository_owner`, which is parsed straight out of the unauthenticated JSON payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization `webhook_secret` config, which is explicitly documented/supported for multi-tenant installs where several distinct GitHub orgs are configured, each with its own app/secret: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` is a plain HMAC-SHA1 check of the raw body against that org's secret: [5](#0-4) 

Because `repository_owner` (used to pick the secret) and `repository.full_name` (used later to identify the target repo/stack) are both attacker-controlled fields inside the *same* JSON body, nothing forces them to refer to the same organization. Anyone who legitimately controls one org configured in this Shipit instance (installed their own GitHub App / knows that org's `webhook_secret`) can craft a body where `repository.owner.login` is their own org (so the correct/known secret is used and the signature check passes) while `repository.full_name` names a repository belonging to a *different* configured org.

`Handler#stacks`/`#repository_name` do use `repository.full_name` to scope which stacks are touched: [6](#0-5) 

`PushHandler` and `CheckSuiteHandler` go through that scoping, so a forged push/check_suite payload with a mismatched `owner.login` vs `full_name` would still resolve to the actual target repo/stack (`Repository.from_github_repo_name(repository_name)`), i.e., the "org authenticated" vs "repo written" binding is broken there too.

`StatusHandler` is worse: it doesn't use `repository_name`/`stacks` scoping at all — it looks up `Commit` purely by SHA, globally, across every stack in the installation: [7](#0-6) 

So as soon as *any* valid signature is produced (for whichever org's secret the attacker knows), `commit.create_status_from_github!(params)` will set a GitHub-style commit status on any commit in the entire Shipit install that happens to share that SHA — with no relationship to the org/secret that produced the valid signature at all.

### Impact Explanation
Commit statuses gate deploy safety checks: `Api::DeploysController#create` uses `commit.deployable?` when `require_ci` is requested, and continuous-deployment scheduling (`Stack.schedule_continuous_delivery`) relies on release/status checks before auto-deploying: [8](#0-7) [9](#0-8) 

A party who only controls the webhook secret for one org configured on a shared/multi-tenant Shipit instance can forge "success" CI statuses for commits on stacks belonging to a completely different org, tricking `require_ci`-gated deploys or continuous-deployment stacks into treating an unreviewed/unsafe commit as deployable — an unauthorized deploy path. This satisfies the report's "unauthorized deploy" Critical-tier impact category. I was not able to fully trace `Commit#deployable?`'s exact status-name/context matching logic in this session (index/iteration limits), so I cannot state with certainty which specific `context`/`state` values are required to flip `deployable?`, but the code shown proves the SHA is looked up with zero repository scoping and the signature check is decoupled from the repo being mutated, which is the core trust-binding break.

### Likelihood Explanation
This requires the deployment to be configured in the documented multi-org mode (`config/secrets.development.example.yml`, `docs/setup.md`), which is an explicitly supported first-class configuration, not a misconfiguration. Any org admin who can install/configure a GitHub App against this shared Shipit instance (a normal, low-privilege onboarding action, not requiring a Shipit account or `ApiClient` token) gains the ability to forge webhook signatures for their own org and can immediately drive `StatusHandler` (unscoped) and craft `full_name` mismatches against `PushHandler`/`CheckSuiteHandler`.

### Recommendation
- Verify the webhook signature using the org derived from a trusted source (e.g. the GitHub App installation associated with the request, not `repository.owner.login`/`organization.login` taken from the unauthenticated body), or at minimum, after selecting the org's secret, assert that `repository.full_name`'s owner equals `repository_owner`.
- Scope `StatusHandler` (and any other handler that doesn't already) through `Handler#stacks`/`repository_name`, so a commit status can only be applied to commits belonging to the repository named in the verified payload.
- Consider binding the per-repo `GithubHook#secret` fixture data still present in the schema, if a per-repository shared secret is intended.

### Proof of Concept
Given a Shipit install configured with two orgs (`attacker-org`, `victim-org`), each with its own `webhook_secret` (per `config/secrets.development.example.yml`), and where `attacker-org`'s secret is known to the attacker (they installed/administer that org's GitHub App):

1. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` — this is possible entirely offline since they know their own org's secret.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and the signature check passes: [1](#0-0) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter and applies the forged "success" status to the victim commit: [10](#0-9) 
5. A user of `victim-org`'s stack subsequently deploys with `require_ci: true` (or continuous deployment fires), treating the forged status as legitimate CI approval for a commit that never actually passed CI in `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
