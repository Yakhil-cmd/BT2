### Title
Unbounded iteration over the growing in-memory unstable-units set in `data_feeds.dataFeedExists`/`readDataFeedValue`, triggered on every AA `data_feed`/`in data feed` evaluation - (File: data_feeds.js)

### Summary
`data_feeds.js` implements the `data_feed`/`in data feed`/`in_data_feed` oscript operations that AAs use to read oracle values. When the lookup is allowed to include unstable data (the `bAA`/`unstable_opts` path), both `dataFeedExists` and `readDataFeedValue` perform a full `for...in` scan over `storage.assocUnstableMessages`, the in-memory map of *every currently-unstable unit in the DAG*, instead of using an indexed/bounded lookup. This is structurally the same anti-pattern flagged in the external report: an ever-growing collection is iterated in full on every check (there, `consentCheck` over MetaVesT sets; here, the unstable-messages map on every AA data-feed read), so the cost of a single AA trigger response grows with the size of the mempool of unstable units, which is influenced by ordinary unit posting activity network-wide.

These loops iterate `for (var unit in storage.assocUnstableMessages)`, i.e. every unit that is not yet stable anywhere on the network, checking `objUnit.author_addresses` against the oracle address list and scanning that unit's messages for a matching `data_feed` app message. `storage.assocUnstableMessages` and the companion `assocUnstableUnits` maps grow with the number of outstanding unstable units and are only pruned as units stabilize; they are populated for every unit written via `writer.js`/`main_chain.js` regardless of author, so any unprivileged party can post ordinary units (in particular ones with `data_feed` messages) to inflate the size of this set network-wide.

This code path is reached from formula evaluation for AAs: [3](#0-2) 
Any AA whose oscript uses `data_feed[[...]]` (or `in data feed`) with the unstable-inclusion option triggers this scan on every single primary/secondary trigger, which is driven by ordinary payments/messages sent by any user — the "unprivileged AA trigger sender" actor explicitly in scope.

### Impact Explanation
Because the loop bound (`storage.assocUnstableMessages` size) is controlled by aggregate network unit-posting activity rather than by the AA or its caller, the per-trigger CPU cost of any AA using unstable-data-feed reads scales with total outstanding unstable units. As the number of unstable units grows (e.g., during high throughput, temporary stabilization delays, or if an attacker deliberately keeps many units with `data_feed` payloads outstanding by controlling timing/witnessing), every AA response computation that touches this operation becomes slower. Since AA trigger handling is on the node's synchronous stabilization/response path (`aa_composer.js` calls formula evaluation while holding the `aa_triggers`/write mutex), a sufficiently large unstable set can materially slow down or stall AA response processing for the whole node, risking the same class of outcome described in the report: growing resource consumption on a hot, unavoidable code path that ordinary (unprivileged) activity can inflate, potentially degrading the node's ability to process/confirm AA responses in a timely manner.

### Likelihood Explanation
Likelihood is moderate: it requires no special privilege — any user can define an AA that reads unstable oracle data via `data_feed`/`in data feed`, and any user can post ordinary units (including `data_feed` messages) to grow `assocUnstableMessages`. The bound is a real-time property of network activity (unstable unit count before stabilization), which fluctuates but is not otherwise capped in this code path, unlike other formula constructs in the same file that were explicitly guarded with size/complexity limits (see the `array`/`dictionary` length caps in `formula/evaluation.js`). Exploitability to a severe DoS depends on how large the unstable set can practically grow before stabilization catches up, which was not independently confirmed here.

### Recommendation
Avoid full in-memory scans of `assocUnstableMessages` for oracle lookups. Options:
- Maintain a secondary index (e.g., a map keyed by `feed_name` and/or oracle address to the list of unstable units posting that feed) that is updated incrementally as units are added/stabilized, so lookups are O(matches) rather than O(all unstable units).
- Bound/limit how many unstable units are scanned per lookup, with a defined fallback behavior once the bound is exceeded, so the cost per AA trigger is capped regardless of mempool size.

### Proof of Concept
Conceptual (not independently executed):
1. Deploy an AA whose oscript contains `data_feed[[oracles="ORACLE_ADDR", feed_name="X", ifseveral="last"]]` or an `in data feed` condition evaluated with unstable inclusion.
2. Have many unprivileged accounts post ordinary units (including some `data_feed` app messages) in a short window so that `storage.assocUnstableMessages` accumulates a large number of entries before the units stabilize.
3. Trigger the AA repeatedly (any unprivileged payment to the AA address).
4. Each trigger causes `readDataFeedValue`/`dataFeedExists` to iterate the full, currently-inflated `assocUnstableMessages` map [2](#0-1) , so the AA response latency scales with the size of that map, which was driven up purely by unprivileged unit posting.
