### Title
Unit fee bypass via declared vs. actual `data_length` mismatch in `temp_data` messages - (File: object_length.js)

### Summary
`extractTempData()` in `object_length.js` computes the payload commission for `temp_data` messages using the attacker-declared `payload.data_length` field rather than the actual byte length of `payload.data`. Since `getTotalPayloadSize()` strips out the real `data` field and substitutes a fee based solely on the declared `data_length`, an attacker can post a unit whose declared `data_length` diverges from the real data size, causing the computed payload commission to not correspond to the actual payload size actually stored/broadcast.

### Finding Description
`getTotalPayloadSize()` calls `extractTempData(objUnit.messages)`, which, for every `app === "temp_data"` message, reads `m.payload.data_length` as a trusted number and adds `data_length + 4` to `temp_data_length`, then deletes the real `data` field from the copy used for length/hash computation: [2](#0-1) 

The final payload size returned is `Math.ceil(temp_data_length * constants.TEMP_DATA_PRICE) + getLength({messages: messages_without_temp_data}, bWithKeys)`: [3](#0-2) 

This mirrors the libming bug class directly: the code trusts a size/length field embedded in attacker-supplied structure (`data_length`) instead of deriving the fee from the actual content (`data`), and the real content is discarded from the calculation entirely (analogous to decompileJUMP trusting the file's declared size header over the actual buffer size). If `data_length` does not match the true size of `data`, the derived `payload_commission`/`oversize_fee` charged to the unit will not reflect the unit's true payload size.

### Impact Explanation
`payload_commission` directly determines the network fee owed by a unit and factors into `MAX_UNIT_LENGTH` size-limit enforcement: [4](#0-3) 
If `data_length` can be set independently of the real `data` size (underreported), an attacker could pay less commission than the unit's actual size warrants and/or evade the `MAX_UNIT_LENGTH` cap, letting oversized `temp_data` payloads bypass anti-spam/size-limit protections — a resource/fee-bypass issue reachable by any unit poster.

### Likelihood Explanation
The `temp_data` message type and its `payload.data_length`/`payload.data` fields are attacker-controlled inputs of a publicly postable unit (no privileged access required), and `extractTempData` unconditionally trusts the declared length while dropping the real content from the size computation used to enforce `payload_commission` and unit-size caps, making this straightforward to trigger with a single crafted unit.

### Recommendation
In `extractTempData()`, validate that `m.payload.data_length` equals the actual byte length of `m.payload.data` (e.g., `Buffer.byteLength(m.payload.data)`) before trusting `data_length` for commission calculation, and reject/flag the unit as invalid if they diverge, rather than silently substituting the declared value.

### Proof of Concept
1. Compose a unit with a `temp_data` message where `payload.data` is a large string (e.g., 100 KB) but `payload.data_length` is declared as a small value (e.g., 10).
2. Submit the unit; `getTotalPayloadSize()` computes `payload_commission` using the declared `data_length` (10 + 4) rather than the real 100 KB content, since the real `data` is stripped from the length computation in `messages_without_temp_data`.
3. The unit passes the `payload_commission` check and `MAX_UNIT_LENGTH` size check with a far lower commission/size than its true payload actually represents, evading the size-based anti-spam protection intended by `validation.js`'s `objUnit.headers_commission + objUnit.payload_commission > constants.MAX_UNIT_LENGTH` check.

*(Note: I was unable to fully trace how `payload.data` is subsequently consumed by other subsystems (e.g., whether it is persisted, streamed, or referenced elsewhere with size assumptions based on `data_length`), since the index does not include every consumer of `temp_data` payloads. A full Devin session with repository access would be needed to confirm all downstream effects of this mismatch, such as whether it can be leveraged beyond a commission/size-cap bypass.)*

function extractTempData(messages) {
	let temp_data_length = 0;
	let messages_without_temp_data = messages;
	for (let i = 0; i < messages.length; i++) {
		const m = messages[i];
		if (m.app === "temp_data") {
			if (!m.payload || typeof m.payload.data_length !== "number") // invalid message, but we don't want to throw exceptions here, so just ignore, and validation will fail later
				continue;
			temp_data_length += m.payload.data_length + 4; // "data".length is 4
			if (m.payload.data) {
				if (messages_without_temp_data === messages) // not copied yet
					messages_without_temp_data = _.cloneDeep(messages);
				delete messages_without_temp_data[i].payload.data;
			}
		}
	}
	return { temp_data_length, messages_without_temp_data };
}
