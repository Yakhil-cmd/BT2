### Title
Cross-repository CI status forgery via unscoped `Commit` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub App/org identified by `repository.owner.login` in the payload, but `Webhooks::Handlers::StatusHandler` never checks that the payload's declared repository actually owns the target `Commit`. It looks up commits globally by `sha` across every stack in the installation, so a validly-signed `status` event for one (attacker-controlled) repository can flip the CI status of a commit belonging to a completely different, unrelated stack/organization.

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to validate against based on the *unverified* `repository.owner.login` (or `organization.login`) field of the payload: [1](#0-0) 

Once the signature check passes for that org, the raw body is dispatched to handlers keyed only on the `X-Github-Event` header: [2](#0-1) 

Every other event handler scopes its side effects to the repository declared in the payload via `Handler#stacks`/`repository_name` (`payload.dig('repository', 'full_name')`), e.g. `PushHandler`: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, does not use `stacks`/`repository_name` at all — it resolves the target purely by commit SHA across the *entire* `Commit` table, with no repository or stack filter: [5](#0-4) 

This breaks the equality that should hold for every webhook-driven mutation: `organization_authenticated (repository.owner.login used for HMAC secret selection) == repository_written (repository whose Commit is mutated)`. For `StatusHandler` the right-hand side is effectively "any repository in the installation," decoupled from the left-hand side.

An unprivileged attacker only needs write/push access to *any* repository that has the Shipit GitHub App installed (their own repo, or an org where the admin left `webhook_secret` unset, which the docs explicitly mark as optional). Git commit SHAs are content-addressed: if the attacker can get an identical commit (e.g. by forking or fetching a public commit from a victim stack's repository and pushing it into their own controlled repository), then trigger a genuine GitHub `status` webhook for that SHA (e.g. via the Statuses API on their own repo, which they can call with their own repository's token/permissions), GitHub will sign the resulting webhook with the attacker's own org's legitimate secret. Shipit's `verify_signature` will pass because the signature really is valid for that org. `StatusHandler#process` then updates `Status` for **every** `Commit` row across the whole installation matching that SHA — including the victim stack's commit — regardless of which repository/org actually owns it.

### Impact Explanation
`Status` creation drives Shipit's continuous-delivery / CI-gating logic (`Status#after_create :enable_ci_on_stack`, `Commit#schedule_continuous_delivery`, and deploy-blocking checks based on `ci.require`/`required_statuses`): [6](#0-5) 

By forging a "success" status for a shared/duplicated commit SHA, an attacker who controls only an unrelated repository (with no access to the victim stack, no `ApiClient` token, and no privileged Shipit account) can mark a victim commit as CI-passing, which can unblock/trigger an unauthorized deploy in the victim's stack — satisfying the "unauthorized deploy" impact bar (Critical/High tier per the rules).

### Likelihood Explanation
Exploitation requires: (1) the attacker to control a repository that is a legitimate GitHub App installation target for the shared `/webhooks` endpoint (realistic for any multi-tenant or open-source-friendly Shipit deployment, or trivially true if the attacker is simply a legitimate but low-privilege GitHub user with push access to some tracked repo), and (2) a commit with the same SHA existing in both the attacker's repo and a victim stack's repo — achievable deliberately by fetching/forking a specific target commit. No secret leakage, no privileged token, and no session are required, matching the "unprivileged attacker" constraint of the prompt. This is a genuine logic gap (missing repository scoping) rather than a theoretical or misconfiguration-dependent issue.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries `Commit`/`Stack` records) by the repository declared in the same payload, consistent with `Handler#stacks`/`repository_name`, e.g. restrict the `Commit.where(sha: params.sha)` query to `stacks` (commits whose `stack` belongs to `Repository.from_github_repo_name(repository_name)`), so a signed webhook can only mutate state for the repository it was actually authenticated for.

### Proof of Concept
1. Attacker controls (or has push access to) `attacker-org/some-repo`, which has the Shipit GitHub App installed with its own `webhook_secret`.
2. Attacker fetches/forks a specific commit `C` (SHA `abc123...`) that also exists as a tracked commit in `victim-org/victim-repo` (a Shipit-tracked stack), and pushes it into `attacker-org/some-repo`.
3. Attacker calls the GitHub Statuses API on `attacker-org/some-repo` for SHA `abc123...` with `state: success`. GitHub sends a `status` webhook to Shipit's shared `/webhooks` endpoint, signed with `attacker-org`'s real `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and confirms the signature is valid — verification passes.
5. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which matches the commit row belonging to `victim-org/victim-repo`'s stack, and calls `commit.create_status_from_github!(params)`, creating a `success` status on the victim's commit — potentially unblocking CI gating and enabling an unauthorized deploy of that commit in `victim-org/victim-repo`'s stack, without the attacker ever having any access to that stack.
