Multi-tenant GitHub org configured with a blank `webhook_secret` allows unauthenticated forged `status` events to write status records for any repository's commit sharing the SHA - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` resolves the `GitHubApp` purely from the attacker-controlled `repository.owner.login` field, and `GitHubApp#verify_webhook_signature` short-circuits to `true` when that org's config has no `webhook_secret`. `StatusHandler#process` then updates `Commit.where(sha: params.sha)` with zero scoping to the authenticating repository/stack, so a forged, unsigned `status` payload naming a secret-less org can write a `Status` onto any commit row in the database that happens to share that SHA, regardless of which org/repo actually owns it.

### Finding Description
The broken binding is: **the webhook body should only affect the repository that supplied the matching `webhook_secret` HMAC**, i.e. `authenticated_repository == affected_repository`. This is violated as follows:

1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) picks the `GitHubApp` config using `repository_owner`, which is read straight out of the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (lines 59-62).
2. `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) returns `true` immediately `unless webhook_secret` — i.e., if the resolved org's Shipit config has no `webhook_secret` configured, the signature check is bypassed entirely and the raw, unsigned body is accepted as authentic. [1](#0-0) 
3. Once accepted, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with no `stack_id`/repository filter whatsoever. [2](#0-1) 
4. `Commit#sha` is not guaranteed globally unique per-repository in a multi-tenant Shipit install — any stack tracking a commit with the same SHA (e.g. same open-source dependency commit, a rebased/cherry-picked commit, or a coincidental match) will have a `Status` row created against it via `Commit#create_status_from_github!` → `Status.replicate_from_github!` (app/models/shipit/commit.rb:165-169).

Exploit flow: an attacker (any internet user, no Shipit credentials) POSTs to `/webhooks` with header `X-Github-Event: status` and a body whose `repository.owner.login` names a GitHub org that is present in Shipit's `secrets.github` config but has no `webhook_secret` key set for it. The `sha` in the payload is set to a SHA that is shared with (or deliberately made to match) a victim stack's tracked commit. Because `verify_webhook_signature` returns `true` for that org unconditionally, the controller proceeds to call `StatusHandler`, which finds and mutates the victim commit's status.

Existing guards do not prevent this:
- `verify_signature`'s `rescue Shipit::GithubOrganizationUnknown` only catches orgs absent from config entirely — a configured-but-secretless org sails through. [3](#0-2) 
- `drop_unhandled_event` and `check_if_ping` do not scope by repository.
- `StatusHandler`'s `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) validates payload shape only, not repository ownership. [4](#0-3) 
- There is no `stack_id` or `repository` filter added anywhere between signature verification and the `Commit.where(sha:)` lookup.

### Impact Explanation
A successful forged request causes a `Status` record to be created/attached to a commit belonging to a stack/repository that never authenticated (or even sent) the webhook — this is a cross-repository state-mutation ("payload for one repository mutating another's stack/commit"), matching the Critical impact category. Downstream effects of injected statuses include: influencing `Commit#deployable?`/`blocked?` logic (app/models/shipit/commit.rb:227-237), triggering `stack.schedule_merges` and `ContinuousDeliveryJob` (lines 383, 281-287), and emitting `Hook.emit(:commit_status/:deployable_status, ...)` for the victim stack — i.e. an attacker can potentially manufacture a fake "success" status on a shared SHA to unblock/trigger a continuous deployment or merge in a stack they do not control. This is repeatable against any org configured in Shipit that lacks a `webhook_secret`, and against any commit SHA colliding across tenants.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub orgs (`secrets.github` keyed by org) where at least one configured org's entry omits `webhook_secret` — this is a real supported configuration path per `GitHubApp#initialize` (`@webhook_secret = @config[:webhook_secret].presence`) and `Shipit.github_app_config`. The attacker needs no credentials, tokens, or team membership; only knowledge (or a guess) of an org name present in the target's config and a colliding commit SHA (attacker can increase odds by targeting known/public shared commits, e.g. from popular open-source dependencies vendored by multiple stacks). Cost is a single unauthenticated HTTP POST, fully repeatable and scriptable.

### Recommendation
- Require every configured GitHub org/app entry to have a non-blank `webhook_secret`; fail closed (reject, do not default to "verified") when it is missing, rather than treating a blank secret as automatically valid.
- Scope all webhook handlers (in particular `StatusHandler`, `CheckSuiteHandler`, etc.) to the authenticated repository, e.g. `Commit.where(sha: params.sha, stack_id: Stack.where(repo_owner: repository_owner, repo_name: ...))` or otherwise join through `Repository`/`Stack` matching the payload's `repository.full_name`, instead of a bare SHA lookup across the whole `commits` table.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "status=#{status}"

    end
