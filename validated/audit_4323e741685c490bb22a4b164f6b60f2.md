### Title
Global, unscoped commit-SHA lookup in `StatusHandler` lets a webhook authenticated for one GitHub organization write CI status onto commits belonging to a different organization/stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), i.e. it authenticates *which organization* sent the event. But `Shipit::Webhooks::Handlers::StatusHandler#process` never checks that organization/repository at all - it resolves the target purely by `Commit.where(sha: params.sha)`, a global lookup across every stack tracked by the Shipit instance. This is the same bug class as the reported Vester.sol issue: a value used to gate/authorize an operation (`repository_owner` for signature verification) is never propagated into the state actually mutated (`Status` records tied to a `Commit`/`Stack` that has nothing to do with the authenticated organization).

### Finding Description
The webhook pipeline is:

1. `WebhooksController#verify_signature` picks the app/secret via `repository_owner` and calls `github_app.verify_webhook_signature`, which validates the whole raw request body against that organization's `webhook_secret`. [1](#0-0) 

2. Once verified, `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`. [2](#0-1) 

3. `StatusHandler#process` operates purely on `params.sha`, with no repository/organization scoping whatsoever:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

Compare this to every other handler, which inherits `Handler#stacks`/`#repository_name`, scoping the write to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [4](#0-3) 

`StatusHandler` overrides `process` and does not call `stacks`/`repository_name` at all, so the org/repo binding validated at the controller layer is dropped by the time the actual DB write happens.

Since Git commit SHAs are content-addressed, an attacker who legitimately controls their own GitHub organization/repository (with the Shipit GitHub App installed there, as documented as a normal supported multi-org configuration - see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) can fetch/import a commit object from an unrelated, victim-tracked repository (any public repo Shipit tracks) into their own repository. GitHub then computes an identical SHA for that duplicated commit object. The attacker (or their own CI, which they fully control) posts a Status API call for that SHA on their own repository. GitHub relays this as a legitimate, correctly-signed `status` webhook event to Shipit, signed with the attacker's own organization's `webhook_secret` - which passes `verify_signature` because that verification is scoped to their organization only.

`StatusHandler`, however, matches `Commit.where(sha: params.sha)` against every `Commit` row Shipit knows about, across all repositories/stacks/organizations, and creates a `Status` for each match, regardless of which organization is authenticated for this specific webhook. This lets the attacker inject a forged `success`/`failure`/`pending` Status onto a victim commit tracked by an entirely different, unrelated stack/organization.

### Impact Explanation
`Status#create` triggers `enable_ci_on_stack` and `schedule_continuous_delivery`: [5](#0-4) 

Commit statuses feed directly into Shipit's deploy-safety and continuous-delivery gating logic (whether a commit is considered "green"/deployable and whether continuous delivery should fire). By forging a `success` status on a victim's commit from a foreign, authenticated-but-unrelated organization, an attacker can flip CI-gating state for a stack they have no access to, enabling an unauthorized deploy/continuous-delivery trigger on that unrelated stack - this matches the "unauthorized deploy" impact bucket (Critical) since no privileged Shipit credential, `ApiClient` token, or GitHub write access to the victim repository is required at all; only ownership of an independent GitHub org with the Shipit App installed (a standard, low-privilege, self-service action supported by the engine's own multi-org design).

### Likelihood Explanation
Moderate-to-high: the multi-org configuration is explicitly supported and documented by the engine (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), so multiple independently-authenticated organizations sharing one Shipit instance is a first-class, expected deployment topology, not a hypothetical. Constructing a commit with an identical SHA in an attacker-controlled repo only requires fetching/duplicating the target's public commit object - a normal Git operation, not a hash preimage attack. No credential, session, or write access to the victim's actual GitHub repository is required.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by content-derived identifiers alone) to the repository/stack indicated by the same `payload['repository']` object that was used to select the verifying webhook secret, mirroring the base `Handler#stacks`/`#repository_name` pattern, e.g.:

```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

This binds the `organization` value used for signature verification to the `repository`/`stack` that is actually written, closing the cross-organization write path.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `VictimOrg` and `AttackerOrg` (both with the Shipit GitHub App installed, per `docs/setup.md`'s multi-org setup), each with a distinct stack tracked (e.g. `VictimOrg/important-repo` and `AttackerOrg/throwaway-repo`).
2. Shipit ingests a commit `C` (SHA `abc123...`) into the `VictimOrg/important-repo` stack via normal `push` sync.
3. Attacker, in their own `AttackerOrg/throwaway-repo`, fetches/cherry-picks the identical commit object `C` (same tree, parents, author/committer metadata/timestamps) so that Git computes the same SHA `abc123...` in their own repo.
4. Attacker's own CI (fully attacker-controlled) posts a GitHub Status update for SHA `abc123...` with `state: "success"` on `AttackerOrg/throwaway-repo`.
5. GitHub delivers a `status` webhook to Shipit, correctly signed with `AttackerOrg`'s `webhook_secret`. `WebhooksController#verify_signature` passes because it only checks the signature against `AttackerOrg`.
6. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, finds the `VictimOrg` commit `C`, and creates a forged `success` `Status` on it - `enable_ci_on_stack`/`schedule_continuous_delivery` fire for the `VictimOrg` stack, potentially satisfying deploy-safety checks the attacker has no legitimate access to influence.
