### Title
Cross-repository forgeable CI status via `StatusHandler#process` bypasses `MergeRequest#all_status_checks_passed?` gating - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Api::MergeRequestsController#create`/`#refresh` are gated by `require_permission!`, but whether a queued `MergeRequest` actually gets merged is decided solely by `MergeRequest#all_status_checks_passed?`, which reads locally-stored `Status` rows. `StatusHandler#process`, reachable through the unauthenticated `WebhooksController` with only a GitHub webhook signature (no `ApiClient` token), writes those `Status` rows keyed purely by commit `sha` with no binding to the `repository.full_name` in the payload, unlike every sibling handler.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`Status(commit).stack_id == Repository.from_github_repo_name(payload.repository.full_name).stacks` — i.e., a status update should only be attributable to the repository asserted in the payload that was cryptographically verified. 

`StatusHandler#process` violates this:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
It looks up `Commit` purely by `sha`, globally across every stack/repository tracked by the Shipit instance, and never consults `params.repository.full_name` or scopes to the repository whose signature was actually verified. This is in stark contrast to every other handler (`OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, `AssignedHandler`, `UnlabeledHandler`), all of which resolve `Repository.from_github_repo_name(params.repository.full_name)` first and only act within that repository's scope [2](#0-1) [3](#0-2) . The `Handler` base class even provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)` [4](#0-3)  that `StatusHandler` simply does not use.

`WebhooksController#verify_signature` verifies the HMAC against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the untrusted payload (`params.dig('repository','owner','login')`), not derived from any already-authenticated identity [5](#0-4) [6](#0-5) . Any GitHub webhook that is genuinely signed by GitHub for *some* repository sharing the same GitHub App/organization installation as the target stack — for example a repository the attacker legitimately owns or contributes to under that org — passes `verify_signature` and reaches `StatusHandler#process` unmodified. The handler then writes a `success` `Status` for any `sha` the attacker names, as long as a `Commit` with that sha exists somewhere in the Shipit database (public information, since it is the head sha of the target's already-open, already-queued pull request).

`MergeRequest#all_status_checks_passed?` reads exactly these `Status` rows via `StatusChecker.new(head, head.statuses_and_check_runs, ...)` [7](#0-6) , and `ProcessMergeRequestsJob#perform` merges any `pending` `MergeRequest` for which that predicate is true [8](#0-7) . Thus the API-level `require_permission!` check on `Api::MergeRequestsController#create` (which only guards enqueueing) is disjoint from the actual trigger condition for merging, and that trigger condition is forgeable through an entirely different, unauthenticated (no `ApiClient` token) controller.

Exploit flow:
1. A legitimate maintainer calls `Api::MergeRequestsController#create`, which calls `MergeRequest.request_merge!`, putting the request in `pending` state without real passing CI.
2. Attacker (no Shipit account, no API token) triggers or replays a GitHub `status` webhook whose signature is valid for some repository under the same GitHub App/organization as the target stack, setting `sha` to the target PR's head sha and `state` to `success`.
3. `StatusHandler#process` finds the `Commit` by sha alone and creates a passing `Status` for it, regardless of which repository the signed payload claims to be about.
4. `ProcessMergeRequestsJob`, on its normal schedule, calls `merge_request.all_status_checks_passed?`, now true, and calls `merge_request.merge!`, merging the PR via the GitHub API using Shipit's own credentials.

### Impact Explanation
An attacker can force an unauthorized merge of an arbitrary pull request in any stack tracked by the same GitHub App/organization installation, without holding any `ApiClient` token, Shipit session, or `Shipit.github_teams` membership — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." The blast radius spans every stack sharing that GitHub App installation's webhook secret, i.e. potentially multiple repositories/teams within an organization, not just the attacker's own repository.

### Likelihood Explanation
Preconditions: (a) a legitimate `MergeRequest` already queued in `pending` state (normal workflow, no special access needed to trigger since PR authors commonly request merges), (b) attacker must be able to cause GitHub to emit a validly-signed `status` webhook — feasible if attacker has push/status access to any repository under the same GitHub App/org installation that Shipit trusts (e.g., their own fork or a low-privilege repo added to that org), and (c) knowledge of the target PR's head sha, which is public GitHub information. No secrets (`webhook_secret`, `api_clients_secret`, GitHub App private key) need to be known by the attacker directly — GitHub computes the signature for them. This is a realistic and repeatable attack against any Shipit deployment tracking multiple repositories per GitHub App/org.

### Recommendation
Scope `StatusHandler#process` to the repository asserted (and cryptographically verified) in the payload, mirroring every other handler: resolve `Repository.from_github_repo_name(params.repository.full_name)` first, and only update `Status` for commits belonging to stacks under that repository (e.g. `Commit.where(sha: params.sha).joins(stack: :repository).where(shipit_repositories: { id: repository.id })`), rejecting/ignoring updates for shas outside that repository.

### Proof of Concept
Minitest plan (no live GitHub):
1. In `Api::MergeRequestsControllerTest`, authenticate a legitimate `ApiClient` and `post :create` to queue a `MergeRequest` for `@stack` with a known head sha, landing in `pending` state with no real `Status`.
2. In a `WebhooksControllerTest` context, without any `ApiClient`/token, stub `verify_signature` to true (simulating a genuinely-signed webhook from a different repository under the same org) and `post :create` with `X-Github-Event: status`, body `{ sha: <target head sha>, state: 'success', context: 'ci', repository: { full_name: 'attacker/unrelated-repo', owner: { login: <same org as target> } } }`.
3. Assert `Status.where(commit_id: merge_request.head_id, state: 'success').exists?` is true and `merge_request.reload.all_status_checks_passed?` is true, even though `repository.full_name` in the payload does not match the target stack's repository.
4. Call `ProcessMergeRequestsJob.perform_now(@stack)` and assert `merge_request.reload.merge_status == 'merged'` (or that `stack.github_api` received `merge_pull_request`), demonstrating an unauthorized merge triggered entirely without an `ApiClient` token.
