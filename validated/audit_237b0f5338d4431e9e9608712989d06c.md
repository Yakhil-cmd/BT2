### Title
Webhook signature verification is bound to an attacker-controlled organization field, not the repository/commit actually acted upon, enabling cross-organization forged status events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on fields taken directly from the *unverified* JSON payload (`repository.owner.login` or `organization.login`), rather than from any property already tied to the specific repository/stack that the event handler will actually act on. Because `Shipit::Webhooks::Handlers::StatusHandler` subsequently resolves the target `Commit` purely by matching `sha` across the entire database — with no check that the commit's stack/repository corresponds to the organization whose secret validated the signature — an attacker who legitimately knows the `webhook_secret` for *any* organization configured on the Shipit instance can forge a `status` webhook that is "authenticated" for their own organization but whose payload content (`sha`, `state`, `context`) targets a commit belonging to a completely different tracked stack/repository, e.g. triggering continuous deployment there.

### Finding Description
`repository_owner`, used to pick the signing organization, is read straight from attacker-supplied JSON before the signature is checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` (and therefore the `webhook_secret`) keyed by that attacker-controlled string: [3](#0-2) 

HMAC verification only proves the raw bytes were signed with *that org's* secret — it does not prove any relationship between the org name embedded in the payload and the `sha`/repository the handler will act on. In particular, `StatusHandler#process` resolves target commits with a *global*, repository-unscoped lookup: [4](#0-3) 

Creating a matching `Status` record on that commit triggers CI enablement and immediately schedules continuous delivery: [5](#0-4) 

So the equality the code implicitly (and incorrectly) assumes is:
`organization whose webhook_secret authenticated the request == organization/repository that owns the commit acted on by the handler`

An attacker who controls (or otherwise knows the `webhook_secret` of) Org A — a legitimate but unrelated organization also configured on the same multi-tenant Shipit instance — can send a `status` webhook with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with Org A's secret, `repository.owner.login = "OrgA"` (satisfying `verify_signature`), but a `sha` value copied from a commit belonging to Org B's stack. `StatusHandler` will happily attach a forged `success` status to that Org B commit, with no cross-check against `OrgA`.

### Impact Explanation
If the targeted stack has `continuous_deployment` enabled and is waiting on a CI status/context, this technique lets an attacker who only controls a different, unrelated organization on the same Shipit instance fabricate a passing CI status for another organization's commit and cause an **unauthorized deploy** to that stack — one of the explicitly listed Critical impacts.

### Likelihood Explanation
Exploitation requires the attacker to know the `webhook_secret` of at least one organization configured on the multi-tenant Shipit instance (e.g. their own org, which they legitimately administer via the GitHub App installation) and knowledge of a target commit `sha` belonging to another org's stack (easily obtainable from GitHub's public commit history/API or Shipit's own UI). No privileged Shipit account, API token, or GitHub write access to the victim repository is required — only the ability to send an HTTP POST to `/github/webhooks`.

### Recommendation
Bind signature verification to the same repository/organization that the handler will act on: verify the request against the secret of the organization that owns the `Stack`/`Repository` actually referenced by `repository.full_name`, and have `StatusHandler` (and any other handler resolving records without an explicit repository scope) filter `Commit` lookups by `stack.repository` matching the verified payload's repository, not by `sha` alone.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (multi-tenant `github:` config keyed by org, as supported by `Shipit.github_app_config`).
2. As an attacker who is a legitimate admin of `OrgA` (and therefore knows `OrgA`'s `webhook_secret`), find a commit `sha` that belongs to a stack tracked under `OrgB` (e.g., from GitHub's public API) where `continuous_deployment` is enabled and CI is pending.
3. Craft a JSON body:
```json
{
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against `OrgA`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgB` commit (no org/repo cross-check), and calls `create_status_from_github!`, creating a `success` `Status` on it.
7. `Status#enable_ci_on_stack` and `Status#schedule_continuous_delivery` fire, potentially triggering an unauthorized `Deploy` on `OrgB`'s stack — achieved entirely using credentials belonging to unrelated `OrgA`.

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
