### Title
Attached deposit (`CallerDeposit`) is permanently stuck in `WalletContract` when the address-registrar lookup or NEP-141 `storage_balance_of` cross-contract call fails - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `WalletContract::rlp_execute` entry point is `#[payable]` and accepts an attached deposit from an external caller (a relayer or the wallet owner). This deposit is tracked in a `CallerDeposit` struct so that it can be refunded if the downstream cross-contract call the wallet contract makes on the user's behalf ultimately fails. The refund is correctly issued from `rlp_execute_callback` when the final promise fails, but two other callback paths that can also terminate the flow on failure — `address_check_callback` and `nep_141_storage_balance_callback` — return an error `ExecuteResponse` directly on `PromiseResult::Failed` without ever creating the refund promise. In these cases the caller's deposit remains held by the `WalletContract` account with no code path to return it, exactly mirroring the reported Solidity bug where a `catch` branch swallows a failed sub-call without returning the attached value.

### Finding Description
`inner_rlp_execute` builds a `CallerDeposit` from the attached deposit whenever the predecessor differs from the wallet's own account: [1](#0-0) 

This `caller_deposit` is threaded through to `address_check_callback` and `nep_141_storage_balance_callback`, and finally to `rlp_execute_callback`, which is the *only* place that actually issues the refund when the resulting promise fails: [2](#0-1) 

However, `address_check_callback`, which runs after calling the external address-registrar contract (`address_registrar.lookup(address)`), handles `PromiseResult::Failed` by immediately returning a failure value — bypassing any refund of `caller_deposit`: [3](#0-2) 

The same pattern exists in `nep_141_storage_balance_callback`, which runs after calling `storage_balance_of` on an NEP-141 token contract for an ERC-20-emulated transfer; on `PromiseResult::Failed` it also returns immediately without refunding `caller_deposit`: [4](#0-3) 

Because NEAR's protocol-level deposit-refund mechanism (documented in `docs/RuntimeSpec/Refunds.md`) only auto-refunds deposits attached to a *receipt* that itself fails, and here the outer `rlp_execute` receipt succeeds (it returns a `Promise`, and the deposit was already consumed/credited to the wallet account's balance as part of that successful `#[payable]` call), the contract must manage the refund itself via `CallerDeposit`. The two callback paths above omit that manual refund, so the deposit is silently absorbed into the wallet account's balance with no promise ever created to return it to the caller. [5](#0-4) 

### Impact Explanation
Any account (typically a relayer, or a user calling through a relayer with an access key) that submits a `rlp_execute` transaction attaching a deposit for an `EOABaseTokenTransfer` with `address_check` set, or for an `ERC20Transfer`, loses that deposit permanently if the intermediate cross-contract call (`address_registrar.lookup` or `token.storage_balance_of`) fails for any reason (e.g., the registrar/token contract is paused, panics, runs out of gas, or does not exist). The funds become stuck in the `WalletContract` account's balance with no code path to withdraw them back to the original caller, constituting an unauthorized/irrecoverable balance loss for an unprivileged account — the same root cause as the referenced Solidity finding (a failure branch that skips the refund step for previously attached value).

### Likelihood Explanation
This path is reachable by any account submitting a normal RPC transaction that calls `rlp_execute` with a deposit and a transaction kind that routes through `address_check_callback` or `nep_141_storage_balance_callback`. Triggering the failure only requires the downstream registrar/token contract call to fail, which can happen for many benign reasons (temporary unavailability, gas exhaustion, contract not deployed, contract logic error) and does not require any malicious validator or network-level behavior.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic already present in `rlp_execute_callback`: on `PromiseResult::Failed`, if `caller_deposit` is `Some`, create a `promise_batch_create`/`promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. An external relayer account `relayer.near` calls `wallet.rlp_execute({ target: <eth-implicit-account>, tx_bytes_b64: <RLP tx encoding an EOABaseTokenTransfer with address_check = Some(addr)> })` attaching a non-zero deposit (this deposit is captured as `CallerDeposit`).
2. `inner_rlp_execute` schedules a call to the configured `ADDRESS_REGISTRAR_ACCOUNT_ID` (`address_registrar.lookup(address)`), chained with `.then(address_check_callback(...))`.
3. Configure/force the registrar call to fail (e.g., deploy no contract at `ADDRESS_REGISTRAR_ACCOUNT_ID`, or have it panic).
4. `address_check_callback` observes `env::promise_result(0) == PromiseResult::Failed` and returns `ExecuteResponse{ success: false, ... }` directly — no refund promise is created.
5. Query `relayer.near`'s balance before/after: the attached deposit is deducted and never returned; querying the wallet contract account shows the balance increased by exactly the attached deposit, with no further receipt that could return it.

    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
