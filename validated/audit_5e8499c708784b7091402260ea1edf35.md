### Title
Webhook signature verification is keyed on `repository.owner.login`, but every handler acts on the unverified `repository.full_name` field — allowing a holder of one organization's `webhook_secret` to forge events for any other tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC against using a value read out of the *same untrusted JSON body* it is about to verify (`repository.owner.login`, or `organization.login` as a fallback) [1](#0-0) [2](#0-1) . The HMAC itself is computed over the *entire* raw request body [3](#0-2) , so anyone who legitimately controls one organization's `webhook_secret` (e.g. because they administer that org's GitHub App integration in a multi-org Shipit deployment) can compute a valid signature for a payload of their own choosing — including a payload whose `repository.full_name` names a completely different, unrelated repository/stack. Every `Handler` subclass (push, status, check_suite, membership, pull_request) resolves the target repository purely from `payload.dig('repository', 'full_name')` [4](#0-3) , with no cross-check that this repository actually belongs to the organization whose secret produced the valid signature. `Repository.from_github_repo_name` does a straight owner/name lookup with no organization binding [5](#0-4) .

### Finding Description
The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization owning the repository the handler acts on`

In practice the engine only enforces:
`verify_signature` picks the secret via `repository.owner.login` (or `organization.login`) → HMAC(secret, raw_body) matches header.

But the handler layer separately re-reads `repository.full_name` from the *same signed but attacker-authored* body to decide which `Stack`/`Repository` to mutate [4](#0-3) . Nothing ties `repository.full_name`'s owner segment to the `repository.owner.login`/`organization.login` value that selected the verifying secret. Because Shipit supports per-organization GitHub Apps/secrets (`config/secrets.*.yml` documents a `github: { orgA: {...webhook_secret}, orgB: {...webhook_secret} }` shape) [6](#0-5) , a party who legitimately possesses the `webhook_secret` for org A (because they administer org A's GitHub App, which Shipit trusts to speak for org A only) can craft any JSON body, put `repository.owner.login: "orgA"` in it (so `verify_signature` fetches and matches org A's secret) [1](#0-0) , while setting `repository.full_name: "orgB/victim-repo"` so the handler acts on org B's stack [7](#0-6) .

Concretely for the `push` event, this triggers `stack.sync_github(expected_head_sha:)` on org B's stacks matching the forged branch [7](#0-6) , i.e. an org-A-secret holder can force a resync/deploy-eligible state on org B's stack using an `after` SHA of their choosing, without ever having write access to org B's repository, purely because the *signature-selection field* and the *acted-upon field* are two different, independently-forgeable parts of the same unauthenticated JSON payload.

### Impact Explanation
This breaks the intended trust boundary between organizations hosted on the same Shipit instance: authentication with organization A's `webhook_secret` should authorize actions only on organization A's repositories, but instead it authorizes forged events for *any* repository name string embedded in the payload, letting an org-A-scoped credential holder drive state changes (forced resync of commit history, injected head SHAs) against an unrelated org B's `Stack`. Depending on which webhook event/handler is targeted (`push`, `status`, `check_suite`), this can influence what Shipit believes about a victim stack's CI/commit state and interacts with continuous-delivery gating, moving toward an unauthorized deploy/rollback trigger on a repository the attacker was never authorized to write to.

### Likelihood Explanation
Requires only knowledge of one organization's `webhook_secret` — a credential an org's own GitHub App administrator legitimately holds under Shipit's own multi-org design — and the ability to send an arbitrary HTTP POST with a matching `X-Hub-Signature`; no Shipit session, `ApiClient` token, or GitHub write access to the victim repository is needed. In single-organization Shipit deployments this is not exploitable (there is only one secret/one trust domain), but the engine explicitly supports and documents multi-organization configuration with per-org secrets, making the cross-org boundary a real, engine-supported trust boundary that this code fails to enforce.

### Recommendation
After selecting the GitHub App/secret via `repository.owner.login` (or `organization.login`) and verifying the signature, the controller/handler layer must re-verify that the `repository.full_name` (and `organization.login` for org-level events) used later by each `Handler` actually belongs to that same verified organization before doing any lookup/mutation — e.g. assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0` in `WebhooksController#verify_signature` or in `Handler#repository_name`, rejecting mismatches with `422`.

### Proof of Concept
1. Operate (or administer) organization `orgA`'s GitHub App integration with Shipit; obtain `orgA`'s configured `webhook_secret`.
2. Craft a JSON body for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"` from the payload [2](#0-1) , fetches `orgA`'s `github_app`, and the signature matches, so the request passes [1](#0-0) .
5. `PushHandler` resolves the target via `payload.dig('repository', 'full_name')` = `"orgB/victim-repo"` [4](#0-3) , and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `orgB`'s stack [7](#0-6)  — despite the attacker having no relationship to `orgB` beyond knowing `orgA`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
