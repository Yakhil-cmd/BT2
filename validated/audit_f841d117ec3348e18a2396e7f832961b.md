### Title
Webhook signature is verified against the org named in `repository.owner.login`, but every handler acts on the independently-attacker-controlled `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-tenant Shipit installation (multiple GitHub Apps/organizations configured, each with its own `webhook_secret`), `WebhooksController#verify_signature` picks which org's secret to verify the HMAC against using a field read straight out of the untrusted JSON body, while the actual event-handling code resolves the target repository/stack from a *different* field of that same untrusted body. Nothing ties these two fields together, so a valid signature from one tenant's app does not guarantee the payload is only allowed to affect that tenant's repositories.

### Finding Description
`WebhooksController#verify_signature` computes the org to check the signature against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`), and is used solely to select which configured GitHub App/organization's `webhook_secret` to validate the `X-Hub-Signature` against via `Shipit.github(organization: repository_owner)` → `verify_webhook_signature`: [3](#0-2) 

Once the signature check passes, `create` dispatches the *same raw payload* to every registered handler for the event: [4](#0-3) 

Handlers, however, resolve which repository/stacks to affect using a **different** field of the payload — `repository.full_name` — not `repository.owner.login`: [5](#0-4) 

Because HMAC-SHA1 verification is only checked against the secret belonging to the org identified by `repository.owner.login`, and the code never asserts that `repository.full_name` actually starts with `repository.owner.login/`, these two fields can be made inconsistent by anyone who can produce a validly-signed payload for **any one** configured organization in the instance (e.g., a legitimate but low-privilege GitHub App installer/admin on OrgB, or anyone who has obtained OrgB's `webhook_secret`). Such an actor can sign a payload where `repository.owner.login = "OrgB"` (so the signature check passes against OrgB's secret) but `repository.full_name = "OrgA/target-repo"`, causing `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` to run push/status/check_suite/membership handling logic against OrgA's stacks — an organization the attacker has no legitimate access to.

This is the same trust-binding failure pattern as the referenced report: a value that is authorized/verified (the org whose secret backs the signature) is not the same value that downstream code actually acts on (the repository named in the body). Just as `StrategySupplyBase.harvest` let unprivileged callers mutate protected accounting state because no check tied caller identity to the state being mutated, here no check ties the authenticated org to the repository being mutated.

### Impact Explanation
Handlers triggered by forged cross-org webhooks include, at minimum:
- `push` → `GithubSyncJob`, which re-syncs commit history for the target stack from GitHub using the app's own installation token, and can trigger `CacheDeploySpecJob` (re-fetch and cache `shipit.yml` for the targeted stack). [6](#0-5) 
- `status` → updates a `Commit`'s CI status, which is exactly the signal the merge queue / continuous-deployment logic relies on to decide whether a commit is safe to merge/deploy.

If an attacker can forge a "success" status webhook or push event bound to an OrgA repository while only holding a valid signature for OrgB, they can influence OrgA's merge-queue/continuous-deployment decisions — i.e., an unauthorized deploy/merge path. This matches the Critical impact bucket ("cross-repository writes ... unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires a multi-tenant Shipit deployment where more than one GitHub organization/App is configured (each with distinct `webhook_secret`s via `Shipit.github(organization:)`), and requires the attacker to already control (or have compromised) the webhook secret for at least one of the configured organizations — which is a materially lower bar than compromising the target organization's own secret or gaining write access to the target repository. Whether this repo/config is normally run in single-tenant mode is not fully clear from the indexed files, which somewhat limits confidence in real-world exploitability; this should be validated against `Shipit.github_apps`/config loading code not fully covered by this index.

### Recommendation
After signature verification succeeds, explicitly validate that `repository.full_name`'s owner segment matches the `repository_owner` (or `organization.login`) that was used to select the verifying secret, and reject the webhook (422) if they diverge. Alternatively, resolve the target `Repository`/`Stack` using the same org value that was cryptographically verified rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `lib/shipit/github_app.rb`).
2. As an attacker who controls/knows OrgB's `webhook_secret` (e.g., a GitHub App admin for OrgB), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "repository": {
       "owner": { "login": "OrgB" },
       "full_name": "OrgA/target-repo"
     },
     ...
   }
   ```
3. Sign the raw body with OrgB's `webhook_secret` and send it to `POST /webhooks` with header `X-Hub-Signature: sha1=<hmac>`.
4. `verify_signature` resolves `repository_owner` = `"OrgB"`, fetches OrgB's app, and the signature validates successfully.
5. `Shipit::Webhooks.for_event('push')` handlers run against `repository.full_name = "OrgA/target-repo"` (per `app/models/shipit/webhooks/handlers/handler.rb`), triggering sync/job logic for OrgA's stack despite the attacker never having proven any relationship to OrgA.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
