## Title
AA-based swap contracts computing exchange output solely from the AA's live balance provide no real slippage protection, enabling sandwich attacks on trigger senders - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The reported bug is a class of "phantom slippage protection": the minimum acceptable output (`_min_dy`) is derived from the very same live-state function (`get_dy`) that computes the actual swap output at execution time, so the check can never reject an unfavorable execution and the trader can be sandwiched. The equivalent pattern exists in ocore's own reference AA-based automated-market-maker contract, `test/samples/uniswap_like_market_maker.oscript`, which is exactly the kind of oscript/AA logic that an unprivileged AA author can deploy and that an unprivileged trigger sender interacts with by posting a payment unit.

### Finding Description
In the "exchange bytes to asset" and "exchange asset to bytes" cases of the market-maker AA, the payout amount is computed purely from the AA's current on-chain balances at the moment the trigger is executed, with **no user-supplied minimum-output parameter at all** (worse than `get_dy`, which at least echoes back a computed value): [1](#0-0) [2](#0-1) 

Contrast this with the "invest in MM" case in the same contract, which *does* protect the caller by bouncing if the deposited ratio doesn't match `$expected_asset_amount` computed from state that was fixed before the trigger's own outputs are counted: [3](#0-2) 

No such check exists for the two swap cases — `$amount` is simply whatever the constant-product formula yields from `balance[$asset]` / `balance[base]` at execution time, and it is paid out unconditionally. The trigger sender has no way to encode "abort if the received amount is less than X" in the trigger.

This is exploitable because AA trigger execution order is deterministic but attacker-influenceable: triggers stabilized in the same MCI are queued and executed in an order keyed by `mci, level, unit, address`: [4](#0-3) [5](#0-4) 

An attacker who authors units can control their own unit's `level` (by choosing parents) and can grind/select which of their own units gets included, allowing them to place a swap in the same or an adjacent MCI immediately before a victim's swap trigger and then reverse it immediately after (both landing before the victim's next chance to react), moving the pool ratio unfavorably for the victim and reverting it afterward — a classic sandwich, mechanically identical to the Curve-pool sandwich in the referenced report, except here the ocore contract offers *zero* slippage protection instead of a broken one.

### Impact Explanation
Any user (unprivileged AA trigger sender) who calls the swap functions of an AA built on this pattern can have their entire trade executed at an attacker-manipulated price, with no ability to abort the trade even if the received amount is far below fair value. This is a direct fund-loss impact reachable purely by posting ordinary payment units to a public AA address — matching the "AA fund loss" impact category.

### Likelihood Explanation
The pattern is exactly the reference/example AA distributed with ocore for building automated market makers on the platform; any AA author copying this pattern (a common and encouraged use case for the AA/oscript engine) inherits the flaw, and any trigger sender who swaps through such an AA is exposed. Exploitation only requires the ability to post units around a target's trigger and does not require any privileged or malicious-node behavior, so likelihood is high whenever such swap AAs are deployed and used.

### Recommendation
AA-based exchange contracts should accept a user-supplied minimum-output (or maximum-slippage) parameter in `trigger.data` (e.g. `trigger.data.min_amount`) and `bounce()` the trigger if the computed `$amount` falls below it, rather than relying solely on the AA's own live balance at execution time. Documentation/reference contracts such as `uniswap_like_market_maker.oscript` should be updated to demonstrate this pattern so AA authors do not copy the vulnerable version.

### Proof of Concept
1. AA author deploys an AA using the "exchange asset to bytes" / "exchange bytes to asset" logic shown above (no min-output check).
2. Attacker posts unit A: a large swap (e.g. asset→bytes) that shifts `balance[base]`/`balance[$asset]` unfavorably.
3. Victim's pre-broadcast trigger unit (bytes→asset swap) becomes stable in the same or next MCI and is executed against the manipulated balances per the deterministic `mci, level, unit` ordering in `aa_composer.js`/`main_chain.js`, receiving a much smaller `$amount` than expected.
4. Attacker posts unit B reversing their initial swap, restoring the pool and capturing the value extracted from the victim.
5. At no point could the victim's trigger specify or enforce a minimum acceptable `$amount`, so the AA pays out unconditionally per lines 118 and 140 of `uniswap_like_market_maker.oscript`.
