### Title
Divide-before-multiply precision loss in `other-debt-repayable` can trigger premature bad-debt socialization onto all vault suppliers - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Inside `liquidate`, the decision of whether a borrower's position has `no-collateral-left` (which drives `bad-debt-socialized`, i.e., wiping the borrower's remaining debt and writing down the shared vault `lindex` for **all depositors**) depends on `other-debt-repayable`, a value computed by dividing before multiplying in several chained steps, exactly the GMX bug-class described in the report.

### Finding Description
`other-debt-repayable` is computed as: [1](#0-0) 

Step by step:
1. `other-adj = div-bps-down(other-coll-usd, BPS + liq-penalty-max)` — a division.
2. `other-tokens = mul-div-down(other-adj, 10^debt-decimals, debt-price)` — multiplies the already-divided/truncated `other-adj` and divides again, compounding truncation instead of doing `other-coll-usd * 10^debt-decimals / (debt-price * (BPS+liq-penalty-max))` in one combined numerator/denominator step.
3. `other-scaled = mul-div-down(other-tokens, INDEX-PRECISION, other-borrow-idx)` then `mul-div-up(other-scaled, other-borrow-idx, INDEX-PRECISION)` — a round-trip scaled-debt conversion applied on top of the already-truncated `other-tokens`.

Each of these divisions truncates downward, and each truncated result feeds the next multiplication/division, so the cumulative rounding error is larger than if the whole expression were computed with a single combined numerator/denominator (the exact "multiplication after division" pattern flagged in the GMX report for `cache.fundingUsd`/`cache.positionPnlUsd`).

`other-debt-repayable` is then used only in a boolean check: [2](#0-1) 

If accumulated truncation pushes `other-debt-repayable` down to `u0` in a borderline case where the borrower's remaining, unliquidated collateral in *other* asset(s) is actually just barely sufficient to cover the remaining debt, `no-collateral-left` becomes `true` even though real collateral value existed. This triggers: [3](#0-2) 

which calls `socialize-debt-asset` → `vault-socialize-debt`, and inside the vault this write-downs the shared `lindex` used by every depositor of that vault: [4](#0-3) 

### Impact Explanation
`lindex` (the liquidity index used to compute every depositor's redeemable balance) is shared state written by the liquidator's transaction but consumed by every unrelated depositor of that vault. A borderline-case truncation error in `other-debt-repayable` computed via divide-then-multiply chains can cause the protocol to declare "no collateral left" prematurely and socialize debt that the borrower's other collateral could still have covered. This forces an artificial loss write-down onto all depositors in that vault — a socialization charged to unprivileged suppliers who did not cause and cannot prevent the mis-evaluation, i.e., temporary/permanent freezing (loss) of funds for those depositors. This lands in the in-scope **High** impact class (freezing/loss of unclaimed yield/principal value for third-party suppliers via socialized bad debt).

### Likelihood Explanation
This requires a borderline liquidation scenario where remaining collateral value is very close to the threshold that decides socialization, and where the multiple chained truncations (bps division, token conversion, scaled-debt round trip) are large enough relative to the margin to flip the boolean outcome. This is a narrow but realistic edge case for small-value residual collateral or low-decimal/high-price debt assets, consistent with the "Medium" likelihood typically assigned to this bug class in the original GMX report (repeated truncation, not attacker-controlled amplification, but reachable in ordinary liquidation flows without any privileged action).

### Recommendation
Compute `other-debt-repayable` using a single combined numerator/denominator instead of sequential divide-then-multiply steps, e.g. combine `other-coll-usd * 10^debt-decimals` into one multiplication before dividing by `debt-price * (BPS + liq-penalty-max)`, using an overflow-safe muldiv (analogous to OpenZeppelin's `Math.mulDiv`) as GMX ultimately adopted. Avoid the intermediate round-trip `mul-div-down`/`mul-div-up` conversion where possible, or ensure it strictly rounds in the direction that is conservative for depositors (i.e., never under-estimates `other-debt-repayable`, which would make `no-collateral-left` true when it should be false).

### Proof of Concept
Conceptual (arithmetic) PoC:
1. Borrower has a position with debt asset D (e.g., 6-decimals, high price) and multiple collateral assets, most of which get exhausted in a partial liquidation, leaving a `coll-remaining`/`other-coll-usd` value that is real but small — just at the threshold able to fully repay `remaining-debt-to-repay`.
2. Liquidator calls `liquidate` on the largest collateral. The code computes `other-coll-usd` for the position's remaining collateral (the other, non-liquidated collateral asset) at `mainnet/contracts/market/v0-4-market.clar:1514-1517`.
3. `other-debt-repayable` is derived via `div-bps-down` → `mul-div-down` → `mul-div-down`/`mul-div-up` chain (`v0-4-market.clar:1518-1525`). Choose `debt-price`, `liq-penalty-max`, and `debt-decimals` such that the sequential truncations in each step round `other-adj`, `other-tokens`, and the scaled round-trip down to zero cumulatively, even though a single combined-fraction computation would yield a strictly positive value.
4. `other-debt-repayable` evaluates to `u0`; combined with `coll-removed == u0` and matching list-length conditions, `no-collateral-left` becomes `true` (`v0-4-market.clar:1526-1532`), triggering `socialize-debt-asset` for the borrower's remaining debt even though the borrower actually retained enough collateral value to cover it.
5. `socialize-debt` executes in the debt vault, reducing `lindex` for the entire vault (`v0-vault-usdc.clar:948-967`), diluting every depositor's redeemable balance — harm inflicted on third parties who did not participate in the liquidation transaction.

Note: I could not fully verify the exact numeric magnitude/decimals combination needed to flip the boolean in a concrete on-chain scenario (would require running the Clarity arithmetic with specific price/decimals fixtures), so likelihood is stated as dependent on borderline collateral/price configurations rather than proven with concrete numbers.
