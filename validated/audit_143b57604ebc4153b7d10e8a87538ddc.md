### Title
Second preimage attack on `merkle.js` due to missing domain separation between leaf and internal node hashing - (File: `merkle.js`)

### Summary
`merkle.js` computes leaf hashes and internal-node hashes with the exact same single-round SHA-256 function and no distinguishing prefix/format, exactly the anti-pattern flagged in the referenced report. This lets anyone who can observe two sibling hashes at any level of a published tree craft a forged "element" (the concatenation of those two sibling hash strings) together with a truncated proof that verifies successfully against the real merkle root, without that value ever having been a genuine tree leaf. This primitive is reachable from unprivileged inputs via the `in merkle` address-definition authentifier and the `is_valid_merkle_proof()` oscript/AA function.

### Finding Description
`getMerkleRoot`/`getMerkleProof` hash leaves with `hash(element)` and internal nodes with `hash(hash_left + hash_right)` [1](#0-0) [2](#0-1) . `verifyMerkleProof` walks the proof by repeatedly calling the same `hash()` on the concatenation of the running hash and each sibling, starting from `hash(element)` [3](#0-2) . There is no leaf/node domain separation (e.g., a `0x00`/`0x01` prefix byte) and no double-hashing of leaves, so a leaf hash and an internal-node hash are computed identically and are indistinguishable to the verifier.

Because of this, if an attacker knows any two sibling hash strings `H_L` and `H_R` that were combined at some internal level of a published tree (these are visible to anyone who received/derived a proof, or who reconstructs the tree from public data-feed content), they can submit:
- `element' = H_L + H_R` (the exact concatenation used to produce the internal node),
- a `proof'` consisting only of the siblings from that internal node's *parent* upward (i.e., the original proof with the bottom two levels removed) and the original `root`.

`verifyMerkleProof(element', proof')` recomputes `hash(element') = hash(H_L + H_R)`, which is bit-for-bit identical to the real internal node hash, and the remaining siblings replay correctly up to the real `root`. The verification therefore succeeds even though `element'` was never one of the values actually included when the tree was built.

This primitive is reachable in two unprivileged paths:
1. **Address definition authentifier `in merkle`**: an address definition can require `['in merkle', [addresses, feed_name, element, min_mci]]`; the unit's `assocAuthentifiers[path]` supplies an attacker-controlled serialized proof, which is deserialized and checked with `merkle.verifyMerkleProof(element, proof)`, then the proof's `root` is looked up against a data feed [4](#0-3) . Any unit poster satisfying this authentifier path controls both `element` and the serialized proof.
2. **`is_valid_merkle_proof()` oscript function**, usable inside AA trigger data / bounce logic and general formulas, evaluates attacker-supplied `element` and `proof` (string or object) directly through `merkle.verifyMerkleProof` [5](#0-4) . An AA trigger sender fully controls both arguments.

### Impact Explanation
`in merkle` and `is_valid_merkle_proof` are designed as inclusion-membership gates — e.g., an oracle/DAO publishes a merkle root (via a data feed) representing a whitelist of `(address, amount)` or similar claim records, and legitimate members submit a proof of their own leaf to unlock a payment path or AA fund release. Because leaf and internal-node hashing are indistinguishable, an attacker who never appeared in the whitelist can forge an "element" equal to the concatenation of two sibling hashes from any level of the real tree and pass verification against the genuine, oracle-published root. If any AA or address-definition logic conditions a payout/authorization on `in merkle`/`is_valid_merkle_proof` succeeding for attacker-supplied data (a documented, intended usage of these primitives), this allows an unauthorized party to satisfy the membership check and trigger fund release/authorization that was never intended for them — i.e., unauthorized spending or AA fund loss.

### Likelihood Explanation
Exploitability requires only observing legitimate sibling hash pairs at some internal tree level, which are inherently exposed by design (they are exactly the "siblings" array handed out in any legitimate proof, or derivable by anyone with access to the full leaf set that the tree publisher hashed, which is frequently public — e.g., an open whitelist). No cryptographic break of SHA-256 is needed, only the well-known merkle "node-as-leaf" ambiguity; the code in `merkle.js` even contains a comment acknowledging this risk (`// Node-as-Leaf issue might matter in some cases`) without mitigating it [6](#0-5) . The attack is fully unprivileged: any unit author supplying an `in merkle` authentifier, or any AA trigger sender calling `is_valid_merkle_proof`, can attempt it.

### Recommendation
Add domain separation between leaf and internal-node hashing in `merkle.js`, e.g., prefix leaves with a distinct tag before hashing (`hash("0" + element)`) and/or prefix internal node concatenation with a different tag (`hash("1" + h1 + h2)`), or double-hash leaves as recommended by OpenZeppelin's merkle-tree library. Update `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently, and bump any serialized-proof format/version so old proofs are not silently misinterpreted.

### Proof of Concept
1. Build a tree over `arrElements = [e0, e1, e2, e3]` via `merkle.getMerkleRoot`/`getMerkleProof` [7](#0-6) ; let `H0=hash(e0)`, `H1=hash(e1)` be the leaf hashes combined into internal node `N01 = hash(H0+H1)`, and let `proof2 = merkle.getMerkleProof(arrElements, 2)` be the real proof for `e2`, whose sibling chain includes `N01` at the appropriate level and `root` at the top.
2. Attacker, who is not the owner of any of `e0..e3`, computes `element' = H0 + H1` and constructs `proof' = { index: (index of N01's position one level up), siblings: [ the remaining siblings from proof2 above the N01 level ], root: root }`.
3. Call `merkle.verifyMerkleProof(element', proof')` (or trigger it via the `is_valid_merkle_proof()` oscript function or the `in merkle` address-definition authentifier with `element'`/serialized `proof'`) — verification returns `true`, exactly as if `element'` were a genuine original leaf, confirming the second-preimage forgery [3](#0-2) [5](#0-4) .

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
