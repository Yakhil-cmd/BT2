### Title
RPC middleware logs raw `author_insertKey` seed/URI parameters in cleartext to trace logs - ([File: substrate/client/rpc-servers/src/middleware/mod.rs])

### Summary
The `Middleware::call` in `substrate/client/rpc-servers/src/middleware/mod.rs` invokes `RpcMetrics::on_call` on **every** incoming JSON-RPC request, before any per-method authorization (`check_if_safe`) is evaluated by the handler itself. [1](#0-0) 
`on_call` unconditionally logs the full, unredacted parameter payload of the request at `trace` level: [2](#0-1) 
`author_insertKey` (and `author_hasKey`) accept the raw secret key URI/seed phrase (`suri: String`) as a plain RPC parameter: [3](#0-2) 
The handler itself only redacts nothing — the `suri` is passed straight to `Keystore::insert`: [4](#0-3) 

### Finding Description
This closely mirrors CWE-532 in the Undertow advisory: a framework-level component logs the entire request object (including sensitive fields) regardless of whether the underlying application intends to expose that data, and regardless of whether the request ultimately succeeds or is denied.

Here, `MiddlewareLayer`/`Middleware` wraps the jsonrpsee service stack for every configured Substrate RPC server (HTTP/WS). The `on_call` metrics hook runs unconditionally for all requests, before `service.call(req.clone())` is awaited, i.e., before `check_if_safe(ext)` inside `Author::insert_key` has a chance to reject the call for unsafe-RPC-disabled nodes. If the operator enables `trace` (or `rpc_metrics::extra` for full param dumps in `on_response`) logging for the `rpc_metrics` target — a supported, documented logging target, not a debug-build-only artifact — every call to `author_insertKey`, `author_hasKey`, or any other method carrying secret material in its parameters is written verbatim to the node's log output via `log::trace!("... params={:?}", req.params())`.

Unlike Undertow (which logged at ERROR level on failure paths only), this variant is worse in one respect: it fires on the request path for *every* call attempt, success or failure, safe or unsafe method, so even blocked/rejected `author_insertKey` attempts still get their `suri` written to the trace log before the safety check executes.

### Impact Explanation
If `suri` (a raw private key/seed phrase or derivation path) reaches disk-persisted or externally shipped logs (common in production observability pipelines that ship trace/debug logs), an attacker with read access to those logs (log aggregation compromise, misconfigured retention, shared hosting) obtains the plaintext key material and can fully impersonate the account/validator identity — theft of funds or unauthorized validator actions. This matches the "Critical: credential exposure via logs" class from the report, scaled to the blockchain-key-material context.

### Likelihood Explanation
This is conditioned on the operator explicitly enabling `trace` logging for the `rpc_metrics` target and exposing the RPC server’s unsafe methods (or an internal/ops process invoking `author_insertKey` over a locally-exposed but log-monitored RPC endpoint). Default log levels in Substrate nodes are `info`, and `author_insertKey`/other unsafe RPCs are rejected unless `--rpc-methods=unsafe` (or local-only) is set. I could not fully verify within the remaining budget whether `check_if_safe` is enforced strictly before the RPC dispatch reaches `Author::insert_key`'s body in all transports, nor whether any log redaction/scrubbing exists elsewhere in the jsonrpsee pipeline that would prevent `Debug` formatting of `Bytes`/`String` params from including the raw `suri`. This uncertainty, plus the operator-controlled log-level prerequisite, places this at most at Medium likelihood, not a directly attacker-triggerable, always-on leak.

### Recommendation
Redact or omit parameters for RPC methods known to carry secret material (e.g., `author_insertKey`, `author_hasKey`) in the `on_call`/`on_response` trace logging paths in `substrate/client/rpc-servers/src/middleware/metrics.rs`, either via an explicit denylist of method names or by never logging raw `params()` at any level for methods marked "unsafe"/`with_extensions`. Alternatively, redact the `suri` field of `author_insertKey` before it reaches any logging sink, matching the `SecretString`/`expose_secret()` pattern already used elsewhere in the CLI (`substrate/client/cli/src/commands/insert_key.rs`, `substrate/client/cli/src/commands/utils.rs`) but seemingly not applied to the RPC parameter itself.

### Proof of Concept
I was not able to complete an executable local reproduction within the available tool budget. A reproduction would require: (1) starting a node with `--rpc-methods=unsafe` and `-l rpc_metrics=trace`, (2) issuing `author_insertKey` with a test seed over RPC, (3) inspecting stdout/log output for the literal seed string logged by `RpcMetrics::on_call`/`on_response` in `substrate/client/rpc-servers/src/middleware/metrics.rs:207-217` and `:242-267`. This was not executed; the analysis is based on static code tracing only. Given the unverified enforcement ordering of `check_if_safe` relative to the middleware `on_call` hook, and the required non-default log-level configuration, I flag this as a **provisional Medium-severity** finding requiring dynamic confirmation, not a confirmed Critical exploit.

	fn insert_key(
		&self,
		ext: &Extensions,
		key_type: String,
		suri: String,
		public: Bytes,
	) -> Result<()> {
		check_if_safe(ext)?;

		let key_type = key_type.as_str().try_into().map_err(|_| Error::BadKeyType)?;
		self.keystore
			.insert(key_type, &suri, &public[..])
			.map_err(|_| Error::KeystoreUnavailable)?;
		Ok(())
	}
