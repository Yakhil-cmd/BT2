## Analysis

The reported bug class — EIP-712 message hashes lacking `chainId`, enabling a signature valid on one chain to be replayed on another — has a structural analog in nearcore's meta-transaction (NEP-366/NEP-611) signing scheme.

### Title
Meta-transaction (`DelegateAction`) signatures lack any chain/network binding, enabling cross-network signature replay - (`core/primitives/src/action/delegate.rs`)

### Summary
`SignedDelegateAction` and `VersionedSignedDelegateAction` are verified purely from a hash over `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`, and an off-chain/on-chain NEP discriminant. Unlike ordinary `Transaction`s, which bind to a specific chain via `block_hash` (a value that is unique per network), `DelegateAction` contains no chain- or genesis-specific identifier at all.

### Finding Description
`DelegateAction::get_nep461_hash` and `VersionedDelegateActionPayload::get_nep461_hash` build the signed payload via `SignableMessage::new(&self, SignableMessageType::DelegateAction[/V2])`, hashing only the NEP discriminant plus the action fields.

Signature verification (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) checks only that this hash matches the signature under `public_key` — nothing chain-specific is checked. [2](#0-1) [3](#0-2) 

At runtime, `apply_delegate_action` only re-verifies the signature, checks `max_block_height`, `sender_id` match, and delegates key/nonce validation to `validate_delegate_action_key` — none of these bind the signature to a specific network/genesis. [4](#0-3) 

By contrast, a regular `Transaction` includes `block_hash`, a value inherently unique to a specific chain, which is the mechanism ordinary NEAR transactions rely on for chain-scoping and freshness. [5](#0-4) [6](#0-5) 

`DelegateAction` deliberately carries only `nonce` and `max_block_height` (a plain integer, not a hash), with no analogous chain-binding field. [7](#0-6) 

Notably, nearcore's own mirroring tooling (`tools/mirror`) remaps keys specifically when moving accounts between an original chain and a forked/mirrored chain, which is circumstantial evidence that account state (same `sender_id`/`public_key`) can legitimately exist in parallel across multiple NEAR-protocol-based networks (mainnet forks, appchains built from this codebase, or migrated testnets). [8](#0-7) 

### Impact Explanation
If the same account (`sender_id` + `public_key`) exists with matching nonce/access-key state on two different NEAR-protocol networks (e.g., a genesis-forked testnet, a chain split, or another chain built on nearcore that shares initial account state), a `SignedDelegateAction` an account holder intended for use on chain A can be forwarded by any relayer and executed unmodified on chain B. This results in unauthorized action execution (e.g., adding a full-access key, transferring funds, calling contracts) on a network the signer never intended to authorize — an unauthorized state/balance change carried out by an untrusted relayer.

### Likelihood Explanation
This requires a relatively narrow precondition: the sender account must exist with matching public key and nonce state on two different networks derived from/related to nearcore (forked testnets, chain-migration snapshots, or independent appchains sharing initial state). It cannot be exploited against two arbitrary unrelated NEAR deployments with independent account histories, since nonces and account existence diverge over time. This limits likelihood to specific migration/fork scenarios rather than general mainnet/testnet cross-replay.

### Recommendation
Include a chain- or genesis-specific binding value (e.g., `genesis_hash`/`chain_id`) in the `SignableMessage`/`DelegateAction` payload that is hashed and signed, analogous to how EIP-712 recommends including `chainId`, and analogous to how `Transaction` already binds to `block_hash`. This ties a `DelegateAction` signature to one specific chain and prevents cross-network replay even when account state coincidentally matches across networks.

### Proof of Concept
1. Network A and Network B are both nearcore-based chains that, at some point, shared genesis/account state for account `alice.near` with public key `K` and access-key nonce `N` (e.g., B is a fork/mirror of A, or a migrated testnet).
2. Alice signs a `DelegateAction{sender_id: alice.near, receiver_id: X, actions: [...], nonce: N+1, max_block_height: H, public_key: K}` intending it to run on Network A via relayer R.
3. Relayer R (or any party who obtains the `SignedDelegateAction`) instead wraps it in a transaction addressed to Network B, where Alice's account also has nonce `N` at that key.
4. `apply_delegate_action` on Network B verifies the signature successfully (per `SignedDelegateAction::verify`, `core/primitives/src/action/delegate.rs:83-96`) since no chain-specific data was in the signed hash, and the action executes on Network B without Alice's chain-B-specific consent.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateActionV2);
        let bytes = borsh::to_vec(&signable).expect("failed to serialize");
        hash(&bytes)

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
