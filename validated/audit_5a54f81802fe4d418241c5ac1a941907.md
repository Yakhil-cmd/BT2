### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target of an incoming `status` webhook purely by `Commit.where(sha: params.sha)`, with no scoping to the repository that authenticated the webhook. Because the outer `verify_signature` check only proves the payload was signed for *some* repository/organization known to this Shipit instance — not that it was signed for the specific repository whose commit is being mutated — an attacker who controls any Shipit-integrated repository can forge a `codecov/project` status for a SHA that also exists in a victim stack (trivially achievable via forking/mirroring, since git SHAs are content-addressed and identical across clones/forks of the same history).

### Finding Description
The invariant claimed by the code is: **`status.repository == commit.stack.repository`** (a status webhook should only ever mutate commits belonging to the repository that signed it). The actual code never establishes this equality:

- `WebhooksController#verify_signature` verifies the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body (`params.dig('repository', 'owner', 'login')`) [1](#0-0) . This only proves the request was signed for *that* organization's webhook secret — it says nothing about which commit rows get touched.
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
`Commit` is a global table shared by every `Stack`/`Repository` in the Shipit instance (`belongs_to :stack`, and `Stack` `belongs_to :repository`), and this query has no `stack_id`/`repository_id` filter — it matches **every** commit row across every tenant with the same SHA [3](#0-2) .
- `create_status_from_github!` then writes the status and recomputes `deployable?`/`blocked?`/scheduling for whichever stack owns that commit, regardless of which repository actually authenticated the webhook [4](#0-3) [5](#0-4) .

Exploit flow: an attacker who owns (or forks/mirrors) a GitHub repository that is already integrated with this Shipit instance can fork the victim's public repository, obtaining commits with the *exact same SHA-1* values as those recorded for the victim's stack (git SHAs are computed from tree/parent/author content, not from the remote they are pushed to). The attacker then sends a normally-signed `status` webhook for their own repository/org (`context: codecov/project`, `state: success`, `sha: <shared sha>`). This passes `verify_signature` legitimately. `StatusHandler#process` then applies the status to **all** matching `Commit` rows, including the victim's, because the lookup is unscoped.

The `review_stacks_enabled`/`provision?` precedence issue in `PullRequest::OpenedHandler#provision?` [6](#0-5)  is a real operator-precedence bug (`&&` binds tighter than `||`, so `provisioning_behavior_allow_with_label?`/`prevent_with_label?` branches can provision a review stack even when `review_stacks_enabled` is false), but it is **unrelated to `StatusHandler`**: `review_stacks_enabled` only gates automatic creation of new review stacks from pull requests, not whether an already-existing stack's `Commit` rows accept incoming statuses. Once any stack/commit exists in the database — review-stack or not — `StatusHandler` will happily mutate it regardless of `review_stacks_enabled`. The question's causal link between the two bugs does not hold, but the underlying cross-tenant write via unscoped SHA lookup is independently real and sufficient to break the stated invariant.

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`, model validations) checks that the commit being mutated belongs to the repository/org that signed the webhook.

### Impact Explanation
A payload validly signed for repository/org A can flip the CI status of a commit belonging to stack/repository B, as long as both share a commit SHA (achievable at will via fork/mirror of a public repo). If the forged context (`codecov/project`) is in `stack.required_statuses`, `blocking_statuses`, or otherwise affects `Commit#deployable?`/`blocked?`, this can force `stack.schedule_merges` and `ContinuousDeliveryJob` to trigger an unauthorized deploy, or conversely block a legitimate deploy — matching "a payload for one repository mutating another's stack, commit... or an unauthorized deploy" in the Critical impact category. The blast radius spans every tenant stack on the shared Shipit instance whose commit history overlaps (even partially, via shared upstream commits) with any repository the attacker can legitimately sign webhooks for.

### Likelihood Explanation
Preconditions: the attacker must already control (or be able to add) at least one repository that is integrated with the target Shipit instance and can therefore produce a validly-signed webhook — a low bar for any self-service multi-tenant Shipit deployment. The attacker additionally needs a commit SHA shared with the victim's stack, trivially obtained by forking/mirroring the victim's public repository (identical git objects, identical SHAs). No GitHub App private key, `webhook_secret`, or Shipit session is required beyond what the attacker already legitimately possesses for their own integrated repository. This is fully repeatable and requires no timing/race conditions.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) to the repository that authenticated the webhook, e.g. join through `stack.repository` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })`, deriving `repository` the same way `verify_signature` derives `repository_owner`/full name from the payload. Separately, fix the operator-precedence bug in `PullRequest::OpenedHandler#provision?` by explicitly parenthesizing so `review_stacks_enabled` gates all three provisioning-behavior branches.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repository_a` (attacker's, `review_stacks_enabled` irrelevant) and `repository_b` (victim, `review_stacks_enabled: false`) with `stack_b` requiring `codecov/project` in `required_statuses`.
2. Create `commit_b` under `stack_b` with `sha: "deadbeef..."` and no existing `codecov/project` status; assert `commit_b.deployable?` is `false` (binding: `commit_b.stack.repository == repository_b`, status originates from `repository_a`).
3. Also create `commit_a` under a stack belonging to `repository_a` with the **same** `sha`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(build_params(sha: "deadbeef...", context: "codecov/project", state: "success")).call` (simulating a webhook validly signed for `repository_a`).
5. Reload `commit_b`; assert its `status.success?` is now `true` and `deployable?` changed to `true`, even though the webhook never authenticated for `repository_b` — proving the cross-repository write and disproving the claimed binding.
