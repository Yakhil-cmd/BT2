### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while event handlers act on an unrelated `repository.full_name`/commit `sha`, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), both attacker-controlled JSON fields in the raw webhook body. [1](#0-0)  The event handlers that subsequently act on the verified payload, however, identify *which repository/commit to mutate* using a completely different field — `repository.full_name` — or, in the case of commit statuses, no repository scoping at all. [2](#0-1) [3](#0-2) 

### Finding Description
`Shipit.github(organization:)` only enforces a match against the requested `organization` when the deployment uses the multi-organization credentials schema (`github_default_organization` present); it looks up per-org config via `github_app_config(organization)`. [4](#0-3)  `GitHubApp#verify_webhook_signature` explicitly treats a blank/nil `webhook_secret` as "always verified":

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [5](#0-4) 

This is a documented, supported configuration state (nil `webhook_secret` per organization), as shown in the multi-org fixture where each org can independently have `webhook_secret: # nil`. [6](#0-5) 

Consequently, in a multi-organization Shipit deployment, an attacker who knows (or who can pick) the identity of **any one** onboarded organization with no configured `webhook_secret` can craft a raw JSON body where:
- `repository.owner.login` (or `organization.login`) = that org (auth bypass side), and
- `repository.full_name` = a **different**, victim organization's repository that does have stacks configured in Shipit.

`verify_signature` will select the attacker-chosen org's config, see `webhook_secret` is blank, and set `verified = true` unconditionally — no valid HMAC is required at all. [7](#0-6)  The request then proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and handlers resolve the target `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — the victim org/repo, never cross-checked against the org used for authentication. [2](#0-1) 

`StatusHandler` is even less scoped: it updates `Commit.where(sha: params.sha)` across the entire installation with no repository check whatsoever, so a forged `status` webhook can set the state of any known commit SHA in any stack. [3](#0-2) 

This breaks the trust binding: **organization that authenticated the request ≠ repository/commit that is written by the handler**.

### Impact Explanation
An attacker able to onboard, or already aware of, one weakly-configured organization (no `webhook_secret`) in a multi-org Shipit instance can forge `push`, `status`, `check_suite`, `pull_request`/`merge`, or `membership` webhooks for stacks belonging to a completely unrelated, victim organization, without ever possessing that victim's `webhook_secret`. Forged `status` events can mark arbitrary commits as `success`, which feeds into deploy-readiness/merge-queue checks (`create_status_from_github!` → deployable status), potentially enabling an unauthorized deploy or merge decision on a victim stack. This satisfies the High-impact bar of "escalation ... or an unauthorized deploy, rollback or merge" via a broken cross-organization authentication boundary.

### Likelihood Explanation
This requires only an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and mismatched `X-Github-Event`/no valid signature required, no GitHub credentials, no Shipit session — provided at least one configured organization has a blank `webhook_secret` (an explicitly supported state in the code and fixtures) or the attacker knows any single org's secret while targeting another org's repository. Multi-org GitHub App deployments where organizations are onboarded with differing security postures make this a realistic deployment shape.

### Recommendation
- Cross-validate that `repository.owner.login`/`organization.login` (used to select the verifying webhook secret) matches `repository.full_name`'s owner before dispatching to handlers.
- Do not implicitly treat a blank `webhook_secret` as "verified" — require secrets be configured per organization, or reject payloads if the resolved repository/org doesn't correspond to the organization whose secret validated the signature.
- Scope `StatusHandler` (and other handlers) to the repository identified during signature verification, not solely to `Commit.sha`.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub App config: `OrgWeak` (no `webhook_secret`) and `OrgVictim` (has stacks configured, has its own secret).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "OrgWeak" },
  "repository": { "owner": { "login": "OrgWeak" }, "full_name": "OrgVictim/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/build"
}
```
No valid `X-Hub-Signature` is required because `OrgWeak`'s `webhook_secret` is blank, so `verify_webhook_signature` returns `true` per `lib/shipit/github_app.rb:76-83`.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) applies the forged "success" status to the matching commit in `OrgVictim`'s stack, with no check that `OrgVictim` was ever authenticated.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
