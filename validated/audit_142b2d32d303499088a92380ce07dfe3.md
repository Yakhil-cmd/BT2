Based on my research, I found a genuine analog to the reported bug class: a field used to select the *trust context* (which secret verifies the signature) is not cryptographically bound to the field that actually determines *what gets written* — mirroring the L1/L2 timestamp confusion, where a value from one trust domain is silently assumed to be consistent with another.

### Title
Webhook organization used to select the signing secret is not bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on a field pulled out of the *same untrusted JSON body* that is about to be verified: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` is used purely to pick *which secret* to check the signature against. The signature check itself (`verify_webhook_signature`) then HMACs the entire raw body against that chosen secret: [3](#0-2) 

While the whole raw body is technically covered by the HMAC, the *secret used* is chosen by a value inside that same body. In a multi-org Shipit installation (`config/secrets.*.yml` supports per-organization `github:` blocks with independent `webhook_secret`s, as shown in `config/secrets.development.shopify.yml`), a party who legitimately administers **their own** GitHub org/app installation knows **their own** `webhook_secret`. Nothing stops them from crafting a POST to `/webhooks` where `repository.owner.login` (used only to pick the verifying secret) is their own org, while other payload fields actually used downstream to resolve the target `Stack`/`Repository` (e.g. `repository.full_name`) are set to an unrelated, victim-owned repository that also happens to be tracked by the same shared Shipit instance. Because the signature check only proves "this body was signed by *someone's* configured secret," not "this body pertains to the org whose secret was used," the equality `authenticated_organization == repository_being_written` is never actually enforced — the same class of unstated cross-domain equality assumption as `_timestamp` (from L1) being compared against `block.timestamp` (on L2) in the reported finding.

### Impact Explanation
If exploitable, this allows a party with only self-service control of their own GitHub org/app (an "unprivileged" actor with respect to any other tenant) to inject forged `push`, `status`, `check_suite`, or `pull_request` webhook events that are attributed to a different repository/stack, potentially triggering unintended `GithubSyncJob`, status writes, or check-run refreshes for a stack they do not control — a cross-repository write.

### Likelihood Explanation
This requires a multi-organization Shipit deployment where multiple independent parties each have their own GitHub App/webhook_secret configured against the same Shipit instance, and requires the downstream event handlers to key off a payload field (e.g. `repository.full_name`) that is different from the field used for secret selection (`repository.owner.login`/`organization.login`). I was not able to fully confirm, within the available tool budget, the exact field(s) used by `app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, and `check_suite_handler.rb` to resolve the target `Stack`/`Repository` — I could only confirm (via `grep_search`) that `full_name` appears in the shared `handler.rb` base class and several `pull_request/*` handlers, not the exact line-level logic. This is a material gap: if those handlers additionally re-validate that `repository.owner.login` matches the resolved repository's owner, this analog would not be exploitable. I could not verify this within the remaining tool calls.

### Recommendation
- In `verify_signature`, do not select the verification secret from an untrusted, unauthenticated field of the same payload being verified. Alternatively, after successful HMAC verification, re-derive/re-check that the organization whose secret validated the signature matches the owner of the repository the handler is about to act on, and reject on mismatch.
- Audit all webhook handlers (`app/models/shipit/webhooks/handlers/**`) to confirm the field(s) they use to resolve `Stack`/`Repository` are the same field(s) used to select the verifying secret.

### Proof of Concept
Conceptual (not fully verified against handler internals):
1. Attacker operates `attacker-org`, which has its own Shipit-configured GitHub App with `webhook_secret = S`.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push`, `X-Hub-Signature` computed with `S`, and a body where `repository.owner.login = "attacker-org"` (drives secret selection) but `repository.full_name = "victim-org/victim-repo"` (a stack tracked in the same Shipit instance).
3. `verify_signature` selects `attacker-org`'s app via `repository_owner`, and the signature validates because it was actually computed with `S`.
4. `create` re-parses the same body and dispatches to `Shipit::Webhooks.for_event('push')`, which (pending confirmation of exact handler logic) may act on `victim-org/victim-repo` based on `repository.full_name`.

Due to the tool-call limit, I could not directly read `push_handler.rb`'s stack-resolution code to confirm step 4 conclusively; this should be verified against `app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, and `check_suite_handler.rb` before treating this as fully proven.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
