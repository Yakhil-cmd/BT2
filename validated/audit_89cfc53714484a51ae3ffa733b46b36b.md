### Title
Webhook signature verified against `repository.owner.login` while stack resolution uses the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to authenticate a webhook against using `repository.owner.login` (falling back to `organization.login`), but the actual handlers that act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target `Stack` using the sibling field `repository.full_name`. Nothing ties these two fields together, so a party who legitimately knows the `webhook_secret` for one onboarded GitHub organization can forge a signed payload whose `repository.full_name` points at a completely different organization's repository, causing Shipit to act on stacks the sender has no relationship to.

### Finding Description
`verify_signature` computes the signing organization from the payload itself: [1](#0-0) [2](#0-1) 

This `repository_owner` is used only to pick which configured GitHub App's `webhook_secret` should HMAC-verify the raw request body: [3](#0-2) 

Once verification passes, `create` blindly dispatches the full parsed JSON to the registered handlers: [4](#0-3) 

Handlers, however, resolve the *target* stack using a **different** field of the same JSON object — `repository.full_name` — not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`PushHandler` uses this to trigger a GitHub sync on any stack whose repository matches `full_name` and branch matches attacker-controlled `ref`: [7](#0-6) 

Since Shipit explicitly supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` configured under `github.<org>.webhook_secret`: [8](#0-7) 

...the binding that should hold is: *the organization whose secret authenticated the request* == *the organization/repository the request is allowed to act on*. Because `verify_signature` and the handlers key off two independently-controlled JSON fields (`repository.owner.login` vs `repository.full_name`) inside the very payload the signer controls, that equality is never enforced. Anyone who legitimately possesses the `webhook_secret` for **their own** onboarded organization (set on the GitHub App they administer) can set `repository.owner.login` to their own org (to pass signature selection/verification) while setting `repository.full_name` to `victim-org/victim-repo`, and the HMAC — computed over the whole raw body with their own known secret — will validate.

This is the same class of bug as the disclosed geth issue: a value is trusted/acted upon (the peer's declared identity / here, `repository.full_name`) that is not actually constrained by the verified credential (secp256k1 point validity / here, the org-derived `webhook_secret`).

### Impact Explanation
An attacker who administers a GitHub App for one organization onboarded into a shared Shipit instance can forge `push`/`check_suite` events that reference stacks belonging to a different, unrelated organization. This triggers `Stack#sync_github`/`GithubSyncJob` and `schedule_refresh_check_runs!` on stacks the attacker has no GitHub access to, potentially interacting with continuous-deployment logic and CI-gating checks on someone else's stack — an unauthorized action against a repository/stack outside the caller's authenticated scope. This matches the "High" bar of escalation via a deployment-trust binding break (organization authenticated vs. repository acted upon).

### Likelihood Explanation
Requires the deployment to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to be an administrator of the GitHub App for at least one of those organizations (so they know its `webhook_secret`) — not privileged access to Shipit itself, not the app's `GITHUB_TOKEN`, and not repository write access on the victim org. This is a realistic scenario for shared/managed Shipit deployments serving several business units or external partner orgs.

### Recommendation
In `WebhooksController#verify_signature` and/or `Shipit::Webhooks::Handlers::Handler`, cross-check that the organization used to select the verifying `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting (422) any payload where they diverge.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`: `OrgA` (attacker-administered GitHub App, secret `S_A` known to attacker) and `OrgB` (victim, has a Shipit stack `orgb/victim-repo`).
2. Attacker crafts a raw JSON body for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<arbitrary-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "orgb/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using the secret they legitimately possess for OrgA.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's `webhook_secret`, and the HMAC validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `create` dispatches to `PushHandler`, which resolves the target stack via `repository.full_name = "orgb/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), triggering `sync_github` on OrgB's stack despite the request never being authenticated against OrgB's credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
