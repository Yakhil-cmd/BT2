### Title
Signature verification is keyed by an attacker-controlled `repository.owner.login`, decoupling authenticated organization from the repository actually written to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App/organization secret to use for HMAC verification directly from the untrusted, unauthenticated request body, before the signature has been checked. The downstream webhook handlers then act on a *different* field of that same body (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. Because these two fields are only loosely related (both attacker-supplied, both under the same JSON payload, but never cross-checked against each other), an organization whose `webhook_secret` is unset can be used to "authenticate" a forged webhook that actually targets a repository belonging to a completely different, properly-secured organization.

### Finding Description
`verify_signature` computes the org to authenticate against straight from the request body: [1](#0-0) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That value is used to look up a `GithubApp`/config entry and check the `X-Hub-Signature` against **that org's** `webhook_secret`: [2](#0-1) 

`GithubApp#verify_webhook_signature` explicitly no-ops when the resolved org has no secret configured: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

This "no secret configured" state is a documented, supported configuration shape (`webhook_secret: # nil` is shown as a valid entry per organization in the sample multi-org config): [4](#0-3) 

Meanwhile, every webhook `Handler` resolves the `Stack`/`Repository` to mutate from a **different** JSON field — `repository.full_name` — never re-checked against `repository.owner.login` or against which org's secret actually authenticated the request: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, for instance, uses this to trigger `stack.sync_github` for whatever stacks match `repository.full_name`: [6](#0-5) 

**The broken binding, as an equality:**
`organization authenticated by verify_signature (repository.owner.login → org's webhook_secret)` **must equal** `repository actually written to by the Handler (repository.full_name)`. Nothing in the controller or `Handler` base class enforces this equality — both fields are independently attacker-controlled in the same unauthenticated request body, and only one of them (`repository.owner.login`) gates which secret is checked.

**Before/after across the request:**
- Before: Attacker has no signing key. A normal webhook for org `secured-org/victim-repo` is rejected unless signed with `secured-org`'s `webhook_secret`.
- After: Attacker POSTs a forged body where `repository.owner.login` = `"unsecured-org"` (an org onboarded into Shipit's multi-tenant config without a `webhook_secret`, e.g. a dev/staging org or one still being provisioned) but `repository.full_name` = `"secured-org/victim-repo"`. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret to check), so the request passes with **no signature at all**. The handler then acts on `repository.full_name`, mutating `secured-org/victim-repo`'s tracked commits/status/stacks as if GitHub had legitimately sent the event.

### Impact Explanation
This is an authentication bypass with cross-repository write consequences, matching the report's "Critical" bar directly:
- A `push` webhook forged this way triggers `GithubSyncJob`/`Stack#sync_github` for the victim repository's stacks, injecting attacker-chosen commits into Shipit's tracked history for a repo the attacker does not control.
- A `status`/`commit_status` webhook forged this way can mark an arbitrary victim commit's CI status as passing, which — combined with continuous deployment or a human clicking Deploy — leads to an unauthorized deploy of unvetted code.
- `merge`/`pull_request` events can similarly be forged to affect merge-queue state on stacks belonging to organizations the attacker has no access to.

This requires no `ApiClient` token, no `webhook_secret`, no GitHub App key, and no repository write access to the victim org — only that *some* organization onboarded into the multi-tenant Shipit config has an unset `webhook_secret` (a state the code itself treats as valid and silently permits).

### Likelihood Explanation
Likelihood depends on operational configuration: it requires a Shipit deployment that serves more than one GitHub organization and where at least one onboarded organization has not yet configured (or intentionally omitted) a `webhook_secret` — a state explicitly modeled and accepted by `GithubApp#verify_webhook_signature` and shown as a valid example in the shipped multi-org secrets template. In any such deployment, exploitation requires only a single unauthenticated HTTP POST with a crafted JSON body; no credentials, timing races, or privileged access are needed.

### Recommendation
Bind the authenticated identity to the resource acted upon instead of trusting two independently-supplied payload fields:
- Require `repository.owner.login` (or `organization.login`) to match the owner portion of `repository.full_name` before dispatching to handlers, rejecting mismatches with 422.
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank in production; treat a missing secret for a configured organization as "reject all webhooks for this org" rather than "accept unsigned webhooks for this org."
- Consider deriving the org/repo used for verification and the org/repo used for mutation from the same single, unambiguous field, so no attacker-controlled field can select a different trust domain than the one actually being written to.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. via `config/secrets.yml`:
   - `secured-org`: `webhook_secret: <real-secret>` (tracks stack `secured-org/victim-repo`)
   - `unsecured-org`: `webhook_secret:` (nil/unset, e.g. a staging org not yet fully provisioned)
2. POST to `/webhooks` (unauthenticated, no valid `X-Hub-Signature` needed) with:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "secured-org/victim-repo",
       "owner": { "login": "unsecured-org" }
     }
   }
   ```
   and header `X-Github-Event: push`.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"unsecured-org"`, calls `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)`, which returns `true` because `webhook_secret` is blank for that org — no valid signature is required.
4. `PushHandler#process` runs unauthenticated, looks up stacks via `Repository.from_github_repo_name("secured-org/victim-repo")`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing Shipit to sync a commit into `secured-org/victim-repo`'s tracked history without any GitHub-verified signature for that organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
