Confirmed: `Repository.from_github_repo_name` at [1](#0-0)  parses `full_name` independently and does zero cross-check against the `owner.login` field used for signature verification.

### Title
Signature-verified org (`repository.owner.login`) is decoupled from the acted-upon repository (`repository.full_name`), allowing cross-org ReviewStack respin - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check based solely on `params.dig('repository','owner','login')`, while `ReopenedHandler#repository` resolves the actual `Repository` record to mutate using the unrelated `params.repository.full_name` field from the same attacker-controlled JSON body. Because these two values are never cross-validated to refer to the same GitHub repository, a payload whose `owner.login` names an org with no configured `webhook_secret` (or whose secret the attacker otherwise controls) passes signature verification trivially, while `full_name` can simultaneously name a completely different, fully-protected victim repository whose ReviewStack is then unarchived/re-created using attacker-chosen `head.sha`/`head.ref`.

### Finding Description
The claimed binding is: `repository_owner` used in `verify_webhook_signature` (`params.dig('repository','owner','login')`, [2](#0-1)  ) MUST equal the owner encoded in `params.repository.full_name` used to select the record acted upon in the handler ( [3](#0-2) ).

Tracing the code:
- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, raw_post)`, where `webhook_secret` is looked up per-organization and, per `GitHubApp#verify_webhook_signature`, `return true unless webhook_secret` [4](#0-3) . This "no secret configured for an org" state is a documented, supported configuration (`webhook_secret: # nil` in `config/secrets.development.example.yml` and `docs/setup.md`'s multi-org section), so at least one org in a multi-org Shipit install can legitimately have signature checking effectively disabled.
- `ReopenedHandler#repository` resolves the `Repository` purely from `params.repository.full_name` via `Repository.from_github_repo_name`, which just splits the string on `/` and does a DB lookup — it never checks it against `repository.owner.login` [1](#0-0) .
- `ReopenedHandler#process` → `unarchive?`/`stack.unarchive!` (via `ReviewStackAdapter#unarchive!`/`#find_or_create!`) then acts on that resolved repository's ReviewStack using `params.pull_request.head.sha`/`ref` taken straight from the same payload [5](#0-4) , [6](#0-5) .

Attacker request: a `pull_request` `reopened` webhook JSON body with `repository.owner.login` set to an org whose Shipit `webhook_secret` is unset (or otherwise attacker-controllable), but `repository.full_name` set to `"victim-org/victim-repo"`, plus attacker-chosen `pull_request.head.sha`/`ref` and a `number` matching a previously-provisioned-then-torn-down victim ReviewStack (or a fresh PR number to trigger `find_or_create!`). `verify_signature` passes because the org resolved from `owner.login` has no secret; the handler then resolves and mutates the victim repository's stack using `full_name`, entirely bypassing the intended per-repo authentication guarantee.

Existing guards do not close this gap: `verify_signature` never compares its resolved org against `full_name`'s owner, `drop_unhandled_event`/`check_if_ping` are irrelevant, `ExplicitParameters` only enforces payload *shape* (types/presence) not cross-field consistency [7](#0-6) , and `Repository` model validations only constrain `owner`/`name` character format, not that they match a specific verified org.

### Impact Explanation
An attacker can force unauthorized re-provisioning of a victim's ReviewStack (build/deploy-adjacent action) using attacker-chosen `head.sha`/`ref`, for any repository tracked by the same Shipit instance, as long as some org configured in that instance's `github` secrets section lacks a `webhook_secret`. This is a payload-for-one-repository-mutating-another's-stack scenario, matching the Critical impact category. It is repeatable against any victim repository/PR number on the same Shipit deployment and is not limited to a single tenant if the instance hosts multiple orgs.

### Likelihood Explanation
Requires: (1) `repository.review_stacks_enabled` and matching `provisioning_behavior` for the victim repo (attacker-controllable choice of target, but org-level provisioning policy must allow it), and (2) at least one org configured in Shipit's multi-org `github` secrets with no `webhook_secret` set — a state the project's own example configs (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) show as a normal/expected setup, not a misconfiguration flagged anywhere in code. Attacker cost is a single unauthenticated HTTP POST to `/webhooks`; no secrets, sessions, or privileged roles are needed.

### Recommendation
In `WebhooksController#verify_signature` (or in the handler layer), require that the organization used to select/verify the webhook secret match the owner encoded in `params.repository.full_name` (and reject if they diverge), and/or require every org used to receive webhooks to have a mandatory non-nil `webhook_secret`, rejecting requests when `verify_webhook_signature` would otherwise short-circuit to `true`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure `Shipit.stubs(:secrets)` (or use `test/dummy/config/secrets_double_github_app.yml`-style config) with `OrgOne` having `webhook_secret: nil` and `OrgTwo` having a real `webhook_secret`.
2. Create a `Shipit::Repository` for `"OrgTwo/victim-repo"` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`, and a previously archived `ReviewStack` for PR `#2`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, a body where `repository.owner.login == "OrgOne"` and `repository.full_name == "OrgTwo/victim-repo"`, `action: "reopened"`, `number: 2`, and `pull_request.head.sha`/`ref` set to attacker-chosen values, with no valid `X-Hub-Signature` (or one only valid for `OrgOne`).
4. Assert `response.status == 200`, and assert (equality check before/after) `Shipit::Repository.find_by(owner: "orgtwo", name: "victim-repo").review_stacks.find_by(environment: "pr2").archived? == false` and that the stack's `branch`/associated commit reflect the attacker-supplied `head.ref`/`sha`, proving `ReviewStackAdapter#find_or_create!`/`#unarchive!` acted on the `OrgTwo` repository despite signature verification only ever touching `OrgOne`'s (absent) secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

          def unarchive!(*args, &block)
            if stack.blank?

          def create!
