### Title
Webhook signature verification organization is not bound to the repository the handler acts on, enabling cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature with based on `repository_owner`, a value read out of the untrusted JSON payload, while the actual event handlers (`PushHandler`, `PullRequest::*Handler`, `Handler#repository_name`) resolve the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`. Nothing enforces that these two independently-attacker-suppliable fields refer to the same repository/organization, so a party who legitimately controls the webhook secret for one configured GitHub organization can forge a request that authenticates as that organization but acts on a stack belonging to a completely different organization configured in the same Shipit instance.

### Finding Description
`verify_signature` picks the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-organization app configs (including distinct `webhook_secret`s) when Shipit is configured for multiple GitHub organizations, a documented and supported setup (`docs/setup.md`, "Using Multiple Github Applications"; `test/dummy/config/secrets_double_github_app.yml`): [3](#0-2) 

Once the signature validates against that org's secret, the shared `Handler` base class and event handlers resolve the affected repository from a *separate* field, `repository.full_name`, with no check that it is consistent with `repository.owner.login`/`organization.login` used above: [4](#0-3) [5](#0-4) 

Because `verify_webhook_signature` only checks that the HMAC of the raw body matches the secret it was told to use for `repository_owner`, and `repository_owner` and `repository.full_name` are two independent fields inside that same signed body, an attacker who legitimately possesses the `webhook_secret` for organization `A` (e.g., because they created/administer the GitHub App for `A`, which is a normal, unprivileged configuration step, not an attack on Shipit itself) can construct a JSON payload where:
- `repository.owner.login` = `"A"` → causes `verify_signature` to select and successfully validate against `A`'s secret,
- `repository.full_name` = `"B/some-repo"` → causes the handler to act on a `Stack` belonging to organization `B`, which the attacker has no relationship to.

This breaks the intended trust binding: *the organization that authenticated (via HMAC) must equal the repository being written to*. Instead, only the "authenticating organization" is checked, while the "repository acted upon" is taken from an unrelated, unauthenticated field of the same payload.

### Impact Explanation
Sending a forged `push` event this way reaches `PushHandler#process`, which calls `stack.sync_github(expected_head_sha:)` for every non-archived stack matching the branch of the *victim* organization `B`'s repository, via `GithubSyncJob`: [6](#0-5) [7](#0-6) 

`GithubSyncJob` fetches real commits using `stack.github_api` (the legitimate GitHub App credentials for `B`), so the attacker cannot inject arbitrary commit content; however, this forged, cross-tenant event can force premature synchronization and — for any stack with continuous deployment enabled — trigger an **unauthorized deploy** of already-existing but not-yet-deployed commits on organization `B`'s repository, using only a webhook secret the attacker owns for an unrelated organization `A`. The same class of mismatch (`repository.full_name` vs. `repository.owner.login`/`organization.login`) is reachable through the `pull_request` handlers (`opened_handler.rb`, `labeled_handler.rb`, etc.), which provision/archive review stacks and add/remove PR labels for a repository chosen independently from the field used to select the verifying secret.

### Likelihood Explanation
Exploitability requires only that: (1) the Shipit instance is configured with the multi-organization GitHub App schema (an explicitly documented, supported configuration), and (2) the attacker legitimately controls the webhook secret of at least one of those configured organizations (e.g., by being the admin of their own org's GitHub App, which is normal setup activity, not a privileged Shipit credential). No Shipit session, `ApiClient` token, or GitHub App private key for the *victim* organization is required — only knowledge of one's own org's `webhook_secret`, which does not by itself grant any authority over other organizations' stacks. This is a realistic condition for any Shipit deployment serving multiple tenants/organizations.

### Recommendation
Require that the organization used to select/verify the webhook secret is cryptographically and logically the same repository being acted upon. Concretely, after verifying the signature, re-derive `repository_owner` from `payload.dig('repository', 'full_name')`'s owner segment (or otherwise validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`) and reject the webhook if they disagree, before dispatching to any handler.

### Proof of Concept
1. Configure Shipit with the multi-org schema, e.g. `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows `OrgA`'s `webhook_secret` (its own GitHub App), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<any-sha-that-exists-upstream-for-OrgB/some-repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/some-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret.
5. `Shipit::Webhooks::Handlers::PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/some-repo")` and enqueues `GithubSyncJob` for `OrgB`'s stack — a resource the attacker only knows via `OrgA`'s credentials, demonstrating the cross-organization write/trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
