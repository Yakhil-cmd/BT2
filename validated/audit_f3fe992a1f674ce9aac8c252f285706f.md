Webhook signature verification authenticates the payload's `repository.owner.login` organization, but handlers act on the unverified `repository.full_name` field, allowing cross-repository forgery of GitHub events — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify a webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`). However, the event handlers that actually process the payload (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, and subclasses like `PushHandler`, `StatusHandler`, `PullRequest` handlers) resolve the target `Repository`/`Stack` from a *different* field: `payload.dig('repository', 'full_name')`. The HMAC signature covers the whole raw payload bytes, but the binding between "which org's secret validated this request" and "which repository the handler will act on" is never itself checked. This mirrors the compound-fork "first depositor" bug class: the same struct exposes two independently-trusted fields (one checked, one acted upon) whose consistency is never enforced.

### Finding Description
Shipit supports multi-organization GitHub App configuration (see `config/secrets.development.shopify.yml`), where each organization has its own `webhook_secret`.

In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) 

`verify_signature` calls `Shipit.github(organization: repository_owner)` to fetch the `GitHubApp` config object for whichever organization is named in `repository.owner.login` of the *attacker-controlled JSON payload*, then verifies the HMAC signature against that organization's `webhook_secret`.

Once verification passes, `create` dispatches the parsed payload to handlers: [3](#0-2) 

Every handler resolves the actual `Repository`/`Stack` to operate on via a **separate** field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

This is used identically in `PushHandler` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`): [5](#0-4) 

and in `StatusHandler`, which does not scope by repository at all — it matches purely on commit SHA globally: [6](#0-5) 

**The break in the trust binding:** `verify_signature` authenticates "organization X sent this," where X = `payload['repository']['owner']['login']`. The handler then trusts "this event is about repository Y," where Y = `payload['repository']['full_name']`. Nothing enforces `Y ∈ X`'s repositories. An attacker who legitimately controls (or has admin rights over) any organization that is configured in Shipit's `github:` multi-org secrets — and therefore knows that organization's own `webhook_secret` — can craft a payload where:
- `repository.owner.login` = `"attacker-org"` (so `verify_signature` picks attacker-org's own known secret and passes)
- `repository.full_name` = `"victim-org/victim-repo"` (any repository actually tracked by Shipit)
- HMAC signature computed correctly with attacker-org's own secret over the full raw body

The request passes signature verification, then the handler blindly acts on `victim-org/victim-repo`.

### Impact Explanation
This is a **cross-repository write / unauthorized action** across the equality `organization authenticated == repository written`, which the rules explicitly call out as a valid analog class. Concretely:

- Via `StatusHandler`, the attacker can inject an arbitrary `Status` (`state: 'success'`, arbitrary `context`) for **any commit SHA** in Shipit's database, without any scoping to the org that "authenticated" the request — the query is `Commit.where(sha: params.sha)`, entirely repo-agnostic [6](#0-5) . Creating this `Status` triggers `Commit#schedule_continuous_delivery`, and if the targeted stack has `continuous_deployment: true` and the commit becomes `deployable?`, this results in `ContinuousDeliveryJob` firing and an **unauthorized deploy** being triggered on a stack the attacker has no legitimate relationship to [7](#0-6) .
- Via `PushHandler`, the attacker can force `stack.sync_github` resyncs on arbitrary victim stacks by spoofing `repository.full_name`, `ref`, and `after` [5](#0-4) .
- Via `PullRequest` handlers (`ClosedHandler`, `ReopenedHandler`, etc.), the attacker can archive/unarchive review stacks belonging to victim repositories.

This satisfies the Critical bar ("unauthorized deploy") when combined with continuous deployment, and at minimum the High bar (unauthenticated manipulation of stack/task state) even without CD enabled.

### Likelihood Explanation
Requires the attacker to be an administrator of *some* organization that a Shipit operator has configured in the multi-org `github:` secrets block (a supported, documented deployment mode) — i.e., they legitimately know one org's `webhook_secret` and can freely send webhooks to that org's own GitHub App. No access to the victim org, no repository write access to the victim repo, and no Shipit session/API token is required. Because the webhook endpoint is deliberately public and unauthenticated apart from this per-org HMAC check, and payload fields are entirely attacker-controlled JSON, exploitation is a simple crafted HTTP POST.

### Recommendation
After signature verification succeeds for organization X, enforce that the handler-visible `repository.full_name` (and `organization.login` for org-scoped events) actually belongs to organization X before processing — i.e., verify `payload.dig('repository','full_name').split('/').first == repository_owner` (case-insensitively) in `WebhooksController#verify_signature`, or thread the authenticated organization down into `Handler` and re-validate ownership there via `Repository#owner` before resolving stacks. Reject the event (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two orgs in `config/secrets.yml`: `attacker-org` (secret known to the attacker, who legitimately administers that org's installed GitHub App) and `victim-org` (a tracked stack, e.g. `victim-org/victim-repo`, with `continuous_deployment: true`).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<known deployable commit sha of victim-org/victim-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC_SHA1(attacker-org_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and the signature validates successfully (attacker knows this secret).
6. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha)` — unscoped by org/repo — finds the victim commit, and calls `create_status_from_github!`, marking it `success`.
7. If `victim-org/victim-repo`'s stack has `continuous_deployment: true` and the commit is otherwise deployable, `ContinuousDeliveryJob` is scheduled, triggering an unauthorized deploy — with no interaction with `victim-org` at all.
