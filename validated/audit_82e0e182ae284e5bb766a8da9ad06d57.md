### Title
Fee-on-Transfer Token Drains Bridge ERC20 Reserves via Inflated `RequestValueTransfer` Event — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer()` calls `safeTransferFrom` to pull `_value + _feeLimit` tokens from the caller, then unconditionally passes the nominal `_value` into `_requestERC20Transfer()` and emits `RequestValueTransfer(_value, ...)`. For fee-on-transfer tokens the bridge receives fewer tokens than `_value + _feeLimit`, but the counterpart bridge operator reads the event and calls `handleERC20Transfer(_value)`, releasing the full nominal amount on the other chain. The source bridge is left undercollateralized by the transfer-fee delta on every crossing.

### Finding Description

`requestERC20Transfer` in `BridgeTransferERC20.sol`:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
``` [1](#0-0) 

No balance snapshot is taken before or after the `safeTransferFrom`. The actual tokens credited to the bridge are never measured. `_requestERC20Transfer` is then called with the original `_value`:

```solidity
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← nominal, not actual received
    requestNonce, fee, _extraData
);
``` [2](#0-1) 

The Go relay layer reads `ev.GetValueOrTokenId()` directly from the event and forwards it verbatim to `HandleERC20Transfer` on the counterpart bridge:

```go
case ERC20:
    handleTx, err = bi.bridge.HandleERC20Transfer(
        auth, txHash, from, to, ctpartTokenAddr,
        valueOrTokenId,   // ← taken from event, not verified
        requestNonce, blkNumber, extraData)
``` [3](#0-2) 

`handleERC20Transfer` on the counterpart bridge then releases the full nominal `_value` to the recipient:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

The same flaw exists in the 1-step `onERC20Received` path: the token contract transfers tokens to the bridge (with a fee deducted) and then calls `onERC20Received(_value)` with the nominal amount, which is forwarded unchanged. [5](#0-4) 

### Impact Explanation

For every `requestERC20Transfer` call with a fee-on-transfer token (transfer fee rate `r`):

- Bridge receives: `(_value + _feeLimit) × (1 − r)`
- Bridge pays bridge-fee and refund from `_feeLimit` portion (these transfers also incur `r`, compounding the shortfall)
- Counterpart bridge releases: `_value`

The source bridge's ERC20 reserve shrinks by approximately `(_value + _feeLimit) × r` per crossing. After enough crossings the bridge cannot satisfy future `handleERC20Transfer` calls, permanently locking or losing user funds. This is an unauthorized drain of bridge-managed ERC20 assets.

### Likelihood Explanation

The `onlyRegisteredToken` modifier requires the bridge owner to have registered the token. However:

1. Many real-world tokens (e.g., STA, PAXG, tokens with dynamic fees) implement transfer fees; a bridge operator may register one without realizing it is deflationary.
2. Once registered, **any unprivileged user** can call `requestERC20Transfer` and trigger the drain repeatedly.
3. The 1-step path (`onERC20Received`) is callable by anyone who holds the token and invokes `requestValueTransfer` on the token contract, requiring no additional approval from the bridge owner beyond the initial registration. [6](#0-5) 

### Recommendation

Measure the actual received balance before and after `safeTransferFrom` and use the delta as the effective deposit amount:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(before);
    // Derive actual _value and _feeLimit from actualReceived proportionally,
    // or require(actualReceived == _value.add(_feeLimit), "fee-on-transfer token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

The simplest safe fix is to revert if `actualReceived < _value.add(_feeLimit)`, explicitly rejecting fee-on-transfer tokens. Alternatively, scale `_value` down to `actualReceived - _feeLimit` and emit the corrected amount in the event.

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` with a 1% transfer fee.
2. Bridge owner registers `FeeToken` on both the parent and child bridge.
3. Alice approves the parent bridge for `110 FeeToken` (`_value = 100`, `_feeLimit = 10`).
4. Alice calls `parentBridge.requestERC20Transfer(FeeToken, bob, 100, 10, "0x")`.
   - `safeTransferFrom` pulls 110 tokens; bridge receives `110 × 0.99 = 108.9`.
   - `_payERC20FeeAndRefundChange` pays bridge-fee (e.g., 5) to feeReceiver and refunds 5 to Alice (each transfer also loses 1%, so actual outflows are slightly less, but the accounting uses nominal values).
   - `RequestValueTransfer(ERC20, alice, bob, FeeToken, 100, nonce, 5, "")` is emitted.
5. The relay operator observes the event and calls `childBridge.handleERC20Transfer(..., 100, ...)`.
   - Child bridge transfers exactly 100 `FeeToken` to Bob.
6. Net result: parent bridge received ~108.9 tokens but is debited 100 (value) + 5 (fee) + 5 (refund) = 110 nominal tokens worth of obligations. The ~1.1 token shortfall accumulates with every crossing, eventually making the parent bridge insolvent. [1](#0-0) [7](#0-6) [8](#0-7)

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
