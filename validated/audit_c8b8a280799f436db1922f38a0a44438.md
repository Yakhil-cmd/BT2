## Cross-organization webhook forgery via mismatched signature-verification / target-repository binding - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, which is read from the JSON body's `repository.owner.login` (or `organization.login`) field. Every event handler, however, resolves the *stack/repository it will actually act on* from a **different** field of the same body — `repository.full_name` — via `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`. Because the field used to pick the verifying secret is not the same field used to pick the affected repository, and both are attacker-supplied JSON, a party that can produce a validly-signed payload for *one* organization can point the `repository.full_name` field at a stack belonging to a *different* organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` looks up the `GitHubApp` (and thus the `webhook_secret`) purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple independent GitHub organizations/apps, each with its own `webhook_secret` in `secrets.yml`: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` only proves the payload was signed with *the secret belonging to `repository_owner`*, nothing else: [5](#0-4) 

Note also that if an org's `webhook_secret` is left `nil` (a documented, non-error configuration, see the example configs), verification is bypassed entirely (`return true unless webhook_secret`), meaning **any** unauthenticated caller can produce a “verified” payload for that organization.

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw parsed JSON to the registered handlers: [6](#0-5) 

Every handler resolves its target stacks from a **different** JSON field, `repository.full_name`, completely decoupled from the `repository.owner.login`/`organization.login` field used for signature selection: [7](#0-6) 

For example, `PushHandler` uses this shared `stacks` scope to select which stacks to run `sync_github` on: [8](#0-7) 

The equality that the deployment-trust model assumes but that the code fails to enforce is:
`organization authenticated by verify_signature (repository.owner.login) == organization owning the repository acted on (repository.full_name)`

Nothing in `WebhooksController` or `Handler` enforces this equality — an attacker can set `repository.owner.login`/`organization.login` to an org they control (or one with `webhook_secret: nil`) while setting `repository.full_name` to `victim-org/victim-repo`, a stack tracked under a completely different, unrelated GitHub App/organization configured on the same Shipit instance.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out as a valid analog class. With a validly-signed-for-org-A payload but an org-B `repository.full_name`, an attacker can drive any registered handler against an arbitrary tracked stack outside their own organization, e.g.:
- Force `PushHandler`/`GithubSyncJob` to resync a victim stack against attacker-chosen `expected_head_sha`.
- Forge `status`, `check_suite`/`check_run` events (routed through the same `Handler#stacks`/`repository_name` mechanism) to inject fake commit statuses into a victim's commits, which factor into `Commit#deployable?`/blocking-status checks (`app/models/shipit/stack.rb`, `app/models/shipit/deploy_spec.rb`) — potentially causing an unsafe/unauthorized deploy to be considered "green" and eligible for continuous deployment or merge-queue processing on a repository the attacker never had legitimate access to.
- Forge `pull_request`/`membership` events against stacks/teams belonging to another organization.

This is a cross-repository/cross-organization write achieved purely by controlling JSON fields in an HMAC-signed-for-a-different-scope request; the impact rises to the "cross-repository writes" / "unauthorized deploy" tier called out in scope.

### Likelihood Explanation
Exploitability requires the target Shipit instance to be configured with more than one GitHub App/organization (an explicitly documented, supported configuration — `docs/setup.md`), and requires the attacker to be able to produce a validly-signed webhook payload for *any one* of the configured organizations. This is realistic when: (a) the attacker controls a repository in one of the configured organizations and can register/trigger real GitHub webhooks there, or (b) any organization in the multi-org config has `webhook_secret` unset (a valid, non-default configuration shown in the shipped example secrets files), which bypasses signature verification entirely for that org. No Shipit session, API token, or repository write access to the *victim* repository is required — only to one org sharing the same Shipit deployment, or none at all if a secret is unset.

### Recommendation
Bind the two fields together before dispatching: after `verify_signature` succeeds for `repository_owner`, require that the owner/org portion of `repository.full_name` (and `organization.login`, when present) match the `repository_owner` value used to select the verifying `GitHubApp`/secret, rejecting (422) any payload where they diverge. Alternatively, have `Handler#repository_name`/`#stacks` scope lookups to only the organization that was actually verified, rather than trusting an independent, unauthenticated field from the same JSON body.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `OrgA` and `OrgB` (as in the shipped `docs/setup.md` multi-org example), each with its own `webhook_secret`, and a stack tracking `OrgB/victim-repo`.
2. As an attacker who only has access to a repository under `OrgA` (or where `OrgA.webhook_secret` is `nil`), craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` (known to the attacker, or omitted if `nil`) and send it to `/github/webhooks` with header `X-Hub-Signature`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgA"` [2](#0-1)  and verifies successfully against `OrgA`'s secret.
5. `PushHandler` (via `Handler#stacks`) resolves stacks using `repository.full_name` = `"OrgB/victim-repo"` [7](#0-6)  and triggers `sync_github` on the victim's `OrgB` stack — despite the request never having been authenticated for `OrgB`.

Note: I was unable to fully inspect `status_handler.rb` and `check_suite_handler.rb` contents in this session (tool errors on final iteration), so the exact downstream effect on `Commit#deployable?`/merge-queue gating for those specific handlers is inferred from `Handler`'s shared `stacks`/`repository_name` mechanism and `app/models/shipit/stack.rb`/`deploy_spec.rb` deployability logic rather than directly confirmed line-by-line in those two files.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
