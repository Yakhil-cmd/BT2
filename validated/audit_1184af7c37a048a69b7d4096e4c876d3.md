### Title
Webhook signature is verified against the organization app whose secret signed the payload, but handlers act on the unrelated `repository.full_name` field also carried in that same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against using `repository_owner`, read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). It confirms only that "this HTTP body was signed by *some* configured organization's app". Every event handler, however, resolves the target `Repository`/`Stack` using a *different* field from the very same JSON body: `payload.dig('repository', 'full_name')` (see `Shipit::Webhooks::Handlers::Handler#repository_name`, and each handler's `Repository.from_github_repo_name(params.repository.full_name)`). Nothing ties `repository.full_name` to the `repository.owner.login`/organization that produced the valid signature.

### Finding Description
`Shipit` explicitly supports running one engine instance against multiple GitHub Apps/organizations (`config/secrets.development.shopify.yml`, `docs/setup.md`), each with its own `webhook_secret`. The webhook signature check is: [1](#0-0) 

`repository_owner` is derived from the request body itself: [2](#0-1) 

Because HMAC verification is performed over `request.raw_post` using the secret for whatever organization `repository_owner` names, an attacker who legitimately controls their own GitHub organization/App installation (e.g. `attacker-org`, with its own valid `webhook_secret`) can craft an arbitrary JSON payload, set `repository.owner.login = "attacker-org"` (so the correct, attacker-known secret is selected and the HMAC validates), while setting `repository.full_name` to a victim organization's repository, e.g. `"victim-org/private-repo"`.

Every downstream handler ignores `repository.owner.login` and instead looks up the target repository/stack purely from `repository.full_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

The signature therefore authenticates "this message came from an app that has some organization configured," but the code acts on a payload field (`repository.full_name`) that was never bound to that organization identity during verification. This is exactly the "organization authenticated vs. repository written" trust-binding break: the equality that should hold — `organization_whose_secret_signed == owner(repository_that_is_acted_upon)` — is never checked.

### Impact Explanation
With a forged `repository.full_name`, an attacker who controls one legitimately configured tenant (their own org/app installation on the shared Shipit instance) can:
- Trigger `PushHandler` to call `stack.sync_github(expected_head_sha:)` against a victim stack/repository, causing `GithubSyncJob` to run using the Shipit-wide `Shipit.github.api` credentials against the victim's GitHub repo (`app/jobs/shipit/github_sync_job.rb`), potentially advancing/altering deploy state.
- Trigger `CheckSuiteHandler`/`StatusHandler` to inject/alter commit statuses for a victim's commits.
- Trigger `PullRequest::OpenedHandler`/`ReviewStackAdapter` to create or archive `ReviewStack`s for a victim repository, which can provision/deprovision infrastructure (`stack.deprovision`, `ReviewStackProvisioningQueue`).
- Trigger `MembershipHandler`-style state changes tied to a repository they do not own.

This qualifies as cross-repository/cross-tenant writes and an unauthorized deploy-state manipulation on a multi-tenant Shipit deployment — meeting the "Critical: cross-repository writes / unauthorized deploy" bar, since it only requires control of any one legitimately configured organization's webhook secret, not the victim's.

### Likelihood Explanation
This only matters in multi-organization Shipit deployments (`Shipit.github(organization: ...)` supporting a hash of orgs, as documented and fixture-configured). In that configuration, any tenant/org onboarded to the same Shipit instance is effectively another "unprivileged attacker" relative to every other tenant's repositories, and can trivially forge this cross-field mismatch since they legitimately know their own `webhook_secret`. In a single-organization deployment this is not exploitable, since only one webhook secret/org mapping exists and `repository_owner` will always match the real org.

### Recommendation
Bind the two fields explicitly instead of trusting `repository.full_name` independently of the field used for authentication: after verifying the signature, re-derive/validate that `repository.full_name`'s owner segment matches the `repository_owner` (or the `organization.login`) that was used to select the `webhook_secret`, and reject (422) on mismatch. Alternatively, pass the already-verified `repository_owner`/organization down to `Shipit::Webhooks::Handlers::Handler` and have `repository_name`/`stacks` filter by that verified owner rather than trusting the unauthenticated `repository.full_name` owner portion.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (supported multi-tenant config per `docs/setup.md` / `config/secrets.development.shopify.yml`).
2. As the attacker (who owns `attacker-org`'s GitHub App and therefore its `webhook_secret`), build a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/private-repo"
  }
}
```
3. Sign the raw body with `attacker-org`'s `webhook_secret` and send it to `/webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/private-repo")` and invokes `sync_github` on `victim-org`'s stacks, even though the signature only proved authorship by `attacker-org`. [3](#0-2) [4](#0-3)
