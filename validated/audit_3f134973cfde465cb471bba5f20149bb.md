### Title
Webhook signature verification is silently bypassed when `webhook_secret` is unset, allowing unauthenticated forgery of GitHub events - (File: `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController` gates all inbound GitHub events behind a single check, `verify_signature`, which delegates to `GitHubApp#verify_webhook_signature`. That method treats a missing `webhook_secret` as automatic success rather than a hard failure, so any organization configured without a webhook secret accepts arbitrary, unsigned webhook payloads.

### Finding Description
The controller's only defense against forged webhooks is: [1](#0-0) [1](#0-0) 

which calls into: [2](#0-1) 

`verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` — i.e. if the per-organization GitHub App config has no `webhook_secret` set, **no signature check is performed at all**, and every payload is accepted regardless of the `X-Hub-Signature` header. The setup documentation explicitly marks this field as optional, confirming it is a supported production configuration, not a misconfiguration edge case: [3](#0-2) [4](#0-3) 

This mirrors the AMM `settleFunding` bug class: the check that is supposed to *equally* gate every organization's webhook (`verified == true` implying "HMAC over raw_post matches organization's secret") instead degrades to an unconditional pass for any organization whose config omits the secret — the equality "signature checked" vs "signature accepted" silently collapses to true/true with zero attacker-supplied proof. Once past `verify_signature`, `create` dispatches the parsed, attacker-controlled JSON directly to registered handlers: [5](#0-4) 

Handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and `MembershipHandler` resolve the target `Stack`/`Repository`/`Team`/`User` purely from payload fields (e.g. `repository.full_name`, `organization.login`): [6](#0-5) 

so a forged event is treated identically to a genuine GitHub-originated one for that organization's stacks.

### Impact Explanation
An unauthenticated, unprivileged attacker who knows only the target's Shipit hostname and repository/organization names (no session, no `ApiClient` token, no `webhook_secret`, no GitHub credentials) can POST arbitrary JSON to `/webhooks` for any organization whose GitHub App is configured without `webhook_secret`. This lets them forge `push` events (to queue arbitrary sync/deploy-relevant jobs), `status`/`check_suite` events (to mark arbitrary commits as passing CI, which Shipit uses to gate deployability), and `membership`/`pull_request`/`merge` events (to manipulate teams, review stacks, or merge-request state). Forged CI/status success on an otherwise-unreviewed commit can lead to an unauthorized deploy — squarely within the defined Critical impact ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
High for any deployment following the documented "optional" webhook secret guidance: the vulnerable code path requires no secret, no session, and no prior interaction — a single crafted HTTP request is sufficient. Only deployments that always set a non-blank `webhook_secret` for every configured organization are unaffected.

### Recommendation
Make `webhook_secret` mandatory (fail closed) rather than optional-with-bypass: `verify_webhook_signature` should return `false` (not `true`) when no secret is configured, and `Shipit::WebhooksController#verify_signature` should reject (422) any organization lacking a configured secret instead of allowing verification to trivially pass.

### Proof of Concept
1. Configure (or identify) a Shipit organization whose `github` config omits `webhook_secret`, as shown supported in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and a body such as `{"sha": "<victim-commit-sha>", "state": "success", "repository": {"owner": {"login": "<org>"}, "full_name": "<org>/<repo>"}}`, without any valid `X-Hub-Signature` header.
3. `verify_webhook_signature` returns `true` because `webhook_secret` is blank; `StatusHandler` processes the forged payload and records a passing status for the targeted commit, influencing deploy eligibility without any authentic GitHub-signed request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
