### Title
Cross-organization webhook forgery via payload-derived signature-secret selection - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body, then verifies the whole payload against that org's secret. Once verification passes, the event is dispatched to handlers that act on a *different* payload field — `repository.full_name` — to resolve the target `Stack`/`Repository`. Nothing ties the organization whose secret validated the signature to the repository the handlers actually operate on.

### Finding Description
`verify_signature` computes the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GithubApp` instance holding a **per-organization** `webhook_secret`, as configured for multi-org deployments: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` only checks the HMAC of the raw body against that single org's secret: [5](#0-4) 

Once the signature is accepted, `create` hands the *entire* parsed JSON body to the event handlers without any re-validation that `repository.owner.login` (the field used to pick the verifying secret) matches `repository.full_name` (the field handlers use to resolve which tracked `Stack`/`Repository` to mutate, e.g. via `GithubSyncJob`, as shown in the push-event test): [6](#0-5) [7](#0-6) 

Since Shipit explicitly supports hosting several independently-configured GitHub Apps/organizations side by side (each with its own `webhook_secret`), an operator who legitimately controls the webhook secret for organization **A** (e.g. because they administer a GitHub App Shipit trusts for their own org's repos) can sign an arbitrary JSON body with secret **A** while setting `repository.full_name` to `"org-B/tracked-repo"` — a repository belonging to a completely different, unrelated organization **B** also tracked by the same Shipit instance. `repository_owner` (used only to pick the verifying key) will read `"org-A"` from `repository.owner.login`, verification succeeds against A's secret, but the dispatched handler (e.g. the push handler enqueuing `GithubSyncJob`, or the `membership`/`status`/`check_suite` handlers) acts on `org-B/tracked-repo` because it trusts `repository.full_name` from the same already-verified body.

This breaks the equality that should hold: **organization whose secret authenticated the request == organization owning the repository the handlers mutate**. The HMAC does cover the raw bytes faithfully, but the two logically-independent identifiers (`repository.owner.login` used for key selection, `repository.full_name` used for repository binding) are never cross-checked against each other, so a legitimate secret-holder for one tenant can forge events scoped to another tenant's repository.

### Impact Explanation
This lets an attacker who is a legitimate, authorized webhook sender for one organization onboarded to a shared Shipit instance forge trusted GitHub events (push notifications driving `GithubSyncJob`, commit `status`, `check_suite`, `membership`, `pull_request` handlers, etc.) attributed to a repository under a *different* organization. Depending on the handler, this can inject fabricated commit statuses/check results that influence deployability, or create/remove team memberships and users cross-tenant — a cross-repository/cross-organization trust boundary violation matching the "authenticated organization vs. written repository" pattern called out in the assignment.

### Likelihood Explanation
Requires the attacker to already hold a valid `webhook_secret` for *some* organization configured on the shared Shipit instance (a standard, low-privilege credential every onboarded GitHub App/org possesses), and for the instance to be configured with more than one organization sharing the same `/webhooks` endpoint, as explicitly documented and supported (`config/secrets.development.shopify.yml`). No repository write access, session, or `ApiClient` token is needed — only knowledge of one tenant's webhook secret, which is handed out to every organization onboarded to the shared deployment.

### Recommendation
After signature verification, re-derive `repository_owner`/`organization` strictly from the same value used to select the verifying secret, and reject (422) any payload where `repository.full_name`'s owner segment does not match the organization whose secret validated the signature. Alternatively, verify the payload against the secret of the organization that actually owns the resolved `Stack`/`Repository`, not the organization named in the (still-unauthenticated-at-that-point) `repository.owner.login`/`organization.login` field.

### Proof of Concept
1. Configure Shipit with two organizations, `org-A` and `org-B`, each with its own `github_app` `webhook_secret` (as supported per `config/secrets.development.shopify.yml`), both having tracked repositories in Shipit.
2. As the legitimate owner of `org-A`'s GitHub App/webhook secret, craft a `push` event JSON body with:
   - `repository.owner.login = "org-A"`
   - `repository.full_name = "org-B/tracked-repo"`
3. Sign the raw body with `org-A`'s `webhook_secret` and send it to `POST /webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` to `"org-A"`, fetches `org-A`'s `GithubApp`, and `verify_webhook_signature` succeeds because the body was validly signed with `org-A`'s secret.
5. `Shipit::Webhooks.for_event('push')` handlers run against the full payload, enqueuing `GithubSyncJob` (or equivalent) scoped to `org-B/tracked-repo`, a repository the attacker does not own and whose organization never authenticated this request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
