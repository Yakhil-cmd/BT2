## Finding

### Title
EVM `SuiBridge` vault withdrawal trusts a stale bridged amount without verifying vault solvency, breaking the escrow invariant for non-standard ERC20 tokens - (File: `bridge/evm/contracts/SuiBridge.sol`)

### Summary
This is a direct analog of the Nibiru finding: the Sui native bridge's EVM leg measures the *actual* balance delta on deposit (to be non-standard-token-safe) but blindly trusts the previously-recorded, decimal-adjusted amount on withdrawal without ever re-checking the vault's real ERC20 balance. If the vault's holdings for a listed token can change independently of bridge transfers (rebasing, fee-on-transfer, external donations/skims), the same 1:1 "escrowed amount == committed amount" invariant that Nibiru assumed is broken here too.

### Finding Description
On deposit, `bridgeERC20` explicitly avoids trusting the nominal `amount` and instead computes the real transferred amount from a balance snapshot: [1](#0-0) 

But on the claim/withdrawal path, `_transferTokensFromVault` (invoked from `transferBridgedTokensWithSignatures`) does the opposite: it takes the amount decoded from the committee-signed message (fixed at deposit time, converted between Sui/ERC20 decimals) and unconditionally calls `vault.transferERC20(tokenAddress, recipientAddress, amount)`, with no check that the vault still holds at least `amount` of that token: [2](#0-1) 

`BridgeVault.transferERC20` just performs `SafeERC20.safeTransfer` for the exact requested `amount`, with no balance verification of its own: [3](#0-2) 

This mirrors the Nibiru root cause precisely: the protocol assumes that whatever amount was recorded as "escrowed" when the deposit happened is still available, in full, at withdrawal time — an assumption that only holds for tokens whose balances never change outside of transfers. Any token added to `BridgeConfig`'s supported list that can change the vault's balance independently of bridge-mediated transfers (rebasing tokens, fee-on-transfer/deflationary tokens that also charge a fee on the *outbound* leg, or tokens allowing external balance manipulation) breaks the invariant:
- If the vault balance for that token decreases (negative rebase, external skim, fee taken again on withdrawal), `safeTransfer` for the full recorded `amount` reverts, permanently stranding that specific signed message — since the amount and content of an already-quorum-signed `BridgeMessage` cannot be altered or re-issued, this results in a **permanently locked bridge transfer**.
- If the vault balance increases (positive rebase, donations), the surplus is simply never accounted for or distributed — an unintentional accumulation with no accounting mechanism to reconcile it back into future withdrawals.

The Move side (`bridge::treasury`) does not have this issue, since it uses `coin::mint`/`coin::burn` against a `Supply<T>` object rather than a queryable external balance: [4](#0-3) 

so the analog is specifically confined to the EVM vault/escrow leg of the bridge, which is the exact architectural pattern (querying/trusting an external balanceOf) that caused the original Nibiru bug.

### Impact Explanation
Once a `BridgeMessage` for a token withdrawal is quorum-signed, its `amount` field is immutable (the message is hashed and signed by the committee). If the vault's actual token balance later falls short of that committed amount (due to rebasing/fee mechanics acting on the escrowed balance while it sits in `BridgeVault`), `transferBridgedTokensWithSignatures` will permanently revert for that nonce, and there is no code path to reissue the message with a corrected amount — this is a **permanent fund lock** for the affected user, which matches the repo's own allowed High/Medium impact category ("permanent fund lock"). In the surplus-accumulation direction, funds become unclaimable/unreconciled inside the vault (unintended value stuck outside user control).

### Likelihood Explanation
Exploitability depends entirely on which ERC20 tokens are configured via `BridgeConfig`/`addTokensOnEvm`. The tokens currently exercised in tests (WETH, USDC, USDT, WBTC) are not classic rebasing tokens, so under the current, narrow token list the practical likelihood is low. However, the vulnerability is a structural code-level flaw, not a configuration safeguard — nothing in `SuiBridge.sol`, `BridgeVault.sol`, or `BridgeConfig.sol` prevents an ordinary, non-malicious future token listing (e.g. any token with fee-on-transfer, rebasing, or "balance changes outside of transfers" behavior, which is a widely-used real-world token category) from immediately triggering stuck/lost funds for any user who bridges it — with no attacker privilege required beyond being a normal bridge user of that token.

### Recommendation
Mirror the deposit-side pattern on withdrawal: measure the vault's actual pre/post balance for the token and only transfer `min(committedAmount, availableBalance)`, or explicitly disallow/flag tokens whose balance can change outside of transfer semantics from ever being added via `addTokensOnEvm`/`add_new_token`. Alternatively, maintain an internal per-token ledger of "amount owed" independent of the vault's live ERC20 balance, and reconcile discrepancies via a governance-only sweep/rebalance function rather than relying on `balanceOf` at withdrawal time.

### Proof of Concept
1. Governance lists a hypothetical rebasing/fee-bearing ERC20 token `X` via `addTokensOnEvm`/`add_new_token` (this is a legitimate, non-malicious listing decision, same premise as the original Nibiru report).
2. User A calls `bridgeERC20(tokenID_X, 1000, recipient, dstChain)`; `1000` tokens of `X` land in `BridgeVault`, and `TokensDeposited` is emitted with `amountTransfered` measured via balance delta — see `SuiBridge.sol` lines 158-175.
3. While the corresponding Sui→claim message is pending committee signatures, token `X` rebases down (or the vault's holdings decrease via any external mechanism such as an internal fee), leaving less than `1000` tokens in `BridgeVault`.
4. The bridge node collects signatures and submits `transferBridgedTokensWithSignatures`; `_transferTokensFromVault` calls `vault.transferERC20(X, recipient, 1000)` — `SafeERC20.safeTransfer` reverts because the vault balance is insufficient (`BridgeVault.sol` lines 37-45).
5. The nonce/message is now permanently unfulfillable: `isTransferProcessed[nonce]` was never set to `true` (revert happened before), but the committee-signed message content (fixed `amount = 1000`) can never succeed again since the vault will never regain that exact balance through normal operation — the user's funds are permanently locked.

        // Check that the token address is supported
        require(tokenAddress != address(0), "SuiBridge: Unsupported token");

        // transfer eth if token type is eth
        if (tokenID == BridgeUtils.ETH) {
            vault.transferETH(payable(recipientAddress), amount);

            // transfer tokens from vault to target address
            vault.transferERC20(tokenAddress, recipientAddress, amount);
        }

        // update amount bridged
        limiter.recordBridgeTransfers(sendingChainID, tokenID, amount);
    }
