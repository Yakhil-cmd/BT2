### Title
Webhook signature validated against `repository.owner.login` while all event handlers act on the unbound `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the `X-Hub-Signature` against based on `repository.owner.login` (or `organization.login`), but every event handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) instead resolves the target `Repository`/`Stack` using `repository.full_name` from the same payload. Nothing ties these two fields together, so a valid signature computed with *one* organization's webhook secret authorizes writes against *any* repository named in `repository.full_name`, including repositories that belong to a completely different GitHub organization configured in the same Shipit instance.

### Finding Description
In a multi-org Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), each organization has its own `app_id`/`webhook_secret` under `Shipit.github(organization: ...)`.

The signature check:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

only proves that the raw POST body was HMAC-signed with the secret belonging to the org named in `repository.owner.login`. It never verifies that `repository.full_name` (the field that actually drives behavior) is owned by that same organization.

Every handler bases its target repository lookup on `repository.full_name`, not on `repository.owner.login`:
```ruby
# app/models/shipit/webhooks/handlers/handler.rb
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

and `PushHandler` uses this to sync any matching stack:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

Because `X-Hub-Signature` is an HMAC over the *entire raw request body*, an attacker who legitimately controls one organization's GitHub App installation on this Shipit instance (and therefore knows that org's `webhook_secret`) can craft an arbitrary JSON payload — setting `repository.owner.login` to their own org (so `verify_signature` picks their own org's secret and it validates), while setting `repository.full_name` to `OtherOrg/other-repo` — and sign the whole thing with their own secret. The signature will verify successfully, and the handler will act on `OtherOrg/other-repo`'s stacks, which the attacker does not control.

This breaks exactly the binding called out by the rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Depending on which event is forged:
- `push`: triggers `stack.sync_github(expected_head_sha:)` for another organization's stacks, forcing unscheduled GitHub sync jobs against a repository/stack the attacker doesn't own [3](#0-2) .
- `status`/`check_suite`: could inject forged commit statuses/check results for another org's commits, which, per the documented `ci.require` feature, gates whether Shipit permits deploys/continuous delivery — a step toward an unauthorized deploy on a repository the attacker has no legitimate access to.
- `pull_request` events (`opened`/`labeled`/`closed`): can create/archive/unarchive review stacks for another organization's repository via `Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) .

This crosses a GitHub-organization trust boundary the multi-org configuration is meant to enforce, and can culminate in cross-repository state changes/writes without genuine authorization from the target organization, satisfying the High/Critical bar ("cross-repository writes" / "escalation" via a forged authenticated event).

### Likelihood Explanation
Requires the attacker to control (be an admin of / have installed the app for) at least one GitHub organization that is configured in the same multi-tenant Shipit instance — a realistic scenario for any Shipit deployment serving multiple orgs/teams, since knowing your own org's `webhook_secret` is not a privileged action against the *target* org. No access to the target repository, no Shipit session, and no target org credentials are required — only knowledge of one's own org's webhook secret and the ability to POST to the public `/webhooks` endpoint.

### Recommendation
Bind organization identity used for signature verification to the same field(s) used for repository resolution: derive the authorized organization strictly from `repository.full_name`'s owner segment (or vice versa), and reject the webhook if `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`. Alternatively, verify the signature using the webhook secret associated with the resolved `Repository`/`Stack` rather than a value taken from an unauthenticated part of the same payload.

### Proof of Concept
1. Deploy Shipit with two orgs configured (`OrgA`, `OrgB`) per the multi-app setup in `docs/setup.md`, each with distinct `webhook_secret`s.
2. As an attacker who administers `OrgA`'s installed GitHub App, obtain `OrgA`'s `webhook_secret` (legitimately known to them).
3. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
5. POST to `/webhooks` with header `X-Github-Event: push`.
6. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret [5](#0-4) .
7. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")` on its stacks, acting on `OrgB`'s repository despite the signature having been produced with `OrgA`'s secret [2](#0-1) [3](#0-2) .
