### Title
Webhook signature verification only binds the authenticating organization to `repository.owner.login`, not to the repository the event handlers actually act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to verify a webhook against using a field read out of the *same* unparsed JSON body it is about to verify (`repository.owner.login`, falling back to `organization.login`). Once the HMAC check passes, the entire parsed payload — including the `repository.full_name` field that the event handlers use to resolve the target `Stack`/`Repository` — is handed to `Shipit::Webhooks.for_event(event)` handlers without any re-check that the repository being acted on actually belongs to the organization whose secret was used to authenticate the request.

### Finding Description
In a multi-organization Shipit deployment (the officially documented configuration shape, see `config/secrets.development.shopify.yml` and `docs/setup.md`, where each GitHub organization has its own `webhook_secret`), verification works like this: [1](#0-0) [2](#0-1) 

`repository_owner` is only used to select *which secret* to check the HMAC signature against (`Shipit.github(organization: repository_owner)`); it is never checked again against the repository that the handlers subsequently operate on. After signature verification succeeds, the full raw body is parsed and dispatched verbatim to handlers: [3](#0-2) 

Handlers such as `PushHandler` and `StatusHandler` resolve the affected `Stack`/`Commit` from other fields of the same payload (branch, sha, and — through the base `Handler`/`Repository.from_github_repo_name` mechanism used elsewhere in the engine, e.g. `Repository.from_github_repo_name` in `app/controllers/shipit/api/stacks_controller.rb`) rather than from `repository_owner`: [4](#0-3) [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the repository the handler mutates`

Because `repository.owner.login` (used for authentication routing) and the repository/commit-resolution fields consumed by the handlers are independent parts of a single JSON body that the *sender* fully controls, an attacker who legitimately controls one configured organization (and therefore knows/owns that organization's `webhook_secret`, obtained by installing/administering their own GitHub App instance in a shared, multi-org Shipit deployment) can craft a payload where `repository.owner.login` = their own org (so the signature validates against their own secret) while other identifying fields (e.g. `sha`, or the repository identity resolved deeper in the handler chain for `push`) reference a stack/commit that in fact belongs to a completely different, unrelated organization hosted on the same Shipit instance.

### Impact Explanation
This breaks the intended isolation between organizations sharing one Shipit instance (the deployment mode Shipit explicitly documents, see `config/secrets.development.shopify.yml`). An attacker who only administers their own organization's GitHub App / webhook secret can forge webhook events that are processed as if authoritative for a different organization's repository — e.g., forging a `status` event to post a fabricated commit status against a real commit SHA belonging to another org's stack (`StatusHandler#process`, `Commit#create_status_from_github!`), or forcing a `push`-triggered `GithubSyncJob`/resync of another organization's stack. Forged commit statuses can be used to satisfy CI-status gating on stacks with continuous deployment enabled, resulting in an unauthorized deploy. This is a cross-repository/cross-organization write performed without any credential or privilege on the victim organization or its repository, matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Exploitability is limited to Shipit instances configured for multiple organizations, each with its own `github.<org>.webhook_secret` (the multi-org config format Shipit ships and documents). Within that configuration, no privilege on the victim organization is required — only ownership of any one configured organization's own webhook secret, which is entirely within the attacker's control for their own org. The `verify_signature` logic never cross-checks that `repository_owner` (used to pick the secret) matches the repository/commit actually referenced deeper in the payload, so likelihood is high once the multi-tenant configuration is used.

### Recommendation
After computing `repository_owner` for the purpose of choosing which secret to verify with, re-derive the "acted upon" repository from the same payload (e.g. `repository.full_name`'s owner segment, or the resolved `Commit#stack.repository`) and reject the webhook (422) unless the two match. This restores the equality `authenticating organization == repository being written to` before dispatching to any handler in `Shipit::Webhooks.for_event`.

### Proof of Concept
1. Deploy Shipit with a multi-org config where `orgA` and `orgB` are both configured with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml`), each having stacks tracked by the instance.
2. As an attacker who only administers `orgA` (and thus knows `orgA`'s `webhook_secret`), craft a `status` webhook payload where `repository.owner.login` = `orgA` (so `Shipit.github(organization: 'orgA')` is selected and the HMAC signature computed with `orgA`'s secret validates) but `sha` is a real commit SHA belonging to a stack/commit under `orgB`'s repository.
3. `POST /webhooks` with `X-Github-Event: status` and the forged, correctly-HMAC'd (for `orgA`) body.
4. `verify_signature` passes because it only checked the signature against `orgA`'s secret; `StatusHandler#process` then finds `Commit.where(sha: params.sha)` matching `orgB`'s commit and calls `create_status_from_github!`, writing an attacker-controlled status onto a commit that belongs to an organization the attacker has no access to — [5](#0-4) .
