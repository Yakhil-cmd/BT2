## Title
Webhook signature verification key is selected by `repository.owner.login`, but event processing acts on the unrelated `repository.full_name` field — enabling cross-repository forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, while every webhook handler resolves the actual `Stack`/`Repository` to act on using a **different** field of the same unverified body: `repository.full_name`. Nothing ties these two fields together, so a signature that is valid for organization A's secret is accepted for a payload whose `full_name` targets organization B's repository/stack.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` maps this attacker-supplied `repository.owner.login` string to a per-organization `GitHubApp` instance built from `Shipit.github_app_config(organization)`, i.e. the config block (and `webhook_secret`) registered under that org name in `secrets.yml`, a first-class supported multi-tenant setup documented in `docs/setup.md`'s "Using Multiple Github Applications" section [3](#0-2) .

`verify_webhook_signature` then HMACs the **entire raw body** with that org's secret [4](#0-3) . This means the check only proves "this body was signed by *some* org's registered secret" — specifically the org named in `repository.owner.login` — not that the org whose secret produced the signature is the actual owner of the repository being mutated.

Every handler, however, resolves the target repository independently from a different, un-cross-checked field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [5](#0-4) 

`PushHandler` uses this to trigger a GitHub sync/deploy pipeline for matching stacks [6](#0-5) , and the pull-request handlers use `params.repository.full_name` to look up `Shipit::Repository.from_github_repo_name` and then archive/unarchive/merge review stacks [7](#0-6) , [8](#0-7) .

So a party who legitimately administers **one** onboarded GitHub organization/app (and therefore knows that org's `webhook_secret`, since they configure it identically on both the GitHub App side and are given it to register with the Shipit operator) can craft an arbitrary JSON body where:
- `repository.owner.login` = their own org (so `verify_signature` selects their own known secret and the HMAC passes), and
- `repository.full_name` = `"victim-org/victim-repo"` (any other repository configured in the same Shipit instance).

The controller accepts this as a validly-signed event for the victim repository, and the handler dispatches actions (push-triggered sync/deploy, PR-label-driven stack archive/unarchive, review-stack provisioning, etc.) against stacks that belong to an organization the attacker never authenticated as.

This is the exact "organization that authenticated versus the repository that is written" binding break called out in scope: before the fix, `authenticated_org == acted_upon_repo.owner` was implicitly assumed but never enforced; after crafting the payload, `authenticated_org != acted_upon_repo.owner` while the request is still treated as verified.

### Impact Explanation
This allows cross-repository/cross-tenant forged webhook delivery in any Shipit deployment configured with multiple GitHub organizations (`docs/setup.md`, "Using Multiple Github Applications"). An attacker controlling one onboarded org's webhook secret can trigger unauthorized `push` (deploy pipeline sync), pull-request lifecycle actions (archive/unarchive review stacks, label-driven provisioning), and other webhook-driven state changes against **any other repository/stack** hosted on the same Shipit instance, without any credentials for that repository. This matches the "cross-repository writes / unauthorized deploy" High/Critical impact category.

### Likelihood Explanation
Requires a deployment using the documented multi-organization GitHub App configuration and an attacker who is a legitimate operator of one of the onboarded organizations (i.e., someone entrusted with only one org's secret) — a realistic mid-privilege actor relative to other tenants, not an anonymous internet user. No GitHub App private key, session, or `ApiClient` token is needed; only knowledge of one tenant's `webhook_secret`, which such an operator is expected to hold to configure their own GitHub webhook.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the app/secret by `repository_owner`, additionally verify (before dispatching to handlers) that the owner segment of `repository.full_name` (and/or `organization.login`) matches `repository_owner` used for key selection, rejecting the request with `422` otherwise. Handlers should also assert `repository.owner.login`/`full_name` consistency rather than trusting `full_name` alone when multiple GitHub App configurations are in use.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` per `docs/setup.md`'s multi-org example.
2. As the operator of `attacker-org`, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` with `attacker-org`'s known `webhook_secret` over the exact raw body, per `Hook::DeliverySigner`/`verify_webhook_signature` [4](#0-3) .
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` selects `attacker-org`'s app via `repository_owner` ("attacker-org"), the signature validates, and `PushHandler` resolves `stacks` from `victim-org/victim-repo` via `payload.dig('repository','full_name')`, triggering `stack.sync_github(expected_head_sha: ...)` on the victim's stack [6](#0-5) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
