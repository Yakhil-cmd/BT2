## Title
Address/asset spending-limit definitions using `has`/`has one` with `amount_at_most` can be bypassed by splitting or adding extra outputs, since the check only requires the *existence* of one matching output, not that the total spend is bounded - ([File: definition.js])

## Summary
The DeXe report's root cause is a limit check performed on a single action (one `buy()` call) rather than on the cumulative total across all of a user's actions, allowing the limit to be trivially bypassed by splitting a large purchase into many small ones that each individually satisfy the per-call check. The analogous weakness in ocore is the `has` / `has one` opcode in address- and asset-spending-condition definitions (`definition.js`), which is commonly used together with `amount_at_most` filters to grant a reduced-authorization tier ("if the total is small, one signature/condition is enough") but only verifies that **at least one** output/input in the unit matches the filter — it does not sum or otherwise bound the *total* amount transferred by the unit.

## Finding Description
`validateDefinition` in `definition.js` defines the `has`/`has one` grammar for spending-condition expressions and accepts `amount`, `amount_at_least`, and `amount_at_most` fields in the filter object: [1](#0-0) 

At authentication-evaluation time, `has`/`has one` simply delegates to `augmentMessagesAndEvaluateFilter(op, args, cb)` and returns whatever boolean that returns — i.e., whether **any** (or exactly one, for `has one`) output/input matches the filter criteria: [2](#0-1) 

Contrast this with the `sum` opcode, which was specifically added to correctly aggregate amounts across *all* matching outputs/inputs in the unit and compare the sum against `at_least`/`at_most`/`equals`: [3](#0-2) 

The existence of `sum` as a distinct, more complex opcode (it must locate *all* matches and add them up) versus `has`'s single existence check confirms that `has ... amount_at_most: X` only proves "there exists an output of at most X", not "the total amount sent is at most X". Any address definition (or asset `issue_condition`/`transfer_condition`) that uses `has`/`has one` with `amount_at_most` as a stand-in for a spending cap — e.g., "single signature suffices if `amount_at_most: 100`, otherwise the second key is needed" — is exactly the same class of flaw as the DeXe `maxAllocationPerUser` bug: the check is evaluated per-instance/per-output rather than as a bound on the total. A holder of only the "small-amount" signing key can construct a single unit containing one output that is `<= 100` (satisfying `has`) **plus** additional outputs to arbitrary addresses that are not bounded by the check at all, since `has` doesn't require that *every* output conform to the limit, only that one does. This lets an attacker with restricted signing authority move an unbounded amount out of the address in one unit, defeating the intended per-signer spending cap — analogous to the reported bug where a per-call cap failed to bound cumulative user spending.

The same semantics apply in the AA (`aa_composer.js` via `formula/evaluation.js`) evaluation engine used for AA definition-template/condition checks, and in asset `issue_condition`/`transfer_condition` evaluation (`Definition.evaluateAssetCondition`, invoked at `validation.js:2644-2657`), so any AA- or asset-based scheme relying on `has ... amount_at_most` for a cap is equally exposed: [4](#0-3) 

## Impact Explanation
Address definitions (and asset transfer/issue conditions) using this pattern are typically deployed to implement tiered/limited signing authority — e.g., a co-signer or a device that is authorized to auto-approve only small payments without requiring a second factor. Because `has`/`has one` verifies existence rather than bounding the total, a party holding only the restricted key can smuggle an unbounded additional payment through the same unit, resulting in **unauthorized spending** beyond the intended limit — a direct fund-loss/authorization-bypass impact, matching the severity class validated in the original report (loss of funds control / limit bypass).

## Likelihood Explanation
Exploitation requires only posting a single, ordinarily-valid unit from an address whose definition (or an AA/asset condition it interacts with) uses `has`/`has one` with `amount_at_most`/`amount_at_least`/`amount` as an approximation for a spending cap — no privileged access, no consensus-breaking behavior, and no cooperation from other parties is needed. Any wallet, multisig template, AA, or asset condition author who (reasonably, but incorrectly) assumes `has ... amount_at_most` bounds the *total* payment is affected. This is a foot-gun in a documented, user-facing primitive rather than a deep consensus bug, so likelihood of at least one deployed definition using this incorrectly is not negligible, though it depends on adoption of this specific pattern in the wild.

## Recommendation
- Document explicitly (and enforce via linting/validation warnings) that `has`/`has one` with amount filters only proves existence of one matching item, not a bound on totals, and that `sum` (with `at_most`) must be used whenever a genuine spending cap across all matching outputs/inputs is required.
- Consider adding a stricter combinator, e.g. `has none`/`for all`, or extending `has`/`has one` semantics so that when combined with `amount_at_most`, it can optionally also assert that no *other* output in the same unit toward the same asset/address class exceeds the cap (similar to the "not has input from other address" pattern already used in `arbiter_contract.js` to prevent combining multiple contracts in one unit).
- Update any bundled templates/wallet helpers that construct spending-limit definitions to use `sum` instead of `has ... amount_at_most` for aggregate caps.

## Proof of Concept
1. Define an address (or shared address) with a definition intended to allow single-signature spends up to 100 bytes and require a second signature above that, implemented (incorrectly) as:
```
["or", [
  ["and", [["sig", {pubkey: KEY_FULL}], ["sig", {pubkey: KEY_SMALL}]]],
  ["and", [["sig", {pubkey: KEY_SMALL}], ["has", {what: "output", address: "other address", amount_at_most: 100}]]]
]]
```
The intent: holder of `KEY_SMALL` alone may authorize a payment out only if it is `<= 100`.
2. An attacker who controls only `KEY_SMALL` composes a single unit with two outputs from this address:
   - Output A: 100 bytes to `attacker_address_1` (satisfies the `has ... amount_at_most: 100` filter).
   - Output B: 1,000,000 bytes to `attacker_address_2` (not itself checked by the `has` filter, since `has` only requires one matching output to exist).
3. During validation, `evaluate` for the `"has"` branch calls `augmentMessagesAndEvaluateFilter("has", {what:"output", address:"other address", amount_at_most:100}, cb2)`, which returns `true` because Output A matches; Output B is never constrained. [2](#0-1) 
4. The unit passes authentication with only `KEY_SMALL`, letting the attacker move 1,000,000 bytes despite the "100-byte single-signature limit" — the definition author intended a cumulative cap enforced via existence-check, mirroring exactly how `maxAllocationPerUser` in the DeXe report was checked per-call instead of cumulatively.
