## Title
Rounding of per-recipient headers-commission shares can mint extra bytes beyond the fee actually collected - ([File: headers_commission.js])

### Summary
`calcHeadersCommissions()` in `headers_commission.js` splits the winning `headers_commission` fee (`full_amount`) of a parent unit among the addresses listed in `earned_headers_commission_recipients` by independently rounding each recipient's share with `Math.round(full_amount * share / 100.0)`. [1](#0-0) [2](#0-1) 

Although `validateHeadersCommissionRecipients()` enforces that the declared `earned_headers_commission_share` values sum to exactly 100%, that check only guarantees the *percentages* sum to 100 — it says nothing about the sum of the *rounded* byte amounts derived from those percentages. [3](#0-2) 

Because each recipient's `Math.round()` is applied independently, the sum of the individually rounded amounts can exceed `full_amount` (e.g. two recipients each holding a 50% share of an odd `full_amount` of 1: `Math.round(0.5)` rounds up to 1 for both, giving a total payout of 2 instead of 1). These per-recipient amounts are written straight into `headers_commission_contributions`/`headers_commission_outputs`, which later become spendable via a `type: "headers_commission"` input.

### Finding Description
This is the direct analog of the GVault bug: a fixed accounting quantity (`full_amount`, the headers commission actually owed by a payer unit) is distributed to multiple parties by rounding each share independently, with no compensating "last recipient gets the remainder" logic and no post-hoc reconciliation against the original total. The GVault report's core complaint — "rounding direction gives away shares/assets that can accumulate over time" — maps onto this code as "the sum of rounded per-recipient headers-commission amounts is not guaranteed to equal the amount actually collected."

The recipient list (`earned_headers_commission_recipients`) is fully attacker-controlled: any multi-authored unit must supply it, and the poster chooses both the addresses and the percentage shares, subject only to the "sum of shares == 100" constraint. [4](#0-3) 
An attacker who authors a unit under two or more of their own addresses can pick shares (e.g. many small shares like 1%, 1%, ..., or 50/50 splits) specifically engineered so that `Math.round(full_amount * share / 100.0)` rounds up for every recipient, so the sum of the individually credited amounts exceeds `full_amount`. [5](#0-4) 

These amounts are inserted unconditionally into `headers_commission_contributions`, then aggregated into `headers_commission_outputs`. [6](#0-5) 
The extra minted amount is not paid by any offsetting output/input elsewhere in the DAG — it is simply invented headers-commission balance that the attacker's addresses can later spend as ordinary bytes via a `type: "headers_commission"` input.

### Impact Explanation
Every time an attacker successfully wins the headers-commission of a parent unit while using an engineered multi-way recipient split that rounds favorably, the total credited `headers_commission_outputs` for that parent unit exceeds the actual `headers_commission` fee collected from the payer. This is a genuine, small, but repeatable inflation of the base-currency (bytes) supply, reachable by any ordinary unprivileged unit poster who controls two or more addresses (a trivial requirement — an attacker can simply author every unit multi-authored with self-controlled addresses). Because the bug is deterministic and can be triggered on essentially every stable unit the attacker authors, the "dust" from rounding accumulates over time, exactly as described in the exploit scenario of the source report ("Eve uses [repeated small operations] to slowly drain/inflate ... possibly affecting internal bookkeeping").

### Likelihood Explanation
High. No special privileges, mining position, or race condition is required — only the ability to post a multi-authored unit (something any address holder can do) and to choose `earned_headers_commission_recipients` shares that trigger favorable rounding (e.g., 50/50 with an odd headers_commission amount, which is common since `headers_commission` sizes vary per unit). The condition can be engineered deterministically rather than probabilistically, and can be repeated unit after unit.

### Recommendation
Change `calcHeadersCommissions()` (and the equivalent MySQL `ROUND()` path) to allocate rounding deterministically so that the sum of all recipient shares for a given `full_amount` never exceeds (or, to favor the protocol, never falls below) `full_amount` — e.g. round all-but-the-last recipient normally and assign the last recipient `full_amount - sum(previous rounded amounts)`, or use largest-remainder-style distribution. Add an invariant check (as already done elsewhere in the code with `throwError`) asserting that `SUM(rounded recipient amounts) === full_amount` before insertion, and add unit tests covering multi-recipient splits with amounts/shares chosen specifically to exercise rounding edge cases. [7](#0-6) 

### Proof of Concept
1. Attacker controls addresses `A` and `B`.
2. Attacker posts a 2-author unit (authors `A`, `B`) with `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` (passes the "sum == 100" check in `validateHeadersCommissionRecipients`). [4](#0-3) 
3. This unit wins the headers commission of a parent unit whose `headers_commission` (`full_amount`) is an odd number, e.g. `full_amount = 1` (or any odd value).
4. In `calcHeadersCommissions()`, both `A` and `B` receive `Math.round(1 * 50 / 100.0) = Math.round(0.5) = 1` byte each, for a combined payout of 2 bytes credited into `headers_commission_contributions`/`headers_commission_outputs`, i.e. twice the actual fee owed. [7](#0-6) 
5. Both `A` and `B` later spend their credited balance via ordinary `type: "headers_commission"` payment inputs, realizing 1 extra byte of supply per occurrence. Repeating this across many self-authored units accumulates real, unaccounted-for byte inflation.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
