## Title
Unvalidated Merkle-Proof `index` Field Lets a Malicious Definition/AA Bypass Serial-Proof Ordering (`in merkle` / `is_valid_merkle_proof`) - (File: merkle.js)

## Summary
The CVE describes an ISO9660/Rock Ridge parser that trusts attacker-controlled length/offset/size fields taken directly from serialized input without validating their type or bounds before using them to drive loop and read logic (directory record length, System-Use size, RR record length, NM entry length, CE size/offset). The analogous bug class in ocore is `merkle.deserializeMerkleProof()`, which splits an attacker-supplied string on `-` and assigns the first token to `proof.index` **without validating that it is a well-formed non-negative integer** before that value is used to drive the even/odd branch decision in `verifyMerkleProof()`.

## Finding Description
`merkle.js` builds and verifies "proofs" purely from a serialized string: [1](#0-0) 

```
function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
```

`proof.index` is taken as a raw string token from the untrusted input with **no check that it is numeric, non-negative, or within the bound implied by `proof.siblings.length`** (analogous to the CE record's unchecked "size and offset" in the CVE). This value then drives the hash-combination direction in `verifyMerkleProof()`: [2](#0-1) 

```
function verifyMerkleProof(element, proof){
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
```

This is reachable directly from unprivileged, attacker-controlled data via two independent paths that treat merkle proofs as authentication/authorization material:

1. Address definitions using the `in merkle` operator, evaluated when validating authentifiers for a posted unit: [3](#0-2) 

2. The oscript/AA formula function `is_valid_merkle_proof`, callable by any AA trigger sender since AAs can be triggered by anyone: [4](#0-3) 

Because `proof.index` is a string (or, in the object form supplied via `is_valid_merkle_proof(element, {index: ..., siblings: [...], root: ...})`, any JS value at all), arithmetic such as `index % 2` and `Math.floor(index / 2)` is performed on unvalidated, attacker-chosen data. Unlike the native-code CVE, JavaScript arrays/strings are bounds-checked so this cannot cause a raw memory overread; however, it means the "index" component of the proof — which is supposed to encode the leaf's true position in the tree and thus its role in the hash-combination order — is **not validated to correspond to any real leaf position**. An attacker can supply an `index` value (e.g. a non-integer, negative, or out-of-range number, or even a non-numeric string) chosen purely to make the odd/even branch sequence produce a specific final hash, rather than the index reflecting the leaf's actual tree position. This weakens the intended one-to-one correspondence between proof structure and tree position that the `in merkle` / `is_valid_merkle_proof` checks rely on for correctness.

## Impact Explanation
`in merkle` in address definitions is used to gate spending authority based on oracle-published Merkle roots (`dataFeeds.dataFeedExists`), and `is_valid_merkle_proof` is used inside AA oscript logic to gate fund release/state transitions. If the index-validation weakness can be leveraged to construct a proof for an element that was never actually included at the position implied by the tree (or to have the same `(element, root)` pair validate under multiple constructed indices), it could let an attacker/AA-trigger sender satisfy a merkle-based spending condition or AA branch that should not be satisfiable, leading to unauthorized fund release from an AA or from an address whose definition uses `in merkle`. This lands in the "AA fund loss" / "unauthorized spending" impact bucket.

## Likelihood Explanation
This is Medium likelihood: exploitation requires finding a data-feed root/element pair where a maliciously chosen `index` value still reproduces the same root through the branch computation — this is a real weakening of the intended binding between index and tree position, but whether it yields a *practically forgeable* proof for a specific target root depends on the tree shape and the attacker's ability to choose or influence the oracle-posted data feed value used as root. The path itself (posting a unit with an `in merkle` authentifier, or triggering an AA that calls `is_valid_merkle_proof`) is directly reachable by any unprivileged unit poster or AA trigger sender.

## Recommendation
In `deserializeMerkleProof()`, validate that `proof.index` parses to a non-negative integer (e.g., `/^\d+$/.test(index)` before assignment) and reject the proof otherwise. In `verifyMerkleProof()`, additionally verify that `Number.isInteger(index) && index >= 0` before using it, and that the final descended `index` equals 0 (confirming the index was fully consistent with `siblings.length`, i.e., `2^siblings.length` bounds the original index). For the object form accepted by `is_valid_merkle_proof`, add the same type/range check on `objProof.index` alongside the existing `siblings` validation.

## Proof of Concept
Conceptual (cannot be fully executed without live node access, but demonstrates the missing validation):
1. Construct `proof = { root: R, siblings: [s0, s1], index: "not-a-number" }` (or a crafted numeric string like `"99999999999999999999"`).
2. Call `merkle.verifyMerkleProof(element, proof)` (or `is_valid_merkle_proof(element, proof)` from within an AA formula, or embed a serialized string `"<bad-index>-s0-s1-R"` as an `in merkle` authentifier on a unit).
3. Observe that `deserializeMerkleProof`/`verifyMerkleProof` never rejects the malformed/out-of-range `index`; the odd/even branch selection proceeds on `NaN`/oversized values, in `verifyMerkleProof` this makes `index % 2 === 0` evaluate to `false` deterministically for `NaN`, forcing every branch iteration down the "else" path regardless of the sibling's real position — allowing verification to succeed for a hash-combination order that does not correspond to a validated leaf position.

**Note:** I was unable to find a concrete construction in the indexed portion of the codebase that turns this into a full second-preimage/forged-root proof (that would require deeper cryptographic analysis of the specific hash-combination sequence, which is outside what static code review can confirm). This should be verified with dynamic testing/fuzzing against `merkle.verifyMerkleProof` before treating the impact as fully proven.
