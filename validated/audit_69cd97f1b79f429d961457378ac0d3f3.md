Confirmed vulnerability: the webhook signature-verification key is selected using `repository.owner.login` (or `organization.login`) from the payload, while the repository/stack that actually gets acted upon is resolved using a *different* field of the very same payload: `repository.full_name` (`Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`). These two fields are never cross-checked against each other, so an attacker who legitimately controls one GitHub organization/App installation known to Shipit can forge a payload whose `repository.owner.login` matches their own org (so the HMAC computed with their own org's `webhook_secret` verifies), but whose `repository.full_name` names a repository belonging to a *different* org/stack that Shipit also tracks. ### Title
Webhook signature verified against the payload's `repository.owner.login`, but stack/repository lookup uses the unverified `repository.full_name` — (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) taken directly from the untrusted JSON body, then verifies the raw body signature against that org's `webhook_secret`. Downstream, every `Handler` subclass resolves the target `Repository`/`Stack` using `repository.full_name` from the same body. Nothing enforces that `full_name`'s owner segment matches the `owner.login`/`organization.login` field that was used to choose the verifying secret.

### Finding Description
This is the "which org authenticated versus which repository is written" binding break, analogous to the `MinVotingPowerCondition` bug where the field checked (balance) differed from the field that mattered (transferability/lock status). Here the field verified by the signature-selection logic (`repository_owner`) and the field actually used to act (repository_name/full_name → `Repository.from_github_repo_name`) are two independent strings inside the same JSON body, and no code path asserts they agree. [2](#0-1) 

Because Shipit supports multi-organization configuration (`Shipit.github(organization: ...)`), each org has its own `webhook_secret`. If an attacker is a legitimate member/admin of "Org A" (has installed the Shipit GitHub App for Org A and thus can trigger genuine, correctly-signed webhooks for Org A, or has otherwise obtained Org A's `webhook_secret` through any legitimate low-privilege channel available to an App admin of that org), they can craft a POST to `/webhooks` with:
- `repository.owner.login` = `"org-a"` (so `verify_signature` loads Org A's `webhook_secret` and the attacker signs the raw body with it — signature passes),
- `repository.full_name` = `"org-b/some-tracked-repo"` (a completely different, victim org/repo that Shipit also tracks).

The signature check only proves "this body was signed with Org A's secret" — it does not prove anything about `org-b/some-tracked-repo`. Yet handlers such as the `pull_request`, `push`, `status`, `check_suite`, and `membership` handlers act on `repository.full_name` to find the `Stack`/`Repository` and mutate its state (creating commits, changing commit statuses, updating merge/PR status, enqueuing `GithubSyncJob`, etc.), all attributing the action to the forged payload contents for Org B's stack.

### Impact Explanation
This crosses the "cross-repository writes" boundary explicitly called out as Critical impact: an actor authorized only for Org A's webhook channel can inject fabricated events (fake commit statuses, fake PR/merge events, fake push notifications) into Org B's stack that Shipit tracks, without ever having credentials for Org B. Depending on which handler is reached, this can influence real deploy/merge decisions (e.g., forging a passing CI `status` event or a `pull_request`/`merge_status` event that the merge queue or deploy gating logic trusts), i.e., an unauthorized influence on deploy/merge state for a repository the attacker does not control.

### Likelihood Explanation
Requires only that Shipit be configured for multiple GitHub organizations (a documented, supported configuration — see `config/secrets.development.example.yml` multi-org example) and that the attacker have legitimate access to trigger/sign webhooks for at least one configured org. No repository write access, no `ApiClient` token, and no compromise of Org B's secret is needed. This is a plausible deployment for any Shipit instance serving more than one GitHub org, which the engine explicitly supports.

### Recommendation
After signature verification, re-derive the acting organization strictly from the same field verified against the secret (or verify the signature using the org actually referenced by `repository.full_name`'s owner segment) and reject the webhook if `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`. Do not allow `verify_signature`'s org-selection field and `Handler#repository_name`'s org segment to diverge.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per multi-org config in `config/secrets.development.example.yml`).
2. As an attacker with Org A's `webhook_secret` (e.g., a legitimate GitHub App admin for Org A), build a JSON body for a `push` or `status` event where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"`.
3. Sign the raw body with Org A's `webhook_secret` per `Hook::DeliverySigner`/`GithubApp#verify_webhook_signature` (`sha1=<hmac>`), and set `X-Hub-Signature` accordingly.
4. POST to `/webhooks` with `X-Github-Event` set appropriately.
5. `verify_signature` computes `repository_owner = "org-a"`, loads Org A's app, verifies successfully. `WebhooksController#create` then dispatches to the handler for the event, which resolves `Repository.from_github_repo_name("org-b/victim-repo")` and mutates Org B's stack/commit/status state — despite the attacker never holding Org B's secret.
