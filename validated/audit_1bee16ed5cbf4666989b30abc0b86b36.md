### Title
`remote_proxy` weight is fixed regardless of attacker-supplied trie `proof` size, allowing underweighted execution cost - (File: pallets/remote-proxy/src/lib.rs)

### Summary
The `remote_proxy` extrinsic's declared weight only includes the fixed benchmarked `WeightInfoOf::<T,I>::remote_proxy()` value plus the inner call's `call_weight`, but never accounts for the size of the attacker-controlled `proof: Vec<Vec<u8>>` field, which is fed unbounded into `sp_trie::StorageProof::new(proof).into_memory_db()` and `read_trie_value` inside `do_remote_proxy`. An attacker can submit a `remote_proxy` call with a maximally sized, garbage-filled proof vector that forces the node to hash and insert many bytes into a `MemoryDB` before ultimately failing with `Error::InvalidProof`, at a cost not reflected in the declared weight.

### Finding Description
`Pallet::remote_proxy`'s weight annotation is: [1](#0-0) 

It adds `WeightInfoOf::<T, I>::remote_proxy()` (a constant benchmarked weight), a fixed `DbWeight::get().reads_writes(1,1)`, and the inner call's `di.call_weight` — nothing scales with the size of the `proof` parameter itself.

The benchmarked weight for `remote_proxy()` comes from a single-item trie proof built in `create_remote_proxy_proof` (only one leaf node inserted): [2](#0-1) 
and the resulting autogenerated fixed weight is a flat constant: [3](#0-2) 

However, at execution time `do_remote_proxy` processes the *actual, attacker-supplied* `proof` unconditionally: [4](#0-3) 

`RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, block }` has no bound (no `BoundedVec`, no explicit max-size or max-node-count check) enforced anywhere in the pallet: [5](#0-4) 

`sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T,I>>()` hashes and inserts every element of the supplied `Vec<Vec<u8>>` into an in-memory trie DB — this cost scales with total proof size (number of nodes × their byte length), not with the depth of a real trie path. An attacker does not need a valid trie at all: any well-formed `Vec<Vec<u8>>` of arbitrary byte blobs will be accepted by `StorageProof::new` and processed by `into_memory_db`, and only afterwards will `read_trie_value` fail to locate the `key` and the call return `Error::InvalidProof`. The cost of hashing/inserting the padding nodes is paid regardless of whether they are part of any real proof path.

Because the size of `proof` is only implicitly bounded by the overall extrinsic/block length limits (not by pallet-level or weight-level accounting), a malicious signed account can submit `remote_proxy` calls with proof vectors padded up to those limits, forcing the runtime to spend CPU proportional to the padding size while the transaction is charged (in `Weight`, which is what limits block execution) only the small fixed benchmarked amount.

### Impact Explanation
This is a weight-accounting gap: the declared extrinsic weight does not bound the actual execution cost of proof verification. Since a parachain block's execution budget is governed by declared `Weight`, not by wall-clock measurement, an attacker filling extrinsics with oversized bogus proofs can cause the node to do disproportionately more hashing/memory work per unit of accounted weight than intended, degrading block execution throughput relative to the weight accounting model. The call fails with `InvalidProof` so it doesn't corrupt state, but the invariant "declared weight bounds actual execution cost" is violated, which is the specific issue scoped by this question.

### Likelihood Explanation
The attack requires only an ordinary signed account (no privilege) and a crafted extrinsic — no cross-module state setup is needed. The `proof` field is a plain `Vec<Vec<u8>>` that decodes successfully for any byte content, so constructing a maximal, garbage-filled proof within extrinsic/block size limits is straightforward and fully repeatable across many transactions within a block, since fees only scale with transaction length/weight billed, not with the actual hashing cost incurred.

### Recommendation
- Bound the `proof` field (e.g., cap total node count and/or total byte length via a `MaxProofNodes`/`MaxProofSize` config constant) and reject oversized proofs early, before calling `into_memory_db`.
- Alternatively/additionally, make the declared weight for `remote_proxy` and `remote_proxy_with_registered_proof` scale with `proof.encoded_size()` (e.g., add a linear weight component per byte/node of the proof, benchmarked against worst-case proof sizes), rather than using a constant derived from a single-node benchmark proof.

### Proof of Concept
Rust benchmark/fuzz test plan (in `pallets/remote-proxy/src/tests.rs` or a new integration test):
1. Construct a `RemoteProxyProof::RelayChain` where `proof: Vec<Vec<u8>>` contains N garbage byte vectors (e.g., 10_000 entries of 1KB pseudo-random bytes each), sized close to the max extrinsic length allowed by the runtime's `BlockLength`.
2. Call `Pallet::<Test>::remote_proxy(origin, real, None, call, crafted_proof)` and measure actual wall-clock/instruction cost of `do_remote_proxy` (e.g., via `frame_benchmarking`'s timing harness or manual `std::time::Instant`).
3. Compare measured cost against `WeightInfoOf::<Test, ()>::remote_proxy()` (the fixed autogenerated constant).
4. Assert: `measured_execution_time > K * declared_weight_ref_time` for some small tolerance factor `K` (e.g., K=1.2), demonstrating the declared weight underestimates actual cost as proof size grows, while the call still returns `Err(Error::InvalidProof)`.
5. Repeat with proof sizes swept from 1 node to max block-length-constrained size, plotting execution time vs. declared (constant) weight to show the ratio is unbounded as a function of attacker-controlled input size.
