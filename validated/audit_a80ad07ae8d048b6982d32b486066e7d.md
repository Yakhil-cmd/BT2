### Title
Webhook signature verification keys off `repository.owner.login`, but event processing acts on the independently-attacker-controlled `repository.full_name` — allowing a low-secret org to forge writes against a different, unrelated Stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`:
<cite repo="Jortegata/shipit-engine--020" path="app/controllers/shipit/webhooks_controller.rb" start="24-49" />

The actual side effect of the request — which `Stack`/`Repository` record is looked up and mutated (e.g. `sync_github` triggered, `Commit` status created) — is computed independently by `Shipit::Webhooks::Handlers::Handler#repository_name`, which reads `payload.dig('repository', 'full_name')`:
<cite repo="Jortegata/shipit-engine--020" path="app/models/shipit/webhooks/handlers/handler.rb" start="32-38" />

and is used by `PushHandler#process` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`) and by `StatusHandler#process` (writes a `Commit` status looked up only by `sha`, with no repo/owner check at all):
<cite repo="Jortegata/shipit-engine--020" path="app/models/shipit/webhooks/handlers/push_handler.rb" start="12-17" />
<cite repo="Jortegata/shipit-engine--020" path="app/models/shipit/webhooks/handlers/status_handler.rb" start="20-24" />

Because the raw JSON body is entirely attacker-controlled (it isn't actually delivered by GitHub — it's whatever is POSTed to `/webhooks`), nothing enforces that `repository.owner.login` (used to pick the signing secret) is consistent with `repository.full_name` (used to pick the target `Repository`/`Stack`). These are two independently-settable JSON fields inside the same request body.

Compounding this, `GitHubApp#verify_webhook_signature` treats a blank/`nil` `webhook_secret` as an automatic pass:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
<cite repo="Jortegata/shipit-engine--020" path="lib/shipit/github_app.rb" start="76-83" />

This is a documented, supported configuration — the setup docs and example secrets files explicitly show `webhook_secret: # nil` as valid per-organization config in multi-org deployments:
<cite repo="Jortegata/shipit-engine--020" path="docs/setup.md" start="181-209" />
<cite repo="Jortegata/shipit-engine--020" path="config/secrets.development.example.yml" start="18-38" />

`Shipit.github(organization:)` resolves the app/secret purely by the organization key from the multi-org `github:` config hash:
<cite repo="Jortegata/shipit-engine--020" path="lib/shipit.rb" start="170-181" />

**The broken binding:** `organization authenticated by verify_signature` (`repository.owner.login`) ≠ `repository actually written by the handler` (`repository.full_name`'s owner segment). GitHub itself always keeps these consistent for genuine webhooks, but Shipit's controller never re-derives or cross-checks `repository_name` against `repository_owner` — it trusts the raw POST body wholesale once *any* signature check for the attacker-chosen org passes (including the "no secret configured" bypass).

### Impact Explanation
An unprivileged network attacker who knows (or exploits) one org in a multi-org Shipit deployment configured with a blank `webhook_secret` (a documented, supported configuration) can send a forged HTTP POST to `/webhooks` with:
- `repository.owner.login` = the blank-secret org (or `organization.login` fallback) → passes `verify_signature` unconditionally.
- `repository.full_name` = `"OtherOrg/production-repo"` (a fully protected, unrelated repository tracked by Shipit).

This is routed to `PushHandler`, which resolves `Repository.from_github_repo_name("OtherOrg/production-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on stacks the attacker has no legitimate relationship to, forcing Shipit to re-sync/deploy state based on an attacker-chosen `after` SHA against a repo/org the attacker never authenticated against. `StatusHandler` is worse: it performs zero repository-owner verification at all, matching purely on `sha`, letting the attacker inject arbitrary CI status text for any commit tracked anywhere in the Shipit instance merely by satisfying the blank-secret org's signature check. This can be used to fabricate a passing CI status on a commit to trigger an unauthorized deploy gated on CI status, and to force out-of-band syncs across repositories/orgs the attacker has no write access to — an unauthorized-deploy / cross-repository-write class impact.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (explicitly documented and supported), and (2) at least one onboarded org configured with a blank/nil `webhook_secret` (also explicitly documented as a valid option, e.g. for local/dev or low-risk orgs) — or knowledge of any one org's webhook secret via other means. Given the docs actively suggest `webhook_secret: # nil` as acceptable, this is a realistic, low-effort misconfiguration rather than a purely theoretical one. No session, `ApiClient` token, or GitHub write access to the target repo is required — only the ability to POST arbitrary JSON to the public `/webhooks` endpoint.

### Recommendation
- In `WebhooksController#verify_signature`, cross-check that the organization used to select the signing key matches the organization embedded in `repository.full_name` (and reject payloads where these disagree).
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-org configurations; require a non-blank secret for every onboarded organization, or explicitly disable event processing for organizations without one.
- In `StatusHandler#process`, verify that the commit's repository matches the repository asserted in the payload before creating a status, rather than trusting the raw `sha` alone.

### Proof of Concept
1. Configure Shipit in multi-org mode with two orgs: `LowSecOrg` (`webhook_secret: nil`) and `HighSecOrg` (proper `webhook_secret`, tracking `HighSecOrg/prod`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "attacker-chosen-sha",
  "repository": {
    "owner": { "login": "LowSecOrg" },
    "full_name": "HighSecOrg/prod"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "LowSecOrg")`, whose `verify_webhook_signature` returns `true` unconditionally since `webhook_secret` is blank — no valid `X-Hub-Signature` needed.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("HighSecOrg/prod")` and invokes `sync_github` on its stacks, despite the attacker never having authenticated against `HighSecOrg`.
