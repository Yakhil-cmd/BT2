This confirms Shipit is explicitly designed to support multiple GitHub Apps, each with its own `webhook_secret`, keyed by organization login [1](#0-0) , and the fixture `secrets_double_github_app.yml` demonstrates two distinct orgs (`OrgOne`, `OrgTwo`) each with an independent installation/secret [2](#0-1) . This is the precondition the audit question requires: an attacker who legitimately controls their own org's GitHub App knows/controls that org's `webhook_secret`.

### Title
Cross-repository webhook trust confusion between `repository.owner.login` and `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to validate the HMAC against using `repository.owner.login`, while `Handler#stacks`/`#repository_name` (used by `PushHandler`) resolve the actual `Repository`/`Stack` to mutate using the independent `repository.full_name` field from the same JSON body. No code anywhere checks that these two fields agree, so a signature valid for one org's secret can be paired with a `full_name` naming a completely different, unrelated org's repository.

### Finding Description
The broken binding: `repository_owner (params.dig('repository','owner','login'))` used in `verify_signature` [3](#0-2) [4](#0-3)  must equal `repository.full_name.split('/').first` used in `Handler#repository_name`/`#stacks` [5](#0-4) , but nothing enforces this equality.

Code path: `WebhooksController#create` calls `verify_signature` as a `before_action`, which picks `github_app = Shipit.github(organization: repository_owner)` [6](#0-5)  and verifies the HMAC of the *entire raw body* against that org's `webhook_secret` via `GitHubApp#verify_webhook_signature` [7](#0-6) . If valid, `create` parses the same raw body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, e.g. `PushHandler#process` [8](#0-7) , which resolves `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` [5](#0-4) .

Because Shipit supports multiple independently configured GitHub Apps/orgs, each with its own `webhook_secret` [1](#0-0) , an attacker who owns an org with a legitimate GitHub App installation knows (or controls) that org's `webhook_secret`. They can then POST directly to `/webhooks` (bypassing real GitHub delivery entirely, permitted since the attacker is "any internet user who can send HTTP requests... including POST /webhooks") with a crafted JSON body where `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` picks their org's `GitHubApp` and their self-computed `X-Hub-Signature` validates), but `repository.full_name` = `"victim-org/victim-repo"`. Since the HMAC covers the raw bytes of the body they fully control, they can compute a valid signature for arbitrary content, including the mismatched `full_name`. `verify_signature` passes, `PushHandler` then resolves the *victim's* `Repository`/`Stack` via `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` on it.

None of the existing guards catch this: `verify_signature` never reads or compares `full_name`; `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema (`PushHandler.params`) only requires `:ref` and `:after`, not that `repository.owner.login == repository.full_name`'s owner; `Repository.from_github_repo_name` and its validations do not know about `owner.login` at all [9](#0-8) .

### Impact Explanation
An attacker-controlled org's genuinely valid webhook signature can trigger `GithubSyncJob`/`stack.sync_github` on a `Stack` belonging to a repository the attacker does not own and never authenticated against. This is a cross-tenant write: the party whose secret validated the signature (`repository_owner`) is not the party whose repository/stack is mutated (`repository.full_name`'s owner). This matches the Critical impact category "a payload for one repository mutating another's stack" and is repeatable against any Shipit-tracked stack whose owner/name the attacker can guess or discover, as long as the attacker holds any single legitimate org+secret pair configured in the multi-org Shipit deployment.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations/Apps (the `github_app_config`/multi-org support path in `lib/shipit.rb`), and (2) the attacker legitimately controls at least one of those orgs and its App/`webhook_secret` (as stated in the attacker model — an unprivileged GitHub user creating their own org and installing a legitimate GitHub App on it, which is the normal, low-cost onboarding flow for a self-serve multi-tenant Shipit instance). No Shipit or victim secrets are needed. Feasibility is high — a single crafted HTTP POST suffices — and the attack is repeatable against any other tracked repository/stack.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), assert that the owner segment of `repository.full_name` equals `repository.owner.login` (or `organization.login`) before processing, e.g. reject the request with 422 if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`. Enforce this check centrally in the controller before any handler runs, not per-handler.

### Proof of Concept
minitest `ActionDispatch::IntegrationTest` (or `ActionController::TestCase` matching existing `test/controllers/webhooks_controller_test.rb` style):
1. Configure two orgs in test secrets (as in `secrets_double_github_app.yml`), each with a distinct `webhook_secret`.
2. Build a `push` payload where `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"` (a real, existing `Stack`'s repository), with `ref`/`after` matching the victim stack's branch.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, raw_body)`.
4. POST to `/webhooks` with that header and body.
5. Assert (currently failing / vulnerable): `assert_no_enqueued_jobs { post ... }` for `GithubSyncJob` targeting the victim stack, and/or `assert_response :unprocessable_entity` — both fail today because the signature check passes and `GithubSyncJob` is enqueued for the victim's stack, demonstrating `repository_owner (attacker-org) != repository.full_name.split('/').first (victim-org)` is never checked.

    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations

  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
