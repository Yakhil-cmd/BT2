### Title
Webhook signature verified against `repository.owner.login`'s secret while the event body's `repository.full_name` (used to identify the target stack) is never bound to that verification — cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of the `unspecifiedAmount` bug: the Uniswap hooks let one field (`_targetOutput`, computed under an assumption about which side of the swap is "unspecified") govern an action on a different field (the actual amount charged) without re-validating that the two refer to the same quantity. In shipit-engine, `Shipit.github(organization:)` supports **multi-organization** configuration (`github_organizations`, `github_app_config`) [1](#0-0) , each org holding its own `webhook_secret` [2](#0-1) . `WebhooksController#verify_signature` selects *which* organization's HMAC secret to check the signature against using `repository_owner`, read from the same untrusted payload it is about to verify: `params.dig('repository', 'owner', 'login')` [3](#0-2) . The signature only proves the raw payload was signed with *that org's* secret — it never binds the signature to the field the handlers actually act on, `repository.full_name`, which is a completely separate JSON field [4](#0-3) .

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handler mutates`

Before the flaw (intended trust model): a webhook is only accepted if it is signed by the GitHub App installed on the same org that owns the affected repository, since GitHub always sets `repository.owner.login` to the actual repo's owner and signs the payload with that installation's secret.

After the flaw: `repository_owner` and the value used for stack resolution (`repository.full_name`) are two independent, attacker-writable JSON fields in the same unsigned-until-verified request body. Nothing forces `full_name` to start with `repository_owner`. Any principal who legitimately controls a GitHub App installation on **their own** organization (and therefore genuinely knows *that org's* `webhook_secret` — a normal, unprivileged action, since GitHub webhook secrets are configured per-installation and are not secret from the org's own admins/members who can trigger real webhooks) can:

1. Send a POST to `/webhooks` with `X-Github-Event: push` (or `check_suite`, `status`, etc.).
2. Set `repository.owner.login = "attacker-org"` (their own org) so `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and validates the signature against the secret they legitimately possess [5](#0-4) .
3. Set `repository.full_name = "victim-org/victim-repo"` — a completely independent field never covered by the "which secret to check" decision.
4. `verify_signature` succeeds (HMAC(attacker's own secret, raw_post) matches, because the attacker legitimately signs their own payload).
5. `create` dispatches to handlers using the same `params`, e.g. push handling resolves the stack via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [4](#0-3)  and `Repository.from_github_repo_name` splits `full_name` and looks up the victim's actual `Repository`/`Stack` row [6](#0-5) .
6. The push webhook handler enqueues `GithubSyncJob` against the victim stack, which fetches refs and can advance the tracked commit/HEAD state Shipit uses to decide what is deployable, using entirely attacker-supplied `before`/`after` SHAs and branch data — a write into a repository/stack the attacker's org has no relationship to.

This exactly mirrors the reported bug class: a value (`_targetOutput`, computed from one side of the swap) is used to cap/validate a different, independently-controlled value (`unspecifiedAmount`), without checking whether they represent the same thing. Here, the org whose key validated the HMAC is not cryptographically tied to the org/repo the handler subsequently mutates.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. An attacker who only has legitimate control of their own GitHub App installation (unprivileged with respect to the victim's Shipit instance and repositories) can forge webhook events that get accepted as authentic and are then processed against an arbitrary victim repository/stack tracked by the same Shipit instance, corrupting sync state (`GithubSyncJob`), commit statuses, check-run refresh, or membership/team records depending on which event type is replayed — a cross-repository write satisfying the Critical impact bar.

### Likelihood Explanation
Requires the deployment to configure more than one GitHub organization under `secrets.github` (the multi-org schema explicitly supported by `Shipit.github_app_config`/`github_organizations` in `lib/shipit.rb`), and requires the attacker to control (or have push access triggering webhooks for) at least one of the configured orgs so they know that org's `webhook_secret`. Under that realistic multi-tenant configuration, the attack requires only crafting a raw HTTP POST with mismatched `owner.login` vs `full_name` — no elevated privilege against the victim stack is needed.

### Recommendation
In `WebhooksController#verify_signature`, do not let the payload itself pick which secret validates the payload's own claims about a different repository. Concretely:
- After signature verification succeeds for `repository_owner`, re-derive the repository/org actually referenced by `full_name` and reject (422) if `full_name`'s owner segment does not case-insensitively match `repository_owner`.
- Alternatively, resolve the target `Repository`/`Stack` via the *verified* organization only (i.e., constrain `Repository.from_github_repo_name` lookups to repos owned by `repository_owner`) rather than trusting `full_name` wholesale in `Handler#repository_name`.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 computed with attacker-org's real webhook_secret over the exact raw body below>

{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "before": "0000000000000000000000000000000000000000",
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/main"
}
```
`verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates successfully because the attacker legitimately knows that org's secret [5](#0-4) . `create` then dispatches to the push handler, which computes `repository_name` from `full_name = "victim-org/victim-repo"` [4](#0-3) , resolves the victim's real `Repository`/`Stack` via `Repository.from_github_repo_name` [6](#0-5) , and enqueues sync work against it — despite the request never having been signed by anything related to `victim-org`.

*Note: I could not fully trace every downstream handler (e.g., exact `GithubSyncJob` write semantics) within the available context/time; the push-handler path shown above is directly supported by the cited files, but a full audit of all event handlers listed in `Shipit::Webhooks::DEFAULT_HANDLERS` for the worst-case write would benefit from a dedicated Devin session with full repo access.*

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
