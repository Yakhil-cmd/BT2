### Title
Cross-organization `Team` hijack via `github_id`-only lookup in membership webhook - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `github_id`, ignoring `organization`. An attacker who controls a *different*, Shipit-known GitHub organization can guess/know an existing team's numeric `github_id` and send a membership webhook signed with their own organization's secret, causing the existing team (belonging to another organization, e.g. `shopify`) to gain a new `Membership` for an attacker-controlled user without its `organization` column ever being touched.

### Finding Description
Binding claimed to hold: `Team#organization after find_or_create_team! == organization that authenticated the payload` (i.e. `team.organization == repository_owner` used in `verify_signature`). Tracing the code shows this binding is **not enforced**:

- `WebhooksController#verify_signature` resolves the authenticating org via `repository_owner`, which for membership events (no `repository` key in the real GitHub payload) falls back to `params.dig('organization','login')` [3](#0-2) , and verifies the signature against `Shipit.github(organization: repository_owner)` [4](#0-3) . This only proves the payload was signed by *some* organization known to Shipit (the org whose webhook secret matches) — namely whichever org the attacker controls and has legitimately onboarded to Shipit.
- `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [2](#0-1) . `find_or_create_by!` only runs the block on **creation**; if a `Team` row with that `github_id` already exists (e.g. `github_id: 42, organization: 'shopify'`), it is simply returned, and its `organization` is left as `'shopify'` regardless of `params.organization.login`.
- The `teams` table has a unique index on `["organization", "slug"]`, not on `github_id` alone [1](#0-0) , so nothing at the DB layer stops a second organization's team from colliding on `github_id`.
- `process` then calls `team.add_member(member)` (or removes a member) on whatever `Team` was returned — the pre-existing `shopify` team — using a `User` resolved purely from `params.member.login` via `User.find_or_create_by_login!` [5](#0-4) .

Attacker's request: they must own/administer a GitHub organization (e.g. `attacker-org`) that is already connected to Shipit (has a configured `GithubHook::Organization`/webhook secret — a normal, low-privilege onboarding action, not requiring Shipit admin rights). They configure that org's webhook to point at the Shipit host and craft (or simply let GitHub send, by adding themselves to a team whose numeric id they choose... but they don't control `team.id` from GitHub directly) a `membership` event. More directly, since they control the webhook secret for `attacker-org`, they can POST arbitrary JSON to `/webhooks` with a valid `X-Hub-Signature` for that secret, setting `organization.login = "attacker-org"`, `team.id = 42` (the target `shopify` team's known/guessable GitHub team numeric id), and `member.login` = their own GitHub login, `action = "added"`.

Existing guards fail to prevent this:
- `verify_signature` only checks that the payload was signed by *a* known org's secret — it does not check that the org named inside the payload matches any specific team's `organization`, nor does the handler cross-check `params.organization.login` against the existing team's `organization` before mutating.
- `ExplicitParameters` schema only validates types/presence of `team.id`, `organization.login`, `member.login` [6](#0-5) ; it does not validate that the ids are consistent with a specific tenant.
- No model validation on `Team` ties `github_id` to `organization`.

### Impact Explanation
An attacker who administers any GitHub organization already connected to Shipit can inject themselves (or any GitHub user) as a `Membership` of an arbitrary, pre-existing `Team` belonging to a different organization, without ever needing that organization's webhook secret. Since `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , and `Shipit.github_teams` is built from `Shipit.github_teams` config (teams considered authoritative for authorization) [8](#0-7) , adding oneself as a member of a `Team` row that is one of `Shipit.github_teams` grants `authorized?` — i.e., escalation into the `Shipit.github_teams` authorization boundary from an unrelated, attacker-controlled organization. This matches the "High - escalation into `Shipit.github_teams` authorization" category. This is repeatable against any team whose `github_id` the attacker can determine (GitHub team ids are enumerable/discoverable) and is not scoped to a single repository — any org with a Shipit-connected webhook can be used as the signing vector.

### Likelihood Explanation
Preconditions: the attacker must control at least one GitHub organization that is already integrated with Shipit (has a `GithubHook::Organization`/webhook secret configured) — a normal, unprivileged onboarding step available to any GitHub org owner, not requiring any Shipit secret to be stolen. The attacker must know or guess the target team's numeric GitHub `team.id` (teams are often discoverable via GitHub's team API for public/known orgs, or brute-forceable given small integer ranges). No Shipit session, API token, or the victim organization's webhook secret is required. This is a low-cost, repeatable attack once the attacker has any Shipit-connected org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization` (matching the authenticating organization), e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and reject/raise if a team with that `github_id` exists under a *different* `organization` rather than silently reusing it. Additionally consider verifying that `params.organization.login` matches the organization derived by `verify_signature` (`repository_owner`) before processing the event.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, minitest)
test "cross-organization github_id collision does not repoint an existing team's organization" do
  shopify_team = Shipit::Team.create!(github_id: 42, organization: 'shopify', slug: 'developers', name: 'Developers')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 42, 'name' => 'Attacker Team', 'slug' => 'attacker-team', 'url' => 'https://example.com' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'mallory' },
  }

  Shipit::User.expects(:find_or_create_by_login!).with('mallory').returns(Shipit::User.new(name: 'Mallory', login: 'mallory'))

  assert_no_difference -> { Shipit::Team.count } do
    Shipit::Webhooks::Handlers::MembershipHandler.new(payload).process
  end

  shopify_team.reload
  assert_equal 'shopify', shopify_team.organization # binding claims this should only be mutated by 'shopify'-signed payloads
  assert_includes shopify_team.members.map(&:login), 'mallory' # but attacker-signed payload still wrote a Membership into it
end
```
This demonstrates the fixture `shopify` team (not a new team) receives the attacker's membership while `organization` remains `'shopify'`, proving the write crosses the tenant boundary implied by the webhook's signing organization.
