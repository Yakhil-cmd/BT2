### Title
Signature-verification target org is read from unauthenticated payload fields that are independent of the repository actually acted upon, allowing forged webhooks against any repository whose owning organization has no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate the request's HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** JSON body. The handler layer that subsequently acts on the event resolves the target `Stack`/`Repository` using a *different* field from that same unverified body: `repository.full_name`. These two lookups are never required to agree, so an attacker can pick any org for the "authenticated organization" role while pointing the actual write/action at a completely different, unrelated repository.

### Finding Description
`verify_signature` computes the signing org purely from attacker-supplied JSON, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance whose `verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, every event handler resolves the `Stack`(s) to operate on using an entirely separate field of the same unauthenticated body, `repository.full_name`, with no cross-check against `repository_owner`: [4](#0-3) 

This breaks the intended binding: **organization authenticated == repository written**. The controller authenticates "org X sent this," but the handler acts on "repo owned by org Y," where X and Y can be chosen independently by the attacker as long as X is a configured Shipit organization with a blank/unset `webhook_secret` (a supported, documented configuration - see `config/secrets.development.shopify.yml`, where `webhook_secret:` is left `nil`).

### Impact Explanation
Because the `POST /webhooks` endpoint is public and unauthenticated by design (it exists to receive GitHub's webhooks), any external actor can send a crafted payload directly. If Shipit hosts even one organization configured without a `webhook_secret` (a valid, non-error configuration state per `verify_webhook_signature`), the attacker can spoof `repository.owner.login` to that org while setting `repository.full_name` to any *other*, properly-secured stack's repository. The `status` handler, for example, creates `Status` records for arbitrary commits from unauthenticated webhook data (confirmed by existing controller tests creating a `Status` from a `status` event payload). A forged, always-`success` status on a victim stack's commit can defeat CI-gating (`require_ci`) checks used by the deploy API to decide `deployable?`, enabling an **unauthorized deploy** of a commit that never actually passed CI on the real repository - directly matching the Critical "unauthorized deploy" impact category. Other handlers (`push`, `check_suite`, `membership`) are similarly reachable against a victim repo/org whose payload fields are entirely attacker-chosen once the "authenticating" org is unrelated and secret-less.

### Likelihood Explanation
Requires no credentials, no repository write access, and no session: only that the Shipit deployment has at least one configured GitHub organization with no `webhook_secret` set - an explicitly supported configuration shown in the project's own sample secrets file. The attacker only needs to know that org's name and the victim's `owner/repo` full name, both public information.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: resolve the target `Repository`/`Stack` from `repository.full_name` first, then use that repository's *own* owner to select the `GithubApp` config for signature verification, rather than trusting a separately-read, unverified `repository.owner.login`/`organization.login` field. Additionally, do not treat a missing `webhook_secret` as an implicit signature-verification bypass (`return true unless webhook_secret`); require explicit opt-in (e.g., a boolean flag) if unsigned webhooks are intentionally supported for a given org.

### Proof of Concept
1. Configure Shipit with two orgs: `attacker-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`, owns a tracked `Stack` for `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (absent/invalid) `X-Hub-Signature` header.
4. `StatusHandler` resolves the stack via `repository.full_name = "victim-org/victim-repo"` and records a forged successful `Status` for the victim commit, which can subsequently satisfy `require_ci` deploy checks for that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
