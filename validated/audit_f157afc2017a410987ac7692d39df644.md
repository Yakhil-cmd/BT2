### Title
Webhook signature verification keys off an unauthenticated payload field (`repository.owner.login`), decoupled from the field handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the attacker-controlled JSON body, before the signature itself has been checked. If that organization has no `webhook_secret` configured (a supported configuration, e.g. `secrets_double_github_app.yml`'s `OrgTwo`), `verify_webhook_signature` returns `true` unconditionally, and the entire payload — including other fields such as `repository.full_name` that downstream handlers use to resolve the actual `Stack`/`Repository` to act on — is accepted as authentic.

### Finding Description
`verify_signature` derives the signing organization from the payload itself: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. `GithubApp#verify_webhook_signature` returns `true` immediately if that organization's `webhook_secret` is blank/nil. Since a Shipit installation can configure multiple GitHub Apps for multiple organizations (some with a secret, some without, per the multi-org config format), an attacker who knows (or guesses) the name of an org configured *without* a webhook secret can supply that org's login in `repository.owner.login`/`organization.login` to pass `verify_signature` trivially, while still shipping any other payload contents (e.g. `repository.full_name` pointing at a different, secret-protected org's stack) that the actual event handler (`Shipit::Webhooks.for_event(event)`) subsequently trusts and acts on. The equality being broken is: *organization whose signature was verified* ≠ *repository the handler actually writes state for*.

### Impact Explanation
If exploitable end-to-end, this allows an unauthenticated attacker to forge GitHub webhook events (`push`, `status`, `check_suite`, `membership`, etc.) for a victim stack/repository that does have a configured secret, by "borrowing" the identity of a sibling, secret-less organization on the same installation. This could trigger unauthorized `GithubSyncJob`s, fabricate commit statuses, or manipulate merge-queue state for a repository the attacker does not control — an authentication-bypass-class issue matching the required "unauthorized deploy/merge" impact bar, contingent on confirming no downstream cross-check between `repository_owner` and the fields resolving the target `Stack`.

### Likelihood Explanation
Likelihood depends entirely on operator configuration: a Shipit instance must have at least one organization installed without a `webhook_secret` for this to be exploitable, and the attacker must know that org's login. This is a real, documented configuration shape (seen in the multi-org test fixtures), but not necessarily how most installations are deployed, so likelihood is best characterized as low-to-medium and configuration-dependent.

### Recommendation
Do not select the verification secret from attacker-controlled payload fields that are also used later for authorization/resolution. Instead, verify the signature using a secret bound to the receiving endpoint/route (e.g., one shared or per-installation secret validated up front), or, if per-organization secrets are required, cross-validate that the organization used to select the secret matches the organization ultimately used to resolve the target repository/stack before acting on the payload. Additionally, avoid treating "no secret configured" as an automatic pass when other organizations on the same install do have secrets configured — consider requiring all configured organizations to define a `webhook_secret`.

### Proof of Concept
Conceptual, not fully verified against handler code:
1. Attacker learns (e.g., via GitHub org enumeration) that `OrgTwo` is installed on the target Shipit instance with no `webhook_secret` configured.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and body `{"repository": {"owner": {"login": "OrgTwo"}, "full_name": "OrgOne/victim-repo"}, ...}`, omitting/forging `X-Hub-Signature`.
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is nil, so the before_action passes.
4. `Shipit::Webhooks.for_event('push')` handlers run against the full payload, which references `OrgOne/victim-repo`, without ever re-validating that `OrgOne` actually signed the request.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
