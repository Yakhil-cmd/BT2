### Title
`provision?` operator-precedence bug lets `review_stacks_enabled: false` be bypassed when `provisioning_behavior` is `allow_with_label`/`prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` (and the identical `ReopenedHandler#unarchive?`) writes `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...) || (...)`. Because Ruby's `&&` binds tighter than `||`, `review_stacks_enabled` only gates the `allow_all?` disjunct, not the `allow_with_label?`/`prevent_with_label?` disjuncts. This is not a hypothetical: `LabeledHandler#respond_to_label_change?` in the same codebase correctly hoists `repository.review_stacks_enabled` as an independent top-level `&&` guard, proving the intended binding and confirming `OpenedHandler`/`ReopenedHandler` diverge from it.

### Finding Description
Intended binding: `provision? == review_stacks_enabled && (allow_all? || (allow_with_label? && has_label) || (prevent_with_label? && !has_label))`.

Actual code (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`):
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. The identical pattern exists in `ReopenedHandler#unarchive?` [2](#0-1) . By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` at the top level before evaluating `archive?`/`unarchive?` [3](#0-2) , demonstrating the correct, intended guard shape and that its absence in `opened_handler.rb`/`reopened_handler.rb` is a genuine defect rather than a stylistic choice.

`Repository#provisioning_behavior` is a Rails enum (`prefix: :provisioning_behavior`) over `%w[allow_all allow_with_label prevent_with_label]` [4](#0-3) , with column default `allow_all` and `review_stacks_enabled` default `false` [5](#0-4) . So on an unconfigured/default repository both `provisioning_behavior_allow_with_label?` and `provisioning_behavior_prevent_with_label?` are false, and the bug is masked. But `allow_with_label` and `prevent_with_label` are first-class, UI-exposed configuration options (`app/views/shipit/repositories/settings.html.erb`) that any Shipit operator can select without touching `review_stacks_enabled`. Once either is selected, `review_stacks_enabled` no longer participates in `provision?`/`unarchive?` at all — only the label condition on the incoming PR matters.

Exploit path: an unprivileged GitHub user who can open a pull request (and label their own PR, or omit a label for `prevent_with_label`) against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`) triggers a `pull_request.opened` webhook that reaches `OpenedHandler#process`, which calls `respond_to_pull_request_opened?` → `provision?` (true despite `review_stacks_enabled: false`) → `ReviewStackAdapter#find_or_create!`, creating a live `Stack`/`ReviewStack` record and driving it into the provisioning queue (`assert_pending_provision` pattern in tests shows `awaiting_provision?`) [6](#0-5) . None of `verify_signature`, `ExplicitParameters`, or model validations touch this logic bug — they only validate payload shape and authenticity of the webhook sender/repo lookup, not the business-logic gate.

### Impact Explanation
An operator who disables review-stack auto-provisioning for a repository (`review_stacks_enabled: false`) while leaving `provisioning_behavior` at `allow_with_label`/`prevent_with_label` gets provisioning behavior identical to having review stacks fully enabled: any PR author who can add/omit a label on their own PR causes a `Shipit::Stack` to be created and enter the provisioning workflow for that repository, contrary to the operator's explicit intent to disable the feature. This is a repository-scoped authorization gate failure — the "review_stacks_enabled" kill switch does not actually gate provisioning for two of three behavior modes — leading to unauthorized stack creation/provisioning that the operator believed was turned off.

### Likelihood Explanation
Preconditions: the target repository must be Shipit-tracked with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (both are ordinary, documented, UI-selectable settings — not a misconfiguration) and `review_stacks_enabled: false`. No secrets, tokens, or privileged roles are needed; the attacker only needs to be able to open a PR against/from the tracked repository and control PR labels, which is the baseline unprivileged-attacker capability given in this audit's threat model. The condition is deterministic and repeatable for every PR against every such repository.

### Recommendation
Fix operator precedence by explicitly parenthesizing so `review_stacks_enabled` gates the whole expression, matching the correct pattern already used in `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_precedence_test.rb
test "does not provision when review_stacks_enabled is false, even for allow_with_label with matching label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not provision when review_stacks_enabled is false, even for prevent_with_label with no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :prevent_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Both assertions fail against current code (`Shipit::Stack.count` increases by 1 in each case) because `provision?` evaluates true regardless of `review_stacks_enabled: false`, proving the binding `provision? == review_stacks_enabled && (...)` does not hold.
