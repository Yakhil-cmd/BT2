### Title
`pallet-oracle` consumers can be fed a permanently-stale aggregated price with no on-chain freshness check, unlike Chainlink's recommended heartbeat/sequencer validation - (File: substrate/frame/honzon/oracle/src/default_combine_data.rs)

### Summary
The reported issue is that JOJO's Chainlink adaptor trusts `latestRoundData()` without checking whether the L2 sequencer is live, allowing stale price data to be used indefinitely. The Polkadot SDK analog is `pallet-oracle`'s `DefaultCombineData::combine_data` and `DataProvider::get`: when the set of fresh operator submissions drops below `MinimumCount` (feed-provider "outage" analog to sequencer downtime), the pallet silently returns the old `prev_value` from storage — with no check on how old that carried-forward value itself is — and any consumer calling `Oracle::get`/`DataProvider::get` receives it as if it were current.

### Finding Description
`DefaultCombineData::combine_data` filters incoming raw values by `expires_in` but then falls back to `prev_value` unconditionally whenever the surviving count is below the configured minimum: [1](#0-0) 

`prev_value` is the last value written into the `Values` storage map, which itself is never re-validated against `expires_in` in this fallback path — it is only checked for the newly submitted raw values, not for the value that gets carried forward. If oracle operators stop feeding data (analogous to the L2 sequencer going down and price feeds stalling), `Values` keeps returning the last stored aggregate forever, because nothing ever expires the stored aggregate itself.

On the read side, `Pallet::get` and the `DataProvider`/`DataProviderExtended` implementations return the value with no freshness assertion at all: [2](#0-1) [3](#0-2) 

The `TimestampedValue` wrapper does carry a `timestamp` field [4](#0-3)  so the pallet has the information needed to detect staleness, but nothing enforces it at the read path (`DataProvider::get` strips the timestamp entirely) or in the write-path fallback.

The dispatchable entry point (`feed_values`) is permissioned to `T::Members` (a `SortedMembers` set, e.g. `TechnicalMembership` in the reference kitchensink wiring) or root: [5](#0-4) [6](#0-5) 

so the attacker-controlled input here is not the extrinsic call itself, but the *absence* of fresh submissions (analogous to the sequencer outage — an externally-driven halt of live data rather than a privileged/malicious call).

### Impact Explanation
Any consumer pallet that relies on `DataProvider::get`/`DataProviderExtended::get_all_values` (e.g. a stablecoin/PSM module reading a price to compute swap rates, collateral valuation, or liquidation thresholds) would silently keep operating on an arbitrarily old, un-flagged price once operator feeds stop, exactly mirroring the reported Chainlink issue: users can continue interacting with the protocol against stale rates with no on-chain signal that the data is no longer live. This is a data-integrity gap rather than a direct fund-theft path in the oracle pallet itself; actual severity depends entirely on what a downstream consumer does with the value, since in this repository no live/production runtime currently wires a financial pallet to `pallet-oracle`'s `DataProvider` (`pallet-psm`, introduced in the same PR, does not reference `DataProvider`/`Oracle` in the code I could inspect). I could not confirm any currently-deployed Parity/Snowbridge program runtime that consumes this oracle for value-bearing decisions.

### Likelihood Explanation
Low-to-Medium as a standalone finding: `pallet-oracle` is newly introduced (PRDoc `prdoc/stable2512/pr_9815.prdoc` for the AssetHub stablecoin effort) and is only wired into the `kitchensink-runtime` (a test/reference runtime), not into a shipped production chain. Without a concrete consumer that trusts the value for a fund-moving decision, this is a design gap rather than an immediately exploitable, in-scope bounty-eligible bug on a live Parity/Snowbridge program.

### Recommendation
- Track/expose the staleness of the *stored aggregate* itself, not just incoming raw submissions: compare `Values::<T,I>::get(key).timestamp` against `now - expires_in` before returning it from `combine_data`'s fallback branch, and clear/return `None` when stale instead of perpetuating `prev_value`.
- Expose the `DataProvider` trait (or add a variant) that returns the `TimestampedValue` (not just the bare `Value`), or expose a `is_fresh`/`get_no_older_than` helper, so downstream consumers can enforce their own maximum-age policy rather than silently trusting the aggregate.
- Document clearly in the pallet's rustdoc that consumers MUST check timestamp freshness themselves via `DataProviderExtended`/`Values` storage before using data for value-sensitive logic, mirroring the Chainlink heartbeat-check guidance in the original report.

### Proof of Concept
Not independently reproduced with a Rust integration test; this analysis is based on static code review only. A minimal reproduction would use the pallet's own mock (`substrate/frame/honzon/oracle/src/mock.rs`, `DefaultCombineData<Self, ConstU32<3>, ConstU32<600>>`) to: (1) feed 3 operators to establish a combined `Values` entry, (2) advance `Timestamp` well past `600` (the `ExpiresIn`) without any further feeds, (3) call `ModuleOracle::get(&key)` and observe it still returns the old `TimestampedValue` with no error/None and no staleness indicator — confirming the fallback-to-`prev_value` path never expires the previously stored aggregate. This was not executed against the actual test harness in this session; only the source logic (`combine_data`'s `values.retain(...)` followed by unconditional `return prev_value`) was verified by reading `substrate/frame/honzon/oracle/src/default_combine_data.rs`.
