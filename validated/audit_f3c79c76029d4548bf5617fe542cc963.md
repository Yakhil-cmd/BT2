### Title
Push-sweep records findings keyed only by `(filePath, category)`, letting a same-category-different-vulnerability follow-up bypass future warnings - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_push_sweep_posttooluse` records reported findings into the shared `previous_findings` state using only `(filePath, category)` as the identity key, instead of the content-based `(filePath, vulnerableCode)` key that the rest of the pipeline documents as the intended dedup granularity. Because `_dedup_against_state` consults `previous_findings` (via `_finding_keys`) to decide whether a finding was "already prompted," a second, genuinely different and more dangerous vulnerability of the same category in the same file introduced by a later push can be silently classified as a duplicate and dropped from `new_vulns`, so no warning fires and `sys.exit(2)` (the blocking/rewake path) never triggers.

### Finding Description
`handle_push_sweep_posttooluse` reviews the pushed commit range, computes `vulns`, and de-dupes them against `previous_findings`: [1](#0-0) 

When findings are reported, only the top `PUSH_SWEEP_REPORT_CAP` are written back into `previous_findings`, and the record function builds its own dedup seen-set purely from `(filePath, category)`: [2](#0-1) 

This is coarser than the content-based identity the surrounding design assumes elsewhere in the plugin, where the module-level comment explicitly documents that dedup is meant to be `(filePath, vulnerableCode)`-based so that only exact repeats are suppressed and code changes (regressions/new bugs) are not masked: [3](#0-2) 

Because `previous_findings` is the same structure fed into `_dedup_against_state` for every subsequent commit-review, push-sweep, and Stop-hook fire (through `_finding_keys(previous_findings)`), once one finding of category `X` in file `F` has been reported and recorded, any later — even unrelated and more severe — vulnerability of category `X` in the same file `F` will match the coarse key and be treated as already-prompted. This causes `new_vulns` to come back empty (or missing that entry) on the next push, so `handle_push_sweep_posttooluse` takes the `if not new_vulns: sys.exit(0)` no-warning path: [4](#0-3) 

The attacker fully controls the diff content and file path/category pairing through ordinary edits and commits (push-sweep is driven purely by `git push` output and diff content, both attacker-influenced in a normal development workflow). No approval, rate-limit, or content check re-validates that a "same category, same file" finding is truly identical — the check is purely categorical, not content-based, which breaks the invariant that dangerous edits must remain reviewable/blockable across retries and pushes.

### Impact Explanation
This allows an attacker (or a compromised agent operating under normal commit/push flow) to "vaccinate" a file against future push-sweep warnings: first push a low-severity or already-fixed finding of a given category in a file, get it reported and recorded, then push a genuinely dangerous change (e.g., a new command-injection or path-traversal introduction) of the *same category* in the *same file* — this second, dangerous change is silently dropped from `new_vulns` and never surfaces via the asyncRewake/guidance banner or `sys.exit(2)` block. This directly enables unauthorized local command execution / dangerous code changes to escape Claude Code's approval and review controls, matching the "Unauthorized local command execution that bypasses Claude Code approval or deny controls" impact category.

### Likelihood Explanation
The precondition is realistic and cheap to trigger: any two pushes touching the same file with findings sharing a `category` string (categories are broad buckets like "Command Injection", "SQL Injection", etc., not per-line identifiers) will collide. No special privileges are needed beyond normal repository write/push access, which is exactly the attacker model in scope (ordinary edits/commits/pushes). The bug is deterministic given the code path shown, not probabilistic, making it highly repeatable.

### Recommendation
Change the push-sweep `_record` seen-set (and any equivalent recording in commit-review) to key on the same content-based identity documented as the design intent — `(filePath, vulnerableCode)` or an equivalent hash of the vulnerable snippet — rather than `(filePath, category)`. Ensure `_finding_keys`/`_dedup_against_state` and the `_record` closure in `handle_push_sweep_posttooluse` use one consistent, content-sensitive key so that a new, distinct vulnerability in a previously-flagged file/category is never conflated with the earlier, already-reviewed finding.

### Proof of Concept
Integration test plan against `handle_push_sweep_posttooluse`:
1. Set up a repo, mock `HAS_API_CREDENTIALS`/`ENABLE_CODE_SECURITY_REVIEW` on, and stub `_agentic_review_with_race`/`analyze_code_security` to return controllable `vulns` lists.
2. First push: commit a file `app.py` introducing a low-severity finding `{"filePath": "app.py", "category": "Command Injection", "vulnerableCode": "os.system(cmd1)"}`. Drive `handle_push_sweep_posttooluse` with a crafted `tool_response` containing valid `git push` range output so it passes the HEAD/range guards. Assert the finding is reported (`sys.exit(2)`) and `previous_findings` in session state now contains `{"filePath": "app.py", "category": "Command Injection", ...}`.
3. Second push: commit a new, unrelated, more dangerous line in the same file, e.g. `{"filePath": "app.py", "category": "Command Injection", "vulnerableCode": "subprocess.run(user_input, shell=True)"}` (different `vulnerableCode`, same file+category). Drive `handle_push_sweep_posttooluse` again with the same session/state.
4. Assert (failing expectation exposing the bug): `_dedup_against_state` returns this second finding as deduped/dropped, `new_vulns` is empty, and the hook exits with `sys.exit(0)` — i.e., no warning/rewake is emitted for the second, genuinely new dangerous code — even though `vulnerableCode` differs from the first recorded finding.
5. Expected correct behavior after fix: the second finding should NOT be deduped (distinct `vulnerableCode`), and the hook should emit guidance and `sys.exit(2)`.
