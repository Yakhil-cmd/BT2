### Title
Webhook signature is verified against the org derived from an unverified payload field, allowing cross-organization event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC validation based on `repository_owner`, a value read directly out of the still-unauthenticated JSON body [1](#0-0) . The `repository_owner` field is derived independently from the `repository`/`organization` sub-object [2](#0-1) , while the event handlers that actually act on the request (e.g. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) consume the full `params` hash, including `repository.full_name`, which is not required to be consistent with `repository.owner.login` [3](#0-2) .

### Finding Description
Shipit supports multiple GitHub organizations, each with its own `webhook_secret`, resolved via `Shipit.github(organization: repository_owner)` [4](#0-3) . The signature check is:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` is picked from the same untrusted, unverified JSON body being validated (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), i.e., the attacker chooses which organization's secret is used to check their own forged signature [2](#0-1) .

If an attacker legitimately controls (or has installed the Shipit GitHub App integration for) any organization tracked by this Shipit instance, they know that organization's `webhook_secret` and can compute a valid `X-Hub-Signature` for an arbitrary raw payload. Because the field used to select the verification secret (`repository.owner.login`) is not cryptographically bound to the rest of the payload beyond being part of the same raw body, the attacker can craft a single JSON body where:
- `repository.owner.login` (and/or `organization.login`) = the attacker's own org (so `verify_webhook_signature` uses the attacker's known secret and succeeds), while
- `repository.full_name`, `sha`, `branches`, or other event-processing fields reference a **different**, victim organization's repository/stack that also happens to be hosted on the same Shipit instance.

This breaks the intended binding: *the organization whose secret authenticated the request* must equal *the repository the event handlers actually act upon*. Since `verify_signature` only checks the raw body against a secret chosen from attacker-controlled data, and the downstream handlers (`Handlers::PushHandler`, `Handlers::StatusHandler`, `Handlers::CheckSuiteHandler`, etc.) locate a `Stack`/`Repository` from the `repository.full_name` field independently of `repository_owner` [5](#0-4) , the two values can diverge, letting the attacker's validly-signed webhook drive state changes for a repository they don't own (e.g. `push` triggering `GithubSyncJob` which fetches/appends commits for the victim `Stack`, or `status`/`check_suite` events forging CI results that unlock deploys/merges) [6](#0-5) .

### Impact Explanation
This crosses the "Critical - cross-repository writes / unauthorized deploy" bar: a webhook forged with a valid signature (using the attacker's own org secret) can inject fabricated commits, CI statuses, or check-run results into an arbitrary victim stack tracked by the same Shipit instance, potentially enabling an unauthorized deploy or merge through the merge queue (`status`/`check_suite` handlers feed `MergeRequest#all_status_checks_passed?`, which gates `merge!`) [7](#0-6) .

### Likelihood Explanation
Exploitation requires the attacker to control at least one organization/repository already integrated with the target Shipit deployment (so they legitimately know that org's `webhook_secret`), and requires that Shipit deployment to track multiple organizations with independently configured secrets. This is a realistic scenario for any shared/multi-tenant Shipit instance (the documented common deployment model), but is not exploitable against a single-org Shipit instance where all repos share one webhook_secret.

### Recommendation
Verify the webhook signature using a secret resolved from a value the engine independently trusts and that must be immutable for the request (e.g., verify against every configured `webhook_secret` and only accept the request if verification succeeds AND the authenticated org matches the org of the resource the handlers subsequently act on), or reject the request if `repository.owner.login`/`organization.login` don't match the resolved `Repository`/`Stack`'s known owner before executing handlers. At minimum, re-validate that `repository_owner` used for secret selection equals the actual owner of the `repository.full_name` referenced by the payload before dispatching to handlers.

### Proof of Concept
1. Attacker controls org `attacker-org`, whose Shipit `webhook_secret` is `S_attacker` (known to them since they installed/configured the GitHub App).
2. Attacker crafts a `push` payload body:
```json
{
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "after": "<attacker-chosen sha>",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, raw_body)>` and posts to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using `S_attacker`.
5. `create` then dispatches `params` (containing `repository.full_name = "victim-org/victim-repo"`) to `Handlers::PushHandler`, which enqueues a `GithubSyncJob` for the victim stack — as demonstrated structurally by the existing test asserting `GithubSyncJob` is enqueued from `params["repository"]["full_name"]` in the push payload [8](#0-7) .

Note: I was unable to directly inspect `Handlers::PushHandler`'s lookup logic (excluded from indexed context) or the exact `Shipit.github` organization-config resolution code in `lib/shipit.rb` beyond confirming its existence, so the precise mechanics of stack lookup by `repository.full_name` should be independently confirmed by a Devin session with full repository access before treating this as fully proven.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

        merge_message,

      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
