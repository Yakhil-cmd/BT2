### Title
Webhook signature verified against `repository.owner.login`, but stack resolution keyed on unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The oracle bug in the report is a "trust the input without checking it is consistent with what was actually verified" pattern. In this engine's `/webhooks` endpoint, the HMAC signature is verified using a secret selected by one field of the JSON body (`repository.owner.login`), while the handler that actually mutates state (creates/syncs a `Stack`) selects its target using a *different* field of the same body (`repository.full_name`), with no cross-check that the two agree.

### Finding Description
`WebhooksController#verify_signature` picks the `GithubApp` (and thus the webhook secret used for HMAC verification) based on `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit::GithubApp#verify_webhook_signature` performs a straightforward HMAC-SHA1 comparison against `webhook_secret`, which is configured per organization (Shipit explicitly supports multiple orgs, each with its own `webhook_secret`): [3](#0-2) [4](#0-3) 

Once the signature passes, `WebhooksController#create` dispatches the entire raw JSON body to the event handlers: [5](#0-4) 

`Shipit::Webhooks::Handlers::Handler` (the base class used by `PushHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves the target `Stack`/`Repository` using a *different* field: `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

`PushHandler` then uses that resolution to sync a real stack against an attacker-supplied `after` sha: [7](#0-6) 

The binding that should hold is:
`organization whose secret validated the signature == organization that owns the repository the handler acts on`

Nothing in the code enforces `repository.full_name.split('/').first == repository_owner`. Both fields live inside the *same* signed byte string, but the signature only proves "this body was signed by whoever holds the secret for `repository_owner`" — it says nothing about whether `repository.full_name` is consistent with that owner. An attacker who legitimately controls a GitHub App/organization "attacker-org" registered in this same multi-tenant Shipit instance (and therefore knows or can obtain a valid webhook delivery/secret for "attacker-org") can hand-craft an arbitrary JSON body — never actually sent by GitHub — with:
- `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")` is selected and the attacker's own known secret validates the HMAC)
- `repository.full_name = "victim-org/victim-repo"` (an unrelated repository registered as a `Stack` in the same Shipit instance)

and POST it directly to the public, unauthenticated `/webhooks` endpoint.

### Impact Explanation
Because verification and resolution key off different fields of the attacker-controlled body, the attacker gains the ability to make Shipit believe a push happened against `victim-org/victim-repo` while only proving control of `attacker-org`'s secret. `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` for the victim's `Stack`, injecting an attacker-chosen `after` sha into the victim stack's commit-sync/continuous-delivery pipeline. This is a cross-tenant boundary violation: an action authenticated as belonging to organization A is applied to organization B's repository/stack — i.e., a cross-repository write into an org the attacker does not control, without ever proving possession of that org's real GitHub webhook secret or having write access to that repository. Other handlers keyed the same way (`CheckSuiteHandler`, PR handlers via `Repository.from_github_repo_name(params.repository.full_name)`) are similarly reachable, extending the same confusion to check-run refresh and review-stack archive/unarchive/provisioning flows for a repository outside the attacker's authenticated organization.

### Likelihood Explanation
Exploitability requires the attacker to operate their own GitHub organization/App installation that is *also* configured in the same multi-tenant Shipit deployment (a documented, supported configuration in `secrets.yml`), which is a realistic scenario for shared/self-hosted Shipit instances serving multiple orgs. No GitHub write access to the victim repository, no `ApiClient` token, and no session are required — only the ability to compute an HMAC with a secret the attacker legitimately possesses for their own org, and knowledge/enumeration of a victim `full_name` that is registered as a Stack.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after signature verification, assert that the organization used to select the secret matches the organization embedded in `repository.full_name` (and `organization.login`/`sender.login` where relevant) before dispatching to handlers. Reject the webhook if the owner used for secret selection does not match the owning org of the repository the handler is about to act on.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `attacker-org` (attacker controls this GitHub App/webhook secret) and `victim-org` (has a `Stack` registered for `victim-org/victim-repo`), per the multi-org `secrets.yml` format shown in `config/secrets.development.example.yml:18-38`.
2. Craft JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known webhook secret over the exact raw body.
4. `POST /webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` from `repository.owner.login`, verifies successfully with the attacker's own secret (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `PushHandler` resolves the target via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's real `Stack` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the signature only proved control of `attacker-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
