### Title
Unsanitized release asset `Name` enables path traversal via `filepath.Join` in `makePath` - ([File: pkg/cmd/release/download/download.go])

### Summary
`downloadAsset`/`destinationWriter.makePath` build the destination path with `filepath.Join(w.dir, name)` using the asset's `Name` field taken directly from the release API response, with no validation that it is a single path element free of `..` or separators. If a malicious/attacker-controlled API host (e.g., a GHES-style host the victim points `gh` at) returns an asset with a `Name` like `../../.bashrc`, `filepath.Join` will clean the traversal and can place the written file outside `w.dir`.

### Finding Description
- `downloadRun` (download.go:196-207) iterates `release.Assets` and, for each asset matching `--pattern` (or all assets if no pattern), builds a `downloadTarget{url, name: a.Name}` (download.go:238-243) with `a.Name` coming verbatim from the parsed API response (`shared.ReleaseAsset`), with no character/format restriction applied by the CLI.
- `downloadAsset` calls `dest.Check(fileName)` and `dest.Copy(fileName, ...)` (download.go:300-350), both of which resolve the write location via `makePath`:
  ```go
  func (w destinationWriter) makePath(name string) string {
      if w.file == "" {
          return filepath.Join(w.dir, name)
      }
      return w.file
  }
  ``` [1](#0-0) 
- `filepath.Join` calls `filepath.Clean`, which resolves `..` segments syntactically. If `name` contains enough `../` components (e.g., `../../../home/victim/.ssh/authorized_keys`), the resulting path can escape `w.dir` entirely, and `Copy` will `MkdirAll` the parent directory and write attacker-supplied bytes there (download.go:435-452).
- The only filename hardening present is `isWindowsReservedFilename` (checked only on Windows, and only blocks reserved DOS device names, not traversal) and `filepath.Base` applied solely to a Content-Disposition-derived name for archive downloads (download.go:344) — this sanitization is not applied to normal asset names sourced from `release.Assets`.
- Regarding `matchAny` (download.go:248-255): `filepath.Match(p, name)` treats `name` as a literal string to compare against the glob `pattern` — glob metacharacters embedded in `name` (`*`, `?`, `[`) have no special meaning there; only characters in `p` (the victim-supplied `--pattern`) are interpreted as glob syntax. Additionally, `filepath.Match` splits both pattern and name on path separators and requires equal segment counts, so a `name` containing `/` cannot be spuriously matched by a separator-free pattern like `*.deb`. This part of the question is not exploitable — there is no fail-open/mismatch behavior induced by attacker-chosen glob metacharacters in `name`.

### Impact Explanation
This matches GitHub's "file write outside the intended path" impact class. A hostile release API response (attacker controls the GHES/API host the victim's `gh` is configured against, per the threat model) can cause `gh release download` to write attacker-controlled file contents to an arbitrary path reachable from `w.dir` via `..` traversal, subject to OS file permissions of the invoking user — e.g., overwriting dotfiles, shell profile files, or SSH `authorized_keys`, which can lead to further code execution or persistence on the victim's machine.

### Likelihood Explanation
Requires the victim to run `gh release download` against a release whose API response is served by an attacker-controlled or attacker-manipulated host (consistent with the stated threat model of "a host the victim points gh at"). No token/social engineering needed beyond the victim invoking the download command; the traversal is deterministic given a crafted asset name and is trivially repeatable.

### Recommendation
Reject or sanitize asset names before constructing the destination path: verify `name == filepath.Base(name)` (or equivalently reject any name containing `/`, `\`, or resolving outside `w.dir` after `filepath.Clean`/`filepath.Abs`) in `makePath`/`downloadAsset`, returning an error for any asset name that is not a plain filename. Additionally, after computing `fp := filepath.Join(w.dir, name)`, assert `strings.HasPrefix(filepath.Clean(fp)+string(os.PathSeparator), filepath.Clean(w.dir)+string(os.PathSeparator))` before writing.

### Proof of Concept
```go
func TestMakePathTraversal(t *testing.T) {
    dir := t.TempDir()
    w := destinationWriter{dir: dir}
    // Simulates a malicious asset Name from an attacker-controlled API response
    fp := w.makePath("../../etc/evil-cron")
    absDir, _ := filepath.Abs(dir)
    absFp, _ := filepath.Abs(fp)
    if !strings.HasPrefix(absFp, absDir) {
        t.Fatalf("path escaped destination dir: dir=%s resolved=%s", absDir, absFp)
    }
}
```
Fuzz plan: generate asset names containing `../`, absolute paths (`/etc/x`), and mixed separators; for each, call `downloadAsset`/`Copy` against an httpmock server returning that asset name, and assert the written file's absolute path always has `filepath.Clean(w.dir)` as a prefix. Expect the current implementation to fail this assertion for names like `../secret`.

Note on `matchAny`: no PoC is provided because analysis shows `filepath.Match`'s segment-based matching prevents glob metacharacters embedded in `name` from causing spurious matches against a separator-free `--pattern`; this sub-question is not exploitable.
