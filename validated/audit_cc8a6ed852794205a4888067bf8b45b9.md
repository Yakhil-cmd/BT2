### Title
Webhook signature verification is silently bypassed when `webhook_secret` is unset, allowing unauthenticated forged GitHub events - (File: lib/shipit/github_app.rb, app/controllers/shipit/webhooks_controller.rb)

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for an organization, instead of rejecting the request. Because `webhook_secret` is a documented **optional** setting, any Shipit deployment (single-org or multi-org) that leaves it blank accepts arbitrarily forged webhook payloads with no HMAC check at all. This breaks the binding "request accepted ⇔ HMAC(secret, raw_body) matches `X-Hub-Signature`" the same way `NonUSTStrategy` broke the binding "shares issued ⇔ depositor pays the swap fee": a check that is supposed to gate the operation is skipped, and any unprivileged caller reaps the benefit at the expense of the system's trust model.

### Finding Description
`WebhooksController#verify_signature` selects an organization-scoped `GitHubApp` from the untrusted payload and asks it to verify the signature: [1](#0-0) 

The verification itself is: [2](#0-1) 

`return true unless webhook_secret` means: if the operator never configured `github.webhook_secret` (or `github.<org>.webhook_secret`), **every** POST to `/webhooks`, regardless of the `X-Hub-Signature` header (or its absence), is treated as authentic. The docs and example secrets files present this key as optional, with no warning that omitting it disables all authentication of inbound webhooks: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the attacker-controlled JSON straight into the registered handlers with no further authentication: [5](#0-4) 

Several handlers act on trust-sensitive fields taken directly from this payload, e.g. `pull_request` handlers that archive/unarchive review stacks based on `repository.full_name` and label lists: [6](#0-5) [7](#0-6) 

Most notably, the `membership` webhook handler creates local `Team`/`User`/membership records purely from payload data, as shown by its test coverage (the handler is not indexed, but its externally observable behavior is): [8](#0-7) 

Authorization in Shipit is gated on team membership synced this way: [9](#0-8) 

### Impact Explanation
When `webhook_secret` is not set (a supported configuration, not a misconfiguration outside documented behavior), the `/webhooks` endpoint becomes fully unauthenticated. An external, credential-less attacker can:
- Forge `membership` events to add an arbitrary (real) GitHub login into a locally-tracked `Team`, escalating that account into any `Shipit.github_teams` handle used for authorization — matching the explicit High-impact category "escalation into `Shipit.github_teams` authorization".
- Forge `pull_request`/`push`/`status`/`check_suite` events to archive/unarchive review stacks, enqueue sync jobs, or otherwise manipulate stack state that downstream deploy/merge logic relies on.

This is a genuine authentication-bypass of the webhook ingestion pipeline, not a feature request or best-practice note, and requires no session, API token, or `webhook_secret` knowledge from the attacker (the attacker's whole point is that no secret exists to know).

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: an operator must have left `webhook_secret` blank. Since this is explicitly presented as optional in `docs/setup.md` and the example secrets templates (with no adjacent warning that it disables authentication), it is a plausible real-world configuration, especially for internal/self-hosted GitHub Enterprise setups where operators may believe network isolation is sufficient. No GitHub-side control prevents a third party from hitting the publicly routable `/webhooks` endpoint.

### Recommendation
Change `verify_webhook_signature` to fail closed: reject the request (or require `X-Hub-Signature`/`X-Hub-Signature-256` match) whenever `webhook_secret` is blank, rather than treating a missing secret as "always verified." At minimum, make `webhook_secret` mandatory and refuse to boot the engine (or refuse to process webhooks) if it is not configured for an organization that has webhooks enabled.

### Proof of Concept
1. Deploy Shipit with `github.webhook_secret` left blank (as shown to be valid/documented in `config/secrets.development.example.yml`).
2. `POST /webhooks` with header `X-Github-Event: membership` and a crafted JSON body naming an arbitrary real GitHub `login` and a `team` matching (or colliding with) a `Shipit.github_teams` handle.
3. Because `webhook_secret` is `nil`, `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` without checking `X-Hub-Signature`, so `WebhooksController#create` dispatches the forged payload to the `membership` handler, which creates the `Team`/`Membership` records exactly as exercised in `test/controllers/webhooks_controller_test.rb:129-148`.
4. The named user is now a member of a team Shipit trusts for authorization, per `User#authorized?` (`app/models/shipit/user.rb:80-82`), without ever completing GitHub OAuth or possessing any Shipit credential.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
