### Title
Cross-organization webhook signature verification lets an attacker forge CI status / push events for repositories they do not control - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the incoming `X-Hub-Signature` against by reading `repository_owner` out of the *unverified* JSON body, but the downstream handlers act on other, independently attacker-controlled fields of that same body (`repository.full_name`, or in the case of `status` events, a global `sha` lookup with no repository scoping at all). This breaks the intended binding "the organization whose secret authenticated the request == the repository/commit the event is applied to."

### Finding Description
`verify_signature` computes the organization used for HMAC verification purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` picks the `GitHubApp` whose `webhook_secret` will be used by `verify_webhook_signature`: [3](#0-2) [4](#0-3) 

Because Shipit is designed to host multiple GitHub organizations each with its own `webhook_secret` (see `github_app_config`/`github_organizations`), any GitHub organization admin who legitimately owns a webhook secret for **one** org configured in this Shipit instance can compute a valid `X-Hub-Signature` for a JSON body whose `repository.owner.login` matches their own org (so the correct secret is selected and the signature verifies), while every other field of the same payload — including `repository.full_name`, `sha`, `ref`, etc. — is completely attacker-controlled and can reference a *different* organization's repository/commit.

Downstream handlers do not re-validate that the acted-upon repository matches the verified organization:
- `Handler#stacks`/`#repository_name` trust `payload.dig('repository', 'full_name')` verbatim, independent of the `owner.login` used for signature selection: [5](#0-4) 
- `StatusHandler#process` doesn't even scope by repository — it matches commits **globally by `sha` across the entire Shipit instance** and writes a GitHub-reported CI status onto them: [6](#0-5) 
- `PushHandler#process` resolves stacks via `repository_name` (attacker-supplied `full_name`) and enqueues a sync against that stack with an attacker-chosen `expected_head_sha`: [7](#0-6) 

The equality that should hold but is broken:
`organization_whose_secret_verified_the_signature == organization/repository_that_the_handler_mutates`

Before the attack: signature-verification org and acted-upon repository are the same org, as GitHub itself guarantees for real webhooks.
After the attacker's crafted request: the signature-verification org (`repository.owner.login`) is the attacker's own org (or any org whose secret they know), while the acted-upon repository/commit (`repository.full_name`, `sha`) is a victim's, decoupling the two.

### Impact Explanation
This allows cross-repository writes without any prior Shipit session, `ApiClient` token, or repository write access to the victim repo — only knowledge of a webhook secret for *any* organization configured on the same Shipit instance (which the attacker legitimately has for their own org). Concretely:
- Forge a `status` event for any commit sha tracked anywhere in the Shipit instance, marking arbitrary commits in unrelated repositories as CI `success`, which `Commit#create_status_from_github!` persists and which Shipit's deploy-gating logic (`Stack`/`CommitChecks`/`Status::Group`) consults to decide whether a commit is deployable.
- Forge a `push` event referencing a victim `repository.full_name`/branch to trigger `GithubSyncJob`/`stack.sync_github` against that stack.

Faking a green CI status on a target commit can enable an unauthorized deploy of that commit if Shipit's UI/API otherwise treats it as ready-to-ship, which matches the "unauthorized deploy" Critical-impact category.

### Likelihood Explanation
Exploitability requires only:
1. Knowledge of one organization's `webhook_secret` in a multi-organization Shipit deployment (an unprivileged attacker relative to the *victim* org/repo — they never touch the victim's secret, token, or GitHub permissions).
2. Ability to send an arbitrary HTTP POST to the public `WebhooksController#create` endpoint with a self-computed signature.

No GitHub webhook delivery is actually required — the attacker directly POSTs a crafted JSON body plus a correctly-computed `X-Hub-Signature` header for the org they legitimately administer.

### Recommendation
After signature verification succeeds, re-derive and enforce that the repository/commit acted upon actually belongs to the organization whose secret validated the signature (e.g., verify `repository.full_name` starts with `#{repository_owner}/`, and scope `StatusHandler#process`'s commit lookup by the stack's repository rather than a bare global `sha` match). Alternatively, verify the signature per-repository (using the `Repository`/`Stack`'s own registered organization) rather than trusting an unauthenticated `repository_owner` value to select the verification secret.

### Proof of Concept
1. Attacker administers `org-attacker`, a GitHub organization onboarded to this Shipit instance, and therefore knows `webhook_secret` for `org-attacker` (`Shipit.github(organization: 'org-attacker').webhook_secret`).
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<victim-commit-sha-tracked-by-shipit>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_of_org_attacker, raw_body)`.
4. POST to `/github/webhooks` (or configured webhook route) with `X-Github-Event: status`.
5. `verify_signature` selects `org-attacker`'s app via `repository_owner` = `"org-attacker"`, verifies successfully, and `StatusHandler#process` writes a fabricated "success" status onto the victim commit, regardless of the mismatched `full_name`. [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
