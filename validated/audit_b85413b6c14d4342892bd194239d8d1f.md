### Title
Webhook Signature Verified Against a Different Organization Than the Repository Acted Upon — Cross-Organization Webhook Forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate an incoming webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body. Every downstream handler, however, resolves the target `Stack`/`Repository` using `repository.full_name` from that same unverified body. Because both fields are attacker-controlled prior to signature validation, they are not required to agree, allowing a webhook "authenticated" against one organization's (lax or known) secret to be dispatched as if it came from a completely different organization's repository.

### Finding Description
`verify_signature` picks the app config purely from payload content, before the signature has been checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization** config (`app_id`, `installation_id`, `webhook_secret`, `private_key`) as shown by the multi-org fixture: [3](#0-2) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when the selected organization has no `webhook_secret` configured: [4](#0-3) 

Once the (possibly no-op) signature check passes, the webhook is dispatched to handlers, which resolve the target stack from `repository.full_name` — a **different** field of the same unverified payload: [5](#0-4) 

**Binding broken:** `authenticating_organization` (derived from `repository.owner.login`, used to pick the verification secret) is implicitly assumed to equal `acted_upon_repository_owner` (derived from `repository.full_name`, used to locate the `Stack`/`Repository` that the handler mutates). Nothing enforces this equality before verification, and both values come from the same untrusted, not-yet-verified JSON body.

### Impact Explanation
In a multi-organization Shipit deployment (a documented, supported configuration — see `secrets_double_github_app.yml`), an attacker who can produce a validly-signed (or unsigned, if `webhook_secret` is blank for one org) payload for *any one* configured organization can set `repository.owner.login` to that lax/known organization while setting `repository.full_name` to `victim-org/target-repo`. The forged webhook is accepted (`head(:ok)`), then dispatched to handlers that:
- Enqueue `GithubSyncJob` for the victim stack on `push` events, forging commits/branch state.
- Create/modify `Status` on victim commits, which feeds `Commit#deployable?` and can unblock or trigger continuous deployment (`Stack.schedule_continuous_delivery` → unauthorized deploy).
- Create/delete `Team`/`Membership` records via the `membership` handler, potentially escalating into `Shipit.github_teams` authorization used by `User#authorized?`.

This satisfies the Critical/High bar: unauthorized deploy triggering and escalation into `Shipit.github_teams` authorization, achieved purely by crafting a webhook payload — no repository write access, GitHub App key, or `ApiClient` token required.

### Likelihood Explanation
Requires the Shipit instance to be configured for more than one GitHub organization (a documented feature, not a misconfiguration of the "host app not mounting the engine" variety) where at least one configured organization either has no `webhook_secret` or one the attacker can obtain (e.g., their own org onboarded to the same Shipit instance). Given webhook endpoints are unauthenticated by design (that's the entire point of HMAC verification), and the org-selection/full_name fields are two independent, attacker-controlled JSON keys, this is straightforward to exploit once the multi-org condition holds.

### Recommendation
After selecting the signing organization and verifying the HMAC, re-derive `repository.owner.login`/`organization.login` from the verified payload and assert it matches the organization actually resolved for `repository.full_name` before handing off to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Alternatively, bind webhook signature verification to the `Repository`/`Stack`'s own configured organization (looked up from the DB) rather than trusting the unverified payload to choose which secret to check against, and require a non-blank `webhook_secret` for every configured organization (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
1. Configure Shipit with two organizations, `OrgB` (attacker-controlled GitHub App installation, `webhook_secret` blank or known) and `OrgA` (victim org hosting a tracked stack `OrgA/victim-repo`), per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends:
```
POST /github_hooks
X-Github-Event: push
X-Hub-Signature: sha1=<anything, or valid for OrgB>
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgB")` and, since `OrgB.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally [6](#0-5) .
4. The `push` handler resolves `Repository.from_github_repo_name("OrgA/victim-repo")` [5](#0-4)  and enqueues `GithubSyncJob` for the victim stack, even though the request was never validated against `OrgA`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
