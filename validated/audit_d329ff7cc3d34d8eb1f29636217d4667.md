### Title
Webhook signature verification key is selected from an unsigned, attacker-controlled field decoupled from the field used to identify the target repository, allowing cross-tenant PullRequest mutation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, while `EditedHandler#repository` (and all sibling pull-request handlers) subsequently resolves the record to mutate using the independent `repository.full_name` field from the same unverified body. Because these two fields are never cross-checked, an attacker can set `repository.owner.login` to an org that has no `webhook_secret` configured (which `GitHubApp#verify_webhook_signature` trivially accepts) while setting `repository.full_name` to a victim org/repo, causing the handler to update a victim `Shipit::PullRequest` row using entirely attacker-supplied data.

### Finding Description
The broken binding: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` succeeding should imply `repository_owner == owner(params.repository.full_name)`, but the code never enforces this equality.

- `WebhooksController#verify_signature` picks the verification config from `repository_owner`, defined as `params.dig('repository','owner','login') || params.dig('organization','login')`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally, without checking the supplied signature at all, whenever the selected org's `webhook_secret` is blank: [3](#0-2) 
- After the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the whole (still attacker-controlled) body to handlers such as `EditedHandler`: [4](#0-3) 
- `EditedHandler#repository` resolves the target repository from `params.repository.full_name` — a completely separate JSON field from the one used above for signature selection: [5](#0-4) 
- `EditedHandler#process` then looks up the `PullRequest` by `number` scoped to that repository and overwrites its GitHub-derived attributes (`github_id`, `number`, `api_url`, `title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, `head`) straight from the unsigned payload: [6](#0-5) [7](#0-6) 

Exploit: An attacker sends `POST /webhooks` with header `X-Github-Event: pull_request` and a JSON body where `repository.owner.login` (or top-level `organization.login`) is set to any org configured in Shipit's multi-org `secrets.github` map that has no `webhook_secret` set (a state explicitly shown as the default in the shipped config templates, e.g. `webhook_secret: # nil`), while `repository.full_name` is set to `"victim-org/victim-repo"` and `number` is set to a real victim PR number. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, which returns `true` regardless of the (even absent/garbage) `X-Hub-Signature` header because `webhook_secret` is blank for that org. `EditedHandler` then resolves and updates the victim's `PullRequest` row using the attacker's payload.

Existing guards do not stop this: `drop_unhandled_event` only checks event type, `ExplicitParameters` schema in `EditedHandler.params` only validates shape/types (not cross-field consistency between `repository.owner.login` and `repository.full_name` — note the schema doesn't even require `repository.owner`, only `repository.full_name`), and there is no code anywhere comparing the org used for verification against the org embedded in `full_name`.

Note: the question's claim that `changes.base`/base-branch metadata is updated is not supported by the code — `PullRequest#github_pull_request=` does not read or persist any `base` field at all [7](#0-6) , so no base-branch-driven deploy/merge mistargeting is possible through this handler. The actually demonstrable impact is limited to overwriting the victim PR's `title`, `state`, `additions`, `deletions`, `assignees`, `labels`, and `head` (commit) — the latter of which triggers `find_or_create_commit_from_github_by_sha!`, an unauthenticated cross-tenant commit-record write for the victim's stack.

### Impact Explanation
An unprivileged, secret-less attacker can force writes into a victim organization's `Shipit::PullRequest` record (and indirectly create/attach `Shipit::Commit` rows to the victim's stack via the forged `head.sha`), entirely bypassing the intent of per-organization webhook signing. This matches the explicitly listed Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any repository/PR number that the attacker can guess or observe (PR numbers are public on GitHub), and against any tenant stack hosted on the same Shipit instance, as long as at least one org in the multi-org config lacks a `webhook_secret`. Blast radius spans all tenants sharing the Shipit installation, not just the misconfigured org's own repos.

### Likelihood Explanation
Requires: (1) Shipit deployed in the multi-org `github:` config mode (`github_default_organization` non-nil), and (2) at least one configured org entry with a blank/absent `webhook_secret`. The shipped example configs (`config/secrets.development.example.yml`, `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`) all show `webhook_secret: # nil` as a plausible/default state, so this is a realistic, low-effort misconfiguration rather than a purely theoretical one. Given that precondition, attacker cost is a single unauthenticated HTTP POST with no secrets, tokens, or sessions required, and the attack is fully repeatable and scriptable against arbitrary victim repos/PRs already tracked by Shipit.

### Recommendation
In `WebhooksController#verify_signature`, derive the org used for signature verification and reject the request if it doesn't match the owner embedded in `params['repository']['full_name']` (or `params['organization']['login']` consistently). Additionally, do not treat a blank `webhook_secret` as an automatic pass in `GitHubApp#verify_webhook_signature`; require explicit opt-in (e.g., a dedicated `insecure_webhooks: true` flag) rather than silently trusting unsigned traffic. As defense in depth, have each `Handler` (e.g. `EditedHandler`) assert that the resolved `Repository#owner` matches the org that passed signature verification before mutating any record.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_org_test.rb
require 'test_helper'

module Shipit
  class WebhooksCrossOrgTest < ActionController::TestCase
    tests Shipit::WebhooksController

    setup do
      # multi-org config: "attacker-org" has NO webhook_secret; "victim-org" does.
      Shipit.stubs(:github_default_organization).returns('attacker-org')
      Shipit.stubs(:github_app_config).with('attacker-org').returns({}) # no webhook_secret
      victim_repo = shipit_repositories(:shipit) # owner: 'shopify', name: 'shipit-engine' (example)
      victim_pr = shipit_pull_requests(:review_stack_review)

      @victim_owner  = victim_repo.owner
      @victim_repo   = victim_repo
      @victim_pr     = victim_pr
    end

    test "attacker org with no webhook_secret cannot mutate victim org's PullRequest" do
      payload = {
        action: 'edited',
        number: @victim_pr.number,
        pull_request: @victim_pr.github_pull_request_payload_hash.merge(title: 'PWNED BY ATTACKER'),
        repository: { owner: { login: 'attacker-org' }, full_name: @victim_repo.full_name },
        sender: { login: 'attacker' }
      }.to_json

      @request.headers['X-Github-Event'] = 'pull_request'
      @request.headers['X-Hub-Signature'] = 'sha1=garbage' # no valid secret known

      assert_no_changes -> { @victim_pr.reload.title } do
        post :create, body: payload, as: :json
      end
      assert_response :unprocessable_entity
    end
  end
end
```
Before the fix: `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `attacker-org` (`lib/shipit/github_app.rb:76-83`); `EditedHandler` then resolves `victim-org/victim-repo` via `params.repository.full_name` and updates `@victim_pr.title` to `"PWNED BY ATTACKER"`, so `assert_no_changes` fails and the response is `200 OK`, demonstrating the cross-tenant mutation. After applying the recommended fix (rejecting mismatched owner vs. full_name, or refusing to trust blank secrets), the request is rejected with `422` and `@victim_pr.title` remains unchanged.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
