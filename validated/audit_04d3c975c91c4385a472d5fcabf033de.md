### Title
Encrypted-transaction ciphertext-to-sender binding is not enforced at mempool/VM admission, only at REST submission - ([File: types/src/transaction/encrypted_payload.rs])

### Summary
Aptos's new `EncryptedPayload` transaction type binds a ciphertext to a specific `(sender, signer_auth_keys)` pair via `PayloadAssociatedData`, and this binding is only checked by `EncryptedPayload::verify()`. I traced every call site of this function and found it is invoked only from the REST submission handler (`api/src/transactions.rs::validate_signed_transaction_payload`) and from consensus batch verification for peer-supplied batches (`consensus/consensus-types/src/common.rs::verify_batch_kind_transactions`). Neither `vm-validator` (used for mempool's own transaction admission) nor the Move prologue (`transaction_validation.move`) nor `EncryptedPayload::try_into_decrypted` re-check this binding.

### Finding Description
`EncryptedPayload::verify()` is the only function that ties an encrypted ciphertext to the `sender` address and the set of `signer_auth_keys` that are allowed to submit/decrypt it: [1](#0-0) 

The commitment enforced during actual decryption (`try_into_decrypted`) only checks that `payload_hash == CryptoHash::hash(&plaintext)` and, optionally, a `claimed_entry_fun` — it never re-validates the `(sender, signer_auth_keys)` binding that `PayloadAssociatedData` was designed to protect: [2](#0-1) 

Signature verification (`TransactionAuthenticator::verify`) also does not check this binding — it only verifies signatures over the *encrypted* (pre-decryption) variant of the raw transaction via `as_encrypted_variant()`, which is agnostic to whether the ciphertext's baked-in associated data matches the transaction's actual `sender`/signer set: [3](#0-2) [4](#0-3) 

I confirmed the only two call sites of `EncryptedPayload::verify()` in the entire codebase:
1. The REST submission handler, gated behind `allow_encrypted_txns_submission`, which is only reached when a client posts directly via `/transactions`: [5](#0-4) 
2. Consensus's `verify_batch_kind_transactions`, which validates batches for `BatchKind::Encrypted` — but this is called when validating remotely-received quorum-store batches, not when a validator's own `BatchGenerator` pulls transactions out of local mempool to build a batch (per `consensus/src/quorum_store/README.md`, `BatchGenerator` "Pulls transactions from mempool... Persists the batch to local DB... Broadcasts BatchMsg" with no verification step listed): [6](#0-5) 

Crucially, `grep` across `vm-validator/` (the code path used to admit transactions directly into mempool, including via mempool-to-mempool network gossip that bypasses the REST API) shows **no reference at all** to `EncryptedPayload`, `is_encrypted`, or any ciphertext binding check. Mempool's admission relies on `vm_validator::validate_transaction`, which only runs the standard VM prologue (`transaction_validation.move`), and that prologue has no knowledge of `EncryptedPayload` or `PayloadAssociatedData` at all — it only checks the wrapped executable via signature/auth-key/sequence-number/chain-id/expiration, none of which validate the ciphertext-to-sender-set binding.

### Impact Explanation
Because the ciphertext-to-`(sender, signer_auth_keys)` binding is enforced only at the REST ingestion boundary of the *originating* node (and, for foreign batches, only at batch-verification time by receiving validators), any encrypted transaction that reaches a validator's mempool via the peer-to-peer mempool broadcast protocol (rather than through that validator's own `/transactions` endpoint) is admitted without this check. If a validator's own `BatchGenerator` pulls such an unchecked transaction from its local mempool to build a batch, the batch-kind check applied by *other* validators upon receiving the batch is the only remaining guard; if that check were skipped, weakened, or raced by a batch author that has a way to author `Encrypted`-kind batches with ciphertexts whose baked-in associated data does not correspond to the packaged `sender`, decryption would proceed and execute a transaction whose declared `sender`/signer set never matches what was cryptographically committed to when the ciphertext was created — i.e., a wrong-sender/wrong-signer-set admission failure exactly matching the required impact category (transaction execution under the wrong sender or signer set).

### Likelihood Explanation
This requires the encrypted-transaction feature (`FeatureFlag::ENCRYPTED_TRANSACTIONS`) to be enabled and `allow_encrypted_txns_submission` to be set on at least the ingesting node. Likelihood is Medium: the binding gap is real and independently verifiable by tracing call sites, but exploiting it fully depends on how strictly `verify_batch_kind_transactions` is enforced for locally-authored batches (which I was unable to fully verify within available tool budget — I could not locate the `BatchGenerator`/`BatchCoordinator` source to confirm whether local batch creation ever calls this check before broadcasting, or whether it is intentionally skipped because local mempool transactions are assumed pre-validated by the local API). This is a genuine unresolved gap in my analysis.

### Recommendation
Move the `EncryptedPayload::verify()` (ciphertext-to-sender/signer-key binding) check into the VM prologue path (`transaction_validation.move` / `vm-validator`) so that it is enforced uniformly for every transaction admitted into mempool regardless of ingestion path (REST API vs. p2p gossip vs. batch reception), rather than relying solely on the REST handler and remote-batch verification. Alternatively, ensure `BatchGenerator` (or whichever component packages local mempool transactions into `Encrypted`-kind batches) also calls `verify_batch_kind_transactions`/`EncryptedPayload::verify()` before broadcasting, and that `try_into_decrypted` re-validates `PayloadAssociatedData` against the transaction's actual `sender` and signer authentication keys as an additional defense-in-depth check at decryption time.

### Proof of Concept
Not independently reproducible from static analysis alone. A full PoC would require standing up a multi-node testnet with `ENCRYPTED_TRANSACTIONS` enabled, crafting a `SignedTransaction` with a valid signature over `sender = B` but an `EncryptedPayload::Encrypted` ciphertext whose `PayloadAssociatedData` was generated for `sender = A`, injecting it directly into a validator's mempool via the mempool network protocol (bypassing that validator's REST `/transactions` endpoint, e.g. by speaking the mempool gossip protocol directly or via a node with `allow_encrypted_txns_submission = false`), and observing whether it reaches decryption/execution without ever having `EncryptedPayload::verify()` invoked against it. This step was not performed; the finding is based on static call-site tracing showing the absence of the check outside the two identified call sites.

    /// Verify the decrypted plaintext against the stored commitments and, on success,
    /// transition `self` to `Decrypted`. On mismatch, `self` is left as `Encrypted` and the
    /// failure reason is returned so the caller can mark the payload failed.
    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }

    /// TransactionExecutable::Encrypted for signature verification.
    /// This is needed because signatures are verified over the executable, not the encrypted ciphertext.
    pub fn as_encrypted_variant(&self) -> Cow<'_, Self> {
        match &self.payload {
            TransactionPayload::EncryptedPayload(EncryptedPayload::Decrypted {
                original, ..
            })
            | TransactionPayload::EncryptedPayload(EncryptedPayload::FailedDecryption {
                original,
                ..
            }) => Cow::Owned(RawTransaction {
                sender: self.sender,
                sequence_number: self.sequence_number,
                payload: TransactionPayload::EncryptedPayload(EncryptedPayload::Encrypted(
                    original.clone(),
                )),
                max_gas_amount: self.max_gas_amount,
                gas_unit_price: self.gas_unit_price,
                expiration_timestamp_secs: self.expiration_timestamp_secs,
                chain_id: self.chain_id,
            }),
            _ => Cow::Borrowed(self),
        }

pub fn verify_batch_kind_transactions(
    kind: Option<BatchKind>,
    txns: &[SignedTransaction],
) -> anyhow::Result<()> {
    match kind {
        Some(BatchKind::Encrypted) => {
            txns.par_iter()
                .with_min_len(24)
                .try_for_each(|txn| -> anyhow::Result<()> {
                    ensure!(
                        txn.is_encrypted_txn(),
                        "Encrypted batch contains non-encrypted transaction"
                    );
                    let encrypted_payload = txn
                        .payload()
                        .as_encrypted_payload()
                        .expect("already verified is_encrypted_txn");
                    ensure!(
                        encrypted_payload.is_encrypted(),
                        "Encrypted batch contains transaction not in Encrypted state"
                    );
                    ensure!(
                        !encrypted_payload.extra_config().is_multisig(),
                        "Encrypted transactions do not support multisig"
                    );
                    let signer_auth_keys = txn
                        .authenticator()
                        .all_signer_auth_keys(txn.sender())
                        .context(
                        "Encrypted transactions are not supported with this authenticator type",
                    )?;
                    encrypted_payload
                        .verify(txn.sender(), signer_auth_keys)
                        .context("Encrypted transaction ciphertext verification failed")
                })?;
