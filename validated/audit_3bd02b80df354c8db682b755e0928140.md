### Title
Capped AA asset can never be issued once a first issuance unit is voided, freezing all attached funds - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `issueAsset()` helper decides whether an AA is still allowed to issue a capped asset by checking only whether *any* `type='issue'` row for that `asset` already exists in the `inputs` table, with no filter on `sequence` or `is_stable`. This mirrors the Rio bug class: a "queued/consumed" state is recorded once an operation begins, but the code never verifies that the operation actually settled successfully, and there is no mechanism to revert/clear that state if the underlying unit is voided. Any capped asset issuance attempt by an AA that ends up on a `final-bad` unit permanently blocks that asset from ever being issued.

### Finding Description
When an AA response tries to pay out more of a capped asset than it currently holds, `completePaymentPayload` calls `issueAsset()`: [1](#0-0) 

For capped assets, the "already issued" check is:
```
conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
    if (rows.length > 0) // already issued
        return cb2('already issued');
    addIssueInput(1);
});
```
This query has **no** `sequence='good'` / `is_stable` condition. Compare this to the analogous "is it actually issued" check used elsewhere in the codebase (`formula/evaluation.js`), which is careful to require the issuing unit to be stable and of `sequence='good'` (or be an unconfirmed AA response): [2](#0-1) 

and the standalone-wallet issuance path in `inputs.js`, which has the same unconditional check pattern: [3](#0-2) 

The `inputs` table retains rows for units regardless of their final `sequence` value; only `is_unique` may be nulled out, and only when a genuine competing double-spend on the *same* `(asset, denomination, serial_number, address)` key is detected during validation: [4](#0-3) 

If the AA response unit that contains the `issue` input never has a competing double-spend on that exact key (e.g., it becomes `final-bad` because of an unrelated conflict on another message/input within the same unit, or because a parent it depends on is voided), the `issue` row simply stays in `inputs` forever with `is_unique=1`, but the unit itself is excluded from the ledger since it is `final-bad`. From that point on:
- `issueAsset()`'s query `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` still returns a row, so the AA will always get `'already issued'` and refuse to issue the asset again.
- The asset's `is_issued` state as computed for the `asset[]` operator will correctly report `false` (because it filters on `sequence='good'`/`is_stable`), so any AA logic gated on `asset[$asset].is_issued` will keep waiting for issuance that can never happen.

This is structurally the same root cause as the Rio bug: recording that an operation has been "started/queued" (issuance attempted) without any invariant ensuring that state is cleared or corrected if the operation is later voided, and without gating the check on the operation having actually landed on a valid, good unit.

### Impact Explanation
Once triggered, the capped asset becomes permanently un-issuable through the AA:
- Any bytes/assets sent by users to the AA expecting the asset to be minted and paid out remain stuck in the AA's balance forever (the AA can never satisfy `objAsset.cap` issuance, so the code path returns `'not enough funds for ... of asset ...'` on every subsequent attempt).
- Any other AA logic (state vars, secondary AAs) conditioned on the asset eventually being issued is permanently deadlocked.
- This is an AA fund-freezing bug reachable purely from a normal, unprivileged AA-trigger sender's actions (no special privileges, no malicious node/hub behavior needed) — the trigger sender only needs to cause the AA's issuing response unit to end up on a losing side of a legitimate double-spend on an unrelated input within the same unit (e.g. by racing/double-spending an unrelated output the AA consumes, if reachable, or more simply this occurs naturally whenever a competing conflicting unit wins the sequence race for any input consumed by that response).

### Likelihood Explanation
The condition requires an AA response unit carrying the `issue` input to become `final-bad`, which is a normal (if relatively rare) DAG outcome whenever there is a losing side of a legitimate double-spend affecting any input in that unit — not necessarily the issue input itself. Because AA response units are auto-generated and deterministic, this is not attacker-arbitrary, but any real-world double-spend race touching a response unit that also issues a capped asset triggers permanent freezing with no possible recovery path in the current logic (no retry/clear mechanism exists).

### Recommendation
Align the capped-asset "already issued" check in `aa_composer.js` with the stricter check used in `formula/evaluation.js`'s `asset[$asset].is_issued` logic: require the existing `issue` input's containing unit to be `sequence='good'` and either stable (`is_stable=1`) or itself an AA response (`is_aa_response=1`) before concluding the asset was already issued. This ensures that if the unit carrying the issue input is voided (`final-bad`), the AA can retry issuance of the capped asset instead of being permanently frozen.

### Proof of Concept
1. An AA defines and later issues (in a subsequent trigger) a capped asset `A` (per the "issue recently defined asset" pattern already tested in `test/aa_composer.test.js`).
2. Craft/cause the AA's issuing response unit `U` to also spend/consume an input that is contested by a genuine competing unit that ultimately wins (any ordinary double-spend race on a base-byte output the AA is also consuming that mci), so `U` ends up `sequence='final-bad'`.
3. `U`'s `issue` input row for asset `A` remains present in `inputs` (with `is_unique=1`, since nothing conflicted at the `(asset, denomination, serial_number=1, address)` key).
4. Any later trigger causing the AA to attempt `issueAsset()` for `A` again hits `SELECT 1 FROM inputs WHERE type='issue' AND asset=?`, finds the stale row, and returns `'already issued'` — permanently blocking issuance even though `asset[A].is_issued` (per `formula/evaluation.js`) correctly evaluates to `false`, since it excludes the `final-bad` unit `U`.
5. All funds sent to the AA anticipating this asset are now permanently stuck. [5](#0-4)
