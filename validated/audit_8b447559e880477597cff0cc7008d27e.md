### Title
Webhook signature is verified against the organization named in the payload, while the affected `Stack`/`Commit`/`Repository` are resolved from unrelated payload fields with no organization cross-check, allowing a holder of any one tenant organization's `webhook_secret` to forge events that write to a different organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit supports multiple GitHub organizations in a single deployment, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to check the HMAC against using `repository_owner`, a value read straight out of the unverified JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`) [2](#0-1) . Once the signature check passes, the actual event handlers determine which `Stack`/`Commit` to mutate using **different, independent fields** of the same body - `repository.full_name` in `Handler#repository_name` [3](#0-2) , or a bare, repo-unscoped `sha` lookup in `StatusHandler#process` [4](#0-3) . Neither of these is cross-checked against the organization that was actually authenticated by the signature.

### Finding Description
The binding that should hold is: `organization authenticated by HMAC == organization owning the repository/commit that gets written`. In this codebase that binding is broken:

1. `verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that org's secret [5](#0-4) . This only proves the request was signed by *some* configured organization's secret - the one named in `repository.owner.login`/`organization.login`.
2. `PushHandler` (and every other handler) resolves the target `Stack`s via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [6](#0-5) [7](#0-6) . `full_name` is a completely separate JSON field from `repository.owner.login`; nothing forces them to refer to the same repository.
3. `StatusHandler` is even weaker: it looks up `Commit.where(sha: params.sha)` with **no repository/organization scoping at all** and creates a GitHub status on every matching commit across the entire Shipit instance [4](#0-3) .
4. `Repository.from_github_repo_name` itself just splits `"owner/name"` and does a plain `find_by`, with no relation to which org's secret verified the request [8](#0-7) .

Consequently, anyone who legitimately controls the `webhook_secret` for organization **A** (a valid tenant of a multi-org Shipit install) can sign a payload whose `repository.owner.login`/`organization.login` is `A` (so the signature check passes) while its `repository.full_name` (for push/PR events) or `sha` (for status events) references a stack or commit belonging to organization **B**, a completely different, unrelated tenant they have no access to.

### Impact Explanation
This is a cross-repository/cross-organization write, explicitly called out as a Critical-impact category:
- Forging a `status` webhook lets the attacker inject a fabricated GitHub commit status onto any commit in the system, for any stack, regardless of which org it belongs to. This can satisfy `ci.require` checks and other gating logic used before deploys/merges of a completely unrelated tenant's stack.
- Forging a `push` webhook lets the attacker cause `GithubSyncJob` to run for a foreign organization's stack with an attacker-chosen `expected_head_sha`, effectively steering that stack's sync/deploy pipeline using a commit SHA the attacker picked [7](#0-6) .
- Combined, an attacker who only administers their own tenant organization's GitHub App/webhook_secret can manufacture a passing CI status for an arbitrary commit in someone else's tracked repository and trigger that repository's sync, contributing to an unauthorized deploy path for a repository they were never authorized to touch - satisfying the "cross-repository writes" / "unauthorized deploy" criteria.

### Likelihood Explanation
This requires the attacker to control a `webhook_secret` for at least one organization configured in the same multi-tenant Shipit instance (a legitimate, low-privilege credential relative to other tenants) - it does not require compromising `api_clients_secret`, a `User`'s GitHub token, or any privileged Shipit account. Any deployment that onboards more than one GitHub organization (as documented and supported via `config/secrets.*.yml` with multiple org keys [9](#0-8) ) is affected, and the crossing payload fields (`repository.owner.login` vs `repository.full_name`/`sha`) are trivial to construct.

### Recommendation
After `verify_signature` succeeds, thread the authenticated `repository_owner` through to every handler and require that any `Repository`/`Stack`/`Commit` acted upon actually belongs to that verified owner (e.g., compare `Repository#owner` to `repository_owner`, and scope `StatusHandler`'s `Commit` lookup by the commit's stack's repository owner) before performing any writes.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as supported by `config/secrets.yml`).
2. Attacker legitimately administers `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`.
3. Attacker crafts a `status` event body:
```json
{
  "sha": "<sha of a commit belonging to org-b/victim-repo, tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over this exact body and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against `org-a`'s secret [5](#0-4) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit under `org-b/victim-repo`, and calls `commit.create_status_from_github!(params)`, creating a fabricated "success" status on a commit the attacker has no authorization over [4](#0-3) .
7. Analogously, a forged `push` event with `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"` passes signature verification and causes `PushHandler` to invoke `stack.sync_github(expected_head_sha: params.after)` on `org-b`'s stack [7](#0-6) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
