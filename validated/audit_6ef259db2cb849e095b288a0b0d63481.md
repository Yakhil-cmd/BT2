### Title
Cross-organization webhook forgery via mismatched signature-selection field vs. repository-write field in `WebhooksController` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook's HMAC signature using `repository_owner`, a value parsed directly out of the unauthenticated, attacker-controlled JSON body (`repository.owner.login` or `organization.login`), *before* any signature has been verified. The webhook handlers (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) then act on a *different* field of that same unauthenticated body — `repository.full_name` (or `sha`, which is looked up globally across all stacks) — to decide which `Stack`/`Commit` to mutate. In multi-organization Shipit deployments (the documented `github: { org1: {...}, org2: {...} }` configuration), these two fields are never bound together by the signature check, so a payload can be signed with the webhook secret of one organization while its "write" fields target a repository/stack belonging to a completely different organization.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is computed as: [2](#0-1) 

This value comes straight from the raw, unverified JSON body. `Shipit.github(organization:)` looks up a *per-organization* secret from `secrets.github` when multiple GitHub Apps are configured, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section, and implemented in [3](#0-2) .

Once the HMAC passes (using the secret tied to `repository_owner`), the raw `params` are handed unmodified to the handlers: [4](#0-3) 

Handlers resolve the actual `Stack`/`Repository` to write to from a *different* JSON field, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [5](#0-4) 

or, for `status` events, from `sha` alone, matched globally against `Commit.where(sha: ...)` with no repository/organization scoping at all: [6](#0-5) 

Nothing ties `repository.owner.login` (used to pick the verification secret) to `repository.full_name` or `sha` (used to pick the object that gets written). An attacker who legitimately owns/administers a GitHub organization/App configured on the same Shipit instance (and therefore knows or can trigger correctly-signed deliveries for that org's webhook secret) can send a signed webhook whose `repository.owner.login` is their own organization (so it passes `verify_webhook_signature` against their own secret) but whose `repository.full_name`/`sha` refers to a stack or commit belonging to a victim organization also hosted on that Shipit instance. This breaks the intended binding: `organization that authenticated == repository that is written`.

Concretely:
- `push` event: `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on the victim stack, an attacker-chosen `expected_head_sha`, potentially triggering an unauthorized deploy pipeline sync for a repository/organization the attacker never authenticated for. [7](#0-6) 
- `status` event: `StatusHandler` creates a forged CI status on any commit matching `sha` globally, across all stacks/organizations, letting the attacker mark an arbitrary victim commit as `success`, which is commonly used as a merge/deploy gate. [6](#0-5) 
- `pull_request` events resolve the target repository the same way via `params.repository.full_name`, independent of the org used for signature verification. [8](#0-7) 

### Impact Explanation
This crosses an authentication boundary: a party who is only authorized to send webhooks for organization A can forge state changes (fake CI statuses, spurious sync/deploy triggers) for stacks belonging to organization B, purely by controlling fields of the JSON payload that are outside what the HMAC binds them to. Forged `status` events feeding merge/deploy gating logic can contribute to an unauthorized deploy pathway, which matches the "unauthorized deploy" high-impact category. The severity depends on how many distinct GitHub organizations/webhook secrets are configured on a single Shipit instance — for a single-org install (the default/most common config) there is no cross-secret to exploit, but the multi-org configuration is explicitly documented and supported by this engine.

### Likelihood Explanation
Exploitability requires: (1) the target Shipit instance to be configured with multiple GitHub organizations (each with its own `webhook_secret`), which is a documented, supported configuration; and (2) the attacker to have legitimate control of at least one of the configured organizations (so they can compute a valid HMAC for that org's secret, e.g. by pointing an actual repository under their control at the shared Shipit webhook endpoint via a real GitHub App/webhook installation, then replaying a hand-crafted body). No repository write access, session, or API token to the victim organization is required — only the ability to deliver an arbitrary, differently-shaped JSON body with a signature valid for the attacker's own organization.

### Recommendation
Bind the signature-selection field to the field(s) the handlers actually act on. Specifically:
- After verifying the signature, re-derive `repository_owner`/the organization from the same object used by the handler logic (or, better, use `repository.full_name`'s owner segment consistently in both `verify_signature` and the handlers), and reject the request if they don't match.
- In `StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup by the verified organization/repository rather than matching `sha` globally across all stacks.
- Consider having `verify_webhook_signature` return which organization actually validated, and pass that verified organization into the handler pipeline instead of re-parsing organization info from the untrusted payload downstream.

### Proof of Concept
Given a Shipit instance configured with two orgs, `attacker-org` (attacker's own GitHub org with app/webhook installed) and `victim-org` (hosts a stack Shipit also tracks):
1. Attacker computes `signature = HMAC-SHA1(attacker-org_webhook_secret, body)` for a crafted `status` event body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
2. POST to `/github/hooks` (webhook endpoint) with `X-Github-Event: status` and `X-Hub-Signature: sha1=<signature>`.
3. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s webhook secret, and the signature validates successfully (attacker controls this secret).
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the victim's commit (looked up globally, with no dependency on `attacker-org`), and calls `commit.create_status_from_github!(params)`, forging a `success` status on a commit the attacker does not own or have write access to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
