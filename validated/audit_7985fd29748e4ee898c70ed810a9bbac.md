### Title
Webhook signature is bound to an attacker-chosen `organization`/`repository.owner.login` field, not to the `repository.full_name`/commit actually acted upon, allowing cross-organization forgery of push syncs and commit statuses - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify the HMAC against using a field taken from the *same, unauthenticated* payload it is about to verify: `repository.owner.login` or, if absent, `organization.login` [1](#0-0) . If that organization has no `webhook_secret` configured — an explicitly supported configuration shown in the docs and secrets templates — `GitHubApp#verify_webhook_signature` returns `true` unconditionally, with no signature check at all [2](#0-1) . The handlers that subsequently act on the payload, however, key off a *different* field: `repository.full_name` for stack resolution, or a bare `sha` for commit status updates — neither of which is tied to the `organization`/`owner.login` value that was used for authentication [3](#0-2) [4](#0-3) . This is a direct analog of the `getBidValue()` bug class: the field used to satisfy the trust check (`repository_owner`/`organization.login`) is not the field the privileged action is actually performed on (`repository.full_name` / `sha`).

### Finding Description
`verify_signature` computes `repository_owner` from the untrusted JSON body itself, then asks `Shipit.github(organization: repository_owner)` for the matching per-org `GitHubApp`, and calls `verify_webhook_signature` on it [5](#0-4) . `GitHubApp#verify_webhook_signature` short-circuits to `true` when the org's `webhook_secret` is blank [2](#0-1) ; a blank/`nil` `webhook_secret` is a normal, documented configuration state (see the `webhook_secret: # nil` placeholders in the setup docs and secrets templates) [6](#0-5) .

Once verification passes, `WebhooksController#create` dispatches the raw JSON to the registered handlers for the event [7](#0-6) . `Handler#stacks`/`#repository_name` resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a completely separate field from `repository.owner.login` used for the signature-org lookup [3](#0-2) . `PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on that repository/branch [8](#0-7) . Even more starkly, `StatusHandler` looks commits up **only by `sha`**, with no repository/owner scoping whatsoever, and writes a GitHub-sourced commit status for any commit matching that sha across the entire installation [4](#0-3) .

The equality that should hold but is broken: `organization that authenticated the request == organization/repository the privileged action is performed on`. Because the "authenticating" field is attacker-supplied and independent of `repository.full_name`/`sha`, an attacker who picks/knows of any configured GitHub org with no `webhook_secret` can forge the `owner.login`/`organization.login` to that unsecured org while pointing `repository.full_name` (or `sha`) at a target stack/commit that actually belongs to a different, properly-secured organization.

### Impact Explanation
An unprivileged attacker with no GitHub credentials, no Shipit session, and no knowledge of any `webhook_secret` can:
- Force `Stack#sync_github` on any repository/branch tracked by Shipit by targeting a `repository.full_name` belonging to a securely-configured organization, while satisfying authentication via an unrelated organization that has no `webhook_secret` set [8](#0-7) .
- Forge arbitrary commit statuses for any commit SHA tracked by any stack via the `status` event, since `StatusHandler` never checks repository ownership [4](#0-3) . Since deploy eligibility in Shipit is commonly gated by required commit statuses, this can be used to fabricate a passing status and enable an unauthorized deploy of a commit that never actually passed CI on the real (secured) repository — matching the Critical "unauthorized deploy" impact bucket.

This crosses the authentication boundary the webhook signature is meant to enforce: the whole point of `verify_webhook_signature` is to prove the request originated from GitHub for a specific organization/app installation; here that guarantee does not extend to the repository/commit actually mutated.

### Likelihood Explanation
Any Shipit deployment that configures more than one GitHub organization (a documented, supported setup — see "Using Multiple Github Applications" in `docs/setup.md`) and leaves `webhook_secret` unset for at least one of them (also documented/templated as an accepted value) is exploitable purely by an external HTTP POST to `/webhooks`, with an attacker-controlled JSON body and no valid `X-Hub-Signature` needed. No credentials, sessions, or GitHub App keys are required — only knowledge of the org name lacking a secret and the target `repository.full_name`/commit `sha`, both of which are public information.

### Recommendation
Bind the field used for signature verification to the same repository/organization identity that the handlers act on: resolve the target `Stack`/`Repository` first (from `repository.full_name`), derive the authenticating organization strictly from that resolved repository's known owner (server-side, not payload-supplied), and reject the webhook if the app config's expected owner does not match. Additionally, do not treat a blank `webhook_secret` as an implicit "always verified" bypass — require every configured organization to have a non-blank secret, or explicitly disable event processing for repositories owned by secret-less organizations. Scope `StatusHandler`'s commit lookup by the repository/org it authenticated against, not by a bare, cross-repository `sha`.

### Proof of Concept
Preconditions: Shipit is configured with at least two GitHub orgs — `unsecured-org` (no `webhook_secret` configured, per the documented optional setting) and `victim-org` (properly configured with a `webhook_secret`), and Shipit tracks a stack for `victim-org/protected-repo`.

1. Attacker sends, without any valid GitHub signature header:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/protected-repo"
  }
}
```
2. `verify_signature` computes `repository_owner = "unsecured-org"` [1](#0-0) , fetches `Shipit.github(organization: "unsecured-org")`, and `verify_webhook_signature` returns `true` unconditionally because that org has no secret [9](#0-8) .
3. `PushHandler#process` resolves stacks via `repository.full_name = "victim-org/protected-repo"` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim org's stack [8](#0-7)  — despite the request never being authenticated against `victim-org`'s real webhook secret.

A parallel PoC with `X-Github-Event: status` and a forged `sha` belonging to a commit on `victim-org/protected-repo` similarly writes an unauthenticated commit status via `StatusHandler`, with no repository/owner check at all.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
