### Title
Webhook `status` events are applied to matching commit SHAs across all repositories with no binding to the authenticating organization/repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App/organization derived from `repository.owner.login` (or `organization.login`) in the JSON body, then hands the *entire* raw payload to whichever handler is registered for the event. Handlers, however, resolve *what to write* from other, independently-controlled fields of that same payload, without re-checking that they belong to the organization that was actually authenticated. This breaks the binding "organization authenticated == repository/commit written to."

### Finding Description
`WebhooksController#verify_signature` picks the signing key purely from the payload's owner/organization login: [1](#0-0) [2](#0-1) 

Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler with the raw parsed JSON, unchanged: [3](#0-2) 

`Handlers::StatusHandler` then updates commit CI status by looking up commits **globally by SHA only**, with no repository/organization scoping whatsoever: [4](#0-3) 

Contrast this with the base `Handler` class, which *does* have a notion of "the repository this event is for" (`payload.dig('repository', 'full_name')`), used by other handlers like `PushHandler`: [5](#0-4)  — but `StatusHandler` never applies this scoping to the `Commit` lookup, so a `status` payload that is correctly signed for **organization A** can still target a `Commit` row that actually belongs to a stack/repository owned by **organization B**, purely by supplying that commit's SHA (a public, non-secret value visible in any GitHub URL).

The equality that should hold but doesn't:
`organization whose webhook_secret verified the payload == repository/commit that gets mutated by the handler`

Before the attacker's request: commit statuses for repository B's commits can only be legitimately created by GitHub events signed with organization B's webhook secret.
After the attacker's request: any organization onboarded to this (potentially multi-tenant) Shipit instance — verified only against its own secret — can forge a `commit_status`/`Status` record on any commit belonging to any other tracked repository, as long as it knows that commit's SHA.

### Impact Explanation
Shipit stacks use commit CI status (`Status`) to gate deployability (`deployable_status`) and, per the engine's documented merge-queue and CI-gating features, to decide whether a commit is safe to merge/deploy. An attacker who legitimately controls (or has been granted access to) even one low-value organization/repository connected to this Shipit instance can inject a forged "success" status for an arbitrary commit SHA belonging to a **different, higher-value repository/stack** they do not control. This can make an unreviewed or malicious commit appear CI-green in that other repository's stack, enabling an unauthorized deploy/merge decision to be made on the basis of forged status data — a cross-repository write that maps directly to the "Critical: cross-repository writes / unauthorized deploy" impact bucket, without requiring any Shipit session, `ApiClient` token, or repository write access on the victim repository — only knowledge of the target commit SHA and legitimate (but unprivileged w.r.t. the victim repo) webhook access to any other org on the same instance.

### Likelihood Explanation
Requires the attacker to control an organization/repository that is already connected to the same Shipit deployment (multi-tenant setups configure multiple GitHub Apps/organizations, as seen in `test/dummy/config/secrets_double_github_app.yml`), and to know a target commit SHA in the victim repository (trivially obtainable — SHAs are public). No signature forgery is needed since the attacker uses their own organization's legitimately-issued webhook secret; only the SHA-based cross-repo lookup is exploited.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up records independent of `repository_name`) to the repository resolved from the payload via the base `Handler#stacks`/`repository_name` helper, e.g. `Commit.where(sha: params.sha, stack: stacks... )`, so a status update can only affect commits belonging to the repository that was actually authenticated for this webhook delivery.

### Proof of Concept
1. Attacker legitimately owns/administers "attacker-org", which is configured in this Shipit instance's `secrets.yml` with its own `webhook_secret` (multi-org setups such as `test/dummy/config/secrets_double_github_app.yml` support this).
2. Attacker computes a valid `X-Hub-Signature` for `attacker-org`'s secret over a JSON body like:
```json
{
  "sha": "<40-hex sha of a commit in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}
}
```
3. POST to `/webhooks` with `X-Github-Event: status` and the forged-but-valid-for-attacker-org signature.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the HMAC (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), matching the victim's commit purely by SHA with no owner/repository check, and creates a forged `success` status on it via `create_status_from_github!`.
