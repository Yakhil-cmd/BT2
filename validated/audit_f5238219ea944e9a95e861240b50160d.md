### Title
Cross-repository status webhook rewrites CI state for any stack sharing a commit sha, allowing unauthorized rejection of a foreign `MergeRequest` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository/stack filter, unlike every other webhook handler in the codebase which scopes lookups through `Repository.from_github_repo_name(params.repository.full_name)`. Because `Commit` uniqueness is only `(sha, stack_id)` (not globally unique on `sha`), any organization that can trigger a real, correctly-signed GitHub `status` webhook containing a sha that happens to also exist as a `Commit` row in a different stack can write a `Status` row onto that foreign stack's commit, and thus flip `MergeRequest#any_status_checks_failed?` for a `MergeRequest` it does not own.

### Finding Description
The broken binding is: **"the organization whose webhook signature was verified (`repository_owner` from the payload) == the organization owning the `stack`/`Commit` row that receives the new `Status`."** The code should enforce this equality but does not.

Path:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the raw payload and dispatches to `Shipit::Webhooks.for_event(event)`, i.e. `StatusHandler.call(params)`.
2. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC signature using `Shipit.github(organization: repository_owner)` — this only proves the webhook truly came from GitHub for the *attacker's own* organization/repository, not that the sha belongs to that org.
3. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is a **global** lookup by `sha` across *all* stacks in the installation — it never touches `params.repository` (the params schema for this handler doesn't even declare/require a `repository` field), unlike sibling handlers such as `PullRequest::OpenedHandler`, `EditedHandler`, `AssignedHandler`, and the shared `Handler#stacks` helper (app/models/shipit/webhooks/handlers/handler.rb:32-34), all of which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record.
4. `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` (app/models/shipit/commit.rb:165-169) creates the `Status` using `self.stack_id`, i.e., the **victim stack's** id, with `state: params.state` (attacker-controlled, e.g. `'failure'`).
5. `Commit` uniqueness is only `(sha, stack_id)` (see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` and `test/dummy/db/schema.rb` unique index `["sha","stack_id"]`), not globally unique on `sha` — so identical commit objects (e.g. shared base commits, or a commit that exists verbatim in a public fork the attacker controls and also as a tracked PR head in the victim's stack) legitimately produce multiple `Commit` rows with the same `sha` under different `stack_id`s.
6. On the next `ProcessMergeRequestsJob#perform` (app/jobs/shipit/process_merge_requests_job.rb:10-17), `merge_request.reject_unless_mergeable!` → `any_status_checks_failed?` (app/models/shipit/merge_request.rb:199-202) evaluates `StatusChecker` over `head.statuses_and_check_runs`, finds the injected `failure` status, and calls `reject!('ci_failing')` (app/models/shipit/merge_request.rb:145-153, 158), writing `rejection_reason` on a `MergeRequest` belonging to a stack/repository the attacker never authenticated against.

Existing guards fail to close this gap: `verify_signature` only authenticates *which org sent the webhook*, not *which sha/stack it is entitled to write to*; there is no `ExplicitParameters` requirement for `repository` in `StatusHandler`; and no model-level validation ties `Status#stack_id`/`Commit#sha` uniqueness across stacks.

### Impact Explanation
An attacker who owns any repository (or fork) that legitimately shares a commit sha with a victim's tracked `Commit` can write a `Status` row of state `failure`/`error` onto the victim's `Commit`, and via `ProcessMergeRequestsJob` this causes `MergeRequest#reject!('ci_failing')` — an unauthenticated cross-tenant write that denies a legitimate merge on a repository/stack the attacker does not own and never authenticated to. This is repeatable against any stack/commit sha the attacker can find or cause to collide (e.g., shared upstream/base commits between forks), and the blast radius spans all stacks hosted by the Shipit instance, not just the attacker's own. This matches the "payload for one repository mutating another's stack/commit" Critical category, though the direction is rejection rather than merge/deploy.

### Likelihood Explanation
Preconditions: the attacker must control (or have webhook-trigger ability for) some repository/org connected to the same Shipit instance whose GitHub App/webhook secret they can drive a genuine `status` event for, and a `Commit` sha must exist identically in both the attacker-reachable repo and the victim's stack (feasible via shared git history/forks — not a hash-preimage attack). Given that, the attacker cost is a single legitimate GitHub API call (`POST /repos/:owner/:repo/statuses/:sha`) on their own repository; no Shipit secrets, sessions, or privileged roles are needed. This is fully repeatable per matching sha.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring other handlers: require `repository.full_name` in the params schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit.where(sha: ...)` lookup to `commit.stack.repository == repository` (e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { id: repository.id })`) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
```ruby
test "status webhook from a foreign repository must not reject an unrelated stack's merge request" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repo_full_name = "attacker-org/attacker-repo"

  merge_request = shipit_merge_requests(:shipit_pending)
  shared_sha = merge_request.head.sha

  # Simulate attacker's own repository also containing a Commit row with the same sha
  # (as would happen with legitimately shared/forked history), tracked under a different stack.
  attacker_stack = shipit_stacks(:some_other_stack_owned_by_attacker_org)
  attacker_stack.commits.create!(sha: shared_sha, message: "shared", authored_at: Time.now, committed_at: Time.now)

  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  post :create, body: payload, as: :json, headers: { 'X-Github-Event' => 'status' }

  refute_equal 'ci_failing', merge_request.reload.rejection_reason
  refute_predicate merge_request.reload, :rejected?
end
```
Assertions on both sides of the binding: before the fix, `merge_request.reload.rejected?` is `true` and `rejection_reason == 'ci_failing'` even though the webhook named `attacker-org/attacker-repo`, not the victim's repository — proving `repository_owner (webhook signer) != stack.repository.owner (record mutated)`. After applying the recommended scoping fix, the assertions above pass (no cross-tenant write occurs).
