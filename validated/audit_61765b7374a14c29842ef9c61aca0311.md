### Title
Interest accrual overflows RAY-valued market totals and permanently freezes the market - (File: common/src/rates/simulate.rs)

### Summary
Severity: Medium. A sufficiently large market can grow its borrow or supply index until `scaled_amount * index / RAY` no longer fits in `i128`; the next accrual panics before updating state, leaving every later operation to repeat the same overflow. [1](#0-0) 

### Finding Description
`accrue_step` first un-scales total borrowed and supplied shares using `scaled_to_original`, which is implemented as `scaled.mul(env, index)` and panics when the RAY-valued result exceeds `i128::MAX`. [2](#0-1) [3](#0-2) 

The accrual then multiplies the same scaled debt by both the old and new borrow indexes when calculating interest, creating additional overflow sites even if utilization were computed another way. [4](#0-3) 

`global_sync` only calls `mark_accrued()` after every chunk completes, so an arithmetic panic leaves `last_timestamp` and the indexes stale; every retry starts from the same overflowing state. [5](#0-4) 

An unprivileged user can create the state through `Controller::supply` and `Controller::borrow`, while `Controller::update_indexes` forwards market keys to the pool accrual entrypoint. [6](#0-5) [7](#0-6) 

The pool’s `accrue` operation loads each selected market, invokes `global_sync`, and commits only after successful accrual. [8](#0-7) 

### Impact Explanation
Once the market crosses the representable RAY-value boundary, `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `recapitalize`, and any other path that accrues first revert with `MathOverflow`, permanently freezing supplier and borrower funds under the deployed code. [9](#0-8) [10](#0-9) 

This is more than a failed single transaction: the stale timestamp guarantees that subsequent transactions attempt the same overflowing product, so there is no in-protocol path to unwind positions after crossing the boundary. [11](#0-10) 

The protocol documentation already acknowledges that valid caps and bounded indexes do not guarantee accrued values fit and that this overflow can block repayment and withdrawal before the static index ceiling. [12](#0-11) 

### Likelihood Explanation
The condition requires a very large market and enough sustained borrowing for an index to multiply the market’s scaled shares beyond `i128::MAX`, so it is economically gated rather than triggerable from a small transaction. [13](#0-12) 

The repository’s harness demonstrates the scenario with a one-billion-whole-token, 18-decimal market at 98% utilization; accrual eventually fails before the configured borrow-index ceiling, and subsequent withdrawal and repayment attempts fail with `MathOverflow`. [14](#0-13) 

Because the amounts are within the documented token-to-RAY input domain and below the admitted cap bound, the scenario does not depend on malformed input or an arithmetic trap outside the contract’s accepted domain. [15](#0-14) 

### Recommendation
Make accrual boundary-safe instead of allowing unscaled market totals to overflow:

- Before each `accrue_step`, derive per-market index ceilings from the stored scaled totals, such as `floor(i128::MAX * RAY / scaled_amount)`, and clamp `new_borrow_index` or `new_supply_index` before any `scaled * index` multiplication. [16](#0-15) 
- Alternatively, perform accrual internals over `I256` market totals and clamp persisted indexes to the largest value whose total remains representable; do not merely saturate silently where that would break debt valuation invariants. [17](#0-16) 
- Enforce supply and borrow caps against the maximum permitted index, not only the current index, so accepted scaled shares cannot overflow during later accrual. [18](#0-17) 
- Add a regression test that accrues to the boundary, verifies the index clamps instead of panicking, and then confirms repayment, withdrawal, liquidation, and revenue accounting remain functional. [10](#0-9) 

### Proof of Concept
The existing harness reproduces the vulnerability:

1. Create an 18-decimal market and a collateral market with caps large enough for a one-billion-token deposit.
2. Call `supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18)])`.
3. Supply sufficient collateral and call `borrow(caller, account_id, [(BIG18, 980_000_000 * 10^18)], to)`.
4. Advance ledger time in bounded chunks and call `update_indexes([BIG18])` until `borrowed_scaled * borrow_index / RAY` exceeds `i128::MAX`.
5. Call `withdraw(..., [(BIG18, 1)], ...)` or `repay(..., [(BIG18, payment)])`; both attempt accrual first and fail with `MathOverflow`. [14](#0-13) 

The decisive state transition is the multiplication in `accrue_step`; because the panic occurs before `mark_accrued`, the market remains permanently positioned immediately before the same overflowing calculation. [1](#0-0) [11](#0-10)

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
```

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
