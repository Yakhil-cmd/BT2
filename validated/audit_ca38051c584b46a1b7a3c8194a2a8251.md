## Analog Found

### Title
Single-step, irreversible `address_definition_change` allows permanent address lockout with no ownership-transfer safety pattern - (File: `validation.js`)

### Summary
The Kairos finding flags that `OwnershipFacet.transferOwnership` performs a one-step transfer of a critical control role, so a mistaken target renders the contract's privileged functions permanently unreachable. The equivalent "ownership" primitive in ocore is the `address_definition_change` message: it lets the current definition holder of an address immediately and irrevocably replace the signing/authorization rules (definition) for that address in a single step, with no two-step propose/accept or validity-proof mechanism. A mistaken or unusable `definition_chash` permanently locks the address, including any base/asset funds held there and its capacity to act as an asset definer or AA trigger sender.

### Finding Description
`validateInlinePayload` in `validation.js` handles the `address_definition_change` app. The only check performed on the new definition is `isValidAddress(payload.definition_chash)` — a syntactic/format check that the value looks like a 32-byte base32 chash, not that a definition matching that chash was ever published, is well-formed, or is actually spendable by the poster: [1](#0-0) 

Once this message is included in a stable unit, `writer.js` persists the new `definition_chash` for the address: [2](#0-1) 

From that point on, any unit from the address must supply a definition hashing exactly to the new `definition_chash` (see `validateDefinition` in `validation.js`, which errors on any mismatch: `wrong definition: ... !== ...`): [3](#0-2) 

There is no built-in two-step confirmation (e.g., requiring the new definition to co-sign an acceptance unit, or a pending/challenge period during which the old definition can still veto/revert), unlike patterns such as LiFi's `OwnershipFacet` that require the new owner to explicitly accept before the transfer finalizes. Because `address_definition_change` is a single serial-enforced, one-shot operation per address (`objValidationState.arrDefinitionChangeFlags`), a single mistake (wrong hash, or a hash for which the poster doesn't actually control matching signing material) is final and unrecoverable. [4](#0-3) 

### Impact Explanation
If the posted `definition_chash` is incorrect or corresponds to a definition the poster cannot produce, the address becomes permanently unusable: any base-currency or asset balance held at that address is frozen forever, and if the address also happens to be an asset's `definer_address`, the ability to issue additional units of a capped/uncapped asset (`issued_by_definer_only`) is permanently lost, as seen in the definer-address dependent issuance logic in `inputs.js` and `indivisible_asset.js`: [5](#0-4) 

This is a genuine, protocol-level fund/asset-control freezing risk directly analogous to the reported one-step ownership-transfer class, reachable by an ordinary, unprivileged unit poster acting on their own address.

### Likelihood Explanation
This requires no attacker — it is triggered purely by the poster's own mistake (typo in `definition_chash`, miscomputed hash, or referencing a definition whose private key/signing material they don't actually hold) when composing an `address_definition_change` message via `composer.composeDefinitionChangeJoint`: [6](#0-5) 

Given that this is a normal, frequently-used wallet/AA operation for rotating keys or upgrading multisig rules, and there is no built-in safeguard requiring proof that the new definition is valid/controllable before the old one is discarded, the likelihood of an irreversible accidental lockout is non-trivial for any user, wallet-service address, or asset-definer address performing key rotation.

### Recommendation
Introduce an optional two-step definition-change pattern: require the new definition to co-sign (or separately confirm via a unit authored under the *new* definition) before the old definition is fully invalidated, or add a pending-state/timelock window during which the previous definition can still be used to cancel the pending change. At minimum, wallets/tools composing `address_definition_change` should mandate a round-trip proof that the poster actually possesses working credentials for the new `definition_chash` before broadcasting it.

### Proof of Concept
1. User `A` composes and posts an `address_definition_change` unit for address `A` with `definition_chash = H`, where `H` was computed incorrectly (e.g., transcription error) or corresponds to a definition array the user does not actually hold matching keys for.
2. The unit passes validation because only `isValidAddress(payload.definition_chash)` is checked (`validation.js:1743-1744`).
3. Once the unit becomes stable, `storage.readDefinitionByAddress` for address `A` now returns/expects chash `H` (via `writer.js:186-192`).
4. Any subsequent unit from `A` must supply a definition matching `H` or it is rejected with `"wrong definition"` (`validation.js:1472-1473`), permanently freezing all funds at `A` and any asset-issuance rights tied to `A` as `definer_address`.
