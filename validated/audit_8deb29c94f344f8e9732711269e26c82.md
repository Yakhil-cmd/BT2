### Title
Webhook signature is verified against `repository.owner.login` while repository writes are keyed on `repository.full_name`, letting one onboarded organization forge events into another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`. Once the signature check passes, the handler dispatch (`Shipit::Webhooks::Handlers::Handler#stacks`) resolves the target `Repository`/`Stack` using a *different* payload field, `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that gets written to" are two independently attacker-controlled strings inside the same signed JSON body.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`verify_signature` computes `repository_owner` from the payload itself and uses it to look up the correct per-organization `Shipit.github(organization: repository_owner)` app config (and thus the correct `webhook_secret`) to check `X-Hub-Signature` against `request.raw_post`.

Once that passes, `WebhooksController#create` hands the raw parsed JSON straight to the handlers: [2](#0-1) 

Handlers resolve the actual repository/stack to act on via a *separate* field: [3](#0-2) 

`repository_name` comes from `payload.dig('repository', 'full_name')`, which is parsed independently as `"owner/name"` by `Repository.from_github_repo_name`: [4](#0-3) 

Nothing in this chain asserts that `repository.owner.login` (used to pick the signing secret) equals the owner portion of `repository.full_name` (used to pick the repository/stack that gets acted on). In Shipit's documented multi-org deployment mode, each onboarded GitHub organization gets its own `app_id`/`installation_id`/`webhook_secret` entry under `github:`, and organization administrators legitimately possess (or can rotate/view) their own App's webhook secret, since they own the GitHub App installation: [5](#0-4) [6](#0-5) 

This is exactly the deployment-trust binding break called out in the analog rules: "an organization that authenticated versus the repository that is written." Concretely:
- Equality that should hold: `verified_org == full_name.split('/').first`
- Equality actually enforced: none — `verified_org` is derived from `repository.owner.login`, while the write target is derived from `repository.full_name`, and both are attacker-supplied JSON fields inside the same request body that only needs to be signed with *any* onboarded org's secret.

An administrator/member of Org A (a legitimately onboarded, low-trust organization in a multi-tenant Shipit instance) knows Org A's `webhook_secret` (they configured the GitHub App themselves under their own organization settings, per `docs/setup.md`). They can then POST a webhook to Shipit's `/webhooks` endpoint with:
- `repository.owner.login = "org-a"` (so `verify_signature` selects Org A's app/secret and passes),
- `repository.full_name = "org-b/victim-repo"` (a different, higher-trust organization's repository that Shipit also manages).

The HMAC over the raw body is computed with Org A's secret and matches, so `head(422)` is never hit. The handler then resolves `Repository.from_github_repo_name("org-b/victim-repo")` and dispatches events (e.g. `push`, `status`, `check_suite`) as if they legitimately originated from Org B.

### Impact Explanation
Using the `push` handler as the concrete vector: [7](#0-6) 

An attacker who only controls Org A's webhook secret can trigger `stack.sync_github(expected_head_sha: params.after)` for any branch/stack belonging to Org B's repository, forcing Shipit to treat an attacker-chosen SHA as the new head for that branch. Combined with `continuous_deployment: true` on the target stack (`Stack.schedule_continuous_delivery`), this can drive an unauthorized deploy/rollback of a commit the attacker asserts is the branch head, on a repository the attacker's organization never legitimately owns or has push access to — a cross-organization write/deploy that crosses the "cross-repository writes" / "unauthorized deploy" bar for Critical/High impact. The `status` and `check_suite` handlers are similarly reachable and can forge CI status/check state for Org B's commits, which feeds directly into merge/deploy gating logic (`StatusChecker`, `MergeRequest#all_status_checks_passed?`).

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to be an administrator of *any one* of the onboarded, lower-privilege organizations — not the target organization, and no Shipit user session, `ApiClient` token, or GitHub push access to the victim repository is required. Given that webhook secrets are organization-owned and rotated by each organization's own GitHub App settings (not centrally managed secrets like `webhook_secret`/`api_clients_secret` at the Rails app level), this is a realistic misuse path in any multi-tenant deployment, and is not blocked by any check in this engine's code.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature with the org derived from `repository_owner` (or `organization.login`), assert that this same organization matches the owner segment of `repository.full_name` before dispatching to handlers; reject with `422` on mismatch. Equivalently, `Handler#repository_name`/`Repository.from_github_repo_name` should be passed the already-authenticated organization explicitly rather than re-deriving it from an unvalidated payload field, so a single signed field is the sole source of truth for both authentication and target resolution.

### Proof of Concept
Given a multi-org Shipit configuration (`docs/setup.md` "Using Multiple Github Applications") with `org-a` and `org-b` both onboarded and their own `webhook_secret`s, and `org-b/victim-repo` having a stack with `continuous_deployment: true` tracking branch `main`:

1. Attacker (an admin of `org-a`, who legitimately knows `org-a`'s `webhook_secret` because they configured that GitHub App) crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-in-org-b/victim-repo>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(org-a-webhook-secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")`, verifies the signature successfully (it was signed with `org-a`'s real secret), and lets the request through.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/victim-repo")` (via `repository.full_name`, never checked against `org-a`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Org B's stack, with continuous delivery potentially triggering an unauthorized deploy of that SHA — despite the attacker having no legitimate relationship to `org-b/victim-repo` and no Shipit session or GitHub write access to it.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
