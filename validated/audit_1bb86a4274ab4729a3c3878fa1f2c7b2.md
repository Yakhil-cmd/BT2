### Title
CCMenuController bypasses ApiClient stack scoping, allowing stack-scoped API clients to read cc.xml for any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack via `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks` helper defined in `BaseController`, and `check_permissions!` only validates the permission name, never `stack_id`. An `ApiClient` restricted to one stack can therefore fetch the CCMenu XML (deploy/rollback history) of any other stack.

### Finding Description
The intended binding is `current_api_client.stack_id == params[:stack_id]` whenever an `ApiClient` has `stack_id` set (i.e., is scoped to a single stack). `BaseController#stacks` enforces this: [1](#0-0) 
`stacks` filters `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and the default `stack` method resolves through that scope.

`CCMenuController`, however, overrides `stack` to bypass this scope entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model, and `authenticate_api_client` only verifies the token signature via `ApiClient.authenticate`, never comparing `stack_id`.

`require_permission :read, :stack` (line 6) triggers `require_permission!` → `current_api_client.check_permissions!(:read, :stack)`: [3](#0-2) 
This only checks that `"read:stack"` is in the `permissions` array — it never inspects `stack_id`. So an `ApiClient` created with `stack_id = A` and `permissions = ['read:stack']` passes this check for any stack, not just A.

Exploit flow: attacker owns `ApiClient X` (`stack_id=A`, `permissions=['read:stack']`), knows/derives `X.authentication_token`, and sends `GET /api/stacks/B/cc.xml?token=<token>` where B belongs to a repository the attacker doesn't own. `authenticate_api_client` authenticates X successfully; `stack` resolves stack B unscoped; `require_permission!` passes because `read:stack` is present; `#show` renders B's `deploys_and_rollbacks` history in the XML response — leaking deploy status, commit info, and build labels for a stack/repository outside the client's intended scope.

Existing guards fail here specifically because `CCMenuController` re-implements `stack` without using the scoped `stacks` accessor that every other API controller relies on, and no other check ties `current_api_client.stack_id` to `params[:stack_id]`.

### Impact Explanation
An attacker with any valid stack-scoped API token (even one restricted to their own repository's stack) can read the CI/deploy status of any other stack on the same Shipit instance — cross-tenant disclosure of deploy/rollback activity, commit SHAs, build success/failure state, and lock status. This is repeatable for every stack ID on the instance (stack IDs/params are typically the repository `owner/name/env` path, easily guessable/enumerable). This matches the High-severity category "unauthenticated read of stack state" in effect, since the token used carries no legitimate authorization for the target stack.

### Likelihood Explanation
Preconditions: attacker needs any valid `ApiClient` with `read:stack` permission and a `stack_id` restriction (a common, minimal-privilege configuration for CI integrations, easily attained by any user granted a scoped token for their own repo). No GitHub secrets, session, or maintainer role are required — only their own legitimately-issued scoped token. The attack is a single unauthenticated-parameter GET request, trivially repeatable against every stack.

### Recommendation
Change `CCMenuController#stack` to use the scoped accessor consistent with the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it inherits `BaseController#stacks`' `current_api_client.stack_id`-based filtering, returning 404 when the client is scoped to a different stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped api client cannot read another stack's cc.xml" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: @user, name: 'scoped', stack: stack_a, permissions: ['read:stack']
  )

  assert_equal stack_a.id, scoped_client.stack_id
  refute_equal scoped_client.stack_id, stack_b.id

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Expected (secure) behavior: reject cross-stack access
  assert_response :not_found
  # Actual (vulnerable) behavior observed today: assert_response :ok with stack_b's data rendered
end
```
