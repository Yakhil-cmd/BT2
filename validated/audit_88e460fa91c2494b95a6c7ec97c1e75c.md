### Title
Zip-Bomb Denial of Service in Textcoin Private-Payment File Handler - (File: wallet.js)

### Summary
`handlePrivatePaymentFile()` in `wallet.js` unzips an attacker-suppliable "private payment file" (a textcoin claim/redeem file that a counterparty sends the victim, e.g. as an email/social-media attachment) with JSZip and decompresses the embedded `private_textcoin` entry before validating its size in a robust way. The size guard depends on an undocumented internal property, and even when present, still permits decompression of a very large payload, which is exactly the zip-bomb class described in the Gradio advisory (CVE-2024-10569): a small compressed input expands into memory-exhausting content processed by the app.

### Finding Description
`handlePrivatePaymentFile(fullPath, content, cb)` [1](#0-0)  loads attacker-controlled bytes into a `JSZip` instance and looks up the `private_textcoin` entry:

```js
zip.loadAsync(data).then(function(zip) {
    const entry = zip.file("private_textcoin");
    if (!entry)
        return cb("missing private_textcoin entry in zip");
    if (entry._data && entry._data.uncompressedSize > 100 * 1024 * 1024)
        return cb("private_textcoin entry is too large");
    entry.async("string").then(function(data) { ... });
``` [2](#0-1) 

The only safeguard against a maliciously crafted small ZIP that expands to an enormous uncompressed payload is the check on `entry._data.uncompressedSize`. This is:

1. **Conditional on an internal/undocumented property** (`entry._data`) rather than a public JSZip API — if `_data` is absent or shaped differently (which can legitimately happen depending on how the entry was produced/streamed by the zip library), the `if` short-circuits to `false` and the size check is skipped entirely, so `entry.async("string")` decompresses the entry fully into memory with no bound.
2. **Even when the check fires, it allows up to 100 MB of decompressed string data** per redemption file, which is still large enough to be used repeatedly to exhaust memory/CPU on constrained wallet clients (mobile/desktop Obyte wallets), especially since the subsequent code does `JSON.parse(data)` on that string [3](#0-2) , adding further CPU/memory pressure for parsing a huge JSON blob.

This is functionally analogous to the Gradio dataframe zip-bomb bug: an untrusted, attacker-supplied compressed artifact is decompressed and parsed without a reliably-enforced, pre-decompression size limit, enabling a compression-ratio attack (a few KB compressed file expanding to gigabytes) that crashes or hangs the victim's process.

The private-payment file is explicitly a mechanism for one party (the textcoin sender/counterparty) to hand a redeemable payload to another party (the recipient), matching the private-payment counterparty attacker profile in scope for this analysis. There is no authentication of the file's origin — the recipient wallet processes whatever bytes it is given.

### Impact Explanation
Successful exploitation crashes or freezes the victim wallet process (OOM kill / event-loop stall) purely by having the victim open a maliciously crafted textcoin/private-payment file — a normal wallet redemption action. This is a genuine availability impact against a node's/wallet's ability to continue operating (matching the DoS impact class), reachable without any privileged keys, from a private-payment counterparty role explicitly allowed by the scope rules.

### Likelihood Explanation
Likelihood is high for the "check bypass via missing `_data`" scenario if JSZip's internal representation for the entry doesn't populate `uncompressedSize` under all code paths (this is not part of JSZip's public/documented API and its presence is an implementation detail the ocore code relies on without verification). Even without a bypass, the 100 MB budget is large enough to cause meaningful resource pressure, and the attacker fully controls the file content and can tune the compression ratio to maximize damage under the enforced ceiling.

### Recommendation
- Do not rely on the undocumented `entry._data.uncompressedSize` field. Instead, either use JSZip's decompression bomb protections/limits, or stream-decompress with an explicit byte-counting wrapper that aborts once a defined cap (e.g., a few hundred KB — textcoin payloads are small JSON objects) is exceeded, independent of any internal library state.
- Lower the size cap dramatically; 100 MB is far larger than any legitimate `private_textcoin` payload should ever be.
- Validate the compressed-to-uncompressed ratio (reject entries with implausible compression ratios) before calling `entry.async(...)`.
- Wrap the whole unzip/parse pipeline with a hard timeout so a still-unbounded decompression cannot hang the process indefinitely.

### Proof of Concept
1. Attacker crafts a ZIP archive containing a single entry named `private_textcoin` whose compressed size is a few KB but whose declared/actual uncompressed content is many hundreds of MB to GB (a classic zip bomb, e.g. all-zero content compressed at near-maximum ratio with DEFLATE).
2. Attacker sends this file to the victim as a "textcoin" redemption file (the normal user flow for `receiveTextCoin`-style textcoins, which are typically shared via email/chat/social links and opened via `handlePrivatePaymentFile`).
3. Victim's wallet calls `handlePrivatePaymentFile(fullPath, content, cb)` on the file.
4. `zip.loadAsync(data)` parses the ZIP central directory (cheap), then the code reads `entry.file("private_textcoin")`. If `entry._data` doesn't carry a usable `uncompressedSize` in the victim's JSZip build/version for this entry type, the size guard never triggers.
5. `entry.async("string")` decompresses the full multi-hundred-MB/GB payload into a JS string, and the process then attempts `JSON.parse(data)` on it, exhausting memory and crashing or freezing the wallet process — denial of service triggered purely by opening a received file.

**Note on evidence limits**: I was unable to further verify from the indexed code exactly where/how `handlePrivatePaymentFile` is invoked in the UI/IPC layer (e.g., whether it's wired to a URI handler or file-open dialog only) beyond the 4 in-file references found in `wallet.js`; the full call sites outside `wallet.js` were not present in the index. If deeper confirmation of the exact triggering surface (UI-only vs. remotely-triggerable via a deep link) is needed, a Devin session with full repository access should be used to trace all callers.
