## Analysis

The NATS advisory describes a **length-parameter inconsistency** (CWE‑409/770): the server checked an expected/declared message size but did not bound the actual memory consumed while decompressing, so a compression bomb could blow past the check and exhaust memory before validation could reject it.

The closest reachable analog in this codebase is the private‑textcoin ZIP handling in `wallet.js`, used to recover privately‑paid textcoins that a private‑payment counterparty sends as a file.

### Root cause

`storePrivateAssetPayload` builds a DEFLATE‑compressed ZIP file containing the private‑chain payload for a textcoin, which is the exact artifact an attacker acting as a private‑payment counterparty controls and hands to a victim wallet: [1](#0-0) 

`handlePrivatePaymentFile` is the counterpart that loads and decompresses that untrusted file: [2](#0-1) 

The size guard only inspects `entry._data.uncompressedSize`, which is a value taken from the ZIP entry's local/central‑directory metadata — i.e. **attacker‑declared**, not a bound enforced during actual decompression: [3](#0-2) 

Immediately after that check, `entry.async("string")` performs the actual DEFLATE decompression of the whole entry with `JSZip`/`pako`, with no incremental cap on the number of bytes produced: [4](#0-3) 

This is structurally identical to the NATS flaw: a size value is checked, but the real decompression path is not independently bounded, so a crafted entry that under‑reports `uncompressedSize` in its header while its DEFLATE stream actually expands to a very large output can bypass the 100 MB gate and force the process to allocate an unbounded string/buffer during `entry.async("string")`.

### Title
Zip “private-textcoin” payload decompression bomb bypasses size check via forged uncompressedSize header - (File: wallet.js)

### Summary
`handlePrivatePaymentFile` gates decompression of an attacker-supplied private-textcoin ZIP entry using the ZIP-header-declared `uncompressedSize`, then unconditionally decompresses the entry with no independent memory bound, mirroring the NATS websocket compression-bomb flaw (CWE‑409/770).

### Finding Description
`storePrivateAssetPayload`/`handlePrivatePaymentFile` implement a file-based private-payment channel where a private-payment counterparty (the sender of a textcoin) produces a ZIP file that the recipient's wallet later opens to claim the coin. The recipient-side code at `wallet.js:2895-2897` trusts the `uncompressedSize` field taken from the ZIP entry metadata to reject "too large" payloads, then calls `entry.async("string")`, which performs the actual DEFLATE decompression through `JSZip`. Because `uncompressedSize` is attacker-controlled metadata and not verified against the real decompressed length before or during the inflate operation, an attacker can craft a ZIP entry whose header declares a small size (e.g., a few KB, well under the 100 MB threshold) while its actual DEFLATE-compressed bit stream expands—using standard zip-bomb techniques—into gigabytes of data once passed through `entry.async`. The size check therefore provides no real protection: it validates a claim, not the outcome of decompression, exactly the class of bug fixed upstream in nats-server (bounding the message check but not the decompression stream itself).

### Impact Explanation
Opening/importing such a malicious textcoin file causes the wallet process to allocate an effectively unbounded string/buffer while decompressing the ZIP entry, exhausting available memory and crashing or hanging the wallet process (denial of service). Because `handlePrivatePaymentFile` is the standard flow used to recover privately-paid textcoins from another party, this puts every wallet user who accepts a private-payment textcoin file from an untrusted counterparty at risk of an out-of-memory crash, disrupting their ability to operate the node/wallet.

### Likelihood Explanation
Exploitation requires no special privileges: any private-payment counterparty (the party that would normally send a legitimate textcoin ZIP) can instead craft and hand over a malicious ZIP with a forged `uncompressedSize` header and a compression-bomb payload. The victim only needs to run the normal recovery/import flow (`handlePrivatePaymentFile`) that the protocol already expects users to perform for textcoins, i.e. no code execution or elevated trust is needed by the attacker.

### Recommendation
Do not rely on the ZIP-declared `uncompressedSize`. Enforce a hard cap during decompression itself, e.g. by using a streaming inflate API that aborts once a fixed number of output bytes (matching the intended payload size, well below 100 MB) has been produced, regardless of what the ZIP metadata claims, before calling `entry.async(...)`.

### Proof of Concept
1. Attacker crafts a ZIP file containing an entry named `private_textcoin` whose local file header/`uncompressedSize` metadata field is set to a small value (e.g., 1 KB), but whose actual DEFLATE-compressed data stream, when inflated, expands to several GB (a classic zip-bomb construction with highly repetitive plaintext, achievable at ~1000:1+ ratios with DEFLATE).
2. Attacker sends/hands this file to the victim as though it were a legitimate private-textcoin payload (mirroring the normal `storePrivateAssetPayload` output format).
3. Victim wallet calls `handlePrivatePaymentFile(fullPath, content, cb)`; the check at `wallet.js:2895-2896` passes because the reported `uncompressedSize` is small.
4. `entry.async("string")` at `wallet.js:2897` decompresses the full bomb payload into memory, causing excessive memory consumption and crashing the wallet process.
