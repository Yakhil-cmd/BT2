### Title
Command-argument `$VAR` interpolation falls back to the Shipit host process's own `ENV`, bypassing the deploy/task environment whitelist - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate`, used to expand `$VARIABLE` references inside shell command arguments defined in a repository's `shipit.yml`, silently falls back to the Shipit application process's real `ENV` for any variable that is not present in the task/deploy's sanitized environment hash. This breaks the same class of invariant flagged in the external report: a value/parameter that is supposed to be constrained by an explicit allow-list (`EnvironmentVariables#permit`, whitelisted `deploy.variables`/`tasks.variables`) is actually used in a context where an unvalidated, broader source of data is substituted in instead.

### Finding Description
`Command#interpolated_arguments` interpolates the shell arguments produced from `shipit.yml` step definitions using the task's merged environment: [1](#0-0) [2](#0-1) 

The actual substitution logic is: [3](#0-2) 

Note the fallback: `@env.fetch(variable) { ENV[variable] }`. `@env` here is the task/deploy's curated environment (`Shipit.env`, `stack.env`, `deploy_spec.machine_env`, and the user-supplied env that already passed `EnvironmentVariables#permit` against an explicit whitelist): [4](#0-3) [5](#0-4) 

Meanwhile, `Command` explicitly strips the *spawned subprocess's* environment down to a sanitized `BASE_ENV`, unsetting any host-process variables that aren't part of the Bundler-clean env: [6](#0-5) [7](#0-6) 

So the codebase deliberately curates two things: (1) which env vars are *permitted* to be supplied by a caller (`EnvironmentVariables.permit`, whitelisted by `deploy.variables`/`tasks.variables`), and (2) which env vars are actually *exported* to the spawned subprocess (`BASE_ENV`, explicitly nulling anything not in the Bundler clean env). `interpolate`, however, is a third, uncontrolled path: it reads directly from the Shipit Ruby process's live `ENV` hash for any `$NAME` token that appears in a step's command-line arguments and isn't already in the curated `@env`. This is the "permitted vs. spawned" binding break called out in scope: the set of variables a repository's `shipit.yml` is entitled to reference (the whitelist) does not equal the set of variables actually resolved and substituted into the executed command line (whitelist ∪ full host process `ENV`).

Any `shipit.yml`/`.shipit/*.yml` `deploy.override`/`deploy.pre`/`deploy.post`/`tasks.*.steps` entry containing a `$SOME_NAME` token will have that token replaced with whatever value the Shipit web/worker process happens to have in its OS environment (e.g., credentials injected via 12-factor-style env-based configuration — database URLs, cache URLs, or other secrets a deployment might set as process environment variables), even though that value was never declared in the whitelist and was never intended to be exposed to deploy scripts. Because `shipit.yml` is read from the repository's working tree at deploy/task time (`DeploySpec::FileSystem`), and for review stacks that tree is the content of an external contributor's pull-request branch when a repository has review stacks enabled with `allow_all` provisioning: [8](#0-7) 

an unprivileged PR author can craft `shipit.yml` steps that reference arbitrary `$VARIABLE` names, causing the interpolated value (sourced from the Shipit host's own process environment) to be embedded in the executed command line and streamed to the task/deploy output, which is readable by anyone with `read:stack` access to that stack.

### Impact Explanation
If the deployment operator configures any secret via process environment variables (a common Rails/12-factor pattern — e.g. database/cache URLs, third-party API keys, or other credentials not otherwise present in `secrets.yml`), this interpolation path can expose that value in task/deploy output logs to any actor who can get a `shipit.yml` executed and can view the resulting output (PR authors on repositories with review stacks enabled, or any user able to read stack task output). This matches the "credential exfiltration" class of impact required by scope, though the specific secret exposed depends entirely on host operator configuration rather than a hardcoded Shipit-managed credential — this is the main source of uncertainty in severity.

### Likelihood Explanation
Exploitability requires: (1) a repository with review stacks enabled and `allow_all`/`allow_with_label` provisioning (or simply a repo maintainer merging a PR with a crafted `shipit.yml`), and (2) the Shipit host process having secret-bearing environment variables not otherwise present in the curated `env` hash. Both are plausible but operator-dependent, and I could not verify from the indexed code whether any Shipit-managed secret (e.g. `GITHUB_TOKEN`, `api_clients_secret`) is ever supplied purely via process `ENV` rather than `secrets.yml`/config — those are explicitly injected into `env` hashes by name (e.g. `GITHUB_TOKEN` in `lib/shipit/stack_commands.rb`/deploy commands), which would already be reachable via `@env.fetch` without needing the `ENV[variable]` fallback at all. This weakens the "guaranteed Critical" claim; the leak is real but its severity is contingent on external deployment configuration I cannot confirm from this index.

### Recommendation
Remove the `ENV[variable]` fallback in `EnvironmentVariables#interpolate` (`lib/shipit/environment_variables.rb:25`) and raise/no-op for any `$VARIABLE` not present in the already-curated task/deploy environment hash, so that command-line interpolation is strictly bound to the same whitelist enforced by `EnvironmentVariables#permit`.

### Proof of Concept
Not independently reproducible from static code alone — exploitation depends on the operator's specific process-environment configuration, which I cannot verify from the indexed files. The code-level root cause (fallback to raw `ENV` in `interpolate`) is confirmed directly by inspection of `lib/shipit/environment_variables.rb:20-27` and its caller in `lib/shipit/command.rb:51-55,81-83,103-105`.

```ruby
    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
```
