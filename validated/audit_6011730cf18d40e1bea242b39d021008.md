### Title
Webhook organization used for signature verification is never bound to the repository/commit the event handler mutates - cross-tenant webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate a webhook against using one field of the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), but the event handlers that subsequently act on the payload use a *different* field of that same untrusted body (`repository.full_name`, or, in the case of `StatusHandler`, no repository field at all — just a raw commit `sha` lookup across the entire installation). Nothing enforces that the organization whose secret validated the signature is the organization that owns the repository/commit actually mutated. This breaks the "organization that authenticated == repository that is written" binding called out in scope.

### Finding Description
`verify_signature` resolves the signer using a value taken from the JSON body itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance configured per-organization, each with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

So a self-service organization admin — someone who legitimately set up their own GitHub App/organization in this Shipit instance and therefore knows (or can view) that organization's `webhook_secret` (`docs/setup.md` explicitly instructs org admins to "keep it in clear on the side") — can compute a valid `X-Hub-Signature` for **any raw JSON body they want**, as long as `repository.owner.login`/`organization.login` in that body is their own org.

The event handlers, however, never re-check that the repository/commit acted upon belongs to that same organization:

- The generic `Handler` base class resolves the target stacks purely from `repository.full_name`, a sibling field of `repository.owner.login` inside the very same attacker-controlled JSON, with no cross-check against the org used for signature verification: [5](#0-4) 

- `PushHandler` uses those `stacks` (i.e. `repository.full_name`) to trigger `sync_github`: [6](#0-5) 

- `StatusHandler` is even more permissive: it does not consult the repository at all, only a bare commit `sha`, matching against **every commit in the whole Shipit installation**, and writes a GitHub-style status onto it: [7](#0-6) 

Because `repository.owner.login` (checked) and `repository.full_name` (acted upon) — or, worse, the commit `sha` (acted upon, unchecked against any repo/org) — are independent, attacker-controlled fields of the same JSON body, an org admin who is only supposed to be trusted for their own organization's webhooks can forge events that are verified with their own secret but whose effects land on a completely different organization's stacks/commits.

### Impact Explanation
This breaks the "organization that authenticated == repository that is written" binding explicitly listed in scope. Concretely:
- Via `PushHandler`, an attacker can force `stack.sync_github` on stacks belonging to a different organization's repository merely by putting that repository's `full_name` in a self-signed payload.
- Via `StatusHandler`, an attacker can forge arbitrary commit statuses (`state`, `context`, `description`, `target_url`) for any commit SHA tracked anywhere in the Shipit instance, regardless of which org/repo it belongs to. Since Shipit uses commit/CI statuses to gate deployability and the merge queue (`commit_status`, `deployable_status`, `merge_status` are first-class hook events per `Hook::EVENTS`), forging a "success" status for a victim organization's commit can be used to unblock or misrepresent deploy/merge safety checks it does not control.

This matches the "unauthorized deploy" / cross-repository-writes impact bucket in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant deployment of this engine (multiple organizations/GitHub App configs sharing one Shipit instance, which the `Shipit.github(organization:)` lookup and `GithubOrganizationUnknown` handling are explicitly built to support). Any org admin who is entitled to configure their own org's GitHub App/webhook secret already has everything needed to compute a valid signature for a payload that lies about the target repository/commit — no GitHub-side spoofing, no `ApiClient` token, and no privileged Shipit account is required, only knowledge of their own org's `webhook_secret`, which is a credential every onboarded organization owner is handed.

### Recommendation
- After verifying the signature, do not trust any organization/repository identifiers taken from the same request body for authorization decisions. Instead, derive the acting organization strictly from the verified `GithubApp`/installation context and require that `repository.owner.login` / `repository.full_name`'s owner segment match the resolved organization before dispatching to handlers.
- In `Handler#stacks`/`repository_name`, and specifically in `StatusHandler`, scope the affected commit/stack lookup to the repository whose organization matches the one that produced a valid signature (e.g., pass the verified organization down to handlers and filter `Commit`/`Stack` queries by repository ownership, not by SHA/full_name alone).
- Consider maintaining a canonical repository→organization mapping in Shipit and rejecting payloads where the declared `repository.full_name` does not belong to the organization identified for signature verification.

### Proof of Concept
1. Register/administer "OrgA" as an organization in a multi-tenant Shipit deployment; note its configured `github.webhook_secret` (an org admin is expected to know this per `docs/setup.md`).
2. Craft a JSON body for a `status` event:
```json
{
  "sha": "<victim-commit-sha-belonging-to-OrgB-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using OrgA's `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: status` and the header above.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and the signature validates successfully because it was computed with OrgA's own secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — which matches OrgB's commit regardless of the organization used to authenticate — and writes an attacker-chosen status onto it, even though the attacker only controls OrgA.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
