### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery in multi-GitHub-App deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the request's HMAC signature against using `repository_owner`, derived from the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) [2](#0-1)  However, once the signature passes, the actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, used transitively by `PushHandler`, and the various `PullRequest::*Handler`s) resolve the repository/stack to mutate using a *different, independently attacker-controlled* field: `repository.full_name`. [3](#0-2)  `StatusHandler` and `MembershipHandler` don't even check the owning organization at all — they act on any commit `sha` or `organization.login` present in the body. [4](#0-3) [5](#0-4)  Shipit explicitly supports configuring multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, exactly the deployment mode where this binding break matters. [6](#0-5) [7](#0-6) 

### Finding Description
The equality that should hold is: **organization whose secret authenticated the webhook == organization owning the repository/stack the handler writes to**. This engine breaks that binding.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and uses it purely to pick which `GitHubApp` (and therefore which `webhook_secret`) is used to HMAC-verify the raw body. [1](#0-0) [2](#0-1) 
- Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire, attacker-controlled JSON body* to handlers with no re-validation tying it back to `repository_owner`. [8](#0-7) 
- `Handler#stacks`/`#repository_name` (base class used by `PushHandler` and PR handlers) looks up the target `Repository` via `payload.dig('repository', 'full_name')` — a completely separate field from the one used for signature-app selection. [3](#0-2) 
- `Repository.from_github_repo_name` simply splits `owner/name` from that string and does a DB lookup with no relation to which GitHub App/organization verified the request. [9](#0-8) 
- `StatusHandler#process` is even more permissive: it matches on `Commit.where(sha: params.sha)` across the whole database, with zero repository/organization scoping at all, and directly calls `commit.create_status_from_github!(params)`. [4](#0-3) 

Because a `sha1=` HMAC signature is computed over the raw JSON body using the secret configured for whatever organization the attacker names in `repository.owner.login`/`organization.login`, an attacker who is the maintainer/owner of *any one* organization configured in Shipit's multi-app `secrets.github` map (and therefore knows that organization's `webhook_secret`, e.g. because they set it themselves when creating their own GitHub App installation as documented in `docs/setup.md`) can:
1. Set `repository.owner.login` (or `organization.login`) to *their own* org so `verify_signature` selects the `GitHubApp` whose secret they know.
2. Set `repository.full_name` (for push/PR events) or `sha` (for status events) to point at a **victim** repository/stack/commit belonging to a completely different, unrelated organization also configured in the same Shipit instance.
3. Compute a valid `X-Hub-Signature` over the full crafted body using their own known secret.

The signature check in `GitHubApp#verify_webhook_signature` only confirms the body was signed with *some* configured secret — it never confirms that secret belongs to the organization the payload claims to be mutating. [10](#0-9) 

### Impact Explanation
This lets an attacker who legitimately controls one organization's GitHub App forge status/push/pull_request/membership events for a different, victim organization's repositories tracked by the same Shipit instance:
- Forge a `status` webhook (`state: success`) for an arbitrary commit SHA belonging to a victim stack, since `StatusHandler` has no owner scoping at all — this can flip a commit's CI state to `success`/`deployable?`, potentially triggering continuous deployment or bypassing required-status gating on the merge queue (`reject_unless_mergeable!`/`any_status_checks_missing?` rely on this same status data). [11](#0-10) 
- Forge `push` events causing `stack.sync_github` to run against a victim stack. [12](#0-11) 
- Forge `pull_request` events (opened/closed/labeled) causing archival/unarchival/provisioning of victim review stacks. [13](#0-12) 

Falsifying a "success" CI status that feeds into automatic deploy/merge decisions for a repository the attacker does not control constitutes an unauthorized-deploy-class impact, matching the Critical bucket ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability requires the attacker to control at least one organization configured under Shipit's `github` multi-app secrets map alongside the victim organization — this is a realistic scenario for shared/hosted Shipit instances serving multiple orgs (the feature this engine explicitly documents and tests, see `test/dummy/config/secrets_double_github_app.yml` and `Shipit#github_organizations`). [14](#0-13)  No GitHub App private key, Shipit session, or `ApiClient` token is needed — only knowledge of one's own configured webhook secret and the ability to send an HTTP POST to the public `/webhooks` endpoint (`skip_before_action :verify_authenticity_token`). [15](#0-14) 

### Recommendation
After signature verification, re-derive the organization from the *same* field(s) trusted for verification and enforce that every entity resolved by a handler (`Repository.from_github_repo_name`, `Commit` lookup in `StatusHandler`, `Team`/`organization` in `MembershipHandler`) actually belongs to that verified organization before mutating any state — e.g., pass the verified organization into `Handler.call` and have `Repository.from_github_repo_name`/`Commit.where(sha:)` scope by `owner == verified_organization`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps for orgs `attacker-org` and `victim-org` (as in `docs/setup.md`'s "Using Multiple Github Applications" section), each with its own `webhook_secret`. The attacker installs/owns the `attacker-org` GitHub App and thus knows its `webhook_secret`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-stack-head-sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged "success" status onto the victim's repository's commit. [4](#0-3) 

I could not fully verify downstream automatic-deploy triggering behavior (e.g. exact continuous-deployment job wiring) within the indexed context, so the precise blast radius of the forged status (auto-deploy vs. only unblocking merge-queue gating) should be confirmed by a full read of `ContinuousDeliveryJob` and `Commit#create_status_from_github!`/`deployable?` — this is noted as an area not completely traced due to index scope limits.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
