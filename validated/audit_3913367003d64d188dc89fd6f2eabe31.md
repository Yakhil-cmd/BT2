### Title
AAs permanently freeze private-asset funds sent to them because they can never compose a valid outgoing payment for that asset - ([File: aa_composer.js])

### Summary
Any unprivileged user can send a private asset (e.g. blackbytes-style asset with `is_private: true`) to an Autonomous Agent address as part of a trigger unit. The AA composer explicitly refuses to build any outgoing payment message for a private asset because it lacks the spend-proof material needed for private-payment validation, and it does not attempt any alternate return path (e.g., private payment chain) for the received funds. The result is functionally identical to the reported bug: funds sent to a payable/receiving contract can never be withdrawn.

### Finding Description
When an AA composes its response messages, for every payment message it iterates through and loads the asset info via `storage.loadAssetWithListOfAttestedAuthors`. If the asset is private, the composer immediately fails that message with the hardcoded error `"sending private asset from AA"`: [1](#0-0) 

This means an AA definition can never legitimately include a `payment` message that sends out a private asset — any attempt is rejected during response composition, regardless of what the AA author's oscript intended. There is no fallback mechanism (such as constructing a private payment chain to hand back to the sender) analogous to a "withdrawETH" function; the composer simply treats it as an error condition.

Critically, nothing at the trigger level prevents a user from sending a private asset to an AA in the first place — a payment message with a private asset in `trigger.outputs` is a normal, valid input to `handleTrigger`. Once such a trigger is processed, the AA's internal balance accounting (`assocBalances`) will record the private-asset balance, but the AA logic has no way to ever pay it back out, since any message app: 'payment' referencing that asset will always be rejected by the check above.

If the AA bounces (insufficient bounce fees, or explicit `bounce()` calls in the oscript), the bounce-message generator in `handleTrigger`/`bounce()` also builds `payment` messages for every asset in `trigger.outputs`, including private ones: [2](#0-1) 

This bounce path constructs the same disallowed private-asset payment message and would hit the identical `"sending private asset from AA"` rejection deep inside `sendUnit`'s asset-processing loop, meaning even the AA's own bounce mechanism cannot return the private funds to the sender.

### Impact Explanation
Any private-asset funds transferred to an AA address are permanently locked. Neither the AA's designed business logic (a payment message crafted by the AA author to move balances) nor its automatic bounce-refund mechanism can construct a valid unit sending that asset back out, because the composer treats all outgoing private-asset payments from an AA as an unconditional error. This is a direct analog of the reported "funds stuck, no withdrawal path" bug class — it is AA fund freezing reachable by any ordinary user simply sending a private-asset payment to an AA address, with no privileged access required.

### Likelihood Explanation
This is trivially reachable: a private asset only needs to exist (assets with `is_private: true` are a first-class, commonly used feature of the protocol, e.g., blackbytes) and any user can send such an asset to any AA address as part of a normal trigger payment. No cooperation from the AA owner, no bug in the AA's oscript, and no special network conditions are required — the freezing happens purely as a structural limitation of the AA composer's payment-composition logic.

### Recommendation
- At validation time (`aa_validation.js` or trigger acceptance in `aa_composer.js`), reject/ignore triggers that include private-asset outputs to an AA address, so private funds can never enter an AA's balance in the first place, or
- Implement an explicit refund/withdraw path for private assets accidentally sent to an AA (e.g., automatically bouncing the *entire* unit before balances are updated when a private asset is detected among `trigger.outputs`), ensuring the sender's private payment chain is preserved and returned rather than silently absorbed into an unspendable AA balance.

### Proof of Concept
1. Define/issue a private asset `P` (`is_private: true`) via a normal `asset` message.
2. Deploy any AA that accepts payments and, in its business logic, would normally try to pay back or forward the asset it received (e.g., a simple echo/bank-style AA as seen in the `a_bank_without_percent.oscript`/`order_book_exchange.oscript` withdraw patterns used elsewhere in the test suite: [3](#0-2) ).
3. Send a trigger unit to the AA with `payload.asset = P` in the outputs.
4. Observe that `handleTrigger` → `sendUnit` rejects any `payment` message referencing asset `P` with `"sending private asset from AA"` at aa_composer.js:1329-1330, and the automatic `bounce()` path (aa_composer.js:930-944) constructs the same kind of message and would hit the identical rejection when reaching `sendUnit`'s per-asset loop — leaving the private-asset balance permanently stuck in the AA's state with no code path capable of emitting a valid unit to move it out.
