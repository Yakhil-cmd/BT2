### Title
Cross-organization team-membership forgery via unbound `github_id` lookup - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `params.team.id` (the numeric GitHub team id) without ever checking that this id actually belongs to `params.organization.login`. Because webhook signature verification is scoped per-organization (using the sender's own `organization.login`/`repository_owner` to pick the `webhook_secret`), an attacker who legitimately owns a Shipit-configured organization can sign a forged `membership`/`team` "added" event with their own valid secret while setting `team.id` to a privileged team's `github_id` and `organization.login` to their own org, causing `team.add_member(member)` to add an attacker-controlled `User` to the existing privileged `Team` row.

### Finding Description
The binding that must hold is: `params.team.id` (the `github_id` used to locate/mutate the `Team` row) `==` the id of a team that actually belongs to `params.organization.login`, as authenticated by the webhook signature for that organization.

Trace:
- `WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository_owner`, which falls back to `params.dig('organization', 'login')` for org-level events like `membership`: [1](#0-0) [2](#0-1) . This proves only that the request was signed by *some* configured organization's secret (the attacker's own org, if they own a Shipit-registered organization) — it says nothing about whether the `team` object inside the payload truly belongs to that organization.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`, looking up purely by numeric `github_id`. If a `Team` row with that `github_id` already exists (e.g., a privileged team listed in `Shipit.github_teams`), the block that would set `team.organization = params.organization.login` is **not** run (it only runs on create), so the existing (privileged) team is returned unchanged, and then `team.add_member(member)` is called unconditionally for the `'added'` action: [3](#0-2) .
- `Team#add_member` performs no organization check either: [4](#0-3) .
- Authorization elsewhere (`User#authorized?`) trusts `Team` membership directly, comparing against `Shipit.github_teams` (teams resolved once at boot via `Team.find_or_create_by_handle`): [5](#0-4) [6](#0-5) . A `Membership` row created via the forged webhook is indistinguishable from a legitimate one and grants the attacker's `User` record standing in a privileged team.

No existing guard closes this gap: `verify_signature` authenticates the org identity of the sender but the handler discards that identity when reusing an existing `Team` row; there is no re-validation that `params.organization.login == team.organization` before mutating membership.

Attacker requirements: they must own (or control the webhook secret of) at least one organization that Shipit is configured to receive webhooks from (`Shipit.github(organization: ...)` config present for that org) — this is plausible in multi-tenant/Shipit-for-many-orgs deployments. They must also know the numeric `github_id` of a privileged team (obtainable via GitHub's team API if not private, via a previous webhook they were copied on, or by brute-forcing small sequential ids, none of which requires any Shipit secret).

### Impact Explanation
A successful forged request causes `Membership.exists?(team: privileged_team, user: attacker_user)` to become true, effectively an authentication/authorization bypass: the attacker gains membership in a team listed in `Shipit.github_teams`, which is used by `User#authorized?` to gate access into Shipit itself (stacks, deploys, rollbacks, merges). This is repeatable against any privileged team whose `github_id` becomes known, and is only bounded by which organizations are configured in Shipit's `secrets.github` — in a multi-org Shipit deployment, an org with low trust can escalate a user into a fully privileged org's team. This matches the "Critical: authentication bypass" / "High: escalation into `Shipit.github_teams` authorization" categories.

### Likelihood Explanation
Preconditions: (1) Shipit configured with more than one GitHub organization (multi-tenant `secrets.github` config, each with its own `webhook_secret`), one of which is attacker-controlled and lower-trust than the privileged org; (2) attacker must discover the numeric `github_id` of a team listed in `Shipit.github_teams`. Cost to the attacker is low once these two conditions are met — no Shipit secrets, sessions, or API tokens are needed, only their own legitimate webhook secret for their own organization. In a single-organization Shipit deployment (one `webhook_secret` for the whole instance) this specific cross-org vector collapses, since the attacker would already need to control that org's webhook secret to sign anything — but the underlying missing binding (no organization check on `Team` lookup) remains a latent bug that manifests as soon as more than one organization/webhook_secret is configured, which the `github_app_config`/`github_organizations` machinery in `lib/shipit.rb` explicitly supports.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team`'s `organization` matches `params.organization.login` (case-insensitively) before performing any mutation; if it does not match, raise/drop the event instead of proceeding. E.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  unless team.organization.casecmp?(params.organization.login)
    raise ArgumentError, "Team #{params.team.id} organization mismatch: expected #{team.organization}, got #{params.organization.login}"
  end
  team
end
```

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual addition)
test "membership handler must not attach members to a team from a mismatched organization" do
  privileged_team = Team.create!(github_id: 999, name: 'Core', slug: 'core', organization: 'privileged-org', api_url: 'https://api.github.com/teams/999')

  params = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Core', 'slug' => 'core', 'url' => 'https://api.github.com/teams/999' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(params).process

  attacker = Shipit::User.find_by(login: 'attacker')
  # Binding check: params.team.id (999) must belong to params.organization.login ('attacker-org'),
  # but privileged_team.organization == 'privileged-org' != 'attacker-org'
  assert_not Shipit::Membership.exists?(team: privileged_team, user: attacker),
             "attacker was added to a privileged team belonging to a different organization"
end
```
Currently this assertion fails (membership is created), demonstrating the missing organization binding in `find_or_create_team!`. [7](#0-6)
