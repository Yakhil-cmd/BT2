### Title
Webhook signature is verified against the wrong GitHub organization, allowing repository-owner spoofing to bypass HMAC verification - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check against based on an **unauthenticated, attacker-controlled field of the very payload being verified** (`repository.owner.login` / `organization.login`), rather than binding the signature check to a fixed, pre-known organization. Combined with `GitHubApp#verify_webhook_signature` returning `true` when the selected organization has no `webhook_secret` configured, an attacker can choose a `repository_owner` value that maps to an organization/app config without a `webhook_secret`, causing the signature check to be trivially satisfied, while the rest of the payload (event handlers) freely process the `repository.full_name` field, which need not belong to that organization at all.

### Finding Description
The engine supports multi-organization / multi-GitHub-app configuration, keyed by organization name via `Shipit.github(organization:)`: [1](#0-0) 

The webhook signature verification looks up the app/config to use **from the payload itself**: [2](#0-1) 

Specifically, `repository_owner` is read straight from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), and that value is used to pick which `GitHubApp` — and therefore which `webhook_secret` — is used to verify the HMAC over the same body: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` is a no-op (`return true unless webhook_secret`) whenever the selected app config has no secret configured: [5](#0-4) 

Configuration examples in this codebase show that `webhook_secret` is commonly left `nil` for a given org: [6](#0-5) 

Meanwhile, the actual event-processing code (job enqueuing, repository/stack resolution) trusts `repository.full_name` from the same payload independently of which org's secret was used to "verify" it: [7](#0-6) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization whose webhook_secret authenticated the request == organization that owns the repository the handlers act on`.

Before the report's underlying bug class (and as an analog here): a payload can claim `repository.owner.login = "org-with-no-secret"` for the purpose of signature verification, while `repository.full_name` points at `"org-with-a-secret/victim-repo"` for the purpose of business logic (`GithubSyncJob`, commit status updates, `push`/`status`/`check_suite`/`membership`/`pull_request` handlers, etc.). Since verification is scoped to the *owner org field*, not to the actually-affected repository/stack, an attacker who knows (or guesses) that at least one configured GitHub app in the multi-org config has no `webhook_secret` (a state explicitly supported and exemplified in this repo's own sample secrets file) can craft a payload that:
1. Sets `repository.owner.login` (or `organization.login`) to that secret-less org, so `verify_webhook_signature` short-circuits to `true` unconditionally.
2. Sets `repository.full_name` to a real, tracked stack belonging to a *different*, properly-secured organization.

This bypasses HMAC authentication for events that end up mutating state for repositories/stacks the attacker does not control — e.g. forging `push` events to trigger `GithubSyncJob` for the target stack, forging `status`/`check_suite` events to fabricate CI state used for merge/deploy safety checks, or forging `membership`/`team` events to add/remove team memberships (`Membership.count` changes shown in the test suite) that back `Shipit.github_teams` authorization.

### Impact Explanation
This crosses the "unauthenticated read/write of stack state" and "escalation into `Shipit.github_teams` authorization" boundaries called out as High-severity impacts: forged, unauthenticated webhook events can (a) manipulate commit/CI status used to gate deploy safety checks on a legitimate stack, (b) trigger sync jobs against a legitimate repository/stack without any valid signature, and (c) forge `membership`/`team` events that alter `Team`/`Membership` records feeding directly into `Shipit.github_teams`-based authorization (`app/controllers/concerns/shipit/authentication.rb#force_github_authentication`). This is only exploitable in the multi-organization GitHub app configuration mode (`github_default_organization` non-nil) where at least one configured organization lacks a `webhook_secret` — a configuration explicitly documented/sampled in this repository (`config/secrets.development.shopify.yml`). In single-app mode (the common case, `github_default_organization` nil), this specific spoofing vector does not apply since there is only one, statically-chosen config.

### Likelihood Explanation
Requires: (1) the deployment to use the multi-organization GitHub app config schema, and (2) at least one configured organization to have `webhook_secret: nil` (e.g., during onboarding of a new org before its secret is set, which the codebase's own sample config demonstrates as a normal state). Given that condition, exploitation requires no credentials — only knowledge/guessing of an org name in the config without a secret and the target stack's `repository.full_name`, both of which are often discoverable (public repos, org listings).

### Recommendation
Bind signature verification to a fixed, pre-determined organization/app config rather than one derived from the unauthenticated payload — e.g., resolve the target `Repository`/`Stack` first (from routing or a signed/trusted source), determine its owning organization from that trusted record, and verify the signature using that organization's `GitHubApp`. Additionally, treat a missing `webhook_secret` as "reject" rather than "accept" for any organization used in a multi-org context, or require `webhook_secret` to be mandatory once multi-org mode is enabled.

### Proof of Concept
Conceptual request against `POST /github_authentication`-adjacent webhook endpoint (`WebhooksController#create`):
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<any value, or omitted-equivalent since secret is nil>
Body:
{
  "repository": { "owner": { "login": "org-without-secret" }, "full_name": "victim-org/victim-repo" },
  "after": "<attacker-chosen sha>",
  ...
}
```
`repository_owner` resolves to `"org-without-secret"`; `Shipit.github(organization: "org-without-secret").verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb#L76-L83` because `webhook_secret` is blank for that org. `Shipit::Webhooks.for_event('push')` then runs handlers keyed off `repository.full_name` = `"victim-org/victim-repo"`, enqueuing `GithubSyncJob` for that stack with attacker-chosen `after` sha, despite the request never being validated with `victim-org`'s actual `webhook_secret`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
