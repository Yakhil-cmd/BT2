### Title
Attacker-controlled swap route bytes inject arbitrary contract calls into the caller's signed authorization tree, draining unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The SQL-injection bug class (user-supplied `column`/`order` values interpreted as executable query structure, bypassing a sanitization layer) maps directly onto the `swap: StrategySwap` parameter of the controller's router strategies. Like an unsanitized ORDER BY clause, the route bytes are opaque attacker-controlled input that the protocol interprets as a program: the controller forwards them verbatim to the swap aggregator, which invokes whatever pool/token addresses the payload names. Because venue calls execute inside the caller's `require_auth` tree, a malicious "pool" in the route can inject an extra `token.transfer(victim, attacker, x)` that simulation records under the victim's `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` auth entry. If the victim signs the simulated tree — the normal wallet flow — the injected transfer executes and steals tokens the protocol never touched.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 33–38) authorizes exactly one input-token transfer to the router and then calls `router.execute_strategy(&controller, &amount_in, swap)` with fully caller-controlled `swap` bytes; the only validation is `!swap.is_empty()` and post-hoc balance deltas (`RouterOverspend`, `NoSwapOutput`, lines 42–54, 75–83). There is no allowlist or structural check on the pools, tokens, or venues embedded in the route. The router, per its execution model, calls `env.invoke_contract(&hop.pool, "swap", ...)` on whichever addresses the payload names (`contracts/swap-aggregator/src/venues/aquarius/pool.rs:34`), so arbitrary attacker-deployed code runs on the call stack below the caller's authorization. `docs/explanation/threat-model.md` (lines 154–165) confirms there is no venue allowlist and that a transfer such code makes from the caller "executes if the caller signs that tree," with the loss being "the caller's wallet, not the routed amount." The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end: `RogueHopPool.swap` calls `token::Client::transfer(victim → attacker)` (lines 62–71), simulation records it as a child of Alice's `swap_collateral` entry (lines 194–227), and signing that tree moves her entire unrelated wallet balance to the attacker while she still receives a fair ETH output (lines 258–268).

### Impact Explanation
Theft of user funds. Any token held in the victim's wallet — including assets the protocol never lists — can be transferred to the attacker within the same transaction, for any amount the victim holds, with the swap itself still settling honestly so no controller-side check reverts. The injected call is not bounded by the routed input, the payload `min_out`, or the final health-factor gate; `strategy_finalize` only sees a healthy account holding the swapped collateral.

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-crafted route. Routes are opaque XDR blobs produced by an off-chain quote service (`skills/xoxno-lending-contracts/composing.md:39–40` instructs integrators "do not construct StrategyPayload on-chain"), so a compromised or malicious quoting path, phishing UI, or a pasted route can deliver the payload. The victim's wallet will sign the simulated auth tree, which legitimately contains nested children for an honest swap, so the extra `transfer` child is not obviously distinguishable to a non-expert signer. The threat model explicitly assigns mitigation to clients decoding the tree, meaning the contracts themselves provide no protection — the injected structure is faithfully interpreted, mirroring the CVE where `safeSqlParse` is bypassed. Affected entrypoints: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and direct `router.execute_strategy` calls.

### Recommendation
Do not let route-selected code ride on the user's auth. Options: maintain an allowlist of recognized venue pool contracts (set via governance) and have the controller or router reject hops naming unlisted pools; or execute the venue call from a context where the caller's auth is not implicitly in scope — e.g., pull the input into router custody first, then have the router settle hops exclusively via `authorize_as_current_contract` invoker auth so pool code cannot `require_auth` the end user. At minimum, controller-side documentation/SDK (`verifyRouteBytes`/`verifyRoutePayload`) should simulate and refuse any signed auth tree whose children exceed the single expected input transfer, and wallets should hard-fail on unexpected sub-invocations.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies 10,000 USDC and holds `WALLET_BALANCE` of an unlisted token. Attacker deploys `RogueHopPool` hard-coded with `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` (lines 56–71).
2. Attacker builds a route `USDC → ETH` whose hop pool is `RogueHopPool` and `min_out` a fair ETH amount (lines 111–125).
3. Alice submits `swap_collateral(alice, account_id, USDC, SWAP_IN, ETH, route)`. Recording-mode simulation shows the auth tree her wallet must sign contains `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` nested under her `swap_collateral` entry (lines 194–222).
4. Signing that tree executes the theft: `balance(alice) = 0`, `balance(attacker) = WALLET_BALANCE`, and Alice still receives the full `FAIR_OUT_ETH` collateral — every controller risk and settlement check passes (lines 224–226, 265–268).
5. Control: with an honest tree (no rogue child) the host rejects the transfer and the whole call rolls back (lines 239–256), proving the loss is enabled purely by the route injecting foreign code under the caller's authorization.
