### Title
Zip-bomb resource exhaustion via unchecked declared size before decompression of private textcoin payload - (File: wallet.js)

### Summary
`handlePrivatePaymentFile()` in `wallet.js` unzips an attacker-suppliable private-textcoin file using `JSZip`, enforcing a 100 MB cap only against the zip entry's declared `uncompressedSize` metadata field before calling `entry.async("string")` to actually inflate the data, mirroring the websocket-driver flaw of checking a size value from the compressed-message metadata instead of the true post-decompression size.

### Finding Description
When a wallet receives a private-asset textcoin (a private payment counterparty flow), it calls `handlePrivatePaymentFile(fullPath, content, cb)`, which loads the file into a `JSZip` object and checks: [1](#0-0) 
```

    const entry = zip.file("private_textcoin");
    if (!entry)
        return cb("missing private_textcoin entry in zip");
    if (entry._data && entry._data.uncompressedSize > 100 * 1024 * 1024)
        return cb("private_textcoin entry is too large");
    entry.async("string").then(function(data) {
```
`entry._data.uncompressedSize` is a value taken from the zip's local file header / central directory metadata, which is attacker-controlled and not cryptographically bound to the actual compressed stream. This is analogous to the websocket-driver bug where the resource limit is checked against a size field describing the message before decompression rather than the actual decompressed size produced by `entry.async("string")`. An attacker can construct a zip entry whose declared `uncompressedSize` is small (passing the check) while the actual compressed payload, when inflated by `entry.async("string")`, expands to an arbitrarily large amount of data (a classic "zip bomb"), because the check happens against untrusted declared metadata rather than the real, monitored output size of the decompression call.

This file is produced with `storePrivateAssetPayload()` (using `JSZip` DEFLATE compression) and is meant to be shared as a private textcoin between wallets — i.e., it is data that one private-payment counterparty hands to another, exactly the "private-payment counterparty" reach the scope calls out. [2](#0-1) 

### Impact Explanation
A malicious counterparty could craft a private-textcoin zip file whose declared `uncompressedSize` passes the 100 MB gate but which decompresses into a far larger amount of data in memory (or repeatedly, since the code fully materializes the string with `entry.async("string")` before any further processing). This can exhaust process memory/CPU on the recipient wallet, crashing or hanging it while it attempts to import a private payment — a resource-exhaustion condition consistent with CWE-770, delivered through a normal, unprivileged private-payment exchange path rather than any network/hub/malicious-peer mechanism.

### Likelihood Explanation
Any party who can send another user a "textcoin" file (a standard private-payment sharing mechanism in the wallet, e.g. via email/link/file-share) can trigger this path merely by crafting the zip's central-directory metadata to differ from the true compressed payload size — no privileged access, hub cooperation, or network interaction is required, only that the target opens/imports the received textcoin file.

### Recommendation
Do not trust `entry._data.uncompressedSize` as the enforcement mechanism. Instead, enforce the size limit against the actual bytes produced during decompression — e.g., stream `entry.internalStream("uint8array")` (or `nodebuffer`) and abort as soon as the accumulated output exceeds the configured cap, rather than checking pre-decompression/declared metadata before calling `entry.async(...)`.

### Proof of Concept
1. Create a ZIP file with an entry named `private_textcoin` whose central-directory/local-header `uncompressedSize` field is manipulated to report a small value (e.g., 1 KB) while its DEFLATE-compressed data stream actually decompresses to hundreds of MB/GB (a standard zip-bomb construction).
2. Send this file to a victim as a "private textcoin" (the normal sharing flow for `storePrivateAssetPayload`/`handlePrivatePaymentFile`).
3. When the victim's wallet imports it, `entry._data.uncompressedSize > 100 * 1024 * 1024` evaluates false (declared size is small), so the check at wallet.js:2895 passes.
4. `entry.async("string")` at wallet.js:2897 fully inflates the real, much larger payload into memory, causing excessive memory/CPU consumption on the victim's device.
