### Title
Webhook signature verification is bound to `repository.owner.login`, but write path uses unrelated `repository.full_name` — allowing cross-organization commit-status/sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, read from `params.dig('repository', 'owner', 'login')` [1](#0-0) . Every webhook `Handler` (used by `StatusHandler`, `PushHandler`, `CheckSuiteHandler`, etc.) instead resolves the target repository/stacks using a completely different field: `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing enforces that these two independently attacker-supplied JSON fields refer to the same repository/organization.

### Finding Description
Shipit supports multi-tenant configuration where several GitHub organizations, each with its own `app_id`/`webhook_secret`, can be registered against a single Shipit instance (see `config/secrets.development.example.yml` multi-org example). For any inbound webhook, `verify_signature` does:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This means the org whose secret is used to *authenticate* the request is chosen from a field the attacker fully controls in the raw JSON body, before the signature is validated. Once validated, the entire `params` hash (including the untouched `repository.full_name` and other fields) is passed unmodified to the handlers:

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers determine *which repository's data gets mutated* using a different, unrelated field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`StatusHandler#process` looks up commits by SHA globally (not even scoped by repository) and writes a status: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . `PushHandler#process` and `CheckSuiteHandler#process` both scope through `stacks`, which is keyed off `repository.full_name` [5](#0-4) [6](#0-5) .

**The binding that breaks (the direct analog of the reported bug):** the equality the system implicitly assumes is
`organization authenticated by signature (repository.owner.login) == organization that owns the repository actually written (repository.full_name)`.
Just as the DEX finding let an attacker manipulate the *price input* (pool spot price) independently from the *actual trade effect*, here an attacker who administers one org onboarded to the shared Shipit instance (and therefore legitimately knows that org's `webhook_secret`, since org admins configure it themselves when creating their GitHub App) can set `repository.owner.login` to their own org (to pass signature verification) while setting `repository.full_name`, `sha`, `state`, `ref`, `after`, `check_suite.head_sha/head_branch` to point at a victim repository/stack hosted on the same Shipit instance. Signature verification only proves "this HMAC was computed with org A's secret" — it proves nothing about the actual repository content of the payload.

### Impact Explanation
By forging a `status` event this way, an attacker with knowledge of only their own org's webhook secret can call `Commit#create_status_from_github!` to write an arbitrary CI status (e.g., `state: "success"`) onto any commit SHA belonging to another organization's stack tracked by the same Shipit instance — without ever having credentials, GitHub App access, or write access to that target repository. Because Shipit stacks commonly gate `continuous_deployment` and deployability on commit statuses, this can be leveraged to make an unreviewed/malicious commit appear deployable, contributing to an unauthorized deploy. It can similarly forge `push`/`check_suite` events to trigger `stack.sync_github` or check-run refresh cycles for a repository the attacker's org has no authorization over. This crosses a repository/organization trust boundary using only a credential (webhook secret) legitimately scoped to a different, unrelated tenant — matching the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
This requires the attacker to control (as an org admin) at least one GitHub organization/App that is configured in the same shared Shipit deployment as the victim (a realistic scenario for any shared/multi-tenant Shipit instance, which the engine explicitly supports via its multi-org config format). No access to the victim org, victim GitHub App, or Shipit application credentials is needed — only the ability to POST a JSON body with a valid HMAC computed from a secret the attacker legitimately possesses. This is a moderate-likelihood, config-dependent (multi-org) but code-level flaw, since the vulnerable binding exists unconditionally in `WebhooksController` and `Handler` regardless of deployment size.

### Recommendation
After signature verification succeeds for organization X, validate that `repository.owner.login` (or `organization.login`) used for verification actually matches the owner of `repository.full_name` used by the handlers, and reject the webhook otherwise. Alternatively, resolve the target repository/stack strictly from the verified organization's own repositories, never from an independently attacker-suppliable field in the same JSON body.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs: `attacker-org` (attacker is admin, knows its `webhook_secret`) and `victim-org` (hosts the target stack/commit).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": {
    "owner": {"login": "attacker-org"},
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks`.
4. `WebhooksController#repository_owner` resolves to `attacker-org`; `verify_signature` fetches `Shipit.github(organization: 'attacker-org')` and validates successfully against the attacker's own known secret [7](#0-6) .
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — matching the real commit in `victim-org/victim-repo` — and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto a victim commit the attacker never had access to [4](#0-3) .
