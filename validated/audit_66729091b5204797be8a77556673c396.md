## Title
Missing `return` after malformed private-payload hash failure causes double `cb()` invocation and re-processing of a deleted private-payment record in `handleSavedPrivatePayments` - (File: network.js)

### Summary
`network.js`'s `handleSavedPrivatePayments()` re-processes queued private payment chains (`unhandled_private_payments`) that were previously posted by any peer/paired device. In the inner `validateAndSave()` closure, when the head private element's `payload` is malformed such that `objectHash.getBase64Hash()` throws, the `catch` block deletes the row and invokes the `async.each` iteratee callback `cb()`, but execution does **not** `return` — the function falls through and unconditionally re-invokes `privatePayment.validateAndSavePrivatePaymentChain()` on the same already-"cleaned up" record, which independently calls `deleteHandledPrivateChain(..., cb)` again on its `ifOk`/`ifError` path. This is the logic-level analog of the reported NanoMQ bug: malformed properties in an untrusted payload trigger premature cleanup of a resource (deletion of the DB row / completion of the iteratee) while a stale reference to that same resource keeps being used afterward, invoking the completion callback a second time.

### Finding Description [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

The head element's `payload` (attacker-controlled — this data originates from a private-payment chain that any peer, AA-triggered private asset transfer, or paired device can post via `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` and is persisted verbatim as JSON in `unhandled_private_payments.json`) can be crafted so that `objectHash.getBase64Hash()` throws (e.g., non-serializable/invalid structure). This is analogous to "invalid MQTTV5 properties" in the original report: malformed input fields drive an error path that performs premature resource cleanup.

`deleteHandledPrivateChain()` (`network.js:2523-2527`) issues a `DELETE FROM unhandled_private_payments ...` and calls `cb()` — the completion signal for this `async.each` item — freeing/finalizing that logical unit of work. [2](#0-1) 

Because there is no `return` statement after the `catch` block, control flow continues past it and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same `arrPrivateElements`/row that was just marked "handled" and deleted. That call's `ifOk`/`ifError` handlers each call `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` again (`network.js:2486`, `network.js:2495`), invoking the shared `cb` for the same `async.each` element a second time. [3](#0-2) 

Double-invoking an `async.each` iteratee callback is undefined/dangerous behavior in the `async` library: it can cause the final callback (`function(){ unlock(); ... }` at `network.js:2512-2517`) to fire prematurely or multiple times, releasing the `"saved_private"` mutex lock early while the queue is still logically "in use," and racing concurrent invocations of `handleSavedPrivatePayments()` against each other over the same connection/lock state — the message-handling analog of a use-after-free where a freed structure is still referenced and re-released. [4](#0-3) 

### Impact Explanation
Double release of the `mutex.lock(["saved_private"])` guard and double completion of the per-row work item can desynchronize the private-payment processing state: `unlock()` may run before all rows are actually processed, letting a re-entrant call to `handleSavedPrivatePayments()` (triggered by `eventBus` events or timers) run concurrently over the same `unhandled_private_payments` rows while validation of the malformed one is still (redundantly) in flight, and it also invokes `privatePayment.validateAndSavePrivatePaymentChain` on data whose associated DB row/reference no longer represents pending state. Depending on interleaving, this can lead to processing/state confusion around private-payment acceptance (`assocNewUnits`, duplicate `eventBus.emit` of `new_my_transactions`/`all_private_payments_handled` events, or wallet double-processing of a chain) — a node/wallet disagreement or loss-of-funds-adjacent condition through malformed private payment data, without any special privileges beyond sending a private-payment chain.

### Likelihood Explanation
Any unprivileged peer, paired device, or hub-relayed sender that can deliver a private-payment chain (`handleOnlinePrivatePayment`, `handlePrivatePaymentChains`) controls the JSON `payload` of the head private element that gets stored in `unhandled_private_payments` and later re-validated by `handleSavedPrivatePayments`. Crafting a `payload` that makes `objectHash.getBase64Hash()` throw (e.g., by nesting cyclic-looking or otherwise hash-incompatible structures acceptable to `JSON.parse` but rejected by the hashing routine) is a low-effort, remotely triggerable input; the code path executes automatically whenever queued private payments are periodically reprocessed.

### Recommendation
Add a `return;` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave()` (network.js:2476) so that on hash failure the function does not fall through to re-run `validateAndSavePrivatePaymentChain` on the already-finalized/deleted record, and audit all other early-cleanup branches in this file that call `cb()`/`deleteHandledPrivateChain()` for missing `return` guards to avoid duplicate `async.each` callback invocation.

### Proof of Concept
1. As any unprivileged sender, submit a private-payment chain via device messaging / `handleOnlinePrivatePayment` whose head element's `payload` is a JSON-serializable object crafted so `objectHash.getBase64Hash(payload, true)` throws (e.g., a `payload` containing a value type that `objectHash`'s canonical-JSON/hash routine rejects, while still passing the earlier `isNonemptyObject`/array checks in `handlePrivatePaymentChains`).
2. The malformed chain is persisted to `unhandled_private_payments` and later picked up by `handleSavedPrivatePayments()`.
3. In `validateAndSave()`, `getBase64Hash` throws; `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` deletes the row and invokes `cb()`.
4. Because there is no `return`, execution proceeds to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the same data; its `ifOk`/`ifError` handler calls `deleteHandledPrivateChain(..., cb)` again, invoking `cb()` a second time for the same `async.each` iteration — observable via duplicate `DELETE` attempts on the already-removed row and/or the final `async.each` completion callback (`unlock()`) firing before all rows have been handled once the input is repeated across multiple rows in the same batch.

Note: I was unable to fully trace the exact runtime behavior of the `async` library version in use (whether the second `cb()` throws, is silently ignored, or corrupts iteration state) since that depends on the specific `async` package version pinned in `package.json`, which was not inspected in this pass; the code-level double-callback defect itself is confirmed directly from the source shown above.
