### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act On the Independent, Unverified `repository.full_name` Field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository.owner.login` (or `organization.login`) from the JSON payload, but every event handler (`PushHandler`, and other `Handler` subclasses) resolves the `Repository`/`Stack` to mutate using the separate, independently-controlled `repository.full_name` field. Because these two fields are never cross-checked against each other, a signature that is valid for organization A does not guarantee that the repository being acted upon actually belongs to organization A.

### Finding Description
The equality this engine relies on, but never enforces, is:

`organization whose webhook secret authenticated the request == owner of the repository the handler writes to`

- `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) and uses it to pick the `Shipit.github(organization: repository_owner)` app instance whose `webhook_secret` is used to verify `X-Hub-Signature`: [1](#0-0) , with `repository_owner` defined at [2](#0-1) .
- Once the signature check passes, `create` simply dispatches the raw parsed JSON to all registered handlers for the event: [3](#0-2) .
- The base `Handler` class (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the repository/stacks to operate on from a *different* JSON field, `repository.full_name`, with no reference back to `repository.owner.login`: [4](#0-3) .
- `PushHandler#process`, for example, uses that same `stacks` helper to find matching, non-archived stacks and calls `stack.sync_github(expected_head_sha: params.after)` on them: [5](#0-4) .

Because Shipit supports multiple GitHub organizations, each with its own App/webhook secret (`Shipit.github(organization:)`, exercised in `verify_signature` and tested in `test/controllers/webhooks_controller_test.rb`), a party that legitimately controls the webhook secret for **their own** organization/repository (e.g. they administer a repo under `attacker-org` that is registered with this Shipit instance) can send a webhook whose body has `repository.owner.login = "attacker-org"` (making `verify_signature` succeed using their own valid secret) while `repository.full_name` is set to an unrelated, victim-owned repository (e.g. `"victim-org/victim-repo"`). The signature only proves the request was signed with `attacker-org`'s secret; it says nothing about which repository's full name appears elsewhere in the same JSON body, and the handler never checks that `full_name`'s owner matches `repository.owner.login`.

### Impact Explanation
This breaks the binding between "the organization that authenticated the webhook" and "the repository actually written to," matching the required High-impact category of "unauthenticated read of stack state" / escalation-adjacent cross-tenant writes: an attacker with legitimate webhook-signing capability for one organization can forge push/status/check-run events attributed to a completely different organization's repository that they do not control. For `push` events this triggers `GithubSyncJob` (`stack.sync_github`) against the victim stack; for `status`/`check_suite` events it can inject or manipulate commit statuses/check-run refreshes on commits belonging to a stack the attacker has no relationship to. This can be used to spoof CI status, trigger unwanted syncs, or interfere with merge-queue/CI gating logic on a stack the attacker was never authorized to touch — a cross-repository write across tenant boundaries.

### Likelihood Explanation
Requires the attacker to already control a legitimate GitHub App/webhook secret for at least one organization configured in the same multi-tenant Shipit deployment (i.e., they can send a request that legitimately signs with `attacker-org`'s secret). This is a real-world configuration for shared/multi-tenant Shipit installations serving multiple GitHub organizations, and no repository-write access to the victim's repository is needed — only the ability to shape the JSON body of a webhook sent to the shared endpoint, which is entirely attacker-controlled once the signing secret is known for their own tenant. This is not dependent on the host failing to mount the engine as documented; it is a defect in `verify_signature`'s trust binding itself.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), cross-validate that `repository.owner.login` (the value used to select the signing organization) matches the owner segment parsed from `repository.full_name` before any handler is allowed to act on it. Reject the webhook (422) if they diverge. Alternatively, have handlers derive the target repository strictly from the same field that was used for signature verification, rather than trusting an independent, unauthenticated `full_name` field.

### Proof of Concept
1. Configure a multi-tenant Shipit instance with two organizations, `attacker-org` (secret known to the attacker because they administer that org's GitHub App/webhook) and `victim-org` (a repository the attacker does not control, tracked by an existing Stack).
2. Craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Sign the raw body with `attacker-org`'s known `webhook_secret` and send it as `X-Hub-Signature` to `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check succeeds because the attacker used the correct secret for that organization (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github` on the victim's stack — a write triggered by an actor who never authenticated as, or was authorized for, `victim-org`.
