### Title
Creator fee collection permanently DoS'd if either token's associated fee account is frozen/blacklisted - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs])

### Summary
`collect_creator_fee` and its permissionless counterpart `collect_creator_fee_permissionless` unconditionally attempt to transfer both `creator_fees_token_0` and `creator_fees_token_1` in the same atomic instruction, to fixed, deterministically-derived associated token accounts owned by the pool creator. If either of those destination accounts becomes frozen (e.g. the mint's freeze authority blacklists the creator's account for a regulated/pausable token such as a Token-2022 stablecoin), the entire instruction reverts, and the creator can never collect the fee balance for the *other*, unfrozen token either, because both transfers must succeed together and the destination accounts cannot be substituted.

### Finding Description
`collect_creator_fee` reads both fee balances and, provided at least one is non-zero, performs two sequential `transfer_from_pool_vault_to_user` calls — one for token_0 and one for token_1 — inside a single atomic instruction: [1](#0-0) 

The destination accounts, `creator_token_0` and `creator_token_1`, are not chosen freely by the caller; they are constrained to be the canonical associated token accounts of the `creator` for `vault_0_mint`/`vault_1_mint`: [2](#0-1) 

The same pattern (fixed ATA + two bundled unconditional transfers) exists in the permissionless variant, which anyone can invoke on the creator's behalf: [3](#0-2) [4](#0-3) 

The underlying transfer primitive is a plain `transfer_checked` CPI, which will fail (and thus abort the whole transaction) if the source or destination account is frozen: [5](#0-4) 

Because Solana transactions are atomic, a revert of either leg reverts the whole call, so `pool_state.creator_fees_token_0`/`creator_fees_token_1` are never zeroed and the funds sit permanently in the vault, inaccessible through this instruction: [6](#0-5) 

This is the direct analog of the reported `SdtRewardReceiver::_withdrawRewards` issue: one blacklisted/frozen token blocks distribution of an otherwise-claimable, unrelated token because both are bundled into a single failing operation. Unlike `withdraw`/`deposit`, where the destination token accounts are freely chosen by the caller (no `token::authority` binding them to a specific frozen ATA) and thus a frozen account can be worked around by supplying a fresh token account, `collect_creator_fee`/`collect_creator_fee_permissionless` hard-code the destination to the creator's *canonical* ATA with no alternative path to redeem the fee.

### Impact Explanation
If the pool creator's ATA for one of the two pool tokens becomes frozen (e.g., issuer-level blacklisting on a Token-2022 mint with freeze/default-account-state extensions, analogous to USDT-style blacklisting), the creator permanently loses the ability to collect creator fees accrued in *both* tokens — including the fee balance of the token whose account is not frozen — since both transfers are bundled into one atomic, non-substitutable instruction. Accrued fees remain locked in the pool vaults indefinitely with no recovery path, since `creator_fees_token_0`/`creator_fees_token_1` can only be reset via a fully successful call to `collect_creator_fee`/`collect_creator_fee_permissionless`. This constitutes permanent freezing of legitimate creator funds.

### Likelihood Explanation
This requires that the token mint used by the pool has an authority capable of freezing/blacklisting a specific account (e.g., a Token-2022 mint with freeze authority or default-account-state extension, similar to how USDT operates), and that the pool creator's canonical ATA for one leg becomes frozen. Given Raydium CP-Swap explicitly supports Token-2022 mints throughout (`token_0_program`/`token_1_program` interfaces, transfer-fee handling in `utils/token.rs`), pools paired with such regulated/pausable tokens are a realistic and anticipated configuration, and the permissionless variant means any third party can trigger the failing call once one leg's ATA is frozen, repeatedly confirming the fee remains stuck.

### Recommendation
Decouple the two transfers so a failure on one token does not block collection of the other — e.g., allow the caller to specify which token's fee to withdraw, or handle each transfer with a fallible pattern that still zeroes and returns the successfully-transferred side while leaving the failed side's accounting untouched for a later retry, rather than reverting both transfers when only one fails.

### Proof of Concept
1. Create a pool where `token_0_mint` is a Token-2022 mint with a freeze authority (or default-account-state extension) held by a third party (issuer), and accumulate non-zero `creator_fees_token_0` and `creator_fees_token_1` via normal swaps.
2. The issuer freezes the pool creator's canonical associated token account for `token_0_mint` (the account constrained by `associated_token::mint = vault_0_mint, associated_token::authority = creator` in `CollectCreatorFee`/`CollectCreatorFeePermissionless`).
3. The creator (or anyone, via the permissionless variant) calls `collect_creator_fee`/`collect_creator_fee_permissionless`; the `transfer_checked` CPI for `token_0` in `transfer_from_pool_vault_to_user` fails because the destination is frozen, reverting the entire instruction.
4. `creator_fees_token_1`, though fully claimable and unaffected by the freeze, can never be collected either, because there is no way to invoke the instruction with only the token_1 leg — the destination accounts are fixed to the frozen creator's ATA and both transfers are bundled atomically.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;
```

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
