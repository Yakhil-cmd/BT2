### Title
CCMenu API endpoint bypasses per-token stack scoping, letting a stack-scoped `ApiClient` read the deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The Sherlock report describes a broken binding: `AstariaRouter.liquidate()` checks one condition (`auctionWindow`) to decide which epoch an auction will settle in, while the actual `AuctionHouse` can extend the auction past that window, so the authorization/accounting boundary the code assumes (`epoch it was scoped to == epoch it will actually resolve in`) does not hold. The same class of bug exists in shipit-engine's API stack-scoping: the binding the system is supposed to enforce is `stack an ApiClient token is scoped to == stack the controller action actually operates on`. `Shipit::Api::BaseController` establishes this binding through its `stacks`/`stack` helpers, but `Shipit::Api::CCMenuController` overrides `stack` and re-implements it without the scoping check, breaking the binding for that one endpoint.

### Finding Description
`Shipit::Api::BaseController` enforces stack scoping for every API controller that inherits from it: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped to a single stack, and `stack` resolves `params[:stack_id]` only within that restricted set. This is the mechanism that makes `ApiClient#stack_id` (a `belongs_to :stack, optional: true` scoping field) meaningful: [2](#0-1) 

Permission checking itself (`check_permissions!`) only verifies that the client's `permissions` array contains e.g. `read:stack` - it never looks at which stack is being accessed: [3](#0-2) 

So the *only* thing preventing a client scoped to stack A from touching stack B is the `stacks`/`stack` helper in `BaseController`. `CCMenuController` bypasses that helper entirely: [4](#0-3) 

It declares `require_permission :read, :stack` (checks the permission string only) and then defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly against **all** stacks, never consulting `current_api_client.stack_id`. The `show` action then renders the target stack's latest deploy/rollback status using that unscoped lookup: [5](#0-4) 

The route is mounted under the API namespace with the standard `stack_id` segment: [6](#0-5) 

The fixture data demonstrates the intended scoping semantics: `here_come_the_walrus` is an `ApiClient` scoped to stack `shipit` with only `read:stack` permission, meant to only see that one stack (as verified for `StacksController` in its test suite): [7](#0-6) [8](#0-7) 

Because `CCMenuController#stack` never applies this restriction, presenting the same `here_come_the_walrus` token against `GET /api/stacks/<other-owner>/<other-repo>/<other-env>/ccmenu` succeeds and returns that other stack's build/deploy status, name, and last build info - exactly the binding violation pattern in the source report (a check performed against one scope while the actual operation resolves against a broader one).

### Impact Explanation
This is an authorization-boundary break: a token deliberately restricted to a single stack (a common integration pattern for e.g. CI dashboards, exposed via `CCMenuUrlController`) can be replayed against the `ccmenu` endpoint to read the deploy state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity/lock status) of any other stack in the installation, including stacks the token holder was never meant to see. This matches the in-scope "High" impact category of unauthorized read of stack state via a token that should not authorize it.

### Likelihood Explanation
Any holder of a valid, narrowly-scoped `ApiClient` token (created and distributed for a single stack's CCMenu integration, as `CCMenuUrlController#client` does) can trigger this by simply substituting a different `stack_id` in the URL path - no privilege escalation, secret discovery, or additional access is required beyond possessing one legitimately-issued scoped token.

### Recommendation
Make `CCMenuController` use the inherited, scope-respecting `stack`/`stacks` helpers from `Shipit::Api::BaseController` instead of its private override, e.g. remove the private `stack` method (or have it delegate to `stacks.from_param!(params[:stack_id])`) so that `current_api_client.stack_id` scoping is enforced consistently with every other API controller.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A only, e.g. equivalent to the `here_come_the_walrus` fixture (`stack: A`, `permissions: [read:stack]`).
2. Authenticate to the API using that token (Basic auth per `BaseController#authenticate_api_client`).
3. Request `GET /api/stacks/<owner-of-stack-B>/<repo-of-stack-B>/<env-of-stack-B>/ccmenu`.
4. Observe that `require_permission :read, :stack` passes (the client does have `read:stack`), and `CCMenuController#stack` resolves Stack B via the unscoped `Stack.from_param!`, returning Stack B's CCMenu XML (`lastBuildStatus`, etc.) even though the token is scoped to Stack A only - contrast with the same token against `Api::StacksController#show` for Stack B, which correctly 404s due to `BaseController#stacks` scoping.
