### Title
Incorrect balance retroactively overwritten in merged `aa_response` events for repeated AA invocations - ([File: aa_composer.js])

### Summary
When the same AA address is invoked more than once within a single primary-trigger cascade (e.g. an AA that receives a secondary trigger, sends a payment, and is triggered again later in the same cascade, or is otherwise called twice as `bSecondary`), `handlePrimaryAATrigger` merges the balances of all responses in `arrResponses` and overwrites the `balances` field of **every** response for that AA address with the value from the **last** invocation, discarding the correct balance that existed right after each earlier invocation.

### Finding Description
Each individual AA invocation computes and finalizes its own balance snapshot via `updateFinalAABalances` and attaches it to `objAAResponse.balances = objValidationState.assocBalances[address]` inside `addResponse`. [1](#0-0) 

After the whole trigger chain (including all secondary triggers) finishes and the batch/transaction commits, `handlePrimaryAATrigger` post-processes `arrResponses` before emitting them on the event bus. If more than one response was produced, it builds `assocBalances` by iterating `arrResponses` and **overwriting** the entry for each `aa_address` with whichever response comes last in the array, then reassigns `r.balances = assocBalances[r.aa_address]` to **every** response sharing that address — not just the last one: [2](#0-1) 

This is the same root-cause pattern as the reported Solidity issue: state (balance) is captured correctly at one point in execution, but the emitted event is populated using a value read/computed *after* subsequent mutations, so the event body no longer reflects the true balance at the time that particular response actually executed. In ocore's case, this mutation is not "balance transferred then logged after" but "final per-invocation balance overwritten by a later invocation's balance before being logged," with the same net effect: the persisted/emitted record misrepresents the AA's actual balance history.

The `aa_response` events (with the erroneous `balances` field) are then:
- Stored/forwarded to full-node listeners via `eventBus.emit('aa_response', ...)`. [3](#0-2) 
- Relayed to light clients that are watching the AA, via `network.js`'s `light/aa_response` justsaying handler, which forwards the (mutated) `objAAResponse` object as-is over the wire. [4](#0-3) 
- Persisted into `aa_responses.response` (JSON) for light-client history sync and API queries such as `light/get_aa_responses` / `light/get_aa_response_chain`. [5](#0-4) [6](#0-5) 

Any unprivileged actor can trigger this by posting a unit that causes the target AA to be invoked more than once within the same primary-trigger cascade (directly reachable from a single posted trigger unit, satisfying the "AA trigger sender" threat model).

### Impact Explanation
The emitted/relayed `balances` field is consumed by light wallets and third-party services (including private-payment counterparties building on ocore, e.g. payment-channel-style AAs like the one in `test/samples/payment_channels.oscript`) to track an AA's balance history without independently reconstructing it from the full DAG. If a counterparty or wallet trusts the reported per-response `balances` value to decide when it is safe to close a channel, split proceeds, or accept a state transition, it can be misled into acting on an incorrect balance snapshot for an earlier response in the chain. This mirrors the Medium-severity classification of the original report: it is a data-integrity flaw in emitted event data (not a corruption of the authoritative `aa_balances` table itself), but it can cause off-chain systems and paired devices to make decisions based on stale/incorrect balance figures, particularly problematic for AAs where multiple invocations of the same address happen within one trigger cascade.

### Likelihood Explanation
Any unit poster can trigger secondary/cascading invocations of the same AA address by crafting payment/data flows that route back to the same AA more than once within a single primary trigger's cascade — this only requires normal permissionless unit posting and AA composition, no privileged access, matching the reachable trust model (single posted unit → AA trigger cascade).

### Recommendation
Do not overwrite the `balances` snapshot of earlier responses with a later invocation's balance. Instead of merging `assocBalances` by address and applying the last value to all matching responses, retain each response's own finalized balance as captured in `addResponse` (i.e., keep `r.balances` untouched), and only use a separately-computed "final/aggregate balances" map (e.g. via the existing `r.allBalances`) for consumers that need the AA's overall latest balance across the whole cascade. This preserves per-event historical accuracy while still exposing the aggregate final state where needed.

### Proof of Concept
1. Deploy an AA `X` whose logic can be invoked twice within the same primary-trigger cascade — e.g., `X` sends a payment to AA `Y` as a secondary trigger; `Y`'s logic sends a payment back to `X`, causing `X` to be triggered a second time as a secondary trigger in the same cascade (`handleSecondaryTriggers` recursion in `aa_composer.js`).
2. Post a single unit triggering `X` with an initial payment. This produces `arrResponses` containing (at least) two entries with `aa_address === X`: response #1 (from the first invocation) with `balances = B1`, and response #2 (from the second invocation) with `balances = B2`.
3. In `handlePrimaryAATrigger`, since `arrResponses.length > 1`, the merge logic sets `assocBalances[X] = B2` (last write wins) and then sets **both** `arrResponses[0].balances` and `arrResponses[1].balances` to `B2`.
4. The `aa_response` event for response #1 (and its persisted `aa_responses` row / relayed `light/aa_response` message) now reports balance `B2` instead of the true post-invocation balance `B1`, misrepresenting the AA's balance at that point in its execution history to any listener (light wallet, payment-channel counterparty, or monitoring service) relying on this data.
