### Title
Unbounded `RemoteProxyProof::RelayChain` proof size not reflected in charged weight, allowing execution-time DoS via `Pallet::remote_proxy` - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`remote_proxy`'s `#[pallet::weight]` closure charges a fixed benchmarked weight (`WeightInfoOf::<T,I>::remote_proxy()`) plus the *inner* call's declared weight, but never accounts for the size of the caller-supplied `proof: Vec<Vec<u8>>`. Since `proof` is an unbounded `Vec<Vec<u8>>` and the benchmark that produced the fixed weight only ever exercises a single-node trie proof, an attacker can submit a proof many orders of magnitude larger (up to the extrinsic length limit) while declaring/paying for a tiny fixed weight, causing `sp_trie::StorageProof::new(proof).into_memory_db()` and `sp_trie::read_trie_value` to do work proportional to the real proof size but charged at a constant rate.

### Finding Description
The `remote_proxy` extrinsic weight annotation is: [1](#0-0) 

The declared weight is `WeightInfoOf::<T, I>::remote_proxy()` (a fixed constant from benchmarking) plus one DB read/write plus `di.call_weight` (the inner call's own declared weight, e.g. `System::remark`'s weight). Nothing in this formula scales with the size of `proof`.

`proof` is typed as `RemoteProxyProof<RemoteBlockNumberOf<T, I>>::RelayChain { proof: Vec<Vec<u8>>, block }`, an unbounded, caller-controlled vector of byte vectors: [2](#0-1) 

Inside `do_remote_proxy`, this proof is fully materialized into an in-memory trie database and used to verify a value via `sp_trie::read_trie_value`, work that scales with the number/size of supplied nodes (hashing every submitted node, building the `MemoryDB`, and performing a keyed lookup) — regardless of whether verification ultimately succeeds: [3](#0-2) 

The benchmark that generates the constant weight only ever constructs a trie with a single inserted `ProxyDefinition` entry, producing a proof of a handful of nodes: [4](#0-3) [5](#0-4) 

And the resulting autogenerated weight is a small fixed value (`Weight::from_parts(18_259_000, 0)` plus a fixed 1846-byte proof-size component and one DB read), independent of any proof-size parameter: [6](#0-5) 

Because the weight formula has no term keyed to `proof.len()` (number of nodes) or total encoded byte-length of `proof`, an attacker can pass `call = System::remark` (cheap, filtered-allowed, near-zero `di.call_weight`) together with a `proof` containing many/large `Vec<u8>` trie nodes (well below the extrinsic length limit, since `proof` is unbounded and not subject to any `MaxEncodedLen`/`BoundedVec` constraint at the pallet level). The declared/charged weight stays essentially constant (`remote_proxy()` benchmark weight + `di.call_weight` of `remark`), while the actual CPU time spent hashing/decoding the oversized `MemoryDB` and walking the trie during `read_trie_value` scales with the real proof size. The call will ultimately fail with `InvalidProof` or `DidNotFindMatchingProxyDefinition` (no valid proxy relation is required to trigger the expensive verification path — the proof lookup happens before the proxy-definition match), but the underestimated declared weight is what the block builder/`CheckWeight` extension uses to decide whether the extrinsic fits in the remaining block weight, not the real execution time.

### Impact Explanation
Repeated submission of `remote_proxy` calls with maximal-size but bogus `RelayChain` proofs lets an attacker pack a block with extrinsics whose *declared* weight is tiny but whose *actual* execution time is large (proof decoding/hashing cost), causing the collator/validator's actual wall-clock block-authoring time to exceed the block's real-time budget while the on-chain weight accounting shows plenty of headroom left. Repeated across blocks this can degrade or stall block production (execution-time DoS), matching the scoped network-wide block-time overrun impact.

### Likelihood Explanation
The attacker only needs to be a normal signed account — no proxy relationship, no privileged origin, and no successful proof verification is required, since the expensive `sp_trie` work happens unconditionally before the proof/definition match is checked. The proof content can be arbitrary garbage nodes (it need not correspond to a real relay-chain trie) as long as it deserializes as `Vec<Vec<u8>>`, so crafting a maximal-size proof is trivial and repeatable every block up to the extrinsic length limit.

### Recommendation
Make the charged weight scale with the actual size of the supplied proof (e.g. total byte length of `proof` and/or number of nodes), either by adding a linear weight component derived from `proof.encoded_size()`/node count (benchmarked across a range of proof sizes) to the `#[pallet::weight]` formula for `remote_proxy` and `remote_proxy_with_registered_proof`, or by bounding `proof: Vec<Vec<u8>>` with a `BoundedVec<BoundedVec<u8, MaxNodeSize>, MaxNodes>` and charging worst-case weight for that bound.

### Proof of Concept
Rust benchmark/fuzz-style test in `pallets/remote-proxy/src/tests.rs`:
1. Construct `RemoteProxyProof::RelayChain` proofs of varying sizes: (a) the normal single-node proof as in `remote_proxy_works`, and (b) a proof padded with many additional random/garbage `Vec<u8>` "nodes" up to the extrinsic-length limit.
2. For each proof size, call `Pallet::<Test>::do_remote_proxy` (or the extrinsic) with `call = System::remark` and measure wall-clock execution time (e.g. `std::time::Instant`).
3. Assert that `WeightInfoOf::<Test, ()>::remote_proxy()` (the constant weight from `weight.rs`/`()` impl) stays fixed across all proof sizes while measured execution time grows with proof size — demonstrating the charged weight is not an upper bound on measured execution time, i.e. `measured_time(large_proof) > weight_to_time(declared_weight)`.
4. Expected assertion: for the padded/large proof, `Error::<Test, ()>::InvalidProof` or `DidNotFindMatchingProxyDefinition` is still returned (the call fails), but measured execution time significantly exceeds the time budget implied by the declared, size-independent weight — confirming the DoS vector.

	#[cfg(feature = "runtime-benchmarks")]
	fn create_remote_proxy_proof(
		caller: &u64,
		proxy: &u64,
	) -> (RemoteProxyProof<Self::RemoteBlockNumber>, u64, H256) {
		use sp_trie::TrieMut;

		let (mut db, mut root) = sp_trie::MemoryDB::<BlakeTwo256>::default_with_root();
		let mut trie =
			sp_trie::TrieDBMutBuilder::<sp_trie::LayoutV1<_>>::new(&mut db, &mut root).build();

		let proxy_definition = vec![ProxyDefinition::<u64, ProxyType, u64> {
			delegate: *caller,
			proxy_type: ProxyType::default(),
			delay: 0,
		}];

		trie.insert(&Self::proxy_definition_storage_key(proxy), &proxy_definition.encode())
			.unwrap();
		drop(trie);

		(
			RemoteProxyProof::RelayChain {
				proof: db.drain().into_values().map(|d| d.0).collect(),
				block: 1,
			},
			1,
			root,
		)
	}
