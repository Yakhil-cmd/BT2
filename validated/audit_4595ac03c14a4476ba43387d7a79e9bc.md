### Title
Unauthenticated P2P Peer Can Corrupt Persisted KEFAddr/KIFAddr via No-Op Validation in `DeliverStakingInfos`, Redirecting Pre-Kaia Block Treasury Rewards — (`datasync/downloader/queue.go`)

### Summary
During FastSync/SnapSync for pre-Kaia blocks, the `queue.DeliverStakingInfos` validate closure is a deliberate no-op. A connected P2P peer can deliver a `P2PStakingInfo` with arbitrary `KEFAddr`/`KIFAddr` values. `commitFastSyncData` writes these directly to the staking info DB via `PutStakingInfoToDB`. Because `GetStakingInfo` treats the DB as authoritative for pre-Kaia source blocks (returning on first DB hit without state verification), the corrupted addresses are used by the reward module to determine KEF and KIF transfer recipients for every block in the affected staking epoch.

### Finding Description
`queue.DeliverStakingInfos` passes a no-op `validate` function to the generic `deliver` helper. Unlike `DeliverBodies` (which checks `TxHash`) and `DeliverReceipts` (which checks `ReceiptHash`), staking info has no cryptographic binding to the block header. The `P2PStakingInfo` struct carries `KEFAddr` and `KIFAddr` as plain fields with no commitment in any header field. The TODO comment confirms this is a known gap. `commitFastSyncData` then calls `PutStakingInfoToDB` unconditionally on any non-nil `StakingInfo`. `GetStakingInfo` returns the DB value on the first hit, bypassing the AddressBook contract state entirely.

### Impact Explanation
For chains/nodes where pre-Kaia blocks are being processed after FastSync, the KEF and KIF portions of block rewards (determined by `reward.ratio` governance parameter, typically a significant fraction of minted KAIA) are transferred to attacker-controlled addresses instead of the legitimate treasury contracts. The corruption persists across node restarts because it is written to the key-value database.

### Likelihood Explanation
Any connected P2P peer can send a `StakingInfoMsg` response. The attacker only needs to be a registered peer at the time the victim node requests staking info during FastSync. No validator keys, governance authority, or majority collusion is required. The constraint is that the victim must be processing pre-Kaia blocks after FastSync (i.e., the chain has not yet reached the Kaia hardfork, or the pivot is pre-Kaia).

### Recommendation
Replace the no-op validate closure with a check that re-derives the expected `KEFAddr`/`KIFAddr` from the local AddressBook state at the source block (or at minimum checks that the delivered `BlockNum` matches the requested header and that the addresses are non-zero). Alternatively, after writing to DB, verify the entry against the canonical state before using it for reward computation.

### Proof of Concept
1. Start a victim node in FastSync mode on a pre-Kaia chain.
2. Connect a malicious peer that responds to `StakingInfoRequestMsg` with a `P2PStakingInfo` where `KEFAddr = attacker_address` and `KIFAddr = attacker_address`.
3. Observe that `commitFastSyncData` calls `PutStakingInfoToDB` with the fake addresses.
4. After sync, call `GetStakingInfo(N)` for a pre-Kaia block N in the affected epoch — it returns the corrupted entry from DB.
5. Process a new block in that epoch and observe that the KEF and KIF reward transfers go to `attacker_address` rather than the legitimate treasury contracts.
