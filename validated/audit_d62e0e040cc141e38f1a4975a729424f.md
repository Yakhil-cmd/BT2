### Title
Signer bond rewards inflated by joining a bond without settling the signer's existing reward snapshot - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
In `pox-5.clar`, `add-staker-to-bond-for-cycle` (called from `add-staker-to-bond-cycles`, itself invoked by `register-for-bond`/bond-rollover flows) increases `signer-shares-staked-for-cycle` and `total-shares-staked-for-cycle` for a bond cycle **without first calling `settle-rewards`** for that signer/bond-index, unlike every other mutation site (`unstake-sats-from-bond-cycle`, `add-staker-to-signer-for-cycle`, `remove-staker-from-signer-for-cycle`). This mirrors the audited bug class: mutating a balance that a cumulative-accrual snapshot depends on, without first crystallizing rewards under the old balance — except here the direction inflates rather than reduces the accrued amount.

### Finding Description
`settle-rewards` is documented as: "This MUST be called before any update to `signer-shares-staked-for-cycle`, because changes to that state will effect rewards calculations" [1](#0-0) . It computes `earned = shares * (rpt_current - rpt_paid)` using the **shares as they were before the mutation**, then advances the signer's settled snapshot (`signer-rewards-per-token-settled-for-cycle`) to `rpt_current` [2](#0-1) .

Every code path that changes `signer-shares-staked-for-cycle` for STX-only staking correctly calls `settle-rewards` first: `add-staker-to-signer-for-cycle` [3](#0-2)  and `remove-staker-from-signer-for-cycle` [4](#0-3) , as does the bond-cycle unstake path `unstake-sats-from-bond-cycle` [5](#0-4) .

However, `add-staker-to-bond-for-cycle` — which adds a new staker's sats into an existing bond/signer/cycle via `map-set signer-shares-staked-for-cycle` and `map-set total-shares-staked-for-cycle` — contains **no call to `settle-rewards`** before bumping the signer's aggregate bond shares [6](#0-5) . It only updates the *new joining staker's own* settlement marker (`staker-rewards-per-token-settled-for-cycle`) to the current signer-level rewards-per-token, which correctly protects that individual staker from retroactive credit [7](#0-6) . It does nothing to protect the signer-level aggregate accounting.

The equality broken: the signer's `signer-unclaimed-rewards-for-cycle` (used to compute the signer-manager's claimable sBTC via `get-earned`/`claim-rewards`) should equal shares-weighted rewards distributed while those shares were actually staked. Because `signer-shares-staked-for-cycle` is bumped up (by a newly-joining staker's sats) **before** the signer's cumulative snapshot (`signer-rewards-per-token-settled-for-cycle`) is advanced, the next `settle-rewards`/`get-earned` call multiplies the **larger, post-join** share count against `(rpt_current - old_settled_rpt)`, a delta that accrued **before** the new staker joined. This retroactively attributes reward-per-token accrued to the pre-existing (smaller) share pool to the new, larger share count, inflating the signer's claimable sBTC total beyond what the reserve actually earned for that cycle — a double-counting of bond rewards.

### Impact Explanation
This inflates `signer-unclaimed-rewards-for-cycle`/`get-earned` for the affected signer/bond-index, which directly feeds `claim-rewards`'s `update-claimable-bond-rewards` sBTC transfer out of the pox-5 contract's reserve to the signer-manager contract. This is unbacked minting/theft of pooled sBTC bond rewards from the contract's reserve/other participants, matching the "Critical: theft or unbacked minting of ... sBTC rewards ... double-counting a commitment or reward" category.

### Likelihood Explanation
Exploitability requires only ordinary, unprivileged actions available to any staker: (1) an existing bond with staked sats already accruing rewards for a signer/bond-index, (2) rewards computed via `calculate-rewards` so `rewards-per-token-for-cycle` has advanced past the signer's stale settled snapshot, and (3) a new staker (attacker-controlled or colluding) calling `register-for-bond` for that same signer/bond-index before the signer's snapshot is otherwise settled (e.g., before anyone else triggers `settle-rewards` via unstake or another registration). No admin/bond/pause privileges or another user's key are required.

### Recommendation
Call `settle-rewards signer reward-cycle (some bond-index)` at the start of `add-staker-to-bond-for-cycle`, before reading `current-total-staked`/`current-signer-staked` and before the `map-set` calls that increase `signer-shares-staked-for-cycle` and `total-shares-staked-for-cycle`, mirroring the pattern already used in `unstake-sats-from-bond-cycle` and `add-staker-to-signer-for-cycle`.

### Proof of Concept
1. Signer S has bond-index B active for reward-cycle C with `signer-shares-staked-for-cycle = X` sats from staker Alice, already generating rewards via `calculate-rewards`.
2. Time passes; `rewards-per-token-for-cycle(C, B)` advances (via `calculate-bond-rewards`) while `signer-rewards-per-token-settled-for-cycle(S, C, B)` remains at its stale value (no intervening settle for the signer).
3. Attacker Bob calls `register-for-bond` for bond B with signer S, adding `Y` more sats. This routes through `add-staker-to-bond-cycles` → `add-staker-to-bond-for-cycle`, which sets `signer-shares-staked-for-cycle(S, C, B) = X + Y` directly, without calling `settle-rewards` first [8](#0-7) .
4. Any subsequent trigger of `settle-rewards(S, C, B)` (e.g., another staker joining/leaving, or `claim-rewards`) computes `earned = (X+Y) * (rpt_current - old_settled_rpt)` instead of the correct `X * (rpt_current - old_settled_rpt) + Y * (rpt_current - rpt_at_join)`, over-crediting the signer's claimable bond rewards by `Y * (rpt_current - old_settled_rpt)`.
5. The signer-manager contract calls `claim-rewards`, pulling the inflated sBTC amount out of the pox-5 reserve — sBTC that was never actually earned by Bob's newly added sats for the period before he joined.

;; Update all earned-but-unclaimed rewards for a signer, and update the snapshot
;; (signer-rewards-per-token-settled-for-cycle) for the signer.
;;
;; This MUST be called before any update to `signer-shares-staked-for-cycle`,
;; because changes to that state will effect rewards calculations.
(define-private (settle-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let (
            (shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
            (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
            (earned (compute-earned-rewards
                shares
                rewards-per-token
                (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index)
            ))
        )
        (map-set signer-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            earned
        )
        (map-set signer-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            rewards-per-token
        )
        (if (> shares u0)
            (map-set signer-rewards-per-token-for-cycle {
                signer: signer,
                reward-cycle: reward-cycle,
                bond-index: bond-index,
            }
                rewards-per-token
            )
            true
        )
        {
            earned: earned,
            rewards-per-token: rewards-per-token,
        }
    )
)
