### Title
Webhook signature verification is bound to `organization.login`/`repository.owner.login` while event handlers act on the unrelated `repository.full_name`, allowing cross-organization forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) authenticates a webhook using `repository_owner`, derived from `repository.owner.login` or, if absent, `organization.login`. Every event handler (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) instead resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, with no re-check that this repository actually belongs to the organization that was cryptographically verified. In a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set, an attacker can pass signature verification trivially for that organization while pointing `repository.full_name` at a repository belonging to a different, properly-secured organization.

### Finding Description
The binding the code implicitly assumes but never enforces is:
`verifying_org = params.dig('repository','owner','login') || params.dig('organization','login')` **must equal** `owning_org = params.dig('repository','full_name').split('/').first`.

Trace:
- [1](#0-0)  computes `repository_owner` with this fallback chain.
- [2](#0-1)  uses that value to pick the `GitHubApp` (and its `webhook_secret`) that performs HMAC verification.
- [3](#0-2)  shows `verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that app (`return true unless webhook_secret`).
- [4](#0-3)  `Shipit.github(organization:)` looks up per-organization config via `github_app_config`, confirming multi-org setups keep independent `webhook_secret`s per organization.
- [5](#0-4)  shows every handler resolves `stacks`/`repository` strictly from `payload.dig('repository', 'full_name')`, completely independent of whatever organization was used for signature verification.
- [6](#0-5)  and [7](#0-6)  confirm the mutation (`sync_github`, `schedule_refresh_check_runs!`) targets whatever repository `full_name` names, with zero cross-check against `repository_owner`.

Exploit flow: attacker POSTs to `/webhooks` with `X-Github-Event: push`, body `{"organization":{"login":"org-without-secret"},"repository":{"owner":{"login":null},"full_name":"org-with-secret/victim-repo"},"ref":"refs/heads/master","after":"<any-sha>"}`, and any (even garbage) `X-Hub-Signature`. `repository_owner` resolves to `"org-without-secret"` (organization fallback, since `repository.owner.login` is absent). `Shipit.github(organization: "org-without-secret")` returns a `GitHubApp` with `webhook_secret` unset, so `verify_webhook_signature` returns `true` regardless of body/signature. `PushHandler` then looks up `Repository.from_github_repo_name("org-with-secret/victim-repo")` and, if that stack tracks branch `master`, enqueues `GithubSyncJob` for it - a write triggered against a repository belonging to a completely different, properly-secured organization, without ever validating that org's secret.

Existing guards do not catch this: `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` schemas (e.g. `PushHandler`'s `requires :ref, :after`) never require or validate `repository`; there is no code anywhere comparing `repository_owner` to `repository.full_name`'s owner segment.

### Impact Explanation
An attacker can trigger `GithubSyncJob` (and CI check-run refresh, and for pull_request events, creation/archival of review stacks) against any tracked stack belonging to any organization in a multi-org Shipit deployment, as long as at least one configured organization lacks a `webhook_secret`. This is a cross-tenant action: a payload "authenticated" (trivially, due to a blank secret) for one organization causes writes/enqueued jobs scoped to a stack/repository owned by a different organization. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is fully repeatable against any repository/stack tracked by the instance, for every push/check_suite/pull_request event handled.

### Likelihood Explanation
Requires: (1) a multi-organization `github:` config (top-level keys are org names) — a documented, supported configuration, and (2) at least one of those organizations configured with `webhook_secret` left blank (also explicitly shown as an accepted value, `# nil`, in the shipped example configs `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`). Given those two operator-controlled conditions, the attacker needs no secret, no session, no token — only knowledge of the no-secret organization's name (guessable or discoverable, e.g. via public GitHub App installation pages) and the target repository's `owner/name`. Cost per request is a single unauthenticated POST.

### Recommendation
In `WebhooksController#verify_signature`, or in `Handler#stacks`/`Handler#repository_name`, enforce that the organization used to select the verifying `GitHubApp` matches the owner segment of `payload.dig('repository', 'full_name')` (reject/422 on mismatch). Additionally, treat organizations without a `webhook_secret` as untrusted for any organization-scoped mutation, or require `webhook_secret` to be present for all configured organizations in multi-org mode.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Stub `Shipit.secrets.github` with two orgs: `org-without-secret` (no `webhook_secret`) and `org-with-secret` (`webhook_secret: "s3cr3t"`), matching the multi-org schema used in `test/unit/shipit_test.rb`.
2. Create a `Stack`/`Repository` fixture owned by `org-with-secret/victim-repo`, tracking branch `master`.
3. POST `X-Github-Event: push` with body `{"organization":{"login":"org-without-secret"},"repository":{"owner":{"login": null},"full_name":"org-with-secret/victim-repo"},"ref":"refs/heads/master","after":"deadbeef"}` and an arbitrary/garbage `X-Hub-Signature`.
4. Assert `response` is `:ok` (not `:unprocessable_entity`), i.e. `Shipit.github(organization: 'org-without-secret').verify_webhook_signature` returned `true` despite an invalid signature.
5. Assert `GithubSyncJob` was enqueued with `stack_id: victim_stack.id`, proving a stack owned by `org-with-secret` was mutated using authentication performed against `org-without-secret`.
6. Equality check: assert `repository_owner` (`"org-without-secret"`) != owner segment of `params.dig('repository','full_name')` (`"org-with-secret"`), demonstrating the broken binding directly.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
