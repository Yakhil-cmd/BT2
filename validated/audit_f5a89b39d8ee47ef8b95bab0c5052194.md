### Title
Unbounded OCI attestation bundle layer read enables memory-exhaustion DoS during `gh attestation verify`/`download` - (File: pkg/cmd/attestation/artifact/oci/client.go)

### Summary
`LiveClient.GetAttestations` in `pkg/cmd/attestation/artifact/oci/client.go` fetches Sigstore bundle layers from an OCI registry referenced by the user (`gh attestation verify oci://<image-uri> --bundle-from-oci` or `gh attestation download oci://<image-uri>`) and loads the entire decompressed layer content into memory with `io.ReadAll` and no size cap, mirroring the report's root cause: attacker-controlled response data is unconditionally read into memory without any bound, allowing a remote host to force unbounded memory consumption on the invoking client.

### Finding Description
The `--bundle-from-oci` / `gh attestation download oci://…` flow lets a user point `gh` at an arbitrary, attacker-controllable OCI registry/image reference. `GetAttestations` walks the referrers of that image, resolves any referrer whose `ArtifactType` starts with `application/vnd.dev.sigstore.bundle`, decompresses its first layer, and reads it fully into memory before parsing it as JSON: [1](#0-0) 

There is no limit on the compressed layer size, the decompressed size, or the number of bytes read by `io.ReadAll(layer0)`. Because the registry and the returned manifest/layer descriptors are fully attacker-controlled (the user can point the command at any `oci://` reference, including third-party or malicious registries), an attacker can advertise a referrer manifest whose "bundle" layer is a large or highly compressed (decompression-bomb) blob. `layers[0].Uncompressed()` transparently decompresses the layer stream, and the subsequent `io.ReadAll` call will keep growing an in-memory buffer until the process runs out of memory or is killed, exactly analogous to the reported issue where unrestricted `returndata` loaded into memory during a low-level call could be weaponized to exhaust available gas.

This is reachable from a normal, unprivileged invocation of `gh attestation verify` or `gh attestation download` against a user-supplied `oci://` reference — no special privileges or MITM position are required, since the "victim" (the `gh` CLI user) chooses to run the command against a reference that can point to any registry the attacker controls.

Reachability path: [2](#0-1) [3](#0-2) 

### Impact Explanation
A malicious or compromised OCI registry/image reference can cause the `gh` process to allocate an effectively unbounded amount of memory while running `gh attestation verify --bundle-from-oci` or `gh attestation download oci://...`, resulting in denial of service (OOM crash or severe resource exhaustion) on the machine invoking the CLI. This is a resource-exhaustion vulnerability triggered purely by pointing the CLI at attacker-controlled remote content, with no other precondition.

### Likelihood Explanation
The `--bundle-from-oci` and `oci://` download flows are documented, supported features; a user (or a script/CI pipeline) can be induced to run `gh attestation verify`/`download` against an untrusted or attacker-supplied OCI reference (e.g., a supply-chain scenario where the "image to verify" itself is attacker-influenced). Constructing an oversized or bomb-compressed layer requires no special access beyond hosting/serving an OCI registry response, making exploitation straightforward once the target is convinced to reference it.

### Recommendation
Wrap the layer reader with a bounded reader (e.g., `io.LimitReader`) before calling `io.ReadAll`, and reject bundles whose declared/actual size exceeds a sane maximum (similar to the way GitHub's own Contents API path enforces size limits, e.g. `fetchRawFile`/inline content size checks). Fail fast with a clear error rather than allowing unbounded decompression/read of attacker-supplied OCI layer data.

### Proof of Concept
1. Host or control an OCI registry that responds to `remote.Referrers` for a target image digest with a manifest whose `ArtifactType` is `application/vnd.dev.sigstore.bundle+json`.
2. Have the referenced layer's compressed content decompress to a very large size (a decompression bomb) or simply serve a very large layer.
3. Run `gh attestation verify oci://<attacker-registry>/<image>:<tag> --owner <org> --bundle-from-oci` (or `gh attestation download oci://<attacker-registry>/<image>:<tag> --owner <org>`).
4. `LiveClient.GetAttestations` calls `layers[0].Uncompressed()` then `io.ReadAll(layer0)` with no size limit, causing the `gh` process to consume memory proportional to the attacker-chosen (decompressed) size until it exhausts available memory.

func GetOCIAttestations(client oci.Client, artifact artifact.DigestedArtifact) ([]*api.Attestation, error) {
	attestations, err := client.GetAttestations(artifact.NameRef(), artifact.DigestWithAlg())
	if err != nil {
		return nil, fmt.Errorf("failed to fetch OCI attestations: %w", err)
	}
	if len(attestations) == 0 {
		return nil, fmt.Errorf("no attestations found in the OCI registry. Retry the command without the --bundle-from-oci flag to check GitHub for the attestation")
	}
	return attestations, nil
}
