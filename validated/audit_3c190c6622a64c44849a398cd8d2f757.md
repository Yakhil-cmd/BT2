### Title
Unhandled crash in optional AA dry-run path when a posted unit triggers a primary AA — ([File: network.js])

### Summary
The BIND CVE crashes the resolver process when an optional feature (`stale-answer-client-timeout`) is enabled and the resolver processes a specific query type (RRSIG) that hits an unguarded code path. The ocore analog is `conf.bDryRunNewTriggers`, an opt-in operator setting that, when enabled, makes `handleJoint()`'s `ifOk` callback in `network.js` synchronously dry-run every AA trigger contained in a freshly-validated, attacker/peer-supplied unit **before** the process has finished saving/committing that unit, with no `try/catch` around the call chain.

### Finding Description
When `conf.bDryRunNewTriggers` is turned on (non-light, non-catchup node), every time a unit that has already passed `validation.validate()` and calls back via `ifOk` in `network.js`, and it is a primary AA trigger (`objValidationState.count_primary_aa_triggers`), the code does: [1](#0-0) 

- `aa_composer.getTrigger()` is called on the untrusted `objJoint.unit` and can `throw Error("no outputs to " + receiving_address)` synchronously. [2](#0-1) 
- `aa_composer.dryRunPrimaryAATrigger()` runs the full trigger execution pipeline (`handleTrigger`), which contains multiple unconditional `throw Error(...)` statements reachable from attacker-controlled AA definitions/triggers (e.g. "bad AA definition", "assocBalances and bAir do not match", "unexpected params", "base AA not found") as well as from `evaluateAA`/formula evaluation errors that are not always funneled through the `bounce()` error-handling callback. [3](#0-2) [4](#0-3) 

`ifOk` is declared `async` but is invoked as a plain (non-awaited) callback from `validation.js`: [5](#0-4) 

Because nothing ever attaches a `.catch()` to the promise this `async ifOk` function returns, any exception thrown inside the `await aa_composer.dryRunPrimaryAATrigger(...)` chain becomes an **unhandled promise rejection**. The codebase has no global `unhandledRejection` handler in production code (only in test files), and the existing `uncaughtException` handler in `network.js` explicitly `throw err` again to intentionally crash the whole node process to avoid an inconsistent state: [6](#0-5) 

The comment at the call site — "if it would crash, let it crash now, not when we execute the trigger for real" — shows this is a deliberate but unguarded fail-fast design; it does not anticipate that the "crash" happens inside an unawaited async function whose rejection is unhandled, i.e., it takes down the entire node process (not just the trigger execution), exactly analogous to BIND's resolver crashing the whole `named` daemon when a specific optional-feature code path throws on a crafted query.

### Impact Explanation
Since `ifOk` runs before the unit's real persistence/response processing completes for every peer connection and this code path is reachable by any node/light peer that posts (or forwards) a unit which triggers an AA, a single such unit can crash any full node that has opted into `bDryRunNewTriggers`. Because this happens during normal unit-relay processing (not caused by a malicious peer/protocol violation but by a *validly formed* unit that happens to interact with an AA in a way that hits one of the `throw` statements in `handleTrigger`), repeated posting of such units can prevent the affected nodes from confirming new units, matching the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Likelihood is bounded by the fact that `bDryRunNewTriggers` is an opt-in configuration flag — nodes must explicitly enable it. However, on any node/hub operator that does enable it (e.g., to get early crash detection, per the comment's intent), the trigger conditions are reachable with a legitimately-validated unit: any attacker can post a payment to an AA address whose triggered execution deterministically hits one of the unguarded `throw Error(...)` statements in `aa_composer.js` (e.g. by targeting a parameterized AA and crafting inputs that make `handleTrigger`'s early-exit checks fail before `bounce()` is invoked, or a scenario reaching `getTrigger`'s `no outputs to` throw due to a race/edge case in output aggregation). No special privileges, malicious peer behavior, or protocol violation is required — a normal posted/forwarded unit suffices.

### Recommendation
Wrap the `bDryRunNewTriggers` block in `network.js`'s `ifOk` handler in a `try/catch` (and ensure the returned promise from the `async ifOk` function is always consumed with `.catch()` wherever it is invoked), so that a dry-run failure only logs/records the anomaly instead of producing an unhandled rejection that crashes the entire node process. Additionally, audit `aa_composer.js`'s `handleTrigger`/`dryRunPrimaryAATrigger`/`getTrigger` for `throw Error(...)` statements that are reachable from untrusted unit/trigger data and are not routed through the `bounce()` error path, converting them to caught, bounced errors where the condition can be triggered by external input rather than only by internal programming invariants.

### Proof of Concept
1. Enable `bDryRunNewTriggers` in a node's configuration.
2. Deploy or use an existing autonomous agent (AA) whose definition can be driven into one of the unconditional-throw branches of `handleTrigger` by attacker-supplied trigger data — for instance, a parameterized AA (`base_aa`) scenario, or a payment message whose output aggregation logic can trip `getTrigger()`'s `"no outputs to " + receiving_address` guard under specific concurrent/edge conditions.
3. Post (or have a peer forward) a unit that pays to this AA, causing `objValidationState.count_primary_aa_triggers` to be set and `validation.js` to invoke `callbacks.ifOk()`.
4. Observe that `network.js`'s `ifOk` async handler throws inside `aa_composer.dryRunPrimaryAATrigger`, producing an unhandled promise rejection that is not caught anywhere in the call chain, ultimately crashing the node process (verified structurally via the code paths cited above; a live reproduction requires constructing a concrete AA definition/trigger pair that hits one of the throw sites, which was not verified end-to-end in this analysis due to tool/time constraints).

**Note on confidence**: I was not able to fully verify, from static reading alone, a concrete attacker-controlled AA definition/trigger combination that deterministically reaches one of `handleTrigger`'s raw `throw Error(...)` statements (as opposed to the `bounce()`-guarded error path) without further live testing. The core mechanism — an unguarded, unawaited-rejection-prone opt-in dry-run path that can crash the whole process on unit ingestion — is confirmed by the code cited above.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
