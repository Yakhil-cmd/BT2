### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA, with no repository or stack scoping, so a `status` webhook that is legitimately signed for one GitHub repository can mutate the commit status of a `Commit` row belonging to a completely different stack/repository whenever the two commits share the same SHA (e.g. via a fork of the victim's repository). The `review_stacks_enabled` framing in the question is not supported by the cited files — that flag only affects whether a review stack is auto-provisioned from a Pull Request webhook and has no bearing on how an already-existing stack's commit statuses are looked up or evaluated.

### Finding Description
The broken binding is: `Commit#stack_id` (the commit found by `Commit.where(sha: params.sha)`) is implicitly assumed to equal `Repository.from_github_repo_name(payload.repository.full_name).stacks` (the repository that actually authenticated the webhook) — but the code never enforces this equality.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This query is global across the `commits` table; unlike every PR-event handler (`OpenedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`), which resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope subsequent lookups to `repository.stacks`/`repository.review_stacks` [2](#0-1) , `StatusHandler` never consults `params.repository` at all, and the base `Handler#stacks` helper that does this scoping [3](#0-2)  is unused here.

`create_status_from_github!` then writes a `Status` tied to whatever stack the matched `Commit` belongs to and recomputes deployability/merge scheduling:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 
`add_status` recomputes `deployable?`/`blocked?` and triggers `stack.schedule_merges` when the new status becomes `success` or `pending` [5](#0-4) .

`verify_signature` does prevent a fully unauthenticated attacker from forging the webhook: it looks up `Shipit.github(organization: repository_owner)` and validates GitHub's HMAC signature against the raw body [6](#0-5) . This means the attacker must control (own) a repository/org that is itself legitimately integrated with the Shipit instance, and can only generate genuinely-signed webhooks for that repository. However, GitHub commit SHAs are content-addressed: if the attacker's own repo shares history with the victim's repository (e.g. a fork of the same project), an identical commit will have an identical SHA in both repositories. The attacker can then post a real GitHub status (`context: buildkite/deploy`, `state: success`) to that shared SHA from their own repository/CI. GitHub signs and delivers this webhook correctly for the attacker's own org, it passes `verify_signature`, and `StatusHandler` then matches and mutates the `Commit` row belonging to the victim's stack because the lookup is by bare SHA only.

The `review_stacks_enabled`/"provisioning precedence bug" part of the question does not hold in the cited files: `review_stacks_enabled` is only referenced in the PR-event handlers' `provision?`/`unarchive?`/`respond_to_label_change?` predicates (e.g. `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`, `reopened_handler.rb:70-75`) to decide whether to auto-create/unarchive a review stack from a Pull Request event [7](#0-6) . Neither `status_handler.rb` nor `commit.rb` reference `review_stacks_enabled`, `provisioning_behavior`, or any provisioning state at all — commit-status handling and deployability evaluation apply identically to an already-existing stack regardless of whether review stacks are enabled. So the claimed "provision precedence bug still provisions" mechanism is not part of this code path; the underlying cross-repository write does not require or depend on it.

### Impact Explanation
An attacker who legitimately owns/controls one GitHub repository registered with the Shipit instance (and who happens to share commit history, e.g. via a fork, with a victim repository/stack) can cause a `Status` to be written against a `Commit` belonging to a stack they do not own, potentially flipping `Commit#deployable?` to `true` for a required context like `buildkite/deploy`, which can unblock automatic merges/deploys (`stack.schedule_merges`) on the victim stack. This matches the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." The blast radius is any stack whose commits share a SHA with a repository the attacker controls; it is repeatable for every shared SHA the attacker can produce a status for.

### Likelihood Explanation
Requires the attacker to own/control a repository that is (a) registered as a legitimate integration with the same Shipit instance (so `verify_signature` succeeds), and (b) shares actual commit history/SHAs with the victim's repository (typically via forking a public repo). This is a realistic precondition for open-source projects deployed via a shared/multi-tenant Shipit instance, but it is not "fully unauthenticated" in the sense of requiring zero setup — it requires the attacker to have an integrated repository of their own. The `review_stacks_enabled` precondition asserted in the question is unnecessary and unsupported by the code.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, analogous to the PR handlers: resolve `Repository.from_github_repo_name(params.repository.full_name)` and restrict the `Commit` lookup to `repository.stacks.flat_map(&:commits).where(sha: params.sha)` (or add a `repository_id`/join constraint to the `Commit`/`Stack` query) instead of a bare `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not update commit status for a stack belonging to a different repository sharing the same sha" do
  victim_repo  = create_repository(owner: "victim-org", name: "app")
  victim_stack = create_stack(repository: victim_repo, required_statuses: ["buildkite/deploy"])
  shared_sha   = "a" * 40
  commit = victim_stack.commits.create!(sha: shared_sha, message: "shared commit")

  payload = payload_parsed(:status_success).merge(
    "sha" => shared_sha,
    "context" => "buildkite/deploy",
    "state" => "success",
    "repository" => { "full_name" => "attacker-org/other-repo" }
  )

  refute commit.reload.deployable?, "sanity: not deployable before"

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  # EXPECTED (secure): commit belonging to victim_stack must not be mutated
  # by a status webhook authenticated for attacker-org/other-repo.
  assert_not commit.reload.deployable?,
    "Commit#deployable? for victim_stack must equal its pre-webhook value; " \
    "it changed due to a status authenticated for a different repository"
end
```
This test currently fails against `Commit.where(sha: params.sha)` in `status_handler.rb`, demonstrating the unscoped write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      ].join(' '))
