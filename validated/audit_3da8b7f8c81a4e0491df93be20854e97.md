## Analysis

`WebhooksController#verify_signature` selects **which** GitHub App secret to validate the HMAC signature against based on `repository_owner`, a value extracted from the *unauthenticated* request body itself (`params.dig('repository', 'owner', 'login')`, with a fallback to `organization.login`): [1](#0-0) [2](#0-1) 

That check only proves "this body was signed with *some organization's* configured `webhook_secret`" — it never binds the signature to the repository/commit/stack that the event handlers subsequently mutate. `create` then hands the *entire raw JSON body* to every registered handler for the event type: [3](#0-2) 

Handlers resolve the target `Repository`/`Stack` from a **different** field of the same attacker-controlled body — `repository.full_name` — completely decoupled from `repository.owner.login` used for signature selection: [4](#0-3) [5](#0-4) 

Worse, `StatusHandler` doesn't even scope by repository at all — it matches by SHA across *every* commit stored in the entire Shipit instance: [6](#0-5) 

`Shipit.github` is explicitly designed to be multi-tenant, with independent `webhook_secret` per organization (see the double-org fixture), so a Shipit deployment routinely trusts several distinct organizations with their own secrets: [7](#0-6) 

## Title
Webhook signature is validated against `repository.owner.login`, but event handlers act on the unrelated `repository.full_name`/`sha` fields of the same signed body, letting a webhook signer for one organization forge events against a different repository/stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` proves only that the raw request body was HMAC-signed by *the organization named in the payload's own `repository.owner.login`/`organization.login` field*. It never verifies that this organization is the one whose repository is actually operated on. Downstream handlers (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`, and especially `StatusHandler`) pick their target `Stack`/`Repository`/`Commit` from other, unchecked fields of the same JSON body (`repository.full_name`, `sha`), breaking the binding "organization that authenticated" == "repository that is written."

### Finding Description
`verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight out of the untrusted JSON (`params.dig('repository', 'owner', 'login')`), then verifies the raw body's HMAC against that organization's configured `webhook_secret`. As long as the HMAC checks out for *any* configured organization named in the payload, the request passes `verify_signature` and is dispatched to handlers with the full, attacker-supplied JSON — [3](#0-2) .

Handlers never re-check that the repository they act on belongs to the organization that produced a valid signature:
- `Handler#stacks` resolves the target purely from `payload.dig('repository', 'full_name')` — [4](#0-3) , a field independent of `repository.owner.login`.
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matched branch — [8](#0-7) .
- `StatusHandler#process` doesn't consult `repository` at all; it matches `Commit.where(sha: params.sha)` **across the whole database** and writes a GitHub status onto it — [6](#0-5) .
- `CheckSuiteHandler#process` similarly only scopes by `stacks` (again via `repository.full_name`) and branch — [9](#0-8) .

Since Shipit explicitly supports multiple GitHub organizations, each with an independently configured `webhook_secret` — [7](#0-6)  — an unprivileged party who controls (or is an admin of) *any one* of those organizations' GitHub Apps can obtain that organization's `webhook_secret` and use it to sign a JSON body whose `repository.owner.login` names their own organization, while its `repository.full_name`/`sha` fields target a completely different tracked repository/stack/commit.

### Impact Explanation
This is a cross-repository write: a party trusted only for organization A's webhooks can forge:
- Fake `push` events causing `sync_github`/deploy pipeline activity on any stack tracked under organization B, keyed on an attacker-chosen `after` SHA.
- Fake `status` events forging a `success`/`failure` CI status onto *any* commit in the entire Shipit database (no repository scoping whatsoever), which can be used to fabricate a green CI state that gating logic ("wait for CI") relies on before allowing a deploy - directly enabling an unauthorized deploy of a commit that never actually passed CI.
- Fake `check_suite`/`pull_request` events (archive/unarchive review stacks, merge status changes) against repositories/organizations the attacker does not own.

This matches the Critical bar ("an unauthorized deploy...") because the CI-status forgery path lets an attacker manufacture the precondition ("commit is green") that real deploy authorization logic depends on, for repositories outside their control.

### Likelihood Explanation
Requires only administrative control over one GitHub App/organization already registered in the same multi-tenant Shipit instance (a normal, supported configuration, as shown by the double-org fixture) — no Shipit session, API token, or the victim organization's own secret is needed. The attacker crafts the raw POST body and signs it with the secret they legitimately hold; Shipit's own checks never cross-reference the signing organization against the repository actually mutated.

### Recommendation
- Enforce that the organization used to select/verify the webhook secret matches the organization implied by every repository-scoped field the handler will use (i.e., `repository.full_name`'s owner segment must equal the authenticated `repository_owner`), rejecting the request otherwise.
- Scope `StatusHandler`'s `Commit.where(sha:)` lookup (and any other handler) to commits belonging to the authenticated organization's repositories, never to the whole instance.
- Consider signing/validating per-repository rather than per-organization where multiple repositories share one GitHub App installation.

### Proof of Concept
1. Attacker administers `OrgA`'s GitHub App installed on the shared Shipit instance and knows `OrgA`'s `webhook_secret` (a normal capability for any org onboarded per `secrets_double_github_app.yml`).
2. Attacker crafts:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "victim-org/victim-repo" },
  "sha": "<real sha of a commit in victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose secret matches, so the request passes — [1](#0-0) .
5. `StatusHandler#process` finds the commit by `sha` alone (no organization check) and writes the forged "success" status onto `victim-org/victim-repo`'s commit — [6](#0-5) .

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
