## Finding

### Title
`liquidate-multi` batch entirely reverts on an `unwrap-panic` triggered by a single mismatched position, blocking liquidation of unrelated, legitimately unhealthy borrowers bundled in the same call - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` is documented and designed so that a failure in one bundled position "returns error codes but doesn't revert entire batch" [1](#0-0) . This resilience only holds for controlled `(err ...)` paths produced via `try!`/`asserts!`. However, `liquidate` itself calls `unwrap-panic (get-cached-indexes debt-aid)` in multiple places [2](#0-1) [3](#0-2) , which is populated only for asset IDs that are actually present in the borrower's debt list, via `accrue-user-debts (get debt pos-full)` [4](#0-3) . The `debt-aid`/`debt-ft` for each position, however, is chosen by the caller of `liquidate-multi`, independent of whether the target borrower actually still holds debt in that asset [5](#0-4) . If any single bundled position no longer has debt in the specified asset when the batch executes (e.g., the borrower repays/clears that specific debt in the same block, front-running the batch transaction), `get-cached-indexes` returns `none` for that entry, `unwrap-panic` triggers a genuine Clarity runtime error, and — unlike a returned `(err ...)`, which `map` would simply collect into the results list via `liquidate-multi`'s `(ok (map call-liquidate positions))` [6](#0-5)  — this runtime error aborts the *entire* transaction, rolling back every other liquidation bundled in the same call.

### Finding Description
- Shared state: the single atomic `liquidate-multi` transaction and its all-or-nothing execution outcome, shared by every borrower/position bundled into it by the caller.
- Attacker: any borrower included (deliberately or incidentally) in someone else's `liquidate-multi` batch, who can make the batch's chosen `debt-ft` for their position stop matching an actual debt they hold (e.g., a small same-block repay of exactly that asset, front-running the pending batch liquidation transaction).
- Victim: other, unrelated borrowers bundled in the same `liquidate-multi` call whose positions are genuinely liquidatable — their liquidation gets reverted along with the attacker's, even though the liquidator's transaction is otherwise perfectly valid for them.
- Root cause: `liquidate` unconditionally does `unwrap-panic (get-cached-indexes debt-aid)` [2](#0-1) [3](#0-2)  instead of using a checked `unwrap!`/`asserts!` that would produce a normal `(err ...)` response collectible by `map`. Because `accrue-and-cache`/`accrue-user-debts` only primes the cache for assets actually in the borrower's debt list [7](#0-6) , any mismatch between the caller-supplied `debt-ft` and the borrower's live debt composition at execution time produces a cache miss and a hard runtime panic rather than a graceful error.

This is directly analogous to the reported bug class: an unchecked/unvalidated conversion (`unwrap-panic` standing in for Rust's `.expect()`) on a value that can legitimately be absent/negative under conditions influenced by a third party, causing a crash (here, a full-transaction abort) instead of a contained error — except here the blast radius extends to other users' positions bundled in the same shared transaction, exactly matching the accepted "ordering dependence between two users in one block" analog category.

### Impact Explanation
An attacker can grief liquidators' batched calls, causing temporary freezing of liquidation of otherwise-valid unhealthy positions bundled together in the same `liquidate-multi` transaction. This delays bad-debt realization for those unrelated borrowers, extending the window during which their under-collateralized debt continues to accrue, ultimately increasing losses socialized to suppliers via `socialize-debt-asset` [8](#0-7)  when they are eventually liquidated. This lands on the in-scope "temporary freezing of funds" impact class, since legitimate liquidations (and thus timely bad-debt clearing) are blocked for an indeterminate period whenever a batch is crafted or gamed this way.

### Likelihood Explanation
Any liquidator who batches multiple positions in a single `liquidate-multi` call (the exact use case the function's own comments recommend: "Prevents front-running attacks that prevent bad debt socialization") is exposed. An attacker only needs the ability to alter their own debt composition for the specific asset the liquidator selected, in the same block before the batch executes — a normal repay of a small amount of that debt is sufficient. No privileged access, DAO compromise, or oracle manipulation is required.

### Recommendation
Replace the `unwrap-panic (get-cached-indexes debt-aid)` calls in `liquidate` (used both directly and via `scale-debt-for-liquidation`) with a checked `unwrap!`/`asserts!` returning a proper `(err ...)`, so that a per-position failure surfaces as a normal error entry in `liquidate-multi`'s result list instead of aborting the whole batch transaction.

### Proof of Concept
1. Liquidator observes borrowers Alice and Bob are both unhealthy, and calls `liquidate-multi` with two positions: `{borrower: alice, debt-ft: usdc, ...}` and `{borrower: bob, debt-ft: usdc, ...}`.
2. Alice, monitoring the mempool, submits (or has already arranged) a same-block `repay` that fully clears her USDC debt just before the batch executes, front-running the liquidator's transaction.
3. When `liquidate-multi` executes, `call-liquidate` for Alice's position calls `liquidate`, whose `accrue-user-debts (get debt pos-full)` no longer includes the USDC asset id (Alice has no USDC debt anymore), so `index-cache` has no entry for it.
4. `unwrap-panic (get-cached-indexes debt-aid)` at [2](#0-1)  hits `none` and triggers a Clarity runtime error.
5. The runtime error propagates out of `map call-liquidate positions`, aborting the entire `liquidate-multi` transaction — Bob's legitimate, unrelated liquidation is also reverted, even though nothing about Bob's position was invalid.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
