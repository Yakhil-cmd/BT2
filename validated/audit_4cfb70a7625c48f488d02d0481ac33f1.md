### Title
Unbounded recursive lookup of shared-address control chains causes memory exhaustion - ([File: wallet_defined_by_addresses.js])

### Summary
`readAllControlAddresses()` in `wallet_defined_by_addresses.js` walks the `shared_address_signing_paths` table recursively to resolve all "control" (member) addresses and cosigner devices behind a shared address, with no cycle detection and no depth limit. Shared-address definitions are accepted individually via `handleNewSharedAddress()` without validating that they do not form a cross-address cycle with previously accepted shared addresses. A paired device (or two paired devices acting in concert) can therefore make a wallet locally store two (or more) shared addresses whose member graphs reference each other, and then trigger `readAllControlAddresses()` (e.g. by sending a private payment chain to one of those addresses) to drive the wallet into unbounded recursion, similarly to how `parse_dos_extended` in the CVE recurses forever over a self-referencing extended-partition record and exhausts memory.

### Finding Description
`readAllControlAddresses` recurses on the addresses discovered in `shared_address_signing_paths` with no visited-set / depth cap: [1](#0-0) 

Each level issues a DB query, builds `arrControlAddresses` from the query result, and immediately calls itself again with those addresses; the result arrays are additionally accumulated via `_.union` in every returned callback. If the address graph contains a cycle (A's members include B, B's members include A), this function never reaches the `rows.length === 0` base case and will recurse without bound, growing the call stack, JS heap (each level's array and closures), and issuing unbounded DB queries.

The rows that feed this recursion come from `shared_address_signing_paths`, which is populated by `addNewSharedAddress()` whenever a `new_shared_address` message from a paired device is accepted: [2](#0-1) 

The acceptance path validates the incoming definition with `validateAddressDefinition`, which calls `Definition.validateDefinition` with `bAllowUnresolvedInnerDefinitions = true` and a fake unit with `bAllowUnresolvedInnerDefinitions` set: [3](#0-2) 

This validation only checks the internal structure/complexity of the single definition being added — it does not (and cannot, since the referenced address is treated as "unresolved" and skipped) verify whether accepting this shared address, together with shared addresses accepted earlier or later, creates a member-address cycle across the `shared_addresses` / `shared_address_signing_paths` tables. Two paired devices (or one attacker controlling two device identities the victim has paired with) can therefore get the victim's wallet to store shared address A (member: address B) and shared address B (member: address A) as two independently "valid" shared addresses.

Once such a cycle exists locally, any code path that calls `readAllControlAddresses` on this address set will recurse indefinitely. This function is invoked from wallet private-payment forwarding logic: [4](#0-3) 

`forwardPrivateChainsToOtherMembersOfSharedAddresses` is reached whenever the wallet processes a private payment chain whose author/output addresses intersect with the cyclic shared addresses, e.g. via `handlePrivatePaymentChains` from a private-payment counterparty: [5](#0-4) 

This mirrors the CVE-2016-5011 bug class: a crafted structure (there, a self-referencing extended partition table entry; here, a self-referencing shared-address member graph) is fed into a recursive parser/resolver with no cycle/­depth guard, leading to unbounded memory growth and denial of service.

### Impact Explanation
Triggering this causes the wallet process to enter unbounded recursion, consuming stack and heap memory and issuing unbounded DB queries until the process crashes or becomes unresponsive. Because this runs inside the same process handling normal wallet operations (payment forwarding, message handling from the hub/peers), a paired counterparty or private-payment sender can render the victim wallet unable to process further private payments or other wallet operations — a "network unable to confirm/process new units for this wallet" style denial of service, without requiring any privileged network or hub position.

### Likelihood Explanation
Reachability is via steps available to a normal paired device / private-payment counterparty: (1) get the victim to accept two shared addresses (via `new_shared_address` messages) whose definitions reference each other by address, which passes existing per-definition validation because inner address resolution is skipped (`bAllowUnresolvedInnerDefinitions`); (2) send a private payment chain touching one of those addresses to trigger `forwardPrivateChainsToOtherMembersOfSharedAddresses` → `readAllControlAddresses`. Both steps use documented, reachable message types (`new_shared_address`, private payment chain forwarding) and require no malicious node/hub/network position — only normal paired-device / counterparty capability.

### Recommendation
- Add cycle detection (a visited-address set) and/or a maximum recursion depth to `readAllControlAddresses` (and any similar recursive resolvers such as `readFullSigningPaths`), aborting/erroring instead of recursing indefinitely.
- When accepting a new shared address definition in `handleNewSharedAddress`/`addNewSharedAddress`, check whether any of its member addresses are themselves existing shared addresses that (directly or transitively) reference the new address, and reject definitions that would introduce a cycle in the persisted `shared_addresses` graph.

### Proof of Concept
1. Attacker controls (or colludes with) two paired devices D1 and D2 with the victim wallet W.
2. D1 sends `new_shared_address` for address SA_A whose definition is `["address", "SA_B"]` (member address SA_B), matching signer info consistent with the local per-definition validation (which does not resolve/verify SA_B).
3. D2 sends `new_shared_address` for address SA_B whose definition is `["address", "SA_A"]`.
4. Both are accepted locally by W via `handleNewSharedAddress` → `addNewSharedAddress`, populating `shared_address_signing_paths` with SA_A→SA_B and SA_B→SA_A entries.
5. Attacker sends a `private_payment` chain whose output/author address is SA_A (or SA_B) to W, causing `handlePrivatePaymentChains` → (eventually) `forwardPrivateChainsToOtherMembersOfSharedAddresses` → `readAllControlAddresses(conn, [SA_A], ...)`.
6. `readAllControlAddresses` recurses SA_A→SA_B→SA_A→... indefinitely, exhausting memory/stack and crashing or hanging the victim's wallet process.
