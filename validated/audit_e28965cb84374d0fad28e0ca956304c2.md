### Title
Webhook signature verification is keyed off an attacker-controlled field that is decoupled from the field the event handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the inbound HMAC signature against, by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, unauthenticated request body. The event handlers that subsequently act on the very same payload (e.g. `PushHandler`, and every `PullRequest::*Handler`) instead resolve the target `Repository`/`Stack` using a *different* field of the same payload: `repository.full_name`. Nothing enforces that the organization used to pick the verification secret is the same organization that owns the repository the handler mutates.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
```
`repository_owner` is used only to pick `Shipit.github(organization:)`, i.e. which of the potentially multiple configured GitHub Apps' `webhook_secret` must sign the payload [1](#0-0) , [2](#0-1) .

The handlers that then execute the actual event never re-check that binding; they derive the target repository from a totally separate field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) 

`PushHandler` uses this to sync any stack whose branch matches, using an attacker-controlled `after` sha: [4](#0-3) 

Every `PullRequest::*Handler` independently re-derives `repository` from `params.repository.full_name` for its own authorization/archival decisions: [5](#0-4) [6](#0-5) 

Shipit explicitly supports multiple GitHub App configurations, each with its own (optional) `webhook_secret`, keyed by organization login: [7](#0-6) . Critically, `verify_webhook_signature` short-circuits to `true` whenever an app's `webhook_secret` is blank/unset, which the setup docs and template explicitly present as a normal, supported configuration: [8](#0-7) , [9](#0-8) , [10](#0-9) .

**Binding that should hold**: `organization_authenticating_signature == organization_owning(repository.full_name)`. In this engine that equality is never checked. The controller reads `params.dig('repository','owner','login')` to authenticate, while `Repository.from_github_repo_name` independently parses `owner` out of `full_name` (`github_repo_name.downcase.split('/')`, see [11](#0-10) ) to find the actual `Stack`. An attacker who fully controls the raw JSON POST body (the endpoint is a public, unauthenticated Rails controller with `skip_before_action :verify_authenticity_token`, see [12](#0-11) ) can set `repository.owner.login` to an organization whose GitHub App has no `webhook_secret` configured (or one the attacker otherwise controls), while setting `repository.full_name` to `"<victim-org>/<victim-repo>"`. The signature check passes (since that org's secret check is a no-op), but the handler dispatch acts on the victim organization's stack.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary called out as in-scope. Concretely, with `PushHandler`, an attacker can force `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` to run against any tracked stack belonging to a different, victim organization, without ever presenting a valid signature for that organization. Depending on downstream sync/continuous-delivery configuration this can trigger unauthorized deploy pipelines to run against attacker-chosen commits/branches for a repository the attacker has no access to and whose organization's real webhook secret they never possessed - satisfying the "unauthorized deploy" bar for High/Critical impact. It also lets an attacker forge `pull_request` lifecycle events (open/close/label) against review stacks of a repository they don't control, since each `PullRequest::*Handler` re-derives `repository` the same insecure way.

### Likelihood Explanation
The prerequisite - at least one configured GitHub App/organization with no `webhook_secret` (explicitly shown as a supported, common configuration in the docs, template, and test fixtures) or an attacker who owns any one of the multiple orgs pointed at this Shipit instance - is realistic in any multi-tenant/multi-org Shipit deployment, which is a first-class supported topology (see `secrets_double_github_app.yml`). No authentication, GitHub App private key, or `webhook_secret` for the *victim* organization is required; only the ability to POST arbitrary JSON to the public `/webhooks` endpoint.

### Recommendation
After `verify_signature` succeeds, re-derive the organization/repository the handler is about to act on (`repository.full_name`) and assert its owner equals `repository_owner`/the verified organization before dispatching to any handler. Reject the request if they differ. Additionally, avoid silently treating a missing `webhook_secret` as "signature verification passed"; require an explicit opt-in for unsigned webhook acceptance, scoped narrowly per organization.

### Proof of Concept
1. Configure two GitHub Apps, `OrgA` (no `webhook_secret` set, matching the documented default/example) and `OrgB` (victim, with tracked stacks and a real `webhook_secret`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally - no `X-Hub-Signature` header is even required.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, matching the real victim stack, and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")`, even though the attacker never had `OrgB`'s webhook secret.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
