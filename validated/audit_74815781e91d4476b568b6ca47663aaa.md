### Title
`add_liquidity` mints LP tokens based on desired transfer amount, not the actual amount received by the pool account - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet-asset-conversion::do_add_liquidity` (invoked by the public, unprivileged `add_liquidity` extrinsic) transfers `amount1`/`amount2` into the pool account via `T::Assets::transfer(..)?` but discards the returned actual-transferred amount and instead uses the pre-transfer, desired `amount1`/`amount2` values to compute the LP token amount minted to the caller. This mirrors the reported Allo.sol `fundPool` pattern, where `increasePoolAmount` used the pre-fee amount instead of the actual balance delta caused by a fee-on-transfer token.

### Finding Description
`do_add_liquidity` computes `amount1`/`amount2` (desired/optimal contribution amounts) from pre-transfer reserves, then: [1](#0-0) 
```rust
T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
T::Assets::transfer(asset2, who, &pool_account, amount2, Preserve)?;
```
The return value of `transfer()` — which is explicitly documented elsewhere in the codebase as "the actual amount placed into `dest`" and can differ from the requested amount — is discarded (the `?` only propagates errors, not the `Ok` value). [2](#0-1) 

Downstream, LP token minting is computed directly from the *requested* `amount1`/`amount2`, not from any post-transfer balance check of `pool_account`: [3](#0-2) 

This is structurally identical to the reported bug: the protocol assumes "amount requested to move" == "amount actually received by the custody account," and uses the former for share/pool accounting. In the fungible/fungibles `Mutate::transfer` default trait implementation, this discrepancy is architecturally possible: `decrease_balance` is invoked with `Precision::BestEffort`, which silently caps the withdrawal at `reducible_balance` instead of erroring, while `increase_balance` is (in the default implementation) invoked with the original, uncapped `amount` rather than the actual amount debited — and the function unconditionally returns `Ok(amount)` (the request), not the true post-mutation delta: [4](#0-3) 

### Impact Explanation
If the actual amount credited to `pool_account` for either asset is less than `amount1`/`amount2` (e.g., due to destination-side existential-deposit/dust handling, or a non-standard `T::Assets` implementation whose `transfer` legitimately returns less than requested — as its own docstring allows), `do_add_liquidity` still mints LP tokens as if the full `amount1`/`amount2` was deposited. This overstates the depositor's contribution relative to the real reserve increase, diluting existing liquidity providers' claim on the pool (a value-transfer/integrity issue), analogous in class to the reported Medium-severity `fundPool` bug.

### Likelihood Explanation
Reachability is unprivileged and direct: `add_liquidity` is a standard signed extrinsic on `pallet-asset-conversion`, callable by any account with sufficient balance, no governance or special role required. However, whether the discrepancy is *actually triggerable* depends on the concrete `T::Assets`/`T::PoolAssets` implementation configured in a given runtime (e.g., `pallet-assets`, native `pallet-balances`, or a custom `fungibles` adapter). I was not able to fully confirm, within the available tool budget, whether the production overrides in `substrate/frame/balances/src/impl_fungible.rs` and `substrate/frame/assets/src/impl_fungibles.rs` correctly propagate the actual transferred amount and reject (rather than silently truncate) short transfers in the currently deployed configuration — grep confirmed these files override `transfer`/`decrease_balance`/`increase_balance`, but I did not read their bodies to verify Exact-vs-BestEffort semantics end-to-end. This is a material open question that a background agent or reviewer would need to close before treating this as more than a Low/Medium-likelihood structural finding.

### Recommendation
In `do_add_liquidity`, capture the actual amounts returned by `T::Assets::transfer(...)` (rather than discarding them) and use those actual values — not the desired `amount1`/`amount2` — for LP token minting, event emission, and reserve accounting. Alternatively, use `Precision::Exact` for these transfers so any shortfall causes the whole extrinsic to fail atomically rather than silently under-crediting the pool.

### Proof of Concept
No test was executed. A concrete PoC would require constructing a runtime configuration where `T::Assets::transfer` legitimately returns an actual amount smaller than the requested `amount1`/`amount2` (e.g., via `pallet-assets` dust/ED edge cases on the `pool_account`, or a custom `fungibles::Mutate` adapter that exhibits BestEffort truncation), then calling `add_liquidity` and asserting `LiquidityAdded.lp_token_minted` corresponds to `amount1`/`amount2` while `pool_account`'s real balance increase is smaller — demonstrating dilution of existing LP holders. This reproduction was not built or run here; the finding is based on static code inspection of `substrate/frame/asset-conversion/src/lib.rs:855-879` and the documented/actual semantics of `T::Assets::transfer` in `substrate/frame/assets/src/functions.rs:623-646` and `substrate/frame/support/src/traits/tokens/fungible/regular.rs:317-339`.

	/// Transfer funds from one account into another.
	///
	/// A transfer where the source and destination account are identical is treated as No-OP after
	/// checking the preconditions.
	fn transfer(
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(source, amount).into_result(preservation != Expendable)?;
		Self::can_deposit(dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(dest, amount, BestEffort);
		Self::done_transfer(source, dest, amount);
		Ok(amount)
	}
