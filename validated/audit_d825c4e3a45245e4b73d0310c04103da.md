### Title
Cross-organization/cross-repository forged commit statuses via unscoped `StatusHandler` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the `webhook_secret` of whichever GitHub organization is named in `payload.dig('repository','owner','login')`, but the `status` event handler that actually mutates data never re-checks that the commit it writes to belongs to that same organization/repository. `StatusHandler` resolves the target purely by SHA, globally, across every stack in the Shipit instance.

### Finding Description
The signature check in `verify_signature` selects the GitHub App/secret to validate with based on the attacker-controlled payload field `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 

This only proves the requester holds the `webhook_secret` for *some* organization configured in `Shipit.github` (Shipit explicitly supports multiple independently-administered GitHub organizations sharing one instance, per `docs/setup.md`'s "Using Multiple Github Applications" section and `config/secrets.development.shopify.yml`). It never checks that the repository the payload claims to describe (`repository.full_name`) is actually owned by that organization, nor that the record being mutated belongs to that repository.

`StatusHandler#process`, invoked for the `status` event, ignores repository scoping entirely and resolves target commits purely by SHA across the whole database: [3](#0-2) 

Unlike `PushHandler`, which scopes lookups through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), `StatusHandler` never calls `stacks` or checks `repository_name` at all. `Commit#create_status_from_github!` then persists attacker-controlled `state`, `description`, `target_url`, and `context` directly onto that commit: [4](#0-3) 

So the binding that should hold — "organization whose webhook secret authenticated the request" == "repository/stack whose commit is written" — is never enforced. Only the *raw bytes* of the payload are covered by the HMAC signature; nothing ties the signing organization to the specific commit/stack being modified.

### Impact Explanation
An administrator of Organization A, who legitimately possesses Org A's `webhook_secret` (documented, generated by them when creating their own GitHub App per `docs/setup.md`), can sign a forged `status` webhook whose `repository.owner.login` is `"OrgA"` (satisfying `verify_signature`) but whose `sha` is a commit SHA belonging to a stack owned by a completely different Organization B on the same shared Shipit instance. `StatusHandler` will happily attach a fabricated `state: "success"` status to that foreign commit, with no cross-check against `repository.full_name`. Since `Commit#deployable?` and continuous-deployment gating (`schedule_continuous_delivery`, `blocked?`, required/blocking statuses) rely on these `Status` records: [5](#0-4) [6](#0-5) 

this can be used to falsely satisfy CI-status requirements on a repository the attacker has no access to, unblocking a merge/deploy that should have been gated — i.e., an unauthorized deploy through a stack the attacker does not own or have write access to. This matches the "Critical: unauthorized deploy" impact bucket.

### Likelihood Explanation
This requires only that (a) the Shipit instance hosts more than one GitHub organization (an explicitly documented, supported configuration), and (b) the attacker administers/controls one of those organizations' GitHub Apps (fully "unprivileged" with respect to the victim organization). No GITHUB_TOKEN, `api_clients_secret`, or session compromise is needed — only knowledge of one's own legitimately-issued `webhook_secret`, which by design every onboarded organization's administrator possesses. Guessing/knowing a target commit SHA is trivial since SHAs are public on GitHub.

### Recommendation
In `StatusHandler` (and any other handler that mutates records by cross-referencing payload identifiers), always re-verify that the resolved record's repository/stack matches `payload.dig('repository', 'full_name')` (and, transitively, that this repository belongs to the organization that satisfied `verify_signature`), e.g. scope the lookup through `Handler#stacks` the same way `PushHandler` does, rather than querying `Commit` globally by `sha` alone.

### Proof of Concept
1. Shipit is configured with two independent GitHub organizations, `orga` and `orgb`, each with its own `webhook_secret` (per the documented multi-org setup).
2. The attacker, an administrator of `orga`, knows `orga`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "sha": "<commit sha belonging to a stack owned by orgb>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orga" }, "full_name": "orga/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orga_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `orga`'s `webhook_secret`, and the signature validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `orgb` commit (no ownership check), and calls `create_status_from_github!`, writing a forged `success` status onto a commit in a stack the attacker does not control, potentially unblocking deploy/merge gating for `orgb`.
