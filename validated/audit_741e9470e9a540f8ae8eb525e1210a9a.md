### Title
Non-network-aware signed packages let an AA accept authorization from a permanently stale address definition, bypassing key-rotation revocation - (File: signed_message.js)

### Summary
`is_valid_signed_package()` is an oscript primitive that AA authors use exactly like an API "bearer token" check: an off-chain signed JSON blob (`signed_message`) is passed by an untrusted unit poster/trigger sender as proof that a given address authorized an action, and the AA trusts `true`/`false` returned by this check to gate spending or state changes. The external report's bug class is "a credential (token) that should be time/validity-bound is instead accepted based on stale-cached authorization state that was never re-validated against the credential's *current* validity." The ocore equivalent is a signed package that omits `last_ball_unit` (non-network-aware signing, still supported via `signMessage()`'s `bNetworkAware=false` branch and via the format accepted by `validateSignedMessage`).

### Finding Description
When a signed package includes `last_ball_unit`, `signed_message.js` resolves the signer's address definition **as of that stable point** (`storage.readDefinitionByAddress(conn, objAuthor.address, last_ball_mci, ...)`), which correctly reflects whatever key/definition was authoritative at the time the signature was produced: [1](#0-0) 

But when `last_ball_unit` is absent (`bNetworkAware === false`), the code takes a different path that does **not** consult the address's on-chain definition history at all — it simply trusts whatever `definition` array is embedded in the signed package itself, verifying only that its hash matches the address: [2](#0-1) 

This means a signed package produced once, using the address's *original* (or an old, later-superseded) definition, remains "valid" forever — there is no mechanism to check whether that key/definition has since been revoked, rotated via `address_definition_change`, or is otherwise no longer authoritative for the address. Unlike normal on-chain unit authorship, where `validateAuthor()` in `validation.js` always resolves the *current* stable definition at `last_ball_mci` before checking signatures: [3](#0-2) 
the AA-callable `is_valid_signed_package()` primitive allows an attacker (any unit poster/trigger sender who can supply the `signed_package` and `address` arguments to an AA) to feed in a non-network-aware package and thereby skip the freshness check entirely — analogous to `doorkeeper_token` never being validated for current validity.

`is_valid_signed_package()` itself only performs the `last_ball_unit` freshness/MC-membership check *if the field is present*: [4](#0-3) 
and simply skips straight to `validateSignedMessage()` when it's absent, inheriting the same stale-definition trust described above.

### Impact Explanation
Any AA whose logic is written as `if (is_valid_signed_package($pkg, $addr)) { ... release funds / update state ... }` — a common pattern for off-chain authorization proofs, payment channels, and order-book/exchange contracts (seen used in `test/samples/order_book_exchange.oscript` and `test/samples/payment_channels.oscript`) — can be tricked by an attacker who once obtained a validly-signed package from a counterparty **before that counterparty rotated or revoked their signing key**. Because the non-network-aware path never re-resolves the address's current definition, the AA will treat the old, no-longer-authorized definition as still valid, allowing unauthorized fund release/state changes controlled by a key the legitimate address owner believed they had revoked. This directly maps to "AA fund loss" from the accepted analog categories.

### Likelihood Explanation
Medium-High: exploitation requires only (1) an AA that uses `is_valid_signed_package()` without additionally constraining packages to be network-aware, and (2) an attacker possessing an old signed package plus knowledge that the signer later changed the address definition (e.g., a rotated multisig cosigner, a revoked payment-channel key, or an address whose definition was changed after a dispute). Both preconditions are realistic for payment-channel/order-book style AAs that are explicitly designed around this primitive, and the attacker interaction is a single trigger unit — well within reach of an unprivileged AA trigger sender.

### Recommendation
Require `last_ball_unit` (i.e., enforce `bNetworkAware`) for any signed package accepted by `is_valid_signed_package()`, or otherwise force resolution of the signer's *current* stable definition (at the AA's evaluation `mci`) rather than trusting an embedded, unanchored `definition`. At minimum, document/require AA authors to reject non-network-aware packages, and consider deprecating the non-network-aware code path in `signed_message.js`'s `validateOrReadDefinition()` for any callers reachable from AA formula evaluation.

### Proof of Concept
1. Address `A` is defined with an `and`/multisig definition granting a cosigner key `K1`. `A` signs (off-chain, non-network-aware, i.e., without `last_ball_unit`) an authorization package `P` for withdrawal from AA `X` — analogous to obtaining a bearer token.
2. Owner of `A` legitimately rotates the definition off-chain policy — sends an `address_definition_change` unit revoking `K1` and switching to `K2` (this is committed and stable on-chain).
3. Attacker who retained `P` (still containing the old embedded `definition` referencing `K1`) posts a trigger unit to AA `X` invoking `is_valid_signed_package($P, 'A')`.
4. Because `P` has no `last_ball_unit`, `validateOrReadDefinition()` in `signed_message.js` (lines 241-252) bypasses `storage.readDefinitionByAddress` entirely and validates `P`'s signature purely against the embedded (now-revoked) `definition`, returning `true`.
5. AA `X` executes the authorized action (e.g., releases funds) using a credential the address owner believes was revoked — the equivalent of using an expired/revoked `doorkeeper_token` to access a protected resource.
