### Title
`CCMenuController#stack` bypasses API-client stack scoping, allowing a token scoped to Stack A to read Stack B's CCMenu XML - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to `current_api_client.stack_id` via the `stacks`/`stack` helper methods, but `CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, bypassing that scoping. `ApiClient.authenticate` only resolves a token to an `ApiClient` record and `require_permission :read, :stack` only checks the operation:scope permission pair, not that the resolved client's `stack_id` matches the requested stack, so a token scoped to Stack A is accepted unchanged for Stack B's CCMenu URL.

### Finding Description
The claimed binding is: `current_api_client.stack_id == params[:stack_id]` (resolved stack) must hold whenever a stack-scoped `ApiClient` is used. In the base controller this is enforced by: [1](#0-0) 
`stacks` filters by `current_api_client.stack_id` when the client is scoped, and `stack` calls `stacks.from_param!`, so any controller that uses the inherited `stack` method is protected.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 
This calls `Stack.from_param!` on the full `Stack` relation, not the client-scoped `stacks` relation.

`ApiClient.authenticate` only verifies the signed token and loads the client by id; it performs no stack comparison: [3](#0-2) 

`check_permissions!`/`require_permission :read, :stack` only checks that `"read:stack"` is in the client's `permissions` array, not which stack it is scoped to: [4](#0-3) [5](#0-4) 

Exploit flow: attacker (or legitimate low-trust integration) obtains/knows a valid `authentication_token` for an `ApiClient` that is scoped (`stack_id` set) to Stack A with `read:stack` permission. They send `GET /api/<owner>/<repoB>/<stackB-branch>/ccmenu.xml?token=<A's token>`. `authenticate_api_client` resolves `@current_api_client` to the Stack-A client successfully (token signature valid, id found). `require_permission :read, :stack` passes because the client has `read:stack` in its permissions list, regardless of stack. `stack` then resolves Stack B via the unscoped `Stack.from_param!`, and `show` renders Stack B's CCMenu XML (last deploy, build status, etc.) — data the token was never authorized to see. This works precisely because `CCMenuController#stack` does not go through `BaseController#stacks`, which is the only place the `stack_id` binding is enforced.

### Impact Explanation
Any holder of a stack-scoped API token with `read:stack` permission can enumerate and read CCMenu status (build/deploy status, last build label/time, web URL) for **any other stack** on the Shipit instance, not just the one they were authorized for. This is an unauthenticated-relative-to-target read of stack state across tenants/stacks — matching the "High: unauthenticated read of stack state" impact category. It is fully repeatable against arbitrary stacks by simply changing `stack_id` in the URL; no additional secrets are needed beyond the one token the client already legitimately possesses for its own stack.

### Likelihood Explanation
Preconditions: an `ApiClient` scoped to some stack with `read:stack` permission must exist and its token must be known to the requester (this is the normal case for any CI/CCMenu integration for stack A). The attacker only needs a token that is valid for *some* stack — a low-privilege, narrowly-scoped credential — and simply changes the `stack_id` route/query parameter to a different stack's identifier. No signature forgery, no secret_key_base/api_clients_secret knowledge, no session is required. This is low-cost and highly feasible for anyone who legitimately holds one scoped ccmenu token (e.g., a build-status widget deployed for stack A being repurposed to probe stack B).

### Recommendation
Make `CCMenuController#stack` use the scoped `stacks` relation from `BaseController` instead of the raw `Stack` model, e.g. change:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
to
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the same `current_api_client.stack_id` scoping enforced elsewhere in `BaseController` applies to CCMenu requests, and remove the private `stack` override entirely if it adds no behavior beyond the inherited one.

### Proof of Concept
minitest under `test/controllers/api/ccmenu_controller_test.rb` (existing file):
```ruby
test "a token scoped to stack A cannot read stack B's ccmenu xml" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-to-a',
    stack: stack_a,
    permissions: ['read:stack']
  )

  # Sanity: binding assumed by the system - client's stack_id should equal the requested stack
  assert_equal stack_a.id, scoped_client.stack_id
  refute_equal stack_a.id, stack_b.id

  request.headers['Authorization'] = 'bleh' # force query-string token path
  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Expected secure behavior: 403/404, NOT 200 with stack B's data
  assert_response :forbidden # or :not_found, but currently returns :ok with stack_b's XML
end
```
Running this against current code shows `assert_response :ok` with `stack_b`'s CCMenu XML returned, demonstrating the token scoped to Stack A is accepted for Stack B due to `CCMenuController#stack` bypassing `BaseController#stacks` scoping.
