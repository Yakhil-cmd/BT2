### Title
CCMenu API token created for one stack authorizes read access to every stack's deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `read:stack` permission but never binds it to the requesting stack, and `Api::CCMenuController#stack` looks up the stack purely from the request parameter instead of the scoping the base controller normally enforces. The token embedded in a per-stack CCMenu URL therefore authorizes reading the deploy state of any stack in the installation, not just the stack it was generated for — the exact "stack a token authorises versus a stack it touches" binding called out in scope.

### Finding Description
`CCMenuUrlController#client` creates (or reuses) an `ApiClient` scoped only by `creator` and `name`, with permission `read:stack`, but does **not** set the `stack:` association: [1](#0-0) 

Because `stack_id` is left `nil`, `ApiClient#stack_id?` is `false`. Normally, `Api::BaseController#stacks`/`#stack` uses this predicate to restrict a scoped client to its single authorized stack: [2](#0-1) 

However, `Api::CCMenuController` overrides `#stack` and bypasses that scoping entirely, resolving the stack directly from the URL parameter with no relation to the authenticated `current_api_client`: [3](#0-2) 

The token itself is a simple HMAC over the `ApiClient` id (`SimpleMessageVerifier`) — it authenticates *which client record* is presenting the token, but carries no binding to a specific stack: [4](#0-3) 

Since (a) the `ApiClient` record has no `stack_id`, (b) `find_or_create_by!(creator:, name:)` means the *same* client/token is reused for every stack the same user requests a CCMenu URL for, and (c) `CCMenuController#stack` never checks `current_api_client.stack_id` against the requested `stack_id`, a token generated for `stacks/A/ccmenu` can be replayed by simply changing the `stack_id` query parameter to read `stacks/B`'s CCMenu XML feed, for any stack in the installation, including ones the token holder was never intended to access.

This mirrors the reported bug class: the signature/token proves possession of a credential, but the field it is meant to be scoped to (`stack_id`) is not covered by, or checked against, that credential — allowing the "signed" token to be reused against a different target than the one it was minted for.

### Impact Explanation
This is unauthenticated read of stack state for arbitrary stacks using a token minted for a different, single stack — explicitly listed as a High-impact outcome (`unauthenticated read of stack state, task streams or deploy output`). Any leaked CCMenu URL (these are designed to be embedded in third-party CI-status dashboard tools, so leakage via referrer headers, browser history, or the dashboard tool itself is the expected threat model for this feature) grants the holder read access to deploy status of every stack in the Shipit installation, not just the one it was generated for.

### Likelihood Explanation
Likelihood is moderate-to-high in a normal deployment: CCMenu URLs are generated specifically to be pasted into external tools (CCTray/CCMenu-compatible dashboards), so they are inherently more exposed to leakage than session cookies or `ApiClient` basic-auth tokens configured out-of-band by admins. No special privilege is needed beyond obtaining one such URL/token — the exploitation step (swapping `stack_id`) requires no additional credentials.

### Recommendation
- Set `stack:` on the `ApiClient` created in `CCMenuUrlController#client`, scoped per stack (e.g., include the stack in the `find_or_create_by!` lookup key), so each stack gets its own token.
- In `Api::CCMenuController#stack`, use the base controller's scoped `stacks`/`stack` helpers (or explicitly verify `current_api_client.stack_id == requested stack.id`) instead of resolving the stack directly from the parameter.

### Proof of Concept
1. As an authenticated Shipit user, visit stack A's settings page and fetch its CCMenu URL: `GET /stacks/:owner/:repo/:env_a/ccmenu_url` → response contains `ccmenu_url` with a `token` query parameter (`CCMenuUrlController#fetch`, `app/controllers/shipit/ccmenu_url_controller.rb:7-11`).
2. Take that URL, e.g. `https://shipit.example.com/api/stacks/1/ccmenu.xml?token=<TOKEN>`, and change the `stack_id` in the path/params to stack B's id (a stack the requester has no access to).
3. `Api::CCMenuController#authenticate_api_client` accepts the token (it only validates the `ApiClient` id/signature, not any stack binding) (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`), and `#stack` resolves stack B directly from the parameter (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), returning stack B's latest deploy/rollback status in the XML response — despite the token having been minted only for stack A.
