### Title
Uncontrolled Recursion in Device Message Hashing (`cleanNullsDeep` / `getDeviceMessageHashToSign`) Leading to Stack Exhaustion - ([File: object_hash.js])

### Summary
`object_hash.js` computes the hash used to verify signatures on incoming device (wallet-to-wallet) messages via `getDeviceMessageHashToSign()`, which calls `cleanNullsDeep()` on the message body before hashing. Both functions recurse over the message structure with no depth limit, mirroring the cJSON `cJSON_Delete()`/`cJSON_Duplicate()` unbounded-recursion pattern in the reported CVE: an attacker-controlled tree is walked recursively with no nesting cap, so sufficiently deep nesting can exhaust the call stack.

### Finding Description
`getDeviceMessageHashToSign()` is used to hash an incoming device message prior to signature verification: [1](#0-0) 

It calls `cleanNullsDeep()`, whose own comment explicitly acknowledges that "device messages have free format and we can't guarantee absence of malicious fields" — i.e., the code is aware this input is attacker-controlled — yet the function only strips `null` values recursively with **no depth bound at all**: [2](#0-1) 

This is structurally the same bug class as the reported cJSON issue: a recursive tree-walking routine (`cJSON_Delete`/`cJSON_Duplicate` in cJSON, `cleanNullsDeep`/`getSourceString` here) with no nesting limit, invoked on untrusted, attacker-supplied nested data before any size/depth validation is performed. Contrast this with the unit-validation path, where `isTooDeeplyNestedOrHasTooManyNodes()` enforces a depth/node cap (`depthLimit = 100`, `nodesLimit = 10000`) on posted units: [3](#0-2) 

and `objectHash.getUnitHash()` (which itself recurses via `getSourceString`/`_.cloneDeep`) is called inside a `try/catch` in `validation.js`, so a stack-overflow `RangeError` there is caught and converted into a normal joint error rather than crashing the process: [4](#0-3) 

No equivalent depth cap or defensive `try/catch` wrapping was found for `cleanNullsDeep`/`getDeviceMessageHashToSign` in `object_hash.js`. A paired device (or any peer able to inject a message into the device-messaging channel that reaches this hashing step) can supply a deeply nested payload object that triggers unbounded recursion in `cleanNullsDeep` and `getSourceString`, exhausting the stack.

### Impact Explanation
If the recursive call chain here is not wrapped in a `try/catch` at the call site (unlike the unit-hash path), a `RangeError: Maximum call stack size exceeded` can propagate out of an event handler and crash the Node.js process, denying wallet/device-message service — a legitimate denial-of-service consistent with the "VA:H" (availability-high) impact of the reported CVE. This matches the allowed impact category "node disagreement on validity or stability" / inability to process messages, reachable by a paired device or message-relaying party.

### Likelihood Explanation
Medium. The vulnerable recursive routines (`cleanNullsDeep`, `getSourceString`) are simple, unconditional recursions with no depth guard, and the comment in the code itself flags that the input is untrusted/"free format." However, I was not able to fully confirm from available tooling whether every call site in `device.js` wraps `getDeviceMessageHashToSign()` in a `try/catch` (I found references in `device.js` via search but could not read the exact call-site code before running out of tool calls), which would affect whether this manifests as a caught error versus a process crash. This is the main uncertainty in this analysis.

### Recommendation
Add an explicit depth/node-count bound (reusing `string_utils.isTooDeeplyNestedOrHasTooManyNodes` or similar) before recursing in `cleanNullsDeep()` and before `getSourceString()`/`getJsonSourceString()` are invoked on any externally supplied, free-format object such as device messages, and/or ensure all such hashing calls are wrapped in `try/catch` with recursion converted to an iterative, stack-safe traversal.

### Proof of Concept
A conceptual PoC (not verified end-to-end due to tool-call limits): craft a device message whose JSON body contains deeply nested objects/arrays (e.g., thousands of levels, `{"a":{"a":{"a": ... }}}`), send it through the device-messaging path so it reaches `getDeviceMessageHashToSign()`; `cleanNullsDeep()` recurses once per nesting level with no cap, exhausting the JS call stack.

**Caveat:** Because I could not confirm whether the `device.js` call site catches stack-overflow errors, I cannot certify with full confidence that this results in an uncaught process crash rather than a caught, non-fatal error — this should be verified directly against `device.js` before treating this as a confirmed exploitable DoS.

```javascript
function cleanNullsDeep(obj){
	Object.keys(obj).forEach(function(key){
		if (obj[key] === null)
			delete obj[key];
		else if (typeof obj[key] === 'object') // array included

	});
}
```

```javascript
function getDeviceMessageHashToSign(objDeviceMessage) {
	var objNakedDeviceMessage = _.clone(objDeviceMessage);
	delete objNakedDeviceMessage.signature;
	cleanNullsDeep(objNakedDeviceMessage); // device messages have free format and we can't guarantee absence of malicious fields
	return crypto.createHash("sha256").update(getSourceString(objNakedDeviceMessage), "utf8").digest();
}
```

```javascript
function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
```
