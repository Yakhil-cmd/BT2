### Title
Unlocked in-memory cache reset during `light/dry_run_aa` corrupts shared unit/stability state used by concurrent unit validation - ([File: network.js])

### Summary
The Linux CVE fixes a race where a lock-protected structure (`gfn_to_pfn_cache`) could be re-initialized while another thread was actively using it, corrupting the lock and the cache it guards. In `ocore`, the analogous shared, lock-protected structure is the global in-memory unit cache (`assocUnstableUnits`, `assocStableUnits`, `assocStableUnitsByMci`, `assocBestChildren` in `storage.js`), which is normally only mutated while holding the `["write"]` mutex (see `writer.js` `saveJoint`, `network.js` `startRelay`). The handler for `light/dry_run_aa` calls `storage.resetMemory()` (which wipes and asynchronously repopulates these caches) **without acquiring the `write` mutex**, creating a window where concurrently validated units read a torn/incomplete cache.

### Finding Description
`storage.resetMemory()` [1](#0-0)  clears `assocUnstableUnits`/`assocStableUnits`/`assocStableUnitsByMci`/`assocBestChildren` and repopulates them via `initUnstableUnits`/`initStableUnits`, which issue asynchronous DB queries and rebuild the maps in a later callback [2](#0-1) . Every legitimate mutator of this state takes the `["write"]` mutex first — e.g. `writer.js` `saveJoint` (`const unlock = ... await mutex.lock(["write"])`) [3](#0-2) , and the startup path `network.js startRelay` (`const unlock = await mutex.lock(['handleJoint', 'initial']); await storage.initCaches();`) [4](#0-3) .

However, the `light/dry_run_aa` request handler calls `storage.resetMemory` directly inside `db.executeInTransaction`, with no `mutex.lock(["write"])` around it: [5](#0-4) . This handler is reachable by any peer/light client sending the `light/dry_run_aa` command with an arbitrary `trigger`/`address`; no privilege is required (`handleRequest` case `'light/dry_run_aa'`, guarded only by basic address/trigger format checks) [6](#0-5) .

Because `resetMemory` deletes all keys from `assocUnstableUnits`/`assocStableUnits`/`assocStableUnitsByMci`/`assocBestChildren` and repopulates them asynchronously, any unit validation (`validation.js validate()`), `writer.saveJoint`, or `main_chain.js` main-chain/stability computation that reads these same module-level objects during the gap will observe an empty or partially-repopulated cache. This is structurally the same bug class as the KVM CVE: a shared, normally lock-protected data structure is torn down and reinitialized on a path that fails to take the same lock other legitimate mutators/readers rely on, producing state corruption visible to concurrent operations. Unlike the CVE (a `rwlock_init()` re-init of an actual lock), here the "lock" that should protect the reset (the `write` mutex) is simply not acquired on this path, so the race is even more directly exploitable by an ordinary network peer.

### Impact Explanation
While the cache is torn down/rebuilding, concurrent unit validation (`validation.js` -> `main_chain.js`) that consults `storage.assocUnstableUnits`/`assocStableUnits`/`assocBestChildren`/`assocStableUnitsByMci` can compute wrong best-parent/main-chain/stability results (missing units it should see, or seeing units without their stability flags), because these maps are being cleared and refilled outside of the mutex all other logic assumes protects them. This can lead to nodes disagreeing on unit validity/stability or temporarily failing to see already-stable units as stable, which is a node-disagreement / stability-corruption class of impact. The existing project code explicitly acknowledges the fragility of this reset path in single-witness setups via a test-only hack (`fixCache()` in `test/aa_composer.test.js`, comment: "this hack is necessary only for 1-witness network where an AA-response unit can rebuild the MC to itself") [7](#0-6) , showing the authors are aware `resetMemory`/dry-run interactions can desynchronize the cache from the DB truth, but the production network handler does not serialize this reset against the write lock the way other mutators do.

### Likelihood Explanation
The trigger condition is `constants.COUNT_WITNESSES === 1` [8](#0-7) , i.e. single-witness/private networks (a supported and used ocore deployment mode, as evidenced by the dedicated test-suite comment above). On such a network, any peer can send `light/dry_run_aa` for any AA address with an attacker-chosen trigger, and the response handler unconditionally fires an un-locked `storage.resetMemory()` immediately after, racing with any unit currently being validated/written via `writer.saveJoint` or `main_chain.js`. Because `resetMemory` performs multiple async DB round-trips before finishing, the window is not negligible, making the race practically triggerable by an unprivileged network peer issuing repeated dry-run requests.

### Recommendation
Wrap the `storage.resetMemory()` call in `network.js`'s `light/dry_run_aa` handler with `mutex.lock(["write"], ...)`, exactly like `writer.saveJoint` and `network.js startRelay` do for all other mutations of `assocUnstableUnits`/`assocStableUnits`/`assocStableUnitsByMci`/`assocBestChildren`, so the reset-and-repopulate sequence is atomic with respect to concurrent validation/write operations. Alternatively, avoid mutating global caches from the dry-run path entirely (e.g., perform the MC-rebuild check on a private/local snapshot rather than the shared `storage` module state).

### Proof of Concept
1. Run an ocore-based node with `constants.COUNT_WITNESSES === 1` (single-witness/private network).
2. From any peer, concurrently:
   - (a) Post a new valid unit to the node (triggers `validation.validate` → `writer.saveJoint`, which reads/writes `storage.assocUnstableUnits`/`assocStableUnits` under the `write` mutex), and
   - (b) Repeatedly send `light/dry_run_aa` requests with a trigger against an existing AA address, causing the node to call `storage.resetMemory()` unlocked after each dry run.
3. Because (b) clears and asynchronously rebuilds `assocUnstableUnits`/`assocStableUnits`/`assocStableUnitsByMci`/`assocBestChildren` without holding `["write"]`, unit (a)'s validation/write can interleave with the reset, observing a torn cache (missing best-parent/best-children entries or missing stability flags), leading to incorrect main-chain/stability computation for that unit relative to what other nodes (not racing a dry-run) compute — a node-disagreement condition.

function fixCache() {

	for (var unit in storage.assocUnstableUnits) {
		var objUnit = storage.assocUnstableUnits[unit];
