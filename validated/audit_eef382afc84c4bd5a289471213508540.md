### Title
ReDoS via attacker-controlled hookify rule regex pattern causes PreToolUse hook to hang and fail open, bypassing block enforcement - (File: plugins/hookify/core/rule_engine.py)

### Finding Description
`compile_regex` compiles an arbitrary `pattern` string taken directly from a rule's YAML frontmatter with no length limit, complexity check, or timeout, and the result is memoized via `@lru_cache(maxsize=128)` [1](#0-0) . `_regex_match` then calls `regex.search(text)` against `field_value`, which for Bash rules is `tool_input['command']` extracted verbatim from the tool call by `_extract_field` [2](#0-1) [3](#0-2) . Rule patterns originate from `.claude/hookify.*.local.md` files loaded by `load_rules`/`load_rule_file`/`extract_frontmatter`, which parse the `pattern` (or `conditions[].pattern`) field with no validation of regex safety or length [4](#0-3) [5](#0-4) . `pretooluse.py:main` reads the untrusted JSON tool input, calls `load_rules` then `RuleEngine.evaluate_rules` -> `_rule_matches` -> `_check_condition` -> `_regex_match`, all inside a `try/except Exception` that is followed by `sys.exit(0)` in a `finally` block [6](#0-5) . This exception handling only guards against exceptions raised synchronously (e.g. `re.error`); a catastrophic-backtracking pattern (e.g. `(a+)+$`, `(.*){10,}`) does not raise — it blocks the interpreter indefinitely in `regex.search`, so the try/except/finally never executes and `sys.exit(0)` is never reached. No timeout, thread, or subprocess isolation wraps the regex evaluation anywhere in this call chain.

### Impact Explanation
If an attacker can introduce a `.claude/hookify.*.local.md` rule file (e.g. via a merged PR containing a malicious rule, or a plugin that ships one) with a `pattern` designed for catastrophic backtracking, and the victim later runs a `Bash` command whose `command` string triggers exponential backtracking against that pattern, the PreToolUse hook process hangs. Because Claude Code's hook runner enforces an external timeout on hook execution, a hung PreToolUse hook is treated as a non-response; depending on Claude Code's fail-open/fail-closed policy for hook timeouts, this can result in the tool call proceeding without the intended `deny` decision being delivered, violating the "deny means deny" invariant and allowing the underlying (potentially dangerous) Bash command to execute unblocked. This matches an "approval/block bypass via hook enforcement failure" impact.

### Likelihood Explanation
The precondition is that an attacker-controlled rule file (with an attacker-chosen regex `pattern`) is present in `.claude/hookify.*.local.md` and is later evaluated against attacker-influenceable `tool_input.command`. This is realistic in collaborative/plugin-distribution workflows: a contributor-supplied rule file merged into the repo, or a plugin bundling a `hookify.*.local.md`, is normal, unprivileged content that would not typically be scrutinized for regex safety. Once present, triggering the hang only requires a single Bash tool call whose command text matches the crafted pattern's backtracking trigger — fully repeatable and deterministic given the same pattern/input.

### Recommendation
- Enforce a hard timeout on regex evaluation (e.g. run `regex.search` in a worker process/thread with `signal.alarm`, or use a safe regex engine such as `re2`/`regex` module with backtracking limits) and treat a timeout as an automatic `block`/deny rather than allow.
- Validate/sanitize rule patterns at load time (e.g. static ReDoS detection, pattern length caps, disallow nested unbounded quantifiers) in `config_loader.py` before they are registered.
- Change `pretooluse.py`'s fail-safe behavior for hook errors/timeouts on `block`-action rules to deny by default instead of unconditionally exiting 0.

### Proof of Concept
Fuzz/unit test in `plugins/hookify/core/rule_engine.py`:
1. Construct a `Rule` with `conditions=[Condition(field="command", operator="regex_match", pattern="(a+)+$")]`, `action="block"`.
2. Build `tool_input={"command": "a"*40 + "!"}` (classic ReDoS trigger with no match, forcing full backtracking).
3. Call `RuleEngine().evaluate_rules([rule], {"tool_name": "Bash", "tool_input": tool_input, "hook_event_name": "PreToolUse"})` in a subprocess/thread with a wall-clock timeout (e.g. 2 seconds).
4. Assert the call either completes within the timeout with a bounded-time deny/allow decision, or — if it times out — assert that the overall system enforces `deny` on timeout rather than treating the hang as an implicit allow.
5. Expected current behavior: the call exceeds the timeout (demonstrating unbounded execution time), proving the absence of any backtracking guard, contradicting the "deny means deny" invariant when combined with fail-open timeout handling in `pretooluse.py`.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
