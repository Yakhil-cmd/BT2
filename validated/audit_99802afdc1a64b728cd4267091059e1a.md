### Title
Rounding in headers-commission/witnessing-commission distribution among multiple recipients permanently destroys bytes - (File: headers_commission.js, paid_witnessing.js)

### Summary
When a unit's `headers_commission` (or `payload_commission` paid to witnesses) must be split among several recipients via `earned_headers_commission_recipients`, each recipient's share is computed independently with `Math.round(full_amount * share / 100.0)`. Because `validateHeadersCommissionRecipients` only guarantees that the recipients' percentage shares sum to exactly 100, not that the rounded integer amounts sum back to `full_amount`, the sum of rounded per-recipient amounts can be strictly less (or more) than `full_amount`. Any unprivileged unit poster can create a multi-authored unit with an `earned_headers_commission_recipients` list whose shares cause this rounding drift.

### Finding Description
`validateHeadersCommissionRecipients` in `validation.js` only enforces `total_earned_headers_commission_share === 100`, with no constraint tying individual integer amounts to the parent unit's actual commission value. [1](#0-0) 

`calcHeadersCommissions` then splits the collected `headers_commission` (`full_amount`) among the listed recipients using independent rounding per recipient: [2](#0-1) 
and in the SQLite non-faster path, using `Math.round(full_amount * share / 100.0)` per row as well: [3](#0-2) 

For example, with `full_amount = 10` and shares `[33, 33, 34]` (summing to 100 as required), the per-recipient amounts round to `3, 3, 3` = 9, one byte less than the `10` actually deducted from the payer unit's size fee. Conversely, other share splits can round the total *upward*, paying out more than `full_amount`. The MySQL path performs the same per-row `ROUND(...)` computation in SQL, so the discrepancy is consistent across the network (not a consensus mismatch), but the resulting `headers_commission_outputs` total no longer conserves the value that was actually withheld as the commission fee.

The identical pattern exists for paid witnessing commissions, where `payload_commission` is divided by `countPaidWitnesses[v.unit]` with `Math.round`: [4](#0-3) 
and the equivalent SQL-side computation `ROUND(1.0*payload_commission/count_paid_witnesses)`: [5](#0-4) 

Later, `mc_outputs.calcEarnings` simply sums `headers_commission_outputs`/`witnessing_outputs` rows for a claiming address's spend range, so whatever total was actually inserted (short of or in excess of the true fee) is what recipients can ever claim: [6](#0-5) 

### Impact Explanation
Every multi-authored unit (or unit whose author designates external `earned_headers_commission_recipients`) that has share percentages not evenly divisible into the collected commission amount will silently under-pay (bytes vanish, permanently unclaimable — no one holds them) or over-pay (bytes are effectively created from nothing) recipients. Both directions break the fixed/conserved-supply invariant of `base` bytes. Because unit authors freely choose the recipient list and shares, this can be repeated at scale by any unprivileged unit poster, causing accumulating, permanent drift in the total money supply.

### Likelihood Explanation
Any user can author a multi-authored unit (or specify `earned_headers_commission_recipients` for a single author) with recipient shares that don't evenly divide the eventual `headers_commission`/`payload_commission` amount — this is trivial to trigger and requires no special privilege, at the cost of only the fees of composing a normal unit.

### Recommendation
When distributing a fixed integer amount among multiple recipients by percentage share, avoid independent per-recipient rounding. Instead, accumulate a running remainder (e.g., largest-remainder method) or assign the leftover/deficit (`full_amount - sum_of_rounded_shares`) to a designated recipient (e.g., the last one, sorted by address) so that the sum of the distributed amounts is always exactly equal to `full_amount`, both in the JS in-memory computation and the SQL `ROUND(...)` computation, for both `headers_commission.js` and `paid_witnessing.js`.

### Proof of Concept
1. Author a 2-authored unit with `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 33}, {address: B, earned_headers_commission_share: 67}]` — validation accepts this because `33 + 67 === 100` (`validation.js` lines 1101-1123).
2. This unit wins headers commission of `full_amount = 10` from a parent unit (`calcHeadersCommissions`).
3. Computed amounts: `A: round(10*33/100) = round(3.3) = 3`; `B: round(10*67/100) = round(6.7) = 7`. Total distributed = 10 (no drift in this specific case), but choosing shares such as `[10, 10, 10, 10, 10, 10, 10, 10, 10, 10]` with `full_amount = 15` yields each recipient `round(15*10/100) = round(1.5) = 2` (banker's/half rounding aside), summing to 20 > 15 — an inflationary overpay; or shares like `[11, 11, 11, 11, 11, 11, 11, 11, 11, 11]` (110% total is rejected by validation, so use a valid split such as nine recipients at `11%` and one at `1%`) where per-recipient rounding-down uniformly causes `sum(rounded) < full_amount`, permanently losing the shortfall. In all such cases `mc_outputs.calcEarnings`'s `SUM(amount)` over `headers_commission_outputs` (or `witnessing_outputs`) never equals the `full_amount` (or `payload_commission`) actually withheld, demonstrating the conservation break.

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
