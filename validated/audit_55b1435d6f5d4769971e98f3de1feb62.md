### Title
Stack-scoped API tokens can read the CCMenu status of any stack, bypassing the `stack_id` restriction - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts an `ApiClient` that has a `stack_id` to only the stacks it owns via the `stacks` helper method, and every other API controller (`Api::StacksController`, etc.) resolves the target stack through that scoped helper. `Shipit::Api::CCMenuController#stack` overrides this and instead calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` class, so a token that is supposed to be limited to a single stack can be used to fetch the CCMenu deploy status of any other stack in the installation.

### Finding Description
The binding that should hold is: for any request handled through `Api::BaseController`, `stack.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` is true (enforced by `stacks` at `app/controllers/shipit/api/base_controller.rb:74-80`, which does `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` and then `stacks.from_param!(params[:stack_id])`).

`Shipit::Api::CCMenuController` re-defines `stack` and drops that scoping entirely: [1](#0-0) 

It calls `Stack.from_param!(params[:stack_id])` on the bare `Stack` model (all stacks), instead of `stacks.from_param!(params[:stack_id])` used by the base controller: [2](#0-1) 

`require_permission :read, :stack` only checks that the token has the `read:stack` permission string via `ApiClient#check_permissions!` — it never checks which stack the client is bound to: [3](#0-2) 

So the only place the per-stack restriction is normally enforced is the `stacks` scoping helper in `BaseController`, and `CCMenuController` bypasses it. An attacker who holds any valid `ApiClient` token that was issued scoped to stack A (i.e. `ApiClient#stack_id` set to A) can call `GET /api/stacks/:stack_id/cc.xml?token=...` (or with Basic Auth) with `stack_id` pointing at stack B, C, D, … and the controller will happily resolve and render stack B's/C's/D's latest deploy/rollback status, lock state, and build label — data that token was never authorized to see.

None of the existing guards catch this: `authenticate_api_client` only verifies the token signature is valid (`ApiClient.authenticate`), `require_permission!` only checks the permission string not the target record, and `Stack.from_param!` has no notion of the authenticated client's scope.

### Impact Explanation
This is an unauthenticated-for-that-resource read of stack state: a token minted for one stack can enumerate and read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, `webUrl`) of every other stack in the Shipit install, across repositories/tenants that the token was never granted access to. This matches the High-severity category "escalation ... unauthenticated read of stack state, task streams or deploy output." It is fully repeatable — a single request per target stack id/slug, and can be scripted to enumerate the entire `stacks` table.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one valid, stack-scoped `ApiClient` token with the `read:stack` permission (e.g. one legitimately issued to them for their own stack) — no operator privileges, no GitHub secrets, no session. This is exactly the kind of "unprivileged holder of any valid CCMenu token" scenario described in the question. The attack costs a single crafted HTTP GET per target stack and requires no special repository configuration.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` helper inherited from `Api::BaseController` (i.e. remove the private `stack` override, or change it to `@stack ||= stacks.from_param!(params[:stack_id])`), so the `current_api_client.stack_id` restriction applies uniformly to this endpoint as it does to every other API controller.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (or an equivalent minitest under `test/`):

```ruby
test "a client scoped to one stack cannot read another stack's CCMenu status" do
  other_stack = shipit_stacks(:shipit2) # a different stack/repository
  @client.update!(stack_id: @stack.id, permissions: ['read:stack'])

  get :show, params: { stack_id: other_stack.to_param, token: @client.authentication_token }

  # Binding under test: stack.id == current_api_client.stack_id
  assert_not_equal other_stack.id, @client.stack_id
  assert_response :forbidden # or :not_found — currently fails, controller returns :ok
  refute_includes response.body, other_stack.repository.name
end
```

Before the fix this test fails because the controller returns `200 OK` with `other_stack`'s XML payload; after scoping `stack` through `stacks.from_param!`, the request should be rejected (404, since `other_stack` is outside the scoped `stacks` relation).
