### Title
Permissionless `DepositDelegatorRewards` deposit allows front-running griefing that raises a vote account's minimum-withdrawable balance and can block full account closure - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote program's `DepositDelegatorRewards` instruction (SIMD-0123) lets **any signer** transfer lamports into **any** V4 vote account and unconditionally increment that vote account's `pending_delegator_rewards` field, with no relationship or consent from the vote account's authorized withdrawer required.

### Finding Description
`deposit_delegator_rewards` only verifies that the *source* account signs the transfer; it performs no check that the caller is the vote account's authorized withdrawer, staker, or otherwise related party: [1](#0-0) 

The deposited lamports are added to the vote account via a CPI transfer, and `pending_delegator_rewards` is incremented unconditionally: [2](#0-1) 

This value directly gates the withdraw path. When `pending_delegator_rewards > 0`, the vote account can never be closed to zero balance, and any partial withdrawal must always leave at least `rent_exempt_minimum + pending_delegator_rewards` in the account: [3](#0-2) 

This is structurally identical to the reported bug class: an unrelated third party can, without the victim's consent, "deposit on someone else's behalf" and thereby mutate a piece of state (`_lastDeposit` / `pending_delegator_rewards`) that gates the victim's ability to withdraw/close.

### Impact Explanation
An attacker can observe a pending `Withdraw` transaction attempting to fully close a vote account (e.g., in the mempool/leader's pending queue) and front-run it with a minimal `DepositDelegatorRewards` deposit (even amount = 1) targeting the same vote account. This:
- Sets `pending_delegator_rewards > 0`, which permanently blocks `Withdraw` from fully closing/deinitializing the vote account (`InstructionError::InsufficientFunds` per the check at line 1090-1091 above) until a corresponding reward-distribution mechanism reduces `pending_delegator_rewards` back to zero.
- Forces the withdrawer to always retain `rent_exempt_minimum + pending_delegator_rewards` lamports in the account, denying the withdrawer full access to the funds they intended to withdraw.

This does not cause fund theft or consensus divergence, but it is an unsigned, uninvited state mutation on someone else's account that degrades their ability to fully withdraw/close it — a griefing/DoS impact on the affected validator's vote account owner, analogous to the "freeze deposit indefinitely" bug class in the report, though of lesser severity because the amount frozen is bounded to whatever the attacker chooses to deposit and the mechanism only affects V4 vote accounts (behind several feature gates: `commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`).

### Likelihood Explanation
Any account holding lamports can issue this instruction against any target vote account address in a single transaction; no special privilege, staking relationship, or prior state is required. The instruction is fully permissionless by design (per SIMD-0123 to allow arbitrary reward depositors), which is also the root cause — the same permissionlessness intentionally required by the design is what enables the griefing.

### Recommendation
Consider whether `Withdraw`'s full-close path should be resilient to attacker-inflated `pending_delegator_rewards`, e.g., by allowing the authorized withdrawer to force-reduce/reclaim `pending_delegator_rewards` that were not distributed by the protocol's own reward mechanism, or by tracking "legitimately expected" pending rewards separately from arbitrary third-party deposits, so an unrelated depositor cannot indefinitely gate the withdrawer's ability to fully close the account.
