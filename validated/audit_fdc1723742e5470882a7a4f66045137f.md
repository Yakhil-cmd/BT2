I'll investigate the codebase to check whether a genuine analog of this "value overwritten by intervening call" bug class exists within the specified trust boundaries.### Title
Webhook org used for HMAC signature selection is decoupled from the repository the payload acts on, enabling cross-tenant push forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) to validate an inbound webhook against using `repository_owner`, a value read straight out of the attacker-supplied JSON body. Every webhook handler, however, resolves the target `Stack`/`Repository` from a **different** field of the same body — `repository.full_name`. Because these two fields are never checked for consistency, an actor who legitimately owns/controls one GitHub organization configured in a multi-tenant Shipit instance (and can therefore produce a validly-signed payload for that org) can set `repository.full_name` to point at a repository belonging to a completely different, unrelated org hosted on the same Shipit instance, and have Shipit act on that org's stacks.

### Finding Description
`verify_signature` computes the organization used to choose the verification secret like this: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

and: [2](#0-1) 

```
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: ...)` returns the `GitHubApp` instance configured for that org, and its secret is used to HMAC the raw body: [3](#0-2) 

The engine explicitly supports multiple independently-configured GitHub organizations, each with its own `webhook_secret`, as shown in the sample multi-org configuration: [4](#0-3) 

Once the signature passes, every handler resolves the affected repository/stacks purely from `repository.full_name`, a field that is never cross-checked against `repository.owner.login`/`repository_owner`: [5](#0-4) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` then acts on those stacks directly: [6](#0-5) 

```
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```

This mirrors the reported bug class exactly: the binding actually enforced is `verified_org == repository.owner.login`, while the binding that governs the resulting action is `acted_repository == repository.full_name`. Nothing ties these two fields together, so `verified_org` and `acted_repository`'s owner can diverge. This matches the explicitly allowed analog: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Any actor who can produce a validly-signed webhook for one org configured on a shared/multi-tenant Shipit instance (e.g. by legitimately triggering GitHub webhook delivery from a repo they control under that org — GitHub itself computes the HMAC using the org's secret at delivery time) can instead point `repository.full_name` at a repository belonging to an unrelated org also tracked by the same Shipit instance. Since `stacks` is looked up solely from `full_name`, this forces `GithubSyncJob`/`sync_github` to run against a victim org's stacks the attacker has no authorization over — refreshing commits and, when combined with `continuous_deployment`, accelerating/triggering an unintended deploy on a stack outside the attacker's authorization boundary. This is a cross-tenant authorization boundary break (High impact: unauthorized action against another team's stack, escalation across the authorization domain the webhook signature is meant to enforce).

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate GitHub user/webhook source for at least one org configured in a multi-org Shipit deployment (a common, documented deployment topology per `config/secrets.development.shopify.yml`), and for the victim repository to already be tracked as a `Stack` on the same instance. No privileged Shipit session, API token, or GitHub App private key is needed — only the ability to get GitHub to deliver one correctly-signed webhook for the attacker's own org, with a hand-picked JSON body pointing `repository.full_name` elsewhere (achievable by controlling the payload of custom/forwarded delivery mechanisms, or in setups where webhook payload content is influenced by repo-level settings the attacker controls, e.g. repository renames/transfers or forwarding proxies). This is a realistic scenario in any shared Shipit instance serving multiple GitHub organizations.

### Recommendation
Bind signature verification to the same repository identity that handlers act on. Concretely:
- Verify the signature using the org associated with `repository.full_name` (i.e., derive the org for `Shipit.github(organization: ...)` and the org used by handlers from the exact same parsed field), or
- After signature verification, independently confirm that the resolved `Repository`'s owner matches `repository_owner` before dispatching to handlers, rejecting the webhook if they diverge.

### Proof of Concept
1. Shipit instance is configured (per `config/secrets.development.shopify.yml`-style setup) with two orgs, `org-a` (attacker-controlled) and `org-b` (victim), each with their own tracked stacks and independent `webhook_secret`.
2. Attacker arranges for a webhook to be delivered/signed for `org-a` (satisfying `verify_signature`, since `repository.owner.login == "org-a"`), but crafts the JSON body's `repository.full_name` to `"org-b/victim-repo"`.
3. `WebhooksController#verify_signature` validates the HMAC using `org-a`'s secret and passes.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — an action the attacker has no authorization to trigger. [7](#0-6) [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
