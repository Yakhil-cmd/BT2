### Title
Forced OAuth completion via GET-based request phase binds attacker-controlled GitHub identity to a victim's session - (File: `app/controllers/shipit/github_authentication_controller.rb`, `lib/shipit/engine.rb`, `config/routes.rb`)

### Summary
The GammaSwap report shows a value used across multiple downstream computations was derived from only part of the input that should govern it (`s.decimals[0]` instead of both tokens' decimals), silently corrupting protocol state. The Shipit analog is the OAuth login flow: the state/identity binding that is supposed to tie a completed OAuth exchange to the session that *initiated* it is not enforced, because the request phase is exposed over `GET` without the CSRF-protection add-on that OmniAuth 1.9+ requires for that to be safe. The callback handler then unconditionally writes `session[:user_id]` from whatever `auth` object OmniAuth attaches to the request, without validating that this session is the one that started the flow [6](#0-5) .

### Finding Description
The binding that should hold is: `session that initiates /github/auth/github` == `session that completes /github/auth/github/callback and receives session[:user_id]`.

- OmniAuth's request phase normally embeds a per-session `state` parameter that is echoed back and validated at the callback phase, precisely to guarantee this binding. Since OmniAuth 1.9, the library also restricts the request phase to `POST` by default specifically to prevent an attacker from getting a victim to simply click/load a GET link that begins someone else's OAuth flow (a "forced OAuth" / login-CSRF vector), unless the app adds `omniauth-rails_csrf_protection` to embed a Rails CSRF token in the (now form-based) request-phase call.
- This engine does not add `omniauth-rails_csrf_protection` [4](#0-3)  and does not otherwise configure `allowed_request_methods` (confirmed absent) when mounting the strategy [1](#0-0) .
- Routing still explicitly exposes the request phase as a bare `GET` [5](#0-4) , which is exactly the request shape the OmniAuth 1.9 default was designed to block.
- `GithubAuthenticationController#callback` performs no independent verification that the session receiving `auth` is the one that requested it: it just reads `request.env['omniauth.auth']` and writes `session[:user_id] = sign_in_github(auth)` [6](#0-5) . `sign_in_github` finds-or-creates a `User` purely from the GitHub identity in `auth.extra.raw_info` and stores the fresh `github_access_token` on it [7](#0-6) .

If the `GET`-based request phase can be driven by cross-site navigation (e.g., an attacker frames/redirects the victim through the attacker's own completed OAuth code, or the flow otherwise omits state-checking because the initiating request method wasn't the one OmniAuth 1.9 expects to protect), the victim's browser session ends up bound to the GitHub identity/token the attacker controls, or vice versa — breaking the "GitHub identity vs. `User` bound to the session" invariant described in the rules.

### Impact Explanation
If exploitable, this allows an unauthenticated network attacker to force a victim's browser to complete an OAuth flow the attacker set up, causing the victim's Shipit session to become authenticated as the attacker's GitHub identity (or vice versa, session fixation into a target account). This matches the explicitly listed High-impact category "session fixation / forced OAuth completion," since it results in a session whose bound `User`/GitHub identity does not correspond to the party who actually authenticated in that browser.

### Likelihood Explanation
Likelihood is moderate-to-uncertain: the actual exploitability depends on OmniAuth 1.9.2's internal default behavior for unprotected `GET` request phases (whether it still performs the full flow without a valid `state` roundtrip when the app hasn't opted into stricter method checks), which I could not fully verify by reading gem internals from this index — only the absence of the mitigating gem/config in this engine's own code. This is a configuration/integration gap in the engine itself (missing `omniauth-rails_csrf_protection`, missing `allowed_request_methods` hardening) rather than a deep logic bug, so it is straightforward for the vendor to reproduce and fix once flagged. I am flagging this with reduced confidence because I could not trace through the omniauth gem's exact runtime behavior to confirm exploitability end-to-end in this session.

### Recommendation
Add the `omniauth-rails_csrf_protection` gem, switch the login link/route to a `POST` (button/form) as OmniAuth 1.9+ expects, and verify that `omniauth.auth`/state is only honored for the session that initiated the flow. Alternatively, explicitly configure and audit `provider_ignores_state`/`allowed_request_methods` to ensure they are not inadvertently weakened.

### Proof of Concept
Not independently reproducible from the indexed code alone: exploitation requires exercising the actual OmniAuth 1.9.2 middleware behavior for a `GET` request phase without `omniauth-rails_csrf_protection`, which is outside what I can execute/verify via static code search. The concrete gap I can prove from the repository is the absence of the mitigating gem/config combined with the explicit `GET` route and the callback's unconditional `session[:user_id]` assignment cited above.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

    end
