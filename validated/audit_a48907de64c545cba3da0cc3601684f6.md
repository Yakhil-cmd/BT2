### Title
Share-based AA vault/market-maker pattern is vulnerable to first-depositor donation/inflation attack via `balance[asset]` manipulation - (File: `formula/evaluation.js`, `test/samples/uniswap_like_market_maker.oscript`)

### Summary
Obyte's Autonomous Agent (AA) formula language exposes a `balance[asset]` operator that always reflects the AA address's *actual* on-chain balance, including any coins sent to it outside of a formal trigger invocation. The bundled reference implementation for building tokenized liquidity/market-maker AAs (`test/samples/uniswap_like_market_maker.oscript`) uses exactly this `balance[asset]` value — together with a separately tracked `var['mm_asset_outstanding']` share counter — to compute how many "shares" (the `mm_asset`) to mint on deposit and how much underlying to return on withdrawal. Because `balance[asset]` can be inflated by a bare/naked payment (a "donation") sent directly to the AA's address without going through the deposit branch, and because share issuance is `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`, an attacker can reproduce the classic ERC4626-style vault-inflation attack: front-run a victim's deposit with a minimal share purchase, donate assets directly to the AA to skew the ratio, and force the victim's deposit to round down to fewer shares than deserved, then redeem to capture the victim's donated value.

### Finding Description
The AA formula engine's `balance` operator is implemented in `formula/evaluation.js` (`readBalance`), which reads `objValidationState.assocBalances[address][asset]`, falling back to the `aa_balances` DB table populated in `storage.js`'s `insertAADefinitions`/balance-tracking logic. Crucially, this value is the *cumulative* balance of everything ever paid to the AA address that is unspent — it does not distinguish between coins arriving as part of a recognized "invest" trigger and coins sent as a bare/silent payment with no matching `trigger.data` field. Any unprivileged user can send a payment output to an AA's address at any time; this immediately becomes part of `balance[asset]` for the AA's next execution, per the grammar rule in `formula/grammars/oscript.ne` (`"var"|"balance" "[" ... "]"`) and its evaluation in `formula/evaluation.js` lines 1480-1528.

The bundled sample AA `uniswap_like_market_maker.oscript` (mirrored in `test/ojson.test.js`'s "Uniswap-like market maker" test) implements the canonical share-vault pattern documented for Obyte AA developers:

```
// invest in MM
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
$current_ratio = $asset_balance / $bytes_balance;
...
$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```

and on divestment:

```
$investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
... amount: "{ round($investor_share * balance[$asset]) }"
... amount: "{ round($investor_share * balance[base]) }"
```

This is structurally identical to the vulnerable `BaseLSTAdapter.prefundedDeposit()` / `totalAssets()` pattern from the Sherlock report, which also computed `totalAssets` from a raw `balanceOf` call rather than an internally tracked accounting variable, letting an attacker inflate the denominator via a direct transfer and force the victim's share calculation to round down.

### Impact Explanation
An attacker can:
1. Issue the `mm_asset` and become the first depositor by sending a minimal amount (front-running the victim's larger deposit transaction, which is publicly visible on the DAG before stabilization).
2. Directly donate a large amount of the underlying asset/bytes to the AA's address (a bare payment, not going through the "invest" branch, e.g. with no data or with data that does not match any `if` condition, still gets silently absorbed into `balance[asset]`/`balance[base]`).
3. This skews `$bytes_balance` (or `$asset_balance`) so that when the victim's deposit trigger executes, `$investor_share_of_prev_balance * var['mm_asset_outstanding']` rounds down to fewer shares than the victim's true share of the resulting pool.
4. The attacker then redeems their `mm_asset` shares (computed as `$mm_asset_amount / var['mm_asset_outstanding']` multiplied by the now-inflated `balance[$asset]`/`balance[base]`), extracting a disproportionate amount of the underlying assets — including part of the victim's deposit and the attacker's own donation.

This results in a genuine loss of AA-held funds for the victim depositor, matching the "AA fund loss" impact class.

### Likelihood Explanation
Any user can trigger this without special privileges: sending bytes/assets to an AA address is a normal, unprivileged unit-posting action, and the AA engine's `balance[asset]` semantics guarantee that non-trigger-matching payments still count toward the balance used in share math. The attack requires only observing a pending victim deposit and front-running/back-running it with two of their own units (a minimal invest + a donation), which is a low-cost, well-known MEV-style pattern on DAG-based ledgers where units are visible before final ordering/stabilization.

### Recommendation
- In AA vault/share-issuance templates, do not use raw `balance[asset]` to determine the amount to be split into shares; instead maintain and use internally tracked state variables (e.g. `var['tracked_asset_balance']`, `var['tracked_bytes_balance']`) that are only updated by the AA's own recognized deposit/withdraw logic, ignoring unsolicited direct payments for share-ratio purposes.
- Document this `balance[asset]` risk explicitly for AA developers building share/vault-style contracts, since it is a core protocol semantic (not an app bug) that the official reference sample (`uniswap_like_market_maker.oscript`) currently does not guard against.
- Consider requiring a minimum "dead" share issuance to a burn address on first deposit (analogous to Uniswap V2's `MINIMUM_LIQUIDITY`) as a template-level mitigation, and adding it to the reference sample so developers copying it are not silently exposed.

### Proof of Concept
1. Attacker calls the AA with `trigger.data.define` to create `mm_asset` (no shares yet issued, `var['mm_asset_outstanding']` unset).
2. Attacker sends a small "invest" trigger, e.g. `trigger.output[[asset=base]] = 100001`, with no other assets: since `$asset_balance == 0`, the AA takes the `initial deposit` branch and sets `$issue_amount = balance[base]` (≈100001), so the attacker now owns all outstanding `mm_asset` shares against a small bytes balance.
3. Attacker observes victim's pending large deposit unit (e.g. depositing 10e9 bytes) in the DAG mempool/tips before it stabilizes.
4. Attacker sends a bare payment (a "donation") of a large amount of `$asset` directly to the AA address with a message the AA does not treat as an "invest" (or one whose `if` condition for invest fails), inflating `$asset_balance`/`$bytes_balance` read by `balance[$asset]`/`balance[base]` on the AA's next trigger.
5. When the victim's deposit trigger executes, `$investor_share_of_prev_balance * var['mm_asset_outstanding']` rounds down due to the now-skewed ratio, minting the victim fewer `mm_asset` shares than their fair share of the pool.
6. Attacker sends their `mm_asset` shares back in a "divest" trigger; `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` now entitles them to a disproportionate cut of `balance[$asset]`/`balance[base]`, which includes the victim's freshly deposited funds, extracting value from the victim.
