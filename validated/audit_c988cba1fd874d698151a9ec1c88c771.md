### Title
Cross-org forged Team membership (finding #2) escalates into `Shipit.github_teams` authorization via `User#authorized?` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb], [File: app/models/shipit/user.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` resolves the target `Team` solely by `params.team.id` (GitHub's `github_id`), with no check that the webhook's authenticated organization actually owns that team. `Shipit::User#authorized?` trusts the local `memberships` table unconditionally, so once a forged `Membership` row exists it grants full deploy/merge authorization on next OAuth login, with no re-validation against GitHub.

### Finding Description
The binding assumed safe is: **`membership.team_id == <team actually owned by the organization that signed the webhook>`**. This does not hold.

`find_or_create_team!` in `MembershipHandler` does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [1](#0-0) 
The `find_or_create_by!` lookup key is `github_id` alone; the `organization:` block only fires on create, so if a `Team` row with that `github_id` already exists (e.g., created earlier from the legitimate org's real membership events), it is returned unchanged regardless of which organization actually sent this webhook. `process` then does `team.add_member(member)` for `action == 'added'`, where `member` is `User.find_or_create_by_login!(params.member.login)` — an attacker-controlled login. [2](#0-1) 

The signature check that is supposed to bind a payload to "the org that owns it" is:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
``` [3](#0-2) 
where `repository_owner` is read straight from the attacker-supplied JSON body (`params.dig('organization','login')`), not from any independently authenticated source. [4](#0-3) 
In a multi-org Shipit configuration, `Shipit.github(organization:)` selects the webhook secret per named org key:
```ruby
config = github_app_config(organization)
raise GithubOrganizationUnknown, organization if config.nil?
``` [5](#0-4) 
So an attacker who legitimately owns/administers one configured org ("attacker-org") can sign a payload with their own known webhook secret while setting `team.id` inside the JSON body to the `github_id` of an *unrelated* org's Team (this is finding #2). Because `find_or_create_team!` never checks that `params.organization.login` matches the found team's `organization`, the forged event attaches an arbitrary `member.login` to that unrelated, security-relevant Team row.

The finding under audit is what happens next: once that forged `Membership` row exists, the referenced login (which could be the attacker's own GitHub account) simply completes a normal, unforged OAuth login. `Shipit::User#authorized?`:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [6](#0-5) 
performs a pure local SQL check against `memberships`/`teams`, with no live GitHub re-verification of team membership. If the forged `Team` row's `id` is among `Shipit.github_teams.map(&:id)`, this returns `true`. `force_github_authentication` uses exactly this predicate to gate all access to the app:
```ruby
unless current_user.authorized?
  ... render(plain: ..., status: :forbidden)
end
``` [7](#0-6) 

No existing guard closes this gap: `verify_signature` only proves the payload was signed by *some* configured org's secret, not that the claimed `team`/`organization` fields belong to that org; `ExplicitParameters` (`params do ... end` in `MembershipHandler`) only validates types/shape, not cross-field organizational consistency; and `User#authorized?`/`require_permission!` consult only the local, now-poisoned `memberships` table.

### Impact Explanation
Once the attacker's own login is written into a `Membership` row for a Team in `Shipit.github_teams`, a subsequent normal OAuth login by that attacker makes `current_user.authorized?` return `true`. This is a full authorization bypass into every action gated by `force_github_authentication`/`authorized?` and `require_permission!` — i.e., unauthorized deploys, rollbacks, merges, and stack administration across the Shipit instance, not limited to the attacker's own repository. This matches the "escalation into `Shipit.github_teams` authorization" High/Critical impact category, since it converts a data-integrity bug in one webhook handler into standing, session-based privilege for arbitrary future logins.

### Likelihood Explanation
This requires the preconditions from finding #2 to already hold: a multi-org Shipit deployment (`github_default_organization` non-nil) where the attacker legitimately controls at least one configured organization/GitHub App (and thus knows its `webhook_secret`), and can guess or discover the numeric `github_id` of a `Shipit.github_teams` Team (these IDs are often knowable/enumerable, and Team rows are also created via `refresh_members!`/`find_or_create_by_handle`, giving predictable small sequential local ids and discoverable GitHub team ids via public/semi-public GitHub team pages). Once a forged `Membership` exists, the attacker's remaining step is just a normal OAuth login — zero additional cost, fully repeatable, and does not require any secret beyond the one they already legitimately hold for their own org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/ignore the event if an existing Team with that `github_id` has a different `organization`. Additionally, `User#authorized?` should not treat local `memberships` as an unconditional source of truth for high-value authorization decisions without periodic revalidation, or the membership webhook path should independently confirm that the signing organization matches the team's organization before mutating membership.

### Proof of Concept
Minitest plan (extending `test/controllers/webhooks_controller_test.rb` patterns and `test/models/users_test.rb`):
1. Configure a multi-org secrets fixture with two orgs, `"legit-org"` (owns `shipit_teams(:shopify_developers)`, `github_id: 42`) and `"attacker-org"` (attacker-controlled, its own `webhook_secret`).
2. Seed `Team` fixture `shopify_developers` with `github_id: 42`, `organization: "legit-org"`, and ensure it is in `Shipit.github_teams`.
3. POST to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s webhook secret, and body:
   ```json
   { "action": "added", "team": { "id": 42, "name": "x", "slug": "x", "url": "http://x" },
     "organization": { "login": "attacker-org" }, "member": { "login": "mallory" } }
   ```
4. Assert `Membership.exists?(team_id: shipit_teams(:shopify_developers).id, user: User.find_by(login: "mallory"))` is `true` (broken binding: `membership.team.organization ("legit-org") != webhook signer org ("attacker-org")`, yet the row was written).
5. Log in as `mallory` (`session[:user_id] = User.find_by(login: 'mallory').id`) and assert `mallory.authorized?` is `true`, then hit a `require_permission!`-gated endpoint (e.g., stack deploy trigger) and assert it succeeds instead of `403`.
