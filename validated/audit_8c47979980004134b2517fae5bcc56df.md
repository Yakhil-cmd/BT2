### Title
Webhook signature verified against `repository.owner.login` while target repository is resolved from independent `repository.full_name` field, allowing cross-tenant PullRequest mutation - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`) from the attacker-controlled JSON body, while `EditedHandler` (and all other `Handler` subclasses) resolve the target `Repository`/`Stack`/`PullRequest` using the separate `repository.full_name` field. Because these two fields are never cross-validated, an attacker who owns "attacker-org" (with its own registered GitHub App and `webhook_secret`) can sign a payload with their own secret while setting `repository.full_name` to a victim-org repository, causing the signature check to pass under attacker-org's identity but the resulting write to land on a victim-org `PullRequest`.

### Finding Description
The broken binding, as an equality that must hold but does not:
`Shipit.github(organization: payload.dig('repository','owner','login')).webhook_secret` (the secret that authenticated the request) must equal `Shipit.github(organization: Repository.from_github_repo_name(payload.dig('repository','full_name')).owner).webhook_secret` (the secret that should govern the mutated repository). Nothing in the code enforces this.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (fallback `organization.login`) and calls `Shipit.github(organization: repository_owner)` to select the GitHub App config, then verifies the `X-Hub-Signature` HMAC against that org's `webhook_secret`. [2](#0-1) [3](#0-2) 
2. On success, `WebhooksController#create` dispatches the raw parsed `params` (JSON body) unchanged to the registered `pull_request` handlers, including `EditedHandler`. [4](#0-3) 
3. `EditedHandler#repository` resolves the target repository from `params.repository.full_name` only, via `Shipit::Repository.from_github_repo_name`, with no reference to `repository.owner.login` used in step 1. [5](#0-4) 
4. `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a `find_by(owner:, name:)` lookup — it does not check that this `owner` matches the org whose secret verified the signature. [1](#0-0) 
5. `EditedHandler#pull_request` then finds and mutates the `PullRequest` row scoped to that resolved repository's `id` via `.update(github_pull_request: params.pull_request)`. [6](#0-5) 

Attacker request: a `pull_request` `edited` event JSON body where `repository.owner.login = "attacker-org"` (so `verify_signature` uses attacker-org's `Shipit.github` config, whose `webhook_secret` the attacker legitimately knows because they registered that GitHub App per multi-org setup) and `repository.full_name = "victim-org/victim-repo"`, with `X-Hub-Signature` computed as `sha1=HMAC(attacker_webhook_secret, raw_body)`, and `number` matching a known/guessed victim PR number. `verify_signature` succeeds because it validated against attacker-org's own secret — it never checks that `repository.owner.login` matches `repository.full_name`'s owner segment. `EditedHandler` then looks up and updates the victim's `PullRequest` row using `full_name`, which the attacker fully controls independently of `owner.login`.

This is not prevented by `drop_unhandled_event` (only filters on event type), `ExplicitParameters` schema (only validates types/presence of `repository.full_name`, not consistency with `owner.login`), or any model validation (`Repository` validates format of its own `owner`/`name` columns, not linkage back to the authenticating org).

### Impact Explanation
An attacker controlling only their own GitHub org/app can forge webhook events that are authenticated as belonging to their org but that mutate `Shipit::PullRequest` records (title, state, labels, assignees, head commit reference) belonging to a different, victim organization's stack. This is a payload for one repository (attacker-org, the authenticating identity) mutating another's record (victim-org's `PullRequest`), matching the Critical "payload for one repository mutating another's stack, commit, task or team" category. It is fully repeatable against any victim repository/PR number the attacker can enumerate or guess, and the same pattern (`repository.full_name`-only resolution with no `owner.login` cross-check) is shared by every other `Handler` subclass (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `AssignedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `PushHandler` via `stacks`), so the blast radius extends beyond `EditedHandler` to stack archival/unarchival, label capture, and assignment across tenants.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub Apps/orgs (per `docs/setup.md`'s "Using Multiple Github Applications" section) — a documented, supported configuration. The attacker needs only their own legitimately-registered GitHub App/org (no victim secrets, tokens, or sessions required), and needs to guess or discover a target `pull_request` `number` for the victim stack (PR numbers are small sequential integers, often observable publicly on GitHub). Constructing and sending the forged webhook is a single HTTP POST with a correctly computed HMAC using the attacker's own secret — trivial and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, or in `Handler#repository_name`/`stacks`, enforce that the resolved `Repository.owner` from `full_name` matches the org identity used to validate the signature (`repository_owner`). Reject the webhook (or refuse to resolve/mutate) when `Repository.from_github_repo_name(full_name).owner != repository_owner.downcase`.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/edited_handler_test.rb`):
1. Configure two orgs via `Shipit.stubs(:secrets)` with `github: { 'attacker-org' => { webhook_secret: 'attacker-secret', ... }, 'victim-org' => { webhook_secret: 'victim-secret', ... } }`.
2. Create `victim_repo = shipit_repositories` with `owner: 'victim-org'`, and a `stack`/`pull_request` under it (`shipit_pull_requests` fixture or created record) with a known `number`.
3. Build `payload = payload_parsed(:pull_request_opened).merge('action' => 'edited')`; set `payload['repository']['owner']['login'] = 'attacker-org'` and `payload['repository']['full_name'] = 'victim-org/victim-repo'`; set `payload['number']` to the victim PR's number and `payload['pull_request']['title'] = 'Forged Title'`.
4. Sign: `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', payload.to_json)`.
5. POST to `:create` with `X-Github-Event: pull_request` and `X-Hub-Signature: signature`.
6. Assert the equality before: `Shipit.github(organization: 'attacker-org').webhook_secret != Shipit.github(organization: Repository.from_github_repo_name('victim-org/victim-repo').owner).webhook_secret`.
7. Assert `response.status` is `:ok` (signature accepted under attacker-org).
8. Assert `pull_request.reload.title == 'Forged Title'` — the victim's `PullRequest` was mutated despite the signature only proving attacker-org's identity.
