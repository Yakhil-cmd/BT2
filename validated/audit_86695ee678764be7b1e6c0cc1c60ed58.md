### Title
Cross-organization webhook forgery: `status`/`push` events are authenticated against the payload's own `repository.owner.login`, not against the target `Stack`'s repository, allowing an operator of *any* configured GitHub organization to forge events for *another* organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC against using a field taken from the same untrusted JSON body it is trying to authenticate, and none of the downstream event handlers re-check that the organization used for signature verification actually matches the organization/repository that gets mutated.

### Finding Description
The webhook signature check picks the verifying secret from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` looks up the app config (and thus `webhook_secret`) for that organization from `secrets.github` in multi-org setups [3](#0-2) . Multi-organization configuration is a documented, supported deployment mode where each org has its own independent `webhook_secret` [4](#0-3) .

Once the signature is accepted (proving only that *some* legitimate org's webhook secret produced this HMAC), the event is dispatched to handlers that resolve their target using **other fields of the same body**, which are not required to be consistent with `repository.owner.login`:

- `Handler#stacks` resolves the target repository from `payload.dig('repository', 'full_name')`, a distinct field from `repository.owner.login`: [5](#0-4) 
- `StatusHandler#process` doesn't even scope by repository — it updates **any** `Commit` in the entire database whose `sha` matches the payload, globally: [6](#0-5) 
- `PushHandler#process` triggers `sync_github` for whatever `Stack`s match `repository.full_name` and `branch`: [7](#0-6) 

This breaks the trust binding: *the organization whose secret authenticated the webhook* must equal *the repository/commit being written to*. In this engine, the code enforces only the former via `repository_owner`, while handlers act on `repository.full_name` or a bare `sha` — fields the signature covers cryptographically (so they can't be tampered with after the fact) but that the application never cross-checks against the organization used to select the verifying secret.

### Impact Explanation
In a multi-org Shipit deployment, an actor who is a legitimate administrator of their own GitHub App/org "X" (and therefore knows X's own `webhook_secret`, which is not a Shipit credential) can craft a JSON body where `repository.owner.login` (or the fallback `organization.login`) is "X", but `repository.full_name` (for push/PR events) or `sha` (for status events) refers to a target stack that belongs to a completely different, unrelated organization "Y" also hosted on the same Shipit instance. Signing this forged body with X's own secret passes `verify_signature`, and the handler then acts on Y's stack/commit:
- `status` events can flip CI state on Y's commits with no repository scoping at all, which feeds into commit deployability checks gating auto-deploys.
- `push` events can force `sync_github` on Y's stacks.

This crosses an authentication boundary the engine claims to enforce (per-organization webhook secrets) and results in unauthorized writes/state changes on another organization's stack from an attacker who never held any credential for that organization or for Shipit itself — matching the High-impact criterion of unauthenticated write into stack/commit state and a path toward an unauthorized deploy.

### Likelihood Explanation
Requires the operator to run Shipit in the documented multi-organization mode (multiple independent GitHub Apps configured under `secrets.github`), and requires the attacker to be a legitimate admin of at least one of the configured orgs' GitHub Apps (to know that org's own `webhook_secret`) while targeting a different configured org's stacks. This is plausible in shared/multi-tenant Shipit deployments, which the project explicitly documents as a supported configuration.

### Recommendation
After successful signature verification, re-derive the expected organization strictly from the `GithubApp`/config entry that was used to verify the signature and require every downstream handler to filter its target lookups (`Repository.from_github_repo_name`, `Commit.where(sha:)`, team/org lookups) by that same organization, rejecting any payload where `repository.owner.login`/`organization.login` disagree with it. In particular, `StatusHandler` should scope `Commit` lookups by repository/organization, not by a global `sha` match.

### Proof of Concept
1. Operator configures Shipit with two GitHub orgs, "attacker-org" and "victim-org", per the documented multi-org config [4](#0-3) .
2. Attacker legitimately administers their own GitHub App for "attacker-org" and knows its `webhook_secret`.
3. Attacker crafts a `status` webhook payload: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}, "sha": "<sha of a commit tracked by victim-org's stack>", "state": "success", ...}`, and signs it with `attacker-org`'s `webhook_secret` as `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = "attacker-org", fetches `attacker-org`'s app, verifies the HMAC successfully [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no organization/repository filter and creates a "success" status on victim-org's commit [6](#0-5) , despite the attacker never holding any credential for `victim-org`.

Note: I could not fully trace `Commit#create_status_from_github!` and `Commit#deployable?` inside the given tool-call budget to confirm the exact downstream effect on auto-deploy triggering; this should be verified directly in `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb` before treating the deploy-triggering consequence as fully proven, though the cross-organization write itself (forging a commit status for another org's commit) is confirmed by the code shown above.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
