## Title
Webhook signature verification is bound to the payload's `organization`/`repository.owner` field, not to the `repository.full_name` that is actually acted upon, allowing a valid webhook signer for one GitHub org to trigger syncs/deploys on stacks belonging to a different org - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC against using `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check for that org succeeds, the event handlers (e.g. `PushHandler`) resolve the *target* repository from a completely different field of the same untrusted body — `repository.full_name` — with no re-check that this repository belongs to the org whose secret was used to authenticate the request.

### Finding Description
- `verify_signature` picks the signing organization purely from attacker-controlled payload fields: ` [1](#0-0) ` ` [2](#0-1) `
- The actual repository/stack the event is applied to is derived from a *different* payload field, `repository.full_name`, inside `Handler#stacks`/`#repository_name`: ` [3](#0-2) `
- `Repository.from_github_repo_name` does a raw owner/name lookup with no cross-check against the org used for signature verification: ` [4](#0-3) `
- `PushHandler#process` then syncs/deploys every matching, non-archived stack for that repository name: ` [5](#0-4) `

The binding that is broken as an equality:
`organization authenticated by HMAC (repository_owner)` ≠ `organization of the repository actually written to (repository.full_name)`.

Because the HMAC covers the raw POST body, an attacker who legitimately controls a GitHub App/organization installed on this Shipit instance (and therefore genuinely knows that org's `webhook_secret`) can sign a valid webhook whose `repository.owner.login`/`organization.login` is their own org (so it passes `verify_webhook_signature`), while setting `repository.full_name` to `victim-org/victim-repo` — a stack belonging to a completely different, unrelated organization also hosted on the same Shipit instance. Since `Handler#stacks` and `PushHandler#process` never re-derive or validate the owner from the verified organization, the forged event is dispatched against the victim's stack, triggering `stack.sync_github(expected_head_sha: ...)` (and analogous cross-org effects for other handlers keyed off `repository.full_name`, e.g. status/check_suite/pull_request handlers) for a repository the attacker's org has no relationship to.

### Impact Explanation
This crosses a genuine authentication boundary: the attacker never possesses the victim org's `webhook_secret`, yet is able to make Shipit act on the victim's stack purely because signature verification and target-resolution are keyed off two independent, both attacker-controlled, fields. This matches the "Critical — cross-repository writes / unauthorized deploy" impact category: an attacker-controlled push/status/check_suite event can force a GitHub sync (and, depending on stack configuration such as continuous deployment, an actual deploy) of a repository/stack outside the attacker's authorized scope.

### Likelihood Explanation
Requires the attacker to control any single GitHub organization/App that is legitimately configured on the same multi-tenant Shipit instance (a supported, documented configuration — see `docs/setup.md` "Using Multiple Github Applications"). No GitHub App private key, `ApiClient` token, or Shipit session is needed; only knowledge of one's own org's webhook secret, which the attacker legitimately has. The only variable is that GitHub itself normally sets `repository.owner.login` to match the actual pushed repository — but the check here trusts the JSON body verbatim rather than deriving the owner from the resolved `repository.full_name`/stack, so a crafted, self-signed HTTP request to `/github/webhooks` bypasses that assumption entirely.

### Recommendation
Derive the organization used for signature verification from the same resolved repository record that handlers use to select stacks (i.e., look up `Repository.from_github_repo_name(payload.dig('repository','full_name'))` first, then verify the signature using that repository's owner/org secret), or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before verification, so the org whose secret is checked is always the org that owns the repository actually acted upon.

### Proof of Concept
1. Attacker legitimately installs/operates a GitHub App for `attacker-org`, which is configured in this Shipit instance's multi-org `github:` secrets with a known `webhook_secret`.
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` and `X-Github-Event: push`, then POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and succeeds because the attacker legitimately knows that secret: ` [1](#0-0) `
5. `PushHandler` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` (unrelated to `attacker-org`) and calls `stack.sync_github(...)` on victim-org's stacks: ` [5](#0-4) `
