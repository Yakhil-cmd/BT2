### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` / `repository.full_name` fields lets attacker mutate another repository's PullRequest labels - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify the raw request body against based on `params.dig('repository','owner','login')`, a field taken directly from the attacker-controlled JSON body. `LabelCapturingHandler#repository` (and `#capture_labels`) instead resolves the target `Shipit::Repository` using a *different* field from the same body, `params.repository.full_name`. Because these two fields are never checked against each other, an attacker who controls a repository/org (and therefore genuinely knows that org's `webhook_secret`) can forge a raw HTTP POST to `/webhooks` where `repository.owner.login` names their own org (so signature verification passes) but `repository.full_name` names an unrelated repository, causing that unrelated repository's `PullRequest#labels` to be overwritten.

### Finding Description
The broken binding: `organization_verifying_secret == organization_owning(repository.full_name)` is assumed but never enforced.

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner)` to obtain the `GitHubApp`/secret used for `verify_webhook_signature`: [1](#0-0)  and [2](#0-1) .
- `LabelCapturingHandler#repository` resolves the repository to mutate using `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, a completely separate field of the same JSON body: [3](#0-2) .
- `capture_labels` then persists attacker-chosen label names onto that resolved repository's stack's `PullRequest`: [4](#0-3) .
- `Repository.from_github_repo_name` performs a straightforward DB lookup by `owner`/`name` parsed from `full_name`, with no relation to whichever org's secret verified the request: [5](#0-4) .

Root cause: the controller and the handler each independently read attacker-supplied JSON fields (`repository.owner.login` vs `repository.full_name`) that are assumed to always describe the same repository, but nothing enforces that assumption for a raw POST that bypasses GitHub's actual webhook delivery (i.e., is crafted directly against the endpoint).

Exploit flow: attacker owns `org-a/repo-a` and knows `webhook_secret_a` (since it's their own GitHub App/org config). They POST directly to `/webhooks` with header `X-Github-Event: pull_request` and a JSON body where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/repo-b"` (an existing Shipit-tracked repository with an active `ReviewStack`/`PullRequest`), signed with `webhook_secret_a`. `verify_signature` looks up the App for `org-a`, verifies successfully using the attacker's own known secret, and the request proceeds. `LabelCapturingHandler` then resolves `repo-b` via `full_name` and overwrites `repo-b`'s `PullRequest#labels` with attacker-chosen values via `pull_request.update!(labels: ...)`.

Why existing guards fail: `verify_signature` only proves the raw body was signed by *some* org's secret consistent with a field inside that same body — it does not compare that org against the org actually being written to by any downstream handler. `ExplicitParameters` schema in `LabelCapturingHandler` only validates the types/presence of `repository.full_name`, not its relation to `repository.owner.login`. No model validation in `Repository`, `Stack`, or `PullRequest` re-derives or checks org ownership against the verifying secret.

### Impact Explanation
An attacker who legitimately controls one repository/org configured in Shipit can inject arbitrary label strings into a *different, unrelated* repository's active `PullRequest#labels`, without any interaction from that repository's owners. Since labels feed into `ReviewStack#env`/environment-variable-named injection for the next deploy of that other repository's `ReviewStack`, this is a cross-tenant write that can escalate to attacker-controlled environment variables reaching `Command#unbundled_env` → `PTY.spawn` on repo B's deploy host. This matches the "payload for one repository mutating another's stack" / RCE-adjacent Critical impact category. The attack is repeatable against any repository that (a) is tracked in Shipit and (b) has an active (non-archived) review stack, and works cross-tenant as long as Shipit hosts multiple GitHub Apps/orgs, one of which the attacker legitimately controls.

### Likelihood Explanation
Requires Shipit configured with multiple GitHub Apps (documented multi-org setup) and the attacker legitimately controlling at least one of those orgs/repos (an unprivileged precondition satisfied by "any GitHub user who owns a repo configured in one of the orgs"). No Shipit session, API token, or victim secrets are needed — only the attacker's own webhook secret, which they already possess by definition of owning that org's GitHub App config. The attacker crafts a raw HTTP POST directly to the public `/webhooks` endpoint (no GitHub UI needed to trigger the actual event, since the raw body is fully attacker-controlled and only needs a valid HMAC under their own known secret). This is low-cost and repeatable at will against any Shipit-tracked repository name, provided its label-consuming stack machinery is active.

### Recommendation
After a valid signature is verified for organization `X`, enforce that any repository referenced by a handler (`params.repository.full_name` in `LabelCapturingHandler`, `LabeledHandler`, `UnlabeledHandler`, etc.) belongs to organization `X`. Concretely, compare the owner segment of `repository.full_name` against `repository_owner`/the verified `organization` before resolving/mutating any `Shipit::Repository`, and reject the webhook (422) on mismatch, rather than relying on the two fields being self-consistent.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` patterns):
1. Configure test secrets with two orgs (`org-a`, `org-b`) each with a distinct known `webhook_secret` (use `test/dummy/config/secrets_double_github_app.yml` pattern).
2. Create fixture `Shipit::Repository` for `org-b/repo-b` with an active (non-archived) `Stack`/`ReviewStack` with an existing `PullRequest` whose `labels` are `[]`.
3. Build a `pull_request` "labeled" payload where `payload["repository"]["owner"]["login"] = "org-a"` and `payload["repository"]["full_name"] = "org-b/repo-b"`, `pull_request.labels = [{name: "malicious-label"}]`.
4. Sign the raw JSON body with `webhook_secret_a` (known/attacker-controlled) using `sha1=` + `OpenSSL::HMAC.hexdigest('sha1', webhook_secret_a, body)`, set as `X-Hub-Signature` header, `X-Github-Event: pull_request`.
5. POST to `/webhooks` with this body/header.
6. Assert response is `:ok` (verification against `org-a`'s secret succeeded — left side of the equality: `verifying_org == "org-a"`).
7. Assert `Shipit::Repository.find_by(owner: "org-b", name: "repo-b").review_stacks.find_by(...).pull_request.reload.labels == ["malicious-label"]` (right side: `mutated_repo_org == "org-b"`), proving the two sides diverge and the write crossed organizational boundaries despite no guard comparing them.
