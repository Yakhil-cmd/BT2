## Finding

The strongest local analog to the EIP‑1271 type‑confusion bug is a public‑key type‑confusion bug in Aptos's REST‑API‑to‑internal authenticator conversion, in `api/types/src/transaction.rs`, in `impl TryFrom<&SingleKeySignature> for AccountAuthenticator`: [1](#0-0) 

```rust

        "Failed to parse given public_key bytes as AnyPublicKey::FederatedKeyless",

```

### Title
Incorrect public-key variant wrapping in `SingleKeySignature -> AccountAuthenticator` conversion drops FederatedKeyless binding - (File: `api/types/src/transaction.rs`)

### Summary
When converting an API-level `SingleKeySignature` whose `public_key` field is `PublicKey::FederatedKeyless`, the code correctly parses the bytes into the federated-keyless public-key struct but then wraps it with `AnyPublicKey::keyless(...)` instead of `AnyPublicKey::federated_keyless(...)`. This is exactly the class of bug in the external report: the validator uses the wrong "interface"/type when constructing the authenticator, so downstream signature checking and address binding are performed against the wrong scheme.

### Finding Description
Elsewhere in the same file, the analogous but correct conversion for the general `PublicKey -> AnyPublicKey` path is implemented properly: [2](#0-1) 
which shows the developers' intended distinction between `Keyless` and `FederatedKeyless`. However the `TryFrom<&SingleKeySignature> for AccountAuthenticator` path collapses `FederatedKeyless` into `Keyless`, discarding the federated-issuer binding entirely (the federated-keyless struct encodes an additional `jwk_addr` used to source the JWK set from a specific on-chain address rather than the natively governed JWK set). The resulting `AccountAuthenticator::SingleKey` authenticator carries `AnyPublicKey::Keyless` regardless of the caller's actual intent.

This authenticator is subsequently used by `AccountAuthenticator::verify` / `AnyPublicKey`-based verification logic: [3](#0-2) 
and its derived authentication key/address (`AuthenticationKey::any_key(AnyPublicKey::...)`) differs between `Keyless` and `FederatedKeyless` because the federated variant is domain-separated by the federated issuer's address. Using the wrong variant therefore:
- produces a different authentication key than the one associated with the sender's actual on-chain account (federated-keyless senders bind their account to a specific `jwk_addr`), and
- routes signature verification to the native/trusted-issuer JWK validation path instead of the federated JWK-address validation path.

### Impact Explanation
For any caller that builds a `SignedTransaction`/`AccountAuthenticator` via this API conversion path with a `FederatedKeyless` public key, the authenticator produced will not match the sender's real authentication key, causing prologue's authentication-key check to fail (`PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY`) — directly analogous to the reported bug where legitimate smart-contract-wallet owners are unable to sign valid transactions. This is a genuine admission-boundary correctness bug: the wrong public key type is bound into the authenticator that feeds sender/signature validation.

### Likelihood Explanation
This triggers deterministically whenever this specific conversion function is exercised with a `FederatedKeyless` public key — no privileged access or race condition needed, only construction of a `SingleKeySignature` with `public_key: PublicKey::FederatedKeyless`. I was not able to fully trace, within the remaining tool budget, every REST-API call site that invokes `TryFrom<&SingleKeySignature> for AccountAuthenticator`/`TransactionAuthenticator` to confirm it is reachable from an externally-facing endpoint that actually accepts and submits transactions built from this JSON representation (as opposed to being used only in internal/test tooling). This should be verified before treating this as a high/critical, network-reachable admission bypass.

### Recommendation
Fix the branch to use the correct wrapper:
```rust
PublicKey::FederatedKeyless(ref p) => {
    let key = p.value.inner().try_into().context(
        "Failed to parse given public_key bytes as AnyPublicKey::FederatedKeyless",
    )?;
    AnyPublicKey::federated_keyless(key)
},
```
Add a regression test asserting that round-tripping a `FederatedKeyless` `SingleKeySignature` through this conversion yields an `AccountAuthenticator` whose derived authentication key/address matches the original federated-keyless-derived address, and add exhaustive match coverage (e.g., a `match` without a wildcard/duplicate-arm construction) so future new `PublicKey` variants cannot silently fall through to an unrelated `AnyPublicKey` constructor.

### Proof of Concept
1. Construct a `SingleKeySignature` with `public_key = PublicKey::FederatedKeyless(...)` and a valid `Signature::Keyless(...)`.
2. Call `AccountAuthenticator::try_from(&signature)`.
3. Observe the resulting `SingleKeyAuthenticator` contains `AnyPublicKey::Keyless` (not `AnyPublicKey::FederatedKeyless`).
4. Compute `AuthenticationKey::any_key(...)` for both variants from the same raw key bytes and show they differ, demonstrating the produced authenticator/address does not correspond to the real federated-keyless-derived sender account, causing prologue authentication-key mismatch (denial of admission) for that legitimate class of signer.

**Caveat:** I could not, within the remaining budget, confirm the exact externally reachable endpoint(s) that invoke this specific `TryFrom` conversion (versus its use being limited to internal encode/decode helpers or tests). This should be confirmed to establish the precise reachability/severity before treating it as a critical, network-exploitable admission bypass rather than a functional-correctness/DoS bug for federated-keyless accounts.
