### Title
Signature Reuse / Replay Risk in `is_valid_sig` Formula Primitive Due to Missing Context Binding - (File: `formula/evaluation.js`)

### Summary
The oscript formula primitive `is_valid_sig(message, pem_key, sig)` verifies a raw signature against an arbitrary, free-form message string supplied entirely by the AA definition author, with no protocol-enforced binding to the signer's address, the specific AA instance, the asset, or a deadline/nonce. Because trigger data (and therefore any signed package/signature revealed inside it) is published publicly on the DAG once a triggering unit is posted, an unprivileged trigger sender who observes a previously valid `(message, signature)` pair can replay it against any other AA (or the same AA in a different, unintended context) that accepts a structurally compatible message, exactly mirroring the root cause described in the reported CrosschainMerkleDistributor issue: a signature that does not encode enough context is reusable across unrelated authorization events.

### Finding Description
`is_valid_sig` is implemented in `formula/evaluation.js`: [1](#0-0) 

The primitive only checks that `evaluated_signature` validly signs `evaluated_message` under `evaluated_pem_key`, via `signature.verifyMessageWithPemPubKey`: [2](#0-1) 

There is no requirement that `evaluated_message` embed the AA address (`this_address`), the asset being spent, a deadline/expiry, or a nonce — any binding of the signed message to a specific authorization context is left entirely to the AA author's oscript. This differs from the more structured `is_valid_signed_package`, whose underlying `validateSignedMessage` at least binds the signature to a specific verifying `address` and to the full serialized `signed_message` object: [3](#0-2) 

But even there, the content of `signed_message` itself (e.g., channel id, period, asset) is entirely up to the AA author to include — the primitive itself performs no automatic context binding. This is demonstrated by ocore's own bundled payment-channel template, which must manually re-verify `channel` and `period` fields inside the signed message to prevent cross-channel/cross-period replay: [4](#0-3) 

If an AA author (reachable actor: "AA author") omits such binding fields — e.g., relies on `is_valid_sig`/`is_valid_signed_package` with a message that only contains an amount or an id shared across multiple AA instances/assets — a trigger sender who captured a signature from one public trigger (all trigger `data` becomes visible on-chain the moment the triggering unit is posted) can resubmit it as `trigger.data` to a different AA instance or a different execution branch of the same AA to authorize an unintended payout, analogous to User B reusing User A's signature across different airdrop events in the original report.

### Impact Explanation
Successful replay lets an attacker cause an AA to release funds it should not release, resulting in unauthorized fund loss from the AA's balance — this is a concrete "AA fund loss" impact reachable by an unprivileged AA trigger sender, matching the severity bar (Medium) for reused-signature fund theft.

### Likelihood Explanation
Exploitability depends on an AA definition that uses `is_valid_sig`/`is_valid_signed_package` without independently binding the signed content to a unique context (asset, AA address, nonce/deadline). Because the primitives themselves provide no such binding and it's easy for an AA author copying common patterns (off-chain approvals, airdrop-style claims, multi-instance templates) to omit it, the likelihood of this class of bug appearing in deployed AAs is non-trivial, even though ocore's own bundled example correctly adds channel/period checks as a mitigation, underscoring that the burden of preventing replay is left to the AA author rather than enforced by the primitive.

### Recommendation
- Document prominently (and ideally enforce via linting/validation tooling) that any AA using `is_valid_sig` or `is_valid_signed_package` for authorization must embed a unique context identifier in the signed message — at minimum `this_address` (or another AA-instance-unique identifier), the relevant asset, and a nonce/deadline — to prevent cross-instance and cross-context replay.
- Consider extending `is_valid_signed_package`'s schema (or introducing an optional AA-address-bound wrapper) so that a `signed_message` can be require to include the verifying AA address, making unintentional omission harder.

### Proof of Concept
1. AA author deploys two structurally similar AAs (or two states/branches of one AA) that both accept: `is_valid_sig(trigger.data.message, pem_key, trigger.data.sig)` where `trigger.data.message` only encodes something like `"claim:1000"` without embedding `this_address` or an asset identifier.
2. User A signs `"claim:1000"` intending it to authorize a claim from AA #1.
3. The triggering unit containing `trigger.data = {message: "claim:1000", sig: ...}` is posted publicly and becomes visible to all nodes/observers.
4. User B extracts `(message, sig)` from AA #1's public trigger and submits the same `trigger.data` to AA #2 (or a different execution path of AA #1), which independently re-validates the same signature successfully via `is_valid_sig`, releasing funds not intended for User B.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}
