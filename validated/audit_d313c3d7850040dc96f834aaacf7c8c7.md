## Finding confirmed

This traces to a real, verifiable authorization bypass — but it's not exactly what the question frames it as (a "no branch exists" gap in `check_permissions!`). The actual root cause is a controller override that discards existing scope enforcement. [1](#0-0) [2](#0-1) 

`BaseController` defines `stacks` to be scoped to `current_api_client.stack_id` when the token is stack-scoped, and `stack` calls `stacks.from_param!(params[:stack_id])` — this is the actual per-token stack boundary used correctly by `Api::StacksController#stack` (`stacks.from_param!(params[:id])`). `Api::CCMenuController`, however, redefines `stack` itself as `Stack.from_param!(params[:stack_id])`, entirely bypassing the `stacks` scope. `require_permission :read, :stack` only calls `ApiClient#check_permissions!` which checks the permission string `"read:stack"` against `permissions`, never `stack_id` — so for a stack-scoped `ApiClient` (Stack A) with `read:stack`, a request to `/api/stacks/<Stack B>/ccmenu` succeeds with 200, returning Stack B's build status/name/lastBuildStatus, not a 403.

### Title
Horizontal stack-scope bypass in `Api::CCMenuController#stack` skips `current_api_client.stack_id` restriction - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the inherited `stack` helper with its own version that calls `Stack.from_param!(params[:stack_id])` directly, instead of using `BaseController#stacks` which restricts lookups to `current_api_client.stack_id` when the token is scoped to a single stack. Since `require_permission :read, :stack` only validates the permission string and never the stack scope, any client holding a `read:stack` token scoped to Stack A can read the CCMenu status (build state, last build label, web URL) of any other Stack B.

### Finding Description
The intended binding is: `current_api_client.stack_id.present? ⇒ accessible_stack_ids == {current_api_client.stack_id}`, enforced generically through `BaseController#stacks`/`#stack` [1](#0-0)  and correctly consumed by `Api::StacksController#stack` (`stacks.from_param!(params[:id])`) [3](#0-2) .

`Api::CCMenuController` breaks this binding by shadowing `stack` with its own private method that ignores the scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

The only gate applied is `require_permission :read, :stack` [5](#0-4) , which resolves to `ApiClient#check_permissions!(operation, scope)`:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [6](#0-5) 

This check only inspects the client's `permissions` array (e.g. `read:stack`) — it never compares `stack_id`. So a client created with `stack_id: <Stack A>.id` and `permissions: ['read:stack']` (the exact kind of scoped client that `CCMenuUrlController#client` generates for browser "Fetch URL" usage [7](#0-6) ) can call `GET /api/stacks/<Stack B owner>/<Stack B name>/<Stack B branch>/ccmenu?token=<token>` and receive a 200 with Stack B's data, because `stack` resolves via unscoped `Stack.from_param!` rather than the scoped `stacks` relation.

### Impact Explanation
A holder of a stack-scoped `read:stack` API token (e.g., the CCMenu integration token generated per-stack for CI dashboard tools) can enumerate/read build status, last build label/time, activity, and web URL of any other stack in the Shipit instance, not just the one it was issued for. This is a horizontal privilege escalation across tenants/stacks — an unauthenticated-for-that-resource read of stack state, matching the High severity category ("unauthenticated read of stack state ... task streams"). It is repeatable for any Stack B identifier the attacker can guess or observe (stack identifiers are `owner/repo/branch`, often predictable/public).

### Likelihood Explanation
Requires possession of any valid `ApiClient` token scoped to some stack with `read:stack` permission — these are routinely generated and distributed via `CCMenuUrlController#fetch` for CI status widgets, so such tokens are plausible to exist and leak (e.g. embedded in CCMenu client configs, browser history, shared dashboards). Once held, the exploit is a single unauthenticated-scope GET request with no additional secrets, no timing constraints, fully repeatable.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited `BaseController#stack`/`#stacks` (scoped by `current_api_client.stack_id`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot resolve stacks outside their assigned `stack_id`.

### Proof of Concept
Minitest plan (in `test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a stack-scoped client cannot read another stack's ccmenu status" do
  other_stack = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: "main")
  @client.update!(stack_id: @stack.id, permissions: %w[read:stack])

  get :show, params: { stack_id: other_stack.to_param, token: @client.authentication_token }

  assert_response :forbidden # currently fails: actual response is 200 with other_stack's XML payload
end
```
Assert both sides of the binding: `@client.stack_id == @stack.id` (scope) vs. the stack actually returned in the XML (`name` attribute equals `other_stack.to_param`), demonstrating divergence between the token's granted scope and the resource served.
