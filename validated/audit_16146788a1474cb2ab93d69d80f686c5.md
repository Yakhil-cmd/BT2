### Title
Stack-scoped CCMenu monitoring token grants read access to every stack in the instance, not just the stack it was issued for - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` is supposed to mint a read-only monitoring token scoped to a single stack, embed it in a CCMenu/CCTray URL, and hand that URL to the user for use in third-party CI-status dashboards. The `ApiClient` it creates is never bound to the requested stack, and the consuming `Api::CCMenuController` also bypasses the app's own stack-scoping mechanism, so the resulting token silently authorizes reading the state of *any* stack in the Shipit installation.

### Finding Description
`CCMenuUrlController#client` creates the `ApiClient` like this: [1](#0-0) 
It sets only `permissions: %w[read:stack]` and `creator`/`name` — it never passes `stack:` even though the surrounding action clearly intends the token to be scoped to the single stack requested via `params[:stack_id]` (`api_stack_ccmenu_url(stack_id: stack.to_param)`, line 8). `ApiClient#belongs_to :stack, optional: true` means an unscoped client is created.

The engine's normal stack-scoping mechanism lives in `Api::BaseController`: [2](#0-1) 
`stacks` restricts to `Stack.where(id: current_api_client.stack_id)` only when the client actually has a `stack_id`. Because the CCMenu client never gets one, this check is a no-op for it, and it would fall back to `Stack.all` even if used.

Worse, `Api::CCMenuController` doesn't even use the inherited scoped `stack` method — it overrides it to bypass scoping entirely: [3](#0-2) 
`stack` resolves via `Stack.from_param!(params[:stack_id])` directly, and `authenticate_api_client` only checks that `params[:token]` maps to *some* valid `ApiClient`; it never checks that the client is authorized for the requested `stack_id`.

This is the same bug class as the report's missing-operation-handling issue: the code path that is supposed to bind a granted capability (the token) to a specific target (the stack) never performs that binding, so the "stack a token authorises" and "the stack it touches" diverge.

### Impact Explanation
CCMenu/CCTray URLs are designed to be embedded in external, often less-trusted, CI dashboard tooling on the assumption that leaking them only exposes the build status of one specific stack. Because the token is actually unscoped, anyone who obtains a single CCMenu URL (via a leaked dashboard config, browser history, log, etc.) can use that token against `Api::CCMenuController#show` for arbitrary `stack_id` values and read the deploy/build state (latest deploy id, sha, running/success status) of every stack in the Shipit instance, including stacks the original token holder has no access to. This is an unauthorized cross-stack read of stack state, matching the "High" impact bucket for escalation beyond the authorized stack scope.

### Likelihood Explanation
Any authenticated Shipit user can trigger creation of this improperly-scoped token simply by visiting the CCMenu URL feature for one stack; no special privileges are required to mint it, and the resulting token is meant to be shared/embedded externally, making leakage plausible. Exploiting it requires no further authentication — only knowledge of the token and a target stack id, which for internal Shipit installs may be low/sequential.

### Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific stack (`stack:` attribute), include the stack in the `find_or_create_by!` lookup key so distinct stacks don't share the same token, and change `Api::CCMenuController#stack` to use the inherited, properly-scoped `stack` method from `Api::BaseController` instead of `Stack.from_param!` directly.

### Proof of Concept
1. User with access to Stack A visits the CCMenu URL endpoint for Stack A (`CCMenuUrlController#fetch`, `stack_id=A`). A `read:stack` `ApiClient` named "CCMenu Client" is created with no `stack_id`, and a URL like `https://shipit/api/stacks/A/ccmenu.xml?token=T` is returned/embedded in an external dashboard.
2. An attacker who obtains `token=T` (from the dashboard config, logs, etc.) sends `GET /api/stacks/B/ccmenu.xml?token=T` for an arbitrary Stack B they have no access to.
3. `Api::CCMenuController#authenticate_api_client` validates `T` as a legitimate `ApiClient` (line 34) and `#stack` resolves Stack B directly via `Stack.from_param!` (line 30) with no ownership check.
4. The response renders Stack B's latest deploy id, sha, and status — data the attacker was never authorized to view via this token.
