### Title
`review_stacks_enabled` is bypassed for `allow_with_label`/`prevent_with_label` due to operator precedence in `provision?` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` chains `&&`/`||` such that `repository.review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label` or `prevent_with_label` branches. An operator who disables review stacks (`review_stacks_enabled = false`) but leaves `provisioning_behavior = allow_with_label` (or `prevent_with_label`) still gets stacks auto-provisioned for pull requests, letting any outside contributor trigger `ReviewStackAdapter#create!` → `ReviewStackProvisioningQueue.add` → eventual `Command`/`PTY.spawn` execution of the fork's `shipit.yml`.

### Finding Description
The broken binding: `repository.review_stacks_enabled == false` (as configured by the operator) is claimed to gate stack creation, but the actual gating value evaluated by Ruby is `true` for the `allow_with_label`/`prevent_with_label` disjuncts, because `&&` binds tighter than `||`: [1](#0-0) 

This parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is *not* distributed across the other two disjuncts. The same pattern is duplicated verbatim in `ReopenedHandler#unarchive?`, `LabeledHandler#archive?`/`unarchive?`, and `UnlabeledHandler`: [2](#0-1) 

Attacker's request: an outside contributor opens a pull request against a fork branch (`pull_request.head.ref` = fork branch) on a repository where the operator has set `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label`. The attacker (or anyone with label permission on their own fork PR, or simply a repo configured with `prevent_with_label` where no label is required at all) causes `provision?` to evaluate to `true` even though review stacks are supposedly disabled.

`process` calls `respond_to_pull_request_opened?` → `provision?` → `ReviewStackAdapter#find_or_create!` → `create!`, which builds a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` (attacker's fork branch) and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) 

No other guard intervenes: `ReviewStackAdapter#create!` does not itself re-check `review_stacks_enabled`, and `Repository#review_stacks_enabled` is a plain boolean column with no additional validation forcing consistency with `provisioning_behavior`: [4](#0-3) 

Existing tests only cover `review_stacks_enabled: false` combined with `allow_all`: [5](#0-4) 
There is no test exercising `review_stacks_enabled: false` with `allow_with_label`/`prevent_with_label`, so this divergence went unnoticed by the existing suite.

Once the review stack is provisioned from the attacker's fork branch, downstream provisioning executes the branch's `shipit.yml` steps via `TaskCommands`/`Command#start`/`PTY.spawn` (standard Shipit review-stack provisioning flow) — i.e., attacker-controlled deploy commands run on the host, even though the operator explicitly disabled review stacks for that repository.

### Impact Explanation
This is Critical: RCE on the deploy host via `Command`/`PTY.spawn`, triggered by an unprivileged pull request against a repository whose operator explicitly disabled review-stack provisioning (`review_stacks_enabled = false`). The blast radius is scoped to any repository configured with `allow_with_label` or `prevent_with_label` regardless of the `review_stacks_enabled` flag — a config combination an operator would reasonably expect to be inert. It is repeatable for every PR the attacker opens (and for `prevent_with_label`, requires no label at all, just an unlabeled PR).

### Likelihood Explanation
Preconditions are only repository-configuration state that a Shipit operator could plausibly have (`review_stacks_enabled = false`, `provisioning_behavior = allow_with_label` or `prevent_with_label`) — e.g., an operator who once used review stacks with label-gating and later toggled the enabled flag off without changing `provisioning_behavior`, or simply never realized these two settings aren't independent. Attacker cost is a normal GitHub pull request (with a label, if `allow_with_label`) — no secrets, no privileged role needed. Fully repeatable.

### Recommendation
Fix operator precedence explicitly so `review_stacks_enabled` gates every branch, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to `ReopenedHandler#unarchive?`, and the `archive?`/`unarchive?` methods in `LabeledHandler`/`UnlabeledHandler`, all of which share this pattern.

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label and label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix this assertion fails (`Shipit::Stack.count` increases by 1) because `provision?` evaluates `(false && false) || (true && true) || ...` = `true`, demonstrating the equality `review_stacks_enabled(false) == gating_value(true)` is broken.
