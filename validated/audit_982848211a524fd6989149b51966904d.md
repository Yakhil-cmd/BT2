### Title
Asset definer can retroactively strip existing token holders of the ability to spend/transfer via `asset_attestors`, permanently freezing their already-issued balance - (File: validation.js)

### Summary
For any asset created with `spender_attested: true`, the asset definer can publish an `asset_attestors` message at any time to replace the list of attestors that authorizes a spend. Because payment validation always checks the *current* (latest stable) attestor list rather than the list that was in effect when the coins were received, a holder who legitimately acquired the asset while attested can be instantly and permanently locked out of moving or redeeming those same coins the moment the definer republishes a narrower attestor list — with no delay, no grace period, and no fallback conversion path. This mirrors the Juicebox `changeTokenOf` bug class: a privileged party unilaterally mutates a core parameter of an already-issued asset, stranding value already held by users who relied on the old state.

### Finding Description
When an asset is defined with `spender_attested: true`, `validatePayment` requires that at least one author of a payment unit be present in the asset's attestor list, and for issuance the issuer specifically must be attested: [1](#0-0) 

The attestor list used for this check is not the list that existed when the payer received the funds — it is always the *latest* stable list as of `last_ball_mci`, fetched via `storage.readAsset` → `addAttestorsIfNecessary`, which explicitly queries only the single most recent `asset_attestors`/`asset` unit for that asset: [2](#0-1) 

The attestor list can be replaced at will by the definer through the `asset_attestors` message. `validateAttestorListUpdate` only checks that the message is single-authored, that the asset actually requires attestation, that the sender is the asset's definer, and that the new list is well-formed (sorted, valid addresses, under the max count) — there is no check that previously-attested holders (or holders who already possess a balance) remain in the new list, and no delay/timelock before the new list takes effect: [3](#0-2) 

The update is persisted as a normal DAG message with no special expiry or grandfathering logic: [4](#0-3) 

Consequently: Alice legitimately receives units of a `spender_attested` asset while she is on the attestor list. The definer later publishes `asset_attestors` with a new list that excludes Alice. From that point on, any payment message where Alice is the sole/relevant author fails validation with `"none of the authors is attested"` (validation.js:2118), even though the coins are already hers and were validly transferred to her under the old list. Alice cannot spend, transfer, or otherwise dispose of her existing balance — it is permanently frozen unless/until the definer chooses to re-add her.

### Impact Explanation
This allows the asset definer (an unprivileged, permissionless role reachable simply by anyone issuing a `spender_attested` asset) to unilaterally and instantly freeze other users' already-held asset balances by rewriting the attestor list — a single crafted/malicious follow-up unit turns previously spendable funds into permanently unspendable funds for any holder not included in the new list. This is analogous to the `changeTokenOf` finding: a mid-flight change to a core asset parameter (attestor authorization) strands value belonging to third parties who already transacted under the old rules, with no grace period or conversion mechanism.

### Likelihood Explanation
High reachability: any address can define a `spender_attested` asset (this only requires `spender_attested: true` plus an initial attestor list) and later post a single `asset_attestors` unit to change that list — no special privileges, cooperation from holders, or race conditions are required. The only actor who benefits from being malicious is the asset definer itself, which is a normal, expected participant in this flow (not a "malicious node/hub" scenario), so this fits squarely in the "asset issuer" and "asset issuance and transfer conditions" analog categories.

### Recommendation
- Evaluate `spender_attested` checks against the attestor list that was current at the time the spent output/coin was created (or at time of receipt), not the latest list as of `last_ball_mci`, so that legitimately-held balances remain spendable regardless of later list changes.
- Alternatively, require a mandatory delay/timelock before an `asset_attestors` update takes effect, and/or provide an explicit unwind/redeem path for holders who fall off the list, analogous to the recommended mitigation for `changeTokenOf` (add a delay, or a conversion mechanism) so that changes cannot retroactively strand already-issued funds.

### Proof of Concept
1. Definer D issues asset A with `is_private: false, spender_attested: true, attestors: [D, H1]`.
2. D issues (or H1 acquires by transfer) a balance of asset A to holder H1 while H1 is on the attestor list; this validates fine per `validation.js:2115-2122`.
3. D publishes a new `asset_attestors` message for asset A with `attestors: [D, H2]` (H1 removed). This passes `validateAttestorListUpdate` (`validation.js:2829-2848`) because it only checks D is the definer and the list is well-formed.
4. `storage.readAsset`'s `addAttestorsIfNecessary` (`storage.js:1917-1946`) now returns the new list `[D, H2]` as the asset's current attestor list for any subsequent validation.
5. H1 attempts to spend/transfer her already-held balance of asset A. `validatePayment` checks `objAsset.arrAttestedAddresses.indexOf(issuer_address/author)` and fails with `"none of the authors is attested"` (`validation.js:2118-2121`), permanently freezing H1's coins even though they were validly received before the list change.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
