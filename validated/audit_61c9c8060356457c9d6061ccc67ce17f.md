## Title
Uncaught length-mismatch exception in `chash.isChashValid()` reachable via lax address validation (`isValidAddressAnyCase`) crashes node on a malformed payment output/address in a posted unit - (File: chash.js)

### Summary
`chash.js` decodes a base32/base64-encoded 32-character c-hash and then reconstructs a fixed-size bit string via `buffer2bin()`/`separateIntoCleanDataAndChecksum()`, which **must** be exactly 160 or 288 bits or the code `throw Error("bad length=...")`. This throw is only guarded by a `try/catch` around the *decode* step, not around the subsequent length-dependent parsing. `ValidationUtils.isValidAddressAnyCase()` (used by `validatePaymentInputsAndOutputs()` for units created before `timestampUpgradeMci`) validates only the *length* of the address (32 chars) but not the character set, unlike `isValidAddress()` which enforces `/^[A-Z2-7]{32}$/`. This lets an attacker feed an address string containing characters outside the base32 alphabet into `base32.decode()`, which can silently return a decoded buffer whose byte length differs from the expected 20 bytes (160 bits), triggering the uncaught `Error` deep inside `chash.js` during normal unit validation.

### Finding Description
The vulnerable chain is:
1. `validation.js` → `validatePaymentInputsAndOutputs()` selects `isValidAddressWithCase = ... : ValidationUtils.isValidAddressAnyCase` for units with `last_ball_mci < constants.timestampUpgradeMci` [1](#0-0) , and calls it directly on attacker-supplied `output.address` [2](#0-1) .
2. `isValidAddressAnyCase()` only checks `isStringOfLength(address, 32)` before calling `chash.isChashValid()` — it does **not** apply the `/^[A-Z2-7]{32}$/` base32-alphabet regex that `isValidAddress()` uses [3](#0-2) .
3. Inside `chash.isChashValid()`, the decode call (`base32.decode(encoded)`) is wrapped in `try/catch`, but the follow-up calls `buffer2bin()`, `separateIntoCleanDataAndChecksum()`, and `bin2buffer()` are **not** protected [4](#0-3) .
4. `separateIntoCleanDataAndChecksum()` explicitly throws an uncaught `Error("bad length=...")` whenever the reconstructed bit-string length is not exactly 160 or 288 [5](#0-4) .
5. If the decoded buffer byte-length does not correspond to 160/288 bits (e.g., because `base32.decode` handles out-of-alphabet characters non-fatally, producing a truncated/garbled buffer instead of throwing), this exception is thrown synchronously and propagates uncaught up through `isValidChash` → `isValidAddressAnyCase` → `validatePaymentInputsAndOutputs` → `validate()` during processing of a single posted unit.

This mirrors the XCOFF bug class: a malformed/attacker-controlled structured input (a c-hash-encoded address) is passed into low-level parsing routines that assume a fixed internal structure/length without validating it end-to-end before performing size-dependent operations, causing an unhandled fault deep in the parsing path.

### Impact Explanation
An uncaught synchronous exception thrown during unit validation (inside the `mutex.lock` / `async.series` callback chain in `validation.js`) is not always caught by the surrounding error-handling callbacks since it is thrown, not passed to `callback(err)`. Depending on where in the call stack this occurs, this can escape as an unhandled exception and crash the Node.js process for any full node processing the malicious unit — a node-wide denial of service triggered by an unprivileged unit poster with a single crafted transaction. Because this path is only used for units with `last_ball_mci < constants.timestampUpgradeMci` it primarily affects historical/testnet-style code paths, but any code path that still calls `isValidAddressAnyCase` on live/replay validation is exposed. This qualifies as "a network unable to confirm new units" if nodes crash while validating/reprocessing such units, and represents inconsistent handling relative to the stricter `isValidAddress()`.

### Likelihood Explanation
Moderate. It requires: (a) crafting a unit whose `last_ball_mci` predates `constants.timestampUpgradeMci` (relevant to full replay/historical validation and older/testnet chains), and (b) confirming that the underlying `thirty-two` base32 decoder does not itself throw on invalid alphabet characters and instead returns a buffer of unexpected length. I was not able to inspect the `thirty-two` package source in this repository/index to confirm its exact behavior on invalid input, so the exploitability of step (b) is **unverified** and should be validated experimentally (e.g., calling `base32.decode()` directly with a 32-character string containing digits like `0`, `1`, `8`, `9` or lowercase letters) before treating this as confirmed-exploitable.

### Recommendation
- Make `isValidAddressAnyCase()` validate the character set as well (or reuse a shared alphabet check) rather than only length, to avoid feeding malformed data into `base32.decode()`.
- Wrap the entire body of `chash.isChashValid()` (not just the decode call) in `try/catch` so any length-mismatch or parsing exception returns `false` instead of throwing.
- Audit all other unguarded internal `throw Error(...)` calls in `chash.js` (`separateIntoCleanDataAndChecksum`, `mixChecksumIntoCleanData`, `checkLength`) for similar unguarded reachability from validation code paths.

### Proof of Concept
Conceptual PoC (requires confirming `thirty-two` decode behavior, which I could not verify from the indexed code):
```js
const chash = require('./chash.js');
// 32-char string with invalid base32 characters (e.g. contains '0','1','8','9' or lowercase)
const malformed = "0123456789abcdefghijklmnopqrstuv"; // 32 chars, not [A-Z2-7]
try {
  console.log(chash.isChashValid(malformed));
} catch (e) {
  console.log("UNCAUGHT:", e.message); // expect "bad length=..." if decode doesn't throw
}
```
Then, to trigger it through the full validation path, craft a unit with `last_ball_mci` below `constants.timestampUpgradeMci` containing a payment output whose `address` is such a malformed 32-character string, and submit it for validation via `validatePaymentInputsAndOutputs()`.

**Note on uncertainty:** I could not locate the `thirty-two` package's implementation in the indexed codebase to confirm whether `base32.decode()` throws or silently mis-decodes on out-of-alphabet input — this is the crux of exploitability and should be verified directly (e.g., in a Devin session with full filesystem/npm access) before treating this as a confirmed vulnerability.
