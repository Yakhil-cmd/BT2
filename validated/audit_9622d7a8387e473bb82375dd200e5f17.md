### Title
Uncaught exception on negative AA storage-size computation causes full-node crash while processing an AA trigger - (File: aa_composer.js)

### Summary
The Obyte reference CVE describes a negative-length computation in a legitimate accounting/size-tracking path (rx-queue fragment size) that is reachable from externally supplied packets and, because the negative value is never validated before use, crashes the whole system. `ocore`'s AA (Autonomous Agent) engine has an analogous unchecked negative-size computation in the storage-size bookkeeping that runs for every AA trigger: any user who posts a unit that triggers an AA drives execution into `updateStorageSize()`, which computes a delta from state-variable size differences and `throw`s a raw `Error` if the result is negative, with no `try/catch` anywhere in the async call chain that reaches it.

### Finding Description
`updateStorageSize()` in `aa_composer.js` accumulates `delta_storage_size` from the size difference between a state variable's new value and its `original_old_value`, then computes: [1](#0-0) 
```
var new_storage_size = storage_size + delta_storage_size;
if (new_storage_size < 0)
    throw Error("storage size would become negative: " + new_storage_size);
```
This is a hard, synchronous `throw`, not a callback error. It is reached from `finish()`: [2](#0-1) 
which is invoked at the end of every successful AA trigger response (`handleTrigger` → `sendUnit`/`handleSuccessfulEmptyResponseUnit` → `finish` → `updateStorageSize`). `handleTrigger` is driven directly by trigger units that any wallet, AA, or unprivileged unit poster can send to an AA address — it is normal, unprivileged application logic, not a peer/hub-only path.

The size accounting itself depends on `getValueSize()`, which derives byte length from `toString()`/`toNumber().toString()`/JSON-serialization of the *current* JS representation of a value: [3](#0-2) 
while the actual persisted size was computed at a different point in time from a potentially different representation (`getTypeAndValue()`), and `original_old_value` bookkeeping is only refreshed for secondary AAs via `updateOriginalOldValues()`: [4](#0-3) 
Any place where the size recorded when a value was last charged to `storage_size` diverges from the size computed by `getValueSize()` on the value now being read/deleted (e.g. object/number re-serialization differences, chained primary/secondary AA calls updating the same state var multiple times before `updateStorageSize` reconciles) can make `delta_storage_size` more negative than the account's tracked `storage_size`, driving `new_storage_size` below zero.

Unlike ordinary AA validation failures, which are surfaced through `cb(err)`/`bounce(err)` and handled gracefully, this specific negative-size branch is a bare `throw` deep inside nested async callbacks (`conn.query` callbacks, `async.eachSeries`, etc.) with no surrounding `try/catch`. It therefore propagates as an uncaught exception. `network.js` installs a global handler that intentionally re-throws to kill the process on any uncaught exception: [5](#0-4) 
so any full node (or hub) that processes the offending AA trigger crashes.

### Impact Explanation
A crash triggered from processing a normal AA trigger unit is a denial-of-service against every full node that validates/executes it (analogous to "attackers cause a system crash" in the CVE). Because AA trigger execution happens on every node that keeps the AA's state current, a single crafted trigger can be broadcast network-wide, crashing multiple full nodes/hubs simultaneously and halting further confirmation of units that depend on that AA executing (nodes unable to stay online to confirm/process new units).

### Likelihood Explanation
Reaching the negative-size branch requires a specific accounting mismatch between the size recorded for a state variable when it was last charged and the size computed for it when later deleted/replaced (e.g., through chained primary/secondary AA triggers manipulating the same state var, or representation differences between write-time and read-time serialization of numbers/objects). This is a narrower trigger condition than a simple malformed unit, but it is reachable purely through unprivileged unit-posting/trigger-sending (no special privileges, no p2p/hub compromise needed), matching the CVE's "unprivileged local condition causing a crash under specific data conditions" theme.

### Recommendation
- Never `throw` inside deep async callbacks for a condition derived from attacker-influenced/accounting state; convert the negative-size branch in `updateStorageSize()` (aa_composer.js:1562-1563) into a normal error path (`return cb(...)`) that bounces the AA response instead of crashing the process.
- Audit `getValueSize()`/`getTypeAndValue()` and `original_old_value` tracking (including `updateOriginalOldValues()`) to guarantee they always agree with what was actually persisted, eliminating the possibility of `delta_storage_size` legitimately exceeding `storage_size`.
- Add regression tests exercising multi-hop primary/secondary AA triggers that repeatedly update/delete the same state variables to ensure `storage_size` accounting can never underflow.

### Proof of Concept
Conceptual trigger path (concrete state-var sequence needed to underflow requires further fuzzing/testing against `getValueSize`/`original_old_value` interactions, but the unchecked path is exercised on every AA response):
1. Attacker posts a trigger unit to an AA whose oscript updates/deletes state variables across a primary AA and one or more secondary AA calls in the same trigger cascade.
2. `handleTrigger` executes the AA(s), updates `stateVars`, and on success calls `finish(objResponseUnit)` → `updateStorageSize(cb)`. [6](#0-5) 
3. If the size recorded for a deleted/replaced state var (`original_old_value`) is larger than what `getValueSize()` computes for the value actually being removed/replaced at that moment, `delta_storage_size` can exceed `storage_size` in magnitude, making `new_storage_size` negative.
4. `throw Error("storage size would become negative: ...")` fires with no enclosing `try/catch`, propagating to Node's `uncaughtException` handler in `network.js`, which re-throws and crashes the process on every full node that executes this trigger.
