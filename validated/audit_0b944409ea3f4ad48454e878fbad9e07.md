I found the actual admission-boundary mismatch: `execute_multisig_transaction` in `aptos_vm.rs` determines the *actual executed payload* via `get_next_transaction_payload`, which always prefers the on-chain stored `transaction.payload` over the caller-supplied payload — but `validate_multisig_transaction`'s prologue check of "provided payload matches stored payload" is feature-gated (`abort_if_multisig_payload_mismatch_enabled`) and only applies when `payload_hash` is `None` and the caller-provided payload is non-empty.

### Title
Multisig prologue payload-match check is feature-gated while execution always defers to stored payload - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction` (the VM prologue for `Multisig` transactions) only enforces that the caller-supplied `payload` matches the on-chain payload when the feature flag `abort_if_multisig_payload_mismatch_enabled` is on. When the flag is disabled, an executor can supply an arbitrary/mismatched `payload` argument and admission (mempool + prologue) will succeed regardless, because `execute_multisig_transaction` in `aptos_vm.rs` doesn't use the caller-supplied payload for execution when the transaction has a full payload on chain — it calls `get_next_transaction_payload`, which returns `transaction.payload` unconditionally when `Some`.

### Finding Description
`validate_multisig_transaction` at [1](#0-0)  guards the "provided payload equals stored payload" assertion behind `features::abort_if_multisig_payload_mismatch_enabled()`. If this flag is not enabled, no check happens at all when `transaction.payload_hash` is `None` (i.e., the transaction was created via `create_transaction`, storing the full payload on-chain, as at [2](#0-1) ).

The runtime dispatch is defined by `get_next_transaction_payload`, which unconditionally prefers the stored payload: [3](#0-2) . Execution in the VM calls this same function via `GET_NEXT_TRANSACTION_PAYLOAD` at [4](#0-3) , so the *actual* payload executed as the multisig account is always the on-chain one when present, independent of the caller-supplied `payload` argument.

This means the "payload" argument accepted at admission (mempool validation and prologue) is effectively decorative in the non-feature-gated code path — an attacker-controlled or unrelated payload can be attached to the transaction, pass prologue, and be admitted into mempool/block, while at execution time the different, real on-chain payload silently substitutes in. This is exactly the class of "pre-validation mismatch" called out by the Admission Impact Gate: what the prologue is checking is not what actually gets executed, because the invariant tying the admitted external payload to the executed payload is only conditionally enforced.

### Impact Explanation
While the ultimate executed payload is still the *legitimate* on-chain stored payload (so no unauthorized state transition occurs on execution), the admission layer's payload check is decoupled from execution semantics whenever the feature flag is off. This breaks the invariant that mempool/VM-validator admission decisions reflect what will actually execute — the report's asked-for "pre-validation mismatch that causes a transaction which should fail admission to execute and commit" class. Any tooling, indexer, or downstream consumer relying on the transaction's payload as submitted (e.g., for simulation, gas estimation, or payload verification prior to broadcast) can be misled, and a malicious owner can craft misleading "decoy" transactions that get admitted with one payload while a different pre-approved payload executes.

### Likelihood Explanation
This requires `features::abort_if_multisig_payload_mismatch_enabled` to be disabled (this looks like a newer hardening flag being rolled out, implying older/default network states may not have it enabled) and requires the transaction to have been created via `create_transaction` (full on-chain payload, not hash-only). Both preconditions are ordinary, unprivileged use of the public multisig API, not a privileged operation.

### Recommendation
Make the payload-match check unconditional (remove the `abort_if_multisig_payload_mismatch_enabled` gate), or reject the transaction outright if a non-empty `payload` argument is submitted with a full on-chain payload and it fails to match — regardless of feature flag — so that admission-time validation always reflects what `execute_multisig_transaction` will actually run.

### Proof of Concept
I could not construct/run a full end-to-end PoC within the available tooling (no execution environment access here); this assessment is based on static tracing of `validate_multisig_transaction`, `get_next_transaction_payload`, and `execute_multisig_transaction`. A concrete PoC would: (1) create a multisig account and a transaction via `create_transaction` storing full payload P on-chain; (2) with `abort_if_multisig_payload_mismatch_enabled` disabled, submit an `execute_multisig_transaction`-style user transaction with a `Multisig { transaction_payload: Some(Q) }` where Q ≠ P; (3) observe the transaction is admitted (mempool/prologue succeed) despite Q≠P, then observe P (not Q) is what actually executes — confirming the admission-time payload has no binding relationship to execution.

Given the uncertainty about default feature-flag state in production, and that the ultimate execution still uses the correct/legitimate on-chain payload (bounding the direct exploitability), I present this as a lower-confidence finding relative to a full theft/hijack primitive. Note that I did not find a stronger admission-boundary bug (e.g., in fee-payer/WebAuthn/sequence-number/mempool logic) that independently satisfies the "unprivileged root cause + broken invariant + high/critical impact" bar during this session — those other paths (fee-payer authenticator zero-address dual-verification, mempool sequence-number handling, WebAuthn challenge binding) appeared to be correctly implemented and covered by existing tests.

    /// Return the payload for the next transaction in the queue.
    public fun get_next_transaction_payload(
        multisig_account: address, provided_payload: vector<u8>): vector<u8> {
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let sequence_number = multisig_account_resource.last_executed_sequence_number + 1;
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);

        if (transaction.payload.is_some()) {
            *transaction.payload.borrow()
        } else {
            provided_payload
        }
    }
