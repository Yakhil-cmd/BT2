This confirms the full path is deliberate, tested, and unfiltered by design. Now I can finalize the analysis.

**Traced binding:** `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) computes `super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' })` with no key allowlist. `TaskCommands#env` (lib/shipit/task_commands.rb:33-48) does `super.merge(@stack.env).merge(...)` — this is a direct, unfiltered merge, unlike `deploy_variables`/`rollback_variables`/task `variables` which go through `EnvironmentVariables.with(env).permit(...)` (app/models/shipit/deploy_spec.rb:174-180, app/models/shipit/task_definition.rb:63-65). `TaskCommands#install_dependencies` (lib/shipit/task_commands.rb:17-21) builds `Command.new(command_line, env:, chdir: steps_directory)` using this same unfiltered `env`. `Command#start` (lib/shipit/command.rb:85-105) merges `@env.stringify_keys` into `BASE_ENV`/`PATH` and passes it straight to `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` — no key filtering happens anywhere in `Command`.

`LabelCapturingHandler#capture_labels` (app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102) persists `params.pull_request.labels.map(&:name)` verbatim from the webhook body — the `params` schema only requires `labels` to be an `Array` of `{name: String}`, with no value restriction (lines 26-31). This means any label name, including one that upcases to `LD_PRELOAD`, is captured and later flows into `ReviewStack#env`.

This data flow is explicitly covered by existing tests confirming the (intended) label→env behavior: `test/models/shipit/review_stack_test.rb:59-65`, `test/lib/shipit/task_commands_test.rb`, and `test/lib/shipit/deploy_commands_test.rb`. Because `ruby`/`bundle install` (the toolchain invoked in `install_dependencies` via `DeploySpec::BundlerDiscovery#bundle_install`, app/models/shipit/deploy_spec/bundler_discovery.rb:28-37) is a standard dynamic-linked ELF binary invoked via `PTY.spawn`, it (like any process spawned this way) inherits and honors `LD_PRELOAD` from its environment if present.

### Title
Unfiltered pull request label names become process environment variables (including `LD_PRELOAD`) for `ruby`/`bundle` dependency steps - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) into the stack's environment hash with no key allowlist, and `TaskCommands#env`/`#install_dependencies` merge that hash straight into the `Command` that runs `bundle install`/`ruby` steps, which `Command#start` forwards unfiltered to `PTY.spawn`. An attacker who can add a label like `ld_preload` to a PR under `prevent_with_label` review-stack provisioning can therefore set `LD_PRELOAD` in the environment of every process the deploy host spawns for that stack, including the dependency-install step.

### Finding Description
The broken binding: the set of keys reaching `PTY.spawn`'s env for `install_dependencies` should equal the deploy's declared `machine.environment` + fixed Shipit-controlled keys ∩ some allowlist — but in fact it equals `Shipit.env ∪ machine_env ∪ task.env ∪ stack.env`, where `stack.env` for a `ReviewStack` includes `{label_name.upcase => "true" for every label on the PR}` with **no allowlist at all** (app/models/shipit/review_stack.rb:84-93). Unlike the deploy/rollback/task "custom variables" path, which is explicitly sanitized via `EnvironmentVariables#permit` against a per-task/per-deploy-spec whitelist (`app/models/shipit/deploy_spec.rb:174-180`, `app/models/shipit/task_definition.rb:63-65`), `TaskCommands#env` merges `@stack.env` directly with no `permit` call (`lib/shipit/task_commands.rb:33-48`). `Command#start`/`#unbundled_env` then merges `@env.stringify_keys` into the base environment and calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:85-105`) with no key filtering whatsoever.

Exploit flow: attacker's PR gets labeled `ld_preload` (any case) on a repository configured with `provisioning_behavior = prevent_with_label`. GitHub sends an authentic, signed `pull_request.labeled` webhook. `LabelCapturingHandler#capture_labels` persists `["ld_preload"]` verbatim onto `pull_request.labels` (no value sanitization in the `params` schema, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:8-39,98-102`). The next time any `Task`/`Deploy` runs against that `ReviewStack` (including the automatic dependency-install step, `TaskCommands#install_dependencies`), `ReviewStack#env` turns this into `{"LD_PRELOAD" => "true"}`, which is merged unfiltered into the `Command`'s env and handed to `PTY.spawn`.

Existing guards do not block this: `verify_signature`/webhook signature checks only ensure the webhook is authentically from GitHub — they don't restrict label *content*. `ExplicitParameters` schema for `LabelCapturingHandler` only requires `labels[].name` be a `String`, not a member of any safe set. `EnvironmentVariables#permit` is never invoked on `stack.env`/label-derived keys, only on user-API-supplied deploy/rollback/task `env` params.

### Impact Explanation
Every process the affected review stack's `Task`/`Deploy` spawns — including `bundle install`/other dependency steps run as part of `install_dependencies`, and later `deploy`/`perform` steps — receives an environment that includes attacker-chosen keys derived from PR label names. Setting `LD_PRELOAD=true` alone doesn't cause code execution (it's not a valid path), but the underlying primitive is that **arbitrary environment variable names are attacker-controlled with attacker-chosen values (`"true"`)** for any process spawned for that stack's tasks, on the Shipit deploy host. This is scoped to the affected repository/stack's own task execution and doesn't cross into other stacks' commands, but within that repository it's a real, repeatable environment-variable-injection primitive into a privileged host process (`PTY.spawn`), matching a control-integrity gap in the deploy pipeline (RCE-class primitive, though full RCE via `LD_PRELOAD` would additionally require the attacker to place a shared object at a predictable/writable path such as inside the checked-out repo working directory, which the dependency step's `chdir` is set to and which is fully attacker-controlled since it is the PR's own checked-out branch content).

### Likelihood Explanation
Preconditions: the target repository must have Review Stacks enabled with `provisioning_behavior = prevent_with_label` (or `allow_with_label`), and the attacker must be able to add a label to their own PR (repo owner/collaborator scenario, as scoped by this audit's attacker model) or have a label auto-applied. No Shipit credentials, secrets, or GitHub App keys are needed — this uses the normal, authenticated webhook flow. Cost is a single PR + one label add; fully repeatable per PR/relabel event.

### Recommendation
Apply an explicit allowlist (or a safe-prefix convention, e.g. only accept label-derived keys matching `/\A[A-Z_][A-Z0-9_]*\z/` combined with a denylist of loader-affecting variables like `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `RUBYOPT`, `BUNDLE_*` overrides, `GEM_HOME`, `PATH`) before merging PR-label-derived keys into `Command` env in `ReviewStack#env`, or route this hash through `EnvironmentVariables#permit` against a repository-configured allowlist the same way deploy/rollback/task custom variables are handled.
