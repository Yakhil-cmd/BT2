### Title
Cross-tenant deauthorization via `github_id`-only Team lookup in `MembershipHandler#process` (`removed` action) - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves the `Team` to mutate solely by `params.team.id` (`github_id`), never checking that `params.organization.login` matches the resolved `Team#organization`. Signature verification only proves the requester controls the `webhook_secret` for `repository_owner`/`params.organization.login`, not that they own the specific `team.id` referenced. If a `Team` record with a colliding `github_id` already exists for a different organization, a `removed` membership webhook signed by the attacker's own org can delete a `Membership` belonging to that unrelated victim organization's operator.

### Finding Description
The broken binding: `organization whose webhook_secret verified the request body` (`repository_owner` in `WebhooksController#verify_signature`, `app/controllers/shipit/webhooks_controller.rb:24-30`) must equal `organization owning the Team whose Membership is deleted` (`team.organization` for the `Team` resolved in `find_or_create_team!`). These are never checked against each other.

Path: `WebhooksController#create` dispatches the parsed JSON to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) . `verify_signature` authenticates only that the body was signed with the `webhook_secret` configured for `repository_owner` (derived from `params.dig('organization', 'login')`), i.e., the attacker's own org [2](#0-1) . Inside `MembershipHandler#process`, `find_or_create_team!` looks up the `Team` by `github_id: params.team.id` alone, with no organization-scoping in the query [3](#0-2) . For `action == 'removed'`, the resolved `team.members.delete(member)` is called, deleting the corresponding `Membership` row [4](#0-3) . `Team#members` is a `has_many :members, through: :memberships` association [5](#0-4) , so `delete` destroys the join row regardless of which org "owns" it in Shipit's model — there is no re-check that the team's `organization` matches the webhook's authenticated organization.

Given the stipulated precondition (a pre-existing `Team` row whose `github_id` collides with the `team.id` in the attacker-signed payload, and a `Membership` for the victim operator on that `Team`), the flow is: attacker signs a `membership` webhook with their own valid `webhook_secret` for their own org login → `verify_signature` passes (correctly, for the attacker's own org) → `find_or_create_team!` returns the pre-existing victim `Team` (matched by `github_id`, not `organization`) → `team.members.delete(member)` removes the victim operator's `Membership`. None of `verify_signature`, `ExplicitParameters` schema, or `Team`/`Membership` model validations check organization ownership of the target `Team`; the schema only validates payload shape, and no validation on `Team` enforces `github_id` uniqueness scoped to `organization` (uniqueness is implicitly relied upon globally, but `find_or_create_by!` has no cross-check against `params.organization.login`).

Because `User#authorized?` is computed from `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , if the colliding `Team` is one of `Shipit.github_teams`, deleting the `Membership` flips `operator.authorized?` from `true` to `false`, deauthorizing them for actions gated on that check (e.g. `require_permission!`/`User#authorized?` guards).

### Impact Explanation
A write (deletion of a `Membership` row) occurs against a record owned by an organization that never authenticated the request — the signature only proves control of the attacker's own org's `webhook_secret`, not any relationship to the victim `Team`. This is a cross-tenant mutation: an attacker-controlled webhook deauthorizes a legitimate operator in a completely unrelated organization, flipping `authorized?` to `false` and potentially removing their ability to deploy/merge/administer stacks gated by `Shipit.github_teams` membership. This matches "a payload for one repository/org mutating another's team" and escalation/de-escalation of `Shipit.github_teams` authorization state.

### Likelihood Explanation
This shares the exact same root-cause precondition as the corresponding `added`-action finding: it requires an actual `github_id` collision between the attacker's real GitHub team and a pre-existing Shipit `Team` row for a different org. GitHub team IDs are globally unique identifiers assigned by GitHub itself — the attacker cannot choose or forge this ID in a genuinely-signed webhook; they can only supply whatever ID GitHub assigned to a team they truly own. Engineering such a collision is not attacker-controlled and depends entirely on database state/ID allocation outside the attacker's control, making real-world exploitation costly/impractical to engineer deliberately, though not impossible given a sufficiently large ID space overlap or coincidental prior collision. The code-level guard (organization-scoped lookup) is simply absent, so if the precondition materializes, exploitation is a single unauthenticated-relative-to-victim HTTP POST.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` in `find_or_create_team!`, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify that the resolved `team.organization` matches `params.organization.login` before performing `add_member`/`members.delete`, raising/dropping the event otherwise.

### Proof of Concept
In `test/models/webhooks/handlers/membership_handler_test.rb` (or equivalent):
1. Create `victim_team = Team.create!(organization: 'victim-org', github_id: 42, name: 'x', slug: 'x', api_url: 'http://x')`.
2. Create `operator = User.create!(login: 'operator', name: 'Operator')` and `Membership.create!(team: victim_team, user: operator)`.
3. Ensure `victim_team` is in `Shipit.github_teams` (stub) so `operator.authorized?` is currently `true`.
4. Build a payload: `{ action: 'removed', team: { id: 42, name: 'x', slug: 'x', url: 'http://x' }, organization: { login: 'attacker-org' }, member: { login: 'operator' } }`.
5. Call `MembershipHandler.call(payload)` directly (bypassing controller-level signature check, since the finding is that signature verification is org-scoped correctly but the handler ignores organization for team resolution).
6. Assert: before call, `Membership.exists?(team: victim_team, user: operator)` is `true` and `operator.authorized?` is `true`; after call, `Membership.exists?(team: victim_team, user: operator)` is `false` and `operator.reload.authorized?` (re-memoized) is `false` — despite `params.organization.login == 'attacker-org' != victim_team.organization == 'victim-org'`.
