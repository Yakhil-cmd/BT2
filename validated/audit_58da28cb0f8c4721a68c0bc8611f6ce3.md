## Analysis

The Nomad report describes a class of bug: an **unbounded, attacker-growable queue/list that must be linearly scanned during consensus-critical validation**, where any unprivileged actor can grow the list (via `xcall()`) to increase the cost/time of `improperUpdate()`'s `queue.contains()` scan, degrading availability.

The Obyte/`ocore` analog of "linear scan over an attacker-inflatable set during consensus-critical processing" is the main-chain **stability determination** logic in `main_chain.js`. Any unprivileged unit poster can create additional non-serial/alt-branch tips by choosing suboptimal parents (which the protocol allows — `pickParentUnits`/parent selection only bounds the *count* of parents per unit via `constants.MAX_PARENTS_PER_UNIT`, not the number of distinct alt-branch tips created network-wide), and each additional branch enlarges the sets that `determineIfStableInLaterUnits()` and its helpers must traverse to decide whether a unit is stable.

Specifically:
- `updateStableMcFlag()`/`advanceMcStability()` collects `arrAltBranchRootUnits` from best-children of the last stable unit and, for every alt-branch found, calls `createListOfBestChildren()`, which recursively walks *every* descendant of each alt-branch root down to free tips. [1](#0-0) [2](#0-1) 
- The same pattern repeats in `determineIfStableInLaterUnits()`, whose nested `createListOfBestChildrenIncludedByLaterUnits()` performs a similar unbounded downward/upward graph walk (`goDownAndCollectBestChildrenFast`, `goUp`, `findBestChildrenNotIncludedInLaterUnits`) over all not-yet-included alt-branch descendants before a stability verdict can be reached. [3](#0-2) [4](#0-3) 
- This stability check is invoked on the hot path of **every unit validation** that references a last ball not yet known-stable (`validateParents()` calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(...)` for essentially every incoming/posted unit). [5](#0-4) 

Because the number and depth of alt branches is driven entirely by what units peers/attackers choose to post (parent selection is free-form and only per-unit parent count is capped, not global branch count), a poster can cheaply keep spawning parallel, poorly-connected units that never converge onto the main chain quickly, inflating `arrAltBranchRootUnits`/`arrBestChildren` and thereby the cost of every subsequent stability check network-wide — directly analogous to the Nomad `queue.contains()` griefing vector, where an attacker made every future validating call more expensive without any slashing/cost proportional to the damage caused.

Given the depth of `main_chain.js` (nested recursive DB-driven traversals, `async.eachSeries`, `setImmediate` batching), this is a genuine O(n)-per-check design over an attacker-inflatable graph — the same root cause pattern as the report. However, I could not fully verify (within tool budget) whether there is an existing hard bound elsewhere (e.g., a cap on total number of live alt branches, or the number of "free" tip units single addresses may hold) that would neutralize this, nor could I quantify concretely the gas/DB cost multiplier per additional adversarial branch, or find any existing mitigation/rate-limiting comparable to `MAX_PARENTS_PER_UNIT` that applies at the *branch* level rather than the *per-unit parent count* level. This uncertainty prevents a fully-substantiated High/Critical severity claim without further live testing (e.g., simulating an attacker flooding many divergent tips and measuring the validation time growth on `determineIfStableInLaterUnits`).

### Title
Unbounded alt-branch traversal in main-chain stability checks enables validation-time DoS - (File: main_chain.js)

### Summary
`determineIfStableInLaterUnits()` and `advanceMcStability()`/`updateStableMcFlag()` in `main_chain.js` recursively enumerate all descendants of every non-main-chain ("alt") branch rooted below the last stable unit in order to decide whether a candidate last-ball unit is stable. Because parent selection during unit composition is essentially free-form (bounded only per-unit by `constants.MAX_PARENTS_PER_UNIT`, not bounded network-wide in terms of how many divergent alt branches can exist), an unprivileged actor can cheaply multiply the number and depth of alt branches that every future unit's stability check must traverse — mirroring the Nomad `Queue.contains()` O(n) griefing pattern, where anyone could insert entries that later, unrelated validations were forced to scan.

### Finding Description
Stability determination is not an O(1) or bounded-cost operation. `createListOfBestChildren()` recursively walks every best-child chain from `arrAltBranchRootUnits` down to free tips [2](#0-1) . `determineIfStableInLaterUnits()`'s internal `createListOfBestChildrenIncludedByLaterUnits()` performs an analogous unbounded walk with `goDownAndCollectBestChildrenFast`/`goUp`/`findBestChildrenNotIncludedInLaterUnits`, iterating over all alt-branch descendants not yet provably included by the later units being checked [3](#0-2) [4](#0-3) . This traversal cost scales with the number/depth of divergent (non-serial) branches present in the DAG below the stability point — a quantity directly influenced by what any unit poster chooses as parents. This stability check is invoked from `validateParents()` on essentially every unit whose last ball is not yet locally known stable [5](#0-4) , meaning the cost is paid repeatedly, by every node, for every unit that touches an unstable region of the graph — the same "everyone pays the cost of one attacker's queue-growth" dynamic described in the Nomad report.

### Impact Explanation
If an attacker can cheaply and repeatedly grow the number/depth of alt branches under the current stability frontier, they increase the per-unit validation cost for the whole network. In the worst case this delays or stalls `advanceMcStability()`/`markMcIndexStable()`, i.e., the network becomes slower to confirm new units and advance the stable main-chain index — matching the "network unable to confirm new units" impact bucket from the validation rules.

### Likelihood Explanation
Any address can post units and choose non-ideal parents (subject only to the per-unit `MAX_PARENTS_PER_UNIT` cap and standard fee/commission costs), so growing the number of alt branches is achievable by a normal unprivileged unit poster, similar to how anyone could call Nomad's `xcall()` to grow the queue. The severity depends on how quickly/economically an attacker can multiply alt-branch depth relative to normal network throughput and fees — a factor I was not able to fully quantify with the available tools, which is why the likelihood should be treated as **moderate but unverified** rather than conclusively demonstrated.

### Recommendation
- Bound the total number of concurrently-tracked alt branches / non-serial tips that must be scanned per stability check (e.g., cap depth/branching factor, or require O(log n) skip-list style lookups instead of full recursive descent).
- Consider charging alt-branch/"orphan-tip" units a cost proportional to the validation burden they impose on the rest of the network (akin to tps fees already present in `validateTpsFee`), so that intentionally inflating alt branches becomes economically self-limiting.
- Add monitoring/alerting for abnormal growth in `arrAltBranchRootUnits`/best-children set sizes during `updateStableMcFlag()`/`determineIfStableInLaterUnits()`.

### Proof of Concept
Not independently reproduced with tools in this session (would require running a local network/test harness, having several addresses post many units with deliberately divergent, non-converging parent selections over multiple rounds, and measuring the wall-clock/DB-query growth of `advanceMcStability()`/`determineIfStableInLaterUnits()` as alt-branch count/depth increases). This should be validated with a live Devin session capable of running the test/dev network before treating this as confirmed exploitable.
