### Title
Unauthenticated cross-organization webhook spoofing via `repository_owner`/`repository.full_name` binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a signature against using the attacker-controlled field `repository.owner.login` (or `organization.login`) from the still-unverified JSON body. Every downstream webhook handler, however, resolves the actual `Shipit::Repository`/`Stack` to mutate using a *different* attacker-controlled field, `repository.full_name`. These two fields are never checked against each other, so the "organization that authenticated" and "the repository that is written" are not bound together.

### Finding Description
In `verify_signature`: [1](#0-0) 
the app config (and its `webhook_secret`) is chosen via `repository_owner`, defined as: [2](#0-1) 
`params.dig('repository', 'owner', 'login')`. This value comes straight from the raw, not-yet-verified request body (`params = JSON.parse(request.raw_post)` in `create`, and Rails' own JSON parsing populates the same `params` object used here), i.e. it is fully attacker-controlled at the time it's used to pick the signing secret.

Meanwhile, every default handler (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target repository from a *separate* field: [3](#0-2) 
`payload.dig('repository', 'full_name')` — used to look up `Repository.from_github_repo_name(repository_name)` and then act on that repository's stacks (triggering merge processing, status updates, membership changes, etc.).

Because `webhook_secret` is validated per-organization (`Shipit.github(organization: repository_owner)`), and Shipit explicitly supports configuring multiple GitHub orgs each with an independent, optional `webhook_secret` (shown in `config/secrets.development.example.yml`), and `verify_webhook_signature` treats an unset secret as "always valid" (`return true unless webhook_secret`) in `lib/shipit/github_app.rb`: [4](#0-3) 
an attacker who can trigger (or knows the secret for) webhooks belonging to *any one* configured organization — including an organization deliberately left unsecured (`webhook_secret: nil`) — can forge a webhook whose `repository.owner.login`/`organization.login` names that low-value/unsecured org (so the signature check trivially passes) while setting `repository.full_name` to an entirely different, fully-secured organization's tracked repository. No code path ever asserts that the org used to select/verify the secret equals the org that owns the repository the handler subsequently mutates.

### Impact Explanation
This breaks the equality that should hold: `organization used to verify signature == owner of repository.full_name acted upon`. With that binding broken, an attacker with no Shipit session, no `ApiClient` token, no `webhook_secret` for the target org, and no repository write access to the target repository can still deliver arbitrary forged GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that are processed against a fully-secured, unrelated repository/stack. Depending on which default handler is invoked this can:
- flip commit statuses / check-run state used to gate CI requirements (`status`, `check_suite` handlers), which can unblock the merge queue or deploy gating for a stack the attacker has no access to — an unauthorized deploy/merge path;
- create pull-request/merge-queue entries (`pull_request` opened/labeled handlers) against a stack belonging to another org;
- manipulate `Membership`/`Team` records via the `membership` handler.

This matches the High/Critical impact classes of "an unauthorized deploy, rollback or merge" and effectively a cross-repository/cross-organization write, achieved purely by an unauthenticated actor exploiting the organization-vs-repository binding gap — analogous to the underlying `ConvexStakingWrapper`/`MasterChef` bug where the identity used for one purpose (accounting the `msg.sender`) diverges from the identity the action is actually meant to be scoped to.

### Likelihood Explanation
Exploitability requires the operator to run Shipit with at least two GitHub organizations configured (an explicitly supported and documented configuration shape) where at least one has no `webhook_secret` set (also an explicitly supported, non-error configuration per `config/secrets.development.example.yml`). Given that shape, exploitation needs zero credentials — a single unauthenticated `POST` to the public `/webhooks` endpoint with a crafted JSON body and a matching `X-Github-Event` header. This is a realistic, low-effort deployment scenario (multi-tenant Shipit installs commonly have a mix of secured "production" orgs and unsecured "sandbox/internal" orgs), so likelihood is moderate-to-high wherever this configuration pattern is used.

### Recommendation
- After resolving `repository_owner` and selecting the app used for signature verification, re-derive the repository/organization strictly from the verified GitHub App's own organization scope, not from a second unrelated payload field.
- Alternatively, once the signature is verified against a given organization's secret, assert that `payload.dig('repository', 'full_name')` (and `organization.login`) belongs to that same, verified organization before dispatching to any handler; reject (422) on mismatch.
- Consider requiring `webhook_secret` to be present for every configured organization (fail closed) rather than silently allowing unsigned webhooks for orgs without a configured secret.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`:
   - `sandbox-org`: no `webhook_secret` set.
   - `secure-org`: `webhook_secret: "s3cr3t"`, and it has a tracked `Repository`/`Stack` for `secure-org/critical-app`.
2. Attacker sends, without any authentication or knowledge of `s3cr3t`:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   (irrelevant, will be accepted)

{
  "sha": "<head sha of an open PR/commit on secure-org/critical-app>",
  "state": "success",
  "context": "ci/circleci",
  "repository": {
    "full_name": "secure-org/critical-app",
    "owner": { "login": "sandbox-org" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: 'sandbox-org')`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally — no valid signature required.
4. `Shipit::Webhooks::Handlers::StatusHandler` resolves the target repository via `payload.dig('repository', 'full_name')` = `secure-org/critical-app`, and updates the commit status on that stack as if the event legitimately originated from `secure-org`, potentially satisfying CI-required checks that gate an automatic deploy/merge on `critical-app`.

      github_app = Shipit.github(organization: repository_owner)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
