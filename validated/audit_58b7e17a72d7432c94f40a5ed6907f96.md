Now I have all the evidence needed. Let me look at the `SelfDestruct` and `SelfDestruct6780` implementations in statedb.go more carefully, and compare with go-ethereum's reference implementation.

### Title
Unconditional Balance Transfer in `opSelfdestruct6780` Violates EIP-6780 — (`blockchain/vm/instructions.go`)

### Summary

`opSelfdestruct6780` unconditionally executes `SubBalance` + `AddBalance` before calling `SelfDestruct6780`, which is the only conditional gate on `stateObject.created`. This means any contract **not** created in the same transaction will have its entire KAIA balance drained to an attacker-controlled beneficiary address, while the contract itself persists — directly contradicting EIP-6780's requirement that SELFDESTRUCT be a complete no-op for pre-existing contracts.

---

### Finding Description

`opSelfdestruct6780` in `blockchain/vm/instructions.go` reads the contract balance and performs the transfer unconditionally: [1](#0-0) 

```go
balance := interpreter.evm.StateDB.GetBalance(scope.Contract.Address())
interpreter.evm.StateDB.SubBalance(scope.Contract.Address(), balance)  // ← unconditional
interpreter.evm.StateDB.AddBalance(beneficiary.Bytes20(), balance)      // ← unconditional
interpreter.evm.StateDB.SelfDestruct6780(scope.Contract.Address())      // ← conditional
```

`SelfDestruct6780` in `statedb.go` is the **only** place the `stateObject.created` flag is checked: [2](#0-1) 

```go
func (s *StateDB) SelfDestruct6780(addr common.Address) {
    stateObject := s.getStateObject(addr)
    if stateObject == nil { return }
    if stateObject.created {   // ← only destruction is gated
        s.SelfDestruct(addr)
    }
}
```

The balance transfer (`SubBalance`/`AddBalance`) happens **before** and **outside** this guard. When `stateObject.created == false` (contract deployed in a prior transaction), `SelfDestruct6780` is a no-op for destruction, but the balance has already been moved.

---

### Impact Explanation

For any contract that:
1. Was deployed before Cancun (or in a different transaction), **and**
2. Has a reachable code path that executes `SELFDESTRUCT` (e.g., a public `kill()` function)

An attacker can call that function with an attacker-controlled beneficiary address after Cancun activation. The contract's full KAIA balance is transferred to the attacker. The contract itself is not destroyed and continues to exist with a zero balance. This is an unauthorized KAIA balance redirection that EIP-6780 was specifically designed to prevent.

---

### Likelihood Explanation

- Cancun is activated on Kaia (EIP-6780 is enabled via `enable6780` in `eips.go`).
- Many pre-existing contracts have public or semi-public `selfdestruct` paths.
- The attack requires only a standard transaction to a public contract function — no privileged access, no validator collusion, no key compromise.
- The attacker supplies the beneficiary address as a stack argument, making redirection to any arbitrary address trivial.

---

### Recommendation

Move the balance transfer inside the `stateObject.created` guard. The corrected `opSelfdestruct6780` should mirror the reference go-ethereum implementation: only transfer the balance (and call `SelfDestruct`) when the contract was created in the same transaction. When `stateObject.created == false`, the opcode must be a complete no-op — no `SubBalance`, no `AddBalance`.

Concretely, the balance transfer logic should be moved into `SelfDestruct6780` itself (or gated in `opSelfdestruct6780` by checking `StateDB.Created(addr)` before performing the transfer), so that both the destruction and the balance movement are conditional on the same flag.

---

### Proof of Concept

1. Deploy contract `Victim` (with a `function drain(address payable to) public { selfdestruct(to); }`) pre-Cancun. Fund it with 100 KAIA.
2. Activate Cancun fork (EIP-6780 live). `stateObject.created` for `Victim` is `false`.
3. Attacker calls `Victim.drain(attackerAddress)` via a normal transaction.
4. `opSelfdestruct6780` executes:
   - `SubBalance(Victim, 100)` — balance removed from `Victim`.
   - `AddBalance(attackerAddress, 100)` — balance credited to attacker.
   - `SelfDestruct6780(Victim)` — `stateObject.created == false`, so no-op; `Victim` persists.
5. Assert: `Victim` balance = 0, `attackerAddress` balance = +100 KAIA, `Victim` code still exists in state.

Per EIP-6780, step 4 should have been a complete no-op. The bug causes the balance transfer to execute regardless.
