### Title
Cross-repository `status` webhook confusion lets a Status be forged on another stack's commit, forcing `Deploy#ignored_safeties` to `false` for an unvetted deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits purely by `sha`, with no check that the webhook's `repository`/`organization` matches the `stack` that owns the matched `Commit` row. An attacker who owns any repository with the Shipit GitHub App installed (explicitly an in-scope capability) can emit a genuinely signed `status` webhook whose `sha` happens to match a commit that also exists in a victim stack (trivial via forking, since git commit hashes are content-addressed and identical across forks). This creates a real `Status` row on the victim's `Commit`, flips `Commit#deployable?` to `true` without any CI ever running against the victim repo, and that forged signal flows straight into `Stack#build_deploy`'s `ignored_safeties: force || !until_commit.deployable?`.

### Finding Description
Binding claimed to hold: `Deploy#ignored_safeties == true` whenever the `deployable?` signal did not originate from a webhook verified for that deploy's own repository. That binding is broken because the `status` handler never checks repository identity against the commit it mutates: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit.where(sha: params.sha)` is a global, cross-stack query - it is not scoped to `stack_id` or to the `repository.full_name`/`organization.login` carried in the same payload. `verify_signature` in `WebhooksController` only confirms the request is a genuine GitHub delivery *for the organization named in the attacker's own payload* - it says nothing about whether that organization is allowed to affect commits belonging to a different stack/repository: [2](#0-1) 

Downstream, `create_status_from_github!` → `add_status` writes the status using the **matched commit's own `stack_id`** (the victim's stack), not the attacker's: [3](#0-2) [4](#0-3) 

That status then makes `Commit#deployable?` true for the victim commit: [5](#0-4) 

which is consumed unchanged by `Stack#build_deploy`: [6](#0-5) 

Exploit flow:
1. Attacker forks the victim's public repository (or any repo whose recent commit history overlaps with the victim stack's tracked branch) and installs/keeps the Shipit GitHub App on that fork - an explicitly allowed unprivileged capability ("emit webhooks from a repository they own").
2. Attacker sets a real commit status (`success`) on their own fork for a SHA that is shared history with the victim's tracked branch - since git SHAs are content-addressed, an untouched ancestor commit has the identical SHA in both repos.
3. GitHub delivers a genuinely signed `status` webhook to Shipit's `/webhooks` endpoint, with `repository.full_name` = attacker's fork, `sha` = the shared commit SHA. `verify_signature` passes because the delivery is real and legitimately signed for the attacker's own installation/org.
4. `StatusHandler#process` looks up `Commit.where(sha: ...)` and finds the identical-sha `Commit` row that belongs to the **victim's stack**, creating a `success` `Status` there.
5. `Commit#deployable?` becomes `true` for the victim commit despite zero CI activity against the victim's actual repository.
6. Any subsequent `Stack#trigger_deploy`/`build_deploy` on that commit computes `ignored_safeties: force || !until_commit.deployable?` = `false`, mischaracterizing the deploy as CI-approved, and `stack.schedule_merges`/continuous-delivery logic (`add_status`, `UndeployedCommit#deploy_state`) may also treat the commit as eligible for automatic deployment.

None of the existing guards catch this: `verify_signature` validates delivery authenticity for *an* organization, not that the organization matches the commit's owning stack; there is no `ExplicitParameters` repository-match check in `StatusHandler`; `drop_unhandled_event` and `check_if_ping` are irrelevant; model validations on `Repository`/`Stack` do not constrain cross-stack `sha` collisions.

### Impact Explanation
A record (a `Status`, and transitively a `Deploy.ignored_safeties=false`) is written for a repository/stack that never authenticated that status - satisfying the Critical impact category of "a payload for one repository mutating another's stack, commit, task or team" and directly enabling an unauthorized/CI-gated deploy or continuous-delivery merge on the victim stack. The attack is repeatable against any stack whose tracked commit history overlaps with a repository the attacker controls (trivially achievable via forking of public repos), and is not limited to a single victim - any stack sharing SHAs with attacker-controlled repos is exposed.

### Likelihood Explanation
Preconditions: the attacker needs a repository they control (fork is sufficient) with the Shipit GitHub App installed so they can produce a genuinely signed `status` webhook - explicitly listed as an available attacker capability. Getting a shared SHA with the victim stack requires no special access - it is a natural consequence of git's content-addressed commit hashing when forking a public repository. No secrets, tokens, or privileged roles are required. Feasibility is high and the technique is repeatable per-commit/per-stack.

### Recommendation
In `StatusHandler#process` (and analogously anywhere `Commit.where(sha:)` or similar global-sha lookups are used to apply GitHub webhook data), scope the lookup to commits whose `stack.repository` (or `repo_name`/`github_repo_name`) matches `params.dig('repository', 'full_name')` from the webhook payload before calling `create_status_from_github!`. Reject or skip commits belonging to stacks whose repository does not match the webhook's originating repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from a different repository cannot mark a foreign stack's commit deployable" do
  victim_stack = shipit_stacks(:shipit)          # repo: "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse)      # repo: "attacker/fork", owned/controlled by attacker

  shared_sha = "abc123def456"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  refute_predicate victim_commit, :deployable?

  # No real CI provider is ever contacted for the victim repo
  Shipit::GithubApp.any_instance.expects(:statuses).never

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker-fork',
    'repository' => { 'full_name' => attacker_stack.repository.full_name, 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).call

  victim_commit.reload
  assert_predicate victim_commit, :deployable?   # <-- forged true, proving the cross-repo confusion

  deploy = victim_stack.trigger_deploy(victim_commit, Shipit::AnonymousUser.new)
  assert_equal false, deploy.ignored_safeties     # <-- mischaracterized as CI-approved
end
```
This demonstrates the binding violation: `deployable?` became `true`, and `Deploy#ignored_safeties` became `false`, purely from a webhook authenticated for a different repository, with no CI provider ever contacted for the victim stack.
