### Title
`GasTarget` Governance Parameter Accepts Zero, Causing Division-by-Zero Panic in `NextMagmaBlockBaseFee` — (`params/kip71_config.go`)

### Summary

The `kip71.gastarget` governance parameter has no lower-bound format check, allowing it to be voted to `0`. Once ratified, every subsequent call to `NextMagmaBlockBaseFee` with any non-zero `parentGasUsed` performs an integer division by zero (`big.Int.Div(x, 0)`), which panics in Go and crashes the node. This is called during block header verification (`VerifyMagmaHeader`), tx-pool reset, and the gas-price oracle, halting consensus on all honest nodes that apply the governance update.

### Finding Description

`Kip71BaseFeeDenominator` has an explicit non-zero format check in its `Param` definition:

```go
Kip71BaseFeeDenominator: {
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0          // zero explicitly rejected
    },
    ...
}
```

`Kip71GasTarget` uses `noopFormatChecker`, which accepts every value including `0`:

```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: noopFormatChecker,   // no zero guard
    DefaultValue:  uint64(30000000),
}
```

`checkConsistency` in `VerifyVote` also performs no additional check for `Kip71GasTarget`; it falls through to `return nil`.

After a governance vote for `kip71.gastarget = 0` is ratified, `NextMagmaBlockBaseFee` reads `gasTarget = 0`. When `parentGasUsed > 0` (any block containing transactions), the code takes the `parentGasUsed > gasTarget` branch and executes:

```go
// line 102
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // gasTarget == 0 → panic
```

Go's `(*big.Int).Div` panics on a zero divisor. The same panic occurs on the decrease path at line 120.

`NextMagmaBlockBaseFee` is called from:
- `VerifyMagmaHeader` — block header validation during consensus
- `TxPool.reset` — after every new head block
- `Oracle.isRelaxedNetwork` — gas-price oracle

### Impact Explanation

Every honest node that has applied the governance update will panic and crash the moment it processes a block with non-zero gas used. This causes a complete chain halt and consensus divergence. The corrupted governance state persists across restarts because the ratified parameter is stored in the header governance log; nodes will continue to panic on every non-empty block until the parameter is corrected by another governance vote (which itself requires a functioning chain).

### Likelihood Explanation

In `none` governance mode any GC member can cast the decisive vote. In `single` mode the governing node alone can trigger it. The `FormatChecker` inconsistency (denominator is guarded, gas target is not) makes this a latent code-level defect that any authorized voter can exploit, intentionally or by misconfiguration. The default value is `30_000_000`, so the defect is dormant until a vote changes it.

### Recommendation

Add a non-zero lower-bound check to `Kip71GasTarget`'s `FormatChecker`, mirroring the guard already present for `Kip71BaseFeeDenominator`:

```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v > 0   // reject zero to prevent division-by-zero
    },
    ...
}
```

Additionally, add a defensive zero-check inside `NextMagmaBlockBaseFee` itself before using `gasTarget` as a divisor, so that even a misconfigured genesis cannot panic the node.

### Proof of Concept

1. In `none` governance mode, any GC member casts a vote: `governance_vote("kip71.gastarget", 0)`.
2. The vote passes `NewVoteData` (canonicalized to `uint64(0)`, `noopFormatChecker` returns `true`).
3. `VerifyVote` → `checkConsistency` → falls through to `return nil` (no check for `Kip71GasTarget`).
4. At the next epoch block the vote is ratified; `GetParamSet` now returns `GasTarget = 0`.
5. The next block that includes any transaction has `parentGasUsed > 0`.
6. `VerifyMagmaHeader` calls `NextMagmaBlockBaseFee`; `parentGasUsed > gasTarget` (any positive > 0), entering the increase branch.
7. Line 102: `x.Div(x, new(big.Int).SetUint64(0))` → **panic: division by zero** → node crash.
