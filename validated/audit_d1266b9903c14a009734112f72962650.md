### Title
Unvalidated Staking Info Accepted from Malicious Peers During Fast Sync Corrupts Reward Distribution and Validator Set — (`datasync/downloader/queue.go`)

---

### Summary

During fast sync, staking info received from any connected peer is accepted and persisted to the database without any cryptographic validation against the block's state root. A malicious peer can inject arbitrary staking info (false node IDs, reward addresses, staking amounts) that permanently corrupts the on-chain oracle used for KAIA reward distribution and validator set selection for all pre-Kaia-hardfork blocks.

---

### Finding Description

The external report describes an oracle manipulation pattern: a publicly callable function updates a protected state value once per epoch, and once set, the value cannot be corrected for the remainder of that period. The Kaia analog is the staking info database, which acts as the "oracle" for validator weights and reward distribution. During fast sync, this oracle is populated from peer-supplied data with no validation.

In `datasync/downloader/queue.go`, `DeliverStakingInfos` contains an explicit no-op validation function:

```go
// File: datasync/downloader/queue.go, lines 956-958
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
```

Compare this to `DeliverReceipts`, which validates each receipt against the header's `ReceiptHash`:

```go
// File: datasync/downloader/queue.go, lines 936-940
validate := func(index int, header *types.Header) error {
    if types.DeriveReceiptsRoot(types.Receipts(receiptList[index]), header.Number) != header.ReceiptHash {
        return errInvalidReceipt
    }
    return nil
}
```

No equivalent check exists for staking info. The peer-supplied `P2PStakingInfo` struct (containing `NodeIds`, `StakingContracts`, `RewardAddrs`, `StakingAmounts`) is accepted verbatim and written to the database in `commitFastSyncData`:

```go
// File: datasync/downloader/downloader.go, lines 1881-1884
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
    logger.Info("Imported new staking information", "number", result.StakingInfo.BlockNum)
}
```

`PutStakingInfoToDB` writes directly to the key-value store with no further checks:

```go
// File: kaiax/staking/impl/schema.go, lines 73-74
func (s *StakingModule) PutStakingInfoToDB(sourceNum uint64, stakingInfo *staking.StakingInfo) {
    WriteStakingInfo(s.ChainKv, sourceNum, stakingInfo)
}
```

Once written, `GetStakingInfo` reads from the database before falling back to state derivation for pre-Kaia blocks:

```go
// File: kaiax/staking/impl/getter.go, lines 57-63
if !isKaia {
    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
        s.stakingInfoCache.Add(sourceNum, si)
        return si, nil
    }
}
```

This means the corrupted DB entry permanently shadows the correct state-derived value. The staking info is the sole input to reward distribution and validator set selection for all pre-Kaia-hardfork blocks.

Additionally, the `BlockNum` field in the peer-supplied staking info is used as the DB key without verifying it matches the requested block's number, allowing a malicious peer to overwrite staking info for arbitrary block numbers.

---

### Impact Explanation

A malicious peer can inject staking info with:
- **False `RewardAddrs`**: KAIA block rewards are redirected to attacker-controlled addresses for the entire staking interval (up to `StakingUpdateInterval` blocks, defaulting to 86,400 blocks on mainnet).
- **Inflated `StakingAmounts`**: Specific validators receive disproportionate reward shares.
- **False `NodeIds`**: The qualified validator set is corrupted, affecting proposer selection and committee composition.

The corrupted value is the `StakingInfo` struct persisted at `"stakingInfo" || Uint64LE(sourceNum)` in the chain key-value store. Since `GetStakingInfo` reads the DB before state, the corruption is permanent until the DB entry is manually deleted or overwritten.

---

### Likelihood Explanation

Any node that establishes a P2P connection with a syncing node can serve staking info responses. In a permissionless network, this is reachable by any participant. The attack requires only that the victim node is performing fast sync (a common bootstrap scenario) and that the attacker is a connected peer. No privileged access, key compromise, or validator collusion is required.

---

### Recommendation

Implement state-root-based validation for staking info received during fast sync, analogous to receipt validation. After receiving staking info for block `N`, re-derive the staking info from the block's state root and compare it against the peer-supplied data before persisting:

```go
validate := func(index int, header *types.Header) error {
    received := stakingInfoList[index]
    // Re-derive from state and compare
    derived, err := stakingModule.getFromStateByNumber(header.Number.Uint64())
    if err != nil {
        return err
    }
    if !stakingInfoEqual(derived, staking.ToStakingInfo(received)) {
        return errInvalidStakingInfo
    }
    return nil
}
```

Remove the `// TODO-Kaia-Snapsync update validation logic` placeholder and replace it with this check. Additionally, verify that `received.BlockNum` matches the header's block number before writing to the database.

---

### Proof of Concept

1. Attacker runs a Kaia node and connects to a victim node that is performing fast sync.
2. Victim node requests staking info for block `N` (a staking interval boundary).
3. Attacker's node responds to the `StakingInfoRequestMsg` with a crafted `P2PStakingInfo` where `RewardAddrs` are replaced with attacker-controlled addresses and `StakingAmounts` are inflated for attacker-controlled validators.
4. `handleStakingInfoMsg` in `node/cn/handler.go` decodes the message and calls `pm.downloader.DeliverStakingInfos`.
5. `DeliverStakingInfos` in `queue.go` calls `validate` (which returns `nil`) and then `reconstruct`, storing the malicious staking info in `result.StakingInfo`.
6. `commitFastSyncData` calls `PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))`, persisting the malicious data.
7. All subsequent calls to `GetStakingInfo` for blocks in the affected staking interval read the corrupted DB entry, directing KAIA rewards to attacker-controlled addresses for the entire interval.

// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
