### Title
Webhook `X-Hub-Signature` verification keys off attacker-controlled `repository.owner.login`, while event handlers act on the independently attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a payload against using `repository_owner`, a value read directly from the unauthenticated JSON body. The signature only proves the request was signed by *that* organization's secret. Downstream, `Shipit::Webhooks::Handlers::Handler#repository_name` (and thus `PushHandler#process`, which triggers `stack.sync_github`) resolves the target repository/stack using a *different* field from the same untrusted body: `repository.full_name`. Nothing binds `repository.owner.login` (the identity that was cryptographically verified) to `repository.full_name` (the identity that is actually acted upon). This is structurally the same class of bug as the Shelter `claimed[_to]` vs `msg.sender` mismatch: the field that is checked/authenticated is not the field that is subsequently used to perform the privileged action.

### Finding Description
- `verify_signature` in [1](#0-0)  computes `repository_owner` via `params.dig('repository', 'owner', 'login')` and uses it to fetch the corresponding `Shipit.github(organization: repository_owner)` app config, then verifies `X-Hub-Signature` against that org's `webhook_secret`.
- `repository_owner` is derived purely from attacker-supplied JSON in the same request whose signature is being checked: [2](#0-1) .
- Once the signature check passes, `WebhooksController#create` dispatches the *entire* raw parsed body to the registered handler for the event: [3](#0-2) .
- `Handler#repository_name` reads a *separate* field, `payload.dig('repository', 'full_name')`, to look up the `Repository`/`Stack` that will be mutated: [4](#0-3) .
- `PushHandler#process` uses that repository/stack resolution to call `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack: [5](#0-4) .
- Shipit explicitly supports multiple, independently configured GitHub Apps/organizations sharing one Shipit instance, each with its own `webhook_secret`, all posting to the same `/webhooks` endpoint (documented in "Using Multiple Github Applications"): [6](#0-5) .

**Binding that should hold, but doesn't:** `organization verified by signature == owner(repository written by handler)`. Before the exploit, both sides are supposed to be the same GitHub organization for any legitimate GitHub-originated webhook. After the attack, an operator who legitimately controls a webhook-secret-bearing installation for `OrgA` can craft a raw JSON body where `repository.owner.login = "OrgA"` (so the signature check passes using `OrgA`'s real secret) but `repository.full_name = "OrgB/victim-repo"` (so the handler acts on `OrgB`'s stack). The two sides of the equality diverge because nothing re-validates that `full_name`'s owner segment matches `owner.login`, or that the org resolved for signature verification is the org that actually owns the acted-upon repository.

### Impact Explanation
Exploiting this lets an attacker who legitimately administers one GitHub App/organization onboarded into a shared Shipit instance forge push (and potentially other) events attributed to a different, unrelated organization/repository also configured on that instance. Because `PushHandler` calls `stack.sync_github(expected_head_sha: ...)`, which enqueues `GithubSyncJob` to fetch and append "new" commits reachable from an attacker-influenced SHA and can drive continuous-deployment/merge-queue behavior for the victim's stack, this crosses a cross-repository trust boundary using only credentials belonging to a different tenant. This matches the "cross-repository writes" / "unauthorized deploy" high-impact bucket, since a stack belonging to `OrgB` can be caused to sync and potentially auto-deploy based on data the attacker fully controls, despite the attacker never having any legitimate credential, webhook secret, or repository access for `OrgB`.

### Likelihood Explanation
This requires the specific multi-organization deployment configuration (several GitHub Apps sharing a single Shipit instance/`webhooks` endpoint), which is a documented, first-class configuration Shipit supports. Any tenant with a legitimately configured/self-installed GitHub App and its own valid `webhook_secret` can carry out the attack by simply crafting a raw JSON body and computing the HMAC themselves — no compromise of the victim's org, no access to the victim's secret, and no privileged Shipit account is required, only participation as one of the (mutually distrusting) tenants on the shared instance.

### Recommendation
After resolving `repository_owner` for signature verification, re-derive the acted-upon repository's owner strictly from the verified organization context (or explicitly assert `repository.full_name.split('/').first == repository_owner`, `organization.login == repository_owner`, etc.) before dispatching to handlers, rather than letting `Handler#repository_name` independently trust `repository.full_name` from the same unauthenticated payload. In a single-tenant deployment this is moot, but the multi-org codepath needs the binding enforced explicitly.

### Proof of Concept
1. Instance operator configures two GitHub organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret`, per the documented multi-org setup: [6](#0-5) .
2. Attacker is a legitimate admin of `OrgA`'s GitHub App only, and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a raw JSON push payload:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
   - `ref = "refs/heads/main"`, `after = "<attacker-chosen sha>"`
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, loads `OrgA`'s app, and the HMAC check succeeds (attacker used the correct secret for `OrgA`): [7](#0-6) .
6. `create` dispatches to `PushHandler.call(params)`; `Handler#repository_name` resolves `"OrgB/victim-repo"`, finds `OrgB`'s real `Stack`, and `PushHandler#process` invokes `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for `OrgB`'s stack: [4](#0-3) [5](#0-4) .
7. `GithubSyncJob` runs for `OrgB`'s stack using `OrgB`'s own configured GitHub App credentials, potentially appending commits/triggering deploy pipelines for a repository the attacker never had signature/credential access to.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
