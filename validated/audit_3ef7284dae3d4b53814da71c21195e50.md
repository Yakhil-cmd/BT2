## Finding [1](#0-0) [2](#0-1) 

### Title
Cross-organization/cross-repository commit-status forgery due to unbound signature-verification identity - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `Rewards`-contract bug class is "a security check exists in some places but the thing it's supposed to protect is never actually bound to it." The analogous defect in `shipit-engine` is in the webhook trust chain: `WebhooksController#verify_signature` selects **which** GitHub App/organization secret to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, then — once *any* signature matches for *that* organization — hands the *entire same body* to handlers that independently decide *which repository/commit to mutate*. `StatusHandler` in particular never re-checks the repository at all: it resolves the target purely via `Commit.where(sha: params.sha)`, globally, across every stack/organization tracked by the instance.

### Finding Description
`WebhooksController#verify_signature` picks the signing organization from the payload itself: [3](#0-2) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

It then verifies the raw body against that organization's configured `webhook_secret`: [4](#0-3) 

Once this passes, `create` dispatches the same raw JSON to all registered handlers for the event, with no re-derivation of "which org validated this": [5](#0-4) 

The equality the code implicitly (and incorrectly) assumes is:

`organization whose secret validated the signature == organization that owns the repository/commit the handler will write to`

Nothing enforces that equality. `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` re-reads `repository.full_name` from the same untrusted body to scope most handlers to "that" repo [6](#0-5) , but `StatusHandler` doesn't even use that scoping — it looks up commits **globally**: [7](#0-6) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`create_status_from_github!` → `Status.replicate_from_github!` creates a `Status` scoped only to `commit.stack_id`, derived from whatever commit matched the SHA, not from any organization/repository the signature actually covers: [8](#0-7) [9](#0-8) 

In a multi-organization deployment (`docs/setup.md` "Using Multiple Github Applications"), each configured GitHub App has its own, independently-obtainable `webhook_secret` (marked *optional* in setup docs, and `GitHubApp#verify_webhook_signature` explicitly returns `true` when no secret is configured): [10](#0-9) 

An attacker who can get a legitimately-signed webhook accepted for *any one* onboarded organization (their own org's app, or an org configured with a blank `webhook_secret`) supplies:
- `repository.owner.login` = that organization (used only to select the secret for verification),
- `sha` = the known SHA of a commit belonging to a *different* tracked stack/repository/organization.

`StatusHandler` will locate that unrelated commit purely by SHA and write an attacker-controlled `state`/`context`/`target_url`/`description` `Status` onto it — a write into a stack the attacker's verified organization never owned.

### Impact Explanation
`Status` creation feeds directly into CI gating used by the merge queue and deploy readiness checks (`ci.require`, `merge.require`), and `add_status`/`create_status_from_github!` schedules `ProcessMergeRequestsJob` on success/pending transitions. Forging a `success` status onto an arbitrary tracked commit in a repository/organization the attacker does not control can clear CI requirements and enable an **unauthorized merge**, and pollutes commit history/status shown to operators deciding to deploy. This satisfies the report's "Critical" bar (cross-repository writes / unauthorized merge) because the write crosses the organizational boundary that the signature check was supposed to establish.

### Likelihood Explanation
Exploitation requires only (a) control of, or the ability to trigger, one legitimately signed `status` webhook from any organization onboarded to the same Shipit instance (including one with no `webhook_secret` set, an explicitly supported/optional configuration), and (b) knowledge of the target commit's SHA (public on GitHub for public repos, or knowable to any collaborator). No Shipit session, `ApiClient` token, or the target organization's secret is needed, matching the "unprivileged attacker" threat model.

### Recommendation
Bind the verified identity to the resource being mutated: after `verify_signature` resolves the authenticating organization, pass that organization explicitly into the handler pipeline and require every handler (especially `StatusHandler`) to scope its lookups (`Commit`, `Repository`, `Stack`) to repositories that belong to the verified organization, rejecting/ignoring any payload whose `repository.full_name` owner does not match the organization whose secret validated the signature. Additionally, treat a `nil`/blank `webhook_secret` as a hard misconfiguration to warn/refuse on, rather than silently accepting any signature.

### Proof of Concept
1. Shipit instance configured with two organizations, `attacker-org` (attacker controls its GitHub App/webhook secret) and `victim-org` (unrelated, tracked stack with a known commit `abcd123...`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature` computed with `attacker-org`'s webhook secret, and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" } },
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com"
}
```
3. `verify_signature` resolves `repository_owner` = `attacker-org`, validates against `attacker-org`'s secret → passes.
4. `StatusHandler#process` runs `Commit.where(sha: "<victim-org commit sha>")`, finds the victim's commit (unrelated stack), and creates a forged `success` `Status` on it, potentially clearing CI requirements for `victim-org`'s merge queue/deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
