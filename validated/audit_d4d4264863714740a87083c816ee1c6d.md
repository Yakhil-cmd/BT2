### Title
Cross-repository commit-SHA collision in status webhook forges CI results and bypasses `require_ci` deploy gate - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to update purely by `sha` with no scoping to the repository that sent the webhook, and `sha` is not globally unique — it is only unique per `(sha, stack_id)`. A legitimately signed `status` webhook from a repository the attacker owns can therefore flip `state` (and thus `Commit#deployable?`) on an unrelated stack's commit that happens to share the same SHA, defeating the `Api::DeploysController#create` `require_ci` gate.

### Finding Description
The broken binding: `commit.deployable?` is claimed to equal "the commit's own repository actually reported CI success," but the actual code enforces only `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` [1](#0-0) , i.e. it is scoped to `sha` alone, not to `(sha, repository)`. The `commits` table enforces uniqueness only on `(sha, stack_id)`, not on `sha` alone [2](#0-1) , meaning distinct stacks/repositories can legitimately hold `Commit` rows with identical `sha` values (this is exactly what the index is designed to allow).

Webhook authenticity is verified only against the organization derived from the payload's own `repository.owner.login`/`organization.login`, via `Shipit.github(organization: repository_owner)` and `verify_webhook_signature` [3](#0-2) . This proves the webhook came from GitHub for *that* organization/app installation — it says nothing about which stack/commit should be updated. `Handler#stacks` (used by other handlers) does scope lookups by `repository_name` from the payload [4](#0-3) , but `StatusHandler#process` does not use `stacks` at all — it queries `Commit` globally by `sha`.

Exploit flow: an attacker who owns any repository (and can install the Shipit GitHub App on it, a self-service action requiring no Shipit privilege) can obtain a commit with an identical SHA to a victim's tracked commit — git commit SHAs are content hashes, and a byte-identical commit (same tree, parents, author, committer, timestamps, message) pushed into the attacker's own repository will have the same SHA as the original in the victim repository. The attacker then triggers (or has GitHub emit) a `status` event with `state: success` on that SHA from their own repository. `verify_signature` passes because the signature is validated against the attacker's own organization, which is legitimate. `StatusHandler#process` then finds and updates **every** `Commit` row across the entire installation matching that `sha`, including the victim stack's commit, via `commit.create_status_from_github!(params)` → `add_status` → sets `success` status [5](#0-4) [6](#0-5) .

Once the victim's `Commit#status` reports `success`, `Commit#deployable?` becomes true (assuming not locked/blocked) [7](#0-6) . This directly defeats `Api::DeploysController#create`'s CI gate: `param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?` [8](#0-7) . It also affects continuous delivery, which relies on `deployable?` via `next_commit_to_deploy`/`deployable_commits` [9](#0-8) , and merge queue processing (`stack.schedule_merges` is triggered on the forged transition) [10](#0-9) .

None of the existing guards prevent this: `verify_signature` only proves the webhook is genuinely from the org named in its own payload, not that the org is authorized to speak for a *different* stack's commit; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate the shape of the payload, not repository ownership; there is no `require_permission!`/`stacks` scoping call inside `StatusHandler#process`.

### Impact Explanation
An attacker controlling any GitHub repository can, without any Shipit credentials, corrupt the CI/deployability state of a commit belonging to a completely unrelated stack/repository that happens to share the SHA (achievable deterministically by copying the exact commit object). This bypasses the `require_ci` deploy-gate on `Api::DeploysController#create`, enabling an unauthorized deploy of an unverified commit, and can also trigger continuous-delivery deploys and merge-queue progression for that stack. This is a payload for one repository mutating another's commit/stack, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository they control, (b) the ability to have GitHub sign and deliver a `status` webhook for that repo to the Shipit host (either by installing the Shipit GitHub App on their own repo/org if the app is publicly installable, or by any mechanism that causes GitHub to emit a signed `status` event for their org), and (c) a commit whose SHA collides with a targeted victim commit, achievable deterministically by duplicating the exact git commit object (same tree/parents/author/committer/timestamps) into their own repo. No Shipit session, API token, or secret is required. Whether the Shipit GitHub App used by the target deployment is installable by arbitrary third parties (self-service) determines feasibility precisely, and this could not be fully confirmed from the code alone (`Shipit.github(organization:)` / `GithubOrganizationUnknown` in `lib/shipit/github_app.rb` and `lib/shipit.rb` govern this, but the exact installation model wasn't verified in this pass).

### Recommendation
Scope `StatusHandler#process` (and analogously `check_run`/other webhook handlers touching `Commit`) to the repository named in the webhook payload, mirroring `Handler#stacks`. Concretely: replace `Commit.where(sha: params.sha)` with a lookup restricted to `stacks` (i.e., commits whose `stack_id` is in `stacks.pluck(:id)` for `Repository.from_github_repo_name(repository_name)`), so a status event can only mutate commits belonging to the repository that authenticated it.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, in-scope model/handler test, no live GitHub):
1. Create two stacks/repositories, `victim/repo` and `attacker/repo`, each with a `Commit` row sharing the same `sha` value (e.g. `"deadbeef" * 5`), both initially with unknown/no status.
2. Assert `victim_commit.deployable?` is `false` (binding LHS: victim repo's own CI never reported success).
3. Build a `StatusHandler` payload whose `repository.full_name == "attacker/repo"`, `sha` equal to the shared SHA, `state: "success"`, and call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert `attacker_commit.reload.deployable?` is `true` (expected, same-repo success).
5. Assert `victim_commit.reload.deployable?` is now also `true` — demonstrating the equality `commit.deployable? == "victim repo reported success"` is broken, since only the attacker's repo emitted a success status.
6. Extend to controller-level PoC: POST to `/api/stacks/:victim_stack_id/deploys` with `require_ci: true` before step 3 (expect `422`/`unprocessable_entity` with `errors.require_ci`), then after step 3/4 (expect `202 accepted`), proving the `require_ci` gate at `app/controllers/shipit/api/deploys_controller.rb:22` is bypassed by a same-SHA webhook from an unrelated repository.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
