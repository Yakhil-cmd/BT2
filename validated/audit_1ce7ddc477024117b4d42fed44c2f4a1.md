### Title
Cross-organization webhook forgery via decoupled signature-selection field and repository-resolution field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the HMAC against using `repository.owner.login` (or `organization.login`), while the actual write target (which `Stack`/`Repository` gets synced, statused, or has commits/check-runs mutated) is resolved from a completely different field, `repository.full_name`, in `Webhooks::Handlers::Handler#repository_name`. Nothing enforces that these two fields agree.

### Finding Description
`WebhooksController#repository_owner` is used only to choose the `Shipit.github(organization:)` config for signature verification: [1](#0-0) [2](#0-1) 

Once `verify_signature` passes, `WebhooksController#create` forwards the parsed JSON body unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`, an entirely different JSON path than the one used for signature-organization selection: [4](#0-3) 

Because Shipit supports multiple independent GitHub App configs keyed by organization (as shown in `test/dummy/config/secrets_double_github_app.yml`), a party who legitimately owns/administers one org's GitHub App on a shared, multi-tenant Shipit instance knows that org's `webhook_secret`. They can craft a payload where `repository.owner.login`/`organization.login` = their own org (so `verify_signature` selects and validates against their own known secret), but `repository.full_name` = a target repository belonging to a *different* organization hosted on the same Shipit instance. The signature check passes because it only verifies the raw body against the secret picked from the attacker-controlled `repository_owner` field — it does not verify that the org used for secret selection matches the org actually embedded in `repository.full_name`.

This breaks the intended binding: `organization that authenticated == repository that is written`. The equality is violated because the code enforces `secret_for(repository_owner) verifies raw_body`, but `repository_owner != full_name.split('/').first` is never checked.

### Impact Explanation
Depending on the event type, this allows an attacker who controls a different tenant's webhook secret to:
- Trigger `GithubSyncJob` on a foreign stack (`PushHandler#process` → `stack.sync_github`) [5](#0-4) 
- Forge CI status on foreign commits (`StatusHandler#process` → `commit.create_status_from_github!`), which can unlock `ignore_ci`/deployability gating and enable an unauthorized deploy on that foreign stack [6](#0-5) 
- Trigger check-run refresh cycles on foreign commits (`CheckSuiteHandler#process`) [7](#0-6) 

Forged CI/status events feeding into deploy-gating logic can lead to an unauthorized deploy on a repository/stack the attacker does not control — this matches the Critical-severity "unauthorized deploy" impact bucket in scope.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (documented/supported configuration, per `secrets_double_github_app.yml`), and requires the attacker to control a GitHub App/webhook secret for at least one organization configured on that shared instance — not a Shipit session, `ApiClient` token, or the target org's own secret. This is plausible in shared/hosted Shipit setups serving multiple tenants, matching the "organization that authenticated versus the repository that is written" scenario called out as in-scope.

### Recommendation
In `WebhooksController`/`Handler`, after selecting the app config via `repository_owner`, verify that `repository.full_name`'s owner segment matches the same `repository_owner`/`organization.login` used to select the verification secret, and reject the webhook otherwise. Alternatively, resolve the `Repository`/`Stack` strictly by an owner value that was itself authenticated by the verified secret, not by an independent, unauthenticated field in the same payload.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps for `OrgA` and `OrgB` (as in `test/dummy/config/secrets_double_github_app.yml`), each with a stack, e.g., `OrgA/target-repo` and `OrgB/attacker-repo`.
2. Attacker legitimately controls the GitHub App for `OrgB` and knows its `webhook_secret`.
3. Attacker crafts a `status` (or `push`) event payload:
```json
{
  "sha": "<commit sha of OrgA/target-repo>",
  "state": "success",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgB`'s known `webhook_secret` over the raw body and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#repository_owner` resolves to `OrgB`, `verify_signature` succeeds using `OrgB`'s secret.
6. `StatusHandler#process` resolves stacks via `repository.full_name` = `OrgA/target-repo`, applying the forged status to `OrgA`'s commit despite the attacker never having controlled `OrgA`'s GitHub App.
