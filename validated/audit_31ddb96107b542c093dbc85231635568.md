### Title
Webhook signature verification uses `repository.owner.login` while all event handlers act on `repository.full_name` from the same unverified payload, allowing cross-organization forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` against using `repository_owner`, derived from the still-unverified JSON body: `params.dig('repository', 'owner', 'login')`. All webhook handlers, however, resolve the actual `Repository`/`Stack` to act on using a different field from the very same unverified body: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name` (and equivalently in the `pull_request` sub-handlers). Nothing enforces that `full_name.split('/').first == owner.login`, so these two independently-controlled fields inside one attacker-supplied JSON blob can point to two different organizations.

The `verify_webhook_signature` check only compares an HMAC over the raw body against the secret for the organization chosen this way: [3](#0-2) 

Once the signature check passes (because it validates against Organization A's secret, matched via `repository.owner.login = "OrgA"`), the parsed body is dispatched to handlers unchanged: [4](#0-3) 

Every handler then determines the actual repository/stack to operate on from a *different* field of the same payload: [5](#0-4) 

For example, `PushHandler` triggers a GitHub sync job for whichever stacks belong to the repository resolved from `full_name`: [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` with no cross-check against `owner.login`: [7](#0-6) 

The equality that should hold but does not: `organization authenticated (via signature, keyed by repository.owner.login) == organization whose repository is written (resolved via repository.full_name)`. Since a Shipit deployment can be configured with multiple GitHub Apps/organizations, each with its own `webhook_secret` (as documented in `config/secrets.development.example.yml`), knowledge of *one* organization's webhook secret (e.g. because the attacker's own org is configured on the same Shipit instance) is sufficient to forge a payload whose `repository.owner.login` matches that known-secret organization while `repository.full_name` names a *different* organization's repository/stack.

### Impact Explanation
An attacker who knows (or controls) the webhook secret for one configured GitHub organization on a multi-org Shipit instance can sign an arbitrary JSON body with `repository.owner.login` set to their own organization but `repository.full_name` set to `"victim-org/victim-repo"`. This body will pass `verify_signature` (signed with the attacker's own known secret and validated against that org) yet will be routed by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `pull_request/*` handlers to the victim organization's `Repository`/`Stack`/`PullRequest` records. Concretely this can be used to:
- Trigger `stack.sync_github(expected_head_sha:)` / `GithubSyncJob` against a victim stack, forcing Shipit to treat an attacker-chosen SHA as the head of a branch it doesn't control.
- Forge `status` events to mark victim commits as CI-passing/failing, which feeds `required_statuses`/`blocking_statuses` used to gate deploy eligibility, potentially enabling an unauthorized deploy.
- Archive/unarchive review stacks or mutate `PullRequest` state on repositories the attacker has no access to, via the `pull_request/*` handlers which resolve `repository` from `full_name` alone.

This crosses the repository-write / cross-organization boundary explicitly listed as Critical impact ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Exploitation requires the attacker to possess a valid webhook secret for *some* organization configured on the target Shipit instance — realistic for any Shipit deployment serving multiple GitHub organizations (explicitly supported per `config/secrets.development.example.yml`'s multi-org schema), where an attacker with legitimate GitHub App admin/webhook access to their own low-trust org can forge cross-org events. No repository write access, Shipit session, or `ApiClient` token is required — only a crafted HTTP POST to `/webhooks` signed with a known, unrelated org's secret.

### Recommendation
Cross-validate that the organization used to select/verify the signature is identical to the organization embedded in `repository.full_name` (and any other repository/org identifiers used by handlers) before dispatching the event; reject the webhook if they diverge. Alternatively, resolve the target `Repository`/`Stack` using the same verified `repository.owner.login` that gated signature verification, rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (attacker knows `webhook_secret_A`) and `victim-org` (a separate stack/repo the attacker has no access to).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(webhook_secret_A, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully against `webhook_secret_A`.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` (from `repository.full_name`) and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stacks — despite the request never being signed with `victim-org`'s secret.

Note: I was unable to execute this end-to-end in a live environment; the analysis is based on static code tracing of `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`, and `app/models/shipit/repository.rb`, confirming the two divergent unverified fields (`repository.owner.login` vs `repository.full_name`) used respectively for signature-org selection and target-repository resolution.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
