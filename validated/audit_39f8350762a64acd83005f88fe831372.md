### Title
`git commit` review can be redirected to review a stale/unrelated commit instead of the real one via a bracketed decoy line appended to the compound Bash command - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`handle_commit_review_posttooluse` selects the SHA to review by taking the **last** `[branch sha]`-shaped match found anywhere in the combined stdout/stderr of the whole (possibly chained) Bash command, relying on the unstated assumption that git's own commit line is always the last such bracketed token. An attacker who controls the shell command (already approved as `Bash(git commit:*)`) can append a benign subcommand after `git commit` that prints a decoy `[branch sha]` token referencing a real, pre-existing commit SHA, causing the hook to review that old commit instead of the newly created one.

### Finding Description
The success gate requires only two independent signals present *anywhere* in the combined buffer, with no positional relationship to each other: [1](#0-0) 

The diffstat patterns (`N files? changed`, `create mode`, etc.) are produced by the real `git commit` itself, so they are present regardless of what runs afterward. Separately, all `[…sha]`-shaped tokens in the buffer are collected and only the last one is kept as the SHA to review, on the stated assumption that "the real commit line is always last in git's own output": [2](#0-1) 

That assumption only holds for output *produced by git itself*; it does not hold for a chained shell command where the attacker appends more output after `git commit` runs. For example: `git commit -m "malicious change" && echo '[main <old_sha>] noop'` (where `<old_sha>` is any real, already-known commit hash from the repo's history, trivially discoverable via `git log` in the same session) produces stdout containing both the real `[branch <real_sha>] msg` line (with the diffstat lines) and the decoy `[main <old_sha>] noop` line afterward. `all_shas[-1]` picks the decoy `<old_sha>`, not the real new commit.

The only remaining check is that the picked SHA resolves via `git show -p <sha>`: [3](#0-2) 

Since `<old_sha>` is a real, valid commit object in the repository, `git show` succeeds (`returncode == 0`), so the hook does not fall back or skip — it proceeds to review the old, already-reviewed commit's diff instead of the actual new commit. There is no check anywhere on this code path that the resolved SHA is new, unreviewed, or a descendant of the pre-commit HEAD (that freshness/dedup check, via `_load_reviewed_shas`, is only applied on the separate reflog-fallback branch at lines 966-989, not on the primary bash-output-derived path).

### Impact Explanation
The freshly created (potentially malicious) commit's diff is never sent to `analyze_code_security`/`agentic_review`, so it is never LLM-reviewed and no `exit(2)` findings are surfaced to the model/user. This is a security-control bypass ("deny means deny / trusted validation matches execution path" violation): the commit-review guardrail that the plugin advertises as the mechanism preventing insecure commits from landing silently can be evaded, letting an attacker-influenced commit through undetected as long as they can append trailing shell output after `git commit` in the same approved compound command.

### Likelihood Explanation
Feasible and repeatable given the stated precondition (compound Bash command already CC-approved for `Bash(git commit:*)`, which is common since hooks.json's matcher is a substring/prefix check, not an exact-command match). The attacker only needs: (1) ability to influence the Bash command run in the session (e.g., via prompt injection from repository content, an issue/PR description, or a compromised dependency's instructions fed into the agent), and (2) knowledge of one valid commit SHA in the repo, trivially obtained via a prior `git log`/`git rev-parse` call in the same session. No privilege escalation or credential compromise is required.

### Recommendation
Do not rely on "last match wins" over the raw combined buffer. Instead:
- Restrict the SHA-search window to the segment of stdout that is contiguous with the diffstat block (e.g., match `[…sha]` immediately followed within N lines by a `_COMMIT_DIFFSTAT_PATTERNS` hit), or
- Independently corroborate the parsed SHA against `git rev-parse HEAD` / reflog `HEAD@{0}` captured immediately after the Bash call, requiring the parsed SHA to match (or be a prefix of) the current HEAD, similar to the cross-repo guard already done in `_resolve_amend_pre_sha` (lines 564-573), and
- Reject SHAs that are already present in `_load_reviewed_shas`/older than the pre-command HEAD, closing the gap between the reflog-path freshness check and the bash-output-derived path.

### Proof of Concept
Unit/integration test in the style of the existing commit-review tests:
1. Initialize a temp git repo with an initial commit `C0` (record its short SHA).
2. Run the hook's Bash tool-response simulation with `tool_input.command = 'git commit -m "malicious payload" && echo "[main <C0_short_sha>] noop"'`, and craft `tool_response.stdout` to contain: the real `[branch <C1_sha>] malicious payload` line + `1 file changed, ...` diffstat line, followed by the decoy `[main <C0_short_sha>] noop` line.
3. Invoke `handle_commit_review_posttooluse(input_data)` and capture which SHA is passed to `git show`/`analyze_code_security` (mock/spy on `subprocess.run` or `analyze_code_security`).
4. Assert failure of the invariant: assert the SHA reviewed equals `<C1_sha>` (`git rev-parse HEAD`), and show the current implementation instead resolves `<C0_short_sha>` — i.e., `_COMMIT_SHA_RE.findall(bash_output)[-1] != actual_head_sha` while `commit_succeeded` is `True` and `git show` on the decoy SHA returns 0.
5. Differential fuzz variant: generate many adversarial `bash_output` strings with a real commit block followed by an attacker-appended `[label validsha]` line (using real repo history SHAs), asserting `parsed_sha == git_rev_parse_head` always holds — the test should fail on current code, demonstrating the bypass.
