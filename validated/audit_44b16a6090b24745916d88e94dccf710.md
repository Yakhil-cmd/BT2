### Title
Cross-repository status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, unlike every other webhook handler in this codebase which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any records. Any legitimately-signed `status` webhook for a repository/org an attacker controls can therefore write a `buildkite/deploy` status onto a `Commit` row belonging to a completely different stack/repository, as long as the SHA value happens to match (e.g. shared commit history via a fork, cherry-pick, or identical tree/commit content).

### Finding Description
The broken binding: the code implicitly assumes `Commit.where(sha: params.sha) == commits belonging to the repository that authenticated the webhook`, i.e. `payload.dig('repository','full_name') == commit.stack.repository.full_name` for every row returned. This is never enforced.

Path:
1. `Shipit::WebhooksController#create` dispatches the raw payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks the HMAC using `Shipit.github(organization: repository_owner)` — i.e. it authenticates *who sent the webhook* for their own org, not that the `sha` inside the payload belongs to that org's repositories. [1](#0-0) 
2. `StatusHandler#process` then runs: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no `repository`/`stack` filter at all. [2](#0-1) 
3. Contrast with every `pull_request` handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `AssignedHandler`, etc.), which all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope subsequent queries to `repository.review_stacks`/`repository.id` before mutating anything. [3](#0-2)  The base `Handler` class even exposes a `stacks` helper scoped by `repository_name` that `StatusHandler` simply doesn't use. [4](#0-3) 
4. `create_status_from_github!` then replicates the status and calls `add_status`, which re-evaluates `status`, emits `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` — directly affecting deployability/merge state for whichever stack owns the matched `Commit` row. [5](#0-4) [6](#0-5) 
5. `deployable?` and `blocked?` depend on the status/state derived from these rows. [7](#0-6) 

Attacker request: attacker controls a repository/org for which they can legitimately trigger real GitHub `status` webhooks (their own CI/Buildkite integration on their own repo, correctly signed by GitHub for their org — passes `verify_signature` normally). They pick or create a commit whose SHA is shared with the victim's tracked repository (e.g. a shared ancestor commit present in a public upstream that the victim stack tracks, or an identical commit forked into both repos — SHA is content-addressed and is not scoped to a single repo on GitHub). They send `context: buildkite/deploy`, `state: failure` for that SHA from their own repo/org. The webhook is authenticated (signature matches attacker's own org), passes `drop_unhandled_event` and `verify_signature`, and `StatusHandler` writes the failing status onto the victim's `Commit` row purely by SHA match, with no check that the payload's `repository.full_name` corresponds to the stack that owns that commit.

Existing guards do not catch this: `verify_signature` authenticates the sending org, not the SHA-to-repository binding; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context` are strings) not ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
A `failure` status on `buildkite/deploy` written onto a victim stack's commit flips `deployable?` to `false` (if `blocking_statuses` includes that context) and can block merges/deploys, or conversely a forged `success` status can make `deployable?` true, enabling `schedule_merges`/continuous delivery to proceed on a commit that never actually passed CI for that repository. This is a payload from one repository mutating another repository's stack/commit state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The blast radius spans every tenant/stack hosted by the same Shipit instance whose commit history can produce a SHA collision with an attacker-controlled repo.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository/org where they can generate a genuinely GitHub-signed `status` webhook (trivial — any repo they own with a CI integration, or by directly emulating GitHub's status payload from their own installed app/org), and (b) a SHA that also exists as a tracked `Commit` in the victim stack (feasible for forks of open-source projects, shared base commits, or any content-identical commit — SHA collision by content is a known, exploitable property of Git, not a hash-brute-force requirement). Given those, the attack is a single unauthenticated-from-Shipit's-perspective (session-wise) HTTP POST, fully repeatable against any repository sharing commit history with the attacker's own.

### Recommendation
Scope `StatusHandler#process` to commits belonging to the repository that authenticated the webhook, mirroring the pattern used by the `pull_request` handlers, e.g. resolve `repository = Shipit::Repository.from_github_repo_name(params_or_payload.dig('repository','full_name'))` (or use the existing `stacks` helper on `Handler`) and restrict the query to `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or equivalent join through `stacks: :repository`) before calling `create_status_from_github!`.

### Proof of Concept
minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or `test/controllers/webhooks_controller_test.rb`):
1. Create two `Repository`/`Stack` fixtures, `victim_repo`/`victim_stack` (review_stacks_enabled: true, allow_all, requiring `buildkite/deploy` as a blocking/required status) and `attacker_repo`/`attacker_stack`, both in different orgs.
2. Create a `Commit` with `sha: "deadbeef..."` under `victim_stack`, with an existing passing `buildkite/deploy` status, and assert `commit.deployable?` (or merge/blocking state) is currently as expected (baseline binding: `victim_commit.stack_id == victim_stack.id` and `victim_commit.deployable? == true`).
3. Invoke `StatusHandler.call` with a payload whose `repository.full_name == attacker_repo.full_name` (attacker's own repo) but `sha == victim_commit.sha`, `context: "buildkite/deploy"`, `state: "failure"`.
4. Assert that `victim_commit.reload.statuses.last.state == "failure"` and `victim_commit.deployable?` flips to `false` (or `blocked?` becomes true) — proving the equality `payload.dig('repository','full_name') == commit.stack.repository.full_name` was never checked, and a repository the attacker does not own mutated the victim's stack state.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
