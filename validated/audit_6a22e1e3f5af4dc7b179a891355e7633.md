### Title
Unhandled `throw Error` in data-feed stream reads crashes the node when an AA trigger evaluates `data_feed[[...]]` / `in_data_feed[[...]]` — ([File: data_feeds.js])

### Summary
The external finding is about an oracle consumer function (`getUnderlyingPrice`) that is expected to fail gracefully (return `0`) but instead throws, breaking its caller. The analogous defect in `ocore` sits in the data-feed reader that backs the `data_feed[[...]]` / `in_data_feed[[...]]` oscript operators used by AA formulas: instead of surfacing read errors through the normal callback/`fatal_error` mechanism that the formula evaluator uses everywhere else, the low-level kvstore stream handlers `throw Error(...)` directly inside an asynchronous event-emitter callback, which is not caught by any part of the call chain.

### Finding Description
`readDataFeedByAddress()` and `dataFeedByAddressExists()` in `data_feeds.js` open a `kvstore` read/key stream and attach handlers: [1](#0-0) 

and equivalently [2](#0-1) 

Both `.on('error', ...)` handlers `throw Error(...)` instead of calling `handleResult`/`cb` with an error value. These functions are invoked from `readDataFeedValue()` and `dataFeedExists()`, which are in turn called directly from the formula evaluator's `data_feed` and `in_data_feed` opcodes: [3](#0-2) [4](#0-3) 

Everywhere else in `formula/evaluation.js`, error conditions are propagated through `setFatalError(...)`/`cb(false)`, which lets `evaluate()` gracefully bounce the AA response (see the `fatal_error` short-circuit at the top of `evaluate`): [5](#0-4) 

But the kvstore stream `error` throws bypass this entire mechanism. Because the throw happens inside a Node.js `EventEmitter` callback (not inside the synchronous call stack of `validate()`/`evaluate()`), it becomes an uncaught exception that is not caught by any `try/catch` in `formula/evaluation.js`, `aa_composer.js`, or `validation.js`. Additionally, `onEnd()` itself contains `throw Error("second call of onEnd")` guard logic that can fire under race conditions between the `'data'`/`'end'` events when a match is found and `stream.destroy()` is called: [6](#0-5) 

This is the same bug *class* as the C4 finding: an oracle/data-feed read path that a consumer (here, the AA/oscript formula evaluator and, transitively, `validateAATrigger`/`aa_composer.handleTrigger`) expects to fail softly, but which instead throws and is not converted into a controlled error.

### Impact Explanation
`data_feed[[...]]` and `in_data_feed[[...]]` are ordinary oscript primitives usable by *any* AA definition, and are evaluated whenever a trigger is sent to that AA — reachable by any unprivileged unit/AA-trigger sender, not just the AA author, since triggering is what invokes formula evaluation. If the underlying kvstore read stream ever emits an `'error'` event (I/O error, corrupted/mid-write DB state, resource exhaustion under load, etc.) while processing such a trigger, the resulting uncaught exception is not confined to “this AA bounces” — it propagates as a process-level uncaught exception. Node processing units/AA triggers that hit this code path can crash, which is a liveness/availability issue for the node (and if triggered on many nodes simultaneously by the same posted unit, a network-wide inability to process/confirm units), rather than the intended graceful failure (bounce the AA / reject the malformed data-feed query).

### Likelihood Explanation
The likelihood of naturally hitting a kvstore stream `'error'` event during normal operation is low, but it is not attacker-proof: the code path is on the “hot” path of every `data_feed`/`in_data_feed` evaluation triggered by any AA trigger sender, and any storage-layer error (disk I/O errors, LevelDB corruption, concurrent write races) surfaces as an uncaught crash instead of a contained validation failure. This is a design defect independent of whether it has been observed in practice: it converts what should be, at worst, a rejected/bounced AA trigger into a process crash, matching the root cause described in the external report (consumer expects graceful failure, implementation throws).

### Recommendation
Route kvstore stream errors through the existing callback-based error-handling convention instead of throwing:
- In `readDataFeedByAddress()` and `readDataFeedValue()`'s stream `.on('error', ...)`, call `handleResult`/`cb` with an error indicator (or reject via the async control flow) instead of `throw Error(...)`.
- In `dataFeedByAddressExists()`, replace the `.on('error', ...)` throw the same way, and guard `onEnd()` re-entrancy without throwing (e.g., simply `if (bOnEndCalled) return;`).
- Ensure these errors bubble up through `readDataFeedValue`/`dataFeedExists` callbacks so that `formula/evaluation.js`'s `data_feed`/`in_data_feed` handlers can call `setFatalError(...)` and let the AA bounce cleanly, consistent with every other error path in the evaluator.

### Proof of Concept
Conceptual trigger path (cannot be demonstrated without live storage-layer fault injection, since the actual trigger condition is a kvstore/LevelDB stream error, which is outside application-level control):
1. Any user sends an AA trigger to an AA whose formula contains `data_feed[[oracles="...", feed_name="..."]]` or `in_data_feed[[...]]`.
2. `formula/evaluation.js` calls into `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists` (`formula/evaluation.js:646`, `formula/evaluation.js:745`).
3. `data_feeds.js` opens a `kvstore` stream (`data_feeds.js:196`, `data_feeds.js:331`) to look up the feed.
4. If the underlying stream ever emits `'error'` (I/O fault, DB corruption, resource pressure), the handler executes `throw Error(...)`, which is not inside any `try/catch` reachable by `validate()`/`evaluate()`'s error-handling flow, resulting in an uncaught exception that can crash the node process instead of causing the AA trigger to bounce.
