This is a real vulnerability, but it is not the one the audit question describes. The claimed defect ("Status has no user/actor field, so identity binding is untestable") is not the actual root cause — the real bug is that `StatusHandler#process` fails to scope the commit lookup to the repository that authenticated the webhook, unlike its sibling handlers.

### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a webhook signed for one org write a `Status` onto another tenant's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits system-wide by `sha` alone and never restricts the query to the repository named in the payload, unlike `PushHandler` and `CheckSuiteHandler`, which both scope through the base class's `stacks` helper (itself derived from `payload.dig('repository','full_name')`). Because `WebhooksController#verify_signature` only proves the payload was signed by *some* registered org's `webhook_secret` (looked up via `repository_owner` from the same attacker-controlled payload), an attacker who owns any registered org can forge a `status` event naming their own repository, but with a `sha` value copied from a commit that exists in a different tenant's stack, and get a `Status` row created against that foreign commit.

### Finding Description
The broken binding is: `github_status.repository.full_name == commit.stack.repository.full_name` for every `Status` created via a webhook. This is enforced in `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`) via `stacks`/`stack.commits`, but is absent in `StatusHandler#process`: [1](#0-0) 

`Handler#stacks` exists precisely to enforce this binding for a request: [2](#0-1) 

`WebhooksController#verify_signature` authenticates that the request was signed by *an* org's `webhook_secret` for the org named in the payload's `repository.owner.login`, not that this org owns the commit sha being referenced: [3](#0-2) 

`Status.replicate_from_github!` then blindly attaches the resulting row to `stack_id:` derived from whatever `Commit` matched the sha, with no cross-check against the requesting repository: [4](#0-3) [5](#0-4) 

Attack: attacker registers/owns Org A in Shipit (any registered org — the rules state "any registered org" is a valid precondition) and knows `webhook_secret` for Org A only. Attacker learns (or guesses) the SHA of a commit that is tracked in Org B's stack (SHAs of public repos, or forked/mirrored commits, are frequently knowable/guessable, and multiple stacks can legitimately track the same public upstream commit). Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body `{"repository":{"owner":{"login":"orgA"}}, "sha": "<org B's commit sha>", "state": "success", ...}`, signed with Org A's `webhook_secret`. `verify_signature` passes because it only checks Org A's secret against Org A's own payload — it never checks that Org A's repository actually contains that sha. `StatusHandler#process` then does `Commit.where(sha: params.sha)`, which matches the Org B commit anywhere in the database, and calls `commit.create_status_from_github!(params)`, writing a `Status` row (state, description, target_url, context) attributed to Org B's stack/commit despite the request never having proven any relationship to Org B's repository.

### Impact Explanation
This is a payload for one repository (Org A's, which the attacker legitimately controls) mutating another repository's (Org B's) commit/stack data — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." A forged `success` status can flip `commit.state`/`success?`, which feeds `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and can enqueue `ProcessMergeRequestsJob`/`schedule_continuous_delivery`, potentially triggering an unauthorized continuous deployment or unblocking a commit for merge/deploy on a tenant the attacker never authenticated against. This is repeatable against any commit sha the attacker can predict, across arbitrary tenants, at zero cost per request. Note: the audit's stated root cause (missing `user` column on `Status`) is not itself exploitable — `release_statuses` do carry a `user`, but `Status` rows created by CI systems have never carried a user by design (there is no "acting user" for CI events); the actual defect is the missing repository scoping in the query, not the schema.

### Likelihood Explanation
Preconditions: attacker needs one registered Shipit org with a working webhook (a real, low bar — the rules explicitly allow "any registered org"), and needs to know a target sha tracked by another tenant's stack. Knowing/guessing shas is plausible for public repositories or commits shared across forks/mirrors, but not guaranteed for private, unique commits — this bounds exploitability to cases where sha values are discoverable, which is a real but non-universal precondition. No GitHub App private key, `secret_key_base`, or victim's `webhook_secret` is required.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: use `stacks` (derived from `payload.dig('repository','full_name')`) to restrict the `Commit` lookup, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, so a status can only be attached to a commit belonging to the repository that authenticated the webhook.

### Proof of Concept
minitest under `test/models/webhooks/handlers/status_handler_test.rb` (or via `WebhooksControllerTest`):
1. Create `stack_a` for repository `orgA/repo`, `stack_b` for repository `orgB/repo`, with a `commit` in `stack_b` having `sha = "deadbeef..."`.
2. Stub `Shipit.github(organization: 'orgA').verify_webhook_signature` to return true (as in existing tests, e.g. `GithubHook.any_instance.stubs(:verify_signature).returns(true)`), simulating a legitimate signature for Org A only.
3. POST `/webhooks` with `X-Github-Event: status`, body `{"repository":{"owner":{"login":"orgA"}, "full_name":"orgA/repo"}, "sha": commit.sha, "state": "success", "branches":[{"name": stack_b.branch}]}`.
4. Assert: `commit.reload.statuses.count` increased by 1, and `commit.statuses.last.stack_id == stack_b.id` — i.e. a `Status` was written into `stack_b`'s commit despite the request only authenticating against `orgA`.
5. Assert (equality that should hold but doesn't): `status.stack.repository.full_name == 'orgA/repo'` is false, while `status.stack.repository.full_name == 'orgB/repo'` is true, proving the binding "authenticated repository == mutated repository" is violated.
