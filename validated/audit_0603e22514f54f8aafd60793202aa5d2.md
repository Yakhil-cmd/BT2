### Title
Cross-organization team hijack via `MembershipHandler#find_or_create_team!` matching only on `github_id` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up a `Team` solely by numeric `github_id`, ignoring the `organization` that the webhook signature actually authenticated. An attacker who owns Org A and knows its own `webhook_secret` can sign a `membership` event whose `organization.login` is `org-A` (so `verify_signature` passes) but whose `team.id` equals the `github_id` of a pre-existing `Team` belonging to Org B, causing `team.add_member(member)` to add the attacker to Org B's team.

### Finding Description
The binding claimed to hold is: `organization whose webhook_secret verified the request bytes == organization owning the Team record mutated by the handler`. Tracing the code shows this is false.

`WebhooksController#verify_signature` resolves `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) . For a `membership` payload with no `repository` key, this falls back to `organization.login`, so signing with Org A's secret and setting `organization.login: "org-A"` passes verification regardless of what `team.id` is.

`MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. The `do |team| ... end` block (which sets `team.organization = params.organization.login`) only executes on **create**; if a `Team` row with that `github_id` already exists (owned by Org B), `find_or_create_by!` simply returns the existing record unmodified [3](#0-2) . The organization field on the found record is never checked or reconciled against the organization that signed the request. `process` then calls `team.add_member(member)` for `action == 'added'`, appending the attacker's user (created via `User.find_or_create_by_login!(params.member.login)`) to Org B's team's `members` [4](#0-3) [5](#0-4) .

None of the existing guards catch this: `verify_signature` only authenticates that the org named in the payload's `organization.login` produced the signature — it never cross-checks the `team.id` against that organization. The `ExplicitParameters` schema for `MembershipHandler` requires `team.id`, `team.name`, `team.slug`, `team.url`, `organization.login`, `member.login` as plain types with no relationship constraint between `team.id` and `organization.login` [6](#0-5) . `Team.find_or_create_by!` matches only on `github_id`, a pure GitHub-side numeric identifier that is guessable/enumerable and not scoped by organization.

**Attacker request:** POST `/webhooks` with `X-Github-Event: membership`, `X-Hub-Signature` computed using Org A's known `webhook_secret`, body:
```json
{"action":"added","team":{"id":<org-B-team-github-id>,"name":"x","slug":"x","url":"https://api.github.com/..."},"organization":{"login":"org-A"},"member":{"login":"attacker"}}
```

### Impact Explanation
The attacker adds their own (or any arbitrary) GitHub-login-bound `User` as a member of a `Team` belonging to a completely different, unrelated organization (Org B), using only credentials they legitimately possess for their own organization. If that team is listed in `Shipit.github_teams`, `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) will now return true for the attacker [7](#0-6) , which `force_github_authentication` uses to gate access to the whole Shipit application (`current_user.authorized?` check) [8](#0-7) . This is a genuine cross-tenant write: a payload signed by Org A mutates a `Team` record scoped to Org B, and grants the attacker escalated authorization matching the "escalation into `Shipit.github_teams` authorization" High-severity category in the rules. The attack is repeatable against any `github_id` the attacker can guess/enumerate and is not limited to a single team.

### Likelihood Explanation
Preconditions: attacker must own/control an organization onboarded into this Shipit instance (to have a valid `webhook_secret` for signing), and a `Team` row for the target org/team must already exist with a known or guessable numeric `github_id` (GitHub team ids are sequential/enumerable and often discoverable via public API or prior events) and be referenced in `Shipit.github_teams`. Given those, the attack cost is a single crafted, self-signed HTTP POST — no elevated privileges, no other org's secrets, no session are required, satisfying the "unprivileged attacker" threat model in the rules.

### Recommendation
`find_or_create_team!` must scope the lookup by both `github_id` and the authenticated `organization` (i.e., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` or explicitly verify `team.organization == params.organization.login` before calling `add_member`/`delete`, raising/dropping the event otherwise). Additionally, `verify_signature`/handler dispatch should ensure the organization used for signature verification is the same organization allowed to mutate the resolved `Team`, rejecting mismatches.

### Proof of Concept
Minitest plan (`test/models/webhooks/membership_handler_test.rb`, no live GitHub calls):
1. Create `team_b = Shipit::Team.create!(github_id: 555, organization: 'org-b', slug: 'deployers', name: 'Deployers', api_url: 'https://api.github.com/teams/555')`.
2. Stub `Shipit.github_teams` to include `team_b` (or directly assert on `team_b.members`).
3. Build a `membership` payload: `{"action"=>"added","team"=>{"id"=>555,"name"=>"Deployers","slug"=>"deployers","url"=>"..."},"organization"=>{"login"=>"org-a"},"member"=>{"login"=>"attacker"}}`.
4. Call `Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call` (bypassing HTTP layer, as the signature check is orthogonal — it is stubbed/assumed to have passed for `org-a`).
5. Assert: **before** = `team_b.organization == 'org-b'` and signer organization == `'org-a'` (mismatch, `'org-b' != 'org-a'`).
6. Assert **after**: `team_b.reload.members.map(&:login)` includes `'attacker'`, i.e. Org A's signed payload wrote membership into Org B's team — proving the equality `signing_org == mutated_team.organization` is false, confirming the vulnerability.
