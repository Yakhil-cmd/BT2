### Title
Griefing via repeated pushes indefinitely delays stale-worktree cleanup, leading to persistent disk exhaustion / sync denial - (File: main.go)

### Summary
`git-sync` tracks per-worktree staleness using filesystem mtimes rather than a per-worktree fixed "created" timestamp. Every time a sync produces a new hash, the *previous* current worktree's mtime is reset via `touch()`, restarting its `--stale-worktree-timeout` countdown before `removeStaleWorktrees` will delete it.

### Finding Description
On each successful sync where `changed` is true, `SyncRepo` publishes the new symlink and then calls `touch(currentWorktree.Path())` to bump the mtime of the *outgoing* worktree, explicitly commented as "Start the stale worktree removal timer": [1](#0-0) 

`removeStaleWorktrees` later deletes any worktree directory (other than the current one) only once `time.Since(fi.ModTime()) > git.staleTimeout` has elapsed: [2](#0-1) 

Because a new commit on the tracked ref causes a *new* worktree to become "current" and the *old* one to be (re-)touched, an attacker who controls the upstream repository (has push access, e.g., to a branch/ref that git-sync tracks) can push a trivial commit at an interval shorter than `--stale-worktree-timeout` (or shorter than `--period`, since each poll cycle re-touches the newly-superseded worktree). This causes a rolling chain of never-fully-stale worktrees: each is touched once when superseded and, before it individually reaches the stale threshold, additional worktrees can accumulate. Under sustained low-cost pushes on a short `--period`, worktrees are created (`createWorktree`) faster than the fixed `--stale-worktree-timeout` window permits their removal, since `cleanup()` only removes worktrees whose mtime exceeds the timeout, and cleanup runs once per sync loop: [3](#0-2) 

This mirrors the Mochi bug class: a cheap, repeatable "deposit"-equivalent (a git push) resets a per-object timer that gates a subsequent protective action (removal/reclaim), letting an attacker indefinitely prevent that protective action from firing (worktree cleanup / disk reclamation) as long as they keep repeating the trigger faster than the timeout.

### Impact Explanation
Sustained pushes faster than `--stale-worktree-timeout` (default `0`, meaning immediate removal is normally safe, but operators commonly set a positive value, e.g. per the e2e test `--stale-worktree-timeout=5s`) let an untrusted-but-push-capable actor cause unbounded worktree accumulation on the node running git-sync, exhausting local disk (`--root`) and eventually causing sync failures / container crash (persistent sync denial) for the sidecar and any consumers relying on the `--link` contract. This requires only ordinary push/commit rights to the tracked repo — no leaked credentials, no malicious operator, and no changes to git-sync's own trust boundary.

### Likelihood Explanation
Requires `--stale-worktree-timeout` to be configured to a nonzero value (a documented, common configuration) and requires the attacker to have commit/push access to the tracked ref — a plausible scenario when git-sync is pointed at repos with multiple less-trusted contributors or is fed by CI/webhook automation. With a short `--period` (commonly `100ms`–`10s` in this codebase's own e2e tests) an attacker can far outrun a multi-second `--stale-worktree-timeout` with cheap empty commits, so likelihood is moderate-to-high in that configuration space.

### Recommendation
Do not reuse the touch/mtime of the *current* worktree at supersession time as the sole staleness anchor; instead, record a fixed "superseded-at" or "created-at" timestamp per worktree (independent of how many further syncs occur) and/or cap total worktree count/disk usage independent of individual worktree age, so repeated fast-paced pushes cannot indefinitely re-arm cleanup eligibility windows or unboundedly grow the worktree set.

### Proof of Concept
1. Start `git-sync --repo=<attacker-influenced repo> --period=100ms --root=$ROOT --link=link --stale-worktree-timeout=5s`.
2. Attacker (push-capable to the tracked ref) pushes a trivial one-line commit every ~1s (faster than 5s stale timeout).
3. Observe via `$ROOT/.worktrees/*` that the number of retained worktree directories grows without ever converging, since each newly-superseded worktree's mtime is freshly touched on every sync cycle (`main.go:1964-1970`) before the 5s timeout can be reached relative to *its* touch time, and `removeStaleWorktrees` (`main.go:1420-1441`) never catches up — eventually exhausting `--root`'s filesystem.

func (git *repoSync) removeStaleWorktrees() (int, error) {
	currentWorktree, err := git.currentWorktree()
	if err != nil {
		return 0, err
	}

	git.log.V(3).Info("cleaning up stale worktrees", "currentHash", currentWorktree.Hash())

	count := 0
	err = removeDirContentsIf(git.worktreeFor("").Path(), git.log, func(fi os.FileInfo) (bool, error) {
		// delete files that are over the stale time out, and make sure to never delete the current worktree
		if fi.Name() != currentWorktree.Hash() && time.Since(fi.ModTime()) > git.staleTimeout {
			count++
			return true, nil
		}
		return false, nil
	})
	if err != nil {
		return 0, err
	}
	return count, nil
}

// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}
