### Title
Cross-tenant stack mutation via `pull_request` webhook — signature verified against attacker-chosen org, repository resolved from unverified payload field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/org config (and thus which `webhook_secret`) to verify the HMAC against using `repository.owner.login` taken directly from the untrusted JSON body. If that org exists in Shipit's config but has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, so no HMAC is required at all. The `PullRequest::ClosedHandler` (and sibling PR handlers) then look up the target `Repository` using a *different, independently attacker-controlled* field, `repository.full_name`, so the "verifying org" and the "mutated repository" never have to match.

### Finding Description
The broken binding is: **the org whose `webhook_secret` verified the request MUST equal the owner of the repository whose stack the handler mutates**, i.e. `repository_owner (used in verify_signature) == Repository#owner (resolved in handler via repository.full_name)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)`, which loads whichever org's config matches that string. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank for that org — no HMAC check occurs. [3](#0-2) 
3. If verification passes (or the org is unknown and simply 422's — but here it's a *known, no-secret* org, so it passes), `Webhooks.for_event('pull_request')` dispatches the raw body to every PR handler. [4](#0-3) [5](#0-4) 
4. `ClosedHandler#repository` resolves the actual `Repository` via `params.repository.full_name` — a completely separate JSON field from the one used to pick the signing org — using `Shipit::Repository.from_github_repo_name`. [6](#0-5) [7](#0-6) 
5. `ClosedHandler#process` then calls `review_stack.archive!` on that resolved repository's review stack, entirely driven by attacker-supplied `pull_request`/`head`/`number` fields. [8](#0-7) 

**Attacker request**: POST `/webhooks` with header `X-Github-Event: pull_request`, any (or garbage) `X-Hub-Signature`, and JSON body where `repository.owner.login = "no-secret-org"` (a real org configured in Shipit's `secrets.github` but without a `webhook_secret`) while `repository.full_name = "victim-org/victim-repo"` and `pull_request.head.ref`/`number` identify the victim's open review-stack branch. Because step 2's check trivially passes, the forged closed event is accepted and archives the victim's `ReviewStack`.

**Why existing guards fail**: `drop_unhandled_event` only checks the event type is registered, not authenticity. `verify_signature` authenticates against an org identity chosen from the same untrusted payload it's supposed to protect, and that identity is never cross-checked against the identity used later by the handler for repository lookup. `ExplicitParameters` schemas in the handlers only validate types/presence, not that `repository.full_name`'s owner matches the verified org.

### Impact Explanation
An unauthenticated attacker can force lifecycle actions (e.g., archiving a `ReviewStack`, and by the same mechanism labeling/assigning/reopening PR-driven stacks via the other PR handlers) on **any repository configured in Shipit**, as long as at least one *other* configured GitHub org lacks a `webhook_secret`. This is a cross-tenant/cross-repository state manipulation where one org's (weak) trust is used to forge writes against a victim repo that never authenticated the request — matching the Critical "payload for one repository mutating another's stack" category.

### Likelihood Explanation
Requires Shipit to be configured with multi-org GitHub App config (`secrets.github` keyed by org) where at least one configured org has no `webhook_secret` set. Given that blank `webhook_secret` is explicitly treated as "skip verification" rather than "misconfiguration/reject," this is a realistic operational scenario (e.g., an org added for read-only/legacy purposes without webhook secret rotation). No credentials are needed by the attacker; the request is a single unauthenticated HTTP POST, fully repeatable against arbitrary repositories/stacks.

### Recommendation
- Never allow signature verification to fully bypass based on org selected from the untrusted payload; require `verify_signature` to check the HMAC against the secret of the org that actually owns `params.repository.full_name`'s resolved `Repository`, not `params.repository.owner.login` alone equated with a fallback-to-open Boolean.
- Treat a configured org with a blank `webhook_secret` as a hard misconfiguration (reject/422) rather than "trust unconditionally," or require webhook secret presence for all configured orgs at boot.
- In each PR handler, verify that the resolved `Repository#owner` matches the org that passed signature verification before performing any mutation.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure `Shipit.stubs(:secrets).returns(...)` (or equivalent fixture) with two orgs: `"no-secret-org"` (no `webhook_secret`) and `"victim-org"` (with a `webhook_secret`).
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")` and an associated open `Shipit::ReviewStack` for a PR branch/number.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, arbitrary/garbage `X-Hub-Signature`, and JSON body:
   - `repository.owner.login = "no-secret-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `action = "closed"`, `pull_request.head.ref`/`number` matching the victim review stack.
4. Assert response is `200 OK` (not `422`).
5. Assert the equality binding: BEFORE — `review_stack.archived? == false`; AFTER — `review_stack.reload.archived? == true`, despite no valid signature ever being presented for `"victim-org"`. This demonstrates `repository_owner` used for verification (`"no-secret-org"`) diverging from the repository actually mutated (`"victim-org/victim-repo"`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
