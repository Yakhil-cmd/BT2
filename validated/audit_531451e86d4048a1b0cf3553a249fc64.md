### Title
zToken担保価格計算がブロック内で共有される`index-cache`を再利用し、`socialize-debt`によるバッドデット償却前のインデックスで他者の残高が評価され得る - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`は、zToken担保の価格解決（`resolve-ztoken`）に必要なvaultの`lindex`（清算インデックス）を、`{timestamp: stacks-block-time, aid}`をキーとする`index-cache`マップにキャッシュしてガス最適化を行っている。このキャッシュはブロック内で複数のユーザー・複数のトランザクションから共有され、最初に`accrue-and-cache`を呼んだ呼び出し者がキャッシュを「プライム」し、同ブロック内の以降の全呼び出しがその値を再利用する仕組みになっている [1](#0-0) 。無効化トリガーはブロックタイムスタンプの変化のみであり、`socialize-debt`（バッドデット償却によるvaultインデックスの即時減少）が実行されても明示的なキャッシュ無効化は行われない [2](#0-1) 。

### Finding Description
`index-cache`は次のように定義され、書き込み/読み出しはすべて`accrue-and-cache`を経由する: [3](#0-2) 

```clarity
(define-map index-cache
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })
```

```clarity
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)          ;; cache HIT: no fresh accrual
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [1](#0-0) 

このキャッシュされた`lindex`はzToken担保の価格算出に直接使われる:
```clarity
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
``` [4](#0-3) 

設計文書自身が明記している通り、キャッシュ無効化はブロックタイムスタンプが変わったときのみ発生し、それ以外の「手動無効化は不要」とされている: [2](#0-1) 

一方、`socialize-debt`はvault側で保有される`lindex`をバッドデット償却により即時に減額する処理であり（`mainnet/contracts/vault/v0-vault-*.clar`に実装、`lindex`関連ロジックが各vaultに存在）、これは時間経過に基づく通常のアクルーではなく、瞬間的なヘアカットである。しかし`market.clar`はこの償却がブロック内で発生したことを検知して`index-cache`を無効化するロジックを持たない。

したがって、以下のシーケンスが同一ブロック内で成立し得る:
1. 呼び出し者X（清算人や任意のユーザー）が同ブロックの早い段階で、あるvault(aid)に対する`accrue-and-cache`を発火する市場操作（`collateral-add`/`borrow`等）を行い、`index-cache`に「償却前」の高い`lindex`をプライムする。
2. その後、同ブロック内で清算処理が完全清算（full liquidation）で回収不能なバッドデットが生じ、`socialize-debt`が呼ばれてvaultの実際の`lindex`が引き下げられる。
3. 同ブロック内でzToken担保を保有する他のユーザー（攻撃者自身、または善意の第三者のトランザクションがたまたま同ブロックに入った場合を含む）が`borrow`や`collateral-add`などの操作を行うと、`get-cached-indexes`はステップ1でプライムされた「償却前」の高い`lindex`を返し続け、真の（償却後の）担保価値より高い評価で健全性チェック・借入余力計算が行われる。

この結果、償却が実際に反映される前の過大評価された担保価値に基づいて借入や担保追加の健全性判定が通過してしまい、真の裏付け資産（vaultの実際のシェア価値）はその借入余力を支えられない。これは「一方の呼び出し者がプライムした共有キャッシュを、別の当事者が消費する」「二者間のブロック内順序依存」という、外部レポートのCRLFインジェクション（一方の入力が共有ストリーム状態を汚染し、他方のレスポンス解釈に影響する）と同型の構造的バグである。

### Impact Explanation
過大評価されたzToken担保価値により、ユーザーは本来のプロトコル・ソルベンシー制約を超えて借入を実行できる可能性があり、これはバッドデット償却で本来ヘアカットされるべき損失を他のサプライヤーに socialize する効果を助長し、プロトコルの実質的なソルベンシーを損なう。これは「protocol insolvency」に該当するCritical〜Highクラスの影響である。

### Likelihood Explanation
発生には、同一ブロック内で (a) 該当vaultに対する`index-cache`のプライム、(b) `socialize-debt`の実行、(c) 同キャッシュを消費する担保評価操作、という順序が揃う必要がある。`socialize-debt`はバッドデット発生時にのみ呼ばれる比較的稀な経路だが、ブロックビルダー/トランザクション提出タイミングを攻撃者が制御できるStacksのようなチェーンでは、攻撃者が自身の`collateral-add`/`borrow`トランザクションをバッドデット清算トランザクションの直後に同一ブロックへ含めることで意図的に成立させ得る。

### Recommendation
`socialize-debt`（および他のインデックスを瞬間的に変更するvault操作）が呼ばれた際に、対応する`aid`の`index-cache`エントリを同ブロック内で明示的に無効化（`map-delete`）するか、`socialize-debt`後に必ず`vault-accrue`を強制的に再実行してキャッシュを更新する仕組みを追加する。あるいは、キャッシュのキーにvault側のグローバルなインデックス更新ノンス（例えば`socialize-debt`ごとにインクリメントされるカウンタ）を含めることで、償却後は自動的にキャッシュミスとなるようにする。

### Proof of Concept
1. ブロックN開始時点で、あるvault(aid=USDC)のzUSDCを担保として保有するユーザーが存在し、`lindex = L0`。
2. 攻撃者が同ブロックNの先頭付近で、微小額の`collateral-add`(自身のzUSDC等)を実行し、`accrue-and-cache(USDC)`を発火させ`index-cache{timestamp: T, aid: USDC} = {index: I0, lindex: L0}`をプライムする。
3. 同ブロックN内で、別の清算トランザクションが完全清算を実行し、回収不能債務が発生して`vault-usdc.socialize-debt`が呼ばれ、vault内部の実際の`lindex`が`L0`から`L1 (< L0)`へ引き下げられる。
4. 攻撃者が同ブロックN内で続けて`borrow`を実行し、zUSDC担保の評価に`resolve-ztoken`が呼ばれる。`get-cached-indexes(USDC)`はステップ2でキャッシュされた`{lindex: L0}`をヒットとして返す（`socialize-debt`によるキャッシュ無効化が存在しないため）。
5. 攻撃者の借入健全性チェックは、真の`L1`ではなく古い`L0`（過大評価）に基づいて通過し、実際の裏付け資産価値を超える借入が成立する。
