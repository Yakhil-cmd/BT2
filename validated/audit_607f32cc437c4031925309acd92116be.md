### Title
Status webhook creates commit statuses without scoping to the authenticated organization's repository, allowing cross-stack CI-status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The reported Uniswap issue is a case where a downstream decision (price) trusts a value that can be influenced by an unverified/unbound source. The closest analog in this engine is `Shipit::Webhooks::Handlers::StatusHandler`, which acts on a webhook payload field (`sha`) that is never bound to the organization whose signature was actually verified for that request.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, itself read straight out of the unverified JSON body (`params.dig('repository','owner','login')`), and only then verifies the *whole* raw body against that org's secret: [1](#0-0) 

This confirms that *the payload's claimed organization* possesses a valid secret for the signature — but nothing else. Unlike every other handler (`PushHandler`, `CheckSuiteHandler`, `PullRequest::LabeledHandler`, etc.), which scope their effects through `Handler#stacks`/`Repository.from_github_repo_name(repository_name)` (i.e., bound to `repository.full_name`): [2](#0-1) 

`StatusHandler#process` completely ignores `repository`/organization scoping and instead performs a global, unscoped lookup of commits by `sha` across **every stack in the installation**: [3](#0-2) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit` records belong to a `Stack`, and `Stack`s belong to a `Repository` owned by potentially a completely different GitHub organization/App configuration than the one whose secret validated the inbound request: [4](#0-3) 

The equality that should hold but is broken is:
`organization whose webhook_secret validated this request == organization that owns the repository/stack whose commit status is being written`

Because `StatusHandler` never checks `payload['repository']['full_name']`, any organization/repository that has a Shipit-configured GitHub App/webhook (i.e., any tenant of a multi-org Shipit install) can send a `status` event with an arbitrary `sha` and completely fabricated `state`/`context`, and if that sha happens to also exist as a `Commit` row for a stack belonging to an unrelated organization (e.g. via forked repositories, subtree/mirror pushes, or cherry-picked commits that share the same SHA1 across remotes), Shipit will attach that forged status to the unrelated stack's commit.

### Impact Explanation
`Commit#create_status_from_github!` feeds directly into `Status::Group`/`MergeRequest::StatusChecker`, which the merge queue (`MergeRequest#all_status_checks_passed?`, `#any_status_checks_failed?`) uses to decide whether a pull request is mergeable: [5](#0-4) 

It also triggers `stack.schedule_merges` and continuous-delivery scheduling: [6](#0-5) 

A forged "success" status on a shared/colliding SHA can push an unrelated stack's commit past its CI gating and into the merge queue or continuous-deployment pipeline — an unauthorized merge/deploy triggered purely by cross-tenant webhook data, which matches the High/Critical bar ("escalation... unauthenticated... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires the attacker to control (or compromise) a GitHub App/organization that Shipit already trusts for webhook delivery, and for a target commit SHA to also exist as a tracked `Commit` for a different stack — realistic in fork-based workflows, subtree mirrors, or when multiple orgs' repos share history. This is a real, narrower exposure than the generic AMM price analogy, but it is not a wide-open, zero-precondition bug; it depends on SHA reuse across tenants, which the reporting rules require us to flag honestly as a likelihood-limiting factor.

### Recommendation
Scope `StatusHandler#process` (like every other handler) to the repository named in the payload, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` or filter `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))`, using the same `Handler#stacks`/`repository_name` binding already used elsewhere, so a commit status can only be recorded against a commit belonging to the repository that the (verified) payload claims to originate from.

### Proof of Concept
1. Configure Shipit with two organizations/GitHub Apps, `org-attacker` and `org-victim`, both with valid webhook secrets (a standard multi-tenant Shipit deployment).
2. As `org-attacker`, arrange (or wait) for a commit SHA that is also tracked by a `Stack` under `org-victim` (e.g. a forked/mirrored commit, or a commit cherry-picked with an identical tree+parents+metadata producing the same SHA1).
3. Send a `status` webhook event signed with `org-attacker`'s secret:
```json
{
  "sha": "<shared-sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": {"owner": {"login": "org-attacker"}}
}
```
4. `WebhooksController#verify_signature` verifies successfully because the signature matches `org-attacker`'s secret over the raw body — this only proves the request came from `org-attacker`, not `org-victim`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, unscoped by repository, and finds the `org-victim` commit, calling `create_status_from_github!` on it — recording a forged "success" status on `org-victim`'s stack, which can unblock its merge queue.
