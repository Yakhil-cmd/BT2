### Title
Block-revenue commission updates bypass the mandatory epoch-delay that protects inflation-reward commission, allowing front-run theft of stakers' rewards - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The external report's bug class is: a privileged actor can front-run a protective delay/notice mechanism by changing a critical parameter (`_calldata`) at the very last moment before it is consumed, because the execution path does not bind to a value that was committed earlier. In Agave's vote/reward-distribution code, an analogous pattern exists between the two SIMD-0291 commission mechanisms: inflation-reward commission (`inflation_rewards_commission_bps`) is protected by a mandatory one-epoch delay before it affects reward math, but block-revenue commission (`block_revenue_commission_bps`) is explicitly documented as having "No commission update rule" and is not delayed in the reward-calculation path, letting the authorized withdrawer spike it immediately before rewards are computed/distributed.

### Finding Description
`update_commission_bps` (used for both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue`) contains the comment:

"No commission update rule, per SIMD-0249 and SIMD-0291." [1](#0-0) 

Meanwhile, `calculate_stake_rewards_and_commissions` explicitly compensates for the lack of a timing rule on inflation-reward commission by reading it from a *delayed* epoch snapshot when the `delay_commission_updates` feature is active: [2](#0-1) 

```
// Fetch the voter commission from past epochs to attempt to
// delay the effect of commission updates by at least one
// full epoch.
let commission_bps = if delay_commission_updates {
    let vote_state_for_commission = snapshot_epoch_vote_accounts
        .and_then(|eva| eva.get(&vote_pubkey))
        .or_else(|| rewarded_epoch_vote_accounts.and_then(|eva| eva.get(&vote_pubkey)))
        ...
```

This is fed only into `redeem_delegation_rewards`/`redeem_rewards`, i.e. the **inflation rewards** split. However, the sibling **block revenue** reward split is computed by `calculate_block_reward`, invoked with `cached_vote_accounts.distribution_epoch_vote_accounts` and no `delay_commission_updates` parameter at all: [3](#0-2) 

Unlike the inflation-commission path, there is no visible mechanism forcing `calculate_block_reward` to consult a commission value pinned to a prior epoch; the authorized withdrawer can call `UpdateCommissionBps { kind: CommissionKind::BlockRevenue, .. }` and have it take effect for the very next reward computation, since the instruction handler imposes no epoch-position restriction (unlike the legacy `update_commission` path, which is explicitly gated by `is_commission_update_allowed`, only permitting increases in the first half of the epoch, precisely to stop this kind of front-running): [4](#0-3) [5](#0-4) 

### Impact Explanation
An authorized withdrawer (which is the same unprivileged, non-operator-role key the report's threat model concerns — a leaked/compromised or simply self-interested withdrawer authority) can raise `block_revenue_commission_bps` to a high value (e.g. 100%) immediately before block-revenue rewards for the epoch are computed/distributed, capture the delegators' share of block revenue, and then revert the commission back down afterward. Because there is no analog of the `delay_commission_updates` snapshot protection or the `is_commission_update_allowed` epoch-half restriction for this instruction, this results in misattributed/stolen rewards being redirected from stakers to the validator's commission collector on every epoch boundary, which matches the "misattributed or duplicated rewards" impact category.

### Likelihood Explanation
Likelihood is high for any validator operator wishing to exploit this, and it requires only a single permissionless instruction (`UpdateCommissionBps`) signed by the vote account's authorized withdrawer — no special network position, no operator/validator peer role beyond being the withdrawer of one's own vote account, and no external timing race is needed since the code path itself contains no delay to defeat.

### Recommendation
Apply the same delayed-commission-snapshot mechanism used for `inflation_rewards_commission_bps` (reading from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` when `delay_commission_updates` is active) to `block_revenue_commission_bps` inside `calculate_block_reward`/`calculate_stake_rewards_and_commissions`, or otherwise enforce an equivalent effective-epoch delay for `CommissionKind::BlockRevenue` updates in `update_commission_bps`.

### Proof of Concept
1. Validator withdrawer holds a vote account participating in block-revenue sharing (`block_revenue_sharing` feature active).
2. Near the point where the current epoch's block-revenue rewards will be computed, the withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10_000, kind: CommissionKind::BlockRevenue }`, which succeeds unconditionally per `update_commission_bps` (no epoch-position or delay check).
3. When `calculate_stake_rewards_and_commissions` runs `calculate_block_reward` using `cached_vote_accounts.distribution_epoch_vote_accounts`, it observes the just-updated 100% commission (no delayed-snapshot lookup is applied, unlike the inflation path), causing the entire block-revenue reward for that epoch to be paid to the validator instead of being split with delegated stakers.
4. The withdrawer can then reduce the commission back to its original value for subsequent epochs, or repeat the spike each epoch.

Note: The exact epoch-freshness of `distribution_epoch_vote_accounts` (i.e., whether it is itself pinned to a prior epoch by some other code path not covered in the reviewed context) could not be fully confirmed from the available code; the `redeem_delegation_rewards`/`calculate_stake_rewards_and_commissions` snippets reviewed show no `delay_commission_updates` argument passed to `calculate_block_reward`, and the `update_commission_bps` doc comment explicitly states there is no commission update timing rule, which is the basis for this finding.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}
