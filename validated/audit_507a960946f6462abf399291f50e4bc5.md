### Title
Webhook signature verification is scoped to the payload's own `repository.owner.login`, but `StatusHandler#process` performs an unscoped, cross-tenant `Commit.where(sha:)` lookup, letting an attacker who controls their own registered org mutate commit statuses belonging to another org's stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the GitHub App/secret to check purely from the payload's own `repository.owner.login` (or `organization.login`) and only proves the payload was signed by *that* org's registered webhook secret. It never confirms that this org actually owns the `sha` referenced in the payload, and `StatusHandler#process` looks up commits globally by `sha` with no stack/owner scoping, so a validly-signed payload from org X can write a status onto a commit that belongs to org Y's stack.

### Finding Description
The binding the code should enforce is:
`Shipit.github(organization: repository_owner).verify_webhook_signature(...) == true` implies `repository_owner` is authorized to mutate the commit identified by `params.sha`.

In reality the controller only checks:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where `repository_owner` is taken straight from the attacker-controlled payload (`params.dig('repository','owner','login')`) [2](#0-1) . This proves only that the payload was signed with the webhook secret registered for that org - it says nothing about which stack/commit the `sha` in the body belongs to.

The `create` action then dispatches unconditionally to all handlers for the event, including `StatusHandler`:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [3](#0-2) 

`StatusHandler#process` then does a global, unscoped lookup:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

There is no join/filter against `repository_owner`, the stack's repository, or any tenant boundary - any commit row anywhere in the database with a matching `sha` gets a new status written from the payload's `state`/`description`/`target_url`/`context`.

Because forked GitHub repositories retain identical commit SHAs as their upstream, an attacker who owns/administers their own org already registered in Shipit (`repository_owner == attacker_org`, satisfying `verify_signature` legitimately) can fork a victim org's public repository tracked by Shipit, obtain the victim's real commit SHAs from that fork, and then send a `status` webhook for their own org's repo referencing one of those SHAs. `verify_signature` succeeds (correctly - the payload really is from `attacker_org` and signed with `attacker_org`'s secret), but `StatusHandler#process` will still write the status onto the victim stack's `Commit` row because the lookup is keyed only by `sha`, not by owner/stack.

None of the existing guards close this gap: `drop_unhandled_event` only checks the event type is handled; `verify_signature` only checks HMAC validity against the org named in the payload; the `ExplicitParameters` schema on `StatusHandler` only validates types (`sha`, `state`, etc.), not ownership; there is no `require_permission!`/`stacks` scope applied to webhook-originated writes at all.

### Impact Explanation
An unprivileged attacker who merely owns/administers one org already onboarded into a multi-tenant Shipit instance can inject arbitrary CI status records (`state`, `description`, `target_url`, `context`) onto commits belonging to a different org's stack, without ever needing that org's webhook secret, session, or API token. This is a cross-tenant write - "a payload for one repository mutating another's stack/commit" - matching the Critical severity category. Since commit statuses can factor into merge/deploy gating logic in Shipit (status checks), this can be used to spoof a passing/failing CI status on a victim's commit, potentially enabling or blocking deploys the attacker has no legitimate authority over. The attack is repeatable against any commit SHA the attacker can discover (trivial via forking any tracked public repo) and generalizes to any pair of tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: Shipit must be configured for more than one GitHub organization (multi-tenant), and the attacker must control/administer at least one of those registered orgs (or a repo whose events are proxied through one) - a low bar in any Shipit deployment used by multiple teams/orgs. No secrets belonging to the victim, GitHub App private key, `secret_key_base`, or Shipit session are required. Obtaining matching SHAs is trivial via a GitHub fork of the victim's public repository. The exploit is a single unauthenticated HTTP POST to `/webhooks` per commit to be tampered with, fully repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other handler doing similar global lookups) to commits whose stack's repository matches the verified `repository_owner`/`repository.full_name` from the payload, e.g. join through `Stack`/`Repository` and filter by owner/full_name in addition to `sha`, rejecting or ignoring updates for commits that don't belong to the authenticated organization's repository.

### Proof of Concept
```ruby
test "status webhook validly signed by org X must not mutate a commit belonging to org Y's stack" do
  # victim: stack/commit under org "shopify"
  victim_commit = shipit_commits(:first) # belongs to stack owned by "shopify"

  # attacker: owns org "attacker-org", already registered in Shipit config,
  # forked "shopify/repo" so they know victim_commit.sha from their own fork history
  attacker_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "description" => "forged by attacker",
    "target_url" => "https://evil.example.com",
    "repository" => { "owner" => { "login" => "attacker-org" } }
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true) # attacker's own valid signature

  assert_difference 'victim_commit.statuses.count', 1 do
    post :create, body: attacker_payload, as: :json
  end

  assert_equal 'forged by attacker', victim_commit.statuses.last.description
end
```
Assertion of the broken binding: `verify_signature` succeeds for `repository_owner == "attacker-org"` (left side of binding) while the mutated commit's actual owning stack is `"shopify"` (right side) - the two never match, yet the write proceeds, proving the authorization gap.
