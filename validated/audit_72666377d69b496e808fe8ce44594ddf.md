### Title
Trapped destination-side assets with no recovery path in `TeleportForwarderForAccountId32` accumulate-and-forward teleport - ([File: polkadot/xcm/xcm-builder/src/forwarder.rs])

### Summary
The report describes `finalizeDeposit()` burning/locking funds on one side of a bridge without any callback to return them if the deposit fails on the other side, permanently stranding user funds. The Polkadot SDK analog is `TeleportForwarderForAccountId32::forward()`, the `Forwarder` implementation wired into `pallet_accumulate_and_forward`, which teleports accumulated funds (protocol fees, dust, coretime revenue collected from ordinary user transactions) to a destination system chain. Local burn/withdraw succeeds and is rolled back only on *local* execution failure; but the code and its own doc comment acknowledge that once the local executor reports `Outcome::Complete`, any destination-side rejection (e.g. `AliasOrigin`/`DepositAsset` failing) results in assets trapped at the destination "with no automatic recovery path."

### Finding Description
`pallet_accumulate_and_forward::Pallet::on_nonzero_unbalanced` [1](#0-0)  redirects transaction fees, dust-removal credits, and coretime revenue — all originating from ordinary, unprivileged user activity (paying tx fees is not a privileged action) — into a per-runtime "accumulation account." Periodically, `on_idle` calls the configured `Forwarder::forward()` to teleport the accumulated balance to a fixed destination chain [2](#0-1) .

The production `Forwarder` implementation is `TeleportForwarderForAccountId32`: [3](#0-2) 

Its `forward()` builds an XCM (`WithdrawAsset` → `InitiateTransfer{Teleport}` → remote `DepositAsset`) and executes it locally with `XcmExecutor::prepare_and_execute`: [4](#0-3) 

The transaction wrapper only rolls back local state if the *local* executor outcome is not `Outcome::Complete`: [5](#0-4) 

`Outcome::Complete` only certifies that the local chain successfully withdrew the asset and dispatched the teleport-out XCM message (which reduces total issuance locally, per the crate doc: "Accumulated funds are burnt upon forwarding... and the same funds are minted at the destination when the sent message is received" [6](#0-5) ). It says nothing about whether the remote XCM (`AliasOrigin`/`UnpaidExecution`/`DepositAsset` on the destination) actually succeeds. The adapter's own doc comment states the consequence explicitly:

"Local-execution failures roll back all local state changes. Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path." [7](#0-6) 

This mirrors the report's root cause precisely: value is committed/burned on the sending side based only on local success, with no callback mechanism to detect or reverse a failure on the receiving side — funds simply vanish from the source chain's issuance and never materialize (or become unrecoverable "trapped assets") at the destination.

The pallet is wired into multiple production system-chain runtimes as the fee/dust/revenue handler: `bridge-hub-westend`, `collectives-westend`, `coretime-westend`, `people-westend`, and the Westend relay chain all reference `TeleportForwarderForAccountId32` as their `Forwarder` [8](#0-7) . This is triggered automatically by `on_idle` once `TransferPeriod` has elapsed and the accumulated balance exceeds `MinTransferAmount` — no privileged action is required to *cause* accumulation (any user paying transaction fees or exercising dust-removal/coretime-revenue code paths contributes to the pooled balance that later gets teleported and is put at risk).

### Impact Explanation
If the destination-side XCM fails (e.g., misconfigured `AliasOrigin`/barrier changes, destination weight/version incompatibility, beneficiary account issues, or any other trap condition on the destination), the teleported value is burned on the source chain (reducing its total issuance) but never minted on the destination and becomes untrapped/unrecoverable assets held by the XCM executor's trap mechanism on the destination chain, as acknowledged by the adapter's own documentation. This is systemic protocol revenue (fees, dust, coretime proceeds) rather than an individual user's direct balance, but it is real value permanently lost from total issuance with no automated recovery, matching the "Medium — loss of funds due to missing failure callback" classification of the original report.

### Likelihood Explanation
Likelihood is moderate: the forward is triggered periodically and automatically (`on_idle`, rate-limited by `TransferPeriod`/`MinTransferAmount`), not per-user-request, so a single misconfiguration or transient destination-side barrier/version issue affects the *entire* periodic batch. The condition requires only an ordinary destination-side execution failure (not any attacker privilege) — e.g., XCM version negotiation gaps, barrier changes, or beneficiary/account issues on the destination system chain — which is exactly the class of failure the code's own comment flags as unrecoverable. No malicious actor, governance, or privileged role is needed to trigger it; it is a latent operational risk built into the design.

### Recommendation
Add a failure-recovery mechanism analogous to what the original report recommends for the EVM bridge: either (a) use a query-response / `ReportError`-style XCM instruction so that a destination-side failure is reported back to the source chain, allowing the accumulated funds to be re-credited to the accumulation account rather than burned, or (b) do not treat local `Outcome::Complete` as final — retain the withdrawn/burned funds in a pending state until a delivery/execution confirmation is received, mirroring the request/response pattern used elsewhere in bridge messaging pallets (e.g. `pallet_bridge_messages`' delivery-confirmation flow). At minimum, document and monitor `ForwardFailed`-adjacent trapped-asset scenarios operationally, since currently `ForwardSucceeded`/`ForwardFailed` events only reflect local dispatch success, not remote settlement.

### Proof of Concept
No independent reproduction was executed. Analysis is based on static code review only:
- Confirmed `TeleportForwarderForAccountId32::forward()` treats `Outcome::Complete` from the *local* XCM executor as final success, with no destination-side confirmation, callback, or rollback path [5](#0-4) .
- Confirmed the risk is explicitly acknowledged in the adapter's own doc comment ("destination-side rejection results in trapped assets at the destination with no automatic recovery path") [7](#0-6) .
- Confirmed this component is wired into production Westend-ecosystem runtimes (`bridge-hub-westend`, `collectives-westend`, `coretime-westend`, `people-westend`, relay chain `westend`) as the live `Forwarder` for `pallet_accumulate_and_forward`, which itself is fed by ordinary transaction-fee, dust, and coretime-revenue flows from unprivileged users [9](#0-8) .
- A minimal local FRAME/XCM integration test was **not executed** in this session (no terminal/test-runner access in this ask-only mode); an actual PoC that forces a destination-side `DepositAsset`/`AliasOrigin` failure (e.g., by unregistering the beneficiary alias or corrupting the remote barrier configuration in the emulated test harness at `polkadot/xcm/xcm-builder/src/tests/forwarder.rs`) and asserts trapped assets plus reduced source issuance would be required to fully confirm end-to-end impact and quantify at-risk value; that step should be run under a live Devin session with full test/terminal access before this issue is finalized as bounty-eligible for a specific Parity program.

impl<T: Config> OnUnbalanced<CreditOf<T>> for Pallet<T> {
	fn on_nonzero_unbalanced(amount: CreditOf<T>) {
		let accumulation_account = Self::accumulation_account();
		let numeric_amount = amount.peek();

		// Resolve should never fail because:
		// - can_deposit on destination succeeds assuming accumulation account is pre-funded with ED
		// - amount is guaranteed non-zero by the trait method signature
		// The only failure would be overflow on destination or unfunded account.
		let _ = T::Currency::resolve(&accumulation_account, amount).inspect_err(|_| {
			frame_support::defensive!(
				"🚨 Failed to deposit to accumulation account - funds burned, it should never happen!"
			);
		});

		log::debug!(
			target: LOG_TARGET,
			"💸 Deposited {numeric_amount:?} to accumulation account"
		);
	}
}
