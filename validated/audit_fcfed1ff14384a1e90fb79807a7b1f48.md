### Title
Untrusted strategy bytes can inject unauthorized token transfers into the caller's authorization tree - ([File: contracts/controller/src/strategies/swap_collateral.rs])

### Summary
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` accept opaque `swap` bytes from the caller and execute the resulting route while still beneath the caller's root authorization. If the configured router's encoded route reaches attacker-controlled code, that code can invoke an unrelated token transfer from the caller and have it represented as a child of the caller's authorization. A victim who signs the simulated authorization tree loses wallet assets unrelated to the requested strategy. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` authorizes `caller`, loads the caller-owned account, and passes the caller-supplied `swap` value through `withdraw_and_swap_from_supply`. [1](#0-0)  `multiply` similarly supplies caller-controlled route bytes to `swap_tokens_or_passthrough` after borrowing funds. [3](#0-2) 

The bytes are not decoded or constrained by the controller to a fixed venue list. The authorization boundary therefore includes arbitrary nested calls selected by the encoded route. A rogue pool called by the route can invoke `token.transfer(victim, attacker, amount)` while the victim's `swap_collateral` invocation is still active. [4](#0-3) 

Soroban records that transfer as a child authorization under the caller's root `swap_collateral` authorization. If the transaction is signed with that generated tree, the malicious nested transfer succeeds even though the legitimate strategy itself needed only the routed input transfer. [5](#0-4) 

### Impact Explanation
This is theft of user funds. The stolen asset need not be a listed lending asset, supplied collateral, borrowed debt, or the strategy's input or output token; any token for which the victim's authorization is accepted can be transferred to the attacker. [6](#0-5) 

The protocol-side strategy can remain economically valid. The route can return the expected collateral amount, the controller deposits that amount, and final solvency checks pass, so neither the measured output nor account-risk validation bounds the unrelated wallet loss. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
Any unprivileged account owner or approved delegate can reach `swap_collateral` with arbitrary `swap` bytes after satisfying the normal listed-asset and risk checks. [9](#0-8)  The attack requires the victim to sign a poisoned authorization tree, which is plausible when the tree is generated by simulation and presented as the authorization required for the requested strategy. [10](#0-9) 

The same authorization-shape exposure applies to the other controller strategy entrypoints that accept route bytes, including `multiply` and `swap_debt`. [11](#0-10) 

### Recommendation
Do not allow strategy bytes to introduce caller-authorized side effects unrelated to the swap. At minimum:

- Decode and validate the route at the controller boundary, or require the router to expose a committed machine-readable route manifest covering every nested invocation.
- Reject routes containing user-controlled pool or token callback addresses that are not strictly required by the swap.
- Ensure the caller's authorization covers only the exact input transfer needed by the route.
- Revert if route execution records any nested invocation requiring the caller's auth other than that exact input transfer.
- Require clients to compare the generated authorization tree against the declared route and reject unexpected children; this should remain defense in depth rather than the sole protocol mitigation.
- Add regression tests asserting that a route-selected contract cannot join an unrelated `token.transfer` to the caller's authorization tree. [12](#0-11) 

### Proof of Concept
1. Victim owns a debt-free lending account with supplied USDC and also holds an unrelated token that is not listed by the protocol.
2. Attacker deploys a contract whose `swap` function invokes `token.transfer(victim, attacker, victim_balance)` for that unrelated token. [6](#0-5) 
3. Attacker crafts strategy bytes that route through the malicious contract while returning a fair amount of the requested output asset.
4. Victim calls:

```rust
swap_collateral(
    caller: victim,
    account_id: victim_account,
    current: usdc_hub_asset,
    amount: 5_000_000_000,
    new: eth_hub_asset,
    swap: malicious_route_bytes,
)
```

5. The controller authenticates the victim and forwards the opaque route through the strategy path. [1](#0-0) 
6. During simulation, the malicious contract's token transfer is recorded as a child of the victim's `swap_collateral` authorization. [13](#0-12) 
7. If the victim signs that generated tree, the transaction transfers the unrelated wallet token to the attacker while also depositing the fair strategy output, so the controller's post-strategy checks do not prevent the theft. [8](#0-7)
