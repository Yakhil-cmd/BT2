### Title
Webhook Signature Binds to `repository.owner.login`/`organization.login` While Event Processing Trusts a Different Field, `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) read from the *unverified* JSON body, then validates the whole raw body against that secret. However, the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target `Stack`/`Repository` from a *different* field in the same body: `repository.full_name`. Nothing ties these two fields together, so a signature that is valid for organization A's secret can carry a `repository.full_name` pointing at organization B's stack.

### Finding Description
`verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_webhook_signature` HMACs the raw request body against the secret configured for whichever organization name `repository_owner` claims to be:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

Once verification passes, the event is dispatched to handlers with the same raw body. Those handlers resolve the actually-affected repository/stack via a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` then syncs whatever stacks match `full_name`:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

Shipit's config is explicitly multi-tenant — multiple GitHub organizations, each with its own `webhook_secret`, can be configured on a single Shipit instance:
```yaml
github:
  somegithuborg:
    app_id:
    webhook_secret:
  someothergithuborg:
    app_id:
    webhook_secret:
``` [5](#0-4) 

**The broken binding, as an equality that should hold but doesn't:**
`organization used to select/verify the HMAC secret (repository.owner.login)` == `organization implied by the repository the handler actually mutates (repository.full_name)`.

Because the entire raw body is HMAC'd but the *choice of which secret to check against* is itself taken from an unverified field in that same body, an attacker who legitimately administers **any one** organization onboarded to the same multi-tenant Shipit instance (and therefore knows/controls that org's `webhook_secret`) can produce a validly-signed payload for their own org while setting `repository.full_name` to `victim-org/victim-repo`. The signature check succeeds (it only proves the body was signed with *some* known-to-the-attacker secret, not that the org fields inside the body are self-consistent), and `PushHandler`/`StatusHandler`/`CheckSuiteHandler` then act on the victim's stack using the forged `full_name`.

### Impact Explanation
A validly-signed-but-cross-tenant push webhook lets an unprivileged member of one onboarded organization force `stack.sync_github(expected_head_sha: ...)` on stacks belonging to a completely different organization's repository, and `StatusHandler` writes an attacker-controlled commit `Status` (state/target_url/description) directly onto a victim commit merely by knowing the victim's `sha`. Since Shipit deploy gating typically consults commit statuses/CI checks before allowing a ship, this can be used to force a false "success" status on a victim's commit, contributing to an unauthorized deploy — matching the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Requires no privileged Shipit credential (`ApiClient` token, `github_access_token`, `webhook_secret` of the *target* org). The only requirement is administering (or having push access that triggers webhooks for) any single organization already configured as a Shipit tenant — a realistic scenario on any Shipit install serving more than one GitHub organization, as the shipped multi-org config example demonstrates.

### Recommendation
In `Shipit::WebhooksController#verify_signature` / the handler layer, require that the field used to select the verifying organization (`repository.owner.login` / `organization.login`) is the same field subsequently used to resolve the target repository (`repository.full_name`'s owner segment), rejecting the webhook if they diverge. Alternatively, resolve the target `Stack`/`Repository` first, derive its known GitHub organization from that (trusted) database record, and use that value — not attacker-supplied payload fields — to pick the verification secret.

### Proof of Concept
1. Shipit hosts two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` in `config/secrets.yml`.
2. Attacker, an admin of `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim commit sha attacker wants synced/used>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature` set accordingly.
5. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and the HMAC check passes because the attacker legitimately knows that secret [6](#0-5) .
6. `PushHandler` then loads stacks via `repository.full_name = "victim-org/victim-repo"` [7](#0-6)  and invokes `stack.sync_github` on the victim's stack, despite the signature never having been verified against `victim-org`'s secret.
