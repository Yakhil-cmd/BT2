### Title
`NonTransfer` proxy on Polkadot/Kusama-style relay-chain runtimes falsely claims superset of `SudoBalances` (and other privileged `ProxyType`s), enabling proxy delegate to escalate to `Root` - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
`pallet_proxy::do_proxy` gates `add_proxy`/`remove_proxy` calls solely on `ProxyType::is_superset`, not on `ProxyType::filter`, on the theory that a declared "superset" proxy type necessarily admits every call the "subset" type admits. In `polkadot/runtime/westend/src/lib.rs` (and the structurally identical `substrate/frame/staking-async/runtimes/rc/src/lib.rs`), `ProxyType::is_superset` uses a blanket wildcard `(ProxyType::NonTransfer, _) => true`, declaring `NonTransfer` a superset of every other proxy type — including `SudoBalances`. However, `NonTransfer::filter` explicitly (and correctly) omits the `Sudo` pallet ("`// Specifically omitting Sudo pallet`"), while `SudoBalances::filter` explicitly admits `Sudo::sudo{ call: Balances(..) }`. This is exactly the lattice-violation bug class that was already identified and fixed for the `Governance` variant on Asset Hub Westend (see `prdoc/pr_12769.prdoc`), but the fix was not applied to the relay-chain runtime's `SudoBalances`/`Auction`/`ParaRegistration`/`IdentityJudgement`/`CancelProxy` variants, which still rely on the unconditional wildcard.

### Finding Description
- `pallet_proxy::do_proxy` (`substrate/frame/proxy/src/lib.rs:994-1023`) special-cases `add_proxy`/`remove_proxy` calls: it denies them only `if !def.proxy_type.is_superset(proxy_type)`. Every other call goes through `def.proxy_type.filter(c)`. [1](#0-0) 
- `polkadot/runtime/westend/src/lib.rs` defines `ProxyType::SudoBalances` whose filter admits `Sudo::sudo{ call: Balances(..) }` and `Utility(..)`. [2](#0-1) 
- The same file's `NonTransfer` filter explicitly excludes the `Sudo` pallet ("Specifically omitting Sudo pallet"). [3](#0-2) 
- Yet `is_superset` unconditionally treats `NonTransfer` as a superset of *any* other variant, including `SudoBalances`, `Auction`, `ParaRegistration`, `IdentityJudgement`, `CancelProxy`: [4](#0-3) 
- The exact same code pattern (same variant set and same wildcard) exists in `substrate/frame/staking-async/runtimes/rc/src/lib.rs`. [5](#0-4) 
- The class of bug (declared superset not actually admitting everything the subset admits, letting the "smaller" type be reachable as an escalation through `add_proxy`) is explicitly documented and was fixed for `Governance` on Asset Hub Westend: [6](#0-5) [7](#0-6) 

Attack path (no privileged role required beyond an ordinary, previously-granted `NonTransfer` proxy delegation, which is a routine, low-trust delegation type meant to explicitly deny fund movement):
1. Attacker `D` already holds a `NonTransfer` proxy for account `S` (which happens to be the chain's configured Sudo `Key`). This is a plausible, mundane grant — e.g. an automation/ops key delegated for non-transfer housekeeping.
2. `D` calls `Proxy::proxy(origin=D, real=S, call=Proxy::add_proxy{ delegate: D2, proxy_type: SudoBalances, delay: 0 })`. `do_proxy` checks `NonTransfer.is_superset(SudoBalances)`, which returns `true` due to the wildcard, so the call is **not** filtered and is dispatched as `S`. A new `SudoBalances` proxy relationship (`S -> D2`) is created (`D2` can be `D` itself).
3. `D`/`D2` now calls `Proxy::proxy(origin=D2, real=S, call=Sudo::sudo{ call: Balances::force_set_balance{ who: attacker, new_free: MAX } })`. `do_proxy` falls into the general branch `def.proxy_type.filter(c)` = `SudoBalances.filter(Sudo::sudo{Balances(..)})` = `true`, so the call proceeds, dispatched with origin `Signed(S)`.
4. `pallet_sudo::sudo` checks `ensure_signed(origin)? == Key` — true, since `S` is genuinely the sudo key — then dispatches the inner call via `dispatch_bypass_filter(RawOrigin::Root.into())`, i.e. genuine, filter-bypassing `Root` execution.
5. Net effect: an account holding only a `NonTransfer` delegation (explicitly meant to deny fund movement and Sudo access) obtains full `Root` execution, enabling unbacked issuance (`force_set_balance`), arbitrary runtime upgrade, or any other root-only call.

### Impact Explanation
This breaks the core security guarantee of the proxy system: that a proxy type only ever grants the permissions its own `filter` admits, and that the superset relation enforced by `pallet_proxy` for `add_proxy`/`remove_proxy` never permits privilege escalation beyond the delegate's own filter. Here, a low-trust `NonTransfer` delegate can reach genuine `Root`, enabling unbacked token issuance / arbitrary state mutation — a Critical/High-impact "unauthorized dispatch" and "unbacked issuance" outcome, exactly the category the scan prompt prioritizes.

### Likelihood Explanation
Exploitability depends entirely on whether the account configured as the chain's Sudo `Key` has ever granted a `NonTransfer` proxy to any delegate — a routine, seemingly-safe delegation pattern (since `NonTransfer` is documented/intended to deny fund and privileged-pallet access). On Westend (a public testnet) and on the staking-async reference relay-chain runtime, `Sudo` pallet and `SudoBalances` proxy type are both present and wired, so the precondition is realistic operationally (e.g., convenience delegation from a sudo-controlling key to an automation account). Mainnet Polkadot/Kusama runtimes do not appear to run `pallet_sudo`, limiting current live exposure to Westend and any runtime derived from the `staking-async/runtimes/rc` template that retains `pallet_sudo` + this `ProxyType` design.

### Recommendation
Replace the blanket `(ProxyType::NonTransfer, _) => true` wildcard in `polkadot/runtime/westend/src/lib.rs` and `substrate/frame/staking-async/runtimes/rc/src/lib.rs` with an explicit, filter-consistent lattice (as was already done for `Governance` on Asset Hub Westend in `prdoc/pr_12769.prdoc`), and add a `proxy_type_superset_relation_matches_call_filters`-style regression test (mirroring `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2493-2516`) across all relay-chain `ProxyType`s to prevent recurrence.

### Proof of Concept
No live/mocked execution was run (out of scope per instructions: no privileged/mock authority acceptance permitted, and no network execution performed). The reproduction path above is derived purely from reading the actual production code:
- `substrate/frame/proxy/src/lib.rs:994-1023` (`do_proxy` gating logic),
- `polkadot/runtime/westend/src/lib.rs:950-1032` (`ProxyType::filter`/`is_superset` inconsistency),
- `substrate/frame/sudo/src/lib.rs` (`Sudo::sudo` root-bypass dispatch semantics, standard FRAME sudo pattern).

A concrete integration test could be built by adapting the existing `substrate/frame/proxy/src/tests.rs::filtering_works` harness (lines 318-437) with the Westend `ProxyType` enum, asserting that `NonTransfer.is_superset(&SudoBalances)` is `true` while `SudoBalances.filter` admits a call that `NonTransfer.filter` denies — this alone proves the lattice violation without needing to execute the full escalation chain, consistent with the already-existing regression test pattern `non_transfer_proxy_is_not_a_superset_of_governance` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2523-2559`, which was written specifically to catch this bug class for a different variant pair. This test was **not executed** as part of this analysis; the finding is based on static code reading only, and should be verified by an engineer running the described test against the Westend/staking-async-rc runtime before remediation.

	fn is_superset(&self, o: &Self) -> bool {
		match (self, o) {
			(x, y) if x == y => true,
			(ProxyType::Any, _) => true,
			(_, ProxyType::Any) => false,
			(ProxyType::Assets, ProxyType::AssetOwner) => true,
			(ProxyType::Assets, ProxyType::AssetManager) => true,
			(ProxyType::Staking, ProxyType::StakingOperator) => true,
			// NOTE: `Governance` is deliberately *not* listed here. `NonTransfer` denies the
			// `Treasury`, `ConvictionVoting`, `Referenda` and `Whitelist` calls that `Governance`
			// admits, so it is not a superset of it. Claiming otherwise would let a `NonTransfer`
			// proxy grant itself a `Governance` proxy and widen its own permissions, since
			// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `is_superset`.
			(
				ProxyType::NonTransfer,
				ProxyType::Collator |
				ProxyType::Staking |
				ProxyType::NominationPools |
				ProxyType::StakingOperator,
			) => true,
			_ => false,
		}
	}
}
