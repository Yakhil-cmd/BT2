The reported bug class is a runtime-sized `stackalloc` in C# where an attacker-controlled MessagePack extension length is used to allocate stack memory before validating it against the legal timestamp sizes (4/8/12 bytes), triggering an uncatchable `StackOverflowException`. This specific bug class does not have a demonstrable analog in the polkadot-sdk codebase for the following reasons:

1. **No runtime-sized stack allocation primitive exists in safe Rust.** Unlike C#'s `stackalloc`, Rust's fixed-size arrays (`[u8; N]`) require `N` to be a compile-time constant. There is no direct equivalent of `stackalloc(attackerControlledLength)` reachable from safe code in this codebase.

2. **SCALE codec decoding uses heap allocation, not stack allocation, for variable-length data.** Length-prefixed types (`Vec<u8>`, `Compact<u32>`-prefixed containers) allocate via `Vec::with_capacity`/`Vec::extend` on the heap, and the relevant decode paths I inspected — e.g. `UncheckedExtrinsic::decode`/`decode_with_len` [1](#0-0)  and `StorageInput::read` in the stream iterator [2](#0-1)  — bound-check lengths against actual remaining input or use heap buffers, not stack arrays sized from untrusted length fields.

3. **Fixed-size byte arrays used for timestamps/keys in the codebase are always compile-time-sized**, e.g. `BETimestamp`/`BEBlockNumber` decode into `[u8; 8]`/`[u8; N]` with `N` fixed by the type [3](#0-2) , and `block_entry_key`/`stagnant_at_key` in chain-selection use compile-time-fixed array sizes rather than attacker-supplied lengths [4](#0-3) . None of these derive an array/stack-buffer size from an attacker-controlled length field the way the Nerdbank.MessagePack `tokenSize` did.

4. Searches for `stackalloc`/`alloca`-equivalent patterns, and for length-derived fixed-size buffer allocations preceding validation, turned up no reachable code path via a real user entry point (signed extrinsic, contract call, or XCM message) where an attacker-controlled size value is used to size a stack allocation before length validation.

Given the absence of any runtime-sized stack allocation mechanism triggerable by untrusted input in this codebase, there is no demonstrable Polkadot SDK analog to the reported Nerdbank.MessagePack vulnerability.

impl codec::Input for StorageInput {
	fn remaining_len(&mut self) -> Result<Option<usize>, codec::Error> {
		Ok(Some(self.total_length.saturating_sub(
			self.offset.saturating_sub((self.buffer.len() - self.buffer_pos) as u32),
		) as usize))
	}

	fn read(&mut self, into: &mut [u8]) -> Result<(), codec::Error> {
		// If there is still data left to be read from the state.
		if self.offset < self.total_length {
			if into.len() > self.buffer.capacity() {
				return self.read_big_item(into);
			} else if self.buffer_pos + into.len() > self.buffer.len() {
				self.fill_buffer()?;
			}
		}

		// Guard against `fill_buffer` not reading enough data or just not having enough data
		// anymore.
		if into.len() + self.buffer_pos > self.buffer.len() {
			return Err("Not enough data to fill the buffer".into());
		}

		let end = self.buffer_pos + into.len();
		into.copy_from_slice(&self.buffer[self.buffer_pos..end]);
		self.buffer_pos = end;

		Ok(())
	}
