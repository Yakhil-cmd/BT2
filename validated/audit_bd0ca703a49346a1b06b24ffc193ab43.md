### Title
Webhook status forgery bypasses CI requirements and can trigger unauthorized deploys via `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The Arborist bug is a "trust binding not re-checked" issue: a whitelist entry, once granted, is used for a privileged write with no way to scope/revoke it. The direct analog in shipit-engine is in the webhook trust chain: the organization used to authenticate a webhook (`repository_owner`) is not the same entity as the data actually written by the handler that processes that webhook (a commit `sha` matched globally, with no scoping to the authenticated organization/repository at all).

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization secret to verify the HMAC signature against using an attacker-supplied field of the JSON body itself: [1](#0-0) [2](#0-1) 

The signature check itself is skipped entirely whenever the resolved organization has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret: # nil` is the documented/shipped default for a Shipit organization config, both in the single-org example and in the multi-org fixture: [4](#0-3) [5](#0-4) 

Once the (possibly-unverified) request passes `verify_signature`, the full unverified JSON body is dispatched to handlers: [6](#0-5) 

`StatusHandler`, unlike `PushHandler`/`CheckSuiteHandler` (which scope to `Repository.from_github_repo_name(repository_name)`), matches purely on commit `sha` with **no repository/organization scoping whatsoever**: [7](#0-6) [8](#0-7) 

The binding that should hold as an equality is:
`organization authenticated by verify_signature (repository_owner in payload, checked against that org's secret)` == `repository/stack whose commit state is mutated by the handler (matched by sha, globally, engine-wide)`.

Before the attack, this equality holds for a correctly configured deployment where every configured organization has a `webhook_secret` set — forging a signature requires the secret, and even then `repository.full_name` is protected because it's part of the HMAC-signed raw body.

After the attack: if **any one** organization entry in the multi-org `github:` config (a documented, out-of-the-box valid configuration, cf. `webhook_secret: # nil`) has no `webhook_secret` set, `verify_webhook_signature` returns `true` unconditionally for any payload claiming `repository.owner.login`/`organization.login` equal to that org — regardless of actual signature. The attacker then supplies an arbitrary commit `sha` value (not scoped to that org's repositories) and an arbitrary `state`/`context`, and `StatusHandler#process` writes a status onto **any** commit row in the whole Shipit instance that happens to match that sha, including commits belonging to stacks in a completely different, properly-secured organization.

### Impact Explanation
This is a cross-repository/cross-organization write: an unauthenticated, unprivileged network client can forge a passing CI status (`state: success`, matching the `context` the target stack's `shipit.yml` lists under `ci.require`) on an arbitrary commit belonging to any stack tracked by the Shipit instance, without ever holding a webhook secret for the target organization. On stacks that have Continuous Delivery enabled, satisfying `ci.require` via forged status is exactly the condition that unblocks/triggers an automatic deploy, producing an **unauthorized deploy** — one of the explicitly qualifying impacts.

### Likelihood Explanation
Requires only that one GitHub App entry among (potentially many) organizations configured in a multi-org Shipit deployment omits `webhook_secret` — which the project's own example and test configs show as a normal, supported configuration (`webhook_secret: # nil`). No session, API token, or GitHub credential is needed; the request is a plain unauthenticated `POST /github_authentication/... webhooks` (actually `/webhooks` endpoint routed via `WebhooksController`) with a crafted JSON body and an `X-Github-Event: status` header.

### Recommendation
- Scope every webhook handler (especially `StatusHandler` and `CheckSuiteHandler`) to the repository/organization that was actually authenticated for that request, the same way `Handler#stacks` does via `Repository.from_github_repo_name`, instead of matching commits globally by `sha` alone.
- Require `webhook_secret` to be present for every configured GitHub App/organization (fail fast at boot if absent) rather than silently trusting any payload (`return true unless webhook_secret`) when it is missing.
- Cross-check that the organization used for signature verification (`repository_owner`) matches the owner implied by `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with a multi-org `github:` config where `OrgA` has `webhook_secret` unset (as in the shipped `secrets_double_github_app.yml` example) and `OrgB` (containing the real target stack) has a properly configured secret.
2. As an unauthenticated attacker, `POST /webhooks` (or wherever `WebhooksController` is mounted) with header `X-Github-Event: status`, any/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<sha-of-a-commit-in-OrgB-stack-requiring-ci/required>",
  "state": "success",
  "context": "ci/required"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (invalid) signature.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, writing a forged passing status onto the `OrgB` commit, satisfying its `ci.require` check and, if CD is enabled, triggering an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
