### Title
Unbounded `RemoteProxyProof::RelayChain.proof` size lets weight charged for `remote_proxy` diverge from actual `sp_trie` verification cost - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::remote_proxy` / `Pallet::do_remote_proxy` charge a fixed `WeightInfoOf::<T,I>::remote_proxy()` weight that was benchmarked against a proof containing a single trie node, but the extrinsic accepts an attacker-supplied `proof: Vec<Vec<u8>>` of essentially unbounded size (only limited by the runtime's max extrinsic/block length). Since `sp_trie::StorageProof::new(proof).into_memory_db()` must decode and hash every supplied node before `read_trie_value` runs, a signed account can submit a structurally valid but oversized proof so that actual execution cost scales with attacker-chosen proof size while the charged weight stays constant.

### Finding Description
In `do_remote_proxy` [1](#0-0) , the pallet builds an in-memory trie DB from the caller-supplied `proof: Vec<Vec<u8>>` and calls `sp_trie::read_trie_value`. `into_memory_db()` must hash and insert every node in `proof` regardless of whether it lies on the path to `key`, so cost is proportional to `proof.len()` and the total byte size of its entries, not just to the actual trie depth needed to resolve the key.

The extrinsic's weight, however, is a compile-time constant returned by `WeightInfoOf::<T, I>::remote_proxy()` plus the inner call's own weight [2](#0-1) . The benchmark that produced this constant uses `create_remote_proxy_proof`, which builds a trie with a single inserted key and derives the proof from that minimal trie [3](#0-2) , yielding a `remote_proxy()` weight of `18_259_000` ps / 1846 bytes of PoV [4](#0-3) . Nothing in `Config<I>` (`MaxStorageRootsToKeep`, `RemoteProxy`, `WeightInfo`) or in `RemoteProxyProof` bounds the number or size of proof nodes [5](#0-4) [6](#0-5) . The only implicit limit is the runtime's normal-class max extrinsic/block length (a few MB), which is a length/fee constraint, not a weight constraint tied to trie-decoding cost.

An attacker who knows any `storage_root` retained in `BlockToRoot` (these are public relay-chain storage roots, retained for `MaxStorageRootsToKeep` blocks) can construct `proof` containing many large, well-formed (but irrelevant) trie nodes alongside (or instead of, if they don't need `InvalidProof` to be avoided) the real path nodes, submit `remote_proxy` with a cheap inner `call` (e.g. `remark`), and force `into_memory_db`/`read_trie_value` to spend CPU proportional to the submitted byte volume while only the fixed benchmarked weight is deducted from the block's weight budget.

### Impact Explanation
Because the charged weight for `remote_proxy` does not scale with `proof` size, an attacker can fill many extrinsics in a block with maximal-length low-relevance proofs, each contributing only microseconds of "charged" weight but consuming disproportionately more actual CPU time for trie-node hashing/decoding during block execution. This mismatch between charged and actual weight is the classic PoV/weight-DoS pattern and can push actual block execution time toward (or past) the intended per-block time budget, degrading block production/import performance on any parachain using `pallet-remote-proxy` (e.g. Asset Hub Kusama/Polkadot).

### Likelihood Explanation
Feasibility depends on how large a `remote_proxy` extrinsic proof can practically be relative to the parachain's max extrinsic/normal-class block length, and on how expensive `into_memory_db`'s hashing of a few MB of nodes actually is in wall-clock terms versus the microsecond-scale benchmarked weight. Constructing "many long trie nodes" that are individually valid-format nodes (decodable) does not require them to be part of a real path from `storage_root` — only the nodes actually needed to resolve `key` must be correct; extras only need to be well-formed enough that `into_memory_db` accepts/hashes them, which is a low bar. This is directly reachable by any signed account with no privileged prerequisites beyond knowing a retained relay `storage_root` (which is public), making the precondition trivially satisfiable and the attack repeatable per block.

### Recommendation
Charge weight (and/or reject the call) based on the actual size of the supplied `proof`, e.g.:
- Add a bounded `MaxEncodedLen`/count limit on `RemoteProxyProof::RelayChain.proof` (bound `Vec<Vec<u8>>` via `BoundedVec` with a max node count and per-node max size), and reject oversized proofs early with a cheap length check before calling `into_memory_db`.
- Make the `#[pallet::weight]` annotation for `remote_proxy`/`remote_proxy_with_registered_proof` a function of `proof`'s total encoded length (similar to how many bridge/relay proof-verification extrinsics compute weight from proof size), rather than a single benchmarked constant.
- Re-benchmark `WeightInfo::remote_proxy()` against worst-case (max-allowed) proof sizes/node counts instead of the single-node case currently used in `create_remote_proxy_proof`.

### Proof of Concept
Rust benchmark/fuzz-style integration test in `pallets/remote-proxy/src/tests.rs`:
```rust
#[test]
fn oversized_proof_costs_far_more_than_charged_weight() {
    // 1. Build a small trie with the real proxy definition key (as in remote_proxy_works),
    //    but pad the resulting StorageProof with N additional large, well-formed
    //    (unrelated-path) trie leaf/branch nodes encoded for LayoutV1<BlakeTwo256>,
    //    up to the runtime's normal-class max extrinsic length.
    // 2. Register the real block/root in BlockToRoot via on_validation_data.
    // 3. Measure wall-clock time (or instrument `sp_trie::read_trie_value` call site)
    //    of `RemoteProxy::do_remote_proxy` for:
    //      a) baseline proof (1 node, as in benchmarking.rs)
    //      b) padded proof (many large nodes)
    // 4. Compute ratio = time(b) / time(a) and compare against
    //    WeightInfoOf::<Test, ()>::remote_proxy() (constant, independent of proof size).
    // Assert: ratio should be bounded by ~1 (i.e., weight scales with cost); if measured
    // execution time for (b) grows roughly linearly with proof size while charged weight
    // stays fixed, assert!(false, "charged weight does not bound actual execution cost").
}
```
Expected result: charged weight (`WeightInfoOf::<T,I>::remote_proxy()`) remains constant across (a) and (b), while measured execution time for (b) grows with proof size, demonstrating that the statically charged weight fails to bound actual execution cost.

		#[cfg(feature = "runtime-benchmarks")]
		fn create_remote_proxy_proof(
			caller: &AccountId,
			proxy: &AccountId,
		) -> (pallet_remote_proxy::RemoteProxyProof<Self::RemoteBlockNumber>, BlockNumber, Hash) {
			use codec::Encode;
			use sp_trie::TrieMut;

			let (mut db, mut root) = sp_trie::MemoryDB::<BlakeTwo256>::default_with_root();
			let mut trie =
				sp_trie::TrieDBMutBuilder::<sp_trie::LayoutV1<_>>::new(&mut db, &mut root).build();

			let proxy_definition =
				alloc::vec![ProxyDefinition::<AccountId, ProxyType, BlockNumber> {
					delegate: caller.clone(),
					proxy_type: ProxyType::default(),
					delay: 0,
				}];

			trie.insert(&Self::proxy_definition_storage_key(proxy), &proxy_definition.encode())
				.unwrap();
			drop(trie);

			(
				pallet_remote_proxy::RemoteProxyProof::RelayChain {
					proof: db.drain().into_values().map(|d| d.0).collect(),
					block: 1,
				},
				1,
				root,
			)
		}
