### Title
Malformed private-payment payload triggers an uncaught hashing exception that permanently deletes the recipient's only local record of an incoming private payment - ([File: network.js])

### Summary
`handleSavedPrivatePayments()` in `network.js` computes a hash of an attacker-supplied private-payment payload before any real validation takes place. If hashing throws (which any private-payment counterparty can trigger deterministically), the `catch` block treats the exception as fatal and calls `deleteHandledPrivateChain()`, which unconditionally issues `DELETE FROM unhandled_private_payments ...`. This permanently destroys the only local copy of the incoming chain before `validateAndSavePrivatePaymentChain()` ever gets to judge whether the payment is actually valid.

### Finding Description
Incoming private-payment chains received from a peer/device are queued in the `unhandled_private_payments` table and later processed by `handleSavedPrivatePayments()`: [1](#0-0) 

The head element's `payload` is fully attacker-controlled (it comes straight from the sender's device message, unvalidated) and is hashed with `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)`, which calls `getJsonSourceString`: [2](#0-1) 

`getJsonSourceString` unconditionally throws on any empty array or empty object anywhere in the (possibly deeply nested) `payload`, since `bAllowEmpty` is never passed at this call site: [3](#0-2) 

A sender of a private payment fully controls the shape of `payload` (it is JSON they construct themselves, prior to any on-chain validation), so including a single empty array/object anywhere in it (e.g. an empty `outputs` sub-array or an empty nested condition object) deterministically causes `getBase64Hash` to throw.

The exception is caught, but the error handling is dangerous: instead of treating hashing failure as "cannot validate yet" (i.e., leaving the record intact for retry/investigation, as the sibling `ifError` handler of `validateAndSavePrivatePaymentChain` does further down), it immediately calls `deleteHandledPrivateChain()`, which hard-deletes the row: [4](#0-3) 

Note also that the `catch` block does not `return`, so execution falls through into the rest of `validateAndSave` using an undefined `json_payload_hash`, compounding the mishandling, but the security-relevant defect is the irreversible `DELETE` performed purely as a side effect of an uncaught JS exception, not of any actual finding that the payment is invalid.

### Impact Explanation
Any private-payment counterparty (the sender of a private chain) can craft a payload that trips this exception. Once triggered, the recipient's node permanently deletes its only local record of that incoming private payment from `unhandled_private_payments` — there is no on-chain retry path, no backup, and no re-validation once the row is gone. This is the same bug class as the Mattermost advisory: a remote, unprivileged actor abuses careless error handling on a parsing/hashing failure to trigger irreversible deletion of local data. For a wallet, the practical result is loss of a legitimately received private payment: the recipient never gets credited and, unless the sender voluntarily resends it out-of-band, that fund transfer is effectively lost to the recipient — a concrete funds-loss condition for a private-payment counterparty, reachable with zero special privileges.

### Likelihood Explanation
Likelihood is high: the trigger condition (any empty array/object nested anywhere in a JSON payload) is trivial to construct and 100% deterministic given `getJsonSourceString`'s unconditional throw behavior for empty containers when `bAllowEmpty` is not set. No race condition, no special timing, and no elevated privilege are required — only the ability to originate a private payment (something every wallet user can normally do).

### Recommendation
- Wrap the payload hashing call in a way that distinguishes "cannot yet judge validity due to an internal/parsing error" from "confirmed invalid," and do not delete the `unhandled_private_payments` row on the former.
- Pass `bAllowEmpty: true` (or otherwise tolerate empty containers) to `getJsonSourceString`/`getBase64Hash` for payloads that are not yet structurally validated, or run a proper schema/structure validation pass before hashing.
- Add the missing `return` after invoking `deleteHandledPrivateChain` inside the `catch` block so execution does not continue with an undefined `json_payload_hash`.
- Consider archiving the raw payload (e.g., into `known_bad_joints`-style storage) instead of hard-deleting on any error, so operators/users can investigate or recover if the deletion turns out to be a false positive due to library bugs or edge cases.

### Proof of Concept
1. As a private-payment sender, construct a private-element payload for a divisible/indivisible asset transfer where any nested field is an empty array or empty object (e.g. an extraneous `"foo": []` field, or an output entry whose `denomination`/custom field is `{}`).
2. Send this chain to the recipient's node/light wallet as you would a normal private payment (via the hub / device message flow that populates `unhandled_private_payments`).
3. On the recipient side, `handleSavedPrivatePayments()` retrieves the row and calls `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)`, which throws `Error("empty array in ...")` / `Error("empty object in ...")`.
4. The `catch` block at `network.js:2472-2477` fires and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which executes `DELETE FROM unhandled_private_payments WHERE unit=? AND message_index=? AND output_index=?` — the record is now permanently gone from local storage, regardless of whether the payment was otherwise legitimate.

**Uncertainty note:** I could not fully trace every code path that populates `unhandled_private_payments` (e.g., the exact device-message handler that inserts these rows) within the available index, so I cannot cite the exact insertion point confirming the payload is unvalidated at insertion time; this is inferred from the comment in `network.js:2667-2668` ("we are leaking to light vendor information about the full chain") and the fact that `validateAndSavePrivatePaymentChain` (the real validator) is called only after the hash succeeds. function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}

function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
