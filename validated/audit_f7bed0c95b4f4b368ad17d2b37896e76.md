## Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook handler updates commit CI state by looking up commits **globally by SHA only**, without scoping the lookup to the repository/organization that the verified webhook signature actually belongs to. Every other webhook handler in this engine (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) first resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and scopes all subsequent queries through that repository's stacks. `StatusHandler` does not do this.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC signature based on `repository_owner`, extracted from the payload itself: [1](#0-0) [2](#0-1) 

This proves authenticity of *"this payload was signed by organization X's webhook secret"* — i.e. it binds `organization authenticated == organization named in payload`. It does **not** bind *"the record being written belongs to a repository owned by organization X"*.

Every handler except `StatusHandler` re-establishes that missing binding by resolving `Repository.from_github_repo_name(...)` from the payload and scoping all reads/writes to that repository's stacks, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores `repository`/`stacks` entirely and looks up commits by SHA across the *entire installation*: [6](#0-5) 

Since Shipit can host stacks for multiple organizations/repositories (each configured with its own GitHub App/webhook secret in `secrets.yml`, selected by `Shipit.github(organization:)`), a webhook validly signed for organization **A** (whose repo/webhook the attacker legitimately controls, e.g. a public repo they own within an org that has a Shipit-integrated app) can carry an arbitrary `sha` value. If that SHA matches a commit SHA tracked under organization **B**'s stack (git SHAs are content-addressed 40-hex values that can — and frequently do — collide across repositories through forks, cherry-picks, subtree merges, or vendored/shared history), the attacker's forged `status` event will call `commit.create_status_from_github!(params)` on organization **B**'s commit, even though the signature was only ever verified against organization **A**'s secret.

The equality that should hold but is broken:
`organization whose webhook_secret authenticated the request == organization that owns the repository/commit being mutated`

### Impact Explanation
Commit CI status directly gates deploy safety and merge-queue behavior (`Commit#deployable?`, `required_statuses`/`blocking_statuses` checks used by `Stack#trigger_deploy` and the merge queue). By forging a `success` status for a targeted commit in a different organization's stack, an attacker who only controls a webhook in one Shipit-connected organization can flip CI gating for a completely unrelated organization's stack, enabling an unauthorized deploy/merge to proceed once a colliding/known SHA is used. This lands in the High-impact bucket ("escalation into authorization... unauthorized deploy") described by the scope rules, since it crosses an organizational trust boundary that the signature check was specifically designed to enforce.

### Likelihood Explanation
Exploitation likelihood is **low-to-moderate**: the attacker needs (a) legitimate control of a webhook-registered repository in *some* org connected to the Shipit instance, and (b) a target commit SHA in a *different* org's tracked stack. This is most practical in multi-tenant Shipit deployments (many orgs configured under one `secrets.yml`, per `test/dummy/config/secrets_double_github_app.yml`), where an attacker in one tenant org can target the shared initial commit of a forked/templated repository, or brute-force/guess a known public commit SHA already tracked in another tenant's stack. It does not require compromising anyone else's webhook secret, GitHub credentials, or Shipit session — only the attacker's own legitimately-authorized webhook.

### Recommendation
Scope `StatusHandler#process` (and any other handler relying on payload-supplied identifiers) through the repository resolved from the payload, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the missing equality by ensuring only commits belonging to stacks under the repository named (and thus organization-signature-verified) in the payload can be mutated.

### Proof of Concept
1. Operate a Shipit instance configured with two GitHub Apps for orgs `A` and `B` in `secrets.yml` (multi-tenant setup, as supported by `Shipit.github(organization:)`).
2. As a legitimate maintainer of a repo in org `A` (which is registered as a Shipit webhook target), trigger/forge a `status` event with:
   - `sha`: a commit SHA known to also exist in org `B`'s tracked stack (e.g. from a shared template/fork history, or a previously observed commit hash from org B's public repo).
   - `state`: `success`
   - `context`: matching one of org B's `required_statuses`/`blocking_statuses`.
   - `repository.owner.login`: `A` (so the signature check in `WebhooksController#verify_signature` passes using org A's own `webhook_secret`).
3. Shipit's `verify_signature` validates the HMAC using org A's `webhook_secret` and accepts the request.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository/org scoping, finds the matching commit belonging to org B's stack, and calls `commit.create_status_from_github!(params)`, marking it as passing CI in org B — even though the request was never verified for org B's webhook secret.
