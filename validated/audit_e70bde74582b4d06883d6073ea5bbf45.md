### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but events act on the repository named by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook against using an **unverified** field taken directly from the still-unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`), while the handler that actually executes the event (`Handler#stacks` / `Handler#repository_name`) resolves the target `Stack`/`Repository` using a **different** unverified field in that same body, `repository.full_name`. These two fields are never cryptographically bound together by the signature check, breaking the equality "organization whose secret authenticated the request == repository that is written."

### Finding Description
`verify_signature` runs before the payload is trusted: [1](#0-0) 

It picks the verification context with: [2](#0-1) 

i.e. `Shipit.github(organization: repository_owner)`, where `repository_owner` comes straight from the raw JSON body before the HMAC has been checked. `verify_webhook_signature` also short-circuits to `true` whenever that organization's `webhook_secret` is blank/unset — a state explicitly supported as "optional" by the setup docs: [3](#0-2) 

Once (or if) the signature check passes, `create` dispatches the *entire* raw params to the registered handlers: [4](#0-3) 

Handlers resolve which `Stack`/`Repository` to mutate using a *different* field of the same body: [5](#0-4) 

and e.g. the push handler drives real side effects (GitHub sync, which feeds continuous delivery/auto-deploy) purely off that resolved repository plus attacker-controlled `ref`/`after`: [6](#0-5) 

Because `repository_owner` (used to pick the *authenticating* secret) and `repository.full_name` (used to pick the *acted-upon* repository) are independent, attacker-controlled keys in the same unauthenticated JSON body, a request can be crafted so that:
- `repository.owner.login` / `organization.login` = an organization configured in `Shipit.github` with **no** `webhook_secret` (a documented, supported configuration) — making `verify_webhook_signature` return `true` unconditionally, and
- `repository.full_name` = any other organization/repository known to Shipit (one that *does* have a secret configured and is not controlled by the attacker).

This is the direct analog of the fyToken bug: the Witch's Dutch-auction price check trusted `cauldron.auctions(vaultId)` (a value never populated because `grab` was bypassed) instead of validating the real state that should gate the price; here, the controller trusts a same-body-but-uninvolved field (`repository.owner.login`) to select the authorization secret while a sibling field (`repository.full_name`) — never covered by that authorization decision — determines which resource is actually written to. The signature covers *bytes*, not the *semantic binding* between "who authenticated" and "what got changed."

### Impact Explanation
This lets an unprivileged attacker forge unauthenticated `push`, `status`, `check_suite`, or `pull_request` webhooks against a target `Stack` belonging to a *different, secured* organization, as long as any organization in the Shipit deployment has no webhook secret configured (or one whose secret the attacker can otherwise obtain/guess). Consequences include:
- Spoofed `push` events causing `Stack#sync_github` to run for a targeted repository/stack, which can trigger Shipit's continuous-delivery auto-deploy path on attacker-chosen timing — an unauthorized deploy trigger against a stack the attacker has no GitHub write access to.
- Spoofed `status`/`check_suite` events forging CI state (`commit.statuses`) for arbitrary commits on a targeted stack, which can unblock/trigger continuous deployment or merge-queue automerging that relies on that status.
- Spoofed `pull_request` events manipulating review-stack lifecycle/merge-queue state for repositories the attacker does not control.

This matches the "unauthorized deploy, rollback or merge" and "cross-repository writes" High/Critical impact categories, and requires no session, API token, GitHub App key, or repository access — only knowledge that some configured organization lacks (or has a leaked) webhook secret, which the engine's own docs treat as a normal, supported setup.

### Likelihood Explanation
Likelihood is meaningful specifically for multi-organization Shipit deployments (explicitly supported, see `test/dummy/config/secrets_double_github_app.yml`) where organizations can be configured independently, and `github.webhook_secret` is documented as optional per org. In that common configuration, any org left without a secret becomes a skeleton key that bypasses signature verification for webhooks claiming any `repository.full_name`, including repositories under fully-secured organizations. Even in a single-org deployment where the operator forgot/omitted `webhook_secret` (again, documented as optional), the same bypass applies to that instance's own repositories.

### Recommendation
- Derive the verification identity and the acted-upon repository from the *same, single* field, and validate that `repository.owner.login`/`organization.login` is consistent with `repository.full_name`'s owner before dispatching to handlers.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in production; require an explicit `Shipit.authentication_disabled?`-style opt-in, or fail closed and log loudly.
- After signature verification succeeds for organization `O`, assert that every repository-scoped field consumed by handlers (`repository.full_name`, `organization.login`) actually belongs to `O` before invoking `Shipit::Webhooks.for_event(event)`.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs: `SecureOrg` (has `webhook_secret: s3cr3t`) and `OpenOrg` (has no `webhook_secret`, a supported/documented state), each with at least one `Stack`.
2. Attacker crafts a `push` webhook JSON body with:
   - `repository.owner.login` = `"OpenOrg"`
   - `organization.login` = `"OpenOrg"`
   - `repository.full_name` = `"SecureOrg/target-repo"`
   - `ref` = `"refs/heads/master"`, `after` = a real commit SHA on `SecureOrg/target-repo`
3. POST it to `/webhooks` with header `X-Github-Event: push` and any (or no) `X-Hub-Signature` value.
4. `verify_signature` resolves `Shipit.github(organization: 'OpenOrg')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the header/body — see `verify_webhook_signature` in `lib/shipit/github_app.rb`.
5. `create` calls `Shipit::Webhooks.for_event('push')`, dispatching to `PushHandler`, which resolves `stacks` via `payload.dig('repository','full_name')` == `"SecureOrg/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb`), and calls `stack.sync_github(expected_head_sha: 'after-sha')` on the `SecureOrg` stack — despite `SecureOrg`'s own `webhook_secret` never having been checked.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
