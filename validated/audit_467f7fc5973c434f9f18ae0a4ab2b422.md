This confirms the core mismatch. The `StatusHandler` at [1](#0-0)  looks up commits purely by `sha` with no repository/owner scoping at all, and writes a status via `commit.create_status_from_github!(params)`. Combined with the `WebhooksController#verify_signature` selecting the HMAC key by `repository.owner.login` (or `organization.login`) while the handler that actually mutates data (`Handler#stacks`/`Repository.from_github_repo_name`) keys off `repository.full_name` [2](#0-1) , `repository.owner.login` and `repository.full_name` are never cross-validated for consistency.

### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act on Unrelated `repository.full_name`/`sha` — Cross-Organization/Repository Status & Sync Forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC `webhook_secret`) to verify the payload against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [3](#0-2) . However, none of the fields actually consumed by the event handlers are bound to that verified owner. `Handler#stacks` resolves the target repository from `payload.dig('repository', 'full_name')` [2](#0-1) , and `StatusHandler#process` looks up commits globally by `sha` with no owner/repo scoping whatsoever [1](#0-0) . Nothing in the request pipeline enforces that `repository.owner.login` (the field whose value picks the signing secret) equals the owner embedded in `repository.full_name` (the field the handlers actually act on).

### Finding Description
Shipit explicitly supports multiple GitHub Apps, one per organization, each with its own `webhook_secret`, selected by `Shipit.github(organization: repository_owner)` [4](#0-3) . This is a documented, supported configuration (`docs/setup.md`, "Using Multiple Github Applications") [5](#0-4) .

Any attacker who owns/administers their own GitHub organization ("OrgA") can create and install their own GitHub App on that org if the Shipit instance they're targeting is configured to accept webhooks from multiple orgs (or, in a single-org deployment, simply omit/guess a null `webhook_secret`, which is optional per the setup docs). They know OrgA's `webhook_secret` because it's their own app. The equality the deployment trust model needs to hold is:

`organization used to verify HMAC (repository.owner.login)` == `organization/repository the handler mutates state for (repository.full_name, or commit sha owner)`

This equality is never checked. An attacker can craft a webhook body where:
- `repository.owner.login = "OrgA"` → `verify_signature` picks OrgA's webhook_secret, which the attacker knows and signs correctly.
- `repository.full_name = "OrgB/victim-repo"` (or, for the `status` event, simply any `sha` that happens to match a commit tracked in Shipit for a completely different stack) → the handler processes state changes against that unrelated repository/stack.

Because the signature check only proves "this body was signed by *someone's* configured webhook secret," not "signed by the secret belonging to the org whose data is being modified," a self-signed, fully attacker-controlled payload is treated as a legitimate event for a victim repository/stack.

The `status` handler is the sharpest instance of this: it has no repository scoping at all, matching purely on `Commit.where(sha: params.sha)` [1](#0-0) , then calls `commit.create_status_from_github!(params)`, which creates a `CommitStatus`/`Status` record used by `MergeRequest#all_status_checks_passed?` to gate the automatic merge queue [6](#0-5)  and `ProcessMergeRequestsJob` to trigger `merge_request.merge!` [7](#0-6) .

### Impact Explanation
By forging a `status` webhook event (signed with a secret the attacker legitimately owns for their own GitHub App/organization) that references the `sha` of an arbitrary commit sitting in Shipit's queue for a victim stack, an attacker can inject a fabricated `success` status for a required CI context. Because `all_status_checks_passed?` only checks locally stored `Status`/`CheckRun` rows, this forged status is indistinguishable from a real one and can cause `ProcessMergeRequestsJob` to call `merge_request.merge!`, triggering an **unauthorized merge** on a repository the attacker has no access to. The same owner/repository binding gap also lets an attacker trigger `GithubSyncJob`/`sync_github` for an unrelated stack via a forged `push` event, since `PushHandler` resolves stacks purely from `payload['repository']['full_name']` with no tie-back to the verified signer's organization [8](#0-7) . This satisfies the "unauthorized deploy, rollback or merge" Critical-impact criterion.

### Likelihood Explanation
Exploitation only requires the attacker to control any single GitHub organization/App (something an unprivileged internet user can trivially create for free) that happens to be one of the organizations configured in the target Shipit instance's `secrets.yml` `github` map, or to exploit a deployment where `webhook_secret` is left blank (explicitly shown as a supported/likely default in every example config in this repo, e.g. `webhook_secret: # nil`) [9](#0-8) . `repository.full_name`/target `sha` values for victim stacks are public GitHub information. No GitHub write access, Shipit session, or `ApiClient` token is required — only the ability to sign an HTTP POST with a webhook secret the attacker legitimately possesses for their own org.

### Recommendation
Bind the verified signer identity to the data being mutated: after `verify_signature` succeeds, pass the verified `repository_owner` (and ideally the whole verified `repository.full_name`) down to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and have every `Handler` (especially `StatusHandler`) reject/ignore payloads where the commit's/stack's actual owning repository does not match the organization whose secret validated the signature. At minimum, `StatusHandler#process` should scope `Commit.where(sha: params.sha)` by the repository resolved from the verified organization, mirroring `Handler#stacks`.

### Proof of Concept
1. Attacker registers their own GitHub organization `OrgA` and creates a GitHub App on it; the target Shipit instance is configured with a multi-org `github:` section that includes `OrgA` (or any deployment with `webhook_secret: nil`).
2. Attacker identifies a victim stack tracked by Shipit under `OrgB/victim-repo`, and a pending/required-status commit `sha` for a merge-queued PR on that stack (visible via GitHub's public API/UI).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "<required ci context>",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
   signed with `X-Hub-Signature: sha1=<hmac using OrgA's webhook_secret>`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature using the attacker's own secret [10](#0-9) .
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against the victim's commit (unrelated to OrgA) and creates a passing status record for it [1](#0-0) .
6. `ProcessMergeRequestsJob` subsequently observes `all_status_checks_passed?` and merges the victim PR, an unauthorized merge/deploy on a repository the attacker never had write access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

    github_config[github_organization]
  end
