## Analysis

Confirmed root cause: `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) resolves target `Commit` rows with a **global, unscoped query** — `Commit.where(sha: params.sha)` — with no repository/stack filter at all, even though the base `Handler` class provides a `repository_name`/`stacks` scoping mechanism (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that every other handler (`PushHandler`, `PullRequest::*`) uses. Meanwhile, `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30, 59-62`) picks the webhook secret using `repository_owner = params.dig('repository', 'owner', 'login')` taken directly from the untrusted JSON body, and this Shipit instance supports multiple onboarded organizations, each with its own `webhook_secret` (`config/secrets.development.shopify.yml:5-23`, `lib/shipit.rb:170-200`). ### Title
Cross-organization commit-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` — organization that authenticated ≠ repository whose commit is written - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
An operator of *any* organization onboarded to a shared Shipit instance can forge a GitHub `status` webhook, correctly signed with their own org's `webhook_secret`, and have it mark a commit belonging to a completely unrelated organization/repository as `success`. This breaks the binding: **organization that authenticated == repository/commit that is written**.

### Finding Description
`WebhooksController#verify_signature` selects which HMAC secret to validate against using `repository_owner`, itself read straight out of the unauthenticated JSON payload (`params.dig('repository', 'owner', 'login')`). Because this Shipit instance is multi-tenant (multiple `github:` orgs configured with independent `webhook_secret`s, per `Shipit.github_app_config`/`config/secrets.development.shopify.yml`), a person who legitimately controls the GitHub App/webhook for **their own** onboarded organization knows that org's own `webhook_secret` and can therefore self-sign an arbitrary POST body to `/webhooks` that passes `verify_signature`, as long as `repository.owner.login` in the body names their own org.

Once signature verification passes, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query has **no repository or stack scoping whatsoever** — unlike every other handler, which resolves the target via `Handler#repository_name`/`#stacks` (`payload.dig('repository', 'full_name')`). Consequently the attacker only needs to know a commit SHA belonging to a *victim* stack tracked anywhere on the shared instance (visible from GitHub's public commit history, PR pages, or the target org's own public Shipit deploy pages) and can post a forged `status` event naming that SHA with `state: "success"`, `context: <required-ci-context>`, signed with their own org's webhook secret. `Commit#create_status_from_github!` will attach that fabricated status to the victim's commit regardless of which organization actually owns it.

### Impact Explanation
`Commit#deployable?` and `Commit#status` (`app/models/shipit/commit.rb:219-229, 304-306`) drive whether a commit is treated as CI-green. A forged `success` status on a required CI context can satisfy `ci.require` gating and `stack.schedule_merges` (`app/models/shipit/commit.rb:383`) triggers, and combined with `continuous_deployment?` (`Commit#schedule_continuous_delivery`, lines 281-287) can cause an **unauthorized deploy or merge** of a commit in a repository the attacker never had write access to — this maps directly to the "unauthorized deploy, rollback or merge" Critical impact category. This is a direct structural analog of the report's inflation-attack root cause: a value from one trust domain (the authenticating organization) is used to unlock an action on state (`Commit`) belonging to a different, unverified domain, with no equality check enforced between the two.

### Likelihood Explanation
Requires only that (a) the Shipit instance is configured for multiple organizations (a documented, supported deployment mode — see `lib/shipit.rb#github_organizations`), and (b) the attacker legitimately administers the webhook/App for one of those organizations (an unprivileged role relative to other tenants' repositories) and can learn a target commit SHA (trivially public information for most CI/CD-integrated projects). No `ApiClient` token, GitHub App private key, or repository write access to the victim repo is required — this is a pure confused-deputy flaw within the engine's own webhook dispatch code.

### Recommendation
Scope `StatusHandler#process` the same way as every other handler: resolve `Repository`/`Stack` via `payload.dig('repository', 'full_name')` (using `stacks`/`repository_name` from the base `Handler`) and restrict the `Commit` lookup to `stacks.commits.where(sha: params.sha)` (or equivalent), rather than a global `Commit.where(sha:)`. Additionally, consider validating that `repository.full_name`'s owner segment matches the `repository.owner.login` used to select the webhook secret, to eliminate this entire class of cross-tenant confusion at the controller layer.

### Proof of Concept
1. Multi-tenant Shipit instance configured with two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` schema).
2. Attacker legitimately owns/administers the GitHub App for `attacker-org` and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker identifies a commit SHA `S` belonging to a stack tracked under `victim-org/some-repo` (visible publicly via GitHub or the victim's own Shipit UI), where `S` is required to have a `ci/tests` status of `success` before it can be deployed/merged.
4. Attacker crafts a JSON body:
   ```json
   {
     "sha": "S",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "attacker-org" } }
   }
   ```
5. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact body and POSTs it to `/webhooks` with header `X-Github-Event: status`.
6. `WebhooksController#verify_signature` looks up `attacker-org`'s secret (via `repository_owner`) and verification succeeds.
7. `StatusHandler#process` runs `Commit.where(sha: 'S')`, finds the commit under `victim-org/some-repo` (no repository check performed), and calls `create_status_from_github!`, recording a fabricated `success` status for the victim's required CI context — potentially unblocking merge/deploy for that commit.
