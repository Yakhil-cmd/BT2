## Finding: API client stack-scope bypass in `CCMenuController`

### Title
Stack-scoped API client can read the status of any stack via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports being restricted to a single stack via its `stack_id` column, and `Api::BaseController` enforces that scope for every API endpoint through the `stacks`/`stack` helper methods. `Api::CCMenuController` overrides `stack` with an unscoped lookup, breaking the binding between "the stack a token authorizes" and "the stack it actually touches" — exactly the class of bug described in the referenced report, where an entity is checked but the checked value is never enforced/locked at the point of use.

### Finding Description
`Api::BaseController` defines the authoritative scoping logic: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the client is scoped to one stack, and `stack` looks the requested `params[:stack_id]` up only within that restricted set. This is the mechanism that is supposed to guarantee a stack-scoped `ApiClient` can only ever "touch" the one stack it was authorized for — this is confirmed by an existing test asserting "an api client scoped to a stack will only see that one stack" [2](#0-1) .

`Api::CCMenuController`, however, defines its own `stack` method that performs an unscoped, global lookup, completely bypassing `current_api_client.stack_id`: [3](#0-2) 

It only checks `require_permission :read, :stack` (i.e., that the token has the `read:stack` permission string), which is a permission-name check, not a stack-identity check. Because `stack` no longer routes through `stacks`, any authenticated `ApiClient` holding `read:stack` — even one deliberately restricted at creation time to a single stack via `belongs_to :stack, optional: true` on the `ApiClient` model [4](#0-3)  — can pass an arbitrary `stack_id` in the request and receive that other stack's build/deploy status, including whether it is locked, its last build result, and identifying details, as rendered by `Api::CCMenuController#show` [5](#0-4) .

### Impact Explanation
This is an authorization-scope escalation: a credential that was deliberately restricted to authorize actions on one stack (`token authorizes stack A`) can be used to read state (`token touches stack B`) belonging to any other stack in the Shipit instance, including private/internal stacks the client was never granted access to. This matches the "unauthenticated [cross-boundary] read of stack state" high-impact category — the token holder gains visibility into deploy/lock status of stacks entirely outside its granted authorization scope, without any additional privilege.

### Likelihood Explanation
Any party who legitimately holds a stack-scoped `ApiClient` token with `read:stack` permission (the minimal, expected permission for this kind of integration — e.g. a CI dashboard or CCMenu client meant to see just their own stack) can immediately exploit this by simply changing the `stack_id` route/query parameter on requests to the CCMenu endpoint. No additional access, timing, or race condition is required — the check is unconditionally bypassed for every request to this controller.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and instead rely on `Api::BaseController#stack` (or explicitly re-apply the `stacks` scoping) so that the `stack_id` param lookup is always constrained to `current_api_client.stack_id` when the client is scoped, consistent with every other API controller.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only.
2. Using this client's `authentication_token`, call `GET /api/<stack_B_owner>/<stack_B_name>/<stack_B_env>/ccmenu.xml` (i.e., substitute Stack B's `to_param` for `stack_id`), authenticating via Basic Auth as shown in `Api::CCMenuControllerTest` [6](#0-5) .
3. Observe the response returns Stack B's `lastBuildStatus`/lock state, even though the client's `stack_id` only authorizes Stack A — because `Api::CCMenuController#stack` never checks `current_api_client.stack_id`.
