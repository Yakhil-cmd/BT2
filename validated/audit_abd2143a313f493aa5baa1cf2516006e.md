### Title
Webhook signature verified against attacker-chosen organization while handlers act on a different repository/organization in the payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a signature against using an **attacker-controlled** field of the unauthenticated JSON payload, while the handlers that actually mutate Shipit data (create teams/memberships, sync commits, update statuses) act on **different fields** of that same payload. If any configured organization has no `webhook_secret` set, signature verification for that organization is a no-op, letting an attacker forge webhook deliveries for stacks/teams belonging to other organizations.

### Finding Description
`repository_owner` — the value used to pick which app config (and thus which HMAC secret) verifies the request — is read straight from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

That organization is then used to fetch its `GitHubApp` and verify the HMAC: [3](#0-2) 

Critically, `verify_webhook_signature` **returns `true` unconditionally when `webhook_secret` is blank** (`return true unless webhook_secret`). Blank/nil `webhook_secret` is a documented, valid configuration state, as shown in the sample configs: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `create` dispatches the **entire raw JSON payload** to event handlers: [6](#0-5) 

Those handlers act on payload fields unrelated to `repository_owner` — e.g. the `:membership` event handler creates/deletes `Team` and `Membership` records straight from the `team`/`member` payload fields, and the `:push`/`:status` handlers act on `repository.full_name` / `sha` to locate the target `Stack`/`Commit`, as demonstrated by the controller's own tests: [7](#0-6) [8](#0-7) 

This is the binding the report's bug class describes: **organization that authenticated the request (`repository_owner` looked up for signature verification) ≠ repository/organization that is actually written to by the handlers (`repository.full_name`, `team`, `member` fields)**. Before the attack: a legitimate webhook has `repository.owner.login` equal to the actual target repo's owner, and its HMAC is checked against that owner's real secret. After the attacker's crafted request: `repository.owner.login`/`organization.login` is set to any configured org that happens to have `webhook_secret` unset (making `verify_signature` trivially pass), while `repository.full_name`, `team`, or `member` fields reference a completely different, protected organization's stack/team — and the handler processes them anyway since nothing re-checks that the verified organization matches the object being mutated.

### Impact Explanation
An unauthenticated attacker who knows (or guesses) that any one configured GitHub organization in the multi-tenant Shipit deployment has no `webhook_secret` configured can forge webhook deliveries claiming to originate from that organization while embedding payload content that targets a different, secret-protected organization's `Stack`, `Team`, or `Commit` records. Concretely this allows: creating arbitrary `Team`/`Membership` records that feed into `User#authorized?` and `Shipit.github_teams` authorization checks (privilege escalation into team-based authorization, listed as a High-severity impact), spoofing `commit_status`/`check_suite` events to mark otherwise-unreviewed commits as deployable, or injecting fabricated `push` events to enqueue sync jobs against arbitrary stacks — all without holding a Shipit session, API token, or the correct webhook secret for the targeted organization.

### Likelihood Explanation
Exploitability only requires that at least one org among the deployment's configured GitHub Apps has a blank `webhook_secret` (an explicitly supported, sample-documented configuration) and that the deployment hosts more than one organization/repository (the intended multi-tenant use case for `Shipit.github` keyed by organization). No credentials, sessions, or repository access are required — only an HTTP POST to the public `/github/webhooks` endpoint with a crafted JSON body.

### Recommendation
- Reject webhook payloads where `repository.owner.login`/`organization.login` differs from the organization actually referenced by the event's mutated resource (`repository.full_name` owner, `team.organization`, etc.).
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank for multi-tenant configurations; require an explicit "signature verification disabled" opt-in per organization instead of an implicit bypass.
- Add tests ensuring a webhook whose declared `repository_owner` differs from the organization owning the target stack/team is rejected even when one org has no secret configured.

### Proof of Concept
1. Deploy Shipit with two configured GitHub organizations: `OrgA` (no `webhook_secret` set) and `OrgB` (protected stacks/teams, secret unknown to attacker).
2. POST to `/github/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": {"login": "OrgA"},
  "team": {"id": 1, "name": "OrgB-Admins", "slug": "orgb-admins", "url": "https://example.com"},
  "member": {"login": "attacker"}
}
```
3. `verify_signature` resolves `repository_owner` to `OrgA`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/forged) `X-Hub-Signature` header.
4. `MembershipHandler` processes the payload and adds `attacker` to `OrgB-Admins`, a team belonging to the protected organization, escalating the attacker into `Shipit.github_teams`-gated authorization without ever proving knowledge of `OrgB`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
