### Title
Unauthenticated `membership` webhook bypasses signature verification and grants attacker-controlled GitHub logins `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The Jimbo exploit broke a binding between the price signal the protocol trusted and the price actually manipulable by an attacker. The analog here is a binding break between "the webhook whose HMAC signature was verified" and "the Team/User records actually mutated": `Shipit::WebhooksController#verify_signature` can be satisfied trivially (with no secret at all) whenever the targeted GitHub App's `webhook_secret` is unset, and the `membership` handler then unconditionally creates/grants `Team` membership from attacker-supplied JSON fields, feeding straight into `Shipit.github_teams` — the exact authorization gate that decides who may use the whole application.

### Finding Description
`WebhooksController#verify_signature` picks a GitHub App configuration purely from attacker-controlled JSON body fields and delegates the actual cryptographic check to it: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that App's `webhook_secret` is blank — a state the project's own setup documentation and example secrets files treat as a normal, supported configuration (`webhook_secret: # nil`): [3](#0-2) 

For any organization configured with no `webhook_secret`, this means the entire signature-verification step is a no-op: any anonymous client can POST an arbitrary JSON body with `X-Github-Event: membership` and have it processed as if it came from GitHub.

`MembershipHandler#process` then trusts that body completely — it creates a `Team` keyed off attacker-supplied `team.id`/`team.name`/`team.slug`/`organization.login`, resolves/creates a `User` from `member.login`, and directly adds that user to the team, with no scoping to any pre-existing repository, stack, or organization membership fact fetched from GitHub: [4](#0-3) 

Unlike `push`/`status`/`pull_request` handlers, which scope their effects to `Repository.from_github_repo_name(...)` records already known to Shipit, `MembershipHandler` has no such scoping — it can create brand-new `Team` records and mutate membership globally, and that global `Team` set is exactly what feeds `Shipit.github_teams`: [5](#0-4) 

which is the authorization boundary enforced on every request: [6](#0-5) 

Note that this same `force_github_authentication` code path also discloses the exact required team handles to any unauthenticated visitor in the 403 response body (`"You must be a member of #{team_list}..."`), as shown by the existing test expectation: [7](#0-6) 

Putting this together: (1) the binding the code verifies is "does this request carry a signature for *some org name found in this JSON body*" — which is either absent (blank secret) or, even when present for a *different* org than the one an attacker names, is decoupled from what the handler subsequently acts on; (2) the binding the `membership` handler acts on is "add this arbitrary GitHub login to this arbitrary team", with the team's identity/handle fully attacker-chosen and able to be crafted to match a handle disclosed by the app itself. The equality that is supposed to hold — *the organization whose webhook signature was cryptographically verified* == *the team/organization whose membership state is being mutated* — does not hold: the former can be trivially true (no secret) or attacker-selected, while the latter is unscoped and fully attacker-supplied.

### Impact Explanation
Successfully forging a `membership` `added` event lets an unprivileged, unauthenticated party add any real GitHub login (including their own account) to a `Team` whose `handle` matches one of the configured `Shipit.github_teams`. Because `force_github_authentication`/`current_user.authorized?` gate the entire engine on membership in `Shipit.github_teams`, this directly escalates an attacker's own GitHub identity into full authorization to use Shipit — including triggering deploys, rollbacks, and merges. This matches the explicitly in-scope High-impact category "escalation into `Shipit.github_teams` authorization," and can chain into Critical impact (unauthorized deploy/merge) once authorization is obtained.

### Likelihood Explanation
The precondition — at least one configured GitHub App/org with no `webhook_secret` — is presented throughout the project's own documentation and shipped example configs as a valid, non-degraded setup, so it is plausible in real deployments (particularly single-organization installs, which are the primary documented use case). No credential (`ApiClient` token, `webhook_secret`, `api_clients_secret`, GitHub App private key, repository write access, session) is required for the request itself. The attacker only needs a real GitHub login (their own) and the target team handle, which the application itself discloses in its 403 response. This makes the attack fully unprivileged and remotely exploitable.

### Recommendation
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank; require an explicitly configured secret for every organization, or reject/flag unsigned webhooks in production.
- Scope `MembershipHandler` (and any other handler that mutates authorization-relevant state) to the organization whose signature was actually validated, rather than trusting `organization.login`/`team.*`/`member.login` fields taken verbatim from the JSON body.
- Avoid disclosing configured team handles in unauthenticated error responses.

### Proof of Concept
Conceptually (assuming a Shipit instance where the configured GitHub App has no `webhook_secret`, as shown valid in `docs/setup.md` and `config/secrets.development.shopify.yml`):

```
POST /github/webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 999999, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "shopify"},
  "member": {"login": "attacker-controlled-real-github-login"}
}
```

Because no `X-Hub-Signature` check succeeds/matters (blank `webhook_secret`), `WebhooksController#create` dispatches this straight to `MembershipHandler#process`, which creates/looks up `Team` with handle `shopify/developers` (matching a handle disclosed via the 403 message shown in `test/controllers/repositories_controller_test.rb`) and adds the attacker's real GitHub login as a member — after which that GitHub account passes `current_user.authorized?` on subsequent OAuth login.

I was unable to directly inspect `app/models/shipit/team.rb` and `app/models/shipit/user.rb` (handle format and `authorized?` implementation) within the available iterations; the mechanics above are inferred from `lib/shipit.rb#github_teams`, `app/controllers/concerns/shipit/authentication.rb`, and existing test expectations, and should be verified against those files' exact logic before remediation.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
