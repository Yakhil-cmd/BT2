Based on the investigation, I found an analogous bug-class instance in `arbiters.js`.

### Title
Unsanitized peer-controlled address interpolated into ArbStore HTTP request path enables path/endpoint manipulation - (File: arbiters.js)

### Summary
`arbiters.getInfo()` builds an HTTP request path by directly string-concatenating a caller-supplied `address` value into a URL path template, exactly the bug class described in the LangGraph SDK advisory (unsanitized identifier interpolation into a URL path template that can redirect the request to an unintended resource).

### Finding Description
`arbiters.getInfo(address, cb)` fetches the ArbStore base URL from the hub and then issues a GET request to `url+'/api/arbiter/'+address` with no validation or encoding of `address`: [1](#0-0) 

```
requestInfoFromArbStore(url+'/api/arbiter/'+address, ...)
``` [2](#0-1) 

This `address` value is `objContract.arbiter_address`, which originates from an arbiter contract record. Arbiter contracts are populated both from local user input (`createAndSend`) and — critically — from data received from an untrusted peer device via `store()`, which persists whatever `arbiter_address` string a remote peer sends in an `arbiter_contract_offer`/`arbiter_contract_shared` message without validating it as a well-formed Obyte address: [3](#0-2) . The stored value is later read back via `getByHash` and passed straight into `arbiters.getInfo` from `openDispute()`: [4](#0-3) , and into `arbiters.getArbstoreInfo` from `deriveSharedAddress()`: [5](#0-4) , and `getArbstoreInfo` itself performs the same unsanitized concatenation for `/api/get_info`: [6](#0-5) .

No `ValidationUtils.isValidAddress()` check is applied to `arbiter_address` before it reaches the path-concatenation call sites in `arbiters.js`; the only place `isValidAddress` is checked on `arbiter_address`-adjacent data appears unrelated to this incoming-peer-message flow (search across `wallet.js` and `arbiter_contract.js` did not surface a check gating `store()`'s `arbiter_address` field before it's persisted and later used to build the ArbStore path).

### Impact Explanation
Because `address` is concatenated raw into the path segment of a same-origin HTTP request to the ArbStore server, a malicious contract counterparty can craft an `arbiter_address` string containing `/`, `..`, or query-string metacharacters. This can cause the wallet's request to be routed to a different ArbStore endpoint/resource than `/api/arbiter/<address>` or `/api/get_info` intends (e.g., diverting to an unrelated ArbStore API path or appending crafted query parameters), potentially causing the wallet to consume attacker-influenced ArbStore data (e.g., a spoofed `device_pub_key`, `real_name`, or `cut`/`address` fields cached in `arbStoreInfos`/`wallet_arbiters`). Since `arbStoreInfos` and `wallet_arbiters` data feed directly into shared-address definition construction (`deriveSharedAddress`), which determines fund-split conditions between contract parties and the arbstore, corruption of this information could influence AA/shared-address definitions used for payment splitting — creating potential fund misdirection risk if an attacker can control both the malicious `arbiter_address` value and force the request to reach a response they control.

### Likelihood Explanation
The `arbiter_address` value is attacker-controlled end-to-end when the contract is received from an untrusted device counterparty (`store()` accepts peer-originated `arbiter_address` and persists it directly). Exploitation requires the local wallet to subsequently call `openDispute`, `getAppealFee`, `appeal`, or `deriveSharedAddress` on that stored contract, which are normal user-triggered wallet flows once a contract is accepted — making this reachable without any privileged access, matching the "unprivileged... AA trigger sender / private-payment counterparty" reachability criterion.

### Recommendation
Validate `arbiter_address` (and any other identifier interpolated into ArbStore request paths, e.g. in `arbiter_contract.js`'s `httpRequest` calls) against `ValidationUtils.isValidAddress()` immediately upon receipt from a peer in `store()`/`handleReceivedSharedAddress`, and additionally apply `encodeURIComponent()` to any identifier before interpolating it into a URL path in `arbiters.js` (`getInfo`, `getArbstoreInfo`) and `arbiter_contract.js` (`httpRequest` path construction), consistent with the LangGraph SDK fix of path-segment-encoding identifiers before URL interpolation.

### Proof of Concept
1. Attacker (peer device) sends an `arbiter_contract_offer` / accepts and shares a contract with `arbiter_address` set to a crafted string such as `"VALIDADDR/../malicious_endpoint?x=1"` instead of a genuine 32-character address.
2. Victim's wallet calls `store()` on the received contract, persisting the malicious `arbiter_address` unchanged: [3](#0-2) .
3. Victim later calls `openDispute()` or `arbiter_contract.appeal()`, which internally calls `arbiters.getInfo(objContract.arbiter_address, ...)`: [7](#0-6) .
4. `arbiters.getInfo` issues `requestInfoFromArbStore(url + '/api/arbiter/' + address, ...)` with the unsanitized value, sending the request to an unintended path on the ArbStore host: [8](#0-7) .
