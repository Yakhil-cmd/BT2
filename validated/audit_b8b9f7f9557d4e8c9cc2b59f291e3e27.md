### Title
`review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning modes due to missing parentheses in `provision?` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with `&&`/`||` such that the master toggle only gates the `allow_all` behavior; the `allow_with_label` and `prevent_with_label` branches evaluate independently of `review_stacks_enabled`. A repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` will still auto-provision a review stack for any PR carrying the configured label.

### Finding Description
The intended binding, per the settings UI copy ("Dynamically provision stacks for Pull Requests?"), is that `repository.review_stacks_enabled == true` must hold for *any* dynamic provisioning to occur, i.e. `provision? => review_stacks_enabled == true`, regardless of `provisioning_behavior`. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` is only ANDed into the first disjunct; the second and third disjuncts are evaluated with no reference to `review_stacks_enabled` at all. The settings view text confirms the intended semantics — the checkbox is described as the overall enable/disable switch for dynamic provisioning, with `provisioning_behavior` merely refining *how* provisioning occurs, not whether the master switch is bypassed: [2](#0-1) 

Exploit flow: attacker opens a `pull_request opened` webhook (or triggers one legitimately by opening a real PR) against a tracked repository whose owner has `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, with the PR carrying the repo's `provisioning_label_name` label. `respond_to_pull_request_opened?` calls `provision?`, which returns `true` via the second disjunct even though `review_stacks_enabled` is `false`, and `process` proceeds to `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, provisioning a stack keyed on `params.pull_request.head.ref` — the attacker-controlled branch.

The existing regression test suite tests `review_stacks_enabled: false` only in combination with `allow_all` behavior (asserting no stack is created), and separately tests `allow_with_label`/`prevent_with_label` only with the default `provisioning_enabled: true`. No test exercises the `review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label` combination, so this divergence is untested and unguarded: [3](#0-2) [4](#0-3) [5](#0-4) 

None of the standard guards (`verify_signature`, `respond_to_pull_request_opened?`'s action check, `ExplicitParameters` schema, model validations on `Repository`) address this — they validate webhook authenticity and payload shape but not this authorization-logic error.

### Impact Explanation
Any repository owner who sets `review_stacks_enabled: false` (opting out of dynamic PR provisioning) while leaving `provisioning_behavior` at `allow_with_label` or `prevent_with_label` (the enum default order suggests these are plausible non-default configurations) will still have review stacks auto-created and queued for provisioning from PR branches, including forks/PRs from unprivileged contributors who can label their own PR. This is an unauthorized-provisioning bug: a security control the repository owner believes is off (`review_stacks_enabled = false`) is silently ignored for two of three configuration modes, resulting in attacker/contributor-controlled branches being deployed onto Shipit infrastructure. This matches the "unauthorized deploy" / provisioning-of-attacker-controlled-code impact category.

### Likelihood Explanation
Requires a real, Shipit-tracked repository configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`. For `allow_with_label`, the attacker additionally needs to get the configured label applied to their PR (label name is operator-configured, often a common default like "deploy" — plausible to guess or discover from repo label lists). For `prevent_with_label`, no label at all is needed — provisioning occurs by default in this misconfiguration since `review_stacks_enabled` is not checked, only the label needs to be *absent*, which is the default state of any new PR. This makes `prevent_with_label` combined with `review_stacks_enabled: false` trivially and repeatably exploitable by any user able to open a PR, with zero extra effort. The only dependency is repository misconfiguration, which is plausible given the code bug makes `review_stacks_enabled: false` behave unexpectedly.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three behavior branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Add regression tests covering `review_stacks_enabled: false` combined with each `provisioning_behavior` value.

### Proof of Concept
Minitest plan for `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # binding under test: review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # label absent -> prevent_with_label clause would provision

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not create stacks when review_stacks_enabled is false, even with allow_with_label and label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # binding under test: review_stacks_enabled == false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Both assertions currently fail against the existing code (a `Shipit::Stack`/`Shipit::ReviewStack` is created despite `review_stacks_enabled == false`), demonstrating the broken binding `review_stacks_enabled == true` is not enforced for these two provisioning behaviors.
