### Title
Organization authenticated by `WebhooksController#verify_signature` does not bind to the repository acted on by event handlers, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a payload against using `repository.owner.login` (or `organization.login`), while the event handlers that execute the webhook's side effects (e.g. `Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, etc.) resolve the target `Stack`/`Repository` using a *different* field of the same payload: `repository.full_name`. Nothing ties these two fields together, so an attacker who legitimately controls the webhook secret for one organization onboarded into a multi-tenant Shipit instance can forge a signed payload whose `repository.owner.login` names their own org (so signature verification passes) while `repository.full_name` names a victim organization's repository, causing Shipit to execute the handler's write against the victim's stack.

### Finding Description
`verify_signature` picks the credential used to validate the HMAC based on a field taken from the *untrusted, attacker-supplied* JSON body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature itself is a valid HMAC over the *entire* raw body using the secret belonging to whichever organization `repository_owner` names — it does not cryptographically bind the signature to a specific repository being acted on, only to "some org's secret was used to sign this exact byte string."

Once the signature check passes, `create` dispatches the payload to handlers: [3](#0-2) 

Those handlers determine which `Stack`/`Repository` to act on from a *different* payload field: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

For example `PushHandler` triggers a GitHub sync on any stack matching `repository.full_name` and the pushed branch: [5](#0-4) 

and `StatusHandler`/commit-status handling creates a `Status` record for a commit resolved only by SHA, with attacker-controlled `state`/`description`/`target_url`/`context`, as exercised in the test suite (`":state create a Status for the specific commit"`): [6](#0-5) 

**Binding broken:** organization authenticated by `verify_signature` (`repository.owner.login` / `organization.login`) ≠ repository whose `Stack` is written by the handler (`repository.full_name`). Before the attack: `repository.owner.login == owner_of(repository.full_name)` for every legitimate GitHub-originated payload. After a forged request: `repository.owner.login` (attacker's own org, whose secret they legitimately hold) while `repository.full_name` names an arbitrary victim org/repo whose stacks live in the same Shipit instance.

### Impact Explanation
This is only exploitable in a multi-tenant Shipit deployment where more than one GitHub organization is configured (each with its own `webhook_secret` via `Shipit.github(organization:)`), and the attacker is a legitimate administrator of one such organization's GitHub App installation — they never need a Shipit session, `ApiClient` token, or the victim's `webhook_secret`. Once exploited, they can drive any webhook-triggered side effect (`push`, `status`, `check_suite`, `pull_request`, `membership`) against a victim stack they do not otherwise control, including forging `Status` records (state/description/target_url/context) for arbitrary commit SHAs in the victim's stack. Because deploy eligibility and continuous-deployment logic in this engine consult required/blocking CI statuses, this can be used to make an already-merged victim commit appear CI-green, potentially triggering an unauthorized/continuous deploy of that commit — meeting the Critical "unauthorized deploy" bar defined in scope.

### Likelihood Explanation
Requires a specific precondition (multiple GitHub orgs configured on one Shipit instance) that may not be universal, but where present the attack requires nothing beyond crafting one HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses — no privileged Shipit credential, session, or social engineering is needed. This is comparable in likelihood/severity structure to the referenced SurplusGuildMinter finding: a validation performed against the wrong reference value creates a straightforward, unprivileged bypass.

### Recommendation
Bind the webhook signature/authorization to the exact repository/stack being written, not to a caller-controlled sibling field. Concretely: after verifying the signature with the organization's secret, re-derive/require that `repository.full_name`'s owner equals the `repository_owner` used for signature verification (or, more robustly, verify the payload per-repository rather than per-organization, and reject any event whose `repository.full_name` owner does not match the org whose secret validated the signature).

### Proof of Concept
Conceptual PoC (cannot be executed without a live multi-org Shipit instance to confirm end-to-end, but derivable purely from the code paths cited above):
1. Configure/attacker-control GitHub App + webhook secret for org `attacker-org`, onboarded into the same Shipit instance that also hosts stacks for `victim-org/victim-repo`.
2. Craft webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/travis",
     "target_url": "https://example.com",
     "description": "forged"
   }
   ```
3. Sign the raw body with `attacker-org`'s known `webhook_secret` (`sha1=` HMAC), set `X-Github-Event: status`, POST to `/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the attacker's own valid signature.
5. `Shipit::Webhooks.for_event('status')` handler resolves stacks via `repository_name` = `"victim-org/victim-repo"` (the `full_name` field), and creates/updates a `Status` on the victim's commit, unrelated to the `attacker-org` credential that authenticated the request.
