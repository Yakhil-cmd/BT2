### Title
Webhook Authentication Bypass via Per-Organization Nil `webhook_secret` Combined with Mismatched Repository-Selector Fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit's `/webhooks` endpoint selects *which* GitHub App/organization's secret to use for HMAC verification from one JSON field (`repository.owner.login` / `organization.login`), while every webhook `Handler` resolves the *stack/repository to act on* from a completely different field (`repository.full_name`). Because Shipit's own documented multi-org configuration allows any individual organization to be configured with `webhook_secret: nil`, and `GitHubApp#verify_webhook_signature` unconditionally treats a blank secret as "verified," an unauthenticated internet attacker can trivially satisfy the org-selection field with a secret-less org while pointing the actually-processed data at an arbitrary victim repository/stack.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for signature verification purely from attacker-controlled JSON, before any cryptographic check happens: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` bypasses verification entirely whenever that organization's secret is blank: [3](#0-2) 

Shipit's own supported/documented configuration schema explicitly allows configuring multiple GitHub organizations, each with an independent, optionally-nil `webhook_secret`: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature` (trivially, for the org with a nil secret), the shared `Handler` base class — used by every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, etc.) — resolves the repository/stack to operate on from an entirely different, independently attacker-controlled field: [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository the handler subsequently mutates`

The code breaks this equality because `repository_owner` (`repository.owner.login` / `organization.login`) and `repository_name` (`repository.full_name`) are two unrelated, independently attacker-settable JSON keys within the same unsigned-or-trivially-signed payload. An attacker who knows (or is told, since it can be `nil` by design) that org `"OrgWithoutSecret"` has no `webhook_secret` configured can submit:

```json
{
  "repository": { "owner": { "login": "OrgWithoutSecret" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
with `X-Github-Event: push` and any (or no) `X-Hub-Signature`. `verify_signature` calls `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` immediately — no signature is actually checked. `PushHandler` then resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")`, a repository belonging to a completely different (fully protected, secret-bearing) organization, and queues a sync using attacker-supplied `after` (SHA). The same base-class field mismatch is inherited by `StatusHandler`, letting an attacker forge a `status` event for arbitrary commits of `victim-org/victim-repo` (state, description, target_url are attacker-controlled), independent of the org whose secret was checked.

### Impact Explanation
This crosses the "unauthorized deploy" and "cross-repository writes" impact bar:
- Forged `status` webhooks let an attacker mark arbitrary commits of any tracked repository as passing CI (`ci.require`), even though no real CI ran and no legitimate credential/session was used.
- For stacks configured with `continuous_deployment: true`, satisfying required statuses via this forged webhook can trigger an automatic, unauthorized deploy without any Shipit session, `ApiClient` token, or GitHub write access — solely through the public `/webhooks` endpoint.
- More generally, this breaks repository isolation between distinct GitHub organizations configured on the same Shipit instance: authentication material scoped to one org effectively authorizes writes against any other org's repositories/stacks tracked by Shipit.

### Likelihood Explanation
Reachable by any unauthenticated network attacker who can reach `/webhooks` (explicitly documented as a public endpoint: `<homepage>/webhooks`), requiring only that the Shipit deployment (a) tracks more than one GitHub organization (an officially supported/documented configuration) and (b) leaves `webhook_secret` unset for at least one of them — itself a documented, valid configuration value (`webhook_secret: # nil`). No session, API token, or GitHub credentials are required.

### Recommendation
Verify the webhook signature using the secret of the organization that actually owns `repository.full_name` (or `organization.login` used by the handler), not a separately-attacker-chosen field, and ensure `verify_webhook_signature` treats a missing/blank secret as "verification required and failing" rather than "verification skipped," at least when multiple organizations are configured. Cross-check that `repository.owner.login` (or `organization.login`) is consistent with `repository.full_name`'s owner segment before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs per the documented multi-org schema: `VictimOrg` (with a real `webhook_secret`) tracking `victim-org/victim-repo`, and `AttackerOrg` (with `webhook_secret: nil`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "description": "forged"
}
```
3. `verify_signature` selects `Shipit.github(organization: "AttackerOrg")`, whose blank `webhook_secret` causes `verify_webhook_signature` to return `true` unconditionally (`lib/shipit/github_app.rb:76-83`).
4. `StatusHandler` (via the shared `Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) resolves the stack/commit from `repository.full_name` = `"victim-org/victim-repo"`, and records the forged "success" status against that commit — despite the request never having been authenticated for `VictimOrg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
