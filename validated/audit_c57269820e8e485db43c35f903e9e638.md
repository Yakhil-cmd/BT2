### Title
Webhook organization used for signature verification is not bound to the repository/stack the handler acts on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App's `webhook_secret` to verify an inbound webhook against using an organization name pulled straight out of the untrusted, not-yet-verified JSON body, rather than from any value already bound to a specific installation. Every downstream webhook handler (e.g. `PushHandler`) subsequently acts on the repository identified elsewhere in that same untrusted body. Nothing forces the "organization whose secret cryptographically authenticated this delivery" to equal "the organization/repository that the handler actually mutates," which is the exact class of binding break called out in the rules ("an organization that authenticated versus the repository that is written").

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unauthenticated payload: [1](#0-0) 

and uses that attacker-controlled value to pick the `GitHubApp` instance (and therefore the `webhook_secret`) that the HMAC is checked against: [2](#0-1) 

`Shipit.github(organization:)` looks the config up by exactly that string: [3](#0-2) 

This is the documented multi-organization schema, where each organization gets its own App/secret: [4](#0-3) 

Once the signature passes (i.e., it was HMAC'd with *some* configured organization's secret), the event is dispatched to handlers such as `PushHandler`, which resolves and mutates `Stack`s using repository fields taken from the same payload independently of the `repository.owner.login` value used purely for secret selection: [5](#0-4) 

Because the equality "organization that authenticated the delivery" == "organization/repository the handler writes to" is never explicitly checked anywhere in `WebhooksController` or `Handler`, an operator running Shipit for multiple organizations (a documented, supported configuration) has no code-level guarantee that a payload verified with org-A's `webhook_secret` is actually describing an org-A repository. If the handler's repository resolution (in the `Handler` base class, not fully inspected due to tool-call limits) derives the target `Stack`/`Repository` from a payload sub-field (e.g. `repository.full_name` or `repository.name`) that is not re-derived from the same `repository.owner.login` used for secret selection, an attacker who legitimately possesses org-A's `webhook_secret` (e.g., as an org-A GitHub App owner/admin — not a credential for org-B) can forge a payload that authenticates as org-A but whose repository/ref fields target an org-B stack, triggering `stack.sync_github(expected_head_sha: ...)` and downstream continuous-deployment behavior for a repository they do not control.

### Impact Explanation
If exploitable as described, this breaks the deployment-trust binding between "which org's webhook credential signed this request" and "which org's stacks get mutated," enabling a webhook holder for one organization to force GitHub sync / deploy-triggering actions (`sync_github`, continuous deployment) against a different organization's stack — i.e., unauthorized cross-organization write/deploy triggering without possessing that organization's own webhook secret, GitHub App credentials, or repository access. This falls under the Critical "cross-repository writes / unauthorized deploy" category if the `Handler` base class indeed resolves the acted-upon repository from a field independent of `repository.owner.login`.

### Likelihood Explanation
This only matters for deployments using the multi-organization `secrets.github` schema (organizations as top-level keys) — the default/most common single-org schema is unaffected because there `github_default_organization` is `nil` and only one secret exists (`lib/shipit.rb:170-181`). Within multi-org deployments, exploitability hinges entirely on how the `Handler` base class (not retrievable within the available tool budget) resolves the target repository/stack from the payload — specifically, whether it re-derives the owner from `repository.owner.login` (in which case this is not exploitable, since the two fields would have to agree) or from an independent field such as `repository.full_name`/`repository.name` (in which case it is directly exploitable). I could not confirm this file's contents before running out of iterations, so likelihood is uncertain and requires verification of `app/models/shipit/webhooks/handlers/handler.rb`.

### Recommendation
Before dispatching any webhook to handlers, re-verify that the repository/organization referenced by every field the handlers will act on (`repository.full_name`, `repository.name`, `repository.owner.login`) are mutually consistent, and bind the signature-selected organization explicitly to the specific `Repository`/`Stack` records touched, rather than trusting independent sub-fields of the same unauthenticated JSON body.

### Proof of Concept
Not executable — this finding is contingent on the repository-resolution logic in `app/models/shipit/webhooks/handlers/handler.rb`, which could not be retrieved within the remaining tool-call budget. A concrete PoC would require confirming that this base class resolves the target `Stack`/`Repository` from a payload field independent of `repository.owner.login`; if confirmed, the PoC is: craft a `push` webhook body with `repository.owner.login = "org-A"` (attacker's own org, whose `webhook_secret` the attacker legitimately holds) but `repository.full_name`/`repository.name` referencing an `org-B` stack, sign it with org-A's `webhook_secret`, and POST it to `/webhooks` to trigger `sync_github` on the org-B stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
