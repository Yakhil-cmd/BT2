### Title
Cross-Site State Mutation via GET `stacks#refresh` + `SameSite=None` Session Cookie - ([File: lib/shipit/same_site_cookie_middleware.rb])

### Summary
`config/routes.rb` explicitly maps `refresh` to a bare `GET` verb (`get :refresh, controller: :stacks # For easier design, sorry :/`) in addition to `POST`, and `StacksController#refresh` performs the state-mutating `RefreshStatusesJob`/`RefreshCheckRunsJob`/`GithubSyncJob` enqueue with no additional authorization check beyond the standard session-based `current_user`. Because `Shipit::SameSiteCookieMiddleware#call` unconditionally appends `; SameSite=None` (plus `; Secure`) to every `Set-Cookie` header on SSL responses whenever the middleware is enabled, the Shipit session cookie set by `GithubAuthenticationController#callback` is sent cross-site by the victim's browser, letting a third-party page trigger the authenticated GET and enqueue jobs as the victim.

### Finding Description
The binding claimed broken: "the session cookie attached to a state-changing GET request == a cookie that Rails' CSRF protection actually validated." This is false for `stacks#refresh` reached via GET.

- `ShipitController` sets `protect_from_forgery with: :exception` [1](#0-0) . Rails' default forgery protection only guards non-GET request methods; GET requests never require or validate an authenticity token.
- `config/routes.rb` maps `refresh` twice, once via POST and once via bare GET, with the comment acknowledging the deliberate but risky choice: [2](#0-1) .
- `StacksController#refresh` enqueues `RefreshStatusesJob`, `RefreshCheckRunsJob`, and `GithubSyncJob` (with `force_spec_cache: true`) purely based on `@stack` loaded via `load_stack`, with authorization gated only by `force_github_authentication`/`current_user.authorized?` from the `Shipit::Authentication` concern [3](#0-2) .
- `Shipit::Authentication#force_github_authentication` and `#current_user` rely entirely on `session[:user_id]` [4](#0-3) , i.e., whichever session cookie the browser attaches to the request is trusted as the identity, with no separate CSRF-token check for GET.
- `Shipit::SameSiteCookieMiddleware#call` appends `SameSite=None` to *every* `Set-Cookie` header on any SSL response, unconditionally, once `Shipit.enable_samesite_middleware?` is enabled [5](#0-4) . This includes the Rails session cookie set after `GithubAuthenticationController#callback` populates `session[:user_id]`/`session[:authenticated]`.

Exploit flow: an attacker hosts a page (or gets a victim to view one) containing `<img src="https://shipit.example/<owner>/<repo>/<env>/refresh">`. Because the cookie carries `SameSite=None; Secure`, the browser attaches the victim's Shipit session cookie to this cross-site GET. `force_github_authentication` sees `current_user.logged_in?` and `authorized?` are true (using the victim's session), and `StacksController#refresh` runs unconditionally, enqueuing `GithubSyncJob`/`RefreshStatusesJob`/`RefreshCheckRunsJob` for that stack — no authenticity token is required because GET bypasses `protect_from_forgery`.

Existing guards do not close this gap: `protect_from_forgery with: :exception` only applies to non-GET verbs by Rails default; there is no `verify_authenticity_token` override forcing GET checks; `require_permission!`/`ExplicitParameters` guard the JSON `Api::StacksController`, not the HTML `StacksController`; and `SameSiteCookieMiddleware` has no cookie-name allowlist or `Strict`/`Lax` exception for the session cookie.

### Impact Explanation
This lets an attacker force a logged-in Shipit operator's browser to trigger `RefreshStatusesJob`, `RefreshCheckRunsJob`, and `GithubSyncJob.perform_later(stack_id:, force_spec_cache: true)` for any stack the attacker can address by owner/repo/env in the URL, riding the victim's session with no consent or CSRF token. This is a genuine state-mutating action taken on behalf of an authenticated user without their explicit action, matching the "unauthorized ... deploy" adjacent High-severity category (forced state mutation via CSRF), though it is not itself an RCE, credential leak, or a deploy/rollback/merge — the `refresh` action only re-syncs status/commit data and cache, it does not deploy, rollback, or merge. The blast radius is limited to whichever stacks the victim operator has read access to and can be addressed by path, repeatable per request against any stack visible to the browser.

### Likelihood Explanation
Preconditions: (1) `Shipit.enable_samesite_middleware?` must be true in the app configuration (not default-on; this is an opt-in via `lib/shipit/engine.rb`), (2) the victim must have an active Shipit session and visit an attacker-controlled page while authenticated, (3) the attacker must know or guess the `owner/repo/environment` path. No secrets, tokens, or GitHub privileges are required, and the attacker does not need to be logged into Shipit. The cost is low (a single crafted URL/image tag), and it is trivially repeatable across different stacks by changing the path segment.

### Recommendation
Remove the `get :refresh, controller: :stacks` route in `config/routes.rb` and require POST only for this state-changing action; alternatively, explicitly verify the authenticity token for GET-based state changes, or convert `refresh` to require an unguessable per-request token. Independently, scope `SameSiteCookieMiddleware` to skip or use `SameSite=Lax`/`Strict` for the Shipit session cookie specifically, rather than blanket `SameSite=None` on all cookies.

### Proof of Concept
```ruby
# test/middleware/same_site_cookie_middleware_test.rb (extend existing suite)
test "appends SameSite=None to the Shipit session cookie over SSL" do
  app = lambda do |_env|
    [200, { 'Set-Cookie' => "_shipit_session=abc123; path=/; HttpOnly" }, ['ok']]
  end
  middleware = Shipit::SameSiteCookieMiddleware.new(app)
  env = Rack::MockRequest.env_for('https://shipit.example/', 'HTTPS' => 'on')
  _status, headers, _body = middleware.call(env)
  assert_match(/_shipit_session=abc123.*SameSite=None/i, headers['Set-Cookie'])
end

# test/controllers/stacks_controller_test.rb (extend existing suite)
test "#refresh is reachable via bare GET with no authenticity token, riding only the session cookie" do
  session[:user_id] = shipit_users(:walrus).id # simulate attacker-forced cross-site GET carrying victim's session cookie
  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @stack.id, force_spec_cache: true]) do
    get :refresh, params: { id: @stack.to_param } # no authenticity_token param supplied
  end
  assert_response :redirect # succeeds without CSRF check, unlike POST/PATCH/DELETE actions
end
```
Both sides of the equality diverge: the cookie carries `SameSite=None` (browser will attach it cross-site) while the GET request that consumes it performs a state mutation without any CSRF-token validation, confirming the binding is broken as claimed.

    def refresh
      RefreshStatusesJob.perform_later(stack_id: @stack.id)
      RefreshCheckRunsJob.perform_later(stack_id: @stack.id)
      # force_spec_cache: explicit refreshes always recompute the cached deploy
      # spec, even when the head hasn't moved: refreshing is how a stale or
      # broken cached spec is fixed. Threading it through the sync job (rather
      # than enqueuing CacheDeploySpecJob directly) guarantees the spec is
      # computed from the post-sync head.
      GithubSyncJob.perform_later(stack_id: @stack.id, force_spec_cache: true)
      flash[:success] = 'Refresh scheduled'
      redirect_to(request.referer.presence || stack_path(@stack))
    end

    def call(env)
      status, headers, body = @app.call(env)

      if headers && headers['Set-Cookie'] &&
         Rack::Request.new(env).ssl?

        set_cookies = headers['Set-Cookie'].split(COOKIE_SEPARATOR).compact
        set_cookies.map! do |cookie|
          cookie << '; Secure' if cookie !~ /;\s*secure/i
          cookie << '; SameSite=None' unless cookie.match?(/;\s*samesite=/i)
          cookie
        end

        headers['Set-Cookie'] = set_cookies.join(COOKIE_SEPARATOR)
      end
