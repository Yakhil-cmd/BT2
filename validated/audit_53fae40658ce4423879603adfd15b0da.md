I have enough evidence to answer now. The confirmed root cause is at `aa_composer.js` `handleSecondaryTriggers`: when a primary AA's response unit pays multiple recipient addresses in one trigger and one of those recipients is itself an AA that bounces during its secondary trigger, the whole primary AA execution (all its state changes and all its other payments to other, unrelated recipients in the same unit) is reverted via `revert()`.

### Title
Single malicious/failing recipient AA can DoS an entire multi-recipient AA payout, reverting all other legitimate payments in the batch - (File: aa_composer.js)

### Summary
In `handleTrigger`'s `sendUnit`/`handleSecondaryTriggers` flow, when an AA response unit contains payment outputs to several different addresses and one of those addresses is itself an Autonomous Agent (AA), the recipient AA is triggered as a "secondary trigger." If that secondary AA bounces for any reason, the caller does not isolate the failure to that single recipient — it reverts the entire primary AA's execution, undoing all of its state changes and every other output in the same response unit, including payments to unrelated, well-behaved recipients.

### Finding Description
`handleSecondaryTriggers` iterates over all output addresses of the just-composed unit that happen to be AA addresses and recursively calls `handleTrigger` for each with `bSecondary = true`: [1](#0-0) 

The completion callback of this `async.eachSeries` treats *any* error from *any* of the secondary AAs as fatal to the whole primary response, calling `revert()`: [2](#0-1) 

`revert()` then rolls back all of the primary AA's saved state variables, forgets the response units already generated in this trigger's chain, restores balances, and issues a ROLLBACK to the savepoint before finally bouncing the primary trigger: [3](#0-2) 

This is directly analogous to the reported Gitcoin QF bug class: a single payment recipient that is guaranteed/designed to fail (there, a contract that rejects Ether; here, an AA definition that always calls `bounce(...)`) causes the entire batch of payments/state updates initiated by one trigger to fail, even though the failure has nothing to do with the other, independent recipients in the same unit. Any AA design that fans out payments to multiple addresses supplied or influenced by external/untrusted parties (e.g., a multi-recipient payout, matching-funds distribution, or "send to whichever AA the caller names" pattern as seen in `test/samples/fundraising_proxy.oscript`'s `$destination_aa` forwarding) is vulnerable: an attacker can deploy a trivial "always bounce" AA definition and get it added as one of the recipients (or as a chained/forwarding target) to force the entire trigger's payout — including payments meant for unrelated, honest recipients — to be reverted every time.

Note that a **primary** trigger to the same address in the same unit is blocked by the "second primary trigger not allowed" check, but nothing similarly restricts an attacker from being one of several **secondary** recipients targeted by another AA's outputs, which is exactly the pattern exploited here.

### Impact Explanation
Any AA logic that pays out to a set of addresses in a single response (state changes + payment) is subject to complete denial of service if even one of the recipient addresses is (or later becomes) an AA that always bounces. This can:
- Freeze funds/state changes intended for legitimate, unrelated recipients in the same trigger, because the entire unit (and its state var changes) is rolled back with `revert()`.
- Be weaponized by an attacker who controls or can influence one of the payout addresses (e.g. in a crowdfunding/matching/voting-style AA where destination AAs are configurable or attacker-supplied) to repeatedly force reverts, preventing the AA from ever completing that class of trigger.
- Cause repeated resource-wasting bounces at the primary trigger's expense (bounce fees), while permanently starving other recipients of intended funds/state updates.

This matches the High-severity impact criteria: AA fund loss/freezing and a class of triggers becoming permanently unconfirmable/unusable for the affected AA.

### Likelihood Explanation
Likelihood is high in any composed-AA system where recipient addresses are attacker-influenced, dynamic, or simply chosen from an open set (as in the `fundraising_proxy.oscript` sample forwarding to `$destination_aa`, or any voting/grants-style AA that forwards funds to arbitrary AA addresses supplied by users). Creating an "always bounce" AA is trivial — it requires only a one-line `getters`/`init` formula calling `bounce(...)`. No special privileges are needed: posting a unit that triggers the vulnerable AA with the attacker's AA as one of the intended payees is sufficient.

### Recommendation
Do not let a single secondary AA's bounce revert the entire primary trigger's already-computed outputs/state changes. Options:
- Isolate secondary-trigger failures: when a secondary AA in `handleSecondaryTriggers` bounces, only account for/undo the effects attributable to that one recipient (e.g., leave the coins in that recipient's regular non-AA balance / treat it as a normal address) rather than calling `revert()` on the whole primary chain.
- Alternatively, document this clearly as an intentional "all-or-nothing" semantics of AA-to-AA composition and require AA authors to avoid sending funds to arbitrary/attacker-controlled AA addresses in the same unit as payments to other trusted recipients, or to split such payouts into separate independent trigger units so failure of one payee cannot roll back the others.

### Proof of Concept
1. Deploy `always_bounce_aa`:
```
['autonomous agent', {
  messages: [{ app: 'state', state: `{ bounce('nope'); }` }]
}]
```
2. Deploy `payout_aa` whose response, for a single trigger, pays two addresses: `always_bounce_aa` and a normal, unrelated recipient `victim_address`, plus a state var update, e.g.
```
messages: [
  { app: 'payment', payload: { asset: 'base', outputs: [
      { address: "{always_bounce_aa}", amount: 1000 },
      { address: "{victim_address}", amount: 1000 }
  ]}},
  { app: 'state', state: `{ var['done']=1; }` }
]
```
3. Trigger `payout_aa`. Following `sendUnit` → `handleSecondaryTriggers`, `always_bounce_aa` bounces, causing the `async.eachSeries` completion handler at [4](#0-3)  to call `revert()`. This unwinds `payout_aa`'s state var `done` and its payment to `victim_address`, even though `victim_address` had nothing to do with the failure, and `payout_aa`'s trigger ends up bounced (see `revert()` at [3](#0-2) ).
