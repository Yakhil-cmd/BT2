### Title
Cross-repository authentication bypass via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by raw `sha` alone and never checks that the `repository`/`organization` named in the payload (the value used to select the `webhook_secret` for signature verification) actually owns the matched commit. Because `Commit.where(sha: params.sha)` is global across every Stack/repository stored in Shipit, a webhook whose signature was verified against Repository A's `webhook_secret` can still create a `Status` on a commit that belongs to Repository C's Stack, as long as the attacker supplies a `sha` value that exists in Repository C's `commits` table (git commit shas are not secret — they are publicly observable in GitHub/Shipit UIs, URLs, and commit histories).

### Finding Description
The binding the code is supposed to enforce is:
`organization_that_signed_request (repository_owner from payload, used in Shipit.github(organization:)) == organization_that_owns_the_mutated_Stack/Commit`

Tracing the path:
1. `WebhooksController#verify_signature` derives `repository_owner` purely from `params.dig('repository','owner','login')` (attacker-controlled JSON) and picks a `GitHubApp` instance keyed on that organization name to verify the HMAC signature against that org's `webhook_secret`. [1](#0-0)  and [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` only HMACs the raw body against that org's secret — it has no knowledge of, or binding to, which `sha`/commit/stack the payload will end up mutating. [3](#0-2) 
3. `WebhooksController#create` then dispatches the *entire* raw JSON to `Shipit::Webhooks.for_event(event)` handlers, `StatusHandler` included. [4](#0-3) 
4. `StatusHandler`'s `ExplicitParameters` schema only requires `:sha` and `:state` — `repository` is never required, never read, never checked. [5](#0-4) 
5. `StatusHandler#process` resolves target commits with a bare, global `Commit.where(sha: params.sha)` — no `joins(:stack)` filter tying the result to the organization/repository that supplied the signature. Each matched commit — regardless of which Stack/repository it belongs to — gets `create_status_from_github!(params)` called on it. [6](#0-5) 
6. `Commit#create_status_from_github!` uses `stack_id` taken from the matched `Commit` record itself (i.e., Repository C's own stack), completely independent of the payload's `repository` field: `statuses.replicate_from_github!(stack_id, github_status)`. [7](#0-6) 

Attack: attacker legitimately owns/administers Repository A (or an org whose GitHub App is configured in Shipit with a `webhook_secret` they can sign with — a precondition explicitly stipulated as satisfied by the question). They observe (via GitHub or Shipit's own public UI) the `sha` of any commit belonging to Repository C's tracked Stack. They then POST a `status` event to `/webhooks` with `X-Hub-Signature` computed from Repository A's `webhook_secret`, and a body containing `repository.owner.login = "<repo-a-owner>"` (to pick the correct signing key) but `sha = "<repo-c-commit-sha>"` and `state: "success"`. `verify_signature` passes (it only checks the signature against Repo A's secret and the raw body — it has no cross-check against `sha`). `StatusHandler#process` then finds the Commit row in Repository C's Stack matching that sha and writes a new `Status` into it, entirely without Repository C's `webhook_secret` ever being consulted.

No existing guard intercepts this: `verify_signature` only authenticates "a request signed by *some* configured org's secret," not "a request authorized to mutate this specific commit/stack." `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` do not require/validate `repository`. `force_github_authentication`, `User#authorized?`, and `Shipit.github_teams` are irrelevant here — this is an unauthenticated webhook endpoint, not a session-based one.

### Impact Explanation
An attacker with legitimate (self-service) control over one GitHub organization/repository registered in Shipit can inject fabricated CI status (`success`/`failure`/`pending`) onto arbitrary commits belonging to *any other* Stack/repository tracked by the same Shipit instance, as long as they can guess/observe the target commit's sha (trivial, since shas are public). Since commit status directly gates Shipit's continuous-delivery/merge logic (`Status#after_create :enable_ci_on_stack`, `after_commit :schedule_continuous_delivery`) and CI checks (`Commit#create_status_from_github!` → `ProcessMergeRequestsJob`, per `test/models/commits_test.rb:763-777`), this is a cross-tenant authentication-boundary bypass that can trigger merges/deploys of Repository C driven by a request Repository C's own credentials never authorized. This matches the "Critical" impact category explicitly listed: "a payload for one repository mutating another's stack, commit, task or team." [8](#0-7) 

### Likelihood Explanation
Preconditions: the attacker needs one repository/organization legitimately registered in Shipit with a webhook secret they can sign with (stipulated true by the question), and the target commit sha must exist in some other tracked Stack's `commits` table — both trivially satisfiable (shas are public; multi-tenant Shipit deployments with per-org GitHub Apps are explicitly supported and tested, e.g. `test/dummy/config/secrets_double_github_app.yml`). The attack costs a single crafted HTTP POST and is fully repeatable against any known sha in any Stack, with no rate limiting or additional authorization layer in the way.

### Recommendation
In `StatusHandler#process` (and any other handler using bare sha/id lookups), scope the `Commit`/`Stack` lookup by the repository named and cryptographically verified in the same request — e.g., resolve the target `Stack`/`Repository` from `params.dig('repository','full_name')`, confirm it matches the organization used in `verify_signature`, and join that constraint into the `Commit.where(sha:, stack_id: expected_stack_ids)` query before calling `create_status_from_github!`. Require `:repository` in the `StatusHandler` `ExplicitParameters` schema and reject/ignore statuses whose `repository.full_name` doesn't match a Stack tracked under the verified organization.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:

```ruby
test ":status webhook signed by org A can write a status onto a commit belonging to org C's stack" do
  # Repository C's stack/commit, unrelated to the attacker
  repo_c_stack = shipit_stacks(:shipit) # belongs to organization "shopify"
  repo_c_commit = shipit_commits(:first)
  repo_c_commit.update!(sha: "c" * 40)

  # Attacker's own org "attacker-org" is a legitimately configured Shipit tenant
  attacker_secret = "attacker-org-secret"
  attacker_app = Shipit::GitHubApp.new("attacker-org", webhook_secret: attacker_secret)
  Shipit.stubs(:github).with(organization: "attacker-org").returns(attacker_app)

  payload = {
    "sha" => repo_c_commit.sha,           # sha copied from Repository C's public commit
    "state" => "success",
    "repository" => { "owner" => { "login" => "attacker-org" } } # only used for signing key selection
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, payload)

  request.headers["X-Github-Event"] = "status"
  request.headers["X-Hub-Signature"] = signature

  assert_difference -> { repo_c_commit.reload.statuses.count }, 1 do
    post :create, body: payload, as: :json
  end
  assert_response :ok
end
```

Binding checked before/after: `signing_org = "attacker-org"` (attacker's own tenant) vs. `mutated_stack_owner = repo_c_stack.repository.owner` ("shopify"). Before the request they differ (no relationship); after the request `repo_c_commit.statuses.count` still increased by 1 — proving the mutation happened for Repository C's Stack despite the signature only ever having been verified against Repository A's (`attacker-org`'s) secret, confirming the binding is false and exploitable.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
