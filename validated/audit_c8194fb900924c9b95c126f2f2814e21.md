### Title
Cross-repository Status forgery via SHA-scoped commit lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up `Commit` rows purely by `sha`, with no check that the `repository.full_name` in the verified webhook payload matches the repository that owns the matched commit's stack. Since `sha` values are attacker-influenceable git commit hashes (not Shipit-issued secrets), a correctly-signed webhook from a repository the attacker controls (R2) can create a `Status` row against a commit belonging to an unrelated victim stack (S1/R1) if the SHA happens to coincide.

### Finding Description
The binding that should hold is: `payload.dig('repository','full_name')` (the repository whose webhook signature was verified in `WebhooksController#verify_signature`, using `Shipit.github(organization: repository_owner)`) must equal `commit.stack.repository.full_name` for every `Commit` mutated by the handler. `StatusHandler#process` breaks this: [1](#0-0) 

It calls `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` and never calls the inherited `Handler#stacks` helper (which scopes by `Repository.from_github_repo_name(repository_name)`), nor does it compare `payload.dig('repository','full_name')` against `c.stack.repository.full_name`: [2](#0-1) 

Every other status/CI-related mutation path scopes to the resolved repository's stacks via this `stacks` method, but `StatusHandler` is the exception — it performs a global `Commit` lookup by `sha` across all stacks/repositories in the installation.

`Commit#create_status_from_github!` then unconditionally creates a `Status` on `statuses` (`belongs_to :stack`), tied to whatever stack owns that commit row, regardless of which repository's webhook triggered it: [3](#0-2) 

`verify_signature` in `WebhooksController` only proves the payload was signed by *some* GitHub App install Shipit trusts for the named repository/organization — it says nothing about whether that repository is the same one that owns a `Commit` row with a given `sha`: [4](#0-3) 

Exploit flow: attacker owns R2 (any onboarded repo/org with the GitHub App installed). They engineer a commit in R2 whose git-object bytes (tree + parents + author/committer identity and timestamps + message) are identical to an existing commit already tracked as a `Commit` row in victim stack S1/R1 — the given precondition states this collision exists. GitHub computes the sha from the commit object content, so if the object is byte-identical the sha is identical (no cryptographic break needed if content genuinely matches, e.g., orphan/empty-tree commits). Attacker then triggers or waits for GitHub to send a real, validly-signed `status` event for R2 for that sha (e.g., attacker's own CI reports `state=success` on it). `StatusHandler#process` finds the `Commit` row by `sha` alone — matching the one in S1 — and writes a `Status` under S1, with `commit.stack` (S1) untouched by R2's authentication scope.

### Impact Explanation
A `Status` record is created/attributed under victim stack S1 (repository R1) as a side effect of a webhook authenticated only for attacker-controlled repository R2. `add_status` further triggers `Hook.emit(:commit_status, ...)`, potentially `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` if the injected state is `success`/`pending` — this can flip a commit's deployability, satisfy `blocking?`/`deployable?` checks, and feed into `ContinuousDeliveryJob`, potentially enabling an unauthorized deploy on S1 if continuous delivery is enabled. This matches the specified Critical category: "a payload for one repository mutating another's stack, commit, task or team." The flaw is repeatable against any repository pair where a sha collision can be engineered, and is not limited to a single tenant — any onboarded repository can target any other onboarded stack's commits given a matching sha.

### Likelihood Explanation
Preconditions required: both R1 and R2 must be configured in Shipit; a `Commit` row must already exist in S1 for the colliding sha; and the attacker must produce a git commit object in R2 that is byte-identical to one already committed in R1 (matching tree, parents, author/committer identity+timestamps, and message exactly). This is feasible in limited but real cases — most plausibly orphan/root commits with an empty tree (well-known sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904` for the tree object) or other public commits where all commit-object fields are known/reproducible — without requiring a SHA-1 cryptographic collision break. No Shipit secrets, sessions, or maintainer privileges are needed; the attacker only needs their own repository onboarded and the GitHub App installed on it (a standard, low-privilege setup), consistent with the stated threat model. The exact commit-collision precondition is given as an assumption in the prompt, so likelihood beyond that engineering step is high given the code has no other check at all.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the authenticated repository, not by `sha` alone — e.g., use `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently restrict via `Commit.joins(stack: :repository).merge(stacks).where(sha: params.sha)`, mirroring the pattern used by `Handler#stacks`/`repository_name`. Add an explicit invariant check that `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`, and skip/log any commit whose owning repository doesn't match the payload's `repository.full_name`.

### Proof of Concept
Minitest integration test (`test/controllers/webhooks_controller_test.rb`-style or `test/models/shipit/webhooks/handlers_test.rb`-style, no live GitHub):
1. Create `stack_r1 = shipit_stacks(:shipit)` (or a factory stack) with `repository.full_name = "acme/r1"`, and `commit = stack_r1.commits.create!(sha: "<colliding_sha>", ...)`.
2. Create `stack_r2` with `repository.full_name = "acme/r2"` (attacker-owned, no commit with that sha).
3. Stub/allow signature verification to pass for `acme/r2` (as `verify_signature` would for a legitimately signed R2 payload).
4. POST a `status` payload: `{ "sha" => "<colliding_sha>", "state" => "success", "repository" => { "full_name" => "acme/r2", "owner" => { "login" => "acme" } } }` with `X-Github-Event: status`.
5. Assert: `commit.reload.statuses.count == 1` (a `Status` was created under `stack_r1`), and assert `"acme/r2" != stack_r1.repository.full_name` — proving R2's webhook mutated R1/S1's commit despite authenticating only R2.
