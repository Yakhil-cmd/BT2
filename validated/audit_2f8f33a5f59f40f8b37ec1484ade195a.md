### Title
`StatusHandler#process` never uses parsed `branches`, confirming unmitigated cross-repository/cross-tenant status write - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `branches` field accepted in `StatusHandler`'s params schema (`status_handler.rb:15-17`) is parsed but never referenced anywhere in `#process` (`status_handler.rb:20-24`) or in `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`). It provides no repository/branch/stack scoping whatsoever, so it does not mitigate the cross-tenant write behavior of `Commit.where(sha: params.sha)`.

### Finding Description
The claimed binding to check is: does `params.branches` cause the code to verify `branch's owning stack == verifying org` before writing a status? Tracing the code:

- `StatusHandler#process` (`status_handler.rb:20-24`) does exactly:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
It looks up commits **only by `sha`**, globally across the `commits` table, with no reference to `params.branches`, `params.repository`, or any stack/org scoping.
- `Commit#create_status_from_github!(github_status)` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)` inside `add_status`. It reads only `stack_id` (the `Commit`'s own `belongs_to :stack`, set at commit-creation time) and the passed-in status payload attributes (state, description, target_url, context, created_at). There is no read of `github_status.branches` anywhere in `Commit`, `Status`, or `add_status` (`app/models/shipit/commit.rb:360-386`).
- A grep across the engine confirms `branches` is referenced nowhere outside the `params do ... end` schema declaration in `status_handler.rb`. No subclass overrides `StatusHandler`, and no callback on `Commit` inspects `branches`.

Therefore the equality to validate — "`params.branches` used ⇒ branch's owning stack is checked against verifying org" — is **vacuously false on the left-hand side**: `branches` is never used, so no such check exists, incidental or otherwise. The pre-existing scoping gap (any commit row across any stack/repo sharing the pushed `sha` gets its status/state mutated, based solely on the unauthenticated `sha` value in the webhook payload) is not addressed by this field.

### Impact Explanation
This confirms — it does not independently establish — the cross-tenant write path already flagged in the referenced Q15/Q17 analysis: `StatusHandler#process` writes a `Status` row (and can flip a commit's CI/deploy-gating state via `add_status` → `Hook.emit(:commit_status/:deployable_status)` → `stack.schedule_merges`) for **every** `Commit` record across **every** stack that happens to share the pushed SHA, regardless of which repository's webhook triggered the request. Since `branches` is dead code, there is no code-level mitigation limiting this to the correct stack/org. This finding itself, in isolation, is confirmatory — it does not introduce a new distinct vulnerability beyond what Q15/Q17 already describe; it demonstrates that the one plausible incidental mitigation (the `branches` field) does not exist.

### Likelihood Explanation
No additional preconditions beyond what Q15/Q17 already require (a `status` webhook reaching the endpoint with signature verification passing, and a colliding/attacker-controlled `sha` matching a `Commit` row in another stack). Confirming `branches` is dead code required no Shipit/GitHub configuration — it is a static-analysis fact about the code, verifiable by reading `status_handler.rb` and `commit.rb` directly.

### Recommendation
Not applicable as a standalone fix recommendation for this sub-question — the underlying issue is the missing repository scoping in `StatusHandler#process`'s `Commit.where(sha: params.sha)` lookup, which should filter by the webhook's authenticated `repository.full_name`/owning stack rather than by `sha` alone across all stacks. The `branches` field, being unused, should either be removed from the schema or wired in as a real check, but its removal/addition would not by itself close the underlying scoping gap.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "branches param has zero effect on which Commit row receives the status" do
  stack_a = shipit_stacks(:shipit)
  commit  = shipit_commits(:first)
  commit.update!(stack: stack_a)

  params_with_branches = ExplicitParameters::Params.new(
    sha: commit.sha, state: 'success', branches: [{ name: 'refs/heads/totally-unrelated-branch' }]
  )
  params_without_branches = ExplicitParameters::Params.new(
    sha: commit.sha, state: 'success'
  )

  # Both calls must produce the identical write: same commit row, same resulting status.
  Shipit::Webhooks::Handlers::StatusHandler.new(payload: params_with_branches.to_h).process
  status_with = commit.reload.status

  commit.statuses.delete_all
  Shipit::Webhooks::Handlers::StatusHandler.new(payload: params_without_branches.to_h).process
  status_without = commit.reload.status

  assert_equal status_with.state, status_without.state
  # Assert no branch/stack ownership check occurred: commit belongs to stack_a regardless of
  # branches referencing an unrelated branch/stack.
  assert_equal stack_a.id, commit.stack_id
end
```
This confirms `branches` has no bearing on which `Commit`/stack is mutated, per the requested proof idea.
