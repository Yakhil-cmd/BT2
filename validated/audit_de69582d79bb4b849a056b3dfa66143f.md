## Confirmed exploit chain

The `WebhooksController` selects **which GitHub App's `webhook_secret` to verify the signature against** using `repository_owner`, which is read directly from the unverified JSON payload: [1](#0-0) [2](#0-1) 

The signature verification itself is a no-op whenever the selected organization has no `webhook_secret` configured: [3](#0-2) 

Multiple-organization installs are an explicitly documented and supported configuration (`config/secrets.development.shopify.yml`, `docs/setup.md` "Using Multiple Github Applications"), and it is normal for some orgs to be configured with `webhook_secret: nil` while others have a real secret (see `test/dummy/config/secrets_double_github_app.yml`). [4](#0-3) 

Meanwhile, `Handler#stacks` — used by `PushHandler` and all other webhook handlers to locate the target `Stack`/`Repository` — resolves the repository from a **completely different, independently attacker-controlled field**: `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` (the value that was actually used to pick the signing secret): [5](#0-4) [6](#0-5) 

## Binding broken

`repository.owner.login` (the field the HMAC verification is scoped to) ≠ `repository.full_name` (the field actually used to select the `Stack` that gets mutated). The signature only proves "this request came from whoever holds the webhook secret for org X"; it proves nothing about the `repository.full_name` field, which routes the payload to an arbitrary tracked stack, including one belonging to a different, securely-configured organization Y.

### Title
Webhook signature is verified against `repository.owner.login`, but the repository actually acted upon is taken from the unverified `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and thus the `webhook_secret` used for HMAC verification) based on `repository.owner.login`/`organization.login` from the raw JSON body. `Webhooks::Handlers::Handler#repository_name` (used by every handler, e.g. `PushHandler`) instead resolves the target `Stack` using `repository.full_name` from the same untrusted body. Nothing ties these two fields together, so a request can be signed for one (unsecured) organization while acting on a stack belonging to a different, properly secured organization.

### Finding Description
In a multi-organization Shipit deployment (an explicitly supported and documented configuration, see `docs/setup.md`), each GitHub organization can have its own `webhook_secret`. `GitHubApp#verify_webhook_signature` treats a missing secret as automatically valid: `return true unless webhook_secret`. `WebhooksController#verify_signature` looks up which `GitHubApp` (and hence which secret, possibly `nil`) to use via `repository_owner`, derived from `params.dig('repository','owner','login')`. However, the handler that actually processes the event (`Handler#stacks` / `#repository_name`) looks up the `Repository`/`Stack` using `payload.dig('repository','full_name')` — a different field of the same untrusted JSON body, not cross-validated against `repository.owner.login`.

An attacker only needs the ability to send an unauthenticated HTTP POST to the public `/github/webhooks` endpoint (no Shipit session or credentials required, matching the "unprivileged attacker" scope). By setting `repository.owner.login`/`organization.login` to an organization that has no `webhook_secret` configured (or one the attacker fully controls), signature verification passes unconditionally, while setting `repository.full_name` to a real, secured stack's repository (e.g., `victim-org/victim-repo`), the forged payload is routed to that victim stack.

### Impact Explanation
`PushHandler` enqueues `GithubSyncJob` for the resolved stack, which mutates commit history/deploy-readiness state used to gate deploys, and other handlers (`status`, `check_suite`, `membership`, `pull_request`) can similarly forge CI/check status, team membership, or merge-queue state for a victim stack whose actual GitHub organization is properly secured with a real `webhook_secret`. This is a cross-organization write into a `Repository`/`Stack`'s state that should only be reachable by that organization's authenticated GitHub webhook, effectively bypassing the per-organization webhook trust boundary and enabling an unauthorized influence over deploy/merge decisions for repositories the attacker does not control.

### Likelihood Explanation
Requires only: (1) a multi-org Shipit installation (documented, supported topology) where at least one configured organization has `webhook_secret` unset/empty (which the docs list as a valid `# nil` default), and (2) knowledge of a victim stack's `owner/name` (publicly discoverable via the Shipit UI/API or GitHub itself). No credentials, sessions, or tokens are needed — only an HTTP POST to the public webhook endpoint with a crafted JSON body and a fabricated `X-Github-Event`/`X-Hub-Signature` header.

### Recommendation
After selecting the `GitHubApp` used for verification, require that the same field(s) used for organization selection (`repository.owner.login` / `organization.login`) match the organization implied by `repository.full_name` before dispatching to handlers. Alternatively, resolve the target `Repository`/`Stack` using the same verified organization identity that determined the signing secret, rather than trusting `repository.full_name` independently. Additionally, consider making `verify_webhook_signature` fail closed (reject) rather than pass when `webhook_secret` is blank, at least for installations with more than one configured organization.

### Proof of Concept
1. Deploy Shipit configured for two organizations per `docs/setup.md`'s "Using Multiple Github Applications": `attacker-org` (with `webhook_secret: nil`) and `victim-org` (with a real, secret webhook secret), each tracking their own stacks (e.g., `victim-org/victim-repo`).
2. Attacker sends:
```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   (irrelevant, since attacker-org has no secret)
Body:
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha claiming to exist on victim repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the signature.
4. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `Handler#stacks` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and enqueues `GithubSyncJob` for that stack — a stack belonging to the properly secured `victim-org`, mutated using a request that was never validated by `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
