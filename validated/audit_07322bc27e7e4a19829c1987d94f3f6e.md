### Title
Double-fetch of the spent output's address/denomination/asset between validation and write in multi-authored payments - (File: `writer.js`)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` reads a transfer input's source output (`address`, `amount`, `denomination`, `asset`, `sequence`, `main_chain_index`) from the `outputs`/`units` tables once, and performs all authorization/consistency checks against that value. Later, when the joint is actually written by `writer.saveJoint()`, for any multi-authored unit the address of that very same source output is **re-fetched independently** by `determineInputAddressFromSrcOutput()` in `writer.js` with a second, separate `SELECT`, and this second read — not the value validated earlier — is what gets persisted into the `inputs` table and used to authorize ownership of the spent coin. This is the classic “double fetch” pattern from CVE‑2016‑5728: the same externally‑influenced record is read twice for two different purposes (check vs. use), with no guarantee the two reads observe the same value.

### Finding Description
During validation, `validatePaymentInputsAndOutputs()` selects the src output being spent: [1](#0-0) 
and uses the result (`src_output.address`, `.denomination`, `.asset`, `.sequence`) to verify ownership, denomination, asset match, and sequence/serial status: [2](#0-1) 

This validated data is *not* threaded through to the writer. Instead, `writer.js`'s `addInlinePaymentQueries()` explicitly defers resolving the payer address for payment messages ("we'll add inputs/outputs later because we need to read the payer address from src outputs"): [3](#0-2) 
and for multi-authored inputs it performs a brand-new query against `outputs` to fetch `address, denomination, asset` again: [4](#0-3) 

The address returned by this **second, independent fetch** (not the one validated earlier) is what is written into the `inputs.address` column and what determines whose funds are considered spent for that input: [5](#0-4) 

Between the validation-time read (`validation.js:2443`) and the write-time re-read (`writer.js:301`), an asynchronous gap exists — validation and writing are performed as separate DB round-trips, and private-payment address reveal logic (`private_payment.js` / `indivisible_asset.js` / `divisible_asset.js` precommit callbacks) can update the very same `outputs` row (setting `address`, `blinding`, `is_spent`) via its own transaction that is not synchronized with the “write” mutex guarding `validation.validate()`→`writer.saveJoint()`: [6](#0-5) 
If the row's `address`/`denomination`/`asset` differs between the two reads, `writer.js` records ownership of the spent input using data that was never checked by the validator (the validator only confirmed that *some* value was among the unit's authors and matched the claimed denomination/asset — a different value observed later is not re-verified against `arrAuthorAddresses` beyond a bare existence check, and any mismatch causes only a thrown/uncaught error rather than a controlled rejection): [7](#0-6) 

### Impact Explanation
If the two reads diverge, `writer.js` can attribute a spent (validated) output to a different address than the one actually verified as its owner during validation, or throw mid-write leaving `saveJoint`'s multi-query batch in an inconsistent state before commit. In the worst case this creates a discrepancy between what validation certified (author ownership, correct denomination/asset) and what gets durably recorded, which can manifest as spending an output on behalf of the wrong author in a multi-authored transaction, or a crash (`throw Error(...)`) partway through committing a unit that was already accepted as valid — a node-crash/DoS and node-disagreement-on-validity risk, matching the required "node disagreement on validity" / "unauthorized spending" impact classes.

### Likelihood Explanation
Exploitation requires an attacker (an ordinary unit poster building a multi-authored payment) to win a race where the referenced source output's row is mutated (e.g., via the private-payment address-reveal path, which runs its own `BEGIN`/`COMMIT` transaction independent of the `write` mutex) in the narrow window between validation's `SELECT` and the writer's re-`SELECT`. This is a genuine TOCTOU window in the code, but it is narrow (both reads happen within the same node-local processing of one unit, with only intervening async I/O), so likelihood is moderate rather than trivially reproducible — consistent with the CVSS AC:H (high attack complexity) characteristic of the original double-fetch CVE.

### Recommendation
Thread the already-validated `src_output` (address, denomination, asset) from `objValidationState` through to `writer.saveJoint()` instead of re-querying `outputs` in `determineInputAddressFromSrcOutput()`. If a second read is unavoidable, re-verify it against the value captured during validation and abort the write (transient error / re-validate) rather than blindly trusting the new read, and take the row lock (`SELECT ... FOR UPDATE`) for the full validate-then-write span so no other transaction can mutate it in between.

### Proof of Concept
Conceptual PoC (cannot be executed here, requires a running two-node/two-transaction ocore instance):
1. Author a private, multi-authored payment `unit_A` that spends output `O` (currently hidden, `address = NULL`) from asset `X`.
2. Have the reveal of `O`'s owning address happen (via `validateAndSavePrivatePaymentChain`, a separate DB transaction) concurrently with `unit_A`'s validation/write cycle, such that validation's `SELECT` in `validation.js:2443` sees `O` with address `Addr1`, but the reveal transaction commits a different `Addr2` for `O` before `writer.js:301`'s re-`SELECT` runs.
3. Observe that `writer.js` persists `inputs.address = Addr2` for `unit_A`, even though only `Addr1` was checked against `arrAuthorAddresses` during validation — or observe the writer throw mid-commit ("src output address not among authors") after the unit was already accepted as valid by validation, producing an inconsistent/aborted write for an otherwise-approved unit.

					if (rows.length > 1)

					if (arrAuthorAddresses.indexOf(address) === -1)
						throw Error("src output address not among authors");
