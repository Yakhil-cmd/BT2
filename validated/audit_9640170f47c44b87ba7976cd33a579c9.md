Confirmed. `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) overrides the scoped `Api::BaseController#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`), which is the only place that enforces `current_api_client.stack_id` scoping. ### Title
Stack-scoped CCMenu API token authorizes read access to any stack, not just its bound stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` accessor to look up the stack directly from `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` scoping that `Shipit::Api::BaseController#stack`/`#stacks` normally enforce. Any valid CCMenu token — including one deliberately scoped to a single stack — can therefore read the deploy/build status of every stack in the installation.

### Finding Description
`CCMenuUrlController#client` mints an `ApiClient` bound to one specific stack with only the `read:stack` permission: [1](#0-0) 
That token is meant to authorize read access to exactly the stack for which it was created (`ApiClient#stack_id`).

`Api::BaseController` establishes the invariant that a client scoped to a stack may only touch that stack: [2](#0-1) 

However, `Api::CCMenuController` defines its own `stack` method that ignores `current_api_client` entirely and resolves the stack purely from the request parameter: [3](#0-2) 

The `require_permission :read, :stack` before_action only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`: [4](#0-3) 
It never checks `stack.id == current_api_client.stack_id`. So the binding `token.authorized_stack == stack_acted_upon` (enforced everywhere else in the API via `stacks.from_param!`) is broken specifically in this controller.

### Impact Explanation
This is a High-severity authorization escalation matching "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output" — here specifically unauthorized cross-stack read of stack/deploy state. A CCMenu URL/token generated for (and often distributed to, e.g., CI dashboard tools or third parties) one particular stack lets its holder enumerate `stack_id` and read the deploy status of any other stack hosted by the same Shipit instance, including private/internal stacks the token was never meant to expose.

### Likelihood Explanation
High likelihood: the token is handed out via `CCMenuUrlController#fetch` as a URL query parameter (`?token=...`) intended for third-party CI status tools, so it is routinely exposed outside of trusted operator control. Exploitation requires no privilege beyond possessing any valid CCMenu token and knowing/guessing another stack's `to_param` (repo/branch/environment identifiers, which are generally not secret and are visible on the Shipit UI).

### Recommendation
In `Api::CCMenuController`, remove the local `stack` override (or reimplement it to delegate to the base class), so the base `Api::BaseController#stacks`/`#stack` scoping (which checks `current_api_client.stack_id`) is enforced, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. As a legitimate user, request a CCMenu URL for stack A: `GET /stacks/:A_id/ccmenu_url` → `CCMenuUrlController#fetch` creates/returns an `ApiClient` with `stack_id = A.id`, `permissions = ["read:stack"]`, and returns `https://shipit.example.com/api/stacks/A/ccmenu.xml?token=<token>`.
2. Take the returned `<token>` and replace the stack identifier in the path with stack B's identifier: `GET /api/stacks/B/ccmenu.xml?token=<token>`.
3. `Api::CCMenuController#authenticate_api_client` authenticates the token successfully (it's a valid `ApiClient`), `require_permission :read, :stack` passes because the token has `read:stack`, and `stack` resolves to stack B via `Stack.from_param!` with no ownership check.
4. The response renders stack B's latest deploy/rollback status via `shipit/ccmenu/project`, even though the token was only ever authorized for stack A. [5](#0-4)
