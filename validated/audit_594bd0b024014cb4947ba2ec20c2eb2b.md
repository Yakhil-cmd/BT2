### Title
Reward recalculation reads live `StakesCache` instead of a rewarded-epoch snapshot, allowing fork-dependent `PartitionedStakeRewards` — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`Bank::recalculate_stake_rewards`, invoked by `recalculate_partitioned_rewards_if_active` whenever the epoch-rewards sysvar is still `active`, recomputes stake rewards for the previous ("rewarded") epoch but pulls stake account state from `self.stakes_cache.stakes()` — the *current* bank's live stake cache — rather than from an immutable snapshot taken at the epoch boundary. Because the epoch-rewards distribution phase spans many blocks, and any bank created during that window can call this recalculation, an attacker who mutates their own stake account (e.g. via `Split`/`Withdraw`) on one fork before that fork's recalculation runs can cause the computed `stake_rewards`/`partition_indices` to differ from an honest fork that has not observed the same mutation.

### Finding Description
`recalculate_partitioned_rewards_if_active` is gated only by `epoch_rewards_sysvar.active`, which remains true for the *entire* multi-block reward distribution window, not just the epoch-boundary block [1](#0-0) . Inside `recalculate_stake_rewards`, the rewarded epoch is fixed as `self.epoch() - 1`, but the stake data used to recompute rewards is taken from `self.stakes_cache.stakes()` on the *current* bank, as the function's own doc comment confirms: "stake accounts from StakesCache" [2](#0-1) .

`get_epoch_params_for_recalculation` derives `stake_delegations` from this live snapshot, and those delegation objects carry the stake account's current lamport/delegation amount — which is exactly what `Split` and `Withdraw` mutate. `calculate_stake_rewards_and_commissions` then computes point values and stake rewards from these live delegation amounts and the fixed `point_value` derived from the sysvar, before `hash_rewards_into_partitions` deterministically distributes the resulting `PartitionedStakeRewards` into partitions keyed by `epoch_rewards_sysvar.parent_blockhash` [3](#0-2) .

Because `parent_blockhash` is fixed and identical on both forks (inherited from the shared epoch-boundary parent), the only source of divergence is the live `stake_delegations` snapshot. An unprivileged attacker who owns a stake account already captured in `PartitionedStakeRewards` for the rewarded epoch can submit a `Split` or bounded `Withdraw` on fork A (but not fork B) before fork A's bank invokes `recalculate_partitioned_rewards_if_active`. Both forks descend from the same parent and process the same rewarded epoch, but fork A's recalculation observes a different (attacker-modified) delegation amount for that pubkey than fork B's, producing a different `stake_rewards` vector and potentially different `partition_indices`. No signer/authority check prevents this because `Split`/`Withdraw`/`SetLockup` on one's own withdrawer-authorized stake are legitimate operations; the vulnerability is not in the stake-program authorization logic but in the reward-recalculation function reading mutable state that differs across forks referencing the same rewarded epoch.

### Impact Explanation
This causes divergent `Bank::epoch_reward_status` (specifically the `PartitionedStakeRewards` and partition indices) on different forks that share the same parent and rewarded epoch, violating the invariant that all honest validators compute identical state for the same block sequence. This falls under the "consensus/state divergence" bounty category — an epoch-boundary safety violation during the reward distribution phase, potentially leading to a fork/halt if validators disagree on distributed lamports, or to misattributed/duplicated stake reward amounts for the attacker's own account relative to what other validators compute.

### Likelihood Explanation
Preconditions are attacker-controlled and require no privileged access: only an active `EpochRewardStatus` (which occurs every epoch during the multi-block partitioned distribution phase) and the ability to land a `Split`/`Withdraw`/`SetLockup` transaction on one fork before a competing fork's bank triggers `recalculate_partitioned_rewards_if_active`. Since recalculation is gated solely on `epoch_rewards_sysvar.active` and not on any epoch-boundary-only guard, it can be invoked at multiple block heights during the distribution window, giving the attacker a realistic timing window across natural fork races (e.g., during leader rotation or minor network partitions).

### Recommendation
Snapshot the stake delegations relevant to the rewarded epoch (e.g., via a frozen copy of `StakesCache`/`EpochStakes` taken at the epoch boundary, analogous to how vote accounts are already sourced from `EpochStakes` rather than the live vote-account cache) and use that frozen snapshot for all recalculations, instead of re-reading `self.stakes_cache.stakes()` from the bank on which recalculation happens to run. This ensures `recalculate_stake_rewards` is a pure function of the rewarded epoch's state and independent of any transactions executed after the epoch boundary.

### Proof of Concept
Rust integration test outline (in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` test module, using existing `create_reward_bank`/`create_reward_bank_with_specific_stakes` helpers):
1. Build a reward bank at an epoch boundary with `EpochRewardStatus` active and a `PartitionedStakeRewards` entry for `attacker_stake_pubkey`.
2. Clone the bank into fork A and fork B (both children of the same parent bank/slot).
3. On fork A only, process a `stake_instruction::split` (or `withdraw`) transaction from `attacker_stake_pubkey`, signed by the attacker's own withdrawer authority, moving lamports to a new stake account.
4. Call `bank_a.recalculate_partitioned_rewards_if_active(...)` and `bank_b.recalculate_partitioned_rewards_if_active(...)`.
5. Assert `bank_a.get_epoch_reward_status()`'s `PartitionedStakeRewards`/`partition_indices` differ from `bank_b`'s for entries besides the attacker's own pubkey (or that the total distributed lamports/partition assignment for the rewarded epoch diverge), demonstrating cross-fork state divergence rooted in `recalculate_stake_rewards` reading live `self.stakes_cache.stakes()`.

            let (stake_rewards, partition_indices) =

                stake_rewards,
                partition_indices,
            );
        }
    }

    /// Returns a vector of partitioned stake rewards. StakeRewards are
    /// recalculated from an active EpochRewards sysvar, vote accounts from
    /// EpochStakes, and stake accounts from StakesCache.
    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
