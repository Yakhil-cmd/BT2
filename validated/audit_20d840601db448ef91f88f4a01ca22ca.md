### Title
Utilization and solvency guards inside `claim_revenue` make fee collection revert exactly when the market is stressed, freezing protocol revenue and compounding a withdrawal block - ([File: contracts/pool/src/ops/revenue.rs])

### Summary

The Knox report describes a flow where a mandatory external interaction (`Pool.withdraw`) inside fee collection reverts under a stressed state (liquidity locked / insufficient liquidity), blocking both fee collection and user exits. XOXNO Lending has the same shape: `pool::claim_revenue` unconditionally enforces `require_utilization_below_max` and `require_supply_for_debt` *after* burning claimable revenue, and normal `withdraw` enforces the same utilization gate via `gate_and_debit`. When a market's utilization is driven above `max_utilization`, every `claim_revenue` call reverts and every ordinary (non-liquidation) withdrawal that keeps utilization above the cap also reverts — so the exact moment revenue is largest and LPs most want to exit is precisely when both operations are denied.

### Finding Description

`ops::revenue::accounting` in `contracts/pool/src/ops/revenue.rs` runs:

```rust
let net_transfer = cache.burn_claimable_revenue();
guards::require_utilization_below_max(env, &cache);
guards::require_supply_for_debt(env, &cache);
cache.debit_cash(net_transfer);
```

The pool README confirms the guards run "even when nothing is claimable" (`contracts/pool/README.md`, "claim_revenue is capped by cash... `require_utilization_below_max` and `require_supply_for_debt` run even when nothing is claimable"). `require_utilization_below_max` in `contracts/pool/src/guards.rs` computes `borrowed.div_ceil(supplied)` using the *current* indexes and panics with `UtilizationAboveMax` when it exceeds `params.max_utilization`.

The controller entrypoint `claim_revenue` (`contracts/controller/src/markets.rs`) is permissionless — it only requires `require_authorized_caller`, i.e. the caller's own signature — and wraps the call in `pool_claim_revenue_call`, so a pool-side revert propagates and the whole transaction fails. The same gate is applied to ordinary withdrawals in `ops::withdraw::accounting` via `gate_and_debit(..., is_liquidation || empty_close)`, meaning `WithdrawKind::Normal` exits revert while utilization sits above the cap (liquidation exits skip it).

### Impact Explanation

- **Freezing of unclaimed yield**: revenue shares minted inside total supply cannot be converted to cash while utilization is above `max_utilization`. Because `borrowed` compounds at `borrow_index` while `supplied` compounds at the lower `supply_index`, utilization drifts upward on its own once near the cap; claims revert for the entire period until borrowers voluntarily repay or are liquidated, and resume paying only after utilization recovers.
- **Temporary freezing of user funds**: the same gate on `WithdrawKind::Normal` blocks supplier withdrawals during the stressed window — the direct analog of the Knox "user is blocked from withdrawing their token" impact. Withdraw-all exits that still leave utilization above the cap are refused even though removing supply only makes the ratio worse is exactly why the check exists; the user has no way out except waiting for debt repayment.
- In a bad-debt aftermath (`clean_bad_debt` writes the supply index down), `require_supply_for_debt` can leave the market in a state where `supplied == 0` while residual `borrowed != 0`, making `claim_revenue` permanently revert — permanently freezing any remaining claimable revenue in that market.

### Likelihood Explanation

High utilization is not an exotic state: borrowers are economically incentivized to max out borrowable liquidity on attractive markets, and the borrow gate only checks utilization *at borrow time* — interest accrual then pushes the ratio over `max_utilization` with no one crossing the guard. No privileged action, oracle manipulation, or parameter misconfiguration is required; a single unprivileged borrower bringing utilization to the cap plus ordinary interest accrual is sufficient to trigger the claim/withdraw revert window.

### Recommendation

- In `ops::revenue::accounting`, skip `require_utilization_below_max` when `net_transfer == 0`, and consider skipping it entirely for claims since paying out revenue only *reduces* cash, but the burn itself is a pure share operation — alternatively gate claims on the post-claim ratio only when it actually worsens solvency.
- Mirror the Knox fix: make fee/yield collection non-blocking — return `actual_amount = 0` instead of reverting when the market is stressed, so revenue shares simply keep accruing claimable value.
- For `withdraw`, consider allowing exits that *reduce* utilization-or-supply monotonically (a withdraw-all / partial exit that does not increase the ratio) rather than hard-reverting, so suppliers are not trapped while utilization is above the cap.

### Proof of Concept

```rust
// Market: USDC hub asset, max_utilization < 1.0
// 1. ALICE supplies 100_000 USDC.
// 2. BOB supplies collateral and borrows USDC up to just below
//    max_utilization (borrow gate passes at t0).
// 3. Time advances: borrow_index grows faster than supply_index,
//    so borrowed.div_ceil(supplied) > max_utilization with no
//    further user action.
// 4. ALICE calls controller.withdraw(USDC, amount=0 /*all*/):
//      pool::withdraw -> accounting -> gate_and_debit
//        -> require_utilization_below_max  => PANIC UtilizationAboveMax
//    Her funds are frozen until BOB repays or is liquidated.
// 5. Any caller invokes controller.claim_revenue([USDC]):
//      pool::claim_revenue -> accounting
//        -> burn_claimable_revenue (succeeds in memory)
//        -> require_utilization_below_max  => PANIC UtilizationAboveMax
//    Revenue cannot be claimed during the entire stressed window;
//    if a later clean_bad_debt leaves supplied == 0 && borrowed > 0,
//    require_supply_for_debt makes the claim revert permanently.
```
