### Title
Webhook signature verification is bypassed for any GitHub organization configured without a `webhook_secret`, and the org selected for verification is not bound to the repository the payload actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` instance (and therefore the HMAC secret) used to authenticate an inbound webhook from an **unauthenticated field of the same request body** (`repository.owner.login` / `organization.login`), before any cryptographic check has occurred. `GitHubApp#verify_webhook_signature` then treats a blank/unset `webhook_secret` for that selected org as automatically "verified." Because the downstream webhook handlers resolve the target `Stack`/`Repository` from a *different*, equally unauthenticated field of the same body (`repository.full_name`), the "organization that authenticated" and "the repository that is written" are never actually bound together. Any org entry lacking a `webhook_secret` becomes a universal skeleton key that lets an unauthenticated caller inject fabricated GitHub events (e.g. commit statuses) against any repository tracked by the instance.

### Finding Description
`verify_signature` computes `repository_owner` straight from the raw JSON body and uses it to fetch the app config: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up that org's config and hands back a `GitHubApp` built from whatever `webhook_secret` (or lack thereof) is configured for it: [3](#0-2) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is blank, regardless of the actual `X-Hub-Signature` header supplied: [4](#0-3) 

Once "verified", `WebhooksController#create` dispatches the raw, attacker-controlled JSON to the registered handlers: [5](#0-4) 

Every handler resolves *which* `Stack` to act on from `repository.full_name` in that same unauthenticated body - a field that has no relationship whatsoever to the `repository_owner` value that determined which secret (or absence of secret) was used for verification: [6](#0-5) 

This is the exact bug class from the report: a value used to gate/short-circuit an accounting/verification step (`bptClaim == 0` skipping the ledger decrement) desynchronizes two states that are supposed to move together. Here, "verification passed for org X" is treated as "this payload's repository/stack references are trustworthy," but nothing binds X to the `repository.full_name` actually used by the handler - exactly the "organization that authenticated versus the repository that is written" binding called out in scope. If any org configured in `secrets.github` has no `webhook_secret` (a state the code explicitly treats as valid, not an error), an attacker who knows only that org's *name* (not any secret) can send a POST to `/github/webhooks` naming that org as owner while pointing `repository.full_name` at any other repository tracked by the instance, e.g., via `StatusHandler`, which builds a `CommitStatus` straight from attacker-supplied `sha`/`state`/`target_url` fields (exercised in `test/controllers/webhooks_controller_test.rb`): [7](#0-6) 

### Impact Explanation
A forged "success" `CommitStatus` on an arbitrary existing commit influences `Commit#deployable?` gating used by continuous delivery (`Stack.schedule_continuous_delivery` / `trigger_deploy`), meaning an attacker with zero Shipit credentials could get a stack with `continuous_deployment: true` to autonomously deploy a commit that never actually passed CI - an unauthorized deploy, which falls in the Critical bucket ("an unauthorized deploy, rollback or merge"). More broadly, any webhook-driven side effect (creating `Team`/`User` records via `MembershipHandler`, queuing `GithubSyncJob`, etc.) becomes forgeable against any tracked repository once one org's secret is unset, because the verification step never checks that the org it authenticated is the same org owning the repository the handler subsequently mutates.

### Likelihood Explanation
The attacker needs no session, `ApiClient` token, `webhook_secret`, or GitHub write access - only the public webhook endpoint and knowledge of an org name configured in this Shipit instance without a `webhook_secret` set (a state the code path explicitly supports and does not warn about). Multi-tenant Shipit deployments (`secrets.github` keyed by org) that onboard a new org before wiring up its `webhook_secret`, or leave one org's secret blank intentionally, are directly exposed. This requires no host-misconfiguration outside of documented, supported configuration shapes (`github_app_config`/`TOP_LEVEL_GH_KEYS`), so it isn't excluded by the "host not mounting the engine as documented" carve-out.

### Recommendation
Bind the verified organization to the repository actually referenced by the payload before dispatching to handlers: after selecting `github_app` by `repository_owner`, re-validate that `repository.full_name`'s owner matches `repository_owner`, and require signature verification to fail closed (never return `true`) when `webhook_secret` is blank for a multi-org config - or refuse to register an org without a configured secret. Additionally, `Handler#stacks`/`repository_name` should be scoped/cross-checked against the same org identity used for verification rather than trusted independently.

### Proof of Concept
1. Shipit instance is configured with two orgs in `secrets.github`, e.g. `orgA` (has `webhook_secret` set) and `orgB` (created but `webhook_secret` left blank).
2. Attacker sends, with no authentication and no valid `X-Hub-Signature`:
```
POST /github/webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/some-tracked-repo" },
  "sha": "<existing commit sha in orgA/some-tracked-repo>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "context": "ci/fake",
  "description": "forged"
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgB")`, finds `webhook_secret` blank for `orgB`, and `verify_webhook_signature` returns `true` unconditionally - request is accepted.
4. `StatusHandler` (registered in `Shipit::Webhooks.default_handlers`) resolves the target stack via `repository.full_name` = `orgA/some-tracked-repo`, and creates a forged, "verified" `success` status on a commit in `orgA`'s repository despite verification never having touched `orgA`'s secret.
5. If that stack has `continuous_deployment: true` and this status satisfies its CI-gating requirement, the commit becomes deployable and is auto-shipped - an unauthorized deploy triggered entirely by an unauthenticated request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
