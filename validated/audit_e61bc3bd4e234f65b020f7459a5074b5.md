### Title
Race condition in unsynchronized private-payment save paths causes duplicate-key DB error and node crash - (File: [network.js](https://github.com/Jaredbentat/ocore--009/blob/main/network.js), [private_payment.js](https://github.com/Jaredbentat/ocore--009/blob/main/private_payment.js), [divisible_asset.js](https://github.com/Jaredbentat/ocore--009/blob/main/divisible_asset.js))

### Summary
Private-payment chains can be delivered to a node through two independent, unsynchronized code paths that both ultimately call `privatePayment.validateAndSavePrivatePaymentChain()` on separate DB connections/transactions for the *same* `(unit, message_index, output_index)`. Each path performs a duplicate-check `SELECT` followed by an `INSERT` without any shared mutex serializing them by unit, creating a TOCTOU race. A concurrent duplicate `INSERT` into `outputs`/`inputs` violates the primary key, and the DB layer converts any query error into an unconditional `throw Error(...)`, which propagates to the global `uncaughtException` handler that deliberately re-throws to crash the whole process.

### Finding Description
Two entry points feed private payment chains into the same save function with no common lock:

1. `handleOnlinePrivatePayment()`'s `ifKnown` branch calls `privatePayment.validateAndSavePrivatePaymentChain` directly, with no `mutex.lock` and no `assocUnitsInWork` guard (explicitly commented out): [1](#0-0) 

2. `handleSavedPrivatePayments()` processes queued rows from `unhandled_private_payments` with `async.each` ("handle different chains in parallel"), each iteration opening its own connection and calling the same save function, guarded only by a `saved_private` mutex that does not prevent overlap with path (1): [2](#0-1) 

Both paths converge on `private_payment.validateAndSavePrivatePaymentChain`, which does a duplicate-detection `SELECT` and then, if no row is found, proceeds to insert via `divisibleAsset`/`indivisibleAsset` — each call taking its own pooled connection with its own `BEGIN`/`COMMIT`: [3](#0-2) 

The actual insert of `outputs`/`inputs` for divisible private payments uses a plain `INSERT` (no `OR IGNORE`) keyed by `(unit, message_index, output_index)`, which is the table's primary key: [4](#0-3) 

If two concurrent invocations both pass the duplicate `SELECT` (finding zero matching rows because neither transaction has committed yet) and then both attempt the `INSERT`, the second one violates the primary key constraint. The SQLite pool layer treats any query error as fatal and throws unconditionally rather than surfacing it as a normal callback error: [5](#0-4) 

This uncaught exception is caught by network.js's global handler, which explicitly re-throws to crash the process "to avoid ending up in an inconsistent state": [6](#0-5) 

This is structurally analogous to CVE-2017-5986: a race between two independent execution paths that operate on the same underlying state without adequate locking, where hitting a specific state (here: duplicate primary key from a race, there: buffer-full state during peel-off) triggers an assertion/exception failure that crashes the process (kernel panic there, process crash here).

### Impact Explanation
A crash of the node process is a concrete denial-of-service against that node: it stops confirming/relaying units until restarted, and for a wallet/hub process this means it can no longer serve its private-payment counterparties or peers. This falls squarely into the "network unable to confirm new units" / node-availability impact category for the affected node.

### Likelihood Explanation
The race requires two deliveries of the same private-payment chain content to arrive/be-processed concurrently on separate DB connections before either commits. This is achievable by a private-payment counterparty: e.g., a sender who both pushes the payment directly (`private_payment` justsaying handled via `handleOnlinePrivatePayment`, path 1) while an already-queued copy of the same payment (from an earlier partial delivery, e.g., recipient and cosigner sharing a device, or a resend/retry) is concurrently drained by `handleSavedPrivatePayments`'s parallel `async.each` (path 2). No malicious peer/hub/node capability is required beyond normal private-payment protocol messages, and the codebase's own comments acknowledge duplicate/re-delivery of the same `(unit, message_index)` is a normal, expected scenario ("we may receive the same unit and message index... twice"). Because the actual constraint violation depends on precise timing of two DB transactions racing past the duplicate check, likelihood is moderate rather than trivially deterministic.

### Recommendation
- Serialize all writers of a given private-payment element by unit/message_index/output_index (e.g., `mutex.lock(['priv-'+unit+'-'+message_index+'-'+output_index], ...)`) before performing the duplicate-check `SELECT` and subsequent `INSERT`, across both `handleOnlinePrivatePayment` and `handleSavedPrivatePayments`.
- Alternatively/additionally, make the insert idempotent (`INSERT OR IGNORE`/`INSERT ... ON DUPLICATE KEY`) consistently in `divisible_asset.js`'s output/input inserts, matching the pattern already used elsewhere (e.g., `indivisible_asset.js`'s `INSERT "+db.getIgnore()+"`).
- Avoid converting ordinary constraint-violation errors into an unconditional `throw`/process crash in `sqlite_pool.js`; distinguish expected races (duplicate key on a payment already recorded) from truly unrecoverable DB errors.

### Proof of Concept
Not independently executable without live wallet/network infrastructure, but the trigger sequence is:
1. Attacker/counterparty A sends the same private payment chain to victim node twice through two channels that reach different handling paths — e.g., once via direct `private_payment` justsaying while the node is also draining a previously queued copy of the identical `(unit, message_index)` from `unhandled_private_payments` (this queuing/draining race is native to normal operation per the code's own comments about "same unit and message index... twice").
2. Both `privatePayment.validateAndSavePrivatePaymentChain` invocations run on separate connections/transactions; both perform the "already exists?" `SELECT` before either commits its `INSERT`.
3. The second `INSERT INTO outputs (unit, message_index, output_index, ...)` (divisible_asset.js:34) violates the table's primary key.
4. `sqlite_pool.js`'s query callback throws unconditionally, which is caught by network.js's `process.on('uncaughtException', ...)` handler, which re-throws and crashes the node.

I was unable to fully verify exact timing feasibility on the MySQL storage backend (transaction isolation differs) or measure real-world race-window size without running the code; this assessment is based on static code-path and locking analysis.
