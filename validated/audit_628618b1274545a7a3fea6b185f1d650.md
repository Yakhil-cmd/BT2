### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhoo16/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, unlike sibling handlers (e.g. `PushHandler`, `PullRequest::*Handler`) which explicitly scope to the originating repository via `stacks`/`Repository.from_github_repo_name`. Any tenant that operates their own GitHub organization/repo wired into the same Shipit instance can therefore write a `security/scan` `failure` status onto a `Commit` row belonging to a different tenant's stack whenever the SHA values collide (e.g. shared git history from a public fork), flipping `blocked?`/`deployable?` for a stack they never authenticated against.

### Finding Description
The broken binding: the code implicitly assumes `Commit.sha == params.sha` uniquely identifies "the commit this webhook is about" `AND` that the webhook's authenticated repository (`params.repository.full_name`) equals the repository owning that `Commit` row. In reality: [1](#0-0) 

`Commit.where(sha: params.sha)` has no `joins`/`where` clause tying the result back to `params.repository.full_name`, so it will match **every** `Commit` row in the database sharing that SHA, across every stack and every repository. Compare this to `PushHandler#process`, which scopes explicitly via the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`): [2](#0-1) [3](#0-2) 

`StatusHandler` never calls `stacks` or filters on `repository_name` at all.

The webhook signature check (`WebhooksController#verify_signature`) only proves the payload genuinely came from GitHub for the organization named in `params.repository.owner.login` — it authenticates the *sender*, not that the *commit SHA belongs to that sender's repository*: [4](#0-3) 

Once `create_status_from_github!` runs, it calls `add_status`, which can flip `Status::Group` state and re-evaluate deployability: [5](#0-4) [6](#0-5) 

Because `Commit#blocked?` iterates `stack.commits.reachable...any?(&:blocking?)`, a forced `failure` status with a `context` matching the victim stack's `blocking_statuses` configuration can set `blocked?` to `true` for a commit the attacker never had access to, or (if the state is later flipped to something non-blocking) clear it, gating or unblocking deploys: [7](#0-6) 

Exploit flow: an attacker who administers their own GitHub org/repo that is (or can be) wired up as a Shipit tenant forks or otherwise shares commit history with the victim's tracked repository so that a commit SHA is identical in both repositories' `commits` tables. The attacker posts a real GitHub `status` event (`context: security/scan`, `state: failure`) against that SHA in their own repo. `verify_signature` passes because it validates against the attacker's own org's webhook secret. `StatusHandler#process` then finds and updates **all** `Commit` rows with that SHA, including the victim's, because the query is not scoped to `params.repository.full_name`.

None of the existing guards catch this: `verify_signature` checks sender authenticity only, not SHA-to-repository ownership; `drop_unhandled_event` and `ExplicitParameters` only validate payload shape; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
A payload authenticated for one repository/organization can mutate `Commit`/`Status` records — and therefore `blocked?`/`deployable?`/merge-queue gating — belonging to a completely different tenant's stack. This matches the "Critical: a payload for one repository mutating another's stack, commit, task or team" category, since it can force or block a deploy on a stack the attacker does not own or administer.

### Likelihood Explanation
Requires: (1) the target Shipit deployment to host multiple GitHub organizations/tenants (the codebase explicitly supports this via the multi-org `secrets.github` schema), (2) the victim stack to have `blocking_statuses` configured requiring a context like `security/scan`, and (3) a SHA collision between the attacker's own repo and the victim's tracked repo — most practically achieved by the attacker's repo sharing commit ancestry with the victim's public repo (a fork). Given those preconditions, the attack is cheap and fully repeatable (attacker can post statuses at will from their own repo) against any victim stack sharing history.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to the authenticated repository, e.g. join through `stack: :repository` and filter by `repository_name` (as `Handler#stacks` already does for `PushHandler`), before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or controller test):
1. Create two stacks/repositories: `victim/repo` (with `blocking_statuses` configured to include `security/scan`) and `attacker/repo`.
2. Create a `Commit` with `sha: "deadbeef..."` on `victim/repo`'s stack, and a separate `Commit` with the **same** `sha` on `attacker/repo`'s stack (simulating shared history).
3. Send a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha: "deadbeef..."`, `context: "security/scan"`, `state: "failure"`, signed with `attacker`'s configured webhook secret.
4. Assert equality before: `victim_commit.blocked?` == expected baseline (e.g. `false`) and no `Status` exists for `victim_commit` with that context.
5. Post to `/webhooks` (or call `StatusHandler.call(params)` directly).
6. Assert equality after: `victim_commit.reload.statuses.where(context: "security/scan").exists?` is now `true` and `victim_commit.blocked?`/`stack.deployable?` has changed — proving the attacker's own-repo webhook wrote a status onto, and altered gating for, the victim's unrelated stack.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
