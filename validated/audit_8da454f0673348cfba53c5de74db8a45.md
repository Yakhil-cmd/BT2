### Title
Premature mutex release in `shrinkCache()` causes concurrent unlocked mutation of unit caches during writer mutation - ([File: storage.js])

### Summary
`storage.js`'s `shrinkCache()` acquires the global `"write"` mutex lock (the same lock that serializes `writer.saveJoint()`, `forgetUnit()`, and other unit-cache mutations) but calls `unlock()` before the asynchronous cache-eviction work it protects has actually completed, mirroring the CVE-2024-47679 pattern of releasing/asserting protection state (`i_count` check) before the state mutation it guards is safely completed, letting a second actor mutate/evict the same shared structure concurrently.

### Finding Description
`shrinkCache()` takes the `"write"` lock: [1](#0-0) 

but then fires off several async `db.query()` calls in a loop and calls `unlock()` synchronously right after issuing them — not after their callbacks (which perform the actual `delete assocKnownUnits[...]`, `delete assocCachedUnits[...]`, `delete assocStableUnits[...]`, `delete assocBestChildren[...]`, etc.) have run: [2](#0-1) 

Because `unlock()` executes before the `db.query` callbacks fire, the `"write"` lock is released while pending cache-deletion callbacks are still queued to mutate `assocKnownUnits`, `assocCachedUnits`, `assocStableUnits`, `assocBestChildren`, `assocCachedUnitAuthors`, and `assocCachedUnitWitnesses`. Any other code path that also uses `mutex.lock(["write"], ...)` — most importantly `writer.saveJoint()`, which populates exactly these same structures when a new unit is written — can now acquire the lock and run its own cache mutations (`storage.assocStableUnits[...] = objNewUnitProps`, `storage.assocBestChildren[...].push(...)`, etc.) fully interleaved with the still-pending `shrinkCache` deletion callbacks: [3](#0-2) 

This is the same bug class as the kernel CVE: a lock is treated as covering an operation, but the actual mutating step happens asynchronously after the lock has already been dropped, so a second writer can observe/mutate the same object concurrently with the "protected" operation, producing memory/state inconsistent with what either operation assumed.

### Impact Explanation
If `writer.saveJoint()` for a newly arrived unit runs concurrently with `shrinkCache()`'s in-flight deletion callbacks for the *same* unit keys (e.g., a unit whose props were cached from before, or a best-parent entry being pushed to `assocBestChildren` at the same moment a stale entry for the same parent is deleted), the caches (`assocStableUnits`, `assocUnstableUnits`, `assocBestChildren`, `assocCachedUnits`) can end up missing entries that downstream stability/validation logic assumes are present. `readUnitProps()` explicitly throws `Error("no unstable props of "+unit)` and `Error("different props of ...")` when the caches disagree with the DB, and `forgetUnit()` throws `Error("trying to forget stable unit ...")`. Given that main-chain stability determination, witness level updates, and validation of new joints (`validateParents`, `main_chain.updateMainChain`) directly depend on these in-memory caches being self-consistent, corruption here can cause a node to throw and crash (denial of service / inability to process further units) or, in the worse case, to compute stability/validity based on stale or missing props, producing node disagreement about unit stability or validity.

### Likelihood Explanation
`shrinkCache()` runs unconditionally every 300 seconds via `setInterval(shrinkCache, 300*1000)` whenever the cache has grown past `MAX_ITEMS_IN_CACHE` (300 items) — a threshold trivially reachable by normal network activity or by an unprivileged party simply posting/propagating many units to grow `assocCachedUnits`/`assocKnownUnits`/`assocStableUnits`. The race window is proportional to the number of `CHUNK_SIZE` (500-unit) `db.query` batches outstanding, so under sustained unit posting the window recurs periodically and is not a rare one-off race; every 300s cycle when the cache is large re-creates the exposure while new units keep arriving and calling `writer.saveJoint()` under the same `"write"` lock.

### Recommendation
Move the `unlock()` call so it only executes after all cache-deletion callbacks have actually completed — e.g. collect the `db.query` calls into an `async.each`/`Promise.all` and call `unlock()` in the final completion callback, not immediately after the loop that issues the queries. This ensures the `"write"` lock genuinely covers the entire mutation of the shared unit caches, matching how `writer.saveJoint()` relies on that same lock for exclusivity.

### Proof of Concept
1. Let the node accumulate more than `MAX_ITEMS_IN_CACHE` (300) entries in `assocCachedUnits`/`assocKnownUnits`/`assocStableUnits` by normal unit traffic (trivially achievable by any peer posting/relaying units).
2. Wait for the periodic `setInterval(shrinkCache, 300*1000)` to fire; `shrinkCache()` acquires `"write"`, issues N `db.query` calls in a loop, then calls `unlock()` immediately (`storage.js:2274-2296`), before any of the `db.query` callbacks that perform the actual `delete assocStableUnits[...]/assocBestChildren[...]/...` have run.
3. Concurrently, have another unit arrive and be processed via `writer.saveJoint()`, which also acquires `"write"` (`writer.js:34`) — because `shrinkCache`'s lock was released early, this can proceed while the queued deletion callbacks from step 2 are still pending, interleaving writes (`storage.assocStableUnits[...] = objNewUnitProps`, `storage.assocBestChildren[...].push(...)`) with deletes (`delete assocStableUnits[row.unit]`, `delete assocBestChildren[row.unit]`) on the same maps.
4. Depending on timing, this can trigger the internal consistency-check throws in `readUnitProps()` (`storage.js:1526-1550`) or `forgetUnit()` (`storage.js:2227-2229`), crashing the node process, or silently leave `assocBestChildren`/`assocStableUnits` in a state inconsistent with the DB used by main-chain stability logic.
