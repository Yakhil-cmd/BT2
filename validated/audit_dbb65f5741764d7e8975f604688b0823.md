### Title
Missing `return` after error in `validateAndSave()` causes double invocation of the row-completion callback (double-free-style resource release) - ([File: network.js])

### Summary
`getBase64Hash(obj, bJsonBased)` calls `getJsonSourceString(obj)` (or `getSourceString`) which can throw on malformed input (e.g. unexpected types embedded in the private-payment payload). [1](#0-0) 
In `network.js`'s `handleSavedPrivatePayments()`, the inner `validateAndSave` function catches that exception, but the `catch` block calls `deleteHandledPrivateChain(..., cb)` **without returning**, so execution falls through to the rest of the function, which subsequently invokes `privatePayment.validateAndSavePrivatePaymentChain(...)`. That call's own `ifOk`/`ifError` handlers also call `deleteHandledPrivateChain(..., cb)`, so the shared `cb` (the `async.each` iteratee-done callback) ends up being invoked twice for a single row — a "double free" of the completion callback, analogous to CVE-2022-2008's double-free of a WebGL resource.

### Finding Description
`handleSavedPrivatePayments()` iterates over rows of `unhandled_private_payments` (private payment chains previously queued for later validation) using `async.each`, one `cb` per row: [2](#0-1) 

Inside the per-row handler, `validateAndSave` computes a hash of the head private element's payload:
```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){
            ...
            deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
            ...
        },
        ifError: function(error){
            ...
            deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
            ...
        },
        ...
    });
};
``` [3](#0-2) 

There is no `return` statement after the `catch` block's `deleteHandledPrivateChain(..., cb)` call, so control flow continues into the `privatePayment.validateAndSavePrivatePaymentChain(...)` call below the `catch`, using `json_payload_hash === undefined`. That call will eventually invoke either `ifOk` or `ifError`, each of which independently calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` again — passing the *same* `cb` a second time.

`deleteHandledPrivateChain` itself simply performs a `DELETE` query and calls `cb()`: [4](#0-3) 

so `cb` — the per-item completion handle owned by `async.each` — gets called twice for one item. `async.each`'s final callback fires once the expected number of iteratees have completed; calling an item's callback twice causes the overall iteration to complete (and its final callback, which calls `unlock()` on the `["saved_private"]` mutex and emits `new_my_transactions`) prematurely/incorrectly while the actually still-in-flight `validateAndSavePrivatePaymentChain` call for that same malformed row is still running against the database. [5](#0-4) [6](#0-5) 

Because the outer `mutex.lock(["saved_private"], ...)` releases its lock as soon as the (prematurely-satisfied) `async.each` final callback fires, a concurrent invocation of `handleSavedPrivatePayments()` — triggered by `new_direct_private_chains`/`new_my_transactions` events or a new incoming private payment — can start operating on `unhandled_private_payments` rows while the first, still-outstanding `validateAndSavePrivatePaymentChain` transaction for the malformed row (which opens its own `BEGIN`/`COMMIT` transaction via `db.takeConnectionFromPool`) is not yet finished. This breaks the mutual-exclusion invariant the `"saved_private"` lock is meant to guarantee for processing of saved private payments, allowing overlapping validation/commit of private payment chains that the lock was designed to serialize.

### Impact Explanation
This is reachable by any private-payment counterparty (or hub-forwarded sender) who can craft a private payment payload whose head element triggers an exception in `getBase64Hash`/`getJsonSourceString` (e.g., unsupported/edge-case value types nested in the attacker-controlled `payload` object that is JSON round-tripped through `unhandled_private_payments.json`). By doing so, the attacker forces the callback to be invoked twice, defeating the `"saved_private"` mutex's serialization guarantee for private-payment chain processing on the victim's own full/light node. Because private payment validation/commit involves marking outputs spent and crediting the local view of a private asset's chain, breaking this serialization opens a race window where two runs of private-chain validation can interleave, risking inconsistent/duplicated acceptance of a private payment chain (an internal double-spend/double-credit condition in the victim's own private-payment bookkeeping) — a control-flow corruption bug of the same class (premature release/duplicate release of a serialization primitive) as the double-free described in the CVE.

### Likelihood Explanation
Medium. Triggering the exception requires the attacker to construct a payload whose hashing throws (this is plausible with typed/edge-case values `getJsonSourceString` cannot serialize, but the exact throwing input was not confirmed in this analysis due to index limitations on `string_utils.js`'s `getSourceString`/`getJsonSourceString` implementation). The attacker only needs to send (or have forwarded via the hub) a single crafted private-payment chain reaching `handleSavedPrivatePayments`; no privileged position is required.

### Recommendation
Add a `return` after `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);` inside the `catch` block in `validateAndSave` (network.js) so that the function does not fall through to also call `privatePayment.validateAndSavePrivatePaymentChain`, guaranteeing `cb` is invoked exactly once per row. More generally, audit all `deleteHandledPrivateChain(..., cb)` call-sites to ensure each code path calls the shared iteratee callback exactly once.

### Proof of Concept
1. Attacker (private-payment counterparty or hub) sends a `private_payment_chains` message whose head element's `payload` contains a value that causes `getJsonSourceString`/`getSourceString` to throw when hashed (e.g., an unsupported nested structure) — this gets stored via `savePrivatePayment` into `unhandled_private_payments`. [7](#0-6) 
2. When `handleSavedPrivatePayments()` next processes this row, `getBase64Hash` throws inside the `try` block of `validateAndSave`.
3. The `catch` block calls `deleteHandledPrivateChain(..., cb)` (1st invocation of `cb`) but does not `return`.
4. Execution continues to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which — regardless of whether it succeeds or fails — calls `deleteHandledPrivateChain(..., cb)` again inside `ifOk`/`ifError` (2nd invocation of `cb`).
5. `async.each`'s bookkeeping is violated, causing its final callback (which calls `unlock()` on `mutex["saved_private"]`) to fire before the second, still-in-flight database transaction from `validateAndSavePrivatePaymentChain` completes, allowing a concurrently triggered `handleSavedPrivatePayments()` run to execute against `unhandled_private_payments` under the false assumption of exclusive access.
