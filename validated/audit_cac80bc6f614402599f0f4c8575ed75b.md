### Title
Operator-precedence bug in `provision?` bypasses `Repository#review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` combines `review_stacks_enabled` with the provisioning-behavior checks using `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch. The `allow_with_label`/`prevent_with_label` branches are evaluated independently of `review_stacks_enabled`, letting an attacker who can label/unlabel their own PR create a `Shipit::ReviewStack` on a repository whose operator explicitly disabled review stacks.

### Finding Description
The claimed binding is `repository.review_stacks_enabled == true` must hold before any `ReviewStack` is provisioned via `provision?`. The actual code is: [1](#0-0) 

Because Ruby's `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. If a `Repository` has `review_stacks_enabled: false` but `provisioning_behavior` left at `allow_with_label` (or `prevent_with_label`) from a prior configuration, `provision?` still returns `true` whenever the label condition matches, regardless of `review_stacks_enabled`.

`respond_to_pull_request_opened?` gates only on `action == "opened"` and `provision?`: [2](#0-1) 

If it returns true, `ReviewStackAdapter#find_or_create!` is called, and `create!` builds a `Shipit::ReviewStack` using attacker-controlled `branch: params.pull_request.head.ref` and enqueues provisioning: [3](#0-2) 

Exploit flow: attacker opens a PR (or applies the configured label) on a GitHub repository that is registered in Shipit with `provisioning_behavior: allow_with_label` and `review_stacks_enabled: false`. GitHub sends the legitimate, correctly signed `pull_request opened` webhook (attacker does not need to forge signatures — they only need to control the PR/label on a repo already connected to Shipit). `provision?` incorrectly evaluates true and a `ReviewStack` is created and queued for provisioning, even though the operator disabled review stacks for that repository.

None of the existing guards catch this: webhook signature verification and `ExplicitParameters` schema validation only confirm the webhook truly originates from GitHub for that repo, they do not enforce the `review_stacks_enabled` policy; `Repository` model validations (`app/models/shipit/repository.rb`) validate name/owner format only, not the provisioning flag combination; there is no model-level guard in `ReviewStackAdapter` or `ReviewStack` that re-checks `review_stacks_enabled` before creation.

### Impact Explanation
An unauthorized `Shipit::ReviewStack` record is created and queued for provisioning on a repository where the operator disabled review stacks. Since review-stack provisioning subsequently runs deploy tasks/commands (build/deploy pipeline), this can lead to command execution the operator did not authorize for that repository, and is repeatable for every PR/label toggle against any repository stuck in this `review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label` state. This matches "a payload for one repository mutating another's stack" / unauthorized deploy category in severity, contingent on the described misconfiguration existing.

### Likelihood Explanation
Requires a specific repository configuration state: `review_stacks_enabled: false` combined with `provisioning_behavior` still set to `allow_with_label` or `prevent_with_label` (e.g., left over from disabling review stacks without resetting provisioning behavior, since the UI/model do not appear to force `provisioning_behavior` back to a neutral value when `review_stacks_enabled` is toggled off). Given that precondition, the attacker cost is trivial: open a PR and/or apply a label they control on their own fork/branch. This is a configuration-dependent bug, not a universally exploitable one — but the code path in `provision?` is objectively wrong and would misbehave for any repository administrator who disables review stacks without also resetting `provisioning_behavior`.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three branches:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (conceptual, not to be added to out-of-scope test dirs by this audit, but describing the reproduction):
1. Create a `Shipit::Repository` with `review_stacks_enabled: false, provisioning_behavior: :allow_with_label, provisioning_label_name: "deploy-preview"`.
2. Build a `pull_request opened` payload whose `labels` include `{ name: "deploy-preview" }`.
3. Assert binding before fix: `repository.review_stacks_enabled` is `false` (LHS) vs. what `provision?` requires to create a stack should also be `false` (RHS) — they must match for no stack to be created.
4. Call `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process`.
5. Assert `Shipit::ReviewStack.count` increased by 1 (bug present) — i.e., `repository.review_stacks_enabled == false` yet a stack was created, proving LHS ≠ RHS behavior and confirming the precedence bug.
6. After applying the parenthesization fix, re-run the same test and assert `Shipit::ReviewStack.count` is unchanged (0 created), confirming the binding now holds.
