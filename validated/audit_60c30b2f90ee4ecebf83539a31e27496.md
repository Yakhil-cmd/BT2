### Title
`Api::CCMenuController` bypasses stack-scoped `ApiClient` restriction, letting a single-stack token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` enforces that an `ApiClient` scoped to a specific stack (`current_api_client.stack_id?`) can only resolve `stack` against `Stack.where(id: current_api_client.stack_id)` [1](#0-0) . `Api::CCMenuController` overrides `stack` and resolves it directly with `Stack.from_param!(params[:stack_id])` against the full `Stack` table, never consulting `current_api_client.stack_id` [2](#0-1) . The permission check that gates the action only verifies the coarse-grained `read:stack` permission string, not which specific stack the token is bound to [3](#0-2) . This breaks the binding: **stack a token authorizes == stack the action actually touches**.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [4](#0-3) , and `Api::BaseController#stacks`/`#stack` is the mechanism that enforces this scoping for every other API controller (`DeploysController`, `TasksController`, `HooksController`, etc.):

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

This is a deliberate, tested security control — e.g. `"an api client scoped to a stack will only see that one stack"` [5](#0-4) .

`Api::CCMenuController`, however, defines its own `stack` method that does not go through `stacks`:

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
``` [6](#0-5) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks the `permissions` array for the literal string `"read:stack"` — it never compares `current_api_client.stack_id` to the requested `stack_id` [3](#0-2) . Thus a valid, correctly-authenticated `ApiClient` whose `stack_id` is set to stack A, but which carries the `read:stack` permission, can hit `GET /api/stacks/:owner/:repo/:env/ccmenu` (route defined at `config/routes.rb:28`) for any other stack B and receive B's build status.

The webhook-style analog to the Pyth "verify vs. act" mismatch is direct: the binding that should hold is `token.stack_id == stack_being_read`, verified once through `check_permissions!`, but the object actually acted upon (`stack`) is resolved through a different, unscoped code path, so the check and the action are performed on inconsistent scopes — exactly the same class of bug as verifying one price/value and acting on a different one.

### Impact Explanation
This allows a caller holding an `ApiClient` token deliberately restricted to a single stack (for least-privilege API integrations, e.g. CI dashboards) to read the CCMenu XML build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of any other stack in the Shipit instance, including stacks belonging to other repositories/teams that the token was never granted access to [7](#0-6) . This is an authorization-scope bypass reading stack state that the token holder is not authorized for.

### Likelihood Explanation
Any deployment that issues stack-scoped `ApiClient` tokens (this is the intended way to hand a limited-purpose token to third-party CI dashboard tools per `CCMenuUrlController`/`ApiClient.stack`) is affected as soon as that token also carries `read:stack` permission — which is exactly the permission `CCMenuUrlController#client` grants when minting a CCMenu token [8](#0-7) . No special conditions are required beyond possessing any valid `read:stack` token and guessing/knowing another stack's `owner/repo/environment` identifier, which is not secret.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the inherited, scope-aware `stacks`/`stack` helper from `Api::BaseController` (i.e., remove the private `stack` override, or reimplement it as `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot read data for stacks outside their assigned `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to stack A: `ApiClient.create!(creator: user, name: 'ci', permissions: %w[read:stack], stack: stack_a)`.
2. Authenticate as this client and request `GET /api/stacks/:owner_b/:repo_b/:env_b/ccmenu` for unrelated stack B.
3. `require_permission :read, :stack` passes because the client has `read:stack` in its permission list [3](#0-2) .
4. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against all stacks, not `current_api_client.stack_id`-restricted ones [9](#0-8) , so stack B's build status is returned to a token that should only see stack A — analogous to `test/controllers/api/ccmenu_controller_test.rb`'s existing `"#show renders the xml"` test but performed with a stack B outside the client's assigned `stack_id`.
