### Title
Cross-organization webhook forgery: GitHub App/org whose `webhook_secret` authenticates a request is never checked against the repository the webhook payload writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App configuration (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) from `repository_owner`, which is read directly out of the unauthenticated JSON body. All downstream handlers instead resolve which `Repository`/`Stack`/`Commit` to mutate from a different, independently-controlled field of that same unauthenticated body (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all). Because these two fields are never checked for consistency, a payload that is validly signed for org A can be crafted to act on org B's repositories/commits.

### Finding Description
`verify_signature` derives the signing org solely from the payload itself, before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) selects `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is used for HMAC verification: `github_app.verify_webhook_signature(...)`. This is legitimate for single-org Shipit instances, but Shipit explicitly supports multi-org configuration where each org has its own independent `webhook_secret`: [3](#0-2) 

Once the signature passes, the event handlers never re-check `repository_owner`; they instead re-read the same untrusted JSON body using an entirely different field, `repository.full_name`, to find the target: [4](#0-3) 

`PushHandler` uses `stacks` (i.e. `Repository.from_github_repo_name(repository_name)`) to enqueue a resync for any matching, non-archived stack on the named branch: [5](#0-4) 

`StatusHandler` is worse: it does not consult `repository`/`stacks` at all, and matches purely by commit SHA across the entire Shipit instance: [6](#0-5) 

The broken binding, stated as an equality that should hold but doesn't:
`organization whose webhook_secret authenticated the request` == `organization/repository the handler subsequently writes to`.

Before the attacker's request: only genuinely GitHub-signed events for org A can affect org A's stacks, and only genuinely GitHub-signed events for org B can affect org B's stacks/commits.
After the attacker's request: an actor holding org A's `webhook_secret` (e.g. because they administer their own GitHub App/org that is one of the multiple orgs configured in this Shipit instance, and thus legitimately possesses that org's webhook secret from GitHub App setup) can sign an arbitrary payload with `repository.owner.login = "org-A"` (to pass `verify_signature`) while setting `repository.full_name = "org-B/victim-repo"` (for `push`/`check_suite`) or simply an arbitrary `sha` belonging to any tracked commit (for `status`), causing Shipit to act on org B's data despite never having proven possession of org B's secret.

### Impact Explanation
`StatusHandler` lets anyone who controls just one configured org's webhook secret forge a passing (or failing) CI status (`state`, `context`, `description`, `target_url`) attached to an arbitrary commit tracked anywhere in the Shipit instance, via `Commit#create_status_from_github!`. Commit/check statuses are the mechanism Shipit uses to gate whether a commit is considered safe (its "checks"/CI signal), so an attacker can spoof a green build for a victim organization's commit they do not control, without ever authenticating to that organization's GitHub App. `PushHandler` similarly lets the same attacker enqueue `Stack#sync_github` for any tracked branch of any other configured organization's repository, using a signature that only proves control of a different org's secret. This crosses an authentication boundary between organizations that the multi-org GitHub App design is meant to enforce, matching the "authorization bypass" / "unauthorized deploy"-adjacent class of impact (feeding a forged trust signal — a fake status check — into a different organization's release pipeline).

### Likelihood Explanation
Requires the attacker to legitimately control (or have compromised) at least one of the multiple GitHub App configurations registered in the same Shipit instance's `secrets.yml` (i.e. know that org's `webhook_secret`) — a realistic scenario for any Shipit deployment shared across several organizations/teams, which the engine explicitly supports via keyed `github:` config. No GitHub write access, Shipit session, or `ApiClient` token to the victim org is needed; only the ability to send a raw HTTP POST to the shared `/webhooks` endpoint with a correctly-signed body for the attacker's own org.

### Recommendation
Bind the signature-verification org to the same field used by the handlers to select the affected repository (`repository.full_name`, or `organization.login` for org-level events), and reject the payload if `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`. `StatusHandler` (and any other handler that does not scope by `stacks`) should be changed to additionally filter matched commits/stacks by the repository asserted in the payload and verified against the authenticating org, e.g. `Commit.where(sha: params.sha).where(stack: Repository.from_github_repo_name(repository_name)&.stacks)`.

### Proof of Concept
1. Attacker administers a GitHub App/org "attacker-org", which is one of several organizations configured under `Shipit.github` in `secrets.yml`, and thus knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<sha of a commit belonging to victim-org/victim-repo tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and sends it to `POST /webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit purely by SHA, with no relation to `attacker-org` — and calls `create_status_from_github!`, injecting a forged "success" status onto a commit the attacker never authenticated for.
