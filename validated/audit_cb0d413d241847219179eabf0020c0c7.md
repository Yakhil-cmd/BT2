The reported bug is specific to Balancer's `BPTOracle.sol` `BptPriceStablePool()` function, which computes a stable-pool BPT valuation by taking the minimum of constituent token USD prices and multiplying by a single pool-level `IRateProvider(poolAddress).getRate()`, without first normalizing each token's price by its own per-token rate provider. This is a DeFi AMM-specific oracle pricing bug tied to Balancer's stable-pool architecture (multiple pegged tokens each with individually different rate providers).

`pallet-asset-conversion` in this repo is the closest conceptual analog (an on-chain AMM/LP pallet), but it implements a constant-product (Uniswap V2 style) two-asset pool, not a Curve/Balancer-style multi-token "stable pool" with per-token `RateProvider`s and peg normalization [1](#0-0) . Its pricing/quoting logic (`quote_price_exact_tokens_for_tokens`, `quote_price_tokens_for_exact_tokens`, `get_reserves`) is based on reserve ratios via `get_amount_out`/`get_amount_in`/`quote`, not on comparing a "minimum" of independently-sourced USD prices across multiple pegged assets with heterogeneous rate providers [2](#0-1) [3](#0-2) . There is no "min of USD prices across pool tokens then multiply by a single pool rate" pattern, no per-token `RateProvider` normalization step, and no BPT-style LP valuation oracle in this codebase that mirrors the flawed invariant described in the report.

Searches for stable-pool pricing, LP/BPT valuation, and rate-provider normalization patterns across the indexed codebase found only the constant-product AMM pallet and unrelated price-oracle pallets (`pallet-oracle`, `pallet-broker`'s `MinimumPrice` price adapter for coretime sales) [4](#0-3) [5](#0-4) , neither of which shares the structural invariant (multi-asset peg-normalized minimum pricing) that the Balancer report is about. Forcing this Solidity/Balancer-specific stable-pool oracle bug onto FRAME's asset-conversion pallet would not be a faithful analog, per the scan's own instruction not to force an EVM analogy onto FRAME.

/// `AdaptPrice` like `CenterTargetPrice`, but with a minimum price.
///
/// This price adapter behaves exactly like `CenterTargetPrice`, except that it takes a minimum
/// price and makes sure that the returned `end_price` is never lower than that.
///
/// Target price will also get adjusted if necessary (it will never be less than the end_price).
pub struct MinimumPrice<Balance, MinPrice>(core::marker::PhantomData<(Balance, MinPrice)>);

impl<Balance: FixedPointOperand, MinPrice: Get<Balance>> AdaptPrice<Balance>
	for MinimumPrice<Balance, MinPrice>
{
	fn leadin_factor_at(when: FixedU64) -> FixedU64 {
		CenterTargetPrice::<Balance>::leadin_factor_at(when)
	}

	fn adapt_price(performance: SalePerformance<Balance>) -> AdaptedPrices<Balance> {
		let mut proposal = CenterTargetPrice::<Balance>::adapt_price(performance);
		let min_price = MinPrice::get();
		if proposal.end_price < min_price {
			proposal.end_price = min_price;
		}
		// Fix target price if necessary:
		if proposal.target_price < proposal.end_price {
			proposal.target_price = proposal.end_price;
		}
		proposal
	}
}
