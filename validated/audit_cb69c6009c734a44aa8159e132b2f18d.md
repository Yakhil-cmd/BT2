## Title
Cross-organization commit-status forgery via webhook signature scoped to the wrong tenant - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a GitHub webhook against the `webhook_secret` of a *single organization*, derived from `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . Once that check passes, the entire raw payload is handed to the event handlers, which act on data that is **not** re-scoped to the authenticated organization. `StatusHandler` in particular resolves the target purely by commit SHA, globally across the whole database: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .

### Finding Description
The binding that should hold is: *the organization whose `webhook_secret` authenticated the request* == *the organization whose data the request is allowed to mutate*. This engine breaks that binding for the `status` webhook event.

- `verify_signature` picks a `github_app` using `Shipit.github(organization: repository_owner)`, where `repository_owner` comes from the payload's `repository.owner.login` (or `organization.login`) [1](#0-0) . This only proves the request was signed with the secret configured for that *claimed* organization.
- `StatusHandler#process` never re-checks that the commit being updated actually belongs to a stack/repository under that organization. It matches purely by SHA, which is attacker-controlled, unscoped, and collides across any repositories tracked by the same Shipit instance: `Commit.where(sha: params.sha)` [3](#0-2) .
- Multi-organization deployments of Shipit are an explicitly supported configuration — each org gets its own `webhook_secret`, `app_id`, `private_key`, etc. [4](#0-3) .

As a result, an attacker who legitimately controls (or has learned) the webhook secret for Organization A — e.g., because they administer a GitHub App/webhook for a repo they own inside Org A, which is tracked by the same Shipit instance — can craft a `status` event payload where `repository.owner.login` = `"OrgA"` (so `verify_signature` passes using OrgA's real secret) but `sha` is the SHA of a commit belonging to a completely different tenant, Organization B, also served by the same Shipit instance. `StatusHandler` will happily write a forged `Status` (`state`, `context`, `description`, `target_url`) onto Org B's commit, because nothing in the handler chain re-validates that the SHA belongs to a repository under the authenticated organization.

### Impact Explanation
Commit statuses are the mechanism Shipit uses to gate safety: `required_statuses`, `blocking_statuses`, and continuous-deployment checks in `DeploySpec` consult `Commit#statuses` to decide if a commit is deployable. By forging a `state: "success"` status with a `context` matching a required/blocking check on someone else's commit, a caller who only owns credentials for an unrelated organization can cause Shipit to treat Org B's commit as CI-green, unblocking an otherwise-blocked deploy — this is an **unauthorized deploy** authorization bypass across a repository the attacker has no legitimate relationship with, satisfying the "unauthorized deploy" Critical impact category defined in scope.

### Likelihood Explanation
Requires: (1) the target Shipit instance manages more than one GitHub organization/repository (explicitly supported and documented via `Shipit.github(organization:)` and per-org secrets), and (2) the attacker holds a valid webhook secret for *any one* of those organizations (e.g., as a legitimate GitHub App admin/webhook owner for their own org, not for the victim org). No repository write access, GitHub token, or Shipit session is required — only knowledge of one org's `webhook_secret`, which is exactly the credential the unprivileged-attacker rule anticipates being crossed against a different resource's boundary.

### Recommendation
`StatusHandler` (and other handlers relying only on `payload.dig('repository', ...)`) must verify that the resolved `Commit`/`Repository` actually belongs to the same organization/repository owner that was used to select the `webhook_secret` in `verify_signature`, rejecting or filtering out commits whose stack's repository owner does not match `repository_owner`. Alternatively, scope the `Commit.where(sha: params.sha)` lookup by joining through `stacks.repositories.owner` and comparing to the authenticated organization before calling `create_status_from_github!`.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `OrgA` and `OrgB`, each tracking at least one stack (as supported by `config/secrets.*.yml`).
2. As an attacker with legitimate control of `OrgA`'s webhook secret (e.g., because you own a repo in OrgA that Shipit tracks and you can configure/read its webhook secret), compute a valid `X-Hub-Signature` for a crafted JSON body:
```json
{
  "sha": "<sha of a commit belonging to a Stack under OrgB>",
  "state": "success",
  "context": "<required/blocking context name used by OrgB's stack>",
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. POST this to `/webhooks` with header `X-Github-Event: status` and the OrgA-computed signature.
4. `verify_signature` resolves `repository_owner == "OrgA"` and validates the signature using OrgA's real secret — passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds OrgB's commit (unscoped by organization), and calls `create_status_from_github!`, writing a forged green CI status onto OrgB's commit even though the request was never authenticated against OrgB's credentials.
