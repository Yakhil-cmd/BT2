### Title
Tokens transferred directly to the pool or controller are permanently locked with no recovery path - (File: contracts/pool/src/lib.rs)

### Summary
The XOXNO Lending pool deliberately does not credit unsolicited inbound token transfers to any market's `cash` book, and neither the pool nor the controller exposes any sweep/rescue/skim entrypoint. Any tokens sent directly to the pool or controller address — outside of `supply`/`repay`/`recapitalize` — become unbooked surplus that no unprivileged or privileged flow can ever withdraw, permanently freezing the funds.

### Finding Description
The pool's reserve accounting is a tracked book, not the token balance: "Reserve checks use tracked market cash; token donations alone do not increase it" (INV-ACCT-02, `docs/reference/invariants.md`), and "direct donations do not automatically increase booked cash" (`docs/reference/architecture.md`, Custody and accounting). The threat model confirms: "One token listed in several hubs shares physical pool custody even though market books are separate. Direct donations do not rewrite those books" (`docs/explanation/threat-model.md`).

The test `pool_all_money_paths_preserve_books_and_shared_token_custody` in `tests/test-harness/tests/pool_money_flow_audit.rs` codifies this: a `token.transfer` to the pool leaves `state.cash` unchanged, so `token.balance(pool) = cash_market1 + cash_market2 + donation`, and the donation is visible only as excess physical balance.

Crucially, every outbound flow is gated by the book, not the balance:

- `withdraw` and `borrow` pass `Cache::require_reserves`, which debits/checks `cash` — donated tokens are invisible to it.
- `repay` and `recapitalize` refunds pay out the excess of the *funded, measured* receipt; they never reference unbooked surplus.
- `claim_revenue` pays only booked `revenue` shares.
- A grep across `contracts/pool/src` and the controller shows no `sweep`/`rescue`/`skim`/`recover` function — there is no governance or owner path that returns unbooked tokens either (pool mutations require the controller as owner, and the controller itself holds no stranded-asset recovery; the threat model explicitly notes "the adapter has no recovery path for arbitrary stranded assets" as an analogous design fact).

The same applies to tokens pushed to the controller: "Refunds cover only positive callback deltas of refund-listed tokens... Neither category sweeps prior balances" — prior stray balances are never returned.

This mirrors the Allo `fundPool` lock: an unprivileged user can move funds into the custody contract (direct SAC `transfer`, Aquarius reward push, liquidation misroute, or simply a mistaken transfer) at a time when the protocol gives no credit, and the protocol offers no `withdraw` for that surplus. Because the same physical balance backs multiple hub markets, the lock applies across every spoke of that token.

### Impact Explanation
Permanent freezing of funds. Any token amount that reaches the pool or controller address without going through a measured inbound entrypoint is locked forever — no book ever claims it, no exit leg can spend it (all exits are book-bounded), and no recovery function exists. Unlike Allo, this is not merely theoretical: the codebase documents real sources of pushed tokens (e.g., Aquarius venue rewards claimable by any caller pushing into the pool address, `docs/explanation/threat-model.md`), and users/liquidators can fat-finger a direct `transfer` expecting credit.

### Likelihood Explanation
Medium. The trigger requires only a plain `token.transfer` — reachable by any unprivileged address, and also reachable involuntarily via third-party reward pushes. The probability of accidental transfers is non-trivial (the SKILL guide explicitly warns liquidators that "transferring repayment directly to the pool is a donation"), and the protocol's own design guarantees the funds can never be recovered once sent.

### Recommendation
Add a recovery entrypoint that pays out only the unbooked surplus: `token.balance(pool) − Σ_markets(cash + outstanding in-flight obligations)`, callable by governance or permissionlessly to a treasury address. Alternatively, skim donations into `cash`/revenue at the start of measured inbound ops so the surplus is at least claimable by suppliers/revenue rather than permanently locked.

### Proof of Concept
```rust
// In any environment where `pool` is deployed (pattern from
// tests/test-harness/tests/pool_money_flow_audit.rs):
let market = resolve_market("USDC");
let token = token::Client::new(&env, &market.asset);

// 1. Attacker/victim sends tokens directly to the pool (no supply call).
token_admin.mint(&victim, &1_000 * UNIT);
token.transfer(&victim, &market.pool, &1_000 * UNIT);

// 2. The book is unchanged; custody exceeds all books.
let state = pool.get_sync_data(&key).state;
assert_eq!(token.balance(&market.pool), state.cash + 1_000 * UNIT);

// 3. No entrypoint can release the surplus:
//    - withdraw/borrow are bounded by `cash` via require_reserves
//    - repay/recapitalize refunds only return funded excess
//    - claim_revenue pays only booked revenue shares
//    - no sweep/rescue function exists in contracts/pool/src/lib.rs
// Result: the 1_000 * UNIT is permanently locked.
```
