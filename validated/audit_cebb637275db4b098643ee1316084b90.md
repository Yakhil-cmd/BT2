Confirmed root cause: `handleAATriggers` in `main_chain.js` only queues an AA trigger when `outputs.asset IS NULL OR is_private=0` [1](#0-0) , and `insertAADefinitions`/`checkBalances` build `aa_balances` from outputs filtered by `(is_private=0 OR is_private IS NULL)` [2](#0-1) [3](#0-2) . Meanwhile an AA explicitly refuses to spend a private asset it holds ("sending private asset from AA") [4](#0-3) . This is the exact bug class from the report: real value can land at an address (here, private payment outputs sent to an AA address) while the tracked ledger (`aa_balances`/`balance[]`) and the trigger mechanism both ignore it, and the code path that would spend it out is blocked, so the funds become permanently stuck with no funnel-back mechanism.

### Title
Private payments received by an AA are permanently locked because AA balance tracking and outgoing payment logic both exclude private assets - (File: aa_composer.js, main_chain.js, storage.js)

### Summary
Any unprivileged wallet can send a private (blackbytes-style) payment to an Autonomous Agent's address. `handleAATriggers` explicitly excludes private outputs from what triggers an AA (`outputs.asset IS NULL OR is_private=0`), so the AA is never invoked in response to receiving this value, and `aa_balances`/`balance[]` (the only asset-balance abstraction oscript exposes) is likewise populated only from non-private outputs. As a result the AA's own accounting never reflects that it received these coins. Even if a developer wrote AA logic intending to relay any incoming asset back to the sender, `sendUnit()` bounces with `"sending private asset from AA"` whenever a message tries to pay out a private asset, so there is no way for an AA to ever spend or forward such funds. The coins sit as valid, unspent, private outputs at the AA's address forever, since only the AA (as an oscript program, with no private keys) can author units from that address, and AA logic can neither see them (no trigger, no balance[] entry) nor send them (explicit private-asset ban in `completePaymentPayload`/`sendUnit`).

### Finding Description
1. Trigger selection excludes private outputs to AA addresses:
```
WHERE units.main_chain_index = ? AND units.sequence = 'good' AND (outputs.asset IS NULL OR is_private=0)
``` [5](#0-4) 
This means a private payment landing at an AA address never enqueues an `aa_triggers` row and the AA's formula never runs to acknowledge, process, or forward it.

2. `aa_balances`, the ledger read by the `balance[...]` oscript primitive, is built and reconciled purely from non-private outputs:
```
... WHERE address=? AND is_spent=0 AND sequence='good' AND ... AND (is_private=0 OR is_private IS NULL) ...
``` [2](#0-1) 
and the periodic consistency check `checkBalances()` uses the identical filter when recomputing `calculated_balance` from `outputs`:
```
WHERE is_spent=0 AND sequence='good' AND (...) AND (is_private=0 OR is_private IS NULL)
``` [6](#0-5) 
So even an AA whose oscript reads `balance[asset]` will never see the private funds it holds; there is no accounting hook at all for this asset class.

3. Outgoing AA payments of a private asset are hard-blocked:
```
if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs
    return cb("sending private asset from AA");
``` [4](#0-3) 
`pickDivisibleCoinsForAmount`, used to select the outputs for `sendUnit`, can generate `spend_proof`s for a private asset, but an AA has no private state to author the proof outside consensus visibility that would satisfy validation for a non-AA-triggerable scenario, hence the explicit early bounce rather than attempting it.

This mirrors precisely the reported bug class: value flows into a smart-contract-like account through a path the account's internal balance bookkeeping (`aa_balances`/`balance[]`, the direct analogue of `lockedFunds`) does not track, and no mechanism exists to reconcile or funnel this untracked value back out, so it becomes permanently inaccessible even though it is a real, spendable, valid on-chain output.

### Impact Explanation
Any address that is an AA can be sent a private payment (a normal wallet operation any user can perform, exactly like sending blackbytes to any base32 address, since `is_private` payments are validated generically and do not require the recipient to be a non-AA [7](#0-6) ). Once landed at an AA address, that value is unrecoverable: no trigger fires to process it, no `balance[]` reflects it, and even a specially-written AA cannot pay it back out. This constitutes permanent freezing of user funds (medium/high severity fund loss), and it can be triggered by any unprivileged unit poster or private-payment counterparty without any special privilege, simply by choosing an AA as the recipient of a private payment (by mistake, or maliciously to grief a specific AA/DAO's treasury tracking, or as a griefing vector against wallets that don't distinguish AA vs non-AA recipients for private sends).

### Likelihood Explanation
Likelihood is high: sending a private payment is a normal, unauthenticated wallet feature (`private_payment.js`, `divisible_asset.js` compose private payloads whenever `objAsset.is_private`), and nothing in the payment validation path forbids the recipient address from being an AA. No special timing, race condition, or validator collusion is needed — a single ordinary private transfer to any AA address suffices to permanently lock the transferred value.

### Recommendation
Either (a) reject/refuse validation of private-asset outputs whose address is a known AA address (mirroring the existing `checkNotAAs` pattern already used elsewhere for OP lists, at `validation.js:2053`) so such payments can never be created, or (b) add explicit accounting and a permitted send path for private assets held by AAs (tracking them in `aa_balances` and allowing `sendUnit` to construct valid spend proofs for private outputs an AA legitimately owns), so the funds are not silently and permanently stranded.

### Proof of Concept
1. Deploy any AA (e.g., the default no-op contract from `test/samples/create_an_asset.oscript`).
2. From a normal wallet, compose and send a private payment (blackbytes-style asset, `is_private: true`) with the AA's address as the sole recipient, using `divisibleAsset.composeDivisibleAssetPaymentJoint`/`private_payment.js` flow.
3. Observe: `handleAATriggers` in `main_chain.js:1691-1706` never inserts a row into `aa_triggers` for this unit (filter excludes `is_private=1` outputs), so the AA never runs.
4. Query `aa_balances` for the AA address/asset — it shows no entry / 0, confirming `storage.js:954-961` never counted the private output.
5. Attempt to write an AA that tries to relay any incoming asset with `app: 'payment', payload: { asset: "{trigger...}" }` for that private asset — `aa_composer.js:1329-1330` unconditionally bounces with `"sending private asset from AA"`.
6. The private output remains `is_spent=0` in the `outputs` table indefinitely, with no code path in the codebase capable of spending it from the AA address.
