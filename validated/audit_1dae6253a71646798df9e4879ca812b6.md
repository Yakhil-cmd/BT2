### Title
Multisig `k`-of-`n` quorum check silently converts an owner's explicit rejection vote into an implicit approval when that owner executes - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction` (invoked by the VM during prologue/admission of `MultisigTransaction`) and `transaction_execution_cleanup_common` compute the approval count used for the k-of-n quorum check using `has_voted_for_approval`, which returns `false` both when an owner has *not voted* and when an owner has *explicitly voted to reject*. Both call sites then unconditionally add +1 "implicit approval" for the executing owner whenever `has_voted_for_approval` is `false`, without distinguishing "never voted" from "voted no." This lets an owner who explicitly rejected a pending multisig transaction later flip their own vote to a counted approval simply by calling execute, inflating `num_approvals` past the required threshold even though the actual number of owners who affirmatively approved is one short of quorum.

### Finding Description
`has_voted_for_approval` is defined as: [1](#0-0) 

It only distinguishes "voted `true`" from "everything else" (including an explicit `false`/reject vote), so it cannot tell a *silent* owner from a *dissenting* owner.

`validate_multisig_transaction` — the VM-only function called during transaction admission for every `MultisigTransaction` — uses exactly this predicate to add an implicit approval for the executing owner: [2](#0-1) 

The same pattern is repeated in the post-execution cleanup path used by both the success and failure epilogues: [3](#0-2) 

And the identical logic exists in the `can_execute` view function that off-chain clients rely on to predict admission: [4](#0-3) 

Consequence: if owner `O` calls `reject_transaction` (recording `votes[O] = false`), then later (or in the same flow) calls the execute entry point for the same multisig transaction, `has_voted_for_approval(..., O)` still returns `false` (because `voted && vote` is `false` when `vote == false`), so the code adds `num_approvals += 1` for `O` as if `O` had never voted and were implicitly approving by executing. `O`'s on-chain rejection vote is silently overridden for quorum-counting purposes without any explicit `approve_transaction` call and without an event correcting the earlier `Vote{approved:false}` record (the rejection event/state itself is not deleted — only the quorum arithmetic is wrong).

### Impact Explanation
This is a pre-admission mismatch at the transaction-execution boundary for multisig accounts: a `MultisigTransaction` that should be rejected by the prologue's quorum check (`ENOT_ENOUGH_APPROVALS`) because a required owner explicitly voted against it can instead pass admission and execute, because the executing-owner's dissent is silently recounted as consent. In a k-of-n scheme where every genuine approval is required to reach the threshold, this allows execution of a transaction (e.g., moving funds, changing owners, rotating keys) without the intended level of authorization from the owner set — a wrong-approval-set admission bypass analogous to the underlying report's "partial state treated as full/complete."

### Likelihood Explanation
The path is reachable by any owner of any multisig account using the standard `create_multisig_account` flow (no special privilege beyond being a listed owner), simply by voting reject and then invoking execution (or having another party route the reject-then-execute sequence). It requires the `multisig_v2_enhancement` feature flag path in `validate_multisig_transaction`/`transaction_execution_cleanup_common`, but no admin/governance grants are needed. It only manifests in the edge case where the rejecting owner is themselves the executor and their vote determines whether quorum is met, so it is a corner case rather than a universally-triggered bug, but it directly relies on normal transaction admission and multisig approval-counting code, matching the required admission pivot around "authenticator/multisig approval validation accepting the wrong approval set."

### Recommendation
Change `has_voted_for_approval` usage in `validate_multisig_transaction`, `transaction_execution_cleanup_common`, and `can_execute` so the implicit approval is added only when the owner has **not voted at all**, not merely when they haven't voted "yes." I.e., use a check like `!has_voted(...)` (voted status regardless of value) rather than `!has_voted_for_approval(...)`, so that an owner who explicitly rejected cannot have their vote silently reinterpreted as an approval for quorum purposes.

### Proof of Concept
1. Create a 2-of-2 multisig account with owners `A` and `B`.
2. `A` calls `create_transaction` (implicitly approves) — 1 approval recorded.
3. `B` calls `reject_transaction` — `votes[B] = false` recorded (1 rejection, 0 additional approvals; only 1 of 2 required approvals present).
4. `B` (the same owner who rejected) submits a `MultisigTransaction` to execute the pending transaction.
5. During prologue, `validate_multisig_transaction` computes `num_approvals_and_rejections` → `(1, 1)`; then checks `has_voted_for_approval(multisig, seq, B)` → `false` (B voted, but `vote == false`), so `num_approvals += 1` → `2`.
6. `assert!(num_approvals >= num_signatures_required(...))` → `2 >= 2` passes, and the transaction executes — despite `B` never having approved it and only 1 genuine approval existing among 2 required.

    inline fun transaction_execution_cleanup_common(executor: address, multisig_account: address): u64 {
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        let implicit_approval = !has_voted_for_approval(multisig_account, sequence_number, executor);

        let multisig_account_resource = borrow_global_mut<MultisigAccount>(multisig_account);
        let (num_approvals, _) = remove_executed_transaction(multisig_account_resource);

        if (features::multisig_v2_enhancement_feature_enabled() && implicit_approval) {
            emit(
                Vote {
                    multisig_account,
                    owner: executor,
                    sequence_number,
                    approved: true,
                }
            );
            num_approvals += 1;
        };

        num_approvals
    }
