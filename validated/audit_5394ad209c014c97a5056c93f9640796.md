### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repos - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` across every branch, but `OpenedHandler#provision?` only ANDs `review_stacks_enabled` with the `allow_all` branch due to Ruby `&&`/`||` precedence. For a repository configured with `provisioning_behavior = allow_with_label` or `prevent_with_label` and `review_stacks_enabled = false`, opening a matching pull request still creates and queues-for-provisioning a `ReviewStack`, while the equivalent `labeled` event correctly refuses.

### Finding Description
The claimed-safe binding is: `review_stacks_enabled == false` ⇒ no stack creation/mutation, for every PR lifecycle event on that repository.

`LabeledHandler#respond_to_label_change?` enforces this correctly: [1](#0-0) 
`review_stacks_enabled` is `&&`-chained with the other three conditions in one flat expression, so `false` short-circuits the whole predicate regardless of `provisioning_behavior`.

`OpenedHandler#provision?` does not: [2](#0-1) 
Because `&&` binds tighter than `||` in Ruby, this parses as:
```
(review_stacks_enabled && provisioning_behavior_allow_all?) ||
(provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
`review_stacks_enabled` is scoped only to the `allow_all` disjunct. If the repository is configured with `provisioning_behavior_allow_with_label?` (PR carries the label) or `provisioning_behavior_prevent_with_label?` (PR lacks the label), `provision?` returns `true` even when `review_stacks_enabled` is `false`.

`process` then unconditionally calls `find_or_create!`, which creates the `ReviewStack` and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) [4](#0-3) 

No existing guard prevents this: `params` schema validation, `verify_signature`/`drop_unhandled_event` and `Repository` model validators only constrain payload shape and webhook authenticity, not this authorization logic; they do not touch the `review_stacks_enabled` gate. The existing test suite for `OpenedHandler` only exercises `review_stacks_enabled: false` combined with `behavior: :allow_all` ("only provision stacks for repos with auto-provisioning enabled" at [5](#0-4) ), never combined with `allow_with_label`/`prevent_with_label`, so the gap is untested and unnoticed.

Attack: for a repository already tracked by Shipit with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` (or `prevent_with_label`), an attacker who can open a pull request against that repository (and, for `allow_with_label`, apply the configured label to their own PR — labeling one's own PR requires no special permission if the repo permits it, or the label may already be default-added by automation) causes GitHub to emit an `opened` webhook. `OpenedHandler.provision?` returns `true` despite the org/operator having disabled review stacks for that repo, creating and queuing a `ReviewStack` for provisioning.

### Impact Explanation
This is an authorization-gate bypass: a repository owner/operator that disabled review-stack auto-provisioning (`review_stacks_enabled = false`) still gets stacks created and queued for provisioning purely from an `opened` PR event, whenever `provisioning_behavior` is `allow_with_label` or `prevent_with_label`. This results in unauthorized creation of infrastructure-provisioning work (`ReviewStackProvisioningQueue.add(stack)`) for a repository that explicitly opted out, i.e. an unauthorized deploy/provision action taken on behalf of a repository that did not authorize it via its current configuration. It is repeatable for every PR opened against that repository (one stack per PR/environment `pr#{number}`), but is confined to repositories that carry this specific configuration combination — it does not cross repository boundaries or leak credentials.

### Likelihood Explanation
The repository must already be tracked by Shipit, must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`, and must have `review_stacks_enabled` set to `false` — a plausible real-world state (e.g., an operator temporarily disabling review stacks without resetting `provisioning_behavior` back to `allow_all`). Given that configuration, any actor able to open a pull request (and, for `allow_with_label`, apply/have the label present) triggers the bug at zero cost, with no authentication beyond normal repository interaction, and is fully repeatable.

### Recommendation
Parenthesize `provision?` so `review_stacks_enabled` gates all three branches, mirroring `LabeledHandler#respond_to_label_change?`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_review_stacks_disabled_test.rb
test "review_stacks_enabled=false blocks LabeledHandler but not OpenedHandler for allow_with_label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  labeled_payload = payload.merge("action" => "labeled")
  labeled_handler = Shipit::Webhooks::Handlers::PullRequest::LabeledHandler.new(labeled_payload)
  assert_equal false, labeled_handler.send(:respond_to_label_change?),
    "LabeledHandler must refuse to act when review_stacks_enabled is false"

  opened_handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload)
  assert_equal true, opened_handler.send(:provision?),
    "BUG: OpenedHandler#provision? ignores review_stacks_enabled for allow_with_label"

  assert_difference -> { Shipit::Stack.count } do
    opened_handler.process
  end
end
```
This demonstrates the equality `LabeledHandler.respond_to_label_change? (false) != OpenedHandler.provision? (true)` for the identical repository configuration (`review_stacks_enabled: false`), confirming the divergence and the resulting unauthorized `Shipit::Stack` creation.
