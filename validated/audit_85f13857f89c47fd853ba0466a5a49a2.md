### Title
Cross-tenant `status` webhook forgery via unscoped `Commit.where(sha:)` lookup bypassing per-organization signature verification - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify a webhook against using the attacker-controlled `repository.owner.login`/`organization.login` field from the JSON body, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org has no `webhook_secret` configured. `StatusHandler#process` then mutates `Commit`/`Status` records found purely by `sha`, with zero repository or organization scoping, so a forged `status` event "authenticated" against an unrelated, secret-less org can write a `Status` onto a commit/stack belonging to a completely different, properly-secured organization.

### Finding Description
The broken binding is: `organization_used_for_signature_check (repository_owner from params) == organization_that_actually_owns_the_mutated_Commit/Stack`. This equality is never checked.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` straight from the untrusted payload (`app/controllers/shipit/webhooks_controller.rb:59-62`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) does `return true unless webhook_secret` — if the org named in the payload has no configured `webhook_secret` (an explicitly "optional" setting per `docs/setup.md:30`), the signature check is a no-op and always passes, no matter what signature (or none) is sent.
- Once the request passes this per-org gate, `WebhooksController#create` dispatches to `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This query has no `stack_id`, `repository`, or organization filter — it matches any `Commit` row in the entire database sharing that `sha`.
- `Commit#create_status_from_github!` → `Status.replicate_from_github!(stack_id, ...)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:23-33`) creates a `Status` scoped to the *victim commit's real* `stack_id`, which fires `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:18-19`) and, in `Commit#add_status`, `stack.schedule_merges if new_status.pending? || new_status.success?` (`app/models/shipit/commit.rb:379-384`).

Exploit flow: attacker learns the `sha` of a commit on a victim stack (trivial — PR head SHAs, push SHAs, and commit history are public GitHub information, and with `review_stacks_enabled=true, allow_all` the attacker's own PR already creates a tracked commit/stack with a known SHA). Attacker sends `POST /webhooks` with header `X-Github-Event: status`, body `{"sha": "<victim-sha>", "state": "success", "repository": {"owner": {"login": "<org-with-no-webhook_secret>"}}}`. `verify_signature` resolves the GitHub App config for `<org-with-no-webhook_secret>`, finds no secret, and accepts unconditionally. `StatusHandler` then writes a forged "success" `Status` onto the victim's real commit/stack.

Existing guards do not stop this: `verify_signature` only guarantees the *request as a whole* matches *some* configured org's secret (or that org has none); it never re-validates that the `sha`/commit being touched actually belongs to that org's repositories. `ExplicitParameters` (`StatusHandler.params`) only validates types/shapes of `sha`/`state`, not ownership. No `Repository`/`Stack` scoping exists in the query at all.

### Impact Explanation
This is a payload nominally "from" one (attacker-reachable, secret-less) organization mutating another organization's `Commit`/`Stack`/`Status` records — explicitly listed as Critical impact ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). Concretely:
- Forging `state: success` on a commit whose stack has `continuous_deployment: true` triggers `ContinuousDeliveryJob` (`app/models/shipit/commit.rb:281-287`, `app/models/shipit/deploy.rb:327-331`) → an unauthorized deploy executing the stack's `shipit.yml` deploy commands (`Command`/`PTY.spawn`).
- Forging `state: success`/`pending` triggers `stack.schedule_merges` → `ProcessMergeRequestsJob`, potentially auto-merging a PR that never actually passed CI.
- Combined with `review_stacks_enabled: true, allow_all`, the attacker's own externally-created PR already yields a fully-known, tracked commit SHA and a review stack that runs `shipit.yml`; the forged status amplifies this by letting the attacker fake CI success/failure signals on that (or any other) stack it does not own, regardless of that stack's own webhook secret.
- The bug is repeatable against arbitrary commits/stacks across the whole Shipit installation, as long as one configured org lacks a `webhook_secret` — a single misconfigured tenant undermines the isolation of every other tenant sharing the instance.

### Likelihood Explanation
Preconditions: the Shipit deployment must be running the multi-org `github:` config schema with at least one organization that has no `webhook_secret` set (explicitly documented as optional, so realistic), and the attacker must know a target `sha` (public GitHub data, and trivially attacker-supplied via their own PR when `review_stacks_enabled + allow_all`). No Shipit credentials, sessions, or GitHub secrets are required — the attacker only needs to send one unauthenticated HTTP POST. This is cheap, fully repeatable, and does not depend on any race condition or timing.

### Recommendation
- In `StatusHandler#process` (and analogously in other handlers keyed only by `sha`/loose identifiers), scope the `Commit` lookup by the repository/organization that was actually verified in `WebhooksController#verify_signature` — e.g., resolve `Repository.from_github_repo_name(params.repository.full_name)` and restrict `Commit.where(sha: params.sha, stack: repository.stacks)` (or equivalent), rejecting any commit whose stack's repository doesn't match the verified org/repo.
- Treat a missing `webhook_secret` as a hard misconfiguration warning rather than an implicit "trust everything" bypass, or at minimum require that verification tie the specific repository in the payload to a repository that Shipit tracks for that org before any mutation occurs.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "forged status from a secret-less org mutates an unrelated stack's commit" do
  victim_commit = shipit_commits(:first) # belongs to a stack under an org WITH a webhook_secret configured

  # Attacker-controlled org that has no webhook_secret configured
  attacker_org_config = { webhook_secret: nil }
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", attacker_org_config)
  )

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: victim_commit.sha,
    state: 'success',
    repository: { owner: { login: 'attacker-org' } } # unrelated to victim_commit's real org
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  assert_response :ok

  # Binding under test: organization used to verify signature (attacker-org, no secret)
  # must equal organization that owns victim_commit's stack — it does NOT, yet the write succeeded.
  refute_equal 'attacker-org', victim_commit.stack.repository.owner
end
```
This demonstrates the invariant "a forged `status` event cannot produce a state change on a stack it did not authenticate" is violated: the request is verified against `attacker-org`'s (secret-less) config, yet mutates `victim_commit`, which belongs to a different, properly-secured organization/stack.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  class Status < Record
    include Common
    include DeferredTouch

    STATES = %w[pending success failure error].freeze
    enum :state, STATES.zip(STATES).to_h

    belongs_to :stack, required: true
    belongs_to :commit, required: true

    deferred_touch commit: :updated_at

    validates :state, inclusion: { in: STATES, allow_blank: true }, presence: true

    after_create :enable_ci_on_stack
    after_commit :schedule_continuous_delivery, :broadcast_update, on: :create

    delegate :broadcast_update, to: :commit

    class << self
      def replicate_from_github!(stack_id, github_status)
        find_or_create_by!(
          stack_id:,
          state: github_status.state,
          description: github_status.description,
          target_url: github_status.target_url,
          context: github_status.context,
          created_at: github_status.created_at
        )
      end
    end

    private

    def enable_ci_on_stack
      commit.stack.enable_ci!
    end

    def schedule_continuous_delivery
      commit.schedule_continuous_delivery
    end
  end
end
