### Title
Cross-organization/cross-repository commit-status forgery leading to unauthorized continuous deployment - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook handler resolves the target `Commit` purely by `sha`, with no scoping to the GitHub organization/repository whose signature was actually verified. Because Shipit's webhook signature check selects the signing secret from an attacker-controlled field of the *same unverified payload*, any tenant organization configured in Shipit (a supported multi-org deployment, see `secrets_double_github_app.yml`) can forge a signed "success" status for a commit belonging to a completely different organization's stack, triggering an unauthorized continuous deployment.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using a value taken directly from the still-unverified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository','owner','login')` or `params.dig('organization','login')` — both attacker-supplied. This only proves "the sender knows *some* configured organization's webhook secret," not that the secret matches the repository/commit the payload claims to describe.

`StatusHandler#process` then acts on the payload with no such repository binding at all: [3](#0-2) 

Its `params` block does not `require :repository`, and `process` looks up the target purely with `Commit.where(sha: params.sha)` — a global, unscoped query across every stack/repository tracked by the Shipit instance — then calls `commit.create_status_from_github!(params)`.

Compare this with other handlers that correctly scope by repository via the base `Handler#stacks`/`repository_name` helpers: [4](#0-3) 

`StatusHandler` bypasses this pattern entirely.

The forged status is not inert: `Commit#create_status_from_github!` → `add_status` recomputes `status`, and `Commit#schedule_continuous_delivery` uses it directly to gate automatic deployment: [5](#0-4) [6](#0-5) 

**Binding broken:** *the organization whose webhook secret authenticated the request* ≠ *the repository/commit whose CI status and deploy-gating state is written*. The payload field carrying the routing/authorization decision (`repository.owner.login` used to pick a webhook secret) is never actually bound to the field the handler executes on (`sha`, globally resolved).

### Impact Explanation
An attacker who legitimately administers Organization B's own GitHub App/webhook integration in a multi-tenant Shipit instance (as explicitly supported by `config/secrets*.yml`/`secrets_double_github_app.yml`) knows Organization B's `webhook_secret`. Using it, they can sign an arbitrary JSON body containing `organization.login: "OrgB"` (or `repository.owner.login: "OrgB"`) to pass `verify_webhook_signature`, while setting `sha` to a known commit SHA belonging to a stack owned by an unrelated Organization A that they have no GitHub access to. This forges a `success` (or any) CI status for that foreign commit. If the targeted stack has `continuous_deployment` enabled and no other CI gating catches the discrepancy, `schedule_continuous_delivery` will enqueue `ContinuousDeliveryJob`, producing an **unauthorized deploy** of Organization A's stack — meeting the Critical bar ("unauthorized deploy, rollback, merge").

### Likelihood Explanation
Requires only knowledge of the webhook secret for *any one* organization configured in the Shipit instance (attainable by any legitimate but unprivileged tenant admin in a shared/multi-org deployment) and knowledge of a target commit SHA in another tracked repository (commonly public on GitHub). No access to the victim repository, no `ApiClient` token, and no Shipit session are required — only an HTTP POST to `/webhooks` with a computed HMAC.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already use `Handler#stacks`) to the repository declared in the payload, and cross-check that the organization used to select/verify the webhook signature matches the owner of that repository before processing. Require and validate a `repository` field in `StatusHandler`'s parameter definition, and restrict the `Commit` lookup to commits belonging to stacks under the verified organization/repository, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` instead of the unscoped `Commit.where(sha:)`.

### Proof of Concept
1. Attacker legitimately controls Organization B's Shipit GitHub App and therefore knows `webhook_secret_B` (configured per `secrets_double_github_app.yml`-style multi-org setup).
2. Attacker identifies a public commit SHA `deadbeef...` belonging to a stack of unrelated Organization A tracked by the same Shipit instance, with `continuous_deployment: true`.
3. Attacker builds the JSON body:
```json
{
  "organization": { "login": "OrgB" },
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `sha1=HMAC-SHA1(webhook_secret_B, body)` and POSTs to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgB")` and successfully verifies the signature using `webhook_secret_B`.
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — finding the Organization A commit — and records a forged `success` status via `create_status_from_github!`.
7. If this flips `deployable?` to true, `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, deploying Organization A's stack without any legitimate CI success or GitHub authorization for that organization.
