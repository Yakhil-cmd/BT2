### Title
Medium: Accrual caps the index instead of the resulting market value, permanently freezing saturated markets - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` computes total debt and total supply by multiplying stored scaled shares by their indexes before applying the index ceiling, so `borrowed * borrow_index` or `supplied * supply_index` can overflow `i128` while both indexes remain below `MAX_*_INDEX_RAY`. [1](#0-0) [2](#0-1) 

### Finding Description
`scaled_to_original` is a checked fixed-point multiplication and returns `MathOverflow` when the resulting RAY value does not fit `i128`. [3](#0-2) [4](#0-3)  `update_borrow_index` multiplies the old index by the growth factor and only then compares the index—not the resulting debt value—to `MAX_BORROW_INDEX_RAY`. [5](#0-4)  `update_supply_index` likewise multiplies `supplied` by `old_index` and adds rewards before clamping only the resulting supply index. [6](#0-5)  Consequently, a sufficiently large admitted market can cross the `i128` market-value boundary before the `10^36` index ceiling is reached. [7](#0-6) 

Every pool leg loads the market through `synced_market`, which runs `global_sync` before the requested operation. [8](#0-7)  Public controller operations including `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `update_indexes` therefore all enter the overflowing accrual path for the affected market. [9](#0-8) [10](#0-9) 

### Impact Explanation
Once either market total crosses the representable RAY-value boundary, `update_indexes`, repayment, withdrawal, liquidation, bad-debt cleanup, and further market operations revert during the mandatory accrual step. [8](#0-7) [11](#0-10)  Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot rescue or close positions, permanently freezing funds in that market unless an administrative upgrade changes the arithmetic. [11](#0-10) 

### Likelihood Explanation
An unprivileged user can reach the condition on any market whose valid configured caps and interest-rate model admit enough shares and growth; the protocol admits caps up to `max_cap_for_decimals`, approximately 170 billion whole units for an 18-decimal asset. [12](#0-11) [13](#0-12)  The same address can create one account to supply the debt asset and another account to supply collateral and borrow it, after which any address can trigger the freeze by calling `update_indexes` once ledger time advances. [14](#0-13) [15](#0-14)  The requirement for very large balances and sustained high utilization reduces likelihood, so this is Medium rather than High.

### Recommendation
Bound accrual by the current scaled-share headroom, not only by `MAX_*_INDEX_RAY`; for example, cap `borrow_index` at `min(MAX_BORROW_INDEX_RAY, floor(i128::MAX / borrowed))` and cap `supply_index` at `min(MAX_SUPPLY_INDEX_RAY, floor(i128::MAX / supplied))`, accounting for revenue shares before each subsequent chunk. [16](#0-15) [17](#0-16)  Alternatively, make market-total valuation saturating for utilization while preventing index or share updates that would make debt, supply, or position values unrepresentable. [18](#0-17)  Add a regression test that repeatedly calls `update_indexes` past the market-value boundary and then proves `repay`, `withdraw`, and `liquidate` still execute. [19](#0-18) 

### Proof of Concept
The existing test demonstrates the condition with a valid 18-decimal debt market, a collateral market, approximately `1e9` whole debt tokens supplied, and a 98% draw. [20](#0-19)  Its helper raises fixture caps to the protocol's valid maximum; the equivalent production precondition is simply a market configured with caps sufficient for the position. [21](#0-20) [22](#0-21)

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
