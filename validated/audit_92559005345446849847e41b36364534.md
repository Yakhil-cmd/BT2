### Title
Unvalidated `P2PStakingInfo.BlockNum` in fast-sync allows a malicious peer to corrupt the staking info DB — (`datasync/downloader/queue.go`)

### Summary

During fast-sync, a malicious P2P peer can respond to a staking info request for block N with a `P2PStakingInfo` whose `BlockNum` field is set to an arbitrary value M. Because the `validate` callback in `queue.DeliverStakingInfos` is an explicit stub that always returns `nil`, and because `commitFastSyncData` uses `result.StakingInfo.BlockNum` (the attacker-controlled field) as the DB key for `PutStakingInfoToDB`, the staking info is permanently written at the wrong block number. Block N's entry is never written; block M gets a spurious entry. This persistently corrupts reward distribution for all blocks whose staking source is N or M.

### Finding Description

**Entry point:** Any P2P peer connected to a fast-syncing node can send a `StakingInfoMsg`.

**Step 1 — `handleStakingInfoMsg`** decodes the message and forwards it with no field-level checks: [1](#0-0) 

**Step 2 — `Downloader.DeliverStakingInfos`** delivers to the queue channel: [2](#0-1) 

**Step 3 — `queue.DeliverStakingInfos`** — the `validate` callback is a TODO stub that unconditionally returns `nil`, performing zero cross-checking between the received `P2PStakingInfo.BlockNum` and the `header.Number` of the block that was actually requested: [3](#0-2) 

Compare this to `DeliverReceipts`, which validates the receipt root against the header, and `DeliverBodies`, which validates the tx root — both use the header as a cryptographic anchor. Staking infos have no such anchor.

**Step 4 — `queue.deliver`** iterates over `request.Headers` (the legitimately requested headers) and calls `reconstruct(accepted, res)`, which blindly assigns `stakingInfoList[index]` (the attacker-supplied object) into `result.StakingInfo`: [4](#0-3) 

**Step 5 — `commitFastSyncData`** uses `result.StakingInfo.BlockNum` — the attacker-controlled field — as the key passed to `PutStakingInfoToDB`: [5](#0-4) 

**Step 6 — `PutStakingInfoToDB`** writes to the misc DB keyed by the attacker-supplied number: [6](#0-5) 

The `SyncStakingInfo` recovery path does check `BlockNum` against the expected list (line 673), but that guard is only active when `d.isStakingInfoRecovery == true`. The fast-sync path through `queue.DeliverStakingInfos` has no equivalent guard. [7](#0-6) 

### Impact Explanation

The staking info DB is the authoritative source for validator reward distribution before the Kaia hardfork. `GetStakingInfo` reads from this DB for pre-Kaia blocks: [8](#0-7) 

A corrupted entry means:
- Block N's staking info is **never written** → all blocks whose `SourceNum` resolves to N use an empty/missing staking info → reward distribution for those blocks is broken (wrong validators rewarded or no reward distributed).
- Block M gets a **spurious entry** with wrong staking data → reward distribution for blocks whose `SourceNum` resolves to M is also wrong.

This is a persistent, durable DB corruption affecting KAIA reward distribution, squarely within the allowed impact gate.

### Likelihood Explanation

- Any peer on the public P2P network can connect to a fast-syncing node.
- Fast-sync is the default mode for new nodes joining the network.
- The attacker only needs to be the peer that wins the staking info fetch race for a given block.
- No cryptographic break, no privileged key, no validator collusion required.
- The `// TODO-Kaia-Snapsync update validation logic` comment confirms the missing guard is a known gap, not an intentional design choice.

### Recommendation

In `queue.DeliverStakingInfos`, replace the stub `validate` callback with a check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`:

```go
validate := func(index int, header *types.Header) error {
    if stakingInfoList[index].BlockNum != header.Number.Uint64() {
        return errInvalidStakingInfo
    }
    return nil
}
```

Additionally, in `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` as the DB key rather than `result.StakingInfo.BlockNum`, so the key is always derived from the locally-verified header chain, not from peer-supplied data.

### Proof of Concept

1. Node A starts fast-sync from a malicious peer B.
2. Node A requests staking info for block 100 (by hash).
3. Peer B responds with `P2PStakingInfo{BlockNum: 200, CouncilNodeAddrs: [...attacker addrs...]}`.
4. `queue.DeliverStakingInfos` accepts it (validate returns nil).
5. `commitFastSyncData` calls `PutStakingInfoToDB(200, ...)`.
6. Assert: `ReadStakingInfo(db, 100)` returns `nil`; `ReadStakingInfo(db, 200)` returns the attacker-supplied data.
7. All blocks whose `SourceNum` is 100 now use empty staking info; blocks whose `SourceNum` is 200 use the attacker's staking data → reward distribution is broken for both ranges.
