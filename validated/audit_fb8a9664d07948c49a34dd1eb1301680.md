## Title
Excessive synchronous logging via `augmentMessages()` payment-input filter evaluation in address definitions - (File: definition.js)

### Summary
`definition.js`'s `augmentMessages()` function, invoked whenever an oscript address definition uses an `input`-related filter (`has`/`has one` with `what: "input"`), synchronously calls `console.log` for *every single payment input* in *every* payment message of the unit being validated, in addition to unconditional per-call banner logs. Since this code runs during normal, unprivileged unit validation, an attacker who controls (or pays with) an address whose definition contains such an `input` filter can post units with many payment inputs to force large volumes of synchronous console output on every validating node — the same bug class as CVE-2025-47287 (log flood from attacker-controlled, per-item logging that isn't gated or rate-limited).

### Finding Description
`augmentMessages()` is reached from `evaluateFilter`/`augmentMessagesAndEvaluateFilter`/`augmentMessagesOrIgnore` inside `validateAuthentifiers()`'s `evaluate()` in `definition.js`, which is the core routine that evaluates address definitions (`sig`, `hash`, `has`, `has one`, `formula`, etc.) for every author of every posted unit (`validation.js` `validateAuthor` → `Definition.validateAuthentifiers`) — this is completely attacker-reachable via a normally-formed unit or AA trigger: [1](#0-0) 

Specifically:
- `console.log("augmenting")` fires once per invocation.
- `console.log("augmenting inputs")` fires per payment message with an `inputs` array.
- `console.log("input", input)` fires **once per input** in that message — unconditionally, regardless of whether the input is valid.
- For "transfer" type inputs, it further does a DB query and logs `console.log("src", rows[0])` or `console.log(rows.length+" src outputs found")` per input.

None of this loop aborts early on encountering "bad" data — like Tornado's multipart parser, it keeps iterating over the whole attacker-supplied `payload.inputs` array and logging for each entry, even for entries that are ultimately going to fail validation (`bHasInvalidInput`).

This routine is triggered by `augmentMessagesAndEvaluateFilter` (called from the `has`/`has one` oscript ops) whenever the filter references `input.address`, `amount`, `amount_at_least`, `amount_at_most`, etc: [2](#0-1) 

and by `augmentMessagesOrIgnore` for `formula` conditions that reference `input`: [3](#0-2) 

`validateAuthentifiers` itself is called for **every unit** and its address definition is **re-evaluated on every validation pass**, per the code's own comment: "we need to re-validate the definition every time, not just the first time we see it": [4](#0-3) 

### Impact Explanation
An address owner can register/use a definition such as `["has", {"what":"input","type":"transfer","address":"..."}]` and then post a unit signed by that address containing a `payment` message with a large number of inputs (bounded only by unit-size/complexity limits, not specifically capped for this purpose). Every node that validates that unit — during initial acceptance, during re-validation triggered by witness list/definition changes, and (per the comment above) on repeated re-evaluations — will synchronously emit one `console.log` call per input (plus a DB round-trip per input for "transfer" inputs). Because Node.js's `console.log`/stdout writes are synchronous when stdout is not a TTY (e.g., redirected to a file, as is typical for a running daemon), this blocks the event loop for the duration of the writes, matching the CWE-770/DoS pattern of the advisory: unauthenticated/low-privilege attacker input drives an uncontrolled volume of synchronous logging. Repeated posting of such units (or having many peers relay/re-validate the same unit) can degrade or stall the node's unit-processing throughput, hindering confirmation of new units — the network-availability impact class explicitly listed as acceptable proof for this scan.

### Likelihood Explanation
High. The oscript `has`/`has one input` construct is a standard, publicly documented feature for address definitions and AA definitions (used for conditional payments), so any user can define such an address without needing special privilege, and any of their outgoing units (or units sent to an AA/asset that uses this pattern in its definition, since asset-transfer and AA conditions share the same `validateAuthentifiers`/`evaluateFilter` code path) will invoke the vulnerable loop. No malicious peer/node cooperation is required — a single self-authored unit exercises the code path on every node that validates it.

### Recommendation
Remove or gate the debug `console.log` statements inside `augmentMessages()` (and its per-input/per-src-output logging) behind an explicit, disabled-by-default debug flag, and ensure any remaining diagnostic logging is emitted at most once per validation call rather than once per input/message. Additionally, consider bounding the number of qualifying inputs processed by input-filter evaluation, and use asynchronous/batched logging (or `util.debuglog`) instead of unconditional `console.log` in code paths reachable from untrusted unit content.

### Proof of Concept
1. Create an address whose definition is `["has", {"what": "input", "type": "transfer", "address": "SOME_ADDRESS"}]` (or an AA/asset definition using the same construct) — a normal, documented oscript pattern.
2. Compose and broadcast a payment unit signed by that address whose `payment` message contains as many `transfer` inputs as the network's per-message/complexity limits allow.
3. Observe that on any node validating this unit, `definition.js`'s `augmentMessages()` executes `console.log("input", input)` (and DB-driven `console.log("src", ...)`/`console.log(... + " src outputs found")`) once per input synchronously, and that this re-runs on every re-validation of the unit (per the "re-validate the definition every time" logic), producing repeated bursts of synchronous log output proportional to attacker-chosen input count.

				if (!Array.isArray(payload.inputs)) // skip now, will choke when checking the message
