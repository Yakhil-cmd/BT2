### Title
AA-based merkle-drop distributor loses claimability of unclaimed funds when the stored root state variable is overwritten - ([File: aa_composer.js], [File: formula/evaluation.js], [File: merkle.js])

### Summary
ocore's Autonomous Agent (AA) formula language exposes `is_valid_merkle_proof(element, proof)` [1](#0-0)  together with mutable, AA-owned state variables (`var[...]`) that are persisted via `saveStateVars()` after each trigger [2](#0-1) . This combination lets an AA author implement a classic "merkle-drop" prize/airdrop pattern: store a `merkle_root` state variable, and on each trigger check `is_valid_merkle_proof(leaf, proof) AND proof.root == var['merkle_root']` before paying out to the claimer. Because the root is a plain, overwritable state variable (unlike ocore's own `in merkle` address-definition authentifier, which checks the root against append-only, historical `data_feed` records via `dataFeedExists()` and therefore never "forgets" an old valid root [3](#0-2) ), any state-update formula that reassigns `var['merkle_root']` to a new value permanently invalidates every previously-issued, still-unclaimed proof for the old root — exactly the same root-cause pattern as the reported Solidity issue.

### Finding Description
`merkle.js` implements a standard binary merkle tree: `getMerkleRoot`, `getMerkleProof`, `verifyMerkleProof` [4](#0-3) [5](#0-4) . The oscript formula function `is_valid_merkle_proof` calls `merkle.verifyMerkleProof(element, objProof)` where `objProof` is decoded from trigger data or from a state var supplied by the caller [6](#0-5) . It returns only a boolean; whether the derived `proof.root` matches an authorized value is entirely up to the AA author's own oscript logic (typically comparing it against a persisted `var['merkle_root']`).

AA state variables are ordinary key/value entries in the AA's own storage (`kvstore`), fixed and overwritten by whatever the AA's `state` formula assigns via `bStateVarAssignmentAllowed` execution [7](#0-6) , and persisted unconditionally to the batch on every trigger that updates them [2](#0-1) . There is no framework-level protection preventing an AA (whether by its owner posting a "reset/rotate root" trigger, or by any address permitted to update `var['merkle_root']` per the AA's own definition) from overwriting the root before all originally-airdropped leaves have claimed their share. Any unclaimed leaf's `element`/`proof` pair, generated against the old root, will fail `proof.root == var['merkle_root']` forever after the update, because `verifyMerkleProof` recomputes the root purely from the supplied proof and compares it to whatever value is currently stored — there is no fallback to "any historical root" the way ocore's own `dataFeeds.dataFeedExists()` provides for the built-in `in merkle` authentifier [3](#0-2) .

This mirrors the reported FootiumPrizeDistributor bug: a privileged party changes the single "current root" state, and every proof computed against the prior root becomes permanently `false`, while the bytes/assets earmarked for those unclaimed leaves remain locked inside the AA's balance with no path to recovery (the AA logic would need to explicitly special-case "old root" claims, which most simple airdrop AAs do not).

### Impact Explanation
Funds sent to the AA to fund the airdrop/prize pool become permanently unclaimable by legitimate, un-claimed leaf holders once the root is rotated, since the on-chain, immutable proof they hold can never satisfy the new `var['merkle_root']`. This is a direct AA fund freeze/loss for the intended recipients, matching the "High" severity class of the original report (loss of funds locked under a merkle-root scheme).

### Likelihood Explanation
This requires the AA to be designed with a single, overwritable root variable and a mechanism (owner-only trigger, timelock, or periodic rotation for new campaigns) to update it — a very common airdrop/prize-distribution pattern that developers are highly likely to build using `is_valid_merkle_proof` given it's a first-class oscript primitive intended exactly for this purpose. No consensus-level flaw in ocore itself is required beyond the fact that the primitive offers no built-in historical-root fallback (unlike the native `in merkle` definition operator), so any AA author replicating a naive "current root only" design inherits the vulnerability.

### Recommendation
- When designing AA-based merkle distributors, do not overwrite the root outright; instead, add new roots to a list/mapping of currently-valid roots (`var['root_' + hash]`) and check membership in that entire mapping rather than equality with one variable, or provide a claim-then-migrate function that lets committee move outstanding unclaimed allocations to the new root before invalidating the old one.
- Alternatively, favor ocore's built-in `in merkle` / `data_feed` based root storage at the address-definition level for this exact use case, since it inherently supports validating a proof against any historically-published root value within an mci window, rather than a single mutable value [3](#0-2) .

### Proof of Concept
Example AA sketch that reproduces the pattern (illustrative oscript, not present verbatim in the repo but constructible using primitives shown above):
```
{
  messages: {
    cases: [
      { // owner sets/rotates root
        if: `{trigger.address == 'OWNER_ADDR' AND trigger.data.new_root}`,
        messages: [{ app: 'state', state: `{ var['merkle_root'] = trigger.data.new_root; }` }]
      },
      { // claim
        if: `{is_valid_merkle_proof(trigger.address || ":" || trigger.data.amount, trigger.data.proof) AND trigger.data.proof.root == var['merkle_root'] AND !var['claimed_' || trigger.address]}`,
        messages: [
          { app: 'payment', payload: { asset: 'base', outputs: [{ address: "{trigger.address}", amount: "{trigger.data.amount}" }] } },
          { app: 'state', state: `{ var['claimed_' || trigger.address] = 1; }` }
        ]
      }
    ]
  }
}
```
1. Owner funds the AA and sets `merkle_root = ROOT_A` covering leaves L1..L100.
2. Only L1..L50 claim before the owner posts a trigger with `new_root = ROOT_B` for a new campaign.
3. L51..L100 can never claim again: their `trigger.data.proof.root` (computed from `ROOT_A`-tree data) will never equal `var['merkle_root']` (now `ROOT_B`), even though the AA still holds bytes/assets reserved for them — verified via `merkle.verifyMerkleProof` [5](#0-4)  and the state-var overwrite semantics in `aa_composer.js` [2](#0-1) .

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
