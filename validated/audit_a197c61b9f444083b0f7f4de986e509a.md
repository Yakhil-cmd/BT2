Found it. `checkUpstreamProvenance` in `pkg/cmd/skills/install/install.go` derives trust/origin attribution purely from attacker-controlled repository content and uses it to auto-redirect a `gh skill install` to a different repository — an analog of the ZetaChain bug's core flaw (a security-relevant identity/origin decision is derived from data an attacker fully controls, rather than a source that can't be spoofed by that attacker).

### Title
Skill install "upstream provenance" redirect trusts attacker-controlled `github-repo` frontmatter to silently install from a different repository - (File: `pkg/cmd/skills/install/install.go`)

### Summary
`gh skill install` resolves a skill from a user-specified repository, but before installing, it fetches the target `SKILL.md`'s YAML frontmatter and checks for a `metadata.github-repo` key. If present and different from the repo the user asked to install from, the CLI treats this as proof that the skill was "re-published" and offers (or, with `--upstream`/non-interactive nuance, can even redirect) to install from that different, attacker-named repository instead [1](#0-0) .

### Finding Description
`checkUpstreamProvenance` fetches the raw `SKILL.md` content via the GitHub Contents API for the exact repo/ref the user specified, parses its frontmatter, and reads `metadata.github-repo` directly out of attacker-supplied file content: [2](#0-1) 

There is no verification that this `github-repo` value corresponds to any real relationship between the two repositories — it is a bare string taken from a file the target repo's owner fully controls. This is functionally the same class of bug as the ZetaChain issue: a critical decision (here, "which repository should I actually trust/install from") is derived from an untrusted, attacker-supplied field (the `Sender`/EOA in ZetaChain; the `github-repo` frontmatter key here) instead of a cryptographically- or protocol-verified origin.

The consequence is realized in `installRun`, where a match causes the tool to literally swap `opts.repo` to the attacker-named "upstream" and re-run installation against it: [3](#0-2) 

Concretely, an attacker who controls `attacker/evil-skills` can publish a skill whose `SKILL.md` frontmatter contains `metadata.github-repo: https://github.com/legit-org/legit-skills`. When a victim runs `gh skill install attacker/evil-skills some-skill`, the CLI will report "This skill was originally published in legit-org/legit-skills" and, in a TTY, present "upstream" as a selectable, seemingly more-trustworthy option; in non-interactive mode with `--upstream` set (a documented, reasonable-sounding flag for automation/agents), the CLI redirects automatically without further confirmation, installing from `legit-org/legit-skills` version resolution logic that is itself driven by data supplied through the initial attacker-controlled request. More importantly, the reverse and more damaging direction is that this same unauthenticated claim mechanism lets any repository "vouch" that arbitrary content is a re-publish of a trusted org, manipulating the human-readable trust signal ("This skill was originally published in ...") shown to the user/agent, and steering automated agent workflows (this is explicitly designed to be consumed by "self-managing" agents per `skills/gh-skill/SKILL.md`) toward installing from a namespace the attacker chose, with no cryptographic binding between the claim and the claimed upstream repository [4](#0-3) .

### Impact Explanation
An attacker-controlled repository can inject an arbitrary, unverified `github-repo` claim that: (1) is displayed to the user as an authoritative provenance statement ("This skill was originally published in ..."), influencing install decisions made by humans or autonomous coding agents; and (2) can trigger an automatic repository redirect for the install target in non-TTY/`--upstream` automation flows, which is the exact kind of "trusted intermediary" flow (agents self-managing skills, as documented) that the attacker can hijack. While the direct code fetched/executed after the redirect still originates from wherever the "upstream" repo resolves to (so this isn't full remote code execution by itself unless combined with typosquatting/repo takeover of the claimed upstream name), it is a verification/trust bypass: the CLI's own UI text and control flow can be manipulated by fully attacker-controlled data to assert a false provenance relationship, which is the described bug class (identity/origin attribution derived from the wrong, attacker-influenced source).

### Likelihood Explanation
This is reachable by any unprivileged remote attacker who can publish a public GitHub repository with a skill — no privileges on the victim's system or the claimed upstream repo are required. The victim only needs to run `gh skill install <attacker>/<repo> <skill>`, which is the primary documented flow for this feature. The `--upstream` non-interactive path further increases likelihood in CI/agent automation contexts where a human is not present to notice the misleading provenance claim.

### Recommendation
Do not trust the `metadata.github-repo` (or any other frontmatter-supplied) value as a provenance/trust signal on its own. If "re-publish detection" is a desired feature, it should be based on verifiable evidence (e.g., comparing actual file content/hash against the claimed upstream's tree at a resolved ref, and only displaying the claim after confirming the claimed upstream repository actually contains matching content), or clearly and unambiguously label the message as an unverified, repository-author-supplied claim, with no automatic redirect behavior (even under `--upstream`) unless independently corroborated.

### Proof of Concept
1. Attacker publishes `attacker/evil-skills` with `skills/some-skill/SKILL.md` containing:
```yaml
---
name: some-skill
description: ...
metadata:
  github-repo: https://github.com/legit-org/legit-skills
---
```
2. Victim (or an automated agent per the documented self-management loop) runs:
```
gh skill install attacker/evil-skills some-skill --upstream
```
3. `checkUpstreamProvenance` reads the attacker-controlled `github-repo` value, parses it as `legit-org/legit-skills` via `source.ParseRepoURL`, and because `--upstream` is set, the code path immediately redirects: `opts.repo = upstreamRepo; ... return installRun(opts)` — reflected in the test `TestInstallRun_UpstreamDetection / "non-interactive with --upstream redirects to upstream"` [5](#0-4) , confirming the redirect is driven purely by the attacker-supplied frontmatter with no cross-verification.

// checkUpstreamProvenance fetches the skill's SKILL.md via the contents API
// to check if it contains github-repo metadata pointing to a different
// repository, indicating the skill was re-published from an upstream source.
// In interactive mode, the user is asked whether to install from the
// re-publisher or redirect to the upstream. Non-interactive mode always
// installs from the re-publisher.
// Returns (repo to redirect to, whether upstream was detected, error).
func checkUpstreamProvenance(opts *InstallOptions, client *api.Client, hostname string, skill discovery.Skill, commitSHA string) (ghrepo.Interface, bool, error) {
	u, err := safeurl.JoinPath("repos", opts.repo.RepoOwner(), opts.repo.RepoName(), "contents", skill.Path+"/SKILL.md")
	if err != nil {
		return nil, false, err
	}
	u.SetQuery("ref", commitSHA)
	var fileResp struct {
		Content  string `json:"content"`
		Encoding string `json:"encoding"`
	}
	if err := client.REST(hostname, "GET", u.String(), nil, &fileResp); err != nil {
		return nil, false, nil //nolint:nilerr // best-effort check; failing to fetch is not fatal
	}
	if fileResp.Encoding != "base64" {
		return nil, false, nil
	}
	decoded, decodeErr := io.ReadAll(base64.NewDecoder(base64.StdEncoding, strings.NewReader(fileResp.Content)))
	if decodeErr != nil {
		return nil, false, nil //nolint:nilerr // best-effort; decode failure is not fatal
	}
	content := string(decoded)

	result, parseErr := frontmatter.Parse(content)
	if parseErr != nil || result.Metadata.Meta == nil {
		//nolint:nilerr // unparsable frontmatter means no upstream to detect
		return nil, false, nil
	}

	existingRepo, _ := result.Metadata.Meta["github-repo"].(string)
	if existingRepo == "" {
		return nil, false, nil
	}

	currentRepoURL := source.BuildRepoURL(hostname, opts.repo.RepoOwner(), opts.repo.RepoName())
	if existingRepo == currentRepoURL {
		return nil, false, nil
	}

	upstreamRepo, parseErr := source.ParseRepoURL(existingRepo)
	if parseErr != nil {
		//nolint:nilerr // invalid repo URL means we can't redirect; install normally
		return nil, false, nil
	}
