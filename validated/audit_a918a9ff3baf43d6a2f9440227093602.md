### Title
Emergency `op_list` governance override lacks meaningful safeguards, enabling unilateral consensus/witness-list takeover - (File: `main_chain.js`)

### Summary
The C4 report flags `GovDev.updateSolution` in Sherlock: an owner-gated function that can instantly rewrite core contract logic and reach all funds, with no timelock, creating rug/consensus risk. `ocore` has an analogous "instant, low-friction override of core governance" path: the *emergency* `op_list` (witness/Order-Provider list) replacement mechanism, triggered by an ordinary `system_vote_count` message from any unprivileged unit author, which forcibly recomputes and REPLACEs the witness list used to determine DAG stability, bypassing the normal vote-counting-at-stabilization flow.

### Finding Description
Any unit author may post a `system_vote` message with `subject: 'op_list'` [1](#0-0)  and a `system_vote_count` message for the same subject [2](#0-1) . The only checks performed are that the sender is not an AA, that the vote is well-formed, that the proposed OPs are valid, non-AA, "known and good" witnesses, and that only one such message exists per unit — there is no check on the caller's identity, role, or any waiting period tied to the sender.

When a unit carrying a `system_vote_count` for `op_list` is written with `sequence==='good'`, the writer immediately (at write time, not at stabilization) invokes the emergency path: [3](#0-2) 

`applyEmergencyOpListChange` only checks that the main chain has been stalled (no new stable unit) for longer than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT`: [4](#0-3) 

`countVotes` is then invoked with `is_emergency=1`, which pulls in **unstable** (not-yet-confirmed) votes collected from in-memory unstable messages, requiring only that each vote is older than `EMERGENCY_COUNT_MIN_VOTE_AGE` (1 hour): [5](#0-4) 

These unstable, balance-weighted votes are merged with previously stable votes and used to immediately overwrite the live in-memory `op_list` and the `system_vars` table used by the whole node/network for main-chain stability determination: [6](#0-5) [7](#0-6) 

The relevant constants show the only safeguard is a fixed timeout, not a per-actor cooldown, multi-party review, or extended "funds can exit" window analogous to what Sherlock/Evert0x proposed: [8](#0-7) 

Once `op_list` is replaced, every node applies the new witness set and re-derives DAG stability/order accordingly, and light clients are pushed the new list live: [9](#0-8) 

### Impact Explanation
The witness/`op_list` is the trust anchor for main-chain stability determination — analogous in criticality to `LibDiamond.diamondCut` controlling all contract logic and funds in the Sherlock report. Unlike a Diamond upgrade (owner-gated), this override is reachable by *any* unprivileged unit poster who can accumulate/persuade enough stake-weighted votes and simply wait for (or, if colluding with a large stake, help cause) a main-chain stall. Because the override consumes still-*unstable* votes (not yet finalized/immutable) and is applied without any additional delay or independent confirmation beyond the fixed timeout, an attacker or a small coalition of high-balance addresses could force in a captured/malicious `op_list`. A captured witness set can subsequently: cause different nodes to disagree about unit validity/stability (network split), stall confirmation of new units, or set the stage for double-spend/finality attacks — all impacts explicitly in scope (node disagreement on validity/stability, network unable to confirm new units).

### Likelihood Explanation
Likelihood is bounded by the requirement that the main chain must actually be stalled for `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) and that votes must be balance-weighted and at least 1 hour old, so this is not trivially triggerable in a healthy network. However, unlike the Sherlock case (owner-only), there is no privileged-role gate at all here — the entire safeguard rests on a single fixed timer, with no cooling-off period post-change, no requirement for the new OPs to be independently vetted beyond automated checks, and no mechanism giving users time to react/exit before the new list takes effect network-wide. This mirrors exactly the risk profile Sherlock's own team acknowledged and proposed mitigating with a 14-day wait window — a mitigation absent here for the emergency path.

### Recommendation
Add a stability-preserving delay before an emergency `op_list` change takes full network effect (e.g., broadcast the pending emergency result and require it to itself become "stable" over some minimum number of MCIs/time before being applied to `system_vars`/witness selection), and/or require the emergency-vote balances to be locked/proven for a minimum age, and add rate-limiting/cooldown so a single stall event cannot be exploited repeatedly. At minimum, publish emergency `op_list` changes to all watchers with a defined grace period, mirroring the spirit of the "push, wait, then execute" mitigation Sherlock adopted for `GovDev.updateSolution`.

### Proof of Concept
1. Attacker (or colluding stakeholders) accumulate large `base` balances and post `system_vote` units for `op_list` pointing to attacker-controlled addresses (validation only checks the addresses are valid, non-AA, known witnesses — `validation.js:1860-1883`).
2. Attacker waits for/engineers a genuine main-chain stall (no unit becomes stable) exceeding `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) — `constants.js:18`.
3. Attacker posts a unit with `system_vote_count` for `op_list`; `validation.js:1913-1923` accepts it with no author-privilege checks.
4. On write, `writer.js:639-645` calls `main_chain.applyEmergencyOpListChange`, which passes the stall-timeout check (`main_chain.js:1936-1946`) and calls `countVotes` with `is_emergency=1`.
5. `countVotes` (`main_chain.js:1824-1876`) tallies unstable, balance-weighted votes (only ≥1 hour old, per `getUnstableVotes`, `main_chain.js:1915-1933`) and immediately overwrites `storage.systemVars.op_list` and the `system_vars` table (`main_chain.js:1908-1912`), which propagates to all connected light clients via `onSystemVarUpdated` (`network.js:2157-2182`).
6. The network now operates under an attacker-influenced witness list with no further review period, enabling downstream stability/consensus manipulation.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
