### Title
Path traversal in `inherit_from` allows arbitrary host file read outside the checkout - (File: app/models/shipit/deploy_spec/file_system.rb)

### Summary
`DeploySpec::FileSystem#build_config` resolves the attacker-controlled `inherit_from` key with `path.dirname.join(...)` and then calls `.exist?`/`.read` on the result with no confinement check against `@app_dir`. Because `Pathname#join` does not sandbox absolute paths or `../` sequences, an attacker who controls their own `shipit.yml` (any repo owner/PR author) can make Shipit read and YAML-parse an arbitrary file on the deploy host filesystem, not just files inside their checkout.

### Finding Description
The claimed binding is: `inherits_from_path == a path confined within @app_dir`. This does not hold. In `app/models/shipit/deploy_spec/file_system.rb`: [1](#0-0) 

`inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))` performs a raw `Pathname#join`. `Pathname#join` has two unsafe behaviors here:
1. If the attacker supplies an absolute path (e.g. `inherit_from: /etc/passwd`), `join` discards the base and returns the absolute path verbatim.
2. If the attacker supplies a relative traversal (e.g. `inherit_from: ../../../../etc/passwd`), the resulting `Pathname` is not normalized, but `.exist?` and `.read` (via `read_config`, `app/models/shipit/deploy_spec/file_system.rb:162-164`) resolve it through the OS, which does follow `..` components and can walk outside `@app_dir`.

There is no `File.expand_path` + prefix check, no `Pathname#realpath` comparison against `@app_dir`, and no rejection of absolute paths anywhere in `build_config`, `read_config`, or `file`. The `file` helper (`app/models/shipit/deploy_spec/file_system.rb:27-33`) is only used for locating the primary `shipit.yml`/`shipit.<env>.yml` candidates, not for the `inherit_from` resolution path, so its containment (weak as it is) does not apply to `inherit_from` at all.

Attack flow: an attacker opens a PR against their own repository (or pushes to their own fork) containing a `shipit.yml` with `inherit_from: ../../../../etc/hostname` (or an absolute path). When Shipit checks out that commit into `@app_dir` and loads the deploy spec (`load_config` → `build_config`), it will read the target file if it exists on the host, parse it as YAML via `SafeYAML.load`, and deep-merge its contents into the stack's effective configuration.

No existing guard stops this: `verify_signature`/webhook checks are irrelevant (this executes during normal config load for a legitimate, signed webhook/PR event on the attacker's own repo); `ExplicitParameters`, `Repository`/`Stack` validators, and `EnvironmentVariables#permit` validate unrelated inputs (repo names, environment strings, env var permit-lists) and never touch `inherit_from` content or path resolution.

### Impact Explanation
The confirmed impact is **arbitrary local file read on the deploy host**, scoped to files readable by the Shipit process user, triggered purely by content the attacker controls in their own repository's `shipit.yml`.       def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))

        end
