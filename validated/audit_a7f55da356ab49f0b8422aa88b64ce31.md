### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while handlers act on the independent `repository.full_name`/`sha` fields — organization-authenticated ≠ repository-written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/HMAC secret to validate a webhook against using a field read out of the **same untrusted JSON body** it is about to verify, while the handlers that actually mutate data (`Stack`, `Commit`, `Status`) key off a **different, independent** field from that same body. Because the engine never checks that the field used to pick the verification secret matches the field used to select the target repository/commit, a payload can be crafted so that it is authenticated as belonging to one GitHub organization while it mutates state belonging to a completely different repository/stack.

### Finding Description
`repository_owner` is computed straight from the unauthenticated JSON body: [1](#0-0) 

This value chooses which `GitHubApp` (and therefore which `webhook_secret`) is used to verify the HMAC signature: [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as "always verified": [3](#0-2) 

Shipit's own documentation and shipped example configs show `webhook_secret` as an optional, per-organization value in multi-app setups (i.e., it is fully supported to have some orgs signed and others not): [4](#0-3) [5](#0-4) 

Once the (potentially unauthenticated) request passes `verify_signature`, the **same raw body** is dispatched to handlers, which pick the target `Stack`/`Commit` using a *different* field of the body — `repository.full_name` — with no cross-check against `repository.owner.login`/`organization.login` used earlier for signature selection: [6](#0-5) 

For the `status` event specifically, the handler doesn't even use `repository` at all — it looks up commits globally by `sha` and blindly creates a status on whichever `Stack`/`Commit` owns that sha: [7](#0-6) 

Creating a `Status` triggers CI-enablement and continuous delivery/merge-queue processing: [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`verified_organization(payload.repository.owner.login) == owner_of(payload.repository.full_name / commit.sha acted upon by handler)`

Before the attacker's request: only genuinely signed payloads for a given org can mutate that org's stacks/commits.
After the attacker's request: a payload can be signed (or unsigned, if that org has no `webhook_secret`) as `OrgWithNoSecret`, yet carry a `sha`/`repository.full_name` belonging to `TargetOrg`'s stack — and the handler happily mutates `TargetOrg`'s data because it never re-checks the owner used for authentication.

### Impact Explanation
This crosses the "cross-repository writes" bar: an attacker who can reach the webhook endpoint (public, unauthenticated by design) can inject a `status` webhook that is nominally authenticated for one (weakly-configured or default) GitHub organization but whose `sha` belongs to a commit in a different stack/repository managed by the same Shipit instance. The forged `success` status enables CI on that commit and feeds `ProcessMergeRequestsJob` / continuous delivery, which can result in an unauthorized deploy or merge for a repository the attacker does not control and for which no valid signature was ever produced.

### Likelihood Explanation
The webhook endpoint is unauthenticated by design (it's meant to be hit by GitHub) and is reachable by any external actor who can guess or discover the Shipit host. Exploitation requires that the Shipit instance be running the documented multi-organization configuration (`config/secrets.yml` keyed by org name) with at least one configured organization lacking a `webhook_secret` — a state the engine's own example configs and docs present as normal/supported, not a misconfiguration outside the engine's control. No GitHub credentials, session, or `ApiClient` token are required.

### Recommendation
- Bind the field used to select the verifying `GitHubApp`/secret to the same field the handlers use to resolve the target repository (`repository.full_name`), and re-validate after verification that the two agree.
- Require a `webhook_secret` to be configured for every org in multi-org mode, or scope handlers to only operate on repositories that belong to the organization whose secret validated the request.
- In `Shipit::Webhooks::Handlers::StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup by the verified organization/repository instead of matching `sha` globally across all stacks.

### Proof of Concept
Preconditions: Shipit configured with multi-org `github:` config where org `UnsignedOrg` has `webhook_secret: nil` (a supported configuration) and org `TargetOrg` hosts the real stack/commit to be attacked.

```
POST /github/webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json
(no valid X-Hub-Signature required, or any bogus value)

{
  "sha": "<sha of a real commit belonging to TargetOrg's stack>",
  "state": "success",
  "context": "ci/whatever-context-the-stack-requires",
  "repository": { "owner": { "login": "UnsignedOrg" } }
}
```

`repository_owner` resolves to `UnsignedOrg`; `GitHubApp#verify_webhook_signature` returns `true` unconditionally because `UnsignedOrg` has no `webhook_secret`. The request passes `verify_signature`, then `Shipit::Webhooks::Handlers::StatusHandler` looks up `Commit.where(sha: ...)` — matching `TargetOrg`'s commit regardless of `repository.owner` — and calls `create_status_from_github!`, marking CI as passing and kicking off continuous delivery/merge processing for `TargetOrg`, despite no valid signature ever having been produced for `TargetOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
