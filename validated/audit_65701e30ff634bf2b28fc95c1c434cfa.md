### Title
Unhandled `throw Error("no latest attestor list")` in `storage.readAsset` crashes node on spender-attested asset with no attestor list - (File: storage.js)

### Summary
`storage.readAsset()`'s helper `addAttestorsIfNecessary()` assumes that once an asset is defined with `spender_attested: true`, a corresponding `asset_attestors` record always exists. If an asset issuer never posts an `asset_attestors` message, any later attempt to validate a payment, an `asset_attestors` update, or any AA logic reading this asset causes an uncaught `throw Error` inside a DB-query callback, which is unreachable by the caller's normal error handling and crashes the node process.

### Finding Description
`validateAssetDefinition()` in `validation.js:2725-2827` only validates the *shape* of `payload.attestors` when `spender_attested` is `true` (`checkAttestorList`, [1](#0-0) ), but never enforces that an `asset_attestors` message accompanies (or immediately follows) the asset definition. Posting the attestor list is handled entirely separately via `case "asset_attestors"` in `validateInlinePayload` ( [2](#0-1) ), which is optional and can be omitted indefinitely by the issuer — an unprivileged asset issuer fully controls this.

Later, whenever any node (including a payment validator or an AA evaluating `asset[...]`/balance formulas) calls `storage.readAsset()` for that asset, `addAttestorsIfNecessary()` is invoked because `objAsset.spender_attested` is true: [3](#0-2) 

It queries for the latest `asset_attestors` unit; if none exists (`latest_rows.length === 0`), it executes `throw Error("no latest attestor list")` directly inside the async DB-query callback (`storage.js:1929`). This throw is not passed through any `handleAsset`/`callback` error channel — it is a raw synchronous throw inside an asynchronous callback, which in Node.js is uncatchable by any surrounding `try/catch` in the call chain (e.g., `validatePayment` in `validation.js:2084`), and will propagate up and crash the process (uncaught exception), unless something else catches at the process level.

This exactly mirrors the analog bug class of the CVE: a lookup performed against attacker-influenced/absent state (`ic_id_table` miss ↔ missing `asset_attestors` record) is dereferenced/used without a graceful-failure path, producing a hard crash instead of a validation error.

### Impact Explanation
Any node (full or light-relevant logic that touches `readAsset`/`loadAssetWithListOfAttestedAuthors`) that attempts to validate a payment of this asset, or evaluates AA formulas referencing `asset[...]` fields or balances for it, hits the same crash. Since asset definition and payment validation are part of ordinary DAG processing for units broadcast by any peer, this can be used to reliably crash any node that processes a unit spending (or an AA that references) the malicious asset — a network-wide denial of service / inability to confirm new units affecting nodes that process the offending asset.

### Likelihood Explanation
Trivially reachable: an unprivileged user posts a normal `asset` definition unit with `spender_attested: true` (and, if using the same-unit attestor-shape check, a non-empty `attestors` array satisfying `checkAttestorList`), and simply never publishes the corresponding `asset_attestors` message referencing that asset. Any subsequent attempt by anyone to pay in this asset, or by an AA to read `asset[...]` properties or issue/spend it, triggers `readAsset` → `addAttestorsIfNecessary` → the uncaught throw. No special privileges, hub cooperation, or malicious peer/node behavior is required — only a single, otherwise well-formed posted unit.

### Recommendation
In `storage.js`'s `addAttestorsIfNecessary()`, replace the `throw Error("no latest attestor list")` (and the sibling `throw Error("no attestors?")`) with a graceful error path through `handleAsset(err)`/`handleAssetInfo(null)`, and have all callers (`validatePayment`, `validateAttestorListUpdate`, AA formula evaluation paths) treat "attestor list not yet posted" as an ordinary validation failure ("asset requires attestors but none published yet") rather than an unrecoverable exception. Additionally, consider requiring `validateAssetDefinition` to enforce that an `asset_attestors` message is present in the same unit (or bundled) whenever `spender_attested` is `true`, closing the window where the asset is spendable-checkable but has no attestor list.

### Proof of Concept
1. Attacker posts a valid `asset` definition unit (message app `asset`) with `spender_attested: true`, `attestors: ["VALID_ADDR1", ...]` in the payload only for shape validation (the shape check in `validateAssetDefinition` passes), but never posts a follow-up `asset_attestors` message that actually stores an `asset_attestors` DB row for this asset unit.
2. Any node/user (or the same attacker) then posts a `payment` message spending or issuing this asset, or an AA formula evaluates `asset[<asset>].definer_address` or a balance/payment involving this asset.
3. `validatePayment` (`validation.js:2084`) calls `storage.loadAssetWithListOfAttestedAuthors` → `readAsset` → `addAttestorsIfNecessary` (`storage.js:1917-1946`).
4. Because no `asset_attestors` row exists for the asset, the query at `storage.js:1923-1929` returns zero rows and executes `throw Error("no latest attestor list")` inside the `conn.query` callback, an uncaught exception that crashes the node process handling that unit. function readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, handleAsset) {
	if (arguments.length === 4) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	if (last_ball_mci === null){
		if (conf.bLight)
			last_ball_mci = MAX_INT32;
		else
			return readLastStableMcIndex(conn, function(last_stable_mci){
				readAsset(conn, asset, last_stable_mci, bAcceptUnconfirmedAA, handleAsset);
			});
	}
	readAssetInfo(conn, asset, function (objAsset) {
		if (!objAsset)
			return handleAsset("asset " + asset + " not found");
		if (objAsset.sequence !== "good")
			return handleAsset("asset definition is not serial");
		
		function addAttestorsIfNecessary(byAA = false){
			if (!objAsset.spender_attested)
				return handleAsset(null, objAsset);

			// find latest list of attestors
			const before_last_ball_cond = byAA ? "" : `AND main_chain_index<=${+last_ball_mci} AND is_stable=1`;
			conn.query(
				"SELECT unit FROM asset_attestors CROSS JOIN units USING(unit) \n\
				WHERE asset=? " + before_last_ball_cond + " AND sequence='good' ORDER BY "+ (conf.bLight ? "units.rowid" : "level") + " DESC LIMIT 1",
				[asset],
				function (latest_rows) {
					if (latest_rows.length === 0)
						throw Error("no latest attestor list");
					var latest_attestor_list_unit = latest_rows[0].unit;

					// read the list
					conn.query(
						"SELECT attestor_address FROM asset_attestors CROSS JOIN units USING(unit) \n\
						WHERE asset=? AND unit=? " + before_last_ball_cond + " AND sequence='good'",
						[asset, latest_attestor_list_unit],
						function (att_rows) {
							if (att_rows.length === 0)
								throw Error("no attestors?");
							objAsset.arrAttestorAddresses = att_rows.map(function (att_row) { return att_row.attestor_address; });
							handleAsset(null, objAsset);
						}
					);
				}
			);
		}

		if (objAsset.main_chain_index !== null && objAsset.main_chain_index <= last_ball_mci)
			return addAttestorsIfNecessary();
		// && objAsset.main_chain_index !== null below is for bug compatibility with the old version
		if (!bAcceptUnconfirmedAA || constants.bTestnet && last_ball_mci < testnetAssetsDefinedByAAsAreVisibleImmediatelyUpgradeMci && objAsset.main_chain_index !== null)
			return handleAsset("asset definition must be before last ball");
		readAADefinition(conn, objAsset.definer_address, last_ball_mci, function (arrDefinition) {
			arrDefinition ? addAttestorsIfNecessary(true) : handleAsset("asset definition must be before last ball (AA)");
		});
	});
}
