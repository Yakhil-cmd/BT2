### Title
Webhook signature is verified against the organization named in an attacker-controlled JSON field, decoupled from the repository the handlers actually write to — cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted request body, before any handler runs. Handlers, however, resolve which `Stack`/`Repository` to mutate using the payload's `repository.full_name` field. Because these are two independent, attacker-controlled fields inside the same forged JSON body, an attacker who legitimately controls a GitHub App installation on their own organization (and therefore knows that organization's `webhook_secret` binding, i.e. can produce a correctly-signed body) can set `repository.owner.login` to their own org (so the signature check passes) while setting `repository.full_name` to any other tracked `owner/repo` to act on a victim stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [1](#0-0) 

and `repository_owner` is derived purely from the request body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This value selects *which* per-organization `webhook_secret` (configured via `Shipit.github(organization:)`, see `lib/shipit/github_app.rb:44-51` where `@webhook_secret = @config[:webhook_secret]`) is used inside `verify_webhook_signature` to HMAC-verify `request.raw_post`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Once the signature passes, `create` dispatches the *entire raw payload* to every registered handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers do not re-derive their target repository from `repository.owner.login` — they use the payload's `repository.full_name` (or nested `pull_request` fields), a value that is never covered by the signature check's organization selection logic. This is visible across every pull-request handler (`closed_handler.rb`, `opened_handler.rb`, `label_capturing_handler.rb`, `labeled_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb` all reference `full_name` to resolve the target repository/stack), and in `CheckSuiteHandler`, which resolves target `stacks` from the same class of payload-supplied identifiers:
```ruby
def process
  stacks.where(branch: params.check_suite.head_branch).each do |stack|
    stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
  end
end
``` [5](#0-4) 

The security-relevant equality the app is *supposed* to maintain is:
`organization whose secret authenticated the request == organization that owns the repository the handler acts on`

But the controller only enforces:
`organization named in payload["repository"]["owner"]["login"] == organization whose configured secret matches the HMAC`

with no cross-check that this is the *same* organization as the one named in `payload["repository"]["full_name"]` (or other repository-identifying fields the handlers actually consume). An attacker who is a legitimate GitHub App/webhook holder for *any* organization tracked by this Shipit instance can therefore forge a signature that is valid for their own org's secret while pointing the rest of the payload at a different, victim-tracked repository.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated" vs. "repository that is written," matching a High-severity primitive from the rules: an attacker who legitimately controls webhook delivery for one tracked organization (e.g., because they administer a small internal repo that Shipit also tracks) can forge `pull_request`, `check_suite`, `status`, `push`, or `membership` events attributed to any *other* tracked organization/repository, since only the signature-selection field is checked, not the field the handlers use to pick the mutated record. Depending on handler this allows unauthorized state changes on victim stacks: forging `pull_request` `closed`/`opened`/`labeled` events to archive/unarchive or auto-provision victim review stacks, forging `check_suite` events to trigger `schedule_refresh_check_runs!` on victim commits, or forging `membership`/`status` events affecting victim team/commit state — all without ever holding a valid secret for the victim organization.

### Likelihood Explanation
Requires the attacker to control (or be granted) a legitimate GitHub App/webhook installation for at least one organization that this Shipit instance also tracks — a realistic, low-privilege scenario for multi-tenant Shipit deployments tracking many orgs/teams, and does not require any Shipit session, API token, or the victim's secret. The forged JSON body is trivial to construct (standard JSON with mismatched `owner.login` vs `full_name`), and no additional guard exists anywhere in `verify_signature` or `create` to reconcile the two.

### Recommendation
After computing `repository_owner` for secret selection, re-validate that every repository-identifying field the dispatched handlers will consume (`repository.full_name`, and any nested `pull_request.base.repo.full_name`, etc.) resolves to the *same* organization used to select the webhook secret; reject (422) on mismatch. Alternately, derive the webhook secret from a value the app itself controls (e.g. the `Repository`/`Stack` looked up by `full_name`) rather than trusting `owner.login` from the unauthenticated body to pick which secret to check against.

### Proof of Concept
1. Attacker administers `attacker-org/some-repo`, which is tracked by this Shipit instance and has its own `webhook_secret` configured for `attacker-org`.
2. Attacker crafts a `pull_request` (or `check_suite`) webhook JSON body where:
   - `repository.owner.login = "attacker-org"` (used only for secret selection in `repository_owner`)
   - `repository.full_name = "victim-org/victim-repo"` (used by the handler to resolve the target `Stack`)
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)` — a signature they can legitimately compute since they know `attacker-org`'s secret.
4. `POST /github/webhooks` with this body/header: `verify_signature` calls `Shipit.github(organization: "attacker-org")` and the HMAC check passes.
5. `create` dispatches the full parsed body to the relevant handler (e.g. `OpenedHandler`), which resolves the target stack via `repository.full_name = "victim-org/victim-repo"`, mutating/creating/archiving a stack that belongs to `victim-org`, an organization the attacker never authenticated for.
