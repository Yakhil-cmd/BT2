### Title
Atomic recursive secondary-trigger chains allow flash-loan-style reserve manipulation of constant-product AMM AAs - ([File: aa_composer.js])

### Summary
Ocore's Autonomous Agent (AA) composer allows a single top-level trigger unit to cascade into an arbitrarily deep, fully atomic chain of secondary AA triggers (bounded only by `MAX_RESPONSES_PER_PRIMARY_TRIGGER`), where any AA in the chain can route funds back into an AA it (or an ancestor) already called. Because the whole chain commits or reverts together, this gives any AMM-style AA on Obyte exactly the "borrow → manipulate price → extract value → auto-unwind-if-it-fails" atomicity primitive that BSC flash-loan attackers (e.g. the JulSwap incident) had to rent liquidity for. An AA that prices trades from its own instantaneous `balance[asset]` (the officially documented `uniswap_like_market_maker.oscript` pattern shipped in this repo's test suite) can be hit with several sequential, self-referential swaps inside one atomic unit, moving its own reserve ratio and reaping the resulting arbitrage/rounding profit, with the entire operation reverting cleanly if the final step fails.

### Finding Description
`getTrigger` aggregates only outputs from the top-level unit's own author to a given address [1](#0-0)  and `validateAATrigger` restricts a *human-authored* unit to at most one primary AA trigger and one output per asset to that AA [2](#0-1) . This looks like it prevents a single unit from invoking the same AA multiple times, but it does not prevent an AA's **own** response unit from re-invoking any AA (including itself, or another pool it previously drained) via `handleSecondaryTriggers`, which recursively calls `handleTrigger` for every AA address that receives outputs from the response unit [3](#0-2) .

Each nested `handleTrigger` invocation reads the *current* balance of the target AA via `updateInitialAABalances`, which queries `aa_balances`/`objValidationState.assocBalances` freshly for every hop [4](#0-3) . Crucially, the whole cascade shares one SQL transaction and one `kvstore` batch, and any bounce anywhere in the chain triggers a full `ROLLBACK TO SAVEPOINT initial_balances` plus `batch.clear()`, undoing every state and balance change made in earlier hops [5](#0-4) . This is precisely the "all-or-nothing, unwind on failure" property that a flash loan supplies on EVM chains — except here it is a first-class feature of the AA engine itself, reachable by any unprivileged unit poster who funds a chain of interacting AAs with a single trigger payment.

The repository's own canonical example AA, `uniswap_like_market_maker.oscript`, prices bytes-for-asset and asset-for-bytes swaps purely from the constant product of its live balances:
```
$p = $asset_balance * $bytes_balance;
$new_asset_balance = round($p / balance[base]);
$amount = $asset_balance - $new_asset_balance;
``` [6](#0-5)  and again for the reverse direction [7](#0-6) . There is no TWAP, no oracle cross-check, and no restriction against being invoked multiple times within one atomic secondary-trigger cascade. An attacker can therefore construct: trigger unit → AA_pool (swap #1, skews ratio) → helper AA (forwards proceeds straight back into AA_pool or into a second correlated pool) → AA_pool again (swap #2 at the now-skewed ratio) → … all inside one atomically-committed/rolled-back chain, exactly mirroring the reserve-manipulation mechanics behind the JulSwap-style flash-loan incident, but without needing to actually borrow anything since the chain's own atomicity plus the depositor's own funds moving through multiple hops is sufficient to swing `$asset_balance`/`$bytes_balance` before the final, profit-taking leg executes.

### Impact Explanation
Any AMM/bonding-curve AA that follows this widely-published design pattern (spot-balance pricing, no reentrancy guard, no per-unit call cap) is exposed to atomic, capital-efficient reserve manipulation, resulting in direct fund loss from the AA's balance to the attacker — a concrete "AA fund loss" outcome. Because the mechanism lives in the core AA composer (`handleSecondaryTriggers`/`handleTrigger`) rather than in any one AA's script, it affects the entire class of liquidity/AMM AAs built on ocore, not a single deployment.

### Likelihood Explanation
No special privileges are required — a normal unit author only needs to deploy (or reuse) a routing/helper AA and send one funded trigger unit; the composer's own recursive secondary-trigger dispatch and atomic rollback semantics do the rest. The attack surface is directly reachable from a single posted unit, matching the "AA trigger sender" actor class explicitly in scope.

### Recommendation
- Add a per-primary-trigger reentrancy guard so the same AA address cannot be invoked more than once (or more than N times) within a single top-level trigger's secondary-trigger cascade, unless explicitly opted into by the AA definition.
- Encourage/require AMM-style AAs to use time-weighted or externally-oracled prices rather than raw spot `balance[...]` ratios, and document the atomic multi-hop composability risk prominently next to the `uniswap_like_market_maker.oscript` example.
- Consider exposing a "call depth" or "distinct-hop" counter to AA scripts (already tracked internally as `arrResponses`/`number_of_responses`) so AA authors can bound and detect suspicious same-block repeated invocation.

### Proof of Concept
1. Deploy `Pool AA` implementing the constant-product formula from `uniswap_like_market_maker.oscript`.
2. Deploy `Router AA` whose only logic is: on receiving asset X from `Pool AA`, immediately forward it back into `Pool AA` (or into a second, correlated `Pool2 AA`).
3. Send one top-level unit with a single output to `Pool AA` sized to trigger a swap.
4. `Pool AA`'s response feeds `Router AA` (secondary trigger); `Router AA`'s response feeds `Pool AA`/`Pool2 AA` again (tertiary trigger) — all inside `handleSecondaryTriggers`'s recursive `async.eachSeries` chain, sharing the same transaction/savepoint [8](#0-7) .
5. Because each hop re-reads the just-updated balance, the second swap executes against the ratio already skewed by the first, letting the attacker extract more value than a single honest swap would allow — and if the final hop bounces, `revert()` unwinds every prior hop atomically [5](#0-4) , so the attacker can safely probe/retry without cost beyond bounce fees.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}

		conn.query("SELECT address, definition, mci, main_chain_index FROM aa_addresses LEFT JOIN units USING(unit) WHERE address IN(?) AND mci<=? ORDER BY address", [arrOutputAddresses, mci], function (rows) {
			if (rows.length > 0 && constants.bTestnet && mci < testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci)
				rows = rows.filter(function (row) {
					if (row.main_chain_index && row.main_chain_index < mci) // previous definition is already stable
						return true;
					var len = storage.getUnconfirmedAADefinitionsPostedByAAs([row.address]).length;
					if (len > 0)
						console.log("not calling secondary trigger from unit " + objUnit.unit + " to AA " + row.address);
					return (len === 0);
				});
			if (rows.length === 0) {
				saveStateVars();
				addUpdatedStateVarsIntoPrimaryResponse();
				return onDone(objUnit, bBouncing ? error_message : false);
			}
			if (bBouncing)
				throw Error("secondary triggers while bouncing");
			async.eachSeries(
				rows,
				function (row, cb) {
					var child_trigger = getTrigger(objUnit, row.address);
					child_trigger.initial_address = trigger.initial_address;
					child_trigger.initial_unit = trigger.initial_unit;
					if ("max_aa_responses" in trigger && mci >= constants.pemCurvesFixMci) // propagate the cap set on the primary trigger to secondary triggers
