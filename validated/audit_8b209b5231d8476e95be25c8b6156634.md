### Title
Webhook signature verified against attacker-controlled `repository.owner.login`, while all event handlers act on a separate, unchecked `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on one field of the untrusted JSON payload (`repository.owner.login`), while every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, …) resolves the actual `Stack`/`Repository` to mutate from a *different* field of the same payload (`repository.full_name`). Because these two fields are never cross-validated, a party that legitimately owns the webhook secret for *one* organization configured in a multi-org Shipit deployment can forge a payload whose signature validates against their own org while `repository.full_name` names a repository belonging to a completely different organization/stack tracked by the same Shipit instance. This breaks the trust binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization config (including `webhook_secret`) purely by the string found in `repository.owner.login` (or `organization.login`) inside the attacker-supplied JSON body, and `verify_webhook_signature` HMACs the raw body with that organization's secret: [3](#0-2) 

Once the signature check passes, the full, unfiltered `params` (the entire JSON body) is dispatched to every registered handler for the event: [4](#0-3) 

Handlers such as `PushHandler` resolve which `Stack`/`Repository` to act on using a *different* field from the same payload — `repository.full_name` — with no check that it matches the organization that produced a valid signature: [5](#0-4) [6](#0-5) 

Shipit explicitly supports hosting multiple independent GitHub organizations/apps, each with its own `webhook_secret`, in a single instance: [7](#0-6) 

Given this multi-tenant configuration, nothing stops an attacker who controls (or knows) the `webhook_secret` for organization `attacker-org` (e.g., because they administer that org's own GitHub App/webhook settings on the same shared Shipit instance) from POSTing a payload where `repository.owner.login` = `attacker-org` (used only for the signature check) but `repository.full_name` = `victim-org/victim-repo` (used by every handler to find the actual `Stack`/`Repository` to mutate). The signature will validate using `attacker-org`'s secret, and the handler will then operate on `victim-org`'s tracked stack.

The `status` event handler in particular writes commit statuses for the resolved repository/commit, which is directly used to gate whether a commit is "deployable" — confirmed by the controller test that shows an arbitrary `status` webhook creating a `Status` for a specific commit: [8](#0-7) 

Similarly, `push` events (via `PushHandler`) trigger `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack matching the forged `full_name`/branch, and `check_suite` events trigger `RefreshCheckRunsJob`, all scoped only by the unverified `full_name`.

### Impact Explanation
An attacker who legitimately controls the webhook secret of any one organization onboarded into a shared/multi-org Shipit instance can forge signed-looking webhook events (`push`, `status`, `check_suite`) that are applied to stacks belonging to a completely unrelated organization they do not control. This is a cross-repository write: the attacker can inject fabricated commit statuses (potentially flipping a commit's CI state to "success", which feeds into `Stack` deployability/CI-gating logic used by deploy and continuous-deployment flows) and force `GithubSyncJob` syncs against a repository/stack outside their authorization boundary — all without ever presenting an `ApiClient` token, a Shipit session, or credentials for the victim's organization. This matches the Critical "cross-repository writes" / potential "unauthorized deploy" impact category, since forged green CI statuses can enable continuous-deployment or manual deploys of unvetted commits on a victim's stack.

### Likelihood Explanation
Exploitability requires the attacker to know a `webhook_secret` for at least one organization configured on the target Shipit instance — realistic in any multi-tenant/multi-org Shipit deployment where different teams or business units each administer their own GitHub App/webhook secret on a shared engine instance, which is an explicitly supported configuration shape (`config/secrets.development.example.yml`). No GitHub write access, Shipit session, or API token is needed; only the ability to send a raw HTTP POST with a payload whose two organization-identifying fields diverge, which the endpoint never cross-validates.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), assert that the organization used to select/verify the `webhook_secret` matches the owner segment of `repository.full_name` (and any `organization.login` present) before dispatching to handlers, rejecting the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the already-verified `repository_owner` rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known to attacker) and `victim-org` (secret unknown), each tracking stacks such as `victim-org/victim-repo`.
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org_webhook_secret, raw_body)>` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, validates the HMAC successfully with the attacker's own known secret.
5. `Shipit::Webhooks.for_event('status').each { |h| h.call(params) }` runs the status handler, which resolves the commit/stack via `repository.full_name = "victim-org/victim-repo"` and records a forged `success` status on the victim's commit — as demonstrated generically by `test/controllers/webhooks_controller_test.rb` (`:state create a Status for the specific commit`), but here achieved cross-organization using only `attacker-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
