This confirms the vulnerability: the base `Handler` class provides a `stacks` helper that scopes lookups to the repository named in the webhook payload (`Repository.from_github_repo_name(repository_name)&.stacks`), and other handlers like `push_handler.rb` and the `pull_request/*` handlers use `repository_full_name` scoping. `StatusHandler`, however, does not use `stacks` or `repository_name` at all — it queries `Commit.where(sha: params.sha)` directly, matching by bare SHA across the entire `commits` table with no join or filter on `stack.repository`.

### Title
Unscoped `status` webhook writes commit status across repositories via bare-SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, ignoring the webhook payload's `repository.full_name`/owner, unlike sibling handlers (`push_handler.rb`, `pull_request/*_handler.rb`) which scope via `Handler#stacks`/`repository_name`. Any commit row in any stack sharing that SHA gets its status mutated by a webhook that only proves authorization for the repository that actually sent it.

### Finding Description
The broken binding: the code should enforce `commit.stack.repository == payload.repository` before writing, but instead enforces nothing — `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  only filters by `sha`, a value fully controlled by whoever created the commit/status.

`WebhooksController#verify_signature` authenticates the *organization* owning the payload's `repository` (`Shipit.github(organization: repository_owner)`), not the specific target repository being written to [2](#0-1) . So a valid signature only proves "this event genuinely came from GitHub for a repo owned by `repository_owner`" — it says nothing about which `Commit`/`Stack` should be updated. The base `Handler` class exposes `stacks`/`repository_name` helpers precisely to bind writes to the repository that authenticated the event [3](#0-2) , and other handlers use this pattern, but `StatusHandler` bypasses it entirely.

Exploit flow: an attacker who owns (or controls status-posting rights on) any repository — e.g. a fork — that happens to contain a commit with the same SHA as a commit already ingested into a victim's Shipit stack (this occurs naturally with forks/shared history, cherry-picks, or rebase-preserved commits) posts a real GitHub `status` event for `context: ci/e2e`, `state: failure` on their own repo. GitHub signs and delivers this webhook legitimately; `verify_signature` passes because it only checks the attacker's own org's secret. `StatusHandler#process` then updates the status for every `Commit` row across the database matching that SHA, including the victim stack's identical commit, via `commit.create_status_from_github!(params)` → `statuses.replicate_from_github!` [4](#0-3) .

Because the victim stack has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` re-evaluates `deployable?`/`stack.continuous_deployment?` and enqueues `ContinuousDeliveryJob` whenever status changes flip deployability [5](#0-4) ; `add_status` also triggers `stack.schedule_merges` on state transitions [6](#0-5) . A forced `failure` on `ci/e2e` (a required context) can block deploys/merges of the victim's real commit, or conversely a forged `success` can force-ship it — either direction is an unauthorized deploy/rollback/merge decision made using status data that the victim repository never produced.

Existing guards fail here specifically because they operate at the wrong layer: `verify_signature` validates the *sender's own* org/repo association, `drop_unhandled_event`/`ExplicitParameters` validate payload shape, none of them validate that the resolved `Commit`'s owning `Repository` matches `payload.dig('repository','full_name')`.

### Impact Explanation
An attacker who can legitimately post a GitHub commit status on any repository they control can flip CI status for an unrelated victim stack's identical-SHA commit, forcing `ContinuousDeliveryJob` to ship or block based on attacker-controlled data — a cross-tenant "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category (unauthorized deploy/block decision driven by forged status).

### Likelihood Explanation
Requires: (1) a commit SHA that exists in both the attacker's controllable repo and the victim's Shipit-tracked stack — realistic for forks, mirrors, or shared upstream history, which is common in open-source/monorepo setups; (2) the victim stack enabling `continuous_deployment` and requiring/soft-failing on the same status `context`. No Shipit credentials, session, or GitHub App secret are needed — only the ability to post a real status on a repo the attacker controls, which is a normal unprivileged GitHub capability.

### Recommendation
Scope `StatusHandler#process` using the same pattern as other handlers: resolve `stacks` from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`, and restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalently filter commits whose `stack.repository` matches the authenticated repository) before calling `create_status_from_github!`.

2. Create `Commit` rows with the identical `sha` under each stack (`commit_a` on `stack_a`, `commit_b` on `stack_b`).
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha`, `context: "ci/e2e"`, `state: "failure"`.
