### Title
`provision?` operator precedence lets `allow_with_label`/`prevent_with_label` bypass `review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` combines `review_stacks_enabled` with `&&`/`||` without parentheses, so Ruby's operator precedence only ANDs `review_stacks_enabled` against the `allow_all` clause. The `allow_with_label` and `prevent_with_label` clauses are independent `||` branches that can evaluate `true` even when `review_stacks_enabled == false`, causing `ReviewStackAdapter#find_or_create!` to create a real `ReviewStack` for a repository whose owner never opted into review stacks.

### Finding Description
The intended binding is: a `Shipit::ReviewStack` must only be created when `repository.review_stacks_enabled == true`. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. If a repository has `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, and the incoming pull request carries the configured label, the second disjunct alone evaluates to `true`, so `provision?` returns `true` regardless of `review_stacks_enabled`. The same divergence exists for `prevent_with_label` when the label is absent.

`respond_to_pull_request_opened?` gates only on `params.action == "opened" && provision?` [2](#0-1) , and `process` then unconditionally calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [3](#0-2) . `ReviewStackAdapter#create!` performs no independent `review_stacks_enabled` check — it creates the stack from `stack_attributes` (`branch: params.pull_request.head.ref`) and enqueues it for provisioning unconditionally [4](#0-3) .

`Repository#review_stacks_enabled` defaults to `false` at the database level [5](#0-4) , so any repository that has merely turned on `allow_with_label`/`prevent_with_label` behavior (e.g. for planning purposes) without flipping the master "review stacks enabled" switch is exposed. `Repository` has no server-side authorization tied to who opens the PR or applies the label — the attacker only needs to open a PR from their own fork and attach a label whose name matches `provisioning_label_name` (a value that, per the settings view, is visible/configurable metadata, not a secret) [6](#0-5) .

None of the existing tests cover this combination: `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`'s `"only provision stacks for repos with auto-provisioning enabled"` test only disables `review_stacks_enabled` while using `allow_all` behavior [7](#0-6) , and the `allow_with_label`/`prevent_with_label` tests rely on the helper's default `provisioning_enabled: true` [8](#0-7) , so the `review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label` gap is never exercised.

### Impact Explanation
An unprivileged GitHub user who can open a pull request against any repository tracked by Shipit — even one whose owner explicitly left `review_stacks_enabled` off — can force creation of a `Shipit::ReviewStack` pointed at their fork's branch. Once queued via `Shipit::ReviewStackProvisioningQueue.add(stack)`, the stack proceeds through Shipit's normal provisioning/deploy pipeline, which reads `shipit.yml` from the attacker-controlled branch and executes its steps through `Command#start`/`PTY.spawn` on the deploy host — i.e., attacker-controlled code execution on infrastructure the repository owner believed was not review-stack-enabled. This matches the Critical category (RCE on the deploy host via `Command`/`PTY.spawn`) and is repeatable against any repository configured with `allow_with_label` or `prevent_with_label` but `review_stacks_enabled: false`.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` (attacker adds the known/guessable label to their own PR) or `prevent_with_label` (attacker simply omits the label, which is the default state of any PR) while `review_stacks_enabled` is `false` — a plausible misconfiguration since `review_stacks_enabled` defaults to `false` and an operator may set a provisioning behavior in advance of fully enabling review stacks. No Shipit credentials, GitHub App keys, or webhook secrets are needed beyond the attacker's own ability to open a PR and label it (both self-service actions on their own PR). This is a pure logic bug reachable through the normal, signed `pull_request` webhook flow, so it does not require forging signatures.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every provisioning behavior clause, e.g.:

```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Apply the same fix to any sibling handlers with the same pattern (e.g. `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler` if they replicate this logic).

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:

```ruby
test "does NOT create stacks for allow_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Assert `repository.review_stacks_enabled == false` before the call and `Shipit::Stack.count` unchanged after — with the current code this assertion fails because a stack IS created (`assert_difference` would pass instead), demonstrating the binding `repository.review_stacks_enabled == true` is not enforced before `ReviewStackAdapter#create!`.
