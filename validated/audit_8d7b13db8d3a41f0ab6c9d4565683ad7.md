## Analysis

The reported bug class — summing multiple independently-rounded-up constituent fee shares causes the total distributed amount to exceed the collected amount — has a direct analog in ocore's commission-distribution logic (`headers_commission.js` and `paid_witnessing.js`). In both cases a single collected commission amount is split into several shares (one per recipient/witness), each share is rounded with `Math.round` **independently**, and the sum of the rounded shares is later inserted as brand-new spendable `_outputs` records that become real currency once claimed via a `headers_commission`/`witnessing` input in a payment message.

### Title
Independent rounding of split headers/witnessing commission shares can mint more bytes than were actually collected - (File: `headers_commission.js`, `paid_witnessing.js`)

### Summary
When a unit's `headers_commission` (paid to the winning child unit's author(s)) or `payload_commission` (paid to witnesses) is split among multiple recipients, each recipient's share is computed with `Math.round()` independently instead of rounding the whole amount once and apportioning remainders. Because the shares are summed and inserted as new `headers_commission_outputs`/`witnessing_outputs` rows that later become spendable “income” for those addresses, the aggregate amount distributed for a single payer unit can exceed the commission that unit actually paid — creating bytes out of thin air.

### Finding Description
For headers commission with multiple `earned_headers_commission_recipients`, each recipient's cut is computed as: [1](#0-0) 
and, in the SQL/db-driven code path, again per recipient row: [2](#0-1) 

Each recipient's amount is `Math.round(full_amount * share / 100.0)`, rounded in isolation. `validateHeadersCommissionRecipients` only enforces that the declared percentage shares sum to exactly 100: [3](#0-2) 
but this guarantees the *percentages* sum to 100, not that the *rounded byte amounts* sum to `full_amount`. An attacker who is the sole author of multiple addresses recorded as `earned_headers_commission_recipients` can choose share percentages (e.g. 34/33/33, or more recipients with skewed splits) such that each individual `Math.round` rounds up, so the sum of the recipients' rows exceeds `full_amount` by 1+ bytes.

The analogous flaw exists in witnessing commission distribution, where a unit's `payload_commission` is split evenly among the witnesses who get credit for it: [4](#0-3) 
and the SQL equivalent: [5](#0-4) 
Here `Math.round(payload_commission / countPaidWitnesses[unit])` (or `ROUND(1.0*payload_commission/count_paid_witnesses)`) is applied per witness and then summed across `countPaidWitnesses` witnesses. Whenever `payload_commission mod countPaidWitnesses >= countPaidWitnesses/2`, every witness's share rounds up, and the total distributed exceeds `payload_commission` by up to `countPaidWitnesses - remainder` bytes. Since `payload_commission` is simply the byte size of the unit's payload — fully controlled by whoever posts the unit — an attacker can deliberately size their unit's payload to trigger this condition on (close to) every unit they post.

These per-mci amounts are not just bookkeeping: they are inserted into `headers_commission_outputs` / `witnessing_outputs` and later become genuine spendable value. `calcEarnings` sums these rows over an mci range for an address: [6](#0-5) 
and this sum is added directly to `total_input` when validating a payment message that spends a `headers_commission`/`witnessing` input: [7](#0-6) 
`total_input` is checked against the unit's declared outputs, so any excess bytes minted by the rounding bug become fully transferable, spendable currency.

### Impact Explanation
This is a systemic, permissionless supply-inflation bug: every stable unit that pays headers/witnessing commission goes through `calcHeadersCommissions`/`updatePaidWitnesses`, invoked automatically during main-chain stabilization: [8](#0-7) 
No special privilege is required — any ordinary unit poster (for witnessing commission, by controlling their own payload size) or any multi-author unit author (for headers commission, by controlling `earned_headers_commission_recipients` shares) can trigger rounding-up on their own commission splits repeatedly, minting extra bytes into their own or colluding addresses over time. This is a genuine base-currency (bytes) supply inflation, matching a High severity issue.

### Likelihood Explanation
High. The condition (`remainder >= n/2`) is met roughly half the time for arbitrary payload sizes and is straightforward to force deterministically by choosing payload size (witnessing case) or recipient share percentages (headers-commission case). No race condition, no cooperation from other network participants, and no elevated privileges are needed — only posting ordinary units/messages that ocore already accepts as valid.

### Recommendation
Do not round each recipient/witness share independently. Compute the total once, then allocate remainders deterministically (e.g., distribute the whole integer part per recipient/witness and assign the leftover remainder units to a canonical subset, such as the first N recipients by sort order, so the sum of distributed amounts is provably equal to the original `full_amount`/`payload_commission`). Apply this fix to both the RAM/in-memory computation and the SQL/db-driven computation paths in `headers_commission.js` (lines 183, 202) and `paid_witnessing.js` (lines 162, 173), keeping both code paths consistent (they are already cross-checked against each other via `_.isEqual`, so both must be fixed together).

### Proof of Concept
Witnessing-commission case:
1. A unit poster crafts a unit whose `payload_commission` (byte size fee) is, for example, 11 bytes, and it ends up credited to 3 witnesses (`countPaidWitnesses[unit] = 3`).
2. In `buildPaidWitnesses`/`buildPaidWitnessesForMainChainIndex`, each of the 3 witnesses' share is computed as `Math.round(11/3) = Math.round(3.667) = 4`. [9](#0-8) 
3. Total inserted into `witnessing_outputs` for this unit = 4 × 3 = 12, one byte more than the 11 bytes actually collected as `payload_commission`.
4. Each witness address can later spend its 4-byte `witnessing_outputs` row as a `type: "witnessing"` input in a payment, per `calcEarnings`/`validatePaymentInputsAndOutputs`, so the extra byte becomes real, transferable currency, inflating the total byte supply.
5. Repeating this pattern across many self-authored/sized units in which the poster or colluding witnesses control the rounding remainder, produces systemic, cumulative inflation of the byte supply.

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
