### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no scoping to the repository named in the webhook payload, unlike `PushHandler` and `CheckSuiteHandler` which both scope through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`). Because `sha` is only unique per `(sha, stack_id)` and not globally, a single validly-signed `status` webhook for repository X can write CI status onto commits belonging to an unrelated stack Y whenever the two share a commit sha (e.g., forked repositories with shared history).

### Finding Description
The binding that should hold is: **every `Commit` mutated by a webhook == a `Commit` belonging to a stack whose `Repository` matches `payload.dig('repository', 'full_name')`**.

`PushHandler#process` enforces this via `stacks.not_archived.where(branch:)...` [1](#0-0) , and `CheckSuiteHandler#process` enforces it via `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [2](#0-1) . Both route through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` before touching any commit [3](#0-2) .

`StatusHandler#process`, however, does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [4](#0-3) 

This query is a bare, table-wide `Commit.where(sha:)` — it never calls `stacks`, never touches `repository_name`, and never checks `commit.stack.repository`. The `sha` column is indexed and constrained unique only per `(sha, stack_id)` pair, not globally [5](#0-4) , meaning the schema explicitly permits (and the app populates, via independent per-stack GitHub sync in `PushHandler`/`Stack#sync_github`) multiple `Commit` rows across different stacks sharing the same `sha` — the normal case for forks or shared-history repos.

`commit.create_status_from_github!(params)` writes a new `Status` row scoped to `commit.stack_id` [6](#0-5) , and further triggers `Hook.emit` for `commit_status`/`deployable_status` and can call `stack.schedule_merges` [7](#0-6) , which can affect deploy/merge decisions.

**Exploit flow:** Attacker forks a public repo tracked as stack X, also has stack Y tracked (their own fork, satisfying "any GitHub user who can push to a fork"). Both stacks contain a `Commit` row with the same `sha` (shared ancestor commit, common in fork workflows and something Shipit does nothing to prevent). Attacker sends one webhook POST to `/webhooks` with a valid signature for repo Y (which they control) and `X-Github-Event: status`, `sha` = the shared sha, `state: success`. Because `StatusHandler` never checks that `repository_name` (=Y) corresponds to the commit's owning stack, the query also finds and mutates the `Commit` belonging to stack X, writing a forged `Status` for repository X that the attacker does not control.

**Why existing guards fail:** `verify_signature`/`GitHubApp#verify_webhook_signature` only prove the payload came from GitHub for repo Y — they say nothing about which stacks the `sha` may belong to. `ExplicitParameters` only validates the shape of `sha`/`state`, not ownership. There is no model validation preventing identical `sha` across different stacks (by design, since the unique index is `(sha, stack_id)`). No other guard rescopes the query to `repository_name`.

### Impact Explanation
A single crafted, validly-signed webhook for a repository the attacker controls can write a fabricated `Status` (e.g., forcing `success`) onto a commit belonging to a completely different tenant's stack, without any authentication or authorization tied to that other stack/repository. Since `deployable?` and `blocked?` on `Commit` depend on `status` derived from these `Status` rows [8](#0-7) , and `schedule_continuous_delivery`/`schedule_merges` can act on status changes, this can enable an unauthorized deploy or merge on the victim stack. This is a cross-tenant write triggered by an unprivileged party controlling only their own fork — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Preconditions: two Shipit stacks (X = victim, Y = attacker-controlled fork) exist and share at least one commit sha, which is common and unavoidable in fork-based CI workflows and not prevented anywhere in the codebase. The attacker needs a valid webhook signature for repo Y only — trivially available since they own/administer that repo's GitHub webhook configuration (or can get GitHub to emit the event by pushing/creating a status there). No Shipit credentials, session, or team membership required. The attack is a single HTTP POST and is fully repeatable against any shared sha across any pair of stacks.

### Recommendation
Scope `StatusHandler#process` through the same `stacks` resolution used by `PushHandler`/`CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures only commits belonging to stacks whose `Repository` matches the webhook's `repository.full_name` are mutated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, though `test/**` itself is out-of-scope for this audit, this proof would live there for validation):
1. Create `repository_x` (`Shipit::Repository`, e.g. `owner/repo-x`) with `stack_x`, and `repository_y` (`owner/repo-y`) with `stack_y`.
2. Create `commit_x = Shipit::Commit.create!(stack: stack_x, sha: 'deadbeef'*5[0,40], ...)` and `commit_y = Shipit::Commit.create!(stack: stack_y, sha: same_sha, ...)`.
3. Build a `status` webhook payload with `repository.full_name = 'owner/repo-y'` and `sha: same_sha`, `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing controller-level signature verification, or POST through `/webhooks` with a computed valid HMAC for the test's `webhook_secret`).
5. Assert `commit_y.statuses.reload.count == 1` (expected) AND assert `commit_x.statuses.reload.count == 1` (this assertion currently **passes**, proving the cross-tenant write — after the fix it must be `0`). [4](#0-3) [3](#0-2)
