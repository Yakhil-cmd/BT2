### Title
Webhook signature verification org (`repository.owner.login`) is never bound to the repository actually mutated (`repository.full_name`), enabling cross-tenant `PullRequest#update` - (File: `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to verify against using `params.dig('repository','owner','login')`, but the handler that actually mutates state (`AssignedHandler#process`) looks up the target `Repository`/`Stack`/`PullRequest` using the independent field `params.repository.full_name`. Nothing forces these two fields to refer to the same organization, so an attacker who legitimately owns a tenant (`attacker-org`) with its own valid `webhook_secret` can sign a payload whose `repository.owner.login` is `attacker-org` (to pass signature verification) while `repository.full_name` points at `victim-org/victim-repo`, producing an authenticated-looking webhook that mutates victim-org's `PullRequest`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks:

`org(secret that verified the HMAC) == org(Repository row mutated)`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and fetches `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature(signature, raw_post)` against the **entire raw body**. [1](#0-0) 
2. `GitHubApp#verify_webhook_signature` only checks that the HMAC of the raw body matches the secret for whichever org was resolved — it has no notion of which repository is "inside" the payload; it just proves "whoever holds `attacker-org`'s secret signed this exact byte string." [2](#0-1) 
3. Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the parsed JSON to `AssignedHandler`, which never re-reads `repository.owner.login`. Instead it derives the repository solely from `params.repository.full_name`: [3](#0-2) 
4. `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)`, returning the real victim `Repository` row if it exists (a legitimately onboarded stack): [4](#0-3) 
5. `AssignedHandler#pull_request` joins `stacks: :repository` to find the victim's `PullRequest` by `number` and `repositories.id`, then `#process` calls `pull_request.update(github_pull_request: params.pull_request)` — an unauthenticated write to victim-org's data driven entirely by attacker-controlled payload content. [5](#0-4) 

Exploit flow: attacker (owner of `attacker-org`, with their own legitimately configured `webhook_secret` in `Shipit.github`) builds a JSON body:
```json
{
  "action": "assigned",
  "number": <victim PR number>,
  "pull_request": { ... attacker-chosen fields ... },
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
Signs the raw body with `attacker-org`'s own secret, sets `X-Hub-Signature` and `X-Github-Event: pull_request`, and POSTs to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (a real, known org) and successfully verifies the signature against the attacker's own secret — nothing here inspects `full_name`. The request proceeds to `AssignedHandler`, which resolves the *victim's* real `Repository`/`Stack`/`PullRequest` via `full_name` and executes `pull_request.update(...)`.

None of the existing guards prevent this: `drop_unhandled_event` only checks the event type exists; `verify_signature` only checks org-vs-secret consistency for whatever org is *claimed* in `owner.login`, never against `full_name`; `ExplicitParameters` schema (`requires :repository do requires :full_name, String end`) validates types/presence, not cross-consistency with `owner.login` (which the schema doesn't even declare); there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` in the webhook path since it is a machine-to-machine endpoint authenticated purely by HMAC.

### Impact Explanation
An unprivileged attacker who owns any org onboarded to the multi-tenant Shipit instance can force writes into **any other tenant's** `PullRequest` records (`github_pull_request` payload, which downstream code treats as trusted GitHub API pull request data — labels, assignees, head SHA/ref, state, etc.) by simply changing `repository.full_name` in a self-signed webhook body. This is a cross-tenant unauthorized write ("a payload for one repository mutating another's stack") and is repeatable against any victim stack/PR number the attacker can guess or observe (PR numbers are small integers, and stack repo names are typically public). Same-shaped handlers (`EditedHandler`, `ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) share the identical `repository = Repository.from_github_repo_name(params.repository.full_name)` pattern decoupled from the signature-verifying `owner.login`, so the same technique can archive/unarchive victim review stacks, capture forged labels onto a victim PR, etc. This matches the Critical category: "a payload for one repository mutating another's stack."

### Likelihood Explanation
Preconditions: the multi-tenant `Shipit.github` config must include at least one other org besides the victim's (i.e., the attacker's own org must be legitimately onboarded with its own `webhook_secret` — not a leaked secret). This is exactly the scenario described in the question and is realistic for any Shipit instance serving multiple GitHub orgs/tenants, which is the documented multi-tenant configuration format shown in `config/secrets.development.example.yml`. Attacker cost is trivial: sign one HTTP POST with a secret they legitimately hold, no GitHub API calls, no session, no privileged role needed. Fully repeatable per victim PR/stack.

### Recommendation
In `WebhooksController#verify_signature` (or before dispatch), enforce that the repository referenced for lookup (`params.repository.full_name`) belongs to the same organization whose secret verified the signature — e.g., reject the request unless `repository.full_name.split('/').first.casecmp(repository_owner) == 0`. Additionally, in `Shipit::Webhooks::Handlers::Handler` (and all subclasses using `Repository.from_github_repo_name(params.repository.full_name)`), cross-validate that the resolved `Repository#owner` matches the verified organization before performing any lookup/mutation, rather than trusting `full_name` in isolation.

### Proof of Concept
minitest plan (no live GitHub, using existing test fixtures/patterns from `test/controllers/webhooks_controller_test.rb`):

```ruby
test "assigned webhook signed by attacker-org's own secret can mutate victim-org's pull request via mismatched full_name" do
  victim_stack = shipit_stacks(:shipit) # real onboarded stack, e.g. owner "shopify"
  victim_pr = shipit_pull_requests(:...) # existing PR on victim_stack, number: N

  attacker_secret = "attacker-orgs-own-legit-secret"
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", webhook_secret: attacker_secret)
  )

  body = {
    action: "assigned",
    number: victim_pr.number,
    pull_request: { id: 1, number: victim_pr.number, url: "https://...", title: "pwned",
                     state: "open", additions: 0, deletions: 0,
                     head: { sha: "deadbeef", ref: "attacker-branch" },
                     user: { login: "attacker" }, assignees: [], labels: [] },
    repository: { owner: { login: "attacker-org" }, full_name: victim_stack.repository.github_repo_name },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)}"

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  before_json = victim_pr.github_pull_request

  post :create, body: body, as: :json

  assert_response :ok
  victim_pr.reload
  refute_equal before_json, victim_pr.github_pull_request # victim PR mutated by attacker-org-signed payload
end
```

Assert both sides of the binding explicitly:
- Side A (org whose secret verified HMAC): `"attacker-org"`
- Side B (org owning mutated `Repository`/`PullRequest`): `victim_stack.repository.owner` (e.g. `"victim-org"`/`"shopify"`)
- Test proves A != B yet the write still occurs (`assert_response :ok` + `victim_pr.github_pull_request` changed), confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
