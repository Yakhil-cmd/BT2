This confirms the vulnerability. Notably, `PushHandler`, `CheckSuiteHandler`, and all `PullRequest::*Handler` classes correctly scope their queries through `stacks` / `repository`, both of which derive from `Handler#repository_name` (`payload.dig('repository', 'full_name')`) via `Repository.from_github_repo_name`. `StatusHandler` is the outlier: it uses `Commit.where(sha: params.sha)` globally with no repository/stack scoping at all.## Title
`StatusHandler#process` matches commits globally by SHA with no repository/stack scoping, letting an attacker's own signed `status` webhook flip CI state and trigger continuous deployment on an unrelated victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire installation, with no filter on repository or stack, unlike every other webhook handler in this codebase. `WebhooksController#verify_signature` only proves the payload was signed by *some* GitHub organization/app configured in Shipit (the one named as `repository.owner.login` in the payload); it never checks that this organization actually owns the commit(s) being mutated. Combined, an attacker who legitimately controls a repository (and thus a legitimately signed webhook channel) can flip the state of any commit sharing that SHA in any other stack, including ones belonging to different repositories/organizations, triggering `Status#after_create :enable_ci_on_stack` and `Status#after_commit :schedule_continuous_delivery` on the victim's stack.

## Finding Description
The broken binding: the question posits `stack_that_signed_the_webhook == stack_that_gets_mutated`. Tracing the code shows this equality is **not enforced**:

- `WebhooksController#verify_signature` at [1](#0-0)  resolves `Shipit.github(organization: repository_owner)` from the *payload's own* `repository.owner.login` and verifies HMAC against that organization's `webhook_secret`. This only proves "this payload was signed by whichever org's secret matches the org named inside the payload" - it does not bind the payload to any specific commit/stack ownership.
- `StatusHandler#process` at [2](#0-1)  does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - a global, unscoped lookup by `sha` alone, with no join on `repository`/`stack`.
- Contrast with every other handler in the same `Handlers::Handler` base class, which uses `stacks` (derived from `Repository.from_github_repo_name(repository_name)`, i.e., `payload.dig('repository', 'full_name')`) at [3](#0-2) , e.g. `PushHandler#process` (`stacks.not_archived.where(branch:)`) at [4](#0-3)  and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`) at [5](#0-4) . `StatusHandler` never reads `payload['repository']` at all, so it cannot scope by it.
- Once a matching `Commit` row is found (regardless of which stack/repository it belongs to), `create_status_from_github!` creates a `Status` at [6](#0-5) , which fires `after_create :enable_ci_on_stack` (`commit.stack.enable_ci!`) and `after_commit :schedule_continuous_delivery` (`commit.schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)`) at [7](#0-6) .
- `ContinuousDeliveryJob#perform` at [8](#0-7)  calls `stack.trigger_continuous_delivery` if `continuous_deployment?` is true and the stack isn't occupied.
- `Stack#trigger_continuous_delivery` at [9](#0-8)  calls `next_commit_to_deploy`, which relies on `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) at [10](#0-9) . If the attacker's `state: 'success'` status flips this previously-`pending`/genuinely-unreviewed commit to `success`, and it is not blocked, `trigger_deploy` proceeds.

Why existing guards fail: `verify_signature` correctly authenticates *the attacker's own org's webhook*; that guard is working as intended for the attacker's own tenant. The actual gap is authorization-scoping inside `StatusHandler`, which trusts a raw `sha` string from the payload to select *any* commit across *any* tenant's stacks. There is a unique index on `(sha, stack_id)` at [11](#0-10) , confirming the schema explicitly allows the same SHA to exist under multiple distinct `stack_id`s - which is the exact scenario (shared git history / forked template repos) the question describes, and which `StatusHandler` fails to disambiguate.

Exact attacker request: attacker POSTs to `/webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with their own org's `webhook_secret` (obtained by installing the Shipit GitHub App on their own throwaway repo, if the deployment uses the documented "multiple GitHub applications" per-organization config, as described in `docs/setup.md`), and body `{"sha": "<shared_sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}}, ...}`. `verify_signature` passes because `attacker-org`'s own secret is used to sign a payload naming `attacker-org`. `StatusHandler#process` then matches and mutates the victim's `Commit` row purely by `sha`.

## Impact Explanation
This is an unauthorized deploy trigger: a payload authenticated for one repository/organization (`attacker-org`) mutates another organization's stack's commit status (`victim/prod`) and can cause `Stack#trigger_continuous_delivery` to run a real deploy of a commit the victim organization never approved via CI, satisfying the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". It is repeatable against any pair of stacks that happen to share a git-identical commit SHA (feasible via shared template repos / cherry-picked commits / vendored subtree histories), and the blast radius spans every tenant/stack hosted on the same Shipit instance whose commit history could ever collide with an attacker-controlled repository.

## Likelihood Explanation
Preconditions required: (1) the victim stack has `continuous_deployment: true` and a genuinely `pending` commit; (2) the attacker must have their own repository wired into the same Shipit instance with a legitimately configured GitHub App installation (their own org's `webhook_secret`) — feasible under the documented multi-org configuration (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`); (3) the attacker needs a commit with an identical SHA to the victim's pending commit, which is realistically achievable only via shared git history (common ancestor/template repos), not by brute force. Given these conditions, the attacker's cost per request is a single signed webhook POST that requires no secrets belonging to the victim.

## Recommendation
Scope `StatusHandler#process`'s commit lookup by the repository the payload claims to be for, mirroring every other handler: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and constrain the query to `stacks.commits.where(sha: params.sha)` (or `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { ... })`) instead of the unscoped `Commit.where(sha: params.sha)`.

## Proof of Concept
minitest plan (add to `test/controllers/webhooks_controller_test.rb` or a new `status_handler_test.rb`):
1. Create `victim_stack` (`continuous_deployment: true`) with a `victim_commit` whose `state` is `pending` (no statuses / only pending status), belonging to `Repository` `victim/prod`.
2. Create a second `attacker_stack`/`Repository` `attacker/throwaway`, with a `Commit` row having the **same `sha`** as `victim_commit` (simulating shared git history) but attached to `attacker_stack`.
3. 4. POST to `/webhooks` with `X-Github-Event: status`.
