### Title
Webhook signature verification is bound to an attacker-chosen organization, but downstream handlers act on payload fields never covered by that binding, enabling cross-organization forgery of CI status and unauthorized deploy triggers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on an attacker-supplied field inside the JSON payload itself, rather than any value tied to the specific stack/repository the webhook is meant to affect. Because the handlers that consume the payload (in particular `StatusHandler`) do not re-validate that the acted-upon resource actually belongs to the organization whose secret was used to authenticate the request, an entity that legitimately controls one GitHub App/organization configured in a multi-org Shipit deployment can forge webhooks that mutate state belonging to a completely different organization's stacks.

### Finding Description
`verify_signature` computes `repository_owner` straight from the untrusted request body and uses it to pick the `github_app`/secret to verify against: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple independent GitHub Apps/organizations sharing a single instance, each with its own `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications"). Each org's own administrator necessarily knows (or generated) that org's `webhook_secret` when creating their App. Nothing in `verify_signature` binds the authenticated organization to the specific repository/stack that the event payload is later used to mutate — the signature only proves "this body was signed by *some* org's secret," where the org is picked by a field (`repository.owner.login` / `organization.login`) inside that very body.

The `status` event handler compounds this: it never scopes by repository or organization at all — it matches purely on commit SHA globally across the entire Shipit installation: [3](#0-2) 

Creating a `Status` record triggers CI-gating and continuous-delivery side effects automatically: [4](#0-3) [5](#0-4) 

And whether a commit is eligible for deployment depends directly on having a `success` status: [6](#0-5) 

This is the same class of bug as the Tapioca report: a binding used for authorization/authentication (which secret verified the message) is decoupled from the binding actually enforced when the payload is acted upon (which commit/stack/repository gets mutated). Here the equality that should hold — "organization that authenticated == repository/stack that is written" — is never enforced.

### Impact Explanation
An entity that only administers organization A's GitHub App/webhook secret in a shared, multi-org Shipit deployment can:
1. Craft an HTTP `X-Github-Event: status` webhook whose JSON body sets `repository.owner.login` to their own org "A" (so `verify_signature` selects and validates against A's own known secret), while setting `sha` to the head commit SHA of a stack that belongs to an unrelated organization B configured on the same instance.
2. Because `StatusHandler` matches `Commit.where(sha: params.sha)` with no repository/org scoping, a forged `state: "success"` status gets attached to organization B's commit.
3. This status creation calls `schedule_continuous_delivery`, and combined with `deployable?`/`trigger_continuous_delivery` logic, can trigger an unauthorized deploy for organization B's stack — an escalation the attacker has no legitimate authority over.

This matches the "unauthorized deploy" High/Critical impact category in scope.

### Likelihood Explanation
Requires only that: (a) the Shipit instance hosts more than one organization (a documented, supported configuration), and (b) the attacker administers/controls one of those organizations' GitHub App webhook secret — not any Shipit `ApiClient` token, GitHub App private key, or repository write access on the victim organization. This is a realistic misuse of a documented multi-tenant feature by an "unprivileged" (with respect to the victim org) but technically-capable party.

### Recommendation
- Do not use a payload-controlled field to select the verifying secret; either verify signatures per-organization based on a securely known routing key (e.g., a per-org endpoint URL/path segment, not payload content), or verify against all configured secrets and then require every downstream handler to independently confirm the resolved organization matches the resource being mutated.
- In every handler (especially `StatusHandler`, `CheckSuiteHandler`, `PushHandler`), scope lookups (`Commit.where(sha:)`, etc.) to the repository/organization that was actually authenticated for this request, not solely to unscoped identifiers like a bare SHA.
- Consider passing the authenticated organization from `verify_signature` through to `Webhooks.for_event(event).each { |handler| handler.call(params) }` and asserting equality with `params.dig('repository','owner','login')` before processing.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps/orgs, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config), each with its own stacks/commits synced.
2. As the administrator/holder of `orgA`'s `webhook_secret` (a role with no legitimate authority over `orgB`), construct a JSON body:
```json
{
  "sha": "<head sha of an orgB commit/stack>",
  "state": "success",
  "repository": { "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner == "orgA"`, fetches `orgA`'s app/secret, and the signature validates successfully — [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the orgB commit (no org check), creating a `success` `Status` for it — [7](#0-6) .
6. `Status#schedule_continuous_delivery` fires, and if orgB's stack has continuous delivery enabled and the commit is otherwise deployable, an unauthorized deploy is triggered for a stack the attacker (as `orgA`'s controller only) has no legitimate authority over.
