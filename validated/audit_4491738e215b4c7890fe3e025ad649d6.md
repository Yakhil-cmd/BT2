### Title
Forged CI status for arbitrary commits due to unscoped `StatusHandler` and organization-based signature selection - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController` selects which GitHub App (and therefore which webhook secret) to verify a webhook against using an unverified payload field, and `Shipit::Webhooks::Handlers::StatusHandler` writes commit statuses without ever checking that the commit belongs to a repository owned by the organization whose secret validated the request. In a multi-organization installation where at least one configured organization has no `webhook_secret` (a supported, documented configuration), an unauthenticated attacker can forge a `status` webhook that is accepted without any real signature check, and use it to set an arbitrary CI state on a commit belonging to a completely different, properly-secured stack/repository — enabling an unauthorized merge.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and its secret) to validate the signature against using `repository_owner`, which is read straight out of the *unverified* JSON body before the signature check occurs: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: [3](#0-2) 

`webhook_secret` is explicitly documented/shipped as an optional value (`webhook_secret: # nil`) in both the setup docs and example secrets files, so a real installation with multiple GitHub Apps can legitimately have one organization configured without a secret: [4](#0-3) [5](#0-4) 

Once the (forged) signature check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` updates commit statuses using only the `sha` supplied in the payload — it never scopes the lookup to the repository/organization that the signature was validated against, unlike `Handler#stacks`/`PushHandler`/`CheckSuiteHandler`, which do filter by `repository_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository/commit being written`

Because (a) the org used to select the secret is taken from unverified payload data, (b) a blank secret makes verification a no-op, and (c) `StatusHandler` performs a global `Commit.where(sha:)` with no repository/stack scoping, this equality is broken: an attacker can authenticate as "organization with no secret" while writing a status onto a commit that belongs to a stack of "organization with a real secret."

### Impact Explanation
`Status#state` transitions drive `Commit#add_status`, which calls `stack.schedule_merges` whenever the new state is `pending` or `success`: [9](#0-8) 

An attacker-forged `success` status on a target commit can therefore make that commit appear CI-green to the merge queue, enabling `MergeRequest#merge!` to proceed and merge/deploy a pull request that never actually passed CI — an unauthorized merge on a repository the attacker has no legitimate write access to. This crosses the "unauthorized deploy, rollback, or merge" Critical-impact bar defined for this engine.

### Likelihood Explanation
Exploitation requires no session, no `ApiClient` token, and no possession of any organization's real `webhook_secret`. It only requires: (1) the Shipit installation configures more than one GitHub organization (the documented multi-org pattern) and at least one of them has a blank/unset `webhook_secret` (an explicitly supported configuration shown in the shipped example secrets files), and (2) knowledge of a target commit `sha` that is trivially public information on GitHub. Given `webhook_secret` is presented as optional in the engine's own setup documentation, this is a realistic deployment state rather than a contrived misconfiguration, making the likelihood moderate-to-high for any multi-tenant Shipit deployment.

### Recommendation
- Verify the HMAC signature before doing anything else, and do so using the secret chosen for the resolved *repository* (derived from a value covered by the signature check flow), not by trusting `repository_owner`/`organization.login` from the unverified body to pick which secret to check against.
- Reject webhooks entirely for organizations configured with a blank `webhook_secret`, or require a secret to be present for every configured organization, rather than treating a blank secret as "always verified."
- In `StatusHandler#process` (and any other handler that mutates commit/stack state), scope the query by the repository the webhook was authenticated for (e.g., via `Handler#stacks`/`repository_name`) instead of a bare `Commit.where(sha:)` lookup across the entire instance.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `victim-org` (with a real `webhook_secret`, owning stack `victim-org/app`) and `attacker-org` (with `webhook_secret` left blank, per the documented optional config).
2. Find the `sha` of a real, currently-pending/failing commit in `victim-org/app` (public GitHub data).
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
   ```json
   { "repository": { "owner": { "login": "attacker-org" } }, "sha": "<victim commit sha>", "state": "success", "context": "ci/forged" }
   ```
   No `X-Hub-Signature` needs to be valid — `verify_webhook_signature` returns `true` because `attacker-org` has no configured secret (`lib/shipit/github_app.rb:76-77`).
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches the commit purely by `sha` and creates a `success` status on it, regardless of it belonging to `victim-org`'s stack, potentially triggering `schedule_merges` and an unauthorized merge.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
