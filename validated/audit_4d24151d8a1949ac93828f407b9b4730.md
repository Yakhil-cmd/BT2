### Title
Operator-precedence bug in `PullRequest::ReopenedHandler#unarchive?` bypasses `review_stacks_enabled` gate, allowing unauthenticated PR-reopen to trigger stack unarchival/provisioning and `PTY.spawn` execution - (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`ReopenedHandler#unarchive?` replicates the same `&&`/`||` precedence defect present in `opened_handler.rb`: `repository.review_stacks_enabled` only binds to the first disjunct (`allow_all?`), so when `provisioning_behavior == :prevent_with_label` and the PR carries no label, `unarchive?` evaluates `true` regardless of `review_stacks_enabled`. This lets an attacker who owns a PR simply reopen it (with no label) to trigger `ReviewStackAdapter#unarchive!` → `ReviewStackProvisioningQueue.add` → eventual `Command`/`PTY.spawn` execution of `shipit.yml` from the attacker's ref, on a repository where review stacks were explicitly disabled. This part of the claim is confirmed. However, `UnlabeledHandler` does **not** share this bug: its gating method `respond_to_label_change?` places `repository.review_stacks_enabled` as an explicit top-level `&&` term ANDed with the parenthesized `(archive? || unarchive?)`, and its own `archive?`/`unarchive?` methods contain no `review_stacks_enabled` reference at all, so no precedence ambiguity exists there.

### Finding Description
The broken binding is: `repository.review_stacks_enabled == true` must equal the actual condition gating any `Command`/`PTY.spawn` execution for that repository's stacks. In `ReopenedHandler`: [1](#0-0) 
`unarchive?` is written as `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Because Ruby's `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)` — the third disjunct is entirely independent of `review_stacks_enabled`. `respond_to_pull_request_reopened?` only ANDs `params.action == "reopened"` with `unarchive?`, so no outer guard fixes this: [2](#0-1) [3](#0-2) 

Attack: attacker owns a repo/PR where the maintainer has set `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label` (a legitimate, non-attacker-controlled config choice meant to disable review stacks entirely, or restrict provisioning). Attacker ensures no provisioning label is present on their own PR (fully attacker-controlled), closes then reopens the PR (or the PR was already closed and they reopen it), sending a standard `pull_request` `reopened` webhook. `unarchive?` evaluates true, `stack.unarchive!` is called via `ReviewStackAdapter#unarchive!`: [4](#0-3) 
which either creates the stack (`create!` if none exists, itself also calling `ReviewStackProvisioningQueue.add`) or re-enqueues an existing archived stack via `ReviewStackProvisioningQueue.add(stack)`. `ReviewStackProvisioningQueue.add` calls `stack.enqueue_for_provisioning`: [5](#0-4) 
This queued stack is later picked up by the cron-driven `ReviewStackProvisioningQueue.work` → `stack.provision`, eventually invoking `Command`/`PTY.spawn` against the attacker's branch/ref. No signature or authentication check intervenes here: `verify_signature`/webhook signature checks validate that the request came from GitHub for *some* repo, but do not re-validate the semantic gating logic of `review_stacks_enabled`; that gate is defeated purely by the precedence bug in application code, not by forging any signature.

By contrast, `UnlabeledHandler` correctly isolates the gate: [6](#0-5) 
Here `respond_to_label_change?` ANDs `repository.review_stacks_enabled` with the parenthesized `(archive? || unarchive?)` at the top level, where every top-level operator is `&&`; there's no operator-precedence hazard because `archive?`/`unarchive?` themselves never reference `review_stacks_enabled`. So the claim that `UnlabeledHandler` "replicates" the bug does not hold for this codebase snapshot.

### Impact Explanation
For repositories where the maintainer has disabled review stacks (`review_stacks_enabled = false`) but left `provisioning_behavior = :prevent_with_label`, any attacker who can open/reopen a PR on that repository (i.e., any GitHub user with fork/PR access, no Shipit privileges) can force stack unarchival/(re)provisioning, which flows into `TaskCommands#perform` → `Command#start` → `PTY.spawn` executing `shipit.yml` sourced from the attacker's ref/branch. This is repeatable per reopen event and scoped to any repository misconfigured this way (not to a single tenant, but to whichever repos use this combination). This matches the Critical category: RCE on the deploy host via `Command`/`PTY.spawn` triggered by an unauthorized action.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label` — a specific but plausible admin configuration (explicitly disabling review stacks while retaining a label-based provisioning policy, e.g., during a rollback or partial disablement). The attacker needs only PR authoring rights (their own PR) and the ability to remove/never-add a label and reopen the PR — all actions available to any unprivileged contributor to their own PR. No secrets, sessions, or tokens are needed. This is a low-cost, fully repeatable action.

### Recommendation
Fix operator precedence explicitly in `ReopenedHandler#unarchive?` (and audit `OpenedHandler#provision?` similarly) by parenthesizing the entire behavior-based disjunction and ANDing it with `review_stacks_enabled`, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to `OpenedHandler#provision?`. `UnlabeledHandler`/`LabeledHandler` do not need this fix since their gating is already structurally correct.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
1. Create a `Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: :prevent_with_label`.
2. Build/stub a `params` payload with `action: "reopened"`, `pull_request.labels: []` (no provisioning label), pointing at that repository's `full_name`.
3. Assert: `assert_no_enqueued_jobs`/`Shipit::ReviewStackProvisioningQueue.expects(:add).never` before invoking `ReopenedHandler.new(params).process`.
4. Run the handler; current code will call `stack.unarchive!`/`create!`, which invokes `ReviewStackProvisioningQueue.add` — the `.never` expectation fails, proving `repository.review_stacks_enabled == false` does not equal the actual gate applied (`unarchive?` still returns `true`).
5. As a control, assert `ReopenedHandler.new(params).send(:unarchive?)` returns `true` even though `repository.review_stacks_enabled` is `false`, directly demonstrating the equality violation `review_stacks_enabled == gate_applied` is false.
