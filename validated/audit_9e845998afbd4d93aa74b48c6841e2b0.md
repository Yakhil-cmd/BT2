### Title
AA payment to a batch of addresses of a `spender_attested` asset can be permanently DoS'd by a single unattested recipient - ([File: validation.js])

### Summary
The Y2K Carousel bug lets any user register a "poisoned" receiver address in a shared queue; when the batch-processing loop reaches it, the whole batch transaction reverts, permanently freezing every other participant queued behind it. In `ocore`, the analogous root cause exists in `validatePaymentInputsAndOutputs`, which validates a `spender_attested` asset's payment message: it requires that **every** output address in the message be attested, or the entire message (and therefore the whole unit) fails validation. Because an AA composes and sends all pending payouts to multiple addresses inside a single payment message (`aa_composer.js`, `mergeMessagesAndOutputs` / `sendUnit`), a single output address that has not been (or can no longer be) attested by the required attestor is enough to bounce the whole unit — reverting all AA state changes for that trigger, including any bookkeeping meant to remove the poisoned entry from a persistent payout queue. If the poisoned entry is not removed on bounce (state changes are rolled back together with the failed payment), the AA can become stuck retrying the same batch forever, freezing funds owed to unrelated, honest users.

### Finding Description
`validatePaymentInputsAndOutputs` enforces, for `spender_attested` assets:
```javascript
if (!objAsset.spender_attested)
    return cb();
storage.filterAttestedAddresses(
    conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses,
    function(arrAttestedOutputAddresses){
        if (arrAttestedOutputAddresses.length !== arrOutputAddresses.length)
            return cb("some output addresses are not attested");
        cb();
    }
);
``` [1](#0-0) 

This check is applied to the **whole set of output addresses of the payment message** — if even one address among many outputs is not attested, the entire message (and the entire unit, since a unit is atomic) is rejected with `"some output addresses are not attested"`. There is no per-output skip/partial-success behavior.

An AA that batches multiple recipients' payouts of a `spender_attested` asset into a single `payment` message (as is idiomatic in `oscript`, and as done internally by `mergeMessagesAndOutputs`) will have all its outputs merged into one message per asset: [2](#0-1) 

When `sendUnit` builds and validates this merged unit via `validateAndSaveUnit`, a single unattested recipient address anywhere in the merged output list causes the entire unit to fail, triggering `bounce(err)`: [3](#0-2) 

Because AA state changes (including var updates like removing an item from a "processed" queue, or decrementing a counter) are applied only on success (`addResponse`) and discarded on bounce, any queue-processing/state logic designed to advance past the poisoned address never executes — the AA is left in the same state it was before the attempt, so it will fail identically the next time it tries to flush the same batch, unless AA logic explicitly special-cases and skips bad recipients (which `oscript`/`aa_composer` do not provide primitives for at the payment-message level).

This mirrors the reported class of bug precisely: a single attacker-controlled, permission-gated recipient address embedded in a batch/queue can deadlock processing for all other participants sharing that batch.

### Impact Explanation
Any AA design that (a) accepts self-registered addresses from untrusted users into a persistent queue/array state var, and (b) later pays out a `spender_attested` asset to all queued addresses in one message, is vulnerable to permanent fund freezing for every other legitimate participant in that batch, once a malicious participant registers an address that is not (or is no longer) attested for that asset. This is High severity: it results in AA fund loss/freezing (fund stuck), matching the accepted-impact criteria (AA fund loss or freezing) in the validation rules.

### Likelihood Explanation
Likelihood is Medium-High for AAs that implement shared queues/batches paying an attested asset: an unprivileged AA-trigger sender only needs to (1) get itself registered into the shared batch with an address the asset's current attestor set will not attest (attestor lists can also change over time via `asset_attestors` updates, meaning even a previously-attested address can become unattested later, `storage.js` `addAttestors`/`asset_attestors` table), and (2) trigger the batch flush. No special privilege is required; only asset design pattern (shared batched payouts of a `spender_attested` asset) needs to be present, which is a documented/common `oscript` pattern for AAs distributing revenue or rewards.

### Recommendation
- In AA `oscript` design, avoid merging multiple untrusted recipients' outputs of a `spender_attested` (or otherwise conditionally-restricted) asset into a single payment message; instead pay out to one address per unit/trigger cycle so a single bad recipient cannot block others.
- Alternatively, have AA logic validate attestation status of a recipient (via a data feed / oracle or attestation lookup) before enqueueing it, and remove/skip entries whose recipient later becomes unattested, persisting that removal in a way that is not rolled back together with the failed payment attempt (e.g., process removal in a prior, independent trigger/state update rather than in the same atomic unit as the payment).
- Consider adding an oscript/AA primitive or documentation guidance that surfaces per-output validation failures (e.g., "which output failed attestation") so bounced units can be diagnosed, and encourage AA authors to design payout queues with an admin/self-service mechanism to evict a poisoned entry without requiring the entire batch to validate successfully first.

### Proof of Concept
1. Attestor A creates a `spender_attested` asset `X` with `attestors: [A]`, `is_transferrable: true`. [4](#0-3) 
2. Deploy a "reward pool" AA that lets any trigger sender register `trigger.address` into a state array/queue (e.g., `var['queue']`) to receive a share of asset `X` on a later flush trigger.
3. Attacker sends a trigger from address `M`, which is never attested by `A`, registering itself in the queue.
4. Honest users B, C, D also register in the queue with addresses attested by `A`.
5. Someone triggers the "flush" case; the AA's `oscript` builds a single `payment` message with `asset: X` and outputs to `[B, C, D, M]`.
6. During validation, `filterAttestedAddresses` finds `M` is not attested, so `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, and `validatePaymentInputsAndOutputs` returns `"some output addresses are not attested"`. [5](#0-4) 
7. `sendUnit`'s `validateAndSaveUnit` callback receives this error and calls `bounce(err)`, discarding all AA state changes for this trigger. [3](#0-2) 
8. Because state changes (e.g., clearing the queue or marking it flushed) are rolled back with the bounce, `M` remains in the queue; every subsequent flush attempt repeats the same failure, permanently freezing B, C, D's payouts as long as `M` remains unattested.

Note: I was not able to directly inspect a live/example AA `oscript` in this repo that implements exactly this "queue + attested-asset batch payout" pattern (no such sample was found in the indexed `test/samples/*.oscript` files), so this analog is derived from combining the documented behavior of `validatePaymentInputsAndOutputs` (attested asset output checks) with the generic AA batch-payment mechanics in `aa_composer.js`, rather than from an existing shipped AA template. A Devin session with full repository/file access could confirm whether any bundled or commonly-deployed AA templates use this exact pattern.

			const payload = message.payload;

			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}

					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
