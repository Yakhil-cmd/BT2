### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup triggers unauthorized deploys — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with a global `Commit.where(sha: params.sha)` query instead of scoping to the repository named in the verified webhook payload. Any commit row in any stack/repo whose sha happens to match the attacker's sha gets a new `Status` created, which fans out to `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery`, causing unauthorized deploy triggers on unrelated tenants.

### Finding Description
The broken binding is: `payload.dig('repository', 'full_name')` (the repository the attacker proved control of via signature verification) MUST equal `commit.stack.repository.github_repo_name` for every `Commit` the status is applied to — but the code never enforces this.

Path:
1. `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) verifies the HMAC signature via `verify_signature`, which resolves the GitHub App/secret using `repository_owner` from the payload (`app/controllers/shipit/webhooks_controller.rb:24-29,59-62`). This only proves the request is a legitimately signed webhook for the named owner/org — it does not scope which `Commit`/`Stack` rows may be mutated.
2. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler.call(params)` (`app/models/shipit/webhooks.rb:19`).
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) — with **no** filter on `repository_name`/`stack`, unlike the base `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) which every other handler (`PullRequest::*Handler`) explicitly uses via `Repository.from_github_repo_name(repository_name)`.
4. `Commit#create_status_from_github!` → `Status.replicate_from_github!(stack_id, ...)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:19-44`) creates the status against `commit.stack_id` — i.e., whatever stack that colliding-sha commit actually belongs to, not the stack tied to the attacker's named repository.
5. `Status#schedule_continuous_delivery` (`app/models/shipit/status.rb:42-44`) calls `commit.schedule_continuous_delivery`, which if `stack.continuous_deployment?` and `stack.deployable?`, enqueues `ContinuousDeliveryJob.perform_later(stack)` (`app/models/shipit/commit.rb:281-287`).
6. `ContinuousDeliveryJob#perform` → `Stack#trigger_continuous_delivery` → `next_commit_to_deploy` → `deployable_commits(commits).find(&:deployable?)` (`app/models/shipit/stack.rb:210-243`) can now select that colliding commit as deployable and call `trigger_deploy`, all triggered by a single webhook payload naming only one repository.

Existing guards fail to prevent this: `verify_signature` only authenticates that *a* payload came from a given GitHub org's app installation; it says nothing about which `Commit`/`Stack` rows the handler is permitted to touch. The `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`, and does not even require a `repository` block (unlike `PullRequest` handlers), so there is no natural place forcing scoping — and the handler doesn't scope to `stacks` (via `Repository.from_github_repo_name(repository_name)`) the way `Handler#stacks` was designed to allow.

### Impact Explanation
A single crafted/repeated `status` webhook for one attacker-controlled repository can plant a `success` status on `Commit` rows belonging to entirely unrelated stacks/tenants whenever the sha coincides (e.g., identical initial commits, cherry-picks, or any sha collision across repos using the same content). This can cause an unauthorized deploy to be triggered on stacks with `continuous_deployment: true` that the attacker never authenticated against, and can pollute deploy-gating status data on arbitrary other tenants' commits. This is a payload for one repository mutating another repository's `Commit`/`Stack` state and triggering an unauthorized deploy — matching the Critical impact category.

### Likelihood Explanation
Requires: multiple stacks with commits sharing an identical sha (realistic for initial commits from templated scaffolds, or any two repos sharing history/cherry-picked commits), and at least one victim stack has `continuous_deployment: true` with no blocking checks. The attacker only needs to control one repository/webhook endpoint they can legitimately trigger status events for (e.g., their own GitHub repo with the Shipit GitHub App installed, or any CI system posting a `status` event with an attacker-chosen `sha`/`state`) — no Shipit credentials, session, or API token are needed. This is directly repeatable per request since `sha` is fully attacker-controlled.

### Recommendation
Scope `StatusHandler#process` to only update `Commit` rows belonging to the repository named in the verified payload, e.g. filter via `stacks.commits.where(sha: params.sha)` (using the existing `Handler#stacks`/`repository_name` helper) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status webhook only updates commits belonging to the named repository" do
  repo_a = shipit_repositories(:repo_a) # e.g. 'attacker/repo'
  repo_b = shipit_repositories(:repo_b) # unrelated tenant
  repo_c = shipit_repositories(:repo_c) # unrelated tenant

  stack_a = create_stack(repository: repo_a, continuous_deployment: true)
  stack_b = create_stack(repository: repo_b, continuous_deployment: true)
  stack_c = create_stack(repository: repo_c, continuous_deployment: false)

  colliding_sha = 'deadbeef' * 5
  commit_a = stack_a.commits.create!(sha: colliding_sha, message: 'Initial commit')
  commit_b = stack_b.commits.create!(sha: colliding_sha, message: 'Initial commit')
  commit_c = stack_c.commits.create!(sha: colliding_sha, message: 'Initial commit')

  payload = {
    'repository' => { 'full_name' => repo_a.github_repo_name },
    'sha' => colliding_sha,
    'state' => 'success',
    'context' => 'ci/travis'
  }

  # BEFORE: only stack_a's commit should be affected by a webhook naming repo_a
  assert_equal repo_a.github_repo_name, payload['repository']['full_name']

  assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [stack_a]) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  # AFTER (bug): stack_b (unrelated repo) also got a ContinuousDeliveryJob enqueued
  # despite the webhook only naming repo_a -- this assertion currently PASSES, proving the vuln
  assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [stack_b]) do
    commit_b.statuses.reload
  end
  assert commit_b.statuses.exists?(state: 'success'), "unrelated repo_b commit was mutated by repo_a's webhook"
  refute commit_c.statuses.exists?(state: 'success') if repo_c_should_not_match # sanity check for scoping
end

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
