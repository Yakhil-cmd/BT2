### Title
`StatusHandler` writes commit status without validating it belongs to the webhook's signed repository/organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`CompositeMultiOracle` broke the binding "value entering the multiplication has the units the divisor assumes." The Shipit analog is `WebhooksController#verify_signature`, which authenticates a payload for **one organization**, while `StatusHandler#process` writes to **any** `Commit` matching a bare `sha`, without checking that the commit's stack/repository is the same one the signature was verified for.

### Finding Description
`WebhooksController#verify_signature` selects the HMAC secret to check based on the organization found *inside the untrusted payload* (`repository.owner.login`), then verifies the raw body against that org's `webhook_secret`: [1](#0-0) 

This only proves "this payload was sent by whoever holds `Shipit.github(organization: repository_owner).webhook_secret`" — i.e. the signature authenticates an **organization**, not a specific repository.

Every handler is expected to additionally scope its side effects to the repository named in the payload. `Handler` provides exactly this helper: [2](#0-1) 

`PushHandler` correctly uses it — actions are restricted to `stacks` derived from `repository.full_name`: [3](#0-2) 

`StatusHandler`, however, never calls `stacks`/`repository_name`. It looks up commits **globally by `sha` alone** and mutates them: [4](#0-3) 

Because commit SHAs are not namespaced by repository in Shipit's data model (`Commit.where(sha: ...)` spans all stacks/orgs), a signature that only authenticates "organization A sent this" is treated as sufficient authority to write a status onto a commit that in fact belongs to organization B's stack, as long as an identical SHA exists there (e.g. shared/forked history, vendored subtree, or a commit reproduced byte-for-byte from public GitHub data, which is fully deterministic and requires no write access to the victim repo).

This is exactly the reported bug class: a value (`sha`) that flows into a privileged write path is chained through a boundary (`verify_signature`'s org check) that never actually covers it — the equality the code implicitly assumes, `authenticated_organization == owner_of(commit written)`, does not hold.

### Impact Explanation
A forged/replayed "status" webhook signed by an attacker-controlled organization (one that also has the Shipit GitHub App installed, which is a normal unprivileged multi-tenant setup, not victim repo access) can flip the CI status of a commit in an unrelated stack it doesn't own. Since commit checks gate deploy readiness (`@commit.checks.schedule` in `DeploysController#new`) and PR auto-merge/review-stack logic elsewhere in the engine consults commit statuses, this can be used to force an unauthorized deploy or merge decision on a repository the attacker never had write access to — meeting the "unauthorized deploy/merge" Critical impact bar. [5](#0-4) 

### Likelihood Explanation
Requires: (a) the target Shipit instance hosts multiple GitHub orgs/apps (documented multi-tenant config in `config/secrets.development.shopify.yml`), (b) attacker controls at least one of those orgs' repos/webhook delivery, and (c) a matching SHA exists in the victim stack — feasible for forks/mirrors/shared histories or by deterministically reconstructing a public commit. This is a narrower likelihood than a fully generic cross-repo bypass, but the root-cause gap (missing repository scoping in `StatusHandler`, present in `PushHandler`) is concrete and directly analogous to the reported issue.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to `stacks` (derived from `repository_name`) the same way `PushHandler` does, e.g. `Commit.where(sha: params.sha, stack: stacks)`, so a verified organization can only write statuses for commits that belong to its own repository.

### Proof of Concept
1. Attacker operates `org-attacker/repo-x`, onboarded to the same Shipit instance with its own `webhook_secret` (legitimate multi-tenant setup, per `config/secrets.development.shopify.yml`).
2. Attacker reconstructs (or otherwise obtains) a commit whose SHA equals a SHA already tracked in victim stack `org-victim/repo-y` (e.g. shared upstream history).
3. Attacker sends a `status` webhook to `/webhooks`, `X-Github-Event: status`, body `{"sha": "<shared-sha>", "state": "success", "repository": {"owner": {"login": "org-attacker"}}}`, signed with `org-attacker`'s own `webhook_secret`.
4. `WebhooksController#verify_signature` succeeds (correct secret for `org-attacker`).
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, which matches and updates the commit in `org-victim/repo-y`'s stack, even though the signature never authenticated anything about `org-victim`. [4](#0-3)
