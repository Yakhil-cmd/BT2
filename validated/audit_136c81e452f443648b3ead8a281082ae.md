### Title
Rounding of `earned_headers_commission_share` allows systematic over-distribution (bytes inflation) of headers commissions - ([File: headers_commission.js])

### Summary
`validateHeadersCommissionRecipients()` only checks that the individual `earned_headers_commission_share` percentages of a self-declared recipient list sum to exactly 100, but the actual per-recipient payout is computed independently for each recipient with `Math.round(full_amount * share / 100.0)` in `headers_commission.js`. Because each recipient's amount is rounded independently instead of being derived by subtracting already-allocated amounts from a running total, the sum of the rounded per-recipient amounts can exceed (or fall short of) `full_amount`, the actual headers-commission pool available from the parent unit. This is the same bug class as the Sherlock report: a proportional/shares calculation is rounded per-unit without validating that the sum of the rounded parts still matches the total being distributed, breaking the accounting invariant.

### Finding Description
When a child unit collects headers commission from its parent unit(s), the payout is split among `earned_headers_commission_recipients` (or the single author by default). The recipient list and per-recipient share percentages are fully attacker-controlled fields of the unit that the attacker posts: [1](#0-0) 

The actual distribution is computed as: [2](#0-1) 
and, for units already parsed once with rows from SQL, again as: [3](#0-2) 

Both computations round each recipient's share independently with `Math.round(full_amount * share / 100.0)`. Validation only enforces `total_earned_headers_commission_share === 100` (i.e. the *declared percentages* sum to 100), never that the *resulting rounded byte amounts* sum to `full_amount`. Because `Math.round` in JavaScript rounds `.5` up, an attacker who splits the recipients such that each recipient's fractional share lands near `.5` can make every recipient round *up*, so the sum of amounts credited into `headers_commission_contributions`/`headers_commission_outputs` exceeds the real commission pool taken from the parent unit's `headers_commission` field. For example, with two recipients at 50%/50% and an odd `full_amount` (e.g. 5), each recipient's raw share is `2.5`, which `Math.round` turns into `3` for both, crediting `6` total from a pool of `5` – one extra byte minted out of thin air. With more recipients (there is no explicit maximum length enforced on the `earned_headers_commission_recipients` array), the aggregate over-rounding can be made larger, since the maximum possible overshoot scales with the number of recipients.

This is directly analogous to the reported Surge `Pool.repay()` issue: a derived, rounded quantity (rounded shares / rounded per-recipient commission) is applied to update balances/state without any check that the sum of rounded parts is consistent with the un-rounded total being spent/credited, so value can be lost or created purely from arithmetic rounding.

### Impact Explanation
Headers-commission outputs feed directly into `headers_commission_outputs`, which are spendable bytes inputs validated in `validation.js` (`"headers_commission"` input type). If the sum of rounded recipient amounts systematically exceeds the actual commission taken from parent units, the protocol is minting extra bytes not backed by any burned/committed fee — a form of unauthorized bytes supply inflation. Because the computation is deterministic and run identically by every node (both the in-RAM fast path and the SQL fallback path are supposed to match, per the `_.isEqual` cross-checks), this does not directly cause consensus disagreement, but it does let an attacker who repeatedly posts multi-recipient units with carefully skewed shares extract more spendable bytes commission than they are entitled to over time, at the cost of the network's overall byte-supply integrity.

### Likelihood Explanation
Both `earned_headers_commission_recipients` (addresses and per-address percentage shares) and, to a significant extent, the general magnitude of `headers_commission` earned by units the attacker authors, are under attacker control. An attacker only needs to author units (optionally multi-authored, or simply supply `earned_headers_commission_recipients` even as a way to route funds to owned addresses) with share splits chosen so that `Math.round(full_amount * share/100)` rounds up for every recipient. This requires no special privilege beyond being an ordinary unit poster and repeating the pattern across many units to accumulate the rounding surplus, making the likelihood realistic though the gain per unit is small (bounded by roughly `recipients/2` bytes per distribution event).

### Recommendation
Do not round each recipient's commission independently. Instead, accumulate amounts using a running remainder so the sum of distributed amounts is guaranteed to equal `full_amount` exactly — e.g., process recipients in a fixed (already-required, sorted) order, track `remaining_amount = full_amount`, compute each recipient's amount as `Math.round(remaining_amount * share / remaining_share)`, then subtract the awarded amount and the awarded share from the running totals before processing the next recipient (largest-remainder / cascading rounding). Apply this fix consistently to both the in-RAM (`assocChildrenInfosRAM`/`arrValuesRAM`) and SQL-based code paths in `headers_commission.js`, and add a cross-check (already present as a `_.isEqual` sanity check between the two code paths) that also asserts `sum(recipient_amounts) === full_amount` before inserting into `headers_commission_contributions`.

### Proof of Concept
1. Attacker authors (or co-authors) a unit `U` and sets:
```
earned_headers_commission_recipients: [
  { address: A, earned_headers_commission_share: 50 },
  { address: B, earned_headers_commission_share: 50 }
]
```
This passes `validateHeadersCommissionRecipients` because `50 + 50 === 100`.
2. `U` becomes the winning child unit of a parent unit `P` whose `headers_commission` (the pool being distributed) happens to be an odd integer, e.g. `5` bytes (attacker can influence unit sizes/timing over repeated attempts to hit favorable values, or simply repeat the attack across many units until an odd `full_amount` occurs).
3. In `headers_commission.js` at [4](#0-3) , for each recipient:
   - `Math.round(5 * 50 / 100) = Math.round(2.5) = 3` for address `A`
   - `Math.round(5 * 50 / 100) = Math.round(2.5) = 3` for address `B`
4. Total credited into `headers_commission_contributions` (and subsequently `headers_commission_outputs`) is `3 + 3 = 6`, exceeding the actual `5`-byte commission pool taken from `P` — one byte has been created without being backed by any burn/fee, and can be spent by `A` and `B` as normal `headers_commission` inputs per `validation.js`'s `"headers_commission"` input handling [5](#0-4) .

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
