## Title
Concurrent private-payment chains processed without serialization allow double-acceptance of the same private output - ([File: network.js])

### Summary
`handleSavedPrivatePayments` in `network.js` processes multiple queued private-payment chains **in parallel**, each on its own DB connection/transaction, guarded only by an outer `mutex.lockOrSkip/lock(["saved_private"])` that is released before the per-row work even starts being awaited concurrently. Each chain's acceptance decision (its "is this output already spent/duplicate" check) is a check-then-act sequence performed on an independent, uncommitted transaction, mirroring the smq CVE pattern where a predicate (`e->allocated`) is evaluated outside the lock that protects the subsequent destructive/state-changing operation. [1](#0-0) 

### Finding Description
`handleSavedPrivatePayments` selects all rows from `unhandled_private_payments` and runs `async.each` (explicitly commented "handle different chains in parallel") over them, calling `validateAndSave()` for every chain without any shared mutual exclusion keyed on the underlying spent output: [2](#0-1) 

Each chain's `validateAndSave` invokes `privatePayment.validateAndSavePrivatePaymentChain`, which opens its **own** `db.takeConnectionFromPool()` connection and its **own** `BEGIN`/`COMMIT` transaction per chain, then performs a "check if duplicate" `SELECT` against the `outputs` table to decide whether this exact output was already received: [3](#0-2) 

If the row is not found to be a duplicate, control proceeds to `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)`, which — still inside the *same, independent* transaction — issues the mutating `INSERT`/`UPDATE` sequence that marks the source output as spent, guarded only by a `WHERE ... AND is_spent=0` clause with **no check of the affected row count**: [4](#0-3) 

Because each of the concurrently-running chains uses an independent connection/transaction and the "is this already claimed/duplicate" predicate (private_payment.js's duplicate check, and `checkForDoublespends`/`checkInputDoubleSpend` in `validation.js`) is evaluated against not-yet-committed state from sibling transactions, two chains that both try to consume the same private output (e.g. the same textcoin/private payment claimed twice, or resent to two different peers/hubs) can both pass their "not a duplicate" check before either commits — exactly the check-then-act race described in the smq CVE, where the allocation predicate was read outside the lock that serializes the actual state mutation: [5](#0-4) 

Since the terminal `UPDATE outputs SET ... WHERE ... AND is_spent=0` silently no-ops when a competing transaction already consumed the row (no row-count check, no error path), the losing transaction still reaches `callbacks.ifOk()` and is treated as a **successfully validated and saved** private payment, even though its output was never actually marked spent for it.

### Impact Explanation
This allows a party controlling (or resending) a private payment chain to have the *same* private output accepted as valid by two independent recipients/instances of the node concurrently — a double-spend of private funds that the code otherwise guards against only in the serial, non-concurrent case. This maps directly to the "concrete unauthorized spending / double-spend" impact class required by the report's validation rules.

### Likelihood Explanation
Reachable purely via the private-payment counterparty message path (`handleSavedPrivatePayments`/`unhandled_private_payments`), which is explicitly listed as an allowed unprivileged trigger surface. No privileged/hub/node compromise is required — an attacker only needs to cause the same private chain (or two conflicting chains sharing a source output) to be queued and processed concurrently, which `async.each` in `network.js` makes structurally possible by design.

### Recommendation
Serialize the check-then-act sequence (duplicate/double-spend check + the subsequent write that marks the output spent) for a given source output across concurrently processing chains — e.g. take a `mutex.lock` keyed by `src_unit/src_message_index/src_output_index` (or asset) before evaluating "is duplicate"/`checkForDoublespends`, and hold it until the corresponding `INSERT`/`UPDATE` commits, analogous to moving smq's `e->allocated` check inside `mq->lock`. Additionally, check the affected-row count of the `UPDATE outputs ... WHERE is_spent=0` and treat 0 rows affected as a failure (`ifError`), not `ifOk`.

### Proof of Concept
1. Attacker (or two colluding/cloned wallets) posts the same private-payment chain (same `src_unit`/`message_index`/`output_index`) to the node twice in quick succession, e.g. via two peers/hub deliveries so both land in `unhandled_private_payments` before either is processed.
2. `handleSavedPrivatePayments` fires and `async.each` starts processing both rows concurrently, each opening its own connection/transaction.
3. Both transactions run the "check if duplicate" `SELECT` in `private_payment.js` and both see the output row as not-yet-claimed (neither has committed).
4. Both proceed into `validateAndSavePrivatePaymentChain`; both run their `INSERT ... IGNORE` and `UPDATE outputs SET is_spent=1 ... WHERE is_spent=0`. Depending on transaction interleaving/isolation, one update applies; the other affects 0 rows but is not checked.
5. Both `transaction_callbacks.ifOk()` fire and `COMMIT`; both callers receive `ifOk()` and treat the private payment as accepted — the same output has now been "spent" to two recipients.
