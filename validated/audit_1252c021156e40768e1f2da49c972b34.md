### Title
`transfer_ownership` in pallet-nfts/pallet-uniques silently accepts partial deposit repatriation, desynchronizing the recorded owner deposit from what is actually reserved - ([File: substrate/frame/nfts/src/features/transfer.rs])

### Summary
`Pallet::do_transfer_ownership` in `pallet-nfts` (and the equivalent `transfer_ownership` extrinsic in `pallet-uniques`) calls `T::Currency::repatriate_reserved(&details.owner, &new_owner, details.owner_deposit, Reserved)?` but discards the `Ok(remaining_balance)` returned by `repatriate_reserved`. `repatriate_reserved` is a best-effort/`Polite`-fortitude operation: if the current owner has a lock/freeze overlapping their free balance, only part of the reserved deposit is actually moved, and the function still returns `Ok(remainder)` rather than an error. Because the code never checks that `remainder == 0`, ownership is transferred as if the full `owner_deposit` had moved to `new_owner`, even though it may not have.

### Finding Description
`repatriate_reserved` (defined in `substrate/frame/balances/src/lib.rs:1258-1325` as `do_transfer_reserved`, exposed via `impl_currency.rs:725-734`) moves reserved balance from `slashed` to `beneficiary` on a `BestEffort`/`Polite` basis and returns `Ok(value.saturating_sub(actual))` — i.e., it reports the *unmoved* remainder as a success value, not an error, whenever a freeze/lock blocks the full move.

`pallet-nfts`'s `do_transfer_ownership` (`substrate/frame/nfts/src/features/transfer.rs:124-162`) and `do_force_collection_owner` (same file, lines 197-234), and `pallet-uniques`'s `transfer_ownership` (`substrate/frame/uniques/src/lib.rs:868-905`), all invoke `repatriate_reserved` purely with `?`, which only propagates `Err`, and throw away the `Ok(remaining)` value:
```rust
T::Currency::repatriate_reserved(
    &details.owner,
    &new_owner,
    details.owner_deposit, // or details.total_deposit
    Reserved,
)?;
```
No check is performed that `remaining.is_zero()`. Afterward the collection record is updated to make `new_owner` the owner while `owner_deposit`/`total_deposit` (the bookkeeping value used later for full unreserve on `do_destroy_collection`, see `substrate/frame/nfts/src/features/create_delete_collection.rs:140`: `T::Currency::unreserve(&collection_details.owner, collection_details.owner_deposit)`) is left unchanged, assuming the full deposit now sits reserved under `new_owner`.

This is precisely the same bug class that was already identified and fixed in `pallet-assets`'s `transfer_ownership` (see `prdoc/pr_12366.prdoc` and the current `substrate/frame/assets/src/lib.rs:1343-1347`, which now captures the remainder and rejects the dispatch with `Error::IncompleteDepositTransfer` if it is non-zero). `pallet-nfts` and `pallet-uniques` still contain the pre-fix pattern. ### Impact Explanation
A collection owner can lock/freeze part of their own free balance (e.g. via `pallet-balances::set_lock`/an existing vesting or staking lock any signed user can create on themselves) so that `reducible_total_balance_on_hold` used by `do_transfer_reserved` (`substrate/frame/balances/src/lib.rs:1270-1277`) is less than `owner_deposit`. Calling `transfer_ownership` to an accepting `new_owner` then only partially repatriates the reserved deposit, but the extrinsic still succeeds and `CollectionDetails.owner_deposit`/`total_deposit` is left recording the *full* original amount, now attributed to `new_owner`. When the collection is later destroyed (by `new_owner` or a permitted caller), `do_destroy_collection` unreserves `collection_details.owner_deposit` from the (new) owner's account (`create_delete_collection.rs:140`), attempting to unreserve more than is actually reserved under `new_owner`, or — depending on unreserve's saturating behavior — silently under-releasing/over-crediting balance state, breaking the deposit accounting invariant. The prior owner keeps some balance locked/reserved that should have moved, and downstream accounting (deposit tracked in storage vs. actually reserved on-chain) desynchronizes, mirroring the exact failure mode Parity fixed for `pallet-assets` in pr_12366.

### Likelihood Explanation
The prerequisite (placing a lock/freeze on one's own account before calling a permissionless, self-service extrinsic `transfer_ownership`/`do_force_collection_owner`) requires no privileged role — any signed collection owner can set a freeze/lock on themselves via existing balance mechanisms and then call `transfer_ownership`, which only requires the `new_owner` to have called `set_accept_ownership`. This is a normal, unprivileged extrinsic path, and the underlying `Polite`/best-effort semantics of `repatriate_reserved` are documented, well-understood behavior — the same root cause was already exploited/caught for `pallet-assets`.

### Recommendation
Apply the same fix used for `pallet-assets` (pr_12366) to `pallet-nfts::do_transfer_ownership`, `pallet-nfts::do_force_collection_owner`, and `pallet-uniques::transfer_ownership`: capture the `Balance` returned by `repatriate_reserved` and `ensure!(remaining.is_zero(), Error::<T, I>::IncompleteDepositTransfer)` before mutating collection ownership, rolling back the storage mutation on partial transfer.

### Proof of Concept
No local Rust/FRAME integration test was executed in this session; only static code inspection was performed and cited above (unlike the original external Solidity report, the exact same discard-the-remainder pattern was located and confirmed present, unfixed, in `pallet-nfts` and `pallet-uniques`, while the historical `pallet-assets` instance of this exact pattern is confirmed fixed via `prdoc/pr_12366.prdoc`). A reproduction would require: (1) a runtime with `pallet-nfts` (or `pallet-uniques`) and `pallet-balances`, (2) an account `A` creating a collection (reserving `owner_deposit`), (3) `A` placing a lock/freeze on part of its free balance so that `reducible_total_balance_on_hold(A, Polite) < owner_deposit`, (4) account `B` calling `set_accept_ownership(collection)`, (5) `A` calling `transfer_ownership(collection, B)` and observing it succeeds (`Ok`) despite `repatriate_reserved` returning a non-zero remainder, followed by (6) inspecting `Collection::<T,I>::get(collection).owner_deposit` vs. actual reserved balance under `B` to show the mismatch. This was not executed against a live test harness in this session; findings rest on source-level tracing of `do_transfer_reserved`'s best-effort semantics and the unguarded `?` call sites.

		pub(crate) fn do_transfer_reserved(
			slashed: &T::AccountId,
			beneficiary: &T::AccountId,
			value: T::Balance,
			precision: Precision,
			fortitude: Fortitude,
			status: Status,
		) -> Result<T::Balance, DispatchError> {
			if value.is_zero() {
				return Ok(Zero::zero());
			}

			let max = <Self as fungible::InspectHold<_>>::reducible_total_balance_on_hold(
				slashed, fortitude,
			);
			let actual = match precision {
				Precision::BestEffort => value.min(max),
				Precision::Exact => value,
			};
			ensure!(actual <= max, TokenError::FundsUnavailable);
			if slashed == beneficiary {
				return match status {
					Status::Free => Ok(actual.saturating_sub(Self::unreserve(slashed, actual))),
					Status::Reserved => Ok(actual),
				};
			}

			let ((_, maybe_dust_1), maybe_dust_2) = Self::try_mutate_account(
				beneficiary,
				false,
				|to_account, is_new| -> Result<((), Option<T::Balance>), DispatchError> {
					ensure!(!is_new, Error::<T, I>::DeadAccount);
					Self::try_mutate_account(slashed, false, |from_account, _| -> DispatchResult {
						match status {
							Status::Free => {
								to_account.free = to_account
									.free
									.checked_add(&actual)
									.ok_or(ArithmeticError::Overflow)?
							},
							Status::Reserved => {
								to_account.reserved = to_account
									.reserved
									.checked_add(&actual)
									.ok_or(ArithmeticError::Overflow)?
							},
						}
						from_account.reserved.saturating_reduce(actual);
						Ok(())
					})
				},
			)?;

			if let Some(dust) = maybe_dust_1 {
				<Self as fungible::Unbalanced<_>>::handle_raw_dust(dust);
			}
			if let Some(dust) = maybe_dust_2 {
				<Self as fungible::Unbalanced<_>>::handle_raw_dust(dust);
			}

			Self::deposit_event(Event::ReserveRepatriated {
				from: slashed.clone(),
				to: beneficiary.clone(),
				amount: actual,
				destination_status: status,
			});
			Ok(actual)
		}
