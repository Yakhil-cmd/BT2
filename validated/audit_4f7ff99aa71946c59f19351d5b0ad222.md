### Title
Untrusted swap route executes attacker-controlled pool code under the caller’s authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
High. `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque route bytes and execute them through the configured router inside a transaction authorized by the account caller. A route can name an attacker-controlled pool; that pool can request additional authorization from the caller, such as transferring unrelated wallet tokens. Transaction simulation records the malicious transfer as a child authorization, and the theft succeeds if the caller signs the poisoned tree.

### Finding Description
The controller authenticates `caller` at the strategy root, then verifies that the caller owns or delegates the target account. `swap_collateral` accepts attacker-influenced `swap` bytes without interpreting their destination venues. It withdraws collateral into controller custody and calls `swap_tokens_or_passthrough` with that route.

`swap_tokens` forwards the opaque bytes to the configured aggregator. The controller tightly constrains only its own token transfer—one exact input-token `transfer` from the controller to the router—and then checks input spend and positive output receipt. Those checks do not constrain other code reached by the route. [1](#0-0) 

The router decodes pool and token addresses from the route’s address registry, and each `Swap` instruction dispatches the supplied `pool` to a venue adapter. [2](#0-1)  For example, the Soroswap adapter invokes `get_reserves` and `swap` on the supplied pool address without checking a pool allowlist. [3](#0-2) 

Because this all occurs below the caller’s authorized controller invocation, malicious pool code can invoke `token.transfer(caller, attacker, amount)` on an unrelated token held by the caller. Honest simulation records that call as a child of the caller’s authorization tree; the host executes it if the caller signs that tree. The repository’s harness demonstrates this behavior: recording mode places the malicious wallet-token transfer beneath `swap_collateral`, and enforcing mode succeeds when that child is signed. [4](#0-3) 

### Impact Explanation
A malicious route can steal tokens unrelated to the lending position and outside the routed `amount_in`. The controller’s balance-delta checks, router minimum-output check, and post-strategy solvency check only bound the controller/router swap legs; they do not bound a nested transfer charged to the caller’s wallet. [5](#0-4) 

The demonstrated loss is the caller’s entire balance of an unrelated token while the lending strategy still completes successfully and deposits fair swap output. [6](#0-5) 

### Likelihood Explanation
An unprivileged attacker can deploy a contract exposing the expected venue functions and encode it as a route hop. The malicious pool can return enough output to satisfy the route minimum and controller output check while also attempting an unrelated caller-token transfer.

Execution requires the victim to sign the authorization tree containing the extra transfer. An honest client that rejects unexpected child authorization prevents the theft, but the route bytes are opaque to the controller and do not themselves establish that no unauthorized child call will be requested. The documented authorization model explicitly expects clients to detect and reject such poisoned trees. [7](#0-6) 

### Recommendation
Do not execute unallowlisted route-selected pool contracts beneath a caller-authorized lending operation.

- Maintain a governance-approved pool/venue registry and reject route instructions whose resolved `pool` is not approved.
- Alternatively, split route execution into an authorization boundary that cannot request the lending caller’s authorization, rather than relying on users or clients to inspect nested authorization trees.
- Until routes are allowlisted, wallets and integrators should decode every simulated authorization tree and reject any controller strategy containing children other than the expected input transfer.

### Proof of Concept
1. Deploy `RoguePool` with `get_reserves()` and `swap(amount_0_out, amount_1_out, to)` functions compatible with the Soroswap adapter.
2. Configure `RoguePool.swap` to:
   - call `token::Client::new(victim_token).transfer(victim, attacker, victim_balance)`;
   - transfer a positive amount of the expected output token to the router.
3. Encode a `StrategyPayload` whose `assets` include the input token, output token, and `RoguePool`; encode one `Swap(Soroswap)` instruction whose pool index resolves to `RoguePool`.
4. Have the victim invoke:

```text
swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = USDC_hub_asset,
    amount = supplied_usdc_amount,
    new = ETH_hub_asset,
    swap = malicious_payload
)
```

5. Simulation records `victim_token.transfer(victim, attacker, victim_balance)` as a child authorization under the victim’s `swap_collateral` invocation.
6. If the victim signs the returned authorization tree, the rogue pool transfer succeeds, the router’s measured output remains positive, the account’s final risk checks pass, and the unrelated wallet token is transferred to the attacker.

```rust
pub(crate) fn swap(ctx: &HopContext<'_>) {
    let token_in_is_0 = ctx.hop.token_in < ctx.hop.token_out;

    let no_args: Vec<Val> = vec![ctx.env];
    let (reserve_0, reserve_1): (i128, i128) = ctx.env.invoke_contract(
        &ctx.hop.pool,
        &Symbol::new(ctx.env, "get_reserves"),
        no_args,
    );
    let (reserve_in, reserve_out) = if token_in_is_0 {
        (reserve_0, reserve_1)
    } else {
        (reserve_1, reserve_0)
    };

    let requested_out = soroswap_amount_out(ctx.env, ctx.amount_in, reserve_in, reserve_out);
    if requested_out <= 0 {
        panic_with_error!(ctx.env, Error::ZeroOutput);
    }

    let token_client = token::Client::new(ctx.env, &ctx.hop.token_in);
    token_client.transfer(ctx.router, &ctx.hop.pool, &ctx.amount_in);

    let (amount_0_out, amount_1_out) = if token_in_is_0 {
        (0_i128, requested_out)
    } else {
        (requested_out, 0_i128)
    };

        ctx.env,
        amount_0_out.into_val(ctx.env),
        amount_1_out.into_val(ctx.env),
        ctx.router.into_val(ctx.env),
    ];

        .env
        .invoke_contract(&ctx.hop.pool, &symbol_short!("swap"), args);
```

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

        .expect("recording mode accepts the route");

    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

        sub_invocations: std::vec![stolen_transfer],
```

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
