### Title
Check-suite webhook payload allows repository-owner/full_name mismatch, enabling cross-repository check-run refresh scheduling - ([File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the signing secret from `payload.dig('repository','owner','login')` [1](#0-0)  only, while `Handler#stacks`/`Handler#repository_name` resolve the target `Repository` from `payload.dig('repository','full_name')` [2](#0-1) . Nothing enforces that `repository.full_name` and `repository.owner.login` in the same JSON payload actually refer to the same repository, so a webhook validly signed with an attacker-controlled org's secret can still name a victim's `full_name` and cause `CheckSuiteHandler#process` to schedule `RefreshCheckRunsJob`/`schedule_refresh_check_runs!` against a victim's commit [3](#0-2) .

### Finding Description
Binding claimed: `repository_owner` (used by `verify_signature` to pick the `GithubApp`/secret) == `repository_name`'s owner (used by `stacks`/`Repository.from_github_repo_name` to select the tenant whose commit gets scheduled). In code these are two independent reads of the same JSON object:

- `repository_owner` = `params.dig('repository','owner','login')` [1](#0-0) 
- `repository_name` = `payload.dig('repository','full_name')` [4](#0-3) 

`verify_signature` only checks that the raw POST body's HMAC matches the secret configured for the organization named by `owner.login` [5](#0-4) ; HMAC verification says nothing about the semantic content of the body, including whether `full_name`'s owner segment matches `owner.login`. `CheckSuiteHandler`'s `ExplicitParameters` schema only requires `check_suite.head_sha`/`head_branch` and never requires or validates `repository.full_name` against `repository.owner.login` [6](#0-5) .

Exploit flow: an attacker who administers (or has configured the Shipit GitHub App/webhook for) their own organization `attacker-org` knows the webhook secret Shipit uses for that org. They POST to `/webhooks` with header `X-Github-Event: check_suite`, a body whose `repository.owner.login = "attacker-org"` and `repository.full_name = "victim/repo"`, and `check_suite.head_branch`/`head_sha` matching a real branch/commit of the victim's stack, signed with `attacker-org`'s secret. `verify_signature` passes because it only checks the signature against `attacker-org`'s secret [5](#0-4) . `CheckSuiteHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim/repo")` [7](#0-6)  and schedules `RefreshCheckRunsJob` against the victim's commit [8](#0-7) , which then calls `Commit#refresh_check_runs!`/`Stack#commits...refresh_check_runs!` [9](#0-8)  on the victim's tenant data, using data supplied by an unrelated, attacker-signed request.

The provenance claim in the question ("both fields derive from the same signed payload subtree, so binding holds") does **not** hold: HMAC signing only guarantees the bytes weren't tampered with in transit — it guarantees nothing about internal cross-field consistency of attacker-authored JSON that they themselves construct and sign with their own known secret.

### Impact Explanation
This is a cross-repository task-scheduling primitive: a webhook signed for one tenant (`attacker-org`) triggers a job resolved and executed against another tenant's (`victim`) `Stack`/`Commit` records, matching the Critical category "a payload for one repository mutating another's stack, commit, task". The scheduled job itself only re-fetches check-run status from GitHub using the victim's own configured GitHub App credentials (not a credential leak), but it is an unauthorized, attacker-triggered mutation/refresh of victim state, repeatable at will against any repository/stack whose `full_name` the attacker can guess, as long as the attacker knows any one org's webhook secret registered with Shipit.

### Likelihood Explanation
Preconditions: attacker must know (or control) the webhook secret Shipit uses for at least one org they administer (`Shipit.github(organization:)` config), which is plausible since org admins typically configure/know their own webhook secret when wiring up GitHub → Shipit. Attacker must know the victim's exact `full_name`, target `branch`, and a `head_sha` corresponding to an existing commit tracked by the victim's stack (all typically public/discoverable via GitHub for public repos). No Shipit session, API token, or GitHub App private key is needed. This is directly reachable via `POST /webhooks` with attacker-controlled headers and body, repeatable without rate limiting concerns being in scope.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler`, validate that `repository.full_name`'s owner segment matches `repository.owner.login` (or, better, derive `repository_owner` from `full_name` split, and derive the target repository/stack lookup from the same verified owner) before processing any handler. Reject payloads where these are inconsistent.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest sketch)
test ":check_suite with mismatched owner/full_name does not schedule refresh for victim stack" do
  victim_stack = shipit_stacks(:shipit) # owner: 'shopify', name: 'shipit-engine' e.g.
  victim_commit = shipit_commits(:first)

  body = {
    repository: { owner: { login: 'attacker-org' }, full_name: victim_stack.github_repo_name },
    check_suite: { head_sha: victim_commit.sha, head_branch: victim_stack.branch }
  }.to_json

  @request.headers['X-Github-Event'] = 'check_suite'
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  assert_no_enqueued_jobs only: RefreshCheckRunsJob do
    post :create, body:, as: :json
  end
end
```
Given the current code, this assertion **fails** (a job IS enqueued), demonstrating the broken binding between `repository_owner` (verification) and `repository_name` (authorization/scoping) in `app/models/shipit/webhooks/handlers/check_suite_handler.rb` and `app/models/shipit/webhooks/handlers/handler.rb`.
