### Title
Overflow during fixed-point interest accrual permanently freezes a high-utilization whale market - ([File: common/src/rates/scaling.rs](https://github.com/Jortegata/rs-lending-xlm--020/blob/master/common/src/rates/scaling.rs))

### Summary
A market whose scaled debt or supply value grows beyond `i128::MAX` can brick all subsequent operations on that market. The permissionless `update_indexes` entrypoint can commit enough index growth to reach that state, after which every later accrual panics before ordinary withdrawals, repayments, liquidations, or parameter replacement can execute.

### Finding Description
The controller exposes `update_indexes` to any authorized caller and forwards the requested `HubAssetKey` batch to the pool. [1](#0-0) 

The pool's `accrue` handler loads each market and invokes `interest::global_sync`. [2](#0-1) 

`global_sync` processes elapsed milliseconds in bounded chunks, but each chunk recomputes the market's unscaled debt and supply through `accrue_step`. [3](#0-2) [4](#0-3) 

`accrue_step` calculates `borrowed * borrow_index` and `supplied * supply_index` via `scaled_to_original`. [5](#0-4)  `scaled_to_original` performs a non-saturating `Ray::mul`, so a product outside `i128` raises `MathOverflow`. [6](#0-5) 

The borrow-index cap is applied only after the multiplication producing the new index, and it does not bound the separate scaled-position-times-index product used for utilization and reward calculation. [7](#0-6)  Consequently, the stored index can remain below `MAX_BORROW_INDEX_RAY` while `borrowed * borrow_index` or `supplied * supply_index` overflows.

Every pool operation loads an interest-synchronized market through `synced_market`, so the same overflow is encountered before subsequent withdraw, repay, liquidation, or other market mutations can proceed. [8](#0-7)  The repository's test suite demonstrates the condition: a billion-unit, 18-decimal market at 98% utilization eventually fails `update_indexes` with `MathOverflow`, and subsequent withdraw and repay calls fail with the same error. [9](#0-8) 

### Impact Explanation
This permanently freezes funds in the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot process unhealthy positions, and revenue or rate-model operations that first accrue interest also trap. Since account positions and market state remain recorded but unusable, affected users lose access to collateral and debt-management functionality absent a contract upgrade.

### Likelihood Explanation
Likelihood is constrained by scale and time: triggering the overflow requires a very large scaled position, sustained high utilization, and enough elapsed accrual for the index-value product to exceed the `i128` domain. The demonstrated scenario uses a billion whole 18-decimal units at 98% utilization and market caps configured to permit that size. [10](#0-9)  No privileged action is needed to trigger it once such a state exists: any caller can invoke `update_indexes`, while the underlying state can be established through ordinary `supply` and `borrow`.

### Recommendation
Bound both operands of `scaled_amount * index` before multiplication and propagate the existing index-cap invariant to total market value. Specifically:

- Use a checked/saturating market-value helper in `accrue_step` rather than `scaled_to_original`.
- When the unscaled debt or supply value would exceed `i128::MAX`, clamp the resulting index or market value to the maximum representable value before utilization and reward calculations.
- Enforce a market-level cap on scaled shares times index, not only on the index itself.
- Add regression coverage for `update_indexes`, `withdraw`, `repay`, `liquidate`, and `update_params` after crossing the representable-value boundary.
- Consider a rescue path that can update indexes or parameters without unconditionally executing the overflowing accrual step.

### Proof of Concept
The existing test establishes the vulnerable path:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();

lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// Repeatedly advance time and invoke permissionless index accrual.
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break;
    }
}

// Once the cliff is reached, all accrual-gated exits/repayments fail.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The test asserts that `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, confirming the cap does not prevent the `scaled debt × index` overflow. [11](#0-10)

    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);

    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);

    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(

        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
