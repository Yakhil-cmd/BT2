### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the repository/stack that is written is looked up from the independent, unchecked `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`) of the attacker-supplied JSON body. [1](#0-0) [2](#0-1)  Once the signature check passes, the actual event handlers (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target stacks/commits using `Handler#repository_name`, which reads a *different*, independent field of the same JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing enforces that `repository.owner.login` (the identity cryptographically bound to the signature check) matches the owner encoded in `repository.full_name` (the identity that is actually written to via `Repository.from_github_repo_name`). [4](#0-3) 

### Finding Description
Shipit supports hosting multiple GitHub organizations/apps from a single instance, each with its own `webhook_secret`, as shown in the multi-org secrets fixture. [5](#0-4) 

The verification flow is:
1. `repository_owner` is read straight from the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`). [2](#0-1) 
2. `Shipit.github(organization: repository_owner)` is used to pick the `GithubApp` instance/secret to validate the HMAC signature of the raw body. [1](#0-0) 
3. If the org's `webhook_secret` matches (i.e. attacker knows/controls the secret for *some* org tenant on this instance), the whole request is accepted, and `Shipit::Webhooks.for_event(event)` handlers run with the full, unfiltered `params`. [6](#0-5) 
4. Every handler determines *what gets written* via `Handler#repository_name`, defined as `payload.dig('repository', 'full_name')` - a field completely independent of `repository.owner.login` used in step 1. [7](#0-6) 
5. `Repository.from_github_repo_name` splits this `owner/name` string and looks up the `Repository`/`Stack` to act on. [4](#0-3) 

Because steps 1 and 4 read two different JSON keys of the same attacker-controlled body, an attacker who legitimately controls a GitHub organization tenant "OrgA" configured on the same shared Shipit instance (and therefore knows/owns OrgA's `webhook_secret`) can send a validly-signed webhook (signed with OrgA's secret, `repository.owner.login = "OrgA"`) while setting `repository.full_name = "OrgB/victim-repo"` for a completely different tenant "OrgB" hosted on the same instance. The signature check in `verify_signature` only proves the sender knows OrgA's secret; it proves nothing about OrgB, yet the actual mutation targets OrgB's `Stack`.

This breaks the equality the deployment-trust model is supposed to guarantee:
`organization whose secret authenticated the request == organization/repository actually written to`

Concretely reachable handlers include:
- `PushHandler`, which triggers `stack.sync_github(expected_head_sha:)` for any not-archived stack matching `repository.full_name` + branch. [8](#0-7) 
- `StatusHandler`, which writes a CI `Status` for any `Commit` matching the attacker-chosen `sha`, regardless of which repo it belongs to (status handler doesn't even scope by `stacks`/`repository_name` and is purely `sha`-driven). [9](#0-8) 

### Impact Explanation
This is a cross-tenant/cross-repository write: an attacker who is only a legitimate low-privilege administrator of their own GitHub org/app tenant on a shared Shipit deployment can forge push-sync and CI-status events for a different, victim organization's stacks that they have no authorization over. Faking a `status` event can flip a commit's CI state to `success`, which is used by Shipit to gate whether a commit is deployable/mergeable, and faking a `push` event can force a resync of the victim's stack against an attacker-chosen `expected_head_sha`. This matches the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the attacker to be a legitimate holder of a `webhook_secret` for at least one org configured on the same multi-tenant Shipit instance (a scenario explicitly supported and documented via the multi-org `github:` secrets config), but zero privileges on the victim org/repository. No GitHub App private key, `ApiClient` token, or Shipit session is needed - only knowledge of one's own tenant's webhook secret, which is by design known to that tenant's admin.

### Recommendation
In `Handler#repository_name` (and any handler resolving target stacks/commits), require that `repository.owner.login` (or `organization.login`) equals the owner portion of `repository.full_name` before resolving stacks, or have `WebhooksController#verify_signature` re-derive/validate `repository_name` from the same field used for org selection, rejecting requests where the two disagree.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as supported by `Shipit.github(organization:)` multi-org config). [5](#0-4) 
2. Attacker is a legitimate admin of `OrgA`'s GitHub App and knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success"
   }
   ```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over this exact raw body.
5. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `OrgA`'s `GithubApp`, and successfully verifies the signature. [1](#0-0) 
6. `StatusHandler#process` (or `PushHandler#process`) runs using `repository.full_name = "OrgB/victim-repo"`, mutating `OrgB`'s commit status / triggering a sync on `OrgB`'s stack, despite the attacker having no relationship to `OrgB`. [9](#0-8) [3](#0-2)
