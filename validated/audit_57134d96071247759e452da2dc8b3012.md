### Title
Missing global outpoint tracking in pox-5 L1 BTC lockup verification allows the same Bitcoin lockup output to back multiple bond/stake registrations - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` in pox-5 accepts either an sBTC deposit or a proof that sats are locked in a Bitcoin timelock output (the "L1 lockup" path). The sats amount used to size a staker's bond membership (and thus their signing weight / reward share) is computed by `verify-l1-lockups` / `validate-l1-lockup`, which only deduplicates outpoints *within the single call* via a locally-scoped `seen-outpoints` list, and never records the outpoint in persistent contract state. [1](#0-0) [2](#0-1) 

### Finding Description
The expected P2WSH script for a lockup output is derived from `(staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes)`, where `early-unlock-bytes` comes from the bond record (`(get early-unlock-bytes bond)`), and `staker-unlock-bytes` is attacker/staker-supplied at call time. [3](#0-2)  The only replay protection against reusing the *same* Bitcoin outpoint as proof of a lockup is the `seen-outpoints` accumulator, which is built fresh inside each `verify-l1-lockups` call and discarded afterward — it is never persisted to a contract map keyed by `(txid, output-index)`. [4](#0-3) 

Because a locked Bitcoin UTXO remains unspent and spendable via the same timelock script for as long as it sits on the Bitcoin chain (until `unlock-burn-height` matures and the owner sweeps it), the same real-world BTC lockup can be presented as proof in two separate Stacks transactions: once to register for bond A, and again — after the staker's position in bond A ends (bond ends or the staker unstakes) — to register for bond B, reusing the identical unspent Bitcoin output. `ERR_ALREADY_REGISTERED` only prevents the *same staker from being a member of two bonds concurrently*; it does not prevent sequential reuse of the same L1 proof once the staker has exited their first bond membership. If two bonds happen to share the same `early-unlock-bytes` (plausible since bonds can be created by the same admin using the same early-exit key), or if the staker registers for the same bond a second time in a later cycle after an earlier bond exit, the identical `(header, tx, output-index)` tuple validates successfully every time — the contract's only signal that "this BTC is really locked" is the on-chain BTC proof, and that proof is not consumed/invalidated by a successful registration.

This breaks the equality the PoX-5 L1 mechanism is meant to enforce: *sats credited to bond membership / signing weight == sats genuinely and currently locked on Bitcoin, once*. Reusing the proof lets one real Bitcoin lockup back multiple simultaneous or sequential Stacks-side reward-earning positions.

### Impact Explanation
This matches the "High" impact category: *signing weight or reward slots exceeding locked value*, since the sats amount driving stake/bond sizing (and hence rewards and voting/signing power) can be credited more than once from a single Bitcoin-locked value. It is not simple denial-of-service or griefing — it is a violation of the 1:1 backing invariant between STX-equivalent stake and the underlying locked BTC.

### Likelihood Explanation
Exploiting this requires: (1) locking BTC once under the pox-5 script, (2) registering for a bond with the L1 proof, (3) later exiting that bond (either it ends normally or the staker unstakes) while leaving the BTC output unspent, and (4) re-submitting the same proof for a second bond registration (ideally when `early-unlock-bytes` between bonds coincide, which is plausible under a single bond-admin's operational pattern, or by registering for a later instance of the same bond parameters). No signer, admin, or bond-pause privilege is required — `register-for-bond` is public and callable by any allowlisted staker, and the bug is a pure code-flow gap (no persistent outpoint registry), so likelihood is moderate rather than requiring implausible preconditions.

### Recommendation
Persist consumed L1 lockup outpoints in a durable map (e.g., `used-l1-lockup-outpoints: {txid, output-index} -> bool`) that is checked and set inside `validate-l1-lockup`, independent of any single call's `seen-outpoints` accumulator, so that a given Bitcoin outpoint can only ever back one bond/stake registration for the lifetime of the contract (or until the staker verifiably spends/withdraws the BTC, if a "re-lock" flow is desired, that flow should require a fresh, distinct Bitcoin outpoint).

### Proof of Concept
Note: I was unable to fully trace the `unstake` code path for L1-locked members before the session ended (the final `grep_search` call failed due to a malformed regex and no further tool calls were available), so I cannot cite the exact line(s) confirming that `unstake` does not require proof of BTC-side spend. This is the one uncertain link in the chain — if `unstake` (or bond expiry) *does* somehow invalidate the staker's ability to reuse the exact same outpoint (e.g. by storing a global "outpoint used" flag elsewhere not found by my searches), the analog would not hold. Based on all lockup-verification code found (`register-for-bond`, `verify-l1-lockups`, `validate-l1-lockup`), no such persistent registry exists in `pox-5.clar`, and the described double-registration path is directly supported by the code cited above. A concrete PoC would be:
1. Staker locks `sats` BTC via `construct-lockup-output-script(staker, H, staker-unlock-bytes, early-unlock-bytes-A)` for Bond A.
2. Staker calls `register-for-bond(bond-index=A, ..., btc-lockup=ok([lockup-output]))` — succeeds, staker gains bond A membership and sats-based stake/reward weight.
3. Staker's Bond A position ends (bond winds down) or staker unstakes.
4. A second bond (Bond B) is set up with identical `early-unlock-bytes` (or is the same bond re-registered in a later window).
5. Staker calls `register-for-bond(bond-index=B, ..., btc-lockup=ok([same lockup-output]))` using the *same, still-unspent* BTC UTXO — `validate-l1-lockup` re-derives the same expected script hash, finds the same on-chain output, and credits `sats-total` again, granting a second round of stake/reward weight from BTC that was only ever locked once.
