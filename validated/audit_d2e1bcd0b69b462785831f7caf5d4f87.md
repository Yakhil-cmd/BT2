### Title
Cross-organization status forgery bypasses CI/merge gating due to unscoped commit lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `WebhooksController` verifies an incoming GitHub webhook's HMAC signature using a secret keyed only by the *organization* named in the payload (`repository.owner.login`), but the `StatusHandler` that processes `status` events looks up the target `Commit` purely by `sha`, with **no repository or organization scoping at all**. This breaks the intended binding: *the organization whose secret authenticated the request* ≠ *the repository/commit whose CI status gets written*. An operator/administrator who legitimately controls the webhook secret for any one onboarded GitHub organization can forge a "status" webhook that sets a fabricated CI status (e.g. `success`) on a commit belonging to any other stack/organization hosted on the same Shipit instance, which can satisfy `required_statuses`/`blocking_statuses` gating and enable an unauthorized merge/deploy on a repository they don't control.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using only the organization name taken from the payload itself: [1](#0-0) [2](#0-1) 

This design is correct for GitHub Apps generally (each configured organization has its own `app_id`/`webhook_secret`, see the "Using Multiple GitHub Applications" section of the setup docs), and the HMAC does cover the full raw body — so an attacker cannot tamper with a *real* GitHub-issued webhook. However, anyone who legitimately possesses a valid `webhook_secret` for **any** configured organization (e.g., an admin who set up their own org's GitHub App per the multi-tenant setup flow) can craft an arbitrary, fully self-signed payload, since the secret is the only thing that binds the request — nothing cryptographically ties the `owner.login` used for secret selection to any other field in the same payload beyond "the whole body must hash correctly with that org's secret," which the forger controls entirely.

The `status` event is routed to `StatusHandler`, which processes it like this: [3](#0-2) 

Unlike other handlers, `StatusHandler` never uses the base `Handler#stacks`/`repository_name` scoping helpers: [4](#0-3) 

`Commit.where(sha: params.sha)` performs a **global** lookup across every stack/repository/organization tracked by the Shipit instance. Because commit SHAs are effectively public/guessable (visible on GitHub, in PRs, in build logs, etc.), an attacker who can pass the signature check for their own organization can supply any victim commit's SHA and any `state`/`context`/`description`/`target_url`, and `commit.create_status_from_github!(params)` will persist it as if GitHub itself reported it for that commit — regardless of which repository/organization actually owns that commit.

The test suite documents that this lookup is not repository-scoped: the `:state` webhook test only merges org/repo params for other reasons, and the handler code path itself never checks them: [5](#0-4) 

Commit statuses set this way feed directly into deploy/merge gating logic (`required_statuses`, `blocking_statuses`, `soft_failing_statuses`) defined in `DeploySpec`: [6](#0-5) 

### Impact Explanation
This crosses the trust boundary the report describes as "an organization that authenticated versus the repository that is written": the webhook signature only proves possession of one organization's secret, yet the code writes to *any* commit/stack in the entire multi-tenant Shipit deployment. By forging a passing status (e.g., `state: "success"`, matching a `required` or `blocking` CI context) for a specific commit SHA belonging to a victim organization's stack, an attacker can make that commit appear to have passed CI checks it never actually passed, satisfying the merge queue's status requirements and enabling an unauthorized merge/deploy of code that never passed real CI on a repository/organization the attacker does not own. This matches the "unauthorized deploy, rollback, or merge" High-impact category.

### Likelihood Explanation
Exploitation requires the attacker to hold a valid `webhook_secret` for at least one organization configured in the Shipit instance's `github:` section — plausible in any multi-tenant/self-service deployment (as documented in `docs/setup.md`'s "Using Multiple GitHub Applications" section) where different customer organizations each provision and know their own GitHub App's webhook secret. No repository write access, GitHub App installation on the victim org, or Shipit session/API token is needed; the attacker only needs the target commit's SHA, which is generally public.

### Recommendation
`StatusHandler#process` (and any other handler that doesn't already use `Handler#stacks`) should scope the `Commit` lookup to stacks belonging to the repository named in the same payload (`payload.dig('repository', 'full_name')`), and that repository's owning organization should be cross-checked against the organization used to select the verifying webhook secret, so a forged cross-organization payload cannot silently write into an unrelated repository's commit history.

### Proof of Concept
1. Attacker operates/administers "org-attacker", a legitimate GitHub organization onboarded into a shared Shipit instance, and knows `org-attacker`'s configured `webhook_secret`.
2. Attacker learns the SHA of a commit belonging to a stack under "org-victim/private-repo" (commit SHAs are visible on GitHub PRs/commits pages).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required",
  "target_url": "https://example.com",
  "created_at": "2026-09-01T00:00:00Z"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_of_org-attacker, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` — but the crafted payload need not even contain a `repository`/`organization` key matching org-victim; `verify_signature` only needs *some* org key it can resolve to `org-attacker`'s app to pick the matching secret (the attacker controls this field to match whichever secret they hold).
6. Signature check passes (`Shipit.github(organization: 'org-attacker').verify_webhook_signature` succeeds because attacker signed with the correct secret).
7. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit (irrespective of org/repo), and records a forged `success` status via `create_status_from_github!`.
8. If `ci/required` is part of `org-victim`'s `required_statuses`, the merge queue now considers the victim commit deployable/mergeable based on a status the attacker fabricated.
