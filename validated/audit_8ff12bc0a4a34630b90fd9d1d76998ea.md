### Title
CLStakingInfo Overwrite in `consolidateNodes()` Silently Drops CL Pool Staking Rewards — (File: `kaiax/staking/staking_info.go`)

---

### Summary

In `consolidateNodes()`, when two validators share the same `RewardAddr` and both have `CLStakingInfo` entries registered in the CLRegistry, the second `CLStakingInfo` **overwrites** the first via plain assignment (`=`) instead of accumulation. The first CL pool's staking amount is silently dropped from the consolidated node, causing that pool to receive zero staking rewards every block.

---

### Finding Description

`consolidateNodes()` builds a `cmap` keyed by `RewardAddr`. When multiple `NodeId`s share the same `RewardAddr`, their `StakingAmount`s are correctly **accumulated** (`cn.StakingAmount += si.StakingAmounts[i]`). However, the subsequent CL-staking loop uses plain **assignment**:

```go
// kaiax/staking/staking_info.go lines 151-159
if len(si.CLStakingInfos) > 0 {
    for _, clsi := range si.CLStakingInfos {
        if r, ok := nToR[clsi.CLNodeId]; ok {
            // One CLStakingInfo per validator is guaranteed by CLRegistry.
            cmap[r].CLStakingInfo = clsi   // ← ASSIGNMENT, not accumulation
        }
    }
}
``` [1](#0-0) 

The comment "One CLStakingInfo per validator is guaranteed by CLRegistry" refers to a per-`NodeId` guarantee. The CLRegistry maps `nodeId → CLPool`; it has no knowledge of `RewardAddr`. Two distinct `NodeId`s (e.g., `n1` and `n3`) that share the same `RewardAddr` (`r1`) can each independently register a `CLPool` in the CLRegistry. When both appear in `si.CLStakingInfos`, the second entry silently overwrites the first in `cmap[r1].CLStakingInfo`.

The test suite explicitly documents this overwrite behavior:

```go
// "4 nodes consolidated to 2 nodes and one node has two CLs"
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
{CLNodeId: n3, CLPoolAddr: clPool2, CLStakingAmount: clStakingAmount2},
``` [2](#0-1) 

The "not feasible in real" assumption is incorrect: the CLRegistry enforces uniqueness per `NodeId`, not per `RewardAddr`. Two validators with the same `RewardAddr` can each hold a valid `CLStakingInfo`.

The corrupted `consolidatedNode` is then consumed by both `assignStakingRewards` and `assignStakingRewardsFlex` during `FinalizeState`:

```go
// kaiax/reward/impl/getter.go lines 521-525
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount  // only the surviving CL pool
}
``` [3](#0-2) 

`cn.Split()` uses only the surviving `CLStakingInfo.CLStakingAmount`, ignoring the dropped pool entirely:

```go
// kaiax/staking/staking_info.go lines 169-187
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    cnAmountBig = big.NewInt(int64(c.StakingAmount))
    clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    ...
}
``` [4](#0-3) 

The dropped pool's address never appears in `alloc`, so `FinalizeState` never calls `state.AddBalance` for it:

```go
// kaiax/reward/impl/blockstate.go lines 53-55
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
``` [5](#0-4) 

---

### Impact Explanation

- **Dropped CL pool receives zero staking rewards** every block, permanently, for as long as the two validators share a `RewardAddr` and both hold CLStakingInfos.
- **Total staking amount for the consolidated node is understated** by the dropped pool's `CLStakingAmount`, skewing the proportional reward calculation across all eligible validators.
- The corrupted value is the `alloc` map entry for the dropped `CLPoolAddr`: it is `nil` (absent) instead of the correct proportional reward amount.

---

### Likelihood Explanation

- Two validators sharing the same `RewardAddr` is an explicitly supported and tested configuration (the consolidation logic exists precisely for this case).
- Each of those validators can independently register a `CLPool` in the CLRegistry (one per `NodeId`).
- No privileged action is required; any validator operator can set their `RewardAddr` to match another validator's.
- The scenario can arise accidentally (misconfiguration) or deliberately (one operator controls both validators).

---

### Recommendation

Replace the plain assignment with accumulation. Since `consolidatedNode.CLStakingInfo` is a single pointer, the fix requires either:

1. **Accumulate into the existing entry** — if a `CLStakingInfo` already exists for `cmap[r]`, add the new `CLStakingAmount` to it rather than replacing the struct:

```go
if existing := cmap[r].CLStakingInfo; existing != nil {
    existing.CLStakingAmount += clsi.CLStakingAmount
} else {
    cmap[r].CLStakingInfo = clsi
}
```

2. **Change `CLStakingInfo` to a slice** and update `Split()` to iterate over all CL entries, distributing rewards to each `CLPoolAddr` proportionally.

---

### Proof of Concept

**Setup:**
- Validator A: `NodeId = n1`, `RewardAddr = r1`, `StakingAmount = 10M KAIA`, `CLPool = clPool1`, `CLStakingAmount = 5M KAIA`
- Validator B: `NodeId = n3`, `RewardAddr = r1`, `StakingAmount = 40M KAIA`, `CLPool = clPool2`, `CLStakingAmount = 3M KAIA`

**`consolidateNodes()` result (buggy):**
```
cmap[r1] = {NodeIds:[n1,n3], StakingAmount:50M, CLStakingInfo:{clPool2, 3M}}
// clPool1 and its 5M KAIA are silently dropped
```

**Expected result:**
```
cmap[r1] = {NodeIds:[n1,n3], StakingAmount:50M, CLStakingInfo:{clPool1+clPool2, 8M}}
```

**Consequence in `assignStakingRewards` (Prague):**
- `cn.Split(reward)` splits reward between `r1` and `clPool2` only
- `clPool1` receives `0` KAIA every block
- `cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount = 50M + 3M = 53M` instead of the correct `58M`, understating this validator's weight in the total-excess calculation and redistributing the difference to other validators

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
