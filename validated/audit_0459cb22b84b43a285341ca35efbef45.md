### Title
Naive substring-based frontmatter delimiter split causes deny (`action: block`) hookify rules to silently downgrade to `warn` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` splits the raw file content on the literal substring `---` using `content.split('---', 2)` instead of matching `---` only as a standalone delimiter line. If a `pattern`, `conditions[].pattern`, or any other frontmatter value legitimately contains the three-character substring `---` before the real closing delimiter, the split terminates the frontmatter block early, and every field after that point—including `action: block`—falls into the discarded/`message` portion instead of the parsed `frontmatter` dict. Since `Rule.from_dict` defaults `action` to `"warn"` when the key is absent, a rule authored as blocking is silently loaded and enforced as a mere warning.

### Finding Description
`.claude/hookify.*.local.md` rule files are loaded by `load_rules()` → `load_rule_file()` → `extract_frontmatter()` in `plugins/hookify/core/config_loader.py`, and the resulting `Rule` is evaluated by `RuleEngine.evaluate_rules()` in `plugins/hookify/core/rule_engine.py`, invoked on every `Bash`/`Edit`/`Write`/`MultiEdit`/`Stop` event via the `PreToolUse` hook in `plugins/hookify/hooks/pretooluse.py`.

`extract_frontmatter` performs:
```python
if not content.startswith('---'):
    return {}, content
parts = content.split('---', 2)
if len(parts) < 3:
    return {}, content
frontmatter_text = parts[1]
message = parts[2].strip()
``` [1](#0-0) 

This splits on the raw substring `---` anywhere in the file, not on a line consisting solely of `---` (unlike a real YAML frontmatter parser, which anchors on `^---$`). If a rule file's frontmatter contains a value with an embedded `---` (e.g., a `pattern` designed to catch a command containing `---`, or a stylistic separator inside a quoted string) that appears *before* the intended closing delimiter line, `content.split('---', 2)` treats that embedded occurrence as the second delimiter. Everything physically located after it in the file—including a later `action: block` line and the real closing `---`—gets swept into `parts[2]`, which becomes the plain-text `message` rather than parsed frontmatter.

Example malicious/malformed rule file:
```markdown
---
name: deny-rm
enabled: true
event: bash
pattern: "rm -rf ---"
action: block
---
Blocked message
```
Here `content.split('---', 2)` produces:
- `parts[1]` = `\nname: deny-rm\nenabled: true\nevent: bash\npattern: "rm -rf ` (truncated before `action: block`)
- `parts[2]` = `"\naction: block\n---\nBlocked message` (treated entirely as message text)

`frontmatter` therefore never contains the `action` key. `Rule.from_dict` computes `action=frontmatter.get('action', 'warn')` [2](#0-1) , so the rule is loaded with `action == "warn"` even though the file visibly states `action: block`.

`RuleEngine.evaluate_rules` treats blocking vs. non-blocking purely by string equality `if rule.action == 'block'` [3](#0-2) . A rule with `action != 'block'` is placed in `warning_rules`, which only emits a `systemMessage` and **does not deny the tool call** — the dangerous `Bash`/`Edit`/`Write` invocation proceeds [4](#0-3) , compared to the `permissionDecision: "deny"` path used for real block rules [5](#0-4) .

No validation anywhere (`load_rules`, `load_rule_file`, `RuleEngine`) cross-checks the parsed frontmatter against the raw file text, and parsing failures are swallowed silently by broad `except` clauses in `load_rules`/`load_rule_file` [6](#0-5) [7](#0-6) , and `pretooluse.py` unconditionally exits 0 on any error, defaulting to allow [8](#0-7) . There is no defense-in-depth check that would catch a `block` rule silently reverting to `warn`.

### Impact Explanation
This breaks the stated invariant that a deny rule must never be parsed into a non-blocking configuration. A rule file authored (by the user, via `/hookify`, or committed into a cloned repository as project-level `.claude/hookify.*.local.md` config) with `action: block` intended to hard-stop dangerous `Bash`/`Edit`/`Write` operations can be turned into a no-op guard (warn-only, tool call still executes) purely by the presence of an unescaped `---` substring earlier in the same frontmatter block — something easy to introduce accidentally or intentionally by whoever supplies the `pattern`/`conditions` values (e.g., a pattern crafted to catch a `git diff` style `---`/`+++` marker, or any value containing a horizontal-rule-like string). This matches "Unauthorized local command execution that bypasses Claude Code approval or deny controls" since the intended blocking hook silently degrades to warn-and-allow.

### Likelihood Explanation
- Reaching the vulnerable code requires only placing a `.claude/hookify.*.local.md` file with the crafted content in the repository/working directory `load_rules()` scans [9](#0-8) ; this is ordinary repo content, no elevated privilege needed, and the `/hookify` command itself documents and generates exactly this file format (`pattern`, `action: block`) [10](#0-9) .
- The trigger condition (an embedded `---` substring inside a frontmatter value before the closing delimiter) is trivial to construct and not inherently suspicious — it can appear naturally in regex patterns describing dash sequences, diff markers, or Markdown horizontal rules pasted into a `pattern` value.
- The bug is fully deterministic and repeatable: every load of the malformed file produces the same silent downgrade.

### Recommendation
Rewrite `extract_frontmatter` to split on `---` only when it appears alone on its own line (e.g., using `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or splitting `content.splitlines()` and matching lines that are exactly `---`), matching standard YAML frontmatter semantics. Additionally, consider validating that `action` is one of the allowed literal values (`warn`/`block`) and failing closed (treat unparseable/ambiguous rule files as `block`-safe or reject them loudly) rather than silently defaulting to `warn` when frontmatter parsing is ambiguous. As a stronger fix, replace the hand-rolled parser with Python's `yaml.safe_load` on a properly delimited frontmatter block.

### Proof of Concept
Unit test to add to `plugins/hookify/core/config_loader.py` test suite (or a new `test_config_loader.py`):
```python
from hookify.core.config_loader import extract_frontmatter, Rule

def test_embedded_dashes_downgrade_block_rule():
    content = '''---
name: deny-rm
enabled: true
event: bash
pattern: "rm -rf ---"
action: block
---
Blocked message
'''
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Vulnerable behavior (current): action key missing, rule silently becomes "warn"
    assert 'action' not in frontmatter        # demonstrates delimiter truncation
    assert rule.action == 'warn'               # BUG: file visibly says action: block

    # Expected/fixed behavior:
    # assert frontmatter.get('action') == 'block'
    # assert rule.action == 'block'
```
Integration assertion via `RuleEngine`:
```python
from hookify.core.rule_engine import RuleEngine

engine = RuleEngine()
result = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf ---"}
})
# Vulnerable: no "permissionDecision": "deny" is emitted, only a systemMessage warning
assert result.get("hookSpecificOutput", {}).get("permissionDecision") != "deny"
```
Expected fixed-code assertions: `frontmatter['action'] == 'block'`, `rule.action == 'block'`, and `result["hookSpecificOutput"]["permissionDecision"] == "deny"`.
