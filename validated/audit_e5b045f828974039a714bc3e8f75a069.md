### Title
`OpenedHandler#provision?` operator-precedence bug creates unauthorized review stacks for any registered repository regardless of `review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
For a nonexistent `repository.full_name`, `Shipit::Repository.from_github_repo_name` returns `nil`, `NullRepository` is substituted, and every provisioning predicate on it is hard-coded `false`, so `provision?` correctly evaluates to `false`. This confirms the precedence bug in `provision?` is only reachable when `params.repository.full_name` resolves to a real, registered `Shipit::Repository` row, but does **not** require any special probing — repository full names are public, so no case-variation oracle is needed, and in fact none would work because `from_github_repo_name` normalizes case before lookup.

### Finding Description
Binding under test: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` resolving to a real `Repository` record (not `nil`) `==` necessary precondition for `provision?`'s precedence bug to yield a created stack.

`provision?` is defined as:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby's `&&`/`||` precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`. Critically, `review_stacks_enabled` only gates the first disjunct; the second and third disjuncts fire independently of it.

For `NullRepository`, every predicate (`review_stacks_enabled`, `provisioning_behavior_allow_all?`, `provisioning_behavior_allow_with_label?`, `provisioning_behavior_prevent_with_label?`) is hard-coded `false`: [2](#0-1) 
so all three disjuncts collapse to `false`, and `provision?` is `false` — no stack is created for an unregistered repo name. This confirms the claimed precondition: the bug requires `repository` in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54` to resolve to a real, admin-registered `Repository`.

For a real, registered repository whose admin set `review_stacks_enabled: false` but left `provisioning_behavior: prevent_with_label` (a valid, independent enum column on `Repository` — `enum :provisioning_behavior, ...` at `app/models/shipit/repository.rb:51`), the third disjunct `(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` evaluates `true` whenever the PR lacks the provisioning label, **regardless of `review_stacks_enabled`**. This causes `respond_to_pull_request_opened?` → `provision?` to return `true`, and `ReviewStackAdapter#find_or_create!` creates a review stack for a repository whose admin explicitly disabled dynamic review-stack provisioning.

Regarding the "near-miss full_name to test exploitability without alerts" premise: `from_github_repo_name` calls `github_repo_name.downcase` before splitting and querying: [3](#0-2) 
and `Repository#name=`/`#owner=` always downcase on write, so stored values are always lowercase. A differing-case `full_name` in the payload is normalized to the same lookup key and resolves to the *same* registered repository — it does not produce a distinguishing "miss" versus "hit" oracle. This part of the question's premise is incorrect: case variation provides no covert probing capability; repository names/owners are public GitHub identifiers anyway, so no oracle is needed to find registered repos.

Existing guards do not prevent this: `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?` [4](#0-3) , and webhook signature verification (`app/controllers/shipit/webhooks_controller.rb`) only authenticates that the payload came from GitHub for *some* repository with a configured webhook secret — it does not gate the `provisioning_behavior`/`review_stacks_enabled` logic, which is purely a data-driven precedence bug independent of signature validity.

### Impact Explanation
Any unprivileged GitHub user who can open a pull request against a repository that is registered in Shipit with `provisioning_behavior: prevent_with_label` (a common opt-out configuration) can force creation of a review stack even though the repository admin explicitly disabled dynamic provisioning via `review_stacks_enabled: false`. This is an unauthorized creation/provisioning action that bypasses the admin's intended control, scoped to any repository configured this way — a real, repeatable authorization bypass on the provisioning workflow (Critical per "unauthorized deploy" category, since review stacks provision infrastructure/deploy instances). It does not, however, allow cross-repository mutation, nor does it allow probing via case variation as hypothesized.

### Likelihood Explanation
Preconditions: the target repository must already be registered in Shipit (`Shipit::Repository` record exists) and have `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`, depending on label state) with `review_stacks_enabled` left `false`. No secrets, sessions, or special permissions are needed — merely opening a PR against that repository, which is available to any contributor able to open a PR (including via fork). This is trivially repeatable per PR/per repository matching the configuration.

### Recommendation
Add explicit parentheses to `provision?` in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb` (and the equivalent logic in `reopened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`) so that `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest plan in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
1. POST/process an `opened` payload where `repository.full_name` does not match any `Shipit::Repository` record. Assert `assert_no_difference -> { Shipit::Stack.count }` — confirms `NullRepository` path yields `provision? == false`.
2. Create/configure a real `Shipit::Repository` (`shipit_repositories(:shipit)`) with `review_stacks_enabled: false, provisioning_behavior: :prevent_with_label`. Process an `opened` payload for that repo's `full_name` with no provisioning label on the PR. Assert `assert_difference -> { Shipit::ReviewStack.count }` — confirms the precedence bug creates a stack despite `review_stacks_enabled` being `false`, validating the equality that a registered repository (regardless of `review_stacks_enabled`) is the sole precondition for exploitation.
