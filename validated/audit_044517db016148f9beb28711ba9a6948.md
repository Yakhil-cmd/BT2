### Title
`runWithStdin` kills only the direct child on context cancellation, leaving orphaned grandchildren/process-group members alive - ([File: pkg/cmd/cmd.go])

### Summary
`runWithStdin` builds `exec.CommandContext(ctx, command, args...)` without any `SysProcAttr` (no `Setpgid`), without a custom `cmd.Cancel`, and without `cmd.WaitDelay`. When the context is canceled or its deadline expires, Go's `os/exec` sends `SIGKILL` only to the direct child PID, not to any process group or descendants that child spawned. A hook script (attacker-influenced content run via `Do(ctx, hash)` in `pkg/hook/hook.go`) or a git subprocess that forks/execs further children can leave those children running indefinitely after the parent is killed, holding open file descriptors on `--root`, CPU, and repository locks.

### Finding Description
`runWithStdin` at [1](#0-0)  constructs the command with `exec.CommandContext(ctx, command, args...)` and never sets `cmd.SysProcAttr`, `cmd.Cancel`, or `cmd.WaitDelay`. The default `os/exec` cancellation behavior on context expiry is to call `Process.Kill()` on the single spawned process — it does not create a new process group and does not kill any subtree. If the invoked command (a git subprocess, or in `--one-time` mode a user/repo-controlled hook run through `HookRunner.Run` → `hook.Do(ctx, hash)`, see [2](#0-1) ) forks background children (e.g., a hook script that backgrounds a long-lived process, or a git subprocess that spawns a credential helper or pack process) that ignore or outlive the parent's termination, those descendants are never targeted by the context's kill signal and become orphans reparented to PID 1 inside the container. There is no post-`cmd.Run()` reconciliation, no process-group kill (`syscall.Kill(-pgid, syscall.SIGKILL)`), and no timeout-based force-reap logic anywhere in this file.

Because the attacker in scope can control repo content/refs that git-sync fetches (and, per hook semantics, hook execution is triggered by published hashes derived from that content), a hook or a git child process invoked to process that content can be made to spawn a background process that ignores the parent's SIGKILL delivery target (since it was never sent to it at all — it's an orphan issue, not signal-ignoring). This breaks the invariant "no subprocess outlives its context," particularly damaging in `--one-time` mode where `WaitForCompletion` ( [3](#0-2) ) gates process exit on hook success — the main process can exit while orphaned children continue to hold the volume/lock, and in long-running mode repeated triggers accumulate orphaned processes over time, exhausting CPU/FDs/volume locks.

### Impact Explanation
This matches the Kubernetes bug-bounty "resource exhaustion / denial of service via subprocess mismanagement" class: repeated triggering of syncs/hooks with a repo-controlled ref accumulates leaked processes that consume CPU and hold the `--root` volume (e.g., via open FDs or `.git/index.lock`), degrading or breaking git-sync's ability to complete future syncs — a form of persistent sync wedging distinct from a simple crash.

### Likelihood Explanation
No non-default flags are required beyond `--one-time` and an already-supported `--webhook`/`--exechook` configuration for triggering hooks — both are standard, documented git-sync features. The attacker only needs the ability to push refs/content that get synced (in scope). The core mechanic (default `os/exec` context cancellation only signals the direct child, not descendants) is deterministic and reproducible on every run where a subprocess forks additional children; it does not depend on race conditions.

### Recommendation
- Set `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` when constructing the command in `runWithStdin`, and on context cancellation kill the whole process group (`syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL)`) instead of relying on the default single-process kill.
- Alternatively use Go's `cmd.Cancel` and `cmd.WaitDelay` (Go 1.20+) to implement group-kill-on-timeout with a bounded grace period, then hard verify no descendants remain (e.g., reap `/proc/<pid>/task/*/children` or use `pdeathsig`).
- For hook execution specifically, apply the same process-group isolation so hook subprocesses and anything they spawn are terminated as a unit when the sync/hook context ends.

### Proof of Concept
Integration test outline for `pkg/cmd/cmd_test.go` (not present, needs to be added):
1. Invoke `runWithStdin` with a short `context.WithTimeout` and a shell command such as `sh -c '(sleep 100 &) ; sleep 100'`, which backgrounds a grandchild that detaches from the parent's process group before the parent is killed.
2. Assert `runWithStdin` returns after the context deadline (confirming the direct child was killed).
3. After the call returns, check `/proc` (or use `pgrep sleep`) and assert the backgrounded `sleep 100` process is still running — demonstrating the orphan survives past the context's deadline, violating the "no subprocess outlives its context" invariant.
4. Repeat under `--one-time` semantics by wiring this command as a `--exechook-command`, calling `HookRunner.Run` with a canceled context, and confirming `WaitForCompletion` returns while the orphaned process remains alive and holding a file lock under the test `--root` directory.

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
}

func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}

// WaitForCompletion waits for HookRunner to send completion message to
// calling thread and returns either true if HookRunner executed successfully
// and some error otherwise.
// Assumes that r.oneTimeResult is not nil, but if it is, returns an error.
func (r *HookRunner) WaitForCompletion() error {
	// Make sure function should be called
	if r.oneTimeResult == nil {
		return fmt.Errorf("HookRunner.WaitForCompletion called on async runner")
	}

	// Perform wait on HookRunner
	hookRunnerFinishedSuccessfully := <-r.oneTimeResult
	if !hookRunnerFinishedSuccessfully {
		return fmt.Errorf("hook completed with error")
	}

	return nil
}
