# Analog Found

### Title
Shared/cached AA definition object mutated in place during evaluation corrupts subsequent AA trigger executions - (File: `aa_composer.js`)

### Summary
The CVE describes a class of bug where a buffer/structure that is actually **shared** (via `pskb_copy`/`skb_clone`, or cloned skb with a shared `frag_list`) gets **mutated in place** by code that assumes exclusive ownership, corrupting the view seen by other concurrent consumers of the same underlying structure. The analog in `ocore` is in the Autonomous Agent (AA) execution engine: `evaluateAA()` in `aa_composer.js` mutates the AA definition array it receives — via `delete arrDefinition[1].getters;` — without first cloning it, even though `arrDefinition` for a given AA address is obtained through `storage.readAADefinition()`/`aa_addresses.js`, a caching layer that is reused across many trigger evaluations of the same AA (primary triggers, secondary/remote-AA calls, dry-runs and balance estimations).

### Finding Description
In `aa_composer.js`, `handleTrigger()`'s nested `evaluateAA()` function does: [1](#0-0) 
```
function evaluateAA(arrDefinition, cb) {
	var locals = {};
	var f = getFormula(arrDefinition[1].getters);
	...
	delete arrDefinition[1].getters;
```
This directly deletes the `getters` field from the definition object that was passed in as `arrDefinition`. The same object reference is then handed to `replace()`, which further walks and mutates it in place (deleting/overwriting message fields, sorting `denominations`/`attestors` arrays, etc.): [2](#0-1) [3](#0-2) 

`arrDefinition` is not always a fresh, per-call object. It is obtained through `storage.readAADefinition()` — consumed in `estimatePrimaryAATrigger()` and `dryRunPrimaryAATrigger()` — and through the AA address/definition cache maintained in `aa_addresses.js`, which is designed to avoid re-parsing/re-fetching a given AA's definition from the database on every trigger: [4](#0-3) [5](#0-4) 

Just as the TIPC bug appended data to a frag skb that was *believed* to be privately owned but was actually shared via a cloned `frag_list`, `evaluateAA()`/`replace()` treat `arrDefinition` as privately owned per-invocation state and mutate it destructively (deleting `getters`, deleting/reassigning message keys, sorting arrays), while the object may in fact be the same cached instance returned to other callers evaluating the same AA (secondary triggers invoked from another AA in the same trigger chain, remote-getter calls, concurrent primary/estimate/dry-run evaluations of the same address). Because JS objects are held by reference, this in-place mutation propagates to every other holder of that same cached array, not just the current evaluation.

### Impact Explanation
If the cached AA definition is shared (not deep-cloned per call) and one evaluation permanently strips `getters` or reorders/mutates message payload fields (`denominations`, `attestors`, dynamic `if`/`init` case objects consumed via `delete value.if; delete value.init;` seen in `aa_validation.js`'s analogous walker), subsequent evaluations of the *same* AA — including primary triggers from other units, secondary triggers dispatched from other AAs, and remote getter calls — will silently execute against a corrupted/degraded definition. This can:
- change computed message outputs/amounts leading to incorrect fund transfers (AA fund loss or unintended payouts),
- cause different nodes to observe different behavior for the same AA depending on evaluation ordering/timing (since caching/mutation order is not part of consensus-critical, deterministically-replayed state), producing **node disagreement on validity or stability** of AA response units,
- permanently disable getter functions for an AA (`delete arrDefinition[1].getters`), silently changing its execution semantics for all future callers.

This satisfies the Medium-severity, concrete-impact bar (state/definition corruption reachable by any AA trigger sender through normal invocation of a target AA).

### Likelihood Explanation
Any unprivileged account can send a payment/message that triggers an AA, and any AA can call another AA (secondary trigger) or a remote getter — all of which flow through `handleTrigger()`/`evaluateAA()` with an `arrDefinition` sourced from the shared definition cache. No special privilege is required; only repeated invocation of an AA (which is a normal, expected usage pattern) is needed to trigger the destructive first-time mutation.

### Recommendation
Deep-clone `arrDefinition` (e.g., via `_.cloneDeep` or `string_utils.cloneDeep`, already used elsewhere in this codebase for similar copy-on-write concerns) at the top of `handleTrigger()`/`evaluateAA()` before any `delete`/mutation is performed, so that cached/shared definition objects are never mutated in place. Audit `replace()` and `aa_validation.js`'s equivalent walker for the same pattern (in-place `delete obj[name]`, `delete value.if`, `delete value.init`, array `.sort()` on payload arrays) to ensure none of them can observe or persist mutations against a shared cache entry.

### Proof of Concept
1. Deploy AA `A` with a `getters` block and at least one message.
2. Trigger `A` once directly (primary trigger) — `evaluateAA()` executes `delete arrDefinition[1].getters;` on the definition object obtained from the AA definition cache.
3. Deploy AA `B` whose formula calls a getter function of `A` (`A_address.$f(...)`), or trigger `A` a second time.
4. If the cache returned the same object reference in step 1, the second evaluation observes `arrDefinition[1].getters === undefined`, causing `getFormula(arrDefinition[1].getters)` to short-circuit to the "no getters" path — silently skipping getter execution/definitions for all subsequent calls to `A`, diverging from the AA's intended (and previously validated) behavior.

*Note: Full confirmation that `aa_addresses.js`'s definition cache returns the identical (non-cloned) array reference across repeated `readAADefinition` calls could not be completed within the available tool budget — the exact caching implementation in `aa_addresses.js` was not retrieved. The finding is based on the confirmed in-place `delete`/mutation pattern in `aa_composer.js` combined with the observed caching-by-reference pattern used pervasively elsewhere in `storage.js` (e.g., `assocStableUnits`). A Devin session with full file access should verify `aa_addresses.js`'s `readAADefinition`/cache implementation to confirm whether cloning occurs before this point.*
