## Analysis

The reported Superposition bug is a "check-then-irrevocable-act" race: a state-dependent guard (slippage check) can be defeated by a party who mutates the shared state between the check and an unconditional follow-up action, permanently destroying value because the underlying execution order/finality isn't guaranteed at the time the check runs.

The equivalent condition exists in ocore's data-feed reading logic used by AA (Autonomous Agent) oscript formulas. There are two parallel data-feed lookup functions:

- `readDataFeedValue()` in `data_feeds.js` — used by the `data_feed[[...]]` formula operator — explicitly filters out any unstable candidate unit whose `sequence` is not `'good'`: [1](#0-0) 
- `dataFeedExists()` in the same file — used by the `in_data_feed[[...]]` formula operator — scans the exact same `storage.assocUnstableMessages` structure for AA-authored data-feed messages, but performs **no** `sequence` check at all before accepting a match: [2](#0-1) 

Both are reachable identically from AA oscript, e.g. via `formula/evaluation.js`'s `in_data_feed` case, which forwards `bAA` straight into `dataFeedExists`: [3](#0-2) 

Whether an unstable unit's `sequence` will finally resolve to `'good'` or `'final-bad'` is only settled at stabilization time, via `findStableConflictingUnits`/`markMcIndexStable`'s conflict-resolution pass: [4](#0-3) [5](#0-4)  Prior to that, a double-authored/conflicting unit sits in `'temp-bad'` and can still flip to `'final-bad'` (permanently voided) once the conflict is adjudicated, as set up in `validateAuthor`'s `checkSerialAddressUse`: [6](#0-5) 

### Title
`in_data_feed` AA formula operator accepts data-feed values from unstable, unresolved (`temp-bad`) units that may later become permanently voided - (File: data_feeds.js)

### Summary
The `in_data_feed[[...]]` oscript formula, evaluated during AA trigger execution, calls `dataFeedExists()` to search data-feed messages posted by unstable AA-related units. Unlike its sibling `readDataFeedValue()` (used by the `data_feed[[...]]` operator), `dataFeedExists()` never checks the candidate unit's `sequence` field, so it treats data-feed messages from units whose finality has not yet been decided (`sequence='temp-bad'`) as if they were confirmed truth.

### Finding Description
`dataFeedExists()` iterates `storage.assocUnstableMessages`, filtering only on `objUnit.bAA`, `latest_included_mc_index` bounds, and author-address membership: [7](#0-6)  It never inspects `objUnit.sequence`, so a unit that is currently `temp-bad` (i.e., conflicts with another unit from the same address and has not yet been resolved as good or final-bad) is treated identically to a fully serial ("good") unit. `readDataFeedValue()` was written with an explicit sequence check for the same scenario: [1](#0-0)  demonstrating the intended, correct behavior that `dataFeedExists()` omits.

Conflict resolution for double-authored/competing units happens only when the relevant MCI stabilizes, deterministically picking one unit "good" and voiding the other(s) to `'final-bad'`: [8](#0-7)  Before that point, a unit can legitimately be included as an ancestor of an AA trigger (satisfying `latest_included_mc_index <= mci`) while its own `sequence` is still `temp-bad` and its ultimate fate ('good' vs 'final-bad') undecided.

### Impact Explanation
An address that is used as an oracle/data-feed provider for one or more AAs can post two units from the same address carrying conflicting `data_feed` payloads — e.g., one with a value that would make an `in_data_feed[[...]]` condition evaluate to `true`, and a conflicting, higher-priority unit with the "real"/different value. If the AA trigger executes while the favorable-but-conflicting unit is still `temp-bad` (not yet resolved), `dataFeedExists()` will report a match and the AA will act on it — issuing payments, locking/unlocking funds, or updating state — irreversibly, exactly like the referenced report's "burn position" step that proceeds despite the preceding state-dependent step's premise being invalid. Once stabilization resolves the conflict, the favorable unit can become `'final-bad'` (as though it never happened), but the AA's response has already been finalized and cannot be undone, resulting in AA fund loss/misallocation or freezing based on a data-feed condition that never actually became true.

### Likelihood Explanation
Reaching this path requires only posting two ordinary, validly-signed units from the same author address with conflicting content (a standard "double author" conflict any unprivileged unit poster can create) and having an AA definition that uses `in_data_feed[[...]]` referencing that address as an oracle — a common oscript pattern for AAs. No hub, network, or node-privilege access is required; this is entirely reachable by an ordinary AA trigger sender/oracle author composing units through the public protocol.

### Recommendation
Add the same `objUnit.sequence !== 'good'` filter to `dataFeedExists()` that already exists in `readDataFeedValue()`, so that `in_data_feed[[...]]` is consistent with `data_feed[[...]]` and never counts a `temp-bad` (unresolved) unit's data-feed payload as a match.

### Proof of Concept
1. Address `Oracle` posts unit `U1` authored solely by `Oracle`, containing `data_feed: {price: 100}` (the value that would satisfy an AA's `in_data_feed[[...]]` condition), built on parents that make it conflict with a later unit from the same address.
2. Address `Oracle` posts a second unit `U2`, also authored solely by `Oracle`, spending/conflicting with `U1` (e.g., differing parents causing `checkSerialAddressUse` in `validation.js` to flag both as competitors), carrying `data_feed: {price: 50}`.
3. Both `U1` and `U2` are accepted as `temp-bad`/pending while unstable (per `validation.js` lines 1304-1330).
4. A victim posts a trigger to an AA whose oscript includes `in_data_feed[[oracles="Oracle", feed_name='price', feed_value>=100]]`. If the trigger's MCI stabilizes while `U1` is still `temp-bad` and included in the trigger's ancestry, `dataFeedExists()` in `data_feeds.js` (lines 34-96) returns `true` because it never checks `sequence`, and the AA executes the `price>=100` branch (e.g., releasing funds).
5. Later, MC stabilization resolves the conflict and `U1` becomes `final-bad` (as per `main_chain.js` lines 1327-1351) — meaning `price` was never actually `>=100` — but the AA's fund release has already occurred and cannot be reversed.
