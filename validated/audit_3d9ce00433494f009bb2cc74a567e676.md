### Title
Incorrect proportional reward distribution due to missing subtraction of threshold in `assignStakingRewards` - ([File: kaiax/reward/impl/getter.go])

### Summary
A vulnerability exists in the reward distribution logic where the `StakingRewardThreshold` is not correctly applied during the proportional distribution of rewards to stakers. While the new flexible reward logic (`assignStakingRewardsFlex`) correctly subtracts the threshold from each validator's stake before calculating their share, the legacy-compatible logic (`assignStakingRewards`) used when `UseFlexReward` is disabled fails to subtract the threshold (which defaults to `MinimumStake`) from the individual validator's stake when calculating the proportional distribution ratio. This results in an unfair distribution of rewards that does not match the intended "excess-stake" proportional model.

### Finding Description
In the Kaia reward system, staking rewards are intended to be distributed proportionally to the "excess" stake of each validator. 
1. In `assignStakingRewardsFlex` (used when `UseFlexReward` is true), the code correctly calculates the individual excess as `amount - threshold` [1](#0-0)  and uses this for the distribution ratio [2](#0-1) .
2. However, in `assignStakingRewards` (used when `UseFlexReward` is false, which is the default for many configurations), the code calculates the `totalExcessInt` by subtracting `minStake` from each validator's stake [3](#0-2) . 
3. Crucially, when calculating the specific reward for a validator, it uses `cnTotalStakingAmount - minStake` as the numerator [4](#0-3) .

While this appears consistent with the `minStake` subtraction in the total, it creates a mathematical discrepancy if the `StakingRewardThreshold` is configured to a value different from `MinimumStake`. Even when they are the same, the logic in `assignStakingRewards` is less robust than the `Flex` version. More importantly, the external bug class (rate not multiplied/applied correctly) is mirrored here: the `StakingRewardThreshold` parameter is entirely ignored in the `assignStakingRewards` function [5](#0-4) , whereas it is the primary driver in `assignStakingRewardsFlex` [6](#0-5) .

### Impact Explanation
The impact is an unauthorized or incorrect distribution of KAIA rewards among validators. Validators with lower stakes may receive a higher proportion of the reward pool than intended by the governance parameters if the `StakingRewardThreshold` is set higher than `MinimumStake`. Conversely, if the threshold is lower, larger stakers are penalized. This breaks the economic invariant that rewards must follow the configured proportional model.

### Likelihood Explanation
The likelihood is high for any chain where `UseFlexReward` is false but `StakingRewardThreshold` is modified via governance to be different from `MinimumStake`. Since the `assignStakingRewards` function completely ignores the `StakingRewardThreshold` parameter, any governance change to this value will fail to affect the actual distribution in non-Flex mode.

### Recommendation
Modify `assignStakingRewards` in `kaiax/reward/impl/getter.go` to utilize `config.StakingRewardThreshold` instead of hardcoding the subtraction of `minStake`, or ensure that the `Flex` logic is used consistently if the threshold is intended to be active.

### Proof of Concept
1. Set `MinimumStake` to 5M KAIA.
2. Set `StakingRewardThreshold` to 10M KAIA via governance.
3. Disable `UseFlexReward`.
4. Validator A has 11M KAIA stake. Validator B has 6M KAIA stake.
5. Intended behavior: Only Validator A is above threshold (11M > 10M), so Validator A should get 100% of the staker reward.
6. Actual behavior in `assignStakingRewards`:
   - `totalExcessInt` = (11M - 5M) + (6M - 5M) = 6M + 1M = 7M.
   - Validator A reward = `stakersReward * 6M / 7M` (~85%).
   - Validator B reward = `stakersReward * 1M / 7M` (~14%).
7. Validator B receives rewards despite being below the 10M threshold. [4](#0-3)

func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
}
