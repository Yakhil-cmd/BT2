### Title
Weak `(filePath, category)` dedup key lets a new, distinct vulnerability be silently suppressed as "already handled" - ([File: plugins/security-guidance/hooks/llm.py])

### Summary
The `security-guidance` plugin's commit/push/stop security-review hooks track which vulnerabilities have already been surfaced to the user via a `previous_findings` list, keyed only on `(filePath, category)`. Both the storage layer and the LLM review prompt itself instruct that any finding matching an already-recorded `(filePath, category)` pair must **not** be re-reported, even though the actual vulnerable code (`vulnerableCode`) is explicitly excluded from the identity. This mirrors the `DKIMRecoverySigValidator` bug class: a "one-time/already-handled" identifier is built from too few validated fields, so a distinct event (a genuinely different vulnerability) can collide with a prior identifier and have its protective action (surfacing/blocking) permanently suppressed.

### Finding Description
The dedup key is computed by `_finding_keys` and used everywhere findings are recorded or filtered: [1](#0-0) 

`_dedup_against_state` drops any new finding whose `(filePath, category)` already exists in `previous_findings`. The recording sites (`_record_findings` in commit-review, `_record` in push-sweep, `_record_fire` in the Stop hook) all build their `seen` set the same way: [2](#0-1) [3](#0-2) 

Crucially, the LLM prompt itself hard-codes this weak identity as an instruction to the reviewing model, telling it to skip anything matching a prior `(filePath, category)` regardless of whether the actual vulnerable snippet is new: [4](#0-3) 

The comment at the recording site even acknowledges the tradeoff explicitly ("vulnerableCode bytes drift ... so matching on it under-dedupes") but never accounts for the opposite failure mode: two *distinct* vulnerabilities of the same category in the same file are indistinguishable by this key, so the second one is treated as already-handled and dropped, exactly like the DKIM report's non-canonical `sigMeta` collapsing distinct recovery payloads into the same `identifier`.

### Impact Explanation
Once any (even low-severity, benign, or LLM-misclassified) finding of a given category is reported for a file, `previous_findings` "vaccinates" that `(filePath, category)` pair for the remainder of `PREVIOUS_FINDINGS_TTL_SEC` (default 3600s, `security_reminder_hook.py:36`). Any subsequent commit/push/turn that introduces a *new and more severe* vulnerability of the same category in the same file — e.g., a second hardcoded secret, a new SQL-injection sink, a new SSRF path — will be silently dropped by `_dedup_against_state` and never shown to the user or fed back to Claude via the `exit(2)` guidance path. This is a direct bypass of the plugin's core security control (an unprivileged-user-facing automated code-review gate on git automation), without any privilege escalation needed — a normal session that triggers one finding of a category effectively disables future detection of that category in that file.

### Likelihood Explanation
Medium. It requires two conditions that are common in real workflows: (1) an earlier finding of a given `(filePath, category)` gets recorded (which happens routinely — the review runs on every commit/push/turn), and (2) a later, different vulnerability of the same category is introduced in the same file within the TTL window (e.g., iterative development on a config/auth file, or an attacker/prompt-injected change deliberately reusing a previously-flagged category to "ride" the suppression). No special access is needed; it happens naturally in normal Claude Code sessions doing back-and-forth security fixes, and could be deliberately exploited via prompt injection in file contents that steers the model toward reusing a category label.

### Recommendation
Bind the dedup identity to content that actually distinguishes vulnerabilities, not just `(filePath, category)`. For example, hash a normalized/stable representation of the vulnerable location (e.g., line-range-independent code fingerprint, or the pre/post diff hunk identity) in addition to category, and only suppress re-reporting when the *fix* for the previously reported instance is still present unchanged. At minimum, cap suppression stronger by verifying `vulnerableCode` similarity (e.g., fuzzy match) rather than ignoring it entirely, so a second distinct instance of the same category in the same file is not unconditionally treated as already-handled.

### Proof of Concept
1. Claude commits code that introduces a low-severity hardcoded value in `config.py`, and the commit-review hook flags it as `category="Hardcoded Secret"`, `filePath="config.py"`. This is recorded into `previous_findings` as `("config.py", "Hardcoded Secret")` via `_record_findings`: [5](#0-4) 
2. In a later commit within the same session (within `PREVIOUS_FINDINGS_TTL_SEC`), Claude (or an attacker steering it via prompt injection) introduces a genuinely different and more severe hardcoded secret elsewhere in `config.py` (e.g., an admin API key), again categorized as `"Hardcoded Secret"`.
3. `analyze_code_security` is invoked with `previous_findings` containing the first finding; the prompt explicitly instructs the model not to re-flag any `(filePath, category)` match: [6](#0-5) 
4. Even if the model does return the new finding anyway, `_dedup_against_state` filters it out server-side because its `(filePath, category)` tuple already exists in `previous_findings`: [7](#0-6) 
5. The second, more severe secret is never surfaced to the user and the hook exits without triggering the `exit(2)` remediation path, effectively defeating the security-guidance plugin's protection for that file/category for the rest of the TTL window.

```python
def _finding_keys(findings: List[Dict[str, Any]]) -> set:
    return {(f.get("filePath", ""), f.get("category", ""))
            for f in findings if isinstance(f, dict)}


def _dedup_against_state(session_id: str, vulns: List[Dict[str, Any]],
                         prompted: set) -> Tuple[List[Dict[str, Any]], int]:
    """Drop vulns that a CONCURRENT asyncRewake hook wrote to
    previous_findings while this hook's LLM was running.

    `prompted` is the (filePath, category) set the LLM was already told about
    via the prev_section prompt block. The LLM is instructed to only re-flag
    those if the attempted fix is incomplete, so a re-flag of a `prompted`
    entry is an intentional "fix didn't work" verdict and MUST pass through.
    We therefore re-read state now and only filter the race delta —
    (seen_now − prompted) — i.e. findings the LLM was never told about
    because they were written mid-review by the other hook.
    Returns (surviving_vulns, n_dropped).
    """
    if not vulns:
        return vulns, 0
    fresh = with_locked_state(
        session_id, lambda s: list(s.get("previous_findings", []))
    ) or []
    race_delta = _finding_keys(fresh) - prompted
    kept = [v for v in vulns
            if (v.get("filePath", ""), v.get("category", "")) not in race_delta]
    return kept, len(vulns) - len(kept)
```

```python
        }
        for v in new_vulns

    def _record_findings(state):
        existing = [f for f in state.get("previous_findings", []) if isinstance(f, dict)]
        seen = {(f.get("filePath", ""), f.get("category", "")) for f in existing}
        for f in finding_snapshots:
            key = (f["filePath"], f["category"])
            if key not in seen:
                seen.add(key)
                existing.append(f)
        state["previous_findings"] = existing
        state["previous_findings_ts"] = _time.time()
    with_locked_state(session_id, _record_findings)
```
