### Title
Webhook signature is verified against an attacker-selectable organization secret that is decoupled from the repository the payload actually writes to - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App / organization webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the untrusted, attacker-supplied JSON body, while the downstream event handlers act on a completely independent field of the same body — `repository.full_name` — to decide which `Stack`/`Repository` gets synced. Because the two fields are never cross-checked, an attacker who legitimately controls one configured GitHub organization (and therefore knows that organization's `webhook_secret`) can forge a signed payload whose `repository.owner.login` matches their own org (so the correct/known secret is used to pass verification) but whose `repository.full_name` points at a stack belonging to a *different* organization/repository configured in the same Shipit instance.

### Finding Description
`verify_signature` selects the verifying `GitHubApp` instance using attacker-controlled data before the HMAC check is meaningful for anything except "was this byte blob signed by *some* known secret": [1](#0-0) [2](#0-1) 

The secret itself is per-organization, stored in `@config[:webhook_secret]` inside `GitHubApp#initialize`, and `verify_webhook_signature` just HMACs the raw body with whichever org's secret was selected: [3](#0-2) [4](#0-3) 

Multiple independent organizations, each with their own secret, can be configured in the same Shipit instance: [5](#0-4) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire* parsed body to the event handler: [6](#0-5) 

`Handler#stacks` (used by `PushHandler`, the handler for `push` events) resolves the target repository/stack from a *different* field of the same payload — `repository.full_name` — with no relation whatsoever to `repository.owner.login`: [7](#0-6) [8](#0-7) 

The equality that should hold but does not is:
`organization whose secret authenticated the request (repository.owner.login)` == `organization/repository that is actually written to (repository.full_name)`

Before the attack: a legitimate GitHub webhook for org A always has `repository.owner.login == A` and `repository.full_name == "A/..."`, so the two fields are naturally consistent and the HMAC (computed over the whole body by GitHub using A's secret) implicitly binds them together.

After the attack: the attacker, who administers org A's GitHub App installation (and thus legitimately possesses A's `webhook_secret` — this is not a privileged Shipit credential, just ordinary control of their own GitHub org/app), constructs a raw JSON body with `repository.owner.login = "A"` but `repository.full_name = "B/some-repo"` (org B being an unrelated org/repo also configured on the same Shipit instance), computes `sha1=HMAC(A_secret, body)` themselves, and POSTs it directly to `/webhooks`. `verify_signature` looks up `Shipit.github(organization: "A")`, uses A's secret, and the signature checks out because the attacker computed it with the correct (their own) secret. `PushHandler` then resolves `stacks` for `"B/some-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA for a repository the attacker has no legitimate relationship to.

### Impact Explanation
This breaks the cross-repository/cross-organization isolation that the per-organization webhook secret is supposed to enforce. An attacker who legitimately controls org A's GitHub App/webhook secret can inject synthetic push/status/check_suite/pull_request events against stacks belonging to org B, forcing `GithubSyncJob` to resynchronize a stack to an arbitrary attacker-chosen commit SHA. Depending on the target stack's configuration (e.g. continuous deployment enabled), this can drive an unauthorized deploy of attacker-chosen commits into a stack the attacker does not own — a cross-repository/organization write and potential unauthorized deploy, matching the "Critical: cross-repository writes, or an unauthorized deploy" bucket.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with more than one GitHub organization/app (a supported and documented configuration, as shown by `secrets_double_github_app.yml`), and (2) the attacker controls at least one of those organizations' webhook secret — a routine, unprivileged capability for anyone managing their own org's GitHub App, not a Shipit credential. No Shipit session, API token, or repository write access on the target org is needed. This is a realistic multi-tenant deployment scenario for Shipit.

### Recommendation
Cross-validate the field used to select the verifying secret (`repository.owner.login` / `organization.login`) against the field used to resolve the target repository (`repository.full_name`) — e.g., reject the webhook if the owner segment of `full_name` doesn't match the resolved organization, or resolve the `Repository`/`Stack` strictly within the same organization boundary that authenticated the request. Additionally, do not rely solely on organization-scoped secrets for repository binding; verify that the repository referenced in the payload is actually owned by the authenticating organization before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret`, and a `Stack` for `OrgB/private-repo`.
2. As an attacker who administers `OrgA`'s GitHub App (thus knows `OrgA`'s `webhook_secret`), build a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/private-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `signature = "sha1=" + HMAC-SHA1(OrgA_webhook_secret, body)`.
4. POST to `/webhooks` with headers `X-Github-Event: push` and `X-Hub-Signature: <signature>`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` from `repository.owner.login`, verifies successfully against `OrgA`'s secret [1](#0-0) .
6. `PushHandler` resolves `stacks` via `repository.full_name = "OrgB/private-repo"` [7](#0-6)  and enqueues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the `OrgB` stack, despite the request never being authenticated by `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
