## Vulnerability Found

### Title
Unauthenticated forgery of GitHub commit-status/push webhooks across the entire multi-tenant Shipit installation, due to the organization used to verify a webhook's signature being decoupled from the repository/commit the payload's handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub organization's secret to check a webhook's HMAC signature against by reading an attacker-controlled field of the very payload being verified (`repository.owner.login`, falling back to `organization.login`). Handlers that subsequently act on the payload (in particular `StatusHandler`) do not re-derive or re-check that organization/repository binding — `StatusHandler` matches purely by commit SHA across the whole database. Combined with `GithubApp#verify_webhook_signature` returning `true` whenever an organization has no `webhook_secret` configured (a state explicitly documented as "optional"), an unauthenticated caller can pick an organization entry that has no secret to sail through verification, while the payload's `sha`/status fields are applied against *any* commit belonging to *any* stack in the installation.

### Finding Description
`verify_signature` resolves the GitHub App/secret to check against using data taken from the raw, unauthenticated request body itself: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no configured `webhook_secret`: [3](#0-2) 

The setup docs and template explicitly present `webhook_secret` as optional for any organization: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw JSON to every registered handler for the event, with no additional binding of "the organization whose secret validated this request" to "the repository/commit this payload is about": [6](#0-5) 

`StatusHandler`, which processes GitHub `status` events, looks up commits **only by SHA, with no repository/organization scoping whatsoever**: [7](#0-6) 

The binding that should hold — `organization authenticated via signature == organization/repository owning the object being mutated` — is broken:
- Before the attack: signature verification is meant to prove "this payload originated from GitHub for organization X", and object mutation is meant to be scoped to org X's repositories.
- After the attack: an attacker sends a POST to `/webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` (or `organization.login`) names any org configured *without* a `webhook_secret` (satisfying `verify_signature`), and a `sha`/`state` pointing at a commit that belongs to a completely different, fully-secured stack. `StatusHandler#process` finds and mutates that commit regardless of which organization "authenticated" the request.

### Impact Explanation
A forged `success` status is written via `Commit#create_status_from_github!`, which:
- Enables CI on the stack and schedules continuous delivery: [8](#0-7) 
- Feeds `MergeRequest#reject_unless_mergeable!`/`merge!`, which rely on `StatusChecker` over the (now-forged) statuses to decide whether a pull request may be merged: [9](#0-8) 

This lets an unauthenticated party fabricate passing CI results for arbitrary commits/stacks, enabling an unauthorized deploy (via continuous delivery) or an unauthorized merge (via the merge queue) on repositories they have no legitimate relationship to — matching the Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
No credentials, tokens, or repository access are required. The only precondition is that at least one organization entry in the multi-tenant Shipit configuration has no `webhook_secret` set — a state the project's own setup documentation calls out as optional/acceptable. Any internet-reachable Shipit instance meeting that documented configuration is exploitable with a single crafted HTTP request.

### Recommendation
- Scope every webhook handler's lookups (especially `StatusHandler`) to the repository named in the payload, and verify that repository actually belongs to the organization whose secret validated the request, rather than matching by SHA/ref alone.
- Make `webhook_secret` mandatory (fail closed) instead of allowing `verify_webhook_signature` to return `true` when it is unset.
- Bind the "authenticated organization" resolved in `verify_signature` to the "repository/stack acted upon" downstream, so the two can never diverge for a single request.

### Proof of Concept
1. Configure (or identify) a Shipit deployment where one organization in `secrets.yml`'s `github:` map has `webhook_secret` unset (per the documented optional setting).
2. Find/guess a commit `sha` belonging to a **different**, fully-secured stack/organization tracked by the same Shipit instance (e.g. via the public stack pages).
3. Send, with no authentication:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "<org-without-webhook_secret>" } }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "<org-without-webhook_secret>")`, whose `verify_webhook_signature` returns `true` unconditionally (no `X-Hub-Signature` even required).
5. `StatusHandler#process` executes `Commit.where(sha: "<victim-commit-sha>").each { |c| c.create_status_from_github!(params) }`, writing a fabricated `success` status onto the victim's commit, potentially unblocking its merge/deploy.

      return true unless webhook_secret

    end
