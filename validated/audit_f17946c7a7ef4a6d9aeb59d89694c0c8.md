### Title
Webhook organization used for HMAC verification differs from repository used to act on the payload, allowing cross-repository event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (`secrets.github` keyed by organization, each with its own `webhook_secret`), the field used to select which organization's secret verifies the HMAC signature (`repository.owner.login`) is not the same field the event handlers use to resolve the target repository/stack (`repository.full_name`). An attacker who is a legitimate, unprivileged GitHub org admin/webhook manager for *one* configured organization (call it `attacker-org`, which they know the `webhook_secret` for) can craft a webhook body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`. The signature will validate against `attacker-org`'s secret, but the handler will look up and mutate state (sync commits, post commit statuses, close/open PRs, archive stacks) for the victim repository.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from attacker-controlled payload content:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

It then verifies the signature using `Shipit.github(organization: repository_owner)`'s `webhook_secret` [4](#0-3) . Once verified, `create` hands the *entire raw* JSON payload to every registered handler for the event type [5](#0-4) .

The base `Handler` class, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, and all `PullRequest::*Handler`s, resolves the acted-upon repository from a *separate* field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

Nothing in the controller or handler cross-checks that `repository.owner.login` (the field trusted for HMAC-key selection) is consistent with `repository.full_name` (the field trusted for identifying which `Repository`/`Stack` to mutate). The equality that should hold — "organization whose secret authenticated the request == organization that owns the repository being acted on" — is never enforced.

### Impact Explanation
This breaks the same trust binding described in the OtterSec report (a value used for one authorization check diverging from the value the protocol actually acts on). Here it lets an actor who legitimately controls the webhook configuration of *any one* configured GitHub organization in a multi-org Shipit install forge validly-signed events for a repository belonging to a completely different organization/tenant, e.g.:
- `PushHandler` → force `GithubSyncJob` to run for an arbitrary victim stack with an attacker-chosen `expected_head_sha` [7](#0-6) .
- `StatusHandler` → inject fabricated CI statuses onto victim commits [8](#0-7) , which can satisfy `ci.require`/`ci.blocking` checks and enable an unauthorized deploy of the victim stack.
- `PullRequest::ClosedHandler` → archive a victim stack.

This is a cross-repository/cross-tenant write achieved without any credential belonging to the victim organization, satisfying the "cross-repository writes" / "unauthorized deploy" Critical/High impact bar.

### Likelihood Explanation
Requires the Shipit instance to be configured with the multi-organization `secrets.github` schema (each org has its own `webhook_secret`) as documented in `docs/setup.md`, and requires the attacker to control (or compromise) the webhook delivery for at least one of those configured organizations — this is a realistic multi-tenant Shipit deployment scenario, and the attacker does not need any Shipit-side credential, only the ability to send an HTTP POST with a body/signature they compute themselves for their own org. No `ApiClient` token, `github_access_token`, or Shipit session is needed, keeping it in scope as an unprivileged-attacker path.

### Recommendation
In `WebhooksController`, after verifying the signature, re-derive/cross-check that the repository named in the delivered payload (`repository.full_name`) actually belongs to the same organization whose secret validated the signature (`repository.owner.login`/`organization.login`), rejecting the request (422) on mismatch — mirroring the OtterSec fix pattern of pinning the value used for authorization to a single verified source of truth rather than trusting two independently attacker-controlled fields to agree.

### Proof of Concept
1. Configure/observe that the target Shipit instance uses per-organization `github.webhook_secret` (multi-org schema) and that the attacker's own GitHub organization, `attacker-org`, is one of the configured organizations, giving the attacker access to (or knowledge of) `attacker-org`'s `webhook_secret`.
2. Craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org webhook_secret, body)>`.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates [4](#0-3) .
6. `PushHandler` resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [6](#0-5)  and enqueues `GithubSyncJob` for the victim stack with the attacker-supplied `after` SHA [7](#0-6) , despite the attacker having no relationship to `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
