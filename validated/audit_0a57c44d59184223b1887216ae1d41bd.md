### Title
CCMenu API endpoint bypasses per-`ApiClient` stack scoping, allowing cross-stack disclosure of deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The external report describes `RegistryManager#_commitNewBoolForAddressOnRemoteRegistry` calling the wrong namespace-replacement helper (`BYTES32` instead of `BOOL`), so the *entity acted upon* (a boolean value) diverges from the *entity actually used for the storage-key computation*. The same bug class — "the field bound by an authorization/verification check is not the field actually acted upon" — is present in `Shipit::Api::CCMenuController`, where the stack an `ApiClient` token is scoped to (`ApiClient#stack_id`) diverges from the stack the controller actually reads.

### Finding Description
`Shipit::Api::BaseController` establishes the authorization binding "an `ApiClient` may only touch the stack named in `stack_id`" via: [1](#0-0) 

Here, `stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` whenever the client is stack-scoped, and `stack` resolves the requested record only from within that restricted relation (`stacks.from_param!`).

`Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the unscoped `Stack` model, breaking that binding: [2](#0-1) 

The controller only re-validates the coarse-grained permission `read:stack` via `require_permission :read, :stack`, never the per-record `stack_id` scope: [3](#0-2) 

The equality that should hold is: `stack authorized by ApiClient#stack_id == stack read by CCMenuController#show`. After the change (override of `stack`), this equality is broken: the left side is "any stack, if `current_api_client.stack_id` is nil, or exactly `current_api_client.stack_id` otherwise", while the right side becomes "whatever `stack_id` param the caller supplies," entirely independent of the token's actual scope.

### Impact Explanation
An `ApiClient` token that was deliberately minted scoped to a single stack (e.g. via `Shipit::CcmenuUrlController#client`, which creates a `read:stack`-only, single-stack-scoped client) can be replayed against `GET /api/*stack_id/ccmenu` for *any other* `stack_id`, not just the one it was issued for: [4](#0-3) 

This discloses cross-stack build/deploy state (last build status/label/time, lock status) that the token holder was never authorized to see — an unauthenticated-scope read of stack state across repository/stack boundaries, matching the "High — unauthorized read of stack state" impact category.

### Likelihood Explanation
Exploitation only requires possessing any valid, stack-scoped `ApiClient` token with `read:stack` permission (these tokens are handed out routinely, e.g. embedded in CCMenu/CCTray URLs shared with CI dashboards) and knowledge/guessing of another stack's `stack_id` (`owner/repo/env` or numeric id), which are not secret. No privileged account, GitHub credentials, or session is needed beyond the token itself, satisfying the "unprivileged attacker" requirement for this class of finding.

### Recommendation
Remove the `stack` override in `CCMenuController`, or make it call the inherited scoped `stacks.from_param!(params[:stack_id])` (or otherwise explicitly re-check `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`) so the CCMenu endpoint enforces the same per-client stack binding as the rest of the API base controller.

### Proof of Concept
1. Create (or obtain) a stack-scoped, `read:stack`-only `ApiClient` for `stack A` (as `CcmenuUrlController#client` does).
2. Using that client's `authentication_token`, issue: `GET /api/<owner>/<name>/<env-for-stack-B>/ccmenu?token=<token>`.
3. `authenticate_api_client` in `CCMenuController` accepts the token via query string and authenticates the client successfully.
4. `require_permission :read, :stack` passes because the client does hold `read:stack`.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` directly against stack B, ignoring `current_api_client.stack_id` (which points to stack A).
6. The CCTray XML for stack B (build status, label, lock state) is returned to a caller whose token was never authorized for stack B.
