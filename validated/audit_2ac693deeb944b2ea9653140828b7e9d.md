### Title
Cross-organization deploy trigger via mismatched signature-verification org vs. handler-selected repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner`, parsed from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, every webhook `Handler` (e.g. `PushHandler`) resolves the target `Stack`/`Repository` using a *different* field from the same JSON body: `payload.dig('repository', 'full_name')`. Nothing in the code enforces that `repository.owner.login` (the field whose value selects the verifying secret) is consistent with the owner portion of `repository.full_name` (the field whose value selects the repository actually acted upon).

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`verify_signature` calls `Shipit.github(organization: repository_owner)` to pick the correct per-organization webhook secret (Shipit explicitly supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, as documented in `docs/setup.md` "Using Multiple Github Applications"), then verifies the raw body HMAC against that secret: [2](#0-1) 

If the signature is valid, `create` dispatches the parsed `params` to every registered handler for the event: [3](#0-2) 

Every handler, however, determines which `Repository`/`Stack` to operate on using `payload.dig('repository', 'full_name')`, not `repository.owner.login`: [4](#0-3) 

e.g. `PushHandler#process` triggers `stack.sync_github` (which can advance branch HEAD and kick off deploy pipelines) for whatever stacks match that `full_name`: [5](#0-4) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks the record up — there is no cross-check against the `owner.login` field used for signature verification: [6](#0-5) 

Since a webhook signature is an HMAC over the *entire raw JSON body*, a party who legitimately controls a webhook secret for organization B (their own GitHub App installation, configured in Shipit's multi-org `github:` secrets block) can construct and sign an arbitrary payload themselves (not necessarily relayed by GitHub) where `repository.owner.login = "orgB"` (so `verify_signature` resolves and validates against organization B's secret) while `repository.full_name = "orgA/some-repo"` (a repository belonging to a *different* organization configured in the same Shipit instance). The signature check only binds the payload to *a* valid secret holder; it never binds the *identity that authenticated* (`orgB`) to the *repository that is actually written to* (`orgA/some-repo`).

This breaks exactly the binding class called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
An org B webhook-secret holder can forge signed webhook events that are processed as if they originated from org A's repository, causing handlers to act on org A's stacks:
- `PushHandler` can trigger `stack.sync_github` / re-deployment flows on org A's `Stack` for a branch push that never happened.
- `StatusHandler`, `CheckSuiteHandler`, and the various `PullRequest::*Handler`s can create/archive Review Stacks, flip commit CI statuses used as deploy gates, and mutate pull-request state tracked by Shipit for org A's repositories — all without ever needing org A's webhook secret, GitHub identity, or Shipit session.

Because CI status webhooks can gate `deploy`/rollback logic elsewhere in the engine, forged status/push events can be used to manipulate deploy eligibility or falsely mark repositories synced, which can facilitate an unauthorized deploy — matching the "unauthorized deploy" Critical impact category, or at minimum the High "escalation" category for cross-tenant state tampering.

### Likelihood Explanation
Exploitability depends on the deployment being configured for multiple GitHub organizations (explicitly supported and documented) and on the attacker legitimately holding a webhook secret for *any one* of those organizations. This is a realistic multi-tenant Shipit deployment scenario: an org admin who is authorized to configure/own the GitHub App for their own org is not privileged with respect to *other* orgs hosted on the same Shipit instance, yet can reach every stack across every configured org because the repository-selection field is never validated against the authenticating organization.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select/verify the webhook secret matches the owner segment of `payload.dig('repository', 'full_name')` (and/or `organization.login`) before dispatching to handlers — reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per the documented multi-org `github:` secrets format).
2. As an attacker who controls `orgB`'s GitHub App / webhook secret, craft a JSON body for a `push` event:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/target-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgB_webhook_secret, raw_body)>`.
4. POST this body directly to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgB")` and successfully verifies the signature against `orgB`'s secret.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgA/target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on org A's stack — an action the attacker (an org B secret holder) has no legitimate authority over.
