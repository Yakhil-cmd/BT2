### Title
Session fixation on GitHub OAuth callback — session ID not regenerated on login ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` establishes an authenticated session by writing `session[:user_id]` (and `session[:authenticated] = true`) directly into whatever session the requesting browser already has, without ever calling `reset_session` to rotate the session identifier at the authentication boundary.

### Finding Description
The callback action is:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
``` [1](#0-0) 

Contrast this with the other place the engine explicitly resets the session when moving between trust levels — `force_github_authentication` calls `reset_session` before redirecting a user who "requires a fresh login":
```ruby
if current_user.logged_in? && current_user.requires_fresh_login?
  Rails.logger.warn(...)
  reset_session
  redirect_to(...)
``` [2](#0-1) 

The engine relies on `session[:user_id]` alone to identify `current_user` for the rest of the app:
```ruby
def find_current_user
  session[:user_id].present? && User.find_by(id: session[:user_id])
end
``` [3](#0-2) 

The binding being broken here is: *the pre-authentication session identifier issued to an anonymous visitor* is treated as equivalent to *the session identifier that is subsequently trusted to represent the authenticated GitHub identity*, with no rotation between the two states. If an attacker can get a victim's browser to carry a session cookie that is known/controllable by the attacker (a classic fixation setup — e.g. the attacker visits the app first to obtain a valid session cookie value, then plants that cookie in the victim's browser through any of the usual delivery mechanisms for a shared/writable cookie jar), the completed OAuth login for the victim will be written into that same session record. The attacker, already holding the session identifier, then has an authenticated Shipit session bound to the victim's GitHub identity — without ever knowing the victim's GitHub credentials.

### Impact Explanation
This matches the "session fixation / forced OAuth completion" High-impact category. If successfully fixated, the attacker inherits the victim's authenticated Shipit session, which means gaining `current_user`'s authorization level, including whatever `Shipit.github_teams` scoped access the victim holds (per `authorized?`): [4](#0-3) 
This could let an unprivileged outsider ride into a session that is authorized to view stack/task state and, depending on team assignment, trigger deploys/rollbacks — an escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Exploitability depends heavily on the deployment's session cookie configuration (domain scope, `SameSite`, secret_key_base rotation policy) and on the availability of a cookie-fixation delivery vector, which are host/application concerns outside this engine's code. Within the engine itself, however, the root cause is concrete and verifiable: there is exactly one place session identity is minted after third-party authentication, and it does not rotate the session ID, while the codebase demonstrates elsewhere (`force_github_authentication`) that it is aware `reset_session` is the correct control at authentication-state transitions.

### Recommendation
Call `reset_session` (or otherwise rotate/regenerate the session ID) in `GithubAuthenticationController#callback` immediately before assigning `session[:user_id]`, mirroring the pattern already used in `Shipit::Authentication#force_github_authentication`.

### Proof of Concept
Conceptual (session-fixation) PoC, since exploitation also depends on a cookie-delivery vector outside this engine:
1. Attacker visits the Shipit instance anonymously and records the session cookie value `S` issued by the app.
2. Attacker causes the victim's browser to adopt session cookie `S` (e.g., via a shared/writable cookie jar for the app's domain).
3. Victim completes the GitHub OAuth flow (`GET /github/auth/github/callback`); the controller sets `session[:user_id] = victim.id` on the same session record `S`, without regenerating the session ID: [1](#0-0) 
4. Attacker reuses cookie `S` and is now recognized as `current_user == victim` by `find_current_user`: [3](#0-2)
