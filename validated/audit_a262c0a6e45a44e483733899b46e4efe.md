## Analog Found: L1 BTC lockup proof has no global replay protection — the same Bitcoin UTXO can be credited to multiple pox-5 bonds

### Title
Missing global nonce/registry for L1 lockup outpoints lets a single Bitcoin UTXO be credited to multiple pox-5 bonds - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path accepts a Merkle/SPV proof of a Bitcoin output locked into pox-5's canonical timelock script and credits `sats-total` (and a matching `amount-ustx` STX lock plus signer reward-slot weight) to the caller. The only duplicate-outpoint check (`seen-outpoints`) is scoped to a single call's `fold`, and is discarded once that call returns. There is no persistent, contract-level map recording which Bitcoin outpoints have already been consumed.

### Finding Description
`verify-l1-lockups` seeds the fold accumulator with an empty `seen-outpoints: (list)` on every invocation: [1](#0-0) 

`validate-l1-lockup` checks the outpoint against that per-call list and appends to it, but never persists it to contract storage: [2](#0-1) [3](#0-2) 

A `grep` across the repo for a persistent used-outpoint registry (`used-l1-outpoints`, `l1-outpoint`, `used-lockup`, etc.) found no matches outside this one function, confirming no such map exists.

The validations performed (unlock-height floor, BIP113 locktime threshold, expected script hash, amount match, block-header PoW/height check, Merkle inclusion proof) all prove that a *specific Bitcoin transaction output* exists and matches the canonical timelock script for `tx-sender`. None of them prove the output has not already been used to back a previous `register-for-bond` call. Consequently, an attacker who owns (or has ever seen) a valid `{height, tx, output-index, header, leaf-hashes, tx-count, tx-index, amount, unlock-burn-height}` tuple for a real on-chain lockup can submit that identical tuple in a second (and third, ...) `register-for-bond` call — from a different allow-listed staker principal, or from the same staker after exiting a bond and re-registering — and pox-5 will credit `sats-total` again, locking a fresh `amount-ustx` STX position and minting fresh signer-manager reward-slot weight, backed by BTC that was locked exactly once.

This is the direct analog of the reported CWE-22 class: a value derived from user-supplied, structurally-valid input (a path in the CVE; here, a Bitcoin outpoint proof) is trusted without checking it against previously-consumed state, letting the same underlying resource be consumed/credited more than once.

### Impact Explanation
Each successful replay locks additional STX (`amount-ustx`) and grants additional bond/sBTC reward-slot share (`sats-total`) without any additional BTC ever being locked. This double-counts a commitment that maps directly to sBTC/BTC-backed reward entitlement and signer reward-slot weight — Critical per the rules ("theft or unbacked minting of ... sBTC rewards ... double-counting a commitment or reward"). The staker's real STX must still be genuinely transferred/locked for each replay (the `amount-ustx` STX check in `register-for-bond` is real), but the sats-backing claim (`is-l1-lock: true`, `amount-sats: sats-total`) used for reward/allowance accounting is duplicated against a single BTC lock, and the STX->sats accounting invariant ("uSTX locked must correspond to sats actually locked on L1") is broken.

### Likelihood Explanation
The proof material (block header, Merkle path, raw tx) required to satisfy `validate-l1-lockup` is fully public once the Bitcoin lockup transaction confirms — none of the fields are secret or single-use tokens. Any allow-listed staker (their own principal must be in `protocol-bond-allowances`/`allowlist`, and the script is bound to `tx-sender`, so the *same* staker principal is required to reuse their own lockup proof) can trivially replay their own already-submitted proof for a second bond as long as they are allow-listed for it (e.g., after an early exit, or if allow-listed for multiple concurrent bond periods). This requires no admin, miner, or other user's key — only the attacker's own previously-submitted, still-public proof — so it is directly reachable by an unprivileged account.

### Recommendation
Add a persistent map, e.g. `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`, and in `validate-l1-lockup` assert `(map-insert used-l1-outpoints outpoint true)` (failing with a new `ERR_LOCKUP_OUTPOINT_ALREADY_USED` on `false`) instead of/in addition to the per-call `seen-outpoints` list, so a given Bitcoin outpoint can only ever back one `register-for-bond` call across the contract's lifetime.

### Proof of Concept
1. Staker A locks `N` sats into the canonical pox-5 timelock P2WSH script committed to their principal (real Bitcoin tx, output `O`).
2. Staker A calls `register-for-bond(bond-index=0, ..., btc-lockup=ok({outputs:[proof(O)], ...}))`. `verify-l1-lockups` validates the SPV proof and credits `sats-total = N`; bond membership is created with `amount-sats: N`, `is-l1-lock: true`.
3. Staker A's bond ends (or A is separately allow-listed on bond-index=6). A calls `register-for-bond(bond-index=6, ..., btc-lockup=ok({outputs:[proof(O)]}))` reusing the identical proof tuple for the *same still-locked* Bitcoin output `O`.
4. `verify-l1-lockups`/`validate-l1-lockup` re-validate the same header/Merkle proof/script/amount successfully (nothing in the checked fields depends on prior contract state), `sats-total = N` is credited again, and bond-index 6 records `amount-sats: N` — a second, independent sats-backed bond membership funded by the same single Bitcoin UTXO.
