### Title
Cross-stack commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha` across the entire `commits` table and writes the webhook's raw `state`/`context`/`description` fields into `create_status_from_github!`, with no check that the sha actually belongs to the stack/repository that sent the webhook. This differs fundamentally from `Commit#refresh_statuses!`, which only ever writes statuses that were freshly re-fetched from `stack.github_api.statuses(github_repo_name, sha, ...)` — i.e., scoped to the owning stack's own repository.

### Finding Description
The broken binding: for a status written via the webhook path, `status.written_content == params (attacker-controlled)` should equal `status.written_content == stack.github_api.statuses(stack.github_repo_name, sha)` (the authoritative source), but it does not.

`StatusHandler#process` does: [1](#0-0) 
It queries `Commit.where(sha: params.sha)` with no repository/stack filter, then calls `commit.create_status_from_github!(params)` directly using attacker-supplied `state`, `description`, `target_url`, and `context` from the webhook body — never re-fetching from GitHub.

The base `Handler` class exposes a `stacks` helper scoped to the payload's `repository.full_name`: [2](#0-1) 
`StatusHandler` does not use it, unlike the pattern implied for other handlers.

By contrast, `Commit#refresh_statuses!` guarantees provenance because it re-fetches from the commit's own stack's API before writing: [3](#0-2) 
and `RefreshStatusesJob#perform` only ever calls `refresh_statuses!` on a single, already-resolved `Commit`: [4](#0-3) 

**Root cause / exploit flow**: `verify_signature` in `WebhooksController` validates the HMAC signature using the webhook secret configured for `repository_owner` taken from the attacker's own JSON body: [5](#0-4) 
Because the signature check only proves "this body was signed with the secret belonging to the org named in `repository.owner.login`," an attacker who legitimately controls **any one Shipit-configured repository** (their own throwaway repo/org onboarded to Shipit) can send a validly-signed `status` event whose JSON body sets `sha` to a commit SHA belonging to a **different, unrelated stack** (SHAs are public — visible via git history, GitHub UI, or the Shipit UI itself). Since `Commit.where(sha: params.sha)` matches by sha alone across the whole table, the forged `state`/`context`/`description` gets written onto that unrelated commit via `create_status_from_github!` → `add_status`, which can flip `deployable?`, trigger `Hook.emit(:deployable_status, ...)`, and call `stack.schedule_merges`/`ContinuousDeliveryJob` for a stack the attacker has no relationship to. [6](#0-5) [7](#0-6) [8](#0-7) 

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) check that the sha belongs to the repository named in the payload; they only validate signature and shape, not cross-tenant scoping.

### Impact Explanation
A payload legitimately signed for repository A can forge a "success"/passing CI status on a commit belonging to stack B (any other stack in the same Shipit instance), because status resolution is keyed only on `sha`, not on `(stack, sha)`. If the SHA coincides with a required/blocking status context on stack B, this can make an otherwise-blocked commit `deployable?` and, combined with continuous deployment, trigger an unauthorized deploy of another tenant's stack — matching "a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy" (Critical). This is repeatable against any stack/commit whose SHA the attacker can learn, and the attacker only needs write access (or even just push access producing webhook traffic) to any single onboarded repository.

### Likelihood Explanation
Precondition: the attacker must control (or have signing rights over) at least one repository already registered as a Shipit stack, which is a low bar relative to the definition of "unprivileged" in this audit (any GitHub user able to emit webhooks from a repo they own, provided that repo participates in this Shipit instance). Commit SHAs are not secret. No Shipit session, API token, or `webhook_secret` of the *victim* org needs to be known — only a legitimately signed webhook from the attacker's own configured org, whose body content is otherwise fully attacker-controlled JSON. This is straightforward and repeatable.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to the stacks associated with the webhook's own `repository.full_name`, using the existing `stacks` helper on `Handler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a commit can only receive a forged status if it belongs to a stack whose repository matches the authenticated webhook's repository.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually — not to be created by this audit but proposed):
1. Create `stack_a` for `repo_a`, `stack_b` for `repo_b`.
2. Create `commit_b` under `stack_b` with `sha: "deadbeef"`.
3. Build a `status` webhook payload with `repository.full_name = "repo_a/repo_a"`, `sha: "deadbeef"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_b.reload.statuses.last.state == "success"` even though the payload's `repository` was `repo_a`, proving cross-stack write with no re-fetch from `stack_b.github_api`.
6. Contrast: stub `stack_b.github_api.statuses(stack_b.github_repo_name, commit_b.sha)` to return an empty/failure list and call `commit_b.refresh_statuses!`; assert the resulting status matches only the stubbed API response, never the webhook's forged `state`, proving `refresh_statuses!`/`RefreshStatusesJob` is correctly stack-scoped while `StatusHandler#process` is not.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
