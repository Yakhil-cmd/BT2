### Title
Signature verification is keyed on `repository.owner.login`/`organization.login` while webhook handlers act on the unrelated `repository.full_name` field, letting a blank-secret org's identity authorize writes against any other tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate a webhook exclusively from `repository.owner.login`, falling back to `organization.login`, both attacker/GitHub-supplied JSON fields read *before* the signature is checked: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly treats a blank/unconfigured `webhook_secret` as automatically verified: [3](#0-2) 

Once "verified", `WebhooksController#create` dispatches the entire raw JSON `params` to handlers: [4](#0-3) 

Critically, the handlers do **not** use the field that was checked for authentication (`repository.owner.login` / `organization.login`). Instead, `Handler#stacks` and `Handler#repository_name` resolve the target `Repository`/`Stack` from a completely different payload field, `repository.full_name`: [5](#0-4) 

`PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` on every matching stack, and `StatusHandler` writes commit statuses for whatever `sha` is supplied, purely based on that mismatched `stacks` lookup: [6](#0-5) [7](#0-6) 

This is structurally the same class of bug as the report: the invariant that should hold — "the entity whose credential authenticated the request equals the entity the request is permitted to mutate" — is never asserted. Here the equality that should be enforced is:
`organization used to select/verify webhook_secret == organization prefix of repository.full_name acted on by the handler`
but no such check exists anywhere in `WebhooksController` or `Handler`.

In Shipit's documented multi-org configuration (`config/secrets.*.yml`, `TOP_LEVEL_GH_KEYS`/`github_app_config` in `lib/shipit.rb`), each organization can have its own `webhook_secret`, and that field is explicitly optional (`webhook_secret: # nil` in every example file): [8](#0-7) [9](#0-8) 

If any one configured organization is left with no `webhook_secret` (a supported, documented configuration state, not an operator error the engine warns against), `verify_webhook_signature` returns `true` unconditionally for that organization regardless of the actual signature header. Because `repository_owner`/`organization.login` (used only for secret selection) and `repository.full_name` (used for the actual write) are independent, unrelated JSON keys in the same unauthenticated request body, a request whose `organization.login`/`repository.owner.login` names the no-secret org, but whose `repository.full_name` names a tracked repository belonging to a *different, properly secured* organization, sails through `verify_signature` and is then fully processed against the other org's real stack.

### Impact Explanation
This breaks the deployment-trust binding "the organization that authenticated the webhook == the repository whose stacks are written," matching the Critical criteria: it allows cross-repository/cross-organization writes triggered by an unauthenticated request — e.g., forcing `PushHandler` to invoke `stack.sync_github` (queues Git sync / merge-queue re-evaluation) or `StatusHandler` to inject arbitrary/forged commit statuses (`commit.create_status_from_github!`) onto a victim organization's tracked commits, all without ever supplying that victim organization's `webhook_secret`.

### Likelihood Explanation
This requires no session, `ApiClient` token, or the victim's `webhook_secret`. It only requires that Shipit's operator has configured multiple GitHub organizations (a documented, supported deployment mode) and left `webhook_secret` blank for at least one of them (also a documented, supported state — every example secrets file in this engine ships with `webhook_secret: # nil`). Given the engine explicitly documents and supports this combination without warning against the cross-org exposure, likelihood is realistic in any multi-tenant Shipit deployment that hasn't set a secret on every single configured org.

### Recommendation
Enforce the missing invariant explicitly: after resolving the `GitHubApp` used to verify the signature, re-derive the repository/organization actually referenced by the payload (`repository.full_name`) and assert its owner matches the `repository_owner`/`organization.login` used for verification, rejecting the request otherwise. Alternatively, stop allowing per-organization webhook secrets to be blank when running in the multi-org configuration mode, or require a single global secret validated independent of any payload-derived field before organization-specific dispatch.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, e.g. in `config/secrets.yml`:
```yaml
production:
  github:
    AttackerOrg:
      app_id: ...
      installation_id: ...
      webhook_secret:        # left blank
      private_key: ...
    VictimOrg:
      app_id: ...
      installation_id: ...
      webhook_secret: a-real-secret
      private_key: ...
```
2. VictimOrg has a tracked `Stack` for `VictimOrg/app`.
3. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "AttackerOrg" },
  "repository": { "full_name": "VictimOrg/app", "owner": { "login": "AttackerOrg" } },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
No `X-Hub-Signature` (or any garbage value) is required.
4. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` per `app_github_app.rb:76-77` [10](#0-9) .
5. `WebhooksController#create` dispatches the payload to `PushHandler`, which resolves `stacks` via `repository.full_name = "VictimOrg/app"` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: ...)` on VictimOrg's real stack — all without ever knowing VictimOrg's actual `webhook_secret`.

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
