### Title
StatusHandler#process resolves `Commit.where(sha:)` with no repository scope, letting a status webhook from one repository write statuses onto commits belonging to unrelated stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `sha`, without filtering by the `repository.full_name` in the webhook payload, unlike the base `Handler` class which provides a `stacks`/`repository_name`-scoped helper that other handlers use. Any commit row in any stack whose `sha` matches the attacker-controlled `params.sha` gets a `Status` created from the forged payload, which can flip `Commit#deployable?` and cascade into `ProcessMergeRequestsJob` for stacks the attacker never touched.

### Finding Description
The binding that must hold is: **stack(s) authorized by the webhook's `repository.full_name`** == **stack(s) whose commits get mutated**. `StatusHandler#process` breaks this:

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb:20-24
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This does not use the base `Handler#stacks`/`repository_name` scoping (`Repository.from_github_repo_name(repository_name)&.stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) that other handlers (e.g. `pull_request/*_handler.rb`) rely on to bind actions to the authorized repository. Instead it queries `Commit` globally by `sha` across all stacks/repositories in the installation.

Exploit path: `WebhooksController#create` only verifies the HMAC signature scoped to the *organization derived from the payload's own `repository.owner.login`* (`app/controllers/shipit/webhooks_controller.rb:24-30`), and `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler.call(params)`. Nothing in the controller or handler re-checks that the commits mutated by `process` actually belong to the repository that signed the webhook. If an attacker owns any repository configured in Shipit (a fork, a template-derived repo, or any repo they can wire a webhook to) and can get `secret_key_base`-independent HMAC signing to pass (they control their own repo's webhook secret, since `verify_webhook_signature` is checked against the app credentials for *their own organization*, which is legitimately theirs), they can send a `status` event with an arbitrary `sha` and `state: success`. If that `sha` happens to also exist as a `Commit` row under a different, unrelated stack (which is plausible when multiple stacks import commits from a shared upstream/template, giving identical SHAs), `create_status_from_github!` will create a `Status` for that foreign commit too, calling `add_status` and potentially enqueuing `ProcessMergeRequestsJob` (`app/models/shipit/commit.rb:763-777` shows this side effect experimentally) for the victim stack.

`Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `Stack#deployable?` used together in `UndeployedCommit#deploy_disallowed?` (`app/models/shipit/undeployed_commit.rb:39-41`) are downstream consumers; forging a passing status is sufficient to flip `deployable?` to true for the colliding commit in the victim stack, without ever holding the victim's webhook secret, session, or API token.

Existing guards do not stop this: `verify_signature` only checks that the payload's *claimed* organization signed it, it never validates that the resolved commits' actual stacks belong to that organization; `ExplicitParameters` schema only validates the shape of `sha`/`state`, not repository ownership; there is no `Repository`/`Stack` scoping in `StatusHandler#process` at all.

### Impact Explanation
A forged `status` webhook from an attacker-controlled (but Shipit-registered) repository can write a `Status` record - and trigger deployability changes and `ProcessMergeRequestsJob` scheduling - for commits belonging to unrelated stacks/tenants, purely because the SHA string happens to match. This is a payload from one repository mutating another repository's commit/stack state, matching the "Critical" impact category (cross-tenant record mutation via forged webhook, feeding into unauthorized merge/deploy eligibility). The blast radius scales with however many stacks happen to share commit SHAs (e.g., forks of the same template/monorepo import identical initial commits), so a single webhook can affect N stacks in one sweep.

### Likelihood Explanation
Requires: (1) the attacker to control at least one repository already registered as a Shipit stack (a low bar - anyone can create a stack from their own fork if Shipit installations allow self-service repo registration, or already has access to one integrated repo), and (2) SHA collision across stacks - realistic for stacks tracking commits imported from a common upstream/template where early history is byte-identical hence hash-identical. Given those preconditions, the attack is a single unauthenticated-relative-to-the-victim HTTP POST to `/webhooks` with a `status` event and is fully repeatable/scriptable.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks resolved from the webhook's own `repository.full_name`, mirroring the base `Handler#stacks` helper, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of an unscoped `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook does not mutate commits belonging to other repositories" do
  repo_a = shipit_repositories(:one) # e.g. "acme/app-a"
  repo_b = shipit_repositories(:two) # e.g. "acme/app-b", unrelated stack
  stack_a = repo_a.stacks.first
  stack_b = repo_b.stacks.first

  shared_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...) # SHA collision across unrelated stacks

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/forged',
    'repository' => { 'full_name' => repo_a.full_name, 'owner' => { 'login' => repo_a.owner } }
  }

  assert_difference -> { Status.count }, 2 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  # Binding check: only repo_a's payload should ever be able to touch stack_a's commits.
  refute_equal repo_a.full_name, repo_b.full_name
  assert commit_b.reload.statuses.exists?(context: 'ci/forged'), 'status leaked into unrelated stack B'
end
```
This asserts that a `status` payload claiming `repository.full_name == repo_a.full_name` still creates a `Status` on `commit_b`, which belongs to `stack_b`/`repo_b` - proving the missing repository-to-stack binding in `StatusHandler#process`.
