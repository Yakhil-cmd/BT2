### Title
Webhook signature verification is keyed on `repository.owner.login` while the event handlers act on the unverified `repository.full_name`, allowing cross-organization webhook forgery in multi-tenant deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a direct analog of the reported accounting bug: two related quantities that should stay bound together are computed from independent, attacker-controllable fields. Just as the audited contract measured "available liquidity" from a value (`flowLimiter.getFlowLimit`) that isn't backed by the same accounting unit as `balanceOf`, Shipit's webhook pipeline picks *which secret to verify the signature with* from one field of the payload (`repository.owner.login` / `organization.login`) but then dispatches the *actual write operation* (push sync, status update, check-suite refresh) using a different field of the same, attacker-supplied payload (`repository.full_name`). Nothing binds these two fields together.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration (and thus the HMAC secret used to validate `X-Hub-Signature`) purely from the JSON body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is derived exclusively from `params.dig('repository','owner','login')` or the `organization.login` fallback. This is fed into `Shipit.github(organization: repository_owner)`, which for a multi-org install looks up a per-organization webhook secret: [3](#0-2) 

Once the signature is accepted, the same raw payload is dispatched to handlers, but those handlers determine *which repository/stack to act on* from a completely different key, `repository.full_name`: [4](#0-3) 

For example, `PushHandler` finds all stacks for the branch of that repository and immediately syncs/deploys: [5](#0-4) 

Because the signature only proves "this payload was signed with organization X's secret" and organization X is picked from `repository.owner.login`, an attacker who legitimately possesses the webhook secret for *their own* configured organization (a normal, unprivileged tenant in a shared/multi-org Shipit instance, as explicitly supported by `config/secrets.development.example.yml` and `docs/setup.md`) can craft a payload where:
- `repository.owner.login` = their own org (so `verify_signature` selects their own known secret and the HMAC check passes), and
- `repository.full_name` = `victim-org/victim-repo` (an entirely different, unrelated stack tracked by the same Shipit instance).

The equality that should hold — "organization whose secret authenticated the request" == "repository the handler writes state for" — is broken. The webhook body itself, not any Shipit-verified identity, decides which stack is affected.

### Impact Explanation
If the attacker knows a valid full sha the target stack would accept (or simply lets the push handler resolve `HEAD` via `sync_github`/`GithubSyncJob`, which calls back out to GitHub using the app's own installation token — not attacker-controlled data), they can trigger a `GithubSyncJob`/`sync_github` for a victim repository they do not own, and if `continuous_deployment` is enabled on that victim stack, this results in an unauthorized deploy being triggered by a forged webhook from an unrelated, unprivileged tenant. `status` and `check_suite` handlers similarly write commit status / check-run state for a stack the attacker doesn't own. This reaches the Critical bar of "cross-repository writes / unauthorized deploy" without requiring any Shipit session, `ApiClient` token, or GitHub write access to the victim repository — only knowledge of a webhook secret belonging to any one organization configured on the shared Shipit instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a documented, supported configuration in `config/secrets.development.example.yml`/`docs/setup.md`) where the attacker's own org is one of the configured tenants. Given that, forging the payload is trivial: compute HMAC-SHA1 over the crafted JSON body using the attacker's own known webhook secret and set the two fields independently.

### Recommendation
Bind the verification and processing paths to the same authenticated identity: after selecting the GitHub App/secret via `repository_owner`, re-derive `repository_owner` from `repository.full_name`'s owner segment (or vice versa) and reject the webhook (422) if they don't match. Alternatively, always verify with a secret tied to the resolved `Repository`/`Stack` (looked up by `full_name`) rather than a value chosen from an as-yet-unverified field of the same payload.

### Proof of Concept
1. Deploy Shipit with a multi-org `github` config, e.g. `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, tracked stack `orgB/victim-repo` with `continuous_deployment: true`).
2. Craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-repo-head-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `WebhooksController#verify_signature` resolves `repository_owner == "orgA"`, verifies the signature using `orgA`'s secret (attacker-known) — passes.
6. `Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository','full_name') == "orgB/victim-repo"`, an org the attacker has no relationship with, and triggers `sync_github`/deploy for it — [6](#0-5) [4](#0-3) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
