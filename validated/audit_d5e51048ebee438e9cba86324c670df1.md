### Title
Reentrancy via Unguarded External Call in `_requestERC721Transfer` Allows Bridge `requestNonce` Double-Consumption and Double-Spend of Bridged ERC721 Assets — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721._requestERC721Transfer` makes an external low-level call to the token contract (`_tokenAddress.call(tokenURI...)`) **before** incrementing `requestNonce`. The public `onERC721Received` entry point has no access control and no reentrancy guard. A registered malicious ERC721 token whose `tokenURI` function reenters the bridge via `onERC721Received` can cause two `RequestValueTransferEncoded` events to be emitted with consecutive nonces for a single token deposit, causing bridge operators to release two tokens on the counterpart chain for one deposited token.

---

### Finding Description

In `_requestERC721Transfer` (lines 86–105), the execution order is:

1. **External call 1** — low-level `_tokenAddress.call(tokenURI selector + tokenId)` (line 86)
2. **External call 2** — `ERC721Burnable(_tokenAddress).burn(_tokenId)` in mintBurn mode (line 91)
3. **State write** — `requestNonce++` (line 105)

`BridgeTransferERC721` does not inherit `ReentrancyGuard` and neither `requestERC721Transfer` nor `onERC721Received` carries a `nonReentrant` modifier. Compare this with `BridgeTransferKLAY`, which explicitly applies `nonReentrant` to both `handleKLAYTransfer` and `_requestKLAYTransfer`.

`onERC721Received` is `public` with no access control:

```solidity
function onERC721Received(address _from, uint256 _tokenId, address _to, bytes memory _extraData)
    public
{
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
```

`msg.sender` becomes the `_tokenAddress` passed to `_requestERC721Transfer`. The only guard is `onlyRegisteredToken(msg.sender)`, which passes for any registered token.

**Reentrant call chain (non-mintBurn / lock mode):**

1. Attacker calls `requestERC721Transfer(MaliciousNFT, to, tokenId, data)`.
2. Bridge calls `MaliciousNFT.transferFrom(attacker, bridge, tokenId)` — bridge now holds the token.
3. Bridge calls `_requestERC721Transfer(MaliciousNFT, attacker, to, tokenId, data)`.
4. Bridge executes `MaliciousNFT.call(tokenURI(tokenId))` — **external call before state write**.
5. Malicious `tokenURI` calls `bridge.onERC721Received(attacker, tokenId, to, data)`.
6. `onERC721Received` calls `_requestERC721Transfer(MaliciousNFT, ...)` — **reentrant entry**.
7. Reentrant execution: `requestNonce = N` → emits `RequestValueTransferEncoded(nonce=N)` → `requestNonce = N+1`.
8. Outer execution resumes: `requestNonce = N+1` → emits `RequestValueTransferEncoded(nonce=N+1)` → `requestNonce = N+2`.

Two events with distinct nonces are emitted for one deposited token.

---

### Impact Explanation

Bridge operators on the counterpart chain observe both `RequestValueTransferEncoded` events and submit two `handleERC721Transfer` transactions. Each passes the `_lowerHandleNonceCheck` and `_voteValueTransfer` guards independently (different nonces, different `keccak256(msg.data)` vote keys). Both are executed, releasing or minting two tokens on the counterpart chain for one token deposited on the source chain. This is an unauthorized mint/transfer of bridged ERC721 assets — a direct double-spend of bridge-managed funds.

---

### Likelihood Explanation

Requires a registered malicious ERC721 token whose `tokenURI` implementation reenters the bridge. Token registration is controlled by the bridge owner, making this a semi-trusted trigger. However, the bridge is designed to support arbitrary ERC721 tokens, and `tokenURI` is not expected to have side effects, making this a realistic attack surface for a malicious or compromised token owner. The `onERC721Received` entry point is fully public with no caller restriction, lowering the bar once a registered token is involved.

---

### Recommendation

1. Add `nonReentrant` to `requestERC721Transfer` and `onERC721Received` (or to `_requestERC721Transfer` itself), mirroring the pattern already used in `BridgeTransferKLAY`.
2. Move `requestNonce++` to before any external calls (checks-effects-interactions pattern).
3. Consider restricting `onERC721Received` to only accept calls from registered token contracts.

---

### Proof of Concept

```solidity
// MaliciousNFT — registered with the bridge by its owner
contract MaliciousNFT is ERC721Metadata, ERC721Burnable {
    address bridge;
    bool reentered;

    function tokenURI(uint256 tokenId) external view returns (string memory) {
        if (!reentered) {
            reentered = true;
            // Reenter bridge: msg.sender in onERC721Received will be address(this)
            IBridgeERC721(bridge).onERC721Received(
                tx.origin, tokenId, victim, ""
            );
        }
        return "";
    }
}

// Attack:
// 1. MaliciousNFT is registered with bridge (bridge.registeredTokens[MaliciousNFT] == true)
// 2. Attacker mints tokenId=1 to themselves
// 3. Attacker approves bridge for tokenId=1
// 4. Attacker calls bridge.requestERC721Transfer(MaliciousNFT, victim, 1, "")
//
// Result: two RequestValueTransferEncoded events emitted (nonce=0, nonce=1)
// Bridge operators process both → victim receives two tokens on counterpart chain
// for one token deposited on source chain.
```
