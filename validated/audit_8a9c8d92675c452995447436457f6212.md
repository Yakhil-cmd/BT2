### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name` field, letting an admin of one configured GitHub org forge writes against a different org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multiple independently-configured GitHub Apps/organizations in a single deployment, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects *which* organization's secret to verify the HMAC signature against using a field taken directly from the untrusted, attacker-suppliable JSON body (`repository.owner.login`, falling back to `organization.login`), then verifies the raw body against that org's secret [2](#0-1) . Once verification passes, every webhook handler resolves the actual repository/stack to mutate using a *different* field from the very same body: `payload.dig('repository', 'full_name')` [3](#0-2) , reused identically across `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `EditedHandler`, `ReopenedHandler`, etc. [4](#0-3) [5](#0-4) .

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository/stack being written`. Because both `repository.owner.login` (used only to pick the verification key) and `repository.full_name` (used to pick the repository/stack to mutate) live inside the same attacker-controlled JSON payload, nothing forces them to refer to the same repository.

Any actor who legitimately administers **one** of the GitHub organizations configured in Shipit's `secrets.yml` (and therefore knows/controls that org's `webhook_secret`, e.g. `somegithuborg`) can craft an arbitrary payload where:
- `repository.owner.login` = `somegithuborg` (or `organization.login` = `somegithuborg`) — so `verify_signature` picks `somegithuborg`'s app/secret and the HMAC check succeeds, since the attacker computed it themselves.
- `repository.full_name` = `someothergithuborg/victim-repo` — a completely different, victim organization's repository that is also tracked by the same Shipit instance.

`verify_signature` never checks that the org used to select the key matches the org embedded in `full_name`; it simply calls `Shipit.github(organization: repository_owner)` and verifies the raw body [6](#0-5) . The dispatched handler then resolves `Repository.from_github_repo_name(params.repository.full_name)` and operates on whatever stack it finds [7](#0-6) , with zero further authorization tying the verified organization to the acted-upon repository.

This is structurally identical to the reported OffRamp bug class: the program (Shipit) treats a globally-reachable creation/action path as implicitly trustworthy because *some* signature/counter check passed, without binding the specific identity that passed the check to the specific resource being acted upon.

### Impact Explanation
Depending on which handler is reached, this allows a low-privileged party (admin of any one org onboarded to the shared Shipit instance) to manipulate a victim organization's stacks without ever having credentials for that org: archiving/unarchiving review stacks, closing/reopening/relabeling PRs tracked by Shipit, and — most severely — driving state transitions consumed by the merge queue and CI-status pipeline (`StatusChecker`, `MergeRequest#refresh!`/`merge!`) that gate automatic merges and deploys [8](#0-7) . Forged status/PR events for a repository the attacker does not own can push a pull request through the merge queue or otherwise trigger an unauthorized deploy/merge on the victim stack, matching the Critical "unauthorized deploy, rollback or merge" criterion.

### Likelihood Explanation
This requires the Shipit operator to actually run in the documented multi-org configuration (explicitly supported and documented) [1](#0-0) , and for the attacker to be a legitimate admin/maintainer of at least one of the configured orgs (i.e., someone who can set up a GitHub App webhook secret for their own org, not someone with no relationship to the Shipit instance at all). No Shipit session, `ApiClient` token, or GitHub App private key of the victim org is required — only knowledge of a secret the attacker legitimately possesses for their own org.

### Recommendation
After signature verification, enforce that the organization used to select the verifying key matches the owner encoded in `repository.full_name` (and any other identity fields the handlers consume) before dispatching to handlers — e.g. reject the webhook if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`. More generally, bind the verified organization to the specific `Repository`/`Stack` resolved by each handler rather than trusting attacker-controlled body fields independently.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two orgs: `somegithuborg` (attacker-administered) and `someothergithuborg` (victim), each with distinct `webhook_secret`.
2. Attacker crafts a `pull_request` `labeled` payload:
```json
{
  "action": "labeled",
  "number": 42,
  "pull_request": { "...": "...", "labels": [{"name": "pull-requests-label"}] },
  "repository": { "owner": {"login": "somegithuborg"}, "full_name": "someothergithuborg/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Attacker computes `X-Hub-Signature` using `somegithuborg`'s known `webhook_secret` over the raw JSON body and POSTs it to `/webhooks` with `X-Github-Event: pull_request`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: 'somegithuborg')`, verifies successfully (since attacker signed with that org's real secret) [6](#0-5) .
5. `LabeledHandler` resolves `Shipit::Repository.from_github_repo_name('someothergithuborg/victim-repo')` and archives/unarchives the victim's review stack [9](#0-8) , despite the request never being authenticated as belonging to `someothergithuborg`.

**File:** app/controllers/shipit/webhooks_controller.rb (L24-49)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
