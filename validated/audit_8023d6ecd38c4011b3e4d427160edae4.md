## Analog Analysis

### Binding broken
`organization authenticated by webhook signature (repository_owner in payload)` ≠ `repository/commit actually written by the handler`.

`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using only `params.dig('repository','owner','login')` (or `organization.login`) from the unauthenticated JSON body, then verifies the HMAC signature against that same body. [1](#0-0) 

Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* raw payload to handlers, and it is up to each handler to scope its writes to the repository that was actually authenticated. [2](#0-1) 

Most default handlers *do* scope correctly, by resolving `stacks` through `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — e.g. `Handler#stacks`, `PushHandler#process`, `CheckSuiteHandler#process`. [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does **not** use `stacks`/`repository_name` at all — it looks up commits globally by SHA across the entire installation: [6](#0-5) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This writes a `Status` record (`commit.create_status_from_github!`) onto *any* `Commit` row in the database whose `sha` matches the attacker-supplied `sha` field — completely independent of which organization/repository owned the verified webhook signature. [7](#0-6) 

### Why this matters
Commit statuses directly gate deployability: `Commit#deployable?` requires `success? && !blocked?`, and `status` is computed from `statuses_and_check_runs` (`Status::Group.compact`). [8](#0-7) [9](#0-8) 

If a shared Shipit instance hosts multiple GitHub organizations (a documented supported configuration — `config/secrets.yml` supports a per-organization `github:` map with independent `webhook_secret`s, and one org can legitimately be configured with **no** `webhook_secret`, in which case `verify_webhook_signature` returns `true` unconditionally: `return true unless webhook_secret`), an attacker who only controls a repository/organization on the Shipit host (a legitimate but unprivileged webhook sender for their own org) can send a forged `status` event whose top-level `sha` matches a real commit SHA belonging to an unrelated, higher-privilege stack, and inject a fabricated `success` status for it — pushing that unrelated commit toward becoming "deployable" and potentially triggering an unauthorized/continuous deploy via `schedule_continuous_delivery`. [10](#0-9) [11](#0-10) 

Even without a no-secret org, because SHA is a global, cross-repository lookup key with no organization/repository boundary check, this is a structural binding break in the handler itself, distinguishing it from `PushHandler`/`CheckSuiteHandler`/pull-request handlers which correctly scope by `repository.full_name`.

### Title
Cross-repository commit status spoofing via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by the attacker-controlled `sha` field from the webhook payload, without restricting the query to the repository/organization that the webhook signature was actually verified against. This breaks the trust binding between "the organization whose webhook signature was validated" and "the commit/repository whose CI status gets written," analogous to the smart-contract report's core issue of the executed operation ranging further than what was authenticated/verified.

### Finding Description
`WebhooksController#verify_signature` derives the GitHub App/secret to check the HMAC against solely from `params.dig('repository','owner','login')` in the unauthenticated JSON body, then dispatches the full payload to `Shipit::Webhooks.for_event(event)` handlers. Most handlers (`PushHandler`, `CheckSuiteHandler`, PR handlers) re-derive scope from `repository.full_name` via `Repository.from_github_repo_name`, ensuring writes stay within the authenticated repository. `StatusHandler` instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-repository, cross-organization lookup keyed only on the attacker-supplied `sha` string, with no repository/stack scoping at all.

### Impact Explanation
`Commit#create_status_from_github!` creates a `Status` row that feeds `Commit#status`/`#deployable?`, which gate `continuous_deployment` (`schedule_continuous_delivery`) and manual deploy eligibility. An attacker who is a legitimate webhook sender for one org/repo hosted on the same Shipit instance (or any org configured without a `webhook_secret`) can forge a `status` event carrying the `sha` of a commit belonging to a different, unrelated stack, injecting a fabricated `success` status and nudging that unrelated commit toward automatic/allowed deployment — an unauthorized-deploy-adjacent integrity break of CI gating across repository boundaries.

### Likelihood Explanation
Requires: (a) a multi-organization Shipit deployment (an explicitly documented, supported configuration) or an org configured with no `webhook_secret` (also explicitly supported/documented), and (b) knowledge of a target commit SHA in another hosted repository (SHAs are often public via GitHub). No privileged Shipit credentials, `ApiClient` token, or repository write access to the *target* repo are required — only the ability to fire a webhook event that passes signature verification for *some* configured organization.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook was authenticated for, mirroring `Handler#stacks`/`repository_name`, e.g. restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or otherwise join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before matching by SHA, rather than querying `Commit` globally.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` (attacker-controlled, webhook secret known/absent) and `OrgB` (victim, hosts the target stack), per the documented multi-org `secrets.yml` schema. [12](#0-11) 
2. Identify a real commit SHA on a stack under `OrgB` (e.g. via GitHub's public commit history).
3. Send `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login: OrgA`, and body `{"sha": "<OrgB commit sha>", "state": "success", ...}`, signed with `OrgA`'s webhook secret (or unsigned if `OrgA` has none).
4. `verify_signature` passes because it only checks `OrgA`'s secret against the payload. [13](#0-12) 
5. `StatusHandler#process` matches the `OrgB` commit purely by `sha` and creates a `success` `Status` on it, regardless of the fact the request was authenticated for `OrgA`. [14](#0-13) 
6. If `OrgB`'s stack has `continuous_deployment: true` and was previously blocked only by missing/pending CI, the injected status can push it toward automatic deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
