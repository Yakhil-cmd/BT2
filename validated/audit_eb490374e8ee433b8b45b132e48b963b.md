### Title
Unbounded slice access on attacker-controlled public-key response causes panic/DoS in `setSecret` - ([File: pkg/cmd/secret/set/set.go])

### Finding Description
`getPubKey` in `pkg/cmd/secret/set/http.go` performs an unauthenticated-content REST call and decodes the JSON response directly into the `PubKey{ID, Key}` struct without any validation of the `Key` field's length or format: [1](#0-0) 

The returned `pk.Key` (a base64 string fully controlled by whatever host/mock the request is sent to) then flows into `setSecret`, which base64-decodes it and copies the first 32 bytes into a fixed-size `[32]byte` array used as the NaCl box public key: `decodedPubKey, _ := base64.StdEncoding.DecodeString(pk.Key)` followed by `copy(peersPubKey[:], decodedPubKey[0:32])`. There is no check that `len(decodedPubKey) >= 32` before this fixed re-slice. Because `base64.StdEncoding.DecodeString` allocates its output buffer sized to the decoded length of the input (not padded to 32 bytes), a short base64 payload (e.g. decoding to 1–31 bytes) yields a slice whose capacity is also below 32, so `decodedPubKey[0:32]` panics with "slice bounds out of range" rather than silently succeeding.

The call chain is: `setRun` → `getOrgPublicKey`/`getRepoPubKey`/`getEnvPubKey`/`getUserPublicKey` → `getPubKey` → `client.REST` (untrusted response body) → `setSecret` → unchecked slice. No length validation, `safeurl`, or schema check protects the `Key` field's byte length anywhere in this path.

### Impact Explanation
An attacker who controls the response of the public-key endpoint (e.g., a malicious/compromised host the victim points `gh` at via `GH_HOST`, an Enterprise Server-like alternate host, or an HTTP proxy/mock under attacker influence) can return a short `Key` value and crash the victim's `gh` process with an unrecovered panic when the victim runs `gh secret set`. This is a client-side denial-of-service: the command aborts ungracefully instead of failing with a clean error, but it does not achieve code execution, credential exfiltration, or file writes.

### Likelihood Explanation
This requires the victim's `gh` to be directed at a host controlled or compromised by the attacker (default github.com API responses are not attacker-controlled), which is an explicitly permitted precondition in the threat model ("controls responses from a host the victim points gh at"). Given that precondition, the panic is deterministic and trivially reproducible — any base64 string decoding to fewer than 32 bytes triggers it.

### Recommendation
Validate `len(decodedPubKey) >= 32` immediately after decoding in the `setSecret` path and return a descriptive error (e.g., "invalid public key length") instead of slicing unconditionally.

### Proof of Concept
Using `httpmock`, register the public-key endpoint to return `{"key_id":"1","key":"AAAA"}` (decodes to 3 bytes), then invoke `setRun`/`getRepoPubKey` → `setSecret`. Expected current behavior: panic ("slice bounds out of range [:32] with capacity 3"); expected fixed behavior: a clean returned error.
