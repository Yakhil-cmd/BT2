### Title
Sui→Ethereum ETH claims permanently revert (and lock bridged funds) when the Sui-specified EVM recipient is a contract without `receive`/`fallback` - (File: bridge/evm/contracts/BridgeVault.sol, bridge/evm/contracts/SuiBridge.sol)

### Summary
This is a direct EVM-side analog of the Taiko `sendEther()` bug. When a Sui user bridges native ETH from Sui to Ethereum, the destination `recipientAddress` is arbitrary attacker/user-controlled bytes decoded from the Sui-originated message. On the Ethereum side, `SuiBridge.transferBridgedTokensWithSignatures` unconditionally calls `_transferTokensFromVault`, which for the ETH token routes to `BridgeVault.transferETH`, doing a raw `call{value: amount}("")` and `require(success, ...)`. If `recipientAddress` is a contract with neither `receive()` nor a payable `fallback()`, the low-level call fails, the `require` reverts the whole claim transaction, and — critically — `isTransferProcessed[message.nonce]` is only set to `true` *after* this call succeeds, so the message can never be marked processed and the funds can never be released.

### Finding Description
`SuiBridge.transferBridgedTokensWithSignatures` (bridge/evm/contracts/SuiBridge.sol) decodes the committee-approved `TokenTransferPayload` and unconditionally forwards to `_transferTokensFromVault`, which for `tokenID == ETH` calls into `BridgeVault.transferETH`:

```
function transferETH(address payable recipientAddress, uint256 amount)
    external override onlyOwner nonReentrant
{
    wETH.withdraw(amount);
    (bool success,) = recipientAddress.call{value: amount}("");
    require(success, "ETH transfer failed");
}
``` [1](#0-0) 

`recipientAddress` originates from a `bytes` field the Sui-side user supplies when bridging (e.g. via `bridge::send_token`), and on the Ethereum side it's decoded and used exactly as-is by `transferBridgedTokensWithSignatures`, with `isTransferProcessed[message.nonce] = true` only executed *after* the vault transfer succeeds: [2](#0-1) 

If the recipient is a contract without a payable `receive`/`fallback`, `recipientAddress.call{value: amount}("")` returns `success = false`, the `require` reverts, and the entire `transferBridgedTokensWithSignatures` transaction (including the `isTransferProcessed` write and the `TokensClaimed` event) is rolled back. Because the underlying tokens were already burned/escrowed on the Sui side (the Sui `bridge::send_token_internal` burns the coin and records the pending transfer before any signature is collected) [3](#0-2) 
there is no source-chain recall mechanism analogous to Taiko's `recallMessage`/`failMessage` for this direction — the committee/relayer can resubmit the same signatures indefinitely, but the call will always revert against the same immutable contract bytecode. The result is a permanently stuck bridge message and permanently locked ETH.

### Impact Explanation
This is a "permanent fund lock" outcome: tokens burned on Sui for an Ethereum-bound ETH transfer become unrecoverable if the specified recipient is a contract lacking `receive`/`fallback`. This matches the allowed High-severity impact category "permanent fund lock" for the Sui bridge scope. It does not require any privileged actor — an ordinary Sui bridge user simply supplies (accidentally or via a mis-integrated dApp) a contract address as the Ethereum recipient.

### Likelihood Explanation
Likelihood is realistic but not trivial: it requires the recipient address encoded in the bridge message to be a deployed EVM contract without a payable fallback/receive. This can happen from user error (typo/misconfigured integration) or a malicious dApp instructing users to bridge ETH to a contract it controls that intentionally lacks receive/fallback logic to grief/lock a specific transfer, similar to the original Taiko finding. ERC20 transfers via `BridgeVault.transferERC20`/`SafeERC20.safeTransfer` are not affected since ERC20 transfers to contracts without hooks do not revert.

### Recommendation
- In `BridgeVault.transferETH`, do not unconditionally revert the whole claim on a failed native transfer; e.g., wrap the recipient's ETH into WETH and transfer the ERC20 WETH instead when the raw call fails, so the claim can still be marked processed and the funds recoverable by the recipient later.
- Alternatively, allow the recipient to withdraw via a pull-based mechanism (escrow balance) instead of a push `call{value:...}`.
- Ensure `isTransferProcessed[nonce]` is set (or an equivalent "attempted"/"failed" state is recorded) even when the ETH push fails, and expose a retry/redeem path so tokens are not permanently unrecoverable.

### Proof of Concept
1. On Sui, a user calls `bridge::send_token` (native ETH type) with `target_address` bytes encoding the address of an Ethereum contract `NoFallback` that implements neither `receive()` nor `fallback()`. Sui burns/escrows the coin and records the pending `BridgeRecord`. [3](#0-2) 
2. The bridge committee signs and a relayer calls `SuiBridge.transferBridgedTokensWithSignatures(signatures, message)` on Ethereum with `recipientAddress = address(NoFallback)`. [4](#0-3) 
3. Internally this reaches `BridgeVault.transferETH(recipientAddress, amount)`, whose `recipientAddress.call{value: amount}("")` returns `success = false` since `NoFallback` cannot receive ETH, causing `require(success, "ETH transfer failed")` to revert the entire transaction. [1](#0-0) 
4. `isTransferProcessed[message.nonce]` remains `false` forever; every future replay of the same signed message reverts identically. The ETH burned on Sui in step 1 is permanently unrecoverable — no recall path exists in this direction.

**Note:** I was unable to view the exact body of `_transferTokensFromVault` (only its call sites were located) due to index limits, so I could not fully confirm whether it has an existing zero-amount guard or token-type branching beyond what's shown; however, the `BridgeVault.transferETH` revert-on-failed-call behavior and the post-transfer-only `isTransferProcessed` write are directly confirmed in the cited code, which are sufficient to establish the vulnerable pattern. Starting a Devin session with full repository access would allow verifying `_transferTokensFromVault`'s complete logic.
