### Title
Webhook signature validation is bound to `repository.owner.login`, but the state-mutating handlers act on unrelated payload fields (`repository.full_name`, global `sha`) - allowing cross-repository status/stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`) from the JSON payload. [1](#0-0) [2](#0-1)  Once the request passes, the entire raw payload is dispatched to event handlers, [3](#0-2)  which use **different fields of the same payload** to decide which repository/stack/commit is actually mutated: `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, [4](#0-3)  and `StatusHandler#process` looks up commits **globally by `sha`, with no repository/stack scoping at all**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [5](#0-4) 

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == repository/commit that gets written`

In this engine, this equality is never enforced. The signature check only verifies that the HMAC matches the secret for the org named in `repository.owner.login`/`organization.login`:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

But the actual mutation targets are derived independently:
- `PushHandler`/other repo-scoped handlers key off `repository.full_name` via `Repository.from_github_repo_name`. [4](#0-3) [6](#0-5) 
- `StatusHandler` keys off `sha` **alone**, with no scoping to the repository/organization that was authenticated at all: `Commit.where(sha: params.sha)`. [5](#0-4) 

Because GitHub computes the HMAC signature over the exact bytes an org admin submits, anyone who legitimately controls a webhook secret for *any one* GitHub organization/repository configured in this Shipit instance (i.e., any org whose admins installed the Shipit App/legacy webhook, which is not privileged with respect to *other* tenants' stacks) can freely construct an arbitrary JSON payload, sign it with their own known secret, set `repository.owner.login`/`organization.login` to their own org (satisfying `verify_signature`), and set `sha` (for `status` events) or `repository.full_name` (for `push`/other repo-scoped events) to values belonging to a **completely different, victim repository/stack** tracked by the same Shipit instance.

This is directly analogous to the reported bug class: a value is validated for one purpose (`_interestRateMode`/`repository.owner.login` selects a branch/secret) while an unrelated, unvalidated value drives the actual state mutation (`_newBorrowRateMode` fields/`sha`, `repository.full_name`), letting the caller silently steer the write path into a state the validator never checked.

### Impact Explanation
The most severe path is via `StatusHandler`: an attacker who administers any org/repo whose Shipit-configured `webhook_secret` they know can inject a fabricated **success** commit status onto an arbitrary commit `sha` belonging to a victim stack they do not control, because `Commit.where(sha: params.sha)` performs no repository or organization scoping whatsoever. [5](#0-4)  A commit's deployability is gated by exactly this status data: `deployable?` checks `success? && !blocked?`, [7](#0-6)  and successful/pending statuses also trigger `stack.schedule_merges` for the merge queue. [8](#0-7)  Forging a passing CI status on a victim's commit can therefore unlock an **unauthorized deploy or merge** on a stack the attacker has no legitimate relationship to — this falls squarely in the "Critical" impact bucket (unauthorized deploy/merge) defined by the rules.

### Likelihood Explanation
Exploitation requires the attacker to possess a valid webhook secret for at least one org/repo integrated with the target Shipit instance — a bar met by any legitimate but unprivileged tenant of a multi-tenant Shipit deployment (a very plausible real-world setup, since Shipit is explicitly designed to host many independent teams/orgs on one instance). No Shipit session, API token, or GitHub write access to the *victim* repository is required; only knowledge of the attacker's *own* webhook secret is needed, and Shipit performs no cross-check between the authenticating org and the entity being mutated.

### Recommendation
- Bind the signature/authentication decision to the same identifier used for the write path. Concretely, `verify_signature` should verify against the org/repo derived from `repository.full_name` (or the resource actually being written), not a separate `owner.login` field, and each handler should re-validate that the resource it is about to mutate (`Commit`, `Repository`, `Stack`) actually belongs to the organization that produced a valid signature.
- In `StatusHandler`, scope the `Commit` lookup by the verified repository (e.g., `stack.commits.where(sha: params.sha)` for stacks belonging to the authenticated repository) instead of a global `Commit.where(sha:)`.
- Add regression tests asserting that a validly-signed webhook for organization A cannot mutate state for a stack/repository owned by organization B.

### Proof of Concept
1. Attacker administers `attacker-org/some-repo`, which is a legitimately configured Shipit-integrated org with webhook secret `S` (known to the attacker, since they configured it).
2. Attacker finds (via Shipit's UI, which is often broadly readable, or via history) the `sha` of an undeployed commit on `victim-org/victim-repo`'s tracked stack.
3. Attacker crafts a `status` event JSON payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S, payload)` using their own known secret `S`.
5. POSTs to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the HMAC matches → request is accepted. [9](#0-8) 
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matches the victim's commit regardless of repository — and calls `create_status_from_github!`, writing a fabricated "success" status onto it. [5](#0-4) [10](#0-9) 
8. The victim commit now reports as `success`; if CI is the only blocker, it becomes `deployable?` and can be auto-merged/deployed via the merge queue/continuous delivery scheduling. [7](#0-6) [8](#0-7) 

*Note:* I was unable to fully trace the continuous-deployment/merge-queue triggering code path beyond `schedule_merges`/`schedule_continuous_delivery` due to index coverage limits; a Devin session with full repository access could confirm the exact downstream automatic-deploy trigger if deeper verification is desired.
