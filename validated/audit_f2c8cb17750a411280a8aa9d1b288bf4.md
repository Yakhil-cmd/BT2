This confirms the pattern strongly: every other webhook handler (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler` via the base `Handler#stacks`) scopes its DB lookups through `Repository.from_github_repo_name(params.repository.full_name)` as seen in the base class `app/models/shipit/webhooks/handlers/handler.rb:32-38` and in every `PullRequest::*Handler#repository` method. `StatusHandler`, however, is the outlier — it queries `Commit.where(sha: params.sha)` globally with no repository/organization scoping whatsoever.### Title
StatusHandler applies no repository/organization scoping, allowing any configured GitHub App to write Status records onto arbitrary tenants' commits - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` correctly resolves the GitHub App by `repository_owner` and validates the HMAC against that app's own `webhook_secret`, so an attacker cannot forge a signature for an organization they don't control. However, once verification passes for the attacker's own app/org, the dispatched handler for the `status` event, `Shipit::Webhooks::Handlers::StatusHandler`, performs `Commit.where(sha: params.sha)` with zero scoping to the repository or organization that authenticated the request, unlike every other handler in the codebase.

### Finding Description
The broken binding: `verified_organization(webhook_signature) == organization_scoping(status_write)` — true for signature verification, but false for the write itself.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) does `Shipit.github(organization: repository_owner)` and checks the HMAC against that specific app's `webhook_secret` (`lib/shipit/github_app.rb:76-83`). This part is sound: an attacker who controls App #2/OrgTwo can only produce a valid signature for payloads whose `repository.owner.login` matches OrgTwo (`Shipit.github_app_config`, `lib/shipit.rb:196-200`).
- After verification, `WebhooksController#create` dispatches purely by event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`), passing the raw, attacker-controlled `params` hash with no organization/repository binding attached.
- Every other handler re-derives and enforces the repository scope from the *payload's own* `repository.full_name` via `Repository.from_github_repo_name` — see the base `Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and each `PullRequest::*Handler#repository` method (e.g. `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53`, `opened_handler.rb:50-54`, `labeled_handler.rb:65-68`).
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) is the outlier:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
It never consults `params.repository` (indeed its `params do ... end` schema doesn't even require a `repository` key), so it matches by `sha` alone across the entire `Commit` table shared by all stacks/apps/orgs.

Exploit flow: attacker installs their own Shipit-App variant on their own org (App #2, precondition per `docs/setup.md` "Using Multiple Github Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`). They compute a valid HMAC over a JSON body using App #2's `webhook_secret` (which they legitimately possess as the owner of that app/org) with `X-Github-Event: status`, `repository.owner.login` = their own org (so `verify_signature` passes), but `sha` set to a commit sha that exists in another org's/App #1's `Commit` table (git SHAs are content-addressed and commonly known/guessable/forkable — e.g. copying a public commit's SHA, or forking a victim's public repo to obtain identical commit objects). `StatusHandler#process` finds and mutates that commit regardless of which org/app it belongs to, calling `commit.create_status_from_github!(params)` which creates a `Status` row tied to the victim's `Stack`.

Why guards don't help: `verify_signature` only proves "this request is authentically from App #2," not "this request may act on App #2's data only." `drop_unhandled_event`, `ExplicitParameters` (`StatusHandler.params`) validate types/presence only, not ownership. No `force_github_authentication`, `User#authorized?`, or `stacks` scope applies to webhook processing.

### Impact Explanation
The attacker can write forged CI `Status` records (state/description/target_url/context/created_at, from `Status.replicate_from_github!`/`create_status_from_github!`) onto a `Commit` belonging to an unrelated organization's `Stack`, without ever authenticating to that organization. `Commit#add_status` (`app/models/shipit/commit.rb:366-386`) fires `Hook.emit(:commit_status, ...)` and `:deployable_status`, and can call `stack.schedule_merges` when the new status is `pending` or `success`. Since Shipit's merge queue and continuous-deployment triggers act on `deployable_status` and CI states, this lets an attacker mark an arbitrary victim commit as `success`, potentially unblocking a merge or deploy on a stack they have no permission on — a cross-organization boundary break, matching Critical ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any known commit SHA in any stack across the whole multi-tenant installation, as long as the attacker controls one configured app among several.

### Likelihood Explanation
Requires a multi-app Shipit deployment (`Shipit.github_apps`/`secrets.github` keyed by organization, as documented in `docs/setup.md` "Using Multiple Github Applications"), and requires the attacker to control at least one of the configured GitHub Apps/orgs (i.e., be a legitimate, if low-privilege, tenant of that Shipit instance) plus knowledge of a target commit SHA in another tenant's stack (often discoverable via public GitHub history or via forking a public repo containing the same commits). Cost is low: no secrets beyond the attacker's own legitimately-issued `webhook_secret` are needed, and the attack is a single scripted HTTP POST, repeatable at will.

### Recommendation
Scope `StatusHandler` the same way as all other handlers: require `repository.full_name` (or resolve via the authenticated `repository_owner`/app) in the params schema, and restrict `Commit.where(sha: params.sha)` to commits under `Repository.from_github_repo_name(params.repository.full_name)&.stacks` (or equivalently intersect with `stacks` from the base `Handler`), so no commit belonging to a different repository/organization than the one that authenticated the webhook can be updated.

### Proof of Concept
Minitest plan (controller-level, no live GitHub):
1. Load `test/dummy/config/secrets_double_github_app.yml` fixture (OrgOne/OrgTwo, each with distinct `webhook_secret`) via `Shipit.stubs(:secrets)`.
2. Create `stack_one` owned by `OrgOne` with `commit_one` (`sha: "abc123..."`), and `stack_two` owned by `OrgTwo`.
3. Build a `status` event payload: `{ "sha" => commit_one.sha, "state" => "success", "repository" => { "owner" => { "login" => "OrgTwo" } } }`.
4. Compute `X-Hub-Signature` using OrgTwo's `webhook_secret` (the attacker's own, legitimately-known secret).
5. POST to `/webhooks` with that signature and `X-Github-Event: status`.
6. Assert response is `:ok` and `assert_difference('commit_one.statuses.count', 1)`.
7. Assert `commit_one.reload.statuses.last.state == 'success'` even though the authenticating app/org was `OrgTwo`, not `OrgOne` which owns `stack_one`/`commit_one` — proving the equality `authenticated_org(OrgTwo) == owning_org(commit_one.stack.repository.owner) (OrgOne)` is false yet the write still succeeded.
