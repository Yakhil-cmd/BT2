### Title
Cross-repository status forgery flips `UndeployedCommit#deploy_disallowed?` to false, exposing a "Deploy" control for a commit that never passed CI in its own repository - (File: app/models/shipit/undeployed_commit.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by SHA, without scoping to the repository/stack the webhook signature was verified for, so a validly-signed `status` webhook from an attacker-controlled repository in the same GitHub organization can create a `success` `Status` on a commit that belongs to a different stack. This forged status makes `Commit#deployable?` true, which directly flips `UndeployedCommit#deploy_disallowed?` from true to false, causing the stack's commit-list UI/API to present the commit as deployable even though it never received a real CI success from its own repository.

### Finding Description
The broken binding: `deploy_disallowed? == true` should hold whenever the commit's own repository has not reported a CI success for it. Concretely: `UndeployedCommit#deploy_disallowed?` is `!deployable? || !stack.deployable?` [1](#0-0) , and `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [2](#0-1) , where `success?` is delegated to `status`, which is built from the commit's own `statuses` association [3](#0-2) [4](#0-3) .

The root cause is in `StatusHandler#process`, which resolves target commits purely by SHA with no repository/stack scoping:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

Webhook signature verification in `WebhooksController#verify_signature` is scoped only to the GitHub **organization** (`Shipit.github(organization: repository_owner)`), not to the specific repository/stack that owns the commit [6](#0-5) . Any repository within that same organization — including one an attacker creates or forks and fully controls (per the stated attacker capabilities: "push to a fork... and emit webhooks from a repository they own") — produces webhooks that pass this check. If that attacker-owned repository shares a commit SHA with a commit tracked by a victim stack (trivially achievable by forking the victim's repository, which shares full commit history and therefore SHAs), the attacker can call GitHub's Statuses API on their own fork for that shared SHA with `state: success`. GitHub delivers this as a correctly-signed `status` webhook for the organization. `StatusHandler#process` then finds the `Commit` record by SHA alone (no `stack_id`/`repository` filter) and calls `commit.create_status_from_github!(params)` on the **victim's** `Commit`, creating a `Status` row with `state: 'success'` attached to the victim stack (`statuses.replicate_from_github!(stack_id, github_status)` in `create_status_from_github!` [7](#0-6) ).

After this, `commit.success?` is true, so `Commit#deployable?` becomes true (assuming not locked/blocked), and `UndeployedCommit#deploy_disallowed?` (`!deployable? || !stack.deployable?`) becomes false purely from the forged status, exposing the stack's Deploy control as enabled wherever `UndeployedCommit` is used, e.g. `Shipit::StacksController` and `Shipit::StacksHelper` [8](#0-7) [9](#0-8) .

None of the listed guards prevent this: `verify_signature` only checks the payload is signed by the correct GitHub App for the stated organization, not that the commit SHA belongs to that same repository; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` (`requires :sha`, `requires :state`, etc.) validate shape, not repository ownership; there is no `require_permission!`/`User#authorized?` check on the webhooks path since it is machine-to-machine; and no model validation ties a `Status` to the `Repository` that actually owns the `sha`.

### Impact Explanation
A record (`Status`) is written for a commit belonging to a repository/stack that never authenticated or reported that result — the classic "payload for one repository mutating another's commit/stack state." This is Critical because it directly causes an unauthorized/incorrect deploy signal: an operator relying on `deploy_disallowed?` to gate the UI's "Deploy" button is misled into believing CI passed, enabling a one-click deploy of code that never passed its own repository's CI, matching the impact category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy." It is repeatable against any stack in the same GitHub organization for any commit SHA the attacker can reproduce in a controlled fork (blast radius spans all stacks sharing that org's GitHub App installation, not just one tenant).

### Likelihood Explanation
Preconditions: attacker must control (own or have push access to) at least one repository within the same GitHub organization as the victim stack, and be able to produce a commit with the identical SHA as a commit in the victim's tracked history (straightforward via forking, since forks share full git history and SHAs are content-addressed). No Shipit session, API token, or GitHub App secret is required — GitHub itself signs the webhook using the organization's registered secret because the attacker's action (posting a status via GitHub's API on their own repo) is a legitimate, unprivileged GitHub action. This is low-cost and fully repeatable against any commit/stack combination sharing the same GitHub App/organization webhook secret.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository identified in the webhook payload (e.g., join through `Stack`/`Repository` matching `params.repository.full_name` or `repository_owner`/`repository_name` from the request) instead of a bare `Commit.where(sha: params.sha)`. Reject or ignore statuses whose payload repository does not match the `stack.repository` of the commit being updated.

### Proof of Concept
```ruby
# test/models/undeployed_commits_test.rb (new test)
test "deploy_disallowed? flips to false from a cross-repository status forgery" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to victim_stack, no success status
  assert UndeployedCommit.new(victim_commit, index: 0).deploy_disallowed?

  # Simulate StatusHandler#process being invoked for a webhook whose signature
  # was validly verified for the SAME GitHub organization but for a DIFFERENT
  # repository/stack that merely shares this commit's sha (e.g. a fork).
  forged_params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: victim_commit.sha,
    state: 'success',
    description: 'forged',
    context: 'ci/forged',
    created_at: Time.now.utc.iso8601
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.process_for_test(forged_params) # calls Commit.where(sha:).each { |c| c.create_status_from_github!(params) }

  victim_commit.reload
  refute UndeployedCommit.new(victim_commit, index: 0).deploy_disallowed?, 
    "deploy_disallowed? should remain true for a commit whose own repository never reported success"
end
```
This test demonstrates that `deploy_disallowed?` becomes `false` solely due to a `Status` created via the SHA-only lookup in `StatusHandler#process`, with no dependency on the victim repository having reported anything.
