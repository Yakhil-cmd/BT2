### Title
Cross-organization webhook forgery allows an attacker to overwrite another tenant's `PullRequest.assignees` via `AssignedHandler#process` - ([File: app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login`, while `AssignedHandler` (and its sibling `EditedHandler`) scope the `PullRequest` row to update based on the separate `repository.full_name` field. Because nothing cross-checks that these two payload fields refer to the same repository/organization, an attacker who controls a repository (and therefore its valid `webhook_secret`) can sign a payload whose `repository.owner.login` is their own org but whose `repository.full_name` names a victim's repository, causing the victim's tracked `PullRequest.github_pull_request` (including `assignees`) to be overwritten.

### Finding Description
The binding that should hold is:
`organization verifying the webhook (Shipit.github(organization: repository_owner))` == `organization owning the Shipit::PullRequest row mutated (via Repository.from_github_repo_name(params.repository.full_name))`.

In `app/controllers/shipit/webhooks_controller.rb`:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
This value picks which `GitHubApp`/`webhook_secret` is used in `verify_webhook_signature` [2](#0-1) .

In `AssignedHandler`, the record to mutate is looked up using a **different** JSON field, `params.repository.full_name`:
```
def pull_request
  @pull_request ||= Shipit::PullRequest
                    .joins(:stack, stack: :repository)
                    .find_by(number: params.number, stacks: { repositories: { id: repository.id } })
end

def repository
  Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new
end
``` [3](#0-2) 
and the update itself:
```
def process
  return unless respond_to_assignee_change?
  pull_request.update(github_pull_request: params.pull_request) if pull_request.present?
end
``` [4](#0-3) 

There is no code anywhere in `WebhooksController` or `Handler` that asserts `repository.owner.login == repository.full_name.split('/').first`. Since both fields live in the same attacker-controlled JSON body, an attacker who owns/controls a repository under `attacker-org` (and therefore knows the valid `webhook_secret` configured for `attacker-org`, or for a Shipit instance with no `webhook_secret` configured at all, in which case `verify_webhook_signature` returns `true` unconditionally per `return true unless webhook_secret` [5](#0-4) ) can send:
```
POST /webhooks
X-Github-Event: pull_request
X-Hub-Signature: sha1=<valid HMAC using attacker-org's webhook_secret>
body: {
  "action": "assigned",
  "number": <victim PR number>,
  "pull_request": { ..., "assignees": [{"login":"attacker"}], ... },
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
`verify_signature` computes the HMAC using `attacker-org`'s secret and succeeds because the attacker legitimately owns that secret. `AssignedHandler#repository` then resolves `victim-org/victim-repo` and finds the victim's tracked `Shipit::PullRequest`, which is updated with attacker-supplied `github_pull_request` data, overwriting `assignees` (and other fields such as `title`, `labels`, `head.sha`) for a repository/tenant the attacker never proved control of. This is structurally identical to the already-covered `EditedHandler` case (`test/models/shipit/webhooks/handlers/pull_request/edited_handler_test.rb` exists for that class), since both handlers share the exact same lookup/update pattern.

No existing guard prevents this: `drop_unhandled_event` only checks event type is registered; `verify_signature` only checks the signature against `repository_owner`, never cross-validated against `full_name`; `ExplicitParameters` schema only validates types/shape, not cross-field consistency; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` involved in webhook processing at all.

### Impact Explanation
The attacker achieves an unauthorized cross-tenant database write: a `Shipit::PullRequest` row belonging to a victim's repository/stack has its `github_pull_request` JSON (including `assignees`, `title`, `labels`, `head.sha`) overwritten by a payload the attacker signed with credentials for an unrelated repository. This is repeatable against any tracked PR in any repository whose `full_name` the attacker guesses/knows (repo names are public), for every `assigned`/`unassigned` (and separately `edited`) event. I was not able to confirm, within the available indexed context, that `assignees` is subsequently consumed as an authorization or merge-gating signal (e.g., no evidence found that `merge_status_controller.rb` or stack merge-lock logic reads `PullRequest#assignees` to authorize merges/deploys); the confirmed, in-scope impact is the unauthorized cross-tenant write itself, not a further escalation into merge/deploy authorization. If downstream code (not found in this pass) does trust `assignees` for approval workflows, severity would rise to Critical.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to control any single GitHub repository connected to Shipit (or exploit a Shipit deployment where `webhook_secret` is unset for some organization, which disables verification entirely) — no privileged Shipit role, no `ApiClient` token, and no knowledge of the victim's secret is required. The attack is a single crafted HTTP POST to `/webhooks` and can be repeated for any PR number/repository the attacker chooses.

### Recommendation
In `WebhooksController#verify_signature`, or in `Shipit::Webhooks::Handlers::Handler`, enforce that the organization/owner used to select the verifying `webhook_secret` matches the owner encoded in `repository.full_name` (and reject the request otherwise). Additionally, `AssignedHandler`/`EditedHandler` (and other PR handlers using the same pattern) should scope `Repository.from_github_repo_name` lookups using the same `repository_owner` value that was authenticated by `verify_signature`, not blindly trust `full_name` from the payload body.

### Proof of Concept
Minitest plan (analogous to the edited_handler test):
1. Create `victim_stack` with `Repository` `full_name: "victim-org/victim-repo"` and a tracked `Shipit::PullRequest` with `number: 42`, `github_pull_request: { assignees: [] }`.
2. Configure two GitHub orgs in `Shipit` config: `attacker-org` with a known `webhook_secret`, and `victim-org` with a different secret unknown to the attacker.
3. Build a `pull_request` `assigned` payload with `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `number: 42`, and `pull_request.assignees = [{"login" => "attacker"}]`.
4. Sign the raw JSON body using `attacker-org`'s `webhook_secret` (HMAC-SHA1) and POST to `/webhooks` with `X-Github-Event: pull_request` and the computed `X-Hub-Signature`.
5. Assert response is `200`/`204` (not `422`), i.e., signature verification succeeded using `attacker-org`'s secret.
6. Reload `victim_stack`'s `PullRequest` and assert `pull_request.github_pull_request["assignees"]` now equals `[{"login" => "attacker"}]`, proving the equality `organization verifying webhook (attacker-org) == organization owning mutated PullRequest (victim-org)` is false yet the write still occurred.
