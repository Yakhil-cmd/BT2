### Title
API clients can impersonate arbitrary `User`s via the unverified `X-Shipit-User` header, breaking the identity-to-action binding for deploys, rollbacks, locks, task triggers/aborts, and merge requests - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`Shipit::Api::BaseController` authenticates *requests* via an `ApiClient` bearer token (`authenticate_api_client`), which only proves the caller holds a valid `ApiClient` credential and its associated `permissions`/`stack_id` scope. Separately, the controller derives `current_user` — the `Shipit::User` that is *attributed* to the action being performed — from the client-supplied, unsigned `X-Shipit-User` HTTP header, with no cryptographic binding to the authenticated `ApiClient` at all.

### Finding Description
`authenticate_api_client` verifies a signed `ApiClient` token via `ApiClient.authenticate`, which uses `Shipit::SimpleMessageVerifier` to validate the token signature and load the record: [1](#0-0) . That verification binds the request to an `ApiClient` and its `creator` (`belongs_to :creator, class_name: 'User'`) [2](#0-1) , and gates the operation via `permissions`: [3](#0-2) .

However, `current_user` — used to record *who* triggered a deploy/rollback/lock/task/merge — is computed independently and is never covered by that signature check: [4](#0-3) 

Any request that presents a *valid ApiClient token* (which only proves possession of that token, scoped by `permissions`/`stack_id`) can set an arbitrary `X-Shipit-User: <any-login>` header and have Shipit look up and treat that arbitrary `Shipit::User` row as the actor for the operation — with no verification that the token holder is, or is acting on behalf of, that user.

This is consumed as the attributed actor across all mutating API endpoints:
- `stack.trigger_task(params[:task_name], current_user, ...)` and `task.abort!(aborted_by: current_user)` [5](#0-4) 
- `stack.trigger_deploy(commit, current_user, ...)` [6](#0-5) 
- `stack.lock(params.reason, current_user)` [7](#0-6) 
- `active_task.abort!(aborted_by: current_user, ...)` / `deploy.trigger_rollback(current_user, ...)` [8](#0-7) 
- `MergeRequest.request_merge!(stack, params[:id], current_user)` [9](#0-8) 

The equality that should hold — "the identity that presented valid credentials" == "the `User` bound to the resulting action record" — is broken: any holder of an `ApiClient` token (which may be a narrowly-scoped, unlocked integration token deliberately created to *not* represent any particular human) can forge the second half of that equality to be any `Shipit::User` in the database, including admins or GitHub-team-privileged users, purely via a request header.

### Impact Explanation
This satisfies the "GitHub identity versus the `User` bound to the session" trust-binding category. An attacker holding *any* valid `ApiClient` token with `deploy:stack`/`lock:stack`/etc. permission (e.g., a CI-scoped token meant only for that stack) can attribute deploys, rollbacks, locks, task triggers/aborts, and merge requests to an arbitrary victim `User` — including privileged maintainers — without that user's involvement or consent. This causes unauthorized/misattributed deploys, rollbacks, and merges to be recorded and executed as if approved/initiated by someone else, which maps to the "unauthorized deploy, rollback or merge" Critical-impact category, since the actual mutating action (deploy/rollback/merge) is executed by the app regardless of whose identity is forged in the audit trail — only the attribution of that already-permitted action is spoofed.

### Likelihood Explanation
Likelihood is high for any deployment where `ApiClient` tokens are distributed to automation/CI systems (the intended use case per `docs/setup.md`/`ccmenu`), since exploitation requires nothing beyond a valid token for the targeted stack and knowledge of a victim's GitHub login (which is generally public). No GitHub App private key, webhook secret, or session cookie is needed — only possession of one legitimately-issued `ApiClient` credential, which is explicitly the "unprivileged attacker" starting point for this class of engine per the scan rules.

### Recommendation
Do not derive `current_user` from a client-supplied header. Either:
- Bind `current_user` to `current_api_client.creator` (the verified, signed identity), or
- Require a second, independently-signed proof of the human actor (e.g., a signed user-token analogous to `ApiClient.authentication_token`) rather than a bare `X-Shipit-User` login string, and validate it belongs to the presenting `ApiClient`'s permitted scope before trusting it for attribution.

### Proof of Concept
1. Obtain any valid `ApiClient` token scoped with `deploy:stack` (e.g., a CI token for stack X): `Authorization: Basic base64("<id>--<token>")`.
2. Send:
```
POST /api/stacks/1/deploys
Authorization: Basic <valid-apiclient-basic-auth>
X-Shipit-User: victim-admin-login
Content-Type: application/json

{ "sha": "<some-sha>" }
```
3. `identify_user` looks up `User.where('lower(login) = ?', 'victim-admin-login')` [10](#0-9)  and returns that `User` record as `current_user`.
4. `stack.trigger_deploy(commit, current_user, ...)` [11](#0-10)  creates and executes the deploy attributed to `victim-admin-login`, despite that user never having made the request — confirmed by the header being trusted verbatim with no signature check anywhere in `authenticate_api_client` or `identify_user`.

        else

        end

      end
