### Title
Nil-pointer dereference / index-out-of-range panic when processing attacker-supplied attestation bundles - ([File: pkg/cmd/release/shared/attestation.go])

### Summary
`FilterAttestationsByFileDigest` (and its sibling `FilterAttestationsByTag`) dereference `att.Bundle.Bundle.GetDsseEnvelope().Payload` without checking that `att.Bundle`, the inner `Bundle`, or the `DsseEnvelope` are non-nil, and `verify.go`'s callers index `filteredAttestations[0]` without guarding for an empty slice in every path. A GitHub attestation record shaped with a missing/empty DSSE envelope or bundle can crash `gh release verify` / `gh release verify-asset` while processing an attacker-controlled repository's release attestations.

### Finding Description
`FilterAttestationsByFileDigest` iterates over the `[]*api.Attestation` fetched from `GetByDigest` and unconditionally does: [1](#0-0) 
`att.Bundle` is a `*bundle.Bundle` from `sigstore-go`, populated from the attestation JSON via `api.Attestation.Bundle` field: [2](#0-1) 
If `att.Bundle` is `nil` (e.g., the JSON payload has `"bundle": null` or is malformed such that the field fails to populate), then `att.Bundle.Bundle` dereferences a nil pointer, since it accesses the embedded `Bundle` protobuf field directly rather than through a nil-safe getter. Even where `GetDsseEnvelope()` itself may be a nil-safe proto getter, the subsequent `.Payload` field access on a possibly-nil `*DsseEnvelope` return value is not nil-checked, so a bundle without a DSSE envelope also panics. The same unguarded pattern appears in `printVerifiedSubjects`: [3](#0-2) 
These attestations originate from the target repository's attestation store, which for `gh release verify`/`verify-asset` is `baseRepo` — a repo the attacker fully controls (their own fork/repo, since it's the "base repo" the victim runs the command against). An attacker who controls the repo that hosts the release can shape the attestation records associated with it (or the raw bundle content) to include malformed/null bundle data.

### Impact Explanation
This results in a crash (panic) of the `gh` CLI process during `gh release verify` or `gh release verify-asset` — a denial-of-service against the invoking client, not remote code execution, credential leak, or file-write outside the intended path. Per the target's stated "Expected Immunefi impact: High - Unbounded resource consumption," that specific framing does not match this bug class; a single unhandled panic is a crash/DoS, not resource exhaustion. This is best categorized as a client-side crash/availability issue, which is a lower severity impact than data compromise or authentication bypass classes.

### Likelihood Explanation
Preconditions: the victim must run `gh release verify` or `gh release verify-asset` against a repository controlled by the attacker (an ordinary, permitted scenario per the rules), and the attacker must be able to produce a release + associated attestation whose `bundle` JSON is null/malformed or lacks a DSSE envelope. Whether GitHub's real attestation-store API enforces schema validation on ingestion (which would block a `null` bundle from ever being returned) could not be confirmed from this repository, since the server-side attestation storage isn't part of this codebase — the client only trusts whatever JSON the API returns. This uncertainty affects feasibility but not the client-side code defect itself.

### Recommendation
Add nil checks before dereferencing: verify `att.Bundle != nil`, `att.Bundle.Bundle != nil`, and that `GetDsseEnvelope()` returns non-nil before accessing `.Payload`, returning a descriptive error (e.g., "attestation missing bundle/envelope") instead of panicking. Apply the same guards in `FilterAttestationsByTag` and `printVerifiedSubjects`. Additionally, audit `verify.go`/`verify_asset.go` for any indexing of `filteredAttestations[0]` to ensure it is only reached after confirming `len(filteredAttestations) > 0` (already done in the reviewed code paths, but should be kept consistent with any future changes).

### Proof of Concept
```go
func TestFilterAttestationsByFileDigest_NilBundle(t *testing.T) {
    atts := []*api.Attestation{
        {Bundle: nil, BundleURL: "https://example.com"},
    }
    // Expect a graceful error, not a panic
    _, err := shared.FilterAttestationsByFileDigest(atts, "deadbeef")
    if err == nil {
        t.Fatal("expected error for nil bundle, got nil")
    }
}
```
Running this test today panics with a nil pointer dereference at `att.Bundle.Bundle.GetDsseEnvelope().Payload` instead of returning an error, confirming the defect. A fuzz target could similarly construct `api.Attestation` values from arbitrary/mutated JSON (`{"bundle": null}`, `{"bundle": {}}`, `{"bundle": {"dsseEnvelope": null}}`) and assert `FilterAttestationsByFileDigest`/`FilterAttestationsByTag` never panic.
