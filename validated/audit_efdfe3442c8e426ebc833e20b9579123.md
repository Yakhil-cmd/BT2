### Title
Race condition in duplicate-check-then-save of private payment chains allows double-processing of the same private payment - ([File: private_payment.js])

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` performs a "check-then-act" duplicate detection for incoming private payment elements without any mutex/lock serializing concurrent invocations for the same `(unit, message_index[, output_index])`, mirroring the NEAR "reconstructing witness" bug class where `processed_witnesses` was checked outside a lock and could be evaluated twice concurrently before either write landed.

### Finding Description
`validateAndSavePrivatePaymentChain` in <cite repo="Jaredbentat/ocore--004" path="private_payment.js" start="45|/*jslint node: true */" end="45|/*jslint node: true */" /> reads the current DB state to decide whether an incoming private-payment output is a duplicate, and only then calls the underlying asset module to insert it: [1](#0-0) 

The "check if duplicate" `SELECT` happens on its own DB connection/transaction, and the decision of "is this a duplicate, skip" vs "not a duplicate, insert" is made without holding any global lock (`mutex.lock`) across the check. `network.js`'s `handleOnlinePrivatePayment`, which is the caller for privately-delivered payment elements from peers/cosigners/hub, explicitly acknowledges this class of concurrency but has the protective flag intentionally commented out: [2](#0-1) 

The comment at lines 2391-2392 explicitly documents the exact concurrent-delivery scenario ("we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device... we also receive the same (unit, message_index, output_index) twice"), i.e., the same private element can legitimately arrive from two different sources (peer + hub, or cosigner + recipient device) at nearly the same time. If two such deliveries race:
1. Both calls to `validateAndSavePrivatePaymentChain` open separate connections and run the duplicate-check `SELECT` before either has committed its `INSERT`.
2. Both see `rows.length === 0` (or the row not yet revealed), so both conclude "not a duplicate" and both proceed to `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)`.
3. For indivisible assets, `indivisible_asset.js`'s `validateAndSavePrivatePaymentChain` inserts outputs/inputs, but it does use `INSERT `+db.getIgnore()` for `inputs`/`outputs`` rows, which can mask the double INSERT at the row level, but the accompanying `UPDATE outputs SET is_spent=1 WHERE ... AND is_spent=0` at [3](#0-2)  and analogous logic in the divisible path (`divisible_asset.js` lines 32-71, no `IGNORE`) can double-apply spend/unspend transitions or produce two independent successful `ifOk()` callbacks for what should be a single, once-only chain acceptance.
4. This exactly parallels the NEAR bug class: a state check (`processed_witnesses` / "is this a duplicate output") is done without holding the relevant lock across the check-then-write sequence, letting two concurrent handlers both believe they are first and both act.

Unlike `handleJoint` in `network.js`, which correctly guards concurrent unit processing via the `assocUnitsInWork` map set synchronously before any async work ` [4](#0-3) `, the private-payment path for already-known units (`ifKnown` branch) has that equivalent guard commented out, and no other mutex (e.g., `mutex.lock(['handleJoint'])` used elsewhere in `divisible_asset.js`/`indivisible_asset.js` for the writer-composition path) protects this specific check-then-insert sequence.

### Impact Explanation
Concurrent delivery of the same private payment (unit, message_index, output_index) from multiple legitimate sources (hub + direct peer, or cosigner + recipient on the same device, as explicitly anticipated by the code's own comments) can cause `validateAndSavePrivatePaymentChain` to be executed twice concurrently for the same private element, bypassing the duplicate-skip logic. Depending on which asset module handles it and the interleaving of the two transactions, this can lead to inconsistent `is_spent`/`is_serial` state transitions being applied twice, or the recipient/cosigner logic (`callbacks.ifOk` firing twice → `eventBus.emit("new_my_transactions", ...)` fired twice) causing a wallet to record or credit the same private transaction twice. This falls into "AA/wallet fund loss or freezing" / node disagreement on private-chain validity territory, since private payment state (which underlies balances for private assets) can become inconsistent between racing writers.

### Likelihood Explanation
Likelihood is Medium: the race requires near-simultaneous delivery of the identical private element from two sources, a scenario the code's own comments confirm is a real, expected occurrence (hub relaying + direct sender, or a cosigner and the recipient being the same device), so it is not a purely theoretical timing window — it is a documented normal operational pattern, just one for which the protective in-work marker was disabled.

### Recommendation
Re-enable and correctly scope a lock (e.g., `mutex.lock(['pp-'+unit+'-'+message_index+'-'+output_index])` or similar) around the full duplicate-check + insert sequence in `private_payment.js`'s `validateAndSavePrivatePaymentChain`, so that the duplicate `SELECT` and the subsequent `INSERT`/`UPDATE` execute atomically with respect to other concurrent calls for the same key. Restore the `assocUnitsInWork` guard (or an equivalent per-key lock) in `network.js`'s `handleOnlinePrivatePayment` `ifKnown` branch instead of leaving it commented out.

### Proof of Concept
Not directly executable from the indexed code alone (requires two live peers/hub deliveries racing at the network layer), but the reachable trigger path is: an attacker or two legitimate senders (hub + peer, or two cosigner devices) deliver the identical `private_payment` message for the same `(unit, message_index[, output_index])` within a small time window so that both invocations of `network.js:handleOnlinePrivatePayment` → `private_payment.js:validateAndSavePrivatePaymentChain` execute their duplicate-check `SELECT` before either `COMMIT`s, both concluding "not a duplicate" and both proceeding to insert/update, per [1](#0-0)  and [2](#0-1) .
