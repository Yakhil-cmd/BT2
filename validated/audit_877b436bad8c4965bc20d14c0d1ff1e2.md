### Title
Unsanitized GitHub PR label names become injected environment variable KEYS reaching `PTY.spawn` - (File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`LabelCapturingHandler#capture_labels` stores raw GitHub label name strings verbatim onto `PullRequest#labels` with no charset/format validation. `ReviewStack#env` later upcases each label name and uses it as an environment variable **key** (`labels[label_name.upcase] = "true"`), which is merged unfiltered into `TaskCommands#env` and ultimately into `Command#unbundled_env`, which is passed directly to `PTY.spawn`.

### Finding Description
The binding claimed by the question is: *the set of label names an authorized maintainer intends as env-toggles == the literal set of label name strings stored by `capture_labels` and later turned into environment KEYS by `ReviewStack#env`*. Tracing the code shows this binding is broken because nothing enforces it.

- `LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` directly from the webhook payload's label names [1](#0-0) .
- `PullRequest#labels` is a plain serialized array column with no format, charset, or allowlist validation [2](#0-1) .
- `ReviewStack#env` turns every stored label name into an environment variable key: `labels[label_name.upcase] = "true"`, merged onto the base stack env [3](#0-2) .
- `TaskCommands#env` merges `@stack.env` (which includes the label-derived keys) directly, with **no call to `EnvironmentVariables#permit`, `filter_envs`, `filter_deploy_envs`, or `filter_rollback_envs`** anywhere in this merge chain [4](#0-3) .
- The whitelist mechanism `EnvironmentVariables#permit` (`Stack#trigger_task`/`Stack#build_deploy`) only filters the *user-supplied* `env:` argument passed when manually triggering a deploy/task via the UI/API — it is never applied to `@stack.env`, so it does not protect this path at all [5](#0-4) .
- `Command#unbundled_env` merges `@env.stringify_keys` directly on top of `BASE_ENV` (which includes `PATH`), and this result is passed straight to `PTY.spawn` [6](#0-5) [7](#0-6) .

Exploit flow: an attacker able to attach a label named e.g. `PATH` or `LD_PRELOAD` to a PR on a repository provisioning a review stack causes the `pull_request.labeled` webhook to fire `LabelCapturingHandler`, which stores the literal label string. On the next task/deploy run for that review stack, `TaskCommands#env` unconditionally includes `PATH=true` (or `LD_PRELOAD=true`) in the environment handed to `PTY.spawn`, overriding the intended `PATH` set by `unbundled_env` (`BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — note `@env` is merged *last*, so a label-derived `PATH` key wins and clobbers the sanitized `PATH`).

Existing guards checked and found not to prevent this: `EnvironmentVariables#permit` (bypassed entirely for this code path, confirmed above); `Stack` model validations (`environment` format validator exists but there is no `labels` format validator) [8](#0-7) ; the webhook handler's `ExplicitParameters` schema only requires `labels` entries have a String `name`, imposing no charset restriction [9](#0-8) .

Note on attacker capability: on GitHub, applying a label to a PR normally requires "triage" write-level access to the repository, not merely being able to open a PR. The audit brief explicitly frames this as conditional ("any PR author can add labels to their own PR if the repo allows"). This engine's webhook handler performs no independent verification of who applied the label or what permission they had — it trusts whatever label state GitHub reports in the payload (subject to normal webhook signature verification), so the code-level exploitability is real whenever GitHub-side label permissions are permissive (e.g., external triage bots, public label-any-contributor settings, or maintainer misconfiguration).

### Impact Explanation
Once a maintainer enables continuous delivery / review-stack provisioning on a repository (`repository.review_stacks_enabled`, `provisioning_behavior_allow_all` or similar), any subsequent task or deploy for that review stack executes `PTY.spawn` with attacker-influenced environment KEYS such as `PATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc. This can result in code execution on the deploy host (RCE) if the spawned command consults any of those variables (e.g., PATH hijacking of a subshell/tool invoked during deploy steps) — matching the Critical severity category ("RCE on the deploy host via `Command`/`PTY.spawn`"). The blast radius is scoped to the single repository/review stack that has provisioning enabled and whose GitHub label permissions permit the attacker to add labels; it is repeatable on every task/deploy run as long as the label remains attached.

### Likelihood Explanation
Requires: (1) review stacks enabled for the target repository with a provisioning behavior that creates a stack for the attacker's own PR, and (2) GitHub-side permission to attach labels to that PR (not available to arbitrary internet users by default GitHub permission model, but achievable in some repository configurations or via automation that mirrors labels). Given those preconditions, exploitation is a single label-add action, fully repeatable, and requires no Shipit credentials, session, or secrets — consistent with the question's threat model.

### Recommendation
Sanitize label names before use as environment variable keys: restrict `ReviewStack#env` to only emit keys matching a safe identifier charset (e.g., `/\A[A-Z][A-Z0-9_]*\z/` after upcasing) and/or maintain an explicit allowlist of "toggle" labels configured in `shipit.yml` (similar to `deploy_variables`/`VariableDefinition`), running the label-derived hash through `EnvironmentVariables#permit` before merging into `TaskCommands#env`. Additionally, never allow label-derived keys to override reserved/security-sensitive variable names (`PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `BUNDLE_*`, etc.) regardless of allowlist configuration.

### Proof of Concept
Minitest plan (extends existing `test/models/shipit/review_stack_test.rb` and `test/lib/shipit/task_commands_test.rb` patterns):
```ruby
test "#env does not allow PR labels to inject dangerous environment keys" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["LD_PRELOAD", "PATH"]

  env = stack.env

  # BINDING CHECK: the maintainer-intended toggle-label set is empty/allowlisted,
  # but capture_labels + ReviewStack#env produced dangerous keys anyway.
  assert env.key?("LD_PRELOAD"), "demonstrates unsanitized label became an env KEY"
  assert env.key?("PATH"), "demonstrates unsanitized label overrides PATH"

  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  task_env = Shipit::TaskCommands.new(task).env

  assert_equal "true", task_env["LD_PRELOAD"]
  assert_equal "true", task_env["PATH"]

  command = Shipit::Command.new("echo hi", env: task_env, chdir: Dir.tmpdir)
  spawned_env = command.unbundled_env
  assert_equal "true", spawned_env["LD_PRELOAD"], "attacker-controlled LD_PRELOAD reaches PTY.spawn's env"
end
```
This proves the equality is broken: the literal label strings stored by `capture_labels`/`github_pull_request=` become environment KEYS in `Command#unbundled_env` without ever passing through `EnvironmentVariables#permit` or any charset allowlist.
