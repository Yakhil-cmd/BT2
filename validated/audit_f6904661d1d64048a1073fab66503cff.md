### Title
Partial/truncated asset content is left on disk as a normal file after a failed download - (File: pkg/cmd/release/download/download.go)

### Summary
`destinationWriter.Copy` in `pkg/cmd/release/download/download.go` writes the HTTP response body directly into the final destination file path using `os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644)` followed by `io.Copy(f, r)`, with no temporary file, no atomic rename, and no cleanup of the partially-written file if the copy fails or the body is truncated. If a remote host controlled or influenced by the attacker (e.g. a release asset endpoint, or a Codeload archive endpoint reached via `--archive`) cuts the connection mid-transfer, the truncated bytes remain on disk under the exact final filename the user expected, indistinguishable from a complete, correctly downloaded file.

### Finding Description
The path `downloadRun` → `downloadAssets` → `downloadAsset` → `dest.Copy` in [1](#0-0)  retrieves the HTTP response body for a release asset or archive URL and passes it straight to `destinationWriter.Copy`.

`Copy` performs the write like this: [2](#0-1) 

There is no staging/temp file (`os.CreateTemp` + `os.Rename`), no size/checksum verification against any expected length or digest, and no `os.Remove(fp)` in the error path when `io.Copy` returns a non-nil error (e.g. `io.ErrUnexpectedEOF` from a truncated body, or a network error). The file is opened with `O_TRUNC` directly at the user-visible target path (`fp` from `makePath`), so partial bytes are visible under the final name for the entire duration of a slow or failing download, and remain there permanently if the transfer fails.

`downloadAssets` only aggregates the returned error to report failure to the user via the process exit code [3](#0-2) ; it never inspects or deletes the on-disk artifact that `Copy` may have already created. Because GitHub release assets, archive downloads (`--archive=zip`/`tar.gz`), and content served through Codeload are all attacker-influenced (the attacker publishes the release/repo, and Codeload/asset delivery can be interrupted by any network condition an attacker who controls the response stream can trigger, e.g. by publishing an oversized asset and cutting the connection, or a slow/backpressured response), a truncated file with attacker-chosen name and attacker-chosen (partial) bytes is left in the destination directory. If the CLI or a downstream script treats a non-error absence of a fatal-looking message, or any external tooling later inspects the directory for "does this asset exist" rather than validating exit codes strictly, a truncated/corrupted artifact can be mistaken for a fully and correctly downloaded one.

### Impact Explanation
This is a file-integrity/verification-bypass issue: `gh release download` provides no guarantee that a file present in the destination directory after a failed run is complete or trustworthy, since partial writes are made directly to the final path rather than through a temp-file-then-rename pattern. In supply-chain contexts (downloading release binaries/archives to later execute or verify), a truncated file bearing the final name could be picked up by automation that doesn't strictly gate on the `gh` exit code, resulting in use of unverified/incomplete content presented at the expected path.

### Likelihood Explanation
Any interrupted download - a dropped connection, a server closing the stream early, a canceled process partway through a large asset/archive - triggers this. No special privileges are needed beyond publishing the asset/release/repo (already assumed attacker capability), and network interruption during transfer is a completely ordinary occurrence, not a contrived one, making this readily and repeatably reproducible.

### Recommendation
Write asset content to a temporary file in the same directory (e.g. `fp + ".tmp"` or via `os.CreateTemp` in `filepath.Dir(fp)`), and only `os.Rename` it into place at `fp` after `io.Copy` completes without error (and, if applicable, after verifying the received length against `Content-Length`/any provided checksum). On any error from the copy, explicitly remove the temp file before returning, so a failed download never leaves a file at the user-visible destination path.

### Proof of Concept
Go test sketch for `pkg/cmd/release/download/download_test.go`:
```go
func TestCopy_TruncatedBodyLeavesNoFinalFile(t *testing.T) {
    dir := t.TempDir()
    w := destinationWriter{dir: dir}

    // Simulate a body that returns data then an error mid-stream.
    body := &truncatingReader{
        data: []byte("some initial bytes that look like a full file..."),
        err:  io.ErrUnexpectedEOF,
    }

    err := w.Copy("asset.bin", body)
    require.Error(t, err)

    fp := filepath.Join(dir, "asset.bin")
    _, statErr := os.Stat(fp)
    // EXPECTED (fails today): file should not exist after a failed copy.
    require.True(t, os.IsNotExist(statErr), "partial file must not remain at %s after failed download", fp)
}

// truncatingReader returns partial data then a read error.
type truncatingReader struct {
    data []byte
    err  error
    sent bool
}

func (r *truncatingReader) Read(p []byte) (int, error) {
    if r.sent {
        return 0, r.err
    }
    n := copy(p, r.data)
    r.sent = true
    return n, nil
}
```
Running this against current `Copy` implementation shows `asset.bin` exists on disk with partial content despite `Copy` returning an error, confirming the missing temp-file/rename/cleanup invariant.
