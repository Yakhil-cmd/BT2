### Title
Attacker-controlled swap routes can escape the intended input authorization and steal unrelated caller tokens - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
The controller accepts opaque attacker-supplied `swap` bytes in `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, then forwards them to the configured router without decoding or constraining the route's contract addresses. [1](#0-0)  A malicious route can therefore place attacker-controlled code beneath the caller's signed authorization tree and add an unrelated `token.transfer(caller, attacker, amount)` child authorization. [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` requires the caller to own or delegate the account, but treats `swap` as unrestricted opaque bytes and forwards it to `router.execute_strategy(controller, amount_in, swap)`. [3](#0-2)  The controller only self-authorizes the expected input transfer for `amount_in`; it does not authorize or constrain any venue, pool, or token address named inside the route. [4](#0-3) 

The missing boundary is analogous to the reposync path traversal: attacker-controlled route data is interpreted as execution targets, and an operation intended to stay inside the swap can instead reach an unrelated token contract and transfer funds from the transaction signer. [5](#0-4)  The repository's regression test demonstrates this with a malicious route pool calling `token::Client::transfer(victim, attacker, amount)` while the router still returns a normal-looking swap output. [6](#0-5) 

### Impact Explanation
A victim who signs the simulated authorization tree loses unrelated wallet tokens in addition to supplying the intended collateral input. [7](#0-6)  This is theft of user funds rather than merely route-quality loss: the rogue transfer is not bounded by `amount`, router min-out, controller balance-delta checks, or the final account risk gate. [8](#0-7) 

### Likelihood Explanation
Exploitation requires the victim to accept a malicious route and sign the expanded authorization tree, so an attacker cannot invoke it against a victim account unilaterally. [9](#0-8)  The exposure is still material because route bytes are opaque data supplied with strategy transactions, while simulation records the malicious transfer as a child under the victim's normal `swap_collateral` authorization. [10](#0-9) 

### Recommendation
Constrain route execution to governance-approved venue and pool contracts, rather than allowing payload-selected addresses to execute below user authorization. [2](#0-1)  Until the router boundary enforces that allowlist, clients must decode every route, verify all venue/token addresses, simulate the complete controller transaction, and reject any authorization child other than the exact expected input pull. [11](#0-10) 

### Proof of Concept
1. Alice owns a lending account with USDC collateral and holds an unrelated token `WALLET`. [12](#0-11) 
2. The attacker deploys a fake hop contract configured with `(alice, WALLET, attacker, WALLET_BALANCE)` and embeds it in a route whose declared input/output still satisfies the strategy. [13](#0-12) 
3. Alice submits `swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, malicious_route)`. [14](#0-13) 
4. During simulation, the fake hop executes `WALLET.transfer(alice, attacker, WALLET_BALANCE)`, and the host records that transfer as a child of Alice's `swap_collateral` authorization. [15](#0-14) 
5. If Alice signs the poisoned tree, enforcing mode executes the unrelated transfer: Alice's `WALLET` balance becomes zero and the attacker receives `WALLET_BALANCE`, while the collateral swap still completes. [7](#0-6)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],

        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),

        sub_invocations: std::vec![stolen_transfer],

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
