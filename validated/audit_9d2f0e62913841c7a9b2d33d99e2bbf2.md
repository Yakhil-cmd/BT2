### Title
`session[:authenticated] = true` is set without checking `current_user.authorized?`, letting any authenticated-but-unauthorized GitHub user reach the `/events` stream - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` sets `session[:authenticated] = true` for any successfully authenticated GitHub identity, with no check against `Shipit.github_teams`. The `/events` route is mounted directly as a Rack endpoint (`Pubsubstub::StreamAction`) in `config/routes.rb`, bypassing the `Shipit::Authentication` concern (`force_github_authentication`/`current_user.authorized?`) that gates every other Shipit controller, so team membership is never enforced on that endpoint.

### Finding Description
The intended binding is: `session[:authenticated] == true` should imply `current_user.authorized?` (i.e., the user is a member of `Shipit.github_teams`, per `User#authorized?` in `app/models/shipit/user.rb#80-82`). In reality:

- `callback` (`app/controllers/shipit/github_authentication_controller.rb#13-18`) sets `session[:user_id]` and unconditionally `session[:authenticated] = true` for anyone who completes OAuth, with an explicit comment stating this flag exists so `/events` and `/sidekiq` (gated only by an external `UserRequiredMiddleware`) recognize the user as "authenticated."
- Every normal Shipit controller enforces authorization via the `Shipit::Authentication` concern's `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb#20-34`), which calls `current_user.authorized?` and renders `403 Forbidden` if the user is not on an allowed team.
- `/events`, however, is mounted in `config/routes.rb#9` as `mount Pubsubstub::StreamAction.new, at: "/events"` — a raw Rack app, not a Shipit controller including the `Authentication` concern. Nothing in this engine calls `force_github_authentication` or `current_user.authorized?` for this route; the only gate is whatever external `UserRequiredMiddleware` checks (per the comment, `session[:authenticated]`), and that flag does not encode team membership.

So for a GitHub user who is not in any `Shipit.github_teams`: `session[:authenticated] == true` while `current_user.authorized? == false` — the two diverge, breaking the intended invariant, and the divergence is directly exploitable against `/events` because that route never runs the `authorized?` check that would have caught it.

### Impact Explanation
Any GitHub account that can complete OAuth against the app (no team membership, no repo maintainer status required) can subscribe to `/events`, which streams live pubsub events for stacks, deploys and tasks (broadcast by `app/models/shipit/hook.rb` and task/deploy models). This is an unauthenticated-tier read of stack state and deploy/task output, matching the "High" impact category (unauthenticated read of stack state, task streams or deploy output). It is repeatable indefinitely and not scoped to a single repository — any stream broadcast on the shared `/events` channel is exposed to any completed-OAuth user, regardless of team.

### Likelihood Explanation
Preconditions: the attacker only needs a valid GitHub account and to complete the standard OAuth callback flow at `github_authentication#callback` — no special repo permissions, no `Shipit.github_teams` membership, and no secrets. This is a low-cost, fully repeatable action available to any internet user capable of an OAuth handshake with the app.

### Recommendation
Gate `/events` (and `/sidekiq`) with an authorization check equivalent to `current_user.authorized?`, not merely `session[:authenticated]`. Either wrap `Pubsubstub::StreamAction` behind a Shipit controller/middleware that checks team membership, or only set `session[:authenticated] = true` in `callback` after confirming `Shipit.github_teams.empty? || user.authorized?`, and have `UserRequiredMiddleware` (or its equivalent) revalidate `authorized?` per request rather than trusting a static session flag set at login time.

### Proof of Concept
```ruby
# test/integration/events_authorization_test.rb
require 'test_helper'

class EventsAuthorizationTest < ActionDispatch::IntegrationTest
  test "session[:authenticated] diverges from current_user.authorized? for non-team users" do
    Shipit.stubs(:github_teams).returns([Shipit::Team.new(id: 1, handle: 'core')])

    # Simulate a completed OAuth callback for a user NOT in any Shipit.github_teams
    OmniAuth.config.mock_auth[:github] = OmniAuth::AuthHash.new(
      provider: 'github',
      uid: '12345',
      extra: { raw_info: { id: 12345, login: 'outsider' } },
      credentials: { token: 'ghp_faketoken' }
    )
    get '/github/auth/github/callback'

    user = Shipit::User.find_by(github_id: 12345)
    assert_equal true, session[:authenticated]
    assert_equal false, user.authorized?, "user must not be on an allowed team"

    # The two sides of the intended equality now disagree:
    refute_equal session[:authenticated], user.authorized?
  end
end
```
Note: the actual `UserRequiredMiddleware` referenced in the callback's comment is not defined anywhere in this engine (only mentioned in the comment), so its exact gating behavior for `/events` cannot be exercised end-to-end from this repo alone; the proof above demonstrates the concrete, in-engine divergence (`session[:authenticated]` set true while `authorized?` is false) and the fact that `config/routes.rb` mounts `/events` outside the `Shipit::Authentication` before_action chain, which is the root cause within this engine's own code.
