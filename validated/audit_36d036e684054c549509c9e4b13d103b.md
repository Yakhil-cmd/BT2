### Title
Webhook signature verification is keyed on `repository.owner.login` while the payload actually acted upon is selected by `repository.full_name`, letting an attacker forge events for any org that has no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and thus which HMAC secret) to validate the request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Verification itself is done by `GitHubApp#verify_webhook_signature`, which explicitly bypasses HMAC checking when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [3](#0-2) . Once verification passes, the raw JSON body is handed unchanged to every registered handler for the event [4](#0-3) . Those handlers resolve the `Repository`/`Stack` to act on from a *different* field of the same payload: `payload.dig('repository', 'full_name')` [5](#0-4)  (and similarly `params.repository.full_name` in the pull-request handlers [6](#0-5) ).

### Finding Description
This is the exact bug class from the report, translated to Shipit's trust model: the value the code verifies (`repository.owner.login`, used only to select the signing organization for HMAC comparison) is not bound to the value the code subsequently acts on (`repository.full_name`, used to resolve the concrete `Repository`/`Stack` that gets updated). Both fields live in the same attacker-controlled JSON body, since the webhook endpoint is a public, unauthenticated HTTP endpoint gated only by the HMAC signature check.

Docs explicitly describe the webhook secret as "optional" per GitHub App/organization [7](#0-6) , and Shipit supports multiple organizations each with independently configured, possibly-nil secrets [8](#0-7) . If an org `A` is configured in Shipit without a `webhook_secret` (nil), any POST to `/webhooks` claiming `repository.owner.login == "A"` sails through `verify_signature` unconditionally, because `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank [9](#0-8) .

The attacker can then set `repository.full_name` to `"OrgB/protected-repo"` — a real repository/stack tracked under a *different*, properly-secured organization `B` — in the very same payload. Handlers never re-check that `full_name`'s owner matches the `repository_owner` used for signature verification; they simply do `Repository.from_github_repo_name(repository_name)` and act on whatever stacks are attached [5](#0-4) . For example, `PushHandler#process` finds matching stacks by branch and calls `stack.sync_github(expected_head_sha: params.after)` [10](#0-9) , and the `status`/`check_suite` handlers create local CI status/check-run records for a given commit that feed directly into `Commit#add_status` / continuous delivery decisions (confirmed by tests such as `test/models/commits_test.rb:233-243`, where creating a `success` status on a commit for a stack with `continuous_deployment: true` enqueues a `ContinuousDeliveryJob` and triggers a real `Deploy`) [11](#0-10) , backed by `Deploy#schedule_continuous_delivery` / `Stack#trigger_continuous_delivery` [12](#0-11) [13](#0-12) .

Before/after the equality this breaks:
- Before (intended): `organization that signed the webhook == organization that owns the repository being written`.
- After (attacker payload): `organization that signed the webhook (org A, no secret)` ≠ `organization actually written (org B, secured, via repository.full_name)`.

### Impact Explanation
An unauthenticated external attacker who knows (a) that any single organization configured in the Shipit instance has no `webhook_secret` set, and (b) the `owner/repo` full name of a stack tracked under a different, secured organization, can forge `push`/`status`/`check_suite` webhook payloads that are accepted as valid and that manipulate CI status and sync state for that unrelated stack. Combined with `continuous_deployment` on the target stack, this can result in an unauthorized automated deploy being triggered — matching the report's "Critical: unauthorized deploy" impact category, since the attacker never needed a Shipit session, API token, or the target organization's real webhook secret.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: it requires at least one organization onboarded to the same Shipit instance with no `webhook_secret` set (explicitly allowed and documented as "optional" per `docs/setup.md`), and knowledge of a target stack's repository name (public information for public repos). Given multi-tenant Shipit deployments hosting many organizations, and webhook secret configuration being opt-in rather than enforced, this is a realistic misconfiguration rather than a purely theoretical one.

### Recommendation
Bind the value used for signature verification to the value used for repository resolution: derive the acting repository/stack strictly from the same authenticated context used to select the signing key, or better, verify the signature using the config keyed by the organization actually referenced by `repository.full_name` (not a separately-extracted `owner.login`/`organization.login` field), and reject the request if these disagree. Consider also making `webhook_secret` mandatory (non-nilable) for all configured organizations, removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two orgs: `orgA` (no `webhook_secret`) and `orgB` (has a `webhook_secret` and an existing stack for `orgB/target-repo` with `continuous_deployment: true`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no/invalid `X-Hub-Signature`, and a JSON body:
```json
{
  "sha": "<head sha of orgB/target-repo>",
  "state": "success",
  "context": "ci/travis",
  "repository": {
    "full_name": "orgB/target-repo",
    "owner": { "login": "orgA" }
  }
}
```
3. `verify_signature` resolves `repository_owner` to `orgA`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/incorrect) signature header [9](#0-8) .
4. `Shipit::Webhooks::Handlers::StatusHandler` (not directly inspected in this session due to tool errors on the final iteration, but structurally consistent with `Handler#repository_name`) resolves the stack via `full_name` = `orgB/target-repo` and records a `success` status for the commit, which — per the `commits_test.rb` behavior — schedules `ContinuousDeliveryJob` and can trigger an unauthorized `Deploy` on `orgB`'s stack.

**Uncertainty note:** I was not able to open `app/models/shipit/webhooks/handlers/status_handler.rb` and `check_suite_handler.rb` directly in this session (tool errors on the final iteration), so the exact field names/validations inside those two specific handler classes are inferred from the shared `Handler` base class and from `test/models/commits_test.rb`'s behavior rather than read verbatim. The `PushHandler` and `PullRequest::OpenedHandler` code paths, which independently demonstrate the same `owner.login`-vs-`full_name` mismatch, were read directly and support the finding.

```ruby
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
