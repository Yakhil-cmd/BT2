### Title
Webhook signature verification silently disabled when `webhook_secret` is unset, allowing unauthenticated forgery of commit CI status and cross-stack merge/deploy approval - ([File: lib/shipit/github_app.rb])

### Summary
`GithubApp#verify_webhook_signature` returns `true` (i.e., treats the request as authenticated) whenever `webhook_secret` is blank, instead of enforcing that a secret must be configured. This mirrors the reported bug class exactly: a security-critical threshold (`minReward` in the analog, `webhook_secret` here) is never enforced to be present, so the protective check silently degrades to a no-op. Combined with the fact that `StatusHandler` looks up commits purely by `sha` with no repository/stack scoping, this lets an unauthenticated caller inject a fabricated "success" CI status onto any commit that shares that sha across any stack, which the merge queue and deploy gating rely on to authorize merges.

### Finding Description
`WebhooksController#verify_signature` picks the `GithubApp` instance to verify against using an attacker-controlled field from the unauthenticated payload itself (`repository_owner`), then delegates verification to that app's `webhook_secret`: [1](#0-0) [2](#0-1) 

The actual signature check is: [3](#0-2) 

`return true unless webhook_secret` means that for any configured organization whose `webhook_secret` is left blank/nil (a state the codebase's own example configs show as valid, e.g. `webhook_secret: # nil`), signature verification is bypassed entirely — any JSON body, with any `X-Hub-Signature` header (or none), is accepted as if it came from GitHub. [4](#0-3) 

Once inside the `create` action, handlers process the raw JSON without any additional per-repository authorization: [5](#0-4) 

`StatusHandler#process` is especially exploitable because it resolves target commits purely by `sha`, with no filter on repository, stack, or organization: [6](#0-5) 

This status is what the merge queue trusts to decide if a pull request is mergeable: [7](#0-6) 

and what `ProcessMergeRequestsJob` uses to actually invoke `merge!` against GitHub with the app's own GitHub credentials: [8](#0-7) 

**The binding that breaks:** "organization authenticated" (whichever org's `github_app` object ends up handling `verify_signature`, potentially with no secret configured) should equal "repository/commit actually written to" (any commit, in any stack, matching an attacker-chosen `sha`). Because verification can be a no-op and the handler enforces no additional per-repo authorization on `status` events, these two are not bound together at all when a webhook secret is absent.

### Impact Explanation
An unauthenticated network attacker who can reach the webhooks endpoint can:
1. Discover (or brute force via trial payloads and the 422 response) any organization configured in the Shipit instance without a `webhook_secret`.
2. Submit a forged `status` event naming that organization as `repository.owner.login`, with an arbitrary `sha` and `state: success`.
3. Have that fake "success" status attached to any commit sharing that sha in the database, satisfying `all_status_checks_passed?` for merge requests and CI gating for deploys.
4. Trigger `ProcessMergeRequestsJob` to call `merge_pull_request` on GitHub using Shipit's own GitHub App credentials — an unauthorized merge — or unblock an automated/continuous deploy that was gated on required CI statuses.

This matches the "Critical" impact bar: an unauthorized deploy or merge performed with the app's own GitHub credentials, triggered without any valid credential from the attacker.

### Likelihood Explanation
Likelihood depends on at least one configured GitHub organization lacking a `webhook_secret`. This is not a hypothetical edge case: the repository's own example/dev configuration explicitly shows this as a supported value (`webhook_secret: # nil`), and nothing in `GithubApp#initialize` or elsewhere enforces that a secret must be present before the app is considered usable. An operator following the documented setup that omits the optional-looking `webhook_secret` field (or leaves it blank during initial bring-up) exposes this without realizing the check is fully disabled.

### Recommendation
- Fail closed instead of open: if `webhook_secret` is not configured for an organization, `verify_webhook_signature` should reject the request (or the app should refuse to start / refuse to register webhook routes for that org) rather than returning `true`.
- Independently scope `StatusHandler` (and any other handler that mutates commit/build state) to the repository identified in the verified payload, rather than trusting `sha` alone to locate commits across all stacks.
- Enforce `webhook_secret` presence at configuration-load time, analogous to enforcing `minReward` at contract initialization in the referenced report.

### Proof of Concept
1. Configure (or identify) an organization in `secrets.yml` with `webhook_secret` left blank, as shown in `config/secrets.development.shopify.yml`.
2. Send:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<sha-of-a-commit-pending-merge-in-any-stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "<org-without-webhook-secret>"}}
}
```
No `X-Hub-Signature` header is required to pass `verify_signature` because `webhook_secret` is blank.
3. `StatusHandler#process` creates a `success` `Status` on the targeted commit.
4. `ProcessMergeRequestsJob` (or deploy CI gating) now considers the corresponding pull request/commit as passing required checks, and can merge/deploy it using Shipit's own GitHub credentials. [3](#0-2) [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
