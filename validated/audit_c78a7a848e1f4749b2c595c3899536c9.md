### Title
Unhandled exception in `definition template` expansion crashes node during unit validation - ([File: ocore/definition.js])

### Summary
`Definition.validateDefinition()` and `Definition.validateAuthentifiers()` both support the `definition template` opcode, which fetches a previously-stored `definition_template` payload from the DB, `JSON.parse`s it, and then recursively substitutes parameters into it via `replaceInTemplate()` → `replaceInVar()`. Any exception thrown while expanding the template other than the expected `NoVarException` is deliberately re-thrown (`else throw e;`), and this happens inside an asynchronous `conn.query()` callback with no surrounding try/catch on the call stack, so the exception becomes an uncaught exception that crashes the whole ocore process. This mirrors the GnuTLS class of bug: a crafted/malformed chain of data (here, a maliciously nested "definition template") triggers an unhandled fault during structure verification/expansion.

### Finding Description
`evaluate()` inside `validateDefinition()` handles the `'definition template'` opcode: [1](#0-0) 

The template payload is read from the `messages`/`units` tables (any already-stable unit with `app='definition_template'`), parsed with `JSON.parse`, and expanded with `replaceInTemplate`. The try/catch only special-cases `NoVarException`; any other exception is re-thrown:
```
catch(e){
    if (e instanceof NoVarException)
        return cb(e.toString());
    else
        throw e;
}
```
This `throw e` occurs inside the `conn.query(...)` result callback — i.e., inside an async I/O callback, not inside the synchronous call chain that invoked `validateDefinition`. In Node.js, a `throw` from inside an async callback cannot be caught by any `try/catch` higher up the (already-unwound) call stack; it becomes an uncaught exception on the event loop and, unless a global `uncaughtException`/`domain` handler swallows it (ocore does not wrap unit validation in such protection), it crashes the node process.

`replaceInTemplate` → `replaceInVar` (used identically in both the validating (`validateDefinition`) and signature-checking (`validateAuthentifiers`) code paths) recurses over the template structure: [2](#0-1) 

Its `default: throw Error("unknown type");` branch and its unbounded recursion into nested arrays/objects (no depth limit, unlike `evaluate()` in `aa_validation.js` which explicitly enforces `MAX_DEPTH`, see `aa_validation.js:598-604`) give two distinct ways to raise an exception here: (1) any value type not covered by number/boolean/string/object (reachable if the "template" payload is not itself validated to be JSON.parse-only-safe values, e.g. via constructed alternate encodings before this call), and (2) unconstrained recursion depth on `x[i]`/`x[key]` that can exhaust the call stack (`RangeError: Maximum call stack size exceeded`) with a deeply nested template array. Both are exceptions that are not `NoVarException` and thus get re-thrown from inside the async DB-query callback.

Reachability: `definition template` is evaluated both when a new address/asset condition definition is validated (`validateDefinition`, reachable from `validateAuthor`/`validateAssetDefinition`/`wallet_defined_by_addresses.validateAddressDefinition`) and when an existing address's signature is checked (`validateAuthentifiers`, same op at `definition.js:802-819`), which runs on every incoming unit signed by an address using that construct. Both are reachable by any unprivileged unit poster: they can (a) post a `definition_template` message once (a normal, allowed app type) containing a maliciously deep/crafted structure, then (b) post/reference an address whose definition uses `['definition template', [unit, params]]` pointing at that stored template. Every node that subsequently validates a unit referencing this address definition (as part of normal DAG unit validation) will execute the vulnerable expansion path and crash.

### Impact Explanation
A successful trigger crashes any full node that validates the malicious unit/definition — this includes ordinary nodes processing units broadcast over the network, not just the attacker's own node. Repeated/targeted posting of such units can be used to crash multiple nodes each time they attempt to validate the affected definition, i.e., "a network unable to confirm new units" in the affected nodes, satisfying the required Medium-severity impact bar (availability-only crash, analogous to the GnuTLS CVSS vector C:N/I:N/A:H).

### Likelihood Explanation
Low complexity for the attacker: crafting a nested array/object as a `definition_template` payload and referencing it from an address definition uses only standard, already-permitted ocore primitives (`definition_template` messages and the `definition template` address-definition opcode) — no special privileges beyond being able to post units are required. The main precondition is that another party's unit references/uses that address definition (analogous to GnuTLS's requirement that `certtool --verify-chain` be run on the crafted bundle — i.e., some validating action must be performed on the crafted structure), which happens naturally as soon as the address is used to author or co-author a unit that gets gossiped to peers.

### Recommendation
- Wrap the `replaceInTemplate`/`evaluate` "definition template" expansion in a try/catch that treats *all* exceptions (not just `NoVarException`) as validation failures (`return cb("invalid template: " + e)`), never re-throwing from within an async callback.
- Add an explicit recursion-depth guard (mirroring `MAX_DEPTH` in `aa_validation.js`) inside `replaceInVar` to bound nesting depth of templates and prevent stack-overflow-triggered crashes.
- Validate the `definition_template` payload's structure/depth/size at the time it is stored (message validation), not only at usage/evaluation time.

### Proof of Concept
1. Attacker posts a unit with a `definition_template` message whose `payload` is a deeply nested JSON array (e.g., thousands of levels of `["seen address", [...]]`-shaped nesting) or otherwise structured to trigger `replaceInVar`'s recursion.
2. Attacker creates/uses an address whose definition (or an asset's `issue_condition`/`transfer_condition`) is `['definition template', [<template_unit>, {param: 'x'}]]`, referencing the stored template.
3. Attacker (or anyone) posts a unit authored by/co-authored by that address, or referencing that asset condition, and broadcasts it.
4. Any node that receives and validates this unit calls `Definition.validateAuthentifiers`/`validateDefinition`, which reaches the `'definition template'` branch, calls `replaceInTemplate`, hits the stack-overflow/`unknown type` exception path inside the `conn.query` async callback, and the uncaught exception crashes the node process.

Note: I was unable to directly inspect `validation.js`'s handling of incoming `definition_template` messages (to confirm exactly what structural constraints, if any, are enforced when the template is first stored) due to search/tool limitations in this session; a full Devin session with file access would be needed to confirm the precise boundary of accepted template shapes and to build a concrete reproducible payload.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
