### Title
Webhook signature verified against the org derived from the unverified payload, allowing cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using a field read out of the **unverified** JSON body, then hands the same unverified body to the event handlers, which resolve the target repository from a *different* field of that same unverified body. This breaks the intended binding "the organization whose secret authenticated this request == the organization whose repository is written to."

### Finding Description
`WebhooksController#verify_signature` picks the `github_app` to check the HMAC signature against based on `repository_owner`, which is computed straight from the raw JSON payload before any signature check occurs: [1](#0-0) [2](#0-1) 

Shipit supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, as shown in the multi-org secrets template: [3](#0-2) 

Once `verify_signature` passes, `create` re-parses the same raw body and dispatches it, unmodified, to every registered handler for the event: [4](#0-3) 

Handlers such as `PushHandler` resolve the affected `Stack`/`Repository` from the payload's `repository.full_name` (via `stacks`, delegated through `Repository.from_github_repo_name`), a different JSON path than `repository.owner.login`/`organization.login` used for signature-org selection: [5](#0-4) [6](#0-5) 

Because `repository.owner.login`/`organization.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are independent, attacker-controlled fields inside the same unverified body, and only one of them is cryptographically bound to the secret used to check the signature, an attacker who can produce a valid signature for *any one* configured organization (e.g., because that org was configured with no `webhook_secret`, i.e. `nil`, or its secret is otherwise known/weak) can craft a body where `organization.login`/`repository.owner.login` names that org (to satisfy `verify_signature`) while `repository.full_name` names a repository belonging to a completely different organization/stack. The signature check passes, but the acted-upon repository is not the one whose credential validated the request. This matches the "organization authenticated vs. repository written" binding-break pattern.

`verify_webhook_signature` further weakens this: if `webhook_secret` for the selected org is blank, verification is skipped entirely (`return true unless webhook_secret`): [7](#0-6) 

So in the common single-org (or partially-configured multi-org) deployment where `webhook_secret` is left `nil` for at least one configured organization (the example templates default it to `nil`), any request whose `organization.login`/`repository.owner.login` names that org bypasses signature verification altogether while the actual repository acted upon (`repository.full_name`) can be forged to reference any other stack/organization known to that Shipit instance.

### Impact Explanation
This allows an unauthenticated network attacker to forge GitHub webhook events (`push`, `status`, `pull_request`, `check_suite`, `membership`) that are attributed to and act on a repository/organization the attacker does not control, as long as any one org configured on the instance has no/weak webhook secret. Concretely, forged `push` events trigger `stack.sync_github` (GitHub re-sync/deploy pipeline progression) and forged `status`/`check_suite` events can flip CI state used to gate deploys — an unauthorized cross-repository write into Shipit's deploy state, which can influence which commits become "deployable" without any credential tied to the targeted repository/org.

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured GitHub org/App with a blank/`nil` `webhook_secret` (explicitly shown as the default/example value in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`), or a weak/known secret for one org. In a single-org install this only matters if `webhook_secret` was left unset (also a documented default), which is realistic misconfiguration that this endpoint doesn't guard against — the code makes no attempt to bind the verified org to the repository actually acted upon.

### Recommendation
After parsing and verifying the payload, re-derive the repository/organization to act upon strictly from the same field that was cryptographically verified (or verify that `repository.full_name`'s owner matches the `repository_owner` used to select/verify the signing secret) before dispatching to handlers. Additionally, consider requiring a non-blank `webhook_secret` for every configured organization and rejecting requests where it's missing rather than silently accepting them.

### Proof of Concept
1. Configure Shipit with two orgs in `github:` — `orgA` (no `webhook_secret` set, i.e. `nil`) and `orgB` (has a stack, e.g. `orgB/target-repo`).
2. Send a POST to `/webhooks` with header `X-Github-Event: push` and a JSON body where `organization.login`/`repository.owner.login` = `orgA` (so `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header supplied), but `repository.full_name` = `orgB/target-repo` and `ref`/`after` referencing an attacker-chosen SHA.
3. `verify_signature` passes (org A has no secret configured), `create` dispatches the full body to `PushHandler`, which resolves `Repository.from_github_repo_name("orgB/target-repo")`'s stacks and calls `stack.sync_github(expected_head_sha: <attacker sha>)` — an action on `orgB`'s stack triggered without ever presenting a valid credential for `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
