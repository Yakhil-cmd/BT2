### Title
Webhook signature "verification" silently no-ops when `webhook_secret` is unset, letting an unprivileged attacker forge `membership` events and self-grant `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` is the sole gate protecting `WebhooksController#create`, but it silently returns `true` (i.e. "verified") whenever the organization's `webhook_secret` config value is blank [1](#0-0) . Every documented/example configuration in this engine ships `webhook_secret:` empty by default (`# nil`) [2](#0-1) [3](#0-2) . Under that (undocumented-as-dangerous, but perfectly normal) configuration, `WebhooksController#verify_signature` accepts **any** unsigned payload, dispatches it to the registered handler for the `X-Github-Event` header [4](#0-3) [5](#0-4) , and the `organization` used to pick which app/secret to check is itself read straight out of the unverified body (`params.dig('repository','owner','login')`) [6](#0-5) .

The `membership` handler trusts every field of that unauthenticated payload to create/find a `Team` and add an arbitrary `member.login` to it [7](#0-6) , and `Team#add_member` just appends the row with no re-validation against GitHub [8](#0-7) . `User#authorized?`, which gates every controller in the engine via `force_github_authentication`, checks only the local `teams` join table against `Shipit.github_teams` [9](#0-8) [10](#0-9) .

### Finding Description
The binding that should hold is:
`organization/event that produced a webhook and is trusted to mutate local authorization state` == `organization that cryptographically signed the raw request body with the app's registered `webhook_secret``.

`verify_webhook_signature` breaks this equality:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret          # <-- unauthenticated bypass
  ...
end
``` [1](#0-0) 

If the operator has not configured `webhook_secret` for an organization (the value in every shipped example config), this method is not "verify" at all — it's a pass-through, exactly analogous to `TransferHelper._safeTransferFrom` being named "safe" while not implementing the actual safety check it claims to perform.

`WebhooksController#verify_signature` derives which GitHub App/secret to check with from the very payload it hasn't verified yet:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Combined, an unauthenticated network attacker who knows (or guesses) the target organization name can POST a `membership` event body with:
- `action: "added"`
- `team: { id, name, slug, url }` matching a team already referenced by `Shipit.github_teams`
- `member: { login: "<attacker-github-login>" }`

`MembershipHandler#process` then does:
```ruby
team = find_or_create_team!
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member)
``` [11](#0-10) 

This creates/updates the local `Team`/`Membership` rows purely from attacker-supplied JSON — no call back to GitHub to confirm the membership actually exists. The attacker then completes a normal OAuth login with their own (real) GitHub account; `User#authorized?` only checks the local `teams` table, which now (falsely) contains them:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [9](#0-8) 

This flips `force_github_authentication` from forbidding to allowing full access [10](#0-9) .

### Impact Explanation
This is an authentication/authorization bypass: an attacker who was never actually a member of any privileged GitHub team obtains full authenticated access to the Shipit instance (deploy dashboards, deploy/rollback triggers, API client management, etc.), because `Shipit.github_teams` authorization — the engine's core privilege gate — is escalated into via a forged, unsigned webhook. From there the attacker has all capabilities of a legitimate authorized user, including triggering unauthorized deploys/rollbacks. This matches the explicitly listed High/Critical impacts: "escalation into `Shipit.github_teams` authorization" and downstream "unauthorized deploy, rollback".

### Likelihood Explanation
High. No credentials, GitHub App private key, or `webhook_secret` are required — the whole point is that `webhook_secret` is unset. Every shipped example configuration (`docs/setup.md`, `template.rb`, `config/secrets.development.example.yml`) leaves `webhook_secret` blank by default, so this is the common/default deployment posture rather than a misconfiguration outside the documented setup. The attacker only needs the org name (publicly visible) and the ID/slug of a team referenced in `Shipit.github_teams` (also discoverable via the GitHub org's public/authorized team listing or simply by using the Shipit UI's own "you must be a member of X" error message, which reveals the exact team handles) [12](#0-11) .

### Recommendation
- Fail closed: `verify_webhook_signature` should reject requests (not return `true`) when `webhook_secret` is not configured, or require `webhook_secret` to be mandatory at boot for any organization that registers privilege-affecting handlers (e.g. `membership`).
- Never resolve `repository_owner`/the signature-checking organization from the unverified body; verify against every configured secret, or require an explicit organization binding independent of attacker-controlled JSON.
- Do not let `MembershipHandler` (and any other authorization-affecting handler) trust webhook payload fields blindly — reconcile membership changes against the GitHub API instead of/in addition to trusting the event body.

### Proof of Concept
1. Target Shipit instance is configured per the documented template with `webhook_secret` left blank for organization `acme` [2](#0-1) .
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything

{
  "action": "added",
  "team": {"id": 123, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/123"},
  "organization": {"login": "acme"},
  "member": {"login": "attacker-gh-login"},
  "repository": {"owner": {"login": "acme"}}
}
```
3. `verify_signature` calls `Shipit.github(organization: "acme").verify_webhook_signature(...)`, which returns `true` immediately because `acme`'s `webhook_secret` is blank [13](#0-12) .
4. `MembershipHandler#process` creates/finds `Team(github_id: 123, organization: "acme", slug: "deployers")`, creates `User(login: "attacker-gh-login")`, and appends the membership [11](#0-10) .
5. Attacker performs normal GitHub OAuth login as `attacker-gh-login`; `User#authorized?` now returns `true` because `teams` includes the `acme/deployers` team referenced in `Shipit.github_teams` [9](#0-8) .
6. Attacker now has full authenticated access, including deploy/rollback capability, without ever being a real member of the GitHub team.

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
