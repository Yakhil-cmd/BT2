### Title
Missing global cap on cumulative balance/issuance of uncapped assets enables floating-point precision loss and undetectable supply inflation - (File: validation.js, constants.js)

### Summary
`validatePaymentInputsAndOutputs` in <cite repo="Ellentat/ocore--007" path="validation.js" start="2157,2159" end="2160" /> only checks that each individual output amount and each individual issue-input amount stay below `constants.MAX_CAP` (9e15) [1](#0-0) . For assets defined without a `cap` field, issuance is unbounded — an issuer can repeat `type: "issue"` inputs indefinitely, each one individually validated but never summed against any global ceiling [2](#0-1) . Because `MAX_CAP = 9e15` is set intentionally close to `Number.MAX_SAFE_INTEGER` (9007199254740991) [3](#0-2) , a small number of such issuances (or of transfers accumulating to one address) can push a single address's cumulative asset balance, or the asset's total circulating supply, past `Number.MAX_SAFE_INTEGER`. All of these amounts are handled as ordinary JS numbers throughout validation, wallet composition and the AA formula engine, so values above that threshold silently lose precision.

### Finding Description
ocore already recognizes this exact bug class for AA-held balances: `aa_composer.js` defines `MAX_BALANCE = 2**63 - 1 - MAX_MESSAGES_PER_UNIT * MAX_CAP` and explicitly rejects triggers/updates that would push an AA's per-asset balance above it, returning `"balance overflow"` [4](#0-3) [5](#0-4) [6](#0-5) . This is precisely the "global outbound/cumulative limit" defense recommended in the reference report, but it is implemented **only for AA balances**.

No equivalent aggregate check exists for:
1. **Uncapped-asset total issuance** — `validateAssetDefinition` only bounds a single `cap` value or per-denomination caps [7](#0-6) ; when `cap` is absent, issuance has no ceiling at all, and each issue input is checked independently against `MAX_CAP` with no running total [8](#0-7) .
2. **Regular (non-AA) address balances** — `validatePaymentInputsAndOutputs` validates `total_input == total_output` per message using plain JS arithmetic [9](#0-8) , but never checks that an address's *cumulative* balance for an asset (summed across many stable units over the asset's lifetime) stays within `Number.MAX_SAFE_INTEGER`.

Once amounts exceed `Number.MAX_SAFE_INTEGER`, double-precision arithmetic can make two mathematically distinct integers compare as equal (`total_input == total_output`) even though the true BIGINT-stored values differ by more than the rounding error, or vice versa. The codebase's own `checkBalances` sanity job in `aa_composer.js` already tolerates and explicitly ignores such discrepancies once values pass `Number.MAX_SAFE_INTEGER`, filtering them out as inconsequential "precision loss" rather than treating them as consensus-relevant [10](#0-9) , confirming the underlying numeric model is not safe once magnitudes reach that region — yet the transaction-time validator that decides consensus validity performs no equivalent bound on non-AA balances.

### Impact Explanation
If an issuer of an uncapped asset (or a series of colluding senders) repeatedly issues/transfers amounts just under `MAX_CAP` to the same address until the cumulative balance crosses `Number.MAX_SAFE_INTEGER`, subsequent payment validation for that address's outputs/inputs of that asset can pass `total_input == total_output` checks that are actually incorrect at the true integer level, because both sides collapse to the same imprecise double. This can let an attacker manufacture additional balance (supply inflation) that different, more precise consumers of the ledger (e.g., a hub storing BIGINT in SQL versus the JS-number validation path) would disagree on, causing node disagreement on validity/balance and potential unauthorized value creation for that asset.

### Likelihood Explanation
Likelihood is low: it requires either (a) an asset issuer willing/able to issue very large uncapped totals over time, or (b) many colluding senders funneling large sums to one address, before the precision boundary near 9e15 is crossed. This mirrors the "High impact / Low likelihood" characterization of the source report — individually-checked amounts are safe, but there is no defense against the cumulative case, exactly as in the original finding.

### Recommendation
- Track the cumulative issued amount for uncapped assets (e.g., persisted running total per asset) and reject issuance once the total would exceed a safe threshold well below `Number.MAX_SAFE_INTEGER`.
- Extend the `MAX_BALANCE`-style overflow check currently applied only to AA balances in `aa_composer.js` [4](#0-3)  to ordinary address balances validated in `validatePaymentInputsAndOutputs`, rejecting units whose resulting cumulative balance for an asset would exceed a safe integer bound.
- Consider using BigInt or an arbitrary-precision library consistently for amount arithmetic in the validation hot path, rather than relying on doubles once magnitudes approach `MAX_CAP`.

### Proof of Concept
1. Define an asset without a `cap` field (`issued_by_definer_only: true`), which is accepted by `validateAssetDefinition` [7](#0-6) .
2. As the definer, repeatedly post `payment` messages with `type: "issue"` inputs of amount `9e15` (the max allowed by `input.amount > constants.MAX_CAP` check) [8](#0-7) , each with an incrementing `serial_number`, all crediting the same output address.
3. After two such issuances, the address's asset balance (1.8e16) exceeds `Number.MAX_SAFE_INTEGER` (~9.007e15). No validation step anywhere sums historical issuance or checks the resulting balance against a safe bound (unlike the AA-only `MAX_BALANCE` check).
4. Further transfers/spends of this balance are validated using plain JS-number equality (`total_input !== total_output`) [11](#0-10) , which is unreliable once operands exceed the safe-integer range, allowing crafted amounts to pass balance checks that should fail at the true integer level.
