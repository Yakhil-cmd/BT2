I investigated whether the Polkadot SDK has an analog of this Bancor bug — pool withdrawals settled on a first-come-first-served basis against a reference point that doesn't reflect real-time reserve/supply changes, causing later withdrawers to get shortchanged or leaving losses unevenly distributed.

**pallet-asset-conversion** (`substrate/frame/asset-conversion/src/lib.rs`): `do_remove_liquidity` computes each withdrawal as a proportional share of *current* reserves against the *current* LP token `total_issuance`, not a fixed/historical reference point: [1](#0-0) 

This is precisely the "distribute losses evenly" fix the Bancor report recommends — every LP token represents a live pro-rata claim on the pool's actual reserves at withdrawal time, so gains/losses are automatically spread across all remaining holders rather than benefiting only earlier withdrawers. The Bancor bug specifically arose because `LiquidityPoolV2Converter` divided by a fixed `initialPoolSupply` captured at pool creation instead of the live token supply — `pallet-asset-conversion` does not replicate that pattern.

**pallet-nomination-pools** (`substrate/frame/nomination-pools/src/lib.rs`): slashes are applied via a points/balance ratio mechanism across bonded and unbonding sub-pools, explicitly designed so that "100 points in a bonded pool can be worth 90 DOTs" — i.e., losses are absorbed by adjusting the point-to-balance ratio for all points-holders in a pool/sub-pool, not by draining balance for early withdrawers while leaving nothing for later ones: [2](#0-1) [3](#0-2) 

The `withdraw_unbonded` extrinsic applies pending slashes before computing `balance_to_unbond`, and caps the withdrawal to `transferable_balance`, which is itself derived from the (already-adjusted) points/balance ratio: [4](#0-3)  Tests (`pool_slash_non_proportional_only_bonded_pool`, `pool_slash_non_proportional_bonded_pool_and_chunks` in `substrate/frame/nomination-pools/test-delegate-stake/src/lib.rs`) confirm slashes reduce the shared pool balance/points ratio for all remaining members, not just the last withdrawer.

**Conclusion:** Both of the closest analogs in this codebase — `pallet-asset-conversion`'s liquidity removal and `pallet-nomination-pools`' slashing/withdrawal — already implement the share/ratio-based proportional accounting that the Bancor report's "Recommendation" section calls for as the fix. Neither uses a fixed historical reference point (like Bancor's `initialPoolSupply`) that could let early withdrawers race to drain reserves while leaving later stakers with nothing. I did not find a genuine, reachable analog of this specific bug class in the current codebase.
