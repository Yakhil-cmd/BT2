This confirms the trust-binding break: the `status` webhook handler matches on `Commit.where(sha: params.sha)` globally, and `StatusHandler` at [1](#0-0)  operates on the sha across all stacks with no repository/organization scoping check at all beyond the top-level signature verification — which is keyed off `repository.owner.login`, not the sha's actual owning stack. Combined with `WebhooksController#verify_signature` selecting the verifying `github_app`/secret using `params.dig('repository','owner','login')` while never validating this owner matches the repository that owns the target commit/stack that ends up mutated, this is a genuine analog of the reported bug class: a field used for the trust decision (verification key selection) is decoupled from the field(s) actually acted upon.

### Title
Webhook signature verification keys off `repository.owner.login` while status/commit mutations are scoped only by SHA across all stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against based on the attacker-suppliable `repository.owner.login` (or `organization.login`) field of the JSON body, via `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature`. [2](#0-1)  Any org configured in the multi-app `secrets.yml` schema (documented at [3](#0-2) ) has its own independent `webhook_secret`, known to whoever administers that org's GitHub App. Once a request authenticates against that org's secret, the `status` handler does not re-validate that the payload's `repository` corresponds to a repository actually owned by that org — it looks up commits purely by `sha` across the entire installation: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) .

### Finding Description
The equality that should hold is: *organization whose secret authenticated the request* == *organization owning the stack/commit being mutated*. Before the fix in the analogous upstream bug class, an amount computed from one leftover source ended up not attributed to the same bucket it was drawn from; here, the identity used to pass HMAC verification (`repository.owner.login`, scoped per-GitHub-App secret) is never re-checked against the identity of the resource the handler subsequently writes to. The `StatusHandler` params schema only requires `sha`, `state`, and other loose optional fields, with no `repository` binding requirement at all [4](#0-3) , and its `process` method resolves target commits solely via a global `Commit.where(sha: ...)` lookup, independent of which org's secret validated the request. Because SHAs are effectively public information (visible in any repo, PR, or webhook payload the attacker's own org already receives) and Shipit stores commits from all onboarded repositories in a single `commits` table, an org administrator who knows only their own org's `webhook_secret` can forge a `status` event with a SHA belonging to a stack/repository owned by an entirely different organization, sign it with their own secret, and have it accepted and applied to that unrelated commit.

### Impact Explanation
Applying a forged `success` status to a foreign commit feeds directly into merge/deploy trust decisions: `Commit#create_status_from_github!` persists the status, `Status#schedule_continuous_delivery` runs, and any pending `MergeRequest` for that commit is re-evaluated via `ProcessMergeRequestsJob`, which calls `all_status_checks_passed?` → `StatusChecker` and, if it now reports success, invokes `MergeRequest#merge!`, which calls GitHub's merge API to merge the pull request into the victim's repository [5](#0-4) [6](#0-5) . This lets an attacker who administers a separate, legitimately-onboarded organization inject a fabricated passing CI status for a commit in a victim organization's repository, bypassing required checks and causing an unauthorized cross-organization merge/deploy decision — a cross-repository write outside the attacker's own credential scope.

### Likelihood Explanation
High: any organization admin who legitimately owns a GitHub App configured in Shipit's multi-org `secrets.yml` already possesses a valid `webhook_secret` for signing arbitrary payloads to the shared `/webhooks` endpoint, requires no Shipit session, `ApiClient` token, or GitHub write access to the victim repository, and only needs to know a target commit SHA (routinely public via PR links, CI badges, or the target repo's own webhook deliveries which many CI integrations broadcast).

### Recommendation
The `status` (and any other) webhook handler must be scoped to the repository/organization that the verified signature belongs to: pass the authenticated `repository_owner`/organization identity from `WebhooksController#verify_signature` down into the handler dispatch, and require `Handler` subclasses (in particular `StatusHandler`) to filter target commits/stacks through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` scoped additionally to the verified organization, rejecting or ignoring events whose `repository.owner.login`/`organization.login` does not match the org whose secret validated the signature.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.yml`: `VictimOrg` (owns `VictimOrg/app`, a stack with a pending `MergeRequest` awaiting one passing `ci/tests` status) and `AttackerOrg` (attacker is a legitimate admin of this org's own GitHub App, hence knows `AttackerOrg`'s `webhook_secret`).
2. Attacker observes/knows the head SHA of the victim PR (e.g. via the PR's public GitHub page).
3. Attacker crafts a `status` event JSON body: `{"sha": "<victim_head_sha>", "state": "success", "context": "ci/tests", "repository": {"owner": {"login": "AttackerOrg"}, "full_name": "AttackerOrg/whatever"}}`.
4. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s known `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"AttackerOrg"`, looks up `Shipit.github(organization: "AttackerOrg")`, and the signature verifies successfully [7](#0-6) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (owned by `VictimOrg`), and creates a passing status on it, with no check that `VictimOrg` matches the authenticating `AttackerOrg` [1](#0-0) .
7. `ProcessMergeRequestsJob` subsequently sees all checks passed for the victim's pending merge request and calls `merge!`, merging the PR into `VictimOrg/app` — an unauthorized cross-organization merge triggered entirely with `AttackerOrg`'s own credentials.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
