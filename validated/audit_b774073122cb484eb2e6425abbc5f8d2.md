### Title
Floor-division rounding loss in TPS fee distribution permanently strands part of `total_tps_fees_delta` among multiple recipients - (File: `storage.js`)

### Summary
`storage.js`'s `updateTpsFees()` distributes each unit's change in TPS fee (`total_tps_fees_delta`) among one or more recipient addresses (header-commission-sharing authors) using `Math.floor(total_tps_fees_delta * share / 100)`. When a unit has multiple recipients with percentage shares that don't divide the delta evenly, the sum of the floored per-recipient amounts is smaller than `total_tps_fees_delta`, and the remainder is never credited to anyone or carried forward. This mirrors the reported `notifyRewardAmount()` rounding-dust bug class (`rewardRate = reward.div(duration)` truncation), except here it recurs on every stable unit with multiple earned-headers-commission recipients.

### Finding Description
`updateTpsFees()` computes, for each newly stabilized unit, the difference between its previously-recorded `tps_fee` and its newly computed `actual_tps_fee`: [1](#0-0) 

For every recipient address returned by `getTpsFeeRecipients()`, the code does:
```
const tps_fees_delta = Math.floor(total_tps_fees_delta * share / 100);
```
and adds that value to the recipient's running `tps_fees_balance`. Because `Math.floor` always rounds toward negative infinity (truncating any fractional remainder), when a unit has several recipients whose `share` percentages don't evenly divide `total_tps_fees_delta`, the sum of the per-recipient `tps_fees_delta` values is strictly less than `total_tps_fees_delta`. Unlike the headers-commission distribution logic in `headers_commission.js`, which explicitly uses `Math.round` (see `Math.round(full_amount * share / 100.0)` at `headers_commission.js:183` and `:202`) to minimize rounding bias, the TPS-fee code uses `Math.floor`, guaranteeing the total distributed is monotonically less than or equal to the true delta, with no mechanism to re-queue or redistribute the truncated remainder on a subsequent call. There is also no accumulator (analogous to `queuedRewards` in the reported Solidity bug) that carries the lost fractional amount into the next `notifyRewardAmount`/`updateTpsFees` cycle.

This is directly reachable by any unpaired unit poster: any address can become an `earned_headers_commission_recipients` co-recipient of a unit's TPS fee shares (multi-authored/co-signed units routinely define multiple recipients with arbitrary percentage splits), and `updateTpsFees()` runs automatically for every stabilized unit from `v4UpgradeMci` onward, compounding the loss over time.

### Impact Explanation
The TPS-fee balance (`tps_fees_balance`) is consumed later via `getPaidTpsFee()`, which reads back the balance per recipient, divides by `share` and compares against `min_tps_fee` used in validation logic (`validation.js` references `tps_fees_balance` in at least 5 places) to determine how much TPS fee a unit has effectively pre-paid. Because floor-division causes a systematic under-crediting of `tps_fees_balance` whenever a unit has multiple percentage-based recipients, addresses that share TPS-fee credit are consistently credited slightly less than what they truthfully worked/paid for. Over many units (each stable unit can trigger this update, further multiplied by `count_aa_responses`), the accumulated shortfall is not bounded to a single rounding unit like in the Solidity report — it can grow unboundedly as calls repeat, permanently depriving recipients of a portion of the fee credit they should be entitled to. This weakens the intended TPS-fee accounting/anti-spam economics, resulting in unwarranted under-crediting (economic loss) to unprivileged addresses who are earned-header-commission recipients, without any mechanism to recover the truncated dust.

Because every fully-synced node performs the exact same deterministic floor computation, this does not cause node disagreement on validity/stability by itself, so the primary damage is the functional-fund-loss/economic-drain to affected recipients, not a consensus split.

### Likelihood Explanation
Any multi-authored/co-signed unit whose author defines `earned_headers_commission_recipients` with non-trivial percentage splits (a completely normal, unprivileged, user-controlled feature already used for headers-commission sharing) will trigger this rounding loss automatically every time `updateTpsFees()` processes that unit post-`v4UpgradeMci`. No special privilege or malicious network behavior is required — only posting ordinary multi-author units with commission-recipient definitions repeatedly, which is a completely realistic and common usage pattern (team wallets, shared mining/witness setups, etc.). The loss compounds naturally with normal network activity, making exploitation/occurrence high-likelihood, though the per-unit magnitude is small (bounded by the number of recipients and share granularity).

### Recommendation
Change the TPS-fee distribution in `updateTpsFees()` from `Math.floor` to `Math.round`, mirroring the same pattern already used correctly in `headers_commission.js` (`Math.round(full_amount * share / 100.0)`), or explicitly track/carry forward the rounding remainder (e.g., allocate any leftover dust to a designated primary recipient, similar to accumulating into `queuedRewards` in the reported vulnerability) so that the sum of all per-recipient deltas always equals `total_tps_fees_delta` exactly.

### Proof of Concept
1. Author unit `U` with two `earned_headers_commission_recipients`: address A with `share=1` (%) and address B with `share=99` (%).
2. Suppose `total_tps_fees_delta` for `U` = 150 (in indivisible fee units).
   - For A: `Math.floor(150 * 1 / 100) = Math.floor(1.5) = 1`
   - For B: `Math.floor(150 * 99 / 100) = Math.floor(148.5) = 148`
   - Total credited = 1 + 148 = 149, while the true delta is 150 — 1 unit is permanently lost and never credited to any address.
3. Because `updateTpsFees()` is invoked for every stable unit (and multiplied per AA response count via `objUnitProps.count_aa_responses`), repeating this pattern across many units compounds the uncredited/lost TPS-fee balance without any corrective or catch-up mechanism, matching the "notifyRewardAmount rounding dust" bug class from the external report.
