### Title
Submodule URLs from untrusted repo content reuse git-sync's stored credentials, enabling confused-deputy fetch of unauthorized content into the published volume - (File: main.go)

### Summary
`git-sync` performs `git submodule update --init [--recursive]` automatically on every sync, using submodule URLs that come entirely from the **tracked repository's `.gitmodules` file** — i.e., untrusted content that anyone with push/merge access to the synced ref controls. Because git-sync's authentication is configured globally (via `git config --global credential.helper 'cache ...'` and `git credential approve`), any submodule URL that resolves to the same host as the primary `--repo` will silently reuse the operator's stored credentials for that host. This lets an attacker who can push a commit to the tracked branch (but who does not have legitimate access to some *other* private repository on the same git host) smuggle a submodule pointing at that other repository, causing git-sync's authenticated identity to fetch it and publish its contents through the trusted symlink.

### Finding Description
`configureWorktree` unconditionally runs submodule update for any hash it checks out, driven by `git.submodules` (`recursive` by default): [1](#0-0) 

The submodule URLs are read from `.gitmodules`, which is ordinary repo content synced from `git.ref` — content an attacker can fully control by pushing a commit (the exact "untrusted repo content" trust boundary this analog targets), and there is no allowlist flag restricting which hosts/paths submodules may point to.

Credentials are established process-wide and keyed only by the URL(s) passed to `StoreCredentials`/`--credential`/`--username`: [2](#0-1) 

and the credential cache is configured globally for the whole `git` invocation environment: [3](#0-2) 

Git's default credential matching keys on `protocol://host` (not full path) unless `credential.useHttpPath` is set, which git-sync does not set. Consequently, when `configureWorktree` shells out to `git submodule update --init --recursive` for a submodule URL sharing the primary repo's host but a different path/repo, git will transparently offer the cached credential to authenticate that fetch — a classic confused-deputy pattern. The retrieved submodule content is checked out into the worktree and unconditionally published via the atomic symlink flip: [4](#0-3) 

This mirrors the reported `Fees::sellProfits()` bug class: a function reachable by an under-privileged/untrusted actor (there, "anyone calling `sellProfits`"; here, "anyone who can commit to the synced ref") drives a sensitive, credentialed operation (there, swap execution; here, submodule fetch+publish) with attacker-supplied parameters (there, swap amount/pool; here, submodule URL) and no validation/allowlisting, causing assets/data the caller should not control to be moved/exposed (there, contract's ERC-20 balance; here, another private repository's contents and reuse of the sync credential).

### Impact Explanation
An attacker with only write/merge access to the tracked ref of the synced repository can cause git-sync to fetch and publish the contents of an unrelated, otherwise-inaccessible-to-them repository on the same git host, using the operator's own stored credentials. This is disclosure of unauthorized content ("publishing wrong or partial content") and effectively a credential/authorization-scope confusion, since the fetch is performed with the shared service credential rather than the attacker's own (lack of) access. Depending on deployment (e.g., a shared CI/CD PAT with org-wide read access, or an SSH deploy key with broader `insteadOf`/host-wide scope), this can expose sensitive private repository contents to downstream consumers of the git-sync volume.

### Likelihood Explanation
Likelihood is moderate-to-high in any git-sync deployment that (a) allows submodules (the default is `recursive`), and (b) grants the sync identity credentials scoped at the host level rather than to a single exact repository path (common for PATs, GitHub Apps installed org-wide, or SSH keys with host-level access), and (c) the tracked repository accepts contributions/merges from less-trusted parties. No special flags beyond the default `--submodules=recursive` are required; the attacker only needs the ability to add/modify `.gitmodules` in a commit that gets synced.

### Recommendation
- Add an explicit submodule URL allowlist (e.g., a `--submodule-allowed-hosts`/`--submodule-allowed-urls` flag) validated before running `git submodule update`, rejecting any submodule whose resolved URL is not on the allowlist.
- Set `credential.useHttpPath=true` (or scope credentials more narrowly) so cached credentials are not offered to arbitrary paths on the same host.
- Document/require operators to scope sync credentials to the exact repository path rather than host-wide access, and warn prominently in the README about the confused-deputy risk of `--submodules` combined with host-scoped credentials.

### Proof of Concept
1. Operator configures `git-sync --repo=https://git.example.com/org/legit-repo --submodules=recursive` with a PAT that has read access to `org/legit-repo` and, incidentally (host-scoped token), to `org/private-repo` as well.
2. Attacker, who only has push access to `org/legit-repo`, commits a `.gitmodules` entry:
   `git submodule add https://git.example.com/org/private-repo secret`
3. On next sync, `configureWorktree` (main.go:1733-1747) runs `git submodule update --init --recursive`; git offers the cached PAT (stored via `StoreCredentials`, matched by host per default `credential.helper` config) to fetch `org/private-repo`.
4. `publishSymlink` (main.go:1960) atomically publishes the new worktree, including `secret/` containing `org/private-repo`'s contents, into the shared volume consumed by the application — data the attacker was never authorized to read directly but can now retrieve via any sidecar/app reading the synced volume.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

		}
