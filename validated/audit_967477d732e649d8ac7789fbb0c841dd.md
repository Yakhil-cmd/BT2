### Title
Deposited block-revenue delegator rewards can become permanently frozen in a vote account when it loses all delegated stake before distribution - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`pending_delegator_rewards` is accumulated in a vote account via `deposit_delegator_rewards` (SIMD-0123), and is only ever decremented implicitly by being paid out as `block_reward` to still-delegated stake accounts during `calculate_block_reward`. If a vote account's total active delegated stake for the reward epoch (`total_active_stake`, sourced from `RewardEpochDelegatedStakes`) is zero at reward-calculation time, no stake delegation exists to receive the payout, so `pending_delegator_rewards` is never reduced. Because `withdraw()` unconditionally refuses to close a vote account (or reduce its balance below `pending_delegator_rewards + rent_exempt_minimum`) while `pending_delegator_rewards > 0`, the deposited lamports become permanently stuck: unpayable to any staker and unwithdrawable by the authorized withdrawer.

### Finding Description
`add_pending_delegator_rewards` credits `pending_delegator_rewards` on deposit with no expiry or reconciliation mechanism: [1](#0-0) 

The only code path that reduces the effective unpaid balance is `calculate_block_reward`, which computes a stake delegation's share of `pending_delegator_rewards` proportional to `stake / total_active_stake`. When `total_active_stake` for the vote account is zero (i.e., no delegated stake is recorded in `reward_epoch_delegated_stakes` for that epoch), the function short-circuits and returns `0`: [2](#0-1) 

This function is only invoked per-existing `stake_delegations` entry in `calculate_stake_rewards_and_commissions`: [3](#0-2) 

If there are zero stake delegations pointed at the vote account (fully undelegated/deactivated validator), this loop never even calls `calculate_block_reward` for that vote pubkey, so `pending_delegator_rewards` is untouched — it is neither distributed to any staker nor reset.

Meanwhile, `withdraw()` in the vote program enforces that a vote account cannot be closed, nor drawn below `rent_exempt_minimum + pending_delegator_rewards`, while `pending_delegator_rewards > 0`: [4](#0-3) 

Since nothing in the codebase ever explicitly zeroes or refunds `pending_delegator_rewards` other than the block-reward payout path (confirmed by exhaustive search — no `checked_sub`/`saturating_sub`/reset assignment exists for this field outside test code), a vote account that reaches zero total delegated stake while still holding a nonzero `pending_delegator_rewards` balance has no code path to ever clear that balance. The lamports remain locked in the account forever, and the account can never be closed.

### Impact Explanation
This is a direct analog of the reported bug class: rewards deposited for distribution during a period when the "pool" (here, the vote account's delegated stake) has zero size become permanently unwithdrawable by anyone — not the intended stakers (there are none to pay), and not the vote account's authorized withdrawer (blocked by the `withdraw()` check). This constitutes a permanent freezing of lamports, matching the "frozen accounts" acceptance criterion.

### Likelihood Explanation
This requires a validator vote account to have accumulated `pending_delegator_rewards` (via `DepositDelegatorRewards`, gated behind SIMD-0123/`block_revenue_sharing`, `commission_rate_in_basis_points`, and `custom_commission_collector` features) while its delegated stake later drops to zero before the reward-calculation epoch snapshot is taken. This is plausible for a validator that is fully undelegated/deactivated shortly after receiving block-revenue deposits, and is unprivileged from the perspective of the affected delegators — no delegator or validator misbehavior is required, just an ordinary full-unstake event coinciding with reward timing.

### Recommendation
When `total_active_stake == 0` for a vote account during block-reward calculation (or more generally, whenever no stake delegation exists to absorb `pending_delegator_rewards`), the outstanding `pending_delegator_rewards` should either be reassigned (e.g., to a fee/incinerator sink, similar to the referenced Valkyrie fix accumulating to `accumulatedFees`) or made withdrawable by the vote account's authorized withdrawer once no stake is delegated, instead of being permanently locked and simultaneously blocking `withdraw()`/account closure indefinitely.

### Proof of Concept
1. Enable SIMD-0123 features (`block_revenue_sharing`, `commission_rate_in_basis_points`, `custom_commission_collector`) and create a `VoteStateV4` vote account with active delegated stake.
2. Call `DepositDelegatorRewards` to add lamports; `pending_delegator_rewards` becomes non-zero as verified in the existing test at [5](#0-4) .
3. Fully deactivate/withdraw all stake delegated to this vote account so that, by the time `RewardEpochDelegatedStakes` is computed for the reward epoch, `delegated_stakes.get(&vote_pubkey)` is `None`/`0`.
4. Run epoch reward calculation: `calculate_block_reward` returns `0` for this vote account due to the `total_active_stake == 0` branch, and since no stake delegations reference the vote account, it is never invoked with any distribution.
5. Attempt to call `withdraw()` (or `CloseVoteAccount`) with the authorized withdrawer: it fails with `InstructionError::InsufficientFunds` per the `pending_delegator_rewards > 0` check, and this condition can never be resolved because no future code path reduces `pending_delegator_rewards` when there are no stake delegations to pay it out — the deposited lamports are permanently frozen.

        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());

        }

        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
