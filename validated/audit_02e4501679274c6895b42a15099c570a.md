### Title
Cross-tenant CCMenu deploy/rollback metadata disclosure via unscoped `stack` lookup - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` overrides `Api::BaseController#stack` and resolves the target stack via the global `Stack.from_param!(params[:stack_id])` instead of the token-scoped `stacks.from_param!(params[:stack_id])`. Any valid `ApiClient` token with `read:stack` permission — even one minted for an unrelated stack A — can therefore fetch `#show`'s CCMenu XML for any other stack B, leaking that stack's latest deploy/rollback metadata (commit sha, status, `webUrl`).

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`stack_resolved_in(Api::CCMenuController#show) == stack_scoped_by(current_api_client.stack_id)` — in the base controller this equality holds via `stacks` [1](#0-0) , but `CCMenuController` breaks it by redefining `stack` to bypass the scope entirely: [2](#0-1) 

`Api::BaseController#stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the token is bound to a specific stack [3](#0-2) . `CCMenuController` does not use `stacks` at all; it calls `Stack.from_param!` directly against the entire `Stack` relation, so `params[:stack_id]` can name any stack in the system regardless of what the presented token is scoped to.

The `require_permission :read, :stack` before_action only checks that the token's `permissions` array contains the string `"read:stack"` — it never compares against `stack_id`: [4](#0-3) 

So a token that was issued for stack A but carries `read:stack` permission passes this check unconditionally, no matter which stack is requested. Once past the permission check, `show` renders `stack.deploys_and_rollbacks.last` (or `NoDeploy`) directly into the `shipit/ccmenu/project` XML template with no further ownership comparison: [5](#0-4) 

Exploit flow: attacker holds a CCMenu token for stack A (self-owned, `read:stack` permitted). They request `GET /api/stacks/:owner_b/:repo_b/:env_b/ccmenu.xml?token=<A's token>` (or whatever URL param name the mounted route uses for `stack_id`) naming private stack B. `authenticate_api_client` in this controller only verifies the token signature via `ApiClient.authenticate(params[:token])` [6](#0-5) , `require_permission` passes because A's token has `read:stack`, and `stack` resolves stack B unscoped. The response XML then contains stack B's latest deploy/rollback commit sha, status and URL.

Existing guards that fail to prevent this: `verify_signature`/webhook checks are irrelevant here (this is a GET API endpoint, not the webhook path); `ExplicitParameters`/model validations don't scope stacks; `require_permission!` checks only the permission string, not the `stack_id` binding; and the scoping mechanism that does exist (`Api::BaseController#stacks`) is simply not used by this controller because it defines its own `stack` method that shadows it.

### Impact Explanation
An attacker who legitimately holds any CCMenu/API token scoped to their own stack (or even a generic token with `read:stack` and no `stack_id` restriction) can read the latest deploy/rollback status, commit SHA, and `webUrl` for any other stack in the Shipit instance, including private repositories they have no GitHub access to. This is a cross-tenant unauthorized read of stack/deploy state, repeatable against arbitrary stack IDs by simple parameter substitution, matching the High severity category ("unauthenticated read of stack state ... across a stack the token isn't scoped for").

### Likelihood Explanation
Preconditions are minimal: the attacker only needs any valid `ApiClient` token bearing `read:stack` permission — this could be a token they were issued for their own project. No GitHub access to the victim's repository, no Shipit session, and no secrets are required. The `stack_id`/route path for the target stack is typically guessable or discoverable (owner/repo/environment naming), making this trivially repeatable across many stacks.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that when `current_api_client.stack_id?` is true the lookup is constrained exactly as it is for every other API controller.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b` (`stack_b` simulating a private repo), each with a deploy/rollback that has a distinct, known commit sha.
2. Create an `ApiClient` scoped to `stack_a.id` with `permissions: ['read:stack']`, generate `token_a = api_client.authentication_token`.
3. `get shipit.api_ccmenu_path(stack_b), params: { token: token_a }` (or the corresponding route for stack B).
4. Assert `response.status == 200` and the XML body includes `stack_b`'s deploy's `lastBuildLabel`/commit sha — a value never exposed to `token_a`'s owner via any authorized channel.
5. Assert equality-side-by-side: `assigns(:stack)&.id` (or the stack resolved inside the controller) equals `stack_b.id` even though `current_api_client.stack_id == stack_a.id`, demonstrating the binding `stack_resolved == stack_scoped_by(current_api_client.stack_id)` does not hold.
