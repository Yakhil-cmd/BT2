### Title
Webhook signature is verified against a GitHub App config selected from an unauthenticated payload field, while the actual repository/stack acted upon comes from a different, unverified field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App configuration (and therefore which `webhook_secret`) to validate the request against using `repository_owner`, a value read straight out of the untrusted, unauthenticated JSON body — before the HMAC signature has been checked. The event handlers, however, resolve the `Repository`/`Stack` to act on using a completely different field, `repository.full_name`. In a multi-organization Shipit deployment (the documented `github: <org>: {...}` schema), this breaks the binding "the organization whose secret authenticated this webhook" == "the organization/repository the webhook payload is allowed to act on."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is attacker-controlled: it's parsed from the raw, unauthenticated request body before any signature check occurs. It is used solely to pick the `GitHubApp` instance (and thus the `webhook_secret`) that `verify_webhook_signature` checks against:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret

  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

Critically, if an organization is configured with no `webhook_secret` (a supported, documented configuration — see `webhook_secret: # nil` in the multi-org example), `verify_webhook_signature` returns `true` unconditionally for **any** payload/signature pair: [3](#0-2) 

`Shipit.github(organization:)` looks the config up purely by the organization name string, with no cross-check against the rest of the payload:
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  @github ||= {}
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [4](#0-3) 

Once `verify_signature` passes (head(422) is only called on failure, but `create` is not itself gated by this — see below), `WebhooksController#create` dispatches the *entire unauthenticated payload* to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Handlers resolve the target `Repository`/`Stack` using `repository.full_name` from the same payload — a field never tied to, or cross-validated against, `repository.owner.login` used for signature-org selection:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`PushHandler` uses this to trigger real state changes (`sync_github`) on any matching stack:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [7](#0-6) 

Other handlers (membership, pull_request opened/labeled/closed/reopened) similarly act on entities keyed from `repository.full_name` or other payload fields independent of `repository.owner.login`.

**Attack**: In a deployment with two configured orgs — one high-value org (`OrgOne`, real secret) and any other org present in the config with a blank/absent `webhook_secret` (`OrgTwo`, as shown in the shipped multi-org example config) — an attacker POSTs to `/webhooks` with:
- `repository.owner.login = "OrgTwo"` (selects the org whose `verify_webhook_signature` always returns true)
- `repository.full_name = "OrgOne/victim-repo"` (the real, protected stack)
- any `X-Github-Event` / arbitrary `X-Hub-Signature` value (irrelevant, since it will be trivially accepted)

The signature check passes unconditionally (because `OrgTwo` has no `webhook_secret`), yet the payload's `repository.full_name` field — never covered by that check — drives the handler to act on `OrgOne`'s repository/stack.

### Impact Explanation
This crosses an authentication boundary: an unprivileged, unauthenticated actor can forge GitHub webhook events for repositories/organizations they do not control, causing Shipit to trigger `GithubSyncJob`, `Membership`/`Team` creation, pull-request-driven review-stack `archive!`/`unarchive!`/provisioning, and status/commit processing for arbitrary stacks — effectively an authentication bypass on the webhook ingestion boundary and a cross-repository/cross-organization state-manipulation vector, which maps to "High - unauthenticated read/manipulation of stack state" in the rubric (and can escalate toward unauthorized deploy state changes depending on which webhook events are wired to deploy-adjacent behavior, e.g. `GithubSyncJob` affecting `undeployed_commits`/CI status used to gate deploys).

### Likelihood Explanation
Requires only that the deployment use the multi-organization `github:` config schema with at least one organization lacking a `webhook_secret` (an explicitly documented/supported configuration in this codebase, `test/dummy/config/secrets_double_github_app.yml`). No credentials, no GitHub App private key, and no prior access are needed — a single unauthenticated HTTP POST to the public `/webhooks` endpoint suffices.

### Recommendation
Do not let any field taken from the unauthenticated payload determine which secret is used to validate that same payload's authenticity. Concretely:
- Verify the webhook signature using every configured organization's secret in a signature-first, org-agnostic way (or require the actual target repository's owner — resolved via `repository.full_name`, which is what handlers act on — to match, and verify with that owner's secret), rather than trusting `repository.owner.login`/`organization.login` pre-verification.
- After verification succeeds, additionally assert that the verified organization equals the owner of the repository named in `repository.full_name` before invoking any handler.
- Treat organizations configured without a `webhook_secret` as unable to authenticate cross-repository events, or require `webhook_secret` to be mandatory in multi-org configs.

### Proof of Concept
1. Deploy Shipit with a multi-org `github:` config where `OrgOne` has a real `webhook_secret` and `OrgTwo` has none (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` → `verify_webhook_signature` returns `true` because `OrgTwo`'s `webhook_secret` is blank, regardless of the bogus `X-Hub-Signature`.
4. `create` dispatches the payload to `PushHandler`, which resolves the stack via `Repository.from_github_repo_name("OrgOne/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgOne`'s real stack — an unauthenticated actor has driven state changes on a repository they never proved control of.
