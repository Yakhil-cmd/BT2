### Title
Webhook signature verified against organization only, while `StatusHandler` writes commit status with no repository binding at all - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook only against the **organization** derived from the payload, using that organization's shared `webhook_secret`. Downstream, `Shipit::Webhooks::Handlers::StatusHandler` never re-checks that the commit/repository the status applies to is the one that was actually verified — it looks up commits by SHA across the **entire installation**, with no repository or organization scoping whatsoever. This breaks the intended binding "organization that authenticated == repository that is written," which is precisely the class of bug the `minAmountOut_` report illustrates: a value is checked in one place (the org used to pick the HMAC secret) but a materially different value (the specific repository/commit the mutation applies to) is never validated against it.

### Finding Description
`WebhooksController#verify_signature` derives the organization solely from the payload's `repository.owner.login` (or `organization.login`) field and fetches that organization's GitHub App config to validate the HMAC signature: [1](#0-0) [2](#0-1) 

A successful verification only proves the request was signed with the secret configured for *that organization* — Shipit supports multiple GitHub Apps/organizations sharing one instance, each with its own `webhook_secret` as documented in `docs/setup.md`'s "Using Multiple GitHub Applications" section, and one GitHub App installation typically covers many repositories in that org.

Once verification passes, the generic `Handler` base class resolves the target `Stack`/`Repository` from a *different* field of the same payload (`repository.full_name`), independent of the field used for verification: [3](#0-2) 

`StatusHandler`, however, goes further and drops even that scoping — it mutates state by looking up commits by raw SHA with **no repository/organization filter at all**: [4](#0-3) 

`Commit.create_status_from_github!` is invoked for every `Commit` record across the whole Shipit instance that happens to share that SHA, regardless of which repository/organization the verified webhook actually belongs to. Commit statuses gate CI requirements (`ci.require`) and continuous deployment/merge-queue eligibility per `README.md`: [5](#0-4) 

So the equality that should hold — "organization whose secret signed this payload" == "repository/commit that gets its CI status mutated" — is never enforced. The signature only proves *an* org-scoped secret was known; it does not prove the specific commit belongs to a repository under that verified org, nor to the repository named in the payload.

### Impact Explanation
Because the org-wide `webhook_secret` is shared across every repository covered by a GitHub App installation, and `StatusHandler` performs a global, repository-agnostic lookup by SHA, a legitimate CI/status event genuinely fired by GitHub for one repository in the org can cause a `Commit` record belonging to a completely different repository/stack in Shipit to be marked with an attacker-chosen state (e.g. `success`). If a matching commit SHA also exists in a higher-trust stack (e.g. via shared history, forked/mirrored repos, or a crafted commit object with identical tree/parent/author/committer/message/timestamp fields — git commit hashing is deterministic, so an identical commit object recreated in an unrelated repository under the same org yields an identical SHA), this can satisfy `ci.require` and unblock an unauthorized deploy or merge-queue admission for a commit that never passed CI in its real target repository — an unauthorized deploy, matching the "High" impact bucket ("escalation into authorization … or an unauthorized deploy").

### Likelihood Explanation
Exploitation requires the attacker to control (or induce a genuine webhook event from) some repository whose events are signed by the same organization-scoped `webhook_secret` as the target stack — a realistic setup any time a single Shipit instance/GitHub App tracks multiple repositories for one organization, which the project's own multi-org documentation confirms is a supported configuration. No possession of the `webhook_secret` itself, no privileged write access to the *target* repository, and no `ApiClient`/session credential is needed — only the ability to trigger a real, GitHub-signed status/push event on any repository covered by the same organization-level installation.

### Recommendation
`Handler#stacks`/`StatusHandler#process` should scope every downstream lookup (commit, stack, repository) to the repository/organization that was actually verified in `WebhooksController#verify_signature`, rather than trusting an independently-read field of the same untrusted-until-verified payload. Concretely, pass the verified `repository_owner` (and ideally the full `owner/name`) down to the handler and require an exact match against the payload's `repository.full_name` and the `Commit`'s parent `Stack`/`Repository` before applying any status mutation, e.g.:
```ruby
def process
  Commit.where(sha: params.sha).where(stack: Repository.from_github_repo_name(repository_name)&.stacks).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`) with one GitHub App installed on organization `Acme`, tracking two repositories as separate stacks: `Acme/public-sandbox` (low value, attacker has push access) and `Acme/prod-service` (high value stack with `ci.require` configured).
2. Attacker crafts a commit object in `Acme/public-sandbox` with the identical tree, parent, author, committer, message and timestamps as an existing pending commit in `Acme/prod-service` (obtainable from a previously public diff/PR), producing an identical SHA.
3. Attacker sets a `success` commit status on that SHA via the GitHub API for `Acme/public-sandbox` (full control over their own repo).
4. GitHub delivers a genuine, correctly HMAC-signed `status` webhook (signed with `Acme`'s shared `webhook_secret`) to Shipit's `/webhooks` endpoint.
5. `WebhooksController#verify_signature` passes because the signature validates against `Acme`'s secret [1](#0-0) .
6. `StatusHandler#process` matches the SHA against the `Commit` record belonging to `Acme/prod-service` (no repository filter applied) and marks it as passing CI [4](#0-3) , potentially satisfying `ci.require` for `Acme/prod-service` and enabling an unauthorized deploy/merge for a commit that never had genuine CI success in that repository.
