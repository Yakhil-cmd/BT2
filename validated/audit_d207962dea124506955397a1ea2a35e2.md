### Title
Unallowlisted PR-label-derived `ENV`/`BASH_ENV` injection into shell-invoked `bundle`/`ruby` dependency steps enables RCE - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no key allowlist, and this hash is unconditionally merged into `TaskCommands#env`, which is passed to every `Command` built for `install_dependencies` (bundler/ruby steps). Since `Command#start` executes the command line as a single string through the system shell via `PTY.spawn`, an attacker who can label their own PR (`allow_with_label` mode) can inject shell-honored variables such as `ENV`/`BASH_ENV` into the exec environment of the deploy host.

### Finding Description
The broken binding: `TaskCommands#env["BASH_ENV"]` should equal `nil` (no key sourced from an unauthenticated PR label should ever reach the process env used to spawn a shell), but it equals `"true"` for any repository configured `allow_with_label` if the attacker names a label `bash_env`/`BASH_ENV`/etc.

Path:
1. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim from the webhook payload onto `PullRequest#labels`, with only a `String` type check in the `ExplicitParameters` schema — no allowlist on label content. [1](#0-0) 
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` into the base env with no key filtering. [2](#0-1) 
3. `TaskCommands#env` unconditionally merges `@stack.env` (which is `ReviewStack#env` for review stacks) into the process environment used for every command. [3](#0-2) 
4. `install_dependencies` builds one `Command.new(command_line, env:, chdir: steps_directory)` per bundler/ruby dependency step, using that same merged `env`. [4](#0-3) 
5. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` where `interpolated_arguments` is a single string (the whole command line, e.g. `"bundle install --jobs 4 --retry 2"`), which Ruby's `Process.spawn`/`PTY.spawn` executes via `/bin/sh -c` because it is a single multi-word string. [5](#0-4) 

This is corroborated directly by the repo's own tests, which confirm labels flow unfiltered into `env`: [6](#0-5)  and [7](#0-6) .

Attacker request: open a PR from their own fork against a repository configured with `provisioning_behavior: allow_with_label`, apply a label named `bash_env` (case-insensitive; GitHub preserves the label's display case but the handler only reads `.name`, and `ReviewStack#env` force-uppercases it to `BASH_ENV`), and commit a file literally named `true` at the repository root (or wherever `steps_directory` resolves) containing malicious shell code. When Shipit runs the `bundle install`/other ruby dependency step for the review stack, `/bin/sh -c "bundle install ..."` is spawned with `BASH_ENV=true` in its environment; if the resolved shell is `bash` (even invoked as `sh` in POSIX-script-execution mode), Bash sources the file named by `BASH_ENV` before running the actual command, executing attacker-controlled code on the deploy host.

Existing guards do not stop this: `EnvironmentVariables#permit` is used to allowlist deploy/rollback/task `variables` supplied through the public API (`deploy_spec.rb#filter_deploy_envs/filter_rollback_envs`, `task_definition.rb#filter_envs`), but this allowlist is never applied to `ReviewStack#env`'s label-derived hash — it bypasses the allowlist entirely. [8](#0-7) [9](#0-8) 

### Impact Explanation
If reachable (i.e., the deploy host's `/bin/sh` honours `BASH_ENV`/`ENV` in the code path used to spawn the dependency step, and the attacker can place a file with the matching name in the checked-out working directory), this results in arbitrary code execution on the Shipit deploy host under the identity that runs deploy tasks — Critical RCE, matching the stated impact category. The blast radius is scoped to the attacker's own review stack/repository (labels only affect `stack.env` for that stack's tasks), but it lets an unprivileged PR author on any repository with `allow_with_label` provisioning turn a labeled PR into host code execution, without any Shipit credentials.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`, both use the same unfiltered `ReviewStack#env`), which is a repository-level opt-in but is a documented, ordinary Shipit configuration. The attacker needs only the ability to open a PR and apply a label on their own fork — capabilities explicitly listed as available to an unprivileged attacker. The exploit's reliability further depends on operational specifics not verifiable from this codebase alone: whether the deploy host's `/bin/sh` resolves to (or behaves like) `bash` when executing the single-string command, and whether a file literally named after the env var (`true`) placed in the working directory is picked up as the startup file. These are host/OS-configuration dependent, not guaranteed by the engine's code, but the underlying flaw — arbitrary, unfiltered env var **names** reaching a shell-invoked subprocess — is squarely a defect in this engine's own code (`ReviewStack#env` + `Command#start`).

### Recommendation
- Do not let PR label names flow into the process environment un-filtered. In `ReviewStack#env` (`app/models/shipit/review_stack.rb`), run the label-derived hash through `EnvironmentVariables.with(...).permit(...)` against an explicit allowlist (e.g., repository-configured "known label env" definitions), matching the pattern already used for `deploy`/`rollback`/task `variables`.
- Additionally, reject/strip any label name that collides with shell- or loader-sensitive variable names (`BASH_ENV`, `ENV`, `IFS`, `LD_PRELOAD`, `RUBYOPT`, `PATH`, etc.) regardless of allowlist configuration.
- In `Command#start`/`unbundled_env` (`lib/shipit/command.rb`), consider building an explicit denylist of shell/interpreter startup-file variables that are always stripped before spawning, and/or avoid single-string shell invocation for internally generated dependency commands where argv-array execution (no shell) is possible.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (add)
test "#env leaks fork-controlled BASH_ENV from a PR label into dependency step env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  assert_equal "true", env["BASH_ENV"]

  command = Shipit::TaskCommands.new(task).install_dependencies.first
  assert_equal "true", command.env["BASH_ENV"]
end
```
This demonstrates, with no live GitHub, that a label name attacker-controlled via the `pull_request` webhook (`LabelCapturingHandler#capture_labels`) reaches the env hash of a `Command` built by `TaskCommands#install_dependencies`, satisfying the invariant violation: a fork-controllable key (`BASH_ENV`) alters the environment of a `ruby`/`bundle` dependency step.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env

    end
