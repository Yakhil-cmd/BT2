### Title
`StatusHandler#process` writes GitHub statuses by global commit SHA with no repository/stack scoping, unlike `Commit#refresh_statuses!` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Commit#refresh_statuses!` is safely scoped because it fetches statuses via `stack.github_api.statuses(github_repo_name, sha, ...)`, i.e. the victim's own token and its own `github_repo_name`, before ever calling `create_status_from_github!`. The webhook path, `StatusHandler#process`, calls the same sink `create_status_from_github!` but reaches it via `Commit.where(sha: params.sha)` — a global lookup that ignores `repository_name`/`repository_owner` entirely, so any commit row in the database sharing that SHA (from any stack, any tenant) gets mutated.

### Finding Description
The binding claimed: `refresh_statuses!(commit) ⇒ stack.github_api.statuses(stack.github_repo_name, commit.sha)` — i.e. the fetch is always parameterized by the *victim stack's own* `github_repo_name`, so the returned `github_status` objects can only ever originate from that stack's own repository [1](#0-0) , and it always feeds into the same sink, `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` [2](#0-1) .

Contrast with the webhook path: `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Unlike `PushHandler`, which scopes its query through the `stacks` helper derived from `Repository.from_github_repo_name(repository_name)` before acting [4](#0-3)  and the base `Handler#stacks`/`repository_name` helpers that exist precisely for this purpose [5](#0-4) , `StatusHandler` never calls `stacks` or filters by `repository_name` at all. `params.sha` is attacker-controlled (`requires :sha, String` with no repository binding) [6](#0-5) , so the query `Commit.where(sha: params.sha)` returns every `Commit` row across the entire Shipit instance that happens to share that SHA — regardless of which stack/repository it belongs to — and writes a status to each one.

This confirms the asymmetry exactly as stated: the pull-based path is constrained by `stack.github_repo_name`/`stack.github_api` (the victim's own scoped credentials and endpoint), while the push-based path has no equivalent constraint — the only "scoping" is an incidental SHA match, which is not tenant isolation. Because Git commit SHAs are stable across forks/mirrors of the same history, any two stacks tracking overlapping history (e.g. a public repo and any fork of it that Shipit also tracks) will have `Commit` rows with identical SHAs in unrelated stacks, and `StatusHandler` cannot distinguish them.

### Impact Explanation
A crafted `status` webhook event whose `sha` matches a commit tracked by a victim stack causes `Commit#create_status_from_github!`/`add_status` to run for that victim's commit: it creates a `Status` row, can flip `deployable?`/CI state, trigger `Hook.emit(:deployable_status, ...)`, and schedule `stack.schedule_merges` if the resulting state becomes `pending`/`success` [7](#0-6) . Because a `success` status can make a commit `deployable?` and trigger continuous-delivery merge/deploy scheduling on the victim stack, this is a payload from one repository context mutating another stack's commit/task state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / potentially enabling an unauthorized merge or deploy for a repository the attacker never authenticated against. It is repeatable against any tracked stack whose commit history overlaps a SHA the attacker can produce (trivial for forks/mirrors of the same public repository).

### Likelihood Explanation
Reaching `StatusHandler#process` still requires passing `WebhooksController#verify_signature`, which is a Shipit/GitHub-configuration-dependent gate scoped by `repository_owner` (the org, not the specific repo) [8](#0-7) , and `verify_webhook_signature` returns `true` unconditionally whenever no `webhook_secret` is configured for that organization [9](#0-8) . This question's scope is limited to confirming the code-level scoping asymmetry inside `Commit`/`StatusHandler`, not re-litigating signature-verification bypass (a separate concern); assuming the webhook is reachable (as is the framing of this question), no further Shipit privilege, session, or secret is needed to exploit the SHA-based cross-tenant write — only knowledge of a target commit SHA, which is public/discoverable for open-source or forked repositories.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks under the webhook's own `repository_name`, mirroring `PushHandler`'s use of `stacks`/`Repository.from_github_repo_name`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or join through `stack.repository`) before calling `create_status_from_github!`, so cross-repository SHA collisions cannot write statuses onto unrelated stacks.

### Proof of Concept
Minitest plan (no live GitHub, uses fixtures):
1. `refresh_statuses!` scoping proof — stub `stack.github_api.statuses` with `mocha` and assert it is always invoked with `stack.github_repo_name` (the fixture stack's own repo name), never an attacker-supplied value:
```ruby
test "#refresh_statuses! only queries the commit's own stack github_repo_name" do
  commit = shipit_commits(:first)
  commit.stack.github_api.expects(:statuses).with(commit.stack.github_repo_name, commit.sha, per_page: 100).returns([])
  commit.refresh_statuses!
end
```
2. Cross-tenant write proof via `StatusHandler` — create two stacks/repositories ("victim" and "attacker") each with a `Commit` sharing the same `sha`, then assert `StatusHandler.new(payload).process` (with `payload['repository']['full_name']` set to the attacker's repo) still writes a `Status` onto the victim's commit:
```ruby
test "StatusHandler writes a status onto a commit belonging to a different repository than the webhook payload declares" do
  victim_stack = shipit_stacks(:shipit) # repo: "shopify/shipit-engine"
  victim_commit = shipit_commits(:first)
  attacker_repo = Repository.create!(owner: 'attacker', name: 'evil-fork')
  attacker_stack = Stack.create!(repository: attacker_repo, environment: 'production')
  Commit.create!(stack: attacker_stack, sha: victim_commit.sha, message: 'shared history commit')

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => attacker_stack.branch }],
    'repository' => { 'full_name' => 'attacker/evil-fork', 'owner' => { 'login' => 'attacker' } }
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
Both assertions confirm the equality claim: side A (`refresh_statuses!`) is always parameterized by `stack.github_repo_name`; side B (`StatusHandler#process`) has no such parameter and mutates a commit regardless of the declared payload repository.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
