### Title
Webhook signature is verified against the organization named in an untrusted payload field, while handlers act on a different, also-untrusted `repository.full_name` field — allowing cross-organization/cross-repository webhook forgery in multi-tenant Shipit instances - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/webhook secret to validate a request against using `repository_owner`, a value read straight out of the still-unverified JSON body. The event handlers that subsequently execute (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, …) instead use a *different* field from that same body — `repository.full_name` (or, for `StatusHandler`, no repository scoping at all) — to decide which `Repository`/`Stack`/`Commit` to mutate. Nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository being acted upon. In Shipit's supported multi-organization configuration (`Shipit.github_organizations`, `Shipit.github_app_config`), an org that has legitimately been given its own GitHub App/webhook secret can therefore forge a webhook payload that authenticates as "its own org" while directing the handler to mutate a stack belonging to a completely different, unrelated organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the signing secret based on an unauthenticated field of the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization key from `secrets.github`, confirming Shipit supports multiple, independently-secured organizations in one deployment: [3](#0-2) 

After signature verification passes (using the secret for whatever organization `repository.owner.login` claims to be), the raw, already-`JSON.parse`d payload is dispatched unchanged to handlers: [4](#0-3) 

The base `Handler` class resolves the target `Repository`/`Stack` from `repository.full_name` — a sibling field of `repository.owner.login`, but never cross-checked against it or against the organization that produced a valid signature: [5](#0-4) 

Concrete handlers act on this attacker-controlled repository resolution, e.g. `PushHandler` triggers a GitHub sync/deploy pipeline for whatever stacks match: [6](#0-5) 

and `PullRequest` handlers archive/unarchive review stacks or mutate PR/label state for the resolved repository: [7](#0-6) [8](#0-7) 

`StatusHandler` is even less scoped: it doesn't consult `repository` at all and updates the status of **any** commit in the entire installation matching the given `sha`: [9](#0-8) 

The binding that should hold — `organization authenticated by signature == owner(repository written by handler)` — is never asserted anywhere in this chain.

### Impact Explanation
An entity that controls one organization's Shipit-registered GitHub App (and thus its `webhook_secret`) — a routine, unprivileged-relative-to-other-tenants scenario in a multi-org Shipit deployment — can HMAC-sign an arbitrary JSON body with their own secret while setting `repository.owner.login` to their own org (to pass `verify_signature`) and `repository.full_name` to any other tracked repository/stack in the instance. This produces:
- Cross-repository/cross-organization writes: forcing `sync_github`, archiving/unarchiving review stacks, and mutating pull-request/label state on stacks they do not own.
- For `status` events, an unscoped write to commit statuses across the whole installation by sha alone, with no repository ownership check at all.

This satisfies the "cross-repository writes / unauthorized deploy" criterion for High/Critical impact, since it lets one tenant influence another tenant's deployment pipeline state without ever needing that tenant's secret, GitHub write access, or a Shipit session/API token.

### Likelihood Explanation
Requires only that the attacker administers one legitimately-configured organization on the shared Shipit instance (a routine, low-privilege position relative to other tenants) — no Shipit session, ApiClient token, or GitHub write access to the victim repository is needed. The exploit is a single crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
After signature verification succeeds, re-derive the organization/owner strictly from the field that was cryptographically bound to the verified secret (`repository_owner`), and require that every handler's resolved `Repository`/`Stack`/`Commit` belongs to that same, verified owner before acting — rejecting (422) any payload where `repository.full_name`'s owner segment (or the commit's owning repository, for `StatusHandler`) does not match the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (standard multi-org setup per `lib/shipit.rb`).
2. `attacker-org` knows its own `webhook_secret` (they administer their own GitHub App/organization).
3. Craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Compute `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact raw body.
5. POST to `/webhooks` with header `X-Github-Event: push`.
6. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository_owner`) and validates successfully against `attacker-org`'s secret.
7. `PushHandler#process` resolves stacks via `repository_name = payload.dig('repository','full_name')` → `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on a stack the attacker does not own.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
