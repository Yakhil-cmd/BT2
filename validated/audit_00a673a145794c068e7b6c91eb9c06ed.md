Confirmed: `addIndirectCorrespondents` in `device.js:906-920` marks other cosigners of a shared/multisig wallet as `is_indirect=1` in `correspondent_devices`, and these are exactly the "less-trusted" peers the original code intended to restrict via the check that is now commented out in `wallet.js:92-93`.

### Title
Disabled indirect-correspondent trust check lets an untrusted multisig co-signer inject fictive wallet-protocol messages (signing/shared-address spoofing) - (File: wallet.js)

### Summary
`handleMessageFromHub` in `wallet.js` is supposed to restrict which message `subject`s an `is_indirect` correspondent (a co-signer introduced only indirectly through a shared/multisig wallet setup, per `device.js` `addIndirectCorrespondents`) is allowed to send. That restriction is commented out, so an indirect correspondent — someone whose only relationship to the victim is being listed as a cosigner address in a shared-address definition template, never a directly paired/trusted device — can send **any** wallet-protocol subject, including `sign`, `new_shared_address`, `approve_new_shared_address`, and `create_new_shared_address`, exactly as if it were a fully trusted, directly-paired device.

### Finding Description
`handleMessageFromHub` in `wallet.js:64-93` receives device messages whose sender authenticity (permanent-key signature + device address) is already verified in `device.js` (`handleJustsaying` case `'hub/message'`), but whose *trust level* is tracked separately via the `bIndirectCorrespondent` flag, sourced from `correspondent_devices.is_indirect` (`device.js:204`, `device.js:906-920`). [1](#0-0) 

The intended safeguard — visible as a comment — [2](#0-1) 

was removed from enforcement (left commented), meaning `bIndirectCorrespondent` is now accepted as a parameter but never checked anywhere in the switch statement. Indirect correspondents are added automatically and silently, without the user's consent, whenever another device offers a shared/multisig address whose definition template lists them as one of the cosigner addresses: [3](#0-2) 

This means any party who can get themselves listed as a "cosigner" in a shared-address definition template that some other correspondent forwards can become an `is_indirect=1` correspondent of the victim's wallet, and then send fabricated protocol messages that the victim's wallet treats as authentic peer traffic for cases such as:
- `sign` (`wallet.js:251-402`) — request the victim to co-sign an attacker-crafted unit for a shared/multisig address, potentially prompting the victim (or forwarding through the victim as a signing proxy) to sign attacker-controlled payment outputs.
- `new_shared_address` / `create_new_shared_address` / `approve_new_shared_address` (`wallet.js:197-245`) — register or approve a shared address definition the victim never intended to trust as coming from a genuine, vetted correspondent.
- `create_new_wallet` / `new_wallet_address` — inject wallet-address bookkeeping entries into the victim's BIP44 wallet metadata.

This is analogous to the referenced Mattermost CVE-2017-18889 class of bug: a lower-privileged actor (there, any webhook/slash-command caller; here, an automatically-added, unvetted "indirect" correspondent) is able to produce protocol messages ("fictive system posts" there; fictive wallet-protocol/signing messages here) that the recipient's application logic treats as coming from a legitimately trusted party, because the authorization check meant to gate this class of sender was removed/disabled while the authentication (signature) check remained intact.

### Impact Explanation
Because signature/authenticity checks in `device.js` only prove *who* sent the message, not that the sender is *authorized* to issue every wallet-protocol subject, a merely-introduced indirect correspondent can:
- Solicit co-signatures on attacker-chosen payment units for shared/multisig addresses (`sign` case), risking unauthorized spending if the victim's UI/flow doesn't independently re-verify the legitimacy of the shared address membership.
- Register spoofed shared-address definitions/approvals that pollute the victim's wallet state (`new_shared_address`, `approve_new_shared_address`), potentially leading the victim to believe funds are protected by a multisig set that includes an address the victim did not actually vet, causing fund loss or freezing when that address is later used for real transfers.

This maps to the "AA fund loss or freezing" / "unauthorized spending" impact classes required, reached purely through the private-payment/multisig counterparty relationship (an indirect correspondent), without needing a malicious hub or peer.

### Likelihood Explanation
Medium likelihood: the attacker only needs to be named as a cosigner address inside a shared-address definition template that reaches the victim through any correspondent (direct or another indirect chain), automatically triggering `addIndirectCorrespondents`. From that point on, no further user confirmation on the victim's side is required for the attacker to start sending `sign`/`new_shared_address`/other messages, since the intended gating check is disabled.

### Recommendation
Re-enable and enforce the indirect-correspondent allow-list check that is currently commented out in `wallet.js:92-93`, restricting `bIndirectCorrespondent` senders to a minimal safe subset of subjects (e.g., `cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`), and reject all other subjects (`sign`, `new_shared_address`, `approve_new_shared_address`, `create_new_shared_address`, `create_new_wallet`, etc.) from such senders unless/until the user explicitly promotes them to a fully trusted correspondent.

### Proof of Concept
1. Attacker device A is *not* directly paired with victim device V.
2. Attacker gets any other correspondent (or crafts the flow directly, e.g. via a `create_new_shared_address`/`new_shared_address` offer that lists A's device address as a cosigner) to cause V to run `walletDefinedByAddresses` logic that calls `device.addIndirectCorrespondents`, inserting A into V's `correspondent_devices` with `is_indirect=1` (`device.js:906-920`) — without any explicit approval prompt to V's user for trusting A's future messages.
3. Attacker A, now an authenticated (via permanent device key signature) but merely *indirect* correspondent, sends a `hub/deliver` → `hub/message` device message with `subject: "sign"` (or `new_shared_address`, `approve_new_shared_address`) and an attacker-crafted `body` (e.g., referencing a shared address on which V is a cosigner).
4. `device.js` `handleJustsaying` verifies the signature and forwards to `handleMessageFromHub` in `wallet.js` with `bIndirectCorrespondent = true`.
5. Because the check at `wallet.js:92-93` is disabled, execution proceeds directly into the `sign`/`new_shared_address` case exactly as it would for a fully trusted, directly-paired correspondent, triggering a signing-request UI event or shared-address registration based on attacker-supplied data.
