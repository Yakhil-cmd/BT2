### Title
Unfiltered PR-label-derived environment variables in `ReviewStack#env` bypass `EnvironmentVariables#permit` whitelist and override deploy variable defaults - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased, value `"true"`) directly into the stack's environment hash with no whitelist check. `TaskCommands#env` merges this unfiltered `@stack.env` before `@task.env`, while the whitelist enforced by `EnvironmentVariables#permit`/`Stack#filter_deploy_envs` is applied only to the operator-supplied `deploy_params[:env]` on the way into `@task.env`. An attacker who can label their own PR can therefore inject a key matching any operator-declared `deploy_variables` name (e.g. `SAFETY_DISABLED`) into the process environment reaching `Command`/`PTY.spawn`, as long as the operator does not explicitly submit a competing value for that same key in the deploy form.

### Finding Description
The intended binding is: *"the only environment keys entering `Command#unbundled_env` are members of `deploy_variables` whitelist, i.e. `env.keys` ⊆ `DeploySpec#deploy_variables.map(&:name)`."* This is enforced at `Stack#build_deploy` via `filter_deploy_envs(env.to_h)` [1](#0-0) , and the controller further restricts the raw params via `params.require(:deploy).permit(:until_commit_id, env: @stack.deploy_variables.map(&:name))` [2](#0-1) .

However, `TaskCommands#env` builds the final environment by merging `@stack.env` directly at line 35, *before* the filtered `@task.env` at line 47: [3](#0-2) 

`@stack.env` is not the filtered value from `build_deploy`; for a `ReviewStack` it is overridden to merge every PR label name (uppercased) mapped to `"true"`, with no call to `EnvironmentVariables#permit` or any whitelist check: [4](#0-3) 

`EnvironmentVariables#permit`/`sanitize_env_vars` is only invoked through `filter_deploy_envs`, which is called on `env.to_h` in `build_deploy` — the operator-authored `deploy_params[:env]`, never on `@stack.env`'s label-derived contribution [5](#0-4) .

Exploit flow: attacker opens/owns a PR against the repository (base branch they don't control) and adds a label whose name (case-insensitively) equals a `deploy_variables` name declared in the repo's `shipit.yml` (e.g. `safety_disabled`). GitHub emits a `pull_request` `labeled` webhook, which is processed by the webhook handler that updates `pull_request.labels` on the `ReviewStack`'s associated `PullRequest` record. On the next deploy of that review stack, `TaskCommands#env` calls `@stack.env`, which merges `'SAFETY_DISABLED' => 'true'` unconditionally. Because this merge happens at line 35, prior to `@task.env` at line 47, this value survives into the final environment unless the operator's own deploy submission explicitly sets `SAFETY_DISABLED` in `deploy_params[:env]` (which becomes part of `@task.env` and overrides it). If the operator relies on the deploy_variable's declared *default* (not resubmitted every deploy) or simply doesn't set it, the attacker's label-injected value wins.

None of the existing guards catch this: `verify_signature`/webhook signature checks only validate that the webhook came from GitHub for that repo — they don't scope what a label can be named; `EnvironmentVariables#permit` is simply never invoked on `@stack.env`; the `deploy_params` `permit` list in the controller only constrains the HTTP form input, not the label-derived merge that happens later inside `TaskCommands#env`.

### Impact Explanation
An unprivileged PR author on a repository they don't administer can inject arbitrary attacker-chosen environment variable *values* (fixed to string `"true"`, but with attacker-chosen *key*, matching any deploy-variable name declared by the operator, including safety-gating flags like `SAFETY_DISABLED`) into the shell environment used by `Command`/`PTY.spawn` during that stack's deploy/review-stack tasks. This can disable operator-intended safety checks embedded in deploy scripts that gate on such variables, resulting in an unauthorized/unsafe deploy execution on the deploy host. This is repeatable for every review stack of a repository that declares an env-based safety toggle in `deploy_variables`, and is triggerable purely via GitHub label actions the PR author controls. This matches the Critical category ("RCE on the deploy host via `Command`/`PTY.spawn`... unauthorized deploy").

### Likelihood Explanation
Preconditions: the target repository must be configured as a ReviewStack, and its `shipit.yml` must declare a `deploy.variables` entry whose `name` an attacker can guess or discover (these are typically documented/discoverable in the repo's `shipit.yml`, which is often visible to the PR author since it lives in the repo). No secrets, tokens, or elevated GitHub permissions are required — only the ability to label a pull request the attacker owns/opened, which any GitHub user with issue/PR write access on their own fork-based PR can typically do, or which is otherwise a low-privilege action. The attack is cheap and repeatable across any review stack in scope.

### Recommendation
Apply `EnvironmentVariables#permit` (via `filter_deploy_envs` or an equivalent whitelist check against `deploy_spec.deploy_variables`) to `@stack.env`'s label-derived contribution before it is merged in `TaskCommands#env`, or restrict `ReviewStack#env`'s label-to-env mapping to only labels matching declared `deploy_variables` names and require review/approval, and ensure the merge order can never let label-derived values silently satisfy variables an operator expects to control via explicit defaults (e.g., apply the whitelist check even when the operator doesn't resubmit the variable, and treat unlisted labels as never eligible to populate a deploy_variable-shaped key).

### Proof of Concept
Minitest plan (`test/lib/shipit/task_commands_test.rb` style, no live GitHub):
1. Build a `Shipit::DeploySpec` fixture / stub whose `deploy_variables` includes a `VariableDefinition` named `SAFETY_DISABLED` with `default: 'false'`.
2. Create a `Shipit::ReviewStack` fixture with an associated `pull_request` and set `stack.pull_request.labels = ['safety_disabled']`.
3. Trigger a deploy via `stack.trigger_deploy(commit, user, env: {})` (simulating the operator submitting no explicit `SAFETY_DISABLED` value in `deploy_params[:env]`).
4. Assert `Shipit::EnvironmentVariables.new({'SAFETY_DISABLED' => 'true'}).permit(deploy_spec.deploy_variables)` would raise `NotPermitted` is never actually invoked on `stack.env`'s label contribution — i.e., assert directly: `Shipit::DeployCommands.new(deploy).env['SAFETY_DISABLED'] == 'true'`, even though `deploy.env['SAFETY_DISABLED']` (the filtered, task-persisted value) is `nil`/absent, proving the value reaching the command environment did not pass through `filter_deploy_envs`/`permit`.
5. Contrast with `deploy.env` (persisted, filtered) not containing `SAFETY_DISABLED`, confirming the divergence between the filtered whitelist path and the actual `TaskCommands#env` output used by `Command#unbundled_env`.
