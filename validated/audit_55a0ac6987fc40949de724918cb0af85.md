Based on my research, I've identified a legitimate admission-analog issue in the multisig approval-binding logic, distinct from AIP-103/104 and not requiring any admin/governance trust assumption beyond what the module already documents as a normal owner-role.

### Title
Multisig transaction execution can bypass approval-to-payload binding when full payload is stored on-chain - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the function invoked by the VM prologue to admit a `MultisigTransaction`, only checks that the **executed** payload matches the **approved** payload when the feature flag `abort_if_multisig_payload_mismatch_enabled()` is turned on. When it is off, an owner can submit any non-hash-checked payload at execution time and it will be accepted as long as the vote count for the (different) stored transaction record meets quorum.

### Finding Description
`create_transaction` stores the full payload on-chain (`transaction.payload = option::some(payload)`), and owners vote via `approve_transaction`/`reject_transaction` against that stored record identified only by `sequence_number` — they do not sign or bind their vote to a specific payload hash in this code path. At execution time, `validate_multisig_transaction` is supposed to re-bind the caller-supplied `payload` (the one that will actually be executed) to what was approved: [1](#0-0) 

The binding check is split into two branches:
1. If only a payload **hash** was stored (`create_transaction_with_hash`), the check `sha3_256(payload) == *payload_hash` is unconditional.
2. If the **full payload** was stored (`create_transaction`), the equality check `payload == *stored_payload` is only performed when `features::abort_if_multisig_payload_mismatch_enabled()` is true and `payload` is non-empty.

If that feature is not enabled, an owner who has accumulated enough approvals for the stored payload can call the execution entry point with a **different** `payload` argument, and the module performs no comparison at all against what other owners actually voted on. The quorum check (`num_approvals >= num_signatures_required`) still passes, because it counts votes against the `sequence_number` record, not against the payload content.

### Impact Explanation
This breaks the core invariant of the multisig admission boundary: "N owners approved transaction X" must guarantee that only X executes as the multisig account. With the mismatch check gated off, any single owner effectively gains unilateral ability to execute an unapproved payload under cover of a quorum that approved something else — a classic "approval validation accepting the wrong approval set" admission failure. Given the multisig account can control arbitrary funds/permissions, this is a critical unauthorized-execution impact.

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active on a given network. I was not able to confirm from the available index whether this flag defaults to enabled or is still an opt-in/staged feature; the presence of a dedicated feature flag guarding a payload-integrity check strongly suggests it was added after the base functionality shipped (a hardening fix), which is a red flag for networks or test/dev environments where it is not yet turned on. This mirrors the external report's pattern exactly: a real accounting/binding bug that was fixed by the protocol team behind a flag, and is only "safe" once admins explicitly enable the fix.

### Recommendation
Make the full-payload comparison unconditional (remove the feature gate on the mismatch check) so that `payload == *stored_payload` is always enforced whenever a full payload was stored, matching the hash-based branch's unconditional treatment. Alternatively, bind votes cryptographically to a content hash at vote time rather than only at (optional) execution-time comparison.

### Proof of Concept
Conceptual sequence (constrained by index access — I could not trace the exact deserialization point in `aptos-move/aptos-vm/src/transaction_validation.rs` where `payload` is subsequently used to build the executed entry function/script, so this should be verified in a live/checkout environment):
1. Owner A calls `create_transaction(multisig_account, payload_P1)` — stores full payload P1.
2. Owners B, C vote `approve_transaction` for that sequence number (approving P1 conceptually, though their vote is only tied to the sequence number).
3. On a network where `abort_if_multisig_payload_mismatch_enabled` is disabled, Owner A (or any owner) submits a `MultisigTransaction` at execution time with a different `payload_P2` (non-empty).
4. `validate_multisig_transaction` checks quorum against the sequence number (passes) but skips the `payload == stored_payload` check because the feature is off.
5. P2 executes as the multisig account despite never having been reviewed or approved by B/C.
