### Title
Cross-organization CI status forgery via globally-scoped `StatusHandler` commit lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check in `WebhooksController` authenticates a payload against the GitHub organization named in the payload itself, but `StatusHandler` — one of the handlers invoked after that check — never verifies that the commit it updates belongs to the organization that was actually authenticated. It looks up commits by SHA alone, globally across every repository/stack tracked by the Shipit instance. This breaks the same class of binding as the `StakeManager.addStakeTo` bug: "the entity that authenticated" ≠ "the record that gets mutated."

### Finding Description
`WebhooksController#verify_signature` resolves which organization's secret to check against straight from the untrusted payload: [1](#0-0) [2](#0-1) 

So the signature only proves "this payload was signed by organization `X`'s GitHub App secret," where `X` is whatever organization the caller wrote into the JSON body. In a multi-organization Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications"), any organization admin legitimately possesses their own org's `webhook_secret` and can produce validly signed payloads for organization `X = "their-own-org"`.

The `create` action then dispatches the parsed payload to the registered handler for the event type with no further binding to `X`: [3](#0-2) 

`StatusHandler` (registered for the `status` event) does not require or check any `repository`/organization field at all, and resolves the target `Commit` purely by SHA, across the whole database: [4](#0-3) 

Because `Commit.where(sha: params.sha)` is not scoped to a repository/stack owned by organization `X`, any org admin whose own org has the Shipit GitHub App installed (with their own valid `webhook_secret`) can sign a `status` webhook event whose payload contains an arbitrary `sha` — e.g., a commit SHA that also exists in a victim organization's tracked repository (trivial to obtain by forking the victim's public repo, or simply knowing the SHA from GitHub) — and Shipit will apply the forged CI status (`state: "success"`) to the victim's `Commit` record via `commit.create_status_from_github!(params)`.

The generic `Handler` base class does have a `stacks`/`repository_name` helper scoped by `payload.dig('repository', 'full_name')`, used by most other handlers (`PushHandler`, `CheckSuiteHandler`, `PullRequest::*`): [5](#0-4) 

`StatusHandler` is the outlier that bypasses this scoping entirely, so the equality that should hold — `organization verified by signature == organization owning the mutated Commit` — is never enforced for this handler.

### Impact Explanation
Forged commit statuses feed directly into Shipit's deploy-eligibility gating (`ci.require`/`blocking_statuses` in `deploy_spec.rb`, and continuous-deployment auto-trigger logic), meaning an attacker who controls any organization onboarded to a shared Shipit instance can flip a victim organization's commit to "deployable" without ever touching the victim's GitHub org, repository, or webhook secret. Depending on the victim stack's configuration (`continuous_deployment: true`, or a human simply trusting the now-green status), this can result in an **unauthorized deploy** of a commit that never actually passed CI — matching the Critical impact bar ("unauthorized deploy or rollback"). [6](#0-5) 

### Likelihood Explanation
Any of the (potentially many, per the documented multi-org support) onboarded organizations' admins can exploit this with zero additional privileges on the victim organization — they only need their own legitimate, already-provisioned webhook secret and a colliding/known commit SHA (obtainable by forking the target public repo or simply knowing the target SHA from GitHub UI/API). No compromise of the victim's credentials, webhook secret, or GitHub App is required, satisfying the "unprivileged attacker" bar.

### Recommendation
Scope `StatusHandler` (and any other handler that mutates state without going through `Handler#stacks`) to the organization that was cryptographically verified by `WebhooksController#verify_signature`, e.g., require and validate the payload's `repository.owner.login` matches the verifying organization, and restrict the `Commit` lookup to commits belonging to stacks whose `Repository#owner` equals that verified organization, rather than a bare `Commit.where(sha:)`.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which has the Shipit GitHub App installed on this shared Shipit instance with webhook secret `S_attacker` (a normal, documented multi-org setup).
2. Attacker forks (or otherwise learns the SHA of) a commit `deadbeef...` that is also tracked as a `Commit` under `victim-org/victim-repo`'s Shipit stack.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a body `{"sha":"deadbeef...","state":"success","context":"ci/required"}`, and `X-Hub-Signature` computed with `S_attacker`.
4. `WebhooksController#verify_signature` resolves `repository_owner` (absent `repository` key, falls back to `organization.login`, or is simply omitted/self-consistent with `attacker-org`) and validates the signature against `attacker-org`'s secret — it passes.
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, which matches the `victim-org` commit row, and calls `create_status_from_github!`, marking it "success" — even though `victim-org` never sent this webhook and the attacker has no access to it.

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```
