### Title
Merkle-tree "node-as-leaf" forgery in `in merkle` address condition due to unbounded/unchecked proof length and lack of leaf/node domain separation - (File: `merkle.js`, `definition.js`)

### Summary
The `in merkle` address-definition condition lets a spender satisfy a spending condition by supplying a Merkle proof that an `element` belongs to a tree whose root was posted by a trusted oracle as a data feed. The underlying `verifyMerkleProof()` never enforces that the supplied proof length matches the real depth of the tree, and `merkle.js` uses the same hash function for leaves and internal nodes with no domain separation. This is the same bug class as the reported "merkleProof length not checked" issue: an attacker can use a shortened proof to make an internal tree node masquerade as a leaf, forging membership for a value that was never part of the original dataset.

### Finding Description
`merkle.js` builds the tree and verifies proofs with an undifferentiated hash function: [1](#0-0) 
The code even contains an acknowledgment of the flaw ("Node-as-Leaf issue might matter in some cases") but does not mitigate it.

This primitive is exposed to unprivileged unit posters through the `in merkle` address-definition condition. The definition-time validation only constrains `element` to a printable-ASCII string of length 1–100 (which comfortably fits a base64-encoded sha256 hash) and does not require the proof length to correspond to a known/expected tree depth: [2](#0-1) 

At authentication time, the attacker-supplied `serialized_proof` (an authentifier under the spender's control) is deserialized and verified against the oracle-posted root with no bound on `proof.siblings.length` and no check that `element` is an original leaf rather than a concatenation of two internal node hashes: [3](#0-2) 

Because `getMerkleRoot`/`getMerkleProof` compute internal node hashes as `hash(leftHash + rightHash)` (the same `hash()` used for leaves), an attacker who knows the (often externally-known) contents of the oracle's dataset can pick any two sibling hashes at some level `L`, set `element = leftHash + rightHash` (which fits the allowed character set/length), and supply a proof consisting only of the siblings from level `L` up to the root (omitting the true leaf-level depth). `verifyMerkleProof` will recompute the same root and return `true`, even though `element` was never an actual leaf of the tree: [4](#0-3) 

The same unchecked-length/no-domain-separation pattern also exists in the `is_valid_merkle_proof()` oscript function used inside AA formulas/bounce conditions; post-fix code only bounds `siblings.length <= 50` and checks element type, but does not add leaf/node separation or tie the proof length to an expected tree depth: [5](#0-4) 

### Impact Explanation
Any address (or AA-driven authorization/claim logic) that uses `in merkle` (or `is_valid_merkle_proof` in oscript) to gate spending/claims against an oracle-posted Merkle root of a whitelist, snapshot, or allocation table can be bypassed by a party who was never a genuine leaf of that dataset. This results in unauthorized spending from the address (or unauthorized AA-side fund release/claim), matching the "unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
Exploitation requires only that the attacker know (or can compute) two adjacent node hashes of the oracle's published dataset — feasible whenever the underlying dataset (e.g., a snapshot list) is public or reconstructible, which is the common use case for such oracle-posted Merkle roots. No special privileges (oracle, hub, or node) are needed; a normal unit poster crafts the authentifier and posts the unit.

### Recommendation
- Add domain separation in `merkle.js` hashing (e.g., prefix leaf hashes and internal node hashes with distinct tags) so an internal node value can never validate as a leaf.
- In `verifyMerkleProof`/`is_valid_merkle_proof`, require the caller (or the `in merkle` condition definition) to specify/verify the expected tree depth (or total leaf count) so that `proof.siblings.length` must exactly match, rejecting truncated proofs.

### Proof of Concept
1. Oracle posts data feed value `R = getMerkleRoot(arrElements)` for a known/public `arrElements` list.
2. Attacker computes intermediate hashes `H_left`, `H_right` of `arrElements` at some tree level (usable since `arrElements`, and thus every intermediate hash, is reproducible from `merkle.js`'s deterministic construction: `merkle.js:9-20`).
3. Attacker sets `element = H_left + H_right` (satisfies the `element` regex/length check in `definition.js:470-475`) and builds `proof = { index: parentIndex, siblings: [siblings from parent level up to root], root: R }`.
4. Attacker submits a unit spending from the address whose definition contains `["in merkle", [oracleAddrs, feed_name, element]]`, providing the forged `serialized_proof` as the authentifier at that path.
5. `merkle.verifyMerkleProof(element, proof)` in `definition.js:1016` returns `true` and `dataFeeds.dataFeedExists(... proof.root ...)` matches the oracle's posted root, so the condition is satisfied even though `element` (a concatenation of two internal hashes) was never one of `arrElements`.

		var arrOverHashes = []; // hashes over hashes

			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
