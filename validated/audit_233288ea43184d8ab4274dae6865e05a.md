I have enough information now to provide the analysis. There's no wrapping try/catch around `formulaParser.evaluate` in `aa_composer.js` that catches synchronous throws inside comparator functions passed to `Array.prototype.sort` — such a throw propagates synchronously out of `readDataFeedValue` and up through the `evaluate` call chain in `formula/evaluation.js`, becoming an uncaught exception in the node process during AA trigger handling.

### Title
Uncaught exception in `readDataFeedValue()` sort comparator crashes node when evaluating an AA's `data_feed[]` formula against ambiguous unstable oracle data - (File: data_feeds.js)

### Summary
`readDataFeedValue()` in [1](#0-0)  is the function used by AA formula evaluation (`data_feed[[...]]`) to resolve oracle data feed values, including unstable (not-yet-stabilized) candidates when called from an AA context. When multiple unstable candidate data-feed postings match the same feed name/value and cannot be strictly ordered by `latest_included_mc_index`/`level`, the sort comparator unconditionally `throw`s a synchronous `Error`, with no sanity/fallback handling analogous to the missing checks described in the reference report (which similarly lacked handling for ambiguous/duplicate state updates).

### Finding Description
When an AA formula calls `data_feed[[oracles=..., feed_name=..., ...]]`, `formula/evaluation.js`'s `getDataFeed()` invokes `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)`, passing `bAA` (truthy while evaluating inside an AA) as the `unstable_opts` argument: [2](#0-1) 

Inside `readDataFeedValue`, when `bIncludeUnstableAAs` is true and `bIncludeAllUnstable` is false (i.e., regular AA lookup, not `'all_unstable'`), all unstable messages from the specified oracle addresses are collected as candidates and, if there is more than one matching candidate and `ifseveral` is not `'abort'`, they are sorted by `latest_included_mc_index` then `level`: [3](#0-2) 

If two candidates have identical `latest_included_mc_index` and identical `level` (which can happen when two different oracle-address units are siblings under the same parents/witness state), the comparator falls through to `throw Error("can't sort candidates "+a+" and "+b)` because `bIncludeAllUnstable` is false in this AA path. This is a synchronous `throw` executed inside the callback passed to `Array.prototype.sort`, which is not guarded by any `try/catch` along the call chain (`readDataFeedValue` → `getDataFeed` → `evaluate` in `formula/evaluation.js` → `evaluateAA`/`replace`/`executeStateUpdateFormula` in `aa_composer.js`, none of which wrap the evaluate call in a try/catch): [4](#0-3) [5](#0-4) 

Because `assocUnstableMessages`, `assocUnstableUnits`, `level`, and `latest_included_mc_index` are deterministic, consensus-derived state shared by every node processing the same DAG, this crash is fully reproducible by any node evaluating the same AA trigger — it is not a local-only fault.

### Impact Explanation
An uncaught exception thrown synchronously during AA trigger processing will propagate up through the node's `handleTrigger`/`evaluate` call stack as an unhandled exception, which in Node.js crashes the process (or, at minimum, aborts trigger processing state in an unexpected, non-recoverable way). Since every full node/witness deterministically evaluates the same AA triggers over the same unstable-unit state, all nodes that reach this AA trigger evaluation will hit the same throw, causing a synchronized network-wide crash/DoS that stalls confirmation of new units referencing or depending on this AA — a High severity impact matching "a network unable to confirm new units."

### Likelihood Explanation
This is triggerable by any unprivileged unit poster/AA trigger sender: they just need to (1) deploy or use an AA whose formula/getters read `data_feed[[oracles="addrA:addrB", ...]]` for two or more oracle addresses without a distinguishing `min_mci`/`ifseveral=abort`, and (2) arrange for two unstable data-feed-posting units from different oracle addresses in the list to be posted as siblings (same parents, hence same computed `level` and `latest_included_mc_index`) before either stabilizes, then send a trigger to the AA. Since level/mci equality among sibling units is a normal, easily engineered DAG condition (not requiring any privileged role, hub, or malicious peer behavior), likelihood is Medium-to-High.

### Recommendation
Do not `throw` inside the sort comparator. Instead:
- Treat truly ambiguous candidates the same way `ifseveral === 'abort'` is treated (return `bAbortedBecauseOfSeveral: true`) or deterministically tie-break (e.g., by unit hash) instead of throwing, mirroring the reference recommendation of adding explicit sanity checks/deterministic ordering rather than silently corrupting or crashing on ambiguous updates.
- Alternatively, extend the tie-break chain in [6](#0-5)  with a further deterministic key (e.g., unit id lexicographic order) before falling back to any error path, and make that error path a normal `cb`/error propagation rather than a synchronous `throw`.

### Proof of Concept
1. Deploy an AA whose `getters`/state formula includes: `data_feed[[oracles="ADDR_A:ADDR_B", feed_name="x"]]` (no `min_mci`, default `ifseveral="last"`).
2. As the poster, construct two units U1 (authored by ADDR_A) and U2 (authored by ADDR_B), each containing a `data_feed` message with `{x: <value>}`, both built on the same parent set/witness state so that `storage.assocUnstableUnits[U1].level === storage.assocUnstableUnits[U2].level` and both have the same `latest_included_mc_index` (e.g., post them as siblings before any MC advance).
3. Send a trigger unit to the AA while U1 and U2 are both unstable.
4. During trigger processing, `readDataFeedValue` collects both as candidates, `arrCandidates.length > 1`, `ifseveral !== 'abort'`, and the sort comparator hits `throw Error("can't sort candidates ...")` at [7](#0-6) , propagating as an uncaught exception during AA trigger handling on every node that processes this trigger.
