### Title
Baseline-preservation race between `consume_stop_state` and `restore_unreviewed_stop_state` lets a concurrent `UserPromptSubmit` silently re-baseline past unreviewed edits - (File: `plugins/security-guidance/hooks/diffstate.py`)

### Summary
`consume_stop_state` clears `touched_paths` under a lock, and if the asyncRewake Stop hook later fails partway through (e.g. transient CCR/API error), `restore_unreviewed_stop_state` is supposed to put the paths back so the next turn's `UserPromptSubmit` (UPS) doesn't advance `baseline_sha` past the unreviewed edit. Because the clear and the restore are two separate locked operations with an unbounded window between them, a concurrent UPS that fires in that window observes an empty `touched_paths`, fails the preservation guard, and unconditionally captures a fresh `baseline_sha`/`head_at_capture` that already includes the dangerous change — permanently shifting the review baseline past it.

### Finding Description
`consume_stop_state` (`plugins/security-guidance/hooks/diffstate.py:74-113`) snapshots and clears `touched_paths` in one `with_locked_state` call. If the Stop hook then exits early for a transient reason, `restore_unreviewed_stop_state` (`diffstate.py:116-137`) is called afterward, in a *second*, independent locked call, to re-merge the paths back and to conditionally seed `baseline_sha` (only `if baseline_sha and not state.get("baseline_sha")`).

`handle_user_prompt_submit` (`security_reminder_hook.py:446-515`) decides whether to preserve the prior baseline solely by checking, under its own lock, `if state.get("touched_paths") and state.get("baseline_sha")` (`security_reminder_hook.py:493`). Because Stop is documented as asyncRewake — "the user can submit a new prompt before this hook finishes its initial state read" (`diffstate.py:77-80`) — a new UPS can run in the gap between `consume_stop_state`'s clear and the eventual `restore_unreviewed_stop_state` call. At that instant `touched_paths` is empty, so the preservation guard fails and UPS unconditionally overwrites `state["baseline_sha"]`/`state["head_at_capture"]` with a fresh `capture_git_baseline(cwd)` snapshot of the *current* working tree — which already contains the dangerous, unreviewed edit (normal git operations: edit, commit, amend, or just leaving the file dirty is enough).

When `restore_unreviewed_stop_state` finally runs, it re-adds the paths to `touched_paths` (so the marker is restored) but does **not** overwrite `baseline_sha` because the guard `not state.get("baseline_sha")` is now false — the racing UPS already set one. The actual review set, however, is computed independently from git state by `compute_v2_review_set` (`diffstate.py:353-438`) via `dirty_now ∩ changed_since(baseline_sha)`, not from `touched_paths` directly. Since the new baseline SHA already matches the working tree content that contains the dangerous change, `changed_since` no longer contains that file, so the next Stop's review set silently drops it even though it is "restored" in `touched_paths`.

This breaks the stated invariant that "the review set must stay bound to the right repo, baseline, and touched paths" — restoring `touched_paths` gives the illusion the edit will still be reviewed, but the baseline has already moved past it via the unguarded race window.

### Impact Explanation
This is a Security-control bypass: a dangerous edit made by Claude (or injected via repository content that steers Claude into that edit) can end up permanently excluded from the git-diff-based LLM security review with no error, warning, or metric distinguishing this from a legitimately-reviewed clean state. Because the Stop-hook review is the last line of defense (`ENABLE_CODE_SECURITY_REVIEW`), silently routing around it defeats the plugin's blocking/review guarantee for that turn's change while all other bookkeeping (fire counts, findings) looks normal.

### Likelihood Explanation
No special privilege is required — this is triggerable purely through ordinary session activity: (1) Claude edits/commits a file (`record_touched_path`), (2) Stop hook starts and hits any transient failure path (network blip, HTTP error) causing it to call `restore_unreviewed_stop_state` instead of completing normally, and (3) a next user turn's `UserPromptSubmit` fires before the restore completes — plausible in automated/agentic loops or fast-follow-up usage, and the codebase's own comments acknowledge Stop's async nature and the exact race shape this bug exploits (they built `restore_unreviewed_stop_state` specifically to close a related race, but left the clear→restore window itself unguarded). Reproducibility depends on hitting the timing window, but the window is bounded only by the Stop hook's network/API latency (potentially seconds), which is a realistic and repeatable race under load or with induced latency.

### Recommendation
Close the window instead of patching around it: either (a) merge `consume_stop_state`'s clear and any eventual restore into a single lock scope by not clearing `touched_paths` until the Stop hook has durably confirmed success (e.g., use a "reserved"/pending marker rather than deleting), or (b) have `handle_user_prompt_submit` check a new "stop_in_flight" flag (set before `consume_stop_state` returns, cleared only after the Stop hook fully completes or explicitly calls `restore_unreviewed_stop_state`) and preserve the baseline whenever that flag is set, regardless of `touched_paths` being empty at that instant.

Call `compute_v2_review_set(cwd, baseline_sha=B, head_at_capture=...)` against a repo fixture where `dangerous.py`'s content matches what SHA `B` captured — assert `dangerous.py` is absent from the returned review set, demonstrating the dangerous change is skipped despite being "restored" in `touched_paths`.
