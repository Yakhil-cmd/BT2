### Title
Webhook signature verification is bypassed for any GitHub organization configured without a `webhook_secret`, allowing unauthenticated forgery of webhook events for other organizations' stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the selected organization [1](#0-0) . Which organization's app/secret is selected is derived from an **unverified, attacker-controlled** field in the raw JSON payload (`repository.owner.login` / `organization.login`), read *before* any cryptographic check is performed [2](#0-1) [3](#0-2) .

### Finding Description
This mirrors the reported bug class: a value is used to select/derive a trust context, but that value itself, and the ultimate object acted upon, are never bound by the cryptographic check that is supposed to authorize the action (in the LlamaCore case, `role` selected quantity accounting but was never checked to equal `approvalRole`).

Here, the binding that should hold is:
`organization that authenticated the webhook (i.e., whose `webhook_secret` produced a valid HMAC) == organization/repository whose stack state is mutated by the handler`.

In `Shipit::WebhooksController#verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

`repository_owner` is read straight from the untrusted, unauthenticated JSON body before the signature is verified, and is used only to pick which `GitHubApp` config (and thus which `webhook_secret`) to check against.

In `GitHubApp#verify_webhook_signature`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

Shipit explicitly supports multi-organization configuration where each org has its own `webhook_secret`, and documents `webhook_secret` as optional (`# nil`) for each org individually [5](#0-4) [6](#0-5) .

Consequence: if the Shipit deployment is configured for multiple GitHub organizations and **any one** of them has no `webhook_secret` configured (a supported, documented configuration), an attacker who knows that org's name can set `repository.owner.login` (or `organization.login`) to that org's name in an otherwise-arbitrary POST body to `/webhooks`. `verify_webhook_signature` then returns `true` unconditionally (because `webhook_secret` is blank for that org), completely bypassing signature verification — regardless of the actual `X-Hub-Signature` header content. The handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) then processes the full, attacker-supplied JSON body, including any `full_name`/`sha`/`state`/`branches` fields that reference a completely different (properly secured) repository/stack [7](#0-6) . Nothing re-checks that the "authenticating organization" (the one whose blank secret let the request through) matches the organization/repository that the event payload actually claims to belong to and that handlers act on (e.g. `PushHandler`, status handler updating `Commit#statuses`, `membership` handler creating `Team`/`User`/`Membership` records).

### Impact Explanation
This breaks the authentication boundary between the GitHub organization that is supposed to have cryptographically produced the webhook and the repository/stack whose state (commit statuses, push-triggered `GithubSyncJob`, membership/team records, merge-status data) is written by the handler. An external, completely unprivileged attacker (no Shipit session, no API token, no GitHub credentials) can inject forged GitHub events for any stack/repository tracked by the Shipit instance, as long as one configured org lacks a webhook secret. This can trigger unauthorized syncs, poison commit statuses used to gate deploys (`status` event), or create fake team/user/membership records (`membership` event) — i.e., unauthorized manipulation of deploy-gating state, matching the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: it requires a Shipit instance configured with the multi-org `github:` hash and at least one org that has no `webhook_secret` set. This is an explicitly supported and documented configuration in this engine (`config/secrets.development.shopify.yml`, `docs/setup.md`), so it is a realistic operational state, not merely theoretical misuse outside the engine's control. No credentials, tokens, or prior access are required — only knowledge of the GitHub organization name for the "open" org, which is typically public.

### Recommendation
Do not let `verify_webhook_signature` unconditionally pass when the *selected* organization's secret is blank; instead, either:
- Require a `webhook_secret` for every organization if more than one organization is configured, or
- Reject the request when the payload's claimed `repository`/`organization` login does not correspond to a securely-signed, resolvable installation with a non-blank secret, before dispatching to handlers, or
- After signature verification, re-verify that the resolved `github_app`'s organization actually matches the `Shipit::Repository`/`Stack` being mutated by the handler (bind the authenticated org to the object being written).

### Proof of Concept
Given a `secrets.yml` such as:
```yaml
production:
  github:
    trusted-org:
      webhook_secret: "s3cr3t"
      ...
    open-org:
      webhook_secret:     # not set
      ...
```
1. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "trusted-org/some-tracked-repo" },
  "after": "deadbeef...",
  "ref": "refs/heads/main"
}
```
No `X-Hub-Signature` header is required to be valid (any/no value works).
2. `verify_signature` calls `Shipit.github(organization: "open-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [8](#0-7) .
3. `create` runs `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` on the full, forged body, which references `trusted-org/some-tracked-repo` — a stack the attacker has no legitimate access to [7](#0-6) .

*Note: I could not fully inspect `PushHandler`/status handler internals (the `push_handler.rb` file content and repository lookup logic were not returned by the tools before the iteration limit), so the exact downstream write path (e.g., whether `full_name` alone is sufficient to resolve and mutate an arbitrary tracked `Stack`) is inferred from the routing/dispatch code and test fixtures observed, not fully confirmed line-by-line for every handler.*

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
