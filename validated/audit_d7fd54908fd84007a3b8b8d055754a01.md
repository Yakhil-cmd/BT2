### Title
Inconsistent `isRunning` and `isLockedKLAY` Status Checks Allow Bridge Asset Outflows When Bridge Is Stopped — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge contracts expose two independent "pause" flags — `isRunning` (global) and `isLockedKLAY` (KLAY-specific) — but apply them only to outbound *request* paths. All three inbound *handle* functions (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`) omit both checks entirely. When the bridge owner invokes `setRunningStatus(false)` or `lockKLAY()` to halt asset movement during an incident, registered operators can still call the handle functions and transfer KLAY, ERC20, or ERC721 assets out of the bridge contract, defeating the intended emergency stop.

---

### Finding Description

`BridgeTransfer.sol` declares a single `isRunning` boolean and a `setRunningStatus` setter:

```solidity
bool public isRunning = true;

function setRunningStatus(bool _status) public onlyOwner {
    isRunning = _status;
    emit RunningStatusChanged(_status);
}
``` [1](#0-0) 

`BridgeTransferKLAY.sol` adds a second, KLAY-specific lock:

```solidity
bool public isLockedKLAY;
modifier unlockedKLAY { require(!isLockedKLAY, "locked"); _; }
``` [2](#0-1) 

**Outbound request paths check both flags:**

- `_requestKLAYTransfer` applies `unlockedKLAY` modifier **and** `require(isRunning, "stopped bridge")`. [3](#0-2) 

- `_requestERC20Transfer` checks `require(isRunning, "stopped bridge")`. [4](#0-3) 

- `_requestERC721Transfer` checks `require(isRunning, "stopped bridge")`. [5](#0-4) 

**Inbound handle paths check neither flag:**

`handleKLAYTransfer` carries only `onlyOperators` and `nonReentrant`; no `isRunning` or `isLockedKLAY` guard: [6](#0-5) 

`handleERC20Transfer` carries only `onlyOperators`; no `isRunning` guard: [7](#0-6) 

`handleERC721Transfer` carries only `onlyOperators`; no `isRunning` guard: [8](#0-7) 

The result is a direct structural analog to the Drift finding: the bridge's "stopped" status does not map cleanly to all operations that move assets, and the status is checked in some code paths but silently absent in others.

---

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` — the intended emergency kill-switch — the contract's KLAY, ERC20, and ERC721 balances remain fully accessible to any registered operator via the handle functions. A compromised or malicious operator can drain the bridge's liquidity pool (lock-mode) or mint unbacked tokens on the destination chain (mint-burn mode) while the owner believes the bridge is halted. The corrupted value is the exact KLAY/token balance transferred by each `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` call, directly affecting KAIA and bridged assets held in the service-chain bridge contract.

---

### Likelihood Explanation

The trigger requires a registered operator — a semi-trusted role, not the owner. Operators are registered by the owner and are expected to be honest under normal conditions. However, the inconsistency means the owner's emergency action (`setRunningStatus(false)`) silently fails to achieve its stated purpose. In a real incident (key compromise, bridge exploit), the window between the owner stopping the bridge and deregistering all operators is exactly when this gap is exploitable. The likelihood is **Low-Medium**: low under normal operation, elevated during the precise incident-response window the flag is designed to protect.

---

### Recommendation

**Short term:**
- Add `require(isRunning, "stopped bridge")` to `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer`, mirroring the guard already present in the request paths.
- Add the `unlockedKLAY` modifier (or an equivalent `isRunning` check) to `handleKLAYTransfer` to make the KLAY-specific lock consistent with the KLAY request path.

**Long term:**
- Adopt a single, centralized status-check helper (e.g., a `whenRunning` modifier) applied uniformly to every asset-moving function — both request and handle — so that a future addition of a new handle function cannot silently omit the guard.
- Document explicitly which operations each flag governs, and add a test that asserts handle functions revert when `isRunning == false`.

---

### Proof of Concept

1. Bridge is deployed with two registered operators (`op1`, `op2`) and threshold 2; bridge holds 1000 KLAY liquidity.
2. A security incident is detected; owner calls `bridge.setRunningStatus(false)`.
3. `bridge.isRunning()` returns `false`; `requestKLAYTransfer` now reverts with `"stopped bridge"`.
4. Attacker (compromised `op1`) calls:
   ```solidity
   bridge.handleKLAYTransfer(txHash, victim, attacker, 1000 ether, 0, blockNum, "");
   ```
5. `op2` (also compromised, or colluding) calls the same function to reach threshold.
6. `handleKLAYTransfer` executes — no `isRunning` check — and transfers 1000 KLAY to `attacker`.
7. Bridge KLAY balance is now 0 despite the owner having stopped the bridge.

The same sequence applies to `handleERC20Transfer` (drains ERC20 liquidity or mints unbacked tokens in mint-burn mode) and `handleERC721Transfer` (mints unbacked NFTs).
