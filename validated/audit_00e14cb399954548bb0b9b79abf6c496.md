### Title
Cross-organization/cross-repository forged webhook status can trigger unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an incoming webhook against using the payload's own `repository.owner.login` (or `organization.login`) field, then hands the entire raw payload to event handlers. `StatusHandler`, however, looks up the target `Commit` purely by `sha` across the whole database, with no check that the commit belongs to a repository owned by the organization whose secret validated the signature. In a Shipit installation configured for multiple GitHub organizations (a documented, supported configuration), an operator of one organization's own legitimately-configured GitHub App can forge a `status` webhook that is valid for their own organization's secret but whose `sha` corresponds to a commit belonging to a completely different organization's stack, injecting a fake `success` status and potentially triggering an unauthorized continuous-deployment run for a stack/repository they do not own.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to fetch the GitHub App / `webhook_secret` exclusively from attacker-controlled JSON body fields: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple GitHub organizations, each with its own `webhook_secret`, in a single installation: [3](#0-2) 

Once the signature is verified against the org derived from `repository.owner.login`, `WebhooksController#create` dispatches the *entire* payload to all registered handlers for the event type, without re-checking that any repository/commit referenced elsewhere in the payload also belongs to that same organization: [4](#0-3) 

`StatusHandler#process` resolves the target purely by commit SHA, globally, with no repository/organization scoping at all: [5](#0-4) 

This breaks the binding "an organization that authenticated versus the repository that is written": the signature only proves the request was signed by *some* configured org's secret (determined from the `repository.owner.login`/`organization.login` field), but the actual database write (`Commit.where(sha: params.sha)`) is not constrained to that organization's repositories at all — it can match a commit belonging to any other organization hosted on the same Shipit instance.

Creating a `Status` record has a direct side effect: it schedules continuous delivery for the stack that owns the matched commit: [6](#0-5) [7](#0-6) 

If the target stack has `continuous_deployment` enabled and the forged `success` status satisfies its required checks, `next_commit_to_deploy`/`trigger_continuous_delivery` will schedule and run a real `Deploy` for a repository the attacker does not own and was never authenticated against: [8](#0-7) 

This is corroborated by existing test coverage showing that creating a `success` `Status` on a commit is sufficient, by itself, to enqueue a `Deploy`/`ContinuousDeliveryJob` when continuous deployment is enabled: [9](#0-8) 

### Impact Explanation
An attacker who legitimately controls their own GitHub organization's App/webhook configuration in a multi-org Shipit deployment (i.e., they know only their own org's `webhook_secret`, never the victim org's) can forge signed webhook deliveries that pass `verify_signature` for their own org, but whose payload content (`sha`) targets an entirely different organization's stack. Because `StatusHandler` has no cross-checking between the authenticated organization and the commit/repository being mutated, this can be used to inject fabricated CI `success` statuses on a victim organization's commits, potentially satisfying continuous-deployment gating and triggering an unauthorized `Deploy` (an unauthorized ship) for a stack the attacker was never authorized to write to. This matches the required "Critical" impact category of an unauthorized deploy across organizational/repository boundaries.

### Likelihood Explanation
Likelihood is moderate: it requires the Shipit instance to be configured to serve more than one GitHub organization (a supported, documented configuration) and requires the target stack to have `continuous_deployment` enabled with status-based gating that a forged `success` context can satisfy. No possession of the victim org's secret, no privileged Shipit account, and no `ApiClient` token are needed — only the attacker's own, legitimately obtained organization webhook secret, which they control by design.

### Recommendation
In `StatusHandler` (and any other handler that looks up records solely by fields embedded in the payload body, e.g. `sha`), scope the lookup by the `repository.full_name` from the same payload, and cross-verify that this repository belongs to the same organization (`repository.owner.login`) that was used to select the webhook secret in `WebhooksController#verify_signature`. More generally, `verify_signature` should ensure the organization used to validate the HMAC matches the organization owning every repository referenced later during dispatch, rather than trusting an unrelated part of the same JSON body as authoritative without a matching post-verification consistency check.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own `webhook_secret`, as supported by `config/secrets.development.shopify.yml`.
2. Attacker (who owns `OrgA`'s GitHub App) crafts a `status` webhook payload:
   ```json
   {
     "sha": "<sha of a commit belonging to a stack owned by OrgB>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
3. Attacker signs the raw body with `OrgA`'s known `webhook_secret` and sends it to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as `"OrgA"`, fetches `OrgA`'s GitHub App/secret, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the `OrgB` commit (no org/repo check), and calls `commit.create_status_from_github!(params)` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
6. `Status#after_create`/`after_commit` callbacks fire `schedule_continuous_delivery`, and if `OrgB`'s stack has `continuous_deployment` enabled and this status satisfies its required checks, a `Deploy` is triggered for `OrgB`'s stack (`app/models/shipit/status.rb:18-19,42-44`, `app/models/shipit/stack.rb:210-229`) — an unauthorized deploy of a repository the attacker never controlled.

      end
