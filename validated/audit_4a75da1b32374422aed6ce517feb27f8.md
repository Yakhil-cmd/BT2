### Title
Cross-tenant `membership` webhook allows an org with a valid `webhook_secret` to add an attacker-controlled user to another organization's `Shipit::Team` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Shipit::Team` solely by `github_id`, never re-validating that the existing record's `organization` matches the `organization.login` in the incoming payload. Because webhook signature verification for org-scoped events like `membership` falls back to the payload's own `organization.login` field, any organization that is a legitimate tenant of the Shipit instance (and therefore knows its own `webhook_secret`) can forge a `membership` event naming a `team.id` belonging to a different organization's team and add an arbitrary GitHub login to it.

### Finding Description
The broken binding: the question assumes `organization_that_signed == organization_that_owns(team)`, i.e. `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` implicitly guarantees that `params.team.id` belongs to `repository_owner`'s org. It does not.

- Signature verification in `app/controllers/shipit/webhooks_controller.rb` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and then verifies with `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . GitHub's real `membership` webhook payload has no top-level `repository` key, so `repository_owner` resolves to `params['organization']['login']` — a value fully controlled by whichever org sends the payload (ATTACKER_ORG). The HMAC is checked against ATTACKER_ORG's own `webhook_secret`, which the attacker (as that org's administrator/webhook configurer) legitimately knows. This step only proves "this request was signed by ATTACKER_ORG," not "this request may only touch ATTACKER_ORG's resources."
- `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The block only runs on **creation**; if a `Shipit::Team` row already exists with that `github_id` (belonging to VICTIM_ORG), it is returned unmodified, and `organization` is never re-checked against `params.organization.login`.
- `process` then unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , and `Team#add_member` appends the member to `members` (and thus creates a `Membership` row) with no organization check [5](#0-4) .

Exploit flow: attacker controls ATTACKER_ORG (already onboarded to this Shipit instance with its own `webhook_secret` in `secrets.yml`, e.g. because they set up the GitHub webhook themselves for their own org). They discover VICTIM_ORG's team `github_id` (team IDs are visible via the public/unauthenticated GitHub API for the team's org, or simply known if VICTIM_ORG is public). They POST to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with ATTACKER_ORG's `webhook_secret`, and a JSON body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"...","slug":"...","url":"..."},"organization":{"login":"ATTACKER_ORG"},"member":{"login":"attacker-controlled-login"}}
```
Signature verification passes (signed with ATTACKER_ORG's secret against `organization.login = ATTACKER_ORG`). `find_or_create_team!` finds the pre-existing victim `Team` by `github_id` and returns it unchanged (`organization` stays `VICTIM_ORG`). `process` adds the attacker-chosen GitHub user as a member of that victim team.

No existing guard prevents this: `verify_signature` only authenticates "who signed," not "what resource is referenced"; `find_or_create_by!(github_id:)` has no companion check like `find_by!(github_id:, organization: params.organization.login)`; the `ExplicitParameters` schema only enforces types/presence, not cross-field consistency; there is no `require_permission!`/ownership check inside `MembershipHandler`.

### Impact Explanation
A single crafted webhook, signable by any org that is a legitimate Shipit tenant, writes a `Membership` row associating an attacker-chosen GitHub login with a `Shipit::Team` belonging to an unrelated organization. If that team's handle (`organization/slug`) is listed in `Shipit.github_teams` (used to gate OAuth/authorization, `lib/shipit.rb` line ~256-258), this directly escalates the attacker's chosen account into an authorization group for VICTIM_ORG, which can gate deploy/rollback permissions elsewhere in the app. This is repeatable against any victim team whose `github_id` is known/guessable, and the write "belongs" to a different tenant than the one that authenticated the request — a cross-tenant record mutation. This matches the High-severity category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: (1) attacker must control (or be an admin of) an organization already configured as a tenant on this Shipit instance, i.e. possess that org's `webhook_secret` — this is a real but not-trivial precondition (it requires the attacker's org to already be onboarded, which is plausible in a multi-tenant Shipit deployment shared across many orgs); (2) attacker needs the numeric `github_id` of an existing `Shipit::Team` row for VICTIM_ORG, obtainable via GitHub's team API or by having previously observed webhook traffic/team pages; (3) a `Shipit::Team` record for that `github_id` must already exist in Shipit's DB (created by a prior legitimate `membership` event for VICTIM_ORG). Given these, the attack is a single unauthenticated-to-Shipit HTTP POST, fully repeatable, and cheap once the preconditions are met.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization`, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify that `params.organization.login` matches the organization used to authenticate the webhook (`repository_owner`) before mutating any `Team`. More generally, `WebhooksController#repository_owner` should not silently trust `organization.login` for verification without also asserting that any org-scoped resource referenced deeper in the payload (`team.id`, etc.) is confirmed to belong to that same organization inside each handler.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerCrossTenantTest < ActiveSupport::TestCase
        test "cannot add a member to a team belonging to a different organization" do
          victim_team = Shipit::Team.create!(
            github_id: 999,
            organization: 'victim-org',
            slug: 'core',
            name: 'Core',
            api_url: 'https://example.com/victim-org/core'
          )

          payload = {
            'action' => 'added',
            'team' => { 'id' => 999, 'name' => 'Core', 'slug' => 'core', 'url' => 'https://example.com' },
            'organization' => { 'login' => 'attacker-org' }, # signed by attacker-org's webhook_secret
            'member' => { 'login' => 'attacker-controlled-login' }
          }

          assert_no_difference -> { Shipit::Membership.count } do
            MembershipHandler.call(payload)
          end

          victim_team.reload
          assert_equal 'victim-org', victim_team.organization
          refute victim_team.members.exists?(login: 'attacker-controlled-login')
        end
      end
    end
  end
end
```
This test currently fails against the existing implementation (a `Membership` row IS created, `victim_team.members` DOES include `attacker-controlled-login`), demonstrating the cross-tenant write. The equality claimed safe by the code (`repository_owner used for signing == organization owning the mutated Team`) does not hold: `organization.login = 'attacker-org'` while `victim_team.organization = 'victim-org'`.
