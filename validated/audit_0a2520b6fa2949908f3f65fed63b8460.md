## Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, while every event handler dispatches on the unrelated `repository.full_name` field — allowing a valid signer for one configured GitHub organization to forge events for repositories belonging to a different configured organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit` supports hosting multiple GitHub Apps, one per GitHub organization, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which app/secret to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) inside the untrusted JSON body [2](#0-1) . However, every event `Handler` resolves which `Stack`/`Repository` to act on using a **different** field of the same untrusted body: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties these two fields together, so the signature only proves the request was signed by *some* configured organization's app — not that it was signed by the owner of the repository the handler is about to act on.

### Finding Description
The binding that should hold is: `organization authenticated == organization of repository written`. Instead the code enforces two independent, unlinked reads of the same attacker-controlled JSON:

- Authentication path: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [4](#0-3) [5](#0-4) .
- Action path: `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [3](#0-2) .

`Shipit.github(organization:)` looks up per-organization app config keyed by whatever string is supplied, with no relation enforced between it and `full_name`'s owner segment [6](#0-5) . In a legitimate GitHub payload these two fields always agree (both derive from the same repository object), but the controller never checks that `repository.owner.login == repository.full_name.split('/').first`. Since the entire request is a single JSON body under attacker control, an attacker who is an admin of *any one* of the GitHub organizations that has its own app configured in Shipit's multi-org `secrets.yml` (and therefore legitimately knows or can trigger a correctly-signed webhook for their own org, e.g. by pushing to their own repo) can instead hand-craft the JSON body so that `repository.owner.login`/`organization.login` names their own org (whose `webhook_secret` they control/know), while `repository.full_name` names a repository belonging to a *different* organization configured on the same Shipit instance. The HMAC signature is computed over `raw_post` using their own org's secret and will verify successfully; `verify_signature` passes; the handler then processes the event against the victim organization's repository/stack.

### Impact Explanation
This breaks the deployment-trust boundary between separately-authenticated GitHub organizations sharing one Shipit instance:
- `push_handler.rb` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the targeted branch of the spoofed repository [7](#0-6) , which can trigger sync/deploy-pipeline side effects for a repository the attacker never actually pushed to and does not own.
- `status_handler.rb` creates a commit status from attacker-supplied `state`/`description`/`target_url` on any `Commit` matching an attacker-chosen `sha`, across the whole install, not scoped to the org whose secret was used [8](#0-7) .
- Pull-request handlers similarly resolve stacks via `full_name` unrelated to the signing org, per `Handler#stacks`.

This qualifies as a cross-organization/cross-repository write triggered by an unauthorized event source — an unauthorized deploy-pipeline action performed against a repository/organization the request was not authenticated for.

### Likelihood Explanation
Exploitability is gated on the deployment running Shipit's **multi-organization** GitHub App configuration (documented as a supported feature) [1](#0-0)  and on the attacker controlling (or being an admin of) at least one of the configured organizations so they can obtain a validly-signed webhook body for it — which they can generate themselves, since they administer that org's app/webhook. From there, crafting the JSON body with a mismatched `full_name` requires no additional privileges: the whole POST body is attacker-supplied and only the HMAC over `raw_post` is checked, never field-internal consistency. No `ApiClient` token, session, or GitHub App private key is needed for the victim organization. Likelihood is Medium-to-High specifically for the multi-org deployment model; the single-org config is not exposed to this issue since there is only one secret to select.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner`/`organization` from the same fields the handlers use (`repository.full_name`'s owner segment, or `organization.login`) and assert they match the value used to select the verifying app before dispatching to `Shipit::Webhooks.for_event`. Alternatively, make `Handler#repository_name`/`#stacks` derive the owner strictly from the value that was already authenticated in `WebhooksController#repository_owner`, rather than independently re-reading `repository.full_name` from the body.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret`, per the documented multi-org config [1](#0-0) .
2. Attacker administers `attacker-org`'s GitHub App and therefore knows/can generate a validly HMAC-signed `push` webhook body using `attacker-org`'s `webhook_secret`.
3. Attacker crafts the JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature` over this exact `raw_post` using `attacker-org`'s known `webhook_secret` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` extracts `repository_owner = "attacker-org"`, looks up `Shipit.github(organization: "attacker-org")`, and verifies the signature successfully [4](#0-3) .
6. `PushHandler` (via `Handler#stacks`) resolves stacks using `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: ...)` on `victim-org/victim-repo`'s stacks [7](#0-6) , despite the attacker never having produced a signature trusted by `victim-org`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
