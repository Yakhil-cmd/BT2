## Title
Webhook signature is verified for a different GitHub organization than the repository/stack the payload actually mutates, enabling cross-tenant webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, `WebhooksController` selects which organization's `webhook_secret` validates an inbound webhook's HMAC signature using one field of the JSON body (`repository.owner.login`), but every downstream event handler determines which `Repository`/`Stack` to mutate using a *different, unrelated* field of the same body (`repository.full_name`). Nothing cross-checks that these two fields refer to the same organization. A tenant that legitimately possesses a valid webhook secret for their own onboarded organization can therefore forge a payload whose signature validates against their own secret while its `repository.full_name` points at a completely different organization's tracked repository, causing Shipit to act on that foreign repository/stack.

`PushHandler` (triggers a stack's GitHub sync), `StatusHandler` (writes commit statuses matched globally by `sha`, not scoped to repo), and `MembershipHandler` (mutates `Team`/`Membership` records keyed off `organization.login`, itself another independently-controlled field) all consume attacker-controlled fields without validating them against the organization whose secret produced the signature: [7](#0-6) [8](#0-7) [9](#0-8) 

The equality that is supposed to hold but is never enforced:
`organization whose webhook_secret validated the signature == organization that owns the repository/stack the handlers write to`.

Before the fix: the two sides can diverge because they are read from independent JSON keys in a single payload the attacker fully controls (once they hold *a* valid secret for *some* onboarded organization). After a correct fix, `repository.full_name`'s owner would be required to match the organization used in `verify_signature` (or the two lookups would be unified to a single authenticated source), rejecting the mismatched request instead of processing it.

### Impact Explanation
In the documented multi-organization configuration (`Shipit.github_organizations`, `github_app_config`, per-org `webhook_secret` — a supported first-class feature, not a deviation from setup docs), a tenant who only holds credentials/webhook-secret knowledge for their **own** organization can cause Shipit to process events against **another** organization's tracked stacks/repositories/teams:
- Force `stack.sync_github` on an arbitrary foreign stack (`PushHandler`).
- Inject arbitrary commit statuses on any commit sha tracked by Shipit, regardless of repository, since `Commit.where(sha:)` is not scoped by repository (`StatusHandler`), potentially manipulating deploy-gating CI checks.
- Create/modify `Team`/`Membership` records under an arbitrary `organization.login` (`MembershipHandler`), affecting `Shipit.github_teams` authorization data.

This is a cross-tenant/cross-repository write achieved without any Shipit session, `ApiClient` token, or actual GitHub write access to the targeted repository — matching the Critical "cross-repository writes" / High "escalation into `Shipit.github_teams` authorization" impact classes.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a documented, intended configuration) where the attacker is one legitimately onboarded tenant organization. No other Shipit credential (ApiClient secret, session, GITHUB_TOKEN, GitHub App private key) is required — only the ability to compute a valid HMAC for their own org's webhook secret and freely choose the JSON body content (`repository.full_name`, `organization.login`) that is sent to `/webhooks`, which is entirely under the sender's control since they are constructing the raw POST body themselves.

### Recommendation
Do not select the signature-verification organization and the mutation target from independently-controlled fields of the same untrusted payload. Either:
- Bind the webhook's HMAC secret to the specific stack/repository record (looked up first from `repository.full_name`) rather than an attacker-suppliable `owner.login`/`organization.login` field, or
- After verifying the signature for `repository_owner`, additionally assert that every repository referenced anywhere in the payload used by handlers (`repository.full_name`, `organization.login`) belongs to that same verified organization, rejecting the request otherwise.

### Proof of Concept
1. Deploy Shipit in multi-organization mode with at least two onboarded organizations, `attacker-org` (secret known to the attacker as its legitimate tenant/admin) and `victim-org` (has a tracked `Stack` for `victim-org/some-repo`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/some-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and sends the request with `X-Github-Event: push` to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, fetches `attacker-org`'s secret, and validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `create` forwards the payload to `PushHandler`, which resolves the target repository from `repository.full_name` = `victim-org/some-repo` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)` on `victim-org`'s stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the signature only ever proved knowledge of `attacker-org`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
