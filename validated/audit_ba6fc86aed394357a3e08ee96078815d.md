### Title
Webhook signature verification authenticates a different entity (`organization`/`repository.owner`) than the one actually written by the handler (`repository.full_name`, `team`/`member`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub organization's `webhook_secret` to HMAC-verify the request against using a value pulled straight out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`), before the signature has been checked. Every webhook handler that subsequently processes the same body acts on a *different* field of that body (`repository.full_name` for repo/stack lookups, `team`/`member`/`organization` for `MembershipHandler`). Nothing ties the org used to select the verification secret to the org/repo/team that is actually mutated. Any Shipit deployment that configures more than one GitHub organization (a documented, supported topology, see `config/secrets.development.shopify.yml`) and leaves any one of them without a `webhook_secret` breaks the binding completely, because `verify_webhook_signature` returns `true` unconditionally when the secret is blank.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#repository_owner` derives the "authenticating organization" purely from attacker-supplied payload content: [1](#0-0) 

That value feeds directly into which secret is used to verify the signature: [2](#0-1) 

`lib/shipit/github_app.rb#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured: [3](#0-2) 

Once the request is (nominally) verified, `create` hands the *entire raw body* to every registered handler for the event, unchanged: [4](#0-3) 

`Shipit::Webhooks::Handlers::Handler#repository_name` (used by `PushHandler`, `StatusHandler`, etc. to locate the target `Stack`) reads a completely different field of the body — `repository.full_name` — with no cross-check against the organization that was used for authentication: [5](#0-4) [6](#0-5) 

The bug-class equality broken: **"organization that authenticated" (`repository_owner`, used to pick the `webhook_secret`) ≠ "repository (or team) that is written"** (`repository.full_name` for `PushHandler`, or `team`/`member` for `MembershipHandler`, whose test coverage shows it creates `Team`/`Membership` records tied to `Shipit.github_teams` authorization): [7](#0-6) 

Just as the CL-2021-47 report describes independent processing of two fields of the same block that should have been evaluated jointly (slashing vs. exit), Shipit independently (a) picks a signing identity from one payload field and (b) acts on an entirely different payload field, with no code anywhere asserting the two must match.

### Impact Explanation
If an operator's Shipit instance is configured with multiple GitHub organizations (explicitly supported, see `docs/setup.md` and the sample `config/secrets.development.shopify.yml` showing `webhook_secret: # nil` as a valid value) and any one org lacks a `webhook_secret`, an unauthenticated attacker can send a raw HTTP POST to `/webhooks` claiming `repository.owner.login` (or `organization.login`) equal to that unsecured org — bypassing signature verification entirely — while setting `repository.full_name`, `team`, or `member` to target a *different*, secured organization's stacks or teams. This lets the attacker:
- Force `GithubSyncJob` runs / stack state changes on repositories belonging to organizations they do not control (cross-repository interaction via `PushHandler`/`StatusHandler`), and
- Potentially inject `Team`/`Membership` records (per `MembershipHandler`, evidenced by `test/controllers/webhooks_controller_test.rb:129-165`) that back `Shipit.github_teams`-based OAuth authorization, which is the High-severity "escalation into `Shipit.github_teams` authorization" category. I was unable to load `membership_handler.rb`'s source directly in this session (index/tool limits) — only its test behavior — so this specific escalation path should be re-verified by reading `app/models/shipit/webhooks/handlers/membership_handler.rb` directly before triage decisions are finalized.

### Likelihood Explanation
Exploitation only requires an unauthenticated HTTP POST to a public endpoint (`/webhooks`) — no session, token, or GitHub credentials are needed. The only precondition is that the Shipit instance manages more than one GitHub organization and at least one has no `webhook_secret` set, a configuration state that is explicitly shown as valid in the repo's own example config.

### Recommendation
- Do not select the verification secret from unauthenticated payload content. Verify the signature against the secret of the organization that actually owns the resolved `Repository`/`Stack`/`Team` being modified, not a value taken from the same untrusted body before that value is trusted.
- Stop treating a blank `webhook_secret` as an implicit "always verified" pass in `GitHubApp#verify_webhook_signature`; require an explicit configuration flag to allow unsigned webhooks for a given org.
- After signature verification, assert that the organization used for verification matches the owner of `repository.full_name` (or `organization.login` for membership events) before invoking handlers.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, e.g. `secure-org` (has `webhook_secret`) and `open-org` (no `webhook_secret`), both installed and visible to any observer of the Shipit UI.
2. Send, without any secret knowledge:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/critical-repo"
  },
  "ref": "refs/heads/main",
  "after": "<sha>"
}
```
3. `repository_owner` resolves to `open-org` → `verify_webhook_signature` returns `true` because `open-org` has no `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
4. `PushHandler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves `secure-org/critical-repo` via `repository.full_name` and enqueues `GithubSyncJob` for that stack — a stack belonging to an org whose webhook trust was never actually established for this request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
