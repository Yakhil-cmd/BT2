### Title
CCMenu API endpoint lets a stack-scoped API token read the build/deploy status of any stack, not just the stack it authorizes - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Shipit binds API tokens to a specific stack via `ApiClient#stack_id`, and `Api::BaseController` enforces this binding for every endpoint by scoping the resolvable `Stack` set through `current_api_client.stack_id?`. `Api::CCMenuController` overrides `stack` to bypass that scoping entirely, resolving the target stack straight from the request parameter instead of from the token's authorized scope. This breaks the equality `stack authorized by token == stack acted upon`, letting any valid `read:stack` token disclose CI/deploy status for stacks it was never granted access to.

### Finding Description
`Api::BaseController` establishes the binding between a token and the stacks it may touch: [1](#0-0) 

`stacks` is filtered to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped (`stack_id?` is true), and every controller that inherits `stack` from `BaseController` inherits this enforcement.

`Api::CCMenuController`, however, defines its own `stack` method that ignores the client's scope and resolves any stack by parameter: [2](#0-1) 

The only authorization check performed is `require_permission :read, :stack`, which merely verifies the token's `permissions` array contains `"read:stack"` — it does not verify which stack the permission applies to: [3](#0-2) 

Because `permissions` is a global list on the `ApiClient` record and `check_permissions!` never compares it against `stack_id`, a token created with `stack: A` and `permissions: ["read:stack"]` (exactly the shape produced by `CCMenuUrlController#client`, which is the officially documented way to mint a per-stack CCMenu token) is fully able to authenticate on `CCMenuController#show` and then, because `stack` resolves independently of `current_api_client.stack_id`, retrieve `deploys_and_rollbacks.last` for **any** `Stack.from_param!(params[:stack_id])`, including stacks the client was never scoped to.

Root cause: the equality the engine is supposed to guarantee for every scoped `ApiClient` — `stack the token authorizes == stack the endpoint acts on` — is only enforced by `BaseController#stack`/`#stacks`, and `CCMenuController` silently reimplements `stack` without threading through that scoping logic. The other endpoints in the same `Api::` namespace (e.g. `StacksController#stack`) correctly go through `stacks.from_param!` and are not affected.

### Impact Explanation
This meets the High-severity bar for "escalation into... unauthenticated [here: cross-scope] read of stack state, task streams or deploy output": an attacker who legitimately holds one stack-scoped CCMenu token (a token type Shipit itself generates and hands to users/CI dashboards, intended to be narrowly scoped to a single stack) can enumerate and read the last deploy/rollback status (name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of every other stack hosted by the same Shipit instance, including private/internal stacks the token holder has no legitimate visibility into. This is a direct violation of the stack-scoping guarantee the rest of the API enforces.

### Likelihood Explanation
Likelihood is high: `CCMenuUrlController#fetch` is the standard, documented mechanism (`app/controllers/shipit/ccmenu_url_controller.rb`) any logged-in Shipit user can use to mint a `read:stack`-scoped CCMenu token for a stack they have access to. No special privilege beyond normal Shipit UI access is required to obtain such a token, and exploiting the bug only requires changing the `stack_id` query/path parameter on the public `api/:stack_id/ccmenu.xml`-style route — no additional credentials or cryptographic material are needed.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoped resolution as the rest of the API (`stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so the `current_api_client.stack_id?` restriction from `BaseController` is honored, restoring the `token-authorized stack == stack acted upon` invariant.

### Proof of Concept
1. As a legitimate Shipit user with access to `stack-A`, call `GET /stack-A/ccmenu_url` (`CCMenuUrlController#fetch`) to mint a `read:stack`-scoped `ApiClient` token bound to `stack-A` (`Shipit::ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack: stack_a, name: 'CCMenu Client')`-equivalent).
2. Using that token (`Authorization: Basic <base64(token)>` or `?token=<token>`), send `GET /api/stack-B/ccmenu.xml` where `stack-B` is a stack the user/token was never granted access to.
3. `CCMenuController#authenticate_api_client` successfully authenticates the token; `require_permission :read, :stack` passes because the token has `"read:stack"` in `permissions`; `stack` resolves `stack-B` directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` check that `BaseController#stacks` would otherwise apply.
4. The response renders `stack-B`'s CCMenu XML (name, activity, last build status/label/time, web URL) — data the token was never authorized to see.
