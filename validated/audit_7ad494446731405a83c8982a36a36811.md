### Title
Webhook signature verification authenticates the claimed organization while a different, attacker-controlled repository field is used to select the Stack that gets written - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` derives the GitHub App/organization used for HMAC verification from `params.dig('repository', 'owner', 'login')`, while the handlers that actually mutate state (e.g. `PushHandler` via `Handler#repository_name`) resolve the target `Repository`/`Stack` from an entirely different field, `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so the "organization whose secret authenticated the request" and "the repository that gets written" can be made to diverge.

### Finding Description
`verify_signature` computes the owning organization from the payload and fetches that organization's `GithubApp` to validate the signature: [1](#0-0) 

Crucially, `GithubApp#verify_webhook_signature` treats an unconfigured `webhook_secret` as an automatic pass: [2](#0-1) 

Meanwhile, the code path that actually performs writes (looking up the `Stack`/`Repository` to sync) uses a *different* JSON field from the same attacker-supplied payload: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository actually acted upon (repository.full_name)`

In this codebase that equality is never enforced — the two lookups are independent reads of attacker-controlled JSON in the same unauthenticated POST body. `WebhooksController#create` is a public, unauthenticated endpoint (only `skip_before_action :verify_authenticity_token`, no session/API-token check), so any external party can submit an arbitrary JSON body as long as `verify_signature` passes.

If a Shipit deployment is configured for multiple GitHub organizations (as documented/supported via the multi-org `github:` config block in `config/secrets.development.example.yml` and exercised by `test/dummy/config/secrets_double_github_app.yml`), and any one of those organizations has no `webhook_secret` configured (`webhook_secret: # nil` is the documented default), an attacker can:
1. Set `repository.owner.login` to that unsecured organization's login, so `Shipit.github(organization: repository_owner).verify_webhook_signature` trivially returns `true` regardless of the actual `X-Hub-Signature` header.
2. Set `repository.full_name` to a *different*, victim organization/repository that is registered as a Shipit `Repository`/`Stack`.
3. Send a forged `push` event; `PushHandler#stacks` resolves the victim `Stack` via `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)`, forcing the victim stack's `Commit` head/ref state to whatever SHA the attacker specifies.

### Impact Explanation
This crosses a genuine trust boundary in the Shipit engine's own code with no session, `ApiClient` token, or repository write access required — the webhook endpoint is unauthenticated by design and relies solely on HMAC verification to establish which organization is "speaking." By decoupling the field used to select the verification key from the field used to select the write target, an unprivileged network attacker can inject fabricated commit-head/state data into a victim's `Stack` sync pipeline, which drives subsequent deploy/rollback decisions (`GithubSyncJob`/`Stack#sync_github`). This is an unauthorized write into another repository's Shipit state, satisfying the Critical "cross-repository writes" bar in the rules.

### Likelihood Explanation
Requires: (a) the Shipit instance to be multi-org-configured, and (b) at least one configured organization lacking a `webhook_secret` (a state explicitly supported and shown as the documented default in `config/secrets.development.example.yml`). Given that, no credentials, tokens, or prior access are needed — only knowledge of the unsecured organization's login and the victim repository's `owner/name`, both of which are public GitHub information. This is a realistic misconfiguration rather than a purely theoretical one, since the example/default config ships with `webhook_secret` commented out.

### Recommendation
- In `WebhooksController#verify_signature`, require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`) in `lib/shipit/github_app.rb`.
- Cross-validate that the organization used to select the verification key (`repository.owner.login`) matches the owner segment of `repository.full_name` before dispatching to handlers in `app/controllers/shipit/webhooks_controller.rb` / `app/models/shipit/webhooks/handlers/handler.rb`, rejecting the payload if they disagree.

### Proof of Concept
1. Configure Shipit with two organizations in `github:` config, e.g. `orgA` (no `webhook_secret` set) and `orgB` (properly configured, hosting the victim `Repository`/`Stack`).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
using any (or no valid) `X-Hub-Signature` header.
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`; since `orgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-83`.
4. `PushHandler` resolves the stack via `repository.full_name = "orgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating the victim stack's state despite the request never having been authenticated for `orgB`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
