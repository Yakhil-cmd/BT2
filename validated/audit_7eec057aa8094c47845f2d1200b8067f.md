### Title
Membership webhook handler trusts `organization.login`/`team.id` without verifying it matches the organization whose secret authenticated the request - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` mutates `Team`/`Membership` records using `params.organization.login` and `params.team.id` from the webhook body, but the signature check in `WebhooksController#verify_signature` selects the HMAC secret using a *different, independently attacker-influenced* value (`repository_owner`), and never compares the two. This breaks the implicit binding "the organization whose secret verified the request == the organization whose team is mutated."

### Finding Description
The binding that should hold is: `github_app.organization` (the org whose `webhook_secret` produced a valid HMAC) `== params.organization.login` (the org the handler uses to create/select the `Team` and mutate its membership). No code path enforces this equality.

- `WebhooksController#verify_signature` derives the verifying organization from `repository_owner`: [1](#0-0) [2](#0-1) 
`repository_owner` prefers `repository.owner.login` over `organization.login`. Membership events don't naturally contain a `repository` key, but nothing prevents an attacker from adding one to the raw POST body.

- `MembershipHandler#process`/`find_or_create_team!` instead trusts `params.organization.login` and `params.team.id` directly, with no cross-check against `repository_owner` or the `GitHubApp#organization` that verified the signature: [3](#0-2) 

- Critically, in the single-org (legacy) secrets schema, `Shipit.github(organization:)` **ignores the `organization` argument entirely** and always resolves to the one configured app: [4](#0-3) 
`github_default_organization` is `nil` in this schema, so `config = secrets.github` regardless of what `repository_owner` (attacker-controlled `organization.login`) says. This means an attacker who owns their own org (with the sole configured GitHub App) can sign an arbitrary payload with their own real, known `webhook_secret`, while setting `organization.login` and `team.id` to values referencing a `Team` belonging to a victim org that only exists via a `Shipit.github_teams` handle: [5](#0-4) 

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: membership`, a body `{"action":"added","team":{"id":<victim_team.github_id>,...},"organization":{"login":"victim-org"},"member":{"login":"attacker-login"}}`, signed with the attacker's own genuine `webhook_secret`. `verify_signature` passes (single-org schema uses the sole secret unconditionally, or in multi-org schema the attacker can additionally supply a spoofed `repository.owner.login` pointing at their own org to force selection of their own known secret while the `organization` sub-object still names the victim). `MembershipHandler#find_or_create_team!` finds the pre-existing victim `Team` by `github_id` and `team.add_member(member)` adds the attacker's account to it.

No other guard intercepts this: `verify_webhook_signature` only checks HMAC validity against the resolved (attacker-controllable) app, `drop_unhandled_event` only checks the event type is registered, and the `ExplicitParameters` schema on `MembershipHandler` only validates presence/type of `team`, `organization`, `member`, not their relationship to the verifying identity. [6](#0-5) 

### Impact Explanation
If the victim's `Team` (referenced by `Shipit.github_teams`) is used for authorization (`User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id))`), this lets an unprivileged attacker add an arbitrary GitHub login (their own) to that team purely by sending a self-signed webhook, escalating themselves into `Shipit.github_teams` authorization without ever being a real GitHub member of the victim's team: [7](#0-6) 
This matches the High severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any `Team` record whose `github_id` the attacker can learn/guess (team IDs are not secret), and does not require any Shipit or GitHub secret belonging to the victim.

### Likelihood Explanation
Preconditions: the attacker must genuinely own a GitHub org/repo with the Shipit GitHub App installed (satisfied per the question), and the victim org's team must be referenced in `Shipit.github_teams` (an existing, common authorization configuration) or the deployment must use the legacy single-org secrets schema. The attacker needs the target `Team#github_id` (discoverable via the GitHub API for the victim org's public/known teams, or via the Shipit UI). No signature forgery or secret theft is required, only a correctly-signed POST using the attacker's own legitimate secret — this is low-cost and fully repeatable.

### Recommendation
In `MembershipHandler#process`/`find_or_create_team!`, require that `params.organization.login` (case-insensitively) equals the organization resolved by `verify_signature` (i.e., pass `repository_owner`/`github_app.organization` into the handler and assert equality before creating/mutating any `Team`). Additionally, in `WebhooksController#repository_owner`, do not allow an unrelated `repository.owner.login` to silently override `organization.login` for org-level events like `membership`; and fix `Shipit.github` so that when using the multi-org schema it never accepts a `nil`/mismatched org silently, and for the single-org schema, still validate that the payload's own organization claim matches the sole configured organization when such a claim is present.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "cannot mutate a team belonging to a different org than the one that verified the signature" do
  victim_team = shipit_teams(:some_victim_org_team) # github_id known, organization: 'victim-org'
  attacker_login = 'attacker'

  # Simulate: signature verified using ATTACKER's own org secret (repository_owner == 'attacker-org'),
  # but payload claims organization.login == victim_team.organization.
  params = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => victim_team.name, 'slug' => victim_team.slug, 'url' => victim_team.api_url },
    'organization' => { 'login' => victim_team.organization },
    'member' => { 'login' => attacker_login }
  }

  verifying_org = 'attacker-org' # what verify_signature actually authenticated

  assert_no_difference -> { victim_team.members.count } do
    # Assert the equality that SHOULD be enforced but isn't:
    assert_not_equal verifying_org, params['organization']['login']
    Shipit::Webhooks::Handlers::MembershipHandler.call(params)
  end
  # Currently this assertion fails: team.add_member is invoked despite verifying_org != organization.login
end
```
This demonstrates that no code compares `repository_owner`/the verifying `GitHubApp#organization` against `params.organization.login` before `MembershipHandler` mutates `Team`/`Membership` records.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
