### Title
Underpriced Congestion-Gas Griefing Blocks All Transactions to a Shard - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
NEAR's cross-shard congestion control rejects **all** new transactions addressed to a shard once that shard's `incoming_congestion` exceeds `reject_tx_congestion_threshold` (default 0.8). The congestion metric is computed from the **full prepaid/attached gas** declared on a receipt, not from the gas actually burnt. Because the protocol's gas-refund penalty (`gas_refund_penalty` / `min_gas_refund_penalty`) is currently set to **0** (NEP-536 rollout has not yet enabled the fee), an attacker can flood a target shard with receipts that declare very high `prepaid_gas` but execute cheaply (e.g. call a non-existent method or a trivial function), get almost the entire attached gas refunded at zero penalty, and still have contributed the full attached-gas amount to `incoming_congestion` while the receipt sat in the delayed-receipt queue. This is the same "no-fee daily-limit exhaustion" pattern as the reported Boba `Teleportation` bug: an unprivileged account can lock (not permanently spend) enough NEAR to congest a shard and lock out other users' transactions to accounts on that shard, at negligible net cost.

### Finding Description
Congestion accounting is done in `action_receipt_congestion_gas`, which sums `prepaid_exec_gas`, `prepaid_send_cost`, and `gas_attached_to_fns` — i.e. the receipt's full declared gas budget, independent of how much gas is eventually burnt during execution: [1](#0-0) 

This value is added to the shard's `delayed_receipts_gas` while the receipt is queued (`DelayedReceiptQueueWrapper::push` / `apply_congestion_changes`): [2](#0-1) [3](#0-2) 

`incoming_congestion` is `delayed_receipts_gas / max_congestion_incoming_gas`, and once it crosses `reject_tx_congestion_threshold`, `shard_accepts_transactions()` returns "no", which blocks **new transactions from any sender** targeting that shard: [4](#0-3) [5](#0-4) 

This rejection is enforced at the RPC boundary via `can_verify_and_charge_tx`, returning `InvalidTxError::ShardCongested` to legitimate users, which is exactly the DoS behavior confirmed by the existing test: [6](#0-5) 

Critically, the actual token cost to the attacker is bounded by burnt gas only, because unused prepaid gas is refunded, and the refund penalty that was designed to discourage over-attaching gas is currently disabled (set to 0): [7](#0-6) [8](#0-7) 

So an attacker can submit many transactions/receipts to a target shard that (a) attach very large `prepaid_gas` (maximizing their contribution to `incoming_congestion`), and (b) fail immediately or execute a cheap no-op (minimizing burnt gas), receiving nearly all the attached NEAR back as a refund at zero penalty. The design documentation for congestion control explicitly acknowledges this class of gaming is possible and only bounded by falling back to a guaranteed minimum per-shard throughput, not prevented: [9](#0-8) 

### Impact Explanation
While an attacker holds the (refundable) locked NEAR balance and pays only the negligible exec fee, they can push a target shard's `incoming_congestion` above `reject_tx_congestion_threshold`, causing chunk producers and RPC nodes to reject transactions to any account on that shard for as long as the delayed-receipt queue takes to drain (bounded by the shard's per-chunk gas budget for delayed-receipt processing). This denies service to all unrelated, unprivileged users trying to interact with accounts/contracts on that shard — directly analogous to the reported Boba issue where an attacker exhausts a shared, fee-free capacity limit to block other users for an extended window.

### Likelihood Explanation
The attack requires only: (1) an account with enough NEAR balance to cover attached gas upfront (fully refundable, since `gas_refund_penalty` is 0), and (2) the ability to submit many function-call transactions targeting a chosen shard with large attached gas and a cheap/failing execution path (e.g., call a nonexistent method). No special privileges, validator status, or protocol bugs are required — it is a documented, currently-unmitigated consequence of the congestion-control design combined with the temporarily-disabled gas-refund penalty.

### Recommendation
- Re-enable/accelerate rollout of the NEP-536 gas-refund penalty (`gas_refund_penalty` / `min_gas_refund_penalty`) so that attaching large, unused prepaid gas carries a real cost, discouraging cheap congestion griefing.
- Consider weighting `incoming_congestion` accounting toward gas that is likely to actually be burnt (or capping per-sender/per-account contribution to a shard's congestion metric) rather than the full declared `prepaid_gas`, to reduce the ability of a single account to unilaterally spike a shard's congestion level with cheap-to-fail receipts.

### Proof of Concept
The existing test `test_rpc_client_rejection` in `test-loop-tests/src/tests/congestion_control_limits.rs` already demonstrates the mechanics: submitting a burst of high-prepaid-gas function calls (`submit_n_100tgas_fns`) drives a shard into `ShardCongested` rejection state for subsequent transactions from any signer: [10](#0-9) 
To turn this into a low-cost griefing attack, replace the successful 100-Tgas contract calls with function calls that attach similarly large `prepaid_gas` but target a nonexistent method or immediately fail, so that the bulk of the attached gas is refunded (at zero penalty per `docs/architecture/how/gas.md` lines 219-242) while the same full `prepaid_gas` amount is still counted toward `incoming_congestion` via `action_receipt_congestion_gas`.

```rust
fn action_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
    action_receipt: VersionedActionReceipt,
) -> Result<Gas, IntegerOverflowError> {
    let prepaid_exec_gas =
        total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
            .gas
            .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee().gas)
            .ok_or(IntegerOverflowError)?;
    // account for gas guaranteed to be used for creating new receipts
    let prepaid_send_cost = total_prepaid_send_fees(config, &action_receipt.actions())?;
    let prepaid_gas = prepaid_exec_gas.checked_add_result(prepaid_send_cost.gas)?;

    // account for gas potentially used for dynamic execution
    let gas_attached_to_fns = total_prepaid_gas(&action_receipt.actions())?;
    let gas = gas_attached_to_fns.checked_add_result(prepaid_gas)?;

    Ok(gas)
}
```

```markdown
### Gas Refund Fee

After executing the transaction, there might be unspent gas left. For function
calls, this is the normal case, since attaching exactly the right amount of gas
is tricky. Additionally, in case of receipt failure, some actions that did not
start execution will have the execution gas unspent. This gas is converted back
to NEAR tokens and sent as a refund transfer to the original signer.

Before protocol version 78, the full gas amount would be refunded and the refund
transfer action was executed for free. With [NEP-536](https://github.com/near/NEPs/pull/536)
which was implemented in version 78, the plan was to have the network charge a
fee of 5% of unspent gas or a minimum of 1 Tgas. This often removes the need to
send a refund, which avoids additional load on the network, and it compensates
for the load of the refund receipt when it needs to be issued. This is intended
to discourage users from attaching more gas than needed to their transactions.
In the nearcore code, you will find this fee under the name `gas_refund_penalty`.

However, due to existing projects that need to attach more gas than they
actually use, the introduction of the new fee has been postponed. The code is
still in place but the parameters were set to 0 in PR
[#13579](https://github.com/near/nearcore/pull/13579). Among other problems, in
the reference FT implementation, `ft_transfer_call` requires at least 30 TGas
even if most of the time only a fraction of that is burnt. Once all known
problems are resolved, the plan is to try and introduce the 5% / 1 Tgas parameters.
```

```markdown
## Gas Refunds

Gas refunds are generated when a receipt used the amount of gas lower than the attached amount of gas.

If the receipt execution succeeded, the gas amount is equal to `prepaid_gas + execution_gas - used_gas`.

If the receipt execution failed, the gas amount is equal to `prepaid_gas + execution_gas - burnt_gas`.

The difference between `burnt_gas` and `used_gas` is the `used_gas` also includes the fees and the prepaid gas of
newly generated receipts, e.g. from cross-contract calls in function calls actions.

From this unspent gas amount, the network charges a gas refund fee, starting with protocol version 78. The exact fee is calculated as `max(gas_refund_penalty * unspent_gas, min_gas_refund_penalty)`. As of version 78, `gas_refund_penalty` is 0% and `min_gas_refund_penalty` 0 Tgas, always resulting in a zero-cost fee. This is only a stepping stone to give projects time to adapt before the fee is taking effect. The plan is to increase this to 5% and 1 Tgas, as specified in [NEP-536](https://github.com/near/NEPs/blob/master/neps/nep-0536.md). There is no fixed timeline available for this.

Should the gas refund fee be equal or larger than the unspent gas, no refund will be produced.
```
