### Title
Archived `Owner(token_id)` persistent entry makes every controller operation on the account fail closed (`AccountNotFound`), freezing the position and blocking liquidations — ([File: contracts/controller/src/storage/account.rs])

### Summary
The controller resolves account ownership by calling `owner_of` on the position-nft contract (`try_account_owner` → `nft_try_owner_of_call`). The NFT's `Owner(token_id)` / `Balance(owner)` persistent entries are only lifted to the 120-day user TTL window at `mint` (and via the permissionless `renew`). They are **not** renewed by the OZ `transfer`/`approve` paths (reachable by any unprivileged holder via position-nft `transfer`/`approve`, which are in scope). If the `Owner` entry expires/archives while the controller-side account entries (`AccountMeta`, `SupplyPositions`, `BorrowPositions`) are still live — e.g., because account activity keeps calling `renew_user_account`/`set_user` while nothing touches the NFT contract — then `try_account_owner` returns `None`, `account_owner`/`get_account` panic with `AccountNotFound`, and `nft.renew` itself panics (`Base::owner_of` traps on the missing key rather than restoring it). This is the on-chain analog of a null-pointer dereference: an assumed-present object is absent and every path through it crashes.

### Finding Description
- `try_account_owner` returns `None` on "missing token, or failed lookup" and `get_account`/`get_account_borrow_only` convert that into a hard panic via `AccountNotFound` / `AccountNotInMarket` [1](#0-0) [2](#0-1) 
- Every state-changing controller entrypoint (`supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `multiply`, `swap_*`, `update_account_threshold`, `recapitalize`, flash paths) loads the account through `get_account`, so all of them revert for the affected account.
- On the NFT side, `Owner`/`Balance` are extended to `TTL_BUMP_USER` only inside `mint` and `renew`; nothing in `transfer`/`approve` (inherited OZ enumerable implementation, exposed via `NonFungibleToken`/`NonFungibleEnumerable`) re-lifts them, and a transfer rewrites `Owner` at the default persistent window [3](#0-2) [4](#0-3) 
- The recovery path `renew(token_id)` is documented to panic on a missing/archived token rather than restore it: `extend_ttl` on a missing key traps, and the pre-check `Base::owner_of` itself traps on the archived entry [5](#0-4) 
- Meanwhile the controller's own account entries are renewed independently on every successful read/write (`renew_user_key`/`set_user`/`renew_user_account`), so the account data can easily outlive the NFT ownership entry that gates it [6](#0-5) [7](#0-6) 

### Impact Explanation
Temporary freezing of funds, and a temporary insolvency vector. While `Owner(token_id)` is archived, the account's collateral and debt are unreachable: the owner cannot withdraw or repay, and — critically — `liquidate` also loads the account through `get_account`, so an underwater position cannot be liquidated or have its bad debt cleaned. Any holder can trigger this deliberately on their own account (transfer the NFT, then let the shortened `Owner` TTL lapse while keeping the controller account warm via any successful op) to dodge liquidation during adverse price moves; interest keeps accruing against the pool while the account is untouchable. Recovery requires a ledger footprint restore transaction for the NFT persistent entries, which is possible but is an external dependency the protocol does not perform itself.

### Likelihood Explanation
Requires the `Owner` entry's TTL to lapse while the account stays active — a 30-ish-day default window after any `transfer`/`approve` (or simply a long-inactive NFT whose account is renewed by other means). Not exploitable on demand, but deliberately inducible by the account holder at near-zero cost (one `transfer`), and liquidation-dodging gives it an economic motive. Medium.

### Recommendation
Have the controller renew the NFT ownership TTL itself whenever it resolves ownership — e.g., make `try_account_owner`/`account_owner` (or `renew_user_account`) call a restore-or-extend path on the NFT, and extend `Owner`/`Balance` inside the NFT's `transfer`/`approve` overrides so they stay on the user window regardless of holder activity. At minimum, ensure `renew` (or a new controller-invoked function) issues `restore`/`extend_ttl` handling for archived entries instead of relying on `owner_of` succeeding.

### Proof of Concept
1. Alice supplies collateral and borrows; her account id `N` is minted (`mint` lifts `Owner(N)` to `TTL_BUMP_USER`).
2. Alice calls `position_nft.transfer(alice, alice, N)` (or `approve`). The OZ `Base::update` rewrites `NFTStorageKey::Owner(N)` at the default persistent TTL, discarding the user-window lift.
3. Alice keeps the controller account alive via a cheap successful op (e.g., `update_account_threshold` or a tiny `supply`), which renews `AccountMeta`/`SupplyPositions` to 120 days but never touches the NFT contract.
4. Wait for the `Owner(N)` default TTL to elapse. The entry archives while `AccountMeta(N)` is still live.
5. Market moves against Alice. A liquidator calls `controller.liquidate(liquidator, N, ...)`: `get_account(N)` → `get_account_meta` succeeds → `try_account_owner(N)` → `nft_try_owner_of_call` traps on the archived `Owner(N)` and returns `None` → panic `AccountNotFound`. Liquidation reverts; the position cannot be seized and `clean_bad_debt` likewise fails.
6. Alice's own `withdraw`/`repay` and the permissionless `position_nft.renew(N)` also revert (`renew` calls `Base::owner_of` on the archived entry). Funds stay frozen and debt keeps accruing until someone submits a Soroban `restore_footprint` for `Owner(N)`/`Balance(alice)`.

```rust
/// Renews user TTL for each existing account entry; does not renew the NFT.
pub(crate) fn renew_user_account(env: &Env, account_id: u64) {
    let persistent = env.storage().persistent();
    let keys = [
        ControllerKey::AccountMeta(account_id),
        ControllerKey::SupplyPositions(account_id),
        ControllerKey::BorrowPositions(account_id),
        ControllerKey::Delegates(account_id),
    ];
    for key in &keys {
        if persistent.has(key) {
            renew_user_key(env, key);
        }
    }
}
```

```rust
/// Extends the persistent `Owner(token_id)` and `Balance(owner)` entries to the
/// user window. The OZ enumeration entries (`NFTEnumerableStorageKey::*`) keep
/// their default windows and rely on protocol-23 auto-restore; they hold no
/// accounting state (INV-STOR-02b, INV-STOR-02d).
fn extend_user_persistent_ttl(e: &Env, owner: &Address, token_id: u32) {
    let p = e.storage().persistent();
    p.extend_ttl(
        &NFTStorageKey::Owner(token_id),
        TTL_THRESHOLD_USER,
        TTL_BUMP_USER,
    );
    p.extend_ttl(
        &NFTStorageKey::Balance(owner.clone()),
        TTL_THRESHOLD_USER,
        TTL_BUMP_USER,
    );
}
```

```rust
    /// Extends the TTL of `token_id`'s persistent `Owner` entry and its owner's
    /// `Balance` entry to the protocol's per-user renewal window, plus the
    /// instance TTL.
    /// Permissionless: a TTL extension cannot move, approve or reassign the
    /// token, and it cannot shorten a lifetime.
    ///
    /// OZ `owner_of` extends `Owner` to only 30 days. The controller calls this
    /// from `renew_account`, so account renewal keeps ownership alive for the
    /// same 120-day window as the account entries (INV-STOR-02b).
    ///
    /// Panics with the OZ `NonExistentToken` error when the token was never
    /// minted or was burned.
    pub fn renew(e: &Env, token_id: u32) {
        // Existence check first: extend_ttl on a missing key would trap with
        // a storage error; owner_of gives the standard token error instead.
        let owner = Base::owner_of(e, token_id);
        extend_user_persistent_ttl(e, &owner, token_id);
        renew_instance(e);
    }
```
