### Title
Unvalidated route venues can append arbitrary wallet transfers to signed strategy authorization - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
User-supplied swap routes cause the configured router to invoke payload-selected pool contracts. Although the controller limits its own authorization to one exact input transfer, a malicious venue can request additional token transfers from the original caller while executing below that caller’s authorization entry. If the wallet signs the authorization tree returned by simulation—including the malicious child transfer—the venue can steal arbitrary unrelated tokens from the caller while still returning a valid swap output.

### Finding Description
`swap_tokens` forwards the caller-controlled `swap` payload to `router.execute_strategy` after authorizing only the intended `token_in -> router` transfer for `amount_in`. [1](#0-0) 

The router dispatches every encoded `Swap` hop to the venue implementation and payload-selected `pool` address, with no venue-address allowlist. [2](#0-1) [3](#0-2) 

A route-selected contract can therefore execute under the strategy’s authorization context and invoke `token.transfer(caller, attacker, amount)` for an unrelated wallet token. The harness demonstrates that simulation records this malicious transfer as a child invocation beneath `swap_collateral`, and that signing that returned tree authorizes the theft. [4](#0-3) [5](#0-4) 

Reachable entrypoints include `swap_collateral`, `multiply` and its `convert_swap`, `swap_debt`, and `repay_debt_with_collateral`, each of which accepts a route that reaches `swap_tokens`. [6](#0-5) [7](#0-6) 

### Impact Explanation
Theft of user funds. A malicious route can steal wallet assets unrelated to the listed lending assets and unbounded by `total_in`, `min_out`, or the final account risk check. The route can still return sufficient output to satisfy the strategy, leaving the user with a valid position but losing arbitrary approved/signable wallet tokens. The regression test demonstrates loss of the victim’s entire `WALLET_BALANCE` while the expected ETH collateral is deposited. [8](#0-7) 

### Likelihood Explanation
Likelihood is moderate because exploitation requires the victim to submit a malicious route and sign the complete authorization tree produced by simulation. A wallet or client that transparently displays every child invocation would prevent the attack. However, ordinary users may treat a quoted route as opaque data, and the malicious child transfer is embedded in a root authorization for a normal-looking lending operation rather than submitted as a separate transfer.

### Recommendation
Restrict route execution so venue calls cannot request authorization from the original caller. Prefer invoking venues from a router context that only authorizes the router’s own exact input transfer, or add an explicit allowlist/registry of venue contracts. At minimum, require clients and wallet integrations to reject any authorization tree containing calls other than the expected token input transfer and venue operations, and document that `simulateTransaction` output must be decoded before signing.

### Proof of Concept
The harness contains a complete reproduction:

1. The test router pulls the declared input and invokes the `hop_pool` address embedded in the route. [9](#0-8) 
2. The attacker-deployed pool calls `wallet_token.transfer(victim, attacker, amount)`. [4](#0-3) 
3. `Controller.swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)` is invoked with that route. [10](#0-9) 
4. Simulation records the rogue `wallet_token.transfer` as a child of Alice’s `swap_collateral` authorization. [11](#0-10) 
5. Signing that tree makes the transaction succeed, transfers all `77_770_000_000` wallet-token units to the attacker, and deposits the expected swap output. [12](#0-11)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
