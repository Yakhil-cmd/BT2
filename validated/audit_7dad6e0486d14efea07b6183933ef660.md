### Title
Cross-organization team membership confusion in `MembershipHandler#process` allows escalation into `Shipit.github_teams` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id` and never verifies that the webhook's authenticated organization (`params.organization.login`) matches `team.organization`. In a multi-org Shipit deployment, an attacker who administers their own legitimately-configured GitHub org (with their own real `webhook_secret`) can send a `membership` webhook naming a `team.id` that belongs to a different, protected organization, and `team.add_member(member)` will still run, granting an arbitrary GitHub login membership in that protected team.

### Finding Description
The binding that should hold is: `webhook.organization.login == team.organization` before any `Membership` is written for that `team`. The code never establishes this.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`). Membership payloads have no `repository` key, so `repository_owner` becomes `params.organization.login` — attacker-controlled.
- `Shipit.github(organization: repository_owner)` (`lib/shipit.rb:170-181`) resolves the `GitHubApp` for that org via `github_app_config`, so if the attacker genuinely administers `attacker-org` as a configured org in this multi-tenant Shipit instance, the signature check against their own real `webhook_secret` succeeds — this is a *correct* verification of "the request came from attacker-org," not a forged signature.
- `MembershipHandler.call` → `#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`). This matches purely on `github_id`; if a `Team` row already exists (e.g. seeded via `Shipit.github_teams`, `lib/shipit.rb:256-258`) with `organization: 'target-org'`, the block is skipped and `team.organization` is left untouched at `'target-org'`.
- `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) then unconditionally creates a `Membership` linking the attacker-controlled `User` (created via `User.find_or_create_by_login!(params.member.login)`, itself derived from unauthenticated payload data) to the *target org's* team.
- Nothing in `Handler`, the `ExplicitParameters` schema, or `MembershipHandler` cross-checks `params.organization.login` against `team.organization`.

This is a confused-deputy flaw: the org that authenticated the webhook is not the org the mutated `Team` belongs to.

### Impact Explanation
A successful request creates a `Membership` binding an attacker-chosen `User` (login taken straight from the unauthenticated `member.login` field) to a `Team` that may be listed in `Shipit.github_teams`. `User#authorized?` (`app/models/shipit/user.rb:80-82`) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, so this directly grants that user full Shipit UI/API access as if they were a member of a protected GitHub team — an escalation into `Shipit.github_teams` authorization, matching the "High" impact category (unauthorized access is *not* achieved by forging the target org's signature, only by exploiting the missing organization-binding check on `Team` lookups). It is repeatable against any `Team` row whose `github_id` the attacker can learn or guess, and against any `member.login` the attacker wants to add.

### Likelihood Explanation
Exploitation requires: (1) a multi-org Shipit deployment where `github_default_organization` is non-nil and multiple orgs each have their own `webhook_secret` configured in `secrets.github` (`lib/shipit.rb:170-200`), (2) the attacker legitimately administering one such configured org (so they possess a real, valid `webhook_secret` for *their own* org only), and (3) a `Team` row for the target org already existing with a known `github_id` (teams are pre-created via `Shipit.github_teams`/`teams:fetch`, and GitHub team IDs are not secret). Given these operator/deployment-level conditions, the attacker's cost is a single crafted HTTP POST with a correctly-computed HMAC using their own secret — no target-org secret is ever needed.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, verify that `params.organization.login` matches the existing `team.organization` before performing any mutation; reject (or no-op) the event if they diverge instead of relying on `github_id` alone to identify the team.

### Proof of Concept
Minitest plan (`test/models/webhooks/membership_handler_test.rb`, `ActionController::TestCase`):
1. Seed `Team.create!(github_id: 4242, organization: 'target-org', name: 'core', slug: 'core', api_url: '...')` and ensure it is included in a stubbed `Shipit.github_teams`.
2. Configure multi-org secrets so `Shipit.github(organization: 'attacker-org')` resolves to a distinct `GitHubApp` with its own `webhook_secret`.
3. POST `/webhooks` with header `X-Github-Event: membership`, signed with `attacker-org`'s real secret, body: `{action:'added', team:{id:4242,name:'core',slug:'core',url:'...'}, organization:{login:'attacker-org'}, member:{login:'attacker'}}`.
4. Assert response is `200`, then assert `Shipit::Membership.exists?(team: Team.find_by(github_id: 4242), user: User.find_by(login: 'attacker'))` is `true` — i.e. `team.organization` (`'target-org'`) != authenticated org (`'attacker-org'`) yet the membership was written.
5. Assert `User.find_by(login: 'attacker').authorized?` returns `true`.
