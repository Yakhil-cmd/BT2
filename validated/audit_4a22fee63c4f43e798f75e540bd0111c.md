Confirmed root cause: `WebhooksController#verify_signature` selects the GitHub App (and its `webhook_secret`) to validate the request against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) straight out of the **unverified** `request.raw_post` JSON body [1](#0-0) [2](#0-1) . Once the signature check for that org passes, `create` re-parses the same raw body and dispatches it to handlers such as `PushHandler`, which resolves the target `Stack`/`Repository` using a *different* field of the same unverified body: `payload.dig('repository', 'full_name')` [3](#0-2) , then `Repository.from_github_repo_name` splits that string on `/` to get `owner`/`name` and looks up the stack by that owner [4](#0-3) .

### Title
Webhook signature is validated against `repository.owner.login`, but the repository actually written to is resolved from the independent `repository.full_name` field, letting a holder of Org A's webhook secret spoof events for Org B's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multiple GitHub Apps, one per GitHub organization, each with its own `webhook_secret` [5](#0-4) . `WebhooksController#verify_signature` picks which app/secret to use for HMAC verification based on `repository_owner`, computed from the JSON body itself [1](#0-0) [2](#0-1) . The HMAC only proves the raw bytes were signed by *some* configured org's secret; it never binds "the org whose key produced this signature" to "the repository whose stacks get mutated" — that binding is instead re-derived later from a sibling JSON field (`repository.full_name`) that isn't cryptographically tied to `repository.owner.login`.

### Finding Description
This is a direct structural analog of the Sherlock M-1 bug class: a value used to derive a downstream trust decision (there: the calldata fee amount used to compute a keeper refund; here: the repository/stack that gets written) is taken from a payload field that is never actually covered/bound by the verification step (there: `_calldataFee` always returns 0 regardless of input; here: `full_name` is never checked against `owner.login`, the field that *is* used to pick the verifying secret).

Concretely:
1. `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and asks `Shipit.github(organization: repository_owner)` for that org's `GitHubApp`, then calls `verify_webhook_signature` with that org's `webhook_secret` [1](#0-0) .
2. `verify_webhook_signature` just does an HMAC-SHA1 compare of the raw body against that one secret [6](#0-5) . It says nothing about which repository the body concerns beyond the org whose secret was used to select it.
3. `create` re-parses the same raw body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the full untouched params hash [7](#0-6) .
4. `PushHandler` (and other handlers via `Handler#stacks`) resolve the repository using `payload.dig('repository', 'full_name')`, not `repository.owner.login` [3](#0-2) .
5. `Repository.from_github_repo_name` blindly splits `full_name` on `/` to get an independent `owner`/`name` pair used for the DB lookup [4](#0-3) .

So the equality that should hold is: `org whose webhook_secret validated this request == owner of the repository whose stacks are mutated by this request`. Nothing enforces `repository.owner.login == full_name.split('/').first`. An attacker who legitimately controls (or has compromised) a GitHub App installation/webhook secret for **Org A** (a repo they are entitled to send webhooks for) can craft a raw POST body where `repository.owner.login = "OrgA"` (so it passes signature verification against Org A's secret) but `repository.full_name = "OrgB/target-repo"`. The signature check passes because it only ever looks at `owner.login`, and the push handler then syncs/writes to stacks belonging to `OrgB/target-repo`, a repository never authenticated by the presented signature.

### Impact Explanation
This breaks the deployment-trust boundary between GitHub organizations that Shipit's multi-org config is explicitly designed to preserve (`docs/setup.md`'s "Using Multiple Github Applications" section states a GitHub App can only authenticate to the org it's installed in) [8](#0-7) . By forging `repository.full_name` while keeping `repository.owner.login` matching an org whose secret the attacker controls, the attacker can trigger `GithubSyncJob`/`sync_github` for stacks belonging to a completely different, unrelated organization/repository, causing unauthorized commit/status ingestion and out-of-band syncs against a repository the attacker was never granted webhook rights to. This is a cross-repository/cross-organization webhook-trust bypass — a `PushHandler`-triggered write against a stack that the presented signature never authorized.

### Likelihood Explanation
Exploitation only requires the attacker to already possess a valid webhook secret for *any one* configured GitHub organization on the Shipit instance (a very plausible position for a customer/tenant in a multi-org deployment, or anyone who can trigger/replay an app-installation webhook for a repo they legitimately administer) and the ability to send an arbitrary POST to `/webhooks` with a forged body — no privileged Shipit session, API token, or GitHub write access to the target org is required, satisfying the "unprivileged attacker" scope.

### Recommendation
Bind the field used for signature-org selection to the field used for repository resolution: after verifying, additionally assert `repository.owner.login` (or the org actually associated with the verified `GitHubApp`) matches `full_name.split('/').first` before dispatching to handlers, or derive `repository_name`/stack lookup exclusively from `repository.owner.login` + `repository.name` rather than the independently-supplied `full_name` string.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, and a Stack tracking `OrgB/target-repo`.
2. As the holder of `OrgA`'s webhook secret, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
   with `X-Hub-Signature` computed using `OrgA`'s webhook secret over this exact raw body.
3. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `OrgA`'s `GitHubApp`, and the HMAC check passes [1](#0-0) .
4. `create` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("OrgB/target-repo")` and finds/syncs the `OrgB` stack, even though the presented signature only ever proved knowledge of `OrgA`'s secret [3](#0-2) [4](#0-3) .

    # Backward compatibility

    else

    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

    secrets.github.keys
  end
