## Title
Webhook `status` events bypass repository/organization scoping, allowing a legitimately-configured org's webhook secret to forge CI status for any other organization's commits and trigger unauthorized merges/deploys — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
Shipit's multi-tenant webhook pipeline verifies a webhook's HMAC signature against the GitHub organization named in the payload, but the `status` event handler never re-checks that the commit it updates actually belongs to a stack owned by that same organization. This breaks the equality `organization that authenticated == repository/organization that is written`, letting anyone who legitimately owns a webhook secret for *their own* onboarded organization forge CI status updates for commits belonging to a *different* organization's repositories, which feed directly into the merge queue and continuous-deployment logic.

## Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the signature against using the organization derived from the payload itself: [1](#0-0) [2](#0-1) 

This is a documented, supported configuration where each onboarded GitHub organization has its own `app_id`/`webhook_secret` in `config/secrets.yml`: [3](#0-2) 

Once the signature is verified for organization "B" (via B's own webhook secret, which B's own GitHub App administrator legitimately knows), the raw JSON payload is dispatched to handlers with no further scoping enforced at the controller level: [4](#0-3) 

Most handlers correctly scope themselves to the repository named in the payload via `Handler#stacks`/`repository_name` (`payload.dig('repository', 'full_name')`), e.g. `PushHandler`: [5](#0-4) [6](#0-5) 

However, `StatusHandler` does not scope to `stacks`/`repository_name` at all — it looks up commits **globally across every stack in the Shipit instance** purely by `sha`: [7](#0-6) 

So the binding that should hold — "the organization whose secret signed this payload" equals "the organization/repository whose commit is being written" — is never enforced for `status` events. Any commit sha across any stack tracked by the Shipit instance can be targeted, regardless of which organization's secret produced the valid signature.

A forged/replayed "success" status is persisted via `Commit#create_status_from_github!` → `Status.replicate_from_github!`, and immediately affects merge/deploy decisioning: [8](#0-7) [9](#0-8) 

This status is consumed directly by the merge queue's readiness checks and by continuous deployment scheduling: [10](#0-9) [11](#0-10) [12](#0-11) 

## Impact Explanation
An attacker who legitimately administers Organization B's GitHub App in a multi-org Shipit deployment (and therefore legitimately knows B's `webhook_secret`, per the documented setup) can sign a `status` webhook payload that references an arbitrary commit sha in Organization A's tracked repositories, with `state: "success"` and a `context` matching a required status check (e.g., the value configured under `ci.require`/`merge.require` in that stack's `shipit.yml`, documented in README.md). Because `StatusHandler` performs no cross-organization scoping, this fabricated "success" status is stored against Organization A's commit, satisfies `MergeRequest#all_status_checks_passed?`/clears `any_status_checks_missing?`/`any_status_checks_failed?`, and can allow `MergeRequest#merge!` to merge a pull request, or trigger `stack.schedule_continuous_delivery`/`schedule_merges` to deploy that commit — an unauthorized merge or deploy on a repository the attacker has no legitimate access to. This matches the Critical impact category "unauthorized deploy, rollback or merge."

## Likelihood Explanation
This requires only the attacker's own legitimately-provisioned webhook secret for an organization already onboarded to the shared Shipit instance (a normal, documented multi-tenant configuration), plus a known/guessable commit sha (commit shas of tracked open-source or internal repos are frequently public/discoverable) and the target stack's required-status `context` string (often documented publicly, e.g. `continuous-integration/travis-ci/push`). No Shipit session, API token, or elevated privilege on the target organization is needed, making this practically reachable in any Shipit deployment servicing multiple organizations.

## Recommendation
Scope `StatusHandler` (and any other handler that doesn't already use `Handler#stacks`) to only update commits that belong to a stack whose repository matches `repository_name`/the organization that produced a valid signature, mirroring `PushHandler`'s use of `stacks`. Additionally, `WebhooksController#verify_signature` should assert that the organization used to validate the signature matches the organization owning every resource the event subsequently mutates, rather than trusting handlers to independently re-derive and check that binding.

## Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. As the administrator of `org-b` (who legitimately owns and knows `org-b`'s `webhook_secret`), craft a `status` event payload:
```json
{
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-b/some-repo" },
  "sha": "<sha of a commit tracked in an org-a stack>",
  "state": "success",
  "context": "continuous-integration/travis-ci/push"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-b's webhook_secret, payload)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `org-b`, validates successfully against `org-b`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the matching commit in `org-a`'s stack (no ownership check), creating a "success" `Status` for it.
6. `ProcessMergeRequestsJob`/`MergeRequest#all_status_checks_passed?` sees the required status satisfied and proceeds to `merge!` the pull request (or continuous deployment deploys the commit) on `org-a`'s repository — an unauthorized merge/deploy achieved purely with `org-b`'s own webhook credentials.

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
