### Title
Cross-organization webhook forgery — webhook signature is verified against the org named in an unverified payload field while handlers act on a different unverified field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read straight out of the still-unverified JSON body [1](#0-0) [2](#0-1) . Every event handler, however, resolves the `Repository`/`Stack` to act on using a *different* JSON field, `repository.full_name` [3](#0-2) . Nothing binds these two fields together, so an attacker who legitimately controls the GitHub App/webhook secret for one configured organization can forge a payload whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` names a repository belonging to a completely different organization also hosted on the same Shipit instance.

### Finding Description
Shipit explicitly supports hosting multiple GitHub organizations from a single installation, keyed by organization name under `secrets.github` [4](#0-3) . `Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization.

The webhook controller determines *which* organization's app/secret to verify against purely from the incoming (unauthenticated) payload:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`verify_webhook_signature` HMACs the raw body with the secret belonging to whatever organization `repository_owner` names [6](#0-5) . This only proves the sender knew *that org's* secret — it says nothing about the rest of the payload's contents.

Once verification "passes," every handler ignores `repository.owner.login` entirely and instead resolves the target repository from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` then syncs/deploys any stack under that repository [7](#0-6) , and the pull-request handlers similarly resolve `repository` from `params.repository.full_name` to create/close/label review stacks [8](#0-7) .

Because `owner.login` (the field the signature check binds to) and `full_name` (the field the write path binds to) are two independent strings inside the same JSON object, an attacker with legitimate knowledge of Organization A's webhook secret can:
1. Set `repository.owner.login = "OrgA"` so `verify_signature` picks OrgA's `GitHubApp` and the attacker's HMAC (computed with OrgA's real secret) validates.
2. Set `repository.full_name = "OrgB/some-repo"` (or any other repository registered in the same Shipit instance) so the downstream handler resolves and acts on OrgB's `Repository`/`Stack` instead.

This is precisely the analog called out by the report's bug class: two independent "modes" (here, the org used to *authenticate* the request vs. the org whose repository is *written*) that are supposed to be the same value but are never checked for equality, allowing a state that should be impossible.

### Impact Explanation
This breaks the trust boundary between organizations hosted on a shared Shipit instance (`organization that authenticated == repository that is written`, which the code never enforces). An attacker who controls the webhook secret for one onboarded organization can forge push/pull_request/status/membership events that are attributed to and acted upon a different organization's repositories/stacks — e.g. triggering `GithubSyncJob`/deploy pipelines, creating/managing review stacks, or manipulating commit statuses and team memberships for a repository they don't otherwise control. This is a cross-repository, cross-organization write achieved purely by an unprivileged party who only administers a different org's GitHub App — matching the "cross-repository writes" Critical impact bucket.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with the multi-org schema (`secrets.github` keyed by org name), which is a first-class, documented-in-code configuration path in `lib/shipit.rb`. Any party who is the administrator of one such GitHub App (or who otherwise obtains that org's `webhook_secret`) can immediately exploit this without any Shipit session, API token, or GitHub write access to the target org/repo — they only need the ability to POST an HTTP request with a valid `X-Hub-Signature` for their own org.

### Recommendation
Bind verification and action to the same value. Either:
- Derive `repository_owner` from the same field used by handlers (`repository.full_name`'s owner segment) and reject events where `owner.login` doesn't match the owner portion of `full_name`; or
- After signature verification, re-validate that the resolved `Repository` (via `full_name`) belongs to the same GitHub organization/app that successfully verified the signature, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (the supported multi-org schema in `lib/shipit.rb`).
2. As the (legitimate) owner/administrator of `OrgA`'s GitHub App, craft a `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-controlled sha already present in OrgB's tracked repo>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/target-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully using OrgA's secret [1](#0-0) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/target-repo")` via `repository_name` (`full_name`) and enqueues `GithubSyncJob`/deploy actions for OrgB's stack [3](#0-2) [7](#0-6) , even though the request was never authenticated for OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
