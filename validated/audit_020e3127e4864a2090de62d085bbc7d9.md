### Title
Repository-controlled `credential.<url>.helper` config bypasses gh's credential-helper reset in `AuthenticatedCommand`, exposing the gh git-credential token to attacker-supplied helper commands - ([File: git/client.go])

### Summary
`Client.AuthenticatedCommand` resets and re-adds a `credential.helper` entry using either an unscoped key (`AllMatchingCredentialsPattern`, used by `Fetch`/`Pull`/`Push`) or a host-scoped key (`CredentialPatternFromGitURL`, used by `Clone`). Because the "reset" `-c` flag only clears the *exact* config key it targets, a credential helper that an attacker plants under the *other* key form in a cloned repository's `.git/config` is never cleared and remains active alongside gh's helper.

### Finding Description
`AuthenticatedCommand` builds `preArgs` depending on the `CredentialPattern` passed in: [1](#0-0) 

- For `AllMatchingCredentialsPattern` (used by `Fetch`, `Pull`, `Push`, and `pkg/cmd/repo/sync/git.go`'s `Fetch`) the reset/set pair operates on the **unscoped** key `credential.helper`. [2](#0-1) [3](#0-2) 

- For `Clone`, the pattern is derived per-URL via `CredentialPatternFromGitURL`/`CredentialPatternFromHost`, and the reset/set pair instead operates on the **host-scoped** key `credential.<host-prefix>.helper` (e.g. `credential.https://github.com.helper`). [4](#0-3) [5](#0-4) 

Git's credential subsystem accumulates helpers from *all* matching config sections rather than treating "the last helper wins" as a single scalar; an empty-string helper value only clears helpers accumulated **under that same config key** up to that point, it does not clear helpers set under a differently-scoped key. Consequently:

- If a victim clones an attacker-published repository (or extracts a template/workflow artifact containing a pre-built `.git/config`) that defines a *host-scoped* section, e.g.:
  ```
  [credential "https://github.com"]
      helper = /tmp/exfil.sh
  ```
  then any subsequent `gh`-driven `Fetch`/`Pull`/`Push` on that repo uses `AllMatchingCredentialsPattern`, whose reset only clears the unscoped `credential.helper=` key. The attacker's `credential.https://github.com.helper` entry from the repo-local config is never reset and remains registered as an additional credential helper for that exact host.
- Conversely, if the repo config instead sets the unscoped form `[credential] helper = /tmp/exfil.sh`, that survives `Clone`'s host-scoped reset (though `Clone` happens before the target directory/config exists, so this direction is not reachable via `Clone` itself — it is reachable once the repo is already checked out and a later `Fetch`/`Pull`/`Push` is issued, at which point `AllMatchingCredentialsPattern`'s unscoped reset *would* actually catch it — so the concretely exploitable direction is the host-scoped section surviving the unscoped reset used by `Fetch`/`Pull`/`Push`).

Git invokes every registered helper for the `get` operation until it has both a username and password, and (more importantly) invokes every registered helper for the `store`/`erase` operations after a successful authentication, passing the resolved credentials (including gh's OAuth token used as the git password) on stdin. Because the attacker's helper is never cleared, git will also call it with `store`, handing the real GitHub token to an attacker-controlled command that runs with the victim's OS user privileges.

There is no existing mitigation for this key-scope mismatch in the codebase; `git/client_test.go`'s `TestClientAuthenticatedCommand` only verifies the two reset/set pairs in isolation and does not test interaction with pre-existing scoped config. [6](#0-5) 

### Impact Explanation
This is credential/token exfiltration: an unprivileged attacker who gets a victim to clone/extract their repository (including via workflow artifacts, template repos, or any tarball containing a crafted `.git/config`) can arrange for the victim's own `gh`-brokered GitHub token to be handed to an attacker-controlled local command during subsequent `gh repo clone`, `gh pr checkout`, `gh repo sync`, or any git operation that calls `Fetch`/`Pull`/`Push` on that repository. This matches the "credential/token exfiltration" bounty impact class.

### Likelihood Explanation
Requires the victim to check out a repository (or extract an artifact) containing an attacker-crafted `.git/config` and to subsequently run an authenticated `gh` git operation (`gh pr checkout`, `gh repo sync`, `git fetch`/`pull`/`push` triggered by gh) against that same repo. `.git` directories are not part of normal repo checkouts via `git clone`, but they are trivially included in tarball/zip artifacts, git bundles, or template-generation flows that a victim might extract directly rather than via `git clone` (e.g., downloading a release asset or workflow artifact as a zip and unzipping it into a working directory that already contains a `.git/config`). This is a plausible, low-effort attack the attacker fully controls (they choose the exact config key form), but does depend on victim workflow specifics rather than a normal `gh repo clone` of an untrusted git remote.

### Recommendation
Make the credential-helper reset comprehensive regardless of the pattern used: always issue `-c credential.helper=` (unscoped reset) in addition to the pattern-scoped reset before adding gh's helper, so that both `credential.helper` and `credential.<pattern>.helper` inherited/local entries are cleared. Alternatively, refuse to trust `.git/config`-provided credential helper sections entirely by invoking git with `-c include.path=` disabled or by using `GIT_CONFIG_NOSYSTEM`/isolated config equivalents, or by using `git -c protocol.credential.helper=` /  running through a mechanism that ignores repository-local `credential.*` sections for gh-authenticated invocations.

### Proof of Concept
Go unit test extending `TestClientAuthenticatedCommand` / `git/client_test.go` to assert full clearing:
```go
func TestClientAuthenticatedCommand_ClearsBothScopes(t *testing.T) {
    client := Client{GhPath: "gh", GitPath: "path/to/git"}
    cmd, err := client.AuthenticatedCommand(context.Background(), AllMatchingCredentialsPattern, "fetch")
    require.NoError(t, err)
    // Expect BOTH the unscoped and a defensive scoped reset to be present so that
    // a repo-local [credential "https://github.com"] helper cannot survive.
    joined := strings.Join(cmd.Args, " ")
    require.Contains(t, joined, "-c credential.helper=")
    // Currently FAILS: no reset targets credential.<host>.helper when
    // AllMatchingCredentialsPattern is used, so an attacker-planted
    // `[credential "https://github.com"] helper = ...` in .git/config
    // is never cleared.
}
```
Integration-level PoC (git-stub scenario):
1. Create a working repo with `.git/config` containing:
   ```
   [credential "https://github.com"]
       helper = "!echo captured=$(cat) >> /tmp/exfil.log; true"
   ```
2. Run `gh`'s `Fetch` (or `pr checkout`/`repo sync`) against a `https://github.com/...` remote.
3. Observe `/tmp/exfil.log` receiving the `store` payload (including the OAuth token) alongside gh's own helper being invoked — demonstrating the attacker helper was not cleared by the `-c credential.helper=` reset.

// CredentialPatternFromGitURL takes a git remote URL e.g. "https://github.com/cli/cli.git" or
// "git@github.com:cli/cli.git" and returns the credential pattern that should be used for it.
func CredentialPatternFromGitURL(gitURL string) (CredentialPattern, error) {
	normalizedURL, err := ParseURL(gitURL)
	if err != nil {
		return CredentialPattern{}, fmt.Errorf("failed to parse remote URL: %w", err)
	}
	return CredentialPatternFromHost(normalizedURL.Host), nil
}

// CredentialPatternFromHost expects host to be in the form "github.com" and returns
// the credential pattern that should be used for it.
// It does not perform any canonicalisation e.g. "api.github.com" will not work as expected.
func CredentialPatternFromHost(host string) CredentialPattern {
	return CredentialPattern{
		pattern: strings.TrimSuffix(ghinstance.HostPrefix(host), "/"),
	}
}
