### Title
Clickjacking on `Shipit::MergeStatusController#show` via unconditional `X-Frame-Options: ALLOWALL` combined with operator-enabled `SameSite=None` cookies allows UI-redress-driven unauthorized merge-queue actions - (File: `app/controllers/shipit/merge_status_controller.rb`)

### Summary
`MergeStatusController#show` unconditionally sets `response.headers['X-Frame-Options'] = 'ALLOWALL'`, and — only when the operator has opted in via `Shipit.enable_samesite_middleware?` (`SHIPIT_ENABLE_SAMESITE_NONE`) — `SameSiteCookieMiddleware` rewrites the session cookie to `SameSite=None; Secure`. Under that combination, an authenticated victim's session and the real merge-queue UI (including a valid, page-rendered CSRF token) can be rendered inside an attacker-controlled iframe, letting the attacker perform classic UI-redress ("clickjacking") to trick the victim into submitting the "Add to merge queue" form for a PR/stack chosen by the attacker.

### Finding Description
Binding claimed broken: `response.headers['X-Frame-Options'] == 'ALLOWALL'` AND cookie `SameSite == 'None'` ⇒ an attacker-controlled origin can render the victim's authenticated merge-status UI in a frame and induce a genuine, correctly-authenticated state change.

Trace:
- `show` sets the header unconditionally, with no origin allow-list: [1](#0-0) 
- `skip_authentication only: %i[check show]` lets `show` render for anyone, but it internally checks `current_user.logged_in?` and falls back to a "logged_out" partial when no valid session is present: [2](#0-1) 
- When the victim's browser attaches the session cookie (i.e. only when `SameSite=None` is forced), `current_user.logged_in?` is true inside the frame and the real "Add to merge queue" / "Remove from merge queue" forms are rendered, each carrying a legitimate, server-generated CSRF token via `form_tag`: [3](#0-2) 
- `SameSiteCookieMiddleware#call` force-appends `SameSite=None` (and `Secure`) to every `Set-Cookie` over TLS, unconditionally rewriting Rails' default (`Lax`) cookie policy: [4](#0-3) 
- This middleware is only active when the operator sets `SHIPIT_ENABLE_SAMESITE_NONE`: [5](#0-4) 
- The state-changing endpoints are `enqueue`/`dequeue`, which write to `MergeRequest` state using `current_user` from the (attacker-carried) session: [6](#0-5) 

Why existing guards don't stop this specific class of attack: `protect_from_forgery with: :exception` is active on `ShipitController` (and inherited by `MergeStatusController`): [7](#0-6) . This guard defends against *forged* cross-origin requests lacking a valid token, but it does **not** defend against clickjacking, because the attacker is not forging the request — the victim's browser is submitting a genuinely server-rendered form (with a correct, session-matched authenticity token) from within the framed same-origin document. UI-redress techniques (e.g., a transparent overlay button positioned over the real "Add to merge queue" button) can trick the victim into completing that legitimate submission. `X-Frame-Options` is the control that is supposed to prevent this class of attack, and it is explicitly disabled here (`ALLOWALL`), with no origin restriction, in contrast to a `Content-Security-Policy: frame-ancestors <trusted-origin>` allow-list.

Attacker request/flow: attacker hosts `attacker.example.com` with an iframe pointed at `https://shipit.example.com/merge_status?referrer=https://github.com/OWNER/REPO/pull/N&branch=master`, overlaid with decoy UI to bait a click on the real "Add to merge queue" button rendered inside the frame.

### Impact Explanation
If successful, the victim's own session performs `MergeRequest.request_merge!` on a stack/PR chosen by the attacker, which can lead to an unauthorized merge being queued and eventually executed under the victim's identity — this maps to the "unauthorized deploy, rollback or merge" Critical category, but is conditioned entirely on the victim being an already-authorized/team member for that specific repository (i.e., no privilege escalation into `Shipit.github_teams` occurs; the attacker rides an existing, legitimate authorization). The attack is repeatable per victim/session but requires (a) `SHIPIT_ENABLE_SAMESITE_NONE` to be set by the operator, and (b) successfully deceiving the victim into a real click inside the frame — it is a UI-redress technique, not a fully automated one-shot exploit.

### Likelihood Explanation
Requires the operator to have explicitly opted into `SHIPIT_ENABLE_SAMESITE_NONE` (non-default) — this flag exists specifically to support the official browser-extension embedding workflow shown in `contrib/browser-extension/src/inject.js`, where the extension deliberately loads the merge-status widget cross-origin over GitHub PR pages inside a sandboxed iframe (`sandbox = 'allow-scripts allow-forms allow-same-origin allow-popups ...'`). Absent that opt-in, `show` remains framable (`ALLOWALL` is unconditional) but the session cookie is not sent cross-site by default (`Lax`), so the frame renders the "logged_out" state and the attack fails. Given the opt-in precondition, the remaining requirements are only social-engineering cost (baiting a click) and no secrets/privileges — this is a low-cost, code-reachable path once the precondition holds, but the precondition itself is an explicit, narrow operator configuration choice tied to a documented, intended cross-origin embedding feature.

### Recommendation
Scope the frame-embedding allowance instead of a blanket `ALLOWALL`: replace `X-Frame-Options: ALLOWALL` with a `Content-Security-Policy: frame-ancestors 'self' https://github.com` (or an explicit configurable allow-list matching only the origins that need to embed the widget, e.g., github.com for the browser extension), and avoid disabling `X-Frame-Options` for arbitrary origins even when `SameSite=None` is enabled for legitimate cross-origin cookie delivery.

### Proof of Concept
Minitest plan (`test/controllers/merge_status_controller_test.rb` style, using `ActionController::TestCase`):
```ruby
test "show sets ALLOWALL with no origin restriction" do
  get :show, params: { referrer: 'https://github.com/Shopify/shipit-engine/pull/42', branch: 'master' }
  assert_equal 'ALLOWALL', response.headers['X-Frame-Options']
end

test "SameSiteCookieMiddleware forces SameSite=None when enabled" do
  Shipit.stubs(:enable_samesite_middleware?).returns(true)
  # simulate app returning a Set-Cookie without SameSite, over TLS
  app = ->(env) { [200, { 'Set-Cookie' => '_session=abc; Secure' }, []] }
  middleware = Shipit::SameSiteCookieMiddleware.new(app)
  env = Rack::MockRequest.env_for('https://shipit.example.com/merge_status', 'HTTPS' => 'on')
  _, headers, _ = middleware.call(env)
  assert_match(/SameSite=None/i, headers['Set-Cookie'])
end
```
This confirms both halves of the claimed binding are true in code as written; the residual condition (`Shipit.enable_samesite_middleware?` must be operator-enabled) is the only gating factor for exploitability.

    def call(env)
      status, headers, body = @app.call(env)

      if headers && headers['Set-Cookie'] &&
         Rack::Request.new(env).ssl?

        set_cookies = headers['Set-Cookie'].split(COOKIE_SEPARATOR).compact
        set_cookies.map! do |cookie|
          cookie << '; Secure' if cookie !~ /;\s*secure/i
          cookie << '; SameSite=None' unless cookie.match?(/;\s*samesite=/i)
          cookie
        end

        headers['Set-Cookie'] = set_cookies.join(COOKIE_SEPARATOR)
      end

      [status, headers, body]
    end
