### Title
Unscoped `StatusHandler#process` lets a webhook authenticated for one repository mutate commit status of another repository's stack via shared SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with `Commit.where(sha: params.sha)`, ignoring the repository that the `status` webhook was actually verified for. An attacker who forks a victim's repository shares identical commit SHAs (git objects are content-addressed), and can trigger a genuinely-signed `status` webhook from their own fork/org that GitHub delivers with `context: deploy/production`. That legitimately-signed payload is then applied to the victim stack's commit because the handler never checks `repository.full_name`.

### Finding Description
The broken binding that must hold is: `status.commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — i.e. any `Shipit::Status` record created from a webhook must belong to the same repository that authenticated (signed) that webhook.

Trace:
1. `Shipit::WebhooksController#verify_signature` validates `X-Hub-Signature` using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the *attacker's own payload* (`params.dig('repository', 'owner', 'login')`) [1](#0-0) [2](#0-1) . This only proves the request came from GitHub for the attacker's own org/repo — it says nothing about which stack the SHA belongs to.
2. The generic `Handler` base class does correctly scope by repository via `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`) [3](#0-2) , but `StatusHandler#process` does not use this helper at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
`Commit.where(sha: ...)` matches by bare SHA across **all** stacks/repositories, with no `stack_id`/`repository` filter.
3. `create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` writes a `Status` row scoped to the *victim* commit's `stack_id`, using attacker-supplied `state`/`context`/`description` [5](#0-4) [6](#0-5) .
4. `Status#after_commit :schedule_continuous_delivery` calls `commit.schedule_continuous_delivery`, which re-evaluates `deployable?` and, if `stack.continuous_deployment?` and `stack.deployable?`, enqueues `ContinuousDeliveryJob` [7](#0-6) ; `deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` and `blocked?` inspects `stack.blocking_statuses` [8](#0-7) . A forged `failure` status on the required `deploy/production` context flips the commit's aggregate status (`Status::Group`), making it `blocked?`/non-deployable, which prevents the victim's `ContinuousDeliveryJob` from shipping (or, with a forged `success`, could make an otherwise-pending commit `deployable?` and trigger an unwanted ship).

Exploit flow: attacker forks victim's public GitHub repository (or otherwise obtains/has a repository sharing a git commit, e.g. via cherry-pick/rebase preserving the same tree+parents+timestamps), so a commit exists with an identical SHA in both the attacker's repo and the victim's Shipit-tracked stack. Attacker sets a commit status (`context: deploy/production`, `state: failure`) on that SHA in their own repository via the GitHub API (something any repo owner can legitimately do). GitHub signs and delivers the `status` webhook for the attacker's own repository; `verify_signature` passes because it is verifying the app installed for the attacker's own org, and it's a real GitHub-signed request. `StatusHandler#process` then finds the commit by SHA in the victim's stack (unscoped) and writes/updates a `Status` for the victim's `stack_id`, flipping the victim commit's required-context result and driving the victim's continuous-deployment ship/block decision.

No existing guard catches this: `verify_signature` authenticates the *sender's* repository, not the *target* of the mutation; `drop_unhandled_event` only filters event types; there is no `ExplicitParameters` check tying `params.sha` to `repository_name`; model validations on `Status`/`Commit` don't check cross-repository ownership.

### Impact Explanation
An attacker who controls (or forks) any repository can write a `Shipit::Status` record for a completely different tenant's stack/commit — this is exactly the "payload for one repository mutating another's stack, commit" Critical category. Concretely: forging a `failure` on a stack's `required_statuses` context blocks/prevents `ContinuousDeliveryJob` from shipping a legitimate green commit (denial of a deploy), and forging a `success` can make a commit `deployable?` prematurely and trigger `ContinuousDeliveryJob` to ship it before real CI passed. The blast radius is any Shipit installation with multiple stacks/repos sharing common ancestor commits (forks, mirrors, monorepo splits), and is repeatable per SHA/target stack.

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository they control that is registered with/reachable by the same Shipit-configured GitHub App/org verification path used by `verify_signature`, and (b) a commit SHA that is shared with a target victim stack (trivially achievable by forking a public repo and setting a status on an existing, unmodified commit — git SHAs are content-addressed and identical across forks/clones for unmodified commits). No Shipit credentials, session, or API token are required — only the ability to set a commit status via the normal GitHub API on their own repo, which is a standard, unprivileged GitHub capability for any repo owner. This is easily repeatable against any stack whose tracked repository has public forks.

### Recommendation
Scope `StatusHandler#process` (and any other bare-SHA lookups reachable from webhooks) to the repository that authenticated the webhook, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or explicitly filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the `Handler#stacks` repository-scoping helper already used elsewhere.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook is scoped to the repository that authenticated it" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment enabled, requires 'deploy/production'
  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared commit")

  # Binding under test (before): victim_commit.stack.repository.full_name != attacker_repo.full_name
  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'deploy/production',
    'repository' => { 'full_name' => 'attacker/fork', 'owner' => { 'login' => 'attacker' } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    # Simulate: verify_signature passed for attacker/fork (legit GitHub delivery),
    # but StatusHandler must not write into victim_stack's commit.
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  victim_commit.reload
  assert_not_equal 'failure', victim_commit.status.state,
    "victim stack's commit status must not be mutated by a webhook authenticated for a different repository"
end
```
This demonstrates that, prior to a fix, `StatusHandler.call` with an attacker-controlled payload authenticated only for `attacker/fork` still creates/updates a `Shipit::Status` under `victim_stack`'s commit purely because `params.sha` matches, violating the repository-scoping invariant.
