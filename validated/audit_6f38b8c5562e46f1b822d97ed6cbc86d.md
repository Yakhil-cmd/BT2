## Analysis

This is a valid analog. The Obyte AA ecosystem has the same structural weakness as the reported `recoverERC20()` issue: many Autonomous Agents pay out custom assets to a single hard-coded destination — `trigger.address` (the address of whoever sent the request) — with no way for the caller to specify an alternate beneficiary. If the asset being paid out has a `transfer_condition` (Obyte's on-chain equivalent of an ERC20 blacklist/allowlist, defined by the asset issuer), and the withdrawing address is later excluded by that condition, every attempt by the AA to pay funds back to that same address will keep failing, permanently freezing the user's balance recorded inside the AA with no code path to redirect the funds elsewhere.

### Title
Withdrawals from Autonomous Agents can be permanently frozen when the recipient address is excluded by an asset's `transfer_condition` - (File: `aa_composer.js`, `validation.js`)

### Summary
Obyte assets can define a `transfer_condition`/`issue_condition` that an issuer can use to restrict who may receive the asset, functioning like an ERC20 blacklist. Autonomous Agents that pay out such assets to users (banks, exchanges, ICOs, order books, etc.) hard-code the destination as `trigger.address` — the address that triggered the payment — and provide no parameter to redirect the payout to a different address. If that address becomes excluded from the transfer condition after the user's balance has already accrued inside the AA, the AA's payment message will always fail validation and bounce, and since AA logic offers no alternate-recipient mechanism, the funds are permanently locked in the AA.

### Finding Description
Asset transfer conditions are enforced in `validatePaymentInputsAndOutputs` when an asset payment message is validated: the issuer-defined `transfer_condition` is evaluated against the payment's addresses, and if it fails, the whole payment message is rejected with `"transfer or issue condition not satisfied"`. [1](#0-0) 

Similarly, an asset can require `spender_attested`, restricting valid recipients to an attestor-approved list — functionally the same denylist/allowlist mechanic. [2](#0-1) 

When an AA composes its response unit and this payment validation fails, `aa_composer.js`'s `sendUnit()` calls `validateAndSaveUnit`, and on any error it calls `bounce(err)`, discarding the state update and any response payment. [3](#0-2) 

`bounce()` only refunds whatever assets were sent together with the *current* trigger back to `trigger.address` — it has no knowledge of, and does not touch, the AA's internal balance/state-variable accounting for that user (e.g., previously deposited funds tracked via `var[...]`). [4](#0-3) 

Numerous representative AA patterns pay out user balances strictly to `trigger.address`, with no alternate "beneficiary" parameter, mirroring the `recipient()`-hardcoded pattern in the reported `VestingEscrow.recoverERC20()`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the withdrawal condition (`trigger.address == ...` and the `if` guard) is unconditionally tied to the same `trigger.address` used as the payment output, once that specific address is excluded by the asset's `transfer_condition` (or drops off the `spender_attested` list), every subsequent withdrawal attempt from that address fails the same way, and the AA offers no way to have the funds sent to a different, non-excluded address.

### Impact Explanation
This is an AA fund-freezing issue: a user's asset balance/entitlement recorded in AA state variables becomes permanently unrecoverable once their withdrawal address is excluded by the asset's `transfer_condition`, because the AA logic (as in the standard patterns shipped and widely reused in the Obyte ecosystem) has no mechanism to redirect payouts to another address. This matches the reported severity (Medium): loss/freezing of funds is possible, but requires the somewhat unlikely precondition that the asset issuer denylists the specific withdrawing address after the balance accrued.

### Likelihood Explanation
Likelihood is low-to-medium: it requires an asset with a restrictive `transfer_condition` or `spender_attested` requirement, and a scenario where a given address is later excluded after already accumulating a balance inside the AA (e.g., due to a compliance-driven denylist update by the issuer). This is directly analogous to the "recipient/owner gets blacklisted" precondition in the original report.

### Recommendation
AA authors should not hard-code the payout destination to `trigger.address` only. Where feasible, expose a way for the caller to (a) specify an alternate `trigger.data.address` recipient for withdrawals validated against the caller's authorization, or (b) support a rescue/redirect path so that if a payout fails validation (e.g., due to transfer condition), the recorded balance is not lost and can later be claimed to a different, permitted address. This is a design guidance for AA authors rather than a core protocol bug, since ocore's validation logic (`transfer_condition`, `spender_attested`) is working as intended — the risk lies in how AA scripts consume `trigger.address` as an immutable payout target.

### Proof of Concept
1. Asset issuer creates a divisible, transferrable asset with a `transfer_condition` such as `["not", ["address", "BLACKLISTED_ADDR"]]` (rejecting outputs to a specific address), per `validateAssetDefinition`/`Definition.validateDefinition` handling of `transfer_condition`. [8](#0-7) 
2. A user deposits this asset into a bank/exchange-style AA (e.g., modeled on `test/samples/a_bank_without_percent.oscript`), and the AA credits `var['balance_<address>_<asset>']`. [9](#0-8) 
3. The issuer later updates the condition (or the condition references a data feed) such that the user's address becomes "BLACKLISTED_ADDR".
4. The user sends a withdrawal trigger; the AA composes a payment message with `outputs: [{address: trigger.address, amount: ...}]`. [10](#0-9) 
5. `validatePaymentInputsAndOutputs` evaluates the `transfer_condition` against the output address and rejects the unit. [1](#0-0) 
6. `aa_composer.js` bounces the trigger, the state update (balance decrement) is rolled back, but the AA has no way to pay the balance to a different address — the funds remain permanently stuck, exactly as in the original ERC20 `recoverERC20()`/blacklist scenario. [3](#0-2)
