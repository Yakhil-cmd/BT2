This confirms the analog: the multi-org config (`docs/setup.md:182-209`) allows distinct `webhook_secret` values per organization, keyed by `Shipit.github(organization:)` [1](#0-0) . `WebhooksController#verify_signature` selects which secret to check the HMAC against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` from the *unverified* JSON body itself [2](#0-1) . But every downstream `Handler` resolves the target `Stack`/`Repository`/`Team` using a *different* field of that same payload — `repository.full_name` (`Handler#repository_name`) or `organization.login` in `MembershipHandler#find_or_create_team!` — with no check that it matches the org whose secret validated the signature. ### Title
Webhook signature is verified against one org field while handlers act on a different, unverified org/repo field, enabling cross-tenant forgery in multi-GitHub-App deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
When Shipit is configured with multiple GitHub Apps (one per organization, per `docs/setup.md`'s "Using Multiple Github Applications" section), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` picks which secret to validate the request signature with based on `repository_owner`, computed from the raw (attacker-controlled at the JSON level, though normally populated by GitHub) `repository.owner.login`/`organization.login` field of the payload. Every event handler, however, resolves the actual `Stack`, `Repository`, or `Team` to mutate using a different field — `repository.full_name` (used across `PushHandler`, all `PullRequest::*Handler`s) or `organization.login` (`MembershipHandler`). Nothing enforces that these two fields refer to the same organization.

### Finding Description
`Shipit.github(organization:)` maintains one `GitHubApp` (and one `webhook_secret`) per configured organization [1](#0-0) . The controller selects which app/secret to verify against purely from `repository_owner`:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`verify_signature` then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` over the full raw body [6](#0-5) . Because the HMAC covers the whole payload, this step only proves "whoever holds Org A's `webhook_secret` produced this exact byte string" — it does not prove that the *content the handlers will act on* is scoped to Org A.

Every handler's stack lookup is driven by a separate field:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

and `MembershipHandler` derives/updates `Team#organization` straight from `params.organization.login` [4](#0-3) .

An administrator of a low-trust GitHub organization that is itself onboarded onto the same shared Shipit instance (a legitimate, intended multi-tenant setup per `docs/setup.md`) knows their own org's `webhook_secret` (they configured the GitHub App and can rotate/read that secret from their own App settings, or simply replay/derive it since they control that App). They can therefore craft an arbitrary JSON body, set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` selects and matches their own secret, while setting `repository.full_name` to `victim-org/victim-repo` (a stack tracked for a different, more trusted organization on the same Shipit instance) or `organization.login`/`team` fields referencing a `Shipit.github_teams` team used for authorization. The equality the system should enforce — "the org whose secret verified this request" == "the org/repo the handler is about to mutate" — is never checked.

### Impact Explanation
This breaks the authorization boundary between tenants of a single Shipit instance configured with multiple GitHub Apps: an attacker who only controls one (possibly low-privilege) organization's webhook secret can forge events that are attributed to and acted on for a different organization's stacks or teams. Concretely:
- Via `PushHandler`/`PullRequest::*Handler`, they can force `sync_github`/archive/unarchive/label-capture actions against another org's `Stack`, corrupting deploy state (`app/models/shipit/webhooks/handlers/push_handler.rb`, `.../pull_request/*_handler.rb`).
- Via `MembershipHandler`, they can add or remove members of a `Team` object whose `organization` was seeded from the attacker-controlled field, and `Shipit.github_teams` membership is exactly what `Authentication#force_github_authentication`/`User#authorized?` uses to gate access to the whole app [7](#0-6) [8](#0-7) . Forging `added` membership events for a victim org's authorization team lets an attacker escalate an arbitrary `User` record into `Shipit.github_teams` authorization — a High-severity escalation into `github_teams` authorization as scoped in this engagement.

### Likelihood Explanation
Requires only that the deployment uses the documented multi-organization GitHub App configuration and that the attacker administers (or has push access sufficient to configure a webhook secret for) at least one onboarded, lower-trust organization — no Shipit session, `ApiClient` token, or `webhook_secret` of the *victim* org is needed. This is a realistic configuration explicitly documented in `docs/setup.md`.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive `repository_owner`/`organization.login` from the payload and enforce that every handler's repository/organization resolution (`Handler#repository_name`, `MembershipHandler#find_or_create_team!`) is scoped to that same, already-authenticated organization — reject (422) if `repository.full_name`'s owner segment or `organization.login` disagrees with the org used to verify the signature.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `trusted-org` (tracks a sensitive `Stack`/`Team` used for `Shipit.github_teams` authorization) and `attacker-org` (attacker is admin, knows its `webhook_secret`).
2. Attacker crafts a `membership` event body: `{"action":"added","team":{...victim team id...},"organization":{"login":"attacker-org"},"member":{"login":"attacker-controlled-user"}}`, computes `X-Hub-Signature` with `attacker-org`'s `webhook_secret`.
3. POST to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature matches, so the request passes.
4. `MembershipHandler#process` adds `attacker-controlled-user` to the `Team` matched by `params.team.id` (the victim's authorization team), regardless of which org's secret verified the request, because team membership is `find_or_create_by!(github_id: params.team.id)` with no cross-check against the verified org.
