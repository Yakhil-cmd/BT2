### Title
Webhook Organization Used For Signature Selection Is Never Bound To The Repository The Handlers Act On - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a delivery against using an organization name read straight out of the *unverified* JSON body, then hands that same unverified body to the event handlers, which independently pick the target repository/stack from other fields of that same body. Nothing enforces that the organization whose secret validated the signature is the organization that owns the repository the handlers subsequently write to. This is analogous to the audit finding: a control (the cooldown / here, the signature check) is bound to the wrong scope (an account / here, an attacker-chosen organization field) instead of the actual asset being acted upon (the whole kHYPE balance / here, an unrelated repository).

### Finding Description
`verify_signature` picks the GitHub App config with: [1](#0-0) 
using `repository_owner`, computed as: [2](#0-1) 
i.e. `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback), taken directly from the attacker-suppliable JSON payload, *before* the HMAC signature over that payload has been confirmed valid for that organization's secret. `Shipit.github(organization:)` looks up the per-organization `webhook_secret` (multi-org support is a documented, in-scope feature — see `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit/github_app.rb#verify_webhook_signature`) and `verify_webhook_signature` only HMACs the raw body against that one secret: [3](#0-2) 

Once the signature matches (using the secret for the organization named in `repository.owner.login`), `create` re-parses the *same* raw body and dispatches it to handlers unmodified: [4](#0-3) 

The handlers (e.g. `Shipit::Webhooks::Handlers::PushHandler`, `StatusHandler`, pull-request handlers) locate the `Repository`/`Stack` to act on using other fields of the same JSON body (repository full name, sha, etc.) rather than re-deriving it from `repository_owner`. Because JSON is attacker-authored (only the raw bytes must match the HMAC of a secret the attacker legitimately knows for their own organization), nothing prevents a payload where `repository.owner.login` (used for secret selection) names one organization while `repository.full_name`/other repository-identifying fields used by the handler name a completely different organization's repository. The binding "organization whose secret authenticated this request" == "repository the handler subsequently writes to" is never checked.

### Impact Explanation
Any party who legitimately administers (or has the webhook secret for) one GitHub organization/App connected to this shared Shipit instance can forge a webhook body that passes signature verification under their own organization's secret, while pointing the embedded repository fields at a completely unrelated, victim organization's tracked stack. Depending on the event type this can:
- Trigger `GithubSyncJob`/`RefreshCheckRunsJob` for a victim stack via forged `push`/`check_suite` events, or
- Inject fabricated CI `status` records for a victim commit via the `status` handler, undermining `ci.require` gating and enabling an unauthorized deploy of an unreviewed commit,
- Create/attach arbitrary `Shipit::User`/`Team`/`PullRequest` records associated with a victim repository via `membership`/`pull_request` handlers.

This crosses the organization/repository trust boundary that the per-org webhook secret is meant to enforce — a cross-repository/cross-organization write and a path to an unauthorized deploy, matching the Critical/High impact classes in scope (cross-repository writes, unauthorized deploy).

### Likelihood Explanation
Exploitability requires only that the attacker control (or know the webhook secret of) *any* organization onboarded to the shared Shipit instance — not the victim organization, not a Shipit session, ApiClient token, or GitHub App private key for the victim. In a multi-tenant Shipit deployment (the documented multi-org configuration) this is a realistic "unprivileged relative to the victim" attacker. The forgery only requires crafting a JSON body with internally inconsistent `repository.owner.login` vs. other repository-identifying fields and computing one HMAC — no cryptographic weakness needs to be broken.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive and pin the effective organization strictly from the same field(s) the handlers use to resolve the target `Repository`/`Stack`, and reject the request if that repository's owner does not match the organization whose secret validated the signature. Equivalently, look up the `Repository`/`Stack` first, resolve its Stack-installation organization from stored data (not from the untrusted payload), and use that to select/verify the webhook secret, ensuring a single, trusted source of truth for "which organization's key must sign this delivery."

### Proof of Concept
1. Shipit instance is configured with multiple GitHub Apps (`OrgB` and victim `OrgA`), each with its own `webhook_secret`, per the documented multi-org setup.
2. Attacker controls/administers `OrgB` and therefore legitimately possesses `OrgB`'s `webhook_secret`.
3. Attacker crafts a `push` (or `status`) webhook JSON body where `repository.owner.login = "OrgB"` (so `repository_owner` resolves to `OrgB`) but `repository.full_name` (and any other repository-identifying fields consumed by `PushHandler`/`StatusHandler`) reference `OrgA/victim-repo`.
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgB_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push` (or `status`).
5. `verify_signature` calls `Shipit.github(organization: "OrgB").verify_webhook_signature(sig, raw_body)`, which succeeds because the attacker signed with `OrgB`'s real secret.
6. `create` dispatches the same body to `PushHandler`/`StatusHandler`, which resolve and act on `OrgA/victim-repo`'s `Stack`, enqueuing sync jobs or writing forged commit statuses for a repository the attacker does not control and whose organization never authenticated this request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
