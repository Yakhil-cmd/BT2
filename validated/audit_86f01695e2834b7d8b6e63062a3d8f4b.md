### Title
Cross-organization webhook signature confusion allows one org's secret to authorize writes to another org's Stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using `repository_owner`, which is read from `params.dig('repository','owner','login')`, while `PushHandler` (via `Handler#repository_name`) resolves the target `Repository`/`Stack` using a completely independent field, `payload.dig('repository','full_name')`. Since these two fields are never checked for consistency, an attacker who owns `attacker-org` and knows its real `webhook_secret` can forge a payload where `repository.owner.login` is `attacker-org` (so the signature check passes using `attacker-org`'s secret) but `repository.full_name` is `victim-org/victim-repo` (so the handler acts on victim's stack).

### Finding Description
The broken binding is: the organization whose secret verified the request bytes must equal the organization owning the repository the handler mutates, i.e. `repository_owner (used in verify_signature) == full_name.split('/').first (used in repository_name)`. This does not hold.

- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)` to obtain a `GitHubApp` instance, then calls `github_app.verify_webhook_signature(header, request.raw_post)`, which HMAC-verifies the raw bytes using that organization's configured `webhook_secret` (lib/shipit/github_app.rb:76-83).
- Once verification passes, `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) re-parses the same raw body and dispatches it to handlers for the event, e.g. `PushHandler.call(params)`.
- `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) resolves target stacks through `stacks`, which is defined in `Handler#stacks`/`Handler#repository_name` (app/models/shipit/webhooks/handlers/handler.rb:32-38) as `Repository.from_github_repo_name(payload.dig('repository','full_name'))`.
- Nothing in the controller or handler checks that `repository.owner.login` (used to pick the verifying secret) is consistent with the owner encoded in `repository.full_name` (used to pick the target stack). An attacker who owns a repo/org and therefore knows its real `webhook_secret` can set `owner.login` to their own org (so signature verification succeeds against their own secret) while setting `full_name` to `victim-org/victim-repo` (so the handler mutates the victim's stack).

Exploit request: POST `/webhooks` with header `X-Github-Event: push` and body
```json
{"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/master","after":"<sha>"}
```
signed with `X-Hub-Signature: sha1=<hmac_sha1(attacker-org_webhook_secret, raw_body)>`. `verify_signature` looks up `attacker-org`'s `GitHubApp`, verifies successfully (the attacker legitimately controls that secret), and `create` proceeds to call `PushHandler.call(params)`, which finds `victim-org/victim-repo`'s stacks on branch `master` and calls `stack.sync_github(expected_head_sha: params.after)` — a real GitHub sync triggered on a stack the attacker never authenticated against.

None of the existing guards prevent this: `drop_unhandled_event` only checks the event type exists a handler; `ExplicitParameters` (`PushHandler`'s `params do requires :ref; requires :after end`) only validates the shape of `ref`/`after`, not repository ownership; `force_github_authentication`/`User#authorized?`/`require_permission!` are unrelated (this is the unauthenticated webhook path, not the session/API-token path); no model validation on `Repository`/`Stack` re-derives or checks the owner against the verifying organization.

### Impact Explanation
A payload that is only cryptographically authenticated for `attacker-org` causes a real, unauthenticated (from victim's perspective) mutation on `victim-org`'s `Stack` — a GitHub sync via `stack.sync_github(expected_head_sha:)`. This is a cross-tenant write: any organization with a Shipit-configured `webhook_secret` (even a low-trust or newly onboarded org) can trigger syncs against any other organization's stacks whose repo name it can guess (`owner/repo` is generally public knowledge on GitHub). This matches the Critical category: "a payload for one repository mutating another's stack." The blast radius spans every tenant/org configured in this Shipit instance, and the attack is trivially repeatable (attacker just needs a valid HMAC over their own chosen body).

### Likelihood Explanation
Preconditions: attacker owns/administers an org that has any `webhook_secret` configured in `Shipit.github(organization:)` (a very low bar — this is the default onboarding requirement for using Shipit with any org at all, and the attacker's own org's secret is by design known to the attacker/its admins). Attacker needs to know victim's `owner/repo` full name, which is public. Attacker cost is minimal: compute one HMAC-SHA1 over a crafted JSON body and POST it. Fully repeatable against arbitrary victim stacks/branches as long as `full_name` resolves to an existing `Repository` with matching `branch`.

### Recommendation
Bind the signature-verification organization to the same organization the handler will act on: e.g. in `WebhooksController#verify_signature`, or in `Handler#repository_name`, require that `payload.dig('repository','owner','login')` equals the first path segment of `payload.dig('repository','full_name')`, and reject the webhook (422) if they diverge. Alternatively, derive `repository_owner` from `full_name` directly instead of from the separate `owner.login` field, so there is a single source of truth used consistently for both verification and dispatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push webhook signed by attacker-org cannot sync victim-org's stack via mismatched full_name" do
  attacker_org_secret = 'attacker-secret'
  Shipit.github_apps['attacker-org'] = Shipit::GitHubApp.new('attacker-org', webhook_secret: attacker_org_secret)

  victim_stack = shipit_stacks(:shipit) # owned by victim-org/victim-repo, branch: master
  original_sha = victim_stack.sha

  body = {
    repository: { owner: { login: 'attacker-org' }, full_name: 'victim-org/victim-repo' },
    ref: 'refs/heads/master',
    after: 'deadbeef' * 5
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_org_secret, body)

  post '/webhooks', params: body, headers: {
    'X-Github-Event' => 'push',
    'X-Hub-Signature' => signature,
    'Content-Type' => 'application/json'
  }

  assert_response :ok # verify_signature passes using attacker-org's secret
  victim_stack.reload
  assert_equal original_sha, victim_stack.sha,
    "victim-org's stack must not be mutated by a signature verified against attacker-org's secret"
end
```
Both sides of the binding to assert: `repository_owner` used in `verify_signature` (`'attacker-org'`) vs. the owner implied by `repository_name` used in `PushHandler#process` (`'victim-org'`) — the test demonstrates these diverge and the fix should make them equal (or reject the request) before any `sync_github` call occurs.
