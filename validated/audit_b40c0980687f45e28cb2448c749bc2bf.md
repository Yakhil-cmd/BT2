Confirmed: `Stack.from_param!` performs a global, unscoped lookup across `Stack.all` — no `stack_id` restriction is applied. [1](#0-0) 

### Title
Scoped API token can read the build status of any stack via CCMenu, bypassing token stack scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` authenticates an `ApiClient` and enforces a `read:stack` permission check, but resolves the target `stack` with a private `stack` method that queries `Stack.from_param!(params[:stack_id])` directly, instead of using the inherited, scope-aware `stack`/`stacks` helpers from `BaseController`. This breaks the binding "the stack a token authorizes = the stack it touches": an `ApiClient` created with a `stack_id` restriction can be replayed against an arbitrary `stack_id` in the URL and will return that other stack's CI/build status.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping for every other API resource controller: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a non-nil `stack_id`, and `stack` builds on top of that scoped relation. [2](#0-1) 

`ApiClient` supports an optional `belongs_to :stack` association, meaning tokens can be minted that are meant to be usable for exactly one stack (this is precisely the mechanism the fixture `here_come_the_walrus` exercises, and the pattern the "an api client scoped to a stack will only see that one stack" test in `stacks_controller_test.rb` validates for the stacks index). [3](#0-2) [4](#0-3) 

`CCMenuController`, however, overrides `stack` and completely bypasses this scoping:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

`Stack.from_param!` is a bare, application-wide lookup with no notion of the current API client at all: it just parses `repo_owner/repo_name/environment` from the param and returns the first matching record from the entire `Stack` table. [1](#0-0) 

The only gate before reaching `stack` is `require_permission :read, :stack`, which only checks that the permission string `read:stack` is present in the client's `permissions` array — it does not check which stack the permission applies to: [6](#0-5) [7](#0-6) 

As a result, a token that was authorized (e.g. by its creator, via `CCMenuUrlController#client`, which explicitly grants only `%w[read:stack]` and is expected to be tied to one stack's CI badge URL) can be replayed with a different `stack_id` path segment and will successfully render CI/build state for any other stack in the installation. [8](#0-7) 

### Impact Explanation
This is an unauthorized/unscoped read of stack state (last build status, last build label, last build time, web URL) for stacks the token holder was never authorized to view — this maps to the "High — unauthenticated read of stack state, task streams or deploy output" impact bucket, since the token's authorization is scoped to one stack by the application's own token model but the controller doesn't enforce that scope. Any stack name (`repo_owner/repo_name/environment`) that the attacker can guess or discover (e.g. from a public URL, an internal wiki, or brute-forcing common environment names like `production`) is exposed, including whether a deploy locked/failed/succeeded, which can leak internal repository/environment naming and deployment health across stacks/repositories the token was never granted access to.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped CCMenu token (a widely distributed, low-privilege "read only build badge" token, since these are typically embedded in CI dashboards like CCTray/CCMenu clients) can trivially exploit this by changing the `stack_id` route segment of the `GET /api/stacks/:stack_id/ccmenu` request — no additional credentials, GitHub access, or session are required beyond the token itself, which the rules permit since it is not "a Shipit session" but rather exploitation of the engine's own scoping logic given a token the attacker already legitimately possesses.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (and the equivalent unscoped lookup in `CCMenuUrlController#stack`, which is used only to mint the token so is less critical) and rely on the inherited, scope-aware `BaseController#stack`/`#stacks`, so that a stack-scoped `ApiClient` can only ever resolve to the stack it is bound to, consistent with every other API resource controller (`Api::DeploysController`, `Api::TasksController`, `Api::HooksController`, etc.).

### Proof of Concept
1. Have a user create a stack-scoped CCMenu URL for stack A: `GET /ccmenu/owner/repoA/production` → `CCMenuUrlController#fetch` creates/returns an `ApiClient` with `permissions: ['read:stack']` (no `stack_id` set in this default flow, but the same code path applies to any `ApiClient` a Shipit admin creates with `stack: stackA` and `permissions: ['read:stack']` via the `api_clients` UI) and its `authentication_token`.
2. As the holder of that token (e.g. embedded in a CI dashboard config, or leaked via a public build badge URL), issue: `GET /api/stacks/owner/repoB/production/ccmenu?token=<token>` where `repoB/production` is a *different* stack than the one the token/client is bound to.
3. `CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`. [9](#0-8) 
4. `require_permission :read, :stack` passes because the client has `read:stack` in its `permissions`, regardless of which stack. [6](#0-5) 
5. `stack` resolves via `Stack.from_param!('owner/repoB/production')`, an unscoped, engine-wide lookup, returning stack B's record. [10](#0-9) [1](#0-0) 
6. The response renders stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl`, none of which the token was ever authorized to see, unlike the equivalent `Api::StacksController#index`/`#show` paths which correctly restrict results to `current_api_client.stack_id` when set. [2](#0-1)
