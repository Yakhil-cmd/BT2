### Title
AA Trigger Sender Spoofing via Multi-Author Unit — `trigger.address` Derived from `authors[0]` Instead of the Actual Payer - ([File: aa_composer.js])

### Summary
`getTrigger()` in `aa_composer.js` sets `trigger.address = objUnit.authors[0].address` unconditionally, taking the lexicographically-first author of the unit as the "sender" identity that gets passed into AA logic (`trigger.address`, `trigger.initial_address`) and used as the bounce-refund destination. Because ocore requires unit authors to be sorted in ascending address order (`validation.js:validateAuthors`, `author addresses not sorted`), any co-signer can force themselves into position `authors[0]` simply by having (or grinding) an address that sorts before the address that actually supplies the payment. This is structurally identical to the Hono `getConnInfo()` bug: a value that should identify the "real" party is taken from a fixed position in an attacker-influenced list, while the trustworthy value can exist elsewhere in the same list.

### Finding Description
`getTrigger()`:
```js
function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	...
``` [1](#0-0) 

`trigger.address` is not derived from which author's UTXO actually funded the payment output the AA is going to process — it's simply `authors[0]`. Meanwhile the `outputs` aggregation in the same function correctly sums amounts by matching `output.address === receiving_address`, irrespective of which author input funded them, so the payment amount and the "sender" identity can come from two different, unrelated authors.

The ordering constraint is enforced in `validateAuthors`:
```js
for (var i=0; i<arrAuthors.length; i++){
    var objAuthor = arrAuthors[i];
    if (objAuthor.address <= prev_address)
        return callback("author addresses not sorted");
    prev_address = objAuthor.address;
}
``` [2](#0-1) 

There is no check anywhere in author/message validation requiring that every listed author actually own an input in the payment message — `validatePaymentInputsAndOutputs` only checks that an input's `address` is *among* the authors (`arrAuthorAddresses.indexOf(...) === -1`), not that every author is a spender: [3](#0-2) 
This means an attacker can co-sign a unit as an additional, non-spending author whose address happens to be alphabetically smaller than the real payer's address, and that attacker's address becomes `trigger.address`/`trigger.initial_address` for the resulting AA trigger, even though the attacker contributed no funds.

`trigger.initial_address`/`trigger.address` is propagated unchanged through the whole AA call chain and exposed to oscript via `trigger.address`/`trigger.initial_address`: [4](#0-3) [5](#0-4) 
It is also recorded as the bounce-fee refund identity via `objAAResponse.trigger_address` / `trigger_initial_address`: [6](#0-5) 

Since AA developers commonly use `trigger.address`/`trigger.initial_address` for sender identification (ownership checks, whitelists, per-user accounting, KYC/attestation gating, referral tracking, "who sent this" bookkeeping) and it is also the destination address bounced funds are attributed to, the attacker's address is trusted to represent "who sent the payment" without the AA (or ocore) verifying that this address actually funded the trigger output.

### Impact Explanation
This is an authentication/identity-spoofing bug analogous to the Hono XFF issue (CWE-290/345): a security-relevant identity value (`trigger.address`) is taken from a position in an attacker-controllable ordered list rather than being tied to the actual economic actor. Concrete impacts on ocore's AA ecosystem:
- Any AA logic gating privileged actions on `trigger.address`/`trigger.initial_address` (e.g., "only the depositor may withdraw", staking/voting attribution, KYC allow-lists, anti-Sybil address tracking, referral/commission crediting) can be bypassed or manipulated by an attacker who merely co-signs the triggering unit with a cheap, non-funding address chosen to sort first.
- Bounce refunds (`trigger_address`/`trigger_initial_address` used for fee/refund bookkeeping) can be misattributed to the attacker's address instead of the genuine payer, causing state/accounting inconsistency and potential unauthorized crediting of value or privileges within the AA — this constitutes AA fund/logic manipulation reachable purely by any unpermissioned unit poster.

### Likelihood Explanation
Exploitation requires no special access: an attacker only needs to be an additional co-author on the unit sending a payment to an AA, adding a signature over an address they control that they've chosen (or ground, which is cheap since it only needs to sort before the true payer's address — a small search space) to be the smallest lexicographic author address. No inputs from that address are required, and validation places no constraint preventing non-spending co-authors. This is exploitable by any ordinary unit poster targeting AAs that rely on `trigger.address`/`trigger.initial_address` for identity-sensitive logic, which is a common oscript pattern.

### Recommendation
Do not derive `trigger.address` from `authors[0]`. Instead, derive the trigger sender from the address(es) that actually supplied the input(s) funding the payment output(s) sent to the AA (i.e., correlate with the payment message's `inputs`/owning address), or, if multiple distinct payer addresses are possible, reject/disambiguate multi-payer triggers explicitly rather than silently picking the first author. At minimum, require that `authors[0]` (or whichever author is used to populate `trigger.address`) be an address that owns an input in the triggering payment message.

### Proof of Concept
1. Attacker generates (or grinds) an address `A_attacker` that sorts lexicographically before a victim's real spending address `A_victim` (cheap; only a few characters need to be smaller, and ocore addresses are base32 chash160 values with wide first-character variance).
2. Attacker constructs (or convinces a victim wallet/co-signing protocol to produce) a unit with two authors: `A_attacker` (no payment inputs, just a valid signature) and `A_victim` (whose input funds the `payment` message with an output to AA address `X`).
3. Because `A_attacker < A_victim`, `objUnit.authors` is sorted with `A_attacker` first per `validateAuthors`'s ordering requirement.
4. When the unit is processed by `getTrigger(objUnit, X)` in `aa_composer.js`, `trigger.address = objUnit.authors[0].address = A_attacker`, while `trigger.outputs` correctly reflects the amount paid by `A_victim`'s funds.
5. Any AA whose oscript checks `trigger.address` (or `trigger.initial_address` for chained AA calls) for authorization, crediting, or refund-destination purposes will treat `A_attacker` as the payer/sender, even though `A_victim` funded the payment — allowing the attacker to spoof sender identity to bypass address-based checks or redirect bounce refunds.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
