### Title
Delimiter Injection in Arbiter Contract Hash Allows Content/Hash Mismatch - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` derives a contract's integrity-anchoring hash by naively joining user-supplied string fields (`title`, `text`, party names, etc.) with a fixed, non-length-prefixed delimiter string, without validating that none of those fields contain the delimiter itself. This mirrors the reported `ebay-mcp` bug class: untrusted values are blindly concatenated into a structured string without escaping/validating the separator, allowing an attacker to inject the separator and change how the string is parsed/interpreted downstream.

### Finding Description
`getHashSrc()` builds the hash source by joining contract fields with `exports.DELIMITER = "[|#|]"`: [1](#0-0) [2](#0-1) 

None of `contract.title`, `contract.text`, `contract.my_party_name`/`peer_party_name`, or `contract.asset` are validated to exclude the literal delimiter substring `"[|#|]"` before being joined. Because plain string concatenation with a fixed separator is used (not a length-prefixed or escaped encoding, unlike the collision-resistant `getSourceString()` in `string_utils.js`, which explicitly rejects the `\x00` join character in field values): [3](#0-2) 

a party crafting a contract offer (via the paired-device message `arbiter_contract_offer`, handled through `createAndSend`/`store` in `arbiter_contract.js`) can embed the delimiter sequence inside `title` or `text`. This allows constructing two different sets of field values that serialize to the identical joined string and therefore hash to the same `objContract.hash` via `getHash()`: [4](#0-3) 

Because the `title`/`text`/party-name fields are free-form strings accepted from a paired device counterparty with no server-side/consensus validation rejecting the delimiter, the field-boundary ambiguity is directly attacker-reachable through the private-payment/contract counterparty channel explicitly listed as in-scope ("private-payment counterparty", "wallet and contract message handling").

### Impact Explanation
The contract `hash` is the authoritative identifier used for status updates, cosigner sharing, and dispute resolution among arbiter, payer, and payee (`shareContractToCosigners`, `shareUpdateToPeer`, `respond`, `revoke`). If a malicious payer/payee can make two semantically different contract bodies (e.g., different terms in `text`) hash to the same value by shifting the delimiter boundary between fields, they can present one version to the counterparty/arbiter for signing/acceptance and later claim, or have accepted elsewhere, a different version with the same hash — undermining the integrity guarantee arbitration relies on. This is a real integrity/fraud risk within an in-scope contract/message-handling path, though it is a wallet-layer, off-chain object (not consensus-validated on the DAG), which somewhat bounds the severity relative to a direct spending/inflation bug.

### Likelihood Explanation
Exploitation only requires an attacker acting as one of the two contracting parties (payer or payee) crafting `title`/`text` values containing the fixed delimiter string `"[|#|]"` before sending the `arbiter_contract_offer`/`arbiter_contract_update` device message. No cryptographic breaking is needed — it's a straightforward string-boundary confusion, comparable in mechanism to the newline/quote injection in the referenced `ebay-mcp` advisory. Likelihood is moderate: it requires a cooperating or malicious counterparty and careful crafting of field values, but no special privileges beyond normal paired-device contract negotiation.

### Recommendation
Reject (or escape) any field value that contains the delimiter substring before computing `getHashSrc()`/`getHash()`, analogous to the `\x00`-byte check already performed in `string_utils.js`'s `getSourceString()`. Alternatively, switch to a length-prefixed or JSON-based canonical serialization (e.g., `getJsonSourceString`) for the hash source instead of ad-hoc delimiter joining, eliminating field-boundary ambiguity entirely.

### Proof of Concept
1. Attacker (as payer or payee) crafts `contract.title = "A"` and `contract.text = "[|#|]evil-terms"`.
2. A legitimate contract has `contract.title = "A[|#|]evil"` and `contract.text = "terms"`.
3. Both produce the same joined string `"A[|#|]evil[|#|]terms[|#|]..."` for the remaining identical fields, producing identical `sha256` hash via `getHash()` (`arbiter_contract.js` lines 205-207), even though the human-readable `title`/`text` differ. The attacker can present the version favorable to them to the arbiter or counterparty for the same `hash`, while the counterparty believes they agreed to different terms.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
