Confirmed: Shipit supports a multi-tenant `secrets.github` config keyed by organization name (`github_app_config`), and `WebhooksController#verify_signature` selects which organization's secret to verify against using a field parsed straight out of the *attacker-controlled* JSON body (`repository_owner`, i.e. `repository.owner.login` or `organization.login`), before the signature has been checked. The signature itself only proves "this body was HMAC'd with organization X's secret" — it proves nothing about which organization's *business data* (e.g. `organization.login` used by `MembershipHandler`) the body actually claims to describe.

### Title
Cross-organization webhook forgery breaks `Shipit.github_teams` authorization boundary - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner`, a value read directly from the unverified JSON body [1](#0-0) . That value is only used to pick *which* organization's `webhook_secret` to check the raw body against [2](#0-1) ; it is not cryptographically bound to the other organization-identifying fields inside the same payload (e.g. `organization.login`) that the event handlers actually trust and act on [3](#0-2) . This is structurally identical to the donation-attack bug class: a value the code uses to compute/validate one thing (which secret proves authenticity) is not the same value later consumed for the security-relevant business decision (which organization's `Team`/`Membership` records get modified), and an attacker who legitimately controls one tenant (their own GitHub org with the Shipit GitHub App installed) can produce a validly-signed payload whose *content* impersonates a different organization.

### Finding Description
`Shipit.github(organization:)` looks up per-organization app config from `secrets.github`, keyed by lowercase organization name, and raises `GithubOrganizationUnknown` if it can't find one [4](#0-3) . In multi-tenant mode, any organization present as a key in `secrets.github` is a valid tenant with its own `webhook_secret`.

`WebhooksController` computes `repository_owner` purely from the untrusted payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it only to pick which tenant's secret to HMAC-verify the raw body against [1](#0-0) , [5](#0-4) .

Because an attacker who legitimately installs Shipit's GitHub App on a GitHub org they control (`attacker-org`, with its own valid `webhook_secret` entry in `secrets.github`) can compute a correct `X-Hub-Signature` for *any* raw body of their choosing, they can craft a `membership` event payload where:
- `repository.owner.login` (or fallback `organization.login`, whichever `repository_owner` resolves to) = `attacker-org`, so `verify_signature` selects and successfully validates against `attacker-org`'s own secret, and
- `organization.login`, `team.id`/`team.slug`, and `member.login` inside the same payload claim to belong to `victim-org`.

`MembershipHandler#process` never revalidates that the `organization` field matches `repository_owner`/the tenant whose secret verified the request — it directly does `Team.find_or_create_by!(github_id: params.team.id) { team.organization = params.organization.login }` and then `team.add_member(User.find_or_create_by_login!(params.member.login))` [6](#0-5) .

`Shipit::Authentication#force_github_authentication` and `User#authorized?` gate all access to the app purely on `Team` membership derived from these `Team`/`Membership` rows [7](#0-6) , [8](#0-7) . So an attacker who forges a `membership` webhook this way can insert an arbitrary GitHub login (their own account) as a member of a `Team` belonging to `victim-org`'s `Shipit.github_teams` config, then log into Shipit via the normal GitHub OAuth flow (`GithubAuthenticationController#callback` → `User.find_or_create_from_github`) [9](#0-8)  and be treated as `authorized?`, gaining full access to deploy/rollback/lock any stack belonging to that victim organization.

### Impact Explanation
This breaks the equality the deployment is supposed to enforce: `organization whose webhook secret authenticated the request == organization whose Team/Membership data is written`. In a multi-tenant Shipit deployment, any tenant (even one an attacker legitimately owns) can forge writes into another tenant's authorization data, escalating into `Shipit.github_teams` authorization — the High-severity impact explicitly listed in scope ("escalation into `Shipit.github_teams` authorization"). Once a rogue member is added to the victim's team, the attacker obtains an authenticated, `authorized?` Shipit session for the victim org, from which they can trigger deploys/rollbacks against the victim's stacks — bordering on Critical (unauthorized deploy/rollback).

### Likelihood Explanation
This requires the deployment to run Shipit in multi-tenant mode (`secrets.github` keyed by multiple organizations), which is a documented, supported configuration (`github_app_config`, `TOP_LEVEL_GH_KEYS`) [10](#0-9) , [2](#0-1) . The attacker only needs to control one tenant (e.g. install the app on their own free GitHub org) to forge signed webhooks whose body content targets a different tenant — no privileged credentials, GitHub App private key, or repository write access to the victim org is required. `membership` webhooks are one of the default event handlers the setup guide instructs admins to enable [11](#0-10) .

### Recommendation
Do not select the verification secret and the business-logic organization from independently-controlled, unauthenticated fields of the same untrusted payload. After signature verification succeeds against the tenant selected by `repository_owner`, re-derive/require that every organization-identifying field consumed by handlers (`organization.login` in `MembershipHandler`, `repository.owner.login` used by sync jobs, etc.) is identical to the tenant whose secret validated the signature, and reject the webhook otherwise. Alternatively, verify the signature against the specific organization only after confirming (via a separate authenticated channel, e.g. GitHub's per-installation webhook secrets or event payload cross-checks) that the claimed organization and the authenticating organization are the same tenant.

### Proof of Concept
1. Deploy Shipit with `secrets.github` configured for two organizations: `attacker-org` (attacker installs the Shipit GitHub App on it themselves) and `victim-org` (a real customer org with a `Team` referenced in `Shipit.github_teams`).
2. Attacker computes `sha1=HMAC(attacker-org's webhook_secret, body)` for a crafted `membership` event body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "attacker-org"}},
  "organization": {"login": "victim-org"},
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999"},
  "member": {"login": "attacker-github-login"}
}
```
3. POST this body to `/webhooks` with `X-Github-Event: membership` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, and the signature validates successfully [1](#0-0) .
5. `MembershipHandler#process` creates/updates `Team` with `organization = "victim-org"` and adds `attacker-github-login` as a member [6](#0-5) .
6. Attacker logs into Shipit via GitHub OAuth using `attacker-github-login`; `User#authorized?` now returns true because of the forged `Team`/`Membership` row tied to `victim-org`'s configured `Shipit.github_teams`, granting the attacker full access to victim-org's stacks.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
