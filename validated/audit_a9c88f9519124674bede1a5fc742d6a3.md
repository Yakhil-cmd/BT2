## Analog Found

### Title
Rounding in Headers-Commission / Witnessing Reward Distribution Inflates Spendable Base-Asset Supply - (File: `headers_commission.js`, `paid_witnessing.js`)

### Summary
`calcHeadersCommissions()` splits a parent unit's `headers_commission` fee among the recipients listed in `earned_headers_commission_recipients` using `Math.round(full_amount * share / 100.0)` for each recipient, and `buildPaidWitnessesForMainChainIndex()` does the analogous thing for `payload_commission` among paid witnesses with `Math.round(payload_commission / countPaidWitnesses)`. Because each recipient's share is rounded independently, the sum of the rounded per-recipient amounts inserted into `headers_commission_outputs` / `witnessing_outputs` can exceed the actual fee amount that was paid by the unit, creating spendable balance that was never actually collected from anyone — the exact rounding-error class described in the report, but here it manifests as supply inflation rather than merely stranded funds.

### Finding Description
In `headers_commission.js`, when a child unit has multiple `assocEarnedHeadersCommissionRecipients`, the code computes: [1](#0-0) 
and the SQL/fallback path does the equivalent with `row.earned_headers_commission_share`: [2](#0-1) 

`validateHeadersCommissionRecipients()` only enforces that the recipient shares are positive integers, sorted by address, and sum to exactly 100 — it never constrains the shares in a way that prevents rounding from producing an aggregate greater than `full_amount`: [3](#0-2) 

Because `Math.round()` rounds .5 and above up, for an odd `full_amount` split with shares like 50/50, each recipient's share rounds `full_amount/2` **up**, so the two recipients together receive `full_amount + 1`. This extra unit is inserted into `headers_commission_contributions` and then aggregated into `headers_commission_outputs`: [4](#0-3) 

These `headers_commission_outputs` rows are later spent as `headers_commission` inputs, and the amount credited to the spending unit is derived purely from `mc_outputs.calcEarnings` reading back the (already-inflated) `headers_commission_outputs` sum — not from any check against the true fee originally paid by the parent unit(s): [5](#0-4) 

The per-unit conservation check in `validatePaymentInputsAndOutputs` only verifies that a *single* unit's `total_input === total_output + headers_commission + payload_commission + ...` for the fees *that unit itself* is paying; it has no visibility into whether the sum of historically-distributed `headers_commission_contributions` for a payer unit matches that payer's original `headers_commission` value: [6](#0-5) 

The same rounding pattern exists for witnessing rewards, where `payload_commission` is divided among `countPaidWitnesses[v.unit]` witnesses via `Math.round`: [7](#0-6) 

### Impact Explanation
An unprivileged unit author who authors (or co-authors, via multiple addresses they control) a multi-authored unit and wins the headers-commission race for a parent unit can specify `earned_headers_commission_recipients` shares (e.g., 50/50, 34/33/33, etc.) chosen so that rounding-up occurs across the split. This lets the author systematically mint 1+ extra bytes of spendable `headers_commission_outputs` balance per qualifying unit beyond what the network actually collected as fees — a genuine, repeatable base-asset supply-inflation bug, not merely "tokens stuck," since the excess is created and made spendable rather than lost. Repeated at scale by posting many cheap multi-authored units, this can mint a nontrivial and unbounded amount of extra bytes over time, directly breaking the invariant that total confirmed output value equals total issued value.

### Likelihood Explanation
The attack requires no special privilege: any address can author a unit with multiple authors and an `earned_headers_commission_recipients` list under its own control, and win headers-commission or witnessing distribution simply by posting valid units in the ordinary DAG (this is validated purely by `validateHeadersCommissionRecipients`, which does not check for rounding safety). The exploit is deterministic (choose shares that round up) and repeatable indefinitely, making likelihood high, though the per-transaction gain (fractions of a byte, rounded to at most a few units per split) is small, requiring volume to accumulate a meaningful amount.

### Recommendation
Distribute `full_amount` / `payload_commission` among recipients using a scheme that guarantees the sum of parts equals the whole exactly (e.g., largest-remainder method: round down all shares, then distribute the leftover units one-by-one to the recipients with largest fractional remainder, sorted deterministically by address) instead of independently rounding each recipient's share with `Math.round`. Apply the same fix to the witnessing-reward distribution in `paid_witnessing.js`. Additionally, consider adding a consistency check that the sum of `headers_commission_contributions`/`witnessing` amounts distributed for a given payer unit never exceeds the unit's recorded `headers_commission`/`payload_commission`.

### Proof of Concept
1. Author unit `A` (payer) with a byte-size such that its computed `headers_commission` is an odd number, e.g. `headers_commission = 101`.
2. As the author of the winning child unit `B` for that headers-commission (`B` is multi-authored, e.g. by addresses `addr1` and `addr2`, both controlled by the attacker), set `earned_headers_commission_recipients = [{address: addr1, earned_headers_commission_share: 50}, {address: addr2, earned_headers_commission_share: 50}]`. This passes `validateHeadersCommissionRecipients` since the shares sum to 100.
3. When `calcHeadersCommissions()` runs, each recipient gets `Math.round(101 * 50 / 100.0) = Math.round(50.5) = 51`, so `addr1` and `addr2` each receive 51, totaling 102 — one byte more than the 101 actually paid by unit `A`.
4. `headers_commission_outputs` now holds 102 spendable bytes for mci-range tied to unit `A`, even though only 101 were ever collected; both addresses can later spend their 51-byte shares via `headers_commission` inputs, validated solely against `mc_outputs.calcEarnings`/`headers_commission_outputs`, with no cross-check against the original 101 fee.
5. Repeating this across many multi-authored units accumulates unlimited extra bytes, inflating the effective circulating base-asset supply beyond genesis issuance.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
