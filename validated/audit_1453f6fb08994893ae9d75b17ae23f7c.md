### Title
Unvalidated P2P Staking Info Delivery During Fast-Sync Allows Reward Address Poisoning — (`datasync/downloader/queue.go`)

### Summary

The `validate` callback inside `queue.DeliverStakingInfos` is an explicit no-op stub. A remote P2P peer that is assigned a staking-info fetch request can deliver a `P2PStakingInfo` with arbitrary `KEFAddr`, `KIFAddr`, and `CouncilRewardAddrs`. The poisoned struct is stored into `fetchResult.StakingInfo` and subsequently committed to the node's database via `commitFastSyncData`, with no content check at any point in the pipeline.

### Finding Description

`DeliverStakingInfos` constructs its `validate` closure as:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

The generic `deliver` helper calls `validate(i, header)` before calling `reconstruct`. Because `validate` always returns `nil`, the `reconstruct` closure unconditionally executes:

```go
reconstruct := func(index int, result *fetchResult) {
    result.StakingInfo = stakingInfoList[index]
    result.SetStakingInfoDone()
}
``` [2](#0-1) 

This sets `fetchResult.StakingInfo` — the `P2PStakingInfo` field — to whatever the peer sent, with no hash-binding, no Merkle proof, and no comparison against the block header. [3](#0-2) 

Compare with `DeliverBodies` and `DeliverReceipts`, which both verify the delivered data against the header's committed root (`TxHash` / `ReceiptHash`) before accepting: [4](#0-3) [5](#0-4) 

Staking info has no equivalent check. The `P2PStakingInfo` struct carries all reward-sensitive fields: [6](#0-5) 

After `fetchResult` items are completed, `commitFastSyncData` in `downloader.go` persists them to the key-value store. The staking info written there is later read by `GetStakingInfo` (called from `PostInsertBlock`) to drive reward distribution for subsequent blocks: [7](#0-6) 

### Impact Explanation

A malicious peer that is assigned a staking-info fetch request (a normal outcome of the downloader's peer-assignment logic during fast-sync) can supply a `P2PStakingInfo` where:

- `CouncilRewardAddrs` → attacker-controlled addresses (validator block rewards)
- `KEFAddr` → attacker-controlled address (KEF fund)
- `KIFAddr` → attacker-controlled address (KIF fund)

These values are written to the DB. For any block number `N` at a staking-update-interval boundary that falls within the fast-synced range, the poisoned staking info governs reward distribution for all blocks in `[N, N + stakingUpdateInterval)`. If that window extends past the fast-sync pivot, the node distributes live block rewards to attacker-controlled addresses after sync completes — without ever executing a transaction or holding a governance key.

### Likelihood Explanation

Fast-sync is a standard, publicly reachable sync mode. Any peer that successfully connects and is assigned a staking-info fetch task can exploit this. No privileged key, validator majority, or governance action is required. The only precondition is being a connected P2P peer at the time the victim node is fast-syncing.

### Recommendation

Implement the missing validation logic. The staking info must be cryptographically bound to the block header. Options:

1. Include a hash of the canonical staking info in the block header (similar to `TxHash`/`ReceiptHash`) and verify it in `validate`.
2. Re-derive staking info from the AddressBook contract state at the pivot block and reject any peer-supplied value that diverges.
3. At minimum, after fast-sync completes, re-derive and overwrite all staking-info DB entries from the available state trie before switching to full-sync mode.

Remove the `TODO-Kaia-Snapsync update validation logic` placeholder and replace it with a real check before this code ships to production.

### Proof of Concept

```go
// Unit test sketch (not production code)
func TestDeliverStakingInfosNoValidation(t *testing.T) {
    q := newQueue(...)
    // Schedule a header at a staking-update-interval boundary
    q.Schedule([]*types.Header{header}, header.Number.Uint64())
    // Simulate peer reservation
    req, _, _ := q.ReserveStakingInfos(peer, 1)

    // Attacker-controlled staking info: mismatched block content
    poisoned := &staking.P2PStakingInfo{
        BlockNum:           header.Number.Uint64(),
        CouncilRewardAddrs: []common.Address{attackerAddr},
        KEFAddr:            attackerAddr,
        KIFAddr:            attackerAddr,
    }

    n, err := q.DeliverStakingInfos(peer.id, []*staking.P2PStakingInfo{poisoned})
    // Expect: n == 1, err == nil — poisoned info accepted with no error
    assert.Equal(t, 1, n)
    assert.Nil(t, err)

    results := q.Results(false)
    // Poisoned info is now in fetchResult, ready for commitFastSyncData
    assert.Equal(t, attackerAddr, results[0].StakingInfo.KEFAddr)
}
```

The test passes because `validate` unconditionally returns `nil`, confirming the invariant is violated and the poisoned info is stored.
