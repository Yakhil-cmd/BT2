### Title
Webhook signature verification key is selected from an unauthenticated field, allowing cross-organization/repository spoofing - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the **unauthenticated** JSON body, then the actual handler that mutates state (e.g. `PushHandler`) looks up the target `Repository`/`Stack` using a **different** field, `repository.full_name`. Nothing binds these two fields together, so an attacker can pick the verification key from any configured GitHub organization while acting on any other organization's repository.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes the org used for signature verification purely from attacker-supplied JSON, before any authentication has occurred: [1](#0-0) [2](#0-1) 

The selected `github_app` (and therefore the `webhook_secret` used) comes from `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — fields inside the raw, unverified request body.

Signature verification itself is: [3](#0-2) 

If the organization selected via `repository_owner` has no `webhook_secret` configured (`webhook_secret: nil` is explicitly documented as **optional**, see `docs/setup.md`), `verify_webhook_signature` unconditionally returns `true` regardless of the actual `X-Hub-Signature` header or body content.

Meanwhile, every webhook handler determines which `Repository`/`Stack` to act on using a completely different payload field, `repository.full_name`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to select the verification key) and `repository.full_name` (used to select the write target) are two independent, attacker-controlled JSON fields inside the same unauthenticated body, there is no requirement that they agree. This breaks the binding: `organization authenticated == repository written`. An attacker who knows (or controls) any organization onboarded to this Shipit instance that has no `webhook_secret` set (plausible for a staging/dev org, or one the attacker registers if self-service repository/stack creation is enabled) can set `repository.owner.login` to that org to make `verify_webhook_signature` trivially return `true`, while setting `repository.full_name` to any other tracked repository (e.g. `victim-org/victim-repo`) so the handler acts on it.

`Shipit::GithubOrganizationUnknown` is only raised for organizations that are *not configured at all* in `Shipit.github` — it does not protect against this cross-field confusion between two *configured* organizations.

### Impact Explanation
This allows an unauthenticated attacker to forge GitHub webhook events (push, status, check_suite, pull_request, membership) for a repository/stack they do not control, as long as the Shipit instance manages at least one other organization without a webhook secret. Concretely:
- `push` events trigger `Stack#sync_github` (`GithubSyncJob`), causing Shipit to fetch and record attacker-influenced commit history for the victim stack via `stack.github_api` — cross-repository state corruption without any credential.
- `status`/`check_suite` events can fabricate CI status on a victim commit, potentially unblocking `deployable?` checks used to gate deploys, contributing to an unauthorized deploy.
- `membership` events can add/remove team memberships via `MembershipHandler` for an org named in the payload, again gated only by the mismatched, attacker-chosen verification key.

This matches the "unauthorized deploy/rollback" and "cross-repository writes" impact bar, since it uses a legitimate-but-mismatched signature check to write into a repository/organization that never authorized the request.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is multi-tenant (manages more than one GitHub organization via `Shipit.github`), and (2) at least one of those organizations has no `webhook_secret` configured — explicitly documented as optional in `docs/setup.md`. This is a realistic operational configuration (e.g., a low-risk sandbox/dev org left without a secret) and requires no prior authentication, session, or token — only knowledge of the org name and the target's `full_name`, both discoverable from GitHub itself.

### Recommendation
Bind the field used for signature/key selection to the field used for state mutation:
- Verify the webhook using a secret tied to the specific repository (not just the organization-level lookup derived purely from an unauthenticated field), or
- After successful signature verification, re-derive `repository_owner` from `repository.full_name` and assert they match the organization whose secret was actually used to verify, rejecting the request otherwise.
- Alternatively, always require a non-blank `webhook_secret` for every configured organization so `verify_webhook_signature` can never short-circuit to `true`.

### Proof of Concept
1. Shipit instance configures two orgs in `secrets.yml`: `victim-org` (with `webhook_secret` set) and `sandbox-org` (with `webhook_secret: nil`, e.g. left blank per docs' "optional" note).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "sandbox-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No valid `X-Hub-Signature` is required, since `repository_owner` resolves to `sandbox-org`, whose `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
3. `WebhooksController#create` then dispatches to `PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, enqueuing `GithubSyncJob` for the victim stack — a state change on a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
