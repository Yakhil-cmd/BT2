### Title
Unauthenticated author address causes unreleased `handleJoint`/per-address mutex lock and DB connection leak on validation crash - ([File: validation.js])

### Summary
The Redis advisory describes a class of bug where malformed/erroring input on a connection is not cleaned up properly, so the resources tied to that connection (and the connection-handling loop) are never released, starving other clients. The same bug class — "an error path fails to release a held resource, freezing out future legitimate work" — is reachable in `ocore`'s unit-validation pipeline through `validation.js`'s `validate()` function.

### Finding Description
`validate()` locks the mutex keyed by the **unauthenticated** author addresses taken straight from `objUnit.authors[].address` *before* any signature/authentifier check is performed: [1](#0-0) [2](#0-1) 

Because `arrAuthorAddresses` is only checked with `isValidAddress` (a format check), an attacker can name *any* well-formed address — including one belonging to another legitimate user/AA — as an "author" of a unit they broadcast, with no valid signature required to acquire the lock. Once inside `mutex.lock(arrAuthorAddresses, ...)`, a database connection is taken from the pool and a long `async.series` of validation steps runs: [3](#0-2) 

`validation.js` contains 36 `throw Error(...)` statements reachable from inside this series (e.g., in `validateAuthor`, hash-tree/parent/skiplist checks, AA-trigger/tps-fee checks, message validation). These are written as "should never happen" invariant guards, but several of them are fed by data that ultimately derives from the attacker-supplied joint content (addresses, definitions, parent references, hash-tree balls, etc.) rather than from values validated earlier in the same call. If any such `throw` fires **synchronously inside one of the `async.series` step functions**, execution never reaches the final callback at the bottom of `validate()`: [4](#0-3) 

That final callback is the *only* place that calls `commit_fn` → `conn.release()` and the mutex `unlock()`. If it is skipped:
- The DB connection acquired via `db.takeConnectionFromPool` is never returned to the pool.
- The mutex lock on the attacker-chosen author address(es) is never released — permanently blocking any future validation of units authored by that address (including the victim's real address, since the lock key is the bare address string, shared by all future `mutex.lock(arrAuthorAddresses, ...)` calls for that address).
- Because `network.js`'s `handleJoint` first takes the coarser `handleJoint` lock and only calls `unlock()` from inside the `validation.validate()` callbacks, an uncaught throw inside `validate()` also propagates as an unhandled exception up through that lock's callback chain, so the single global `handleJoint` mutex used to serialize *all* unit processing is never released either: [5](#0-4) 

This mirrors the Redis pattern: a badly-handled error path on attacker-supplied input leaves a critical serialization resource (mutex / connection) permanently held, instead of being released on the error branch.

### Impact Explanation
Because `handleJoint` is a single global mutex guarding the entire validate → save pipeline for the whole node, a single crafted unit that trips one of these `throw Error` guards can wedge the node's unit-processing pipeline indefinitely: no further joints (from any peer, in memory or from `unhandled_joints`/hash-tree catch-up) can be validated or saved once the lock is stuck. This is a node-wide "unable to confirm new units" condition, and depending on which invariant is hit, it can also leak DB connections from the finite pool, compounding the outage. If the throw instead only exhausts the per-address lock (not `handleJoint`), it still permanently DoSes future transactions from the targeted address (fund freezing) because that address's mutex key can never be acquired again by legitimate composer flows that also lock on the same address key.

### Likelihood Explanation
Reaching this requires crafting a unit whose fields are internally consistent enough to reach deep into `validateAuthors`/`validateMessages`/hash-tree checks but which trips one of the many `throw Error` invariant assertions with attacker-influenced data — none of these throws are behind privileged access; an attacker only needs to post/broadcast a single unit as an ordinary, unauthenticated peer. Whether a concretely reachable invariant violation exists could not be fully confirmed within available tool calls (36 candidate `throw` sites in `validation.js` would each need individual data-flow tracing to prove attacker-reachability from unvalidated joint fields), so this should be treated as a **plausible but not fully proven** analog pending closer per-throw-site review.

### Recommendation
- Wrap the entire `async.series` body of `validate()` (and the `handleJoint`/per-address locking in `network.js`) in error handling that guarantees `conn.release()` and `unlock()` are always called, even on synchronous throws — e.g., wrap each step in try/catch that routes to the `cb(err)` path instead of throwing, or wrap the whole `mutex.lock` callback in a `try { ... } finally { unlock(); conn && conn.release(); }`.
- Convert internal "should never happen" invariant violations that are actually reachable from untrusted joint data into regular validation errors (`callbacks.ifUnitError`/`ifJointError`) instead of `throw Error`, so they flow through the existing cleanup path.
- Add a watchdog/timeout on the `handleJoint` and per-address mutex keys so a stuck lock is detected and can trigger a controlled recovery/restart rather than a silent permanent hang.

### Proof of Concept
A fully deterministic PoC (a specific joint payload that hits one of the 36 `throw Error` sites in `validation.js` with externally-controlled data) could not be constructed with certainty from static reading alone within the available investigation budget. The exploitable mechanism — an uncaught throw inside the `async.series` step functions bypassing `commit_fn`/`unlock()` in the final callback at `validation.js:445-472`, after the mutex has already been acquired on attacker-named author addresses at `validation.js:357` — is demonstrated by the code path itself; a working PoC would require picking one specific reachable throw site (e.g., inside `validateAuthor`'s `findUnstableInitialDefinition` or an AA/hash-tree check) and constructing a joint whose `parent_units`/`authors`/message fields drive execution into that branch, which requires deeper tracing than could be completed here.
