### Title
Webhook Signature Verifies the Claiming Organization, Not the Repository/Commit Actually Written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound webhook based on one attacker-supplied field (`repository.owner.login`), while the handlers that perform the actual write (e.g. `StatusHandler`, and any handler built on `Handler#repository_name`) act on a *different*, independently-controlled field (`sha` / `repository.full_name`) that is never cross-checked against the organization whose secret validated the request. In a multi-organization Shipit deployment, this lets a party who legitimately knows only one organization's webhook secret forge events that are applied to a completely unrelated organization's stacks and commits.

### Finding Description
`verify_signature` derives the GitHub App/secret to validate against solely from the payload itself: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is read straight from the JSON body: [2](#0-1) 

For multi-org configurations, `Shipit.github(organization:)` looks up a *per-organization* `webhook_secret` keyed by that value: [3](#0-2) 

Once the HMAC is confirmed to match *some* organization's configured secret, the raw body is dispatched unchanged to every registered handler for the event: [4](#0-3) 

Crucially, the handlers do not re-validate that the object they act on belongs to the organization whose secret was used to authenticate the request:

- `StatusHandler#process` matches **globally by commit SHA**, with no repository/organization scoping at all: [5](#0-4) 

- The generic `Handler` base class (used by push/pull_request handlers) derives the target repository from `repository.full_name`, a field **distinct** from the `repository.owner.login` field used for signature-secret selection: [6](#0-5) 

The binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository/commit that gets written`

What the code actually enforces is:
`HMAC(secret_for(payload["repository"]["owner"]["login"]), raw_body) == signature`

with **no** subsequent check that `payload["repository"]["owner"]["login"]` matches the organization owning `payload["sha"]`'s commit (`StatusHandler`) or `payload["repository"]["full_name"]` (generic `Handler`). Because the whole raw body is attacker-supplied JSON (only its HMAC is checked, using a secret keyed off a field inside that same JSON), anyone who legitimately possesses one organization's `webhook_secret` (e.g., an admin of their own onboarded GitHub App/org, a normal, documented, non-privileged-relative-to-other-tenants scenario per `docs/setup.md`'s "Using Multiple Github Applications" section) can freely set every other field, including which commit/repo the event applies to.

### Impact Explanation
This breaks the equality "organization authenticated == repository/commit written," enabling:
- **Unauthorized deploy/rollback**: `PushHandler` (built on the same `Handler#repository_name`) can be pointed, via a spoofed `repository.full_name`, at a different organization's stack, forcing `stack.sync_github(expected_head_sha: ...)` to run against an attacker-chosen SHA on a stack the caller has no legitimate relationship with.
- **CI status forgery bypassing merge/deploy gating**: `StatusHandler` writes a `Status` for *any* commit SHA present in the database, regardless of which org/secret authenticated the request. If that SHA belongs to a required CI context (`ci.require`) on another organization's stack, an attacker can forge a passing status to unblock the merge queue or a gated deploy — a concrete "unauthorized merge/deploy" per the accepted impact criteria.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a first-class, documented configuration) and possession of one organization's own legitimately-issued `webhook_secret` — something any org onboarded to the shared instance already has by design, without needing any Shipit session, `ApiClient` token, or privileged Shipit account. The cross-tenant confusion is a direct, reachable consequence of using unrelated payload fields for authentication-secret-selection versus target-object-resolution.

### Recommendation
Bind the verified organization to the object being mutated:
- After HMAC verification, re-derive the acted-upon repository/commit strictly from a field that is provably tied to `repository_owner` (e.g. require `repository.full_name.split('/').first.casecmp?(repository_owner)`), and reject mismatches.
- In `StatusHandler`, scope the `Commit` lookup by the repository identified in the payload (and verify that repository's owner matches the authenticating organization), instead of matching globally by `sha`.
- More generally, do not let a single JSON blob supply both "which secret authenticates this" and "which tenant this write applies to" without cross-validating the two.

### Proof of Concept
1. Shipit is configured for two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. The maintainer of `OrgA` (who legitimately owns/knows `OrgA`'s `webhook_secret` from their own GitHub App settings) crafts an arbitrary JSON body:
   ```json
   {"sha": "<sha-of-a-commit-belonging-to-OrgB-repo>", "state": "success", "context": "ci/required-check"}
   ```
3. They compute `sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POST it to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as absent/irrelevant for this payload shape but still validates via `Shipit.github(organization: repository_owner)`; regardless, once any configured secret matches, `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — with no verification that the commit belongs to `OrgA`. A forged "success" status is recorded on `OrgB`'s commit, potentially satisfying a required CI check and unblocking an unauthorized merge/deploy on `OrgB`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
