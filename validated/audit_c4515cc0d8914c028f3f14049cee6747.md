### Title
Cross-organization webhook signature confusion allows unauthorized actions on another tenant's Stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, the field used to select which organization's webhook secret verifies the HMAC signature (`repository.owner.login` / `organization.login`) is *not* the same field later used to resolve which `Repository`/`Stack` the webhook payload actually acts on (`repository.full_name`). Both fields are attacker-controlled inside the same signed payload, so a party who legitimately knows only their own organization's webhook secret can forge a signed payload that passes verification under their own org but targets another organization's tracked repository.

### Finding Description
Shipit supports running a single instance against multiple GitHub organizations, each with its own `GitHubApp` config and (optionally) its own `webhook_secret`, as shown by the multi-org fixture [1](#0-0) . `Shipit.github(organization:)` looks up the per-organization config and instantiates the corresponding `GitHubApp` [2](#0-1) .

`WebhooksController#verify_signature` picks which organization's secret to verify the incoming signature against based on `repository_owner`, which is read straight from the untrusted JSON payload: [3](#0-2) [4](#0-3) 

The HMAC check (`GitHubApp#verify_webhook_signature`) only proves that *someone who knows the secret of the organization named in `repository.owner.login`* produced this exact raw body [5](#0-4) . It says nothing about which repository the *content* of that body targets.

Once verification passes, every event `Handler` resolves the target `Stack`(s) using a *different* field of the same payload — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

`Repository.from_github_repo_name` then does a straight DB lookup on that attacker-supplied owner/name pair with no cross-check against the organization whose secret validated the signature [7](#0-6) .

This breaks the binding **organization that authenticated (via `repository.owner.login`/`organization.login`, matched to a known `webhook_secret`) == repository that is written (via `repository.full_name`, resolved to a `Stack`)**. Because both fields live inside the same HMAC-covered body, an attacker who owns/administers Organization A's GitHub App (and therefore legitimately knows Organization A's `webhook_secret`, since they configured that App on github.com) can sign a payload with `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/some-repo"`, where OrgB is an unrelated tenant tracked by the same Shipit instance.

### Impact Explanation
Handlers act on whatever `Stack`s resolve from the (forgeable) `repository.full_name`, independent of the organization that actually authenticated. For example, the `push` handler enqueues `GithubSyncJob` keyed on the resolved stack, which syncs commits and can trigger continuous delivery/deploys for that stack — as confirmed by the request/response mapping in the controller test suite [8](#0-7) . Other handlers similarly act cross-org: `check_suite`/`status` update commit deployability and release statuses, `pull_request/opened` can auto-provision review stacks, and `membership` creates teams/users, all keyed off attacker-controlled payload fields rather than the authenticated organization. This can result in an unauthorized deploy being triggered on a repository/stack belonging to a different organization than the one whose credentials validated the request — a cross-tenant write achieved purely by mismatching two fields inside one signed body.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately control one organization onboarded to the same multi-tenant Shipit instance (and thus knows their own org's `webhook_secret`, which they themselves provisioned when creating their GitHub App) and that a victim organization's repository is also tracked by that instance. No GITHUB_TOKEN, private key, or victim secret is needed — only crafting `repository.owner.login`/`organization.login` to name the attacker's own org while `repository.full_name` names the victim's repo, then POSTing to the shared `/webhooks` endpoint with a correctly-computed signature.

### Recommendation
After verifying the signature, cross-check that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the owner of `repository.full_name` (and of any other repository referenced in the payload) before dispatching to handlers. Reject the request if they diverge, and/or resolve the target repository using an owner value that has itself been authenticated against the verifying organization's config.

### Proof of Concept
1. Shipit is deployed multi-tenant with `secrets.github` containing both `OrgA` and `OrgB`, each with distinct `webhook_secret` (mirrors `test/dummy/config/secrets_double_github_app.yml`), and both `OrgA/repo-a` and `OrgB/repo-b` have Shipit `Stack`s.
2. Attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker builds a `push` payload JSON with:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/repo-b"`
   - `after = <attacker-chosen sha>`
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` → `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature check passes (attacker signed correctly for OrgA).
6. `PushHandler#process` resolves stacks via `Handler#repository_name` → `"OrgB/repo-b"` → `Repository.from_github_repo_name` → OrgB's stack, and enqueues `GithubSyncJob` for OrgB's stack with the attacker-chosen SHA, potentially triggering CD/deploys on OrgB's stack despite the attacker never having authenticated for OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
