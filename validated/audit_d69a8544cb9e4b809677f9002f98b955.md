### Title
Unchecked RAY valuation overflow permanently freezes large accrued markets - (File: `common/src/rates/simulate.rs`)

### Summary
A very large market can grow its supply or borrow index until `scaled_to_original(scaled_shares, index)` exceeds `i128::MAX`, causing `MathOverflow` before the configured index ceiling can clamp growth. Because every pool mutation and `update_indexes` first calls `global_sync`, the affected market then permanently rejects repayments, withdrawals, liquidations, and further keeper accruals. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` calculates utilization by first unscaling both aggregate positions with `scaled_to_original`, so both `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` must fit an `i128`. [3](#0-2)  `scaled_to_original` delegates to `Ray::mul`, which returns a checked `mul_div_half_up` result and panics with `MathOverflow` when the final value is unrepresentable. [4](#0-3) [5](#0-4) 

The borrow index ceiling only clamps the index itself after multiplication; it does not prevent the already-recorded scaled balances from becoming too large to value at an index below that ceiling. [6](#0-5)  Consequently, a book near the protocol’s maximum representable balance can cross the lower “share value fits `i128`” boundary long before `MAX_BORROW_INDEX_RAY` is reached. [7](#0-6) [8](#0-7) 

The public attack trigger is `Controller::update_indexes(caller, assets)`, which is permissionless aside from caller authorization and forwards the target market to the pool accrual entrypoint. [9](#0-8) [10](#0-9)  The same panic also occurs organically on the next `supply`, `borrow`, `withdraw`, `repay`, liquidation-related pool call, or other mutation because each operation loads a synced market and runs `global_sync` first. [11](#0-10) 

### Impact Explanation
The result is permanent freezing of all funds and debt operations for the affected `(hub_id, asset)` book. Once the stored index crosses the valuation ceiling, no in-scope user entrypoint can pass the mandatory pre-mutation accrual: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot resolve the position, and `update_indexes` itself cannot advance the timestamp. [11](#0-10) [12](#0-11)  This satisfies permanent freezing of user funds and can leave the protocol unable to operate that market. [13](#0-12) 

### Likelihood Explanation
Likelihood is medium: the condition requires a very large market balance and sustained interest growth, but all inputs are ordinary unprivileged protocol operations and the trigger itself is permissionless. [9](#0-8)  The repository’s own stress test demonstrates the reachable state with a one-billion-token, 18-decimal market at 98% utilization on the steep XLM rate curve and shows that a subsequent `update_indexes`, `withdraw`, or `repay` fails with `MATH_OVERFLOW` while the borrow index remains below its cap. [14](#0-13)  Cap validation accepts balances up to the largest amount whose initial RAY scaling fits `i128`, but that bound does not account for later index multiplication. [15](#0-14) 

### Recommendation
Calculate utilization and accrual against saturated or widened valuations rather than panicking on the valuation product. For example, add a saturating `scaled_to_original`/`position_value` path for aggregate market accrual, or perform the utilization comparison directly in `I256` and cap utilization at `RAY` when either side exceeds the representable range. The cap must be enforced before any required `Ray` multiplication so a market can continue accruing or reach `MAX_BORROW_INDEX_RAY` instead of becoming unrecoverable. [16](#0-15) [6](#0-5) 

### Proof of Concept
The existing production-path test reproduces the failure by supplying one billion whole tokens of an 18-decimal asset, borrowing 98% of that market, advancing time until the index crosses the representable-value boundary, and then calling `update_indexes`; it asserts `MATH_OVERFLOW` and verifies both withdrawal and repayment remain frozen. [14](#0-13)

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
