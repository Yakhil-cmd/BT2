### Title
MultiEdit content-check bypass via space-joined `new_string` fragments splits detection from actual on-disk content - ([File: plugins/security-guidance/hooks/patterns.py] / [File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`extract_content_from_input` reconstructs the text to be scanned for a `MultiEdit` call by joining each edit's `new_string` with a literal space `" ".join(...)`, rather than reproducing the actual resulting file content produced by sequentially applying each edit's `old_string`→`new_string` replacement at its real position in the file. An attacker can split a dangerous token (e.g. `os.system(`) across two adjacent edits so the synthetic space-joined string never contains the contiguous dangerous substring, while the real post-edit file does, because the two edits' replacement regions are contiguous in the source file with no separating space.

### Finding Description
`check_patterns` is a purely regex/substring-based scanner over a `content` string built by `extract_content_from_input`: [1](#0-0) 

For `MultiEdit`, this joins every edit's `new_string` with a space, not the actual file bytes that result from applying `old_string → new_string` substitutions to the target file. `check_patterns` then regex-searches this synthetic string against rules such as `os_system_injection` (`\bos\.system\s*\(`) and `python_subprocess_shell`: [2](#0-1) 

The match call itself is at: [3](#0-2) 

`MultiEdit`'s documented tool semantics apply each edit's literal `old_string → new_string` substitution sequentially against the evolving file content, at whatever position `old_string` occurs. If an attacker picks two `old_string`s that are textually adjacent in the source file — e.g. `old_string1` ends exactly where `old_string2` begins — and sets `new_string1` to end in `"os.sy"` and `new_string2` to start with `"stem("`, the two replacements land back-to-back in the real file with no separator, producing the contiguous token `os.system(`. But `extract_content_from_input`'s `" ".join(...)` inserts a literal space between the two `new_string` fragments before scanning, yielding `"...os.sy stem(..."` — which does not match `\bos\.system\s*\(` nor any subprocess-shell pattern. The validation layer therefore evaluates a different string than what actually gets written to disk, letting the dangerous command-injection sink through with no PostToolUse warning and no entry in `pending_warnings` for the Stop-hook sweep (since `record_pending_warnings` is only invoked when `check_patterns` reports a match).

### Impact Explanation
This breaks the trust boundary the plugin is meant to enforce: an unprivileged content source (attacker-controlled instructions or generated edits routed through Claude via prompt injection or automation) can cause a real `os.system(...)` (or `subprocess.*(..., shell=True)`) call to be written to a file with zero pattern-based warning and zero Stop-hook `pending_warnings` follow-up, since the sweep only re-checks files previously flagged. The scoped impact is exactly as stated in the question: a command-injection sink is persisted to disk while the guidance/warning layer silently misses it, defeating the plugin's core "PostToolUse, every edit" detection guarantee described in its own architecture docs.

### Likelihood Explanation
Feasible and fully attacker-controlled: the attacker only needs to supply a `MultiEdit` `tool_input` (via a plugin-file/prompt-injection-controlled edit plan) with two edits whose `old_string`s are contiguous in the target file and whose `new_string`s are chosen so the dangerous token's substring split falls exactly at the edit boundary. No special privilege, race condition, or timing dependency is required — it is a pure parsing/reconstruction mismatch between the checker's `" ".join` approximation and MultiEdit's real substitution semantics, reproducible deterministically every time.

### Recommendation
Do not approximate MultiEdit's resulting content by joining `new_string` fragments with a space. Instead, reconstruct (or read back) the actual post-edit file content — e.g. read the file after the tool has applied edits (PostToolUse already runs after the edit succeeds) and run `check_patterns` against the real file contents, exactly as `sweep_pending_warnings` already does for its sweep. If pre-write inspection is required, simulate the edits by applying each `old_string → new_string` substitution against a copy of the current file content (in order) rather than concatenating `new_string`s independently, so the joined regex context matches what will truly land in the file.

### Proof of Concept
Unit test (pseudo-code, targeting `check_patterns`/`extract_content_from_input` in `plugins/security-guidance/hooks/security_reminder_hook.py` and `plugins/security-guidance/hooks/patterns.py`):

```python
from security_reminder_hook import extract_content_from_input, check_patterns

# Original file content: "...prefix<A><B>suffix..."
# Simulate MultiEdit that: replaces <A> with "os.sy" and <B> with "stem(cmd)"
tool_input = {
    "edits": [
        {"old_string": "<A>", "new_string": "os.sy"},
        {"old_string": "<B>", "new_string": "stem(cmd)"},
    ]
}

checked_content = extract_content_from_input("MultiEdit", tool_input)
# checked_content == "os.sy stem(cmd)" -> space-joined
assert not check_patterns("evil.py", checked_content)  # no match reported (BUG demonstrated)

# Simulate the real file after MultiEdit applies substitutions sequentially,
# where <A> and <B> are contiguous in the original file with no separator:
original = "prefix<A><B>suffix"
after_edit1 = original.replace("<A>", "os.sy")
after_edit2 = after_edit1.replace("<B>", "stem(cmd)")
final_file_content = after_edit2  # "prefixos.systemstem(cmd)suffix" -> contains "os.system(" is wrong example;
# use old_strings adjacent so result is "os.system(cmd)" exactly:
# e.g. original = "prefix<A><B>suffix" with new_string1="os.sy", new_string2="stem(cmd)"
# final_file_content contains "os.system(cmd)" contiguous.

assert check_patterns("evil.py", final_file_content)  # real file DOES trigger os_system_injection
```

Expected assertions: `check_patterns` on the joined `extract_content_from_input` output returns no match for `os_system_injection`/`python_subprocess_shell`, while `check_patterns` on the actual reconstructed post-edit file content returns a match — demonstrating the detection/enforcement divergence.

```python
def extract_content_from_input(tool_name, tool_input):
    """Extract content to check from tool input based on tool type."""
    if tool_name == "Write":
        return tool_input.get("content", "")
    elif tool_name == "Edit":
        return tool_input.get("new_string", "")
    elif tool_name == "MultiEdit":
        edits = tool_input.get("edits", [])
        if edits:
            return " ".join(edit.get("new_string", "") for edit in edits)
        return ""
    return ""
```
