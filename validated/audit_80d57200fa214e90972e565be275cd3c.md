### Title
Unvalidated shared-address definitions let a paired correspondent register a spoofed "joint" address that grants the sender unilateral spending rights - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts an address definition and a `signers` map from any already-paired correspondent device and persists it as a `shared_addresses` entry that the receiving wallet will subsequently treat, watch, and display as *its own* jointly-controlled address, without ever verifying that spending from that definition actually requires the local user's key. This mirrors the Nextcloud CVE-2021-32654 root cause: a party is able to register itself into a "shared" resource (federated share / here, a shared wallet address) with a level of control the resource owner did not intend to grant, because the acceptance path only checks structural/format validity, not the substantive privilege the definition confers.

### Finding Description
`handleNewSharedAddress` (`wallet_defined_by_addresses.js:378-415`) performs only these checks on an incoming `new_shared_address` device message:
- the definition is a well-formed `[op, args]` array,
- `objectHash.getChash160(body.definition)` matches the claimed `body.address`,
- each `signers[path].address` is a syntactically valid address,
- each signing path in `signers` matches an `["address", …]` leaf actually present in the definition (`extractAddressPathsFromDefinition`, lines 339-375), and vice versa.

`determineIfIncludesMeAndRewriteDeviceAddress` (lines 281-315) only confirms that *one* of the referenced addresses belongs to the local wallet (`my_addresses` or `shared_addresses`); it does not verify that the local address is required by the boolean structure of the definition to authorize spending.

`validateAddressDefinition` (lines 520-528) merely calls `Definition.validateDefinition`, which checks that the oscript is syntactically/semantically legal (correct ops, valid pubkeys, etc.) — it enforces no policy about how many independent parties must cooperate to spend.

Because of this, a correspondent can send a definition such as:
```
["or", [["address","VICTIM_ADDR"], ["address","ATTACKER_ADDR"]]]
```
This passes every check: it is a valid definition, the chash matches, both signer entries match `["address", …]` leaves, and the victim's own address is referenced (satisfying `determineIfIncludesMeAndRewriteDeviceAddress`). `addNewSharedAddress` (lines 239-268) then silently inserts the address into `shared_addresses` / `shared_address_signing_paths`, fires `new_address` events, and (for light wallets) starts watching it — all without any user confirmation dialog in this code path. The wallet's UI/back end subsequently lists the attacker as a "cosigner" of what looks like a jointly controlled address (`readSharedAddressCosigners`, lines 592-606), while in reality the `or` branch lets the attacker alone author a valid payment unit spending any funds sent to that address — no cooperation or signature from the victim is required.

The result: an address the victim's own wallet database now classifies and displays as a shared/multi-party address (implying joint custody) can in fact be fully controlled by the sender alone, and the address is even auto-forwarded to the victim's other correspondents/cosigners (`forwardNewSharedAddressToCosignersOfMyMemberAddresses`, lines 317-336), propagating the illusion of shared custody across the trust network — analogous to the federated-share bug where accepting a share request granted privileges beyond what was actually verified.

### Impact Explanation
Any funds a user sends to (or receives at) an address that their own wallet believes is protected by joint/multi-signature custody can be swept unilaterally by the attacker, resulting in direct loss of funds (unauthorized spending / theft), which maps to "concrete unauthorized spending" in the validation criteria. Because the malicious definition is silently accepted and stored as first-class wallet state (not merely displayed), it also corrupts the victim's local view of which addresses require multi-party cooperation, which can influence downstream flows (e.g., prosaic/arbiter contracts or private-payment sharing) that rely on `shared_address_signing_paths` to reason about who must co-sign.

### Likelihood Explanation
The trigger requires only a paired correspondent device (in-scope actor per the rules) to send a single `new_shared_address` message — no special privileges, hub cooperation, or race conditions are needed. The check gating this message type only requires the sender to already be a "known correspondent" (`device.js` `arrSubjectsAllowedFromNoncorrespondents` gate is for *other* subjects, not `new_shared_address`), a status any private-payment counterparty or pairing partner routinely obtains. The lack of any semantic check on the definition (only structural validity) makes crafting the malicious `or` definition trivial.

### Recommendation
When accepting a `new_shared_address` message, in addition to the existing structural checks, enforce that every locally-owned address referenced in the definition (`assocMyMemberAddresses`) sits behind an `and`-type node that is unconditionally required for the definition to evaluate true — i.e., reject definitions where a local address can be bypassed by an alternative `or` branch that does not itself require the local address. At minimum, surface an explicit user-confirmation step (rather than silent `addNewSharedAddress`) before persisting any inbound shared address, showing the full definition and clearly indicating whether the counterparty can spend unilaterally.

### Proof of Concept
1. Device A (victim) and Device B (attacker) are paired correspondents (e.g., via a normal pairing/private-payment interaction).
2. Device B computes `arrDefinition = ["or", [["address", VICTIM_ADDR], ["address", ATTACKER_ADDR]]]` where `VICTIM_ADDR` is an address B has learned belongs to A (e.g., from a prior payment), and sends:
   ```
   device.sendMessageToDevice(A, "new_shared_address", {
     address: objectHash.getChash160(arrDefinition),
     definition: arrDefinition,
     signers: {
       "r.0": {address: VICTIM_ADDR, device_address: A_addr},
       "r.1": {address: ATTACKER_ADDR, device_address: B_addr}
     }
   });
   ```
3. On A's device, `handleNewSharedAddress` accepts this (definition well-formed, chash matches, `VICTIM_ADDR` known locally), `addNewSharedAddress` stores it, and A's wallet now lists this address as a "shared address" involving B as a cosigner.
4. A's wallet — believing it needs both parties or is otherwise a legitimate multisig — funds this address, or is instructed to receive payment there.
5. B alone constructs and signs a unit spending the funds via the `["address", ATTACKER_ADDR]` branch of the `or`, without any signature from A, and broadcasts it — resulting in complete, unilateral loss of the funds from A's perspective.

*Note:* I was unable to fully confirm from the indexed code whether any higher-level UI layer (outside the indexed files) imposes additional confirmation before crediting/debiting such addresses; the analysis above is based on the `ocore` core library logic shown in `wallet_defined_by_addresses.js`, `wallet.js`, and `device.js`. If a confirmation dialog exists exclusively in a GUI wallet layer not present in this repository, the practical exploitability may depend on that missing layer — a full audit of the calling wallet application would be needed to close this gap, which a Devin session with broader file access could investigate further.
