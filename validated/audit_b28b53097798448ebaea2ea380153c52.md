### Title
Webhook signature is verified against the org derived from `repository.owner.login`/`organization.login`, but the write target is looked up from the independent `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a delivery against using `repository_owner`, which is parsed from the payload's `repository.owner.login` (or `organization.login`) key. Every handler, however, resolves the repository/stack to act on using a completely different payload key: `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name`. Nothing ties these two fields together, so the organization whose secret authenticated the request is never required to match the repository that is actually written to.

### Finding Description
`verify_signature` computes the org used to fetch the correct `GitHubApp` (and thus the correct `webhook_secret`) purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

The HMAC only proves the raw body was signed by *some* configured org's secret, and the org used for that lookup is itself read from the body (`repository.owner.login`/`organization.login`). Once verification passes, `WebhooksController#create` dispatches the entire, unmodified payload to handlers: [3](#0-2) 

Every handler resolves its target repository/stack from a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

Shipit explicitly documents and supports multi-tenant configuration where distinct GitHub organizations each have their own `webhook_secret` in `config/secrets.yml`: [6](#0-5) 

Because the signing-org field (`repository.owner.login`/`organization.login`) and the acted-upon field (`repository.full_name`) are independent JSON keys inside the same signed payload, an org administrator who legitimately knows their own org's `webhook_secret` (set at GitHub App creation time, a value they configured themselves, not something requiring GitHub's private signing infrastructure) can craft an arbitrary payload: set `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` selects their own secret and `verify_webhook_signature` succeeds), while setting `repository.full_name` = a `owner/repo` belonging to an entirely different, unrelated org configured on the same Shipit instance. `Repository.from_github_repo_name` and the `push`/`pull_request` handlers will act on that unrelated stack, e.g. enqueuing `GithubSyncJob` / triggering `stack.sync_github` for a push event they have no authorization over.

This is exactly the binding break called out in scope: *"an organization that authenticated versus the repository that is written."* The signature only proves "signed by org X's secret"; it never proves "and X owns the repository this payload claims to describe."

### Impact Explanation
An attacker who administers one legitimate, Shipit-configured GitHub organization can forge webhook deliveries that are treated as authentic for any *other* organization's repositories/stacks hosted on the same Shipit instance, as long as they can guess or observe that org's `repository.full_name`. This lets them trigger unauthorized `GithubSyncJob` runs and, for stacks with `continuous_deployment` enabled, unauthorized deploy pipelines against a repository/stack that does not belong to them - satisfying the "unauthorized deploy" criterion for a High/Critical-impact cross-tenant authorization bypass in a multi-org Shipit deployment.

### Likelihood Explanation
Requires only a self-controlled, legitimately configured GitHub org/App on a multi-tenant Shipit instance (a scenario explicitly documented and supported), plus knowledge of the target org's `owner/repo` name, which is typically public. No GitHub App private key, no `ApiClient` token, and no privileged Shipit account is needed - only the attacker's own webhook secret, which they control. This is realistic wherever `docs/setup.md`'s multi-organization configuration is used.

### Recommendation
Bind the two fields together before dispatching to handlers: after selecting the `GitHubApp`/secret via `repository_owner`, verify that the resolved repository's owner (from `repository.full_name`, or from the `Repository` record looked up by `Handler#repository_name`) matches `repository_owner` used for signature verification, and reject (422) the delivery otherwise.

### Proof of Concept
1. Shipit is configured with two orgs in `config/secrets.yml`: `orgA` (attacker-controlled, webhook_secret known to attacker) and `orgB` (victim, with a tracked stack for `orgB/victim-repo`).
2. Attacker crafts a `push` payload JSON with `repository.owner.login` = `"orgA"` and `repository.full_name` = `"orgB/victim-repo"`, `ref`/`after` referencing an arbitrary commit.
3. Attacker computes `X-Hub-Signature` as `sha1=` + HMAC-SHA1 of the raw JSON body using `orgA`'s known `webhook_secret`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "orgA")` and `verify_webhook_signature` succeeds against the forged HMAC.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and enqueues `stack.sync_github` for `orgB`'s stack - an action the attacker was never authorized to trigger.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
