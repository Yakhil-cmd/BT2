### Title
Cross-org membership webhook binds attacker-owned organization's signature to a pre-existing Team via unchecked `github_id` lookup - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook using the organization named in the payload (`repository_owner`/`params.organization.login`), selecting the corresponding `GitHubApp` and its `webhook_secret`. `MembershipHandler#find_or_create_team!` then resolves the target `Team` purely by `github_id`, never checking that `params.organization.login` matches the found team's `organization` column, so a signature valid for OrgTwo can be used to add/remove membership on a Team row that belongs to a different organization (e.g. `shopify`).

### Finding Description
The broken binding: `organization_that_signed_the_request` (`repository_owner` resolved in `WebhooksController#repository_owner`, `app/controllers/shipit/webhooks_controller.rb:59-62`, used at line 25 to pick `Shipit.github(organization: repository_owner)`) should equal `organization_owning_the_mutated_team` (the `organization` column on the `Team` row mutated in `MembershipHandler#find_or_create_team!`). After tracing, they no longer match.

Path: For `membership` events there is no `repository` key in the payload, so `repository_owner` falls back to `params.dig('organization', 'login')` [1](#0-0) . `verify_signature` uses that value to fetch `Shipit.github(organization: repository_owner)` and verify the HMAC signature against that organization's own `webhook_secret` [2](#0-1) . If the attacker owns `OrgTwo` and legitimately configured it in `secrets.github` (per `Shipit.github_app_config`, `lib/shipit.rb:196-200`), they hold `OrgTwo`'s real `webhook_secret` and can produce a validly signed request for `organization.login: 'OrgTwo'`.

`MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g. a legitimate `shopify` team the attacker learned/guessed the GitHub team ID for), `find_or_create_by!` returns the existing record and the block (which sets `team.organization = params.organization.login`) is **not** executed — but critically, `params.organization.login` is never compared against `team.organization` even when the team is found rather than created. `process` then calls `team.add_member(member)` or `team.members.delete(member)` [4](#0-3) , mutating membership on the `shopify`-owned team using only OrgTwo's signature. This is a real authentication-binding failure: the "who signed this" and "whose resource is being mutated" checks are decoupled.

Existing guards that fail to prevent this: `verify_signature` only proves the request was signed by *some* configured org's secret — it says nothing about which org's *data* the payload is allowed to touch. `find_or_create_by!` in `find_or_create_team!` provides no cross-check between `params.organization.login` and an existing team's `organization`.

### Impact Explanation
An attacker who owns any organization configured under `secrets.github` can, once they learn or guess the GitHub numeric team ID (`github_id`) of a team belonging to a different, higher-privilege organization (e.g. `shopify`), add themselves (or any GitHub login) as a member of that team by sending a signed `membership` webhook from their own org. Since `Shipit.github_teams` and team-based `User#authorized?`/permission checks key off `Team` membership rather than which org the webhook came from, this is escalation into `Shipit.github_teams` authorization for a team the attacker does not own — matching the High/Critical impact category described (escalation into `Shipit.github_teams`). The action is repeatable against any `Team` row whose `github_id` the attacker can determine, across any number of tenants sharing the same Shipit instance's `secrets.github`.

### Likelihood Explanation
Preconditions: multi-org `secrets.github` configuration where the attacker legitimately controls one configured organization (and therefore its `webhook_secret`), and a target `Team` row already exists in the database with a known `github_id` belonging to a different organization. GitHub team IDs are not secret (visible via GitHub API/UI to team members, sometimes enumerable), so obtaining the target `github_id` is plausible but not guaranteed trivial for an outsider with zero access to the target org. Attacker cost is low once the `github_id` is known: a single signed HTTP POST. This is realistic in any Shipit deployment onboarding multiple GitHub organizations, which the engine explicitly supports.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after finding or creating the team, verify `team.organization == params.organization.login` (case-insensitively as appropriate) and raise/reject (e.g. respond 422 or drop the event) if it does not match, rather than silently operating on a team owned by a different organization. More generally, `WebhooksController` should validate that the organization used to select the signing secret matches the organization that owns any record being mutated by the handler, for every handler that accepts an `organization` payload without a `repository` context.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a new membership handler test):
1. Configure `Shipit.secrets.github` with two orgs: `shopify` (`webhook_secret: 'shopify_secret'`) and `OrgTwo` (`webhook_secret: 'orgtwo_secret'`).
2. Create a `shipit_teams(:legit)` fixture/`Team.create!(github_id: 999, organization: 'shopify', ...)`.
3. Build a `membership` payload: `{action: 'added', organization: {login: 'OrgTwo'}, team: {id: 999, name: 'x', slug: 'x', url: 'x'}, member: {login: 'attacker'}}`.
4. Sign the raw JSON body with `orgtwo_secret` (HMAC-SHA1, `X-Hub-Signature` header format `sha1=...`), set `X-Github-Event: membership`.
5. POST to `/webhooks`.
6. Assert response is `200`.
7. Assert equality check: before, `team.organization` (`'shopify'`) != `params.organization.login` (`'OrgTwo'`) — the binding is broken.
8. Assert `Shipit::Membership.exists?(team: team, user: User.find_by(login: 'attacker'))` is true.
9. Assert `Shipit.github_teams` (or equivalent authorization check using `shopify`'s team) now includes the attacker's team membership, demonstrating cross-org escalation with no live GitHub call required (signature verification is self-contained via `GitHubApp#verify_webhook_signature`).
