## Analysis

The Wekan CVE's root cause is: the server trusts an *external, attacker-suppliable identity claim* (OIDC email/username) and unconditionally merges it into an existing trusted identity, without any cryptographic proof of ownership. The closest reachable analog in `ocore` is in the wallet/device correspondent-trust model, which is reachable by any paired device or by a device merely *introduced* as a cosigner.

### Title
Disabled trust check lets an indirectly-introduced (non-pairing-verified) device be treated as a fully-trusted wallet correspondent - (File: `wallet.js`, `device.js`)

### Summary
`device.js`'s `addIndirectCorrespondents` inserts a `correspondent_devices` row for a device based solely on a `device_address`/`pubkey`/`hub`/`name` tuple *reported by an already-paired peer* (e.g. as "other cosigners" of a shared wallet), with no pairing-secret exchange or other proof that the operator behind that device actually intended a trust relationship with the recipient. This is the ocore analog of trusting an unverified external identity claim. Once inserted, `device.js`'s `handleJustsaying` treats any signed message from that `device_address` as coming from a "known correspondent" (`device.js:204-221`), bypassing the restrictive whitelist (`pairing`, `my_xpubkey`, `wallet_fully_approved`) normally applied to unknown devices. The remaining safety net — a check in `wallet.js` meant to restrict which message `subject`s can be trusted from such indirectly-introduced correspondents — is commented out.

### Finding Description
`addIndirectCorrespondents` blindly inserts a correspondent record supplied by a third party: [1](#0-0) 

This makes an attacker-controlled device address a "known" correspondent (`is_indirect=1`) without ever exchanging a `pairing_secret` with it directly, i.e., without the victim ever verifying that this device is who the introducer claims.

Normally, unknown correspondents are restricted to a narrow safe subject whitelist: [2](#0-1) 

But once inserted via `addIndirectCorrespondents`, the device is in the "known" branch, and the only remaining restriction meant to keep indirectly-introduced correspondents constrained is disabled: [3](#0-2) 

With that check disabled, an attacker who is merely *mentioned* as a co-signer device by a legitimate paired party (during shared/multisig wallet setup) can freely send any wallet-protocol `subject`, including `sign`, `create_new_shared_address`, `approve_new_shared_address`, `new_shared_address`, and `removed_paired_device`, and have them processed as if from a trusted correspondent: [4](#0-3) 

Critically, `wallet_defined_by_addresses.js`'s handling of `new_shared_address` only validates that the given `definition` hashes to the claimed `address` and that per-path addresses are internally consistent with the definition — it does **not** cryptographically verify that the `device_address` claimed for a given signing path is actually controlled by the party that owns that path's key: [5](#0-4) [6](#0-5) 

Because `shared_address_signing_paths` uses `INSERT OR IGNORE` keyed on `(shared_address, signing_path)`, whichever party's message is processed **first** for a given signing path wins and determines where future signing requests for that path are routed (see `findAddress`'s `ifRemote` routing in `wallet.js:1233-1316` and the `sign` message's `ifRemote` proxy trust at `wallet.js:374-392`). An indirectly-introduced attacker device — now fully trusted due to the disabled check — can race to deliver a spoofed `new_shared_address` message claiming to be the device holding a cosigner's key for a shared/multisig address the victim is about to fund, hijacking the signing-request routing for that path before the legitimate cosigner's message arrives.

### Impact Explanation
This breaks the intended trust boundary between "cryptographically paired correspondent" and "device merely mentioned by a third party." It allows an unprivileged device — never directly paired with the victim — to be escalated to full wallet-protocol trust and to inject itself as the routing target for multisig signing requests on a shared address the victim is establishing. This can result in denial of signing (funds frozen in an unusable shared address) or interception/manipulation of the signing negotiation for a multisig payment, i.e., AA/wallet fund loss or freezing consistent with the required impact bar.

### Likelihood Explanation
Exploitation requires the attacker to be named as a purported "other cosigner" in a legitimate multisig/shared-wallet setup flow that calls `addIndirectCorrespondents` (or otherwise get itself introduced this way), and to win a race to deliver a spoofed `new_shared_address` message before the real cosigner's device does. This requires some social/protocol positioning but no cryptographic secret and no direct pairing with the victim, which is a materially lower bar than a fully paired attacker.

### Recommendation
Re-enable and correctly scope the indirect-correspondent subject whitelist in `wallet.js` (the commented-out check at lines 92-93), and additionally require that `shared_address_signing_paths` entries for a given `(shared_address, signing_path)` can only be set/updated by a device that has independently completed direct pairing (i.e., is not `is_indirect`), or bind device_address claims to a verifiable proof of association with the signing key before honoring routing changes.

### Proof of Concept
1. Victim device V is a paired correspondent of legitimate device L. L is setting up a multisig shared address with V and reports another purported cosigner device via `addIndirectCorrespondents`, using a device_address/pubkey/hub controlled by attacker A (`device.js:906-919`); V now has A in `correspondent_devices` with `is_indirect=1`.
2. Because the check at `wallet.js:92-93` is disabled, V will process *any* subject from A, not just the safe whitelist.
3. A crafts and sends a `new_shared_address` message to V (`wallet.js:236-245` → `wallet_defined_by_addresses.js:378-415`) describing the real shared-address definition (public knowledge from the coordination) but substituting itself as `device_address` for the legitimate cosigner's signing path.
4. Because `shared_address_signing_paths` insertion is `INSERT OR IGNORE` on first-arrival, if A's message reaches V before the legitimate cosigner's message, V will route future signing requests for that path to A instead of the legitimate cosigner, disrupting or hijacking the multisig signing flow for the shared address.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
