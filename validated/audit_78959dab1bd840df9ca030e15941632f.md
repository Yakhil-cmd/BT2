### Title
`DenyReserveTransferToRelayChain` (non-recursive) allows reserve-asset deposit to Relay Chain to bypass the deny-filter when nested in `SetAppendix`/`SetErrorHandler` - ([File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs])

### Summary
Asset Hub Polkadot's `Barrier` wraps the bare `DenyReserveTransferToRelayChain` filter instead of the `DenyRecursively<DenyReserveTransferToRelayChain>` wrapper that Parity itself introduced and already applies on `bridge-hub-polkadot` and `bulletin-polkadot` in this same codebase. Because the plain filter only inspects the top-level instruction slice passed to `Barrier::should_execute`, a `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting `Location::parent()` nested inside a `SetAppendix`/`SetErrorHandler` sub-program is invisible to the matcher and is executed later without ever going through a fresh barrier check. [1](#0-0) [2](#0-1) 

### Finding Description
`asset-hub-polkadot`'s `Barrier` is defined as:
```
DenyThenTry<DenyReserveTransferToRelayChain, (...)>
``` [3](#0-2) 

Its `use xcm_builder::{...}` import list explicitly pulls in `DenyReserveTransferToRelayChain` but **not** `DenyRecursively`. [2](#0-1) 

Compare this to `bridge-hub-polkadot` and `bulletin-polkadot` in the same repo, which explicitly wrap the same filter with `DenyRecursively<DenyReserveTransferToRelayChain>`: [4](#0-3) [5](#0-4) 

The upstream `DenyReserveTransferToRelayChain::should_execute` walks only the flat `&mut [Instruction<RuntimeCall>]` slice given to it via a matcher (`match_next_inst_while`); it does not descend into the `Xcm` payload carried inside `SetAppendix(Xcm)` or `SetErrorHandler(Xcm)` instructions. `DenyRecursively` was created upstream precisely to close this gap by also inspecting these embedded sub-programs. Because Asset Hub Polkadot omits `DenyRecursively`, a message such as:
```
SetAppendix(Xcm(vec![DepositReserveAsset { dest: Location::parent(), .. }]))
<top-level instruction(s) that satisfy TakeWeightCredit/AllowTopLevelPaidExecutionFrom, etc.>
```
passes the deny-filter stage (the deny check never even sees the reserve-deposit-to-parent instruction) and is then admitted by the allow-list barriers on its own top-level merits (e.g. `AllowTopLevelPaidExecutionFrom<Everything>` for a paying account). The xcm-executor runs the appendix at the end of message processing within the same `execute_xcm` invocation, without invoking `Barrier::should_execute` again — so the deferred `DepositReserveAsset { dest: Parent, .. }` executes unchecked.

An unprivileged, signed account can reach this path via `pallet_xcm::execute`, whose origin is converted via `EnsureXcmOrigin<_, LocalSignedOriginToLocation>`, letting any signed account submit an arbitrary XCM program for local execution through `XcmExecutor<XcmConfig>`, which uses this same `Barrier`.

### Impact Explanation
This lets a normal signed user perform a functionally-equivalent "reserve transfer of DOT to the Relay Chain" that the runtime's deny-filter was explicitly designed to block. Since DOT's reserve/teleport accounting between AssetHub and the Relay Chain is intentionally restricted to teleport-only flows, forcing a reserve-style deposit to the Relay Chain risks broken/duplicated asset accounting (the Relay Chain does not recognize AssetHub as a reserve for DOT), which maps to the "user-controlled assets must remain fully backed" invariant. The scoped impact matches the question: an explicitly-disallowed DOT reserve-transfer path to the Relay Chain becomes reachable by an unprivileged local `execute()` call.

### Likelihood Explanation
Feasible and repeatable with only a signed account and no special privileges: `pallet_xcm::execute` is a standard user-facing extrinsic, and the barrier gap is a pure logic/structural omission (missing `DenyRecursively`) that will trigger deterministically for any correctly-constructed nested XCM, not a probabilistic race. The only precondition is that the outer program still needs to pass one of the allow-list barriers (e.g., `AllowTopLevelPaidExecutionFrom<Everything>` by paying fees), which any user can satisfy.

### Recommendation
Wrap the deny-filter on Asset Hub Polkadot (and Asset Hub Kusama, Collectives, Coretime, People — all of which show the same bare `DenyReserveTransferToRelayChain` pattern in this codebase) with `DenyRecursively<DenyReserveTransferToRelayChain>`, matching the fix already applied to `bridge-hub-polkadot`/`bulletin-polkadot`:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        (...)
    >,
>;
```

### Proof of Concept
xcm-emulator / integration test plan:
1. Build an XCM program for local execution via `pallet_xcm::execute` from a funded signed account on Asset Hub Polkadot:
   ```rust
   let xcm = Xcm(vec![
       WithdrawAsset(fee.clone().into()),
       BuyExecution { fees: fee, weight_limit: Unlimited },
       SetAppendix(Xcm(vec![
           DepositReserveAsset {
               assets: All.into(),
               dest: Location::parent(),
               xcm: Xcm(vec![]),
           },
       ])),
       // trivial top-level instruction, e.g. ClearOrigin
   ]);
   ```
2. Call `PolkadotXcm::execute(RuntimeOrigin::signed(user), Box::new(VersionedXcm::V4(xcm)), max_weight)`.
3. Assert: with current code (no `DenyRecursively`), `Barrier::should_execute` on the top-level instructions returns `Ok(())` (deny-filter does not flag it), and the appendix's `DepositReserveAsset { dest: Parent, .. }` executes, moving the asset toward the Relay Chain reserve path — i.e. `Outcome::Complete`/`Outcome::Incomplete` (not an `Outcome::Error(ProcessMessageError::Unsupported)` immediately at barrier stage).
4. After applying the recommended fix (`DenyRecursively<DenyReserveTransferToRelayChain>`), re-run the same test and assert `Barrier::should_execute` rejects the message (`ProcessMessageError::Unsupported`) because the recursive filter now inspects the `SetAppendix` payload.
