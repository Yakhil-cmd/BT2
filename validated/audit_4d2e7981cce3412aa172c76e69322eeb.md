### Title
Missing slippage/minimum-output check in `snowbridge-pallet-system-frontend::add_tip` enables sandwich attack on tip-to-Ether swap - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
The Snowbridge `system-frontend` pallet's public `add_tip` extrinsic swaps a user-supplied tip asset for Ether through `pallet_asset_conversion`'s on-chain AMM, but explicitly passes `None` for `amount_out_min`, disabling any minimum-output protection. This is structurally the same missing-guard class as the reported M-8 issue (a token-selling swap performed without meaningful slippage protection, exploitable via sandwich attack), even though the specific mechanism here is a missing minimum-output check rather than a `deadline` parameter.

### Finding Description
`add_tip` is a signed, permissionless extrinsic: [1](#0-0) 

It calls `swap_fee_asset_and_burn`, which for any tip asset other than Ether calls `swap_and_burn`: [2](#0-1) 

`swap_and_burn` invokes `T::Swap::swap_exact_tokens_for_tokens` with the `amount_out_min` argument hard-coded to `None`, with an explicit comment confirming the intent to skip minimum-amount enforcement: [3](#0-2) 

`T::Swap` is configured as `pallet_asset_conversion::Swap`, whose `swap_exact_tokens_for_tokens` treats `amount_out_min: None` as "no floor enforced" — the swap executes at whatever price the pool has at execution time: [4](#0-3) [5](#0-4) 

The underlying AMM pools (`create_pool`, `add_liquidity`, `swap_exact_tokens_for_tokens`, etc.) are permissionless — any signed account can create pools and perform swaps that move the price: [6](#0-5) 

This pallet is wired into a production runtime (AssetHub Westend's bridge-to-Ethereum configuration references this pallet and a `Swap` type), not just a test mock: [7](#0-6) 

Root cause mapping to the reported bug class: the original report's core violated invariant is "a swap that converts a reward/fee token to another asset must be protected against price manipulation between quote-time and execution-time." Uniswap's `exactInput` provides two knobs for this: `amountOutMinimum` and `deadline`. `Swap.swapTokensMulti` set `deadline` to `block.timestamp` (a no-op) but still kept `amountOutMinimum`, so the residual risk was a *stale* min-out threshold from momentary mempool delay. In this Polkadot SDK analog, the situation is more severe: `add_tip`'s call site drops the minimum-out protection entirely (`None`), so there is no floor at all — an attacker who observes `add_tip` pending inclusion can sandwich the swap by manipulating the `tip_asset`/Ether pool's reserves immediately before and after the victim's extrinsic is included in the same or an adjacent block, extracting the price impact as MEV profit and leaving the tip payer with far less Ether than the tip amount implies.

### Impact Explanation
The Ether obtained from the swap is teleported/burned as the relayer tip amount reported to BridgeHub (`ether_gained`) used in `AddTip`/`RegisterToken` calls. If the swap executes at an attacker-manipulated price, the resulting tip credited toward message relay incentives is diminished versus what the user intended to pay, while the difference is captured by the sandwiching attacker rather than benefiting the protocol, relayers, or the tipping user. This is analogous to "gamers/depositors receiving less yield than expected" in the original report, translated to "relayers/bridge messages receiving less tip value than intended, with value leaking to a MEV attacker." The severity is bounded by the size of the tip/registration fee and the depth of the specific AMM pool, and is a value-leakage/economic issue rather than unbacked issuance or unauthorized dispatch.

### Likelihood Explanation
Any account can call `add_tip` (it is a plain signed extrinsic with no privileged origin) and any account can create/manipulate a `pallet_asset_conversion` pool for the tip asset / Ether pair via ordinary signed `add_liquidity`/`swap_*` calls, since these are permissionless. Executing a sandwich requires only the ability to submit transactions before and after the victim's `add_tip` call within the same block-production window, which is achievable by any network participant without validator/collator privilege, matching the attacker model constraints (no privileged role required).

### Recommendation
- In `swap_and_burn` (`bridges/snowbridge/pallets/system-frontend/src/lib.rs`), do not pass `None` for `amount_out_min`. Compute a reasonable minimum output using `QuotePrice::quote_price_exact_tokens_for_tokens` (already available on `pallet_asset_conversion`) at call time, and apply a caller- or protocol-configurable slippage tolerance.
- Alternatively/additionally, expose an `amount_out_min` (or slippage-tolerance) parameter on the `add_tip`/`register_token` extrinsics so callers can protect themselves the way Uniswap-style AMM front-ends do.
- Consider guarding against unbounded price impact for thinly-liquid tip-asset pools, e.g., by rejecting swaps whose price impact exceeds a configurable bound.

### Proof of Concept
No executable PoC was run against a live network or test harness in this session (out of scope for this analysis tool). The reachability and missing-guard claim is demonstrated via static code evidence:
1. `add_tip` is a public signed extrinsic with no privileged origin check (`ensure_signed(origin)?`).
2. It unconditionally reaches `swap_and_burn`, which calls `AssetConversion::swap_exact_tokens_for_tokens(..., None, ...)`, explicitly disabling the `amount_out_min` guard (comment: "No minimum amount required").
3. `pallet_asset_conversion` pools are permissionless to create and to trade against, so an attacker can move the pool price arbitrarily around the victim's transaction inclusion (front-run/back-run), i.e., a classic sandwich, since no floor price is enforced on the victim's swap.
4. The pallet is wired into a real runtime config path (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/bridge_to_ethereum_config.rs` references this pallet's `Swap` type), indicating production reachability rather than a test-only or mock-only artifact.

A full reproduction would require constructing a local FRAME test (using the existing `bridges/snowbridge/pallets/system-frontend` test harness plus a real `pallet_asset_conversion` `Swap` implementation instead of the `SwapExecutor` test double) that: creates a pool, adds liquidity, submits `add_tip`, and in the same block executes a counter-swap before/after to demonstrate reduced `ether_gained` versus the pre-manipulation quote. This reproduction was not executed in this session; only static-code evidence of the missing guard and its permissionless reachability is provided here.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
