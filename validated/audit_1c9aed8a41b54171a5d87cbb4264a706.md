### Title
Cross-organization Team hijack via `github_id` reuse in `MembershipHandler#find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
In a multi-organization Shipit deployment, `MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, ignoring the `organization` field on any existing record. An attacker who administers one onboarded GitHub organization (org A) can sign a `membership` webhook with their own valid `webhook_secret`, set `team.id` to the `github_id` of a `Team` that legitimately belongs to a different onboarded organization (org B), and get themselves added as a member of org B's team, which can be part of `Shipit.github_teams`.

### Finding Description
The broken binding: the organization that authenticates the request via `verify_signature` must equal the organization that actually administers the `Team` row identified by `params.team.id`. Concretely, this should hold: `params.organization.login == team.organization` for the `Team` row mutated by the handler. The code never checks this.

Path:
1. `app/controllers/shipit/webhooks_controller.rb#verify_signature` derives the signing organization as `repository_owner`, which for a `membership` event (no top-level `repository` key) falls back to `params.dig('organization', 'login')` [1](#0-0) . It then verifies the signature with `Shipit.github(organization: repository_owner)`, i.e. against org A's own configured `webhook_secret` [2](#0-1) . Because org A is a legitimately onboarded org (per `docs/setup.md`'s "Using Multiple Github Applications" model), its administrator legitimately possesses/controls that secret and can produce a valid signature for any payload whose `organization.login == "orgA"`.
2. `MembershipHandler#find_or_create_team!` resolves the target `Team` purely via `Team.find_or_create_by!(github_id: params.team.id)`; the block setting `team.organization = params.organization.login` only executes on record creation [3](#0-2) . If a `Team` with that `github_id` already exists (created earlier for org B), the existing record — still owned by org B — is returned unchanged, and `params.organization.login` (org A) is silently discarded.
3. `MembershipHandler#process` then calls `team.add_member(member)` with `member` built from attacker-controlled `params.member.login` [4](#0-3) , and `Team#add_member` unconditionally appends the member [5](#0-4) .

Exploit request: attacker signs a JSON POST to `/webhooks` with header `X-Github-Event: membership`, HMAC-SHA1 signature computed using org A's `webhook_secret`, and body: `action: "added"`, `organization.login: "orgA"`, `team: { id: <org-B-team-github_id>, name, slug, url }`, `member.login: "attacker-login"`. `verify_signature` succeeds (org A's secret matches org A's login in the payload), `find_or_create_team!` fetches org B's pre-existing `Team` row by `github_id`, and `add_member` inserts a `Membership` granting the attacker membership in org B's team.

Why existing guards fail: `verify_signature` only proves "this payload was signed by the organization named in the payload" — it never proves "the organization named in the payload is the one that administers the referenced team". `ExplicitParameters` schema on `MembershipHandler` only validates types/presence, not cross-referential ownership. No model validation or handler code compares `params.organization.login` to the existing `team.organization`.

### Impact Explanation
If the targeted `Team` is one of `Shipit.github_teams` (used by `force_github_authentication`/`current_user.authorized?` to gate access to the entire Shipit application) [6](#0-5) , the attacker gains authenticated access to the Shipit instance as if they were a member of that authorized team, without any GitHub org B credentials. This is repeatable against any organization pair the Shipit instance has onboarded, provided the target team's `github_id` is known/guessable, and grants persistent access (a `Membership` row) rather than a one-shot effect. This matches the "High — escalation into `Shipit.github_teams` authorization" category.

### Likelihood Explanation
Preconditions: Shipit must be configured for multiple GitHub organizations (per `docs/setup.md`, top-level keys per org, each with its own `webhook_secret`), and the attacker must administer/own one such onboarded org (org A), which the threat model in this question treats as attacker-controlled. The attacker also needs the numeric `github_id` of the target team in org B — GitHub team IDs are small sequential integers and can often be discovered via GitHub's API/UI depending on team visibility, and once org B's team has been synced into Shipit once (creating the `Team` row), its `github_id` is fixed and reusable indefinitely. No Shipit session, API token, or org B secret is required. This is a low-cost, repeatable attack once org A onboarding exists.

### Recommendation
In `find_or_create_team!`, validate that any existing `Team` found by `github_id` belongs to `params.organization.login`; if it belongs to a different organization, reject the event (raise/log and drop) rather than silently reusing the record. Additionally, scope the lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and treat a `github_id` collision across organizations as an integrity error rather than a match.

### Proof of Concept
Minitest plan (fixtures/multi-org config):
1. Configure two orgs in test secrets: `orga` (attacker-owned) with `webhook_secret: "secretA"`, and `orgb` with `webhook_secret: "secretB"`.
2. Create fixture `Team` `shipit_teams(:orgb_admins)` with `organization: "orgb"`, `github_id: 999`, included in `Shipit.github_teams` stub.
3. Build a `membership` payload: `{ action: "added", organization: { login: "orga" }, team: { id: 999, name: "Admins", slug: "admins", url: "https://api.github.com/teams/999" }, member: { login: "attacker" } }`.to_json.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "secretA", payload)`.
5. POST to `/webhooks` with `X-Github-Event: membership` and `X-Hub-Signature: signature`.
6. Assert response is `:ok` (signature verification against org A succeeded).
7. Assert `Team.count` unchanged (no new team created — `find_or_create_by!` matched existing org B team by `github_id`).
8. Assert `shipit_teams(:orgb_admins).reload.members.map(&:login)` includes `"attacker"` — proving `params.organization.login` ("orga") != `team.organization` ("orgb") yet the membership was still written, confirming the binding is broken.
