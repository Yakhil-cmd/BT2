### Title
Cross-repository commit-status forgery via unscoped SHA lookup — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
This is a valid analog of the "boundary that should be enforced is bypassed for an edge-case input" bug class from M-4. In Perennial, the code assumed a price could never legitimately equal zero, so no check enforced the implicit invariant, and a division succeeded on attacker-influenced input that should have been rejected. In Shipit, `StatusHandler` assumes every commit SHA is unique across the whole installation, so it never checks that the *organization that authenticated the webhook* is the same as the *repository the resulting write applies to* — an invariant that other handlers (`PushHandler`, `CheckSuiteHandler`) do enforce via `stacks`.

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization that owns the `repository`/`organization` payload key: [1](#0-0) [2](#0-1) 

All other handlers derive the affected `Stack`s from the same payload's `repository.full_name`, so the entity that is authenticated (the organization owning that repository) is always the same entity whose data gets written: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, breaks this equality. It looks up commits **globally by SHA**, with no repository/stack scoping at all: [6](#0-5) 

The equality that should hold is:
`organization authenticated by verify_signature (repository_owner) == repository that owns the Commit row being mutated`

For `StatusHandler` this equality is never checked — any organization whose webhook signature verifies can write a `CommitStatus` onto **any** `Commit` record in the database that happens to share the same 40-hex SHA, regardless of which repository/stack that commit actually belongs to.

Git commit SHAs are content-addressed, not repository-scoped: a fork of a repository (a completely ordinary, unprivileged GitHub action) shares identical SHAs with its upstream for every commit up to the point of divergence. Any trusted organization in this Shipit install that has its own webhook secret configured (`config/secrets.yml` supports multiple orgs, e.g. `somegithuborg`/`someothergithuborg`) can therefore forge a `status` event for a SHA that also exists in a different org's tracked stack, and `StatusHandler` will happily attach that status to the victim's commit.

### Impact Explanation
`CommitStatus` records feed into deploy-safety gating (`ci.require` / `required_statuses`) that decides whether a commit is deployable: [7](#0-6) 

By forging a fake "success" status on a shared-SHA commit that belongs to an unrelated stack, an unprivileged attacker (who only needs push access to a *fork* of the target repo, or any repo whose org is registered in this Shipit instance) can satisfy CI requirements for a commit they never actually validated, enabling an unauthorized deploy of that commit in the victim's stack — this is a cross-repository write of security-relevant state, matching the report's Critical "cross-repository writes / unauthorized deploy" category.

### Likelihood Explanation
Requires only: (1) the attacker controls, or has push/CI-trigger rights on, a repository that shares commit history with the victim's tracked repository (trivially achieved via a public GitHub fork) and (2) that repository's owning organization is one of the organizations configured in this Shipit instance (a realistic condition for any multi-tenant/internal Shipit deployment tracking many repos/orgs). No token, session, or privileged GitHub role is needed — only an ordinary GitHub `status` webhook from a legitimately-configured org.

### Recommendation
Scope the commit lookup in `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict to commits belonging to `stacks` derived from `payload.dig('repository', 'full_name')`, e.g. `Commit.where(sha: params.sha, stack: stacks)`, so the authenticated repository/organization must equal the repository being written.

### Proof of Concept
1. Attacker forks a public repository that is tracked by Shipit as `victim-org/app` (stack `victim-org/app`), and pushes their fork under `attacker-org/app`, which is also a trusted organization in this Shipit instance's `secrets.yml`.
2. Both `victim-org/app` and `attacker-org/app` share commit `abc123...` (pre-fork history).
3. Attacker's CI (or attacker manually via API) posts a GitHub `status` event for `attacker-org/app` referencing SHA `abc123...` with `state: success` and a required CI context name.
4. `WebhooksController#verify_signature` validates the HMAC using `attacker-org`'s legitimate webhook secret — signature check passes.
5. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which matches **both** the attacker's own commit row and the victim's identical-SHA commit row in `victim-org/app`'s stack, and calls `create_status_from_github!` on all of them.
6. The victim's commit now has a forged "success" status for a required CI context it never actually passed, potentially unblocking merge/deploy for that commit in `victim-org/app`.
