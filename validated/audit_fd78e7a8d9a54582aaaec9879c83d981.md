## Finding: Deploy → Rollback Env-Variable Whitelist Bypass on Abort - (File: app/models/shipit/deploy.rb)

### Summary
The bug-class analog to the token-bridge "check one thing, act on something else" flaw is a whitelist bypass in Shipit's deploy/rollback environment-variable filtering. Deploy env vars are validated against `deploy_variables`, but when a deploy is aborted with `rollback_once_aborted: true`, the *already-validated-for-deploy* environment hash is forwarded verbatim into the automatically-created `Rollback`, bypassing `filter_rollback_envs` (validation against `rollback_variables`) entirely.

### Finding Description
Normal, user-facing rollback creation paths filter the caller-supplied `env` against the `rollback_variables` whitelist declared in `shipit.yml`, using `Shipit::EnvironmentVariables#permit`: [1](#0-0)  and this filtering is confirmed to run in the web `RollbacksController` path (`":create ignore :env keys not declared in the deploy spec"`): [2](#0-1) .

However, the internal automatic-rollback path used by `Deploy#build_rollback` and `Deploy#trigger_revert` never calls `filter_rollback_envs`. `build_rollback` assigns `env: env.to_h` directly onto the new `Rollback`: [3](#0-2) , and `trigger_revert` similarly assigns `env: env || self.env` straight onto `Rollback.create!` with no permission/whitelist check: [4](#0-3) .

The `env` forwarded here is `self.env` on the `Deploy` — a hash that was only ever validated against `deploy_variables` at creation time via `Stack#build_deploy`, which calls `filter_deploy_envs(env.to_h)` (validated against `deploy_variables`, not `rollback_variables`): [5](#0-4) . `deploy_variables` and `rollback_variables` are configured independently in `shipit.yml` and can differ (`rollback_variables` only falls back to `deploy_variables` when unset): [6](#0-5) .

This is confirmed by test behavior: a `Deploy` with `env = { 'CUSTOM_VAR' => 'value' }` that is `abort!`-ed with `rollback_once_aborted: true` produces a `Rollback` whose `.env` is `{ 'CUSTOM_VAR' => 'value' }` verbatim, with no re-validation against rollback's own whitelist: [7](#0-6) .

Once assigned to the task record, this `env` hash is merged unfiltered directly into the shell environment used to execute the rollback script: [8](#0-7) .

**The broken binding (as an equality):**
`env_keys_permitted_for(deploy) == env_keys_spawned_in(rollback_process)`

Before: the deploy path enforces `env_keys ⊆ deploy_variables`; the rollback execution path is supposed to separately enforce `env_keys ⊆ rollback_variables`.
After abort-triggered auto-rollback: `env_keys_spawned_in(rollback_process) = env_keys_permitted_for(deploy)`, i.e. the rollback shell environment inherits deploy's whitelist instead of its own, whenever the two whitelists diverge.

### Impact Explanation
If a `shipit.yml` intentionally declares a **narrower** `rollback.variables` list than `deploy.variables` (e.g., to prevent a dangerous flag like `SKIP_SAFETY_CHECKS` or a destructive migration toggle from being settable during rollback, while allowing it during forward deploys, or vice versa), a user who only has permission to trigger deploys can set that variable on a deploy, abort the deploy with `rollback_once_aborted: true`, and have that variable injected into the rollback shell command — even though the operator explicitly excluded it from `rollback.variables`. Since deploy/rollback scripts run arbitrary shell commands defined in `shipit.yml` with these variables interpolated into the environment, this can escalate into command/behavior changes the rollback-specific whitelist was designed to prevent, effectively bypassing an operator-defined execution-time authorization boundary.

### Likelihood Explanation
The abort-with-rollback flow is a standard, easily reachable feature (`Deploy#abort!(rollback_once_aborted: true)`), triggerable by any user/API client holding ordinary `deploy:stack` permission — no elevated privileges, webhook secrets, or GitHub App credentials are required. Exploitation only requires that the target stack's `shipit.yml` defines differing `deploy.variables` and `rollback.variables` lists, which is an explicitly documented, supported configuration pattern.

### Recommendation
Route the environment hash carried from an aborted `Deploy` into its automatic `Rollback` through `filter_rollback_envs` (i.e., `stack.filter_rollback_envs(self.env)`) in both `Deploy#build_rollback` and `Deploy#trigger_revert`, mirroring the filtering already performed by the `RollbacksController` create path, so that rollback execution always re-validates env keys against `rollback_variables` regardless of how the rollback was initiated.

### Proof of Concept
1. Configure `shipit.yml` with:
```yaml
deploy:
  variables:
    - name: DANGEROUS_FLAG
rollback:
  variables: []   # explicitly disallow DANGEROUS_FLAG during rollback
```
2. As a user/API client with only `deploy:stack` permission, trigger a deploy with `env: { DANGEROUS_FLAG: '1' }` (permitted, since it's in `deploy.variables`).
3. Abort that deploy with `rollback_once_aborted: true` (e.g. `Deploy#abort!(rollback_once_aborted: true, aborted_by: user)`), as exercised in [7](#0-6) .
4. The resulting `Rollback` record's `.env` still contains `DANGEROUS_FLAG => '1'`, and `TaskCommands#env` merges it unfiltered into the rollback script's shell environment [8](#0-7) , even though `rollback.variables` forbids it.

      rollback = Rollback.create!(
        user_id:,
        stack_id:,
        parent_id: id,
        since_commit: until_commit,
        until_commit: previous_successful_commit,
        env: env || self.env,
        allow_concurrency: force
      )

      rollback.enqueue
      lock_reason = "A rollback for #{until_commit.sha} has been triggered. " \
        "Please make sure the reason for the rollback has been addressed before deploying again."
      stack.update!(lock_reason:, lock_author_id: user_id)
      stack.emit_lock_hooks
      rollback
    end
