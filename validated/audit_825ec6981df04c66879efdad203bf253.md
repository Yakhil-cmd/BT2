### Title
Arbiter contract dispute/appeal flow leaks the permanent device pairing secret to the arbiter's HTTP service - ([File: arbiter_contract.js])

### Summary
The permanent pairing secret used to authenticate new device pairings (`device.js: getOrGeneratePermanentPairingInfo`) is embedded in the `my_pairing_code` field that `arbiter_contract.js` stores on a contract when the user accepts it, and this same field is later transmitted in cleartext JSON to the third‑party arbstore HTTP endpoint whenever a dispute or appeal is opened. This mirrors the OpenClaw advisory pattern (CWE‑345): a value that must stay confidential to preserve an authentication guarantee is reused for, and exposed through, an unrelated channel that was never meant to carry it.

### Finding Description
`device.getOrGeneratePermanentPairingInfo()` generates (once) and persists a long‑lived (`expiry_date='2038-01-01'`), reusable `pairing_secret`: [1](#0-0) 

Anyone who presents this secret over the wallet's normal pairing protocol is accepted as a *confirmed* correspondent device, without any further proof of identity: [2](#0-1) 

When a user accepts an arbiter contract, `respond()` builds `my_pairing_code = device_pubkey@hub#pairing_secret` from this permanent secret and stores it on the contract row (`my_pairing_code` column): [3](#0-2) 

Later, when the user opens a dispute or files an appeal, this exact stored `objContract.my_pairing_code` (i.e., the permanent pairing secret) is placed into a plain JSON body and POSTed to the externally hosted arbstore's `/api/dispute/new` and `/api/appeal/new` HTTP endpoints: [4](#0-3) [5](#0-4) 

Note that a fresh, local `pairing_code`/`my_pairing_code` variable is computed just above each of these blocks but is never used — the code sends the previously‑stored, permanent secret instead, which is the same secret that must remain confidential to protect the pairing trust model. The arbiter/arbstore does not need this secret at all: it already receives the party's `device_pub_key` via `arbiters.getInfo`/`arbiters.getArbstoreInfo` for encrypting messages (`device.createEncryptedPackage(..., objArbiter.device_pub_key)`), so transmitting the pairing secret provides no functional benefit and only exists as leftover/incidental data.

### Impact Explanation
The `pairing_secret` sent here is not a per‑session, single‑use, or contract‑scoped credential — it is the wallet's single permanent pairing secret, valid until 2038 and reusable to pair with *any* number of peers. Anyone who obtains it (the arbstore operator, anyone with server/log access to the arbstore, or anyone who can observe the request) can subsequently send a `pairing` device message using that secret and be silently added as a fully `is_confirmed=1` correspondent of the victim's wallet, indistinguishable from a device the victim intentionally paired with. Because this permanent secret is shared with every arbiter the user ever disputes or appeals with, it converts a single semi-trusted, one-time interaction into a durable device-wide trust weakness. A holder of the leaked secret can then leverage the trusted-correspondent status for social engineering (e.g., proposing new arbiter contracts, phishing "sign" requests for shared/multisig addresses the victim will treat as coming from a "confirmed" contact) to induce fund loss in later, unrelated transactions.

### Likelihood Explanation
Any user who opens a dispute or appeal on an arbiter contract — a normal, documented user action reachable without any special privileges — automatically transmits their permanent pairing secret to the arbiter's HTTP service. This happens on every dispute/appeal, not just in an edge case, making the exposure highly likely to occur in real usage of the arbiter-contract feature.

### Recommendation
Remove the pairing secret from the dispute/appeal payloads entirely (the arbiter already has the party's `device_pub_key` needed for encrypted communication). If pairing with the arbstore is actually required, generate and send a fresh, single-use, dispute-scoped pairing secret (via `device.startWaitingForPairing`) rather than reusing the account-wide permanent secret, and invalidate it after use.

### Proof of Concept
1. User A creates an arbiter contract and accepts it, causing `respond()` to store `my_pairing_code = <pubkey>@<hub>#<permanent_pairing_secret>` on the contract.
2. The contract is paid and later disputed: `openDispute()` POSTs `{ ..., my_pairing_code: objContract.my_pairing_code, ... }` to the arbstore's `/api/dispute/new`.
3. The arbstore operator (or anyone with visibility into that HTTP request/response) extracts `pairing_secret` from `my_pairing_code`.
4. The attacker sends a `pairing` device message to User A's device address/hub using the extracted `pairing_secret`; per `handlePairingMessage`, since the secret is `is_permanent`, the attacker's device is inserted into `correspondent_devices` with `is_confirmed=1`.
5. The attacker is now a permanently confirmed correspondent of User A's wallet and can leverage that trust for follow‑on social‑engineering attacks against User A's funds, entirely independent of the original contract/arbiter relationship.
