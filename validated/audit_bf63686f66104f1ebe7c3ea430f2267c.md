## Analog Found

The Symm IO bug's essence — a permissionless, cost-free action that bumps a *victim's* nonce (not the caller's own) with no cooldown/minimum-effect requirement, thereby invalidating a pending nonce-bound signed operation from that victim — has a structural analog in `pallet-revive`'s EIP-7702 authorization processing, whose nonce bump shares the same `frame_system::Account` nonce namespace used by ordinary signed extrinsics and by `pallet-meta-tx`.

### Title
EIP-7702 authorization relay allows third-party nonce-griefing of a victim's pending signed extrinsic / meta-transaction - (File: `substrate/frame/revive/src/evm/eip7702.rs`)

### Summary
`pallet_revive::evm::eip7702::process_authorizations` increments the authority (victim) account's `frame_system` nonce as a side effect of processing an EIP-7702 authorization tuple that any relayer may submit via a permissionless `eth_transact`. Because this nonce is the exact same counter checked by `frame_system::CheckNonce` for ordinary signed extrinsics and by `pallet-meta-tx` for relayed meta-transactions, a relayer who is in possession of *any* previously-signed, still-nonce-matching authorization from the victim (e.g., one originally signed for an unrelated purpose such as a later delegation or a routine revocation) can submit it at a moment of their choosing to bump the victim's nonce and invalidate the victim's currently pending, differently-purposed transaction — with no cooldown and no minimum economic requirement, mirroring the missing-cooldown/no-minimum-effect root cause of the Symm IO `settleUpnl` report.

### Finding Description
`process_authorizations` is reachable from any account submitting an Ethereum-style `eth_transact`/`eth_call` with a non-empty `authorization_list`, as documented at the call boundary: "`eth_call` gains an `authorization_list`... it's the inner call of `eth_transact`, signed by an Ethereum wallet and submitted via `eth-rpc`" [1](#0-0) . Any caller can be `origin` — the function only requires that each tuple carry a *valid signature from the authority*, not that the authority itself submits the transaction: [2](#0-1) 

Once chain-id, signature, nonce-match and non-contract checks pass, the code applies the delegation change and, regardless of whether the delegation is a meaningful change or effectively a no-op/self-revocation, unconditionally bumps the authority's on-chain nonce: [3](#0-2) [4](#0-3) 

The implementation explicitly acknowledges the relay-by-anyone property: "Authorizations can be relayed by anyone, so the account that paid when the delegation was set and the account submitting the next set/clear can differ" [5](#0-4) .

This nonce is not scoped to EIP-7702 usage — it is `frame_system::Account<T>::nonce`, the same value read by `CheckNonce::validate_nonce_for_account`/`prepare_nonce_for_account` for regular extrinsics [6](#0-5) , and by `pallet-meta-tx`, whose `MetaTxBareExtension` includes `frame_system::CheckNonce` bound to the signer's `frame_system::Pallet::account(&account).nonce` at signing time [7](#0-6) . The codebase's own test suite demonstrates the exact griefing primitive — bumping a signer's nonce out-of-band turns their already-signed, in-flight transaction `Stale`: [8](#0-7) 

Combining these two facts: (1) any relayer can submit a previously-obtained, still-valid EIP-7702 authorization from a victim to bump the victim's nonce at a time of the relayer's choosing, and (2) that same nonce gates the victim's independently-signed pending extrinsic or meta-tx, gives a third party ("PartyB"-equivalent) the ability to invalidate a victim's ("PartyA"-equivalent) pending nonce-bound operation without the victim's real-time cooperation, at the cost of only the attacker's own `eth_transact` fee, with no cooldown and no requirement that the authorization accomplish anything of substance (e.g., a self-revocation authorization, `auth.address == 0`, still bumps the nonce).

### Impact Explanation
An attacker who has been handed (or has observed being shared, e.g. with a delegation relay service) any of the victim's valid, unconsumed EIP-7702 authorizations can weaponize it purely to increment the victim's nonce and grief/DOS the victim's separately pending signed extrinsic or relayed meta-transaction, forcing it to fail validation with `Stale`/nonce-mismatch. This is a griefing/availability impact (transaction invalidation, forced resubmission, potential loss of a time-sensitive window) rather than a direct fund-theft or unbacked-issuance bug, so it aligns with a Medium-severity classification, consistent with how the analogous Symm IO report was rated.

### Likelihood Explanation
Likelihood depends on an attacker being in possession of a still nonce-valid authorization signed by the victim for some other purpose — this is a realistic but not universal precondition, since EIP-7702's entire design intentionally allows "anyone" to relay a signed authorization, and users/wallets/relay services routinely hold such artifacts before they are submitted on-chain. The griefing requires no privileged role, no stolen keys beyond a signature the victim voluntarily produced, and no validator/collator collusion — only mempool-level ordering control (front-running the relay of a held authorization ahead of the victim's own pending transaction), which is a normal, low-cost capability for any network participant.

### Recommendation
Do not let EIP-7702 authorization processing bump the shared `frame_system` account nonce that also gates unrelated pending extrinsics/meta-transactions for the same account, or otherwise decouple/rate-limit this side effect (e.g., require the authorization's nonce to be strictly tied to the specific dispatch that consumes it, add a minimum-effect check so a no-op/self-revocation authorization cannot be used purely to bump nonce, and/or use a dedicated authorization-nonce counter distinct from the transaction nonce, as later EIP-7702-style designs elsewhere sometimes do).

### Proof of Concept
No PoC was executed against a live network. The reproduction path is inferable purely from existing unit tests already in the repository, which independently confirm both halves of the mechanism:
- `substrate/frame/revive/src/tests/eip7702.rs::authorization_happy_path` confirms `process_authorizations` bumps the authority's `frame_system` nonce when called by an arbitrary `origin` distinct from the authority [9](#0-8) .
- `substrate/frame/meta-tx/src/tests.rs::meta_tx_extension_work` confirms that bumping the signer's nonce out of band after they've signed but before the signed transaction is applied causes the pending transaction to fail with `Error::<Runtime>::Stale` [8](#0-7) .

Composing these two already-demonstrated behaviors (not executed together here) is the basis of the analog; no new test harness run was performed, so this should be treated as a design-level finding requiring a combined integration test (submit a victim-signed EIP-7702 authorization via a third-party `eth_transact`, then attempt to apply the victim's separately-signed, same-nonce meta-tx/extrinsic and observe `Stale`) to fully confirm before remediation.

pub fn process_authorizations<T: Config>(
	authorization_list: &[AuthorizationListEntry],
	origin: &T::AccountId,
	exec_config: &ExecConfig<T>,
) -> AuthorizationResult<BalanceOf<T>> {
	if authorization_list.is_empty() {
		return Default::default();
	}

	let chain_id = U256::from(T::ChainId::get());
	let ed = <T::Currency as Inspect<T::AccountId>>::minimum_balance();
	let mut result: AuthorizationResult<BalanceOf<T>> = Default::default();

	for auth in authorization_list.iter() {
		if !auth.chain_id.is_zero() && auth.chain_id != chain_id {
			log::debug!(target: LOG_TARGET, "Invalid chain_id in authorization: expected {chain_id:?} or 0, got {:?}", auth.chain_id);
			continue;
		}

		let Ok(authority) = recover_authority(auth) else {
			log::debug!(target: LOG_TARGET, "Failed to recover authority from signature");
			continue;
		};
		let account_id = T::AddressMapper::to_account_id(&authority);

		let current_nonce: u64 =
			frame_system::Pallet::<T>::account_nonce(&account_id).saturated_into();
		let Ok::<u64, _>(expected_nonce) = auth.nonce.try_into() else {
			log::debug!(target: LOG_TARGET, "Authorization nonce too large: {:?}", auth.nonce);
			continue;
		};

		if current_nonce != expected_nonce {
			log::debug!(target: LOG_TARGET, "Nonce mismatch for {authority:?}: expected {expected_nonce:?}, got {current_nonce:?}");
			continue;
		}

	pub fn validate_nonce_for_account(
		who: &T::AccountId,
		nonce: T::Nonce,
	) -> Result<ValidNonceInfo, TransactionValidityError> {
		let account = crate::Account::<T>::get(who);
		if account.providers.is_zero() && account.sufficients.is_zero() {
			// Nonce storage not paid for
			return Err(InvalidTransaction::Payment.into());
		}
		if nonce < account.nonce {
			return Err(InvalidTransaction::Stale.into());
		}

		let provides = vec![Encode::encode(&(who.clone(), nonce))];
		let requires = if account.nonce < nonce {
			vec![Encode::encode(&(who.clone(), nonce.saturating_sub(One::one())))]
		} else {
			vec![]
		};

		Ok(ValidNonceInfo { provides, requires })
	}

	/// In transaction extension, prepare nonce for account.
	pub fn prepare_nonce_for_account(
		who: &T::AccountId,
		mut nonce: T::Nonce,
	) -> Result<(), TransactionValidityError> {
		let account = crate::Account::<T>::get(who);
		if nonce > account.nonce {
			return Err(InvalidTransaction::Future.into());
		}
		nonce = nonce.checked_add(&T::Nonce::one()).unwrap_or(T::Nonce::zero());
		crate::Account::<T>::mutate(who, |account| account.nonce = nonce);
		Ok(())
	}
