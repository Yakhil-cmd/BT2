### Title
Cross-Block Index-Cache Reuse Causes Wrong zToken Price/Notional Calculation for Unrelated Positions - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The market caches vault accrual indexes in `index-cache` keyed only by `{ timestamp: stacks-block-time, aid }` rather than by transaction. [1](#0-0)  The design intentionally assumes "one accrual per second-resolution timestamp," but `stacks-block-time` only has second-level granularity while Stacks Nakamoto tenures can produce multiple distinct blocks within the same second. Whichever caller happens to be first to touch a given asset id in a given `stacks-block-time` second permanently determines the cached `{index, lindex}` pair that every *other, unrelated* caller in that same second will silently reuse for pricing zToken collateral/debt, instead of re-accruing against the vault's actual up-to-date state.

### Finding Description
`accrue-and-cache` is the single gate through which vault liquidity/borrow indexes reach price/notional computations for zTokens: [2](#0-1) 

On a cache **miss** it calls `vault-accrue` and stores the result under `{ timestamp: stacks-block-time, aid }`; on a cache **hit** it returns the already-stored value without touching the vault at all. This cached value is what feeds `resolve-ztoken`, which every zToken-collateral/debt price resolution depends on: [3](#0-2) 

The project's own documentation states the invalidation assumption explicitly: "Cache is **automatically invalidated** each block... New block → new timestamp → cache miss → fresh accrual... Eliminates stale data risks." [4](#0-3)  That assumption is false whenever more than one Stacks block shares the same `stacks-block-time` value (a documented Nakamoto behavior — multiple blocks can be produced within one tenure faster than 1/second). In that case:

1. User A (attacker or simply an unrelated first mover) executes any operation (`borrow`, `supply`, `collateral-add`, `liquidate`, etc.) touching vault `aid` in block `N`. This calls `accrue-and-cache(aid)`, which is a cache-miss, calls `vault-accrue`, and stores the resulting `{index, lindex}` under key `{timestamp: T, aid}`.
2. Vault state for `aid` continues to change after block `N` (further deposits, borrows, or socialized bad debt) in a subsequent block `N+1` that still reports the same `stacks-block-time = T` (same-second block).
3. User B — completely unrelated to User A — executes `borrow`, `collateral-remove`, or `liquidate` on their own or on a third party's position involving a zToken derived from `aid`. `accrue-and-cache(aid)` now hits the block-`N` cache entry for `{T, aid}` and returns User A's stale `{index, lindex}` instead of the vault's true current index, because the cache key never changed.
4. `resolve-ztoken` (and therefore `get-notional-evaluation`, `process-debt-asset`, `process-collateral-asset`, health checks, and liquidation math) all compute collateral/debt USD value from this stale index, producing a wrong price for the zToken asset that no party involved in transaction B actually caused or can detect.

This is a shared-state ("cache primed by one caller, consumed by another") defect distinct from ordinary shared-pool economics: the harmed party's own transaction never queries the vault for the correct index — it is served a value determined entirely by an unrelated transaction's timing.

### Impact Explanation
The wrong price can move in either direction and harm either the position owner or the protocol/suppliers:
- If the stale cached `lindex`/`index` undervalues a victim's zToken collateral (e.g., because a same-timestamp deposit should have increased it), a healthy position can be pushed under the borrow/liquidation LTV threshold, triggering `is-healthy` failures or a liquidator's `liquidate` call seizing collateral from a position that would be healthy under the correct, current index — direct theft of user funds at rest via wrongful liquidation.
- Conversely, if the stale index overvalues zToken collateral (e.g. a same-timestamp `socialize-debt-asset` write-down that reduces `lindex` hasn't propagated because a competing transaction already primed the cache with the pre-write-down value), an unhealthy position can pass the `is-healthy`/`is-healthy-with-mask` checks in `borrow` [5](#0-4)  or `collateral-remove`, letting a user withdraw collateral or take on debt beyond what real collateralization allows, socializing losses onto suppliers — protocol insolvency.

Both outcomes land in-scope: theft of user funds at rest (Critical) or protocol insolvency (Critical), depending on the direction of the stale value.

### Likelihood Explanation
No special privileges are required. Any two ordinary users' transactions landing in the same `stacks-block-time` second (a routine occurrence on a fast-tenure Nakamoto chain, not an attacker-induced condition) can trigger this; an attacker can also actively engineer it by intentionally issuing a transaction early in a tenure to prime the cache with a value favorable to a subsequent attack transaction, or to freeze an unfavorable cache value that harms a victim's later transaction in the same window.

### Recommendation
Do not key `index-cache` solely by `stacks-block-time`. Either:
- Key the cache by `stacks-block-height` in addition to (or instead of) `stacks-block-time`, since block height strictly increases once per block, or
- Make the cache transaction-scoped (e.g., re-derive it fully within each top-level call rather than persisting it in a contract map across transactions), or
- Always call `vault-accrue` directly rather than trusting any cross-transaction cache for values that feed health/liquidation math, reserving caching only for genuinely idempotent, single-transaction reuse (multiple lookups of the same asset within one call).

### Proof of Concept
Not directly reproducible as a Solidity/EVM PoC (this is a Clarity/Stacks issue); conceptually:
1. Block `N` (timestamp `T`): User A calls `market.borrow` on vault `STX`, causing `accrue-and-cache(STX)` cache-miss and storing `{index_N, lindex_N}` under `{T, STX}`.
2. Block `N+1` also reports timestamp `T` (documented possible under Nakamoto fast tenures).
3. In block `N+1`, a large repayment/socialize-debt event changes the real vault index for `STX` to `{index_N+1, lindex_N+1}`.
4. User B calls `market.liquidate` against Victim's position holding `zSTX` collateral. `accrue-and-cache(STX)` returns the stale `{T, STX}` cache entry `{index_N, lindex_N}` instead of `{index_N+1, lindex_N+1}`, and `resolve-ztoken`/`get-notional-evaluation` price Victim's `zSTX` using the wrong index, producing an incorrect liquidation outcome. (define-private (accrue-and-cache (aid uint))
```text
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
