### Title
Cross-organization webhook forgery via secret-selection/repository-binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (as documented in `config/secrets.development.shopify.yml`, where multiple GitHub orgs each have distinct `webhook_secret` values), `WebhooksController#verify_signature` selects which organization's secret to verify the payload against using an untrusted field of the very payload it is about to authenticate, while every event handler subsequently acts on a *different* field of the same payload to decide which repository/stack to mutate. These two fields are never required to agree, breaking the binding "organization whose secret authenticated the request == owning organization of the repository the handler writes to."

### Finding Description
`WebhooksController#verify_signature` computes the organization used for signature verification purely from body content, before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). `Shipit.github(organization: repository_owner)` then looks up that organization's own `webhook_secret` and uses it in `verify_webhook_signature`.

Every registered handler, however, resolves the repository to act on from a *separate* field of the same JSON body — `repository.full_name` — not `repository.owner.login`: [3](#0-2) [4](#0-3) [5](#0-4) 

Because the HMAC signature covers the raw JSON body as a whole, and each configured organization's `webhook_secret` is independent per the multi-org config schema, an attacker who legitimately knows/controls the `webhook_secret` for one configured organization (`OrgA`) can craft an arbitrary JSON payload where `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against `OrgA`'s secret, which the attacker holds) while `repository.full_name = "OrgB/victim-repo"` (a completely different, unrelated organization/repository also mounted on the same Shipit instance). The signature check only binds the secret-selection key (`repository.owner.login`/`organization.login`) — it never verifies that this key matches `repository.full_name`, so a validly-signed, attacker-crafted event can be dispatched against any repository configured under a different organization's Shipit stacks.

The equality that should hold but doesn't:
`organization authenticating the signature` == `organization owning the repository the handler mutates`.

Concretely, this lets the attacker deliver forged `push` events (triggering `stack.sync_github` for arbitrary stacks under `OrgB`, `Handler#stacks` at `app/models/shipit/webhooks/handlers/handler.rb:32-38`), forged `status` events (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, creating/altering `Commit#create_status_from_github!` for commits in `OrgB`'s repositories, which can influence release/deploy gating via commit statuses), and any of the other handlers (`pull_request`, `check_suite`, `membership`) keyed the same way, all cross-organization.

### Impact Explanation
This crosses a credential/authentication boundary the code intends to enforce per-organization: knowledge of one organization's webhook secret should only authorize forged events for that organization's own repositories. Here it authorizes forged, validly-"signed" GitHub webhook events for any other organization mounted in the same engine instance, enabling cross-repository writes (stack sync triggers, spoofed commit statuses that can influence deploy safety checks) without ever touching `OrgB`'s real secret. This matches the "cross-repository writes" / "unauthorized deploy" high/critical impact bar, since forged commit statuses can be used to satisfy `release_status`/CI-gating checks that safety checks or `deploy_spec` steps rely on before a deploy proceeds.

### Likelihood Explanation
Requires the engine to be configured with multiple GitHub organizations (a documented, supported configuration per `config/secrets.development.shopify.yml`) and requires the attacker to know one configured organization's `webhook_secret` (e.g., because they administer that org's GitHub App settings — a normal, unprivileged-with-respect-to-other-orgs position, not requiring any Shipit session, API token, or GitHub App private key). Single-organization deployments are not affected since there's only one secret to select regardless of payload content.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the signature, re-derive the repository owner from the same field the handlers will use (`repository.full_name`'s owner segment) and reject the request (422) if it doesn't match the organization whose secret validated the signature. Equivalently, have handlers require and check that the resolved `Repository`'s stored owner matches the organization that authenticated the webhook, rather than trusting `repository.full_name` unconditionally once any org's signature validates.

### Proof of Concept
1. Deploy Shipit with two orgs configured, e.g. `OrgA` (attacker is the GitHub App admin, knows `webhook_secret_A`) and `OrgB` (victim, unrelated, `webhook_secret_B` unknown to attacker), as in `config/secrets.development.shopify.yml`.
2. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `webhook_secret`, and the signature validates successfully (per `app/controllers/shipit/webhooks_controller.rb:24-30` and `app/models/shipit/hook.rb`/`lib/shipit/github_app.rb#verify_webhook_signature`).
6. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (`Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) and triggers `stack.sync_github` on `OrgB`'s stacks — despite the attacker never possessing `OrgB`'s webhook secret.
