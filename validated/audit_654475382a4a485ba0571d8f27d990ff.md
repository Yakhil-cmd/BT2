### Title
Webhook authentication binds the wrong field to the wrong action, allowing cross-repository writes on the `/webhooks` endpoint - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` derives which GitHub organization's secret to check against from `repository.owner.login` (or `organization.login`), but every webhook handler that actually mutates state (syncs pushes, closes/labels/archives pull requests, provisions review stacks, etc.) looks up the target `Stack`/`Repository` using a *different* field of the same attacker-supplied JSON body: `repository.full_name`. These two fields are never cross-validated, so "the organization whose secret authenticated the request" and "the repository that gets written to" are two independent, unauthenticated inputs.

### Finding Description
The verification path is: [1](#0-0) 

`repository_owner` is computed purely from the request body: [2](#0-1) 

That value selects which `GithubApp`/secret is used: [3](#0-2) 

Note that `verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization — an explicitly optional setting per the setup docs (`Webhook secret (optional)`), so any org onboarded without a secret makes signature checking a no-op for payloads claiming to be from it.

Once past `verify_signature`, every handler ignores `repository.owner.login` entirely and instead resolves the target repository from `repository.full_name`: [4](#0-3) 

and acts on whatever stacks that resolves to, e.g. syncing an arbitrary commit SHA into the stack's git history: [5](#0-4) 

or archiving/unarchiving/labeling a pull-request-backed review stack, and creating `Shipit::User`/`PullRequest` records from attacker-controlled `full_name`/`user.login`: [6](#0-5) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write) are independent fields of the same JSON body, an attacker who legitimately controls a GitHub organization "OrgX" that is already configured in this Shipit instance (i.e., they know or can set OrgX's own `webhook_secret`, or OrgX has none configured — a documented, optional setting) can craft a raw POST to `/webhooks` where `repository.owner.login = "OrgX"` (so signature verification passes against OrgX's secret) while `repository.full_name = "OrgY/target-repo"` points at a completely unrelated repository/stack tracked by the same Shipit deployment. The handler dispatch never checks that `full_name` actually belongs to `OrgX`.

Before the attack: `repository.owner.login` == org-prefix of `repository.full_name` is assumed but never enforced.
After the attacker's crafted request: `repository.owner.login = OrgX` (authenticates), `repository.full_name = OrgY/target-repo` (is written) — the equality is broken, and Shipit performs a write scoped to `OrgY`'s stack using only `OrgX`'s credentials.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out as an accepted analog. Concretely it lets an attacker with no access whatsoever to the victim's repository:
- Force `Stack#sync_github` to fetch/record an attacker-chosen `expected_head_sha` for a victim stack (`PushHandler`).
- Archive/unarchive or auto-provision/deprovision review stacks, and forge pull-request metadata (`title`, `labels`, `assignees`, `user`) tied to the victim repository (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReviewStackAdapter`).
- Create/poison `Shipit::User`/`Shipit::PullRequest` records associated with the victim stack.

This is a cross-repository write achievable by a party that is unprivileged with respect to the victim repository — the required capability (control of some other, unrelated organization already onboarded to the same Shipit instance, or an org with no webhook secret configured, a documented optional setting) grants no legitimate access to the victim's Shipit stacks or GitHub repository.

### Likelihood Explanation
Multi-organization Shipit deployments are explicitly supported and documented (`config/secrets.development.shopify.yml` shows multiple orgs configured side-by-side, each with its own, optional `webhook_secret`). Any customer onboarding a second, low-trust GitHub org (or any org that leaves `webhook_secret` blank, which the setup guide marks optional) onto a shared Shipit instance is immediately exposed to this cross-repository write path via a single unauthenticated HTTP POST — no session, token, or private key is required to exploit it once the mismatch condition holds.

### Recommendation
Do not select the verification org from a field disjoint from the field used for authorization/routing. `verify_signature` should validate the HMAC using the secret for the organization actually named in `repository.full_name` (or `organization.login` used consistently by the same handler), and handlers should re-derive/validate `repository_owner` against `repository.full_name`'s org segment before performing any write, rejecting mismatches. Additionally, treat unset `webhook_secret` as "reject" rather than "trust", or require it to be mandatory for any org configuration.


```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
