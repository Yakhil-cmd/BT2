### Title
Insufficient Bridge Pausability: `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` Bypass the `isRunning` Emergency Stop — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain `Bridge` contract exposes an `isRunning` flag and `lockKLAY`/`lockToken` mechanisms as its emergency stop controls. However, all three **handle** functions that actually transfer assets out of the bridge (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`) do **not** check `isRunning` or any lock state. Setting `isRunning = false` only blocks new user deposit requests; it cannot stop ongoing fund outflows. In an incident where an operator key is compromised or a bug in the nonce/vote logic is being exploited, the owner has no on-chain mechanism to halt asset transfers from the bridge.

---

### Finding Description

`BridgeTransfer.sol` declares `isRunning = true` and provides `setRunningStatus(bool)` as the owner-controlled emergency stop: [1](#0-0) 

The **request** (deposit) path correctly enforces this flag. `_requestKLAYTransfer` requires `isRunning`: [2](#0-1) 

`_requestERC20Transfer` and `_requestERC721Transfer` also enforce it: [3](#0-2) [4](#0-3) 

However, the **handle** (withdrawal) path — which actually moves assets out of the bridge — has no such check. `handleKLAYTransfer` sends native KLAY to `_to` with no `isRunning` guard: [5](#0-4) 

`handleERC20Transfer` mints or transfers ERC20 tokens with no `isRunning` guard: [6](#0-5) 

`handleERC721Transfer` mints or transfers ERC721 tokens with no `isRunning` guard: [7](#0-6) 

Similarly, `lockKLAY` only guards `_requestKLAYTransfer` via the `unlockedKLAY` modifier, and `lockToken` only guards `_requestERC20Transfer`/`_requestERC721Transfer` via `onlyUnlockedToken`. Neither lock affects the handle functions. [8](#0-7) 

---

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` in response to a security incident:

- New user deposit requests are blocked (correct).
- Operators can **still** call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` to transfer KLAY, ERC20, and ERC721 assets out of the bridge contract.

If an operator key is compromised, or if a bug in `_voteValueTransfer` / `_lowerHandleNonceCheck` is being exploited, the owner cannot stop the asset drain by toggling `isRunning`. The only recourse is to deregister all operators one by one via `deregisterOperator`, which is a slower, multi-step operation that gives an attacker more time to drain funds.

**Affected assets:** Native KLAY held in `BridgeTransferKLAY`, ERC20 tokens held or mintable by `BridgeTransferERC20`, ERC721 tokens held or mintable by `BridgeTransferERC721`.

---

### Likelihood Explanation

- The trigger requires a compromised bridge operator account or a logic bug in the voting/nonce path — a semi-trusted, realistic threat model for a bridge.
- The `isRunning` flag is explicitly documented as the emergency stop, so operators and integrators will rely on it to halt all bridge activity. The gap between its documented intent and actual coverage is non-obvious.
- The bridge holds or controls minting rights over potentially large amounts of bridged assets, making it a high-value target.

---

### Recommendation

Add an `isRunning` check to all three handle functions, mirroring the pattern already used in the request path:

```solidity
// In handleKLAYTransfer, handleERC20Transfer, handleERC721Transfer:
require(isRunning, "stopped bridge");
```

Alternatively, introduce a dedicated `whenRunning` modifier in `BridgeTransfer` and apply it uniformly to all six public transfer entry points (three request + three handle).

---

### Proof of Concept

1. Deploy `Bridge` with `modeMintBurn = false` and fund it with 1000 KLAY.
2. Register operator `op1`. Set `operatorThreshold(ValueTransfer) = 1`.
3. Owner calls `setRunningStatus(false)` — bridge is "stopped."
4. Verify: `bridge.requestKLAYTransfer(...)` reverts with `"stopped bridge"`. ✓
5. `op1` calls `bridge.handleKLAYTransfer(txHash, from, attacker, 1000 ether, nonce=0, blockNum, "")`.
6. Transaction succeeds. Attacker receives 1000 KLAY despite `isRunning == false`.

The `isRunning` flag provides no protection against the handle path, leaving all bridge-held assets drainable even during an active emergency stop.
