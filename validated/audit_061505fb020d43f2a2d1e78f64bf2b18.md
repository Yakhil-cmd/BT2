## Finding

### Title
Permanent front-running squat of `sui::coin_registry::CurrencyKey<T>` derived-object slot blocks legitimate coin registration and enables metadata spoofing - (File: `crates/sui-framework/packages/sui-framework/sources/registries/coin_registry.move`)

### Summary
The Solidity report's root cause is: a deterministic address (`CREATE` nonce-based) is computable off-chain before the legitimate deployer's transaction executes, letting an attacker pre-register that address in an idempotent factory (`getVault[stakingToken]`), permanently DoS-ing the legitimate call. Sui's `sui::derived_object` framework module and its consumer `sui::coin_registry` reproduce the exact same pattern: a globally known singleton parent (`CoinRegistry` at `0xc`) plus a caller-supplied key (`CurrencyKey<T>`) yield a fully deterministic, publicly computable address via `derived_object::derive_address`, guarded only by a one-shot "claimed" check identical in spirit to `getVault[stakingToken] != address(0)`.

### Finding Description
`derived_object::claim` implements the exact idempotent-registration guard analogous to `createRewardsVault`: [1](#0-0) 

`sui::coin_registry::new_currency<T>` is a fully `public` entry point that any unprivileged caller can invoke for *any* type `T` satisfying only the `key` ability — the intended restriction to "the module that defines `T`" is expressed only as a source comment (`T: /* internal */ key`), not enforced by the type system or a capability check: [2](#0-1) 

Internally it calls `derived_object::claim(&mut registry.id, CurrencyKey<T>())` against the single, well-known shared `CoinRegistry` object at address `0xc`: [3](#0-2) 

Because `CoinRegistry`'s ID is fixed and `CurrencyKey<T>` depends only on the public type name `T`, the derived address for `Currency<T>` is computable off-chain by anyone the moment `T`'s defining package is published — mirroring how the `PassesStakingToken` address was computable from `Passes.sol`'s address and nonce before `initialize()` ran. The same permanent-claim semantics apply here: once claimed, `derived_object::exists` returns true forever, even after the derived object is deleted (documented explicitly): [4](#0-3) 

An attacker who observes a package publish transaction (mempool or checkpoint) containing a coin type `T` intended to later be registered via `new_currency<T>` (the doc explicitly says this call "can be called ... any time after it has been published" — i.e., not necessarily inside `init`, leaving a public window) can race ahead and call `coin_registry::new_currency<T>(...)` themselves with arbitrary attacker-chosen `symbol`/`name`/`description`/`icon_url`, claiming the `CurrencyKey<T>` slot in the canonical shared registry before the legitimate project does.

The security-review checklist bundled in this same repository independently documents this exact bug class as a known High-severity pattern for `derived_object`: [5](#0-4) 

### Impact Explanation
`new_currency<T>`'s guard, `assert!(!registry.exists<T>(), ECurrencyAlreadyExists)`, is the exact analog of `if (getVault[stakingToken] != address(0)) revert;` in the report: [6](#0-5) 

Once the attacker's front-run call succeeds, the legitimate project's subsequent call to `new_currency<T>` (or `migrate_legacy_metadata<T>`, which uses the identical `derived_object::claim` path) permanently aborts, because the `Claimed` marker persists forever: [7](#0-6) 

The consequence is a permanent, irreversible denial-of-service against that coin type's canonical entry in the Sui-wide `CoinRegistry`, and — because the attacker's spoofed `Currency<T>` is shared with attacker-controlled `name`/`symbol`/`description`/`icon_url` fields — this doubles as a metadata-spoofing/supply-chain-style attack: any wallet, indexer, or DEX that trusts `CoinRegistry` as the canonical source for coin metadata will forever display attacker-controlled data for that legitimate coin type `T`, with no on-chain recovery path. This matches the "harmful smart-contract behavior" / "permanent fund lock"-class High impact bucket (it does not require a malicious validator/peer/governance quorum — only an ordinary unprivileged caller reacting to public on-chain input, i.e., a just-published package).

### Likelihood Explanation
High. The attack requires no privileged capability, no compromise, and no special access — only observing a public package-publish transaction (or knowing the coin module's fully qualified type name in advance, which is common for anticipated/announced token launches) and submitting a competing PTB calling `coin_registry::new_currency<T>()` before the legitimate team does. Since `new_currency` explicitly documents it can be invoked separately from `init` "any time after publish," there is a real window for front-running distinct from atomic same-transaction protection.

### Recommendation
- Gate `coin_registry::new_currency<T>` (and `migrate_legacy_metadata<T>`) behind a real capability that proves the caller controls the module defining `T` (e.g., require a one-time witness `T: drop` as `new_currency_with_otw` already does, or require the `TreasuryCap<T>`/`Publisher` object as proof of authorship) instead of relying solely on the `key` ability bound, which any caller can satisfy for any public type.
- Alternatively/additionally, allow the legitimate `TreasuryCap<T>` holder to "reclaim"/overwrite a `CurrencyKey<T>` slot that was claimed by a party without proof of authorship over `T`, analogous to the report's recommended try/catch-and-fallback pattern.

### Proof of Concept
1. Project `P` publishes package `M` defining coin type `M::COIN` (an ordinary struct with `key`, not yet registered in `CoinRegistry`), intending to call `coin_registry::new_currency<M::COIN>(...)` in a follow-up transaction (per the module's documented usage pattern).
2. Attacker observes the publish transaction/checkpoint, extracting the fully qualified type name `M::COIN` (public data).
3. Attacker submits `coin_registry::new_currency<M::COIN>(registry, 0, b"FAKE", b"Fake Token", b"scam", b"http://evil", ctx)` before `P`'s transaction lands, then finalizes/shares it via `finalize`/`finalize_and_delete_metadata_cap`.
4. `derived_object::claim(&mut registry.id, CurrencyKey<M::COIN>())` succeeds for the attacker and permanently marks the slot claimed.
5. `P`'s subsequent legitimate call to `new_currency<M::COIN>` hits `assert!(!registry.exists<M::COIN>(), ECurrencyAlreadyExists)` and aborts, forever — `P` can never register authentic metadata for `M::COIN` in `CoinRegistry`, while the shared registry entry now permanently shows attacker-controlled name/symbol/description/icon for `M::COIN`.

*Note: I was unable to fully verify, before running out of tool calls, whether `coin::new_treasury_cap(ctx)` (called internally by `new_currency`) enforces a one-time-witness check independent of `coin_registry`. If it does not, the same front-run additionally hands the attacker a `TreasuryCap<M::COIN>` (a spoofed treasury cap for the type, separate from `P`'s real cap) — this would need separate confirmation and is not asserted here as a proven finding.*

/// Creates a new currency.
///
/// Note: This constructor has no long term difference from `new_currency_with_otw`.
/// This can be called from the module that defines `T` any time after it has been published.
public fun new_currency<T: /* internal */ key>(
    registry: &mut CoinRegistry,
    decimals: u8,
    symbol: String,
    name: String,
    description: String,
    icon_url: String,
    ctx: &mut TxContext,
): (CurrencyInitializer<T>, TreasuryCap<T>) {
    assert!(!registry.exists<T>(), ECurrencyAlreadyExists);
    assert!(is_ascii_printable!(&symbol), EInvalidSymbol);

    let treasury_cap = coin::new_treasury_cap(ctx);
    let currency = Currency<T> {
        id: derived_object::claim(&mut registry.id, CurrencyKey<T>()),
        decimals,
        name,
        symbol,
        description,
        icon_url,
        supply: option::some(SupplyState::Unknown),
        regulated: RegulatedState::Unregulated,
        treasury_cap_id: option::some(object::id(&treasury_cap)),
        metadata_cap_id: MetadataCapState::Unclaimed,
        extra_fields: vec_map::empty(),
    };

    (CurrencyInitializer { currency, is_otw: false, extra_fields: bag::new(ctx) }, treasury_cap)
}

macro fun migrate_legacy_metadata_impl<$T>(
    $registry: &mut CoinRegistry,
    $legacy: &CoinMetadata<$T>,
): Currency<$T> {
    let registry = $registry;
    let legacy = $legacy;

    assert!(!registry.exists<$T>(), ECurrencyAlreadyRegistered);
