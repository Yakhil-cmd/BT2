### Title
AA "empty pool / first-deposit" balance checks can be permanently broken by pre-funding the deterministic AA address before deployment - (File: `test/samples/uniswap_like_market_maker.oscript`, `storage.js`)

### Summary
Autonomous Agent (AA) addresses in ocore are deterministic: they equal `chash160(definition)`, so anyone can compute an AA's future address and send funds to it before the AA definition is ever posted or activated. `storage.insertAADefinitions()` then folds all such pre-existing outputs into `aa_balances` for that address the moment the AA becomes active, and the AA's own `init`/formula code never gets a chance to validate or reject those funds via a normal trigger. AMM/liquidity-pool style AAs — including the officially bundled `uniswap_like_market_maker.oscript` sample — rely on `balance[asset] == 0` (or similarly derived reserve values) to detect the "no liquidity yet" / genesis state, exactly the same pattern that caused the Curve `get_D()`/`add_liquidity()` DOS: an attacker donates a tiny amount of an asset to the not-yet-initialized pool so its balance is never truly zero, corrupting the invariant the AA logic depends on.

### Finding Description
`aa_composer.getTrigger`/`handleTrigger` treat `balance[asset]` as `aa_balances` rows that are updated in `updateInitialAABalances` [1](#0-0) . Separately, `storage.insertAADefinitions()` seeds `aa_balances` for a newly-activated AA address by summing **all** prior unspent outputs sent to that address that are not yet accounted for by a trigger, explicitly to "reflect the payments received from non-AAs between definition and stabilization" [2](#0-1) . This means value sent to the address *before* the AA is even defined (which is possible because the address is a pure function of the definition, as demonstrated by the "generated definition of new AA and immediately sending to this new AA" test pattern) is merged into the AA's balance without ever passing through the AA's own oscript logic as a trigger [3](#0-2) .

AMM-style AAs bundled as canonical examples in the codebase use exactly the `balance[asset]==0` pattern to detect the very first deposit and bootstrap the pool ratio, e.g. `uniswap_like_market_maker.oscript`:
```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
``` [4](#0-3) 

If an attacker computes the AA's deterministic address ahead of time and sends a dust amount of the pool asset to it before the pool AA is deployed/activated, that dust is folded into `aa_balances` via `insertAADefinitions`. When the legitimate first depositor later triggers the AA, `balance[$asset]` is no longer zero even though no genuine liquidity exists, so the "initial deposit" branch is skipped (or its ratio math operates against an attacker-chosen near-zero/donated reserve). This is the same root cause as the reported Curve issue: reserve/balance state used to detect "empty pool" can be manipulated by unsolicited external transfers before the pool logic has a chance to initialize state on its own terms.

### Impact Explanation
For any AMM/liquidity-pool AA built on this well-documented and codebase-endorsed pattern, this allows a single low-cost transaction (an unprivileged unit poster only needs to know/compute the future AA address and send 1 unit of any asset to it) to permanently corrupt the pool's genesis-detection logic. Depending on the specific AA's arithmetic, this can permanently DOS the pool's initialization (deposits keep being computed against a corrupted non-zero reserve, producing wrong ratios and bounced deposits), or let the attacker manipulate the initial exchange rate/share-issuance ratio to their advantage, causing fund loss/freezing for the intended first liquidity provider(s). This matches the accepted impact classes of AA fund loss or freezing due to unauthorized manipulation of AA state before it can validate incoming funds.

### Likelihood Explanation
Likelihood is high for any AA-based AMM deployed on ocore/Obyte that uses `balance[...]==0` (or an equivalent zero-reserve check) as its bootstrap condition, since the AA address is deterministic and computable off-chain before deployment, and sending dust bytes/asset units to any address requires no special privilege — it is exactly the kind of transaction an ordinary unit poster is authorized to send.

### Recommendation
AA templates that need to detect "no liquidity/first deposit yet" should not rely solely on `balance[asset]==0`; instead they should track their own explicit state variable (e.g. `var['initialized']` or `var['total_reserve']`) that is only set by the AA's own logic on the very first successful trigger, and treat balances above what that state variable records as unaccounted/donated funds (which can be swept, refunded, or ignored rather than used to compute ratios). At the protocol level, consider whether `insertAADefinitions`'s behavior of silently crediting pre-definition transfers into `aa_balances` without ever invoking the AA's trigger logic should be more clearly documented/flagged as a footgun for AA authors, since it breaks the assumption that all AA balance changes flow through validated trigger executions.

### Proof of Concept
1. Attacker computes `pool_address = chash160(pool_aa_definition)` for a not-yet-posted uniswap-like pool AA (analogous to `test/samples/uniswap_like_market_maker.oscript`).
2. Attacker sends `1` unit of the pool's target asset (plus minimal bytes) to `pool_address` before the AA definition is posted/activated.
3. Once the AA is deployed and activated, `storage.insertAADefinitions()` credits this pre-existing output into `aa_balances[pool_address][asset] = 1` [5](#0-4) .
4. A legitimate user then sends the first real deposit (`base` + `asset`) to `pool_address`. Inside the AA, `balance[$asset] - trigger.output[[asset=$asset]]` no longer equals `0` (it equals the attacker's donated `1`), so the `"initial deposit"` branch condition `$asset_balance == 0 OR $bytes_balance == 0` behaves incorrectly/inconsistently depending on exact amounts, corrupting the pool's bootstrap ratio or share issuance [4](#0-3) .
