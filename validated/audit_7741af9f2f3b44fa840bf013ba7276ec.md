## Title
Webhook signature verified against `organization`/`repository.owner.login`, while every handler acts on the unrelated `repository.full_name` field — enables cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login`, falling back to `organization.login` if the former is absent from the JSON body. Every webhook `Handler` subclass, however, resolves the *target* repository/stack from a completely different field: `payload.dig('repository', 'full_name')`. Because the signature check and the repository-resolution logic read different, independently-attacker-controlled JSON keys of the same unsigned-but-verified body, nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository the handler will act on.

### Finding Description [1](#0-0) 

`verify_signature` computes `repository_owner` as:
```ruby
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
and uses it purely to pick the `Shipit.github(organization: repository_owner)` app config whose `webhook_secret` is used for `verify_webhook_signature`. [2](#0-1) 

Every handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) determines which `Repository`/`Stack` to mutate via the shared `Handler#repository_name`/`#stacks` helpers, which read `payload.dig('repository', 'full_name')` — a field that is never checked against the org used for signature verification.

In a real GitHub-originated webhook these two fields are always consistent because GitHub itself populates the whole JSON body. But the engine explicitly supports multiple, independently configured GitHub Apps/organizations on one Shipit instance (see `config/secrets.development.shopify.yml` and `docs/setup.md`, each org has its own `webhook_secret`). An admin of *any one* of those configured organizations knows that org's own `webhook_secret` (they configured it when creating their GitHub App). Nothing stops them from crafting an arbitrary JSON payload where:
- `organization.login` / `repository.owner.login` = their own org (so `verify_signature` selects their own known secret and the HMAC passes), and
- `repository.full_name` = `"other-tracked-org/other-repo"` (any other repository tracked by the same Shipit instance).

Because `verify_signature` and the handler's repository lookup consult different fields, the request is accepted as validly signed for the attacker's own org while all downstream logic (`stacks`, `Repository.from_github_repo_name`) operates against a repository/stack that belongs to a different organization entirely.

This is the same class of bug as the report: a check is performed against one field (`organization`/`repository.owner.login`, analogous to the fee-bearing `_end` path being invoked regardless of pre/post-sale state) while the actual effect is driven by another field (`repository.full_name`, analogous to funds moving to `saleReceiver` without the guard being applied to the right condition) — the verification and the effect are bound to different, independently-controlled inputs.

### Impact Explanation
An attacker who administers one org configured on a shared Shipit instance can forge `push`, `status`, `check_suite`, `membership`, or `pull_request` events that pass signature verification (using their own known secret) but drive handler logic against any *other* organization's repository/stack tracked by the same instance — e.g. force `GithubSyncJob` enqueues, inject/alter `CommitStatus` records that gate deploys (`StatusHandler`), or affect PR-state-driven flows (`PullRequest::*Handler`) for repositories the attacker has no legitimate access to. This crosses the repository/organization trust boundary the engine relies on and matches the "cross-repository writes" / unauthorized deploy-influencing category.

### Likelihood Explanation
Requires only that a) the Shipit deployment hosts multiple organizations (an explicitly documented/supported configuration, `config/secrets.development.shopify.yml`), and b) the attacker is able to configure/administer a GitHub App for at least one of those organizations (which they can do freely for their own org, without needing any Shipit credential, `ApiClient` token, or access to the victim repository). No Shipit session or GitHub write access to the victim repo is required — only knowledge of a secret the attacker legitimately possesses for their own tenant.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the acting organization strictly from the same field used for verification, and require that `repository.full_name`'s owner segment match `repository_owner`/`organization.login` before any handler is invoked; reject the webhook (422) on mismatch. Alternatively, bind stack/repository resolution in `Handler` to the already-verified organization instead of trusting `repository.full_name` independently.

### Proof of Concept
1. Attacker administers `attacker-org`, which has installed its own GitHub App on the shared Shipit instance with `webhook_secret = S` (attacker knows `S`, since they configured it).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha>",
  "organization": {"login": "attacker-org"},
  "repository": {"full_name": "victim-org/victim-repo"}
}
```
(omitting `repository.owner.login` so `repository_owner` falls back to `organization.login`).
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, raw_body)` using their own known secret `S`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "attacker-org")`, validates the signature successfully with `S`.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `stack.sync_github` for the victim's stack — despite the signature only ever proving control of `attacker-org`'s secret. [3](#0-2) [2](#0-1) [4](#0-3)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
