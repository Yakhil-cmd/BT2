### Title
`Shipit::Commit.where(sha: params.sha)` cross-repository status injection - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` matches commits solely by `sha`, with no `stack_id` or `repository` predicate, so a correctly-signed `status` webhook from *any* onboarded GitHub organization can write a `Status` row onto a `Commit` belonging to a completely different stack/repository, provided the sha values collide. Signature verification (`WebhooksController#verify_signature`) only proves the payload came from the organization named in the payload's own `repository.owner.login`/`organization.login` field, it never checks that this organization actually owns the commit being updated.

### Finding Description
The claimed binding — `Commit.where(sha: params.sha)` should be equivalent to `stack.commits.where(sha: params.sha)` where `stack` is derived from `payload.repository.full_name` (as every other handler does) — does not hold. `CheckSuiteHandler#process` correctly scopes via `stacks.where(branch: ...)` then `stack.commits.where(sha: ...)` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:14-16`), but `StatusHandler#process` does not use `stacks`/`repository_name` at all:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Handler#stacks` exists specifically to scope by `repository_name` derived from `payload.dig('repository', 'full_name')` [2](#0-1) , but `StatusHandler` never calls it, and the `params` schema for this handler doesn't even require/parse `repository` [3](#0-2) .

`verify_signature` only checks that the raw HTTP body was signed with the webhook secret configured for the organization identified by `repository_owner` (from the payload itself) [4](#0-3) , and `verify_webhook_signature` compares against that same org's own `webhook_secret` [5](#0-4) . This proves organizational authenticity of the sender only — it does not, and cannot, prove that the `sha` in the body belongs to that sender's repository. Any org/repo already onboarded to this Shipit instance (attacker's own org, with attacker's own legitimately-configured webhook secret) can send a `status` event naming an arbitrary `sha`, and `StatusHandler` will apply it to every `Commit` row across every stack in the database sharing that sha, including stacks belonging to unrelated repositories/tenants.

Exploit precondition: git commit shas are content-derived, so an attacker needs the literal sha to collide with a real Commit row already ingested for a victim stack (via `PullRequestHandler`/`PushHandler` calling `Commit.create_from_github!`). The most practical way to obtain a matching sha for a target commit is if the attacker forks the victim's (public) repository — fork commits retain identical SHA1 values to the upstream commit they are cloned from, since the hash is a function of tree/parent/author/message content, not repository location. Recently opened PR head shas are visible on GitHub for public repos, so an attacker can read/enumerate them directly rather than guessing.

### Impact Explanation
The attacker can create a `Status` row (`state`, `description`, `target_url`, `context`) attached to a `Commit` belonging to a victim stack they do not control, with `commit.create_status_from_github!(params)` calling `statuses.replicate_from_github!(stack_id, github_status)` using the **victim's own** `stack_id` [6](#0-5) . Because `deployable?` gates purely on status/check success (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [7](#0-6) , injecting a forged `success` status context can influence CI gating/continuous-delivery scheduling (`schedule_continuous_delivery`) for a victim's stack. This is a write to another tenant's Commit/Status records originating from an unrelated, attacker-controlled repository — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Requires: (1) attacker has any repository already onboarded to the target Shipit instance as its own Stack (achievable by any GitHub org that can be added, or if Shipit allows self-service repo onboarding) with a legitimately configured GitHub App/webhook secret for that org — this is a normal, unprivileged onboarding, not a stolen secret; (2) a sha collision with a targeted victim commit — trivially achieved by forking a public victim repository, since forked commits are byte-identical and thus sha-identical to the upstream commit. Given both, the attacker sends one POST to `/webhooks` with `X-Github-Event: status`, correctly signed with their own org's secret, containing the victim's sha. This is repeatable against any commit whose sha the attacker can reproduce (any commit in any public repo reachable by fork).

### Recommendation
Scope `StatusHandler#process` by the reporting repository, mirroring `CheckSuiteHandler`: parse the `repository` object from the payload, resolve `stacks` via `Repository.from_github_repo_name(repository_name)`, and restrict the update to `stack.commits.where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_test.rb (minitest, no live GitHub)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "StatusHandler#process query has no stack/repository scoping" do
          source = StatusHandler.instance_method(:process).source_location
          method_src = File.read(source[0])
          # Extract just the `process` method body via Ruby reflection is brittle across versions,
          # so assert on the known unscoped call directly reachable from the constant:
          assert_match(/Commit\.where\(sha: params\.sha\)/, method_src)
          refute_match(/stack\.commits\.where\(sha:/, method_src.lines[source[1]-1, 6].join)
        end

        test "a status webhook for repo B's sha updates a commit that belongs to stack A" do
          stack_a = shipit_stacks(:shipit)
          victim_commit = stack_a.commits.create!(
            sha: "deadbeef" * 5, # 40-char sha, simulating a forked/duplicated commit
            author: shipit_users(:walrus),
            committer: shipit_users(:walrus),
            authored_at: Time.now,
            committed_at: Time.now,
            message: "victim commit"
          )

          # Attacker's payload names an unrelated repository ("attacker/repo"), not stack_a's repo,
          # but StatusHandler never inspects payload.repository at all.
          payload = {
            "sha" => victim_commit.sha,
            "state" => "success",
            "context" => "attacker-forged-ci",
            "repository" => { "full_name" => "attacker/repo", "owner" => { "login" => "attacker" } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.call(payload)
          end

          assert_equal "attacker-forged-ci", victim_commit.statuses.last.context
          assert_equal stack_a.id, victim_commit.statuses.last.stack_id
        end
      end
    end
  end
end
```
This demonstrates both sides of the claimed binding: the query executed (`Commit.where(sha: params.sha)`, no `stack_id`/`repository` predicate) versus the required binding (`stack.commits.where(sha: ...)` scoped to the payload's own repository), and shows the divergence lets a payload naming `attacker/repo` mutate a `Status` row tied to `stack_a`'s `stack_id`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
