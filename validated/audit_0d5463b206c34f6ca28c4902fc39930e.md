### Title
LP supply desync via unrestricted external `Burn` on LP mint - (File: `programs/cp-swap/src/instructions/withdraw.rs`, `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState.lp_supply` is a program-tracked "circulating LP supply" counter, updated only inside the program's own `deposit`/`withdraw` instructions [1](#0-0) . However, the LP mint itself is a normal SPL/Token-2022 mint whose token accounts (e.g. `owner_lp_token`) are owned by ordinary users, and any token owner can invoke the standard `Burn` instruction directly against the token program (no mint authority or program cooperation required). This is architecturally analogous to the qiibee `MigrationAgent`/`QiibeeToken` bug: a cached "supply" bookkeeping variable can be silently invalidated by an unrestricted `burn` path that bypasses the code that is supposed to keep it in sync.

### Finding Description
`deposit` and `withdraw` both compute the LP holder's proportional share of the vaults using `pool_state.lp_supply` as the denominator via `CurveCalculator::lp_tokens_to_trading_tokens` [2](#0-1) , and only `withdraw`/`deposit` themselves adjust `lp_supply` in lockstep with the `token_burn`/`token_mint_to` CPIs they perform [3](#0-2) , [4](#0-3) .

The `lp_mint` account used in these instructions is a normal `InterfaceAccount<Mint>` with the pool authority PDA as mint authority; nothing prevents an LP token holder from calling the SPL Token(-2022) program's own `Burn` instruction directly on their `owner_lp_token` account outside of the `withdraw` instruction. `Burn` only requires the token account owner's signature, not the mint authority, so this path is fully reachable by any token holder with a single transaction and no program cooperation — exactly as in the `QiibeeToken.burn()` case referenced in the report.

When this happens, the real on-chain LP mint supply decreases, but `pool_state.lp_supply` is never told about it (there is no reconciliation, no `get_mint`/supply check against `lp_mint.supply` anywhere in `deposit.rs`/`withdraw.rs`). The core curve math `ConstantProductCurve::lp_tokens_to_trading_tokens` always divides by the caller-passed `lp_token_supply` [5](#0-4) , i.e. `pool_state.lp_supply`, not the mint's actual supply.

### Impact Explanation
Once `pool_state.lp_supply` is permanently larger than the real circulating LP supply, every subsequent `withdraw` computes each LP holder's share against an inflated denominator, so `token_0_amount`/`token_1_amount` returned are systematically smaller than the holder's true pro-rata claim. Because the sum of all future withdrawals is capped by `(real_supply / pool_state.lp_supply) * vault_balance < vault_balance`, a portion of the vault's `token_0`/`token_1` balances becomes permanently unreachable by any instruction in the program — there is no code path that reconciles `lp_supply` with the mint's true supply or otherwise drains this residual. This is a permanent freezing of pool/LP funds and a structural insolvency in the pool's own accounting invariant (`lp_supply` should always equal actual outstanding LP tokens), matching the "insolvent pool accounting" / "permanent freezing of LP funds" criteria.

### Likelihood Explanation
Trivial to trigger: any LP token holder can submit a standard SPL Token `Burn` instruction against their own `owner_lp_token` account at any time, with no special privileges, and no interaction with the raydium-cp-swap program is required to do so. No attacker-chosen accounts beyond their own token account and the LP mint are needed.

### Recommendation
Do not treat `pool_state.lp_supply` as authoritative without validation: at minimum, in `deposit`/`withdraw` read the true `lp_mint.supply` from the passed-in `lp_mint` account and use it in the curve math (or reconcile it into `pool_state.lp_supply` before use), removing reliance on a value that can be invalidated by permissionless direct `Burn` CPIs against the mint outside the program's control.

### Proof of Concept
1. Attacker (or any LP holder) deposits liquidity via `deposit`, receiving `owner_lp_token` LP tokens; `pool_state.lp_supply` increases accordingly [6](#0-5) .
2. Instead of calling the program's `withdraw`, the holder submits a standalone `spl_token_2022::instruction::burn` (or `burn_checked`) instruction directly against `owner_lp_token`/`lp_mint`, signed only by themselves as token account owner. This decreases the real LP mint supply and the holder's token balance, but `pool_state.lp_supply` is left unchanged because it is only mutated inside `withdraw`/`deposit`.
3. Any subsequent `withdraw` call by any LP holder now divides by the stale, inflated `pool_state.lp_supply` in `lp_tokens_to_trading_tokens` [7](#0-6) , so aggregate future withdrawals can never fully drain `token_0_vault`/`token_1_vault`, permanently locking the residual difference in the pool with no recovery instruction.
