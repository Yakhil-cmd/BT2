### Title
Asset definer can unilaterally replace the attestor list via `asset_attestors`, retroactively freezing funds of previously-attested holders - (File: `validation.js`, `storage.js`)

### Summary
For assets with `spender_attested: true`, ownership/spendability of already-issued outputs is checked against the **latest** attestor list, not the list that was in effect when the holder received the asset. The definer can post a new `asset_attestors` message at any time that completely replaces the trusted attestor set with no restriction to preserve or migrate previously attested addresses. This is directly analogous to the referenced Symmetry `setCollateral` bug: a privileged single-party configuration change (attestor list swap, analogous to changing the collateral token) instantly makes previously-legitimate holdings unspendable/frozen for regular users who did nothing wrong.

### Finding Description
When an asset has `spender_attested = true`, spending or receiving that asset requires the address to be attested by the asset's current attestor list: [1](#0-0) 
and outputs must also be attested by the current list before a payment is accepted: [2](#0-1) 

The "current" attestor list is not fixed at issuance time; `storage.readAsset` always resolves it to the most recently published attestor-list unit: [3](#0-2) 
and `filterAttestedAddresses` checks addresses only against attestations issued by attestors in that latest list: [4](#0-3) 

Critically, the definer can replace the attestor list at any time via the `asset_attestors` message, and validation of this update does **not** check for continuity with the previous list — it only checks that the new list is well-formed: [5](#0-4) 

So a single-authored message from the asset definer (`objUnit.authors[0].address === objAsset.definer_address`) can drop any number of previously-trusted attestors and add new ones. Any address that was attested only by the removed attestors instantly loses the ability to spend the asset units it legitimately holds, and also can no longer receive that asset as a payment output, because both checks are evaluated against the attestor list current at validation time, not the one at receipt time.

This mirrors the Symmetry finding precisely: `setCollateral` is a legitimate, privileged admin function, but changing it retroactively breaks already-deposited user balances because withdrawal logic checks the *current* collateral token rather than the one used at deposit time. Here, `asset_attestors` is a legitimate, privileged definer function, but changing it retroactively breaks already-issued/held asset balances because both send and receive validation check the *current* attestor list rather than the one in effect when the holder acquired the funds.

### Impact Explanation
Holders of an attested asset can have their existing, legitimately-owned balance become permanently unspendable the moment the definer republishes a new attestor list that excludes their attestor. There is no fallback, grace period, or requirement that a previously-attested address remain attested across attestor-list changes. This is a direct "funds frozen" outcome for regular, unprivileged asset holders, matching the High severity of the original report (funds frozen due to a privileged, unilateral configuration change breaking prior balances).

### Likelihood Explanation
This does not require any malicious peer/hub/network behavior — it only requires the asset definer (a normal, allowed actor per the asset's own design of `spender_attested`) to post one more `asset_attestors` unit, which is a fully supported, validated message type. Any asset that uses `spender_attested` (including assets issued by AAs, since the same `asset_attestors` app is available and validated identically for AA-composed assets) is exposed. Legitimate reasons to rotate attestors (attestor key compromise, business changes) make this a realistic, not just theoretical, scenario.

### Recommendation
When enforcing `spender_attested`, checks on already-existing outputs should be evaluated against the attestor list that was current when the output was created (or when the address was attested), not strictly the latest attestor list at spend time. Alternatively, require that attestor-list updates only add attestors (never remove ones that would strand currently-held balances) unless the definer explicitly issues a migration path, and/or expose this risk clearly so wallets can react (e.g., warn holders and give them a window to re-attest or move funds before an attestor is dropped).

### Proof of Concept
1. Definer issues asset `X` with `spender_attested: true` and attestor list `[A]`.
2. Attestor `A` attests address `U` (a regular user address). `U` receives/holds output(s) of asset `X`.
3. Definer posts `asset_attestors` message changing the list from `[A]` to `[B]` (validated purely by `checkAttestorList`, no historical-continuity check — [6](#0-5) ).
4. `storage.readAsset` now resolves the asset's attestor list to `[B]` (the "latest" list) — [7](#0-6) .
5. `U` tries to spend the previously received output of asset `X`. Validation calls `filterAttestedAddresses`/checks `arrAttestedAddresses` against list `[B]`; since `U` was never attested by `B`, spending fails with "owner address is not attested" — [1](#0-0) .
6. `U`'s previously legitimate balance of asset `X` is now permanently frozen, with no way to recover it unless `B` also attests `U`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
