### Title
Unfunded overpayment refund in `repay`/`recapitalize` pays out of pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary

The CVE class is "a failure path still dereferences the missing object": `TIFFClose()` dereferences a NULL handle after the output open fails. The analog here is a settlement leg that pays out a *refund* even though the inbound leg that would justify it never happened — the pool dereferences custody that the caller never provided. `ops::repay::apply` computes `overpayment` purely from the declared `action.amount` versus book debt, then calls `transfer_out(payer, overpayment)` from the pool's own balance without verifying that any tokens were transferred in. `ops::recapitalize::apply` does the same with `refund = amount - applied` [1](#0-0) . The design comment states "The controller transfers the repay amount into the pool before this call," but the pool does not measure the receipt — it trusts the declared amount [2](#0-1) . The repo's own tests demonstrate that calling `repay` on a market with no debt refunds the entire declared amount out of real custody and leaves the cash book overstating the balance [3](#0-2) .

### Finding Description

In `repay::accounting`, when the position's `current_debt_ceil` is zero, `resolve_repay` takes the full-close branch: `burned = 0`, `overpayment = amount`, `net_repay = 0`. The `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, `credit_cash(0)` is a no-op, and `apply` then transfers `overpayment` to `payer` from pool custody [4](#0-3) . The test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `client.repay(&payer, &t.ract(0, custody_before))` with no prior transfer and asserts the payer receives `custody_before` while `after.cash == before.cash` [5](#0-4) . Similarly, `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` drains the entire pool balance via `client.recapitalize(&hub, &payer, &custody)` when `backing_shortfall == 0`, so `applied = 0` and `refund = amount` [6](#0-5) .

Whether this is exploitable depends on the pool's access control on `repay`/`recapitalize` (I could not fully enumerate `lib.rs`'s auth gates in the available iterations — the grep results for `require_auth`/`only_owner` in `lib.rs` were not expanded). If those entrypoints are gated to the controller, the trust assumption holds and this is not reachable by an unprivileged address; the tests suggest direct client calls succeed, which points toward missing gating, but `mock_all_auths` in `TestSetup` could mask an auth check.

### Impact Explanation

If reachable, an unprivileged address calls `repay` (or `recapitalize`) with `amount` equal to the pool's token balance on a market with zero debt (or zero backing shortfall) and receives the entire pool custody as a "refund" — direct theft of all suppliers' funds. Even a partial drain leaves `cash` overstating custody, so `require_reserves` admits exits that later fail inside the SAC transfer, permanently freezing remaining suppliers' withdrawals [7](#0-6) .

### Likelihood Explanation

One transaction, no collateral, no price dependence: pick any (hub, token) book with `borrowed == 0` and positive custody (e.g., a freshly supplied but unborrowed market, or donations sitting in the shared balance). The failing-precondition-then-unsafe-deref shape mirrors the CVE exactly: the missing inbound transfer is the "failed open," and `transfer_out` is the unconditional deref.

### Recommendation

Verify the inbound receipt before refunding: measure the pool's token balance delta (or require the controller to pass a measured receipt) and cap `overpayment`/`refund` at the amount actually received in this invocation. Alternatively, gate `repay`/`recapitalize` on the pool to the registered controller address so the transfer-in-first invariant is enforced by the only allowed caller.

### Proof of Concept

```rust
// Market with custody but no debt (borrowed == 0).
let custody = token.balance(&pool);
// Attacker transfers nothing; declares amount = custody.
pool.repay(&attacker, &vec![&env, PoolAction {
    hub_asset: key,
    amount: custody,            // declared, not delivered
    position: ScaledPositionRaw { scaled_amount: 0 },
}]);
// resolve_repay: overpayment = custody, net_repay = 0
// transfer_out(attacker, custody) drains the pool; cash book unchanged.
```

Demonstrated by `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` and `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs` [3](#0-2) .

**Caveat:** validity hinges on whether `pool::repay`/`recapitalize` are callable without controller auth. If the pool enforces an operator/controller check on these entrypoints, the unfunded-refund path is unreachable by an unprivileged address and this reduces to a documented trust assumption rather than a vulnerability.

#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
