### Title
Cross-organization webhook signature confusion allows unauthorized cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook's HMAC signature against using one field of the attacker-controlled JSON body (`repository.owner.login` / `organization.login`), while the event handlers that act on the payload (e.g. `PushHandler`, `StatusHandler`) resolve the target `Repository`/`Stack` using a *different* field of the same payload (`repository.full_name`). Because these two fields are never cross-checked, a party who legitimately controls one GitHub organization configured on a multi-tenant Shipit instance can forge a validly-signed webhook that is authenticated as "belonging" to their own organization but whose effective payload targets a completely different organization's repository, causing Shipit to sync/mutate that other stack.

### Finding Description
The verification step picks the app/secret based on the payload itself, not on any transport-level or otherwise trusted identifier: [1](#0-0) [2](#0-1) 

`repository_owner` is computed purely from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), both of which are attacker-controlled JSON fields inside the raw POST body. `Shipit.github(organization: repository_owner)` returns the `GitHubApp` instance configured for that organization, and its `webhook_secret` is used to compute the expected HMAC and compare it against `X-Hub-Signature`: [3](#0-2) 

Once the signature check passes, the *same raw payload* is dispatched to handlers, which resolve the target repository using an entirely different field, `repository.full_name`: [4](#0-3) 

For example, `PushHandler` uses `stacks` (derived from `repository.full_name`) to look up and mutate stacks belonging to whatever repository that field names, regardless of which organization's secret validated the signature: [5](#0-4) 

`StatusHandler` similarly writes commit statuses for any commit matching `params.sha`, with no repository-ownership check at all: [6](#0-5) 

The security-relevant binding that should hold is: **the organization whose secret authenticated the request == the organization that owns the repository being written to**. Shipit's own documentation confirms that a single instance can host many independent GitHub organizations, each with its own distinct `webhook_secret`, precisely because "a GitHub application can only authenticate to the GitHub organization it's installed in": [7](#0-6) 

Because `verify_signature` derives the authenticating organization from the same untrusted payload that also carries the target repository name, and the two are never compared, an attacker who is a legitimate GitHub App administrator for **organization A** (and therefore knows organization A's `webhook_secret`) can:
1. Build a JSON body with `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")` is selected) but `repository.full_name = "org-b/victim-repo"`.
2. Sign that exact raw body with organization A's `webhook_secret` to produce a valid `X-Hub-Signature`.
3. POST it to `/webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, etc.).

`verify_signature` succeeds (org A's secret matches org A's signature), and the request is then routed to `PushHandler`, which looks up stacks for `org-b/victim-repo` and calls `stack.sync_github(expected_head_sha: params.after)`, or to `StatusHandler`, which writes a forged commit status for any commit whose SHA is guessed/known, on a repository the attacker has no relationship to.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written." It allows a tenant of a multi-organization Shipit deployment to force GitHub-sync operations, forged commit statuses, or check-run refreshes on another tenant's stacks/repositories without having any access, membership, or webhook secret for that victim organization — an unauthorized cross-repository write, matching the Critical impact bar ("cross-repository writes").

### Likelihood Explanation
Any customer/organization legitimately onboarded onto a shared Shipit instance (a supported, documented configuration — see the "Using Multiple GitHub Applications" setup) already possesses everything needed: their own organization's `webhook_secret`. No privileged access to the victim org, no interception of the app's private key, and no Shipit session/API token is required — only crafting one HTTP POST with a computable HMAC over an attacker-chosen JSON body. This makes the likelihood high wherever multiple organizations are configured on one instance.

### Recommendation
Cross-check the identifier used to select the signing secret against the identifier used by the handlers to select the target repository/stack before dispatching — e.g. require that `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))&.owner` (or the resolved stack's organization) matches `repository_owner`/the organization whose secret validated the signature, rejecting the webhook otherwise. Alternatively, resolve the repository owner consistently from a single canonical field and use that same value both to select the verifying secret and to constrain which repositories a given webhook payload is permitted to affect.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` (per `docs/setup.md`, "Using Multiple GitHub Applications").
2. As an administrator of `org-a`'s GitHub App (attacker), craft:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": {"login": "org-a"},
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hex hmac>` using `org-a`'s known `webhook_secret` over the exact raw JSON body (per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` algorithm).
4. `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `GitHubApp`, and validates the signature successfully.
6. `PushHandler#process` is invoked using `repository.full_name = "org-b/victim-repo"`, finds `org-b`'s stack(s), and calls `stack.sync_github(expected_head_sha: ...)` — a write against `org-b`'s stack triggered purely by `org-a`'s credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
