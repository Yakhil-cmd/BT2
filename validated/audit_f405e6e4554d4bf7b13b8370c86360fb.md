### Title
Cross-repository commit-status forgery lets an attacker with webhook control over any Shipit-connected repository unlock CI checks and trigger an unauthorized deploy on an unrelated stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler`, the handler for GitHub `status` webhook events, resolves the target commit purely by `sha` across the entire `Commit` table, without ever checking that the event's `repository` (the entity whose organization secret produced a valid signature) actually owns that commit's stack. Every other webhook handler in the engine scopes lookups to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` via the shared `stacks` helper, but `StatusHandler#process` bypasses that helper entirely.

### Finding Description
The webhook signature check in `WebhooksController#verify_signature` only proves that the raw payload bytes were signed with the webhook secret configured for **the organization named in the payload's own `repository.owner.login`/`organization.login` field**: [1](#0-0) 

It never binds the verified organization to any specific repository being *acted upon* elsewhere in the payload — the only role that field plays is selecting which `webhook_secret` to check the HMAC against, and `repository_owner` is read straight out of the (otherwise-untrusted) JSON: [2](#0-1) 

For every other event type, the individual handler still re-derives and enforces the repository scope using `Handler#stacks`, which looks up `Repository.from_github_repo_name(repository_name)` from the *same* payload before touching any records: [3](#0-2) 

`PushHandler`, for example, correctly restricts itself to `stacks` (i.e., stacks belonging to the payload's own repository) before doing anything: [4](#0-3) 

`StatusHandler`, however, ignores `repository` altogether and matches **globally** by `sha`: [5](#0-4) 

Because `Commit.where(sha: params.sha)` is not scoped by stack/repository, any `status` event that is validly signed for **Organization A's** webhook secret can still create/update a `Status` on a commit that belongs to a completely different stack owned by **Organization B**, as long as the attacker knows (or brute-forces/observes) a 40-hex-char SHA that also exists in Org B's tracked commit history (SHAs are public via GitHub, git history, PRs, CI logs, etc., so this is trivially satisfiable for any organization that has ever exposed a commit SHA to the attacker).

This breaks exactly the binding called out in scope: **the organization that authenticated the webhook request versus the repository whose data is written.** `verify_signature` binds the signature to Org A; `StatusHandler#process` writes to Org B's commit unconditionally.

`Commit#create_status_from_github!` (invoked directly from the handler) runs the full status-processing pipeline including hooks and, on state transitions to `success`, deployability logic and continuous-delivery scheduling: [6](#0-5) [7](#0-6) 

### Impact Explanation
If the target stack has `continuous_deployment` enabled (a common Shipit configuration), forging a `success` status for a specific SHA belonging to that stack can cause an unauthorized deploy to be scheduled/triggered for a repository the attacker has no GitHub write access to — this satisfies the "unauthorized deploy" Critical-impact criterion. Even without continuous deployment, this allows an attacker to satisfy required/blocking CI status checks (used for merge-queue gating, deploy safety checks, and review-stack promotion) on a stack they do not control, undermining the core trust boundary that ties CI status to the repository's own CI system. The only requirement on the attacker is that they control (or can trigger) genuine webhook delivery for **any** repository/organization that is itself connected to the same Shipit instance — a much weaker bar than requiring write access to the victim repository.

### Likelihood Explanation
Exploitability depends on: (1) the attacker having legitimate control over a `status` webhook delivery for some other repository already connected to the Shipit instance (realistic in any multi-tenant/self-serve Shipit deployment where many teams' repos share one instance, or where the attacker is a low-privilege collaborator/CI integration on one repo but not another), and (2) knowledge of a target SHA (public and easily discoverable). Given how common multi-repo Shipit deployments are, and that commit SHAs are not secrets, this is readily reachable without any Shipit session, API token, or GitHub write access to the victim repository.

### Recommendation
In `StatusHandler#process`, scope the lookup through the handler's own `stacks`/repository resolution (as `PushHandler` and the pull-request handlers do), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or explicitly `Commit.joins(:stack).where(stack: { repository: repository_for(payload) }, sha: params.sha)`, so a commit can only be updated by a status event whose payload repository matches the commit's own stack/repository.

### Proof of Concept
1. Attacker controls (or can trigger CI on) `attacker-org/attacker-repo`, which is connected to the same Shipit instance and has a legitimate configured `webhook_secret`.
2. Attacker discovers the SHA of the head commit of `victim-org/victim-repo`'s stack (public git history / PR page).
3. Attacker triggers (e.g., via their own CI integration, or a script using their repo's real GitHub App/webhook credentials) a `status` webhook POST to Shipit with:
   - `repository.owner.login = "attacker-org"` (so `verify_signature` validates against attacker-org's real secret — always succeeds because it's their own legitimate webhook)
   - `sha = "<victim commit sha>"`
   - `state = "success"`, `context = "<a required context for victim stack>"`
4. `verify_signature` passes because the signature is genuinely valid for `attacker-org`'s secret and payload.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit (no repository check), calling `create_status_from_github!` on it — marking the victim commit's CI check as passed and potentially triggering continuous deployment or merge-queue promotion on `victim-org/victim-repo`, despite the attacker never having any credential or access to that repository.
