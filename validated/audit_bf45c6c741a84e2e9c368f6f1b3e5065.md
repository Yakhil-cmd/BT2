The signature verification binds to `repository_owner`, but the actual write target (`repository_name`) is a separate, unverified field within the same signed payload — this is exactly the "organization that authenticated versus the repository that is written" binding class named in the rules.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independently-controlled `repository.full_name` field, allowing a compromised/rogue installation of one GitHub org to write into stacks of a different org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but the payload's `repository.full_name` — the field actually used by every event handler to look up the target `Stack`/`Repository` — is never checked against that verified owner.

### Finding Description
`verify_signature` computes `repository_owner` purely from the untrusted JSON body and uses it only to pick the HMAC secret (`Shipit.github(organization: repository_owner)`), then verifies the raw body's signature with that secret: [1](#0-0) 

The binding assumed by the design is: `repository.owner.login == organization whose secret validated the signature == organization whose repositories may be mutated`. But `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every concrete handler (e.g. `PushHandler`) to resolve which `Stack`s to act on, reads a *different* JSON key — `repository.full_name` — from the same payload: [2](#0-1) [3](#0-2) 

Nothing in the request pipeline enforces `repository.full_name`'s owner segment equals `repository.owner.login`. An attacker who controls (or compromises) any GitHub organization/App installation that Shipit trusts — i.e., possesses a valid `webhook_secret` for org A, exactly analogous to the bug's "supplier updates but borrower doesn't" mismatch, here it's "signature covers field X (owner) but the engine trusts field Y (full_name) for the write target" — can craft a payload where `repository.owner.login = "A"` (so the HMAC computed with A's secret validates) while `repository.full_name = "B/some-repo"` for a stack belonging to org B tracked by Shipit. `PushHandler` will then call `stack.sync_github(expected_head_sha: params.after)` for org B's stack using attacker-supplied `after`/`ref`, triggering a sync/deploy pipeline for a repository the attacker does not control, purely because org A's secret was valid.

This is structurally the same class of bug as the report: the "total interest accrued" (signature) is computed over one quantity (owner) while the "total debt/supply" (handler behavior) is driven by a second, unsynchronized quantity (full_name) — the two are supposed to move together but nothing enforces it.

### Impact Explanation
This breaks the equality `verified_signer_org == acted_upon_repository_org`, letting an attacker who owns/controls a single trusted GitHub organization (with its own legitimate `webhook_secret`) forge webhook events that cause Shipit to sync/deploy pipelines for a stack belonging to a completely different, unrelated organization/repository it has no access to. This is a cross-repository write triggered without possessing that repository's own webhook credentials — matching the Critical "cross-repository writes" impact category, since `sync_github` can enqueue deploy-affecting jobs (`GithubSyncJob`) against another org's tracked stacks.

### Likelihood Explanation
Requires the attacker to control at least one GitHub organization/repository already onboarded to the Shipit instance (to obtain a valid `webhook_secret` via normal GitHub webhook configuration UI) — this is a plausible, low-privilege position for a multi-tenant Shipit deployment where many independent teams/orgs each configure their own webhooks. No repository write access, API token, or session is needed for the *target* stack; only knowledge of the target's `full_name`, which is public.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after signature verification, re-derive the acting organization strictly from the verified `repository_owner` and pass it through to handlers, rejecting (or scoping queries) whenever `repository.full_name`'s owner segment differs from `repository_owner`. Concretely, `Handler#repository_name`/`stacks` should require and validate that the owner portion of `full_name` matches the organization whose secret verified the request, not trust `full_name` independently.

### Proof of Concept
1. Attacker legitimately administers GitHub org `attacker-org`, which is configured in Shipit with `webhook_secret = S`.
2. Shipit also tracks `Repository`/`Stack` for `victim-org/victim-repo` (owned by a different, unrelated org).
3. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `S` over this exact raw body (`sha1=HMAC(S, body)`).
5. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and verifies successfully — see [4](#0-3) .
6. `create` then dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` via `repository_name` reading `payload.dig('repository', 'full_name')` — see [2](#0-1) .
7. `stack.sync_github(expected_head_sha: params.after)` is invoked for `victim-org/victim-repo`'s stacks using the attacker-controlled `after` SHA, even though the request was never signed by `victim-org`'s webhook secret.
