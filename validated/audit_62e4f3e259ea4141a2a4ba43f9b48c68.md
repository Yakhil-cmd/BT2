### Title
SecretarySalaryPaymaster reuses FellowshipSalaryInteriorLocation, causing both salary instances to share one AssetHub sovereign account and budget pool - ([File: system-parachains/collectives/collectives-polkadot/src/secretary/mod.rs])

### Summary
`SecretarySalaryPaymaster` is configured with `crate::fellowship::FellowshipSalaryInteriorLocation` as its `InteriorLocation` instead of a dedicated Secretary interior location. As a result, both `pallet_salary::Instance1` (Fellowship) and `pallet_salary::Instance3` (Secretary) resolve, via `LocationToAccountId`/`AliasesIntoAccountId32`, to the exact same AssetHub sovereign account keyed on `PalletInstance(64)`. Any unprivileged member of either collective can register and claim a salary payout through the intended `pallet_salary::payout`/`payout_other` extrinsic, and both draw down from the same shared pot even though the pallet-level `Budget` accounting (`FellowshipSalaryBudget` vs `SecretarySalaryBudget`) is tracked independently per instance.

### Finding Description
`SecretarySalaryPaymaster` is defined as: [1](#0-0) 

using `crate::fellowship::FellowshipSalaryInteriorLocation` as its interior location rather than defining its own, e.g. `PalletInstance(<crate::SecretarySalary as PalletInfoAccess>::index() as u8)`. Compare this to the equivalent Ambassador and Fellowship treasury/salary paymasters, each of which defines a dedicated `*InteriorLocation`/`*Location` derived from its own pallet index: [2](#0-1) [3](#0-2) 

Because `PayOverXcm`'s pay-from account on the destination chain (AssetHub) is derived purely from this `InteriorLocation` combined with the sending chain's location, both `FellowshipSalaryPaymaster` and `SecretarySalaryPaymaster` compute the identical AssetHub sovereign account (`Parent, Parachain(Collectives), PalletInstance(64)`). This is confirmed directly in the existing integration test, whose comment states explicitly: "SecretarySalary uses FellowshipSalaryPaymaster, so the pay_from account is derived from the fellowship salary pallet's interior location (pallet index 64)": [4](#0-3) 

The attacker path is fully reachable via normal extrinsics: any rank-1 member of `SecretaryCollectiveInstance` calls `pallet_salary::Pallet::<Runtime, SecretarySalaryInstance>::register` then `payout` (or `payout_other`), gated only by `Members = pallet_ranked_collective::Pallet<Runtime, SecretaryCollectiveInstance>` and rank checks inside `pallet_salary` — no root/governance origin required: [5](#0-4) 

Each instance's `Budget` type (`SecretarySalaryBudget`, `FellowshipSalaryBudget`) only bounds how much that instance's own `pallet_salary::Status` storage can register/allocate per period; it does not reflect or reserve actual on-chain balance held at the shared AssetHub account. Since both instances' `PayOverXcm` withdraw XCM instructions target the same sovereign account, a Secretary member's successful payout physically withdraws funds from the account that governance intended to fund according to `FellowshipSalaryBudget` (as documented/expected by the Fellowship salary flow), regardless of the Secretary's separately-tracked budget ledger. No filter, barrier, or origin check in the XCM/PayOverXcm stack distinguishes "Fellowship-earmarked" from "Secretary-earmarked" funds at that shared account, because the pallet configuration itself collapsed both instances onto one interior location.

### Impact Explanation
The invariant that each salary instance's budget is isolated and draws only from its own configured location is broken at the funds-custody level even though pallet-level bookkeeping (`Status`/`Claimant` storage) stays separate per instance. Concretely: if AssetHub's sovereign account for `PalletInstance(64)` is funded to cover `FellowshipSalaryBudget` for a period, a Secretary Collective member (an unprivileged, non-governance role) can register and successfully claim a payout that withdraws from that same account, consuming funds intended for Fellowship members. This can cause legitimate Fellowship salary claims to fail (insufficient balance for the `WithdrawAsset`/`InitiateTransfer` in the corresponding XCM program) or force governance to over-provision the account beyond either budget's nominal size to avoid cross-draining — a real cross-instance budget-isolation violation, not merely a cosmetic naming issue.

### Likelihood Explanation
This requires no privilege escalation: any inducted Secretary Collective member (rank 1) can call the normal, intended `payout`/`payout_other` extrinsic of `pallet_salary::Instance3` after registering. It is fully deterministic and repeatable every salary period as long as both instances are active and the shared account isn't funded for the sum of both budgets. The bug is present in production configuration, not merely benchmarking/test code — the non-benchmark `Paymaster` type is `SecretarySalaryPaymaster` unconditionally when `runtime-benchmarks` is off: [6](#0-5) 

### Recommendation
Define a dedicated `SecretarySalaryInteriorLocation` derived from `SecretarySalary`'s own pallet index (mirroring `FellowshipSalaryInteriorLocation`, `AmbassadorTreasuryInteriorLocation`, etc.) and use it in `SecretarySalaryPaymaster` instead of reusing `crate::fellowship::FellowshipSalaryInteriorLocation`. This ensures the Secretary salary draws from its own AssetHub sovereign account, funded and tracked independently of the Fellowship salary budget.

### Proof of Concept
xcm-emulator test plan (extending `collectives_salary.rs`):
1. On `AssetHubPolkadot`, mint exactly `FellowshipSalaryBudget` worth of the configured salary asset into the sovereign account derived from `(Parent, Parachain(Collectives), PalletInstance(FELLOWSHIP_SALARY_PALLET_ID))` (which, due to the bug, is identical to the Secretary's pay-from account).
2. On `CollectivesPolkadot`, as a Fellowship member, call `FellowshipSalary::register` then `FellowshipSalary::payout` for the full budget amount; assert the XCM is sent and AssetHub processes a successful `Transferred`/withdrawal event, fully depleting the funded account.
3. As an unprivileged Secretary Collective member (rank 1), call `SecretarySalary::register` then `SecretarySalary::payout`; assert this either drains the account further (if any residual balance) causing the total withdrawn across both instances to exceed the amount funded solely under `FellowshipSalaryBudget`, or fails only because the shared account is empty — proving both instances compete for one pot instead of independent, isolated budgets.
4. Assert: `total_XCM_withdrawn_by_both_instances > FellowshipSalaryBudget` alone is possible, or equivalently that Secretary payouts succeed using funds that were provisioned and events-labeled as Fellowship's, violating the isolation invariant.
