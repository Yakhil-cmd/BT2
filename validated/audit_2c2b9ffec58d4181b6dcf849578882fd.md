### Title
Webhook signature verification is bound to an attacker-chosen organization, not to the repository the event actually writes to, allowing unauthenticated commit-status forgery and unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against using an attacker-supplied field of the very payload being verified (`repository.owner.login`), rather than the identity of the repository the event will actually mutate. Combined with `GitHubApp#verify_webhook_signature` treating a blank `webhook_secret` as automatically valid, and with `StatusHandler` resolving target `Commit` records globally by `sha` with no repository scoping at all, an attacker who can name *any* configured organization that lacks a `webhook_secret` can forge webhook events (in particular `status`) that affect commits/stacks belonging to a completely different, secured organization/repository.

### Finding Description
`verify_signature` computes the organization used for verification purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is fully attacker-controlled JSON content (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), and it is used solely to pick which `Shipit::GitHubApp` (and thus which `webhook_secret`) is used to check the signature:

`GitHubApp#verify_webhook_signature` unconditionally accepts any request when the selected app has no `webhook_secret` configured: [3](#0-2) 

Multi-organization configuration, including organizations with an intentionally blank `webhook_secret`, is a documented, first-class Shipit configuration pattern: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, for the blank-secret org), the payload is dispatched to handlers. Most handlers scope their effect to a specific repository via `repository.full_name`: [6](#0-5) 

But `StatusHandler` does not use `repository` at all - it looks up `Commit` **globally by `sha`**, across every stack/repository tracked by the Shipit instance: [7](#0-6) 

This breaks the intended binding `verified_organization == organization_owning_the_data_acted_on`. In reality: `verified_organization` (any org configured with a blank `webhook_secret`) can differ arbitrarily from the repository/stack whose commit status is actually written, because `StatusHandler` never checks which repository the `sha` belongs to.

### Impact Explanation
An attacker who knows (from public Shipit config docs/conventions, or simply by trial) the name of *any* GitHub organization configured in the target Shipit instance with a blank/unset `webhook_secret` can:
1. Send an unauthenticated POST to `/webhooks` with `X-Github-Event: status` and `repository.owner.login` set to that blank-secret organization (satisfying `verify_signature` trivially, since `verify_webhook_signature` returns `true` for a blank secret).
2. Set `sha` to the head commit SHA of any commit tracked by any *other*, fully-secured stack in the same Shipit instance (this is public information visible on the stack's GitHub commit history and Shipit UI).
3. Set `state: "success"` with a `context` matching a required/blocking CI status configured in that other stack's `shipit.yml` (`ci.require`).

This forges a required CI check as passing on a stack the attacker has no legitimate relation to. If that stack has `continuous_deployment` enabled, or if a human is later relying on Shipit's displayed CI status to decide to deploy, this can lead to an **unauthorized deploy** of arbitrary code that was never validated by real CI - directly matching the High-severity "unauthorized deploy" impact bucket, without needing a Shipit session, API token, or GitHub write access to the targeted repository.

### Likelihood Explanation
Likelihood is moderate to high in any multi-tenant/multi-org Shipit deployment where at least one configured organization omits `webhook_secret` (a state explicitly supported and shown in the shipped example config and setup docs, e.g. for internal/dev orgs). No credentials, GitHub App key, or repository access are required — only knowledge of one org name in the same Shipit install and a target commit `sha`, both of which are typically public or easily inferable from the Shipit UI (stack list, commit history).

### Recommendation
- In `WebhooksController#verify_signature`, do not let the payload itself pick the verification context to trust; instead, bind the authenticated organization to the specific repository the handler will subsequently act on, and reject any event whose `repository.full_name`/owner does not match a repository actually mapped to the organization whose secret verified the signature.
- Do not treat a blank `webhook_secret` as automatic verification success; either require a secret for every configured app or, at minimum, ensure a blank-secret organization cannot be used to authenticate events referencing repositories owned by other organizations.
- Fix `StatusHandler#process` (and any other handler that doesn't scope by repository) to filter `Commit` lookups by the repository/stack the verified webhook's organization actually owns, not merely by `sha`.

### Proof of Concept
Assume Shipit is configured with:
- `github.trusted-org` → real `webhook_secret` set, owns the tracked stack `trusted-org/app` (production, `continuous_deployment: true`, `ci.require: ["ci/tests"]`).
- `github.sandbox-org` → `webhook_secret: nil` (per the shipped example config), not otherwise related to `trusted-org/app`.

Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<head sha of trusted-org/app's latest undeployed commit>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "sandbox-org" } }
}
```
- `verify_signature` computes `repository_owner = "sandbox-org"`, loads `Shipit.github(organization: "sandbox-org")`, and `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank for `sandbox-org` — no `X-Hub-Signature` header is even required.
- `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the commit belonging to `trusted-org/app` regardless of `sandbox-org` having nothing to do with it, and calls `commit.create_status_from_github!(params)`, forging a passing `ci/tests` status for that commit.
- With continuous deployment enabled, this forged status can unlock an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
