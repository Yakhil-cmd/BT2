### Title
Webhook signature verification uses an attacker-controlled organization while event handlers act on an attacker-controlled repository field, allowing signature-check bypass across GitHub organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body. The event handlers that subsequently act on the request, however, resolve the target repository/stack from a *different* payload field, `repository.full_name` [1](#0-0) . Because these two fields are never bound to each other or to the verified signature, an attacker can pick whichever organization key is convenient for passing the signature check while pointing `repository.full_name` at a repository belonging to a completely different, fully-protected organization.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization app config (`app_id`, `installation_id`, `webhook_secret`, ...) as documented for multi-org installs [3](#0-2) , and `GitHubApp#verify_webhook_signature` explicitly treats a **blank/unset `webhook_secret` as an automatic pass**:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

`webhook_secret` is documented as **optional** for each configured organization [5](#0-4) , and the multi-org example config shows organizations that may be configured with `webhook_secret: # nil` [6](#0-5) .

Once `verify_signature` passes (for *any* reason, including the "no secret configured" bypass above), the raw JSON body is dispatched unchanged to all matching handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

The base `Handler` class resolves which `Stack`/`Repository` to operate on using `repository.full_name`, a field entirely independent from `repository.owner.login` used for signature verification:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

This breaks the deployment-trust equality that should hold: `organization authenticated == repository acted upon`. An unprivileged attacker can craft a JSON payload where:
- `repository.owner.login` = an organization configured on the instance with a blank/absent `webhook_secret` (this makes `verify_webhook_signature` return `true` unconditionally, regardless of the `X-Hub-Signature` header sent),
- `repository.full_name` = `"<victim-org>/<victim-repo>"` — a repository belonging to a different, fully-secured organization on the same Shipit instance.

The `push` handler (`push_handler.rb`) and other handlers then act on the victim repository's `Stack` using this forged, otherwise-unauthenticated payload.

### Impact Explanation
This is a cross-organization signature-check bypass leading to actions being taken against a repository/stack that never authenticated the request. On a multi-tenant Shipit deployment (the documented "Using Multiple GitHub Applications" mode), an unprivileged external attacker can spoof push/status/check_suite/membership events for any repository in the system as long as any single organization on that instance has no `webhook_secret` configured — a state the docs present as normal/optional, not a misconfiguration. Concretely this allows the attacker to enqueue `GithubSyncJob` for a targeted stack (updating its known-commit state) or forge `status`/`check_suite` results, and in the `membership` handler, alter `Team`/`Membership`/`User` records tied to `Shipit.github_teams` authorization [8](#0-7) . Depending on which handler is targeted, this can result in a cross-repository state write and, via membership/team manipulation, escalation into the app's GitHub-teams-based authorization — matching the High/Critical impact bar (cross-repository writes / escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
The prerequisite (at least one org on a multi-org Shipit instance without a `webhook_secret`) is explicitly presented in the project's own documentation and sample configs as a supported, optional configuration, not a deviation from documented deployment. No credentials, session, or repository write access are required — only knowledge of one organization's public login name and any target repository's `owner/repo` full name, both public information. The attacker needs zero access to any Shipit or GitHub secret.

### Recommendation
Bind the signature-verification identity to the identity actually acted upon: verify the signature using the organization that matches `repository.full_name`'s owner (not a possibly different `repository.owner.login`/`organization.login`), and reject payloads where these fields disagree. Additionally, do not silently succeed verification for organizations with a blank `webhook_secret` when the payload references a different, protected organization's repository — either require a secret to be present for every configured organization or scope acceptance strictly to the repository owner whose secret was actually used.

### Proof of Concept
1. Configure Shipit for multi-org mode: `OrgLax` (no `webhook_secret`) and `OrgSecure` (with a real secret), both installed on the same Shipit instance, per `docs/setup.md`'s "Using Multiple Github Applications" section.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "OrgLax" }, "full_name": "OrgSecure/victim-repo" },
  "after": "<attacker-chosen sha>",
  ...
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgLax")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the bogus signature header.
4. `PushHandler` (via `Handler#repository_name`) resolves the target using `repository.full_name = "OrgSecure/victim-repo"`, enqueuing sync/deploy-relevant jobs against `OrgSecure`'s stack despite no valid signature ever being presented for `OrgSecure`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
