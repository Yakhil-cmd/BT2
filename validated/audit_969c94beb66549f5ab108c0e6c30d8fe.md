## Analog Found

### Title
Unbounded input-selection loop when an AA sends a payment lets a dust-flooding attacker permanently block the AA from paying out an asset - (File: aa_composer.js)

### Summary
When an Autonomous Agent (AA) needs to send a payment message as part of its response, `sendUnit()`'s `completePaymentPayload()` selects unspent outputs owned by the AA address and pushes every one of them into `payload.inputs` until the target amount is reached, with no limit on how many rows can be fetched or iterated [1](#0-0) . The SQL that supplies these rows, `readStableOutputs()` and `readUnstableOutputsSentByAAs()`, has no `LIMIT` clause, unlike the equivalent wallet-side coin-picker in `inputs.js` which caps the query at `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` rows [2](#0-1) [3](#0-2) . Worse, the general "too many inputs" validation check in `validatePaymentInputsAndOutputs()` explicitly exempts AA-generated payments: `if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA) return callback("too many inputs")` [4](#0-3) . The only dust filter that exists applies solely to the base-asset case (`amount>=FULL_TRANSFER_INPUT_SIZE`); for any custom/attached asset there is no minimum-amount filter at all [5](#0-4) .

### Finding Description
Any unprivileged unit poster can send an unlimited number of dust-amount outputs of a given asset to a known AA address (this is a normal, permissionless payment to an address, not requiring cooperation from the AA). Because the outputs table for that asset accumulates without bound and the query that selects "unspent outputs owned by the AA" has no row limit, the next time the AA needs to pay out that asset (e.g., as part of a normal bounce/response triggered by any user), `iterateUnspentOutputs()` will keep consuming rows one by one, pushing each into `payload.inputs`, until the target amount is reached or the outputs are exhausted [6](#0-5) . If the attacker deposits enough dust outputs, the number of inputs required to reach a normal payout amount can be made arbitrarily large. Since AA-authored units are exempt from the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap during validation [4](#0-3) , this huge input set is not rejected there, but it still must pass through unit-size limits (`MAX_MESSAGES_PER_UNIT`, oversize fee calculations) computed later in `sendUnit()`. Because `completePaymentPayload()` never caps the loop or falls back to a smaller subset, the resulting unit becomes oversized/invalid, and the AA's attempt to send that asset payment fails, causing the whole trigger to bounce.

### Impact Explanation
Every future trigger that requires the AA to pay out the poisoned asset from that address will repeatedly hit the same unbounded set of dust inputs and fail/bounce, since the deposit set can never shrink (outputs are never consumed because the payment never succeeds). This permanently locks any balance of that asset held by the AA for that address, denying legitimate users their expected AA-mediated payouts — a direct AA fund-freezing condition, analogous to the reported `getLockedFunds()` DoS where excess dust deposits prevent legitimate refunds.

### Likelihood Explanation
The attack requires no special privilege: any address can send arbitrarily many small-value payments of any asset to a public AA address, which is a normal permission-less operation. The number of dust outputs needed to trigger oversized/failing units is bounded only by the attacker's own transaction fees, making this a straightforward, replicable griefing vector against any AA that pays out assets (e.g., DEX/bridge/DeFi AAs) whose address is public and predictable.

### Recommendation
- Apply the same `MAX_INPUTS_PER_PAYMENT_MESSAGE` limit (with a `LIMIT` clause) to `readStableOutputs()` / `readUnstableOutputsSentByAAs()` in `aa_composer.js`, mirroring `pickMultipleCoinsAndContinue()` in `inputs.js`.
- Remove or tighten the `!objValidationState.bAA` exemption in `validatePaymentInputsAndOutputs()` so AA-generated payments are also bound by `MAX_INPUTS_PER_PAYMENT_MESSAGE`.
- Extend the existing dust-filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) that currently only protects the base asset to non-base assets as well, so dust outputs of arbitrary assets cannot be used to poison an AA's spendable-output set.

### Proof of Concept
1. Identify a deployed AA address that is known to eventually pay out asset `X` (e.g., a bridge/DEX AA).
2. Send N small payments (1 unit each) of asset `X` to that AA address from freely creatable addresses — no cooperation from the AA needed.
3. Trigger the AA in a way that requires it to send an output in asset `X`. `completePaymentPayload()`'s `iterateUnspentOutputs()` will pull in the dust outputs one at a time (no `LIMIT` on the query, no cap enforced by `validatePaymentInputsAndOutputs` for AA units) until the required amount is reached.
4. With enough dust outputs pre-seeded, the resulting payment message contains far more inputs than any legitimate user-composed payment ever could, pushing the unit past size/oversize-fee limits and causing `sendUnit()` to fail, bouncing every subsequent trigger that needs asset `X` payout from that address.
