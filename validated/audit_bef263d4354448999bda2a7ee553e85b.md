### Title
API-scoped ApiClient tokens can read any stack's CI status via `Api::CCMenuController` bypassing stack scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces that a stack-scoped `ApiClient` (one with a `stack_id` set) can only ever touch the single stack it was authorized for, by routing all stack lookups through the `stacks`/`stack` helpers. `Api::CCMenuController` overrides `stack` and bypasses this scoping entirely, so any valid token — even one deliberately restricted to a single stack — can be used to read the CI/deploy status of every other stack in the installation.

### Finding Description
`Api::BaseController` defines the binding "a stack a token authorises == a stack it touches": [1](#0-0) 
`stacks` filters by `current_api_client.stack_id` when present, and `stack` (used by `StacksController`, `HooksController`, `CommitsController`, etc.) always resolves through that scoped relation, e.g.: [2](#0-1) [3](#0-2) 

`Api::CCMenuController`, however, defines its own `stack` method that resolves directly from `Stack.from_param!(params[:stack_id])`, completely ignoring `current_api_client.stack_id`: [4](#0-3) 

The controller only checks `require_permission :read, :stack`, which validates the client's `permissions` array (e.g. `read:stack`) but never validates which *specific* stack the client is scoped to: [5](#0-4) 

So a token that was intentionally minted/scoped for stack A (`ApiClient#stack_id == A`) — the equivalent of the report's "internal mapping recording who may redeem" — is never re-checked when the request targets stack B; the payload field (`params[:stack_id]`) is acted upon but never covered by the authorization check that supposedly binds the token to a single stack. This exactly mirrors the report's root cause: an internal ownership/scope mapping (`stack_id`) that is bypassed by a code path (`CCMenuController#stack`) that doesn't go through the mechanism (`BaseController#stacks`) meant to enforce it.

### Impact Explanation
Any holder of a stack-scoped `ApiClient` token (e.g. the per-user "CCMenu Client" minted by `CcmenuUrlController`, or any admin-issued stack-restricted token) can enumerate and read CI/deploy status (`shipit/ccmenu/project` XML, including last build status/label/time and lock state) for every stack in the Shipit installation, not just the one it was authorized for. This is an unauthenticated-scope read of stack state beyond the token's granted authorization — matching the "unauthenticated read of stack state" High-impact category, since it defeats the deliberate per-stack restriction (`stack_id`) that is the only mechanism by which `ApiClient` tokens can be limited to a subset of stacks.

### Likelihood Explanation
High/likely to be exploitable whenever stack-scoped tokens are used: the attacker only needs one valid token that was scoped to a single stack (a normal, documented `ApiClient` configuration, and the exact configuration exercised in `test/fixtures/shipit/api_clients.yml`'s `here_come_the_walrus` fixture, which has `stack: shipit`). No additional privilege is required — simply changing the `stack_id` request parameter against the `ccmenu` endpoint is sufficient, since `require_permission` only checks the permission name, not the stack scope, and `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (and in `CcmenuUrlController`, if it faces similar risk) and instead rely on the scoped `stacks`/`stack` helpers from `Api::BaseController`, so that `Stack.from_param!` is always evaluated against `current_api_client`'s authorized stack set. Add a regression test that asserts a stack-scoped `ApiClient` token receives a 404/403 when the `stack_id` in the ccmenu request does not match its `stack_id`.

### Proof of Concept
1. As an admin, mint (or observe an existing) `ApiClient` scoped to a single stack, e.g. `here_come_the_walrus` with `stack: shipit`, `permissions: ['read:stack']` (see `test/fixtures/shipit/api_clients.yml`).
2. Generate its `authentication_token` (`ApiClient#authentication_token`).
3. Request `GET /api/stacks/:other_stack_id/ccmenu.xml?token=<token>` where `:other_stack_id` is **not** the stack the client was scoped to.
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds and returns CI status for the unauthorized stack, even though `current_api_client.stack_id` restricts the token to a different stack.
