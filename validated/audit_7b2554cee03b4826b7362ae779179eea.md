### Title
Unbounded synchronous recursion in nested-address definition evaluation causes stack-overflow DoS - (File: `ocore--018/definition.js`)

### Summary
`AcroForm::scanField`'s bug class — recursive descent into a structure that can reference itself, with no loop/depth protection — has a direct analog in ocore's address-definition evaluators. Both `validateDefinition()` and `validateAuthentifiers()` in `definition.js` recursively resolve the `'address'` operator by fetching another address's definition and re-evaluating it in the same, purely synchronous JS call stack, with no per-recursion stack-unwind (`setImmediate`) protection like the one used elsewhere in the codebase for exactly this reason.

### Finding Description
When `evaluate()` encounters the `'address'` opcode inside a definition, it loads the referenced address's definition and calls itself again on that nested definition, synchronously within `readDefinitionByAddress`'s `ifFound`/`ifDefinitionNotFound` callback: [1](#0-0) 

The counterpart in `validateAuthentifiers()` performs the identical unbounded recursive pattern, but with no complexity accounting at all in that function's `evaluate`: [2](#0-1) 

`validateDefinition()`'s `evaluate` at least increments a `complexity`/`count_ops` counter on every call and aborts once `MAX_COMPLEXITY`/`MAX_OPS` is exceeded: [3](#0-2) 

However, this counter check happens on the JS call stack itself — there is no `setImmediate`/`process.nextTick` stack-unwind on every N calls, unlike the equivalent formula evaluators (`formula/validation.js`, `formula/evaluation.js`, `aa_validation.js`) which explicitly interrupt the call stack every 100 iterations specifically "to prevent Maximum call stack size exceeded": [4](#0-3) [5](#0-4) [6](#0-5) 

Because address-definition recursion in `definition.js` has no analogous stack-unwind, and inner `'address'` lookups (especially those resolved via `arrDefiningAuthors` matching `author.definition` in the same unit, or via cached DB reads) can return synchronously/in the same tick, a chain of nested `'address'` references embedded across co-author definitions in a single posted unit can drive the recursion depth high enough to hit V8's native call-stack limit (`RangeError: Maximum call stack size exceeded`) before the `complexity`/`MAX_COMPLEXITY` check has a chance to reject the definition — the same "lack of loop checking → recursion crash" defect the CVE describes for `AcroForm::scanField`.

### Impact Explanation
A crash (uncaught `RangeError`) during unit validation on a full node is a process-level denial of service: the validating node crashes or the validation pipeline throws, potentially affecting all nodes that process the same malicious unit (since `validateAuthentifiers`/`validateDefinition` run during standard unit and address-definition validation, on the write path any node must execute to accept/reject the unit). This can stall confirmation of new units network-wide if the crash occurs in the hub/witness validation path, which matches "node disagreement / network unable to confirm new units" impact class.

### Likelihood Explanation
An unprivileged unit poster can author a unit with multiple co-authors whose definitions chain `'address'` references to one another (A→B→C→…), each definition matched via the `arrDefiningAuthors` in-unit lookup (`author.definition` + `chash`) at line 289-301, requiring no privileged access, no prior on-chain address history, and no cooperation from other parties — just careful crafting of a single unit's `authors[]` array with many co-author definitions and matching addresses. This is directly reachable by "an unprivileged unit poster," matching the allowed threat scope. Likelihood depends on exactly how many nesting levels are needed to exceed V8's default stack size versus how many are needed to hit `MAX_COMPLEXITY`; this could not be fully confirmed without executing the code (exact stack frame size per `evaluate` call, and the concrete value of `MAX_COMPLEXITY` in `constants.js`, were not verified in this session).

### Recommendation
Add the same "interrupt the call stack" pattern already used in `formula/validation.js` and `aa_validation.js` to `definition.js`'s `evaluate()` functions in both `validateDefinition()` and `validateAuthentifiers()`: periodically (e.g., every 20–100 recursive descents into a nested `'address'` definition) yield via `setImmediate`/`process.nextTick` before continuing, so the complexity/op-count guard is guaranteed to run before the native JS stack is exhausted. Additionally, track visited addresses along the current path and reject direct or indirect self-reference cycles explicitly, rather than relying solely on a complexity counter to eventually catch runaway recursion.

### Proof of Concept
Conceptually: post a single unit with N co-authors, `author_1 .. author_N`, each supplying an inline `definition` of the form `['address', address_of_author_(i+1)]`, with `author_N`'s definition looping back to `author_1`'s address (or simply chaining to sufficient depth). During `validateAuthentifiers`/`validateDefinition`, `evaluate()` recurses through the `'address'` case at `definition.js:269-304` and `definition.js:774-800` once per co-author link, synchronously, with no stack-unwind — if the chain is deep enough (or looped), this can throw `RangeError: Maximum call stack size exceeded` before the complexity limit at `definition.js:103-111` is reached, crashing the validating process. Full exploitation (exact required chain depth vs. `MAX_COMPLEXITY`/stack limits) would need to be verified experimentally.
