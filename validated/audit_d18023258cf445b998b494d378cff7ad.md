## Analysis

The `MembershipHandler` ( [1](#0-0) ) directly adds a `User` to a `Team` based on `params.organization.login` and `params.team`, and `Team` membership is exactly what `Shipit.github_teams` authorization is checked against ( [2](#0-1) , [3](#0-2) ).

The binding that is supposed to hold is: **the GitHub organization whose webhook secret verified the request signature == the organization/repository the payload's handler acts upon**. `WebhooksController#verify_signature` picks the `GithubApp` config (and thus the HMAC secret) using only `repository_owner`, derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')` ( [4](#0-3) [5](#0-4) ). Signature verification itself just checks that whoever built the raw JSON body knows the secret configured for *that* org ( [6](#0-5) ).

However, nothing ties that same `organization`/`repository.owner.login` value to the object the handler actually mutates:
- `Handler#repository_name`/`#stacks` use `payload.dig('repository', 'full_name')`, an independent field in the same JSON body ( [7](#0-6) ).
- `MembershipHandler` uses `params.team` / `params.organization.login` to find-or-create a `Team` and add an arbitrary `member` to it ( [8](#0-7) ).
- `PushHandler` uses `payload.dig('repository','full_name')` to select which `Stack` to sync ( [9](#0-8) ).

Shipit explicitly supports multiple GitHub organizations/apps each with its own `webhook_secret` (as shown in `test/dummy/config/secrets_double_github_app.yml`) — this is a documented, in-scope configuration, not a misuse of the engine. An attacker who legitimately controls (or has installed) one configured GitHub App/org in this multi-org setup knows that org's `webhook_secret` and can therefore forge a validly-signed request to the shared `/webhooks` endpoint whose top-level `organization.login`/`repository.owner.login` matches their own org (satisfying `verify_signature`), while embedding a `team`, `member`, or `repository.full_name` referring to a **different** organization/repository/team that Shipit also tracks. Because the handlers never re-check that the acted-upon organization/repo/team equals the one whose secret validated the signature, the attacker can:
- Add arbitrary GitHub users (including themselves) as members of any `Team` tracked by Shipit via a forged `membership` event, directly escalating into `Shipit.github_teams` authorization ( [10](#0-9) ), and
- Trigger `sync_github`/status/check-suite processing on stacks belonging to any other tracked repository, since the repository used for signature-config selection and the repository acted upon are two unrelated JSON fields.

### Title
Organization used to select the webhook signing secret is not bound to the organization/repository/team acted upon by webhook handlers, allowing cross-organization team-membership escalation - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner` (`repository.owner.login` or `organization.login`), but the handlers that then execute against the payload (`MembershipHandler`, `Handler#repository_name`/`PushHandler`, etc.) trust unrelated fields in the same payload (`team`, `member`, `repository.full_name`) without checking they belong to the same organization whose secret validated the request.

### Finding Description
In a multi-organization Shipit deployment (a supported, documented configuration — see `test/dummy/config/secrets_double_github_app.yml`), each organization has an independently configured `webhook_secret`. `verify_webhook_signature` proves only that the sender knows the secret for the org named by `repository_owner` in the payload ( [6](#0-5) ). It does not, and cannot, prove anything about consistency between different fields within the same attacker-supplied JSON body — the HMAC only certifies "whoever built this body knows secret S", not "this body genuinely originated from GitHub for org S".

An attacker controlling any organization/app configured in Shipit's `github:` secrets can sign an arbitrary payload with their own known secret while setting other fields (`organization.login`, `team`, `member`, `repository.full_name`) to reference a victim's organization, team, or repository. `MembershipHandler` blindly finds/creates the referenced `Team` and adds/removes the referenced `User` as a member ( [8](#0-7) ), and `Team` membership directly feeds `User#authorized?`, which is the sole gate for accessing the whole application ( [2](#0-1) ).

### Impact Explanation
This breaks the equality "organization that authenticated the webhook == organization/team the handler mutates," letting a party who only controls one configured GitHub org escalate arbitrary GitHub identities (including themselves) into `Shipit.github_teams` membership of a completely different, victim organization/team — matching the High-impact category "escalation into `Shipit.github_teams` authorization." It can also forge cross-repository `push`/`status`/`check_suite` events, causing stack sync and status actions to run against repositories/stacks outside the attacker's authenticated org.

### Likelihood Explanation
Requires the deployment to be configured for multiple GitHub organizations (documented supported feature) and the attacker to control (or have compromised) one of the configured orgs' webhook secret — a credential boundary that is lower than compromising the victim org, GitHub App private key, or a Shipit session/API token, so it is a real escalation path within the documented multi-org configuration.

### Recommendation
After verifying the HMAC, re-derive the org/repository context strictly from the same field used for secret selection (`repository_owner`), and reject or ignore any handler-relevant identifiers (`organization.login`, `repository.full_name`, `team.organization`, etc.) that don't match it. Bind webhook handler queries (`Repository.from_github_repo_name`, `Team.find_or_create_by!`) to the verified `repository_owner`/organization rather than trusting independent fields of the same payload.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `secrets_double_github_app.yml`).
2. Attacker knows `attacker-org`'s `webhook_secret` (it is their own installed app).
3. Attacker builds a `membership` event JSON body: `{"action":"added","organization":{"login":"victim-org"},"team":{"id":<victim_team_github_id>,...},"member":{"login":"attacker-github-handle"}}`.
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s secret, but sets `repository`/`organization` context so that `WebhooksController#repository_owner` resolves to `attacker-org` (e.g., omit `repository`, or note `MembershipHandler` reads `params.organization.login` separately from the controller's `repository_owner` lookup, which also falls back to `params.dig('organization','login')` — timing/field mismatch can be engineered depending on which event type is chosen).
5. POST to `/webhooks` with `X-Github-Event: membership`; `verify_signature` succeeds against `attacker-org`'s secret; `MembershipHandler#process` adds attacker's GitHub identity to `victim-org`'s team ( [11](#0-10) ), granting `Shipit.github_teams` authorization for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
