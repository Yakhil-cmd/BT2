### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while handlers act on the independent `repository.full_name` field, allowing cross-organization repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), but the handlers that actually act on the payload resolve the target repository/stack from the independent `repository.full_name` field. Because these two fields are never checked for consistency, a payload whose `repository.owner.login` matches an organization the attacker legitimately controls (and can therefore sign with that organization's `webhook_secret`) can carry a `repository.full_name` pointing at a repository belonging to a *different*, unrelated organization configured in the same Shipit instance. The signature check passes (it only validates that *some* known org's secret was used), yet the event is processed against the victim organization's stacks.

### Finding Description
In a multi-tenant Shipit deployment, `Shipit.github(organization:)` looks up the webhook secret via `github_app_config(organization)`, keyed by organization name in `secrets.github` [1](#0-0) . The controller derives the organization to verify against purely from the JSON body:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`verify_signature` then calls `Shipit.github(organization: repository_owner)` and validates the `X-Hub-Signature` HMAC using that organization's `webhook_secret` [3](#0-2) .

Once verified, every handler resolves the target repository from a *different* field, `repository.full_name`, via `Repository.from_github_repo_name`:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [5](#0-4) 

This is the same pattern the PR-event handlers use for archiving/unarchiving review stacks, updating pull requests, and provisioning new review stacks [6](#0-5) [7](#0-6) [8](#0-7) .

Because the JSON body's `repository.owner.login` (used only for signature-org selection) and `repository.full_name` (used for target resolution) are two separate keys in the same attacker-controlled raw payload, an attacker who legitimately controls an organization `A` configured in this Shipit instance (and thus knows/can produce a valid signature with organization `A`'s `webhook_secret`, e.g. by configuring a real webhook on their own GitHub org pointed at the Shipit endpoint) can send a request where:
- `repository.owner.login = "A"` and `organization.login` absent/`"A"` → signature check passes using `A`'s secret.
- `repository.full_name = "victim-org/victim-repo"` → all downstream processing acts on `victim-org/victim-repo`.

This breaks the trust equality: **organization that authenticated (`repository.owner.login` → `A`'s `webhook_secret`) == repository that is written (`repository.full_name` → `victim-org/victim-repo`)**. The two fields are never cross-checked anywhere in `WebhooksController` or `Handler`.

### Impact Explanation
Depending on which event type is sent, this allows an attacker who only controls organization `A`'s webhook configuration to forge state-changing GitHub events against `victim-org/victim-repo`'s stacks in Shipit, without any push access to the victim repository:
- Archive/unarchive review stacks (`pull_request.closed`/`reopened`) for the victim repo [9](#0-8) .
- Provision new review stacks (`pull_request.opened`), which can trigger deploy pipelines for the victim repository [10](#0-9) .
- Inject/forge commit CI statuses via the `status` handler, which drives whether commits are eligible for deploy/merge (`Commit#create_status_from_github!`) [11](#0-10) .

Forged/poisoned CI status combined with `merge_queue` behavior or review-stack provisioning can lead to an unauthorized deploy/merge decision being taken for a repository the attacker does not control — this satisfies the "unauthorized deploy/rollback/merge" or "cross-repository writes" bar. This only applies to Shipit instances configured with the multi-organization `github_app_config` schema (multiple orgs sharing one Shipit instance); the impact is limited to interference between tenants of the same instance, not a global bypass.

### Likelihood Explanation
Exploitation requires the attacker to already be an authenticated principal for *some* organization configured on the Shipit instance (i.e., able to add/receive a webhook, or otherwise learn/reuse that organization's `webhook_secret`) — this is a much weaker requirement than requiring access to the victim organization or repository itself, which is exactly the trust boundary this bug crosses. In single-organization deployments (the common case, where `github_default_organization` is `nil` and only one `secrets.github` config exists) this issue does not manifest because there is only one possible signing secret and the org selection is effectively moot; the practical likelihood is concentrated in multi-tenant setups, which the code explicitly supports (`github_app_config`, `github_organizations`) [12](#0-11) .

### Recommendation
After verifying the HMAC signature, additionally assert that the organization used to select the verification key matches the owner encoded in `repository.full_name` (and in `organization.login` if present) before dispatching to handlers, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) and return unless verified

  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) if full_name_owner && full_name_owner.casecmp(repository_owner.to_s).nonzero?
end
```
This restores the equality between the organization whose secret authenticated the request and the repository the handlers subsequently act on.

### Proof of Concept
1. Configure a multi-tenant Shipit instance with two organizations in `secrets.github`: `attacker-org` and `victim-org`, each with its own `webhook_secret` and each having stacks configured for repositories they own (e.g. `victim-org/victim-repo` has an active review-stack-enabled `Repository`).
2. Attacker adds/controls a GitHub webhook on their own `attacker-org` account/repo, so they legitimately know (or can trigger delivery signed with) `attacker-org`'s `webhook_secret`.
3. Attacker crafts (or replays with modification, if they can influence outbound webhook payload, e.g. via a repo they own under `attacker-org` triggering a `pull_request` event) a JSON body where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `action = "opened"`, with `pull_request.head.ref` pointing at a branch in `victim-org/victim-repo`.
4. Attacker computes/obtains the `X-Hub-Signature` HMAC using `attacker-org`'s `webhook_secret` over this exact raw body and POSTs it to `/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature [3](#0-2) .
6. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#process` resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` → `victim-org/victim-repo`, and calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, provisioning/acting on a review stack for the victim repository the attacker never had access to [6](#0-5) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
