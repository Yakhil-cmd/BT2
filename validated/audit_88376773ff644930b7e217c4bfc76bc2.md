### Title
`CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, allowing cross-stack enumeration - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `#stack` helper from `BaseController` to resolve stacks via `Stack.from_param!(params[:stack_id])` directly, instead of `stacks.from_param!(params[:stack_id])`. Since `stacks` in `BaseController` is what applies the `current_api_client.stack_id` restriction, any `ApiClient` with the `read:stack` permission bit (even one scoped to a single, unrelated stack) can retrieve deploy status for any stack in the instance by guessing/enumerating `stack_id` params.

### Finding Description
The intended binding is: `stack.id ∈ stacks.pluck(:id)`, where `stacks` is defined as:
`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) 

This scoping is correctly applied by `BaseController#stack`, which calls `stacks.from_param!(params[:stack_id])` [2](#0-1) .

`CCMenuController` redefines `#stack` to skip `stacks` entirely: `@stack ||= Stack.from_param!(params[:stack_id])` [3](#0-2) . This resolves against the full `Stack` table regardless of `current_api_client.stack_id`.

The only authorization gate on this controller is `require_permission :read, :stack`, which is a `before_action` calling `current_api_client.check_permissions!(:read, :stack)` [4](#0-3) . `check_permissions!` only checks whether the literal string `"read:stack"` is present in the client's `permissions` array [5](#0-4) ; it has no knowledge of which stack is being requested and never consults `stack_id`.

Attack: obtain (legitimately, as an authorized operator of stack A) or otherwise possess an `ApiClient` token whose `permissions` include `read:stack` and whose `stack_id` is scoped to stack A only. Then issue `GET /:stack_id/cc.xml?token=<token_for_stack_A>` (or via Basic Auth) with `stack_id` set to `org/repo/production` (stack B, unrelated/private). `#show` calls `stack.deploys_and_rollbacks.last`, rendering `lastBuildStatus`, `lastBuildLabel`, `webUrl`, `activity` for stack B [6](#0-5) . Because `#stack` never intersects with the client's authorized `stacks`, this succeeds with 200 for any existing `stack_id`, and a 404 for non-existent ones — enabling enumeration of which private stacks exist and their current build/deploy status.

None of the existing guards prevent this: `require_permission` checks only the static permission string, not stack identity; there is no `ExplicitParameters` schema on this action; `authenticate_api_client` is overridden here to also accept `params[:token]` but this only affects authentication method, not stack scoping [7](#0-6) .

### Impact Explanation
An `ApiClient` scoped to one stack can read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) of any other stack in the instance, including stacks belonging to unrelated repositories/tenants, by brute-forcing `owner/repo/environment` triples in `stack_id`. This is repeatable indefinitely and across arbitrary stacks — it is an unauthenticated (relative to the target stack) read of stack/deploy state across tenants, matching the "High" impact category (unauthenticated read of stack state across tenants).

### Likelihood Explanation
Preconditions: attacker needs *any* valid `ApiClient` token with `read:stack` permission for *some* stack (even one they legitimately administer). No secrets belonging to the target stack, no GitHub credentials, and no operator/maintainer role on the target repo are required. Cost is low: a single valid token plus knowledge/guessing of `owner/repo/environment` naming conventions (often predictable, e.g. `org/repo/production`). Fully repeatable against any number of stacks.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` collection inherited from `BaseController` instead of querying `Stack` directly, e.g. replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])`, so resolution is bound to `current_api_client.stack_id` scoping exactly as in `BaseController#stack`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's cc.xml" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "private-repo"), branch: 'master', environment: 'production')

  client_scoped_to_a = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack: stack_a,
    permissions: ['read:stack']
  )

  # Binding under test: stack_b.id must NOT be in the set authorized for client_scoped_to_a
  assert_not_includes Stack.where(id: client_scoped_to_a.stack_id).pluck(:id), stack_b.id

  get :show, params: { stack_id: stack_b.to_param, token: client_scoped_to_a.authentication_token }

  # Vulnerable behavior: returns 200 with stack B's data despite scoping to stack A
  assert_response :ok
  project = Hash.from_xml(response.body)['Projects']['Project']
  assert_equal stack_b.to_param, project['name']
end
```
