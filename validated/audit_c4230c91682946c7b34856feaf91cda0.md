### Title
RAY value overflow during interest accrual permanently freezes a large high-utilization market - (File: `contracts/pool/src/interest.rs`)

### Summary
Interest accrual calculates total borrowed and supplied RAY values with `i128`-representable fixed-point results. Once `scaled_amount * index` exceeds `i128::MAX`, `scaled_to_original` panics with `MathOverflow` before the borrow-index ceiling can be reached. Because every state-changing market operation accrues before executing, this numeric overflow permanently blocks withdrawals, repayments, liquidations, recapitalization, and further index updates for that market. The integration test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the condition and confirms that `withdraw` and `repay` subsequently revert with `MathOverflow`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`global_sync` is called when market state is loaded and processes elapsed time through `accrue_chunk`. Each chunk invokes `accrue_step`, after which the cache writes the new borrow and supply indexes. [4](#0-3) 

The market's utilization calculation materializes RAY-scaled book values using:

```rust
let total_borrowed = scaled_to_original(&self.env, self.borrowed, self.borrow_index);
let total_supplied = scaled_to_original(&self.env, self.supplied, self.supply_index);
```

This happens inside `Cache::calculate_utilization`. [1](#0-0) 

The supplied and borrowed totals are RAY-scaled share quantities, not ordinary token-unit balances. For an 18-decimal asset, one billion whole tokens produce approximately `1e36` RAY units of scaled supply. Since `i128::MAX` is approximately `1.70e38`, an index increase of roughly 170× is sufficient to push the materialized value beyond the representable range. The configured `MAX_BORROW_INDEX_RAY` ceiling does not prevent this because the overflow occurs while computing the value used by the accrual/rate path before a capped result can safely be committed. [5](#0-4) 

After the first accrual fails, the last committed state remains below the index ceiling but still close enough that every subsequent accrual repeats the same overflowing calculation. `LiquidityPool::update_indexes` performs this accrual for every requested market. [6](#0-5) [7](#0-6) 

The exposed controller paths inherit the same failure because their owner-only pool calls load and accrue the market first. This includes `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, flash operations, and debt/collateral strategies touching the affected `(hub, asset)` book. [8](#0-7) [9](#0-8) 

### Impact Explanation
All user funds represented by the affected market can become permanently frozen. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot clear underwater positions, and recapitalization cannot rescue the book because these paths must pass through accrual first. The protocol cannot reduce the oversized scaled totals or roll back to a usable index through a public flow. [10](#0-9) 

This is more than an isolated transaction failure: the last committed market state deterministically overflows on every later invocation. The affected market remains operational only until the first post-threshold accrual attempt; afterward, its accounting state cannot advance.

### Likelihood Explanation
Exploitation requires a market configured with very large caps and enough decimals for actual deposits to create a large RAY-scaled base. An attacker also needs enough collateral to establish sustained high utilization and enough time for the borrow index to approach the overflow threshold. The test scenario uses approximately one billion 18-decimal tokens and 98% utilization. [11](#0-10) 

Those requirements are substantial, but they do not require privileged access, malformed storage, a malicious oracle, or an unsafe token implementation. If a production listing admits enough supply, an unprivileged account can provide the target liquidity and collateral through ordinary `supply` and `borrow` calls. After the threshold is crossed, any user can trigger the freeze with `update_indexes` or any operation touching the market. [12](#0-11) [7](#0-6) 

### Recommendation
Do not materialize unbounded scaled totals as an `i128` value during accrual. Use a wider intermediate representation, a checked saturation bound, or a two-stage calculation that applies `MAX_BORROW_INDEX_RAY` before multiplying potentially overflowing totals.

A robust fix should:

- compare or cap the prospective borrow index before evaluating `scaled_to_original`;
- preserve utilization calculation when totals exceed `i128`, for example by computing the utilization ratio through `I256` or algebraically reducing `scaled / index`;
- add an invariant that the index ceiling is reached before the RAY-value representation ceiling for every admissible cap and decimal configuration;
- keep a public recovery path that can accrue and clamp a market already at the boundary without requiring lower-level state surgery;
- extend regression coverage beyond the existing test to withdrawals, repayments, liquidations, bad-debt cleanup, and recapitalization after the cap engages.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
