### Title
Webhook signature verification key is selected from an unauthenticated payload field that is never bound to the field handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to validate the `X-Hub-Signature` HMAC by reading `repository.owner.login` (or `organization.login`) directly out of the *same, still-unverified* JSON body. Every webhook handler, however, resolves the target `Repository`/`Stack` from a different field of that same body: `repository.full_name` (`Handler#repository_name`). Nothing ties these two fields together, so the "organization whose secret authenticated the request" and the "repository the handlers actually mutate" are never proven to be the same tenant.

`verify_signature` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` and used only to pick which per-organization `webhook_secret` (`Shipit.github(organization: repository_owner)`) validates the signature over the raw body.

Once the signature check passes, `create` dispatches the *entire* parsed body to the registered handler for the event: [3](#0-2) 

Every handler resolves the affected repository/stack from a **different key** in that same body: [4](#0-3) 

e.g. `PushHandler#process` looks up stacks via `stacks` (built from `repository.full_name`) and syncs them: [5](#0-4) 

and `CheckSuiteHandler` similarly acts on `stacks` derived from `full_name`: [6](#0-5) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon repository) live in the same attacker-controlled JSON payload and are never cross-checked, the equality the system implicitly relies on —
`organization authenticated via webhook_secret == organization owning the repository the handler writes to`
— is not enforced anywhere in `WebhooksController` or `Shipit::Webhooks::Handlers::Handler`.

In a single-organization deployment this is latent (both fields always describe the same org in a real GitHub-issued payload), but Shipit explicitly supports multi-organization configurations (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple Github Applications"), each with its own independent `webhook_secret`: [7](#0-6) 

Any org whose GitHub App webhook secret is compromised, weak, or intentionally left blank (`webhook_secret` is documented as optional and `verify_webhook_signature` returns `true` when absent) becomes a valid signer for a payload that names a *different* org's repository in `repository.full_name`: [8](#0-7) 

### Impact Explanation
An attacker who can produce a validly-signed payload for **any one** configured organization (including one with no `webhook_secret` set, which requires no secret at all) can set `repository.owner.login` to that organization while setting `repository.full_name` to an arbitrary, unrelated org/repo pair known to Shipit. The signature check passes (it only validates against the attacker-chosen `repository_owner`), and the dispatched handler then acts on the victim org's stacks:
- `PushHandler` enqueues `GithubSyncJob` for the victim stack, forcing Shipit to fetch and append arbitrary attacker-influenced commit history into a victim's deploy queue and to invalidate/rebuild its cached deploy spec.
- `CheckSuiteHandler` forces `schedule_refresh_check_runs!` on victim commits, letting an attacker manipulate CI/check-run state used by merge/deploy safety gates on a repository they don't own.
- Pull-request handlers (`ReopenedHandler`, `LabelCapturingHandler`, etc.) resolve `Repository.from_github_repo_name(params.repository.full_name)` and can unarchive review stacks or mutate PR/label state for a victim repository.

This breaks the "organization that authenticated vs. repository that is written" binding and enables cross-repository/cross-organization state manipulation with no legitimate credential for the victim organization.

### Likelihood Explanation
Exploitability depends on the attacker having *any* organization configured in Shipit for which they can produce a valid signature — trivially true for organizations left with no `webhook_secret` (documented as optional), and otherwise requires knowledge of one org's secret. Given that operators are told the field is optional and multi-org setups are a first-class documented feature, this is a realistic misconfiguration/multi-tenant scenario, not a purely theoretical one.

### Recommendation
Bind signature verification to the same repository identity the handlers act on:
- After verifying the HMAC with the organization selected from `repository.owner.login`/`organization.login`, additionally require that `repository.full_name`'s owner segment (and/or the resolved `Repository#owner`) matches `repository_owner` before dispatching to handlers.
- Alternatively, resolve the `Repository` first (from `full_name`), derive its trusted `github_app`/secret from the stored `Repository`/stack configuration rather than from unauthenticated payload fields, and reject the webhook if the payload's claimed owner doesn't match the repository's actual configured organization.
- Do not allow `verify_webhook_signature` to return `true` (i.e., skip verification) purely because `webhook_secret` is unset in a multi-organization configuration; require an explicit secret per organization in that mode.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (secret known/blank) and `OrgB` (victim, has a stack tracked in Shipit) — as supported by `docs/setup.md`'s multi-org config.
2. Craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Sign the raw body with `OrgA`'s webhook secret (or send unsigned if `OrgA` has none configured) and set `X-Hub-Signature` accordingly; set `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and verifies successfully.
5. `create` dispatches the parsed body to `PushHandler`, which resolves `repository_name` from `repository.full_name = "OrgB/victim-repo"` and enqueues `GithubSyncJob` for `OrgB`'s stack — despite the request never being authenticated by anything belonging to `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
