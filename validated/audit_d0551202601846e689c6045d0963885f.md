### Title
Cross-repository status webhook can clear a blocking status on another stack's commit, unblocking `Commit#blocked?` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` matches commits purely by `sha`, without scoping to the repository named in the verified payload, unlike every other webhook handler in this codebase. An attacker who controls a repository/organization that shares a commit sha with a target stack (e.g. via a public fork, which by git's nature shares identical commit shas for common history) can send a validly-signed `status` webhook for their own repo and have it applied to the commit row belonging to a victim stack, altering that commit's CI state (e.g. flipping a `blocking_statuses` context to `success`).

### Finding Description
The broken binding: the question posits `commit.stack.repository.full_name == payload['repository']['full_name']` should hold for any `Status` record created by a webhook, but it does not.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the attacker-controlled `payload['repository']['owner']['login']`. This only proves the payload was signed with the webhook secret configured for *that organization* - an org the attacker fully controls (their own fork/repo), giving them the secret needed to forge a valid signature for **their own** repository's events.
- Every other handler (`Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`, and e.g. `PullRequest::EditedHandler#repository`, `PullRequest::LabelCapturingHandler#repository`) explicitly resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and scopes all subsequent queries/writes to that repository's stacks.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not do this. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - a global, repository-agnostic lookup across the entire `commits` table.
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) creates a `Status` scoped to `commit.stack_id` (the victim stack), using `state`/`context` taken directly from the attacker's payload.
- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) evaluates `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)`, and `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) is `!success? && commit.blocking_statuses.include?(context)`. If the attacker's forged status sets `state: 'success'` for the exact `context` in stack B's `ci.blocking` list, on the commit whose sha collides, `blocking?` flips to `false` for that commit, and `blocked?` flips to `false` for every later commit in stack B - unblocking `deployable?` and `Stack#next_commit_to_deploy`/`trigger_continuous_delivery`.

Why guards fail: `verify_signature` only proves *an* organization's webhook secret was used, not that the *named repository* in the payload is authoritative over the *matched commit*. `drop_unhandled_event` and `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) do not perform any repository-ownership check. There is no `Repository.from_github_repo_name`/`stacks` scoping call anywhere in `StatusHandler`, which is the exact mechanism used elsewhere in the codebase to close this hole.

Feasibility caveat: this requires a real sha collision between the attacker's repository and the victim stack's repository. In practice this occurs naturally for forked repositories (shared git history/ancestor commits keep identical SHA1 hashes across the fork boundary), not a cryptographic SHA1 break. If Shipit tracks the upstream repo as a stack and an attacker's public fork shares ancestor commits, the attacker can trigger a `status` event on their own fork (e.g., by pushing a commit status via a CI integration they control on their fork, or directly POSTing to `/webhooks` with a payload signed by their own configured webhook secret if they operate their own GitHub App/webhook targeting the shared Shipit host) for a sha that also exists in the victim's stack. ### Impact Explanation
A payload correctly signed for repository A can create a `Status` on a `Commit` belonging to stack B (a different tenant/repository), overriding CI state data that Shipit's `ci.blocking` gate relies on. This bypasses tenant B's CI blocking-status safety gate, resulting in `Commit#blocked?`/`deployable?` returning `false`/`true` incorrectly and enabling `Stack#next_commit_to_deploy` / continuous-delivery to select and deploy commits that never actually passed the required blocking CI check on their own repository. This matches the Critical category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." Repeatable for any commit sha shared between an attacker-controlled repository and a victim stack (most realistically forked repositories with common ancestor history).

### Likelihood Explanation
Preconditions: the target stack must configure `ci.blocking` (a documented, common Shipit safety feature), and there must exist a commit sha shared between the attacker's repository and the victim stack (naturally the case for public forks that haven't diverged from a shared ancestor commit, or repositories mirroring the same upstream). The attacker needs no Shipit credentials - only control of a repository whose organization's webhook secret they know (their own fork's Shipit-configured GitHub App/webhook, or any repo they can wire up), consistent with the "unprivileged attacker" definition given. This is a straightforward, repeatable, low-cost attack against any Shipit deployment tracking upstream repos that are also publicly forkable.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring `Handler#stacks`/`Repository.from_github_repo_name`. E.g., restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or, more precisely, `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { id: Repository.from_github_repo_name(repository_name)&.id })`, ensuring a status can only be attached to a commit whose owning stack's repository matches the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "a status for a colliding sha in a different repository does not unblock a victim stack's blocked commit" do
  blocking_commit = shipit_commits(:soc_second)   # in stack `soc`, context configured in ci.blocking
  guarded_commit  = shipit_commits(:soc_third)     # later commit, gated by blocking_commit

  assert_predicate blocking_commit, :blocking?
  assert_predicate guarded_commit, :blocked?

  # Attacker-controlled repository, unrelated to `soc` stack, but git-forked so it
  # shares the sha of blocking_commit (simulated by forcing sha equality in fixtures)
  attacker_repository = shipit_repositories(:attacker_repo)

  payload = {
    'sha' => blocking_commit.sha,
    'state' => 'success',
    'context' => blocking_commit.stack.blocking_statuses.first,
    'repository' => { 'full_name' => attacker_repository.full_name,
                       'owner' => { 'login' => attacker_repository.owner } }
  }

  # Handler is invoked as it would be after verify_signature passes for attacker_repository's org
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  blocking_commit.reload
  guarded_commit.reload

  refute_predicate blocking_commit, :blocking?          # status flipped by cross-repo payload
  refute_predicate guarded_commit, :blocked?             # gate incorrectly lifted
  assert_equal guarded_commit, blocking_commit.stack.next_commit_to_deploy # now deployable
end
```
This test should fail before the fix (proving the vulnerability) and pass after scoping `StatusHandler#process` to the payload's repository.
