### Title
Legitimate stakers' rewards are silently burned instead of credited when the stake account is closed via `withdraw` before its partition is processed - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`store_stake_accounts_in_partition` looks up each stake account in a live `StakesCache` snapshot taken at the moment its partition is processed, not at the moment rewards were calculated for the previous epoch. An unprivileged staker who has already fully deactivated stake can, under their own withdrawer authority, call `solana_stake_program::instruction::withdraw` to zero out and close the account after reward calculation but before their `partition_index` is reached, causing `build_updated_stake_reward` to fail with `AccountNotFound` and the owed reward to be routed into `stake_reward_lamports_burned` rather than credited.

### Finding Description
`build_updated_stake_reward` resolves the reward recipient purely from `stakes_cache_accounts.get(&partitioned_stake_reward.stake_pubkey)`, a snapshot of `self.stakes_cache.stakes().stake_delegations()` taken fresh inside `store_stake_accounts_in_partition` at distribution time [1](#0-0) , and `store_stake_accounts_in_partition` refreshes this snapshot on every call [2](#0-1) .

Because rewards are only distributed a fraction of accounts per block across many blocks (`distribute_partitioned_epoch_rewards` walks `partition_index` per block height) [3](#0-2) , there is a window of multiple blocks between the reward-calculation snapshot (taken once, at the epoch boundary) and the block where any given account's `partition_index` is actually processed.

`StakesCache::check_and_store` removes a pubkey's delegation entirely once its lamports reach zero: `if account.lamports() == 0 { ... stakes.remove_stake_delegation(...) }` [4](#0-3) . A staker who deactivated their stake in a prior epoch (so `delegation_effective_stake` is already 0) can legitimately submit `withdraw` under their own withdrawer authority for the full balance — this is exactly the flow validated by the CLI's `test_stake_delegation_and_withdraw_all` (withdraw of all funds succeeds once stake is fully inactive) [5](#0-4) . Closing the account this way removes it from the `StakesCache` before the reward-distribution phase reaches its partition.

When `store_stake_accounts_in_partition` then processes that account's index, `build_updated_stake_reward` returns `DistributionError::AccountNotFound`, and the code explicitly burns the reward instead of crediting it: [6](#0-5) 

The function's own doc comment acknowledges this should be impossible ("Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned") [7](#0-6) , but no restriction preventing ordinary account-mutating instructions (including stake `withdraw`) during the active reward interval was found; a repository test explicitly demonstrates normal transactions continue to be processed against stake-owned accounts throughout the reward period [8](#0-7) .

The burned amount is added to `stake_reward_lamports_burned`, which is subtracted from the epoch-rewards sysvar's remaining pool via `update_epoch_rewards_sysvar(stake_reward_lamports_minted + stake_reward_lamports_burned, ...)` but is never added back to `self.capitalization`, and never re-paid to the staker [9](#0-8) . The result is a permanent, silent loss of the staker's earned reward for that epoch — a single-payment invariant violation via burn rather than credit.

### Impact Explanation
This falls under Reward-accounting for legitimate stakers: a staker who is fully entitled to a `DeactivatedStake`-type reward for the epoch in which their stake was still (partially) active loses that reward permanently and with no error surfaced to the user (only an `error!` log server-side) [10](#0-9) . This is not lamport creation/theft from other accounts, but it is a real violation of the "earn rewards for a given epoch exactly once" property (here: zero times) purely as a side effect of the staker exercising their own withdrawer authority in the normal course of unstaking, which should not be a rewards-forfeiting action.

### Likelihood Explanation
Preconditions are entirely under attacker control and require no privileged role: (1) have a delegated, staked account that earns a partitioned reward for the rewarded epoch, (2) deactivate it early enough that it is fully inactive by the time the reward-calculation block occurs, (3) immediately submit a `withdraw` for the full balance once the calculation block for the new epoch lands, racing to land before the specific block that processes their `partition_index`. Because distribution spans many blocks (partitioned by `partitioned_rewards_stake_account_stores_per_block`, up to 10% of an epoch's slots) [11](#0-10) , and partition assignment is a deterministic hash of `stake_pubkey` and `parent_blockhash` (computable by the attacker once the epoch-boundary block is known) [12](#0-11) , an attacker can predict whether their own withdraw will land ahead of their assigned block, making this reliably repeatable at the cost of losing/self-inflicting the burn on their own reward (a self-DoS on their own yield, not third-party theft).

### Recommendation
Do not treat `AccountNotFound` in `build_updated_stake_reward` as a silent burn path for accounts that were closed by their own owner's legitimate `withdraw`. Options: (1) resolve the stake account from a snapshot fixed at reward-calculation time rather than the mutable, live `StakesCache` at distribution time, so a subsequent withdrawal cannot retroactively erase entitlement; (2) if the account no longer exists at distribution time, deposit the owed lamports to a recoverable destination (e.g., increment the still-existing withdrawer/staker-controlled destination, or hold in a claimable escrow) instead of unconditionally discarding into `stake_reward_lamports_burned`; (3) explicitly document/enforce that `stake_reward_lamports_burned` is reserved for truly adversarial/impossible cases (e.g. arithmetic overflow) and add a guard that rejects/queues withdrawals for accounts with a still-pending partitioned reward.

### Proof of Concept
Rust integration test sketch (in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` test module, alongside `test_store_stake_accounts_in_partition`):

```rust
#[test]
fn test_withdraw_during_distribution_burns_reward() {
    let (genesis_config, _mint_keypair) = create_genesis_config(1_000_000 * LAMPORTS_PER_SOL);
    let bank = Bank::new_for_tests(&genesis_config);

    // Build a PartitionedStakeReward for a fully-deactivated stake account
    // (so DeactivatedStake reward applies), store the matching starting
    // stake account via populate_starting_stake_accounts_from_stake_rewards.
    let stake_reward = PartitionedStakeReward::new_random(); // deactivated variant
    populate_starting_stake_accounts_from_stake_rewards(&bank, &bank.rent_collector.rent, &[stake_reward.clone()]);

    // Simulate the attacker's own withdraw closing the account to zero
    // lamports BEFORE store_stake_accounts_in_partition runs, by directly
    // driving the account to zero and updating the stakes cache exactly as
    // the runtime would after a successful withdraw instruction:
    bank.store_account_and_update_capitalization(&stake_reward.stake_pubkey, &AccountSharedData::default());

    let partitioned_rewards = StartBlockHeightAndPartitionedRewards {
        distribution_starting_block_height: bank.block_height(),
        all_stake_rewards: Arc::new([Some(stake_reward.clone())].into_iter().collect()),
        partition_indices: vec![vec![0]],
    };

    let pre_cap = bank.capitalization();
    let DistributionResults {
        stake_reward_lamports_minted,
        stake_reward_lamports_burned,
        ..
    } = bank.store_stake_accounts_in_partition(&partitioned_rewards, 0);

    // Assert the reward was burned, not minted/credited to the staker.
    assert_eq!(stake_reward_lamports_minted, 0);
    assert_eq!(stake_reward_lamports_burned, stake_reward.inflation.stake_reward);
    assert!(bank.get_account(&stake_reward.stake_pubkey).is_none());
    // Capitalization does not reflect a payout to the staker for this epoch.
    assert_eq!(bank.capitalization(), pre_cap);
}
```

For a fuller end-to-end PoC, use `TestValidator`/`BanksClient` (as in `cli/tests/stake.rs::test_stake_delegation_and_withdraw_all`) to: delegate → deactivate → wait one epoch → at the next epoch boundary immediately submit `stake_instruction::withdraw` for the full balance before the block corresponding to the account's hashed `partition_index`, then assert via `bank.get_epoch_rewards_sysvar()` / `RewardsStoreMetrics.burned_rewards` that the staker's expected reward was logged as burned and never appears in the staker's post-distribution balance.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
