### Title
Unbounded Data-Feed Key-Range Scan in Address/Asset Definitions Causes Validation DoS - (File: data_feeds.js)

### Summary
The `in data feed` condition inside an address (or asset) definition [1](#0-0)  is evaluated by every full node whenever a unit that spends from (or references) that address is validated. This condition is resolved by `dataFeeds.dataFeedExists()`, which for `>`, `<`, `>=`, `<=` (and, recursively, for `!=`) relations opens a `kvstore` key stream and only stops early if a matching record is found [2](#0-1) . If the searched value never satisfies the relation among the oracle's posted feed values, the stream is read to completion with no cap on the number of records inspected, similar to the vLLM `best_of` issue where an attacker-controlled parameter (here: the size/history of the referenced data feed) drives unbounded per-request work with no resource ceiling.

### Finding Description
`dataFeedByAddressExists()` builds a `kvstore` range (`gte`/`lte`/`gt`/`lt`) keyed by `df\n<address>\n<feed_name>\n<value>` and streams every key in that range, counting matches and only calling `stream.destroy()` once a satisfying record is located [3](#0-2) . There is no `limit` option set for the `>`, `<`, `>=`, `<=` cases (unlike the `=` case, which sets `options.limit = 1`) [4](#0-3) , and there is no cap on how many feed values an oracle address may have posted over its lifetime.

`dataFeedExists()` (the AA/getter-facing wrapper) also recurses for the `!=` relation, invoking the `>` and `<` scans back-to-back, doubling the cost [5](#0-4) , and iterates the same scan for every address in the caller-supplied `arrAddresses` list via `async.eachSeries` [6](#0-5) .

This `in data feed` op is directly reachable from an ordinary address (or asset) definition, evaluated inside `validateAuthentifiers()` for every unit spending from, or invoking as an asset condition, that address [1](#0-0) . The generic complexity accounting in `definition.js` (`complexity++`, `count_ops++`, capped by `MAX_COMPLEXITY`/`MAX_OPS`) only limits the number of AST nodes evaluated [7](#0-6) ; it does not account for, or bound, the O(N) cost of the underlying `kvstore` scan performed by a single `in data feed` node, where N is the number of records the referenced oracle has ever posted for that feed name.

An attacker can:
1. Control (or collude with) an oracle address and post a large number of `data_feed` messages under a chosen `feed_name` over time (this is normal, permitted usage — no validation limits total feed history size).
2. Define an address whose spending condition includes `in data feed` referencing that oracle/feed with a relation/value pair that never matches any posted value.
3. Post ordinary units spending from that address (or units that trigger authentifier/asset-condition evaluation against it).

Every full node that validates such a unit must perform the full unbounded key-stream scan, and the attacker can repeat this with many units, degrading validation throughput for the whole network — the oscript/data-feed evaluation path is explicitly in-scope, unlike a raw network/p2p flood.

### Impact Explanation
Each spending unit referencing the crafted definition forces every validating node to execute an O(N) `kvstore` scan with no upper bound tied to real complexity accounting. Because units referencing this address can be posted repeatedly and cheaply (normal fee cost, no extra fee for the expensive scan), an attacker can impose disproportionate CPU/I-O cost on all full nodes during unit validation, delaying or stalling processing of legitimate units — a resource-exhaustion condition analogous to the vLLM `best_of` DoS, where a single caller-controlled parameter drives unbounded backend work.

### Likelihood Explanation
Building an oracle with a large feed history requires only ordinary, low-cost `data_feed` messages (no special privilege), and defining an address with an `in data feed` condition is a standard oscript feature available to any unit poster. No cap exists on data feed history size or on the number of records inspected per evaluation, so the attack is straightforward to mount and repeat.

### Recommendation
- Set a `limit` on the `kvstore` stream for the `>`, `<`, `>=`, `<=` cases in `dataFeedByAddressExists()`, similar to the `=`/`ifseveral` cases, or otherwise bound the number of records inspected per `in data feed` evaluation.
- Track and add to `count_ops`/`complexity` a cost proportional to the number of records actually scanned (or a configured worst-case bound) in `definition.js`'s `evaluate()` for the `in data feed` op, rather than treating it as a flat `complexity++`.
- Cap the length of `arrAddresses` passed to `in data feed`, and avoid doubling the cost silently for `!=` without accounting for it.

### Proof of Concept
1. Oracle address `O` posts `N` (e.g., 10⁶) `data_feed` messages with `feed_name = "x"` and monotonically increasing values, none of which will equal a chosen target `T`.
2. Attacker defines address `A` with condition `['in data feed', [['O'], 'x', '=', T]]`-like relation using `>`/`<` so no match exists (or `!=`, which triggers both scans).
3. Attacker (or anyone) posts a unit spending from `A`; `validateAuthentifiers()` calls `dataFeeds.dataFeedExists(['O'], 'x', '>', T, ...)` which streams through all `N` records in `data_feeds.js` before returning `false` [8](#0-7) .
4. Repeating step 3 with multiple units multiplies the cost across every validating node, without a corresponding increase in `complexity`/`count_ops` accounting that would otherwise reject the unit as "too expensive."
