### Title
Webhook Signature Verified Against `repository.owner.login`/`organization.login` While Handlers Act on Unrelated `repository.full_name` or Global Commit SHA — Cross-Tenant Writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using the GitHub App/secret associated with the organization derived from `repository.owner.login` (or `organization.login`) in the JSON body. However, the handlers invoked afterward select the `Repository`/`Stack`/`Commit` records to mutate using a *different* field of the same attacker-controlled payload (`repository.full_name`, or in one handler, a bare commit SHA with no repository scoping at all). The signature check never verifies that the org used for authentication actually owns the repository being written to, breaking the intended binding `organization authenticated == repository written`.

### Finding Description
The controller derives the signing organization solely from the payload itself, before any signature validation of cross-field consistency: [1](#0-0) [2](#0-1) 

Once `verify_signature` passes (i.e., the HMAC matches the webhook secret configured for whatever `repository_owner` the attacker supplied), the full raw payload is forwarded unmodified to the registered handlers: [3](#0-2) 

The base `Handler` class then resolves which `Stack`/`Repository` to act on using a completely independent JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` that was used for signature verification: [4](#0-3) 

`PushHandler` uses this unbound `stacks` lookup to trigger a GitHub sync on any stack matching the attacker-chosen `repository.full_name` and branch, using an attacker-chosen `after` SHA: [5](#0-4) 

`StatusHandler` is worse still — it does not even use the repository-scoped `stacks` helper. It matches commits **globally by SHA alone**, across every repository/stack in the entire Shipit instance, and writes a GitHub status onto them: [6](#0-5) 

`CheckSuiteHandler` similarly acts on `stacks` derived from the unbound `repository.full_name`: [7](#0-6) 

**Root cause:** `verify_signature` binds trust to `repository_owner` (from `repository.owner.login`/`organization.login`), but every downstream handler binds its write target to a *different* attacker-supplied field (`repository.full_name`, or nothing at all in `StatusHandler`). Nothing in the request pipeline enforces that these two identify the same repository/organization. In a multi-tenant Shipit deployment (multiple entries under `Shipit.github_organizations`, each with its own `webhook_secret`), any organization admin who can produce a validly-signed webhook for their *own* org can forge `repository.full_name` (or, for `status`, an arbitrary known commit SHA) to target a completely different tenant's stacks.

### Impact Explanation
This breaks the "organization authenticated versus repository written" binding explicitly called out as in-scope, and results in **cross-repository writes**: an attacker who controls (or is a legitimate admin of) one organization configured in this Shipit instance can create/advance commits and trigger `stack.sync_github` on another organization's stacks (`PushHandler`), attach arbitrary commit statuses to any commit in the system regardless of ownership (`StatusHandler`), or trigger check-run refreshes on foreign stacks (`CheckSuiteHandler`). Forged/advanced commit status and `sync_github` calls can influence deployability checks (`Commit#create_status_from_github!`) and the commit set considered for merge/deploy decisions on a stack the attacker does not own — this is a direct cross-tenant write and can feed into unauthorized deploy/merge decisions that rely on commit status state.

### Likelihood Explanation
Requires the attacker to be able to produce one validly-signed webhook body for *any* organization configured in the multi-tenant Shipit instance (e.g., their own org's webhook secret, or an org whose `webhook_secret` is left blank — in which case `verify_webhook_signature` returns `true` unconditionally). No Shipit session, `ApiClient` token, or the victim org's own secret is needed; only the payload's `repository.full_name` (or, for `status`, an arbitrary SHA) needs to be forged, both of which are attacker-controlled fields inside the very same signed request body.

### Recommendation
- Bind the authenticated organization to the write target: after computing `repository_owner` for signature verification, re-derive the acted-upon repository strictly from that same trusted value, not from a separately-parsed `repository.full_name`.
- In `Handler#repository_name`, validate that `payload.dig('repository','full_name')`'s owner segment matches the `repository_owner`/`organization.login` used to select the signing secret; reject the webhook otherwise.
- Fix `StatusHandler` specifically to scope its `Commit.where(sha: ...)` lookup through `stacks` (i.e., only commits belonging to repositories under the authenticated organization), instead of matching SHAs globally.

### Proof of Concept
1. Attacker is (or controls) organization `attacker-org`, which is configured in this Shipit instance with a known/self-chosen `webhook_secret`.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
   signed with `attacker-org`'s webhook secret via `X-Hub-Signature`.
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully.
4. `PushHandler#process` runs `stacks` derived from `repository.full_name` = `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a write the attacker's org credentials should never have been able to authorize.
5. Equivalently, for `X-Github-Event: status` signed the same way, `StatusHandler` will attach the attacker-supplied status to **any** commit in the whole instance matching the given `sha`, with no repository-ownership check at all.
