### Title
Cross-repository forgery of commit CI status/checks via mismatched signature-verification identity vs. handler-processed repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using an **unverified, attacker-controlled field** of the raw JSON body (`repository.owner.login`), before the signature has actually been checked. Once verification passes, `WebhooksController#create` dispatches the **same raw, attacker-controlled payload** to event handlers, several of which act on a **different field** of that payload (`repository.full_name`, or in the `status` handler's case, no repository binding at all) to decide which stack/commit to mutate. The identity that authenticated the request (the organization whose secret matched) is never checked against the identity the handler actually writes to.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body and uses it purely to pick which configured `GitHubApp`/secret to verify against: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub Apps keyed by organization, each with its own independently configured `webhook_secret` (self-service, admin-chosen per org, per `docs/setup.md`): [3](#0-2) [4](#0-3) 

Once `verify_webhook_signature` succeeds for whichever org was named in `repository.owner.login`, the entire raw payload is handed unchanged to the registered handlers: [5](#0-4) 

Several handlers resolve the repository/stack to act on from a *different* field, `repository.full_name`, e.g. the base `Handler#stacks`: [6](#0-5) 

and `CheckSuiteHandler`, which schedules a check-run refresh for any stack/commit matching a branch+sha regardless of which org's secret authenticated the request: [7](#0-6) 

Worse, `StatusHandler` does not scope by repository at all — it looks up commits **globally by SHA** across the entire Shipit database and writes a GitHub commit-status record onto them: [8](#0-7) 

The binding that should hold is: `organization authenticated by verify_signature == organization owning the repository/stack the handler mutates`. Before the attack, an admin of Org A (who legitimately created and configured Org A's GitHub App, and therefore knows Org A's own `webhook_secret`) can only affect Org A's stacks. After crafting a payload where `repository.owner.login = "OrgA"` (used only for signature-key selection) while `repository.full_name` (or a colliding commit `sha`) targets Org B's/victim's repository, the request is HMAC-signed correctly with the Org A secret the attacker legitimately controls, passes `verify_signature`, and the handler then mutates state belonging to a repository/stack the attacker does not administer.

### Impact Explanation
- `CheckSuiteHandler` calls `schedule_refresh_check_runs!` and `StatusHandler` calls `create_status_from_github!` on commits that don't belong to the authenticating organization; because `StatusHandler` matches purely on SHA with no repository scoping, an attacker who knows any configured org's webhook secret can inject arbitrary CI status records (`state`, `context`, `target_url`, `description`) onto a commit in an entirely unrelated stack. If deploy/lock gating anywhere in Shipit consults commit status/check-run state to decide whether a commit is safe to deploy, this allows an attacker to forge a "green" CI signal for a victim commit — a step toward an unauthorized deploy — without ever holding a Shipit session, `ApiClient` token, or GitHub write access to the victim repository.
- `PushHandler`/`Handler#stacks` and the `PullRequest::*` handlers key off `repository.full_name`, so the same organization/repository confusion lets an attacker (using their own org's secret) trigger `stack.sync_github` or provisioning/archiving actions against another org's repository stacks.
- This crosses the "authenticated organization != repository being written" boundary defined as in-scope, and can escalate to unauthorized deploy signal manipulation, matching the High/Critical impact bar.

### Likelihood Explanation
The prerequisite is that the deployment runs Shipit's documented multi-organization GitHub App configuration (explicitly supported and shown in `test/dummy/config/secrets_double_github_app.yml`) and that the attacker administers at least one onboarded organization's own GitHub App (a normal, unprivileged setup step per `docs/setup.md`, not requiring any Shipit credential). No Shipit session, `ApiClient` token, or victim-repository access is required — only knowledge of a webhook secret the attacker legitimately set up for their own org. This is a realistic configuration for any Shipit instance serving more than one GitHub organization.

### Recommendation
After `verify_signature` succeeds, re-derive the organization/owner strictly from the same trusted context used to select the verification key, and reject (or re-verify) any payload whose `repository.full_name`/commit ownership does not belong to that same organization before handlers execute. `StatusHandler` in particular must scope its `Commit.where(sha: ...)` lookup to commits whose stack's repository owner matches the organization that authenticated the webhook, not merely by SHA.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the (unprivileged, attacker-controlled) admin of `OrgA`'s GitHub App, craft a `status` webhook JSON body:
```json
{
  "sha": "<victim-commit-sha-in-OrgB-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" }
}
```
3. Sign it with `sha1=` HMAC using `OrgA`'s known `webhook_secret` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully. [9](#0-8) 
5. `StatusHandler#process` then updates status on any commit in the database matching the given `sha`, regardless of the fact that it belongs to `OrgB`, not `OrgA`. [8](#0-7)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
