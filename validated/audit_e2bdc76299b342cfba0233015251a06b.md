### Title
Malicious seller/counterparty AA can force perpetual bounce of buyer transactions by reverting on receipt of payment - ([File: aa_composer.js])

### Summary
Any AA-based marketplace/escrow-style template (e.g. `test/samples/things_registry_and_marketplace.oscript`) that pays out proceeds to a counterparty-supplied address as a secondary AA trigger is vulnerable: if that counterparty registers/controls an AA at the payout address whose logic unconditionally bounces, the whole primary buyer trigger reverts, denying the buyer's purchase every time while letting the attacker keep the item listed and repeatedly collect bounce fees or block resolution.

### Finding Description
Autonomous Agents (AAs) in ocore are permissionless: any user can post a definition unit deploying an AA at an address they compute in advance (`aa_validation.js`, `storage.readAADefinition`). A common AA pattern (illustrated by `test/samples/things_registry_and_marketplace.oscript` lines 97-107) pays sale proceeds to `$owner`, an address chosen by whoever registered the item — this address can be an AA.

When a primary AA's response payment targets an address that is itself a registered AA, `aa_composer.js`'s `handleSecondaryTriggers` (lines 1702-1757) invokes `handleTrigger` recursively with `bSecondary=true` for that address. If the secondary AA's own logic causes it to bounce (`bounce()`, lines 909-945, sets `bBouncing` and — for secondary triggers — calls `finish(null)` which propagates the error via `onDone(null, errorObj)`, lines 1671-1689), the outer `async.eachSeries` callback receives an error and, since the trigger is not itself secondary, calls:
```
return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
```
(`aa_composer.js` line 1749). `revert()` (lines 1759-1798) then rolls back **all** state-variable and balance changes made by the primary AA (`ROLLBACK TO SAVEPOINT initial_balances`, cache reverts) and re-enters `bounce()` for the primary trigger, causing the entire primary AA operation — including its own bookkeeping (e.g. `var['owner_'||$id]`, `var['price_'||$id]` reassignment) — to fail and the buyer's payment to simply bounce back (minus bounce fee).

A malicious seller can pre-deploy an AA at the address they list as `$owner`/payout recipient that always bounces regardless of the payment received (e.g., an AA whose only message evaluates a formula that always calls `bounce(...)`). Every legitimate buyer attempt then permanently reverts, exactly like the Cooler `_onRepay()`/`_onRollLoan()` griefing pattern where an untrusted counterparty-controlled hook is invoked synchronously inside the victim's success path and can be made to always fail.

### Impact Explanation
Any buyer who is unaware their payment is routed to a hostile AA loses the ability to ever complete the purchase through this AA; their trigger unit is bounced (bounce fee is retained/burned per-attempt) while the seller keeps the item permanently "in escrow"-like limbo, effectively freezing marketplace state and any funds sent by buyers minus bounce fees, over and over. In lending/escrow-style AA templates suggested directly by the sample's own comments ("Allow to borrow money using an owned thing as a collateral. If the debt is not repaid in time, the lender can seize the thing."), the same mechanism lets a malicious lender force every repayment attempt (paid to the lender/AA address) to bounce, while a separate, un-gated default/seizure path (not depending on the lender's callback) still succeeds later — mirroring the exact High-severity Cooler scenario: forced default and loss of the borrower's collateral to an uncooperative counterparty.

### Likelihood Explanation
Any address can be an AA (deployment is fully permissionless), and any oscript template that forwards funds to a user-chosen/counterparty address as part of an atomic secondary trigger is exposed. A malicious counterparty needs only to register/list using an AA address they control that is coded to always bounce — no special privilege or timing race is required, and the attack succeeds on every buyer attempt.

### Recommendation
AA templates that pay third-party-controlled addresses within the same atomic response (as secondary AA triggers) should not let a bounce at the recipient revert the payer's own already-finalized side effects. Where possible: (1) avoid depending on synchronous secondary-trigger success for critical state transitions (e.g., finalize ownership/state change and marketplace bookkeeping independently of whether the payment message to a foreign AA succeeds), or (2) use a two-step pull/withdraw pattern rather than push-payment to an unknown/attacker-controlled address, so a hostile recipient AA's `bounce()` cannot cascade into `revert()` of the payer's or protocol's own state as seen in `aa_composer.js` lines 1743-1749.

### Proof of Concept
1. Attacker deploys AA `M` whose sole message logic is `bounce('always fail')` (or a formula guaranteed to throw/bounce) — a valid, permissionless AA definition.
2. Attacker calls the `register` case of `things_registry_and_marketplace.oscript` for thing id `X`, setting themselves (address `M`, the malicious AA) as `$owner` and listing it `on sale` for `$price`.
3. Victim buyer sends `$price` bytes with `trigger.data = {id: X, buy: true}` to the marketplace AA.
4. Marketplace AA computes `$owner = M`, builds a payment message routing `$price` to `M`, and this becomes a secondary trigger to AA `M` (`aa_composer.js` `handleSecondaryTriggers`, line 1702).
5. AA `M` bounces unconditionally; `async.eachSeries`'s error callback fires `revert(...)` (line 1749), rolling back the marketplace's `var['owner_'||X]`/`var['price_'||X]` updates and bouncing the buyer's original trigger.
6. Buyer's funds (minus bounce fee) are returned, the purchase never completes, and the attacker can repeat step 3-5 indefinitely against every prospective buyer, permanently denying the sale while incurring only the attacker's own listing cost. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
