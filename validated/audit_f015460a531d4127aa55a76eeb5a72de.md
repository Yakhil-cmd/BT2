## Title
StackStxOp::check() logs but does not reject an out-of-range `num_cycles`, allowing an unvalidated burnchain-op field to reach pox-4's `stack-stx` as `lock-period` — ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::check()` is the consensus-critical gate that a `stack-stx` burnchain operation must pass before `stackslib/src/chainstate/burn/db/processing.rs::check_transaction` will admit it to the operation list that is later fed into the `stack-stx` contract call. For the `num_cycles` field — parsed directly from attacker-supplied OP_RETURN bytes in `StackStxOp::parse_data` — the check only `warn!`s on an invalid value but never returns an `Err`, unlike the sibling check for `stacked_ustx == 0` in the same function. This mirrors the report's root cause: a value taken from unauthenticated wire data is used for a critical decision (bounding the lock period) without the validation path that was clearly intended to enforce it.

### Finding Description
`StackStxOp::parse_data` (stackslib/src/chainstate/burn/operations/stack_stx.rs:176-230) parses `num_cycles` as a raw `u8` from byte 16 of the OP_RETURN payload, with no range restriction at parse time:
```
let num_cycles = *data.get(16)?;
```
The intended range enforcement lives in `check()`:
```rust
pub fn check(&self) -> Result<(), op_error> {
    if self.stacked_ustx == 0 {
        warn!("Invalid StackStxOp, must have positive ustx");
        return Err(op_error::StackStxMustBePositive);
    }

    if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
        warn!(
            "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
            self.num_cycles, POX_MAX_NUM_CYCLES
        );
    }
    ...
    Ok(())
}
``` [1](#0-0) 

Unlike the `stacked_ustx == 0` branch, the `num_cycles` branch has no `return Err(...)`. Execution falls through the `if`, past the signer-key check, and returns `Ok(())` regardless of whether `num_cycles` is `0` or greater than `POX_MAX_NUM_CYCLES`.

`check()` is invoked from `SortitionHandleTx::check_transaction` as the sole gate for admitting a `StackStx` burnchain op:
```rust
BlockstackOperationType::StackStx(ref op) => op.check().map_err(|e| { ... }),
``` [2](#0-1) 

Because `check()` returns `Ok(())` for a malformed `num_cycles`, the op is admitted and later passed unmodified into `process_stacking_ops`, which forwards `num_cycles` as the `lock-period` argument to the boot contract's `stack-stx`:
```rust
let mut args = vec![
    Value::UInt(*stacked_ustx),
    reward_addr.as_clarity_tuple()...,
    Value::UInt(u128::from(*block_height)),
    Value::UInt(u128::from(*num_cycles)),
];
``` [3](#0-2) 

This is directly analogous to the Zebra report's bug class: a field derived from attacker-controlled, unauthenticated data (there: the coinbase scriptSig height; here: the `num_cycles` byte in a Bitcoin OP_RETURN payload) is meant to be validated by a specific check before being trusted for a consensus decision, but the validation silently no-ops instead of enforcing the invariant, so the unvalidated value flows downstream.

### Impact Explanation
This is not gated by an admin key, miner privilege, or another user's private key — any unprivileged party can construct a `stack-stx` burnchain transaction with `num_cycles = 0` (or `> POX_MAX_NUM_CYCLES`, capped at 255 by the u8 wire encoding). If `pox-4.clar`'s own `stack-stx`/`can-stack-stx` path does not independently re-derive/clamp `lock-period` to `[MIN_POX_REWARD_CYCLES, MAX_POX_REWARD_CYCLES]` before it is used to compute `unlock-burn-height` and populate `reward-set-indexes`, an attacker's STX lock is scheduled to unlock at an incorrect (potentially zero-length or absurdly long) height. This can break the equality between the amount actually locked/committed to reward slots and the amount the node's Rust-side lock-application code (`stx_account`/`pox-locking`) applies, or diverge `unlock-burn-height` from the value the stacker actually intended — i.e., a stacking action whose lock-period parameter was never validated against consensus bounds. The concrete blast radius (permanent freeze vs. early/wrong unlock vs. reward-set corruption) depends on how `pox-4.clar`'s `can-stack-stx` handles a `lock-period` of `0` or values above `MAX_POX_REWARD_CYCLES` — I was not able to fully trace and confirm that boundary within the remaining budget, so this should be verified in the contract's `can-stack-stx`/`minimal-can-stack-stx` helpers before concluding the exact impact tier.

### Likelihood Explanation
Reachable by any unprivileged Bitcoin transaction sender who follows the `PreStx`→`StackStx` wire protocol — no special key, contract-caller allowance, or miner role is required. The bug is a straightforward missing `return` in a hand-written match arm, so it is 100% reliably triggerable given a crafted OP_RETURN payload with `num_cycles = 0` or `> POX_MAX_NUM_CYCLES`.

### Recommendation
Add the missing `return Err(op_error::StackStxInvalidCycles)` (or equivalent) in the `num_cycles` branch of `StackStxOp::check()`, mirroring the pattern already used for `stacked_ustx == 0`, so malformed ops are rejected before being handed to `process_stacking_ops`.

### Proof of Concept
1. Construct a `PreStx` burnchain transaction from an unprivileged wallet, followed by a `StackStx` op whose OP_RETURN payload encodes `num_cycles = 0` (byte 16 of the data) while otherwise following the documented wire format in `StackStxOp::parse_data` comments (stackslib/src/chainstate/burn/operations/stack_stx.rs:177-188).
2. Observe that `StackStxOp::parse_from_tx` succeeds (no range check at parse time) and `StackStxOp::check()` returns `Ok(())` because the `num_cycles == 0 || num_cycles > POX_MAX_NUM_CYCLES` branch only logs a warning and falls through.
3. The op is admitted by `SortitionHandleTx::check_transaction` and passed to `StacksChainState::process_stacking_ops`, which calls `pox-4.stack-stx` with `lock-period = 0` (as `Value::UInt(u128::from(*num_cycles))`).
4. Inspect whether `pox-4.clar`'s `can-stack-stx`/lock-period arithmetic (`reward-cycle-to-burn-height (+ first-reward-cycle lock-period)`) produces a degenerate or unintended `unlock-burn-height` for `lock-period = 0`, confirming the downstream effect on the stacker's lock schedule.
