### Title
Stack-scoped API token bypasses stack authorization on CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token that is scoped to a single stack (`stack_id` set) is meant to only ever "touch" that one stack, as enforced by `Api::BaseController#stacks`/`#stack`. `Api::Ccmenu::CCMenuController` overrides the `stack` accessor and looks the stack up directly via `Stack.from_param!(params[:stack_id])`, completely bypassing the scoping filter. Any holder of a stack-scoped, `read:stack`-permissioned token can therefore read the CI/build status of any stack in the installation, not just the one the token authorizes.

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting stack lookup: [1](#0-0) 

`stacks` is filtered to `current_api_client.stack_id` when the client is scoped, and `stack` is derived from that filtered relation, so a scoped client requesting a stack it doesn't own gets a `RecordNotFound`/404.

`Api::CCMenuController`, however, defines its own private `stack` method that ignores this scoping entirely: [2](#0-1) 

It only enforces the coarse-grained `require_permission :read, :stack` check (a permission-string check via `ApiClient#check_permissions!`), which validates the `permissions` array but never validates `stack_id`: [3](#0-2) 

Consequently the binding that should hold — "the set of stacks a token authorizes" == "the set of stacks a token can touch" — is broken specifically for this endpoint: the token authorizes only its own `stack_id`, but the `show` action can touch any `stack_id` supplied in the URL.

### Impact Explanation
This allows unauthorized/scope-escaped read access to another stack's deploy/CI state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) via `GET /api/stacks/:stack_id/ccmenu`, using a token that was only ever meant to be usable against a single, specific stack. This matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" — here achieved by a token whose stack-scoping guarantee is bypassed, letting it read state of stacks that were never delegated to it.

### Likelihood Explanation
Any application embedding this engine that issues stack-scoped tokens (e.g. via `CCMenuUrlController`, which itself creates a `read:stack`-scoped client tied to a specific stack) is affected. Exploitation only requires possession of a legitimate but narrowly-scoped token (e.g. a CCMenu URL shared for one project) and knowledge/guessing of another stack's `owner/repo/environment` identifier — no privileged access or additional secrets are required.

### Recommendation
Remove the custom `stack` override in `Api::CCMenuController` (or reimplement it to reuse `Api::BaseController#stack`, i.e. look the stack up through the scoped `stacks` relation) so that stack-scoped tokens can never resolve a stack outside their `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack A: `stack_id = A`, `permissions = ['read:stack']` (mirrors fixture `here_come_the_walrus`, see [4](#0-3) ).
2. Authenticate with that token and call `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu` for an unrelated stack B.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!` on all stacks (not the client's scoped relation), the request returns `200 OK` with stack B's CI status, instead of the `404`/scope-restricted result produced by any endpoint that goes through `Api::BaseController#stack` (compare with `Api::StacksControllerTest#"an api client scoped to a stack will only see that one stack"`, [5](#0-4) ).
