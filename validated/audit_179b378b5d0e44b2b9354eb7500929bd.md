### Title
Stack-scoped API token can read CCMenu build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to look up `Stack.from_param!(params[:stack_id])` directly, bypassing the stack-scoping enforced by `Shipit::Api::BaseController#stack`/`#stacks`. Any `ApiClient` token that only carries the generic `read:stack` permission — including one deliberately restricted to a single stack via `stack_id` — can be replayed against any other stack's CCMenu endpoint to read that stack's deploy status.

### Finding Description
`Shipit::Api::BaseController` defines the "stack a token authorises" binding: [1](#0-0) 

`stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a stack (`stack_id?`), and `stack` looks the requested `params[:stack_id]` up only within that relation. This is the mechanism the app relies on to make a stack-scoped token (e.g. `here_come_the_walrus`, fixture-defined with `stack: shipit`) unable to touch any other stack — confirmed by the existing test "an api client scoped to a stack will only see that one stack".

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 

It authenticates the request via `authenticate_api_client` (accepting the token from either Basic Auth or the `?token=` query parameter) and then only checks the coarse-grained `require_permission :read, :stack` before-action: [3](#0-2) 

`require_permission!` only calls `ApiClient#check_permissions!`, which checks that the string `"read:stack"` is present in `permissions` — it never checks `current_api_client.stack_id`: [4](#0-3) 

So the equality the app is supposed to enforce — "the stack a token authorises" == "the stack it touches" — is broken specifically in `CCMenuController#stack`, because it queries `Stack.from_param!` against the whole `Stack` table instead of the api-client-scoped relation used everywhere else (e.g. `StacksController`).

### Impact Explanation
A stack-scoped, read-only token (of the kind `CCMenuUrlController` mints for every user who visits a stack's settings page, embedding it in cleartext in a CCMenu URL) can be used to fetch `lastBuildStatus`, `lastBuildLabel`, `activity`, and `webUrl` for **any** stack in the Shipit instance, not just the one it was issued for. This is an unauthenticated-by-design (query-string token) read of deploy/task state across stack boundaries — matching the "High: unauthenticated read of stack state, task streams or deploy output" impact category, since it lets a holder of one stack's low-privilege CCMenu token enumerate/observe the deploy status of other stacks they were never granted access to.

### Likelihood Explanation
Likelihood is high for anyone already holding a legitimate CCMenu token (these tokens are handed out broadly — created automatically for any authenticated user who loads a stack's CCMenu URL, and are transmitted/embedded in plaintext URLs meant for third-party CI dashboard tools). No additional privilege is required: the attacker only needs to know or guess another stack's `stack_id` (predictable — `owner/repo/branch` slug) and swap it into the `stack_id` request parameter while reusing their own valid token.

### Recommendation
Have `CCMenuController` resolve the stack the same way `BaseController` does — via `stacks.from_param!(params[:stack_id])` (i.e., delegate to `super`/remove the overriding `stack` method) so that a stack-scoped `ApiClient` cannot resolve a `stack_id` outside `current_api_client.stack_id`.

### Proof of Concept
1. As user Alice, visit Stack A's settings page; Shipit's `CCMenuUrlController#fetch` auto-creates (or reuses) an `ApiClient` scoped to Stack A with permission `read:stack`, and returns a URL containing `?token=<Alice's token>`.
2. Using that same token, request `GET /api/stacks/<OWNER>/<REPO>/<BRANCH_OF_STACK_B>/ccmenu?token=<Alice's token>` for unrelated Stack B.
3. `authenticate_api_client` in `CCMenuController` accepts the token (it is a valid `ApiClient`), `require_permission :read, :stack` passes because Alice's token has `read:stack`, and `stack` resolves Stack B via `Stack.from_param!` with no scoping check — the response renders Stack B's deploy status even though Alice's token was only meant to authorize Stack A.
