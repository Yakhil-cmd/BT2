### Title
Missing Upper Bound on `count_coins` in Asset Denomination Definitions Enables Integer-Precision Overflow and Cap-Enforcement Bypass - (File: `aa_validation.js`, `validation.js`, `indivisible_asset.js`)

### Summary
Both the plain asset-definition validator and the AA-asset-definition validator only require `count_coins` (and `denomination`) to be positive integers, unlike `denomination` and `cap`, which are explicitly capped at `constants.MAX_CAP`. Because `count_coins` is later multiplied by `denomination` to compute the total issuable supply, an unbounded `count_coins` value lets an asset definer (including an unprivileged AA whose asset-defining message is triggered by any user) create a denomination whose `count_coins * denomination` product exceeds `constants.MAX_CAP` or even JavaScript's safe-integer range, defeating the very cap check that is supposed to bound the asset supply.

### Finding Description
When validating an asset definition (either posted directly or produced by an AA), `denomination` and `cap` are both checked against `constants.MAX_CAP`: [1](#0-0) [2](#0-1) 

But `count_coins` for each denomination entry is validated only with `isPositiveInteger`, with no upper bound at all: [3](#0-2) 

The same unbounded pattern exists in the AA-definition validator that is reachable from an unprivileged AA trigger sender causing the AA to emit an `asset` message: [4](#0-3) 

`isPositiveInteger` only checks that the value is a finite integer greater than zero — it performs no comparison against `constants.MAX_CAP` or `Number.MAX_SAFE_INTEGER`: [5](#0-4) 

The unbounded `count_coins` is then multiplied by `denomination` to derive `total_cap_from_denominations`, which is only compared against the (correctly bounded) `payload.cap`: [6](#0-5) 

and it is used again at issuance time in the indivisible-asset issuer to compute the actual `issue_amount = count_coins_to_issue * denomination`: [7](#0-6) 

Because `denomination * count_coins` is computed as an ordinary JS `Number`, values whose product exceeds `Number.MAX_SAFE_INTEGER` (2^53−1) lose precision silently. This means:
- The `total_cap_from_denominations === payload.cap` comparison in `validateAssetDefinition` can pass (due to rounding) even though the true intended supply differs from the value actually storable/issuable, i.e., the “upper bound” enforced by `cap` can be circumvented by precision loss.
- Downstream consumers (light clients, other full nodes) recomputing the same multiplication could, in edge cases involving different code paths/precision, disagree on the effective issued amount, which is exactly the kind of validation-divergence class this bug report describes ("reversion in critical functions" / value mismatch), except here it manifests as inconsistent enforcement of the asset cap rather than a simple revert.

This mirrors the CVE class described in the external report: a numeric parameter that influences a critical financial computation (fee in the original report; issuable supply cap here) is validated for positivity/type but never bounded against the system-wide maximum (`MAX_CAP`), allowing the definer to pick a value that breaks the invariant the bound was meant to protect.

### Impact Explanation
An asset issuer (a normal, unprivileged unit poster or an AA that composes an `asset` message from unprivileged trigger data) can define an indivisible asset with a `denominations` array containing a `count_coins` value large enough that `count_coins * denomination` silently overflows JS's safe-integer precision while still passing the `total_cap_from_denominations === payload.cap` equality check in `validation.js`. This breaks the guarantee that `cap` (which is correctly bounded to `MAX_CAP`) actually limits the maximum issuable supply of the asset, since the real per-denomination issuance amount computed later in `indivisible_asset.js` (`count_coins_to_issue * denomination`) can diverge from the intended value. This is a supply-inflation / cap-bypass risk for indivisible assets, which corresponds to the "value that directly affects LP/asset accounting because an owner-set numeric field lacks an upper bound" impact class in the referenced report.

### Likelihood Explanation
Any account can author an asset definition (or drive an AA that emits one) with an arbitrarily large `count_coins`; the check is a simple client-side/node-side numeric type check with no cap comparison, so it is trivially reachable without any special privilege — only crafting the message with an oversized `count_coins`.

### Recommendation
Add an explicit upper-bound check on `count_coins` (and equivalently on the product `count_coins * denomination`) against `constants.MAX_CAP` / `Number.MAX_SAFE_INTEGER` in both:
- `validateAssetDefinition` in `validation.js` (denomination loop, around line 2775), and
- the AA asset-definition validator `validateDenominations` in `aa_validation.js` (around line 272),

mirroring the existing bound already applied to `denomination` itself (`denomInfo.denomination > constants.MAX_CAP`). Additionally, guard the multiplication `count_coins * denomination` for overflow (e.g., reject if the product exceeds `constants.MAX_CAP`) rather than relying on floating-point equality comparisons.

### Proof of Concept
1. Author a unit defining a `fixed_denominations` indivisible asset with `denominations: [{denomination: 1, count_coins: N}]` where `N` is chosen (e.g., close to `Number.MAX_SAFE_INTEGER`) so that `count_coins * denomination` loses precision but is set equal to `cap` in the payload.
2. `validateAssetDefinition` (`validation.js`, lines 2757-2792) only checks `isPositiveInteger(denomInfo.count_coins)` — no bound versus `MAX_CAP` — and accepts the definition as long as the (possibly imprecise) `total_cap_from_denominations` matches `payload.cap`.
3. When the asset is later issued via `indivisible_asset.js` (`issueNextCoin`, lines 516-546), `issue_amount = count_coins_to_issue * denomination` is computed again; due to floating point, this can silently differ from the value implied by the declared `cap`, defeating the cap's purpose as an enforced upper bound on issuable supply.
