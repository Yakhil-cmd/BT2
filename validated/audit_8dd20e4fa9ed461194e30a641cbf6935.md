This is a real, exploitable cross-tenant issue confirmed by the code.

### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a status webhook write statuses onto commits belonging to *any* stack sharing that SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by bare SHA with `Commit.where(sha: params.sha)` with no repository/owner scoping, then calls `create_status_from_github!` on every matching row across the entire `commits` table. Because `verify_signature` in `Shipit::WebhooksController` only authenticates the webhook against the GitHub App/organization tied to `params['repository']['owner']['login']` (the sending repo), and never restricts which `Commit` rows the payload is allowed to mutate, a status payload signed for repository A can flip the state of a `Commit` row that belongs to repository B's stack, as long as the two share the same commit SHA (a legitimate, common occurrence: forks, cherry-picks, shared mono-history, or an attacker who simply forks the victim repo and pushes the victim's existing SHA history).

### Finding Description
The broken binding the handler implicitly assumes is:
`commit.stack.repository.full_name == params['repository']['full_name']` (the status only applies to the commit inside the repo that authenticated the webhook).

Tracing the code:
- `WebhooksController#create` parses `params`, resolves `event` from `X-Github-Event`, and dispatches to `Shipit::Webhooks.for_event(event)` handlers — `verify_signature` only checks `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, which authenticates that the payload was signed by *some* GitHub App/org matching `params.dig('repository','owner','login')`. It does **not** check that the `sha` inside the payload belongs to that same repository. [1](#0-0) 
- `StatusHandler#process` then runs:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is global across the `commits` table — it is not scoped by `stack_id`, `repository_id`, or any tenant boundary. [2](#0-1) 
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, which creates a `Shipit::Status` row scoped to `commit.stack_id` — i.e., whichever stack that Commit row happens to belong to. [3](#0-2) [4](#0-3) 
- This new `Status` participates in `Commit#deployable?`/`blocked?`/merge-queue gating for whatever stack the matched commit belongs to, because gating is computed from `stack.blocking_statuses`/`required_statuses` against that commit's `status`. [5](#0-4) 

**Attacker's exact request:** attacker forks or otherwise obtains repository X (any repo they own/control, satisfying `verify_signature` against their own org/app), pushes/creates a commit whose SHA equals a SHA already present in victim stack's commit history (trivial via fork-and-cherry-pick, or by pushing the exact same tree/parent chain so git produces an identical SHA), then sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for repo X, and body `{"sha": "<shared sha>", "context": "security/scan", "state": "failure", "repository": {"owner": {"login": "<attacker-org>"}, ...}}`. Because the lookup is by bare `sha` only, `Commit.where(sha: ...)` also returns the victim's `Commit` row, and a `Status` row is written under the victim stack's `stack_id` with `context: security/scan`, `state: failure` — even though the victim never received (or requested) that status from GitHub for that repository.

**Why existing guards fail:** `verify_signature` validates *who signed* the payload, not *which commit/stack the payload is permitted to touch*; `ExplicitParameters` schema in `StatusHandler` only validates presence/type of `sha`/`state`/`context`, not repository ownership; there is no `stacks`/`repository` scope applied before the `Commit.where` lookup.

Regarding the "review_stacks_enabled false / provisioning precedence" portion of the question specifically tied to `ReviewStack`/`OpenedHandler` provisioning logic: I was not able to fully verify a "provision precedence bug" in `provision?` within this session — the `provision?` predicate in `OpenedHandler` (`repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || ...`) does gate on `review_stacks_enabled`, and no unscoped provisioning path from `StatusHandler` itself was found; `StatusHandler` only writes `Status` rows and does not call any provisioning code. I could not confirm the claimed "review stacks disabled yet still provisions" precedence bug from the available code, so that specific compound claim should be treated as unconfirmed/unverified rather than validated.

### Impact Explanation
An attacker fully controlling only their own repository/webhook can write arbitrary `Status` rows (any `context`, `state: failure`/`success`) against a **different tenant's** stack/commit merely by matching a SHA, without ever authenticating to or being a collaborator on the victim repository. This directly affects `Commit#deployable?`, `blocked?`, and merge-queue/CD gating (`ProcessMergeRequestsJob` is enqueued on Status creation), meaning the attacker can force a required `security/scan` context to `failure` and block deploys/merges on a victim stack, or conversely force it to `success` to unblock/ship a commit that never passed the victim's real CI/security checks. This is a payload for one repository mutating another's commit/stack state, matching the "Critical — payload for one repository mutating another's stack/commit" impact category. [6](#0-5) 

### Likelihood Explanation
Preconditions: attacker needs (1) a GitHub repo they control (to get a valid webhook signature from their own org's GitHub App/secret), and (2) a commit SHA that also exists in the victim's commit history for a targeted stack — achievable via git fork/cherry-pick or, in cases of shared upstream history (common monorepo/fork workflows), by simply referencing an existing shared commit. No Shipit credentials, session, or victim-repo permissions are required. This is fully repeatable against any victim stack whose commit history intersects with an attacker-controlled repo's history, and cost is minimal (a single crafted HTTP POST per attempt).

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) by the authenticated repository, e.g. resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and constrain `Commit.where(sha: params.sha, stack: repository.stacks)` (or equivalent join through `stack.repository_id`) before calling `create_status_from_github!`, so a status can only mutate commits belonging to stacks of the repository that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status handler does not write statuses onto commits of a different repository's stack" do
  victim_repo = shipit_repositories(:shipit) # some_owner/some_repo
  victim_stack = create_stack(repository: victim_repo)
  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  attacker_repo_full_name = "attacker-org/attacker-repo"
  payload = {
    "sha" => shared_sha,
    "state" => "failure",
    "context" => "security/scan",
    "repository" => { "full_name" => attacker_repo_full_name, "owner" => { "login" => "attacker-org" } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end

  victim_commit.reload
  refute_equal "failure", victim_commit.status.state
end
```
Before the fix, `Commit.where(sha: shared_sha)` matches `victim_commit` regardless of `payload["repository"]`, so the `assert_no_difference` fails and `victim_commit.status.state` becomes `"failure"`, demonstrating the cross-tenant write. [2](#0-1)
