### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` (or no repository field at all) — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate `X-Hub-Signature` based on the `repository.owner.login` (or `organization.login`) field of the *same JSON body it is verifying*. All the event handlers, however, decide what Shipit data gets mutated using a *different* field in that same payload (`repository.full_name`) — or, in the case of `StatusHandler`, no repository field at all. Because the signature only proves "whoever holds the `webhook_secret` for the organization named in `repository.owner.login` sent this JSON," and does not bind that organization to the repository/commit the handlers actually act on, an attacker who administers *any* GitHub organization onboarded to a multi-tenant Shipit instance can forge a signed webhook that manipulates a *different* organization's stacks.

### Finding Description
`verify_signature` picks the signing organization purely from attacker-controlled payload fields: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```

`verify_webhook_signature` just checks the HMAC against that organization's own `webhook_secret`: [3](#0-2) 

If Shipit is configured for multiple GitHub organizations (a documented deployment mode — `docs/setup.md`, "Using Multiple Github Applications"), each org has its own `webhook_secret` known to that org's own admins. So any org admin can trivially sign an arbitrary JSON body using their *own* org's secret, as long as `repository.owner.login`/`organization.login` in the body names their own org.

The handlers, however, resolve the target Stack/Commit from a *different, unverified* field of the same JSON: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.full_name` is never checked against `repository.owner.login`/the organization whose secret produced a valid signature. So `PushHandler` will call `stack.sync_github(expected_head_sha:)` for any stack whose `Repository` matches the attacker-chosen `repository.full_name`, even though the signature only proved the sender controls a *different* org's secret: [5](#0-4) 

`CheckSuiteHandler` similarly scopes only by `repository.full_name`/branch, not by the signing organization: [6](#0-5) 

Worse, `StatusHandler` does not scope by repository at all — it matches purely on commit SHA across the entire installation: [7](#0-6) 

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This is a direct analog of the reported bug class: the "verified" credential (webhook signature ⇒ organization X) is not bound to the payload field that is actually acted upon (repository/commit belonging to organization Y). Exactly as the ecall functions trusted register-supplied pointers without checking they stayed inside the region the security check was meant to cover, the webhook handlers trust attacker-supplied `repository.full_name`/`sha` fields without checking they stay inside the organization whose secret actually signed the request.

### Impact Explanation
An attacker who is an admin/owner of any GitHub organization that has installed the Shipit GitHub App on a shared, multi-org Shipit instance can:
- Forge a `push` webhook naming a victim organization's repository in `repository.full_name` (while self-signing with their own org's secret via `repository.owner.login`), forcing `stack.sync_github(expected_head_sha:)` to run against the victim stack with an attacker-chosen SHA — a cross-repository write.
- Forge a `status` webhook to inject a passing/failing CI status on an arbitrary commit SHA belonging to any stack in the instance, since `StatusHandler` performs no repository/organization scoping at all. Since Shipit's merge queue / CI gating (`ci.require`) and deploy safety checks rely on `Commit#statuses`, this can be used to fabricate green CI on a victim's commit, which can unblock automatic merges or continuous deployment for that commit — an unauthorized deploy/merge.

This satisfies the Critical bar: "cross-repository writes, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires only that the attacker administers one legitimate, lower-trust GitHub organization already installed on a shared Shipit instance (a documented, supported configuration — multiple orgs sharing one Shipit deployment). No Shipit session, `ApiClient` token, or GitHub App private key is needed; only knowledge of the attacker's own org's `webhook_secret`, which the attacker legitimately possesses. This is a realistic "unprivileged-attacker-relative-to-victim-org" scenario within the documented multi-tenant setup.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, bind the two payload fields together before trusting either: after signature verification succeeds for organization `repository_owner`, additionally assert that `payload.dig('repository', 'full_name')&.split('/')&.first` (and any commit/stack resolved from the payload) belongs to that same verified organization, rejecting the webhook otherwise. `StatusHandler` in particular must scope `Commit.where(sha:)` to commits whose stack's repository owner matches the verified `repository_owner`.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` and `victim-org`, both with the app installed (per `docs/setup.md` "Using Multiple Github Applications"), each with its own `webhook_secret`.
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org's GitHub App settings).
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha, e.g. scraped from public stack page>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker_webhook_secret, body)`.
5. POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s `GithubApp`, and the signature validates successfully (attacker signed with their own known secret).
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged passing CI status on a commit that belongs to `victim-org`, potentially satisfying `ci.require` and enabling an unauthorized merge/deploy of that commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
