### Title
`StatusHandler#process` mutates commits across every stack sharing a SHA, ignoring the org scope proven by `verify_signature` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that a webhook was signed by the `webhook_secret` belonging to `params.dig('repository','owner','login')` — i.e. it authenticates one organization. `StatusHandler#process`, unlike its sibling `CheckSuiteHandler`, never uses the request's `repository` at all: it runs `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match, so a status event authenticated for org A can write status data onto a commit belonging to org B's stack whenever the two share a SHA (forks, mirrors, or shared upstream history are the common case in a single Shipit instance).

### Finding Description
The claimed binding, stated explicitly:

`verified_org(webhook) == owning_org(every Commit mutated by handler.process)`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and validates the signature against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. it authenticates exactly one organization/App installation. [1](#0-0) [2](#0-1) 
2. The base `Handler` class exposes a `stacks` helper that scopes correctly to the repository named in the *same* payload that was authenticated: `Repository.from_github_repo_name(repository_name)&.stacks`. [3](#0-2) 
3. `CheckSuiteHandler#process` uses that scoped helper correctly: `stacks.where(branch: ...)` then `stack.commits.where(sha: ...)` — mutation is confined to stacks belonging to the repository whose owner was just verified. [4](#0-3) 
4. `StatusHandler#process`, however, never touches `stacks`/`repository_name` at all — it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, an unscoped, instance-wide lookup by SHA across all stacks/organizations in the Shipit database. [5](#0-4) 
5. `create_status_from_github!` writes attacker-supplied `state`, `description`, `target_url`, `context`, `created_at` into the `statuses` table for the matched commit's stack. [6](#0-5) 

Root cause: `verify_signature` proves "this event genuinely came from org A," but `StatusHandler#process` never re-checks that the `sha` it is about to mutate belongs to a stack under org A's repository — it trusts the payload's `sha` field globally. Any commit SHA that is also present in another organization's stack (a very plausible situation: a fork, mirror, or shared upstream commit tracked by two different Shipit stacks) gets its status mutated by an event that authenticated only org A.

Existing guards do not stop this: `verify_signature` authenticates the org, not the sha's ownership; `ExplicitParameters` only validates the shape of `sha`/`state`/etc, not their scope; `drop_unhandled_event` and `force_github_authentication` are irrelevant to this path; there is no `subset`/scope validator anywhere in the `StatusHandler` path.

### Impact Explanation
An attacker who only controls org A's genuinely-signed status events (e.g. via a CI/status-reporting integration on a repository they own inside org A) can write arbitrary `state`, `description`, `target_url`, and `context` values into `Shipit::Status` rows attached to any commit in org B's stack, provided the commit SHA is shared between the two repositories/stacks (forks and mirrors of the same upstream are the realistic trigger). This is a cross-tenant write with zero org B authentication, matching the "payload for one repository mutating another's commit" Critical category. It is repeatable per request and against any org/stack pair that shares commit history, and since commit statuses drive CI-gating and deploy eligibility (`deployable?`, `blocking?`), it can be used to falsely mark org B's commits as green/red, influencing deploy decisions. [7](#0-6) 

### Likelihood Explanation
Requires: (a) two orgs/stacks configured in the same Shipit instance that happen to track overlapping git history (forks/mirrors of the same upstream repo are common), and (b) attacker control of a genuinely GitHub-signed status event for their own org (a normal CI/status integration on a repository they own or have push access to). No secrets, tokens, or elevated privileges are needed beyond what an ordinary contributor already has on their own repo. The bug is deterministic once the SHA collision precondition is met — no timing or race is required.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: restrict the `Commit` lookup to `stacks` derived from the authenticated `repository_name`/`repository_owner` of the current payload (e.g. `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }`), rather than an instance-wide `Commit.where(sha: ...)`.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `GithubApp`/`Shipit.github` configs for `org-a` and `org-b`, each with distinct `webhook_secret`s.
2. Create `Repository`/`Stack` `org-a/repo` and `Repository`/`Stack` `org-b/repo`.
3. Create `Commit` `c_b` under `org-b/repo`'s stack with `sha = "deadbeef..."`.
4. Build a `status` event payload for `org-a/repo` (`repository.owner.login == "org-a"`) with `sha == c_b.sha`, `state == "success"`.
5. Sign the payload with `org-a`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: status`.
6. Assert: `github_app_for("org-a").verify_webhook_signature(...) == true` (org A authenticated) AND `c_b.reload.statuses.last.state == "success"` even though `c_b.stack.repository.owner == "org-b"` — i.e. `verified_org ("org-a") != owning_org(mutated_commit) ("org-b")`, proving the binding is broken with zero org-b credentials used.
