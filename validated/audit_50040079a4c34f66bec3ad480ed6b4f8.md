### Title
Cross-organization forged GitHub webhooks via organization/repository binding mismatch enabling unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController` selects which GitHub App secret to verify a webhook's HMAC signature against using one payload field (`repository.owner.login` / `organization.login`), while every event handler downstream acts on a *different* payload field (`repository.full_name`) to decide which `Repository`/`Stack` to mutate. Nothing ties these two fields together. An attacker who legitimately controls a GitHub App/organization installation on this Shipit instance (i.e., knows their own org's `webhook_secret`, which is not a victim credential) can therefore forge a signed webhook whose `repository.owner.login` names their own org (so signature verification passes) but whose `repository.full_name` names an unrelated victim repository, causing Shipit to record fake CI statuses, push events, or PR events against a stack that attacker has no rights to.

### Finding Description
`verify_signature` picks the `GitHubApp`/secret to check against with: [1](#0-0) [2](#0-1) 

This uses `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) purely to look up which per-organization `webhook_secret` should validate the HMAC of the raw body.

Once the signature check passes, the raw JSON `params` are handed to the registered handler(s): [3](#0-2) 

Every handler, however, resolves the target `Repository`/`Stack` from a *different* field — `repository.full_name` — not from `repository.owner.login`: [4](#0-3) 

For example `PushHandler` triggers a `GithubSyncJob`-equivalent sync against whatever stacks match that `full_name`: [5](#0-4) 

and the `status` event handler creates a `Status` row directly from attacker-controlled `sha`/`state`/`context`/`target_url` fields (see fixture test showing exactly those fields flowing straight into the created `Status`): [6](#0-5) 

`Commit#deployable?` treats a commit as safe to auto-deploy once required CI contexts report `success` and it isn't blocked/locked: [7](#0-6) 

and continuous delivery is driven purely off stack state, with no re-validation that the statuses genuinely originated from GitHub for that repository's own organization: [8](#0-7) 

Because the code that decides "is this signature valid" and the code that decides "which repository does this event apply to" read two independent, attacker-influenceable JSON fields from the same request body, the verified identity (the organization whose secret matched) is never bound to the entity that is actually written (the repository named in `full_name`). This is the same "trust the acted-upon field without confirming it's inside what was validated" class of bug as the reported `extend()` prototype-pollution issue: one shared, blindly-merged payload field ends up controlling behavior with a scope that outstrips what was actually verified.

### Impact Explanation
An attacker who is an unprivileged (from the victim's perspective) but legitimate installer of the Shipit GitHub App on their *own* organization — a normal, self-service action requiring no access to Shipit or to the victim's GitHub org — can forge webhook deliveries for any other repository tracked by the same Shipit instance:
- Forge `status` events with `state: success` for the exact CI contexts a victim stack requires, making an unreviewed/failing commit appear `deployable?`.
- Forge `push` events to trigger repository sync against an arbitrary `expected_head_sha`.
- Forge `pull_request` events (`opened`/`closed`/`reopened`) to create/archive/unarchive review stacks belonging to a repository the attacker doesn't own.

If the victim stack has `continuous_deployment` enabled, forged success statuses can cause Shipit to autonomously trigger an **unauthorized deploy** of a commit that never actually passed CI/review — this maps to the "Critical: unauthorized deploy" impact category.

### Likelihood Explanation
Requires only: (1) the attacker legitimately controls a GitHub App/organization installation on the same multi-tenant Shipit instance (self-service, not a victim credential), and (2) knowledge of the victim's public `owner/repo` name. No `webhook_secret` of the victim, no Shipit session, and no `ApiClient` token are needed — the attacker signs the forged body with their *own* org's secret. This is realistic for any Shipit deployment serving more than one GitHub organization/App configuration (`github_app_config(organization)` / `TOP_LEVEL_GH_KEYS`).

### Recommendation
Bind signature-verification identity to the entity being mutated: after verifying the signature for `repository_owner`, re-derive `repository_owner` from the *same* field the handlers use (`repository.full_name`'s owner segment) and reject the request if the two disagree. Alternatively, have handlers reject/ignore events where `repository.owner.login` (the field used for secret selection) does not match the owner segment of `repository.full_name`, ensuring the verified organization and the mutated repository are provably the same.

### Proof of Concept
1. Attacker installs the Shipit GitHub App on their own org `attacker-org` (self-service, legitimate), obtaining/knowing `webhook_secret_A`.
2. Attacker POSTs to `/webhooks` (whatever route mounts `WebhooksController#create`) with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-context",
  "target_url": "https://attacker.example/ok",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` with `webhook_secret_A` over the exact raw body.
4. `verify_signature` resolves `repository_owner` → `attacker-org`, fetches `Shipit.github(organization: "attacker-org")`, and the signature matches → verification passes.
5. The status handler creates a `Status` row for `victim-org/victim-repo`'s commit using the attacker-supplied `state`/`context`, potentially flipping `Commit#deployable?` to `true` and, if continuous deployment is enabled on that stack, triggering an unauthorized deploy.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
