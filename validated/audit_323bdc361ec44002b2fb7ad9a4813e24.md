### Title
Webhook signature verification is bound to a different organization than the repository the payload actually mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) is used to validate an inbound webhook's HMAC based on a payload field (`repository.owner.login` / `organization.login`) that is completely independent of the field the downstream event handlers use to decide *which repository/stack/team is mutated* (`repository.full_name`, `organization.login` in `MembershipHandler`). Because Shipit explicitly supports hosting multiple organizations behind one instance, each with its own `webhook_secret`, an actor who legitimately knows the secret for *one* onboarded organization can craft a signed payload whose "owner" field points at their own org (to pass signature verification) while every other field in the same JSON body (`repository.full_name`, commit `sha`, `organization.login`, etc.) targets a completely different, victim organization's repository/stack/team. This breaks the equality the code implicitly assumes: `organization that authenticated == repository/organization that is written`.

### Finding Description
Signature verification:
```ruby

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` resolves a per-organization `GitHubApp` instance whose `webhook_secret` is configured independently per org (`config/secrets.development.example.yml` shows the multi-org `github: { org1: {...webhook_secret...}, org2: {...} }` schema, and `lib/shipit.rb`/tests confirm `Shipit.github(organization:)` looks the config up case-insensitively). [2](#0-1) 

The signature is verified over the *entire raw body*, but only the `repository.owner.login`/`organization.login` sub-field determines *which secret* is used — nothing ties that field to the other fields in the same payload that the handlers subsequently act on:

- `Handler#repository_name` (shared by `PushHandler`, `ClosedHandler`, etc.) resolves the target repository from a **different** field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

- `StatusHandler` writes a `Status` for any commit already tracked by Shipit, purely from attacker-suppplied fields (`sha`, `state`, `context`, `description`, `target_url`), with no cross-check against which org's secret verified the request:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

- `MembershipHandler` uses `params.organization.login` (yet another independent field) to set `team.organization`, again with no binding back to the org that signed the request:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [5](#0-4) 

**Before the attack:** `webhook signer org == repository/organization mutated` is assumed to hold because, for genuine GitHub-delivered webhooks, `repository.owner.login`, `repository.full_name`, and `organization.login` are all internally consistent (GitHub always fills them from the same event source).

**After the attack:** An operator who legitimately administers *any* one organization onboarded to the shared Shipit instance (and thus knows that org's `webhook_secret`, e.g. because they set up their own GitHub App per `docs/setup.md`) can POST directly to `/webhooks` with a body where `repository.owner.login`/`organization.login` = "their-org" (so `verify_signature` picks the secret they know) but `repository.full_name` = "victim-org/victim-repo" (or `organization.login` inconsistent with the signing org for `membership` events). The signature check passes, yet the handler mutates state belonging to a repository/org the attacker never authenticated for.

### Impact Explanation
Via `StatusHandler`, a forged `status` webhook lets the attacker set an arbitrary CI status (state, `context`, `description`, `target_url`) on any commit sha already recorded for a **victim repository they don't administer**, as long as they know the webhook secret of any org configured on the same Shipit instance. Since `Commit#deployable?` and merge-queue/CI gating rely on `stack.required_statuses`/`blocking_statuses` matched against these very `Status` records, an attacker can mark a required check "success" for a victim's commit, defeating CI-gating and enabling an **unauthorized deploy** of that commit — one of the explicitly listed Critical impacts. This crosses the boundary "an organization that authenticated versus the repository that is written" without requiring a Shipit session, `ApiClient` token, repository write access on GitHub, or a privileged Shipit account — only knowledge of one org's `webhook_secret`, which multiple independent orgs legitimately hold on a shared multi-tenant Shipit instance.

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multiple GitHub organizations (an explicitly documented, supported configuration), and (2) the attacker being a legitimate admin/owner of one of those organizations (who therefore knows that org's own `webhook_secret`, since they configure/received it when onboarding their org). No compromise of the victim org, no GitHub repo write access, and no Shipit application credentials are needed — only a direct HTTP POST to the shared `/webhooks` endpoint with a crafted body. This is a realistic misuse of the intentional multi-org architecture rather than a purely theoretical scenario.

### Recommendation
Bind the field used to select the verifying `webhook_secret` to the field(s) the handler actually consumes: after verifying the signature, re-derive `repository_owner`/`organization` from the *same* `repository.full_name` (or `organization.login`) that `Handler#repository_name` and `MembershipHandler#find_or_create_team!` use, and reject the webhook (422) if they diverge. Alternatively, look up the `Repository`/`Stack` first, resolve its actual owning organization from Shipit's own trusted configuration/DB, and verify the signature only with that organization's secret — never with an organization name taken from an unrelated part of the same attacker-controlled payload.

### Proof of Concept
1. Shipit instance is configured with two organizations, e.g. `github: { attacker-org: { webhook_secret: "S1", ... }, victim-org: { webhook_secret: "S2", ... } }`, as documented in `config/secrets.development.example.yml`.
2. Attacker legitimately administers `attacker-org` in Shipit and therefore knows `S1`.
3. Attacker crafts:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(S1, raw_body)>
Body: {
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha already tracked by Shipit>",
  "state": "success",
  "context": "<required CI context for victim-repo>"
}
```
4. `verify_signature` computes `repository_owner` = `"attacker-org"` (per `app/controllers/shipit/webhooks_controller.rb:59-62`), fetches `Shipit.github(organization: "attacker-org")`, verifies the HMAC with `S1` — succeeds.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) creates a `Status` record on the victim's commit marking the required CI context as `success`, regardless of the real CI state, enabling that commit to satisfy `Commit#deployable?` for an unauthorized deploy on `victim-org/victim-repo` — a repository/organization the attacker never authenticated against.
