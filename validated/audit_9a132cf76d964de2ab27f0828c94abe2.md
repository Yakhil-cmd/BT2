### Title
CCMenu Endpoint Ignores API Client's Stack Scope, Allowing a Single-Stack Token to Read Any Stack's Build Status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` authenticates requests using a bare `token` query parameter and then resolves the target stack directly from `params[:stack_id]`, bypassing the `stacks` scoping helper that every other API controller relies on to enforce an `ApiClient`'s `stack_id` restriction. This is structurally the same class of bug as the PoolTogether finding: a value that should be bound and validated against the authorization the credential actually carries (`_promotion.token`/promotion balance) is instead trusted/acted upon independently, letting the actor affect a resource outside what they were authorized for.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0)  and the fixtures show this is a real, supported configuration (`here_come_the_walrus` is scoped to `stack: shipit` with only `read:stack`) [2](#0-1) .

Every normal API controller enforces this scope through `BaseController#stacks`/`#stack`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the client is stack-scoped: [3](#0-2) 

`CCMenuController`, however, overrides both the authentication method and the `stack` resolver, and neither honours that scope: [4](#0-3) 

Specifically:
- `authenticate_api_client` accepts any token via `ApiClient.authenticate(params[:token])` and falls back to normal Basic-Auth handling only if that fails [5](#0-4) .
- `stack` is redefined to `Stack.from_param!(params[:stack_id])` — a direct, unscoped lookup — instead of delegating to the inherited `stacks.from_param!` that would filter by `current_api_client.stack_id` [6](#0-5) .
- `require_permission :read, :stack` only checks that the permission string `read:stack` is present in the client's `permissions` array via `ApiClient#check_permissions!`; it never checks `stack_id` [7](#0-6) [8](#0-7) .

Root cause: the binding "stack the token authorizes" (`current_api_client.stack_id`) is never checked against "stack the request touches" (`params[:stack_id]` resolved via `Stack.from_param!`). Before the (hypothetical) fix, a token created and handed out specifically for one stack (e.g. `stack: shipit`) is silently valid for `GET /api/:any_stack_id/cc.xml` on every other stack in the installation. After a correct fix, `CCMenuController#stack` would need to be resolved through the scoped `stacks` relation (as `BaseController` does) so the equality `current_api_client.stack_id == requested stack.id` (or "client is unscoped") holds before returning data.

### Impact Explanation
This is a "High — unauthenticated read of stack state" issue per the impact taxonomy: possession of any single valid `ApiClient` authentication token (even one deliberately restricted to a single, less-sensitive stack, e.g. handed to an external CI/status-badge integration) is sufficient to read the deploy status of every other stack managed by the Shipit instance — an authorization escalation across stack boundaries with only a `read:stack`-scoped credential for a completely different, narrower resource.

### Likelihood Explanation
Likelihood is high in scenarios where per-stack API clients are actually created (the fixtures indicate this is an intended feature), because the exploit requires nothing more than swapping the `stack_id` route segment in an otherwise legitimate, low-privilege token's request — no additional secrets, sessions, or GitHub credentials are needed.

### Recommendation
Have `CCMenuController#stack` resolve through the same `stacks` scope used by `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient`'s token cannot be used to fetch data for any stack other than the one it was created for.

### Proof of Concept
1. An administrator creates a stack-scoped `ApiClient` for Stack A with `permissions: ['read:stack']` and `stack: A` (mirrors `here_come_the_walrus` fixture) [2](#0-1) .
2. This token is distributed to a low-trust integration (e.g., a public CCMenu/CI-status widget) that is only supposed to see Stack A's build status.
3. That integration (or anyone who obtains the token from the widget's URL) sends `GET /api/<STACK_B_ID>/cc.xml?token=<TOKEN>`.
4. `authenticate_api_client` succeeds because the token is valid [5](#0-4) ; `require_permission :read, :stack` passes because `permissions` includes `read:stack` [7](#0-6) ; `stack` resolves Stack B directly, ignoring the client's `stack_id` binding to Stack A [6](#0-5) .
5. Stack B's latest deploy/rollback status is rendered and returned, even though the token was never authorized for Stack B [9](#0-8) .

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
