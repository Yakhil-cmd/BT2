### Title
Webhook signature verified against `repository.owner.login` while event handlers act on `repository.full_name`, allowing cross-organization event forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the webhook secret used to authenticate the request) based on `repository.owner.login`, but every `Handler` subclass resolves the actual `Stack`/`Repository` to mutate using a completely different payload field, `repository.full_name`. In a multi-organization Shipit deployment these two fields are never cross-checked against each other, so a payload can be signed with organization A's secret while acting on organization B's repository.

### Finding Description
The controller picks the verifying `GitHubApp` like this: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` loads the `GitHubApp` config (and its `webhook_secret`) for that specific organization, per the multi-org config schema documented in `docs/setup.md` (`github.somegithuborg.webhook_secret`, `github.someothergithuborg.webhook_secret`, etc.). Verification uses `github_app.verify_webhook_signature`, which is a pure HMAC comparison over the raw body with the secret belonging to whatever organization `repository.owner.login` claims to be: [3](#0-2) 

Once verification passes, `WebhooksController#create` dispatches the parsed JSON to handlers keyed only by event type — it never re-checks `repository.owner.login`: [4](#0-3) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) inherits `Handler#stacks` / `Handler#repository_name`, which resolves the target repository from a **different** field, `repository.full_name`: [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` to find the `owner`/`name` pair and loads that `Repository`'s stacks — independent of whichever organization's secret verified the request: [6](#0-5) 

This is structurally identical to the reported DEX bug class: one check (the swap/LP fee, here the HMAC signature) is computed over one basis (a virtual swap using a portion of the deposit, here `repository.owner.login`), while the actual effect that gets realized (the full asymmetric swap, here the repository/stack that is mutated) is driven by a different, unchecked basis (`repository.full_name`). The binding that should hold — "organization whose secret authenticated the payload" == "repository the payload's action is applied to" — is never enforced.

### Impact Explanation
In a Shipit instance configured with multiple GitHub App organizations (as explicitly supported and documented in `docs/setup.md`), an administrator/attacker who legitimately controls one organization's GitHub App (and thus its `webhook_secret`) can sign an arbitrary payload with their own secret while setting `repository.full_name` to point at a repository belonging to a *different* organization tracked by the same Shipit instance. Examples of resulting cross-organization writes:
- `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for the victim org's stack, forcing an out-of-band sync using an attacker-chosen `after` SHA.
- `StatusHandler` calls `commit.create_status_from_github!(params)` for any commit matching `params.sha` across all repositories/stacks tracked by the instance — commit SHAs are not organization-scoped, so this can inject a fabricated CI "success" status onto a victim's commit, which can influence continuous-delivery deploy eligibility checks.
- `CheckSuiteHandler` schedules check-run refreshes for a victim stack's commit.

This is a cross-repository write reachable without ever possessing the victim organization's `webhook_secret`, `api_clients_secret`, or any Shipit session — it only requires legitimate control of *any one* configured GitHub App/organization in a multi-org deployment. That satisfies the Critical bar of "cross-repository writes."

### Likelihood Explanation
Requires a multi-organization Shipit configuration (explicitly supported/documented) and requires the attacker to be an administrator of one of the configured GitHub App installations — not a privileged Shipit user, and not a leak of another organization's secret. This is a realistic operating mode for larger Shipit deployments serving multiple GitHub orgs, so likelihood is moderate rather than purely theoretical, though it depends on this specific deployment topology.

### Recommendation
`WebhooksController#verify_signature` (or `Handler#repository_name`) should cross-validate that the organization used to select the verifying secret (`repository.owner.login`) matches the owner encoded in `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org example).
2. As the administrator of `org-a`'s GitHub App, craft a JSON body for a `push` event:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, body)>` and POST to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "org-a")` and verifies successfully using `org-a`'s secret.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `org-b`'s stack — an action performed under `org-a`'s authentication but affecting `org-b`'s repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
