Based on my research, I found a concrete algorithmic-complexity (DoS) analog in the payment input/output validation path.

### Title
Unbounded, linear-scan duplicate-key check in AA payment validation causes quadratic-time DoS - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs` in `validation.js` deduplicates payment inputs/outputs by repeatedly calling `Array.prototype.indexOf` on a growing array (`objValidationState.arrInputKeys` / `arrOutputAddresses`) once per input/output, producing O(n²) validation cost for a single message. Crucially, the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap that would normally bound `n` is explicitly skipped for AA-generated messages, so a message emitted by an Autonomous Agent (AA) in response to an ordinary trigger is not size-limited before this quadratic check runs.

### Finding Description
The output-validation loop pushes each new address into `arrOutputAddresses` and checks membership with `indexOf` for every iteration: [1](#0-0) 

The same anti-pattern is repeated for every input type (issue, transfer, headers_commission/witnessing) against `objValidationState.arrInputKeys`, which grows unbounded across the whole message: [2](#0-1) [3](#0-2) [4](#0-3) 

The size cap that should keep `n` small is explicitly disabled for AA responses: [5](#0-4) 

This is structurally the same bug class as the glib gvariant report: input-validation hardening (duplicate/uniqueness checking added to prevent double-spends) that itself performs an O(n) operation per element inside an O(n) loop, and the size limit meant to bound `n` does not apply on the reachable path (AA responses), unlike the bounded case for ordinary user-authored units.

An AA's payment output amount/count is controlled by its own formula logic and by whatever UTXOs are available at its address (`aa_composer.js` builds the response payment by selecting inputs to cover the AA's requested outputs). Because `!objValidationState.bAA` disables the input-count cap, an attacker can:
1. Send a very large number of tiny "unprivileged" payments to a target AA's address (fragmenting its balance into many small UTXOs).
2. Send one ordinary trigger unit that causes the AA to emit a payment whose required output amount forces the automatic input-selection/composer to spend a huge number of those small UTXOs in a single response payment message.
3. When this AA response unit is validated by any node (as part of normal DAG processing that every node performing validation must do), `validatePaymentInputsAndOutputs` runs its `indexOf`-based duplicate check across all of these inputs without any cap, producing quadratic-time processing.

### Impact Explanation
A node validating the AA response unit incurs quadratic CPU cost proportional to the (attacker-inflated, uncapped) number of inputs. Because AA responses must be validated (and their validity affects unit/ball stability) by every full node, an attacker can use a modest amount of "unprivileged" fund fragmentation plus a single trigger to force disproportionate validation cost on the network, which is the requested class of "network unable to confirm new units in a timely manner" DoS impact — as opposed to a fatal validation-logic error.

### Likelihood Explanation
Triggering fragmented AA balances via many small payments and then sending a single trigger is achievable by any unprivileged unit poster/AA trigger sender; no special privileges, hub/peer trust, or node compromise are required. The exemption `&& !objValidationState.bAA` is explicit and easy to identify in the codebase, making the reachable path deterministic rather than probabilistic.

### Recommendation
- Replace the `arrInputKeys`/`arrOutputAddresses` linear-scan dedup with a hash-set (`Set`/plain-object lookup) for O(1) membership checks, removing the quadratic blow-up regardless of `n`.
- Apply a hard cap on the number of inputs (and inputs-per-message) generated by AA responses (remove or tighten the `!objValidationState.bAA` exemption at `validation.js:2137`), matching the bound already enforced for ordinary units.

### Proof of Concept
1. Author an AA that, on trigger, sends `trigger.output` bytes to a fixed address using a "send-all"/computed-amount payment message (a normal, permitted AA construct).
2. As an unprivileged user, send several thousand minimal-amount payments to the AA's address so its balance becomes fragmented into many tiny UTXOs (each such payment is an ordinary valid unit).
3. Send one trigger unit invoking the AA so that its automatic response payment must consolidate/spend a large fraction of those UTXOs as inputs in a single message.
4. Because `payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` is not enforced for AA responses (`validation.js:2137`), the resulting response message can contain an arbitrarily large `inputs` array; each node validating this unit executes the `indexOf`-based duplicate checks (`validation.js:2356-2359`, `2402-2405`, `2569-2572`) for every input against the ever-growing `arrInputKeys`, producing O(n²) validation time for that single unit.

Note: I was not able to retrieve the exact numeric values of `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` before the tool budget was exhausted; the finding is based on the confirmed code logic (the AA exemption and the linear-scan dedup pattern) rather than the specific constant magnitudes, which a Devin session with full repo access could confirm precisely.
