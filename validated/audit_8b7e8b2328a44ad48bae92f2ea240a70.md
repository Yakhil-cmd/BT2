### Title
Path traversal via unsanitized `file.Name` in `writeToOutput` allows writes outside `--output` directory - ([File: pkg/cmd/repo/read-file/read_file.go])

### Summary
`writeToOutput` builds the destination path by joining the user-supplied `--output` directory with `file.Name`, which is populated verbatim from the Contents API `"name"` JSON field with no sanitization. Since the value flows unchecked into `filepath.Join(dest, file.Name)` and then `os.WriteFile`, a response containing a `name` with `../` segments or an absolute path can cause the file to be written outside the directory the victim specified.

### Finding Description
`readFileRun` calls `fetchFile`, which unmarshals the API response into `contentsResponse` and copies `content.Name` directly into `repoFile.Name` with no validation [1](#0-0) . That struct is then passed to `writeToOutput`, where, if the output path is (or is treated as) a directory, the destination is computed as `dest = filepath.Join(dest, file.Name)` [2](#0-1) . `filepath.Join` cleans `..` segments arithmetically but does not prevent the result from escaping `dest` — e.g. `filepath.Join("./safe-dir", "../../etc/cron.d/evil")` resolves outside `safe-dir`. There is no `filepath.Base(file.Name)` call, no check that the resolved `dest` remains within `output`, and no rejection of absolute paths in `file.Name`. The only path-related sanitization in this file is for `content.Path` in error messages (to avoid escape-sequence injection), not for `content.Name` used in the file-write path [3](#0-2) .

Under normal operation against genuine GitHub, `name` is derived server-side from a git blob's basename, which git itself disallows containing `..` path components, so this is not reachable against api.github.com. However, the threat model explicitly includes "a host the victim points gh at" as attacker-controlled. If the victim runs `gh repo read-file <path> --hostname <attacker-controlled-host> --repo attacker/repo --output ./safe-dir/`, the attacker fully controls the HTTP response body returned for the Contents API call built in `contentsAPIPath`/`fetchContent` [4](#0-3) , and can set `"name"` to an arbitrary traversal string, causing `writeToOutput` to write attacker-controlled content to an arbitrary path reachable by the victim's OS user.

### Impact Explanation
Arbitrary file write outside the intended `--output` directory, with content fully controlled by the malicious host (via `file.Content`, itself taken verbatim from the same untrusted response). This matches GitHub's bounty impact class for file write/overwrite outside intended path, and can lead to further compromise (e.g. overwriting startup files, cron entries, or shell profile files) depending on which paths are writable by the victim's user.

### Likelihood Explanation
Requires the victim to run `gh repo read-file` against a host controlled by the attacker (e.g., via `--hostname`/GHE_HOST configuration, or a compromised/malicious enterprise endpoint) with `--output` pointing at a directory. This is a legitimate scenario under the stated attacker model ("controls responses from a host the victim points gh at") but is a more constrained precondition than a plain public-GitHub attack, since real github.com/GHES Contents API responses derive `name` from git tree basenames, which cannot contain `..` segments. Against the standard github.com host this is not exploitable.

### Recommendation
Sanitize `file.Name` before using it to build a destination path: take `filepath.Base(file.Name)` (or reject values containing path separators/`..`/leading `/` outright), and additionally verify with `filepath.Rel`/prefix-checking that the resolved `dest` stays within `output` before writing, rejecting the operation otherwise.

### Proof of Concept
```go
func TestWriteToOutput_PathTraversalViaName(t *testing.T) {
    dir := t.TempDir()
    outputDir := filepath.Join(dir, "safe-dir") + string(os.PathSeparator)
    require.NoError(t, os.MkdirAll(outputDir, 0755))

    file := &repoFile{
        Name:    "../../evil.txt", // attacker-controlled "name" field from Contents API response
        Path:    "path/to/file",
        Content: []byte("pwned"),
    }

    dest, err := writeToOutput(file, outputDir, false)
    require.NoError(t, err)

    // Assert the resolved destination escaped outputDir
    absOut, _ := filepath.Abs(outputDir)
    absDest, _ := filepath.Abs(dest)
    require.False(t, strings.HasPrefix(absDest, absOut),
        "expected write to escape output dir, got %s (outside %s)", absDest, absOut)

    content, err := os.ReadFile(absDest)
    require.NoError(t, err)
    require.Equal(t, "pwned", string(content))
}
```
This can be wired end-to-end with `httpmock` stubbing the Contents API GET to return `{"type":"file","name":"../../evil.txt","path":"path/to/file","content":"cHduZWQ=","encoding":"base64"}` and invoking `readFileRun` with `--output ./safe-dir/`, confirming the file lands outside `safe-dir`.

func fetchContent(httpClient *http.Client, repo ghrepo.Interface, filePath, ref string) (*contentsResponse, error) {
	apiPath, err := contentsAPIPath(repo, filePath, ref)
	if err != nil {
		return nil, err
	}

	req, err := http.NewRequest("GET", apiPath.String(), nil)
	if err != nil {
		return nil, err
	}
	// We use the "application/vnd.github.object+json" media type to request a unified object
	// representation from the Contents API. Without this, the API returns a JSON array for
	// directories and a JSON object for files.
	req.Header.Set("Accept", "application/vnd.github.object+json")

	resp, err := httpClient.Do(req)
	if err != nil {
		return nil, err
	}
	defer resp.Body.Close()

	if resp.StatusCode > 299 {
		return nil, api.HandleHTTPError(resp)
	}

	body, err := io.ReadAll(resp.Body)
	if err != nil {
		return nil, err
	}

	var content contentsResponse
	if err := json.Unmarshal(body, &content); err != nil {
		return nil, err
	}
	return &content, nil
