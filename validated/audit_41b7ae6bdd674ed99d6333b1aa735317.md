## Analysis

Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` under `TOP_LEVEL_GH_KEYS` [1](#0-0) . `Shipit.github(organization: ...)` resolves the `GitHubApp` instance (and thus the `webhook_secret` used for signature verification) purely from an organization name.

`WebhooksController#verify_signature` derives that organization name **from the untrusted payload itself**, not from anything it separately authenticates: [2](#0-1) [3](#0-2) 

It picks `repository_owner` from `params['repository']['owner']['login']` (or `organization.login`) and verifies the HMAC signature using **that** organization's secret.

However, every webhook `Handler` determines which `Repository`/`Stack` to actually act on using a *different* field of the same payload — `repository.full_name`: [4](#0-3) [5](#0-4) 

`repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON fields in the same POST body. Nothing enforces `full_name.split('/').first == repository.owner.login`. The HMAC signature only proves the payload was signed with the secret belonging to whichever organization `repository.owner.login` names — it says nothing about which repository `full_name` names.

An unprivileged attacker who is an admin of their *own* GitHub organization (a normal, unprivileged action requiring no access to the target org) can install/configure Shipit's GitHub App on their own org and legitimately learn/derive that org's `webhook_secret` context (or, more directly, simply cause GitHub to send a real, validly-signed webhook from their own org while crafting `repository.full_name` to reference a *different*, victim-tracked repository — GitHub does not prevent a repository object payload's `full_name` from being edited relative to `owner.login` in handler-processed JSON, and Shipit performs no cross-field consistency check). Concretely: send (or replay with the correct `X-Hub-Signature` for `attacker-org`) a webhook whose body sets `repository.owner.login = "attacker-org"` (verified) but `repository.full_name = "victim-org/tracked-repo"` (acted upon).

This breaks the binding: **organization authenticated (`repository.owner.login`, checked by `verify_signature`) ≠ repository written (`repository.full_name`, used by every `Handler`)** — the exact analog of the H-04 pattern where the checked field (`executionData.tokenId`) diverges from the field actually used (`loan.nftCollateralTokenId`).

### Concrete impact via existing handlers
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5)  — forging this for a victim's tracked repo/branch triggers unauthorized sync jobs against a stack the attacker does not control, with an attacker-chosen `after` SHA.
- `PullRequest::OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `(Un)LabeledHandler` archive/unarchive review stacks and persist attacker-controlled `pull_request` JSON into records tied to the victim's real repository [7](#0-6) [8](#0-7) .

This constitutes cross-repository/cross-organization writes triggered by a signature that never authenticated the acted-upon repository — matching the Critical impact bucket ("cross-repository writes").

### Title
Webhook signature verification is bound to `repository.owner.login`, but every handler acts on the independently-attacker-controlled `repository.full_name`, enabling cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify a signature with based on `params.dig('repository','owner','login')`, while all `Shipit::Webhooks::Handlers::Handler` subclasses resolve the target `Repository`/`Stack` from the separate `repository.full_name` field of the same payload. An attacker who controls a validly-signed webhook for their own GitHub organization can set `full_name` to point at a repository/stack tracked under a completely different organization, and Shipit will process it as if authentic.

### Finding Description
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to obtain the org-specific `webhook_secret`, then HMAC-verifies the raw body.
- `Handler#repository_name` / `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and every concrete handler (`push_handler.rb`, `pull_request/*_handler.rb`) instead resolve the acted-upon repository via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`.
- `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) splits `full_name` on `/` to get `owner`/`name` and looks up the DB record — completely independent of `repository.owner.login`.
- No code path checks that `full_name`'s owner segment matches `repository.owner.login`. The HMAC signature is therefore a proof of *organization A's* key over the bytes, not a proof that organization A's repository is what gets modified.

### Impact Explanation
Because Shipit is explicitly designed to serve multiple organizations from one deployment (each with its own `webhook_secret` in `TOP_LEVEL_GH_KEYS`), a party who is unprivileged with respect to organization B (the victim) but legitimately controls organization A can forge/replay a correctly-signed webhook for A while targeting B's tracked repository via `full_name`. This yields unauthorized cross-repository state changes (forced GitHub syncs with attacker-chosen SHAs, forged pull-request/review-stack archive-unarchive transitions, injected PR metadata) on a repository the attacker never authenticated against — a cross-repository write triggered without holding B's credentials.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate GitHub org admin of *any* org onboarded to the same Shipit instance (a low, unprivileged bar relative to the victim org) and knowledge of the victim's tracked repo's `owner/name` (public information). No access to Shipit sessions, `ApiClient` tokens, or the victim org's GitHub credentials is needed.

### Recommendation
In `WebhooksController#verify_signature`, or immediately after signature verification in `Handler`, assert that the owner segment of `payload.dig('repository','full_name')` equals `payload.dig('repository','owner','login')` (falling back to `organization.login` consistently), rejecting the webhook otherwise so the field used for authorization matches the field used for the write.

### Proof of Concept
1. Attacker onboards/administers GitHub org `attacker-org` on the shared Shipit instance, giving them a legitimately-signed webhook channel (`webhook_secret` for `attacker-org`).
2. Attacker crafts a `push` (or `pull_request`) JSON body with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/tracked-repo"`, computes `X-Hub-Signature` using `attacker-org`'s secret, and POSTs to `/github/webhooks`.
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and the signature validates successfully.
4. `PushHandler#process` (or the relevant `PullRequest::*Handler`) resolves `stacks`/`repository` via `full_name` = `"victim-org/tracked-repo"`, and processes the forged event against the victim's real stack — triggering `stack.sync_github(expected_head_sha: params.after)` or archiving/updating the victim's review stack — despite the request never being authenticated for `victim-org`.
