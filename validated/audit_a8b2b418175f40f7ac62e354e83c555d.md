### Title
`StatusHandler#process` binds CI statuses to a commit's SHA without verifying the webhook's claimed repository, letting cross-repository CI results satisfy `Commit#deployable?` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Commit#deployable?` trusts `Status` rows created purely from `sha`, and `StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` without ever checking that the webhook payload's `repository` matches the commit's own stack/repository [1](#0-0) . Because GitHub webhook signature verification is scoped to an *organization*/App-level `webhook_secret`, not to the specific repository named in the payload, a legitimately-signed webhook from one repository can attach a "success" status to a same-SHA commit tracked under a different stack, corrupting `Stack#next_commit_to_deploy` while `Stack#deployable?` remains untouched.

### Finding Description
Broken binding: `commit.statuses.last.state == 'success' for sha S` should imply `"the CI of commit S's actual tracked repository (stack.repository.full_name) reported success"`. Instead it only implies `"some webhook payload claiming state=success for sha S was accepted"`, with no equality check `payload['repository']['full_name'] == commit.stack.repository.full_name`.

Code path:
1. `WebhooksController#verify_signature` computes the expected HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly out of the attacker-controlled JSON body [2](#0-1) [3](#0-2) .
2. `Shipit.github` resolves to a single shared `GitHubApp` instance per organization (or a single global instance in "single-org" config mode where `github_default_organization` is `nil`), so the same `webhook_secret` verifies requests for every repository under that org/App installation [4](#0-3) .
3. Once the HMAC passes, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never consults `params['repository']` at all, and matches purely by SHA across the whole `commits` table (i.e., across every stack/repository Shipit tracks) [1](#0-0) .
4. `Commit#create_status_from_github!` stores the status using the commit's own `stack_id`, so the forged status lands on the *real* victim stack's commit row, not some throwaway record [5](#0-4) .
5. `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) then evaluates true off this forged status [6](#0-5) .
6. `Stack#next_commit_to_deploy` selects this "deployable" commit purely via `deployable_commits`/`commit.deployable?`, with no re-validation of provenance [7](#0-6) .
7. `Stack#trigger_continuous_delivery` proceeds to `trigger_deploy(commit, Shipit.user, ...)` once `Stack#deployable?` (locked/active-task/provisioning/deployment-checks — all independent of the forged commit status) is satisfied on its own schedule [8](#0-7) [9](#0-8) .

Exploit flow: an attacker who controls (or forks) a repository sharing the same GitHub App/webhook_secret scope as the victim's org (a very common single-secret-per-App/per-org GitHub configuration, documented in `docs/setup.md` and `config/secrets.*.yml` as the default single-org mode) can either (a) obtain a commit with an identical SHA to a pending commit in the victim repo (trivial for public repos via fork, since git commit hashes are content-addressed and portable across repos), then post a genuine "success" status against that SHA from their own repo/CI, which GitHub relays to Shipit's `/webhooks` endpoint with a valid signature for that shared secret; or (b) if `webhook_secret` is unset for the relevant org, `GitHubApp#verify_webhook_signature` returns `true unconditionally` [10](#0-9) , letting the attacker POST directly to `/webhooks` with a completely fabricated `sha`/`repository` body. Either way, `verify_signature`, `drop_unhandled_event`, and the `StatusHandler` `params` schema (which only validates types, not repository ownership) all pass, because none of them check that the reporting `repository` matches the commit's tracked stack.

### Impact Explanation
The result is an unauthorized deploy: the victim stack executes its deploy `Command`s (via `PTY.spawn`) against a commit that was never vetted by its own repository's CI, based solely on a status forged by/relayed from an unrelated repository. This matches the "unauthorized deploy" Critical category and, in the single-shared-secret/App configuration, is repeatable against any stack/repository sharing that App installation, and any SHA the attacker can reproduce (all pending/public commits of forked repos). Blast radius scales with how many stacks/orgs share one GitHub App webhook secret, which per this engine's own documented setup is often "all repos in one org."

### Likelihood Explanation
Requires: (1) the target stack already satisfying `Stack#deployable?` on its own (not locked, no active task — a normal, frequent operating state for CD-enabled stacks), (2) the attacker's repository sharing the org/App-level `webhook_secret` scope with the victim stack (the default single-org GitHub App topology used by this engine), and (3) the attacker being able to produce/report a status for a SHA that already exists as an undeployed `Commit` row on the victim stack (straightforward for public repos via forking, since SHA-1 commit hashes are identical across any repo holding the same commit object). No Shipit session, API token, or webhook secret is required beyond controlling a repo under the shared App installation. This is a repeatable, low-cost attack once the shared-secret precondition holds.

### Recommendation
In `StatusHandler#process` (and the equivalent check-run handler), verify that the incoming webhook's `params['repository']['full_name']` (or owner/name) matches `commit.stack.repository.full_name` before calling `create_status_from_github!`, discarding/logging mismatches instead of blindly matching by `sha` alone across all stacks.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status webhook naming a different repository still marks the victim commit deployable" do
  victim_stack = shipit_stacks(:shipit) # tracks "shopify/shipit-engine"
  commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...) # no statuses yet
  refute_predicate commit, :deployable?

  forged_payload = {
    "sha" => commit.sha,
    "state" => "success",
    "context" => "ci/travis",
    "repository" => { "full_name" => "attacker/unrelated-fork", "owner" => { "login" => "attacker" } }
  }

  # Signature computed with the org's shared webhook_secret (attacker's own CI legitimately triggered this)
  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  post :create, body: forged_payload.to_json, as: :json,
       headers: { "X-Github-Event" => "status" }

  commit.reload
  assert_predicate commit, :deployable?          # BROKEN: success came from "attacker/unrelated-fork", not "shopify/shipit-engine"
  assert_equal "attacker/unrelated-fork", forged_payload["repository"]["full_name"] # binding mismatch proven

  assert_difference "Deploy.count", 1 do
    victim_stack.trigger_continuous_delivery      # deploys the unvetted commit
  end
end
```
Assertion on both sides of the equality: `commit.stack.repository.full_name` ("shopify/shipit-engine") vs. `forged_payload["repository"]["full_name"]` ("attacker/unrelated-fork") — they differ, yet `commit.deployable?` and the subsequent `trigger_continuous_delivery` proceed identically to a legitimate success.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
