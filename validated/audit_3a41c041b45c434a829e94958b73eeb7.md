Found it: in the multi-organization GitHub App configuration, `Shipit.github(organization:)` looks up the webhook secret / signing key by `github_app_config(organization)` where `organization` is derived, in `WebhooksController#verify_signature`, from an **unverified field of the very payload being verified** — `repository_owner` in `app/controllers/shipit/webhooks_controller.rb:59-62` reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` before any HMAC check has taken place. This value selects *which* organization's `webhook_secret` is used to validate `X-Hub-Signature` in `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`), so the key used to authenticate the payload is chosen based on data the signature is supposed to protect.

### Title
Webhook signature verification key is selected from an unverified payload field, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/organization's `webhook_secret` to validate the request against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, not-yet-verified JSON body, then uses that organization's secret to check `X-Hub-Signature` against the same body.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from the raw request body before the signature has been validated: [1](#0-0) 
It then fetches the app config for that organization via `Shipit.github(organization: repository_owner)`, which resolves to `github_app_config(organization)` — a per-organization `webhook_secret` lookup keyed purely off this attacker-controlled string: [2](#0-1) 
The signature check itself (`verify_webhook_signature`) then HMACs the full raw body against whatever secret was resolved for that organization login: [3](#0-2) 
In a multi-tenant/multi-org deployment (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS`), each organization has its own GitHub App with its own `webhook_secret`. Because the org used for key selection comes from the same untrusted payload the signature is supposed to authenticate, an attacker who is a member/admin of *any one* organization configured on the Shipit instance (and thus knows or can obtain that organization's `webhook_secret`, e.g. from their own GitHub App settings) can craft a payload where:
- `repository.owner.login` = the org they control (so the signature check passes using that org's `webhook_secret`), while
- the rest of the payload's `repository.full_name`, `sha`, etc. reference a **stack belonging to a different organization/repository** entirely, since downstream handlers (`PushHandler`, `StatusHandler`, etc.) look up stacks/commits generically by whatever repository fields are present in `params`, independent of `repository_owner`.

This breaks the intended binding: `organization whose webhook_secret authenticated the request == organization whose repository/stack is written by the handler`.

### Impact Explanation
This allows cross-organization event injection: an attacker controlling one organization's legitimate webhook secret can forge `push`/`status`/`check_suite` events that Shipit will accept as authentic for a **different** organization's repositories, because only the org-selection field is checked, not a binding between the verified org and the acted-upon repository. This can be used to trigger `GithubSyncJob`, update commit/deploy statuses, or otherwise manipulate stack state for repositories the attacker does not control — cross-repository writes via a forged, "verified" webhook.

### Likelihood Explanation
Requires: (1) the deployment configured with multiple GitHub Apps/organizations (documented, supported feature — `Shipit.github_organizations`), and (2) the attacker to know/control one configured organization's `webhook_secret` (plausible if they administer their own org's GitHub App integrated with the same Shipit instance, e.g. a self-service or multi-tenant setup). No Shipit session, API token, or GitHub write access to the *target* repository is needed — only knowledge of one org's `webhook_secret`, which is an explicit deployment-trust boundary this engine is meant to enforce per-organization.

### Recommendation
Verify the signature using the secret selected the same way regardless of attacker-supplied fields is insufficient by itself; the real fix is to bind the *content acted upon* (`repository.full_name` / stack lookup) to the *organization whose secret validated the signature*, e.g., after successfully verifying with organization `O`, reject/ignore the event unless every repository referenced in the payload actually belongs to `O` (cross-check against `Repository`/`Stack` records scoped to that organization) before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is an admin of `OrgA`'s GitHub App and knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload where `repository.owner.login = "OrgA"` (so `repository_owner` resolves to `OrgA`, and the HMAC signature is computed correctly with `OrgA`'s secret) but `repository.full_name = "OrgB/target-repo"`.
4. `verify_signature` passes because the signature matches `OrgA`'s secret for the raw body.
5. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs `PushHandler`, which looks up the stack/commit using `repository.full_name`, i.e. `OrgB/target-repo`, and processes the (forged but "verified") event against `OrgB`'s stack.

Note: I was unable to fully trace `PushHandler`'s exact repository-lookup logic (its source wasn't returned by the index) to confirm it uses `repository.full_name` independent of `repository_owner`; this should be verified directly in `app/models/shipit/webhooks/handlers/push_handler.rb` before treating this as fully confirmed. Given the size/indexing limits, starting a full Devin session would allow inspecting that handler and downstream `Stack.from_github_repo_name`-style lookups to complete the proof.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
