### Title
Spending authority stays pinned to the mint-time `account.owner`, so a transferred position NFT leaves the previous owner/delegates able to drain the account - ([File: contracts/controller/src/account.rs])

### Summary
Controller spend paths authorize callers against the `owner` field stored inside the `Account` struct at mint time, while ownership itself is defined by the transferable position NFT (`owner_of`). The two authorization namespaces diverge on transfer: the NFT changes hands, but `account.owner` — and the delegate list keyed to it — is never updated, so the previous owner (or their still-active delegates) retains full spending authority over an account they no longer own.

### Finding Description
`create_account_with` writes `Account { owner: owner.clone(), ... }` once at mint, and nothing in `contracts/controller/src/account.rs` ever mutates that field afterward. Every value-moving entrypoint (`withdraw`, `borrow`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `flash_position`, `migrate_from_blend`) funnels through `require_owner_or_delegate(env, account_id, caller, &account.owner)`, which returns early only when `caller == account.owner` or `caller` is an active manager present in `storage::get_delegates(env, account_id, owner)` — again keyed on the stale stored owner. `add_delegate`/`renew_account` do authenticate via `storage::account_owner` (the NFT `owner_of`), proving the codebase treats NFT ownership as authoritative in one namespace but the stored field as authoritative in the other. The position NFT is the stock OpenZeppelin `NonFungibleToken`/`Enumerable` implementation (`contracts/position-nft/src/contract.rs:131-173`); its `transfer`/`transfer_from` paths carry no callback or hook that would let the controller re-sync `account.owner`, and `DataKey` exposes no such entrypoint.

### Impact Explanation
A user who sells, gifts, or transfers a position NFT loses ownership in the NFT registry but the controller still honors the previous owner's `require_auth` on every spend path. The previous owner (or any delegate they granted while still owner — the grant persists because `storage::add_delegate` was keyed to their address) can call `withdraw` to pull all collateral or `borrow` to draw debt against it, sending proceeds to themselves via the `to` recipient argument. This is theft of user funds reachable by a single unprivileged address, and also blocks the legitimate new owner, since `require_owner_or_delegate` will reject them (`caller != account.owner`, not in the stale delegate list), permanently freezing their control over the position they bought.

### Likelihood Explanation
Position NFTs are designed to be transferable (standard `transfer`/`transfer_from` are exposed, and the wiki documents `position-nft transfer/approve` as in-scope user actions). Any secondary-market sale, wallet migration, or transfer to a vault contract triggers the divergence with no special conditions. The attack requires only that the victim transfer their NFT while the account holds supply or borrowing capacity — the normal state of a lending position.

### Recommendation
Authorize every account-mutating path against the current NFT owner (`storage::account_owner`) rather than the cached `account.owner` field, or drop the stored field entirely. Delegate grants should be keyed to the current owner and invalidated on transfer; alternatively restrict transfers (soulbound) or add a controller-invoked owner-sync hook on NFT transfer that also clears the prior owner's delegate set.

### Proof of Concept
1. Alice calls `supply` with `account_id = 0`; controller mints NFT id N to Alice and stores `Account.owner = Alice`.
2. Alice optionally calls `add_delegate(N, manager)`.
3. Alice calls `position_nft.transfer(alice, bob, N)` — succeeds via the stock OZ implementation; no controller state changes.
4. Alice (or `manager`) calls `withdraw(caller=alice, account_id=N, withdrawals=[...], to=alice)`. `require_owner_or_delegate` compares `alice == account.owner` (still Alice) and passes; collateral is paid out to Alice.
5. Bob holds NFT N but `require_owner_or_delegate` rejects him (`bob != account.owner`, absent from `get_delegates(N, alice)`), so he cannot withdraw or manage the position he owns.

Caveat: this conclusion rests on `Account.owner` being stored state that is never refreshed after `create_account_with` — confirmed in `account.rs`, and the position NFT exposes no transfer hook — but I did not exhaustively verify `storage::get_account` doesn't re-derive `owner` from the NFT on load; if it did, this finding would collapse.
