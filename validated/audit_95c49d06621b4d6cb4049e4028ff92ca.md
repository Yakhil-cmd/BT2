### Title
Cross-repository `PullRequest` state forgery via `owner.login`/`full_name` split bypasses webhook signature scoping - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which org's webhook secret to verify against using `repository.owner.login`, while every `PullRequest` handler (including `AssignedHandler`) resolves the repository/stack it actually mutates using `repository.full_name`. These two fields come from the same untrusted JSON body and are never cross-checked, so an attacker can pick a "no-secret" org for `owner.login` (which makes signature verification a no-op) while pointing `full_name` at an arbitrary victim repository whose `PullRequest` record gets mutated.

### Finding Description
The broken binding the code implicitly assumes is:
`params.dig('repository','owner','login') == Repository.from_github_repo_name(params.dig('repository','full_name')).owner`

This is never enforced. Trace:

1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login')` and looks up the corresponding `GitHubApp` config: `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` **returns `true` unconditionally when `webhook_secret` is blank** for that org: `return true unless webhook_secret`. [3](#0-2) 
3. If the attacker names, in `repository.owner.login`, any org configured in `Shipit.github_apps`/organizations without a `webhook_secret` (or an org that resolves such that no secret check applies), the signature check trivially passes for *any* payload/signature — the request is accepted as authenticated for that (irrelevant) org.
4. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then dispatches the full raw JSON to handlers such as `AssignedHandler`, which never look at `repository.owner.login` at all. Instead they resolve the repository to act on purely from `params.repository.full_name`:
   `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. [4](#0-3) 
5. `AssignedHandler#process`, for `action` in `["assigned","unassigned"]`, then does `pull_request.update(github_pull_request: params.pull_request)`, mutating the persisted `Shipit::PullRequest` row joined to the victim stack/repository located via that `full_name`. [5](#0-4) 

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "unassigned",
  "number": <victim_pr_number>,
  "pull_request": { "...": "attacker-controlled state/head/sha/labels" },
  "repository": { "owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
No valid `X-Hub-Signature` for the victim org is needed since verification is keyed off `no-secret-org`, which has `verify_webhook_signature` short-circuiting to `true`.

Existing guards fail to prevent this because: `check_if_ping` and `drop_unhandled_event` only gate on event type presence, not repository identity; `ExplicitParameters` schema only validates shapes/types of `repository.full_name`/`owner.login`, not their consistency; there is no `require_permission!`/`current_user` check on this unauthenticated endpoint by design (webhooks are meant to be verified by HMAC signature, which is exactly what's bypassed here).

### Impact Explanation
The attacker can overwrite the `github_pull_request` JSON payload stored on a victim's `Shipit::PullRequest` record for a repository/stack they do not control and never authenticated against. Since `blocking_statuses` is configured on the victim stack, and `PullRequest#blocked?`/status logic (per `app/models/shipit/pull_request.rb`) derives from this stored `github_pull_request` data (state, head sha, labels, etc.), the attacker can flip whether the PR is considered blocking, potentially unblocking a deploy gate that should remain blocked, or vice versa. This is a payload for one repository (attacker's `no-secret-org`, which they nominally "authenticated" as) mutating another repository's stack/PR record — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any repository/stack whose `full_name` the attacker knows, as often as desired, and is not limited to `AssignedHandler` — the same `full_name`-based resolution pattern is shared by `ClosedHandler`, `EditedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, and `OpenedHandler`, widening blast radius across all PR-triggered webhook effects (stack archive/unarchive, review-stack provisioning, etc.).

### Likelihood Explanation
Preconditions: (a) at least one org/App config in `Shipit.github_apps` with no `webhook_secret` set (a fairly common misconfiguration/deliberate default for internal or low-security orgs) or, per the question's framing, any org an attacker can select via `repository.owner.login` that resolves without requiring a secret match; (b) knowledge of the victim's `full_name` (public information); (c) victim stack has `blocking_statuses` configured (common for CI-gated deploys). Attacker cost is a single unauthenticated HTTP POST with no valid GitHub secrets, no session, and no API token — fully within the declared attacker capability. This is trivially repeatable and scriptable against any number of target repositories.

### Recommendation
Enforce that the org used to select/verify the webhook secret is the same org that owns the repository referenced by `full_name` before dispatching to handlers — e.g., derive `repository_owner` from `repository.full_name.split('/').first` rather than `repository.owner.login`, and additionally require that any configured `GitHubApp` for that owner actually has a `webhook_secret` set (never silently return `true` from `verify_webhook_signature` for an app used to gate real repos); reject requests where these two do not match.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.github_apps` (or equivalent) with `"no-secret-org"` having no `webhook_secret`, and `"victim-org"` having a `webhook_secret` set.
2. Create `Shipit::Repository` with `github_repo_name == "victim-org/victim-repo"`, a `Stack` with `blocking_statuses` configured, and a `Shipit::PullRequest` (`number: 42`) attached to that stack, with a known initial `github_pull_request` (`state: "open"`, no blocking label/status).
3. Assert binding before: `pull_request.reload.github_pull_request["state"] == "open"` and `pull_request.blocked? == <expected baseline>`.
4. POST `/webhooks` with header `X-Github-Event: pull_request`, no valid signature for `victim-org`, and JSON body: `action: "unassigned"`, `number: 42`, `repository: { owner: { login: "no-secret-org" }, full_name: "victim-org/victim-repo" }`, `pull_request: {... attacker-chosen state/labels designed to flip blocked? ...}`.
5. Assert response is `200 OK` (not `422`), proving signature bypass.
6. Assert binding after: `pull_request.reload.github_pull_request` now reflects attacker-supplied data, and `pull_request.blocked?` has flipped from the baseline — despite the request never presenting a valid signature for `victim-org`. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
