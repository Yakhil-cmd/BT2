### Title
Unbounded-magnitude numeric validation (`^[0-9]+$`) in `stop-hook.sh` lets an oversized `max_iterations`/`iteration` value break bash arithmetic and silently disable the max-iterations bound - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
`stop-hook.sh` validates `ITERATION` and `MAX_ITERATIONS` only with the regex `^[0-9]+$`, which accepts digit strings of arbitrary length/magnitude, not just values that fit in bash's native (64-bit, `intmax_t`) arithmetic range. A crafted `max_iterations` value such as `99999999999999999999` passes this check but exceeds what bash's `[[ ... -gt ... ]]` numeric test and `$(( ))` arithmetic can represent, causing bash to raise an arithmetic evaluation error at that comparison rather than a clean true/false result.

### Finding Description
`stop-hook.sh` reads `iteration:` and `max_iterations:` from the YAML frontmatter of `.claude/ralph-loop.local.md` and validates them with `[[ ! "$ITERATION" =~ ^[0-9]+$ ]]` and the analogous check for `MAX_ITERATIONS` [1](#0-0) . This regex only enforces "digits only" — it places no upper bound on the number of digits, so a value like `99999999999999999999` (far beyond the ~1.8×10^19 range of a 64-bit signed integer) passes validation cleanly.

That value is then used directly in a numeric test without any range check: [2](#0-1) 
and later in arithmetic expansion: [3](#0-2) 

Bash's `[[ -gt ]]`/`$(( ))` operators convert operands via `intmax_t`-based parsing; digit strings beyond the representable range trigger a "value too great for base" arithmetic evaluation error rather than a normal comparison result. Because the erroring test sits inside an `if [[ ... ]] && [[ ... ]]; then` condition (line 51), and commands used purely as the condition of an `if` are exempt from `set -e` termination, the error is effectively swallowed and the condition is treated as false. The practical consequence: the max-iterations gate at line 51 can never fire again for the remainder of the loop's life, because `MAX_ITERATIONS` is copied verbatim into the state file each iteration and never revalidated/clamped by `sed` on line 155 — only `ITERATION` is rewritten. `ITERATION` itself stays small (it increments by 1 each turn via `$((ITERATION + 1))` at line 131, which works fine since `ITERATION` alone is small), so the enforcement of the user-approved `--max-iterations` bound is permanently defeated for that session.

The value reaches the state file through `setup-ralph-loop.sh`'s `--max-iterations` argument handling, which also only checks `^[0-9]+$` with no magnitude bound [4](#0-3) , and is written unmodified into the frontmatter [5](#0-4) . If prompt-injected content in a repo/issue/PR persuades the agent to invoke `/ralph-loop ... --max-iterations 99999999999999999999`, this oversized digit string flows straight into the state file and later into the hook's flawed arithmetic checks.

### Impact Explanation
This breaks the invariant that the user-approved `max_iterations` bound is enforced: instead of terminating the loop at the specified iteration count, the loop's cap silently stops being checked, causing the stop hook to keep blocking session exit ("decision: block") indefinitely. This is a denial-of-service via effectively unbounded looping/resource and API consumption, bypassing a user-approved safety bound rather than an early/graceful failure.

### Likelihood Explanation
Feasibility is moderate: the attacker does not need any elevated privilege, only the ability to get the value into the `--max-iterations` argument once (either directly by the user mistakenly supplying an oversized number, or indirectly via prompt-injected repository/issue/PR content that induces the agent to run `/ralph-loop` with that flag value). The regex check in both scripts is deterministic and always passes any all-digit string regardless of length, so the condition is 100% reproducible once the value is present in the frontmatter file.

### Recommendation
Bound the numeric validation to a sane range compatible with shell arithmetic, e.g. reject values greater than a fixed cap (such as `2^31-1` or a project-defined maximum like 100000) in both `setup-ralph-loop.sh`'s `--max-iterations` parser and `stop-hook.sh`'s frontmatter validation, rather than only checking `^[0-9]+$`. Additionally, wrap the arithmetic/comparison operations in `stop-hook.sh` with explicit error handling (e.g., validate with a numeric range regex like `^[0-9]{1,9}$`, or use `printf '%d'` with error trapping) so any residual overflow fails closed (state file treated as corrupted, loop stopped) instead of silently disabling the bound check.

### Proof of Concept
Unit/integration test plan:
1. Create `.claude/ralph-loop.local.md` with frontmatter:
   ```
   ---
   active: true
   iteration: 1
   max_iterations: 99999999999999999999
   completion_promise: null
   started_at: "2026-01-01T00:00:00Z"
   ---
   some prompt
   ```
2. Construct a minimal valid `transcript_path` JSONL with one assistant message containing non-promise text, and feed the corresponding hook input JSON via stdin to `stop-hook.sh`.
3. Run the hook repeatedly (simulating iterations 1, 2, 3, ...) and assert:
   - Expected/desired behavior: after exceeding a sane cap, the hook should either stop the loop (remove state file, exit 0 with no `block` decision) or clearly report state-file corruption for the oversized value — mirroring the existing "State file corrupted" messages at lines 29-37/40-48.
   - Actual behavior observed: the `if [[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]` check at line 51 raises a bash arithmetic "value too great for base" error (or is silently treated as false), the max-iterations branch is never taken, and the hook keeps emitting `{"decision":"block", ...}` regardless of how many iterations pass — demonstrating the bound is not enforced.
4. Add a regression assertion that any digit string longer than a defined maximum (e.g. 10 digits) causes the script to take the "state file corrupted" branch and `rm`+`exit 0`, rather than reach the arithmetic comparison at line 51.
