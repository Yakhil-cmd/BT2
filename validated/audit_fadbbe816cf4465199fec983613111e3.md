### Title
Cross-organization commit-status spoofing via webhook org/repository binding mismatch enables unauthorized deploy unblocking - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
In a multi-organization Shipit deployment (the documented "Using Multiple GitHub Applications" configuration), the webhook signature check authenticates the *organization* named in the payload, but the `status` event handler acts on the *commit* identified only by its `sha`, with no scoping to that organization or its repositories. This is the "organization that authenticated versus the repository that is written" binding break described in the rules.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the raw request body against using a value pulled from the very payload it is about to verify: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` is used to fetch the matching org's `webhook_secret`, per the documented multi-org config schema in `docs/setup.md` and `config/secrets.development.shopify.yml`: [3](#0-2) 

Because the entire request body is attacker-controlled JSON (the attacker only needs to know the `webhook_secret` for *any one* configured organization — e.g. their own, legitimately onboarded org, `OrgA`), they can set `repository.owner.login = "OrgA"` (to make verification pass using OrgA's known secret) while the `status` event's actual processing logic uses a *completely different field* that is not cross-checked against the verified organization at all:

`StatusHandler#process` looks up the target purely by global commit SHA, with no repository/organization scoping: [4](#0-3) 

`Commit.where(sha: params.sha)` searches the entire `commits` table across **all stacks belonging to all organizations** in the shared Shipit instance, since `Commit` has no repository/organization filter applied by this handler. Any commit whose SHA the attacker knows (SHAs are not secret — they're visible in PRs, CI logs, git history) belonging to *any other org's* stack can have a fabricated CI status attached via `Commit#create_status_from_github!`.

This directly feeds `Commit#deployable?`, which determines whether a commit is eligible for deploy or unblocking of the merge queue: [5](#0-4) 

### Impact Explanation
An attacker who is a legitimate (but unprivileged w.r.t. other orgs) participant in one organization configured on a shared multi-tenant Shipit instance can forge a `status` webhook, signed with their own org's `webhook_secret`, that spoofs `state: "success"` for an arbitrary commit SHA belonging to a **different organization's** stack. Since `Commit#deployable?` depends on `success? && !blocked?` derived from `Status`, this can flip a commit from "CI failing/pending" to "deployable" in another organization's repository — unblocking deploys/merges (`ProcessMergeRequestsJob` is enqueued on such transitions per `commits_test.rb`) that should have been gated by real CI results. This is an unauthorized bypass of deployment/merge gating across a repository/organization trust boundary the attacker does not control, matching the High-impact category ("escalation into... authorization... unauthorized deploy... cross-repository writes").

### Likelihood Explanation
Requires: (1) the host app to run the documented multi-org configuration (explicitly supported and documented), (2) the attacker to know the `webhook_secret` for at least one configured org (plausible for an org admin who set up their own org's GitHub App integration on the shared instance), and (3) knowledge of a target commit SHA in another org's stack (commit SHAs are routinely public in GitHub PRs/commits, not secret). No GitHub write access or Shipit session is needed — only the ability to send an HTTP POST with a valid HMAC for one org's secret.

### Recommendation
Scope the `status` (and any similarly-affected) webhook handler lookups by the verified organization: derive the target `Repository`/`Stack` set via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (as `Handler#stacks` already does for other handlers) and constrain `Commit` lookups to that repository's stacks, rather than a global, unscoped `Commit.where(sha: ...)`. Additionally, cross-validate that the organization used for signature verification matches the organization embedded in `repository.full_name` before processing any event.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per documented multi-org setup).
2. As a user who knows `OrgA`'s `webhook_secret` (e.g., an org admin of `OrgA`), craft a JSON body:
```json
{
  "sha": "<known commit sha from OrgB's stack, e.g. one currently failing CI>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/unrelated-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/github_hooks` (or the mounted webhook endpoint) with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s secret, and the signature verifies successfully.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the targeted commit in `OrgB`'s stack — and calls `create_status_from_github!`, setting a fabricated `success` status for a repository/org the attacker's credentials never authenticated against.
6. If that commit was blocking deploys/merges in `OrgB`, it is now marked deployable, without any real CI or GitHub-side confirmation.
