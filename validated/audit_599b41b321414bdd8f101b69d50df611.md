### Title
Webhook signature verification is keyed on `repository.owner.login` while stack resolution is keyed on `repository.full_name`, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` from the JSON body, but every `Handler` subclass (e.g. `PushHandler`, pull-request handlers) resolves the target `Stack`/`Repository` using `repository.full_name` from the same body. Because nothing binds these two fields together, an attacker who legitimately controls a webhook secret for their own org can forge a signature over a body whose `repository.owner.login` is their org (making it verify) while `repository.full_name` names a victim's stack.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`payload.dig('repository','owner','login')` (used to pick the HMAC secret) `== payload.dig('repository','full_name').split('/').first` (used to pick the target `Stack`).

Trace:
1. `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and uses it to fetch the appropriate `GitHubApp` via `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(signature, request.raw_post)`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` simply HMACs the entire raw request body with that org's configured `webhook_secret` and compares to the signature header. It has no knowledge of, or dependency on, `repository.full_name`. [3](#0-2) 
3. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then dispatches the same parsed body to handlers. [4](#0-3) 
4. `Handler#stacks` and `#repository_name` resolve the target repository purely from `payload.dig('repository', 'full_name')`, independent of `owner.login`: `Repository.from_github_repo_name(repository_name)`. [5](#0-4) 
5. `Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` columns directly - it does not cross-check against the HMAC-verified owner at all. [6](#0-5) 

Exploit: attacker administers `attacker-org` in Shipit's `secrets.github` config (a legitimate, documented multi-org setup) and knows `attacker-org`'s `webhook_secret`. They POST to `/webhooks` with header `X-Github-Event: push` and a JSON body where `repository.owner.login = "attacker-org"` (so `verify_signature` looks up and validates against the correct, attacker-known secret) but `repository.full_name = "victim-org/victim-repo"`. They compute a correct `sha1=` HMAC over this exact body using `attacker-org`'s secret and place it in `X-Hub-Signature`. `verify_signature` passes because the org used for secret lookup (`attacker-org`) and the secret used both belong to the attacker. `PushHandler#process` then calls `Repository.from_github_repo_name("victim-org/victim-repo")` and, if a matching stack/branch exists, invokes `stack.sync_github(expected_head_sha: params.after)` for the victim's stack, an attacker-chosen SHA. [7](#0-6) 

None of the existing guards prevent this: `drop_unhandled_event` only checks the event name is handled; `verify_signature` only checks the HMAC matches whichever org's secret corresponds to `owner.login` (which the attacker controls and deliberately sets to their own org); `ExplicitParameters` schemas (e.g. in `PushHandler`) only validate presence/type of `ref`/`after`, not that `repository.full_name`'s owner matches the verified `repository.owner.login`.

### Impact Explanation
This is a "payload for one repository mutating another's stack" scenario (Critical per the stated impact rubric). Concretely, the attacker can force `GithubSyncJob` to run against a victim's `Stack` with an attacker-chosen `expected_head_sha`, and analogous pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) resolve their target `repository`/review stack purely from `params.repository.full_name`, so the same divergence lets the attacker archive/unarchive/create review stacks belonging to a victim org they don't own, purely by knowing their own org's webhook secret. This is repeatable against any stack/repository configured in the same Shipit instance regardless of which GitHub org it belongs to, as long as the attacker controls at least one org's webhook secret in that instance's multi-org config.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with multiple GitHub organizations (a documented, supported configuration - `docs/setup.md` "Using Multiple GitHub Applications"), (2) attacker legitimately administers at least one of those orgs and therefore knows its `webhook_secret`, (3) a victim stack exists for a distinct repository in the same instance. Given these preconditions (single-org Shipit installations are unaffected since there's only one secret and thus one implicit trust boundary), the attack is cheap: one crafted POST with a correctly-computed HMAC, fully scriptable and repeatable without any live GitHub interaction.

### Recommendation
Bind the two identifiers before dispatching to handlers: in `WebhooksController#verify_signature` (or in `Handler#initialize`), verify that the owner segment of `payload.dig('repository','full_name')` matches `payload.dig('repository','owner','login')` (or `organization.login`), rejecting (422) if they diverge. Alternatively, have `Handler#repository_name`/`#stacks` also cross-check `payload.dig('repository','owner','login')` against `Repository#owner`, and only allow the org whose secret was used for verification to affect stacks under its own `Repository#owner`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "signature valid for attacker's own org cannot mutate a victim org's stack" do
  # Preconditions: multi-org secrets configured similarly to test/dummy/config/secrets_double_github_app.yml
  # "attacker-org" webhook_secret is known to the attacker; "victim-org" is a distinct, unrelated org.
  victim_stack = shipit_stacks(:shipit) # repository owner == 'shopify' (acts as victim-org)
  attacker_secret = Shipit.github(organization: 'attacker-org').send(:webhook_secret)

  body = {
    "ref" => "refs/heads/#{victim_stack.branch}",
    "after" => "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
    "repository" => {
      "owner" => { "login" => "attacker-org" },       # used by verify_signature -> attacker's own secret
      "full_name" => victim_stack.repository.full_name # used by PushHandler -> victim's stack
    }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)}"

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"]) do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```
Assert both sides of the equality explicitly: `body_owner = JSON.parse(body).dig('repository','owner','login')` (`"attacker-org"`) vs `body_full_name_owner = JSON.parse(body).dig('repository','full_name').split('/').first` (`"shopify"`/victim org) - they differ, yet the request still succeeds and mutates the victim stack, proving the binding is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
