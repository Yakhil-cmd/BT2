### Title
Asset attestor-list update can permanently freeze already-received asset outputs for existing holders - (File: `validation.js`)

### Summary
Obyte assets can be created with `spender_attested: true`, requiring every payer/payee of the asset to be attested by one of the asset's attestors before they can spend or receive it. The `asset_attestors` message lets the asset **definer** replace this attestor list at any point after issuance, and the new list is the only one used by validation going forward. Users who already legitimately hold the asset (received it while attested under the old list) permanently lose the ability to move those coins once the attestor list is changed such that they are no longer attested — with no fallback path to reclaim/withdraw the funds, mirroring the Biconomy `removeSupportedToken` bug where a later config change by a privileged party locks already-deposited user funds.

### Finding Description
When an asset has `spender_attested: true`, `storage.readAsset`/`loadAssetWithListOfAttestedAuthors` always looks up only the **latest** attestor list unit for the asset (ordered by level DESC LIMIT 1), not the list that was active when a given output was created: [1](#0-0) 

The asset definer can publish a new `asset_attestors` message at any time — this is not restricted to the genesis of the asset — and it is validated only for basic well-formedness and single-authorship by the definer: [2](#0-1) 

Once a new list is stable, `validatePayment` re-checks attestation against the current list for every subsequent payment message: if none of the authors is in the new attested-address set, the unit is rejected outright: [3](#0-2) 

The same freeze applies at the input level for existing (already-received) outputs of `is_private`/`fixed_denominations` assets and for divisible transferable assets — `owner address is not attested` is checked against the *current* attestor list, not the list that applied when the coin was created: [4](#0-3) [5](#0-4) 

There is no mechanism analogous to Biconomy's recommended mitigation (“allow withdrawals even if unsupported”): a holder whose address is dropped from the attestor list has no path to move or destroy the coins they already legitimately hold — every future payment message involving that address and that asset will fail `validatePayment`/`validatePaymentInputsAndOutputs`.

### Impact Explanation
This is a fund-freezing bug reachable by the asset issuer (an in-scope actor per the rules) acting entirely within the protocol: no consensus bug or hub compromise is needed. Legitimate holders of a `spender_attested` asset can have their existing balance made permanently unspendable the moment the definer posts a new `asset_attestors` list that omits them (whether maliciously, by mistake, or simply by replacing an attestor service). Because divisible/indivisible outputs already received under the old list are checked against the *current* list at spend time, the funds are effectively locked forever with no recovery path — the same category of impact as the referenced Biconomy finding (assets "not at direct risk" of theft, but liquidity/funds becoming permanently unwithdrawable).

### Likelihood Explanation
Any asset can be defined with `spender_attested: true` (a normal supported feature, not an edge case), and the definer legitimately controls posting `asset_attestors` updates at will after issuance — no special privilege beyond being the asset's own definer is required, and no additional confirmation, timelock, or grandfather clause exists. Any definer who rotates attestors (routine key/service rotation) can inadvertently or deliberately strand every previously-attested holder's balance.

### Recommendation
Consider one of:
- Snapshotting the attestor list applicable at the time an output was created and honoring that snapshot when validating a later spend of that specific output (grandfathering), rather than always requiring the *current* list; or
- Requiring `asset_attestors` updates to only add attestors (never fully replace/remove), or requiring an overlap/quorum with the previous list; or
- Providing an explicit "unwind" transfer path (analogous to Biconomy's suggested fix) allowing addresses no longer attested to move funds to the asset definer or to a whitelisted address once attestation is lost, so balances are not permanently stranded.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true`, initial `attestors: [X]`.
2. Attestor `X` attests address `H`. `H` receives a payment of asset `A` (validated fine, since `H` is attested — `validation.js:2115-2122`).
3. Definer posts a new `asset_attestors` message for asset `A` with `attestors: [Y]` (`Y` ≠ `X`), which passes `validateAttestorListUpdate` since only single-authorship by the definer and list well-formedness are checked (`validation.js:2829-2848`).
4. Once this update unit is stable, `storage.readAsset` resolves the *latest* attestor list to `[Y]` (`storage.js:1917-1946`).
5. `H` (never attested by `Y`) attempts to spend the previously-received asset `A` output. `validatePayment` finds `objAsset.arrAttestedAddresses.length === 0` for `H` and rejects with `"none of the authors is attested"` (`validation.js:2118-2119`); for private/fixed-denomination inputs the same is enforced via `"owner address is not attested"` (`validation.js:2432` / `2506`).
6. `H`'s previously valid balance in asset `A` is now permanently unspendable, with no path in the protocol to reclaim it.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
