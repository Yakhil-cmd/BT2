### Title
Webhook signature verified against attacker-chosen organization's secret while handlers act on a different, unverified `repository.full_name` — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-tenant Shipit deployments (multiple GitHub organizations configured under `secrets.github`, each with its own `webhook_secret`), `WebhooksController#verify_signature` selects which organization's secret to use for HMAC verification from an **untrusted, unverified** field in the payload (`repository.owner.login` / `organization.login`), while the event handlers that act on the payload use a **different** untrusted field (`repository.full_name`) to decide which `Stack`/`Repository` to operate on. The binding "organization whose secret authenticated the request" is never equal to "repository the handlers write to," so a webhook correctly signed with Org A's secret can carry `repository.full_name` pointing at Org B's repository, and Shipit will act on Org B's repo/stack as if it came from GitHub.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for signature verification purely from the raw JSON body, before any authentication has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `webhook_secret` from `secrets.github`: [3](#0-2) 

and `verify_webhook_signature` only checks the HMAC of the *whole raw body* against whatever secret was resolved for that organization: [4](#0-3) 

Once the body's HMAC matches the secret belonging to the organization named in `repository.owner.login`, the entire raw JSON — including a completely different `repository.full_name` value — is handed unmodified to the event handlers: [5](#0-4) 

All handlers (e.g. `PushHandler`) resolve the target `Repository`/`Stack` solely from `repository.full_name`, with no cross-check against the organization used to verify the signature: [6](#0-5) [7](#0-6) 

The same disjoint pattern exists in the PR/review-stack handlers (`OpenedHandler`, `LabeledHandler`, `AssignedHandler`, etc.), which independently resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`.

**Binding broken (equality that must hold but doesn't):**
`organization whose webhook_secret authenticated the request` == `organization owning the repository the handler subsequently writes to`.

Before the attacker's request: for a legitimately-delivered GitHub webhook, both fields (`repository.owner.login` and `repository.full_name`'s owner segment) always refer to the same repository/org, because GitHub itself populates them consistently and signs the whole payload with the secret of the org that owns that repo.

After the attacker's request: an attacker who is a legitimate/authorized user of Org A's repo (able to configure or observe Org A's `webhook_secret`, e.g. because they administer that org's GitHub App/webhook in a shared multi-tenant Shipit instance) can send a payload:
```json
{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}
```
signed with Org A's `webhook_secret`. `verify_signature` resolves `repository_owner` = `orgA`, verifies successfully against Org A's secret, and then `PushHandler` (using the *same* parsed payload) looks up the stack for `orgB/victim-repo` and calls `stack.sync_github(expected_head_sha: params.after)` — a write operation on a repository/stack belonging to Org B, which the attacker never authenticated for.

### Impact Explanation
This breaks the tenant isolation the per-organization `webhook_secret` design (`docs/setup.md` "Using Multiple Github Applications") is meant to provide: possession of one organization's webhook secret lets an attacker forge Shipit-processed GitHub events (push, status, check_suite, membership, pull_request, etc.) that are attributed to and acted upon a different organization's repositories/stacks. Depending on the handler this can trigger unauthorized `GithubSyncJob` syncs with attacker-chosen `expected_head_sha`, fabricate commit statuses, or affect merge-queue scheduling (`stack.schedule_merges` is triggered from status transitions) for a stack the attacker does not own — a cross-repository/cross-organization write performed without the corresponding organization's authentication, matching the "unauthorized deploy/rollback" and "cross-repository writes" impact classes.

### Likelihood Explanation
Exploitability requires only knowledge of a webhook secret for *any one* organization onboarded to a shared, multi-tenant Shipit instance (the normal operating mode documented in `docs/setup.md`), plus knowledge of the target `full_name` of a repository already configured as a Stack in the same instance (`full_name` is not secret — it's a public GitHub repo path). No GitHub App private key, `GITHUB_TOKEN`, or Shipit session/API token is needed; this is purely a mismatch in how the controller performs signature-scoped authentication versus how handlers use the payload.

### Recommendation
Bind the verification target to the same field the handlers use for authorization: derive the organization for `verify_signature` from `repository.full_name`'s owner segment (or, better, cross-validate that `repository.owner.login` matches the owner segment of `repository.full_name` before verifying), so the same repository is both the subject of authentication and the subject of the write. Alternatively, after successful signature verification, re-derive and enforce that any repository the handler acts on belongs to the same GitHub organization/installation whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As someone with access to Org A's webhook secret (e.g., an Org A admin), craft a `push` event payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
     "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}
   }
   ```
3. Sign the raw body with `orgA`'s `webhook_secret` (`sha1=` HMAC) and POST it to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"orgA"`, verifies successfully with Org A's secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/victim-repo")` [6](#0-5) [7](#0-6)  and enqueues `stack.sync_github(expected_head_sha: "deadbeef...")` for Org B's stack — a write triggered without any authentication from Org B.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
