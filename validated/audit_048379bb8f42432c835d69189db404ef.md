### Title
Asset attestor list can be freely updated by the definer after coins are already issued/held, freezing spendable funds - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, the definer publishes an initial attestor list at asset-definition time, but nothing prevents the definer from later posting an `asset_attestors` message that adds or removes attestors *after* the asset has already been issued and transferred to holders. `validateAttestorListUpdate` performs no check analogous to nounsbuilder's missing `mintCount`/`totalSupply` guard — it only checks that the asset requires attestors and that the sender is the definer, with no restriction tied to whether coins already exist for addresses relying on the current attestor set.

### Finding Description
`validateAttestorListUpdate` in `validation.js` validates an `asset_attestors` message purely against the asset's static properties and sender identity: [1](#0-0) 

There is no check on prior issuance/spending activity (e.g. no equivalent of `settings.mintCount > 0` in the referenced `updateFounders`/`setReservedUntilTokenId` pattern) before allowing the attestor list to be rewritten. The definer alone (`onlyOwner`-style check `objUnit.authors[0].address !== objAsset.definer_address`) can attach a fresh `asset_attestors` message at any main chain index, arbitrarily late in the asset's lifetime.

This matters because spend validation for `spender_attested` assets is evaluated dynamically against the *current* attestor list, not the list that was in effect when the funds were received. In `validatePayment`: [2](#0-1) 

`objAsset.arrAttestedAddresses` is computed at validation time from `storage.loadAssetWithListOfAttestedAuthors`, which filters the unit's authors against attestations issued by the *currently active* attestor set for that asset. If the definer removes an attestor (or replaces the whole list) via a later `asset_attestors` message, any address whose attestation came only from the removed attestor immediately fails `arrAttestedAddresses.length === 0` on every subsequent spend attempt — even though those coins were legitimately received earlier under the previously valid attestor set.

### Impact Explanation
This is directly analogous to the `updateFounders` issue: a privileged, single-signer configuration change (attestor list / analogous to founder list) is permitted with no state guard reflecting that funds have already been distributed under the prior configuration (analogous to `mintCount > 0`). The consequence here is concrete and reachable by an unprivileged actor holding the asset: previously valid, already-issued or already-transferred coins of a `spender_attested` asset can be rendered permanently unspendable (fund freezing) by a later, single unilateral action from the asset definer, with the DAG/validation logic enforcing this freeze deterministically for every full node. This satisfies the "AA/asset fund freezing" impact class even though the actor here is the asset definer rather than an AA, because the freezing is achieved purely through unit-level validation rules reachable by any asset holder attempting to later spend their balance.

### Likelihood Explanation
The action requires only that the actor be the asset's `definer_address` — no other privilege or vulnerability chain is needed, and it is a completely valid, in-protocol operation (`asset_attestors` message) at any main_chain_index after the asset was created. Any asset creator who sets `spender_attested: true` can trivially trigger this by posting a new attestor list once they have observed holders receiving/transferring the asset, making this a straightforward, repeatable action rather than a theoretical edge case.

### Recommendation
Introduce guards in `validateAttestorListUpdate` (and/or `checkAttestorList`) mirroring the `mintCount`/`totalSupply` checks recommended for `updateFounders`: e.g., disallow removing addresses that already hold outstanding balances attested under the old list without a migration/transition mechanism, or require that historical attestation status (at the time coins were received) be honored for already-issued outputs rather than re-evaluating attestor membership against the current list at spend time. At minimum, document and rate-limit this as a known centralization/freezing risk for `spender_attested` assets, or add on-chain notice/timelock so holders can react before losing access to their funds.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and initial `attestors: [X]`. [3](#0-2) 
2. Attestor `X` attests address `H`; `H` receives asset `A` outputs via `payment`, which validates successfully because `arrAttestedAddresses` includes `H` (attested by `X`).
3. Later, the definer posts an `asset_attestors` message replacing attestors with `[Y]` (removing `X`) — accepted because `validateAttestorListUpdate` only checks `objAsset.spender_attested` and sender identity, not whether `H` already holds funds attested under `X`. [1](#0-0) 
4. `H` attempts to spend the previously received asset `A` outputs. `storage.loadAssetWithListOfAttestedAuthors` now computes `arrAttestedAddresses` using the new attestor `Y`; since `H` was never attested by `Y`, `arrAttestedAddresses` no longer contains `H`.
5. `validatePayment` rejects the spend with "none of the authors is attested": [2](#0-1) 
6. `H`'s previously valid funds are now permanently frozen, purely due to a unilateral, unrestricted definer action taken after issuance — with no mitigating check present in the codebase (verified: `validateAttestorListUpdate` has no issuance/holding-based guard).

Note: I was unable to fully trace `storage.loadAssetWithListOfAttestedAuthors`'s exact SQL/logic within the available tool budget (only partial visibility into `storage.js` was obtained), so the precise mechanics of how `arrAttestedAddresses` is filtered should be double-checked by a follow-up review of `storage.js` before remediation, though the validation-layer reachability and lack of guards in `validateAttestorListUpdate` are confirmed directly from the cited code.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
