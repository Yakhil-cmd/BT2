### Title
Cross-repository status forgery via SHA-only matching in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, ignoring the `repository` field present in the same webhook payload, unlike every other handler (e.g. `PushHandler`) which scopes through `Repository.from_github_repo_name(repository_name)&.stacks`. Since git commit SHAs are content-addressed and identical commits legitimately exist in forks/mirrors of a public repo, a validly-signed status webhook about a commit in one repository can silently attribute a status to the *same-SHA* commit tracked under a completely unrelated Shipit stack (e.g. `victim/prod`).

### Finding Description
The binding the question implies should hold is: `status.context` satisfaction for `victim/prod`'s required-context policy == a status reported by `victim/prod`'s own configured CI integration for that exact commit in that exact repository. In code, this binding is never enforced: `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1)  with no filter on `payload['repository']['full_name']`, whereas `Handler#stacks` — used by `PushHandler` — explicitly resolves the target via `Repository.from_github_repo_name(repository_name)` [1](#0-0) .

Downstream, `Commit#create_status_from_github!` → `add_status` reloads the commit's `status`, and if the new simple_state differs, calls `stack.schedule_merges if new_status.pending? || new_status.success?` [4](#0-3) , which feeds `MergeRequest::StatusChecker` (built from `stack.cached_deploy_spec.merge_request_required_statuses`) [5](#0-4)  and `reject_unless_mergeable!` [6](#0-5) , exactly the path the question describes.

However, exploiting this still requires a *validly signed* webhook to reach `/webhooks`. `WebhooksController#verify_signature` computes the signature per organization via `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature` (an HMAC keyed with the org's `webhook_secret`, unknown to an unprivileged attacker) [7](#0-6) [8](#0-7) . This means an attacker cannot simply POST an arbitrary JSON body claiming `repository.full_name = "attacker/repo"` — the signature must be genuine, i.e. GitHub itself must have actually delivered that webhook, which only happens for a repository within an org where Shipit's GitHub App is installed. Given the audit's stated attacker capability of "emit webhooks from a repository they own," the realistic exploit requires that the attacker's repository (or fork) sits within the same GitHub App installation scope as `victim/prod` (e.g. an org-wide App install), and that the attacker can create a commit with the *identical SHA* as the target commit in `victim/prod` (trivial for public repos/forks, since commits are content-addressed and can be pushed byte-for-byte into any repository the attacker controls) and set a real status on their own repo/commit via GitHub's real API. GitHub would then deliver a genuinely signed `status` webhook whose `repository` differs from `victim/prod` but whose `sha` collides — and `StatusHandler` applies it to `victim/prod`'s commit regardless.

### Impact Explanation
If exploited, an attacker-controlled repository can inject a status update — with an arbitrary `context`, `state: success`, `description`, `target_url` — onto a commit tracked by an entirely different stack/tenant (`victim/prod`), satisfying required-status policy it never actually met. This can cause `MergeRequest#reject_unless_mergeable!` to stop returning `'ci_missing'`/`'ci_failing'`, allowing `merge!` to proceed and merge a PR that never passed the victim's real CI (unauthorized merge), and/or trigger `stack.schedule_merges`/continuous-deployment on the strength of a forged status. This is a cross-tenant/cross-repository payload mutating another repository's commit/stack state, matching the "Critical: payload for one repository mutating another's stack, commit, task or team / an unauthorized deploy or merge" category.

### Likelihood Explanation
Preconditions are non-trivial but realistic: (1) `victim/prod` must be a public repo (or otherwise forkable) so an attacker can reproduce an identical commit SHA in a repository they control; (2) that attacker-controlled repository must be within the scope of the same GitHub App/webhook installation that Shipit trusts for `victim/prod`'s organization (org-wide App installs are common); (3) the attacker needs write access to set a commit status on their own repo (trivial — it's their own repo) or trigger their own CI there. Given those, the attack is fully repeatable and requires no secrets, tokens, or Shipit privileges — it only relies on GitHub's own signing of a webhook the attacker legitimately triggered on infrastructure they control.

### Recommendation
Scope `StatusHandler#process` to the payload's own repository, mirroring `Handler#stacks`/`PushHandler`: resolve `stacks` (or the specific `Repository`) from `payload.dig('repository', 'full_name')` and restrict the `Commit` lookup to `stacks.commits.where(sha: params.sha)` (or equivalently join through `Stack`/`Repository`) instead of an unscoped `Commit.where(sha: params.sha)` across all tenants.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks, `stack_a` (repo `attacker/repo`) and `stack_b` (repo `victim/prod`), each with a `Commit` having the **same `sha`** (simulating identical content pushed to both repos).
2. Configure `stack_b.cached_deploy_spec` with `merge.require: ["ci/required"]` (or `ci.require`) so `merge_request_required_statuses` includes `"ci/required"`.
3. Assert baseline: build a `MergeRequest` on `stack_b` with `head` = that commit, call `reject_unless_mergeable!`, and assert it returns `'ci_missing'` (equality: `commit.statuses.for_context('ci/required')` empty == required not satisfied).
4. Simulate delivering a `status` webhook whose `payload['repository']['full_name'] == 'attacker/repo'` but `sha` equals the shared SHA and `context: 'ci/required', state: 'success'`, via `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Reload `stack_b`'s commit and assert a `Status` row was created for it (`commit.statuses.where(context: 'ci/required', state: 'success').exists?` is now true) even though `payload['repository']['full_name']` never equals `'victim/prod'`.
6. Call `reject_unless_mergeable!` again on the `victim/prod` merge request and assert it no longer returns `'ci_missing'`, demonstrating the forged cross-repository status satisfied the required-context check without any status ever being reported against `victim/prod`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
