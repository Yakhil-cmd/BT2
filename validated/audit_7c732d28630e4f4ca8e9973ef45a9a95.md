### Title
AA payments of `spender_attested` assets permanently bounce (and freeze the AA's funds/state) if the payout recipient is not on the asset's attestor list - (File: `aa_composer.js`, `validation.js`)

### Summary
An Autonomous Agent (AA) that must pay out a `spender_attested` asset to a specific address (e.g. a lending/liquidation-style AA settling collateral or repaying a counterparty) composes and sends the payment without pre-checking whether the recipient is currently on the asset's attestor list. The attestor-list check is only enforced later, during unit validation. If the recipient is not attested, the whole triggering unit bounces, the AA's state changes for that trigger are discarded, and — critically — this failure is deterministic and will recur on every retry as long as the recipient remains unattested, permanently freezing the funds/logic tied to that payout inside the AA.

### Finding Description
`spender_attested` assets restrict who may hold/receive them: `validatePaymentInputsAndOutputs` in `validation.js` calls `storage.filterAttestedAddresses` over all output addresses and rejects the unit with `"some output addresses are not attested"` if any recipient is missing from the current attestor list: [1](#0-0) 

The attestor list itself is fully controlled by the asset's definer, who can update it at will via an `asset_attestors` message; only the definer may edit it: [2](#0-1) 

When an AA composes a response containing a `payment` message for such an asset, `aa_composer.js`'s `sendUnit`/`completePaymentPayload` flow loads asset info via `storage.loadAssetWithListOfAttestedAuthors` (keyed on the AA's own spending address), but does not check that the *output* recipient addresses are attested before building and posting the unit: [3](#0-2) 

The recipient-attestation check only happens afterwards, inside `validateAndSaveUnit`, which reuses the same `validatePaymentInputsAndOutputs` logic described above: [4](#0-3) 

If that validation fails (e.g. because the recipient was removed from, or never added to, the attestor list), the AA bounces the entire trigger: [5](#0-4) 

Bouncing discards all state variable updates for that trigger and refunds the trigger amount minus bounce fees, i.e. the intended state transition (marking debt repaid, releasing collateral, crediting a counterparty, etc.) never happens: [6](#0-5) 

This is directly analogous to the Sentiment V2 bug: there, USDC's issuer-controlled blacklist could make a `transfer()` to a specific position address always revert, permanently bricking that position's liquidation. Here, the asset definer's attestor list plays the same role as USDC's blacklist/allowlist — an externally, issuer-controlled admission list gating whether a specific address can ever receive that asset — and an AA-mediated payout to a non-attested address will bounce every single time it is attempted, with no way for the AA (or anyone else) to route around it.

### Impact Explanation
Any AA-based protocol built on top of a `spender_attested` asset (e.g. a whitelisted stablecoin-like asset used for lending, collateral settlement, or counterparty payouts) that must eventually send that asset to a fixed, user-controlled address can have that specific operation permanently and irrecoverably fail if the recipient is (or becomes) unattested. Because bouncing rolls back all state changes for the trigger, funds/state that were supposed to move as part of that operation remain stuck inside the AA — an AA fund-freezing condition, matching the "AA fund loss or freezing" impact class.

### Likelihood Explanation
Likelihood is low but non-negligible, mirroring the original report's own low/medium likelihood classification: it requires (a) an AA-based protocol built around a `spender_attested` asset, and (b) the specific recipient address failing to be (or ceasing to be) attested — which is entirely at the asset definer's discretion and can also happen incidentally (e.g. an address simply never having been attested, or being pruned from an updated attestor list) rather than requiring active malice.

### Recommendation
- Before composing/sending a payment message for a `spender_attested` asset in `aa_composer.js`, check `storage.filterAttestedAddresses` (or equivalent) against the intended output addresses and fail fast (or route to an alternate address / hold in escrow) rather than relying solely on the later `validateAndSaveUnit` check to catch it via a bounce.
- AA developers using `spender_attested` assets should be warned (in documentation/oscript guidance) that outgoing payments to arbitrary addresses can permanently fail, and should design fallback/escrow logic (e.g. allow the intended recipient or a third party to claim funds once attested, instead of hard-coding a single payout attempt whose failure discards all state progress).

### Proof of Concept
1. Define an asset `A` with `spender_attested: true` and an initial attestor list `[X]`, via the `asset` message.
2. Deploy an AA that, on trigger, computes some internal state (e.g. "debt repaid to user U") and, in the same response, sends a `payment` message of asset `A` to address `U`, where `U` is not currently in `A`'s attestor list.
3. Fire the trigger. `aa_composer.js` composes the response and reaches `completePaymentPayload` (`aa_composer.js:1312-1345`), which does not verify `U`'s attestation. The unit is built and passed to `validateAndSaveUnit` (`aa_composer.js:1405-1411`), which calls into `validatePaymentInputsAndOutputs` (`validation.js:2630-2641`) and fails with `"some output addresses are not attested"`.
4. The AA bounces (`aa_composer.js:1388-1391`), discarding the "debt repaid" state update; the trigger amount is refunded minus bounce fees.
5. Retrying the trigger reproduces the same bounce indefinitely as long as `U` stays unattested — demonstrating that the AA can never complete this payout, permanently freezing the associated funds/logic.
