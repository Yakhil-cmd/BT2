**Analysis:**

The premise assumes a "stale local chain-id cache" in mempool or vm-validator that could cause `prologue_common`'s chain-id assert to pass incorrectly. This does not match the actual implementation:

- `chain_id::get()` in Move directly reads the live on-chain `ChainId` resource (`borrow_global<ChainId>(@aptos_framework).id`) — there is no caching layer inside the Move VM's execution path. [1](#0-0) 

- `prologue_common` performs this comparison against the transaction's `chain_id` argument on every validation, using the resolver/state view tied to the specific ledger state being validated (not any external mempool-maintained cache): `assert!(chain_id::get() == chain_id, error::invalid_argument(PROLOGUE_EBAD_CHAIN_ID));`. [2](#0-1) 

- `AptosVM::validate_transaction` (the vm-validator entrypoint) builds a fresh `MoveResolver` from the passed-in `state_view` for each call and invokes the prologue against that resolver — there is no separate long-lived "local chain-id cache" object that could desync from actual chain state. [3](#0-2) 

- Mempool itself does not independently validate or cache `chain_id` at all — it defers entirely to the VM validator's prologue check via `TransactionValidation`, so there's no mempool-side chain-id state to go "stale."

- Existing tests explicitly confirm the check works correctly: submitting a transaction signed with a mismatched `chain_id` is rejected with `StatusCode::BAD_CHAIN_ID` both at execution and at `vm-validator` level. [4](#0-3) [5](#0-4) 

Since `chain_id::get()` always reflects the actual state being validated against (there is no separable/staleable cache that the check could read instead), there's no code path by which an attacker-controlled cross-chain-signed transaction could bypass this assert. The admission checks (mempool → vm-validator → VM prologue) converge correctly on the live chain-id value in every case, so per the Review Sequence's rejection criterion, this does not qualify as a valid finding.
