### Title
`Commit.where(sha:)` in `StatusHandler#process` writes CI status without repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Finding Description

The broken binding: `params.repository.full_name` (the repo GitHub actually authenticated the webhook signature for) is claimed to equal `commit.stack.repository.full_name` (the repo whose stack record gets mutated). In `StatusHandler#process`, this equality is never enforced:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, table-wide lookup with no `stack_id`/repository filter. Any `Commit` row across the entire installation whose `sha` column matches the attacker-supplied `sha` param gets its status updated via `create_status_from_github!`, which calls `add_status`, evaluates `deployable?`/`blocked?`, emits `deployable_status` hooks, and can trigger `stack.schedule_merges` and `schedule_continuous_delivery` [2](#0-1) [3](#0-2) .

`WebhooksController#verify_signature` only validates the webhook's HMAC against the secret registered for the `repository_owner` (the GitHub *organization* the payload claims), via `Shipit.github(organization: repository_owner)` [4](#0-3) . This proves the payload was signed by GitHub for *some* repository under that organization/app installation — it does **not** bind the payload to the specific repository whose stack the SHA belongs to. `StatusHandler` then performs no additional repository check before mutating `Commit` rows.

Because git commit SHAs are content-addressed, any commit shared between two repositories under the same GitHub App/organization installation (e.g., a fork sharing history with upstream, or a repo mirrored/renamed and re-added as a second stack) has an identical SHA in both. An attacker who owns a repository in that same org/installation can push a commit and cause GitHub to emit (or, per the threat model, directly submit) a validly-signed `status` webhook with `context: ci/circleci`, `state: success` for that shared SHA. `StatusHandler` will apply this status to **every** `Commit` row with that SHA — including one that belongs to an unrelated victim `Stack` — without checking that the victim stack's repository matches the one that authenticated the request.

If the victim stack has `bot_login` configured (`Shipit.user`), continuous delivery and merge-queue automation run under that bot identity with no additional human authorization gate; flipping a required `ci/circleci` context to `success` for the shared-SHA commit makes `Commit#deployable?` true and can trigger `schedule_continuous_delivery` / `stack.schedule_merges`, resulting in an actual deploy or merge action performed by the bot for a repository/stack the attacker never authenticated against [5](#0-4) .

None of the listed guards close this gap: `verify_signature` is organization-scoped, not repository- or stack-scoped [6](#0-5) ; the `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`, `state`, `context`, etc., not repository ownership [7](#0-6) ; and `Commit#create_status_from_github!` performs no repository cross-check either [8](#0-7) .

### Impact Explanation

A `status` webhook for one repository can flip CI state (and, transitively, deployability, merge scheduling, and bot-driven continuous delivery) for a `Commit`/`Stack` belonging to a different, victim repository whenever the two share a commit SHA (forks, mirrors, renamed remotes tracked as separate stacks). This is a cross-tenant write: "a payload for one repository mutating another's stack, commit" is explicitly listed as Critical impact. Repeated for every shared SHA, and automatically weaponized into an unauthorized deploy/merge when the victim stack has a `bot_login` configured, since continuous delivery there proceeds without a human approval step.

### Likelihood Explanation

Exploitation requires: (1) a shared commit SHA between an attacker-controlled repository and a victim stack's tracked repository — realistic for forks or repositories re-pointed/renamed and re-added to Shipit as new stacks sharing history, not generally exploitable across arbitrary unrelated repositories due to SHA1 preimage difficulty; (2) both repositories under a GitHub App/organization installation configured in Shipit, so `verify_signature`'s per-organization secret check passes; (3) the victim stack configured to require the `ci/circleci` context and to auto-deploy via a `bot_login`. Given these preconditions, the attacker's cost is a normal commit push/fork plus one HTTP webhook, and the attack is fully repeatable against any other stack sharing that SHA.

### Recommendation

Scope the `StatusHandler` (and analogous handlers using bare-SHA lookups) query by the repository asserted in the webhook payload, e.g. join through `Commit -> Stack -> Repository` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_for(params) })`, resolving the repository from `params.repository.full_name`/`id` rather than trusting only the organization-level signature check.

### Proof of Concept

minitest plan under `test/`:
1. Create two `Stack`s (`stack_a` for repo `attacker/repo`, `stack_b` for victim repo `victim/repo`), with `stack_b.bot_login` set to a configured `Shipit.user`, and `stack_b` requiring `ci/circleci`.
2. Create `Commit` rows on both stacks with the identical `sha` (simulating shared fork history).
3. Assert baseline: `commit_b.deployable?` is `false` (no successful status yet) — left side of the binding: `commit_b.stack.repository.full_name == "victim/repo"`, right side (attacker's authenticated repo): `"attacker/repo"` — these differ.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(params_for(sha:, context: 'ci/circleci', state: 'success')).process` (payload signed/attributed to `attacker/repo`).
5. Assert `commit_b.reload.deployable?` is now `true` and/or that `stack.schedule_merges`/`ContinuousDeliveryJob` was enqueued for `stack_b`, proving a status authenticated for `attacker/repo` mutated `victim/repo`'s stack despite the two `full_name` values never matching.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
      head(422) unless verified

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
