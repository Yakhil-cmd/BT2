### Title
`is_collateralizable` / `is_borrowable` edits are enforced only at position entry; existing positions keep their collateral weight and debt treatment forever - (File: contracts/controller/src/positions/mod.rs)

### Summary
`SpokeAssetConfig.is_collateralizable` and `SpokeAssetConfig.is_borrowable` are the per-listing analogs of the WLFI `categoryInfo.enabled` flag. Governance can clear them via `edit_asset_in_spoke` (`contracts/controller/src/config/asset.rs:29`), but the flags are read exclusively in `require_can_supply` / `require_can_borrow`, invoked only from `validate_position_entry_gates` (`contracts/controller/src/positions/mod.rs:243-252`). Nothing in the risk/exit path — `risk/totals.rs` health-factor math, `update_account_threshold`, `withdraw`, `liquidate`, `clean_bad_debt` — ever reads them. A `grep` of `contracts/controller/src` confirms `is_collateralizable`/`is_borrowable` appear only in `config/asset.rs` (write) and `positions/mod.rs` (entry gate). So once a user's position exists, the flags are meaningless: governance cannot actually revoke collateral status for already-deposited assets.

### Finding Description
The check in `validate_position_entry_gates`:

```rust
// contracts/controller/src/positions/mod.rs:243-252
for (hub_asset, _) in aggregated {
    match position_type {
        AccountPositionType::Deposit => {
            require_can_supply(env, cache, account.spoke_id, &hub_asset);
        }
        AccountPositionType::Borrow => {
            require_can_borrow(env, cache, account.spoke_id, &hub_asset);
        }
    }
}
```

runs only on new deposit/borrow legs. The health-factor path (`risk/totals.rs`, cached `loan_to_value`/`liquidation_threshold` restamped by `update_account_threshold`) values every stored deposit position at its `SpokeAssetConfig.ltv`/threshold regardless of `is_collateralizable`. The harness test `test_spoke_collateral_flag_update_blocks_new_supply_but_existing_withdraw_works` (`tests/test-harness/tests/controller/spoke.rs:580`) confirms the intent that clearing `can_collateral` is a *prospective* gate only — but nothing compensates on the risk side: the existing balance keeps contributing full collateral weight, and `frozen`/`paused` are the only halt flags consulted on exit (`enforce_spoke_asset_flags`, `positions/mod.rs:257-278`).

This is the exact WLFI bug shape: a disable that looks like a circuit breaker but silently does nothing for already-assigned state.

### Impact Explanation
When governance decides an asset is unsafe as collateral (oracle doubt, depeg, exploit) and clears `can_collateral`, the flag has zero effect on accounts already holding it: they keep full LTV/threshold credit, can keep borrowing against it via other entries, and remain shielded from liquidation exactly as before. The admin lever implied by the flag and the test name ("blocks new supply") does not reduce protocol exposure to the toxic collateral. On a volatile delisted asset this is the classic path to protocol insolvency — new supply is stopped but existing bad collateral keeps underwriting new borrows (`borrow` checks `require_can_borrow` on the *debt* asset, never on the collateral legs backing it).

### Likelihood Explanation
Requires only an existing collateral position plus a governance `edit_asset_in_spoke` call clearing `can_collateral` — a routine operation (flag tightening is even guardian-privileged per ADR-0007, i.e., expected in emergencies precisely when revocation matters most). No attacker privilege needed; any unprivileged holder of the flagged asset benefits automatically. Severity is bounded to Medium/High because governance retains partial mitigations (`paused`, `frozen`, `no_seize`, LTV reduction to 0 via `edit_asset_in_spoke`), so the flag's failure is a footgun rather than an unpatchable hole — but the code and tests never document that `is_collateralizable` is entry-only, mirroring the original report.

### Recommendation
Enforce `is_collateralizable` in the risk path, not just entry: in `risk/totals.rs` (and the `update_account_threshold` restamp), treat positions whose current `SpokeAssetConfig.is_collateralizable == false` as zero collateral weight, or force them into a debt-like accounting bucket. If gradual unwinding is preferred, zero the effective `loan_to_value`/`liquidation_threshold` for non-collateralizable assets so `update_account_threshold` converges accounts to liquidation eligibility. Symmetrically, decide and document whether `is_borrowable = false` should also affect accrued debt treatment. At minimum, state the entry-only semantics explicitly in the `SpokeAssetConfig` natspec and invariants doc, since the current behavior is indistinguishable from a bug from an operator's perspective.

### Proof of Concept
1. Alice supplies USDC in spoke 2 (`supply`), collateral flag true, LTV 97%. She also supplies/uses it to back a borrow of USDT.
2. Governance (or guardian) calls `edit_asset_in_spoke` with `can_collateral = false` for USDC (test at `tests/test-harness/tests/controller/spoke.rs:590` does exactly this via `t.edit_asset_in_spoke("USDC", 2, false, true, 9700, 9800, 200)`).
3. New `supply` of USDC reverts `NOT_COLLATERAL` (proven in the test).
4. Yet Alice's HF still counts her USDC at `loan_to_value = 9700` — `risk/totals.rs` reads `ltv`/`threshold`, not `is_collateralizable` — so she can call `update_account_threshold` and continue borrowing on other listings, or simply avoid liquidation, entirely on collateral governance has disabled.
5. The state persists indefinitely; only an explicit LTV-to-0 edit (a separate, non-obvious operator action) removes the weight.

Unknown/unverified: I did not read `risk/totals.rs` or `require_can_supply`'s body line-by-line; the conclusion that `is_collateralizable` is never consulted outside entry gates rests on the grep showing only two references in `controller/src`, which is strong but not exhaustive evidence (a compiled-generated wrapper could theoretically check it).
