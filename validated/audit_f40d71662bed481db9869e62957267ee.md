### Title
Cascading revert of the entire AA chain when a downstream secondary AA bounces will DoS deposits/composability of independent upstream AAs - (File: aa_composer.js)

### Summary
In `aa_composer.js`, when a primary AA's response sends funds to another AA address in the same unit, `handleSecondaryTriggers()` is used to fire a secondary trigger into that AA. If the secondary AA "bounces" for any reason internal to its own logic (e.g. it enforces its own pause/frozen condition, insufficient internal balance, or any unmet `if` condition), the entire primary trigger — including all of the primary AA's own state changes and payments that had nothing to do with the failure — is unwound via `revert()`. This mirrors the Sherlock finding where `StakedEXA.harvest()` unconditionally depends on an external `Market` that may be paused/frozen, causing the whole (unrelated) deposit flow to revert.

### Finding Description
`handleTrigger()` composes an AA's response and, if that response sends assets to another AA address, calls `handleSecondaryTriggers()`: [1](#0-0) 

Each output AA is triggered as a "secondary" AA via a recursive `handleTrigger()` call: [2](#0-1) 

Crucially, if any of these secondary AAs bounces (returns an error), the primary (non-secondary) trigger does not simply ignore or isolate that failure — it reverts the *entire* chain, discarding the primary AA's own already-computed state/balance changes and payments: [3](#0-2) 

`revert()` then performs a real rollback of the database transaction back to the initial savepoint, clears all in-memory state var caches, and calls `bounce()` on the primary AA, undoing any legitimate, independent work the primary AA had already done: [4](#0-3) 

This means a primary AA (e.g. a vault/staking AA analogous to `StakedEXA`) that forwards part of a user's deposit to a secondary AA (analogous to `Market`) is fully at the mercy of that secondary AA's own internal preconditions. If the secondary AA enforces any pausable/frozen state (a common, legitimate oscript pattern using a state variable check and `bounce(...)`), then every trigger to the primary AA that results in an onward payment to the secondary AA will unconditionally fail and roll back, even though the primary AA's own logic executed correctly and has nothing to do with the secondary AA's internal state.

### Impact Explanation
Because any user can send a trigger unit to the primary AA (deposit), and the DoS condition is entirely controlled by the state of an *independent* secondary AA that the primary AA's author chose to integrate with (analogous to Exactly's `Market`), this can:
- Freeze all deposits/composable operations of the primary AA whenever the downstream AA it forwards funds to enters a paused/frozen/error state, exactly matching the reported impact of "frozen deposits" and "new users missing out on yield while current AA balance state is stuck."
- Force affected users to eat bounce fees while receiving no state update, and prevents the primary AA from processing any trigger that touches the secondary AA until the secondary AA's condition changes — a condition the primary AA's users/author do not control.

### Likelihood Explanation
This is reachable by any unprivileged user simply by sending a normal payment/trigger unit to a primary AA that is composed with another AA (a common, encouraged design pattern for chained/composable AAs, as shown in the "chain of AAs" test). No special privileges are needed to trigger the primary AA; the only precondition is that the downstream AA it forwards funds to has entered a state where it bounces (which itself could be set by its own unprivileged users/oracles or built-in logic, not necessarily an admin).

### Recommendation
Provide a documented pattern/primitive for primary AAs to safely detect a paused/unavailable downstream AA before forwarding funds (e.g. reading the downstream AA's state vars via `var[address]['key']` and gating the forward payment on it, or exposing a `bounce_fees`/return-code mechanism) so the primary AA's own composed logic (e.g. accepting a deposit) does not have to be fully atomic with, and does not have to unconditionally revert because of, the downstream AA's arbitrary internal preconditions. At minimum, the AA authoring guide should highlight that any onward payment to another AA makes the whole trigger's fate depend on that AA's bounce conditions, and authors should add explicit guards (e.g. checking a `paused` state var of the target AA) before sending funds to it.

### Proof of Concept
1. Deploy `Downstream AA` with a `paused` state var that, when true, causes every trigger to `bounce('paused')` (a normal oscript pattern).
2. Deploy `Vault AA` whose response for any deposit trigger performs its own state update and then forwards part of the received funds to `Downstream AA` (same pattern as the "chain of AAs" test in `test/aa_composer.test.js`, lines 156–252, where `primary_aa` forwards payment to `secondary_aa`).
3. Set `paused = 1` in `Downstream AA` (an action independent of `Vault AA`'s admin).
4. Any user sends a normal deposit trigger to `Vault AA`.
5. `Downstream AA`'s secondary trigger bounces; per `handleSecondaryTriggers` (aa_composer.js:1742-1749), `Vault AA`'s entire response — including its own unrelated state changes — is reverted via `revert()` (aa_composer.js:1759-1783), and the user's deposit trigger itself bounces, losing bounce fees with no state progress in `Vault AA`.
