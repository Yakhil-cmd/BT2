### Title
Webhook signature verification is bypassed for GitHub organizations configured without a `webhook_secret`, allowing forged events to write to *any* tracked repository - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success, and the controller that calls it selects *which* organization's secret to check against using an attacker-controlled field from the unauthenticated request body — a field that is never cross-checked against the field the downstream handlers actually act on. This is the same class of bug as the reported `mintWithPermit` issue: a security-critical action (accepting the webhook, then executing it against a repository) is taken on the strength of a check whose scope does not cover the data actually consumed.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` instance to verify against based on the payload's own `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations, each with its own independently-configured (and documented as *optional*) `webhook_secret`: [4](#0-3) [5](#0-4) 

Once `create` runs, the payload is dispatched to a handler that determines *which repository/stack to mutate* using a **different** field, `repository.full_name`, with no relationship enforced back to the organization used for signature selection: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that is broken is: **organization authenticated (via `repository.owner.login`/`organization.login`, used solely to pick a secret) ≠ repository written (via `repository.full_name`, used by the handler)**. An unprivileged, unauthenticated attacker can send a POST to `/webhooks` claiming to be from an organization X that has no `webhook_secret` configured (satisfying `return true unless webhook_secret`), while setting `repository.full_name` to any *other* tracked repository/stack in the Shipit instance (belonging to organization Y, which does have a secret). The signature check never inspects Y's secret at all, and the handler blindly trusts `repository.full_name` from the same unverified body.

### Impact Explanation
This lets an attacker with no GitHub credentials and no Shipit account:
- Force an arbitrary tracked stack to sync to an attacker-chosen commit SHA via `PushHandler` → `stack.sync_github(expected_head_sha:)`.
- Inject forged commit statuses (`state`, `context`, `target_url`, `description`) via `StatusHandler#process` → `commit.create_status_from_github!`, which can be used to fabricate a passing CI/deployable status that stacks rely on to gate/allow deploys.
- Create/delete team memberships cross-organization via `MembershipHandler`.

Because this can result in forged deploy-gating state and unauthorized state changes on repositories/stacks that do not belong to the attacker, this reaches "cross-repository writes / unauthorized deploy" territory (Critical) at minimum, and unauthenticated read/write of stack and task state (High) at minimum.

### Likelihood Explanation
The precondition — one configured organization lacking a `webhook_secret` while others are tracked in the same Shipit instance — is explicitly presented as a supported, "optional" configuration in the docs and is present in the repo's own multi-org fixtures/tests (`webhook_secret: # nil`). Any installation that follows the documented setup for a secondary/low-priority org without a webhook secret, while running other higher-value orgs' repos on the same instance, is exposed. No credentials, GitHub App keys, or session are required — only a direct HTTP POST to the public `/webhooks` endpoint.

### Recommendation
- Make `webhook_secret` mandatory (or reject events for any organization without one) instead of returning `true` in `GitHubApp#verify_webhook_signature` when `webhook_secret` is blank.
- Bind the organization used for signature verification to the organization the handler actually mutates: after determining the target repository/stack from `repository.full_name`, assert its owning organization matches `repository_owner` used in `WebhooksController#verify_signature` before processing.
- Consider verifying against all configured GitHub Apps/secrets rather than trusting an attacker-suppliable field to pre-select which secret is checked.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `OrgA` (no `webhook_secret`) and `OrgB` (with a `webhook_secret`, tracking a sensitive stack, e.g. `orgb/prod-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "OrgA" },
  "repository": { "full_name": "orgb/prod-repo", "owner": { "login": "OrgA" } },
  "sha": "<target commit sha in orgb/prod-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` to `"OrgA"` (line matches `owner.login`), calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which returns `true` unconditionally since `OrgA` has no `webhook_secret` — no signature needed at all.
4. `StatusHandler` then creates a forged successful status on the commit belonging to `orgb/prod-repo`, despite the attacker never possessing `OrgB`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
