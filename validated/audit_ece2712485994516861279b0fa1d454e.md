### Title
Cross-Repository Commit Status Forgery via Unscoped `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit supports multi-tenant configuration where several independent GitHub organizations/Apps, each with its own `webhook_secret`, are registered on the same Shipit instance [1](#0-0) . The webhook signature is verified using the secret of whichever organization is *named inside the untrusted JSON payload itself* [2](#0-1) , but the `status` event handler that consumes that payload never re-checks which repository/organization the event actually claims to belong to — it matches purely by commit SHA across the whole database [3](#0-2) . This breaks the binding: `organization that authenticated the webhook == repository whose commit status is written`.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login')` — a field taken from the unauthenticated raw JSON body — and uses it to pick which configured GitHub App/org's `webhook_secret` should verify the HMAC signature: [4](#0-3) [5](#0-4) 

This only proves the request was signed with *some* configured org's secret — not that the org matches the actual content of the payload being processed. Other handlers, like `PushHandler` and `CheckSuiteHandler`, do scope their side effects to the repository named in the payload via the `Handler#stacks`/`repository_name` helper (`Repository.from_github_repo_name(repository_name)`) [6](#0-5) [7](#0-6) [8](#0-7) .

`StatusHandler`, however, does not use `stacks`/`repository_name` at all — it looks up commits solely by SHA, globally, with no repository filter: [3](#0-2) 

Because a commit SHA is a public value (visible via GitHub UI/API for any public or accessible repo) and is not tied to the org that signed the request, an attacker who legitimately controls their **own** unrelated organization registered in the same multi-tenant Shipit instance (i.e., they know their own `webhook_secret`, which they set up themselves — not the victim's) can:
1. Compute a valid `X-Hub-Signature` using their own org's secret over an arbitrary JSON body.
2. Set `repository.owner.login` to their own org login (so `verify_signature` picks their own known secret and passes).
3. Set `sha` in the body to the SHA of a commit belonging to a completely different, victim stack/repository they have no access to.

`verify_signature` succeeds because it only checks that the payload was signed by *an* org's secret it knows about — it never checks that `repository_owner` equals the owner of the repo the commit with that `sha` actually belongs to. `StatusHandler#process` then writes an attacker-controlled status (`state`, `context`, `description`, `target_url`) onto the victim commit via `commit.create_status_from_github!(params)`.

### Impact Explanation
This is a cross-repository write: an attacker who is only authorized for one organization/repository in a multi-tenant Shipit deployment can inject arbitrary CI/commit statuses onto commits belonging to a different organization/repository that they do not own or have any access to. Since Shipit's deploy safety gating (`release_status?`/`release_status_context`, referenced from `Stack`) relies on commit statuses to determine whether a commit is deployable [9](#0-8) , a forged "success" status on the required CI context could make an otherwise-non-deployable commit appear deployable, potentially enabling an unauthorized deploy of that commit on the victim's stack. This matches the "cross-repository writes" / "unauthorized deploy" high/critical impact classes.

### Likelihood Explanation
Requires: (a) a multi-org/multi-tenant Shipit installation (an explicitly documented and supported configuration) [1](#0-0) , (b) the attacker controlling their own legitimately-registered organization/App in that instance (not the victim's credentials — no privileged access to the victim needed), and (c) knowledge of a target commit SHA, which is generally public/discoverable information for the target repository. No webhook secret theft, no ApiClient token, and no privileged account on the victim's side is required — only participation as a tenant of the shared Shipit instance.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`), require that the commit's stack repository matches the `repository_name`/`repository_owner` declared in the same verified payload before applying any status update, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of an unscoped `Commit.where(sha: params.sha)`. More generally, `WebhooksController#verify_signature` should not use attacker-supplied payload fields to select the verification secret without also asserting, post-verification, that the same fields match the repository/org actually mutated by the handler.

### Proof of Concept
1. Attacker registers/operates their own GitHub organization `attacker-org` in the shared Shipit instance, with known `webhook_secret` `S_attacker`.
2. Attacker identifies a target commit SHA `deadbeef...` belonging to `victim-org/victim-repo`, tracked as a stack in the same Shipit instance.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
signed with `HMAC-SHA1(S_attacker, raw_body)` as `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully with `S_attacker`.
5. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, finds the victim's commit, and calls `create_status_from_github!`, writing the forged `success` status onto `victim-org/victim-repo`'s commit despite the attacker having no relationship to that repository.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

        'WebhookController#verify_signature',
