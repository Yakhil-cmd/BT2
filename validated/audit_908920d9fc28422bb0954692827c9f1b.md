### Title
Webhook signature verified against `repository.owner.login`, but the acted-upon repository is resolved from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `payload.dig('repository', 'owner', 'login')`, while every `Handler` subclass resolves the `Repository`/`Stack` that will actually be mutated using a *different* payload field, `payload.dig('repository', 'full_name')`. These two fields are never cross-validated, so a valid signature computed with one organization's `webhook_secret` does not guarantee that the payload's `repository.full_name` actually belongs to that organization.

### Finding Description
`verify_signature` picks the GitHub App/org config solely from the owner login field: [1](#0-0) [2](#0-1) 

Every webhook `Handler` instead determines the target repository from `full_name`: [3](#0-2) 

`PushHandler` and `StatusHandler` then act on whatever `Stack`/`Commit` that `repository_name` resolves to: [4](#0-3) [5](#0-4) 

Because `Shipit.github(organization: repository_owner)` implies the engine supports multiple independently-configured organizations (each with its own `webhook_secret`), the security boundary is: "the organization whose secret produced a valid `X-Hub-Signature`" must equal "the repository the payload claims to describe." The code enforces `HMAC(owner_org_secret, raw_body) == signature`, but never enforces `repository.full_name` starts with `repository.owner.login`. An attacker who legitimately controls one configured organization (and therefore its `webhook_secret`) can forge a payload where `repository.owner.login` is their own org (so the HMAC check passes) but `repository.full_name` names a completely different, victim-owned repository. The handler layer will happily resolve and mutate the victim's `Stack`/`Commit` records.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." With a forged `push` payload, an attacker can trigger `stack.sync_github(expected_head_sha: ...)` for a victim repository/stack they do not own [4](#0-3) , and with a forged `status` payload can inject fabricated commit statuses onto arbitrary victim commits [5](#0-4) , which can be used to satisfy deploy/merge gating logic that checks required statuses, ultimately enabling an unauthorized deploy on a stack the attacker has no legitimate access to.

### Likelihood Explanation
Requires the attacker to control at least one organization that is genuinely configured in this Shipit instance (and thus knows a valid `webhook_secret` for that org) - a plausible scenario in any multi-tenant/multi-org Shipit deployment where organizations are not mutually trusted. No repository write access, `ApiClient` token, or session is needed; only the ability to send an HTTP POST with a self-crafted JSON body and a correctly computed HMAC for the attacker's *own* organization.

### Recommendation
In `Handler#repository_name`/`stacks`, cross-check that `payload.dig('repository', 'owner', 'login')` matches the owner segment of `payload.dig('repository', 'full_name')` before resolving to a `Stack`, or better, verify the signature using the same field (`full_name`'s owner) that handlers use to resolve the target repository, so the two checks are provably bound to the same value.

### Proof of Concept
1. Attacker registers/controls organization `evil-org` in the Shipit instance, knowing its `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "evil-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(evil-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: 'evil-org')`, computes HMAC with `evil-org`'s secret, and it matches → request accepted.
5. `PushHandler` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: attacker_chosen_sha)` on the victim's stack, even though the attacker never controlled `victim-org`.
