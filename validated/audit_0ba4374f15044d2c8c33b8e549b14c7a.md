### Title
`data_feed[[...ifnone=X]]` allows AAs to silently substitute a hard-coded default price when an oracle has not posted, leading to the same "default price" mis-valuation bug as the Frax report - (File: `formula/evaluation.js`, `data_feeds.js`)

### Summary
The Frax report describes a pattern where a pricing helper silently falls back to a hard-coded default ($1) instead of reverting when no oracle price is configured, causing the protocol to mis-value collateral. `ocore`'s oscript language provides the exact same footgun at the protocol level via the `ifnone` parameter of the `data_feed[[...]]` operator: if the referenced oracle has not posted a data feed value, the AA formula silently returns the author-supplied `ifnone` constant instead of aborting (unless `ifnone='abort'` is explicitly chosen). Any AA that uses `data_feed[[...]]` to price collateral, compute a conversion rate, or check collateralization and supplies a numeric `ifnone` fallback (e.g. `ifnone=1`) will use that fixed value whenever the oracle is silent, stale, or has not yet posted for the queried `min_mci`/`feed_value` — this is evaluated deterministically by every node during consensus, so it is not a bug that "might" happen off-chain, it is baked into unit/trigger validation itself.

### Finding Description
In `formula/evaluation.js`, the `data_feed` case reads the oracle value and, if `objResult.value` is `undefined` (no matching data feed found) and `ifnone` was supplied, simply returns the caller-supplied literal instead of failing: [1](#0-0) 

The same fallback is implemented in the non-AA data feed reader used by `data_feed` authentifiers: [2](#0-1) 

`ifnone` accepts any literal value (string, number, boolean) and is validated only for well-formedness, not economic sanity, in `formula/validation.js`: [3](#0-2) 

This is functionally identical to the Frax pattern: `collatDolarValue` falls back to treating `balance` as if the price were 1 unit when no oracle is set. In `ocore`, an AA author who writes something like `data_feed[[oracles='ORACLE', feed_name='PRICE', ifnone=1]]` to price collateral, compute a swap rate, or gate a payout will have that AA silently treat the asset as worth the hard-coded default whenever the oracle hasn't posted yet (e.g., right after AA deployment, during an oracle outage, or if an attacker constructs a `min_mci`/`feed_value` filter that never matches a real feed entry) — this is visible in the shipped sample contracts that use `data_feed[[...]]` for exchange-rate/collateral logic, e.g. the futures contract's `GBYTE_USD_MA` blackswan/exchange-rate check: [4](#0-3) 

Unlike that particular sample (which purposely omits `ifnone` so the formula aborts if the rate isn't posted — "data_feed will abort if the exchange rate not posted yet"), the language itself does not prevent or warn against combining pricing logic with `ifnone`, so any AA author can (intentionally or accidentally) introduce the exact Frax-style default-price bug, and it will be enforced identically and silently by every full node during trigger processing.

### Impact Explanation
Any AA whose economic logic (collateral valuation, swap rate, liquidation threshold, redemption amount) depends on `data_feed[[...ifnone=<constant>]]` will use the wrong price whenever the real oracle value is absent or not yet posted for the queried range. Because `ifnone` fallback is deterministic and consensus-critical, an attacker can trigger the AA at a moment when the real price has diverged from the hard-coded default, causing the AA to pay out, mint, or release assets based on a stale/incorrect valuation — this is a direct path to fund loss or drain from the AA (e.g., extracting overvalued collateral, minting under-collateralized stable-asset units, or forcing a below-market redemption), analogous to the underestimation/overestimation of collateral value described in the report's exploit scenario.

### Likelihood Explanation
Likelihood is dependent on AA design choices (whether the author picked `ifnone` with a fixed numeric default for a pricing computation), but the language provides no guardrail, and the pattern is a natural convenience for AA authors who want a formula to "not abort" when a feed is missing. Any unprivileged user can post a trigger unit at the moment the fallback condition holds (before an oracle first posts, or when a min_mci filter/feed_value filter deliberately fails to match), making exploitation trivially reachable by a single posted trigger, without needing privileged/oracle/operator access.

### Recommendation
- Short term: document explicitly (and warn AA authors) against using `ifnone` with a fixed numeric literal for any economically sensitive value, and consider requiring pricing-oriented AAs to always use `ifnone='abort'` for price feeds instead of a numeric default.
- Long term: consider adding an oscript lint/audit tool (or protocol-level constraint) that flags `data_feed[[...]]` calls whose result feeds into payment amounts/asset issuance and which specify a non-abort `ifnone`, so AA authors are forced to consciously handle "oracle absent" as an explicit case rather than silently defaulting.

### Proof of Concept
1. An AA author defines a definition using:
   `$price = data_feed[[oracles='ORACLE_ADDR', feed_name='USD_PRICE', ifnone=1]];`
   and uses `$price` to compute how much of an asset to release per byte received.
2. Deploy the AA before the oracle (`ORACLE_ADDR`) has ever posted `USD_PRICE`, or query with a `min_mci` that excludes the latest posted value.
3. Any user (no special privilege) sends a trigger unit with payment to the AA. The `data_feed[[...]]` evaluation in `formula/evaluation.js` (lines 646-663) finds no matching feed and returns the literal `1` from `ifnone`, which is used as the market price even though the real price may be materially different (e.g., $0.50 or $5).
4. The AA computes payouts/collateral checks using the wrong price of `1`, letting the trigger sender extract more value than they should (or the AA under/over-collateralizes an issued asset), all confirmed deterministically by every node since the evaluation is part of unit validation.
