### Title
Single-step, unconfirmed `address_definition_change` can irreversibly brick an address and any asset/attestor logic that depends on it - ([File: validation.js])

### Summary
Obyte allows any address to change its signing/authentication rule (its "definition") via an `address_definition_change` message. Unlike a two-step ownership-transfer pattern, the new `definition_chash` takes effect as soon as the unit is included and becomes stable — there is no "pending" state and no requirement that the new definition ever be revealed or be satisfiable. If a wrong or unsatisfiable `definition_chash` is posted (equivalent to passing a wrong `newAdmin`/`newOwner` address in the report), the address becomes permanently unable to authorize any future unit, exactly the "role lost forever" failure mode described in the report.

### Finding Description
`address_definition_change` messages are validated only for structural correctness, not for whether the new `definition_chash` corresponds to any known, satisfiable definition: [1](#0-0) 

The only checks are that `payload.definition_chash` is a syntactically valid address/chash string (`isValidAddress`) and that only one change per address is allowed per unit — there is no verification that a definition matching that hash exists, is well-formed, or is ever satisfiable by any key the poster controls.

Once the unit stabilizes, `writer.js` records the change unconditionally: [2](#0-1) 

From that point on, `storage.readDefinitionChashByAddress` always resolves the address's current authentication rule to the *last* recorded `definition_chash`, with no fallback to the original address-derived definition: [3](#0-2) 

Because `definition_chash` is a one-way hash, if the poster made a typo, referenced a non-existent/never-revealed definition, or accidentally created a definition that can never be satisfied (e.g., wrong pubkey, wrong address in a `sig`/`hash` template, or a nonsensical boolean composition), there is no way to reverse-engineer a definition array whose hash matches, and the address can never again produce a valid signature. This is a single, irrevocable state transition — the same class of bug as the "single-step ownership transfer" in the report, applied to the on-chain authentication/ownership primitive of ocore (the address definition, which functions as the "owner"/"admin" key of that address).

The blast radius is not limited to the poster's own wallet balance. `definer_address` of an asset (an address, subject to the same `address_definition_change` mechanism) is used to gate asset-level privileged operations such as attestor-list updates for `spender_attested` assets: [4](#0-3) 

and definer-only issuance for capped/definer-restricted assets: [5](#0-4) 

If the `definer_address` of such an asset is bricked by a bad `address_definition_change`, no unit can ever again satisfy `attestor list can be edited only by definer` or `only definer can issue this asset`, permanently freezing that governance/issuance capability for every current and future holder of the asset — not just the definer.

### Impact Explanation
- Direct impact: an unprivileged unit poster can permanently freeze their own address (and any funds subsequently sent to it) by supplying a bad `definition_chash` in a single, unconfirmed step.
- Indirect/broader impact: if the bricked address is an asset's `definer_address`, all future definer-gated operations (attestor list maintenance for `spender_attested` assets, definer-restricted issuance) become permanently impossible, freezing functionality that other, unrelated asset holders depend on — this satisfies the "AA/asset fund loss or freezing" bar, since legitimate participants lose access to functionality tied to that address with no recovery path.
- There is no two-step "propose new definition → confirm/reveal" pattern anywhere in the `address_definition_change` flow, so mitigation (catching the mistake before it's final) is not possible once the unit is stable.

### Likelihood Explanation
Low-to-medium: requires a poster (or asset definer) to make an error when constructing/broadcasting the `definition_chash` (e.g., wallet UI/tooling bug, manual composition error, copy-paste mistake, or mismatched local key material vs. the hash actually signed). The validation layer performs no sanity check that would catch such an error before it becomes irreversible, so the probability is entirely a function of client-side correctness, not of network-level defenses.

### Recommendation
Introduce a two-step confirmation for `address_definition_change`:
1. Treat the message as a "proposed" `definition_chash` that only becomes the effective definition once a unit signed under the *new* definition (i.e., revealing and using it successfully) is seen and stabilized, or
2. Require the `address_definition_change` message to include the full new definition (or a reveal within a bounded window) so validators can confirm at inclusion time that the new definition is well-formed and, ideally, satisfiable by the same author before the change takes effect, and
3. For definer-gated asset operations, consider allowing a fallback/recovery authority (e.g., a pre-declared backup definition or timelocked override) so an asset's governance is not permanently lost if `definer_address` is bricked.

### Proof of Concept
1. Attacker/poster (or asset issuer) constructs an `address_definition_change` message with `definition_chash` computed from a definition array they do not actually control the preimage of (e.g., a manual typo in a `sig`/`hash` template, or hashing the wrong pubkey).
2. Post a unit with this message from address `A` (or from the asset's `definer_address`).
   - Validation only checks `isValidAddress(payload.definition_chash)`, per `validation.js:1743-1744`.
3. Once the unit stabilizes, `writer.js` persists the new `definition_chash` for `A` unconditionally (`writer.js:186-192`).
4. Any subsequent unit from `A` will be resolved against this new `definition_chash` via `storage.readDefinitionChashByAddress` (`storage.js:754-768`). Since no definition hashing to this value can be produced, `A` can never sign a valid future unit — permanently freezing all funds and privileges tied to `A`.
5. If `A` is an asset's `definer_address`, then per `validation.js:2109-2113,2841-2842`, definer-only issuance and attestor-list updates for that asset become permanently impossible for anyone, freezing asset governance for all holders.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}
