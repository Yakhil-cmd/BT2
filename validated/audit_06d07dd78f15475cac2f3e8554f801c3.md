### Title
Webhook signature verified against `repository.owner.login`, but repository state is synced/mutated using an unrelated `repository.full_name` from the same unauthenticated payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository.owner.login` (falling back to `organization.login`), both taken from the raw, unauthenticated JSON body. All webhook handlers, however, resolve the actual `Repository`/`Stack` to act on using a completely different field from the very same payload: `repository.full_name` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together, so a signature that only proves "this payload was signed with organization A's webhook secret" is treated as authorization to mutate/sync any stack whose repository full name the attacker chooses to put in the body, even one that has nothing to do with organization A.

### Finding Description
`verify_signature` derives the signing organization purely from payload content and uses it to pick which secret to check the HMAC against: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the entire parsed body to the handler: [3](#0-2) 

Every handler resolves which repository/stacks to touch from a *different* field of the same payload, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` that was used for signature selection: [4](#0-3) 

For example, `PushHandler` finds stacks strictly by `repository_name` (i.e. `full_name`) and branch, and enqueues a real sync against them: [5](#0-4) 

This breaks the intended trust binding: `organization authenticated by HMAC == repository being written to`. Concretely, if an attacker administers (or has installed the GitHub App on, or otherwise knows the `webhook_secret` for) any organization "OrgA" configured in `config/secrets.yml`, they can craft a raw POST to `/webhooks` with:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` picks OrgA's secret and the HMAC computed over the exact raw body validates,
- `repository.full_name = "OrgB/target-repo"` for any other repository tracked by this Shipit instance, under a completely unrelated organization/token.

Because `repository_name` in `Handler` never re-derives or cross-validates against `repository.owner.login`, the handler will happily operate on `OrgB/target-repo`'s stacks despite the signature only proving control of OrgA's secret.

### Impact Explanation
Via `PushHandler`, this lets an unprivileged-but-OrgA-scoped attacker force `GithubSyncJob` (and subsequently `CacheDeploySpecJob`) to run against stacks that belong to a completely different organization/repository, with an attacker-chosen `expected_head_sha`. Under stacks configured with `continuous_deployment` or `merge_queue_enabled`, forcing an out-of-band sync can trigger the deploy/merge pipeline to react to what the attacker claims is the new head, effectively letting the attacker steer when an unauthorized deploy/rollback/merge cycle fires on a stack they have no legitimate authorization over. This directly maps to the "an organization that authenticated versus the repository that is written" binding called out in scope, and lands in the High/Critical impact bucket (unauthorized deploy/rollback/merge) depending on the target stack's configuration.

Other handlers (`status`, `check_suite`, `pull_request/*`) share the same `Handler#repository_name` resolution and are equally exposed to cross-repository targeting once any organization's signature passes.

### Likelihood Explanation
Exploitation requires only knowledge of one configured organization's `webhook_secret` (deliberately "optional" per `docs/setup.md`, and per the multi-org config in `config/secrets.development.shopify.yml`) plus the ability to POST directly to the public `/webhooks` endpoint — no Shipit session, `ApiClient` token, or GitHub App private key is needed, satisfying the rules' unprivileged-attacker requirement. Any tenant/organization admin who is legitimately allowed to install the Shipit GitHub App on their own org (and thus is aware of that org's webhook secret) automatically obtains the ability to target any other org's stacks tracked by the same Shipit instance.

### Recommendation
After signature verification, re-derive the organization from the same trusted `repository.owner.login` used to select the secret, and require that every handler cross-check `repository.full_name`'s owner segment against that already-authenticated organization before resolving stacks/repositories. Alternatively, resolve the `Repository`/`Stack` via a lookup scoped by the authenticated organization rather than by an independently attacker-controlled `full_name` string, so the field that authorizes and the field that is acted upon are provably the same.

### Proof of Concept
1. Attacker administers (or otherwise knows the webhook secret for) organization `OrgA`, configured in `config/secrets.yml` alongside victim organization `OrgB` (multi-org schema as documented in `config/secrets.development.shopify.yml`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and validates the HMAC — it passes, because the attacker legitimately knows OrgA's secret. [1](#0-0) 
5. `PushHandler#process`/`Handler#repository_name` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for `OrgB`'s stacks — a repository the attacker's authenticated secret has no relation to. [4](#0-3) [5](#0-4)
