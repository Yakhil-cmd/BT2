### Title
Api::CCMenuController bypasses the ApiClient-to-stack scope check, letting a stack-scoped token read any other stack's CI status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` restricts a stack-scoped `ApiClient` to only the `Stack` it is bound to by intersecting the requested `stack_id` with `Stack.where(id: current_api_client.stack_id)` before resolving it [1](#0-0) . `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, against the *entire* `Stack` table, completely bypassing that scoping [2](#0-1) . The permission check performed via `require_permission :read, :stack` only verifies the string `"read:stack"` is present in `current_api_client.permissions` [3](#0-2)  — it never checks that `stack_id` on the token matches the stack being requested. This breaks the equality "stack a token authorizes == stack it touches" described in the external report's bug class (stale/mismatched data used for an authorization decision).

### Finding Description
`ApiClient` can optionally be scoped to a single `Stack` via `belongs_to :stack, optional: true` [4](#0-3) . The engine's intended enforcement of this scope lives in `Api::BaseController#stacks`/`#stack`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::StacksController` relies on this correctly-scoped helper [5](#0-4) , and the base `Api::BaseController#index` route also demonstrates the intended pattern: any endpoint acting on a stack should be resolved through `stacks.from_param!`, not `Stack.from_param!`.

`Api::CCMenuController`, however, redefines `stack` to resolve unscoped:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 

`Stack.from_param!` just parses `"owner/name/environment"` and looks the record up with no client/tenant restriction [7](#0-6) . The action is reachable at `GET /api/stacks/*stack_id/ccmenu` [8](#0-7) , guarded only by `require_permission :read, :stack` [9](#0-8) , which only checks the `"read:stack"` string is in the token's `permissions` array, independent of which stack the token is bound to [3](#0-2) .

Before the attacker's request: an `ApiClient` token exists with `stack_id = A` and `permissions = ["read:stack"]`; the equality the system is supposed to enforce is `stack the token authorizes == A`.
After the request: the attacker sets `stack_id` in the URL to `B` (any other stack in the installation, e.g. a private/internal repository's stack); `Api::CCMenuController#stack` resolves `B` directly from the global `Stack` table, and `require_permission` never re-checks `A == B`. The response discloses `B`'s latest deploy/rollback status (`running?`, `ended_at`, success/failure) via the CCTray/CCMenu XML view [10](#0-9) .

This is the same class of bug as the report: an authorization decision (`read:stack` permission check) is evaluated against one piece of state (the permission string) while the actual object acted upon (`stack`) is resolved independently and can diverge from what the token was actually bound to — analogous to computing `cRatio` from a stale price while the actual collateral effect applies to the current price.

### Impact Explanation
This is an unauthenticated-from-the-target's-perspective, unauthorized read of another stack's state/CI status by a caller holding only a token deliberately scoped to a different, unrelated stack (e.g. a CCMenu token minted by `CCMenuUrlController` for one stack, `app/controllers/shipit/ccmenu_url_controller.rb`). It matches the High severity bucket "escalation into ... unauthenticated read of stack state, task streams or deploy output," since the intended per-stack authorization boundary enforced elsewhere in the API (`Api::BaseController#stacks`) is silently skipped for this endpoint.

### Likelihood Explanation
High likelihood: exploitation requires no privileged access beyond possessing *any* valid `ApiClient` token scoped to a single stack (these are routinely handed out by `CCMenuUrlController#client`, which is reachable by any authenticated Shipit user for any stack they can view, and are deliberately minimal, read-only, and embedded in plaintext CI-status URLs) [11](#0-10) . The attacker only needs to change the `stack_id` path segment of the request; no signature or secret needs to be forged, and the code path is a single overridden method, not a nested/rare condition.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped helper, e.g. `Stack.where(id: current_api_client.stack_id).from_param!(params[:stack_id])` when `current_api_client.stack_id?`, falling back to `Stack.all` otherwise — i.e. reuse `Api::BaseController#stacks`/`#stack` instead of overriding it with a call to the unscoped `Stack.from_param!`.

### Proof of Concept
1. As a legitimate Shipit user, visit stack A's settings page and let `CCMenuUrlController#fetch` mint a stack-scoped `ApiClient` (permissions `["read:stack"]`, `stack_id = A.id`) and return its `authentication_token` [12](#0-11) .
2. Using that token as Basic Auth, request `GET /api/stacks/<owner-B>/<repo-B>/<env-B>/ccmenu` for an unrelated stack B that the attacker is not authorized to view.
3. `authenticate_api_client` succeeds (token is valid) [13](#0-12) ; `require_permission :read, :stack` passes because `"read:stack"` is present regardless of `stack_id` [3](#0-2) ; `stack` resolves stack B directly via `Stack.from_param!` with no tenant filter [6](#0-5) .
4. The response returns stack B's CCTray XML, including its latest deploy/rollback status — data the token was never authorized to see.
