### Title
Stale votes from removed multisig owners are silently reactivated if the same address is re-added as owner - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`update_owner_schema()` removes an address from `MultisigAccount.owners` but never touches the `votes: SimpleMap<address, bool>` stored inside each pending `MultisigTransaction`. Vote-counting (`num_approvals_and_rejections_internal`) simply intersects the *current* `owners` vector with whatever is stored in `transaction.votes`. If a removed owner's address is later re-added to `owners` (via `add_owner(s)`, `swap_owner(s)`, or `update_owner_schema`), their old vote on any transaction that is still pending in the queue automatically counts again — without the owner casting any new vote — exactly mirroring the NFT floor oracle bug where `feederPrice` entries survived asset removal and were silently reused after re-addition.

### Finding Description
- Vote storage: each `MultisigTransaction.votes` is a `SimpleMap<address, bool>` that is only ever added to (`vote_transanction`, `add_transaction`) and is never pruned when an owner is removed: [1](#0-0) 

- Owner removal only mutates the `owners` vector; it does not touch `MultisigAccount.transactions` or any `votes` map at all: [2](#0-1) 

- Approval counting derives the effective vote set by iterating the *current* owners list and simply checking whether that address key exists in the transaction's (never-cleared) `votes` map: [3](#0-2) 

- `validate_multisig_transaction`, the function invoked by the VM prologue to gate execution, relies directly on this recomputed approval count: [4](#0-3) 

The existing test suite confirms the removal side of this (a removed owner's vote stops counting immediately): [5](#0-4) 

But there is no corresponding test or code path that clears/invalidates the vote when that same address is subsequently re-added. Because `votes` is keyed purely by `address`, not by any owner-generation/epoch counter, re-adding the address causes `num_approvals_and_rejections_internal` to count the **old** vote as if it were freshly cast under the current owner set.

### Impact Explanation
This breaks the intended admission invariant that "only owners are allowed to vote for a valid transaction" and that approvals reflect the *current* owner set's intent (this invariant is explicitly documented as Critical in the module's own audit checklist: "Only owners are allowed to vote for a valid transaction"). Concretely:
1. Owner A votes to approve a sensitive pending transaction.
2. Owner A is removed (e.g., due to key compromise, policy change, or because the owners want to exclude them from decision-making going forward) — their vote is correctly excluded while removed.
3. Owner A's address is later re-added as an owner (a routine, unprivileged-with-respect-to-past-votes governance action taken by the multisig account itself through the normal owner-management flow).
4. The old approval instantly and silently counts again toward quorum for any transaction that is still pending in the `transactions` table, without A casting any new vote or being aware their old stance is being reused.

This can let a `MultisigTransaction` reach `num_signatures_required` and pass `validate_multisig_transaction` (the VM-level admission gate for multisig execution) using an approval that does not reflect the current will of the current owner, i.e., a pre-validation mismatch that lets a transaction execute/commit under an approval set that should not be considered valid. The transaction executed could be anything (fund transfers, module upgrades, ownership changes) queued while the address was un-vetted or since removed — leading to unauthorized execution under the wrong effective approval set.

### Likelihood Explanation
Requires: (a) a pending, unexecuted multisig transaction, (b) an owner votes and is later removed, (c) that same address is later re-added as an owner while the transaction is still pending. This is a plausible operational sequence (e.g., temporarily removing an owner for KYC/compliance reasons, personnel rotation, or accidental removal/re-add) and does not require any privileged bypass beyond the normal owner-management entry functions (`add_owner`, `add_owners`, `swap_owner`, `swap_owners`), which are the standard multisig governance flow. No attacker needs elevated access beyond what a legitimate multisig owner quorum already has for owner management — the bug is that reinstating an address silently resurrects unrelated historical consent.

### Recommendation
Invalidate/clear stale votes tied to a removed address when that address is added back as an owner, or better, tag votes with an owner "epoch"/generation number that increments on every owner-set change, and only count votes whose recorded epoch matches the current epoch. Concretely, in `update_owner_schema`, when owners are removed, iterate all pending `transactions` and remove/mark stale any vote entries keyed by the removed addresses; alternatively bump a per-account `owner_generation` counter and store it with each `Vote`, requiring exact generation match at count time.

### Proof of Concept
1. Create a multisig account with owners `[O1, O2, O3]`, `num_signatures_required = 2`.
2. `O1` creates a transaction (auto-votes yes) → `create_transaction`.
3. `O2` approves it: `approve_transaction(O2, ms, seq)`. Transaction now has 2 approvals (O1, O2), meeting quorum, but suppose execution is deliberately delayed/not yet submitted.
4. The multisig account removes `O2` via `remove_owners(multisig_signer, [O2_addr])` (e.g., O2 is suspected compromised). At this point `can_be_executed`/`num_approvals_and_rejections` correctly drops to 1 approval (only O1), matching the existing test at [5](#0-4) .
5. Some time later, the account re-adds `O2` via `add_owners(multisig_signer, [O2_addr])` for unrelated reasons (O2 was cleared, or simply rotated back in).
6. Because `transaction.votes` was never cleared, `num_approvals_and_rejections` again reports 2 approvals for the still-pending transaction from step 2 — reactivating O2's stale, pre-removal vote — and `validate_multisig_transaction` will allow execution to proceed as if O2 had freshly re-approved the exact transaction under the current owner set, which O2 never did.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }
