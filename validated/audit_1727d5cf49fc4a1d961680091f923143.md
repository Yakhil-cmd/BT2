Based on the extensive research, I found a genuinely analogous pattern worth flagging: `private_payment.js`'s duplicate-detection logic for divisible private payments matches an incoming claimed output against *any* previously-stored output row instead of the specific one being referenced, similar in spirit to the kernel bug's core flaw — trusting an attacker-influenced identifier to select among multiple candidate elements rather than strictly binding to the exact expected one.

### Title
Divisible private-payment duplicate check matches wrong stored output, allowing bypass of chain re-validation - ([File: private_payment.js])

### Summary
`validateAndSavePrivatePaymentChain` in `private_payment.js` decides whether an incoming private-payment chain element is a "duplicate" (and thus skips full chain validation/saving) by querying stored `outputs` rows keyed only by `(unit, asset, message_index)` — with no `output_index` filter for divisible (non-fixed-denomination) assets — and then matching the claimed output's `amount`/`address`/`blinding` against *any* row returned by `.some()`.

### Finding Description
For divisible private assets, the SQL in `private_payment.js` (around lines 62-69) is:
```
"SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?"
```
without an `output_index` constraint, because divisible payments only have one payload per message but potentially multiple outputs. The duplicate check then does: [1](#0-0) 
This matches the claimed head element's outputs against *any* stored output row for that `(unit, message_index)`, not necessarily the exact output slot that corresponds to the private element being processed. If an attacker crafts a chain where a different, already-known output (e.g., a change output belonging to a different address that happens to share `amount`/`blinding` combination, or a row from a partially-processed prior duplicate) satisfies the `.some()` match, the function short-circuits with `ifOk()` — **skipping** the call to `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)` entirely, per [2](#0-1) . This mirrors the kernel bug class: an untrusted, attacker-supplied identifier (event pointer / here, claimed output attributes) is used to select among multiple candidate stored records instead of being strictly bound to one exact record, and the mismatch causes the code to skip processing that should otherwise have occurred.

### Impact Explanation
If this path is reachable with attacker-controlled collisions, it results in the full-chain re-validation (`validateSpendProofs`, `validation.validatePayment`, spend-proof matching, input authorization, denomination checks) being skipped for a private-payment chain that was never actually verified — the code simply calls `ifOk()` as if it had validated and saved. Because private divisible outputs can also be revealed later (address/blinding filled in after being hidden), this create a route to accept unverified private payment claims, which is core to correctly enforcing balances and spend uniqueness in the private-asset ledger.

### Likelihood Explanation
Exploitation requires the attacker to construct a private-payment chain element whose `amount`/`address`/`blinding` triple happens to collide with an existing stored output row for the same `(unit, asset, message_index)` — since `blinding` is a 16-character random-looking field normally supplied by the payer, an attacker composing their own chain (rather than colliding with someone else's random blinding) can trivially set matching values themselves. Reaching this code path only requires sending a `private_payment` message as any peer via `network.js`'s `handleOnlinePrivatePayment`, which is reachable by an unprivileged unit poster / private-payment counterparty.

### Recommendation
Constrain the duplicate-detection SQL and matching logic for divisible assets to the exact output being claimed (e.g., match by `output_index` if available, or otherwise verify the full set of `payload.outputs` against the full set of stored rows for that message rather than using `.some()` against an unconstrained set), ensuring the duplicate short-circuit is only taken when the *entire* claimed output set is verified to already be identically stored — never on a partial/any-match basis.

### Proof of Concept
1. As an attacker who is an authorized author of a private divisible-asset unit, or a peer relaying to a victim's light wallet, submit an initial legitimate private-payment chain element with a fabricated `blinding` value `B` and `amount` `A` to address `X`, causing it to be stored in `outputs`.
2. Submit a second, unrelated/invalid private-payment chain (different, invalid inputs/spend proofs) for the same `(unit, message_index)` but whose claimed `payload.outputs` includes an entry with the same `amount=A`, `address=X`, `blinding=B`.
3. `private_payment.js`'s duplicate check at [3](#0-2)  matches this crafted entry against the stored row and calls `transaction_callbacks.ifOk()`, bypassing `assetModule.validateAndSavePrivatePaymentChain` — the chain is treated as validated and saved without ever exercising `validateDivisiblePrivatePayment`.
