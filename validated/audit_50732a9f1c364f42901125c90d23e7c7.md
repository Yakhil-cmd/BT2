Confirmed: `Shipit.github(organization:)` supports a multi-organization schema where each organization key in `secrets.github` has its own `webhook_secret` [1](#0-0) . The webhook controller picks which organization's config (and therefore which `webhook_secret`) to verify the signature against using `repository_owner`, which is read directly from the untrusted, unverified JSON payload before any HMAC check has passed [2](#0-1) [3](#0-2) . Once `verify_signature` passes, the full raw `params` (including whatever `repository.full_name`, `sha`, etc. it contains) is handed unmodified to the event handlers, e.g. `PushHandler`, `StatusHandler`, `GithubSyncJob` [4](#0-3) .

This is precisely the analog class described: "an organization that authenticated versus the repository that is written." The signature check authenticates against the org named in `repository.owner.login`/`organization.login`, but the handlers act on `repository.full_name` from the same attacker-controlled JSON body — these two fields are never cross-checked against each other.

### Title
Webhook signature verification selects the signing organization from an unverified payload field, decoupling the authenticated org from the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives the organization used to look up the HMAC `webhook_secret` from `params.dig('repository','owner','login')` (or `organization.login`), fields taken straight from the unauthenticated request body [3](#0-2) . Only after selecting a secret for that claimed organization is the signature checked [5](#0-4) . In Shipit's multi-org GitHub App configuration, each organization key in `secrets.github` carries its own independent `webhook_secret` [6](#0-5) [7](#0-6) .

### Finding Description
The equality that should hold is: `organization whose secret authenticated the request == organization that owns the repository being mutated by the handler`. In this engine, that binding is broken because the "authenticated organization" is picked from `repository.owner.login`, while every downstream handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) reads its own repository/target fields (e.g. `repository.full_name`, `sha`, `branches`) from the very same untrusted payload without re-deriving or re-checking them against the value that was used for signature selection [4](#0-3) . Because `verify_webhook_signature` only proves that *some* configured organization's secret matches the raw body, an attacker who legitimately knows (or controls) the webhook secret of Organization A can craft a payload whose `repository.owner.login`/`organization.login` is Organization A (so it authenticates) while embedding a `repository.full_name` (or other repository-identifying fields) that maps to a stack belonging to Organization B or a differently-named repository under A. Nothing in `verify_signature` or in `Hook#deliver`/handler dispatch enforces that the two must match. This mirrors the audited bug class exactly: a validation check (`lockTime`) was performed on the wrong operation (`deposit`) instead of the operation it was meant to protect (`withdraw`); here, the signature/org check is performed against a payload field (`repository.owner.login`) different from the field the handlers actually act upon (`repository.full_name`), and no code ties the two together.

### Impact Explanation
If exploited, an attacker holding a valid webhook secret for one configured GitHub organization could inject forged webhook events (`push`, `status`, `check_suite`, `pull_request`) that are accepted as authentic for a stack under a different organization/repository than the one whose secret validated the signature. Depending on the handler reached, this enables cross-repository state manipulation — e.g. forging CI `status` updates that mark commits under another org's stack as `success`, triggering continuous-deployment (`ContinuousDeliveryJob`) to actually run a deploy/merge for a repository the attacker does not control. This crosses the "cross-repository writes" / "unauthorized deploy" bar in the given impact taxonomy.

### Likelihood Explanation
This requires the deployment to be configured with the multi-organization `secrets.github` schema (multiple orgs, each with its own `webhook_secret`) — a supported, documented configuration path (`github_app_config`) rather than a hypothetical one [6](#0-5) . Any party who legitimately possesses one organization's webhook secret (e.g., a compromised or malicious tenant in a shared Shipit instance) can mount this without any additional privilege, satisfying the "unprivileged attacker" requirement.

### Recommendation
- Short term: After signature verification succeeds for organization `O`, explicitly verify that every repository-identifying field in the payload used by the dispatched handler (`repository.full_name`, `repository.owner.login`) is consistent with `O`, rejecting (422) any mismatch, instead of trusting the payload's self-reported `repository.full_name` in handlers.
- Long term: Tie signature verification directly to a specific `Stack`/`Repository` record (looked up by `full_name` after verification) rather than allowing the payload to select which secret is used to validate itself.

### Proof of Concept
1. Configure Shipit with multi-org support: `secrets.github` containing `org_a: { webhook_secret: SECRET_A, ... }` and `org_b: { ... }`.
2. As an attacker who knows `SECRET_A` (e.g., a legitimate GitHub App installer for `org_a`), craft a `push` (or `status`) webhook payload with `repository.owner.login = "org_a"` (so `Shipit.github(organization: "org_a")` is selected) but `repository.full_name = "org_b/some-stack"`.
3. Sign the raw body with `SECRET_A` and set `X-Hub-Signature` accordingly; `verify_signature` succeeds because it only checks the body against `org_a`'s secret [5](#0-4) .
4. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` processes the event using `repository.full_name = "org_b/some-stack"`, causing `GithubSyncJob`/`PushHandler` to operate on `org_b`'s stack despite the request only being authenticated for `org_a`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
