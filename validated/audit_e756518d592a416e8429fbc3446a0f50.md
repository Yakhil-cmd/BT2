### Title
Type-confusion in `RuleEngine._extract_field`/`_check_condition` lets non-string `tool_input` fields silently bypass block rules (fail-open) - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._extract_field` only coerces a field to `str()` when the condition's `field` name is a literal key already present in `tool_input` (e.g. `command`). For aliased fields used by Edit/Write/MultiEdit (`new_text`→`new_string`, `old_text`→`old_string`, `content`), the raw value from `tool_input.get(...)` is returned without any type coercion. If that value is not a `str` (e.g. a list), the `contains`/`equals`/`not_contains` operators in `_check_condition` silently evaluate incorrectly (no exception, wrong logical result) and `starts_with`/`ends_with` raise `AttributeError`, which is caught by the generic `except Exception` in `pretooluse.py` and converted into a non-blocking "Hookify error" message — i.e., the tool call is allowed.

### Finding Description
Call path: `pretooluse.py:main()` → `RuleEngine.evaluate_rules` [1](#0-0)  → `_rule_matches` [2](#0-1)  → `_check_condition` → `_extract_field`.

In `_extract_field`, only fields whose name matches the literal `tool_input` key are string-coerced: [3](#0-2) 

But for Edit/Write's aliased fields (`new_text`/`old_text`/`content`) and MultiEdit's concatenation, the code returns raw dictionary values with no `isinstance`/`str()` guard: [4](#0-3) 

In `_check_condition`, the extracted `field_value` is used directly with Python string operators: [5](#0-4) 

If `tool_input["new_string"]` (or `edits[].new_string`) is, e.g., a `list` of strings instead of a single `str`:
- `pattern in field_value` (`contains`) checks list-membership of the *exact* pattern string against list elements instead of substring search across the joined text — a dangerous substring split across list items, or embedded inside a longer string, will not match, so the rule silently fails to fire with **no exception at all** (bypasses even the outer `try/except` in `pretooluse.py`).
- `field_value.startswith(pattern)` / `.endswith(pattern)` raise `AttributeError` since lists have no such method.

Any exception that does occur is swallowed by the blanket exception handler in `pretooluse.py`, which always allows the operation and exits `0`: [6](#0-5) 

This is a fail-open pattern: a parser/type differential in a single condition field silently disables the entire block rule rather than blocking or raising loudly, violating the stated invariant.

### Impact Explanation
A configured `block` rule intended to stop a dangerous `Bash`/`Edit`/`Write`/`MultiEdit` tool call can fail to trigger when the relevant `tool_input` field is a non-string type (list/dict/number) instead of the expected string. This defeats hookify's core security-gating purpose (PreToolUse block enforcement), letting the dangerous tool call proceed as if no rule matched, and matches "hook/permission enforcement bypass" impact.

### Likelihood Explanation
Preconditions: the attacker must be able to influence how `tool_input` is structured for the tool call being reviewed (e.g., via prompt injection in reviewed content/repo/issue text that induces the model, or an MCP/custom tool with a loosely-typed schema, to place structured (non-string) content into `new_string`/`old_string`/`content`/`edits[].new_string`). Whether Claude's own tool-call schema strictly enforces `string` typing for built-in Edit/Write tools limits but does not eliminate this path, since third-party/MCP tools and model-generated malformed tool calls are plausible vectors. The bug itself is deterministic and repeatable once such a tool_input is produced — no timing or race conditions involved.

### Recommendation
In `_extract_field`, always coerce non-`None` values to `str` (mirroring lines 198-200) before returning, for every branch (Bash/Edit/Write/MultiEdit special cases), including list-concatenation in MultiEdit. Additionally, in `_check_condition`, validate `isinstance(field_value, str)` and, on failure, either raise/log loudly and fail closed (treat as a match for block rules) rather than defaulting to `False`, and remove the blanket `except Exception` fail-open behavior in `pretooluse.py` for rule-evaluation errors so that unexpected exceptions in the rule engine do not translate into unconditional allow.

### Proof of Concept
Unit test in `plugins/hookify/core/rule_engine.py` test suite:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-rm-rf",
    enabled=True,
    event="file",
    tool_matcher="Edit",
    conditions=[Condition(field="new_text", operator="contains", pattern="rm -rf")],
    action="block",
    message="Dangerous content!"
)

engine = RuleEngine()

# Attacker-influenced tool_input: new_string split across a list instead of a single string
malicious_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {
        "file_path": "script.py",
        "old_string": "pass",
        "new_string": ["os.system('", "rm -rf /", "')"]
    }
}

result = engine.evaluate_rules([rule], malicious_input)
# Expected (secure): result should still contain
#   {"hookSpecificOutput": {..., "permissionDecision": "deny"}, "systemMessage": ...}
# Actual (vulnerable): result == {} -- rule silently fails to match despite
# "rm -rf" being present in the reviewed content, allowing the edit through.
assert result != {}, "Block rule was silently bypassed due to non-string field_value"
```
Also assert, for the `starts_with`/`ends_with` operator variant, that `evaluate_rules` does not raise an uncaught exception that `pretooluse.py`'s outer handler converts into a silent allow (`{"systemMessage": "Hookify error: ..."}` with no `permissionDecision: deny`).

```python
    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
```
