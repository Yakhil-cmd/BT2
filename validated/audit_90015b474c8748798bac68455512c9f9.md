### Title
Webhook signature verification keys off an unverified `repository.owner.login` field decoupled from the `repository.full_name` that handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using `repository_owner`, a value read straight out of the **unverified** JSON body. The field that the downstream handlers actually trust to select the target `Stack`/`Repository` — `repository.full_name` — is a *different* field that is never cross-checked against the organization used for signature verification. In a multi-org Shipit deployment, an attacker can pick any configured organization whose `webhook_secret` is blank (which makes verification a no-op) to "authenticate" the request, while setting `repository.full_name` to point at a completely different, properly-secured org's repository/stack.

### Finding Description
The webhook signature check is:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up the app config by the organization name taken from the payload, case-insensitively, from the `secrets.github` hash of multiple configured GitHub organizations (as documented for multi-org setups): [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an org with **no `webhook_secret` configured** as fully trusted, skipping HMAC verification entirely:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

This dual-org configuration schema and the possibility of an org missing `webhook_secret` are directly documented/exercised in the codebase (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`, `test/unit/shipit_test.rb`): [4](#0-3) [5](#0-4) 

Crucially, once the request passes `verify_signature` (successfully or because the chosen org's secret is nil), the actual webhook handler resolves the target `Stack`/`Repository` using an entirely different field — `repository.full_name` — with no link back to the organization used above:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [7](#0-6) 

The binding that is broken: `organization authenticated by verify_signature == organization of repository.full_name acted on by the handler`. The webhook body is a single unauthenticated JSON blob controlled entirely by the requester (there is no per-field signing; the whole raw body is what would need to be HMAC-signed by the real GitHub, and it isn't when the chosen org has no secret). This lets an attacker set `repository.owner.login` to an org with `webhook_secret: nil` (satisfying `verify_signature`) while setting `repository.full_name` to `victim-org/victim-repo` (a different, secured org). Because the two org fields are never reconciled, and the second one is what selects the `Stack`, the attacker can forge events for stacks belonging to a securely-configured organization by hiding behind an unsecured sibling organization in the same Shipit instance.

### Impact Explanation
This breaks the trust boundary between "the organization whose webhook we can validate" and "the repository the payload is allowed to affect." A forged `push` event drives `PushHandler` to call `stack.sync_github(expected_head_sha:)` against the victim stack's branch: [8](#0-7) 
and a forged `status`/`check_suite` event can inject fabricated commit statuses/check runs for arbitrary shas on the victim repository, which are consumed by CI-gating logic that ultimately decides whether a deploy or a merge-queue merge is allowed to proceed (`Commit#deployable?`, `MergeRequest#all_status_checks_passed?`/`merge!`). By forging green CI statuses for a malicious commit on a victim stack (using the unsecured org purely as an entry point to bypass signature checking), an unprivileged external attacker can cause an unauthorized deploy or an unauthorized PR merge on a repository/organization they were never meant to have any control over — satisfying the "unauthorized deploy, rollback or merge" Critical impact bar, without needing any Shipit session, ApiClient token, or GitHub credentials.

### Likelihood Explanation
Likelihood depends on the deployment having at least two GitHub organizations configured (a documented, supported configuration) where at least one organization does not have a `webhook_secret` set — either because it was never configured, or because an operator assumed a "low-value" org's webhooks didn't need a secret. No authentication, GitHub App private key, or Shipit credentials are required to exploit this: the attacker only needs to know the name of any org key configured in `secrets.github` and craft one HTTP POST to the public `/webhooks` endpoint (`config/routes.rb` mounts `WebhooksController` unauthenticated aside from `verify_signature`). This is a realistic, config-dependent but code-rooted flaw rather than a theoretical one, since the multi-org schema and the "no secret ⇒ skip verification" behavior are both first-class, intentional, documented features.

### Recommendation
- Require `Shipit.github(organization:)`/`verify_webhook_signature` to hard-fail (422) instead of returning `true` when no `webhook_secret` is configured for a multi-org setup, or require `webhook_secret` presence validation at boot for every configured organization.
- After signature verification, cross-check that the organization used to select the verifying app config (`repository.owner.login`/`organization.login`) matches the owner segment of `repository.full_name` before dispatching to any handler; reject the webhook if they diverge.
- Consider deriving the "authenticated organization" strictly from the resolved `Repository`/`Stack`'s configured organization rather than from attacker-controlled JSON fields.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (has a real `webhook_secret`) and `OrgTwo` (`webhook_secret: nil`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-already-existing-as-a-commit>",
  "repository": {
    "full_name": "OrgOne/victim-repo",
    "owner": { "login": "OrgTwo" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally — no `X-Hub-Signature` needed at all.
4. `PushHandler` then resolves `stacks` via `repository.full_name` = `"OrgOne/victim-repo"`, i.e. the *actually secured* org's stack, and triggers `stack.sync_github(expected_head_sha: ...)` for it — a forged event fully accepted for a repository the attacker has no legitimate relationship to.

*(Note: I could not execute this end-to-end against a live instance in this analysis; the reasoning is derived directly from the cited source, and confidence rests on `verify_webhook_signature`'s `return true unless webhook_secret` short-circuit combined with `Handler#stacks` never re-checking the organization used for verification.)*

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
