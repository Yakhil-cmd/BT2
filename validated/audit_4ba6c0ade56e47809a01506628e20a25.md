## Title
Reward/accumulator state variables silently lose precision and stop growing due to the 15-significant-digit `Decimal` precision used for all AA arithmetic - (File: `formula/common.js`, `formula/evaluation.js`)

### Summary
Every arithmetic operation performed inside an Autonomous Agent (AA) — including compound state-variable assignments such as `var['x'] += ...` — is evaluated with `decimal.js` configured to only **15 significant digits** of precision. Any AA that implements a Symm-Staking-style "reward accumulator" pattern (a cumulative per-share value that is incremented by `rate * elapsed_time / total_stake` or similar on every trigger) can have its increments silently rounded away to nothing once the accumulator has grown large enough, exactly like the `perTokenStored` rounding-to-zero bug described in the external report. An unprivileged trigger sender can grief this by repeatedly sending cheap triggers that both advance the "denominator"/accumulator and consume time/opportunities for legitimate updates, causing reward funds to become permanently unaccounted for (and effectively stuck) in the AA's balance.

### Finding Description
All numeric evaluation for AAs goes through `decimal.js`, globally configured with only double-like precision: [1](#0-0) 

This precision setting applies to **every** decimal operation, including the compound state-variable assignment operators (`+=`, `-=`, `*=`, `/=`, `%=`) that AAs commonly use to maintain accumulators in persistent storage: [2](#0-1) 

The only "loss" check performed after every operation is `toDoubleRange`, which merely detects a *complete* underflow to exactly `0` — it does nothing to detect or prevent partial precision loss when adding a small delta to an already-large accumulated value: [3](#0-2) 

This is the direct oscript analog of the reported Solidity bug: instead of `perTokenStored += rewardRate * dt * 1e18 / totalSupply` truncating to `0` in integer (fixed-point) math because the numerator is too small relative to `totalSupply`, in oscript the same class of accumulator (`var['reward_per_token'] += ...`) silently truncates because `decimal.js` only retains 15 significant digits per operation. Once the state var has accumulated enough magnitude, any subsequent increment smaller than roughly `10^-15` of its current magnitude is rounded away with **no error, no bounce, and no revert** — the transaction succeeds, `updated=true` is still set, but the numeric delta is lost.

Numerous existing sample AAs demonstrate exactly this accumulator/share pattern that is reachable by any external trigger sender:
- `var['mm_asset_outstanding'] += $issue_amount;` in the Uniswap-like AMM sample [4](#0-3) 
- `var['team_' || trigger.data.team || '_amount'] += trigger.output[[asset=base]];` in the attack-game sample [5](#0-4) 

Any real-world AA (e.g. a staking/reward AA analogous to SymmStaking) written with this same pattern — maintaining a growing cumulative reward-per-share state var that is updated on every deposit/withdraw/claim-style trigger — inherits this precision-loss weakness natively from the oscript engine, with no protection offered by the platform.

### Impact Explanation
An attacker (any address able to send a trigger unit, i.e. an unprivileged AA trigger sender) can send frequent low-value triggers to an AA that maintains such a cumulative accumulator. Once the accumulator's magnitude is large enough relative to the per-trigger increment, further legitimate increments are silently dropped by the engine's 15-significant-digit precision, while "last update" bookkeeping (timestamps, counters) still advances. This causes:
- Under-distribution or complete loss of reward accounting for legitimate stakers/participants of the AA, exactly mirroring the "High" impact rated in the original report (funds effectively frozen/unclaimable inside the AA, recoverable only by whoever controls/administers the AA, if at all).
- No revert/log signals the failure — the loss is completely silent, making it hard for AA authors or users to detect.

This is a fund-freezing / accounting-corruption class issue reachable purely through normal AA trigger sending, satisfying the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
High. No special privileges are required — any address can send trigger units to an AA. AAs implementing reward-per-share/cumulative-accumulator patterns are a common and idiomatic pattern in oscript (as evidenced by the shipped sample contracts using the identical `var[...] += ...` idiom), so this is not a hypothetical, contrived pattern but the standard way such logic is written in this ecosystem. The precision limitation is a platform-wide, unconditional characteristic of `formula/common.js`'s `Decimal.set({ precision: 15, ... })`, applying identically to all AAs regardless of author intent, so exploitation only requires timing/volume of cheap triggers, not any bug in a specific AA's logic beyond using the natural accumulator idiom.

### Recommendation
- Document/mitigate the 15-significant-digit precision limitation for compound state-variable assignments used as accumulators, or increase the working precision used internally for `+=`/`-=` on state vars (e.g. track an internal higher-precision remainder, or warn/bounce when an increment would be fully absorbed by rounding rather than silently dropping it).
- Consider adding a diagnostic/detection path so that when `value.plus(res)` (or other compound ops) returns a result numerically indistinguishable from `value` (i.e., `res` was effectively lost to precision) while `res` was non-zero, this is at least logged/flagged, since it currently fails completely silently, unlike Solidity's SymmStaking where the same defect was at least analyzable via unit tests.

### Proof of Concept
1. Deploy an AA analogous to a staking/reward contract, maintaining `var['reward_per_share']` incremented on every trigger by `$reward_rate_evaluated_delta`, similar to the accumulator idioms already present in the codebase's own sample AAs, e.g.:
   `var['team_' || trigger.data.team || '_amount'] += trigger.output[[asset=base]];` [6](#0-5) 
2. Grow `var['reward_per_share']` (or an analogous large accumulator such as `mm_asset_outstanding`) to a large magnitude through normal usage.
3. Have an attacker repeatedly send triggers each of which is supposed to add a small delta (`rate*dt/total_stake`)-sized increment to the accumulator; because `decimal.js` is configured at `precision: 15` [7](#0-6) , once the accumulator exceeds ~15 significant digits relative to the increment, `value.plus(res)` in the `+=` handling returns `value` unchanged [8](#0-7) , silently discarding the increment while the bounce/response still succeeds.
4. Over time, legitimate reward claims computed from the frozen `var['reward_per_share']` under-pay stakers, while the AA's underlying asset/byte balance retains the undistributed funds, becoming effectively stuck.
