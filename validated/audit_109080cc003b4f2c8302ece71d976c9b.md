### Title
Cross-tenant `Status` creation via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits globally by `sha` with no repository or stack scoping, and never reads `params.branches` or `repository.full_name` at all. Any signed `status` webhook for sha `S` mutates every `Shipit::Commit` row across the entire installation whose `sha` equals `S`, regardless of which repository the webhook actually came from.

### Finding Description
The binding the payload appears to assert is: `params.repository.full_name == <owning repo of the target commit>` (reinforced by the presence of the `branches` schema field, which looks like it exists to validate the target branch/repo). In fact neither field is consulted: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this queries the `commits` table across *all* stacks/repositories, with no `stacks`/`repository_name` filter, and `params.branches` is declared in the schema but never read.

Compare with the base `Handler` class, which does provide a `stacks`/`repository_name` scoping helper: [2](#0-1)  — `StatusHandler` simply never uses it, unlike other handlers (e.g. push) that filter by repository first.

Signature verification does not close this gap: `WebhooksController#verify_signature` derives the GitHub App/secret from `repository_owner` (`params.dig('repository','owner','login')`) and validates the HMAC against that organization's own `webhook_secret`: [3](#0-2) , [4](#0-3) . This only proves the request was signed by *some* organization onboarded to Shipit — it says nothing about which `Commit`/`Stack` the payload is allowed to mutate. An attacker who legitimately owns (or administers) any repository/stack tracked by the same multi-tenant Shipit instance can produce a validly-signed `status` webhook for their own repo, naming a `sha` that also exists in a victim's stack (e.g., via shared git history from a fork, a cherry-picked/rebased commit, or a coincidental duplicate `Commit` import). `Commit.sha` has no global uniqueness constraint tying it to a specific stack in `app/models/shipit/commit.rb`, so the same sha value can legitimately exist as separate `Commit` rows under multiple stacks.

Attacker's exact request: a `status` webhook, signed with the attacker's own (legitimately configured) org secret, body:
```json
{
  "sha": "<sha shared with victim's tracked commit>",
  "state": "success",
  "context": "ci/attacker",
  "branches": [{"name": "master"}],
  "repository": {"full_name": "attacker/own-repo", "owner": {"login": "attacker-org"}}
}
```
This passes `verify_signature` (real secret for `attacker-org`), passes the `ExplicitParameters` schema (branches present, well-formed), then `StatusHandler#process` finds and mutates *every* `Commit` row with that sha — including the victim's — creating a `Status`, which can flip CI/deployability state (`enable_ci_on_stack`, `schedule_continuous_delivery`, `Hook.emit(:deployable_status, ...)`) on the victim's stack: [5](#0-4) , [6](#0-5) , [7](#0-6) .

### Impact Explanation
A cross-tenant write: a payload signed for repository A creates/mutates a `Shipit::Status` (and can trigger `deployable_status`/continuous-delivery scheduling) attached to a `Commit`/`Stack` belonging to repository B, with no dependency on B's identity being present or correct in the payload. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." It can influence whether a victim's commit is treated as deployable/blocked, and can spuriously enable CI on a victim stack.

### Likelihood Explanation
Requires (a) a multi-tenant Shipit instance tracking both attacker's and victim's repositories, (b) attacker holding legitimate webhook credentials for their own onboarded repo (a normal precondition for any onboarded tenant, not a privileged Shipit role), and (c) a `sha` collision between attacker's and victim's tracked commits — realistic when repos are forks/mirrors sharing history, or when the same upstream commit is imported into two stacks. This is not exploitable against an arbitrary internet victim with zero shared context, but is fully repeatable/scriptable against any victim stack sharing commit history with an onboarded attacker repo, with no rate limiting concerns in scope.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the requesting repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the existing `Handler#stacks`/`repository_name` helpers instead of an unscoped `Commit.where(sha:)`. Either use `params.branches` to further restrict to tracked branches or remove the field if it will never be enforced, to avoid misleading readers of the schema.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create `stack_a` (owns `repo_a`) and `stack_b` (owns `repo_b`), each with a `Commit` sharing the identical `sha` value (`commit_a` under `stack_a`, `commit_b` under `stack_b`).
2. Build a payload: `{ sha: commit_a.sha, state: 'success', context: 'ci', repository: { full_name: 'owner/repo_a' } }`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert `commit_b.statuses.reload.count == 1` (cross-tenant mutation occurred) even though `payload['repository']['full_name']` never named `repo_b`.
5. Repeat with `branches: [{ name: 'master' }]` added and matching/mismatching `victim`'s tracked branch — assert identical outcome (status still created on `commit_b`), proving `branches` is inert and provides no scoping whatsoever.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
