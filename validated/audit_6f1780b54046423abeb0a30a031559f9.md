### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` resolution method used by every other API controller, replacing the scoped lookup (`stacks.from_param!`) with an unscoped one (`Stack.from_param!`). This breaks the binding: *stack a token authorises == stack it touches*.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting resolution: [1](#0-0) 

`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set, and `stack` is derived from that restricted relation. This is the mechanism that turns the `stack_id` column on `ApiClient` (`belongs_to :stack, optional: true`, [2](#0-1) ) into an actual authorization boundary: a client scoped to stack A cannot resolve stack B through `params[:stack_id]`.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [3](#0-2) 

It also overrides `authenticate_api_client` to accept the token from a URL query parameter (`params[:token]`) rather than the `Authorization` header, so it can be hit directly with a bookmarked/shared URL: [4](#0-3) 

`ApiClient#check_permissions!` only checks that the permission string (`read:stack`) is present in the client's `permissions` array — it never checks whether the requested stack matches the client's `stack_id`: [5](#0-4) 

The stack-id restriction is enforced solely by the `stack`/`stacks` helper methods in `BaseController`, and `CCMenuController` opts out of that helper. Consequently, any valid `ApiClient` token with `read:stack` permission — no matter which single stack it was scoped to when created (e.g. via `CCMenuUrlController#client`, [6](#0-5)  — can be replayed against `CCMenuController#show` with an arbitrary `stack_id` in the URL to read the CI/deploy status (`show` renders latest deploy state, lock status, etc.) of any stack in the Shipit instance.

### Impact Explanation
This is an authorization-scope escalation: a token that is only supposed to authorize read access to one stack ends up touching (reading state of) every stack. It falls in the High-impact bucket ("escalation into authorization" / unauthorized read of stack state) required by the analog rules, since it discloses deploy/lock status of stacks the token holder was never granted access to.

### Likelihood Explanation
High likelihood: this requires only possession of any single valid scoped `ApiClient` token with `read:stack` permission (e.g., a personal CCMenu URL a user generated for their own stack) and knowledge/guessing of another stack's `to_param` (owner/repo/environment), which is not secret information. No additional privilege or interaction with GitHub is needed.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the scoped `stacks.from_param!` helper from `BaseController`) so that stack-scoped `ApiClient` tokens cannot resolve stacks outside their `stack_id` scope:

```diff
 def stack
-  @stack ||= Stack.from_param!(params[:stack_id])
+  @stack ||= stacks.from_param!(params[:stack_id])
 end
```

### Proof of Concept
1. As user U, visit `CCMenuUrlController#fetch` for stack A to obtain a token: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: U, name: 'CCMenu Client')` (unscoped or scoped to stack A depending on deployment).
2. Assume/obtain an `ApiClient` scoped to stack A only (`stack_id` set to A's id, `permissions: ['read:stack']`).
3. Request `GET /api/:owner/:repo/:env/cc.xml?token=<A's token>` but substitute stack B's `owner/repo/env` in the path (`params[:stack_id]`).
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (unscoped), successfully resolving stack B, and `check_permissions!` only checks the `read:stack` string, so the request succeeds and returns stack B's deploy/lock status even though the token is scoped to stack A.
