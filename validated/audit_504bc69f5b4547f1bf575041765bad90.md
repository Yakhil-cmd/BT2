### Title
Api::CCMenuController leaks any stack's deploy status to an ApiClient scoped to a different stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` restricts stack access for stack-scoped `ApiClient` tokens by resolving `stack_id` only against the client's own scope: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the token is stack-scoped, and `stack` calls `stacks.from_param!(params[:stack_id])`. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing that scoping. Because permission enforcement only checks the generic `"read:stack"` string on the client and never compares it against the requested stack, a token authorized to read **one specific stack** can be used to read **any stack** in the installation.

### Finding Description
`Api::BaseController#stacks` and `#stack` implement the scoping guarantee for stack-bound API clients: [1](#0-0) 

This is the mechanism that makes a client such as fixture `here_come_the_walrus` (created with `stack: shipit`) only able to see its own stack, as validated by the test "an api client scoped to a stack will only see that one stack" in `Api::StacksController`.

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and loads the stack unconditionally from the global `Stack` relation: [2](#0-1) 

Authorization is enforced only via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 

This method checks only whether the string `"read:stack"` is present in the client's `permissions` array — it never inspects `current_api_client.stack_id` nor compares it to the `stack_id` param being requested. The binding that should hold is:

`stack_id authorised for the token (current_api_client.stack_id)` == `stack_id actually touched (params[:stack_id] resolved via CCMenuController#stack)`

Before the request: the token is only supposed to represent authorization for one stack (or all stacks, if `stack_id` is nil). After the request: because `CCMenuController#stack` resolves against the unrestricted `Stack` relation, the equality is broken — any `stack_id` value supplied in the URL is honored regardless of the client's `stack_id` binding.

`Api::CCMenuUrlController`'s sibling, `CCMenuUrlController#client` (a different, session-authenticated, non-API controller) similarly resolves `Stack.from_param!` directly, but that controller is guarded by the standard `Shipit::Authentication` session flow and generates a fresh `ApiClient` for the currently authenticated `current_user`'s own requested stack — it is not the vulnerable code path. The vulnerable code path is specifically `Api::CCMenuController`, which is reached with only a bearer-style API token via HTTP Basic auth, not a Shipit session.

### Impact Explanation
This qualifies as **High** impact: "unauthenticated read of stack state, task streams or deploy output" relative to the token's actual authorization. An `ApiClient` explicitly scoped to read only Stack A (e.g., a CCMenu widget token issued to an external CI dashboard for one project) can be reused to query `GET /api/stacks/:stack_id/ccmenu.xml` for any other stack ID in the same Shipit installation, disclosing:
- the name of the other stack (`name` — implicitly repo/environment identifying info)
- its latest build status (`lastBuildStatus`)
- its last build label/commit info (`lastBuildLabel`)
- its last build/deploy timestamp (`lastBuildTime`)
- the web URL to the deploy in Shipit's UI (`webUrl`)

as rendered in `app/views/shipit/ccmenu/project.xml.builder`. This is exactly the class of "scope a token authorizes vs. scope it actually touches" boundary violation called out in the rules, and it discloses deploy/task state across stack boundaries without the requesting party having been granted access to that stack.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack`-permission `ApiClient` token (Basic auth credentials or the CCMenu `token` query param), regardless of which stack it was originally scoped to, plus knowledge or guessing of another stack's numeric ID or slug (`repo_owner-repo_name-environment`), which are often predictable/enumerable (e.g., sequential IDs, or guessable slugs based on repo/environment names visible elsewhere in the UI or via the public `/api/stacks` index endpoint if the requester has an unscoped token, or simply visible stack pages if any is public). No collusion by a privileged administrator, no signature forgery, and no session are needed — a legitimately-issued, narrowly-scoped API token is sufficient. This is not out of scope under the "requires an ApiClient token" exclusion, because the point of the finding is precisely that a *legitimately issued, narrowly-scoped* token grants broader access than intended — an authorization/scoping bypass, not merely "having a token."

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation inherited from `Api::BaseController`, instead of querying `Stack` unscoped:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Remove the private override entirely so the controller falls back to `BaseController#stack`, which already respects `current_api_client.stack_id`.

### Proof of Concept
1. Create two stacks, Stack A and Stack B.
2. Issue (or use the CCMenu widget flow to auto-issue) an `ApiClient` scoped to Stack A only (`stack_id` set to Stack A's ID, permission `read:stack`), e.g. equivalent to fixture `here_come_the_walrus`.
3. As an unrelated party with only this Stack-A-scoped token, request:
   `GET /api/stacks/<stack-B-id-or-slug>/ccmenu.xml?token=<stack-A-scoped-token>` (or via HTTP Basic auth with the token).
4. Observe the response returns HTTP 200 with Stack B's `name`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — despite the token never having been granted permission to Stack B.
5. Contrast with `GET /api/stacks?stack_id=<stack-B-id>` or `Api::StacksController#show` for Stack B using the same token, which correctly returns 404/empty because `Api::StacksController#stack` uses the properly-scoped `stacks.from_param!`.
