### Title
Unprivileged asset attestor-list update can permanently freeze AA payments made to previously-recorded counterparty/bidder addresses of a `spender_attested` asset - (File: `validation.js`, `aa_composer.js`)

### Summary
The report describes an ERC-20 blacklisting feature (e.g. USDC) that can permanently block a required outbound token transfer inside a smart-contract flow (auction refund, liquidation payout), because there is no way to catch the revert and the whole operation gets stuck. Obyte/ocore has a structurally equivalent mechanism: an asset can be defined with `spender_attested: true`, which requires that *every output address* of every payment in that asset be currently on the definer's attestor-approved list, verified in `validation.js` at payment-validation time. An Autonomous Agent (AA) that stores a counterparty address in its persistent state (e.g. a previous bidder, escrow counterparty, marketplace seller) and later must pay that exact address can be permanently DoS'd if the address's attestation is revoked between the two events, because AA execution has no analogue of Solidity's `try/catch` — any payment-validation failure causes the whole response unit to `bounce()`, rolling back all state changes for that trigger.

### Finding Description
When a payment message references a `spender_attested` asset, `validatePaymentInputsAndOutputs` requires that **all** output addresses of the payment be attested at time of use: [1](#0-0) 

The set of currently-attested addresses is derived from the *latest* `asset_attestors` list published by the asset's definer — a completely separate, single-authored control message that can be updated at any later mci: [2](#0-1) [3](#0-2) 

This means the attestation status of any address (an AA counterparty, escrow bidder, marketplace seller, etc.) is not fixed at the time it was first recorded by an AA — it can be revoked afterward by the asset definer, functioning exactly like an ERC-20 blacklist entry.

Many common AA patterns store a counterparty address in AA state and later must pay a `spender_attested` asset back to that *same, fixed* address — e.g., paying the seller `$owner` in a marketplace AA, refunding a previous bidder in an auction AA, or forwarding funds to a fixed destination AA. If that stored address is de-attested in the interim, the payment-composition step (`completePaymentPayload`/`validateAndSaveUnit`) fails validation with `"some output addresses are not attested"`, and `sendUnit()` calls `bounce(err)`: [4](#0-3) 

`bounce()` unconditionally reverts **all** state changes made during that trigger evaluation (restoring `stateVars` and balances), and the primary trigger's coins/fees are consumed by the bounce-fee logic; the underlying item/escrow/entry stays exactly where it was, i.e., permanently un-payable: [5](#0-4) 

Because oscript has no `try/catch` construct around message generation (unlike Solidity), and because the attestation check happens deep in unit validation rather than at oscript-formula evaluation time, an AA author cannot detect or work around a de-attested recipient address inside the AA logic itself — every subsequent trigger that requires paying that exact address will bounce identically, forever.

### Impact Explanation
Any AA design that (a) accepts a `spender_attested` asset and (b) later must pay that asset back to an address recorded from a prior interaction (bidder refund, marketplace payout to seller, escrow counterparty payout, proxy/forwarding AA) is vulnerable to a permanent denial of service and fund freezing: if the recipient's attestation is revoked after the address was recorded but before the AA needs to pay it, the specific state entry (auction, listing, escrow) becomes permanently stuck — the AA can never successfully execute that payment, and since bounce rolls back state, there is no way to mark the entry as abandoned or redirect funds elsewhere. This matches the report's "Medium" severity risk category of DoS + fund freezing caused by an unprivileged, deny-list-like restriction on a specific address.

### Likelihood Explanation
This requires only that the asset in question be defined with `spender_attested: true` (a legitimate, in-scope, commonly-documented ocore asset feature) and that its definer later removes an address from the attestor-approved list via a normal `asset_attestors` unit — an action fully within the asset definer's authorized, unprivileged capabilities and independent of the AA's own logic. Any AA author using such an asset for third-party/counterparty payouts is exposed without any special validation gap needed beyond the AA design pattern itself.

### Recommendation
- AA design guidance / oscript documentation should warn against using `spender_attested` assets for payouts to addresses recorded from prior triggers, since attestor status is not immutable.
- Consider adding an oscript-level mechanism analogous to a "safe transfer" that lets an AA branch/skip an output when the destination fails an attestation check (instead of unconditionally bouncing the whole unit), e.g., evaluating attestation status via `in data feed`/`attested` in the `if:`/`init:` formula (already possible for **address definitions** via the `attested` op in `definition.js`) *before* composing the payment, so bounces can be avoided when the AA author explicitly checks attestation first. [6](#0-5) 
- At minimum, document that AAs relying on `spender_attested` outputs to stored addresses should independently re-check `attested` status in their `init` formula and provide an alternate resolution path (e.g., allow redirecting to a different address) rather than relying solely on the payment validation step, which offers no partial-success or catch semantics.

### Proof of Concept
1. Definer creates asset `X` with `spender_attested: true` and attestor list `[A]`.
2. A marketplace AA lists an item for sale; the seller address `S` (attested by `A` at the time) is stored in AA state as `owner_<id>`.
3. A buyer triggers the AA's "buy" branch, which composes a payment message paying asset `X`'s underlying value to `S`.
4. Before the buy trigger is processed, attestor `A` publishes a new `asset_attestors` update for asset `X` that no longer includes `S` (analogous to blacklisting `S`).
   - Validated only by: `validateAttestorListUpdate` (single-authored, definer-only), see `validation.js:2829-2848`.
5. When the buy trigger executes, `sendUnit()` builds the payment to `S`; `validatePaymentInputsAndOutputs` rejects it because `S` is no longer in `arrAttestedOutputAddresses` (`validation.js:2630-2641`), causing `bounce("some output addresses are not attested")`.
6. `bounce()` reverts all AA state changes for this trigger (`aa_composer.js:909-925`); `owner_<id>` and `price_<id>` remain unchanged.
7. Every future "buy" trigger for this listing repeats step 5–6 identically: the item is now permanently un-sellable and any escrowed value tied to it is permanently stuck, with no AA-level recourse since oscript cannot catch or route around the failed output.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
