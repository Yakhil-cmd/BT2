### Title
HTTP Request Injection via Unvalidated `arbiter_address` in Arbiter Contract ArbStore Requests - (File: arbiter_contract.js, arbiters.js)

### Summary
`arbiter_contract.js` and `arbiters.js` build raw HTTP requests to an ArbStore server by concatenating a peer-supplied `arbiter_address` string (and a hub-supplied URL) directly into the request path/host without filtering control characters (CR/LF). This mirrors the FreeRDP class of bug: an untrusted string received over a message channel (there, the RDP redirection `TargetNetAddress`; here, `arbiter_address` from an `arbiter_contract_offer` device message) is embedded verbatim into an outbound HTTP request, allowing header/request injection.

### Finding Description
When a wallet creates an arbiter contract, `arbiter_address` is taken from `objContract` and stored/used as-is: [1](#0-0) 
This value is attacker-influenced because a contract can be received from a peer device via `arbiter_contract_offer`/`arbiter_contract_shared` and then stored through `store()`, which inserts `objContract.arbiter_address` into `wallet_arbiter_contracts` with no call to `ValidationUtils.isValidAddress` or any character-set check anywhere in `arbiter_contract.js`.

That same field is later used, unescaped, to build ArbStore API requests: [2](#0-1) 
Here `address` (== `arbiter_address`) is concatenated directly into a URL path (`url+'/api/arbiter/'+address`) that is passed to `http.get()`. The `url` itself also comes from an untrusted source — the hub's `hub/get_arbstore_url` response — and is fed straight into `url.parse()`/`http.request()` in `arbiter_contract.js`'s `httpRequest()`: [3](#0-2) 
Neither `httpRequest()` nor `requestInfoFromArbStore()` sanitizes for CR/LF or other control characters before using the string as part of an HTTP request line/host, and multiple call sites pass `objContract.arbiter_address` straight through: `getArbstoreAddresses`, `openDispute`, `appeal`, and `getAppealFee`. [4](#0-3) [5](#0-4) 

### Impact Explanation
If `arbiter_address` (or the ArbStore path built from it) contains CR/LF or other control characters, it can inject extra header lines or a second request into the HTTP connection made from the victim's wallet to the ArbStore server. Depending on Node's HTTP implementation behavior for the version in use, this can allow request smuggling/response splitting against the ArbStore endpoint, letting an attacker (a paired correspondent device that proposes/relays an arbiter contract) manipulate what the victim's wallet sends to or how it parses responses from the arbitration service that ultimately governs release of shared-address funds (dispute resolution, appeal fee, appeal outcome). Because the whole arbiter/dispute flow controls fund release from a jointly-defined shared address (`deriveSharedAddress` conditions on arbiter's data-feed outcome), corruption of this channel has fund-safety implications for one of the contract parties — a concrete AA/contract fund-loss/freezing analog to the CVSS-critical class of the original bug, even though the confirmed root cause here is missing input sanitization rather than confirmed exploitability against a specific Node version.

### Likelihood Explanation
`arbiter_address` originates from data reachable by a paired device (an `arbiter_contract_offer` sender, or a cosigner via `arbiter_contract_shared`/`arbiter_contract_update`), which is exactly the kind of "paired device" reach explicitly in scope. No validation function (`isValidAddress`, length check, character allow-list) is applied to `arbiter_address` in `arbiter_contract.js` before it is persisted and later interpolated into HTTP request paths, making the injection reachable without any special privilege beyond being a correspondent device that can send/share an arbiter contract.

### Recommendation
- Validate `arbiter_address` with `ValidationUtils.isValidAddress()` (and reject on failure) at every entry point where a contract object is received/stored (`store()`, `handleReceivedSharedAddress`, `handleReceivedSigningUnit`, and the `arbiter_contract_offer`/`_shared`/`_response` handlers in `wallet.js`).
- Strip or reject CR/LF and other control characters (as `mail.js`'s `strip_rn()` already does for email headers) from any value used to build an HTTP path/host, and prefer `encodeURIComponent()` when composing `url+'/api/arbiter/'+address`.
- Validate the ArbStore `url` received from the hub (`hub/get_arbstore_url`) against a strict URL schema (protocol, no embedded credentials/control chars) before passing it to `url.parse()`/`http.request()`, similar to `network.js`'s `isValidWsUrl()`.

### Proof of Concept
1. Device A pairs with victim device B and sends `arbiter_contract_offer` with `arbiter_address` set to a string containing an embedded CRLF sequence and forged header/second request payload (e.g. `"BASE32ADDR\r\nX-Injected: 1\r\n\r\nGET /api/malicious HTTP/1.1\r\nHost: x"`), since no format check rejects it in `store()`. [6](#0-5) 
2. Victim B accepts/interacts with the contract, triggering `openDispute`/`appeal`/`getAppealFee`, which calls `device.requestFromHub("hub/get_arbstore_url", objContract.arbiter_address, ...)` and then `httpRequest(url, ...)`/`arbiters.getInfo`, embedding the malicious `arbiter_address` into the HTTP request path sent to the ArbStore server. [7](#0-6) [8](#0-7) 
3. The injected CR/LF content is interpreted as additional headers or a smuggled second request by the ArbStore HTTP server/any intermediary proxy, allowing the attacker to influence the wallet's arbitration-related network traffic.

**Note on confidence:** I was unable to fully trace the `wallet.js` handlers for `arbiter_contract_offer`/`arbiter_contract_shared` (file too large to load completely) to conclusively confirm the total absence of address validation before `arbiter_contract.store()` is invoked; the `store()` function itself, which is the direct persistence path, does not perform such validation. If a Devin session is started, I recommend re-verifying the exact `wallet.js` event handlers to confirm no upstream validation exists before treating this as fully confirmed.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
