### Title
Unchecked accrued RAY-value growth overflows `i128` and permanently freezes a saturated market - (File: `common/src/rates/scaling.rs`)

### Summary
`scaled_to_original` converts scaled market shares into RAY token values through `Ray::mul`, without checking whether the resulting RAY value fits in `i128`. [1](#0-0)  The fixed-point multiplication widens intermediate arithmetic only to compute the quotient, then panics with `MathOverflow` if that quotient cannot fit into `i128`. [2](#0-1)  Once a market’s scaled exposure times its index crosses that bound, the next accrual aborts before the accrual timestamp can advance. [3](#0-2) 

### Finding Description
The pool accrues every elapsed chunk by calling `accrue_step` with the market’s full `borrowed` and `supplied` scaled-share totals, and only commits the cache after those calculations succeed. [4](#0-3)  `calculate_utilization` separately multiplies the complete scaled borrow and supply balances by their indexes through `scaled_to_original`, so an overflowing total cannot be skipped or partially processed. [5](#0-4) 

The configured index ceilings stop index growth only at `10^36` RAY, but do not bound the product `scaled_shares * index / RAY` against `i128::MAX`. [6](#0-5)  The repository’s long-horizon test demonstrates that a sufficiently large market reaches the RAY-value ceiling first: the index remains below `MAX_BORROW_INDEX_RAY`, while both withdrawal and repayment subsequently revert with `MathOverflow`. [7](#0-6) [8](#0-7) 

An unprivileged actor can construct the precondition using only `supply`, `borrow`, elapsed ledger time, and `update_indexes`; `update_indexes` requires only caller authorization and forwards the requested markets to the pool. [9](#0-8) 

### Impact Explanation
This can permanently freeze all supplier funds and prevent borrowers from repaying in the affected market. [10](#0-9)  Because the panic occurs during accrual before mutating operation state is committed, subsequent calls repeat the same overflowing calculation rather than advancing past it. [11](#0-10)  The pool exposes supply, borrow, withdrawal, repayment, index accrual, recapitalization, flash-loan and liquidation operations through paths that depend on market state, leaving no in-contract recovery path once accrual cannot complete. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The path is unprivileged but capital-intensive: the attacker must supply enough of a listed high-decimal asset and create sustained high utilization until `scaled_shares * index / RAY` exceeds `i128::MAX`. [14](#0-13)  The regression test reaches the failure with one billion 18-decimal tokens and 98% utilization, establishing that the arithmetic cliff is reachable inside admitted amounts rather than being purely theoretical. [7](#0-6) [15](#0-14)  Market caps and realistic token supply reduce practical reachability, so this is a medium-severity permanent-freeze condition rather than a low-cost denial of service. [16](#0-15) 

### Recommendation
Compute a per-market safe index bound from the stored scaled balances before mutating indexes, using widened arithmetic: the larger of borrow and supply scaled shares should satisfy `scaled * index / RAY <= i128::MAX`. [1](#0-0)  Clamp each accrual step to the minimum of `MAX_BORROW_INDEX_RAY`, `MAX_SUPPLY_INDEX_RAY`, and that derived value ceiling before any multiplication that can panic. [4](#0-3)  When the value ceiling is reached, mark the market accrued and continue processing exits and repayments with the last representable indexes instead of repeatedly attempting overflowing accrual. [17](#0-16) 

### Proof of Concept
The existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` is a direct reproduction. [18](#0-17) 

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
``` [19](#0-18) 

Advance ledger time until `update_indexes(caller, [BIG18])` fails. [15](#0-14)  The final stored borrow index is still below the configured index ceiling, but `withdraw` and `repay` both fail with `MathOverflow`, proving that the value product—not the index bound itself—created the lockup. [8](#0-7)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
