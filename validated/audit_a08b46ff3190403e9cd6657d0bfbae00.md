### Title
CCMenuController bypasses ApiClient stack-scoping, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug-class from the C4 report is a parsing/authorization mismatch where one code path enforces a stricter binding than another path that consumes the same authenticated input, letting the weaker path act outside the boundary the strict path enforces. In shipit-engine, `Shipit::Api::BaseController` establishes the binding "stack an `ApiClient` token authorizes == stack a request may touch" by resolving `stack` through `stacks`, which restricts the queryable `Stack` set to `current_api_client.stack_id` when the client is scoped: `stacks.from_param!(params[:stack_id])` where `stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the stack directly from client-supplied `params[:stack_id]` against the global `Stack` table: `@stack ||= Stack.from_param!(params[:stack_id])` [2](#0-1) , while still only checking the generic `read:stack` permission string via `require_permission :read, :stack` [3](#0-2)  and `ApiClient#check_permissions!` [4](#0-3) , which never inspects `stack_id`.

### Finding Description
`ApiClient` supports being scoped to a single `Stack` via `belongs_to :stack, optional: true` [5](#0-4) , and `Shipit::Api::BaseController` is the enforcement point for that scoping across the JSON API: any subclass relying on the inherited `stack`/`stacks` helpers can only ever resolve a `Stack` that matches `current_api_client.stack_id` [1](#0-0) .

`CCMenuController < BaseController` re-implements `stack` privately and drops the scoping filter, resolving directly against `Stack.from_param!(params[:stack_id])` with no reference to `current_api_client.stack_id` [2](#0-1) . Authentication for this controller is also customized to accept the token via the URL query string instead of the `Authorization` header: `@current_api_client = ApiClient.authenticate(params[:token])` [6](#0-5) , which is exactly the token format produced for a stack-scoped CCMenu client by `CCMenuUrlController#client`, `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` embedded in a URL with a fixed `stack_id` [7](#0-6) .

The binding broken is: *the stack a token authorizes* (`current_api_client.stack_id`, when set) *!=* *the stack the request actually touches* (`params[:stack_id]` in `CCMenuController#show`). Because the override does not intersect with `current_api_client.stack_id`, any valid `read:stack` token — including one intentionally scoped to a specific stack — can be replayed with a different `stack_id` in the URL to read another stack's CCMenu status.

### Impact Explanation
`CCMenuController#show` renders `stack.deploys_and_rollbacks.last`, exposing stack name, last build status/label/time, and web URL for whatever stack is named in the path [8](#0-7) . An attacker in possession of any `read:stack`-scoped token (even one meant to be limited to a single stack) can enumerate `stack_id` values and read build/deploy state for stacks the token was never authorized for. This is an unauthenticated-boundary-crossing read of stack state gated behind a token whose entire purpose (per the `ApiClient.stack_id` scoping mechanism enforced everywhere else in the API) is to prevent exactly this cross-stack access.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` bearer token carrying `read:stack` permission (no admin/privileged access, no session, no GitHub credentials) and knowledge/guessing of another stack's `to_param`. Because `BaseController` correctly enforces scoping everywhere else, this override is a latent trap: any stack-scoped token, distributed for narrow CI-status purposes, silently grants read access to every stack in the instance.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reintroduce scoping) so it resolves the stack the same way as `BaseController`, e.g., `@stack ||= stacks.from_param!(params[:stack_id])`, ensuring `current_api_client.stack_id` is honored consistently across all API controllers, including token-authenticated ones like this and `Shipit::CCMenuUrlController`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_A` with `permissions: ['read:stack']` and `stack_id: stack_A.id` (as intended for CCMenu tokens via `CCMenuUrlController#client`) [9](#0-8) .
2. Take that client's `authentication_token` (generated by `ApiClient#authentication_token` [10](#0-9) ).
3. Request `GET /api/stacks/:stack_B_id/ccmenu.xml?token=<token>` where `stack_B` is a different, unrelated stack.
4. `authenticate_api_client` accepts the token [6](#0-5) ; `require_permission :read, :stack` passes because `check_permissions!` only checks the permission string, not `stack_id` [4](#0-3) ; `stack` resolves `stack_B` directly, ignoring the client's `stack_id` scope [2](#0-1) ; the response returns `stack_B`'s build status, disclosing state the token was never authorized to read.
