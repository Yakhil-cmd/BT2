### Title
Cross-tenant Status forgery via global `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` to verify the HMAC signature purely from the payload's own `repository.owner.login` (or `organization.login`) field, and once verified, `StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` — a global, cross-stack, cross-tenant query with no filter tying the matched commit's owning repository back to the org that signed the request. Any organization B onboarded to Shipit (i.e., with its own valid `webhook_secret` configured) can therefore send a `status` webhook signed with its own secret, set `repository.owner.login` to itself for signature verification purposes, but supply a `sha` belonging to a completely unrelated org A's commit, and have Shipit write a `Status` row onto org A's commit.

### Finding Description
The binding that should hold is: `repository_owner` (used in `Shipit.github(organization: repository_owner)` for HMAC verification) must equal `commit.stack.repository.owner_login`/`full_name` owner for every `Commit` mutated by that request. Tracing the code:

- `app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-49) computes `repository_owner` from `params.dig('repository', 'owner', 'login')` [1](#0-0) , fetches `github_app = Shipit.github(organization: repository_owner)`, and checks the HMAC signature against that app's `webhook_secret` [2](#0-1) . This only proves the request was signed by whichever org's secret matches the `repository_owner` claimed in the payload — it does not prove anything about the `sha` field elsewhere in the same payload.
- `app/models/shipit/webhooks/handlers/status_handler.rb#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query is global across all stacks/repositories/tenants in the database — there is no `.where(stack: { repository_owner: repository_owner })` or any join back to the signing organization.
- `Commit#create_status_from_github!` writes directly into `statuses` on that commit and triggers hook emission, continuous-delivery scheduling, etc. [4](#0-3) , [5](#0-4) .

Root cause: the `repository` object used for authentication (signature check) and the `sha`/commit used for mutation are two independent, attacker-controlled fields of the same JSON body, and nothing enforces they refer to the same tenant. An attacker who owns/controls org B's GitHub organization/repo (and thus its legitimately configured `webhook_secret` in Shipit) can sign an arbitrary payload with `repository.owner.login: "B"` and `sha: "<org-A's-commit-sha>"`. `verify_signature` succeeds (B's secret matches B's declared identity), and `StatusHandler` then finds and mutates org A's `Commit` row because the SHA lookup is unscoped.

Existing guards do not close this gap: `verify_signature` only rejects unknown orgs (`GithubOrganizationUnknown`) or bad signatures, it never compares `repository_owner` to the repository owning the matched commit. `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`, `state`, etc. [6](#0-5) , not ownership. There is no `force_github_authentication`/session check here since this is an unauthenticated webhook endpoint by design; the security boundary is supposed to be exactly the signature-to-repository binding, which is broken.

### Impact Explanation
Any org B with its own (legitimately provisioned) webhook secret can inject arbitrary CI `Status` records onto any commit in any other tenant's stack, by SHA collision-free targeting (SHAs are globally unique in practice, so an attacker who knows or guesses/observes a target commit's SHA — e.g., from a public repo, PR, or prior notification — can forge its status). This can mark another org's commit as `"success"`, which per `Commit#deployable?` [7](#0-6)  and `schedule_continuous_delivery` [8](#0-7)  can trigger an unauthorized deploy of org A's stack if continuous deployment is enabled, or otherwise pollute/falsify org A's CI history. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". Blast radius: every tenant on a shared Shipit instance; repeatable per request against any known SHA.

### Likelihood Explanation
Preconditions: attacker needs their own org onboarded to Shipit with a webhook configured (a normal, low-privilege step available to any org that self-registers a Shipit stack) — no access to org A's secrets, sessions, or tokens is required. Attacker needs org A's target commit SHA, which is typically public (GitHub SHAs on public repos, PR pages, commit emails, status-check UI, etc.). Attack cost is one crafted HTTP POST to `/webhooks` with a valid HMAC computed using the attacker's own secret. Fully repeatable and scriptable against arbitrary known SHAs across tenants.

### Recommendation
In `StatusHandler#process` (and similarly in other handlers keyed by SHA, e.g. check_run/deployment handlers if they share this pattern), scope the `Commit` lookup to commits whose `stack.repository` owner/full_name matches the verified `repository_owner`/`repository.full_name` from the webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner })`. More robustly, pass the verified `repository_owner` (and repo name) from the controller into each handler and require handlers to filter by it before mutating any record, rather than trusting a global SHA match.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub — signatures generated locally using each org's `webhook_secret` from `test/dummy/config/secrets*.yml`):

1. Fixtures: use two configured GitHub orgs, e.g. `shopify` (secret `S1`, used by `shipit_stacks(:shipit)` / `shipit_commits(:first)`) and a second org, e.g. `george` or another org present in `test/dummy/config/secrets_double_github_app.yml` (secret `S2`), which does not own `shipit_commits(:first).stack.repository`.
2. Build payload: `{ "sha" => shipit_commits(:first).sha, "state" => "success", "branches" => [{ "name" => shipit_commits(:first).stack.branch }], "repository" => { "owner" => { "login" => "<org B login>" } } }.to_json`.
3. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', S2, payload)` (org B's own real secret, matching `repository.owner.login`).
4. `assert_equal repository_owner_used_for_signature = "org B"`, `commit.stack.repository.owner_login = "shopify"` — assert these are NOT equal (binding violated) before sending.
5. `request.headers['X-Github-Event'] = 'status'`; `request.headers['X-Hub-Signature'] = signature`; `post :create, body: payload, as: :json`.
6. Assert response is `:ok` (200) and `assert_difference('shipit_commits(:first).statuses.count', 1)` — proving org B's secret successfully wrote a `Status` onto org A's (`shopify`) commit, confirming the cross-tenant mutation despite `repository_owner ("org B") != commit.stack.repository.owner_login ("shopify")`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
