This confirms a real, distinct vulnerability, though it is different in mechanism from what the prompt hypothesizes: signature verification correctly scopes the request to a **known configured GitHub organization/webhook_secret**, but `StatusHandler#process` never checks that the organization/repository sending the `status` webhook actually **owns the commit's stack**.

### Title
`StatusHandler#process` applies GitHub `status` webhooks to any commit sharing a `sha`, regardless of the sending repository/organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other webhook handler in this engine resolves the target `Stack`/`Repository` via `Handler#stacks`, which is derived from `payload.dig('repository', 'full_name')` [1](#0-0) . `StatusHandler#process`, however, looks up commits purely by `sha` across the entire commits table with no repository/stack scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! ... }` [2](#0-1) . Any organization that has a validly configured GitHub App/webhook secret in Shipit can post a `status` event whose `sha` happens to collide with a commit belonging to a completely different tenant's stack, and that unrelated stack's `Commit#create_status_from_github!` → `add_status` → `schedule_continuous_delivery` → `ContinuousDeliveryJob` chain will fire for it.

### Finding Description
The broken binding is: **the organization authenticated by `verify_signature` (`payload.dig('repository','owner','login')`, checked against `Shipit.github(organization: repository_owner).verify_webhook_signature`) MUST equal the organization/repository that owns the `Stack` whose `Commit` gets mutated.** In `StatusHandler` this equality is never checked.

Trace:
1. `WebhooksController#verify_signature` authenticates the request only against the `repository.owner.login` named in the payload, using that organization's configured `webhook_secret` [3](#0-2) . This proves "a request signed by organization X's webhook secret," not "this `sha` belongs to a repository owned by X."
2. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` [4](#0-3) .
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never calls `stacks`/`repository_name` (the pattern every other handler, e.g. `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, uses to scope to `Repository.from_github_repo_name(params.repository.full_name)`) [2](#0-1) [1](#0-0) .
4. `Commit#create_status_from_github!` → `add_status` fires `deployable_status` hooks and, via `Status#schedule_continuous_delivery` (`after_commit` callback) [5](#0-4) , calls `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` if `deployable? && stack.continuous_deployment? && stack.deployable?` [6](#0-5) . `stack` here is `commit.stack` — determined entirely by which `stack_id` happens to already own a `Commit` row with the matching `sha`, not by the webhook payload's `repository`.

Since git SHAs are content-addressed, any two independent repositories containing bit-identical commit content (a very plausible scenario for forks, vendored/shared code, cherry-picks, subtree merges, or simply an attacker crafting a commit with the exact same tree/parent/timestamp/message as a target commit) will produce the same 40-character SHA. An attacker who can get their own repository (with any commit content producing a colliding sha, or more practically who can predict/replay a sha value observed via the target's public GitHub activity) onto a Shipit-configured organization can send `status` events for that `sha` and have them applied to the victim's `Commit` row, because `StatusHandler` performs a global, unscoped lookup.

Existing guards do not stop this:
- `verify_signature`/`GitHubApp#verify_webhook_signature` authenticate the sender's organization, but say nothing about which stack's commits that organization is allowed to touch — this is exactly the `stacks` contract that `Handler#stacks` exists to enforce, and `StatusHandler` bypasses it entirely.
- `ExplicitParameters` schema only validates types/presence of `sha`, `state`, etc., not ownership [7](#0-6) .
- `add_status`'s "not already deployed" and simple-state-transition checks gate whether hooks fire, but do not gate which stack is targeted.

### Impact Explanation
An attacker who controls (or whose organization's app installation is configured in) any Shipit-known organization can forge a `status` webhook for a `sha` that collides with a commit in an unrelated tenant's stack, causing that stack's `Commit#create_status_from_github!` to run and, if the victim stack has `continuous_deployment: true`, enqueue and execute an unauthorized `ContinuousDeliveryJob` → deploy for a repository/tenant the attacker has no relationship with. This matches "Critical - unauthorized deploy...triggered" and "a payload for one repository mutating another's...commit." The same mechanism also lets the attacker forge `commit_status`/`deployable_status` webhooks and manipulate `Status` history for arbitrary stacks, independent of continuous deployment. This is repeatable against any commit sha the attacker can produce or predict, across every stack in the Shipit instance, not just one target.

### Likelihood Explanation
Exploitation requires the attacker to be able to send a `status` webhook authenticated for *some* organization already configured in Shipit (i.e., they need to control/own a repository under an org with a GitHub App/webhook installed pointing at this Shipit instance — a normal, low-privilege condition for a member of a large multi-repo organization or a Shipit deployment that installs its app broadly). It also requires a `sha` collision or prediction with the victim's commit — feasible via forks/shared history, or by an attacker with write access to any repo under that org pushing a commit whose sha they then reuse against a different stack in the same org (cross-stack, same signing org, is the most immediately practical variant, since `verify_signature` only ties the payload to *an org*, not to the specific repository/stack named in `payload.repository`). Cross-organization collision requires finding a genuine SHA-1 collision or shared git history, which is harder but not the only viable exploitation path — the intra-organization, cross-stack case (multiple stacks under one org authenticated by one webhook secret) requires no collision at all, only a legitimate commit landing in one stack that also has the same sha recorded under a sibling stack's Commit row (e.g., via a shared upstream/fork relationship configured as two different Shipit stacks).

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to stacks belonging to the webhook's repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the same repository-ownership binding enforced by every other handler.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not apply a status to a commit belonging to a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, dormant/pending
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.last
  victim_commit.statuses.destroy_all

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'branches' => [{ 'name' => victim_stack.branch }],
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' } # != victim_stack.repository.full_name
  }

  assert_no_enqueued_jobs only: ContinuousDeliveryJob do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  assert_equal 0, victim_commit.reload.statuses.count
end
```
Against current code, this test fails: `Commit.where(sha: params.sha)` finds `victim_commit` regardless of `attacker_payload['repository']`, `create_status_from_github!` runs, and (given `continuous_deployment: true` and a deployable state) `ContinuousDeliveryJob.perform_later(victim_stack)` is enqueued — demonstrating the cross-tenant binding violation.
