### Title
Webhook signature verified against attacker's org while Team write uses victim org's login - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#repository_owner` prefers `params['repository']['owner']['login']` over `params['organization']['login']` when selecting which GitHub App/organization secret to use for signature verification, but `Shipit::Webhooks::Handlers::MembershipHandler` writes the `Team#organization` column from `params.organization.login` unconditionally. An attacker who legitimately owns a Shipit-configured GitHub App/organization can forge a `membership` webhook whose `repository.owner.login` points at their own org (so verification succeeds against their own known `webhook_secret`) while `organization.login` points at a victim org, causing a `Team` row to be created/updated under the victim organization.

### Finding Description
The broken binding is: *the organization whose `webhook_secret` verified the request* (`repository_owner` = `params.dig('repository','owner','login')`) **must equal** *the organization whose record is mutated* (`params.dig('organization','login')` used in `MembershipHandler#find_or_create_team!`). These are read from two independent, attacker-controlled JSON keys in the same POST body, so nothing enforces this equality.

Code path:
- `Shipit::WebhooksController#verify_signature` resolves the verifying app via `Shipit.github(organization: repository_owner)` [1](#0-0)  where `repository_owner` falls back from `repository.owner.login` to `organization.login` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` just HMAC-verifies the raw body against whichever org's `webhook_secret` was selected [3](#0-2) .
- `#create` parses the same raw body and dispatches it, unmodified, to the registered handler(s) for the event [4](#0-3) .
- `MembershipHandler#find_or_create_team!` sets `team.organization = params.organization.login` — reading the `organization` key directly, independent of which org was used for verification [5](#0-4) .

Attacker's exact request: attacker who legitimately controls a Shipit `GithubHook`/GitHub App config for `attacker-org` (and thus knows its `webhook_secret`) sends:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC over raw body using attacker-org's webhook_secret>
{
  "action": "added",
  "team": {"id": 1, "name": "n", "slug": "s", "url": "u"},
  "repository": {"owner": {"login": "attacker-org"}},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-org-member"}
}
```
`repository_owner` returns `"attacker-org"` (present, so the `||` fallback to `organization.login` never triggers), `Shipit.github(organization: "attacker-org")` resolves to the attacker's own legitimately-configured app, signature verification succeeds because the attacker signed with their own known secret, `verify_signature` passes, and the handler then persists a `Team` row with `organization: "victim-org"` and adds the attacker's chosen member to it.

No existing guard prevents this: `drop_unhandled_event` only checks the handler exists for the event type; `check_if_ping` is irrelevant; the `ExplicitParameters` schema on `MembershipHandler` only validates presence/types of `organization.login`, not that it matches the org used for verification; there is no cross-check between `repository_owner` and `params.organization.login` anywhere in the controller or handler.

### Impact Explanation
An unprivileged attacker who owns any Shipit-configured GitHub App/org can create or manipulate `Team` records scoped to an arbitrary victim organization string, and add arbitrary "members" (created via `User.find_or_create_by_login!`) to that team via `team.add_member(member)`. Since `Team` records back GitHub-team-based authorization (`Shipit.github_teams`/OAuth team scoping per `Team#organization`/`#handle`), this is a cross-tenant write that can escalate a team the attacker fully controls into being associated with a victim organization's namespace, and is repeatable against any victim org string with no per-request cost beyond the attacker's own legitimate webhook secret. This matches "escalation into `Shipit.github_teams` authorization" / cross-repository write into another tenant's record — High to Critical depending on how `Team#organization` is subsequently trusted for permission checks.

### Likelihood Explanation
Preconditions are modest and match the attacker model described: the attacker must have their own legitimately Shipit-configured GitHub App/`GithubHook` (something any org admin onboarding their own repos into Shipit would have), and knowledge of their own `webhook_secret` — no victim secrets, sessions, or tokens are required. The attacker directly controls the JSON body of `POST /webhooks` and only needs to set two independent top-level keys (`repository.owner.login` and `organization.login`) to different values. This is a single crafted HTTP POST, fully repeatable against any victim organization name.

### Recommendation
Do not let signature-verification org selection diverge from the org used by the event handler. Either (a) require `repository_owner` to be derived the same way the handler consumes organization identity (e.g., always use `params.dig('organization','login')` when both `organization` and `repository` are present and the event is an org-level event like `membership`), or (b) after selecting `repository_owner` for verification, assert it equals `params.dig('organization','login')` (when both present) and reject (422) on mismatch before dispatching to handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest)
test "membership webhook signed by attacker org cannot mutate victim org Team" do
  attacker_org = 'attacker-org'
  victim_org = 'victim-org'

  payload = {
    action: 'added',
    team: { id: 999, name: 'n', slug: 's', url: 'u' },
    repository: { owner: { login: attacker_org } },
    organization: { login: victim_org },
    member: { login: 'attacker-member' }
  }.to_json

  Shipit.stubs(:github).with(organization: attacker_org).returns(
    stub(verify_webhook_signature: true)
  )

  post shipit.webhooks_path, params: payload,
       headers: { 'X-Github-Event' => 'membership', 'CONTENT_TYPE' => 'application/json' }

  team = Shipit::Team.find_by(github_id: 999)
  # Binding equality check: verifying org must equal mutated Team's organization
  assert_equal attacker_org, team.organization,
    "expected verification org (#{attacker_org}) to match Team#organization, " \
    "but got #{team.organization.inspect} — cross-tenant write confirmed"
end
```
This test demonstrates that `team.organization` ends up as `victim-org` even though verification succeeded solely against `attacker-org`'s secret, proving the two sides of the binding diverge.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
