### Title
Reused Bitcoin L1 lockup outpoints can be credited multiple times in pox-5, double-counting sBTC bond stake never re-locked on Bitcoin - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`pox-5.clar`'s `validate-l1-lockup`/`verify-l1-lockups` functions verify a Bitcoin SPV proof that a staker locked BTC into a timelock script, then credit the reported `amount` (in sats) toward the staker's protocol-bond stake. The duplicate-outpoint check (`seen-outpoints`) is only accumulated and checked *within a single call's fold* over the `outputs` list supplied in that one transaction, and is never persisted to contract storage. Nothing prevents the same `(txid, output-index)` outpoint from being submitted again in a subsequent, separate call (e.g. a later `register-for-bond`/registration update), letting a staker get sats credited multiple times for a single Bitcoin lock.

### Finding Description
`verify-l1-lockups` [1](#0-0)  folds over the caller-supplied `outputs` list via `validate-l1-lockup`, threading a `seen-outpoints` accumulator that starts empty on every invocation: [2](#0-1) 

`validate-l1-lockup` only rejects an outpoint if it was already seen *earlier in the same fold* (`is-none (index-of? seen-outpoints outpoint)`), then appends it to the local `seen-outpoints` list: [3](#0-2) 

Crucially, the check compares the SPV-proven output's `amount`/`script` against the timelock derivation, and sums valid amounts into `sum`, which is returned by `verify-l1-lockups` as the sats amount to credit for the bond. There is no map in this contract (e.g., a `used-l1-outpoints` map keyed by `{txid, output-index}`) that persists which outpoints have already been consumed by a previous, separate transaction. This means the exact same on-chain Bitcoin UTXO lock proof can be resubmitted in a later call (a new `register-for-bond`, or a rollover/registration-update call that reruns this verification) and be credited again, crediting `total-sbtc-staked`/bond `amount-sats` for BTC that was only ever locked once.

This is directly analogous to the reported bug class: just as the mtOFT `wrap()` return value was not properly reconciled against the actual minted amount (causing an accounting mismatch between believed and real custody), here the contract does not reconcile "sats it has already credited from this proof" against "sats actually newly locked on Bitcoin" beyond the scope of a single call — the equality `sum of Bitcoin-locked sats == sum of sats credited across all pox-5 credits` can be broken by re-submitting the same lockup proof in separate calls.

### Impact Explanation
Reward emissions in pox-5 (`calculate-rewards`) and the bond membership's stake weight are computed from the amount of sats credited (`amount-sats`/`total-sbtc-staked`), not the amount of BTC provably still locked on-chain outside of the single verification call. If a staker can double-submit an L1 lockup proof across separate registration calls, they inflate their credited sats without locking additional BTC, letting them (a) claim a disproportionate share of sBTC rewards relative to other honest stakers, and (b) potentially exceed allowlisted `maxSats` caps by splitting the same proof across multiple registration transactions. This is a double-counting of a Bitcoin commitment that was never actually re-locked, matching the "Critical: double-counting a commitment or reward" impact category.

### Likelihood Explanation
This requires only that a staker already possesses a valid Bitcoin lockup output (an ordinary bonding participant) and calls the bond-registration entrypoint more than once with the same lockup evidence in separate transactions — no privileged role, miner, or other user's key is required. The barrier is whether higher-level registration logic (`register-for-bond`, its update path) independently prevents reuse of the same lockup across calls; based on the code inspected, the only reuse guard (`seen-outpoints`) is scoped to a single call's fold and does not persist, so likelihood is assessed as plausible pending confirmation of the full registration call graph, which I was unable to fully trace within the available iterations.

### Recommendation
Persist consumed L1 lockup outpoints in a durable map (e.g., `(define-map used-l1-outpoints {txid: (buff 32), output-index: uint} bool)`), and have `validate-l1-lockup` check/set this map in addition to the local `seen-outpoints` list, so that once a Bitcoin lockup output has been credited to a staker's bond, it cannot be credited again in any subsequent call.

### Proof of Concept
1. Staker locks `X` sats into a timelock output on Bitcoin, matching their bond's `construct-lockup-output-script`.
2. Staker calls `register-for-bond` (bond A) with an `outputs` list containing this lockup's SPV proof; `verify-l1-lockups` validates it and credits `X` sats to `total-sbtc-staked` / bond A.
3. Staker later calls the registration path again (e.g. for bond B, or via an update/rollover path that re-invokes `verify-l1-lockups`) submitting the *same* `(txid, output-index)` outpoint and proof.
4. Because `seen-outpoints` is reinitialized empty for this new call (it is only a local fold accumulator, not contract storage), `validate-l1-lockup` finds no prior record of this outpoint and credits `X` sats again — doubling the staker's total credited sats without any additional BTC being locked.

Note: I was not able to fully trace every call site of `verify-l1-lockups` (e.g., whether `register-for-bond`/`update-bond-registration` impose an additional persistent-outpoint check elsewhere in `pox-5.clar` that I did not reach before running out of tool iterations), so this finding should be verified against those call sites before remediation.

;; Verify l1 lockup information for a staker. This asserts that each lockup
;; corresponds to the right timelock script for this staker, and that the lockup
;; occurred on-chain. If everything is valid, this returns the sum of all lockups in sats.
(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)
