### Title
API scoped `ApiClient` tokens can read the CCMenu status of any stack, bypassing token stack-scoping - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via the optional `stack_id` association, and `Shipit::Api::BaseController` is supposed to enforce that scoping for every API endpoint by resolving stacks through the `stacks` helper. `Shipit::Api::CCMenuController` overrides `#stack` to bypass this helper entirely, breaking the binding between "the stack a token authorises" and "the stack the endpoint touches."

### Finding Description
`ApiClient` belongs to an optional `stack`, and `Shipit::Api::BaseController#stacks` is the mechanism meant to restrict a client's visibility to that single stack when `stack_id` is present: [1](#0-0) [2](#0-1) 

Every controller that inherits `stack` from `BaseController` (e.g. `Api::StacksController#stack` at `stacks.from_param!(params[:id])`) is correctly restricted to the client's authorized stack: [3](#0-2) 

However, `Api::CCMenuController` defines its own `stack` method that resolves directly from `Stack.from_param!`, never consulting `current_api_client.stack_id` / the `stacks` scoping helper: [4](#0-3) 

Its authorization check is only `require_permission :read, :stack`, i.e. a generic permission check on the operation/scope pair, not on the specific stack the token was issued for: [5](#0-4) 

The equality that should hold is: `stack_touched_by_request == stack_authorised_for(current_api_client)` (i.e. `params[:stack_id] ∈ {current_api_client.stack_id}` when the client is stack-scoped). `CCMenuController#stack` breaks this by resolving any `stack_id` param against the global `Stack` scope, so a token that was created/authorized for stack A can be replayed with `stack_id` of stack B and still succeed, as long as it holds the generic `read:stack` permission.

### Impact Explanation
A holder of any valid `read:stack` `ApiClient` token — even one deliberately scoped by an administrator to a single stack (`api_client.stack_id` set) — can enumerate and read the CCMenu XML status (build/deploy state, activity, last build label/time, web URL) of every stack in the installation, not just the one it was authorized for. This is an authorization-scope escape: the deployment-trust binding between "stack a token authorises" and "stack it touches" is broken, giving unauthenticated-for-that-stack read access to deploy/task state, which matches the "unauthorized read of stack state ... or deploy output" High-impact category.

### Likelihood Explanation
Any user who can obtain a stack-scoped `read:stack` token (a normal, low-privilege workflow — e.g. via `CCMenuUrlController`, which creates `read:stack` `ApiClient`s, or any client whose permissions were intentionally narrowed to a single stack by an admin) can immediately exploit this by changing the `stack_id` request parameter; no additional credentials, signatures, or GitHub access are required.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the inherited, scope-aware `stacks` helper (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot be used to view stacks outside their authorized scope.

### Proof of Concept
1. As an authenticated Shipit user, create (or have an admin create) an `ApiClient` with `permissions: ['read:stack']` and `stack: <stack A>` (stack-scoped token).
2. Using that token's `authentication_token`, issue `GET /api/<stack_A_or_B>/ccmenu.xml` with `stack_id` set to a *different* stack B's param (e.g. `owner/repo/env`), analogous to:
   ```
   GET /api/<stack_B>/ccmenu.xml
   Authorization: Basic base64(<stack_A_scoped_token>)
   ```
3. Observe the response returns stack B's CCMenu project XML (name, lastBuildStatus, lastBuildLabel, webUrl, etc.), despite the token only being authorized for stack A — confirmed by `CCMenuController#stack` at `app/controllers/shipit/api/ccmenu_controller.rb:29-31` using `Stack.from_param!` instead of the scoped `stacks.from_param!` used elsewhere (`app/controllers/shipit/api/base_controller.rb:78-80`, `app/controllers/shipit/api/stacks_controller.rb:87-89`).
