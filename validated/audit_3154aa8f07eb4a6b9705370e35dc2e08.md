### Title
Skill install `--upstream` auto-redirect trusts unauthenticated, attacker-controlled repository metadata to silently retarget the install source - ([File: pkg/cmd/skills/install/install.go])

### Summary
`gh skill install` contains an "upstream provenance" feature that inspects the `SKILL.md` frontmatter of the skill being installed for a `metadata.github-repo` field, and — when the user or an automation script passes `--upstream` — automatically re-runs the install against whatever repository that field names, with no independent verification of the claim. Because the `SKILL.md` content is fully attacker-controlled (it's the artifact being installed), any repository author can cause the CLI to silently redirect the install target to a repository of the attacker's choosing.

### Finding Description
`checkUpstreamProvenance` fetches the `SKILL.md` of the skill the user asked to install and looks for a `github-repo` frontmatter key: [1](#0-0) 

This value is parsed with `source.ParseRepoURL` into a `ghrepo.Interface` and, when `opts.Upstream` (the `--upstream` flag) is set, is returned immediately as the new install target, with only a log line printed — no additional confirmation step in non-interactive contexts: [2](#0-1) 

Back in `installRun`, the returned `upstreamRepo` unconditionally replaces `opts.repo`/`opts.SkillSource`, clears the pin/version, and the whole install pipeline recurses against the new repository: [3](#0-2) 

The `github-repo` field is not a GitHub-verified provenance attestation — it is plain text inside a file that lives in the repository the attacker controls (the same repository the user pointed `gh skill install` at). This is structurally analogous to the Turnstile bug: a permissionless, self-declared registration (`register()` in Turnstile / `metadata.github-repo` in `SKILL.md`) is trusted by downstream logic (fee routing in `PostTxProcessing` / repo redirection in `checkUpstreamProvenance`) to redirect a benefit or destination that the caller did not actually choose.

### Impact Explanation
When `--upstream` is used (e.g. baked into a script, alias, or CI pipeline that always wants "canonical" skill sources), the CLI will silently fetch and install skill content from a repository named entirely by the untrusted artifact's own metadata rather than the repository the user specified. Because installed skills are described elsewhere in the codebase as capable of containing "prompt injections, hidden instructions, or malicious scripts" (an explicit, acknowledged risk baked into the disclaimer text): [4](#0-3) 
an attacker can leverage this redirect to point installs at a second attacker-controlled repository whose content differs from what a reviewer of the first repository saw, undermining the "review before use" trust model the tool otherwise tries to establish, and causing the CLI to fetch/install/execute (via agent skill invocation) content from a source the user never vetted or explicitly named.

### Likelihood Explanation
Exploitation requires: (1) the victim (or their tooling) to run `gh skill install <attacker-repo> <skill> --upstream`, and (2) the attacker to control the content of the `SKILL.md` being installed (trivial, since they publish the repo). The interactive path already surfaces a choice to the user ("re-publisher, recommended" vs "upstream"), which is a meaningful mitigation, but the `--upstream` flag and the non-interactive default logic remove that human check. Overall likelihood is moderate — it depends on `--upstream` usage, which the CLI's own help text and examples encourage as a normal, "get the canonical source" convenience feature rather than a rare edge case.

### Recommendation
- Do not let unauthenticated in-repo metadata unilaterally decide the install source when `--upstream` is passed; require an explicit confirmation of the *specific* resolved upstream repo/host even in flagged/non-interactive runs, or restrict `--upstream` to interactive sessions only.
- Cross-check the claimed upstream repository against some independently verifiable signal (e.g., the discovered skill actually exists at the claimed path/SHA in the upstream repo, and/or require the upstream repo to have GitHub's own attestation of authorship) before ever silently switching the fetch target.
- Add a mandatory disclaimer akin to `printPreInstallDisclaimer` whenever a redirect occurs, and log/telemetry the redirect target for auditability (there is already a `skill_upstream_redirect` telemetry event which is good, but it is not user-facing enough to prevent the redirect itself).

### Proof of Concept
1. Attacker publishes `attacker/skills-repo` containing `skills/git-commit/SKILL.md` with frontmatter:
```yaml
---
name: git-commit
description: Writes commits
metadata:
  github-repo: https://github.com/attacker2/evil-skills
---
```
2. Victim (or a CI script) runs:
```
gh skill install attacker/skills-repo git-commit --upstream --all
```
3. `checkUpstreamProvenance` detects the `github-repo` metadata and, because `--upstream` is set, immediately returns `attacker2/evil-skills` as the new install target: [5](#0-4) 
4. `installRun` recurses and installs the skill named `git-commit` from `attacker2/evil-skills` instead of `attacker/skills-repo`, with only a printed notice and a telemetry event, and no independent verification that `attacker2/evil-skills` is a legitimate "upstream" of the original.

Note: I was not able to fully inspect `internal/skills/source/source.go` (`ParseRepoURL`/`ValidateSupportedHost`) within the available tool budget, so I cannot confirm whether arbitrary hosts (beyond github.com/GHES) can be specified in the `github-repo` field, which would affect whether this could also be leveraged to route authenticated requests to a host outside the user's intended set of trusted GitHub instances. This should be verified directly in a follow-up review of that file.

```go
// checkUpstreamProvenance fetches the skill's SKILL.md via the contents API
// to check if it contains github-repo metadata pointing to a different
// repository, indicating the skill was re-published from an upstream source.
// In interactive mode, the user is asked whether to install from the
// re-publisher or redirect to the upstream. Non-interactive mode always
// installs from the re-publisher.
// Returns (repo to redirect to, whether upstream was detected, error).
func checkUpstreamProvenance(opts *InstallOptions, client *api.Client, hostname string, skill discovery.Skill, commitSHA string) (ghrepo.Interface, bool, error) {
	u, err := safeurl.JoinPath("repos", opts.repo.RepoOwner(), opts.repo.RepoName(), "contents", skill.Path+"/SKILL.md")
	if err != nil {
		return nil, false, err
	}
	u.SetQuery("ref", commitSHA)
	var fileResp struct {
		Content  string `json:"content"`
		Encoding string `json:"encoding"`
	}
	if err := client.REST(hostname, "GET", u.String(), nil, &fileResp); err != nil {
		return nil, false, nil //nolint:nilerr // best-effort check; failing to fetch is not fatal
	}
	if fileResp.Encoding != "base64" {
		return nil, false, nil
	}
	decoded, decodeErr := io.ReadAll(base64.NewDecoder(base64.StdEncoding, strings.NewReader(fileResp.Content)))
	if decodeErr != nil {
		return nil, false, nil //nolint:nilerr // best-effort; decode failure is not fatal
	}
	content := string(decoded)

	result, parseErr := frontmatter.Parse(content)
	if parseErr != nil || result.Metadata.Meta == nil {
		//nolint:nilerr // unparsable frontmatter means no upstream to detect
		return nil, false, nil
	}

	existingRepo, _ := result.Metadata.Meta["github-repo"].(string)
	if existingRepo == "" {
		return nil, false, nil
	}

	currentRepoURL := source.BuildRepoURL(hostname, opts.repo.RepoOwner(), opts.repo.RepoName())
	if existingRepo == currentRepoURL {
		return nil, false, nil
	}

	upstreamRepo, parseErr := source.ParseRepoURL(existingRepo)
	if parseErr != nil {
		//nolint:nilerr // invalid repo URL means we can't redirect; install normally
		return nil, false, nil
	}
```
