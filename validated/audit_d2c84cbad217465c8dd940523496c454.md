### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting a cross-tenant commit-SHA collision flip a `merge_queue_enabled` victim stack's merge state - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` [1](#0-0)  instead of scoping through `stacks` (the repository-derived scope every other handler uses) [2](#0-1) . Because Git SHAs are content-addressed and identical across forks/mirrors of the same history, any repository whose webhook is legitimately signed (verified per `repository.owner.login` in the payload) can write a `ci/lint` success status onto a commit row belonging to an unrelated victim stack that happens to share that SHA, and if that victim stack has `merge_queue_enabled: true`, `add_status` schedules `ProcessMergeRequestsJob`/merges via `stack.schedule_merges` when the state becomes `pending` or `success` [3](#0-2) .

### Finding Description
The broken binding: `commit.stack_id` (the stack that authenticated/owns the commit via its repository) should equal the stack whose repository originated the webhook (`payload['repository']['full_name']`) for every commit mutated by a status webhook. Instead, `StatusHandler#process` never consults `repository_name`/`stacks` at all — it does a bare, cross-tenant `Commit.where(sha: params.sha)` [1](#0-0) , then calls `commit.create_status_from_github!(params)` on every matching row regardless of which stack/repository it belongs to.

Path: `WebhooksController#create` parses the raw JSON payload and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates the signature using `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-supplied payload (`params.dig('repository','owner','login')`) [4](#0-3) [5](#0-4) . This check only proves the payload was genuinely signed by GitHub for the org named in the payload — it does not, and cannot, prove that the specific commit SHA inside the payload "belongs" to that repository. An attacker who owns any repository (e.g., a fork of, or a repo sharing history with, the victim's tracked repository) with the Shipit GitHub App installed can generate a completely legitimate, correctly-signed `status` webhook (`context: ci/lint`, `state: success`) for a commit SHA that is identical in both repositories (shared git history/fork). Once past `verify_signature`, `StatusHandler#process` fires and matches **every** `Commit` row across **all stacks** with that SHA — including the victim's — and calls `create_status_from_github!`, which persists the new status and, via `add_status`, calls `stack.schedule_merges` when the resulting status is `pending` or `success` [6](#0-5) . If the victim stack's `merge_queue_enabled` is true, `ProcessMergeRequestsJob` picks up `to_be_merged` requests and calls `merge_request.merge!` once `allows_merges?` (`merge_queue_enabled? && !locked? && merge_status == 'success'`) is satisfied [7](#0-6) [8](#0-7) .

None of the existing guards prevent this: `verify_signature` authenticates the *sender org*, not the *commit ownership*; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not scope; there is no `Repository`/`stacks` lookup anywhere in `StatusHandler`, unlike `PullRequest::LabeledHandler`/`UnlabeledHandler` which do scope via `repository_name`/`stacks` [2](#0-1) .

### Impact Explanation
A payload authenticated for repository A can mutate a `Commit` record owned by an unrelated stack B whenever A and B share a commit SHA (common with forks, mirrors, or repos that merge/rebase shared upstream history). For stacks with `merge_queue_enabled: true`, this status flip is sufficient to trigger `stack.schedule_merges` → `ProcessMergeRequestsJob` → `MergeRequest#merge!`, i.e., an unauthorized merge/ship action driven entirely by a third party's own (legitimately signed) webhook traffic. This is a cross-tenant "payload for one repository mutating another's commit/stack" scenario, matching the Critical impact category (unauthorized merge of code the victim repository's own CI never approved).

### Likelihood Explanation
Preconditions: the victim stack must have `merge_queue_enabled: true` and a pending merge request whose only missing requirement is the `ci/lint` (or whichever) status context; the attacker must control a repository (fork or otherwise) that shares at least one identical commit SHA with the victim's tracked history and has the Shipit GitHub App/webhook installed so it can emit genuinely-signed `status` events. This is realistic in fork-based workflows (very common on GitHub) since the initial shared commits between an upstream repo and any fork have identical SHAs. Attacker cost is low — a normal `git push`/CI run on their own fork produces a real, validly-signed `status` webhook; no secrets need to be forged. The attack is repeatable against any stack sharing history with an attacker-controlled repository.

### Recommendation
Scope `StatusHandler#process` to the sending repository, mirroring the base `Handler#stacks` scope: resolve `stacks = Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, then update only `Commit.where(sha: params.sha, stack: stacks)` (or equivalently filter by `commit.stack.repository.full_name == repository_name`) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_test.rb (conceptual)
test "status webhook for repo A does not mutate a commit belonging to stack B with a shared SHA" do
  shared_sha = 'a' * 40

  stack_a = shipit_stacks(:shipit) # tracks octocat/repo-a
  stack_b = create_stack(repository: create_repository(full_name: 'victim/repo-b'), merge_queue_enabled: true)

  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)
  merge_request = create_merge_request(stack: stack_b, commit: commit_b) # pending, awaiting ci/lint

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/lint',
    'repository' => { 'full_name' => 'attacker/repo-a', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test: commit_b.stack_id (victim, repo-b) must NOT be mutated
  # by a payload authenticated for 'attacker/repo-a'.
  assert_not_equal 'success', commit_b.reload.status.state, "victim commit must remain unaffected"
  assert_not merge_request.reload.merged?, "no unauthorized merge should occur"
end
```
This demonstrates the current unscoped `Commit.where(sha: params.sha)` write in `StatusHandler#process` [1](#0-0)  would flip `commit_b`'s status and, given `merge_queue_enabled: true` and `allows_merges?`, drive `stack.schedule_merges` toward `merge!` [3](#0-2) [7](#0-6) , violating the invariant that a `ci/lint` status affects only the repository that authenticated it.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end

      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?

        merge_request.refresh!

          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
