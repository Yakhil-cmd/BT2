### Title
Cross-repository SHA-collision status webhook triggers unauthorized continuous-delivery deploy on a victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone (`Commit.where(sha: params.sha)`), with no scoping to the repository that authenticated the webhook. An attacker who owns any GitHub repo/org can craft a commit whose SHA collides with (or, more practically, is deliberately shared/pre-computed to match) a pending head commit of a victim stack with `continuous_deployment: true`, then emit a signed `status` webhook from their own org. This flips the victim commit to `success`, causing `Commit#schedule_continuous_delivery` to enqueue `ContinuousDeliveryJob` against the victim's stack even though the victim's own CI never reported success.

### Finding Description
The broken binding: `webhook_signing_org (attacker org, verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` == `org owning stack whose commit gets the status applied`. This is false, and nothing in the code re-establishes it after signature verification.

Path:
1. `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) verifies the signature per `repository_owner` taken directly from the attacker-controlled payload (`repository.owner.login`), then dispatches the *raw payload* to every registered handler for the event type — it never re-validates that the payload's `repository.full_name` matches anything downstream.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha`, ignoring `payload['repository']` entirely. Note the base `Handler` class even provides a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) that scopes lookups by `Repository.from_github_repo_name(repository_name)`, but `StatusHandler` does not use it.
3. `Commit#create_status_from_github!` → `#add_status` → sets state, and via the `deployable_status` transition path, `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) runs: `return unless deployable? && stack.continuous_deployment? && stack.deployable?` then `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)`.
4. `deployable?` (`app/models/shipit/commit.rb:227-229`) is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` — purely a function of the commit's aggregated status state, which the attacker just set via the forged-but-validly-signed payload.

Existing guards fail because they operate at the wrong layer: `verify_signature` only proves the payload's *claimed* owning org controls that org's `webhook_secret` — it says nothing about which `Commit` rows the payload is allowed to mutate. `StatusHandler` performs no second check tying `params.dig('repository','full_name')` to `commit.stack.repository`. If a victim stack's head commit's SHA (a git SHA-1, 40 hex chars) is ever attacker-known or attacker-influenced (e.g., attacker forks/mirrors the victim's public repo, or crafts a commit that happens to reuse the same tree — trivially achievable if attacker simply names an object with the *same sha* by pushing the identical blob/tree/commit content to their own repo, which is not a hash collision but a legitimate SHA reuse since git SHAs are content-addressed and identical byte-for-byte commits produce identical SHAs), the attacker's own repo status webhook will match and mutate the victim's commit status cross-tenant.

### Impact Explanation
This is a cross-repository write: a webhook signed for repository A mutates commit/status state that drives a real deploy for stack B, which the attacker does not own and never authenticated against. It matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The result is `ContinuousDeliveryJob.perform_later(stack)` being enqueued for the victim's stack, which will run the victim's configured deploy pipeline with attacker-influenced timing/trigger, without any interaction with the victim's own GitHub org or CI. This is repeatable against any stack whose head commit SHA becomes known/reproducible to the attacker and which has `continuous_deployment` enabled. ### Likelihood Explanation
Requires: victim stack has `continuous_deployment: true` and `stack.deployable?` true (no lock, not too-recently deployed, deploy spec cached), victim's target commit is currently pending (unblocked, undeployed head). The attacker needs no Shipit credentials — only the ability to push commits to a repo they own and receive/emit its `status` webhooks, which is standard unprivileged GitHub access. Producing a colliding/matching SHA against a victim's known head commit is feasible when victim repos are public (attacker can read the target SHA directly and craft or replicate identical commit content in their own repo) — no cryptographic SHA-1 collision is required, since Shipit trusts SHA equality alone as the sole authorization boundary.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the requesting repository, mirroring the `stacks` helper already defined on `Handler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status webhook can only mutate commits belonging to stacks tied to the repository that authenticated the payload, restoring the broken binding.

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical — engine already has an equivalent structure in `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status webhook from unrelated repository must not mutate another stack's commit / trigger deploy" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.last # pending head commit
  victim_commit.statuses.destroy_all

  attacker_payload = {
    'sha' => victim_commit.sha, # attacker crafts/knows the same SHA on their own repo
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  refute_predicate victim_commit.reload, :success?
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `attacker_payload['repository']`, the status is applied, `deployable?` becomes true, and `ContinuousDeliveryJob.perform_later(victim_stack)` is enqueued — the assertion fails, proving the vulnerability. After scoping lookups through `stacks` (repository-derived), the job is never enqueued and the commit status is unchanged.
