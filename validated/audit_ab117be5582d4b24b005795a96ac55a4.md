## #Vulnerability found for this question

### Title
Race condition in `shrinkCache()`: "write" mutex released before pending cache-eviction queries complete, corrupting shared unit-props caches - (File: `storage.js`)

### Summary
The Linux report fixes a UAF caused by a background worker (`page_reporting_process`) running on a non-freezable workqueue, so it kept executing against resources that a synchronized teardown path had already destroyed. The analogous flaw in `ocore` is `shrinkCache()` in `storage.js`, a periodic background job (`setInterval(shrinkCache, 300*1000)`, [1](#0-0)  ) that takes the global `"write"` mutex meant to serialize all consensus-critical mutations of the in-memory unit caches, but releases that lock *before* the asynchronous DB queries it just issued have actually mutated those same caches, opening a window where concurrent writers can race with delayed cache deletions.

### Finding Description
`shrinkCache()` acquires the `"write"` mutex — the same lock used by `writer.js`'s `saveJoint()` and `main_chain.js`'s `markMcIndexStable()`/`updateMainChain()` to serialize all writes to `assocUnstableUnits`, `assocStableUnits`, `assocStableUnitsByMci`, `assocBestChildren`, `assocKnownUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, and `assocCachedUnitWitnesses`: [2](#0-1) 

Inside the `readLastStableMcIndex` callback it fires off a series of `db.query()` calls in a loop, each of which asynchronously deletes entries from the shared caches once its own callback runs later: [3](#0-2) 

Critically, `unlock()` is invoked immediately after the loop that *dispatches* these queries — not after their callbacks (which perform the actual `delete assocKnownUnits[row.unit]`, `delete assocStableUnits[row.unit]`, `delete assocBestChildren[row.unit]`, etc.) have executed: [4](#0-3) 

Because `db.query()` callbacks are asynchronous (queued on the event loop / DB driver), the `"write"` lock is released while these deletions are still pending. Any other consensus path waiting on `mutex.lock(["write"], ...)` — e.g. `writer.js`'s unit-saving logic (`storage.assocStableUnits[objUnit.unit] = objNewUnitProps`, `storage.assocBestChildren[my_best_parent_unit].push(...)`) — can now acquire the lock and mutate the very same objects concurrently with `shrinkCache`'s still-pending delete callbacks: [5](#0-4) 

and `main_chain.js`'s stabilization logic which pushes newly-stabilized units into `assocStableUnits`/`assocStableUnitsByMci`: [6](#0-5) 

If `shrinkCache`'s deferred callback deletes a unit's entry from `assocStableUnits`/`assocBestChildren`/`assocCachedUnitAuthors` right after a concurrent writer under the (already-released) lock inserted or depends on that same entry, downstream consensus code that assumes cache/DB consistency will diverge or crash. For example, `readUnitProps()` throws `"no unstable props of "+unit` or a `"different props"` consistency-check error if the in-memory cache disagrees with the DB state it expects: [7](#0-6) 

### Impact Explanation
This is a race condition in a lock that is supposed to serialize *all* writes to the consensus-relevant in-memory caches (`assocStableUnits`, `assocStableUnitsByMci`, `assocBestChildren`, `assocUnstableUnits`-adjacent structures) used by unit validation, main-chain stability advancement, and AA-trigger processing. Corruption or premature loss of these caches can cause a node to throw unexpected errors during unit writing/stabilization (`readUnitProps` "different props"/"not 1 row" checks), or silently diverge from other nodes on cached unit properties (e.g. `headers_commission`, `count_aa_responses`, best-children/witnessed-level bookkeeping) that feed into stability and commission calculations — i.e., a node disagreement on unit validity/stability, satisfying the required impact bar.

### Likelihood Explanation
`shrinkCache` runs automatically every 5 minutes once any of the tracked caches (`assocCachedUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocKnownUnits`, `assocStableUnits`) exceeds `MAX_ITEMS_IN_CACHE`. An unprivileged unit poster who sustains a high rate of unit posting (fully within the reach of a normal DAG participant — no privileged/hub/peer role required) will routinely grow these caches past the threshold, guaranteeing periodic execution of `shrinkCache` concurrently with the node's normal high-throughput unit writing — exactly the condition needed to hit the release-before-completion race window.

### Recommendation
Move `unlock()` inside the completion callback of the last dispatched cache-eviction query (e.g., use `async.eachSeries`/`Promise.all` over the `arrUnits` chunks and only call `unlock()` once every chunk's `db.query` callback has actually applied its `delete` operations), so the `"write"` lock is not released until all cache mutations performed by `shrinkCache` are complete.

### Proof of Concept
1. Continuously post units from an ordinary wallet/AA-triggering account to grow `assocCachedUnits`/`assocStableUnits`/`assocCachedUnitAuthors` past `MAX_ITEMS_IN_CACHE`.
2. Once `shrinkCache()`'s 300s interval fires, it takes the `"write"` lock, issues several `db.query(...)` calls, then calls `unlock()` synchronously right after dispatching them (`storage.js:2274-2294`), before their callbacks run.
3. Immediately after `unlock()`, keep posting/broadcasting units so that `writer.js`'s `saveJoint()` (or `main_chain.js` stabilization) acquires the freed `"write"` lock and mutates `assocStableUnits`/`assocBestChildren` for units that are also targeted by `shrinkCache`'s still-pending delete callbacks.
4. When the deferred `db.query` callbacks from `shrinkCache` fire, they delete cache entries that the concurrent writer just created/relied on, producing consistency-check throws in `readUnitProps` (`storage.js:1547-1550`) or silently stale/missing cache state, resulting in node-level errors or divergence from peer nodes on unit state.
