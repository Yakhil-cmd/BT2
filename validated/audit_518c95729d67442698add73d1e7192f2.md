### Title
`status` webhook creates commit statuses on any repository's commits, not just the authenticated organization's - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an incoming webhook by resolving the signing organization solely from `repository.owner.login` (or `organization.login`) in the JSON body and checking the HMAC with that organization's `webhook_secret`. [1](#0-0)  However, `Shipit::Webhooks::Handlers::StatusHandler`, unlike `PushHandler` and `CheckSuiteHandler`, never scopes its side effect to the repository that was used to authenticate the request — it looks up commits purely by `sha` across the entire Shipit database.

### Finding Description
The equality that should hold is: **organization that authenticated the webhook == repository/stack whose data is mutated**. `PushHandler` and `CheckSuiteHandler` both enforce this by scoping to `stacks` derived from `Handler#repository_name` (`payload.dig('repository', 'full_name')`). [2](#0-1) [3](#0-2) [4](#0-3) 

`StatusHandler`, however, does not require or use `repository` at all in its parameter schema, and its `process` method queries `Commit.where(sha: params.sha)` globally, then calls `create_status_from_github!` on every match, regardless of which stack/repository that commit belongs to: [5](#0-4) 

Because the HMAC signature only proves the payload was signed with *some* organization's `webhook_secret` (chosen by whatever `repository.owner.login`/`organization.login` value the attacker puts in the payload), and the org that gets used to select the secret is not the org whose data is subsequently mutated, an attacker who legitimately administers **any** organization/repository already onboarded to this Shipit instance (and thus can configure its own valid webhook secret — a routine, non-privileged action within their own GitHub org) can forge a `status` event whose `repository.owner.login` matches their own org (so it passes signature verification) but whose `sha` is a commit SHA belonging to a completely unrelated stack/repository hosted on the same Shipit instance. `StatusHandler` will happily create/update a commit status on that unrelated commit.

### Impact Explanation
Shipit's deploy/merge gating relies on commit statuses (`Shipit::Status`, surfaced through `CommitChecks`/`commit_checks_controller.rb` and used by `Stack`/`Deploy` logic to decide whether a commit is deployable). [6](#0-5)  By forging a `state: "success"` status for a target commit in a stack the attacker does not own or control, the attacker can inject a spoofed "green" CI status into another team's stack, which can be used to satisfy required-check gating and enable an unauthorized deploy of a commit that never actually passed CI in that repository. This lands in the "unauthorized deploy" bucket of Critical impact, since it crosses a repository/organization trust boundary purely because of a missing binding between the authenticating repository and the repository/commit actually written.

### Likelihood Explanation
Likelihood is High for any Shipit instance hosting more than one organization/repository (a very common multi-tenant deployment): any org admin who can add/edit a webhook for their own onboarded repository (a normal, unprivileged action relative to Shipit itself) can trigger this. The only obstacle is guessing/knowing a target commit `sha` in another repository, which is often public information (e.g., for open-source or shared-visibility repos, or observable via other Shipit UI/API endpoints that expose commit SHAs).

### Recommendation
Scope `StatusHandler#process` to only mutate commits that belong to the repository identified by the payload's `repository.full_name`, and additionally verify that this repository's owner matches the organization actually used to validate the webhook signature (`repository_owner` in `WebhooksController`) — mirroring the `stacks`/`repository_name` scoping already used by `PushHandler` and `CheckSuiteHandler`. Reject the status update if `Repository.from_github_repo_name(payload.dig('repository','full_name'))` doesn't correspond to a repository owned by the authenticating organization.

### Proof of Concept
1. Attacker legitimately administers `attacker-org/repo-x`, which is onboarded to a shared Shipit instance with its own configured `webhook_secret` (a normal, unprivileged configuration step within their own GitHub org settings — no Shipit credentials required).
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<sha-of-a-commit-in-victim-org/important-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker signs it with `attacker-org`'s own `webhook_secret` and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org` and successfully verifies the signature using `attacker-org`'s secret. [7](#0-6) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (unrelated to `attacker-org`), and calls `create_status_from_github!`, writing a forged "success" status onto it. [8](#0-7)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
