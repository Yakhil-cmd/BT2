### Title
Cross-repository `Status` forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a `Status` to every `Commit` row in the entire database whose `sha` matches the webhook payload, with no check that the webhook's authenticated repository matches the `Stack`/`Repository` that owns that `Commit`. This is inconsistent with sibling handlers (`PushHandler`, `CheckSuiteHandler`), which correctly scope their side effects through the `stacks` collection bound to the webhook's repository, demonstrating that repository-to-record binding is the intended invariant elsewhere in the engine but is missing here.

### Finding Description
The broken binding, stated as an equality that is never checked: `webhook.repository.full_name == commit.stack.repository.full_name` before `commit.create_status_from_github!(params)` is called.

Trace:
- `WebhooksController#verify_signature` only checks that the HMAC signature matches the GitHub App configured for `repository_owner` (`Shipit.github(organization: repository_owner)`), per `lib/shipit/github_app.rb:76-83`. This proves the request came from *some* organization/app Shipit knows about; it proves nothing about which repository's `Commit` rows may be mutated. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, unscoped query across the `commits` table — it is not restricted to commits belonging to a `Stack` whose repository matches `params.repository`/`repository_owner`. [2](#0-1) 
- Contrast with `PushHandler#process` and `CheckSuiteHandler#process`, both of which restrict their effect to `stacks` (a repository-scoped association), never touching commits/stacks outside the authenticated repository:
```ruby
stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }
```
```ruby
stacks.where(branch: params.check_suite.head_branch).each do |stack|
  stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
end
``` [3](#0-2) [4](#0-3) 

- `Status#replicate_from_github!` and `Commit#create_status_from_github!` do not re-validate repository ownership either; they simply persist the state/context onto the given `Commit`. [5](#0-4) 
- Once the `Status` row exists on the shared `Commit`, `MergeRequest#all_status_checks_passed?` recomputes over `head.statuses_and_check_runs` via `StatusChecker` (a `Status::Group` subclass) with no repository check either: [6](#0-5) 
- `ProcessMergeRequestsJob` then calls `merge_request.all_status_checks_passed?` and, if true, `merge_request.merge!`, which calls `stack.github_api.merge_pull_request` for the *victim's* stack and repository. [7](#0-6) [8](#0-7) 

Exploit flow: attacker owns a repository under a GitHub organization for which Shipit has a legitimately configured GitHub App (this is a supported, documented deployment pattern — "Using Multiple GitHub Applications" — one Shipit instance serving several distinct orgs each with independent `webhook_secret`s). GitHub will sign the attacker's own `status` webhook with that org's real, valid `webhook_secret`, so `verify_signature` passes without the attacker knowing any secret belonging to the victim's organization. The attacker sends `sha` equal to the victim `MergeRequest`'s `head.sha` (achievable if the attacker can produce/replicate an identical commit object, as stated in the precondition), `state: success`, and `context` equal to the victim's required status name. `StatusHandler#process` writes the `Status` onto the victim's shared `Commit` row purely because the SHA matches, with no verification that the authenticated repository is the one that owns that commit.

### Impact Explanation
An attacker who controls any repository in any organization configured on a shared Shipit instance can inject fabricated `success` statuses onto commits belonging to a completely different tenant's stack, provided they can produce a commit with the same SHA as the victim's PR head. This can push a pending `MergeRequest` past `all_status_checks_passed?` and trigger `MergeRequest#merge!`, i.e., an unauthorized merge of a pull request in a repository the attacker never authenticated against. This matches the "Critical: a payload for one repository mutating another's stack/commit ... or an unauthorized ... merge" category. The blast radius is every stack sharing the Shipit instance across all configured GitHub organizations/apps, and the attack is repeatable per targeted `MergeRequest`.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub App/organization (a documented, supported configuration), (2) the attacker controls at least one repository in one of those configured organizations, (3) the attacker can engineer or reuse a commit with a SHA identical to the victim's PR head — this is the binding constraint and is nontrivial in general (SHA is content-derived, including full commit metadata), but is explicitly granted as a precondition in the audit scenario (e.g., a fork or reused tree/commit). Given the precondition holds, the rest of the exploit requires no secrets, no session, and no privileged role — only the ability to author a real GitHub webhook event from an unrelated, attacker-owned repository within a co-tenanted org.

### Recommendation
Scope `StatusHandler#process` (and any other handler operating on `Commit`/`Status`/`CheckRun` by bare SHA) to the repository authenticated by the webhook signature, mirroring the pattern already used in `PushHandler` and `CheckSuiteHandler`: restrict the query to `stacks` (or `Repository.find_by(full_name: params.repository.full_name)&.stacks`) before resolving commits, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, or add an explicit check `commit.stack.repository.full_name == params.repository.full_name` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar):
1. Create `Stack` A with `Repository` `"victim-org/app"` and a `MergeRequest` in `pending` state whose `head` is a `Commit` with `sha = "deadbeef..."`.
2. Create `Stack`/`Repository` B (`"attacker-org/app"`), unrelated to Stack A, with no `Commit` sharing that sha in the fixture initially (simulate attacker-controlled repo).
3. Directly invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => 'deadbeef...', 'state' => 'success', 'context' => '<victim-required-context>', 'repository' => { 'full_name' => 'attacker-org/app', 'owner' => { 'login' => 'attacker-org' } })`, bypassing only the outer signature check (as the controller test suite already does via `GithubHook.any_instance.stubs(:verify_signature).returns(true)`), to isolate the handler-level authorization gap.
4. Assert:
   - `merge_request.head.statuses.where(context: '<victim-required-context>', state: 'success').exists?` is `true` (the write happened on Stack A's commit despite the webhook's `repository.full_name` being `attacker-org/app`, not `victim-org/app`).
   - `merge_request.reload.all_status_checks_passed?` is `true`.
   - Assert the equality that should have blocked this never held: `merge_request.stack.github_repo_name != 'attacker-org/app'` while the status was nonetheless written.
