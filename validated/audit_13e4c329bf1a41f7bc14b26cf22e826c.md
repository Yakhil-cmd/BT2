### Title
Shared, stack-unbound CCMenu API token grants read access to every stack, not just the one it was minted for - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints a token from a single `ApiClient` record shared by all of a user's CCMenu widgets (`find_or_create_by!(creator: current_user, name: 'CCMenu Client')`), and that client is created without a `stack` association, so its `read:stack` permission is never scoped to any particular stack. Fetching the CCMenu URL for stack A and then for stack B returns byte-identical tokens, and either URL authenticates against `Api::CCMenuController#show` for any stack, not just the one embedded in the URL path.

### Finding Description
The intended binding is: `token minted while fetching stack A's CCMenu URL` should authorize `GET /stacks/.../A/ccmenu.xml` and nothing else — i.e. `authorized_scope(token) == { A.id }`.

The actual code: [1](#0-0) 
creates/finds the same `ApiClient` for a given `current_user` regardless of `stack`, and never sets `stack:` on it. As a result: [2](#0-1) 
`client.stack_id` is `nil` for every CCMenu client ever created.

On the read side, `Api::BaseController#stacks` is supposed to restrict a scoped client to its own stack: [3](#0-2) 
Since `current_api_client.stack_id?` is `false` for the CCMenu client, this resolves to `Stack.all` — the client is not restricted to any stack. Worse, `Api::CCMenuController` doesn't even use this `stacks` helper; it defines its own `stack` method that resolves directly from `params[:stack_id]` with no scoping at all: [4](#0-3) 
The only permission check is the generic, non-stack-specific `require_permission :read, :stack`: [5](#0-4) 
which is satisfied by any client whose `permissions` array includes `read:stack` — true for the shared CCMenu client, for every stack.

So both halves of the claimed equality hold: `token_A == client.authentication_token == token_B` (same `ApiClient#id`, same message-verifier signature) because the client row is shared across stacks, and `authorized_scope(token) == Stack.all` because the client's `stack_id` is never set and `CCMenuController#stack` doesn't consult `stacks` at all. Neither `verify_signature`, `force_github_authentication`, nor any model validator intervenes here — this is a same-host, authenticated-API-token flow with no webhook signature involved.

Attack flow: the operator (current_user) fetches the CCMenu URL for stack A via `POST/GET` to the `fetch` route and embeds it in a public/unauthenticated CI dashboard widget. Later, they (or anyone) fetches the CCMenu URL for stack B under the same account. Both URLs carry the same `token` query parameter. Anyone who has captured stack A's URL can substitute stack B's (or any other stack's) `stack_id` into the URL path and successfully call `ccmenu.xml`, reading that stack's latest deploy/rollback status — even for stacks that were never intentionally shared via CCMenu.

### Impact Explanation
An attacker in possession of one leaked CCMenu URL (which is explicitly designed to be pasted into third-party, unauthenticated CI widgets) gains unauthenticated read access to the deploy/rollback status of every stack accessible on the Shipit instance, not just the one the URL nominally names. This is a horizontal privilege violation: `read:stack` permission granted for one stack's monitoring widget silently covers all stacks. This matches the "High — unauthenticated read of stack state" impact category. The blast radius grows over time as the same user fetches more CCMenu URLs (though even a single fetch already grants `Stack.all` access due to `stack_id` never being set).

### Likelihood Explanation
No special privileges are needed beyond already having (or having leaked) a CCMenu URL that a legitimate operator generated and pasted into a public/unauthenticated dashboard — which is the intended distribution mechanism for this feature. No GitHub secrets, webhook signatures, or session are required; the token is a self-contained bearer credential verified purely by `Shipit.api_clients_secret`. The bug is deterministic and requires no race condition or timing — every CCMenu client for a given user is unrestricted to `Stack.all` from creation.

### Recommendation
Scope the CCMenu `ApiClient` per stack: create/find it as `find_or_create_by!(creator: current_user, stack: stack, name: "CCMenu Client for #{stack.to_param}")` and set the `stack:` association so `current_api_client.stack_id?` is true and `Api::BaseController#stacks` restricts to that one record. Additionally, fix `Api::CCMenuController#stack` to use the inherited `stacks` scope (`stacks.from_param!(params[:stack_id])`) instead of an unscoped `Stack.from_param!`, closing the bypass even for other scoped clients.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (conceptual)
test "CCMenu token is shared and unscoped across stacks" do
  user = shipit_users(:walrus)
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack

  session[:user_id] = user.id

  get :fetch, params: { stack_id: stack_a.to_param }
  token_a = URI(JSON.parse(response.body)['ccmenu_url']).query.then { |q| Rack::Utils.parse_query(q)['token'] }

  get :fetch, params: { stack_id: stack_b.to_param }
  token_b = URI(JSON.parse(response.body)['ccmenu_url']).query.then { |q| Rack::Utils.parse_query(q)['token'] }

  assert_equal token_a, token_b # same ApiClient, same token -> binding violated

  # Prove stack-A's token authenticates against stack-B's ccmenu.xml endpoint
  get "/stacks/#{stack_b.repository.owner}/#{stack_b.repository.name}/#{stack_b.environment}/ccmenu.xml",
      params: { token: token_a }
  assert_response :success
end
```
This demonstrates: (1) tokens minted for distinct stacks under the same user are byte-identical, and (2) a token embedded in stack A's public URL successfully authenticates a read of stack B's CCMenu XML, confirming the broken binding.
