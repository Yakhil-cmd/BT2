### Title
Denial of Service via unhandled exception on duplicate-output check in private payment validation - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` checks whether the referenced public output(s) for a private-asset payment already exist by querying the `outputs` table, and unconditionally `throw`s a JavaScript `Error` if more than one row is returned. This throw happens inside an asynchronous `conn.query()` callback, so it cannot be caught by any synchronous `try/catch` in the caller chain, causing an uncaught exception at the process level for any node (full or light wallet) that processes a maliciously/incorrectly shaped private payment chain.

### Finding Description
The relevant code: [1](#0-0) 

For a divisible (non-`fixed_denominations`) private asset, the duplicate-check query is:
```
SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?
```
with no `output_index` filter [2](#0-1) . If the referenced payment message legitimately has more than one output for that asset/denomination in the `outputs` table (e.g., a normal divisible payment message with a recipient output plus a change output, both hidden/private and already written to the `outputs` table by the normal unit-writing path), the query returns more than one row, and the code executes:
```js
if (rows.length > 1)
    throw Error("more than one output "+sql+' '+params.join(', '));
``` [3](#0-2) 

This is analogous to the RuoYi bug class: an operation that assumes a uniqueness invariant which can actually be violated by an ordinary/attacker-influenced input, and instead of handling the violation gracefully, the code fails in a way that disrupts availability rather than returning a controlled error.

`validateAndSavePrivatePaymentChain()` is invoked whenever a private payment chain arrives from a private-payment counterparty (a wallet peer sending a chat/private-payment device message), i.e., from an untrusted, unprivileged party as covered by the in-scope surfaces ("private payment chains"). Because the throw occurs inside the `db.query(...)` callback — an asynchronous continuation — it is not caught by the `try { ... } catch` blocks that protect synchronous validation paths elsewhere in the codebase; it propagates as an uncaught exception. Unless something further up (e.g. `process.on('uncaughtException')`) intercepts it, this crashes the running node process, denying service to the wallet/node for all subsequent operations until manually restarted.

### Impact Explanation
An uncaught exception thrown from an async DB callback can crash the full Node.js process, taking down the entire wallet or hub instance — a hard denial of service, not merely a failed validation of one message. Since this can be triggered by any counterparty capable of sending a private-payment chain (a normal wallet-to-wallet interaction, not requiring elevated trust), the impact matches "a network unable to confirm new units" / node-availability loss for the affected instance, satisfying the required unauthorized-impact bar (functional DoS of a reachable path).

### Likelihood Explanation
Reaching the `rows.length > 1` branch does not require exotic conditions: a normal divisible-asset private payment message with a change output stored alongside the recipient output in the same `unit`/`message_index` is sufficient to produce two rows matching the query, since the query has no `output_index` restriction for divisible assets. A private-payment counterparty controls the shape of the chain it sends (unit, message_index, payload), making this trivially and repeatably triggerable without any special privilege — likelihood is high.

### Recommendation
- For divisible assets, do not assume exactly one row can match; either add filtering that uniquely identifies the specific output being claimed (matching against the specific claimed output in `payload.outputs`, as already attempted afterward), or iterate `rows` instead of assuming/enforcing `rows.length <= 1`.
- Replace the `throw Error(...)` with `transaction_callbacks.ifError(...)` so that an unexpected duplicate count degrades to a graceful validation failure/rollback instead of crashing the process.
- Add defensive handling (`try/catch` plus `ifError`) around the whole duplicate-check/comparison block so any unexpected internal error is surfaced as a controlled validation failure rather than an uncaught exception.

### Proof of Concept
1. Alice and Bob complete a normal transaction using a private (non-fixed-denomination) asset where the payment message contains two outputs in the same `message_index` for that asset — e.g., a payment output to Bob and a change output back to Alice — which get written into the `outputs` table with hidden/blinded addresses as part of normal unit processing.
2. An attacker (or Alice herself, replaying/crafting a chain) sends Bob's wallet a private payment chain (`arrPrivateElements`) whose head element references that same `unit`/`asset`/`message_index`.
3. `validateAndSavePrivatePaymentChain()` runs the duplicate-check query at `private_payment.js:62-69`, which — lacking an `output_index` filter for divisible assets — returns both output rows.
4. The code hits `private_payment.js:74-75` and throws an uncaught `Error` inside the async query callback, crashing the node process and denying service.

Note: I was unable to fully trace whether any global `uncaughtException` handler in `network.js` (referenced there) intercepts and gracefully recovers from this specific throw before process termination; this could not be fully confirmed within the available context, so the exact severity (process crash vs. contained failure) should be verified directly in `network.js`'s `uncaughtException` handling and in the runtime entry points that call `validateAndSavePrivatePaymentChain`.
