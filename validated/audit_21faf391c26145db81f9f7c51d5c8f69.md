### Title
Insufficient reward-per-token precision in `pallet-asset-rewards` causes reward truncation/loss - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards`'s `reward_per_token` computation uses a fixed scaling factor of only `4096` (`PRECISION_SCALING_FACTOR`) rather than a high-precision fixed-point type (e.g. `FixedU128`, base `1e18`, as used elsewhere in the codebase such as nomination-pools' `RewardCounter`). [1](#0-0)  When `total_tokens_staked` is large relative to `reward_rate_per_block * blocks_elapsed * 4096`, integer division truncates the incremental reward to zero, and because `last_update_block` is unconditionally advanced to the current block on every update, the rewards accrued for that period are permanently lost — never carried forward and never distributed to any staker. This mirrors the root cause identified in the Yieldoor report: an interest/reward accrual function using a coarse fixed-point representation that loses precision when principal (`total_tokens_staked` here, analogous to `reserve.totalBorrows`) is large relative to the per-period increment.

The numerator is scaled only by `4096` (a 12-bit fixed-point precision), far coarser than the `1e18` scale used by `FixedU128`-based reward accounting elsewhere in the codebase (e.g., nomination-pools' `RewardCounter`, which the code's own accuracy comments treat as safe precisely because of its `10^18` base). [4](#0-3)  If `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked`, the division truncates to `0`, so `reward_per_token_stored` does not advance for that update — yet `last_update_block` is unconditionally bumped to the current block regardless of whether any reward was actually recorded. Any un-accrued reward for the elapsed blocks is silently and permanently discarded; it is not carried over to the next update because the next call's `rewardable_blocks_elapsed` is computed relative to the new `last_update_block`, not the block where truncation occurred.

`total_tokens_staked` is directly attacker-influenced: any signed account can call the permissionless `stake` extrinsic to increase it. [5](#0-4)  `stake` first calls `update_pool_and_staker_rewards` (computing `reward_per_token` against the *old*, smaller `total_tokens_staked`), and only afterward increases `total_tokens_staked`. But subsequent calls (by the same or other callers, including `harvest_rewards`/`unstake`/further `stake` calls) will then compute `reward_per_token` divided by the new, inflated `total_tokens_staked`, causing truncation to zero as long as that inflated stake remains.

### Impact Explanation
This is directly analogous to the Yieldoor Medium-severity finding: legitimate stakers/lenders lose real, measurable yield because interest/reward accrual silently rounds to zero when the "principal" denominator is large relative to the per-period reward numerator, and the loss is not deferred/corrected but discarded outright since `last_update_block` always advances. The effect scales with pool activity frequency (the more frequently `stake`/`unstake`/`harvest_rewards` are called — trivially triggerable by anyone, cost = base fee only — the more reward periods get truncated to zero) and with the ratio of staked-asset decimals/amount to `reward_rate_per_block`. This causes reduced or entirely withheld rewards for genuine stakers, a Medium-severity integrity/economic-loss issue consistent with the referenced report's classification, not theft/unbacked issuance.

### Likelihood Explanation
Reachability is via a fully permissionless, unprivileged extrinsic path (`stake`/`unstake`/`harvest_rewards`), no governance or privileged role required. [6](#0-5)  Likelihood depends on runtime-specific configuration of `T::Balance` decimals and typical `reward_rate_per_block`/`total_tokens_staked` magnitudes for a given deployed pool; pools with high-decimal staked assets and modest reward rates (analogous to wbtc in the original report) are more susceptible. This is config/parameter-dependent rather than universally exploitable across all possible pool configurations, which is why I present it as Medium rather than a higher severity.

### Recommendation
Increase `PRECISION_SCALING_FACTOR` substantially (e.g., to `1e18`-scale fixed-point arithmetic, consistent with `FixedU128`/`RewardCounter` used in nomination-pools) or track/accrue a remainder across updates so that sub-unit rewards are not permanently lost when `last_update_block` advances. Alternatively, skip advancing `last_update_block` (or persist the un-applied remainder) when `reward_per_token` would truncate to no observable increase.

### Proof of Concept
No executable local reproduction was run (ask-only investigation, no filesystem/terminal access in this mode). The mechanism is demonstrated by code inspection: `reward_per_token`'s integer division by `pool_info.total_tokens_staked` after scaling only by `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) [7](#0-6)  combined with unconditional `last_update_block` advancement in `update_pool_rewards` [8](#0-7)  and attacker-reachable `total_tokens_staked` inflation via the permissionless `stake` call [9](#0-8)  together establish the truncation path. A concrete numeric PoC (analogous to the Yieldoor report's worked example) would require selecting a pool's actual `reward_rate_per_block`, `T::Balance` decimals, and stake sizes to show `reward_rate_per_block.ensure_mul(blocks).ensure_mul(4096) < total_tokens_staked`; this arithmetic check was not executed against a live runtime/test harness in this session, so I flag this PoC step as unverified/not run rather than claiming a completed test result.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()

					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
