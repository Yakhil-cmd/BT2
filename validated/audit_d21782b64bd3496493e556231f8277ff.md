### Title
Race between async `restore_unreviewed_stop_state` and next-turn `handle_user_prompt_submit` re-baselines past unreviewed dangerous edits, causing them to be silently dropped from the Stop-hook review set - (File: plugins/security-guidance/hooks/diffstate.py)

### Summary
`restore_unreviewed_stop_state` re-arms `touched_paths` after a transient Stop-hook failure but only restores `baseline_sha` when the state's current `baseline_sha` is empty. If the asynchronous Stop hook's restore call loses a race against the next turn's `handle_user_prompt_submit` (UPS), UPS re-baselines to a fresh `capture_git_baseline` snapshot that already includes the unreviewed dangerous edit, and the subsequent restore call then leaves that newer baseline in place while merely re-adding the file path to `touched_paths`. On the next Stop fire, `compute_v2_review_set` intersects `dirty_now` with `changed_since` (computed against the now-advanced baseline), which no longer shows the dangerous file as changed, so it is dropped from the review set despite being present in `touched_paths`.

### Finding Description
`consume_stop_state` (plugins/security-guidance/hooks/diffstate.py:74-113) snapshots and clears `touched_paths` under a lock when Stop begins. If Stop then exits early for a transient reason — `ensure_anthropic_reachable()` failing or an LLM HTTP error — `restore_unreviewed_stop_state` (diffstate.py:116-137) is called to "put consumed touched_paths back so the next Stop reviews them" and to keep the UPS preservation guard armed, per its own docstring warning: "if Stop then exits early... the next UPS would see an empty list, fall through the preservation guard, and re-baseline past the unreviewed edits." [1](#0-0) 

The Stop hook is explicitly asyncRewake (runs in the background after the model turn ends), and `consume_stop_state`'s own docstring acknowledges "UPS overwrites of baseline_sha after this snapshot are invisible to this Stop fire." [2](#0-1)  This means a fast next user turn can invoke `handle_user_prompt_submit` (security_reminder_hook.py:446-515) before the failing Stop's `restore_unreviewed_stop_state` call executes. At that moment `state["touched_paths"]` is already `[]` (cleared by `consume_stop_state`), so UPS's preservation guard `if state.get("touched_paths") and state.get("baseline_sha")` is false, and UPS proceeds to overwrite `state["baseline_sha"]` with a freshly captured `capture_git_baseline(cwd)` SHA that already reflects the dangerous, not-yet-reviewed edit. [3](#0-2) 

When the delayed `restore_unreviewed_stop_state` call finally runs, it merges the dangerous file path back into `touched_paths` (so it is not lost from that list), but its baseline-restore guard `if baseline_sha and not state.get("baseline_sha")` is false because UPS already wrote a baseline — so the stale-but-safe pre-edit `baseline_sha` (`snap_baseline`) is never restored. [4](#0-3) 

On the next Stop fire, `compute_v2_review_set` computes `changed_since = _git_name_only(repo, baseline_sha)` against this newer baseline that already contains the dangerous edit, and intersects it with `dirty_now` (git status vs HEAD). Since the dangerous file's content matches the new baseline, it is excluded from `changed_since`, so `review_set = dirty_now & changed_since` drops it even though it is present in `touched_paths`. [5](#0-4)  The Stop hook then either finds an empty review set (`_skip(9, ...)`) or reviews a smaller set that omits the dangerous file. [6](#0-5) 

This breaks the stated invariant that the review set must stay bound to the right baseline and touched paths: `touched_paths` correctly still names the file, but `baseline_sha` has silently advanced past it, so the git-diff-derived review set treats the dangerous change as already-known/old and skips it.

### Impact Explanation
A dangerous edit made during a turn where the Stop-hook LLM call transiently fails (Anthropic API unreachable or HTTP error — a routine, attacker-uninfluenced but reliably reproducible condition, or one an attacker embedding malicious repo content can wait for/retry against) can permanently escape the git-diff-derived Stop review if the next turn starts quickly enough to race the async restore. This results in unauthorized local command execution / dangerous code changes being introduced without the security-guidance plugin ever presenting them for Claude's approval/deny gating, matching the "Unauthorized local command execution that bypasses Claude Code approval or deny controls" impact category.

### Likelihood Explanation
Requires: (1) a transient Stop-hook failure path that triggers `restore_unreviewed_stop_state` (already a documented/expected occurrence — API unreachable or HTTP error), and (2) the next turn's `UserPromptSubmit` firing before the async Stop hook's restore call completes. Given Stop is explicitly asyncRewake and the codebase's own comments acknowledge this exact race for `baseline_sha` overwrites, the timing window is real and not contrived; rapid successive turns are common in agentic/automated harnesses. No elevated privileges are needed — only ordinary use of the tool combined with an unlucky (or attacker-encouraged, e.g. via prompts that induce quick follow-up turns) timing window.

### Recommendation
In `restore_unreviewed_stop_state`, always restore `baseline_sha` to the earlier (`snap_baseline`) value when it is an ancestor of (or equal to/older than) the current `state["baseline_sha"]`, rather than only filling it in when currently unset — or, simpler, always prefer the older of the two baselines so no unreviewed edit's content can already be "inside" the effective baseline. Alternatively, extend the UPS preservation guard to also check a monotonic "pending restore" flag/generation counter set by `consume_stop_state` and cleared only by `restore_unreviewed_stop_state`, so UPS cannot re-baseline while a Stop restore is still outstanding.

### Proof of Concept

3. Call `consume_stop_state(session_id)` to snapshot (`touched_paths=[dangerous_file]`, `baseline_sha=sha0`) and clear `touched_paths` on disk — simulating Stop having started but not yet finished.
4. Before calling `restore_unreviewed_stop_state`, simulate the race: call `handle_user_prompt_submit`-equivalent logic directly — with `touched_paths` empty on disk, it re-baselines `state["baseline_sha"]` to `sha1 = capture_git_baseline(cwd)` (now including the dangerous file's content).
5. Now call `restore_unreviewed_stop_state(session_id, [dangerous_file], sha0)` (simulating the delayed Stop's restore-on-failure call).
6. Assert `load_baseline_sha(session_id) == sha1` (baseline was NOT reverted) while `touched_paths` on disk contains `dangerous_file`.
7. Call `compute_v2_review_set(cwd, sha1, head_at_capture, {})` and assert `dangerous_file` is **absent** from the returned `review_paths` — demonstrating the review set no longer contains the dangerous file despite it being in `touched_paths`, violating the expected invariant that it should remain reviewable.
8. As a regression guard for the fix, assert that after the fix, `load_baseline_sha(session_id) == sha0` (or an equivalently older/safe baseline) and that `compute_v2_review_set` includes `dangerous_file` in `review_paths`.

```python
def restore_unreviewed_stop_state(session_id, paths, baseline_sha):
    """Put consumed touched_paths back so the next Stop reviews them.

    consume_stop_state cleared touched_paths on disk; if Stop then exits
    early for a transient reason (CCR API unreachable, Haiku HTTP error)
    the next UPS would see an empty list, fall through the preservation
    guard, and re-baseline past the unreviewed edits. Restoring keeps the
    guard armed. Prepend+dedupe so any concurrent next-turn PostToolUse
    appends survive.
    """
    if not paths:
        return

    def _restore(state):
        existing = state.get("touched_paths", [])
        merged = list(dict.fromkeys(list(paths) + list(existing)))
        if len(merged) > 200:
            merged = merged[:200]
        state["touched_paths"] = merged
        if baseline_sha and not state.get("baseline_sha"):
            state["baseline_sha"] = baseline_sha
    with_locked_state(session_id, _restore)
```
