### Title
Unscoped CCMenu API client lets a token minted for one stack read the CI/deploy status of every stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints a per-user `ApiClient` intended to grant `read:stack` access to exactly the requesting stack's CCMenu/CCTray status feed, but it never binds that client to a `stack_id`, and `Api::CCMenuController` bypasses the normal client-to-stack scoping used everywhere else in the API. The result is that a signed token meant only for `Stack A`'s public build-status badge is honored for `Stack B`, `Stack C`, ... any stack, breaking the binding "stack the token authorizes" == "stack the token touches."

### Finding Description
The CCMenu feature is designed to hand out a durable, unauthenticated-looking token embedded in a URL (used by CI-status widgets / CCTray clients) that is expected to only reveal the state of the one stack it was generated for: [1](#0-0) 

Two things break the intended per-stack scope:

1. `client` is looked up/created with `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — the finder key is only `creator` + a fixed `name`, not `stack:`. `stack:` only appears inside `create_with`, so it's applied on first creation but is not part of the lookup key. Every subsequent call to `/ccmenu_url` for *any* stack by the same user returns the very same `ApiClient` record and the very same `authentication_token`, regardless of which stack was requested. [2](#0-1) 

2. `Api::CCMenuController` overrides the base controller's stack-scoping helper. In the normal API flow, `Api::BaseController#stack` restricts lookups to `stacks`, which itself is filtered to `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`: [3](#0-2) 

But `Api::CCMenuController#stack` redefines this to look up the stack directly from the request param, completely skipping the `stacks` scoping/allow-list: [4](#0-3) 

Because the controller only checks the generic permission `read:stack` (`require_permission :read, :stack`, line 6 of the same file) and never verifies that `current_api_client.stack_id` (if set) matches `params[:stack_id]`, any valid CCMenu token — even one whose `ApiClient.stack_id` happens to be set to a *different* stack, or one that is unset entirely because of bug (1) — can be replayed against `/api/1/stacks/:stack_id/ccmenu` for an arbitrary `stack_id` and will return that stack's deploy/build data.

The equality binding that should hold: `ApiClient#stack_id (the stack the token authorizes)` == `params[:stack_id] (the stack the token is used to read)`. Both `CCMenuUrlController#client`'s incomplete `find_or_create_by!` key and `Api::CCMenuController#stack`'s bypass of the `stacks` scope break this binding.

### Impact Explanation
An attacker who obtains one legitimate CCMenu URL (these are designed to be embedded in third-party CI dashboards/CCTray clients, i.e., shared outside of the Shipit session boundary and not treated as secret in the same way as an API key) can use its `token` query parameter to query `/api/1/stacks/:any_stack_id/ccmenu` for every other stack in the Shipit instance, obtaining deploy status, last build outcome, and stack existence for repositories the token was never meant to expose. This matches the "unauthenticated read of stack state / deploy output" High-impact category: the disclosure surface silently grows from "1 stack" to "all stacks in the installation" without any additional secret or privilege.

### Likelihood Explanation
Likelihood is moderate: it requires only possession of one previously-issued CCMenu URL (which, by design, is meant to be pasted into external CI dashboards, README badges, or CCTray tools, i.e., is far more likely to leak than a Shipit session or a purpose-built API client credential), plus knowledge/guessing of other stacks' `to_param` identifiers (repo `owner/name/environment`), which are often predictable or discoverable via the public Shipit UI/API index. No signature forgery, private key, or session is needed — only replay of an existing, intentionally-distributed token against a different resource id.

### Recommendation
- In `CCMenuUrlController#client`, include `stack:` in the `find_or_create_by!` lookup key (not just `create_with`), so a distinct `ApiClient` is minted per (`creator`, `stack`) pair.
- In `Api::CCMenuController`, remove the private `stack` override and use the inherited, scoped `stacks.from_param!(params[:stack_id])` from `Api::BaseController` so the client's bound `stack_id` (when present) is enforced, consistent with every other API controller.
- As defense in depth, explicitly assert `current_api_client.stack_id.blank? || current_api_client.stack_id == stack.id` before rendering CCMenu data.

### Proof of Concept
1. User with access to `Stack A` visits `/stacks/A/settings` and triggers `GET /A/ccmenu_url` → server calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: user, name: 'CCMenu Client')`, creating client `C1` with `stack_id = A.id`, returning a signed `token`.
2. The same user (or anyone who obtains the URL from step 1) requests `GET /stacks/B/ccmenu_url` for an unrelated `Stack B` they should not be able to read. Because the `find_or_create_by!` lookup key is only `(creator, name)`, the existing client `C1` (bound to `A`) is returned again, and its unchanged `token` is embedded in the new URL for `B`.
3. Using either token, an attacker calls `GET /api/1/stacks/B/ccmenu?token=<C1's token>` (or even `GET /api/1/stacks/<any-other-stack>/ccmenu?token=<C1's token>`). `Api::CCMenuController#stack` resolves the stack directly from `params[:stack_id]` without checking it against `C1.stack_id`, so the request succeeds and returns `Stack B`'s (or any other stack's) latest deploy/build status in the CCTray XML response — data the token was never intended to expose.

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
