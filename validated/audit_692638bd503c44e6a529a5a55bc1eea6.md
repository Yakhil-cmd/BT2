### Title
Cross-organization signature/target binding break in `WebhooksController` enables forged `status` events to unblock CI-gated deploys on repositories the attacker does not control - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the HMAC signature against based on the attacker-controlled `repository.owner.login` (or `organization.login`) field in the JSON body: `Shipit.github(organization: repository_owner)`. Nothing binds that verified organization identity to the entity actually mutated by the event handlers, which instead act on whatever `repository.full_name` (or, in the `status` handler, just `sha`) is present in the same attacker-controlled body. This is the same class of bug as H-16: the field the signature "covers"/authorizes (the organization used to select the secret) is not the field the write actually targets, so an attacker who satisfies verification for one namespace can cause writes against a different one.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is read straight from the JSON payload (`repository.owner.login`, falling back to `organization.login`). `Shipit.github_app_config`/`GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) unconditionally returns `true` when no `webhook_secret` is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
Shipit explicitly supports (and documents in `docs/setup.md` / `config/secrets.development.example.yml`) a multi-organization configuration where `webhook_secret` is optional per organization. Whenever any configured organization in a Shipit instance has no `webhook_secret` (a documented, supported state), signature verification for that organization passes unconditionally for any payload body, no matter its contents.

After `verify_signature` passes, `create` re-parses the same attacker-controlled body and dispatches it to handlers (`app/controllers/shipit/webhooks_controller.rb:10-15`). The handlers derive the entity to mutate from different, independently attacker-controlled fields of that same body:
- `Handler#stacks`/`#repository_name` use `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), used by `PushHandler`, all `PullRequest::*Handler`s, etc.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) doesn't even scope by repository - it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, matching purely on commit SHA across the entire Shipit database, spanning all stacks/repositories/organizations hosted by the instance.

Nothing ties `repository.owner.login` (used to pick the verifying secret) to `repository.full_name`/`sha` (used to select the mutated record). An attacker who can satisfy the signature check for organization A (because A has no `webhook_secret` configured, or because they legitimately control A's app/secret) can submit a `status` (or `push`/`pull_request`) payload whose `repository.full_name`/`sha` references a completely different, unrelated organization/repository B hosted on the same Shipit instance, and the handler will happily write to B's commit/stack.

### Impact Explanation
Via `StatusHandler`, an attacker can create arbitrary commit statuses (`commit.create_status_from_github!`, `app/models/shipit/commit.rb:165-169`) for any commit SHA tracked by any stack on the instance, as long as they can pass signature verification for *some* configured organization (trivially true if that org lacks a `webhook_secret`, per the documented optional setting). `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) gate deploys/continuous delivery on status success (`ci.require`/`success?`). Forged "success" statuses for a targeted victim repository's commit can unblock/trigger an unauthorized deploy (`stack.schedule_merges`, `ContinuousDeliveryJob`) on a stack the attacker has no legitimate GitHub relationship to. This satisfies the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Requires only that the Shipit deployment configures multiple GitHub organizations (a documented, supported configuration) and that at least one configured organization has no `webhook_secret` set - itself documented as optional (`docs/setup.md` webhook secret step says "(optional)"; `config/secrets.development.example.yml` ships with `webhook_secret: # nil`). No repository write access, session, or `ApiClient` token is required; the `/webhooks` endpoint is unauthenticated apart from the (bypassable, per-org) signature check.

### Recommendation
Bind the verified signing identity to the entity mutated: require the organization/owner used to select and verify the webhook secret to exactly match the owner of `repository.full_name` referenced by the payload before any handler executes, and reject (422) on mismatch. Additionally, scope `StatusHandler` (and any other handler) lookups by repository/stack, not solely by commit SHA, and consider making `webhook_secret` mandatory for every configured organization rather than optional.

### Proof of Concept
1. Configure Shipit with multiple GitHub organizations, e.g. `attacker-org` (no `webhook_secret`) and `victim-org` (has a secret, hosts a stack tracking commit `deadbeef...`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; since `attacker-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header value/content.
4. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` and calls `create_status_from_github!`, creating a "success" status on the victim's commit even though the attacker has no relationship to `victim-org` and never satisfied `victim-org`'s webhook secret.
5. If `victim-org`'s stack requires that CI context and has continuous deployment enabled, this forged status can trigger an unauthorized deploy. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
