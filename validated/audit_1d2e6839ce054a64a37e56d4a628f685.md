The only SQL query construction in this codebase is in the pallet-revive Ethereum JSON-RPC proxy's SQLite indexer, `substrate/frame/revive/rpc/src/receipt_provider.rs`. All dynamic query construction there uses `sqlx::query!`/`QueryBuilder::push_bind` for user/attacker-influenced values (filter addresses, topics, block hashes, block numbers), which are properly parameterized rather than string-concatenated [1](#0-0) . The two places using raw `format!` construct only a fixed number of `?` placeholders based on array length (not attacker-controlled content) for bulk-delete statements, with all actual values still bound via `.bind()` [2](#0-1) . This is not a SQL-injection-prone pattern.

Beyond that, this component is an off-chain RPC/indexing service, not a runtime entry point reached by a signed extrinsic, XCM message, or contract call — FRAME storage itself is trie-based key-value and has no SQL query surface reachable from consensus-critical dispatch. There is no demonstrable analog satisfying the report's bug class (blind SQL injection via unsanitized `orderBy`/`where` criteria reaching a real user-facing, fee-paying, state-mutating entry point) anywhere else in the scanned production code.

		&self,
		filter: Option<Filter>,
		resolve_block_number: impl Fn(BlockNumberOrTag) -> Fut,
	) -> anyhow::Result<Vec<Log>>

		Fut: Future<Output = anyhow::Result<U256>>,
	{

		let filter = filter.unwrap_or_default();

		match filter.block_option {
			FilterBlockOption::AtBlockHash(hash) => {
				qb.push(" AND block_hash = ").push_bind(hash.as_slice().to_vec());
			},
			FilterBlockOption::Range { from_block, to_block } => {
				let from_block =
					OptionFuture::from(from_block.map(&resolve_block_number)).await.transpose()?;

					},

						anyhow::bail!("invalid block range params");
					},
					(Some(from_block), Some(to_block)) if from_block == to_block => {
						qb.push(" AND block_number = ").push_bind(from_block.as_u64() as i64);
