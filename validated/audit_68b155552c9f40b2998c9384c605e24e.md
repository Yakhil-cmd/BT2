## Title
Cross-organization forgery of commit CI status via `StatusHandler` global `sha` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization secret to check the HMAC against using `repository_owner`, a value taken **from the attacker-supplied payload body itself** (`params.dig('repository','owner','login')`), rather than from any pre-established binding to the stack being acted on. `StatusHandler#process` then looks up the target `Commit` by `sha` **globally across the entire `Commit` table**, with no scoping to the organization/repository whose secret validated the signature. An attacker who controls (or has installed the Shipit GitHub App on) their own, unrelated repository can forge a `status` webhook that is correctly signed with their own org's `webhook_secret`, but whose `sha` matches a commit that also exists in a victim's tracked stack (trivial to obtain by forking/mirroring the victim's public repository, since git commit SHAs are content-derived and identical across clones/forks). This breaks the equality: `organization that authenticated the webhook == repository whose commit state is written`.

### Finding Description
- `WebhooksController#verify_signature` picks the app config via `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight out of the untrusted, attacker-controlled JSON payload: [1](#0-0) [2](#0-1) 
- The signature is verified with `HMAC-SHA1` using that org's `webhook_secret`: [3](#0-2) 
- Once verified, `WebhooksController#create` dispatches the parsed payload to all registered handlers for the event, with no further scoping to the org that was actually authenticated: [4](#0-3) 
- `StatusHandler#process` finds commits **by SHA alone**, with no `stack`/`repository` filter at all, and calls `create_status_from_github!` on whatever `Commit` rows match, across every stack in the Shipit installation: [5](#0-4) 
- `Commit#create_status_from_github!` persists the forged state directly as a real `Status` record tied to that commit/stack: [6](#0-5) 

Contrast this with `PushHandler` and `CheckSuiteHandler`, which correctly scope their lookups to `Repository.from_github_repo_name(repository_name).stacks` derived from the payload's `repository.full_name` field: [7](#0-6) [8](#0-7) [9](#0-8) 

`StatusHandler` is the only handler among these that omits this scoping — it neither checks `repository.full_name` from the payload nor restricts the query to commits belonging to a stack whose repository is owned by the organization whose secret validated the signature. Because git commit SHAs are content hashes that persist unchanged across `git clone`/fork operations, an attacker can:
1. Register/have a GitHub App installation on their own organization (obtaining a legitimate `webhook_secret` for that org, exactly as any GitHub App installer would).
2. Fork or otherwise obtain a local copy of the victim's public repository so they possess a commit with an **identical SHA** to one already tracked by the victim's Shipit stack.
3. Send a `status` webhook (`X-Github-Event: status`) with `repository.owner.login` set to their own org (so `verify_signature` selects and validates against their own webhook secret) and `sha` set to the victim's commit SHA, `state: "success"`.
4. `Commit.where(sha: params.sha)` matches the victim's `Commit` row (SHAs are effectively globally unique in practice) and a forged `success` status is written to it via `commit.create_status_from_github!(params)`.

### Impact Explanation
This is a High-severity finding under the rubric's "unauthenticated read of stack state" / authorization-escalation class, but here it is actually an **unauthenticated write** of stack state: an attacker with zero privileges on the victim repository/organization can inject arbitrary CI status entries (`success`, `failure`, with attacker-chosen `context`, `description`, `target_url`) onto commits belonging to a stack they do not own. `Status` records feed directly into `Commit#state`/`deployable?` and CI-gating logic used before merges and deploys (see `Commit.successful`, `deployable?` checks referenced by `app/models/shipit/commit.rb`), so a forged "success" status can be used to make an otherwise-failing or unreviewed commit appear CI-green, letting an attacker (or a compromised low-trust actor) push a merge/deploy of that commit through Shipit's CI gate without ever touching the victim's repository or webhook secret. This maps to the "escalation into stack authorization" impact bucket.

### Likelihood Explanation
Likelihood is high: the only prerequisite is installing/owning a GitHub App on any organization that Shipit is configured with (a normal, unprivileged, self-service action many Shipit deployments allow for arbitrary orgs), and forking a public target repository to obtain matching commit SHAs — both are trivial, unprivileged actions requiring no access to the victim's Shipit instance credentials, `ApiClient` tokens, or GitHub tokens.

### Recommendation
`StatusHandler#process` (and any other handler that queries by `sha` alone) must scope its lookup to commits belonging to stacks whose repository matches `payload.dig('repository','full_name')`/`repository_owner`, mirroring the pattern already used in `PushHandler`/`CheckSuiteHandler` via `Handler#stacks`/`#repository_name`. Additionally, `WebhooksController#verify_signature` should not rely purely on an attacker-suppliable field to select the verifying secret without cross-checking that the resulting authenticated organization actually owns the repository referenced elsewhere in the same payload before any handler is allowed to mutate records tied to that repository.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the cited code):
1. Attacker creates/owns GitHub org `attacker-org` and installs the Shipit GitHub App on it, obtaining `webhook_secret_attacker`.
2. Attacker forks victim's public repo `victim-org/app`, thereby possessing a commit with the exact same `sha` as a commit already tracked in the victim's Shipit stack for `victim-org/app`.
3. Attacker POSTs to `/webhooks`:
   - `X-Github-Event: status`
   - `X-Hub-Signature: sha1=<HMAC using webhook_secret_attacker>`
   - body: `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim commit sha>", "state": "success", "context": "ci/forged"}`
4. `verify_signature` resolves org `attacker-org` from the payload, validates successfully against `webhook_secret_attacker`.
5. `StatusHandler#process` executes `Commit.where(sha: "<victim commit sha>")`, matches the victim's commit (owned by `victim-org`), and calls `create_status_from_github!`, persisting a forged `success` status on the victim's stack's commit — despite the attacker never having interacted with `victim-org`'s repository, webhook secret, or Shipit credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
