### Title
Webhook Signature Verified Against `repository.owner.login` While Write Target Is Selected by an Unchecked `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook by looking up the per-organization GitHub App/secret using `repository.owner.login` (or `organization.login`) from the JSON body, but the handler that actually acts on the payload (e.g. `PushHandler`) selects which `Stack`/`Repository` to mutate using a *different* field of the same body: `repository.full_name`. Nothing ties these two fields together, so the "organization that authenticated" is never checked against the "repository that is written."

### Finding Description
`verify_signature` picks the GitHub App config used to validate `X-Hub-Signature` via: [1](#0-0) 
using [2](#0-1) 

In a multi-organization deployment (`github:` config keyed by org login, resolved via `github_app_config`): [3](#0-2) 
each organization has its own `webhook_secret`, so the signature is only proof that the request was signed by *some* organization's secret registered in Shipit — not that it concerns a repository belonging to that organization.

The event handler, however, never re-checks the owner used for authentication. It derives the write target purely from `repository.full_name`: [4](#0-3) 
and `PushHandler` uses that to look up stacks and trigger a sync/deploy pipeline: [5](#0-4) 

Because the whole raw body is HMAC-signed, an attacker cannot tamper with a message already signed by another organization's secret — but they *can* forge a brand-new payload themselves, signed with **their own organization's legitimately-known secret**, in which `repository.owner.login` = their own org (so signature verification passes) while `repository.full_name` = `"victim-org/victim-repo"`, a repository/stack that belongs to a completely different organization tracked in the same Shipit instance. `verify_signature` and `repository_name` never cross-check that the owner used to select the secret matches the owner encoded in `full_name`.

### Impact Explanation
This breaks the binding *"organization that authenticated == repository that is written"*. An organization admin who legitimately controls only their own GitHub App installation/webhook secret in a shared multi-org Shipit instance can forge push/status/check_suite events that Shipit will process as if they came from a *different* victim repository. For `push`, this causes `Stack#sync_github` → `GithubSyncJob` to run against the victim's stack using Shipit's own GitHub API credentials for that installation, fetching and appending commits and potentially triggering continuous delivery deploys the victim never requested — an unauthorized deploy/rollback trigger on a repository the attacker has no access to. This matches the "unauthorized deploy" / cross-repository impact criteria.

### Likelihood Explanation
Exploitation only requires being one of the (possibly many) organizations already configured in a multi-tenant Shipit installation, and the ability to send an HTTP POST to the shared `/webhooks` endpoint with a body signed with one's own known secret — no Shipit session, GitHub private key, or victim's webhook secret is needed. This is squarely an "unprivileged attacker" relative to the victim repository, matching the required threat model.

### Recommendation
When processing a webhook, verify that the organization used to select the signing secret (`repository_owner` / `organization.login`) matches the owner encoded in `repository.full_name` before dispatching to handlers, e.g. reject the request if `repository_owner != full_name.split('/').first`.

### Proof of Concept
1. Attacker controls org `attacker-org`, configured in Shipit's multi-org `github:` secrets with `webhook_secret: S`.
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<any_existing_sha_on_victim_repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `S` and sends it as `X-Hub-Signature` to Shipit's `/webhooks` endpoint with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, verifies successfully using `S`.
5. `PushHandler#process` looks up stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `sync_github`, triggering `GithubSyncJob` against the victim's stack — despite the request never being authenticated as coming from `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
