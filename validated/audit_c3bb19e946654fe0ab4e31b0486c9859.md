### Title
Incomplete control-character/length validation of AA-generated `data_feed` messages allows corruption of the data-feed key format - ([File: aa_composer.js])

### Summary
The newline/length checks that protect the `data_feed` key format in the key-value store are enforced only against **static, literal** feed names/values at AA-definition validation time [1](#0-0) . When a feed name or value is produced by a **formula** (i.e. computed dynamically at trigger time), that same source-time check is explicitly skipped (`getFormula(feed_name) === null` / `getFormula(value) === null` guards) [2](#0-1) , and the runtime code path that turns the evaluated formula result into the actual outgoing `data_feed` message never re-validates it before the message is written into the unit.

### Finding Description
For a normal, human/posted unit, `data_feed` payloads are validated in `validation.js`, which rejects feed names/values that are too long or that contain `\n` [3](#0-2) . The `\n` character is significant because data feeds are physically stored in the key-value store using `\n` as a field separator, e.g. `'df\n'+address+'\n'+feed_name+'\ns\n'+strValue+'\n'+strMci` and `'dfv\n'+address+'\n'+feed_name+'\n'+strMci` → `value+'\n'+unit` [4](#0-3) . Readers such as `getMciFromDataFeedKey`/`getValueFromDataFeedKey` assume an exact, fixed number of `\n`-delimited fields [5](#0-4) , and range queries in `dataFeedByAddressExists` rely on `\n`/`\r` sentinel bytes to bound a feed's key-prefix range [6](#0-5) . Any stray `\n`/`\r` byte in a stored `feed_name` or `value` therefore corrupts this delimiter scheme.

For AA-defined `data_feed` messages, `aa_validation.js` only performs the `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH`/`\n`-content checks when the feed name or value is a **static literal string in the AA source** (`getFormula(...) === null` branch) [1](#0-0) . If the feed name or value is instead a formula expression (e.g. built from trigger data, string concatenation, or `\{...\}` oscript templates), no length/character check is performed at definition-validation time, because the actual string is not yet known.

At execution time, once the formula evaluates and produces the concrete `messages` array, `aa_composer.js`'s `handleTrigger`/`sendUnit` pipeline post-processes messages but only validates `payment` message structure and sorts `asset`/`asset_attestors` fields [7](#0-6) [8](#0-7) . There is no equivalent re-check of `data_feed` payload length or forbidden control characters (`\n`) before the message is hashed and included in the unit that is written by `writer.js`/`main_chain.js`. This mirrors the CVE-2026-3644 bug class exactly: the control-character/format check exists on one construction path (the static-literal path checked during definition validation) but is missing on the other path that produces the same logical object (the dynamic, formula-evaluated path used at trigger time), so the guard is trivially bypassed.

### Impact Explanation
A malicious AA author can define a `data_feed` message whose feed name or value is built from a formula (so it escapes the static check in `aa_validation.js`) and have it evaluate, at trigger time, to a string containing `\n` (and/or exceeding the length limits). This value flows unchecked into the `data_feed` message of the AA's outgoing response unit and gets persisted via `addDataFeeds` directly into `\n`-delimited key-value store keys [4](#0-3) . The injected delimiter corrupts the assumed 6-field key format relied upon by `getValueFromDataFeedKey`/`getMciFromDataFeedKey` and the prefix-range scans in `dataFeedByAddressExists`/`readDataFeedValue`, which other AAs' oracle-based conditions (`data_feed[[...]]`, `in_data_feed`, and the `in data feed` address-definition operator) depend on to decide fund release/spending conditions. Corrupting or spoofing these lookups can cause a genuine oracle value to be missed (denial for legitimate release logic) or cause an attacker-crafted feed to be picked up as if it belonged to a different, trusted feed_name/address, leading to AA fund loss or unintended release of funds guarded by data-feed conditions.

### Likelihood Explanation
Reachable by any unprivileged AA author: they only need to define an AA whose `data_feed` message payload uses a formula expression for the feed name or value (fully within the allowed oscript grammar, since dynamic values are explicitly permitted and exempted from the static check), then send a trigger that causes the formula to evaluate to a string containing `\n`. No special privileges, network position, or cooperation from other nodes is required — this is entirely within the single-author, single-unit AA execution model.

### Recommendation
Apply the same `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH`/no-`\n` checks used in `validation.js`'s `data_feed` case (and in the static branch of `aa_validation.js`) to the **evaluated, runtime** values of AA-produced `data_feed` messages before they are hashed/included in the outgoing unit — i.e., add a validation pass in `aa_composer.js`'s message-assembly pipeline (alongside the existing payment/asset checks around `aa_composer.js:1868-1885`) that re-validates every `data_feed` message's feed names and values for length and forbidden control characters, regardless of whether they originated from a literal or a formula.

### Proof of Concept
1. Deploy an AA whose response template includes:
   ```
   {
     messages: [{
       app: 'data_feed',
       payload: { ["feed" || "\n" || "attacker_injected_key"]: 1 }
     }]
   }
   ```
   (feed name built via oscript string concatenation so it is a formula, bypassing `aa_validation.js`'s static-literal `\n` check.)
2. Trigger the AA; `evaluateAA` computes the concrete feed_name string containing an embedded `\n`.
3. `sendUnit`/`handleTrigger` assemble and hash the message without re-checking for `\n` or length [7](#0-6) .
4. On stabilization, `addDataFeeds` writes the corrupted key directly into the key-value store [4](#0-3) , breaking the delimiter assumptions used by other AAs' `data_feed`/`in_data_feed` reads.

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}

// df:address:feed_name:type:value:strReversedMci
function getValueFromDataFeedKey(key){
	var m = key.split('\n');
	if (m.length !== 6)
		throw Error("wrong number of elements in data feed "+key);
	var type = m[3];
	var value = m[4];
	return (type === 's') ? value : decodeLexicographicToDouble(value);
}
