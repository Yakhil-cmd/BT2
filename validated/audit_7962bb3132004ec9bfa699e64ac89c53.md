### Title
Silent enforcement bypass in `Condition.from_dict` due to missing field-inference defaulting for explicit conditions - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` infers a sensible default `field` (`command`/`new_text`/`content`) from the rule's `event` only for the legacy `pattern:` style, but `Condition.from_dict` silently defaults `field` to an empty string `''` when the modern `conditions:` list omits it. Because the rule engine treats an unresolved field as a non-match, an `action: block` rule authored (or shipped) with the explicit-conditions style and a missing/mistyped `field` key silently becomes a permanent no-op, while appearing valid and enabled.

### Finding Description
`Condition.from_dict` builds a `Condition` with no field inference or validation: [1](#0-0) 

Compare this to the legacy path in `Rule.from_dict`, which explicitly infers a field from `event` (`command` for bash, `new_text` for file, `content` otherwise) when only a simple `pattern` is given: [2](#0-1) 

No such inference or validation exists for the `conditions:` (explicit) path — a missing `field` key simply becomes `''`: [3](#0-2) 

At evaluation time, `RuleEngine._check_condition` calls `_extract_field(condition.field, ...)`; if the field can't be resolved (which is guaranteed for `field=''`, since it will not be a key in `tool_input` nor match any of the special-cased Stop/`reason`/`transcript` names), it returns `None`, and the condition — and therefore the whole rule, since **all** conditions must match — is treated as not matching: [4](#0-3) [5](#0-4) 

`load_rule_file`/`load_rules` perform no schema validation on condition dicts — a `conditions:` entry missing `field` (e.g. via an attacker-authored repo-shipped `.claude/hookify.*.local.md` file, or a subtly malformed `/hookify`-generated file) loads without warning and is marked `enabled: True`: [6](#0-5) 

The net effect: a rule file that visually and semantically looks like a legitimate `action: block` guard (e.g., intended to block `rm -rf`, credential leaks, etc.) using the "advanced" multi-condition format documented in the README/SKILL, silently never fires if any condition's `field` key is dropped or misspelled — with zero error, log entry, or user-facing indication that the rule is inert. Anyone relying on that shipped rule file for protection (a normal collaborator pulling the repo, or a user who ran `/hookify` and trusted the generated file) gets no enforcement at all, while believing they are protected.

### Impact Explanation
This breaks the intended invariant that default/implicit field handling must never silently weaken enforcement relative to the legacy pattern-based inference. A `block` rule meant to stop dangerous local commands (`rm -rf`, credential exfiltration writes, etc.) can be rendered permanently inert by a single missing/mistyped key in a condition entry, with no error surfaced anywhere in the load/evaluate pipeline (`load_rule_file`, `load_rules`, `RuleEngine.evaluate_rules`). This maps to "Unauthorized local command execution that bypasses Claude Code approval or deny controls" because the victim's Bash/Edit/Write operations that should have been denied via `hookSpecificOutund.permissionDecision = "deny"` in `RuleEngine.evaluate_rules` instead silently fall through to the "no matches — allow operation" path. [7](#0-6) 

### Likelihood Explanation
Feasibility is moderate and depends on who authors/ships the malformed rule file:
- If a malicious/careless repo-shipped `.claude/hookify.*.local.md` (committed by any contributor, no special privilege required beyond normal repo write/PR access) uses the `conditions:` format and omits `field` on one entry, the rule silently never enforces for every user who checks out that file — this is fully reproducible and requires no runtime privilege.
- The bug is also latent in `/hookify`-generated files if the underlying LLM or a future template change produces a `conditions:` entry lacking `field` — since there is no schema check, the failure is invisible until someone manually inspects behavior.
- The scenario does not require admin/maintainer privilege, leaked credentials, or social engineering — only the ability to supply repository content (a rule file), which is explicitly in-scope per the question's attacker model.

### Recommendation
- In `Condition.from_dict`, do not default `field` to `''`; instead raise/reject the condition (fail closed, not fail silent) if `field` is missing, or reuse the same event-based inference logic used for legacy `pattern` rules.
- Add explicit validation in `load_rule_file`/`Rule.from_dict` that every condition dict has a non-empty `field`, a recognized `operator`, and a non-empty `pattern`; log a clear, loud warning (or refuse to load the rule) if any of these are absent, especially for `action: block` rules.
- Consider making `_check_condition`/`_extract_field` fail "block"-style rules loudly (e.g., emit `systemMessage` warning) when a field cannot be resolved, rather than silently treating it as "no match."

### Proof of Concept
Unit test targeting `plugins/hookify/core/config_loader.py` and `plugins/hookify/core/rule_engine.py`:

```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

def test_missing_field_silently_disables_block_rule():
    frontmatter = {
        "name": "block-rm-rf",
        "enabled": True,
        "event": "bash",
        "action": "block",
        "conditions": [
            # 'field' key omitted/mistyped -- simulates attacker-shipped rule file
            {"operator": "regex_match", "pattern": r"rm\s+-rf"}
        ],
    }
    rule = Rule.from_dict(frontmatter, "Blocked dangerous rm -rf")

    # Condition.from_dict defaulted field to ''
    assert rule.conditions[0].field == ""

    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /important-data"},
    }
    result = engine.evaluate_rules([rule], input_data)

    # Expected (secure) behavior: rule should block the dangerous command
    # Actual (vulnerable) behavior: result == {} — operation silently allowed
    assert result == {}, "Block rule silently failed to enforce due to unresolved field"
```

Expected assertion failure demonstrates that a `block` rule using the explicit `conditions:` format with a missing `field` key never triggers, contrasting with the equivalent legacy `pattern:` rule which correctly infers `field="command"` for `event: bash` and would block the same input.
