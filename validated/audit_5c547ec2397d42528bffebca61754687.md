## Analysis

The reported bug class — using a block-height counter that does **not advance at a constant, attacker-resistant rate** as a proxy for elapsed real time — has a direct analog in `ocore`'s `age` operator for address definitions.

### Analog location

`definition.js` implements the `age` operator, which is used inside **address definitions** (smart-contract-like spending conditions that any unprivileged user can create for their own address) to gate spending based on how long ago funds were received: [1](#0-0) 

The relevant validation logic for `age` (and its sibling `mci`) treats `main_chain_index` (MCI) exactly the way the Optimism report treats `block.number`: [2](#0-1) 

Critically, `ocore` itself already recognized that MCI is not a reliable clock and introduced a dedicated `timestamp` operator (guarded by `constants.timestampUpgradeMci`) as the "real time" alternative for definitions and authentifiers: [3](#0-2) 

However, the `age` operator was **not** migrated to use `timestamp`; it still compares `main_chain_index` deltas of the source-input units against `objValidationState.last_ball_mci - age`: [4](#0-3) 

### Root cause parity with the Optimism report

- On Optimism, `block.number` does not correlate with wall-clock time because block production isn't rate-limited to a fixed interval — anyone submitting transactions can push block numbers forward irregularly.
- In `ocore`, MCI is incremented once per unit that lands on the evolving main chain, and the rate of MCI growth depends on the pace and structure of unit posting across the network, as implemented in the MC advancement logic: [5](#0-4) 

Any unprivileged unit poster can influence how quickly new units become part of (and advance) the main chain by posting a rapid sequence of low-cost units that chain onto the current tip, without needing witness cooperation, thereby decoupling MCI growth from real elapsed seconds — the same "block number ≠ time" issue as the Optimism finding.

### Why this matters

Any user who defines a spending condition like `["age", [">", N]]` in their own address definition (e.g., a personal time-locked vault, vesting-style rule, or escrow condition) is relying on `age` to enforce a **minimum real-time holding period** before funds become spendable, exactly as Frankencoin's `redeem()` relies on `anchorTime()`/`block.number` for its 90-day minimum. Because `age` counts MCIs, not seconds, the actual elapsed wall-clock time required to satisfy `age > N` can be compressed (if MCI advances unusually fast due to bursty unit posting) or stretched (if MCI advances slowly during quiet periods), causing the enforced holding duration to deviate from what the address's own author intended when writing the definition.

### Title
Address definitions relying on the `age` operator use `main_chain_index` instead of real timestamp to gate time-based spending conditions - (`File: definition.js`)

### Summary
The `age` operator, used inside `ocore` address definitions to require a minimum holding period on spent inputs, measures elapsed "time" in main-chain-index (MCI) units rather than real elapsed time (`block.number`-style clock, analogous to the Optimism `anchorTime()` finding), even though `ocore` already added a dedicated `timestamp` operator for this exact purpose in other contexts.

### Finding Description
`validateAuthentifiers`'s handling of the `age` op computes the input's holding duration purely from `main_chain_index` arithmetic: `objValidationState.last_ball_mci - age` compared against the input unit's `main_chain_index` [4](#0-3) . MCI is incremented by the main-chain advancement algorithm each time a new unit becomes part of the evolving best-parent chain [5](#0-4) , a process whose rate is a function of network unit-posting activity rather than a fixed time interval. `ocore`'s own developers acknowledged that MCI-based conditions are unreliable proxies for time by introducing a parallel `timestamp` relation operator gated behind `constants.timestampUpgradeMci` [2](#0-1) [3](#0-2) , but `age` was never migrated to use real timestamps.

### Impact Explanation
Any unprivileged user who builds an address definition using `age` to enforce a minimum spending delay (time-locked wallets, vesting-style payouts, escrow release conditions) is exposed to the delay being enforced in MCI units instead of wall-clock time. Because MCI growth rate is variable and influenced by overall unit-posting throughput (which any unprivileged poster can affect by rapidly chaining low-cost units onto the current main-chain tip), the real elapsed time required to satisfy an `age` condition can differ substantially from what the address owner intended, allowing funds to become spendable earlier (or later) than the designed holding period — a fund-freezing/early-unlock deviation directly analogous to Equity.sol's `redeem()` minimum-holding-duration violation.

### Likelihood Explanation
Exploitation requires only that (1) a user has created (or interacted with) an address definition using the `age` operator to gate spending, and (2) network unit-posting throughput varies from what was assumed when the condition's numeric threshold was chosen. Since ordinary unit posting rate is not fixed and can be influenced by any actor posting extra units, the mismatch between MCI-time and real time is a naturally occurring condition, not a rare edge case, though the impact is limited to users/contracts that specifically choose to rely on `age`.

### Recommendation
Migrate the `age` operator (or provide an equivalent using `objValidationState.last_ball_timestamp`) to measure real elapsed time between the input unit's timestamp and the current last-ball timestamp, consistent with how the `timestamp` operator was already introduced to solve this exact class of problem elsewhere in `definition.js`.

### Proof of Concept
1. User A defines an address using `["age", [">", N]]` intending a fixed real-time holding period before certain inputs can be spent.
2. During a period of low network activity, MCI advances slowly relative to real time — extending the real-world delay far beyond intended.
3. Conversely, a burst of rapid unit posting (achievable by any unprivileged poster) advances MCI quickly relative to real time, allowing the `age` condition to be satisfied and the input spent well before the real-time holding period the definition author intended, as shown by the pure MCI-difference check in `age`'s evaluation query [4](#0-3) .
