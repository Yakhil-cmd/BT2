### Title
Dangling account after independent TTL eviction of one position map: expired supply/debt map silently reads as empty while `AccountMeta` persists - ([File: contracts/controller/src/storage/account.rs](contracts/controller/src/storage/account.rs))

### Summary
The external bug class is "session-persisted object freed on an error path while a pointer to it is retained" (use-after-free). In XOXNO Lending the analogous shape is per-key Soroban persistent-entry eviction: an `account_id` is a durable pointer to four independently-expiring storage entries (`AccountMeta`, `SupplyPositions`, `BorrowPositions`, `Delegates`). Readers default a missing position map to `Map::new` instead of failing, and the renewal helper only renews keys that still exist. Once one position map expires while `AccountMeta` survives, every flow dereferences a "freed" map as an empty-but-valid object, enabling wrongful liquidation or unbacked collateral withdrawal.

### Finding Description
`get_supply_positions`/`get_debt_positions` return `Map::new(env)` when the key is absent, so a missing map is indistinguishable from a legitimately empty one (`account.rs:63-73`). `try_get_account` only requires `AccountMeta` plus NFT owner resolution, then assembles the account from whatever maps exist (`account.rs:146-162`). `renew_user_account` iterates all four keys but renews each only under `persistent.has(key)`, so an already-evicted key is skipped forever while `AccountMeta` keeps being renewed on every interaction (`account.rs:259-272`). This mirrors the PHP bug exactly: the "pointer" (`AccountMeta`/`account_id`/NFT) is kept alive while one pointed-to object is freed, and later use reads garbage-as-valid state.

Divergent TTLs arise naturally and are reconstructible by users: `write_side_map` deletes the map key when it becomes empty (`account.rs:93-105`), so e.g. an account that fully withdraws supply, then re-supplies in a later ledger, ends up with a `SupplyPositions` entry whose lifetime started later than `BorrowPositions`, or vice versa. There is no code that reconciles lifetimes — `persist_account_positions` writes only the sides in `PositionSides` and calls `renew_user_account`, which cannot resurrect a dead key (`positions/mod.rs:153-170`).

Two exploitable dereferences:

- `SupplyPositions` evicted, `BorrowPositions`+meta live: `process_liquidation` loads the account via `storage::get_account`, sees zero collateral and real debt, so `plan::build_liquidation_plan` treats it as maximally undercollateralized. Any unprivileged address calls `liquidate` and seizes/burns the position, or `check_bad_debt_after_liquidation`/`clean_bad_debt` writes down the supply index while the user's real (archived) collateral shares are orphaned — permanent loss/freezing of user funds.
- `BorrowPositions` evicted, `SupplyPositions`+meta live: `withdraw` computes the post-withdraw health factor over an empty debt map (`calculate_account_risk_totals` reads the empty map), returns `i128::MAX`-class HF, and lets the user withdraw all collateral while real debt remains recorded in the pool's reserve accounting — the shares can be re-claimed later only against an insolvent position, producing protocol bad debt.

### Impact Explanation
Permanent freezing of user funds and/or protocol insolvency. Case 1 lets anyone drive a healthy-collateral account through liquidation/bad-debt cleanup that ignores its real shares, orphaning them and forcing a supply-index write-down or seizure of a misstated position. Case 2 lets the account owner withdraw collateral leaving invisible debt, i.e. direct insolvency against pool suppliers.

### Likelihood Explanation
Medium. The attacker cannot force eviction, but the precondition arises organically: Soroban persistent TTL is per-entry, the protocol deliberately deletes empty maps, and `renew_user_account` only renews surviving keys, so once one map lapses while meta is renewed by keepers/owner activity (`renew_account`, `update_account_threshold`, any position op), the split state is durable and sticky. Exploitation itself is a single unprivileged `liquidate` or `withdraw` call. Note `account_exists` explicitly checks only `AccountMeta` (per `skills/xoxno-lending-contracts/abi.md:65-68`), confirming the runtime tolerates meta-live/maps-dead states.

### Recommendation
Fail closed on partial account state instead of defaulting to empty: in `try_get_account`/`get_account` (or in `get_supply_positions`/`get_debt_positions` when meta exists), panic with `AccountNotFound`/`InternalError` when `AccountMeta` exists but a position map key that previously existed is absent — or track a "map ever written" flag in `AccountMeta`. Additionally, align lifetimes: always `set` an explicit (possibly empty-map sentinel or tombstone) entry rather than deleting the key in `write_side_map`, or make `renew_user_account` re-create+renew missing keys so all four entries share one TTL horizon.

### Proof of Concept
1. Alice supplies USDC and borrows XLM (account id `N`); later fully repays XLM — `write_side_map` deletes `BorrowPositions(N)`. She borrows again in a later ledger, recreating `BorrowPositions(N)` with a fresh TTL that now differs from `SupplyPositions(N)`/`AccountMeta(N)`.
2. Ledgers pass; `SupplyPositions(N)` entry expires. A keeper calls `update_account_threshold` (permissionless) or Alice calls `renew_account`, which renews `AccountMeta`/`BorrowPositions`/`Delegates` via `persistent.has` but cannot touch the dead `SupplyPositions` key (`account.rs:259-272`).
3. Any liquidator calls `controller::liquidate(liquidator, N, [(XLM, amount)], SeizeMode::Transfer)`: `storage::get_account` succeeds on meta+NFT, `get_supply_positions` returns an empty map (`account.rs:67`), the liquidation plan sees debt with zero collateral, and `check_bad_debt_after_liquidation` classifies the residual as bad debt — Alice's real collateral shares are orphaned while the pool takes a write-down.
4. Symmetric variant: `BorrowPositions(N)` expires first; Alice calls `withdraw` for her entire supply — risk totals computed over an empty debt map return maximal HF and the withdrawal succeeds against debt still owed to the pool.
