### Title
Liquidator-supplied price feed lets an attacker choose an unfavorable, still-"fresh" price to liquidate another user - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The Pyth staleness/recency check used by `v0-4-market.clar` only requires that a submitted price be *more recent than the last stored one* and *within `max-staleness`* of the current block time — it does not require it to be the single truest/latest Pythnet price. Because Pythnet republishes signed price updates roughly every 400ms, several distinct, independently valid VAAs typically exist for the same window. Any public market function that accepts an optional list of Pyth `feeds` (e.g. `liquidate`) writes the caller-chosen feed into the shared oracle storage and then immediately values *another user's* position with it. A liquidator can therefore pick, off-chain, whichever valid recent VAA is most unfavorable to the victim before triggering the liquidation, extracting a larger seizure than the true current price would justify — exactly the "different valid prices in the same window" primitive from the referenced Sherlock report, but here the two parties (liquidator vs. borrower) are different unprivileged principals, not the same actor arbitraging themselves.

### Finding Description
`write-feeds`/`write-feed` push any Pyth VAA bytes supplied by the caller into the shared `pyth-oracle-v4` / `pyth-storage-v4` contracts: [1](#0-0) 

The only two guards on acceptance of a submitted price are (a) monotonic recency vs. the last stored publish-time, enforced in `pyth-storage-v4`'s `write-batch-entry`, and (b) the market's own staleness/recency check: [2](#0-1) [3](#0-2) 

`oracle-timestamp-fresh` only checks `ts >= prev` and `block_time - ts <= max-staleness` — any of several concurrently valid Pythnet VAAs within that window passes. Neither check enforces that the *most current* price at broadcast time is used; it only prevents replay of an older-than-previously-seen price.

Liquidation logic (`process-debt-asset`, `process-collateral-asset`, `calc-final-liquidation-amounts`) values the victim's debt/collateral using whatever price was just written by the caller's feed: [4](#0-3) 

The batch-liquidation helper explicitly documents that individual (non-batch) `liquidate` calls *do* take a `price-feeds` argument that updates prices before valuation, confirming the price-update-then-evaluate pattern is reachable by an arbitrary liquidator against an arbitrary victim: [5](#0-4) 

Shared state exploited: the `last-update` map and the Pyth `prices`/`timestamps` maps are global, not scoped to caller — one caller's chosen price becomes the price everyone else's position is valued against until superseded: [6](#0-5) [7](#0-6) 

Attacker/victim outcome:
- Attacker (liquidator, unprivileged) monitors off-chain Pythnet updates for a borrower sitting near the liquidation threshold, and collects several concurrently-valid, differently-priced VAAs.
- Attacker chooses the VAA that minimizes the victim's collateral valuation (or maximizes debt valuation) while still satisfying `ts >= prev` and `<= max-staleness`.
- Attacker calls `liquidate(borrower, ..., feeds: (some [chosen-vaa]))`.
- Without the attacker's transaction, the same liquidation executed against the true/latest market price would have seized less collateral (or none, if the position would be healthy under the accurate price) — with the attacker's transaction, the victim loses more collateral than the true price justifies, and the market's global oracle state is now pinned to that manipulated value for subsequent readers as well.

### Impact Explanation
This is a "seizure exceeding its bound": the liquidation penalty/collateral seized from the victim borrower is computed off a price the attacker cherry-picked from a set of concurrently valid oracle updates, rather than the honest, freshest price. This directly transfers value (excess collateral + liquidation bonus) from an unprivileged victim to an unprivileged attacker-liquidator — theft of user funds at rest, landing in the Critical/High impact class per the rules (direct theft of user funds other than yield).

### Likelihood Explanation
Feasibility mirrors the original Sherlock finding: Pythnet emits new signed prices roughly every 400ms, so multiple valid VAAs are commonly available within the `max-staleness` window (protocol staleness thresholds are typically tens of seconds to minutes for L2/L1 use, e.g. this repo's test suite uses a 3-hour stale threshold in some configs, and the market layer's own `max-staleness` is configurable per asset). No privileged access is required — any address can call `liquidate` with a chosen feed. Likelihood is proportional to price volatility and the width of the `max-staleness` window; it is not guaranteed on every attempt but is systematically exploitable whenever a target position is close enough to the liquidation boundary that a price choice within the valid window changes the outcome.

### Recommendation
- Do not let a liquidator (or any third-party caller) choose which price feed update to apply before evaluating someone else's position. Either: (1) require price updates affecting a victim's valuation to be submitted by the victim/keeper independently of the liquidator's own transaction, or (2) enforce a minimum settlement delay between a submitted price update and its use for liquidation of another account, so the price cannot be selected adversarially in the same call.
- Tighten `oracle-timestamp-fresh`/`price-resolve` to reject price updates that are not the *first* update accepted for their publish-time slot, or bind `max-staleness` much tighter, reducing the number of concurrently "valid" VAAs a caller can choose among.
- Consider disallowing a `feeds` parameter on `liquidate` (or any function) that acts upon another principal's position; require the oracle to already be fresh via a separate, keeper-only update path.

### Proof of Concept
Conceptual PoC (cannot be executed here without full liquidate function body, which was truncated by index size limits — a Devin session with full repo access would be needed to build and run this against the Clarinet simnet test harness):
1. Set up a borrower position near the liquidation threshold (`v0-4-market.clar` liquidation math, lines 700-877).
2. Off-chain, fetch two concurrently valid Pyth VAAs for the collateral asset within the `max-staleness` window, where VAA #2's price is less favorable to the borrower than VAA #1.
3. Call `liquidate(borrower, collateral-ft, debt-ft, debt-amount, min-collateral-expected, none, (some [VAA #2]))` as an unrelated liquidator.
4. Confirm `write-feeds` (lines 128-152) stores VAA #2 into `pyth-storage-v4`, and `process-collateral-asset`/`calc-final-liquidation-amounts` (lines 785-853) seize more collateral from the borrower than would have resulted from VAA #1. [8](#0-7)

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

  (debt-aid uint)
  (max-debt-usd uint)
  (assets (list 64 {
    id: uint, addr: principal, decimals: uint,
    oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
    collateral: bool, debt: bool, price: uint
  })))
  (let ((debt-asset-info (unwrap-panic (find-asset debt-aid assets)))
        (debt-price (get price debt-asset-info))
        (debt-decimals (get decimals debt-asset-info))
        (debt-usd (normalize (* debt-amount debt-price) debt-decimals false))
        ;; cap debt at maximum liquidatable amount
        (debt-actual-usd (if (> debt-usd max-debt-usd) max-debt-usd debt-usd))

      debt-actual-usd: debt-actual-usd,
      debt-actual: debt-actual,
      debt-price: debt-price,
      debt-decimals: debt-decimals
    }))
