### Title
Signer weight in `make_signer_set` aggregates STX contributed by addresses that will be auto-unlocked via the missed-reward-slot logic, letting signing weight exceed actually-locked STX for the cycle - (File: `stackslib/src/chainstate/stacks/boot/mod.rs`)

### Summary
`make_reward_set` computes `signer_set = Self::make_signer_set(threshold, &addresses)` (line 1095) by grouping `RawRewardSetEntry` items by **signing key** across all reward addresses, before the subsequent per-`reward_address` loop determines which entries fail to meet the slot threshold and are pushed onto `missed_slots` for auto-unlock (lines 1143-1177). Because the two groupings use the same `threshold` but different aggregation keys (signing key vs. reward address), a stacker can split its STX across two low-value stacking registrations that share one signing key: each registration individually floors to `slots_taken == 0` and is queued for auto-unlock, while their combined amount, summed under the shared signing key in `make_signer_set`, crosses the signer weight threshold and yields `weight >= 1`.

### Finding Description
The invariant that should hold is: **signing weight assigned to a signer key for a reward cycle == STX that remains locked (and un-expired) for that cycle**. This is violated because:

- `make_signer_set` (mod.rs:1020-1072) builds a `BTreeMap<signing_key, stacked_amt>` by summing `entry.amount_stacked` for *every* entry sharing a signing key, regardless of `reward_address`, then computes `weight = stacked_amt / threshold` (line 1054).
- `make_reward_set` (mod.rs:1081-1191) instead groups by `reward_address` (line 1116 loop) to compute `slots_taken = stacked_amt / threshold` for that address only (line 1130). If `slots_taken == 0` and a `stacker` pointer exists, the entry is pushed to `missed_slots` (lines 1143-1177), which is documented as the "auto-unlock list" — those tokens are not expected to remain locked for the reward cycle since the address never captured a slot.
- Both computations use the identical `threshold` value (it is passed once into `make_signer_set` at line 1095), so the only source of divergence is the aggregation key (signing key vs. address). An attacker who registers two low-value stacking positions under **different reward addresses** but the **same signer key** can have each position individually miss the reward-address threshold (queued for auto-unlock) while their sum crosses the signer-key threshold and is credited full weight in the `NakamotoSignerEntry` returned by `make_signer_set`.
- Nothing in this code path — nor `verify-not-prepare-phase`, `check-pox-lock-period`, or `verify-signer-key-grant` referenced in the audit rubric — reconciles the signer weight against the `missed_slots` set. The `signer_set` and `missed_slots` are computed independently from the same `addresses` vector and packaged together unmodified into `RewardSet::V0` (lines 1183-1190); no step subtracts auto-unlocked amounts from `stacked_amt`/`weight` before finalizing the signer set.

### Impact Explanation
The result is that a signer key can carry Nakamoto signing weight for a reward cycle backed partly (or, in the limiting two-position case, mostly) by STX that is auto-unlocked and no longer locked for that cycle. This directly matches the audit's High-severity category "signing weight or reward slots exceeding locked value": block-signing authority (which gates block acceptance) is granted disproportionately to stake that is not actually committed for the cycle's duration. This does not mint or steal STX/sBTC, but it degrades the security assumption that signing power is proportional to locked capital, and it is repeatable every reward cycle simply by re-splitting stake across multiple low-value registrations under one signing key.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: the attacker needs two (or more) independent STX-holding principals (trivial to create), each stacking an amount below the reward-address threshold, both registering the same signer public key (a normal, permitted operation — signer keys are independent of reward addresses and stacking principal). No privileged role, timing race, or node/RPC assumption is required; this can be done purely by the attacker's own PoX transactions in the reward-set-forming cycle. It is fully repeatable each cycle at the cost of the (below-threshold) amounts the attacker chooses to stack.

### Recommendation
Reconcile signer-key aggregation with the missed-slot outcome before computing weight: when building `signer_set` in `make_reward_set`, subtract (or exclude) the `amount_stacked` contributed by entries that end up in `missed_slots` (i.e., entries whose own reward address failed to reach `threshold`) prior to calling/using `make_signer_set`, or alternatively compute `make_signer_set` only from entries that were *not* redirected to the auto-unlock path. This restores signer weight == locked STX for the cycle.

### Proof of Concept
Rust unit test (analogous to existing tests in `stackslib/src/chainstate/stacks/tests/reward_set.rs`):
1. Choose `threshold = T`.
2. Build two `RawRewardSetEntry` items:
   - Entry A: `reward_address = addr_A`, `stacker = Some(principal_A)`, `signer = Some(key_S)`, `amount_stacked = T/2`.
   - Entry B: `reward_address = addr_B`, `stacker = Some(principal_B)`, `signer = Some(key_S)`, `amount_stacked = T/2 + 1`.
   (Individually each entry's own-address `slots_taken = 0`.)
3. Call `StacksChainState::make_reward_set(T, vec![A, B], epoch_id)` with an epoch where `supports_pox_missed_slot_unlocks()` is true.
4. Assert both sides of the equality:
   - `result.start_cycle_state.missed_reward_slots` contains `(principal_A, T/2)` and `(principal_B, T/2+1)` — i.e., both entries were flagged for auto-unlock (no STX remains locked for the cycle for either).
   - `result.signers` (from `make_signer_set`) contains an entry for `key_S` with `weight >= 1` (since `T/2 + (T/2+1) = T+1 >= T`), demonstrating nonzero signing weight granted despite zero STX remaining locked for the cycle under either registration.
