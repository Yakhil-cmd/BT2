### Title
Accrual value overflow permanently freezes a high-utilization market - (File: `common/src/rates/index.rs`)

### Summary
The pool calculates accrued debt with checked RAY multiplication before applying the borrow-index ceiling, so an oversized high-utilization book can overflow `i128` before `MAX_BORROW_INDEX_RAY` is reached. [1](#0-0) [2](#0-1)  Once that state is reached, permissionless `update_indexes`, withdrawals, repayments, and liquidation-related settlement all load the market through an accrue-first path and revert with `MathOverflow`, leaving assets permanently inaccessible unless privileged code changes the state. [3](#0-2) [4](#0-3) 

### Finding Description
Every mutation loads market `Cache`, calls `interest::global_sync`, and only then performs the requested accounting. [5](#0-4) [6](#0-5)  Each accrual chunk first unscales total borrowed and supplied shares through `scaled_to_original`, which is `scaled.mul(env, index)` and therefore returns `MathOverflow` when the total RAY value exceeds `i128::MAX`. [7](#0-6) [8](#0-7)  It then multiplies `borrowed * old_borrow_index` and `borrowed * new_borrow_index` again inside `calculate_supplier_rewards`, so oversized debt can overflow both before and after the new index is calculated. [1](#0-0) 

The configured index ceiling does not prevent this condition because `MAX_BORROW_INDEX_RAY` is only applied after `old_index * interest_factor`, and the value-overflow threshold can be crossed while the index remains below that ceiling. [2](#0-1) [9](#0-8)  Because `mark_accrued` happens only after all chunks complete, a failed accrual leaves `last_timestamp` stale and the next operation repeats the same overflowing calculation. [10](#0-9)  The repository already contains a regression test demonstrating that a billion-token 18-decimal market with 98% utilization eventually makes `update_indexes`, `withdraw`, and `repay` all revert with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`. [11](#0-10) 

### Impact Explanation
This is permanent freezing of user funds and protocol insolvency rather than a bounded transaction failure: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot settle the affected market after the RAY total-debt value crosses the arithmetic ceiling. [12](#0-11) [13](#0-12) [14](#0-13)  The condition is reachable through unprivileged `supply`, `borrow`, and `update_indexes` calls, although practical reachability depends on market caps and on an attacker or honest users assembling an exceptionally large book. [15](#0-14) [16](#0-15) [17](#0-16) 

### Likelihood Explanation
Likelihood is limited by the need for a very large market and sustained high utilization, but it does not require privileged access, malformed token behavior, oracle manipulation, or a failed external call. [18](#0-17)  The token-to-RAY domain admits roughly 170 billion whole tokens before input conversion itself overflows, while the demonstrated failure uses a smaller billion-token market because index growth multiplies the scaled debt again. [19](#0-18)  Since the fixed accrue-before-action design removes any bypass once the overflow exists, the consequence is deterministic rather than dependent on ordering or MEV. [6](#0-5) 

### Recommendation
Bound the market by maximum RAY value, not only by token caps and index ceilings: cap admitted supply and debt so `supplied * MAX_SUPPLY_INDEX_RAY` and `borrowed * MAX_BORROW_INDEX_RAY` cannot exceed `i128::MAX`. [9](#0-8) [1](#0-0)  In addition, make accrual handle saturation explicitly—clamp the index before unscaled-value multiplication can overflow, or keep a safe total-value invariant in `Cache::commit`—while preserving the existing rounding and index-monotonicity rules. [20](#0-19) [21](#0-20) 

### Proof of Concept
1. Create or use a listed 18-decimal market and lift configured caps enough to admit a very large book, matching the repository test setup. [22](#0-21) 
2. Through permissionless controller `supply`, deposit approximately `1_000_000_000 * 10^18` native units into the debt market. [23](#0-22) [24](#0-23) 
3. From a sufficiently collateralized account, call permissionless `borrow` for approximately 98% of that market’s cash; this mints scaled debt whose raw RAY principal is already near `i128::MAX`. [25](#0-24) [26](#0-25) 
4. Let the ledger timestamp advance and call permissionless `update_indexes(caller, [hub_asset])`; `Cache::load` sees a positive `elapsed_ms`, `global_sync` calls `accrue_step`, and `scaled_to_original(borrowed, borrow_index)` or `borrowed.mul(new_borrow_index)` overflows `i128`. [15](#0-14) [10](#0-9) [27](#0-26) 
5. Repeat `update_indexes`, then attempt `withdraw` or `repay`; all calls enter the same accrue-first path and revert with `MathOverflow`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [3](#0-2) [28](#0-27)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {

        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let failure = loop {
        years += 1;
        assert!(
            years <= 40,

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();

| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
