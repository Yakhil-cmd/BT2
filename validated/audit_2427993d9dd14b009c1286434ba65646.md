### Title
Bridge Operator Keystore Password Stored in Plaintext on Disk Enables Unauthorized Cross-Chain Value Transfers — (`node/sc/bridge_accounts.go`)

### Summary

`InitializeBridgeAccountKeystore` in `node/sc/bridge_accounts.go` automatically generates a random password for the bridge operator keystore and writes it to a plaintext file on disk adjacent to the encrypted keystore. Any process or user with read access to the node's data directory can read this password file, decrypt the keystore, obtain the bridge operator's private key, and sign fraudulent value-transfer transactions — draining bridged KAIA or KCT tokens.

### Finding Description

When a service-chain node starts and no bridge account keystore exists, `InitializeBridgeAccountKeystore` generates a random password, creates a new keystore encrypted with it, and then immediately writes the password in plaintext to the filesystem:

```go
// node/sc/bridge_accounts.go lines 207-213

acc, err := ks.NewAccount(password)
...

```

The password file lives at `<datadir>/<parent_bridge_account|child_bridge_account>/<hex_address>` — a predictable path in the same directory as the encrypted keystore JSON. The scrypt-encrypted keystore provides no protection once the password file is readable.

A developer TODO comment in the same function acknowledges this is not production-safe:

```go
// TODO-Kaia-Servicechain A test-option will be added and this routine will be only executed with it.
```

Despite this, the code ships without any such guard and executes unconditionally in production.

### Impact Explanation

The bridge operator accounts (`pAccount` / `cAccount`) are the only signers authorized to submit cross-chain value-transfer transactions to the bridge contracts. An attacker who reads the plaintext password file can:

1. Decrypt the bridge operator keystore (`ks.GetKey` with the recovered password).
2. Obtain the operator's ECDSA private key.
3. Sign and submit arbitrary `handleValueTransfer` / `requestValueTransfer` transactions to the bridge contract.
4. Drain bridged KAIA or KCT tokens from the bridge contract to an attacker-controlled address.

This satisfies the allowed impact: **unauthorized transfer of KAIA and bridged assets**.

### Likelihood Explanation

Any local user, co-located container, or process running under the same OS user as the node can read the password file. Cloud environments with shared storage, misconfigured volume mounts, or backup agents that snapshot the data directory all expose the file. The path is deterministic and requires no brute-force.

### Recommendation

- Remove the auto-write of the plaintext password file from production code paths. Gate it behind an explicit test/dev flag as the TODO intends.
- Require the operator to supply the bridge account password interactively or via a secrets manager (e.g., environment variable, HSM, or encrypted secrets store) rather than storing it alongside the keystore.
- If auto-unlock is required for unattended operation, use OS-level secret storage (e.g., Linux kernel keyring, `secret-service`) rather than a plaintext file.

### Proof of Concept

1. Start a service-chain node with `SubBridge` enabled. `NewBridgeAccounts` calls `InitializeBridgeAccountKeystore` for both parent and child bridge accounts.
2. Observe that `<datadir>/parent_bridge_account/<hex_address>` and `<datadir>/child_bridge_account/<hex_address>` are created as plaintext password files.
3. Read the password file: `cat <datadir>/parent_bridge_account/<hex_address>`.
4. Use the recovered password to decrypt the adjacent keystore JSON: `DecryptKey(keystoreJSON, password)` — this succeeds immediately, yielding the bridge operator's `*ecdsa.PrivateKey`.
5. Construct and sign a `handleValueTransfer` call to the bridge contract using the recovered key, transferring bridged tokens to an attacker address.

// InitializeBridgeAccountKeystore initializes a keystore, imports existing keys, and tries to unlock the bridge account.
// This returns the 1st account of the wallet, its address, the lock status and the error.
func InitializeBridgeAccountKeystore(keystorePath string) (*keystore.KeyStore, common.Address, bool, error) {
	ks := keystore.NewKeyStore(keystorePath, keystore.StandardScryptN, keystore.StandardScryptP)

	// If there is no keystore file, this creates a random account and the corresponded password file.
	// TODO-Kaia-Servicechain A test-option will be added and this routine will be only executed with it.
	if len(ks.Accounts()) == 0 {
		password := setup.RandStringRunes(params.PasswordLength)
		acc, err := ks.NewAccount(password)
		if err != nil {
			return nil, common.Address{}, true, err
		}
		setup.WriteFile([]byte(password), keystorePath, acc.Address.String())

		if err := ks.Unlock(acc, password); err != nil {
			logger.Error("bridge account wallet unlock is failed by created password file.", "address", acc.Address, "err", err)
			os.RemoveAll(keystorePath)
			return nil, common.Address{}, true, err
		}

		return ks, acc.Address, false, nil
	}

	// Try to unlock 1st account if valid password file exist. (optional behavior)
	// If unlocking failed, user should unlock it through API.
	acc := ks.Accounts()[0]
	pwdFilePath := path.Join(keystorePath, acc.Address.String())
	pwdStr, err := os.ReadFile(pwdFilePath)
	if err == nil {
		if err := ks.Unlock(acc, string(pwdStr)); err != nil {
			logger.Warn("bridge account wallet unlock is failed by exist password file.", "address", acc.Address, "err", err)
			return ks, acc.Address, true, nil
		}
		return ks, acc.Address, false, nil
	}

	return ks, acc.Address, true, nil
}
