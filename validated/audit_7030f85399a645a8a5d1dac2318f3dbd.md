### Title
Stack-scoped `ApiClient` token can read CCMenu status of any stack, bypassing its `stack_id` authorization scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary

### Finding Description
`Shipit::Api::BaseController` implements per-token stack scoping: a request-scoped `ApiClient` (one that has a `stack_id` set) is restricted to only the stack it was issued for, via `stacks` and `stack`: [1](#0-0) 

The `ApiClient` model itself supports this scoping (`belongs_to :stack, optional: true`), and fixture data demonstrates a real stack-scoped, read-only token (`here_come_the_walrus`, permission `read:stack`, `stack: shipit`): [2](#0-1) [3](#0-2) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to resolve the target stack directly from `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!` used everywhere else in the API: [4](#0-3) 

The controller only enforces the coarse `read:stack` permission bit (`require_permission :read, :stack`), never checking whether `current_api_client.stack_id` matches the requested `stack_id`: [5](#0-4) 

This breaks the binding `stack_authorized_by_token == stack_touched_by_request` for this single endpoint: every other `BaseController` subclass (`Api::StacksController`, task/deploy resources, etc.) enforces the equality through `stacks.from_param!`, but `CCMenuController#stack` unconditionally resolves any stack ID in the system.

### Impact Explanation
A token that was deliberately scoped to a single stack (an intentional "least privilege" configuration supported by the `ApiClient` model, e.g. a CI-status widget token limited to one stack) can be replayed against `CCMenuController#show` with an arbitrary `stack_id` to read that other stack's build/deploy status: last build result, last build label (commit sha), running state, and web URL: [6](#0-5) 

This is an unauthorized read of stack state/deploy status for stacks the token holder was never granted access to — the same class of "stack a token authorises vs. stack it touches" boundary violation called out in scope, and it maps to the High-severity "unauthenticated/unauthorized read of stack state, task streams, or deploy output" category.

### Likelihood Explanation
Any holder of a legitimate, narrowly-scoped `read:stack` `ApiClient` token (a normal, unprivileged credential type explicitly supported by the data model and exercised in the test suite) can trivially trigger this by changing the `stack_id` route/query parameter on the `CCMenu` endpoint — no additional secrets, sessions, or elevated permissions are required beyond the token itself, and the token is exactly the credential the scoping mechanism was designed to constrain.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so stack-scoped tokens cannot read status for stacks outside their `stack_id` scope, consistent with `Api::BaseController#stack`.

### Proof of Concept
1. Provision a stack-scoped read-only token, e.g. fixture `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`): [3](#0-2) 
2. Authenticate as that client and request the CCMenu status for a *different* stack ID than the one it is scoped to:
   `GET /api/ccmenu/<other_stack>.xml` with `Authorization: Basic <base64(here_come_the_walrus token)>`.
3. `authenticate_api_client` succeeds (valid token) and `require_permission :read, :stack` passes (client has `read:stack`).
4. `stack` resolves via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`, so the response returns the other stack's build status/commit — contrast with `Api::StacksController#show`, whose equivalent test enforces the stack-scoping restriction via `stacks.from_param!`: [7](#0-6)
