## Title
Silent underflow reset to zero in pending-transaction-queue accounting can under-report `paid_from_balance`/`paid_from_gas_key`, bypassing SPICE pending-balance admission checks - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
`chain/client/src/pending_transaction_queue.rs` defines `checked_sub_or_default!`, a helper that performs a checked subtraction and, on underflow, fires a `debug_assert!` and logs an error but then **silently substitutes `Default::default()` (i.e. `0`)** rather than propagating an error or refusing to proceed [1](#0-0) . This is the exact bug class from the report: a helper that is expected to represent "not enough to fulfill the operation" instead returns a default/zero value and lets execution continue, and the callers do not treat that fallback specially.

### Finding Description
This macro is used in three places that maintain the SPICE-mode `PendingTransactionQueue`'s aggregate accounting for the still-uncertified (pending) chunks:
- `PendingNonce::remove` decrementing chunk contribution counts [2](#0-1) 
- `PendingAccount::subtract`, which reverses `access_key_tx_count`, `deploy_tx_count`, and critically `paid_from_balance` when a certified chunk is removed [3](#0-2) 
- `remove_certified_chunk_by_block_hash`'s reversal of `pending_gas_key_costs` [4](#0-3) 

These aggregates (`paid_from_balance`, `paid_from_gas_key`, `max_nonce`) are exposed via `PendingTransactionQueue::get_pending_constraints` / `query_pending_state` as `PendingConstraints`, which are consumed directly by:
- the RPC handler, to compute the `state_root`/`constraints` passed into `can_verify_and_charge_tx` before admitting a transaction [5](#0-4) 
- chunk production's `PendingTxSession::check_pending`, whose result becomes the `pending_constraints` fed into `verify_and_charge_tx_ephemeral` / `verify_and_charge_gas_key_tx_ephemeral` [6](#0-5) 

In the runtime verifier, `available_balance = account.amount().saturating_sub(pending.paid_from_balance)` is the balance actually checked against a new transaction's cost [7](#0-6) , and for gas keys `gas_key_info.balance.checked_sub(pending.paid_from_gas_key)` guards against double-spending gas-key balance across pending, uncertified chunks [8](#0-7) . If `paid_from_balance` or `paid_from_gas_key` is prematurely reset to `0` by an underflow in `checked_sub_or_default!` (e.g., a chunk-removal/reorg race where a chunk's contribution is subtracted more than once, or subtracted from state that was already partially cleared), the admission checks in `verify_and_charge_tx_ephemeral`/`verify_and_charge_gas_key_tx_ephemeral` will believe there is no pending balance commitment for the signer, and will admit further transactions that, combined with the still-outstanding (not-yet-certified) pending cost, exceed the account's or gas key's real available balance.

The code's own comments acknowledge this design is "best-effort" and only relevant off the consensus fast path (SPICE / RPC pre-check), explicitly noting `saturating_sub` is used because pending constraints should be non-negative on that path [9](#0-8) . The `checked_sub_or_default!` macro is the only defense against a corrupted/negative pending state turning into an outright panic; instead of surfacing the invariant violation as a hard error (which would trigger corrective action, e.g. clearing/rebuilding the queue), it masks it by resetting to zero and continues serving stale/incorrect admission decisions.

### Impact Explanation
If the invariant "removed chunk's contribution ≤ tracked pending total" is violated (via a race between reorg handling, out-of-order certified-chunk removal, or a bug in per-chunk aggregation), the pending-queue's `paid_from_balance`/`paid_from_gas_key` silently drops to `0` in release builds (where `debug_assert!` is compiled out), rather than failing loudly. This causes:
- SPICE-mode chunk producers and the RPC pre-admission check (`can_verify_and_charge_tx`) to under-count outstanding balance commitments for a signer/gas key across multiple uncertified chunks in flight, allowing additional transactions to be admitted that the signer's real balance cannot cover once all pending chunks are certified.
- Because the actual balance deduction still happens deterministically at chunk-execution/certification time in the authoritative runtime (the trie-based execution path), the ultimate on-chain outcome is that some of these over-admitted transactions will fail execution (e.g. `NotEnoughBalance`) rather than causing an on-chain double-spend — but this can still cause `NotReadyToProcess`/queue-management inconsistencies, wasted chunk space, unnecessary transaction rejections, and denial-of-service-style throughput degradation for the affected account, since the admission control (P_MAX/deploy-exclusivity/balance pre-check) meant to bound concurrent pending load is bypassed.

### Likelihood Explanation
This is gated behind the SPICE protocol feature and only active when `spice_pending_transaction_queue_enabled` is set, and it only affects the admission pre-check path, not the authoritative consensus balance accounting (which uses `checked_sub(...).unwrap()` and is exact on the consensus path) [10](#0-9) . The comments in the code indicate the underflow path is understood to be an "invariant violation" that "tests catch" via `debug_assert!`, implying the developers believe it should not normally occur, but the fallback to `Default::default()` was deliberately added for release-build robustness rather than to correctly propagate the error [1](#0-0) . I was unable to fully verify whether a concrete reachable sequence of reorgs/chunk removals can trigger this underflow in practice; the search did not surface a specific race scenario proven in tests, so likelihood is assessed as low-to-moderate and would require further investigation of the SPICE chunk lifecycle/reorg handling to confirm reachability from a submitted transaction alone (not just from a malicious/validator-controlled sequence of chunk certifications, which per the analog rules would be out of scope).

### Recommendation
Replace `checked_sub_or_default!`'s silent zero-fallback with an approach that does not let a detected invariant violation continue: propagate an error that forces the affected pending-queue shard (or account entry) to be dropped/rebuilt from certified state and marks it unavailable for pending-constraint admission, or at minimum ensure `PendingConstraints` produced against a corrupted entry are never trusted (e.g., return `Skip` for the involved account/gas key rather than defaulting to `0`, which is the value that removes the safety constraint entirely).

### Proof of Concept
Not independently reproduced. Based on static analysis: (1) trigger `PendingAccount::subtract` or the `pending_gas_key_costs` reversal in `remove_certified_chunk_by_block_hash` with a `chunk_account`/`chunk_gas_key_cost` value greater than the currently tracked total for that account/key (e.g., via a race where the same chunk's contribution is applied/reversed twice, or a stale chunk snapshot is removed after the totals were already reduced by another path); (2) observe that in a release build the `debug_assert!` is compiled out, so `paid_from_balance`/`paid_from_gas_key` becomes `0` instead of erroring; (3) show that subsequent calls to `get_pending_constraints`/`check_pending` return `PendingConstraints { paid_from_balance: 0, .. }` for that account, which is then passed into `verify_and_charge_tx_ephemeral`/`verify_and_charge_gas_key_tx_ephemeral`, allowing admission of a transaction that would have been rejected had the correct non-zero pending balance been retained [11](#0-10) [7](#0-6) .

/// Checked subtraction that falls back to `Default::default()` on underflow,
/// logging an error and firing a debug_assert so tests catch the invariant violation.
macro_rules! checked_sub_or_default {
    ($a:expr, $b:expr, $msg:expr) => {
        match ($a).checked_sub($b) {
            Some(v) => v,
            None => {
                debug_assert!(false, $msg);
                tracing::error!(target: "client", $msg);
                Default::default()
            }
        }
    };
}
