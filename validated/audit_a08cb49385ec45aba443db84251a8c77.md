### Title
Webhook signature check keys off `repository.owner.login` while handlers resolve the target repository/stack from the independent `repository.full_name` field, allowing repository-confusion across organizations - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the GitHub App/secret selected by `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , but `LabeledHandler#repository` resolves the actual `Shipit::Repository`/stack to mutate from the separate, unrelated `params.repository.full_name` field [3](#0-2) . Nothing enforces that `full_name`'s owner segment matches the authenticated `owner.login`, so once signature verification passes for any org (in particular, an org configured without a `webhook_secret`, which the setup docs call optional), the payload's `repository.full_name` can name a completely different organization's repo, causing `stack.archive!`/`stack.unarchive!` to run against that victim org's `ReviewStack`.

### Finding Description
Binding claimed: org authenticating the webhook (via `repository_owner` = `params.repository.owner.login`, used in `GitHubApp#verify_webhook_signature`) == org owning the repository/provisioning config consulted (`Repository.from_github_repo_name(params.repository.full_name)`).

Tracing the code:
- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and picks the `GitHubApp` instance for that organization: `Shipit.github(organization: repository_owner)` [1](#0-0) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the org's `webhook_secret` is blank: `return true unless webhook_secret` [4](#0-3) . The setup docs explicitly describe `webhook_secret` as optional [5](#0-4) .
- Once `verified` is true, `WebhooksController#create` dispatches the raw, attacker-supplied JSON to `LabeledHandler` [6](#0-5) .
- `LabeledHandler#repository` looks up the `Repository` purely from `params.repository.full_name`, split into owner/name by `Repository.from_github_repo_name` [7](#0-6) [3](#0-2) . This value is never cross-checked against `repository_owner`/`owner.login`.
- `archive?`/`unarchive?` then evaluate `repository.provisioning_behavior_prevent_with_label?` / `provisioning_label_name` against the resolved (victim) `Repository`'s config and, if matched, call `stack.archive!` on that repository's `ReviewStack` [8](#0-7) .

Exploit flow: attacker POSTs directly to `/webhooks` (per the rules, this is an in-scope capability: "any internet user who can send HTTP requests to the Shipit host, including POST /webhooks") with a body where `repository.owner.login` = an organization configured in Shipit without a `webhook_secret` (or one whose secret the attacker otherwise knows), and `repository.full_name` = `"org_b/victim-repo"`, `pull_request.labels` containing org_b's `provisioning_label_name`, and a `pull_request.number` matching a live PR/review stack of org_b. `verify_signature` passes (bypassed via blank secret for the named `owner.login` org), and `LabeledHandler` archives org_b's stack.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) do not catch this because: (1) `verify_signature` only checks that the request is legitimately from *some* configured org, not that the referenced `full_name` belongs to that same org; (2) the `params` schema for `LabeledHandler` only requires `repository.full_name` to be a `String`, with no format/consistency validation against `owner.login` [9](#0-8) .

### Impact Explanation
A single crafted POST to `/webhooks` can cause `Shipit::Stack#archive!` to execute against a review stack belonging to an organization/repository the attacker never authenticated against — a payload authenticated for one repository/org mutating another repository's stack, matching the Critical category explicitly listed ("a payload for one repository mutating another's stack"). This is repeatable against any victim repo configured with `provisioning_behavior: 'prevent_with_label'` (or `allow_with_label`) that has an active `ReviewStack`, as long as the attacker can get `verify_signature` to pass for whatever org name they place in `repository.owner.login`.

### Likelihood Explanation
Exploitability is gated entirely on Shipit's own multi-tenant configuration: it requires at least one org registered in `Shipit.github` config with a blank/no `webhook_secret` (explicitly documented as optional), or an org whose secret the attacker otherwise possesses. If every configured org enforces a non-blank `webhook_secret`, the attacker cannot produce a valid `X-Hub-Signature` for any `owner.login` value and the attack is blocked at `verify_signature`. Thus the vulnerability is real and the root cause (missing binding between `repository.owner.login` and `repository.full_name`) is a genuine flaw in this engine's code, but its exploitability is conditional on operator configuration (an org without a webhook secret) rather than being universally exploitable.

### Recommendation
In `WebhooksController#verify_signature` (or in a shared handler concern), after determining `repository_owner`, also validate that any `repository.full_name`/`organization.login` referenced elsewhere in the payload is prefixed by/matches `repository_owner`, and reject the webhook (422) on mismatch. Additionally, consider requiring `webhook_secret` to be present for every configured org in production, or logging/alerting when a webhook is accepted for an org with no secret.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or a new handler test):
1. Configure two orgs in `Shipit.github` config for the test: `org_a` with `webhook_secret: nil`, and `org_b` with a `Repository` (`owner: 'org_b', name: 'victim-repo'`) configured `provisioning_behavior: 'prevent_with_label'`, `review_stacks_enabled: true`, plus an active `Shipit::ReviewStack` for pull request number `7`.
2. Build a JSON body: `{ action: 'labeled', number: 7, pull_request: { ..., labels: [{ name: repository.provisioning_label_name }] }, repository: { owner: { login: 'org_a' }, full_name: 'org_b/victim-repo' }, sender: { login: 'attacker' } }`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request` and no valid `X-Hub-Signature` (or an arbitrary bogus one), without any `org_b` credentials.
4. Assert: response is `:ok` (signature check bypassed via `org_a`'s blank secret), and `org_b`'s `ReviewStack` is now `archived?` — i.e. assert `binding_left (verify_signature org) = 'org_a' != binding_right (repository consulted) = 'org_b'` yet `stack.archive!` still executed.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
