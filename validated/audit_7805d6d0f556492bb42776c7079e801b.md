### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login` but write actions act on the unverified `repository.full_name`, allowing cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/secret to verify a webhook against using a field taken from the untrusted JSON body (`repository.owner.login` or `organization.login`), independently of the field the downstream handlers actually act on (`repository.full_name`, used to resolve the target `Stack`/`Repository`). In a Shipit instance configured for multiple GitHub organizations, an attacker who legitimately controls the webhook secret of one onboarded organization can forge a signed payload whose "owner" field points at their own org (to pass verification) while its "repository" field points at a different, unrelated org's repository, causing Shipit to process spoofed events (push, status, check_suite, membership, …) for a stack they do not control.

### Finding Description
`verify_signature` derives the verification key from `repository_owner`, computed purely from request body content, before the signature is checked: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` then HMACs the *entire* raw body against the secret configured for that specific organization: [3](#0-2) 

Shipit explicitly supports configuring multiple, independent GitHub organizations/apps with independent `webhook_secret`s in the same instance: [4](#0-3) 

Each organization's operator is trusted only to control their own org's webhook secret (they set the "Webhook secret" on their own GitHub App, per the setup docs), and Shipit assumes that a signature verified with OrgA's secret only speaks for OrgA's repositories: [5](#0-4) 

However, nothing ties `repository.owner.login` (used to pick the verification key) to `repository.full_name` or `organization.login` (the values the event handlers use to resolve the actual `Stack`/`Repository`/`Team`/`User` being written). Both are independent, attacker-controlled JSON fields inside the same signed body. Because the signature only proves "this body was signed with OrgA's secret," not "this body may only describe OrgA's resources," an operator/admin of OrgA (who legitimately possesses OrgA's `webhook_secret`) can construct a body where `repository.owner.login = "OrgA"` (to select OrgA's key for verification) but `repository.full_name = "OrgB/some-repo"` (to make handlers act on OrgB's stack). Once `verify_signature` passes, `create` dispatches to all registered handlers for the event with the full `params`: [6](#0-5) 

This breaks the intended binding "organization whose secret authenticated the request == organization/repository that gets written," letting a cross-tenant party of one onboarded org act as if they owned another onboarded org's stack.

### Impact Explanation
Handlers triggered by this route include status/check_suite processing that feeds `StatusChecker`/CI gating used by continuous deployment and the merge queue, and `membership` handling that creates `Team`/`User` records on the fly (seen in `test/controllers/webhooks_controller_test.rb`). By spoofing `status`/`check_suite` events for a victim org's commit with forged "success" statuses, an attacker controlling only their own org's webhook secret can satisfy `ci.require`/merge-queue checks for a stack they were never granted access to, enabling an unauthorized deploy or merge through Shipit's continuous-delivery/merge-queue automation on the victim stack — without ever holding a Shipit session, `ApiClient` token, or the victim org's GitHub credentials. This is a cross-repository/cross-organization write via a credential-selection bypass, matching the Critical/High "unauthorized deploy/merge" and "cross-repository writes" impact categories.

### Likelihood Explanation
The precondition is that the same Shipit instance is configured with more than one GitHub organization (a documented, supported configuration, not a misuse of the engine). Given that, exploitation requires no special access beyond what any onboarded organization's admin already legitimately has (their own org's `webhook_secret`), and the forged HTTP POST to `/webhooks` is trivial to construct. This is a moderate-likelihood issue confined to multi-org deployments, but it directly negates the isolation multi-org configuration is meant to provide.

### Recommendation
Do not let a value taken from the unverified request body select the verification key while a *different* body field determines what gets written. Either:
- Verify the signature using every configured org's secret and require that the *same* org/repository identity used for verification is the one referenced by all resource-identifying fields in the payload (`repository.full_name`, `organization.login`) — reject on mismatch, or
- After successful verification with OrgX's secret, restrict all handler processing strictly to resources that belong to OrgX (cross-check `repository.owner.login == organization.login == full_name.split('/').first` and reject otherwise), or
- Isolate multi-org webhook secrets per-endpoint (e.g., per-org webhook URL) so verification key selection is out-of-band and not attacker-influenced.

### Proof of Concept
1. Shipit instance configured with two orgs, `OrgA` (attacker-administered) and `OrgB` (victim), each with distinct `webhook_secret`s per `config/secrets.development.example.yml`.
2. Attacker (owner of the OrgA GitHub App) knows `OrgA_secret`.
3. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(OrgA_secret, body)`.
5. POST to `/webhooks` with `X-Github-Event: status`.
6. `repository_owner` resolves to `"OrgA"` → `Shipit.github(organization: "OrgA")` is used → signature validates against `OrgA_secret`, which the attacker legitimately knows.
7. The status handler processes the payload against `OrgB/victim-repo`'s commit, recording a forged "success" status that can satisfy `ci.require`/merge-queue checks configured on OrgB's stack — all without any credential belonging to OrgB.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.
```
