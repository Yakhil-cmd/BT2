### Title
`OpenedHandler#provision?` operator-precedence bug lets `review_stacks_enabled: false` repositories still auto-provision review stacks for `allow_with_label`/`prevent_with_label` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` is written as `a && b || c || d`, and in Ruby `&&` binds tighter than `||`, so `repository.review_stacks_enabled` only gates the `allow_all?` branch and never gates the `allow_with_label?`/`prevent_with_label?` branches. As a result, a repository administrator who disables review-stack auto-provisioning (`review_stacks_enabled = false`) while leaving `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` will still have stacks auto-provisioned from PRs opened by any GitHub user, contrary to the disabled setting. No existing test in `opened_handler_test.rb` exercises this combination.

### Finding Description
Binding claimed: `provision? == false` whenever `repository.review_stacks_enabled == false`, for every `provisioning_behavior`. Actual code: [1](#0-0) 

Ruby operator precedence parses this as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`

i.e., `review_stacks_enabled` is ANDed only with the first disjunct. For `review_stacks_enabled = false`, `provisioning_behavior = prevent_with_label`, and a PR opened with no matching label, evaluation is `(false && false) || (false && ...) || (true && true) == true`. `provision?` returns `true` despite the master switch being off.

`process` then unconditionally creates the review stack and enqueues it for provisioning: [2](#0-1) [3](#0-2) 

The newly created stack transitions `deprovisioned -> provisioning`, which triggers `stack.provisioner.up`: [4](#0-3) 

That provisioning flow ultimately runs the stack's deploy/provision commands on the host, using `branch: params.pull_request.head.ref` (attacker-controlled fork branch name) as the checked-out ref: [5](#0-4) 

No signature/authorization guard in the handler chain checks this condition — `respond_to_pull_request_opened?` only checks `action == "opened" && provision?`, and `provision?` itself is the broken gate: [6](#0-5) 

Test coverage confirms the gap: the only test that sets `provisioning_enabled: false` pairs it exclusively with `behavior: :allow_all`, never with `allow_with_label` or `prevent_with_label`: [7](#0-6) 

All `allow_with_label`/`prevent_with_label` tests in that suite leave `review_stacks_enabled` at its default `true` (via `configure_provisioning_behavior`'s default `provisioning_enabled: true`), e.g.: [8](#0-7) [9](#0-8) 

So the precedence bug is not caught by CI.

### Impact Explanation
For any repository where an operator has explicitly turned off review-stack auto-provisioning (`review_stacks_enabled = false`) but left `provisioning_behavior` at `allow_with_label` or `prevent_with_label` (e.g., a leftover/partial configuration), any unprivileged GitHub user who can open a pull request against that repository can force Shipit to create and provision a review stack for their own attacker-controlled branch. This drives the stack into `provisioning`, invoking `stack.provisioner.up` and executing deploy/provision tooling against a branch name the attacker fully controls — an unauthorized deploy/provisioning action the repository owner believed was disabled. This matches the "unauthorized deploy" Critical impact category, and is repeatable against every repository sharing this misconfiguration.

### Likelihood Explanation
Requires a Shipit-tracked repository configured with `review_stacks_enabled = false` and `provisioning_behavior` in `{allow_with_label, prevent_with_label}` — a plausible, non-exotic configuration (e.g., an operator who disabled the feature but didn't reset the behavior dropdown, or intends to allow only labeled PRs but mistakenly believes the top-level toggle is authoritative). Given that configuration, the attack costs nothing beyond opening a PR (for `prevent_with_label`, no label is even needed) and is fully repeatable.

### Recommendation
Fix operator precedence by explicitly parenthesizing the intended AND-gated form:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, enumerating `review_stacks_enabled = false` against all three `provisioning_behavior` values with and without the label:

```ruby
[:allow_all, :allow_with_label, :prevent_with_label].each do |behavior|
  [true, false].each do |label_present|
    test "does not create stacks when review_stacks_enabled is false (behavior=#{behavior}, label_present=#{label_present})" do
      repository = shipit_repositories(:shipit)
      configure_provisioning_behavior(
        repository:,
        provisioning_enabled: false,
        behavior:,
        label: "pull-requests-label"
      )
      payload = payload_parsed(:pull_request_opened)
      payload["pull_request"]["labels"] = label_present ? [{ "name" => "pull-requests-label" }] : []

      assert_no_difference -> { Shipit::Stack.count } do
        OpenedHandler.new(payload).process
      end
    end
  end
end
```
Binding under test: `provision? == false` for every combination when `review_stacks_enabled == false`. With the current source, the `behavior=:prevent_with_label, label_present=false` case (and `allow_with_label, label_present=true`) fails because `Shipit::Stack.count` increases, proving `provision?` returned `true` despite `review_stacks_enabled` being `false`.
