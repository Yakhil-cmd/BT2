### Title
Cross-Organization Webhook Forgery via Mismatched Signature-Scoping and Repository-Resolution Fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The reported bug class is "a value acted upon later is never covered by the check performed earlier" (pending redelegation tracked by `delegation.amount` but the removal check only looked at `can_redelegate.amount`). The equivalent binding in `shipit-engine` is: **the GitHub organization used to select the webhook signature secret ≠ the repository that event handlers actually write to**. `WebhooksController#verify_signature` picks which `Shipit.github(organization:)` config (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository.owner.login` from the *unauthenticated* JSON body, while the downstream handlers resolve the repository/stack/commit to mutate using a *different* field (`repository.full_name`, or in the case of `StatusHandler`, no repository scoping at all). Nothing ties these two payload-derived values together, so an attacker who legitimately controls a GitHub App/webhook secret for one organization can forge signatures that Shipit accepts, then redirect the payload body to act on another organization's repository/commit.

### Finding Description
`WebhooksController#verify_signature` derives the org used for signature verification purely from the request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GithubApp` instance configured for that specific org (Shipit supports multiple orgs with independent `webhook_secret` values, as shown in the multi-org fixture), and `verify_webhook_signature` HMACs the raw body against that org's own secret: [3](#0-2) 

Crucially, the field used to pick *which secret* verifies the signature (`repository.owner.login`) is never re-checked against the field the handlers use to pick *which data gets mutated* (`repository.full_name`): [4](#0-3) 

For `PushHandler`, this repository name is used to look up `Stack`s and immediately trigger a GitHub sync: [5](#0-4) 

`StatusHandler` is worse: it performs **no repository scoping check at all** — it looks up commits globally by SHA and writes a GitHub status onto them: [6](#0-5) 

So the equality that should hold — `organization_whose_secret_verified_the_signature == organization_that_owns_the_data_being_written` — is never enforced. An attacker only needs a valid webhook secret for *some* org configured in the Shipit instance (e.g. their own GitHub App installation on their own org, a legitimate, unprivileged registration) to forge signatures that are accepted for payloads whose `repository.full_name`/`sha` point at a completely different org's stacks/commits.

### Impact Explanation
By supplying `repository.owner.login = "OrgA"` (an org the attacker controls a webhook secret for) alongside `repository.full_name = "OrgB/victim-repo"` and a signature computed with OrgA's secret, an attacker can:
- Trigger `stack.sync_github` for `OrgB`'s stacks (`PushHandler`), causing Shipit to re-sync commits/branches for a repository the attacker has no legitimate authorization over.
- Forge arbitrary GitHub commit statuses (`StatusHandler`) on **any** commit tracked by Shipit, across any org/stack, since `Commit.where(sha: params.sha)` has no repository/org filter at all. Required/blocking statuses gate deploy eligibility in Shipit, so forging a passing status on a commit belonging to a stack the attacker does not control can remove a deploy safety gate for that unrelated stack — an escalation toward an unauthorized deploy.

This satisfies the "unauthorized deploy" / cross-repository-write impact bar, because the attacker never presents a signature verified against the victim org's own secret, yet is able to influence state (sync triggers, commit statuses) belonging to that victim org's stacks.

### Likelihood Explanation
Requires only an unprivileged attacker who (a) knows the multi-org Shipit instance tracks more than one GitHub organization/App, and (b) controls a legitimate, low-privilege webhook secret for at least one of those orgs (e.g. their own GitHub App/org registered in the same Shipit deployment) — no Shipit session, `ApiClient` token, or GitHub App private key for the victim org is needed. The `X-Github-Event` header and JSON body are fully attacker-controlled and there is no code path anywhere in `WebhooksController`, `Handler`, `PushHandler`, or `StatusHandler` that cross-checks `repository.owner.login` against `repository.full_name`.

### Recommendation
After `verify_signature` succeeds, enforce that the organization used to select the verifying secret matches the owner encoded in `repository.full_name` (and any other repository-identifying fields used by handlers) before dispatching to handlers — reject the webhook (422) on mismatch. Additionally, `StatusHandler#process` should scope its `Commit` lookup by the verified repository/organization rather than querying by SHA globally.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` (or `status`) webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1 with OrgA's webhook_secret over the raw body>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and the signature verifies successfully against OrgA's secret.
6. `PushHandler#process` then resolves `repository_name` from `repository.full_name` = `"OrgB/victim-repo"`, finds `OrgB`'s real stacks, and calls `stack.sync_github(expected_head_sha: ...)` — mutating state for a repository the attacker never authenticated against.
7. For `StatusHandler`, the same forged signature (using OrgA's secret) combined with an arbitrary `sha` belonging to any commit in the system (no repository field required at all) lets the attacker write a fabricated commit status via `commit.create_status_from_github!`, affecting deploy-gating logic for any stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
