### Title
User-supplied `swap_xdr` route executes arbitrary contract code under the caller's signed auth tree, enabling theft of unrelated wallet tokens - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The SSTI bug class — user-controlled data evaluated as an executable program in a privileged context — maps directly onto the swap-aggregator's `swap_xdr`: an unprivileged caller submits an arbitrary byte program (`ops`, `amounts`, `assets` registries) that the router decodes and executes. Because hop `pool`/`token` addresses come from the caller's `assets` registry with no allowlist, the payload can place attacker-deployed contract code on the call stack *below* the caller's `require_auth` entry. Soroban's recording-mode auth then attaches any `token.transfer(caller, attacker, X)` that code performs as a signed child of the caller's authorization tree — turning a "swap" signature into authorization to drain any token in the caller's wallet.

### Finding Description
- `execute_strategy(sender, total_in, swap_xdr)` decodes a fully caller-controlled `StrategyPayload` (`contracts/swap-aggregator/src/program.rs`); per the payload spec, hop instructions reference an `assets` registry by `u8` index and there is no venue/pool allowlist (`skills/xoxno-swap-aggregator/payload.md:61-115`).
- `dispatch_hop` invokes whatever `hop.pool` address the payload names via the venue adapters (`contracts/swap-aggregator/src/venues/mod.rs:23-59`), e.g. Comet's `env.invoke_contract(&ctx.hop.pool, "swap_exact_amount_in", …)` (`contracts/swap-aggregator/src/venues/comet.rs:30-34`). Aquarius/Soroswap/Phoenix/Sushi adapters likewise call `ctx.hop.pool` directly.
- The only sender-level check is the measured balance delta around the venue call and the final `min_out` (`dispatch_hop` lines 42-58; `execute/mod.rs` semantics in `payload.md:98-105`). Neither bounds what the invoked contract does *under the caller's auth tree*, because the router's only self-auth is its own pool-pull, while the invoked contract can itself call `token.transfer(sender, attacker, amount)` on any token the sender holds.
- This is reachable both directly via `execute_strategy` and through controller strategy verbs (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`), which forward caller-supplied `swap` bytes to the router under the caller's `require_auth` (`contracts/controller/src/strategies/swap.rs:34-38`).
- The behavior is demonstrated by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`: a rogue hop pool calls `token::Client::transfer(alice, attacker, WALLET_BALANCE)` during Alice's `swap_collateral`; the recorded auth tree shows the stolen transfer as a child of her signed `swap_collateral` entry, and enforcing mode executes it, leaving `balance(alice) = 0`, `balance(attacker) = WALLET_BALANCE`. The threat model describes the same exposure (`docs/explanation/threat-model.md:154-165`).

### Impact Explanation
Theft of user funds. A victim who signs a transaction whose route contains a malicious hop authorizes — as a child of her own `require_auth` entry — arbitrary `transfer` calls from her address. The attacker can drain every Stellar asset the victim holds (in the test, an unrelated token the protocol never listed), not merely the `total_in` routed amount. Neither the router's `min_out` check nor the controller's `RouterOverspend`/`NoSwapOutput`/risk gates bound this loss, since the stolen transfer is a sibling sub-invocation, not a measured balance delta of the router or controller.

### Likelihood Explanation
High. The attacker is fully unprivileged: they deploy a rogue "pool" contract, craft a `swap_xdr` whose `assets` registry points at it, and get the victim to sign (malicious frontend, phishing quote, or any route-building intermediary — the controller forwards `swap_xdr` opaquely without decoding it, so a compromised or malicious route source suffices). Wallets and SDK users typically sign the simulated auth tree without decoding per-hop pool addresses; the threat model itself notes the only defense is the client decoding the route and rejecting unexpected auth children, which is not enforced on-chain. Cost to the attacker is one contract deployment.

### Recommendation
- Enforce a venue/pool allowlist in the router: maintain an owner-managed registry of approved pool addresses per venue (or validate `hop.pool` against a registry keyed by `(venue, token_in, token_out)`), and reject hops whose `pool` is not registered (`InvalidRouteXdr`). Alternatively, resolve pool addresses on-chain from the venues' factory contracts rather than trusting the payload.
- Belt-and-suspenders for callers: document and enforce in the SDK (`verifyRouteBytes`/`verifyStandaloneEnvelope` in `payload.md:211-292`) that every hop's `pool` and `token_*` addresses match the quote's expected venues, and that the simulated auth tree contains exactly the expected children (one input `transfer` for standalone; the controller's entry plus nothing else for composed calls).

```rust
#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
