### Title
Webhook signature verified against organization derived from an unauthenticated payload field, while stack/repository lookup uses a different unauthenticated field, breaking the "organization authenticated == repository written" binding - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook's HMAC against based on `repository_owner`, a value read directly out of the untrusted, unsigned JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check passes, the very same untrusted body is handed to event handlers, which locate the `Stack`/`Repository` to act on using a *different* field of that body, `payload.dig('repository','full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Because HMAC verification only proves "this body was signed with organization X's secret," and never binds that verified organization to the `repository.full_name` value the handler actually acts on, an attacker who legitimately administers a webhook for org X can forge a request whose `repository.owner.login`/`organization.login` is `X` (so it signs and verifies correctly) but whose `repository.full_name` names a completely different, victim-owned stack tracked by this Shipit instance.

### Finding Description
- `verify_signature` computes the app config to verify against solely from payload data, not from any credential tied to the actual target repo: [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` resolves to a distinct `GitHubApp` (and distinct `webhook_secret`) per organization key configured in `secrets.github`, and `verify_webhook_signature` just HMAC-compares the raw body against that org's secret: [3](#0-2) [4](#0-3) 
- After the signature is accepted, the raw, still-untrusted `params` hash is dispatched to handlers as-is: [5](#0-4) 
- Every handler resolves the target `Stack`/`Repository` using `repository_name`, which reads `payload.dig('repository','full_name')` — a field never checked for consistency with the `repository.owner.login`/`organization.login` value used to pick the verifying secret: [6](#0-5) 
- `Repository.from_github_repo_name` then does a plain DB lookup on that unverified `full_name` string, with no cross-check against the organization whose secret validated the request: [7](#0-6) 

The equality that should hold is: `organization whose secret authenticated the request == owner of the repository the handler subsequently writes to`. Before the attack, both values happen to come from the same trusted GitHub-originated payload, so they coincide. After the attacker's forged request, the attacker fully controls both JSON fields independently: they set `repository.owner.login`/`organization.login = "attacker-org"` (an org they administer in this multi-tenant Shipit install, whose webhook secret they configured/know when wiring up the webhook) to make `verify_signature` pass, while setting `repository.full_name = "victim-org/victim-repo"` to redirect the handler to a stack they don't own. Nothing recomputes or re-validates that the signed organization matches the acted-upon repository owner.

### Impact Explanation
This lets an attacker who only controls a webhook for one org onboarded on a shared/multi-org Shipit deployment (see `Shipit.github_organizations`/`github_app_config`, which explicitly support multiple orgs each with their own `webhook_secret`) forge events processed as authentic GitHub events for a repository/stack they have no access to. Depending on event type this can: enqueue `GithubSyncJob` to ingest attacker-chosen commit SHAs into a victim `Stack`'s commit history (`push` event, matched via `full_name` in `PushHandler`), flip `commit_status`/`merge_status`/`deployable_status` records that gate deploy eligibility, or drive `review_stack`/`pull_request` lifecycle transitions (archive/create review stacks) for a repository under a different organization's control. This is a cross-organization/cross-repository write achieved purely by exploiting a signature-vs-processing-field mismatch, matching the report's "authenticated field vs. acted-upon field" divergence pattern and this engine's Critical impact bucket ("cross-repository writes").

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one GitHub organization (a documented, supported configuration via `secrets.github` with per-org `webhook_secret`) and that the attacker administers the webhook for any one of those onboarded orgs — a much lower bar than compromising the victim repository's own webhook secret, GitHub App private key, or an authenticated Shipit session. No social engineering, TLS interception, or privileged Shipit account is needed; the attacker only crafts one raw HTTP POST to `/webhooks` with a chosen `X-Github-Event` and `X-Hub-Signature` computed over a body they fully control.

### Recommendation
Bind the field used to select/verify the webhook secret to the field used for repository resolution: derive `Repository`/`Stack` lookup from the organization already resolved and verified in `verify_signature` (e.g., pass the verified `repository_owner`/`GitHubApp` instance forward and require `payload.dig('repository','full_name')` to start with that verified owner, rejecting the request otherwise), or verify the signature against the config keyed by the *target* repository's actual owner rather than a raw payload field that the handler will later trust independently.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`, `attacker-org` (attacker administers this org's GitHub webhook and therefore knows/controls its `webhook_secret`) and `victim-org` (a real, unrelated tenant with a `Stack` tracked by this Shipit instance).
2. Attacker builds a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_of_attacker_org, body)>`, sets `X-Github-Event: push`, and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker signed with that org's own known secret [1](#0-0) .
5. `create` dispatches the same body to `PushHandler`, which resolves the target stack via `repository_name` = `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` [6](#0-5)  and `Repository.from_github_repo_name` [7](#0-6) , enqueuing `GithubSyncJob` for the victim's stack using attacker-supplied SHAs — despite the request never being signed by victim-org's own secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
