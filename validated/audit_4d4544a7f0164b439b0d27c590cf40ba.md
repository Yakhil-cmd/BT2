### Title
Cross-repository status webhook forgery bypasses `all_status_checks_passed?` and triggers unauthorized PR merge - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub webhook secret to validate against using an attacker-controlled `repository.owner.login` field from the JSON payload, not the repository actually associated with the target `Commit`/`Stack`. `StatusHandler#process` then looks up `Commit.where(sha: params.sha)` with no scoping to the organization/repository that authenticated the request, so a validly-signed webhook from an unrelated repository/organization can write a passing status onto a commit belonging to a completely different `Stack`, which `MergeRequest#all_status_checks_passed?` will trust before `ProcessMergeRequestsJob` calls `merge_request.merge!`.

### Finding Description
The claimed binding is: `repository_that_signed_the_webhook == Stack#repository` for the `Commit` being mutated. This is never enforced.

- `WebhooksController#verify_signature` resolves which `GithubApp`/secret to check against via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the untrusted payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . This only proves the request was signed by *some* organization configured in `Shipit.github`, not that it corresponds to the `Stack` that owns the target commit.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — matched purely by `sha`, with no check of `params['repository']['full_name']` against `commit.stack.repository` [3](#0-2) .
- `Commit#create_status_from_github!` unconditionally writes the forged status via `add_status`, updating `Commit#status` [4](#0-3) .
- `MergeRequest#all_status_checks_passed?` reads exactly this mutable, cross-tenant state: `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [5](#0-4) .
- `ProcessMergeRequestsJob#perform` gates the real `merge!` call (which invokes `stack.github_api.merge_pull_request`) solely on this boolean: `next unless merge_request.all_status_checks_passed?` then `merge_request.merge!` [6](#0-5) [7](#0-6) .

Exploit precondition: the attacker must be able to get a GitHub `status` webhook, signed with a secret known to Shipit's `verify_webhook_signature`, delivered to `/webhooks` for the exact `sha` of the victim's PR head commit. `verify_webhook_signature` short-circuits to `true` entirely when no `webhook_secret` is configured for the resolved organization (`return true unless webhook_secret`) [8](#0-7) , and even when a secret is configured, Shipit supports multiple independently-configured organizations (each with its own `webhook_secret`), so an attacker who is the legitimate admin/owner of their own org's GitHub App integration (a different org than the victim's) knows that org's secret and can forge an arbitrary JSON body — including `sha` set to the victim's PR head sha and `state: success` — and sign it correctly for their own org. `Shipit.github(organization: repository_owner)` will happily resolve to that attacker-controlled org's config because `repository_owner` comes straight from the same forged payload. Signature verification therefore passes even though the request has nothing to do with the victim `Stack`'s repository. `StatusHandler#process` then matches the victim's `Commit` purely by `sha`, with no cross-check that the authenticating organization/repository matches `commit.stack.repository`, and writes the forged "success" status.

Existing guards that were checked and do not stop this: `drop_unhandled_event` only checks the event is registered, not who sent it; `verify_signature` only proves authenticity relative to whichever org's secret the attacker-chosen `repository_owner` field selects, not relative to the target `Stack`; the `StatusHandler` `ExplicitParameters` schema (`requires :sha`, `requires :state`, …) validates shape only, not provenance; there is no model validation on `Commit`/`Status` tying the incoming payload's repository to `stack.repository`.

### Impact Explanation
A successful forgery causes `Commit#statuses` for the victim's PR head commit to contain a fabricated `success` status from an attacker-controlled source, which flips `MergeRequest#all_status_checks_passed?` to `true` regardless of the PR's actual CI outcome. `ProcessMergeRequestsJob` then calls `merge_request.merge!`, which calls `stack.github_api.merge_pull_request` using the app's own GitHub credentials, merging an unreviewed/failing PR into the victim repository's default branch. This is an authentication-bypass / unauthorized-merge (Critical) impact: a payload authenticated for one tenant's/org's GitHub App integration is used to mutate another `Stack`'s commit and trigger a privileged GitHub API action on a repository the attacker never authenticated against. This is repeatable against any `Stack`/`Commit` whose `sha` the attacker can learn (trivial for public PRs) as long as the attacker holds a legitimately-configured Shipit webhook secret for *any* organization (their own).

### Likelihood Explanation
Feasibility depends on Shipit's deployment configuration: single-organization deployments (one `github:` config in `secrets.yml`) mean there's only one webhook secret, so this exact "different org, same Shipit instance" exploitation path requires either (a) a multi-org Shipit deployment where the attacker administers/knows the webhook secret for a second, distinct organization also configured in the same `Shipit.github` registry, or (b) a deployment where `webhook_secret` is unset for some organization, making `verify_webhook_signature` return `true` unconditionally. Given rule constraints excluding misconfiguration/best-practice notes, the demonstrable, in-scope path is the multi-org case, which the codebase explicitly supports (`config/secrets.development.shopify.yml` shows multiple orgs each with independent `webhook_secret`) [9](#0-8) . In that configuration, the attacker's cost is minimal — one crafted HTTP POST — and the exploit is fully repeatable against any known head `sha`.

### Recommendation
In `StatusHandler#process` (and other handlers matching on `sha` alone), verify that the authenticated `repository_owner`/`repository.full_name` from the payload matches the `stack.repository` of every `Commit` before applying the status, e.g. scope the lookup as `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: authenticated_repository.id })`, and reject/skip any commit whose owning stack's repository does not match the webhook's authenticated repository.

### Proof of Concept
```ruby
# test/jobs/process_merge_requests_job_test.rb (conceptual addition)
test "forged foreign-repo status webhook triggers unauthorized merge" do
  victim_stack = shipit_stacks(:shipit)
  pending_pr = shipit_merge_requests(:pending) # belongs_to victim_stack, head.sha known
  attacker_org_secret = "attacker-known-secret" # attacker legitimately owns this org's Shipit GitHub App config
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GithubApp::Repo.new(nil, webhook_secret: attacker_org_secret)
  )

  forged_body = {
    sha: pending_pr.head.sha,
    state: 'success',
    context: 'ci/forged',
    repository: { full_name: 'attacker/unrelated-repo', owner: { login: 'attacker-org' } }
  }.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_secret, forged_body)

  Shipit.github.api.expects(:merge_pull_request).once # asserts unauthorized merge fires

  post_webhook(event: 'status', body: forged_body, signature:) # hits /webhooks, passes verify_signature
  assert pending_pr.head.reload.success?
  ProcessMergeRequestsJob.new.perform(victim_stack)
end
```
Both sides of the binding to assert: `forged_request.authenticated_organization == 'attacker-org'` vs `pending_pr.stack.repository.owner == victim organization` — they diverge, yet the merge call fires, proving the vulnerability.

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
