### Title
CCMenu API endpoint bypasses per-token stack scoping, allowing a stack-restricted `ApiClient` to read any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (via `stack_id`) can only ever resolve `stack` to that one stack, by routing all lookups through the `stacks` scope. `Shipit::Api::CCMenuController` overrides `#stack` and looks the stack up directly from `params[:stack_id]` without going through that scope, so any authenticated `ApiClient` token — even one that is supposed to be restricted to a single stack — can read the CCMenu status (build/deploy state) of every stack in the installation.

### Finding Description
`ApiClient` records may carry an optional `stack_id`, and `BaseController` is explicitly designed to bind a token's authority to that stack: [1](#0-0) 
`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the token is scoped, and every controller that inherits `#stack` from `BaseController` (deploys, tasks, rollbacks, hooks, etc.) is therefore restricted to the stack the token authorizes.

`CCMenuController`, however, redefines `#stack` to bypass this scope entirely: [2](#0-1) 
`stack` here calls `Stack.from_param!(params[:stack_id])` directly against the global `Stack` relation. The controller still enforces `require_permission :read, :stack`, i.e. `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb`, permission list check only, no stack matching), but permission checking only validates the *type* of permission (`read:stack`) and never validates that the requested `stack_id` matches `current_api_client.stack_id`.

This breaks the trust binding: **the stack a token authorizes (`current_api_client.stack_id`) ≠ the stack the request actually touches (`params[:stack_id]` resolved against all stacks)**. Before the flaw, a stack-scoped token could only ever see its own stack's CCMenu XML; after crossing this code path, the same token can fetch CCMenu data (build status, last build label/time, activity) for any other stack in the Shipit instance simply by changing the `stack_id` route param.

### Impact Explanation
This meets the "High" bar of "unauthenticated read of stack state" from the impacted stack's perspective: a holder of a token intentionally restricted to Stack A (e.g., handed to a low-trust external CI/status dashboard integration) can read build/deploy status information belonging to Stack B, C, ... without ever having been granted permission on those stacks. This is exactly the kind of authorization/scope-binding violation the underlying bug class (a version/scope check applied inconsistently across otherwise-equivalent code paths) analogizes to: the "stack it touches" is not constrained to equal "the stack it authorizes."

### Likelihood Explanation
Likelihood is limited by the fact that stack-scoped `ApiClient` records (`stack_id` set) cannot be created through the web UI (`ApiClientsController#create_params` only permits `:name` and `:permissions`), so this scoping is only exercised for tokens provisioned out-of-band (e.g., via Rails console/seed data) specifically to hand out restricted, single-stack tokens to less-trusted integrations — the exact scenario the `stacks` scoping mechanism exists to protect. Any deployment that uses this supported restriction mechanism is exposed via the unauthenticated (token-only) CCMenu endpoint.

### Recommendation
Make `CCMenuController#stack` consistent with the rest of the API by resolving the stack through the scoped `stacks` relation instead of the raw `Stack` model, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This reuses the same `stacks` helper already defined in `BaseController` and ensures a stack-restricted token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. An admin creates (via console/seed) a stack-restricted token: `ApiClient.create!(creator: admin, name: "ci-status", permissions: ["read:stack"], stack_id: stack_a.id)`.
2. This token is handed to a low-trust consumer expecting to view only Stack A's CCMenu status:
   `GET /api/stacks/stack-a-owner/stack-a-repo/production/ccmenu.xml?token=<token>` → 200, returns Stack A's XML (expected).
3. The same token is reused against a different stack:
   `GET /api/stacks/stack-b-owner/stack-b-repo/production/ccmenu.xml?token=<token>` → 200, returns Stack B's build status/name/lastBuildStatus, even though the token's `stack_id` is bound to Stack A only.
4. Contrast with any other scoped API endpoint (e.g. `GET /api/stacks/stack-b-owner/stack-b-repo/production/tasks`) using the same token, which correctly 404s/forbids because it uses `BaseController#stack` → `stacks.from_param!`. [2](#0-1) [1](#0-0) [3](#0-2)
