### Title
Double issuance of a capped asset within a single AA response due to stale DB-only "already issued" check - (File: `aa_composer.js`)

### Summary
An AA (Autonomous Agent) response unit containing multiple `payment` messages that issue the same capped asset can cause the cap to be issued more than once, inflating the asset supply beyond its declared `cap`, because the "already issued" check queries only the committed `inputs` table and ignores in-flight issuance already staged in the current unit being composed.

### Finding Description
When an AA response contains payment messages, `sendUnit()` in `aa_composer.js` iterates them with `async.eachSeries(messages, function(message, cb) {...})` (`aa_composer.js:1298-1345`), calling `completePaymentPayload()` for each asset-payment message. If funds are insufficient, `completePaymentPayload()` calls `issueAsset()`:

```
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
```
(`aa_composer.js:1195-1201`)

This check queries the database `inputs` table, but the issue input created by `addIssueInput()` for an earlier message in the same response is only appended to `payload.inputs` in memory (`aa_composer.js:1181-1193`) — it is not written to the database until the whole unit is later saved via `validateAndSaveUnit`. Therefore, if a second `payment` message paying the same capped asset appears later in the same response (before the unit is saved), its `issueAsset()` call runs the same `SELECT 1 FROM inputs...` query, still finds zero rows, and issues the full `cap` amount a second time.

The mitigation for this is `mergeMessagesAndOutputs()` (`aa_composer.js:1010-1041`), which merges same-asset payment messages into one — but it is only invoked conditionally: `if (mci >= constants.pemCurvesFixMci) messages = mergeMessagesAndOutputs(messages);` (`aa_composer.js:1287-1288`). Before the `pemCurvesFixMci` upgrade point this merge did not exist/apply, meaning any AA whose oscript legitimately (or via `cases`/branching logic) emits two separate `payment` messages for the same capped asset in one response could double-issue that asset.

### Impact Explanation
Double issuance of a capped asset directly inflates its total supply beyond the declared `cap`, breaking the fundamental guarantee that a capped asset can be issued at most once for its full cap amount (`aa_composer.js:1195` comment explicitly assumes "no unstable consensus-breaking issues possible", relying solely on this single check). This constitutes concrete supply inflation for a user-defined asset, which can undermine any economic assumptions (fixed supply, backing ratios, etc.) built by applications/AAs relying on that asset's cap.

### Likelihood Explanation
Reachable purely through an AA's own oscript definition — no privileged actor, node, or hub cooperation is required. An AA author (or an AA invoked with malicious/attacker-controlled trigger data driving branch logic in the AA's `messages`/`cases`) can construct a response with two `payment` messages targeting the same capped asset (e.g., paying different addresses in two separate payment blocks) before an internal merge step neutralizes it. Whether this is exploitable in the current `mci` regime depends on whether `pemCurvesFixMci` has already passed on the network being analyzed (the merge would prevent it post-upgrade) — I was not able to fully confirm from the available code whether other message-construction paths (e.g., `bounce`/`cases` templates producing multiple message arrays for the same trigger) could still generate duplicate same-asset payment messages that reach `sendUnit()` post-merge without going through `mergeMessagesAndOutputs`, since the merge is only applied once at `aa_composer.js:1287-1288` and not re-applied if messages are regenerated/extended afterward (e.g., `objBasePaymentMessage` push at `aa_composer.js:1362-1365`). This residual uncertainty should be verified against the exact deployed `mci`/upgrade state.

### Recommendation
Track already-issued capped assets for the in-progress response unit in-memory (e.g., in a `Set` or on `objValidationState`) rather than relying solely on a DB query, and check/update this local state before/after each `issueAsset()` call, in addition to the DB check. Alternatively, ensure `mergeMessagesAndOutputs()` (or an equivalent dedupe) unconditionally runs on the final message list immediately before `completePaymentPayload`/`issueAsset` are invoked, regardless of `mci`, and re-runs if messages are mutated afterward (e.g., after appending `objBasePaymentMessage`).

### Proof of Concept
1. Define an AA whose `messages`/`cases` oscript, for a given trigger, produces two separate `payment` messages both paying out the same capped asset `X` (defined earlier with `cap: N`) to different addresses, with total requested amount exceeding the AA's current balance of `X` for both messages combined.
2. Ensure the code path that reaches `sendUnit()` bypasses/precedes the `mergeMessagesAndOutputs` merge (e.g., verify against the network's current `mci` relative to `constants.pemCurvesFixMci`, or find a message-construction path executed after the merge step).
3. On processing the trigger, `completePaymentPayload` is invoked once per message via `async.eachSeries` (`aa_composer.js:1298`); each call independently reaches `issueAsset()` (`aa_composer.js:1175`), and each queries `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` (`aa_composer.js:1196`) against the DB, which has not yet recorded either issuance (both are still only in `payload.inputs` in memory).
4. Both calls succeed, each issuing `objAsset.cap` amount of asset `X`, producing a response unit whose total issued amount for `X` is `2 * cap`, violating the asset's cap invariant once the unit is saved and stabilized. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
