## Title
Uncaught `throw Error()` assertions in unit/double-spend validation crash the entire node process on a crafted unit - (File: `validation.js`, function `checkForDoublespends`)

### Summary
The Wireshark CVE is a DoS in a protocol dissector: a single malformed/crafted input triggers an unhandled crash condition that the dissector's developers believed could "never happen." `ocore` has an analogous bug class: several code paths in the unit-validation pipeline encode developer assumptions as bare `throw Error(...)` ("unreachable code…") rather than as regular validation errors returned through the `ifUnitError`/`ifJointError`/`callback(err)` machinery. Because the whole process installs a global `uncaughtException` handler that deliberately re-throws to kill the process, any single posted unit that violates one of these "impossible" assumptions crashes the node that validates it — the same "malformed input → dissector/parser crash → DoS" pattern as the Opus bug, but here the "dissector" is `validation.js`'s unit/double-spend validator and the blast radius is every full node/hub that receives and validates the propagated unit.

### Finding Description
`validation.js` validates messages coming from an ordinary unit poster through `validatePaymentInputsAndOutputs` → `checkInputDoubleSpend` → `checkForDoublespends`: [1](#0-0) 

Inside the per-row callback, the code assumes that once a conflicting spend is found to be *included* in the current unit's ancestry (`bIncluded`) and stable (`main_chain_index <= last_ball_mci`), its `sequence` can only be `'good'`; any other value is treated as impossible:

These `throw`s happen inside `conn.query(...)` result callbacks and `graph.determineIfIncludedOrEqual` callbacks — deep inside async chains, not inside the `try { … } catch(e) { … }` blocks that wrap the top-level unit-hash/payload-hash calculations in `validate()`. Any exception thrown here propagates up as an uncaught exception in the event loop.

The process explicitly turns any uncaught exception into a fatal crash by design:
```js
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    console.error('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [4](#0-3) 

This is the exact same bug class as the Wireshark CVE: a developer-assumed-impossible state, reachable from attacker-supplied, low-trust input (a posted unit's inputs/spend-proofs and the addresses/units they reference), that turns a "this should never happen" assertion into a crash. `checkForDoublespends` is reached for every payment message (base or asset) and every spend-proof set, driven entirely by the double-spend query results and the values an attacker puts in `payload.inputs`/`spend_proofs` and the addresses that co-sign the unit — i.e. it is reachable by any unprivileged unit poster who controls both sides of a crafted double-spend (e.g. via multiple authors or addresses they control), not by a "malicious peer/hub" acting on the wire.

### Impact Explanation
Any node (full node, hub, or witness) that runs `validate()` on the crafted unit hits the `throw Error(...)`, which is uncaught and, per the `uncaughtException` handler, crashes the entire process. Because the unit is a normal joint that gets gossiped/forwarded (`forwardJoint`/`purgeDependenciesAndNotifyPeers`) and re-validated by every peer that receives it, a single crafted unit can propagate through the network and crash every node/hub that processes it — a network-wide denial of service preventing the network from validating/confirming new units, which matches the accepted impact category "a network unable to confirm new units."

### Likelihood Explanation
Reaching the specific `throw` requires crafting a genuine double-spend scenario (two inputs/spend-proofs referencing the same output/spend-proof key from different units) where the stability/sequence bookkeeping lands in the state the author believed unreachable (stable + included + non-good sequence, or a conflicting record attributed to a foreign address). This requires some familiarity with the sequence/stability state machine but no privileged access — only the ability to construct and sign units, something any wallet user can do. Given how many independent "assert-via-throw" branches exist in this one function alone (three separate unreachable-state throws), and that these represent an assumption about invariants across multiple asynchronous MC-stability computations, the likelihood that at least one is reachable via a carefully sequenced pair/set of conflicting units is realistic, mirroring how the Wireshark dissector's "impossible" buffer state was in fact reachable via crafted packets.

### Recommendation
- Replace all `throw Error(...)` "unreachable code" assertions in `checkForDoublespends` (and analogous assumption-based throws elsewhere in `validation.js`/`aa_validation.js`/`definition.js` reachable from unit content) with graceful validation-error returns (`cb2(error)` / `callbacks.ifUnitError(...)`) instead of process-crashing exceptions.
- Wrap the double-spend/stability callback chains in `try/catch` at the boundary where they are invoked from `validate()`, converting any unexpected exception into `ifUnitError`/`ifJointError` rather than letting it bubble to `uncaughtException`.
- Add fuzz/property tests that specifically try to construct conflicting-input/spend-proof scenarios that exercise the "impossible" state, to confirm the invariant actually holds before relying on `throw` as a safe assertion.
- Consider not converting all uncaught exceptions into an unconditional process kill in production (`network.js:4542`) for exceptions triggered while validating externally-supplied units, since this converts every latent internal assertion bug into a network-reachable DoS.

### Proof of Concept
A full working exploit requires reproducing the exact sequence/stability bookkeeping to land in the "impossible" branch, which is not verifiable without live database state; however, the reachable path is deterministic given the trigger conditions:
1. Attacker crafts two units, A and B, spending the same output/spend-proof key from addresses under attacker control, arranged so that unit B is included in the ancestry of a subsequently posted unit C's `parent_units`, and so that stability processing marks the conflicting record's `sequence` as neither `'good'` nor `'final-bad'` at the time C is validated (i.e., leaves it `'temp-bad'` while already stable and included).
2. Attacker posts/broadcasts unit C.
3. Every node that validates C runs `checkForDoublespends` → hits `throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit)` at [5](#0-4) , which is uncaught and crashes the process via [4](#0-3) .

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments
							if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}
