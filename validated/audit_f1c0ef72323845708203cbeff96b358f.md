### Title
Webhook signature verification authenticates the payload's organization but never binds it to the repository/commit that handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The webhook pipeline verifies the HMAC signature using a secret selected from `repository.owner.login` (or `organization.login`), but the actual object written to (a `Stack` via `repository.full_name`, or in the `status` event a `Commit` matched purely by `sha`) is never checked against that authenticated organization. This is the same class of bug as the referenced `_depositAmount` finding: a value that is trusted/acted upon is never verified to be the same value that was actually authorized/covered by the "signature" check.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization's secret to use for HMAC verification solely from the top-level owner field of the JSON body: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` computes HMAC-SHA1 over the raw body using the secret configured for that organization: [3](#0-2) 

However, once the signature passes, the handlers resolve *what to act on* from a completely independent field of the same attacker-supplied JSON body. `Handler#stacks` resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`, with no cross-check against the `repository.owner.login` value that was used to select the verifying secret: [4](#0-3) 

`StatusHandler` is worse: it doesn't even use `full_name`/repository at all — it matches purely on a global `sha`, across every `Commit` in the entire Shipit installation, regardless of repository or organization: [5](#0-4) 

Shipit explicitly supports hosting multiple independent GitHub organizations/apps behind one instance, each with its own webhook secret (documented multi-tenant configuration): [6](#0-5) 

The broken equality is:
`organization whose secret authenticated the request (repository.owner.login)` ≠ `repository/commit actually mutated by the handler (repository.full_name / global sha match)`

Because nothing enforces `repository.owner.login == owner(repository.full_name)`, a party who legitimately controls the webhook secret for **their own** tenant (Org A) can forge a signature that is valid for Org A, while setting `repository.full_name` (or, for `status` events, just `sha`) to point at a **different tenant's** repository/commit (Org B) hosted on the same Shipit instance. Additionally, per `verify_webhook_signature`, if any configured organization has no `webhook_secret` set — an explicitly documented "optional" setting — the check trivially returns `true` for any payload claiming that organization, requiring no credential at all: [7](#0-6) , [8](#0-7) .

### Impact Explanation
This breaks cross-repository/cross-tenant isolation:
- Via `PushHandler`, a request "signed" for Org A but carrying `repository.full_name` of an Org B stack enqueues `stack.sync_github(expected_head_sha: ...)` for a stack the attacker does not own [9](#0-8) .
- Via `StatusHandler`, the attacker can inject a fabricated commit status (e.g. `state: "success"`) onto **any** commit sha known to the attacker anywhere in the Shipit database, with no relation whatsoever to the organization/repo used for signature verification [5](#0-4) . Since Shipit uses commit statuses to gate deploy safety/CI checks, this can be used to falsify the CI state of a commit belonging to a stack/repository the attacker has no rights to, potentially unlocking an otherwise-blocked deploy — an unauthorized deploy, matching the Critical impact bar for this engine.

### Likelihood Explanation
Any principal that is legitimately provisioned a webhook secret for one tenant/organization on a multi-org Shipit deployment (a documented, supported configuration) can exploit this with a single crafted HTTP POST to the public `/webhooks` endpoint — no repository write access, no `ApiClient` token, and no access to the victim organization's own secret is required. The condition also holds unconditionally (zero credentials needed) whenever any configured organization omits the optional `webhook_secret`.

### Recommendation
After selecting the organization/secret used for signature verification, enforce that every repository- or commit-scoped field the handler subsequently reads (`repository.full_name`, and any `sha` used for lookup) actually belongs to that same authenticated organization before processing the event — i.e., scope `Commit`/`Stack`/`Repository` lookups by the verified organization rather than trusting unrelated fields from the same unauthenticated JSON body.

### Proof of Concept
1. Shipit is configured with two tenants as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (attacker-controlled) and `OrgTwo` (victim, hosts a stack gated on CI status).
2. Attacker computes a valid `X-Hub-Signature` using `OrgOne`'s known webhook secret over a JSON body of their choosing.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "OrgOne"}, "full_name": "OrgOne/decoy"},
  "sha": "<victim commit sha belonging to OrgTwo's stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "OrgOne")` and successfully verifies the signature (it was legitimately computed with `OrgOne`'s secret) [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgTwo commit (unrelated to `OrgOne`), and calls `create_status_from_github!`, injecting a forged "success" status [5](#0-4) .
6. OrgTwo's deploy safety checks now observe a fabricated green CI status for a commit the attacker never had rights over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
