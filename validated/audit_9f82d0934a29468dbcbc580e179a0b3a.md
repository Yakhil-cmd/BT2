### Title
Cross-organization forged commit status via globally-scoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a `status` webhook against the GitHub App belonging to `repository_owner`, an attacker-controlled field read from the same unsigned-at-this-point-of-inspection payload. `Shipit::Webhooks::Handlers::StatusHandler#process` then looks up the commit to mutate purely by `Commit.where(sha: params.sha)` with no repository/stack scoping at all, so a payload correctly signed by org A's webhook secret can still write a `Status` onto a commit that belongs to org B's stack, as long as the attacker knows (or can guess) a `sha` that exists in org B's history.

### Finding Description
The broken binding, stated explicitly: the equality that must hold is `organization_whose_secret_verified_request == organization_owning_repository_of_commit_being_mutated`. In this code path that equality is never enforced.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (line 61), an attacker-supplied JSON field, and resolves `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp`, then checks `github_app.verify_webhook_signature(signature, raw_post)` [1](#0-0) . `verify_webhook_signature` only computes an HMAC over the raw body using that org's `webhook_secret` [2](#0-1) . Nothing here ties the signature check to which org's repository is actually referenced elsewhere in downstream processing — it just confirms *some* org (chosen by the attacker via the same payload) signed the raw bytes with its own secret.
- The handler dispatch (`app/controllers/shipit/webhooks_controller.rb:10-15`) passes the parsed JSON straight to `StatusHandler.call`.
- `StatusHandler#process` does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This is a bare `Commit` query — not `stacks.where(...)` or `Repository.from_github_repo_name(repository_name).stacks.commits.where(sha:)` — so it is not scoped to any repository at all, unlike, e.g., `CheckSuiteHandler#process`, which correctly scopes through `stacks.where(branch: ...)` derived from `Repository.from_github_repo_name(repository_name)` before touching commits [4](#0-3) [5](#0-4) .

Attack flow:
1. Preconditions: the Shipit operator has configured `Shipit.github_apps` with at least two orgs/apps, e.g. attacker's own org "A" (attacker legitimately owns this GitHub App/org and its `webhook_secret`) and victim org "B" whose repository has a stack with known commit SHAs (SHAs are public git object identifiers, obtainable by anyone who can read the victim's repo, which is explicitly in-scope for an "unprivileged" attacker).
2. Attacker crafts a `status` event body: `{"sha": "<victim's real commit sha in org B's stack>", "state": "success", "repository": {"owner": {"login": "A"}}, ...}`, computes `X-Hub-Signature` using org A's own `webhook_secret` (which the attacker owns), and POSTs to `/webhooks`.
3. `verify_signature` resolves `Shipit.github(organization: "A")`, verifies successfully (attacker's own signature, correctly computed) — no exception, `verified == true`.
4. `StatusHandler#process` runs `Commit.where(sha: <victim's sha>)`, finds the commit under org B's stack (because the query is global, not filtered by owner "A"), and calls `commit.create_status_from_github!(params)`, writing a forged `Status` row (e.g., `state: 'success'`) onto org B's commit.

Existing guards that fail to prevent this:
- `verify_signature` verifies *a* body/secret pairing, but does not compare `repository_owner` to the actual owner of the resource being mutated downstream — the handler never re-derives or checks `repository.full_name` against the committed org.
- `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`, `state`, etc. — it has no `repository` requirement and performs no ownership check [6](#0-5) .
- `Handler#stacks`/`Handler#repository_name` helpers exist and are used correctly by other handlers (e.g. `CheckSuiteHandler`, `pull_request/*` handlers) but `StatusHandler` does not use them at all.

### Impact Explanation
Any org/app registered as a tenant in `Shipit.github_apps` can, using only its own legitimate webhook secret, forge a `Status` (success/failure/error/pending) onto any commit in any other tenant's stack, provided it can guess or read the target SHA. Since `deployable_status`/`commit_status` webhooks fire on transitions and continuous deployment can be gated on commit state, a forged `success` status can unblock or trigger continuous delivery/merge-request processing for a victim's stack (`ProcessMergeRequestsJob`, `ContinuousDeliveryJob` are scheduled from status transitions) even though the attacker has no access to that org, repository, or its real CI. This is a cross-repository/cross-tenant write triggered by an unauthenticated (with respect to the victim tenant) party, matching "Critical — a payload for one repository mutating another's stack, commit, task or team." Repeatable per request against any known SHA in any stack managed by the shared Shipit instance.

### Likelihood Explanation
Requires the Shipit instance to be multi-tenant, i.e., `Shipit.github_apps` configured with more than one organization/app (a supported and documented configuration, not a misconfiguration). The attacker needs to control (or register) one of those orgs' GitHub Apps — which the threat model explicitly grants ("attacker owns a GitHub organization/app configured as a second entry"). No Shipit secrets, sessions, or API tokens are required; only the attacker's own legitimate webhook secret and knowledge of a target commit SHA (public information). This is trivially repeatable and does not depend on timing, race conditions, or fragile guessing beyond a real git SHA.

### Recommendation
In `StatusHandler#process` (and any other handler using a bare `Commit`/model lookup), scope the commit lookup through the repository named in the payload and verify it matches the org that authenticated the request:
1. Resolve `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` (as `Handler#stacks` already does) and only search `stacks.commits.where(sha: params.sha)` instead of the global `Commit.where(sha:)`.
2. In `verify_signature`, after resolving `github_app` from `repository_owner`, also assert that `params.dig('repository','full_name')`'s owner matches `repository_owner` consistently (defense in depth), and reject payloads where the app that verified the signature does not equal the app configured for the repository actually referenced.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status webhook signed by org A cannot forge a status on org B's commit" do
  # Configure two orgs each with distinct webhook secrets
  Shipit.stubs(:github_apps).returns(
    'org-a' => GitHubApp.new('org-a', webhook_secret: 'secret-a'),
    'org-b' => GitHubApp.new('org-b', webhook_secret: 'secret-b')
  )

  victim_commit = shipit_commits(:first) # belongs to a stack under org "org-b"

  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'org-a' } } # attacker names their OWN org
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'secret-a', body) # signed with attacker's own secret

  @request.headers['X-Github-Event'] = 'status'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: body, as: :json
  end
  # Currently this assertion FAILS: verify_signature passes (org-a's own valid signature),
  # and Commit.where(sha:) finds victim_commit regardless of the org named in the payload,
  # so a Status row IS created under org-b despite only org-a having authenticated.
end
```
Binding checked before/after: `organization_whose_secret_verified_request` (= "org-a") vs `organization_owning_commit_mutated` (= "org-b", the victim's stack owner). They do not match, yet the write proceeds — confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
