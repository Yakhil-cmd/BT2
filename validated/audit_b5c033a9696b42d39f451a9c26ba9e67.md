### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` enables unauthorized PR merge - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no constraint tying the lookup to the repository named in the (correctly) signature-verified webhook payload. Because GitHub webhook signature verification in this engine is keyed only by *organization* (`Shipit.github(organization: repository_owner)`), a legitimately signed "status" event for one repository can plant a forged `Status` row on a `Commit` belonging to an entirely different stack, which can flip `Shipit::MergeRequest#all_status_checks_passed?` to `true` and trigger an unauthorized `merge_request.merge!`.

### Finding Description
The broken binding, stated explicitly: the audit assumes `verified_payload.repository.full_name == commit.stack.repository.full_name` for every `Commit` row touched by the handler. This is false. `StatusHandler#process` does: [1](#0-0) 

`Commit.where(sha: params.sha)` is a *global, unscoped* query across every stack in the installation; it never reads or compares `params.dig('repository', 'full_name')`. For each matching `Commit`, `create_status_from_github!` is invoked, which writes the status using that commit's own (real) `stack_id`: [2](#0-1) [3](#0-2) 

Signature verification only proves the payload was signed with the secret of *some* organization named in the payload itself — a value the requester fully controls in the JSON body: [4](#0-3) 

`Shipit::GitHubApp#verify_webhook_signature` keys off a single shared `webhook_secret` per organization, not per repository: [5](#0-4) 

So any actor able to obtain a genuinely GitHub-signed `status` event for that organization (e.g. by having push access to *any* repo in the org and calling GitHub's Create Commit Status API with an arbitrary `sha`, which GitHub does not validate against actual repo contents) can name any `sha` value in the payload. If that `sha` happens to match a `Commit` row belonging to a *different* stack — e.g. the head commit of the victim's own pending `MergeRequest`, whose `sha` is public information visible on the PR page — the forged status is attached to the victim stack's commit with the victim stack's `stack_id`.

The forged status can also be made to shadow the genuine one: `StatusHandler` accepts an attacker-controlled `created_at`: [6](#0-5) 

`Commit#statuses` is ordered `created_at: :desc`, and `Status::Group` selects the effective status per context by taking the first (`uniq(&:context)`) after that ordering: [7](#0-6) [8](#0-7) 

By setting a `created_at` later than the genuine CI's real status, the attacker's forged "success" status for the required context wins, even after `MergeRequest#refresh!` re-fetches genuine statuses from GitHub (that call only *adds* new rows via the same `replicate_from_github!` path; it never removes the earlier forged row): [9](#0-8) [10](#0-9) 

This makes `all_status_checks_passed?` return `true`, and `merge!` is called, invoking `stack.github_api.merge_pull_request` with the victim stack's own real GitHub App credentials against the victim's real repository: [11](#0-10) 

No existing guard closes this gap: `verify_signature` only authenticates the org named in the JSON body (attacker-supplied), `drop_unhandled_event` only checks the event type is handled, the `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`/`state`/`context`/`created_at` — not their relationship to any repository — and there is no model validation or query constraint anywhere in the `Commit`, `Status`, or `StatusHandler` code binding the status to the repository named in the payload.

### Impact Explanation
A forged status write lands on a `Commit`/`Status` row belonging to a stack the attacker does not own, and can cause `Shipit::MergeRequest#merge!` to execute `stack.github_api.merge_pull_request` — an unauthorized merge into a repository the requester never authenticated against. This is repeatable against any stack in the installation whose `sha` an attacker can discover (trivially public via the PR page) and whose organization the attacker has some webhook-triggering foothold in, matching the "payload for one repository mutating another's stack/commit" Critical impact category.

### Likelihood Explanation
Preconditions per the question are already given: `merge_queue_enabled: true` on the victim stack, a pending `MergeRequest` with a known head `sha`, and a required status context whose name the attacker also knows. The attacker needs a genuinely GitHub-signed `status` webhook for *some* organization Shipit has configured — this requires the attacker to have push/API access to at least one repository under an organization whose webhook secret Shipit trusts (the attacker's "own repository" as stated in the question). No Shipit secrets, sessions, or API tokens are required, matching the "unprivileged attacker" constraints in the rules.

### Recommendation
Scope the `StatusHandler` (and analogous handlers) lookup by repository, not sha alone: validate `params.dig('repository', 'full_name')` (or `repository.owner.login` + `name`) against `commit.stack.github_repo_name` before calling `create_status_from_github!`, e.g. `Commit.where(sha: params.sha).select { |c| c.stack.github_repo_name == payload_repo_full_name }`. More robustly, key webhook signature verification and dispatch off the specific repository in the payload rather than trusting any commit-sha match across the whole database.

### Proof of Concept
Minitest plan (model/job level, no live GitHub):
1. Create `stack_a` (attacker-controlled org, arbitrary) and `stack_b` (`merge_queue_enabled: true`).
2. Create `commit_x = shipit stack_b.commits.create!(sha: "X"*40, ...)` and a pending `MergeRequest` on `stack_b` with `head: commit_x`.
3. Assert baseline: `merge_request.all_status_checks_passed?` is `false` (no statuses / required context missing).
4. Simulate the forged webhook by directly invoking `Commit.where(sha: commit_x.sha).each { |c| c.create_status_from_github!(OpenStruct.new(state: 'success', context: required_context, created_at: Time.now, description: nil, target_url: nil)) }` — mirroring `StatusHandler#process`, without ever referencing `stack_b` or its repository.
5. Assert `merge_request.reload.all_status_checks_passed?` is now `true`.
6. Stub `stack_b.github_api.expects(:merge_pull_request)` and call `merge_request.merge!`; assert the stub is invoked, proving the merge fires from a status that never authenticated against `stack_b`'s repository.
7. Assert as the broken-binding check: `status.stack_id == stack_b.id` while the originating (simulated) webhook payload's repository/org never equals `stack_b.repository.full_name` — demonstrating the missing equality check called out in the question.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
