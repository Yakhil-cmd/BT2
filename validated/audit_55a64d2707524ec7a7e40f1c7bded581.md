### Title
Repeated Full AA-Definition Revalidation Before Duplicate-Address Check Enables CPU-Exhaustion DoS - (File: `validation.js`, `aa_validation.js`)

### Summary
When a unit contains a `definition` message (used to register an Autonomous Agent), `validateInlinePayload` performs the entire expensive AA-definition validation (`aa_validation.validateAADefinition`, which recursively walks the whole message tree and formula-validates every field, up to the network's complexity/op limits) *before* checking whether an AA has already been registered at that exact address. The actual "already exists" deduplication only happens later, at write time, inside `storage.insertAADefinitions`, via an `INSERT OR IGNORE`/`affectedRows===0` check.

### Finding Description
The relevant code path is: [1](#0-0) 

For a `definition` message, the only cheap check performed before the expensive work is that `payload.address === objectHash.getChash160(payload.definition)` (a single hash comparison). Immediately afterward, the full, potentially heavy validation is invoked unconditionally: [2](#0-1) 

`aa_validation.validateAADefinition` recursively validates every message, payload field and embedded oscript/ojson formula in the AA template, running the formula validator (complexity/op counting) on each formula found, and recursing up to `MAX_DEPTH` with a counter that periodically yields via `setImmediate`: [3](#0-2) [4](#0-3) 

Because an AA's address is deterministically `getChash160(definition)`, the *same* definition JSON always produces the *same* address. There is no check anywhere in `validateMessage`/`validateInlinePayload` that queries `aa_addresses` (or `storage.readAADefinition`) for an already-registered/already-validated AA at that address before repeating the entire expensive validation. The only place this deduplication occurs is at commit time: [5](#0-4) 

This mirrors the reported bug class exactly: expensive, unbounded work is performed unconditionally, and the cheap "does this already exist" check that could short-circuit the expensive path is applied only after the costly computation has already run (and, in ocore's case, on every subsequent unit that reposts the identical, already-registered definition, since nothing prevents an attacker from constructing many distinct units — different parents/authors/other messages — that each carry the exact same `definition` payload/address).

### Impact Explanation
An attacker can craft an AA definition near the network's maximum allowed complexity (`MAX_COMPLEXITY`/`MAX_OPS`, enforced only inside `validateFormula`, i.e., after most of the recursive walk has already started) and repeatedly post many distinct units (varying unrelated fields such as parents, unrelated messages, or timestamp) that all embed the identical, maximally-complex `definition` payload/address. Every honest full node that receives and validates these units must re-run the full, CPU-heavy `validateAADefinition` recursive/formula-validation pass for each one, even though the AA at that address was already accepted as valid in an earlier unit. Because the cheap existence check is deferred to write time, this validation cost cannot be avoided by an early exit. Repeated at scale, this creates a CPU-exhaustion condition on validating nodes, which is the same "expensive work performed unconditionally before a duplicate check" root cause as the external report, and can degrade network-wide validation throughput/availability — a node unable to keep up with validation cannot confirm new units in a timely manner.

### Likelihood Explanation
The path is reachable by any unprivileged unit poster: constructing a unit with a `definition`-app message requires only being able to post any well-formed unit with a valid parent set and enough bytes/fee to be a "free" unit — no elevated privilege, no dependency on a malicious peer/hub/node. Building a definition payload near the complexity ceiling and repeating it in multiple otherwise-distinct units is straightforward, since address collision is required for the exploit (same address → same expensive path revalidated) and complexity limits are public constants known in advance. The main uncertainty is the exact economic cost (unit posting/byte fees vs. CPU cost of validation) which bounds the practical amplification factor; I could not fully quantify `MAX_COMPLEXITY`/`MAX_OPS` from `constants.js` in this session, so the precise magnitude of the CPU/fee asymmetry is unconfirmed and would need to be measured empirically.

### Recommendation
Before invoking `aa_validation.validateAADefinition` in `validateInlinePayload`'s `"definition"` case, add a cheap existence check (e.g. `storage.readAADefinition(conn, payload.address, ...)` or an equivalent query/cache of `aa_addresses`) for the target address at/below the relevant mci. If the exact same address (i.e., the exact same definition, since address is content-derived) has already been validated/stored, skip the expensive re-validation and simply allow the message to pass this check quickly (the "already exists" branch, if desired, could still enforce `bAlreadyPostedByUnconfirmedAA` bookkeeping as `insertAADefinitions` does, but without repeating the full recursive/formula validation). This mirrors moving the duplicate/existence check to occur before, rather than after, the resource-intensive operation, closing the CPU-exhaustion vector.

### Proof of Concept
1. Craft an AA definition `D` whose nested `messages`/formulas approach (but stay under) `constants.MAX_COMPLEXITY`/`MAX_OPS`, so that `aa_validation.validateAADefinition` performs the maximum allowed amount of recursive/formula validation work before succeeding.
2. Compute `address = objectHash.getChash160(D)`.
3. Post unit U1 containing message `{ app: 'definition', payload: { address, definition: D } }`. It passes validation (paying the cheap hash check plus the one-time full validateAADefinition cost) and is accepted; `storage.insertAADefinitions` registers `address` in `aa_addresses`.
4. Craft N additional units U2..U(N+1), each with different parents/unrelated content but embedding the identical `definition` message `{ address, definition: D }`.
5. Each of these units reaches `validateInlinePayload`'s `"definition"` case in `validation.js` (lines 1747-1767) and is forced through the same full-cost `aa_validation.validateAADefinition` pass again, because no pre-check queries `aa_addresses`/`readAADefinition` for the already-registered address before doing so; the "already exists" short-circuit in `storage.insertAADefinitions` (storage.js lines 904-940) only triggers after validation has already completed and only at write/commit time.
6. Repeating this with many such units imposes N× the CPU cost of a single maximal AA-definition validation on every validating node, for units that add no new AA and whose duplicate nature could have been detected up front.
