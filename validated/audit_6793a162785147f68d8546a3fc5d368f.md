### Title
Cross-tenant webhook authentication bypass via `repository.owner.login` / `repository.full_name` binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (`Shipit.github_organizations` with per-org `webhook_secret`s), the webhook HMAC signature is verified against the GitHub App configured for the organization found at `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload key their lookups off the independent `repository.full_name` field. An attacker who administers their own low-trust org/GitHub-App installation on the same shared Shipit instance knows their own `webhook_secret` and can therefore self-sign a payload whose `repository.owner.login` points at their own org (so signature verification passes) while `repository.full_name`/`sha` point at a victim org's repository, causing Shipit to act on the victim's stack data without ever validating against the victim's secret.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the signature against using only the organization derived from the payload: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-organization secrets via `github_app_config`, which is only meaningfully differentiated when the engine is configured for "Using Multiple GitHub Applications" (documented in `docs/setup.md`): [3](#0-2) 

Once the signature check passes, `create` dispatches the *entire raw payload* to handlers: [4](#0-3) 

Every default handler resolves the target repository/stack from a **different** payload field — `repository.full_name` — via the shared `Handler` base class, completely independent of the `repository.owner.login`/`organization.login` field used for signature routing: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`StatusHandler#process` writes a status directly by matching `sha` in the payload against any `Commit` row (no repo scoping at all): [6](#0-5) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Because `repository.owner.login` (used only for signature key selection) and `repository.full_name` (used for the actual write) are independent, unrelated JSON fields in the same payload, and only the former is covered by the HMAC-secret binding decision — not by content — an attacker who legitimately possesses one org's `webhook_secret` can construct a payload where:
- `repository.owner.login` = attacker's own org (verifies against attacker's own known secret), and
- `repository.full_name` / `sha` = victim org's repository / a victim commit SHA.

The signature is computed over the raw body content, but since the attacker fully controls that body (including the mismatched fields) and knows the secret used to sign it, the signature check succeeds even though the *content being acted upon* belongs to a different, unauthenticated organization. This breaks the intended binding: `organization authenticated == repository written`.

### Impact Explanation
This allows cross-organization forgery of GitHub events against stacks belonging to organizations the attacker does not control. Concretely: `StatusHandler` lets an attacker post arbitrary commit statuses for a victim's commits, which can move CI-gated `continuous_deployment` or `merge` queue decisions (`Merge Queue`/`ci.require` logic depends on these statuses) toward automatically triggering deploys or merges. `PushHandler` and `CheckSuiteHandler` similarly act on `repository.full_name`. This matches the required Critical/High impact bar of an unauthorized deploy/merge via cross-repository writes, achieved purely by a network request with no GitHub App private key, session, or `ApiClient` token.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (each with an independently issued `webhook_secret`, as documented for multi-tenant setups) and requires the attacker to control (or be an admin of) at least one of those organizations/GitHub App installations so they know its `webhook_secret`. Given that condition — which is an explicitly supported and documented Shipit deployment mode, not a misconfiguration outside engine scope — exploitation needs only a single crafted HTTP POST to `/webhooks`; no privileged token, session, or social engineering is required.

### Recommendation
Bind the payload fields used for HMAC secret selection and the payload fields used to resolve the acted-upon repository/stack. Concretely, after verifying the signature with the org-selected secret, re-derive/validate that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, and reject the webhook otherwise.

### Proof of Concept
1. Shipit is configured with multiple GitHub orgs, e.g. `attacker-org` (secret: `S_attacker`, known to the attacker) and `victim-org` (secret: `S_victim`, unknown to attacker), per `docs/setup.md`'s "Using Multiple Github Applications" schema.
2. Attacker crafts a `status` event payload:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_attacker, raw_body)` themselves and sets `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, which uses `S_attacker` — signature verifies successfully.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which matches `Commit.where(sha: params.sha)` for the victim commit (scoped only by `sha`, independent of the verified org) and writes a forged `success` status, potentially unblocking that stack's merge queue/continuous deployment.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
