### Title
Unfiltered PR label injects `IFS` into the deploy step environment, altering shell word-splitting - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) into the stack environment with no allowlist, and this environment flows unfiltered through `TaskCommands#env` / `DeployCommands#env` into `Command#unbundled_env` and finally `PTY.spawn`. Because `Command#unbundled_env` merges `@env` **after** `BASE_ENV`, an attacker-controlled label such as `ifs` becomes `env['IFS'] = 'true'`, which is injected into the environment of the spawned shell process, capable of corrupting word-splitting of the deploy step's command string.

### Finding Description
The broken binding: `ReviewStack#env` should equal `super` filtered to a fixed, safe key allowlist, but instead:
```ruby
# app/models/shipit/review_stack.rb:84-93
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
``` [1](#0-0) 

There is no key restriction here — any label name, uppercased, becomes an environment variable key with value `"true"`.

Labels are persisted verbatim from the untrusted webhook body by `LabelCapturingHandler#capture_labels`:
```ruby
pull_request.update!(labels: params.pull_request.labels.map(&:name))
``` [2](#0-1) 

The `params` schema only requires `labels` to be an `Array` of objects with a `name` `String` — no character or value restriction (confirmed by the existing test that emoji label names are accepted): [3](#0-2) 

This merged environment then flows unfiltered through the deploy pipeline: `TaskCommands#env` merges `@stack.env` (i.e., `ReviewStack#env`) directly:
```ruby
def env
  super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)
end
``` [4](#0-3) 

`DeployCommands#env` further merges on top of `super` (`TaskCommands#env`) without any allowlist: [5](#0-4) 

The deploy step commands are built with this full unfiltered env:
```ruby
def perform
  steps.map { |command_line| Command.new(command_line, env:, chdir: steps_directory) }
end
``` [6](#0-5) 

Finally, `Command#unbundled_env` merges `@env` (attacker-influenced) **last**, so it wins over `BASE_ENV`, and this hash is passed directly as the environment for `PTY.spawn`:
```ruby
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end

def start(&block)
  ...
  @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
  ...
end
``` [7](#0-6) 

Since `interpolated_arguments` is generally a single command-line string (e.g., `"bundle exec cap $ENVIRONMENT deploy"`), `PTY.spawn` invokes it via a shell (`/bin/sh -c "<string>"`). If the spawned shell's environment contains an `IFS` variable, POSIX-compliant shells consult the inherited `IFS` when they start (default is space/tab/newline, but Bash/`sh` will honor an inherited `IFS` unless the shell startup code resets it, which is not guaranteed for non-interactive `-c` invocations run by `PTY.spawn`). A crafted `IFS` value can change how the deploy step string is field-split, letting a value that is normally a single safe token become multiple tokens, potentially reinterpreting the argv boundaries of the executed command.

The existing tests only demonstrate that arbitrary uppercased label names populate `env` (`WIP`, `BUG`), which directly confirms there is **no key denylist or allowlist** for names like `IFS`: [8](#0-7) [9](#0-8) 

None of `filter_deploy_envs`/`filter_rollback_envs` (`DeploySpec#filter_deploy_envs`, using `EnvironmentVariables#permit` against the `deploy.variables` allowlist) are applied to this code path — those helpers are invoked from `Stack`/`Deploy`/`RollbacksController` for user-submitted deploy-trigger form variables, not for the `TaskCommands#env`/`DeployCommands#env` hash that is actually handed to `Command.new` for the deploy steps. This confirms `deploy.variables` allowlisting does **not** protect the real spawn env from PR-label-derived keys.

The attacker's exact PR: open (or already have) a fork PR against a repository configured with `provisioning_behavior: allow_all`, then apply a label literally named `ifs` (case-insensitive, becomes `IFS` after `.upcase`) via the GitHub UI/API on their own PR — an action fully within an unprivileged PR author's/labeler's control on their own PR (assuming they also have label permission, which is typical for PR authors on forks with a `pull_request_target`-less webhook flow, or by the `labeled`/`unlabeled` webhook simply reflecting the state at that time). The webhook (`pull_request` event, `labeled`/`opened`/`reopened` action) is processed by `LabelCapturingHandler`, persisting the label onto the review stack's `PullRequest#labels`. The next deploy of that review stack (continuous deployment or manual) invokes `DeployCommands#env`, which includes `IFS=true` in the process environment for every deploy step command spawned via `PTY.spawn`.

### Impact Explanation
Once `IFS` is attacker-controlled in the spawned shell's environment, deploy step command strings (which may embed further environment-variable expansions or unquoted paths) can be word-split differently than intended, changing which tokens the shell treats as the command name versus arguments. Combined with any step content containing unquoted expansions or attacker-influenced strings (commit SHAs, branch names, other label-derived tokens also merged into env), this creates a path toward argv reinterpretation on the deploy host running as the Shipit service user — a Command/PTY.spawn-based RCE class as defined by the impact rubric. This affects only the specific repository/review-stack whose `allow_all` provisioning policy processed the malicious PR, but is fully repeatable by any unprivileged contributor able to label their own fork PR, and would need to be combined with an actual splittable step to realize full RCE.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior: allow_all` (or already have an active, non-archived review stack so `labeled`/`unlabeled`/`reopened` events are captured), and the attacker must be able to add a label to their own PR (label permission is commonly available to PR authors or is auto-applied by bots/CI in real deployments). No Shipit session, API token, or GitHub secret is required — only a normal PR + label action, which is squarely within the described unprivileged-attacker capability set. This makes the precondition realistic under the stated `allow_all` threat model, though actual RCE additionally requires a deploy step whose command string is vulnerable to `IFS`-based re-splitting, which is environment/`shipit.yml`-dependent and not proven in this codebase alone.

### Recommendation
In `app/models/shipit/review_stack.rb#env`, restrict merged label-derived keys to a safe, fixed prefix or explicit allowlist (e.g., only allow keys matching `/\ASHIPIT_LABEL_/` or a curated set), and explicitly reject/strip environment-variable names that collide with shell-special variables (`IFS`, `PATH`, `LD_PRELOAD`, `BASH_ENV`, `ENV`, etc.) before merging into `super`. Additionally, harden `Command#unbundled_env` to always force a safe default `IFS` (e.g., `" \t\n"`) regardless of `@env` content, so no caller-supplied environment can override it.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (allow_all scenario)
test "#env does not allow PR labels to override IFS" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ifs"]

  assert_not_equal "true", stack.env["IFS"],
    "PR label should not be able to set IFS in the stack env"
end

# lib/shipit/command_test.rb (fast validation reaching PTY.spawn env)
test "Command#unbundled_env does not let caller env override IFS" do
  command = Shipit::Command.new("echo hi", env: { "IFS" => "true" }, chdir: ".")
  refute_equal "true", command.unbundled_env["IFS"]
end
```
Both assertions currently fail against the present code (`stack.env["IFS"] == "true"` and `command.unbundled_env["IFS"] == "true"`), demonstrating the unguarded binding between the pull request label name and the spawned process's `IFS`.
