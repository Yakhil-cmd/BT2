### Title
`is_valid_sig()` / `vrf_verify()` accept RSA and legacy ECDSA keys with no minimum key‑strength check - ([File: signature.js])

### Summary
The reported bug class is a BKS keystore accepting a legacy key format with an insufficiently strong (16‑bit) integrity key, i.e. a crypto‑format validator that checks structure/algorithm identity but fails to enforce a real security‑strength floor. The same class of defect exists in `signature.js`'s `validateAndFormatPemPubKey()`, which is reachable from oscript/AA formulas via `is_valid_sig()` and `vrf_verify()`.

### Finding Description
`validateAndFormatPemPubKey()` parses the DER header of an attacker‑supplied PEM public key, matches the OID against `objSupportedPemTypes`, and — for ECDSA keys — checks that the encoded key length matches the expected `hex_pub_key_length` for that specific named curve. [1](#0-0) 

Critically, this length/strength check is only performed `if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" ...)`; for RSA keys there is **no minimum modulus size enforced anywhere** — only an upper bound (`contentAloneB64.length > 736`, sized for RSA‑4096) is checked. [2](#0-1) [3](#0-2) 

The RSA algorithm identifier itself is unconditionally listed in `objSafePemTypes`, meaning it is treated as "safe" even after the `pemCurvesFixMci` hardening that was introduced to reject weak/legacy elliptic curves: [4](#0-3) 

Tests in the repo confirm that RSA keys as small as 700 bits are accepted by `is_valid_sig`, which is well below currently recommended RSA strength (2048+ bits) and approaches factorization-feasible sizes: [5](#0-4) 

In addition, even for the ECDSA branch, `objSupportedPemTypes` still lists numerous historically weak/legacy curves (56–68 byte keys, e.g. `secp112r1`, `secp112r2`, `sect113r1`, `wap-wsg-idm-ecid-wtls*`) that are only excluded when `bPostPemCurvesFix` is true; when that flag is false (pre-fix MCI / for calls that don't gate on it) these ~56–68-bit-security curves are accepted as valid: [6](#0-5) [7](#0-6) 

These functions are directly reachable from unprivileged input: an AA trigger sender (or unit poster invoking an AA formula) supplies `message`, `pem_key`, and `signature` as `trigger.data` fields evaluated by `is_valid_sig`/`vrf_verify` inside `formula/evaluation.js`: [8](#0-7) [9](#0-8) 

### Impact Explanation
If an AA's logic (e.g., an oracle-gated payout, a multisig-like access condition, or a bridge/attestation AA) relies on `is_valid_sig`/`vrf_verify` to authorize a state transition (e.g., "release funds if this key signs this message"), an attacker who can factor a weak RSA modulus (≤700–1024 bits) or break a legacy 56–68-bit-security ECDSA curve can forge a signature that the AA formula will accept as valid. This can lead to unauthorized AA fund release/spending or manipulation of AA logic gated on `is_valid_sig`, which maps to the "AA fund loss" and "unauthorized spending" impact categories.

### Likelihood Explanation
Exploitability depends on an AA definition trusting a specific externally-supplied or attacker-influenced weak key for authorization via `is_valid_sig`/`vrf_verify` — this is a design choice made by individual AA authors, not a universal protocol invariant, so likelihood is contract-dependent rather than protocol-wide. However, because `ocore` provides no minimum-strength enforcement for RSA and still enumerates a long list of legacy ECDSA curves as "supported" (gated only by the `bPostPemCurvesFix`/`pemCurvesFixMci` flag), any AA author who uses these primitives without independently vetting key strength is silently exposed, and the acceptance path itself is reachable purely from posted trigger/unit data with no special privilege.

### Recommendation
- Enforce a minimum RSA modulus size (e.g., ≥2048 bits) in `validateAndFormatPemPubKey()` in `signature.js`, mirroring the existing max-size check.
- Restrict `objSupportedPemTypes`/`objSafePemTypes` unconditionally (not only gated by `bPostPemCurvesFix`) to a small allow-list of modern, well-vetted curves and remove/deprecate all sub-128-bit-security legacy curves regardless of MCI.
- Consider surfacing key-strength metadata to oscript authors/documentation so AA definitions relying on `is_valid_sig`/`vrf_verify` can be audited for weak-key acceptance.

### Proof of Concept
1. An AA (or any oscript formula evaluated from unit/trigger data) contains a condition such as `is_valid_sig(trigger.data.message, trigger.data.pem_key, trigger.data.signature)` used to authorize a payout.
2. An attacker computes the private key for a 700-bit (or smaller, down to whatever RSA modulus fits the size cap) RSA key via known factorization techniques, or breaks a legacy ECDSA curve such as `secp112r1`/`wap-wsg-idm-ecid-wtls1` via discrete-log attacks feasible for ~56–68-bit security. [5](#0-4) [10](#0-9) 
3. The attacker submits a trigger unit with `pem_key` set to the weak key and `signature` forged with the recovered private key.
4. `validateAndFormatPemPubKey()` accepts the key (no minimum-strength check for RSA; legacy curve accepted when `bPostPemCurvesFix` is false), and `verifyMessageWithPemPubKey()` verifies the forged signature as valid, causing the AA formula to evaluate `true` and execute the attacker-desired branch (e.g., releasing funds) without possessing a legitimately strong key.

Note: I was not able to fully trace every AA/oscript sample in the repo that uses `is_valid_sig`/`vrf_verify` for fund-authorization logic (only `test/samples/order_book_exchange.oscript` and `test/samples/payment_channels.oscript` were found referencing it), so the concrete blast radius depends on how such AAs are deployed in practice; this is stated as a design/library-level weakness rather than a demonstrated end-to-end exploit against a specific live AA.
