### Title
Cross-organization `Team` confusion in `MembershipHandler#find_or_create_team!` allows escalation into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` validates a webhook's HMAC using the GitHub App/org named in the attacker-controlled payload itself, then `MembershipHandler` looks up the `Team` to mutate purely by `params.team.id` (GitHub's global numeric team ID), never checking that this ID belongs to the organization whose secret actually verified the request. An attacker who legitimately controls any second GitHub org/app configured in the same multi-tenant Shipit instance can therefore send a correctly-signed `membership` webhook for their own org that names a `team.id` belonging to a privileged `Team` (one referenced by `Shipit.github_teams`), causing a `Membership` to be created between their own real GitHub login and that privileged team.

### Finding Description
The broken binding, stated explicitly:

`verified_org(webhook) == params.dig('organization','login') (attacker-chosen)`, **not** `verified_org(webhook) == team.organization` (the org that actually owns the referenced `Team`/`team.id`).

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` solely from the JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), fetches `Shipit.github(organization: repository_owner)`, and verifies the HMAC with that org's `webhook_secret`. [1](#0-0) 
   This only proves the request was signed by whichever org the attacker *named in the payload* — if the attacker owns Org A (also configured in Shipit with its own app/secret, as supported by the multi-org config format), they can sign with Org A's real secret and set `organization.login: "OrgA"`, passing verification legitimately.

2. `MembershipHandler#process` / `#find_or_create_team!` then resolves the target `Team` **only by `params.team.id`** (a global GitHub numeric team ID), and only sets `organization` from the payload if the record doesn't already exist: [2](#0-1) 
   If a `Team` row with that `github_id` already exists (which is the normal state for any team listed in `Shipit.github_teams`, since those are pre-populated via `Team.find_or_create_by_handle`/`fetch_and_create_from_github`), `find_or_create_by!` returns the existing record and the block — including the `organization` assignment — never runs. There is no check that `params.organization.login` (the verified org) equals `team.organization` (the real owner of that team ID). [3](#0-2) 

3. `team.add_member(User.find_or_create_by_login!(params.member.login))` then creates a `Membership` for whatever `member.login` the attacker supplies — the attacker supplies their own real GitHub login, so `User.find_or_create_by_login!` resolves/creates their own genuine `User` row. [4](#0-3) [5](#0-4) 

4. `User#authorized?` then reads exactly this table with no additional org check: [6](#0-5) 

Existing guards do not close this gap: `verify_signature` authenticates *an* org, not *the specific team's* org; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross-field consistency between `organization.login` and `team.id`'s true owner. No code path re-derives the team's real organization from GitHub or compares it to the verified webhook org.

### Impact Explanation
A `Membership` row is written for a `Team` that the verified webhook organization does not own, letting an attacker's honestly-authenticated session pass `User#authorized?` and thereby access deploy/merge functionality gated by `Shipit.github_teams` — a privilege escalation into that authorization gate (High/Critical per the stated severity matrix: "escalation into `Shipit.github_teams` authorization"). The write is repeatable at will (attacker can also send `action: 'removed'`/`'added'` repeatedly) and is not scoped to the attacker's own repository/org — it mutates state (`Team`/`Membership`) belonging to a different tenant's authorization domain.

### Likelihood Explanation
Requires: (a) Shipit configured with more than one GitHub org/app (documented, supported multi-org config, e.g. `test/dummy/config/secrets_double_github_app.yml`), and the attacker legitimately controlling one of those secondary orgs/apps' webhook secret (their own, not a secret); (b) the attacker knowing the numeric GitHub `team.id` of the privileged team — this is a non-secret, globally-scoped integer that can often be discovered via GitHub's team API responses, prior team membership, or other leakage, not a credential. No possession of the target org's `webhook_secret`, `secret_key_base`, or any Shipit secret is required. This is a realistic, low-cost path in any Shipit deployment that federates multiple orgs.

### Recommendation
In `MembershipHandler#find_or_create_team!`, require that the org verified by `verify_signature` (i.e., the payload's `organization.login`, which was cryptographically tied to a specific `webhook_secret`) matches the `organization` already stored on any pre-existing `Team` with that `github_id`; reject (or no-op) the event if they diverge. More generally, pass the verified organization from the controller into the handler and validate it against the `Team`/`Repository` being mutated for every handler, not just rely on `github_id` lookups.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test "membership webhook from a different org cannot alter a team it doesn't own" do
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1 (fixture)

  # Attacker owns "OrgTwo" (configured with its own webhook_secret in Shipit)
  # and signs a membership payload naming OrgTwo, but referencing the
  # privileged team's real github_id belonging to "shopify".
  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name,
            slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: 'OrgTwo' },
    member: { login: 'attacker_real_login' },
    repository: { owner: { login: 'OrgTwo' } }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', ORG_TWO_WEBHOOK_SECRET, payload)}"

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Shipit::Membership.where(team_id: privileged_team.id).count } do
    post :create, body: payload, as: :json
  end
end
```
Both sides of the binding: `verified_org == 'OrgTwo'` (attacker's own org, correctly authenticated) vs. `team.organization == 'shopify'` (the real owner of `github_id`) — they diverge, and the assertion should show no `Membership` is created; currently the code creates one, confirming the vulnerability.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "status=#{status}"
      ].join(' '))
    end
