### Title
Unbounded `count_coins` multiplication in indivisible asset denominations causes silent precision-loss overflow analogous to unchecked `wmul`/`wad` overflow - ([File: validation.js], [File: indivisible_asset.js])

### Summary
The Sherlock finding is about Solidity `Maths.sol` multiplying two `uint256` values (`wmul`, `wad`, `rmul`, etc.) without checking that the product doesn't overflow the fixed-width integer, corrupting downstream financial calculations. In `ocore`, JS `Number` arithmetic has an analogous "overflow" class: any product/sum that exceeds `Number.MAX_SAFE_INTEGER` (2^53-1) silently loses integer precision instead of throwing, and the codebase does bound-check some individual operands but not the *product* of a multiplication used for capped-asset denominations.

### Finding Description
When defining a `fixed_denominations` (indivisible) asset, each `denomination` entry can optionally specify `count_coins`. Validation of these fields is: [1](#0-0) 

- `denomInfo.denomination` is checked against `constants.MAX_CAP` (bounded).
- `denomInfo.count_coins` is only checked with `isPositiveInteger`, which merely requires `Number.isInteger` semantics and `>0` — **there is no upper bound on `count_coins`** at all: [2](#0-1) 

- The cap-matching logic then computes `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` using plain floating-point multiplication, with no overflow/precision check on the *product* itself, before comparing it to `payload.cap`: [3](#0-2) 

Since `count_coins` is unbounded, an attacker can choose a huge `count_coins` (e.g. `1e20`) together with a small `denomination` such that the floating-point product `count_coins * denomination` rounds (due to IEEE-754 double precision loss beyond `2^53`) to a value that happens to equal the declared `payload.cap` (which is bounded ≤ `MAX_CAP`), even though the "true" mathematical product is far larger or the rounding masks the real intended values. This passes asset-definition validation.

The same unchecked multiplication pattern re-appears at issuance time in `pickIndivisibleCoinsForAmount`, where a "coin" is minted: [4](#0-3) 

`count_coins_to_issue * denomination` is computed directly from `row.count_coins` (persisted from the attacker-controlled `asset_denominations` table) with no re-validation of the product against `MAX_CAP`/`Number.MAX_SAFE_INTEGER` at issuance.

### Impact Explanation
This is the direct analog of the reported bug class: an unchecked multiplication of two attacker-influenced integers whose product can silently overflow the safe-integer range, corrupting the amount actually recorded/issued versus the amount that was validated against the asset's cap. Because issued-input `amount` fields feed directly into ledger balance accounting (`total_input`, `total_output` balancing checks in `validatePaymentInputsAndOutputs`), a precision-losing product could let an issuer mint/spend an amount inconsistent with the asset's true capped supply — i.e., supply inflation of a capped indivisible asset, which the balance/cap invariants were specifically designed to prevent.

### Likelihood Explanation
Reachable by any unprivileged asset issuer who is defining a new indivisible (`fixed_denominations: true`) asset in a public unit or via an AA asset-definition message — no special privilege needed beyond posting a unit. However, exploitation requires crafting `count_coins`/`denomination` pairs whose float product coincidentally rounds to match a chosen `cap` while diverging from the intended integer value, which is a non-trivial but classic floating-point precision-collision construction (values need to approach/exceed `2^53` to matter, which is large relative to typical byte amounts but not excluded by any check in the code). Likelihood is Medium: the precondition (extremely large `count_coins`, near or above 2^53) is unusual for real-world assets but is not prevented anywhere in validation, and the check that should catch it (`isPositiveInteger`) does not bound magnitude.

### Recommendation
- Add an explicit upper bound to `count_coins` (e.g., `count_coins <= constants.MAX_CAP`) in `validation.js`'s denomination validation, mirroring the existing `denomination > constants.MAX_CAP` check.
- Validate the *product* `count_coins * denomination` against `constants.MAX_CAP` and `Number.MAX_SAFE_INTEGER` before comparing to `payload.cap`, rejecting the definition if precision could be lost (e.g., verify `Number.isSafeInteger(count_coins * denomination)`).
- Apply the same product-safety check in `indivisible_asset.js`'s `issueNextCoin`/`pickIndivisibleCoinsForAmount` before using `count_coins_to_issue * denomination` as the `issue_amount`.

### Proof of Concept
1. An issuer posts an `asset` definition unit with `fixed_denominations: true`, `denominations: [{denomination: 1, count_coins: 9007199254740993}]` (2^53+1) and `cap` set to whatever floating value `1 * 9007199254740993` rounds to in JS double precision (which may differ from the exact integer due to precision loss).
2. `validateAssetDefinition` computes `total_cap_from_denominations = count_coins * denomination` using plain float multiply and compares it to `payload.cap`; because of IEEE-754 rounding, the comparison `total_cap_from_denominations !== payload.cap` can pass even though the mathematically exact product differs from the declared value.
3. Later, when coins are issued via `pickIndivisibleCoinsForAmount` in `indivisible_asset.js`, `issue_amount = count_coins_to_issue * denomination` is computed again with the same imprecise arithmetic and used directly as the ledger `amount` for the `issue` input, propagating the precision-loss discrepancy into on-chain balances.

*Note: this analysis is based on static code review of `validation.js` and `indivisible_asset.js`; I was not able to execute the code to empirically confirm a specific `count_coins`/`denomination` pair that produces an exploitable rounding collision, so the exact numeric PoC values would need to be verified in a JS runtime.*
