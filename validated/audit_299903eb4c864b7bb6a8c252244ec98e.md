Based on the investigation, I have enough to render a verdict.

### Title
`StatusHandler#process` writes cross-repository by bare SHA, letting an attacker-controlled `status` webhook mutate an unrelated victim stack's commit status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository/stack scoping, so a legitimately-signed `status` webhook from an attacker's own (forked) repository can create a `Status` record on any other stack whose `Commit` table happens to contain a matching SHA (e.g., shared pre-fork history), flipping `deployable?`/`blocked?` for a repository that never authenticated that webhook.

### Finding Description
The broken binding: the code assumes `commit.stack.repository == payload.repository`, but nothing enforces this equality.

`WebhooksController#verify_signature` only proves the payload was signed by the GitHub App installation belonging to `repository_owner` taken from the payload itself [1](#0-0) . It never checks that the `sha` inside the payload actually belongs to that same repository.

`StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is global across the entire `commits` table, not scoped to the repository that authenticated the request. `Commit` records only carry `stack_id`, and `Status` is created using `commit.stack_id`, `commit.create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2) [4](#0-3)  — with no comparison against the webhook's `repository.full_name`.

Exploit flow: an attacker forks a public repository tracked by Shipit (the "victim" repo/stack), install's Shipit's GitHub App on their own fork (their own org, which they legitimately control), then uses the GitHub API to set a commit status with `context: ci/circleci`, `state: failure` on a commit SHA that is shared history between the fork and the original repo (any commit that predates the fork point is byte-identical, so its SHA is identical in both repositories). GitHub sends a `status` webhook to Shipit, correctly signed for the attacker's own organization/installation. `verify_signature` passes because the signature genuinely matches the attacker's own webhook secret. `StatusHandler#process` then matches the SHA against **every** `Commit` row with that SHA — including the row belonging to the victim's stack — and calls `create_status_from_github!` on it, inserting a `failure` status for a repository that never sent or authorized that specific status.

Because `Status::Common#blocking?`/`#required?` are evaluated per `context` against `stack.blocking_statuses`/`required_statuses` [5](#0-4) , if the victim stack requires or watches `ci/circleci`, this forged-for-the-victim (but legitimately-signed-for-the-attacker) status can flip `Commit#deployable?` (`success? && !blocked?`) [6](#0-5)  and `#blocked?` [7](#0-6) , and re-triggers `stack.schedule_merges` / `ContinuousDeliveryJob` via `add_status` [8](#0-7) , forcing a block on (or, with a `success`/`pending` state, forcing a) ship on a stack the attacker never authenticated for.

Existing guards do not help: `verify_signature` authenticates *who sent the payload*, not *which commit records the payload is allowed to touch* — these are two independent checks and the second one simply does not exist. `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates payload shape, not commit/repo consistency [9](#0-8) .

Note: the "review_stacks_enabled ... provision? precedence bug" referenced in the question is a real, separate operator-precedence issue in `PullRequest::OpenedHandler#provision?`/`ReopenedHandler#unarchive?`/`LabeledHandler`/`UnlabeledHandler` (`repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...)` — due to Ruby's `&&`/`||` precedence, `review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches) [10](#0-9) . However, `review_stacks_enabled` is irrelevant to `StatusHandler`; it is never read anywhere in `status_handler.rb` or `commit.rb`. The two bugs are not chained as described — the `status` cross-repository write is exploitable regardless of `review_stacks_enabled`, and the provisioning precedence bug affects only PR-open/reopen/label handlers, not `ci/circleci` status ship/block decisions.

### Impact Explanation
An unprivileged attacker who owns any repository that shares commit history with a victim's Shipit-tracked repository (trivially achievable via a public fork) can write arbitrary `Status` rows (`state`, `context`, `description`, `target_url`) onto the victim's `Commit`/`Stack`, matching the rules' Critical category "a payload for one repository mutating another's stack, commit, task or team." This can force `blocked?`/`deployable?` transitions and trigger unauthorized deploy scheduling (`ContinuousDeliveryJob`) or block legitimate deploys, on a stack the attacker never controls. It is repeatable against any victim repository/stack for which shared/ancestor commits exist and is not limited to a single tenant.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own GitHub repository/org with Shipit's GitHub App installed (self-service for public apps), (b) a fork or otherwise shared-history repository with the victim so at least one common-ancestor SHA exists in both, and (c) the victim stack to be tracking that shared commit (normal for any actively-synced repo/fork chain). No Shipit credentials, secrets, or privileged GitHub roles are required — the attacker only ever authenticates their own webhook. This is highly feasible for any public open-source project on Shipit, since forking is unrestricted and shared history is guaranteed up to the fork point, and is fully repeatable per commit/status combination.

### Recommendation
Scope `StatusHandler#process` (and `CheckSuiteHandler`/other SHA-keyed handlers) to the repository that authenticated the webhook, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })` (or equivalent join through `Stack#repository`), rather than a bare `Commit.where(sha: ...)`. Separately (out of scope for this chain but worth fixing), correct the operator precedence in `provision?`/`unarchive?`/`archive?` methods so `review_stacks_enabled` gates all provisioning behaviors: `repository.review_stacks_enabled && (provisioning_behavior_allow_all? || (...) || (...))`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not create a status for a commit belonging to a different repository's stack" do
  victim_repo  = shipit_repositories(:shipit) # tracks "shopify/shipit-engine"
  victim_stack = victim_repo.stacks.first
  shared_sha   = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  attacker_payload = {
    "sha" => shared_sha,
    "state" => "failure",
    "context" => "ci/circleci",
    "repository" => { "full_name" => "attacker/fork", "owner" => { "login" => "attacker" } }
  }

  # Binding under test: commit.stack_id (victim_stack.id) must NOT receive a Status
  # from a webhook whose repository (attacker/fork) != victim_repo.github_repo_name
  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload).process
  end
end
```
Before the fix, this assertion fails: `victim_commit.statuses.count` increases by 1 even though the webhook's `repository.full_name` ("attacker/fork") never equals `victim_repo.github_repo_name` ("shopify/shipit-engine"), proving the write crosses the tenant boundary.
