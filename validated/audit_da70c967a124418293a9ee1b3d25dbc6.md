### Title
Cross-organization webhook forgery via organization/repository binding mismatch in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify an inbound webhook's HMAC signature against using `repository_owner`, derived only from `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')` as a fallback). However, the event handlers that actually act on the payload (e.g. `PushHandler`, `StatusHandler`, `PullRequest::*Handler`) resolve the target `Repository`/`Stack` from a *different* field: `payload.dig('repository', 'full_name')` via `Handler#repository_name` [1](#0-0) . This is the same "authorize on field A, act on field B" bug class as the reported `ensureMaxLocking` issue, applied to organization/repository trust binding instead of VIP level.

### Finding Description
Shipit supports multiple GitHub Apps/organizations in a single deployment, each with its own `webhook_secret`, selected via `Shipit.github(organization: ...)` (confirmed by the multi-org `secrets.yml` schema in `docs/setup.md` and `config/secrets.development.example.yml`, and by `Shipit::ShipitTest#".github uses indifferent access..."`).

`WebhooksController#verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This picks the app/org whose secret is used to validate the signature purely from `repository.owner.login` (or `organization.login`). Once the signature is valid, `create` hands the **entire raw JSON body** to the registered handler(s):
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers, however, determine the repository/stack they operate on from a *separate* field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

`PushHandler#process` then triggers `stack.sync_github(...)` for stacks resolved this way [4](#0-3) , and the `pull_request/*` handlers likewise resolve `repository` from `params.repository.full_name` independent of the field used for signature routing [5](#0-4) .

Because the HMAC signature covers the raw JSON body as a whole, an attacker cannot *tamper* with an authentic GitHub-issued payload post-hoc — but an attacker who legitimately controls (or is an admin of) **one** organization configured on the Shipit instance (Org A) knows/can read Org A's GitHub App `webhook_secret` (a value org owners can view/rotate in their own GitHub App settings, as documented in `docs/setup.md`). Such an attacker can self-construct an arbitrary payload — not derived from any real GitHub event — where `repository.owner.login` = `"orgA"` (so `verify_signature` selects and validates against Org A's known secret) while `repository.full_name` = `"orgB/target-repo"` (any other organization/stack tracked by the same Shipit instance). Because the two fields are never cross-checked, the forged, self-signed payload is accepted, and the handler acts on Org B's stack using Org A's trust.

This exactly matches the required broken binding: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
An attacker who is only a legitimate/authorized user of one GitHub organization onboarded to a shared Shipit instance can forge `push`, `status`, `check_suite`, or `pull_request` webhooks for any *other* organization's repository/stack tracked by that instance, without any Shipit session, API token, or access to the target organization:
- Forged `push` events cause `GithubSyncJob` to sync arbitrary/fabricated commit history into a target stack it doesn't own [6](#0-5) .
- Forged `status` events allow injecting fabricated CI/commit statuses for a target stack's commits, which is exactly the kind of check `ci.require`/continuous-deployment gating in `shipit.yml` relies on — enabling an unauthorized automatic deploy to proceed on a repository the attacker does not control.
- Forged `pull_request` events can create/archive/unarchive review stacks belonging to another organization's repository.

This crosses a repository/authorization boundary between organizations sharing one Shipit deployment, satisfying the "cross-repository writes" / "unauthorized deploy" Critical-impact criteria.

### Likelihood Explanation
Requires the attacker to be a legitimate admin/owner of at least one GitHub organization already configured on the shared Shipit instance (able to view that org's App webhook secret), and requires the instance to be configured for multiple organizations (an explicitly documented and supported configuration, not an edge case). No Shipit session, API token, or GitHub write access to the *target* org/repo is needed — only the ability to craft and POST an arbitrary HTTP request to `/webhooks` with a valid HMAC computed from a secret the attacker legitimately possesses for their own org.

### Recommendation
Bind signature verification to the same field(s) actually used to select the acted-upon repository/stack. At minimum:
- Verify that `repository.owner.login` (used to pick the signing org) is consistent with the owner portion of `repository.full_name` before dispatching to handlers, rejecting the payload otherwise.
- Alternatively, verify the payload's signature against the specific `GithubHook`/`Repository` record identified by `repository.full_name` (per-repository secret) rather than a global per-organization app secret keyed off a separate, unchecked field.
- Reject events where `repository.full_name`'s owner segment does not match `repository_owner`/`organization.login`.

### Proof of Concept
1. Deploy Shipit configured with two GitHub organizations, `orgA` and `orgB`, each with its own GitHub App/`webhook_secret` (as documented in `config/secrets.development.example.yml`'s multi-org format).
2. As an admin of `orgA`, obtain `orgA`'s `webhook_secret` from the GitHub App settings.
3. Craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, loads `orgA`'s app, and validates the signature successfully (it is a legitimate signature for `orgA`'s secret over this exact body) [7](#0-6) .
6. `create` dispatches to `PushHandler`, which resolves the target stack via `repository.full_name` = `"orgB/target-repo"` [1](#0-0)  and triggers `GithubSyncJob`/`sync_github` on `orgB`'s stack [4](#0-3)  — despite the attacker having no privileges in `orgB`.

Note: I could not fully verify (within available tool budget) the exact downstream logic in `app/models/shipit/stack.rb`/`ContinuousDeliveryJob` that would auto-trigger a deploy purely from a forged `status` event, so the "unauthorized deploy" escalation via forged `status` webhooks specifically should be validated further by a Devin session with full file access; the cross-organization repository/stack write via forged `push`/`pull_request` events is confirmed directly from the cited code.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
