### Title
Anyone can fund another account's gas key via `TransferToGasKeyAction`, permanently blocking `DeleteAccount` (`GasKeyBalanceTooHigh`) — [File: runtime/runtime/src/access_keys.rs, runtime/runtime/src/action_validation.rs, runtime/runtime/src/actions.rs]

### Summary
`TransferToGasKeyAction` lets *any* account fund the gas key of *any other* account with no ownership check on the receiver. If the deposited amount pushes the account's gas key balance above `GasKeyInfo::MAX_BALANCE_TO_BURN`, the account's own `DeleteAccountAction` will be permanently rejected with `GasKeyBalanceTooHigh`, mirroring the report's pattern of an unprivileged third party depositing an "unwanted" asset into a victim account to block a state-dependent operation.

### Finding Description
`action_transfer_to_gas_key` only checks that the target `public_key` corresponds to an existing gas key on `account_id`; it performs no check that the action's actor/predecessor is the account owner itself: [1](#0-0) 

The action-level validation for `TransferToGasKeyAction` is likewise limited to a protocol-feature gate — it never validates that the signer/predecessor equals the receiver account: [2](#0-1) 

Because `TransferToGasKeyAction` is a normal action addressable to any `receiver_id` in a transaction (or receipt), any account `A` can sign a transaction with `receiver_id = victim` and `TransferToGasKeyAction { public_key: victim_gas_key, deposit }`, as long as `A` knows `victim`'s gas key public key. Gas key public keys are not secret — they are added via `AddKeyAction` and are publicly observable on-chain/through RPC (`view_access_key_list`). Repeated or large-enough deposits can push `gas_key_info.balance` above `GasKeyInfo::MAX_BALANCE_TO_BURN`.

`action_delete_account` sums all gas key balances on the account and refuses to execute `DeleteAccount` if the sum would exceed the burn cap, leaving the account (and its receipt) completely untouched: [3](#0-2) 

This is structurally identical to the reported bug class: a check assumes the target account's balance/asset composition is bounded ("only cash"/"balance below burn cap") to allow cheap execution of an action (bid / `DeleteAccount`), but an unprivileged third party can deposit into the target account without its consent and push it past that bound, blocking the intended action.

### Impact Explanation
An attacker can grief any account that uses gas keys, indefinitely preventing it from executing `DeleteAccountAction` (and, since the same overall gas-key-balance check gates key deletion too, from removing the offending gas key cheaply — see `GasKeyBalanceTooHigh` also returned from `action_delete_key`). The victim must first issue `WithdrawFromGasKeyAction` to drain the balance before it can delete the account or key, and the attacker can re-fund it again in a race, similar to the "front-run a bid" scenario in the report. This is a targeted denial-of-service on account lifecycle actions triggered purely by an unprivileged transaction from any account, with no state or balance requirement on the attacker beyond a small deposit amount, and does not require any node/validator collusion.

### Likelihood Explanation
High. The attack requires only: (1) the victim account to have an existing gas key (a supported, user-facing feature, `AddKeyAction` with `AccessKey::gas_key_full_access`), (2) knowledge of that gas key's public key, obtainable via a routine RPC query, and (3) a single signed transaction with a `TransferToGasKeyAction`. No special permissions, front-running precision, or races are strictly required to achieve the "over-balance, can't-delete" state — although front-running a deletion attempt makes it repeatable griefing.

### Recommendation
Restrict `TransferToGasKeyAction` (and the corresponding `promise_batch_action_transfer_to_gas_key` host function) so that funding a gas key is only permitted when the action's predecessor/signer is the account that owns the gas key (i.e., `account_id == predecessor_id`), analogous to requiring "approval" before crediting an account with funds that affect its own risk/eligibility checks. Alternatively, exclude externally-deposited gas-key balance from the `MAX_ACCOUNT_DELETION`/`GasKeyBalanceTooHigh` check, or let the owner force-withdraw excess balance as part of `DeleteAccount`/`DeleteKey` rather than failing outright.

### Proof of Concept
1. `victim.near` adds a gas key: `AddKey(AddKeyAction { public_key: gk_pub, access_key: AccessKey::gas_key_full_access(n) })`.
2. `attacker.near` observes `gk_pub` via `view_access_key_list` for `victim.near`.
3. `attacker.near` signs and submits a transaction: `signer_id = attacker.near`, `receiver_id = victim.near`, `actions = [TransferToGasKeyAction { public_key: gk_pub, deposit: <amount pushing balance above MAX_BALANCE_TO_BURN> }]`. This succeeds per `action_transfer_to_gas_key`, which does not check `predecessor_id`.
4. `victim.near` later submits `DeleteAccount { beneficiary_id: ... }`. `action_delete_account` computes `gas_key_balance_to_burn` via `compute_gas_key_balance_sum` and rejects with `ActionErrorKind::GasKeyBalanceTooHigh`, leaving the account and receipt unmodified (test `test_delete_account_gas_key_balance_too_high` in `runtime/runtime/src/access_keys.rs` demonstrates the exact rejection mechanics, only difference being the deposits originate from the account itself in the test instead of a third party).

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
