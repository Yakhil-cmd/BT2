### Title
Permissionless `InitializeBuffer` in the upgradeable BPF loader allows griefing/front-running of buffer account setup - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::InitializeBuffer` handler in the upgradeable BPF loader sets the buffer's authority to whatever pubkey is passed as instruction account index 1, without requiring that account to sign or requiring any relationship to the account that funded/created the buffer. If the `SystemInstruction::CreateAccount` that allocates the buffer (owned by `bpf_loader_upgradeable`) and the subsequent `InitializeBuffer` call are not submitted atomically in the same transaction, any unprivileged party can race to call `InitializeBuffer` first and claim themselves as the buffer authority, permanently locking the legitimate deployer out of that buffer account. This is the exact bug class described in the Velodrome `Bribe.setGauge()` report: a "set-once" initialization guarded only by a "not yet set" check, callable by anyone, that can be front-run between two non-atomic setup steps.

### Finding Description
`process_loader_upgradeable_instruction` handles `InitializeBuffer` as follows: [1](#0-0) 

The check only guards against re-initializing an already-initialized buffer (`AccountAlreadyInitialized`); it does not verify that the caller, the fee payer, or the authority-to-be has any signature or relationship to the account that created/funded the buffer. The authority account at index 1 is not required to be a signer, unlike the parallel `Write` and `SetAuthority` handlers which do enforce `is_instruction_account_signer` on the authority: [2](#0-1) 

The intended, safe workflow bundles `SystemInstruction::CreateAccount` (to allocate/own the buffer under `bpf_loader_upgradeable`) and `InitializeBuffer` into a single instruction list meant to be sent together, as seen in the loader interface helper used across the codebase (e.g. `solana_loader_v3_interface::instruction::create_buffer` referenced in the CLI deploy path): [3](#0-2) [4](#0-3) 

However, nothing in the runtime or the loader enforces that these two steps occur in the same transaction — they are two independent, separately-dispatchable instructions. If a client, wallet, custom tool, or a transaction that gets split/retried ends up submitting `CreateAccount` and `InitializeBuffer` as separate transactions, the buffer account sits in the `Uninitialized` state (still owned by `bpf_loader_upgradeable`, per the system program's `AccountAlreadyInUse` guard which only checks lamports/owner/data, not loader-level state) for the gap between the two transactions. Any transaction sender can observe the new buffer account and submit their own `InitializeBuffer` instruction naming themselves (or anyone) as `authority_address`, which succeeds because there is no signature requirement.

Once initialized by the attacker, the legitimate deployer's own `InitializeBuffer` attempt fails with `AccountAlreadyInitialized`, and any `Write`/`SetAuthority` attempt by the legitimate deployer fails with `IncorrectAuthority`/`MissingRequiredSignature` because the authority no longer matches them. The buffer account (which was already funded with rent-exempt lamports) becomes permanently unusable to the intended owner, mirroring the "Bribe contract unusable, requires redeployment" impact from the reference report — here the deployer must abandon the buffer, and either wait for rent-exemption lamports to be reclaimed via account closure (not possible without authority) or fund a brand-new buffer account.

### Impact Explanation
This is a griefing/DoS vector reachable by any unprivileged transaction sender with a single transaction: it does not move or mint funds directly, but it permanently denies use of a paid-for (rent-exempt) buffer account to its intended owner, wasting the lamports locked in it (since only the authority can reclaim them via `Close`/`SetAuthority`, and the attacker now controls that). This matches "temporary/permanent system-breaking impact requiring redeployment" from the referenced report, scoped here to program-deployment tooling rather than fund custody, so it is a moderate-severity griefing bug rather than a critical fund-loss or consensus bug.

### Likelihood Explanation
Exploitability strictly depends on whether the two setup instructions (`CreateAccount` and `InitializeBuffer`) are ever broadcast as separate transactions in practice. The CLI's default `create_buffer`/`do_process_program_deploy` path bundles them into one message (`initial_message`) which is generally atomic, reducing real-world exposure. However, since the runtime provides no on-chain enforcement of atomicity, any alternate tooling, wallet, or retry/resubmission logic that separates these two steps (e.g., pre-funding/creating a buffer account ahead of time before deciding on the exact deploy flow) is immediately vulnerable, and a bot watching the mempool/leader schedule for `bpf_loader_upgradeable`-owned uninitialized accounts could opportunistically front-run.

### Recommendation
Require the `InitializeBuffer` authority account to be a signer (consistent with `Write` and `SetAuthority`), so that only someone controlling the intended authority key can claim it, closing the front-running window entirely. Alternatively/additionally, consider deriving/validating the buffer authority from the account that funded the `CreateAccount` call (e.g., requiring the same signer for both steps), or documenting/enforcing that `CreateAccount` + `InitializeBuffer` must be composed in a single atomic transaction.

### Proof of Concept
1. Attacker (or a normal user) monitors for `SystemInstruction::CreateAccount` transactions that create a new zero-data account owned by `bpf_loader_upgradeable` (i.e., a soon-to-be buffer account), sized per `UpgradeableLoaderState::size_of_buffer(len)`.
2. Before the legitimate deployer's `InitializeBuffer` transaction lands, attacker submits their own transaction: program `bpf_loader_upgradeable`, instruction data `UpgradeableLoaderInstruction::InitializeBuffer`, accounts `[buffer_pubkey (writable, not signer), attacker_pubkey (not signer)]`.
3. Because the handler at [1](#0-0)  only checks `UpgradeableLoaderState::Uninitialized != buffer.get_state()?` and never checks a signer for the authority account, this transaction succeeds, setting `authority_address = Some(attacker_pubkey)`.
4. The legitimate deployer's subsequent `InitializeBuffer` now fails with `InstructionError::AccountAlreadyInitialized`; any `Write` attempt by the legitimate deployer fails with `IncorrectAuthority`/`MissingRequiredSignature` at [5](#0-4) , permanently locking them out of the pre-funded buffer account.
