Found the binding-break: `WebhooksController#verify_signature` selects the signing key using `repository.owner.login` (or `organization.login`), while every event handler resolves the target `Repository`/`Stack` using `repository.full_name` (`owner/name`) via `Handler#repository_name` and `Repository.from_github_repo_name`. In a multi-org deployment (`config/secrets.development.shopify.yml` shows the `github: { OrgOne: {...}, OrgTwo: {...} }` schema, exercised by `Shipit.github_app_config`), these two fields are independent JSON keys inside the same payload and neither is cross-checked against the other after signature verification.

### Title
Webhook signature is validated against `repository.owner.login`, but the handler acts on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` to validate the HMAC using `repository_owner`, computed from `params.dig('repository','owner','login')` (or `organization.login`). The `create` action then dispatches to handlers that resolve the affected `Stack` using an entirely different payload field, `repository.full_name` in `Handler#repository_name`.

In a multi-tenant configuration (`Shipit.github_app_config`, exemplified in `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml`) each organization has its own `webhook_secret`. Because `repository.owner.login`/`organization.login` and `repository.full_name` are two distinct JSON keys inside the same signed body, they are not required to be consistent with each other by any code path — the HMAC signature only proves the raw byte string was signed with *some* configured org's secret, not that the org used for key-selection matches the org embedded in `full_name`.

However, to exploit this, the attacker would need to control (or already possess) a valid `webhook_secret` for at least one configured organization — the signature covers the entire raw body, so an attacker without any secret cannot forge a payload for a different `full_name` even if `repository.owner.login` matches an org they know the secret for, because they'd need to change `full_name` too, which invalidates the same signature they hold (since the secret is fixed to whichever secret was used, not the field values). Concretely: attacker owns/administers `OrgA` (has `OrgA`'s webhook_secret and can genuinely trigger GitHub webhooks under `OrgA/some-repo`), but crafts (or replays with modification) a payload where `repository.owner.login = "OrgA"` (so `verify_signature` picks `OrgA`'s secret and the HMAC — computed by the attacker using the known `OrgA` secret over their own chosen raw body — validates) while `repository.full_name = "OrgB/other-repo"` (a repository belonging to a different tenant/org, `OrgB`, configured on the same Shipit instance). Since the attacker controls the raw POST body and knows `OrgA`'s secret, they can self-sign an arbitrary body with mismatched owner/full_name fields.

This breaks the intended binding: "the organization whose secret authenticated the webhook" should equal "the organization whose repository/stack gets written to." Instead, `verify_signature`'s key selection and the handler's write target are computed from two independent, unauthenticated-relative-to-each-other fields.

### Impact Explanation
An attacker who legitimately controls one tenant organization (`OrgA`) on a shared multi-org Shipit instance can forge webhook events (e.g. `push`, `status`, `check_suite`, `membership`) that appear to originate for a **different** organization's (`OrgB`'s) repositories/stacks, by only knowing `OrgA`'s `webhook_secret`. Depending on which handler is targeted, this can trigger cross-repository state changes such as creating `Team`/`User` records scoped to `OrgB` (`membership_handler.rb`), updating commit/check statuses that gate deploys (`status_handler.rb`, `check_suite_handler.rb`), or manipulating `Stack` merge-status/pull-request state (`pull_request/*_handler.rb`) for repositories the attacker does not own — a cross-tenant/cross-repository write using credentials scoped to a different repository.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (the `github: { OrgOne: {...}, OrgTwo: {...} }` config schema) where the attacker legitimately controls one org's GitHub App/webhook_secret but targets another org's stacks. This is a plausible SaaS/shared-instance deployment topology explicitly supported by the engine's config schema (`config/secrets.development.shopify.yml`), so it is not a purely theoretical misconfiguration.

### Recommendation
After `verify_signature` succeeds, re-derive the acting organization from the *same* field the handlers use (`repository.full_name`'s owner segment, or `organization.login`) and assert it equals `repository_owner` (the field the signature was verified against) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret`, matching `config/secrets.development.shopify.yml`'s schema.
2. Attacker (owns `OrgA`, knows `OrgA`'s `webhook_secret`) builds a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/some-repo" },
     ...event-specific fields...
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(OrgA_webhook_secret, body)>` and POST to `/github/webhooks` with `X-Github-Event` set to a handled event (e.g. `membership`, `status`).
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies the HMAC against `OrgA`'s secret — succeeds.
5. `create` dispatches to the event handler, which resolves the target via `payload.dig('repository','full_name')` == `"OrgB/some-repo"`, acting on `OrgB`'s data despite the request being authenticated only for `OrgA`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end
