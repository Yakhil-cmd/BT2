### Title
Cross-tenant `Status` forgery via unscoped sha lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` records purely from the webhook's `sha`, ignoring the requesting repository entirely, and creates a `Status` on every matching commit across all stacks/repositories. Any account that can trigger a `status` webhook for a repository containing a commit whose sha coincides with a commit in a victim stack (trivially achievable via forks that share commit history) can flip `Commit#blocked?`/`deployable?` for that victim stack, bypassing its `blocking_statuses` safety gate.

### Finding Description
The broken binding: `commit.stack_id` (the stack the forged status is attributed to) should equal `Repository.from_github_repo_name(payload['repository']['full_name']).stacks.map(&:id)` (the stack authenticated by the webhook's verified repository). It does not.

`Webhooks::Handlers::Handler` already provides a `stacks` helper that scopes lookups to the repository named in the signed payload: [1](#0-0) . However, `StatusHandler#process` bypasses this helper entirely and queries commits globally by sha: [2](#0-1) 

`Commit.where(sha: params.sha)` is not scoped to `stack_id` or the requesting repository at all, so any `Commit` row across any tenant's stack with a matching sha receives a new `Status` via `commit.create_status_from_github!(params)`, which creates the `Status` bound to `commit.stack_id` (the victim's own stack), not the attacker's: [3](#0-2) , [4](#0-3) .

`Commit#blocked?` then re-evaluates blocking commits using exactly this globally-writable state: [5](#0-4)  where `blocking?` is delegated to `status`, which is derived from `statuses` (delegate at [6](#0-5) , `status` built at [7](#0-6) ).

Exploit flow: an attacker registers/owns a repository in Shipit (or any repository whose webhook the app accepts) that shares a commit sha with the victim's blocking commit — trivial for forks, since forked repositories retain identical shas for all commits copied from the upstream/victim repository history. The attacker pushes/merges nothing special; they simply need GitHub to fire (or the attacker directly POSTs, if the webhook secret used for signing is the shared org-level secret configured per-repo rather than per-tenant — note: signature verification proves the payload came from GitHub for *some* registered repository, but does not bind the `sha` field to that repository) a `status` event with `state: success` and the matching `context` for that shared sha. `StatusHandler#process` finds the victim's `Commit` row (same sha, different `stack_id`) and creates a `success` `Status` on it. This flips `blocking?` to false for that commit, and `Commit#blocked?` for later commits in the victim stack now evaluates false, unblocking `deployable?` and continuous deployment for a stack/repository the attacker never authenticated against.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only prove the payload is a genuine GitHub webhook for the attacker's own (fully authorized) repository — they say nothing about which `Commit` record the `sha` field is allowed to target. The `Handler#stacks`/`repository_name` scoping mechanism exists specifically to prevent this class of cross-tenant bug, but `StatusHandler` is the one handler that does not use it.

### Impact Explanation
An attacker with a repository connected to Shipit (or one able to trigger a webhook post recognized as valid by signature) can write a `Status` record — and thus flip `blocking?`/`deployable?`/`Commit#blocked?` — for a `Commit` belonging to an unrelated victim stack/repository, as long as sha collision (fork-sharing) exists. This is a payload for one repository mutating another repository's stack/commit data, and it can unblock/trigger unauthorized continuous deployment for the victim stack — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is repeatable against any victim stack whose commit history is shared with an attacker-controlled fork, for every shared sha, indefinitely.

### Likelihood Explanation
Preconditions: attacker owns/controls a repository connected to Shipit that shares commit sha(s) with the victim stack (fork relationship is common and requires no special access), and knows the `context` string used in the victim's `blocking_statuses` config (often discoverable, e.g. `ci/circleci`, `continuous-integration/travis-ci`). No Shipit credentials, GitHub App key, or webhook secret needed beyond what's already granted to any GitHub repository owner receiving/forwarding standard status webhooks. This is low-cost and highly feasible for any attacker who forks a repository and can trigger (or replay) a `status` webhook for a shared sha.

### Recommendation
Scope `StatusHandler#process` to the repository authenticated by the webhook payload, mirroring the base `Handler#stacks` helper, e.g. restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or add `stack_id: stacks.pluck(:id)` to the `Commit.where` clause so a status can only be attached to commits belonging to stacks of the repository that signed the webhook.

### Proof of Concept
```ruby
test "status webhook cannot set status on a commit belonging to another repository's stack" do
  victim_repo = shipit_repositories(:shipit)
  victim_stack = victim_repo.stacks.first
  blocking_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)
  downstream_commit = victim_stack.commits.create!(sha: 'cafef00d' * 5, ...)
  blocking_commit.statuses.create!(stack: victim_stack, state: 'pending', context: 'ci/blocking')
  victim_stack.update!(cached_deploy_spec: stub_deploy_spec_with_blocking_statuses(['ci/blocking']))

  assert_equal false, downstream_commit.deployable?  # blocked before forgery

  attacker_repo = Shipit::Repository.create!(owner: 'attacker', name: 'evil-fork')
  attacker_stack = attacker_repo.stacks.create!(environment: 'production', branch: 'master')
  attacker_stack.commits.create!(sha: blocking_commit.sha) # colliding sha via fork history

  Shipit::Webhooks::Handlers::StatusHandler.call(
    'repository' => { 'full_name' => attacker_repo.full_name },
    'sha' => blocking_commit.sha,
    'state' => 'success',
    'context' => 'ci/blocking'
  )

  assert_equal false, downstream_commit.reload.deployable?, "downstream_commit should remain blocked; attacker's repo must not resolve victim's commit"
end
```
Expected (vulnerable) behavior: the assertion fails because `blocking_commit.blocking?` flips to false and `downstream_commit.deployable?` becomes `true`, proving the cross-tenant status forgery.
