### Title
Cross-organization webhook authorization bypass via decoupled `repository.owner.login` (signature-selection) and `repository.full_name` (action target) fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using `repository.owner.login` (or `organization.login`) taken directly from the untrusted, attacker-supplied JSON body. But every `Webhooks::Handlers::Handler` subclass (push, pull_request, status, etc.) resolves the actual `Stack`/`Repository` to mutate using a **different** field from that same body: `repository.full_name`. Because these two fields are never cross-checked against each other, and because `GithubApp#verify_webhook_signature` treats an *unset* `webhook_secret` as automatically valid, a webhook that authenticates as one configured GitHub organization can act on stacks belonging to a completely different organization's repository in a Shipit deployment using the documented "Using Multiple GitHub Applications" feature.

### Finding Description
`verify_signature` picks the app/secret to validate against purely from attacker-controlled payload data: [1](#0-0) [2](#0-1) 

The signature check itself explicitly treats a blank/unset secret as automatically verified — a supported, documented configuration (the setup docs list "Webhook secret (optional)"): [3](#0-2) [4](#0-3) 

Once `create` passes `verify_signature`, the actual repository/stack that gets acted upon is resolved from a *different* field of the same untrusted body — `repository.full_name` — with no re-check that it belongs to the organization that was used to authenticate the request: [5](#0-4) [6](#0-5) 

This is the same class of bug as the reported Connext issue: a value that is verified/authenticated (`repository.owner.login`/`organization.login`, which selects the trust anchor) is decoupled from the value that is actually acted upon (`repository.full_name`, which selects the mutated resource). The equality that should hold — "organization whose secret authenticated the request" == "organization owning the repository being written" — is never enforced.

Shipit explicitly supports multiple GitHub Apps/orgs sharing one Shipit instance, each with its own (optional) `webhook_secret`: [7](#0-6) 

### Impact Explanation
In a multi-organization deployment, if any one configured organization has no `webhook_secret` set (a documented, non-privileged, legitimate configuration choice, not a deviation from the documented setup), `verify_webhook_signature` returns `true` unconditionally for any payload claiming `repository.owner.login`/`organization.login` equal to that organization — with **no signature, no secret, and no session required**. An unauthenticated external attacker can then set `repository.full_name` to any other, fully-secured organization's repository tracked by Shipit and have the handler operate on that organization's `Stack`/`Repository`/`Commit` records: e.g. `PushHandler` will invoke `stack.sync_github(expected_head_sha:)` on stacks under the victim org/repo, and PR-event handlers (`pull_request/closed_handler`, `labeled_handler`, etc., which also key off `repository.full_name`) can forge merge/PR/commit-status state for that repository's stacks. This crosses a repository/organization write boundary that the app is supposed to enforce via per-org webhook authentication — matching the "cross-repository writes"/"unauthorized deploy, rollback or merge" impact tier, since forged commit-status/pull_request/push events can influence Shipit's deploy and merge-queue logic for a repository the attacker never authenticated for.

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multiple GitHub organizations (documented feature), and (2) at least one of those organizations left `webhook_secret` unset (documented as "optional"). Given that condition, exploitation requires zero secrets, tokens, or sessions — only a single unauthenticated POST to `/webhooks` with a crafted JSON body and an `X-Github-Event` header, satisfying the "unprivileged attacker" bar. Likelihood is therefore contingent on deployment configuration rather than a code defect that is always exploitable, but the code path itself performs no compensating check to prevent it even when the condition holds.

### Recommendation
Bind the two fields together: after `verify_webhook_signature` succeeds, re-derive/require that the app/organization used for verification (`repository_owner` in `WebhooksController`) matches the organization prefix of `repository.full_name` used by `Webhooks::Handlers::Handler#repository_name`, and reject the request otherwise. Additionally, consider disallowing a blank `webhook_secret` from acting as an implicit "always verified" bypass when more than one GitHub organization is configured, since that combination silently defeats per-organization isolation.

### Proof of Concept
Preconditions: Shipit configured with `github: { org_a: { webhook_secret: nil, ... }, org_b: { webhook_secret: <strong-secret>, ... } }` (multi-org mode per `docs/setup.md`), and Shipit tracks a stack for `org_b/victim-repo`.

1. Attacker sends, unauthenticated:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-empty

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org_a" },
    "full_name": "org_b/victim-repo"
  }
}
```
2. `WebhooksController#verify_signature` computes `repository_owner = "org_a"`, loads `Shipit.github(organization: "org_a")`, and calls `verify_webhook_signature`, which returns `true` immediately because `org_a`'s `webhook_secret` is blank — no valid signature needed.
3. `PushHandler#process` (via `Handler#repository_name` → `payload.dig('repository','full_name')`) resolves the target repository as `org_b/victim-repo`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `org_b`'s stack, even though the request never authenticated with `org_b`'s configured (strong) `webhook_secret`.

This demonstrates a request that authenticates as `org_a` acting on `org_b`'s repository/stack, breaking the intended binding `authenticating_org == acted_upon_repository_org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
