### Title
Unauthenticated disclosure of stack merge status via `MergeStatusController#check` - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`MergeStatusController` skips authentication for both `check` and `show` (`skip_authentication only: %i[check show]`), but only `show` re-checks `current_user.logged_in?` before rendering stack data. `check` renders `stack_status` unconditionally, so any unauthenticated internet client can retrieve a stack's merge status (`success`/`pending`/etc., and in JSON format the raw `stack_status` value) for an arbitrary repository/branch simply by supplying a crafted `referrer` param, with no session, no webhook signature, and no identity binding to the target repository at all.

### Finding Description
The claimed binding is: `current_user.logged_in? == true` should be required before `stack_status` (derived from `stack`, which is selected using attacker-controlled `referrer_parser.repo_owner`/`repo_name`) is disclosed to the requester. Tracing the code:

- `skip_authentication only: %i[check show]` [1](#0-0)  removes the `force_github_authentication` before_action for both actions, so `current_user` can be `AnonymousUser.new` [2](#0-1) .
- `show` explicitly re-enforces the login requirement: `return render('logged_out') unless current_user.logged_in?` before rendering `stack_status` [3](#0-2) .
- `check`, however, has no such guard — it renders `stack_status` directly for both HTML and JSON formats regardless of `current_user` [4](#0-3) .
- `stack` is resolved by parsing `params[:referrer]` through `ReferrerParser`, downcasing the regex-captured owner/name, and querying `Stack` by `repositories: { owner:, name: }` plus `branch`/`environment` — with zero comparison against any authenticated identity or webhook-verified organization [5](#0-4) .

So the only "binding" is repository-named-in-request == repository-whose-status-is-returned; there is no `current_user`/session binding on `check` at all. An attacker sends `GET /merge_status/check?referrer=https://github.com/repo-owner/repo-b/pull/1&branch=production` (or the JSON equivalent) with no cookies, no `Authorization` header, and receives `repo-b`'s `merge_status`. This works for any repo/branch combination that has a matching `Stack` record, entirely unauthenticated.

`show`'s login gate does not protect `check`; they are sibling actions with independent logic. No `verify_signature`, `ExplicitParameters`, or `require_permission!` guard applies to this path since it is a plain browser-facing GET action, not a webhook endpoint.

### Impact Explanation
An unauthenticated attacker can read the merge/CI status (`stack_status` — e.g., `success`, `pending`, `behind`, `pull_request_not_ready`, etc.) of any stack configured in the Shipit instance, for any repository/branch, repeatedly and at will, with no rate limiting or authentication barrier. This is an unauthenticated read of stack state, matching the High severity category ("unauthenticated read of stack state, task streams or deploy output"). It does not itself allow writes, RCE, or credential exfiltration, but it discloses internal CI/deploy status for potentially private repositories to any internet client, and is trivially repeatable across all tenants/stacks hosted by the instance.

### Likelihood Explanation
No special configuration is required beyond the default engine setup (`skip_authentication only: %i[check show]` is present in the shipped controller). The attacker only needs to know or guess a valid `owner/name` and branch/environment combination that matches an existing `Stack`; these are typically public GitHub repo names, so the cost is negligible. It is fully repeatable with a single unauthenticated HTTP GET per query, no GitHub or Shipit secret required.

### Recommendation
Add the same authentication gate used in `show` to `check`: require `current_user.logged_in?` before computing/rendering `stack_status`, e.g. return `503`/`401` (or an empty/generic response) when anonymous, mirroring the `show` action's `return render('logged_out') unless current_user.logged_in?` check.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb
test "GET check as anonymous user discloses stack_status" do
  session.delete(:user_id)
  assert_not AnonymousUser.new.logged_in?

  stack = shipit_stacks(:shipit) # existing fixture stack for repo-a
  get :check, params: {
    referrer: "https://github.com/#{stack.repository.owner}/#{stack.repository.name}/pull/1",
    branch: stack.branch,
  }, format: :json

  assert_response_in [200, 503] # check renders 200 for success or 503 otherwise, never blocked
  body = JSON.parse(response.body)
  assert body.key?("stack_status")
  refute_nil body["stack_status"] # stack data disclosed with no authenticated identity
end
```
This demonstrates that with `current_user` being `AnonymousUser` (`logged_in?` false), `#check` still computes and returns a non-nil `stack_status` for the targeted stack, confirming the missing identity binding present in `#show` but absent in `#check`. [4](#0-3) [3](#0-2) [2](#0-1)
