## Title
CCMenu API token scope bypass — read access to any stack's build/deploy state - (`app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` authenticates requests with a bearer `ApiClient` token (via `params[:token]`) that may be scoped to a single stack (`ApiClient#stack_id`), but the controller resolves the target `stack` without applying that scope, letting the token read the CI/deploy status of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through `stacks`/`stack`: [1](#0-0) 

`current_api_client.stack_id?` restricts the queryable `Stack` relation to the one stack the token was minted for, and `stack` is looked up *within* that restricted relation via `stacks.from_param!`.

`Shipit::Api::CCMenuController`, however, overrides `stack` and bypasses this scoping entirely: [2](#0-1) 

It authenticates with `ApiClient.authenticate(params[:token])` (a token that can be, and by default is, scoped to a single stack — see `CCMenuUrlController`), then calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation instead of `stacks.from_param!`. `require_permission :read, :stack` only checks that the token carries the string permission `"read:stack"` (`ApiClient#check_permissions!`); it never checks that `params[:stack_id]` matches `current_api_client.stack_id`. [3](#0-2) 

The token that legitimately exists for this purpose is auto-provisioned per-stack and handed out via URL: [4](#0-3) 

This breaks the trust binding: **the stack a token authorizes** (`ApiClient#stack_id`, the single stack the CCMenu URL was generated for) **≠ the stack it actually touches** (`params[:stack_id]`, attacker-controlled and unchecked against the token).

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped CCMenu token (these tokens are embedded in plaintext CCMenu/CI-status URLs, commonly shared with third-party CI dashboard tools, and are not treated as highly sensitive since they're "read-only, single-stack" by design) can substitute an arbitrary `stack_id` and read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status) of **any stack** managed by the Shipit instance, including private/internal ones the token holder has no authorization for. This is an unauthorized read of stack state across a trust boundary the token was explicitly scoped to prevent, matching the "unauthenticated/unauthorized read of stack state" class of impact.

### Likelihood Explanation
Exploitation requires only possession of one valid, low-privilege, single-stack CCMenu token (easily obtained by any user with access to one stack via `CCMenuUrlController#fetch`, or leaked since it travels in a URL query string) and knowledge/guessing of another stack's `to_param` (owner/repo/environment), which is often predictable or discoverable. No elevated credentials, GitHub App keys, or webhook secrets are needed.

### Recommendation
Make `Api::CCMenuController#stack` honor the same scoping as `BaseController`, e.g. replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])`, so a stack-scoped token can only ever resolve to its own stack.

### Proof of Concept
1. As a legitimate low-privilege user with access only to `stack-A`, visit `CCMenuUrlController#fetch` for `stack-A` to obtain a token scoped via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, ...)` with `stack_id` = `stack-A.id`.
2. Call `GET /api/stacks/:owner/:repo/:env/ccmenu.xml?token=<stack-A token>` but substitute `stack-B`'s owner/repo/env path parameters (any other stack in the instance).
3. Observe the response returns `stack-B`'s build status via `Api::CCMenuController#show`, even though the token was never authorized for `stack-B`, because `stack` resolves through unscoped `Stack.from_param!` rather than the token-scoped `stacks` relation used elsewhere in the API controllers.
