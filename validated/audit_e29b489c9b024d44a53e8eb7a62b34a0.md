### Title
CCMenuController bypasses ApiClient stack scoping, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` can be scoped to a single stack via its `stack_id` column, and this scoping is the authorization boundary enforced everywhere else in the API. `Api::CCMenuController` overrides the `stack` lookup to bypass that scoping, so a token that is only supposed to authorize reads on stack A can be used to read build/deploy status for any stack B by simply changing the `stack_id` request parameter.

### Finding Description
`Shipit::ApiClient` supports being bound to a specific stack: `belongs_to :stack, optional: true` [1](#0-0) , and this is a real, exercised configuration in the fixtures (`here_come_the_walrus` is scoped to the `shipit` stack with only `read:stack`) [2](#0-1) .

Everywhere else in the API, this scoping is the enforcement point: `Api::BaseController#stacks` restricts the visible stack set to `current_api_client.stack_id` when the client is scoped, and `#stack` resolves the requested id only from that restricted set: [3](#0-2) 

Permission checking (`check_permissions!`) only verifies the string `"#{operation}:#{scope}"` is present in the client's `permissions` array — it has no notion of which stack the token is bound to: [4](#0-3) 

So the *only* place that binds "the stack a token authorizes" to "the stack the request touches" is `BaseController#stack`/`#stacks`.

`Api::CCMenuController` authenticates via a query-string token (`ApiClient.authenticate(params[:token])`) and declares `require_permission :read, :stack`, but then overrides `stack` to resolve directly against the full `Stack` table instead of the scoped `stacks` relation: [5](#0-4) 

This breaks the invariant `token.stack_id == stack_being_read` that `BaseController` establishes for every other endpoint: for CCMenu, `token.stack_id` can be A while `stack_being_read` (from `params[:stack_id]`) is any stack B in the deployment.

### Impact Explanation
This is an authorization-scope escalation: a token deliberately restricted (by an admin, via direct DB/console assignment of `ApiClient#stack_id`, exactly as done for the `here_come_the_walrus` fixture) to `read:stack` on one stack can be replayed against `/api/stacks/:stack_id/ccmenu.xml` for a different `stack_id` and successfully render that other stack's CI/deploy status (`stack.deploys_and_rollbacks.last`, deploy id, `ended_at`, `running?`) via the `shipit/ccmenu/project` template: [6](#0-5) 

This matches the rules' "High" bucket: unauthenticated/unauthorized read of stack state and deploy output, achieved by crossing a scoping boundary the token was never granted for other repositories/stacks it has no relationship to.

### Likelihood Explanation
Exploitation only requires possessing any valid, stack-scoped `ApiClient` token (already an accepted precondition per the rules, since it is not a Shipit session, GitHub App key, or privileged account — it is exactly the kind of narrowly-scoped credential the scoping feature exists to contain) and changing one URL parameter. No other checks (permission string, signature, etc.) catch the mismatch.

### Recommendation
Make `Api::CCMenuController#stack` use the same scoped lookup as the rest of the API (`stacks.from_param!(params[:stack_id])` from `BaseController`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped token cannot resolve stacks outside its `stack_id`.

### Proof of Concept
1. Admin creates/assigns an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (as shown supported by the `here_come_the_walrus` fixture) [2](#0-1) .
2. Attacker obtains this token (e.g., it was issued to embed in a CI dashboard for stack A only).
3. Attacker requests `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<token>`.
4. `authenticate_api_client` accepts the token [7](#0-6) , `require_permission :read, :stack` passes because the permission string exists regardless of stack [4](#0-3) , and `stack` resolves Stack B directly from `params[:stack_id]`, bypassing the `stacks` scoping used everywhere else [8](#0-7) .
5. Response renders Stack B's latest deploy/build status, which the token was never authorized to see.
