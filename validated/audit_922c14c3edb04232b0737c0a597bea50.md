### Title
`StatusHandler` writes GitHub commit statuses by SHA alone, letting a webhook authenticated for one organization/repo forge CI status on another organization's tracked commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target of a `status` webhook by SHA only, without scoping to the repository/stack that the webhook's signature was verified against. Every other comparable handler (`PushHandler`, `CheckSuiteHandler`) scopes writes through `stacks`, which is derived from `Repository.from_github_repo_name(payload.repository.full_name)`. `StatusHandler` does not use `stacks` at all, so a correctly-signed webhook from Organization A can write a commit status onto a `Commit` row belonging to a `Stack`/`Repository` owned by Organization B, as long as the two share a commit with the same SHA (e.g. a shared upstream/fork history).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the incoming signature against based on the organization named in the payload (`repository.owner.login`), i.e. it authenticates "this event genuinely comes from Org X's app installation": [1](#0-0) 

After that authentication step, the actual write is supposed to stay scoped to the repository the org was authenticated for. The base `Handler` class establishes this scoping helper: [2](#0-1) 

`PushHandler` and `CheckSuiteHandler` correctly use `stacks` (i.e. only stacks under the authenticated repository) to decide what to mutate: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, ignores the `stacks`/repository scope entirely and matches purely by SHA across the whole install: [5](#0-4) 

`Commit.where(sha: params.sha)` is a global, cross-repository query — `Commit` belongs to `Stack`/`Repository` but the handler never filters by it. `create_status_from_github!` then persists the attacker-controlled `state`/`context`/`description` directly onto every matching `Commit` row, regardless of which repository/stack it actually belongs to: [6](#0-5) 

This breaks the deployment-trust binding "the organization that authenticated the webhook" vs. "the repository/stack whose data is written": the signature check authenticates Org A's ownership of a payload, but the mutation target is chosen without re-checking that the resolved `Commit` belongs to a stack under Org A's repository.

Because Git SHAs are content-addressed and shared across forks/clones of the same history, an attacker who controls (or forks) any repository that shares commit history with a victim's tracked repository can:
1. Register/point a repo they control at Shipit (or use any repo where they can trigger/emit a `status` webhook correctly signed with their own org's webhook secret — a normal, non-privileged capability for a repo they own/administer).
2. Send (or have GitHub send, via the Statuses API on their own repo) a `status` event for a commit SHA that also exists in the victim's stack (shared ancestor/fork commit).
3. The signature check passes because it is verified against the attacker's own org's app/secret — it is legitimately signed, just for the wrong logical target.
4. `StatusHandler` then writes the forged status (e.g. `state: "success"`, matching a `required_statuses` context) onto the victim's `Commit` row in a completely unrelated stack/organization.

### Impact Explanation
Commit `state`/status is consumed by deploy- and merge-safety logic (`Commit#state`, `MergeRequest::StatusChecker`, `required_statuses`/`ignored_statuses` from `deploy_spec`) to decide whether a commit is safe to merge/deploy: [7](#0-6) [8](#0-7) 

By forging a passing status for a `required_statuses` context on a victim commit, an attacker in an unrelated GitHub organization can make Shipit believe CI has passed for that commit, satisfying merge-queue/deploy gating checks it does not actually meet. This is a cross-repository/cross-organization write leading to a potentially unauthorized merge or deploy decision, which matches the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood is moderate: it requires (a) the attacker to own/administer at least one repository whose GitHub App/webhook is configured in the Shipit instance (or any org onboarded to the multi-org config), and (b) a SHA collision via shared git history (forks of the same upstream, vendored/copied history, or subtree merges) — this is a realistic, non-cryptographic collision that happens naturally with forked open-source projects, not a SHA-1 break. No privileged Shipit session, `ApiClient` token, or the victim's webhook secret is required; the attacker only needs their own legitimately-configured org's signing capability, which the code treats as sufficient authorization for any commit with a matching SHA anywhere in the database.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` and `CheckSuiteHandler` do — restrict the query to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently `Commit.where(sha: params.sha, stack: stacks)`), so a status write can only ever affect commits belonging to the repository the webhook signature was actually verified against.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with their own GitHub App/webhook secret (as supported by the multi-org config in `Shipit.github`).
2. `orgB` has a private Shipit-tracked stack for `orgB/victim-repo`, which was originally forked from a public upstream repo and therefore shares commit SHA `abc123...` with that upstream history.
3. Attacker forks the same public upstream into `orgA/attacker-repo` (also tracked, or simply owns the app installation for `orgA`) and triggers/receives a `status` webhook event for SHA `abc123...` with `state: "success"`, `context: "<required context configured for orgB's stack>"`.
4. `WebhooksController#verify_signature` validates the signature using `orgA`'s webhook secret — it is genuinely signed by `orgA`'s app, so verification succeeds.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, which matches the `Commit` row belonging to `orgB`'s stack (since the SHA is identical due to shared history), and calls `create_status_from_github!`, writing a forged "success" status onto `orgB`'s commit — even though the request never touched `orgB`'s app/secret or repository.
