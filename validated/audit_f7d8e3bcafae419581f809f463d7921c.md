Based on my investigation, this claim is valid. `ReviewStack#env` merges pull-request label names, upcased, directly as environment variable keys with no allowlist: [1](#0-0) . Those label names originate straight from the GitHub webhook payload and are persisted verbatim by `LabelCapturingHandler#capture_labels` via `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [2](#0-1) , with only string-type validation on `labels` in the params schema (`requires :labels, Array do requires :name, String end`) [3](#0-2) , meaning any string (including `GIT_CONFIG_COUNT`) is accepted as a label name and later upcased into a key by `ReviewStack#env`.

That `env` hash is merged into the deploy/task environment in `TaskCommands#env`, which composites `@stack.env` (i.e., `ReviewStack#env` for review stacks) together with other variables and finally with `@task.env` [4](#0-3) . This merged hash is passed as `env:` into `Command.new`, and `Command#unbundled_env` merges it with `BASE_ENV` and `PATH` with no key filtering at all [5](#0-4) . The final `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` call inherits every key from that unfiltered hash, including a fork-controlled `GIT_CONFIG_COUNT` [6](#0-5) .

I was not able to find any reference to `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`, or `GIT_CONFIG_VALUE_0` anywhere else in this codebase (no allowlist, no key-name validator, no `EnvironmentVariables#permit` restriction blocking arbitrary uppercase keys derived from labels) — confirming there is no code path that strips or filters environment variable *keys* before they reach `Command`/`PTY.spawn`. This is a genuine RCE-class chain: any git invocation performed as part of the `ci.require` step (or any step) inherits this attacker-supplied `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` triplet, which is git's documented mechanism for injecting arbitrary config (including `core.fsmonitor`, `core.hooksPath`, or `alias.*` entries that execute as shell commands) into any subsequent git invocation in that process's environment.

The critical caveat, which I could not fully resolve from the code alone, is the threat model's claim that an "unprivileged fork PR" author can label their own PR. On real GitHub, adding labels to a PR normally requires `triage`/`write` access to the *base* repository, not just fork/PR-authoring rights — a plain external contributor typically cannot add labels to their own PR unless the repo maintainer has granted broader permissions or bot automation exists. The `LabelCapturingHandler`/`ReviewStackAdapter` code trusts whatever `pull_request.labels` array arrives in a valid, signature-verified webhook (webhook signature validation is a separate concern not bypassed here) — so the vulnerability is real in the *engine's* code regardless of who is technically allowed to attach the label; the bug is that once *any* label name reaches the webhook (whether attached by the PR author, a bot, or a maintainer performing an action like "labeled"), it is used unsanitized as an env var key with no allowlist or prefix restriction.

### Title
Fork PR label names become unsanitized environment variable keys reaching `Command`/`PTY.spawn`, enabling `GIT_CONFIG_COUNT`-based git RCE - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (upcased) as an environment variable key with value `"true"`, with no allowlist or key-prefix restriction, and this hash flows unfiltered through `TaskCommands#env` into `Command#unbundled_env` and then `PTY.spawn`. A label literally named `GIT_CONFIG_COUNT` (or `git_config_count`, upcased by the code) becomes a real environment variable inherited by every spawned command, including any git invocation performed during deploy/CI steps.

### Finding Description
The broken binding: `ReviewStack#env` should only ever produce boolean "label present" variables under a fixed, safe namespace (e.g., always prefixed like `GITHUB_LABEL_X`), i.e. the invariant `keys(ReviewStack#env) ⊆ SAFE_ALLOWLIST` should hold, but instead `keys(ReviewStack#env) == pull_request.labels.map(&:upcase)`, an attacker-influenced set with no allowlist at all [1](#0-0) .

Path: a webhook `pull_request` event carrying a `labels` array with `name: "GIT_CONFIG_COUNT"` (or similar) is validated only for basic types by `LabelCapturingHandler`'s params schema [3](#0-2) , then persisted verbatim via `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [2](#0-1) . When a task/deploy runs, `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes the upcased label hash) [4](#0-3)  into the env passed to every `Command.new(...)` call for that stack's steps. `Command#unbundled_env` merges this attacker-influenced hash directly with `BASE_ENV`/`PATH`, with no key filtering [5](#0-4) , and `Command#start` passes it straight to `PTY.spawn` [6](#0-5) .

Root cause: `ReviewStack#env` treats label *names* as trusted, safe environment variable key material, performing no allowlisting, no prefixing, and no rejection of reserved/dangerous variable names (`GIT_CONFIG_COUNT`, `LD_PRELOAD`, `BUNDLE_*`, etc.).

Existing guards do not close this gap: `ExplicitParameters` only validates that `name` is a `String`, not its content; there is no `EnvironmentVariables#permit`-style filter applied to `ReviewStack#env`'s own keys (that class is used for interpolation of values, not for restricting which keys can exist in the environment); webhook signature verification only authenticates that GitHub sent the payload, not that its label-name content is safe to use as a shell/process environment key.

### Impact Explanation
Any `ci.require`, deploy, or other task step that invokes `git` (directly or indirectly, e.g. via `git fetch`/`git checkout` performed by `TaskCommands#clone`/`#checkout`, or by the fork's own `shipit.yml` steps) executes with `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`, `GIT_CONFIG_VALUE_0` present in its environment if those exact strings are used as label names. Git honors these variables to inject arbitrary config at process start, and config keys such as `core.fsmonitor`, `core.hooksPath`, or `alias.*` are executed as commands by git itself — yielding remote code execution on the Shipit deploy host under the Shipit process's privileges. This is scoped to whichever repository's review stack triggers the step, but since the deploy host and its credentials (e.g. `GITHUB_TOKEN`) are shared infrastructure, RCE there constitutes a Critical-severity compromise of the whole Shipit deployment environment, not just one tenant's stack.

### Likelihood Explanation
Preconditions: the repository must use `provisioning_behavior: prevent_with_label` (or otherwise be a review-stack-enabled repo) so that `ReviewStack#env` is exercised; a `pull_request` webhook event must be delivered and pass signature verification; and — per the stated threat model — the attacker must be able to attach a label named exactly `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` (case-insensitive since it's upcased) to their own fork's PR. Whether a pure external contributor can label their own PR is a GitHub permissions question outside this engine's code; if the repo grants triage access to contributors, or if any actor with label-write access (including a compromised/malicious collaborator) can add these labels, the exploit is straightforward, cheap, and repeatable on every subsequent CI run for that review stack.

### Recommendation
In `ReviewStack#env`, do not use raw (even upcased) label names as environment variable keys. Either (a) prefix every label-derived key with a fixed safe namespace, e.g. `"LABEL_#{label_name.upcase}"`, or (b) maintain an explicit allowlist of permitted label-derived variable names, or (c) strip/reject label names matching reserved/dangerous patterns (`GIT_*`, `LD_*`, `BUNDLE_*`, `PATH`, etc.) before merging them into the environment hash.
