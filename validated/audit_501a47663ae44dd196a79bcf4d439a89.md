### Title
Webhook signature verification is bound to the attacker-controlled `repository.owner.login`, not to the repository actually acted upon - unauthenticated forged status/push events for any tracked repo (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects which GitHub App configuration (and therefore which `webhook_secret`) is used to verify a webhook's HMAC signature based on a field taken directly from the unauthenticated JSON body, while the event handlers that follow act on a different field (`repository.full_name`) from that same, still-unverified body. Combined with the fact that signature verification is a no-op whenever the selected organization has no `webhook_secret` configured, an attacker can pick *any* zero-secret (or attacker-known-secret) organization to satisfy `verify_signature`, then have the payload's `repository` object point at a completely different, victim-tracked repository. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`repository_owner` is derived straight from the untrusted payload: [1](#0-0) 

It is used to pick the GitHub App/organization config used for HMAC verification: [2](#0-1) 

Crucially, verification is bypassed entirely whenever that organization has no configured secret: [3](#0-2) 

The `webhook_secret` is documented as optional and shown as `nil`/blank in the setup docs and fixtures, so real multi-org Shipit deployments commonly have at least one configured organization with a blank secret: [4](#0-3) [5](#0-4) 

After `verify_signature` passes (using the org keyed by `repository.owner.login`), the controller dispatches the *entire, attacker-controlled* payload to the event handlers without re-checking that `repository.full_name` (used to resolve the actual `Stack`/`Commit`/`Repository`) matches the organization whose secret was used: [6](#0-5) 

The `status` webhook handler writes CI status fields (`state`, `description`, `context`, `target_url`) taken directly from the payload onto the resolved commit, with no round-trip to GitHub's API to confirm authenticity of the content: [7](#0-6) 

This is the same class of bug as the GoGoPool `AVAXAssignedHighWater` finding: a value that is checked/authenticated (there: `getAVAXAssigned`; here: `repository.owner.login`) is not the same value that is ultimately acted upon (there: the increment amount; here: `repository.full_name`), letting an attacker manipulate the acted-upon value while satisfying the check on a different field.

### Impact Explanation
An unauthenticated attacker who knows (or can discover, e.g. via the app's public GitHub App page or a leaked/blank secret) that at least one configured organization in `Shipit.github` has no `webhook_secret` can:
1. POST to `/webhooks` with `X-Github-Event: status`, setting `repository.owner.login` to the zero-secret org (satisfying `verify_signature`), and `repository.full_name`/`sha` to a commit of an entirely different, victim organization's tracked stack.
2. Have Shipit record an attacker-chosen CI status (e.g. `"success"`) for that commit.
3. If the victim stack has `continuous_deployment` enabled and relies on that status context, this can cause Shipit to trigger an **unauthorized deploy** of a commit that never actually passed CI - satisfying the "unauthorized deploy" Critical/High impact criteria without any Shipit session, `ApiClient` token, or GitHub credentials.

### Likelihood Explanation
No credentials, session, or GitHub write access are required - only a POST to the public `/webhooks` endpoint. The only precondition is that the Shipit instance is configured with at least one organization lacking a `webhook_secret` (documented as optional, and shown as the default/blank value in the project's own setup docs and test fixtures), which is a realistic and even encouraged configuration for smaller or single-tenant Shipit instances that skip the "optional" secret step.

### Recommendation
- Verify the webhook signature using the organization/app config that matches `repository.full_name` (or the resolved `Stack`'s configured organization), not a value read from an as-yet-unverified field.
- Require a non-blank `webhook_secret` for every configured GitHub App/organization (stop treating `verify_webhook_signature` as trivially true when unset), or fail closed when it is missing.
- After signature verification, re-validate that `repository.owner.login`/`organization.login` used for verification matches the repository actually resolved and mutated by the handler before processing the event.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` (no `webhook_secret`) and `orgB` (tracked stack `orgB/victim-repo`), as shown possible in `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. `repository_owner` resolves to `"orgA"`; `Shipit.github(organization: "orgA").verify_webhook_signature` returns `true` unconditionally because `orgA.webhook_secret` is blank (`lib/shipit/github_app.rb` lines 76-83).
4. The `status` handler processes the payload against `orgB/victim-repo`'s commit, writing the forged `"success"` status as demonstrated by the behavior tested in `test/controllers/webhooks_controller_test.rb` lines 42-59, potentially unblocking continuous deployment for a stack the attacker never had signed access to.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
