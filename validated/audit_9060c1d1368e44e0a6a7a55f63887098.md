### Title
Webhook signature verified against attacker-chosen organization while handlers act on unauthenticated `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App/organization's `webhook_secret` to verify the HMAC against using an unauthenticated field taken straight from the JSON body (`repository.owner.login`, falling back to `organization.login`), before any signature has been checked. The event handlers that subsequently act on the payload (e.g. `PushHandler`) resolve the **target stack/repository** from a different, equally unauthenticated field of the same body (`repository.full_name`). These two fields are never cross-validated, so the organization whose secret validated the request is not guaranteed to be the organization/repository that is actually acted upon.

### Finding Description
`verify_signature` computes `repository_owner` purely from request JSON: [1](#0-0) 

It then fetches the `GitHubApp` instance for that owner and verifies the signature against *that* organization's secret: [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when the resolved organization has no `webhook_secret` configured (a documented, valid configuration state, e.g. `webhook_secret: # nil` in the multi-org secrets example): [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (based solely on `repository.owner.login`), `WebhooksController#create` dispatches the *entire raw payload* — including the independent `repository.full_name` field — to the handler: [5](#0-4) 

`PushHandler#process` uses `stacks` (resolved from the payload's repository, not from `repository_owner`) to find and sync stacks by branch, ultimately calling `stack.sync_github`: [6](#0-5) 

The binding that should hold is: **organization whose signature was verified == organization/repository the handler acts on**. Because `repository_owner` (verification key selection) and `repository.full_name` (handler's stack lookup) are independent, unauthenticated fields of the same attacker-supplied JSON body, this equality is never enforced.

### Impact Explanation
In a multi-organization Shipit deployment (explicitly supported, see `config/secrets.development.shopify.yml`), if any one configured organization has no `webhook_secret` set (or its secret is otherwise known/weak), an attacker can craft a webhook body where `repository.owner.login` names that unprotected organization (so `verify_webhook_signature` short-circuits to `true`) while `repository.full_name`/branch fields name a stack belonging to a *different*, properly-secured organization. The unauthenticated push is then processed against the victim organization's stack, invoking `Stack#sync_github`, which can trigger a resync and, on stacks with continuous deployment enabled, an unauthorized deploy trigger — without ever presenting a signature valid for the victim org's actual GitHub App secret. This crosses the "unauthorized deploy" / cross-repository-write impact bar for a High-severity finding, since the attacker never needed a Shipit session, an `ApiClient` token, or the target organization's `webhook_secret`.

### Likelihood Explanation
Requires: (1) the Shipit instance configured for multiple GitHub organizations (a documented supported pattern), and (2) at least one configured organization lacking a `webhook_secret` (also a documented supported/valid configuration — the example config files ship with `webhook_secret: # nil`). Given that combination, exploitation only requires sending a single unauthenticated HTTP POST to `/webhooks` with a crafted JSON body; no credentials or GitHub App access are needed. Likelihood is moderate to high in any deployment that mixes strict-secret and no-secret organizations, and is a pure application logic bug independent of GitHub's own trust model.

### Recommendation
After verifying the signature for `repository_owner`, re-derive/validate that every downstream identifier the handler will use (`repository.full_name`, `organization.login`, etc.) belongs to the same verified organization before dispatching to `Shipit::Webhooks.for_event(event)`. Alternatively, disallow trivial `true` verification when `webhook_secret` is unset for any organization sharing infrastructure with organizations that do have a secret, or require that `repository.full_name`'s owner segment match `repository_owner` exactly before processing.

### Proof of Concept
1. Deploy Shipit configured with two organizations: `unsecured-org` (no `webhook_secret`) and `victim-org` (with `webhook_secret` set and Shipit stacks configured).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim commit sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No `X-Hub-Signature` header needed, since `repository_owner` resolves to `unsecured-org`, whose `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-83`.
3. `WebhooksController#create` still dispatches the full payload to `PushHandler`, which resolves stacks from `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: ...)`, acting on the victim organization's stack despite the signature never being checked against `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
