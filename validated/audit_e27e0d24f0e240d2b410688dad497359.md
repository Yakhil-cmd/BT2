### Title
Malformed/short `signer-key` in PoX-5 collapses into a zero-key signer entry, silently merging distinct stakers' weight - ([File: stackslib/src/chainstate/nakamoto/signer_set.rs])

### Summary
In `StakeEntryIteratorPox5::fallible_next`, the `signer-key` buffer returned from the PoX-5 `signers` map (via `get-signer-info`) is converted into a fixed-size `[u8; SIGNERS_PK_LEN]` array using `try_into().unwrap_or([0; SIGNERS_PK_LEN])`. Unlike every other malformed-data path in the same function (which returns `PoxEntryParsingError::Skip(...)` and drops the entry), a conversion failure here is silently swallowed and replaced with the all-zero key rather than skipping the entry or aborting. [1](#0-0) 

### Finding Description
The comment on the sibling PoX-4 parsing path explicitly documents the underlying Clarity semantics: `(buff 33)` "only enforces max size, not min size," which is why `from_pox_4_tuple` performs an explicit `signer.len() == SIGNERS_PK_LEN` check and falls back to a defined all-zero buffer only after that explicit, documented check. [2](#0-1) 

The PoX-5 iterator path (`fallible_next`) reads the same kind of `(buff 33)` value from the contract's `signers` map via `get-signer-info`, but does not perform that length validation before converting to a fixed array — it uses `unwrap_or([0; SIGNERS_PK_LEN])` directly, so any registered `signer-key` shorter than 33 bytes silently becomes the all-zero key instead of causing the entry to be skipped like other malformed data in this same function. [3](#0-2) 

Downstream, `pox_5_make_signer_set` aggregates entries into a `HashMap<[u8; SIGNERS_PK_LEN], u128>` keyed by `entry.signer_key`, summing `amount_ustx` for any entries that share a key. [4](#0-3) 

If two or more distinct signers register with a `signer-key` shorter than 33 bytes (which the Clarity type `(buff 33)` alone does not prevent), their stacked amounts collapse into a single all-zero-key entry in this hash map. That combined entry is then apportioned real reward-slot weight and pushed into the final `signer_set` used to update the `.signers` contract, so a signing identity that nobody legitimately controls (the zero key) can end up carrying weight equal to the sum of multiple honest stakers' locked STX. [5](#0-4) 

This is a direct structural analog of the reported bug class: a field that fails an implicit validity assumption (exact length / non-null) is not checked before being relied upon, and instead of erroring out (as every other malformed-field path in the same function does via `Skip`/`Abort`), the code silently substitutes a default/zero value, changing program state in a way the caller never intended or authorized.

### Impact Explanation
Reward-cycle signing weight is a consensus-critical quantity: it determines which signer identities must co-sign Nakamoto blocks for a cycle. If multiple stakers' locked-STX weight is folded into a bogus zero-key entry, that entry receives real reward-slot weight backed by real locked STX, but the zero key is not an authorization any of those stakers gave for a shared signing identity — it is a stacking/signing action none of them actually authorized. This can permanently or temporarily freeze the affected stakers' ability to have their weight properly represented in signing (since the "signer" that holds their aggregated weight cannot produce valid signatures), and it breaks the equality between "signing weight assigned" and "signing weight legitimately committed by an identifiable key," matching the High-impact criterion of "signing weight or reward slots exceeding locked value" / "an unsigned stacking action."

### Likelihood Explanation
Likelihood depends on whether `pox-5.clar`'s `register-signer` (or equivalent) enforces the `signer-key` to be exactly 33 bytes beyond the Clarity `(buff 33)` type bound (which only enforces a maximum, not exact length) — I was not able to confirm this length check from the available index before running out of iterations, so this is stated as uncertain. The Rust-side defect (silent `unwrap_or` to zero instead of `Skip`, inconsistent with every sibling check in the same function) is confirmed directly from the code.

### Recommendation
In `fallible_next`, replace `signer_key_buff.try_into().unwrap_or([0; SIGNERS_PK_LEN])` with an explicit length check that returns `PoxEntryParsingError::Skip(...)` (consistent with the rest of the function) when the buffer length is not exactly `SIGNERS_PK_LEN`, mirroring the defensive check already present in `RawRewardSetEntry::from_pox_4_tuple`. Additionally, confirm and, if necessary, add an explicit `(len signer-key) == 33` assertion in `pox-5.clar`'s signer-registration entry point so malformed keys can never be written to the `signers` map in the first place.

### Proof of Concept
Conceptual (Rust-level) reproduction against `pox_5_make_signer_set`, mirroring the reporter's JSON PoC style:
1. Two distinct principals register as signers in `pox-5.clar` with `signer-key` values that are valid per the `(buff 33)` type but shorter than 33 bytes (e.g., 1-byte buffers with different content) — assuming `register-signer` performs no additional length assertion (unconfirmed).
2. Each accumulates locked STX independently via the normal `stack-stx`/delegation flow, entering the per-cycle signer-set linked list.
3. During prepare-phase signer-set computation, `StakeEntryIteratorPox5::fallible_next` reads each principal's `signer-key` via `get-signer-info`; the `try_into::<[u8;33]>()` conversion fails for both (length mismatch) and both fall back to `[0u8; 33]` instead of being skipped. [6](#0-5) 
4. `pox_5_make_signer_set` sums both signers' `amount_ustx` under the single `[0u8;33]` key, producing one `NakamotoSignerEntry` with `signing_key = [0;33]` and combined weight/stacked amount from two unrelated stakers. [7](#0-6) 

Note: I could not fully verify, within the available tool budget, whether `pox-5.clar`'s `register-signer` function independently rejects non-33-byte `signer-key` values (the file exists at `stackslib/src/chainstate/stacks/boot/pox-5.clar` but its relevant validation logic was not retrieved before the iteration limit was reached). If that Clarity-side check does enforce exact length, the reachable severity of this analog would be reduced to a defense-in-depth gap rather than a directly exploitable issue; a Devin session with full repo access should confirm this before treating the finding as fully proven.

        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
        }

        let mut signer_set: Vec<_> = apportioned
            .into_iter()
            .filter_map(|entry| {
                if entry.weight == 0 {
                    return None;
                }

                    signing_key: entry.signing_key,
                    stacked_amt: entry.stacked_amt,
                    weight,
                })
            })
            .collect();
