### Title
`printLinkedBranches` writes unsanitized remote branch names/URLs to the terminal/pager - ([File: pkg/cmd/issue/develop/develop.go])

### Summary
`printLinkedBranches` in `pkg/cmd/issue/develop/develop.go` renders `branch.BranchName` and `branch.URL` from the GitHub API directly into a table without stripping ANSI/control escape sequences before the bytes reach `io.Out`, which can be routed to an external pager.

### Finding Description
`developRunList` calls `api.ListLinkedBranches` to fetch linked branches for an issue and passes the raw results straight into `printLinkedBranches`: [1](#0-0) 

`printLinkedBranches` then feeds `branch.BranchName` and `branch.URL` as-is into `tableprinter.New(io, ...).AddField(...)` with no escape stripping or sanitization step applied to the string content itself: [2](#0-1) 

`tableprinter.New` wraps `ios.Out` (`internal/tableprinter/table_printer.go`) and simply writes fields to that writer; it performs padding/truncation/coloring logic but does not sanitize embedded terminal escape sequences in the field values themselves: [3](#0-2) 

`branch.BranchName` comes from a linked-branch record on GitHub's GraphQL API, and the branch name portion is derived from `refs/heads/<name>` on a repository — an attacker who can create a branch (e.g., via a linked branch on an issue they have permission to open, or via a fork) fully controls this string, including embedding raw ANSI/OSC escape sequences (e.g., terminal title changes, cursor manipulation, or clipboard/hyperlink OSC-8 sequences). `branch.URL` is likewise attacker-influenced (constructed from repo/branch names). Because `io.Out` can be an external pager (e.g. `less`) when stdout is a TTY, and pagers may interpret raw ANSI codes differently than gh's own color scheme rendering (e.g. `less -R` passing through OSC 8 hyperlinks or cursor-repositioning sequences that gh itself doesn't otherwise emit for this content), differing escape interpretation between gh and the pager could be used for terminal spoofing (fake prompts, hidden text, cursor tricks).

I could not find any generic ANSI/escape-sequence sanitization applied to arbitrary field values before they are written by `tableprinter` or by `iostreams`'s pager-writing path in this repository (searches for `sanitize`/`removeEscape`-style helpers in `internal/tableprinter` returned nothing). This suggests table field values are trusted to already be "safe" text, which is not true for repository-controlled fields like branch names.

### Impact Explanation
If exploitable, this allows a remote GitHub user to inject terminal control sequences into another user's terminal via `gh issue develop --list`, potentially spoofing terminal output/prompts. This matches the "Terminal output/prompt spoofing" impact class, but it is a **general terminal-escape display issue affecting essentially every gh subcommand that prints repo/branch/user-controlled strings** (not unique to `printLinkedBranches`), which is typically treated by terminal emulators/pagers as an inherent risk of displaying untrusted text rather than a code-execution or credential-exfiltration primitive. I was not able to confirm within the available index that gh has (or lacks) a project-wide policy/helper specifically meant to strip such sequences that this function bypasses, nor could I fully inspect `pkg/iostreams/iostreams.go`'s pager-invocation code path to confirm exactly how bytes are handed off to the pager (e.g., whether `less -R` or similar flags are used, and whether that changes escape interpretation from gh's own).

### Likelihood Explanation
An attacker only needs to create a branch/issue-branch-link with a crafted name (or influence a URL field) — achievable by any user with normal repo permissions to open an issue and link/create a development branch, or by a public repo where they can create branches. The victim then needs to run `gh issue develop --list` against that repo. This is easily repeatable, but requires the victim's pager configuration to interpret the injected sequences in a way that produces a harmful effect (e.g., a maliciously configured or specific pager behavior), which is not fully verifiable from the code alone.

### Recommendation
Sanitize/strip control and ANSI escape sequences from all attacker-controlled string fields (branch names, URLs, etc.) before adding them to `tableprinter` fields, or apply a consistent sanitization pass in `tableprinter.AddField`/`iostreams` writer path regardless of destination (stdout, TTY, or pager), so that raw untrusted bytes never reach the pager unmodified.

### Proof of Concept
Construct a Go test using a stub `api.LinkedBranch` with `BranchName` containing raw escape sequences (e.g., `"\x1b]0;pwned\x07feature"` or OSC 8 hyperlink sequences), call `printLinkedBranches` with an `iostreams.IOStreams` configured with a TTY-like buffer, and assert that the bytes written to `io.Out` still contain the raw `\x1b` sequences unescaped/unstripped — demonstrating that sanitization is not applied before the bytes would be handed to a pager.

Note: I was unable to fully trace `pkg/iostreams/iostreams.go`'s pager-invocation logic (how `io.Out` is redirected to an external pager process and with what flags) within the available index, so the exact escape-handling divergence between gh and the pager (the "different escape handling" claim) could not be conclusively confirmed from code alone — a full session with terminal/process access would be needed to validate actual pager behavior (e.g. `less -R` vs `less` vs `more`).

func developRunList(opts *DevelopOptions, apiClient *api.Client, issueRepo ghrepo.Interface, issue *api.Issue) error {
	opts.IO.StartProgressIndicatorWithLabel("Fetching linked branches")
	defer opts.IO.StopProgressIndicator()

	branches, err := api.ListLinkedBranches(apiClient, issueRepo, issue.Number)
	if err != nil {
		return err
	}
	opts.IO.StopProgressIndicator()

	if len(branches) == 0 {
		return cmdutil.NewNoResultsError(fmt.Sprintf("no linked branches found for %s#%d", ghrepo.FullName(issueRepo), issue.Number))
	}

	if opts.IO.IsStdoutTTY() {
		fmt.Fprintf(opts.IO.Out, "\nShowing linked branches for %s#%d\n\n", ghrepo.FullName(issueRepo), issue.Number)
	}

	printLinkedBranches(opts.IO, branches)

	return nil
}

func printLinkedBranches(io *iostreams.IOStreams, branches []api.LinkedBranch) {
	cs := io.ColorScheme()
	table := tableprinter.New(io, tableprinter.WithHeader("BRANCH", "URL"))
	for _, branch := range branches {
		table.AddField(branch.BranchName, tableprinter.WithColor(cs.ColorFromString("cyan")))
		table.AddField(branch.URL)
		table.EndRow()
	}
	_ = table.Render()
}

// New creates a TablePrinter from an IOStreams.
func New(ios *iostreams.IOStreams, headers headerOption) *TablePrinter {
	maxWidth := 80
	isTTY := ios.IsStdoutTTY()
	if isTTY {
		maxWidth = ios.TerminalWidth()
	}

	return NewWithWriter(ios.Out, isTTY, maxWidth, ios.ColorScheme(), headers)
}

// NewWithWriter creates a TablePrinter from a Writer, whether the output is a terminal, the terminal width, and more.
func NewWithWriter(w io.Writer, isTTY bool, maxWidth int, cs *iostreams.ColorScheme, headers headerOption) *TablePrinter {
	tp := &TablePrinter{
		TablePrinter: tableprinter.New(w, isTTY, maxWidth),
		isTTY:        isTTY,
		cs:           cs,
	}

	if isTTY && len(headers.columns) > 0 {
		// Make sure all headers are uppercase, taking a copy of the headers to avoid modifying the original slice.
		upperCasedHeaders := make([]string, len(headers.columns))
		for i := range headers.columns {
			upperCasedHeaders[i] = strings.ToUpper(headers.columns[i])
		}

		// Make sure all header columns are padded - even the last one. Previously, the last header column
		// was not padded. In tests cs.Enabled() is false which allows us to avoid having to fix up
		// numerous tests that verify header padding.
		var paddingFunc func(int, string) string
		if cs.Enabled {
			paddingFunc = text.PadRight
		}

		tp.AddHeader(
			upperCasedHeaders,
			WithPadding(paddingFunc),
			WithColor(cs.TableHeader),
		)
	}

	return tp
}
