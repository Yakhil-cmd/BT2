### Title
Membership webhook `organization.login`/`team.id` binding diverges from the signature-verifying `repository_owner`, allowing cross-organization team/membership forgery - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` to validate a `membership` event using `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. `MembershipHandler#process`/`#find_or_create_team!`, however, unconditionally trusts `params.organization.login` and `params.team.id` to create/mutate a `Team` and add a `User` to it. An attacker who legitimately controls one Shipit-configured GitHub organization (and therefore knows its `webhook_secret`) can inject an extra `repository.owner.login` field naming their own org (so signature verification passes) while setting `organization.login`/`team.id` to identify a different, victim organization's team, causing the handler to grant membership in the victim org's team.

### Finding Description
The binding that must hold is: `repository_owner` (the field used in `Shipit.github(organization: repository_owner)` at [2](#0-1)  to pick the `webhook_secret` that authenticates the request) `==` `params.organization.login` (the field used at [3](#0-2)  to create/mutate the `Team` row and, transitively, grant `team.add_member(member)` at [4](#0-3) ).

`repository_owner` is computed as: [5](#0-4) 

Because it prefers `repository.owner.login` over `organization.login`, an attacker can supply a JSON body containing both keys with different values. For a real GitHub `membership` event, GitHub does not include a `repository` object at all (it's an org-scoped event, as seen in fixtures where `repository_params` had to be manually merged for the test harness at [6](#0-5) ). Since `WebhooksController#create` just does `JSON.parse(request.raw_post)` with no schema enforcement before `verify_signature` runs, the attacker is free to add an arbitrary `repository.owner.login` field.

Exploit flow:
1. Attacker legitimately controls/operates GitHub org `attacker-org`, which is one of the organizations configured in this Shipit instance's `secrets.yml` (multi-org config as documented) and therefore knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `membership` payload:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. `repository_owner` resolves to `"attacker-org"` (from the injected `repository.owner.login`), so `Shipit.github(organization: "attacker-org")` selects `attacker-org`'s `webhook_secret`, and the attacker computes a valid `X-Hub-Signature` HMAC with it. `verify_webhook_signature` passes at [7](#0-6) .
4. `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which parses only the declared schema fields (`action`, `team`, `organization`, `member`) — it never reads or cross-checks `repository` at [8](#0-7) .
5. `find_or_create_team!` creates (or reuses, if `github_id` already matches) a `Team` with `organization = "victim-org"`, and `team.add_member(member)` inserts a `Membership` row for the attacker's own GitHub login into that victim-org team, at [9](#0-8) .
6. On the attacker's next login, `User#authorized?` reads purely from the local `teams`/`Membership` table — `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` — with no live GitHub re-verification, at [1](#0-0) , so the forged membership immediately grants `victim-org`'s access.

Existing guards fail because: `verify_signature`'s job is only to check "is this request cryptographically bound to *some* configured org's secret", but it derives which org that is from attacker-controlled JSON rather than from the same field the handler subsequently trusts for the mutation. No code path checks `repository_owner == params.organization.login`.

### Impact Explanation
An attacker who operates any one Shipit-configured GitHub organization can grant themselves (or any GitHub login they name) membership in a `Team` belonging to a *different*, victim organization tracked by the same Shipit instance, and that forged membership feeds directly into `Shipit.github_teams`-based `authorized?` checks, escalating authorization across tenant boundaries in a single, repeatable HTTP POST to `/webhooks`. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category, and is repeatable against any `team.id`/`organization.login` combination the attacker can name.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (each with its own `webhook_secret`), and the attacker to legitimately control at least one of those configured organizations — a realistic scenario in the documented multi-org deployment mode (`docs/setup.md`). No GitHub App private key, session, or Shipit-side secret is needed beyond the attacker's own org's `webhook_secret`, which they are entitled to know as that org's operator. The attacker also needs to know or guess the victim team's `github_id` (small sequential integers are commonly enumerable, or a fresh `github_id` can be invented, causing a brand-new `Team` row to be created for the victim org rather than reusing an existing one) and the victim `organization.login` (public information).

### Recommendation
In `MembershipHandler#find_or_create_team!` (and `#process`), verify that `params.organization.login` matches the `repository_owner`/verified organization used during signature verification (e.g., pass the verified organization through to the handler and assert equality, rejecting the event otherwise). Alternatively, remove the `repository.owner.login` fallback ambiguity by having `verify_signature` for org-scoped events (`membership`) key exclusively off `params.organization.login`, and reject payloads that also carry an unrelated `repository` object for such events.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in test secrets (or stub `Shipit.github_app_config`) so `attacker-org` and `victim-org` each have distinct `webhook_secret`s.
2. Build payload: `{ action: 'added', team: { id: 9999, name:'x', slug:'x', url:'https://x' }, organization: { login: 'victim-org' }, member: { login: 'attacker-login' }, repository: { owner: { login: 'attacker-org' } } }.to_json`.
3. Compute `X-Hub-Signature` using `attacker-org`'s `webhook_secret` (`sha1=` + HMAC-SHA1(secret, body)).
4. `assert_equal 'attacker-org', @controller.send(:repository_owner)` (or assert via `Shipit.github.expects(:verify_webhook_signature)` called with `attacker-org`'s app) — this is one side of the binding.
5. POST to `/webhooks` with `X-Github-Event: membership` and the signature; assert `response.status == 200`.
6. Assert `Team.find_by(github_id: 9999).organization == 'victim-org'` — the other side of the binding, proving divergence.
7. Assert `Membership.exists?(team: Team.find_by(github_id: 9999), user: User.find_by(login: 'attacker-login'))`.
8. With `Shipit.github_teams` stubbed to include that team, assert `User.find_by(login: 'attacker-login').authorized?` is `true`.
