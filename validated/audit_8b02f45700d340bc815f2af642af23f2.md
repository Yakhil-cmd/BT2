### Title
Missing cross-process locking on Windows (`fcntl is None`) allows TOCTOU race in `atomic_check_counter`, bypassing `MAX_STOP_HOOK_FIRINGS`/`MAX_COMMIT_REVIEWS_PER_HOUR` limits - ([File: plugins/security-guidance/hooks/session_state.py])

### Summary
`with_locked_state` falls back to a completely unlocked `load_state` → `callback` → `save_state` sequence whenever `fcntl` is unavailable (Windows, or any platform where the import fails), removing the mutual exclusion that rate-limit counters depend on. Any counter built on top of this helper (e.g. `atomic_check_counter` for `MAX_STOP_HOOK_FIRINGS` / `MAX_COMMIT_REVIEWS_PER_HOUR`) is vulnerable to a classic read-modify-write race if two hook invocations execute concurrently.

### Finding Description
`with_locked_state` (`plugins/security-guidance/hooks/session_state.py:118-138`) branches on `fcntl is None`: [1](#0-0) 

In this branch there is no `flock`, no advisory lock, and no other mutual-exclusion primitive — it is a bare read → mutate → write. The counter-enforcement logic in `security_reminder_hook.py` (`atomic_check_counter`) relies entirely on `with_locked_state` to make its increment-and-compare against `MAX_STOP_HOOK_FIRINGS`/`MAX_COMMIT_REVIEWS_PER_HOUR` atomic. If two hook invocations for the same `session_id`/`counter_key` run concurrently on a system without `fcntl` (Windows is the primary real-world case; the code explicitly comments "No file locking available (Windows) — run without locking"), both can call `load_state` before either calls `save_state`, both see the counter below the max, both pass the check, and both write back independently — one overwriting the other's increment. This is a true TOCTOU race rooted in the absence of any lock, not a config/test artifact.

### Impact Explanation
This allows an attacker (or normal concurrent automation) to exceed the intended hard caps enforced by these counters — effectively doubling (or further multiplying, with more overlap) the number of stop-hook firings or commit reviews allowed per session/hour on affected platforms. This violates the "deny means deny" invariant the counters are meant to guarantee, undermining a security control (rate-limited safety nagging/review triggers) rather than merely being a performance or correctness nit.

### Likelihood Explanation
Requires: (1) running on a platform without `fcntl` (Windows, or any environment where the import fails), and (2) genuinely concurrent invocations of the same counter key, which the code's own docstring acknowledges can occur (CCR mode spawns new processes per turn with a stable `CLAUDE_CODE_REMOTE_SESSION_ID`, and overlapping tool calls can trigger overlapping hook executions). No privilege escalation or malicious input is needed — only normal, slightly-overlapping tool-call timing on Windows. This makes it readily reproducible in a unit test and plausible, though not universal, in real usage since it depends on timing/platform.

### Recommendation
Provide a real cross-process lock for the no-`fcntl` fallback, e.g. use `msvcrt.locking` on Windows, or an `os.O_CREAT | os.O_EXCL` exclusive lock-file scheme with retry/backoff, rather than skipping locking entirely. At minimum, serialize access with a process-local `threading.Lock`/`multiprocessing.Lock` keyed by `counter_key` for same-process races, combined with a portable cross-process file-lock library (e.g. `portalocker`) for cross-process races.

### Proof of Concept
Unit test:
1. Monkeypatch `session_state.fcntl = None`.
2. Spawn two threads that each call `atomic_check_counter(session_id, counter_key, max_count=1)` for the same `session_id`/`counter_key`, synchronized so both threads call `load_state` before either calls `save_state` (e.g. insert a small `time.sleep` inside a patched `callback` or `load_state` to widen the race window).
3. Assert that at most one of the two threads receives `True` (i.e., the counter is allowed to fire only once).
4. Expected failing result on current code: both threads observe `True`, demonstrating the counter cap is bypassed; expected passing result after the fix: exactly one thread observes `True`.
