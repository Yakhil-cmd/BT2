### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping, allowing a stack-scoped token to read any stack's CCMenu status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController#stack` restricts stack lookup to the `stacks` scope, which filters by `current_api_client.stack_id` when the client is scoped to a specific stack. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, discarding that restriction entirely, so a token scoped to one stack can be replayed against any `stack_id` in the URL to read another stack's deploy/task status.

### Finding Description
The binding that should hold is: for every stack lookup performed by an authenticated API request, `stack ∈ current_api_client.stack_id? ? {Stack.find(current_api_client.stack_id)} : Stack.all`. `Api::BaseController` enforces exactly this via: [1](#0-0) 

`Api::CCMenuController` overrides `#stack` and drops the `stacks` scope, resolving directly against the global `Stack` relation: [2](#0-1) 

`require_permission :read, :stack` only checks a string permission (`"read:stack"`) present in `ApiClient#permissions`; it is not tied to any specific stack id: [3](#0-2) 

The per-stack restriction exists solely because `ApiClient belongs_to :stack, optional: true` and `BaseController#stacks` filters by it: [4](#0-3) 

So whenever an `ApiClient` is created/administered with a specific `stack_id` (a supported, legitimate scoping mechanism for API clients restricted to one stack's data), the `Api::CCMenuController#show` action ignores that restriction: [5](#0-4) 

Attack: given an `ApiClient` token with `permissions: ["read:stack"]` and `stack_id: 1`, an attacker (or the same low-privilege system that legitimately received that token to poll stack 1's CI status) sends `GET /api/stacks/2/ccmenu.xml?token=<token>`. `authenticate_api_client` only verifies the signature of the token, not which stack it is authorized for: [6](#0-5) 

`require_permission!` passes because the client has `read:stack`, and `stack` resolves stack 2 directly via `Stack.from_param!`, bypassing the `stacks` scope check that would have raised `ActiveRecord::RecordNotFound` for a client restricted to stack 1. `CCMenuUrlController#fetch`/`#client` (which mints tokens for the CCMenu UI flow) does not itself set `stack_id`, but this does not close the gap for any `ApiClient` that is otherwise stack-scoped through legitimate administration - the controller-level bypass applies to any such token, not just ones from this one flow.

### Impact Explanation
Any valid `ApiClient` token bearing `read:stack` permission - even one intentionally scoped to a single stack via `stack_id` - can be replayed against `/api/stacks/:stack_id/ccmenu.xml` for an arbitrary stack, exposing that stack's latest deploy/rollback/task state (branch, revision, running/success/failure status) without being authorized for it. This is an unauthorized cross-tenant read of stack state via a credential that was deliberately restricted, matching "High - unauthenticated/unauthorized read of stack state" for repositories the token holder was not entitled to see. It does not lead to RCE, secret exfiltration, or write access, so it does not rise to Critical.

### Likelihood Explanation
Preconditions: possession of any valid stack-scoped `ApiClient` token with `read:stack` permission (obtained legitimately for one stack, e.g. a CI status badge or CCMenu integration for a repository the attacker's org participates in). No GitHub secrets, session, or admin access is required beyond having one such token. The attacker only needs to change the `stack_id` in the URL - a single unauthenticated-cost HTTP GET - and the attack is fully repeatable against every stack id in the instance.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController`, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so it respects `current_api_client.stack_id` exactly like every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual addition)
test "a token scoped to stack 1 cannot read stack 2's ccmenu status" do
  stack1 = shipit_stacks(:shipit)
  stack2 = shipit_stacks(:shipit2) # a different stack
  scoped_client = Shipit::ApiClient.create!(
    creator: shipit_users(:walrus),
    name: "Scoped CCMenu Client",
    permissions: %w[read:stack],
    stack_id: stack1.id,
  )

  get "/api/stacks/#{stack2.to_param}/ccmenu.xml", params: { token: scoped_client.authentication_token }

  # Binding under test: stack ∈ {stack1} for this token, so stack2 must NOT be reachable.
  assert_response :not_found # currently fails: renders stack2's XML with :ok
end
```
This demonstrates that `current_api_client.stack_id == 1` while the served `stack.id == 2`, violating the binding enforced everywhere else via `Api::BaseController#stacks`.
