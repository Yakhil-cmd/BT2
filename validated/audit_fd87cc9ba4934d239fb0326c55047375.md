## Title
Unchecked return value of critical DB write queries when saving private payment chains leads to false acceptance of unpersisted transfers - (File: `divisible_asset.js`, `indivisible_asset.js`)

### Summary
When ocore persists a validated private (hidden) payment chain, it executes a batch of `INSERT`/`UPDATE` queries (marking source outputs as spent, inserting new outputs/inputs) via `async.series(arrQueries, ...)`. In both `divisible_asset.js` and `indivisible_asset.js`, the completion callback of this `async.series` call discards the error argument and unconditionally invokes `callbacks.ifOk()`, exactly mirroring the reported bug class of "external call performed, return/error value never checked, execution proceeds as if it succeeded."

### Finding Description
In `divisible_asset.js`, `validateAndSaveDivisiblePrivatePayment` builds `arrQueries` (which includes the query that marks the spent source output: `UPDATE outputs SET is_spent=1 WHERE unit=? AND message_index=? AND output_index=?`) and runs them via: [1](#0-0) 

`async.series(arrQueries, callbacks.ifOk)` passes the outer success callback directly as the completion handler of `async.series`. If any query in `arrQueries` errors (e.g., transient DB error, lock timeout, constraint violation), `async.series` invokes the callback with `(err)` as its first argument, but `callbacks.ifOk` does not treat that argument as an error - it is silently ignored and the caller proceeds down the "success" path.

The same pattern is repeated in `indivisible_asset.js`, where the persistence of a private payment chain (inserting inputs/outputs and marking `is_spent`) is finalized with: [2](#0-1) 

Here `async.series(arrQueries, function(){ profiler.stop('save'); callbacks.ifOk(); })` explicitly drops the `err` parameter of the completion function and always calls `callbacks.ifOk()`.

`callbacks.ifOk` in these flows ultimately reaches `private_payment.js`'s `validateAndSavePrivatePaymentChain`, which treats it as a definitive success signal, commits the transaction, and notifies the sender/UI that the private payment was accepted: [3](#0-2) 

Because the `COMMIT` (and the "accepted" callback chain feeding `network.handleOnlinePrivatePayment`'s `ifAccepted`) happens regardless of whether the underlying `INSERT`/`UPDATE` queries in `arrQueries` actually succeeded, this is a direct code-level unchecked-return-value defect in the exact spirit of the reported finding: an external mutating operation's result is not checked, letting fund-affecting code paths silently proceed on failure.

### Impact Explanation
This flow is reached by any private-payment counterparty relaying/forwarding a private payment chain to a peer or hub (`network.js`'s `handleOnlinePrivatePayment`, `wallet.js`'s `handlePrivatePaymentChains`). If a write in the persistence batch silently fails:
- The source output's `is_spent` flag may remain `0` even though the recipient/hub has already been told the payment is `ifOk`/accepted, opening a path to double-spend the same private output later (since it wasn't actually marked spent in this node's local DB).
- The new output/input rows for the incoming private payment may never be inserted, so the recipient's local state is inconsistent with what was communicated as "accepted," which can result in loss/freezing of the received private funds from the recipient's perspective (the balance is unusable/undiscoverable locally) while other participants believe the transfer went through.

This directly maps to the allowed impact categories: double-spend of a stable output and private-payment fund loss/freezing due to node disagreement on the true persisted state.

### Likelihood Explanation
Triggering requires no special privilege - any private-payment counterparty (sender, recipient, or cosigner participating in a private asset transfer) exercises this exact code path during ordinary use. The failure only needs a transient DB error (lock contention, disk/connection hiccup) during the `arrQueries` batch, which is a realistic and not-implausible operational condition, especially under concurrent private payment relaying. Because the code has no `if (err) return callbacks.ifError(err);` guard, any such failure is masked rather than surfaced, making the defect purely a matter of an unlucky/intermittent DB error and not an unusual attack precondition.

### Recommendation
In both `divisible_asset.js` and `indivisible_asset.js`, check the `err` argument returned by `async.series(arrQueries, ...)` before calling `callbacks.ifOk()`. For example:
```js
async.series(arrQueries, function(err){
    if (err)
        return callbacks.ifError(err); // or ROLLBACK path
    callbacks.ifOk();
});
```
This ensures that persistence failures propagate to `private_payment.js`'s transaction handling (`ROLLBACK` + `callbacks.ifError`) instead of being swallowed and treated as a successful save.

### Proof of Concept
1. A private payment chain is received and passes validation (`validateDivisiblePrivatePayment`/`validatePrivatePayment`).
2. During persistence, one of the queries in `arrQueries` (e.g., the `UPDATE outputs SET is_spent=1 ...` or an `INSERT INTO outputs`) fails due to a transient DB error.
3. `async.series` calls its completion function with `err` set, but:
   - `divisible_asset.js` line 72 passes `err` straight into `callbacks.ifOk` (which ignores/misuses it as `bStable`/first success arg).
   - `indivisible_asset.js` line ~291-294 discards the `function(){ ... }` parameter entirely.
4. `callbacks.ifOk()` proceeds, `private_payment.js` issues `COMMIT` and reports `callbacks.ifOk()` upward, and `network.js`'s `ifAccepted` fires, notifying peers the payment was accepted - even though the local DB state for spent/received outputs is now inconsistent with that claim.
