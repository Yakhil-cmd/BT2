### Title
Unvalidated Actual Received Amount in ERC20 Bridge Deposit Enables Counterpart Reserve Drain — (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`requestERC20Transfer` and `onERC20Received` in `BridgeTransferERC20` emit `RequestValueTransfer` using the caller-supplied `_value` parameter without verifying the actual token amount the bridge received. For a fee-on-transfer ERC20 token, the bridge receives fewer tokens than `_value + _feeLimit`, yet the event records the full `_value`. The counterpart bridge's operator relays this event verbatim and calls `handleERC20Transfer` with `_value`, releasing more tokens on the destination chain than were ever deposited on the source chain — a direct drain of counterpart bridge reserves.

### Finding Description

**2-step path — `requestERC20Transfer`:**

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The bridge pulls `_value + _feeLimit` from the caller. For a fee-on-transfer token, the bridge actually receives `(_value + _feeLimit) × (1 − fee_rate)`. No balance snapshot is taken before or after the `safeTransferFrom` call. `_requestERC20Transfer` is then invoked with the original, unverified `_value`:

```solidity

    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // ← caller-supplied, not actual received amount

    _extraData

```

**1-step path — `onERC20Received`:**

```solidity

```

The token contract transfers `_amount + _feeLimit` to the bridge (with a fee-on-transfer token, the bridge receives less), then calls `onERC20Received` with the original `_amount`. The bridge again trusts the caller-supplied value without checking its actual balance increase.

**Counterpart relay — `handleRequestValueTransferEvent` → `handleERC20Transfer`:**

The Go relay in `node/sc/bridge_manager.go` reads `valueOrTokenId` directly from the `RequestValueTransfer` event log and passes it unchanged to `HandleERC20Transfer` on the counterpart bridge:

```go

        auth, txHash, from, to, ctpartTokenAddr,
        valueOrTokenId,   // ← taken verbatim from the event

```

`handleERC20Transfer` then releases exactly `_value` tokens to the recipient:

```solidity
// BridgeTransferERC20.sol L71

```

No guard anywhere in the chain validates that the source bridge actually received `_value` tokens.

### Impact Explanation

Each cross-chain ERC20 transfer with a fee-on-transfer token creates a deficit of `_value × fee_rate` tokens on the counterpart bridge. The counterpart bridge releases `_value` tokens while the source bridge only holds `_value × (1 − fee_rate)`. Repeated transfers progressively drain the counterpart bridge's token reserves until it cannot fulfill legitimate withdrawal requests. This constitutes an unauthorized drain of system-managed bridged assets.

### Likelihood Explanation

The precondition is that a fee-on-transfer ERC20 token is registered on the bridge. This can occur:

1. A token is registered normally and later upgrades its implementation to add a transfer fee (upgradeable proxy tokens).
2. A bridge owner registers a token without auditing its transfer behavior.

Once such a token is registered, any unprivileged user can trigger the vulnerability by calling `requestERC20Transfer` or `token.requestValueTransfer`. The `onlyRegisteredToken` modifier provides no protection against fee-on-transfer behavior.

### Recommendation

In `requestERC20Transfer`, record the bridge's token balance before and after `safeTransferFrom` and use the actual balance delta as the bridged value:

```solidity
function requestERC20Transfer(...) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived >= _value.add(_feeLimit), "fee-on-transfer token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Similarly, in `onERC20Received`, verify the balance increase matches `_value + _feeLimit` before proceeding. Alternatively, document and enforce at registration time that fee-on-transfer tokens are not supported.

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token (1% fee on all transfers) on the source (child) chain.
2. Bridge owner calls `registerToken(feeToken, counterpartFeeToken)` on both source and counterpart bridges.
3. Attacker (any user) approves the source bridge for `100e18 + feeLimit` tokens.
4. Attacker calls `requestERC20Transfer(feeToken, victim, 100e18, 0, "")`.
5. Source bridge receives `99e18` tokens (1% fee deducted by the token).
6. Source bridge emits `RequestValueTransfer(..., valueOrTokenId=100e18, ...)`.
7. Go relay reads `valueOrTokenId = 100e18` and calls `handleERC20Transfer(..., 100e18, ...)` on the counterpart bridge.
8. Counterpart bridge releases `100e18` tokens to the attacker's `_to` address.
9. Net deficit per transfer: `1e18` tokens on the counterpart bridge.
10. Repeat until counterpart bridge reserves are exhausted.
