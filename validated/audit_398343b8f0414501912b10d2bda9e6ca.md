### Title
Unprivileged actor can permanently freeze a market by driving `borrow_index × scaled` past the `i128` ceiling before `MAX_BORROW_INDEX_RAY` engages — ([File: common/src/rates/scaling.rs])

### Summary
The MariaDB report is an assertion-failure → crash class bug: a reachable internal invariant panic aborts operation. The direct analog in XOXNO Lending is the `i128` overflow panic inside `scaled_to_original` during interest accrual. Every mutating pool verb runs `global_sync` → `accrue_step` first, and `accrue_step` unscales `borrowed` and `supplied` through `scaled_to_original`, which panics with `GenericError::MathOverflow` when `scaled × index` exceeds `i128::MAX`. Because the value ceiling is hit while the borrow index is still far below `MAX_BORROW_INDEX_RAY`, the index cap never engages to stop accrual — the panic is permanent. A single unprivileged address can place the market on this trajectory by supplying and borrowing very large amounts via `controller.supply` / `controller.borrow`, after which no one can ever repay, withdraw, liquidate, or sync that market again.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-61` computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` and the same for supply; `scaled_to_original` in `common/src/rates/scaling.rs:14-16` is `scaled.mul(env, index)`, which routes through `mul_div` in `common/src/math/fp_core.rs` and panics on `i128` overflow even on the widened `I256` path (the quotient itself no longer fits `i128`). The only guard on index growth is `update_borrow_index`'s clamp at `MAX_BORROW_INDEX_RAY = 1e36` (`common/src/rates/index.rs:13-19`), which bounds the index but not the product `scaled × index`. For a whale-scale market (e.g., an 18-decimal token with ~1e27 units supplied, scaled ≈ 1e45 RAY-value), the product overflows when the index reaches roughly 170× — long before the 1e36 cap. The pool's mutating path calls `accrue_step` from `accrue_chunk` in `contracts/pool/src/interest.rs:39-53`, and `global_sync` (interest.rs:20-33) runs at the top of every operation. Since the panic aborts the transaction before any state is written, `last_timestamp` never advances and the same overflow re-fires on every subsequent call — the panic is not a one-time revert but a terminal state.

The repo's own test harness proves this end-to-end: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361` builds a market via unprivileged `supply`/`borrow`, advances time, and observes `update_indexes`, `withdraw`, and `repay` all reverting with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — with the comment "the index cap did not engage before the value overflow" and "the bound in docs/reference/formulas.md is wrong", confirming the freeze is reachable earlier than the documented numeric bound implies.

### Impact Explanation
Permanent freezing of all user funds in the affected market: once `scaled × index` crosses `i128::MAX`, every entrypoint that touches the market — `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, `flash_loan`, `update_indexes`, `claim_revenue`, `recapitalize` — reverts in `global_sync` before doing any work. Suppliers' principal and accrued yield and the book's cash become permanently unrecoverable; there is no admin path to rewind the index. This matches the accepted "permanent freezing of funds" impact class.

### Likelihood Explanation
An unprivileged attacker seeds the condition with `controller.supply(market, huge_amount)` and `controller.borrow(...)` (both unpermissioned entrypoints), pushing `borrowed`/`supplied` scaled values high enough that index growth of ~170× overflows. Reaching 170× at sustained ~98% utilization on a steep rate curve takes years of elapsed time (the harness test loops `advance_time(YEAR_SECS)` until failure), so the exploit requires either a high-decimals/high-supply token market, patient capital, or a market that organically grows large — but once the state exists, the freeze is unconditional and needs no further attacker action. Medium likelihood, High-impact outcome → overall Medium-to-High; reported as High given the irreversibility and the confirmed divergence from the documented safety bound.

### Recommendation
Apply saturating math in `scaled_to_original` (or in `accrue_step`'s utilization inputs) so that overflowing unscale results saturate at `i128::MAX` rather than panicking, mirroring the existing `mul_div_floor_saturating` / `calculate_scaled_cap` fail-open pattern in `common/src/rates/scaling.rs:26-33`. Alternatively, clamp `borrow_index`/`supply_index` to `min(index, i128::MAX / scaled)` before unscaling, or lower `MAX_BORROW_INDEX_RAY` to a bound provably safe for the maximum reachable scaled supply, so the index cap always engages before the value ceiling.

### Proof of Concept
Already encoded in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);             // ~98% utilization

// advance years; update_indexes eventually fails
assert_contract_error(Err(failure), errors::MATH_OVERFLOW);
assert!(book(&t, "BIG18").borrow_index < MAX_BORROW_INDEX_RAY);

// market is permanently frozen:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `controller.supply`/`borrow` → pool op → `global_sync` (`contracts/pool/src/interest.rs:20`) → `accrue_chunk` → `accrue_step` (`common/src/rates/simulate.rs:60-61`) → `scaled_to_original` (`common/src/rates/scaling.rs:14-16`) → `fp_core::mul_div` panic when `scaled × index > i128::MAX`.
