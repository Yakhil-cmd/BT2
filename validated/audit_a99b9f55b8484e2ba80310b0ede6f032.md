### Title
`pull_request` webhook signature is verified against `repository.owner.login`, but the target `ReviewStack` is looked up by the independently-attacker-controlled `repository.full_name`, letting a no-secret organization's payload archive another repository's stack - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification via `repository.owner.login` [1](#0-0)  while `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's config has no `webhook_secret` [2](#0-1) . `ClosedHandler`/`ReviewStackAdapter` then resolve the affected repository/stack purely from the separate, independently-set `repository.full_name` field [3](#0-2) [4](#0-3) . This decoupling lets an attacker who controls a no-secret organization forge a `pull_request` `closed` payload naming a victim repository, causing the victim's `ReviewStack` to be archived without any valid signature over that org's secret.

### Finding Description
The broken binding claimed is: **the organization/repo whose secret authenticates a webhook request MUST equal the organization/repo whose records are mutated by that request.** i.e. `repository_owner_used_for_HMAC == repository_used_for_data_mutation`.

Tracing the code:
1. `Shipit::WebhooksController#verify_signature` reads `repository_owner` from `params.dig('repository','owner','login')` and looks up `Shipit.github(organization: repository_owner)` [1](#0-0) [5](#0-4) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` if `@webhook_secret` (from that org's config) is blank — no HMAC is computed or checked at all [6](#0-5) . The fixture `test/dummy/config/secrets_double_github_app.yml` demonstrates this exact configuration shape: multiple orgs (`OrgOne`, `OrgTwo`) each with `webhook_secret:` left nil [7](#0-6) .
3. After `verify_signature` passes, `WebhooksController#create` dispatches the full raw JSON body — including `repository.full_name`, entirely attacker-supplied and never re-validated against `repository.owner.login` — to the handlers [8](#0-7) .
4. `Shipit::Webhooks::Handlers::PullRequest::ClosedHandler#repository` resolves the target `Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , and `#process` calls `review_stack.archive!` when `params.action == "closed"` [9](#0-8) .
5. `ReviewStackAdapter#archive!` looks up the `ReviewStack` by `environment` (`"pr#{params.number}"`) scoped to `repository.review_stacks`, and calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, `stack.archive!(user)` [10](#0-9) .

Because step 1's authentication key (`repository.owner.login`) and step 4's data-selection key (`repository.full_name`) are two distinct JSON fields under full attacker control in the same forged body, the attacker can set `repository.owner.login` to an org they registered in Shipit with no `webhook_secret` (satisfying the bypass in step 2), while setting `repository.full_name` to `"victim-org/victim-repo"` to target any tracked stack, including one with `blocking_statuses` configured (relevant for the deploy-gating amplification referenced in the question, via `blocked?` on commits/stacks affected by status forcing). `respond_to_pull_request_closed?` and the `ExplicitParameters` schema in `ClosedHandler` do not validate any relationship between `repository.owner.login` and `repository.full_name`, so nothing prevents this divergence [11](#0-10) .

Existing tests confirm `repository_owner` used for verification is taken independently: `test/controllers/webhooks_controller_test.rb`'s `"verifies webhook signature"` test stubs `Shipit.github(organization: 'shopify')` based on `repository.owner.login` only, with no cross-check against `full_name` [12](#0-11) .

### Impact Explanation
An attacker who registers/controls a GitHub organization that a Shipit operator has configured in `secrets.github` with a blank `webhook_secret` (this misconfiguration is explicitly represented in `test/dummy/config/secrets_double_github_app.yml`, and is a realistic multi-tenant configuration mistake, not an engine invariant that's enforced) can send unauthenticated `POST /webhooks` requests that pass `verify_signature` for free. By setting `repository.full_name` to any other tracked repository, the attacker can trigger `ClosedHandler`, causing `ReviewStack#archive!`, `remove_from_provisioning_queue`, and `deprovision` to run against a victim's `ReviewStack`/PR-numbered environment they never authenticated for. This is a cross-tenant/cross-repository state mutation: one repository's (attacker-controlled, secret-less org) payload writes another repository's `ReviewStack` records and de-provisions/archives it, matching the Critical impact category "a payload for one repository mutating another's stack." The action is repeatable against any `pr#<number>` environment/stack the attacker can guess or enumerate, for any repository tracked by the same Shipit instance.

### Likelihood Explanation
Preconditions: the Shipit operator must have configured at least one GitHub organization/app entry without a `webhook_secret` (a documented, testable configuration state, not a rare edge case — the multi-org config file in the test fixtures explicitly models this). No GitHub session, API token, or Shipit credential is required by the attacker; they only need to know or guess the victim repository's `full_name` and a PR number, both of which are typically public/predictable. Cost is a single crafted HTTP POST, fully repeatable and scriptable.

### Recommendation
Bind webhook authentication to the same repository identity used for data mutation. Concretely:
- Reject payloads if `params.dig('repository','full_name')`'s owner does not match `repository.owner.login` used to select the signing `GitHubApp`.
- Fail closed (not open) when `webhook_secret` is blank in `GitHubApp#verify_webhook_signature`, or require `webhook_secret` to be present for every configured organization (config-time validation), rather than treating "no secret configured" as "always trusted."
- Alternatively, verify the signature using the org derived from `repository.full_name` rather than `repository.owner.login`, ensuring the two never diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "no-secret organization cannot archive another repository's review stack" do
  # Precondition: configure an org "attacker-org" with webhook_secret: nil,
  # distinct from the victim stack's org "shopify" (which may have a real secret).
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', { webhook_secret: nil, app_id: 1, installation_id: 1 })
  )

  victim_stack = shipit_review_stacks(:blocking_statuses_configured) # has blocking_statuses configured
  pr_number = victim_stack.pull_request.number

  forged_payload = {
    action: 'closed',
    number: pr_number,
    pull_request: { id: 1, number: pr_number, url: 'x', title: 'x', state: 'closed',
                     additions: 1, deletions: 1, head: { sha: 'a'*40, ref: 'feature' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { full_name: victim_stack.repository.full_name }, # victim repo, NOT attacker-org
    repository_owner_login_field: nil, # sent separately below
    sender: { login: 'attacker' }
  }
  forged_payload[:repository][:owner] = { login: 'attacker-org' } # mismatched owner used only for auth

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # irrelevant/garbage - never checked

  post :create, body: forged_payload.to_json, as: :json

  assert_response :ok
  # Binding check: verification org ("attacker-org", no secret) != data-mutation org ("shopify"/victim)
  assert victim_stack.reload.archived?, "victim stack was archived by a payload not authenticated for its repo"
end
```
Both sides of the invariant equality (`auth_org == data_org`) diverge (`attacker-org` vs the victim's real org) yet the request still succeeds and mutates the victim's `ReviewStack`, confirming the vulnerability as described.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
