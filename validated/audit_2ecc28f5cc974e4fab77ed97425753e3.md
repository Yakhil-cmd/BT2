## Proof-of-Concept Numbers (Corrected)

The question's specific numbers are arithmetically wrong. With `qualifiedLen=3` and `committeeSize=4`:

```
F = ceil(qualifiedLen/3) - 1 = ceil(3/3) - 1 = 0   →   2f+1 = 1
```

That quorum of 1 is trivially met and does not demonstrate the bug. A working scenario requires `qualifiedLen ≥ 4`:

## Attack Path

The entry point is P2P block propagation / downloader sync. When an honest node calls `validateHeader → verifySeals` on a received block, the corrupted `signerSet` is used. The live consensus engine (`getRoundCommitteeState`) correctly rejects demoted validators' COMMIT messages during block production, but `verifySeals` during import does not apply the same filter. A malicious qualified proposer can:

1. Collect out-of-band committed-seal signatures from demoted council members (who still hold valid keys and are still in the council).
2. Embed those signatures in the block header's `CommittedSeal` field.
3. Broadcast the block; honest nodes' `verifySeals` counts the demoted seal(s) toward the quorum and accepts the block.

This does not require majority-validator collusion — it requires one malicious qualified proposer plus cooperation from demoted validators (who remain council members with live keys).

## Verdict

The bug is real and confirmed in production code. The `signerSet` on line 300 should be `qualifiedSet` (already computed on line 289), not the full council. Using the council allows demoted validators' seals to satisfy the quorum that is sized for qualified validators only, enabling a block with sub-quorum qualified signatures to pass seal verification on honest nodes.

### Title
Demoted-validator seal counted toward pre-permissionless 2f+1 quorum due to `signerSet` being overwritten with full council — (`blockchain/block_validator.go`)

### Summary
In `verifySeals`, the pre-permissionless branch initialises `signerSet` to `qualifiedSet` but immediately overwrites it with the full council. Because `countValidCommittedSeals` accepts any address present in `signerSet`, a demoted validator's committed seal increments `validSeal`. The quorum threshold is computed from `qualifiedLen` (qualified-only), so the two sides of the comparison are mismatched: the count is inflated by demoted seals while the threshold assumes only qualified signers.

### Finding Description [1](#0-0) 

Line 294 correctly initialises `signerSet` to `qualifiedSet`, but lines 295–301 unconditionally overwrite it with `valset.NewAddressSet(council)` whenever `!rules.IsPermissionless` — which is always true in the pre-permissionless branch. The council is a strict superset of the qualified set; it includes demoted validators. [2](#0-1) 

`countValidCommittedSeals` returns an error only when an address is absent from `signerSet`. A demoted validator present in the council passes the `Remove` check and increments `validSeal`. [3](#0-2) 

The quorum threshold `2*F+1` is derived from `qualifiedLen`, but `validSeal` was counted against the broader council. The mismatch means one or more demoted-validator seals can substitute for missing qualified-validator seals.

The `IstanbulSealer.F` function confirms the threshold is purely a function of `qualifiedLen` and `committeeSize`: [4](#0-3) 

The council/qualified distinction is well-established in the valset module: [5](#0-4) 

### Impact Explanation
An honest node importing a block via P2P sync calls `validateHeader → verifySeals`. If the block's committed seals include a demoted validator's signature, `verifySeals` counts it toward the quorum and returns `nil`. A block that was signed by fewer qualified validators than the 2f+1 threshold is accepted as valid, constituting **invalid block acceptance** and potential **consensus divergence** between nodes that apply the correct check and those that do not.

### Likelihood Explanation
Demoted validators remain council members with live signing keys. A malicious qualified proposer can solicit out-of-band committed-seal signatures from demoted council members and embed them in a crafted block header. No cryptographic break is required; the proposer only needs the cooperation of one or more demoted validators. The attack is delivered through the standard P2P block-propagation path, which is fully public.

### Recommendation
Replace the `signerSet` assignment on line 300 with `qualifiedSet` (already computed on line 289). The council fetch and the overwrite on lines 296–300 should be removed entirely:


Committed seals must only be accepted from qualified validators; demoted validators must not contribute to the quorum regardless of their council membership.

### Proof of Concept
Setup (corrected numbers that actually produce F=1, 2f+1=3):

- Council = [A, B, C, D, E, X]; X is demoted (below minimum stake)
- Qualified = [A, B, C, D, E]; `qualifiedLen = 5`
- Governance `committeeSize = 5`
- `F = ceil(5/3)−1 = 1`; required quorum = `2f+1 = 3`
- Header committers = [A, B, X] — only 2 qualified validators signed

Execution through `verifySeals`:
1. `qualifiedSet = {A,B,C,D,E}`; author A ∈ qualifiedSet → passes.
2. `signerSet` initialised to `{A,B,C,D,E}`, then **overwritten** with council `{A,B,C,D,E,X}`.
3. `countValidCommittedSeals([A,B,X], {A,B,C,D,E,X})` → removes A (ok), B (ok), X (ok, X ∈ council) → returns `validSeal=3, err=nil`.
4. `3 >= 2*1+1 = 3` → **`verifySeals` returns nil**; block accepted.

Expected behaviour: X's seal should be rejected (X ∉ qualifiedSet), `validSeal` should be 2, and `2 < 3` should return `ErrInvalidCommittedSeals`.
