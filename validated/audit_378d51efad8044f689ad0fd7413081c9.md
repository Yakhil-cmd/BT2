### Title
Stability advancement runs outside the "write" mutex, allowing concurrent unit writes to race with in-memory/DB stabilization state - ([File: main_chain.js])

### Summary
`determineIfStableInLaterUnitsAndUpdateStableMcFlag` can advance the stability point (calling `stabilizeMci`/`markMcIndexStable`) while holding only the `["handleJoint"]` mutex, not the `["write"]` mutex that normally serializes all unit persistence in `writer.saveJoint`. This mirrors the f2fs CVE-2024-27034 pattern: a multi-step metadata update (there: cluster block writes; here: `is_stable`, `sequence`, `is_unique` flags and the `assocStableUnits`/`assocUnstableUnits` in-memory caches) is allowed to proceed without holding the lock that guarantees atomicity with respect to concurrent writers, risking inconsistent/corrupted state.

### Finding Description
Normal unit persistence (`writer.saveJoint`) acquires the global `["write"]` mutex before mutating unit state, `is_stable`, `sequence`, `is_unique`, and the storage caches, and only releases it once the entire write (including any stabilization it triggers via `main_chain.advanceMcStability`) is fully committed: [1](#0-0) [2](#0-1) [3](#0-2) 

However, `determineIfStableInLaterUnitsAndUpdateStableMcFlag` (invoked from `validateParents` during unit validation, which itself is protected only by the author-address mutex, not `["write"]`) takes only the `["handleJoint"]` lock before calling `stabilizeMci`, which opens its own DB connection, updates `is_stable`, unwinds nonserial/final-bad sequencing, and toggles `is_unique` on inputs — all the data that double-spend protection and consensus stability rely on: [4](#0-3) [5](#0-4) [6](#0-5) 

The project itself documents the race explicitly in `network.js`: "If the mci became stable in `determineIfStableInLaterUnitsAndUpdateStableMcFlag` (rare), write lock is released before the validation commits, so we might not see this mci as stable yet": [7](#0-6) 

This is functionally the same bug class as CVE-2024-27034: a code path that mutates shared, consistency-critical metadata is not covered by the lock (`cp_rwsem` there, `["write"]` mutex here) that other writers rely on for atomicity, so a concurrent `saveJoint` (running under `["write"]`) can read or write `storage.assocStableUnits`/`assocUnstableUnits`/`is_unique` while `markMcIndexStable` is mid-flight on a separate, unsynchronized connection, and vice versa.

### Impact Explanation
`markMcIndexStable` mutates `is_unique` on `inputs` (the flag that prevents a coin from being spent twice) and flips units between `good`/`final-bad` sequence based on the current snapshot of `storage.assocStableUnits`. If a concurrent `saveJoint` write (holding only `["write"]`, unaware that `["handleJoint"]`-protected stabilization is concurrently mutating the same caches/tables) reads a stale snapshot of stability/sequence data, it can persist unit properties that disagree with the concurrently-committed stabilization results. This can lead to nodes disagreeing on unit validity/stability, or a stale `is_unique`/nonserial determination — the exact double-spend/state-corruption class this scan is required to flag. The bug is triggerable by any unprivileged unit poster whose unit happens to satisfy the "already stable in later units but not yet marked stable in db" condition, which is a naturally occurring race in normal DAG operation, not something requiring a malicious peer.

### Likelihood Explanation
The condition is explicitly called "rare" in code comments, since it requires late/asynchronous confirmation of stability via `determineIfStableInLaterUnits` racing against an in-flight `saveJoint`. However, it does not require any privileged position — a normal unit sent by any node can trigger `determineIfStableInLaterUnitsAndUpdateStableMcFlag` to run concurrently with another node's or the same node's write pipeline, and high transaction throughput increases collision probability.

### Recommendation
Ensure `determineIfStableInLaterUnitsAndUpdateStableMcFlag`/`stabilizeMci` acquire the `["write"]` mutex (or otherwise fully serialize with `writer.saveJoint`) before mutating `is_stable`, `sequence`, `is_unique`, or the `assocStableUnits`/`assocUnstableUnits` caches, matching the upstream f2fs fix of covering the whole metadata-critical section with the lock that other writers depend on, rather than relying on the narrower `["handleJoint"]` lock alone.

### Proof of Concept
Not independently reproducible from static analysis alone — the race is timing-dependent (requires a unit whose stability is confirmed by `determineIfStableInLaterUnits` from later units while `saveJoint` for another unit is concurrently in flight) and I could not execute or step through the runtime to confirm an observable corrupted end-state; this is noted as uncertain and would need dynamic/concurrency testing to fully validate exploitability.

async function stabilizeMci(mci) {
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const batch = kvstore.batch();
	const count_aa_triggers = await markMcIndexStable(conn, batch, mci);
	await util.promisify(batch.write.bind(batch))({ sync: true });
	await conn.query("COMMIT");
	conn.release();
	if (count_aa_triggers > 0) {
		console.log(`executing ${count_aa_triggers} AA triggers after stabilizing MCI ${mci}`);
		// every trigger takes its own db connection
		const aa_composer = require("./aa_composer.js");
		await aa_composer.handleAATriggers();

	if (mci >= constants.v4UpgradeMci) {
		console.log(`updating tps fees after stabilizing MCI ${mci}`);
		// get a new connection to write tps fees
		const conn = await db.takeConnectionFromPool();
		await conn.query("BEGIN");
		await storage.updateTpsFees(conn, [mci]);
		await conn.query("COMMIT");
		conn.release();
	}
}
