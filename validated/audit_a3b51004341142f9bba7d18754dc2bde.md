### Title
Per-Block Index Cache Serves Stale Debt/Liquidity Indexes to Other Users After Bad-Debt Socialization - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s liquidity/debt index cache is keyed only by `{ timestamp: stacks-block-time, aid }`, not by caller or transaction. Any account whose operation runs `accrue-and-cache` first in a block "primes" the cached index/lindex for that asset for the rest of the block. If a later transaction in the same block performs `socialize-debt` on a vault (writing off bad debt onto suppliers, which changes the vault's real `index`/`lindex` outside the normal per-block `accrue` path), every subsequent unrelated user transaction in that same block that touches the same asset will still read the pre-socialization value from `index-cache`, because the cache lookup is a hit and skips calling the vault again.

### Finding Description
The cache is defined and consumed as: [1](#0-0) 

`accrue-and-cache` unconditionally trusts an existing entry for `{ stacks-block-time, aid }` and returns it without re-querying the vault: [1](#0-0) 

`borrow`, `repay`, and `liquidate` all rely on this shared cache to resolve the index used for both scaled-debt math and USD notional valuation: [2](#0-1) [3](#0-2) [4](#0-3) 

The docs explicitly describe this as a deliberate optimization and claim it "eliminates stale data risks" solely because a new block produces a new timestamp: [5](#0-4) 

That reasoning only holds if the vault's `index`/`lindex` cannot change again within the same block once accrued. Normal `accrue()` is idempotent within a block because `next-index`/`next-liquidity-index` compute a `time-delta` of `0` on the second call and return the same value: [6](#0-5) 

However, vaults expose a distinct `socialize-debt` entry point (present in every vault: `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) that is invoked from the market's liquidation flow to write off uncovered debt onto the remaining suppliers, which is a distinct state mutation from the timestamp-gated `accrue()` path: [7](#0-6) 

Because the market's `index-cache` for that asset was already primed earlier in the same block (by some unrelated user's borrow/repay/deposit), any transaction that runs after the socialization but within the same block will hit the stale cache entry instead of observing the vault's updated post-write-off state.

### Impact Explanation
Attacker/victim relationship: the attacker is any account that transacts (borrow/repay/collateral operation) on asset X earlier in a block, unknowingly or deliberately priming `index-cache-` for X; the triggering event is a liquidation elsewhere in the same block that calls `socialize-debt` on vault X. The victims are all other unrelated users whose transactions land later in the same block and touch asset X (or its zToken) — they get valued, borrow-capacity-checked, and liquidated against the stale pre-socialization index rather than the true post-loss index. This is exactly the "shared index/cache primed by one caller and consumed by another" class: one principal's ordinary transaction determines the pricing basis used to evaluate a second, unrelated principal's position after a loss event has already been applied on-chain in the same block. Consequences include third parties borrowing against overstated collateral value, being liquidated with incorrect (higher or lower) collateral/debt notional than the true post-write-off state, and zToken holders receiving mispriced exchange rates for deposit/redeem — a temporary freezing/mispricing of funds within that block, landing in the "temporary freezing of funds" impact class.

### Likelihood Explanation
The condition requires only two ordinary, unprivileged operations landing in the same block: (1) any user transaction that touches asset X and populates `index-cache-` for the current `stacks-block-time`, and (2) a liquidation later in the same block that triggers `socialize-debt` on the same asset's vault. Both are routine protocol operations (borrow/repay/deposit and liquidation of an underwater position), so this can occur without any special privilege, and can be intentionally engineered by an attacker who front-runs/back-runs within the block using normal mempool ordering.

### Recommendation
Invalidate or bypass the `index-cache-` entry for an asset whenever `socialize-debt` (or any non-`accrue` state mutation to `index`/`lindex`) is executed within the same block, e.g., by having the market re-query the vault after any socialization call, or by keying/versioning the cache on a monotonically increasing per-asset state-change counter rather than solely on `stacks-block-time`.

### Proof of Concept
1. Block N begins. User A calls `borrow` on asset X; `accrue-and-cache` populates `index-cache- { timestamp: T, aid: X }` with the current index/lindex (mainnet/contracts/market/v0-4-market.clar:245-257, 1250-1256).
2. Still in block N, a liquidator calls `liquidate` on an underwater borrower whose debt in asset X cannot be fully covered by seized collateral; the market invokes `vault-socialize-debt` on vault X, which directly writes off the bad debt, changing the vault's real `index`/`lindex` outside the timestamp-gated `accrue` path.
3. Still in block N, User B calls `repay` or another `borrow` on asset X. `accrue-and-cache` finds the cache entry for `{T, X}` already populated (from step 1) and returns it directly without re-querying the vault, so User B's transaction is priced/settled using the pre-socialization index instead of the true post-write-off index (mainnet/contracts/market/v0-4-market.clar:245-257, 1327-1336).
4. User B's resulting debt/collateral valuation and liquidation eligibility differ from what the actual, updated vault state would produce, and this discrepancy persists for every remaining transaction on asset X until the block ends.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
