### Title
Webhook signature is verified against the organization derived from the payload, but handlers act on an unrelated `repository.full_name` field never covered by that authorization check - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken straight from the attacker-controlled JSON body. Once the signature validates, every registered `Handler` (e.g. `PushHandler`, `CheckSuiteHandler`) instead resolves the target `Stack`/`Repository` using a *different* field from the same body: `repository.full_name`. Nothing binds these two fields together, so an actor who legitimately administers the GitHub App for organization A (and therefore knows A's `webhook_secret`) can forge a payload where `repository.owner.login` = "A" (to pass signature verification) while `repository.full_name` = "B/victim-repo" (to target organization B's stacks).

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, which only checks that the HMAC over the *entire raw body* matches the secret configured for that organization: [3](#0-2) 

Because the attacker constructs the raw body themselves, they can freely set `repository.owner.login` to their own organization (whose secret they know) while independently setting `repository.full_name` to any string. The signature only proves "this body was produced by someone holding org A's secret" - it says nothing about which repository that body's `full_name` field refers to.

Every handler, however, resolves the actual database `Repository`/`Stack` to act on using `full_name`, not `owner.login`: [4](#0-3) [5](#0-4) 

For example, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack matching the branch, on whatever repository `full_name` names: [6](#0-5) 

This is exactly the "organization that authenticated versus the repository that is written" binding: the equality that should hold is `repository.owner.login == repository.full_name.split('/').first`, but the code never enforces it. The signature check authenticates on `owner.login`; the write path acts on `full_name`.

### Impact Explanation
This is only exploitable in a multi-organization Shipit deployment (as shown by `config/secrets.development.shopify.yml`, which configures multiple orgs each with their own `webhook_secret`, `app_id`, `installation_id`). An entity that has legitimate control of one configured organization's GitHub App (and thus its `webhook_secret`) - but no privileges over another organization's repository or Shipit stacks - can forge webhook deliveries that are accepted as authentic for that other organization's repositories. Depending on the handler invoked:
- `push` forges triggering `Stack#sync_github`, which resyncs commits and, for stacks with `continuous_deployment` enabled, can trigger an unauthorized deploy.
- `check_suite` forges triggering `schedule_refresh_check_runs!`, corrupting CI/CD gating state used to unblock merges/deploys of a stack the attacker does not own.

This crosses the "unauthorized deploy" / cross-repository-write impact bar from the rules, since it lets a party who legitimately controls org A's webhook credentials manipulate org B's stack state and potentially trigger deploys.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the Shipit instance to host more than one organization (a supported and documented configuration) and requires the attacker to legitimately control the `webhook_secret` for at least one of the configured organizations - a bar lower than compromising the target organization or obtaining an `ApiClient` token, since it doesn't require any access to the target org's resources at all.

### Recommendation
After computing `repository_owner` and verifying the signature, re-derive the organization from `repository.full_name` (or `organization.login`) as well and reject the request (422) unless they match. Alternatively, have handlers resolve `Repository` scoped to the authenticated organization instead of trusting `full_name` in isolation, e.g. `Repository.from_github_repo_name(full_name)` should additionally assert `repository.owner == repository_owner_used_for_signature`.

### Proof of Concept
1. Assume Shipit is configured (per `config/secrets.development.shopify.yml`) with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App `webhook_secret`.
2. The attacker (who legitimately administers `attacker-org`'s GitHub App and therefore knows its `webhook_secret`) crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>`.
4. POST to `/github/webhooks` (the engine's `WebhooksController#create`) with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and the signature validates successfully.
6. `PushHandler` resolves stacks via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, and calls `sync_github`/potential deploy trigger on `victim-org`'s stack - despite the attacker having no credentials or access tied to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
