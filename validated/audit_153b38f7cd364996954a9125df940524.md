### Title
Sui→EVM bridge burns tokens irreversibly with no cancellation/refund path if destination-side unlock never completes - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
`send_token`/`send_token_v2` immediately burn/escrow the user's Sui coin via `inner.treasury.burn(token)` and create a pending `BridgeRecord` that can only be completed off-chain by the bridge committee approving the message and the EVM `SuiBridge.sol` contract successfully unlocking funds on Ethereum [1](#0-0) . There is no `cancel`/`refund` entry point anywhere in the bridge Move package that lets the depositing user reclaim their burned tokens on Sui if the destination-chain leg never completes [2](#0-1) .

### Finding Description
This is the direct analog of the Linea report: a two-transaction bridging flow where step 1 (source-chain lock/burn) is irreversible and unconditionally committed, while step 2 (destination-chain completion) depends on off-chain infrastructure (`SuiSyncer`/`BridgeOrchestrator`/`BridgeAuthorityAggregator` and the EVM contract call) that can fail or stall indefinitely.

In the Sui→Ethereum direction:
1. User calls `send_token`, which burns the coin from the treasury and pushes a `BridgeRecord{verified_signatures: none, claimed: false}` keyed by `message.key()` [2](#0-1) .
2. Completion requires: (a) the bridge committee to produce a quorum of signatures, (b) `approve_token_transfer` to attach them on Sui, and (c) `SuiBridge.transferBridgedTokensWithSignatures` to execute successfully on Ethereum (per `bridge/SUI_NATIVE_BRIDGE_PRIMER.md` lines 581–599, out of this repo's Move scope but describing the same flow this repo implements).
3. Nowhere in `bridge.move`, `limiter.move`, `treasury.move`, or `committee.move` (searched for `refund`/`cancel`, zero matches) is there a mechanism for the original sender to reclaim their locked value on Sui if the EVM-side leg permanently reverts (e.g., a broken/blocked recipient contract on the EVM side, a bug in the executor, or the committee never reaching quorum for that particular message) [3](#0-2) .

The `EInvariantSuiInitializedTokenTransferShouldNotBeClaimed` assertion in `approve_token_transfer` even encodes the assumption that a Sui-originated record can only ever be approved, never independently reversed [4](#0-3) . Unlike the Ethereum→Sui direction, where a stuck claim can simply be retried once the limiter window resets (`TokenTransferLimitExceed` allows indefinite retry, `crates/sui-framework/packages/bridge/sources/bridge.move` lines 583–598), the Sui→Ethereum direction has no such retry-to-success guarantee purely on-chain, because completion depends on an external chain's contract execution that Move code cannot force to succeed.

### Impact Explanation
If the destination-side (EVM) unlock permanently fails or the off-chain committee/orchestrator infrastructure never produces a valid approval for a specific pending Sui-originated `BridgeRecord`, the depositor's tokens are burned on Sui with no path to recovery — this is a **permanent fund lock**, which is an explicitly allowed High/Medium impact category under the stated scope. This mirrors the Linea root cause precisely: an unprivileged user's funds become unrecoverable purely due to a stuck/failing second-leg transaction, with no cancellation primitive on the source chain.

### Likelihood Explanation
This does not require a malicious validator, bridge authority, or governance quorum — it requires only that the destination-chain completion path fail or stall for any of the many realistic non-malicious reasons already contemplated by the design (equivalent EVM-side contract call reverting, an authority-aggregator bug, a permanently paused destination bridge, or committee inability to reach quorum for that message due to key rotation/downtream issues). Because `approve_token_transfer`/EVM unlock are entirely off-chain-triggered and irreversible burn happens synchronously in `send_token`, likelihood is comparable to the original Linea scenario: any sustained failure of the second leg — not attacker-induced — produces the loss.

### Recommendation
Add a governance- or time-based cancellation/refund path: e.g., allow the original sender (or committee via signed message) to reclaim the escrowed/burned value from a Sui-originated `BridgeRecord` that has remained unapproved/unclaimed after a defined timeout, mirroring the 48h "bypass limiter" pattern already used for V2 messages [5](#0-4) . This would need a corresponding "mint back" path in `treasury.move` since the coin has already been burned, and must be carefully designed to avoid double-completion if the destination-side action later succeeds.

### Proof of Concept
Not directly exploitable/demonstrable as a state-corruption PoC in this Move package alone — it is a systemic design gap: `send_token` → burn (irreversible, `bridge.move` lines 218–256) with completion contingent on external, unmodifiable-by-Move infrastructure, and no `refund`/`cancel` function exists in the package (confirmed via repository-wide search for `refund`/`cancel` in `crates/sui-framework/packages/bridge/**`, zero matches). A concrete PoC would require simulating the off-chain orchestrator/EVM leg failing permanently, which is outside the scope of the Move test harness (`bridge_env.move`, `bridge_txns.move`) available in this repository.

// Create bridge request to send token to other chain, the request will be in
// pending state until approved
public fun send_token<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    ctx: &mut TxContext,
) {
    let inner = load_inner_mut(bridge);

    let bridge_seq_num = inner.get_current_seq_num_and_increment(message_types::token());
    let token_id = inner.treasury.token_id<T>();
    let token_amount = token.balance().value();
    assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
    assert!(token_amount > 0, ETokenValueIsZero);

    // create bridge message
    let message = message::create_token_bridge_message(
        inner.chain_id,
        bridge_seq_num,
        address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_id,
        token_amount,
    );

    inner.send_token_internal(target_chain, token, message);

    // emit event
    event::emit(TokenDepositedEvent {
        seq_num: bridge_seq_num,
        source_chain: inner.chain_id,
        sender_address: address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_type: token_id,
        amount: token_amount,
    });
}

// Record bridge message approvals in Sui, called by the bridge client
// If already approved, return early instead of aborting.
public fun approve_token_transfer(
    bridge: &mut Bridge,
    message: BridgeMessage,
    signatures: vector<vector<u8>>,
) {
    let inner = load_inner_mut(bridge);
    assert!(!inner.paused, EBridgeUnavailable);
    // verify signatures
    inner.committee.verify_signatures(message, signatures);

    assert!(message.message_type() == message_types::token(), EMustBeTokenMessage);
    assert!(
        message.message_version() <= message::token_transfer_message_version(),
        EUnexpectedMessageVersion,
    );
    let token_payload = if (message.message_version() == 2) {
        message.extract_token_bridge_payload_v2().to_token_payload_v1()
    } else {
        message.extract_token_bridge_payload()
    };
    let target_chain = token_payload.token_target_chain();
    assert!(
        message.source_chain() == inner.chain_id || target_chain == inner.chain_id,
        EUnexpectedChainID,
    );

    let message_key = message.key();
    // retrieve pending message if source chain is Sui, the initial message
    // must exist on chain
    if (message.source_chain() == inner.chain_id) {
        let record = &mut inner.token_transfer_records[message_key];

        assert!(record.message == message, EMalformedMessageError);
        assert!(!record.claimed, EInvariantSuiInitializedTokenTransferShouldNotBeClaimed);

        // If record already has verified signatures, it means the message has been approved
        // Then we exit early.
        if (record.verified_signatures.is_some()) {
            event::emit(TokenTransferAlreadyApproved { message_key });
            return
        };
        // Store approval
        record.verified_signatures = option::some(signatures)
    } else {
        // At this point, if this message is in token_transfer_records, we know
        // it's already approved because we only add a message to token_transfer_records
        // after verifying the signatures
        if (inner.token_transfer_records.contains(message_key)) {
            event::emit(TokenTransferAlreadyApproved { message_key });
            return
        };
        // Store message and approval
        inner
            .token_transfer_records
            .push_back(
                message_key,
                BridgeRecord {
                    message,
                    verified_signatures: option::some(signatures),
                    claimed: false,
                },
            );
    };

    event::emit(TokenTransferApproved { message_key });
}

fun send_token_internal<T>(
    inner: &mut BridgeInner,
    target_chain: u8,
    token: Coin<T>,
    message: BridgeMessage,
) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);

    // burn / escrow token, unsupported coins will fail in this step
    inner.treasury.burn(token);

    // Store pending bridge request
    inner
        .token_transfer_records
        .push_back(
            message.key(),
            BridgeRecord {
                message,
                verified_signatures: option::none(),
                claimed: false,
            },
        );
}
