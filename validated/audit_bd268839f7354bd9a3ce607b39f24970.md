### Title
Webhook signature verification keys off `repository.owner.login` while every `pull_request` handler mutates state keyed by the untrusted `repository.full_name` — cross-org stack mutation across the entire handler dispatch loop - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App / HMAC secret to validate the payload using `repository_owner` (`params.dig('repository','owner','login')`), but `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` passes the *entire* raw, unvalidated `params` hash to every registered `pull_request` handler, each of which independently re-derives its target `Repository`/`Stack` from `params.repository.full_name`. Nothing in the request pipeline enforces that these two fields refer to the same organization, so a payload whose `repository.owner.login` matches an org the attacker can get "verified" against (e.g. an org configured with no `webhook_secret`) but whose `repository.full_name` points at a victim org's repo will pass `verify_signature` once and then have every handler in the `pull_request` list — `LabelCapturingHandler` and `LabeledHandler` alike — mutate the victim's stack in the same request.

### Finding Description
The broken binding, stated as an equality that the code never enforces:

`org_verified = Shipit.github(organization: params.dig('repository','owner','login') || params.dig('organization','login')).organization` (used inside `verify_signature`, [1](#0-0) )

must equal

`org_targeted = params.dig('repository','full_name').split('/').first` (used inside every `pull_request` handler via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, e.g. [2](#0-1)  and [3](#0-2) ).

Tracing the request:
1. `verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)` purely to gate the request — the *only* output used downstream is a boolean `verified`/HTTP status; the chosen `organization` value is discarded afterward. [4](#0-3) 
2. `verify_webhook_signature` short-circuits `return true unless webhook_secret`. [5](#0-4)  Every shipped example configuration (`config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`, `test/dummy/config/secrets_double_github_app.yml`) ships `webhook_secret: # nil`, i.e. the secret is explicitly documented as optional and typically unset. [6](#0-5) 
3. Once `verify_signature` passes (either because the chosen org has no `webhook_secret`, or because the attacker knows the secret for their own org), `create` re-parses the same raw body and dispatches it, unmodified, to every handler registered for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [7](#0-6) 
4. `Shipit::Webhooks.default_handlers['pull_request']` registers both `LabeledHandler` and `LabelCapturingHandler` (among others) for the same event. [8](#0-7) 
5. Each handler independently calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to resolve the repository/stack it will mutate — `LabelCapturingHandler#repository` and `#capture_labels` write PR labels onto `stack.pull_request`; `LabeledHandler#repository` and `#handle` call `stack.archive!`/`stack.unarchive!`. Neither handler checks `repository_owner` or the org used during signature verification at all. [9](#0-8) [10](#0-9) 

Attacker's exact request: a single unauthenticated `POST /webhooks` with header `X-Github-Event: pull_request`, an `X-Hub-Signature` value (irrelevant if the chosen org has no secret, or a correctly-computed HMAC using an org's secret the attacker legitimately knows for their own installation), and a JSON body where `repository.owner.login` names the org that gates verification, but `repository.full_name` is set to `"victim-org/victim-repo"` — a real repository already onboarded onto the target Shipit instance. Because `drop_unhandled_event`/`verify_signature`/`create` never cross-check these two fields, the single gate passes and both `LabelCapturingHandler` (rewrites `stack.pull_request.labels`) and `LabeledHandler` (calls `stack.archive!`/`stack.unarchive!`) act on the victim stack in one request.

Existing guards do not prevent this: `verify_signature` only rejects unknown org names via `GithubOrganizationUnknown` (`Shipit.github_app_config`) and bad signatures for orgs *that have* a secret configured — it never inspects or compares `repository.full_name`. `drop_unhandled_event` only checks that handlers exist for the event, not payload authenticity. `ExplicitParameters` schemas on the handlers (`requires :repository { requires :full_name, String }`) validate only *shape*, not that the value matches the verified organization. No model validation on `Repository`/`Stack` ties them back to the verifying org either.

### Impact Explanation
A single forged/mismatched webhook causes multiple independent handlers — label capture and archive/unarchive — to write to a victim organization's `Stack`/`PullRequest` records in one request, without the attacker needing any credential belonging to the victim org. This is a payload for one repository mutating another repository's/organization's stack, matching the Critical severity category explicitly listed in scope. The blast radius spans every `pull_request`-registered handler (currently 8, including provisioning-affecting `LabeledHandler`/`UnlabeledHandler` and label-writing `LabelCapturingHandler`), and is repeatable against any onboarded repository/stack the attacker can name in `full_name`, as often as desired.

### Likelihood Explanation
Preconditions: the Shipit instance must (a) have at least one configured GitHub org/app with no `webhook_secret` set (shown as the default/example configuration across the repo), or the attacker legitimately controls an org+secret registered in Shipit's multi-org config and merely mismatches `full_name`; and (b) the victim repository must already be a known/onboarded `Repository` in Shipit (discoverable, since these are typically public GitHub repos). No GitHub App private key, session, API token, or team membership is required — `WebhooksController` performs no authentication beyond the (bypassable) signature check. Cost to the attacker is a single crafted HTTP POST; the attack is fully repeatable and scriptable.

### Recommendation
In `verify_signature`, after establishing the verified organization, enforce that `params.dig('repository','full_name')&.split('/')&.first` (case-insensitively) equals the verified `repository_owner`/organization before allowing dispatch; reject (422) on mismatch. Additionally, consider requiring `webhook_secret` to be present for all configured orgs (fail closed rather than `return true unless webhook_secret`), and have each handler's `repository` resolution reject payloads whose `full_name` owner doesn't match the request's verified organization as defense in depth.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative addition)
test "cross-org payload lets ALL pull_request handlers mutate a victim stack in one request" do
  victim_stack = shipit_stacks(:shipit) # belongs to org "shopify", repo "shopify/shipit-engine"

  # Attacker-controlled org "attacker-org" has no webhook_secret configured (default/example config).
  request.headers['X-Github-Event'] = 'pull_request'

  payload = JSON.parse(payload(:pull_request_labeled))
  payload['repository']['owner']['login'] = 'attacker-org'      # gates verify_signature (no secret -> always verified)
  payload['repository']['full_name']      = 'shopify/shipit-engine' # targets the victim stack in every handler
  payload['pull_request']['labels']       = [{ 'name' => 'malicious-label' }]

  assert_difference -> { victim_stack.reload.pull_request.labels.size } do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok

  # Same single request also drove LabeledHandler's archive/unarchive branch against the victim stack.
  assert_not_nil victim_stack.reload.provision_status
end
```
Assertions on both sides of the binding: `org_verified` (`"attacker-org"`, used only inside `verify_signature`) is never compared to `org_targeted` (`"shopify"`, derived from `full_name` and used by both `LabelCapturingHandler` and `LabeledHandler`) — the test shows both handlers act on `shopify/shipit-engine`'s stack despite the request being "verified" for `attacker-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
