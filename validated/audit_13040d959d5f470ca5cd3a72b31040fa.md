### Title
Webhook signature is scoped to `repository.owner.login`, but event handlers dispatch on `repository.full_name` — an org's webhook secret authenticates writes to any repository claimed in the payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the closest reachable analog to the H-23 bug class ("value acted upon is never covered by the check that is supposed to authorize it"). Here, `WebhooksController#verify_signature` selects which GitHub App/org config (and therefore which `webhook_secret`) to verify the HMAC signature against by reading `params.dig('repository', 'owner', 'login')` straight out of the *unauthenticated* JSON body, and only proves that the request bears a valid signature for that named org. But the handlers that actually act on the payload (e.g. `PushHandler`, and the base `Handler#repository_name`) resolve the target `Repository`/`Stack` using a different, independently-attacker-controlled field: `payload.dig('repository', 'full_name')`. Nothing ties the authenticated org to the owner segment of `full_name`.

### Finding Description [1](#0-0) 

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where [2](#0-1) 
`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a value taken directly from the request body, before any signature check occurs.

The actual repository/stack that gets mutated is instead resolved via `full_name`: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
and [4](#0-3) 

`repository.owner.login` and `repository.full_name` are two independent fields in the same untrusted JSON body; GitHub itself keeps them consistent, but nothing in Shipit enforces that `full_name.split('/').first == repository.owner.login`. The equality that should hold — "organization whose secret authenticated the request" == "organization that owns the repository being written to" — is never checked.

This only becomes exploitable in the documented multi-tenant configuration where Shipit is configured with several GitHub orgs/apps, each with its own `webhook_secret` (as shown in `config/secrets.development.shopify.yml`, which lists multiple orgs each with independent `webhook_secret`/`oauth` blocks). In that mode, anyone who legitimately possesses (or can make GitHub emit) a validly-signed webhook for *any one* of the configured orgs — e.g. an org admin who owns/administers their own GitHub App installation pointed at this Shipit instance — can submit a payload whose `repository.owner.login` matches their own org (so `verify_signature` passes with their own secret) but whose `repository.full_name` names a stack belonging to a *different* configured org.

### Impact Explanation
Because `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack found via the forged `full_name`, and `GithubSyncJob#perform` ( [5](#0-4) ) fetches commits with the *app's own* GitHub credentials and appends them to that stack, and `CacheDeploySpecJob`/`ContinuousDeliveryJob` ( [6](#0-5)  — `stack.trigger_continuous_delivery` when `stack.continuous_deployment?`) can subsequently fire, an attacker who controls webhook signing for one tenant org can force sync/deploy activity against a stack owned by a different tenant org on the same Shipit instance. This crosses the "unauthorized deploy" / cross-org write threshold called out as Critical/High impact in the rules, without needing an `ApiClient` token, session, or GitHub write access to the victim repository.

Other handlers (`status`, `check_suite`, `pull_request`) exhibit the same pattern (`repository_name`/`params.repository.full_name` resolved independently of the org used for signature verification), broadening the blast radius (fake CI statuses, spurious review-stack provisioning, etc.) to any repository across any tenant org configured in the same instance.

### Likelihood Explanation
Exploitability is gated on the operator running Shipit in the multi-org configuration and the attacker legitimately controlling the webhook secret for at least one of those orgs (e.g., their own org's GitHub App/installation pointed at the shared instance) — this is exactly the deployment-trust boundary the task calls out ("organization that authenticated versus the repository that is written"), not a purely theoretical crypto bypass. Single-tenant deployments (one org configured) are not exploitable this way since `repository_owner` and the real owner necessarily coincide for legitimate GitHub-issued webhooks and there's no second org whose secret could be substituted. Given the shared-instance/multi-org use case is explicitly documented and supported (`config/secrets.development.shopify.yml`), likelihood is credible in that deployment topology.

### Recommendation
After signature verification succeeds, cross-check that the org used to select the `webhook_secret` (`repository_owner`) matches the owner segment parsed out of `repository.full_name` (and `organization.login` where relevant) before dispatching to handlers. Alternatively, have handlers resolve the target `Repository`/`Stack` using the same, already-verified `repository_owner` value rather than re-parsing `full_name` from the untrusted payload, and reject the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with a distinct `webhook_secret`, and create a stack for a repository owned by `org-b` (e.g. `org-b/victim-repo`).
2. As an attacker who administers the GitHub App/webhook for `org-a` (and thus knows/controls `org-a`'s `webhook_secret`), craft a `push` event JSON body with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
   - `ref = "refs/heads/<victim-branch>"`, `after = "<attacker-chosen sha that exists on GitHub>"`
3. Sign the raw body with `org-a`'s `webhook_secret` and send it to `POST /webhooks` with `X-Hub-Signature` and `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'org-a').verify_webhook_signature(...)`, which succeeds because the signature matches `org-a`'s secret.
5. `Shipit::Webhooks::Handlers::PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — enqueuing `GithubSyncJob`, which fetches commits using the Shipit app's own GitHub credentials for `org-b` and can trigger `ContinuousDeliveryJob` if continuous deployment is enabled, all without the attacker ever having write access to `org-b/victim-repo`.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
