### Title
Unrestricted `git submodule update --init --recursive` executes attacker-controlled transport helpers from a synced repo's `.gitmodules` - ([File: main.go])

### Summary
`git-sync`'s worktree configuration step runs `git submodule update --init [--recursive]` against whatever `.gitmodules`/submodule URLs are present in the remote-controlled repository, with no protocol allow-list configured (`protocol.allow`/`GIT_ALLOW_PROTOCOL`) and no `--credential`-style URL restriction applied to submodule fetches.

### Finding Description
The reported TimeLock bug class is "unrestricted downstream operation reachable from attacker-supplied content, bypassing an intended single-action trust boundary" (arbitrary call execution instead of one vetted call). The closest reachable analog in `git-sync` is `configureWorktree`, which unconditionally shells out to `git submodule update --init` (optionally `--recursive`) whenever `git.submodules != submodulesOff`: [1](#0-0) 

This command is driven entirely by the content of the synced repository's `.gitmodules` file — an attacker who can push a commit to the tracked ref (the same trust boundary `git-sync` is designed to operate on) fully controls the submodule URL and thus the git transport/helper invoked. No protocol allow-list is configured anywhere in the codebase before this call: [2](#0-1) 

A grep across the whole repository for any `protocol.allow`, `protocol.ext`, or `GIT_ALLOW_PROTOCOL` configuration found no results outside of the e2e test harness (which only sets `protocol.file.allow=always` for local test fixtures, not a restriction). This confirms `git-sync` relies entirely on the ambient git installation's default transport policy rather than pinning an explicit allow-list before running submodule operations on untrusted content.

### Impact Explanation
If the git binary/version in the deployed image has permissive protocol defaults (or an operator has set `protocol.ext.allow`/`GIT_PROTOCOL_FROM_USER` more permissively at the system/user gitconfig level, e.g. via `--git-config`), a malicious commit's `.gitmodules` can specify a submodule URL using the `ext::` transport (or other helper-invoking scheme) that spawns an arbitrary local command in the `git-sync` container, or a `file://` URL that exfiltrates content from arbitrary local paths reachable to the process. This would give code execution or file disclosure within the sidecar container — solely from a pushed commit, matching the "code execution / file write outside root" acceptance bar.

### Likelihood Explanation
Likelihood is moderate-to-low in a default deployment: modern git versions disable `ext::` by default unless explicitly allowed, and `git-sync` runs the submodule update as a direct (non-nested) invocation, which git treats as "user"-level and thus still requires an explicit `protocol.ext.allow=user/always` to be effective for `ext::`. However, `git-sync` exposes `--git-config`/`GITSYNC_GIT_CONFIG` which lets operators inject arbitrary git config (including protocol allow-lists) without git-sync validating or restricting the keys, and `git-sync` itself never pins a safe protocol allow-list as defense-in-depth. Because attacker-controlled `.gitmodules` content is the sole external input driving the command, any environment where the ambient git config is more permissive (custom images, older git, or an operator who has relaxed `protocol.*` for other reasons) is directly exploitable.

### Recommendation
1. Before running `git submodule update`, explicitly pin a restrictive protocol allow-list (e.g., pass `-c protocol.allow=never -c protocol.https.allow=always -c protocol.ssh.allow=always -c protocol.file.allow=never -c protocol.ext.allow=never`, adjusted per configured `--repo` scheme) at `git.Run(ctx, worktree.Path(), submodulesArgs...)`.
2. Alternatively/additionally set `GIT_ALLOW_PROTOCOL` in the environment used by `cmd.Runner` for all git invocations touching untrusted repo content, so it cannot be silently overridden by ambient git config.
3. Document and validate that `--git-config`/`GITSYNC_GIT_CONFIG` cannot be used to loosen these protections in ways that reintroduce the exposure, or explicitly disallow `protocol.*` keys from that flag.

### Proof of Concept
Not independently verified end-to-end (requires a specific git version/config combination to actually allow `ext::`); this is a code-path/config-gap finding based on static analysis of `configureWorktree` in [1](#0-0) , not a confirmed working exploit against a default `git-sync` deployment. Conceptual PoC:
1. Attacker with push access to the tracked branch adds `.gitmodules` with a submodule URL `ext::sh -c "id > /tmp/pwned"`.
2. Attacker commits and pushes.
3. `git-sync`'s next sync loop calls `configureWorktree`, which runs `git submodule update --init [--recursive]` against the new commit, invoking the `ext::` helper if the ambient/injected git config permits it.
