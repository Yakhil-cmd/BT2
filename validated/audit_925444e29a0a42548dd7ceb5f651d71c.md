### Title
Webhook signature is verified against `repository.owner.login` while the handler acts on the independent `repository.full_name` field, allowing cross-organization stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization used to check the HMAC signature using `params.dig('repository', 'owner', 'login')`, but the actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, and per-handler `repository` methods) resolve which `Stack`/`Repository` to act on using the sibling, independently-attacker-controlled field `params.dig('repository', 'full_name')`. Nothing binds these two fields together, so the field that is authenticated (`repository.owner.login`) is not the field that is acted upon (`repository.full_name`).

### Finding Description
`verify_signature` picks the GitHub App config with: [1](#0-0) 
using `repository_owner`, which is read from the payload: [2](#0-1) 

Once the signature is verified against `Shipit.github(organization: repository_owner).verify_webhook_signature`, the raw parsed body is dispatched unchanged to every registered handler: [3](#0-2) 

Handlers, however, determine the target repository/stack from a *different* JSON key, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

and `Repository.from_github_repo_name` simply splits that string on `/` and looks up any repo/owner pair with no relation back to whichever organization's webhook secret was used to verify the request: [5](#0-4) 

The same disconnection exists in `PushHandler#process` (deciding to `sync_github`) and in the pull-request handlers (`OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, etc.), all of which resolve `repository` via `params.repository.full_name`: [6](#0-5) [7](#0-6) 

Shipit explicitly supports hosting multiple, independently-configured GitHub App installations (one per organization), each with its own `webhook_secret`: [8](#0-7) [9](#0-8) 

**The broken binding, stated as an equality that should hold but does not**:
`organization whose webhook_secret authenticated the request` ≠ `repository.full_name that the handler subsequently mutates/queries`.

**Attack path**: An unprivileged party who controls (or has been granted, e.g. as a legitimate customer/tenant) one of the configured GitHub App installations — say organization `attacker-org`, with its own valid `webhook_secret` — can craft an arbitrary JSON payload, e.g. for the `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
They compute `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` (which they legitimately possess since it's their own app installation) and POST it to the shared `WebhooksController#create` endpoint. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (matches `repository.owner.login`), verifies the signature successfully because it was signed with that same org's secret, and passes. The handler then calls `Repository.from_github_repo_name("victim-org/victim-repo")` and operates on **victim-org's** stack — e.g. `PushHandler` triggers a `sync_github` for the victim's stack/branch based on an attacker-supplied `after` SHA, or pull-request handlers can create/archive/unarchive review stacks, or capture arbitrary label state on the victim's repository — despite the requester never having proven any relationship to `victim-org`.

### Impact Explanation
This breaks a trust boundary the app documents/relies upon: each GitHub App installation should only be able to authenticate webhooks for (and only act on) its own organization's repositories. By decoupling the field used for cryptographic authentication from the field used for authorization/target-selection, a party holding a legitimately-issued webhook secret for one tenant/org can forge webhook events that manipulate stacks belonging to a completely different, victim organization hosted on the same Shipit instance. This can trigger unintended deploy-adjacent actions (e.g., forcing `Stack#sync_github`, opening/closing/archiving review stacks, mutating PR label state used by provisioning logic) on repositories the attacker does not control — a cross-organization/cross-repository write that meets the "unauthorized deploy/rollback/merge"-class impact for multi-tenant Shipit deployments.

### Likelihood Explanation
Requires the instance to be configured with multiple GitHub App organizations (a supported, documented configuration) and requires the attacker to control one of those app installations (i.e., be a legitimate but unprivileged tenant/organization on a shared Shipit instance). No repository write access, Shipit session, or `ApiClient` token to the victim org is required — only knowledge of the victim's `owner/repo` name and their own org's webhook secret, both readily available. This is a realistic scenario for any shared/multi-org Shipit deployment.

### Recommendation
Bind the field used for authentication to the field used for authorization: after verifying the signature, require that the organization component of `repository.full_name` (and/or `organization.login`) match `repository_owner`/the app used for verification, rejecting (422) any payload where they differ. Alternatively, resolve the target `Repository`/`Stack` by joining on the authenticated organization rather than trusting the attacker-suppliable `full_name` field independently.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-app setup).
2. As the holder of `attacker-org`'s webhook secret, build a push payload:
```json
{"ref":"refs/heads/master","after":"<any sha>","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"}}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org webhook_secret, body)>`.
4. `POST /webhooks` (per `config/routes.rb`) with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which succeeds because the HMAC matches `attacker-org`'s secret.
6. `Shipit::Webhooks::Handlers::PushHandler` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `stack.sync_github(expected_head_sha: ...)` on the victim's stack — action performed on a repository the requester never authenticated for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
