### Title
Webhook signature verification unconditionally passes when an organization's `webhook_secret` is unset, allowing forged webhooks to grant `Shipit.github_teams` membership and fabricate CI status - ([File: lib/shipit/github_app.rb])

### Summary
`GithubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank for the organization resolved from the *attacker-controlled* payload, exactly mirroring the reported `HoldefiPauser` flaw where a degenerate configuration value (`pauseDuration = 0`) causes the guard (`isPause`) to always return `true` regardless of what the other actor does. Here, an admin leaving the (documented as "optional") `webhook_secret` blank for one configured organization causes `WebhooksController#verify_signature` to accept **any** unsigned request claiming to belong to that organization, no matter what signature (or lack thereof) is presented.

### Finding Description
`WebhooksController#verify_signature` selects the verifying `github_app` using a field taken directly from the untrusted JSON body/organization claim: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` in `GithubApp` short-circuits to `true` when no secret is configured for that organization: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

This reproduces the reported bug class precisely: the binding "request is authenticated" == "signature verified against the org's secret" is voided whenever the org's secret is empty — the check becomes an unconditional pass, just like `isPause` always returning `true` once `pauseDuration` is zero. Because `webhook_secret` is explicitly documented as *optional* per organization (`docs/setup.md`), an attacker only needs to know (or guess) that at least one configured GitHub organization on a multi-org Shipit instance has no webhook secret set, and can then POST arbitrary, completely unsigned JSON to the public `/webhooks` endpoint, claiming to be that organization.

The impact is not limited to spoofing repository/commit metadata. The `membership` webhook handler trusts the payload to create `Team`/`User` records and add arbitrary GitHub logins to a `Team`: [4](#0-3) 

```
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
```

`Team#add_member` simply appends the member relation with no validation against actual GitHub state: [5](#0-4) 

And `User#authorized?` — the check gating whether a logged-in GitHub identity may use the whole Shipit application — is based purely on this local `Team`/`Membership` data: [6](#0-5) 

```
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
```

So, for an organization lacking a webhook secret, an unauthenticated attacker can forge a `membership` event (`action: 'added'`) naming any GitHub login and any `team.id` matching one of `Shipit.github_teams`, causing Shipit to add that login to the authorizing `Team`. If the attacker's own GitHub account is then used to sign in via OAuth (`GithubAuthenticationController#callback` → `User.find_or_create_from_github`), `authorized?` will now return `true` for that login even though the attacker was never actually a member of the required GitHub team — a direct escalation into `Shipit.github_teams` authorization.

Separately, the `status` handler lets the same unauthenticated forger mark any known commit SHA's CI state as `success`: [7](#0-6) 

Combined with `continuous_deployment` on a stack, this can cause an unauthorized deploy of a commit that never actually passed CI, since `Commit#deployable?` depends on the (forged) status: [8](#0-7) 

### Impact Explanation
- **High**: escalation into `Shipit.github_teams` authorization via a forged, unsigned `membership` webhook that adds an arbitrary GitHub login to an authorizing `Team`, letting an unprivileged external attacker who signs in through the normal OAuth flow bypass the org/team access-control gate entirely.
- Contributing/compounding: forged `status`/`push` events for the vulnerable organization can fabricate a "successful" CI state for arbitrary commits, enabling an unauthorized deploy through `continuous_deployment` on any stack under that organization — matching the "unauthorized deploy" Critical bucket.

### Likelihood Explanation
Exploitability is gated entirely by whether an admin has left `webhook_secret` blank for at least one of the configured GitHub organizations — an explicitly supported and documented configuration (`docs/setup.md`, `config/secrets.*.yml` examples all show `webhook_secret: # nil` as valid). Given multi-org support is a first-class feature (`docs/setup.md` "Using Multiple Github Applications"), it is plausible for a large installation to have inconsistent secret configuration across organizations, and a single unsecured org is sufficient to compromise the shared `Shipit.github_teams` authorization gate for the whole instance. No credentials, tokens, or repository write access are required — only knowledge (or trial) of which org lacks a secret and a single unauthenticated POST to `/webhooks`.

### Recommendation
1. Treat a missing/blank `webhook_secret` as a hard misconfiguration rather than an implicit "always trust" state: fail closed (reject with 422/500) instead of `return true unless webhook_secret` in `GithubApp#verify_webhook_signature`.
2. Require `webhook_secret` to be present for every configured organization at boot time (fail fast in `lib/shipit/github_app.rb` initializer), removing the "optional" designation from documentation.
3. Add defense in depth for `MembershipHandler`: validate team membership changes against a live GitHub API call rather than trusting the webhook payload outright for `Team#add_member`.

### Proof of Concept
1. Configure a Shipit instance with two organizations, e.g. `orgA` (has `webhook_secret` set) and `orgB` (no `webhook_secret`, i.e. optional field left blank, as shown in `config/secrets.development.example.yml`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and no (or garbage) `X-Hub-Signature`, and a JSON body:
```json
{
  "action": "added",
  "team": { "id": <id-of-a-team-in-Shipit.github_teams>, "name": "X", "slug": "x", "url": "https://x" },
  "organization": { "login": "orgB" },
  "member": { "login": "attacker-github-login" }
}
```
3. Because `repository_owner` resolves to `"orgB"` (from `organization.login`, since no `repository` key is present) and `orgB` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — the request is accepted and processed regardless of signature.
4. `MembershipHandler#process` creates/finds the `Team` and appends `attacker-github-login` as a member via `Team#add_member`.
5. Attacker logs into Shipit via the normal GitHub OAuth flow using `attacker-github-login`; `User#authorized?` now returns `true` because the local `Team` row (falsely) lists them as a member of a team in `Shipit.github_teams`, granting full application access without ever being a real member of the gating GitHub team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
