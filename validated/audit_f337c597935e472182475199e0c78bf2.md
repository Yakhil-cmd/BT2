### Title
Unauthenticated `X-Shipit-User` header lets any API-token holder impersonate an arbitrary `User` for deploy/rollback/task/lock attribution and authorization - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
The bug report's core theme — state-changing operations that are not bound to any verified/authenticated source of truth, so the recorded actor of an action can be forged — has a direct analog in Shipit's API layer. `ApiClient` tokens authenticate *who is allowed to call the API* (a credential/permission binding), but the acting `User` recorded and authorized against for the operation (`current_user`) is derived from a client-supplied, unauthenticated request header (`X-Shipit-User`) instead of being cryptographically bound to the authenticated `ApiClient`.

### Finding Description
`Shipit::Api::BaseController#authenticate_api_client` authenticates the caller via a signed `ApiClient` token (HTTP Basic auth), which establishes `@current_api_client` and its `permissions` scope: [1](#0-0) 

Separately, `current_user` — the identity attributed to and authorized for the action being performed — is derived purely from the client-controlled `X-Shipit-User` request header, with no signature, no relationship to the authenticated `ApiClient`, and no verification that the caller actually is that `User`: [2](#0-1) 

This `current_user` is then used as the actor for high-impact, trust-sensitive operations:
- Locking a stack: `stack.lock(params.reason, current_user)` [3](#0-2) 
- Triggering a deploy: `stack.trigger_deploy(commit, current_user, ...)` [4](#0-3) 
- Triggering/aborting a rollback: `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` [5](#0-4) 
- Triggering/aborting a task: `stack.trigger_task(params[:task_name], current_user, ...)` / `task.abort!(aborted_by: current_user)` [6](#0-5) 

**The binding that is broken, stated as an equality that must hold but does not:**
`identity authenticated by the API credential` == `identity recorded/authorized as the actor of the state change`

Before the request: the `ApiClient` token cryptographically proves possession of a specific client's credentials and its fixed `permissions` array (`read:stack`, `write:stack`, `deploy:stack`, `lock:stack`, ...). The `User` acting on behalf of that client is *unauthenticated* — any string can be sent in `X-Shipit-User`.

After the request: actions like deploys, rollbacks, task aborts, and stack locks are permanently attributed to (and in `current_user.authorized?`-gated code paths, effectively vouched for by) whatever `User` login the attacker chose, without any proof that the holder of the API token is that user, or that the named user consented to or is even aware of the action.

Any holder of a valid `deploy:stack`/`lock:stack` API token (e.g., a CI integration, or any client whose token leaked with narrow intended use) can set `X-Shipit-User` to the login of a privileged human user (e.g., an org admin) to have destructive operations (deploys, rollbacks, aborting other users' running tasks, locking stacks) permanently attributed to that person. `identify_user` looks up any existing `User` record by login case-insensitively with no ownership check: [7](#0-6) 

### Impact Explanation
This breaks the audit/attribution trust boundary for irreversible production actions (deploys, rollbacks, task aborts, stack locks) performed through the API. While the `ApiClient` permission model correctly gates *what operation category* can be performed, it does nothing to prevent *misattribution of who performed it* — enabling an attacker who already possesses a scoped API token to frame another (potentially more privileged) user for an unauthorized deploy/rollback, and to make forensic/audit trails (which record `current_user` as the actor) unreliable. Given the report's own framing (unlogged/unverified changes to trust-relevant state "could go unnoticed and ultimately affect the contract's/system's operations"), the closest reachable class here is High: an unauthorized/misattributed deploy or rollback action riding on a legitimate but narrowly-scoped API credential.

### Likelihood Explanation
Any party with a valid `ApiClient` token that has `deploy:stack`, `lock:stack`, or `read:stack`-only permissions but no legitimate relationship to other users can trivially set the `X-Shipit-User` header to impersonate any existing Shipit `User` login. No additional secret, session, or GitHub credential is required beyond the already-issued API token — this is a design gap present on every API request path that reads `current_user`.

### Recommendation
- Short term: Stop trusting the client-supplied `X-Shipit-User` header as an identity source. Bind `current_user` to the authenticated `ApiClient.creator`, or require the header value to be validated against a signed/verified claim (e.g., mirrored via the same message-verifier mechanism used for `ApiClient.authenticate`), and reject requests where the named user cannot be cryptographically tied to the presented credential.
- Long term: Add logging/audit trails that record both the authenticated `ApiClient` and the resolved `current_user` for every state-changing API action, and add test coverage asserting that `current_user` cannot be forged independently of the authenticated credential.

### Proof of Concept
1. Obtain (or be issued) an `ApiClient` token scoped only to `deploy:stack` for stack `acme/widgets` (e.g., a CI-only credential).
2. Send:
```
POST /api/stacks/acme/widgets/deploys
Authorization: Basic base64(<api_client_id>--<token>)
X-Shipit-User: admin-login
Content-Type: application/json

{"sha": "<commit-sha>"}
```
3. `authenticate_api_client` accepts the request based on the token (app/controllers/shipit/api/base_controller.rb:48-61). `identify_user` resolves `current_user` to the `User` whose login is `admin-login` purely from the header (app/controllers/shipit/api/base_controller.rb:69-72) — with no verification that the token holder is `admin-login`.
4. `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)` (app/controllers/shipit/api/deploys_controller.rb:19-27), permanently recording the deploy as triggered by `admin-login`, even though the actual caller only ever proved possession of the low-privilege CI token.

        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end
