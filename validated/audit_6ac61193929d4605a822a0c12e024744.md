### Title
Deploy environment-variable whitelist is enforced against a stale cached `DeploySpec`, but the whitelisted values are spawned into commands built from the actually checked-out commit — ([File: app/models/shipit/stack.rb])

### Summary
`Stack#build_deploy` whitelists the user-supplied `env` hash against `cached_deploy_spec.deploy_variables` (via `filter_deploy_envs`), a spec object that is only refreshed asynchronously by `CacheDeploySpecJob` against the stack's *last reachable commit at cache time*. The actual deploy commands, however, execute against a fresh `DeploySpec::FileSystem` built from the working directory checked out at the deploy's specific `until_commit` in `TaskCommands`. These two specs can diverge (git history has moved, or an older/newer sha is targeted), so the "permitted" environment key-set checked at task-creation time is not guaranteed to be the same key-set the executed `shipit.yml` for that commit actually expects/guards against.

### Finding Description
- `Stack#build_deploy` calls `filter_deploy_envs(env.to_h)`, which is delegated to `cached_deploy_spec` [1](#0-0) , and `filter_deploy_envs`/`filter_rollback_envs` are also delegated straight to `cached_deploy_spec` at the `Stack` level [2](#0-1) .
- `cached_deploy_spec` is a serialized column populated only by `CacheDeploySpecJob`, which checks out `stack.commits.reachable.last` — i.e. the stack's HEAD **at the moment the job last ran** — and overwrites `stack.cached_deploy_spec` [3](#0-2) . This is asynchronous/eventually-consistent relative to the git history and to whatever specific `sha`/`until_commit_id` a deploy targets.
- `EnvironmentVariables#permit` raises `NotPermitted` only for keys absent from the variable-definition list it is given [4](#0-3) ; it has no notion of *which commit* declared that whitelist.
- The API `Deploys#create` action accepts an arbitrary `sha` and `env` hash from the caller and passes both straight into `stack.trigger_deploy` / `build_deploy` [5](#0-4) , so the commit actually deployed (`until_commit`) is caller-selected and independent from whatever commit the cached spec happens to reflect.
- When the deploy runs, `TaskCommands` builds the final process environment by loading a **new** `DeploySpec::FileSystem` rooted at `@task.working_directory` (i.e. the checkout of `until_commit`, not the cached HEAD spec) and merges `deploy_spec.machine_env` with the previously-whitelisted `@task.env`: `env.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)` [6](#0-5) .
- Because the whitelist check (`cached_deploy_spec.deploy_variables`) and the effective spec used to run the deploy (`DeploySpec::FileSystem` at `until_commit`) are independently sourced, a caller with `deploy:stack` permission can pick a `sha` whose actual `shipit.yml` no longer declares/expects a given `deploy.variables` entry, while the stale cache still permits it (or vice-versa), letting attacker-controlled values reach `Command#interpolate_environment_variables`/process env for a commit whose own configuration never authorized that variable for that specific ref.

### Impact Explanation
This breaks the intended binding "environment key permitted == environment key whose semantics apply to the commit actually executed." An attacker who already holds a `deploy:stack`-scoped `ApiClient` token (a deliberately restricted, non-admin credential) can smuggle environment variables into shell command execution on the deploy host for a commit whose own `shipit.yml` does not authorize/expect them, potentially influencing script behavior (e.g., variables interpolated with `$VAR` in deploy scripts per `Command#interpolate_environment_variables`, `lib/shipit/command.rb:51-55`). This can escalate a scoped deploy permission into command/environment manipulation on the deploy host, i.e., toward the "Critical - RCE on the deploy host" / "unauthorized deploy" impact classes, because the variable set actually enforced is not tied to the ref being deployed.

### Likelihood Explanation
Requires only an `ApiClient` with `deploy:stack` permission (already a normal, non-privileged-admin credential in this engine's threat model) and a repository where `CacheDeploySpecJob` has not yet re-run against the latest commit relative to the `sha` chosen for deploy — a routine, easily engineered timing condition (push a commit that removes/narrows `deploy.variables`, then immediately deploy that new sha via the API before/without the async cache job catching up, or conversely deploy an older sha while the cache reflects newer, broader variable definitions).

### Recommendation
Enforce the environment-variable whitelist using the `DeploySpec` of the exact commit being deployed (`until_commit`), not the stack's asynchronously cached spec. Concretely, `Stack#build_deploy`/`filter_deploy_envs` should validate against a `DeploySpec::FileSystem` (or an equivalently freshly-resolved spec) checked out at `until_commit`, or `TaskCommands#env` should re-validate `@task.env` against the same `deploy_spec` object it uses to build `machine_env`, rejecting any key not defined for that specific commit.

### Proof of Concept
1. On the default branch, commit A declares `deploy.variables: [{name: SAFE_VAR}]` in `shipit.yml`. `CacheDeploySpecJob` runs and populates `stack.cached_deploy_spec` from commit A, whitelisting `SAFE_VAR`.
2. Push commit B that redefines `deploy.variables` to *only* `[{name: SAFE_VAR}]` again but changes deploy scripts to read a formerly-unlisted variable `INTERNAL_FLAG` unsafely (or, inversely, commit B removes a variable that used to be considered dangerous and no longer sanitizes it) — the key point is the cached spec (from A) and commit B's actual spec diverge on the variable set.
3. Immediately, before `CacheDeploySpecJob` re-runs for commit B, call `POST /api/stacks/:owner/:name/:env/deploys` with `sha=B` and `env={"SAFE_VAR_OR_STALE_KEY": "attacker_value"}` using a `deploy:stack`-scoped token.
4. `filter_deploy_envs` validates against the stale `cached_deploy_spec` (commit A's rules) via `Stack#build_deploy` [1](#0-0) , accepting a key/value pair that commit B's actual `shipit.yml` does not intend to authorize for that ref.
5. The task runs against the commit-B checkout; `TaskCommands#env` merges `deploy_spec.machine_env` (fresh, from commit B) with `@task.env` (validated only against stale commit-A rules) [6](#0-5) , spawning the attacker-influenced variable into the process environment for commit B's deploy scripts, which were never audited/whitelisted with that variable in mind.

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
