This confirms the multi-org config model: `Shipit.github(organization:)` looks up per-organization config via `github_app_config`, so each configured org can have its own `webhook_secret`, and `verify_webhook_signature` is validated against that specific org's secret [1](#0-0) . For the `membership` webhook, `repository_owner` falls back to `params.dig('organization', 'login')` since there's no `repository` key in that payload [2](#0-1) , meaning the signature is validated per the org named in the attacker-controlled payload itself — if the attacker legitimately owns/administers an org that is also configured in this Shipit instance (multi-tenant deployment), they can send a validly-signed webhook naming their own org.

### Title
Cross-org team hijack via unchecked `Team#organization` on membership webhook `add_member` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` only sets `team.organization` inside the `find_or_create_by!` block, which ActiveRecord only executes on record creation, never on a subsequent find [3](#0-2) . Worse, even on creation, the code never validates that `params.organization.login` corresponds to the org that legitimately owns `params.team.id`; it simply trusts whatever org string is in the payload. Because `team.add_member`/`team.members.delete` are then called unconditionally regardless of which org sent the webhook [4](#0-3) , any org configured in this multi-tenant Shipit instance can add or remove members of a team belonging to a different org, as long as they can guess/know that team's numeric GitHub `id`.

### Finding Description
The broken binding is: `team.organization == verified_webhook_org` must hold before `team.add_member`/`team.members.delete` executes. The code enforces no such check, ever — not just on the find path described in the prompt, but structurally in `process`, which calls `team.add_member(member)` for `action == 'added'` with zero reference to `params.organization.login` at all [4](#0-3) .

Path: `WebhooksController#create` dispatches the `membership` event to `MembershipHandler` after `verify_signature`, which calls `Shipit.github(organization: repository_owner)` where `repository_owner` is derived from `params.dig('repository','owner','login') || params.dig('organization','login')` [5](#0-4) . Since `membership` payloads carry no `repository` key, the org used to select the verification secret is exactly the attacker-controlled `organization.login` field. `Shipit.github(organization:)` looks up a **per-organization** secret via `github_app_config`, keyed purely by the org name in the request [1](#0-0) . In a multi-tenant Shipit deployment (multiple orgs configured, each with its own webhook secret), an attacker who legitimately administers their own registered org can produce a validly-signed membership webhook naming their own org, while embedding an arbitrary `team.id` value belonging to a *different* configured org's team.

`find_or_create_team!` finds the target `Team` row purely by `github_id` (the GitHub numeric team ID), with no cross-check against `organization` [3](#0-2) . `Team.find_or_create_by!` only executes the block (which sets `organization`) on the creation path; on find, the existing `organization` is left untouched, but no code path ever asserts `team.organization == params.organization.login`. The handler then unconditionally calls `team.add_member(member)` [6](#0-5) , appending an attacker-controlled `User` to `Team#members` regardless of which org actually owns that team.

No existing guard prevents this: `verify_signature` only proves the request was signed by *some* configured org's secret, not that it matches the team being mutated [7](#0-6) ; the `ExplicitParameters` schema only validates types/presence, not cross-org ownership [8](#0-7) ; and `Team` has no model-level uniqueness/validation tying `github_id` to `organization`.

### Impact Explanation
An attacker who legitimately controls one org configured in a multi-tenant Shipit install can forge team membership for a team belonging to a completely different tenant org, by targeting a known/guessed `team.id` (GitHub's numeric team ID, not a secret). Since `Shipit.github_teams` membership (via `User#authorized?` at `app/models/shipit/user.rb:80-82`) can gate access to the entire Shipit application [9](#0-8) , this can escalate an attacker's own GitHub account into a privileged Shipit team of a victim org, bypassing that org's authorization boundary. This matches "High: escalation into `Shipit.github_teams` authorization." It is repeatable against any team `github_id` the attacker can enumerate/observe, across any number of victim orgs hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) the Shipit instance is multi-tenant — multiple GitHub orgs configured with distinct webhook secrets in `secrets.github` — enabling the attacker to obtain a validly-signed webhook for their own org name; (2) the victim's `Team` row (keyed by the real GitHub team `github_id`) already exists in the DB, e.g. seeded via `teams:fetch` or a prior legitimate sync; (3) the attacker knows or can enumerate that numeric `github_id`, which is not treated as a secret by GitHub (visible via org/team APIs). Given these, the attacker's cost is low: send one crafted, self-signed `membership` `added` event. This is feasible specifically in shared/multi-org Shipit deployments and is fully within this engine's own webhook-handling code.

### Recommendation
In `MembershipHandler#process`, after resolving the team, assert `team.organization.casecmp?(params.organization.login)` before calling `add_member`/`members.delete`, and raise/drop the event otherwise. Additionally, avoid ever silently reusing an existing `Team` row when its `organization` doesn't match the current payload's org — treat that as a data integrity error to be logged/dropped rather than acted upon.
