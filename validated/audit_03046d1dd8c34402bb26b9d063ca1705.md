## Analog Found: Integer‑precision overflow in asset denomination cap arithmetic

### Title
Floating-point precision overflow in asset denomination cap validation lets an asset issuer bypass the declared supply cap - (File: `validation.js`)

### Summary
CVE-2020-35523 is a libtiff integer overflow where multiplying image width/height (attacker‑controlled) produces a wrapped/undersized value that is used to allocate a buffer, letting a crafted file corrupt memory. The equivalent bug class in `ocore` is unchecked multiplication of two attacker‑controlled "size" quantities that are used to derive a supply/consistency invariant. In `ocore`, JS numbers are IEEE‑754 doubles, so there is no 32‑bit wraparound, but the same root cause — multiplying two large validated‑as‑"positive integer" values without bounding the product to a safely representable range — produces silent precision loss, which can make an invalid on‑chain invariant look valid.

### Finding Description
When a unit author defines an asset with `fixed_denominations` and a `denominations` array, `validateAssetDefinition` sums the capacity of each denomination row and compares it to the declared `cap`: [1](#0-0) 

Each `denomInfo.denomination` and `denomInfo.count_coins` is only checked with `isPositiveInteger`, i.e. `Number.isInteger(x) && x > 0`. `Number.isInteger` accepts any integral double, including values far larger than `Number.MAX_SAFE_INTEGER` (2^53‑1). The upper bound `denomination <= constants.MAX_CAP` is only enforced conditionally (post `pemCurvesFixMci`), and `count_coins` has **no** explicit upper bound check at all in this code path: [2](#0-1) 

The accumulation `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` is plain JS floating‑point multiplication. Once the product of `count_coins` and `denomination` exceeds 2^53, the result silently loses precision (rounds to the nearest representable double) — this is the direct analog of the libtiff integer‑overflow: two attacker‑supplied "dimension" values are multiplied without an overflow-safe check, and the resulting corrupted magnitude is then trusted as the authoritative supply figure that is compared against the declared `cap` and persisted to `assets`/`asset_denominations` tables.

The same unguarded multiplication pattern is duplicated in the AA-authored asset path used when an AA defines an asset via a trigger/definition (`validateDenominations`), and later, during actual coin issuance, in `indivisible_asset.js`: [3](#0-2) [4](#0-3) 

Because `issue_amount = count_coins_to_issue * denomination` is computed the same unguarded way at issuance time, a denomination/count_coins pair crafted so their true product exceeds 2^53 (but rounds, at validation time, to a value that matches an attacker‑chosen `cap`) could pass asset‑definition validation while actual per‑row issuable amounts (computed independently per row, potentially summed differently, or rounded differently on different nodes/architectures) diverge from the declared cap — creating either a cap‑mismatch across implementations or silently permitting issuance beyond the stated total.

### Impact Explanation
If the precision loss can be engineered so validating nodes and issuing logic disagree on the true summed capacity vs. the declared `cap`, this maps directly to "supply inflation" of an indivisible asset: total issuable coins could exceed the declared cap, or nodes could reach different conclusions about whether the sum matches the cap (a node‑disagreement‑on‑validity scenario), both of which are impacts explicitly in scope.

### Likelihood Explanation
This requires an attacker to construct `denomination` / `count_coins` values whose product straddles the `Number.MAX_SAFE_INTEGER` boundary while still passing `isPositiveInteger` and (pre‑`pemCurvesFixMci`) the `denomination <= MAX_CAP` check. This is a narrow, precision‑engineering effort but requires no privileged access — any unit poster/asset issuer can submit such a definition. I was not able to conclusively verify from the index the exact numeric value of `constants.MAX_CAP` or confirm whether it is itself bounded below 2^53 in all code paths (search results consistently show references but not the constant's literal value), so I cannot fully confirm whether the post-`pemCurvesFixMci` check already forecloses the overflow window for `denomination`. The `count_coins` field, however, appears unbounded in both `validation.js` and `aa_validation.js` regardless of MCI, which is the more concrete, unresolved gap.

### Recommendation
- Bound `count_coins` (and, if not already fully enforced, `denomination`) explicitly to `constants.MAX_CAP` (or `Number.MAX_SAFE_INTEGER`) in both `validation.js`'s `validateAssetDefinition` and `aa_validation.js`'s `validateDenominations`, independent of MCI-gating.
- Perform the cap-sum comparison using an overflow-safe integer type (e.g. BigInt) rather than native JS multiplication/addition, and reject any denomination whose `count_coins * denomination` product cannot be exactly represented as a JS safe integer.
- Apply the same safe-integer check to `issue_amount = count_coins_to_issue * denomination` in `indivisible_asset.js` before it is used to construct payment inputs.

### Proof of Concept
Conceptual (not executed, since I only have read access to the index):
1. Attacker crafts an asset-definition unit with `fixed_denominations: true` and `denominations: [{denomination: D, count_coins: C}]` such that `D * C` mathematically exceeds `Number.MAX_SAFE_INTEGER` but, due to floating point rounding, evaluates in JS to a rounded value equal to an attacker-chosen `payload.cap`.
2. `validateAssetDefinition` (`validation.js:2757-2792`) accepts the definition because `total_cap_from_denominations === payload.cap` after rounding, even though the true product differs.
3. At issuance time, `indivisible_asset.js` computes `issue_amount = count_coins_to_issue * denomination` (line 536) using the same unguarded multiplication, potentially producing an issuance amount inconsistent with the validated cap once real coin-by-coin issuance interacts with `Math.floor` arithmetic elsewhere, or causing disagreement between nodes performing the same computation on different underlying float representations.

I could not fully verify the exact bound of `constants.MAX_CAP` from the available index, so the concrete numeric feasibility of crafting such `D`/`C` pair (i.e., whether the current `MAX_CAP` value already prevents `D*C` from reaching 2^53) remains unconfirmed and should be checked directly in `constants.js` in a full repository clone.
