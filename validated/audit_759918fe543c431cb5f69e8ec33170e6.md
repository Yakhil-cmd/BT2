### Title
Same L1 Bitcoin lockup outpoint can be re-submitted across separate `register-for-bond` calls to double-count sats collateral - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s `register-for-bond` accepts an L1 Bitcoin lockup proof and credits `sats-total` toward a staker's bond weight via `verify-l1-lockups` → `validate-l1-lockup`. The only anti-replay protection (`seen-outpoints` / `ERR_DUPLICATE_LOCKUP_OUTPOINT`) is scoped to the single call's fold accumulator and is never persisted, so the same real Bitcoin outpoint (txid + output-index) that already backed one bond registration can be resubmitted in a later, independent `register-for-bond` call and be credited again as fresh collateral, without any additional BTC ever being locked.

### Finding Description
`validate-l1-lockup` builds `seen-outpoints` fresh on every call to `verify-l1-lockups` [1](#0-0) , and only rejects an outpoint that repeats *within that one list* via `ERR_DUPLICATE_LOCKUP_OUTPOINT` [2](#0-1) . There is no contract-level map that records "this Bitcoin outpoint has already been credited to a bond" across separate transactions/calls. The Bitcoin-side facts that `validate-l1-lockup` checks (header validity, merkle inclusion, script hash, amount) are permanent, immutable facts about the chain — they remain true forever once the lockup transaction is mined, and are true again in every subsequent call with the same parameters [3](#0-2) .

`register-for-bond` only prevents a staker from having two *overlapping* bond memberships at once (`ERR_ALREADY_REGISTERED` via `bond-overlaps-new-position?`) and requires a "rollover" to happen within the ending bond's L1 unlock window [4](#0-3) . Once a staker's earlier bond term ends (or is rolled over), nothing in `register-for-bond`, `verify-l1-lockups`, or `validate-l1-lockup` checks whether the exact same outpoint was already consumed by a prior `register-for-bond` call for a previous bond period. Since the real BTC UTXO is still sitting untouched at the P2WSH address (the on-chain timelock has not necessarily matured/been spent), the staker can present the identical lockup proof again to register for a new bond and have `sats-total` (and thus their bond weight / signing weight / reward share) credited a second time — backed by the same underlying BTC collateral that is only locked once.

This breaks the equality the report's bug class targets: "sats credited by an L1 proof that were never [additionally] locked on Bitcoin" — the contract double-counts a single BTC commitment as if it were two independent commitments.

### Impact Explanation
This matches the "High" impact bucket: "signing weight or reward slots exceeding locked value" and effectively "double-counting a commitment". A staker can reuse one real BTC lockup to inflate `sats-total` (and therefore `min-ustx-for-sats-amount`-derived stake sizing, allowlist consumption via `ERR_TOO_MUCH_SATS`, and signer-set/reward weight) across multiple bond periods without providing additional Bitcoin collateral for each. Because `sats-total` feeds directly into `protocol-bonds-total-staked` and staker bond shares [5](#0-4) , this can distort reward distribution and signer weighting relative to actually-locked BTC.

### Likelihood Explanation
Requires only an unprivileged staker who already went through a normal L1 lockup registration, and who is later eligible to register again (bond ended, or via the rollover path with a new bond period). No admin, miner, or other user's key is needed — the staker simply resubmits the same `tx`/`header`/`leaf-hashes`/`output-index` payload they used previously. Likelihood is moderate: it depends on the staker being allow-listed for a subsequent bond and choosing to reuse rather than obtain a new lockup, but nothing in the contract logic prevents it.

### Recommendation
Persist a global (not per-call) map keyed by the Bitcoin outpoint (`txid`, `output-index`) recording that it has been consumed by a `register-for-bond` call, and check it inside `validate-l1-lockup` (or in `verify-l1-lockups` before folding), rejecting with a new error (e.g. `ERR_LOCKUP_ALREADY_USED`) if the outpoint has been previously consumed by any staker/bond, unless it is explicitly the same staker rolling the same lock into the immediately-following bond period (which should transfer/re-tag ownership of the recorded outpoint rather than allow a second independent credit).

### Proof of Concept
Conceptual sequence (I was not able to fully trace the unstake/rollover cleanup path for L1 memberships in the time available, so verify whether any of these steps reset attacker state; the core defect — the missing global outpoint map — is confirmed by direct code reading):
1. Staker locks `X` sats into a P2WSH at outpoint `O` per `construct-lockup-output-script`.
2. Staker calls `register-for-bond(bond_0, ..., btc-lockup = ok {outputs: [O], ...})`. `verify-l1-lockups` validates `O` and credits `sats-total = X`; membership for `bond_0` is created [6](#0-5) .
3. Bond `bond_0`'s term ends (or the staker becomes eligible to register into a non-overlapping `bond_1` per `bond-overlaps-new-position?`); the on-chain BTC at outpoint `O` has not been spent (timelock possibly not yet matured, or staker simply never spends it).
4. Staker calls `register-for-bond(bond_1, ..., btc-lockup = ok {outputs: [O], ...})` with the exact same `tx`/`header`/`leaf-hashes`/`output-index` as before. `validate-l1-lockup`'s checks (header, merkle proof, script hash, amount) all pass again because they are checking permanent Bitcoin facts, and `seen-outpoints` is a fresh empty list for this new call, so no duplicate is detected. `sats-total = X` is credited again for `bond_1`, backed by the same, single, already-counted BTC lock.
