### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized deploy trigger - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA, with no check that the SHA belongs to the repository named in the webhook payload, unlike every other handler which scopes through `Handler#stacks`/`repository_name`. Because git SHAs are content-addressed and can be identical across independent repositories (forks, cherry-picks, shared history), an attacker who owns any Shipit-tracked repository can send a validly-signed `status` webhook for their own repo whose `sha` happens to collide with a commit tracked by a completely different, victim stack, injecting a forged `success` Status onto that victim commit.

### Finding Description
The binding this system is supposed to guarantee is:
`Status row attached to commit C (belonging to stack S) ⇒ payload['repository']['full_name'] that produced it corresponds to S.repository`.

`StatusHandler#process` breaks this:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Contrast this with the base `Handler` class, which every other handler is expected to use to scope by the payload's own repository:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`StatusHandler#process` never calls `stacks` or `repository_name` — it queries `Commit` globally by `sha` across every stack in the installation. Since `sha` is a git content hash, not a Shipit-scoped identifier, two different repositories (e.g., a victim repo and any fork/rewrite sharing commit history with it) can have `Commit` rows with the identical `sha` value, each belonging to a different `stack_id`.

Exploit path:
1. Attacker signs up their own repository/org with Shipit (self-service onboarding is standard; this does not require any privileged role, GitHub team membership, or knowledge of victim secrets).
2. Attacker's org has a legitimate webhook secret; `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` using the **payload's own** `repository.owner.login`, so as long as the attacker keeps that field pointing at their own org, they can produce a validly-signed request with a body they otherwise fully control (including `sha`, `state`, `context`, etc.) via `POST /webhooks`.
3. Attacker engineers (or opportunistically finds) a commit SHA shared between their own tracked repo and the victim's tracked repo/stack (trivial via forks, cherry-picks, or identical initial/empty commits with the same tree/parent/author metadata — SHAs are deterministic and content-addressed, requiring no secret).
4. The signed webhook is delivered to `WebhooksController#create`, passes `verify_signature`, and is dispatched to `Shipit::Webhooks::Handlers::StatusHandler`.
5. `StatusHandler#process` does `Commit.where(sha: params.sha)` and finds the victim's `Commit` row (regardless of the fact the payload's `repository` field named the attacker's own repo), then calls `commit.create_status_from_github!(params)`, which persists a `Status` scoped to the **victim's** `stack_id` (via `add_status`) using the forged `state`/`context`. [3](#0-2) 

6. `Status#schedule_continuous_delivery` fires `commit.schedule_continuous_delivery` on create: [4](#0-3) 
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [5](#0-4) 

`deployable?` only inspects `Status`/`CheckRun` rows attached to the commit — it has no notion of "did this status actually come from *this stack's own* repository":
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 

7. `ContinuousDeliveryJob` calls `Stack#trigger_continuous_delivery`, which selects `next_commit_to_deploy` and, if `deployed_too_recently?` is false (the normal in-between-deploys window, or exactly the race window described where `deployed_too_recently?` transiently returns false between task completions), calls `trigger_deploy(commit, ...)`: [7](#0-6) 
```ruby
def next_commit_to_deploy
  commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
  ...
  deployable_commits(commits_to_deploy)
end
``` [8](#0-7) 

The result is an unauthorized `Deploy` created for a commit whose only "success" evidence is a forged Status the attacker wrote using their own, unrelated repository's webhook credentials.

Existing guards do not prevent this: `verify_signature` only proves the request came from *some* org the attacker controls, not that the `sha`/commit belongs to that org's repository; `ExplicitParameters` only validates field types/shapes, not cross-referencing `sha` ownership; and `StatusHandler` uniquely, among all handlers, omits the `stacks`/`repository_name` scoping that would have prevented this.

### Impact Explanation
An attacker who onboards even a single innocuous repository into a shared Shipit instance can write forged `Status` rows onto commits belonging to *any other stack in the instance* whose commit history happens to share a SHA with something the attacker can produce, and can use this to make an otherwise non-deployable commit `deployable?`, triggering `Stack#trigger_continuous_delivery` to create a real `Deploy` (running deploy commands against the victim's infrastructure) for a commit that never actually passed the victim's CI. This is a cross-tenant "payload for one repository mutating another's stack/commit" leading to an "unauthorized deploy" — squarely in the Critical bucket. It is repeatable against any victim stack whose commit history intersects with an attacker-controlled SHA and is not limited to a single request (attacker can keep forging additional passing statuses as new commits land).

### Likelihood Explanation
Preconditions: the Shipit instance must host multiple tenants/stacks (typical for a shared internal Shipit deployment), and the attacker needs at least one legitimately onboarded repository/org (self-service, not privileged) to obtain a valid webhook secret. Producing a colliding SHA does not require any secret — git commits are content-addressed and reproducible; forks/cherry-picks/rebases routinely share identical SHAs across repositories, and an attacker fully controls their own repository's commit metadata to engineer a match. The remaining piece — landing the forged status inside the window where `deployed_too_recently?` is false — is a normal, frequently-occurring state (any time between deploys), not a narrow race. Overall this is a low-cost, highly feasible, and repeatable attack.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records purely by SHA) to the repository named in the payload, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ensures a Status can only be attached to a commit belonging to a stack whose `Repository` matches `payload['repository']['full_name']`, restoring the intended binding.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "forged status from unrelated repository is rejected once scoped by repository" do
  victim_stack = shipit_stacks(:shipit)                 # e.g. repository "shopify/shipit-engine"
  attacker_repo_full_name = "attacker/unrelated-repo"

  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "victim commit", ...)
  refute_predicate victim_commit, :deployable?

  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "ci/travis",
    "repository" => { "full_name" => attacker_repo_full_name }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  refute_predicate victim_commit.reload, :deployable?
  assert_no_difference -> { victim_stack.deploys.count } do
    victim_stack.trigger_continuous_delivery
  end
end
```
Against the current (unpatched) code, `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` creates a `Status` on `victim_commit` (because `Commit.where(sha: ...)` ignores `payload["repository"]`), `victim_commit.deployable?` becomes true, and a subsequent `victim_stack.trigger_continuous_delivery` creates a `Deploy` — demonstrating the equality `Status.stack_id == payload-authenticated repository's stack` is violated.

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
