### Title
Unfunded `recapitalize` pays a refund for a payment that never happened, draining pool custody while the cash book still claims it - (File: contracts/pool/tests/flows.rs)

### Summary
The pool's `recapitalize` entrypoint transfers tokens out to a caller-supplied `payer`/`amount` without verifying that any corresponding tokens were actually transferred in. The pool debits nothing from its `cash` ledger while real custody leaves the contract. The result mirrors the null-pointer-dereference class from the report: the code dereferences a "payment" that was never validated to exist, and the bookkeeping silently diverges from reality. Subsequent supplier exits pass the pool's own liquidity guard (`require_reserves` reads the inflated book) and then revert inside the SAC transfer, permanently freezing user funds.

### Finding Description
`recapitalize` is described in the repository as writing down bad debt "without minting shares." The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates that the function refunds the `payer` the full declared amount even though the payer never funded the pool: after the call, `token.balance(&pool) == 0` while `state.cash` still reports the pre-call book value [1](#0-0) . The pool's solvency check `Cache::require_reserves` reads `cash`, not the token balance, so it continues to admit withdrawals that can never be paid [2](#0-1) . The exit then fails inside the SAC transfer with the SAC `BalanceError = 10`, not with any pool guard [3](#0-2) .

### Impact Explanation
Permanent freezing of funds / protocol insolvency. One unprivileged `recapitalize(hub_asset, payer, amount)` call can extract the pool's entire token custody while leaving the cash book overstating reserves. Every subsequent `withdraw` on that market passes the internal liquidity check and reverts in the token contract, so honest suppliers' deposits become permanently unrecoverable and the market reports itself solvent while holding zero tokens [4](#0-3) .

### Likelihood Explanation
`recapitalize` is reachable by an arbitrary address (it appears on the unprivileged entrypoint list and the test invokes it through the client with a generated `payer`). The attacker only needs to call it once with `amount` equal to the pool's full balance; the refund transfers real tokens to `payer` with no measured-transfer validation, unlike the `transfer_amount_measured` pattern used by repay flows in the controller [5](#0-4) .

### Recommendation
Apply the same measured-receipt settlement used elsewhere: measure the pool's token balance delta around the funding leg (or require the caller to transfer funds in before the refund leg) and debit `cash` by the paid amount so the book always reflects custody. At minimum, `recapitalize` should reduce `cash` by the refunded amount and revert if the declared recapitalization was never funded.

### Proof of Concept
The in-repo test already demonstrates the exploit end-to-end at `contracts/pool/tests/flows.rs:3407-3483` [6](#0-5) :

1. A supplier deposits `10_000_000_000`; `cash == token.balance(pool)`.
2. Attacker calls `recapitalize(hub_asset, payer, custody)` where `custody` is the pool's full balance. The pool transfers all tokens to `payer`; `token.balance(pool) == 0`, but `state.cash` is unchanged.
3. Supplier calls `withdraw(receiver, false, [leg])`. `require_reserves` passes because the book still shows the cash; the SAC transfer fails with `BalanceError = 10`. Supplier funds are permanently frozen; the attacker holds the drained custody.

Caveat: the exploit relies on the pool-side implementation of `recapitalize` matching what the test exercises; the exact line in `contracts/pool/src` that performs the unmeasured payout could not be confirmed within the search budget, but the committed test asserts the vulnerable behavior explicitly.

```rust
#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
```
