### Title
`StatusHandler#process` matches commits by SHA only (no repository binding), letting a status from one tracked repo flip `deployable?` on a commit belonging to a different stack and defeat `Api::DeploysController#create`'s `require_ci` check - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and applies the incoming GitHub status to every matching row, without ever checking that `payload.dig('repository', 'full_name')` matches the repository owning that commit's stack. Because `Commit#deployable?` is stack-scoped state that `UndeployedCommit#deploy_disallowed?` and `Api::DeploysController#create`'s `require_ci` check both trust blindly, a validly-signed status webhook from *any* Shipit-tracked repository can flip `deployable?` to `true` for a same-SHA commit sitting in an entirely different stack/repository, bypassing the CI-verification safety net on the deploy API.

### Finding Description
The broken binding, stated explicitly: the question assumes `repository_that_produced_the_CI_signal == repository_whose_deployable?_flag_is_trusted_by_require_ci`. Tracing the code shows these are never actually checked to be equal:

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike every other handler in this codebase (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), which all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope subsequent lookups through that repository, `StatusHandler` never consults `repository_name`/`params.repository` at all — it only requires `sha`, `state`, and optional fields, and dispatches purely by SHA: [2](#0-1) 

`create_status_from_github!` then writes the `Status` scoped to the found commit's *own* `stack_id`: [3](#0-2) 

That status feeds `Commit#deployable?` directly:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [4](#0-3) 

which feeds `UndeployedCommit#deploy_disallowed?`:
```ruby
def deploy_disallowed?
  !deployable? || !stack.deployable?
end
``` [5](#0-4) 

and is the *only* CI check performed by the deploy API:
```ruby
param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?
``` [6](#0-5) 

**Exploit flow:** Signature verification (`WebhooksController#verify_signature`) resolves the webhook secret by organization login taken from the payload's `repository.owner.login`, via `Shipit.github(organization: repository_owner)`: [7](#0-6) 

In a multi-org Shipit deployment (explicitly supported and documented — `github_app_config`/`github_organizations`), each onboarded GitHub organization has its own App and webhook secret, and any legitimate status event for a repository within an onboarded org will be signed correctly by GitHub itself: [8](#0-7) 

An attacker who merely owns/pushes to a repository inside one already-onboarded organization ("Org B") can: (1) reproduce a victim commit's exact SHA by pushing the identical commit content into their own repo (git SHAs are content-derived, so no hash collision is required, only content reuse of a typically-public victim commit), and (2) set a `success` status on that SHA in their own repo via the ordinary GitHub commit-status API (a normal, unprivileged action any repo collaborator can perform). GitHub then dispatches a correctly-signed `status` webhook for Org B to Shipit. Because `StatusHandler#process` never checks `params.repository`/`repository_name` against the commit's actual stack/repository, it applies that forged `success` status to the victim's identically-SHA'd commit in a totally different stack (Org A), flipping `Commit#deployable?` for that stack even though Org A's real CI never ran or failed.

None of the existing guards catch this: `verify_signature` only proves the payload came from *some* onboarded org's GitHub App — it says nothing about which repository's commit the SHA belongs to. `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate presence/types of `sha`/`state`, not repository ownership. `require_permission!`/`current_user` checks on `Api::DeploysController` govern *who* may call deploy, not whether the underlying `deployable?` signal is trustworthy.

### Impact Explanation
An attacker controlling any repository within one Shipit-onboarded organization can inject a forged `success` status into a completely different stack/organization's commit, flipping `Commit#deployable?` and `UndeployedCommit#deploy_disallowed?` to falsely permit deployment. This directly defeats the `require_ci: true` safety check on `Api::DeploysController#create`, and also affects continuous-deployment stacks (`Stack#trigger_continuous_delivery`) that rely on `deployable?`/`next_commit_to_deploy` to auto-deploy. The result is an unauthorized/unverified deploy being triggered for a victim repository whose CI never actually passed — a cross-tenant write (one repository's webhook mutating another stack's deploy-gating state) leading to an unauthorized deploy. This matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly documented and supported configuration), (2) the attacker controlling any repository within one of the onboarded orgs (a very low bar — any developer with push access to a personal or team repo in an onboarded org qualifies, no special Shipit privilege needed), and (3) the victim commit's SHA being obtainable/reproducible (trivial for public repos, and even for private repos if the attacker has any read access or can otherwise learn the SHA). The attacker needs no Shipit session, token, or secret — only ordinary GitHub repository permissions. This is highly feasible and fully repeatable against any commit whose SHA the attacker can reproduce, in any stack tracked by the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` (and `refresh_statuses!`/`create_status_from_github!` call sites) to the repository named in the webhook payload. Require `repository.full_name` in `StatusHandler`'s param schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and filter `Commit.where(sha: params.sha)` further by `stack: { repository_id: repository.id }` (joining through `stacks`) before applying the status — mirroring the pattern already used by `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "cross-repo status forgery flips deployable? for an unrelated stack's commit" do
  victim_stack = shipit_stacks(:shipit)          # repo: shopify/shipit-engine
  attacker_stack = shipit_stacks(:cyclimse)       # repo: attacker-org/attacker-repo (different repository)

  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)
  victim_commit.statuses.create!(stack_id: victim_stack.id, state: "failure")
  refute_predicate victim_commit, :deployable?

  # Forged webhook claims to originate from attacker_stack's repository,
  # but names victim_commit's SHA.
  forged_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => attacker_stack.repository.full_name,
                       "owner" => { "login" => attacker_stack.repository.owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  assert_predicate victim_commit.reload, :deployable?  # BUG: flips true despite failing/unrelated CI

  # Now show this defeats the deploy API's require_ci guard
  post :create, params: {
    stack_id: victim_stack.to_param,
    sha: victim_commit.sha,
    require_ci: true
  }
  assert_response :accepted        # BUG: expected :unprocessable_entity
end
```
This demonstrates both sides of the binding diverging: the webhook's declared `repository.full_name` (attacker's repo) differs from the actual repository backing `victim_commit`'s stack, yet `deployable?`/`require_ci` treat the forged signal as authoritative.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
