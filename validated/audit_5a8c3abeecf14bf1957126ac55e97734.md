### Title
Stack-scoped ApiClient token can read the CCMenu status of any stack, bypassing its `stack_id` restriction - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` lookup method used by every other API controller. The base implementation restricts lookups to the set of stacks the authenticated `ApiClient` is scoped to (`stack_id`), but the CCMenu controller replaces it with an unscoped `Stack.from_param!(params[:stack_id])` call. Any valid `ApiClient` token that only authorizes `read:stack` for one specific stack can therefore be used to fetch the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, etc.) of any stack in the installation, not just the one it was scoped to.

### Finding Description
`Shipit::Api::BaseController` enforces stack scoping for every API endpoint through the `stacks`/`stack` helpers: [1](#0-0) 
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
`require_permission :read, :stack` (used by `CCMenuController`) only checks that the token's `permissions` array contains the string `read:stack`; it never checks whether the requested stack is the one the token is bound to via `ApiClient#stack_id`: [2](#0-1) 
```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
```
The actual per-stack restriction is entirely delegated to the `stacks`/`stack` helper in `BaseController`. However, `Shipit::Api::CCMenuController` defines its own `stack` method that bypasses this scoping: [3](#0-2) 
```
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This lookup queries `Stack` directly (unscoped by the client), so `stack_id?` on the current `ApiClient` is never consulted for this endpoint.

Binding that should hold but is broken: `stack the ApiClient's token authorizes == stack the request touches`.
- Before the attacker's request, an admin creates an `ApiClient` scoped to Stack A (`ApiClient#stack_id = A`, `permissions: ['read:stack']`), intending the token to only expose Stack A's status (e.g., for external monitoring/CI dashboards, mirroring the pattern used by `CCMenuUrlController`/fixture `here_come_the_walrus`, which is deliberately scoped to a single stack: `stack: shipit`).
- After the attacker uses that token against `GET /api/stacks/:stack_id/cc.xml` (or equivalent CCMenu route) with `stack_id` set to Stack B, `CCMenuController#stack` resolves Stack B via the unscoped `Stack.from_param!`, and `require_permission :read, :stack` passes because the token does have the string permission `read:stack` — it just isn't supposed to apply to Stack B. The equality binding "token's authorized stack == accessed stack" no longer holds.

### Impact Explanation
An attacker holding (or having leaked to them) a narrowly-scoped `ApiClient` token — such as one deliberately created with a single-stack scope (`here_come_the_walrus` fixture pattern, and the flow in `CCMenuUrlController#client`) — can read CI/deploy state (build status, build label, lock status, web URL) for every stack managed by the Shipit instance, not just the one the token owner was authorized to see. This is an unauthorized cross-stack information disclosure of stack/deploy state through a valid-but-improperly-scoped credential, matching the "unauthorized read of stack state" category.

### Likelihood Explanation
Any holder of a valid `ApiClient` authentication token with `read:stack` permission (regardless of its intended `stack_id` scope) can exploit this with a single unauthenticated-parameter change (`stack_id` in the URL) — no privilege escalation, signature forgery, or additional credentials are required beyond possessing any one `read:stack`-scoped token. This is trivially reachable via the public `Api::CCMenuController#show` action.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it using the scoped `stacks` helper, e.g. `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot access stacks outside their authorized `stack_id`.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A only: `permissions: ['read:stack']`, `stack_id: <Stack A id>` (mirrors the `here_come_the_walrus` fixture and the `CCMenuUrlController#client` flow).
2. Using that client's `authentication_token` as HTTP Basic auth, send:
   `GET /api/stacks/<Stack-B-owner>/<Stack-B-name>/<Stack-B-env>/cc.xml`
   where Stack B is a different stack the client was never scoped to.
3. Observe that `CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])` (bypassing `current_api_client.stack_id` filtering used everywhere else), `require_permission :read, :stack` passes because the permission string is present, and the response renders Stack B's CI status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`) — data the token was never meant to expose.
