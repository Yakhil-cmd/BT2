### Title
Speculative AA dry-run pollutes global unstable-unit caches with unreverted/racy state - ([File: aa_composer.js])

### Summary
`network.js`'s `ifOk` handler, reachable for every unit posted by any unprivileged peer, optionally invokes `aa_composer.dryRunPrimaryAATrigger()` for units that trigger a primary AA before the real unit is even saved [3](#0-2) . This dry run calls `handleTrigger()`, which — exactly like the real trigger path — writes speculative unit-props directly into the process-wide caches `storage.assocUnstableUnits` and `storage.assocBestChildren` via `writer.saveJoint()` [4](#0-3) , even though the surrounding DB transaction will be rolled back. Cleanup of these speculative entries is done out-of-band by `revertResponsesInCaches()`, which deletes cache entries by unit id and by object identity in `assocBestChildren` [5](#0-4) [6](#0-5) .

### Finding Description
`forgetUnit()` removes a forgotten unit from `assocBestChildren[parent_unit]` using `_.pull(assocBestChildren[parent_unit], assocUnstableUnits[unit])`, which matches by strict reference equality [7](#0-6) . `revertResponsesInCaches()` in turn captures `objFirstUnit.parent_units` from `storage.assocUnstableUnits[first_unit]` *before* calling `forgetUnit` on every response unit, and only afterwards calls `fixIsFreeAfterForgettingUnit(parent_units)` [8](#0-7) . This mirrors the CWE-416 "use of an object after it is conceptually retired" bug class from the Chrome CVE: a JS object standing in for the freed browser-side struct (here, the in-memory unit-props object) is captured by reference, then the object it points to is deleted from the primary registry (`assocUnstableUnits`), while other structures (`assocBestChildren`, `assocUnstableMessages`, `assocStableUnits`) that were populated in the same speculative write are cleaned up separately and rely on the same in-flight object references still being intact and unique. Because the dry-run path is invoked per newly-received/posted unit without taking the `write` mutex around `writer.saveJoint`'s in-memory mutation (that lock is explicitly commented out as unnecessary for the DB half of the operation) [1](#0-0) , an attacker who posts (or gets accepted for processing) two units that trigger the same or dependent AA addresses in close succession can cause the speculative unit-props objects created for one dry run to still be referenced (e.g. as `assocBestChildren` children, or as `stateVars`/`assocBalances` snapshots reused via `arrPreviousAAResponses`) while a second, concurrently-running trigger evaluation reads `storage.assocUnstableUnits` / `assocStableUnits` for the same address to decide balances, `count_aa_responses`, `is_free`, and best-parent/witnessed-level computations [9](#0-8) . If the reverting deletion in `forgetUnit`/`revertResponsesInCaches` runs against a version of the object graph that has already been mutated or replaced by the second, concurrently-running trigger evaluation, the `_.pull` identity check silently fails to remove the stale reference, leaving a dangling unit-props object reachable from `assocBestChildren` after it has been "freed" from `assocUnstableUnits`. Because `assocBestChildren` and `assocUnstableUnits` feed directly into main-chain/witness-level determination logic (`determineWitnessedLevelAndBestParent`, `markMcIndexStable`) [10](#0-9) [11](#0-10) , a stale/duplicated reference can cause different nodes (or the same node on retried validation) to compute different best-parent/main-chain results for the same real unit set, i.e. a stability/validity disagreement.

### Impact Explanation
If exploitable, this leads to node disagreement on unit stability/validity classification (via corrupted `assocBestChildren`/`assocUnstableUnits` used for main-chain determination), which is one of the accepted high-impact outcomes (nodes unable to agree on validity/stability). It could also cause an AA's balance/state calculations during a dry run to leak into or be confused with a concurrently-processed real trigger, potentially causing incorrect AA fund accounting.

### Likelihood Explanation
**Uncertain / low-to-moderate confidence.** The trigger condition (`conf.bDryRunNewTriggers`) gates this code path, and I could not fully verify from the indexed code whether this flag is enabled by default, nor could I conclusively determine whether a higher-level mutex (e.g., a global `["write"]` lock taken elsewhere, outside the snippets I could inspect) fully serializes dry runs against real AA-trigger execution and against each other. Without confirming the absence of such serialization, I cannot assert with confidence that the race is genuinely reachable by an unprivileged unit poster in production configuration.

### Recommendation
- Confirm and, if necessary, enforce that `dryRunPrimaryAATrigger`/`estimatePrimaryAATrigger` and the in-memory cache mutations performed by `writer.saveJoint` (`assocUnstableUnits`, `assocBestChildren`, `assocUnstableMessages`) are always executed under a single mutex (e.g. `["write"]`) shared with the real AA-trigger execution path (`handleAATriggers`) and with `markMcIndexStable`/`forgetUnit`, so no other code can observe or mutate these caches mid-speculation.
- In `revertResponsesInCaches`/`forgetUnit`, avoid relying on reference identity (`_.pull` by object) to clean up `assocBestChildren`; key removals by unit id instead so a stale duplicate object reference cannot survive rollback.
- Consider isolating dry-run cache mutations into a shadow/local structure rather than writing directly into the global `storage.assocUnstableUnits`/`assocBestChildren` maps, only merging into the global caches after the corresponding unit is actually committed.

### Proof of Concept
I could not construct a concrete, verified proof-of-concept within the available exploration budget: doing so would require confirming (a) that `conf.bDryRunNewTriggers` is enabled, (b) the exact mutex coverage of `writer.saveJoint`'s in-memory cache writes relative to `handleAATriggers`/`markMcIndexStable`, and (c) a concrete sequence of two units/AA triggers that provably causes `_.pull` identity mismatch in `assocBestChildren`. These require deeper, session-based tracing (e.g. running the test suite with added race instrumentation) than is available in this read-only investigation.
