## Analog Found [1](#0-0) [2](#0-1) 

### Title
Loss of unread pending HRMP messages when a channel participant unilaterally closes the channel via `hrmp_close_channel` - (File: `polkadot/runtime/parachains/src/hrmp.rs`)

### Summary
`Hrmp::close_channel` can be triggered by *either* participant of an HRMP channel (sender or recipient) via the public dispatchable `hrmp_close_channel`. At the following session boundary, `process_hrmp_close_channel_requests` unconditionally calls `close_hrmp_channel`, which removes `HrmpChannelContents` for that channel without checking whether the counterparty's messages in that channel have actually been read/watermarked by the recipient. This is directly analogous to the `MessageProxy.removeConnectedChain` bug: a channel-tear-down primitive deletes state that may still hold pending, unprocessed cross-chain messages (which may encode asset/token transfers), with no pending-message check or pause step before the irreversible removal.

### Finding Description
`hrmp_close_channel` allows any participant of a channel to request closure:
```
fn close_channel(origin: ParaId, channel_id: HrmpChannelId) -> Result<(), Error<T>> {
    ensure!(channel_id.is_participant(origin), Error::<T>::CloseHrmpChannelUnauthorized);
    ...
    HrmpCloseChannelRequests::<T>::insert(&channel_id, ());
    HrmpCloseChannelRequestsList::<T>::append(channel_id.clone());
    ...
}
``` [3](#0-2) 

`channel_id.is_participant(origin)` is satisfied by either the sender or the recipient parachain — i.e., the recipient alone can request closure of a channel that the sender is actively using to deliver messages. At the next session change, `process_hrmp_close_channel_requests` calls `close_hrmp_channel` unconditionally for every queued closure request:
```
fn close_hrmp_channel(channel_id: &HrmpChannelId) {
    if let Some(HrmpChannel { sender_deposit, recipient_deposit, .. }) = HrmpChannels::<T>::take(channel_id) {
        T::Currency::unreserve(...);
        T::Currency::unreserve(...);
    }
    HrmpChannelContents::<T>::remove(channel_id);
    ...
}
``` [2](#0-1) 

`HrmpChannelContents` holds the messages sent over the channel that have not yet been pruned/read by the recipient (pruning normally happens as the recipient parachain advances its HRMP watermark, consuming messages block by block, as seen in `enqueue_inbound_horizontal_messages` on the Cumulus side [4](#0-3) ). Nothing in `close_channel`/`close_hrmp_channel` checks whether all of the sender's outstanding messages in the channel have already been watermarked/consumed by the recipient before the content is wiped. This mirrors the external report exactly: a "remove chain/connection" primitive deletes queue state without verifying no pending/unprocessed messages remain, and there is no local "pause" step before the irreversible removal, as recommended in the original finding.

Unlike `MessageProxy.removeConnectedChain` (owner-only), here the entry point is *not privileged* — any parachain, acting for itself as one of the two channel participants, can call `hrmp_close_channel` (via `hrmp.hrmpCloseChannel` extrinsic/XCM `HrmpControl`) to close a channel the other side is actively sending on, causing loss of the other side's in-flight, unread messages (which per the implementers-guide can encode arbitrary XCM including asset transfers).

### Impact Explanation
If a sender has queued/sent HRMP messages (e.g., XCM `ReserveAssetDeposited`/`TransferAsset` instructions triggering an asset transfer) that the recipient parachain has not yet watermarked/processed, the recipient (or even the sender itself, in a self-inflicted scenario) can trigger channel closure. On session change, `HrmpChannelContents` for the channel is deleted outright. Any messages within that content that had not been individually read/processed by the recipient's runtime are permanently lost with no delivery, no revert, and no compensating event describing the lost payload — matching the "Loss of pending messages" impact class of the referenced finding (Medium, per the code4rena judge's assessment of the analogous SKALE finding).

### Likelihood Explanation
This does not require any privileged role: it only requires being a registered parachain that participates in an HRMP channel and issuing `hrmp_close_channel`, which is a normal, permitted operation. A parachain (attacker-controlled recipient, or a compromised/rogue collator set for a parachain) can close the channel opportunistically right after the counterparty sends assets/messages but before they've been consumed, guaranteeing loss of that specific message. This requires coordination/timing but no elevated permissions beyond ordinary para-to-relay dispatch rights.

### Recommendation
Before enacting `close_hrmp_channel`, check whether `HrmpChannelContents` for the channel still has un-watermarked/unprocessed messages for the recipient; if so, either defer/refuse the closure, or explicitly drain/deliver-then-purge, and emit an event listing dropped message count/data so integrators (e.g., asset-transfer XCM senders) can react. Alternatively, require that closure requests only take effect once the recipient's HRMP watermark has advanced past all currently queued messages in that channel.

### Proof of Concept
No live/mocked-authority-free integration test was executed as part of this analysis (limited to static code reading, no filesystem/terminal access in this session). The referenced code paths were confirmed via source inspection only:
- `close_channel` allowing recipient-only closure: [5](#0-4) 
- unconditional `HrmpChannelContents::<T>::remove` on close with no pending-message check: [6](#0-5) 
- Existing test `close_channel_works` only asserts the channel disappears after session change; it does not exercise the case where unread messages exist in `HrmpChannelContents` at closure time, so the current test suite does not cover/guard against this loss scenario: [7](#0-6) 

A concrete reproduction would require: (1) open and accept an HRMP channel between two paras, (2) have the sender para queue an outbound HRMP message (e.g., an XCM asset transfer) that lands in `HrmpChannelContents` but is not yet watermarked by the recipient, (3) have the recipient call `hrmp_close_channel` before consuming that message, (4) run to the next session boundary, and (5) assert the message content is gone from `HrmpChannelContents` and was never delivered/executed on the recipient side. This reproduction was not executed in this session; it is proposed as the minimal integration test to confirm the loss, using `polkadot/runtime/parachains/src/hrmp/tests.rs` harness patterns.

	/// This includes returning the deposits.

	/// This function is idempotent, meaning that after the first application it should have no
	/// effect (i.e. it won't return the deposits twice).
	fn close_hrmp_channel(channel_id: &HrmpChannelId) {
		if let Some(HrmpChannel { sender_deposit, recipient_deposit, .. }) =
			HrmpChannels::<T>::take(channel_id)

			T::Currency::unreserve(

				recipient_deposit.unique_saturated_into(),
			);

			}

			if let Ok(i) = v.binary_search(&channel_id.sender) {

			}

	fn close_channel(origin: ParaId, channel_id: HrmpChannelId) -> Result<(), Error<T>> {
		// check if the origin is allowed to close the channel.
		ensure!(channel_id.is_participant(origin), Error::<T>::CloseHrmpChannelUnauthorized);

		// check if the channel requested to close does exist.
		ensure!(
			HrmpChannels::<T>::get(&channel_id).is_some(),
			Error::<T>::CloseHrmpChannelDoesntExist,
		);

		// check that there is no outstanding close request for this channel
		ensure!(
			HrmpCloseChannelRequests::<T>::get(&channel_id).is_none(),
			Error::<T>::CloseHrmpChannelAlreadyUnderway,
		);

		HrmpCloseChannelRequests::<T>::insert(&channel_id, ());
		HrmpCloseChannelRequestsList::<T>::append(channel_id.clone());

		let config = configuration::ActiveConfig::<T>::get();
		let opposite_party =
			if origin == channel_id.sender { channel_id.recipient } else { channel_id.sender };

		Self::send_to_para(
			"close_channel",
			&config,
			opposite_party,
			Self::wrap_notification(|| {
				use xcm::opaque::latest::{prelude::*, Xcm};
				Xcm(vec![HrmpChannelClosing {
					initiator: origin.into(),
					sender: channel_id.sender.into(),
					recipient: channel_id.recipient.into(),
				}])
			}),
		);

		Ok(())
	}

#[test]
fn close_channel_works() {
	let para_a = 2005.into();
	let para_b = 2002.into();
	let para_b_origin: crate::Origin = 2002.into();

	new_test_ext(GenesisConfigBuilder::default().build()).execute_with(|| {
		register_parachain(para_a);
		register_parachain(para_b);

		run_to_block(5, Some(vec![4, 5]));
		Hrmp::init_open_channel(para_a, para_b, 2, 8).unwrap();
		Hrmp::accept_open_channel(para_b, para_a).unwrap();

		run_to_block(6, Some(vec![6]));
		assert!(channel_exists(para_a, para_b));

		// Close the channel. The effect is not immediate, but rather deferred to the next
		// session change.
		let channel_id = HrmpChannelId { sender: para_a, recipient: para_b };
		Hrmp::hrmp_close_channel(para_b_origin.into(), channel_id.clone()).unwrap();
		assert!(channel_exists(para_a, para_b));
		Hrmp::assert_storage_consistency_exhaustive();

		// After the session change the channel should be closed.
		run_to_block(8, Some(vec![8]));
		assert!(!channel_exists(para_a, para_b));
		Hrmp::assert_storage_consistency_exhaustive();
		assert!(System::events().iter().any(|record| record.event ==
			MockEvent::Hrmp(Event::ChannelClosed {
				by_parachain: para_b,
				channel_id: channel_id.clone()
			})));
	});
}
