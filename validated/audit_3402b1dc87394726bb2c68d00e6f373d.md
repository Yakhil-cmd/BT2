Based on my investigation, the strongest local admission-boundary analog to the Boot Finance report is in the Aptos multisig transaction prologue, where a feature-gated check controls whether the payload that actually executes is bound to the payload the owners actually approved.

### Title
Multisig executed payload is not bound to the approved payload unless a feature flag is enabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the Move function invoked by the VM prologue for every multisig transaction [1](#0-0) , is supposed to guarantee that the entry function/script that is about to execute is exactly what the multisig owners approved. This binding is only enforced when the feature `abort_if_multisig_payload_mismatch_enabled` is turned on and the on-chain transaction was created with a full stored payload.

### Finding Description
When an owner creates a multisig transaction with the full payload stored on-chain (as opposed to only a hash), `transaction.payload_hash` is `None`, so the hash-comparison branch is skipped [2](#0-1) . The only remaining check that could bind the approved payload to the payload that is about to execute is:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [3](#0-2) 

This assertion is entirely gated behind `features::abort_if_multisig_payload_mismatch_enabled()`. If that feature is not enabled, the comparison never runs, and the VM proceeds to execute whatever `TransactionExecutableRef` was submitted with the transaction — reconstructed as `provided_payload` on the Rust side in `run_multisig_prologue` [4](#0-3)  — rather than the payload the owners actually voted on and stored via `create_transaction`.

The rest of `validate_multisig_transaction` only checks account existence, owner membership, sequence number, and approval-count/timelock [5](#0-4)  — none of which constrain *what* gets executed, only *whether enough owners approved something*.

### Impact Explanation
This breaks the "approval set binds to the intended action" admission invariant: quorum approvals collected for payload A can be used by any executing owner to run payload B instead, as long as the feature gate is off and the transaction was stored with a full payload (not just a hash). This is a wrong-approval-set / execution-content confusion at the transaction admission boundary — functionally the same bug class as the original report (a value that governs the arbitrage/execution semantics is decoupled from what participants actually agreed to), but here manifesting as unauthorized state transitions (arbitrary entry function execution) under a multisig account's authority rather than a price/arbitrage issue.

### Likelihood Explanation
The likelihood is directly proportional to whether `abort_if_multisig_payload_mismatch_enabled` is active on a given network/deployment. I was not able to fully confirm from the available index whether this feature is enabled by default in the current mainnet feature set (the feature list and defaults live in `types/src/on_chain_config/aptos_features.rs` and `aptos-move/aptos-release-builder/src/components/feature_flags.rs`, which I found references to but could not fully inspect within the available search budget). If the feature is still disabled on any live network, this is directly exploitable by any owner with enough votes for a payload of their choosing to instead execute an entirely different payload.

### Recommendation
Make the payload-match assertion unconditional (not feature-gated) whenever a full payload is stored on-chain, or, until the feature can be safely defaulted on everywhere, treat `create_transaction` (full-payload mode) as deprecated in favor of `create_transaction_with_hash`, which always performs a hash-based binding check regardless of feature state.

### Proof of Concept
1. Owner A calls `create_transaction(owner_a, multisig_account, payload_transfer_1_APT)`, which stores the full payload and implicitly records A's approval.
2. Owners B and C call `approve_transaction` until quorum is reached for that sequence number.
3. Instead of submitting a transaction whose `TransactionExecutableRef` matches `payload_transfer_1_APT`, executing owner D (or A) submits a transaction referencing `multisig_address`/`sequence_number` but with a *different* executable, e.g. `payload_transfer_all_funds_to_D`.
4. In `run_multisig_prologue`, `provided_payload` is derived from this attacker-chosen executable [6](#0-5) .
5. `validate_multisig_transaction` checks quorum/timelock/owner status successfully, and — because `abort_if_multisig_payload_mismatch_enabled` is off and `payload_hash` is `None` — never compares `provided_payload` to the stored payload [3](#0-2) .
6. The VM proceeds to execute `payload_transfer_all_funds_to_D` under the multisig account's authority, even though owners only approved `payload_transfer_1_APT`.

Note: I could not confirm from the indexed code whether this feature flag defaults to enabled on current Aptos mainnet; this should be verified in a full checkout before treating this as exploitable in production.

```rust
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
