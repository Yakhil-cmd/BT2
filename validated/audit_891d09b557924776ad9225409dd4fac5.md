### Title
Duplicate leaves in `r of set` / `weighted and` allow a single signature to satisfy multiple slots, inflating the effective signer count/weight - ([File: definition.js])

### Summary
The reported Folks Finance bug is a "collateral inflation via un-deduplicated array" bug class: a single real event (a zero-amount deposit) is allowed to push the *same* `poolId` into `loan.colPools` multiple times, and the downstream aggregator (`getLoanLiquidity`) sums over the array without deduplicating, so one real collateral balance gets counted N times. The root cause is (1) no uniqueness check when appending to a list that represents "distinct contributing items," and (2) an aggregator that trusts the list's cardinality as if it always represented distinct items.

The same bug class is reachable in `ocore` address-definition evaluation. `r of set` and `weighted and` operators in `validateDefinition`/`validateAuthentifiers` (`definition.js`) accept a `set` array of sub-expressions without checking for duplicate/equivalent entries, and count "the number of options with a matching signature" or "weight of options with a matching signature" by iterating that array positionally. Because each set member is evaluated at its own path (`path+'.'+index`), an author can supply the *same* underlying signature (over the *same* unit hash, valid for the *same* pubkey) at two different paths corresponding to two duplicate `['sig', {pubkey: X}]` (or `['address', addr]`) leaves in the set. This lets a single key satisfy two (or more) slots of an `r of set`/`weighted and` threshold, exactly mirroring the "one real deposit counted N times" pattern from the report.

### Finding Description
`validateDefinition` in `definition.js` validates the *shape* of `r of set` and `weighted and` but never checks that the `set` array's elements are distinct: [1](#0-0) [2](#0-1) 

Both blocks only check length constraints (`args.set.length < 2`, `args.required <= args.set.length` / `<= total_weight`) — they never reject a `set` containing two structurally identical (or semantically equivalent, e.g. same pubkey/address) sub-definitions.

At verification time, `validateAuthentifiers` walks the same `set` array and, for each index, independently evaluates the sub-expression against `assocAuthentifiers[path]`, where `path` is `r.0`, `r.1`, etc. (index-derived, not content-derived): [3](#0-2) 

The actual signature check for a `sig` leaf verifies the *unit hash* against the given `pubkey`, independent of `path`: [4](#0-3) 

Because `ecdsaSig.verify(objValidationState.unit_hash_to_sign, signature, args.pubkey)` only depends on the fixed unit hash and the leaf's `pubkey`, if the address definition contains `['r of set', {required: 2, set: [['sig', {pubkey: A}], ['sig', {pubkey: A}], ['sig', {pubkey: B}]]}]` (pubkey `A` duplicated), a single signature made once by key `A`, submitted twice — once as authentifier at path `r.0` and once at path `r.1` (both are the same signature value, since it's a signature over the same unit hash) — satisfies both `set` members. `count_options_with_sig` becomes 2 even though only one distinct private key participated, satisfying `required=2` with what is effectively 1-of-2 real signers. `weighted and` has the analogous flaw: duplicate `{value: ['sig', {pubkey: A}], weight: w}` entries let one key contribute its weight multiple times, defeating the intended multi-party weight threshold.

This exactly parallels the Folks Finance bug: `increaseCollateral` pushes a `poolId` into `colPools` without deduplication, and `getLoanLiquidity` sums positionally over `colPools` trusting each entry represents independent collateral — inflating one real deposit into N. Here, `set` entries are analogous to `colPools` entries, and `count_options_with_sig`/`weight_of_options_with_sig` is the analogous naive summation that trusts each positional slot represents an independent signer.

### Impact Explanation
An `r of set`/`weighted and` address (including shared/multisig wallets, AA-controlled definitions accepting nested definitions, or asset `issue_condition`/`transfer_condition` definitions using these operators) is meant to enforce that at least `required` *distinct* parties (or a combined weight from distinct parties) authorize a spend. If an attacker can construct — or a victim is tricked into using — a definition with duplicate `sig`/`address` leaves in the `set`, the true security threshold collapses: a single compromised or colluding key can pass a 2-of-3 (or higher) threshold alone. This directly enables unauthorized spending of funds controlled by such an address, i.e., concrete unauthorized spending of user/multisig funds — a direct violation of the payment-authorization guarantees `ocore` is supposed to provide.

### Likelihood Explanation
Reachability requires an attacker (or definer) to be able to post an address definition — this is a normal, unprivileged operation open to any address author or AA author, and `validateDefinition` does not reject duplicate set members. The only precondition is that a shared/multisig address be defined with a `set` containing duplicate signer leaves (which passes all current structural checks). Since users/wallets construct these definitions themselves (e.g., `wallet_defined_by_addresses.js`, `wallet_defined_by_keys.js`), a malicious cosigner proposing a shared-address definition, or a buggy/malicious wallet UI, could silently include a duplicate leaf, after which that single cosigner effectively controls the threshold alone. This is a realistic, unprivileged, network-reachable path, though it does require the victim/other cosigners to accept and sign under such a definition (a social/UX precondition rather than a purely on-chain one), placing likelihood at Medium.

### Recommendation
In `validateDefinition` (`definition.js`), when validating `r of set` and `weighted and`, reject `set` arrays containing duplicate or semantically-equivalent sub-expressions (e.g., normalize/serialize each `arg`/`arg.value` and ensure all serializations are unique) before allowing the definition to be considered valid. This closes the gap symmetric to deduplicating `colPools` in the reported bug, ensuring that `required`/`weight` thresholds always correspond to genuinely distinct signer paths.

### Proof of Concept
Not executed (no local test harness/tool access in this session); the vulnerable mechanism is demonstrated purely via static code inspection above — `validateDefinition`'s `r of set`/`weighted and` cases perform no set-uniqueness check, and `validateAuthentifiers`'s per-index evaluation combined with `sig`'s path-independent `ecdsaSig.verify` confirms that a duplicated leaf can be satisfied twice by one signature. A concrete PoC would construct an address with definition `['r of set', {required: 2, set: [['sig', {pubkey: A}], ['sig', {pubkey: A}], ['sig', {pubkey: B}]]}]`, sign a unit with only key `A`, and supply that single signature as the authentifier for both `r.0` and `r.1` paths, then observe the unit validates successfully despite only one distinct key participating.
