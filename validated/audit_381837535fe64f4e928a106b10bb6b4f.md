### Title
Webhook signature verification keys off `repository.owner.login` while all event handlers act on `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using the `repository.owner.login` (or `organization.login`) field of the JSON payload [1](#0-0) . However, every webhook handler that actually mutates state resolves the target `Repository`/`Stack` from a **different** payload field, `repository.full_name` [2](#0-1) . Because Shipit supports multiple GitHub organizations, each configured with its own independent `webhook_secret` [3](#0-2) , the field used to pick the verification key (`owner.login`) is never cross-checked against the field used to select which repository/stack is acted upon (`full_name`). This is the same class of bug as the PoolTogether report: a signed/verified quantity (here, the organization whose secret authenticates the request) diverges from the quantity actually acted upon (the repository the handlers write to).

### Finding Description
The verification step:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

only binds the HMAC signature to the organization named in `repository.owner.login`. Once verification passes, `create` dispatches the *entire raw payload* to every registered handler for the event type [5](#0-4) . Handlers such as `PushHandler` never look at `repository.owner.login`; they resolve the affected stacks purely from `repository.full_name`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) [6](#0-5) 

The same pattern repeats in every pull-request/status/check-suite handler, all of which derive the target repository from `params.repository.full_name` independent of the signing organization [7](#0-6) .

**Root cause**: the binding `verified_organization == acted_repository.owner` is never enforced. An attacker who legitimately controls one Shipit-configured GitHub organization (and thus legitimately knows/derives that organization's `webhook_secret`, since they administer their own org's GitHub App/webhook settings) can craft a raw payload where:
- `repository.owner.login` = their own organization (so `verify_signature` selects their own known secret and the HMAC checks out), and
- `repository.full_name` = `victim-org/victim-repo` (an entirely different, unrelated organization/stack configured in the same Shipit instance).

Because the two fields are never cross-validated, the forged payload is accepted and dispatched to handlers that act on `victim-org/victim-repo`.

### Impact Explanation
This breaks the equality: *organization whose secret authenticated the request == repository the engine writes to*. An attacker owning one organization's webhook secret can forge `push` events (triggering `GithubSyncJob`/deploy pipeline synchronization), `status`/`check_suite` events (falsifying CI state used for merge-queue/deploy gating), and `pull_request` events (opening/closing/labeling review stacks, archiving/unarchiving stacks) for a stack that belongs to a completely different, unrelated organization. Depending on downstream logic (e.g., commit statuses feeding `required_statuses`/`blocking_statuses` used to gate deploys via the merge queue), this can lead to an unauthorized deploy or manipulation of another team's release pipeline — matching the "unauthorized deploy" High/Critical impact bucket.

### Likelihood Explanation
Exploitation only requires knowledge of a webhook secret for **any one** of the organizations configured in the Shipit instance — which an unprivileged external party can obtain legitimately by being the administrator of their own organization's GitHub App/webhook integration pointed at the shared Shipit instance (a common multi-tenant configuration, as shown by the documented multi-org `secrets.yml` schema). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required. The attack payload is a simple, unauthenticated JSON body sent to the public `/github/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), after signature verification, assert that the organization used to select the signing key (`repository_owner`) matches the owner implied by `repository.full_name` (and `organization.login` where present) before dispatching to handlers. Reject the request (422) on mismatch. Equivalent to fixing the double-counting bug by ensuring the verified field and the acted-upon field always refer to the same entity.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S_A`, known to the attacker) and `victim-org` (secret `S_V`, unknown to the attacker), per the documented multi-org config [3](#0-2) .
2. Craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist on victim stack>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Sign the raw body with `S_A` (known) and send it with `X-Hub-Signature` and `X-Github-Event: push` to the Shipit webhooks endpoint.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `S_A` [1](#0-0) .
5. `create` dispatches the payload to `PushHandler`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` and triggers `sync_github` on the victim's stack [8](#0-7) , despite the attacker never possessing `victim-org`'s webhook secret.

Note: I could not fully retrieve `lib/shipit.rb#github` (the org→config lookup) in this session due to search-result truncation; its behavior is inferred from `webhooks_controller.rb`'s use of `Shipit.github(organization: repository_owner)`, the `GithubOrganizationUnknown` rescue path, and the documented multi-org secrets schema. A full read of `lib/shipit.rb` would be advisable to confirm exact lookup/normalization (e.g., case-folding of org names) before remediation.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      Rails.logger.info([
