### Title
Unbounded per-AA `aa_balances` growth via spam-asset triggers causes unmetered balance-load query during consensus-critical AA execution - (File: aa_composer.js)

### Summary
Any user can permissionlessly trigger an Autonomous Agent (AA) by sending a payment of an arbitrary asset to its address. Each novel asset sent creates a new row in the `aa_balances` table for that AA. On every subsequent trigger, `updateInitialAABalances` unconditionally loads *all* asset balances ever accumulated for the AA with an unbounded, unfiltered query, regardless of how many assets the current trigger actually involves. Because AA-trigger processing runs synchronously and deterministically inside main-chain stabilization on every full node, an attacker can grow this per-address balance set arbitrarily, imposing unbounded, unmetered per-trigger cost on all nodes.

### Finding Description
When a unit pays into an AA address, `getTrigger` builds the trigger and `handleTrigger` is invoked to execute the AA logic [1](#0-0) . As part of every invocation, `updateInitialAABalances` runs:

```
conn.query(
    "SELECT asset, balance FROM aa_balances WHERE address=?",
    [address],
    function (rows) { ... }
``` [2](#0-1) 

This query has no limit and no filter on the assets relevant to the current trigger — it loads and iterates over the *entire* balance set the AA has ever held, building `objValidationState.assocBalances[address]` from all rows before continuing to insert/update balances for any new assets in the trigger [3](#0-2) .

Crucially, whenever a payment includes an asset the AA has never received before, a brand-new row is permanently inserted into `aa_balances` for that address:
```
var arrNewAssets = _.difference(arrAssets, arrExistingAssets);
if (arrNewAssets.length > 0) {
    ...
    conn.addQuery(arrQueries, "INSERT INTO aa_balances (address, asset, balance) VALUES "+arrValues.join(', '));
}
``` [3](#0-2) 

There is no cap on the number of distinct assets that can be registered against a single AA address — any attacker can, over many blocks/units, send payments in many distinct (previously issued) assets to a target AA, permanently growing its `aa_balances` row count. Every future trigger of that AA — including legitimate user interactions — then pays the cost of the unbounded `SELECT ... WHERE address=?` scan and in-memory reconstruction of `assocBalances`, mirroring the reported Cosmos SDK issue where `GetAllBalances` scans an unbounded, attacker-inflated balance set on every block.

This trigger-handling path is invoked from AA-trigger processing during main-chain stabilization/advance (`main_chain.js` references `handleTrigger`), which is consensus-critical: it is executed identically and synchronously by every full node as part of confirming new units, analogous to `BeginBlock` in the Cosmos report.

### Impact Explanation
Because the cost of the `aa_balances` load scales with the number of distinct assets ever received by the AA, and that number is entirely attacker-controlled and unbounded, an attacker can degrade or stall processing of any specific AA on every node that needs to evaluate a trigger against it. Since this computation occurs deterministically during main-chain stabilization (a consensus-critical, unmetered/non-gas-charged operation from the perspective of the *victim* AA's future callers), a sufficiently inflated `aa_balances` set can make the AA effectively unusable and slow down the node processing pipeline for units touching that AA, which is a shared-resource degradation of the type the "no vulnerability without impact" rules classify as a network-liveness/availability concern for the affected AA path.

### Likelihood Explanation
The attack is fully permissionless: it only requires the attacker to author payment units directing distinct existing assets to a target AA address, spreadable over as many blocks as desired to avoid single-unit message limits (`MAX_MESSAGES_PER_UNIT`). The cost to the attacker is bounded by asset issuance and transaction fees, similar to the original report's PoC, which likewise required funding many distinct token denominations.

### Recommendation
Limit `updateInitialAABalances` (and the underlying `aa_balances` growth) so that per-trigger balance loading only queries/loads the assets relevant to the current trigger and AA logic (e.g., assets referenced in `trigger.outputs` plus assets explicitly referenced by the AA's `balance[...]` formula calls), rather than unconditionally loading the AA's entire historical asset balance set. Additionally, consider capping the number of distinct assets an AA address may accumulate in `aa_balances`, or pruning/ignoring dust-level asset balances that were never part of a real economic interaction with the AA, to bound the growth of `aa_balances` per address.

### Proof of Concept
1. Deploy any AA (or target an already-active AA).
2. Author and post units (across multiple blocks to respect `MAX_MESSAGES_PER_UNIT`) that issue N distinct new assets and send a minimal payment (1 unit each) of each asset to the AA's address, triggering `handleTrigger` → `updateInitialAABalances` each time and permanently inserting N new rows into `aa_balances` for that address [3](#0-2) .
3. Trigger the AA again with a normal payment; observe that `updateInitialAABalances` executes `SELECT asset, balance FROM aa_balances WHERE address=?` [4](#0-3)  and reconstructs `assocBalances` over all N+ rows regardless of relevance to the current trigger, with per-trigger latency growing linearly with N — reproducing the "unmetered iteration scaling with attacker-controlled balance-set size" pattern from the reference report, but here occurring during ocore's consensus-critical AA-trigger execution invoked on every node.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
