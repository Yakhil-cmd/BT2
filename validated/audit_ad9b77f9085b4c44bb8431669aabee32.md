### Title
Cross-stack CI status forgery bypasses per-repository binding, enabling an unauthorized production deploy - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects and verifies the HMAC signature using the GitHub organization/App keyed by `params.dig('repository', 'owner', 'login')` [1](#0-0) , but the `status` event handler, `Shipit::Webhooks::Handlers::StatusHandler`, never checks the `repository` field at all — it only requires `sha` and `state` and looks up commits by `Commit.where(sha: params.sha)` across the *entire* database [2](#0-1) . The organization whose secret authenticated the request is never bound to the repository/stack whose commit status actually gets mutated.

### Finding Description
This mirrors the Mochi bug class: a value used to satisfy a verification step (the discounted debt used inside the signature/authorization path) is decoupled from the value that the mutation actually operates on (the undiscounted `_usdm`). Here the analog binding is: **organization that authenticated == repository that is written**, and it is broken.

- `verify_signature` derives `repository_owner` from the payload and asks `Shipit.github(organization: repository_owner)` for that org's `webhook_secret`, then HMAC-verifies the raw payload against it [3](#0-2) . This only proves the payload was signed by *some organization configured in Shipit* — the one named in `repository.owner.login` — nothing more.
- Once verified, `WebhooksController#create` dispatches the *entire raw payload* to every registered handler for the event type, with no re-validation tying the payload to that same organization/repository [4](#0-3) .
- `StatusHandler` (registered for the `status` event) only declares `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` as its schema — it has **no `repository` requirement** and never calls `Repository.from_github_repo_name` or otherwise scopes to the signing organization, unlike every other handler (`PushHandler`, all `PullRequest::*Handler`s) which explicitly call `Repository.from_github_repo_name(params.repository.full_name)` via the base `Handler#stacks`/`#repository_name` helpers [5](#0-4) . Instead it does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) .
- Setting a commit's status to `success` triggers `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` if `commit.deployable?` and `stack.continuous_deployment?` and `stack.deployable?` [7](#0-6) [8](#0-7) .

Because commit SHAs are 40-hex-character git hashes that are public information (visible on GitHub for any repo), an attacker who legitimately controls a *different* GitHub organization that has its own GitHub App configured in Shipit (a normal, supported multi-tenant configuration, as shown by `config/secrets.development.shopify.yml` listing multiple independently-configured orgs each with their own `webhook_secret`) can:
1. Look up the current HEAD SHA of a victim stack's tracked branch (public GitHub data).
2. Send a `status` webhook to Shipit's `/webhooks` endpoint, correctly signed with their *own* org's `webhook_secret`, with `repository.owner.login` set to their own org (so `verify_signature` passes), but `sha` set to the victim's commit SHA and `state: "success"`.
3. `StatusHandler` finds the victim's `Commit` purely by SHA match (ignoring which org/repo actually owns it) and marks it `success`.
4. If the victim stack has `continuous_deployment` enabled and the commit is otherwise deployable, this schedules and runs an actual, unauthorized production deploy.

### Impact Explanation
This crosses the credential/repository trust boundary explicitly called out in scope: an organization's authenticated identity (via its own `webhook_secret`) is used to affect a repository/stack it has no relationship to, resulting in an **unauthorized deploy** — one of the listed Critical-tier impacts. It requires no session, `ApiClient` token, or GitHub App private key from the victim — only that the attacker administers *any* org/App independently registered in Shipit's multi-tenant `github` configuration, which is the documented, supported deployment model (multiple orgs listed side by side in `config/secrets.development.shopify.yml`).

### Likelihood Explanation
Moderate-to-high in any Shipit deployment that supports more than one GitHub organization (the engine's own example secrets file shows this as an intended configuration), and where at least one victim stack has `continuous_deployment` enabled. The attacker needs no privileged access to the victim's repository — only knowledge of its public commit SHAs and control of any other configured tenant org's webhook secret, both of which are easy to obtain.

### Recommendation
Bind the `status` handler (and any other handler that mutates state) to the organization that authenticated the request. Require and validate `repository.full_name`/`repository.owner.login` in `StatusHandler`, and scope the `Commit` lookup through `Repository.from_github_repo_name(...).stacks` (as `PushHandler` and the `PullRequest` handlers already do), rejecting or ignoring statuses whose repository does not belong to the organization that produced a valid signature.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (supported multi-tenant config, per `config/secrets.development.shopify.yml`).
2. Attacker obtains the public HEAD SHA of a commit on a `victim-org` stack with `continuous_deployment: true`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{ "sha": "<victim-commit-sha>", "state": "success", "context": "ci/attacker", "repository": { "owner": { "login": "attacker-org" } } }
```
signed with `attacker-org`'s `webhook_secret` in `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature [1](#0-0) .
5. `StatusHandler.call(params)` runs `Commit.where(sha: params.sha)` and finds the victim's commit regardless of which org signed the request, marking it `success` [9](#0-8) , potentially triggering `ContinuousDeliveryJob` for `victim-org`'s stack.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
