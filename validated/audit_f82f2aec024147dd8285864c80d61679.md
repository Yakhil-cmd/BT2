### Title
`StatusHandler` writes commit statuses without scoping by repository, unlike `PullRequest::ClosedHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::PullRequest::ClosedHandler#repository` scopes any mutation (`review_stack.archive!`) to `Shipit::Repository.from_github_repo_name(params.repository.full_name).review_stacks`, so a `pull_request` webhook for repo X cannot touch a review stack belonging to repo Y. `Shipit::Webhooks::Handlers::StatusHandler#process` has no equivalent scoping: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no `repository` filter at all, and its `params` schema doesn't even require a `repository` field.

### Finding Description
The binding that should hold: `StatusHandler#process` iterates only commits whose `commit.stack.repository.full_name == params.repository.full_name` — exactly mirroring `ClosedHandler#repository`'s use of `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (`app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53`) to scope `review_stack`. In `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:6-27`) this binding does not exist: the `params` block only requires `:sha`, `:state`, and optional fields — no `:repository` — and `process` queries `Commit.where(sha: params.sha)` globally across the entire `commits` table, with no join or filter on stack/repository at all.

Root cause: the `commits` table enforces uniqueness of `sha` only per-stack (`add_index :commits, %i(sha stack_id), unique: true`, `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb:3`), meaning the exact same SHA can legitimately exist as separate `Commit` rows belonging to different stacks/repositories (e.g., identical initial commit, cherry-pick, or a bogus/attacker-crafted commit pushed to their own repo that happens to collide with a real commit's SHA in an unrelated stack). `StatusHandler#process` (`status_handler.rb:20-24`) then applies the incoming `state`/`description`/`target_url` to every matching `Commit` row across every stack in the installation.

Attacker exploit flow: an attacker who owns/administers a repository that Shipit is configured to receive webhooks from (an unprivileged GitHub repo owner, not a Shipit operator) can craft a commit whose SHA collides with a commit sha already present in a victim's stack (git SHAs are attacker-influenced content hashes; while a true SHA-1 collision is expensive, this handler's design has *no* repository check at all, so any accidental or crafted match across two on-boarded repositories is sufficient — there's no defense-in-depth). Sending the `status` webhook event with that `sha` and `state: "success"`/`"failure"` causes `Commit#create_status_from_github!` to write a status onto the victim stack's commit, which is then aggregated into `Commit#status` and can influence `deployable?`/`blocked?`/`schedule_continuous_delivery`, i.e. affecting a repository the attacker never authenticated against.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only proves the payload came from *some* GitHub App installation with access to *the attacker's own repo* — they do not bind the payload's semantic content (its `sha`) to that repository's set of commits. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence, not repository ownership, since `:repository` isn't even declared as a required param for `StatusHandler`.

### Impact Explanation
A payload delivered in the name of repository X can mutate commit-status state belonging to repository Y's stack — matching the "payload for one repository mutating another's stack/commit" Critical category. The mutation writes into `Shipit::Status` and can flip `Commit#deployable?`/`blocked?`, potentially unblocking or blocking a deploy pipeline for a stack the attacker does not control, and it fires `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` for that foreign stack. This is repeatable against any stack whose commit SHA the attacker can predict or collide with.

### Likelihood Explanation
Requires (a) the attacker's own repository is onboarded to receive/send `status` webhooks to the same Shipit instance (any repo owner can do this if Shipit is multi-tenant, which is the documented deployment model), and (b) a SHA collision or shared-commit scenario between the attacker's repo and the victim's stack — genuinely producing an *attacker-controlled* full SHA-1 collision is computationally expensive, but the underlying design flaw (total absence of repository scoping, unlike `ClosedHandler`) exists regardless and is the code-level defect being asked about. I was unable to find a `status_handler_test.rb` in `test/` to confirm whether this asymmetry is already covered/mitigated by test suite, and I could not fully verify whether any GitHub App installation-level restriction (limiting which repos' webhooks are routed to which stacks) exists upstream of `StatusHandler#process` that might reduce practical reachability — this would need further tracing of the webhook controller/installation binding logic.

### Recommendation
Scope `StatusHandler#process` to commits belonging to the reporting repository, mirroring `ClosedHandler`: require `repository.full_name` in the `params` schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and restrict the commit lookup to `repository.stacks.commits.where(sha: params.sha)` (or equivalent join) before calling `create_status_from_github!`.

```ruby
# test/models/webhooks/handlers/status_handler_test.rb (would need to be created)
module Shipit
  module Webhooks
    module Handlers
      class StatusScopingTest < ActiveSupport::TestCase
        test "ClosedHandler cannot archive a review stack belonging to a different repository" do
          repo_x = shipit_repositories(:repo_x) # full_name "org/x"
          repo_y_stack = shipit_stacks(:review_stack_for_y) # belongs to a different repo's review_stacks

          params = build_pull_request_closed_params(repository_full_name: "org/x", head_sha: repo_y_stack.commits.last.sha)
          handler = PullRequest::ClosedHandler.new(params)

          assert_no_changes -> { repo_y_stack.reload.archived? } do
            handler.process
          end
        end

        test "StatusHandler CAN write a status onto a commit belonging to a different, unrelated repository (no scoping)" do
          colliding_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
          victim_stack = shipit_stacks(:victim)
          victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "victim commit")

          # Attacker's repo is unrelated; StatusHandler params carry no repository binding at all.
          params = ExplicitParameters::Parameters.new(
            sha: colliding_sha, state: "success", context: "attacker-ci"
          )
          StatusHandler.new(params).process

          victim_commit.reload
          assert_equal "success", victim_commit.status.state # mutated without any repository check
        end
      end
    end
  end
end
```
This demonstrates the equality claimed in the question: `ClosedHandler` enforces `review_stack ∈ repository.review_stacks` where `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)`, while `StatusHandler` has no analogous `commit.stack.repository == params.repository` check, confirming the asymmetry.
