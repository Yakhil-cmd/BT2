### Title
Indivisible (fixed-denomination) NFT-like assets sent to an Autonomous Agent become permanently stuck - ([File: aa_composer.js])

### Summary
Obyte's closest analog to an ERC-721 NFT is an indivisible asset with `fixed_denominations: true` (e.g., denomination-1 assets used as unique, non-fungible coins). Just as the reported Solidity issue shows that using unsafe `mint()` instead of `safeMint()` lets NFTs get permanently trapped in contracts unable to handle them, Obyte's AA execution engine unconditionally strips any outgoing `fixed_denominations` payment message from every response (and bounce) unit an AA can produce. Any unprivileged unit poster can pay such an asset into an AA address, and the AA — even if written specifically to route the asset elsewhere or refund it — cannot ever move it back out.

### Finding Description
When an AA's oscript evaluates its `messages` template and produces payment messages, `sendUnit()` loads the asset info for every non-base payment and explicitly skips completing `fixed_denominations` payloads ("will skip it later") [3](#0-2) . After the evaluation loop, the code filters the message list a second time, unconditionally removing any payment message whose asset `fixed_denominations` is true [2](#0-1) . If this filtering empties the message list, the AA silently "eats" the coins and returns an empty response, still updating balances/state as if it had processed the payment [4](#0-3) .

The same restriction applies to the automatic bounce path: `bounce()` builds refund messages by iterating `trigger.outputs` for every asset the trigger sent, including indivisible ones, and calls `sendUnit(messages)` [5](#0-4) . That call goes through the identical `sendUnit` pipeline, so any indivisible-asset refund message is stripped out before the bounce unit is built, meaning the "refund" unit is emitted without actually returning the NFT-like asset.

Meanwhile, on receipt, the AA's balance table (`aa_balances`) is credited with the fixed-denomination asset just like any other asset via `updateFinalAABalances`/`updateInitialAABalances`, which do not distinguish fixed-denomination assets from divisible ones [6](#0-5) . Validation of the AA definition itself does not forbid AA authors from referencing or trying to transfer `fixed_denominations` assets in their message templates either [7](#0-6) . There is nothing in `validation.js`/`aa_composer.js` that rejects a trigger unit which pays an indivisible asset to an AA address up front — `validateAATrigger` only checks output counts, not asset type [8](#0-7) .

The net effect: an indivisible asset (Obyte's unique/NFT-like token type) sent to any AA address is accepted, credited to the AA's balance, but the AA architecturally cannot ever send it back out — neither through a normal response message nor through the automatic bounce refund. This mirrors the reported ERC-721 issue: using the "unsafe" transfer path (a plain payment output) to a contract-like recipient (an AA) that has no capability to handle/forward that asset type results in permanent loss.

### Impact Explanation
Any indivisible/NFT-like asset paid into an AA address is permanently and irrecoverably locked, regardless of AA author intent (even an AA explicitly trying to forward or refund it cannot succeed, since the message is dropped after evaluation). This is a permanent fund/asset loss for the sender with no path to recovery, satisfying "AA fund loss or freezing."

### Likelihood Explanation
Trivial to trigger: any unprivileged unit poster can simply pay a fixed-denomination asset (self-issued or otherwise) as a payment output to an existing AA address, or an AA definition itself may be written under the false assumption that it can forward/refund an indivisible asset that a user sends it (as several AA templates in the test suite do generically for "any asset" via `trigger.output[[asset!=base]]`, e.g. `bouncer_infinite_cycle.oscript`). No special privileges or race conditions are required.

### Recommendation
Either:
1. Reject trigger units at validation time (`validateAATrigger`) that pay `fixed_denominations` assets to an AA address, forcing wallets/composers to prevent this class of payment before it is even posted, or
2. Modify `sendUnit`/`bounce` in `aa_composer.js` to support sending fixed-denomination assets back out (at least for simple pass-through/refund cases), or at minimum ensure the bounce path fully refunds indivisible assets instead of silently dropping the corresponding message while still consuming the trigger.

### Proof of Concept
1. Issue an indivisible (`fixed_denominations: true`) asset, e.g. a 1-of-1 "NFT" denomination.
2. Deploy any AA (even `just_a_bouncer.oscript` at [9](#0-8) , which is meant to bounce back everything above bounce fees).
3. Send a trigger unit that includes a payment message transferring the indivisible asset coin to the AA's address, together with enough `base` to cover bounce fees.
4. The AA processes the trigger; `updateInitialAABalances` credits the AA's `aa_balances` with the indivisible asset. The bounce/response logic drops any outgoing message for that asset via the `fixed_denominations` filter in `sendUnit` [2](#0-1) .
5. The indivisible asset coin remains in `aa_balances` for that AA address forever; no code path in `aa_composer.js` can ever emit a payment message moving it back out.
