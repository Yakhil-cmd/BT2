### Title
`review_stacks_enabled` kill-switch is bypassable via operator-precedence bug in `ReopenedHandler#unarchive?` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` and the identically-shaped `OpenedHandler#provision?` gate `repository.review_stacks_enabled` only against the `allow_all` branch due to Ruby `&&`/`||` operator precedence, so the `allow_with_label` and `prevent_with_label` branches fire regardless of `review_stacks_enabled`. An unprivileged PR author on a repo where an operator has set `review_stacks_enabled: false` but left `provisioning_behavior: allow_with_label` configured can close/reopen their PR with the label attached and force `ReviewStackAdapter#unarchive!` to re-enqueue the archived stack via `Shipit::ReviewStackProvisioningQueue.add`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == false` should imply "no PR event unarchives or provisions a stack for this repo," for every `provisioning_behavior` value. The code instead evaluates:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`. `review_stacks_enabled` is ANDed only with the first disjunct; the label-based disjuncts are independent of it. The identical structure exists in `OpenedHandler#provision?` [2](#0-1) . By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` over the whole `(archive? || unarchive?)` expression [3](#0-2) , confirming the reopened/opened handlers deviate from the intended guard shape.

Exploit flow: an operator previously allowed review stacks, a stack was created and later archived/deprovisioned (e.g. PR closed) while `provisioning_behavior` remained `allow_with_label`. The operator later sets `review_stacks_enabled = false` intending to fully disable the feature but does not clear `provisioning_behavior`. The attacker (PR author, no Shipit credentials needed — legitimate GitHub webhooks from their own repo) attaches the provisioning label to their own PR, closes it, and reopens it. GitHub emits a real, signed `pull_request` `reopened` webhook. `ReopenedHandler#process` calls `respond_to_pull_request_reopened?` → `unarchive?`, which evaluates true purely from the `allow_with_label? && label_present` disjunct, ignoring `review_stacks_enabled == false` [4](#0-3) . `stack.unarchive!` on `ReviewStackAdapter` then calls `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.unarchive!` inside a transaction [5](#0-4) . `ReviewStackProvisioningQueue.add` sets `awaiting_provision: true` [6](#0-5) , and the background queue worker later calls `stack.provisioner.up` on transition to `provisioning` [7](#0-6) .

Existing guards do not stop this: `drop_unhandled_event`/signature verification are irrelevant since the webhook is a genuine, GitHub-signed event from a repo the attacker legitimately controls; the `ExplicitParameters` schema only validates payload shape, not authorization semantics [8](#0-7) ; and `Repository` model validations don't constrain the `review_stacks_enabled`/`provisioning_behavior` combination [9](#0-8) .

### Impact Explanation
Within this engine's own code, the confirmed effect is: `awaiting_provision` becomes `true` and a `GithubSyncJob` is enqueued for a repository whose operator explicitly disabled review-stack provisioning (`review_stacks_enabled: false`), and the queue worker will subsequently attempt `stack.provisioner.up` [10](#0-9) . Whether this results in actual command execution (`TaskCommands#perform`/`Command#start`/`PTY.spawn`) depends on the concrete `ProvisioningHandler` the host app registers — the engine's own `ProvisioningHandler::Base#up`/`#down` are no-ops by default [11](#0-10) . I could not find code in this engine that itself wires `up`/`down` to `Command`/`PTY.spawn` execution of `shipit.yml` steps, so the "repeated RCE on the deploy host" portion of the question's claim is not directly demonstrable from this engine's code alone — it is conditional on a host-supplied provisioning handler. The directly provable impact is: **an unauthorized state mutation (re-provisioning of a review stack the operator had disabled) for a repository, bypassing the operator's explicit `review_stacks_enabled: false` kill-switch**, repeatable indefinitely (close/reopen) by the PR's own author, matching a High-severity "authorization/config bypass" rather than a confirmed Critical RCE, since the shell-execution link is outside this engine's own code.

### Likelihood Explanation
Preconditions: a repository configured with `review_stacks_enabled: false` while `provisioning_behavior` is still `allow_with_label` (or `prevent_with_label`) — a plausible operator misconfiguration when "disabling" review stacks without also resetting behavior/label settings. The attacker needs only their own PR against such a repository, ability to label it, and to close/reopen it — all ordinary GitHub actions requiring no Shipit credentials. This is inexpensive and fully repeatable.

### Recommendation
Fix the operator precedence in both `ReopenedHandler#unarchive?` [1](#0-0)  and `OpenedHandler#provision?` [2](#0-1)  by parenthesizing `review_stacks_enabled` over the entire OR expression, matching `LabeledHandler#respond_to_label_change?`'s pattern:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add:
```ruby
test "does NOT unarchive when review_stacks_enabled is false, even for allow_with_label with label present" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived (review_stacks_enabled: false)"
  assert_not stack.reload.awaiting_provision, "Expected stack NOT to be re-queued for provisioning"
end
```
Binding assertions: LHS `repository.review_stacks_enabled == false` (operator intent) vs RHS `stack.awaiting_provision == true` (actual re-arm). With current code this test fails — `awaiting_provision` becomes `true` and `archived?` becomes `false` — demonstrating the bypass; after applying the recommended fix, both sides align and the test passes.
