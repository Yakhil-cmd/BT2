### Title
Hand-rolled YAML parser in `extract_frontmatter` fails to strip inline comments, causing `enabled: false` to be treated as truthy and silently activating supposedly-disabled hookify rules — ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` only recognizes full-line comments (`stripped.startswith('#')`) and never strips inline `#` comments from scalar values, unlike real YAML/PyYAML. As a result, an `enabled: false` line with any trailing comment (or extra text) is parsed as the literal string `"false ..."` rather than the boolean `False`, and this non-empty string is truthy when later checked with `if rule.enabled:` in `load_rules`, silently enabling a rule that its author or a reviewer believed was disabled.

### Finding Description
`extract_frontmatter` handles top-level `key: value` lines like this: [1](#0-0) 

The boolean coercion only triggers on an *exact* match of the string `"true"`/`"false"` (after quote-stripping). It does not strip trailing `#` comments the way a real YAML parser does. Comments are only skipped when they occupy an entire line: [2](#0-1) 

So a rule author writing, in perfectly normal YAML style:
```
---
name: temporarily-disabled-check
enabled: false  # disabled pending review
event: stop
action: block
---
```
would have this parsed as `frontmatter['enabled'] == "false  # disabled pending review"` — a non-empty string, not `False`.

Downstream, `Rule.from_dict` just forwards the raw value: [3](#0-2) 

And `load_rules` decides whether to include the rule using plain Python truthiness, not an equality/type check: [4](#0-3) 

Since `"false  # disabled pending review"` is a non-empty string, `if rule.enabled:` evaluates `True`, so the rule is loaded and included in the active rule set — exactly the "hidden Stop-hook rule that was meant to be inert" scenario. `stop.py` then loads all `event='stop'` rules via this same `load_rules` path and feeds them into `RuleEngine.evaluate_rules`: [5](#0-4) 

If such a rule also has `action: block` (as commonly documented) and its condition matches, `RuleEngine.evaluate_rules` returns a hard `"decision": "block"` for the `Stop` event: [6](#0-5) 

This diverges from real YAML semantics: `yaml.safe_load("enabled: false  # disabled pending review\n")` correctly returns `{'enabled': False}` because YAML strips unquoted trailing comments. The hand-rolled parser does not, so a config file that looks inert to any human reviewer (or to a diff-review tool comparing against YAML semantics) is silently active.

Existing checks do not catch this: there is no schema validation, no strict boolean-typing enforcement, and no fallback to reject non-boolean `enabled` values — `load_rule_file` only guards against I/O/type/parse exceptions, not against subtly-wrong types flowing through successfully. [7](#0-6) 

### Impact Explanation
A rule file that a maintainer/reviewer believes is disabled (`enabled: false`) can be silently active due to a trailing comment, causing an unintended Stop-hook rule to fire. Because Stop-hook rules can set `"decision": "block"` with an attacker/author-controlled `reason`/`systemMessage`, this allows unauthorized blocking of session termination and injection of a persistent message back into the agent/user context whenever the Stop event triggers — a trust-boundary bypass of the "config field controls hook enforcement" guarantee that rule authors and reviewers rely on when auditing `.claude/hookify.*.local.md` files.

### Likelihood Explanation
Any `.claude/hookify.*.local.md` file (rule content is ordinary repository/plugin content per the codebase's own docs) that contains a trailing `#` comment after `enabled: false`, or any other formatting a human would consider valid YAML but that isn't exactly the literal `false`/`true` token, triggers this. This is easy to reproduce with a single crafted rule file and requires no special privileges — only the ability to have such a file present/committed and loaded by `load_rules()`.

### Recommendation
Replace the hand-rolled parser with a real YAML parser (`yaml.safe_load`) for frontmatter, or at minimum: (1) strip unquoted inline `#` comments before scalar parsing, (2) make the `enabled` field coercion explicit and fail closed — reject/normalize any value that isn't literally `True`/`False` after parsing (e.g., raise/log and default to `enabled=False` on ambiguous input) instead of relying on Python truthiness of arbitrary strings.

### Proof of Concept
Unit test in `plugins/hookify/core/` test suite:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: should-be-inert
enabled: false  # disabled pending review
event: stop
action: block
pattern: ".*"
---

This should never fire.
"""

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Real YAML semantics (yaml.safe_load) would give enabled == False (bool)
import yaml
yaml_fm = yaml.safe_load(content.split('---', 2)[1])
assert yaml_fm['enabled'] is False

# Hand-rolled parser diverges: enabled is a truthy string, not False
assert fm['enabled'] != False
assert bool(rule.enabled) is True  # BUG: rule is treated as enabled despite "enabled: false"
```
Differential fuzzing extension: generate random frontmatter blocks varying comment placement, quoting, and multi-line dict items for `enabled`/`event`/`action`, run both `extract_frontmatter` and `yaml.safe_load`, and flag any case where `bool(fm.get('enabled'))` differs from `bool(yaml_fm.get('enabled'))`, or where `fm.get('event')`/`fm.get('action')` differ from the YAML-parsed values.
