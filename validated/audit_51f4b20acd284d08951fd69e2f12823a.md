### Title
Cross-Organization Team Membership Hijack via `membership` Webhook `team.id` Lookup Not Scoped to the Verified Organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook only against the GitHub organization named in the payload itself, using that organization's own `webhook_secret`. [1](#0-0)  The `membership` event handler then looks up the `Team` record to mutate solely by the numeric `params.team.id` GitHub team ID, and only sets `team.organization` on record creation — it never checks that the resolved team actually belongs to the organization that was cryptographically verified for this request. [2](#0-1)  This breaks the trust binding: `verified organization == organization owning the team being mutated`.

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` in `Shipit.github(organization:)`. [3](#0-2)  A webhook is accepted as long as its HMAC signature matches the secret for whichever organization is named in the payload (`repository.owner.login` or `organization.login`): [4](#0-3) 

For `membership` events, `Shipit::Webhooks::Handlers::MembershipHandler#process` resolves the `Team` to modify using:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [5](#0-4) 

The lookup key is `github_id` only — it is not scoped to `params.organization.login`, and the `organization` field is only assigned inside the creation block (which only runs when no row exists yet). If a `Team` row with that `github_id` already exists (created earlier for a legitimate, higher-trust organization), a webhook signed for a *different*, attacker-controlled organization will simply fetch that pre-existing `Team` object and call `team.add_member(member)` on it, adding an arbitrary GitHub user (resolved by `User.find_or_create_by_login!(params.member.login)`) to that team — regardless of which organization the request was authenticated for. [6](#0-5) 

`Shipit.github_teams` (used for the entire application's access-control gate `User#authorized?`) is built from teams configured via `github.oauth.teams`, and a user is authorized simply by being a member of one of those `Team` records: [7](#0-6) [8](#0-7) [9](#0-8) 

**Concrete equality broken**: `organization authenticated by HMAC signature` should equal `organization that owns the Team row being written to`. Before the attack, the `Team` with a given `github_id` belongs only to the legitimate org (e.g. `shopify/developers`, configured in `Shipit.github_teams`). After the attacker's crafted, but validly-signed (for their own org), `membership` webhook, that same `Team` row gains a new member controlled by the attacker — with no verification that the numeric team id actually belongs to the organization whose secret signed the request.

### Impact Explanation
This is a real escalation into `Shipit.github_teams` authorization (an explicitly listed High-severity impact): an attacker who is an admin/member of any GitHub organization that has the Shipit GitHub App installed (a normal, low-privilege tenant relationship, not a Shipit session or `ApiClient` token) can trigger a genuine, correctly-signed `membership` webhook from their own org (e.g., by adding themselves to any team in an org they control) with a `team.id` guessed or observed to collide with a privileged team's GitHub numeric ID in another tenant organization. This grants them membership in a `Team` that gates access to the entire Shipit application (`current_user.authorized?`), bypassing GitHub-organization based authentication entirely and gaining full authenticated access to trigger deploys, rollbacks, and view secrets/output for stacks belonging to a different, unrelated organization.

### Likelihood Explanation
Exploitability depends on the deployment being multi-tenant (multiple GitHub organizations configured under `Shipit.github`), which the engine explicitly supports (`Shipit.github(organization:)` is looked up per-org). It further requires the attacker to learn or guess the numeric GitHub team `id` of the privileged team — GitHub team IDs are visible via the public/authenticated GitHub API to team members and are sequential/enumerable, which is a moderate but realistic bar. No Shipit credentials, session, or `ApiClient` token are required at any point — only ordinary GitHub organization membership/admin rights over an org that is already a legitimate tenant of the installation.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject (or re-key) any pre-existing team whose `organization` does not match `params.organization.login`:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  raise ArgumentError, "team/organization mismatch" if team && team.organization != params.organization.login

  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |t|
    t.github_team = params.team
  end
end
```
Additionally, verify that `repository_owner`/`organization.login` used for signature verification exactly matches the organization embedded in every subsequently trusted payload field before mutating cross-tenant records.

### Proof of Concept
1. Shipit is configured with two organizations, `trusted-org` (with `oauth.teams: [trusted-org/admins]`, `Team#github_id = 555`) and `attacker-org` (also has the Shipit GitHub App installed, own `webhook_secret`).
2. Attacker is an owner of `attacker-org` and creates a team there whose GitHub numeric `id` happens to be (or is forced/observed to be) `555`.
3. Attacker adds their own GitHub account to that `attacker-org` team, causing GitHub to send a legitimately HMAC-signed `membership` webhook to Shipit, signed with `attacker-org`'s `webhook_secret`, with payload:
   ```json
   { "action": "added", "team": {"id": 555, "name": "...", "slug": "...", "url": "..."},
     "organization": {"login": "attacker-org"}, "member": {"login": "attacker"} }
   ```
4. `WebhooksController#verify_signature` validates the signature using `attacker-org`'s secret — succeeds. [1](#0-0) 
5. `MembershipHandler#find_or_create_team!` looks up `Team.find_or_create_by!(github_id: 555)`, finds the pre-existing `trusted-org/admins` team (created earlier for `trusted-org`), and returns it unchanged. [5](#0-4) 
6. `team.add_member(User.find_or_create_by_login!("attacker"))` adds the attacker's GitHub user to `trusted-org/admins`. [10](#0-9) 
7. Attacker now logs into Shipit via GitHub OAuth; `User#authorized?` returns `true` because they are a member of a `Shipit.github_teams` team, granting full application access despite never being part of `trusted-org`. [8](#0-7)
