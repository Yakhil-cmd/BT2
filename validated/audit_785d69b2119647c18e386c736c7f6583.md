### Title
Path traversal in `inherit_from` allows arbitrary host file read via `DeploySpec::FileSystem#build_config` - ([File: app/models/shipit/deploy_spec/file_system.rb])

### Summary
`DeploySpec::FileSystem#build_config` resolves the attacker-controlled `inherit_from` YAML key with `path.dirname.join(...)` and only checks `Pathname#exist?` before reading and parsing the target as YAML, with no confinement to `@app_dir`. Because `Pathname#join` honors absolute paths (discarding the base) and honors `../` traversal segments, an attacker who controls the content of their own branch's `shipit.yml` can make Shipit read and parse arbitrary files reachable by the Shipit worker process, merging their contents into the effective deploy/task configuration.

### Finding Description
The claimed binding — "every file path read by `load_config`/`build_config` for a given task/deploy is a path inside the checked-out repository directory (`@app_dir`)" — does **not** hold for the `inherit_from` recursion.

- `config_file_path` (the entry point) is confined to `@app_dir` because it only iterates a fixed list of filenames via `file(filename, root: true)`, i.e. `@app_dir.join(path)`: [1](#0-0) 
- However, once inside `build_config`, the inherited path is computed directly from attacker-supplied YAML content with no re-validation against `@app_dir`: [2](#0-1) 

`inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))` never calls `file()` and never checks that the resolved path still starts with `@app_dir`. Since `Pathname#join` replaces the base entirely when given an absolute argument, and resolves `../` segments literally, a value like `inherit_from: /etc/passwd` or `inherit_from: ../../../../etc/passwd` escapes `@app_dir` completely. `read_config` then does `SafeYAML.load(path.read) if path.exist?` with no path restriction: [3](#0-2) 

**Attack**: The attacker pushes/PRs a branch containing a `shipit.yml` (or `.shipit/shipit.yml`) with:
```yaml
inherit_from: /path/to/host/file.yml
```
This is read whenever the attacker's own commit/branch is checked out and a `DeploySpec::FileSystem` is built for it — e.g. via `StackCommands#build_cacheable_deploy_spec`/`fetch_deployed_revision` (checked-out temp clone) or `TaskCommands#deploy_spec` for a deploy/rollback/task on that stack: [4](#0-3) [5](#0-4) 

If the target file exists and parses as a YAML hash, its contents are `deep_merge`d into the effective config that later drives `deploy`/`rollback`/`fetch` step lists, `machine.environment`, and variable defaults — values that ultimately become `Command` arguments/env passed to `PTY.spawn` and are echoed into the deploy/task output that the attacker (owner of the stack/PR) can view. Existing tests only exercise the same-directory, `Pathname.any_instance.stubs(:exist?)`-mocked case and never assert confinement: [6](#0-5) . No guard (`verify_signature`, `force_github_authentication`, model validators) addresses this because the flaw is purely in local filesystem path handling within the engine's own deploy-spec parsing code, and it doesn't depend on any authentication bypass — it's exploitable by any user able to have their branch/PR checked out for their own stack.

### Impact Explanation
The affected party is the attacker's own stack (their PR/branch/repository), so this is not directly a cross-tenant compromise, but it is a genuine arbitrary local file read on the deploy host as the Shipit worker user, with contents potentially surfaced into deploy config, environment variables, or task output visible to the attacker. On multi-tenant Shipit installs where multiple stacks/deploy workers share a filesystem (e.g. `Rails.root.join('data','stacks', ...)` for other owners/repos, `config/database.yml`, `config/credentials.yml.enc`, `.env` files, or other stacks' checked-out `shipit.yml`), this can leak deploy-time secrets or configuration that were never scoped to the attacker's repository — matching the "exfiltration of deploy-time secrets" Critical category, contingent on what sensitive readable files exist on the shared host filesystem. It is repeatable on every deploy/task/PR-status refresh for the attacker's own stack.

### Likelihood Explanation
Preconditions are low: the attacker only needs push access to a branch/fork whose stack (or an unmerged PR check) triggers `DeploySpec::FileSystem` parsing — a routine, unprivileged action (`git push`, opening a PR). No secrets, sessions, or elevated GitHub permissions are required. The only uncertainty is whether a sensitive/parseable YAML file exists at a guessable absolute path on the specific deployment host, which is environment-dependent but commonly true (e.g., other stacks' `shipit.yml` under a predictable `Rails.root.join('data','stacks', owner, repo, env)` structure, as shown by `Stack#base_path`) [7](#0-6) .

### Recommendation
In `DeploySpec::FileSystem#build_config`, resolve `inherit_from` through the same confinement logic used for the primary config lookup (i.e., via `file(...)`/`@app_dir`), and explicitly reject the merge (or raise) if the resolved, expanded real path is not a descendant of `@app_dir` (e.g. compare `inherits_from_path.expand_path` against `@app_dir.expand_path` using `Pathname#ascend`/`start_with?` on the expanded path, and reject absolute paths and `..` traversal outright).

### Proof of Concept
```ruby
test '#build_config refuses to read files outside app_dir via inherit_from traversal' do
  Dir.mktmpdir do |app_dir|
    outside_dir = Dir.mktmpdir
    secret_path = File.join(outside_dir, 'secret.yml')
    File.write(secret_path, "deploy:\n  override:\n    - 'cat /etc/shadow'\n")

    stack = shipit_stacks(:shipit)
    deploy_spec = Shipit::DeploySpec::FileSystem.new(app_dir, stack)

    relative_traversal = Pathname.new(app_dir).join('shipit.yml').dirname.join(
      Pathname.new(secret_path).relative_path_from(Pathname.new(app_dir))
    )
    # binding under test: resolved inherited path must stay inside app_dir
    assert_not relative_traversal.to_s.start_with?(app_dir.to_s),
               "traversal path unexpectedly stayed inside app_dir (test setup issue)"

    config_obj = { 'inherit_from' => Pathname.new(secret_path).relative_path_from(Pathname.new(app_dir)).to_s }
    result = deploy_spec.send(:build_config, Pathname.new(app_dir).join('shipit.yml'), config_obj)

    refute result.dig('deploy', 'override')&.include?('cat /etc/shadow'),
           "build_config merged content from a file outside @app_dir"
  end
end
```
This asserts the equality that should hold — `resolved_inherit_path == path inside @app_dir` — fails today, and that `build_config` must not merge configuration read from outside `@app_dir`.

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end
