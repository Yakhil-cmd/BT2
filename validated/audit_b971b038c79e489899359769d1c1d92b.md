### Title
Webhook signature verification is keyed to the wrong GitHub organization, allowing cross-repository webhook forgery when any configured organization lacks a `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC `webhook_secret`) to verify a webhook against using one payload field, while the event handlers that actually act on the payload use a *different* payload field to decide which repository/stack to mutate. These two fields are never bound together, so an attacker can pick an organization whose webhook_secret is unset (or otherwise known/weak) to satisfy verification while acting on an entirely different organization's repository.

### Finding Description
`verify_signature` resolves the signing organization purely from `repository.owner.login` (or `organization.login`) and looks up that organization's `GithubApp` to verify the signature: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally returns `true` when that organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, once the request is accepted, every webhook `Handler` (e.g. `PushHandler`) locates the target repository/stacks using a **different** payload field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because the JSON body is fully attacker-controlled prior to verification (`params = JSON.parse(request.raw_post)` and `event`/`repository_owner` are pulled straight from it), nothing prevents `repository.owner.login` from being set to organization A (unsecured, no `webhook_secret` configured) while `repository.full_name` is set to `"orgB/victim-repo"` belonging to a different, properly secured organization B. Verification succeeds trivially against org A's (blank) secret, yet the handler that actually executes acts on org B's real repository and stacks, invoking `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA.

This breaks the intended binding: **the organization that authenticated the request must equal the organization whose repository is written**. `Shipit.github(organization: repository_owner)` authenticates one organization, but `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` writes to a different one.

### Impact Explanation
The `/webhooks` endpoint is a single shared, unauthenticated (pre-signature) HTTP endpoint for all organizations configured in `Shipit.github`. If any one configured organization omits `webhook_secret` (a documented, valid configuration — see `config/secrets.development.shopify.yml` and `template.rb` where `webhook_secret:` is left blank by default), an attacker can use that organization's identity purely to satisfy `verify_signature`, then supply an arbitrary `repository.full_name` for any other onboarded organization/repository to have handlers act on it unauthenticated. For the `push` event this reaches `Stack#sync_github` with an attacker-chosen `expected_head_sha`, and other events (`status`, `membership`, `check_suite`, `pull_request`) are similarly reachable for any registered repository, letting an unauthenticated actor manipulate commit statuses, team memberships, or trigger GitHub sync jobs against a repository whose real GitHub App is otherwise correctly secured.

### Likelihood Explanation
Exploitability requires only that the attacker can reach the public `/webhooks` endpoint and that at least one organization configured on the same Shipit instance lacks a `webhook_secret` (a common state during setup/staging, and explicitly shown as an accepted default in the repo's own sample secrets file). No GitHub credentials, session, or `ApiClient` token are needed — this is a pure logic flaw in `WebhooksController#verify_signature` combined with `Handler#repository_name`.

### Recommendation
Bind the field used for signature-key selection to the field used for repository resolution: verify the signature using the organization derived from `repository.full_name`'s owner segment (the same field `Handler#repository_name` uses), not a separately-controlled `repository.owner.login`/`organization.login` field. Additionally, consider rejecting webhooks entirely for organizations with a blank `webhook_secret` in production, and cross-check that `repository.owner.login` matches the owner segment of `repository.full_name` before proceeding.

### Proof of Concept
1. Configure Shipit with two organizations: `org-a` (no `webhook_secret`) and `org-b` (`webhook_secret` set, has a real registered stack `org-b/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. `verify_signature` resolves `repository_owner` = `"org-a"`, calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which returns `true` immediately since `org-a` has no `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`) — no valid signature is ever required.
4. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `stacks` method resolves the target using `payload.dig('repository', 'full_name')` = `"org-b/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), acting on org B's real stack with the attacker-supplied `after` SHA (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — despite the request never being authenticated for org B.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
