### Title
Cross-organization webhook forgery triggers unauthorized sync/deploy on a repository the attacker does not own - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook's HMAC signature against based on `repository.owner.login` (or `organization.login`) pulled from the attacker-supplied JSON body, but the handlers that actually act on the payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc., via `Handler#repository_name`) resolve the target `Repository`/`Stack` from a *different* field in the same body: `repository.full_name`. Because the signature only proves the raw body was signed with *some* organization's webhook secret — not that the signing organization matches the repository that gets written to — an attacker who controls a legitimate, low-privilege GitHub App installation on their own organization (a normal, unprivileged setup in any multi-tenant Shipit deployment configured with per-organization `webhook_secret`s, as documented in `test/dummy/config/secrets_double_github_app.yml`) can forge a webhook whose `repository.owner.login` is their own org (so it passes signature verification with their known secret) while `repository.full_name` points at a victim org/repo they don't control.

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository/stack being mutated`

`verify_signature` computes the org used for verification from a field the attacker fully controls: [1](#0-0) [2](#0-1) 

The actual HMAC check only compares the raw body against the secret for `Shipit.github(organization: repository_owner)`: [3](#0-2) 

But every downstream handler resolves the target repository/stack using a *separate* JSON field, `repository.full_name`, which is never cross-checked against `repository.owner.login`: [4](#0-3) 

`Repository.from_github_repo_name` splits this attacker-controlled `full_name` and looks up any repository by owner/name, with no relation to which org's secret validated the signature: [5](#0-4) 

Since `repository.owner.login` and `repository.full_name` are two independent strings inside the same JSON blob the attacker fully writes, nothing forces them to refer to the same GitHub repository. Multi-organization Shipit installations configure a distinct `webhook_secret` per organization (as shown in `test/dummy/config/secrets_double_github_app.yml`), so an attacker who legitimately controls their own org's GitHub App/webhook secret can compute a valid signature for a payload whose `repository.owner.login` is `"attacker-org"` but whose `repository.full_name` is `"victim-org/victim-repo"`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. A forged `push` event with a legitimate signature from the attacker's own org, but `full_name` pointing at a victim repository, is dispatched to `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack of the victim repository matching the spoofed branch: [6](#0-5) 

This is a cross-repository write: an attacker with no privileges on the victim repository can force GitHub sync jobs against the victim's stacks, and — via the sibling `status_handler.rb`/`check_suite_handler.rb` handlers that follow the identical `repository_name`/`full_name` pattern — inject forged commit statuses or check-suite state into the victim's commits, which can influence whether commits are considered deployable, i.e. contribute to an unauthorized deploy decision on a stack the attacker does not own.

### Likelihood Explanation
This requires the attacker to control (or be a collaborator on) their own GitHub organization's App installation with its own `webhook_secret` — which is a normal, unprivileged deployment scenario for multi-tenant Shipit setups, not an escalation of an already-privileged Shipit session. No `ApiClient` token, no GitHub write access to the victim repo, and no compromise of the victim org's secret is required.

### Recommendation
Bind the field used to select the verifying organization to the field used to resolve the target repository: after `verify_webhook_signature` succeeds, re-derive `repository_owner` strictly from `repository.full_name`'s owner segment (or vice versa), and reject the request if `repository.owner.login` does not match the owner segment of `repository.full_name`. Alternatively, have handlers pass through the already-authenticated organization context instead of re-parsing `repository.full_name` independently.

### Proof of Concept
1. Attacker controls organization `attacker-org`, which has its own GitHub App installation on this Shipit instance with `webhook_secret = S_attacker` (a normal, unprivileged multi-org config as in `test/dummy/config/secrets_double_github_app.yml`).
2. Victim organization `victim-org` has a tracked stack for `victim-org/victim-repo`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"` from the payload, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because the attacker legitimately knows `S_attacker`.
6. `PushHandler#process` resolves the target via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, finds the victim's stacks, and triggers `stack.sync_github(expected_head_sha: ...)` — a write against a repository the attacker never authenticated for.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
