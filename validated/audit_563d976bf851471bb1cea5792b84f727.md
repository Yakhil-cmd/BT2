Confirmed root cause: `WebhooksController#verify_signature` picks the HMAC secret to validate against based on `repository_owner`, a field taken from the **unverified** request body, before the signature is checked. The event handlers that actually act on the payload (e.g. `Handler#repository_name`, `OpenedHandler#repository`) key off a *different* field, `payload.dig('repository', 'full_name')`. Because these two lookups are independent and only the first one gates which secret validates the signature, an attacker who knows (or can obtain, e.g. by triggering a real webhook from any org configured with multi-tenant `github_apps`) a valid signature for organization A can replay/craft a body whose `repository.owner.login` is A (so it validates against A's `webhook_secret`) while `repository.full_name` names a repository belonging to organization B, causing handlers to write/act on B's stack. This is only exploitable in the **multi-tenant** `github_apps` configuration (`Shipit.github_app_config`), since in single-app mode there is only one webhook secret and the mismatch has no effect.

### Title
Webhook signature validated against organization derived from unverified payload, not the repository actually mutated - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the `X-Hub-Signature` against using `repository_owner`, extracted from the raw, unauthenticated request body, while every webhook handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, `PullRequest::OpenedHandler#repository`, etc.) resolves the actual `Repository`/`Stack` to act on from a *different* payload field, `repository.full_name`. In a multi-org (`github_apps`) deployment this breaks the binding "organization whose secret authenticated the request == repository that gets written to."

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where `repository_owner` is:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` maps this string to per-organization config (`github_app_config`) which contains a distinct `webhook_secret` per organization: [3](#0-2) 

Meanwhile, the handlers dispatched by `create` (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, `app/controllers/shipit/webhooks_controller.rb:12`) resolve the target repository independently via `payload.dig('repository', 'full_name')`: [4](#0-3) 
and e.g. in `OpenedHandler#repository`: [5](#0-4) 

Because `repository.owner.login` (used for signature-secret selection) and `repository.full_name` (used for the actual write target) are two separate, independently attacker-influenced fields of the same unsigned JSON body, and the HMAC only covers the raw bytes (not "this signature is only valid for org A's repos"), nothing prevents a body from being crafted such that the owner-login field points to org A (whose secret is used to pass `verify_webhook_signature`) while `repository.full_name` points to a repository under org B's stack. Equality broken: `organization(secret) used to authenticate == organization owning the repository actually mutated`.

### Impact Explanation
If exploitable, this allows an unprivileged actor who can obtain any one valid signed webhook body/secret pairing from the multi-tenant instance (e.g. from an app they legitimately administer under org A) to forge webhook deliveries that pass signature verification but are processed against a stack/repository belonging to a different, unrelated organization (org B) configured on the same Shipit instance — e.g. creating review-stack provisioning (`OpenedHandler`), labeling PRs, or altering merge/commit status caches for a repo they don't control. This is a cross-repository/cross-tenant write achieved by defeating the intended per-organization authentication boundary.

### Likelihood Explanation
Likelihood is Low-to-Medium and conditioned on deployment configuration: it only applies when the host configures multiple GitHub Apps/organizations (`Shipit.github_apps`, i.e. `github_default_organization` is non-nil). In the common single-app configuration there's only one `webhook_secret`, so this mismatch has no observable effect. Where multi-tenant config is used, the attacker needs legitimate control of a webhook secret for at least one organization on the instance (e.g. as an admin of their own org's GitHub App/webhook config) to produce a validly-signed body, then craft the `repository.full_name` field to target another tenant.

### Recommendation
Bind signature verification and repository resolution to the same value: verify the webhook using a secret keyed off `repository.full_name` (or verify per-organization secrets against the resolved `full_name`'s owner) rather than a possibly-different `repository.owner.login`/`organization.login` field, and reject requests where these two fields disagree.

### Proof of Concept
1. Configure a multi-tenant instance with `github_apps` for `org-a` (secret `SECRET_A`) and `org-b` (secret `SECRET_B`).
2. As a legitimate admin of `org-a`'s GitHub App, capture/construct any signed `pull_request` payload with `X-Hub-Signature: sha1=<hmac(SECRET_A, body)>` where `repository.owner.login = "org-a"`.
3. Modify the same JSON body so `repository.full_name = "org-b/some-repo"` while keeping `repository.owner.login = "org-a"` unchanged, recomputing nothing else (the HMAC is only over raw bytes, and `verify_signature` only reads `repository.owner.login`, not `full_name`, to pick the secret) — signature still verifies as `SECRET_A` matches.
4. POST to `/github/webhooks`; `verify_signature` passes using `org-a`'s secret; `Handler#repository_name`/`OpenedHandler#repository` resolve and act on `org-b/some-repo`'s `Stack`/`Repository`, e.g. triggering review-stack provisioning against org-b's repo.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
