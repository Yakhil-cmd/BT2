### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository/stack scoping, letting any GitHub organization the attacker controls flip status on a victim stack's commit — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target records with `Commit.where(sha: params.sha)`, with no filter on which repository/organization authenticated the webhook. `Shipit::WebhooksController#verify_signature` only proves the payload was signed by *some* org's configured `webhook_secret` (`Shipit.github(organization: repository_owner)`), it never checks that the commit(s) being mutated actually belong to that same repository. Since git commit SHAs are content-addressed and identical across repositories that share the same commit object (forks, cherry-picks, copied history, mirrored/vendored branches, or multiple Shipit stacks tracking the same upstream repo), a webhook that is validly signed for repository/org A can write a `Status` row onto a `Commit` that belongs to stack/repository B.

### Finding Description
The invariant that should hold is: `status.stack.repository == verified_repository_owner/name` for every `Status` created from a webhook. What the code actually enforces is only: `signature == HMAC(webhook_secret_for(repository_owner_in_payload), raw_body)` (`app/controllers/shipit/webhooks_controller.rb:24-30`), then unconditionally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) — with no join/filter against `params['repository']['full_name']` or the commit's `stack.repository`.

Path:
1. `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with the `webhook_secret` configured for *some* organization the attacker legitimately controls (e.g. their own fork/org that Shipit is configured to receive webhooks from), and a JSON body containing `sha`, `context: codecov/project`, `state: failure`.
2. `verify_signature` passes because it only checks the signature against `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker's own payload (`app/controllers/shipit/webhooks_controller.rb:59-62`) — it never cross-checks that this organization owns the commit(s) that will be mutated.
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally across every `Stack`/`Repository` in the installation, and calls `commit.create_status_from_github!(params)` on each match (`app/models/shipit/commit.rb:165-169`), which persists a `Status` scoped to `commit.stack_id` (`app/models/shipit/status.rb:24-33`) and re-evaluates deployability (`Commit#add_status`, `app/models/shipit/commit.rb:366-386`), including scheduling merges/continuous delivery.

Because the same git commit object can legitimately exist in more than one repository (fork with unmodified head SHA, cherry-pick, mirrored history), an attacker who authenticates as organization A can cause a `Status` to be created on a `Commit` row belonging to victim stack/organization B, changing `commit.status`/`deployable?`/`blocked?` for a stack they never authenticated for. If the victim stack requires `codecov/project` and has `review_stacks_enabled true, allow_all` (auto-provisioning review stacks for external PRs that execute `shipit.yml`), this status flip can gate or unblock the review stack's deploy pipeline.

None of the existing guards prevent this: `verify_signature` validates the signer but not the target scope; `ExplicitParameters` in `StatusHandler.params` only validates payload shape (`sha`, `state`, etc.), not repository identity; there is no `Repository`-based `belongs_to`/scope check in `StatusHandler#process` or in `Commit.where(sha:)`.

### Impact Explanation
A correctly-authenticated webhook for repository A can write a `Status` record — and drive downstream deploy/merge/block decisions — against a `Commit` that belongs to a *different* stack/repository B that never authenticated the request. This matches the "payload for one repository mutating another's stack, commit, task or team" Critical class: it can force `deployable_status`/`commit_status` hooks to fire, trigger `stack.schedule_merges`, or block deploys on stack B (`app/models/shipit/commit.rb:379-386`), all from a webhook whose signature was only valid for stack A's organization. Repeatability depends on the attacker being able to get a commit with a matching SHA recorded in both their own controlled repo and the victim's tracked repo (fork/cherry-pick/mirrored commit), and depends on the victim stack requiring the same `context` (`codecov/project`) that the attacker's own status service reports for their repo.

### Likelihood Explanation
This requires: (1) the attacker to legitimately control at least one GitHub organization/repository already wired into this Shipit instance (so they can produce a validly-signed webhook using that org's real `webhook_secret`, e.g. via a genuine CI/status integration such as Codecov on their own repo), and (2) a commit whose SHA is shared between that repository and the victim stack's repository — which happens naturally for forks (unmodified fork head commits share the exact upstream SHA) or cherry-picked/mirrored commits, not via SHA-1 brute force. This is a plausible but non-trivial precondition (requires a real, Shipit-integrated org under attacker control plus a shared-SHA relationship to the victim), rather than something exploitable by a purely anonymous internet requester with zero relationship to any onboarded repository.

### Recommendation
Scope `StatusHandler#process` (and the underlying `Commit` lookup) to the repository that authenticated the webhook: filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_id_for(params) })` (or equivalent), deriving `repository_id` from `params['repository']['full_name']`/`repository_owner` verified during signature validation, rather than trusting a bare SHA match across the entire installation.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status handler does not write across unrelated repositories sharing a commit sha" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse) # repository "attacker/other-repo"

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  before = victim_commit.reload.status.state

  # Simulate a status webhook that is validly signed for attacker_stack's org
  # but carries a sha that also exists on victim_commit.
  params = ExplicitParameters::Params.new(
    sha: shared_sha, state: 'failure', context: 'codecov/project'
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.process # via Commit.where(sha:)

  after = victim_commit.reload.status.state

  # Binding under test: only attacker_commit (attacker's authenticated repo)
  # should change; victim_commit (unrelated, unauthenticated repo) must not.
  assert_equal before, after, "victim stack's commit state changed from a webhook that never authenticated its repository"
end
```
