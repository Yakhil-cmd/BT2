This confirms the multi-organization design: `Shipit.github(organization:)` in `lib/shipit.rb` looks up a per-organization config via `github_app_config`, and each organization can independently configure a `webhook_secret` (nil/blank is permitted per org), as shown in the multi-org example in `config/secrets.development.example.yml`.### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, allowing signature bypass across organizations with differing `webhook_secret` configuration - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate the request against using `repository_owner`, derived from the **untrusted, unverified** JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Every event handler, however, resolves which `Repository`/`Stack` to act on using a **different** field from the same payload: `payload.dig('repository', 'full_name')`. [3](#0-2) 

This is the same class of bug as the auction report: the field that gates authorization (`repository_owner`, which selects the secret used to "authenticate" the request) is not the field that is actually acted upon (`repository.full_name`, which determines the target Stack that gets written to). The binding `authenticated_org == acted_on_repository_owner` is never enforced by the signature check itself.

### Finding Description
Shipit supports per-organization GitHub App configuration, where each organization has its own independently-configured `webhook_secret` (including `nil`, which is the documented default and explicitly allowed): [4](#0-3) . When `webhook_secret` is blank for the selected org, `verify_webhook_signature` short-circuits and returns `true` unconditionally, regardless of the request body: [5](#0-4) 

The controller flow is:
1. `repository_owner` is read from the unverified body (`repository.owner.login` or `organization.login`). [2](#0-1) 
2. `Shipit.github(organization: repository_owner)` looks up that organization's config and `webhook_secret`. [6](#0-5) 
3. If that org's `webhook_secret` is blank, `verify_webhook_signature` returns `true` with no cryptographic check at all. [5](#0-4) 
4. The event handler then locates the actual target `Stack` via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` — a completely independent field from `repository_owner`. [3](#0-2) [7](#0-6) 

Because these two fields are never cross-checked, an attacker who knows (or can enumerate/guess) that some organization configured in this Shipit instance has no `webhook_secret` set can craft a payload where `repository.owner.login`/`organization.login` names that unprotected org (bypassing the signature check entirely), while `repository.full_name` names an arbitrary *other* organization's/repo's stack that does have signature protection configured. The handler will act on the stack named in `full_name`, not the org that "authenticated" the request.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely reachable unauthorized-write consequences via forged, unsigned webhook events processed by handlers keyed on `full_name`:
- Forged `push` events queue `GithubSyncJob` for the target stack with attacker-chosen `expected_head_sha`, causing the stack's commit list/state to be manipulated based on whatever the real GitHub API subsequently returns, effectively spoofing sync triggers cross-organization. [7](#0-6) 
- Forged `status`/`membership`/`pull_request` events, etc., mutate state (commit statuses, team membership, review stack lifecycle) for stacks belonging to an organization the attacker never authenticated against. [8](#0-7) 

This requires a specific, but plausible and documented, multi-organization configuration where at least one configured organization omits `webhook_secret` (the documented default/example value is `nil`). [9](#0-8) 

### Likelihood Explanation
Moderate-to-low likelihood in practice: it requires the operator to run a **multi-org** configuration (`github: { org_a: {...}, org_b: {...} }`) where at least one organization key has a blank/`nil` `webhook_secret`, which the shipped example configuration explicitly shows as valid/default. [10](#0-9)  An attacker only needs to know or guess the name of that unprotected organization and any target `owner/repo` full_name they want to affect — no secret, session, or API token is required, satisfying the "unprivileged attacker" constraint.

### Recommendation
After resolving the target repository/stack in a handler, verify that the repository's actual `owner` matches the `repository_owner`/organization that was used to select and validate the webhook signature (i.e., bind `Shipit.github(organization: repository.owner)`'s secret to the same repository whose `full_name` is acted upon), rather than allowing the two lookups to diverge. Alternatively, always require `repository.full_name`'s owner segment to equal the value used in `verify_signature`, and reject the request if they differ.

### Proof of Concept
Given a multi-org config:
```yaml
github:
  attacker-org:
    app_id: 1
    installation_id: 1
    webhook_secret: # blank/nil
  victim-org:
    app_id: 2
    installation_id: 2
    webhook_secret: "supersecret"
```
1. Attacker sends `POST /github_webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "victim-org/protected-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
No valid `X-Hub-Signature` is needed.
2. `repository_owner` resolves to `"attacker-org"`. [2](#0-1) 
3. `Shipit.github(organization: "attacker-org")` returns a `GitHubApp` with `webhook_secret == nil`, so `verify_webhook_signature` returns `true` unconditionally. [5](#0-4) 
4. `PushHandler` resolves the target stacks via `repository_name = payload.dig('repository','full_name') = "victim-org/protected-repo"` and enqueues `GithubSyncJob` for that stack, despite `victim-org` having a configured `webhook_secret` that was never checked. [3](#0-2) [7](#0-6)

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

    github_config = secrets.github.deep_transform_keys(&:downcase)

  end

    def verify_webhook_signature(signature, message)
