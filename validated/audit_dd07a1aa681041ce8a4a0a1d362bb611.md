Based on my investigation, I found a genuine analog in the AA (Autonomous Agent) trigger-processing engine that mirrors the reported bug class: an operation that should be able to fix a balance shortfall is itself blocked because the check compares a *dynamically growing reserved requirement* (storage_size) against the *current spendable balance* (byte_balance) at the exact point where any state-increasing trigger is evaluated, and bounce discards the whole unit rather than only the part that made the reservation grow.

### Title
AA state-var growth permanently DoSed once byte balance falls below storage_size reservation - (File: aa_composer.js)

### Summary
`updateStorageSize()` in `aa_composer.js` bounces (reverts) an entire AA response unit whenever the AA's post-trigger `byte_balance` would be lower than the new `storage_size` requirement, mirroring the reported pattern of comparing a live balance against a "reserved" quantity and rejecting the whole operation on any shortfall — including operations that are the very fix (adding funds/state) needed to resolve the shortfall.

### Finding Description
`handleTrigger()` tracks two numbers throughout AA execution: `byte_balance` (the AA's spendable bytes after payments) and `storage_size` (bytes reserved to cover the AA's persisted state). At the end of `sendUnit()`/`finish()`, `updateStorageSize()` computes the new storage requirement and compares it to the balance: [1](#0-0) 

```
console.log('storage size = ' + storage_size + ' + ' + delta_storage_size + ', byte_balance = ' + byte_balance);
var new_storage_size = storage_size + delta_storage_size;
if (new_storage_size < 0)
    throw Error("storage size would become negative: " + new_storage_size);
if (byte_balance < new_storage_size && new_storage_size > FULL_TRANSFER_INPUT_SIZE && mci >= constants.aaStorageSizeUpgradeMci)
    return cb("byte balance " + byte_balance + " would drop below new storage size " + new_storage_size);
```

If the check fails, `updateStorageSize` returns an error string, which both `sendUnit()`’s final callback and `finish()` treat as a hard revert: [2](#0-1) [3](#0-2) 

`revert()`/`bounce()` roll back **all** state changes to the savepoint taken before the trigger, i.e., `ROLLBACK TO SAVEPOINT initial_balances`: [4](#0-3) 

Critically, `SAVEPOINT initial_balances` is created in `updateInitialAABalances()` immediately **after** the AA balance has already been credited with the trigger's incoming bytes: [5](#0-4) 

Because the savepoint is placed after crediting, and because `updateStorageSize` is evaluated on the *entire* unit including any state var writes the AA logic makes as a normal side effect of processing incoming payments (e.g., recording `trigger.address`, updating counters, etc.), an AA whose `storage_size` has grown close to its `byte_balance` reaches a state where **any** trigger that writes new/larger state vars — even ones sending the AA additional bytes intended to top it up — gets fully reverted with `"byte balance ... would drop below new storage size ..."`, unless the sender knows in advance exactly how many bytes are required and sends at least that much in the very same trigger. Ordinary users interacting with the AA through its documented interface (which typically doesn't require them to calculate internal storage economics) will have every state-mutating call rejected once this threshold is crossed, and the reverted balance top-up is not persisted as state (only the underlying payment output eventually lands in `aa_balances`, but any AA-side bookkeeping that depends on state var updates — deposit ledgers, share counters, etc. — never executes), so the AA's own accounting can become permanently unable to track further deposits designed to fix the shortfall, exactly analogous to `getVaultBalance() < reservedFunds` blocking `deposit()`.

### Impact Explanation
This is a fund-freezing condition reachable by any ordinary (unprivileged) unit poster who triggers an AA whose storage requirement has grown relative to its available bytes (a state achievable simply through the AA's normal life cycle of accumulating state, e.g., growing lists/counters/records for many users). Once the threshold is crossed:
- Every subsequent trigger that would add or grow persisted state gets bounced/reverted, even when the trigger is explicitly designed to add funds.
- Because the revert unwinds to the balances savepoint *before* topping up in that same unit is durably recorded through state-var bookkeeping, an AA that tracks internal balances via state vars (a very common pattern, seen throughout the codebase's own AA examples for withdrawal ledgers, order books, and market-maker balances) can be left in a state where user funds are stuck at the AA address with no way to update the AA's internal accounting to reflect further deposits/repairs, unless a sender manually computes and overpays the exact oversize/storage-size delta on the very first attempt — something outside the AA's documented public interface.
- This matches "AA fund loss or freezing" and a "node[/protocol logic] unable to confirm new [state-changing] units" for that address.

### Likelihood Explanation
Any AA design that keeps growing per-user state (balances, order books, counters) is subject to this once accumulated storage cost outpaces its available bytes balance — a state that arises naturally from popularity/usage rather than requiring an attacker with special privileges. No malicious peer, hub, or operator access is needed; a single ordinary posted trigger unit is sufficient to observe and be affected by the bounce.

### Recommendation
Decouple the "would drop below storage_size" check from the general state-update bounce path for the specific case where the current trigger's own payment (received `trigger.outputs.base` bytes) is what would restore the balance above `new_storage_size`. Concretely: recompute `byte_balance` used for this check with the incoming trigger payment fully counted as principal, not conditioned on the outgoing payment logic succeeding as a single atomic all-or-nothing unit; alternatively, allow a lighter-weight "top-up-only" state path (or a dedicated getter/interface) that lets senders replenish storage-size reserve without having their entire other state-mutating logic reverted, and/or emit a machine-readable response (rather than only reverting) so wallets/AAs can programmatically retry with a computed sufficient amount instead of failing silently by convention.

### Proof of Concept
1. Deploy an AA whose `messages` write a growing state var for every new user address, e.g., `var[trigger.address] = trigger.data.something;` (this is the common ocore AA pattern seen in `test/samples/order_book_exchange.oscript` and `payment_channels.oscript`, i.e., persisting per-caller balances).
2. Drive `aa_addresses.storage_size` for the AA up over many distinct interactions (each new/larger key adds to `storage_size`, tracked by `updateStorageSize` at [6](#0-5)  ), while its `aa_balances.base` balance is kept low by the AA's own script (e.g., paying out most received bytes to users, common in exchange/market-maker style AAs shown in `uniswap_like_market_maker.oscript`).
3. Once `storage_size` exceeds `byte_balance`, post a new trigger from an unprivileged address carrying a payment intended to top up the AA's balance and normal script logic that also writes/updates a state var (which is the AA's ordinary operating mode).
4. Observe that `updateStorageSize` returns `"byte balance ... would drop below new storage size ..."`, causing `finish()`/`sendUnit()` to `revert()`/`bounce()` the whole unit via `ROLLBACK TO SAVEPOINT initial_balances` ( [7](#0-6) ), discarding the intended top-up bookkeeping and leaving the AA unable to process further state-mutating triggers from ordinary senders unless they precisely pre-calculate and overpay the storage delta in a single call outside the AA's public documented interface.

			var state = addressVars[var_name];
			if (!state.updated)
				continue;
			if (state.value === false) { // false value signals that the var should be deleted
				if (state.original_old_value !== undefined)
					delta_storage_size -= var_name.length + getValueSize(state.original_old_value);
			}
			else {
				try {
					var newSize = getValueSize(state.value);
				}
