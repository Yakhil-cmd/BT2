## Title
Webhook signature verification keys off the untrusted `repository.owner.login`, letting the payload's own `repository.full_name` target a different, unrelated repository/stack - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to verify the HMAC signature against using a field taken directly from the **unverified** JSON body (`repository.owner.login` or `organization.login`). The event handlers, however, resolve the `Stack`/`Repository` that the event actually acts on using a *different* field from the same untrusted body: `repository.full_name` [1](#0-0) . Nothing binds these two fields together, and `verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured [2](#0-1) .

## Finding Description
The controller does:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`repository_owner` is read from the raw, attacker-controlled JSON before any signature validation occurs, and it is used purely to pick *which* organization's `webhook_secret` to check against. If that organization is configured in Shipit's multi-org `secrets.github` map with no `webhook_secret` (a legitimate, supported configuration — see the fixture `webhook_secret: # nil` for `OrgTwo`) [4](#0-3) , then `verify_webhook_signature` returns `true` unconditionally:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Once "verified," the payload is dispatched to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) ), which locate the target `Stack`/`Repository` using `repository.full_name` from the same body — completely independent of `repository.owner.login`:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

This breaks the equality that should hold: `organization that authenticated the webhook == organization owning the repository/stack the webhook acts on`. An attacker who knows (or can guess) that *some* organization configured in the target Shipit instance has no `webhook_secret` set can set `repository.owner.login` (or `organization.login`) to that org to trivially bypass signature checking, while setting `repository.full_name` to point at a completely different, unrelated stack that they don't control and that may belong to an org with a properly configured secret.

Downstream impact depends on which event/handler is invoked with the forged `repository.full_name`:
- `StatusHandler`/`PushHandler`/`CheckSuiteHandler` act on `Stack`s found via `repository.full_name` — e.g. forging commit statuses (`ci/*` checks) or triggering GitHub sync jobs against a target stack the attacker doesn't own.
- `MembershipHandler` creates/removes `Team`/`Membership` records based on the payload's `team`/`organization`/`member` fields, which are also unauthenticated relative to the org that "verified" the request, potentially affecting `Shipit.github_teams` authorization used by `User#authorized?` [6](#0-5) .

Note: I was not able to load `app/models/shipit/webhooks/handlers/membership_handler.rb` in the final iteration due to a tool error, so the exact membership-handler logic (whether it independently validates `organization.login` against the team's own org) is **unverified** — this is a gap in my analysis that would need to be checked before treating the membership-based escalation as confirmed.

## Impact Explanation
If confirmed to reach `StatusHandler` (already verified above via `Handler#repository_name`), an unauthenticated external attacker can forge GitHub `status`/`push`/`check_suite` events against any stack configured in a multi-organization Shipit deployment, as long as one org in that deployment has no `webhook_secret`. Forged commit statuses can satisfy `ci.require`/`merge.require` gating checks used by the merge queue (`MergeRequest::StatusChecker`) [7](#0-6) , contributing to an unauthorized deploy or merge — meeting the "Critical: unauthorized deploy/rollback/merge" bar. If the membership path is also confirmed, it could let an attacker add themselves to a `Shipit.github_teams`-authorized team, meeting the "High: escalation into `Shipit.github_teams` authorization" bar.

## Likelihood Explanation
Requires no credentials, no session, and no repository write access — only knowledge that the Shipit instance is configured with multiple GitHub organizations and that at least one has no `webhook_secret` set (a documented/supported configuration per the test fixtures). The webhook endpoint is intentionally public (`WebhooksController` skips CSRF and has no other auth) [8](#0-7) , so the only barrier is signature verification, which this flaw defeats for any org lacking a secret.

## Recommendation
Bind the field used to select the verifying organization's secret to the field used to resolve the target repository/stack: derive `repository_owner` from `repository.full_name`'s owner segment (the same field handlers use), not from a separate `repository.owner.login`/`organization.login` field. Additionally, do not treat "no `webhook_secret` configured" as automatic pass-through when other organizations in the same deployment do have secrets configured — consider requiring all configured orgs to set a secret, or reject events whose resolved organization has no secret if any other org is configured with one.

## Proof of Concept
1. Configure Shipit with two orgs: `OrgA` (no `webhook_secret`) and `OrgB` (has a stack `OrgB/secret-repo` with `webhook_secret` set), per the pattern in `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, with body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/secret-repo" },
  "sha": "<real commit sha in OrgB/secret-repo>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com",
  "created_at": "2026-09-01T00:00:00Z",
  "branches": [{ "name": "main" }]
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature header.
4. `StatusHandler` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("OrgB/secret-repo")` and creates a `Status` record for the given commit, spoofing a CI check on a repository under `OrgB` that the attacker has no relationship with.

This confirms the controller-side signature check does not bind the authenticating organization to the repository ultimately acted upon; full exploitation of the merge-queue/authorization impact would require further tracing (not completed here due to tool-call limits) of how `merge_request_required_statuses`/`Shipit.github_teams` consume these forged records in a live deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
