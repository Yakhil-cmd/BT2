### Title
Silently-Accepted Deposits Below the Accounting Threshold Become Permanently Locked in AA Balance - ([File: test/samples/a_bank_without_percent.oscript])

### Summary
Several reference Autonomous Agent (AA) contracts shipped in the ocore repository implement a "deposit" flow that only credits an internal, withdrawable accounting variable (`var[$base_key]` / `var[$asset_key]`) when the amount received in the trigger exceeds an arbitrary threshold (`10000` bytes). Amounts at or below that threshold are still added to the AA's real, spendable balance by the engine, but are never reflected in any state variable that the AA's own withdrawal logic reads. Because withdrawals are gated exclusively on the tracked variable (`var[$key]`), the residual bytes/asset units become permanently stranded in the AA with no code path capable of returning them, mirroring the `P2pYieldProxy._deposit` bug where the un-forwarded remainder was retained by the proxy with no accounting or recovery path.

### Finding Description
In `test/samples/a_bank_without_percent.oscript` (and duplicated verbatim in `test/samples/order_book_exchange.oscript` and `test/samples/fundraising_proxy.oscript`-style deposit branches), the "silently accept coins" branch only updates the ledger variable when the deposited amount is large enough: [1](#0-0) 

Meanwhile, the ocore AA engine itself unconditionally adds every byte/asset unit present in `trigger.outputs` to the AA's real `aa_balances` record, independent of whatever the AA's own oscript logic decides to track in `var[]`: [2](#0-1) 

This split between "real balance" (maintained automatically by the protocol from actual UTXOs, verified by the periodic `checkBalances()` invariant check) and "logical/accounting balance" (a state var maintained solely by hand-written AA formulas) is exactly the same class of defect described in the external report: funds are physically received and retained by the contract/AA, but the bookkeeping that authorizes withdrawal never accounts for the remainder, so the withdrawal branch (`trigger.data.withdraw AND ... AND $required_amount <= var[$key]`) can never authorize its release: [3](#0-2) 

Because there is no admin/governance mechanism in a plain AA (unlike the Solidity proxy, which at least has an `AllowedCalldataChecker`/`callAnyFunction` escape hatch controllable by governance), any deposit at or below the threshold is locked with **no recovery path whatsoever**, not even an out-of-band one.

### Impact Explanation
Any unprivileged AA trigger sender who deposits `<= 10000` bytes (or `<= 10000` of the accepted asset) into an AA using this common pattern loses those funds permanently: the AA's actual on-chain balance increases (confirmed consistent by the engine's balance-integrity check), but no state variable ever authorizes their withdrawal, and the AA logic itself has no other spending branch that could release them. This is a concrete instance of AA fund freezing/loss, matching the accepted impact category of "AA fund loss or freezing."

### Likelihood Explanation
The trigger condition requires nothing more than posting a normal payment unit with an output to the AA address for `<= 10000` bytes/asset units — an action any user can perform without any special privilege, and one that is trivial to hit accidentally (e.g., wallet dust, small top-ups, or partial retries after a failed larger send). Because this exact pattern is reproduced identically across multiple sample AAs shipped in the repository, any AA author who reuses this reference code (a realistic and encouraged practice, since these files exist specifically as templates) reproduces the same freeze condition in a live, user-facing contract.

### Recommendation
Remove the silent-drop threshold, or when an amount is below the threshold, either (a) always credit the full received amount to the tracked accounting variable regardless of size, or (b) immediately bounce/refund amounts that are not large enough to be tracked, rather than accepting them into the AA balance while discarding the entry in `var[]`. More generally, any AA (and any documentation/reference AA shipped with ocore) that partitions "amount received" from "amount accounted for" must guarantee that every unit of the former has a corresponding, reachable spending/accounting path, mirroring the fix applied to `P2pYieldProxy._deposit` of forwarding/crediting the full residual rather than orphaning it.

### Proof of Concept
1. Deploy the AA defined by `test/samples/a_bank_without_percent.oscript` (or reuse the identical pattern in `order_book_exchange.oscript`).
2. As an ordinary user, send a trigger payment with `trigger.data.withdraw` unset and `trigger.output[[asset=base]] = 5000` (i.e., `<= 10000`).
3. Observe: the AA's real balance (`aa_balances`, verifiable via `balance[base]` in oscript or the `checkBalances()` invariant) increases by 5000 bytes, but `var['balance_'||trigger.address||'_base']` is never set/incremented (branch at lines 39-43 is skipped).
4. Attempt a subsequent withdraw of any amount from this trigger address: the `if` condition on lines 5-10 fails because `var[$key]` was never credited for the 5000-byte deposit, and this AA offers no alternative message case to reclaim it — the 5000 bytes remain forever locked in the AA's balance.
