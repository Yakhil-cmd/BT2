### Title
Webhook signature is bound to `repository.owner.login`/`organization.login`, but downstream handlers act on the unrelated `repository.full_name` field, allowing an authenticated GitHub organization to write events into stacks owned by a different organization/repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, derived from `payload.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Once the signature is accepted, every registered handler receives the entire raw JSON body and resolves the target `Repository`/`Stack` using a completely different field, `payload.dig('repository', 'full_name')` [2](#0-1) , which is then split into `owner/name` and looked up directly with `Repository.from_github_repo_name` [3](#0-2) . Neither of these two owner-bearing fields is cross-checked against the other, and only `repository.owner.login`/`organization.login` is covered by the trust decision (which organization's secret was used to accept the signature). This mirrors the UMA `Registry.registerContract` bug class: a field that is used to establish trust (`parties`/here, `repository.owner.login`) is decoupled from the field that is actually acted upon (`contracts`/here, `repository.full_name`), letting an attacker who controls one binding manipulate the other to reach unintended state.

### Finding Description
The binding that should hold is:
`organization whose webhook secret authenticated the request == owner of the repository whose stacks/commits/statuses get mutated`

In `verify_signature`, the app instance used to verify the HMAC is selected purely from `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The signature itself only proves that the raw body was signed with the secret configured for that particular `organization` (`Shipit.github(organization: repository_owner)` → per-org `webhook_secret`) [4](#0-3) [5](#0-4) . It does not constrain any other field of the JSON body, including `repository.full_name`.

After verification, `create` hands the parsed body to every handler for the event, unmodified:
```ruby
params = JSON.parse(request.raw_post)
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [6](#0-5) 

Handlers derive the target stacks from a different path in the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`Repository.from_github_repo_name` blindly splits `full_name` on `/` and does a DB lookup, with no relation back to `repository.owner.login`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [3](#0-2) 

Because a GitHub App/organization owner controls both the secret used to sign requests to their own webhook endpoint and the full, arbitrary JSON body content sent to that endpoint (GitHub computes the signature over the exact payload bytes that the org admin's integration/relay chooses to send — nothing in this engine constrains `repository.full_name` to match `repository.owner.login`), an org that Shipit already trusts (has a configured `webhook_secret` for) can produce a validly-signed payload whose `repository.full_name` names an entirely different repository (e.g., a victim org/repo already registered as a Shipit `Stack`). The `Repository`/`Stack` write path (creating commits, updating statuses, triggering `GithubSyncJob`, etc., depending on handler) will then operate against that victim stack, even though the signature only proves authenticity for the attacker's own organization.

This is directly analogous to the UMA finding: `registerContract`'s `parties` array is trusted/iterated without validating consistency against `partyMap[...].contractIndex`, letting one index diverge from another and corrupt cross-references. Here, `repository.owner.login` (the "authenticated" identity) and `repository.full_name` (the "written" identity) are two independent, attacker-controlled fields in the same signed body that are never cross-validated, letting the authenticated identity diverge from the mutated resource.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. An attacker who operates their own GitHub organization/repository with a Shipit integration configured (i.e., an org already known to `Shipit.github_app_config`, which is an ordinary onboarding step, not a privileged Shipit account) can forge webhook deliveries that make Shipit believe events (pushes, commit statuses, check-suite results, pull_request/merge events, membership changes, etc.) occurred on a **different**, victim repository that is unrelated to their own organization. Depending on which handler processes the event, this can:
- Inject fabricated commits/commit statuses into a victim stack's history, influencing what Shipit considers "deployable," which can lead to unauthorized deploys of code that never passed the intended CI checks (a cross-repository write / unauthorized deploy precondition).
- Corrupt `Stack` state in ways functionally similar to the UMA bug (register inconsistent data against a resource the attacker was never authorized to touch).

This qualifies for the Critical category ("cross-repository writes, or an unauthorized deploy, rollback or merge") because the mutation lands on a stack/repository the attacker does not control and was never authenticated against.

### Likelihood Explanation
Exploitability requires only that the attacker control a GitHub organization/repository that already has a Shipit GitHub App/webhook configured for it (a normal, non-privileged integration step available to any org onboarded into the multi-org `secrets.github` config) — no Shipit account, API token, or GitHub write access to the victim repository is required. The attacker fully controls the raw JSON body delivered to `/webhooks` for their own org's webhook, including the `repository.full_name` field, and GitHub (or the attacker's own webhook relay for their org) signs whatever body is sent with the org's own secret. This makes the attack straightforward to execute for anyone who is a legitimate customer/org owner within a multi-tenant Shipit deployment, while being invisible to Shipit's own signature check, which only validates authenticity of the sender's own organization, not target-resource consistency.

### Recommendation
After signature verification, cross-check that the organization used to verify the signature matches the organization embedded in `repository.full_name` (and `organization.login`, if present) before dispatching to handlers — reject the webhook if they diverge. Concretely, in `WebhooksController#verify_signature`/`create`, derive a single canonical repository owner from the verified organization and pass it (or enforce equality with) whatever `repository_name`/`full_name` handlers subsequently resolve to, rather than trusting two independently-read fields of the same untrusted body for two different purposes.

### Proof of Concept
1. Shipit is configured with a multi-org GitHub App config (`secrets.github` keyed by org, per `Shipit.github_app_config`) [7](#0-6) , including the attacker's own org `attacker-org` (with a known `webhook_secret`) and a victim's stack registered as `victim-org/victim-repo`.
2. The attacker crafts a JSON payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<attacker-chosen-sha>",
  "state": "success",
  ...
}
```
3. The attacker signs this exact body with `attacker-org`'s known webhook secret (`sha1=HMAC(secret, body)`), and sends it to `POST /webhooks` with header `X-Github-Event: status` (or `push`, etc.) and `X-Hub-Signature: sha1=...`.
4. `verify_signature` computes `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against the attacker's own secret [8](#0-7) .
5. `create` dispatches the full body to the `status`/`push` handler, which resolves `repository_name` from `full_name` = `"victim-org/victim-repo"` and mutates the victim's `Stack`/`Commit` state [2](#0-1) , even though the signature never proved anything about `victim-org`.

Note: full exploitation impact (which specific handler leads to an unauthorized deploy vs. just polluted commit-status data) depends on handler-specific code under `app/models/shipit/webhooks/handlers/*`, which was not fully enumerated in this session; a Devin session with full repo access should verify the exact handler set for `push`/`status`/`check_suite` to confirm the strongest concrete consequence (e.g., whether `deployable?` can be flipped to true for unreviewed code).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
