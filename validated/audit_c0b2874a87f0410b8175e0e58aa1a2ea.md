### Title
Unbounded per-account access key enumeration in `TrieViewer::view_access_keys` enables RPC node CPU/memory DoS - ([File: runtime/runtime/src/state_viewer/mod.rs])

### Finding Description
The RPC method `EXPERIMENTAL_view_access_key_list` / `ViewAccessKeyList` query resolves to `TrieViewer::view_access_keys` in `runtime/runtime/src/state_viewer/mod.rs`, which is invoked from `chain/chain/src/runtime/mod.rs` at the `QueryRequest::ViewAccessKeyList` arm [1](#0-0) , and is served without pagination through `view_access_key_list_local`/`view_access_key_list_sharded` in `chain/jsonrpc/src/lib.rs` [2](#0-1) [3](#0-2) . Unlike `EXPERIMENTAL_view_state`, which supports a `prefix`/pagination-friendly key scan, there is no limit, cursor, or byte-size cap on `ViewAccessKeyList`, so a single request enumerates and deserializes every access key stored under an account's trie prefix.

An unprivileged attacker can fund one account and submit many `AddKey` transactions to accumulate a large number of access keys, each only requiring the standard storage stake for the key's storage usage. I was unable to fully verify from the available index the exact per-key storage cost constants (`num_bytes_account`/`num_extra_bytes_record`-style parameters in `core/parameters/src/cost.rs`) or confirm whether there is a protocol-level cap on the number of access keys per account; this could not be fully confirmed within the available tool budget, so the precise economic feasibility (attacker-affordable key count vs. resulting RPC cost) is not fully substantiated. However, since I could not find any per-account access-key count cap enforced at the protocol level (only economic storage-stake cost), this matches the pattern of other reported/known issues in NEAR where storage-stake-bounded but attacker-affordable large per-account collections cause disproportionate RPC-side work with no pagination.

### Impact Explanation
If unbounded, this would only affect RPC/view-node availability (a "view" call path used by `state_viewer`/client query, not part of block execution or consensus). It does not touch balance, gas metering, authorization, or state transition validity — it is a node resource/liveness issue scoped to nodes serving this specific RPC method. This falls short of a protocol-level fund-loss, consensus-divergence, or execution-metering bypass; at most it could contribute to a node-level DoS on RPC infrastructure, which is a narrower/lower-severity impact class than requested (chain stall/crash of validators or state divergence).

### Likelihood Explanation
Not fully confirmed. The exact number of access keys an attacker would need, and whether their affordability at scale is realistic given storage staking costs, could not be established from the retrieved code alone. Additionally, this path executes only in RPC/view context (not in block/chunk execution), so it does not stall chunk production or validator consensus — its blast radius is limited to individual RPC nodes handling the specific account query, and is mitigated by normal RPC-level protections (request timeouts, rate limiting) which exist outside the scope of the audited function itself.

### Recommendation
N/A — impact is bounded to RPC/view-node resource usage, not a core protocol invariant violation (no fund loss, no consensus impact, no metering bypass). If desired, add a pagination/limit parameter to `view_access_keys` and the `ViewAccessKeyList` RPC response analogous to `view_state`'s prefix/limit mechanism, and/or enforce a maximum access-key count per account at the protocol level.

### Proof of Concept
Not constructed — insufficient confirmed detail on (a) per-access-key storage cost constants and (b) any protocol-enforced cap on keys per account, both of which are required to assess real-world attacker feasibility. This would need to be established first via `core/parameters/src/cost.rs` and `runtime/runtime/src/access_keys.rs` before designing a meaningful integration-test PoC comparing `view_access_keys` and `view_state` latency/memory growth vs. N.
