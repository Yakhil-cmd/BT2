This confirms the full path: `ReviewStackAdapter#unarchive!` calls `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.unarchive!`, and `archive!` calls `stack.remove_from_provisioning_queue`/`stack.deprovision`/`stack.archive!` — all scoped by `stack = scope.find_by(environment:)` where `scope` is `repository.review_stacks` and `repository` is resolved purely from the attacker-supplied `params.repository.full_name`.

### Title
Cross-repository review stack provisioning via organization/full_name binding confusion in webhook signature verification - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature using `repository.owner.login` from the untrusted request body, while `LabeledHandler`/`UnlabeledHandler` (and other handlers) resolve the target `Repository`/`ReviewStack` using the separate, independently attacker-controlled `repository.full_name` field from the same body. Because the two fields are never cross-checked, an attacker who controls (or names) any org configured in Shipit with no `webhook_secret` can send a self-crafted, unsigned-content payload naming a victim repository's `full_name`, causing the victim's `ReviewStack` to be archived/unarchived and provisioning-queued.

### Finding Description
The broken binding: `params.repository.owner.login` (used to select the signature-verification secret) MUST equal the owner segment of `params.repository.full_name` (used to select the repository whose stack is mutated) — but nothing enforces this equality.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 
2. `Shipit.github(organization:)` looks up per-org config via `github_app_config(organization)` and instantiates a `GitHubApp` for that org. [2](#0-1) 
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that org's `webhook_secret` is blank, regardless of body content: `return true unless webhook_secret`. [3](#0-2) 
4. `WebhooksController#create` then parses the raw body and dispatches to handlers matching the `X-Github-Event` header, passing the whole attacker-controlled hash. [4](#0-3) 
5. `LabeledHandler#repository` resolves the actual `Shipit::Repository` from `params.repository.full_name`, a field completely independent of `repository.owner.login` used in step 1. [5](#0-4) 
6. `LabeledHandler#archive?`/`#unarchive?` evaluate against that resolved repository's `provisioning_behavior_allow_with_label?`/`provisioning_label_name`, comparing to the attacker-supplied `pull_request.labels` list, then call `stack.archive!`/`stack.unarchive!` via `ReviewStackAdapter`, scoped to `repository.review_stacks`. [6](#0-5) 
7. `ReviewStackAdapter#unarchive!` calls `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.unarchive!`; `#archive!` calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, `stack.archive!`. [7](#0-6) 

Exploit: attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, body `{"action":"labeled", "repository":{"owner":{"login":"attacker-org-with-no-secret"}, "full_name":"victim-org/victim-repo"}, "pull_request":{...state:"open", labels:[...] }, "number": N, "sender":{"login":"attacker"}}`, and any (or missing) `X-Hub-Signature`. If `attacker-org-with-no-secret` is any org configured in Shipit's `secrets.github` map without a `webhook_secret` (a supported, documented configuration — `webhook_secret: # nil`), `verify_webhook_signature` passes trivially, but the handler acts entirely on `victim-org/victim-repo`'s `provisioning_behavior`/`provisioning_label_name` and mutates that repository's review stack #N.

Existing guards fail because: `verify_signature` only binds trust to `repository.owner.login`, never to `repository.full_name`; `drop_unhandled_event`/`check_if_ping` don't inspect repository identity; `ExplicitParameters` schema only validates types/presence, not cross-field consistency; there is no model validation tying `full_name`'s owner segment to any org config.

### Impact Explanation
An unauthenticated/unprivileged attacker can cause `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.archive!`/`stack.unarchive!` to run for an arbitrary victim `Repository`'s `ReviewStack`, regardless of the victim org's own `webhook_secret` configuration — a payload nominally scoped to the attacker's own (secret-less) org mutates a different tenant's repository state. This is a cross-repository/cross-tenant confusion bug matching the Critical bucket "a payload for one repository mutating another's stack" and can trigger real infrastructure provisioning/deprovisioning for the victim's PR environment. It is repeatable against any repository tracked by Shipit and any PR number, as long as one org anywhere in the instance's config lacks a `webhook_secret`.

### Likelihood Explanation
Preconditions: (1) Shipit configured with at least one org (attacker-controlled or attacker-nameable) lacking `webhook_secret` — an explicitly supported, common configuration (`webhook_secret: # nil` shown in `config/secrets.development.example.yml` and multi-org examples). (2) The victim repository has `review_stacks_enabled` and `provisioning_behavior_allow_with_label?`/`prevent_with_label?` configured. No GitHub session, API token, or Shipit credentials are required — a single crafted HTTP POST to `/webhooks` suffices. This is highly feasible and cheap to repeat.

### Recommendation
Bind signature verification to the same repository identity used for state mutation: derive the organization for `Shipit.github(organization:)` from `repository.full_name`'s owner segment (not `repository.owner.login`), or explicitly verify `repository.owner.login` matches the owner parsed from `repository.full_name` before dispatching to handlers. Additionally, consider requiring `webhook_secret` to be present for any org that has repositories with review-stack provisioning enabled, and reject payloads where the two owner references disagree.
