Based on my research, I found a genuine analog in the DeepBook v1/v2 legacy modules that mirrors the exact root cause of the Perennial `MarketFactory` bug: fee balances collected by the contract with no code path to ever withdraw them.

### Title
Permanently locked pool `creation_fee` in DeepBook `clob`/`clob_v2` — ([File: crates/sui-framework/packages/deepbook/sources/clob_v2.move])

### Summary
`Pool<BaseAsset, QuoteAsset>` in both `deepbook::clob` and `deepbook::clob_v2` stores the SUI paid to create the pool in a `creation_fee: Balance<SUI>` field. The field is explicitly annotated in-source as "Stores the fee paid to create this pool. These funds are not accessible." [1](#0-0)  The same struct/comment pattern exists in `clob_v2.move`. Unlike the sibling `quote_asset_trading_fees` balance, which is withdrawable through `withdraw_fees` gated by `PoolOwnerCap`, no equivalent accessor exists anywhere in the module for `creation_fee`. [2](#0-1) 

### Finding Description
This is the same class of bug as the Perennial `MarketFactory#fund` issue: value flows into contract-owned storage (`Balance<SUI>` inside a shared `Pool` object) with no corresponding withdraw/claim function reachable by anyone — not the pool owner via `PoolOwnerCap`, not deepbook governance, not any privileged path. `withdraw_fees` only ever calls `balance::split(&mut pool.quote_asset_trading_fees, ...)`; `creation_fee` is never referenced by any function other than in the struct initializer at pool creation. Since `create_pool`/`create_customized_pool`/`create_pool_with_return` in both `clob.move` and `clob_v2.move` are now deprecated and `abort` unconditionally, no new pools can be created going forward, but historically deployed `Pool` objects on-chain still hold their original creation fees in this balance permanently, with zero code path to extract them.

### Impact Explanation
This matches the "High: permanent fund lock" allowed impact category. Funds (pool creation fees, paid in SUI by ordinary users who created pools) are stuck in shared `Pool` objects indefinitely — the same "funds locked with no withdraw mechanism" root cause as the cited Perennial `H-3` finding. The affected `Pool` objects are part of the standard, currently-deployed DeepBook v1/v2 framework packages.

### Likelihood Explanation
The condition is already realized in production: any historical pool created via the (now-deprecated) `create_pool`/`create_customized_pool` functions accumulated a non-zero `creation_fee` balance that can never be moved. No attacker action is required — the funds are locked by design/omission, matching the "no privileged path exists" pattern from the source report rather than requiring an exploit trigger.

### Recommendation
Add a `withdraw_creation_fee` function (analogous to `withdraw_fees`), gated by `PoolOwnerCap` or deepbook package admin capability, that splits and returns the `creation_fee` balance as a `Coin<SUI>`. If `clob`/`clob_v2` are fully deprecated in favor of DeepBook v3, consider a one-time migration function to sweep any remaining locked balances to a designated deepbook treasury/multisig.

### Proof of Concept
Not applicable as an interactive exploit — this is a structural/omission bug, not something an attacker triggers. The proof is the source itself: the `creation_fee` field comment stating "These funds are not accessible" [3](#0-2) , combined with the absence of any function in either module referencing `pool.creation_fee` outside of its initialization, versus the presence of `withdraw_fees` for `quote_asset_trading_fees` [2](#0-1) , confirms the fund-lock exists for any pool created prior to the v1/v2 deprecation.

**Caveat/uncertainty:** I could not fully confirm within the available index whether DeepBook v1/v2 `clob`/`clob_v2` are still considered "in scope" for the current bounty program (they appear deprecated in favor of DeepBook v3, and their `create_pool*` entrypoints now `abort`). If these legacy modules are explicitly out of scope as deprecated/frozen code, this finding would not qualify. I was not able to locate an authoritative in-repo scope statement confirming or denying this either way — this determination would require checking the current HackenProof/Sui bounty scope documentation directly rather than the codebase.

    /// Function to withdraw fees created from a pool
    public fun withdraw_fees<BaseAsset, QuoteAsset>(
        pool_owner_cap: &PoolOwnerCap,
        pool: &mut Pool<BaseAsset, QuoteAsset>,
        ctx: &mut TxContext,
    ): Coin<QuoteAsset> {
        assert!(pool_owner_cap.owner == object::uid_to_address(&pool.id), EIncorrectPoolOwner);
        let quantity = quote_asset_trading_fees_value(pool);
        let to_withdraw = balance::split(&mut pool.quote_asset_trading_fees, quantity);
        coin::from_balance(to_withdraw, ctx)
    }
