### Title
Signed packages verified via `is_valid_signed_package()` are not bound to the consuming AA, enabling cross-AA signature replay - (File: formula/evaluation.js)

### Summary
The oscript primitive `is_valid_signed_package(signed_package, address)` lets an AA accept off-chain-signed data (e.g. a price, an order, an oracle attestation) as valid if it carries a correct signature from `address`. Exactly like the `OrgStoryNFTFactory`/`StoryBadgeNFT` bug, the digest that gets signed and checked binds only to the signer's address and the payload content — it never binds to *which contract (AA)* is consuming it. Any AA author who reuses the same off-chain signer across multiple AAs (a common pattern for oracle/market-maker keys) is exposed to replay of a signature intended for one AA into a different AA that accepts a structurally-similar `signed_message`.

### Finding Description
`is_valid_signed_package` is evaluated in `formula/evaluation.js` by delegating straight to `signed_message.validateSignedMessage`: [1](#0-0) 

`validateSignedMessage` only checks: the author address matches the `address` argument passed by the AA, and that the address's definition validly signs the hash of the package: [2](#0-1) 

The hash that is actually signed/verified is computed by `getSignedPackageHashToSign`, which covers only `signed_message`, `authors` (without authentifiers), `last_ball_unit` and `version` — nothing that ties the signature to a specific AA address or "purpose": [3](#0-2) 

Because none of these fields are forced to include the destination AA's address, the resulting signed blob is a bearer credential valid for *any* AA/consumer that (a) trusts the same signer address and (b) parses a similarly-shaped `signed_message`. This is structurally identical to the `OrgStoryNFTFactory` bug: `keccak256(abi.encodePacked(msg.sender))` bound the signature only to the caller, not to the specific `StoryBadgeNFT` instance, so one signer's signature was valid across every org using that signer. Here, `getSignedPackageHashToSign` binds the signature only to the message content and the signer's address, not to the specific AA that will consume it.

The repo's own sample AA `order_book_exchange.oscript` demonstrates the exact risky pattern: it calls `is_valid_signed_package(trigger.data.order1, $order1.address)` to accept a signed order containing `sell_asset`, `buy_asset`, `sell_amount`, `price`, with no field binding the signature to *this* AA's address: [4](#0-3) 

If the same maker/signer key is used to sign orders for two different AA instances (e.g. two deployments of the same order-book template, or a market-maker key shared across several trading AAs), a signature produced for AA #1 with a given `(sell_asset, buy_asset, sell_amount, price)` tuple is equally valid input to AA #2 as long as AA #2 independently derives the same `$id` from the same fields and hasn't already marked that id executed. The uniqueness check (`var['executed_'||$id1]`) is local per-AA state, so a signature already consumed in AA #1 can be replayed unmodified into AA #2, executing a trade the signer only ever authorized once.

### Impact Explanation
Any AA author using `is_valid_signed_package` without independently embedding the consuming AA's own address (or another unique per-deployment context) inside the signed payload inherits a replay hole: an order/price/attestation signed once by a shared signer key can be fed into a second, independently-deployed AA instance to execute the same authorized action twice (double-execution of a trade, double release of funds, re-use of an oracle price meant for a single consumer). This is a direct AA-fund-loss / unauthorized-state-change vector reachable by any unprivileged unit poster who can trigger the victim AA with a copy of a signed package obtained from (or intended for) a different AA.

### Likelihood Explanation
Reaching this requires only posting a normal AA-triggering unit containing `trigger.data.signed_package` copied from another chain/AA — no privileged role, no node compromise, just crafting the trigger payload, exactly as in the original PoC where Bob simply reused Carl's stored signature against a second deployment. The pattern is realistic and already present in ocore's shipped `order_book_exchange.oscript` sample, which many real AAs are templated from, so any deployment reusing a signer key across instances is exposed.

### Recommendation
Advise/require AA authors (and consider hardening the primitive itself) to force uniqueness of the signed context: either
1. require the signed `signed_message` to embed the specific AA address it is meant for (e.g. `signed_message.aa = this_address`) and have the oscript check `signed_message.aa == this_address` in addition to `is_valid_signed_package`, or
2. extend `getSignedPackageHashToSign`/`is_valid_signed_package` to optionally accept and bind an application-supplied context value (such as the current AA address) into the hash that is verified, so that a signature cannot be validated as-is by any AA other than the one it was produced for.

### Proof of Concept
1. Deploy two instances of `order_book_exchange.oscript` (AA_X and AA_Y) sharing no state.
2. A maker with address `M` signs an order package `signed_package = {signed_message: {sell_asset:A, buy_asset:B, sell_amount:100, price:2}, authors:[{address:M, ...}], last_ball_unit: LBU}` using `signMessage`, as shown in the test harness pattern: [5](#0-4) 
3. Bob posts a trigger to AA_X with `trigger.data.order1 = signed_package` and a matching counter-order; AA_X validates via `is_valid_signed_package(trigger.data.order1, $order1.address)` and executes the trade, setting `var['executed_'||$id1]=1` in AA_X's own state.
4. Bob copies the identical `signed_package` unmodified and posts it as `trigger.data.order1` to AA_Y along with a matching counter-order. Because `getSignedPackageHashToSign` never included AA_Y's address, `is_valid_signed_package` returns `true` again in AA_Y, and since `executed_$id1` is tracked in AA_Y's separate state var space (not AA_X's), the same maker order executes a second time, against the maker's actual (single) intent — a double execution/fund-loss condition for the maker.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
