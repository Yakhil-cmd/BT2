### Title
Unbounded key-range scan in `data_feeds.dataFeedByAddressExists` reachable from an unprivileged `in data feed` spending condition or AA `in_data_feed` check — statement-timeout-style DOS - (File: data_feeds.js)

### Summary
GitLab's bug (BIT-gitlab-2020-26411 / CVE-2020-26411) is a class of "attacker-supplied query parameter forces an unindexed/unbounded scan that runs until a DB statement timeout, enabling a DOS." ocore has a structurally analogous pattern: the `in data feed` / `in_data_feed` primitive lets any unprivileged unit author (in an address definition) or AA trigger sender (in oscript) request a relational (`>`, `<`, `>=`, `<=`, `!=`) search over an oracle's data-feed history for an attacker-chosen `feed_name`/`value`/`min_mci`/`max_mci` window. The lookup is implemented as a raw key-value range scan with no upper bound on the number of records inspected when the searched relation is never satisfied.

### Finding Description
`dataFeedByAddressExists()` in [1](#0-0)  builds a lexicographically-ordered `kvstore` key range from `address`, `feed_name`, encoded `value`, and mci bounds, then streams all matching keys with `kvstore.createKeyStream(options)`, testing each record's mci against `[min_mci, max_mci]`. The scan only stops early via `stream.destroy()` when a satisfying record is found (line 183-185); otherwise it inspects **every** record in the (attacker-controllable) range before calling `handleResult(false)`.

This routine is reachable from two unprivileged paths with no complexity/record-count cap:
1. **Address/asset spending-condition validation** — the `in data feed` opcode in `validateAuthentifiers()` calls `dataFeeds.dataFeedExists(...)` synchronously during signature/spending-condition validation of *any* unit that spends from an address using this condition: [2](#0-1) .
2. **AA formula evaluation** — the `in_data_feed[[...]]` construct in oscript triggers the identical `dataFeeds.dataFeedExists(...)` call during AA trigger execution: [3](#0-2) .

Both call sites pass `oracles` (any valid address(es), not necessarily a trusted/whitelisted oracle — see the definition-time check, which only requires `isValidAddress`, not that the address be pre-existing or privileged): [4](#0-3) . An attacker who controls the `oracles` address (trivially, since it need not exist yet) can:
- author the oracle address themselves and post an unbounded number of `data_feed` messages (any unprivileged unit author can post `data_feed` messages) with the same `feed_name` but values that never satisfy the eventual relational query, and
- define an address (or AA) whose spending condition/state check uses `in data feed`/`in_data_feed` against that oracle+feed_name with a wide `min_mci`/`max_mci` window,

so that every full node that later validates a unit spending from that address, or every AA trigger touching that condition, must run the full unbounded scan synchronously inside `validateAuthentifiers`/AA execution before it can conclude "not found."

Because unit validation and AA-trigger execution happen under the node's serialized write/validation flow (`validate(objJoint, callbacks, external_conn)` in [5](#0-4)  and `handleTrigger`/`handleAATriggers` in [6](#0-5) ), a single crafted unit/trigger causing a very expensive scan stalls that serialized path, delaying validation and stabilization of subsequent units network-wide — directly analogous to the GitLab statement-timeout DOS: an attacker-chosen "query" parameter (feed_name/value/mci range) drives an unbounded scan instead of a bounded lookup.

### Impact Explanation
This does not directly cause unauthorized spending or inflation, but it can degrade a node's ability to timely validate and confirm new units (an accepted impact category per the validation rules: "a network unable to confirm new units"). Because the record-inspection cost scales with the number of data-feed posts the attacker (as oracle) chooses to make — with no complexity charge, no ops budget, and no cap on rows scanned in `dataFeedByAddressExists` — the attacker fully controls both sides of the equation (the query and the haystack), making the achievable slowdown attacker-tunable and effectively unbounded, unlike most oscript operations which are metered by `MAX_COMPLEXITY`/`MAX_OPS`.

### Likelihood Explanation
Medium. The primitive is reachable by any unprivileged unit author (address definitions) and any unprivileged AA-trigger sender (oscript `in_data_feed`), requires no special role, and the attacker fully controls the oracle address, feed name, posted history size, and the query parameters that force a full scan (relation never satisfied, wide mci range). The only friction is the on-chain cost of posting many `data_feed` messages to build up a large history, which is a one-time investment that can then be reused/replayed against every future unit spending from the crafted address or every trigger touching the crafted AA condition.

### Recommendation
- Cap the number of records inspected per `in data feed`/`in_data_feed` evaluation (e.g., abort/return a transient error or count against `MAX_OPS`/`MAX_COMPLEXITY` proportional to records scanned) in `dataFeedByAddressExists`.
- Charge oscript/definition complexity proportional to the potential feed history size (e.g., based on `max_mci - min_mci` or a maintained per-oracle/per-feed post count) rather than a flat cost, so wide, unbounded scans are priced out.
- Consider requiring an index-backed bounded query (e.g., limit via `options.limit`) with a fallback "aborted, inconclusive" result rather than iterating to stream end when no limit is set.

### Proof of Concept
1. Attacker creates address `Oracle` (self-controlled) and posts N `data_feed` messages over time, each with `{"price": <value never satisfying a future relation, e.g. always the string "abc">}` for a fixed `feed_name="price"`, spanning a wide mci range.
2. Attacker defines a second address `Victim` (or an AA) whose spending condition (or oscript logic) contains:
   `['in data feed', [['Oracle'], 'price', '>', 999999999, 0]]` (or the AA equivalent `in_data_feed[[oracles="Oracle", feed_name='price', feed_value > 999999999, min_mci=0]]`).
3. Attacker (or anyone) posts a unit spending from `Victim` / triggers the AA. Each validating node calls `dataFeeds.dataFeedExists` → `dataFeedByAddressExists`, which streams through all N data-feed records for `Oracle`/`price` before concluding "not found," since the relation is never satisfied and no early-exit condition is hit.
4. Repeating/re-triggering this (e.g., spending repeatedly from `Victim`, or invoking the AA repeatedly) forces every validating node to redo the full scan each time, consuming validation/AA-execution time on the serialized write path and delaying confirmation of other units.
