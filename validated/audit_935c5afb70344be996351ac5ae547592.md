Based on the code I inspected, there is a genuine bug in `StackStxOp::check()`.

### Title
`StackStxOp::check` accepts `num_cycles == 0` and out-of-range cycle counts without rejecting the operation - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::check()` is supposed to reject any Stack-STX burnchain operation whose `num_cycles` field is `0` or greater than `POX_MAX_NUM_CYCLES`, but the validation branch only logs a `warn!` and falls through to `Ok(())` instead of returning `op_error::...`. This lets an attacker submit a burnchain `StackStxOp` with `num_cycles = 0` that is accepted as a valid stacking operation by chainstate processing, exactly the equality-breaking scenario described in the question (SINGLE UNLOCK / LOCK CONSERVATION).

### Finding Description
The invariant SINGLE UNLOCK requires that `num_cycles ∈ (0, POX_MAX_NUM_CYCLES]` so that `unlock-height` is well-defined and equals a single, correctly computed future reward-cycle boundary. `StackStxOp::check()` is the sole gate that is supposed to enforce this on the burnchain-op ingestion path: [1](#0-0) 

Concretely:
```
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(
        "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
        self.num_cycles, POX_MAX_NUM_CYCLES
    );
}
```
Unlike the sibling check two lines above it (`stacked_ustx == 0` → `return Err(op_error::StackStxMustBePositive)`), this branch has **no `return Err(...)`**. Execution falls through to `Ok(())` regardless of whether `num_cycles` is `0` or exceeds the maximum. [2](#0-1) 

An attacker can craft their own Bitcoin `StackStxOp` (an unprivileged action requiring only their own Bitcoin inputs and STX, as permitted by the threat model) with the `num_cycles` byte set to `0`. `StackStxOp::parse_from_tx` parses this value directly from the wire format without independently validating it: [3](#0-2) , and `check()` — the only guard against malformed cycle counts — silently accepts it.

I was not able to fully trace, within the available tool budget, the downstream chainstate/Clarity code that consumes an accepted `StackStxOp` (i.e., whether the `.pox-5` contract call synthesized from this op independently re-validates `num_cycles` via something like `check-pox-lock-period`, or whether it trusts the already-`check()`-approved value when computing `unlock-height`). If the downstream consumer trusts the op-level `check()` as the authoritative validation (which is the apparent intent given the dedicated `check()` function and its analogous positive-STX guard), then a `num_cycles = 0` op would propagate into lock-height computation with an ill-defined cycle count — producing either an unbacked instant-unlock or an underflowed/overflowed unlock height, exactly as described in the question.

### Impact Explanation
If the downstream lock-application logic does not independently re-validate `num_cycles`, this is a Critical-severity SINGLE UNLOCK/LOCK CONSERVATION violation: STX could be recorded as "locked" for zero cycles (i.e., never actually locked, while still occupying reward-cycle-wide accounting), or the unlock height computation (typically `current_cycle + num_cycles`) could wrap/underflow depending on how `0` is handled by the reward-cycle arithmetic, corrupting cycle-wide accounting shared with other stackers.

### Likelihood Explanation
The precondition is minimal: any account can broadcast a `PreStxOp` + `StackStxOp` pair on the Bitcoin chain with `num_cycles` byte set to `0` in the StackStxOp payload. Because `parse_data` at [4](#0-3)  reads `num_cycles` directly from raw bytes with no range check at parse time, and `check()` fails to enforce the range at validation time, the bug is trivially reachable by any unprivileged attacker with Bitcoin transaction-crafting ability, and is fully repeatable per Bitcoin block.

### Recommendation
Add the missing `return Err(op_error::...)` (e.g., a new or existing `StackStxInvalidCycles`/`ParseError` variant) inside the `num_cycles` range check in `StackStxOp::check()`, mirroring the pattern used for `stacked_ustx == 0` immediately above it, so that ops with `num_cycles == 0` or `num_cycles > POX_MAX_NUM_CYCLES` are rejected before being admitted into chainstate processing.

2. Call `op.check()` and assert it currently returns `Ok(())` (demonstrating the missing rejection) — expected/fixed behavior should be `Err(op_error::...)`.
3. impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
