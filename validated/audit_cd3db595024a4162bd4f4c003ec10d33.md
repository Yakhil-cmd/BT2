Investigation summary: The reported bug class (ERC-20 tokens reverting on zero-value `transfer`, causing rounding-to-zero fee amounts to brick withdrawals) does not have a demonstrable analog in this codebase. FRAME's native token abstractions explicitly special-case zero-amount transfers as no-ops rather than requiring callers to guard against reverts:

- `pallet-balances`'s `Currency::transfer` and `withdraw`/`deposit_creating` implementations return `Ok(())`/no-op immediately when `value.is_zero()`, with no revert path for zero amounts. [1](#0-0) [2](#0-1) 
- `pallet-contracts`'s `Ext::transfer` and `pallet-revive`'s transfer routine likewise treat zero value as a guaranteed no-op, explicitly documented as avoiding side effects for zero-balance transfers. [3](#0-2) [4](#0-3) 
- Transaction-payment fee-charging code paths (`pallet-transaction-payment`, `pallet-asset-tx-payment`, `pallet-asset-conversion-tx-payment`) all explicitly check `fee.is_zero()` before attempting a withdrawal/transfer, and their `FungiblesAdapter`/`SwapAssetAdapter` implementations enforce a `min_converted_fee` (or filter zero quotes) precisely to avoid a degenerate zero-fee withdrawal. [5](#0-4) [6](#0-5) [7](#0-6) 
- Similarly, `pallet-psm`'s `redeem` extrinsic explicitly guards `if !fee.is_zero()` before invoking `Fungibles::transfer`, avoiding any zero-amount call entirely. [8](#0-7) 
- There's also a dedicated hardening PR (`pr_11795`) ensuring AMM quote functions return `None` rather than `Some(0)` on rounding to zero, which is the FRAME-side equivalent of the recommended PuttyV2 fix, already applied proactively. [9](#0-8) 

Because Substrate's fungible/currency trait implementations (used uniformly across `pallet-balances`, `pallet-assets`, `pallet-contracts`, `pallet-revive`, and the transaction-payment family) do not model "weird" tokens that revert on zero-value transfer — and every call site that computes a fee already special-cases and guards the zero case — there is no reachable path where a rounded-down-to-zero fee transfer would cause a permanent asset lock analogous to the PuttyV2 issue.

	///
	/// This is a no-op for zero `value`, avoiding events to be emitted for zero balance transfers.
	///
	/// If the destination account does not exist, it is pulled into existence by transferring the
	/// ED from `origin` to the new account. The total amount transferred to `to` will be ED +
	/// `value`. This makes the ED fully transparent for contracts.
	/// The ED transfer is executed atomically with the actual transfer, avoiding the possibility of
	/// the ED transfer succeeding but the actual transfer failing. In other words, if the `to` does
	/// not exist, the transfer does fail and nothing will be sent to `to` if either `origin` can
	/// not provide the ED or transferring `value` from `from` to `to` fails.
	/// Note: This will also fail if `origin` is root.
	fn transfer<S: State>(
		origin: &Origin<T>,
		from: &T::AccountId,
		to: &T::AccountId,
		value: U256,
		preservation: Preservation,
		meter: &mut ResourceMeter<T, S>,
		exec_config: &ExecConfig<T>,
	) -> DispatchResult {
		let value = BalanceWithDust::<BalanceOf<T>>::from_value::<T>(value)
			.map_err(|_| Error::<T>::BalanceConversionFailed)?;
		if value.is_zero() {
			return Ok(());
		}
