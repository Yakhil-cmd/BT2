### Title
Uniswap-style AMM AA mints LP shares against an inflated `balance[base]` on the "initial deposit" path, enabling a donation/inflation attack that drains later liquidity providers - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The Terraport incident was a DeFi liquidity-pool drain caused by a flaw in pool accounting/share logic. The closest reachable analog in ocore is the reference Uniswap-like AMM Autonomous Agent (AA) pattern shipped in the codebase and exercised by the ojson/oscript test-suite. Its "invest in MM" branch computes newly minted LP-share (`mm_asset`) amounts using `balance[base]`/`balance[$asset]`, values that are attacker-influenceable by any unprivileged trigger sender, before establishing a real reserve ratio.

### Finding Description
In the AA's "invest in MM" case, when either side of the pool is empty the code treats the call as the very first deposit and mints shares equal to the *entire current byte balance of the AA*, not the amount actually contributed by the caller: [1](#0-0) 

`balance[base]` here (see the `balance[...]` getter semantics in `formula/evaluation.js`) reflects the AA's total base-asset holdings, including any bytes previously sent to the AA address that did not increase `mm_asset_outstanding` — e.g. left-over bounce fees from unmatched triggers, or bytes sent via the "exchange bytes to asset"/"exchange asset to bytes" swap branches before any shares exist. Because `updateInitialAABalances`/`updateFinalAABalances` in `aa_composer.js` credit every received output to the AA's tracked balance unconditionally, an attacker can pad `balance[base]` independently of `var['mm_asset_outstanding']`: [2](#0-1) 

Any unprivileged unit poster can send a trigger to the AA before the legitimate first liquidity provider deposits, so that when the real first deposit occurs, `$asset_balance == 0 OR $bytes_balance == 0` is true and `$issue_amount = balance[base]` is minted using the *inflated* balance rather than the depositor's real contribution. This sets `var['mm_asset_outstanding']` to an artificially large number relative to the pool's real economic value. Because subsequent investors' share allocation is proportional to `mm_asset_outstanding` (`$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`), the attacker who controls the inflated first mint can capture a disproportionate share of future deposits or force later depositors to receive far fewer shares (or lose funds to rounding to zero) relative to the value they contribute, while the attacker later divests using `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` at the true, later reserve ratio, extracting more base/asset value than they put in.

This mirrors the classic ERC4626 "vault inflation / donation attack" vulnerability class: the root cause is that share-minting for the first deposit is based on the AA's *total balance* rather than on a value insulated from unsolicited/no-op prior transfers, and there is no minimum-liquidity lock or explicit check that `mm_asset_outstanding == 0` (only that one of the *reserve* balances reads zero) before treating a deposit as "initial."

### Impact Explanation
An attacker can manipulate the effective share price of the pool at bootstrap and siphon value from subsequent, honest liquidity providers or traders using the "exchange bytes/asset" swap paths, draining part of the pool's liquidity over time — a direct AA fund-loss/value-transfer condition matching the "Impact" bar in the rules (concrete unauthorized value extraction from an AA-held liquidity pool), analogous to the Terraport liquidity drain.

### Likelihood Explanation
This requires only a single unprivileged trigger before the legitimate first deposit (or interleaving with the swap branches when `mm_asset_outstanding` is still 0, since the "exchange bytes to asset"/"exchange asset to bytes" branches are gated by `var['mm_asset_outstanding']` being truthy — meaning bytes can also reach the AA balance via bounced/no-match triggers whose bounce fee is retained by the AA). Any wallet/AA-trigger sender can attempt this at negligible cost (bounce fee only, a few thousand bytes), so likelihood is high whenever an AMM AA following this exact shipped pattern is deployed with real value.

### Recommendation
- Determine "initial deposit" strictly from `var['mm_asset_outstanding'] == 0` (the share-supply state variable) rather than from `balance[base]`/`balance[$asset]` being zero, since the latter can be non-zero due to unrelated incoming transfers/bounce-fee residue.
- Mint initial shares based on a value derived only from the caller's own contributed `trigger.output[[asset=base]]`/`trigger.output[[asset=$asset]]`, not the AA's total balance.
- Optionally lock a small amount of minimum liquidity (never redeemable) on first deposit, matching the standard fix for this bug class in ERC4626/Uniswap V2-style vaults, and reject/refund unsolicited donations that do not match any case (already partially mitigated by bounce, but bounce-fee residue should not be counted toward reserves used for share pricing).

### Proof of Concept
1. Deploy the AA exactly as in `test/samples/uniswap_like_market_maker.oscript`, with `mm_asset` freshly defined and `mm_asset_outstanding` unset (falsy).
2. Attacker sends a trigger with only base bytes (`data: {}`, output `base > 1e5`, no `asset` output). None of the `if` cases match (`invest` needs asset output > 0; `exchange bytes to asset` requires `mm_asset_outstanding` falsy — actually this one *can* match once `mm_asset_outstanding` is falsy, sending bytes straight into `balance[base]` while `var['mm_asset_outstanding']` stays 0, since that branch does not update it). This inflates `balance[base]` without changing `mm_asset_outstanding`.
3. The legitimate first LP now calls "invest in MM" with a genuine deposit; `$asset_balance == 0` is true (no asset in pool yet), so `$issue_amount = balance[base]` — a value inflated by step 2 — is minted disproportionately relative to `var['mm_asset_outstanding']` going forward.
4. Attacker/colluding party who received (or influenced) the inflated first mint later calls "divest MM shares," receiving `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` of the pool's real, later-grown reserves, extracting more value than contributed at the expense of subsequent depositors.
