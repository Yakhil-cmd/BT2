### Title
Forged `status` webhook can inject fake CI status onto any tracked commit across all stacks, enabling unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by picking a GitHub App configuration keyed on `repository_owner` — derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — and checking the signature against that org's `webhook_secret`. [1](#0-0)  The handler that actually mutates state for `status` events, `StatusHandler#process`, never re-derives or checks which repository/org the payload claims to belong to — it looks up commits purely by SHA across the entire database: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1)  This breaks the binding "organization that authenticated versus the repository that is written": the org whose secret validated the signature is never checked against the stack/repository whose `Commit` row is actually updated.

### Finding Description
`Shipit.github(organization:)` supports one GitHub App configuration per organization, each with its own optional `webhook_secret`. [3](#0-2)  If a `webhook_secret` is blank for a given org, verification is a no-op: `def verify_webhook_signature(signature, message); return true unless webhook_secret; ...`. [4](#0-3)  The engine's own test fixtures show this is a supported configuration shape (`webhook_secret: null` for an org, `OrgTwo` in `secrets_double_github_app.yml`).

Contrast the two independent JSON fields the attacker fully controls in the POST body of `WebhooksController#create`:
- `repository_owner` (used only to select which org's app/secret validates the signature): `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [5](#0-4) 
- The field actually used by `PushHandler`/`Handler#stacks` to scope work to a real tracked repository: `payload.dig('repository', 'full_name')`. [6](#0-5) 

`PushHandler` correctly uses this scoped `stacks` helper before acting. [7](#0-6)  `StatusHandler` does not use `stacks`/`repository_name` at all; it only requires `sha` and `state` and matches every `Commit` row with that SHA, regardless of which `stack`/repository it belongs to. [8](#0-7)  `Commit` rows `belongs_to :stack`, and the same underlying git SHA is commonly tracked by multiple independent `Stack` records (e.g. staging/production, or multiple review stacks), each with its own `Commit` row for that SHA. [9](#0-8) 

Because the org used for `verify_signature` is never checked against the repository whose commits get statused, an attacker who can produce a validly-signed webhook for *any* org tracked by the Shipit instance (including a deliberately or accidentally unsecured org with no `webhook_secret`, or their own legitimately webhook-enabled low-value repo) can forge a `status` event carrying an arbitrary `sha` belonging to a *different*, unrelated, higher-value stack, and inject a fabricated `success` status for it via `Commit#create_status_from_github!`. [10](#0-9) 

### Impact Explanation
Injected statuses directly feed `Commit#deployable?`: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. [11](#0-10)  `Commit#schedule_continuous_delivery` automatically enqueues `ContinuousDeliveryJob` once a commit becomes `deployable?` on a stack with `continuous_deployment?` enabled: `return unless deployable? && stack.continuous_deployment? && stack.deployable?`. [12](#0-11)  `Stack.schedule_continuous_delivery` runs this periodically for every continuous-deployment stack. [13](#0-12)  On such stacks, forging a required CI status via this cross-repository confusion can trigger a fully automated, unauthorized deploy of an attacker-chosen, non-CI-passing commit — satisfying the Critical bar of "an unauthorized deploy". Even without continuous deployment, a human operator relying on the (forged) green status in the UI could be tricked into manually deploying an unreviewed/failing commit.

### Likelihood Explanation
Exploitation requires only the ability to send a request to the public `/webhooks` endpoint with a valid signature for *some* org configured on the instance — no Shipit session, API token, or write access to the *target* repository is needed. This is trivially met if any configured org has an unset `webhook_secret` (an explicitly supported configuration, per the engine's own multi-org test fixtures), or if the attacker legitimately controls webhook delivery for any other, unrelated repo/org tracked by the same Shipit instance. The attacker only needs to know a target commit SHA and its `context`/state expectations, both discoverable via GitHub's public API or the Shipit UI.

### Recommendation
`StatusHandler` (and any other handler that mutates `Commit`/`Stack` state without going through `Handler#stacks`) must scope its lookups by the repository declared in the *same* payload that was cryptographically bound to the authenticating org — e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` instead of an unscoped `Commit.where(sha: params.sha)` — so the authenticated org must actually own the repository being mutated. More generally, `WebhooksController#verify_signature` should ensure the org resolved for signature verification matches the org embedded in `repository.full_name`, and reject mismatches, rather than trusting each handler to re-derive scoping independently.

### Proof of Concept
1. Configure (or discover) an org `weak-org` in Shipit with no `webhook_secret` set (supported per `secrets_double_github_app.yml`), or hold a valid webhook secret for any unrelated, low-value repo tracked by the instance.
2. Identify the SHA of a commit on a high-value stack `victim-org/victim-repo` (e.g., via GitHub's public commit history) and the CI `context` that stack's `shipit.yml` marks as `ci.require`.
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "weak-org" } },
  "organization": { "login": "weak-org" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "<required ci context>",
  "created_at": "<iso8601>"
}
```
4. `verify_signature` resolves `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of (or absent) `X-Hub-Signature`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim commit row (belonging to a completely different, properly-secured stack/org), and calls `create_status_from_github!`, marking it `success`.
6. If `victim-org/victim-repo`'s stack has `continuous_deployment: true`, `Commit#schedule_continuous_delivery` fires and the forged commit is deployed automatically without any legitimate CI pass or human authorization.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
