The second disjunct, `features::is_account_abstraction_enabled() && account_abstraction::using_dispatchable_authenticator(transaction_sender)`, is correctly scoped to the specific `secondary_address` being checked. But the first disjunct, `features::is_derivable_account_abstraction_enabled()`, is a **global** feature flag with no account-specific binding at all. This means that as soon as `secondary_signer_public_key_hashes[j] = option::none()` is supplied for *any* secondary signer, the equality check against `account::get_authentication_key(secondary_address)` is skipped unconditionally — not just for genuinely AA-enabled accounts.

## Where full exploitability is uncertain

Whether this Move-level gap is actually reachable by an unprivileged attacker depends on code outside what I was able to fully inspect within the available tool budget: the Rust-side construction of `secondary_signer_public_key_hashes` (in the VM/transaction-validation glue that builds these prologue arguments from the parsed `AccountAuthenticator`s of a `SignedTransaction`), and the derivable-account-abstraction (DAA) authenticator's address-binding verification. Specifically:

- I could not confirm whether the Rust side ever emits `None` for a secondary signer's hash for anything other than a genuine `AbstractionAuthenticator`/derivable-AA authenticator variant. If `None` is only ever produced when the parsed authenticator is itself an abstraction authenticator, the attacker's ability to exploit the gap depends on whether DAA's own signature/address-derivation check (which ties the account address to the abstraction scheme) can be satisfied for an arbitrary pre-existing, non-AA account address. I was unable to locate and verify this derivation-binding logic (e.g., in `account_abstraction` module or the VM authenticator verification path) within this session.
- If DAA's address derivation strictly binds an address to its own scheme (so an attacker cannot forge a valid DAA authenticator for someone else's pre-existing Ed25519-derived address), then the practical impact is limited: the Move-level gap exists, but the outer authenticator-verification layer would reject an attempt to impersonate an arbitrary existing secondary signer this way.

Given this, I can confirm the Move-level logic bug (global flag improperly conflated with a per-account bypass condition) but **cannot fully confirm end-to-end unprivileged exploitability** without inspecting the Rust-side authenticator-to-hash construction and the DAA address-binding checks, which the current index/tool budget did not let me trace to completion.

### Title
Global `is_derivable_account_abstraction_enabled()` flag improperly bypasses secondary-signer auth-key check in `multi_agent_common_prologue` — ([File: aptos-move/framework/aptos-framework/sources/transaction_validation.move])

### Summary
`allow_missing_txn_authentication_key` gates the "missing hash" bypass for a secondary signer partly on a network-wide feature flag (`is_derivable_account_abstraction_enabled`) rather than a per-account condition, unlike its sibling check (`using_dispatchable_authenticator(transaction_sender)`), which is properly account-scoped.

### Finding Description [3](#0-2) 
This function is invoked per-secondary-signer inside `multi_agent_common_prologue` at [4](#0-3) . When the network-wide DAA flag is enabled, `allow_missing_txn_authentication_key` returns `true` for any address regardless of whether that address is actually configured for AA, so a `None` hash for that signer skips the authentication-key equality assertion entirely.

### Impact Explanation
If reachable by unprivileged transaction construction (see caveat above), a secondary signer's binding to a real, verified authentication key could be skipped, breaking the "secondary-signer handling must bind to the intended account set" guarantee called out in the Admission Pivots.

### Likelihood Explanation
Contingent and not fully verified: requires (1) the DAA feature flag enabled network-wide, and (2) the Rust-side transaction/authenticator parsing to allow emitting a `None` hash for a secondary signer whose authenticator does not correspond to that account's genuine derivable-AA registration — which I could not confirm within this session's tool budget.

### Recommendation
Scope the first disjunct in `allow_missing_txn_authentication_key` to the specific `secondary_address`/`transaction_sender` being checked (e.g., require that the address itself is a genuine derivable-AA address per its own derivation scheme), not merely that the feature is globally enabled. Also independently verify, on the Rust side, that a `None` hash can only ever be constructed for authenticators that are cryptographically tied to the target account's address.
