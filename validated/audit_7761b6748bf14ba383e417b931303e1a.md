### Title
Webhook signature verification is scoped by an untrusted `repository.owner`/`organization.login` field that is never cross-checked against the `repository.full_name` used to resolve the target Stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App configuration (and therefore which `webhook_secret`) is used to authenticate an inbound webhook based on a field read straight out of the unverified JSON body: `repository.owner.login` (or `organization.login`). Once that check passes, every webhook handler resolves the actual database record to mutate using a *different* field from the same untrusted body: `repository.full_name` (or, for membership events, `organization.login` again, but team creation is keyed off the same untrusted org string). Because the multi-organization configuration explicitly supports a `webhook_secret` per organization that can be left blank ("optional"), and `GitHubApp#verify_webhook_signature` short-circuits to `true` when no secret is configured, an attacker who can name any org with no configured secret can forge a payload naming a completely different, victim organization/repository as the target of the event.

### Finding Description
`verify_signature` picks the verification key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and that string is used only to look up which `GitHubApp` instance (and its `webhook_secret`) will validate the `X-Hub-Signature` header: [3](#0-2) 

`verify_webhook_signature` is a no-op when the selected organization's secret is blank: [4](#0-3) 

The multi-organization secrets schema documents `webhook_secret` as optional per organization: [5](#0-4) [6](#0-5) 

Once `verify_signature` passes (whether via a real signature, or trivially because that organization's `webhook_secret` is blank), the payload is dispatched to handlers that never re-check `repository.owner.login`. Instead they resolve the target `Repository`/`Stack` from an independent field, `repository.full_name`: [7](#0-6) [8](#0-7) 

The binding the engine implicitly assumes but never enforces is:
`organization_that_authenticated(repository.owner.login) == organization_whose_repository_is_acted_on(repository.full_name's owner segment)`

Since both fields come from the same attacker-controlled JSON body, and nothing ties them together, an attacker can submit a forged webhook whose `repository.owner.login`/`organization.login` names an organization configured with **no** webhook secret (satisfying `verify_signature` for free), while `repository.full_name` names an arbitrary victim repository/stack that Shipit tracks under a different, secured organization. The `PushHandler` will then look up `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueue `GithubSyncJob` for it; `StatusHandler`/`CheckSuiteHandler` (reachable the same way) can inject forged CI status/check-run results for arbitrary commits on that victim stack.

### Impact Explanation
This breaks the trust boundary between "which org's webhook credential authenticated this request" and "which org's repository is mutated by it." An unauthenticated network attacker who can identify any organization present in the multi-tenant `github:` config with a blank `webhook_secret` (an explicitly supported, documented configuration) can forge `push`, `status`, and `check_suite` events for any other tracked repository/stack. Because Shipit's continuous-delivery gating relies on `status`/`check_suite` webhooks to decide whether required checks (`ci.require`, `ci.blocking`) have passed, forging these events for a victim stack can trick continuous delivery into treating unreviewed/malicious commits as CI-green, resulting in an unauthorized deploy of those commits. This lands in the "High/Critical: unauthorized deploy" impact category defined by the rules.

### Likelihood Explanation
Requires zero credentials or session — `/webhooks` is a public, unauthenticated endpoint by design. The only precondition is that the deployment uses the multi-organization GitHub config (explicitly supported and documented) and at least one configured organization has no `webhook_secret` set — a state the shipped example secrets files (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`) present as the normal/default option ("optional"). Even where every org does have a webhook_secret, the underlying design flaw — using one payload field to select the verification key and a different, uncorrelated payload field to select the write target — remains a latent architecture bug that would be exploitable the moment any tenant's secret is unset or leaked, independent of the target tenant's own secret.

### Recommendation
After successfully verifying the signature for organization `O` (as derived from `repository.owner.login` / `organization.login`), every downstream handler must validate that the resource it is about to act on (`repository.full_name`'s owner segment, or `organization.login` for membership/team events) is exactly `O`, and reject/drop the event otherwise. Additionally, treat a blank `webhook_secret` for any configured organization as a hard configuration error (or at minimum require an explicit separate opt-in flag) rather than silently disabling signature verification for that tenant.

### Proof of Concept
Preconditions: multi-org `github:` config with `attacker-org` having `webhook_secret: nil`, and `victim-org/victim-repo` tracked as a Stack under a different, secured org.

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

- `WebhooksController#repository_owner` returns `"attacker-org"`.
- `Shipit.github(organization: "attacker-org")` returns a `GitHubApp` whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
- `PushHandler#repository_name` reads `"victim-org/victim-repo"` from the same payload and resolves `victim-org`'s stacks, enqueuing `GithubSyncJob` for them — fully bypassing any authentication tied to `victim-org`.

The same technique applies to `status`/`check_suite` payloads to inject forged CI results for `victim-org/victim-repo`'s commits.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
