## Analysis

CVE-2020-8619 is a BIND9 crash: a specific, attacker-plantable data combination (an empty non-terminal name plus a wildcard `*` record) causes an internal invariant to be violated, triggering an assertion failure that crashes `named`. The applicable bug class for ocore is: **attacker-controlled data reaching a hard-coded `throw Error(...)` (uncaught exception, not a graceful validation rejection) inside deterministic AA-trigger evaluation logic, crashing every node that processes the trigger**.

I found this exact pattern in the ambiguous-data-feed-candidate sorter used when an AA reads a data feed with `unstable_opts` enabled.

### Title
Uncaught exception in `readDataFeedValue()` candidate sort crashes AA-processing nodes on crafted unstable data feeds - (File: data_feeds.js)

### Summary
When an Autonomous Agent (AA) reads a data feed via `data_feed[[...]]`/`in_data_feed[[...]]` in oscript, `readDataFeedValue()`/`dataFeedExists()` in `data_feeds.js` scan `storage.assocUnstableMessages` for matching, not-yet-stable `data_feed` messages posted by the listed oracle addresses. [1](#0-0)  If more than one candidate unstable message matches, and `ifseveral` isn't `'abort'`, the candidates are resolved by `Array.prototype.sort`, whose comparator falls back to `throw Error("can't sort candidates "+a+" and "+b)` whenever two candidates have identical `latest_included_mc_index` and identical `level` and the call is not in "all unstable" mode. [2](#0-1)  This throw happens synchronously inside the sort comparator during AA trigger evaluation, not via the normal `cb`/error-string channel used elsewhere in the formula evaluator.

### Finding Description
The AA formula evaluator's `data_feed`/`in_data_feed` opcodes call `dataFeeds.readDataFeedValue(...)`/`dataFeeds.dataFeedExists(...)` with `bAA` acting as the `unstable_opts` flag, so `bIncludeAllUnstable` is `false` for ordinary AA reads. [3](#0-2)  An attacker who controls two or more units posting a `data_feed` message from the oracle addresses named in the AA's `oracles` parameter can arrange for those units to land at the same DAG `level` and the same `latest_included_mc_index` while both are still unstable when the AA trigger is processed. Because `level` is derived purely from parent-count graph structure and is attacker-influenceable by choosing parents, and `latest_included_mc_index` likewise depends on included units, producing two colliding candidates is feasible. When the AA trigger fires and multiple such candidates exist for the queried `feed_name`/`feed_value`, `arrCandidates.sort()` reaches the `throw Error("can't sort candidates ...")` branch since `bIncludeAllUnstable` is false. [4](#0-3)  This throw propagates as an uncaught exception (not funneled through the `cb`/fatal-error mechanism the rest of `evaluate()` uses), because it occurs inside the comparator function called by V8's native `Array.sort`, above the evaluator's normal try/catch-free callback chain.

### Impact Explanation
Since AA trigger processing is deterministic and executed identically by every full node validating the DAG, an uncaught exception thrown mid-evaluation is either (a) unhandled at a level that crashes the node process, or (b) caught generically higher up and treated inconsistently across implementations/versions, both of which threaten network-wide agreement on validity for that unit and can halt processing of the AA (denial of service against the AA and, if uncaught at the process level, against the node itself). This matches the "node disagreement on validity/stability" and "network unable to confirm new units" impact classes.

### Likelihood Explanation
Any unprivileged unit poster can trigger this: they need only post ordinary `data_feed` messages from addresses that some AA already trusts as `oracles` (or self-author them if the AA reads its own trigger-address-controlled oracle list), timed/parented so two competing unstable candidates share `level` and `latest_included_mc_index`, then send the AA trigger. No special privilege beyond normal unit posting is required, and the condition is fully reachable through the public `data_feed`/`in_data_feed` oscript primitives used pervasively by AAs.

### Recommendation
Replace the `throw` in the sort comparator in `readDataFeedValue()` with a deterministic, non-throwing tie-break (e.g., compare by `unit` hash lexicographically) so ambiguous candidates always resolve consistently instead of crashing/aborting evaluation, and route any remaining unexpected error condition through the existing `handleResult`/`fatal_error` callback pathway used elsewhere in `formula/evaluation.js` rather than a raw `throw`.

### Proof of Concept
1. Deploy an AA whose formula includes `data_feed[[oracles="ORACLE1:ORACLE2", feed_name="x", ifseveral="last"]]` (default `ifseveral` behavior falls into the sort branch, not `'abort'`).
2. As an unprivileged user, get `ORACLE1` and `ORACLE2` (or any two addresses in the oracle list) to each post a `data_feed` unit with `feed_name="x"` such that both units remain unstable and end up with identical `level` and identical `latest_included_mc_index` (achievable by carefully choosing identical parent sets/timing).
3. Send a trigger to the AA while both posted units are still unstable and matching.
4. During evaluation, `readDataFeedValue()` collects both as `arrCandidates`, and `arrCandidates.sort()` hits `throw Error("can't sort candidates "+a+" and "+b)` [5](#0-4) , raising an uncaught exception during AA trigger processing on every node evaluating this trigger.
