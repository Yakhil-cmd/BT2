### Title
Cross-AA "spot price" manipulation via secondary-trigger cascades — atomic reserve-ratio oracle read (`balance[address, asset]`) - (File: formula/evaluation.js)

### Summary
The MorphoBlue exploit worked because the lending protocol priced collateral using an AMM's instantaneous reserve ratio, and a flash loan let the attacker skew that ratio and immediately borrow against it inside a single atomic transaction. Ocore's oscript engine has a direct structural analog: any AA can read another AA's live token balance with `balance[address, asset]` [1](#0-0) , and Obyte's own reference pattern for building an on-chain AMM (`uniswap_like_market_maker.oscript`) derives an exchange rate directly from `balance[$asset]`/`balance[base]` ratios with no TWAP, min-liquidity, or slippage-oracle protection [2](#0-1) . Because AA triggers can cascade into "secondary triggers" that are all processed synchronously/atomically within the response to a single primary trigger unit [3](#0-2) , an attacker can swap into the AMM AA to skew its reserve balances and, in the very same atomic chain, have a second (attacker-authored) AA read the now-skewed `balance[amm_address, asset]` to compute a manipulated valuation for pricing/borrowing/minting — with no possibility for anyone to intervene between the two steps, exactly mirroring the flash-loan/oracle read atomicity that made MorphoBlue exploitable.

### Finding Description
`balance[param_address, bal_asset]` in the formula evaluator lets any AA formula query the current balance of an arbitrary AA address (not only its own), reading directly from `objValidationState.assocBalances` (which is kept live/mutated during the ongoing bounce/secondary-trigger cascade) or from `aa_balances` [4](#0-3) . This is the same "spot price from raw reserves" pattern the Morpho PoC abused (reading a live, atomically-manipulable AMM pool state as the price oracle) — except here it is a first-class, documented language feature of the AA engine rather than an external dependency.

The `uniswap_like_market_maker.oscript` reference sample demonstrates the intended usage: `$current_ratio = $asset_balance / $bytes_balance` and `$p = $asset_balance * $bytes_balance` computed straight from `balance[$asset]`/`balance[base]` at trigger time, used to price swaps and mint/redeem shares [5](#0-4) [2](#0-1) . Any downstream AA (e.g. a lending/pricing AA analogous to Morpho) that adopts the same idiom and reads a *different* AA's balance ratio as its price feed is consuming an oracle that can be moved within the very same atomic execution as the consumption.

The atomicity that enables "flash-loan-style" manipulation comes from `handleSecondaryTriggers`: when AA1's response sends funds to AA2, AA2 is triggered as a secondary trigger and processed synchronously as part of the same primary trigger's response tree — all within one DB transaction and one set of `arrResponses`, with no intervening block/unit boundary that would let the market or an oracle correct itself [3](#0-2) . The `test('chain of AAs', ...)` test explicitly demonstrates a primary AA forwarding funds to a secondary AA whose formula reads state from the previous (still in-flight) response, confirming that state produced by one AA in the chain is immediately visible and usable by the next AA in the same atomic sequence [6](#0-5) .

### Impact Explanation
If a pricing/lending AA built on this idiom reads another AA's reserve ratio (via `balance[address, asset]`) as its exchange-rate/collateral-value oracle, an attacker can, within a single posted unit and its atomic secondary-trigger cascade:
1. Send a large one-sided swap into the AMM AA, skewing `balance[amm][collateral]` vs `balance[amm][loanToken]`.
2. In the same cascade, trigger the lending AA which reads the now-skewed ratio to over-value collateral or under-value debt and issue an inflated loan / mint an inflated amount of a pegged asset.
3. Reverse the swap (or let it settle) to restore the AMM's true price, walking away with unauthorized asset issuance / fund loss from the lending AA — the same "$230k in one tx" outcome class as MorphoBlue, but denominated in AA-controlled assets instead of USDC/PAXG.

This falls squarely into "concrete unauthorized spending... supply inflation, AA fund loss" territory, and is Medium/High severity depending on the specific consuming AA's design and available liquidity depth.

### Likelihood Explanation
Likelihood depends entirely on real-world AA authors reusing the raw-reserve-ratio pricing idiom that Obyte's own sample code teaches (`uniswap_like_market_maker.oscript`) as an oracle for a *different* AA, since ocore itself does not ship a production lending protocol. Given that `balance[address, asset]` cross-AA reads and secondary-trigger atomicity are core, well-documented, unrestricted AA-engine features usable by any address, and that the reference AMM example provides no TWAP/liquidity-floor safeguards, the underlying primitive for this class of attack is broadly reachable by any unprivileged AA author or trigger sender. Concrete exploitability is contingent on specific deployed AAs combining these primitives, which cannot be confirmed from the ocore repo alone.

### Recommendation
- Discourage/flag use of raw single-block `balance[other_aa, asset]` ratios as price oracles in AA documentation/samples; provide a canonical TWAP or multi-block-averaged pricing primitive for cross-AA consumption.
- Consider making cross-AA balance reads for AAs acting as price sources reflect only *stable* (previous-MCI) balances rather than the live, in-flight balance mutated during the current cascade, removing the "flash loan" atomicity window described above.
- Update `uniswap_like_market_maker.oscript` and related documentation to explicitly warn against exposing instantaneous reserve ratios as an oracle consumable by other AAs without minimum-liquidity checks or slippage/price-impact limits.

### Proof of Concept
Conceptual (ocore-native) reproduction, mirroring the Morpho PoC structure:
1. Deploy AMM AA `M` using the `uniswap_like_market_maker.oscript` pattern holding asset `X` and bytes, with shallow liquidity [7](#0-6) .
2. Deploy lending AA `L` that reads `balance[M, 'X']` and `balance[M, 'base']` to compute the "price" of `X` and lets a borrower mint/withdraw a stablecoin proportional to that price.
3. Attacker posts one unit whose primary trigger swaps a large amount of bytes into `M` (skewing its ratio) and whose secondary trigger, in the same response cascade (`handleSecondaryTriggers`), immediately calls `L` to borrow against `X` collateral priced at the now-skewed `balance[M, ...]` ratio [8](#0-7) .
4. `L` issues an inflated loan/asset amount based on the manipulated price before the AMM ratio can be arbitraged back by any third party, since the whole sequence completes atomically in one unit's response tree.

Note: this scenario requires an actual deployed lending-style AA using this pricing pattern to be concretely exploitable; ocore's repo provides only the enabling primitives (`balance[]` cross-AA reads, atomic secondary-trigger cascades, and the raw-ratio pricing sample) rather than a shipped vulnerable lending AA.

	function handleSecondaryTriggers(objUnit, arrOutputAddresses) {
		conn.query("SELECT address, definition, mci, main_chain_index FROM aa_addresses LEFT JOIN units USING(unit) WHERE address IN(?) AND mci<=? ORDER BY address", [arrOutputAddresses, mci], function (rows) {
			if (rows.length > 0 && constants.bTestnet && mci < testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci)
				rows = rows.filter(function (row) {
					if (row.main_chain_index && row.main_chain_index < mci) // previous definition is already stable
						return true;
					var len = storage.getUnconfirmedAADefinitionsPostedByAAs([row.address]).length;
					if (len > 0)
						console.log("not calling secondary trigger from unit " + objUnit.unit + " to AA " + row.address);
					return (len === 0);
				});
			if (rows.length === 0) {
				saveStateVars();
				addUpdatedStateVarsIntoPrimaryResponse();
				return onDone(objUnit, bBouncing ? error_message : false);
			}
			if (bBouncing)
				throw Error("secondary triggers while bouncing");
			async.eachSeries(
				rows,
				function (row, cb) {
					var child_trigger = getTrigger(objUnit, row.address);
					child_trigger.initial_address = trigger.initial_address;
					child_trigger.initial_unit = trigger.initial_unit;
					if ("max_aa_responses" in trigger && mci >= constants.pemCurvesFixMci) // propagate the cap set on the primary trigger to secondary triggers
						child_trigger.max_aa_responses = trigger.max_aa_responses;
					var arrChildDefinition = JSON.parse(row.definition);

					var child_trigger_opts = { ...trigger_opts };
					child_trigger_opts.trigger = child_trigger;
					child_trigger_opts.params = {};
					child_trigger_opts.arrDefinition = arrChildDefinition;
					child_trigger_opts.address = row.address;
					child_trigger_opts.bSecondary = true;
					child_trigger_opts.onDone = function (objSecondaryUnit, bounce_message) {
						if (bounce_message)
							return cb(bounce_message);
						cb();
					};
					handleTrigger(child_trigger_opts);
				},
				function (err) {
					if (err) {
						// revert
						if (bSecondary)
							return bounce(err);

						return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
					}
					saveStateVars();
					addUpdatedStateVarsIntoPrimaryResponse();
					onDone(objUnit, bBouncing ? error_message : false);
