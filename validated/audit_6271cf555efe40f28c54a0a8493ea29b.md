### Title
Missing verification of `device_address` authenticity in `handleNewSharedAddress` allows a correspondent to hijack signing‑request routing for another cosigner's path - ([File: wallet_defined_by_addresses.js])

### Summary
`walletDefinedByAddresses.handleNewSharedAddress()` (invoked directly from any paired correspondent via the `"new_shared_address"` device message handled in `wallet.js`) validates that the shared-address `definition` hashes to the claimed `address`, and that each `signerInfo.address` in `body.signers` is either a valid Obyte address or `'secret'`, and that it matches the path extracted from the definition. However, it never validates or authenticates the `signerInfo.device_address` field that is stored per signing path. This value is attacker-controlled data accepted at face value and persisted to `shared_address_signing_paths`, which the wallet later uses to route "please sign" requests for that address/path.

### Finding Description
`handleNewSharedAddress` in `wallet_defined_by_addresses.js` performs these checks: [1](#0-0)  it verifies `body.address === getChash160(body.definition)`, that `signerInfo.address` (when present and not `'secret'`) is a valid address, and that each signing path's claimed address matches what `extractAddressPathsFromDefinition` derives from the definition tree. Crucially, `signerInfo.device_address` — the field that will determine *who gets asked to sign* for that address/path — is passed through unchecked into `addNewSharedAddress`: [2](#0-1) , which blindly inserts `(shared_address, address, signing_path, member_signing_path, device_address)` into `shared_address_signing_paths` with no cryptographic binding between `device_address` and the `address`/path it is claimed to represent.

The only authorization gate on accepting the whole message is `determineIfIncludesMeAndRewriteDeviceAddress`, which merely checks that *some* member address in the definition belongs to my own `my_addresses`/`shared_addresses` — it does not verify that every other `device_address` claimed for other cosigners is authentic: [3](#0-2) . Any of the cosigning devices participating in creating the shared address (a normal, low-privilege, unprivileged counterparty in a multisig/private-payment setup) can set an arbitrary `device_address` for a signing path belonging to a *different* cosigner's address, since nothing ties that field to a signature over it or to a lookup proving the claimed device actually controls that address.

Later, when a payment from the shared address needs collecting the missing signature, the wallet uses the routing information from `shared_address_signing_paths` (see the `sign`/`findAddress` machinery in `wallet.js`) to send the `"sign"` request to the recorded `device_address`. If that field was poisoned by the attacker, sign requests for the legitimate cosigner's key are misrouted to the attacker's device instead, so the legitimate signer never receives them and the transaction can never be completed and broadcast.

This is analogous to the Arduino Create Agent CWE‑345 finding: an endpoint accepts attacker‑supplied data (`device_address`) that is used to make security‑relevant decisions (who is authorized/asked to provide a private signature) without verifying its authenticity/binding to the entity it claims to represent.

### Impact Explanation
A cosigner participating in setting up (or being invited into) a multisig/shared address can cause funds sent to that shared address to become **permanently unspendable/frozen** for the legitimate owner, because the wallet will forever route signature requests for that signing path to the attacker's device rather than the genuine cosigner's device. This matches the "AA fund loss or freezing" / "node disagreement" class of impact accepted by the validation criteria, expressed here as wallet/contract funds freezing rather than an AA specifically, since the vulnerable code path is explicitly part of "wallet and contract message handling" that is in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in shared/multisig or arbiter-style wallet flows: any party invited to co-create a shared address (a normal, unprivileged interaction — e.g. business partners setting up an escrow, or a private-payment counterparty establishing a shared address) can supply this message, and the vulnerable function performs no verification that the claimed `device_address` actually corresponds to the underlying member address before persisting and later trusting it for routing signature requests.

### Recommendation
When processing `handleNewSharedAddress`, require independent verification of each cosigner's `device_address`, e.g. by requiring that the device address be attested by the corresponding member itself (a signed confirmation from the addressed device) or by cross-checking against previously-paired correspondent records (`correspondent_devices`) rather than trusting values embedded by another cosigner in the shared `body`. At minimum, disallow overwriting/creating routing entries for signing paths whose claimed member address is not the sender's own and is not independently confirmed by that member's device.

### Proof of Concept
1. Alice and Bob agree to create a 2-of-2 shared address; Bob is malicious.
2. Bob sends a `"new_shared_address"` device message to Alice with a valid `definition` (hashing correctly to `body.address`) and `signers` map where the entry for Alice's own signing path specifies `address: <Alice's real address>` but `device_address: <Bob's device address>` (attacker-controlled, unrelated to Alice's actual device).
3. `handleNewSharedAddress` accepts the message: the address-vs-definition hash check passes, the per-path address match against `extractAddressPathsFromDefinition` passes (because `address` is still correct), and there is no check at all on `device_address`.
4. `addNewSharedAddress` persists `shared_address_signing_paths` with Bob's device as the routing target for Alice's signing path.
5. When any future payment needs Alice's signature share for that shared address, the wallet's sign-request routing sends the request to Bob's device instead of Alice's, so Alice's genuine device never signs, and the transaction — and the funds locked in the shared address — can never be completed.

// Checks if any of my payment addresses is mentioned.
// It is possible that my device address is not mentioned in the definition if I'm a member of multisig address, one of my cosigners is mentioned instead
function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
