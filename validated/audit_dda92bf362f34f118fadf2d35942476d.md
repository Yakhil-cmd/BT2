Signature verification keyed on unauthenticated `repository.owner.login` allows cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against by reading `repository_owner` straight out of the still-unauthenticated JSON body, before the signature has been checked. The actual repository/stack that event handlers act on is read from the same unauthenticated body (`repository.full_name`). These two fields are never bound to each other or cross-checked against the org whose secret validated the request.

### Finding Description
In a multi-organization Shipit deployment (`docs/setup.md:181-216`), each GitHub organization has its own `webhook_secret` under `Shipit.github(organization:)`. The controller resolves the signing secret to use like this: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload, with no relation yet established to the HMAC: [2](#0-1) 

Meanwhile, `verify_webhook_signature` treats an organization with no `webhook_secret` configured as automatically verified: [3](#0-2) 

and `GitHubApp#initialize` simply take whatever is configured for that org, defaulting to `nil` if absent: [4](#0-3) 

After signature "verification" passes (or is trivially skipped, e.g. for an org configured without a `webhook_secret`, which the setup docs mark as optional at `docs/setup.md:30`), the actual event handler resolves the target `Stack`/`Repository` from a *different, unauthenticated* field of the same payload: `repository.full_name`, completely independent of `repository.owner.login`: [5](#0-4) [6](#0-5) 

This breaks the binding "organization whose secret authenticated the request" = "repository whose stack is written." An attacker who controls (or is simply not required to prove control of) an organization `X` configured in Shipit with no `webhook_secret` (or a leaked/guessable one) can send a webhook claiming `repository.owner.login = X` (satisfying `verify_signature`) while setting `repository.full_name` to any other organization/repo's stack tracked by the same Shipit instance, e.g. `"unrelated-org/production-repo"`. Because `PushHandler`, `check_suite`, `status`, and `pull_request` handlers key exclusively off `repository.full_name` for locating the `Stack`/`Repository` to mutate, the forged payload is applied against a stack the attacker does not control.

### Impact Explanation
This allows an unauthenticated (or org-A-authenticated) actor to trigger `GithubSyncJob` (`stack.sync_github`) against an arbitrary tracked stack belonging to a different organization, push commit statuses, close/archive/unarchive review-stack pull requests, or create teams/memberships tied to unrelated repositories — all state-changing actions gated only by "did the signature validate," not "does this org own this repository." In deployments using the no-secret config (explicitly documented as optional at `docs/setup.md:30`) or where one org's `webhook_secret` is weaker/leaked, this becomes cross-repository writes / unauthorized deploy triggering, matching the High/Critical impact bar (cross-repository writes, unauthorized deploy).

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, and (2) at least one configured organization with no `webhook_secret` set (explicitly supported/optional per `docs/setup.md`) or a weaker secret than the target org. Given that many self-hosted setups leave `webhook_secret` blank for convenience (per the example configs `config/secrets.development.example.yml:11` and `config/secrets.development.shopify.yml:9,18` showing it commented/nil), this is a realistic misconfiguration rather than a purely theoretical one, and no attacker credentials, GitHub App keys, or session are needed.

### Recommendation
After `verify_webhook_signature` succeeds for the organization derived from `repository.owner.login`, re-validate that the `repository.full_name` in the payload actually belongs to that same organization (e.g., assert the owner segment of `full_name` matches `repository_owner`) before dispatching to any handler. Additionally, treat an org with no configured `webhook_secret` as non-authenticating for cross-repo actions (do not silently return `true`), or require `webhook_secret` to be mandatory in multi-org configurations.

### Proof of Concept
Conceptual request (no valid credentials required beyond org `no-secret-org` having no configured `webhook_secret`):
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # ignored because no-secret-org has no webhook_secret
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "full_name": "victim-org/production-stack",
    "owner": { "login": "no-secret-org" }
  }
}
```
`verify_signature` resolves `Shipit.github(organization: "no-secret-org")`, whose `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank), so the request passes. `PushHandler#process` then looks up the stack via `Repository.from_github_repo_name("victim-org/production-stack")` and calls `stack.sync_github(expected_head_sha: "deadbeef")`, acting on a stack unrelated to `no-secret-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
