### Title
Unauthenticated SSE stream exposes live stack/task/deploy events to any caller - ([File: config/routes.rb])

### Summary
`Shipit::Engine.routes.draw` mounts `Pubsubstub::StreamAction.new` directly as a Rack endpoint at `/events`, bypassing the `ApplicationController`/`Shipit::ShipitController` filter chain entirely. Because `Shipit::Authentication#force_github_authentication` is a Rails controller `before_action` and `Pubsubstub::StreamAction` is a raw Rack app mounted via `mount`, no authentication check in this engine's own code runs before the request is served, allowing any unauthenticated caller to subscribe to `stack.<id>` (and other) pubsub channels and receive live task/deploy status events.

### Finding Description
The broken binding: `response_for(GET /events) == response_for(GET /events) after current_user.authorized? == true` — i.e., the engine intends that `Shipit::Authentication#force_github_authentication` gates all engine responses, but for `/events` this equality fails because no such check runs at all.

Code path:
- `config/routes.rb:9`: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` — this is declared as a top-level Rack mount, not a `resources`/`get ... controller:` route.
- All authenticated engine pages inherit authentication from `Shipit::ShipitController` (`app/controllers/shipit/shipit_controller.rb:18`, `include Shipit::Authentication`), which wires `before_action :force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:8`). This mechanism only applies to Rails controller actions dispatched through `ActionController::Base`/`ApplicationController`; it cannot intercept a `Rack::Builder`/`mount`ed endpoint, since `mount` hands the request directly to the target Rack app's `call` method, skipping the entire controller/filter pipeline.
- `Stack#broadcast_update` (`app/models/shipit/stack.rb:561-567`) publishes stack updates to channel `"stack.#{id}"` via `Pubsubstub.publish` on every stack update, and other code (deploys/tasks, per grep matches in `stacks/show.html.erb`, `all_tasks.html.erb`, `merge_requests/index.html.erb`) subscribes browsers to these channels through this same `/events` mount for live UI updates.
- Because `/events` has no controller-level `before_action`, no `Shipit::Authentication` concern, and no Rack middleware added by this engine (`lib/shipit/engine.rb` only adds `OmniAuth::Builder` and optionally `Shipit::SameSiteCookieMiddleware`, neither of which perform authorization), an attacker can send `GET /events?channels[]=stack.<id>` with no session cookie and receive the SSE stream unauthenticated.
- Existing guards checked and found not applicable: `force_github_authentication`, `User#authorized?`, and `require_permission!` are all controller-action-scoped and never execute for a `mount`ed Rack app; there is no Rack middleware in this engine wrapping `/events`; `ExplicitParameters`/model validations are irrelevant since the request never reaches a Shipit controller/model layer for auth purposes.

Attacker request: `GET /events?channels[]=stack.<stack_id>` (guessing or enumerating small sequential integer stack IDs), with no `Shipit` session cookie, no API token, and no GitHub credentials.

### Impact Explanation
The attacker obtains live, unauthenticated read access to task/deploy status change events (e.g., stack updates published via `Stack#broadcast_update`) for any stack in the Shipit instance, including stacks belonging to repositories they have no relationship to. This matches the "High - unauthenticated read of stack state, task streams or deploy output" impact category. The exploit is trivially repeatable against arbitrary stack IDs (simple enumeration, since stack IDs are typically small sequential integers) and affects every tenant/repository hosted on the same Shipit instance — the blast radius is instance-wide, not limited to a single repository.

### Likelihood Explanation
No special configuration is required beyond the documented default mount in `config/routes.rb`. The attacker needs only network access to the Shipit host and a guessed/enumerated stack ID — no secrets, sessions, or privileged roles. This is very low cost and fully repeatable, and does not depend on GitHub-side actions (webhooks, PRs) at all — a bare unauthenticated HTTP client is sufficient.

### Recommendation
Wrap `/events` with the same authentication concern used elsewhere, e.g., replace the direct engine-level `mount` with a Rails controller action guarded by `Shipit::Authentication` (or a dedicated `EventsController`), or add engine-level Rack middleware that validates the session/authorization before allowing `Pubsubstub::StreamAction` to handle the request. Additionally, validate that the requested `channels[]` values correspond to stacks the authenticated `current_user` is authorized to view, to prevent cross-tenant channel subscription even for authenticated users.

### Proof of Concept

```ruby
# test/integration/events_stream_authentication_test.rb
require 'test_helper'

module Shipit
  class EventsStreamAuthenticationTest < ActionDispatch::IntegrationTest
    test "GET /events with a stack channel is rejected for unauthenticated callers" do
      stack = shipit_stacks(:shipit)

      # No session cookie, no API token, no GitHub credentials set up here.
      get "/events", params: { channels: ["stack.#{stack.id}"] }

      # Binding under test:
      #   response_for(GET /events) should equal
      #   response_for(GET /events) AFTER current_user.authorized? == true
      # i.e. the engine should reject (401/403/redirect) exactly like any other
      # Shipit::ShipitController action does via force_github_authentication.
      assert_response :unauthorized # or :forbidden / :redirect, per fixed behavior
      # Currently fails: Pubsubstub::StreamAction responds 200 with an open SSE
      # stream, proving no authentication guard runs for this mounted Rack app.
    end
  end
end
```
This test currently fails against `config/routes.rb:9`, because the mounted `Pubsubstub::StreamAction` returns a `200` SSE stream regardless of authentication state, demonstrating the missing authorization binding.
