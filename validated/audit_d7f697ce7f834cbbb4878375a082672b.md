### Title
Oracle‑priced synthetic asset redemption in AAs can be drained to insolvency, freezing later redeemers' funds - ([File: test/samples/futures_contract.oscript])

### Summary
The Ubiquity report describes a stablecoin redemption function that pays out collateral at an assumed 1:1 rate without verifying that the pool actually holds enough collateral to honor all outstanding claims, so a price move (or a race among redeemers) can leave the last redeemers with claims but no backing. The same design pattern is directly reachable inside ocore's Autonomous Agent (AA) layer: an AA can issue an uncapped, price‑pegged asset against incoming bytes and later redeem it back for bytes using a value read from an oracle `data_feed`, with no check that the AA's actual `bytes` balance can cover all still‑outstanding tokens at the current exchange rate. Because AAs are triggered by ordinary unit posters and because ocore auto‑mints uncapped AA-defined assets on demand, this exact insolvency/"first-come-first-served" freezing scenario is fully reachable through normal payment/trigger units.

### Finding Description
`aa_composer.js`'s `issueAsset` function silently mints more of an uncapped, AA‑defined asset whenever an AA needs to complete an output for that asset and doesn't currently hold enough balance: [1](#0-0) 

This means the "issuance leg" of a synthetic-asset AA (e.g. `usd_asset`/`gb_asset` in `futures_contract.oscript`) never bounces — the AA can always mint tokens 1:1 against bytes received, exactly as shown here: [2](#0-1) [3](#0-2) 

The redemption leg, however, pays real bytes back out of the AA's actual balance based on a value pulled from a single oracle `data_feed` (`GBYTE_USD_MA_2019_04_30`), with the payout amount computed purely from the trigger's token amounts and the oracle price — there is no check that `balance[base]` (the AA's real reserve) is sufficient to cover *all* outstanding `usd_asset`/`gb_asset` supply at that price, only that this particular payment can be completed: [4](#0-3) 

When `completePaymentPayload` cannot find enough unspent `base` outputs to satisfy a requested amount, it simply bounces that one trigger: [5](#0-4) 

So the underlying reserve/liability mismatch is never validated as an invariant of the AA; it is only implicitly discovered per-trigger, one redeemer at a time. Because token issuance (the liability side) is essentially unconstrained thanks to auto-minting in `issueAsset`, while the collateral pool (the asset side) is finite and priced off a single external oracle, any adverse price move or period of heavy redemption produces the same insolvency pattern described in the report: whichever redeemers get their unit stabilized first drain the AA's real byte balance, and every subsequent, otherwise-valid redemption trigger for the same synthetic asset is bounced ("not enough funds for ... bytes"), permanently stranding the tokens held by the losers with no path to recover value.

### Impact Explanation
This is a concrete AA fund-freezing / protocol-insolvency scenario reachable by any trigger sender:
- Holders of the synthetic asset who redeem after the pool is drained have their trigger unconditionally bounced and their tokens become permanently unredeemable (frozen value), matching "protocol insolvency and inability to redeem" in the source report.
- The condition is easy to trigger because minting is essentially unconstrained (`issueAsset` never checks real backing) while the payout leg is a race for a finite, oracle-priced reserve.
- No privileged action, admin pause, or off-chain monitoring exists to prevent it — the imbalance builds up silently through ordinary payment triggers.

### Likelihood Explanation
Any user (an "AA trigger sender") can post ordinary payment units to the AA to buy synthetic tokens and later to redeem them; no special permissions are required. A benign price swing recorded by the oracle, or simply enough volume of buys followed by redemptions, is sufficient to exhaust the AA's base balance before all outstanding tokens are redeemed. This pattern is explicitly demonstrated as a valid, "supported" AA design in ocore's own documentation samples, indicating it is a realistic construct AA authors are encouraged to build, not a contrived edge case.

### Recommendation
- In oscript/AA design guidance (and ideally via new formula-language primitives), require synthetic/pegged-asset AAs to track total outstanding supply and verify a solvency invariant (`balance[base] >= total_outstanding_supply * live_price`) prior to any further minting, and to reduce payout proportionally (haircut) rather than fully honoring first-come redemptions when the pool is undercollateralized.
- Consider tightening `issueAsset` in `aa_composer.js` so uncapped-asset minting driven purely by "not enough balance to complete this output" can be made conditional on an issuer-supplied invariant/guard, rather than being unconditionally auto-minted.
- Document this insolvency/race risk prominently for AA authors building oracle-priced redeemable assets, since ocore currently provides no built-in solvency safeguard.

### Proof of Concept
1. Deploy an AA modeled on `test/samples/futures_contract.oscript`: it defines `usd_asset` and `gb_asset` (uncapped, `issued_by_definer_only: true`) and mints them 1:1 against bytes sent by any trigger sender (`trigger.output[[asset=base]] >= 1e5`).
2. Multiple trigger senders buy `usd_asset`/`gb_asset` with bytes; the AA balance in `base` grows in lock-step with token supply and `issueAsset` (aa_composer.js:1175-1212) mints on demand with no backing check.
3. Once the oracle (`X55IWSNMHNDUIYKICDW3EOYAWHRUKANP`, feed `GBYTE_USD_MA_2019_04_30`) posts a price move (or simply after maturity), the earliest redeemers submit "pay bytes in exchange for the assets" triggers; each is processed independently via `completePaymentPayload`, paying out real bytes from the shared pool.
4. Because minting was unconstrained, cumulative `usd_asset`/`gb_asset` supply can require more bytes at the recorded price than the AA's actual `base` balance holds.
5. Later, otherwise valid redemption triggers fail with `'not enough funds for ' + target_amount + ' bytes'` (aa_composer.js:1231-1232) and are bounced — those token holders can never redeem, demonstrating protocol insolvency and permanent loss/freezing of funds for an unprivileged trigger sender.
