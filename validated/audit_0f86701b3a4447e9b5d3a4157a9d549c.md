### Title
Webhook signature is verified against the org named in `repository.owner.login`, but every handler acts on the unauthenticated `repository.full_name` field - allowing a legitimate GitHub App tenant to forge events against another tenant's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to verify the HMAC against based on `repository.owner.login` (or `organization.login`) taken straight from the *unverified* JSON body [1](#0-0) [2](#0-1) . Every event handler, however, resolves the *actual repository/stack to act on* from a different field of the same unverified body: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties `full_name`'s owner segment to the `owner.login`/`organization.login` that was used to select the verifying secret. In a Shipit deployment configured with multiple GitHub Apps/organizations (a supported and tested configuration - see `test/dummy/config/secrets_double_github_app.yml`), a party that legitimately owns one configured organization's webhook secret can forge a payload whose `owner.login` names their own org (so the signature check passes with their own known secret) while `full_name` names a *different* configured organization's repository, causing Shipit to act on that other tenant's stack.

### Finding Description
- `verify_signature` computes `repository_owner` from the raw, not-yet-verified request body and uses it only to select the HMAC secret: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [2](#0-1) 
- All webhook handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, `pull_request/*`) derive the target `Repository`/`Stack` via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')`. [4](#0-3) 
- These two fields (`repository.owner.login` used for auth, `repository.full_name` used for effect) are independent JSON keys in the same attacker-supplied body and are never cross-checked for consistency.
- `Shipit.github(organization:)` supports multiple distinct GitHub App configs, each with its own `webhook_secret`, keyed by organization name (confirmed by the multi-org fixture `test/dummy/config/secrets_double_github_app.yml`, e.g. `OrgOne`/`OrgTwo`).

The binding that is supposed to hold is: `organization whose secret authenticated the request == organization that owns the repository the handler mutates`. Before the exploit, this holds implicitly. After the attacker's payload, it is broken: the request is authenticated as `OrgTwo` (attacker-controlled/known secret) but the handler mutates a `Stack` belonging to `OrgOne` (or any other configured org), because `full_name` is never checked against `repository_owner`.

### Impact Explanation
An attacker who is a legitimate GitHub App owner/installer for one organization configured in a multi-tenant Shipit instance can forge events (`push`, `status`, `check_suite`, `membership`, `pull_request`) that are attributed to and acted upon a completely different organization's stacks that they have no GitHub-side control over:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` for stacks in the victim org, triggering `GithubSyncJob` which fetches commits from the victim repo using the victim stack's own credentials and appends them, potentially unlocking deploys or changing the deploy queue for a repository the attacker does not control. [5](#0-4) 
- `StatusHandler#process` and `CheckSuiteHandler#process` let the attacker inject fabricated CI status/check results against a victim commit, which can be used to satisfy Shipit's safety checks and unlock a deploy the attacker does not otherwise have rights to trigger. [6](#0-5) [7](#0-6) 

This is a cross-repository/cross-organization write triggered without any of the credentials that should be required to act on the victim org (no victim `webhook_secret`, no victim GitHub App installation access), matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate holder of a webhook secret/GitHub App configured for *some* organization in the same Shipit instance - i.e., this only matters for the documented multi-organization/multi-tenant deployment mode (evidenced by the repo's own multi-app fixture). Within that mode, no additional privilege is needed: the attacker simply POSTs a hand-crafted JSON body with mismatched `owner.login`/`full_name` and a correctly-computed HMAC using their own secret. Single-org deployments are not exploitable this way since there is only one secret and one set of repositories to select from, but the vulnerable code path (`repository_owner` for auth vs `full_name` for action) exists unconditionally in the shared engine code.

### Recommendation
After `verify_webhook_signature` succeeds, derive the acted-upon repository from the *same* authenticated organization used for signature selection rather than trusting `full_name` independently. Concretely, in `Handler#repository_name` (or in `WebhooksController`), assert that the owner segment of `payload.dig('repository', 'full_name')` matches `repository_owner`/the organization whose secret validated the request, and reject (422) the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/orgs, `OrgOne` (victim, has stacks) and `OrgTwo` (attacker's own org, attacker knows `OrgTwo`'s `webhook_secret` because they configured/installed that GitHub App), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha, or a real sha reachable from victim's repo>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgTwo_webhook_secret, raw_body)>` and POSTs it to `/github/webhooks` (or whatever route maps to `WebhooksController#create`).
4. `verify_signature` resolves `repository_owner == "OrgTwo"`, fetches `OrgTwo`'s `webhook_secret`, and the signature verifies successfully. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgOne/victim-repo")` (unrelated to `OrgTwo`) and calls `sync_github` on them, causing `GithubSyncJob` to run against `OrgOne`'s stack despite the request only being authenticated for `OrgTwo`. [4](#0-3) [5](#0-4)
