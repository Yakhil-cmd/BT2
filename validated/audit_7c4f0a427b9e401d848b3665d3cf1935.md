### Title
Unauthorized asset donation to the deterministic pool account disrupts `pallet-asset-conversion` first-liquidity bookkeeping - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
The Solidity report describes a griefing pattern: a protocol has a special "first deposit" branch that initializes bookkeeping state, and any unprivileged user can pre-empt that branch by directly depositing funds into the protocol's account through an unrelated, unprivileged entry point (`Controller.deposit`), corrupting the "is this the first deposit" check and breaking subsequent legitimate calls. I looked for an FRAME analog with the same shape: a pallet that (a) derives a deterministic account for pooled funds, (b) branches its "first liquidity" logic on the observed balance of that account rather than on its own internal accounting, and (c) is reachable by ordinary signed transfers that bypass the pallet's own entry point. `pallet-asset-conversion`'s `do_add_liquidity` matches this shape.

### Finding Description
`do_add_liquidity` in `substrate/frame/asset-conversion/src/lib.rs` (lines 790-892) reads the pool account's *actual* token balances to decide how to price a deposit: [1](#0-0) 

```
let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;
let pool_account = T::PoolLocator::address(&pool_id)...;
let reserve1 = Self::get_balance(&pool_account, asset1.clone());
let reserve2 = Self::get_balance(&pool_account, asset2.clone());
...
if reserve1.is_zero() || reserve2.is_zero() {
    amount1 = amount1_desired;
    amount2 = amount2_desired;
} else {
    let amount2_optimal = Self::quote(&amount1_desired, &reserve1, &reserve2)?;
    ...
}
``` [2](#0-1) 

The "first deposit" branch (`reserve1.is_zero() || reserve2.is_zero()`) is meant to fire only when the pool has never received liquidity, i.e. when the pallet's own `LP token total_issuance` is still zero: [3](#0-2) 

```
let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
let lp_token_amount: T::Balance;
if total_supply.is_zero() {
    lp_token_amount = Self::calc_lp_amount_for_zero_supply(&amount1, &amount2)?;
    T::PoolAssets::mint_into(pool.lp_token.clone(), &pool_account, T::MintMinLiquidity::get())?;
} else { ... }
ensure!(lp_token_amount > T::MintMinLiquidity::get(), Error::<T>::InsufficientLiquidityMinted);
```

`pool_account` is a deterministic function of `(asset1, asset2)` computed by `T::PoolLocator::address`, callable by anyone off-chain, and it can hold a nonzero token balance *before* any `add_liquidity` call ever succeeds — via an ordinary, unprivileged `Assets::transfer`/`Balances::transfer` to that address. Because the branch that decides pricing (`reserve1.is_zero() || reserve2.is_zero()`) checks the *account's raw balance*, not the pallet's own `total_supply`/`Pools` state, an attacker who sends a small "dust" amount of both `asset1` and `asset2` directly to the not-yet-liquidity-bearing pool account forces the legitimate first liquidity provider into the `quote()`-based proportional branch instead of the intended "arbitrary first amounts" branch — exactly the same class of bug as the Solidity report: an unprivileged deposit into the protocol's account disrupts a check gated on "is this the very first deposit," even though the pallet's own bookkeeping (`total_supply == 0`, `Pools` entry not yet backed by liquidity) still thinks it is.

Consequence: `Self::quote(amount1_desired, reserve1, reserve2)` uses the attacker-chosen dust ratio to compute `amount2_optimal`. Depending on the attacker's chosen ratio relative to the legitimate depositor's desired amounts, this can push `amount1`/`amount2` down to values far below what the depositor intended, which combined with `T::MintMinLiquidity` can push `lp_token_amount` at or below `MintMinLiquidity`, triggering `Error::<T>::InsufficientLiquidityMinted` and reverting the depositor's `add_liquidity` call — a direct denial-of-service on that specific pool, reachable by any signed account with no special privilege, and requiring only a de minimis dust transfer.

### Impact Explanation
This is a griefing/DoS on the affected asset pair's pool creation flow, not a fund-theft or unbacked-issuance bug: the attacker cannot mint themselves LP tokens for free, and `total_issuance` accounting for the LP asset itself is not corrupted (the mint-min-liquidity check still correctly rejects an unsafe mint). The main measurable effect is that a legitimate first liquidity provider's chosen `amount1_desired`/`amount2_desired` can be forced through an unintended pricing path and, in adversarially chosen cases, made to revert (`InsufficientLiquidityMinted`), requiring the depositor to retry with different parameters (e.g., after querying `reserve1`/`reserve2` first). Unlike the CrabStrategy report — where *every subsequent* deposit was permanently blocked because the missing one-time initialization branch was a load-bearing state variable used forever after — here the pallet's own `Pools`/`total_issuance` state is unaffected, so once the first `add_liquidity` succeeds (with correctly recomputed amounts, or once `remove_liquidity`/no legitimate LP has claimed), the pool functions normally. This materially reduces severity relative to the Solidity original.

### Likelihood Explanation
Likelihood is high in the sense that reachability requires nothing beyond a signed account and knowledge of `T::PoolLocator::address(pool_id)`, which is a pure deterministic function computable off-chain by anyone before the pool is even created; however, exploitation to cause an outright revert (rather than merely a suboptimal price) depends on the attacker guessing/matching a dust ratio relative to the victim's unknown `amount1_desired`/`amount2_desired`, which the attacker does not control and may not know in advance for a front-run scenario without also being able to observe the victim's pending extrinsic in the transaction pool.

### Recommendation
Gate the "first deposit" pricing branch in `do_add_liquidity` on the pallet's own bookkeeping (`total_supply.is_zero()` from `T::PoolAssets::total_issuance`) rather than on the pool account's raw asset balances (`reserve1`/`reserve2`). This prevents unsolicited direct transfers to the deterministic pool account from being able to influence which pricing branch is taken for the first legitimate liquidity provision.

- I confirmed the code paths above via static reading of `substrate/frame/asset-conversion/src/lib.rs` (`do_add_liquidity`, lines 790-892).
- I did not obtain the exact bodies of `Self::quote`, `Self::calc_lp_amount_for_zero_supply`, `Self::get_balance`, or the configured `MintMinLiquidity`/`PoolLocator::address` for a concrete runtime, so I could not compute concrete numeric amounts that force `InsufficientLiquidityMinted` nor run a `#[test]` reproduction in `substrate/frame/asset-conversion/src/tests.rs`.
- No existing test in `substrate/frame/asset-conversion/src/tests.rs` (e.g., `can_add_liquidity`, `check_no_panic_when_try_swap_close_to_empty_pool`) exercises a pre-funded pool account via direct transfer before the first `add_liquidity` call, so this exact scenario appears untested in the current suite, but that alone does not confirm exploitability at scale — it is a **needs validation** finding rather than a confirmed exploit with measured impact, per the repository's own `RESEARCHER.md` guidance to require target-specific reproduction before elevating a cross-domain analogy to a confirmed finding.

Given the required rigor (exact numeric PoC through the real extrinsic boundary, demonstrated attacker cost vs. expected/actual state) was not completed, and the impact is a bounded griefing/DoS rather than the fund-loss class the scan prioritizes, I present this as a plausible-but-unverified analog rather than a confirmed high-severity finding.
