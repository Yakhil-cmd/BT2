### Title
Webhook signature is verified against the wrong tenant's secret, allowing cross-organization forgery of webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook delivery against by reading a field (`repository.owner.login`) out of the very same untrusted JSON body it is about to authenticate, and the resulting HMAC only proves "whoever sent this knows *that* org's secret." Every webhook handler, however, resolves the actual `Stack`/`Repository` to act on from a *different* field in that same body (`repository.full_name`), which is never cross-checked against the field used for signature routing. This breaks the intended binding: **organization authenticated == repository written**. An attacker who legitimately administers the GitHub App/webhook secret for their own onboarded organization can forge a payload whose `repository.owner.login` matches their own org (so the HMAC validates with a secret they know) while `repository.full_name` names a completely different organization's repository/stack hosted on the same Shipit instance.

### Finding Description
`verify_signature` computes the org to authenticate against purely from payload content, then validates the raw body's HMAC using that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

Because the HMAC covers the *entire* raw request body, an attacker who knows one organization's `webhook_secret` can sign **any** JSON they want, as long as `repository.owner.login` (or `organization.login`) inside it still equals that organization. Nothing forces `repository.full_name`'s owner segment to equal `repository_owner`.

Every handler built on top of `Handler` resolves the target `Stack` purely from `repository.full_name`, independent of `repository_owner`: [3](#0-2) 

So a request can pass signature verification "as org-a" while every handler (push, pull_request, status, etc.) operates on "org-b/victim-repo," since `Repository.from_github_repo_name(repository_name)` only consults `full_name`.

This is precisely the class of bug flagged in the external report: a field that is authenticated/verified (here, the org selected for signature checking) diverges from the field actually acted upon (here, the repository/stack the handler mutates), because both live in the same attacker-supplied payload and are never bound to each other.

### Impact Explanation
An operator/admin of any one organization already onboarded to a shared, multi-tenant Shipit deployment (multiple orgs configured via `Shipit.github(organization: ...)`, confirmed by the `GithubOrganizationUnknown` handling and per-org `webhook_secret` config) can forge webhook deliveries that are cryptographically valid for their own org but semantically targeted at a victim org's `Stack`/`Repository`/`Commit` records. Handlers such as the push handler (`GithubSyncJob` enqueue), pull-request handlers (`review_stack.archive!`/`unarchive!`), and status/commit handlers write into the victim's Stack data using only the attacker's own org credentials — a cross-repository/cross-tenant write into Shipit's database that the attacker was never authorized to perform. This satisfies the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the public `/webhooks` endpoint with an org-a webhook secret the attacker legitimately possesses (as an admin of their own onboarded org) — no repository write access on the victim, no GitHub App private key, no TLS interception, and no privileged Shipit account are required. In a single-org deployment this is not exploitable, but the codebase explicitly supports and expects multiple organizations (`repository_owner`/`Shipit.github(organization:)`), so the cross-tenant boundary is a real, intended trust boundary that this logic fails to enforce.

### Recommendation
After computing `repository_owner` and verifying the signature, additionally assert that every organization-scoped field consumed by handlers (`repository.full_name`'s owner segment, `organization.login`, etc.) is consistent with the `repository_owner` used to select the signing secret, rejecting the request otherwise. Alternatively, route/validate webhooks by GitHub App installation ID rather than by an attacker-controlled login field, and have handlers re-derive/re-check the owning organization from a trusted source before mutating any `Stack`.

### Proof of Concept
1. Attacker administers Org A's GitHub App on the shared Shipit instance and knows Org A's configured `webhook_secret`.
2. Attacker crafts a `push` (or `pull_request`/`status`) JSON payload where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"` (Org B being an unrelated tenant with a registered Stack).
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC-SHA1(org-a's webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "org-a")`, validates the HMAC successfully (attacker knows the secret), and the request proceeds.
5. `PushHandler`/`Handler#stacks` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and dispatches (e.g. enqueues `GithubSyncJob`, or for pull_request handlers calls `review_stack.archive!`) against Org B's stack — a write the attacker had no authorization to trigger.
