### Title
Webhook signature verified against `repository.owner.login` while all handlers act on `repository.full_name` — cross-repository write via unauthenticated/blank-secret organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the request against using the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), but every downstream `Handler` subsequently resolves the `Repository`/`Stack` to act on using a *different* attacker-controlled field, `repository.full_name`. This is the exact same class of bug as the reported Pyth issue: a binding assumed by one part of the system (which org's secret authorizes the request) is never actually enforced to match what the other part of the system operates on (which repository is mutated).

### Finding Description
`verify_signature` computes `repository_owner` straight from the untrusted JSON body and uses it purely to pick which `GitHubApp` config (and thus which `webhook_secret`) to validate the HMAC against: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` explicitly treats a blank/unconfigured `webhook_secret` as automatically verified: [3](#0-2) 

Meanwhile, every `Handler` (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a completely separate payload field, `repository.full_name`, with no cross-check that it matches the organization that was actually used to authenticate the request: [4](#0-3) [5](#0-4) 

The binding that should hold is: `organization used to compute the verified signature == owner of the repository the handler mutates`. This is never enforced. If any organization configured in the Shipit deployment has a blank/unset `webhook_secret` (a documented, legitimate configuration state, as shown in the shipped config samples), an attacker can:
1. Send a POST to `/github/webhooks` with `repository.owner.login` set to that blank-secret organization (or `organization.login` for org-scoped events), so `verify_signature` short-circuits to `true` with no secret needed at all.
2. Set `repository.full_name` in the same payload to any *other* repository/org tracked by the Shipit instance — one that does have a real secret and real stacks.
3. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to the handler using the full raw payload, and the handler looks up the target stack via `full_name`, completely bypassing the intended per-organization trust boundary: [6](#0-5) 

### Impact Explanation
This breaks the authentication boundary between the GitHub Apps that are supposed to be independently scoped per organization. `PushHandler` triggers `stack.sync_github`, effectively forcing a resync/deploy pipeline update for an unrelated organization's stack the attacker has no legitimate relationship to. Other handlers (`status_handler.rb`, `check_suite_handler.rb`, `membership_handler.rb`) similarly act on data keyed by `full_name`/`organization.login` inside the payload without validating it against the authenticated org, letting an attacker forge commit statuses, check-suite results, or team membership changes across an unrelated repository — a cross-repository/cross-organization write that can influence deploy gating and unauthorized deploy decisions. This satisfies the "cross-repository writes / unauthorized deploy" Critical impact bar.

### Likelihood Explanation
Exploitability is entirely conditional on at least one organization configured in the running Shipit instance having a blank/absent `webhook_secret` — this is a normal, supported, and even shown-as-example configuration in this codebase's own sample configs (`webhook_secret: # nil`), rather than a misconfiguration unique to a victim. Any externally reachable Shipit deployment with multiple GitHub Apps, one of which has no webhook secret set (e.g. because it's not yet finished setup, or a legacy/lower-trust org), exposes every other tracked repository to forged webhook events. No credentials, session, or API token are required — only knowledge (or trial) of an organization name with a blank secret, and the target's public repository full name.

### Recommendation
After signature verification succeeds, the controller (or `Handler` base class) must verify that the organization/owner used to select the webhook secret is the *same* owner as the repository/organization the handler is about to mutate (i.e., re-derive and compare `repository.owner.login`/`organization.login` against `repository.full_name`'s owner, or better, look up the `Repository`/`Stack` scoped to the authenticated organization only). Additionally, treat a blank `webhook_secret` as "verification not configured — reject" rather than "always verified," or restrict blank-secret orgs from being able to satisfy verification for events referencing other organizations' repositories.

### Proof of Concept
1. Configure two GitHub App orgs in `secrets.yml`: `OrgWithNoSecret` (no `webhook_secret`) and `VictimOrg` (real secret, has tracked stacks).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgWithNoSecret" }, "full_name": "VictimOrg/target-repo" },
  "ref": "refs/heads/master",
  "after": "deadbeef"
}
```
3. `verify_signature` looks up `Shipit.github(organization: "OrgWithNoSecret")`, finds no `webhook_secret`, and `verify_webhook_signature` returns `true` unconditionally — no signature header is even required. [7](#0-6) 
4. `PushHandler#process` resolves `Repository.from_github_repo_name("VictimOrg/target-repo")` from `full_name` and calls `stack.sync_github`, executing an unauthorized action against `VictimOrg`'s stack despite authentication having only been "verified" for the unrelated, secret-less `OrgWithNoSecret`. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
