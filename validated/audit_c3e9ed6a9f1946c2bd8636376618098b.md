### Title
Spender-attested assets can be permanently frozen because `owner address is not attested` blocks even destroy/return transfers to the asset definer - (File: `validation.js`)

### Summary
For assets defined with `spender_attested: true`, every transfer input is validated against the current attestor list, with no exception for the case where the coin owner is trying to send the funds back to the asset definer (the `auto_destroy` "burn" path). Because the definer fully controls the attestor list at any time via an `asset_attestors` message, an address holding such an asset can be removed from the attestor list after receiving the funds, after which that address can never again move the coins — not even to relinquish/destroy them by sending them to the definer. This mirrors the reported `rOUSG` issue where a privileged/expected "burn" path is blocked by a status check (KYC there, attestation here) that was intended to gate ordinary transfers, not the destroy/reclaim path.

### Finding Description
When a `payment` message spends a `transfer` input of a `spender_attested` asset, `validatePaymentInputsAndOutputs` enforces: [1](#0-0) 

This check unconditionally requires `owner_address` (the `from` address of the funds) to be in `objAsset.arrAttestedAddresses`, which is the attestor list currently in force for the asset as loaded via `storage.loadAssetWithListOfAttestedAuthors`. The identical check exists for private fixed-denomination assets: [2](#0-1) 

The only special-casing for `auto_destroy` assets is a guard against *re-spending* an output that was already sent to the definer (double-destroy protection): [3](#0-2) 

There is no corresponding carve-out that would let an unattested owner still submit the one transfer that returns/destroys their coins by sending them to `objAsset.definer_address`. The attestor list itself is fully mutable by the asset definer at any point via the `asset_attestors` app, independent of any particular holder's balance history: [4](#0-3) [5](#0-4) 

So the sequence is: (1) asset is created with `spender_attested: true` (and optionally `auto_destroy`/non-transferrable, a common pattern for KYC-gated or single-use payment assets, see `initial-db` schema and `validatePaymentInputsAndOutputs`'s transferability rules at lines 2616-2629); (2) an address is attested and receives funds; (3) the definer publishes a new `asset_attestors` list that drops that address; (4) the holder can no longer produce a valid `transfer` input from that address for this asset — including the one transfer path (to the definer) that the protocol's own `auto_destroy` design assumes is always available to unwind/settle balances.

This is directly analogous to the reported bug: a check meant to gate normal transfers ('from' address KYC / attestation status) also blocks the one operation (`BURNER.burn` / definer-directed destroy transfer) that is supposed to be exempt from it.

### Impact Explanation
Coins of a `spender_attested` asset held by an address that is later removed from the attestor list become permanently unspendable by that address — they cannot transfer them onward (also blocked by the same check for the same reason) and cannot even return them to the definer to destroy/settle them. For assets designed around `auto_destroy` (single-use payment/voucher-style assets, as seen in oscript samples such as `create_an_asset.oscript`, `fundraising_proxy.oscript`, `option_contract.oscript`), this is a genuine, protocol-level freezing of funds with no available remediation path within the protocol (the definer cannot force a valid transfer/destroy on the holder's behalf; only the holder can supply the input, and the holder's own transfer is what gets rejected). This matches the accepted impact class "AA fund loss or freezing" / stuck value, reachable purely by an ordinary payment poster and an asset issuer exercising their normal attestor-list-update privilege — no malicious peer/node/hub is required.

### Likelihood Explanation
`spender_attested` is a first-class, documented asset feature and `asset_attestors` updates are an ordinary message any definer can post at will; there is nothing exotic required to reach this state — a single attestor-list update after a payment is enough to trigger the freeze. Since the condition arises from completely legitimate, expected admin actions (updating who's attested) rather than a race condition or attacker-controlled edge case, likelihood is high for any asset that combines `spender_attested` with `auto_destroy`/limited transferability.

### Recommendation
When the destination of a transfer is `objAsset.definer_address` (the recognized destroy/reclaim path for `auto_destroy` assets), exempt the `owner_address` from the `spender_attested` attestation check in both `validation.js:2506` and the private/fixed-denomination equivalent at `validation.js:2432`, analogous to how `_beforeTokenTransfer` should exempt `BURNER_ROLE`-initiated transfers from the KYC check on `from`. Alternatively, expose an explicit definer-authorized "reclaim/destroy" input type that bypasses the attestor check by construction, so that removing an address from the attestor list can never trap already-issued funds.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true`, `auto_destroy: true`, `is_transferrable: false` (a typical single-use/KYC-gated voucher asset).
2. Definer attests address `H`; `H` receives a payment of asset `A` (validated fine since `H` is in `arrAttestedAddresses`).
3. Definer publishes `asset_attestors` update that no longer includes `H` (`validateAttestorListUpdate`, `writer.js` lines 244-251).
4. `H` attempts a `payment` transferring its asset-`A` output back to the definer address (the expected destroy path). `validatePaymentInputsAndOutputs` loads the current (updated) attestor list and rejects the input with `"owner address is not attested"` at `validation.js:2506`, even though the destination is the definer and the intent is to relinquish/destroy the coins.
5. `H`'s funds in asset `A` are now permanently stuck: no valid `transfer` input can ever be constructed from `H` for this asset again.
