### Title
Readiness/liveness endpoint reports data as "fresh" forever after first sync, with no staleness check for ongoing sync failures - (File: `main.go`)

### Summary
`git-sync`'s HTTP liveness endpoint is the analog of the oracle "answer" value in the original report: it is the single signal that downstream consumers (e.g. Kubernetes readiness/liveness probes) rely on to decide whether the data behind `--link` is trustworthy/current. Just like `JBChainlinkV3PriceFeed.currentPrice()` only inspects `answer` and never checks `updatedAt` for staleness, git-sync's `/` handler only inspects a single sticky boolean (`repoReady`) and never checks how long ago the last *successful* sync actually happened, nor does it get cleared when subsequent syncs fail.

### Finding Description
The readiness state is a single package-level boolean guarded by a mutex: [1](#0-0) 

`setRepoReady()` is called once a sync succeeds and is never reset to `false` anywhere in the codebase - there is no corresponding `clearRepoReady()` call on sync failure. The HTTP handler exposed on `--http-bind` only checks this boolean: [2](#0-1) 

In the main loop, when `git.SyncRepo` returns an error, the code increments `failCount` and only exits the process if `failCount >= maxFailures` (from `--max-failures`/`--init-max-failures`), which defaults to unlimited retries when set to a negative value: [3](#0-2) [4](#0-3) 

There is no code path that compares "time since last successful sync" against any threshold (analogous to Chainlink's `updatedAt` vs. `block.timestamp` tolerance check) before reporting readiness/health as OK. Once `repoReady` becomes `true`, the `/` liveness endpoint will keep returning `200 OK` indefinitely even if every subsequent sync attempt fails (e.g., due to expired credentials, network partition to the git remote, or an upstream outage), as long as `--max-failures` is set to `-1` ("retry forever", a documented supported configuration).

### Impact Explanation
This causes a **persistent sync denial** condition to go undetected by the primary external health signal: a Kubernetes deployment using this container as a sidecar with a readiness/liveness probe pointed at `/` will keep considering the pod "ready" and routing traffic to the consuming application, while the actual data under `--link` silently grows arbitrarily stale. This mirrors the "oracle data feed can be outdated yet used anyway" bug class: the signal consumers trust for freshness (`repoReady` / Chainlink `answer`) is decoupled from any actual staleness bound (`updatedAt` tolerance / last-successful-sync timestamp), so stale data is used/served as if it were current, with no automatic remediation (pod restart) being triggered because the health check never flips to unhealthy.

### Likelihood Explanation
This requires no attacker action against the sync target itself — it is a design property that manifests whenever the upstream git remote becomes unreachable/misconfigured (credential rotation failure, network partition, DNS issue, or a malicious/compromised remote intentionally stalling responses) while `--max-failures` is configured for infinite retry (a documented, common configuration for resilience). This is a realistic and likely operational scenario, not a contrived edge case.

### Recommendation
Track the timestamp of the last successful sync (or the current `failCount`) and expose it through the readiness/liveness handler. Either:
1. Reset `repoReady` to `false` once `failCount` exceeds some staleness-relevant threshold (even if below `--max-failures`), or
2. Add a `--max-sync-failures-before-unready` style tolerance, or a `--staleness-threshold` duration compared against `time.Since(lastSuccessfulSync)`, and return `503` from the `/` handler when exceeded, similar to how Chainlink consumers are advised to check `updatedAt` against a heartbeat tolerance.

### Proof of Concept
1. Start `git-sync` with `--max-failures=-1` (retry forever) and `--http-bind=:8080` against a reachable repo; wait for the first successful sync so `/` returns `200`.
2. Simulate an outage (e.g., block network access to the remote, revoke credentials, or point DNS to an unreachable host) so all subsequent `git.SyncRepo` calls fail in the loop at [3](#0-2) .
3. Observe that `curl http://localhost:8080/` continues to return `200 OK` indefinitely (per the handler at [2](#0-1) ), even though the data behind `--link` has not been updated for an arbitrarily long time and `failCount` keeps climbing in the logs, demonstrating that the health signal is fully decoupled from data freshness.

```go
// repoReady indicates that the repo has been synced.
var readyLock sync.Mutex
var repoReady = false

func getRepoReady() bool {
	readyLock.Lock()
	defer readyLock.Unlock()
	return repoReady
}

func setRepoReady() {
	readyLock.Lock()
	defer readyLock.Unlock()
	repoReady = true
}
```
