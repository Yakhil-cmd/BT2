### Title
Cross-organization Team hijack via `membership` webhook allows unprivileged attacker to gain `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` (and therefore the `webhook_secret`) used to authenticate a webhook based solely on `repository_owner`, which falls back to `params.dig('organization','login')` for `membership` events. `MembershipHandler#find_or_create_team!` then looks up/creates the mutated `Team` record purely by `github_id`, never checking that `params.organization.login` matches the `organization` already stored on that `Team`. This lets an attacker who controls their own GitHub org (and its own configured `GithubApp`/`webhook_secret`) forge a signed `membership` webhook naming the `github_id` of a *victim* team already listed in `Shipit.github_teams`, causing their own attacker-controlled `User` to be added as a member of that team and become `authorized?`.

### Finding Description
The broken binding is: *the organization whose `webhook_secret` verified the request* (`attacker-org`, chosen via `Shipit.github(organization: repository_owner)` at `app/controllers/shipit/webhooks_controller.rb:25,61`) must equal *the organization that owns the `Team` row being mutated* (which must be the victim org that actually owns the GitHub team with that `github_id`). This equality is never checked.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . For a `membership` event there is no `repository` key, so `repository_owner` resolves to `params['organization']['login']`, which is attacker-controlled and equals `'attacker-org'`.
2. `Shipit.github(organization: repository_owner)` returns the `GithubApp` configured for `attacker-org` [2](#0-1) , and its signature check only proves the payload was signed by `attacker-org`'s own `webhook_secret` — a secret the attacker controls (as owner of that org's GitHub App). This is a legitimate, valid signature, just for the wrong tenant.
3. Once verified, `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g., the victim's team listed in `Shipit.github_teams`), `find_or_create_by!` returns that existing record — the `organization` attribute inside the block is never applied to an existing record, and more importantly nothing compares `params.organization.login` against `team.organization`.
4. Back in `process`, `team.add_member(member)` inserts a `Membership` for the attacker's `User` into the victim `Team` [4](#0-3) , `Team#add_member` at [5](#0-4) .
5. `User#authorized?` checks `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) . Since the attacker's user now has a membership in a team whose `id` is in `Shipit.github_teams`, this becomes `true`, granting full authenticated access to Shipit.

No existing guard catches this: `verify_signature` only authenticates "some org", not "the org that owns this specific team/repository"; `drop_unhandled_event` doesn't apply since `membership` is a handled event; the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not cross-tenant ownership; `find_or_create_by!` matches solely on `github_id` with no `organization` equality check.

### Impact Explanation
A single forged webhook lets the attacker escalate an arbitrary GitHub account (which the attacker controls) into full Shipit-authenticated access, by joining a `Team` referenced in `Shipit.github_teams` — the exact gate used by `User#authorized?` to grant application-wide access. This is repeatable for any victim team whose `github_id` the attacker can guess or discover (team IDs are often visible via GitHub's public API/UI), and requires no privileges on the victim's side. This matches "escalation into `Shipit.github_teams` authorization" (High), and arguably crosses into authentication bypass since it grants a fully authenticated, authorized session to an attacker who held none of Shipit's secrets — a cross-tenant data write (`Team`/`Membership` rows) driven by a payload whose only legitimate binding was to a different, attacker-owned organization.

### Likelihood Explanation
Preconditions: the deployment must run in the documented multi-org mode (`github:` block with multiple orgs in `Shipit.secrets`), and the attacker must own/administer at least one org with its own configured `GithubApp` (which is exactly the multi-tenant use case the `github:` block is designed to support) so they possess a legitimate `webhook_secret` for their own org. The attacker needs to know the target `github_id` of a `Team` listed in `Shipit.github_teams` — obtainable via GitHub's API for any team the attacker can see (public org team IDs are enumerable in many cases, and note the attacker only needs the `github_id` integer, not access to the team itself). No Shipit secret, session, or token is required. This is highly feasible for any org operator onboarding onto a shared multi-org Shipit instance.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any other org-scoped webhook handler), verify that `params.organization.login` matches the `organization` already recorded on the `Team` (or `GithubHook`) being mutated before creating/updating it or adding members; reject the webhook (or create a distinct team scoped to the payload's organization) if the existing `Team.organization` differs from `params.organization.login`. More generally, `WebhooksController#verify_signature` should bind the verified organization to the entity being mutated across all handlers (repository-owner cross-checks already partially exist for `repository`-keyed payloads; extend the same enforcement to `organization`-keyed payloads like `membership`).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (concept, not to be placed under test/ per rules but illustrating the exploit)
test "membership webhook from attacker org can hijack victim team by github_id" do
  # Configure two orgs each with their own GithubApp/webhook_secret
  Shipit.stubs(:secrets).returns(
    'github' => {
      'shopify' => { 'webhook_secret' => 'victim-secret', ... },
      'attacker-org' => { 'webhook_secret' => 'attacker-secret', ... },
    }
  )
  victim_team = shipit_teams(:shopify_developers) # github_id already in Shipit.github_teams
  Shipit.stubs(:github_teams).returns([victim_team])

  payload = {
    action: 'added',
    organization: { login: 'attacker-org' },
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    member: { login: 'attacker' },
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', payload)

  post '/webhooks', params: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => signature,
    'Content-Type' => 'application/json',
  }

  assert_response :ok
  attacker = Shipit::User.find_by(login: 'attacker')
  assert Shipit::Membership.exists?(user: attacker, team: victim_team)
  assert attacker.authorized?
end
```
Assertion of the broken binding: before the request, `webhook_secret_used == 'attacker-secret' (org 'attacker-org')` while `victim_team.organization == 'shopify'` — these differ, yet after the request a `Membership` linking `attacker` to `victim_team` exists and `attacker.authorized?` is `true`, proving the equality was never enforced.
