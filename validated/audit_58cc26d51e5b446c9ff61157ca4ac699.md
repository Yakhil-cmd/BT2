### Title
Missing signer/authority check on the `creator` field in `initialize_with_permission` permanently freezes creator-fee funds - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` accepts `creator` as an `UncheckedAccount` that is never required to sign and never constrained to equal `payer` or any other verified party, unlike the sibling `initialize` instruction where the analogous field (`creator`) is a `Signer`. This value is written verbatim into `PoolState.pool_creator`, which subsequently gates who can ever withdraw accumulated `creator_fees_token_0/1`.

### Finding Description
In `initialize.rs`, `creator` is declared `pub creator: Signer<'info>` [1](#0-0)  — meaning the party recorded as pool creator must cryptographically consent by signing the transaction.

In `initialize_with_permission.rs`, the equivalent field is declared as an unchecked, non-signer account with only a permissioned `payer` funding the transaction: `pub creator: UncheckedAccount<'info>` [2](#0-1) . The only authorization gate on this whole instruction is the `permission` PDA, which is derived from and only vouches for `payer.key()`, not for `creator.key()`: [3](#0-2) 

`ctx.accounts.creator.key()` is then written directly into the pool's permanent state as `pool_creator`, with no constraint that it match `payer`, be a signer, or otherwise consent: [4](#0-3) 

`pool_creator` subsequently becomes the sole authority permitted to withdraw `creator_fees_token_0/1` via `collect_creator_fee`, which requires `creator` to be the `Signer` matching `pool_state.pool_creator`: [5](#0-4) 

Because a permissioned but otherwise unprivileged `payer` can set `pool_creator` to *any* arbitrary pubkey — including a PDA, a burn address, or any address with no known private key — the pool's accumulated `creator_fees_token_0/1` become permanently uncollectible: `collect_creator_fee` can never be signed for that address, and while `collect_creator_fee_permissionless` can push the tokens into an ATA of that address, no one can ever move them out of that ATA since its authority is the unspendable address: [6](#0-5) 

These creator fees are carved directly out of swap trade fees (a portion of every swap that would otherwise remain in `vault_amount_without_fee` reserves used for pricing/withdrawal), tracked in `PoolState.creator_fees_token_0/1` and subtracted from usable vault balances in `vault_amount_without_fee`: [7](#0-6) [8](#0-7) 

This is the same bug class as the CVE analog: a state-mutating entry point that is supposed to record an authenticated/consenting party (the pgAdmin session owner; here, the pool creator who will later custody fee funds) instead accepts unauthenticated, attacker-chosen data because the authorization check that exists on the sibling code path (`Signer` on `creator` in `initialize`) was omitted on this path.

### Impact Explanation
Any pool created through `initialize_with_permission` with a deliberately or accidentally unspendable `creator` address results in permanent freezing of all `creator_fees_token_0`/`creator_fees_token_1` accrued for the pool's lifetime — funds that are a real portion of trade fees paid by swappers and would otherwise be distributed. This qualifies as permanent freezing of fee-ledger funds under an unauthorized privileged effect (an unconsenting/unverified party being assigned custodial rights over pool revenue).

### Likelihood Explanation
Any account holding a valid `permission` PDA (whitelisted operator) can trigger this in a single `initialize_with_permission` call by simply passing an arbitrary pubkey (not requiring its signature) as `creator`. No cross-instruction setup, timing, or race condition is needed — it is a single, directly reachable path with attacker-chosen account data, matching the exploitability profile of the CVE (single request, no extra preconditions beyond reaching the endpoint).

### Recommendation
Require `creator` in `InitializeWithPermission` to be a `Signer`, or explicitly constrain it (e.g., `constraint = creator.key() == payer.key()`) so `pool_creator` can only ever be set to a party who has consented to the assignment, mirroring the `Signer<'info>` requirement already enforced in `initialize.rs`.

### Proof of Concept
1. Attacker/operator obtains a valid `permission` PDA for their `payer` pubkey (via legitimate `create_permission_pda` flow or an already-permissioned account).
2. Attacker calls `initialize_with_permission` supplying:
   - `payer` = their own signer wallet (funds the pool)
   - `creator` = an arbitrary pubkey with no known private key (e.g., a PDA belonging to an unrelated program, or `Pubkey::default()`), passed as a plain (non-signer) account
3. The instruction succeeds; `pool_state.pool_creator` is set to that unspendable address [4](#0-3) .
4. Swaps against the pool accrue `creator_fees_token_0/1` normally via `update_fees` [8](#0-7) .
5. `collect_creator_fee` can never succeed because no signer exists for `pool_creator` [5](#0-4) ; `collect_creator_fee_permissionless` only moves the tokens into an ATA owned by the unspendable address, permanently locking them [9](#0-8) .

**Note on confidence:** I was unable to fully verify whether `creator` ≠ `payer` in `initialize_with_permission` is an intentional design feature of an upstream permissioned-launchpad flow (e.g., an operator creating pools on behalf of third-party creators by design) versus an unintentional omission of the `Signer` constraint present in `initialize.rs`. The code itself gives no indication of intentionality (no comment justifying the asymmetry), and the direct structural parallel to the CVE's "one route missing the auth annotation that every sibling route has" pattern is what drives this finding.

            .checked_add(self.fund_fees_token_0)

            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

    pub fn update_fees(
        &mut self,
        protocol_fee: u64,
        fund_fee: u64,
        creator_fee: u64,
        direction: TradeDirection,
    ) -> Result<()> {
        if !self.enable_creator_fee {
            require_eq!(creator_fee, 0)
        }
        let is_creator_fee_on_input = self.is_creator_fee_on_input(direction)?;
        match direction {
            TradeDirection::ZeroForOne => {
                self.protocol_fees_token_0 = self
                    .protocol_fees_token_0
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_0 = self.fund_fees_token_0.checked_add(fund_fee).unwrap();

                if is_creator_fee_on_input {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                }
            }
            TradeDirection::OneForZero => {
                self.protocol_fees_token_1 = self
                    .protocol_fees_token_1
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_1 = self.fund_fees_token_1.checked_add(fund_fee).unwrap();
                if is_creator_fee_on_input {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                }
            }
        };
        Ok(())
    }
