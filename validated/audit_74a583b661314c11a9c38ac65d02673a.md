### Title
Team.organization trusted from unverified `organization.login` payload field, independent of the org that signed the webhook - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the org derived from `repository.owner.login` (falling back to `organization.login` only when `repository` is absent), but `MembershipHandler#find_or_create_team!` independently trusts `params.organization.login` to set the newly created `Team#organization`. Because these are two distinct JSON fields, an attacker who controls a legitimately-configured org's webhook secret can sign a `membership` payload as their own org while setting `organization.login` to an arbitrary victim org string, causing a `Team` row to be created and falsely attributed to the victim org.

### Finding Description
The intended binding is: `repository_owner` (the org whose `webhook_secret` produced a valid `X-Hub-Signature`, used in `Shipit.github(organization: repository_owner)` at [1](#0-0)  and resolved via `repository_owner` at [2](#0-1) ) should equal `params['organization']['login']` (the value ultimately written to `team.organization`).

`repository_owner` reads `params.dig('repository','owner','login')` first, and only falls back to `params.dig('organization','login')` if the `repository` key is entirely absent [2](#0-1) . A `membership` webhook payload legitimately contains both a `repository` object and a separate `organization` object (as the test fixtures show, `membership_params` merges `repository_params` = `{ repository: { owner: { login: 'shopify' } } }` together with `organization: { login: 'shopify' }` as independent keys [3](#0-2) ). Nothing forces these two logins to be identical.

`MembershipHandler#find_or_create_team!` never consults `repository_owner`; it creates the `Team` using only `params.organization.login`: [4](#0-3) 

Exploit flow: the attacker legitimately owns/administers a GitHub org ("attacker-org") that is configured in this Shipit instance's multi-org `github:` config with its own `webhook_secret` (per the documented multi-org schema in `config/secrets.development.example.yml`). The attacker sends `POST /webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with attacker-org's own webhook secret, `repository.owner.login = "attacker-org"` (so `verify_signature` resolves and validates against `attacker-org`'s app/secret and passes), a brand-new `team.id` not yet in the datastore, and `organization.login = "victim-org"`. `verify_signature` succeeds because the signature is checked against attacker-org's own secret, then `MembershipHandler` runs and creates `Team.find_or_create_by!(github_id: team.id) { team.organization = "victim-org" }`, producing a `Team` row falsely attributed to `victim-org` despite the request never being authenticated by `victim-org`'s webhook secret.

Existing guards do not prevent this: `verify_signature`'s `GithubOrganizationUnknown` rescue only fires if the org used for *signature verification* (`repository_owner`, i.e., attacker-org) isn't configured — it never checks `organization.login` against the app that actually signed the request [5](#0-4) . The `ExplicitParameters` schema for `MembershipHandler` only validates presence/type of `organization.login`, not its correspondence to the signing org [6](#0-5) .

### Impact Explanation
A falsely-attributed `Team` row (`organization = "victim-org"`) is written to the datastore without victim-org ever authenticating the request. If an operator later configures `Shipit.github_teams` with a handle like `"victim-org/slug"` matching the poisoned team's slug, `Team.find_or_create_by_handle` at [7](#0-6)  would find this pre-existing (attacker-created) row rather than fetching the real team from GitHub, potentially granting the attacker-controlled team's members OAuth/team-based authorization intended for the real victim-org team. This matches the High severity category ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
This requires the Shipit deployment to use the multi-org GitHub App configuration (one `webhook_secret` per org) and for the attacker to be a legitimately onboarded org in that same Shipit instance (i.e., attacker must possess their own valid, configured webhook secret) — this is a plausible but non-trivial precondition in genuinely multi-tenant Shipit deployments. The attacker also needs the target org's exact login string (public GitHub data) and needs an eventual operator misconfiguration of `oauth.teams`/`Shipit.github_teams` referencing a slug that collides with the attacker's forged team to realize the authorization escalation. The webhook request itself is trivially repeatable and costs nothing beyond having one legitimate onboarded org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, do not trust `params.organization.login` blindly; cross-check it against the org resolved during signature verification (e.g., pass `repository_owner`/the verified `GitHubApp#organization` through to handlers) and reject/ignore the event if `params.organization.login` differs from the org that actually signed the webhook. Alternatively, have `WebhooksController#repository_owner` prefer `organization.login` when present for org-scoped events like `membership`, or enforce equality between `repository.owner.login` and `organization.login` before dispatching to handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership team.organization must match the org that signed the webhook" do
  @request.headers['X-Github-Event'] = 'membership'

  # Attacker signs as their own configured org ("attacker-org"),
  # but embeds a different organization.login in the payload.
  forged_payload = {
    action: 'added',
    team: { id: 999_999, name: 'Forged', slug: 'forged', url: 'https://example.com' },
    organization: { login: 'victim-org' },          # <-- untrusted, unverified
    member: { login: 'walrus' },
    repository: { owner: { login: 'attacker-org' } } # <-- actually signs/authenticates
  }.to_json

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(stub(verify_webhook_signature: true))

  assert_difference -> { Team.count }, 1 do
    post :create, body: forged_payload, as: :json
  end

  team = Team.find_by(github_id: 999_999)
  # Broken binding: team.organization ("victim-org") != signing org ("attacker-org")
  assert_equal 'victim-org', team.organization
  refute_equal 'attacker-org', team.organization
end
```
This demonstrates that `Team#organization` equals the unverified `params['organization']['login']` value rather than `attacker-org`, the org that actually signed the request — confirming the broken binding.

      ].join(' '))
    end
