## Title
Cross-organization webhook signature confusion — the GitHub organization whose secret authenticates a webhook is not the same field used to select the repository/stack that gets mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the webhook secret) used to validate the HMAC of an inbound webhook from `repository.owner.login` (falling back to `organization.login`) taken directly out of the **unverified** JSON body. Every event handler downstream, however, resolves the target `Repository`/`Stack` from a *different* field of that same unverified body: `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Because these two fields are never checked for consistency, an attacker who legitimately knows the webhook secret of *one* GitHub organization configured on a multi-org Shipit instance can forge a signed payload that claims to be from that org (`repository.owner.login = "own-org"`) while pointing `repository.full_name` at a completely different organization's repository, causing Shipit to act on a stack the attacker never authenticated for.

### Finding Description
`verify_signature` selects the signing app like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params.dig('repository', 'owner', 'login')` — part of the raw, not-yet-verified request body — and is used solely to pick which `Shipit.github(organization:)` app's `webhook_secret` is used for `verify_webhook_signature`. This works fine for legitimate GitHub deliveries because GitHub itself fills in `repository.owner.login` consistently with `repository.full_name`. But nothing stops a forged, self-signed payload from setting these two fields independently.

Downstream, every default handler (`PushHandler`, `OpenedHandler`, `LabelCapturingHandler`, etc.) resolves the repository/stack to act on from a **different** field: [3](#0-2) [4](#0-3) 

Shipit supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret`, exactly as documented: [5](#0-4) [6](#0-5) 

Since each org's GitHub App (and its `webhook_secret`) is typically created and known by that org's own administrators, an unprivileged-from-Shipit's-perspective org owner ("org-A") legitimately knows `webhook_secret_A`. That person can POST directly to Shipit's public `/webhooks` endpoint (no Shipit session, no `ApiClient` token required) a self-crafted JSON body:
- `repository.owner.login = "org-A"` → `verify_signature` looks up `Shipit.github(organization: "org-A")` and validates the HMAC against `webhook_secret_A`, which the attacker computed correctly since they know that secret.
- `repository.full_name = "org-B/some-repo"` → the handler (`PushHandler`, PR handlers, etc.) resolves `Repository.from_github_repo_name("org-B/some-repo")` and acts on **org-B's** stack, even though org-B's webhook secret was never checked.

The equality that is broken:
`organization authenticated by verify_signature (repository.owner.login)` ≠ `repository/stack actually written to by the handler (repository.full_name)`.

### Impact Explanation
Depending on the handler triggered, this cross-org confusion can cause:
- `PushHandler` forcing `Stack#sync_github` on an arbitrary org's stack via a forged, attacker-signed push event — for stacks with continuous deployment enabled, this can advance the deploy queue and trigger an unauthorized deploy on infrastructure the attacker has no legitimate relationship to.
- PR handlers (`OpenedHandler`, `LabelCapturingHandler`, `ReviewStackAdapter`) creating, labeling, archiving or unarchiving review stacks (which provision/deprovision real infrastructure) belonging to a repository the attacker doesn't control.

This falls under the "unauthorized deploy/rollback" and cross-repository-write impact category, since the binding between the authenticating credential (webhook secret of org X) and the mutated resource (stack/repository of org Y) is not enforced.

### Likelihood Explanation
Requires only: (1) the Shipit instance to be configured with more than one GitHub organization/app (the officially documented "Using Multiple Github Applications" setup), and (2) the attacker to be an admin of any one of those onboarded orgs — a realistic, unprivileged-from-Shipit's-perspective actor who is not required to have any Shipit account, session, or API token. No cryptographic break is needed; the attacker uses a secret they legitimately possess to sign an artificial payload with a mismatched target.

### Recommendation
In `verify_signature`, re-derive/verify the organization used to select the webhook secret from `repository.full_name`'s owner segment (or cross-check `repository.owner.login` against `repository.full_name`'s prefix) and reject the request if they diverge, ensuring the same trusted field is used both to select the verifying secret and to select the repository being mutated.

### Proof of Concept
1. Configure Shipit with two orgs, `org-A` (webhook_secret known to the attacker) and `org-B` (has a tracked repo/stack `org-B/app`).
2. Attacker builds JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/app" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "org-A")`, validates successfully against `webhook_secret_A`. `PushHandler#process` then resolves `Repository.from_github_repo_name("org-B/app")` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on org-B's stack — an action never authorized by org-B's own webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
