### Title
Bridge ERC721 `handleERC721Transfer` Silently Succeeds on Non-Existent Token Contract, Permanently Consuming Bridge Nonce Without Transferring NFT — (File: `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleERC721Transfer` in `BridgeTransferERC721.sol` performs no contract-existence check on `_tokenAddress` before calling `IERC721(_tokenAddress).transferFrom(...)` in non-mintBurn mode. Because `transferFrom` is a `void` function, a call to an address with no deployed code returns `(success=1, data=empty)` at the EVM level, and Solidity 0.5.x silently treats this as success. The bridge nonce is consumed and `HandleValueTransfer` is emitted before the token call, so when the call silently succeeds against a non-existent contract, the state mutation is committed with no NFT ever reaching the recipient.

---

### Finding Description

`handleERC721Transfer` is gated only by `onlyOperators` — there is no `onlyRegisteredToken` guard:

```solidity
function handleERC721Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    ...
)
    public
    onlyOperators          // ← only access control; no onlyRegisteredToken
``` [1](#0-0) 

After the vote threshold is reached, the function irrevocably commits state — nonce, tx-hash record, and event — **before** attempting the token transfer:

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...), "mint failed");
} else {
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);  // ← void, no revert on empty code
}
``` [2](#0-1) 

In the non-mintBurn branch, `IERC721.transferFrom` is declared `void` (no return value). Under Solidity 0.5.x, a high-level call to an address with zero code size issues a `CALL` opcode that returns `(success=1, returndata=empty)`. Because there is no return value to decode and no `require` wrapping the call, Solidity accepts the result as success. The entire transaction commits.

Contrast this with the ERC20 path, which is protected: `SafeERC20.callOptionalReturn` explicitly calls `require(address(token).isContract(), "SafeERC20: call to non-contract")` before proceeding:

```solidity
require(address(token).isContract(), "SafeERC20: call to non-contract");
``` [3](#0-2) 

No equivalent guard exists for the ERC721 `transferFrom` call.

The `onlyRegisteredToken` modifier in `BridgeTokens` only checks that the address is in the mapping (`registeredTokens[_token] != address(0)`); it does not verify that code exists at the address:

```solidity
modifier onlyRegisteredToken(address _token) {
    require(registeredTokens[_token] != address(0), "not allowed token");
    _;
}
``` [4](#0-3) 

And even this modifier is absent from `handleERC721Transfer`.

---

### Impact Explanation

When the vote quorum is reached and `_tokenAddress` has no deployed code (destroyed via `selfdestruct`, or any EOA/zero-code address):

1. `_setHandledRequestTxHash` marks the request tx hash as handled — irreversible.
2. `handleNoncesToBlockNums[_requestedNonce]` is written.
3. `_updateHandleNonce` advances `lowerHandleNonce` — the nonce is permanently consumed.
4. `HandleValueTransfer` is emitted — off-chain monitors and the source-chain bridge treat the transfer as complete.
5. `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` silently succeeds against empty code.
6. The recipient receives no NFT.

The bridge nonce is consumed and cannot be replayed. The user permanently loses the bridged NFT. This is an unauthorized destruction of bridged asset ownership.

---

### Likelihood Explanation

Two realistic triggers exist:

**Scenario A — Honest operators, destroyed contract.** A registered NFT contract on the destination chain is selfdestructed (e.g., by its owner or via a vulnerability). Honest operators, observing a legitimate `RequestValueTransfer` on the source chain, relay `handleERC721Transfer` with the now-codeless address. The bridge silently succeeds.

**Scenario B — Compromised operator quorum.** If the operator quorum is reached with a non-existent `_tokenAddress` (any EOA suffices), the same silent success occurs. Because `handleERC721Transfer` lacks `onlyRegisteredToken`, operators are not constrained to registered token addresses.

The multi-operator vote (`_voteValueTransfer`) raises the bar for Scenario B but does not eliminate it; Scenario A requires no malice at all.

---

### Recommendation

**Short term:** Wrap the `transferFrom` call with a contract-existence check before execution, mirroring the `SafeERC20` pattern:

```solidity
require(address(_tokenAddress).isContract(), "token is not a contract");
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```

Alternatively, add `onlyRegisteredToken(_tokenAddress)` to `handleERC721Transfer` (as `_requestERC721Transfer` already has it) and add an `isContract` check inside `registerToken`.

**Long term:** Move all irreversible state mutations (nonce consumption, event emission) to after the token transfer succeeds, or use a checks-effects-interactions pattern that reverts the entire transaction on transfer failure.
