## Title
Reusable `has`/`has one` output-matching filter in address definitions allows one payment to satisfy multiple independent spending conditions in a single unit - ([File: arbiter_contract.js], [File: definition.js])

### Summary
The reported bug class is: a validation step references *another* transaction/message in the same group "by index" or "by matching criteria" to authorize a payout, but never marks that referenced element as *consumed*, so one repayment/element can be reused to satisfy multiple independent authorization checks in the same atomic operation. In ocore, the closest reachable analog is the `has` / `has one` oscript primitive used inside address definitions (`Definition.evaluateFilter` in `definition.js`) to authorize spending conditional on "this unit also contains a payment/output matching X". Like `flash_loan_end`, this primitive scans the *whole unit* for a matching element and returns true if found — it does not tag or remove the matched output/input, so the very same output can independently satisfy more than one `has` clause evaluated for different signing paths/conditions within the same unit.

### Finding Description
`evaluateFilter` in `definition.js` implements the `has`/`has one` operators used by address definitions (`case 'has': case 'has one':` in `definition.js` at lines 1107-1115, dispatching to `augmentMessagesAndEvaluateFilter` → `evaluateFilter`): [1](#0-0) 

This function iterates over `objUnit.messages` and their `payload.outputs`/`payload.inputs`, and returns `true`/found-objects as soon as *any* matching output/input exists anywhere in the unit: [2](#0-1) 

Nothing in this evaluation marks a matched output as "consumed" for the purposes of a *different* `has` evaluation. If a shared address's definition is built from multiple OR-branches, each independently checking `["has", {what:"output", amount: X, address: Y}]` to authorize different signing paths (e.g. "offeror gets refund" vs "acceptor gets paid"), and the required amounts/addresses of the two branches happen to coincide (or are made to coincide by an attacker crafting the unit), a single payment output can satisfy both branches. Because the definition is only asked "is this condition true for this evaluated branch", and definitions of different branches are evaluated independently without any global "already used" bookkeeping, one output can effectively be double-counted, exactly mirroring the flash_loan_end reuse bug (checking "does an appropriate qualifying element exist in this group" without recording that it was already consumed by an earlier authorization).

The codebase itself acknowledges this exact bug class: `arbiter_contract.js`, when building a smart-contract shared address using `has` conditions, has an explicit code comment warning about it and adds a manual mitigation: [3](#0-2) 

That comment states: *"protect against combining several contracts in a single transaction (if their parties, amounts, and assets are identical, the 'has what' above would satisfy both contracts, allowing the attacker to send the change to themselves)"* — this is a direct, self-documented instance of the exact bug class described in the report (reusing one qualifying element to satisfy multiple independent spend authorizations).

The mitigation added there (`["not", ["has", {what:"input", asset:..., address:"other address"}]]`) only guards this specific contract template against combining *multiple arbiter contracts* in one unit; it does not fix the underlying primitive. Any other address definition (custom smart contracts, wallet-defined addresses, or AA-adjacent oscript definitions) built by end users using `has`/`has one`/`sum`/`has equal` without similarly hand-crafted "no other qualifying element" guards is exposed to the same reuse pattern, since `evaluateFilter` provides no automatic protection.

### Impact Explanation
Any address definition (reachable by any unprivileged unit poster who composes such a definition and gets a counterparty to fund the shared/smart-contract address) that relies on `has`/`has one`/`sum`/`has equal` to gate independent payout branches can be exploited to authorize a payout using a single crafted output that simultaneously satisfies multiple conditions, potentially letting an attacker claim funds intended for someone else or bypass conditions meant to require a separate, dedicated payment. This maps to concrete unauthorized-spending impact from a shared/contract address, consistent with the required "concrete unauthorized spending" bar. The severity depends on how a specific contract composes its `has` conditions; ocore's own `arbiter_contract.js` needed a hand-written guard, demonstrating the primitive is unsafe by default for anyone composing multi-branch spending conditions.

### Likelihood Explanation
Exploitation requires an attacker (or contract designer) to control or influence the definition composition of a shared address (e.g., as one counterparty negotiating a smart contract, or an app author reusing `has`-based patterns without the extra guard used in `arbiter_contract.js`). This is reachable without any special privilege — a wallet/contract author who is a normal unprivileged user can construct such definitions, and the fact that `arbiter_contract.js` (a first-party contract template) required a hand-added guard for exactly this scenario shows the likelihood of the primitive being used unsafely elsewhere (custom or third-party contracts/AAs) is realistic, though it is not a universal, always-triggerable vulnerability in the core protocol — it depends on how a given definition composes the `has` filters.

### Recommendation
- Short term: Document prominently (in oscript/definition authoring docs) that `has`/`has one`/`sum`/`has equal` do not mark matched outputs/inputs as consumed, and that any definition using multiple independent `has` branches whose match criteria could overlap must add explicit "no other qualifying element" (`not has`) guards, as done in `arbiter_contract.js`.
- Long term: Consider extending `evaluateFilter`/`has`/`has one` semantics (or adding a new primitive) that supports "consumed" matching across multiple conditions evaluated together in a single definition evaluation pass, so that the same output/input cannot be double-counted by different clauses of the same top-level `or`/`and` structure without requiring every contract author to hand-write "not has {other address}" guards.

### Proof of Concept
Conceptual (not a full working test, since exploitability is definition-composition dependent):
1. An address definition is composed (via `oscript`) with two `or` branches, each independently gated by `["has", {what:"output", asset:"base", amount: N, address: X}]` for different purposes (e.g., branch A: "party 1 authorizes if a refund output of N to party1 exists"; branch B: "party 2 authorizes if an output of N to party2 exists"), similar in structure to `arbiter_contract.js`'s branches at [4](#0-3) , but *without* adding the `not has {other address}` guard shown at [3](#0-2) .
2. An attacker crafts a single unit containing one payment output of amount N to address X.
3. Both `has` branches independently evaluate to `true` against `evaluateFilter` in `definition.js` because the same output satisfies both filters (`definition.js` lines 1336-1373), letting the attacker sign/authorize spending under whichever branch benefits them, using a single payment to satisfy authorization requirements meant to apply to two different, separately-funded scenarios.

Note: I was not able to fully verify every consumer of `has`/`has one` across the full codebase (e.g., all built-in and third-party contract templates) within the available indexed content, so I cannot guarantee this is exploitable in every context that uses `has`; the concrete, code-documented instance of the risk is the comment/guard in `arbiter_contract.js`, which is direct evidence the bug class exists and had to be manually mitigated in at least one first-party contract.
