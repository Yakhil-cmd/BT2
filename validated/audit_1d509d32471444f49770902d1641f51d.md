## Finding: Missing WebAuthn ceremony-type (`clientDataJSON.type`) verification allows cross-ceremony signature reuse to authorize Aptos transactions

### Title
Missing WebAuthn `client_data.type` check in `PartialAuthenticatorAssertionResponse::verify`/`verify_arbitrary_msg` permits registration-ceremony signatures to be accepted as transaction-authorizing assertions - (File: `types/src/transaction/webauthn.rs`)

### Summary
Aptos's WebAuthn signature verification path checks only the ECDSA signature and the `challenge` field of `CollectedClientData`, but never validates the `type` field (`C.type`) of the client data as mandated by the WebAuthn spec. This omission breaks the ceremony-binding invariant that a WebAuthn assertion signature must be scoped to `"webauthn.get"` (authentication) rather than `"webauthn.create"` (registration/attestation), and this verification function is directly on the transaction-signature admission path.

### Finding Description
`PartialAuthenticatorAssertionResponse::verify` and `verify_arbitrary_msg` parse `client_data_json` into a `CollectedClientData` struct and only check the `challenge` field against the expected transaction hash: [1](#0-0) 

The same omission exists in `verify_arbitrary_msg`, which only compares `challenge_bytes` to `message` and never inspects `collected_client_data.ty`: [2](#0-1) 

The WebAuthn spec (§7.2, "Verifying an Authentication Assertion", step 11) requires implementations to "Verify that the value of `C.type` is the string `webauthn.get`." This step exists precisely because the raw signature format signed by the authenticator — `authenticatorData || SHA-256(clientDataJSON)` — is identical between an authentication ceremony (`navigator.credentials.get`) and, for self-attested/basic-attestation registration ceremonies (`navigator.credentials.create`), the attestation signature. Skipping the type check means a signature blob produced under a **registration** ceremony (where the relying party supplied `challenge = SHA3-256(raw_txn)` as the registration challenge, which is attacker-controllable/known) can be replayed as if it were an **authentication assertion**, since verification only checks signature validity and challenge equality, not the ceremony type.

This function is reached directly from the transaction admission boundary: `AnySignature::verify` dispatches WebAuthn signatures straight to `PartialAuthenticatorAssertionResponse::verify`: [3](#0-2) 

`AnySignature::verify`/`SingleKeyAuthenticator` verification is invoked as part of `SignedTransaction::verify_signature`/`check_signature`, which both the VM validator (`VMValidator::validate_transaction`, mempool admission) and VM execution prologue call before any other admission logic runs: [4](#0-3) 

Because signature verification happens before, and independently of, the sequence-number/authentication-key checks performed later in `prologue_common` in Move, a forged-context WebAuthn assertion that passes `check_signature` is treated by the rest of the pipeline as a fully legitimate signature over the raw transaction, binding it to the sender's account authentication key.

### Impact Explanation
This is a signature/authenticator binding failure at the transaction admission boundary. An attacker able to obtain (via social-engineering-free means, e.g. a legitimate-looking passkey registration flow on any site, or a compromised/malicious relying party front end that the victim's browser+authenticator interacts with) a WebAuthn "create" ceremony response whose `clientDataJSON.challenge` equals `SHA3-256(signing_message(raw_txn))` can package that response as a `PartialAuthenticatorAssertionResponse` and have it accepted as authorization for an arbitrary Aptos transaction signed by the victim's secp256r1 public key. This lets an attacker construct a `SignedTransaction` that passes signature verification without the victim ever having performed an actual "get" (transaction-authentication) ceremony — i.e., unauthorized transaction execution under the victim's sender account, satisfying the "Authenticator ... accepting the wrong signing material" admission-impact criterion.

### Likelihood Explanation
Exploitability depends on an attacker's ability to coax a target's authenticator into producing a "create"-ceremony (or other non-`webauthn.get`) signature over attacker-chosen challenge bytes equal to a transaction hash, and for that response's raw signature bytes to be extractable and reusable in the `authenticatorData || SHA-256(clientDataJSON)` format Aptos expects. This is authenticator/browser-dependent (not all attestation formats yield directly reusable ECDSA signatures over that exact structure), which lowers likelihood versus a purely on-chain defect, but the missing spec-mandated check is a genuine, verifiable code-level gap independent of any external report and is squarely in the "wrong signing material" / ceremony-binding admission-analog category.

### Recommendation
In `PartialAuthenticatorAssertionResponse::verify` and `verify_arbitrary_msg` (`types/src/transaction/webauthn.rs`), after deserializing `collected_client_data`, explicitly assert `collected_client_data.ty == ClientDataType::Get` (rejecting `Create` or any other ceremony type) before proceeding to challenge/signature verification, matching WebAuthn §7.2 step 11.

### Proof of Concept
1. Attacker sets up (or compromises) a web page that triggers `navigator.credentials.create()` for the victim's passkey with `challenge = SHA3-256(signing_message(target_raw_txn))` (attacker knows/controls `target_raw_txn`, e.g. a transfer to their own address, since they choose the challenge before the ceremony).
2. If the authenticator/attestation format used yields a basic/self-attestation signature computed as `sign(authenticatorData || SHA-256(clientDataJSON))` over the credential private key (common for many WebAuthn implementations), the attacker extracts `authenticatorData`, `clientDataJSON` (with `type: "webauthn.create"`), and the raw signature from the attestation response.
3. Attacker builds `PartialAuthenticatorAssertionResponse::new(AssertionSignature::Secp256r1Ecdsa{signature}, authenticator_data, client_data_json)` and wraps it in `AnySignature::webauthn(...)` / `SingleKeyAuthenticator` / `AccountAuthenticator::SingleKey` / `TransactionAuthenticator::SingleSender`, then submits `SignedTransaction::new_signed_transaction(target_raw_txn, txn_authenticator)`.
4. `SignedTransaction::verify_signature()` → `AnySignature::verify` → `PartialAuthenticatorAssertionResponse::verify` succeeds because only `challenge` and the raw ECDSA signature are checked; `clientDataJSON.type == "webauthn.create"` is never rejected.
5. The forged transaction passes VM-validator/mempool admission and prologue signature checks as if it were properly authenticated by the victim.

        &self,

            (Self::Ed25519 { signature }, AnyPublicKey::Ed25519 { public_key }) => {
                signature.verify(message, public_key)
