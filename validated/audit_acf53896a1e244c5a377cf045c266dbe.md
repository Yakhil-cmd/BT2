## Analysis

I have enough evidence to confirm this vulnerability from the code paths traced.

**The broken binding**: The invariant claims "The set of keys in the environment hash passed to PTY.spawn is restricted to the deploy spec's `machine_env` and declared `VariableDefinition` names." This is false. The actual equality that holds is: `command.env.keys ⊇ pull_request.labels.map(&:upcase)`, with no allowlist filtering applied anywhere in the `TaskCommands#env` → `Command#unbundled_env` → `PTY.spawn` path.

**Code path**:
1. `ReviewStack#env` merges every pull request label name (uppercased) as an env key with value `"true"`, with no allowlist: `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" } ` [1](#0-0) 
2. `LabelCapturingHandler#capture_labels` persists label names directly from the webhook payload's `pull_request.labels[].name` with only a `String` type constraint in the params schema — no content restriction: [2](#0-1) [3](#0-2) 
3. `TaskCommands#env` merges `@stack.env` (which includes the ReviewStack's label-derived keys) directly into the command environment with **no call to `EnvironmentVariables#permit`/`filter_envs`**: [4](#0-3) 
4. `TaskCommands#install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` using this unfiltered env for `bundle install` / ruby dependency steps: [5](#0-4) 
5. `Command#unbundled_env` merges `@env.stringify_keys` over `BASE_ENV` with **no key allowlist at all**: [6](#0-5) 
6. `Command#start` passes this merged hash directly to `PTY.spawn`: [7](#0-6) 

This is confirmed by existing tests demonstrating arbitrary label-derived keys reaching `env`: [8](#0-7)  and [9](#0-8) .

**Where the allowlist mechanism (`EnvironmentVariables#permit`) actually is used**: it exists at [10](#0-9)  and is applied via `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` and `TaskDefinition#filter_envs` [11](#0-10) [12](#0-11) , but this filtering is applied to **user-supplied deploy/rollback/task-trigger parameters** (`@task.env` originating from an authenticated deploy/rollback request), not to `@stack.env` (the PR-label-derived hash). `TaskCommands#env` merges `@stack.env` unfiltered, so the label-derived keys bypass the allowlist entirely.

**However**, I was unable to fully verify within available iterations whether the `POST /webhooks` endpoint enforces GitHub webhook signature verification (`GitHubApp#verify_webhook_signature`) before dispatching to `LabelCapturingHandler`. This matters for likelihood: if signature verification is enforced (which is the documented/standard Shipit behavior), then the attacker cannot directly forge a webhook payload from an arbitrary internet request — they would need an actual, real pull request with a label whose name uppercases to `SSH_ASKPASS` on a repository that has Shipit's GitHub App installed and review-stacks/webhooks configured, and GitHub itself would relay that as a legitimately-signed webhook. Since GitHub allows any PR author (including on their own fork) to apply/create a label with essentially arbitrary text, this precondition is trivially satisfiable by an unprivileged fork/PR author without needing to forge the webhook signature themselves — the real webhook coming from GitHub would carry the label. This still satisfies the "unprivileged fork PR author" attacker model even under full signature verification.

## Verdict

The vulnerability is real: the env-key injection point is unguarded (`ReviewStack#env`), the label capture is unguarded (`LabelCapturingHandler#capture_labels`), and the consumption point (`TaskCommands#env` → `Command#unbundled_env` → `PTY.spawn`) applies no allowlist. This matches the question's target precisely.

### Title
Unallowlisted pull-request-label-derived environment keys reach `PTY.spawn` via `TaskCommands#install_dependencies`, enabling `SSH_ASKPASS` injection - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` converts every pull request label name into an uppercased environment variable key with no allowlist, and these labels are persisted verbatim from the GitHub webhook payload by `LabelCapturingHandler#capture_labels`. `TaskCommands#env` merges this unfiltered `@stack.env` into the environment used by `Command`, which `Command#unbundled_env`/`Command#start` pass directly to `PTY.spawn` for every task step including `bundle install`, allowing an attacker-controlled label like `ssh_askpass` to inject `SSH_ASKPASS` into the deploy host's process environment.

### Finding Description
The invariant "env keys reaching `PTY.spawn` are restricted to `machine_env` and declared `VariableDefinition` names" is false. `ReviewStack#env` does `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` with no key allowlist [1](#0-0) . `LabelCapturingHandler#capture_labels` writes `params.pull_request.labels.map(&:name)` straight into `pull_request.labels` from the webhook body with only a `String` type check [2](#0-1) . `TaskCommands#env` merges `@stack.env` (the label hash) into the command environment without any call to `EnvironmentVariables#permit` [4](#0-3) , and `install_dependencies` uses this env directly for dependency steps such as `bundle install` [5](#0-4) . `Command#unbundled_env` merges `@env.stringify_keys` over `BASE_ENV` with no key restriction [6](#0-5) , and `Command#start` passes this to `PTY.spawn` [7](#0-6) . An attacker opens a PR on a repository with review stacks/CD enabled and applies a label named `ssh_askpass` (or any casing); GitHub relays this via a legitimately signed webhook, `LabelCapturingHandler` persists it, and the next task/deploy run exports `SSH_ASKPASS=true` to every spawned subprocess, including `ruby`/`bundle`. The `EnvironmentVariables#permit` allowlist mechanism exists but is only applied to `deploy_variables`/`rollback_variables`/`task_definition` variables (user-triggered params), not to `@stack.env`, so it does not guard this path.

### Impact Explanation
Any environment variable name can be set to a fixed value (`"true"`) via a PR label with no allowlist, on the deploy host, for every task/dependency/deploy step of that stack. While the fixed value `"true"` limits some attacks (e.g., `SSH_ASKPASS=true` alone won't run arbitrary code unless something invokes ssh with `DISPLAY` set and a program path), the broader issue is that **arbitrary environment variable keys are attacker-controlled with no allowlist at all**, which is a serious "loader variable injection" class of bug (e.g., `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`-style variables if the value part could be controlled) — though in this specific case the value is hardcoded to `"true"`, limiting direct RCE via `SSH_ASKPASS` specifically. The confirmed, demonstrable impact is unauthorized injection of arbitrary env keys into the deploy host process environment for a repository the attacker has only PR-author access to, which is a boundary violation on `machine_env`/`VariableDefinition` allowlisting on that repository's stacks.

### Likelihood Explanation
Precondition: the target repository must have review stacks / label capture enabled (`review_stacks_enabled`, and `provisioning_behavior`) [13](#0-12) , which is a normal Shipit deployment configuration, not something the attacker controls. Given that, an unprivileged fork PR author only needs to open a PR and add any label; GitHub itself relays this as a signed webhook, so it doesn't require forging the webhook signature. This is trivially repeatable.

### Recommendation
Do not permit arbitrary pull-request-label-derived keys directly into the process environment. Either namespace label-derived variables (e.g., `SHIPIT_LABEL_<NAME>`) so they cannot collide with security-sensitive env var names, or run label names through an explicit allowlist/deny-list before merging into `env`, and ensure `Command#unbundled_env` enforces a hard deny-list of loader/security-sensitive variable names (`SSH_ASKPASS`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.) regardless of source.

### Proof of Concept
minitest (extends existing `test/models/shipit/review_stack_test.rb` / `test/lib/shipit/task_commands_test.rb` patterns):
```ruby
test "#env allows PR labels to inject security-sensitive keys with no allowlist" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ssh_askpass"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["SSH_ASKPASS"]

  command = Shipit::TaskCommands.new(task).install_dependencies.first
  assert_equal "true", command.unbundled_env["SSH_ASKPASS"]
end
```
This asserts both sides of the claimed invariant: expected (env keys limited to `machine_env`/`VariableDefinition` names) vs. actual (`SSH_ASKPASS` present, sourced solely from an uppercased PR label with no allowlist check).
