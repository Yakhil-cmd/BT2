Based on my investigation, the closest reachable analog in `ocore` to the "upgradable proxy token" bug class is the mutable asset attestor list (`asset_attestors` message), which lets an asset's spending-authorization rule change *after* the asset (and its `spender_attested` flag) has already been issued and relied upon by holders/AAs — conceptually the same risk as TUSD's implementation being swapped behind a fixed proxy address.

### Title
Mutable asset attestor list lets an asset issuer change spending authorization after issuance, freezing or diverting `spender_attested` asset funds - (File: `validation.js`, `definition.js`)

### Summary
An asset defined with `spender_attested: true` derives its authorization semantics from a list of `attestors` that is **not fixed at asset-definition time**. It can be updated later via a separate `asset_attestors` message/app, exactly like swapping the implementation behind a proxy token. Any unit, private payment, or AA that already holds or accepted this asset under one attestor set has no guarantee that the same attestor set (or any working attestor set) will still be valid at the time it tries to spend, because the check is re-evaluated against the attestor list current as of `last_ball_mci` at validation time, not the list that existed when the asset/funds were received.

### Finding Description
The asset definition (`app: "asset"`) explicitly supports a `spender_attested` flag plus an initial `attestors` array [1](#0-0) . Crucially, this attestor list is not immutable: it can be changed later by a distinct `asset_attestors` message that is validated independently and persisted as new rows tied to the same `asset` id [2](#0-1) . The write path confirms attestor-list updates are stored as additional `asset_attestors` rows keyed by the same `asset` unit, separate from the original asset definition row [3](#0-2) .

At payment-validation time, `spender_attested` enforcement is done by checking `objAsset.arrAttestedAddresses`, which is computed from whatever attestor list/attestation rows are current as of `last_ball_mci` — i.e., it reflects the *latest* attestor list, not the one in force when the asset/funds were originally transferred to the current holder [4](#0-3) . AAs and unprivileged asset definers can compose `asset_attestors` messages that update this list for any asset they define, as demonstrated in the AA test suite, which shows an AA updating an asset's `attestors` for an asset referenced purely from `trigger.output[[asset!=base]].asset` (i.e., driven by trigger data controlled by an unprivileged AA-trigger sender) [5](#0-4) .

This is architecturally the same pattern flagged in the external report: the "implementation" (attestor whitelist) sitting behind a fixed "proxy" (the asset id) can be swapped post-issuance, changing who is allowed to move funds denominated in that asset, without any action by the current holders.

### Impact Explanation
- **Freezing**: if the attestor list is cleared or replaced with addresses that no longer include any currently-attested holder (or any AA-reachable address, since AAs cannot themselves be attested by third parties), holders of that `spender_attested` asset — including AAs that received it as trigger payment — permanently lose the ability to satisfy the `arrAttestedAddresses` check on subsequent spends, per the enforcement logic at `validatePayment` [4](#0-3) . This is a concrete AA/unit fund-freezing outcome.
- **Unauthorized-looking authorization shift**: conversely, an issuer can add new attestors after distribution has already happened, retroactively "attesting" addresses that were never vetted when the funds were distributed, allowing spend paths that depositors/AAs did not anticipate when they accepted the asset.
- Both outcomes match the report's core concern: protocol logic that trusted a token/asset's rules at acceptance time can be silently invalidated later by a change the asset creator controls, breaking invariants baked into any AA or wallet logic that assumed a stable authorization model for the asset.

### Likelihood Explanation
Any address that originally defined the asset (`objAsset.definer_address`, checked implicitly through the standard asset/attestor-list validation path) can issue an `asset_attestors` update at any later time; this is a standard, unprivileged message type reachable by any ordinary unit poster or AA that defined the asset in the first place — no elevated network privileges are required, only being the asset's own definer, which any user or AA is free to become by defining a `spender_attested` asset. Given assets are commonly created and consumed by AAs (as shown in the AA composer test), the reachable surface for this includes ordinary AA-trigger-driven flows [6](#0-5) .

### Recommendation
- Snapshot and pin the attestor list (or a hash of it) at the time value is transferred/accepted by an AA or held privately, and re-validate spends against that pinned snapshot rather than the always-current list, or
- Disallow `asset_attestors` updates entirely once the asset has non-definer holders (or require a governance/timelock + advance notice window before an update takes effect), analogous to the MakerDAO TUSD-adapter recommendation of freezing interactions when the underlying "implementation" changes.
- At minimum, expose `spender_attested` asset attestor-list changes as an explicit, queryable state (already partially done via `asset_attestors` table) that AA authors are strongly warned to check/re-validate against on every use rather than assume immutability from the original `asset` definition message.

### Proof of Concept
1. Asset X is defined with `spender_attested: true`, `attestors: [A]` [1](#0-0) .
2. Multiple users/AAs receive and hold asset X, verified as valid because address A currently attests them.
3. The asset definer later posts an `asset_attestors` message for asset X with `attestors: [B]` (B unrelated to any current holder) [2](#0-1) , [3](#0-2) .
4. Any subsequent payment of asset X — even a pure transfer among long-time holders — is now checked against the new attestor list at `last_ball_mci` [4](#0-3) , and holders who are attested only by A can no longer validate as attested; their asset X balance becomes unspendable, i.e., frozen, exactly mirroring the TUSD-style "implementation swapped underneath a fixed proxy" bug class.
