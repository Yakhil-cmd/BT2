### Title
Cross-organization team hijack via `MembershipHandler#find_or_create_team!` — webhook signature is scoped to the sending org but team lookup is scoped only by numeric `github_id` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up the target `Team` purely by `params.team.id` (GitHub's global numeric team ID) and never verifies that the verified webhook-sending organization actually owns that `Team` record. Because `Team.find_or_create_by!` only assigns `team.organization = params.organization.login` when *creating* a new row, any attacker who legitimately owns one onboarded GitHub organization (and therefore knows/controls that org's webhook secret) can forge a `membership` webhook that passes signature verification for their own org, yet targets a pre-existing `Team` record belonging to a completely different organization — including any team listed in `Shipit.github_teams`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`params.organization.login` (the organization whose webhook secret was used to validate `X-Hub-Signature`) **should equal** `team.organization` (the organization that actually owns the `Team` row being mutated) for every `Team` affected by a `membership` webhook.

Trace of the code path:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')`. A `membership` payload has no `repository` key, so `repository_owner == params['organization']['login']`. [1](#0-0) [2](#0-1) 
2. `Shipit.github(organization: repository_owner)` resolves a per-organization `GitHubApp` instance keyed strictly on that login, each with its own independently configured `webhook_secret`. [3](#0-2) 
3. `GitHubApp#verify_webhook_signature` HMACs the raw body with that organization's own secret. An attacker who owns/administers their own onboarded org (`attacker_org`) knows that secret and can produce a valid signature for a payload whose `organization.login` is `attacker_org`. [4](#0-3) 
4. Inside `MembershipHandler#process`, the team is resolved with:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
`find_or_create_by!` only runs the block (which is the only place `organization` is ever assigned from the payload) when it has to **create** a new record. If a `Team` with that `github_id` already exists — which is true for every team in `Shipit.github_teams`, since those are pre-populated via `Shipit.github_teams`/`rake teams:fetch` — the existing record is returned untouched, and its `organization` is never compared against `params.organization.login`. [5](#0-4) 
5. `team.add_member(member)` then unconditionally appends the attacker-supplied `member.login` (created via `User.find_or_create_by_login!`, which just calls the GitHub Users API for that login — any valid GitHub login works, it doesn't need to be a member of any team) to that pre-existing team's `members`. [6](#0-5) 

Exploit flow: attacker owns `attacker_org`, has its webhook secret. They send:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC over body using attacker_org's webhook_secret>
{
  "action": "added",
  "team": { "id": <github_id of Shipit.github_teams(:privileged)>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "attacker_org" },
  "member": { "login": "attacker_github_login" }
}
```
This passes `verify_signature` (bound to `attacker_org`) but writes a `Membership` for the privileged, unrelated team.

Existing guards that fail to stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate *which organization sent the webhook*, not *which team the payload may mutate*; `ExplicitParameters` only enforces types/presence, not cross-field consistency; there is no `require_permission!`/ownership check in `Team` or `MembershipHandler`.

### Impact Explanation
A successful forgery adds an attacker-controlled GitHub login to `team.members` for any pre-existing `Team`, including teams enumerated in `Shipit.github_teams`, which directly gates `User#authorized?`:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [7](#0-6) 
Once that user logs in via OAuth as that GitHub login, `force_github_authentication` grants them full access to the Shipit application (viewing/deploying/rolling back stacks, managing repositories, etc.) rather than being rejected as unauthorized. [8](#0-7) 
This is repeatable against any tenant/team whose numeric `github_id` the attacker can learn, matching the "escalation into `Shipit.github_teams` authorization" category (High), since the actual write is cross-tenant (one org's authenticated webhook mutating another org's `Team`/`Membership` records) rather than confined to the attacker's own org.

### Likelihood Explanation
Preconditions: attacker must own/administer one onboarded GitHub organization with a configured webhook (multi-org Shipit deployments configure a distinct `webhook_secret` per organization key under `github:`), and must know the numeric `github_id` of the target `Team`. `github_id` values are not treated as secrets in this codebase (they're GitHub's own team IDs, exposed via GitHub's team/API URLs, GraphQL node IDs, or prior legitimate membership), so obtaining them is plausible information gathering rather than a cryptographic secret. No Shipit session, `api_clients_secret`, or GitHub App private key is required — only ownership of one organization's own webhook secret, which is explicitly in-scope per the attacker model ("owning one onboarded org with hook access"). The request is trivially repeatable for any team ID.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team#organization` matches `params.organization.login` (the value used for signature verification) before performing any mutation, and raise/drop the event (or refuse to add/remove members) when the organization does not own the team, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "Organization mismatch" unless team.organization.casecmp?(params.organization.login)
  team
end
```
Additionally, consider validating team membership against GitHub directly (e.g. `org_team_membership`) before trusting webhook-asserted membership changes for any team.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "membership webhook cannot add a member to a team owned by a different organization" do
  privileged_team = shipit_teams(:shopify_developers) # organization: "shopify", github_id: 1
  attacker_org = 'attacker-org'

  Shipit.stubs(:github).with(organization: attacker_org).returns(
    stub(verify_webhook_signature: true)
  )

  body = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker_login' }
  }.to_json

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = 'sha1=forged-but-valid-for-attacker_org'

  Shipit.github.api.stubs(:user).with('attacker_login').returns(
    stub(id: 999, login: 'attacker_login', name: 'Attacker', email: 'a@a.com', avatar_url: '', url: '')
  )

  post :create, body:, as: :json
  assert_response :ok

  created_user = User.find_by(login: 'attacker_login')
  # This assertion documents the vulnerability: membership is created despite
  # the signature only proving control of `attacker_org`, not of `shopify`.
  assert Membership.exists?(team_id: privileged_team.id, user_id: created_user.id)
end
```
Both sides of the claimed binding — `params.organization.login` ("attacker-org", cryptographically verified) and `team.organization` ("shopify", the actual owner of the mutated `Team`) — diverge, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
