## Title
Reward-accounting/payment split in `claim-staker-rewards-for-signer` allows a staker's sBTC rewards to be marked "claimed" without any guaranteed transfer, permanently losing rewards owed to a delegating staker - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar` splits sBTC reward *accounting* from the actual sBTC *transfer*, the same pattern that caused the PirexRewards bug: `claim-staker-rewards-for-signer` zeroes a staker's `staker-unclaimed-rewards-for-cycle` entry based on `contract-caller` (the "signer manager" contract), but the function itself never moves any sBTC. It only returns the computed `earned` amount and trusts the calling signer-manager contract to actually pay the staker out-of-band [1](#0-0) . Because pox-5 has no single canonical source that both computes and disburses the reward atomically for this staker-facing path, any mismatch between the amount pox-5 marks as settled and what the external signer-manager contract actually forwards results in silent, permanent loss of the staker's share of the sBTC bond rewards - the tokens stay in the contract's balance but are unrecoverable through `pox-5`'s own accounting, since the "unclaimed" counter is already at `u0`.

### Finding Description
`settle-rewards`/`settle-staker-rewards` compute a staker's/signer's `earned` sBTC (via `compute-earned-rewards`) and immediately persist that as the "already accounted for" checkpoint (`rewards-per-token-settled`), while separately tracking `unclaimed-rewards-for-cycle` [2](#0-1) .

For a *signer's own* claim (`claim-rewards`), the accounting update and the sBTC `transfer` happen in the very same atomic public function and same transaction, protected by `try!` - if the transfer fails, the whole transaction (including the state zeroing) reverts, so no loss occurs [3](#0-2) .

However, `claim-staker-rewards-for-signer` is a *different*, staker-facing entry point meant to be invoked by an external "signer manager" contract (`contract-caller`) that manages rewards on behalf of a delegating `staker`. This function:
1. Computes `rewards-info` (the staker's earned sBTC) via `settle-staker-rewards`.
2. Unconditionally sets `staker-unclaimed-rewards-for-cycle` for that `(reward-cycle, bond-index, signer=contract-caller, staker)` key to `u0` - i.e., marks the reward as fully paid.
3. Returns `rewards-info` without performing (or requiring) any sBTC transfer to `staker` at all [4](#0-3) .

There is no code in `pox-5.clar` that forces the calling signer-manager contract to actually forward `(get earned rewards-info)` sBTC to `staker` in the same transaction, nor any assertion that a transfer occurred, nor any rollback if it does not. The only safeguard present is `validate-no-reentrancy`, which guards against re-entrant calls, not against a missing/incorrect payout [5](#0-4) .

This exactly mirrors the PirexRewards root cause described in the report: the reward-state "already claimed" flag (`user.rewards = 0` / here `staker-unclaimed-rewards-for-cycle = u0`) is set based on a *separate* source of truth (the calling signer-manager contract) from the one that actually performs the payment, and a mismatch between the two (bug, misconfiguration, or a signer-manager contract that simply never executes the forwarding `stx-transfer?`/sBTC transfer) causes the staker's reward to be marked settled with nothing paid, and it can never be re-claimed afterward because the internal counter is already zero.

### Impact Explanation
The sBTC amount corresponding to `rewards-info` remains locked inside the contract's balance (it was never moved out via `as-contract?`/`transfer` at the pox-5 layer for this staker), yet `pox-5`'s own bookkeeping now shows it as `u0` unclaimed for that staker/cycle/bond. The staker permanently loses the ability to claim that reward through `pox-5`, since `settle-staker-rewards`/`get-earned-staker-rewards` will report `0` pending for that period going forward. This is a permanent freeze of sBTC value belonging to the staker (their share of `pox-5`'s reward pot is stranded), meeting the "permanent freezing of staked STX or sBTC" criterion. It does not require the bond/pause admin - any signer-manager contract a signer/staker relationship relies on (which, per the design, is an externally supplied contract implementing the trait, not `pox-5` itself) can trigger this simply by calling `claim-staker-rewards-for-signer` without completing its own forwarding transfer, whether due to a bug, a reentrancy-unrelated failure path, or being paused/misconfigured.

### Likelihood Explanation
Likelihood is moderate: it requires a signer-manager contract in the loop that is buggy or mismanaged (analogous to the "reward token mismanagement" root cause in the original report - a mismatch between two independently-maintained pieces of state/logic). Given that `pox-5` explicitly documents this function as being driven by an external "signer manager" contract and offers no atomic-payment guarantee, any such contract that fails to correctly forward funds (e.g., due to its own accounting bug, an unhandled error path, insufficient balance at call time, or being upgraded/paused) will reproduce this loss without reverting the `pox-5` state change, and without any error surfaced to the affected staker.

### Recommendation
Require the actual sBTC transfer to the `staker` to happen atomically within `claim-staker-rewards-for-signer` itself (e.g., have `pox-5` perform the `as-contract?`/`transfer` directly to `staker`, the same pattern used in `claim-rewards`), rather than relying on the calling signer-manager contract to separately move funds after `pox-5` has already zeroed its internal accounting. If a two-step design (settle accounting, then have caller pay) is required, `pox-5` should not zero `staker-unclaimed-rewards-for-cycle` until it has confirmed (via its own transfer call, or a return receipt validated on-chain) that the sBTC was actually delivered.

### Proof of Concept
1. A staker delegates to `signer` and is registered under a signer-manager contract `SM` that implements whatever trait `pox-5` expects for staker delegation.
2. `SM` calls `pox-5.claim-staker-rewards-for-signer(staker, reward-cycle, bond-index)`.
3. `pox-5.settle-staker-rewards` computes `earned = X` sBTC and `claim-staker-rewards-for-signer` immediately sets `staker-unclaimed-rewards-for-cycle` to `u0` for `(reward-cycle, bond-index, signer=SM, staker)` [6](#0-5) .
4. `SM` (due to a bug, a failed follow-up call, insufficient tracked balance, or simply omitting the forwarding step) never sends `X` sBTC to `staker`.
5. The `pox-5.claim-staker-rewards-for-signer` call still returns `(ok rewards-info)` - no revert occurs, since `pox-5` itself performed no transfer that could fail.
6. `staker` subsequently calls any read-only/claim path (e.g. `get-earned-staker-rewards`) and sees `0` pending for that cycle/bond - the `X` sBTC is now permanently unclaimable through `pox-5`, even though it was never actually paid to `staker`.

;; As a signer manager contract, mark a specific staker as having claimed
;; rewards. This is used to mutate internal rewards settlement state.
;;
;; This is only callable by the signer manager contract.
(define-public (claim-staker-rewards-for-signer
        (staker principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let ((rewards-info (settle-staker-rewards contract-caller reward-cycle bond-index staker)))
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))
        (map-set staker-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: contract-caller,
            staker: staker,
        }
            u0
        )
        (print {
            topic: "claim-staker-rewards-for-signer",
            signer-manager: contract-caller,
            staker: staker,
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            rewards-claimed: (get earned rewards-info),
        })
        (ok rewards-info)
    )
)

;; Update all earned-but-unclaimed rewards for a staker, and update the snapshot
;; (staker-rewards-per-token-settled-for-cycle) for the staker.
;;
;; This MUST be called before any update to `staker-shares-staked-for-cycle`,
;; because changes to that state will effect rewards calculations.
(define-private (settle-staker-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
        (staker principal)
    )
    (let (
            (earned (get-earned-staker-rewards signer reward-cycle bond-index staker))
            (rewards-per-token (get-signer-rewards-per-token-for-cycle signer reward-cycle
                bond-index
            ))
        )
        (map-set staker-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
            staker: staker,
        }
            earned
        )
        (map-set staker-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
            staker: staker,
        }
            rewards-per-token
        )
        {
            earned: earned,
            rewards-per-token: rewards-per-token,
        }
    )
)
