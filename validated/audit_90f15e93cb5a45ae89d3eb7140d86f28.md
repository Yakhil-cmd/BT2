### Title
Unhandled `throw Error` in payment-input validation causes uncaught exception / node crash (DoS) - ([File: validation.js])

### Summary
The reported OpenEXR bug class is a hard abort() triggered by attacker-controlled input in a code path that is only partially wrapped in error handling. In `validation.js`'s `validatePaymentInputsAndOutputs`, several `throw Error(...)` statements are reachable from attacker-supplied unit/message data during normal (non-privileged) unit validation, and they execute inside nested `async`/DB-callback scopes that are not guarded by any enclosing `try/catch`. A thrown error inside such a callback becomes an uncaught exception in Node.js. The codebase's only `uncaughtException` handling lives in `network.js` [1](#0-0) , and the validation entry point `validate()` wraps only a small opening section in `try/catch` [2](#0-1) , leaving the deep validation chain (called via `async.series` inside `validateAuthors`/`validateMessages`/`validatePaymentInputsAndOutputs`) unprotected, mirroring OpenEXR's pattern of only wrapping the header parser while leaving codestream construction unprotected.

### Finding Description
`validatePaymentInputsAndOutputs` processes a `transfer` input for a private, fixed-denomination asset by relying on `objValidationState.src_coin` being pre-populated by the private-chain validator, rather than looking the output up in the database: [3](#0-2) 

If `objValidationState.src_coin` is not set (or lacks `src_output`/`denomination`/`amount`), the code does not return a soft validation error via the `cb(...)` callback convention used everywhere else in this function (e.g. `return cb("...")`), but instead does a bare `throw Error("no src_coin")` / `throw Error("no src_output")` / `throw Error("no denomination in src coin")` / `throw Error("no src coin amount")`. This is the same anti-pattern as the assert-vs-recoverable-error mismatch in the CVE: most malformed-input conditions in this switch statement are handled gracefully with `cb(error_string)`, but these specific conditions abandon that convention and throw synchronously instead.

Because this logic executes inside the `async.eachSeries` input-processing loop that is itself invoked from `validateAuthors`/`validateMessages` inside an outer `async.series` in `validate()` [4](#0-3) , and the top-level `try/catch` in `validate()` only wraps the unit-hash calculation near the top of the function [2](#0-1) , a `throw` here is not caught by that early `try/catch`. It propagates as an unhandled exception through the async callback chain.

Other `throw Error(...)` calls exist in the same style throughout `validatePaymentInputsAndOutputs`, e.g. on malformed DB state assumptions: [5](#0-4) [6](#0-5) 

These are intended as "should never happen" sanity checks against local DB corruption, but the `src_coin` case at lines 2415-2424 is different: `src_coin` is populated purely from data supplied by a private-payment-chain sender before the chain has been persisted to the DB (per the comment "we validate the entire chain before saving anything"), making it attacker-influenced rather than a pure DB-integrity invariant.

### Impact Explanation
An uncaught exception thrown deep inside an `async` callback chain during unit/joint validation is not converted into a soft `ifUnitError`/`ifJointError` callback result. Depending on how the call stack unwinds relative to any `try/catch` frames still on the stack (there are none directly wrapping this async continuation), this can surface as an unhandled promise/callback exception that Node.js treats as a fatal error, terminating the process — a denial of service that stops the node from validating and confirming any further units, matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
Reaching this code requires posting or forwarding a private, fixed-denomination asset payment chain (`hub/private_payment` / `handlePrivatePaymentChains` flow) where the `src_coin` state populated for the chain omits or corrupts `src_output`, `denomination`, or `amount` fields, or omits `src_coin` entirely for a `transfer` input under such an asset. This is reachable by any private-payment counterparty crafting a malformed private chain, which matches the "in-scope" actor list (private-payment counterparty). However, I could not fully trace, within the available index, the exact code in `indivisible_asset.js` that populates `objValidationState.src_coin` before calling into this validator, so I cannot confirm with full certainty whether upstream code already guarantees these fields are always present before reaching line 2415, which would reduce or eliminate reachability. This uncertainty should be treated as a caveat requiring deeper tracing of `indivisible_asset.js`'s private-chain validation flow.

### Recommendation
Replace the bare `throw Error(...)` calls at validation.js lines 2416-2424 (and ideally audit the rest of `validatePaymentInputsAndOutputs`/`validateAuthor` for the same pattern) with graceful `return cb("...")` error returns consistent with the rest of the function, so malformed/missing `src_coin` state on an untrusted private chain results in a normal validation failure (`ifUnitError`) rather than an uncaught exception that can crash the process. Where a `throw` is truly meant to guard an internal invariant unreachable from network input, add an enclosing `try/catch` at the call site that reports the condition through the callback-based validation result APIs instead of letting it escape to the top of the event loop.

### Proof of Concept
Conceptual PoC (subject to confirming exact `src_coin` population path in `indivisible_asset.js`):
1. As a private-payment counterparty, construct a private payment chain declaring a `transfer` input referencing a fixed-denomination private asset, but omit or malform the accompanying `src_coin`-derived data (e.g., missing `src_output` in the chain element) so that `objValidationState.src_coin` ends up unset or incomplete when `validatePaymentInputsAndOutputs` processes the `transfer` case.
2. Send this chain via the `hub/private_payment` / `handlePrivatePaymentChains` path [7](#0-6)  to a victim node.
3. When the victim's node reaches validation.js line 2416 (`if (!objValidationState.src_coin) throw Error("no src_coin");`), the thrown exception propagates outside any protective `try/catch`, crashing the node process and denying further unit validation — the same "unconditional abort not intercepted by surrounding error handling" bug class as CVE-2026-53532.
