### Title
Non-payable `_to` address permanently locks bridged KLAY in `handleKLAYTransfer` with no recovery path — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` uses a push-payment pattern to deliver KLAY to the recipient `_to`. If `_to` is a contract that reverts on receiving KLAY, the `require(ok, ...)` guard causes the entire transaction to revert, rolling back all state changes. Because the bridge has no admin-recovery or pull-withdrawal mechanism, the KLAY is permanently locked in the bridge contract and the affected nonce can never be consumed, freezing `lowerHandleNonce` and `recoveryBlockNumber`.

---

### Finding Description

In `handleKLAYTransfer`, after all nonce bookkeeping and event emission, KLAY is pushed to `_to`:

```solidity
// contracts/service_chain/bridge/BridgeTransferKLAY.sol  lines 98-99
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

The state mutations that precede this call — `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber`, and `_updateHandleNonce` — are all reverted when the `require` fails: [2](#0-1) 

Because every revert undoes those writes, `handleNoncesToBlockNums[_requestedNonce]` is never durably set to a non-zero value. The `_updateHandleNonce` loop advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0`:

```solidity
// BridgeTransfer.sol  lines 150-155
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [3](#0-2) 

So `lowerHandleNonce` is permanently stuck at the failing nonce, `recoveryBlockNumber` never advances from its initial value of `1`, and the bridge recovery daemon replays from block 1 indefinitely.

The `Bridge.sol` contract exposes no `emergencyWithdraw`, no admin-redirect, and no pull-withdrawal function: [4](#0-3) 

---

### Impact Explanation

**Impact: High**

The KLAY that was locked on the source chain and credited to the destination bridge is permanently undeliverable. The user's bridged KAIA is lost with no on-chain recovery path. Additionally, `lowerHandleNonce` freezing at the stuck nonce means `recoveryBlockNumber` stays at `1`, causing the off-chain `valueTransferRecovery` daemon to scan the entire chain history on every recovery cycle, degrading bridge liveness for all users.

---

### Likelihood Explanation

**Likelihood: Low**

A user must specify a `_to` address that is a contract without a payable fallback/receive function. This can happen accidentally (e.g., a multisig or smart-contract wallet that does not accept plain KLAY transfers) or intentionally as a griefing vector. The trigger requires no special privilege — any user of the bridge on the source chain controls the `_to` field.

---

### Recommendation

Replace the push-payment with a pull mechanism: record the pending balance in a mapping and let the recipient withdraw it separately. As a minimal fix, do not `require` success on the KLAY transfer; instead, if the push fails, store the amount in a `pendingWithdrawals[_to]` mapping and expose a `withdraw()` function, analogous to the recommendation in the referenced report:

```solidity
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;
    emit KLAYTransferFailed(_to, _value, _requestedNonce);
}
```

This ensures the nonce is always consumed and `lowerHandleNonce` always advances, while still allowing the recipient to claim their KLAY.

---

### Proof of Concept

1. On the source chain, user calls `requestKLAYTransfer(maliciousContract, value, "")` where `maliciousContract` has no payable fallback.
2. The source bridge emits `RequestValueTransfer` with `_to = maliciousContract`, nonce `N`.
3. Operators call `handleKLAYTransfer(..., maliciousContract, value, N, ...)` on the destination bridge.
4. Execution reaches line 98: `(bool ok, ) = maliciousContract.call.value(value)("")` → `ok = false`.
5. Line 99: `require(false, "handleKLAYTransfer: transfer failed")` → entire tx reverts.
6. `handleNoncesToBlockNums[N]` is never written; `lowerHandleNonce` stays at `N`.
7. Operators retry indefinitely — every attempt reverts. The `value` KLAY is permanently locked in the bridge.
8. `recoveryBlockNumber` remains `1`; the `valueTransferRecovery` daemon scans from genesis on every cycle. [5](#0-4) [6](#0-5)
