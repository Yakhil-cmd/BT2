### Title
Stack-scoped API tokens bypass their `stack_id` scope in `Api::CCMenuController#show`, allowing unauthenticated-style read of any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (`current_api_client.stack_id`) can only resolve `Stack` records from that one stack via the `stacks`/`stack` helpers. `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, so any valid stack-scoped token can be used to read the CI/build status of an arbitrary stack, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` defines the authorization binding between a token and the stacks it may touch: [1](#0-0) 

`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a stack, and `stack` is derived from that restricted relation. This is the binding: *stack a token authorizes == stack a controller action touches*.

`Api::CCMenuController` inherits from `BaseController` and requires only the generic `read:stack` permission string, then redefines `stack` to resolve directly against the global `Stack` table, discarding the `stacks` scoping: [2](#0-1) 

Because `require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks a flat permission list and never compares `current_api_client.stack_id` against the requested `params[:stack_id]`: [3](#0-2) 

...any token carrying `read:stack` — including one deliberately scoped to a single stack — can be replayed with a different `stack_id` in the URL and will successfully authenticate and render that other stack's data. The stack the token *authorizes* (its `stack_id` association) is never verified to equal the stack the action *touches* (`params[:stack_id]`).

This class of tokens is specifically generated by `CCMenuUrlController`, meant to be embedded in third-party CI-status dashboard tools (e.g. CCMenu clients) and is scoped/expected to be limited to one stack: [4](#0-3) 

The existing test suite confirms the intended invariant elsewhere in the API (e.g. `StacksController#index`), where a stack-scoped client ("here_come_the_walrus", scoped to the `shipit` stack fixture) is asserted to only see its own stack: [5](#0-4) [6](#0-5) 

But `CCMenuController`'s own test suite never exercises a stack-scoped client against a foreign `stack_id`, and the code path clearly permits it because `stack` no longer goes through `stacks`.

### Impact Explanation
This is unauthenticated-style read of stack/build state for stacks the token holder was never granted access to. A CCMenu URL/token — a lightweight, semi-public credential intended only to expose one project's build status — can be used to enumerate `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, and `webUrl` for every stack in the Shipit instance, including private/internal deployment stacks the token's creator has no `read:stack` grant on beyond their own project. This matches the in-scope High-severity criterion: "unauthenticated read of stack state, task streams or deploy output," because the effective authorization check for stack scope is entirely absent in this controller despite existing elsewhere in the same API layer.

### Likelihood Explanation
Likelihood is high for any deployment where CCMenu URLs are generated and shared (their purpose is external consumption by CI dashboard tooling, so they are more likely to leak or be embedded in less-trusted contexts than a full API key). No privileged access, TLS interception, or social engineering is required — only possession of any valid, stack-scoped `read:stack` token (which by design is meant to be lower-privilege and shareable) and knowledge/guessing of another stack's `owner/repo/environment` identifier, which is often predictable or discoverable from the Shipit UI.

### Recommendation
Have `Api::CCMenuController#stack` reuse the inherited, properly scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack.from_param!` directly, so that stack-scoped tokens cannot resolve stacks outside their `stack_id` association.

### Proof of Concept
1. As an authorized Shipit user, request a CCMenu URL for stack `myorg/myrepo/production` via `CCMenuUrlController#fetch`; this mints an `ApiClient` with `permissions: ['read:stack']` (in current code, unscoped to a stack) or, using the pattern demonstrated by the `here_come_the_walrus` fixture, an `ApiClient` with `stack: <stack>, permissions: ['read:stack']` scoped to one stack.
2. Take the resulting `token` query parameter.
3. Call `GET /api/*other_org/other_repo/other_env/cc.xml?token=<token>` (routed to `Api::CCMenuController#show`) for a *different* stack than the one the token was scoped/intended for.
4. Observe that `authenticate_api_client` succeeds (valid signature) and `require_permission :read, :stack` passes (token has `read:stack`), and `stack` resolves to the *other* stack because it queries `Stack.from_param!(params[:stack_id])` directly rather than the scoped `stacks` relation — returning that other stack's build status/name/activity in the XML response.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
