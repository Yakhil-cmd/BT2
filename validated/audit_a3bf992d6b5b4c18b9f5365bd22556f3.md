## Finding: Confirmed

The binding claimed in the question — `repository_name` derived from the verified payload (`Handler#repository_name`) == the repository owning every `Commit` mutated by `StatusHandler#process` — is **false**, and this is a real, exploitable cross-tenant vulnerability.

### Broken binding

`Shipit::Webhooks::Handlers::Handler#stacks` exists precisely to scope handler mutations to the repository the verified webhook claims to be from: [1](#0-0) 

Every other status/PR handler (`OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, etc.) resolves `repository`/`stack` via `Repository.from_github_repo_name(params.repository.full_name)` before touching any record: [2](#0-1) 

But `StatusHandler#process` never does this. It runs a **global, unscoped** lookup by `sha` alone: [3](#0-2) 

and `Commit#create_status_from_github!` unconditionally writes a `Status` bound to `commit.stack_id` (the commit's *own* stack, not the requester's): [4](#0-3) [5](#0-4) 

### Why the signature check does not save you

`WebhooksController#verify_signature` only proves the request was signed by *some* `webhook_secret` belonging to the organization named in `params['repository']['owner']['login']` — it says nothing about which `Commit` rows exist with a matching `sha`: [6](#0-5) 

### Root cause / uniqueness

`Commit` uniqueness is only enforced per-stack, not globally, per the index `index_commits_on_stack_id_and_sha` — i.e., the schema explicitly permits the same `sha` to exist under multiple different `stack_id`s simultaneously: [7](#0-6) 

This can legitimately happen whenever two Shipit-tracked repositories (owned by different tenants) share git history — e.g., repository B is a fork of, or shares an ancestor commit with, repository A (a very common real-world case for CI/CD platforms hosting forks or shared upstream libraries) — so both stacks end up with a `Commit` row for the identical `sha`.

### Exploit flow
1. Attacker owns repository B, which shares a commit `X` (identical sha) with repository A's tracked history (fork/shared ancestor). Both `Stack A` and `Stack B` already contain a `Commit` row with `sha = X` (ingested normally via `push`/sync for each stack independently).
2. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with **B's own** `webhook_secret`, `repository.full_name` = B's own repo, `sha: X`, and arbitrary `state`/`description`/`target_url`/`context`.
3. `verify_signature` passes — it only validates against B's organization's secret.
4. `StatusHandler#process` runs `Commit.where(sha: X)`, which returns **both** B's own commit row and A's commit row.
5. `create_status_from_github!` writes a forged `Status` onto A's commit, mutating Stack A's CI state (which can gate `deployable?`, autodeploys, `enable_ci_on_stack`, and `ProcessMergeRequestsJob` — see `Commit#deployable?` and `Status#enable_ci_on_stack`/`#schedule_continuous_delivery`). ### Title
Cross-tenant Status write via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table instead of scoping through `Handler#stacks`/`repository_name`, so a signed `status` webhook for repository B can write a `Status` onto a `Commit` belonging to repository A's stack whenever the two repositories share a commit sha (e.g., forks/shared history), forging tenant A's CI state.

### Finding Description
The broken binding: `repository_name` (verified via B's `webhook_secret`) == owner of every `Commit` row matched by `Commit.where(sha: params.sha)` is false, because `Commit.sha` uniqueness is only enforced per-`stack_id`, not globally [7](#0-6) , and `StatusHandler#process` [3](#0-2)  never filters through `Handler#stacks` [1](#0-0) . `verify_signature` only authenticates that the payload's declared organization owns the secret used [6](#0-5) ; it does not restrict which `Commit` rows the handler is allowed to mutate.

### Impact Explanation
An attacker controlling only repository B's webhook secret can write arbitrary `Status` rows (`state`, `description`, `target_url`, `context`) onto commits belonging to any other stack/repository A whose commit history intersects B's (forks, shared upstream libraries, monorepo splits). This can flip `Commit#deployable?`, trigger `enable_ci_on_stack`, and enqueue `ProcessMergeRequestsJob`/continuous delivery for tenant A — matching "a payload for one repository mutating another's stack/commit" (Critical).

### Likelihood Explanation
Requires: (a) the Shipit instance hosts multiple tenants/stacks, and (b) at least one shared commit sha exists between the attacker's own repository and a victim repository — a realistic condition for forks or shared-history repos, which the attacker can also try to engineer by forking a victim's public repo and creating their own Shipit stack for it if review-stacks/self-service stack creation is permitted. No privileged credentials are required beyond the attacker's own repo's `webhook_secret`, which they legitimately hold as its owner.

### Recommendation
Scope the lookup in `StatusHandler#process` through the verified repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern used by `OpenedHandler`/`LabeledHandler`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, new):
1. Create `repository_a`/`stack_a` and `repository_b`/`stack_b`.
2. Create `commit_a = stack_a.commits.create!(sha: "deadbeef...")` and `commit_b = stack_b.commits.create!(sha: "deadbeef...")` (same sha, different stacks).
3. Build a `status` payload with `repository.full_name = repository_b.full_name`, `sha: "deadbeef..."`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST to `/webhooks` with a stubbed/real signature for B).
5. Assert `commit_a.statuses.count` changed from 0 to 1 (equality broken: B's webhook mutated A's commit) — `assert_equal 1, commit_a.reload.statuses.count` — while only `commit_b`'s repository authenticated the request.
