### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on an attacker-controlled field inside the JSON payload itself (`repository.owner.login`, falling back to `organization.login`), while every webhook handler that actually mutates state (syncs commits, creates statuses, updates pull requests) keys off a *different* attacker-controlled field, `repository.full_name`. These two fields are never cross-checked against each other. This mirrors the reported Folks Finance flaw where a value used to decide "is this trusted/counted" (the pushed `poolId`) was never validated against the value actually used in the security-critical calculation (`colPools` dedup), letting an attacker cause the wrong artifact to be treated as authenticated.

### Finding Description
The `verify_signature` before_action does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a GithubApp/secret configuration scoped to that organization name (raising `Shipit::GithubOrganizationUnknown` if not configured) [2](#0-1) , and each organization gets its own `webhook_secret` from `lib/shipit/github_app.rb`'s `initialize` (`@webhook_secret = @config[:webhook_secret]`) used later in `verify_webhook_signature` [3](#0-2) .

However, once the signature check passes, `create` re-parses the raw body and dispatches it to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler resolves the target repository/stack from `repository.full_name`, not from `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler`, for example, uses this to enqueue a real sync job against a stack: `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [6](#0-5) . The pull request handlers similarly resolve `Repository.from_github_repo_name(params.repository.full_name)` independently [7](#0-6) .

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository/stack) are two separate, independently attacker-supplied JSON fields with no cross-validation, an attacker who legitimately controls (or has been granted) a GitHub App installation for **their own** organization — and therefore knows/controls that organization's `webhook_secret` — can craft a payload where `repository.owner.login` names their own org (so the HMAC check succeeds against their own secret) but `repository.full_name` names a stack/repository belonging to a *different, victim* organization tracked by the same Shipit instance. The binding broken is: **organization authenticated (`repository.owner.login`) ≠ repository actually written (`repository.full_name`)**.

### Impact Explanation
This does not require possession of `webhook_secret`, `api_clients_secret`, or a GitHub App private key for the victim organization — only for the attacker's own (possibly unprivileged) org/app configured on the same Shipit instance. With a forged payload the attacker can:
- Trigger `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, effectively injecting arbitrary commit shas into a repository's Shipit-tracked history/state (`PushHandler`).
- Manipulate `commit_status`/`check_suite` state for a victim's stack, or `pull_request` label/merge-queue state, since those handlers also resolve purely off `repository.full_name`.

Depending on downstream trust in synced commit/status data (e.g., triggering deploys via continuous delivery, altering merge-queue state, marking commits deployable), this could lead to an unauthorized deploy trigger or corrupted deployment history for a repository the attacker does not control — crossing a cross-repository write boundary using only a webhook payload and their own org's credentials.

### Likelihood Explanation
Requires the attacker to control (own or compromise) at least one GitHub organization/App configured in the same multi-tenant Shipit deployment, plus knowledge of that stack naming (`owner/name`) for the target victim repository, which is often discoverable (public repos, Shipit UI listing stacks). This is a realistic scenario for any Shipit instance serving multiple GitHub organizations/teams, which the engine explicitly supports via per-organization `Shipit.github(organization:)` configuration.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the organization portion of `repository.full_name` before dispatching to handlers. Reject the webhook (422) if they don't match. Additionally, consider deriving `repository_owner` strictly from `repository.full_name.split('/').first` rather than trusting a separate JSON field, so there is a single source of truth for "which org's secret verifies this payload" and "which repository the payload acts on."

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker controls the app/webhook secret) and `victim-org` (has a tracked stack, e.g. `victim-org/app`).
2. Craft a webhook POST to `/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/app",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Sign the raw body with `attacker-org`'s known `webhook_secret` and set `X-Hub-Signature` accordingly.
4. `verify_signature` computes `repository_owner` = `"attacker-org"`, loads `attacker-org`'s GithubApp, and the signature verifies successfully [8](#0-7) .
5. `create` re-parses and dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name` = `"victim-org/app"` [5](#0-4)  and enqueues `GithubSyncJob` for the victim's stack with the attacker-chosen `expected_head_sha` [6](#0-5) , despite the request never having been signed by `victim-org`'s secret.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
