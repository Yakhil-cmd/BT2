### Title
Webhook signature scoped to attacker-controlled `repository.owner.login`/`organization.login`, while event handlers act on a separate `repository.full_name` field — cross-organization webhook spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit selects which GitHub App/`webhook_secret` to use for HMAC verification of an incoming webhook based on a field read from the *same untrusted JSON body* that the signature covers (`repository.owner.login`, falling back to `organization.login`). The repository that is actually acted upon by the event handlers, however, is derived from a *different* field of that same body (`repository.full_name`). Because the field selecting the trust boundary (which org's secret validates the request) is decoupled from the field selecting the object acted upon (which repo/stack is synced), a party who legitimately controls a GitHub App installation for Organization A on a multi-tenant Shipit instance can forge a payload whose signature is valid under Org A's secret while its `repository.full_name` points at a repository belonging to Organization B.

### Finding Description
`WebhooksController#verify_signature` looks up the `GitHubApp` (and its `webhook_secret`) using an organization name pulled straight out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

This `repository_owner` string is used only to pick which `webhook_secret` verifies the HMAC signature via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire raw payload* to event handlers such as `PushHandler`: [4](#0-3) 

`Handler#stacks`/`Handler#repository_name` — the base class used by `PushHandler` and other handlers — resolves which `Repository`/`Stack` to act on using a *different* field of the same payload, `repository.full_name`, with no cross-check against the organization used to verify the signature: [5](#0-4) [6](#0-5) 

The equality the code implicitly (and incorrectly) assumes is:

`organization used to select webhook_secret (repository.owner.login / organization.login)` == `organization that owns the repository actually processed (repository.full_name)`

Nothing in `verify_signature` or in `Handler` enforces this equality. As documented in `docs/setup.md`, a single Shipit deployment is explicitly designed to serve multiple GitHub organizations, each with its own `webhook_secret` in `config/secrets.yml`: [7](#0-6) 

An attacker who controls (as an ordinary, unprivileged GitHub org admin) a GitHub App installation pointed at this shared Shipit instance — i.e., "OrgA", one of the tenants — legitimately possesses OrgA's `webhook_secret` (GitHub reveals it to whoever configures the app). They can craft and correctly HMAC-sign a JSON body where:
- `repository.owner.login` = `"OrgA"` (used only to select the verifying secret)
- `repository.full_name` = `"OrgB/victim-repo"` (used to select the actual `Stack`/`Repository` that gets processed)

`verify_signature` succeeds because the signature was computed with OrgA's own, legitimately-known secret. The subsequent `PushHandler#process` then operates on `Repository.from_github_repo_name("OrgB/victim-repo")`, invoking `stack.sync_github(expected_head_sha: params.after)` for a stack that OrgA has no rights over.

### Impact Explanation
This breaks the binding between "the organization whose credential authenticated the request" and "the repository the engine actually writes to," matching the report's bug class (a payload field acted upon that isn't the one the verification actually covers). The practical effect is a forged webhook, valid under OrgA's secret, causing Shipit to enqueue a `GithubSyncJob`/sync for an arbitrary tracked stack under OrgB using an attacker-chosen `expected_head_sha`, which is a cross-repository/cross-tenant integrity violation of webhook trust — the write (stack sync, commit ingestion) targets a repository the presenting credential does not authorize.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly supported and documented) and requires the attacker to be an authorized administrator of at least one of the tenant organizations configured on that instance — no privileged Shipit account, `ApiClient` token, or GitHub token theft is needed, only knowledge of their own org's `webhook_secret`, which they legitimately hold. This is a realistic, low-effort condition in any shared/multi-tenant Shipit instance.

### Recommendation
Bind the signature-verifying organization to the repository actually processed: after `verify_signature` succeeds, re-derive `repository_owner` from `repository.full_name` (not `repository.owner.login`/`organization.login`) and confirm it matches the organization whose secret validated the signature (or, simpler, verify the signature using the `webhook_secret` associated with the `Repository` resolved from `repository.full_name`, looked up server-side, rather than trusting any organization field from the payload for secret selection).

### Proof of Concept
1. Shipit instance configured (per `docs/setup.md`) with two GitHub orgs, `OrgA` and `OrgB`, each with its own `app_id`/`webhook_secret`, both tracking repositories as Shipit stacks.
2. Attacker administers the GitHub App installation for `OrgA` and thus knows `OrgA`'s `webhook_secret`.
3. Attacker builds a `push` payload body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POSTs it with `X-Github-Event: push` to the shared `/webhooks` endpoint.
5. `WebhooksController#repository_owner` returns `"OrgA"`; `verify_signature` succeeds using `OrgA`'s secret. `Handler#repository_name` resolves `"OrgB/victim-repo"`, and `PushHandler#process` calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack — a repository the attacker has no legitimate control over.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
