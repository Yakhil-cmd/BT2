### Title
OSC/ANSI escape sequences in check name/description/URL fields reach the terminal unsanitized via `printTable` writing to `io.Out` instead of `io.ContentOut` - (File: pkg/cmd/pr/checks/output.go)

### Finding Description
`printTable` (`pkg/cmd/pr/checks/output.go:94`) builds a `tableprinter.TablePrinter` via `tableprinter.New(io, ...)` [1](#0-0) , and `addRow` feeds it attacker-influenced fields straight from the `check` struct: `o.Name`, `o.Description`, `o.Link`, `o.Workflow`, `o.Event` [2](#0-1) . These values are populated in `aggregateChecks` directly from the GitHub API check-run/check-suite response (`c.Name`/`c.Context`, `c.Description`, `c.DetailsURL`/`c.TargetURL`, `c.CheckSuite.WorkflowRun.Workflow.Name`, `c.CheckSuite.WorkflowRun.Event`) with no sanitization [3](#0-2) . A GitHub Actions workflow name, a check-run name, or a check-run description/details URL can be set by an attacker who controls a fork/PR/workflow (e.g., a custom check name or a status description string), making these fields attacker-controlled.

Critically, `internal/tableprinter.New` constructs the table printer using `ios.Out` directly — the raw, unsanitized stdout writer — rather than `ios.ContentOut`, which is the writer the codebase designates for untrusted/external content and which wraps output with `asciisanitizer.Sanitizer` to strip ANSI/OSC escape sequences [4](#0-3) . This is confirmed by contrast with `pkg/iostreams/iostreams.go`, where `ContentOut` is explicitly described as "the writer for external content ... where the application is not the author of the bytes" and by default sanitizes escape sequences before they reach stdout [5](#0-4) , and by `pkg/iostreams/untrusted.go`'s `Untrusted` type, which is the pattern used elsewhere in the codebase to guarantee sanitization on any fmt path [6](#0-5) . The `check` struct fields are plain `string`, not `Untrusted`, and are never routed through `ContainsEscapeSequence`/`asciisanitizer` before being handed to the table printer, so any OSC/ANSI byte sequence (including OSC 52, `\x1b]52;...`) embedded in a check name, description, or URL is written verbatim to the victim's real terminal when they run `gh pr checks`.

### Impact Explanation
If exploitable, OSC 52 is a terminal feature that lets an application set the clipboard contents. An attacker who can inject `\x1b]52;c;<base64>\x07` into a check name/description (via a custom check run or workflow name on their own fork/PR) could silently overwrite the victim's clipboard with attacker-chosen text — e.g., a malicious shell command — to be pasted and executed later. This would map to a "Websites and Apps: arbitrary code execution" / clipboard-hijacking class of impact if the victim's terminal emulator supports OSC 52 write and the victim later pastes the staged content into a shell.

### Likelihood Explanation
Preconditions: the victim must run `gh pr checks` against a PR/repo containing attacker-supplied check names/descriptions/URLs (achievable by an unprivileged attacker who opens a PR with a custom GitHub Actions job/check name, or a third-party check-run integration whose fields are attacker-controlled), and the victim's terminal emulator must honor OSC 52. This does not require any privileged access — publishing a PR from a fork is sufficient to populate check metadata. However, I could not fully verify within the available context (1) whether `go-gh`'s `tableprinter.TablePrinter.AddField`/render pipeline (external dependency, not present in this repo's index) performs its own escaping/truncation that might neutralize raw ESC bytes before writing, and (2) the exact width-truncation/formatting behavior for non-TTY vs TTY paths, both of which could affect whether the byte sequence survives to the writer unmodified.

### Recommendation
Route `check` string fields (Name, Description, Link, Workflow, Event) through the same sanitization discipline used elsewhere (e.g., wrap in `iostreams.Untrusted` or run `asciisanitizer` on them before calling `tp.AddField`), or make `tableprinter.New` build on `ios.ContentOut` (or equivalent sanitizing writer) rather than `ios.Out` whenever the table may contain data sourced from a remote API rather than CLI-authored strings.

### Proof of Concept
```go
// pkg/cmd/pr/checks/output_test.go
func TestPrintTable_StripsOSC52(t *testing.T) {
    io, _, stdout, _ := iostreams.Test()
    io.SetStdoutTTY(false)

    checks := []check{
        {
            Name:        "job\x1b]52;c;bWFsaWNpb3Vz\x07",
            Description: "desc\x1b]52;c;bWFsaWNpb3Vz\x07",
            Link:        "https://example.com\x1b]52;c;bWFsaWNpb3Vz\x07",
            Bucket:      "pass",
        },
    }

    err := printTable(io, checks)
    require.NoError(t, err)

    assert.NotContains(t, stdout.String(), "\x1b]52", 
        "OSC 52 clipboard-write sequence must never reach the terminal")
}
```
Expected (per the invariant "OSC sequences are stripped from all remote text"): the assertion should pass after a fix; currently, given `printTable` uses `tableprinter.New(io, ...)` which writes through `io.Out` (not the sanitizing `io.ContentOut`), the raw OSC 52 bytes are expected to appear in `stdout.String()`, failing the assertion — pending confirmation of the exact `go-gh` `tableprinter` internals I could not inspect in this environment.

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
