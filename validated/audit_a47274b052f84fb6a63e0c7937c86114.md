### Title
`Shipit::Commit#create_status_from_github!` matches statuses by SHA across all stacks, causing `add_status`/`Hook.emit(:commit_status,...)` to fire with a victim stack's data - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/commit.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without scoping the lookup to the repository/stack that the inbound webhook actually belongs to. Because `sha` is not unique per repository (it is a git content hash, and Shipit tracks per-stack `Commit` rows), a status event delivered on behalf of one repository/stack can create a `Status` record on, and trigger `Hook.emit(:commit_status, stack:, commit:, status:)` for, an entirely different stack whose `Commit` row happens to share that sha.

### Finding Description
The broken binding: `commit.stack_id == webhook.repository.stacks.map(&:id)` is assumed but never checked — the actual code only enforces `commit.sha == params.sha`.

Path:
- `StatusHandler#process` iterates `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` for every match, with no filter on `stack_id`/`repository` derived from the webhook's own `repository` payload. [1](#0-0) 
- `Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, and `add_status` (defined in `commit.rb`) is responsible for emitting `Hook.emit(:commit_status, commit: self, stack:, status:)` (and, when the state is deployable/meaningful, `:deployable_status` too) once the new `Status` row is persisted. [2](#0-1) 
- `Status.replicate_from_github!` writes a new `Status` row scoped to `commit.stack_id` (i.e., the *victim's* stack, since that's the `stack_id` on the matched `Commit` row), not the attacker's stack. [3](#0-2) 

Root cause: a git commit sha is content-addressed and identical across any repositories that share that commit (forks, template repos, mirrors). Shipit models `Commit` per-stack (`belongs_to :stack`), so the same sha can legitimately exist as multiple distinct `Commit` rows, one per tracked stack. `StatusHandler` never narrows its `Commit.where(sha: ...)` query to only the stacks belonging to the webhook's own `repository`, so any stack tracking a commit with that sha gets a new status and a `Hook.emit` firing with that victim stack's `Commit`/`Stack` objects (message, author, repo name, target_url, etc., depending on what the Hook subscriber renders).

Existing guards that don't cover this: webhook signature verification (`verify_signature`) only proves the payload came from a repository Shipit trusts, it says nothing about which *stack* the resulting DB write should be scoped to; `ExplicitParameters` on `StatusHandler` only validates the shape of `sha`/`state`/etc., not repository ownership of the matched `Commit` rows; there is no stack/repository check inside `StatusHandler#process` or `Commit#create_status_from_github!`/`#add_status` before scanning by sha.

Exploit flow: attacker needs a stack they can trigger a legitimate, signature-valid `status` webhook for (e.g., their own repo/stack in this Shipit instance), and needs to learn a sha that also exists as a `Commit` row in a victim's stack (plausible when repos are forked from a shared public template, or share history through mirroring). They send/trigger a GitHub `status` event naming that sha; `StatusHandler` matches the victim's `Commit` row purely by sha and writes a `Status` + fires `Hook.emit` carrying the victim `stack`/`commit` objects to whatever Hook subscribers/webhooks are configured — which the attacker does not need to control, but which do render/exfiltrate the victim's `commit.message`, `stack.repo_name`, etc., to third parties depending on hook configuration.

### Impact Explanation
Two combined effects on the victim stack: (1) an unauthenticated write — a `Status` row is created against the victim's `Commit`, which can flip `commit.state`, run `enable_ci_on_stack`, and enqueue `ProcessMergeRequestsJob`/continuous-delivery jobs for the victim's stack; (2) an information leak — `Hook.emit(:commit_status, ...)` is dispatched carrying the full victim `Commit` and `Stack` objects to any configured Hook subscriber for that *victim* stack, which may render commit message, author, repo name, sha, etc. This is a cross-tenant mutation ("a payload for one repository mutating another's stack, commit") and also satisfies "unauthenticated read of stack state" via the Hook side channel. Repeatable against any stack sharing a discoverable sha with the attacker's own stack.

### Likelihood Explanation
Requires: (a) attacker controls or can trigger a valid, signature-verified `status` webhook event for some repository/stack tracked by the Shipit instance (e.g., their own repo added as a stack); (b) attacker can learn a sha that is also tracked as a `Commit` row in a victim stack — realistic when stacks are created from a shared public template repository, a common fork, or a mirrored upstream, since git shas are content-addressed and identical across such repos. No Shipit secrets, sessions, or API tokens are required beyond the ability to legitimately trigger their own repo's webhook. Feasibility is moderate-to-high in multi-tenant Shipit deployments where many stacks track forks/clones of the same upstream project.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and any other sha-based handler) to only the stacks belonging to the webhook's verified `repository`, e.g. `stack.repository.stacks` or equivalent, before calling `create_status_from_github!`. Additionally, `Commit#add_status`/`Hook.emit(:commit_status, ...)` should assert `commit.stack.repository == webhook_repository` (or the handler should only ever be handed commits already scoped to that repository) so a cross-repository sha collision cannot cause a write or Hook emission against an unrelated stack.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status event for repo A does not create a status or emit hooks for a commit in unrelated stack B sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)          # repo: "org/victim"
  attacker_stack = create_stack(repository_owner: "attacker", repository_name: "attacker-repo")

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "secret victim message", author: shipit_users(:shipit))
  # attacker's own stack also happens to have a Commit row with the same sha (fork/shared history)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker message", author: shipit_users(:walrus))

  Shipit::Hook.expects(:emit).never.with(:commit_status, victim_commit, stack: victim_stack, status: anything)

  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: "success", description: "d", context: "ci/x",
    created_at: Time.now.to_s
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(stack: attacker_stack, params:).process

  assert_equal 0, victim_commit.statuses.count   # binding: victim stack should be untouched
  assert_equal 1, attacker_commit.statuses.count
end
```
Expected (current code): the test fails — `victim_commit.statuses.count` is `1` and `Hook.emit` is called with `stack: victim_stack, commit: victim_commit`, because `StatusHandler#process` runs `Commit.where(sha: shared_sha)` unscoped by repository/stack.
