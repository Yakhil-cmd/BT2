### Title
Arbiter contract shared address grants unilateral authority to drain the entire address balance instead of only the escrowed contract amount - (File: arbiter_contract.js)

### Summary
`deriveSharedAddress()` in `arbiter_contract.js` builds the multi-signature definition for an arbiter-contract shared address using an `"has"` filter that only checks for the *existence* of one qualifying output, but never limits or sums the *total* funds that can be moved out of the address. Either counterparty can therefore spend the address's entire balance unilaterally as long as they include the single required payout output, taking any surplus funds for themselves — the same "authority beyond what is required" pattern flagged in the external report (unlimited allowance instead of a scoped one).

### Finding Description
The shared address definition built for each arbiter contract looks like this: [1](#0-0) 

For the non-private-asset branch, the authorization condition for each party is:
```
["and", [
  ["address", offeror_address],
  ["has", {what: "output", asset: ..., amount: <required_amount>, address: acceptor_address}]
]]
```
plus a `["not", ["has", {what: "input", ..., address: "other address"}]]` clause added later, intended only to stop two identical-term contracts sharing one address from being combined.

The `"has"` opcode (evaluated in `definition.js`, `evaluate()`/`validateAuthentifiers()` — see the `'has'`/`'sum'` cases around [2](#0-1)  and the filter validation in [3](#0-2) ) only asserts that *at least one* output/input matches the filter. It does not constrain:
- the number or amount of other outputs in the same unit,
- the total value of inputs consumed from the shared address in the same unit.

Consequently, once the offeror's (or acceptor's) signature condition and the single required "has output" condition are satisfied, the definition authorizes spending of *all* UTXOs currently sitting at the shared address, not merely the contract-escrowed amount. Any extra balance at that address (e.g., additional/mistaken deposits sent to the shared address by anyone, since it is a normal Obyte address anyone can pay into, or dust left after prior settlement) can be swept out as unconstrained "change" to the spender in the same transaction that satisfies the counterparty's required payout.

### Impact Explanation
This grants the acting party ("offeror" or "acceptor", each an unprivileged address controlled by an ordinary user in the deal) far more spending authority than what the arbiter-contract escrow logic intends — full control of the address balance instead of only the negotiated `contract.amount`. If the shared address ever holds more than the exact contracted amount, the party who moves first can unilaterally appropriate the surplus, causing unauthorized loss of funds for the counterparty (or for whoever funded the excess), with no requirement for arbiter intervention or the other signer's cooperation. This is a concrete unauthorized-spending / fund-loss scenario reachable by a normal contract participant.

### Likelihood Explanation
This is triggerable by ordinary transaction crafting from a party who is already an authorized signer of the shared address (offeror or acceptor) — no special privilege, hub/network position, or protocol compromise is needed. It only requires the shared address to hold more than the exact contract amount at settlement time, which can happen through accidental overpayment, reuse across contracts with identical terms/parties (the very scenario the existing `"not has input other address"` mitigation was added for but does not fully close for balance draining), or third-party deposits to the known address.

### Recommendation
Constrain the spending condition to the exact amount rather than mere existence of one output:
- Use `"amount_at_most"`/`"equals"` filters, or a `"sum"` condition bounding total input/output value from the shared address to `contract.amount` (plus fee tolerance), so a party cannot consume more than the escrowed sum in a single spend.
- Alternatively, require that the sum of all inputs from the shared address in the unit equals the sum of specified outputs (payout + defined arbstore cut only), eliminating any implicit unrestricted "change" capability.

### Proof of Concept
1. Two parties, A (offeror) and B (acceptor), agree on an arbiter contract for `contract.amount = X` bytes and derive the shared address via `deriveSharedAddress()`.
2. Someone (A, B, or an unrelated third party) sends additional bytes `Y` to the shared address beyond `X` (e.g., accidental double funding, or the address is reused for another identical-term contract).
3. A crafts a unit spending all UTXOs at the shared address (total `X+Y`), with one output of exactly `X` to B (satisfying `["has", {what:"output", amount:X, address:B}]`) and a second output of `Y` back to A as unconstrained change.
4. Definition evaluation in `definition.js` only checks that the required `"has"` output exists and that inputs aren't split across "other address"; it does not check that total spend equals `X`. The unit validates and A walks away with the extra `Y`, which B never authorized to be released.
