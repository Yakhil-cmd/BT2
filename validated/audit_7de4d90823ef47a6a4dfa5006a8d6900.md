### Title
Missing `src_coin` precondition check causes uncaught exception / node crash when validating a "transfer" input for a private, fixed-denomination asset - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` assumes that whenever it processes a `"transfer"` input that spends a *private, fixed‑denomination* asset, `objValidationState.src_coin` has already been pre‑populated by the private‑payment‑chain code path. When that precondition is not met, the function `throw`s a plain `Error` instead of returning a normal validation error through the callback chain, mirroring the CVE‑2016‑3137 pattern where a driver assumed a device always exposed both endpoint descriptors and dereferenced an unchecked structure, crashing the kernel. [1](#0-0) 

### Finding Description
`src_coin` is only ever assigned in the private‑payment‑chain validator (`indivisible_asset.js`), specifically inside `validatePrivatePayment()`'s `"transfer"` branch, right before it calls into `validation.validatePayment()`: [2](#0-1) 

That function is only reached through the dedicated private‑payment‑chain flow (`validateAndSavePrivatePaymentChain` → `validatePrivatePayment` → `validation.initPrivatePaymentValidationState` → `validation.validatePayment`). The *normal* joint‑validation flow that processes ordinary posted units (`validate()` → `validateMessages()` → `validateInlinePayload()` → case `"payment"` → `validatePayment()` → `validatePaymentInputsAndOutputs()`) never populates `objValidationState.src_coin`. [3](#0-2) 

Yet `validatePaymentInputsAndOutputs()` reaches the exact same `"transfer"` branch for *any* payment message that declares `asset` = a known private, fixed-denomination asset and supplies an input of `type` `"transfer"`. Nothing in the message/app‑level checks (`validateInlinePayload`, `case "payment"`) forces `payload_location` to be `"none"` (the convention used for hidden/private payments) before falling into this generic input‑validation routine — the asset's `is_private`/`fixed_denominations` flags are looked up from the already‑stable asset definition, not from how the current message chooses to disclose its payload. As a result, a single ordinarily‑posted (`payload_location: "inline"`) unit that references such an asset with a `"transfer"` input can drive execution into:

```
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");          // <-- unchecked precondition
    ...
``` [4](#0-3) 

Because `objValidationState.src_coin` was never set in this call path, the `throw Error("no src_coin")` fires. This is a synchronous JavaScript exception raised deep inside an `async.eachSeries` iteratee, not a normal `cb(errString)` validation rejection, so it is not caught by the surrounding `async.series`/`async.eachSeries` control flow used throughout `validate()`. It propagates as an uncaught exception. The process's global handler explicitly re-throws such exceptions to intentionally crash the process and avoid an inconsistent state: [5](#0-4) 

This is directly analogous to CVE-2016-3137: code assumes a companion data structure (interrupt‑in/out endpoints in the kernel driver; `src_coin` here) always exists once a related condition is true (device is a Cypress serial device; asset is private+fixed‑denomination), and dereferences/uses it without verifying its presence first, leading to a crash reachable from untrusted, attacker‑controlled input (a USB device; a posted DAG unit).

### Impact Explanation
Any node (full node, relay, hub, or light client performing local validation) that receives and validates a unit containing a payment message that spends any known private, fixed-denomination asset via a `"transfer"` input — sent as an ordinary inline unit rather than through the dedicated private‑payment‑chain protocol — will hit the unguarded `throw Error("no src_coin")`. Given the process‑wide `uncaughtException` handler deliberately crashes the process, this becomes a remotely triggerable denial-of-service: a single malformed unit posted by any unprivileged network participant can crash every node that attempts to validate/relay it, potentially halting confirmation of new units network‑wide until operators patch and filter the offending unit.

### Likelihood Explanation
Likelihood is limited by the precondition that a private, fixed-denomination asset must already exist and be known/stable on the network (an asset issuer must have defined `is_private: true, fixed_denominations: true` at some point, which is a normal, permitted asset configuration, not an operator-only path). Once such an asset exists, any unprivileged unit poster can reference it in a crafted transfer input inside a normal (non-chain) payment message, without needing any special privilege, keys, or cooperation from other parties — making exploitation straightforward for anyone able to construct and broadcast a unit.

### Recommendation
- In `validatePaymentInputsAndOutputs()` (`validation.js`), replace the `throw Error(...)` calls guarding `src_coin`/`src_output`/`denomination`/`amount` with normal callback-based validation errors (`return cb("no src_coin")`, etc.) so malformed/unexpected input is rejected gracefully instead of crashing the process.
- Additionally, explicitly reject (with a normal validation error) any `"payment"` message that references a private asset (`objAsset.is_private`) via `payload_location !== "none"` (i.e., disallow using the public/inline delivery path for private-asset payments) before reaching input/output validation, closing off this call path entirely.
- Audit other `throw Error(...)` statements inside the synchronous, per-input/per-message validation logic reachable from a single untrusted unit (e.g., other precondition checks in `validatePaymentInputsAndOutputs`) and convert them to callback errors as well, since any of them can similarly crash the process if reachable from attacker-controlled data.

### Proof of Concept
1. Have an asset issuer define (and get stabilized) an asset with `is_private: true, fixed_denominations: true` (a normal, supported asset configuration) — e.g. asset `A`.
2. Craft and broadcast an ordinary unit (not via the private‑payment‑chain protocol) containing a `"payment"` message with `payload_location: "inline"` whose payload references `asset: A` and includes an input of `{"type": undefined-equivalent (transfer), "unit": ..., "message_index": ..., "output_index": ...}` (a `"transfer"` input) pointing at any output.
3. Submit this unit to a node for validation via the normal joint-validation path (`validate()` → `validateMessages` → `validateInlinePayload` → `"payment"` → `validatePayment` → `validatePaymentInputsAndOutputs`).
4. Because this path never initializes `objValidationState.src_coin` (only `indivisible_asset.js`'s private-chain validator does), execution reaches `if (objAsset && objAsset.is_private && objAsset.fixed_denominations){ if (!objValidationState.src_coin) throw Error("no src_coin"); ... }` and throws synchronously.
5. The thrown error is not caught by the surrounding `async` control flow, becomes an uncaught exception, and network.js's handler re-throws it, crashing the node process — a working denial-of-service.

Note: I was not able to execute this against a running node in this environment to empirically confirm the exception is truly uncaught end-to-end (versus being caught by some intermediate try/catch I did not locate in the traversed call chain); this should be verified by a background agent with test/runtime access before relying on it as a confirmed crash, but the code path and unguarded `throw` are confirmed by direct reading of `validation.js` and `indivisible_asset.js`.
