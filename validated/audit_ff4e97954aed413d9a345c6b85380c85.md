### Title
Cross-tenant commit status mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone with no repository or stack filter, then calls `create_status_from_github!` on every match. Because `sha` is not unique across the `commits` table (it is only unique per `stack_id`, if constrained at all), a signed webhook from repository A can write `Status` rows onto `Commit` records that belong to unrelated stacks tracking a different repository B, as long as both happen to share a commit SHA.

### Finding Description
The broken binding is: `repository named in payload == repository of every Commit row mutated by params.sha`. This holds for the first matching row but is not enforced for any additional rows.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query has no `stack_id`, `repository_id`, or join to `Stack`/`Repository` at all — it is a global lookup across the entire `commits` table. Contrast this with the base `Handler` class, which already provides a `stacks` helper precisely for this purpose, scoping by the payload's `repository.full_name` via `Repository.from_github_repo_name(repository_name)&.stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Other handlers (e.g. pull-request handlers) use this `stacks` scoping pattern to bind the payload's repository to the correct records, but `StatusHandler` does not — it queries `Commit` directly and unconditionally iterates every match.

`Commit#create_status_from_github!` unconditionally writes a new `Status` and recomputes commit/stack state:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [3](#0-2) 
`add_status` reloads status, emits `commit_status`/`deployable_status` hooks, and can trigger `stack.schedule_merges` for **each** matched stack: [4](#0-3) 

Existing guards do not stop this: `verify_signature` in `WebhooksController` only checks that the payload is signed by the GitHub org named in the payload's own `repository.owner.login` — it authenticates that the *sender* is that org/repo, not that the SHA belongs only to that repo's commits: [5](#0-4)  The `ExplicitParameters` schema in `StatusHandler` only validates types of `sha`/`state`/etc., not ownership: [6](#0-5)  None of these checks constrain which `Commit` rows get mutated once the handler runs.

**Attack**: Attacker controls repository A (owns it or has push access, can trigger any status webhook on it, e.g. via CI integration on their own fork/repo). If a `Commit` with the same `sha` exists under an unrelated `Stack`/repository B in the same Shipit instance (plausible for early/initial commits, trivial squash commits, or cherry-picked shared history), a signed `status` webhook from repo A causes `StatusHandler` to also create a `Status` on repo B's commit, mutating B's stack state (potentially triggering `schedule_merges`/continuous delivery evaluation for a stack the attacker never had access to).

### Impact Explanation
A single validly-signed webhook for repository A writes `Status` rows and can perturb deployability/merge scheduling for commits belonging to any other stack in the instance that happens to store a `Commit` with the same SHA — a payload for one repository mutating another's stack/commit state, matching the Critical impact category ("payload for one repository mutating another's stack, commit, task or team"). This is repeatable per request and scales with the number of tenants/stacks sharing the instance; the more Shipit is used as a shared multi-tenant CI/CD hub, the larger the blast radius.

### Likelihood Explanation
Requires: (1) attacker controls or can trigger status webhooks for at least one repository registered in the Shipit instance (a low bar — any repo owner/CI integrator), and (2) SHA collision with a `Commit` row in an unrelated stack. SHA collisions are not attacker-forced (SHA-1 collision is not the vector) but arise naturally from shared history (identical initial commits, cherry-picks, shared templates, monorepo splits) — a realistic, if not universal, precondition in real deployments with many stacks. No secrets or elevated privileges are needed beyond ordinary webhook delivery for one owned repository.

### Recommendation
Scope the commit lookup in `StatusHandler#process` by the payload's repository, using the same `stacks` helper already available on `Handler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so only commits belonging to stacks tracking the payload's repository can be mutated.

### Proof of Concept
minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, out of scope to author but described for the fix's verification):
1. Create `stack_a` for repo `owner/repo-a` and `stack_b` for repo `owner/repo-b`.
2. Create `commit_a = Commit.create!(stack: stack_a, sha: "deadbeef"*5)` and `commit_b = Commit.create!(stack: stack_b, sha: commit_a.sha)`.
3. Build a signed `status` payload with `repository.full_name = "owner/repo-a"`, `sha: commit_a.sha`, `state: "success"`.
4. POST to `/webhooks` with valid `X-Hub-Signature` for repo-a.
5. Assert `commit_a.statuses.reload.any? { |s| s.state == "success" }` is true (expected, in-scope).
6. Assert `commit_b.statuses.reload` is **empty** (expected after fix) — currently, before the fix, this assertion fails because `commit_b` also gains a `success` `Status`, proving the cross-tenant write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
