### Title
Malicious commit content (broken/dangling submodule reference) on the tracked ref causes persistent, unrecoverable sync failure in `repoSync.SyncRepo` - (File: `main.go`)

### Summary
`git-sync` fetches whatever content is currently pushed to the tracked `--ref` (branch/tag) and, on every sync pass, unconditionally runs `git submodule update --init [--recursive]` against that content via `configureWorktree` [1](#0-0) . Because submodule handling is on by default (`--submodules=recursive`) [2](#0-1) , any committer with push access to the tracked repository (untrusted repo content, not a git-sync operator) can push a commit whose `.gitmodules`/gitlink entries are deliberately broken (e.g. a submodule commit hash that does not exist on the submodule remote, or a submodule URL that is unreachable/requires interactive auth). This is the same bug class as H-14: a piece of attacker-controlled data that is deterministically un-processable, causing the "bulk" synchronization operation to fail every single time it is retried with the same input.

### Finding Description
`SyncRepo` fetches the ref, computes `remoteHash`, and if that hash differs from what is already synced, creates a worktree and calls `configureWorktree` [3](#0-2) . `configureWorktree` performs `reset --hard` to the new commit and then unconditionally runs `git submodule update --init` (optionally `--recursive`) [4](#0-3) . Neither of these steps validates that the referenced submodule commits are actually resolvable before attempting the update, and there is no per-commit skip/quarantine logic for known-bad hashes.

Because `remoteHash` is derived directly from `FETCH_HEAD^{}` of the branch/tag being tracked [5](#0-4) , once a malicious/broken commit becomes the tip of the tracked ref, `remoteHash` stays fixed at that same broken value on every subsequent sync loop iteration until a new commit is pushed. Every iteration therefore repeats the exact same failing sequence: fetch (succeeds, cheap) → `configureWorktree` → `git submodule update --init` fails deterministically on the same dangling gitlink → `SyncRepo` returns an error [6](#0-5) . This mirrors `InsertBulkReputerPayload`'s failure mode: the same "payload" (commit hash) will forever fail identically, and there is no way for the operator to make progress on that ref without out-of-band intervention (force-pushing a fix), since git-sync itself has no mechanism to skip or roll back to a last-known-good ancestor.

### Impact Explanation
The consuming application never receives newer content for the affected ref — the symlink (`--link`) is never advanced past the last good commit because `publishSymlink` is only reached after `configureWorktree` succeeds [7](#0-6) . Repeated failures increment `failCount`; if `--max-failures`/`GITSYNC_MAX_FAILURES` is set (or its default of 0), the process can exit entirely [8](#0-7) , turning a data-availability DoS into a container crash-loop for the whole sidecar. This is a **persistent sync denial** — an explicitly accepted impact category — triggered purely by content an untrusted committer pushed to the tracked repository, with no privileged access to the git-sync deployment itself required.

### Likelihood Explanation
Any contributor with write/push access to the tracked repository (a common trust boundary in monorepos, forks-with-merge workflows, or multi-tenant Git hosting) can trigger this by adding/modifying a `.gitmodules` entry pointing to a private/unreachable/garbage-commit submodule and pushing it to the tracked branch. No special git-sync flags beyond the default `--submodules=recursive` are required, and no cooperation from the git-sync operator is needed. This is a low-effort, high-certainty attack once repo write access is available.

### Recommendation
- Make submodule failures non-fatal for the overall sync (log and skip only the affected submodule, or fall back to leaving the previous good worktree published) instead of aborting the whole `SyncRepo` pass.
- Add a `--submodules-timeout`/bounded-retry so `git submodule update` cannot indefinitely block progress on a single bad ref.
- Allow the operator to configure a policy to "pin to last-known-good hash" and alert, rather than silently retrying an unrecoverable commit forever.
- Document this failure mode clearly so operators tracking untrusted branches understand the risk and can gate merges with CI checks that run `git submodule update --init --recursive` before allowing a push.

### Proof of Concept
1. In the upstream repo tracked by git-sync, add a submodule entry in `.gitmodules` pointing to a real, reachable submodule remote.
2. Commit a gitlink (submodule pointer) that references a commit SHA that does **not** exist in that submodule's remote (or point the submodule URL at a host that requires interactive credentials git-sync does not have).
3. Push this commit to the branch/tag that git-sync's `--ref` tracks.
4. Observe git-sync's sync loop: each iteration successfully fetches the new `remoteHash` [9](#0-8) , but `configureWorktree`'s `git submodule update --init --recursive` step fails every time with the same error (submodule commit not found / auth failure) [1](#0-0) , and `SyncRepo` returns an error on every pass [6](#0-5) .
5. The published symlink never advances past the last good commit, and (depending on `--max-failures`) the process eventually exits, reproducing a persistent, self-inflicted sync denial from a single malicious push.
