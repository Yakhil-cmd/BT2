**Rationale:** CVE-2017-11190 is a stack-based buffer overflow in `unrarlib.c`'s C debug-logging code path, triggered by an unbounded `strcpy`-style copy of an attacker-controlled RAR filename into a fixed-size stack buffer when `_DEBUG_LOG` is compiled in. This is a memory-unsafety bug class specific to unsafe C string handling that has no analog in `polkadot-sdk`:

- There is no `unrar`/RAR-parsing dependency anywhere in the repository [1](#0-0) .
- The codebase is written in Rust, where stack buffers are bounds-checked; the debug-message/logging paths I inspected (e.g. `debug_message` host function and `append_debug_buffer` in pallet-contracts) explicitly bound the copied length against a configured buffer bound before any copy occurs, rather than performing an unchecked fixed-size stack copy of attacker-supplied data [2](#0-1) [3](#0-2) .
- Similarly, sandbox memory reads (`read_sandbox_memory_into_buf` / PVM `Memory::read_into_buf`) perform explicit bounds checks against the destination buffer/memory region before copying, precluding the "long unchecked name copied into fixed buffer" pattern described in the CVE [4](#0-3) [5](#0-4) .

There is no real user-reachable entry point (extrinsic, contract call, or XCM message) in this codebase that parses RAR-style archives or performs unchecked fixed-size stack buffer copies of attacker-controlled variable-length data gated behind a debug flag. The vulnerability class (unsafe C stack buffer overflow in a debug logging feature) does not map onto any FRAME/XCM/contracts invariant present in this Rust codebase.
