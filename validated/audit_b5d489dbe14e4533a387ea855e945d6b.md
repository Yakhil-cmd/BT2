### Title
Autobinding of attacker-controlled `status` field into `prosaic_contracts` via unvalidated device message - (File: `wallet.js`, `prosaic_contract.js`)

### Summary
The `prosaic_contract_shared` device-message handler in `wallet.js` forwards the entire untrusted `body` object it receives from a paired device straight into `prosaic_contract.store(body)` without whitelisting or validating the `status` field, unlike the sibling `prosaic_contract_offer` handler which explicitly rejects a caller-supplied `status`. This mirrors the MITREid Connect autobinding bug: request-controlled fields are bound onto a security-relevant domain object without a field whitelist, letting the sender set state that should only be reachable through the application's own state machine.

### Finding Description
`wallet.js`'s `prosaic_contract_offer` case explicitly guards against the offer creator injecting a `status`: [1](#0-0) 

But the `prosaic_contract_shared` case — reachable from any paired device that is a cosigner on the wallet — performs no such check before calling `store(body)`: [2](#0-1) 

`prosaic_contract.store()` then autobinds `objContract.status` directly, defaulting only when the field is absent: [3](#0-2) 

Compare this to the code path that is supposed to be the sole gate for status changes, `prosaic_contract_update`, which enforces an explicit state machine (`status` may only move from `"pending"` to `"revoked"`, etc.) and restricts the mutable field set via `setField`'s hardcoded whitelist: [4](#0-3) [5](#0-4) 

By sending a crafted `prosaic_contract_shared` message with `status: "accepted"` (or any other value, since there is no enum validation at insert time either), a malicious/compromised paired device can seed the local `prosaic_contracts` row with an attacker-chosen status, bypassing the offeror's genuine acceptance step and the transition checks that normally gate it.

The arbiter-contract analog has a narrower version of the same pattern: `arbiter_contract_shared` also omits a `status` check before calling `arbiter_contract.store(body, true)`, and `store()` explicitly documents the trust assumption ("contracts shared by cosigners are trusted to reflect their true status") without further validating the value: [6](#0-5) [7](#0-6) 

### Impact Explanation
Downstream logic keys off `objContract.status` to decide whether further protocol steps are permitted — e.g., `prosaic_contract_update`'s `"unit"` and `"shared_address"` branches only proceed `if (objContract.status !== "accepted")` fails. If a paired cosigner device can plant `status: "accepted"` via the unguarded `prosaic_contract_shared` path, it can drive the local wallet into believing a contract was mutually accepted when it was not, unlocking the subsequent steps (`shared_address` recording, signing-unit acceptance) that are otherwise conditioned on genuine acceptance. This is a private-payment/contract counterparty flow, and forcing an unearned "accepted" state can lead the victim wallet to proceed toward composing/signing a payment for a contract it never actually accepted.

### Likelihood Explanation
The trigger is a single crafted `justsaying`/device message (`prosaic_contract_shared`) sent by any device already correspondent/cosigner with the target wallet — no special network position or node compromise is required, and it fits the allowed "paired device" actor. The missing check is a straightforward field-whitelisting omission, directly comparable in kind (though narrower in blast radius) to the CVE-2021-27582 autobinding root cause.

### Recommendation
Reject or ignore any attacker-supplied `status` (and any other lifecycle-controlling field) in `prosaic_contract_shared` and `arbiter_contract_shared`, mirroring the explicit rejection already implemented in `prosaic_contract_offer`/`arbiter_contract_offer`. Route all status transitions exclusively through the validated state-machine handlers (`prosaic_contract_update`/`arbiter_contract_update`), and have `store()` always default new contracts to `status_PENDING` regardless of caller input, with lifecycle changes only permitted via `setField`'s controlled transition logic.

### Proof of Concept
1. Attacker device pairs with / becomes a cosigner correspondent of the victim wallet (a normal, low-privilege relationship already supported by the protocol).
2. Attacker sends a `justsaying` message of subject `prosaic_contract_shared` with a valid `title`, `text`, `creation_date`, matching `hash` (computed via `prosaic_contract.getHash`), valid `peer_address`/`my_address`, and an added field `status: "accepted"`.
3. `wallet.js`'s handler validates only title/text/creation_date/addresses/hash/date-format/cosigner-membership — it never inspects or strips `status` — and calls `prosaic_contract.store(body)`. [8](#0-7) 
4. `store()` inserts the row with `objContract.status || status_PENDING`, i.e., the attacker-chosen `"accepted"` value, into `prosaic_contracts`. [9](#0-8) 
5. A subsequent `prosaic_contract_update` message with `field: "unit"` or `field: "shared_address"` from the attacker now passes the `objContract.status !== "accepted"` guard that was meant to require the offeror's real acceptance, letting the attacker push a `shared_address`/signing unit into the flow prematurely.

Note: I was not able to trace every downstream UI/consumer of `prosaic_contracts.status` (e.g., whether the wallet's local UI/API blocks signing on unaccepted contracts elsewhere) in the indexed subset of the codebase, so the exact severity of the resulting fund-loss/spend risk could not be fully confirmed end-to-end; a Devin session with full repository access would be needed to trace all consumers of `status` to establish complete exploit impact.
