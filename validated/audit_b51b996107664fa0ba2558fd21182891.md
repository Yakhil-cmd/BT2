### Title
Cross-organization team membership injection via unauthenticated `membership` webhook binding mismatch - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up/creates a `Team` solely by `params.team.id`, with no verification that the organization whose `webhook_secret` authenticated the request actually owns that team. Combined with `WebhooksController#verify_signature` selecting the signing organization purely from the same attacker-supplied `organization.login`, an attacker who can get any HMAC check to pass for *some* org (trivially true when that org has no `webhook_secret` configured, since `GitHubApp#verify_webhook_signature` returns `true` unconditionally in that case) can add an arbitrary GitHub login as a member of a completely different, victim organization's real team.

### Finding Description
The broken binding: `organization-that-signed-the-payload == organization-that-owns-the-Team-row-being-mutated` is never checked, even though it is implicitly assumed safe.

Path:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) resolves `Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) falls back to `params.dig('organization','login')` for events without a `repository` key — exactly the `membership` event.
2. `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) returns `true` unconditionally `unless webhook_secret` is configured for that org. So a `membership` payload whose `organization.login` names any Shipit-configured org with no configured `webhook_secret` (or a weak/known one) passes signature verification without the attacker knowing any genuine Shipit/GitHub secret.
3. Once the request is accepted, `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34) calls `find_or_create_team!` (lines 38-43), which does `Team.find_or_create_by!(github_id: params.team.id)`. If a `Team` row already exists with that `github_id` (created earlier through legitimate sync, e.g. `Shipit.github_teams` / `Team.find_or_create_by_handle` → `fetch_and_create_from_github`, app/models/shipit/team.rb:17-27), the block is skipped and the existing record — with its real `organization`/`slug` belonging to the victim — is returned unchanged.
4. `process` then unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))` (membership_handler.rb:24,28), adding the attacker-named GitHub login as a member of that victim team, with no cross-check that `params.organization.login` matches `team.organization`.

Existing guards do not close this gap: `drop_unhandled_event` and `check_if_ping` only gate on event type; `ExplicitParameters` schema only validates types/presence, not cross-field/org consistency; there is no `require_permission!` or org-ownership check anywhere in `MembershipHandler`.

Attacker request: POST `/webhooks` with header `X-Github-Event: membership`, a signature computed (or omitted/mismatched, if permitted) against an org with no `webhook_secret`, and JSON body:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "x"},
  "organization": {"login": "<attacker-or-unsecured-org>"},
  "member": {"login": "<attacker-github-login>"}
}
```

### Impact Explanation
The attacker gains membership in a `Team` row that backs `Shipit.github_teams` (lib/shipit.rb:256-258), which is used for authorization decisions elsewhere in the app. This is a direct escalation into `Shipit.github_teams` authorization for a GitHub login the attacker fully controls, achieved purely by forging a webhook body — matching the "High" impact category (escalation into `Shipit.github_teams` authorization). The attack is repeatable against any victim team whose numeric `github_id` the attacker can determine, and is not scoped to any one tenant — it crosses organization boundaries because the code path never checks organization ownership of the `Team` record being mutated.

### Likelihood Explanation
Preconditions: (a) at least one organization configured in Shipit's GitHub app config lacks a `webhook_secret` (or the attacker otherwise controls an org whose HMAC check they can satisfy) — this makes `verify_webhook_signature` return `true` unconditionally, requiring no genuine secret; (b) the attacker must know or guess the victim team's numeric GitHub `team.id`, which is derivable from GitHub's own API/UI in many configurations. No Shipit session, API token, or GitHub App private key is needed. Given a webhook-secret-less/misconfigured org exists, exploitation is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the resolved signing organization (`repository_owner`/the org key used in `verify_signature`) before mutating or creating any `Team`, and reject/no-op when an existing `Team` for `github_id` has a different `organization`. Additionally, `GitHubApp#verify_webhook_signature` should not silently accept unsigned/any-signature payloads when `webhook_secret` is blank — require an explicit "verification intentionally disabled" configuration rather than defaulting to `true`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual)
test "membership webhook cannot add attacker-controlled member to a victim org's team" do
  victim_team = shipit_teams(:victim_team) # organization: "victim-org", github_id: 555

  # Precondition: an org configured with no webhook_secret (or attacker's own weak-secret org)
  # e.g. Shipit.github(organization: 'attacker-org').webhook_secret is nil

  post shipit.github_webhooks_path,
    params: {
      action: 'added',
      team: { id: victim_team.github_id, name: 't', slug: 't', url: 'http://x' },
      organization: { login: 'attacker-org' },
      member: { login: 'attacker_login' }
    }.to_json,
    headers: { 'X-Github-Event' => 'membership', 'Content-Type' => 'application/json' }
    # no valid signature for victim-org's secret provided/needed

  attacker = Shipit::User.find_by(login: 'attacker_login')

  # Binding check (should hold, currently violated):
  assert_equal 'victim-org', victim_team.reload.organization
  refute_includes victim_team.members, attacker,
    "attacker-controlled login must not be added to victim-org's team via a payload authenticated under a different org"
end
```
