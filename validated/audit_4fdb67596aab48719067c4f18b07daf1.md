### Title
Cross-repository forged `deployable_status` via unscoped `StatusHandler#process` commit lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `Commit.where(sha: params.sha)` with no constraint tying the lookup to the repository/organization that signed the inbound webhook [1](#0-0) . Because any GitHub commit with an identical SHA (e.g., identical content pushed into an attacker-controlled fork/mirror repo) satisfies that query, an attacker who owns an org/repo with the Shipit GitHub App installed can send a validly-signed `status` webhook for their own repo that writes a `Status` row onto a `Commit` belonging to an entirely different stack. If that victim commit is not yet deployed, `Commit#add_status` will fire `Hook.emit(:deployable_status, stack, ...)` with the forged state [2](#0-1) .

### Finding Description
Claimed binding: `payload[:stack].repository == webhook.repository` (the stack/commit the hook fires for must belong to the same repository/org that authenticated the webhook). Actual code: `StatusHandler#process` does:
```
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [1](#0-0) 
This is a global, unscoped lookup across all stacks/repositories in the Shipit install — there is no join/filter on `stack.repository`, `repository_owner`, or any organization identifier from the payload. `WebhooksController#verify_signature` only checks that the raw payload is validly signed by the GitHub App belonging to `repository_owner` (the org named in the payload's own `repository`/`organization` object) [3](#0-2) ; it does **not** verify that the `sha` referenced in the payload actually belongs to a commit that was pushed to that same `repository_owner`'s repo in Shipit. Once signature verification passes for the attacker's own org, `StatusHandler` is free to mutate any `Commit` row anywhere in the database that shares that SHA.

`Commit#add_status` then computes `already_deployed = deployed?` and, `unless already_deployed`, fires `Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))` whenever `previous_status.simple_state != new_status.simple_state` and the new status is non-pending (or previous was unknown) [2](#0-1) . This exact `unless already_deployed` guard means the bug is inherently self-selecting for the highest-value targets: undeployed commits awaiting a deploy decision, exactly as the question hypothesizes; already-deployed commits are silently excluded (confirmed by test "`#add_status does not fire webhooks for already deployed commits`" [4](#0-3) ).

Attack flow:
1. Attacker creates/owns a GitHub org/repo and installs the Shipit GitHub App on it (this is something an ordinary, unprivileged GitHub user can do for their own repo — it does not require any Shipit secret).
2. Attacker engineers a commit whose SHA collides with a victim's tracked, undeployed commit — most practically by getting byte-identical content merged into their own fork/mirror of the same upstream history the victim stack tracks (forks naturally share identical commit SHAs for shared history).
3. Attacker pushes a real commit status (`success`) to their own repo/commit via the GitHub API on their own repository. GitHub sends a `status` webhook to Shipit signed with the attacker's own org's legitimate app secret.
4. `WebhooksController#verify_signature` validates the signature against `repository_owner` = attacker's org — this passes because it is genuinely signed.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which also matches the victim's `Commit` row (same SHA, different `stack_id`/repository).
6. `commit.create_status_from_github!(params)` creates the forged `success` status on the victim's commit, and `add_status` fires `Hook.emit(:deployable_status, victim_stack, ... deployable_status: Status::Success)`.
7. Any downstream `Hook` (e.g., Slack notification integration configured for `deployable_status`) delivers a "ready to deploy" / passing-CI announcement for the victim repository, even though the victim's actual CI provider never reported success.

None of the existing guards catch this: `verify_signature` authenticates the org, not the SHA-to-repository binding; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` only validates types (`sha`/`state`/etc.), not repository ownership [5](#0-4) ; and `Commit#add_status`'s `already_deployed` check protects deployed commits but does nothing to protect undeployed ones from cross-repo writes.

### Impact Explanation
The attacker can cause a `Status`/`deployable_status` record to be written for a repository/stack that never authenticated or authorized the write, and can trigger any downstream automation bound to `deployable_status` (Slack notifications, auto-merge/auto-deploy triggers via `stack.schedule_merges`) with a forged `success` signal for a victim's undeployed, high-value commit [6](#0-5) . This matches the "payload for one repository mutating another's stack, commit ... task or team" and "unauthorized deploy" Critical categories: `stack.schedule_merges if new_status.pending? || new_status.success?` can advance merge-queue automation for the victim stack based on the forged status. This is repeatable against any stack whose tracked repository shares commit history (forks/mirrors) with a repository the attacker controls, and the blast radius spans every stack in the Shipit instance sharing that SHA, i.e., cross-tenant.

### Likelihood Explanation
Preconditions: the attacker needs (a) an org/repo where they can install the Shipit GitHub App (feasible for any GitHub user who owns a repo/org and whose org is permitted to install the app — this is a normal, unprivileged GitHub action, not a Shipit secret), and (b) a commit SHA collision with the victim's tracked commit. Practically, (b) is easiest when the victim stack tracks a repository that has public forks/mirrors, or when an attacker can get identical content merged upstream and then mirror it into their own repo before the victim's commit is deployed — a realistic scenario for open-source or monorepo-fork workflows, not a cryptographic SHA1 collision. Cost to the attacker is low (no secrets, no privileged role, uses only their own repo/webhook), and the attack is repeatable per matching commit.

### Recommendation
Scope `StatusHandler#process`'s commit lookup to the repository that authenticated the webhook, e.g., join through `stack.repository_owner`/`stack.repository_name` derived from the payload's `repository` object, or store/validate the stack's `Repository` association against the webhook's own `repository_owner`/`repository` fields before calling `create_status_from_github!`. Never call `Commit.where(sha: ...)` unscoped by repository when processing untrusted webhook input.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "cross-repo status webhook forges deployable_status for a victim stack with colliding sha" do
  victim_stack = shipit_stacks(:shipit)          # tracks "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef", ...)
  refute_predicate victim_commit, :deployed?

  attacker_stack = shipit_stacks(:cyclimse)      # tracks a different org/repo
  attacker_stack.commits.create!(sha: "deadbeef", ...) # same sha, different repository

  params = ExplicitParameters unwrap or OpenStruct.new(
    sha: "deadbeef", state: "success", context: "attacker/ci", created_at: Time.now.to_s
  )

  Hook.expects(:emit).with(:deployable_status, victim_stack, has_entry(deployable_status: instance_of(Shipit::Status::Success)))

  Shipit::Webhooks::Handlers::StatusHandler.new.process # invoked with attacker-signed payload for attacker's own org
end
```
Both sides of the binding: `payload[:stack]` returned to `Hook.emit` is `victim_stack` (repository "shopify/shipit-engine") while the authenticating webhook's `repository_owner`/org is the attacker's own repository — they are not equal, confirming the binding is broken, and demonstrating `StatusHandler#process`'s `Commit.where(sha: params.sha)` at app/models/shipit/webhooks/handlers/status_handler.rb:21 crosses repository boundaries.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
