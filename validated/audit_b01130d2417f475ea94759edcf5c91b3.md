### Title
Cross-repository commit-status spoofing enables unauthorized deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the *organization* derived from the payload (`repository.owner.login`), using that organization's `webhook_secret`. It never verifies that the `repository` referenced by the event body is the one actually bound to the commit/stack the handler mutates. `Handlers::StatusHandler#process` looks up commits purely by `sha`, with no repository/stack scoping at all, and writes an attacker-controlled GitHub commit status onto every matching `Commit` record. This breaks the intended binding: **organization that authenticated == repository that is written**.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` computes `repository_owner` from the payload and asks `Shipit.github(organization: repository_owner)` for the correct app config to verify the HMAC signature: [1](#0-0) 

Once the signature is accepted, the raw JSON is dispatched unmodified to the registered handler for the event, with no additional binding between the "verified" organization and any specific repository or stack: [2](#0-1) 

For the `status` event, `StatusHandler#process` looks up commits globally by SHA across the **entire database**, with zero filtering by repository, stack, or organization: [3](#0-2) 

Compare this to other handlers such as `PushHandler` and `MembershipHandler`, which correctly scope their side effects to a `Repository`/`stack` resolved from `repository.full_name`: [4](#0-3) [5](#0-4) 

`StatusHandler` is the exception: any payload passing signature verification for *some* organization can create a `Status` record on a `Commit` belonging to a completely different stack/repository/organization, because `Commit.where(sha: params.sha)` matches purely on the SHA string: [6](#0-5) 

That status record directly feeds into deploy-gating logic — `Commit#deployable?` and `Commit#status` — which many teams rely on to require passing CI before deploying: [7](#0-6) [8](#0-7) 

**Attack path (equality broken):**
`organization authenticated by verify_signature (repository.owner.login of the webhook sender's own repo)` ≠ `repository/stack whose Commit row gets mutated (looked up solely by sha, unrelated to the authenticated org)`.

An attacker who has push/status-write access to **any** GitHub repository tracked by the same Shipit instance (even an unrelated, low-value sandbox repo in an org that shares a GitHub App/webhook secret, or their own throwaway repo in an org with an App installed) can:
1. Use the GitHub Statuses API (`POST /repos/:owner/:repo/statuses/:sha`) on their own repo to set an arbitrary `state`/`context`/`description` for any commit SHA — including a SHA that exists in a target, higher-value stack (git SHAs are content-addressed; identical commits — e.g. via forks of a public target repo or coincidentally shared history — carry across repositories).
2. GitHub delivers this event to Shipit's `/webhooks` endpoint, correctly signed with the attacker's own (legitimately obtained) org webhook secret.
3. `verify_signature` validates the signature against the attacker's own organization — which succeeds, because it never checks that `repository.full_name` matches an authorized repository for that organization.
4. `StatusHandler` finds the target stack's `Commit` row purely by SHA and writes the forged "success" status onto it, satisfying `Commit#deployable?`/CI-required gating for the target stack.
5. A subsequent deploy (manual or continuous-deployment) on the target stack proceeds even though the real CI never passed on the real commit, i.e., an **unauthorized deploy**.

### Impact Explanation
This matches the Critical-tier impact defined in scope: "an unauthorized deploy, rollback or merge." Forged CI-success statuses bypass Shipit's core safety gate (`ci.require` / blocking statuses / `Commit#deployable?`), allowing an attacker outside the target stack's trust boundary to make Shipit believe an arbitrary commit has passed CI, enabling deployment of code that was never validated (or was never even the intended commit) into production for a repository/organization the attacker has no legitimate authority over.

### Likelihood Explanation
The webhook signature only binds to "some organization the attacker has enough access to trigger a webhook from" — not to the specific repository the payload claims to describe. No `ApiClient`, Shipit session, or GitHub App private key is required; only ordinary repository-level GitHub permissions (ability to set commit statuses on a repo, which is common for CI bots, external contributors with fork-based workflows, or org members) are needed. The main practical constraint is producing a colliding/matching SHA, which is realistic for forked public repositories or shared commit history, making this a credible occurrence in multi-repo/multi-org Shipit deployments.

### Recommendation
In `StatusHandler#process` (and any other handler that mutates commit/stack state), scope the lookup to the stack(s) belonging to the repository identified in the payload (`payload.dig('repository','full_name')`), analogous to `Handler#stacks`, instead of a global `Commit.where(sha: ...)`. Additionally, `WebhooksController#verify_signature` should validate that the authenticated organization actually matches/owns the repository referenced in the event body before any handler runs, closing the gap between "organization whose secret verified the signature" and "repository/stack that gets written."

### Proof of Concept
1. Attacker has legitimate access to set commit statuses on `attacker-org/sandbox-repo`, which is tracked by the same Shipit instance (any low-privilege stack) and whose organization has a valid `webhook_secret`.
2. Attacker identifies a commit `SHA` in a high-value stack `victim-org/critical-repo` (e.g., via a public fork sharing history, or by pushing an identical commit—same tree/parents/author/committer timestamps—to their own repo, producing the same SHA-1).
3. Attacker calls `POST https://api.github.com/repos/attacker-org/sandbox-repo/statuses/<SHA>` with `{"state":"success","context":"ci/required-check"}`.
4. GitHub sends a `status` webhook to Shipit's `/webhooks`, signed with `attacker-org`'s webhook secret.
5. `verify_signature` succeeds (valid signature for `attacker-org`).
6. `StatusHandler#process` executes `Commit.where(sha: SHA)`, which matches the commit row in `victim-org/critical-repo`'s stack, and writes the forged "success" status onto it via `commit.create_status_from_github!`.
7. `victim-org/critical-repo`'s stack now reports the commit as `deployable?` for CI purposes, enabling an unauthorized deploy.
