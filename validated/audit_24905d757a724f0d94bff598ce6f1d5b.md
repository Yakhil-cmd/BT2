## Summary

The strongest local analog to the Lens “stored data ≠ approved/emitted data” bug class is in Aptos's **multisig transaction admission path**: `validate_multisig_transaction` in `multisig_account.move`, which is invoked from the VM prologue via `run_multisig_prologue` in `transaction_validation.rs`.

### Title
Multisig full-payload mismatch check is feature-gated, allowing an approved transaction to execute with an unapproved payload - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Finding Description
`validate_multisig_transaction` runs as the VM prologue for `MultisigTransaction` execution and is the admission gate that decides whether the caller-provided payload is allowed to execute against the approvals recorded on-chain [1](#0-0) .

There are two different storage modes for a proposed multisig transaction:
- **Hash-only mode** (`create_transaction_with_hash`): only a `payload_hash` is stored, and the provided payload at execution time is *unconditionally* checked against that hash [2](#0-1) .
- **Full-payload mode** (`create_transaction`): the entire payload is stored on-chain, but the comparison between the stored payload and the payload actually supplied for execution is only performed **if the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on** [3](#0-2) .

This means that when a multisig transaction is created with the full payload stored on-chain (the common/default flow used by most tooling), and the mismatch-abort feature is not enabled, `validate_multisig_transaction` will admit and execute **any** payload supplied at execution time as long as quorum/timelock conditions are satisfied — it never checks that the executed payload matches what the owners actually approved and voted on.

### Impact Explanation
Because owner votes (`approve_transaction`/`vote_transaction`) are recorded against a `sequence_number`, not against the payload content itself, quorum can be reached for payload A (e.g., "transfer 1000 to Alice"), while the executing owner (who only needs to be one of the `k` owners with sufficient approvals, and per `transaction_execution_cleanup_common` even gets an implicit approval bump if it happens to help meet the threshold) supplies payload B (e.g., "transfer 1000 to attacker") at execution time. With the feature flag off, admission succeeds and payload B executes under the multisig account's authority — an unauthorized state transition executed under the wrong (unapproved) payload, i.e., exactly the "stored/approved content ≠ executed content" invariant break described in the seed report.

### Likelihood Explanation
Exploitability depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active on a given network at the time. I was not able to confirm the default/rollout status of this specific feature flag within the available search budget — the flag and its guarded code path clearly exist in `features.move` and `multisig_account.move`, but I could not verify from the indexed content whether it is enabled by default on mainnet/testnet or whether other unseen guards (e.g. in `aptos_vm.rs`'s multisig transaction handling) additionally constrain the executable independent of this Move-level check.

### Recommendation
Make the full-payload match check in `validate_multisig_transaction` unconditional (not gated behind `abort_if_multisig_payload_mismatch_enabled`), so that when a full payload is stored on-chain, the payload actually executed must always equal the stored/approved payload, mirroring the unconditional treatment already given to the hash-only case.

### Proof of Concept
Not independently reproduced — this requires confirming the live on-chain value of the `abort_if_multisig_payload_mismatch_enabled` feature flag and the exact call path from `aptos_vm.rs` into `run_multisig_prologue`, which I could not fully trace before running out of tool budget. The finding is based on directly-read Move source showing the conditional guard [3](#0-2)  and the prologue wiring [4](#0-3) , but I was unable to confirm the feature flag's default/rollout state, so I cannot assert this is currently exploitable on production networks — flagging this uncertainty explicitly rather than asserting confirmed impact.

```rust
/// Run the prologue for a multisig transaction. This needs to verify that:
/// 1. The multisig tx exists
/// 2. It has received enough approvals to meet the signature threshold of the multisig account
/// 3. If only the payload hash was stored on chain, the provided payload in execution should
/// match that hash.
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };

    session
        .execute_function_bypass_visibility(
            &MULTISIG_ACCOUNT_MODULE,
            VALIDATE_MULTISIG_TRANSACTION,
            vec![],
            serialize_values(&vec![
                MoveValue::Signer(txn_data.sender),
                MoveValue::Address(multisig_address),
                MoveValue::vector_u8(provided_payload),
            ]),
            &mut UnmeteredGasMeter,
            traversal_context,
            module_storage,
        )
        .map(|_return_vals| ())
        .map_err(expect_no_verification_errors)
        .or_else(|err| convert_prologue_error(err, log_context))
}
```
