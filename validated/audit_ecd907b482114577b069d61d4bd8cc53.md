## Title
Cross-organization PullRequest data forgery via owner/full_name divergence in `AssignedHandler` - (File: `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC-verifying `GitHubApp` using `params.dig('repository','owner','login')`, while `AssignedHandler` resolves the `Repository`/`Stack`/`PullRequest` to mutate using `params.repository.full_name`. No code anywhere checks that these two values refer to the same organization, so a webhook validly signed for one onboarded org can be crafted to reference and mutate another onboarded org's `PullRequest` record.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:

`org_that_verified_signature == org_that_owns_the_mutated_record`

where:
- `org_that_verified_signature` = `Shipit.github(organization: repository_owner)` in `WebhooksController#verify_signature`, and `repository_owner` reads `params.dig('repository', 'owner', 'login')` directly from the raw, attacker-controlled JSON body. [1](#0-0) [2](#0-1) 

- `org_that_owns_the_mutated_record` = derived independently from `params.repository.full_name`, which `AssignedHandler` uses to look up a `Repository` and, through it, a `PullRequest` joined to `stack: :repository`: [3](#0-2) 

`AssignedHandler`'s `params` schema only requires `repository.full_name`, not `repository.owner.login`, so nothing in `ExplicitParameters` cross-validates the two: [4](#0-3) 

Root cause: this is a Shipit engine multi-tenant deployment feature — `secrets.yml` can configure multiple independent GitHub Apps/orgs each with their own `webhook_secret`, as documented and tested: [5](#0-4) [6](#0-5) 

Exploit flow: an attacker who legitimately administers one onboarded org ("attacker-org") in a multi-org Shipit instance knows their own `webhook_secret` (they configured it). They send `POST /webhooks` directly to the Shipit host (not via GitHub) with `X-Github-Event: pull_request` and a body where `repository.owner.login = "attacker-org"` (so `verify_signature` picks and passes with attacker-org's own secret) but `repository.full_name = "victim-org/victim-repo"` (so `AssignedHandler#repository`/`#pull_request` resolves to the victim's actual `Repository`/`Stack`/`PullRequest`). `AssignedHandler#process` then calls `pull_request.update(github_pull_request: params.pull_request)`, which — via `PullRequest#github_pull_request=` — rewrites `title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, and re-resolves `head` by fetching a commit sha (attacker-chosen) from the victim's own GitHub repo using the victim's stack's `github_api` credentials: [7](#0-6) 

No existing guard stops this: `verify_signature` only proves the request came from *some* onboarded org, not from the org named in `repository.full_name`; `drop_unhandled_event` and the `ExplicitParameters` schema only check shape, not cross-field provenance; there is no `Repository`/`Stack` ownership check tying the verified org to the mutated record.

### Impact Explanation
An attacker who legitimately controls one org onboarded to a shared/multi-tenant Shipit instance can forge `pull_request` webhooks that rewrite another onboarded org's `PullRequest` records (title, state, labels, assignees, diff head commit) purely by guessing/knowing a PR number, with no need to know the victim org's webhook secret. This is repeatable against every `PullRequest` row across every other tenant repository sharing the instance, and the pattern applies identically to `OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, and `LabelCapturingHandler`, all of which resolve their target `Stack`/`ReviewStack` the same way via `Repository.from_github_repo_name(params.repository.full_name)` without checking it against the org that verified the signature. This matches "a payload for one repository mutating another's stack/commit/task" — Critical, cross-tenant write.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (top-level `github:` keyed by organization, as documented and supported), (2) attacker legitimately controls at least one onboarded org (so they know that org's `webhook_secret`), and (3) a victim `Stack`/`PullRequest` exists for another onboarded org. Given these preconditions — which the rules explicitly grant ("victim review stack provisioned", attacker unprivileged only for the *victim* org) — the attack is a single unauthenticated (from the victim's perspective) `POST /webhooks` request, fully scriptable, with no rate limiting or additional secret required beyond the attacker's own legitimately-known webhook secret.

### Recommendation
In `WebhooksController#verify_signature` (or a shared before-filter), after signature verification, compare the organization used to look up the `GitHubApp`/secret against the organization embedded in `params.repository.full_name` (and reject on mismatch). Alternatively, in each `pull_request` sub-handler (including `AssignedHandler`), require and validate `repository.owner.login`, and assert it matches the owner segment of `repository.full_name` before resolving/mutating any `Repository`/`Stack`/`PullRequest`.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/assigned_handler_test.rb`, using a two-org secrets fixture like `test/dummy/config/secrets_double_github_app.yml`):

```ruby
test "assigned webhook signed for OrgOne cannot mutate a PullRequest owned by OrgTwo" do
  # victim stack/pull_request belongs to OrgTwo/victim-repo
  victim_pr = shipit_pull_requests(:review_stack_review) # stack.repository owned by "OrgTwo"

  payload = payload_parsed(:pull_request_assigned)
  payload["number"] = victim_pr.number
  payload["pull_request"]["number"] = victim_pr.number
  payload["repository"]["full_name"] = victim_pr.stack.repository.github_repo_name # "OrgTwo/victim-repo"
  payload["repository"]["owner"] = { "login" => "OrgOne" } # attacker's own onboarded org

  # signature computed with OrgOne's known webhook_secret
  signature = sign_with(secret_for("OrgOne"), payload.to_json)

  assert_no_changes -> { victim_pr.reload.attributes }, "victim_pr org verifying signature (OrgOne) != org owning pull_request (OrgTwo), so mutation must not occur" do
    @request.headers['X-Github-Event'] = 'pull_request'
    @request.headers['X-Hub-Signature'] = signature
    post :create, body: payload.to_json, as: :json
  end
end
```

The assertion `victim_pr.reload.title/state/labels/assignees` unchanged (equality `org_verifying == org_owning` must hold before mutation is allowed) is expected to **fail** on current code, since the handler updates `victim_pr` regardless of which org's secret verified the signature.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
