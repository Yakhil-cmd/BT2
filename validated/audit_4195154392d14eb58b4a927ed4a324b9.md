## Title
Stale cached `balance[address][asset]` snapshot in oscript evaluation lets an AA make fund decisions on out-of-date balances within a single trigger execution - (File: `formula/evaluation.js`)

### Summary
The `readBalance` helper inside the `evaluate()` function of `formula/evaluation.js` reads another address's balance once per trigger execution and permanently caches it in `objValidationState.assocBalances[param_address][bal_asset]`. Because this cache is never invalidated for the lifetime of the trigger (and is explicitly shared "by reference" across nested/remote getter calls, per the comment in `callGetter`), any AA logic that reads `balance[X][asset]` more than once in the same trigger, after having itself changed X's balance (e.g. by sending it a payment earlier in the same set of messages), will keep observing the stale pre-payment value instead of the updated one. This is directly analogous to the reported Balancer `BalancerStrategy` bug: a value obtained via a "view"-style read is cached and trusted for the rest of the execution without any mechanism to refresh or dispute it, even though the underlying state has since changed.

### Finding Description
`readBalance` is defined at [1](#0-0) :
```
function readBalance(param_address, bal_asset, cb2) {
    ...
    var balance = objValidationState.assocBalances[param_address][bal_asset];
    if (balance !== undefined)
        return cb2(new Decimal(balance));
    conn.query(
        "SELECT balance FROM aa_balances WHERE address=? AND asset=? ",
        [param_address, bal_asset],
        function (rows) {
            balance = rows.length ? rows[0].balance : 0;
            objValidationState.assocBalances[param_address][bal_asset] = balance;
            cb2(new Decimal(balance));
        }
    );
}
```
The first time an AA's formula reads `balance[some_address][asset]`, the value is fetched from the DB (the pre-trigger balance) and written into `objValidationState.assocBalances`. Every subsequent read of the same `(address, asset)` pair within the same trigger execution — including reads performed via nested remote-AA getter calls — returns this cached value instead of re-querying.

Crucially, this cache is *not* kept in sync with intra-trigger changes to other addresses' balances. The trigger's own balance bookkeeping (`trigger_opts.assocBalances`, which is the same object referenced by `objValidationState.assocBalances`) is only mutated for the *currently executing* AA address, in `updateInitialAABalances`/`updateFinalAABalances`/`sendDummyUnit` [2](#0-1) [3](#0-2) . When a payment is sent to a *different* address (e.g. another AA), that recipient's balance in `aa_balances` is only updated once that recipient's own trigger/secondary-trigger is processed — which happens after the current AA's messages finish evaluating. Meanwhile the caller's `objValidationState.assocBalances[recipient][asset]`, if already cached from an earlier `balance[...]` read in the same trigger, is left untouched.

The `callGetter` function explicitly documents and relies on this sharing behavior: [4](#0-3)  "no need to cloneDeep, we need to rewrite only storage size, assocBalances cache can be updated by reference" — i.e. remote getter calls made from within the same trigger chain reuse and can further pollute the same stale cache, propagating the outdated snapshot deeper into a call chain (as demonstrated by the multi-hop remote-function tests in `test/aa_composer.test.js`, e.g. the "calling a chain of remote functions" test at lines 1364-1519, where `balance[base]` is read from a base AA, an intermediary AA, and a chained remote AA within one trigger).

### Impact Explanation
An AA author writing multi-step logic that (a) sends a payment to another address (own state var, another AA, an escrow, etc.) earlier in its `messages`/`cases`, and (b) later in the same trigger re-checks `balance[that_address][asset]` (directly, or indirectly through a chained remote-getter call) to gate a further financial decision (e.g. "only proceed if recipient's balance now exceeds X", solvency/collateral checks, matching engines, vault/aggregator AAs coordinating balances across several cooperating AAs) will observe the pre-payment balance rather than the real one. This can be exploited to:
- Cause an AA to release additional funds or issue extra credit under the false belief that a counterpart AA's balance has not yet increased (double counting the same deposit across two checks within one trigger).
- Cause an AA to incorrectly reject/bounce a legitimate action based on a stale balance that doesn't reflect a payment the AA itself already made earlier in the same execution.
Either outcome constitutes AA fund loss, incorrect accounting, or a state divergence from the AA author's intended invariants — the same class of harm ("discount to depositor", "over-borrow") described in the source report, transplanted to oscript's stale balance cache instead of Balancer's manipulable single-sided pool valuation.

### Likelihood Explanation
This requires a specific coding pattern in an AA (read-then-pay-then-reread balance of the same address within a single trigger, or a getter chain that re-reads a balance already touched earlier in the chain) rather than a universal, always-triggerable protocol bug. It is nonetheless a realistic and easy-to-hit pattern for AAs that coordinate fund flows between multiple addresses/AAs in a single trigger (common in vault/aggregator/matching-style AAs), and the bug is silent — there is no error, warning, or documentation in oscript indicating that `balance[X]` is a point-in-time cached snapshot rather than a live read, making it likely to be unknowingly relied upon by AA developers.

### Recommendation
Do not cache balances of addresses other than the currently executing AA for the full lifetime of `objValidationState`, or explicitly invalidate/refresh `assocBalances[address][asset]` whenever a payment is sent to `address` within the same trigger's processing (mirroring how the executing AA's own balance is kept live via `updateFinalAABalances`). At minimum, document in the oscript reference that `balance[address]` is a cached snapshot per-trigger so AA authors are aware it will not reflect payments made to that address earlier in the same trigger.

### Proof of Concept
1. Deploy AA `V` (a "vault") with two cases in one trigger:
   - Case 1: pays `amount` bytes to helper AA `H`.
   - Case 2 (evaluated after case 1 in the same trigger): reads `balance[H][base]` and, if it now exceeds a threshold, performs a second privileged action (e.g. releases additional funds to the trigger sender).
2. Post a single trigger unit to `V` that satisfies both cases in one execution.
3. Because `readBalance` for `H`'s balance was already cached (e.g., cached at 0 before the payment in case 1, if `V` or another part of its logic reads `balance[H][base]` before sending the payment), the threshold check in case 2 uses the stale pre-payment value of `H`'s balance rather than the updated one, letting the trigger author bypass the intended "only release extra funds once `H` has received the deposit" guard within the very same unit that made the deposit — extracting funds `V` did not intend to release yet.
