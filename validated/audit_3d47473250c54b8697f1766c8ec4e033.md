### Title
`migrate_delegation` relies on a debug-only assertion to prevent migrating funds into an existing `Agent`/`Delegator` account, allowing state corruption in production builds - (File: `substrate/frame/delegated-staking/src/lib.rs`)

### Summary
`Pallet::do_migrate_delegation` in `pallet-delegated-staking` guards against migrating a proxy-delegator's held funds into a destination account that is already an `Agent` or an existing `Delegator` using a `debug_assert!`, not a `ensure!`/production check. In release (non-debug) builds — which is how production runtimes are compiled — this guard is compiled out entirely, so the invariant "a destination account of `migrate_delegation` must not already be a delegator or agent" is not actually enforced on-chain.

### Finding Description
The bug report describes a missing membership flag when adding an address into a per-user list, which lets the same address be processed twice, causing withdrawal accounting to double-count a user and underflow. The structural analog in `pallet-delegated-staking` is that a required "is this identity already present" invariant is checked only via `debug_assert!`, not through a real dispatch-time `ensure!`. Because Substrate/FRAME runtimes used in production are built in release mode, `debug_assert!` macros do not execute, so the very check meant to stop overlapping/duplicate identity state from being created is silently absent on-chain, just as the Solidity contract silently omitted setting `isUserInDelegatedStakeList[msg.sender][msg.sender] = true`.

Relevant code: [1](#0-0) 

```
	/// Migrates delegation of `amount` from `source` account to `destination` account.
	fn do_migrate_delegation(
		source_delegator: Delegator<T::AccountId>,
		destination_delegator: Delegator<T::AccountId>,
		amount: BalanceOf<T>,
	) -> DispatchResult {
		...
		let mut source_delegation =
			Delegators::<T>::get(&source_delegator).defensive_ok_or(Error::<T>::BadState)?;

		// ensure source has enough funds to migrate.
		ensure!(source_delegation.amount >= amount, Error::<T>::NotEnoughFunds);
		debug_assert!(
			!Self::is_delegator(&destination_delegator) && !Self::is_agent(&destination_delegator)
		);
		...
```

Note the check for `source_delegation.amount >= amount` uses `ensure!`, which is enforced in every build, while the identity-overlap check that prevents writing a fresh `Delegation` on top of an account that is already a delegator or an agent uses `debug_assert!`, which is stripped in release builds. The function then unconditionally proceeds to: [2](#0-1) 

```
		let agent = source_delegation.agent.clone();
		// create a new delegation for destination delegator.
		Delegation::<T>::new(&agent, amount).update(&destination_delegator);

		source_delegation.amount = source_delegation
			.amount
			.checked_sub(&amount)
			.defensive_ok_or(Error::<T>::BadState)?;
		...
		// update source delegation.
		source_delegation.update(&source_delegator);
```

`Delegation::update` only checks whether the *destination* key already exists in `Delegators` to decide whether to call `inc_providers`; it does not check whether the destination is an `Agent`: [3](#0-2) 

For comparison, `Delegation::can_delegate` (used by the normal `delegate_to_agent` path) does correctly reject an account that is already registered as an `Agent`: [4](#0-3) 

but `do_migrate_delegation` does not call `can_delegate` and instead only has the debug-only guard, meaning the production-enforced check that exists on the "normal" entry point is missing on the "migration" entry point.

### Impact Explanation
I was unable to fully confirm reachability/attacker-control of `destination_delegator` in the underlying `migrate_delegation` extrinsic (the dispatchable's origin/authorization checks and exactly who may pass an arbitrary `destination_delegator` were not fully inspected before running out of iterations — see "Unknowns" below). If `destination_delegator` is attacker-controlled (e.g., any account being able to specify a delegator target that happens to already be an `Agent`, or if the same address can be reached twice through repeated calls), the missing enforcement would let a `Delegators` entry be created/overwritten for an account that is simultaneously an `Agent`, or double-book delegation amounts for the same identity — mirroring the reported impact of duplicate/overlapping bookkeeping entries that can corrupt withdrawal/balance accounting (`AgentLedger`, `total_delegated`, held balances) and potentially cause `checked_sub`/`defensive_ok_or` failures or fund miscalculation on release/withdraw paths.

### Likelihood Explanation
Low-to-Medium confidence only. This requires (a) confirming that `destination_delegator` in the `migrate_delegation` extrinsic is attacker-supplied without further validation elsewhere in the dispatchable body (only `do_migrate_delegation` was inspected, not the full extrinsic wrapper), and (b) confirming there is no other ensure!-based check earlier in the call path (e.g. in the pallet's `Call::migrate_delegation` dispatchable itself) that duplicates the debug_assert's job. I could not verify either point within the available iterations.

### Recommendation
Replace the `debug_assert!` in `do_migrate_delegation` with a real `ensure!` (returning a proper `Error<T>` such as `InvalidDelegation` or a new `AlreadyDelegatorOrAgent` variant) so the invariant is enforced in all build profiles, consistent with how `Delegation::can_delegate` enforces the same invariant on the normal delegate path.

### Proof of Concept
Not executed. This is a static-analysis-only finding based on reading `substrate/frame/delegated-staking/src/lib.rs` and `types.rs`; no local Rust/FRAME integration test was run to demonstrate the debug_assert being bypassed in a release build, nor was the full `migrate_delegation` dispatchable (origin checks, benchmarking-only flags, and any wrapping `ensure!`s in the `#[pallet::call]` body) reviewed to confirm attacker reachability of `destination_delegator`. Given the "no fabricated PoC" and "no invented behavior" constraints, and that reachability/attacker-control could not be fully verified in the remaining budget, this should be treated as an unconfirmed lead requiring further investigation (full read of the `#[pallet::call] fn migrate_delegation` wrapper and a concrete `ExtBuilder`-based test attempting to migrate into an existing `Agent` account under a release-mode build) rather than a proven, bounty-ready Medium finding.

	/// Save self to storage.
	///
	/// If the delegation amount is zero, no delegation is stored: an existing one is removed and a
	/// new one is not created. Also adds and removes provider reference as needed.
	pub(crate) fn update(self, key: &T::AccountId) {
		let exists = <Delegators<T>>::contains_key(key);

		if self.amount.is_zero() {
			if exists {
				<Delegators<T>>::remove(key);
				// Remove provider if no delegation left.
				let _ = frame_system::Pallet::<T>::dec_providers(key).defensive();
			}
			return;
		}

		if !exists {
			// this is a new delegation. Provide for this account.
			frame_system::Pallet::<T>::inc_providers(key);
		}

		<Delegators<T>>::insert(key, self);
	}
