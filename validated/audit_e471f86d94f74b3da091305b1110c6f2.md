### Title
Webhook signature is verified against `repository.owner.login`, but events act on `repository.full_name` — cross-organization stack/commit forgery in a multi-tenant Shipit install - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an incoming webhook's HMAC signature against based on `repository.owner.login` (or `organization.login`) taken from the untrusted, unsigned-at-the-field-level JSON body. The event handlers, however, resolve which `Stack`/`Repository` to act on using a *different* field of the same body — `repository.full_name` — via `Handler#repository_name`. Since HMAC only proves "this body was signed with organization X's secret," not "every field inside referring to a repository actually belongs to organization X," an attacker who legitimately knows the `webhook_secret` for *any* one organization configured on the shared Shipit instance can forge a signature that validates using that org's secret, while pointing `repository.full_name` at a stack belonging to a completely different organization.

### Finding Description
- `WebhooksController#verify_signature` picks the app/secret with `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and only then calls `github_app.verify_webhook_signature(signature, raw_post)`. [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` only proves the raw bytes were HMAC-signed with that organization's `webhook_secret`; it says nothing about internal consistency between `repository.owner.login` and other fields such as `repository.full_name`. [3](#0-2) 
- The base `Handler` class, used by `PushHandler`, `CheckSuiteHandler`, PR handlers, etc., resolves the affected stacks purely from `repository.full_name`, independent of `repository.owner.login`: [4](#0-3) 
- `Repository.from_github_repo_name` splits that `full_name` into owner/name and looks up any `Repository` record system-wide, not scoped to the organization that authenticated the request: [5](#0-4) 
- `PushHandler#process` then calls `stack.sync_github(...)` for every non-archived stack on that branch: [6](#0-5) 
- `StatusHandler` is even less scoped: it updates `Commit.where(sha: params.sha)` for *any* commit matching that SHA anywhere in the install, with no repository check at all: [7](#0-6) 

**Binding broken (as an equality):** the engine implicitly assumes
`organization that authenticated the signature (repository.owner.login) == organization whose repository/stack the handler mutates (repository.full_name)`.
This equality is never checked in code — both fields are attacker-controlled fields of the same signed payload, but only one of them determines which secret is used, and the other determines the target of the write.

**Before the attack:** in a single Shipit deployment configured for multiple GitHub orgs (as the standard example in `config/secrets.development.shopify.yml` shows), org A and org B each have independent `webhook_secret`s and independent stacks/repositories. [8](#0-7) 

**After the attack:** a user who legitimately controls org A (and therefore knows org A's `webhook_secret`, since they configured that GitHub App/webhook themselves) can POST directly to the shared `/webhooks` endpoint with a JSON body where `repository.owner.login = "org-a"` (so verification succeeds using org A's known secret) but `repository.full_name = "org-b/private-repo"`. This is accepted, and the handler for that event acts on org B's `Stack`/`Repository` — e.g., forcing a `sync_github` re-fetch of undeployed commits for org B's stack (`PushHandler`), or writing a forged commit status for an arbitrary commit SHA that could flip CI-gating and enable an unauthorized deploy (`StatusHandler`, feeding `Stack#trigger_continuous_delivery` gating logic in `app/models/shipit/stack.rb`).

### Impact Explanation
This crosses a repository/organization trust boundary using only a credential (`webhook_secret`) that the attacker legitimately possesses for their own tenant, to write state (`Commit`/`Status`, undeployed-commit tracking) belonging to another tenant's repository they have no access to. Forged commit statuses can satisfy `ci.require` checks and, combined with continuous deployment being enabled on the victim's stack, lead to an unauthorized deploy being triggered — matching the "Critical: cross-repository writes / unauthorized deploy" category.

### Likelihood Explanation
Requires a multi-tenant Shipit install (multiple GitHub orgs configured, as documented/shown in the repo's own secrets template) and requires the attacker to control at least one legitimate `webhook_secret` — something they can obtain simply by being an admin of any one organization onboarded to the shared instance. No GitHub App private key, repository write access to the victim repo, or Shipit session is needed. This is a realistic scenario for shared/hosted Shipit deployments serving several orgs.

### Recommendation
When verifying a webhook, cross-check that `repository.owner.login` (or `organization.login`) used to select the verification secret matches the owner encoded in `repository.full_name` before dispatching to handlers, and reject the request otherwise. Additionally, scope `Handler#stacks` / `StatusHandler#process` lookups by the already-authenticated organization rather than trusting `repository.full_name` alone.

### Proof of Concept
1. Attacker is an authorized administrator of GitHub org `org-a`, onboarded to a shared Shipit instance, and knows `org-a`'s configured `webhook_secret`.
2. Attacker crafts a JSON body for a `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, org-a_webhook_secret)>` and POSTs directly to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "org-a"`, fetches org A's app, and `verify_webhook_signature` succeeds because the body was indeed signed with org A's secret. [1](#0-0) 
5. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `sync_github` on org B's stacks, entirely outside org A's authority. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
