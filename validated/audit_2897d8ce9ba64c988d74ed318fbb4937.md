### Title
Webhook signature verification selects the GitHub App/secret from `repository.owner.login`, while the repository actually mutated is resolved from the independent, uncorrelated `repository.full_name` field, allowing signature bypass for one org to write into another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App config (and thus which `webhook_secret`) to validate the `X-Hub-Signature` against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

`Shipit::GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved app config has no `webhook_secret` set: [3](#0-2) 

Separately, once the request passes `verify_signature`, the actual event handler (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`, inherited from the base `Handler` class: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated repository/stack) are two independent keys inside the same unauthenticated JSON payload, nothing forces them to agree. The setup docs demonstrate real deployments commonly configure multiple GitHub orgs, and some without a `webhook_secret` at all (e.g. `webhook_secret: # nil` for either org): [6](#0-5) 

### Finding Description
The binding that should hold is: **organization whose secret authenticated the webhook == organization that owns the repository being written to**. This engine breaks that equality:

1. `verify_signature` resolves the authenticating organization from `repository.owner.login` (or falls back to `organization.login`) purely from the unverified raw body, and looks up `Shipit.github(organization: repository_owner)`.
2. If that particular organization's config has no `webhook_secret` (a supported, documented configuration state — see `config/secrets.development.shopify.yml`), `verify_webhook_signature` short-circuits and returns `true` for *any* signature/payload, per `lib/shipit/github_app.rb:76-77`.
3. Downstream, `Handler#stacks`/`#repository_name` — used by `PushHandler`, `StatusHandler`, and other webhook handlers — resolves the target `Repository` from `repository.full_name`, a completely separate field of the same JSON body, without re-checking that `repository.owner.login` used in step 1 matches the owner segment of `repository.full_name`.
4. An attacker who knows (or brute-forces) the name of one configured organization lacking a `webhook_secret` can craft a payload where `repository.owner.login` is set to that unsecured org (bypassing signature verification) while `repository.full_name` is set to `"victim-org/real-repo"` — a repository belonging to a *properly secured* organization with real, production stacks.

This is directly analogous to the reported Euro-Dollar bug: two different code paths (`assetsToShares`/`sharesToAssets` price selection there; secret-selection vs. repository-resolution here) draw from the same request but use inconsistent fields, letting an attacker exploit the mismatch instead of the intended shared invariant.

### Impact Explanation
An attacker can trigger unauthenticated `PushHandler`/`StatusHandler` (and other webhook event) execution against a real stack owned by an organization whose webhook secret is properly configured, entirely bypassing GitHub's HMAC signature check. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack tracking the targeted repository/branch — letting the attacker drive GitHub sync behaviour (and, through `StatusHandler`, forge commit statuses via `commit.create_status_from_github!`) for a stack the attacker has no legitimate access to. This lands in the "unauthorized deploy/rollback" / "unauthenticated write into task/deploy state" high-impact category, since it defeats the entire purpose of webhook signature verification for a subset of configured organizations, cross-organization.

### Likelihood Explanation
Exploitability is conditional but realistic in any multi-organization Shipit deployment where at least one configured GitHub App entry omits `webhook_secret` (a state the shipped example config `config/secrets.development.shopify.yml` explicitly shows as supported/expected, and which `lib/shipit/github_app.rb` treats as "verification not required" rather than "app unusable"). No credentials, sessions, or GitHub App private keys are needed — only knowledge of one organization's slug that lacks a webhook secret, obtainable by probing `/webhooks` responses (`GithubOrganizationUnknown` vs. success) which differentiate configured vs. unconfigured orgs, per `WebhooksController#verify_signature`'s distinct error branch. [7](#0-6) 

### Recommendation
Do not select the verifying `webhook_secret`/GitHub App config using a field that has not yet been authenticated (`repository.owner.login`/`organization.login`); the organization used to verify must exactly match the organization derived from the same `repository.full_name` field used by the handlers. Additionally, `verify_webhook_signature` should never silently return `true` for a resolved-but-secret-less org when other configured orgs *do* have a secret — a missing/blank `webhook_secret` should either be a hard misconfiguration error or should not permit a wildcard bypass usable to target other orgs' repositories.

### Proof of Concept
Given a `secrets.yml` with two organizations, one secured and one not:
```yaml
github:
  secure-org:
    webhook_secret: real-secret
  unsecured-org:
    webhook_secret:   # nil
```
Attacker POST to `/webhooks`:
```
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "<attacker_sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secure-org/real-repo"
  }
}
```
- `repository_owner` resolves to `"unsecured-org"` → `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`) since `webhook_secret` is blank.
- `PushHandler#process` resolves stacks via `payload.dig('repository','full_name')` = `"secure-org/real-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), triggering `stack.sync_github(expected_head_sha: "<attacker_sha>")` on the secured org's stack despite the forged/absent signature.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
