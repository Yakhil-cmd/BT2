### Title
Attacker-initiated flash loan forces repayment of principal + fee from an arbitrary receiver contract — the repayment pull is bound to `receiver`, not the initiator - ([File: contracts/pool/src/ops/flash.rs])

### Summary
Like the OAuth plugin that never binds the callback to the session that started the flow, the pool's flash loan never binds the repayment to the party that initiated the loan. `controller::flash_loan(caller, asset, amount, receiver, data)` forwards an arbitrary caller and an arbitrary `receiver` to `pool::flash::apply`, which pays the principal to `receiver`, invokes `execute_flash_loan(initiator, ...)` on it, and then pulls `amount + fee` from `receiver` — never from `initiator`, and without any check that the receiver consented to or originated the flow. Any contract exposing `execute_flash_loan` can be made to pay the fee on an attacker-initiated loan it never requested.

### Finding Description
In `contracts/pool/src/ops/flash.rs`, `apply` (lines 40–71):

1. transfers `amount` from the pool to the attacker-chosen `receiver` (line 60),
2. invokes `execute_flash_loan` on `receiver`, passing `initiator` only as an unauthenticated argument (lines 62–64, 140–163),
3. requires `asset.allowance(receiver, pool) >= amount + fee` and pulls `amount + fee` from `receiver` via `transfer_from` (lines 173–179).

There is no requirement that `receiver == initiator`, that the receiver pre-registered intent, or that any state/nonce bound the callback to a flow the receiver began — the exact missing-`state`-parameter class from the report. The initiator is a pure attacker input: the controller entrypoint `flash_loan` requires only `caller.require_auth()`, and `receiver` may be any WASM contract (`require_wasm_receiver`, line 49).

Two victim shapes lose money:

- **Auto-approving receiver.** A receiver whose `execute_flash_loan` approves `amount + fee` unconditionally or gates only on `pool` (both test harnesses and the documented "approve the pool" pattern do this) loses `fee` on every forced call. The attacker repeats `flash_loan` naming the victim as `receiver`; each call nets the pool `fee` booked as protocol revenue (`book_fee`, lines 124–128) while the victim's balance shrinks by `fee` per iteration.
- **Standing allowance.** If the victim contract ever left a live `allowance(receiver, pool) >= amount + fee` (e.g., an approval from an earlier aborted flow), the pool pulls it even if the callback returns without doing anything, because the allowance check runs after the callback, against `receiver`.

The `data` payload and `initiator` argument are fully attacker-controlled, so the attacker can also drive any `data`-decoding logic the victim runs, but the guaranteed loss is the fee itself.

### Impact Explanation
Theft of user funds. A victim contract's token balance is drained `fee` per forced loan, repeatable until its balance or the pool's liquidity is exhausted, and the protocol books each drained fee as revenue (`interest::add_protocol_revenue`). The attacker pays nothing: the borrowed principal returns to the pool from the victim's own pull. This is a direct loss of the victim's tokens caused by a protocol-level authorization gap, not merely a victim-side integration mistake — the pool design makes repayment the receiver's obligation while initiation is permissionless.

### Likelihood Explanation
**Medium.** Exploitation requires a deployed contract that implements `execute_flash_loan` and either approves inside the callback without verifying `initiator`/`controller`-bound state, or retains a standing allowance to the pool. The protocol's own mocks and skill documentation show receivers that approve based on the callback arguments alone, so such contracts are a realistic deployment shape. Any unprivileged address can call `controller::flash_loan` repeatedly at no cost beyond gas. Impact is capped at `flashloan_fee` per call unless a standing allowance is large, keeping this at Medium rather than High.

### Recommendation
Bind the settlement to the initiator, the way the `state` parameter binds an OAuth callback to the initiating session:

- Pull `amount + fee` from `initiator` instead of `receiver`, or require `receiver == initiator` (or require the initiator to authorize the receiver selection via `receiver.require_auth()` when they differ), and/or
- Have the receiver pass a one-time nonce/`state` it registered in its own storage before initiation, verified inside the callback — as the skill docs already advise receivers to do defensively.

Additionally, document that any contract implementing `execute_flash_loan` must treat `initiator` as unauthenticated and gate on `pool == cfg.pool` plus a locally stored pending request.

### Proof of Concept
1. Victim deploys `V`, a WASM contract implementing `execute_flash_loan` that approves `pool` for `amount + fee` when `pool == cfg.pool` (the documented pattern), and holds tokens.
2. Attacker calls `controller::flash_loan(attacker, hub_asset, amount, receiver = V, data = arbitrary)`.
3. Controller forwards to `pool::flash::apply(env, hub_asset, initiator = attacker, receiver = V, amount, data)`.
4. Pool transfers `amount` to `V`, invokes `V.execute_flash_loan(initiator = attacker, ...)`; `V` sees `pool == cfg.pool` and approves.
5. `collect_repayment` pulls `amount + fee` from `V`; `V` loses `fee`. Repeat until `V` is drained or the pool lacks reserves.
