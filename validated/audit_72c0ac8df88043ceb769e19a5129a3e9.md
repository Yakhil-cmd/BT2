### Title
Cross-organization team membership escalation via `Team.find_or_create_by!(github_id:)` in `MembershipHandler#process` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up teams solely by `github_id`, with no cross-check that the requesting webhook's organization actually owns that team. An attacker who controls a legitimate GitHub organization registered with its own real `webhook_secret` in Shipit can send a validly-signed `membership` webhook naming their own org, but embedding the numeric `team.id` of a *different, unrelated* team already tracked by Shipit (e.g. one in `Shipit.github_teams`). The handler finds the pre-existing team by that id and calls `team.add_member(member)`, granting the attacker-chosen login membership in a team the attacker's organization never controlled on GitHub.

### Finding Description
The intended binding is: *a `Shipit::Membership` row for a team in `Shipit.github_teams` must equal a membership GitHub actually reports for that team's real organization*. Concretely: `membership.team.organization == webhook.organization.login` (the org that GitHub actually generated the event for) must hold before `team.add_member` runs.

`app/controllers/shipit/webhooks_controller.rb#verify_signature` only validates that the payload's HMAC signature matches the `webhook_secret` configured for `repository_owner` (derived from `params.dig('organization','login')` for membership events, `lib/shipit/github_app.rb#verify_webhook_signature`, `app/controllers/shipit/webhooks_controller.rb:59-62`). This only proves the payload was signed by whatever organization's secret the attacker holds (their own, e.g. `evilcorp`) — it says nothing about which team the payload claims to mutate.

`MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```
The `find_or_create_by!` lookup is keyed **only** on `github_id`. The `organization:` assignment inside the block only runs on *creation*; when a `Team` with that `github_id` already exists (e.g. `shipit_teams(:shopify_developers)`, fixture `github_id: 1`, `organization: shopify`), the existing record — and its `organization` — is returned unchanged, and the attacker's claimed `params.organization.login` ("evilcorp") is silently discarded. Nothing in the handler compares the found team's `organization` against `params.organization.login` or against the org that actually authenticated the request.

`User.find_or_create_by_login!(params.member.login)` (`app/models/shipit/user.rb:22-28`) does call `Shipit.github.api.user(login)` to fetch the account from GitHub when creating a new user, so a fully fabricated, non-existent login would raise `Octokit::NotFound` and abort. However, the precondition that `'victim-employee'` is a *real* GitHub login (just one who never used Shipit) is sufficient — the lookup succeeds and a legitimate `User` row is created, keyed by that real login, with no verification that this user has anything to do with the target team.

Exploit flow:
1. Attacker registers/owns GitHub org `evilcorp`, which is a legitimately configured multi-org Shipit installation entry with its own real `webhook_secret`.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `evilcorp`'s secret, and body: `{"action":"added","team":{"id":<shopify_developers.github_id>, "name":..., "slug":..., "url":...},"organization":{"login":"evilcorp"},"member":{"login":"victim-employee"},"repository":{"owner":{"login":"evilcorp"}}}`.
3. `verify_signature` passes because the signature matches `evilcorp`'s own secret.
4. `find_or_create_team!` matches the existing `shopify_developers` `Team` row purely by `github_id`, ignoring that `organization.login` is `evilcorp`.
5. `User.find_or_create_by_login!('victim-employee')` creates/finds the user.
6. `team.add_member(member)` inserts a `Shipit::Membership` binding `victim-employee` into `shopify_developers`.

None of the listed guards prevent this: `verify_signature` authenticates the org's own secret, not team ownership; `drop_unhandled_event` and the `ExplicitParameters` schema only validate event/shape, not cross-org team ownership; `force_github_authentication`/`User#authorized?` are unrelated to webhook ingestion.

### Impact Explanation
This directly escalates an arbitrary attacker-chosen (but real) GitHub login into any `Shipit::Team` already tracked in the database — including teams in `Shipit.github_teams`, which gate authentication/authorization for the entire Shipit instance (`app/controllers/concerns/shipit/authentication.rb:26`, `app/models/shipit/user.rb:80-82`). Once membership is granted, if the named victim login later authenticates via GitHub OAuth against this Shipit instance, `User#authorized?` will treat them as authorized, and if `victim-employee`'s account is later compromised/renamed to the attacker's own account, or if the attacker simply names their own alternate GitHub login, the attacker gains authenticated access to the Shipit application, its stacks, deploys, and secrets. This is repeatable against any team whose `github_id` the attacker can learn (team IDs are often discoverable via GitHub's public API), and it is not scoped to the attacker's own tenant — it mutates state (`Shipit::Membership`) belonging to a completely different organization's trust boundary. This matches "High: escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: Shipit must be configured for multiple GitHub organizations (the multi-org `github:` secrets schema, `lib/shipit.rb:170-200`) with the attacker legitimately controlling one of those orgs (owning its real `webhook_secret`) and having a `membership` webhook registered for it. The attacker needs no privileged Shipit role — only a repository/organization they administer plus knowledge of the target team's numeric GitHub `github_id`. Cost is low: one crafted, self-signed HTTP POST. It is directly repeatable for `action: 'removed'` too, letting the attacker also *evict* real members from another org's team by reusing the same trick.

### Recommendation
In `find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject (or re-key) memberships when an existing team's `organization` doesn't match `params.organization.login`. At minimum, verify `team.organization == params.organization.login` before calling `team.add_member`/`team.members.delete`, and treat a mismatch as an error (e.g. `head(422)`) rather than silently operating on the pre-existing team.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership cannot let another organization mutate a foreign team's membership" do
  @request.headers['X-Github-Event'] = 'membership'
  target_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1

  attacker_payload = {
    action: 'added',
    team: { id: target_team.github_id, name: 'Fake', slug: 'fake', url: 'https://example.com' },
    organization: { login: 'evilcorp' },
    member: { login: 'victim-employee' },
    repository: { owner: { login: 'evilcorp' } }
  }.to_json

  # Simulate evilcorp's *own* real, valid webhook secret
  Shipit.github(organization: 'evilcorp').expects(:verify_webhook_signature).returns(true)
  Shipit.github.api.expects(:user).with('victim-employee').returns(
    stub(id: 999, login: 'victim-employee', name: 'Victim', email: 'v@example.com',
         avatar_url: 'https://x', url: 'https://api.github.com/users/victim-employee')
  )

  post :create, body: attacker_payload, as: :json

  # Binding check: evilcorp must NOT be able to write a membership into shopify's team
  assert_not Membership.exists?(team: target_team, user: User.find_by(login: 'victim-employee')),
             "evilcorp forged membership into shopify/developers without authority"
end
```
Before the fix, this assertion fails (the membership row is created); after scoping team lookup by `organization`, the handler should create/find a *distinct* `evilcorp`-owned team for that `github_id` collision or reject the mismatch, and the assertion passes.
