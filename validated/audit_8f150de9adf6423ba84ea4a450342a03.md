### Title
Unauthenticated `membership` webhook forgery escalates arbitrary GitHub users into `Shipit.github_teams` authorization when `webhook_secret` is unset - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally trusts an incoming webhook whenever `webhook_secret` is not configured for the resolved organization, and `WebhooksController` picks *which* organization's secret/config to use for that verification from a field inside the same unauthenticated payload. Combined with `MembershipHandler`, this lets anyone who can reach the `/webhooks` endpoint forge a `membership` event that adds an arbitrary GitHub login to a `Team` matching `Shipit.github_teams`, which is exactly the set used to authorize access to the whole application in `User#authorized?`.

### Finding Description
`verify_webhook_signature` returns `true` and skips HMAC validation whenever no `webhook_secret` is configured for the organization: [1](#0-0) . `webhook_secret` is optional/commented-out in every example/template configuration [2](#0-1) [3](#0-2) , so an organization left without a webhook secret is a realistic deployment state, not a contrived one.

Which organization's `GitHubApp` (and therefore which `webhook_secret`) is used to verify a given request is decided by `WebhooksController#repository_owner`, which reads `params.dig('repository', 'owner', 'login')` — a value taken directly from the attacker-controlled, unauthenticated request body: [4](#0-3) . So the "identity that authenticated" (the org selected for signature check) is itself picked from the payload being verified — if that org has no `webhook_secret`, any payload claiming to be from it is accepted with zero cryptographic verification, regardless of the real sender.

Once past `verify_signature`, `WebhooksController#create` dispatches the raw, unauthenticated JSON to `Shipit::Webhooks.for_event(event)` handlers [5](#0-4) . For `X-Github-Event: membership`, this is `MembershipHandler`, which finds/creates a `Team` from attacker-supplied `team.id`/`team.name`/`team.slug` and `organization.login`, then adds an attacker-chosen `member.login` to it: [6](#0-5) .

`Team.find_or_create_by_handle`, used to build `Shipit.github_teams`, matches teams purely by `organization`/`slug` string equality — no GitHub-side confirmation is performed for teams that already exist: [7](#0-6) [8](#0-7) . So an attacker who knows (or guesses) the org/slug of a team already present in `Shipit.github_teams` can send a forged `membership` payload with that `team.id` (matched via `github_id`, which the attacker also controls) and any `member.login` of their choice; `MembershipHandler#process` will call `team.add_member(member)` [9](#0-8) , creating a `Membership` row.

`User#authorized?` grants full application access to any user whose `teams` intersects `Shipit.github_teams` by `id`: [10](#0-9) , which is enforced on every controller via `Authentication#force_github_authentication`: [11](#0-10) .

The binding broken is: `organization that authenticated the webhook` ≠ `repository/organization whose Team membership record is written`. Signature verification is (or isn't) performed against a `webhook_secret` selected using an attacker-controlled field, and even when it is genuinely bypassed (blank secret), the write target (which `Team`/`User` gets a `Membership`) is fully attacker-controlled and is the very object that gates authorization.

### Impact Explanation
This is an authentication-bypass / authorization-escalation path: an unauthenticated attacker can grant an arbitrary GitHub identity (including a sock-puppet account they control, once that login is resolved/created via `User.find_or_create_by_login!`) membership in a `Team` that satisfies `Shipit.github_teams`, thereby escalating into full authenticated access to the Shipit instance — matching the "escalation into `Shipit.github_teams` authorization" impact bucket explicitly in scope.

### Likelihood Explanation
Requires only that (a) the target Shipit deployment configures multiple GitHub organizations (or a single org) with at least one entry lacking `webhook_secret` — a state directly encouraged by the shipped example/template configs — and (b) the attacker knows the `organization/slug` handle of a team listed in `Shipit.github_teams` (often discoverable, e.g., from documentation, error messages listing team handles in `Authentication#force_github_authentication`, or org/team names being public on GitHub). No credentials, GitHub App keys, or prior application access are needed.

### Recommendation
- Require `webhook_secret` to be present for every configured organization; refuse to boot (or refuse all webhooks) if any org config lacks one, instead of silently returning `true` from `verify_webhook_signature`.
- Do not select the verification key using a field taken from the unauthenticated payload; verify webhook deliveries using a per-installation secret bound at delivery time (e.g. via GitHub's per-app installation identity) rather than `repository.owner.login`/`organization.login` echoed back by the sender.
- In `MembershipHandler`, do not trust `team.id`/`organization.login` to look up/create a `Team` unconditionally; corroborate membership changes against a GitHub API call using the app's own credentials before mutating `Membership` records that feed into `Shipit.github_teams` authorization.

### Proof of Concept
1. Deploy Shipit with two GitHub orgs configured, where `OrgTrusted` (whose team `OrgTrusted/deployers` is listed in `Shipit.github_teams`) has a `webhook_secret` set, but a second org entry `OrgB` (present in config for unrelated reasons, or simply omitted/blank) has no `webhook_secret`.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "deployers", "slug": "deployers", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "OrgTrusted" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "OrgB" } }
}
```
3. `WebhooksController#repository_owner` resolves to `OrgB` (from `repository.owner.login`), whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally because `OrgB` has no `webhook_secret` — no valid `X-Hub-Signature` is required at all.
4. `MembershipHandler` finds the existing `Team` row for `OrgTrusted/deployers` (matched via `github_id: 1`, matching what `Team.find_or_create_by_handle("OrgTrusted/deployers")` already created) and appends `attacker-controlled-login` as a member.
5. `attacker-controlled-login`, once logged in via GitHub OAuth, now passes `User#authorized?` and gains full access to the Shipit instance.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event

    end

    def repository_owner

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          when 'removed'

        end

        end
