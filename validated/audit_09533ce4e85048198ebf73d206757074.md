Confirmed: `Api::StacksController#stack` correctly uses the scoped `stacks.from_param!(params[:id])` (inherited helper), while `Api::CCMenuController#stack` overrides this with an unscoped `Stack.from_param!(params[:stack_id])`. ### Title
Stack-scoped API tokens can read CCMenu build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the stack-resolution method inherited from `Api::BaseController` in a way that discards the per-token stack scoping, letting any authenticated `ApiClient` with `read:stack` permission — including one deliberately scoped to a single stack — read the CI/build status of every stack in the Shipit instance.

### Finding Description
`Api::BaseController` implements token-to-resource scoping by intersecting the requested stack with the set of stacks the authenticated `ApiClient` is authorized for: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is the binding: `ApiClient#stack_id` (the stack the token authorizes) must equal (or be a superset check against) the stack a request actually touches. `Api::StacksController` respects this by using the inherited `stacks.from_param!` helper [2](#0-1) .

`Api::CCMenuController`, however, redefines `stack` to bypass the scoping entirely: [3](#0-2) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

Because `Stack.from_param!` is called directly on the `Stack` model rather than through the scoped `stacks` relation, the `current_api_client.stack_id` check from `BaseController#stacks` is never applied. The only authorization check performed is `require_permission :read, :stack` [4](#0-3) , which only verifies that the token carries the `read:stack` permission string — it does not verify which specific stack the permission applies to.

This exactly matches the report's bug class: two places are supposed to jointly enforce a constraint (here, "permission string" + "stack scope"), but one of the two enforcement paths (the scope check) is silently dropped in a subclass, just as `endProposal()` in the report failed to reconcile votes split across two independently-added "no action" slots.

### Impact Explanation
A stack-scoped `ApiClient` token — the kind explicitly created for narrow, low-privilege use (e.g. by `CCMenuUrlController`, which mints a token scoped to one stack with only `read:stack` permission for embedding in third-party CI dashboard tools) — can be replayed against `/api/<any-other-stack>/ccmenu.xml` to read that other stack's build status, name, last build label/time, and web URL. This breaks the intended per-stack read isolation that `ApiClient.stack_id` scoping exists to enforce, i.e. "a stack a token authorises versus a stack it touches" as flagged in the rules. It is an authorization-boundary violation: a low-trust, narrowly-scoped credential yields read access to arbitrary stacks' deployment state, equivalent in kind to the High-severity "unauthorized read of stack state" category, since for any stack other than the one it was issued for, the token has effectively zero authorization yet is still granted read access.

### Likelihood Explanation
Exploitation requires only possession of any valid stack-scoped `read:stack` API token (e.g. a CCMenu URL leaked from a CI dashboard, chat integration, or status badge — these tokens are designed to be embedded in external, less-trusted tooling per `CCMenuUrlController`). No additional privilege, write access, or session is needed; only the `stack_id` in the target stack's `to_param` (owner/name/environment) must be known or guessed, which is not secret. This makes the likelihood high once such a token has leaked, which is the exact threat model the per-stack scoping mechanism was built to contain.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation inherited from `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, instead of calling `Stack.from_param!` directly, so that `ApiClient.stack_id` scoping is uniformly enforced across all API endpoints.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id = A` with only `read:stack` permission (this is exactly what `CCMenuUrlController#client` provisions for embedding in external dashboards) [5](#0-4) .
2. Using that token's `authentication_token`, issue `GET /api/<stack-B-owner>/<stack-B-name>/<stack-B-env>/ccmenu.xml?token=<token>` for a different stack `B` that the token was never scoped to.
3. `Api::CCMenuController#authenticate_api_client` authenticates the token successfully (it is valid), `require_permission :read, :stack` passes (the token does have `read:stack`), and `stack` resolves stack `B` unscoped via `Stack.from_param!(params[:stack_id])`, returning stack `B`'s deploy/build status XML — despite the token only being authorized for stack `A`.
