### Title
CCMenuController bypasses ApiClient stack-scoping enforced by BaseController#stacks - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one with `stack_id` set) can only resolve stacks matching its own `stack_id`, via the `stacks`/`stack` helper methods. `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` relation, completely bypassing that restriction, so a stack-scoped token can be used to read the CCMenu status of any stack.

### Finding Description
The binding that should hold is: `current_api_client.stack_id? ? params[:stack_id] resolves only within Stack.where(id: current_api_client.stack_id) : Stack.all`, as implemented in `BaseController#stacks`/`#stack`: [1](#0-0) .

`CCMenuController` inherits from `BaseController` but privately overrides `#stack` to bypass the scoped `stacks` collection and instead call `Stack.from_param!` on the entire `Stack` table: [2](#0-1) . It also overrides `#authenticate_api_client` to accept a token straight from the query string before falling back to basic auth: [3](#0-2) .

The only permission check applied is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!(operation, scope)` — this only checks the client's `permissions` array (e.g. `read:stack`), never comparing `current_api_client.stack_id` to the requested `params[:stack_id]`: [4](#0-3) . `ApiClient.authenticate` itself only verifies the signed token and loads the `ApiClient` row by id; it performs no stack-id comparison either: [5](#0-4) .

The `ApiClient` model supports an optional `belongs_to :stack`, confirming stack-scoped clients are a first-class, supported feature of the model (used by `BaseController#stacks`), even though the currently-shipped UI controller (`ApiClientsController#create_params`) does not expose setting it via the web form: [6](#0-5) [7](#0-6) . A stack-scoped `ApiClient` can be created directly on the model (e.g., console, seed data, or a future admin feature) — its `stack_id` attribute is legitimate application data that other controllers (`BaseController`) already trust to restrict scope.

Exploit flow: possessing a token for a client scoped to stack A (`current_api_client.stack_id == A.id`), the attacker sends `GET /api/stacks/<stack-B-param>/cc.xml?token=<token-for-A>`. `authenticate_api_client` authenticates successfully against stack A's client. `require_permission!` only checks that `read:stack` is in the permissions list — true. `#stack` then resolves `Stack.from_param!(params[:stack_id])` against the full `Stack` table, returning stack B, and `#show` renders stack B's CCMenu XML (build/deploy status) despite the token never having been scoped to B.

### Impact Explanation
An attacker holding any single stack-scoped `read:stack` API token gains unauthenticated read access to the CCMenu status feed (deploy/build activity, last build status/label/time, lock state) of every other stack in the Shipit instance, not just the one the token authorizes. This is repeatable against arbitrary stacks by varying `stack_id` in the URL and does not require the app's `api_clients_secret` to be guessed — only a legitimately-scoped token for any one stack. This matches the "High - unauthenticated read of stack state" impact category in the rubric, though it requires the attacker to already hold a stack-scoped token (an unusual application configuration since no current UI creates stack-scoped clients).

### Likelihood Explanation
Exploitability depends entirely on whether any stack-scoped `ApiClient` (non-null `stack_id`) exists in the deployment. The currently shipped `ApiClientsController` and `CCMenuUrlController#client` never set `stack_id` when creating clients, so out-of-the-box no token is stack-scoped, and this path is currently unreachable via the documented UI. It becomes exploitable only if an operator creates a stack-scoped `ApiClient` some other way (rails console, custom integration, future feature), at which point the divergence is fully attacker-controllable and trivially repeatable.

### Recommendation
Remove the private `#stack` override in `CCMenuController` (and rely on the inherited `BaseController#stack`, which uses the scoped `stacks` relation), or explicitly re-implement it using `stacks.from_param!(params[:stack_id])` so stack-scoped tokens are restricted the same way as in every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read a different stack's ccmenu" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar'), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped',
    stack: stack_a,
    permissions: %w[read:stack]
  )

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Binding under test: scoped_client.stack_id == stack_a.id, must not equal stack_b.id
  assert_equal stack_a.id, scoped_client.stack_id
  refute_equal stack_b.id, scoped_client.stack_id

  # Current (buggy) behavior returns 200 with stack_b's data; expected behavior is 404/forbidden
  assert_response :not_found # fails today: controller renders 200 with stack_b payload
end
```
