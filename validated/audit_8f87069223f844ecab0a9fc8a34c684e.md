This confirms the binding: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` to select which `Stack`/`Repository` gets acted on [1](#0-0) , while `WebhooksController#verify_signature` selects which `GitHubApp`/secret to check the signature against using `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . Both fields come from the same attacker-suppliable JSON body, and `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank/unset [3](#0-2) .

### Title
Cross-organization webhook forgery via mismatched signature-org and repository-full_name bindings when any configured org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-org deployments (`Shipit.github_organizations` > 1, using the per-organization config schema) [4](#0-3) , the webhook signature is verified against the `GitHubApp` selected by `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated request body, but the `Stack`/`Repository` that is actually mutated by the handler is selected independently, from `repository.full_name`, also taken from the same untrusted body [1](#0-0) . If any organization configured in `secrets.github` has `webhook_secret` unset (which the docs present as optional/valid: `webhook_secret: # nil`) [5](#0-4) , `verify_webhook_signature` returns `true` unconditionally for a payload claiming that org as `repository.owner.login`, regardless of the actual `X-Hub-Signature` header [3](#0-2) .

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature == organization whose repository is written by the handler`. It is broken as follows:

1. `WebhooksController#verify_signature` picks the app/secret via `repository_owner`, derived from the same JSON body being verified [6](#0-5) .
2. `Handler#stacks`/`#repository_name` independently reads `repository.full_name` from that same body to find the `Repository`/`Stack` to act on [1](#0-0) .
3. Nothing enforces that `repository.owner.login` (used for auth) matches the owner segment implied by `repository.full_name` (used for the write). An attacker fully controls the raw JSON body, so these two fields can be set independently: e.g. `repository.owner.login = "org-without-secret"` while `repository.full_name = "org-with-secret/target-repo"`.
4. If `org-without-secret` is configured in `secrets.github` with `webhook_secret` empty, `verify_webhook_signature` returns `true` without checking `X-Hub-Signature` at all [3](#0-2) , so the whole webhook check passes.
5. The event is then dispatched to handlers (e.g. `PushHandler`) which look up the `Stack` by `repository.full_name` — i.e., the org/repo that *does* have secret protection — and trigger real side effects: `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` and appends attacker-chosen commits into the stack, followed by `CacheDeploySpecJob`, review-stack archive/unarchive via `PullRequest::LabeledHandler`, `commit_status`/`check_suite` updates, etc. [7](#0-6) [8](#0-7) .

This is only exploitable when at least one organization in a multi-app deployment omits `webhook_secret` — a configuration explicitly documented and defaulted to `nil` in the example/dummy secrets files, and treated by the code as "optional" rather than "trusted only for its own org's traffic."

### Impact Explanation
This allows an unauthenticated third party to inject forged GitHub events (push, status, check_suite, pull_request, membership, etc.) that get processed against a *different, secret-protected* organization's stacks — an unauthorized write of sync/deploy-trigger state and cross-repository/cross-org action, matching the "an organization that authenticated versus the repository that is written" boundary explicitly called out in scope. Depending on which handler fires, this can drive `GithubSyncJob`/`CacheDeploySpecJob`, alter review-stack archive state (`PullRequest::LabeledHandler`), or fabricate commit statuses that gate continuous deployment — all without any valid signature for the targeted org.

### Likelihood Explanation
Requires a specific, but plausible and documented, misconfiguration: a multi-org Shipit install where at least one configured GitHub App has no `webhook_secret` set (shown as a supported "optional" example in the shipped config templates). Once that condition holds, exploitation needs no credentials — only crafting a JSON body and hitting `/webhooks`, since `check_if_ping`/`drop_unhandled_event` don't validate cross-field consistency either.

### Recommendation
- Require the organization used for signature verification to be consistent with the organization implied by `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers — reject if they mismatch.
- Stop treating an absent `webhook_secret` as "verification passes"; either require `webhook_secret` for every configured organization in multi-org mode, or fail closed (422) instead of returning `true` in `GitHubApp#verify_webhook_signature` when no secret is configured.
- Alternatively, derive the app/secret to check strictly from the resolved `Repository`/`Stack` (matching `full_name`) rather than from the attacker-suppliable `owner.login` field, so the org used to select the HMAC key is authoritative rather than attacker-chosen.

### Proof of Concept
Preconditions: multi-org config with orgs `secure-org` (has `webhook_secret`) and `open-org` (no `webhook_secret`), and `secure-org/target-repo` has a Shipit `Stack`.

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/target-repo"
  }
}
```

`repository_owner` resolves to `open-org`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no secret configured) regardless of the bogus/missing `X-Hub-Signature`. The request passes `verify_signature`, and `PushHandler#stacks` resolves `Repository.from_github_repo_name("secure-org/target-repo")`, triggering `stack.sync_github(expected_head_sha: "deadbeef...")` on the secure org's stack — an unauthenticated cross-org sync trigger.
