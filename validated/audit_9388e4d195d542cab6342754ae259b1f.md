### Title
Unhandled `throw` reachable from an attacker-crafted `address` definition condition causes node process crash (complete DoS) - ([File: definition.js])

### Summary
`CVE-2020-14680` is a MySQL Optimizer bug that lets a low-privileged, network-reachable attacker crash the server (availability-only impact, CVSS 6.5). The reachable ocore analog is an unhandled JavaScript `throw` inside the asynchronous `address`-definition evaluation path in `definition.js`, which is reachable by any unprivileged unit poster who defines an address whose definition contains an `['address', other_address]` condition referencing another author in the same unit. If more than one co-author in `objUnit.authors` matches the same `other_address` and the same `definition_chash`, the code throws synchronously inside an async storage callback instead of returning an error through `cb()`.

### Finding Description
Inside `validateDefinition`'s `evaluate()` for the `address` op, when the referenced address's definition isn't found in storage, the code looks for a matching co-author definition in the *same unit* and expects at most one match: [1](#0-0) 

```
ifDefinitionNotFound: function(definition_chash){
    var arrDefiningAuthors = objUnit.authors.filter(function (author) {
        return (author.address === other_address && author.definition && objectHash.getChash160(author.definition) === definition_chash);
    });
    ...
    if (arrDefiningAuthors.length > 1)
        throw Error("more than 1 address definition");
    ...
}
```

This `throw` executes inside the callback passed to `storage.readDefinitionByAddress`, i.e. inside an asynchronous I/O callback, not inside the synchronous `try{...}catch{...}` block that wraps the top-level `validate()` entry point in `validation.js`. A `throw` from that context is not caught by any surrounding `try/catch` and propagates as an uncaught exception all the way up the event loop.

`network.js` explicitly re-throws on any uncaught exception to crash the process: [2](#0-1) 

The precondition for reaching `arrDefiningAuthors.length > 1` is that `objUnit.authors` contains two (or more) authors with the same `address` field and a `definition` field whose chash matches the `definition_chash` being resolved. Author validation (`validateAuthor`/`validateAuthors`) does not appear to reject duplicate `author.address` values prior to reaching this address-condition evaluation for other authors' definitions, so a unit with duplicate-address authors carrying matching definitions can reach this branch.

### Impact Explanation
Hitting this `throw` crashes the entire full node process (both hub/relay and light-vendor nodes that process the unit), not just fail validation of one unit. Because `handleJoint`/`handleOnlineJoint` invoke `validation.validate` from within network message handling, a single crafted unit broadcast to a node is sufficient to bring the node down — matching the CVE's "complete DoS via crash" class of impact. Repeated broadcast of the same/similar crafted unit to many nodes (or resubmission after restart) is a "frequently repeatable crash," directly analogous to the referenced CVE. This can degrade network-wide ability to process/confirm units if enough nodes are hit, which satisfies the "network unable to confirm new units" acceptance bar.

### Likelihood Explanation
Exploitability is straightforward for anyone able to construct and post/broadcast a unit (no special privilege required beyond normal ability to submit a unit, matching PR:L/AV:N in the CVE vector): the attacker needs to author a unit with two authors sharing the same address string but distinct signing artifacts and matching definition-chash for the nested `address` condition reference. This is deterministic (no race condition or timing dependency) and repeatable.

### Recommendation
- Replace `throw Error("more than 1 address definition")` with `return cb("more than 1 address definition")` so it flows through the same error-callback path as sibling checks, preventing propagation as an uncaught exception.
- Audit `validateAuthors`/`validateAuthor` to reject units where multiple authors share the same `address` field early, before any nested-definition evaluation is attempted, closing off this precondition entirely.
- More generally, review all `throw` statements inside asynchronous callbacks in `definition.js`/`validation.js` that are invoked as part of unit validation, since any of them can crash the process the same way; convert unexpected-invariant throws that are reachable from external, attacker-controlled data into propagated `cb(error)` calls instead of synchronous throws.

### Proof of Concept
Construct and broadcast a unit `U` with:
- Two entries in `objUnit.authors`, `A1` and `A2`, both having the identical `address` value `X` (this is otherwise not rejected before this check is reached), each supplying a `definition` field.
- A third author (or one of `A1`/`A2`) whose own address definition contains a nested condition `['address', X]`.
- Craft `A1.definition` and `A2.definition` such that `objectHash.getChash160(A1.definition) === objectHash.getChash160(A2.definition) === definition_chash` expected for address `X` (e.g., both authors submit byte-identical `definition` arrays, which trivially satisfies matching chash), while address `X`'s definition is otherwise unresolved in storage (`ifDefinitionNotFound` branch is taken).
- When `evaluate` processes the `['address', X]` condition and reaches `ifDefinitionNotFound`, `arrDefiningAuthors.filter(...)` will return both `A1` and `A2` (length 2), triggering `throw Error("more than 1 address definition")` inside the async storage callback, which propagates uncaught and crashes the node process per the `process.on('uncaughtException', ...)` handler in `network.js`.

Note: full end-to-end verification (confirming that no earlier validation step rejects duplicate-address authors, and that the `objectHash.getChash160` matching condition is satisfiable together with a duplicate-address unit passing prior joint/unit-level checks) requires running the code with a constructed test unit; this could not be executed in this read-only analysis and should be confirmed by a Devin session with test execution.
