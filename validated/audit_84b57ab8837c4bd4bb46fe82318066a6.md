### Title
Stack-scoped API token can read the CI/deploy status of any stack via the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper in a way that discards the stack-scoping enforced by `Shipit::Api::BaseController`, so any `read:stack`-permitted `ApiClient` token — including one explicitly scoped to a single stack — can be used to fetch build/deploy status for an arbitrary stack by changing the `stack_id` route parameter.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` and the `stack_id` column. [1](#0-0) 

`Shipit::Api::BaseController` enforces this scoping for every API endpoint that relies on it: `stacks` restricts the queryable relation to the client's own `stack_id` when one is set, and `stack` resolves the requested `stack_id` param only within that restricted relation. [2](#0-1) 

This is the binding the system is supposed to maintain: **stack authorised by token == stack touched by the request**.

`Shipit::Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack` (a permission-only check, not a scope check), but it privately redefines `stack` to bypass the client-scoped relation entirely: [3](#0-2) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

`Stack.from_param!` resolves any stack in the database by owner/name/environment path segments, with no reference to `current_api_client` at all: [4](#0-3) 

`check_permissions!` only checks that the token has the string permission `"read:stack"` in its `permissions` array — it never compares the token's own `stack_id` to the stack actually being accessed: [5](#0-4) 

So for `CCMenuController#show`, a valid token authorised to view Stack A (`stack_id` pinned to A, `permissions: ["read:stack"]`) can be presented against `GET /api/:stack_id/cc.xml` with any other stack's `stack_id` in the URL and will successfully render that stack's latest deploy/rollback status.

### Impact Explanation
This breaks the authorization boundary between "stack a token is scoped to" and "stack a request actually touches," matching the required High-impact class: unauthenticated/unauthorized read of stack state and task/deploy status for stacks the token holder was never granted access to. An attacker in possession of any single-stack-scoped `read:stack` token (e.g. leaked from a CI status badge, a public dashboard integration, or a compromised low-privilege client) can enumerate and read deploy/build status of every other stack hosted by the same Shipit instance, including private/internal deployment pipelines, by only knowing or guessing `stack_id` path values.

### Likelihood Explanation
The prerequisite is only possession of any valid `ApiClient` bearer token that has the `read:stack` permission — no repository write access, no webhook secret, and no privileged account is required. Such tokens are commonly distributed for exactly this purpose (CI status widgets, CCMenu URLs), and the endpoint itself is unauthenticated beyond the token, so likelihood is high whenever any such token exists in the deployment.

### Recommendation
Have `CCMenuController#stack` use the inherited, scope-aware `stack`/`stacks` helper from `BaseController` (i.e., delete the private override, or reimplement it as `stacks.from_param!(params[:stack_id])`) so a client's `stack_id` restriction is honored consistently across all API endpoints, including CCMenu.

### Proof of Concept
1. Admin creates (or a legitimate integration already has) an `ApiClient` scoped to Stack A: `permissions: ["read:stack"]`, `stack_id: <A's id>`.
2. Using that token's Basic Auth credentials, or its authentication token as the CCMenu `token` query parameter, issue:
   `GET /api/:stack_id_for_B/cc.xml?token=<TokenForStackA>`
   where `stack_id_for_B` is any other stack in the instance (e.g. `some-other-owner/some-other-repo/production`).
3. `CCMenuController#authenticate_api_client` authenticates the token (`ApiClient.authenticate`), `require_permission :read, :stack` passes because the token has `read:stack`, and `stack` resolves Stack B directly via `Stack.from_param!` — bypassing the `stacks` scope that would have restricted lookups to Stack A only.
4. The response renders Stack B's latest deploy/rollback status (`shipit/ccmenu/project` XML), even though the token was only ever authorised for Stack A.

*Note: I was unable to fully verify from the index alone whether every deployed instance actually issues stack-scoped tokens outside the admin UI (`ApiClientsController`), since the built-in `CCMenuUrlController#client` currently creates unscoped clients; however, the vulnerable code path exists in the engine itself and is reachable by any stack-scoped token created through the standard `ApiClientsController` admin UI, which is in-scope engine code.*

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
