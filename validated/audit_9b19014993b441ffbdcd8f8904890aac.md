### Title
CCMenu API tokens are never bound to a stack, allowing any leaked CCMenu URL to read any stack's status - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb, app/models/shipit/api_client.rb)

### Summary
`ApiClient#check_permissions!` only checks the `permissions` array by string membership (`"read:stack"`) and never compares `ApiClient#stack_id` to the requested stack. This is compounded by two concrete facts in this engine: `CCMenuUrlController#client` mints a single, stack‑agnostic `ApiClient` per user (never setting `stack:`), and `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of the stack‑scoped `stacks.from_param!` helper used elsewhere. The result is that a CCMenu token minted while viewing stack A's CI badge works unmodified against any other stack B.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` (or `stack_id` unset only for globally‑scoped clients created by an operator), for every request gated by `require_permission :read, :stack`.

Trace:
- `CCMenuUrlController#client` [1](#0-0)  creates/reuses an `ApiClient` keyed only by `creator` and `name: 'CCMenu Client'`, with `permissions: %w[read:stack]`. It never sets `stack:`, so `ApiClient#stack_id` is `nil` for this token, regardless of which stack the user was viewing when they requested the CCMenu URL.
- `Api::CCMenuController` requires `:read, :stack` [2](#0-1)  and authenticates via `ApiClient.authenticate(params[:token])` [3](#0-2) , then resolves the target stack with its own override: `Stack.from_param!(params[:stack_id])` [4](#0-3) , bypassing the base controller's `stacks` scoping helper (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) that other API controllers like `Api::StacksController#stack` rely on (`stacks.from_param!`) [5](#0-4) [6](#0-5) .
- `ApiClient#check_permissions!` only checks `permissions.include?("read:stack")`; it never inspects `stack_id` at all [7](#0-6) .

Consequently, `require_permission!` → `check_permissions!('read:stack')` returns `true` for any stack ID in the URL, because the permission string is not stack-specific and the CCMenu controller doesn't even consult the (also-broken) `stack_id` scoping mechanism. Root cause: (1) the CCMenu client is never associated with a stack at creation time, and (2) even the generic per‑client stack-scoping mechanism present in `BaseController#stacks` is not used by `CCMenuController`. Existing guards (`require_permission`, `authenticate_api_client`) check only credential validity and coarse permission strings, not stack identity, so they do not prevent the divergence. This is entirely within-engine code; no GitHub secrets are required — only the URL itself, which the feature explicitly designs to be pasted into third-party dashboards.

### Impact Explanation
Any party holding one CCMenu URL (by design semi-public, meant for external CI dashboards) can substitute an arbitrary `stack_id` in the URL and read that stack's CI status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, deploy history via `stack.deploys_and_rollbacks`) for every stack in the installation, without a Shipit session or any stack-specific credential. This is a cross-tenant confidentiality break: `read:stack` becomes effectively "read all stacks" instead of "read the one stack the token was minted for." It matches **High – unauthenticated read of stack state**. It does not escalate to deploy/rollback since the token's `permissions` array only contains `read:stack`, so `deploy:stack`/`lock:stack` checks still fail for other endpoints.

### Likelihood Explanation
Preconditions are low: a legitimate Shipit user only needs to generate one CCMenu URL for any stack they can view (a normal, intended action of the feature), and that URL (containing the bearer token in the query string) is exactly the kind of artifact meant to be shared/pasted externally per the feature's own design. No `Shipit.github_teams` membership, no operator role, and no secrets are needed by the attacker who obtains the URL — only substitution of `stack_id` in the query string, which is a trivial, repeatable, unauthenticated HTTP GET against `Api::CCMenuController#show` for any stack in the installation.

### Recommendation
- In `ApiClient#check_permissions!`, accept and enforce a `stack` argument and compare it against `stack_id` when the latter is present, e.g. raise `InsufficientPermission` unless `stack_id.nil? || stack_id == stack.id`.
- In `CCMenuUrlController#client`, always associate the created `ApiClient` with the specific `stack` being viewed (`ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, name: "CCMenu Client (#{stack.to_param})")`) instead of sharing one stack-agnostic client per user.
- In `Api::CCMenuController`, replace the `stack` override with the scoped lookup used elsewhere (`stacks.from_param!(params[:stack_id])`) so that `current_api_client.stack_id` scoping (already present in `BaseController#stacks`) is actually enforced.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual addition)
test "a CCMenu token minted for stack A cannot read stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar'), branch: 'main')

  # Simulate CCMenuUrlController#fetch for stack_a as a logged-in user
  user = shipit_users(:walrus)
  client = ApiClient.create_with(permissions: %w[read:stack])
                     .find_or_create_by!(creator: user, name: 'CCMenu Client')
  token = client.authentication_token

  get :show, params: { stack_id: stack_b.to_param, token: token }

  # Binding under test: client.stack_id (nil/unbound) vs stack_b.id
  assert_not_equal client.stack_id, stack_b.id
  assert_response :forbidden # currently fails: actual response is 200 OK, proving the bug
end
```
This demonstrates that a token minted without ever being restricted to `stack_a` (or any stack) successfully authorizes reads against an unrelated `stack_b`, confirming the missing `stack_id == stack.id` binding.
