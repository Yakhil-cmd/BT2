### Title
Externally-inflated stake-account lamports can desync the cached `Delegation::stake` from the account's true balance, causing an `assert_eq!` panic during epoch-reward distribution - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
This is the closest reachable analog to the Ninja Vaults bug: a cached, double-accounted balance field (`user.amount` in Ninja / `Delegation::stake` in Agave) that can be desynchronized from the real, externally-manipulable balance (vault token balance / stake-account lamports) by an attacker directly sending funds to the account, and then an unguarded arithmetic assumption (overflow in `withdraw()` / `assert_eq!` in `build_updated_stake_reward`) that fires on the mismatch.

### Finding Description
`build_updated_stake_reward` in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs:239-294` computes the post-reward stake state for every stake account during partitioned epoch-reward distribution. It reads the *current* cached delegation for the pubkey from `stakes_cache_accounts` (`stake.delegation.stake`) and separately reads the *pre-computed* reward result `partitioned_stake_reward.inflation.stake` (`new_stake`), which was computed earlier, during the "calculation" phase (`calculate_stake_rewards_and_commissions` / `redeem_delegation_rewards`, see `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:610-701,775-904`). [1](#0-0) 

When the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is *not* active, the code does not reconcile these two independently-obtained values against the account's actual lamports; instead it defends the invariant with a hard `assert_eq!`:
```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, "stake reward delegation must be consistent with the updated stake account lamport balance");
```
This is structurally the same pattern as the Ninja Vaults bug: two values that are supposed to represent "the same underlying quantity" (`Delegation::stake`, and lamports actually held) are tracked/derived separately, and one of them (`stake.delegation.stake`, freshly read from `stakes_cache_accounts` at distribution time) is influenced by state that can change between the *calculation* snapshot and the *distribution* execution, which spans multiple blocks (`REWARD_CALCULATION_NUM_BLOCKS`, partitioned over `distribution_starting_block_height`, see `runtime/src/bank/partitioned_epoch_rewards/distribution.rs:78-171`).

Importantly, the codebase's own tests confirm that plain lamport transfers into a stake account *are* explicitly allowed during the active rewards period (`runtime/src/bank/partitioned_epoch_rewards/mod.rs:1082-1092`, `test_rewards_period_system_transfer`), and the comment on `store_stake_accounts_in_partition` only asserts that "further state mutation [is] prevent[ed] by stake-program restrictions" for *stake-program instructions* — it does not claim protection against plain system-program lamport transfers, nor does it protect against the stakes-cache being reloaded/recalculated (`recalculate_partitioned_rewards_if_active`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1011-1095`) picking up a different in-flight state of the account than what was captured in `partitioned_stake_reward`. [2](#0-1) 

### Impact Explanation
`assert_eq!` in Rust panics the thread on failure. In `Bank::distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward`, this call is inline in bank-processing code executed by every validator at the epoch boundary. A panic here is not a per-transaction `InstructionError` that can be gracefully rejected — it is a process-level panic in core bank/consensus-critical code, which would crash the validator process (or, if triggered non-deterministically depending on cache/fork state, could cause cross-node divergence at the exact same epoch boundary on all nodes, i.e., a network-wide halt). This matches the allowed "epoch-boundary halt" / "cross-node state divergence" impact categories.

### Likelihood Explanation
This requires the `!adjust_delegations_for_rent` code path (i.e., before `relax_post_exec_min_balance_check` activation) and precise timing of stake-account state mutation/reload between the calculation snapshot and the distribution store step, which spans multiple blocks. The investigation could not conclusively determine (within the available index) an exact reachable sequence of ordinary, unprivileged instructions that changes `stakes_cache_accounts` for a given pubkey in the multi-block window between reward calculation and reward storage in a way that breaks the invariant, given that stake-program instructions are stated (in code comments) to be restricted during the reward interval. Confidence in exploitability is therefore Low/Uncertain, and should be verified with a live Devin session that can trace `stake_processor` instruction gating logic against `epoch_reward_status` and the `recalculate_partitioned_rewards_if_active` reload path across fork/root transitions.

### Recommendation
Replace the `assert_eq!` invariant check in `build_updated_stake_reward` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:284-294`) with a graceful `Result`/`DistributionError` return path (as already used for the `ArithmeticOverflow` and `AccountNotFound` cases in the same function), so that any unexpected divergence between the cached delegation and the pre-computed reward record is handled by burning/skipping that specific reward rather than panicking the bank thread. Additionally, audit and explicitly document/guarantee (with a compile-time or runtime check, not just a comment) that no external mutation path — including plain lamport transfers, cache recalculation on fork switches, and snapshot restores — can alter a stake account's cached delegation between the reward-calculation snapshot and the corresponding reward-distribution store for that account.

### Proof of Concept
Not fully constructible from the indexed code alone; the existing test `test_delegation_adjustment_at_distribution` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:1214-1293`) demonstrates that lamports *can* be transferred into a stake account between reward calculation and distribution, and that the `adjust_delegations_for_rent == true` path handles this gracefully. No equivalent test exists demonstrating the `adjust_delegations_for_rent == false` `assert_eq!` path under a mid-window state divergence for `stake.delegation.stake` — a Devin session with full checkout/build access would be needed to attempt to construct a fork-switch / cache-recalculation scenario (`recalculate_partitioned_rewards_if_active`) that reproduces the panic and confirm whether stake-program instruction gating actually forecloses this path.
