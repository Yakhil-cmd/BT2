### Title
Stack-scoped API token bypasses its own stack restriction on the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by `Shipit::Api::BaseController` in a way that drops the stack-scoping check that is supposed to bind an `ApiClient`'s token to the single stack it was issued for.

### Finding Description
`Shipit::Api::BaseController` enforces stack scoping for any `ApiClient` that has a `stack_id` set (i.e. tokens created for a single stack, such as those minted by the CCMenu URL flow) by resolving the target stack only from the client's own permitted collection: [1](#0-0) 

`ApiClient#check_permissions!` only checks whether the requested operation/scope string (e.g. `read:stack`) is present in the client's `permissions` array — it never checks which stack the token is scoped to: [2](#0-1) 

So the *only* place that binds "the stack this token authorizes" to "the stack actually returned/acted upon" is the `stacks`/`stack` method in `BaseController`. `Shipit::Api::CCMenuController`, however, overrides `stack` to bypass that scoped collection entirely and resolve directly from all stacks: [3](#0-2) 

This is exactly the "inconsistent verification" bug class from the report: two code paths are supposed to enforce the same binding (`token.authorized_stack == stack_acted_upon`), but only one of them (`BaseController#stack`) actually does, while the other (`CCMenuController#stack`) silently drops it, similar to how depositors' fee-update signature was checked correctly on one chain but validated inconsistently on the other.

Concretely: an attacker who possesses/creates any valid `ApiClient` token scoped to `stack_id: A` with the `read:stack` permission (a very low bar — such a client is created automatically and shown to any user via `CCMenuUrlController#fetch`, see `client = ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)`), can call `GET /api/stacks/:stack_id/ccmenu.xml` with `stack_id` pointing to a *different* stack `B`. `require_permission :read, :stack` only verifies `permissions.include?('read:stack')` — true for the token — and `CCMenuController#stack` resolves `B` directly via `Stack.from_param!`, ignoring that the token was only supposed to authorize stack `A`. [4](#0-3) 

### Impact Explanation
This lets a holder of a narrowly-scoped, low-privilege token (`read:stack` on stack A) read build/deploy status data (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`) for any other stack in the Shipit installation, including stacks belonging to other repositories/teams that the token was never meant to see. This matches the "unauthenticated read of stack state" High-impact category described in scope, since the token is not truly "authenticated" for stack B — the per-stack authorization binding is broken.

### Likelihood Explanation
Likelihood is high for any environment issuing stack-scoped tokens (the built-in CCMenu integration does so automatically for any logged-in user via `CCMenuUrlController#fetch`), because exploitation requires no special privilege beyond already holding one such scoped token — an artifact any user with stack access can generate for themselves.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the stack-scoping check performed for every other API controller is also applied here.

### Proof of Concept
1. As user U, visit stack A's CCMenu URL page; Shipit auto-creates/reuses an `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and `stack: A` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`).
2. Obtain that client's `authentication_token` (exposed by the `ccmenu_url` JSON response as a query parameter, or via the API client show page for a short window per `app/helpers/shipit/api_clients_helper.rb`).
3. Issue `GET /api/{other-owner}/{other-repo}/{other-env}/ccmenu.xml?token=<token_scoped_to_A>` targeting stack B, which the token was never scoped to.
4. `require_permission :read, :stack` passes because the token has `read:stack` in its permissions list; `CCMenuController#stack` resolves stack B directly via `Stack.from_param!`, bypassing the `stacks` scoping that `BaseController` would have applied, and the response leaks stack B's build/deploy status.
