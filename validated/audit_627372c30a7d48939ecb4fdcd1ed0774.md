### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled`, causing an unauthorized `ReviewStack` to be created and provisioned, which in turn makes an installation-authenticated GitHub API call on the attacker's behalf - (`File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/pull_request.rb`)

### Summary
`Repository#review_stacks_enabled` is intended to be a master switch gating all review-stack provisioning, but `OpenedHandler#provision?` (and identically `ReopenedHandler#unarchive?`) combines it with the provisioning-behavior checks using `&&`/`||` in a way that Ruby only applies `review_stacks_enabled` to the `allow_all?` branch. When a repository has `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, any PR author who applies the provisioning label still triggers `ReviewStackAdapter#create!`, which builds a `PullRequest` and calls `github_pull_request=`, which calls `find_or_create_commit_from_github_by_sha!`, which uses `stack.github_api`/`stack.github_repo_name` (the target repo's real installation credentials) to fetch commit data for the attacker-supplied SHA.

### Finding Description
The claimed binding is: `stack.github_api used to fetch commit data == credentials of a repository whose review-stack provisioning was actually approved (repository.review_stacks_enabled == true)`. This binding is broken.

Root cause, in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

In Ruby, `&&` binds tighter than `||`, so this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` only gates the `allow_all?` branch; it is never consulted for the `allow_with_label` or `prevent_with_label` branches. The identical pattern exists in `ReopenedHandler#unarchive?`. [2](#0-1) 

Exploit path: an attacker who can open a PR on a public repository configured with `review_stacks_enabled: false, provisioning_behavior: allow_with_label` opens a PR from their own fork and applies the repo's provisioning label (any collaborator/PR-author-controlled label on their own PR, or via the GitHub `pull_request` webhook payload directly if signature checks are otherwise satisfied by GitHub itself sending the event). `OpenedHandler#process` calls `provision?`, which returns `true` despite `review_stacks_enabled` being `false`, and invokes `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`. [3](#0-2) 

`ReviewStackAdapter#create!` creates the stack and calls `stack.build_pull_request.update!(github_pull_request: params.pull_request)`: [4](#0-3) 

`PullRequest#github_pull_request=` then calls `find_or_create_commit_from_github_by_sha!(github_pull_request.head.sha)`, and on cache miss this calls `stack.github_api.commit(stack.github_repo_name, sha)`, using the target repository's own GitHub App installation credentials to resolve the attacker-supplied `head.sha`: [5](#0-4) 

Finally, `ReviewStackProvisioningQueue.add(stack)` is called, queuing the unauthorized stack for actual provisioning/deployment. [6](#0-5) 

None of the existing guards catch this: `verify_signature`/webhook signature checks only authenticate that GitHub sent the event, not that the repo opted into review stacks; `respond_to_pull_request_opened?` delegates entirely to the broken `provision?`; and there is no separate check anywhere else in the call chain that re-verifies `review_stacks_enabled` before `find_or_create!`/`create!` runs.

### Impact Explanation
For any repository misconfigured as `review_stacks_enabled: false` with `provisioning_behavior: allow_with_label` (or `prevent_with_label`), an unprivileged PR author can force Shipit to: (1) create a `ReviewStack`/`PullRequest` record it should never have created, (2) make an authenticated GitHub API call using that repository's real GitHub App installation token to fetch attacker-chosen commit data, and (3) enqueue the stack for actual provisioning (`ReviewStackProvisioningQueue.add`), which drives real deploy-host provisioning actions (`stack.provisioner.up` via the state machine). This matches the "unauthorized deploy" Critical category, since it results in deploy-host actions being taken for a repository that explicitly disabled review-stack provisioning. It is repeatable against any repository sharing this specific configuration combination, and the blast radius is bounded to that misconfigured repository (not cross-tenant), but is fully attacker-repeatable with no privileges beyond opening/labeling a PR.

### Likelihood Explanation
Requires a specific but plausible repository configuration: `review_stacks_enabled: false` combined with `provisioning_behavior_allow_with_label` (or `prevent_with_label`). Given the UI/settings expose `review_stacks_enabled` as an independent toggle from `provisioning_behavior`, and the intent is clearly for `review_stacks_enabled: false` to disable provisioning outright regardless of the label behavior, this is a realistic misconfiguration/expectation mismatch rather than an exotic edge case. Attacker cost is trivial: open a PR and add a label (which many public-repo workflows allow external contributors to do, or which triggers automatically via `pull_request` payload labels present at open time).

### Recommendation
Fix the boolean grouping in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` to require `review_stacks_enabled` unconditionally:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same parenthesization fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, not to be placed under out-of-scope `test/**` for delivery but described for the fix's verification):
1. Create a `Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: "allow_with_label"`, `provisioning_label_name: "ship-it"`.
2. Build webhook `params` for `action: "opened"` with `pull_request.labels: [{ name: "ship-it" }]` and `pull_request.head.sha` set to an attacker-controlled value.
3. Stub/mock `stack.github_api` (or the underlying `Shipit::GithubApi`/Octokit client returned by `github_api` for the repo) and assert `.commit(repository.github_repo_name, attacker_sha)` **is called** before the fix and **is not called** (because `find_or_create!`/`create!` is never reached) after the fix — i.e., assert `Shipit::ReviewStack.count` and `Shipit::Repository#review_stacks.count` remain `0` and no API call occurs when `review_stacks_enabled: false`.
4. Assertion pair: before fix, `OpenedHandler.new(params).process` results in `repository.review_stacks.exists?(environment: "pr#{params.number}") == true`; after fix, it must equal `false`, matching the documented binding `stack provisioning approved == repository.review_stacks_enabled`.
