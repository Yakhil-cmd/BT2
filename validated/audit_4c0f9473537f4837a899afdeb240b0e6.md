### Title
Webhook signature is validated against the organization derived from an attacker-controlled `repository.owner.login` field while `MembershipHandler` grants team membership based on a separately attacker-controlled `organization.login` field, allowing forged team membership and bypass of `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` first, falling back to `params.dig('organization', 'login')` only when no `repository` key is present. [1](#0-0)  Meanwhile `MembershipHandler#process`, which is invoked with the same raw JSON body after signature verification, derives the `Team`'s authorization-relevant organization from a *different* field, `params.organization.login`, and adds the attacker-supplied `member.login` to that team. [2](#0-1)  These are two independent JSON fields in the same attacker-supplied payload, and the field that gates *which secret validates the signature* is not the field that determines *which organization's team gets the membership write*.

### Finding Description
GitHub's real `membership` webhook payload has no `repository` key (it is an org-scoped event), so in normal operation `repository_owner` falls back to `organization.login` and the two fields coincide. However, the controller does not enforce that a `membership` event payload must omit `repository`, nor does it cross-check that the `organization.login` used by the handler matches the organization whose secret validated the signature. An attacker who legitimately controls (or has been granted access to) one Shipit-configured GitHub organization/App — call it `OrgA`, whose `webhook_secret` they know because they administer that org's GitHub App installation — can craft a JSON body for the `membership` event that includes both:

- `"repository": {"owner": {"login": "OrgA"}}` — causes `verify_signature` to select `OrgA`'s `webhook_secret` for HMAC validation. [3](#0-2) [4](#0-3) 
- `"organization": {"login": "victim-org"}`, `"team": {...}`, `"member": {"login": "attacker-login"}` — processed by `MembershipHandler`, which creates/updates a `Team` scoped to `"victim-org"` and adds the attacker as a member via `team.add_member(member)`. [2](#0-1) 

Because the attacker computes the HMAC-SHA1 signature themselves (they know `OrgA`'s secret and construct the exact raw body), `verify_signature` passes, and the payload is then dispatched to all handlers registered for the `membership` event, unmodified. [5](#0-4)  This is the same class of bug as the Sherlock H-7 finding: a value used to gate/validate an operation (`totalSupply` used for the threshold check) is not the same value that the downstream logic actually depends on (`virtualSupply`, the real circulating amount) — here, the field used to select/validate the signing secret (`repository.owner.login`) is not the field the sensitive write actually keys off of (`organization.login`), breaking the intended binding "organization that authenticated" == "organization whose Team/Membership records are written."

### Impact Explanation
`Team`/`Membership` records populated by this webhook are the same records used by `User#authorized?` to gate access to the entire Shipit application: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`. [6](#0-5)  If `Shipit.github_teams` is configured (restricting access to members of specific org/teams, e.g. `shopify/developers`) an attacker who controls any one Shipit-registered organization can forge a `membership` webhook that adds their own GitHub login as a member of the privileged team belonging to a *different, victim* organization, without ever being a real member of that org or team. This directly escalates the attacker into `Shipit.github_teams` authorization, granting them access to the Shipit UI/API for stacks belonging to the victim organization — one of the explicitly in-scope High-impact outcomes.

### Likelihood Explanation
This requires the attacker to know the `webhook_secret` of at least one organization configured in the Shipit instance's `Shipit.github` config (i.e., they are a legitimate but unprivileged party for `OrgA`, not for the victim org). Given that requirement is satisfiable without any GitHub App private key, `ApiClient` token, or Shipit session — only knowledge of a single org's webhook secret, which is routinely known to org admins/CI operators of that org — the likelihood is realistic in multi-organization Shipit deployments (the engine explicitly supports and documents multiple GitHub organizations with independent secrets, per `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`).

### Recommendation
Do not let `repository_owner`/signature-org-selection be derived from a field that can diverge from the field the handler actually trusts for the write. Specifically:
- For `membership` (and any other org-scoped) events, always resolve the signing organization from `organization.login`, never from `repository.owner.login`, regardless of whether a `repository` key happens to be present in the body.
- After selecting the signing organization, assert that it equals the organization the handler will act upon (`params.organization.login` for `MembershipHandler`, `repository.owner.login` for repo-scoped handlers) before dispatching to `handler.call(params)`, rejecting the request if they differ.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `victim-org`, each with its own `webhook_secret` (as supported by `Shipit.github`). [7](#0-6) 
2. Attacker knows `OrgA`'s `webhook_secret` (e.g., they administer `OrgA`'s GitHub App/webhook config).
3. Attacker crafts the JSON body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "OrgA"}},
  "organization": {"login": "victim-org"},
  "team": {"id": 999, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "member": {"login": "attacker-github-login"}
}
```
4. Attacker computes `sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: membership` and `X-Hub-Signature: sha1=<computed>`.
5. `verify_signature` computes `repository_owner` as `"OrgA"` (from `repository.owner.login`), fetches `Shipit.github(organization: "OrgA")`, and validates the signature successfully since the attacker signed with the correct (`OrgA`) secret. [3](#0-2) 
6. `create` dispatches to `MembershipHandler`, which creates/finds `Team` with `organization: "victim-org"` and adds `attacker-github-login` as a member. [2](#0-1) 
7. If `Shipit.github_teams` includes `victim-org/developers`, the attacker's `User#authorized?` now returns `true`, granting them access to the Shipit application for stacks gated by that team. [6](#0-5)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
