### Title
`Shipit::User.find_or_create_by_login!` binds identity to a mutable login string, letting a webhook verified for one GitHub org attach `Shipit::Membership` rows to an unrelated pre-existing `User` - (File: app/models/shipit/user.rb)

### Summary
`Shipit::User` has no uniqueness constraint on `login` or `github_id`, and `Shipit::Webhooks::Handlers::MembershipHandler#process` resolves the webhook's `member.login` through `User.find_or_create_by_login!`, which matches purely on the `login` string column rather than the immutable `github_id`. Because GitHub allows login reuse after a rename, an attacker who controls their own organization (and therefore its `webhook_secret`) can rename their account to a login string that collides with an existing Shipit `User` row and cause a real `membership` webhook to attach a new `Shipit::Membership` to that unrelated, pre-existing user.

### Finding Description
The broken binding is: `Shipit::User` row resolved by `login` == the GitHub account that currently owns that login string. This does not hold once GitHub login reuse is possible, because `Shipit::User` enforces no uniqueness on `login` (nor `github_id`) [1](#0-0) .

The call path is: `WebhooksController#create` dispatches the `membership` event to `Shipit::Webhooks::Handlers::MembershipHandler` [2](#0-1) . `MembershipHandler#process` calls `team = find_or_create_team!` (keyed on `params.team.id`, the numeric GitHub team id) and then `member = User.find_or_create_by_login!(params.member.login)`, followed by `team.add_member(member)` for `added` events [3](#0-2) .

`find_or_create_by_login!` performs `find_or_create_by!(login:)`, which matches any existing `Shipit::User` row whose `login` column equals the payload string, with no check against `github_id` [4](#0-3) . `Team#add_member` then creates a `Shipit::Membership` row linking the team to whatever `User` row was returned [5](#0-4) .

Signature verification (`WebhooksController#verify_signature`) selects the HMAC secret to check via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization','login')` for membership events [6](#0-5) . Verification only proves the payload is a genuine event from the attacker's own organization; it says nothing about the identity binding of `member.login` to a specific `github_id`. `ExplicitParameters` only requires `member.login` be a `String` [7](#0-6) , and there is no `find_by(github_id:)` fallback or ID cross-check anywhere in this path.

Exploit flow: attacker owns an org (e.g. `attacker-org`) and has its `webhook_secret` because they configured it themselves. They rename their GitHub account's login to `target`, which collides with an already-existing, privileged `Shipit::User` row (`login: 'target'`) created earlier through a legitimate flow. GitHub then emits (or the attacker replays/synthesizes, self-signed with their own secret) a genuine `membership` `added` webhook with `member.login = 'target'`. `find_or_create_by_login!('target')` matches the pre-existing row instead of creating/keying off a fresh `github_id`, and `team.add_member` writes a `Shipit::Membership` connecting the attacker's team to that unrelated `User` row.

### Impact Explanation
The concrete, demonstrable effect is that a webhook payload cryptographically verified only for the attacker's own organization is able to write a `Shipit::Membership` row against a `Shipit::User` record it has no legitimate relationship to — a cross-tenant mutation of team/membership data, matching the "payload for one [tenant] mutating another's ... team" category. This corrupts the affected user's team graph (extra, illegitimate membership entries), which can affect UI displays of team membership and any code relying on `teams`/`memberships` associations for that user. Note, however: because `Shipit::User#authorized?` only checks intersection with the operator-configured `Shipit.github_teams` list [8](#0-7) , and the attacker's own team is not in that list, this specific exploit path (as literally described — renaming and matching by login only) does not by itself grant escalation into `Shipit.github_teams`; the demonstrable impact is unauthorized, cross-tenant data mutation of the `Membership` model, not privilege escalation. The `removed` action path is not separately exploitable here since the attacker's team never legitimately held a prior membership to the victim user to delete.

### Likelihood Explanation
Preconditions are attacker-cheap: own any GitHub organization (free), install/configure its webhook, and rename the account's login to collide with a target's `login` in the Shipit database (feasible because GitHub frees up old logins on rename, and Shipit `login` values are often knowable from stack/commit pages). No Shipit secrets, sessions, or `Shipit.github_teams` membership are required — only the attacker's own legitimately-provisioned `webhook_secret`. The action is repeatable against any `login` string present in the `shipit_users` table, for as long as the attacker controls an org with hook access to the Shipit instance.

### Recommendation
Bind `Shipit::User` identity to the immutable `github_id`, not the mutable `login`. In `MembershipHandler#process`, resolve/create the member via a `github_id`-first lookup (e.g. fetch the GitHub user by login through the API to get `id`, then use `User.find_or_create_from_github`, falling back to `login` only for creation, never for matching). Additionally add a uniqueness validation/index on `Shipit::User#github_id` (and ideally on `login`) to prevent divergent rows and surface collisions instead of silently reusing a stale record.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook cannot attach a Membership to a User keyed by github_id mismatch" do
  privileged_user = Shipit::User.create!(login: 'target', name: 'Real Target', github_id: 999_999)

  payload = {
    'action' => 'added',
    'team' => { 'id' => 555, 'name' => 'Attacker Team', 'slug' => 'attacker-team', 'url' => 'https://example.com' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'target' } # attacker renamed their account to this login
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  membership = Shipit::Membership.find_by(team: Shipit::Team.find_by(github_id: 555), user: privileged_user)

  # Assert the binding is broken: the pre-existing privileged user (by login string)
  # received a Membership from an unrelated org's team, instead of a fresh User
  # keyed on the real webhook-reported github id being created.
  assert membership, "Expected Membership to have been incorrectly attached to the pre-existing 'target' User"
  assert_equal privileged_user.id, Shipit::User.find_or_create_by_login!('target').id
  refute_equal 999_999, payload['member']['id'] # no github_id in payload was ever cross-checked
end
```
