## Title
Cross-Organization Webhook Spoofing via Signature/Payload Repository Mismatch in Multi-Org Deployments - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
In a multi-GitHub-App-organization deployment (`config/secrets.yml` `github:` keyed by organization, as configured in `test/dummy/config/secrets_double_github_app.yml`), the webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but the actual repository/stack that gets mutated by the handlers is looked up using the unrelated `repository.full_name` field. This breaks the equality: `organization whose webhook_secret authenticated the request == organization whose repository is written`.

## Finding Description
`WebhooksController#verify_signature` selects the GitHub App config to verify against solely from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` loads that organization's config and calls `verify_webhook_signature`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` whenever `webhook_secret` is blank for that organization: `return true unless webhook_secret`. In the maintainers' own multi-org fixture, `OrgTwo` is configured with `webhook_secret: # nil`: [4](#0-3) 

Meanwhile, once the request passes `verify_signature`, none of the event handlers re-check `repository.owner.login`. Instead, `Handler#stacks` resolves the target `Repository`/`Stack` using `repository.full_name`, a completely separate JSON field that was never bound to the signature check: [5](#0-4) [6](#0-5) 

Consequently, an unprivileged external attacker who can reach `/webhooks` needs only to set `repository.owner.login` (or `organization.login`) to an organization configured in Shipit with no `webhook_secret` (or one they can otherwise satisfy), while setting the unrelated `repository.full_name` to `victim-org/victim-repo` — an organization/repository that *does* have a real, secret-protected GitHub App. `verify_signature` authenticates the request against the harmless/unsecured organization (or trivially, since no HMAC is required there), yet `PushHandler` (and other handlers keyed off `repository.full_name`, e.g. `status`, `check_suite`, `pull_request` handlers) act on the victim organization's `Stack`, enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha`, forcing re-sync / cache invalidation cycles, and in the `membership` handler creating arbitrary `Team`/`User` records tied to a spoofed org login.

This is the same trust-binding violation class as the referenced Sui kiosk report: the field that is cryptographically verified (`repository.owner.login`, used to select the signing secret) is a different field from the one actually acted upon (`repository.full_name`), letting an attacker present credentials for a low-trust binding while directing effects at a high-trust target.

## Impact Explanation
This crosses the "unauthenticated read of stack state" / "cross-repository writes" boundary explicitly called out as in-scope: an attacker with no Shipit session, no `ApiClient` token, and no genuine webhook secret for the victim organization can force `GithubSyncJob` runs, `CacheDeploySpecJob` invalidation, and DB record creation (`Team`, `User`) scoped to a repository/stack they do not control, purely because Shipit's multi-organization webhook signature check is not bound to the field the handlers actually consume. In deployments running a single GitHub App organization this is mitigated (there's only one org/secret to select), but the multi-org configuration path is a first-class, documented feature (`Shipit.github_organizations`, `github_app_config`) and is exactly the case exercised by the engine's own `secrets_double_github_app.yml` fixture.

## Likelihood Explanation
Requires the operator to run Shipit with more than one GitHub App organization configured (a supported, documented, tested configuration) and at least one of those organizations to have no `webhook_secret` set (also demonstrated in-repo as a valid config state) — or, more generally, requires only that the attacker be able to obtain/guess the signature for *any one* configured organization, then mismatch `owner.login` vs `full_name` to redirect the effect to a different, better-protected organization/repo. No authentication, GitHub write access, or insider access is needed to reach the `/webhooks` endpoint itself.

## Recommendation
Bind the field used for signature-organization selection to the field used for repository/stack resolution: derive the organization strictly from the same `repository.full_name` (or an org identity mathematically tied to it) that handlers use, and reject requests where `repository.owner.login`/`organization.login` do not match the owner segment of `repository.full_name`. Additionally, do not treat a missing per-organization `webhook_secret` as automatic success when other organizations in the same deployment do have secrets configured; either require all configured organizations to set a secret or ensure a request lacking a secret can never affect a repository belonging to a secured organization.

## Proof of Concept
1. Deploy Shipit with multi-org GitHub App config where `OrgA` has a real `webhook_secret` and owns `OrgA/victim-repo` (tracked as a Shipit `Stack`), and `OrgB` has `webhook_secret: nil` (as in `secrets_double_github_app.yml`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
No `X-Hub-Signature` header is required, or any arbitrary value can be sent.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` short-circuits to `true` regardless of the signature header/value.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgA/victim-repo")`, matching the real `OrgA` stack, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha` for a repository the attacker never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
