### Title
Stack-scoped `ApiClient` tokens bypass stack authorization in `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` records can be scoped to a single `Stack` via their `stack_id` association, and `Api::BaseController` enforces that scoping when resolving which stacks a token may touch. `Api::CCMenuController` overrides the `stack` lookup method and bypasses this scoping entirely, so a token that is only authorized to read one stack can be used to read the build/deploy status of any stack in the installation.

### Finding Description
`ApiClient` supports an optional `stack` association used to restrict a token's authority to a single stack: [1](#0-0) . `Api::BaseController` implements the corresponding authorization boundary: when `current_api_client.stack_id?` is true, `stacks` is restricted to that one record, and `stack` is resolved through this scoped relation: [2](#0-1) 

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping and resolves the stack directly from the global `Stack` collection using only the request parameter: [3](#0-2) 

The `require_permission :read, :stack` declaration only checks that the token carries the generic `"read:stack"` permission string via `ApiClient#check_permissions!` [4](#0-3) ; it never verifies that the specific stack being accessed matches the token's `stack_id`. This is precisely the reported bug class: the value that is authorized/verified (the token's bound stack) is not the value that is actually acted upon (`params[:stack_id]`) after the controller re-derives the target — a "stack a token authorises versus a stack it touches" mismatch. The fixtures confirm stack-scoped tokens are a real supported configuration: `here_come_the_walrus` is created with `stack: shipit` and only `read:stack` permission, i.e., it is meant to see only that one stack: [5](#0-4) .

### Impact Explanation
Before the attack: a token bound to stack X (`stack_id` set) can only enumerate/read stack X (as enforced generically in `Api::BaseController#stacks`/`#stack`, and demonstrated by the `Api::StacksController` test "an api client scoped to a stack will only see that one stack" [6](#0-5) ). After the attack: by calling `Api::CCMenuController#show` with `stack_id` set to any other stack's param and the same token, the holder can read that other stack's deploy/build activity (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) even though the token was never granted access to that stack. This is an unauthorized read of stack state/deploy output across stack boundaries, using a deliberately narrow-scoped credential to reach data outside its authorized scope.

### Likelihood Explanation
Any legitimate, narrowly-scoped `ApiClient` (created for CCMenu-style integrations bound to one stack, a supported and tested configuration per the fixtures) can trivially escalate to reading every other stack's status simply by changing the `stack_id` URL parameter — no additional privilege, secret, or session is required beyond the token itself, which is exactly the credential the scoping mechanism was designed to constrain.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same scoped `stacks` relation used by `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the stack scoping enforced elsewhere in the API is not silently bypassed.

### Proof of Concept
1. An administrator issues an `ApiClient` scoped to `stack_id: X` with permission `read:stack` (e.g., analogous to the `here_come_the_walrus` fixture).
2. The token holder sends `GET /api/stacks/Y/ccmenu.xml?token=<token>` where `Y` is a different stack.
3. `Api::CCMenuController#authenticate_api_client` accepts the token, `require_permission :read, :stack` passes (permission name check only), and `#stack` returns `Stack.from_param!('Y')` regardless of the token's `stack_id`, disclosing stack Y's build/deploy status to a token never authorized for it.
