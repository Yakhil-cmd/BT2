### Title
Webhook signature verification is bound to the payload's `repository.owner`/`organization` field while the handlers act on `repository.full_name` — allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` derives *which* GitHub App/organization's `webhook_secret` to check against solely from `repository.owner.login` (or `organization.login`) inside the attacker-controlled JSON body, then uses that organization's secret to validate the HMAC signature. However, every webhook `Handler` (e.g. `PushHandler`, the `PullRequest::*` handlers) resolves the actual `Repository`/`Stack` to mutate from a *different* field of the same payload — `repository.full_name` — via `Handler#repository_name`/`Repository.from_github_repo_name`. Nothing ties the two fields together, and if the organization named in `repository.owner.login` has no `webhook_secret` configured, `verify_webhook_signature` short-circuits to `true` for *any* signature. This lets an attacker "authenticate" as an unprotected/secret-less organization while directing the actual repository-mutating logic at a completely different, protected organization's stack.

### Finding Description
`verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_webhook_signature` is a no-op when the target org has no configured secret:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Meanwhile every handler resolves the repository/stack to act on from a *separate* JSON field, not the one used for signature verification:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Since the controller and handlers each trust a different, independently-forgeable field of the same attacker-supplied JSON body, there is no requirement that `repository.owner.login` (used to select which secret validates the request) match the owner encoded in `repository.full_name` (used to select which `Stack` gets mutated). This is the same class of bug as the audit finding: a verification step checks one thing (a signature/attestor count) while the code that acts checks something else (an unvalidated, attacker-controlled value) — breaking the binding "organization that authenticated == repository that is written."

### Impact Explanation
An attacker who knows (or can enumerate/probe, since a 422 vs 200/204 response leaks which org has no secret) that some organization configured in this multi-tenant Shipit instance has no `webhook_secret` set (explicitly documented as optional in `docs/setup.md`, and modeled that way in `config/secrets.development.shopify.yml`) can craft a POST to `/webhooks` with:
- `repository.owner.login` = the org with no secret (or omit signature header entirely) → `verify_webhook_signature` returns `true` unconditionally,
- `repository.full_name` = `victim-org/victim-repo`, a repository/stack belonging to an org that *does* have a real secret configured.

This request passes `verify_signature` and is dispatched to handlers, which mutate/act on the victim stack: `PushHandler` triggers `stack.sync_github(expected_head_sha:)` [4](#0-3) , and the `PullRequest::*` handlers can archive/unarchive review stacks or capture PR label state for the victim repository [5](#0-4) . This is an unauthenticated write into another organization's/repository's tracked state — a cross-repository-write class impact — achieved without possessing the victim organization's webhook secret, GitHub App credentials, or any Shipit session.

### Likelihood Explanation
Exploitability requires only that at least one organization configured on the shared Shipit instance has no `webhook_secret` set — a state the project's own setup documentation calls out as "optional" [6](#0-5) , meaning this is a realistic, not hypothetical, configuration in multi-org deployments. No prior authentication, token, or repository access is needed; the attacker only needs to send a crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind signature verification and repository resolution to the same, single source of truth: verify the signature using the secret for the organization owning `repository.full_name` (not a separately-read `repository.owner.login`/`organization.login`), or reject any payload where `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, consider making `webhook_secret` mandatory (removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`) so a misconfigured/secret-less organization cannot be used as a signature-verification bypass for any other organization's repositories.

### Proof of Concept
1. Configure (or identify) two organizations in `Shipit.github` config: `unsecured-org` (no `webhook_secret`) and `victim-org` (real `webhook_secret`), with a tracked `Repository`/`Stack` for `victim-org/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or any arbitrary value), and body:
```json
{
  "repository": {"owner": {"login": "unsecured-org"}, "full_name": "victim-org/victim-repo"},
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `repository_owner` = `unsecured-org`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request is accepted with `head(:ok)`.
4. `PushHandler` then resolves the target stack via `repository.full_name` = `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, despite the request never being signed by `victim-org`'s webhook secret. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
