### Title
Cross-organization webhook signature confusion allows spoofing CI status / triggering syncs on other stacks - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a request against using a field (`repository.owner.login`, falling back to `organization.login`) taken from the same untrusted, attacker-controlled JSON body it is about to verify. The signature only proves the raw POST body was HMAC-signed with *that particular organization's* secret — it proves nothing about the other fields of the same body, such as `repository.full_name` (used by `PushHandler`) or `sha` (used by `StatusHandler`, which doesn't even check the repository at all). In a multi-organization Shipit deployment (`docs/setup.md`, "Using Multiple Github Applications"), an attacker who legitimately controls one low-value organization/app installation can forge a webhook body whose `repository.owner.login`/`organization.login` matches their own org (so the signature check passes using their own known secret) while every other field — repository full name, commit sha, state — targets a completely different, higher-value org/stack hosted on the same Shipit instance.

### Finding Description
`repository_owner` is computed purely from request JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . This value picks the `GitHubApp` (and thus the `webhook_secret`) used to validate `X-Hub-Signature` [2](#0-1) . The HMAC check itself, `verify_webhook_signature`, only proves the raw body was signed by *some* known secret — the secret it uses is chosen from a field inside that same unauthenticated body [3](#0-2) .

Once verification passes, the full (attacker-controlled) `params` object — not just the fields used for org selection — is dispatched unmodified to the registered handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . Handlers derive the target repository/stack from other, never-reverified fields of the same body:

- `PushHandler`/base `Handler#repository_name` reads `payload.dig('repository', 'full_name')` to locate `stacks` [5](#0-4) , independent of the org used for signature verification.
- `StatusHandler#process` is even more direct: it looks up `Commit.where(sha: params.sha)` **globally**, with no repository/stack scoping whatsoever, then calls `commit.create_status_from_github!(params)` [6](#0-5) .

The binding broken is: *organization that authenticated the request (via webhook secret) == organization/repository whose data is written*. Before the fix this binding is implicitly assumed to hold because in genuine GitHub-originated webhooks the `owner.login`/`full_name`/`sha` fields are internally consistent; it does not hold for a raw forged POST to `/webhooks`, because nothing after `verify_signature` re-checks that `repository.full_name`'s owner matches `repository_owner`, or that the commit found by `sha` belongs to a stack owned by the authenticating organization.

### Impact Explanation
`create_status_from_github!` feeds into `Commit#add_status`, which recomputes `status`/`deployable?` and can trigger `stack.schedule_merges` when the new status is `success` [7](#0-6) , and `deployable?` gates continuous delivery via `schedule_continuous_delivery` [8](#0-7) [9](#0-8) . Because `StatusHandler` looks up commits solely by `sha` with no ownership check, an attacker who legitimately controls the webhook secret for org A can spoof a `success` CI status for a commit sha belonging to a completely unrelated stack/org B on the same Shipit instance, and potentially trigger an unauthorized merge/continuous-deployment run for that victim stack. This matches the report's "Critical: unauthorized deploy/merge" impact class. `PushHandler` can similarly be pointed at any stack via a forged `repository.full_name`, triggering `GithubSyncJob`s against arbitrary stacks the attacker doesn't control.

### Likelihood Explanation
Exploitation requires the attacker to know a valid `webhook_secret` for at least one organization configured on the target Shipit instance (e.g., because they administer their own low-trust org/app installed on a shared multi-org Shipit deployment, as explicitly supported per `docs/setup.md`'s "Using Multiple Github Applications" section). This is a plausible but non-trivial precondition — it does not require any Shipit account, API token, or GitHub write access to the victim repository. Given that precondition, forging the HTTP request is trivial (just compute HMAC-SHA1 over an arbitrary chosen JSON body and pick the sha of a known/observable commit in the victim stack).

### Recommendation
- After verifying the signature, re-validate that every downstream identity field used by handlers (`repository.full_name`, `sha`'s owning stack, etc.) actually belongs to the same organization/repository that was authenticated (`repository_owner`), rejecting the payload otherwise.
- Scope `StatusHandler`'s `Commit.where(sha:)` lookup by the verified repository/stack rather than a bare global sha match.
- Consider binding the webhook secret 1:1 to a specific repository or resolving repository ownership from Shipit's own DB record (matched by an ID, not by attacker-supplied JSON) before running any handler.

### Proof of Concept
1. Attacker administers `org-attacker`, which has the Shipit GitHub App installed with a known `webhook_secret`, on a Shipit instance also hosting `org-victim/critical-repo`.
2. Attacker computes `sha1=HMAC(webhook_secret_attacker, body)` for a hand-crafted JSON body:
   ```json
   {
     "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/critical-repo" },
     "sha": "<known sha of a pending/blocked commit on org-victim/critical-repo>",
     "state": "success",
     "context": "ci/forged"
   }
   ```
3. POST this body with `X-Github-Event: status` and the computed `X-Hub-Signature` to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches `org-attacker`'s `GitHubApp`, and the signature check succeeds (attacker knows this secret) [2](#0-1) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (matching the victim's commit, regardless of stack/org) and records the forged `success` status, potentially unblocking deploy/merge for `org-victim/critical-repo` [6](#0-5) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
