### Title
StatusHandler#process globally scopes Commit lookups by `sha` alone, allowing a webhook for repository A to mutate commit status of repository B - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository scoping, unlike every other handler that resolves `Repository.from_github_repo_name(repository_name)&.stacks` via `Handler#stacks` before touching any records. Because `sha` values are not repository-scoped identifiers in Shipit's schema (any `Commit` row anywhere can have any sha), a webhook whose `repository.full_name` names the attacker's own repo but whose `sha` matches a `Commit` row belonging to an unrelated stack/repository will cause `create_status_from_github!` to run against that unrelated commit.

### Finding Description
The broken binding: for `StatusHandler`, the intended invariant analogous to other handlers would be `commit.stack.repository.full_name == payload.dig('repository','full_name')`. Tracing the code shows this equality is never established or checked.

- `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to handlers after `verify_signature`, which resolves `Shipit.github(organization: repository_owner)` from `payload.dig('repository','owner','login')` and calls `verify_webhook_signature` [1](#0-0) . This only proves the webhook was signed by the attacker's own organization's registered app/secret for the org named in the payload - it says nothing about which `sha` values are legitimate for that org, since `sha` is attacker-controlled JSON in the same request.
- `Handler#stacks` correctly derives the touched stacks from the payload's own repository name: `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) . Every handler that uses `stacks` is thereby confined to records belonging to the repository that was cryptographically bound to the webhook's signature.
- `StatusHandler#process`, however, never calls `stacks` or filters by `repository_name` at all - it queries `Commit.where(sha: params.sha)` across the entire `commits` table and calls `commit.create_status_from_github!(params)` on every match [3](#0-2) .
- `Commit#create_status_from_github!` writes a new `Status` row for that commit, then `add_status` recomputes `status`, emits `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` if the new status is success/pending [4](#0-3) [5](#0-4) . `schedule_continuous_delivery` on the commit model can also enqueue a `ContinuousDeliveryJob` for the *victim's* stack once the commit becomes `deployable?` [6](#0-5) .

Exploit flow: the attacker owns Repository A (registered on Shipit, so a webhook secret validates signatures for A's org). Repository B (victim, unrelated org/repo) has a `Commit` row with `sha` S - e.g., a shared vendored/submodule commit, or two forks with common history, or simply an attacker discovering a collision by inspecting any public commit that both repos happen to share (git history is shared across forks by design, so this is trivial to obtain deliberately, not merely as an edge case). The attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for org A, `repository.full_name = "attacker/A"`, and `sha = S`. `verify_signature` passes because the signature is valid for org A. `StatusHandler#process` then finds *all* `Commit` rows with `sha = S` - including B's row - and writes a status onto B's commit, potentially triggering `schedule_merges`/`ContinuousDeliveryJob` for stack B.

None of the listed guards catch this: `verify_signature` only authenticates the org in the payload, not the target commit rows; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of `sha`/`state`, not repository ownership; there is no `subset`/`url` validator or `require_permission!` check anywhere in this path; `Repository`/`Stack` model validations don't prevent two different repositories from having `Commit` rows with the same `sha` (there is no uniqueness constraint scoped globally on `sha`, only presumably per-stack).

### Impact Explanation
An attacker with only a Shipit-registered repository (or any repo whose org happens to be configured in Shipit) can write arbitrary CI status data onto a commit belonging to a completely different tenant/repository/stack, without ever authenticating against that victim repository. This can flip a victim commit's computed `status` (e.g., from pending/failure to success), which can cause `stack.schedule_merges` to run and, if continuous deployment is enabled on the victim stack, can lead to that commit being auto-deployed via `ContinuousDeliveryJob`. This is a payload for one repository mutating another's commit/stack state and potentially triggering an unauthorized deploy - matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius is systemic: it applies to any pair of repositories that ever share a commit sha (forks, common upstream history, vendored submodules, or even chosen intentionally by an attacker who forks or mirrors the victim's public repo and pushes the same commits into their own Shipit-tracked repo).

### Likelihood Explanation
Preconditions: attacker needs their own repository registered/configured with Shipit (so `verify_signature` succeeds for their org) - a low bar for any Shipit installation that supports self-service repo registration or has a shared GitHub App across many orgs. The attacker also needs a commit sha that also exists as a `Commit` row in the victim's stack; this is easy to obtain deliberately (fork the victim's public repo, or push identical history into their own tracked repo, then wait for/trigger `Commit` creation e.g. via a push webhook) since Shipit stores every discovered commit's sha per stack. No secrets, sessions, or privileged roles are required. This is fully repeatable against arbitrary target commits/stacks as long as the sha-sharing precondition is met, and the attacker fully controls when and how many times to send the crafted `status` webhook.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are scoped: resolve commits only within the stacks belonging to `Repository.from_github_repo_name(repository_name)` (i.e., use `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), mirroring `Handler#stacks`, instead of querying `Commit.where(sha: params.sha)` unscoped across all repositories.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative - actual file is out of scope per rules but describes the required assertions):

1. Create `repository_a = shipit_repositories(:shipit)` (or a new `Repository` with `full_name = "attacker/A"`) and `stack_a = create(:stack, repository: repository_a)`.
2. Create a distinct `repository_b` with `full_name = "victim/B"` and `stack_b = create(:stack, repository: repository_b)`.
3. Create `commit_a = create(:commit, stack: stack_a, sha: "deadbeef" * 5)` and `commit_b = create(:commit, stack: stack_b, sha: commit_a.sha)` - i.e., identical sha, different stacks/repositories.
4. Build a status payload: `{ 'sha' => commit_a.sha, 'state' => 'success', 'repository' => { 'full_name' => 'attacker/A' } }`.
5. Assert binding before: `commit_b.stack.repository.full_name != payload['repository']['full_name']` (i.e., `"victim/B" != "attacker/A"`).
6. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
7. Assert `commit_b.reload.statuses.last.state == "success"` - proving a payload naming only `attacker/A` mutated a commit belonging to `victim/B`, confirming the binding violation and cross-repository state corruption.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
