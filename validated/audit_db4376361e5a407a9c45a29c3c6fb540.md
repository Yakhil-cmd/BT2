### Title
Cross-repository forged CI status via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the commit to attach an incoming `status` webhook to purely by `Commit.where(sha: params.sha)`, with no check that the webhook's originating repository/org matches the commit's own `stack.repository`. An attacker who controls any GitHub repository configured as a Shipit stack can emit a legitimately-signed `status` webhook from their own org for a commit that happens to share a SHA with a victim's tracked commit (trivially true for forks of the same history), and Shipit will attach a `success` `Status` to the victim's `Commit`, flipping `Commit#deployable?` and triggering an unauthorized continuous deployment.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`Status.stack_id (== commit.stack_id, i.e. the victim's Shipit stack whose repository is being updated)` must equal `the GitHub org/repo that authenticated the inbound webhook (params.dig('repository','owner','login'), the attacker's own org)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` straight from the attacker-controlled payload (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) and verifies the HMAC signature against `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1)  This only proves the request was signed with the secret belonging to whichever org the attacker names in the payload — trivially true if the attacker owns that org/repo and lets real GitHub send the webhook for an event on their own repository.
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup across every stack/tenant, with no filter on repository. [3](#0-2)  Notably, the base `Handler` class already provides a `stacks`/`repository_name` helper scoped from `payload.dig('repository', 'full_name')` that other handlers (e.g. push, pull_request) use to scope by repository — `StatusHandler` never calls it. [4](#0-3) 
3. `Commit#create_status_from_github!` writes the status using the commit's *own* (victim) `stack_id`: `statuses.replicate_from_github!(stack_id, github_status)`. [5](#0-4)  `Status.replicate_from_github!` persists the attacker-supplied `state` (e.g. `success`) under that `stack_id`. [6](#0-5) 
4. The new `Status` record's `after_commit :schedule_continuous_delivery` delegates to `commit.schedule_continuous_delivery`. [7](#0-6) [8](#0-7) 
5. `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) flips to `true` once the forged `success` status lands and no other status blocks it. [9](#0-8)  `blocked?` only checks prior undeployed commits in the *same* stack for blocking statuses and is unaffected by the attacker's org. [10](#0-9) 

Attacker's exact action: register/own any repository that Shipit recognizes as a stack (or any org present in `Shipit.github_teams`/configured GitHub App so `Shipit.github(organization: repository_owner)` resolves), craft a commit whose SHA is identical to a targeted victim commit (deterministic in git — trivially achieved by forking the victim repository and sharing history, or by reproducing the exact tree/parents/author/committer/timestamps of a known public commit), then use the GitHub API/UI on their own repo to set a commit status (`state: success`) for that SHA. GitHub sends a validly signed `status` webhook naming the attacker's own repository; Shipit's signature check passes (correctly, for the attacker's own org), but `StatusHandler` then attaches that status to every `Commit` row across every tenant sharing that SHA — including the victim's.

Existing guards fail because: `verify_signature` only authenticates *which org sent the webhook*, not *which stack's commit the webhook is allowed to affect*; `drop_unhandled_event` and `ExplicitParameters` only validate payload shape (`sha`, `state`, etc.), not repository ownership; there is no model-level or handler-level check binding `Status#stack_id`/`Commit#stack_id` to the webhook's `repository_owner`/`repository_name`.

### Impact Explanation
A `Status` with `state: success` is written into a repository/stack that never authenticated it, and that status is load-bearing for `Commit#deployable?` and `Stack#next_expected_commit_to_deploy` / continuous delivery scheduling. [11](#0-10)  This lets an attacker who does not control the victim's CI pipeline cause the victim's stack to believe a commit passed CI and trigger an unauthorized deploy through continuous delivery — matching the "Critical: forged webhook authentication bypass leading to unauthorized deploy" category. The attack is repeatable against any stack/commit whose SHA the attacker can reproduce (any public fork relationship trivially shares SHAs across the common history), so the blast radius spans all tenants hosted on the same Shipit instance, not just one repository.

### Likelihood Explanation
Preconditions: the victim stack must have `continuous_delivery` enabled and not `ignore_ci`; the commit must currently be unlocked and only blocked by missing/absent success status (as stated). The attacker must own a repository whose org is configured/known to Shipit (so `verify_signature` resolves a real webhook secret) — a low bar in any multi-tenant Shipit deployment where many teams/orgs self-register repositories, and the SHA-sharing precondition is naturally satisfied for forked repositories or reproduced commit metadata, which is common. No Shipit session, API token, or GitHub App private key is required — only the ability to emit a real, GitHub-signed webhook for the attacker's own repository. This is inexpensive and fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the webhook's own repository, not by bare SHA: reuse the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) to restrict `Commit.where(sha: params.sha)` to `stacks.commits` (or equivalently check `commit.stack.repository.full_name == payload.dig('repository', 'full_name')`) before calling `create_status_from_github!`. Apply the same repository-scoping check inside `Commit#create_status_from_github!`/`Status.replicate_from_github!` as a defense-in-depth invariant so no future caller can bypass it.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (new)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook for the attacker's own repo must not mark a victim commit deployable" do
          victim_stack = shipit_stacks(:shipit) # repository owned by "shopify/shipit-engine"
          victim_commit = victim_stack.commits.create!(
            sha: "deadbeefcafefeed",
            message: "victim commit",
            author: shipit_users(:walrus),
            committer: shipit_users(:walrus),
            authored_at: Time.now,
            committed_at: Time.now
          )
          victim_stack.update!(continuous_delivery: true, ignore_ci: false)

          refute_predicate victim_commit.reload, :deployable? # binding LHS: no status yet

          # Attacker payload: repository/org is attacker's own ("attacker/evil-repo"),
          # but sha is identical to the victim's commit (shared history/fork).
          attacker_payload = ExplicitParameters::Parameters.new(
            sha: "deadbeefcafefeed",
            state: "success",
            context: "attacker/ci",
            description: nil,
            target_url: nil,
            created_at: Time.now.iso8601,
            branches: []
          )

          # simulate StatusHandler#process being invoked after signature verification
          # succeeded for the ATTACKER's org (attacker owns attacker/evil-repo),
          # not the victim's org.
          StatusHandler.new(attacker_payload).process

          # Binding check: Status.stack_id (victim_stack.id) must NOT equal a stack
          # whose repository never authenticated this webhook (attacker's repo).
          created_status = victim_commit.reload.statuses.last
          assert_nil created_status, "a status must not be written to a stack that did not own the sha's repository"

          refute_predicate victim_commit.reload, :deployable?
        end
      end
    end
  end
end
```
This test currently fails against the present code (the status IS created under `victim_stack` and `deployable?` flips to `true`), demonstrating the forged cross-repository status and the resulting unauthorized deploy path via `Stack#trigger_continuous_delivery`.
