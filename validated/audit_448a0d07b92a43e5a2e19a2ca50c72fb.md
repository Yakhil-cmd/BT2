### Title
Team membership webhook trusts an attacker-chosen `organization.login` and numeric `team.github_id` unbound from the webhook_secret that authenticated the request, enabling cross-organization privilege escalation into `Shipit.github_teams` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects a GitHub App config (and its `webhook_secret`) using a single attacker-influenced field — `repository_owner`, taken from `params.dig('repository','owner','login')` or, failing that, `params.dig('organization','login')` — and only proves the request was signed by *that* organization's secret. [1](#0-0)  The `membership` event handler, however, does not check that the team/organization it mutates has any relation to the organization whose secret validated the signature: it looks up or creates a `Team` purely by the numeric `github_id` supplied in the payload and adds the specified member to it. [2](#0-1)  Because `Team.find_or_create_by!` returns an existing record untouched when the `github_id` already exists, an attacker who controls (or spoofs) the webhook secret of *any* organization onboarded to the instance can add an arbitrary member to *any* pre-existing Team, including one listed in `Shipit.github_teams`, which directly gates application authorization via `User#authorized?`. [3](#0-2) 

### Finding Description
Shipit supports multiple GitHub organizations configured on the same instance, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`), and `Shipit.github(organization:)` resolves the right app config for signature verification. [4](#0-3)  The signature check is:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

This binds the HMAC verification to whichever organization the caller *declares* in the JSON body (`repository.owner.login`), not to the organization whose resources the payload actually mutates. The `create` action then dispatches the entire raw JSON to the event handler unmodified:

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

`Handlers::MembershipHandler#process` reads `params.organization.login` and `params.team.id` from the same payload, independently of `repository_owner`:

```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
end

def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [2](#0-1) 

`Team.find_or_create_by!(github_id: ...)` looks the team up solely by its numeric GitHub team ID. If a Team with that `github_id` already exists (as it will for any team already referenced in `Shipit.github_teams` and previously synced), the block populating `organization`/`slug` is skipped and the *existing* record is returned — its stored `organization` is never re-validated against the payload's `organization.login` or against `repository_owner`. `Team#add_member` then unconditionally appends the (possibly newly auto-vivified) `member`:

```ruby
def add_member(member)
  members.append(member) unless members.include?(member)
end
``` [7](#0-6) 

The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the Team/member record being written`

but the code only enforces:
`organization whose webhook_secret authenticated the request == params['repository']['owner']['login'] (an attacker-supplied string with no further use)`

Any actor who knows a valid `webhook_secret` configured on this Shipit instance for *some* organization (e.g., an org they legitimately administer, since this instance hosts multiple orgs, as shown by the multi-org secrets template) can:
1. Craft a `membership` event payload with `repository.owner.login` set to *their own* org (so signature verification passes with their known secret).
2. Set `team.id` to the `github_id` of a Team already tied to a `Shipit.github_teams` handle belonging to a *different, privileged* organization.
3. Set `member.login` to their own (or any) GitHub login and `action: 'added'`.

`User.find_or_create_by_login!` will fetch/create the corresponding `User` via `Shipit.github.api.user(login)` and `team.add_member(member)` adds it to the privileged Team. [8](#0-7)  Once that user then completes a normal GitHub OAuth login through `GithubAuthenticationController#callback`, `User#authorized?` evaluates true because the user is now a member of a team in `Shipit.github_teams`, bypassing the intended per-organization authorization gate. [9](#0-8) [10](#0-9) 

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization — explicitly listed as a valid High-impact outcome. An attacker who legitimately possesses (or can obtain, e.g. because they administer an unrelated, lower-privilege organization also onboarded to this shared Shipit instance) one organization's `webhook_secret` can grant themselves membership in a Team gating access for a completely different, higher-privileged organization, and subsequently authenticate into the application with full authorized-user privileges (deploy, rollback, lock stacks, etc., depending on further team-based checks) for stacks they should never be able to touch. The root cause is the mismatch between the field used to select/verify the signing secret (`repository.owner.login`/`organization.login` used only for signature routing) and the field(s) actually trusted to mutate authorization-relevant state (`team.id`, `member.login`) with no cross-check against the authenticated organization.

### Likelihood Explanation
Exploitation requires only: (a) knowledge of one webhook_secret configured on the shared instance (plausible in any deployment that federates several organizations/teams under one Shipit instance, as the repo's own multi-org secrets template demonstrates), and (b) knowledge of the numeric `github_id` of the target Team, which is discoverable via the public GitHub Teams API for any team whose slug/organization is known (`GET /orgs/{org}/teams`). No GitHub App private key, `api_clients_secret`, or session token is required — only a forged HTTP POST to the public `/webhooks` endpoint. This is a realistic and low-effort attack path for any party with legitimate access to one tenant of a multi-tenant Shipit installation.

### Recommendation
- In `MembershipHandler#find_or_create_team!` / `#process`, require that the Team's stored `organization` matches the organization that authenticated the current webhook request, and reject (or no-op) if they differ, rather than trusting `team.id` alone.
- Pass the verified `repository_owner`/organization value from `WebhooksController` into the handler dispatch, and have `Handler` implementations validate all organization-scoped identifiers (`team.id`, `repository.full_name`, etc.) against that verified value before performing any writes.
- Consider scoping `Team.find_or_create_by!` lookups by `(github_id, organization)` rather than `github_id` alone, so a team ID cannot be "claimed" or mutated cross-organization.

### Proof of Concept
1. Attacker administers (or otherwise knows the `webhook_secret` for) organization `attacker-org`, configured on the shared Shipit instance.
2. Attacker identifies, via GitHub's public Teams API, the `github_id` of `victim-org/admins`, a team referenced in `Shipit.github_teams`.
3. Attacker computes `sha1=HMAC(attacker_org_webhook_secret, body)` for the following body and POSTs it to `/webhooks` with header `X-Github-Event: membership`:
```json
{
  "action": "added",
  "team": { "id": <victim_org_admins_github_id>, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret. [11](#0-10) 
5. `MembershipHandler#process` finds the existing `victim-org/admins` Team by `github_id`, creates/looks up the `attacker-github-login` user, and calls `team.add_member(member)`, adding the attacker to `victim-org/admins`. [2](#0-1) 
6. Attacker logs in via `/github/auth/github`; `User#authorized?` returns true because they are now a member of a team in `Shipit.github_teams`, granting them access to `victim-org`'s stacks. [3](#0-2)
