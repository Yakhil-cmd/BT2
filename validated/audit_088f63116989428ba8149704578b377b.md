### Title
Stack-scoped API token can read CCMenu status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces the invariant that an `ApiClient` scoped to a single stack (`current_api_client.stack_id?`) may only touch that stack, by routing all stack lookups through the `stacks` scope. `Shipit::Api::CCMenuController` bypasses this binding by overriding `stack` to resolve directly against `Stack.from_param!(params[:stack_id])`, breaking the equality "stack a token authorizes == stack the request touches." A caller holding any valid, stack-scoped `read:stack` token can request CCMenu status for a stack it was never scoped to.

### Finding Description
`BaseController` defines the scoping contract used by every other API controller: [1](#0-0) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string; it never checks which stack is being accessed - that check is delegated entirely to the `stacks`/`stack` scoping helpers above.

`CCMenuController` re-implements `stack` without going through that scope, and authenticates via a raw `params[:token]` lookup: [2](#0-1) 

Because `stack` is redefined as `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the `current_api_client.stack_id` restriction (enforced everywhere else via `BaseController#stacks`) is never applied here. Any `ApiClient` with `read:stack` permission - even one explicitly created with `stack_id` set to restrict it to a single stack - can supply an arbitrary `stack_id` parameter and receive that other stack's CCMenu XML (name, last build status/label/time, lock state).

Tokens intended to be stack-scoped are routinely generated and exposed outside the main authenticated session, e.g. `CCMenuUrlController` mints an `ApiClient` and embeds its `authentication_token` directly in a URL query string for use by external CI-status tools: [3](#0-2) 

Such URL-embedded tokens are the kind of credential most likely to leak (via browser history, referrer headers, third-party CI dashboards, logs) yet the engine's own controller fails to honor the one restriction that would limit the blast radius of that leak (`stack_id` scoping) for this endpoint.

### Impact Explanation
An attacker in possession of a legitimately-issued, stack-scoped API token (e.g., a leaked CCMenu URL for stack A) can use it to read the CCMenu status - name, last build status/label/time, and lock status - of any stack in the installation, not just the one the token creator intended it to be restricted to. This is an unauthenticated (from the target stack's perspective) read of stack state, matching the High-severity category defined for this engine ("unauthenticated read of stack state").

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token with `read:stack` permission (commonly distributed via `CCMenuUrlController`-generated URLs meant for CI dashboards) and knowledge/guessing of another stack's `to_param` (owner/repo/environment/branch, which is generally public GitHub repo information). No other privilege is required, and the bypass is a straightforward parameter substitution once such a token is obtained.

### Recommendation
Change `CCMenuController#stack` to use the same scoped lookup as the rest of the API (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that `current_api_client.stack_id` is always honored, consistent with `BaseController`.

### Proof of Concept
1. An operator calls `CCMenuUrlController#fetch` for Stack A, obtaining a URL like `.../api/stacks/A/ccmenu.xml?token=<token-scoped-to-A>`.
2. This URL/token is exposed via a CI dashboard, browser history, or logs (its whole purpose is external, unauthenticated consumption).
3. An attacker takes `<token-scoped-to-A>` and requests `GET /api/stacks/B/ccmenu.xml?token=<token-scoped-to-A>` for an unrelated Stack B.
4. `CCMenuController#authenticate_api_client` accepts the token (still valid, still has `read:stack`), and `CCMenuController#stack` resolves Stack B via `Stack.from_param!` with no scope check against `current_api_client.stack_id`.
5. The response renders Stack B's CCMenu XML (name, build status, lock state), even though the token was only ever meant to authorize Stack A.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
