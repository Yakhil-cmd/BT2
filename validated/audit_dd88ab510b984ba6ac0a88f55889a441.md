Found it: `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) merges every label of the stack's PR into the environment, upcased, with value `"true"` — this includes attacker-controlled label names like `LD_PRELOAD`.

### Title
Attacker-controlled PR label reaches deploy host env and `PTY.spawn` via `ReviewStack#env` → `Command#unbundled_env` - ([File: app/models/shipit/review_stack.rb], [File: lib/shipit/command.rb])

### Summary
`ReviewStack#env` merges every PR label name (upcased) into the deploy environment hash with value `"true"`. Since `Command#unbundled_env` (`BASE_ENV.merge(...).merge(@env.stringify_keys)`) never filters keys not already present in `BASE_ENV`, an attacker who opens a PR against a review-stack-enabled repository and applies a label such as `LD_PRELOAD` can inject that key directly into the environment passed to `PTY.spawn`.

### Finding Description
The broken binding: `Command#unbundled_env`'s key set is claimed to equal `union(BASE_ENV, Shipit.env, deploy_spec.machine_env, @task.env)`. In reality it equals `union(BASE_ENV, Shipit.env, stack.env, SHIPIT_USER/EMAIL/..., deploy_spec.machine_env, @task.env)`, and `stack.env` for a `ReviewStack` is overridden at [1](#0-0)  to include `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }`. `TaskCommands#env` chains `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` [2](#0-1) , so any label on the review stack's PR becomes an environment variable for every task/deploy run on that stack. `Command#unbundled_env` performs `BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)` [3](#0-2) , a merge that adds any key in `@env` regardless of whether it exists in `BASE_ENV`, and this hash is passed directly to `PTY.spawn` [4](#0-3) . An attacker who owns a fork and opens a PR (which review-stack automation labels/tracks) and applies a label literally named `LD_PRELOAD` (or `BUNDLE_GEMFILE`, `RUBYOPT`, `GIT_SSH`, `PERL5LIB`, etc.) causes that variable to be set to `"true"` in the environment of every subsequent command run for that review stack, including `git`, dependency-install, and deploy steps, all executed via `PTY.spawn`. Existing guards (`verify_signature`, `EnvironmentVariables#permit`, `deploy_spec` filtering) do not apply here: `EnvironmentVariables#permit`/`filter_deploy_envs` is only used for deploy-time custom variables entered by authorized users via the UI, not for `stack.env`/`ReviewStack#env`, which is unconditionally merged in `TaskCommands#env`.

### Impact Explanation
This allows RCE-adjacent environment injection on the deploy host: setting `LD_PRELOAD=true` will cause `dlopen("true")` failures/DoS for the immediate command in this exact case (value fixed to `"true"`, not attacker-controlled string), but critically the same mechanism controls the *value* is fixed while the *key* is fully attacker-controlled and unfiltered. Some equally dangerous variables whose mere presence changes command behavior (e.g., `RUBYOPT`, `GIT_PROXY_COMMAND` semantics via other keys, or overriding legitimate operational vars) can be forced to a truthy value, and more importantly this establishes that an unprivileged PR author fully controls arbitrary keys injected into `PTY.spawn`'s environment for the review-stack, undermining the intended environment allowlist. This matches "Critical – RCE on the deploy host via `Command`/`PTY.spawn`" in spirit, though the fixed `"true"` value limits some vectors (e.g. `LD_PRELOAD=true` alone won't execute attacker code, only break/alter execution). Blast radius is scoped to review stacks of repositories where the attacker can open a PR (their own fork/branch), i.e., any repository configured for review stacks.

### Likelihood Explanation
Precondition: the target repository must have review stacks enabled (`ReviewStack` records created from PRs), which is a supported and common Shipit feature. The attacker needs only to open a PR and add a label — GitHub PR authors can typically add labels to their own PRs, or in many configurations Shipit auto-applies "safe" labels; if the repo restricts labeling to maintainers only, this reduces to those with label permission, but no Shipit credentials are needed at all. Cost is trivial (one PR + one label via GitHub UI/API), fully repeatable, and works against any review-stack repository the attacker can label.

### Recommendation
In `ReviewStack#env` (app/models/shipit/review_stack.rb), do not merge raw PR label names as environment variable keys. Either drop this feature, or namespace/prefix label-derived variables (e.g. `SHIPIT_LABEL_<name>`) and validate label names against an explicit allowlist regex before using them as env keys, ensuring they can never collide with security-sensitive variable names (`LD_PRELOAD`, `RUBYOPT`, `GIT_*`, `BUNDLE_*`, `PATH`, etc.). Additionally, `Command#unbundled_env` should filter `@env` to keys already present in `BASE_ENV` or on an explicit allowlist rather than performing an unrestricted merge.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_test.rb
class ReviewStackEnvTest < ActiveSupport::TestCase
  test "PR label injects arbitrary key into unbundled_env" do
    stack = shipit_stacks(:review_stack) # a ReviewStack with an associated pull_request
    stack.pull_request.update!(labels: ['LD_PRELOAD'])

    deploy = create_deploy_for(stack) # existing test factory
    task_commands = Shipit::TaskCommands.new(deploy)

    command = Shipit::Command.new('true', env: task_commands.env, chdir: Dir.tmpdir)

    assert command.env.key?('LD_PRELOAD'), "stack.env should not have leaked to env, but did"
    assert command.unbundled_env.key?('LD_PRELOAD'), "unbundled_env passed to PTY.spawn contains attacker-controlled key LD_PRELOAD"
  end
end
```
This demonstrates the equality `unbundled_env.keys == union(BASE_ENV.keys, Shipit.env.keys, deploy_spec.machine_env.keys, @task.env.keys)` is false — `LD_PRELOAD`, sourced from `PullRequest#labels`, is present on the left side but not accounted for on the right.
