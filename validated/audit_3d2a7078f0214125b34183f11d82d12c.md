### Title
Stale multisig owner votes are never invalidated on membership changes, allowing execution with a re-added owner's outdated approval — (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
The `BaseERC20Guild` report's root invariant is: a voter's cast vote is never re-validated against the voter's *current* eligibility/state, so a vote recorded under one membership/权限 condition silently remains valid and counts later under a different (and unauthorized) condition. Searching `MultisigAccount` in `multisig_account.move` shows the same invariant is *mostly* protected (votes from currently-removed owners are excluded, per `test_validate_transaction_should_not_consider_removed_owners` at [1](#0-0) ), but the protection is implemented by filtering on **current owner list membership only** — it does not clear or invalidate the underlying vote record itself.

### Finding Description
`vote_transanction` stores an owner's approve/reject decision keyed by address in `transaction.votes`, a `SimpleMap<address,bool>` scoped to that specific pending transaction (`MultisigTransaction`) — this record is never removed when the transaction is still pending: [2](#0-1) .

`num_approvals_and_rejections_internal` computes the approval count by iterating the **current** `owners` vector and checking, for each current owner, whether `transaction.votes` contains an entry for that address: [3](#0-2) .

`update_owner_schema` (invoked by `add_owners`/`remove_owners`/`swap_owner(s)`) only mutates the `owners` vector; it never touches any pending transaction's `votes` map: [4](#0-3) .

Consequence: if owner `A` votes "approve" on pending transaction #N, is later removed from the multisig (via a separate, legitimate `remove_owners` multisig transaction), and is subsequently **re-added** as an owner (via a later `add_owners`), then as soon as `A` reappears in the `owners` vector, `num_approvals_and_rejections_internal` will again count `A`'s **old, stale** vote toward transaction #N's approval tally — without `A` casting any new vote and without any check that the vote was cast while `A` was continuously an owner. The mechanism that "invalidates" removed owners' votes (demonstrated in `test_validate_transaction_should_not_consider_removed_owners`) is not a real invalidation of the vote record; it is a side effect of filtering by current owner-list membership, and it is trivially reversed by re-adding the same address.

### Impact Explanation
This breaks the "wrong signer/approval set" invariant explicitly called out in the admission pivots: a transaction can reach `can_be_executed` truth and later `execute_transaction` using an approval that does not reflect the *current* multisig owner's consent. In realistic multisig lifecycle usage (owner rotation, temporary board changes, re-onboarding of a previous signer), a stale "approve" vote can resurrect itself and combine with unrelated newer votes to reach `num_signatures_required`, causing an arbitrary queued `MultisigTransactionPayload` (which can call **any** entry function, including transferring funds or altering the account further) to execute without the reinstated owner's actual, current-session consent. Because `MultisigAccount` is a standard general-purpose account abstraction used to control funds and privileged operations across Aptos, this can result in unauthorized execution of a transaction that a genuinely up-to-date quorum did not approve.

### Likelihood Explanation
Exploitation does not require any privileged bypass beyond normal multisig usage patterns that are common in practice: owner removal followed later by owner re-addition (e.g., temporary suspension, personnel rotation, recovery of an account, or an attacker who is briefly removed and then reinstated through social/legitimate means) is a routine multisig operation, not an edge case. The bug is triggered purely by ordinary sequencing of `add_owners`/`remove_owners`/`vote_transanction`/`execute_transaction` calls, with no need for cryptographic bypass, race condition, or malformed input — only for a transaction with a stale approval to still be pending (not yet executed/rejected) when the owner is re-added, which is plausible for any signature threshold that is not "immediately reached" or for owners who deliberately queue transactions to survive rotations.

### Recommendation
When an owner is removed via `update_owner_schema` (or equivalently `remove_owners`/`swap_owner(s)`), iterate all pending `MultisigTransaction` entries and remove that owner's vote entry from each `transaction.votes` map (or record a per-owner "membership epoch" and require votes to be re-validated against the epoch when the vote was cast, rather than only against current list membership). Alternatively, track a monotonically increasing "owner set version" and invalidate/reject votes whose recorded version doesn't match the transaction's or account's current version before counting them in `num_approvals_and_rejections_internal`.

### Proof of Concept
1. Create a 2-of-3 multisig with owners `{A, B, C}`.
2. `A` creates transaction `#1` (auto-approves as creator per `create_transaction`).
3. `B` calls `approve_transaction(B, multisig, 1)` → 2 approvals, `can_be_executed(multisig, 1) == true`, but suppose execution is deferred/not yet called.
4. Via a separate already-executed multisig transaction, `B` is removed (`remove_owners([B])`) — e.g., because of a policy dispute — leaving owners `{A, C}`. At this point `can_be_executed(multisig, 1)` becomes `false` per the existing filtering behavior (as shown in the repo's own test at lines 2268–2289 for a similarly structured scenario).
5. Later, owners decide to reinstate `B` and execute `add_owners([B])`. As soon as this completes, owners are `{A, C, B}` again.
6. Without `B` casting any new vote, `num_approvals_and_rejections_internal` for transaction `#1` now again counts `B`'s original stale "approve" vote from step 3, restoring `can_be_executed(multisig, 1) == true`, and transaction `#1` (whose payload could be anything, e.g., a fund transfer or further owner-schema change) can now be executed using `B`'s outdated consent, which `B` never re-affirmed under the current owner set.

**Uncertainty note:** I did not locate/inspect `execute_transaction`/`get_next_transaction_payload`/`successful_transaction_execution_cleanup` directly (grep for those symbols in this pass returned no direct matches, likely due to index/name differences in this fork), so I cannot confirm from source whether there is an additional guard at execution time that re-validates vote freshness beyond `num_approvals_and_rejections_internal`. The core mismatch — vote records are never cleared on owner removal and are only filtered by current list membership — is directly confirmed from `multisig_account.move` lines 1225–1253, 1532–1548, and 1586–1632, and is consistent with the existing but incomplete protection demonstrated by `test_validate_transaction_should_not_consider_removed_owners`.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
