## Title
State-Var Key Injection via Unrestricted Newline in AA `var[name]` Assignment — Namespace/Path Traversal in KV-Store Key Construction - ([File: formula/evaluation.js])

### Summary
Apache Shiro's CVE-2023-34478 stems from building an authorization/routing decision on a path string without properly normalizing/validating segment delimiters, letting an attacker smuggle characters that make the framework treat one path as another. Ocore has an analogous pattern: AA state-variable storage keys are built by naive string concatenation of untrusted, attacker-controlled segments joined with `\n` as a path/namespace delimiter — `"st\n" + address + "\n" + var_name` — without ever rejecting `\n` inside `var_name`. Because the *address* segment is always a fixed-length, alphabet-restricted string (32 uppercase base32 chars) it cannot itself contain the delimiter, but `var_name` is fully attacker-supplied oscript data and is only checked for length and UTF-16 well-formedness, not for the delimiter character. This allows a value that is nominally "this AA's local variable name" to be turned into a full "address\nvar_name" key, i.e. a path/namespace traversal into another AA's storage segment.

### Finding Description
State vars are persisted in the key-value store using a hand-built, delimiter-based composite key: [1](#0-0) [2](#0-1) 

The key format is always `"st\n" + address + "\n" + var_name`, and lookups over ranges (`readAAStateVars`) rely on `\n` being the unambiguous field separator between `address` and `var_name`: [3](#0-2) 

The `var_name` that ends up in this key is fully controlled by the AA definition author/trigger data via the `state_var_assignment` oscript construct (`var[expr] = expr;`), evaluated in the formula engine: [4](#0-3) 

The only checks applied to the computed `var_name` before it is used to build the storage key are a maximum length check and a "well-formed UTF-16" check — there is **no check rejecting `\n` (0x0A) or other control characters**: [5](#0-4) 

Because `address` is always exactly 32 valid base32 characters (enforced elsewhere by `ValidationUtils.isValidAddress`), it cannot itself introduce a stray `\n`. However, since `var_name` is not restricted from containing `\n`, an AA author can define `var_name` (via `trigger.data`, a getter, or any string expression) equal to something like `"<victim_AA_address>\nsome_var"`. When this is written with `readVar`/`stateVars[address][var_name]` bookkeeping and ultimately persisted via `batch.put("st\n" + address + "\n" + var_name, ...)` (see `saveStateVars` at aa_composer.js:1487-1502), the resulting raw KV key becomes:

```
st\n<attacker_AA_address>\n<victim_AA_address>\nsome_var
```

Because the *"path"* separator used by every reader (`readAAStateVar`, `readAAStateVars`, `checkStorageSizes`, `find_longest_state_var.js`, migration tools) is simply "the second `\n`", any consumer that manually reparses the key (e.g. `checkStorageSizes` in aa_composer.js, which does `data.key.substr(3,32)` / `data.key.substr(36)`, or the `readAAStateVars` range-scan matching by prefix `"st\n"+address+"\n"`) can be confused about which AA the trailing bytes actually belong to, since the naive parsing assumes the first 32 bytes after `st\n` are always the address and everything after the second `\n` is the var name — an assumption that breaks once `var_name` itself contains embedded `\n` sequences that look like `address\nvar_name`.

This is directly analogous to Shiro's bug class: a "path" is built from segments joined by a delimiter, one segment is attacker-controlled and is not checked for the delimiter character, and multiple different code paths parse the resulting composite string with different assumptions about where segment boundaries lie (range-scan prefix matching in `readAAStateVars` vs. fixed-offset substring parsing in `checkStorageSizes`/migration tools). This mismatch between how the value is written (unbounded raw concatenation) and how various readers reparse it (fixed offsets/prefix ranges) is the same "non-normalized path routing" root cause that made Shiro's chain-based path matching bypassable.

### Impact Explanation
The direct, concretely provable consequence is storage-accounting corruption / desynchronization between the authoritative `aa_addresses.storage_size` (SQL) and the actual sizes accounted for by the KV-store scanning tools, because `checkStorageSizes` (aa_composer.js:1918-1952) parses keys by fixed offsets (`data.key.substr(3, 32)` for address, `data.key.substr(36)` for var_name) — a `var_name` containing embedded `\n` will cause the tool to misattribute storage bytes to whichever 32-byte slice happens to land at offset 3, potentially not matching the AA that actually incurred the ledger-tracked storage_size charge. Since AA storage-size accounting gates whether an AA can afford additional storage (`byte_balance < new_storage_size` check in `updateStorageSize`, aa_composer.js:1531-1571), a mismatch between the SQL-tracked size and the actual KV-store footprint can be leveraged by an AA author to make an AA accumulate more on-disk storage than its byte balance should allow, or to cause the consistency check in `checkStorageSizes` (which `throw Error`s on mismatch) to crash a full node's periodic integrity check — a node-availability/DoS-adjacent and AA-fund-accounting-integrity issue reachable purely by posting a trigger to an attacker-authored AA.

### Likelihood Explanation
Any user can define and trigger an Autonomous Agent; a `var[$name] = value;` state assignment with `$name` built from `trigger.data` or oscript string concatenation is a completely ordinary AA pattern (as shown throughout the oscript sample corpus, e.g. `var[$key] = ...` in `a_bank_without_percent.oscript`). Getting `$name` to contain a literal `\n` only requires a JS/oscript string containing a newline character, which is not filtered by the `MAX_STATE_VAR_NAME_LENGTH` or `isWellFormed()` checks. No special privileges, no cooperating counterparties, and no network position are needed — a single AA author plus a single trigger sender (which can be the same actor) is sufficient to reach this code path.

### Recommendation
Reject `var_name` values (and any other identifiers concatenated with `\n` into KV-store keys, e.g. data-feed names, which are explicitly checked for `\n` elsewhere — see `feed_name.indexOf('\n') >= 0` validation in `aa_validation.js` and `validation.js`) that contain the `\n` delimiter character before allowing a `state_var_assignment`, mirroring the existing `data_feed` name validation. Concretely, add a check alongside the existing `var_name.length > constants.MAX_STATE_VAR_NAME_LENGTH` / `!var_name.isWellFormed()` checks in `formula/evaluation.js` (~line 1346-1349) that rejects `var_name.indexOf('\n') >= 0`, and audit all other places that build composite KV-store keys from attacker-controlled strings using `\n` as a delimiter (state vars, data feeds) to ensure symmetrical validation exists on every write path.

### Proof of Concept
1. Author an AA whose state message does:
```
{
  app: 'state',
  state: `{
    $victim = '<VALID_BASE32_ADDRESS_OF_ANOTHER_AA>';
    var[$victim || '\nsome_var'] = 1;
  }`
}
```
2. Post a trigger to this AA with sufficient bytes to pay for the AA's storage-size charge.
3. On AA response processing, `saveStateVars` (aa_composer.js:1487-1502) writes `batch.put("st\n" + <this_AA_address> + "\n" + <victim_address> + "\nsome_var", ...)`.
4. Run the storage-size consistency check (`checkStorageSizes`, aa_composer.js:1918-1952) or `tools/find_longest_state_var.js`: because these tools reparse the KV-store key using fixed offsets/prefix boundaries rather than the writer's original segment boundaries, the write is attributed to a different "address" region than the one billed in `aa_addresses.storage_size`, producing a mismatch that trips the `throw Error("storage size mismatch...")` in `checkStorageSizes`, or, in `readAAStateVars` range scans, returns/attributes data inconsistently for prefix queries scoped to the victim address.

*(I was unable to fully trace the exact byte-for-byte behavior of the LevelDB/kvstore range-scan semantics in `readAAStateVars` under adversarial embedded `\n` values, since I could not execute the code; the impact analysis above is based on the fixed-offset parsing in `checkStorageSizes`/`sqlite_migrations.js`/`tools/find_longest_state_var.js`, which is unambiguously vulnerable to this key-construction assumption break. A live Devin session with code execution would be needed to confirm whether `readAAStateVars`'s `gte/lte` range scan can be tricked into cross-address data leakage in addition to the accounting corruption documented here.)*
