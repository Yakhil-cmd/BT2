## Finding

The bug-class from the Vyper report — a check that compares two values but never validates that they're bound to the *same* trusted context (loss margin never enforced against the actual adapter) — has a direct analog in Shipit's webhook trust model: **the organization whose secret is used to *verify* a webhook is derived from attacker-controlled payload fields, and is never bound to the repository/commit that the handler subsequently *writes to*.**

### Root cause

`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate the HMAC against using data taken straight from the unverified JSON body: [1](#0-0) [2](#0-1) 

That selects a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`, and its `verify_webhook_signature` is checked: [3](#0-2) 

Once the signature validates against *that org's* secret (an org that a low-privilege attacker who only administers their own onboarded GitHub org/webhook can legitimately produce), the payload is dispatched to handlers that key their writes off **other, still-unverified fields** of the same body: [4](#0-3) 

`PushHandler` and PR handlers at least scope the mutation to `Repository.from_github_repo_name(repository.full_name)` — but nothing ties `full_name` to the organization whose secret was actually used to authenticate the request. `StatusHandler` is worse: it doesn't scope by repository at all, it matches purely by commit `sha` across the entire Shipit instance: [5](#0-4) 

`create_status_from_github!` can flip a commit's CI state and, on transition, trigger continuous-deployment merge scheduling: [6](#0-5) 

### The broken equality

`organization whose webhook secret authenticated the request` ≠ `organization/repository whose Stack/Commit gets mutated`.

An attacker who legitimately administers their own onboarded GitHub organization/webhook in a multi-org Shipit deployment (`github_app_config`/`github_organizations`) can sign a `status` (or `push`) event with **their own org's secret** while setting `repository.full_name`/`sha` to point at a target belonging to a **different** organization's Stack. `StatusHandler` will happily create/replicate a fabricated `success` status on that foreign commit, and `Commit#add_status` will schedule merges/continuous-deployment for a stack the attacker has no privilege over — a cross-repository/cross-organization write, and a plausible path to an unauthorized deploy if `continuous_deployment` is enabled on the targeted stack.

### Title
Cross-organization webhook forgery via unbound `repository_owner`/signature-org vs. mutated repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate against using the untrusted `repository.owner.login`/`organization.login` payload fields, then dispatches the same payload to handlers (`StatusHandler`, `Handler#stacks`/`PushHandler`, PR handlers) that key their writes off *other* payload fields (`repository.full_name`, `sha`) with no requirement that those fields belong to the org whose secret validated the signature.

### Finding Description
Signature verification only proves the request was signed with the secret configured for whatever organization `repository_owner` (self-reported in the body) resolves to. No code path checks that the `full_name`/`sha` used later by handlers is actually owned by that same organization. `StatusHandler#process` [7](#0-6)  doesn't even use `repository_name`/`stacks` scoping — it matches globally by `sha`, so any organization capable of sending a validly-signed webhook can affect commits belonging to any other organization's stacks.

### Impact Explanation
This breaks the deployment-trust boundary between organizations hosted on a shared Shipit instance: cross-repository/cross-organization writes (forged CI status, which can trigger `stack.schedule_merges` and continuous deployment via `Commit#add_status` [8](#0-7) ) are possible without any privilege in the target organization/repository.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (`github_app_config`) and that the attacker controls (owns) a webhook/App installation for at least one of them — a realistic multi-tenant deployment scenario, and no Shipit session, `ApiClient` token, or victim's secret/private key is needed.

### Recommendation
Bind the resolved signing organization to the mutation target: after `verify_signature` succeeds, re-derive `repository_owner`/`organization` from the same trusted source used to select the secret, and reject/ignore any handler action whose `repository.full_name` owner (or, for `StatusHandler`, the owning stack's repository owner) does not match the organization that authenticated the request.

### Proof of Concept
1. Shipit configured with `github: { OrgA: {webhook_secret: "orgA-secret", ...}, OrgB: {webhook_secret: "orgB-secret", ...} }`, each maintained independently by each org's own GitHub App/webhook admin.
2. Attacker, who legitimately administers OrgA's webhook (no Shipit privilege, no access to OrgB), crafts a `status` event body:
```json
{"sha":"<existing sha of an OrgB commit>","state":"success","context":"ci","repository":{"owner":{"login":"OrgA"}}}
```
3. Signs it with OrgA's known `webhook_secret`, sets `X-Github-Event: status` and `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"OrgA"`, verifies successfully against OrgA's secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching OrgB's commit — and calls `create_status_from_github!`, forging a `success` status and potentially triggering `schedule_merges`/continuous deployment on OrgB's stack, with zero OrgB privilege.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
