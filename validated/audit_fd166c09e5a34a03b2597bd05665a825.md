All mutating actions across the `Api::*Controller` classes are gated by `require_permission` for `write:stack`, `deploy:stack`, `lock:stack`, or `write:hook`, and the enforcement is model-level (`ApiClient#check_permissions!`) against the authenticated client's actual `permissions` column, not against any claim tied to the endpoint the token was minted for.

### Title
No vulnerability found for this question.

### Summary
The question hypothesizes that a `read:stack`-scoped CCMenu token, when replayed as HTTP Basic-Auth username against other `Api::*Controller` endpoints, could bypass permission checks because `ApiClient.authenticate` performs no "endpoint binding." Tracing the actual authorization flow shows this doesn't hold: permission enforcement is based on the persisted `permissions` attribute of the resolved `ApiClient` record, not on which endpoint the token happened to be minted for.

### Finding Description
The claimed broken binding would be: `token.scope_at_mint_time == endpoint.required_scope`. But that's not how permissions are actually enforced in this codebase. The real binding is: `ApiClient.find(id).permissions == permissions required by require_permission!`.

Tracing the path: `CCMenuUrlController#fetch` creates a client via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` [1](#0-0)  and embeds `client.authentication_token` in the URL [2](#0-1) . This token is just a signed client `id` (`SimpleMessageVerifier#generate(id)`), not a capability-scoped credential.

In `Api::BaseController#authenticate_api_client`, `parts.select(&:present?).join('--')` reduces the Basic-Auth username/password pair to a token string, which is passed to `ApiClient.authenticate(token)` [3](#0-2) . `ApiClient.authenticate` merely verifies the signature and looks up the client record by id: `find_by(id: message_verifier.verify(token).to_i)` [4](#0-3) . This step only identifies *which* `ApiClient` record is making the request — it does not grant any permissions by itself.

Every subsequent authorization decision goes through `require_permission!` → `current_api_client.check_permissions!(operation, scope)`, which checks the *actual, persisted* `permissions` array of that specific client row: `unless permissions.include?(required_permission); raise InsufficientPermission` [5](#0-4) . Since the CCMenu client was created with `permissions: %w[read:stack]` only, this array is fixed in the database — replaying its token anywhere does not change or bypass that array.

Every mutating `Api::*Controller` action is gated: `StacksController` requires `write:stack` for `create/update/destroy` [6](#0-5) ; `LocksController` requires `lock:stack` for all actions [7](#0-6) ; `DeploysController`/`RollbacksController`/`ReleaseStatusesController` require `deploy:stack` [8](#0-7) [9](#0-8) [10](#0-9) ; `HooksController` requires `write:hook` for `create/update/destroy` [11](#0-10) ; `TasksController` requires `deploy:stack` for `trigger`/`abort` [12](#0-11) ; `MergeRequestsController` requires `deploy:stack` for `update`/`destroy` [13](#0-12) .

A `read:stack`-only client presenting its token to any of these actions will fail `check_permissions!` and be rescued into a 403 via `rescue_from ApiClient::InsufficientPermission, with: :insufficient_permission` [14](#0-13) , exactly as the existing test asserts for the `CCMenuController` itself: "a request with insufficient permissions will render a 403" [15](#0-14) .

The premise that "no channel or endpoint binding beyond `SimpleMessageVerifier#verify`" implies a bypass is incorrect — authorization in this system is not endpoint-bound by design; it's client-identity-bound via the persisted `permissions` column, checked independently on every request regardless of which endpoint the token is presented to.

### Impact Explanation
None. A leaked CCMenu token only allows reading that one stack's CCMenu XML status (the exact capability it was minted with), matching `read:stack`. No mutating or write-capable action is reachable because every mutating controller action enforces its own `require_permission` scope against the database-backed `permissions` array, independent of the endpoint the token is presented at.

### Likelihood Explanation
Not applicable — no exploitable divergence exists between the two sides of the actual binding (`ApiClient#permissions` vs. `required_permission` checked per action).

### Recommendation
No change required for this specific concern. (General hygiene notes such as token rotation or short-lived CCMenu tokens are out of scope per the audit rules on best-practice notes.)
