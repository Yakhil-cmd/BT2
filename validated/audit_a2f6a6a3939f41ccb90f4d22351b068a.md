### Title
Signature verified against wrong GitHub organization allows cross-repository event forgery in multi-org Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb](app/controllers/shipit/webhooks_controller.rb))

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, then validates the signature using that org's `webhook_secret`. The event handlers, however, never re-check that this same organization owns the repository/stack they subsequently act on — they instead trust `repository.full_name` from the same untrusted payload (e.g. `Handler#repository_name` at [1](#0-0) ). This breaks the binding "organization that authenticated == repository that is written," analogous to the inflation-attack report's binding break between the asset actually deposited and the share/exchange-rate state acted upon.

### Finding Description
`verify_signature` computes the org used for HMAC validation from attacker-controlled payload fields before the signature is checked: [2](#0-1) [3](#0-2) 

Shipit supports hosting multiple GitHub organizations from one instance (`config/secrets.yml` supports a per-org `github:` map, see `test/dummy` and `docs/setup.md`/README multi-org config comment) — each org has its own independent `webhook_secret`. Once the signature is verified against *whatever org the payload claims to be from*, the raw JSON is handed to all registered handlers for the event (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, [4](#0-3) ). Handlers such as `PushHandler` resolve the target `Repository`/`Stack` purely from `repository.full_name`, with no cross-check against the organization that was used to authenticate the request: [5](#0-4) [1](#0-0) 

Because the `X-Hub-Signature` HMAC only proves "this payload's bytes came from an app holding organization X's `webhook_secret`," and nothing enforces `repository.owner.login == organization X` against `repository.full_name`, an attacker who legitimately controls an org configured in the same Shipit instance (org A, with a real, valid webhook secret) can craft a JSON body where `repository.owner.login` is `A` (so the secret lookup and HMAC check pass) while `repository.full_name` names a repository belonging to a completely different tracked org B. The handler then acts on org B's stack using attacker-chosen values (e.g. `ref`, `after` SHA for push/sync, or fabricated commit `state`/`sha` for the `status` handler, which is not scoped to `repository.full_name` at all and instead writes any commit status by `sha` for any tracked stack: [6](#0-5) ).

### Impact Explanation
This lets an attacker who is a legitimate GitHub-App owner for *one* configured organization in a multi-org Shipit instance forge push/status/check_suite events against repositories owned by *other* organizations tracked by the same instance, meeting the "cross-repository writes" / "unauthorized deploy" bar: forged `status` events can flip a commit's CI/deploy-blocking status green, and forged `push` events can trigger `GithubSyncJob` with an attacker-chosen `expected_head_sha`, both of which feed directly into whether Shipit permits an unattended/continuous deploy of a foreign stack. This corresponds to the report's core pattern: a verified credential (the HMAC/org secret) is bound to one identity, but the state it is allowed to mutate (a different org's repository/stack) is determined by an unverified field in the same payload.

### Likelihood Explanation
Requires the attacker to control (own) at least one GitHub organization that the same Shipit instance has configured with its own `webhook_secret`/app, which is a realistic deployment shape explicitly supported and documented by Shipit (multi-org `github:` config). No repository write access, session, or `ApiClient` token to the *victim* org is needed — only knowledge of the victim's tracked repo `full_name`, which is typically public/discoverable.

### Recommendation
After signature verification, re-derive `repository_owner`/`organization` from the verified payload and enforce that any repository/stack acted upon by a handler actually belongs to that same organization (e.g., compare `Repository#owner` against the authenticated org before dispatching to handlers), rather than trusting `repository.full_name` independently of the org used for HMAC validation.

### Proof of Concept
1. Shipit instance is configured with two orgs, `orgA` (attacker-controlled, webhook secret `S_A`) and `orgB` (victim, hosts stack tracking `orgB/victim-repo`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using their own valid `S_A` secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner` → `"orgA"`, loads `Shipit.github(organization: "orgA")`, and the HMAC check passes (attacker legitimately knows `S_A`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` (unrelated to `orgA`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating org B's stack state despite the request only ever proving possession of org A's secret.

Note: I was unable to execute this end-to-end against a running instance (no filesystem/terminal access in ask-only mode); the analysis above is based on static reading of `WebhooksController`, `Handler#repository_name`, `PushHandler`, and `StatusHandler`. Confirming the exact production impact of `sync_github`/`GithubSyncJob` on deploy gating would benefit from a live test in a Devin session.
