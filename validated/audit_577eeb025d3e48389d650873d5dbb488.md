## Title
Bad-debt socialization silently desynchronizes the per-block zToken index cache, letting later transactions price zToken collateral off a stale, pre-write-down `lindex` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` caches vault `{index, lindex}` per `{timestamp, aid}` to avoid repeated cross-contract calls in the same block [1](#0-0) . The cache is populated once per block by whichever transaction accrues first, and every later transaction in that block trusts the cached value instead of re-querying the vault [2](#0-1) . However, `socialize-debt` in the vault contracts writes down `lindex` directly through a completely separate code path that does not go through `accrue-and-cache` and never invalidates the market's cache entry [3](#0-2) . This mirrors the reported bug class: a piece of accounting state (`committee_sizes`) that is updated on one code path (`constructor`) but not on another (`set_committee`), leaving stale data that downstream logic still trusts.

### Finding Description
`accrue-and-cache` is the single gate market.clar uses to read vault indexes: on a cache miss it calls `vault-accrue` and stores the result under `{timestamp: stacks-block-time, aid}`; on a cache hit it returns the previously stored value without re-checking the vault [1](#0-0) . `resolve-ztoken`, used to price zToken collateral for health checks, borrow capacity, and liquidation math, reads exclusively from this cache via `get-cached-indexes`, and panics only if nothing is cached — it never distinguishes a fresh value from a stale one [2](#0-1) .

`socialize-debt`, invoked from the liquidation flow to write off bad debt when a borrower's collateral runs out, mutates the vault's `lindex` directly and proportionally to the loss, without any interaction with market.clar's `index-cache` map [3](#0-2) , and the liquidation flow in market.clar that triggers it via `vault-socialize-debt`/`socialize-debt-asset` likewise does not touch or invalidate `index-cache` [4](#0-3) .

Because the cache key is `{stacks-block-time, aid}`, and multiple transactions within the same block share the same timestamp, the cached `{index, lindex}` entry persists as shared, cross-transaction state for the whole block [5](#0-4) . This is exactly the "shared cache primed by one caller and consumed by another" shape called out as the analog class: the `lindex` value governing zToken pricing is refreshed by whichever transaction happens to accrue first, and is silently trusted — never re-validated against the vault's actual, now-lower `lindex` — by every subsequent transaction in that block.

### Impact Explanation
Sequence within one block:
1. Transaction A (any ordinary operation touching that vault's zToken, e.g. a supply or borrow) calls `accrue-and-cache`, caching `lindex = L0` for `{T, aid}` [1](#0-0) .
2. Transaction B liquidates an under-collateralized borrower whose remaining debt exceeds seizable collateral, triggering `socialize-debt`, which writes the vault's real `lindex` down to `L1 < L0` to reflect the loss [6](#0-5) . The market's cached entry for `{T, aid}` is left unchanged at `L0`.
3. Transaction C, still in block `T`, deposits/uses that vault's zToken as collateral. `resolve-ztoken` reads the stale cached `L0` instead of the true `L1`, overvaluing the zToken collateral [2](#0-1) .

The victim is every other supplier/borrower of that vault: transaction C's user can pass health/capacity checks and borrow against collateral that is worth less than the market believes, because the market never re-priced it after the bad-debt write-down. Without transaction B's bad-debt event in that block, transaction C's collateral valuation would correctly use fresh `lindex`. With it, transaction C's user gets an inflated valuation it should not have received, which can permit under-collateralized borrowing paid for by the shared vault's other depositors — a temporary/permanent freezing or loss of funds at the pool level rather than something only the caller suffers.

### Likelihood Explanation
This does not require any privileged actor or DAO action — any user can trigger the initial accrual (transaction A, often incidental), any liquidator can trigger `socialize-debt` on an under-collateralized position (transaction B, a normal permissionless liquidation), and any user can immediately follow up with a zToken-collateralized operation (transaction C) in the same block, e.g., via ordering within the same block or by simply operating right after the liquidating transaction is confirmed if timestamps coincide. Bad debt socialization by itself is not an edge case — it is the designed remediation path for insolvent positions — so the precondition (a bad debt event happening) is realistic on any vault with volatile collateral.

### Recommendation
Invalidate or refresh the market's `index-cache` entry for the affected `aid` whenever `socialize-debt` (or any other vault state change that mutates `lindex`/`index` outside of `vault-accrue`) is executed, e.g. by having `vault-socialize-debt` return the vault's updated `{index, lindex}` and having market.clar overwrite the cache entry with it, or by deleting the cache entry for that `{timestamp, aid}` key so the next read is forced to re-query the vault.

### Proof of Concept
Not independently executable from static review; the sequence above (accrue in tx A, socialize-debt in tx B, zToken-collateral operation in tx C, all in block `T`) is derived directly from the code paths cited. Confirming exploitability end-to-end (actual bypass of a health check due to the stale `lindex`) would require running the three transactions against the local test harness under `local-testing/contracts/market/market.clar` and the corresponding vault, which was not runnable in this read-only review.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

```text
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
```
