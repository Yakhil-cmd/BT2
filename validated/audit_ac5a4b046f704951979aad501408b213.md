### Title
Reachable Assertion Abort via Uncaught Exception in `evaluate()` "address" Condition Handler - (File: definition.js)

### Summary
The `definition.js` authentifier evaluator contains a hard `throw Error(...)` reachable from a single attacker-crafted, unprivileged unit. This is the same bug class as CVE-2017-12960 (`dict_rename_var()` reachable assertion abort in libpspp): an assumption about attacker-controlled input is enforced with an unconditional `throw` rather than a graceful validation failure, and that `throw` is not guarded by validation's outer error-handling path, so it can crash the node process — a remote denial of service.

### Finding Description
In the `'address'` case of the authentifier `evaluate()` function inside `validateAuthentifiers()`, when an inner address's definition is not yet found on-chain, the code searches the current unit's `authors` array for an author matching that address and definition hash: [1](#0-0) 

If more than one author entry in the *same unit* matches the target address and `definition_chash`, the code does not return a validation failure — it unconditionally throws:
```
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
``` [2](#0-1) 

This throw executes inside the callback of `storage.readDefinitionByAddress`'s `ifDefinitionNotFound` handler, deep inside an asynchronous callback chain (`validate()` → `validateAuthors()` → `validateAuthor()` → `validateAuthentifiers()` → `evaluate()`), not inside the synchronous `try { ... } catch(e) { ... }` block that wraps only the unit-hash computation near the top of `validate()`: [3](#0-2) 

Because the `objUnit.authors` array and the address-condition definitions (`['address', other_address]`) referenced from a defining address's definition are both fully attacker-controlled fields of a posted unit, an attacker can craft a unit where:
1. One author address's definition (or an asset/AA condition it defines) contains an `['address', X]` sub-condition referring to address `X`.
2. The unit's own `authors` array contains two (or more) entries with `address === X` and a `definition` field whose `getChash160(...)` equals the same `definition_chash` that `storage.readDefinitionByAddress` reports for `X` (i.e., `X`'s definition is not yet known/stable, forcing the `ifDefinitionNotFound` branch).

Since JSON unit structure does not enforce that `authors` entries have unique addresses at this point in validation, this duplicate-author condition is directly reachable by any unprivileged unit poster.

### Impact Explanation
An uncaught exception thrown from inside an asynchronous callback in Node.js is not caught by any surrounding synchronous `try/catch`; it propagates to the top of the event loop and, absent a process-level `uncaughtException` handler that safely recovers state, crashes the ocore node process. Because unit validation is exercised by every full node (and light-vendor/hub) when relaying or accepting a newly posted unit, a single crafted unit posted to the network can crash any node that attempts to validate it — a network-wide denial of service, preventing confirmation of new units, directly matching the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
The path requires: (a) crafting a unit whose author's own definition (or a definition it invokes) uses an `['address', X]` condition, and (b) including duplicate author entries for `X` with a definition matching the still-unknown `definition_chash`. This is entirely within the capability of a normal unit poster — no special privilege, hub/peer position, or leaked key is required; it only requires constructing a specific but well-defined unit/definition/authors combination. This is comparable in complexity to constructing a malformed rename() input in PSPP scripts.

### Recommendation
Replace the `throw Error("more than 1 address definition")` with a graceful validation-failure callback (`return cb2(false)` or an equivalent `fatal_error` assignment consistent with the rest of `evaluate()`), so that a malformed/duplicate-author unit is rejected as invalid rather than crashing the process. Additionally, consider enforcing uniqueness of `author.address` entries earlier in `validateAuthors()` so this code path can never observe more than one author per address in a single unit.

### Proof of Concept
1. Construct address `X` with a definition that is not yet stable (still pending / unstable), so `storage.readDefinitionByAddress` invokes `ifDefinitionNotFound`.
2. Construct another address `Y` whose definition contains `['address', X]` as a sub-condition.
3. Post a unit authored in part by `Y`, whose `authors` array contains two entries with `address: X`, each carrying a `definition` field, both of which hash (via `objectHash.getChash160`) to the same `definition_chash` reported by step 1.
4. When `validateAuthentifiers` evaluates the `Y` definition's `['address', X]` node against this unit, `arrDefiningAuthors.length > 1` is true, and the process throws inside the async callback, escaping all `try/catch` blocks in `validation.js` and crashing the node.
