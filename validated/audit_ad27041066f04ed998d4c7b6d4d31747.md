### Title
Cross-repository commit-status forgery via `sha`-only lookup enables deployment of unvetted commits - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` updates the CI status of **every** `Commit` row matching a webhook's `sha`, regardless of which repository the webhook actually came from. Since a git commit's SHA is a hash of its content, an attacker can reproduce the exact same commit object (same SHA) in a repository they control, mark it `success` there, and have GitHub deliver a validly-signed status webhook to Shipit that Shipit then blindly applies to the identically-shaed commit belonging to a completely unrelated, victim stack/repository.

### Finding Description
The binding the system relies on is:
`Commit#status (used by deployable?/active? filtering in Stack#next_commit_to_deploy / #next_expected_commit_to_deploy)` == `CI truth as reported by the commit's OWN github_repo_name`.

This is broken in `StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike other handlers (`PushHandler`, `PullRequest::*Handler`), which scope their action through `stacks`/`repository` derived from `payload.dig('repository', 'full_name')` (see `Handler#stacks`/`Handler#repository_name`) [2](#0-1) , `StatusHandler`'s param schema doesn't even require a `repository` block [3](#0-2)  and `process` never checks it. It performs a global `Commit.where(sha: ...)` lookup across **all** stacks and applies the status.

Exploit flow:
1. Attacker identifies a commit SHA of an older, currently-stalled (non-deployable) commit belonging to the victim stack (public repo commits are visible via GitHub UI/API).
2. Attacker recreates the identical commit object (same tree/parents/author/committer/timestamps/message → identical SHA, since git SHAs are content hashes) inside a repository they own.
3. Using the normal GitHub Statuses API on their own repo, the attacker sets a `success` status for that SHA. GitHub validly signs and delivers a `status` webhook to Shipit's `/webhooks` endpoint (`WebhooksController#verify_signature` passes, because the signature is genuinely computed by GitHub using the org/App's real `webhook_secret` — the attacker never needs to know the secret, they only need any repo where the relevant GitHub App/webhook is installed, e.g. their own fork or an org repo they can push to).
4. `StatusHandler#process` matches the victim's commit row purely by `sha` and calls `commit.create_status_from_github!(params)`, which invokes `Commit#add_status` → `statuses.replicate_from_github!` [4](#0-3)  and [5](#0-4) , creating a `success` `Status` on the victim's commit for the victim's stack.
5. `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [6](#0-5)  now returns `true` for the victim's older commit, even though it never actually passed CI on its own repository.
6. `Stack#next_commit_to_deploy` (`commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)` → `deployable_commits(...)`) [7](#0-6)  and `Stack#next_expected_commit_to_deploy` (`commits.reject(&:active?)`, then `.find(&:deployable?)`) [8](#0-7)  now consider that forged-green older commit a valid deploy candidate. `Commit#active?` only checks whether the commit is part of the currently running task [9](#0-8)  — it provides no protection against a forged status, so the commit isn't filtered out.
7. Continuous delivery (`Stack#trigger_continuous_delivery`) or a manual deploy via the stack UI can then deploy up through that commit, even though its true CI state (in its own repository) never passed.

Existing guards do not stop this: `verify_signature` only proves the webhook genuinely came from *some* GitHub repository under a configured organization/App — it does not, and cannot, prove the webhook's claimed `sha` belongs to the repository that sent it. `drop_unhandled_event` and `ExplicitParameters` only validate shape/presence of fields, not repository ownership of the SHA. There is no `Repository`/`Stack` scoping check anywhere in `StatusHandler`.

### Impact Explanation
An attacker who can push commits to (and create statuses on) any repository serviced by the same Shipit-configured GitHub App/organization can write a `Status` record for a commit belonging to a **different, victim repository/stack that they don't own or control**, without ever authenticating as that repository. This directly satisfies the Critical class: "a payload for one repository mutating another's stack, commit, task or team" and can lead to "an unauthorized deploy" of code that never passed the victim repository's real CI. It's repeatable against any commit SHA the attacker can reproduce (trivial for any commit whose full content is visible, e.g., public repos, or any commit the attacker can otherwise obtain) and against any stack served by the same webhook_secret/App installation, i.e., broad blast radius across every stack tracked under that organization.

### Likelihood Explanation
Preconditions: the victim stack must have an older undeployed commit that is not yet deployable (true state), and the attacker must be able to push/reproduce an identical commit object into some repository serviced by the same GitHub App/org webhook configuration, then set a status via the ordinary GitHub Statuses API. No Shipit credentials, sessions, tokens, or secrets are required — the attacker rides on GitHub's own legitimate signing of the webhook. This is low-cost and fully repeatable; it only requires basic git/GitHub API usage.

### Recommendation
Scope `StatusHandler#process` (and `Commit#create_status_from_github!`/`Status.replicate_from_github!`) to only accept statuses for commits whose `stack.repository` matches the `repository.full_name` in the webhook payload. Require and validate `params.repository.full_name` in `StatusHandler`'s parameter schema, look up commits via `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { ... full_name: params.repository.full_name })`, and drop/ignore statuses whose payload repository doesn't match the commit's own tracked repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook from a foreign repository forges success on a victim commit and reorders next_commit_to_deploy" do
          victim_stack = shipit_stacks(:shipit)
          older_commit = shipit_commits(:third)   # legitimately stalled/non-deployable, older commit
          newer_commit = shipit_commits(:fifth)   # legitimately pending/newer commit

          refute older_commit.deployable?

          # Compute the true expected next commit before forgery
          true_expected = victim_stack.next_commit_to_deploy

          # Attacker sends a validly-signed webhook claiming to be from a repo they own,
          # but with the sha of the victim's older commit
          forged_payload = {
            'sha' => older_commit.sha,
            'state' => 'success',
            'context' => 'ci/travis',
            'description' => 'forged',
            'target_url' => 'http://attacker.example.com',
            'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
          }

          StatusHandler.call(forged_payload)

          older_commit.reload
          assert older_commit.deployable?, "forged status should not make a foreign commit deployable"

          forged_selection = victim_stack.next_commit_to_deploy
          assert_not_equal true_expected, forged_selection
          assert_equal older_commit, forged_selection, "attacker forged the older commit ahead of the true next commit"
        end
      end
    end
  end
end
```

Note: I was unable to fully verify the exact internal implementation of the private `deployable_commits` helper (its precise selection/ordering algorithm) within the available index snippets, though its call sites and the existing test `"#next_commit_to_deploy returns the last deployable commit"` confirm that flipping a commit's `deployable?` state directly changes which commit `next_commit_to_deploy` selects, which is sufficient to demonstrate the exploit's effect. A full Devin session with file access would be needed to inspect `deployable_commits` in its entirety if a more precise characterization is required.
