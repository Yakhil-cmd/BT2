### Title
Cross-organization CI status forgery bypasses deploy gating via webhook signed by an unrelated GitHub organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting stacks for multiple GitHub organizations behind a single `/webhooks` endpoint, each organization owning its own GitHub App and `webhook_secret`, as documented in `docs/setup.md`. `WebhooksController#verify_signature` picks which organization's secret to verify the HMAC against using a payload field (`repository.owner.login` / `organization.login`) that is *not bound* to the payload's `repository.full_name`, which is the field actually used by event handlers to select which repository/commit to act on. `StatusHandler`, in particular, doesn't even scope by repository — it matches commits globally by SHA — so a validly-signed webhook from any onboarded organization can flip the CI status of a commit belonging to a completely different organization's stack, and `Commit#deployable?` trusts that CI status to gate deploys.

### Finding Description
`WebhooksController` verifies the HMAC signature using an app/secret selected by `repository_owner`: [2](#0-1) [3](#0-2) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` — a field the payload's own author (i.e., whichever organization's webhook secret produced the signature) fully controls and which GitHub itself sets to that org's own login for any real event it emits. Shipit's multi-org support means several distinct, mutually-untrusted GitHub organizations can be configured, each with their own `webhook_secret` known to that organization's admin, as documented at: [4](#0-3) 

Once the signature is verified against *whichever* org’s secret matches `repository.owner.login`, the raw JSON body is dispatched to handlers that read a *different* field, `repository.full_name`, to decide what to act on: [5](#0-4) 

Critically, `StatusHandler` doesn't even use `repository.full_name` — it looks up commits by SHA with no repository scoping whatsoever: [1](#0-0) 

This directly creates/updates a `Status` record via `Commit#create_status_from_github!` → `Status.replicate_from_github!`: [6](#0-5) [7](#0-6) 

`Commit#deployable?` trusts this state to gate deploys: [8](#0-7) 

The equality that should hold but doesn't: `organization whose secret validated the signature == organization that owns the repository/commit the handler mutates`. Because `repository_owner` (used for authentication) and `repository.full_name`/`sha` (used for the mutation) are independent, attacker-supplied fields inside the same signed body, any onboarded organization admin can pick `repository.owner.login = "their-own-org"` (so the signature check passes with their own known `webhook_secret`) while setting an arbitrary `sha` for a commit belonging to a *different* onboarded organization's stack, forging a `success` CI status for it.

### Impact Explanation
An attacker who legitimately administers one GitHub organization/GitHub App onboarded to a shared Shipit instance (an "unprivileged" party with respect to any other organization on that instance) can:
- Forge a `success` CI status for an arbitrary commit SHA belonging to another organization's stack, satisfying `Commit#deployable?` and enabling that commit to pass continuous-deployment checks (`stack.schedule_merges`, `ContinuousDeliveryJob`) — an unauthorized deploy against a repository/organization the attacker has no legitimate access to.
- The same authentication/repository-binding gap affects every handler dispatched from the shared `/webhooks` endpoint (push, pull_request, check_suite, membership), since `verify_signature`'s organization selection is never checked against the repository the dispatched handler subsequently acts on.

This satisfies the Critical bar of "an unauthorized deploy" via a credential/authentication boundary crossing between two organizations' trust domains that this engine is supposed to keep separate.

### Likelihood Explanation
Any operator running Shipit with more than one onboarded GitHub organization (a documented, supported configuration) is exposed. Exploitation only requires the attacker to control a legitimate GitHub App/webhook secret for *any one* onboarded organization — no repository write access, no Shipit account, and no privileged Shipit credential is needed for the *victim* organization.

### Recommendation
After verifying the HMAC, re-derive the organization from the same field the handler will use (`repository.full_name`'s owner, or explicitly re-check that `repository.owner.login` matches the owner segment of `repository.full_name`) and reject the webhook if they diverge. Additionally, `StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`) should scope `Commit` lookups to stacks belonging to the repository/organization whose secret validated the request, not perform a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (victim) and `OrgB` (attacker-administered), per `docs/setup.md`'s multi-org instructions — both webhook to the same `/webhooks` URL.
2. As the admin of `OrgB`, craft a `status` event JSON body: `{"sha": "<OrgA's undeployed commit sha>", "state": "success", "context": "ci/whatever", "repository": {"owner": {"login": "OrgB"}, "full_name": "OrgB/some-repo"}}`.
3. Sign the raw body with `OrgB`'s own `webhook_secret` (known to the `OrgB` admin) and set `X-Hub-Signature` accordingly; POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")` and successfully verifies the signature against `OrgB`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds `OrgA`'s commit (no repository scoping performed), and calls `create_status_from_github!`, forging a `success` status for `OrgA`'s commit.
6. `OrgA`'s commit is now `deployable?` and, if `continuous_deployment` is enabled, will be automatically deployed/merged despite the attacker having no access to `OrgA`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
