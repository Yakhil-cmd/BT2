### Title
Webhook organization used for HMAC-secret selection is decoupled from the repository the event handler writes to, allowing unauthenticated cross-organization event spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`'s webhook secret to verify the signature against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the *unauthenticated* attacker-controlled JSON body [1](#0-0) [2](#0-1) . The event handlers that actually act on the payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve the target `Stack`/`Commit` using a *different* field of the same payload, `repository.full_name` (via `Handler#repository_name`) [3](#0-2) . Because `verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured [4](#0-3) , and the docs explicitly present `webhook_secret` as *optional* per configured GitHub App [5](#0-4) , a Shipit instance managing multiple organizations (as modeled by the test fixture with `OrgOne`/`OrgTwo`, one of which has `webhook_secret: # nil`) can be tricked into accepting arbitrary unsigned events for any *other* organization simply by naming the unauthenticated field to the unsecured org while pointing the acted-upon field at the target repo [6](#0-5) .

### Finding Description
The equality the deployment trust model is supposed to enforce is:

`organization authenticated via verify_signature == organization whose repository the handler writes to`

Before the request is trusted, the controller does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

`repository_owner` is entirely attacker-supplied (nothing about the raw request forces it to correspond to anything already trusted; it's read out of the unverified JSON body before signature is proven). Once `verify_signature` passes (either because the signature genuinely matches the org secret it picked, or — critically — because that org's `webhook_secret` is unset, in which case `verify_webhook_signature` returns `true` unconditionally) [4](#0-3) , `create` dispatches the payload to the registered handlers [8](#0-7) .

The handlers, however, never look at `repository.owner.login`; they resolve the actual `Stack`/`Commit` to mutate via `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses this to trigger `sync_github` on matching stacks [9](#0-8) ; `CheckSuiteHandler` schedules check-run refreshes for matching stacks/commits by branch+sha [10](#0-9) ; `StatusHandler` writes a `Status` for any `Commit` matching the attacker-supplied `sha`, globally (not even scoped by stack/repo) [11](#0-10) .

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are two independent, uncorrelated JSON fields inside the same otherwise-unauthenticated body, nothing prevents an attacker from setting them to different organizations. If *any* configured GitHub App in the installation has no `webhook_secret` (an explicitly supported/optional configuration per the setup docs), an attacker can set `repository.owner.login` (or `organization.login`) to that unsecured org and `repository.full_name` to a target repo belonging to a *different, secured* org. `verify_signature` will authorize the request via the unsecured org's always-true check, while the handler proceeds to mutate state belonging to the secured org's repository — completely bypassing that org's webhook secret.

### Impact Explanation
This breaks the binding "organization authenticated == repository written" and allows an unauthenticated, credential-less network attacker to:
- Inject fake commit `status` events for arbitrary commits in a protected org/repo (`StatusHandler`), which can be used to make Shipit believe CI checks passed, potentially unblocking automated status-gated actions.
- Trigger `GithubSyncJob`/`RefreshCheckRunsJob` for arbitrary stacks in a protected org, forcing state resync using attacker-influenced signals (`PushHandler`, `CheckSuiteHandler`).

This matches the High-severity category "escalation into `Shipit.github_teams` authorization ... or unauthenticated read of stack state, task streams or deploy output" by way of unauthenticated write access to stack/commit state that should require a valid, org-specific webhook signature. No Shipit session, `ApiClient` token, `webhook_secret`, GitHub App private key, or repository write access is needed by the attacker — only that the target Shipit deployment manages at least one other organization/app that has (as documented, optionally) no webhook secret configured.

### Likelihood Explanation
Multi-organization Shipit deployments are an explicitly supported and tested configuration (`Shipit.github(organization:)`, `secrets_double_github_app.yml` fixture) [12](#0-11) , and `webhook_secret` is documented as optional per app [5](#0-4) , so an operator can easily have one org configured without a secret (e.g. a low-value internal org) while other orgs hold sensitive production repos. In that realistic setup, the vulnerability is trivially exploitable with a single crafted HTTP POST to `/webhooks`, requiring no reconnaissance beyond knowing (or guessing) that some org in the instance lacks a secret and the target repo's `full_name`.

### Recommendation
Do not select the verifying `GitHubApp`/secret from unauthenticated payload data that differs from the field the handlers trust for repository resolution. Concretely:
- Verify the signature using the secret associated with the `Repository` resolved from `repository.full_name` (the same field the handlers use), not a separately-read `repository.owner.login`/`organization.login`.
- Reject events where `repository.owner.login` does not match the owner segment of `repository.full_name`.
- Consider requiring `webhook_secret` to be mandatory for every configured `GitHubApp` rather than optional, closing the always-verified bypass in `verify_webhook_signature`.

### Proof of Concept
Assume a Shipit instance configured with two orgs: `unsecured-org` (no `webhook_secret`) and `secured-org` (has a repo `secured-org/target-repo` with an active stack tracking branch `main`).

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<target-commit-sha-in-secured-org>",
  "state": "success",
  "context": "ci/attacker",
  "target_url": "https://attacker.example.com",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/target-repo"
  }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.

1. `verify_signature` computes `repository_owner = "unsecured-org"`, loads `Shipit.github(organization: "unsecured-org")`.
2. `verify_webhook_signature` returns `true` immediately because that app's `webhook_secret` is blank [4](#0-3) .
3. `create` dispatches to `StatusHandler`, which resolves `Commit.where(sha: params.sha)` — the commit belonging to `secured-org/target-repo` — and creates a `Status` record for it, with no relation to `unsecured-org` whatsoever [11](#0-10) .

The same technique applies to `push` (forcing `sync_github`) and `check_suite` (forcing check-run refresh) events by pointing `repository.full_name` at the target stack while keeping `repository.owner.login`/`organization.login` set to the unsecured org.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
