### Title
Cross-organization team membership takeover via unscoped `Team.find_or_create_by!(github_id:)` in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up teams solely by the attacker-suppliable, GitHub-global `github_id` integer, with no check that the requesting organization actually owns that team. Because webhook signature verification is keyed to `params.organization.login` / `params.dig('repository','owner','login')` rather than to the team being mutated, an attacker who owns any org (or an org with a blank `webhook_secret`) can send a signed `membership` webhook that names their own org but supplies a victim org's team `github_id`, causing `Membership` rows to be added/removed on that victim team.

### Finding Description
The broken binding, stated explicitly: **verifying-org(payload) == owning-org(team mutated)** must hold, i.e. `Shipit.github(organization: repository_owner)` (the org whose `webhook_secret` validated the signature) must equal `Shipit::Team.organization` of the row that gets mutated.

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the HMAC signature using `Shipit.github(organization: repository_owner).verify_webhook_signature` [2](#0-1) . Membership events carry no `repository` object, so `repository_owner` falls back to `params.organization.login` — a field fully controlled by the attacker's own payload/org.
2. `verify_webhook_signature` HMACs against that org's own `webhook_secret`, and explicitly returns `true` if the org's secret is blank [3](#0-2) . Either way, this only proves the request was issued by (or on behalf of) the org named in `params.organization.login`, i.e., the attacker's own org — it proves nothing about the `team.id` field elsewhere in the same payload.
3. `MembershipHandler`'s params schema only requires `team.id` to be an `Integer` — no relation to `params.organization.login` is enforced [4](#0-3) .
4. `find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id)`, and only inside the create-block (executed solely on first creation) sets `team.organization = params.organization.login` [5](#0-4) . On the `find` path — which is what happens when the `github_id` already belongs to a pre-existing victim team — the `organization` column is never read, checked, or re-validated against `params.organization.login`.
5. `process` then unconditionally calls `team.add_member(member)` or `team.members.delete(member)` on whatever `Team` record was found [6](#0-5) .

Attacker request: attacker registers/owns an org (`attacker-org`) already configured in `Shipit.github_teams`/`Shipit.github` (so `Shipit.github(organization: 'attacker-org')` resolves and signature verification succeeds using their own `webhook_secret`, or an org with a blank secret). They discover, via GitHub's public org-teams listing API, the numeric `github_id` of a team belonging to an unrelated org (e.g., `shopify/developers`, fixture `shopify_developers` with `github_id: 1`). They POST to `/webhooks` with header `X-Github-Event: membership`, signed for `attacker-org`, and body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Developers", "slug": "developers", "url": "https://example.com/shopify/developers" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-controlled-user" }
}
```
Because `Team#github_id` 1 already exists (owned by `shopify`), `find_or_create_by!` finds it (bypassing the create-block that would have set `organization`), and `team.add_member(attacker-controlled-user)` inserts a `Membership` row granting that user membership on Shopify's `developers` team — a team whose members are used elsewhere in the app for authorization (`Shipit.github_teams` membership grants access, e.g., stack/task permissions gated on team membership).

None of the existing guards catch this: `verify_signature` only authenticates "some request signed by org X," not "org X owns team Y"; `drop_unhandled_event` and the `ExplicitParameters` schema only check shape/type of `team.id`, not ownership; there is no `require_permission!` or team-organization equality check anywhere in this handler.

### Impact Explanation
A completely unprivileged attacker (owning any registered/blank-secret org) can add or remove arbitrary users to/from any `Shipit::Team` in the installation by simply knowing that team's public GitHub `github_id`, without ever authenticating as, or being invited by, the victim organization. Since `Shipit::Team` membership underlies `Shipit.github_teams`-based authorization elsewhere in the app, this is a direct escalation into `Shipit.github_teams` authorization — attacker can insert themselves (or an accomplice account) into a privileged team, or remove a legitimate member, for any tenant/org configured in the same Shipit instance. This is repeatable against arbitrary teams (any `github_id` visible via GitHub's public API) and arbitrary org boundaries, making it a cross-tenant authorization bypass — matching the "High: escalation into `Shipit.github_teams` authorization" (and arguably Critical, since it is an authorization bypass achieved via a webhook accepted from the wrong org).

### Likelihood Explanation
Preconditions are modest and realistic in multi-tenant Shipit deployments: (1) the attacker controls at least one org already present in `Shipit.github_teams`/configured with a `GitHubApp` (or one with a blank `webhook_secret`, which `verify_webhook_signature` explicitly treats as always-valid), (2) the victim team already exists as a `Shipit::Team` row (created from any prior legitimate `membership` webhook or `find_or_create_by_handle`), (3) the attacker knows the victim team's numeric `github_id`, which is exposed by GitHub's own public "list teams" endpoints for many org configurations. No Shipit secrets, sessions, or API tokens are needed — only the ability to send an HTTP POST to `/webhooks`, which is unauthenticated by design (protected only by per-org HMAC).

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (matching `params.organization.login`), e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify on the found record that `team.organization == params.organization.login` before performing any mutation, raising/aborting otherwise. Alternatively, verify webhook provenance directly against the team's actual owning organization rather than trusting the payload's self-reported `organization.login`.

### Proof of Concept
Minitest plan (webhooks controller test, no live GitHub):
```ruby
test ":membership webhook signed for a different org cannot mutate another org's team" do
  victim_team = shipit_teams(:shopify_developers) # github_id: 1, organization: 'shopify'

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'mallory' }
  }.to_json

  # Simulate that 'attacker-org' has its own (or blank) webhook_secret and passes verification
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(stub(verify_webhook_signature: true, api: stub(user: stub(login: 'mallory', id: 999))))

  assert_no_difference -> { Team.count } do
    post :create, body:, as: :json
  end

  victim_team.reload
  # Assert both sides of the binding after the request:
  assert_equal 'shopify', victim_team.organization          # owning org unchanged
  assert_includes victim_team.members.map(&:login), 'mallory' # but membership was mutated by attacker-org's request
end
```
The assertion `assert_includes victim_team.members.map(&:login), 'mallory'` demonstrates that a request authenticated as `attacker-org` successfully wrote a `Membership` onto a `shopify`-owned team, proving the provenance binding is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
