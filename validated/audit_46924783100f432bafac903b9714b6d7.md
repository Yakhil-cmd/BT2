### Title
Webhook signature is verified against an attacker-controlled organization while the acted-upon commit/repository is looked up globally, allowing cross-organization forged CI statuses - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the HMAC signature against based on `repository_owner`, a value read directly from the unverified JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes for *that* organization's secret, the handler dispatch (`StatusHandler`) never re-checks that the payload's `repository` actually belongs to the organization that authenticated the request. Worse, `StatusHandler#process` looks up commits by SHA alone, with no repository/stack scoping at all. This breaks the equality "organization that authenticated the webhook == repository/commit that gets written," matching the report's decimals/precision-mismatch pattern where one attribute is checked while a different, unguarded attribute is what actually gets used.

### Finding Description
In a Shipit deployment configured for multiple GitHub organizations (an explicitly documented/supported configuration, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), each org has its own `webhook_secret`: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is taken straight from the unauthenticated JSON body and is used purely to select *which secret* to HMAC-verify against [2](#0-1) . Nothing ties the selected organization to any other field in the payload — most importantly the `repository.full_name` that downstream handlers actually operate on.

`StatusHandler`, which processes the `status` event, ignores `repository` entirely and updates commits by SHA across the *entire* database: [3](#0-2) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Unlike `PushHandler`, which correctly scopes lookups through `stacks` (which resolves `Repository.from_github_repo_name(repository_name)`) before acting [4](#0-3)  and `Handler#repository_name`/`#stacks` helpers [5](#0-4) , `StatusHandler` never calls these repository-scoping helpers.

The commit's CI gate (`deployable?`) is directly derived from statuses attached by this handler: [6](#0-5) 

### Impact Explanation
An attacker who is a legitimate administrator of *their own* org's GitHub App (a normal, unprivileged setup — they know their own `webhook_secret` because they configured it) can forge a `status` webhook whose:
- `repository.owner.login`/`organization.login` = their own org (so `verify_signature` succeeds using a secret they legitimately possess),
- `sha` = the commit SHA of a target commit that belongs to a *different*, more sensitive stack/repository hosted on the same shared Shipit instance (commit SHAs are public GitHub data, easily discoverable),
- `state` = `success`, `context` = whatever context string is listed in the victim stack's `shipit.yml` `ci.require`.

Because `StatusHandler` does not scope by repository, this update lands on the victim commit regardless of which org "authenticated" the request. This satisfies `required_statuses`, flips `commit.deployable?` to `true` [6](#0-5) , and can be used to push a commit through CI gating and merge-queue validation for a repository the attacker has no legitimate access to (`merge.require`/`ci.require` documented at README.md lines ~446-505). This is a cross-organization/cross-repository write and directly enables an unauthorized deploy/merge, matching the required High/Critical impact categories ("cross-repository writes... an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires the host to run Shipit with more than one GitHub organization configured — a scenario the project explicitly documents and ships example config for (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`). No compromise of the victim org's webhook secret, GitHub token, or any Shipit session/API token is needed; the attacker only needs their own, independently-provisioned GitHub App installation and its secret, which they legitimately control. The only additional knowledge needed is the target commit SHA and a required status context name from the target's `shipit.yml`, both of which are either public (GitHub commit SHAs) or discoverable/guessable (common CI context names, or visible via the Shipit UI for the target stack).

### Recommendation
- In `WebhooksController#verify_signature` / `StatusHandler`, after signature verification, cross-check that the payload's `repository.full_name` actually belongs to the organization whose secret validated the signature, rejecting payloads where they disagree.
- Fix `StatusHandler#process` to scope the `Commit` lookup through the payload's own `repository` (using the same `stacks`/`repository_name` helper already used by other handlers) instead of a global `Commit.where(sha:)` query, so a status update can never cross repository/stack boundaries.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgOne` (victim, hosts the sensitive stack) and `OrgTwo` (attacker's own legitimately-installed GitHub App), as in `test/dummy/config/secrets_double_github_app.yml`.
2. As the administrator of `OrgTwo`'s GitHub App, compute a valid `X-Hub-Signature` HMAC-SHA1 over a crafted JSON body using `OrgTwo`'s own `webhook_secret`:
```json
{
  "sha": "<victim-commit-sha-from-OrgOne-repo>",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "owner": { "login": "OrgTwo" } }
}
```
3. POST this body with header `X-Github-Event: status` and the computed `X-Hub-Signature` to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")` and validates the HMAC successfully against the attacker's own secret.
5. `StatusHandler#process` executes `Commit.where(sha: "<victim-commit-sha>")`, finds the commit belonging to the `OrgOne` stack (unrelated to `OrgTwo`), and calls `create_status_from_github!`, marking it `success` for the required CI context — satisfying `commit.deployable?` for a repository the attacker never authenticated against.
