### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no join or filter against the repository/stack that authenticated the webhook. Any GitHub organization that has the Shipit GitHub App installed can therefore emit a validly-signed `status` event whose `sha` happens to match a commit that also exists in an unrelated victim stack (trivially achievable because git commit SHAs are content-addressed and identical across forks/mirrors), and that status will be written onto the victim's `Commit`/`Status` records, affecting `blocked?`/`deployable?` there.

### Finding Description
The invariant that should hold is:
`commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` row mutated by a `status` webhook.

The actual code breaks this: [1](#0-0) 
`process` loops over `Commit.where(sha: params.sha)` — every commit row across every stack/repository in the installation that shares that SHA — and calls `commit.create_status_from_github!(params)` on each one, with zero comparison to the repository that actually sent the webhook.

Contrast this with `PushHandler`, which scopes its writes to stacks matching the payload's own repository/branch: [2](#0-1) 
This shows the engine's own design intent is to scope webhook effects to the authenticated repository — `StatusHandler` simply omits that scoping.

`WebhooksController#verify_signature` only proves the payload was signed by the GitHub App installation for `repository_owner` taken from the payload itself; it says nothing about which `Commit`/`Stack` rows the SHA belongs to: [3](#0-2) 

`create_status_from_github!` then writes a `Status` row and re-evaluates commit state: [4](#0-3) 
And `blocked?`/`deployable?` are influenced by any commit's status via `blocking?`: [5](#0-4) 
so a forged `failure` (or `success`) status attached to a victim's `Commit` can flip `blocked?`/`deployable?` for a stack whose `blocking_statuses` include that context, gating or unblocking deploys for `stack.schedule_merges`/continuous delivery (`add_status`, `schedule_continuous_delivery`).

**Exploit flow:**
1. Attacker owns/controls a GitHub org/repo that has the (public) Shipit GitHub App installed — legitimately signed webhooks are produced by GitHub itself for this installation, so no secret is stolen.
2. Attacker obtains a commit with an identical SHA to one present in the victim's stack — e.g. by forking the victim's public repository (git SHAs are content-addressed and identical across forks/mirrors) or by pushing an identical tree/commit to their own repo.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a `status` payload for `context: ci/lint`, `state: failure`, and that shared `sha`, from their own repository. This passes `verify_signature` because it is a real, correctly signed event for the attacker's own installation.
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which finds the victim's `Commit` (matching SHA, but belonging to a different `Stack`/repository) via the unscoped `Commit.where(sha: ...)` and writes the forged status onto it.
5. If the victim's stack has `blocking_statuses` configured to include `ci/lint`, `blocked?`/`deployable?` flips for the victim's stack, gating or unblocking a real deploy/merge without any legitimate CI signal from the victim's own repository.

None of the existing guards prevent this: `verify_signature` validates *who sent* the webhook, not *which commit rows may be touched*; there is no `ExplicitParameters` repository check, no `require_permission!`, and `StatusHandler` performs no `stacks`/repository filtering unlike `PushHandler`.

### Impact Explanation
A payload authenticated for one repository mutates `Commit`/`Status` records belonging to another repository's stack, directly matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." Because `blocked?` gates `deployable?` and continuous delivery/merge scheduling, this can force an unauthorized deploy (clearing a real blocking failure with a forged success) or block a legitimate deploy (injecting a forged failure) on a completely unrelated tenant's stack. The attack is repeatable against any stack whose commits share a SHA with a repo the attacker can emit signed webhooks from (forks of public repos are the common case), so the blast radius spans all tenants hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) Shipit's GitHub App must be installable by third parties (typical for a public GitHub App used across many orgs) so the attacker can get GitHub to sign real webhooks for their own repo; (2) the attacker needs a commit whose SHA matches one present in the victim's stack, which is easy for any forked/mirrored public repository since git SHAs are content-addressed and independent of the remote; (3) the victim stack must have `blocking_statuses` configured for the forged `context` to get a deploy-gating effect (statuses on unrelated repos are otherwise just noise, but still constitute unauthorized cross-tenant writes regardless). Attacker cost is low (fork a public repo, push a `status` webhook), and the attack is fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler) to commits belonging to stacks whose repository matches the payload's `repository.full_name`/`repository.owner.login`, e.g. join through `Stack` and filter `Commit.joins(:stack).merge(Stack.where(repository_owner: ..., repository_name: ...)).where(sha: params.sha)`, mirroring the scoping already used in `PushHandler` via `stacks`.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, not part of the excluded paths since it's a new test asserting the vulnerability):
1. Create `stack_a` (repository `attacker/repo`) and `stack_b` (repository `victim/repo`), the latter with `blocking_statuses` including `ci/lint` configured in its deploy spec/stack config.
2. Create `commit_a` under `stack_a` and `commit_b` under `stack_b` with the **same** `sha` value (simulating a shared/forked commit).
3. Assert baseline: `commit_b.blocked?` is `false` and `commit_b.stack.deployable?` reflects normal state (binding: `commit_b.stack.repository.full_name == "victim/repo"`, no status yet referencing `attacker/repo`).
4. Build a `status` params hash with `sha: commit_a.sha` (shared with `commit_b`), `context: "ci/lint"`, `state: "failure"`, as if it came from `attacker/repo`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(params).process` (or dispatch through the documented handler entrypoint).
6. Assert `commit_b.reload.statuses.exists?(context: "ci/lint", state: "failure")` is `true` even though the webhook never referenced `victim/repo` — proving the equality `commit.stack.repository.full_name == payload_repository` is violated.
7. Assert `commit_b.blocked?` (or `stack_b.deployable?`) has changed as a result, demonstrating the cross-tenant deploy-gating impact.
