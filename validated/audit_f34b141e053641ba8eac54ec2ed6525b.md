### Title
Cross-organization webhook spoofing via mismatched signature-selection field and repository-lookup field in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App configuration (and therefore *which* `webhook_secret`) is used to validate the inbound HMAC based on `repository.owner.login` / `organization.login`, but the event handlers that actually mutate state pick the target `Stack`/`Repository` using an entirely different field, `repository.full_name`. Nothing ties these two fields together, so on a Shipit instance configured with multiple GitHub organizations (a documented, supported configuration), an admin of *one* organization can forge a webhook whose signature is valid for their own org but whose payload targets a *different* organization's repository/stack.

### Finding Description
`verify_signature` resolves the signing config purely from attacker-supplied payload fields, before any handler runs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects the `GithubApp`/`webhook_secret` for whichever org string is present in the JSON body. Shipit explicitly supports multiple GitHub orgs configured with independent `webhook_secret`s in the same instance: [3](#0-2) 

Once `verify_signature` passes, `create` hands the *entire* raw payload to the registered handlers: [4](#0-3) 

Every handler resolves the actual `Stack`/`Repository` to act on from a *different* JSON field, `repository.full_name`, with no cross-check against the org that was used to validate the signature: [5](#0-4) 

For example, `PushHandler` calls `stack.sync_github` on whatever stack matches `full_name`: [6](#0-5) 

The `status` handler records a `CommitStatus` directly from attacker-controlled payload fields (state/description/context/target_url) for the commit identified via `repository.full_name`, with no independent verification against GitHub's real API state — confirmed by the existing test that asserts fields are copied verbatim from the payload: [7](#0-6) 

**The broken binding, stated as an equality that is never enforced:**
`organization used to select verify_signature's webhook_secret (params.dig('repository','owner','login') || params.dig('organization','login'))` **≠** `organization implied by repository.full_name used by every Handler to pick the Stack/Repository written to`.

Before the attacker's request: only webhooks whose HMAC matches OrgA's secret and target OrgA's repositories are processed for OrgA's stacks (intended invariant, informally assumed but never checked).
After the attacker's request: a webhook validly signed with OrgA's secret can carry `repository.full_name = "OrgB/victim-repo"`, causing OrgB's stack to receive attacker-controlled state (spoofed CI status, forced sync, PR/review-stack transitions) even though the signature only proves the request originated from someone who knows OrgA's secret, not OrgB's.

### Impact Explanation
An admin/owner of any one GitHub organization configured on the shared Shipit instance (who legitimately knows that org's own `webhook_secret`, since GitHub exposes/lets them rotate it for apps they installed) can forge signed requests that are processed against another organization's tracked repositories. Via the `status`/`check_suite` handlers this allows injecting fabricated "success" CI statuses for a victim repository's commit that never actually passed CI, which can satisfy `ci.require` gating and lead to an unauthorized deploy of that commit — matching the Critical criterion "unauthorized deploy, rollback or merge." This requires no Shipit session, `ApiClient` token, `api_clients_secret`, or GitHub App private key — only knowledge of a webhook secret for an org the attacker legitimately administers, distinct from the victim org whose repository is affected.

### Likelihood Explanation
High for any Shipit deployment using the documented multi-organization configuration (explicitly shown in `config/secrets.development.shopify.yml` and referenced in `docs/setup.md`). The attack requires only crafting a raw HTTP POST with a correctly computed HMAC-SHA1 over a JSON body whose `repository.owner.login`/`organization.login` names the attacker's own org while `repository.full_name` names the victim org's tracked repository — no interaction with GitHub's real webhook delivery pipeline is required since the endpoint accepts any POST with a matching signature header.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler`, derive the organization used for both signature verification and repository/stack resolution from the *same* trusted field, and explicitly assert equality between the org implied by `repository.full_name` (or `repository.owner.login`) and the org whose secret validated the signature before dispatching to any handler. Reject the webhook if they diverge.

### Proof of Concept
1. Shipit is configured with two orgs, `orga` and `orgb`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` pattern), and each tracks stacks for their own repositories.
2. Attacker is an admin of the GitHub App installed on `orga` and therefore knows `orga`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "orgb/victim-repo", "owner": { "login": "orga" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(orga_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"orga"` → looks up `orga`'s `GithubApp` → signature verifies successfully (per `app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `StatusHandler` (via `Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) resolves the target repository from `repository.full_name` = `"orgb/victim-repo"`, and records a forged "success" `CommitStatus` on `orgb`'s tracked commit, even though the request was never signed by `orgb`.

**Note on limits:** I was unable to open `status_handler.rb` and `check_suite_handler.rb` directly in the final iteration (tool call error), so the exact write logic for those two handlers is inferred from `Handler#repository_name`, `PushHandler`, and the corroborating test in `webhooks_controller_test.rb` rather than a direct read of their source. If precise confirmation of `CommitStatus` write semantics or downstream auto-merge/auto-deploy gating logic (`merge_request.rb`, `stack.rb`) is required, a Devin session with full repository access should verify those files directly.
