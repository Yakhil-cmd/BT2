### Title
Cross-Organization Webhook Signature Confusion Allows Forged CI Status / Push Events for Any Tracked Repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), a field taken from the *same unauthenticated JSON body* it is about to verify. Every downstream `Shipit::Webhooks::Handlers::Handler` then resolves the *actual* target repository/stack using a different field from that same body, `repository.full_name`. These two fields are never checked for consistency, and in the documented multi-organization configuration, an organization with no `webhook_secret` set becomes an unauthenticated pivot to forge events (e.g. `status`, `push`) against any other, properly-configured organization's repositories.

### Finding Description
`verify_signature` picks the org used to fetch the verification secret purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-org config from `secrets.github` in multi-app mode, as documented for "Using Multiple Github Applications": [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as always-valid ("optional" per setup docs): [4](#0-3) 

Meanwhile, every webhook handler resolves the *repository actually acted upon* from a completely different payload field, `repository.full_name`, which is not tied in any way to the `repository.owner.login`/`organization.login` used for signature-key selection: [5](#0-4) 

Because both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside the same POST body, an attacker who knows (or is themselves the owner of) an organization "OrgAttacker" configured in Shipit *without* a `webhook_secret` can:
1. Set `repository.owner.login` (or top-level `organization.login`) to `"OrgAttacker"` so `verify_signature` fetches `OrgAttacker`'s `GitHubApp`, whose `verify_webhook_secret` unconditionally returns `true`.
2. Set `repository.full_name` to `"VictimOrg/victim-repo"` — a real, tracked repository belonging to a different, properly-secured org.
3. The request passes `verify_signature` (step 1) and is then dispatched to handlers that resolve and act on `VictimOrg/victim-repo` (step 2), with no requirement that the two organizations match.

This breaks the intended binding: *the organization whose secret authenticated the request* should equal *the organization/repository the request is permitted to write to*. The equality that should hold is `repository_owner (verified) == repository.full_name.owner (acted upon)`, and nothing in the engine enforces it.

### Impact Explanation
The `status` webhook handler creates `Shipit::Status` records straight from payload fields (`state`, `description`, `target_url`, `context`) for a matched commit, as shown by the fixture-driven test asserting status attributes are copied verbatim from the payload: [6](#0-5) 

Commit statuses gate Shipit's merge-queue / deploy readiness checks (`Shipit::Status`/`Shipit::MergeRequest` consult these records to decide mergeability). An attacker abusing the org-confusion described above can forge a `success` status on a real commit of `VictimOrg/victim-repo` without ever possessing that org's webhook secret, potentially causing an unauthorized merge or deploy to proceed as if CI had passed — i.e., an unauthorized deploy/merge, which is explicitly a Critical-severity outcome under the engine's own scope rules. The `push` handler can similarly enqueue `GithubSyncJob` for the victim's stack; while that job re-fetches real commits via the GitHub API (limiting direct data injection), forged `status` events give a more direct write of attacker-controlled state.

### Likelihood Explanation
Exploitability strictly requires the deployment to run in the documented multi-organization mode (`docs/setup.md`, "Using Multiple Github Applications") with at least one configured organization lacking a `webhook_secret` — a state the setup documentation itself presents as a normal, supported configuration (`webhook_secret: # nil` shown in example YAML and in `config/secrets.development.shopify.yml`). Any operator who onboards one org without setting a webhook secret (e.g., during initial setup, or a low-risk internal org) inadvertently opens every other org's repositories to spoofing, with no privileged credential, session, or API token required — purely an unauthenticated POST to `/webhooks`.

### Recommendation
Do not use payload-supplied fields to select the verification key and then use a different, unrelated payload field to select the write target. Concretely:
- After successfully verifying with a given org's app, require that `repository.full_name`'s owner matches the org that supplied the secret (or that the resolved `Repository`/`Stack` is actually owned by that verified organization) before invoking any handler.
- Alternatively/additionally, stop treating "no `webhook_secret` configured" as an implicit "always verified" bypass; require an explicit opt-in flag if operators intentionally want unauthenticated webhooks for a given org, and never let that bypass extend to resolving/acting on other organizations' repositories.

### Proof of Concept
1. Configure Shipit in multi-org mode with two orgs: `VictimOrg` (has `webhook_secret: real-secret`, and a tracked repo `VictimOrg/victim-repo`) and `AttackerOrg` (`webhook_secret` left unset/nil), per the documented schema in `docs/setup.md` lines 182-209.
2. As an unauthenticated network attacker (no GitHub credentials, no Shipit session), POST to `/webhooks` with:
   - Header `X-Github-Event: status`
   - Body: `{"repository": {"owner": {"login": "AttackerOrg"}, "full_name": "VictimOrg/victim-repo"}, "sha": "<real sha on victim-repo>", "state": "success", "context": "ci/required-check", "target_url": "https://attacker.example.com"}`
   - No valid `X-Hub-Signature` needed (or any arbitrary value), because `verify_webhook_signature` for `AttackerOrg` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, which passes verification trivially, then `Shipit::Webhooks.for_event('status')` handlers run and create/update a `Shipit::Status` for the given sha under `VictimOrg/victim-repo` (resolved via `repository.full_name`, per `app/models/shipit/webhooks/handlers/handler.rb:36-38`), exactly as exercised by the existing test `":state create a Status for the specific commit"` (`test/controllers/webhooks_controller_test.rb:42-59`), but now with attacker-chosen state/target_url/description on a repository the attacker never authenticated against.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
