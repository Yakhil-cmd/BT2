## Title
Stale attestations for reassigned/rotated addresses are not invalidated in the oscript `attestation[[]]` formula, unlike the equivalent `attested` definition primitive - ([File: formula/evaluation.js])

### Summary
The `code-423n4` report describes a "domain expiry" bug where a name→address mapping is not invalidated when the underlying ownership changes (address definition/registration change), so getters keep returning the *previous* owner's data. ocore has a directly analogous mapping concept: an **attestor's claim about an address** (`attestations` / `attested_fields` tables), which is looked up by address to authorize behavior in bots and AAs. ocore already anticipated the "stale claim survives ownership change" problem for one code path — `storage.filterAttestedAddresses()`, used by `'attested'` in `definition.js` and by attested-asset spend checks — but the semantically equivalent `attestation[[...]]` oscript function used inside Autonomous Agents (`formula/evaluation.js`) omits this safeguard entirely.

### Finding Description
`storage.filterAttestedAddresses()` explicitly guards against an attestation surviving a later change of the address's definition (i.e., a change of who controls the address, analogous to "domain re-registered by a new owner"): [1](#0-0) 
It requires `main_chain_index > IFNULL(<mci of the last address_definition_change>, 0)` — i.e. an attestation is only honored if it postdates the most recent definition change of that address. This is used by the `'attested'` definition primitive: [2](#0-1) 

However, the `attestation[[...]]` oscript function evaluated inside AAs (`case 'attestation':` in `formula/evaluation.js`) performs the *same kind of lookup* — "what did attestor X say about address Y" — but with **no check against `address_definition_changes`** at all. It simply selects the latest attestation row for the address/attestor/field, first checking unstable AA-authored units and then stable units: [3](#0-2) 

An address in ocore is not immutable ownership-wise: its controlling keys can be changed via an `address_definition_change` message (single-sig key rotation, multisig membership change, or handing over control of a shared/vanity address to a different signer set) while the address string itself stays the same — exactly the same shape of problem as the name-service bug, where the *identifier* (name / address) stays constant but the *actual controller* changes, and a getter (`get_address_from_name` / `attestation[[]]`) keeps surfacing data tied to the old controller.

### Impact Explanation
AAs commonly gate fund transfers, whitelisting, or KYC-style logic on `attestation[[attestors=..., address=$trigger.address]].field` (e.g., "is this address KYC-verified", "is this address on our whitelist", "what tier does this address belong to"). If:
1. Attestor A attests address X with `profile={verified:true}` while X is controlled by Alice.
2. X's definition is later changed (key rotation, sale of a shared/vanity address, or address reused by a different party via a definition template) so that a different party (Bob) now controls X.
3. Bob triggers the AA from address X.

The AA's `attestation[[attestors=A, address=X]]` call still returns Alice's old attestation data (`verified:true`), because there is no `address_definition_changes` cutoff check, unlike `filterAttestedAddresses`. This can let Bob impersonate a previously-verified identity to withdraw funds, bypass KYC/whitelist gating, or otherwise obtain AA-controlled funds/permissions that should require a fresh attestation — a direct funds-loss/permission-bypass analog of the reported bug, reachable simply by any user triggering an AA that relies on `attestation[[]]` after posting an ordinary `address_definition_change` unit for an address they now control.

### Likelihood Explanation
Reaching this requires only standard, unprivileged actions available to any AA trigger sender: (1) obtaining/rotating control of an address that was previously attested (a routine operation via `address_definition_change`, or by being handed a multisig/shared address whose signer set later changes), and (2) triggering an AA that uses `attestation[[...]]` for authorization on that address. No attestor cooperation, no privileged role, and no network/consensus manipulation is required — this mirrors the "specific but reachable sequence of ordinary actions" that the original report was scored Medium for.

### Recommendation
Add the same anti-staleness guard used in `storage.filterAttestedAddresses()` to the `attestation[[...]]` formula evaluator in `formula/evaluation.js`: require that the attestation's `main_chain_index` (or `latest_included_mc_index`/`level` for unstable AA-authored units) be strictly greater than the MCI of the most recent `address_definition_changes` record for the queried address, so attestations issued before the last known change of control over the address are not honored.

### Proof of Concept
Conceptual reproduction (cannot be executed here, but follows directly from the code above):
1. Attestor `A` posts `attestation` message: `{address: X, profile: {tier: "gold"}}` while `X` is defined by Alice's key.
2. Alice posts an `address_definition_change` for `X`, transferring control to Bob's key (e.g., part of normal multisig/shared-address workflow, or vanity-address resale via cosigned handoff).
3. Bob (using the new definition of `X`) triggers an AA whose bytecode contains `attestation[[attestors=A, address=trigger.address]].tier`.
4. Per `formula/evaluation.js` lines 966-1006, the query only filters by `attestor_address`, `address`, and `main_chain_index<=mci` — it never checks `address_definition_changes` — so it returns `"gold"`, the attestation intended for Alice, letting Bob's trigger pass the AA's gold-tier check/fund release though only Alice was ever verified.
5. Compare with `'attested'` in `definition.js` (line 904-915) → `storage.filterAttestedAddresses` (storage.js 1959-1974), which would correctly reject this because `main_chain_index` of the attestation is not greater than the `address_definition_changes` MCI for `X`. [4](#0-3) [1](#0-0) [2](#0-1)
