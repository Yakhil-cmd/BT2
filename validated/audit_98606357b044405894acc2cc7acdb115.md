### Title
Late-delegator dilution/theft of accumulated `pending_delegator_rewards` in block revenue sharing (SIMD-0123) - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
The Autonomint bug (`BorrowLib::redeemYields`) distributed a pooled yield (`usdaToAbondRatioLiq`) pro-rata to *current* token holders without tracking which holders contributed to or were entitled to that pool, letting a late minter steal yield accrued from earlier liquidations. Agave's block-revenue-sharing reward path (SIMD-0123) has the analogous structural weakness: `pending_delegator_rewards` is an undifferentiated pot on the vote account that accumulates over an unbounded number of epochs, and it is redeemed to stakers purely pro-rata to their *current-epoch* effective stake, with no per-staker checkpoint analogous to `credits_observed` for inflation rewards.

### Finding Description
`pending_delegator_rewards` is a single running total stored on the `VoteStateV4` account, incremented via the permissionless `DepositDelegatorRewards` vote instruction [1](#0-0) , using `add_pending_delegator_rewards`, which simply performs a `checked_add` with no timestamping or per-depositor bookkeeping [2](#0-1) .

At epoch-boundary reward calculation, `calculate_block_reward` distributes this entire pool pro-rata using only the *current reward epoch's* `total_active_stake` (from `RewardEpochDelegatedStakes`) and the stake's *current* effective stake — there is no notion of how long a given stake delegation has been active relative to when the pool accumulated:

```
let pending_delegator_rewards = vote_state.pending_delegator_rewards();
...
let total_active_stake = reward_epoch_delegated_stakes.delegated_stakes.get(&vote_pubkey)...
...
(pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
``` [3](#0-2) 

Contrast this with the inflation-rewards path, which explicitly guards against exactly this class of bug by tracking `credits_observed`/`initial_epoch_credits` per stake account so a stake only earns credits for the period during which it was actually delegated [4](#0-3) [5](#0-4) . The block-revenue-sharing pool has no equivalent checkpoint: `pending_delegator_rewards` is deposited by anyone at any time (e.g. a validator depositing MEV/block revenue across many epochs while the pool sits undistributed), and whoever holds delegated stake to that vote account at the moment the pool is finally redeemed collects a full pro-rata share as if they had been staked the entire accumulation period.

This is the same root cause as the reported issue: the distribution ratio is computed from the *current* total-supply/total-stake snapshot with no accounting for which participants contributed to (or existed during) the accrual of the shared pool, so newcomers can capture value earned by (or intended for) earlier participants.

### Impact Explanation
A staker who delegates to a vote account shortly before that vote account's `pending_delegator_rewards` pool is redeemed at an epoch boundary receives a full pro-rata cut of a pool that may have taken many epochs (or many other stakers who have since undelegated) to accumulate, diluting or outright displacing the payout that longer-term/earlier delegators should have received. Because commission/collector logic and stake accounting are otherwise correct, this results in concrete misattribution of lamports between stakers — value that should flow to earlier delegators is instead captured by a delegator with no matching contribution period, which matches the "concrete theft or misattributed rewards" bar.

### Likelihood Explanation
Exploitation requires only ordinary, unprivileged actions: delegating stake to a vote account before an epoch reward calculation and undelegating afterward. It does not require a flashloan-style single-transaction attack because stake must go through the normal warm-up and be reflected in `RewardEpochDelegatedStakes`/`delegation_effective_stake` for the rewarded epoch, but it requires nothing beyond staking for the minimum activation period — well within reach of any user, and worsened the longer a validator waits (or is unable, due to `REWARD_CALCULATION_NUM_BLOCKS`/partitioning delays) to redeem accumulated `pending_delegator_rewards`.

### Recommendation
Track per-stake (or per-epoch) attribution of `pending_delegator_rewards`, e.g. record the stake amount and epoch a deposit was made and only allow delegations active since that deposit to share in it, or drain/distribute the pool incrementally each epoch instead of allowing unbounded accumulation, mirroring the `credits_observed` checkpoint pattern already used for inflation rewards.

### Proof of Concept
No proof-of-concept was constructed; the finding is derived from static analysis of `calculate_block_reward` and `deposit_delegator_rewards`/`add_pending_delegator_rewards`. Note: due to tool-call budget limits, I was unable to confirm from the code whether/where `pending_delegator_rewards` is decremented after being redeemed at distribution time (the decrement logic was not located within the explored files: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` and `runtime/src/bank/fee_distribution.rs` contained related matches but were not fully inspected). This does not affect the core finding — the pro-rata split itself lacks any per-depositor/time-weighted accounting — but a follow-up review of the redemption/decrement path is recommended to fully confirm whether the pool is drained in a single shot (maximizing the described dilution) or partially retained.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Returns how many credits the stake actually earned based on what it has already observed and
/// the vote account has recorded.
///
/// Also updates the `new_credits_observed` as a side effect.
fn calc_earned_credits(
    stake: &Stake,
    final_epoch_credits: u64,
    initial_epoch_credits: u64,
    new_credits_observed: &mut u64,
) -> u128 {
    let credits_in_stake = stake.credits_observed;

    // figure out how much this stake has seen that
    //   for which the vote account has a record
    let earned_credits = if credits_in_stake < initial_epoch_credits {
        // the staker observed the entire epoch
        final_epoch_credits - initial_epoch_credits
    } else if credits_in_stake < final_epoch_credits {
        // the staker registered sometime during the epoch, partial credit
        final_epoch_credits - *new_credits_observed
    } else {
        // the staker has already observed or been redeemed this epoch
        //  or was activated after this epoch
        0
    };
    *new_credits_observed = (*new_credits_observed).max(final_epoch_credits);
    u128::from(earned_credits)
}
