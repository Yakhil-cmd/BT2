### Title
Uncaught exception in `definition template` authentifier evaluation crashes/restarts the node — (File: `definition.js`)

### Summary
`Definition.validateAuthentifiers()` in `definition.js` evaluates a `'definition template'` operator by querying for the referenced template unit and, if the query does not return exactly one row, throws a bare `Error` from inside an asynchronous `conn.query` callback instead of passing an error to the continuation callback. Because the throw happens inside an async DB callback, it cannot be caught by any synchronous `try/catch` in the call chain, so it propagates as a Node.js `uncaughtException`. `network.js` installs a global `process.on('uncaughtException', ...)` handler that logs the error and then explicitly re-throws it to crash the process ("crash the process to avoid ending up in an inconsistent state"). This is directly analogous to CVE-2016-1405, where a crafted document caused libclamav/AMP to hit an unhandled fault and restart the scanning process.

### Finding Description
When authentifiers/signatures for a unit's author (or an asset condition) are validated, `evaluate()` inside `validateAuthentifiers` handles the `'definition template'` case: [1](#0-0) 

If `rows.length !== 1` (template unit not found, not yet stable/good at the required `main_chain_index`, or otherwise not resolvable), the code does `throw Error("not 1 template")` inside the `conn.query` callback rather than invoking `cb2` with an error. Contrast this with the *definition-creation-time* validator `validateDefinition()`'s handling of the same op, which gracefully returns `cb("template not found or too many")`: [2](#0-1) 

Because `'or'`, `'and'`, and `'r of set'` branches in `validateAuthentifiers.evaluate()` are evaluated unconditionally for *all* branches (the code explicitly comments "check all members, even if required minimum already found"): [3](#0-2) 
an attacker does not need to control the actual signing branch — they only need one alternate branch in the address definition containing a `'definition template'` op whose referenced condition can later fail to resolve to exactly one row at unit-signing time.

`validateAuthentifiers` is invoked from `validateAuthor()` in `validation.js`, which is part of the normal per-unit validation path reachable by any unit poster (an attacker broadcasting or posting a unit signed with such an address triggers this evaluation): [4](#0-3) 

Since the throw fires inside an async `conn.query` callback, it escapes all `try/catch` blocks wrapping the validation call stack and becomes a Node `uncaughtException`. `network.js` registers a top-level handler that intentionally re-throws to kill the process: [5](#0-4) 

### Impact Explanation
Any node (full node/hub) that validates a unit signed by an address whose definition contains a `'definition template'` branch referencing a unit that no longer/ever resolves to exactly one stable, good `definition_template` message at the relevant `last_ball_mci` will crash with an uncaught exception. The top-level handler intentionally re-throws to terminate the process, matching the "process restart"/denial-of-service class of CVE-2016-1405. This can be triggered by an unprivileged unit poster whose signing/co-author address happens to use such a definition (or by any address owner deliberately crafting one), causing repeated crashes on any node that attempts to validate the offending unit — a network-wide DoS against nodes trying to confirm/relay/replay that unit.

### Likelihood Explanation
Medium-High. `'definition template'` is a legitimate, documented oscript operator, and any address (or asset condition) can include it inside an `'or'`/`'and'`/`'r of set'` branch that is never actually used for a real signature. Because branches are always fully evaluated by `validateAuthentifiers`, the condition (`rows.length !== 1`) is trivially reachable at signing time if the referenced template unit is not found, or is not yet stable/good by the relevant `last_ball_mci`, or is found more than once. Unlike `validateDefinition` (address-creation time), this code path lacks any graceful-error fallback, so it will always crash rather than reject the unit.

### Recommendation
Change the `throw Error("not 1 template")` in `definition.js`'s `validateAuthentifiers` (line 812) to invoke `cb2(false)` (treat as authentifier-branch failure) instead of throwing, mirroring the graceful error handling already used in `validateDefinition`'s equivalent branch. Audit other bare `throw Error(...)` statements inside async DB callbacks reachable from unit validation (e.g., the `'address'` case at line 795, and similar throws in `storage.js`/`validation.js`) for the same async-uncaught-exception hazard, and convert them to callback-based error propagation.

### Proof of Concept
1. Create/control address `A` with a signature-based definition wrapped as:
   `['or', [ ['sig', {pubkey: P}], ['definition template', ['<unit_not_resolving_to_exactly_one_row>', {}]] ]]`
   Register this definition normally via `validateDefinition` at address-creation time; at that point the referenced template unit resolves to exactly one row (stable, good, `main_chain_index <= last_ball_mci`), so the definition is accepted.
2. Later — or on a node with a different view of stability/finality for the referenced unit, or simply by choosing a template unit reference that never resolves (0 rows) or resolves multiple times (>1 rows) at the `last_ball_mci` used when signing — post/broadcast a new unit authored by address `A`, signed correctly via the `'sig'` branch.
3. During validation, `validateAuthentifiers`'s `evaluate()` still evaluates the sibling `'definition template'` branch (per the "check all members" behavior) and issues the `conn.query`. When the row count is not exactly 1, `throw Error("not 1 template")` fires inside the async callback.
4. This exception is uncaught by any synchronous try/catch, propagates to `process.on('uncaughtException', ...)` in `network.js`, which re-throws it, crashing the node process — denial of service, analogous to the ClamAV AMP process-restart vulnerability in CVE-2016-1405.
