### Title
Stale-but-valid Pyth price update pinned via `price-feeds` param manipulates shared oracle state used by other users' operations - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-feeds` is an optional parameter accepted by several public, unprivileged entrypoints (`borrow`, `collateral-add`, `collateral-remove`, `liquidate`, `supply-collateral-add`) that lets *any* caller push a signed Pyth update into the market's shared oracle state via `write-feeds`/`write-feed` [1](#0-0) . The record of "last accepted timestamp" for a feed is stored in a single global map `last-update { type, ident } -> uint`, not per-caller [2](#0-1) . `price-resolve` only requires that the submitted timestamp be within `max-staleness` and not older than the previously stored value — it never checks that the price is the *most recent* signed update available [3](#0-2) .

### Finding Description
Because the freshness gate is `(<= delta max-staleness) AND (>= ts prev)` rather than "must be the newest available Pyth update," a caller holding a signed-but-slightly-old Pyth VAA (still inside the `max-staleness` window, e.g. up to 300s for stable assets, 60-120s for volatile ones) can choose *when* and *which* valid price to submit. Submitting it through any of the public write-feeds-enabled entrypoints overwrites the shared `last-update` timestamp for that asset globally [4](#0-3) . This shared price/timestamp is then consumed by every other unrelated caller who omits `price-feeds` (which is optional and defaults to doing nothing, see `write-feeds`) on their own borrow/collateral/liquidate calls [5](#0-4) .

Concretely: a borrower whose position is close to the liquidation threshold can, right before a real price move against them, submit an older-but-still-"fresh" signed update that shows a more favorable price for their collateral/debt asset through a cheap public call (e.g., a trivial `collateral-add`). This primes the shared `last-update`/oracle state. A liquidator who then calls `liquidate` with `price-feeds` = `none` (the common case, since prices are usually assumed fresh) will have their health computation (`current-ltv`) evaluated against this attacker-pinned stale price rather than the true current market price, because `oracle-timestamp-fresh` only checks staleness/monotonicity, not recency versus other currently-valid signed updates [6](#0-5) .

### Impact Explanation
- Without the attacker's transaction: the liquidator's `liquidate` call resolves the true, freshest Pyth price, correctly computes `current-ltv >= ltv-liq-partial`, and the liquidation succeeds, seizing collateral and repaying debt.
- With the attacker's transaction: the shared oracle timestamp/price for the relevant asset is pinned to an older, self-favorable (but still "fresh enough") value. The liquidator's `liquidate` call (which does not independently push a corrective price update) computes a healthier LTV, the `ERR-HEALTHY` check fires, and liquidation is blocked or delayed for the duration of the staleness window.
- This is a **temporary freezing of funds**: the liquidator cannot seize collateral it is entitled to during the window, and/or the protocol's vault suppliers bear extended exposure to an under-collateralized position, worsening insolvency risk if the price continues to move adversely before a fresher update is submitted.

### Likelihood Explanation
Likelihood depends on Pyth's actual signing/validity semantics for VAAs (how long a signed update stays acceptable to the underlying `pyth-pnau-decoder-v3`/`wormhole-core-v4` verification, and whether `pyth-storage-v4.write` itself independently enforces monotonic timestamps that would block this). This part of the mechanism (`local-testing/contracts/pyth/contracts/pyth-storage-v4.clar`) was not fully inspected due to iteration limits, so it is **not confirmed** whether the storage layer additionally rejects a non-increasing-timestamp write from a different submission attempt. If it does enforce strict monotonicity across all writes regardless of caller, this analog is materially weakened (an attacker's stale price could only ever be accepted if no fresher one had been submitted yet, narrowing the exploit window to periods when nobody else refreshes the feed). The `price-feeds` parameter being optional and defaulting to `none` on hot paths (`borrow`, `liquidate`) means most callers rely on whatever price state currently exists, which is the precondition that makes this shared-state class of bug reachable.

### Recommendation
- Require `oracle-timestamp-fresh` to reject accepting a submitted price whose timestamp is older than the timestamp of the most recently *known-to-exist* signed update, not merely older than the last one the contract happened to store.
- Consider requiring `liquidate`/`liquidate-multi` to mandate a `price-feeds` update (or at minimum re-verify against a tighter staleness bound) rather than allowing `none`, since liquidation health is uniquely time-sensitive and adversarial actors have a direct incentive to manipulate the shared timestamp just before being liquidated.
- Rate-limit or restrict who can update oracle state for a given feed within a short window, or make the accepted price the max of (submitted, currently cached) rather than blindly overwriting.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
