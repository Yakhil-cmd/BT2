### Title
Hardcoded, non-upgradable `ADDRESS_REGISTRAR_ACCOUNT_ID` in the ETH Wallet Contract permanently DOSes base-token transfers and strands external-caller deposits if the registrar breaks - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The wallet-contract (deployed as the global contract behind every eth-implicit account) hard-codes the address of the "address registrar" contract at compile time via `include_str!("ADDRESS_REGISTRAR_ACCOUNT_ID")` [1](#0-0) , and there is no admin/method to update this value post-deployment. This is structurally analogous to the `operatorFilterRegistry` bug class: a required external dependency that, if it becomes unresponsive or always fails, permanently blocks a whole class of otherwise-legitimate operations, and in this case can also strand user funds that were not refunded.

### Finding Description
Whenever an eth-implicit wallet-contract account executes a base-token transfer to another eth-implicit account whose address is not yet known to be registered, `inner_rlp_execute` must first perform a cross-contract call to the hardcoded registrar to check whether the target is a "named" account before it can safely proceed: [2](#0-1) 

The registrar's account ID is parsed from a value embedded in the compiled wasm at build time, with no setter/updater method anywhere in the contract: [1](#0-0) 

The callback that processes the registrar's response, `address_check_callback`, treats `PromiseResult::Failed` (i.e., the registrar call reverting, panicking, running out of gas, or the account no longer existing/being redeployed incompatibly) as a terminal error and returns immediately — without issuing any refund of the `caller_deposit` that an external, non-self relayer/caller may have attached: [3](#0-2) 

This differs from the general failure-handling in `rlp_execute_callback`, which does explicitly refund `caller_deposit` on `PromiseResult::Failed`: [4](#0-3) 

`CallerDeposit` is constructed for any external (non-self) predecessor account that attaches a non-zero deposit to `rlp_execute`: [5](#0-4) 

Because `ADDRESS_REGISTRAR_ACCOUNT_ID` is baked into the wasm binary rather than being a mutable, settable field on the contract, every already-deployed wallet-contract instance is permanently bound to that one account. If the registrar account is deleted, upgraded incompatibly, runs out of gas/storage, or is otherwise made to fail on every call, every `EOABaseTokenTransfer` requiring `address_check` becomes permanently un-executable for that wallet, exactly mirroring the `operatorFilterRegistry` DOS pattern described in the report (a single external dependency, with no owner-controlled override, whose breakage locks a whole category of transfers). Additionally, unlike the general-purpose refund path, this particular failure path drops any attached deposit from an external caller without refunding it.

### Impact Explanation
- Denial of service: any base-token transfer from an eth-implicit account to another not-yet-registered eth-implicit account becomes permanently unexecutable once the hardcoded registrar breaks, with no way for anyone (not even the account owner) to point the contract at a working registrar, since the value is compiled into the wasm.
- Unauthorized loss of funds: an external caller (non-self predecessor) who attaches a deposit to `rlp_execute` for a transfer requiring `address_check` will have that deposit consumed by the wallet contract and not refunded if the registrar call fails, because `address_check_callback`'s `PromiseResult::Failed` branch never inspects `caller_deposit`.

### Likelihood Explanation
This does not require a malicious validator or privileged actor — a normal user/relayer transaction routed through `rlp_execute` reaches this code path whenever the target is another eth-implicit account not already known to the registrar. The registrar becoming unavailable (deleted, redeployed with a breaking interface change, out of storage/gas, or otherwise made to always fail) is a plausible operational failure mode for any external contract dependency, and once it occurs, the effect is deterministic and reproducible for every affected transaction.

### Recommendation
- Make the registrar account ID a mutable contract field settable only by a privileged/owner call (with appropriate access control), instead of a compile-time constant, so a broken registrar can be replaced.
- In `address_check_callback`, refund `caller_deposit` on the `PromiseResult::Failed` branch, consistent with the handling in `rlp_execute_callback`, so external callers do not lose deposits when the registrar dependency fails.

### Proof of Concept
1. Deploy the wallet-contract global contract with `ADDRESS_REGISTRAR_ACCOUNT_ID` pointing at some registrar account `R`.
2. Cause `R` to always fail (e.g., delete `R`'s account, or deploy code to `R` that panics on `lookup`).
3. Have an external relayer account call `rlp_execute` with an attached deposit for an eth-implicit-account signer whose signed Ethereum transaction is a base-token transfer to a *different*, unregistered eth-implicit account (`target_kind = EthImplicit(address)`), triggering the `address_check: Some(address)` branch in `internal::parse_rlp_tx_to_action` [6](#0-5) .
4. Observe that `inner_rlp_execute` dispatches the call to `R.lookup` then `address_check_callback` [2](#0-1) .
5. Since `R` always fails, `address_check_callback` hits the `PromiseResult::Failed` branch and returns an error response without refunding the relayer's attached deposit [3](#0-2) ; the transfer never succeeds and can never succeed again for this transaction shape, and the relayer's deposit remains with the wallet contract.

Note: I could not fully trace how/whether wallet-contract instances get upgraded to a new global-contract code hash across the network (which could mitigate the "permanently unfixable per-instance" characterization) — that would require examining the global-contract deployment/redeployment and eth-implicit-account wiring in more depth than the indexed context allowed. If precise confirmation of deployment/upgrade mechanics is needed, a full Devin session with repository access would be required.
