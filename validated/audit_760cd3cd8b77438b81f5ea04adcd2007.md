This confirms the vulnerability. The webhook signature is verified per-organization (keyed by `repository_owner`), and multiple GitHub organizations can be configured under one Shipit instance, each with its own webhook secret. Critically, `StatusHandler#process` never checks which repository/organization the status webhook came from — it looks up matching commits purely by SHA across the entire database, then attaches the status to whatever stack that commit row already belongs to.### Title
`StatusHandler#process` matches commits by SHA only, letting a validly-signed webhook from any tracked GitHub organization forge a `success` status on another stack's commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Webhooks::Handlers::StatusHandler#process` looks up target commits with `Commit.where(sha: params.sha)`, with no check that `payload['repository']['full_name']` matches the repository/stack the commit actually belongs to. Combined with `Commit#deployable?` trusting `status` (built from whatever `Status` rows exist for that commit), a 'status' webhook that is validly signed for *any* GitHub organization configured in Shipit can inject a fabricated `success` status onto a commit belonging to an unrelated stack/repository whose commit history happens to share that SHA, causing `Stack#trigger_continuous_delivery` to deploy a commit that never passed CI in its own repository.

### Finding Description
The binding the code should enforce is: `status.stack == commit_being_evaluated.stack_belongs_to_repository_that_emitted(status)`. This binding is broken because `StatusHandler#process` never consults the payload's `repository` at all: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit#create_status_from_github!` then records the forged status against the row's own `stack_id`: [2](#0-1) 

So the status *is* correctly attached to the owning stack of that specific `Commit` row (there is no direct cross-stack row confusion for a single commit id) — but the attacker doesn't need the payload's `stack_id` to match; they only need a commit **row with the same SHA** to already exist in Shipit's database for a stack they don't control, and a webhook signature that verifies for *some* organization Shipit trusts.

Signature verification is per-organization, not per-repository: [3](#0-2) 

Shipit explicitly supports "Using Multiple Github Applications", where the top-level config keys are GitHub organizations, each with its own `webhook_secret` shared across every repository under that org: [4](#0-3) [5](#0-4) 

Since git commit SHAs are pure content hashes (tree + parents + author/committer + message + timestamps), an attacker who forks/clones the victim's public repository will reproduce byte-identical commit objects with **identical SHAs** in their own repository. If that attacker-owned repository lives under (or shares a webhook secret with) any organization Shipit is configured to trust — a realistic scenario for org-wide webhooks or multi-repo orgs — a real, validly-signed GitHub `status` webhook fired from the attacker's own repository (e.g., via the Statuses API, which the attacker fully controls on their own repo) will pass `verify_signature` and reach `StatusHandler#process`. That handler then matches the Shipit `Commit` row with the same SHA belonging to the **victim's** stack and creates a `success` `Status` for it, with no verification that the emitting repository has any relationship to that stack.

Once the forged `Status` row exists, `Commit#status` (`Status::Group.compact`) reports `success?`, so: [6](#0-5) 

`deployable?` returns true, `Status#schedule_continuous_delivery` and `Commit#schedule_continuous_delivery` fire `ContinuousDeliveryJob`, and `Stack#trigger_continuous_delivery` → `trigger_deploy` creates a real `Deploy` — for a stack with `ignore_ci? == false`, deploying a commit whose only "success" originated from the attacker's own repository, never from CI running against the victim repo.

Existing guards do not stop this: `verify_signature` only proves the request came from a GitHub org Shipit trusts, not that it came from the specific repository owning the commit; `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/etc., not repository identity; and `Handler#stacks`/`#repository_name` helpers exist in the base `Handler` class but are **never used** by `StatusHandler#process` (unlike e.g. `PullRequest::OpenedHandler`, which does scope via `Repository.from_github_repo_name(params.repository.full_name)`).

### Impact Explanation
A payload from one repository can cause an unauthorized deploy for a stack it does not own — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" category. The blast radius is every stack/commit in the Shipit instance whose SHA collides with a commit the attacker can reproduce in a repository under a trusted organization; this is trivially repeatable for any public repo the attacker can fork, and is not limited to a single stack — any tracked commit with a colliding SHA across the whole deployment is exploitable with one signed webhook request.

### Likelihood Explanation
Requires: (1) Shipit configured with a webhook-secret scope broader than the individual tracked repository (org-level or shared-secret multi-repo/org configuration, which is explicitly documented and supported), (2) the attacker having (or being able to create) a repository under/sharing that trust scope, and (3) the ability to reproduce an identical SHA (straightforward via fork/clone of the victim's public repo, since GitHub SHAs are content-addressed and preserved verbatim on fork). Given the stated attacker capability of "emit[ting] webhooks from a repository they own," and that many real Shipit deployments configure webhooks at the organization level for convenience, this is a realistic and cheap (single signed HTTP request) attack, repeatable at will.

### Recommendation
Scope `StatusHandler#process` (and any other webhook handler that looks up records purely by content like SHA) to the repository named in the webhook payload, e.g. resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the `Commit` lookup to commits whose `stack.repository` matches that repository (using the existing `Handler#stacks`/`#repository_name` helper pattern already used by other handlers), rather than trusting an unscoped `sha` match across the entire database.

test "status webhook from a foreign repository forges success on a victim stack commit with a colliding SHA" do

  forged_payload = {

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
