### Title
Missing Built-in Domain Separation in `is_valid_signed_package` Allows Signature Replay Across AAs/Purposes - (File: formula/evaluation.js)

### Summary
The oscript primitive `is_valid_signed_package(signedPackage, address)` lets an AA author pass an arbitrary, fully attacker/counterparty-controlled JavaScript object (typically taken from `trigger.data`, e.g. a value forwarded by a private-payment or payment-channel counterparty) to be checked as a valid signed message for a given address. Exactly like `FirewallConsumerBase.firewallProtectedCustom`/`firewallProtectedSig`, which let a consumer pass arbitrary bytes instead of the real `msg.data` to a policy, `is_valid_signed_package` passes an arbitrary user-supplied structure to the underlying authentication routine (`signed_message.validateSignedMessage`) instead of binding the signature check to the real invocation context (the specific AA, action, or nonce). The primitive itself performs no domain separation — the caller (AA author) is fully responsible for manually re-checking context fields inside the signed object.

### Finding Description
`is_valid_signed_package` is implemented in `formula/evaluation.js` (case `'is_valid_signed_package'`) and only validates: the object's field whitelist, an optional `last_ball_unit`/`version`, and finally delegates to `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)`. [1](#0-0) 

`validateSignedMessage` computes the hash-to-sign purely from the contents of the `signed_package` object itself (`signed_message`, `last_ball_unit`, `authors`, `version`) via `objectHash.getSignedPackageHashToSign(objSignedMessage)`, and then verifies the signature against that hash using the standard `Definition.validateAuthentifiers` machinery. [2](#0-1) 

Crucially, nothing in this path binds the signed content to:
- the specific AA address (`this_address`) that is evaluating it,
- the specific trigger/action/purpose for which the signature was intended,
- or any nonce/sequence unless the AA author manually embeds and re-checks such fields inside `signed_message`.

This is confirmed by the reference sample `payment_channels.oscript`, which must manually verify `trigger.data.sentByPeer.signed_message.channel != this_address` and `signed_message.period != var['period']` before trusting the signature — showing that the underlying primitive provides no such context binding on its own: [3](#0-2) 

If any AA author omits these manual checks (there is no compiler/validation-time warning enforcing them — `formula/validation.js`'s `is_valid_signed_package` case only checks expression well-formedness, not semantic context binding): [4](#0-3) 

...a signature that a private-payment/channel counterparty produced for one purpose, one channel, one AA, or one round can be replayed by an unprivileged trigger sender into a different AA, different channel, or different action that also calls `is_valid_signed_package` over structurally similar data, because the cryptographic guarantee only proves "the address's owner signed this JSON blob" — not "the address's owner authorized this specific action in this specific AA context."

This is the direct analog of the Ironblocks report: `firewallProtectedCustom`/`firewallProtectedSig` let a consumer substitute arbitrary bytes for `msg.data`, breaking the implicit assumption that the policy sees the real call context, and requiring integrators to manually reconstruct correct scoping (as documented for `ApprovedCallsPolicy`/`ApprovedVectorsPolicy`). Here, `is_valid_signed_package` lets an AA author substitute an arbitrary JSON blob for a bound protocol message, and requires the same kind of manual, error-prone context reconstruction.

### Impact Explanation
If an AA that uses `is_valid_signed_package` fails to bind the signed content to itself/purpose/state (a very plausible integration mistake given the primitive provides no default binding and only one sample library demonstrates the correct — but non-enforced — pattern), an unprivileged trigger sender who has legitimately obtained a validly-signed package for one context (e.g. a signed balance update for payment channel A) can replay it into another context (a different channel, a different AA instance, or a later/earlier state) to withdraw funds or move AA state in a way the original signer never authorized. This can result in AA fund loss/freezing or unauthorized spending of AA-held balances.

### Likelihood Explanation
Likelihood depends on third-party AA authors' oscript code, not on the ocore protocol enforcing safety automatically — this mirrors the original report's classification as "confusion" arising from a flexible-but-underspecified primitive rather than a memory-safety/consensus bug. Given `is_valid_signed_package` is explicitly designed to accept fully free-form JSON and only the sample templates show the required manual context checks, it is reasonably likely that some AA authors integrate it without full domain separation (channel id / action id / current state binding), especially for multi-round or multi-purpose off-chain-signed protocols like payment channels or order books.

### Recommendation
- Add explicit, prominent documentation/comments at the `is_valid_signed_package` implementation (`formula/evaluation.js`) and in oscript language documentation stating that the primitive performs **no implicit domain separation**: AA authors MUST embed and manually verify identifying context (the AA's own address, action/purpose tag, and any relevant state/sequence number) inside `signed_message` before trusting `is_valid_signed_package`'s boolean result.
- Consider providing an optional enforced binding, e.g. an AA-address or purpose parameter that `validateSignedMessage`/`getSignedPackageHashToSign` automatically mixes into the hash-to-sign, so that signatures cannot trivially be replayed across AAs/purposes without the signer's consent.
- Extend the reference samples/documentation to call out this replay risk clearly, similar to the "Added comments to the two modifiers" fix in the referenced Firewall PR.

### Proof of Concept
Conceptual (protocol-level) scenario:
1. Counterparty B signs a JSON package `{signed_message: {channel: "AA_X", period: 1, amount_spent: 100}, authors: [...]}` intended only for AA `AA_X`'s payment-channel logic, following the exact pattern of `payment_channels.oscript`.
2. A second AA `AA_Y` (written by a less careful author, or an earlier/looser version of similar channel logic) also calls `is_valid_signed_package(trigger.data.sentByPeer, some_address)` but omits the `signed_message.channel != this_address` check that `payment_channels.oscript` deliberately performs at `test/samples/payment_channels.oscript:107-108`.
3. An unprivileged trigger sender submits the same signed package as `trigger.data` to `AA_Y`. `is_valid_signed_package` returns `true` because the signature is valid over the JSON blob — it has no knowledge that the blob was meant only for `AA_X`.
4. `AA_Y` accepts the forwarded state update/authorization and releases funds/updates state as if genuinely authorized for itself, causing unauthorized fund movement. [5](#0-4) [6](#0-5)
