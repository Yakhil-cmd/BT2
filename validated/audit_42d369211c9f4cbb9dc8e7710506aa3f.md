## Title
Cross-organization webhook forgery — webhook signature verifies `repository.owner.login` but handlers act on the unrelated `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

## Summary
Shipit supports multi-tenant GitHub configuration: `Shipit.github(organization:)` looks up a distinct `webhook_secret` per configured GitHub organization key in `secrets.github`. [1](#0-0)  The `WebhooksController#verify_signature` action selects which organization's secret to HMAC-verify against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [2](#0-1) [3](#0-2)  Once the signature check passes, every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` using a completely different field: `payload.dig('repository', 'full_name')`. [4](#0-3) 

Because the attacker crafts the entire raw JSON body themselves and only needs it to be HMAC-signed with a secret they legitimately know (the `webhook_secret` of an org they administer inside the same multi-tenant Shipit install), nothing binds `repository.owner.login` (the field used to select/verify the signing secret) to `repository.full_name` (the field used to pick which repository/stack is actually mutated). This breaks the intended binding: `organization that signed the payload == repository that gets acted upon`.

## Finding Description
`verify_signature` computes `repository_owner` and fetches that organization's `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against the raw POST body using that secret: [5](#0-4) 

After verification succeeds, `create` dispatches the parsed JSON to every registered handler for the event type: [6](#0-5) 

Every handler (e.g. `PushHandler`, `StatusHandler`'s siblings like the PR handlers) resolves which `Repository`/`Stack` to operate on via `Handler#stacks`/`#repository_name`, which reads `payload.dig('repository', 'full_name')` — not `repository.owner.login`: [4](#0-3)  and similarly in the pull-request handlers, e.g. `PullRequest::OpenedHandler#repository`: [7](#0-6) 

`PushHandler#process` then triggers a real sync against whatever stacks match that `full_name`: [8](#0-7) 

`StatusHandler#process` creates commit statuses (which gate deploys) purely by matching `sha`, with no repository/organization check at all: [9](#0-8) 

`PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` create, archive, or unarchive review stacks (which provisions/deprovisions infrastructure) based solely on `repository.full_name` and `pull_request` fields: [10](#0-9) 

The equality the design relies on is:
`organization authenticated by verify_signature (repository.owner.login) == repository written by the handler (repository.full_name)`

Before the attacker's request: this holds because GitHub only ever sends `repository.owner.login` and `repository.full_name` consistently for the org/repo the app installation covers.

After the attacker's request: an attacker who is an admin of *any* GitHub organization configured in the same multi-tenant Shipit instance (and therefore legitimately knows that organization's `webhook_secret`, which is explicitly meant to be shared with that org's admins to configure their GitHub App webhook) can POST a raw JSON body where `repository.owner.login` = their own org (so `verify_signature` succeeds using their known secret) but `repository.full_name` = any other tenant's repository (e.g. `"other-org/other-repo"`). The signature only proves "this exact byte string was HMAC'd with organisation X's secret" — since the attacker authored the byte string, they can put any `full_name` inside it. The equality is broken: verification is scoped to one organization, but the mutation is scoped to whatever repository name is embedded in the same attacker-controlled payload.

## Impact Explanation
This lets a tenant of a multi-org Shipit deployment forge webhook events for repositories/stacks belonging to *other* tenants, i.e., a cross-repository/cross-tenant write with no repository or GitHub write access to the victim repository:
- Forge `push` events to trigger `stack.sync_github` on arbitrary stacks. [8](#0-7) 
- Forge `status` events to inject fabricated commit statuses on arbitrary commits, which are used to gate deploy/merge decisions. [9](#0-8) 
- Forge `pull_request` events to create, archive, or unarchive review stacks (provisioning/deprovisioning infrastructure) for arbitrary victim repositories. [10](#0-9) 

This matches the "cross-repository writes" / "unauthorized deploy" criteria: an attacker without any credential or write access to the victim repository can influence its deploy pipeline state.

## Likelihood Explanation
Requires the deployment to be configured with more than one GitHub organization key under `secrets.github` (multi-tenant mode, supported by `Shipit.github_organizations`/`github_app_config`) [11](#0-10) , and the attacker must be an admin of at least one of those configured organizations (so they know that org's `webhook_secret`, which by design must be shared with each org to let them register the GitHub App webhook — see setup docs referencing per-org webhook secret). Given this common multi-tenant setup, likelihood is high once conditions are met; in a single-organization deployment the impact collapses to self-targeting only.

## Recommendation
In `WebhooksController`, after verifying the signature, additionally assert that `payload.dig('repository', 'full_name')` (and/or `organization.login` for org-level events) belongs to the same organization used to select the verifying secret (`repository_owner`), rejecting the request (e.g. `head(422)`) if they don't match. Alternatively, pass the verified `repository_owner` into each `Handler` and have `Handler#stacks`/`#repository` scope lookups by both `full_name` and the verified owner, rather than trusting `full_name` alone.

## Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-tenant mode as supported by `github_app_config`).
2. As an admin of `attacker-org`, obtain/know `attacker-org`'s `webhook_secret` (legitimately provisioned to configure the GitHub App webhook for `attacker-org`).
3. Craft a raw JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac_sha1(attacker-org secret, body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s secret, and the signature validates successfully. [5](#0-4) 
6. `PushHandler` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `sync_github` on `victim-org`'s stacks, even though the signature only proved knowledge of `attacker-org`'s secret. [4](#0-3) [8](#0-7)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
