### Title
Webhook signature check authenticates the payload's `repository.owner.login` (or `organization.login`) organization, but every event handler resolves its write target from independent, unverified fields (`repository.full_name`, `organization.login`) — an org configured with no `webhook_secret` lets an attacker forge events against *any* repository/stack in the instance - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects a per-organization `GithubApp` using `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`) and asks that app to verify the HMAC signature. `Shipit::GithubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured. Because `webhook_secret` is an optional/nilable setting (`config/secrets.development.example.yml:11`), any Shipit instance with one organization that has no webhook secret becomes an unauthenticated endpoint for *all* webhook event types, not just that organization's events. Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, …) then resolves the actual write target from `repository.full_name` or `organization.login` inside the same JSON body — fields that are never checked for equality against the organization whose (absent) secret authorized the request. This is the same class of bug as the ERC20 report: a value used to authorize the operation (`repository_owner` chosen to pick the signing key) is not the value the operation actually acts on (`repository.full_name` / arbitrary `organization.login` used to locate the `Stack`, `Commit`, or `Team`).

### Finding Description
- `WebhooksController#verify_signature` picks the GitHub App/secret using only `repository_owner`, derived from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 
- `GithubApp#verify_webhook_signature` short-circuits to `true` when that organization has no configured `webhook_secret`: [3](#0-2) 
- `webhook_secret` is documented as optional (commented `# nil`) in the sample config, i.e. a supported/expected deployment state, not a misconfiguration outside the documented setup: [4](#0-3) 
- Once past `verify_signature`, the base `Handler` class resolves the *actual* repository/stack purely from `payload.dig('repository', 'full_name')`, a field that was never covered by the (bypassed) signature check and need not match `repository_owner`: [5](#0-4) 
- `PushHandler`, `StatusHandler` (via `Commit.where(sha:)` — cross-stack, since SHAs aren't repo-scoped), `CheckSuiteHandler`, and `MembershipHandler` all act on whatever `repository.full_name`/`organization.login` the JSON body claims, with no re-check that it equals the organization that "authorized" the request: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

The equality that should hold but is broken:
`organization authenticated to sign the webhook (repository_owner → GithubApp.webhook_secret)` = `repository/organization actually written to by the handler (repository.full_name / organization.login)`

Before the attack: only GitHub (holding the real per-org `webhook_secret`) can deliver events that get processed for a given org's repositories/stacks. After the attack: an unprivileged internet attacker who knows that org `no-secret-org` is configured in the target Shipit deployment (a discoverable/likely condition — orgs without a `webhook_secret` are a documented supported configuration) can POST `X-Github-Event: push` (or `status`, `check_suite`, `membership`) with `repository.owner.login = "no-secret-org"` (to pass the auth-selection/bypass) and `repository.full_name = "victim-org/victim-repo"` (to target any other tracked stack), with no signature at all, and have it processed as if GitHub sent it.

### Impact Explanation
This breaks a credential/authentication boundary: cross-organization/cross-repository writes without any valid GitHub-issued signature. Concretely an attacker can:
- Forge `push` events to force `GithubSyncJob` to sync arbitrary tracked stacks against attacker-chosen `expected_head_sha`.
- Forge `status` events to inject fabricated CI/commit statuses (`Commit#create_status_from_github!`) for any commit by SHA across the whole instance, potentially manipulating deployability gates that downstream deploy authorization relies on.
- Forge `check_suite` events to trigger `RefreshCheckRunsJob` for arbitrary stacks/commits.
- Forge `membership` events to create/delete team memberships and auto-create `User`/`Team` records tied to an arbitrary `organization.login`, corrupting `Shipit.github_teams` authorization bookkeeping.

This matches the "cross-repository writes" and "escalation into `Shipit.github_teams` authorization" criteria for Critical/High impact.

### Likelihood Explanation
Requires only that the Shipit deployment has at least one configured GitHub organization/App without a `webhook_secret` — an explicitly supported, documented configuration (shown as the default/example value). No GitHub webhook secret, `ApiClient` token, repository write access, or privileged account is needed by the attacker; only knowledge of one such organization's login name and the endpoint URL, both of which are typically discoverable (e.g., via the Shipit UI, which lists configured stacks/organizations).

### Recommendation
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank; require a secret to be configured for every organization, or reject unsigned requests outright.
- Independently, re-derive/verify that the organization used to select the signing key (`repository_owner`) matches the organization of the actual `repository.full_name`/`organization.login` the handler operates on, so a valid signature for org A can never be replayed to write into org B's stacks.

### Proof of Concept
1. Configure Shipit with two organizations in `github:` config: `victim-org` (has `webhook_secret: <secret>`), and `staging-org` (no `webhook_secret`, per the documented optional config).
2. As an unauthenticated attacker, POST to `/webhooks`:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "repository": { "owner": { "login": "staging-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "staging-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) — no `X-Hub-Signature` header is even required. [3](#0-2) 
4. `PushHandler.call` runs against `Repository.from_github_repo_name("victim-org/victim-repo")`, enqueuing `GithubSyncJob` for `victim-org`'s stack, even though the attacker never proved control of `victim-org` or possession of its `webhook_secret`. [10](#0-9) [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
