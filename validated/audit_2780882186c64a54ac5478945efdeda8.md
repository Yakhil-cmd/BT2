### Title
CPU exhaustion in unit validation via O(n²) duplicate-input-key scan in `validatePaymentInputsAndOutputs` / `validateMessage` - (File: validation.js)

### Summary
`validation.js` deduplicates payment inputs and spend-proofs across an entire unit using a single shared array (`objValidationState.arrInputKeys`) that is scanned linearly with `Array.prototype.indexOf` on every new input, instead of using a hash-based lookup. A single crafted unit with many payment messages, each carrying many inputs, forces the validator to perform a quadratic number of comparisons, mirroring the `@conform-to/dom` `parseSubmission` bug class where repeated linear scans by key turned parsing into an O(n²) operation exploitable by an attacker-controlled payload.

### Finding Description
`validateMessages` iterates all messages of a unit using the same `objValidationState` object for the whole unit [1](#0-0) . Inside `validateMessage`, spend-proof entries are deduplicated by linearly scanning `objValidationState.arrInputKeys` for every proof and then pushing the new key onto the same array: [2](#0-1) .

For actual payment inputs, `validatePaymentInputsAndOutputs` builds an `input_key` for every "transfer" input and performs the same `indexOf` scan against the very same shared `arrInputKeys` array before pushing the new key: [3](#0-2) .

Because `arrInputKeys` is stored on the shared `objValidationState` and is never cleared between messages, the number of elements it holds grows with the total number of inputs/spend-proofs already validated in the same unit, and each subsequent input triggers a full linear scan of that ever-growing array. With `messages` capped at `constants.MAX_MESSAGES_PER_UNIT` and inputs per payment message capped at `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, a single unit can still contain many messages × many inputs, and the total validation work for duplicate-checking becomes O(N²) in the total number of inputs N, rather than O(N) as it would be with a `Set`/`Map`-based lookup.

This is structurally identical to the reported `@conform-to/dom` issue: a component that should do O(N) work over N items instead performs O(N) scans for each of N items because of a linear "look up by key" pattern, and the input is entirely attacker-controlled (a unit posted to the network).

A similar pattern also exists for output-address deduplication with `arrOutputAddresses.indexOf(output.address)` inside the outputs loop, though that array is local to a single payment message and thus bounded by `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` rather than compounding across the whole unit: [4](#0-3) .

Notably, elsewhere in the codebase this exact bug class was already identified and fixed: the `has equal`/`has one equal` oscript operator evaluation in `definition.js` was rewritten from an O(n·m) nested search into an O(n+m) map-based lookup, with an explicit comment describing the fix [5](#0-4) . The payment-input deduplication path in `validation.js` was not given the same treatment.

### Impact Explanation
Every unit received by a node — including from an unprivileged peer posting a single new unit — goes through `validateMessages`/`validatePaymentInputsAndOutputs`. An attacker can construct one oversized-but-within-limits unit containing the maximum allowed number of payment messages, each with the maximum allowed number of inputs, all with distinct input keys so no early "duplicate" rejection occurs, forcing the validator to perform the full O(N²) scan before returning any error. Since unit validation runs synchronously per unit on the node's validation path, this consumes disproportionate CPU relative to the unit's size, degrading the node's ability to validate other legitimate units in a timely manner. This falls under the CWE-407 "Algorithmic Complexity" class and can contribute to a node being unable to keep up with confirming new units under adversarial submission patterns.

### Likelihood Explanation
Likelihood is high for triggering the code path (any user can post a unit), but the actual CPU blow-up is bounded by the existing per-message and per-unit hard caps (`MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_MESSAGES_PER_UNIT`, `MAX_UNIT_LENGTH`) rather than being unbounded like the original CVE, so the achievable N is finite and the resulting slowdown is a multiplier rather than unlimited, unbounded CPU exhaustion. It still degrades validation throughput measurably more than a linear implementation would, and repeated submission of such units amplifies the effect on validating nodes.

### Recommendation
Replace the linear `indexOf` scans over `objValidationState.arrInputKeys` (and, defensively, `arrOutputAddresses`) with a `Set` (or `Map`) for O(1) membership checks and insertion, mirroring the fix already applied in `definition.js` for the `has equal` operator: [2](#0-1) [3](#0-2) .

### Proof of Concept
1. Construct a unit with `constants.MAX_MESSAGES_PER_UNIT` payment messages, each containing `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` valid "transfer" inputs referencing distinct, existing outputs, ensuring all `input_key` values are unique (so no message is rejected early for a duplicate).
2. Submit this unit to a node via the normal unit-posting path (as any unprivileged user can).
3. During `validateMessages` → `validateMessage` → `validatePaymentInputsAndOutputs`, each of the N total inputs triggers `objValidationState.arrInputKeys.indexOf(input_key)` against the accumulated array from all prior inputs/messages in the same unit [3](#0-2) , producing O(N²) comparisons for validating a single unit, measurably higher CPU time than a linearly-scaling implementation for the same unit size.
