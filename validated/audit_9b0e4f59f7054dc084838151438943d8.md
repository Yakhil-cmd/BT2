### Title
`not_contains` Stop-event condition silently fails open when transcript is unreadable/missing, allowing "require tests before stop" block rule to never fire - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`_check_condition` extracts the field value via `_extract_field` and immediately returns `False` if that value is `None`, before the operator logic runs. For a Stop-event rule using `field='transcript'` and `operator='not_contains'`, any path that leaves `field_value` as `None` (missing `transcript_path`, or a `FileNotFoundError`/`PermissionError`/other read error whose value bypasses the intended `''` fallback) causes the negative-match condition to evaluate to `False` instead of `True`, defeating the "deny means deny" semantics of a block rule meant to catch the absence of expected content.

### Finding Description
In `_extract_field` (`plugins/hookify/core/rule_engine.py:182-254`), the Stop-event `transcript` handling only returns a value inside the `if transcript_path:` branch (lines 209-225); when `input_data.get('transcript_path')` is falsy (key absent, empty string, or `None`), execution falls through that `if/elif` chain, then falls through the tool-specific blocks (which require `tool_name` in `{'Bash','Write','Edit','MultiEdit'}`, not applicable for a Stop event), and the function reaches the final `return None` at line 254. This differs from every actual file-read error path, which explicitly returns `''` (lines 216, 219, 222, 225) — showing the intent that transcript content should be `''`, not `None`, when there is no genuine transcript text to match against.

Back in `_check_condition` (lines 158-160):
```
field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
if field_value is None:
    return False
```
This short-circuit runs before the operator dispatch (lines 163-180). For `operator == 'not_contains'`, the correct behavior against absent/empty content is `pattern not in '' -> True` (condition satisfied, rule should block). Instead, the `None` short-circuit forces `_check_condition` to return `False`, meaning the condition (and therefore the whole rule, since `_rule_matches` requires all conditions to match, `plugins/hookify/core/rule_engine.py:121-123`) never matches, and `evaluate_rules` never blocks the Stop event.

The Stop hook input JSON legitimately may lack `transcript_path` (or point to a path that is deleted/rotated between hook invocations) without any privileged action by the attacker — an ordinary unprivileged Claude Code session that never actually ran tests, or whose transcript file is unavailable for any reason, hits this exact path. This is a real, unprivileged, reachable condition, not a test/mock artifact — it is the literal hook enforcement code path for Stop-event rules described in the README's require-tests-run example.

### Impact Explanation
The scoped impact is a **hook enforcement bypass**: a block rule intended to prevent Claude from stopping unless tests were run (`operator: not_contains`, `field: transcript`, `pattern: pytest` per the README example) fails to fire precisely in the case where it matters most — when there is no transcript evidence of tests being run at all. This directly violates the stated invariant "deny means deny," since the absence of data is treated as "allow" instead of "the strongest possible match for not_contains." This maps to a Claude Code trust-boundary/guardrail bypass: the safety hook meant to gate agent stop behavior silently no-ops.

### Likelihood Explanation
This requires no attacker privilege beyond normal, ordinary use of the plugin: it happens whenever `transcript_path` is absent from the Stop hook payload, or the file is deleted/inaccessible when the hook runs — plausible in normal automation flows (e.g., transient FS issues, custom Stop payloads, non-standard invocation contexts) and fully reproducible via unit test, not dependent on any race or privileged setup.

### Recommendation
In `_extract_field`, when handling `field == 'transcript'` and `transcript_path` is falsy, explicitly `return ''` instead of falling through to `return None`. More generally, `_check_condition` should distinguish "field not supported/not applicable" (`None`, correctly short-circuits to `False`) from "field applicable but empty/unreadable content" (should be treated as `''` and run through the operator, so `not_contains` correctly evaluates to `True`).

```python
    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
```
