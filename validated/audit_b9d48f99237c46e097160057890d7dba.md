### Title
`socialize-debt` writes down supplier-facing `lindex` by the full accrued debt but only removes the principal portion from `assets`, leaving zToken backing overstated - ([File: contracts/vault/vault-stx.clar])

### Summary
This is a Zest-specific analog of the Mochi `debts` mismatch: two internal accounting variables that are supposed to represent the same economic loss (bad debt) are updated using two different bases - one including accrued interest, one excluding it - leaving the vault's reported asset backing permanently inflated relative to the true backing after a bad-debt write-off. Later zToken redeemers absorb the resulting shortfall caused by earlier redeemers extracting the inflated value.

### Finding Description
In every vault contract (`vault-stx.clar`, `vault-sbtc.clar`, `vault-usdc.clar`, etc., mirrored in `mainnet/contracts/vault/v0-vault-*.clar`), `socialize-debt` computes two different reduction amounts from the same `scaled-amount` of bad debt: [1](#0-0) 

- `debt-reduction` = `scaled-amount * idx / INDEX-PRECISION` — the **full** economic loss, principal **plus accrued interest**, and it is used to write down `lindex` (`new-lindex`), which is the value used to price zTokens for every supplier in the pool.
- `principal-reduction` = `scaled-amount * borrowed / scaled-principal` — only the **principal** share of that same debt (no interest), and it is what is actually subtracted from the `assets` data var: `(var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))`.

Because `principal-reduction <= debt-reduction` whenever any interest has accrued on the socialized position, `assets` is under-reduced by the interest component of the written-off debt. `lindex` (correctly) reflects the full loss for zToken pricing, but the `assets` var - which feeds `total-assets`/`total-assets-preview` and is used elsewhere (e.g., the `treasury-lp` fee-reserve mint calculation in `accrue`) - remains inflated: [2](#0-1) 

This is structurally identical to the Mochi finding: `debts` was decremented by an amount that didn't match how it was incremented (excludes vs. includes fee), producing systemic drift in `utilizationRatio`/`stabilityFee`. Here, `assets` is decremented by an amount (principal only) that doesn't match the true loss (principal+interest) already applied to `lindex`, producing drift between the "supplier share price" (`lindex`) and the "total assets" bookkeeping variable that other computations (fee-reserve minting, total-assets-based previews) rely on.

### Impact Explanation
After a `socialize-debt` call (triggered by liquidation shortfalls), the vault's `assets` bookkeeping variable overstates the true backing of the pool by the un-written-off interest portion of the bad debt. Any downstream computation that relies on `assets`/`total-assets` (fee-reserve/treasury-lp minting in `accrue`, and any "total-assets" preview used elsewhere for pricing) works off inflated numbers. Suppliers who interact with the pool immediately after a socialization event can be advantaged or disadvantaged relative to those who interact later, and the treasury fee-share minting logic (which divides `reserve-inc` by `total-assets-preview`) is computed against a value that does not reflect the real, already-realized bad-debt loss. This is a shared-state accounting bug that is charged across all suppliers of the vault, not just the caller of `socialize-debt` - it lands under temporary freezing/misallocation of supplier funds and yield within the affected vault.

### Likelihood Explanation
`socialize-debt` is restricted to authorized callers (`check-caller-auth`), so it is not directly attacker-triggered, but it fires automatically as part of the protocol's own liquidation/shortfall-handling flow whenever a liquidation leaves bad debt - a normal, expected operational event, not a rare edge case. Every time it executes, this discrepancy is introduced, so likelihood of the underlying miscalculation occurring is high; the question is only how large the interest-vs-principal gap is at the time (this grows with vault utilization and time since last accrual).

### Recommendation
Make the reduction applied to `assets` consistent with the reduction applied to `lindex`: either reduce `assets` by the full `debt-reduction` (including interest) to match the `lindex` write-down, or derive `lindex`'s write-down using only `principal-reduction` if `assets` is only meant to track principal. Add invariant tests asserting that `total-assets()` computed via `assets` + `total-debt()` is consistent with the value implied by `lindex * total-supply` immediately after `socialize-debt`.

### Proof of Concept
1. Vault has outstanding scaled debt with accrued interest such that `total-debt() > total-borrowed` (i.e., `idx` has increased since the debt was created).
2. A liquidation leaves bad debt; `socialize-debt(scaled-amount)` is invoked.
3. `debt-reduction = scaled-amount * idx / INDEX-PRECISION` (includes interest) is used to write down `lindex`.
4. `principal-reduction = scaled-amount * total-borrowed / scaled-principal` (excludes interest) is subtracted from `assets`.
5. Since `debt-reduction > principal-reduction`, `assets` retains `(debt-reduction - principal-reduction)` of value that no longer exists economically (it was already written off from suppliers' `lindex`-based valuation).
6. Any subsequent `accrue()` fee-reserve calculation, or any other logic reading `assets`/`total-assets`, operates on this inflated figure, misallocating value among suppliers who interact with the vault before vs. after the discrepancy is (if ever) corrected. [3](#0-2) 

Note: I was not able to fully trace the exact definitions of `total-assets`, `total-assets-preview`, and `total-debt` within the available index (their bodies were not returned by search), so the precise downstream numerical effect on `treasury-lp` minting and zToken redemption pricing could not be fully confirmed from the indexed content alone. Confirming the exact consequence requires reading the full `total-assets`/`total-assets-preview` implementations in `vault-stx.clar` (and sibling vault files) directly, which a Devin session with full file access could verify.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
