### Title
Unauthenticated disclosure of stack merge/CI status via `MergeStatusController#check` - (File: `app/controllers/shipit/merge_status_controller.rb`)

### Summary
`MergeStatusController` exempts the `check` action from Shipit's GitHub-team authorization entirely, and unlike the sibling `show` action, `check` never re-verifies that the requester is an authenticated, authorized GitHub user before rendering the stack's live merge-queue/CI status. This lets any unauthenticated, unprivileged actor query the merge/CI status of any stack (including stacks that back private repositories restricted to specific `Shipit.github_teams`) simply by supplying a `stack_id` or a `referrer` URL.

### Finding Description
Every other Shipit controller enforces GitHub-team based authorization through `Shipit::Authentication#force_github_authentication`, which is a `before_action` included by `ShipitController` [1](#0-0)  and implemented to redirect unauthenticated users to GitHub OAuth and reject users who are not members of a configured `Shipit.github_teams` team [2](#0-1) .

`MergeStatusController` explicitly disables this check for the `check` and `show` actions: [3](#0-2) 

The `show` action compensates for the missing `before_action` by manually gating on `current_user.logged_in?` before rendering any stack data: [4](#0-3) 

The `check` action performs no such compensation — it computes and renders `stack_status` unconditionally for any caller: [5](#0-4) 

`stack_status` invokes `Stack#merge_status`, which reflects the live locking/merge-queue/CI state of the stack: [6](#0-5) 

The target stack is resolved directly from request parameters with no ownership or team check — either from `params[:stack_id]` via `Stack.from_param!`, or by parsing an arbitrary `referrer` GitHub PR URL supplied by the caller: [7](#0-6) [8](#0-7) 

This is the same class of bug as the reported EigenLayer issue: a control that is supposed to gate access (the "proof"/authorization check performed for `show`) is not actually enforced for another code path (`check`) that consumes the same underlying data and is reachable with an equivalent, unauthenticated request. The binding that should hold — "GitHub identity authorized via `Shipit.github_teams`" == "identity permitted to read this stack's status" — is broken for the `check` action, where the left side is empty (no identity at all) while the right side (stack status disclosure) still occurs.

### Impact Explanation
This allows any unauthenticated network client to enumerate and read the CI/merge-queue status (`success`/`failure`/etc., including lock state) of arbitrary stacks by ID or by supplying a crafted `referrer` parameter matching `owner/repo/pull/number`, bypassing the team-restricted-visibility model that the rest of the application enforces. This satisfies the "High - unauthenticated read of stack state" impact category: sensitive deployment/merge state that is meant to be restricted to members of configured GitHub teams is exposed to anyone with network access to the Shipit instance, with no credential, session, or GitHub identity required.

### Likelihood Explanation
High. The `check` action is reachable via a plain, unauthenticated GET request (it is explicitly whitelisted via `skip_authentication only: %i[check show]`) and requires no token, secret, session cookie, or prior interaction — only knowledge of a stack's `owner/repo/environment` param or a public GitHub PR URL, both of which are typically guessable or publicly known for stacks tied to public/semi-public repositories.

### Recommendation
Add the same `current_user.logged_in?` (and, ideally, `current_user.authorized?`) gate to the `check` action that `show` already has, or remove `check` from the `skip_authentication` allowlist and instead have it degrade gracefully (e.g., return a generic/neutral status) for unauthenticated callers instead of leaking real stack state.

### Proof of Concept
1. Without any session cookie, authentication header, or GitHub OAuth flow, send:
   `GET /merge_status/check?stack_id=<owner>/<repo>/<environment>`
   or
   `GET /merge_status/check?referrer=https://github.com/<owner>/<repo>/pull/<number>&branch=<branch>`
2. The response renders `stack_status` (plain text `ok`/failure reason, or JSON `{"stack_status": "..."}` for `format: :json`) directly from `Stack#merge_status`, with no authentication or team-membership check performed, unlike `show` which explicitly requires `current_user.logged_in?`.

    class ReferrerParser
      URL_PATTERN = %r{\Ahttps://github\.com/([^/]+)/([^/]+)/pull/(\d+)}

      attr_reader :repo_owner, :repo_name, :pull_request_number

      def initialize(referrer)
        unless (match_info = URL_PATTERN.match(referrer.to_s))
          raise ArgumentError, "Invalid referrer: #{referrer.inspect}"
        end

        @repo_owner = match_info[1].downcase
        @repo_name = match_info[2].downcase
        @pull_request_number = match_info[3].to_i
      end
