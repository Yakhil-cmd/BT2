### Title
Unvalidated P2P Staking Info Injection Corrupts Reward Distribution and Causes Consensus Divergence — (`datasync/downloader/queue.go`)

---

### Summary

The `DeliverStakingInfos` function in the downloader queue accepts `P2PStakingInfo` payloads from remote peers and writes them directly to the local staking database with **no cryptographic or state-root verification**. A malicious peer connected during fast sync can inject fabricated staking info — with attacker-controlled `RewardAddrs` and arbitrary `StakingAmounts` — that the node will subsequently use for KAIA reward distribution and validator-set selection, corrupting both.

---

### Finding Description

Every other data type delivered during sync is validated against a committed block-header field. Receipts are checked against `header.ReceiptHash`:

```go
// datasync/downloader/queue.go  DeliverReceipts
validate := func(index int, header *types.Header) error {
    if types.DeriveReceiptsRoot(types.Receipts(receiptList[index]), header.Number) != header.ReceiptHash {
        return errInvalidReceipt
    }
    return nil
}
``` [1](#0-0) 

Staking info has no equivalent check — the validate closure is a permanent no-op with an unresolved TODO:

```go
// datasync/downloader/queue.go  DeliverStakingInfos
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [2](#0-1) 

The accepted (unverified) staking info is then committed to the persistent database in two places during fast sync:

```go
// commitFastSyncData
d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
``` [3](#0-2) 

```go
// commitPivotBlock
d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
``` [4](#0-3) 

A second injection path exists via `SyncStakingInfo` (the staking-info recovery API). It checks only that `stakingInfo.BlockNum` matches the expected sequence number; it never verifies the payload content against the canonical state:

```go
if d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum {
    logger.Error("failed to receive expected block", ...)
    return
}
d.stakingModule.PutStakingInfoToDB(stakingInfo.BlockNum, staking.ToStakingInfo(stakingInfo))
``` [5](#0-4) 

Once written, the corrupted record is read back by `GetStakingInfo` for pre-Kaia blocks via the DB-first path:

```go
if !isKaia {
    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
        s.stakingInfoCache.Add(sourceNum, si)
        return si, nil   // returns fake data, never re-checks state
    }
}
``` [6](#0-5) 

The corrupted `StakingInfo` is then consumed by `FinalizeState` to distribute KAIA rewards:

```go
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
``` [7](#0-6) 

The `StakingInfo` struct fields that an attacker can forge include `RewardAddrs` (where KAIA rewards are sent), `StakingAmounts` (which determines each validator's share), and `KEFAddr`/`KIFAddr`/`KPFAddr` (treasury fund destinations): [8](#0-7) 

---

### Impact Explanation

**Unauthorized KAIA transfer / reward redirection**: By replacing `RewardAddrs` with attacker-controlled addresses and inflating `StakingAmounts`, the attacker causes `FinalizeState` to call `state.AddBalance` on attacker addresses for every subsequent block, draining the block reward budget to the attacker.

**Consensus divergence on honest nodes**: Honest nodes derive staking info from the canonical state trie. A node that accepted fake staking info will compute a different `RewardSpec`, apply different balance changes, and produce a different state root. It will reject valid blocks from honest validators (or produce blocks that honest validators reject), permanently forking the compromised node off the canonical chain.

**Treasury fund address hijacking**: Forging `KIFAddr`/`KEFAddr`/`KPFAddr` redirects protocol-level treasury distributions to attacker wallets.

---

### Likelihood Explanation

The fast-sync path is triggered automatically whenever a node syncs from scratch or after a long gap. Any peer that the syncing node connects to — including peers on the public P2P network — can serve `StakingInfoMsg` responses. No special privilege is required beyond being a connected peer. The `SyncStakingInfo` recovery path additionally requires the operator to invoke the API with a peer ID, but the peer itself is untrusted and its payload is unverified.

---

### Recommendation

1. **Derive and commit a staking-info commitment into the block header** (e.g., a hash of the canonical staking info at each staking-interval block), then verify received `P2PStakingInfo` against that commitment inside the `validate` closure in `DeliverStakingInfos`, mirroring the receipt-root check.

2. **Until a header commitment exists**, replace the no-op `validate` with a re-derivation from the local state: after receiving a `P2PStakingInfo`, call `getFromStateByNumber` for the same block and compare the result field-by-field before calling `PutStakingInfoToDB`.

3. **In `SyncStakingInfo`**, apply the same content verification before writing to the DB; a matching `BlockNum` alone is not sufficient.

---

### Proof of Concept

```
Attacker setup:
  - Run a Kaia node (or a custom P2P server speaking the Kaia protocol).
  - Prepare a crafted StakingInfoMsg response where:
      P2PStakingInfo.BlockNum     = <legitimate staking-interval block>
      P2PStakingInfo.CouncilRewardAddrs = [attacker_address, ...]
      P2PStakingInfo.CouncilStakingAmounts = [max_uint64, ...]

Victim node (fast-syncing):
  1. Connects to attacker peer during fast sync.
  2. Sends StakingInfoRequestMsg for block hashes at staking intervals.
  3. Attacker responds with the crafted P2PStakingInfo.
  4. handleStakingInfoMsg → downloader.DeliverStakingInfos →
       queue.DeliverStakingInfos (validate = no-op, always nil) →
       commitFastSyncData → PutStakingInfoToDB writes fake record.
  5. After sync completes, GetStakingInfo for pre-Kaia blocks reads
     the fake record from DB (cache/DB-first path, never re-checks state).
  6. FinalizeState uses fake RewardAddrs → state.AddBalance(attacker, reward)
     for every block in the affected staking interval.
  7. Victim node's state root diverges from honest network; node is forked.
```
