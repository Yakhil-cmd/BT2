### Title
Team-membership authorization is not bound to the repository/organization a Stack is created for, allowing cross-organization writes with the wrong GitHub App's credentials - (File: app/controllers/shipit/stacks_controller.rb)

### Summary
`Shipit::Authentication#force_github_authentication` only checks `current_user.authorized?`, which is backed by global team membership (`Shipit.github_teams`, i.e. `Shipit.github.oauth_teams`) resolved against the *default* configured GitHub organization/App. [5](#0-4)  This check never inspects which repository or organization the user is about to act on. `StacksController#create` (and `RepositoriesController#create`) then accepts fully attacker-controlled `repo_owner`/`repo_name` params and does `Repository.find_or_create_by(owner:, name:)` with no verification that the caller has any GitHub-side permission on that repository. [6](#0-5) 

In a single-App deployment this is contained by the fact that the installed GitHub App can only act on repos in its own installation. But Shipit explicitly supports a **multi-organization** configuration where `config/secrets.yml`'s `github` key is keyed per-organization, each with its own App credentials, `webhook_secret`, and `oauth.teams` list. [7](#0-6)  `Shipit.github(organization:)` resolves credentials purely from the `owner` string carried on the `Repository`/`Stack` record — the same string the requesting user supplied at stack-creation time. [4](#0-3)  `Stack#github_app`/`#github_api` and `Repository#github_app` both call `Shipit.github(organization: repository.owner)` to obtain the API client used for syncing commits, posting statuses, and eventually deploying. [8](#0-7) [9](#0-8) 

### Finding Description
The binding that should hold is: *organization whose team membership authenticated the user* == *organization/repository whose GitHub App credentials get exercised on the user's behalf*. Instead:
- `force_github_authentication` authorizes based on `current_user.authorized?`, itself derived from `Shipit.github_teams`, which is scoped to `github_default_organization` (the first non-reserved key under `secrets.github`). [10](#0-9) 
- `StacksController#create_params`/`#repository` place no constraint on `repo_owner`/`repo_name` other than format validation on the `Repository` model (`owner`/`name` regex, length, uniqueness) — there is no check that `repo_owner` matches an org the authenticated user belongs to. [11](#0-10) [12](#0-11) 
- Once the `Stack`/`Repository` exists, all subsequent GitHub operations (sync, status posting, deploy, merges) resolve the App/token strictly from `repository.owner`, i.e. from attacker-supplied data, via `Shipit.github(organization: owner)`. [13](#0-12) 

Consequently, a user who is only authorized because they belong to a team configured under Organization A's GitHub App section can create a `Stack` whose `repo_owner` names Organization B (also configured in the same multi-org `secrets.yml`), causing Shipit to authenticate to GitHub as **Organization B's App** (its own installation token, `private_key`, `app_id`) to sync commits/statuses and run deploy tasks against Organization B's repository — without ever being vetted against Organization B's `oauth.teams`.

### Impact Explanation
This crosses the "unauthorized deploy" / cross-repository-write category: an actor legitimately authorized only for one configured GitHub organization can cause the engine to act — using another organization's own GitHub App credentials — against a repository/org they were never authorized for, including scheduling deploy `Task`s (`Stack#trigger_task`) and posting commit statuses/merges with that other organization's installation token.

### Likelihood Explanation
Requires only being a member of any one team listed in a multi-organization `Shipit.github_teams` configuration (not privileged, not requiring GitHub write access to the target repo) — reachable through the standard, documented "create stack" web form/endpoint. Likelihood is limited to deployments that actually use the multi-organization `github:` schema; single-App deployments are naturally bounded by GitHub App installation scope.

### Recommendation
Validate, at `Stack`/`Repository` creation and on every `Shipit.github(organization:)` lookup, that `repository.owner` belongs to the same organization(s) the authenticated user's `authorized?` check passed for (i.e., check `current_user`'s team membership against the specific target organization's `oauth.teams`, not just the default org's).

### Proof of Concept
1. Configure `secrets.yml` with two orgs, `OrgOne` (attacker's team) and `OrgTwo` (victim org), each with its own GitHub App per `docs/setup.md`'s multi-app schema.
2. Authenticate as a user who is only a member of `OrgOne`'s configured OAuth team; `force_github_authentication` passes because `current_user.authorized?` only checks membership in the default org's teams.
3. POST to `stacks#create` with `stack[repo_owner]=OrgTwo`, `stack[repo_name]=private-repo`, `environment`, `branch` — `StacksController#repository` happily does `Repository.find_or_create_by(owner: "OrgTwo", name: "private-repo")` with no ownership/permission check.
4. `after_commit :sync_github` fires; `Stack#github_app`/`#github_api` resolve to `Shipit.github(organization: "OrgTwo")`, using OrgTwo's own installation token to read commits/statuses and, if triggered, run deploy tasks — all initiated by a user never authorized against OrgTwo.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
