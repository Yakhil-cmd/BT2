### Title
Global unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a cross-repo SHA collision write attacker-authenticated status onto a victim's commit, triggering an unauthorized deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely `by sha`, with no scoping to the repository that authenticated the webhook. Unlike every other handler in this module, it never uses the `stacks`/`repository_name` scoping helper from `Handler`, so a `status` event signed by an attacker's own GitHub organization can flip the deployable state of, and enqueue a deploy for, a completely unrelated victim stack whose commit happens to share the same SHA.

### Finding Description
The broken binding, stated explicitly: `repository_owner` used by `WebhooksController#verify_signature` (the org that owns the webhook's HMAC secret, i.e., the **attacker's** org) should equal the org that owns the `Stack`/`Repository` whose `Commit#deployable?` state is mutated (the **victim's** org) — but the code never enforces `attacker_org == victim_org`.

Trace:
- `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` [1](#0-0)  and validates the signature against `Shipit.github(organization: repository_owner)` [2](#0-1) . This only proves the payload was signed by whoever owns `repository_owner` (the attacker's org, since the attacker sends the status event from their own repo).
- Every payload is then dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) , with no further repository/stack binding performed by the controller.
- The generic `Handler` base class provides a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)` derived from the payload's own `repository.full_name` [4](#0-3) , which other handlers (e.g. pull_request handlers) use to stay within the authenticated repository's stacks.
- `StatusHandler#process`, however, ignores this scoping entirely and queries the `Commit` table globally by SHA only: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Because `sha` is not `unique` per-repository in the `commits` table's application logic (it's just a git SHA string), any `Commit` row anywhere in the database with a matching SHA is updated — including commits belonging to stacks owned by different GitHub orgs/repos than the one that signed the request.
- `create_status_from_github!` → `add_status` computes the new aggregate `status`, and if the simple-state changes, emits `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges` [6](#0-5) .
- `Commit#deployable?` recomputes based on the newly attached status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [7](#0-6) .
- `schedule_continuous_delivery` (an `after_commit` callback on create, and also invoked by refresh flows) checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` [8](#0-7)  — for the **victim's** `stack`, even though the request was authenticated only as the attacker's org.

Exploit flow: the attacker creates a commit in their own repo whose SHA equals the SHA of the victim's blocked/pending head commit (achievable via cherry-pick or orphan commit with identical tree/parents/author/committer timestamps and message — SHA1 is fully determined by these fields, no secret material is required). The attacker then triggers (or directly POSTs, since they control their own repo's GitHub webhook or can call `POST /webhooks` with a payload whose `repository.owner.login` is their own org) a `status` event with `state=success` for that SHA. `verify_signature` succeeds because it validates against the attacker's own `webhook_secret`, which they legitimately possess for their own org. `StatusHandler#process` then matches the victim's `Commit` row by SHA equality and applies the success status to it, flipping `deployable?` to true and scheduling `ContinuousDeliveryJob` for the victim's stack.

None of the listed guards prevent this: `verify_signature` only checks that the *attacker's own* org's secret matches the payload attacker controls (`repository_owner` in that payload is the attacker's org, so it always passes for the attacker's own signed request); `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not repository ownership; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant since webhooks bypass session-based auth entirely; the `stacks` scoping helper exists in `Handler` but is simply not used by `StatusHandler`.

### Impact Explanation
An attacker who controls no more than their own GitHub repository and its webhook can cause `ContinuousDeliveryJob.perform_later(victim_stack)` to be enqueued for a stack and repository they do not own or have any permission on, resulting in an unauthorized deploy being triggered against the victim's continuous-deployment-enabled stack. This is a cross-tenant write: a payload authenticated for repository/org A mutates commit/stack state belonging to unrelated org B. This matches the "Critical" impact category explicitly listed: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The attack is repeatable against any victim stack for which the attacker can find or construct a SHA-colliding commit (feasible since GitHub SHA1 is a public, non-secret function of author/committer identity, timestamps, tree, parents, and message — none of which are secrets), so it is not limited to one specific stack.

### Likelihood Explanation
Preconditions required: the victim stack must have `continuous_deployment?` true and the shared-sha commit must currently be pending/not-deployable, both plausible defaults for active CD pipelines. The attacker needs only an unprivileged GitHub account capable of pushing a repo and constructing a commit with fields matching the victim's commit (cherry-pick is the simplest and requires no cryptographic effort — a straight cherry-pick or `git commit --author=... --date=... `of the exact same diff against the exact same parent tree reproduces the SHA deterministically). No Shipit secrets, sessions, or `Shipit.github_teams` membership are needed. Triggering the `status` webhook only requires normal GitHub CI activity on the attacker's own fork/repo (or GitHub API access to their own repo's commit statuses), which is fully within an unprivileged user's control. This makes the attack straightforward and repeatable at attacker's discretion.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the pattern used by other handlers via `Handler#stacks`/`repository_name`. For example, restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Stack`/`Repository` filtered by `repository_name` (i.e., `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: Repository.from_github_repo_name(repository_name)&.id })`), so that a status event can only ever mutate commits belonging to the repository identified in, and cryptographically bound to, the same payload that was signature-verified.

### Proof of Concept
Under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or a new test file), add a minitest:

1. Create `victim_stack` belonging to `victim/repo` with `continuous_deployment: true`, and a `victim_commit` with `sha: SHARED_SHA` whose current status is pending (not deployable).
2. Create `attacker_stack`/repository `attacker/repo` (or simply don't create any Shipit stack for the attacker's repo at all — the attacker's repo need not even be onboarded onto Shipit).
3. Build a `status` webhook payload with `sha: SHARED_SHA`, `state: 'success'`, and `repository.full_name: 'attacker/repo'`, `repository.owner.login: 'attacker'`.
4. Assert before: `victim_commit.reload.deployable?` is `false`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, since that's an orthogonal, already-passing control for the attacker's own org) or POST to `/webhooks` with a valid signature computed using `attacker`'s configured `webhook_secret` fixture.
6. Assert after: `victim_commit.reload.deployable?` is `true`, and:
   ```ruby
   assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
     Shipit::Webhooks::Handlers::StatusHandler.call(payload)
   end
   ```
   confirming the deploy job was enqueued for `victim_stack` despite the request only being authenticated for `attacker/repo`.
