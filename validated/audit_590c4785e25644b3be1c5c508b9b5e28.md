### Title
Cross-organization team hijack via `MembershipHandler#process` / `Team.find_or_create_by!(github_id:)` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the `Team` to mutate solely by the attacker-supplied `params.team.id` (GitHub team ID) via `Team.find_or_create_by!(github_id: params.team.id)`, and resolves the `User` to mutate solely by attacker-supplied `params.member.login` via `User.find_or_create_by_login!`. Neither lookup is cross-checked against the organization whose `webhook_secret` actually verified the request, so an attacker who legitimately administers *any* org onboarded to a multi-tenant Shipit instance can add an arbitrary existing `User` to an arbitrary *pre-existing* `Team` belonging to a *different* organization, including a `Team` in `Shipit.github_teams`.

### Finding Description
The binding the design implicitly assumes is:
`organization_that_signed_the_webhook (via webhook_secret) == organization that owns the Team/User membership record being mutated`

Trace:
- `WebhooksController#verify_signature` selects the `GithubApp`/secret to verify against using `repository_owner`, which for events with no `repository` key falls back to `params.dig('organization', 'login')` — a field taken directly from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 
- This only proves the JSON's `organization.login` matches *some* org whose secret the attacker holds (their own onboarded org, e.g. `OrgTwo`), not that it matches the org that actually owns the `team.id` referenced in the payload.
- `MembershipHandler#process` then does:
```
team = find_or_create_team!            # Team.find_or_create_by!(github_id: params.team.id) { ...organization = params.organization.login }
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member)                # on action == 'added'
``` [3](#0-2) 
- Critically, `find_or_create_by!` only runs the `organization = params.organization.login` assignment block **on create**. If a `Team` row with that `github_id` already exists (e.g., it was previously imported as part of `Shipit.github_teams` via `Team.find_or_create_by_handle`/`refresh_members!`, which belongs to a completely different, privileged organization such as `OrgOne`), the existing record is returned unmodified — its real `organization` is never re-validated against the signing org.
- `User.find_or_create_by_login!` matches purely by `login`, which is a GitHub-global (not per-org) identifier, so it will happily return a `User` row originally created from a PR against an entirely unrelated repository/org: [4](#0-3) 
- The result: `team.add_member(member)` creates a `Membership` linking a privileged `Team` (belonging to org `OrgOne`) to a `User` row, using only a webhook signed by an unrelated org `OrgTwo`'s secret.
- `User#authorized?` checks membership across all `Shipit.github_teams` globally, so this membership grants Shipit-wide access: [5](#0-4) , enforced in `force_github_authentication`: [6](#0-5) 

No existing guard prevents this: `verify_signature` only validates the HMAC against whichever org name the attacker put in the body (which the attacker sets to their own org, matching their own real secret), it does not validate that the `team.id`/`team.organization` in the payload is actually owned by that org. `find_or_create_team!` performs no such cross-check either.

### Impact Explanation
An attacker who legitimately administers one onboarded-but-unprivileged GitHub organization (`OrgTwo`) in a multi-tenant Shipit deployment can:
1. Send a forged `membership` webhook signed with `OrgTwo`'s real secret, with `organization.login = "OrgTwo"` (so signature verification passes).
2. Set `team.id` to the known/enumerable GitHub team ID of a privileged team belonging to a different org (`OrgOne`) that is part of `Shipit.github_teams`.
3. Set `member.login` to the login of any existing (or newly creatable) Shipit `User`.
4. `team.add_member(member)` adds that `User` to the privileged `Team`, and `User#authorized?` becomes `true`, granting that user (who may be the attacker's own GitHub account, or an accomplice) full authenticated access to the entire Shipit instance — all stacks, deploys, tasks, and secrets across every tenant, not just `OrgTwo`'s.

This is repeatable per-request and against any team whose `github_id` the attacker can determine (team IDs are visible via the GitHub API to anyone who can list org teams, or may leak elsewhere). It matches the Critical category "a payload for one repository/organization mutating another's team" and directly causes "escalation into `Shipit.github_teams` authorization" (High/Critical bar).

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multiple GitHub organizations (`github: { OrgOne: {...}, OrgTwo: {...} }`, a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), and the attacker must legitimately control one of the onboarded (but unprivileged) orgs, knowing its own `webhook_secret`. The attacker needs to know or guess the target privileged team's numeric GitHub `id` — obtainable via GitHub's public/authenticated API (`GET /orgs/{org}/teams`) if they have any read access, or otherwise guessable/enumerable. No Shipit secrets, sessions, or `Shipit.github_teams` membership are required. Cost is a single crafted HTTP POST; fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!` and `#process`, verify that the `Team`'s stored `organization` matches `params.organization.login` (the org whose secret verified the request) before creating/using it, and reject the webhook (or create a distinct team) if they diverge. Additionally, `WebhooksController#verify_signature` should not trust attacker-controlled `organization.login`/`repository.owner.login` alone — the resolved organization used to look up the secret must be re-validated as the actual owner of any pre-existing `Team`/`Repository` record being mutated, not merely self-consistent with the request body.

### Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/membership_handler_test.rb` or controller-level in `test/controllers/webhooks_controller_test.rb`):
```ruby
test "membership webhook from an unrelated org cannot add members to another org's privileged team" do
  # OrgOne's privileged team, part of Shipit.github_teams
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  victim_user = shipit_users(:walrus) # login originally seen via an unrelated org/PR
  refute privileged_team.members.include?(victim_user)

  # Attacker legitimately controls OrgTwo, signs with OrgTwo's real secret,
  # but claims team.id == privileged_team.github_id (belonging to shopify/OrgOne)
  Shipit.stubs(:github).with(organization: 'orgtwo').returns(orgtwo_github_app_with_real_secret)

  request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: 'orgtwo' },
    member: { login: victim_user.login }
  }.to_json

  post :create, body: sign_with_orgtwo_secret(body), as: :json

  assert_response :ok
  # Binding check: org that signed ('orgtwo') != team's actual organization ('shopify')
  assert_not_equal 'orgtwo', privileged_team.reload.organization
  # But membership was still mutated:
  assert privileged_team.members.reload.include?(victim_user)
  assert victim_user.reload.authorized? # escalated into Shipit.github_teams
end
```
Both sides of the equality (`signing_org = 'orgtwo'` vs `team.organization = 'shopify'`) diverge, and the mutation and privilege escalation still occur, confirming the vulnerability.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

    def self.find_or_create_by_login!(login)
      find_or_create_by!(login:) do |user|
        # Users are global, any app can be used
        # This will not work for users that only exist in an Enterprise install
        user.github_user = Shipit.github.api.user(login)
      end
    end
