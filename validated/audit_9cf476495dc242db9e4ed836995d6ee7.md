### Title
`is_valid_sig()`/`vrf_verify()` in oscript accept RSA public keys of any bit length, including cryptographically broken sizes - ([File: signature.js])

### Summary
ocore's oscript `is_valid_sig()` and `vrf_verify()` formula functions delegate PEM public-key validation to `validateAndFormatPemPubKey()` in `signature.js`, which only checks the key's ASN.1 algorithm OID (RSA vs. ECDSA/curve) and, for RSA, performs no minimum-modulus-size check whatsoever. An AA that uses PEM/RSA signature verification as part of its authorization logic (e.g., to validate an externally-signed message before releasing funds, similar to the reported PGP-2FA pattern) can be configured — deliberately or by mistake — with a small RSA key (512–1024 bits), and any trigger sender who can factor that public modulus can forge a valid signature and satisfy the AA's check, without ever holding the real private key.

### Finding Description
`validateAndFormatPemPubKey()` at [1](#0-0)  parses the DER content of a supplied PEM public key and looks up the algorithm/curve OID in `objSupportedPemTypes`. For ECDSA keys it validates the expected public-key length for the specific named curve (`hex_pub_key_length`), but for RSA (`06092a864886f70d0101010500` — PKCS #1) it validates only that the OID matches; there is no lower bound placed on the RSA modulus size [2](#0-1) .

The codebase already recognizes that some algorithms are cryptographically too weak to allow post a certain point (`pemCurvesFixMci` / `bPostPemCurvesFix`), and restricts ECDSA usage after that MCI to a small allow-list of strong curves (P-256, P-224, P-384, secp256k1) via `objSafePemTypes` [3](#0-2) . However, `'06092a864886f70d0101010500'` (generic RSA, PKCS #1) is included in `objSafePemTypes` unconditionally, regardless of key size, so even after the "curve fix" that blocked weak elliptic curves, RSA keys of any bit length — including 512-bit RSA, which was publicly factorable in 1999 and is trivially factorable with modern tools (matching the exact weakness described in the external report) — continue to be accepted as valid signing keys by `is_valid_sig()`.

`signature.js` is used from oscript formula evaluation (`formula/evaluation.js`, which requires `signature.js` and implements `is_valid_sig`/`vrf_verify`), and the tests in `test/pem_sig.test.js` explicitly confirm that 512-bit RSA keys and PEM signatures are accepted by `is_valid_sig()` as valid [4](#0-3) . The same test file also shows explicit acceptance of extremely weak EC curves such as secp112r2/secp128r1/etc for keys registered before the curve-safety fix [5](#0-4) , again mirroring the report's theme of "weak key generation that undermines cryptographic authentication."

Because `is_valid_sig`/`vrf_verify` are ordinary oscript formula primitives, any AA author can embed logic such as "release funds if `is_valid_sig(message, stored_pem_key, trigger.data.signature)`" where `stored_pem_key` is an RSA key registered by the AA (e.g. for bridging, oracle attestation, or off-chain approval flows). If that RSA key is small (512/768/1024 bits — all of which pass validation with no complaint), an attacker who obtains the public key (which is necessarily public, stored on-chain in the AA's state or definition) can factor the modulus offline, derive the private key, and submit a forged signature inside `trigger.data` from any unprivileged trigger sender, satisfying the AA's authorization check.

### Impact Explanation
If an AA's spending/authorization logic relies on `is_valid_sig()`/`vrf_verify()` with an RSA key that is weak (which ocore's validation silently permits), any trigger sender who factors the modulus can forge signatures accepted by the AA, resulting in unauthorized release of AA funds — a concrete "AA fund loss" scenario matching the accepted impact classes. This is exactly the class of bug in the source report (broken authentication due to unenforced minimum key strength for signature verification), transplanted from PGP 2FA in AVideo to oscript's RSA-based `is_valid_sig` primitive in ocore.

### Likelihood Explanation
Likelihood depends on AA authors choosing to use small RSA keys for on-chain signature verification, which is a plausible but not universal pattern (bridges/oracles that want RSA compatibility with legacy signing tools). Because ocore's library layer performs no minimum-size enforcement and even explicitly whitelists RSA post the curve-safety fix, any weak key an AA author picks (intentionally or through misconfiguration/key-generation-tool defaults) is silently accepted rather than rejected, increasing the chance that a weak deployment goes unnoticed until exploited.

### Recommendation
In `signature.js`'s `validateAndFormatPemPubKey()`, when the detected algorithm is RSA, decode the SubjectPublicKeyInfo to determine the modulus bit length and reject keys below a safe minimum (e.g., 2048 bits), consistent with how ECDSA curve strength is already screened via `objSafePemTypes`. Apply this check unconditionally (not just gated by `bPostPemCurvesFix`) so that AAs cannot register or rely on cryptographically broken RSA keys for `is_valid_sig`/`vrf_verify` authorization logic.

### Proof of Concept
1. An AA author defines logic using `is_valid_sig(message, pem_key, trigger.data.signature)` where `pem_key` is a 512-bit RSA public key (e.g., the exact key used in `test/pem_sig.test.js:807-824`), intending it as an authorization gate for releasing AA funds.
2. Because `validateAndFormatPemPubKey()` performs no RSA modulus-size check [2](#0-1) , this key passes validation without warning, and `is_valid_sig` behaves as documented, returning `true` for correctly signed messages as shown in the test [4](#0-3) .
3. An attacker factors the 512-bit RSA modulus offline (trivial with CADO-NFS/msieve/yafu, hours on commodity hardware) to recover the private exponent.
4. The attacker crafts a forged signature over the message the AA expects and submits it via `trigger.data.signature` in an ordinary, unprivileged AA trigger.
5. The AA's `is_valid_sig()` check returns `true`, and the AA releases funds to the attacker without the legitimate signer ever having authorized the action.

function validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix) {

	if (!ValidationUtils.isNonemptyString(pem_key))
		return handle("pem key should be a non empty string");

	//we remove header and footer if present
	var contentAloneB64 = pem_key.replace("-----BEGIN PUBLIC KEY-----", "").replace("-----END PUBLIC KEY-----", ""); 
	
	//we remove space, tab space or carriage returns
	contentAloneB64 = contentAloneB64.replace(/\s/g, "");

	if (contentAloneB64.length > 736) // largest is RSA 4096 bits
		return handle("pem content is too large");

	if (!ValidationUtils.isValidBase64(contentAloneB64))
		return handle("not valid base64 encoding" + contentAloneB64);

	var contentAloneBuffer = Buffer.from(contentAloneB64, 'base64');

	if (contentAloneBuffer[0] != 0x30)
		return handle("pem key doesn't start with a sequence");

//we determine start and length of algo/curve identifiers
	if (contentAloneBuffer[1] <= 0x7F){
		if (contentAloneBuffer[2] != 0x30)
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 4;
		var identifiersLength = contentAloneBuffer[3];
	} else if (contentAloneBuffer[1] == 0x81){
		if (contentAloneBuffer[3] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 5;
		var identifiersLength = contentAloneBuffer[4];
	} else if (contentAloneBuffer[1] == 0x82){
		if (contentAloneBuffer[4] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 6;
		var identifiersLength = contentAloneBuffer[5];
	} else {
		return handle("wrong length tag");
	}

	//we decode the length of identifiers
	if (identifiersLength != 13 && identifiersLength != 16 && identifiersLength != 19 && identifiersLength != 20)
		return handle("wrong identifiers length" + identifiersLength);

	//we isolate the identifiers
	var contentAloneHex = contentAloneBuffer.toString('hex')
	var typeIdentifiersHex = contentAloneHex.slice(identifiersStart * 2, identifiersStart *2 + identifiersLength *2);

	if (!objSupportedPemTypes[typeIdentifiersHex])
		return handle("unsupported algo or curve in pem key");

	if (bPostPemCurvesFix && !objSafePemTypes.has(typeIdentifiersHex))
		return handle("unsupported curve after pem curves fix MCI");

	if (algo != "any"){
		if (algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "ECDSA")
			return handle("PEM key is not ECDSA type");
		if (algo == "RSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "RSA")
			return handle("PEM key is not RSA type");
	}

	if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].hex_pub_key_length != (contentAloneHex.length - identifiersStart * 2 - identifiersLength *2 - 8))
		return handle("wrong key length");

	//we add back header and footer
	pem_key =	"-----BEGIN PUBLIC KEY-----" + "\n";
	pem_key += contentAloneB64+"\n";
	pem_key += "-----END PUBLIC KEY-----";
	return handle(null,pem_key);
}
