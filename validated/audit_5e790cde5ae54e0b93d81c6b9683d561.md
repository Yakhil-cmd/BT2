### Title
Webhook signature is verified against the payload's `repository.owner.login`/`organization.login` field, but handlers act on the unrelated `repository.full_name`/`team`/`member` fields — allowing an attacker who controls the webhook secret for *any one* configured GitHub organization to forge events for *any other* organization/repository on the same Shipit instance - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to validate a webhook payload against using a field taken from the attacker-controlled JSON body itself (`repository.owner.login` or `organization.login`), then, once the signature is accepted, hands the *entire* raw body to handlers that act on a different field (`repository.full_name`, `team`, `member.login`) to decide which repository/stack/team to mutate. Because the field used to pick the verification secret is not cryptographically bound to the field used to select the target repository/team, an attacker who legitimately knows the webhook secret for one organization configured in the multi-org setup can forge a signature for a payload whose "acted-upon" fields reference a completely different organization/repository/team.

### Finding Description
`verify_signature` computes `repository_owner` purely from the untrusted JSON body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This `repository_owner` is used only to pick *which organization's secret* to HMAC-verify with; it plays no other role in processing. The actual work done by handlers uses a **different** field of the same body: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `owner/repo` from `full_name` and does a plain DB lookup with no cross-check against `repository.owner.login`: [4](#0-3) 

For the `membership` event, the handler creates/looks up an arbitrary `Team` and adds/removes an arbitrary `User` based on `params.team` / `params.organization.login` / `params.member.login`, again independent of the `repository_owner` used for signature selection: [5](#0-4) 

Because Shipit explicitly supports "Using Multiple GitHub Applications" where each organization has its own `webhook_secret`, and `HMAC` verification is keyed off `Shipit.github(organization: repository_owner)`: [6](#0-5) 

an attacker who is a legitimate GitHub-App owner/administrator for org **A** (and therefore knows or can obtain org A's `webhook_secret` the same way a real GitHub webhook delivery does — no repository write access or Shipit session is required, only the raw HTTP endpoint and the secret for their own org) can craft an arbitrary JSON body where:
- `repository.owner.login` (or `organization.login`) = `"org-A"` → causes `verify_signature` to fetch org A's secret and validate correctly, because the attacker computes the HMAC themselves over the exact body they send.
- `repository.full_name` = `"org-B/victim-repo"` (a different organization's repository configured on the same Shipit instance) → causes the handler to look up and mutate `org-B`'s stacks/teams.

The equality broken is exactly the class named in scope: *"an organization that authenticated versus the repository that is written."* Before the attacker's request: `repository_owner` (authenticated org) == `repository.full_name`'s owner (written repo owner) is assumed but never enforced. After: an attacker can make these diverge arbitrarily while the signature still validates.

### Impact Explanation
This is a cross-repository/cross-organization write triggered without any privilege on the target repository: `push` events can trigger `GithubSyncJob`/deploy pipeline synchronization for a victim stack, `pull_request` events can archive/create/label review stacks belonging to a victim repository, `status`/`check_suite` events can inject fake CI statuses/check runs used as deploy gates for the victim stack, and `membership` events can create/delete `Team` records and add/remove arbitrary `User` records from a `Team`. Since `User#authorized?` gates application access on membership in `Shipit.github_teams`, forged `membership` events reaching that code path constitute escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes.

### Likelihood Explanation
Requires only that Shipit be configured for multiple GitHub organizations (a documented, supported configuration in `docs/setup.md`), and that the attacker legitimately owns/administers at least one of those organizations (or otherwise obtains that organization's `webhook_secret`, e.g. by being a normal repository/organization owner who set up their own Shipit-integrated GitHub App). No Shipit session, `ApiClient` token, or repository write access to the *victim* org is needed — only knowledge of one organization's `webhook_secret`, which is a standard, low-privilege credential in a multi-tenant Shipit deployment.

### Recommendation
Bind the field used to select the verification secret to the field used to select the mutation target. Concretely, `verify_signature` should either:
1. Verify the signature using the secret derived from the *same* field the handler will use for repository lookup (`repository.full_name`'s owner segment), rather than an independent `repository.owner.login`/`organization.login` field; or
2. After signature verification, re-check that `repository.owner.login` (or `organization.login`) exactly matches the owner segment of `repository.full_name` (and, for `membership` events, that `organization.login` matches the org the webhook secret was selected for) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `org-A` and `org-B`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple GitHub Applications").
2. As the legitimate owner of `org-A`'s GitHub App (attacker), craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "org-B/victim-repo", "owner": { "login": "org-A" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-A's webhook_secret, raw_body)>` locally.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner == "org-A"`, fetches `org-A`'s app/secret, and the HMAC validates successfully.
6. `PushHandler#process` runs `Repository.from_github_repo_name("org-B/victim-repo")` and triggers `stack.sync_github(expected_head_sha: ...)` on `org-B`'s stack — a cross-organization action the attacker had no legitimate access to trigger.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
