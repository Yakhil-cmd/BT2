### Title
Front-running of a `hash`-authentifier address definition allows anyone who observes the redeeming unit to copy the revealed secret and steal the funds - ([File: definition.js])

### Summary
Obyte address definitions support a `['hash', {algo, hash}]` authentifier that lets a spender authorize an input simply by revealing a string whose sha256 matches a pre-committed hash, with no binding to the spender's address or public key. [1](#0-0) [2](#0-1)  The definition validator explicitly forbids negating this operator and only checks the algorithm/hash format, and the authentifier check simply verifies `sha256(secret) === committed_hash` without any check that the redeemer is the intended recipient.

### Finding Description
When an address is defined (fully or as one branch of an `or`) using `['hash', {hash: sha256(secret)}]`, any unit that spends from that address must include the plaintext `secret` in the `authentifiers` object at the corresponding path so that `validateAuthentifiers` can recompute `sha256(secret)` and compare it to the committed hash. [2](#0-1)  This is directly analogous to a hash-lock/HTLC redemption in other ledgers: the "proof of knowledge" (the secret) is only useful once, and revealing it in a broadcast unit exposes it to anyone watching the network before that unit becomes final.

Because ocore units are gossiped/broadcast to peers before they are stable (`network.broadcastJoint`), and unit inclusion order is not guaranteed by submission order alone (parallel units racing for the DAG can be reordered by main-chain selection), an attacker monitoring the network for such a spending unit can:
1. Extract the plaintext secret from the observed unit's `authentifiers`.
2. Immediately construct their own competing unit spending the *same* unspent output from the *same* hash-locked address, using the copied secret as the authentifier, and pointing outputs to their own address.
3. Race to get their unit propagated/witnessed before (or in parallel main-chain branches with) the original spender's unit.

The wallet code that actually uses this pattern is the textcoin/private-payment "secret" claim flow: `getSigner()` supports a `secret` signer type that produces the raw secret as the authentifier value, and `extractAddressPathsFromDefinition` in `wallet_defined_by_addresses.js` explicitly recognizes `case 'hash': result[path] = 'secret';` as a legitimate address-definition pattern used in shared/handoff addresses. [3](#0-2) [4](#0-3)  This is architecturally the same class of bug as the reported issue: the value needed to claim a reward/output is fully revealed in a public, unconfirmed transaction, so "no need to run a validator (or know the secret in advance) — just copy the transaction/secret and front-run it."

Whether this is exploitable in practice depends on how the `hash` branch is combined with other conditions in a real address definition:
- If `hash` is used **alone** (bearer-secret address, e.g., an ad-hoc handoff/airdrop-style address where whoever presents the secret can spend), the front-running attack directly steals the funds — this mirrors the reported bug exactly.
- If `hash` is combined via `and` with an `address`/`sig` condition binding to a specific claimant's key, front-running the raw secret alone is insufficient because the attacker still cannot produce a valid signature for the second branch, and the vulnerability does not apply.

Standard Obyte textcoins (`wallet.js:expandMnemonic`) use a `sig` (signature-based) definition rather than `hash`, so the shipped textcoin feature itself is not vulnerable to secret copying — the funds sit on a normal key-controlled address derived from the mnemonic, and knowledge of the mnemonic already implies control of the private key, so "front-running" a raw secret does not apply there. The exposure is specific to any address (via `wallet_defined_by_addresses.js` shared-address definitions or other AA/oscript usage) that relies purely on `['hash', ...]` as a bearer/oracle-style unlocking condition without binding it to a signature.

### Impact Explanation
Where a `hash`-only (or otherwise unbound) definition is used to gate spending of value, an observer of the mempool/network can redirect the funds to themselves purely by copying the revealed secret into a competing spend, resulting in concrete unauthorized loss of funds for the intended claimant — matching the High-severity impact class described in the source report (frontrunning a reward/claim transaction without needing to independently produce the underlying proof).

### Likelihood Explanation
Likelihood is conditional: it requires an application/wallet feature to construct an address whose definition uses `hash` without an accompanying signature/address binding on the same branch. The protocol itself permits and validates this pattern (`definition.js`), and the wallet-side code (`getSigner`'s `ifSecret` branch, `wallet_defined_by_addresses.js`'s recognition of `hash` paths as `'secret'`) demonstrates this pattern is an intentional, supported building block for shared/handoff addresses, not merely a theoretical construct. I could not fully verify from the indexed files whether any shipped, unauthenticated single-`hash` address is created by default flows (textcoins use `sig`, not `hash`), so the concrete blast radius depends on downstream/custom usage of this primitive that is outside the reviewed files.

### Recommendation
- Document prominently (and enforce via linting/warnings in wallet UIs that build custom definitions) that a `hash` authentifier must never be used as a standalone/bearer spending condition for value; it should always be combined with an `address`/`sig` condition binding the secret-holder identity, or used only for informational/commitment purposes.
- Consider adding a definition-validation warning (not necessarily a consensus rule change, to preserve backward compatibility) when a `hash` clause exists outside of any `and` with a `sig`/`address` clause, since such definitions are inherently front-runnable once any output exists at that address.
- For any first-party feature (e.g., future bounty/reward AAs) that considers using bare secret-reveal unlocking, require the payload to also bind the destination address (e.gsecret = hash(secret || claimant_address)) so a copied secret cannot be redirected to a different destination.

### Proof of Concept
1. Create address `A` with definition `['hash', {hash: sha256("s3cr3t")}]` and fund it with bytes.
2. The legitimate holder of `"s3cr3t"` composes and broadcasts a unit spending from `A`, with `authentifiers = { r: "s3cr3t" }`, sending funds to their own address `B`.
3. Before this unit stabilizes, an attacker running any full/light node observing gossiped units extracts `"s3cr3t"` from the broadcast unit's `authentifiers.r` field (validated at `definition.js:756-772`).
4. The attacker immediately composes and broadcasts their own competing unit spending the *same* unspent output of `A`, using the same secret `"s3cr3t"` as the authentifier, but directing the outputs to their own address `C`.
5. Depending on network propagation and DAG/main-chain tie-breaking, the attacker's unit can be selected as the "good" (non-conflicting) spend, causing the legitimate claimant's unit to be marked as a doublespend loser and the funds to end up at `C` instead of `B`.
