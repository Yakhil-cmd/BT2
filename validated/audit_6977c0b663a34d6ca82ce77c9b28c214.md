### Title
Byte Holders Are Not Incentivized To Vote For A New OP List, Permanently Stalling The Emergency `op_list` Recovery Mechanism - (File: main_chain.js)

### Summary
Obyte's Order Provider (OP/witness) list can only be changed through balance-weighted `system_vote` messages that are tallied by a `system_vote_count` unit, and — for emergencies where the DAG is stuck because OPs stopped co-signing — through `applyEmergencyOpListChange`, which recounts even *unstable* votes once the chain has been stalled longer than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT`. Both paths depend entirely on unprivileged byte holders voluntarily posting fee-paying `system_vote`/`system_vote_count` units for a full slate of alternative OPs. Exactly as in the Notional report — where `sNOTE` stakers have no incentive to vote for `extractTokensForCollateralShortfall` because it directly reduces their own position — ordinary byte holders have no direct incentive to spend fees voting to replace unresponsive/censoring OPs, especially large holders who may be aligned with (or indifferent to) the incumbent OP set. If turnout never produces a full slate of `constants.COUNT_WITNESSES` distinct OP addresses, the recovery mechanism cannot complete and the network can remain stuck indefinitely.

### Finding Description
Changing the OP list requires:
1. Unprivileged addresses to post `system_vote` messages (`app: 'system_vote', payload: {subject: 'op_list', value: [...]}`), which are only validated/stored, not incentivized in any way [1](#0-0) .
2. Someone to post a `system_vote_count` unit (payable with `SYSTEM_VOTE_COUNT_FEE`) that actually triggers tallying [2](#0-1) [3](#0-2) .

Normal tallying (`countVotes`) only uses **stable** votes and widens the lookback window a year at a time until turnout is sufficient [4](#0-3) . If OPs stop signing units, the DAG can never stabilize, so this ordinary path can't run at all.

For that stuck scenario there is an emergency path: any node/user can send a `system_vote_count` unit; `writer.js` detects it and calls `main_chain.applyEmergencyOpListChange` before running normal MC update [5](#0-4) . `applyEmergencyOpListChange` only proceeds once the chain has been stalled past `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` since the last stable unit [6](#0-5) . It then calls `countVotes(..., is_emergency=1, ...)`, which folds in still-unstable `system_vote` messages (filtered by a minimum vote age, `EMERGENCY_COUNT_MIN_VOTE_AGE`) via `getUnstableVotes` [7](#0-6) , and tallies balance-weighted votes for OP candidates [8](#0-7) .

Crucially, this tally requires that `ops.length === constants.COUNT_WITNESSES` (a full slate of distinct addresses with the most votes); otherwise it throws `"wrong number of voted OPs"` [9](#0-8) . There is no protocol-level reward, bounty, or coordination mechanism compelling byte holders to actually cast (and keep current) votes for a full alternate OP slate. As in the sNOTE case, the actors who are economically positioned to trigger recovery (large byte holders, whose vote weight dominates the balance-weighted tally) may have little individual incentive to pay fees and organize a coordinated vote for a full replacement OP list — particularly if they hold balances precisely because they are comfortable with (or complicit in) the status quo, or simply because voting yields no direct return while confirmation of their own funds is stalled network-wide, not just for them individually (a collective-action/free-rider problem, mirrored one-to-one from the report's staker-apathy argument).

### Impact Explanation
If byte holders never coordinate enough weighted, and sufficiently varied, votes for a full new OP set, `applyEmergencyOpListChange`/`countVotes` cannot produce a valid recovery list (it throws rather than silently degrading), so the stalled OP set is never replaced. Since OP liveness/honesty is required to advance main-chain stability (`advanceMcStability`/witnessed-level calculations depend on the live OP list) [10](#0-9) , a captured or unresponsive OP set combined with voter apathy leaves the entire network unable to confirm new units — the same class of impact ("a network unable to confirm new units") called out as an accepted analog category, directly paralleling the Notional finding where staker apathy leaves the protocol insolvent because nobody executes the one governance action that would fix it.

### Likelihood Explanation
This requires an actual OP failure/censorship event to matter, and depends on real-world voter behavior (hard to guarantee empirically) — the same "hypothetical but valid" characterization the original judge gave the Notional issue. It is a plausible governance/incentive-design gap rather than a directly exploitable bug: no attacker input alone triggers it, but the code path (an unprivileged, fee-paying `system_vote_count` unit) is reachable by any wallet holder, and the mechanism's *only* safety valve for a stuck OP list structurally depends on volunteer, unrewarded, fee-costing voting by exactly the parties least incentivized to act quickly.

### Recommendation
Consider adding explicit incentives or fallback mechanisms decoupled from voluntary participation, for example:
- A bounty/rebate funded from network fees for addresses that successfully help assemble a valid emergency OP slate (paid once `applyEmergencyOpListChange` succeeds), refunding `SYSTEM_VOTE_COUNT_FEE` and rewarding voters.
- A graceful degradation path when `ops.length !== constants.COUNT_WITNESSES` (e.g., padding with the highest-voted addresses regardless of the exact count, or falling back to the previous unaffected OPs) rather than throwing and aborting the whole emergency recount.
- Periodic reminder/telemetry (e.g., wallet UI prompts) to encourage large holders to keep votes current well before a stall occurs, reducing reliance on reactive coordination during an actual outage.

### Proof of Concept
1. Assume the current 12 OPs (`constants.COUNT_WITNESSES`) become unresponsive/censoring, so no more units are authored by them and the DAG cannot advance past `first_unstable_mc_index` in `advanceMcStability`.
2. Time passes beyond `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` since the last stable unit.
3. In principle any wallet can post `system_vote` messages for a new OP slate and then a `system_vote_count` unit for `op_list`, triggering `applyEmergencyOpListChange` → `countVotes(..., is_emergency=1, ...)` [6](#0-5) .
4. In practice, because casting votes costs fees and yields no individual reward, and because those with the largest balance-weight (who dominate the tally) may lack incentive to act, `system_votes` for a full alternate slate of `COUNT_WITNESSES` distinct addresses are never assembled.
5. `countVotes` then either has too few voted OP addresses, causing `ops.length !== constants.COUNT_WITNESSES` and throwing `"wrong number of voted OPs"` [9](#0-8) , or the vote never reaches enough total weight to be posted at all — in both cases the OP list is never replaced and the network remains unable to produce new stable units, indefinitely.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
