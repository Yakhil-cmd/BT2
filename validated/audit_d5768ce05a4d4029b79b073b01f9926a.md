### Title
`X-Frame-Options: ALLOWALL` in `MergeStatusController#show` permits cross-origin framing of merge-queue controls, enabling clickjacking-driven `enqueue`/`dequeue` actions - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`MergeStatusController#show` unconditionally sets `response.headers['X-Frame-Options'] = 'ALLOWALL'`, removing all framing restrictions from the only Shipit page whose HTML contains one-click state-changing forms (`enqueue_merge_request_path` / `dequeue_merge_request_path`). Any origin — not just `github.com`, where this widget is intentionally meant to be embedded via the browser extension — can iframe this page and use standard clickjacking (overlay/opacity tricks) to induce a logged-in victim into submitting a real `enqueue`/`dequeue` request with valid session cookies and a legitimate CSRF token rendered inside the frame.

### Finding Description
Binding claimed: `X-Frame-Options prevents cross-origin framing == true` for state-carrying responses. Actual code: [1](#0-0) 
sets `ALLOWALL` on every `show` response regardless of `params[:referrer]` origin, so the equality is **false**: any third-party page can frame `GET /merge_status?...`.

The page renders merge-queue controls (`_merge_queue_button.html.erb`) whose forms POST to `enqueue`/`dequeue`: [2](#0-1) 

These actions are guarded by Rails CSRF (`protect_from_forgery with: :exception`, inherited from `ShipitController`) and require `current_user.logged_in?`, but neither of those defenses stops clickjacking: the victim's browser, already authenticated (`logged_in?` true from a prior visit), renders the real page and its real CSRF-protected form inside the attacker's iframe. The attacker overlays a decoy UI and lures the victim into clicking through to the real "Enqueue"/"Dequeue" button coordinates. Because the click lands on the genuine framed document, the browser submits the legitimate form with the victim's session cookie and the authenticity token that was rendered into that same document — CSRF protection is satisfied because the request is not forged, it is the real UI, just visually disguised.

`skip_authentication only: %i[check show]` only bypasses the login-wall render for `show`/`check`; `enqueue` and `dequeue` still require `current_user.logged_in?` via the standard `Shipit::Authentication` flow, but that authentication is exactly the victim's own valid session — which is what the attack rides on.

The `referrer` parameter (`ReferrerParser`) restricts which repository/stack is looked up, but does not restrict which *origin* is allowed to frame the response; `ALLOWALL` applies unconditionally, not scoped to `https://github.com`.

### Impact Explanation
A victim who is logged into Shipit and can be lured onto any attacker-controlled web page can be tricked into unknowingly enqueuing or dequeuing a pull request from the merge queue of a stack they have access to — i.e., an unauthorized merge-queue mutation performed under their identity without their intent. This maps to the "unauthorized deploy, rollback or merge" Critical impact category since it results in a merge-queue state change (enqueue/dequeue of a PR) that the victim did not knowingly authorize. The attack is repeatable per victim/session and scoped to whatever stacks the victim has legitimate access to via `stack`/`referrer` resolution; it does not cross tenant boundaries beyond the victim's own permissions (it cannot escalate privileges, only misuse the victim's existing ones).

### Likelihood Explanation
Preconditions: victim must have a live, `logged_in?` Shipit session and must be induced to visit an attacker page (standard clickjacking social-engineering setup, not requiring any secret or privileged role). No GitHub secrets, webhook signatures, or API tokens are needed — this is purely a UI-redress attack against a real, valid browser session, consistent with the specified attacker capabilities (no session, no privileged role required from the attacker; only the victim needs a session). Feasibility is high: `ALLOWALL` is a static, unconditional header with no origin check, so any page can iframe the endpoint. The main mitigating factor is that it requires user interaction (a disguised click) rather than being fully silent, and the resulting action (enqueue/dequeue) is a moderate-consequence, not directly RCE-level.

### Recommendation
Restrict the frame-ancestors permission to only the intended embedding surface. Options:
- Replace `X-Frame-Options: ALLOWALL` with a `Content-Security-Policy: frame-ancestors https://github.com` (and remove the legacy header, which cannot allowlist a single origin the way CSP can).
- Alternatively, keep `X-Frame-Options: SAMEORIGIN`/deny by default and only relax framing for the specific `check`/read-only status badge, never for the page containing the `enqueue`/`dequeue` forms; render those controls only when accessed outside an iframe, or require a fresh explicit confirmation step for `enqueue`/`dequeue` that cannot be clickjacked (e.g., a re-auth or double-confirmation UI pattern resistant to overlay attacks).

### Proof of Concept
```ruby
# test/controllers/shipit/merge_status_controller_test.rb (conceptual addition)
require 'test_helper'

module Shipit
  class MergeStatusControllerTest < ActionDispatch::IntegrationTest
    setup do
      login_as(shipit_users(:walrus))
    end

    test "#show sets ALLOWALL, permitting cross-origin framing" do
      get merge_status_path(referrer: "https://github.com/#{@stack.repository.owner}/#{@stack.repository.name}/pull/1")
      assert_equal 'ALLOWALL', response.headers['X-Frame-Options']
    end

    test "clickjacked enqueue succeeds with victim's legitimate session/CSRF token" do
      # Simulate: victim's browser renders the real /merge_status page inside an
      # attacker-controlled iframe (allowed because X-Frame-Options == 'ALLOWALL').
      get merge_status_path(referrer: pr_referrer, xhr: true)
      csrf_token = response.body[/name="authenticity_token" value="([^"]+)"/, 1]

      # Attacker overlay tricks victim into "clicking through" to the real enqueue button;
      # browser submits the genuine form with the genuine token/session (not forged).
      post enqueue_merge_request_path(stack_id: @stack.to_param, number: pr_number),
           params: { authenticity_token: csrf_token }
      assert_response :success
      assert @merge_request.reload.waiting? # state changed without deliberate victim intent
    end
  end
end
```
This demonstrates both sides of the equality: `response.headers['X-Frame-Options']` equals `'ALLOWALL'` (not a restrictive value), and a same-origin-rendered-but-attacker-framed `enqueue` request succeeds using the victim's own valid session and CSRF token.
