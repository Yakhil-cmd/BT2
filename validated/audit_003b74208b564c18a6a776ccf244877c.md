### Title
Attacker can permanently block liquidation of their own account by collateralizing a `no_seize`-flagged asset — the liquidation plan panics on the flagged leg instead of omitting it - ([File: contracts/controller/src/risk or liquidation planner])

### Summary
The liquidation path builds a pro-rata, multi-leg seizure plan over every collateral position of the target account and then validates each leg against the listing flags. Per the documented invariant (INV-HALT-02), a nonzero `no_seize` collateral leg aborts the **entire** liquidation rather than being skipped, and this applies even to collateral supplied *after* the flag was set. Because entry (`supply`) rejects only `paused`/`frozen` assets — not `no_seize` — an unprivileged borrower can deliberately supply a `no_seize`-flagged asset as collateral and make their own position un-liquidatable. This is an improper-input-validation flaw: the planner treats an unseizable leg as fatal input instead of omitting or handling it (zero-token legs are already omitted, showing a skip path exists). [1](#0-0) 

### Finding Description
Listing flags gate different legs independently: `entry` (supply/borrow) rejects `paused` and `frozen`; liquidation repayment rejects `paused`; **seizure rejects only `no_seize`**. The docs state explicitly:

> "Nonzero `no_seize` collateral can block the whole proportional liquidation, even if supplied after the flag is set." [2](#0-1) 

So the sequence is attacker-controlled end to end:

1. Governance flags an existing listed asset `no_seize` (a routine action when deprecating an asset's collateral role — it does not delist or pause it).
2. The attacker calls `controller.supply` with that asset on their (fresh or existing) account — accepted, since `no_seize` is not an entry gate.
3. The attacker calls `controller.borrow` against the now-boosted collateral.
4. When the position falls below HF 1, any liquidator calling `controller.liquidate(liquidator, account_id, payments, SeizeMode::Transfer)` hits the plan check: the flagged collateral leg is nonzero, the seizure-leg validation reverts, and the whole liquidation aborts. `clean_bad_debt` cannot help while the account's debt exceeds the dust threshold.

The `no_seize` flag exists to *gate* seizure of a specific asset, but because validation is applied to the batch as a whole rather than per-leg, one flagged leg poisons liquidation of every other collateral on the account.

### Impact Explanation
An account carrying a nonzero `no_seize` collateral position cannot be liquidated at all while it holds debt. The attacker obtains risk-free leverage: their position can go arbitrarily underwater with no liquidation recourse. When the position becomes insolvent, the debt must be socialized via `clean_bad_debt` / `recapitalize` — i.e., suppliers and the protocol absorb the loss — which is protocol insolvency / theft of user funds in the qualifying-impact taxonomy. Even before insolvency, the position's liquidation is permanently frozen (not merely delayed) for as long as the flagged collateral remains on the account.

### Likelihood Explanation
Requires only that *some* asset in the protocol be flagged `no_seize` at some point — a documented operational action for asset deprecation — and that an attacker supplies it before/during opening a borrow. No privileged access, no oracle manipulation, and no third-party cooperation is needed; `supply`, `borrow`, and the blocked `liquidate` are all unprivileged entrypoints. Any single unprivileged address can execute it. The fix cost is a one-line leg-skip in the seizure plan, consistent with the existing zero-leg omission.

### Recommendation
In the liquidation planner, filter out collateral legs whose listing is flagged `no_seize` *before* plan validation (the same way zero-amount legs are already omitted), and let the liquidation proceed against the seizable collateral. If the intent is that a `no_seize`-flagged asset must never count toward collateral again, additionally reject it at `supply`/position-enable time for collateral use, and make `update_account_threshold`/`borrow` risk evaluation exclude `no_seize` collateral so the attacker gains no LTV from it.

### Proof of Concept
1. Setup: market with assets A (borrowable) and B (collateral). Governance executes `set_spoke_asset_flags(spoke_id, B, paused=false, frozen=false, no_seize=true)` — e.g., deprecating B.
2. Attacker calls `controller.supply(attacker, account_id, [((hub, B), amountB)], None)` — succeeds, since entry does not check `no_seize`.
3. Attacker calls `controller.borrow(attacker, account_id, [((hub, A), amountA)], None)` up to B's LTV.
4. Price of B drops (or time passes) until HF < 1.
5. Liquidator calls `controller.liquidate(liquidator, account_id, payments, SeizeMode::Transfer)`. The pro-rata plan includes the B collateral leg; the `no_seize` seizure check reverts → `Error(Contract, ...)`. Repeat with any payments/SeizeMode combination; every liquidation attempt reverts while the B leg is nonzero.
6. `clean_bad_debt` reverts while gross debt exceeds the dust threshold. The position accrues debt to insolvency unliquidated, forcing eventual socialization onto suppliers.

Note: I verified the flag-gating behavior from the protocol's own invariant documentation (INV-HALT-02); I was not able to read the exact planner source lines enforcing the `no_seize` check within the available iterations, so the precise file/line in the controller's liquidation module should be confirmed during triage — but the documented behavior is explicit that the flagged leg aborts the whole plan.
