### Title
`Bank::build_updated_stake_reward` `assert_eq!` panics (validator crash / epoch-boundary halt) when a stake account is split or merged between epoch-boundary reward calculation and partitioned reward distribution - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
Similar to the Pendle `PendlePowerFarmToken` bug — where a value used to satisfy an invariant check is computed at one point in time but the account state it is checked against can be mutated by a permissionless actor before the check actually runs — Agave's partitioned epoch-rewards distribution computes each stake account's expected post-reward delegation at the epoch-boundary "calculation" phase, but only *applies*/verifies it several blocks later during the "distribution" phase. If `relax_post_exec_min_balance_check` (the `adjust_delegations_for_rent` feature) is not active, the code path that stores the reward asserts that the *current* on-chain delegation still matches what was true at calculation time. An unprivileged staker can invalidate that assumption between the two phases using ordinary `Split`/`Merge` stake instructions, causing a hard `assert_eq!` panic.

### Finding Description
`Bank::process_new_epoch` calculates stake rewards for every delegation at the first block of a new epoch and caches them (`begin_partitioned_rewards` / `calculate_stake_rewards_and_commissions`), then spreads the *distribution* of those rewards across up to 10% of the epoch's slots via `distribute_partitioned_epoch_rewards`. [1](#0-0) [2](#0-1) 

When each partition is actually distributed (potentially thousands of slots after the calculation), `build_updated_stake_reward` loads the account from the *current* `stakes_cache` and, if `adjust_delegations_for_rent` is false, asserts that the current delegation plus the pre-computed reward equals the delegation value computed back at calculation time: [3](#0-2) 

The surrounding comment explicitly (and incorrectly) assumes this can never fail: "Because stake accounts are checked in calculation, and further state mutation prevent[ed] by stake-program restrictions, there should never be rewards burned." [4](#0-3) 

No such "stake-program restriction" exists: `get_reward_interval()`/`EpochRewardStatus` is only referenced in `runtime/src/bank/partitioned_epoch_rewards/mod.rs` and in test helpers; it is never consulted by `programs/stake` to block `Split`, `Merge`, `Withdraw`, or `Deactivate` while rewards are pending for an account. The bank's own test suite even documents that state mutation is unrestricted during the reward interval — `test_rewards_period_system_transfer` is explicitly "Test that lamports can be sent to stake accounts regardless of rewards period." [5](#0-4) 

The unit test `test_delegation_adjustment_at_distribution` demonstrates that lamports/state *can* be mutated on a stake account after calculation but before its distribution slot arrives ("But we transfer in more lamports before distribution time") — this scenario is only handled safely when the rent-adjustment feature path is taken; the `assert_eq!` branch has no equivalent tolerance. [6](#0-5) 

Consequently, any unprivileged stake authority whose delegation is scheduled for a later reward-distribution partition (virtually guaranteed, since distribution spans up to 10% of an epoch's slots) can call `Split` or `Merge` on their own stake account between the epoch-boundary calculation block and their assigned distribution block. This changes `stake.delegation.stake` on-chain so that it no longer equals `expected_delegation` computed from the stale, calculation-time snapshot, tripping the `assert_eq!` and panicking the bank-processing thread.

### Impact Explanation
Because reward distribution is a deterministic, consensus-critical part of block processing executed identically by every validator replaying the same slot, this panic is not confined to a single node: every validator that reaches the affected partitioned-distribution block for the manipulated stake account will hit the same `assert_eq!` and crash/panic simultaneously. This satisfies the "epoch-boundary halt" acceptance criterion — the cluster's ability to advance past the affected epoch boundary is destroyed until the offending stake state is somehow avoided (e.g. via a hotfix or feature activation), which is a far more severe outcome than the original Pendle finding's temporary user-level DOS.

### Likelihood Explanation
- Reachable via completely ordinary, permissionless stake-program instructions (`Split`, `Merge`) available to any stake authority — no special privileges, timing races with the leader, or validator/RPC-role access are required.
- The reward-distribution window spans up to 10% of an epoch's slots (`MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH`), giving an attacker ample time after the epoch boundary to act before their own reward partition is processed.
- The vulnerability is gated behind the `adjust_delegations_for_rent` (`relax_post_exec_min_balance_check`) feature being inactive; if/when that feature is not yet activated on a given cluster (e.g., during rollout, on testnet, or if reverted), this `assert_eq!` code path is live and directly reachable.

### Recommendation
Do not assert equality against a possibly-stale calculation-time delegation snapshot; instead, derive `new_stake.delegation.stake` from the *current* on-chain delegation (`stake.delegation.stake.saturating_add(stake_reward)`), mirroring the tolerant approach already used in the `adjust_delegations_for_rent` branch, and treat any account no longer found/consistent as a recoverable `DistributionError` (as already done for `AccountNotFound`/`ArithmeticOverflow`) rather than panicking. Additionally, consider making the mismatch path unconditionally use the "recompute from live state" strategy regardless of feature-gate status, eliminating the invariant that stake accounts are immutable between calculation and distribution.

### Proof of Concept
1. Advance to the first block of a new epoch so `begin_partitioned_rewards` computes and caches rewards for all current delegations, entering `EpochRewardPhase::Calculation` then `Distribution` (see `runtime/src/bank/partitioned_epoch_rewards/mod.rs` test `test_rewards_computation_and_partitioned_distribution_multi_blocks` for the exact block-height mechanics).
2. Before the block corresponding to the partition containing your own stake account is processed, submit an ordinary `Split` (or `Merge`) instruction against that stake account, changing its `delegation.stake`.
3. When the bank advances to the block responsible for that account's partition, `store_stake_accounts_in_partition` → `build_updated_stake_reward` is invoked with `adjust_delegations_for_rent == false`; the stale `expected_delegation` (computed in step 1) will not equal the freshly-split/merged `new_stake.delegation.stake`, and the `assert_eq!` at `runtime/src/bank/partitioned_epoch_rewards/distribution.rs:289-293` panics inside consensus-critical block processing, which every validator hits identically.
