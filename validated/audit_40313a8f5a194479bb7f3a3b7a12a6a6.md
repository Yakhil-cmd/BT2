## Confirmed root cause

`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using one payload field, `repository_owner`: [1](#0-0) [2](#0-1) 

but every event handler resolves the actual `Repository`/`Stack` to act on using a *different* payload field, `repository.full_name`: [3](#0-2) [4](#0-3) 

Shipit explicitly supports one GitHub App (and one `webhook_secret`) per organization, keyed by organization name in `secrets.yml`: [5](#0-4) [6](#0-5) 

So for a multi-org Shipit install, the binding the app relies on is: **"organization whose secret verified the HMAC" == "repository whose stack the payload will mutate."** Nothing enforces that equality — `repository_owner` (`repository.owner.login`, or `organization.login`) and `repository.full_name`'s owner segment are independent JSON fields inside the same signed body, and the signature only proves "whoever holds the secret for `repository_owner` produced these bytes," not "the bytes are only about `repository_owner`'s repos." An org administrator who legitimately controls their own GitHub App's `webhook_secret` (config entry for e.g. `OrgA`) can therefore craft and correctly sign a payload where `repository.owner.login: "OrgA"` (selects the secret they know) while `repository.full_name: "OrgB/victim-repo"` (the actual object acted upon), because they compute the HMAC themselves over the whole raw body with their own known secret.

This lets an authenticated-for-their-own-org, unprivileged party push events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against a stack belonging to a completely different organization configured in the same Shipit instance, e.g. triggering `GithubSyncJob`/`sync_github` on `OrgB`'s stacks, forging commit `status`, or manipulating `check_suite`/`pull_request` state used by the merge queue — all cross-organization, cross-repository writes without ever needing `OrgB`'s credentials.

### Title
Webhook signature verification key (`repository.owner.login`) is decoupled from the repository acted upon (`repository.full_name`), allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret via `repository_owner` (`repository.owner.login` or `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` via the independent `repository.full_name` field. In a multi-organization deployment (`Shipit.github(organization:)`), a party who legitimately controls the webhook secret for their own configured organization can sign a payload whose `repository.owner.login` matches their org (so verification passes) while `repository.full_name` names a stack belonging to a different, unrelated organization configured on the same instance.

### Finding Description
- Signature check: [1](#0-0)  uses `repository_owner` defined at [2](#0-1)  purely to choose which `GitHubApp`/secret (`Shipit.github(organization: repository_owner)`) validates `X-Hub-Signature`.
- Action taken: every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, `MembershipHandler`, etc.) inherits `Handler#stacks`/`repository_name`, which reads `payload.dig('repository', 'full_name')` — [3](#0-2)  — and resolves the actual `Repository` row via `Repository.from_github_repo_name` [4](#0-3) .
- Since `repository.owner.login`/`organization.login` and `repository.full_name` are two separate keys in the same JSON body, an attacker who is a legitimate administrator of one configured organization's GitHub App (and thus knows that organization's `webhook_secret`) can compute a correct HMAC over an entire payload of their choosing — including one whose `repository.full_name` points at a completely different, victim organization's stack.
- Multi-organization configuration is a documented, supported mode: [6](#0-5) , resolved by [5](#0-4) .

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated == repository that is written." An org that is any one of Shipit's configured tenants can forge `push` (triggering `GithubSyncJob`), `status`, `check_suite`, and `pull_request` events against another tenant's stacks, corrupting commit/CI/deploy state and merge-queue eligibility for repositories they do not own or have any GitHub permission on — an unauthorized cross-repository write, without needing a Shipit session, API token, or the victim org's GitHub credentials.

### Likelihood Explanation
Requires a Shipit deployment configured with more than one GitHub organization (the documented multi-org mode) where the attacker legitimately administers one of those orgs' GitHub Apps/webhook secret — a low bar within that specific configuration, and the webhook endpoint (`/github/webhooks`) is unauthenticated and reachable by anyone who can send it a correctly signed request.

### Recommendation
After verifying the signature with the secret selected by `repository_owner`, re-validate that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` (or the `organization.login`) before dispatching to handlers; reject mismatches with `422`.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org schema).
2. As the administrator of `OrgA`'s GitHub App, craft a `push` payload body: `{"ref": "refs/heads/master", "after": "<sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` — computable by the attacker since they own `OrgA`'s secret.
4. POST to the shared `/github/webhooks` endpoint with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` as `"OrgA"`, fetches `OrgA`'s config, and the signature verifies successfully.
5. `PushHandler#process` reads `repository.full_name` = `"OrgB/victim-repo"` and calls `sync_github` on `OrgB`'s stacks, an org the attacker has no legitimate access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
