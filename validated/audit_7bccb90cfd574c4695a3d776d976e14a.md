### Title
Webhook signature verification checks the payload's `organization`/`repository.owner` field while every event handler routes on `repository.full_name` — breaking the org-authenticated vs repo-written binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC against using `repository_owner`, a value read directly out of the unverified JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` looks up the target `Stack`/`Repository` using a *different* field from the same body: `repository.full_name`. Nothing ties these two fields together, so the equality "organization whose secret authenticated the request == organization that owns the repository actually acted on" is never enforced.

### Finding Description
`verify_signature` computes the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

It fetches the correct `GitHubApp` (and thus `webhook_secret`) for that organization via `Shipit.github(organization: repository_owner)`, which in a multi-tenant config resolves per-organization secrets from `github_app_config`: [3](#0-2) 

Once the signature is accepted, the event is dispatched to handlers that resolve the target `Stack` from an entirely separate, also-unverified field, `repository.full_name`: [4](#0-3) 

For example `PushHandler` triggers `stack.sync_github` for whatever stacks match that `full_name`/branch, and `MembershipHandler` creates/joins `Team`/`User` records — the same teams later used for `Shipit.github_teams` authorization — keyed off `params.organization.login` and `params.team`, again taken straight from the body with no cross-check against the signing organization: [5](#0-4) [6](#0-5) 

Because `repository.owner.login`/`organization.login` (used for auth) and `repository.full_name` (used for routing) are independent, attacker-controlled JSON keys inside the same signed body, an attacker who legitimately controls the webhook secret for **one** configured organization (org A) can produce a validly-signed payload where the `organization`/`repository.owner` block still says "org A" (so `verify_signature` passes using org A's secret) while `repository.full_name` is set to `"orgB/some-other-repo"`. The request is accepted and dispatched to the handler for org B's stack, even though it was never signed with org B's secret.

Before the analog: signature check is `verify(secret_for(X), body)`, action target is `stack_for(Y)`, with implicitly `X == Y` assumed but never enforced. After: attacker sets `X = orgA` (their own org, whose secret they hold) and `Y = orgB` (a target they don't control) in the same body — `X != Y` and the request is still processed.

### Impact Explanation
This breaks the required binding "an organization that authenticated versus the repository that is written." In a multi-org/multi-tenant Shipit deployment (the `github_app_config`/per-organization secrets path in `lib/shipit.rb`), any org configured with its own GitHub App and webhook secret can forge events attributed to any *other* configured organization's repositories/stacks:
- `push` events can trigger `GithubSyncJob`/`sync_github` against another organization's stack.
- `membership` events can create/modify `Team` records tied to another organization's `organization` field and add arbitrary users to teams, which feeds directly into `Shipit.github_teams` authorization (`app/models/shipit/team.rb`, `lib/shipit.rb` `github_teams`), constituting escalation into `Shipit.github_teams` authorization.
- `status`/`check_suite` events can inject/alter commit statuses for commits under a different tenant's stack, potentially unblocking deploy gating checks for repositories the attacker does not own.

This matches the High-impact category "escalation into `Shipit.github_teams` authorization" explicitly called out in scope.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately control one organization's webhook secret in a multi-tenant Shipit instance (i.e., is a valid App owner/admin for org A but not org B) — no repository write access, API token, or session compromise on the *target* org is needed. This is a realistic operator boundary in shared Shipit deployments serving multiple GitHub organizations, since the engine is explicitly designed to support the multi-org `secrets.github` schema keyed by organization (`github_app_config`, `github_organizations`).

### Recommendation
In `WebhooksController#verify_signature`, after determining the signing organization, cross-validate it against the organization implied by `repository.full_name` (or `repository.owner.login`) that the handler will actually act on, rejecting the request if they diverge. Alternatively, have `Handler#repository_name`/`stacks` derive the repository strictly from the same `repository_owner` value validated during signature verification rather than re-reading `repository.full_name` independently.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing both `orga` and `orgb`, each with its own `webhook_secret`.
2. As an authorized admin of `orga`'s GitHub App, compute a valid `X-Hub-Signature` HMAC over a crafted JSON body using `orga`'s `webhook_secret`:
   ```json
   {
     "organization": { "login": "orga" },
     "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
3. POST to `/github/webhooks` with `X-Github-Event: push` and the computed signature.
4. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `orga`'s secret, and the signature validates.
5. `PushHandler#process` looks up stacks via `repository_name` = `payload.dig('repository','full_name')` = `"orgb/target-repo"`, and triggers `sync_github`/enqueues `GithubSyncJob` for `orgb`'s stack — despite the request never being signed with `orgb`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
