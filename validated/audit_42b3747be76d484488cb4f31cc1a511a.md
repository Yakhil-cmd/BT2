### Title
Webhook signature check authenticates the wrong GitHub organization, allowing cross-repository forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a webhook against using one payload field (`repository.owner.login` / `organization.login`), while every webhook `Handler` decides *which repository/stack/commit to mutate* using an entirely different, unrelated payload field (`repository.full_name`, or in the case of `StatusHandler`, a bare `sha` lookup across all commits). Because these two lookups are never cross-checked, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization has no `webhook_secret` configured, an attacker can satisfy signature verification "as" an org with no configured secret while making the actual write target (`repository.full_name` / commit `sha`) point at a totally different, unrelated, properly-secured organization's stack.

### Finding Description
The equality this breaks is:

`organization whose webhook_secret authenticates the request == organization/repository whose Shipit records are written`

Before the fix these are never checked to be the same:

- `WebhooksController#verify_signature` selects the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` bypasses HMAC verification entirely if that organization has no `webhook_secret` configured: [3](#0-2) 

A blank `webhook_secret` is an explicitly documented, supported configuration value (shown as `nil`/commented-out in the sample configs): [4](#0-3) 

- Once past `verify_signature`, `WebhooksController#create` dispatches the *entire raw payload* to handlers: [5](#0-4) 

- The base `Handler` resolves the affected `Stack`/`Repository` from `payload.dig('repository', 'full_name')` — a field that is completely independent of the `repository_owner` used for authentication: [6](#0-5) 

- `PushHandler` then triggers a GitHub sync for whatever stack matches that repository/branch: [7](#0-6) 

- Worse, `StatusHandler` doesn't even use `repository.full_name` — it looks up commits **globally by SHA**, with no repository scoping at all, and writes a GitHub commit status onto them: [8](#0-7) 

**Before the attacker's request:** a POST to `/webhooks` is only accepted if its `X-Hub-Signature` matches the webhook secret of the organization named by `repository.owner.login`/`organization.login` in the body.
**After (attack path):** the attacker crafts a JSON body where `repository.owner.login` = `OrgWithNoSecret` (any configured org that has no `webhook_secret`, satisfying `return true unless webhook_secret`), but `repository.full_name` = `OrgWithSecret/target-repo` (a real, unrelated, properly-secured org's tracked repository), or for `status` events simply supplies the `sha` of a commit belonging to any tracked stack. No signature at all is required in this scenario. The handler then acts on the targeted stack/commit as if the request had been legitimately authenticated by that stack's real organization.

### Impact Explanation
This is a cross-repository/cross-organization write achieved without possessing the target organization's `webhook_secret`, `GITHUB_TOKEN`, an `ApiClient` token, or any authenticated session — it only requires that at least one GitHub App organization configured on the instance has no `webhook_secret` set (an explicitly supported, documented configuration). Concrete consequences:
- `push` events can force `sync_github` on any tracked stack/branch belonging to a different, properly-secured organization.
- `status` events can forge a passing/failing CI status (`commit.create_status_from_github!`) on **any commit tracked by Shipit, in any stack**, since the lookup is a global `Commit.where(sha:)` with no repository scoping. Since CI status is one of the safety gates Shipit consults before allowing/blocking a deploy, this can be used to make a commit appear deployable when it should not be, contributing to an unauthorized deploy of unreviewed code.
- `pull_request`/`membership`/`check_suite` handlers are similarly reachable for arbitrary tracked repositories using the mismatched-organization trick.

This satisfies the "cross-repository writes" / "unauthorized deploy" Critical impact criteria in scope, since the attacker never needed the target repository's own credentials.

### Likelihood Explanation
Likelihood is moderate: it requires a Shipit deployment that manages more than one GitHub organization and where at least one of them is left without a `webhook_secret` — a state the project's own sample configs show as a normal/valid choice (e.g., during initial setup, or for GitHub Apps relying on installation-scoped auth without webhook signing). Any external, unauthenticated party who can reach the `/webhooks` endpoint (which is a public, unauthenticated Rails route by design, per `Authentication`/`skip_authentication` patterns elsewhere) can exploit this without prior access. Discovering which org lacks a secret is trivial (the request will either be silently 422'd for orgs with secrets or accepted for the one without).

### Recommendation
Bind the field used for authentication to the field used for mutation:
- After verifying the signature for `repository_owner`, require that every field the handler subsequently trusts (`repository.full_name`'s owner, or any repository resolved from `sha`) belongs to that same `repository_owner`/organization — reject or scope queries accordingly (e.g., `StatusHandler` should scope `Commit` lookups to stacks whose repository owner matches `repository_owner`, and `Handler#repository_name`'s owner should equal `repository_owner`).
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in production; instead, treat a missing `webhook_secret` for a configured organization as a hard misconfiguration (raise/log and reject) rather than an implicit auth bypass.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `config/secrets.yml`: `OrgA` with `webhook_secret: nil` and `OrgB` with a real `webhook_secret`, both having repos/stacks tracked in Shipit.
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any garbage value), body:
```json
{
  "organization": { "login": "OrgA" },
  "sha": "<sha of a commit belonging to a stack under OrgB>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged CI status onto OrgB's commit — without ever presenting OrgB's `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
