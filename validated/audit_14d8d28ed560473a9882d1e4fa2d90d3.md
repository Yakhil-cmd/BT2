### Title
Chunk apply panics (chain stall) when a single stale `GlobalContractDistribution` delayed receipt cannot resolve to a shard after resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally calls `.unwrap()` on `Receipt::receiver_shard_id`, which can return `Err` for a `GlobalContractDistribution` receipt whose stale `target_shard` cannot be mapped into the current shard layout. Because this function is invoked while draining the persistent delayed-receipts queue during every chunk apply, a single such receipt stuck in the queue causes the runtime to panic on every subsequent apply attempt of that shard, permanently halting chunk production/state transition for the shard — directly analogous to the reported bug class where one misbehaving asset/item in a shared collection makes the whole system permanently unusable.

### Finding Description
`receiver_shard_id` in `core/primitives/src/receipt.rs` resolves the shard a receipt targets. For ordinary receipts it maps `receiver_id` via `account_id_to_shard_id`, but for `ReceiptEnum::GlobalContractDistribution` it uses the receipt's `target_shard`, and if that shard no longer exists in the current layout it falls back to `shard_layout.resolve_to_current_shard(target_shard)`. If that resolution fails (e.g., after multiple/chained resharding events where the split-history chain can't map the old shard forward), the function returns `Err(EpochError::ShardingError(...))`. [1](#0-0) 

That `Result` is consumed unconditionally with `.unwrap()` in `DelayedReceiptQueueWrapper::receipt_filter_fn`, which is called from `pop` and `peek_iter` every time the delayed-receipt queue is drained during chunk apply: [2](#0-1) 

The delayed-receipt queue is a persistent, shared, in-state queue processed on every `apply()` call for the shard (`process_delayed_receipts` in `runtime/runtime/src/lib.rs`), so once a single stale `GlobalContractDistribution` receipt lands at the head of (or anywhere reachable via) this queue with an unresolvable `target_shard`, every future call to drain/peek the queue re-triggers the same panic — there is no way to skip, requeue, or purge the offending item without governance-less code changes, mirroring the original report's core failure mode: one bad item in a shared collection (basket of collateral vs. delayed-receipt queue) that a privileged mechanism cannot safely remove because the removal/iteration path itself depends on the faulty item's behavior. [3](#0-2) 

The codebase itself contains a regression test explicitly built to catch this exact scenario — `test_stale_global_contract_distribution_after_double_resharding` — which forces two sequential shard splits while a `GlobalContractDistribution` receipt sits in the delayed queue, then asserts the chain does not stall, with an explicit comment: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations." [4](#0-3) 

The test also documents that the fix only reliably works for V3/dynamic shard layouts, and that static resharding layouts don't retain a full split history, implying older layouts remain exposed to the same panic class: [5](#0-4) 

### Impact Explanation
A panic inside `Runtime::apply` for a given shard, triggered from ordinary transaction/receipt processing (not a malicious validator/peer action — it results purely from the natural resharding lifecycle interacting with a global-contract deploy that any account can submit), causes the node to crash or repeatedly fail chunk application for that shard. Because the offending receipt stays in the persistent delayed queue and gets re-encountered on every apply, this is not transient: it is a chain-stall / permanent-DoS condition for the affected shard until a protocol/state fix is deployed, matching the "impacts become permanent" severity described in the analog report (in that case: whole RToken unusable; here: whole shard's chunk processing/state transition unusable).

### Likelihood Explanation
This requires (1) at least one (in the discovered test, two) resharding events to occur while (2) a `GlobalContractDistribution` receipt targeting the shard being split sits in the delayed-receipts queue long enough to become "doubly stale." Any regular account can trigger the necessary precondition by calling `DeployGlobalContract` and by submitting enough load to push the resulting distribution receipt into the delayed queue during a period spanning multiple dynamic-resharding transitions — no special privileges are needed. Given dynamic resharding is an in-protocol feature that can occur automatically based on shard load thresholds, the precondition is reachable through normal network operation, though it depends on resharding cadence and timing, making likelihood moderate rather than trivially triggerable on demand.

### Recommendation
- Replace the `.unwrap()` calls in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:875-876`) with defensive handling: if `receiver_shard_id` fails to resolve, do not panic — either treat the receipt as belonging to a "sink"/error state that can be safely re-delayed or logged and skipped without halting apply, or extend `resolve_to_current_shard` (`core/primitives/src/shard_layout/{mod.rs,v3.rs}`) to correctly walk an arbitrarily deep split-history chain so that any historical `target_shard`, regardless of how many resharding generations have elapsed, can always be resolved.
- Ensure the fix is validated for chains transitioning from static (pre-V3) layouts, since the existing test explicitly scopes the fix to `ProtocolFeature::DynamicResharding`-enabled V3 layouts and notes static layouts don't retain full split history.
- Add/keep the existing `test_stale_global_contract_distribution_after_double_resharding` test enabled in CI (it is currently gated off for the `protocol_feature_spice` build) to guard against regressions across further layout/versioning changes.

### Proof of Concept
The repository's own test-loop test reproduces the exact failure sequence:
1. Deploy a contract on an account in shard S_A, then deploy it as a **global contract**, producing a `GlobalContractDistribution` receipt with `target_shard = S_A`.
2. Saturate S_A's compute budget every block so the distribution receipt is pushed into, and remains in, the persistent delayed-receipts queue.
3. Force two sequential dynamic-resharding splits, the first of which splits S_A itself, so the receipt's `target_shard` becomes stale relative to two shard-layout generations.
4. Stop saturating and let the delayed queue drain; the test asserts the chain height keeps advancing (`head_height >= drain_end`) — if the underlying `receiver_shard_id`/`resolve_to_current_shard` resolution is incomplete, `receipt_filter_fn`'s `.unwrap()` panics while draining the queue, and the chain stalls. [6](#0-5)

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    {

        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(

                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);

        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();

            both_splits_done = true;
            break;
        }

    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails

        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
