### Title
XCM `ERC20Transactor` credits/debits the fixed requested `amount` into `AssetsInHolding` based solely on the ERC20 contract's boolean success return, without verifying the actual balance delta — ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
Asset Hub Westend wires an `ERC20Transactor` into its XCM `AssetTransactors` tuple, allowing any XCM program (including one triggered by a plain signed user via `pallet_xcm::execute`/reserve/local transfers) to reference an arbitrary `pallet-revive` smart-contract token via an `AccountKey20` location [1](#0-0) . Both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke the token's Solidity `transfer()` and trust only the ABI-decoded `bool` return value, crediting/debiting the exact `amount` requested by the XCM instruction into the `AssetsInHolding` register — never reading the ERC20's own `balanceOf` before/after the call [2](#0-1) [3](#0-2) . This is the exact bug class from the report: assuming "amount requested" equals "amount actually transferred" for a token whose `transfer()` can apply a fee/deflation, rather than measuring the real balance delta.

### Finding Description
`pallet-revive` on Asset Hub Westend permits any signed account to permissionlessly `instantiate`/`upload_code` (`UploadOrigin = EnsureSigned`, `InstantiateOrigin = EnsureSigned`) [4](#0-3) . Any address deployed this way whose 20-byte address is embedded in an `AccountKey20` XCM location junction is matched by `assets_common::ERC20Matcher` and routed to `ERC20Transactor`, part of the runtime's live `AssetTransactor` [1](#0-0) . An attacker with no privileges can therefore deploy a custom "ERC20" contract whose `transfer()` function:
- returns `true` (success) while, internally, moving less than `value` to the recipient and burning/redirecting the difference (a classic fee-on-transfer/deflationary pattern), or
- returns `true` while moving *more* to the recipient than debited from the sender.

`withdraw_asset_with_surplus` calls `transfer(checking_address, amount)`; on `is_success == true` it unconditionally constructs `AssetsInHolding` with `Erc20Credit(amount)` — the requested amount — never checking `checking_address`'s real `balanceOf` delta [5](#0-4) . Symmetrically, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` and on `Ok(true)` simply returns success without checking that the beneficiary actually received `amount` [6](#0-5) . The `Erc20Credit` imbalance type itself is explicitly documented as *not* runtime-enforced: "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [7](#0-6) , but that assumption only holds if the transactor actually re-derives the credited amount from a measured `balanceOf` delta, which it does not do — it uses the caller-supplied `amount` from the XCM instruction, not a value derived from the contract state.

This is a direct structural analog of the reported issue: `Allo._fundPool()` trusted `transferFrom`'s nominal `amount` instead of measuring `balanceOf(this)` before/after for fee-on-transfer ERC20s. Here, the XCM executor's on-chain accounting register (`AssetsInHolding`) is populated from the nominal instruction `amount`, not from a measured delta of the actual `pallet-revive` contract ledger.

### Impact Explanation
`AssetsInHolding` is the XCM executor's ledger of "what is actually available to move" during instruction execution, and feeds subsequent `DepositAsset`/`TransferAsset`/`ClaimAsset` instructions and cross-chain reserve/teleport bookkeeping. If the credited amount into holding does not match what the checking account (or beneficiary) actually received, XCM program logic downstream (e.g., a subsequent `DepositAsset` in the same message, or an `AssetTrap`/`ClaimAsset` sequence if a later step fails) operates on a phantom balance that is not backed 1:1 by the ERC20 contract's real ledger. This can produce inconsistent/incorrect settlement (over- or under-crediting recipients relative to what the contract ledger reflects), and in the reverse-fee case (deposit crediting more to the holding register than what was actually removed from the checking account, or a token that mints extra on transfer to itself) could allow an attacker-controlled contract to make the executor believe more value is "in holding" than what is truly backed, undermining the invariant that on-chain XCM asset accounting is faithfully backed by the underlying ledger. Because the attacker fully controls the contract's `transfer()` implementation (it's their own permissionlessly deployed contract), they can freely choose the discrepancy factor to attempt exploitation via crafted multi-instruction XCM programs (e.g., `WithdrawAsset` + `DepositAsset` combinations, or trap/claim). Whether this can be escalated all the way to net cross-account theft depends on exact downstream instruction sequencing (e.g., whether the second leg's contract call would revert due to real insufficient balance), which requires empirical confirmation via an integration test — this is not proven in this analysis and is flagged as unverified.

### Likelihood Explanation
Likelihood is Medium-to-High for reachability: any signed account can deploy the fee-on-transfer contract and execute XCM referencing it via `pallet_xcm::execute` or transfer extrinsics on Asset Hub Westend — no privileged role, governance, or validator collusion needed. The `ERC20Transactor` is live in production XCM config [8](#0-7) . What remains uncertain (and materially affects severity) is whether a concrete XCM instruction sequence can be constructed that converts the phantom-credit into net value extraction rather than simply causing the subsequent leg to revert (since the ERC20's own internal ledger — enforced by the attacker's own contract code — ultimately still gates any real `transfer()` call). I was not able to run a concrete Rust/XCM integration reproduction in this environment to confirm actual loss versus benign failure, so I can attest to the missing-check root cause and its reachability, but not to a confirmed measurable-loss end-to-end exploit.

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual `balanceOf` of the checking/beneficiary account before and after the `transfer()` call (via a `balanceOf` `bare_call` or reading storage directly if colocated in the same runtime), and credit/debit `AssetsInHolding` using the measured delta rather than the nominal `amount`, mirroring the report's core recommendation of before/after balance accounting. Alternatively/additionally, explicitly document and enforce that only trusted (non fee-on-transfer, 1:1 conforming) ERC20 contracts may be represented in `AssetsInHolding`, and reject asset ids failing such a conformance check before allowing them into the `AssetTransactors` tuple's matched set.

- Confirmed via source inspection that `ERC20Transactor` is wired into Asset Hub Westend's `AssetTransactors` [8](#0-7)  and that `pallet-revive` deployment is permissionless (`EnsureSigned`) [9](#0-8) , establishing a real, unprivileged user entry point (deploy contract → reference it in XCM via `pallet_xcm::execute` or transfer extrinsics).
- Confirmed via source inspection that both the withdraw and deposit paths trust the boolean `transfer()` return value and use the nominal instruction `amount` to populate `AssetsInHolding`, with no `balanceOf` before/after check [10](#0-9) [11](#0-10) .
- I did NOT execute a Rust/FRAME/XCM integration test deploying a custom fee-on-transfer Solidity/ink! contract and running a crafted XCM program (e.g., via the existing `withdraw_and_deposit_erc20s` test scaffolding at `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`) to empirically demonstrate net value extraction or ledger desynchronization. This is required to move from "missing check, plausible impact" to a demonstrated, measurable-loss finding, and is explicitly flagged as not yet done. Given the uncertainty about whether the downstream leg simply reverts (bounding the impact to DoS/failed transfer) versus enabling actual desynchronized crediting, I present this as a supported Medium-severity analog pending that concrete reproduction, consistent with instruction 6's requirement for file:line evidence plus a minimal reproduction — the file:line evidence is provided, the reproduction is outstanding.
