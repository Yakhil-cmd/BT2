### Title
Missing verification that a peer-supplied shared-address definition actually requires cooperation before it is accepted as a "shared" (multi-owner) address - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` accepts an unsolicited `new_shared_address` device message from any paired correspondent and, after only syntactic checks (chash match, signer/address consistency, `Definition.validateDefinition`), stores the attacker-supplied spending definition as a local `shared_addresses` record and notifies other correspondents that a new shared/joint address exists. Nothing in this path checks that the definition actually enforces cooperation between the claimed cosigners (e.g. that the local user's address is behind an `and`/`r of set` branch rather than an `or` branch that a single other party can already satisfy).

### Finding Description
`handleNewSharedAddress` [1](#0-0)  is invoked directly on receipt of a `new_shared_address` message from any paired device. It:
1. Verifies `body.address === chash(body.definition)`.
2. Extracts every `["address", X]` leaf from the definition via `extractAddressPathsFromDefinition` [2](#0-1)  and checks that the `signers` map the caller sent matches those leaves 1:1.
3. Runs `Definition.validateDefinition` to make sure the definition is a syntactically valid spending condition.
4. Calls `addNewSharedAddress`, which stores the shared address and its signing paths and immediately forwards it to the local user's own cosigners as a legitimate joint address [3](#0-2) .

At no point is there a check on the *shape* of the definition — i.e., that the addresses being registered as "cosigners" are actually required to jointly authorize spending. A malicious correspondent can submit, for example, `["or", [["address", attacker_address], ["address", victim_address]]]` together with `signers` that legitimately map the victim's real address to the `address` leaf. All of the existing checks pass because the victim's address genuinely appears in the definition at the claimed signing path — the code never verifies that the leaf is behind a conjunction requiring the victim's cooperation. This lets an attacker construct and register a "shared address" that displays as a joint address involving the victim, but which the attacker alone can already spend from, since an `or` branch grants full authority to the attacker's key alone.

This mirrors the underlying bug class in the referenced advisory: the item's "ownership"/spending-authority structure can be redefined and asserted by a caller who should not have unilateral control over such (co-)ownership metadata, because the code omits a permission/consistency check that the new configuration doesn't already grant unilateral control to the requester.

### Impact Explanation
If the victim treats the resulting `shared_addresses` entry as a genuine two-party address (as the UI/notification flow implies) and directs funds to it expecting the attacker's cooperation to be required for any spend, the attacker can immediately and unilaterally move those funds via the `or` branch, resulting in unauthorized spending / theft of funds sent to what was believed to be a jointly-controlled address. This satisfies the "concrete unauthorized spending" bar.

### Likelihood Explanation
Any correspondent device that is paired with the victim (a normal, low-privilege relationship in ocore, comparable to "Item/Read" access in the original advisory) can trigger this by sending a single `new_shared_address` message; no witnessing, stability, or unit-posting requirements are involved, and the message is processed automatically by `handleNewSharedAddress` without additional confirmation of the definition's cooperative structure.

### Recommendation
When accepting a peer-initiated `new_shared_address`, validate the *semantic* structure of the definition, not merely its syntax and chash: ensure every locally-owned/claimed cosigner address is required (e.g., is under an `and`/`r of set` with r>1 or `weighted and` requiring a sufficient weight) rather than reachable through an `or` alone or in an `r of set` where r is small enough to be satisfied without the local party. Alternatively, restrict `handleNewSharedAddress` to definitions that were previously agreed via the existing template-approval flow (`createNewSharedAddressByTemplate` / `approvePendingSharedAddress`) instead of accepting arbitrary complete definitions from an unsolicited device message, and surface a clear warning/require explicit user confirmation showing exactly which key(s) can unilaterally spend before persisting the address as "shared".

### Proof of Concept
1. Attacker pairs with victim's device (a normal wallet correspondent relationship).
2. Attacker sends a `new_shared_address` message: `{address: chash(D), definition: D, signers: {...}}` where `D = ["or", [["address", attacker_addr], ["address", victim_addr]]]`, and `signers` correctly maps the `address` leaf at the victim's path to `victim_addr`.
3. `handleNewSharedAddress` passes all structural checks (address matches chash, signer/leaf mapping matches, `validateDefinition` succeeds) and stores the address via `addNewSharedAddress`, then forwards it to the victim's other cosigners as a legitimate joint address.
4. Victim (or their cosigners), believing the address requires both parties, sends funds to it.
5. Attacker spends the funds unilaterally using the `["address", attacker_addr]` branch of the `or`, without the victim's cooperation or knowledge.

function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
