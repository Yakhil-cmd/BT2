Based on the code reviewed, there is a concrete analog of the reported "binding" bug class: the organization whose secret authenticates a webhook is never checked against the repository/commit that the webhook handler actually mutates.

### Title
Webhook signature is verified against the organization named in the payload, but `StatusHandler` writes to any commit matched by SHA regardless of organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the attacker-supplied JSON body, then dispatches the *same* body to the registered handler for the event type. `StatusHandler`, one of those handlers, updates commit statuses by looking up `Commit.where(sha: params.sha)` with no scoping to the organization/repository whose secret was used to authenticate the request.

### Finding Description
`verify_signature` resolves the signing organization purely from payload data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a per-organization `GithubApp` configuration, each of which can carry its own independent `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature passes for that organization, the entire raw JSON body is handed to the matching event handler: [5](#0-4) 

`StatusHandler#process` then looks up commits purely by `sha`, with no filter tying the lookup back to the `repository_owner`/organization that was used to select the signing secret: [6](#0-5) 

The binding that should hold is: *organization whose secret authenticated the request == organization owning the repository/commit being mutated*. Because the JSON body is fully attacker-controlled (it is not a real GitHub-signed delivery, only forged with a known secret), an attacker who knows (or controls) the `webhook_secret` for **any one** organization configured on the Shipit instance (e.g., their own low-privilege org tracked on the same shared instance) can set `repository.owner.login` in the payload to that organization (so the signature check passes) while setting `sha` to a commit SHA that actually belongs to a completely different, unrelated repository/organization also tracked by the same instance. The handler will happily create/overwrite a `Status` on that commit, since `Commit.where(sha:)` is a global, unscoped lookup.

### Impact Explanation
Commit statuses drive Shipit's deployability signal (green/red CI gating shown to operators and used by `release_status?`/`release_status_context` on the stack). Forging a passing status on an arbitrary tracked repository's commit lets an attacker who only knows one tenant organization's webhook secret make an unrelated organization's commit appear CI-green, which can lead an authorized operator to trigger an **unauthorized deploy** of a commit whose real CI status is failing/unknown. This is a cross-repository write of trust-bearing state (commit status) across an organizational boundary that the signature check was supposed to enforce, matching the "unauthorized deploy" / "cross-repository writes" High/Critical impact category.

### Likelihood Explanation
Exploitation requires only knowledge of one organization's `webhook_secret` on a multi-tenant Shipit deployment (any organization that has registered a GitHub App/webhook pointing at the shared instance) plus the target commit's SHA (public information on GitHub). No Shipit session, `ApiClient` token, or repository write access is needed — only the ability to POST to `/webhooks` with a validly-signed-for-org-A body whose repository/commit fields reference org B. This is a plausible configuration for any installation supporting more than one organization/repository, which the engine explicitly supports via `Shipit.github(organization:)`.

### Recommendation
After resolving the signing organization in `verify_signature`, thread that organization through to the handler dispatch and have each handler verify that the resource it operates on (repository, and by extension the commit's stack/repository) actually belongs to the authenticated organization before making any writes — e.g., scope `StatusHandler`'s `Commit` lookup through `Repository`/`Stack` records owned by `repository_owner`, rather than a bare `Commit.where(sha:)`. More generally, every handler that resolves records by payload-controlled identifiers (SHA, ref, PR number) should be required to prove those identifiers belong to the same `repository.full_name`/organization whose secret authenticated the request.

### Proof of Concept
1. Attacker registers/owns Organization A on the shared Shipit instance and knows `webhook_secret_A` (their own legitimate tenant secret).
2. Attacker finds a commit SHA `deadbeef...` belonging to Organization B's tracked repository/stack (public info from GitHub).
3. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/tests",
  "description": "forged"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` to `"OrgA"`, loads `webhook_secret_A`, and the signature validates. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` and creates a forged "success" status on Organization B's commit, despite the request never being authenticated for Organization B. [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
