### Title
Webhook signature verification binds only the authenticating organization, not the repository the event actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the `X-Hub-Signature` HMAC against using `repository_owner`, a value taken from the incoming JSON body itself. Once the signature check passes, the *entire* raw payload is handed to event handlers, which resolve the target repository/commit from other, independently-controlled fields of that same payload (`repository.full_name`, or in `StatusHandler` no repository field at all). Nothing binds "the organization whose secret validated the signature" to "the repository/stack that the handler subsequently writes to." This is precisely the "organization that authenticated versus the repository that is written" binding described in the rules.

### Finding Description
`verify_signature` computes: [1](#0-0) 

using `repository_owner`: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/`webhook_secret` configured for that organization, and `verify_webhook_signature` just checks the HMAC of `request.raw_post` against that org's secret: [3](#0-2) 

After the signature check succeeds, `create` dispatches the full, attacker-supplied `params` to handlers: [4](#0-3) 

Handlers resolve the actual repository/stack from a *different* payload field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) equals the owner encoded in `repository.full_name` (used to select the stack that gets acted on). Worse, `StatusHandler` doesn't even use a repository field — it resolves target commits purely by `sha`, globally, across every stack in the installation: [7](#0-6) 

An actor who legitimately controls a GitHub App/webhook installation for their own organization onboarded to this Shipit instance (i.e., they know their own org's `webhook_secret` because they configured it) can POST directly to the public `/webhooks` endpoint with:
- `repository.owner.login` (or `organization.login`) set to their own org — so `verify_signature` validates against a secret they legitimately possess, and
- `repository.full_name` / `sha` referencing a completely different (victim) organization's stack/commit.

The signature check passes (it only authenticates "a request signed by org A"), yet the handler acts on org B's data.

### Impact Explanation
Using `StatusHandler`, an attacker can inject a forged `success` CI status for an arbitrary commit sha belonging to a victim's stack, without ever touching that victim's repository or webhook secret. If the victim stack has continuous deployment enabled, creating a success status on the relevant commit is shown to trigger an automatic deploy: [8](#0-7) 

This yields an unauthorized deploy triggered purely by a signature that authenticates a different, attacker-controlled organization than the repository/stack actually affected — matching the Critical impact bar ("an unauthorized deploy"). Using `PushHandler`/other handlers, the same owner/full_name mismatch lets an attacker trigger `GithubSyncJob`/`sync_github` against a victim stack (`app/models/shipit/webhooks/handlers/push_handler.rb`).

### Likelihood Explanation
Moderate. It requires the attacker to control at least one legitimate organization/webhook installation on the shared Shipit instance (a common multi-tenant setup, since `config/secrets*.yml` shows multiple orgs configured under one `Shipit.github` map: `config/secrets.development.shopify.yml`). No Shipit session, `ApiClient` token, or victim credentials are needed — only knowledge of the attacker's own org's `webhook_secret`, which they possess by definition since they configured it.

### Recommendation
After signature verification, re-validate that the organization used to select the verifying secret (`repository_owner`) matches the owner encoded in the fields the handler will act on (`repository.full_name`, and — for `StatusHandler` — the owner of the stack that owns the resolved commit) before processing the event. Reject (422) any payload where these disagree, and have `StatusHandler` scope its `Commit` lookup to the authenticated repository/organization rather than a bare global `sha` lookup.

### Proof of Concept
1. Attacker legitimately owns/administers `attacker-org`, which is configured in Shipit with a known `webhook_secret`.
2. Attacker computes `sha256=...`/`sha1=...` HMAC over a crafted JSON body using `attacker-org`'s `webhook_secret`.
3. Attacker POSTs directly to `/webhooks` with header `X-Github-Event: status`, the computed signature, and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" },
  "sha": "<victim commit sha belonging to victim-org/victim-repo>",
  "state": "success"
}
```
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the HMAC validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of `repository.owner.login` — and calls `commit.create_status_from_github!`, marking it green.
6. If `victim-org/victim-repo`'s stack has `continuous_deployment` enabled, this triggers `ContinuousDeliveryJob`, resulting in an unauthorized deploy of victim code, all authenticated solely by the attacker's own organization's webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
