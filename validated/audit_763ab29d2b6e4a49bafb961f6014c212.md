### Title
Unvalidated route venues can attach unauthorized wallet drains to caller-signed strategy transactions - (File: contracts/controller/src/strategies/swap.rs)

### Summary

`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and other strategy flows pass a caller-supplied `StrategySwap` to the configured router. [1](#0-0)  The router’s payload selects venue pool addresses, and the venue dispatcher executes the selected pool without binding that address to a trusted pool registry. [2](#0-1) [3](#0-2) 

A malicious pool can therefore run contract code inside a caller-signed lending transaction and request an unrelated `token.transfer(victim, attacker, amount)`. [4](#0-3)  Soroban simulation attaches that transfer as a child of the victim’s `swap_collateral` authorization; if the victim signs the returned tree, the host accepts it while the swap still returns valid output. [5](#0-4) 

### Finding Description

`process_swap_collateral` authenticates the caller and confirms that the caller owns or delegates the target account before forwarding the route into the swap path. [6](#0-5) [7](#0-6) 

`swap_tokens` authorizes only the controller’s exact input transfer to the configured router, then invokes `execute_strategy` with caller-controlled route bytes. [1](#0-0)  That authorization protects only the controller’s own transfer and does not constrain additional sub-invocations that route-selected code places under the caller’s root authorization. [8](#0-7) 

After router execution, the controller checks only that its input balance did not increase, measured spend did not exceed `amount_in`, and its output balance increased. [9](#0-8)  It does not verify that the simulated authorization tree contains no unrelated token transfers.

The regression test demonstrates the exact boundary failure: a route-selected rogue pool calls `token.transfer(victim, attacker, amount)`, simulation records that transfer beneath the victim’s `swap_collateral` entry, and enforcing auth accepts it when that child is signed. [10](#0-9) 

### Impact Explanation

This is theft of user funds. The stolen token need not be supplied to the lending market, listed as collateral, or otherwise known to the controller, so the routed amount, output-delta checks, account health checks, and protocol balances do not bound the loss. [11](#0-10) [12](#0-11) 

A malicious pool can preserve the expected swap output, allowing all protocol checks to pass while separately draining the victim’s unrelated wallet balance to the attacker. [13](#0-12) 

### Likelihood Explanation

An unprivileged attacker can deploy a pool-shaped contract and encode its address into the route supplied to `swap_collateral` or another route-consuming strategy. [2](#0-1)  The attacker cannot execute the theft without the victim signing the poisoned authorization tree, so exploitation requires a malicious route, compromised route source, or a wallet/client that does not clearly reject unexpected child invocations. [14](#0-13) 

Because the attack can steal arbitrary unrelated token balances but depends on the victim accepting an expanded authorization tree, the issue is best rated Medium rather than High. [10](#0-9) 

### Recommendation

Constrain route execution to governance-approved venue contracts or an auditable venue registry rather than accepting arbitrary pool addresses in route payloads. If arbitrary venues remain supported, the controller and router boundary should expose a strict authorization-tree contract, and clients should reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or `execute_strategy` authorization containing children beyond the expected input-token transfer. [1](#0-0) [8](#0-7) 

### Proof of Concept

1. Alice owns a lending account with USDC collateral and also holds an unrelated token in her wallet. [15](#0-14) 
2. The attacker deploys a route-compatible pool configured with `(victim=Alice, wallet_token, to=attacker, amount=wallet_balance)`. [16](#0-15) 
3. The attacker encodes a `swap_collateral` route naming that pool while keeping the swap output sufficient for the requested collateral conversion. [17](#0-16) 
4. Alice invokes `swap_collateral(caller=alice, account_id, current=USDC, from_amount, new=ETH, swap=malicious_route)`. [18](#0-17) 
5. During route execution, the rogue pool calls `wallet_token.transfer(alice, attacker, wallet_balance)`. [19](#0-18) 
6. Simulation returns Alice’s `swap_collateral` authorization with that unrelated token transfer as a child; signing the returned tree makes the transfer succeed while Alice still receives the expected ETH collateral. [20](#0-19)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
