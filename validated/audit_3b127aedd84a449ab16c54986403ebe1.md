### Title
Unprivileged Split/Merge of a stake account during partitioned epoch-reward distribution causes `build_updated_stake_reward`'s `assert_eq!` to panic (consensus halt) or apply rewards against a stale delegation - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
`build_updated_stake_reward` reads the *current* stake account from the live `StakesCache` but compares it against a `PartitionedStakeReward` entitlement value that was pre-computed once at the epoch-boundary calculation block [1](#0-0) . Because nothing in the reviewed code blocks a user from issuing `StakeInstruction::Split`/`Merge` on their own stake account during the multi-block distribution window, an attacker can desynchronize the two values and trigger the `assert_eq!` panic, which is a deterministic bank-execution panic replicated on every validator.

### Finding Description
`store_stake_accounts_in_partition` iterates the partition's pre-computed `PartitionedStakeReward`s and, for each, calls `Self::build_updated_stake_reward` passing `stakes_cache_accounts` — a snapshot of `self.stakes_cache.stakes()` taken **at the current bank**, i.e. at whatever block height the partition happens to be processed [2](#0-1) .

Inside `build_updated_stake_reward`:
- `stake_account`/`stake` is fetched fresh from `stakes_cache_accounts.get(&partitioned_stake_reward.stake_pubkey)` — this reflects the *live* delegation at distribution time.
- `new_stake = partitioned_stake_reward.inflation.stake` is the delegation value baked in during the one-time calculation phase (`calculate_stake_rewards_and_commissions`), i.e. the *stale* pre-distribution snapshot with the reward already added on top of the old stake.
- When the `relax_post_exec_min_balance_check` feature is not active, the code takes the `else` branch and asserts:
```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, ...);
``` [3](#0-2) 

`expected_delegation` uses the **current** `stake.delegation.stake` (post-Split/Merge), while `new_stake.delegation.stake` embeds the **old** (pre-Split/Merge) stake plus reward. If the attacker performs a `Split` or `Merge` on their own stake account any time between the epoch-boundary calculation block and the specific block at which their partition index gets processed (which can be many blocks later, since rewards are distributed over up to 10% of an epoch's slots, see `get_reward_distribution_num_blocks` [4](#0-3) ), the two values diverge and the assert panics.

The reward-recalculation safety valve, `recalculate_partitioned_rewards_if_active`, only re-syncs stake rewards to the live `StakesCache` on **snapshot restore**, not on every distribution block [5](#0-4) [6](#0-5) . During normal (non-restart) block production, `distribute_partitioned_epoch_rewards` reuses the single calculation-phase snapshot for the whole distribution window [7](#0-6) .

The `store_stake_accounts_in_partition` doc-comment explicitly (and, per this analysis, incorrectly) assumes protection exists: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."* [8](#0-7) . No such restriction gating `Split`/`Merge` during `EpochRewardStatus::Active` was found anywhere in the reviewed stake-program or bank code; the only related test found, `test_rewards_period_system_transfer`, confirms the opposite — that ordinary transactions/lamport transfers to stake accounts are explicitly permitted "regardless of rewards period" [9](#0-8) .

### Impact Explanation
If the mismatch occurs, `build_updated_stake_reward` panics (`assert_eq!` with a custom message), which propagates out of `store_stake_accounts_in_partition` and `distribute_partitioned_epoch_rewards`, both invoked from ordinary bank block-processing (not from a validated transaction, so it cannot simply be rejected as a failed transaction — it aborts block processing for every validator that replays the block deterministically). This is a cluster-wide liveness/consensus halt triggerable by an unprivileged user with only ordinary `StakeInstruction::Split`/`Merge` transactions, matching the "epoch-boundary halt" impact category in scope. In addition, in cases where the numeric mismatch does not panic but is masked by other code paths, an attacker's stake delegation could be updated inconsistently with the actual post-Split/Merge lamports of the account, corrupting stake-weight accounting.

### Likelihood Explanation
This requires only unprivileged actions: own a delegated, activated stake account with a pending reward, and submit a normal `Split` or `Merge` instruction during the (multi-block) partitioned-distribution window before that account's specific partition index is processed. No validator/operator control, no leaked keys, and no crafted snapshots are needed — the vulnerable code path (`adjust_delegations_for_rent == false`) is exercised whenever `relax_post_exec_min_balance_check` is not active, and is directly covered by unit tests in the repository (e.g. `test_store_stake_accounts_in_partition`, `test_distribute_partitioned_epoch_rewards_bank_capital_and_sysvar_balance`) using `Bank::new_for_tests` with default (non-activated) features. The distribution window spans multiple blocks (up to 10% of an epoch), giving ample opportunity for the attacker's transaction to land between calculation and their partition's distribution block.

### Recommendation
In `build_updated_stake_reward` / `store_stake_accounts_in_partition`, do not compare stale calculation-time delegation state against the live `StakesCache` account. Either: (1) fail gracefully (return `Err(DistributionError::...)` and forfeit/re-route that reward instead of asserting) when the current delegation state does not match what was expected, treating it the same as `AccountNotFound`; or (2) recompute/verify the reward against a delegation snapshot taken at the exact block used, ensuring the stake program actually prevents delegation-affecting instructions (`Split`, `Merge`, `Deactivate`, etc.) on accounts with a pending, not-yet-distributed `PartitionedStakeReward` for the current epoch, e.g. via an explicit epoch-rewards-active check in the stake program's instruction processor.

        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {

            return;

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }
