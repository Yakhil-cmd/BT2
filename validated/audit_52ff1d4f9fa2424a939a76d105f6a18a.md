### Title
Insecure file permissions on saved private textcoin payload expose spendable mnemonic to local attackers - (File: wallet.js)

### Summary
When a wallet sends a private (non-public) asset payment as a "textcoin" to a recipient who is not a device-paired peer, `wallet.js` serializes the mnemonic and the private payment chains into a zip file and writes it to disk with `storePrivateAssetPayload()`. The file is created with Node's default `fs.writeFile` permissions (no explicit mode is passed), which typically results in a world/group-readable file (e.g. `0644` after umask) rather than an owner-only-readable file.

### Finding Description
`storePrivateAssetPayload()` builds a JSON object containing the plaintext `mnemonic` (the secret needed to claim/spend the private asset) and the private payment `chains`, zips it, and persists it to `fullPath` on the local filesystem: [1](#0-0) 

The write is performed via plain `fs.writeFile(fullPath, zipFile, cb)` with no `{ mode: 0o600 }` option, so the resulting file inherits the process's default create mode (masked only by the OS umask), not a restrictive owner-only permission: [2](#0-1) 

This mnemonic is the equivalent of a bearer private key for the associated private-asset output — anyone who can read the file can later call the wallet's `receiveTextCoin`/`handlePrivatePaymentFile` claim flow with that mnemonic and take the funds, exactly as the legitimate recipient would: [3](#0-2) 

This mirrors the root cause of CVE-2021-33923 (Confluent cp-ansible): a locally-reachable sensitive artifact — there private keys/state DB, here a spendable mnemonic/private-payment blob — is written with insecure default permissions, letting any local unprivileged user (or process) on the same host read it.

### Impact Explanation
Any local user or process on the machine that can read the file at `fullPath` (which is supplied by the calling application via `opts.getPrivateAssetPayloadSavePath`, often a predictable location such as a downloads/exports folder) obtains the mnemonic and private payment chain. They can then claim the private asset before the intended recipient, causing unauthorized spending/theft of the private-asset funds. This is a concrete loss-of-funds scenario reachable purely from a normal wallet operation (sending a private-payment textcoin), not requiring any attacker-controlled network unit or privileged access — it only requires local co-residency with the sender's process.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to already have local (even unprivileged) access to the same host/filesystem as the sending wallet, consistent with the CVE's own attack model ("local attackers"). Given multi-user servers, shared hosting, or any environment where the headless wallet runs alongside other tenants/services, an unprivileged co-resident process reading a world-readable file is a realistic and common local-privilege-escalation-style attack.

### Recommendation
Explicitly set a restrictive mode when persisting the private payload, e.g. `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)`, and validate/chmod the target file after creation to `0600`. Additionally, consider encrypting the mnemonic/payload at rest or avoiding writing the raw mnemonic to disk altogether (e.g., prompting for immediate transfer/claim instead of durable storage), and document that `getPrivateAssetPayloadSavePath` must return a path in a directory with restrictive permissions.

### Proof of Concept
1. Use a headless/GUI wallet on a shared multi-user host to send a private asset as a textcoin to an email/offline recipient, supplying `opts.getPrivateAssetPayloadSavePath` pointing at a location such as `/tmp` or a shared "downloads" directory.
2. `storePrivateAssetPayload()` writes the zip (containing `mnemonic` and `chains`) via `fs.writeFile(fullPath, zipFile, cb)` with default permissions.
3. As a second unprivileged local user on the same host, `stat` the file to confirm it is group/world-readable, then read and unzip it to extract `private_textcoin` → `mnemonic`.
4. Call the wallet's textcoin-claim flow (`handlePrivatePaymentFile`/`receiveTextCoin`) using the stolen mnemonic to claim the funds to an attacker-controlled address before the legitimate recipient does.
