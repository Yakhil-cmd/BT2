## Title
Unauthenticated GitHub webhook forgery escalates into `Shipit.github_teams` authorization when no `webhook_secret` is configured - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` delegates trust in the `organization`/`repository` fields of an inbound webhook to `GithubApp#verify_webhook_signature`, but that method silently returns `true` whenever no `webhook_secret` is configured for the organization — a state the setup docs explicitly describe as optional/default (`nil`). With no secret configured, any unauthenticated actor can POST a forged `membership` webhook that is processed as if it came from GitHub, letting them add an arbitrary GitHub login to a `Shipit::Team` that backs `Shipit.github_teams` authorization. This breaks the "organization that authenticated versus the repository/organization that is written" binding: the organization is asserted by the unverified payload, yet `MembershipHandler` uses that same unverified value to create teams and grant memberships that directly control `User#authorized?`.

### Finding Description
`verify_signature` picks a `github_app` purely from the (unverified) request payload: [1](#0-0) 

`verify_webhook_signature` then trivially passes when the organization has no secret configured: [2](#0-1) 

This is a supported, documented configuration — the setup guide and example secrets file both mark `webhook_secret` as optional/`nil` by default: [3](#0-2) [4](#0-3) 

Once the signature check is bypassed, `WebhooksController#create` dispatches the raw, attacker-controlled JSON straight to the registered handlers with no further authentication: [5](#0-4) 

`MembershipHandler` trusts the payload's `organization.login`, `team.id`, and `member.login` fields to create/find a `Team` and attach a `User`: [6](#0-5) 

`User.find_or_create_by_login!` resolves the "member" to a real GitHub identity by making a live GitHub API call for that login, which populates `github_id` with the attacker's own real GitHub numeric ID: [7](#0-6) 

Later, when the attacker performs a legitimate GitHub OAuth login, `GithubAuthenticationController#sign_in_github` looks the user up by `github_id` (not by any webhook-derived flag), so it resolves to the very `User` record the forged webhook attached to the team: [8](#0-7) [9](#0-8) 

`Authentication#force_github_authentication` then grants access based purely on `current_user.authorized?`: [10](#0-9) [11](#0-10) 

No `ApiClient` token, `webhook_secret`, `api_clients_secret`, GitHub App private key, or repository write access is needed at any step — the whole chain relies on the *absence* of a secret, which is a documented default state.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization (explicitly listed as a High-severity impact): an external, unprivileged actor with no Shipit or GitHub App credentials can grant their own real GitHub account membership in a Shipit-recognized team, then complete a normal GitHub OAuth login to gain full authenticated access to the Shipit instance (view/trigger deploys, tasks, stacks, etc., per whatever the impersonated team is authorized to do).

### Likelihood Explanation
Any Shipit deployment that follows the documented, default setup (webhook secret left blank, which the docs and example config explicitly allow) is affected. The only information the attacker needs is the numeric GitHub team `id` for a team referenced in `Shipit.github_teams`, which is often discoverable via the public GitHub API for organizations with any public teams, or via other reconnaissance. No race condition, timing, or resource-exhaustion behavior is involved.

### Recommendation
Require `webhook_secret` for every configured GitHub organization/app and refuse to process webhooks (`head(422)`/`head(:forbidden)`) when it is missing, rather than treating an absent secret as "verification succeeded." At minimum, `GithubApp#verify_webhook_signature` should fail closed instead of returning `true` when `webhook_secret` is blank, and the setup documentation should mark the secret as mandatory rather than optional.

### Proof of Concept
Against a Shipit instance configured with `github.<org>.webhook_secret` unset (the documented default):

1. Discover the numeric `id` of a GitHub team referenced by `Shipit.github_teams` (e.g., via `GET /orgs/<org>/teams` if any team is public, or via other means).
2. POST an unauthenticated, unsigned webhook:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <target_team_id>, "name": "Some Team", "slug": "some-team", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "<target-org>" },
  "member": { "login": "<attacker-github-login>" },
  "repository": { "owner": { "login": "<target-org>" } }
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` returns `true` when `webhook_secret` is blank.
3. `MembershipHandler#process` creates/finds `Team` with `github_id: <target_team_id>` and adds a `User` fetched via `Shipit.github.api.user('<attacker-github-login>')`, whose `github_id` matches the attacker's real GitHub account.
4. The attacker performs a normal GitHub OAuth login at `/github/auth/github`. `sign_in_github` resolves to the same `User` record (matched by `github_id`), and `current_user.authorized?` now returns `true` because the user is a member of a team in `Shipit.github_teams`, granting full authenticated access to the Shipit UI/API.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
```
