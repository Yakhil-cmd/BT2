Now I have enough to confirm the binding mismatch in the multi-organization webhook verification path.

### Title
Webhook signature verified against attacker-controlled organization while handlers act on a different repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization mode, `WebhooksController#verify_signature` selects the HMAC secret to check the request against based on `repository_owner`, a value taken from the *unverified* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The signature is only ever checked against the secret belonging to whatever organization the attacker names in that field — it never confirms that this organization actually corresponds to the repository/stack that the downstream handlers (e.g. `PushHandler`, `StatusHandler`) subsequently act on using other unrelated fields of the same JSON body (`repository.full_name`, `sha`, `ref`, etc.).

### Finding Description
`Shipit.github(organization:)` looks up a per-organization `GitHubApp` (and its `webhook_secret`) from `config/secrets*.yml` [1](#0-0) . `WebhooksController#verify_signature` derives `organization` purely from the request body: [2](#0-1) 
It calls `github_app.verify_webhook_signature(header, raw_post)`, which computes `HMAC(secret_for_that_organization, raw_post)` [3](#0-2) . This proves only that *some* body was signed with *the secret of the organization named in that same body* — it never binds the verified organization to the `repository.full_name` (or `sha`, `ref`) that the handlers act on. Handlers such as `PushHandler` operate on `stacks.where(branch:)` derived from `params.ref`/`params.after` scoped by the `Repository` matched from the payload's `repository` object (looked up elsewhere by full name), not by the same `repository.owner.login` used for signature selection [4](#0-3) .

Concretely: an attacker who legitimately owns/administers **Org A** in Shipit (and therefore knows Org A's `webhook_secret`, e.g. because they set up the GitHub App integration for their own org) can HMAC-sign an arbitrary JSON body with Org A's secret while setting `repository.owner.login = "OrgA"` (satisfying `verify_signature`) but setting `repository.full_name = "OrgB/victim-repo"`, `ref`, `after`, etc. Because `repository_owner` (used only for secret selection) is never cross-checked against `repository.full_name` (used by the handler for the actual write), `verify_signature` passes and the forged event is dispatched to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) , letting the attacker forge a `push`/`status`/`check_suite` event for a repository belonging to a different organization than the one whose secret they used.

This breaks the intended binding: *organization authenticated by the signature* == *organization whose repository is written by the handler*.

### Impact Explanation
If exploitable, this would let an org-scoped attacker forge GitHub events (e.g. `push` triggering `GithubSyncJob`, or `status`/`check_suite` events) against a stack belonging to an unrelated organization/repository configured in the same Shipit instance, since the request passes signature verification. This could trigger unauthorized sync/deploy-adjacent state changes for a repository the attacker doesn't control.

### Likelihood Explanation
Low/uncertain — this requires the Shipit instance to be configured with **multiple GitHub organizations**, each with their own `webhook_secret`, and requires the attacker to control (or know the webhook secret of) at least one of those configured organizations while targeting another organization's stack in the same instance. This is a real but narrow multi-tenant configuration scenario; I could not confirm from the available files whether `Repository`/`Stack` lookup by `full_name` further restricts to the organization actually used for verification (that logic lives in repository/stack lookup code not fully covered here), so I cannot conclusively rule out an additional guard downstream.

### Recommendation
In `WebhooksController#verify_signature`, do not select the verification secret from the same untrusted field the handler will later trust for repository resolution without cross-validating them. Concretely: after selecting `github_app` by `repository_owner`, additionally assert that `params.dig('repository','full_name')&.split('/')&.first` matches `repository_owner` (case-insensitively) before dispatching to handlers, rejecting mismatched payloads with `422`.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` (secret `sA`, known to the attacker) and `OrgB` (secret `sB`, unknown to attacker, hosting `OrgB/victim`):
```json
POST /github_authentication? (webhooks endpoint)
X-Github-Event: push
X-Hub-Signature: sha1=HMAC(sA, raw_body)
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim" }
}
```
`verify_signature` resolves `github_app = Shipit.github(organization: "OrgA")` and successfully verifies the HMAC using `sA`, then `PushHandler` processes the event against stacks matching repository `OrgB/victim` — a repository/organization the attacker's known secret was never meant to authorize.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    def event

    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
