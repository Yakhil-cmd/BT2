### Title
Webhook signature verified against the organization named in `repository.owner.login`, but event handlers act on the independently-controlled `repository.full_name` field, allowing a valid signature from one organization's secret to authorize writes to another organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, a value read straight out of the unverified JSON body (`params.dig('repository', 'owner', 'login')`), before the signature has been checked. Downstream webhook handlers, however, resolve the actual `Stack`/`Repository` to mutate using the `repository.full_name` field elsewhere in that same, attacker-supplied JSON body. Because these two fields live in the same object but are never cross-checked for consistency, and because the field used to pick the verification secret is trusted before verification even happens, an attacker who knows (or controls) the webhook secret for one organization configured on the Shipit instance can forge a payload whose `owner.login` points at "their" org (so the signature check passes) while `full_name` points at a different organization's repository, causing Shipit to process push/status/pull_request/check_suite events - and mutate stack state - for a repository they have no legitimate webhook relationship with.

### Finding Description
In `WebhooksController`, the `verify_signature` before_action resolves the GitHub App config purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` only proves that the raw body was HMAC-signed with *the secret belonging to whichever organization `repository_owner` names* - it says nothing about which repository the rest of the payload actually references: [3](#0-2) 

Shipit supports per-organization secrets (`Shipit.github(organization:)` picks a distinct `webhook_secret` per org), as documented in the multi-org config sample: [4](#0-3) 

Once signature verification passes, the actual event handlers (`push`, `status`, `check_suite`, `pull_request`, etc.) locate the repository/stack to act on using `repository.full_name` from the very same JSON body, independent of `repository.owner.login`: [5](#0-4) 

Because `owner.login` (used for secret selection/authentication) and `full_name` (used for repository resolution/authorization of the write) are two independently-settable JSON keys inside the same signed payload, nothing forces them to refer to the same repository. This breaks the equality that should hold:

`organization whose secret authenticated the request == organization owning the repository whose stack is written`

An attacker who legitimately controls (or has leaked) the webhook secret for *any* organization onboarded to this Shipit instance can compute a valid HMAC for a payload where `repository.owner.login` is set to that organization, but `repository.full_name` is set to `"other-org/private-repo"`. The signature check passes (it only validates the raw bytes against the secret for `repository_owner="that-organization"`), and the handler then updates commit statuses, syncs pushes, or advances the merge queue for `other-org/private-repo` - a repository/org the attacker was never authorized to send webhooks for.

### Impact Explanation
This crosses an organizational trust boundary enforced only by webhook secrets: a party trusted for org A's webhooks can inject and drive webhook-triggered state changes (push syncing, commit statuses, check-suite refresh, PR merge-queue transitions) for org B's repositories on a shared multi-tenant Shipit deployment. This matches the "Critical - cross-repository writes" impact category, since it lets an attacker write/alter deploy-relevant state (commit statuses, merge queue, PR handling) belonging to a repository/organization outside their authorized scope, and could be leveraged to manipulate CI status gating or merge-queue behavior ahead of an unauthorized deploy.

### Likelihood Explanation
Exploitability depends on the instance being configured with multiple GitHub organizations (the multi-org config the codebase explicitly documents and supports) and the attacker holding a valid webhook secret for at least one of them - e.g., their own onboarded org, or one whose secret leaked. This is a lower bar than compromising the target organization's own secret, private key, or an `ApiClient` token, and requires no session, no API token, and no GitHub App private key - only knowledge of one tenant's webhook secret to attack a different tenant's repository, satisfying the "unprivileged attacker" bar for this scan.

### Recommendation
After signature verification succeeds, re-derive the organization strictly from the verified `repository_owner`/`organization.login` used for the signature check, and reject (or re-verify) any event whose `repository.full_name` owner does not match the organization whose secret validated the signature. Concretely, in `WebhooksController`, compare `repository_owner` against the owner segment of `repository.full_name` (and `organization.login` if present) and short-circuit with `422` on mismatch before dispatching to `Shipit::Webhooks.for_event(event)`.

### Proof of Concept
1. Configure Shipit (per `config/secrets.development.example.yml`) with two organizations, `org-a` and `org-b`, each with its own `webhook_secret`.
2. As an attacker who legitimately knows `org-a`'s webhook secret (e.g., they administer an app/repo under org-a), craft a `push` webhook payload:
   ```json
   {
     "repository": {
       "owner": { "login": "org-a" },
       "full_name": "org-b/victim-repo"
     },
     ...
   }
   ```
3. Compute `X-Hub-Signature` using `org-a`'s `webhook_secret` over the raw JSON body, per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` logic.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and the signature validates successfully.
5. `GithubSyncJob`/push handling then resolves the target stack via `repository.full_name = "org-b/victim-repo"`, causing Shipit to process the forged push against `org-b`'s stack - despite the attacker only ever having proven control of `org-a`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
