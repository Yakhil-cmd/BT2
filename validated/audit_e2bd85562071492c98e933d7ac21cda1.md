## Title
Unauthenticated Registration of Shared-Address Membership Enables Cross-Party Disclosure of Private Payment Chains - ([File: wallet_defined_by_addresses.js])

## Summary
The ZITADEL bug allowed a low-privileged, authenticated caller to retrieve another tenant's data by supplying an object ID (`project_id`/`grant_id`/`app_id`) that the API resolved without checking it belonged to the caller's own scope. The analogous root cause in `ocore` is in the paired-device message handler for `new_shared_address`: any paired correspondent (an unprivileged actor) can submit a shared-address definition/signer map that references one of the recipient's own addresses, and the wallet accepts and registers this multisig association **without any correlation to a prior user-approved `create_new_shared_address`/`approve_new_shared_address` handshake and without user confirmation**. This silently binds the attacker's device as an authorized co-signer/member of the resulting combined ("shared") address in the victim's local database.

## Finding Description
`wallet.js` routes the `"new_shared_address"` device message directly into `walletDefinedByAddresses.handleNewSharedAddress`, with no confirmation dialog (unlike the `"create_new_shared_address"` path, which explicitly emits an event for the user to approve): [1](#0-0) 

`handleNewSharedAddress` only checks internal consistency of the message (definition hash matches address, signer addresses are syntactically valid, signer paths match paths extracted from the definition, and every definition leaf has a signer) and that the definition is a valid oscript definition and that at least one of the leaf addresses is "mine": [2](#0-1) 

`determineIfIncludesMeAndRewriteDeviceAddress` merely verifies that some referenced address exists in `my_addresses`/`shared_addresses`, and if so proceeds — it does not verify that the local user ever agreed, out-of-band, to form a multisig/shared-address relationship with the sending device: [3](#0-2) 

Once accepted, `addNewSharedAddress` unconditionally inserts the new combined address and its `shared_address_signing_paths` rows (which record which `device_address` controls which member leaf), regardless of whether this device ever participated in the collaborative `pending_shared_addresses` approval flow: [4](#0-3) 

The consequence is that the attacker's `device_address` is now a legitimate entry in `shared_address_signing_paths` for the newly-fabricated combined address. `forwardPrivateChainsToOtherMembersOfAddresses` uses exactly this table, with no additional authorization check, to decide which devices receive the plaintext private-payment chain whenever a private payment is made to that combined address: [5](#0-4) 

This mirrors the ZITADEL flaw structurally: a caller with no real relationship to the resource (a `project_id`/`grant_id` in ZITADEL, a "member address" association here) supplies an identifier that the target service resolves and acts on without verifying the caller's actual authorization over that identifier/scope.

## Impact Explanation
Because the attacker is silently registered as a co-signer of the combined address, any private (indivisible/divisible) asset payment later sent to that shared address — by the victim or any third party who is given/discovers the combined address — will have its private payment chain (addresses, amounts, blinding factors) automatically forwarded to the attacker's device via `forwardPrivateChainsToOtherMembersOfAddresses`/`forwardPrivateChainsToDevices`, without any consent step. This is an unauthorized disclosure of private payment chain data to an unrelated party, in the private-payment/paired-device surface explicitly called out as in-scope. Because the shared address is genuinely M-of-N, the attacker cannot unilaterally spend funds (my private key is still required), so the primary consequence is confidentiality loss of private-payment data reachable purely from the paired-device message channel, not double-spend/inflation.

## Likelihood Explanation
Any already-paired correspondent device can trigger this by sending a single `"new_shared_address"` message with a crafted definition/signers map referencing a known target address (addresses are often shared for receiving payments) — no server-side flag or MITM is needed, and no user interaction is required to accept the message on the receiving wallet.

## Recommendation
`handleNewSharedAddress`, when handling an unsolicited `"new_shared_address"` message, should require correlation with a prior `pending_shared_addresses`/`approve_new_shared_address` record that the local device itself initiated or explicitly approved (or otherwise require explicit user confirmation before writing to `shared_addresses`/`shared_address_signing_paths`), rather than accepting any syntactically valid definition that happens to reference one of the recipient's own addresses.

## Proof of Concept
1. Pair with the victim's wallet as a correspondent device (a normal, unprivileged wallet-pairing relationship).
2. Learn one of the victim's addresses `V` (addresses are routinely shared for receiving payments).
3. Craft an address definition combining `V` and the attacker's own address `A`, e.g. `["and", [["address","V"], ["address","A"]]]`, compute its chash `S`.
4. Send a `"new_shared_address"` device message: `{address: S, definition: [...], signers: {"r.0": {address: V}, "r.1": {address: A, device_address: <attacker_device>}}}` directly (bypassing `create_new_shared_address`/`approve_new_shared_address`).
5. Victim's node executes `handleNewSharedAddress` → `addNewSharedAddress`, silently inserting `S` into `shared_addresses` and `shared_address_signing_paths` with the attacker's device as a control device, with no confirmation dialog.
6. If `S` is subsequently used to receive a private-asset payment (e.g., victim uses it as a receiving address, or a third party sends to it), `forwardPrivateChainsToOtherMembersOfAddresses` forwards the plaintext private payment chain to the attacker's device automatically.

// Checks if any of my payment addresses is mentioned.
// It is possible that my device address is not mentioned in the definition if I'm a member of multisig address, one of my cosigners is mentioned instead
function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

		JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?) AND device_address!=?",

	);
}
