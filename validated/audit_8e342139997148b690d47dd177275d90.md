### Title
Direct token transfer ("donation") to an Aquarius pool inflates the fair-value LP price used for collateral valuation, enabling over-borrowing when the attacker holds a large share of the LP - (File: common/src/oracle/lp.rs)

### Summary
The Yearn `pricePerShare` bug class is a `totalAssets / totalSupply` ratio that can be inflated by donating assets directly to the underlying pool. XOXNO's own lending share price is not vulnerable: supply/debt shares are valued by stored RAY indexes (`Cache.supply_index` / `borrow_index`) and liquidity is gated on the tracked `cash` book, not the physical token balance (`Cache::require_reserves` only compares `self.cash`), so a direct transfer to the pool contract cannot inflate share value or unlock extra liquidity [1](#0-0) . However, the same donation primitive lands on the price-aggregator side: Aquarius LP collateral is priced from the pool's *live* reserves read in `aquarius::read`, which feed `fair_lp_price_wad` / `fair_stable_lp_price_wad`. A permissionless `token.transfer` to the Aquarius pool contract raises `reserve_a`/`reserve_b` without minting shares, inflating the LP share price that `calculate_account_risk_totals` then uses as collateral value [2](#0-1) [3](#0-2) .

### Finding Description
`fair_lp_price_wad` computes `2 * sqrt(value_a * value_b) * WAD / share_supply_wad` where `value_*` comes from `aquarius_pool_reserves_call` on the live pool [4](#0-3) . The reserves are read fresh on every `read` and there is no smoothing, no per-block observation check, and no bound relative to a trusted reference price — only `min_pool_value_wad`, which is a floor on total pool value, not a ceiling on the per-share price [5](#0-4) . The same holds for `fair_stable_lp_price_wad`, where `D` is homogeneous in the reserves, so donating either leg scales `D` (and therefore the price) roughly linearly with the donated amount [6](#0-5) . The inflated `price_wad` flows into `position_value_floor`/`position_value_ceil` for collateral and into `health_factor_wad`, so the attacker can pass the LTV risk gate and borrow more than the real value of their LP, or block/defer liquidation.

Unlike Yearn, the donation is not pure loss: the attacker must hold LP shares, and the donated reserves accrue pro-rata to all LP holders, so after over-borrowing the attacker can withdraw from the Aquarius pool and recover fraction `f` of the donation where `f` is their share of `total_shares`.

### Impact Explanation
Theft of user funds / protocol insolvency: an account posts Aquarius LP as collateral, inflates the pool's reported reserves with a direct token transfer, calls `update_indexes` + `borrow` on the controller, and the risk gate values the collateral at the manipulated `price_wad`. The borrowed amount exceeds the real redeemable value of the LP; the position is left under-collateralized and the loss is socialized across suppliers of the borrowed market. For the stable formula the multiplier is roughly `1 + donation / pool_value`; for the constant-product formula `sqrt` dampens it to `sqrt(1 + donation / reserve_a)`, but any factor above 1 creates free collateral value.

### Likelihood Explanation
Requires the attacker to hold a large fraction of the LP supply (the donation is shared with all LPs, and net cost is `(1 - f) * donation`). For the stable-pool path, profit is possible when `f > 1 / (1 + ltv)` — e.g. `f > ~56%` at 80% LTV; for the constant-product path, `sqrt` growth requires still larger `f` or a very large donation, but thin Aquarius pools where a single depositor owns the majority of shares are realistic. The donation can be funded with the protocol's own `flash_loan` within the same transaction batch, so the capital requirement is only the unrecoverable `(1 - f)` fraction plus flash fees. No privileged access, leaked key, or oracle misbehavior is needed — only `token.transfer` to the Aquarius pool address and the public controller entrypoints (`supply`, `borrow`, `update_indexes`).

### Recommendation
Treat live-reserve reads as manipulable inputs: (1) bound the computed LP price against a tolerance band around a stored/reference price (as is done for other sanity bands), or require the derived price to stay within a configured deviation of a Reflector/RedStone-implied fair value; (2) for stable pools, consider pricing the LP as `min_leg_price * virtual_price` using the pool's own `virtual_price` (which is also donation-sensitive) combined with an external floor, or reject reserve ratios that deviate sharply from the last attested `attest` state; (3) document or reject pools where a small number of depositors control most of the share supply.

### Proof of Concept
1. Attacker creates/joins an Aquarius stable pool (A/B) that is registered as an `AquariusLpSource` for collateral, depositing until they hold >60% of `total_shares`.
2. Attacker supplies the LP token to the lending controller via `supply`, so it appears as a collateral leg.
3. Attacker flash-borrows a large amount of token A via the pool's `flash_loan` and calls `token.transfer(attacker → aquarius_pool, X)`, raising `reserve_a`.
4. `aquarius::read` now returns `price_wad ≈ base * (1 + X / pool_value)` (stable) or `base * sqrt(1 + X / reserve_a)` (constant product) [7](#0-6) .
5. `borrow` passes the LTV gate in `calculate_account_risk_totals` because `position_value_floor(shares, supply_index, inflated_price)` exceeds the real LP value.
6. Attacker calls the Aquarius pool's `withdraw`, recovering `f * X` of the donation, repays the flash loan, and keeps the over-borrowed assets.

Unverified: whether the price-aggregator applies a deviation band between independent legs or a cached reference that would reject this read before it reaches the risk gate; if such a band exists and is tight, this analog does not hold.

```rust
pub fn fair_lp_price_wad(
    env: &Env,
    a: &LpLeg,
    b: &LpLeg,
    supply: &LpSupply,
) -> Result<i128, OracleError> {
    if a.reserve <= 0
        || b.reserve <= 0
        || a.price_wad <= 0
        || b.price_wad <= 0
        || supply.total_shares <= 0
    {
        return Err(OracleError::InvalidPrice);
    }

    let value_a = reserve_value_wad(env, a)?;
    let value_b = reserve_value_wad(env, b)?;

    let total_value =
        isqrt_of_product(env, value_a as u128, value_b as u128).mul(&U256::from_u32(env, 2));

    let share_supply_wad = try_amount_to_wad(env, supply.total_shares, supply.decimals)?;
    if share_supply_wad <= 0 {
        return Err(OracleError::InvalidPrice);
    }
    let fair = total_value
        .mul(&U256::from_u128(env, WAD as u128))
        .div(&U256::from_u128(env, share_supply_wad as u128));
```
