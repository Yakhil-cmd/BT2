### Title
`MembershipHandler#find_or_create_team!` binds by GitHub `team.id` alone, letting a webhook verified under one organization write `Membership` rows onto a `Team` belonging to another organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Team.find_or_create_by!(github_id: params.team.id)` in `MembershipHandler#find_or_create_team!` looks up teams by GitHub's global, sequential `team.id` with no check that the resolved `Team#organization` matches the organization whose webhook secret verified the request. In a Shipit deployment configured for multiple GitHub organizations (a documented, supported setup), an attacker who controls one configured org can send a validly-signed `membership` webhook claiming a `team.id` that collides with a `Team` row belonging to a different, victim organization, causing `Team#add_member` to write a `Membership` for an attacker-named user against the victim's team.

### Finding Description
The binding the question asserts should hold is:
`Team#organization` (the org that actually owns the GitHub team with id `params.team.id`) == the organization verified by `WebhooksController#verify_signature` for the inbound request (`repository_owner`, i.e. `params.dig('repository','owner','login') || params.dig('organization','login')`). [1](#0-0) 

This binding is **not enforced** anywhere in the membership path. `verify_signature` only proves that the payload was signed with the webhook secret configured for whatever organization the payload itself claims (`repository_owner`) - it says nothing about which organization owns the numeric `team.id` inside the payload: [2](#0-1) 

`MembershipHandler#find_or_create_team!` then resolves the `Team` purely by `github_id`, with no scoping by organization: [3](#0-2) 

Contrast this with `Team.find_or_create_by_handle`, which deliberately scopes lookups by `organization` + `slug`: [4](#0-3) 

No such scoping exists in the webhook path. If a `Team` row with `github_id == params.team.id` already exists (e.g., a victim org's team, previously created by a legitimate membership webhook), `find_or_create_by!` returns that existing row unchanged - it never re-validates or updates `organization`. The handler proceeds to:
```ruby
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member)
```
`Team#add_member` unconditionally appends the member: [5](#0-4) 

**Attacker's exact request**: The attacker controls (as a legitimate customer/org-admin) one GitHub organization ("OrgTwo") that this multi-tenant Shipit instance is configured for (per-org `webhook_secret` support is documented and supported: `docs/setup.md` "Using Multiple GitHub Applications", `test/dummy/config/secrets_double_github_app.yml`). They send `POST /webhooks` with header `X-Github-Event: membership`, a body `{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"OrgTwo"},"member":{"login":"attacker-controlled-login"}}`, signed with `OrgTwo`'s webhook secret (which the attacker legitimately possesses).

**Why existing guards fail**: `verify_signature` correctly confirms the request came from the org identified in the payload (`OrgTwo`) - but that org identifier is never cross-checked against the `team.id`'s true owning organization. `ExplicitParameters` schema only validates types/presence, not cross-organization ownership. `find_or_create_team!` trusts `params.team.id` as a global lookup key.

### Impact Explanation
If the collided `Team#id` happens to be one of the organization's `Shipit.github_teams` (the OAuth-configured authorization teams, sourced from `GitHubApp#oauth_teams`), the newly created `Membership` makes `User#authorized?` return true for an attacker-chosen login: [6](#0-5) [7](#0-6) 

This is a cross-tenant write: a webhook verified under one organization's secret mutates authorization state belonging to a different organization served by the same Shipit instance - matching the Critical category "a payload for one repository mutating another's stack, commit, task or team," and escalating into `Shipit.github_teams` authorization (also listed as High). It is repeatable against any `github_id` the attacker can guess or enumerate (GitHub team IDs are sequential and often discoverable), and against any of the tenant organizations sharing the instance.

### Likelihood Explanation
This requires a **multi-organization Shipit deployment** (explicitly documented and supported) where the attacker is a legitimate admin/owner of one of the configured organizations (holding that org's real `webhook_secret`), while a different, victim organization is also configured on the same instance and has an existing `Team` row whose `github_id` the attacker can predict or brute-force. In a single-org deployment this path does not apply, since the attacker would need a valid webhook secret to reach `MembershipHandler` at all, and there'd be no other tenant to attack. Given multi-org support is a first-class documented feature, this is a realistic, low-cost, deterministic, and repeatable attack for any operator running Shipit as a shared instance across several tenant orgs.

### Recommendation
Scope `find_or_create_team!` (and any subsequent membership mutation) by both `github_id` and the verified organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and reject/raise if an existing `Team` with that `github_id` has a different `organization` than the one that produced a valid signature for this request. Additionally, pass the verified `repository_owner`/organization from the controller into the handler explicitly rather than trusting `params.organization.login` alone, to close any residual spoofing surface.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub)
test "membership webhook for one org cannot write membership on another org's team" do
  victim_team = shipit_teams(:shopify_developers) # belongs to organization "shopify"
  assert_equal 'shopify', victim_team.organization

  # Attacker's org is "attacker-org", verified/signed independently by webhooks_controller
  params = ExplicitParameters::Params.new(
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'mallory' }
  )

  assert_no_difference -> { Shipit::Team.where(organization: 'attacker-org').count } do
    Shipit::Webhooks::Handlers::MembershipHandler.new(params).process
  end

  mallory = Shipit::User.find_by(login: 'mallory')
  # BROKEN BINDING: victim_team.organization ('shopify') != verified webhook org ('attacker-org')
  # yet membership was written on victim_team:
  assert victim_team.members.include?(mallory)

  if Shipit.github_teams.map(&:id).include?(victim_team.id)
    assert mallory.authorized?
  end
end
```
This demonstrates the equality `Team#organization == verified webhook organization` does not hold after processing, while `Membership`/`authorized?` state changes anyway, confirming the vulnerability.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action

          when 'removed'

        end

        end
