Based on the investigation, the closest reachable analog in ocore to the reported "accounting mapping diverges from real balance, then underflows/goes inconsistent" bug class is in the bundled AA template `test/samples/fundraising_proxy.oscript`, which tracks a single scalar state variable (`total_raised`) as a stand-in for the AA's real committed balance, and decrements it based on an unrestricted, attacker-controlled amount without ever validating it against the amount actually still available/owed — exactly the same root cause pattern as the reported `getEarnings()`/`principalAssetsDeposited` bug (state var diverges from real balance because the update lacks a floor/consistency check).

### Title
Unbounded decrement of `total_raised` state variable allows accounting divergence from real AA balance in fundraising proxy AA template - ([File: test/samples/fundraising_proxy.oscript])

### Summary
The `fundraising_proxy.oscript` AA template tracks all Bytes contributed toward a fundraising target in a single state variable `var['total_raised']`, used to compute whether the fundraising target has been reached (`$missing_amount`, `$bDone`). Any holder of the AA's freely-transferable share asset can trigger the "refund" case, which pays out Bytes 1:1 for shares surrendered and unconditionally executes `var['total_raised'] -= $amount;` with no check that the refunded amount does not exceed what is actually still tracked/available, and no check on the round's status.

### Finding Description
In the "contribute" case, the AA issues `$asset` shares 1:1 to the payment amount and stores the aggregate in `var['total_raised']`: [1](#0-0) 

In the "refund" case, any address can send back shares (`trigger.output[[asset=$asset]]`) — the asset is `is_transferrable: true`, so shares may have moved through multiple hands — and receive Bytes back 1:1, decrementing the same global `total_raised` variable with no lower bound and no status check: [2](#0-1) 

This mirrors the reported bug class exactly: an internal accounting variable (`total_raised`, analogous to `principalAssetsDeposited`) is mutated based on a value supplied via a token/share transfer from an address that is not verified to correspond 1:1 to the state actually recorded for that participant, and the decrement has no floor check. Because `refund` fires purely on `$asset AND trigger.output[[asset=$asset]] > 0` — it does not check `var[$asset || '_status']` — a refund can be processed even after the round has already moved to `'raised'` (funds forwarded to `$destination_aa` in the "contribute" case's `$bDone` branch): [3](#0-2) 

Once the round is `'raised'`, the AA's actual Bytes balance no longer reflects `total_raised` (it was sent out), yet `total_raised` is still decremented by any subsequent refund of leftover, still-circulating shares from before the target was reached, exactly as in the reported vulnerability where a value the AA/vault "thinks" it owes diverges from the real backing balance.

### Impact Explanation
Because `total_raised` directly feeds the `$missing_amount`/`$bDone` computation used by future contributions, and can be driven inconsistent with the actual balance held by the AA (via refunds processed after funds have already been forwarded, or via refunds that are unbounded by any per-contributor cap), the AA's fund-raising completion criterion and payout accounting can be corrupted. This can cause the AA to become insolvent for legitimate remaining refund claims (fund freezing/loss for other contributors) or to mis-trigger forwarding of funds to the destination AA based on a corrupted `total_raised`, an AA fund-loss/freezing scenario reachable by any unprivileged AA trigger sender holding transferable shares.

### Likelihood Explanation
The AA's own `if` condition for the refund case (`$asset AND trigger.output[[asset=$asset]] > 0`) does not gate on round status, and `is_transferrable: true` on the share asset means any address that acquires shares (through the normal market for a freely tradable asset) can trigger the refund path at any time, including after the round has moved to `'raised'`. No privileged role or special access is required — only a legitimate unit posted as an AA trigger with the asset payment, which is the exact "unprivileged AA trigger sender" threat model called out in scope.

### Recommendation
- Gate the "refund" case on the round status (`var[$asset || '_status'] == 'open'`) so refunds cannot be requested once the round is `'raised'`/`'done'`.
- Track contributions and refunds per-contributor (or ensure the aggregate can never be decremented below the amount consistent with the AA's actual remaining Bytes balance) rather than relying on a single unguarded scalar decrement, mirroring the fix recommended in the original report: keep the internal accounting variable consistent with the real balance backing it at all times.

### Proof of Concept
1. Call the AA with `trigger.data.start` to open a new fundraising round; AA defines `$asset` and sets `var[$asset||'_status']='open'`.
2. Contributor A sends `1e5` bytes; AA issues `98000` (`amount - 2000` fee) of `$asset` to A and sets `total_raised = 98000`.
3. Enough further contributions arrive so that `$bDone` becomes true in a later "contribute" call; AA forwards `total_raised` Bytes to `$destination_aa`, sets `var[$asset||'_status']='raised'`. At this point AA's actual base balance backing this round is emptied.
4. Contributor A (who still holds unredeemed shares from step 2, or acquired transferable shares from another holder after step 2) sends those `$asset` shares to the AA via the "refund" case. Because this case does not check `var[$asset||'_status']`, the AA attempts to pay Bytes 1:1 and executes `var['total_raised'] -= $amount`, driving the tracked `total_raised` further out of sync with the AA's actual (already-forwarded) balance, resulting either in payment failure for later legitimate refund claims or in corrupted `total_raised` accounting used by any concurrently-open logic.
