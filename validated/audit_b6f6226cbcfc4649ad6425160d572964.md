### Title
Unverified Token Deposit in `onERC20Received` Allows Registered Token Contract to Drain Bridge ERC20 Balance — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`onERC20Received` is a `public` function intended to be called by a token contract *after* it has transferred tokens to the bridge. However, the bridge performs no balance check to verify that the token contract actually transferred `_value + _feeLimit` tokens before calling `_payERC20FeeAndRefundChange`, which pays out from the bridge's *existing* token balance. A registered token contract that calls `onERC20Received` without transferring any tokens causes the bridge to pay fees and refunds from other users' locked deposits.

---

### Finding Description

The normal 1-step deposit flow is:
1. User calls `token.transferAndCall(bridge, value + feeLimit, data)`
2. Token contract transfers `value + feeLimit` to the bridge
3. Token contract calls `bridge.onERC20Received(from, to, value, feeLimit, extraData)`

`onERC20Received` is `public` with no guard beyond `onlyRegisteredToken(msg.sender)`: [1](#0-0) 

It immediately delegates to `_requestERC20Transfer`, which calls `_payERC20FeeAndRefundChange` before any burn or lock: [2](#0-1) 

`_payERC20FeeAndRefundChange` unconditionally transfers from the bridge's token balance — it has no knowledge of how many tokens arrived in the current call: [3](#0-2) 

There is no reentrancy guard on the ERC20 path (only the KLAY path has `nonReentrant`), and no pre/post balance snapshot to enforce that `_feeLimit` tokens were actually deposited.

Compare with `requestERC20Transfer`, which explicitly pulls `_value + _feeLimit` from the caller before proceeding: [4](#0-3) 

`onERC20Received` has no equivalent pull.

---

### Impact Explanation

A registered token contract that calls `onERC20Received` with `_feeLimit = X` and transfers 0 tokens causes the bridge to:
- Transfer `feeOfERC20[token]` tokens to `feeReceiver` from the bridge's balance, and
- Transfer `_feeLimit - fee` tokens to `_from` (attacker-controlled) from the bridge's balance,

or, if no fee is configured, transfer the full `_feeLimit` to `_from`: [5](#0-4) 

This is an unauthorized transfer of bridged assets (other users' locked funds) directly satisfying the required impact gate.

---

### Likelihood Explanation

The prerequisite is controlling a registered ERC20 token contract. This is a meaningful but realistic condition: the bridge owner registers tokens, but the token contract itself is a separate entity. An upgradeable token contract, a token with a privileged `call` function, or a token that was always malicious but passed initial review can all satisfy this condition without requiring bridge owner keys or validator collusion.

---

### Recommendation

In `onERC20Received`, snapshot the bridge's token balance before and after the call, and require that the increase is at least `_value + _feeLimit`:

```solidity
function onERC20Received(
    address _from, address _to, uint256 _value,
    uint256 _feeLimit, bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(msg.sender).balanceOf(address(this));
    // ... (tokens should already be transferred by the calling token contract)
    uint256 received = IERC20(msg.sender).balanceOf(address(this)).sub(balanceBefore);
    require(received >= _value.add(_feeLimit), "insufficient tokens received");
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, deprecate `onERC20Received` and require all deposits to go through `requestERC20Transfer`, which enforces the pull pattern.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
