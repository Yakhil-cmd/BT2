### Title
Webhook signature is verified against `repository.owner.login`, but the target `Stack`/`Repository` is resolved from `repository.full_name` - allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate `X-Hub-Signature` based on `repository.owner.login` (or `organization.login`), while every event `Handler` resolves the `Stack` it acts on from an entirely different field, `repository.full_name`. Because the HMAC only proves "this body was signed by whichever organization's secret was selected," and the field used to pick that secret is decoupled from the field used to pick which repository/stack gets mutated, an operator who legitimately controls one onboarded organization's `webhook_secret` can forge a webhook that authenticates as their own org but drives write actions (sync, deploy triggering, status/check updates) against a *different* organization's stack.

### Finding Description
`verify_signature` computes `repository_owner` purely from the JSON body: [1](#0-0) 
and uses it to fetch the corresponding `GitHubApp` config and verify the signature: [2](#0-1) 

`GitHubApp#verify_webhook_signature` only proves the raw body was HMAC-signed with the secret configured for `repository_owner`'s organization: [3](#0-2) 

However, once verification passes, every handler determines the affected `Stack` using a *different* field, `repository.full_name`, via `Handler#repository_name` / `#stacks`: [4](#0-3) 

`Repository.from_github_repo_name` splits this string on `/` to find owner+name independently of the `repository.owner.login` field used above: [5](#0-4) 

There is no code anywhere in the controller or `Handler` base class that checks `repository.owner.login == repository.full_name.split('/').first`. Nothing ties the identity used to select/validate the HMAC secret to the identity of the repository that ends up acted upon.

**Binding broken:** `organization authenticated (secret owner used in verify_signature) == organization/repository written (owner segment of full_name used by Handler#stacks)`. Before an attacker's request, these two values are always equal for organically-delivered GitHub webhooks (GitHub itself populates both fields consistently for a real event). After a crafted request, an attacker who knows one organization's `webhook_secret` can set them to different values, so the equality is broken while `verify_signature` still succeeds.

### Impact Explanation
This is a self-hosted, multi-tenant deployment topology: `config/secrets.development.shopify.yml` shows the engine natively supports multiple independent GitHub organizations configured on the same Shipit instance, each with its own `app_id`/`installation_id`/`webhook_secret`: [6](#0-5) 

An organization admin who legitimately onboarded their own org (and therefore knows their own `webhook_secret`, since they generated it when creating their GitHub App) is an unprivileged attacker with respect to any *other* organization's stacks hosted on the same Shipit instance. By POSTing a forged JSON body to the shared `/webhooks` endpoint with:
- `repository.owner.login` = their own org (so `verify_signature` picks their own known secret and succeeds), and
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated stack they do not control),

they can drive `PushHandler#process` to invoke `stack.sync_github(expected_head_sha: ...)` on the victim's stack: [7](#0-6) 

or `StatusHandler#process` to inject arbitrary commit statuses on victim commits: [8](#0-7) 

or `CheckSuiteHandler#process` to force check-run refreshes on victim commits: [9](#0-8) 

Forcing fabricated `status` events (e.g. marking CI as green) directly influences `deployable?`/CI-gating logic used by continuous delivery, which can enable an unauthorized deploy on a stack the attacker has no permission over — a cross-repository write / unauthorized-deploy class impact.

### Likelihood Explanation
Requires only that the attacker be a legitimate operator of some organization already onboarded to the shared Shipit instance (a realistic, unprivileged-relative-to-other-tenants position in any multi-org deployment) plus knowledge of the raw JSON+HMAC webhook protocol, which is publicly documented GitHub webhook behavior. No `ApiClient` token, `webhook_secret` of the victim org, session, or GitHub write access to the victim repo is needed — only the attacker's own org's `webhook_secret`, which they possess by construction. This is directly reachable through the unauthenticated public `/webhooks` route with no additional privilege escalation.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), require that the organization used to select/verify the webhook secret matches the owner segment of `repository.full_name` (and/or `organization.login`) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, bind handler-resolved repositories strictly to the same `repository.owner.login`/`organization.login` value that was used for signature verification, rather than independently re-parsing `full_name`.

### Proof of Concept
1. Attacker controls Organization "attacker-org" on a shared Shipit instance and knows its `webhook_secret` (e.g. `s3cr3t`), used in `Shipit.github(organization: 'attacker-org')`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(s3cr3t, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"` (from `repository.owner.login`), fetches `attacker-org`'s config, and verification succeeds because the attacker correctly signed the body with `attacker-org`'s known secret: [2](#0-1) 
5. `PushHandler` is invoked; `Handler#repository_name` reads `repository.full_name = "victim-org/victim-repo"`, resolves the victim's `Stack`s, and calls `stack.sync_github(...)` on them — a write against a repository the attacker never authenticated for: [4](#0-3) [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
