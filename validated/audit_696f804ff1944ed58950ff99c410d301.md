### Title
CCMenu token minted for one stack authorizes reads of any stack's CCMenu XML - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::CCMenuUrlController#client` creates the `ApiClient` used to mint a CCMenu token without binding it to the requested stack (`stack: stack` is never passed), so `ApiClient#stack_id` is always `nil` for these tokens. Independently, `Shipit::Api::CCMenuController` overrides the inherited `stack` accessor to resolve the target stack via `Stack.from_param!(params[:stack_id])` directly instead of the stack-scoped `stacks` collection, so even a properly stack-scoped `ApiClient` would not be restricted. The combination means a CCMenu token minted for stack A works unmodified against `/api/stacks/:stackB/cc_menu.xml?token=...`.

### Finding Description
Broken binding: `current_api_client.stack_id` should equal `stack.id` for the single stack the CCMenu URL was minted for; instead `current_api_client.stack_id` is `nil` (unrestricted) and is never consulted by the endpoint at all.

Path:
1. Any logged-in user with `current_user` visits `GET /stacks/:owner/:repo/:env/cc_menu_url`, hitting `Shipit::CCMenuUrlController#fetch` [1](#0-0) .
2. `client` calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with no `stack:` key, so `stack_id` is `nil` [2](#0-1) .
3. `client.authentication_token` signs only the client `id` via `SimpleMessageVerifier` over `Shipit.api_clients_secret` [3](#0-2) ; the token carries no stack information.
4. That token is reused against `Shipit::Api::CCMenuController#show` for an arbitrary stack B. Authentication resolves `@current_api_client = ApiClient.authenticate(params[:token])` [4](#0-3) . Authorization is `require_permission :read, :stack`, which only checks `permissions.include?('read:stack')` [5](#0-4)  — it never compares `stack_id` to the requested stack.
5. `CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly [6](#0-5) , bypassing `BaseController#stacks`, which is the only place that would have filtered by `current_api_client.stack_id` [7](#0-6) .

Both defects compound: even fixing `create_with(stack: stack, ...)` in `CCMenuUrlController` would not stop cross-stack reuse, because `CCMenuController#stack` never consults the scoped `stacks` collection at all. The `require_permission` guard and `authenticate_api_client` guard both pass, since they check only permission-name membership and token signature validity, not stack identity.

### Impact Explanation
An unprivileged, logged-in user who can view the CCMenu URL for any one stack they can access obtains a long-lived, unscoped bearer token good for `read:stack` on every stack in the installation, including stacks they have no visibility into. This is a cross-tenant unauthorized read of stack state (build/deploy status via `show` -> `deploys_and_rollbacks.last`), matching the "High - unauthenticated/unauthorized read of stack state" category. The token is reusable indefinitely (it's just a signed client id, not stack-scoped, and the `ApiClient` record persists via `find_or_create_by!`), so the exposure is repeatable against arbitrary stacks by simply changing `:stack_id` in the URL.

### Likelihood Explanation
Preconditions are minimal: any authenticated Shipit user with access to the CCMenu URL feature for at least one stack. No GitHub secrets, team membership, or Shipit operator role is required. The attack is a single authenticated GET followed by reuse of the returned token against a different stack's public XML endpoint — trivial to execute and fully repeatable.

### Recommendation
1. Scope the `ApiClient` to the specific stack when minting the CCMenu token: `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`.
2. Fix `Shipit::Api::CCMenuController` to resolve `stack` through the inherited, client-scoped `stacks` collection (remove the local override, or have it call `stacks.from_param!(params[:stack_id])`), and add an explicit check that `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a ccmenu token minted for one stack cannot read another stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # any other fixture stack

  client = Shipit::ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'CCMenu Client',
    permissions: %w[read:stack],
    stack: stack_a, # binding this test asserts SHOULD restrict scope
  )

  assert_equal stack_a.id, client.stack_id

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: current_api_client.stack_id (stack_a.id) must equal
  # the requested stack.id (stack_b.id) for access to be granted.
  assert_response :forbidden # currently fails: request succeeds (200) proving the bypass
end
```
This demonstrates both defects: (a) production code never sets `stack:` when creating the CCMenu client, so `stack_id` is always `nil`; and (b) even when `stack_id` is explicitly set as above, `CCMenuController#stack`'s use of `Stack.from_param!` instead of the scoped `stacks` collection means the request still succeeds for `stack_b`, confirming the broken binding on both sides.
