### Title
Permanent market freeze via i128 overflow in RAY-scaled debt valuation during accrual - (File: contracts/pool/src/cache/scale.rs)

### Summary
Analogous to CVE-2018-20847 (integer overflow from improper intermediate computation), XOXNO Lending computes the RAY-scaled total debt value as `borrowed_shares * borrow_index / RAY` inside `Cache::calculate_utilization` (`contracts/pool/src/cache/scale.rs:23`) via `scaled_to_original` → `Ray::mul` → `mul_div_half_up` (`common/src/rates/scaling.rs:14`, `common/src/math/fp.rs:50`). When the true debt value exceeds what fits in `i128`, the multiply-divide cannot represent the result and panics with `MathOverflow` — even through the exact `I256` widened path, because the *result* does not fit `i128`. This overflow happens *before* the `MAX_BORROW_INDEX_RAY` index cap can engage, and because `global_sync`/`accrue_chunk` (`contracts/pool/src/interest.rs:20-53`) runs at the head of every state-changing entrypoint, the whole market deadlocks.

### Finding Description
- `Cache::calculate_utilization` evaluates `scaled_to_original(self.borrowed, self.borrow_index)` = `borrowed * borrow_index / RAY` (`contracts/pool/src/cache/scale.rs:19-27`).
- `accrue_step` (called from `accrue_chunk`, `contracts/pool/src/interest.rs:39-53`) performs the same valuation to grow indexes and book revenue.
- Both use `mul_div_half_up`/`mul_div_floor` in `common/src/math/fp_core.rs:108-175`, which panic with `GenericError::MathOverflow` when the quotient exceeds `i128::MAX` (`to_i128()` returns `None`).
- `global_sync` is invoked by every pool verb, so once debt value crosses the ceiling, `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, and even the permissionless `update_indexes` all revert on the same panic.
- The repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-362`) demonstrates this: after sustained ~98% utilization on a large 18-decimals market, `try_update_indexes_for` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw`/`repay` also fail. The index ceiling in `common/src/constants/pool.rs` never protects because the value-overflow trips first.

### Impact Explanation
Permanent freezing of funds: all supplier principal and accrued yield in the affected market becomes unrecoverable, and borrowers cannot repay or be liquidated (bad debt can never be settled). The market is bricked with no admin escape, since `recapitalize`/`clean_bad_debt` also accrue first. This is not a fail-closed oracle guard — it is a deterministic arithmetic deadlock reachable purely through normal protocol use.

### Likelihood Explanation
Low-to-moderate. An unprivileged actor must push a market's aggregate RAY-valued debt past `i128::MAX / RAY ≈ 1.7e11` whole tokens, requiring either a whale-scale position (caps can be lifted by governance; nothing bounds cumulative debt value itself) or many years of compounding at high utilization — but no privileged action, no oracle manipulation, and no bug beyond the documented arithmetic domain is needed. The in-repo test proves the path executes exactly as described using only `supply`, `borrow`, and time.

### Recommendation
Bound the aggregate rather than the value: enforce `borrowed_shares * borrow_index` headroom explicitly, e.g., clamp `borrow_index` at `MAX_BORROW_INDEX_RAY` *and* cap total scaled debt issuance in `borrow`/`flash_position` so that `scaled_to_original(borrowed, MAX_BORROW_INDEX_RAY)` stays below `i128::MAX`. Alternatively make `global_sync`/`calculate_utilization` saturate (like `calculate_scaled_cap`'s `mul_div_floor_saturating` in `common/src/rates/scaling.rs:26-33`) so accrual degrades instead of deadlocking every entrypoint.

### Proof of Concept
Using only unprivileged calls (mirroring the existing test):

1. `supply(victim_whale, BIG18_market, ~1e9 * 10^18)` — mints supply shares near the RAY ceiling after caps are raised (caps are governance-settable and not part of the arithmetic bound).
2. `borrow(attacker, BIG18_market, ~98% of supply)` against any collateral market — sets `borrowed` scaled shares near the representable limit.
3. Advance ledger time while utilization stays on the steep curve segment; each permissionless `update_indexes` compounds `borrow_index`.
4. Once `borrowed * borrow_index / RAY > i128::MAX`, `accrue_step`/`calculate_utilization` panics with `MathOverflow`. From then on:
   - `update_indexes` → reverts
   - `withdraw`, `repay`, `liquidate`, `supply`, `borrow`, `clean_bad_debt`, `recapitalize` → all revert, since `global_sync` runs first.
   
   Result: permanent freeze of all supplier funds and unclaimable yield in that market, exactly as asserted in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:343-356`.
