### Title
Cross-repository status forgery flips `UndeployedCommit#deploy_disallowed?` to false via unscoped `Commit.where(sha:)` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` applies an incoming GitHub `status` webhook to **every** `Commit` row across the entire database that shares the reported `sha`, without checking that the commit's `stack`/repository matches the webhook's originating repository. Since `UndeployedCommit#deploy_disallowed?` is a thin negation of `Commit#deployable?` and `Stack#deployable?`, any repository whose genuine webhook can reach Shipit can flip `deploy_disallowed?` to `false` for an identical-sha commit that lives under a completely different, victim stack, causing an operator-facing "Deploy" control to appear enabled for code that never passed CI in its own repository.

### Finding Description
The binding that should hold is: `deploy_disallowed? == true` whenever the *victim stack's own repository* has not reported a successful status for that commit, i.e. `deploy_disallowed?` must depend only on statuses attributable to `commit.stack.repository`. Instead:

- `UndeployedCommit#deploy_disallowed?` at [4](#0-3)  is `!deployable? || !stack.deployable?`, and `Commit#deployable?` at [5](#0-4)  is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, which is driven entirely by `status` built from the commit's own `statuses` association.
- `StatusHandler#process` writes those statuses without any repository check: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` at [1](#0-0) .
- `Commit` has no validation or index tying `sha` uniqueness to a repository/stack — `belongs_to :stack` only, no scoped uniqueness on `sha` [6](#0-5) . Different stacks legitimately can (and, via forks/cherry-picks, commonly do) contain `Commit` rows with identical `sha` values because git commit hashes are content-addressed and repository-independent.
- Compare this to `CheckSuiteHandler`, which correctly scopes lookups to the specific repository via `stacks` (`Repository.from_github_repo_name(repository_name)`) before matching by `head_sha` [2](#0-1) . `StatusHandler` has no equivalent guard.

`WebhooksController#verify_signature` only proves the payload was genuinely sent by GitHub for the organization named in the payload's own `repository.owner.login` [7](#0-6)  — it says nothing about which `sha`s the sender is authorized to influence. Once a real, validly-signed `status` webhook (from any repo whose org has a Shipit GitHub App installed) reports `state: success` for a `sha`, that update is applied to any and all `Commit` rows sharing that sha, including ones belonging to a victim's stack in an unrelated repository, as long as the attacker can produce a commit with an identical sha (e.g., by pushing/forking the exact same tree/parent/author/message combination, which is trivial if the victim commit is public).

Exploit flow:
1. Attacker identifies a target commit `sha` in the victim's public repository (visible via the victim stack's commit list).
2. Attacker recreates or forks that identical commit into a repository they control that is connected to the same Shipit instance (any org with the app installed).
3. Attacker triggers (or fakes via their own CI) a `status` event with `state: success` for that `sha`; GitHub signs and delivers it, `verify_signature` passes because it's genuinely from the attacker's own authorized org.
4. `StatusHandler#process` updates **all** `Commit` rows with that `sha`, including the victim's, via `commit.create_status_from_github!(params)`.
5. `Commit#deployable?` becomes true for the victim commit, so `UndeployedCommit#deploy_disallowed?` becomes false, and the Deploy control renders as enabled in the victim stack's UI/API despite no CI success in the victim's own repository.

### Impact Explanation
This is a record-mutation-across-tenants bug: a payload legitimately originating from one (attacker-controlled) repository mutates `Status` records and thus `deployable?`/`deploy_disallowed?` state belonging to a completely unrelated victim stack/commit. It directly sets up an unauthorized deploy: a misled but legitimate operator, seeing the Deploy control enabled, can trigger `stack.trigger_deploy` on code that never passed CI in its own repository. This matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The blast radius extends to any stack hosted on the same Shipit instance, and is repeatable for any sha the attacker can reconstruct.

### Likelihood Explanation
Preconditions: the attacker needs write/push access to some repository whose owning GitHub org already has the Shipit GitHub App installed (so their webhooks reach the instance) — this is commonly true for any org member or any repo under an org that installs the app at the org level, or in cases of open-source Shipit setups. No Shipit session, API token, or secret is required; the attacker relies entirely on GitHub delivering their own genuinely-signed webhook. Reconstructing an identical `sha` is straightforward given a public target commit (git hashes are reproducible from the same tree/parent/author/committer/timestamp/message). This is a low-cost, repeatable attack limited mainly by needing a connected-but-attacker-controlled repository.

### Recommendation
Scope `StatusHandler#process` to the reporting repository the same way `CheckSuiteHandler` does: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and only update commits within `stack.commits.where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

test "#deploy_disallowed? is not affected by a status webhook for a same-sha commit in another stack" do
  victim_commit = shipit_commits(:cyclimse_first)
  attacker_stack = shipit_stacks(:shipit) # a different, unrelated stack
  # Simulate an attacker-owned commit with an identical sha in a different stack
  attacker_commit = Commit.create!(stack: attacker_stack, sha: victim_commit.sha, message: 'forged')

  undeployed = UndeployedCommit.new(victim_commit, index: 0)
  # Precondition: victim commit has no successful status of its own
  victim_commit.statuses.destroy_all
  assert_predicate undeployed, :deploy_disallowed?

  # Attacker's genuinely-signed webhook (any repository) reports success for the shared sha
  Shipit::Webhooks::Handlers::StatusHandler.call(
    'sha' => attacker_commit.sha,
    'state' => 'success',
    'context' => 'ci/travis'
  )

  # Binding check: deploy_disallowed? must remain true because the victim's own repo never reported success
  refute victim_commit.reload.deployable?, "victim commit should not be deployable from a foreign repo's status"
  refute undeployed.deploy_disallowed? == false, "deploy_disallowed? must not flip false from a cross-repo webhook"
end
