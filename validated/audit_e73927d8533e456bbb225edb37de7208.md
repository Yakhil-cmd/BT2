### Title
Webhook HMAC verification org is chosen from `repository.owner.login`, but repository mutation uses unrelated `repository.full_name` — cross-tenant stack/PR mutation with a foreign org's valid signature - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check via `Shipit.github(organization: repository_owner)` where `repository_owner` comes from the *unverified* `params.dig('repository','owner','login')`. Every `PullRequest` handler (`Handler#stacks`/`#repository_name`, and each handler's private `repository` method) instead resolves the target `Repository` from the separate, independently-controlled `payload.dig('repository','full_name')` field. Because nothing ties `owner.login` to `full_name`, an attacker who controls a Shipit-registered organization's `webhook_secret` (i.e. legitimately owns an org already onboarded in Shipit) can sign a payload as their own org while setting `full_name` to a different, victim organization's repository, causing the handler to mutate the victim org's `Repository`/`ReviewStack` rows.

### Finding Description
Binding that should hold: `organization_that_signed(payload) == organization_owning(Repository.from_github_repo_name(payload['repository']['full_name']))`.

Code path:
- `verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and verifies the signature against that org's `webhook_secret`.
- `repository_owner` is defined purely from the raw, unauthenticated JSON body: [2](#0-1) .
- After verification passes, `WebhooksController#create` dispatches the same raw `params` hash to handlers [3](#0-2) .
- Every `PullRequest` handler resolves the actual mutated `Repository`/stack scope from `payload.dig('repository', 'full_name')`, e.g. `Handler#stacks`/`#repository_name` [4](#0-3)  and `OpenedHandler#repository` [5](#0-4) .
- `Repository.from_github_repo_name` simply splits the `full_name` string it is given and does a DB lookup — it has no relationship to whatever value was used for signature verification: [6](#0-5) .

Root cause: `owner.login` (used to pick the verifying secret) and `full_name` (used to pick the mutated row) are two independent JSON fields inside the same attacker-supplied, unsigned body. Nothing enforces `full_name.start_with?("#{owner.login}/")`. Since `Shipit.github(organization:)` resolves strictly from Shipit's own static `secrets.github` config (`github_app_config`) [7](#0-6) , and each configured organization's `webhook_secret` is set up by that organization's own administrator when they wire up the GitHub webhook for their org, an attacker who administers *their own* legitimately-onboarded Shipit organization ("org A") knows org A's `webhook_secret` (they configured it) and can produce a valid `X-Hub-Signature` for org A per `GitHubApp#verify_webhook_signature` [8](#0-7) .

Exploit flow:
1. Attacker administers org A, onboarded into Shipit with its own `webhook_secret`.
2. Attacker crafts a `pull_request` webhook JSON body with `repository.owner.login = "org-a"` and `repository.full_name = "org-b/victim-repo"` (a real repo/stack belonging to a different, victim-owned org B in the Shipit DB), plus a valid `pull_request`/`sender`/`labels` substructure.
3. Attacker signs the raw body with org A's `webhook_secret` and POSTs to `/webhooks` with header `X-Github-Event: pull_request`.
4. `verify_signature` computes `repository_owner = "org-a"`, verifies against org A's secret — passes.
5. `WebhooksController#create` dispatches to `PullRequest::OpenedHandler` (or `ClosedHandler`/`LabeledHandler`/etc.), which resolves `repository` from `full_name = "org-b/victim-repo"`, finding the real `Shipit::Repository` for org B, and mutates/creates/closes a `ReviewStack` under org B using org A's valid signature.

Existing guards fail to prevent this: `verify_signature` never compares `repository_owner` to the owner segment embedded in `full_name`; `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schemas only validate presence/type of fields, not cross-field consistency with the org that signed the request; `Repository.from_github_repo_name` performs no ownership/tenant check beyond the string it's given.

### Impact Explanation
An attacker who has legitimately onboarded (or compromised) one Shipit-registered organization can forge review-stack lifecycle events (open/close/label/unlabel/reopen/assign/edit a PR) against any *other* organization's repository/stack known to Shipit, as long as that repository's `full_name` is guessed or publicly known (trivial — it's a public GitHub repo name). This can create or destroy `ReviewStack` rows, toggle provisioning labels, and affect deploy/provisioning behavior for a tenant that never authorized org A's traffic — this is a cross-tenant stack mutation using another party's identity, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is fully repeatable per request against any repository/organization pair configured in Shipit.

### Likelihood Explanation
Preconditions: Shipit must be configured in multi-organization mode (`secrets.github` keyed by multiple organizations, each with its own `webhook_secret`) — the single-org legacy mode collapses `repository_owner` handling since `github_default_organization` becomes `nil` and a single shared secret is used, which is a different scenario. Given multi-org mode, the attacker needs no special privilege beyond legitimately controlling one onboarded organization's webhook secret (which they know because they configured it on the GitHub side). Cost is a single crafted HTTP POST with correct HMAC — no GitHub interaction required, no session, no API token. This is realistically feasible in any Shipit deployment that serves more than one GitHub organization, which is the model the config supports (`Shipit.github_organizations`, `github_app_config`).

### Recommendation
In `verify_signature`, after computing `repository_owner`, also derive the owner segment from `params.dig('repository','full_name')` and require them to match (case-insensitively) before verifying the signature; alternatively, have every handler resolve the `Repository` and confirm `repository.owner == repository_owner` used during signature verification, rejecting (or treating as `NullRepository`) any payload where the two diverge.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
```ruby
test "#create rejects/does not mutate a repository owned by a different org than the one that signed the webhook" do
  org_a_secret = Shipit.github(organization: 'org-a') # configured secret for attacker's own org
  victim_repo = shipit_repositories(:some_repo_owned_by_org_b) # full_name => "org-b/victim-repo"

  payload = {
    action: 'opened',
    number: 1,
    pull_request: { id: 1, number: 1, url: 'x', title: 't', state: 'open',
                     additions: 1, deletions: 0,
                     head: { sha: 'a' * 40, ref: 'feature' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { owner: { login: 'org-a' }, full_name: victim_repo.full_name },
    sender: { login: 'attacker' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_secret_value, payload)

  assert_no_difference -> { victim_repo.review_stacks.count } do
    post shipit.webhooks_path, params: payload,
      headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => signature,
                 'Content-Type' => 'application/json' }
  end
end
```
Assert both sides of the binding: `repository_owner` used in `verify_signature` ("org-a") must equal the actual owner of `Repository.from_github_repo_name(payload['repository']['full_name'])` ("org-b") for the mutation to be legitimate — the test demonstrates they diverge and a review stack is nonetheless created/mutated under org B.
