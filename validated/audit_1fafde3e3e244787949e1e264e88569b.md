### Title
`StatusHandler` writes GitHub commit statuses to any commit with a matching SHA, ignoring the repository/organization the webhook signature actually authenticated - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub `status` webhook against the GitHub App configured for the organization named in the payload (`repository.owner.login`, falling back to `organization.login`) [1](#0-0) . Once the signature is accepted, the payload is dispatched to `StatusHandler`, which resolves the target `Commit` **purely by SHA**, with no check that the commit belongs to a stack under the repository/organization that produced the signature [2](#0-1) .

This breaks the equality the deployment trust model is supposed to enforce:

`organization authenticated by HMAC signature == organization whose commit/stack state is mutated`

Here the left side is `repository.owner.login` (or `organization.login`) from the signed payload, and the right side is *every* `Commit` row across the whole Shipit instance whose `sha` column happens to equal `params.sha` — an attacker-influenced, cross-tenant value.

### Finding Description
- `verify_signature` in `WebhooksController` selects a `GithubApp`/secret using `repository_owner` (derived from the payload itself) and verifies the raw body HMAC against that org's `webhook_secret` [3](#0-2) . This proves the request really came from GitHub for **that** organization's App installation — nothing more.
- `Handler#stacks` (the base class used by most handlers) correctly scopes work to `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository','full_name')` [4](#0-3) .
- `StatusHandler`, however, does **not** call `stacks` at all. It looks up commits globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . Since `sha` is a git object hash and identical commits (e.g., shared upstream history between forks, or vendored/mirrored repositories) can exist verbatim in multiple, unrelated repositories tracked by the same Shipit instance, this lookup is not scoped to the organization/repository that the signature authenticated.
- The `status` event and payload fields (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`) are exactly what `StatusHandler.params` accepts, and none of them are cross-checked against the authenticated `repository.full_name` [5](#0-4) .

Concretely: the HMAC signature proves "this JSON blob came from GitHub for OrgA's installation," but the code then acts on "any `Commit` row in the database whose `sha` matches," which can belong to OrgB's stack — a repository OrgA's webhook secret was never meant to authorize writes to.

### Impact Explanation
A commit status write is not cosmetic in Shipit: statuses feed `Status::Group`/`commit_checks` and are used to gate whether a commit is deployable (checks controller, `commit_checks.rb`). Being able to inject a forged `success` status onto a specific commit inside a *different* organization's stack can flip that commit's check state to green, enabling that commit to satisfy Shipit's deploy gating for a repository the attacker has no legitimate relationship to — an unauthorized-deploy-adjacent state corruption via a trust boundary the signature was supposed to enforce. This matches the "Critical: unauthorized deploy" impact bucket in that it lets an attacker who is only authorized for OrgA's webhook manipulate deploy-relevant state for OrgB.

### Likelihood Explanation
Exploitation requires: (1) attacker has legitimate write access to at least one repository whose organization has the Shipit GitHub App installed (so they can trigger a real, correctly-signed `status` webhook via the standard GitHub Statuses API), and (2) a SHA collision between a commit in the attacker's own repo and a commit tracked in the victim stack. Git SHAs are content-addressed, so shared history (forks of the same upstream, vendored copies, monorepo splits, template-based repos) makes such collisions realistic and discoverable by an attacker inspecting public commit history — no cryptographic collision is needed, only overlapping ancestry. This is a real, if narrower-than-arbitrary, likelihood: it is not "any attacker can hit any commit," but it is a genuine cross-tenant boundary break reachable without any Shipit session, `ApiClient` token, or privileged account — only ordinary write access to *some* onboarded repository.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository authenticated by the webhook, not just by `sha`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
i.e., reuse the `Handler#stacks`/`repository_name` scoping (already present in the base class and used by `PushHandler`) so that the organization the signature authenticated is the same organization whose commit state can be mutated.

### Proof of Concept
1. Organization `victim-org` has repository `victim-org/app` onboarded to Shipit, with commit `abcd…` (real SHA) tracked as a `Shipit::Commit` in its stack.
2. Attacker controls organization `attacker-org` with repository `attacker-org/fork`, which shares ancestor history with `victim-org/app` (e.g., both forked from the same public upstream, or `attacker-org/fork` intentionally created to contain commit `abcd…`, e.g. by cherry-picking/rebasing the exact tree+parents so git computes the identical SHA), and `attacker-org` also has the Shipit GitHub App installed with its own `webhook_secret`.
3. Attacker, using ordinary repo write access to `attacker-org/fork` (no Shipit account, no `ApiClient` token), calls GitHub's Create Commit Status API for SHA `abcd…` with `state: success`.
4. GitHub sends a `status` webhook to Shipit, correctly signed with `attacker-org`'s `webhook_secret`. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s app config, and verification succeeds [6](#0-5) .
5. `StatusHandler.call(params)` runs `Commit.where(sha: "abcd…")`, which matches the `victim-org/app` commit row, and calls `commit.create_status_from_github!(params)` on it [7](#0-6) , writing an attacker-controlled `success` status onto a commit belonging to an organization the attacker was never authenticated for.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
