### Title
Webhook signature is verified against the org derived from `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field, letting any onboarded org's webhook secret be used to forge events for a *different* org's repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The reported bug class is "a value used for one calculation/verification diverges from the value actually acted upon, breaking an implicit invariant that both refer to the same thing." In Shipit's webhook pipeline, the field used to pick *which org's secret verifies the HMAC signature* (`repository.owner.login`, falling back to `organization.login`) is a different JSON field than the one handlers use to determine *which repository/stack is actually written to* (`repository.full_name`). Both fields live in the same attacker-supplied JSON body but are never cross-checked against each other.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/org config used to verify `X-Hub-Signature` based on a value taken straight from the unauthenticated request body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once verified, the raw body is re-parsed and dispatched to handlers unchanged: [3](#0-2) 

Every stock handler resolves the affected repository/stack using a **different** field of that same body: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` (used to select the verification secret) and `repository.full_name` (used to select the repository/stack that will be mutated) are independent, attacker-controlled JSON keys inside the same signed body. `Shipit.github(organization: ...)` supports multiple independently configured orgs, each with its own `webhook_secret`, as shown in the multi-org secrets template: [5](#0-4) 

Because the webhook secret used for verification is looked up by `repository.owner.login`/`organization.login` and not cross-validated against `repository.full_name`, an attacker who legitimately controls one onboarded org (and therefore knows that org's `webhook_secret`, e.g. because they configured their own GitHub App integration on the shared multi-tenant Shipit instance) can submit a payload where:
- `repository.owner.login` (or `organization.login`) = their own org (`"attacker-org"`) → signature verification succeeds using their own secret.
- `repository.full_name` = `"victim-org/victim-repo"` → the handler resolves and mutates the *victim's* `Repository`/`Stack`.

This breaks the implicit binding: `organization authenticated by signature == organization of repository the handler writes to`.

### Impact Explanation
This is a genuine cross-tenant confused-deputy: the attacker never needs the victim org's `webhook_secret`, GitHub App private key, or any Shipit credentials — only knowledge of a secret for *any* org configured on the shared instance. Depending on which event type is forged, an attacker can:
- Forge `status`/`check_suite` events for the victim's commits (handled the same way, via `Handler#stacks`/`repository_name`), marking otherwise-failing commits as passing CI. Since Shipit gates deploys and the merge queue on stored commit statuses (`required_statuses`, `merge_request_required_statuses` in `app/models/shipit/deploy_spec.rb`), this can let an attacker unlock deploys or auto-merges on a repository they don't own — an unauthorized deploy/merge.
- Forge `pull_request` events (open/close/label) that create `PullRequest`/`Stack` records or trigger review-stack provisioning for the victim repository (`OpenedHandler`), causing cross-repository writes on a tenant the attacker does not control.
- Forge `push`/`membership` events that enqueue sync jobs or alter team/user membership tied to the victim's repository.

These fall squarely under the specified Critical ("cross-repository writes", "unauthorized deploy, rollback or merge") and High ("escalation into authorization" via forged CI status) impact categories.

### Likelihood Explanation
Requires only that the shared Shipit instance be configured for more than one GitHub organization (a documented, supported configuration pattern per `config/secrets.development.shopify.yml`), and that the attacker legitimately administers one of those orgs (and thus its `webhook_secret`) — no privileged Shipit credential, GitHub App private key, or victim-side secret is needed. This is a realistic deployment scenario for any Shipit instance shared across multiple orgs/teams.

### Recommendation
After verifying the HMAC signature with the org resolved from `repository.owner.login`/`organization.login`, require that the *same* value equals the owner segment of `repository.full_name` (and `organization.login`, when both are present) before dispatching to handlers. Reject the webhook (422) on any mismatch. Alternatively, resolve and pass a single, already-verified "authenticated organization" value into every handler and have `Handler#repository_name`/`stacks` refuse to act on any repository whose owner does not match it.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is configured on the shared Shipit instance with its own GitHub App and knows `webhook_secret_attacker`.
2. Attacker crafts a `status` (or `pull_request`) webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_attacker, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s `GitHubApp`, and successfully verifies the signature against `webhook_secret_attacker`.
5. The event is dispatched to the `status` handler, which resolves the target stack via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` and records the forged `success` status against the victim commit, independent of which org's secret validated the request.
