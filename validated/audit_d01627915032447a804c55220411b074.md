### Title
Missing bridge route validation in `send_token`/`send_token_v2` permits token burn for non-existent (source, target) chain routes, permanently locking user funds - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
The Futaba report flags `Gateway.query()` for accepting unvalidated `dstChainId`, `height`, `slot`, and `message` fields that are later relied upon for cross-chain execution. The Sui native bridge's `send_token`/`send_token_v2` entrypoints exhibit the same root cause: they validate that `target_chain` is a member of the known chain-id enum, but never validate that the concrete `(source_chain, target_chain)` pair is a registered bridge route, even though the bridge module already implements exactly that check (`chain_ids::is_valid_route` / `chain_ids::get_route`) and uses it in unit tests and documentation as the intended guard.

### Finding Description
`send_token<T>` and `send_token_v2<T>` accept a caller-supplied `target_chain: u8` from any unprivileged Sui user: [1](#0-0) 

The only validations performed are `target_address.length() == EVM_ADDRESS_LENGTH` and `token_amount > 0`: [2](#0-1) 

`target_chain` itself is only checked for membership in the enumerated chain IDs (0,1,2,10,11,12) via `chain_ids::assert_valid_chain_id`, invoked deep inside `message::create_token_bridge_message`: [3](#0-2) 

Crucially, `assert_valid_chain_id` only checks that the id is *one of the six known ids*, not that `(inner.chain_id, target_chain)` is a *legitimate route*: [4](#0-3) 

The module defines a separate, stricter concept — `valid_routes()` / `is_valid_route()` / `get_route()` — that only allows specific SUI↔ETH pairs (e.g. `SUI_MAINNET↔ETH_MAINNET`, `SUI_TESTNET↔ETH_SEPOLIA`, etc.), explicitly excluding same-network or mismatched pairs such as `SUI_MAINNET→SUI_TESTNET`: [5](#0-4) 

This `is_valid_route` check exists and is exercised in tests, but it is **not called from `send_token`/`send_token_v2`**. Consequently, a caller on a bridge instance with `inner.chain_id == SUI_MAINNET` can call `send_token(bridge, SUI_TESTNET, target_address, coin, ctx)` — `SUI_TESTNET` passes `assert_valid_chain_id` even though `(SUI_MAINNET, SUI_TESTNET)` is not in `valid_routes()`. The function proceeds to burn the user's coin via `inner.send_token_internal(...)` and record a pending `BridgeRecord` before any route legitimacy is verified: [6](#0-5) 

`approve_token_transfer`, the entrypoint used by the off-chain committee to attach signatures, likewise never re-validates the route — it only checks that either the source or target chain equals the local `inner.chain_id`: [7](#0-6) 

Because the coin was already burned at `send_token` time (irreversibly, since `treasury.burn` destroys the `Coin<T>` before any committee approval), a request built against a non-existent route has no honest completion path: no real-world relayer/oracle infrastructure is defined for a Sui→Sui "route," so the committee will never legitimately sign and approve such a message, and the tokens can never be re-minted on any destination chain.

### Impact Explanation
This falls under the “permanent fund lock” bounty category (High/Medium tier) explicitly listed in scope: an ordinary unprivileged Sui token holder can invoke a public entrypoint (`send_token`) and have their `Coin<T>` irreversibly burned by the bridge treasury for a `target_chain` value that the protocol's own route table (`chain_ids::valid_routes`) does not recognize as valid. There is no on-chain path back to minting/claiming the coin, since `claim_token`/`claim_and_transfer_token` require a signed `BridgeMessage`+committee approval that will never occur for an invalid route in practice. The root cause is functionally identical to the reported issue: unvalidated fields (`dstChainId`-equivalent `target_chain`) are accepted and immediately drive an irreversible state transition before deeper protocol-level validation.

### Likelihood Explanation
Likelihood is high for accidental fund loss (a wrong `target_chain` argument from a wallet/dApp bug or user typo, e.g. passing `1` instead of `11`) and moderate as a deliberate attack surface for griefing token holders via a malicious front-end/dApp that intentionally submits an "invalid-but-enum-valid" chain id, since the call requires no special privileges — any coin holder with a valid `Coin<T>` registered with the bridge treasury can trigger it. The vulnerable code (`send_token`/`send_token_v2`) is a `public fun` reachable directly from a PTB by any unprivileged caller.

### Recommendation
Add an explicit route check in `send_token` and `send_token_v2` before burning tokens, mirroring the existing `chain_ids::get_route`/`is_valid_route` primitive that already exists in the same module:
```move
assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);
```
This should be placed before `inner.send_token_internal(...)` is invoked, i.e., before the coin is burned, so an invalid route aborts the transaction atomically rather than leaving state corrupted after an irreversible burn.

### Proof of Concept
1. Assume a deployed `Bridge` shared object with `inner.chain_id == chain_ids::sui_mainnet()` (0).
2. An unprivileged holder of `Coin<T>` (where `T` is registered with the bridge treasury) calls:
   ```move
   bridge::send_token<T>(&mut bridge, chain_ids::sui_testnet(), target_address_bytes, my_coin, ctx);
   ```
   `chain_ids::sui_testnet()` (1) passes `chain_ids::assert_valid_chain_id` (it is one of the six enumerated ids) inside `message::create_token_bridge_message`, so no abort occurs.
3. `send_token` proceeds to call `inner.send_token_internal(target_chain, token, message)`, which burns `my_coin` via the bridge treasury and stores a pending `BridgeRecord` keyed by `(source_chain=SUI_MAINNET, message_type=token, seq_num)`.
4. `(SUI_MAINNET, SUI_TESTNET)` is not present in `chain_ids::valid_routes()`, so no legitimate bridge committee/relayer infrastructure exists to sign and approve this message via `approve_token_transfer`, and no destination chain will ever mint/settle it.
5. The user's coin is permanently lost with no on-chain recovery path — confirmed by inspecting `claim_token`/`claim_and_transfer_token`, which require a valid signed `BridgeMessage` for the corresponding route that can never legitimately be produced.

Note: I was not able to fully inspect `claim_token_internal`'s body within the tool budget available (only its callers `claim_token`/`claim_and_transfer_token` were confirmed) to double-check whether it independently re-validates routes; however, since the burn in `send_token` is unconditional and precedes any such check, this does not change the conclusion that the fund loss is already finalized at `send_token` time regardless of downstream claim-side validation.

public fun send_token<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    ctx: &mut TxContext,
) {
    let inner = load_inner_mut(bridge);

    let bridge_seq_num = inner.get_current_seq_num_and_increment(message_types::token());
    let token_id = inner.treasury.token_id<T>();
    let token_amount = token.balance().value();
    assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
    assert!(token_amount > 0, ETokenValueIsZero);

    // create bridge message
    let message = message::create_token_bridge_message(
        inner.chain_id,
        bridge_seq_num,
        address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_id,
        token_amount,
    );

    inner.send_token_internal(target_chain, token, message);

    // emit event
    event::emit(TokenDepositedEvent {
        seq_num: bridge_seq_num,
        source_chain: inner.chain_id,
        sender_address: address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_type: token_id,
        amount: token_amount,
    });
}

public fun approve_token_transfer(
    bridge: &mut Bridge,
    message: BridgeMessage,
    signatures: vector<vector<u8>>,
) {
    let inner = load_inner_mut(bridge);
    assert!(!inner.paused, EBridgeUnavailable);
    // verify signatures
    inner.committee.verify_signatures(message, signatures);

    assert!(message.message_type() == message_types::token(), EMustBeTokenMessage);
    assert!(
        message.message_version() <= message::token_transfer_message_version(),
        EUnexpectedMessageVersion,
    );
    let token_payload = if (message.message_version() == 2) {
        message.extract_token_bridge_payload_v2().to_token_payload_v1()
    } else {
        message.extract_token_bridge_payload()
    };
    let target_chain = token_payload.token_target_chain();
    assert!(
        message.source_chain() == inner.chain_id || target_chain == inner.chain_id,
        EUnexpectedChainID,
    );

public fun valid_routes(): vector<BridgeRoute> {
    vector[
        BridgeRoute { source: SUI_MAINNET, destination: ETH_MAINNET },
        BridgeRoute { source: ETH_MAINNET, destination: SUI_MAINNET },
        BridgeRoute { source: SUI_TESTNET, destination: ETH_SEPOLIA },
        BridgeRoute { source: SUI_TESTNET, destination: ETH_CUSTOM },
        BridgeRoute { source: SUI_CUSTOM, destination: ETH_CUSTOM },
        BridgeRoute { source: SUI_CUSTOM, destination: ETH_SEPOLIA },
        BridgeRoute { source: ETH_SEPOLIA, destination: SUI_TESTNET },
        BridgeRoute { source: ETH_SEPOLIA, destination: SUI_CUSTOM },
        BridgeRoute { source: ETH_CUSTOM, destination: SUI_TESTNET },
        BridgeRoute { source: ETH_CUSTOM, destination: SUI_CUSTOM },
    ]
}

public fun is_valid_route(source: u8, destination: u8): bool {
    let route = BridgeRoute { source, destination };
    valid_routes().contains(&route)
}

// Checks and return BridgeRoute if the route is supported by the bridge.
public fun get_route(source: u8, destination: u8): BridgeRoute {
    let route = BridgeRoute { source, destination };
    assert!(valid_routes().contains(&route), EInvalidBridgeRoute);
    route
}
