### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is selected from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the HMAC secret) used to validate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken straight out of the unauthenticated JSON body [1](#0-0) [2](#0-1) . Every webhook handler, however, resolves the repository/stack to act on using a completely different field, `repository.full_name` [3](#0-2) . Nothing enforces that these two fields refer to the same GitHub organization. When Shipit is configured with the documented multi-org schema and at least one configured organization has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` trivially returns `true` for that organization [4](#0-3) . An attacker can therefore forge a webhook that is "verified" against the secret-less org while `repository.full_name` names a totally different, secured repository that Shipit actually manages.

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature == owner of the repository whose stacks are mutated by the handler`. This never holds because:

1. `repository_owner` is read from `params.dig('repository','owner','login')` and used solely to select which `Shipit.github(organization:)` config (and its `webhook_secret`) verifies the HMAC signature [5](#0-4) .
2. `Shipit.github` looks up per-organization secrets only when the "multiple GitHub applications" schema is used (the schema explicitly documented for multi-org installs) [6](#0-5) ; the setup docs and shipped example configs show `webhook_secret` left blank/optional per organization [7](#0-6) .
3. If that organization's `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally, regardless of the actual signature header [4](#0-3) .
4. After the (trivially passing) signature check, `WebhooksController#create` dispatches the entire attacker-supplied JSON body to every handler for the event [8](#0-7) .
5. Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` — a field that is part of the signed payload but never cross-checked against the organization that was actually authenticated [3](#0-2) , [9](#0-8) .

So an attacker can set `repository.owner.login` to a configured no-secret org while setting `repository.full_name` to `victim-org/victim-repo`, an org that does have a real secret, and Shipit will "verify" the request and then act on `victim-org/victim-repo`'s stacks.

The concrete write path with the highest impact is the status webhook: `StatusHandler`/commit-status webhooks write `Status` rows directly from the untrusted payload (confirmed by the controller test creating a `Status` on `commit.statuses` straight from webhook JSON) [10](#0-9) . These locally-stored statuses are later trusted, without re-fetching from GitHub, by the merge queue: `MergeRequest#all_status_checks_passed?` reads `head.statuses_and_check_runs` (the very rows the forged webhook wrote) [11](#0-10) . `ProcessMergeRequestsJob` autonomously calls `merge_request.merge!` for any pending merge request whose status checks pass [12](#0-11) , and `MergeRequest#merge!` performs a real `stack.github_api.merge_pull_request` call using the app's legitimate GitHub credentials for the victim repository [13](#0-12) .

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written." In a multi-org deployment where any one configured organization lacks a `webhook_secret` (a configuration the project itself documents and ships as an example), an unauthenticated, unprivileged attacker can inject forged commit-status data for a repository belonging to a *different, properly secured* organization. Because the merge queue's readiness gate trusts locally stored `Status` rows without revalidating them against GitHub, this can cause Shipit to autonomously call the real GitHub merge API and merge a pull request into the victim repository (`MergeRequest#merge!`) that has not actually passed CI — an unauthorized merge performed with the application's own `GITHUB_TOKEN`. This matches the Critical impact bucket ("cross-repository writes... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires: (a) Shipit configured with the multi-organization `github:` schema, and (b) at least one configured organization with a blank `webhook_secret`. Both conditions are explicitly supported and exemplified in the project's own configuration templates and documentation, making this a realistic operational configuration rather than a contrived one. No session, API token, or secret material is required by the attacker — only knowledge/guessing of one configured org name, which is typically discoverable (public GitHub App installation, org name reuse, etc.).

### Recommendation
Bind the signature verification and the acted-upon repository together: derive the organization used for `verify_webhook_signature` from the same field the handlers use (`repository.full_name`'s owner segment) rather than from a separate, independently-controlled `repository.owner.login`/`organization.login` field, or explicitly assert `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers. Additionally, consider requiring a non-blank `webhook_secret` for every configured organization (refuse to boot / warn loudly otherwise), and have `MergeRequest#all_status_checks_passed?` (or the merge job) re-validate CI status against the live GitHub API immediately before calling `merge!` rather than trusting locally cached `Status` rows populated by webhooks.

### Proof of Concept
1. Configure Shipit with two organizations under the multi-org `github:` schema: `secure-org` (with `webhook_secret` set) and `open-org` (with `webhook_secret` left blank, as shown in `config/secrets.development.shopify.yml`).
2. Shipit manages a stack for `secure-org/secure-repo` with `merge_queue_enabled: true`, and a legitimate pull request is registered in the merge queue (`pending`) but has not yet passed real CI.
3. Attacker sends, without any valid `X-Hub-Signature`, a `status` event to `POST /webhooks`:
```json
{
  "sha": "<head-sha-of-the-pending-PR>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/secure-repo"
  }
}
```
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "open-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of signature [4](#0-3) .
5. The status handler processes the payload using `repository.full_name` = `secure-org/secure-repo`, writing a passing `Status` row for the PR's head commit.
6. `ProcessMergeRequestsJob` next runs, `all_status_checks_passed?` now returns `true` from the forged status, and `merge_request.merge!` calls the real GitHub merge API for `secure-org/secure-repo`, merging a PR that never actually passed CI.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after

        def process
          stacks

            .where(branch:)

        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
