### Title
Cross-tenant Repository resolution in `OpenedHandler#repository` trusts payload `repository.full_name` independent of the webhook-verifying organization - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify a delivery using `params.dig('repository','owner','login')`, while `OpenedHandler#repository` (and all other PR handlers) resolves the `Shipit::Repository` record to mutate using the independent `params.repository.full_name` string. Because these are two separate JSON fields under the same `repository` object and neither is cross-checked against the other, an attacker who controls any organization already onboarded to Shipit (and therefore possesses that org's webhook secret) can forge a payload that authenticates as their own org but names a victim organization's tracked repository, causing a `ReviewStack`/`Stack` to be created and provisioned under the victim's repository.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`organization_that_verified_signature (params.dig('repository','owner','login'))` **==** `organization_owning_the_Repository_record (params.repository.full_name.split('/').first)`

Code path:
1. `Shipit::WebhooksController#verify_signature` picks the verifying GitHub App via `repository_owner`, which reads only `params.dig('repository', 'owner', 'login')`: [1](#0-0) [2](#0-1) 
2. Once the signature verifies (using the attacker's own org's `webhook_secret`), the raw payload is dispatched unmodified to handlers: [3](#0-2) 
3. `OpenedHandler#repository` resolves the target `Repository` purely from `params.repository.full_name`, a completely separate field from `repository.owner.login`: [4](#0-3) 
4. `Repository.from_github_repo_name` just splits the attacker-supplied string on `/` and does a DB lookup — it performs no comparison to the verifying organization: [5](#0-4) 
5. If the resolved victim repository has review stacks enabled, `OpenedHandler#process` creates a stack in the victim repository's `review_stacks` via `ReviewStackAdapter#create!`, which builds the stack, its `PullRequest`, and enqueues provisioning — all attacker-controlled data (`branch`, PR number, labels) is written onto the victim's repository: [6](#0-5) 

Root cause: `repository.owner.login` (used only for webhook-signature routing) and `repository.full_name` (used to resolve which tenant's `Repository`/`Stack` records get mutated) are independent, attacker-controlled JSON leaves of the same payload object, and no code path anywhere compares them. `ExplicitParameters` for `OpenedHandler` only requires `repository.full_name`, not `repository.owner.login`, so nothing forces consistency at parse time either: [7](#0-6) 

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature` computed with the attacker-controlled org's `webhook_secret` over the raw body, and a body such as:
```json
{
  "action": "opened",
  "number": 999,
  "pull_request": { "...": "attacker-controlled, but internally consistent per schema" },
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "sender": { "login": "attacker-user" }
}
```
`verify_signature` verifies successfully against `attacker-org`'s secret, but `OpenedHandler#repository` resolves and mutates `victim-org/victim-repo`.

This is the same unguarded pattern in every PR handler subclassing `Shipit::Webhooks::Handlers::Handler` (`stacks`/`repository_name` also read only `full_name`): [8](#0-7) , and in `LabelCapturingHandler`, `UnlabeledHandler`, etc., which follow the identical `Repository.from_github_repo_name(params.repository.full_name)` pattern: [9](#0-8) [10](#0-9) 

Why existing guards fail: `verify_signature` only proves the request came from *some* org with a valid secret — it never asserts anything about which `Repository` the rest of the payload is allowed to reference. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross-field consistency. Model validations on `Repository` (`owner`/`name` format) constrain the string shape but not which tenant supplied it.

### Impact Explanation
An attacker who controls one Shipit-onboarded organization (with its own valid `webhook_secret`) can create, and cause provisioning of, a `Shipit::ReviewStack`/`Stack` on a *different*, victim organization's tracked repository, injecting attacker-chosen `branch`, PR number/environment, PR title, and PR user/sender data into the victim's records. Because `ReviewStackProvisioningQueue.add` subsequently drives real provisioning tasks/commands against the victim repository's deploy environment (`TaskCommands#perform` / `Command#start`), this is a cross-tenant record injection that can trigger execution against the victim's environment. This matches the "Critical" category: a payload for one repository (attacker's) mutating another's (victim's) stack/task, achieved without possessing the victim's secrets. The attack is repeatable against any other onboarded repository whose owner name the attacker can guess/know and which has review-stack provisioning enabled.

### Likelihood Explanation
The attacker must control (or compromise) at least one organization that is already configured in Shipit with its own GitHub App/`webhook_secret` — otherwise `verify_signature` raises `Shipit::GithubOrganizationUnknown` and the request is rejected with 422. This is a real but plausible precondition in any multi-tenant Shipit deployment onboarding many orgs/customers with varying trust levels. Beyond that, the attacker needs no victim secrets, no Shipit session, and no repository maintainer role on the target — only knowledge of the victim's `owner/repo` string and that its `review_stacks_enabled`/`provisioning_behavior` is configured to auto-provision. The attack is a single crafted, self-signed HTTP POST and is fully repeatable against any tracked repository.

### Recommendation
Cross-validate the organization that verified the webhook signature against the organization implied by `repository.full_name` (and any other repository-identifying fields) before resolving or mutating any `Repository`/`Stack` record. Concretely, in `WebhooksController#create` (or in `Handlers::Handler#initialize`), assert that `payload.dig('repository','owner','login')&.downcase == payload.dig('repository','full_name')&.split('/')&.first` and reject (422) on mismatch, or better, thread the verified `repository_owner` explicitly into each handler and require `Repository.from_github_repo_name` lookups to also match that verified owner.

### Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
```ruby
test "pull_request webhook signed by org A cannot create a stack on org B's repository" do
  # Arrange: two orgs configured in Shipit, each with its own webhook_secret via stubbed Shipit.github
  victim_repo = shipit_repositories(:shipit) # owner: 'shopify', provisioning enabled/allow_all
  attacker_org = 'attacker-org'

  payload = JSON.parse(payload(:pull_request_opened))
  payload['repository']['full_name'] = victim_repo.github_repo_name # e.g. "shopify/shipit-engine"
  payload['repository']['owner']['login'] = attacker_org            # verifies against attacker's secret
  body = payload.to_json

  attacker_github_app = stub(verify_webhook_signature: true)
  Shipit.stubs(:github).with(organization: attacker_org).returns(attacker_github_app)

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=attacker-signed-value'

  assert_no_difference -> { Shipit::Stack.count } do
    post :create, body:, as: :json
  end
  # Equality that should hold but currently doesn't when the guard is missing:
  # payload.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first
end
```
Without a fix, this test fails: `Shipit::Stack.count` increases by 1 for `shopify/shipit-engine` even though the signature was verified only against `attacker-org`'s secret, proving the cross-tenant write.
