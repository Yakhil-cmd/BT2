### Title
Malicious secondary-trigger AA can force revert of the entire primary AA cascade, freezing intended fund distributions (analogous to ERC777 revert-on-receive blocking liquidation) - (File: aa_composer.js)

### Summary
In `MultiRewardDistributor` (external report), a hostile recipient makes an ERC777 `tokensReceived` hook revert so that an entire `liquidateBorrow` transaction — including unrelated legitimate transfers bundled in the same call — fails, letting the borrower dodge liquidation. `ocore`'s Autonomous Agent (AA) engine has the same class of hazard: when a primary AA trigger cascades into secondary AA triggers (AA-to-AA payments processed atomically in one DB transaction/batch), any one secondary AA can unconditionally "bounce" and this forces the whole cascade — including all state changes and payments already computed for other, honest addresses — to be rolled back.

### Finding Description
When a primary AA response includes an output to another AA address, `handleSecondaryTriggers` is invoked to run that AA as a nested ("secondary") trigger in the same unit-of-work [1](#0-0) . If the secondary AA's evaluation bounces, its `onDone` is invoked with a `bounce_message`, which is forwarded via `cb(bounce_message)` into the `async.eachSeries` error handler [2](#0-1) . When the failing branch belongs to (or is reached from) the primary, non-secondary flow, this triggers `revert(err)` [3](#0-2) .

`revert()` unconditionally discards **everything** produced so far for the current primary trigger: it clears in-memory state vars, clears the write `batch`, and issues `ROLLBACK TO SAVEPOINT initial_balances` on the DB connection [4](#0-3) . This undoes not only the failing secondary AA's own side effects, but also any other outputs/state changes the primary AA already produced for completely unrelated, honest addresses in the same trigger execution (e.g., payouts to depositors/creditors made alongside a payment routed through the malicious AA).

Critically, a secondary trigger is not required to have funds to cover its own bounce fees before it is allowed to bounce for free: "being able to pay for bounce fees is not required for secondary triggers as they never actually send any bounce response or change state when bounced" [5](#0-4) . This means an attacker-controlled AA can be built purely to bounce every time it is invoked as a secondary trigger, at zero cost to the attacker, and this is confirmed by existing test coverage showing a called AA that deliberately calls `bounce(...)` and the caller's whole response is bounced as a result [6](#0-5) .

This is structurally identical to the ERC777 hook issue: an untrusted counterparty that is a recipient of value as a side effect of someone else's operation is given unilateral, free power to revert that entire operation, defeating the intended outcome (e.g., liquidation, fee distribution, reward payout) for the honest parties in the same call.

### Impact Explanation
Any AA-based protocol on `ocore` (e.g., a lending/liquidation AA, a reward/fee-distribution AA, or any AA that fans out payments to user-registered AA addresses) that routes part of its output to a borrower/counterparty-controlled AA address is exposed: that counterparty can deploy a trivial "always bounce" AA at their designated address and thereby force the *entire* primary trigger — including payouts meant for liquidators, depositors, or other unrelated recipients — to be rolled back. This matches the accepted impact category of "AA fund loss or freezing": intended fund movements (e.g., liquidation proceeds, distributed rewards) never occur, and the malicious party permanently avoids a state change that would be to their detriment (e.g., being liquidated), while other users' expected settlements are also blocked as collateral damage.

### Likelihood Explanation
Likelihood is high in practice for any deployed AA that performs multi-recipient logic where one recipient address is attacker-influenced (e.g., a borrower registers or is otherwise routed to an AA address of their choosing, or any protocol that pays out to arbitrary/attacker-specified AA addresses as part of a larger settlement). No special privilege, timing, or race condition is needed — the attacker only needs to (a) get value routed to them via a secondary trigger and (b) have their AA definition unconditionally `bounce()`. The zero-bounce-fee-requirement for secondary triggers [5](#0-4)  removes even the small cost that would otherwise limit repeated griefing.

### Recommendation
- Do not allow a failing/bouncing secondary trigger to unwind the entire primary cascade by default. Instead, isolate the failure to the affected branch (similar to how ERC777-style griefing is mitigated by using `try/catch`-style isolation or pull-payment patterns in Solidity): treat a secondary AA's bounce as a local failure that does not roll back unrelated payouts already computed for other addresses in the same primary trigger.
- Alternatively/additionally, require that protocol-level AAs use a "pull" pattern for payouts to externally-influenced/attacker-controlled AA addresses (i.e., record a claimable balance rather than directly cascading a payment message that can trigger a secondary AA invocation), so a hostile recipient cannot affect the primary trigger's atomic outcome.
- Document explicitly (and consider enforcing) that AA developers must not assume secondary-trigger delivery cannot be weaponized to revert unrelated logic in the same primary trigger, given secondary triggers can bounce for free at line [5](#0-4) .

### Proof of Concept
1. Deploy `MaliciousAA` whose code unconditionally calls `bounce("nope")` regardless of trigger data (as in the existing test pattern) [7](#0-6) .
2. Deploy `LiquidationAA` that, on a valid liquidation trigger, sends part of the proceeds to the liquidator/depositor address and sends the remaining collateral/refund to `borrower_address`, where `borrower_address` is (or resolves to) `MaliciousAA`.
3. Trigger `LiquidationAA`'s liquidation logic. The primary trigger computes payouts to both the liquidator and to `MaliciousAA` and issues a secondary trigger for `MaliciousAA`'s payment.
4. `MaliciousAA` bounces immediately upon being invoked as a secondary trigger, without needing to cover its own bounce fees [5](#0-4) .
5. `handleSecondaryTriggers`'s `async.eachSeries` sees the error and calls `revert(...)` on the primary (non-secondary) trigger [3](#0-2) , which performs `ROLLBACK TO SAVEPOINT initial_balances` and clears the batch [8](#0-7) , undoing the liquidator's payout as well.
6. Net effect: the borrower is never liquidated, and the liquidator receives nothing, even though the liquidation trigger itself was otherwise valid.
