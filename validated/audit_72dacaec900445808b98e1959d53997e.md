Based on my investigation, I found a plausible analog to CVE-2017-17499's use-after-free class in `network.js`'s `tryToAdvanceStabilityPointForCatchupAATrigger`.

### Title
Stability point can be advanced on a stale/duplicate database connection outside the write mutex, corrupting shared stability caches - (File: network.js, main_chain.js)

### Summary
`tryToAdvanceStabilityPointForCatchupAATrigger()` is invoked from an unprivileged, network-reachable code path (`handleJoint`'s `ifTransientError` callback, triggered by any peer/unit poster sending a unit that yields "possible AA" while catching up) and calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()` on a dedicated, freshly-taken connection with its own `BEGIN`/`COMMIT` transaction, concurrently with the normal `saveJoint()`/validation write path which also mutates the same process-global in-memory caches (`storage.assocStableUnits`, `assocUnstableUnits`, `assocStableUnitsByMci`, etc.) under the `"write"` mutex. [1](#0-0) 

### Finding Description
`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` itself internally acquires the `"handleJoint"` mutex before calling `stabilizeMci()` (which updates the shared stability caches), but `tryToAdvanceStabilityPointForCatchupAATrigger()` performs its own `BEGIN`/`COMMIT` on a connection it took independently of that same-purpose "write" mutex used by `writer.saveJoint()` for all other cache-mutating commits. [2](#0-1) [3](#0-2) 

Because `saveJoint()`'s stabilization path (`main_chain.advanceMcStability`) and this catch-up path both eventually call into the code that mutates the in-memory unstable/stable unit caches, and each uses a *different* db connection/transaction for its own `BEGIN...COMMIT`, two logically-related mutations of the shared, process-wide JS objects (`assocStableUnits`, `assocUnstableUnits`, `assocStableUnitsByMci`) can interleave across two separate SQL transactions. This is conceptually analogous to the ImageMagick UAF: an object (`Image`) is torn down/rebuilt by one code path while another path retains and uses a stale reference to it, corrupting state that later code trusts as consistent. Here, a stale/half-committed set of caches (e.g., a unit's entry deleted from `assocUnstableUnits`/`assocStableUnits` in one transaction while the parallel path still references the old copy, or the reverse - an update applied to memory that gets rolled back by a `ROLLBACK` in `writer.js`'s error branch which calls `storage.resetMemory(conn)`) can leave nodes with divergent views of stability. [4](#0-3) [5](#0-4) 

### Impact Explanation
If the two independently-committed transactions race, a node's in-memory stability caches can diverge from what is actually committed in the database (or from what peers compute), leading to disagreement on unit stability/validity between nodes, or a node crashing on an internal consistency check like `throw Error("earlier unit is no longer on main chain")` in `main_chain.js` line 1220, effectively producing a remotely-triggerable DoS or consensus-disagreement condition, since `tryToAdvanceStabilityPointForCatchupAATrigger` is invoked purely because a remote peer sent a specific "possible AA" unit while the node is catching up. [6](#0-5) 

### Likelihood Explanation
The path is reachable by any peer sending a unit that trips the `"possible AA"` transient-error branch while `bCatchingUp` is true, which does not require any special privilege - it's purely a function of unit content and node catch-up state. [7](#0-6) 

### Recommendation
Serialize `tryToAdvanceStabilityPointForCatchupAATrigger`'s connection/transaction handling with the same `"write"` mutex used by `writer.saveJoint()`'s stabilization path, or route it through the exact same `advanceMcStability`/commit machinery so that only one code path ever commits cache-affecting stability transactions at a time.

### Proof of Concept
Not directly demonstrable without a running two-node/catch-up harness; the race requires timing a "possible AA" unit arrival during active catch-up while a concurrent `saveJoint()` stabilization is in flight on another connection - reproduction would need controlled DB connection scheduling to force the interleaving described above.

async function tryToAdvanceStabilityPointForCatchupAATrigger(objJoint){
	const objUnit = objJoint.unit;
	const unit = objUnit.unit;

	if (!ball || storage.assocHashTreeUnitsByBall[ball] !== unit)
		return;

		const props = storage.assocUnstableUnits[parent_unit];
		return props && props.is_on_main_chain && !props.is_stable;
	});
	if (!parent_unit)
		return;

	console.log(`possible AA trigger for unit ${unit}: trying to advance the stability point to its MC parent ${parent_unit} using free units ${arrFreeUnits.join(', ')}`);

	console.log(`AA parent ${parent_unit} stable in free units ${arrFreeUnits.join(', ')}? ${bStable}`);
	await conn.query("COMMIT");
	conn.release();
}
