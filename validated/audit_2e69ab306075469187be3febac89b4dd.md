### Title
Arbitrary Attribution of Shared-Address Signing Authority via Unverified `device_address` in `new_shared_address` Message - ([File: wallet_defined_by_addresses.js])

### Summary
The InvenTree CVE lets any authenticated user create an API token bound to an arbitrary target user because the server trusts a caller-supplied identity field (`user`) without checking it maps to the caller. In `ocore`'s device-messaging wallet layer, `handleNewSharedAddress()` in `wallet_defined_by_addresses.js` exhibits the same bug class: it accepts a peer-supplied mapping of cryptographic address → controlling `device_address` (`body.signers`) and persists it verbatim into `shared_address_signing_paths`, without verifying that the sender who transmitted the message actually controls, or is entitled to assert, the `device_address` it lists for each signing path.

### Finding Description
`handleNewSharedAddress(body, callbacks)` [1](#0-0)  performs the following checks on an incoming `"new_shared_address"` device message:
1. `body.definition` hashes to `body.address` (structural integrity of the address).
2. Each `signerInfo.address` in `body.signers` is a syntactically valid address.
3. Each signing path's `signerInfo.address` matches the address embedded at that path inside `body.definition` (via `extractAddressPathsFromDefinition`).
4. `determineIfIncludesMeAndRewriteDeviceAddress` confirms *my* address is a member.

None of these checks validate `signerInfo.device_address` — the field that determines which peer will later be asked to co-sign transactions from this shared address, and which is used to authorize proxied signing requests. This value is taken directly from the untrusted message body and written to `shared_address_signing_paths` in `addNewSharedAddress()` [2](#0-1) .

This attacker-controlled table is later consulted to authorize the `"sign"` message flow in `wallet.js`: when the local user tries to sign a shared-address transaction and the signer is not local, `findAddress` returns `ifRemote(device_address, other_device_addresses)`, and the message handler checks only `other_device_addresses.includes(from_address)` [3](#0-2)  before forwarding the unsigned unit (and, when private, any encrypted private payloads that were revealed to the caller) to the `device_address` on record — the very value that came from the unverified `body.signers` entry. If an attacker seeds a shared address record whose `signers` map another member's signing path to a `device_address` under the attacker's control, subsequent legitimate signing requests routed by other cosigners will be proxied to the attacker's device, exposing the terms of the (multisig/multilateral) transaction, including private payment payloads shared for that signing round, to a party never intended to see them.

### Impact Explanation
Because signing itself still requires possession of the private key matching the on-chain address embedded in `body.definition`, funds cannot be moved directly through this flaw — this differs from the CVE's full-authentication bypass. However, the routing metadata (`device_address`) is a trust anchor for a class of interactions that assume "the party listed as a member's device is the actual party": private payment chains, signing offers, and contract negotiation messages (`signing_request`, `offer to sign`) can be redirected/leaked to an address chosen entirely by the attacker, and legitimate cosigners can be caused to disagree on who controls a given signing path of a shared/multisig address, leading to stalled signing (frozen funds in cosigned/arbiter contracts) or disclosure of private transaction details to an unintended party.

### Likelihood Explanation
`handleNewSharedAddress` is reachable by any correspondent device that can send a `"new_shared_address"` (or `"create_new_shared_address"` / `"approve_new_shared_address"`) message to a wallet — this is a normal, unprivileged multi-device wallet feature, and the message is processed as soon as it is decrypted, requiring no additional user confirmation for the underlying `device_address` binding.

### Recommendation
Cross-check each `signerInfo.device_address` in `body.signers` against a trusted source before storing it: e.g. only accept `device_address` when it is either the sender's own `from_address` (as already verified by `handleMessageFromHub` for the message), or an address that a mutually agreed multisig setup previously exchanged via `approve_new_shared_address`. Reject or flag `new_shared_address` bodies whose `device_address` bindings were not offered/approved by the corresponding correspondent, and never silently persist unverified device_address→address associations into `shared_address_signing_paths`.

### Proof of Concept
Conceptual (message-level) PoC, not fully verified end-to-end due to index limitations on runtime wiring beyond the cited code paths:
1. Attacker device D_evil pairs with victim V (normal correspondent flow).
2. D_evil crafts a valid multisig `arrDefinition` (e.g. `["and", [["address","A1"],["address","A2"]]]`) where A1 is V's real address and A2 is any valid address for which D_evil supplies a plausible `signers` entry mapping A2's signing path to `device_address: D_evil`.
3. D_evil sends `"new_shared_address"` to V with `{address: chash(arrDefinition), definition: arrDefinition, signers: {...}}`.
4. `handleNewSharedAddress` validates structural/definition-address consistency (all satisfiable by D_evil) and, because V's own address A1 is a member, `determineIfIncludesMeAndRewriteDeviceAddress` succeeds; `addNewSharedAddress` stores the record, binding A2's path to D_evil's device address with no verification that D_evil legitimately controls A2 or represents its true device.
5. When V later needs the co-signer for A2's path, `findAddress`/`"sign"` flow proxies the signing request (and any private payload data attached) to D_evil instead of the legitimate owner of A2.

Given the constraints of this review (no live runtime), the write of unverified `device_address` values and their later use for authorization in `wallet.js`'s `"sign"` handling are directly confirmed in the cited source; full exploitation would require confirming a scenario where such attacker-supplied bindings are relied upon by other cosigners in a live wallet — this residual assumption should be validated with a Devin session that can run the wallet/device message flow end-to-end.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
