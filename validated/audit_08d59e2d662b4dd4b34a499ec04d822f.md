### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, but event handlers act on `repository.full_name` — allowing one authenticated GitHub organization to forge events for another organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub App's `webhook_secret` to verify an incoming webhook against using a field extracted from the *unverified* JSON body (`repository.owner.login` or `organization.login`), then hands the *entire* raw body to event handlers, which key their repository/stack lookups off `repository.full_name`. Nothing ties the verified organization to the repository that the handlers actually mutate, so in a multi-organization Shipit deployment, a party that legitimately controls one configured organization's `webhook_secret` can forge a signed-looking payload whose `repository.full_name` points at a different organization's repository, causing Shipit to process attacker-controlled push/status/pull_request/membership events against that victim repository/stack.

### Finding Description
`verify_signature` computes the signing key via: [1](#0-0) 

and `repository_owner` is derived purely from body content that the requester controls: [2](#0-1) 

Once signature verification passes, `create` dispatches the **raw, unrestricted** JSON to registered handlers: [3](#0-2) 

Handlers (e.g. the push handler exercised by `GithubSyncJob`) locate the target `Stack`/`Repository` using `repository.full_name` from that same payload, independent of which field was used for signature selection. This is demonstrated directly by the test suite, which changes only `repository.full_name` to redirect a webhook to an "unknown" repository while the organization/signature-selection logic is untouched: [4](#0-3) 

Shipit explicitly supports multiple independently configured GitHub organizations, each with its own distinct `webhook_secret`, inside a single Shipit instance: [5](#0-4) 

The binding that is broken is: **the organization whose secret authenticated the request** (`repository_owner` / `Shipit.github(organization: repository_owner)`) **≠ the repository whose Stack the handlers write to** (`repository.full_name`). Because `repository_owner` and `repository.full_name` are both attacker-suppliable fields inside the same unverified JSON body, and only the former gates the HMAC check, an attacker can decouple them: set `repository.owner.login` to their own organization (so the signature validates against a secret they legitimately hold), while setting `repository.full_name` to `victim-org/victim-repo`.

### Impact Explanation
This crosses a repository-write trust boundary between GitHub organizations hosted on the same Shipit instance. An operator who administers *Organization A* (and therefore possesses Organization A's legitimately-configured `webhook_secret`, not a stolen credential) can forge signed webhook deliveries that Shipit will process as if they came from *Organization B*, injecting fabricated push events (queuing `GithubSyncJob` for a foreign stack), commit statuses, `check_suite` results, `pull_request`/`merge_status` updates, or team/membership changes against repositories/stacks they do not own or have any legitimate relationship with. Depending on which handler is targeted, this can corrupt deploy-readiness signals (fake commit statuses/checks) or trigger sync/merge-queue side effects on a victim repository — a cross-organization write achieved purely with credentials that are authentic for the attacker's own tenant.

### Likelihood Explanation
This requires Shipit to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to control (legitimately) the webhook secret for at least one of them — which any operator/admin of one hosted organization has by design, without needing to compromise any other tenant's secret, `ApiClient` token, or a Shipit user session. No privileged Shipit account or GitHub App private key is needed; only the ability to send an HTTP POST with a validly-signed-for-their-own-org body whose `repository.full_name` names a different tenant's repository.

### Recommendation
After verifying the HMAC signature, re-derive the authorized organization from the verified payload and assert that `repository.full_name`'s owner segment (or `organization.login`) matches the organization key (`repository_owner`) that was used to select the `webhook_secret`, rejecting the request (422) on mismatch before dispatching to handlers. Alternatively, resolve the target `Repository`/`Stack` and confirm its owner organization equals the authenticated organization inside each handler prior to acting on the payload.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgA` (holder of `OrgA`'s legitimate `webhook_secret`), craft a `push` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
     "after": "<attacker-chosen-sha>"
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` and send it to `POST /github/webhooks` with header `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully.
5. `create` dispatches the full payload to the push handler, which resolves the target stack via `repository.full_name` = `"OrgB/victim-repo"`, enqueuing `GithubSyncJob` (or equivalent) against `OrgB`'s stack — despite the request never being authenticated as `OrgB`.
