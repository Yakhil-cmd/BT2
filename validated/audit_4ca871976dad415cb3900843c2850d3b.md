### Title
Meta-transaction (`DelegateAction`) signatures omit chain identity, enabling cross-chain replay of signed actions - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The NEP-366 meta-transaction signature scheme signs a hash composed only of a `MessageDiscriminant` and the borsh-serialized `DelegateAction`/`DelegateActionV2` payload (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). No chain identifier (e.g. genesis hash or `chain_id`) is folded into the signed digest, mirroring exactly the reported "withdraw digest missing chainId" bug class.

### Finding Description
`SignableMessage::sign` computes `hash(borsh(SignableMessage{discriminant, msg}))` and signs that hash: [1](#0-0) 

`DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash` build the signable message purely from the action's own fields, with no chain-specific salt: [2](#0-1) [3](#0-2) 

`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify` only check this hash against the signature and public key — there is no genesis-hash or chain-id comparison anywhere in the verification path: [4](#0-3) [5](#0-4) 

On-chain execution of a `Delegate`/`DelegateV2` action only validates the access key's existence, nonce, and permission — not any chain-identity binding: [6](#0-5) 

By contrast, ordinary `SignedTransaction`s are chain-bound only indirectly, through the outer transaction's `block_hash` validity-period check performed by the receiving node — but this check applies to the *outer* relayer transaction, not to the inner `DelegateAction` payload's signature itself, which is the only thing the original signer (the account holder) actually authorizes.

### Impact Explanation
If two distinct NEAR chains (e.g., a permissionless fork, a state-snapshot-derived test/shadow network, or any chain instance seeded from the same genesis/account state — same account, same access key, same nonce) both exist, a `SignedDelegateAction`/`VersionedSignedDelegateAction` signed once by a user can be wrapped into a fresh outer transaction and submitted independently on each chain. Because the inner signature check never verifies chain identity and the access-key nonce state is purely chain-local, the same authorized action (e.g., a token transfer, contract call, or access-key modification) can be replayed and executed a second time on the sibling chain, producing an unauthorized duplicate state/balance change equivalent to the "double withdrawal" described in the report.

### Likelihood Explanation
Exploitation requires two chains that share the relevant account/access-key state at some point (a realistic occurrence for chain forks, disaster-recovery relaunches, or test/shadow networks bootstrapped from mainnet state snapshots). Given such a scenario, replay is trivial: any relayer (even the original victim's own delegate action, previously observed on the network) can resubmit the unchanged `SignedDelegateAction` bytes as the inner action of a new outer transaction on the second chain, since no additional chain-specific secret or nonce value is required beyond what already matches on the sibling chain.

### Recommendation
Bind the NEP-366/NEP-611 signable message to chain identity by including the genesis hash (or protocol `chain_id`) as part of the `SignableMessage`/`DelegateAction` payload that gets hashed and signed, so that a `SignedDelegateAction` produced for one chain cannot be verified as valid on any other chain, analogous to adding `chainId` to the withdraw digest in the original report.

### Proof of Concept
1. On chain A, user Alice signs `DelegateAction{sender_id: alice, receiver_id: bob, actions: [Transfer], nonce: N, max_block_height: H, public_key: pk}` via `SignedDelegateAction::sign`, producing signature `S`.
2. A relayer submits `Action::Delegate(SignedDelegateAction{delegate_action, signature: S})` inside an outer transaction on chain A; it executes successfully via `validate_delegate_action_key`, incrementing Alice's access-key nonce on chain A. [7](#0-6) 
3. Suppose chain B is bootstrapped from the same account/access-key state as chain A prior to step 2 (e.g., a fork/shadow chain), so Alice's access key on chain B still has nonce `N-1` and the same public key.
4. The relayer takes the identical `(delegate_action, signature S)` bytes and wraps them in a fresh outer transaction addressed to chain B. `VersionedSignedDelegateAction::verify`/`SignedDelegateAction::verify` succeeds because the signed hash contains no chain-identity information, and `validate_delegate_action_key` accepts it because the nonce matches chain B's independent state.
5. The transfer/action is executed a second time on chain B, doubling the effect of a single user authorization — an unauthorized balance/state change identical in nature to the reported withdraw-replay vulnerability.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
