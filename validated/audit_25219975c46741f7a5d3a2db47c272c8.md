### Title
Webhook signature is verified against the payload's `repository.owner.login`, but stack lookup uses the independent `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate an incoming webhook against based on `params.dig('repository','owner','login')` [1](#0-0) . All webhook event handlers, however, resolve which `Repository`/`Stack` to act on independently, using `payload.dig('repository','full_name')` [2](#0-1) . Because both fields live in the same attacker-controlled JSON body and nothing ties them together, an attacker who can produce a validly-signed payload for one configured GitHub organization can set `repository.full_name` to point at a stack belonging to a completely different organization configured in the same Shipit instance.

### Finding Description
Shipit supports multiple GitHub organizations/Apps per installation, each with its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`), and `Shipit.github(organization: ...)` looks up the app config for whichever organization name is supplied [3](#0-2) .

`verify_signature` derives the organization used for secret lookup solely from `repository.owner.login` (falling back to `organization.login`): [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the raw, still-untrusted JSON body to the registered handler for the event [5](#0-4) . Handlers such as `PushHandler` resolve the target `Stack` via `Handler#stacks`, which looks up `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [2](#0-1) [6](#0-5) .

Nothing enforces that `repository.full_name`'s owner segment matches `repository.owner.login`. A legitimate GitHub-generated payload always keeps these consistent, but the webhook endpoint accepts arbitrary POSTed JSON with a matching `X-Hub-Signature`, so an attacker who controls a validly-signed payload for **Organization A** (e.g., because Organization A's `webhook_secret` is unset/blank — `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, see below — or because they otherwise hold Org A's secret) can set `repository.owner.login = "OrgA"` (to pass verification) while setting `repository.full_name = "OrgB/some-repo"` (to select a stack under a completely different, unrelated organization B configured in the same Shipit deployment).

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

This is the equality that should hold but is broken:
`organization authenticated via signature (repository.owner.login)` ≠ `organization actually written to (owner segment of repository.full_name)`.

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack under the spoofed `repository.full_name` [6](#0-5) . This can drive GitHub sync jobs and, in combination with continuous deployment settings, downstream deploy triggers for a stack/repository that belongs to an organization the attacker has no legitimate relationship with — an unauthorized cross-repository write/trigger, consistent with the "cross-repository writes" / "unauthorized deploy" impact bar. `MembershipHandler` similarly trusts `params.organization.login` independent of the org used for signature verification, letting an attacker manipulate `Team`/`Membership` records (which feed into `Shipit.github_teams` authorization) for organizations other than the one whose credentials were used to pass signature verification [7](#0-6) .

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a validly-signed payload for at least one organization configured on the shared Shipit instance whose owner login differs from the target's `repository.full_name` owner. This is realistically achievable when: (a) that organization's `webhook_secret` is left blank/unset — a documented, supported configuration state (`webhook_secret: # nil` appears in the project's own example secrets files) — which makes `verify_webhook_signature` always return `true`, or (b) the attacker otherwise has that organization's own (lower-value) webhook secret. No session, `ApiClient` token, target org's secret, or GitHub App private key is required for the target organization being attacked, satisfying the "unprivileged attacker" bar for the target.

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`) used for webhook signature verification is consistent with the owner segment of `repository.full_name` before dispatching to handlers, or better, resolve the target `Repository`/`Stack` using the same organization value that was cryptographically verified rather than trusting a second, independently-attacker-controlled field. Consider also rejecting webhook processing entirely for organizations with a blank `webhook_secret` unless explicitly opted into (with a prominent warning), since blank secrets currently make signature verification a no-op.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (weak/blank `webhook_secret`) and `OrgB` (properly secured, hosting a sensitive stack, e.g. `OrgB/prod-repo`), as supported by the multi-org config format shown in `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/prod-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`; because `OrgA`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header [8](#0-7) .
4. `PushHandler` resolves `repository_name` as `"OrgB/prod-repo"` and triggers `stack.sync_github` for the `OrgB` stack, despite the request never being authenticated against `OrgB`'s credentials [2](#0-1) [6](#0-5) .

**Note on confidence:** I was unable to fully trace `Stack#sync_github`/`GithubSyncJob` internals within the tool budget to confirm the exact downstream write operations (e.g., whether it can force a deploy versus only refresh commit metadata), so the ultimate severity of the write action should be verified against `app/models/shipit/stack.rb` and the `GithubSyncJob` implementation before triage.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
