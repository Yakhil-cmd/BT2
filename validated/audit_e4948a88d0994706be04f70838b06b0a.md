### Title
Signature verification selects its GitHub-App/secret using an attacker-controlled `repository.owner.login` field that is decoupled from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC against by reading `repository.owner.login` straight out of the still‑unverified JSON body. The handlers that subsequently act on the payload (`StatusHandler`, `PushHandler`, etc.) key off a *different* field, `repository.full_name`, to find the `Stack`/`Repository`/`Commit` to mutate. Because the "organization that authenticated" and "the repository that is written" are two independent, attacker-supplied fields inside the same unverified body, an attacker can pick an organization whose `webhook_secret` is blank (a documented, supported configuration - see `config/secrets.development.example.yml` and `docs/setup.md`, where `webhook_secret` is explicitly optional/nilable) to make `verify_webhook_signature` short-circuit to `true`, while pointing `repository.full_name` at a completely different, victim organization's stack.

### Finding Description
`Shipit.github(organization: repository_owner)` selects a `GitHubApp` config, and `repository_owner` is computed as: [1](#0-0) 

from the raw, not-yet-verified request body. `verify_webhook_signature` then does: [2](#0-1) 

Note `return true unless webhook_secret` - if the organization named in the (attacker-controlled) `repository.owner.login` field has no `webhook_secret` configured, the check is a no-op and always passes, regardless of the actual signature header. Multiple config templates in this engine explicitly document `webhook_secret` as optional/nullable per organization: [3](#0-2) 

Once `verify_signature` passes, the `create` action dispatches the same raw JSON to event handlers: [4](#0-3) 

Those handlers, however, do not re-check `repository.owner.login`; they resolve the target repository from the independent `repository.full_name` field: [5](#0-4) 

This is the equality that breaks: `organization used to select the verification secret == organization that actually owns the mutated repository` is assumed but never enforced. An attacker only needs to know (or discover) one organization in a multi-org Shipit deployment whose `webhook_secret` is unset, then forge a webhook body with `repository.owner.login` set to that org and `repository.full_name` set to any other tracked repository/stack, e.g. `victim-org/victim-repo`.

The impact is concrete for the `status` event: `StatusHandler` writes a `Status` (commit CI state) for an arbitrary existing commit sha in the target stack directly from unverified payload fields, as shown by the controller test asserting that `commit.statuses.last` mirrors payload fields with no other authentication: [6](#0-5) 

Since deploy eligibility elsewhere in the engine is driven by required/blocking CI statuses (`required_statuses`, `blocking_statuses` in `DeploySpec`), an attacker who can forge a passing status for a commit on a victim stack can make an otherwise-non-deployable or malicious commit appear deployable, entirely unauthenticated (no `ApiClient` token, no session, no repository write access) - satisfying the "unauthorized deploy" impact bar.

### Impact Explanation
This is a **High**-severity unauthenticated-write issue: an outside attacker with no credentials can forge signed-looking webhook events for a repository/organization they don't control, by exploiting an organization whose secret is unset elsewhere in the same multi-tenant Shipit instance. The concrete write is a forged `Status`/CI state on a victim stack's commit (`StatusHandler`), which materially affects "unauthorized deploy" gating logic (`required_statuses`/`blocking_statuses`) — this crosses the "organization that authenticated versus the repository that is written" binding called out in scope.

### Likelihood Explanation
Requires (a) a multi-org Shipit deployment where at least one configured GitHub App/org has no `webhook_secret` set — a state the shipped example configs (`config/secrets.development.example.yml`, `docs/setup.md`) explicitly treat as valid/supported — and (b) the attacker knowing that org's name. Given webhook secrets are documented as "optional," and the endpoint is unauthenticated by design (it's the public `/webhooks` GitHub delivery endpoint), this is plausible in real deployments that mix trusted and less-strict org configurations.

### Recommendation
- Short term: Require `webhook_secret` to be present for every configured GitHub App/organization (fail closed instead of `return true unless webhook_secret`), and reject any webhook whose `repository.owner.login` does not match the organization portion of `repository.full_name`.
- Long term: Bind webhook-signature verification to the specific repository being mutated (not just an organization derived from an unverified field), e.g. by re-deriving the org from `repository.full_name` and verifying that it's consistent with `repository.owner.login` before any handler dispatch, and by having handlers double check the resolved `Repository`'s configured organization against the one whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `victim-org` (has `webhook_secret: <real-secret>`) and `looseorg` (no `webhook_secret` configured, per the supported nil example).
2. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` (or any arbitrary value), and body:
```json
{
  "repository": { "owner": { "login": "looseorg" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "description": "forged"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "looseorg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler` (invoked via `repository.full_name`) creates/updates a `Status` on the victim commit belonging to `victim-org/victim-repo`, as directly reflected by the existing test at `test/controllers/webhooks_controller_test.rb:42-59`, with attacker-controlled `state`/`description`/`target_url`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
