### Title
Webhook signature is verified against the organization named in the payload, not the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/HMAC secret to check against by reading `repository.owner.login` (or `organization.login`) straight out of the *untrusted* JSON body, and only that narrow field is ever authenticated. Every downstream `Webhooks::Handlers::Handler` then acts on other fields of the same body — `repository.full_name` (to resolve the `Stack`/`Repository`) and, for `StatusHandler`, a globally-scoped `sha` lookup — without ever re-checking that those fields belong to the organization whose secret validated the request.

### Finding Description
`verify_signature` picks the app config purely from a payload field: [1](#0-0) [2](#0-1) 

The secret used for that verification comes from `Shipit.github(organization: repository_owner)`, and per-org webhook secrets are explicitly optional in configuration: [3](#0-2) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever that resolved org has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
(lib/shipit/github_app.rb, `verify_webhook_signature`)

Once `verify_signature` passes (either because the correct org secret matched, or because the org keyed off `repository_owner` happens to have no secret configured), the raw JSON body is handed unmodified to every registered handler for the event: [4](#0-3) 

Handlers resolve the *actual* repository/stack to mutate from a **different** field, `repository.full_name`, with no cross-check that it matches the `repository_owner` used for signing: [5](#0-4) [6](#0-5) 

`StatusHandler` is worse: it resolves target commits by SHA **globally**, with no repository/organization scoping at all: [7](#0-6) 

This is the same class of bug as the reported H-04: the field that is checked for authenticity (`repository_owner`, used to pick the signing key, analogous to the destination-router `_to` refund path) is not the field that is actually acted upon (`repository.full_name` / global `sha`, analogous to the bridge-executor `target`). The binding that should hold — *"the organization whose secret authenticated the request" == "the repository/commit the handler writes to"* — is never enforced.

### Impact Explanation
In a multi-organization Shipit deployment (the engine explicitly supports configuring `github:` per organization, each with its own optional `webhook_secret`), if any one configured organization has no `webhook_secret` set, an unauthenticated attacker can:
1. Set `repository.owner.login` (or `organization.login`) in the forged POST body to that unsecured org, causing `verify_webhook_signature` to unconditionally return `true`.
2. Set `repository.full_name` (for push/pull_request handlers) or an arbitrary `sha` (for `StatusHandler`) to reference a **completely different, secured** repository/stack tracked by the same Shipit instance.
3. Cause writes against that unrelated stack — e.g., injecting a fake `success` commit status via `StatusHandler` for any commit SHA in the system, which can influence CI-gated deployability checks (`required_statuses`/`ignore_ci` logic in `DeploySpec`), or forcing an unrelated stack to `sync_github`/archive/unarchive review stacks via the pull_request handlers.

This crosses a genuine authentication boundary (data belonging to org B is written using credentials that only prove knowledge tied to org A's — or no — secret) without requiring any Shipit session, API token, or the target organization's own webhook secret, satisfying the "cross-repository writes" / "unauthenticated read or write of stack state" impact bar.

### Likelihood Explanation
Requires: (a) a multi-org Shipit configuration, and (b) at least one configured organization without a `webhook_secret` (explicitly documented as optional). This is a realistic and likely-innocuous-looking configuration choice (e.g., a low-stakes/test org left unsecured) that silently undermines isolation for every other, properly-secured org sharing the same Shipit instance. No privileged credentials, sessions, or GitHub App keys are needed by the attacker.

### Recommendation
- Bind repository identity to the verified organization: after `verify_signature` succeeds, ensure `repository.owner.login`/`organization.login` used to select the signing key equals the owner implied by `repository.full_name` before dispatching to handlers, and reject on mismatch.
- Scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to the verified repository, not a global search.
- Consider making `webhook_secret` mandatory (or requiring an explicit, loudly-logged opt-out) so that a single unsecured org cannot degrade the authentication guarantee for the whole instance.

### Proof of Concept
1. Configure Shipit with two orgs: `secured-org` (has `webhook_secret`) tracking a sensitive `secured-org/prod-app` stack, and `open-org` (no `webhook_secret` configured) tracking an unrelated low-value repo.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<some commit sha belonging to secured-org/prod-app>",
  "state": "success",
  "repository": { "owner": { "login": "open-org" } }
}
```
No valid `X-Hub-Signature` is required because `verify_webhook_signature` returns `true` for `open-org` (no secret configured) — see `webhooks_controller.rb#verify_signature` and `github_app.rb#verify_webhook_signature`.
3. `StatusHandler#process` (`status_handler.rb:20-24`) matches the commit globally by SHA and creates a fabricated `success` status on `secured-org/prod-app`'s commit, even though the request was never authenticated against `secured-org`'s secret.
