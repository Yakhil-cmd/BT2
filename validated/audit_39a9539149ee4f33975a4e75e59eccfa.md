### Title
Division-by-zero panic in `token_price_x32` causes swap/deposit/withdraw to abort when a vault is fully drained to fee balances - ([File: programs/cp-swap/src/states/pool.rs])

### Summary
`PoolState::token_price_x32` computes an oracle price with raw division (`/`) instead of `checked_div`. If `vault_amount_without_fee` returns `0` for either token (i.e. the vault balance equals the accumulated protocol/fund/creator fees exactly), the subsequent division by that zero amount triggers a native Rust arithmetic panic, aborting the transaction with a program-level panic rather than a graceful `Result::Err`.

### Finding Description
`token_price_x32` first computes `(token_0_amount, token_1_amount)` via `vault_amount_without_fee`, which subtracts accrued protocol/fund/creator fees from the raw vault balances: [1](#0-0) 

It then divides directly with `/` rather than `checked_div`: [2](#0-1) 

`vault_amount_without_fee` can legitimately return `0` for a token amount without erroring — the `checked_sub` only fails (returns `InsufficientVault`) when the vault is *less* than the accumulated fees; when the vault balance equals the accumulated fees exactly, `token_0_amount` or `token_1_amount` becomes `0` and the function returns `Ok((0, y))`. This is directly reachable from `swap_base_input` and `swap_base_output`, both of which call `pool_state.get_swap_params(...)`, which in turn calls `token_price_x32` on attacker-supplied vault amounts and pool state: [3](#0-2) 

Because `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` uses an unchecked `/`, a `token_0_amount == 0` (or `token_1_amount == 0`) causes an integer-division-by-zero panic inside the BPF program, which aborts the whole transaction — unlike the rest of the codebase, which consistently uses `checked_div`/`ok_or` to convert failure into a normal Anchor error.

### Impact Explanation
Any successful swap that drives one side of the pool down to exactly the accumulated fee balance (a fully reachable state for extreme/degenerate pools, e.g. very small remaining liquidity plus normal fee accrual) will make every subsequent `swap_base_input`/`swap_base_output` call panic instead of cleanly erroring. Because the pool becomes permanently stuck in this state (fees keep accruing and the vault can only be topped back up by further swaps, which themselves would panic), it results in a denial of service that freezes further trading and prevents users/LPs from swapping through the affected pool, matching the "hang/crash → DoS" bug class of the referenced CVE.

### Likelihood Explanation
This is reachable by an ordinary unprivileged swapper: no special privilege is required to submit a swap that pushes `total_input_token_amount`/`total_output_token_amount` (post-fee) toward zero via `vault_amount_without_fee`. Very small/thinly-liquid pools or intentionally crafted low-decimal/low-supply pools make hitting exactly `vault == accumulated fees` plausible, and repeated fee accrual over time increases the chance of landing on this exact boundary. It requires a specific numeric coincidence (exact equality, not just "close to zero"), so likelihood is moderate rather than trivial to engineer on demand, but it is not gated behind any privileged signer.

### Recommendation
Replace the unchecked divisions in `token_price_x32` with `checked_div` and return `ErrorCode::MathOverflow` (or a dedicated error) on `None`, consistent with the rest of the codebase's arithmetic-safety pattern used in `vault_amount_without_fee` and `update_lp_supply`.

### Proof of Concept
1. Attacker (or normal usage over time) executes swaps against a low-liquidity pool such that accumulated `protocol_fees_token_0 + fund_fees_token_0 + creator_fees_token_0` equals the exact current `token_0_vault` balance (achievable by repeatedly swapping small amounts that increment fee counters while draining `token_0_amount` towards this exact fee total).
2. On the next `swap_base_input` or `swap_base_output` call, `pool_state.get_swap_params` invokes `token_price_x32(vault_0, vault_1)`. [4](#0-3) 
3. `vault_amount_without_fee` returns `token_0_amount == 0`.
4. `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` executes `x / 0`, causing the BPF program to panic and the transaction to abort, denying service to the pool for any further trade.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }
