### Title
`status` webhook writes are unscoped by repository, letting one repo's `success` payload flip `blocked?`/`deployable?` for a commit belonging to another stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` — with no repository/stack scoping at all — and writes a status onto every matching row across every stack in the installation. Because `Commit#blocked?` and `Commit#deployable?` are derived from `Status::Common#blocking?`/`#required?`, which are matched purely by `context` string against `stack.blocking_statuses`/`required_statuses`, an authenticated-but-foreign webhook (any repository onboarded to the same Shipit install) whose payload happens to carry a SHA that also exists as a `Commit` row in a victim stack (e.g. shared history from a fork, or an old shared base commit) can flip the victim's blocking/required status and therefore its `blocked?`/`deployable?` gating.

### Finding Description
The broken binding: `commit.stack_id == verified_repository.stack_id` is assumed but never enforced. In reality `StatusHandler#process` does:
```
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [1](#0-0) 

Compare this to the base `Handler` class, which explicitly provides a repository-scoped accessor `stacks` (via `Repository.from_github_repo_name(repository_name)&.stacks`) intended for handlers to scope their lookups to the repository that sent the webhook. [2](#0-1) 

`StatusHandler` never calls `stacks`; it queries `Commit` globally by bare SHA. `WebhooksController#verify_signature` only proves the payload was signed by the GitHub App/organization owning the *sender's* repository — it says nothing about which stack's commits the payload may touch: [3](#0-2) 

Once `create_status_from_github!` runs, `Commit#status` is recomputed from `statuses_and_check_runs`, and `Status::Common#blocking?`/`#required?` match purely on `context` against `stack.blocking_statuses`/`required_statuses` — there is no check that the status originated from the same repository as the stack: [4](#0-3) 

This directly affects `Commit#blocked?` (gates deploy eligibility) and `Commit#deployable?`: [5](#0-4) 

Exploit flow: attacker owns/administers Repo A which is legitimately onboarded to the same Shipit instance (so its webhook is correctly signed with the org's real secret). Repo A shares commit history with victim's Repo B/Stack (fork relationship, or both forked from a common upstream commit) so a specific SHA exists as a `Commit` row in both stacks. Attacker triggers (or fabricates, since they control Repo A's git state and can push/force GitHub to emit) a `status` event for that SHA with `context: continuous-integration/travis-ci`, `state: success`. The webhook is properly signed for Repo A and passes `verify_signature`. `StatusHandler#process` then finds **all** `Commit` rows with that SHA — including the one belonging to victim's stack — and calls `create_status_from_github!` on each, writing a new `Shipit::Status` row attributed to the victim commit. If the victim stack has `blocking_statuses` or `required_statuses` configured to include `continuous-integration/travis-ci`, this write can flip `blocking?`/`required?` for that context, changing `Commit#blocked?` and `Commit#deployable?`, which gates `stack.schedule_merges`, continuous delivery (`schedule_continuous_delivery`), and deploy eligibility.

Existing guards do not stop this: `verify_signature` only authenticates the sender's own org/repo, not the set of stacks the payload is allowed to mutate; `drop_unhandled_event` only filters by event type; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository ownership; there is no `require_permission!`/stack-scoping check anywhere in `StatusHandler`.

### Impact Explanation
A payload authenticated for one repository can mutate `Shipit::Status`/`Commit` state belonging to a completely different stack/repository/tenant, directly matching the "Critical: a payload for one repository mutating another's stack/commit" category. The attacker gains the ability to set or clear `blocking?`/`required?` status flags on arbitrary shared-SHA commits in victim stacks, which feeds `Commit#blocked?`, `Commit#deployable?`, `schedule_merges`, and continuous-deployment scheduling — potentially forcing or blocking a deploy for a repository they do not control. This is repeatable against any repository sharing commit ancestry (forks are common) with any victim stack on the same Shipit installation.

### Likelihood Explanation
Preconditions: attacker needs a repository legitimately onboarded to the same Shipit instance (achievable by forking a public victim repo and having it added, or by any repo they administer that shares history with a target), and the victim stack must have `blocking_statuses`/`required_statuses` configured for the spoofed context (a common, documented Shipit configuration). No Shipit session, API token, or GitHub secret is required beyond the attacker's own legitimate webhook signing for their own repo. Fork relationships sharing common-ancestor SHAs are a normal and frequent occurrence, making SHA collision across stacks realistic rather than theoretical. The action is fully repeatable and scriptable (send arbitrary `status` events for any SHA present across stacks).

### Recommendation
Scope `StatusHandler#process` to only the stacks/commits belonging to the repository that authenticated the webhook, mirroring the base `Handler#stacks` helper, e.g. resolve commits via `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Repository.from_github_repo_name(repository_name)` before touching any `Commit` row, rejecting/ignoring any match whose `stack.repository` doesn't correspond to the payload's `repository.full_name`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack`s backed by two different `Repository` records (`repo-a/repo-a`, `repo-b/repo-b`), each with its own `Commit` row using the **same** `sha` value (simulating shared fork history).
2. Configure `stack_b` with `blocking_statuses: ['continuous-integration/travis-ci']` (or `required_statuses`) via its `DeploySpec`/cached spec, so `commit_b.blocked?` depends on that context.
3. Assert baseline: `commit_b.blocked?` / `commit_b.deployable?` reflects no status yet (or a prior blocking state).
4. Build a webhook payload for `repo-a` (`repository.full_name == 'repo-a/repo-a'`) with `sha: <shared_sha>`, `context: 'continuous-integration/travis-ci'`, `state: 'success'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is orthogonal — it only proves repo-a's authenticity, not scope).
6. Reload `commit_b` and assert its `Status`/`blocked?`/`deployable?` changed as a result of a payload that only ever declared `repository.full_name == 'repo-a/repo-a'`, proving `commit_b.stack_id` (Repo B) was mutated by a request that authenticated only Repo A — the equality `commit.stack.repository.full_name == payload.dig('repository','full_name')` is false yet the write still occurred.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )

      ].join(' '))
