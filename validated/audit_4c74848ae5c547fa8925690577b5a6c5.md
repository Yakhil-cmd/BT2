### Title
CCMenu client token authorizes read access to all stacks instead of the one it was minted for - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
The report describes an authorization oversight in `authorize_invoke`: the withdrawal instruction only checks that the request is *signed* by the session authority, but never checks that the source account it withdraws from is the one the session was actually meant to authorize — breaking the intended binding "authority that signed = account that is debited." The same class of bug exists in Shipit's CCMenu token issuance: the token is only checked for the `read:stack` *permission string* and never bound to the specific stack for which it was generated, breaking the binding "stack a token authorizes = stack it can read."

### Finding Description
`CCMenuUrlController#fetch` mints (or reuses) an `ApiClient` token intended to grant read-only access to exactly one stack (the one in the URL, `stack_id`): [1](#0-0) 

Note that `client` is looked up/created via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `permissions: %w[read:stack]` — it never sets `stack:` on the `ApiClient`. Because `stack` is a `belongs_to ..., optional: true` association on `ApiClient`: [2](#0-1) 

an unscoped client (`stack_id` nil) is treated by `Api::BaseController` as authorized for **every** stack, not just the one it was minted for: [3](#0-2) 

`Api::CCMenuController`, which is the endpoint the generated `ccmenu_url` actually points to, authenticates purely via this unscoped token and the `read:stack` permission check, then resolves whatever `stack_id` is present in the request: [4](#0-3) 

Because `find_or_create_by!` is keyed only on `(creator, name)`, every "CCMenu Client" a given user ever creates — regardless of which stack's settings page they requested it from — resolves to the **same underlying `ApiClient` row**, whose scope is `Stack.all`. So the URL displayed on stack A's settings page (`/stacks/A/settings`, requesting `/ccmenu_url` for stack A) contains a token that also authenticates reads (`Api::CCMenuController#show`, and any other `read:stack`-only endpoint) for stack B, C, or any other stack in the instance: [5](#0-4) 

This mirrors the wallet-program flaw exactly: the check that is performed (signer is a valid session authority / permission string is `read:stack`) is real, but the field that should have been bound at issuance time (the specific withdrawal source account / the specific stack) is never enforced, so the credential's blast radius silently exceeds what was intended.

### Impact Explanation
Once a CCMenu URL for any single stack is shared or leaked (these URLs are explicitly designed to be embedded in external dashboards, CI widgets, or public pages, since `Api::CCMenuController` accepts the token via query string with no session), the holder gains unauthenticated read access to the build/deploy state of **every** stack managed by the Shipit instance, not just the one it was generated for. This satisfies the High-impact criterion "unauthenticated read of stack state, task streams, or deploy output," since disclosure of one stack's intentionally-scoped-looking URL grants cross-stack visibility.

### Likelihood Explanation
No special privileges are required beyond being a logged-in Shipit user able to visit any one stack's settings page and click "Generate CCMenu URL" (a normal, low-privilege UI action available to any authenticated team member). The resulting URL is designed for external, unauthenticated consumption, so it is realistically exposed outside the trust boundary (embedded in CI dashboards, status pages, etc.). The bug is deterministic — no race condition or edge case is needed; the very first token generated for any stack already has global scope.

### Recommendation
Bind the `ApiClient` to the specific stack at creation time, and key the `find_or_create_by!` lookup on `(creator, stack, name)` instead of just `(creator, name)`:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')
end
```

This restores the intended equality: "the stack a token authorizes" == "the stack it can be used to read," matching the enforcement already present in `Api::BaseController#stacks` for genuinely stack-scoped clients (e.g. `here_come_the_walrus` fixture).

### Proof of Concept
1. As an authenticated Shipit user, visit `stacks/A/settings` and click to generate a CCMenu URL. Note the returned `token` query parameter.
2. Inspect the DB / behavior: the underlying `ApiClient` record has `stack_id: nil`.
3. Using that same `token`, call `GET /api/stacks/B/ccmenu` (any other, unrelated stack `B`).
4. Observe `200 OK` with stack B's build/deploy XML status returned, despite the token having been generated exclusively from stack A's settings page — confirmed by the existing test `test/controllers/api/ccmenu_controller_test.rb` which shows the token is validated only for the `read:stack` permission, not for a specific `stack_id`: [6](#0-5)

```ruby
# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }
```
