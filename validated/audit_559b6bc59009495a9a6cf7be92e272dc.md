## Title
API client scoped to one stack can read the CI status (CCMenu feed) of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper to bypass the API-client stack scoping that `Shipit::Api::BaseController` enforces for every other API endpoint, allowing a token that authorizes read access to only one stack to read the deploy/CI state of every stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a stack, and `stack` (used by every other API controller, e.g. `Shipit::Api::StacksController#stack` and `Shipit::Api::TasksController#task`) always resolves through this scoped `stacks` relation. This is the binding the protocol intends: `ApiClient.stack_id` authorizes exactly one `Stack`.

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this relation entirely: [2](#0-1) 

`Stack.from_param!(params[:stack_id])` resolves any stack in the database by its param, independent of `current_api_client.stack_id`. The `require_permission :read, :stack` before-action only checks that the token has the string permission `read:stack` present in `ApiClient#permissions` — it never checks `check_permissions!`/`stack_id` binding: [3](#0-2) 

So the only enforcement applied to this endpoint is "does this token have `read:stack` anywhere in its permission list", never "is this token's `stack_id` equal to the stack being requested." A stack-scoped read-only token (e.g. the `here_come_the_walrus` fixture, scoped to a single stack via `stack:` association and `permissions: ['read:stack']`) is exactly such a token: [4](#0-3) 

Using that token against `GET /api/stacks/:stack_id/ccmenu.xml` with a *different* `stack_id`, `show` renders that other stack's latest deploy/rollback state: [5](#0-4) 

This is the exact bug class described in the report, applied to Shipit: `ApiClient.stack_id` is the field the token's authorization is scoped to (`stack a token authorizes`), but the actual controller uses an unscoped `Stack.from_param!` lookup (`the stack it touches`), breaking the equality `token.stack_id == stack_being_read`.

### Impact Explanation
Any holder of a `read:stack` API token scoped to one stack (which is routinely handed out by `CCMenuUrlController#fetch` to any authenticated Shipit user for CI-dashboard integration, and is visible in plaintext on the API client's show page) can enumerate and read the deploy/rollback status of every stack in the Shipit instance, including private or restricted stacks the token holder has no authorization for. This is an unauthenticated-for-that-resource read of stack state — one of the explicitly listed High-impact outcomes (escalation past the token's authorized scope to read stack state).

### Likelihood Explanation
Likely and low-effort to exploit: the attacker only needs any valid `ApiClient` token with the `read:stack` permission (these are routinely created, e.g. automatically by `CCMenuUrlController#fetch` for CI dashboard integrations) and the numeric/slug `stack_id` of the target stack, which is not treated as a secret elsewhere in the application (stack IDs/slugs are visible in URLs across the UI). No additional privileges, GitHub access, or session are required beyond possessing one legitimately-scoped token.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` go through the same scoped lookup as every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override entirely (falling back to `BaseController#stack`) so that `current_api_client.stack_id` is always honored.

### Proof of Concept
1. Create (or reuse) a `Stack` `B` that is not associated with the attacker's `ApiClient`.
2. As a legitimate low-privilege user with access to stack `A`, obtain a CCMenu token via `CCMenuUrlController#fetch` (or possess any existing token scoped to stack `A` with `read:stack` permission), e.g. `token_A`.
3. Send `GET /api/stacks/<B_id_or_slug>/ccmenu.xml?token=<token_A>`.
4. Observe that `Shipit::Api::CCMenuController#show` renders stack `B`'s latest deploy/rollback status (`deploys_and_rollbacks.last`), even though `token_A.stack_id != B.id`, whereas the equivalent request to `Shipit::Api::StacksController#show` or `TasksController#index` for stack `B` with `token_A` would correctly be rejected (empty scope from `stacks`/`from_param!` raising not-found). # frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
