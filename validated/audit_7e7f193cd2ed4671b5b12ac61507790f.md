### Title
Uncaught exception in `in merkle` authentifier evaluation due to unvalidated merkle proof deserialization crashes node process - (File: ocore/definition.js)

### Summary
`Definition.validateAuthentifiers`'s `'in merkle'` handling calls `merkle.deserializeMerkleProof(serialized_proof)` on an attacker-controlled authentifier string without a try/catch, unlike sibling cases in the same function. Any resulting exception is uncaught by the surrounding validation chain and reaches the global `uncaughtException` handler in `network.js`, which deliberately re-throws to terminate the process.

### Finding Description
`definition.js` (`validateAuthentifiers` → `evaluate`, `'in merkle'` case) reads `assocAuthentifiers[path]` — data taken directly from `objAuthor.authentifiers` in an untrusted, network-received unit — and passes it unguarded into `merkle.deserializeMerkleProof()`: [1](#0-0) 
Compare this to the `'address'` case a few hundred lines earlier in the *same* function, which wraps a functionally similar untrusted-data-driven hash computation in `try { ... } catch (e) { return cb2(false); }`: [2](#0-1) 
and the analogous `'hash'`/`'definition template'` cases which are similarly defensive: [3](#0-2) 
No equivalent guard exists for the merkle-proof deserialization call. `validateAuthentifiers` itself is invoked from `validateAuthor` during ordinary unit validation (`validation.js`) with no top-level try/catch around the whole authentifier evaluation switch statement: [4](#0-3) 
If `merkle.deserializeMerkleProof` performs unchecked slicing/parsing of the base64/serialized proof string (the class of bug reported for SM2 PKE — trusting a length/format without validating it against the actual buffer size before slicing), a short or malformed value in `assocAuthentifiers[path]` will throw synchronously inside the callback chain rather than being funneled into `cb2(false)`.
Any exception that escapes this deep, nested, callback-based validation flow is not caught anywhere up the call stack (`handleJoint` in `network.js` only supplies validation *result* callbacks, not a wrapping try/catch around synchronous throws), so it becomes an `uncaughtException`, which `network.js` intentionally converts into a process crash: [5](#0-4) 

### Impact Explanation
Because the trigger is the raw bytes of a single unit's `in merkle` authentifier, every full node that receives and validates that unit deterministically executes the same vulnerable code path and crashes identically. This is a network-wide denial of service: the malicious unit can be broadcast to peers, each of which crashes upon validating it, and repeated posting/propagation can be used to prevent honest nodes from validating and confirming any subsequent units — i.e., a network unable to confirm new units.

### Likelihood Explanation
Any unprivileged unit poster who controls an address whose definition contains an `in merkle` clause (a standard, documented oscript definition primitive) can craft an authentifier value for that path that is malformed/undersized relative to what `deserializeMerkleProof` expects, then post a unit signed with that authentifier. No special privileges, hub/peer position, or leaked keys are required — this is reachable purely through normal unit submission.

### Recommendation
Wrap the `merkle.deserializeMerkleProof` / `merkle.verifyMerkleProof` calls in the `'in merkle'` case of `definition.js` in a try/catch, returning `cb2(false)` (and setting `fatal_error` as appropriate) on any parsing exception, consistent with the defensive pattern already used in the `'address'` and `'hash'` cases of the same function. Additionally, harden `merkle.deserializeMerkleProof` itself to validate lengths/structure before any internal slicing and to throw only well-defined, caught errors.

### Proof of Concept
Concrete exploitation requires confirming the exact unchecked operation inside `merkle.js`'s `deserializeMerkleProof`, which was not available in the indexed context. Conceptually: post a unit whose author has an address defined with `["in merkle", [[oracle_address], "feed_name", "element"]]`, and supply `authentifiers[path]` equal to a truncated/malformed serialized proof string (e.g., too short to contain the expected number of hash segments). If `deserializeMerkleProof` performs a `split`/`substr`/index access assuming a minimum length without checking it first, this throws synchronously, propagates out of `validateAuthentifiers`, and crashes the receiving node via the global `uncaughtException` handler. This must be validated against the actual `merkle.js` source before treating the PoC as proven.
