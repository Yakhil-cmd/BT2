### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on `repository.full_name` — cross-repository / cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify the HMAC signature against using `repository.owner.login` (falling back to `organization.login`), but the webhook handlers that actually mutate state select the target `Repository`/`Stack` using an entirely different field, `repository.full_name`. Neither value is validated against the other, so a payload can be crafted where the "authenticating" org differs from the "written" repository.

### Finding Description
The signature check computes the field used to pick which org's secret to verify with: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. This value is used only to look up `Shipit.github(organization: repository_owner)` and verify `X-Hub-Signature` against that specific organization's `webhook_secret` — a per-organization secret, as documented for multi-org installs: [3](#0-2) 

Once the signature is verified, `WebhooksController#create` dispatches the entire raw payload to the registered handler(s) unchanged: [4](#0-3) 

The base `Handler` class — used by `PushHandler` and `CheckSuiteHandler` — resolves the actual `Repository`/`Stack` to operate on using a *different* payload field, `repository.full_name`: [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` to find the repository purely by owner/name string match, with no cross-check against `repository.owner.login`: [6](#0-5) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack, and `CheckSuiteHandler#process` schedules check-run refreshes for commits on that stack: [7](#0-6) [8](#0-7) 

**Equality broken:** the binding `organization_that_authenticated == repository_that_is_written` is violated. `repository.owner.login` (or `organization.login`) determines *whose secret* validated the request; `repository.full_name` determines *which repository's stacks* get written to. These two values are never required to match.

**Before attacker action:** in a multi-org Shipit deployment (`Shipit.github` configured per-organization, as documented), each org's webhook secret only authorizes webhook traffic claiming to originate from that org's repositories.

**After attacker action:** an actor who knows/controls OrgA's webhook secret (e.g., because they administer the GitHub App installation on OrgA — not a privileged Shipit account, not a `GITHUB_TOKEN`) can POST a payload to `/webhooks` with `repository.owner.login = "orgA"` (making `verify_webhook_signature` pass using OrgA's secret) but `repository.full_name = "orgB/some-repo"` where OrgB is an unrelated organization/repository also tracked by the same Shipit instance. The `PushHandler`/`CheckSuiteHandler` will resolve stacks belonging to OrgB and act on them (queue `GithubSyncJob` with an attacker-chosen `expected_head_sha`, or trigger check-run refresh cycles), even though the request was never validated against OrgB's own credentials.

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding explicitly called out as in-scope. Forcing `sync_github` with an attacker-chosen `expected_head_sha` for a repository/stack the attacker has no legitimate relationship to constitutes an unauthorized cross-repository write into another organization's stack state, satisfying the Critical "cross-repository writes" impact bar.

### Likelihood Explanation
Requires that the Shipit instance is configured with multiple GitHub organizations (a documented supported configuration) and that the attacker legitimately controls one organization's GitHub App webhook secret (e.g., as an admin of their own org's installation) — this is an "unprivileged" position with respect to the *victim* organization/repository, matching the required threat model (no Shipit session, no `ApiClient` token, no victim-org GitHub credentials needed).

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`, enforce that the organization used to select/verify the webhook secret matches the owner embedded in `repository.full_name` before any handler processes the payload — e.g., reject the request if `repository.full_name.split('/').first != repository_owner` (case-insensitively). Alternatively, look up the target `Repository` first and verify the signature using that repository's own owner-derived `GitHubApp`/secret rather than trusting a value that is decoupled from the field used for state mutation.

### Proof of Concept
1. Shipit configured with two orgs in `secrets.yml`: `orgA` (secret `S_A`) and `orgB` (secret `S_B`), each with a tracked repository/stack (`orgA/repoA`, `orgB/repoB`).
2. Attacker controls the GitHub App installed on `orgA` and thus knows `S_A` (legitimately, as an org admin — not privileged within Shipit or org B).
3. Attacker builds a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": {"login": "orgA"}, "full_name": "orgB/repoB" }
}
```
4. Attacker signs the raw body with `S_A` and sends it as `X-Hub-Signature`, `X-Github-Event: push`, to `/webhooks`.
5. `verify_signature` resolves `repository_owner = "orgA"`, fetches `Shipit.github(organization: "orgA")`, and verifies successfully with `S_A`.
6. `PushHandler#process` resolves `repository_name` from `full_name` = `"orgB/repoB"`, looks up `orgB`'s repository/stacks, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — mutating OrgB's stack state despite the request never being authenticated with OrgB's credentials.
