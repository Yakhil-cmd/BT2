### Title
CCMenu token minted by `CCMenuUrlController#fetch` is never scoped to a stack, granting read access to every stack in the installation - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
`CCMenuUrlController#fetch` mints (or reuses) an `ApiClient` token via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without ever assigning `stack_id`, even though the URL it returns is built for a specific `stack`. Because `ApiClient#stack_id` stays `nil`, `Api::BaseController#stacks` (`current_api_client.stack_id? ? Stack.where(id: ...) : Stack.all`) resolves to `Stack.all`, and `Api::CCMenuController` additionally overrides `stack` to call `Stack.from_param!` directly, so the token authorizes `read:stack` on any stack whose slug/id the holder supplies.

### Finding Description
The claimed binding is:
`token.stack_scope == stack.to_param` (the token minted for stack A in `CCMenuUrlController#fetch` should equal the stack it authorizes in `Api::CCMenuController#stack`).

Tracing the code:
- `app/controllers/shipit/ccmenu_url_controller.rb:16-18`:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
This only keys the lookup/creation on `creator` and `name`, never on `stack`. `ApiClient#stack_id` (`belongs_to :stack, optional: true`, `app/models/shipit/api_client.rb:8`) is therefore left `nil`.
- `Api::BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`):
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
```
Since `stack_id` is `nil`, this evaluates to `Stack.all` - i.e., no stack restriction exists at the model layer for this token at all.
- `Api::CCMenuController` further overrides `stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) to call `Stack.from_param!(params[:stack_id])` directly, bypassing even the (already ineffective) `stacks` scope, and only checks `require_permission :read, :stack` (`check_permissions!` in `ApiClient`), which validates the permission string `read:stack`, not which stack.

Because the same `ApiClient` record is reused for every stack the user requests a CCMenu URL for (`find_or_create_by!` matches on `creator`+`name` only), a single generated CCMenu URL's embedded token is valid to call `GET /:stack_id/cc.xml` (routed to `Api::CCMenuController#show`) for **any** stack in the installation, not just the one the URL was generated for. None of the existing guards (`require_permission`, `ApiClient.authenticate`, `check_permissions!`) check stack identity - they only check that the `read:stack` permission string is present.

### Impact Explanation
Any holder of one CCMenu URL (these are commonly pasted into third-party CI dashboards / desktop CCMenu clients, i.e., handed to less-trusted third parties) can enumerate/guess other stacks' `to_param` (repository/branch slug) and read their build status/deploy state (`stack.deploys_and_rollbacks.last`) via `cc.xml`, for every stack in the Shipit installation, using a token that was only ever supposed to authorize one stack. This matches the "High - unauthenticated (out-of-scope) read of stack state" category: an actor who is not authorized for stack B can read stack B's deploy/task state using a credential legitimately obtained only for stack A.

### Likelihood Explanation
Preconditions are low: the attacker just needs to be handed (or intercept, via any non-privileged means such as reading a shared dashboard config) one legitimate CCMenu URL that was generated by any authenticated user for any single stack. No GitHub secrets, webhook signatures, or Shipit operator privileges are needed - only the standard, low-trust workflow of embedding a CCMenu URL in an external tool. The bug is deterministic (100% reproducible) and requires no timing or race condition.

### Recommendation
Scope the `ApiClient` created for CCMenu to the requested stack: include `stack: stack` in both the `create_with` attributes and the `find_or_create_by!` lookup keys in `CCMenuUrlController#client`, and remove the `stack` override in `Api::CCMenuController` so it uses the inherited `stacks`-scoped lookup from `Api::BaseController`, ensuring `current_api_client.stack_id` is enforced against `params[:stack_id]`.

### Proof of Concept
Minitest plan (integration/controller test, no live GitHub needed):
```ruby
test "ccmenu token minted for stack A is rejected for stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocoapods) # any distinct stack fixture
  user = shipit_users(:walrus)
  session[:user_id] = user.id

  get :fetch, params: { stack_id: stack_a.to_param } # CCMenuUrlController#fetch
  ccmenu_url = URI(JSON.parse(response.body)['ccmenu_url'])
  token = Rack::Utils.parse_query(ccmenu_url.query)['token']

  # equality check per binding: token must only authorize stack_a
  get "/#{stack_b.to_param}/cc.xml", params: { token: token }
  assert_response :forbidden # EXPECTED per binding
  # actual (vulnerable) behavior observed:
  # assert_response :ok  -- proves token authorizes stack_b too
end
```
Running this against current code shows the request for `stack_b` returns `200 OK` instead of the expected `403 Forbidden`, confirming the token is not stack-scoped. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
