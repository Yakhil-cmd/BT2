### Title
API-client stack scoping bypass in CCMenu endpoint allows reading any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single `stack` (via `belongs_to :stack, optional: true`), and `Api::BaseController` is supposed to enforce that scoping for every read by filtering the visible `Stack` set through `current_api_client.stack_id?`. `Api::CCMenuController`, however, overrides the inherited `stack` resolution and loads the requested stack directly by param, never checking whether the authenticated client is actually authorized for that particular stack. This breaks the equality "stack a token authorizes == stack the action touches".

### Finding Description
`Api::BaseController` defines the authorization-scoped stack lookup: [1](#0-0) 

`stacks` deliberately restricts the visible set to `current_api_client.stack_id` when the client is stack-scoped, which is exactly the mechanism used to create narrowly-scoped tokens, e.g. the CCMenu URL helper that creates a `read:stack`-only client bound to one specific stack: [2](#0-1) 

But `Api::CCMenuController` overrides `stack` and resolves it with an unscoped, direct lookup that ignores the client's `stack_id` binding entirely: [3](#0-2) 

The only authorization gate applied before `show` runs is a coarse permission-name check, not a stack-identity check: [4](#0-3) [5](#0-4) 

`check_permissions!` only verifies the string `"read:stack"` is in the token's `permissions` array; it never compares `stack_id`. Combined with `CCMenuController#stack` bypassing `stacks`, any token that has the `read:stack` permission — including one deliberately minted and scoped to a single stack — can be replayed against `/api/stacks/:any_stack_id/ccmenu.xml?token=...` for an arbitrary other stack.

Equality that should hold but doesn't:
`token.stack_id (the stack the token authorizes)` == `stack (the stack the CCMenu action actually reads)`

Before the attacker's request: token is scoped to Stack A, `current_api_client.stack_id == A.id`.
After the request: `stack` in `CCMenuController#show` is resolved to Stack B (any stack), with no check that `B.id == current_api_client.stack_id`.

### Impact Explanation
This allows disclosure of deploy/build state — lock status, last build status/label/time, stack name — for any stack in the Shipit instance using a token that was only ever supposed to see one stack's status. This is an authorization-scope escalation: reading stack state the token holder was never granted access to, matching the "unauthorized read of stack state" class of impact.

### Likelihood Explanation
Exploitation only requires possessing any valid CCMenu-style token with `read:stack` permission (these tokens are routinely generated per-stack via `CCMenuUrlController` and embedded in CI dashboard URLs, which are lower-trust, often-shared links). No other privilege or secret is needed; the attacker simply changes `stack_id` in the URL path while reusing their own legitimately-issued, narrowly-scoped token.

### Recommendation
Make `Api::CCMenuController#stack` go through the same authorization-scoped `stacks` relation used elsewhere in `Api::BaseController` (e.g. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so a client bound to one stack cannot resolve any other stack.

### Proof of Concept
1. Create (or obtain) a CCMenu token bound to Stack A: `CCMenuUrlController#fetch` yields a URL like `/stacks/org/repo-A/env/ccmenu_url?token=<TOKEN_A>`, backed by an `ApiClient` with `permissions: ['read:stack']` and `stack: StackA`.
2. Request a different stack's CCMenu feed using that same token:
   `GET /api/stacks/org/repo-B/env/ccmenu.xml?token=<TOKEN_A>`
3. `CCMenuController#authenticate_api_client` accepts `TOKEN_A` (valid signature), `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, and `stack` resolves Stack B via the unscoped `Stack.from_param!`, returning Stack B's build/lock status even though the token was only authorized for Stack A.
