### Title
Unbounded, unauthenticated log growth via unconditional `console.log` on every posted unit/joint validation - ([File: validation.js])

### Summary
`validation.validate()` in `validation.js` unconditionally writes a log line for every single joint/unit it is asked to validate, both at entry and on every completion (success or failure), before any cheap sanity/PoW-like cost is imposed on the sender. Because this function is the single entry point reached from `post_joint` (light clients posting units), `handleOnlineJoint`/`handleSavedJoint` (units broadcast/relayed from peers), and `aa_composer.validateAndSaveUnit` (AA-generated response units), any unprivileged actor who can get a syntactically-shaped unit object accepted into this function (trivially cheap to construct - it only needs a `unit` object with a `.unit` string field to pass the initial guard) can force the node to emit large, attacker-influenced log lines repeatedly and indefinitely, exhausting log storage/IO - the same bug class as CVE-2023-48369 ("fails to limit the log size of server logs ... specially crafted requests to different endpoints").

### Finding Description
`validate()` starts with: [1](#0-0) 
which logs the incoming unit identifier before any structural validation (hash length, unit hash correctness, size limits, etc.) is performed. Because logging happens before these checks, an attacker only has to satisfy the very first (thrown, not gracefully rejected) guard - `typeof objUnit === "object"` and `objUnit.unit` being truthy - to get a log line written on every single call, at effectively zero cost to the caller.

On the completion path, `validate()` again unconditionally logs, embedding the full validation error object (via `JSON.stringify(err)`), which can include arbitrary attacker-supplied identifiers/arrays such as `arrMissingUnits`: [2](#0-1) 
and on success: [3](#0-2) 

This function is reachable from multiple unprivileged entry points without any rate limiting or log-size capping:
- `network.js` `handleJoint()`, used for both peer-relayed joints and `post_joint` (light-client self-posted units), logs additional lines per invalid unit at `ifUnitError`/`ifTransientError`/`ifNeedHashTree` in addition to calling `validate()`: [4](#0-3) 
- `aa_composer.js` `validateAndSaveUnit()`, invoked once per AA response unit produced while handling an externally-triggered AA (i.e., triggerable by any unprivileged user who sends a payment/trigger to an AA address), also logs on validation failure: [5](#0-4) 
- `divisible_asset.js`, used for private/divisible-asset payment validation reachable by any private-payment counterparty, logs on every OK/save outcome, embedding the unit id and private element data: [6](#0-5) 

None of these logging calls are gated by log level, sampling, or rate limiting, and none cap the size of the logged content (e.g., `JSON.stringify(err)` for arbitrary validation errors, or `util.inspect(objUnit, {depth:6})` for full AA-generated units seen elsewhere in `aa_composer.js`).

### Impact Explanation
An attacker who is only an unprivileged unit poster, AA trigger sender, or private-payment counterparty can force the node to write an unbounded number of log lines with attacker-influenced content, at a cost far lower than the cost imposed on the victim node (disk I/O, log rotation/CPU, potential disk-space exhaustion). This does not cause double-spends or fund loss directly, but it can degrade node availability/observability and, if disk fills up, can impair the node's ability to continue writing its database/log files, contributing to a "network unable to confirm new units" condition for the affected node. This matches the Medium severity of CVE-2023-48369 (log-flooding, availability impact only, no confidentiality/integrity impact).

### Likelihood Explanation
High likelihood of triggering the logging itself: constructing a minimal object such as `{unit: {unit: "x"}}` and submitting it via `post_joint` (light client command) is trivial and requires no valid signature, PoW, or fee payment, since the log write in `validate()` occurs before the unit-hash/length checks. Repeating this at high frequency (many connections / many requests per connection) causes proportional log growth. The same pattern applies to sending numerous invalid AA triggers or asset transfers to a given node, each producing additional unconditional log lines in `aa_composer.js` / `divisible_asset.js`.

### Recommendation
- Remove or heavily rate-limit the unconditional `console.log` calls in `validation.js` (lines 126, 454, 480), `network.js` `handleJoint()` per-unit logging, `aa_composer.js` `validateAndSaveUnit`, and `divisible_asset.js` `ifOk`/`onDone` handlers.
- Move the entry log in `validate()` after the cheap structural checks (unit hash length/hash correctness) so a log line is only produced for units that at least pass basic sanity checks.
- Cap the size of any logged payload (e.g., truncate `JSON.stringify(err)` and avoid embedding full `util.inspect` dumps of units/objects).
- Apply per-peer/per-IP or per-connection rate limiting on `post_joint` and joint-validation logging specifically, independent of general request-rate limiting, so that repeated invalid submissions cannot generate unbounded log volume.
- Consider routing this class of diagnostic logging through a level-gated logger (debug/trace) that can be disabled in production rather than always-on `console.log`.

### Proof of Concept
1. As an unprivileged light-client peer, connect to a full node/hub via the existing WebSocket protocol.
2. Send a `post_joint` request repeatedly (in a tight loop / many parallel connections) with a minimal payload of the form:
   ```json
   ["request", {"command":"post_joint", "params": {"unit": {"unit": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="}}, "tag": "x"}]
   ```
   (any string satisfying the `objJoint.unit.unit` truthiness check; it need not be a valid hash yet - `validate()` logs before checking its length/format).
3. Each such request causes at least one `console.log("\nvalidating joint identified by unit "+...)` at `validation.js:126`, followed by a second log line embedding the full error at `validation.js:454` when the malformed unit is rejected, plus additional lines from `network.js` `handleJoint()`'s `ifUnitError`/`ifJointError` handlers.
4. Repeating step 2 at scale (many peers, high request rate) grows the node's log file without bound and without any built-in cap or throttle, reproducing the log-flooding condition described in CVE-2023-48369.
