### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a status from any authenticated repository mutate commit state of another repository sharing the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by bare SHA across the entire `commits` table, with no scoping to the repository that authenticated the webhook. Since GitHub commit SHAs are content-addressed and can collide across independently-owned repositories (e.g. a fork or replayed identical commit), a legitimately-signed `status` webhook from an attacker's own tracked repository can write a `Status` row against a `Commit` belonging to an unrelated victim stack, affecting `release/gate` and other CI checks used for deploy/merge gating.

### Finding Description
The broken binding: the handler should enforce `commit.stack.repository == authenticated_repository`, but instead the invariant actually enforced is only `commit.sha == params.sha`.

Code path: `WebhooksController#create` parses the raw payload and dispatches to `Shipit::Webhooks.for_event(event)` handlers [4](#0-3) . Before dispatch, `verify_signature` validates the payload was signed with the webhook secret configured for `repository_owner` as read from the *attacker-controlled* `params.dig('repository','owner','login')` [5](#0-4) [6](#0-5) . This only proves the request genuinely originated from the org/repo named in the payload — it says nothing about which `Commit`/`Stack` rows that repository is allowed to touch.

`Handler` provides a `stacks` helper that correctly scopes to `Repository.from_github_repo_name(repository_name)` [3](#0-2) , and other handlers like `CheckSuiteHandler` use it before touching commits: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) ... }` [2](#0-1) . `StatusHandler#process`, however, bypasses this entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  — a global, repository-agnostic lookup.

`create_status_from_github!` then writes the status and re-evaluates commit state (`add_status`), which can flip `deployable?`/`blocked?` and trigger `stack.schedule_merges` [7](#0-6) [8](#0-7) .

Exploit flow: an attacker owns/controls a repository that is already tracked by the same multi-tenant Shipit instance (so a real GitHub webhook for it carries a valid HMAC signature for its own org's `webhook_secret`). The attacker crafts (e.g., by forking or replaying) a commit whose SHA is identical to a commit that also exists in a victim's stack — SHA1 collision via identical content is achievable deliberately (e.g. cherry-picking/porting the exact same tree+parents+timestamps+message from a public victim repo into the attacker's own repo). The attacker's repository then legitimately emits (or the attacker triggers via GitHub UI/API on their own repo) a `status` event with `context: release/gate`, `state: success` for that SHA. This webhook is correctly signed for the attacker's own org, passes `verify_signature`, and reaches `StatusHandler#process`, which finds *all* `Commit` rows across the DB with that SHA — including the victim's — and writes/flips the `release/gate` status on the victim's commit, potentially unblocking `deployable?`/triggering `schedule_merges` on a stack the attacker never authenticated against.

Existing guards do not stop this: `verify_signature` validates repository/org identity of the *sender*, not scoping of the *commit rows mutated*; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context`, etc.), not repo ownership of the target commit; there is no `stacks`/`Repository.from_github_repo_name` filter anywhere in `StatusHandler`.

### Impact Explanation
A payload correctly authenticated for repository A (attacker's own tracked repo) can write a `Status`/gate result onto a `Commit` belonging to repository B (victim stack) whenever the two share a commit SHA. This is a cross-repository state mutation: one repo's status webhook flips CI/gate state for another stack's commit, which can unblock deploys or merges gated on `release/gate` or other statuses (`Commit#deployable?`, `Commit#blocked?`, `Stack#schedule_merges`). This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." It is repeatable against any repository pair that shares a colliding SHA and is not limited to a single stack — every `status` webhook received by the engine is subject to this unscoped lookup.

### Likelihood Explanation
Preconditions: (1) attacker must own/control a repository that is already registered as a tracked repository under a Shipit-configured GitHub org (so their webhooks carry a valid signature the engine will accept), (2) attacker must produce a commit whose SHA collides with one that also exists on the victim's stack — trivially achievable if the victim's repo (or a shared upstream) is public and the attacker replicates the exact commit content (tree, parents, author/committer timestamps, message) into their own repo history, or if repos share history via forks/mirrors. Both conditions are attacker-feasible without needing any secret, and require no special privilege beyond controlling one tracked repository (unprivileged relative to the victim's stack). It is fully repeatable and scriptable once a colliding SHA is found or engineered.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository the same way `CheckSuiteHandler` does: resolve `stacks` (or `Repository.from_github_repo_name(repository_name)`) from the payload's `repository.full_name`, and restrict the commit lookup to `stack.commits.where(sha: params.sha)` (or equivalently join `Commit` through `Stack`/`Repository` before writing statuses), rather than issuing a bare, table-wide `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers_test.rb` style, no live GitHub):
1. Create two `Repository`/`Stack` fixtures: `repo_a` (attacker-owned, e.g. `attacker/attacker-repo`) and `repo_b` (victim, e.g. `victim/victim-repo`), each with its own `Stack` requiring `release/gate` in `blocking_statuses`/required statuses via `deploy_spec`.
2. Create a `Commit` on `repo_b`'s stack with `sha: "deadbeef" * 5` (40 hex chars) and no `release/gate` status yet; assert `commit_b.blocked?` (or `deployable?` false) as the "before" state — explicit equality: `commit_b.deployable? == false`.
3. Build a `status` webhook payload with `repository.full_name = "attacker/attacker-repo"`, `sha` equal to `commit_b.sha`, `context: "release/gate"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature, as unit test).
5. Reload `commit_b`; assert it now has a `Status` with `context: "release/gate"`, `state: "success"`, and assert `commit_b.deployable? == true` (or `blocked? == false`) — the "after" state — proving repo A's payload mutated repo B's commit despite `payload['repository']['full_name']` never matching repo B, demonstrating the equality `commit.stack.repository == authenticated_repository` is violated.
