### Title
Webhook Signature Verification Is Scoped by `repository.owner.login`, But Event Processing Is Scoped by an Unrelated `repository.full_name` Field, Allowing Cross-Organization Forged Events - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate a GitHub webhook against using the payload field `repository.owner.login` (with a fallback to `organization.login`), but every `Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to act on using a completely different payload field, `repository.full_name`. Nothing binds these two fields together, and if the organization named in `repository.owner.login` has no `webhook_secret` configured, signature verification is skipped entirely (`return true unless webhook_secret`). This lets an unauthenticated attacker forge an event that is "authenticated" against one (unconfigured) organization while its side effects are applied to a stack belonging to a completely different organization/repository.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up that organization's config and, if the org exists but has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` short-circuits to `true` regardless of what signature (or none) is presented: [3](#0-2) 

The `webhook_secret` field is explicitly documented as optional/`nil`-able per organization in a multi-org configuration: [4](#0-3) 

Once the (possibly-bypassed) signature check passes, `WebhooksController#create` dispatches the raw parsed JSON to the relevant handler: [5](#0-4) 

Every handler resolves which `Repository`/`Stack` to mutate using `payload.dig('repository', 'full_name')` — an entirely separate field from the one used for signature-organization selection: [6](#0-5) 

For example, `PushHandler` uses this `stacks` scope to trigger `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the attacker-supplied branch: [7](#0-6) 

This breaks the intended equality: `organization authorizing the signature == organization whose repository is written`. Concretely:
- Before: `repository.owner.login` (or `organization.login`) is the field GitHub actually sets to the real event's org, and it always matches `repository.full_name`'s owner, so the two happen to coincide for legitimate GitHub-originated traffic.
- After (attacker's request): the attacker sets `repository.owner.login` to any organization configured in `secrets.yml` that has `webhook_secret: nil`/unset (satisfying `verify_signature` trivially), while setting `repository.full_name` to `victim-org/victim-repo` — a completely different, sensitive stack that they do not control on GitHub.

Because the two fields are never cross-checked, `verify_signature` "authenticates" the request against the wrong (unsecured) org, and the handler then unconditionally acts on the attacker-chosen `repository.full_name`.

### Impact Explanation
This is a cross-repository/cross-organization write: an unprivileged, unauthenticated network attacker can inject fabricated GitHub events (`push`, `pull_request`, `status`, `check_suite`, etc.) targeting any repository/stack configured in the Shipit instance, as long as at least one configured organization in the multi-org setup has no `webhook_secret` (an explicitly supported and documented configuration). Depending on which handler is invoked this can force `GithubSyncJob` runs with attacker-chosen `expected_head_sha`, forge commit statuses, or drive pull-request-triggered review-stack provisioning/merge-status logic for a repository the attacker never actually has access to on GitHub — all without needing any Shipit session, `ApiClient` token, or the target organization's real `webhook_secret`.

### Likelihood Explanation
Likelihood is realistic in any Shipit deployment that manages more than one GitHub organization (the documented multi-org `secrets.yml` schema) where any single organization is left without a `webhook_secret` — a state the setup docs present as valid/optional rather than discouraged. No credentials, sessions, or GitHub App keys are required to exploit this; only knowledge of the low-security organization's name and the victim's `owner/name`, both of which are public GitHub identifiers.

### Recommendation
Bind the two fields together before dispatch: after resolving the signing organization for `verify_signature`, assert that it equals the owner segment of `repository.full_name` (or `organization.login` for org-level events) before invoking any handler, and reject the request otherwise. Additionally, treat a missing/blank `webhook_secret` for a configured organization as "signature verification not applicable to that organization's repositories" rather than "always verified", or require `webhook_secret` to be mandatory once multi-org configuration is enabled.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `unsafe-org` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`, hosts a real stack).
2. POST to the webhooks endpoint with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "unsafe-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
No `X-Hub-Signature` header is required, or any bogus value works.
3. `verify_signature` calls `Shipit.github(organization: 'unsafe-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'deadbeef...')` on the real victim stack, even though the request was never validated against `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
