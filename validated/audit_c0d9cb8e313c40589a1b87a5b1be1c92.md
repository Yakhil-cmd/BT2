### Title
Webhook signature is verified against the organization in the payload's `repository.owner.login`, not against the organization whose repository is actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to verify the request against using an unauthenticated, attacker-controlled field from the JSON body (`repository.owner.login` or `organization.login`), then hands the *entire* unauthenticated payload to the event handlers, which independently pick the stack/repository to mutate using a different field (`repository.full_name`). The two fields are never cross-checked, so the signature-verification-org binding and the write-target binding can be made to diverge.

### Finding Description
The controller resolves the app/secret used for HMAC verification from the request body itself, before the signature has been validated: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit explicitly supports multi-org configuration where each org has its own (optional) `webhook_secret`: [4](#0-3) 

Once `verify_signature` passes (either because the org resolved from `repository_owner`/`organization.login` has `webhook_secret` blank, or simply because that org's secret happens to be known to the attacker), the raw, attacker-supplied `params` are dispatched to every registered handler for the event: [5](#0-4) 

The handlers, however, determine which `Repository`/`Stack` to act on using a completely different, also-unverified field — `repository.full_name` — with no relation to the org used for signature verification: [6](#0-5) [7](#0-6) 

Concretely, `PushHandler` and `CheckSuiteHandler` use `stacks` (derived from `repository.full_name`) to enqueue GitHub sync jobs / check-run refreshes for a specific stack, entirely independent of which org's secret gated the request: [8](#0-7) [9](#0-8) 

The broken equality is: `organization whose webhook_secret authenticated the request` ≠ `organization/repository whose Stack state the handler mutates`. An attacker who knows (or can trivially satisfy, e.g. via a nil `webhook_secret`) the signature requirement for **any** GitHub org configured in `Shipit.github`, can forge a payload whose `repository.owner.login`/`organization.login` names that easy org while `repository.full_name` names an entirely different, already-onboarded target repository/stack, and have the handler act on that target stack.

### Impact Explanation
This allows an unauthenticated party to forge push/check_suite/status/membership events against stacks belonging to organizations they have no relationship or credentials for, as long as any other org configured on the same Shipit instance is signature-verifiable (blank secret, or a secret known to the attacker for an unrelated, less-sensitive org). Effects include forcing `GithubSyncJob`/`RefreshCheckRunsJob` for arbitrary stacks, injecting fabricated commit `Status` records, or creating `Team`/`User` records via the `membership` handler for a team/org the attacker doesn't own. This crosses an authentication boundary the Impact criteria treat as High ("escalation into `Shipit.github_teams` authorization" via forged membership events) and can influence merge/CI gating that feeds into deploy decisions.

### Likelihood Explanation
Low-to-Medium. It requires: (a) multi-org (or single-org with blank `webhook_secret`) configuration, which is an explicitly documented and supported setup, and (b) the attacker being able to send a request to the public `/github/*` webhook endpoint with a payload whose `repository.owner.login` differs from `repository.full_name`'s owner — no session, token, or GitHub write access is needed, since the endpoint is designed to be reachable by GitHub without prior authentication.

### Recommendation
Bind the signature-verification organization to the same field the handlers use to select the target repository/stack. Concretely, derive the org used for `Shipit.github(organization: ...)` from `repository.full_name`'s owner (or verify that `repository.owner.login` and the owner segment of `repository.full_name` match) before dispatching to handlers, and reject payloads where they diverge. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` for a *known* org with a blank secret when the payload targets a different org's repository; require an explicit secret per org that is used to gate writes to that org's repositories.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `victim-org` (has a `webhook_secret` and hosts the target `Stack` for `victim-org/app`), `throwaway-org` (configured with no `webhook_secret`, e.g. as shown in `config/secrets.development.example.yml`).
2. POST to `/github` (mounted webhook endpoint) with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "throwaway-org" }, "full_name": "victim-org/app" },
  "ref": "refs/heads/master",
  "after": "deadbeef..."
}
```
No `X-Hub-Signature` header is required to be correct, or any arbitrary value works, since `verify_signature` resolves `Shipit.github(organization: "throwaway-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
3. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which computes `stacks` from `payload.dig('repository','full_name')` = `"victim-org/app"`, matching the real, security-sensitive stack, and enqueues `GithubSyncJob` for it — despite the request never being signed by `victim-org`'s actual webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
