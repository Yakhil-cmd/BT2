### Title
Push webhook resolves victim stacks by `repository.full_name` while signature is verified only against `repository.owner.login`'s app config, letting an attacker impersonate a victim repo's push - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/push_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository_owner` (`params.dig('repository','owner','login')`), while `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks` (used by `PushHandler#process`) select which `Stack` rows to mutate using a completely different field, `payload.dig('repository','full_name')`. Nothing anywhere checks that `full_name` actually starts with `owner.login`, so an attacker who owns a GitHub org/app installation registered in Shipit can send a validly-signed webhook whose `repository.owner.login` is their own org (passing signature verification) but whose `repository.full_name` is `victim-org/victim-repo`, causing `stack.sync_github(expected_head_sha: ...)` to run against the victim's stack with an attacker-chosen `after` sha.

### Finding Description
Broken binding (stated as an equality that the code assumes but never enforces):
`repository_owner` (`params.dig('repository','owner','login')`) == the org/repo portion of `repository_name` (`payload.dig('repository','full_name')`).

Trace:
1. `POST /webhooks` reaches `WebhooksController#create` after `before_action` chain `check_if_ping, drop_unhandled_event, verify_signature` [1](#0-0) .
2. `verify_signature` picks the GitHub App/secret config via `Shipit.github(organization: repository_owner)` and validates the HMAC signature against that org's `webhook_secret` [2](#0-1) . `repository_owner` reads only `params.dig('repository','owner','login')` (or `organization.login`) [3](#0-2) .
3. If the attacker's own org has a registered Shipit GitHub App config (a normal, unprivileged setup for anyone who installs the Shipit GitHub App on their own org/repo), the signature check passes because it is computed with the attacker's own known `webhook_secret` over a payload the attacker fully controls.
4. `create` parses the raw JSON and dispatches to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
5. `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [5](#0-4) . `stacks` resolves via `Repository.from_github_repo_name(repository_name)&.stacks`, and `repository_name` is `payload.dig('repository', 'full_name')` — a field entirely independent from the one used for signature verification [6](#0-5) .
6. Since GitHub's real webhook delivery always keeps `owner.login` consistent with `full_name`, this divergence can only be produced by an attacker directly crafting the raw JSON body they POST to `/webhooks` — which they can fully control, since the "signature" only proves the request came from someone who knows *some* org's `webhook_secret`, not that the payload content is self-consistent.
7. No code path anywhere (controller, `Handler`, `PushHandler`, `ExplicitParameters` schema which only requires `:ref`/`:after`) cross-checks that `full_name`'s owner segment matches `repository_owner`. `drop_unhandled_event` only checks event type presence, not payload structure. `Repository.from_github_repo_name`/`Stack` validations only look up records that already exist for `victim-org/victim-repo`; they perform no ownership/authenticator match against the signing org.

Result: the attacker can force `sync_github(expected_head_sha: <attacker-chosen sha>)` to run on the victim's `Stack` even though the request was authenticated only against the attacker's own org's secret.

### Impact Explanation
This is a cross-repository mutation: a webhook that is only cryptographically valid for the attacker's own org/repo is used to invoke `Stack#sync_github` on a victim's stack that the attacker never authenticated for and does not own. `sync_github(expected_head_sha:)` updates the stack's recorded head commit/state from GitHub using an attacker-supplied `after` sha as the expected head — this directly corrupts the victim stack's tracked commit/head history. Per the question's binding, `Shipit::Rollback#commits`/`#variables` later range over `stack.rollback_variables`/commit history as trusted values when an operator performs a rollback, meaning attacker-influenced head state can propagate into rollback variable computation for the victim stack. This matches the "payload for one repository mutating another's stack/commit" Critical category. It is repeatable against any victim repository configured in Shipit, as long as the attacker controls any org that has its own valid Shipit GitHub App installation (which is a normal, unprivileged action available to any GitHub user/org).

### Likelihood Explanation
Preconditions: the attacker needs their own org/repo to be configured in Shipit with a real `webhook_secret` (achievable by installing the Shipit GitHub App on their own account/org — an unprivileged, self-service action, not requiring any victim secrets). They need to know or guess the victim's `full_name` (public info) and target branch. No GitHub App private key, `secret_key_base`, or victim `webhook_secret` is required — only the attacker's own valid secret, since the vulnerable check only verifies "signed by *an* org I trust" instead of "signed by *the* org this payload claims to be about." This is a low-cost, fully repeatable attack: one crafted `POST /webhooks` request per attempt, with the correct HMAC computed locally by the attacker using their own secret.

### Recommendation
In `Handler#repository_name`/`#stacks`, or upstream in `WebhooksController`, enforce that the `full_name`'s owner segment equals `repository_owner` (the value used to select the verifying secret) before resolving/mutating any `Stack`; reject the webhook (e.g., `head(422)`) if they diverge. Alternatively, derive the target repository strictly from the same trusted field used for signature verification (or validate `repository.full_name.split('/').first == repository.owner.login` in `PushHandler`/`Handler` before calling `stacks`).

### Proof of Concept
Minitest plan (no live GitHub calls; sign payload locally with attacker's known test secret):
1. Configure two orgs in test config: `attacker-org` (with a known `webhook_secret`) and ensure a `Shipit::Stack`/`Shipit::Repository` exists for `victim-org/victim-repo`.
2. Build a JSON push payload: `{"ref" => "refs/heads/master", "after" => "attackershasha", "repository" => {"owner" => {"login" => "attacker-org"}, "full_name" => "victim-org/victim-repo"}}`.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, raw_body)` — a value fully computable by the attacker.
4. `post shipit.webhooks_path, params: raw_body, headers: {'X-Github-Event' => 'push', 'X-Hub-Signature' => sig, 'Content-Type' => 'application/json'}`.
5. Assert response is `200 OK` (signature accepted).
6. Stub/mock `victim_stack.sync_github` and assert it is called with `expected_head_sha: "attackershasha"`, proving a payload signed only for `attacker-org` mutated `victim-org/victim-repo`'s stack — confirming `repository_owner != repository_name`'s owner segment yet the mutation proceeded.
