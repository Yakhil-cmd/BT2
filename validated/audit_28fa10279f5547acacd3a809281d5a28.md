### Title
Missing freeze-authority validation on pool token mints permits permanent DoS/fund-freezing of pool vaults - (File: programs/cp-swap/src/instructions/initialize.rs)

### Summary
`Initialize` (and `InitializeWithPermission`) accept `token_0_mint`/`token_1_mint` from any unprivileged caller and only constrain them with `mint::token_program`, never checking that the mint has no `freeze_authority`. The same absence of freeze-authority validation applies to `input_token_mint`/`output_token_mint` in the swap instructions and the vault mints referenced in `deposit.rs`/`withdraw.rs`. Any token mint — including one whose freeze authority is retained by a malicious pool creator — can therefore be paired into a pool.

### Finding Description
`token_0_mint` and `token_1_mint` in `Initialize` are validated only by `constraint = token_0_mint.key() < token_1_mint.key()` and `mint::token_program = token_0_program/token_1_program`, with no check on `mint::freeze_authority`. [1](#0-0) 

The identical pattern (no freeze-authority check, only `mint::token_program`) exists in `InitializeWithPermission`. [2](#0-1) 

Downstream, `Swap`'s `input_token_mint`/`output_token_mint` are derived only via `address = input_vault.mint` / `address = output_vault.mint`, again with no freeze-authority check, and the corresponding `input_vault`/`output_vault` token accounts (owned by the pool authority PDA) are used directly for CPI transfers. [3](#0-2) 

Because the pool's `creator`/`payer` is an ordinary `Signer` (any unprivileged wallet) and can supply arbitrary SPL/Token-2022 mints at pool-creation time, a malicious actor can create a pool using a mint they control the freeze authority for. Since the pool's vaults are ATAs owned by the `authority` PDA derived from `AUTH_SEED`, the mint's freeze authority can freeze the pool vault token account at any time after LPs have deposited or swappers have transferred funds into it.

### Impact Explanation
Once the vault token account tied to the malicious mint is frozen, all pool operations that require transferring out of (or into, depending on implementation) that vault — `deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, and creator-fee collection — will fail, because SPL Token/Token-2022 rejects transfers from frozen accounts. This permanently locks any tokens already deposited into that vault (both the paired legitimate token and, more importantly, LP principal), matching the report's classification of "Denial of Service" and "Permanent Loss of Funds" for the counter-asset and LP funds in that pool.

### Likelihood Explanation
Pool creation via `Initialize`/`InitializeWithPermission` is permissionless for anyone acting as `creator`/`payer`, and no on-chain constraint prevents a mint with a non-`None` `freeze_authority` from being used as `token_0_mint` or `token_1_mint`. An attacker only needs to create such a mint (trivial with SPL Token or Token-2022), initialize a pool pairing it with a legitimate asset (e.g. USDC/SOL), lure liquidity providers/swappers into using the pool, and then invoke `freeze_account` on the vault ATA. This requires a single crafted transaction stream and standard token tooling — no privileged access to the program itself is needed.

### Recommendation
Add an explicit constraint rejecting mints with a freeze authority (or requiring the pool/PDA to own it) for `token_0_mint`/`token_1_mint` in `initialize.rs` and `initialize_with_permission.rs`, e.g.:
```rust
#[account(
    constraint = token_0_mint.freeze_authority.is_none() @ ErrorCode::InvalidMint,
    mint::token_program = token_0_program,
)]
pub token_0_mint: Box<InterfaceAccount<'info, Mint>>,
```
Apply the same check symmetrically to `token_1_mint`. Since `input_token_mint`/`output_token_mint` in swap instructions are derived from the pool's own vault mints, fixing the check at pool-initialization time is sufficient to close this path for `deposit`, `withdraw`, and both swap directions.

### Proof of Concept
1. Attacker creates SPL mint `M` with `freeze_authority = attacker_key` and mints itself supply.
2. Attacker calls `initialize` (or `initialize_with_permission`) pairing `M` with USDC, becoming `creator`; no constraint rejects `M`'s freeze authority. [4](#0-3) 
3. Legitimate users call `deposit`/`swap_base_input` against this pool, moving USDC and `M` into the pool's vault ATAs owned by the `authority` PDA.
4. Attacker calls SPL Token's `freeze_account` on the pool's `M`-vault ATA using `attacker_key` as freeze authority.
5. All subsequent `swap_base_input`/`swap_base_output`/`withdraw` calls touching that vault fail because the frozen token account cannot be debited, permanently locking the paired USDC and LP funds in the pool.
