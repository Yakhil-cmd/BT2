### Title
Silent burning of legitimate stake/block rewards on unhandled distribution errors - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
`store_stake_accounts_in_partition` treats any error from `build_updated_stake_reward` (`AccountNotFound`, `ArithmeticOverflow`, `UnableToSetState`) as an unconditional "burn": the reward is discarded from state (`stake_reward_lamports_burned`/`block_reward_lamports_burned`) instead of being retried, redirected, or otherwise reconciled with the actual current state of the account. [1](#0-0)  This mirrors the GMX bug class: a legitimate, non-malicious state transition (negative price / here, a stake account no longer matching its calculation-time snapshot) is not classified into a recoverable/expected path, and the system takes an irreversible, loss-causing action (order cancellation / here, permanent reward burn) instead of correct handling.

### Finding Description
Partitioned epoch rewards are computed in two phases that are separated by many blocks: (1) `calculate_stake_rewards_and_commissions` snapshots stake delegations and computes `PartitionedStakeReward` entries at the epoch boundary, and (2) `distribute_epoch_rewards_in_partition` -> `store_stake_accounts_in_partition` -> `build_updated_stake_reward` applies those precomputed rewards to the *current* state of the stake account, read live from `stakes_cache_accounts`, at a later block height. [2](#0-1) 

`build_updated_stake_reward` looks up the account by pubkey in the live `stakes_cache_accounts` map; if it's not found (`AccountNotFound`), if `checked_add_lamports` overflows (`ArithmeticOverflow`), or if `set_state` fails (`UnableToSetState`), it returns an `Err(DistributionError)`. [3](#0-2) [4](#0-3) 

The caller treats every one of these `Err` variants identically as an unrecoverable burn:
```
Err(err) => {
    error!(...);
    stake_reward_lamports_burned += stake_reward_amount;
    block_reward_lamports_burned += block_reward_amount;
}
``` [5](#0-4) 

The developers' own comment states the expected invariant: *"Because stake accounts are checked in calculation, and further state mutation prevented by stake-program restrictions, there should never be rewards burned."* [6](#0-5)  This is precisely analogous to the GMX assumption that Chainlink prices "should never" go negative — the code path exists but is treated as impossible, so no reconciliation/backstop logic exists for it. If any normal, permissionless stake instruction (e.g. `Merge`, which removes the source account from `StakesCache` as a delegated `Stake` account, or `Split`/`Withdraw` that changes an account's balance/state between the calculation snapshot and the later distribution block) can cause the pubkey to no longer resolve to the expected `StakeStateV2::Stake` entry that `build_updated_stake_reward` expects, `AccountNotFound` is triggered and the already-earned reward for that pubkey (both inflation stake reward and any block reward) is silently discarded rather than credited anywhere — the lamports are removed from the un-distributed float and never appear in the destination account or accounted for by capitalization increases (only `stake_reward_lamports_minted` increases capitalization; burned amounts do not). [7](#0-6) 

I could not conclusively verify, within the indexing/search budget of this exercise, whether the stake program processor blocks `Merge`/`Split`/`Withdraw` for accounts with a pending, not-yet-distributed reward during the multi-block distribution window; the stake-program instruction processor source (guarding `Merge`/`Withdraw` behavior against in-flight rewards) was not retrievable via search in this session. This is the key open question that determines whether this is a live, exploitable, permissionless path or a scenario the stake program processor already forbids.

### Impact Explanation
If reachable, the impact is a direct, permanent, unprivileged loss of already-earned staking rewards for legitimate users, with no attacker required — a user performing an ordinary account-lifecycle operation (merge, split, or full withdrawal) during the distribution window that follows an epoch boundary would forfeit their calculated reward for that epoch. This is silent (only logged via `error!`), non-consensus-breaking (all validators compute the same burn deterministically from the same `StakesCache` state), but represents real economic loss of legitimate rewards that were already calculated and committed to the `EpochRewards` sysvar's `total_rewards`/`distributed_rewards` accounting.

### Likelihood Explanation
Likelihood is uncertain without confirming whether the stake program actually permits mutating/closing operations on a stake pubkey between the reward-calculation snapshot and its scheduled distribution block. The comment in the code strongly suggests the developers believe this is prevented by stake-program restrictions, which — if true — would make this theoretical/no-impact under the review's exclusion criteria. Without being able to verify the stake-program instruction-processor guards in this session, I cannot confirm this is concretely reachable by an unprivileged user today.

### Recommendation
Given the inability to conclusively prove or disprove reachability of the `AccountNotFound`/`ArithmeticOverflow` paths via legitimate unprivileged stake operations within this session, and because the comment in the code explicitly documents this as an assumed-impossible invariant rather than a proven-safe one, further investigation (starting a full Devin session with complete access to the stake program's `Merge`/`Split`/`Withdraw` instruction processors) is recommended to confirm or refute reachability before treating this as a confirmed finding.

### Proof of Concept
Not established — reachability of the `DistributionError::AccountNotFound` burn path via a legitimate, permissionless stake instruction executed between the reward-calculation snapshot and the later distribution block could not be confirmed with the available tools/indexed context in this session.

    fn build_updated_stake_reward(
        distribution_epoch: u64,
        stake_history: &StakeHistory,
        new_warmup_cooldown_rate_epoch: Option<Epoch>,
        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
        partitioned_stake_reward: &PartitionedStakeReward,
        rent: &Rent,
        adjust_delegations_for_rent: bool,
        use_fixed_point_stake_math: bool,
    ) -> Result<StakeReward, DistributionError> {
        let stake_account = stakes_cache_accounts
            .get(&partitioned_stake_reward.stake_pubkey)
            .ok_or(DistributionError::AccountNotFound)?
            .clone();

        let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
        let StakeStateV2::Stake(meta, stake, flags) = stake_state else {
            // StakesCache only stores accounts where StakeStateV2::delegation().is_some()
            unreachable!(
                "StakesCache entry {:?} failed StakeStateV2 deserialization",
                partitioned_stake_reward.stake_pubkey
            )
        };
        account
            .checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
        account
            .checked_add_lamports(partitioned_stake_reward.block_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
