### Title
Unauthenticated `X-Shipit-User` header lets an API-token holder impersonate any registered `User` as deploy/rollback/task author - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController#identify_user` resolves `current_user` purely from the client-supplied `X-Shipit-User` request header, with no verification that the header actually corresponds to the identity behind the `ApiClient` bearer token used to authenticate the request. `current_user` is then passed as the acting author/`aborted_by` for deploys, rollbacks, tasks, and locks. This breaks the binding "the GitHub identity that authenticated the request" == "the `User` the action is attributed/authorized to," analogous to the `BridgedIndexToken` report where a value used in security-relevant checks (`REMOTE_TOKEN`) could be set independently of the credential that should govern it.

### Finding Description
`authenticate_api_client` establishes `current_api_client` from the HTTP Basic bearer token via `ApiClient.authenticate` [1](#0-0) . Separately, `current_user` is derived from `identify_user`, which trusts the `X-Shipit-User` header verbatim and looks up any `User` by login, with no cross-check against the `ApiClient`'s `creator` or any authenticated identity: [2](#0-1) 

Any holder of a valid `ApiClient` token (which itself only carries coarse `permissions`/optional `stack_id` scoping - [3](#0-2) ) can set `X-Shipit-User` to the login of any existing `User` in the instance (e.g., an admin, a member of `Shipit.github_teams`, or the bot user) and have that identity attributed as the actor for privileged operations:

- `DeploysController#create` uses `current_user` as the deploy author passed to `stack.trigger_deploy` [4](#0-3) 
- `RollbacksController#create` uses `current_user` as rollback trigger / `aborted_by` [5](#0-4) 
- `TasksController#trigger`/`#abort` use `current_user` as task author / `aborted_by` [6](#0-5) 
- `LocksController` uses `current_user` as lock author [7](#0-6) 

This is the same class of flaw as the `BridgedIndexToken` bug: an unverified, attacker-controllable field (`X-Shipit-User` header / `REMOTE_TOKEN`) is substituted for the value that a security-relevant check should actually be keyed on (the authenticated `ApiClient`'s true identity / the bridge's actual remote token). Authorization gates such as `User#authorized?`, which checks team membership against `Shipit.github_teams`, are evaluated against this spoofable identity rather than the credential that was actually verified [8](#0-7) .

### Impact Explanation
This allows escalation into `Shipit.github_teams` authorization and forged attribution for unauthorized deploys/rollbacks/task executions/locks — matching the High severity criteria in scope ("escalation into `Shipit.github_teams` authorization"). Any code path that trusts `current_user` for audit, notification, "who can unlock/who deployed" checks, or downstream authorization decisions can be silently subverted by any caller possessing a valid (even narrowly-scoped) API token.

### Likelihood Explanation
Requires only an existing, valid `ApiClient` token with any permission granting access to the relevant endpoint (deploy/rollback/task/lock) — no elevated GitHub permissions, no webhook secret, and no session are needed. Setting an arbitrary HTTP header is trivial. Given that API tokens are commonly distributed to CI systems and integrations with narrow intended scope, this significantly lowers the bar for identity spoofing.

### Recommendation
Do not derive `current_user` from an unauthenticated client-supplied header. Instead:
- Bind `current_user` to `current_api_client.creator` (the actual authenticated identity), or
- If `X-Shipit-User` is meant to record "on behalf of" attribution, cryptographically bind it to the token (e.g., embed the user id in the signed `authentication_token`) and verify it server-side rather than trusting a bare header.
- Any authorization decision (e.g., `User#authorized?`, `Shipit.github_teams` checks) must be evaluated against the verified identity, not the spoofable one.

### Proof of Concept
1. Obtain any valid `ApiClient` bearer token with, e.g., `deploy:stack` permission (e.g., a CI token intentionally scoped to only trigger deploys).
2. Send `POST /api/stacks/:id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: <login-of-privileged-admin>`.
3. `identify_user` resolves `current_user` to the admin `User` record purely from the header [9](#0-8) .
4. The deploy is recorded/attributed to the admin, and any downstream logic keyed on `current_user` (audit trail, `authorized?` team checks, notifications) treats the request as if it were performed by the admin, not the actual token holder.

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
