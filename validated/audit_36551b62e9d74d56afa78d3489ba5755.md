## Analog Found

### Title
AAs can never forward, return, or spend indivisible (fixed-denomination) assets they receive, permanently freezing any such tokens sent to them - (File: aa_composer.js)

### Summary
Any coin/asset sent to an Autonomous Agent (AA) is credited to the AA's per-asset balance (`aa_balances`), and the only way for an AA to move funds out again is by including a `payment` message in its response, which is processed by `sendUnit()` in `aa_composer.js`. That function unconditionally strips out any `payment` message whose asset is defined with `fixed_denominations: true` (i.e. an indivisible/textcoin-style asset), regardless of what the AA's oscript logic intended to do with it. Consequently, if a user or another AA sends units of a fixed-denomination asset to *any* AA address (by mistake or otherwise), those units are absorbed into the AA's balance but can never be sent back out — there is no code path in the protocol that allows an AA to spend a `fixed_denominations` asset. This is the same "coins mistakenly/unintentionally locked in a contract with no way to withdraw them" bug class as the referenced Reservoir report, except here it is not a deliberate design choice of one deployed instance — it is a systemic limitation of the core AA execution engine (`aa_composer.js`) that affects every AA on the network, no matter how the AA author writes their oscript.

### Finding Description
In `aa_composer.js`, `sendUnit()` iterates over the AA's outgoing messages and loads asset info for every non-base payment: [1](#0-0) 

```
storage.loadAssetWithListOfAttestedAuthors(conn, asset, mci, [address], true, function (err, objAsset) {
    if (err) return cb(err);
    assetInfos[asset] = objAsset;
    if (objAsset.fixed_denominations) // will skip it later
        return cb();
    if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs
        return cb("sending private asset from AA");
    ...
```

Note the comment "will skip it later" — for `fixed_denominations` assets, `completePaymentPayload` (which actually selects UTXOs/inputs to fund the payment) is never called, and the message is later unconditionally removed from the response unit: [2](#0-1) 

```
messages = messages.filter(function (message) { return (message.app !== 'payment' || !message.payload.asset || !assetInfos[message.payload.asset].fixed_denominations); });
if (messages.length === 0) {
    error_message = 'no messages after removing fixed denominations';
    console.log(error_message);
    return handleSuccessfulEmptyResponseUnit(null);
}
```

This is not an error/bounce condition — the AA simply produces a "successful" response with the payment silently dropped. Meanwhile, `updateInitialAABalances()` credits the AA's `aa_balances` table with whatever asset (including fixed-denomination assets) was sent to it in the trigger: [3](#0-2) 

There is no other outbound path for an AA to move an asset — `sendUnit`/`sendDummyUnit` (dry-run) are the only functions that build outgoing payment messages, and both apply the same asset-type restriction. As a result, once a fixed-denomination asset accumulates in an AA's balance, it is permanently unspendable by that AA, for the lifetime of the protocol, with the funds cryptographically inaccessible to anyone (the AA has no private key and the asset can't be forwarded by oscript logic).

### Impact Explanation
Any unprivileged unit poster or asset issuer can send indivisible/fixed-denomination assets (a normal, supported asset type in ocore, e.g. used for textcoins) as a `payment` output to an existing AA address. This causes those tokens to be irrecoverably locked, since:
1. No AA (regardless of its oscript definition) can ever construct a valid payment message moving a `fixed_denominations` asset out of its balance.
2. The AA cannot bounce/reject the funds either, since the trigger's balance update happens before message evaluation and the response is treated as "successful, nothing to send."

This results in a permanent freeze of assets/funds at the AA address — a concrete instance of "AA fund loss / freezing," which can affect legitimate value locked in any AA that is unaware of this systemic protocol restriction (e.g. an AA meant to act as an escrow, marketplace, or asset-forwarding agent for indivisible assets).

### Likelihood Explanation
High likelihood: triggering this requires nothing more than composing a standard payment message with `asset` set to any indivisible/fixed-denomination asset and an output pointed at an AA address — a completely permissionless action available to any wallet user. No cooperation from the AA author, network operators, or privileged roles is required, and the condition is deterministic (always reproducible), not race-dependent.

### Recommendation
Either:
- Extend `sendUnit()`/`completePaymentPayload()` in `aa_composer.js` to support constructing indivisible-asset payment messages from AA balances (mirroring the coin-selection/issuance logic already used for divisible assets and for wallet-composed indivisible payments in `indivisible_asset.js`), so AAs can forward fixed-denomination assets they hold; or
- If indivisible-asset support for AAs is intentionally out of scope, have the protocol automatically bounce (rather than silently accept) trigger payments made in `fixed_denominations` assets to AA addresses, so senders are not able to strand funds and get their outputs returned/rejected instead.

### Proof of Concept
1. Define/issue an asset with `fixed_denominations: true` (a standard indivisible asset, as used for textcoins), and mint a supply of denominated coins to a user wallet.
2. Send a `payment` message carrying units of that indivisible asset to any deployed AA address (no special cooperation from the AA author needed — this is a plain wallet payment to any address).
3. `aa_composer.js`'s `updateInitialAABalances()` credits the AA's `aa_balances` row for that asset with the received amount.
4. When the AA composes its response (regardless of what its oscript `messages` template says), any payment message for that asset is dropped in `sendUnit()` at lines 1327-1328 (skipped during processing) and lines 1356-1361 (filtered out before the response unit is finalized), producing `error_message = 'no messages after removing fixed denominations'` and a "successful" empty response.
5. Verify via `aa_balances` (or `checkBalances()` in `aa_composer.js`) that the AA's balance for that asset remains non-zero indefinitely, and confirm there is no other function in `aa_composer.js`, `indivisible_asset.js`, or `divisible_asset.js` that allows an AA (a non-key-holding address) to spend a `fixed_denominations` asset — the funds are permanently stuck.
