### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-organization status/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook against using `repository.owner.login` (falling back to `organization.login`), while every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) resolves the actual `Repository`/`Stack` to mutate using the unrelated `repository.full_name` field from the very same attacker-controlled JSON body. Because HMAC verification only proves the payload was signed by *some* configured organization's secret — it does not bind that organization to the `full_name` value the handlers subsequently trust — a party who can produce a validly-signed payload for one configured GitHub organization can make Shipit act on a repository belonging to a *different* organization.

### Finding Description
The signature check: [1](#0-0) 

selects the app config via: [2](#0-1) 

`Shipit.github(organization: repository_owner)` uses `repository_owner` purely to look up which multi-org `webhook_secret` should HMAC-verify the raw body (per the multi-org config shape shown in `config/secrets.development.shopify.yml`). Once verification passes, the full JSON `params` is handed unmodified to every registered handler: [3](#0-2) 

Every handler, however, resolves the repository it is going to mutate via a *different* JSON key — `repository.full_name` — through the shared base class: [4](#0-3) 

and it is exercised directly by, e.g., `PushHandler`: [5](#0-4) 

and by all `PullRequest::*` handlers (`OpenedHandler`, `LabeledHandler`, `AssignedHandler`, `EditedHandler`, `LabelCapturingHandler`, `ReviewStackAdapter`), which each independently call `Shipit::Repository.from_github_repo_name(params.repository.full_name)`: [6](#0-5) [7](#0-6) 

Nowhere does the request pipeline assert `repository.full_name`'s owner matches `repository_owner` (the value that selected the verifying secret). The binding that should hold is:

`organization whose secret verified the HMAC == organization that owns the repository the handler writes to`

Before an attacker's forged request, this equality holds implicitly only because legitimate GitHub-generated payloads always have consistent `owner.login`/`full_name` values. There is nothing in the engine enforcing it. After a forged request where `repository.owner.login = "org-with-known-secret"` and `repository.full_name = "victim-org/some-repo"`, the equality is broken: the signature check is satisfied by `org-with-known-secret`'s secret, but `PushHandler`/`StatusHandler`/PR handlers act on `victim-org/some-repo`.

### Impact Explanation
In a Shipit deployment configured for multiple GitHub organizations (the documented multi-org `secrets.yml` layout), anyone who can produce a validly-signed webhook body for *one* configured organization (e.g., because that org's `webhook_secret` is unset/blank — a documented, non-hypothetical config option shown as `webhook_secret: # nil` in `config/secrets.development.example.yml`, or because it has otherwise leaked for a lower-trust org) can:
- Inject fabricated `status` events (`StatusHandler`) for commits belonging to a *different, victim* organization's repository, forging commit-status state used to gate CI-required merges/deploys.
- Force `GithubSyncJob`/`sync_github` on a victim-org stack via forged `push` events.
- Manipulate pull-request-driven review-stack provisioning/archival (`OpenedHandler`, `LabeledHandler`) for a victim org's repositories.

This crosses an organizational trust boundary that the multi-org webhook-secret design exists specifically to enforce, enabling unauthorized state changes (fake CI status, forced syncs, review-stack manipulation) against a repository the attacker was never authorized to affect — matching the "cross-repository writes" / unauthorized deploy-gating-bypass impact class.

### Likelihood Explanation
Exploitability depends on the operator running a multi-organization Shipit instance and at least one configured organization having a weak or absent `webhook_secret` (an explicitly supported, documented configuration state), or the attacker otherwise obtaining that org's secret through means short of full Shipit/GitHub App compromise. In a single-organization deployment this path collapses since only one secret/organization exists. Given multi-org support is a first-class, documented feature and blank secrets are an accepted example configuration, this is a realistic, engine-level design gap rather than a purely theoretical one.

### Recommendation
Enforce the invariant at the controller/handler boundary: after verifying the signature, assert that `repository.owner.login` (or `organization.login`) used to select the verifying secret matches the owner segment of `repository.full_name` before dispatching to any handler, rejecting (422) any payload where they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-accessible / blank `webhook_secret`) and `orgB` (victim, has stacks tracked in Shipit).
2. Attacker crafts a `push` (or `status`) webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `orgA`'s (known/blank) `webhook_secret` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature against `orgA`'s secret.
5. `PushHandler#process` resolves `stacks` via `payload.dig('repository', 'full_name')` = `"orgB/victim-repo"`, and triggers `stack.sync_github(expected_head_sha: "deadbeef...")` on `orgB`'s stack — despite the request never being authenticated by anything belonging to `orgB`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
