### Title
Webhook signature verification binds to the wrong GitHub App/organization, allowing forged push/status/check_suite events against any stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on an **unauthenticated** field taken from the still-unverified request body (`repository.owner.login` / `organization.login`), while the event handlers that subsequently act on the payload use a **different** field from that same unverified body (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. Nothing binds these two fields together, so in a multi-organization Shipit deployment an attacker can pick the identity used for signature checking independently from the identity that is actually acted upon.

### Finding Description
`verify_signature` resolves the signing secret like this: [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a `GitHubApp` instance per organization (see the documented multi-org config format), and each configured organization may independently have `webhook_secret: nil` ("optional" per the setup docs and example secrets files): [3](#0-2) [4](#0-3) 

If that organization's `webhook_secret` is blank, verification is a no-op: [5](#0-4) 

Once `verify_signature` passes, `create` dispatches the raw, attacker-controlled payload to the registered handlers: [6](#0-5) 

The handlers, however, resolve the target repository/stack from a **different** field of the same payload: [7](#0-6) [8](#0-7) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are two independent, attacker-supplied strings in the same unauthenticated JSON body, an attacker can set:
- `repository.owner.login` = an organization configured in `Shipit.github` with `webhook_secret` unset/blank (bypasses signature check entirely), and
- `repository.full_name` = `"victim-org/victim-repo"`, the actual target stack that *does* have a webhook secret configured and that the attacker does not know.

The equality that should hold — "the organization whose signature was verified" == "the repository that gets written to" — is broken. Before the attacker's request: only requests validly signed by `victim-org`'s configured secret can trigger `PushHandler`/`StatusHandler`/`CheckSuiteHandler` actions on `victim-org/victim-repo`. After the crafted request: any actor who knows that some unrelated org in the multi-app config lacks a webhook secret can trigger those actions on `victim-org/victim-repo` without ever presenting a valid signature for it.

### Impact Explanation
This lets an unauthenticated, unprivileged network attacker trigger `GithubSyncJob` (push), commit status writes (`StatusHandler`), and `RefreshCheckRunsJob` (`check_suite`) on any stack, by forging a webhook whose top-level `repository.owner`/`organization.login` names an organization with no configured `webhook_secret`, while the nested `repository.full_name` names the real target. Depending on downstream sync behavior this can influence what Shipit believes is deployable, corrupt commit status/check state used for deploy gating, and drive unauthorized syncs/deploy triggers — a cross-organization write achieved purely by exploiting the mismatch between the identity verified and the identity acted upon.

### Likelihood Explanation
Exploitability is contingent on the deployment using the documented multi-organization `Shipit.github` configuration (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) where `webhook_secret` is explicitly documented as optional per organization. Any Shipit operator who onboards a second/test organization without setting a webhook secret (the documented default) turns that org into a skeleton key for forging events against every other org's stacks in the same instance. This requires no session, no `ApiClient` token, and no knowledge of any real secret — only knowledge (or a guess) that one configured org lacks a `webhook_secret`.

### Recommendation
- Verify the webhook signature using the secret resolved from the same field the handlers use to select the target repository (`repository.full_name`'s owner), not a separately-read field.
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank if the organization/app in question owns repositories with other, secured configurations; instead require every configured organization to set a webhook secret, or refuse to process events whose `repository.owner.login` does not match the owner segment of `repository.full_name`.
- Add a check in `Handler`/`WebhooksController` asserting `repository.owner.login` (used for auth) equals the owner segment parsed from `repository.full_name` (used for action) before dispatching.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (no `webhook_secret`) and `OrgB` (with a `webhook_secret` and a real stack `OrgB/prod-repo`), per the documented multi-org format in `config/secrets.development.shopify.yml`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/prod-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
   Omit/forge `X-Hub-Signature` arbitrarily.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`) regardless of the signature header.
4. `create` dispatches the payload to `PushHandler`, which resolves the repository via `payload.dig('repository','full_name')` = `"OrgB/prod-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues `GithubSyncJob` for `OrgB`'s real stack — a stack whose actual webhook secret was never checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
