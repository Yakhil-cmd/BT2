### Title
Missing validation of `amount` in private-payment `src_coin` causes an uncaught-exception process crash - (File: `indivisible_asset.js`, `validation.js`)

### Summary
`validatePrivatePayment()` in `indivisible_asset.js` builds `objValidationState.src_coin.amount` directly from `prev_hidden_output.amount`, a field taken from the *previous* private-payment element supplied by the private-payment counterparty, without checking that it is a positive integer. This unvalidated value later reaches a `throw Error(...)` (not routed through the callback-based error path) in `validation.js`'s `validatePaymentInputsAndOutputs()`, matching the CWE-20 "missing validation causes CHECK-failure/crash" pattern from the TensorFlow `StagePeek` report.

### Finding Description
In `indivisible_asset.js:validatePrivatePayment()`:
```js
var prev_hidden_output = objPrevPrivateElement.payload.outputs[input.output_index];
if (!prev_hidden_output)
    return callbacks.ifError("no prev hidden output");
...
objValidationState.src_coin = {
    src_output: src_output,
    denomination: payload.denomination,
    amount: prev_hidden_output.amount
};
``` [1](#0-0) 

Only existence of `prev_hidden_output` is checked (`isNonemptyObject` for the whole output is checked much earlier for the *hidden* payload structure, but not specifically that `.amount` is a positive integer at this callsite). `prev_hidden_output` originates from `objPrevPrivateElement.payload.outputs`, which is attacker-controlled content sent by the other party in a private-payment chain (device-to-device message), and is never re-validated for numeric type/positivity before being copied into `objValidationState.src_coin.amount`.

This `src_coin` object is later consumed in `validation.js:validatePaymentInputsAndOutputs()`:
```js
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
``` [2](#0-1) 

Unlike virtually every other validation failure in this file, which is reported via `return cb("...")`/`return callback("...")` (a normal, caught, asynchronous error path), this specific check uses `throw Error(...)`. Because it executes inside a nested async callback (deep inside `conn.query(...)` callbacks originating from `db.query`), this thrown exception is **not caught by any try/catch** in the call chain and propagates to Node's `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to crash the process:
```js
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [3](#0-2) 

### Impact Explanation
A private-payment counterparty (an unprivileged peer paired for a private asset transfer, reachable via `wallet.js`'s private-payment-chain handling, e.g. `handlePrivatePaymentChains`) can craft a private-asset payment chain where a prior element's hidden output has a non-numeric or non-positive `amount` field (e.g. a string, object, negative number, or `0`). When the recipient validates the next element in the chain that spends this "src_coin", the deliberately-`throw`n `Error("no src coin amount")` bypasses the normal callback-based error reporting and is raised as an uncaught exception, crashing the entire node process (not just failing to validate one payment). This is a genuine denial-of-service: the victim node (wallet/hub) stops entirely and must be manually restarted, matching the CVE-2022-29195 impact class ("CHECK-failure denial of service from missing input validation").

### Likelihood Explanation
Reachable by any counterparty engaging in a private (indivisible/fixed-denomination) asset payment chain — this requires only sending a crafted private-payment chain to a peer via existing wallet flows (`wallet.js` / `network.js` private payment handling), no special privileges, no witness/hub collusion, and no prior trust relationship beyond being a payment counterparty. Reaching the vulnerable `throw` only requires satisfying earlier lightweight checks (`prev_hidden_output` exists, spend-proof hash matches, since the attacker controls both `amount` and the corresponding hash inputs and can make the hash match while `amount` is invalid).

### Recommendation
Replace the `throw Error(...)` statements in `validation.js` (lines checking `src_coin.src_output`, `src_coin.denomination`, `src_coin.amount`) with the same asynchronous `return cb("...")` pattern used elsewhere in this function, so invalid attacker-supplied private payment data results in a normal validation failure instead of an uncaught exception. Additionally, validate `prev_hidden_output.amount` (positive integer) in `indivisible_asset.js` at the point `src_coin` is constructed, before it is ever used downstream.

### Proof of Concept
1. Attacker constructs a private, fixed-denomination asset payment chain (`arrPrivateElements`) where the first element's `payload.outputs[output_index].amount` is set to an invalid value (e.g. `"not_a_number"`, `-5`, or `0`), and computes matching `output_hash`/spend-proof values so earlier hash-integrity checks pass.
2. Attacker sends this chain to a victim node/wallet as a private payment (e.g. via `network.handleOnlinePrivatePayment` / `wallet.js` `handlePrivatePaymentChains`).
3. Victim's `indivisible_asset.js:validatePrivatePayment()` copies the invalid `amount` into `objValidationState.src_coin.amount` unchecked.
4. When `validation.js:validatePaymentInputsAndOutputs()` processes the "transfer" input for this private fixed-denomination asset, `isPositiveInteger(src_coin.amount)` fails and `throw Error("no src coin amount")` executes inside an uncaught async context.
5. The exception bubbles to `process.on('uncaughtException', ...)` in `network.js`, which re-throws, crashing the victim node process.
