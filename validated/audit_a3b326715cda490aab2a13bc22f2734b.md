### Title
Unauthenticated GitHub webhook payloads can create forged commit `Status`/push events when `webhook_secret` is unset, breaking the binding between the organization used to verify a webhook and the repository/stack actually written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GithubApp` (and therefore which `webhook_secret`) to validate a webhook against using a field read directly out of the unauthenticated JSON body (`repository.owner.login` / `organization.login`). The entity that is actually mutated — the `Repository`/`Stack` acted on by the handler — is looked up from a *different* field in that same body (`repository.full_name`), and the GitHub-signature guarantee is only meaningful when a `webhook_secret` is configured. Shipit's own reference configuration ships `webhook_secret` unset/`nil` by default, in which case `verify_webhook_signature` unconditionally returns `true`. This produces exactly the binding break the task calls out: "organization authenticated" ≠ "repository that is written," with no cryptographic binding when the (optional, commonly unset) secret is absent.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to check the HMAC against based on attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` trivially passes when no secret is configured for that organization: [3](#0-2) 

Every shipped secrets template documents `webhook_secret` as optional/`nil` by default: [4](#0-3) [5](#0-4) 

Once the signature check passes (or is skipped because no secret is set), handlers determine *which* `Repository`/`Stack` to mutate from a completely separate field, `repository.full_name`, with no re-validation that it corresponds to the organization/secret that was "verified": [6](#0-5) 

`StatusHandler` writes a `Status` record for any commit SHA present in the database purely from the unauthenticated payload: [7](#0-6) 

`PushHandler` similarly triggers a real sync job for any matching `Stack`: [8](#0-7) 

This is the direct analog of the reported bug class: the EMA oracle updates its trusted state via events that are "monitored" but not cryptographically tied to the real underlying value (direct StableSwap transfers bypass the hook that should gate price trust). Here, Shipit's `Status`/`Stack` state is updated via a webhook event that is only nominally "authenticated" (an org-selection field in the body), while the actual target of the write (`repository.full_name`) is never covered by that authentication, and the authentication itself is a no-op whenever `webhook_secret` — an optional field every shipped config template leaves blank — is not set.

### Impact Explanation
`ci.require` gates whether a commit is deployable based on the presence/state of `Status` records: [9](#0-8) 

Because `StatusHandler` creates/updates `Status` rows straight from an unauthenticated (when `webhook_secret` is unset) `status` event, an unauthenticated network attacker can forge the required CI status context as `success` for any commit already known to Shipit, satisfying `ci.require` and enabling an otherwise-blocked deploy to proceed — an unauthorized deploy, matching the Critical impact bucket. The same lack of binding lets an attacker also trigger spurious `GithubSyncJob`s or fabricate `Team`/`membership` records via `MembershipHandler` for arbitrary organizations, since none of these mutations verify that the field they act on was covered by the (often absent) signature check.

### Likelihood Explanation
`webhook_secret` is documented and shipped as optional/`nil` in every example and test configuration, so unset-secret deployments are the norm rather than an edge case, and the `/webhooks` endpoint is intentionally public and unauthenticated (`skip_before_action :verify_authenticity_token`, no session or API-token requirement). Exploitation requires no credentials, session, or repository access of any kind — only knowledge of an organization name already registered in Shipit and a real commit SHA/stack that Shipit already tracks (both discoverable from Shipit's own public-ish UI/API surfaces or from GitHub itself).

### Recommendation
- Require `webhook_secret` to be present for every configured organization and refuse to boot / reject all webhooks for organizations without one, instead of silently returning `true` from `verify_webhook_signature`.
- Bind the field used to select the verifying secret (`repository.owner.login`/`organization.login`) to the field used to determine what gets written (`repository.full_name`) — reject the payload if they disagree, or derive both from a single authenticated source.
- Consider scoping/allow-listing which repositories a given GitHub App's webhook delivery is permitted to affect, rather than trusting whatever `repository.full_name` accompanies a signed body.

### Proof of Concept
1. Deploy Shipit with a configuration copied from the shipped example templates, i.e. `webhook_secret` left blank for organization `acme`, and with an existing `Stack`/`Commit` tracked for `acme/webapp`.
2. As an unauthenticated network client, `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<existing commit sha for acme/webapp>",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "acme" }, "full_name": "acme/webapp" }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "acme")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` with no signature required.
4. `StatusHandler#process` creates a `Status` record with state `success` for the commit, satisfying `ci.require`, without the attacker ever needing a webhook secret, session, or GitHub credential — enabling deploy actions gated on that CI status to proceed illegitimately.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
