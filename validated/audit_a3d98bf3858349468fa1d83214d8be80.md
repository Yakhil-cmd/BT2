### Title
Signature verified against `repository.owner.login`'s GitHub App while the actual write target is taken from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / `webhook_secret` used to authenticate an inbound webhook by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body, but the handlers that actually mutate state (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, the pull-request handlers, etc.) resolve the target `Repository`/`Stack` from the sibling `repository.full_name` field of that same hash. Nothing ties `full_name` to `owner.login`, so an attacker who legitimately controls the webhook secret for one organization/repository on a multi-tenant Shipit instance can forge a payload whose `owner.login` matches their own org (so signature verification passes) while `full_name` points at a repository belonging to a completely different organization, causing Shipit to act on that unrelated repository.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-controlled JSON, before the HMAC has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, which selects the `Shipit.github(organization: ...)` app config and thus the `webhook_secret` used by `verify_webhook_signature`: [3](#0-2) 

Once the signature check passes, the raw parsed `params` (the exact same JSON body) is forwarded unchanged to every handler for the event: [4](#0-3) 

Handlers resolve which `Repository`/`Stack` to mutate from a *different* subfield of the same `repository` object — `full_name` — with no cross-check against `owner.login`: [5](#0-4) 

For example `PushHandler#process` triggers `stack.sync_github` for every non-archived stack matching that repository/branch: [6](#0-5) 

Because `owner.login` (used to select the trusted secret) and `full_name` (used to select the repository that is written to) are independent, attacker-controlled strings inside the same unauthenticated JSON body, the equality the system implicitly relies on — "the organization whose secret authenticated this request equals the organization owning the repository being written to" — is never enforced.

### Impact Explanation
An attacker who legitimately holds a valid `webhook_secret` for one organization/repository configured on a shared Shipit instance (i.e., they are entitled to send authenticated webhooks for *their own* repo) can craft a payload where `repository.owner.login` matches their own org (so the correct `webhook_secret` validates the HMAC) but `repository.full_name` names a repository belonging to a different, unrelated organization on the same instance. This lets them drive `PushHandler` (and other repository-name-keyed handlers) to act against a repository they do not control — e.g. forcing `Stack#sync_github` on someone else's stack, or exercising pull-request handlers against another org's stacks — constituting a cross-repository write/trigger outside the attacker's authorization boundary, without ever holding a Shipit session, API token, or the victim organization's `webhook_secret`.

### Likelihood Explanation
This requires the Shipit deployment to host multiple organizations/repositories (each with their own GitHub App/`webhook_secret`) — a supported and documented configuration (`config/secrets.development.shopify.yml` shows multiple orgs configured). The attacker needs only the webhook secret for an organization/repo that they are legitimately entitled to send webhooks for; no privileged Shipit credential is needed. This is a realistic misuse of a normal, unprivileged capability (sending a webhook for one's own repo) to affect another tenant's data.

### Recommendation
Validate that `repository.full_name` (or the repository ultimately looked up) belongs to the same organization used to select the verifying `webhook_secret` before dispatching to handlers — e.g., derive both the signing key and the acted-upon repository from a single verified source, or explicitly assert `repository.full_name.split('/').first == repository.owner.login` (or the resolved `Repository#owner`) in `WebhooksController` before invoking `Shipit::Webhooks.for_event`.

### Proof of Concept
1. Attacker administers `github-org-attacker/some-repo`, configured on the shared Shipit instance with its own GitHub App and known `webhook_secret_A`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "github-org-attacker" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` resolves to `github-org-attacker` (from `repository.owner.login`), `Shipit.github(organization: 'github-org-attacker')` returns the attacker's own app, and `verify_webhook_signature` succeeds because the attacker used the correct secret for that org.
5. `params` (still containing `full_name: "victim-org/victim-repo"`) is passed unchanged to `PushHandler`, which resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'deadbeef')` on the victim's stack — a write triggered on an organization/repository the attacker never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
