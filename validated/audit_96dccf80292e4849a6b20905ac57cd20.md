### Title
Webhook signature verification keyed by unverified `repository.owner.login`, while stack mutations are keyed by unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the request against using an attacker-supplied, not-yet-verified field (`repository.owner.login` / `organization.login`), then the request handlers act on a *different* attacker-supplied field (`repository.full_name`) to select which `Stack`/`Repository` is mutated. When any configured organization has no `webhook_secret` set (an explicitly supported/optional configuration), `verify_webhook_signature` short-circuits to `true` for that organization, which lets an attacker forge a webhook payload that claims to originate from the secret-less org while `repository.full_name` points at a stack belonging to a different, secret-protected org.

### Finding Description
Signature verification and org lookup: [1](#0-0) 
The organization used to resolve `Shipit.github(organization: ...)` comes straight from the raw, unverified JSON body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Meanwhile, the actual side effects (e.g. `PushHandler`, pull-request handlers) resolve the target `Stack`/`Repository` using a *separate* field of the same unverified payload, `repository.full_name`, with no cross-check against the organization used for signature verification: [4](#0-3) [5](#0-4) 

Equality that should hold but doesn't:
`organization(verified against) == organization(repository.full_name actually written to)`.

Both `repository.owner.login` and `repository.full_name` are attacker-controlled prior to signature verification succeeding. The webhook secret is documented as optional per organization: [6](#0-5) 
and the shipped multi-org example config leaves `webhook_secret` blank for multiple orgs: [7](#0-6) 

So a multi-tenant Shipit deployment (`config/secrets.yml` with a per-organization `github:` map, as documented) can have Org A protected with a webhook secret and Org B left unsecured. An attacker who knows nothing but public information (that Org B is installed on this Shipit instance and has no webhook secret) can send a forged webhook whose `repository.owner.login` is Org B (making `verify_signature` auto-pass) while `repository.full_name` names a repository actually owned by Org A. `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`) resolves stacks purely from `full_name`, with no re-check that the resolved repository's actual owner matches the organization used for signature verification.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in the rules. Concretely, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack on the matching branch — an unauthenticated write to Shipit's tracked commit/branch state for a stack belonging to a different (properly secured) organization. Depending on which webhook event is forged, this can trigger `GithubSyncJob`, review-stack archive/unarchive, PR-label capturing state changes, etc. against a stack the attacker does not control and has no legitimate credentials for — i.e., cross-repository writes reachable without any Shipit session, API token, or the target org's webhook secret. This maps to the report's Critical bucket ("cross-repository writes").

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, and (2) at least one configured organization with `webhook_secret` left blank — both explicitly supported/documented configurations, not a hardening violation. Given the setup docs mark `webhook_secret` as optional and the shipped multi-org secrets example leaves it blank for both orgs, this is a plausible, easy-to-hit misconfiguration rather than a contrived edge case. As with the referenced analog report, the issue is "currently not always exploitable" (single-org deployments, or deployments where every org sets a secret, are unaffected) but represents a missing binding check that becomes dangerous the moment one org in a multi-tenant setup omits its secret — directly mirroring the original bug's framing ("not exploitable now... could become a concern").

### Recommendation
Enforce that the organization used to verify the signature is the same organization that owns the resolved `Stack`/`Repository`, e.g.:
- Derive/verify the repository's actual owning organization independently (e.g., look up the pre-existing `Shipit::Repository`/`Stack` record and compare its stored owner against the payload's claimed owner) before dispatching to handlers.
- Alternatively, require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), removing the "unsecured org" escape hatch entirely.
- At minimum, reject payloads where `repository.owner.login` does not match the actual owner segment of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `SecureOrg` (with `webhook_secret` set) and `OpenOrg` (with `webhook_secret` left blank), per the documented multi-org format.
2. Create/track a stack for `SecureOrg/target-repo` in Shipit.
3. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "SecureOrg/target-repo" }
}
```
No `X-Hub-Signature` needs to be valid for `SecureOrg`'s secret — `repository_owner` resolves to `OpenOrg`, `Shipit.github(organization: "OpenOrg")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb` lines 76-83).
4. `WebhooksController#create` proceeds to `PushHandler`, which resolves the stack via `repository.full_name` = `"SecureOrg/target-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a state-changing action on `SecureOrg`'s stack that should have required `SecureOrg`'s webhook secret.

Note: I was unable to fully confirm from the index alone how `Repository.from_github_repo_name` parses/validates the owner segment of `full_name` (its implementation body wasn't returned in search results), so I could not verify whether any additional owner-matching safeguard exists there. If such a check exists, it could reduce or eliminate this finding; a Devin session with full repo access would be needed to inspect `app/models/shipit/repository.rb` in full to close out this uncertainty.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
