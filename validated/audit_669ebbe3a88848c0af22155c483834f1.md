This confirms the vulnerability: `Handler#repository_name` resolves the acted-upon repository from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate against using a *different* JSON path, `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [2](#0-1) . These two fields are independently attacker-controlled in the raw JSON body and are never checked for consistency with each other.

### Title
Webhook signature verification authenticates a different organization than the repository the payload acts on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-org Shipit deployments, `WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the webhook secret) to validate the `X-Hub-Signature` against by reading `repository.owner.login`/`organization.login` from the untrusted, unsigned-at-that-point JSON body [3](#0-2) . The event handlers that actually act on the payload instead resolve the target `Repository`/`Stack` using `repository.full_name` [4](#0-3) . Nothing binds these two fields together, and `verify_webhook_signature` trivially returns `true` whenever the selected organization has no `webhook_secret` configured [5](#0-4) .

### Finding Description
The binding that should hold is: `organization that authenticated == organization owning the repository being written`. Concretely, both fields come from the same attacker-supplied JSON body, so nothing prevents them from diverging:

```json
{
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```

`repository_owner` (used only for signature-key selection) resolves to `attacker-org` [6](#0-5) , while the `PushHandler`/`StatusHandler`/etc. that runs afterward resolves the acted-upon repository via `repository.full_name`, i.e. `victim-org/victim-repo` [1](#0-0) , [7](#0-6) .

`Shipit.github(organization:)` supports per-organization configuration, explicitly designed for multi-org installs where each org has its own `app_id`/`webhook_secret` [8](#0-7) , [9](#0-8) , and the `webhook_secret` key is explicitly documented as optional (`# nil`) for a given org [10](#0-9) . If `attacker-org` is one of the configured organizations that has no `webhook_secret` set, `verify_webhook_signature` returns `true` unconditionally regardless of the actual `X-Hub-Signature` header, since the check is skipped entirely: `return true unless webhook_secret` [5](#0-4) . The request then proceeds to `create`, which dispatches the full attacker-controlled JSON to the handlers keyed only by `X-Github-Event` [11](#0-10) , and those handlers act on `victim-org/victim-repo` — an organization whose GitHub App/webhook secret was never checked at all.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary the report's analog targets. An unprivileged external attacker, without any Shipit credential and without knowledge of the victim organization's real webhook secret, can forge `push` events that trigger `Stack#sync_github(expected_head_sha:)` for arbitrary tracked stacks in a *different, secret-protected* organization [7](#0-6) , or forge `status` events that inject fabricated commit statuses via `Commit#create_status_from_github!` for arbitrary commits by `sha` [12](#0-11) . Fabricated/forced commit statuses can be leveraged to satisfy deploy-gating checks and enable an unauthorized deploy, matching the required "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires: (1) a multi-org Shipit configuration (documented, supported feature) where at least one configured organization omits `webhook_secret` (an explicitly supported/"optional" configuration per `docs/setup.md` and `secrets.development.example.yml`), and (2) another configured organization hosts the target stack. Given webhook secrets are documented as optional, this misconfiguration is realistic in the wild, and exploitation requires only a single unauthenticated POST to `/webhooks` — no session, token, or GitHub write access needed.

### Recommendation
Do not select the verification key from unauthenticated payload content. Either: (a) require `webhook_secret` to be mandatory for every configured organization (reject boot/config if absent), removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`; and/or (b) after verifying the signature for the organization named by `repository_owner`, additionally assert that the organization portion of `repository.full_name` used by the handlers matches `repository_owner` before dispatching to handlers, so the authenticated organization and the acted-upon repository's organization are provably the same value.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (no `webhook_secret` set) and `victim-org` (has a `webhook_secret` and a tracked `Stack` for `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "ref": "refs/heads/master",
  "after": "<sha not actually pushed>"
}
```
Any `X-Hub-Signature` value (or none) is accepted because `Shipit.github(organization: 'attacker-org').verify_webhook_signature` short-circuits to `true` [5](#0-4) .
3. `WebhooksController#create` dispatches the payload to `PushHandler`, which resolves `victim-org/victim-repo` via `payload.dig('repository', 'full_name')` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [4](#0-3) , [7](#0-6)  — despite the request never being authenticated by `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
