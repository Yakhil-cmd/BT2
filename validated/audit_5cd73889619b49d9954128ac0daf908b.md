### Title
`StatusHandler#process` writes GitHub status updates to *every* commit sharing a SHA across all stacks, regardless of which repository's webhook authenticated the request - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `Commit.where(sha: params.sha)`, with no filter on the repository that emitted the webhook, unlike the base `Handler` class's `stacks`/`repository_name` scoping mechanism used by other handlers. Because `Shipit::WebhooksController#verify_signature` authenticates the request only at the GitHub organization level (`Shipit.github(organization: repository_owner)`), and the `Commit` table's uniqueness constraint is `(stack_id, sha)` rather than global, a genuinely-signed `status` webhook from one repository under an org can write a `Status` record onto a commit belonging to a completely different stack/repository under that same org whenever the SHAs coincide (forks, shared history, cherry-picks).

### Finding Description
The broken binding is: the set of stacks/commits mutated by a `status` webhook should equal `Repository.from_github_repo_name(payload.repository.full_name).stacks.commits`, but the actual code computes it as `Commit.where(sha: params.sha)` — i.e. **all commits in the database with that SHA, from any stack/repository**.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` authenticates the request against `Shipit.github(organization: repository_owner)` — an organization-scoped secret, not a per-repository one [1](#0-0) .
- `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` [2](#0-1) .
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no reference to `payload.dig('repository', 'full_name')` at all, unlike the `Handler` base class's own `stacks`/`repository_name` helper that other handlers (e.g. push) rely on [3](#0-2) [4](#0-3) .
- `Commit#create_status_from_github!` → `add_status` writes the `Status`, and if the state transitions to `pending`/`success`, calls `stack.schedule_merges` and, via `Status#schedule_continuous_delivery`/`Commit#schedule_continuous_delivery`, can trigger `ContinuousDeliveryJob` when `stack.continuous_deployment?` and the commit becomes `deployable?` [5](#0-4) [6](#0-5) [7](#0-6) .
- The `Commit` schema enforces uniqueness only on `(stack_id, sha)`, per migration `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, confirming the same SHA is expected/allowed to exist across multiple stacks (e.g., forks or shared history), which is exactly the condition `StatusHandler` fails to disambiguate.

Attacker's request: a real `status` webhook, correctly signed for the target GitHub organization (because it originates from a repository the attacker owns/controls under that same org's installation), with `context: continuous-integration/travis-ci`, `state: success` (or `failure`), and `sha` equal to a commit SHA that is also present in the victim's stack (shared ancestor commit, cherry-pick, or fork). `StatusHandler#process` will locate and update the `Status` on the victim's commit row too, even though the victim repository never sent this event.

Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) only validate the shape of the payload and the org-level HMAC signature; none of them constrain which repository's commits get mutated, so they do not prevent this divergence.

### Impact Explanation
A status event authenticated for repository A can flip the CI/deploy-gating state (`success`/`failure`/`pending`) of a commit that also belongs to stack B (a different repository/stack) whenever both share the SHA. On a `production` stack with `continuous_deployment?` enabled and requiring `continuous-integration/travis-ci`, this can make an otherwise-blocked commit `deployable?` and trigger `ContinuousDeliveryJob`, or conversely block a legitimate deploy by injecting a `failure`/error status. This is a cross-tenant "payload for one repository mutating another's stack/commit" — matching the Critical impact category (unauthorized deploy/rollback caused by a forged-but-authenticated-for-a-different-repo payload). Repeatable per matching SHA/organization, and blast radius spans every stack under the same GitHub organization whose commit history overlaps with the attacker's repository.

### Likelihood Explanation
Preconditions: the attacker must control a repository that is (a) tracked/authorized under the same GitHub organization/App installation as the victim stack (so `verify_signature` passes with a legitimately GitHub-signed event), and (b) shares at least one commit SHA with the victim stack's branch (achievable via forking, cherry-picking, or rebasing onto the same base commit — routine in real orgs). No Shipit secrets, sessions, or team membership are required; the attacker only needs ordinary GitHub push/CI access to their own repository within that org. This is moderately feasible in any organization that hosts multiple repositories/forks under one Shipit-configured GitHub App, and is repeatable at will since the attacker fully controls their own CI status pushes.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the `Handler#stacks` helper used elsewhere: resolve `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, then constrain `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or iterate over `stacks.commits.where(sha: params.sha)`) instead of an unscoped `Commit.where(sha:)` lookup.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repositories, `victim/repo` (environment `production`, `continuous_deployment: true`, requiring `continuous-integration/travis-ci`) and `attacker/repo`, both under the same fixture organization (e.g. `shopify`) so `verify_signature` passes for both.
2. Create two `Commit` rows with the **same** `sha` value: one belonging to `victim_stack`, one belonging to `attacker_stack` (allowed because the DB uniqueness index is `(stack_id, sha)`, not global — see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`).
3. Before: assert `victim_commit.reload.status.state` is not `success` (equality check: `victim_commit.statuses.count == 0`).
4. POST to `/webhooks` with `X-Github-Event: status`, a valid signature for `attacker/repo`'s organization, and body `{"sha": shared_sha, "state": "success", "context": "continuous-integration/travis-ci", "repository": {"full_name": "attacker/repo", "owner": {"login": "shopify"}}}`.
5. After: assert `victim_commit.reload.statuses.count == 1` and `victim_commit.status.state == "success"`, proving a webhook authenticated for `attacker/repo` mutated `victim/repo`'s commit — the equality `mutated_stack_id == webhook_repository.stacks.map(&:id)` is violated (it instead equals `Commit.where(sha:).pluck(:stack_id)`, including the victim's stack).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
