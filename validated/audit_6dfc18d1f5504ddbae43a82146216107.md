### Title
AA payment construction can fail ("not enough funds") even when the AA's logical balance is sufficient, causing withdrawal bounces and fee loss - ([File: aa_composer.js])

### Summary
An Autonomous Agent's ability to pay out funds during `handleTrigger` is bounded not by its recorded logical balance (`aa_balances` table / `trigger_opts.assocBalances`) but by the set of currently spendable on-chain outputs that `completePaymentPayload` can find via `readStableOutputs`/`readUnstableOutputsSentByAAs`. If those queries cannot assemble enough UTXOs to cover `target_amount`, the payment fails with `'not enough funds for ' + target_amount + ' bytes'` (or asset) and the whole trigger is bounced, exactly mirroring the TrueFi `liquidExit`-cannot-execute-when-liquidity-is-insufficient bug class: state believes funds are available, but the mechanism that must actually move value cannot satisfy the request.

### Finding Description
In `completePaymentPayload` (invoked from `sendUnit` while building the AA's response unit), the target amount to pay is computed from the message outputs and required change/fee overhead: [1](#0-0) 
Funding is attempted purely by iterating actually-unspent outputs owned by the AA address, first stable then unstable-sent-by-other-AAs: [2](#0-1) 
If `bFound` is never set (i.e., the sum of discovered UTXOs never reaches `target_amount`) and the asset is `base`, the code unconditionally errors out with `cb('not enough funds for ' + target_amount + ' bytes')`: [3](#0-2) 
This error propagates up and the whole unit construction is bounced: [4](#0-3) 
`bounce()` reverts `stateVars` and (for `bAir`/dry-run) balances to their pre-trigger values, and for a real trigger the response unit becomes a bounce message that returns the deposited amount minus `bounce_fees`: [5](#0-4) 

Crucially, oscript-level AA logic (as written by AA authors) authorizes withdrawals purely against a bookkeeping variable, e.g. the withdraw case in the bank/order-book sample AAs compares `trigger.data.amount` only to `var[$key]`: [6](#0-5) 
There is no way for the oscript author to check, before emitting the `payment` message, whether the AA's address actually has enough *spendable* outputs to satisfy `target_amount` (which also includes per-input overhead `FULL_TRANSFER_INPUT_SIZE`, oversize fees, and a change/storage-size output). Base-asset outputs smaller than `FULL_TRANSFER_INPUT_SIZE` are filtered out of `readStableOutputs` entirely as anti-dust protection, further shrinking the effectively spendable balance versus the logical one: [7](#0-6) 

So an AA can accumulate a "balance" in its state variables (and in `aa_balances`) that is fully backed by real coins on the DAG, yet still be unable to execute a legitimate withdrawal trigger because those coins are split across many small/dust outputs, or fee/change overhead pushes `target_amount` just over what the discovered UTXO set can cover — the AA is unable to "liquid exit" its own funds on that request.

### Impact Explanation
When this happens, the withdrawal trigger bounces: the state update requested by the trigger author never occurs (balance is not decremented, as `bounce()` restores `originalStateVars`), and the depositor only gets back `trigger.outputs - bounce_fees`, permanently losing the bounce fee for a withdrawal that never happened. From the perspective of the withdrawing user this is a fund-loss/denial-of-withdrawal event: the AA claims (via its own state) to owe funds that it cannot actually pay out on that trigger, and the requester is charged a fee for a failed attempt. This matches the "AA fund loss or freezing" impact class.

### Likelihood Explanation
This does not require a malicious counterparty; it is a natural consequence of normal AA operation (accepting many small deposits over time, dust-output filtering, and per-transfer-input/oversize-fee overhead in `completePaymentPayload`) combined with any AA design — such as the sample bank/order-book AAs in this very codebase — that authorizes withdrawal purely by comparing the requested amount to a bookkeeping state variable rather than to actually spendable UTXOs. Any sufficiently active AA that receives many payments and later faces a large or send-all withdrawal request can hit this condition.

### Recommendation
Expose to oscript a way to query the actually available "liquidity" of the AA's own address (e.g., count/sum of currently unspent, non-dust outputs) so AA authors can gate withdrawals accordingly, or have `completePaymentPayload` support partial/best-effort withdrawal amounts (similar to `send_all`) instead of failing the whole message set and bouncing the trigger when `target_amount` cannot be fully met. At minimum, document this limitation clearly so AA authors cross-check `var[$key]`-style balances against reachable UTXO liquidity before authorizing large withdrawals.

### Proof of Concept
1. Deploy an AA using the bank-style pattern where deposits accumulate `var[$key] += trigger.output[[asset=base]]` for many small deposits over time (as in `test/samples/a_bank_without_percent.oscript`). [8](#0-7) 
2. Send enough small deposits that the AA's on-chain address ends up holding funds mostly as many outputs below/near `FULL_TRANSFER_INPUT_SIZE`, or otherwise such that summing all discoverable stable/unstable UTXOs is less than `target_amount` for a subsequent large withdrawal (which also needs room for `FULL_TRANSFER_INPUT_SIZE` per consumed input and possible oversize fees).
3. Trigger a withdraw for an amount `<= var[$key]` (passes the oscript `if` condition) but greater than what `readStableOutputs` + `readUnstableOutputsSentByAAs` can supply.
4. Observe `completePaymentPayload`'s callback receives `'not enough funds for ' + target_amount + ' bytes'`, and `bounce(err)` fires: [4](#0-3) 
5. The trigger unit's response is `bounced: true`, state changes are rolled back, and the depositor loses `bounce_fees` while receiving no withdrawal — reproducing the "can't liquid exit despite sufficient logical balance" condition.
