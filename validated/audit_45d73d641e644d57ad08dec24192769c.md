### Title
API-scoped token bypasses stack scoping in CCMenu status endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug report describes a general class of trust-binding failures: a party is granted authorization for a limited scope of resources/actions, but the system fails to verify that the specific resource actually acted upon matches that granted scope. In `shipit-engine`, `ApiClient` tokens can be scoped to a single `Stack` (`stack_id`), and `Api::BaseController` is designed to enforce "the stack a token authorizes" by filtering the `stacks` relation to `current_api_client.stack_id`. `Api::CCMenuController`, however, overrides `#stack` to bypass that scoping entirely, breaking the equality `stack authorized by token == stack actually served`.

### Finding Description
`Api::BaseController` establishes the scoping contract used by every other API controller (`StacksController`, `TasksController`, `DeploysController`, `HooksController`, etc.): [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

If an `ApiClient` was created with a `stack_id` (i.e., scoped to a single stack, as exercised by the `here_come_the_walrus` fixture / "an api client scoped to a stack will only see that one stack" tests), `#stack` in the base controller can never resolve to any stack other than the one the token is bound to — `from_param!` raises a not-found error for any other `stack_id` param.

`Api::CCMenuController` re-defines `#stack` and does not go through the scoped `stacks` relation at all: [2](#0-1) 

```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`Stack.from_param!` is called directly on the `Stack` model — i.e., it can resolve **any** stack in the system, not merely the one identified by `current_api_client.stack_id`. The only authorization check performed is `require_permission :read, :stack`, which validates the client has the `read:stack` *permission string* — it never checks whether the client's `stack_id` binding matches the specific stack requested: [3](#0-2) 

```ruby
module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack
```

So the equality that should hold — `current_api_client.stack (the stack the token authorizes) == stack (the stack the request touches)` — is broken specifically in this controller, even though the surrounding framework (`BaseController#stacks`/`#stack`) was built to enforce it.

### Impact Explanation
Any holder of a valid `ApiClient` token that is scoped to a single stack and has the generic `read:stack` permission can query `GET /:stack_id.xml` (the CCMenu endpoint) for **any** stack in the Shipit instance, not just the one it was issued access to. This discloses that stack's deploy/build status, last build label, and activity (`app/views/shipit/ccmenu/project` template, rendered with `stack:` and `deploy: latest_deploy`), which is deploy-state information the token owner is not authorized to see. Per the accepted-impact list this is a High severity finding: "unauthenticated read of stack state, task streams or deploy output" — here read is effectively unauthorized (out-of-scope) rather than fully unauthenticated, but it crosses exactly the same boundary that the scoped-token mechanism exists to enforce.

### Likelihood Explanation
This does not require any privileged access beyond possessing (or being handed) a normal, narrowly-scoped `ApiClient` token — the exact kind of credential organizations issue to third parties/services expecting it to only see one stack. No signature forgery, no host misconfiguration, and no additional secrets are needed; simply calling the CCMenu endpoint with a different `stack_id`/`stack_id.xml` than the one the token is scoped to is sufficient. The bug is a straightforward method-override oversight (`stack` bypasses `stacks`), directly visible in the shipped controller code.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `Api::BaseController` instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Add regression tests asserting that a stack-scoped `ApiClient` (e.g. `here_come_the_walrus`) receives a 404 (or equivalent) when requesting `Api::CCMenuController#show` for a stack other than the one it is bound to.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to Stack A (`stack_id` set to Stack A's id) with `permissions: ['read:stack']` (analogous to the `here_come_the_walrus` fixture used in existing specs).
2. As that client, issue: `GET /Stack-B-Owner/Stack-B-Name/Stack-B-Environment.xml?token=<token>` where Stack B ≠ Stack A.
3. Observe that `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])`, `require_permission :read, :stack` passes (permission string check only), and the response renders Stack B's build/deploy status — despite the token only being authorized for Stack A.
