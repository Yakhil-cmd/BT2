### Title
Cross-repository forged CI status unblocks unrelated Stack's deploy via unscoped SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit purely by `Commit.where(sha: params.sha)`, without ever checking that the webhook's originating `repository.full_name` matches the `Commit`'s owning `Stack`/`Repository`. An attacker who controls any repository/org already onboarded to Shipit can push a commit with identical content (and therefore identical SHA) to a victim commit that exists in a different Stack, post a `success` status for a blocking CI context on their own repo, and have GitHub deliver a legitimately-signed webhook that Shipit will apply to the victim's `Commit` — clearing the victim Stack's `blocking_statuses` gate and unblocking a later, unrelated commit for deploy.

### Finding Description
The broken binding the system should enforce is:
`payload.dig('repository','full_name') == commit.stack.repository.full_name` for every `Commit` a `status` webhook is allowed to mutate.

In practice, `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This never calls the `Handler#stacks` helper — `Repository.from_github_repo_name(repository_name)&.stacks` — which every other handler (`PushHandler`, `CheckSuiteHandler`, the pull-request handlers) uses to scope work to the repository named in the payload: [2](#0-1) [3](#0-2) [4](#0-3) 

`WebhooksController#verify_signature` only proves the payload was signed by *some* GitHub App configured for `repository_owner` (the org named in the payload itself) — it does not, and cannot, prove any relationship between that repository and the `Commit` row being matched by SHA: [5](#0-4) 

Because git commit SHAs are a deterministic hash of commit content (tree, parents, author/committer, message, timestamps), an attacker who forks or otherwise obtains the exact bytes of a real, public victim commit can reproduce an identical SHA in a repository they own — no cryptographic SHA‑1 collision is required, just content identity. They then legitimately push/tag that commit in their own repo and generate a real `status` event (via GitHub API or their own CI) with `state: success` and a `context` equal to one of the victim Stack's `blocking_statuses`. GitHub signs and delivers this webhook using the credentials for the attacker's own org, which passes `verify_signature` unchanged.

`Commit.where(sha: params.sha)` matches the victim's `Commit` row purely by SHA equality, ignoring `stack_id`/repository, and `create_status_from_github!` creates a `Status` scoped to `commit.stack_id` (the victim Stack) via `replicate_from_github!`: [6](#0-5) [7](#0-6) 

This flips `Status::Common#blocking?` to `false` for that earlier commit: [8](#0-7) 

which flips `Commit#blocked?` for a later, unrelated commit that scans `stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?)`: [9](#0-8) 

and therefore `Commit#deployable?`: [10](#0-9) 

`Status#after_create` also schedules `commit.schedule_continuous_delivery`, so the later commit can be picked up and deployed automatically without any further attacker action. [11](#0-10) 

None of the listed guards prevent this: `verify_signature` validates the attacker's own repository's signature (which is valid, since it's their own repo), not a relationship to the victim's commit; there is no `ExplicitParameters` field or model validation tying `Status#stack_id` to the webhook's `repository.full_name`; and `drop_unhandled_event`/`force_github_authentication`/team checks are irrelevant to unauthenticated webhook delivery.

### Impact Explanation
An attacker who owns (or can push to) any repository in an org already using Shipit can cause an **unauthorized deploy** on a completely unrelated Stack/repository by writing a `Status` record that was never authenticated by that Stack's own repository CI. This is a payload for one repository mutating another repository's Stack/commit data, and it results in an unauthorized deploy — matching the "Critical" impact category (unauthorized deploy achieved, and a payload for one repository mutating another's stack/commit). It is repeatable against any victim commit whose exact byte content the attacker can reproduce (any public commit, or any commit an attacker otherwise has visibility into), across arbitrary Stacks configured with `blocking_statuses`.

### Likelihood Explanation
Preconditions: the victim Stack must configure `blocking_statuses` (a common CI-gating feature) and have an earlier undeployed commit that is currently blocking due to a missing/failing status in that context; a later commit must otherwise be deployable. Attacker cost: obtain a byte-identical copy of a real, existing victim commit (trivial for any public commit via fork/clone) and push it to a repository they control that is under an org already onboarded to Shipit, then create one `status` API call (or use any real CI) with the matching `context` and `state: success`. No Shipit credentials, session, API token, or GitHub secrets are needed — only ordinary push/API access to a repository the attacker legitimately owns. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` the same way other handlers do: resolve the commit set via `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and restrict `Commit.where(sha: params.sha)` to `stack.commits` for stacks belonging to that repository, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This enforces `payload.repository.full_name == commit.stack.repository.full_name` before any `Status` is written.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create `repo_a = shipit_repositories(...)` and `stack_a` with `blocking_statuses` including `"ci/travis"`; create `commit_earlier` and `commit_later` on `stack_a` such that `commit_later` is `newer_than` `stack_a.last_deployed_commit` and `older_than` itself scans `commit_earlier`. Leave `commit_earlier` with no status for `"ci/travis"` so `commit_earlier.blocking? == true` and assert `commit_later.blocked? == true` / `deployable? == false`.
2. Create an unrelated `repo_b` (different `full_name`, e.g. `"attacker/evil-repo"`) with its own `stack_b`, containing no relationship to `stack_a`.
3. Build a `status` webhook payload with `repository.full_name = "attacker/evil-repo"`, `sha = commit_earlier.sha` (simulating a byte-identical forged commit), `state: "success"`, `context: "ci/travis"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, since the finding is about repository scoping inside the handler, not signature bypass).
5. Assert `commit_earlier.reload.blocking? == false` (the binding: SHA matched a commit whose owning stack/repository ≠ payload's repository, yet the status was still applied).
6. Assert `commit_later.reload.blocked? == false` and `commit_later.deployable? == true`.
7. Optionally assert that `stack_a.trigger_continuous_delivery` (or the scheduled `ContinuousDeliveryJob`) now selects `commit_later` for deploy, demonstrating the unauthorized-deploy impact.
