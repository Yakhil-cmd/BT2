### Title
Webhook signature verification binds the wrong `organization` to the acted-upon `repository`, enabling cross-tenant webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using the GitHub App secret associated with `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . However, every event handler that actually acts on the payload resolves the target repository/stack from a completely different, unauthenticated field: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties `repository.owner.login` (the value used to select the signing secret) to `repository.full_name` (the value used to select the object being mutated). In Shipit's multi-organization configuration, each org has its own `webhook_secret` [4](#0-3) [5](#0-4) , so this binding gap allows an attacker who legitimately controls one tenant's webhook secret to sign a payload as their own org while pointing `repository.full_name` at a different organization's repository.

### Finding Description
The signature check is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

This only proves the raw body was signed with the secret belonging to whatever organization `repository.owner.login` names — it never checks that `repository.full_name` (i.e., `owner/repo`) is actually owned by that same organization. Every handler, however, resolves the object to mutate solely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Because HMAC verification covers the entire raw JSON body, the attacker cannot forge a signature without knowing *some* org's secret — but Shipit supports per-organization secrets (`secrets.github[organization][:webhook_secret]`) [5](#0-4) [4](#0-3) , so an attacker who legitimately administers/installed the GitHub App for their own low-privilege organization "Org A" possesses Org A's `webhook_secret`. That attacker can craft:
```json
{ "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/private-repo" }, ... }
```
Sign it with Org A's secret, and `verify_signature` will pass (`repository_owner` = `"org-a"` resolves to Org A's `GitHubApp`), while `PushHandler`, `StatusHandler`, `MembershipHandler`, and the `PullRequest::*Handler`s all operate against `org-b/private-repo` because they only look at `repository.full_name` [7](#0-6) [8](#0-7) [9](#0-8) .

This is the exact class of bug in the external report: a value that participates in the trust decision (`repository.owner.login`, analogous to the risk-engine's clamped inputs) is disjoint from the value that the "protection" is actually supposed to bind to (`repository.full_name`, the actually-mutated resource) — the check exists, executes, and even blocks bad signatures, but it verifies the wrong binding, so it provides no real cross-tenant isolation.

### Impact Explanation
Concretely reachable, unprivileged-relative-to-the-victim actions include:
- **Forged CI status injection** via `StatusHandler#process`, which calls `commit.create_status_from_github!(params)` for any commit whose sha the attacker specifies, on Org B's stack [10](#0-9) . Since deployability gates on required statuses (`Commit#deployable?` / `blocked?`) [11](#0-10) , forged "success" statuses can unblock/trigger an **unauthorized deploy** of a commit that never actually passed CI on Org B's real repository, especially with `continuous_deployment?` enabled (`schedule_continuous_delivery`) [12](#0-11) .
- **Forced resync / state corruption** on Org B's stack via `PushHandler`, which enqueues `GithubSyncJob` for any stack matching `repository.full_name` + branch [13](#0-12) .
- **Review-stack manipulation** (archiving PR-based review stacks) via `PullRequest::ClosedHandler`, scoped only by `repository.full_name` [9](#0-8) .

These map to the required impact bar of "cross-repository writes" / "an unauthorized deploy," since a party with no access to Org B's repository or GitHub organization can cause Shipit to write state (statuses, sync, review-stack archival) against Org B's stack.

### Likelihood Explanation
Requires the attacker to already possess a valid webhook secret for *some* organization configured in the same multi-tenant Shipit instance (their own, legitimately installed GitHub App) — no session, no `ApiClient` token, and no compromise of the victim's secret is needed. Any Shipit deployment serving more than one GitHub organization with per-org `webhook_secret`s (`Shipit.github(organization:)` / `github_app_config`) is exposed [4](#0-3) . The forged JSON body is trivial to construct and sign once the attacker's own secret is known.

### Recommendation
After signature verification succeeds, cross-check that `repository.full_name`'s owner segment matches the `repository_owner` (or `organization.login`) value that was used to select the verifying `GitHubApp`/secret, and reject the webhook (422) if they diverge. Apply the same cross-check inside `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks` so handlers cannot be reached with a mismatched owner even if the controller-level check is bypassed by a future refactor.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, `org-a` and `org-b`, each with its own `webhook_secret`.
2. As the (legitimate, low-privileged) admin of `org-a`, compute `sha1=HMAC(org-a-secret, body)` for the body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/private-repo" }
   }
   ```
3. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=...`.
4. Observe `verify_signature` passes (`repository_owner` = `"org-a"`), and `PushHandler` enqueues `GithubSyncJob` against `org-b/private-repo`'s stack — despite the attacker never being authenticated for, or having write access to, `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
