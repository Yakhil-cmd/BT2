Let me verify the final piece: `MembershipHandler` uses `params.team.id` (attacker-controlled `github_id`) and `params.organization.login` to find-or-create a `Team`, then adds `params.member.login` as a member — and this `Team` can be one of `Shipit.github_teams` used for authorization in `Authentication#force_github_authentication` / `User#authorized?`.### Title
Unauthenticated webhook signature bypass via attacker-selected organization allows forged `membership` events to grant `Shipit.github_teams` authorization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using an **unauthenticated field from the JSON body itself** (`repository.owner.login`, falling back to `organization.login`), not a value tied to any credential the requester holds. In a multi-organization Shipit deployment (a documented, supported configuration - see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), each configured GitHub organization has its own independent `webhook_secret`. Because the organization used for signature verification is attacker-chosen payload data, and `GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatically verified (`return true unless webhook_secret`), an attacker can pick any configured organization whose secret is blank (or unknown to them) to make the signature check pass unconditionally, then supply a `membership` event payload naming a **different**, real organization/team. This breaks the intended binding: "the organization whose secret authenticated the request" must equal "the organization/team the payload is allowed to mutate," but the code never enforces that equality.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read straight from the unauthenticated request JSON body before any signature has been validated. This value is used to select **which** `GitHubApp` (and therefore which `webhook_secret`) is used to verify the signature: [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally passes if that organization has no secret configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Shipit explicitly supports hosting multiple GitHub organizations simultaneously, each with its own independently-configured `webhook_secret`: [4](#0-3) [5](#0-4) 

Because the organization used to pick the secret (`repository_owner`) comes from the same untrusted body that is later processed by the event handler, and can differ from the actual `organization`/`team` object embedded elsewhere in the same payload, an attacker who knows (or controls) one org with a blank/no `webhook_secret` can craft a body whose `repository.owner.login` (or top-level `organization.login`, used as fallback) points at that blank-secret org while the nested `membership` payload's `organization.login`/`team` fields target a completely different, real organization/team.

The `membership` handler trusts the payload's team/organization fields to find-or-create a `Team` and add/remove members, without any further binding to the value used for signature verification:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
end

def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [6](#0-5) 

If the resulting `Team` (matched purely by attacker-supplied `github_id`) is one of the teams configured in `Shipit.github_teams` (the OAuth authorization allowlist), adding a `Membership` for an arbitrary GitHub login directly grants that user access to the entire Shipit application: [7](#0-6) [8](#0-7) 

This is structurally the same class of bug as the reported Prover.sol issue: two logically-linked fields (the value that gates a check, and the value that is actually acted upon) are validated together in appearance but never bound to each other, letting an attacker supply a "valid" gating value alongside an arbitrary target value.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization — explicitly listed as a valid High-impact outcome. An attacker who is not a member of any authorized team, and who has no legitimate webhook secret, can grant themselves (or anyone whose GitHub login they know) membership in a Shipit-recognized authorized team, bypassing OAuth-team-based access control entirely and gaining full application access (deploys, rollbacks, stack management, etc., depending on what `force_github_authentication` gates).

### Likelihood Explanation
Exploitability requires the target Shipit instance to be running in the documented multi-organization mode with at least one configured organization lacking a `webhook_secret` (webhook secrets are explicitly optional per `docs/setup.md`). This is a realistic and supported configuration, not a contrived edge case, since multi-org support and optional webhook secrets are both first-class, documented features. No prior authentication, session, or API token is required — only knowledge of an organization name with no configured secret (which may be guessable, e.g., a newly-added/staging organization) and the target organization/team's public GitHub metadata (login, team id, name/slug — all discoverable via the public GitHub API).

### Recommendation
- Do not select the verification secret from unauthenticated payload data. Verify the raw body's signature against **every** configured organization's secret (or at least confirm that whichever secret validates the signature also equals the organization referenced by the event's substantive payload fields, e.g., `membership`'s `organization.login`/`team.id`).
- For the `membership` handler specifically, ensure `repository_owner`/the organization used for signature verification is cryptographically bound to (equal to) `params.organization.login` before trusting `team`/`member` mutations.
- Treat organizations with a blank `webhook_secret` as never a valid signer for events affecting other organizations' state (or require all configured organizations in multi-org mode to have a non-blank secret).

### Proof of Concept
Preconditions: Shipit is deployed in multi-org mode (`config/secrets.yml` → `github: { OrgWithNoSecret: {...webhook_secret: nil}, RealOrg: {...webhook_secret: "s3cr3t"} }`), and `Shipit.github_teams` includes a team belonging to `RealOrg`.

1. Attacker sends `POST /webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature` (or any arbitrary value), and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Real Team", "slug": "real-team", "url": "https://github.com/..." },
  "organization": { "login": "RealOrg" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "OrgWithNoSecret" } }
}
```
2. `repository_owner` resolves to `"OrgWithNoSecret"` [9](#0-8) , so `Shipit.github(organization: "OrgWithNoSecret")` is used to verify the signature, and since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally [3](#0-2) , regardless of the (missing/garbage) `X-Hub-Signature` header — the request passes `before_action :verify_signature`.
3. `MembershipHandler#process` runs against `params.organization.login == "RealOrg"` and `params.team.id == 999` (matching the real `RealOrg` team's GitHub team ID, obtainable via GitHub's public API), creating/finding that `Team` and calling `team.add_member(User.find_or_create_by_login!("attacker-github-login"))` [6](#0-5) .
4. If that team is in `Shipit.github_teams`, `attacker-github-login`'s Shipit user now passes `authorized?` [7](#0-6)  and, after completing the (unauthenticated to Shipit, standard) GitHub OAuth login flow as that GitHub user, gains full access to the Shipit application.
