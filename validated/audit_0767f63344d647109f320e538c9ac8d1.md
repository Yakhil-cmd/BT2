### Title
AA reward/share-distribution logic using `balance[asset]` can be stolen when a conditional message skip leaves previously-received funds credited to the AA's balance without being routed onward - (File: `aa_composer.js`, `formula/evaluation.js`)

### Summary
The reported Cap issue is a class of bug where funds are transferred into a contract's balance, but a subsequent conditional check (`coverage == 0`) causes the distribution step that should forward those funds to be skipped. Because the funds are already recorded as balance, they sit there until an unrelated, later distribution call sweeps them up and pays them to a different beneficiary than intended. The Obyte AA engine has the same structural footgun: an AA's `balance[asset]` (and `var`/`balance` operators) reflect funds that have already been credited to the AA even when the AA's own `if`/message-filtering logic decides not to forward them in the same response. A subsequent, unrelated trigger that computes a payout as a function of `balance[asset]` (a documented and common AA pattern, e.g. proportional/"send-all" distributions) will unintentionally include this stranded balance in its own payout, diverting it to whoever posts that next trigger.

### Finding Description
When a unit sends coins to an AA (as a primary trigger or as a secondary trigger from another AA), `updateInitialAABalances` immediately credits the AA's balance with the full amount received, before the AA's own logic decides what to do with it: [1](#0-0) 

If the AA's `messages` template evaluates in a way that filters out all payment messages for this particular trigger (e.g., an `if` condition analogous to Cap's `totalCoverage == 0` check evaluates false, so no output message is emitted), the AA "eats" the coins and simply performs state changes without sending anything back — the funds remain part of the AA's on-chain balance: [2](#0-1) 

This "eat the coins silently" behavior is by design and is exercised by real tests (`no messages`, `no outputs`, `only 0 output` in `test/aa.test.js`), confirming these funds stay in `aa_balances` rather than being returned or forwarded: [3](#0-2) 

Later, an entirely different, unrelated trigger unit can invoke the same AA. If that AA's payout formula computes an amount as a share of `balance[asset]` (the current total balance, read via the `balance` formula operator), the stranded funds from the earlier skipped distribution are indistinguishable from freshly received funds and get folded into the new payout: [4](#0-3) 

This exact "compute payout from current pooled `balance[asset]`" pattern is the idiomatic way AAs distribute proportional rewards/shares in Obyte (bonding-curve/market-maker AAs, dividend/fundraising AAs), as shown in the repo's own sample AAs: [5](#0-4) [6](#0-5) 

The root cause parallels the Cap finding precisely: a value is transferred into a shared pool (contract balance / AA balance), a conditional skip based on a computed metric (coverage == 0 / an `if` branch resolving false) prevents that value from being forwarded in the same operation, and the value remains commingled in the pool's balance. The *next* unrelated party who triggers a balance-proportional distribution captures value that rightfully belonged to the earlier depositor.

### Impact Explanation
Any user can post a trigger unit to an AA (unprivileged action). If the AA is one of the common share/dividend/bonding-curve-style AAs that (a) sometimes conditionally skips forwarding received funds in the same response (leaving them credited to `aa_balances`), and (b) computes payouts to future callers as a function of `balance[asset]`, a subsequent unrelated caller's payout will include the stranded funds, resulting in concrete unauthorized reallocation of AA-held funds from the rightful depositor to a subsequent, unrelated trigger sender — an AA fund loss/theft matching the accepted impact criteria (AA fund loss).

### Likelihood Explanation
This requires a specific but common AA design pattern (conditional skip of forwarding + later balance-proportional payout), which is exactly the pattern demonstrated by the repository's own bundled sample AAs (`uniswap_like_market_maker.oscript`, `bounce_half_of_balance.oscript`, `fundraising_proxy.oscript`). Because triggering an AA and choosing when to send is entirely within reach of any unprivileged unit poster, and the underlying engine behavior (`balance[]` returning pooled, undifferentiated balance; silent coin-eating when messages filter out) is a core, unconditional feature of `aa_composer.js` and `formula/evaluation.js`, the precondition is realistic for any AA author who follows this common accumulation-then-distribute idiom without explicitly tracking a separate "owed" state variable.

### Recommendation
AAs that manage pooled/shared funds and use `balance[asset]` to compute payouts should not conflate "current total balance" with "funds eligible for the current distribution." AA authors should track amounts owed/undistributed in explicit state variables (`var[...]`) rather than relying on `balance[asset]`, and any conditional skip path that "eats" received coins should either bounce (returning funds to sender) or explicitly account for the received amount in state so it is not later double-counted by an unrelated distribution formula. Documentation/guidance for AA authors should call out this balance-pooling hazard explicitly, since the engine itself provides no protection against balance-based formulas silently including stranded/skipped funds.

### Proof of Concept
1. Deploy an AA that, on trigger, only forwards received bytes if some condition C is true; otherwise it performs no payment message (funds are "eaten" into `aa_balances`, per `aa_composer.js:1868-1877`).
2. Post a trigger to this AA where condition C is false (e.g., analogous to `coverage == 0`) — the sent bytes are credited to the AA's balance via `updateInitialAABalances` (`aa_composer.js:474-490`) but no payment is issued back.
3. Deploy/trigger a second flow (or the same AA on a later branch) whose payout to the caller is computed as `share * balance[base]` (per the pattern in `test/samples/uniswap_like_market_maker.oscript:33-48` and `bounce_half_of_balance.oscript`), using `readBalance` (`formula/evaluation.js:1510-1528`), which returns the AA's full pooled balance including the funds stranded in step 2.
4. The second (unrelated) caller's payout includes the stranded funds from step 2, which were never returned to the original sender — demonstrating fund diversion analogous to the Cap `distributeRewards`/`realizeRestakerInterest` issue.
