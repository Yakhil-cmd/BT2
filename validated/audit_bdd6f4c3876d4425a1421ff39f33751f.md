### Title
Cross-organization commit status forgery via unscoped `Commit.where(sha:)` lookup - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository/organization that the verified webhook belongs to, and then calls `create_status_from_github!` on every match. Because `Commit.sha` is only unique per `stack_id` (not globally), a webhook whose signature was verified using Org1's `webhook_secret` can create/mutate status rows on a `Commit` belonging to a completely unrelated Org2 stack if the two stacks happen to share a commit `sha`.

### Finding Description
The broken binding, stated as an equality that the code must (but does not) maintain:
`organization_that_verified(payload) == organization_owning(stack_of_every_commit_mutated_by(payload))`

Trace:
1. `WebhooksController#verify_signature` resolves the app/secret purely from the payload's `repository.owner.login` (or `organization.login`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, at `app/controllers/shipit/webhooks_controller.rb:24-30`. This only proves the payload was signed by *Org1's* secret — it says nothing about which `Commit`/`Stack` rows the payload is allowed to touch.
2. Once verified, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` at `app/controllers/shipit/webhooks_controller.rb:10-15`, passing the raw parsed JSON — the `repository` field is never passed to the handler nor used to scope the lookup.
3. `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
(`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) — this query has no `stack_id`/`repository_id` filter at all.
4. `Commit` records are uniquely indexed on `(sha, stack_id)`, not on `sha` alone: `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb:1-5` and `test/dummy/db/schema.rb:63-87` show `t.index ["sha", "stack_id"], unique: true`. The same `sha` can legitimately exist in many different stacks/repositories (shared history, cherry-picks, the empty-tree SHA, or a stack whose repo hasn't diverged from another org's fork).
5. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) creates a `Status` on that commit and triggers `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` and can call `stack.schedule_merges`, i.e., it can influence deployability/merge state of the *unrelated* stack (`app/models/shipit/commit.rb:366-386`).

Attacker request: an unprivileged GitHub user pushes/owns a repository "attacker/evil" registered under their own org (Org1) with its own `webhook_secret`. They arrange (or simply wait) for a commit `sha` to coincide with a `sha` already present in a Shipit-tracked Org2 stack (trivially achievable with the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee491`, or by forking a public upstream repo before Org2's stack diverges). They then send:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<computed with Org1's webhook_secret>
{ "repository": {"owner": {"login": "org1"}}, "sha": "<shared sha>", "state": "success", ... }
```
`verify_signature` validates this with Org1's secret and passes. `StatusHandler` then matches `Commit.where(sha: "<shared sha>")`, which returns commits from *both* Org1's and Org2's stacks (if both have a commit with that sha), and writes a forged `success`/`failure` status onto Org2's commit — without Org2's `webhook_secret` ever being checked.

Existing guards fail because they operate at the wrong level: `verify_signature` proves *which org's secret* signed the payload, but never constrains *which stack/commit rows* the payload's `sha` is permitted to affect; `ExplicitParameters` (`params do ... end` block in the handler) validates types/presence of `sha`/`state` but not repository scope; and there is no `drop_unhandled_event` or model validation preventing a global `sha` lookup.

### Impact Explanation
A payload verified with one organization's `webhook_secret` can write `Status` rows (and trigger `Hook.emit`/`schedule_merges` side effects) on `Commit` rows owned by a different organization's `Stack`, entirely bypassing that organization's `webhook_secret` isolation. This is a cross-tenant state mutation: an attacker controlling any registered Shipit organization/repo (even a throwaway one they create) can forge CI status for commits in unrelated organizations' stacks whenever a `sha` collision occurs, which is repeatable and requires no privileges in the victim organization. This matches the Critical impact category "a payload for one repository mutating another's stack/commit."

### Likelihood Explanation
Preconditions: the attacker needs their own Shipit-registered GitHub organization/repo with a valid webhook secret they control (trivial — any GitHub org can install the Shipit GitHub App per `docs/setup.md`), and a `sha` collision between their commit and a target Org2 commit. Exploitation is deterministic for edge cases like the git empty-tree SHA, or achievable by forking a shared upstream before divergence. No GitHub/Shipit secrets of the victim are needed. Attacker cost is a single crafted HTTP POST per exploitation attempt, fully repeatable against any stack that happens to contain the colliding `sha`.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository that the verified webhook payload actually belongs to (e.g., resolve `Stack`/`Repository` from `params.dig('repository', 'full_name')` and restrict `Commit.where(sha: params.sha, stack_id: stack.id)`), mirroring how other code paths (e.g., `app/jobs/shipit/github_sync_job.rb`, `app/controllers/shipit/api/commits_controller.rb`) always scope commits through `stack.commits`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_org_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossOrgTest < ActiveSupport::TestCase
        test "status verified for org1 mutates a commit belonging to org2's stack" do
          shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee491'

          repo1 = Repository.create!(owner: 'org1', name: 'repo1')
          stack1 = Stack.create!(repository: repo1, environment: 'production', branch: 'master')
          commit1 = stack1.commits.create!(sha: shared_sha, message: 'x', author: AnonymousUser.new,
                                            committer: AnonymousUser.new, authored_at: Time.now, committed_at: Time.now)

          repo2 = Repository.create!(owner: 'org2', name: 'repo2')
          stack2 = Stack.create!(repository: repo2, environment: 'production', branch: 'master')
          commit2 = stack2.commits.create!(sha: shared_sha, message: 'y', author: AnonymousUser.new,
                                            committer: AnonymousUser.new, authored_at: Time.now, committed_at: Time.now)

          # Simulate: WebhooksController#verify_signature already succeeded using ONLY org1's webhook_secret
          params = ActionController::Parameters.new(
            'sha' => shared_sha, 'state' => 'success', 'context' => 'ci',
            'repository' => { 'owner' => { 'login' => 'org1' }, 'full_name' => 'org1/repo1' }
          )

          assert_equal 0, commit2.statuses.count

          StatusHandler.new.call(params) # only org1 authenticated this call

          # broken binding: org2's commit was mutated despite org2's webhook_secret never being checked
          assert_equal 1, commit2.reload.statuses.count,
            "commit belonging to org2's stack was mutated by a payload verified only with org1's webhook_secret"
        end
      end
    end
  end
end
