### Title
Missing `return` after payload-hash exception in `handleSavedPrivatePayments` causes double invocation of the async iteration callback and a crash-prone desync of private-payment processing state - (File: network.js)

### Summary
`handleSavedPrivatePayments()` iterates over queued private-payment chains with `async.each`, and for each row calls an internal `validateAndSave` closure. Inside that closure, a `try/catch` around `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` handles the case where the payload cannot be hashed, but the `catch` block does not `return` after handling the error, so execution falls through and continues to run the rest of the function using corrupted state. This mirrors CVE-2016-6509's root cause pattern: a single crafted input puts a per-item conversation/state-tracking routine into an inconsistent state instead of cleanly aborting, and the routine keeps running as if nothing happened, eventually double-firing its completion bookkeeping.

### Finding Description
`arrPrivateElements` (and thus `objHeadPrivateElement.payload`) originates from network-supplied `private_payment` messages that are persisted into `unhandled_private_payments` after only shallow structural checks in `handleOnlinePrivatePayment` (non-empty array, valid unit hash, non-negative `message_index`/`output_index`); the payload's internal shape is not validated before being queued [1](#0-0) .

When `handleSavedPrivatePayments` later reprocesses a queued row, it computes a payload hash to build a dedup/event key:

```
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
``` [2](#0-1) 

`objectHash.getBase64Hash(obj, true)` calls `getJsonSourceString`, which deliberately `throw`s on structurally "malformed" but syntactically valid JSON values, e.g. empty arrays/objects, `null`, non-finite numbers, or unknown types anywhere in the nested payload [3](#0-2) . Because none of these shapes are rejected by the earlier shallow checks in `handleOnlinePrivatePayment`, an attacker-controlled `payload` can deterministically trigger this exception.

When the exception fires, the `catch` block already calls `deleteHandledPrivateChain(..., cb)` — which itself calls `cb()` once the DB delete completes — but execution does not stop there. It falls through to build `key` (with `json_payload_hash` now `undefined`) and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`. That call will eventually reach one of `ifOk`/`ifError`/`ifWaitingForChain`, each of which itself calls `deleteHandledPrivateChain(..., cb)` (or `cb()` directly) a second time for the same `async.each` item [4](#0-3) . This double-invocation of the per-item `cb` for a single `async.each` iteration desyncs the iteration bookkeeping exactly as the LDSS dissector desynced its per-conversation state on a single crafted packet.

### Impact Explanation
Double-invoking the `async.each` completion callback (`cb`) for one item causes the final callback of `handleSavedPrivatePayments` — which calls `unlock()` on the `"saved_private"` mutex — to fire prematurely/twice while other rows in the same batch may still be mid-processing. Depending on the `async` library's semantics for a callback invoked twice, this can:
- release the `"saved_private"` mutex early, allowing a concurrent `handleSavedPrivatePayments` run to interleave with an in-flight one, or
- throw ("callback already called") as an unhandled exception on the event loop, crashing the wallet/hub Node.js process.

Either outcome is a denial-of-service in the private-payment / personal-wallet-and-hub pipeline that is directly reachable by any peer or hub correspondent sending a private-payment chain with a malformed head payload — no privileged position required, matching the "unprivileged trigger causes conversation-state mishandling → crash" bug class from the report.

### Likelihood Explanation
Any device/peer that can send a `private_payment` message (a normal wallet-to-wallet or hub-relayed operation) can supply a payload whose nested structure contains an empty object/array or similarly "un-hashable" shape without failing any of the shallow checks performed before persistence, so the vulnerable code path is trivially reachable without special privileges.

### Recommendation
Add a `return` (or otherwise short-circuit) immediately after handling the `catch` branch in `network.js`'s `handleSavedPrivatePayments`/`validateAndSave` so that once `deleteHandledPrivateChain` is invoked for the hash-failure case, no further code — including the second call into `privatePayment.validateAndSavePrivatePaymentChain` — executes for that item.

### Proof of Concept
1. From a peer/hub-connected device, send a `private_payment` (or `private_payment_chain` via hub) message whose head element's `payload` includes a deeply nested empty object/array (e.g. `payload.outputs[0] = {}` or any nested `[]`), while still satisfying the shallow checks in `handleOnlinePrivatePayment` (non-empty `arrPrivateElements`, valid-looking `unit` hash, integer `message_index`/`output_index`).
2. The message is queued into `unhandled_private_payments` via `savePrivatePayment` without deep validation.
3. When `handleSavedPrivatePayments` processes the row, `objectHash.getBase64Hash(payload, true)` throws inside `getJsonSourceString` due to the empty nested array/object.
4. The `catch` block calls `deleteHandledPrivateChain(..., cb)` but execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose callback also calls `deleteHandledPrivateChain(..., cb)`/`cb()`, invoking `cb` twice for the same `async.each` item and desyncing the mutex-guarded batch completion.

function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	return stringify(obj);
}
