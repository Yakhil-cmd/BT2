### Title
Unrelated unit's `saveJoint` can crash/hang node processing when triggered AA execution throws - (File: `writer.js`)

### Summary
`writer.js`'s `saveJoint` synchronously awaits `aa_composer.handleAATriggers()` (and `main_chain.advanceMcStability`) whenever the unit being saved happens to advance main-chain stability into an MCI that carries pending AA triggers, even though the unit being saved may itself have nothing to do with any AA. Any unhandled exception thrown while processing those unrelated triggers propagates up through the `saveJoint` call of the innocent unit, exactly mirroring the Canto `PostTxProcessing` bug where a hook unrelated to the transaction's purpose can revert/crash processing of that transaction.

### Finding Description
Every unit that becomes the "trigger" to advance the main-chain stability point runs `writer.saveJoint()`, which, after committing the DB transaction for that specific unit, checks whether `bStabilizedAATriggers` is set and if so calls: [1](#0-0) 
This function pulls *every* pending row from the global `aa_triggers` queue (posted by potentially unrelated addresses/units) and processes them serially: [2](#0-1) 
Inside `handlePrimaryAATrigger`, several code paths use bare `throw Error(...)` instead of returning an error to a callback, e.g.: [3](#0-2) 
Because these are plain synchronous throws inside nested callbacks/async functions invoked from an `await aa_composer.handleAATriggers()` in `saveJoint`, any such throw (cache inconsistency, DB write failure, "unit not found in cache", etc., for a *completely different* trigger unit/address than the one being saved) becomes an unhandled exception (or unhandled promise rejection) in the middle of `saveJoint`'s post-commit logic for the original, unrelated unit. Similar unguarded `throw Error(...)` sites also exist in the headers/witnessing commission recalculation path that runs unconditionally for every stabilized MCI: [4](#0-3) [5](#0-4) 
This is architecturally identical to the reported Canto issue: a hook that runs on the critical path of an unrelated transaction/unit (there: `PostTxProcessing` for every EVM tx; here: AA-trigger execution and commission calculation for every unit that advances MC stability) can fail for reasons entirely disconnected from the triggering unit's own content, and the failure propagates back to affect that unrelated unit's processing/commit flow instead of being isolated and logged.

### Impact Explanation
Because the DB transaction for the originating (unrelated) unit has *already been committed* by the time `handleAATriggers()` runs, an uncaught exception here does not roll back that unit, but it can crash the node process (Node.js terminates on unhandled promise rejections in this codebase, as seen in the test harness `process.on('unhandledRejection', up => { throw up; })`), or leave the `saveJoint` callback chain permanently unresolved, halting further unit processing on that node. Because AA execution and commission math are deterministic and running on every full node, a single crafted AA trigger or state inconsistency that hits one of these unguarded `throw` paths would crash the same code path on every full node processing that MCI, producing a network-wide inability to progress/confirm new units — matching the "network unable to confirm new units" impact category. At minimum, it demonstrates the same class of unrelated-unit collateral impact identified in the original report.

### Likelihood Explanation
Reaching this code path only requires posting ordinary units that (a) target an AA address (to populate `aa_triggers`), or (b) advance the main-chain stability point — routine, unprivileged actions available to any unit poster. Triggering the specific `throw` requires hitting one of the internal-consistency-violation branches (e.g., `handlePrimaryAATrigger`'s "unit not found in cache", or `headers_commission.js`'s RAM/DB mismatch assertions), which are intended as defensive assertions rather than attacker-reachable in normal operation; likelihood of a specific exploit path is therefore moderate/uncertain without further code-path analysis of exactly which inputs can force `storage.assocStableUnits[unit]` to be missing or the RAM/DB commission calcs to diverge. This should be treated as a real design gap (undifferentiated `throw` on the critical path of unrelated units) confirmed by direct code inspection, even though a concrete triggering input for the assertion branches could not be fully proven within the scope of this analysis.

### Recommendation
- Do not let unhandled exceptions from `aa_composer.handleAATriggers()`, `headers_commission.calcHeadersCommissions()`, or `paid_witnessing.updatePaidWitnesses()` propagate into the `saveJoint()` flow of an unrelated unit.
- Wrap these calls in explicit `try/catch`, log the error, and either retry safely or halt gracefully (fatal-log-and-exit) without corrupting/blocking the already-committed unrelated unit's processing pipeline.
- Replace ad-hoc `throw Error(...)` assertions inside `handlePrimaryAATrigger` and `headers_commission.js` with structured error handling that isolates failures to the specific trigger/commission computation rather than the calling unit's save flow.
- Add regression tests that simulate a failure inside AA-trigger execution triggered indirectly by an unrelated unit's stabilization and assert that the unrelated unit's save/commit result is unaffected and the node continues operating.

### Proof of Concept
1. Post AA definition `AA1` and have it accumulate a pending row in `aa_triggers` (e.g., via a payment to `AA1` that becomes a primary trigger).
2. Force one of the internal assertion branches in `handlePrimaryAATrigger` to fail — e.g., manipulate timing/cache state so `storage.assocStableUnits[unit]` lacks the entry for the trigger unit right before line 104-106 executes: [6](#0-5) 
3. Post an entirely unrelated unit `U2` (plain payment, no AA involvement) whose acceptance happens to advance the main-chain stability point to the MCI containing the pending AA trigger from step 1.
4. Observe that `writer.saveJoint()` processing `U2` calls `await aa_composer.handleAATriggers()` at line 727 of `writer.js`, which throws inside `handlePrimaryAATrigger`, propagating the exception into `U2`'s save/commit callback chain and crashing/hanging the node — despite `U2` never interacting with any AA.
