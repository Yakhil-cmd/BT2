### Title
Webhook signature verified against `repository.owner.login`-selected secret while handlers act on the unrelated `repository.full_name` field, enabling cross-organization/cross-repository webhook forgery in multi-GitHub-App deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`config/secrets.yml` `github:` keyed by organization, as documented in `docs/setup.md`), the field used to select *which* GitHub App secret authenticates an inbound webhook is decoupled from the field used to determine *which repository/stack* the webhook payload subsequently writes to. This breaks the binding "organization that authenticated == repository that is written," letting a party who legitimately controls the webhook secret for one tracked organization forge events that write to stacks belonging to a different organization on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App (and thus the HMAC secret) using `repository_owner`, which is read straight out of the untrusted, attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves per-organization app configs (each with its own `webhook_secret`) as documented for multi-tenant setups: [3](#0-2) 

Once the HMAC check passes (`github_app.verify_webhook_signature`), the controller hands the *entire* raw JSON body — unmodified and with no re-validation of `repository.owner.login` against the org whose secret validated it — to the registered handlers: [4](#0-3) 

Every handler resolves the target repository/stack independently, using `repository.full_name`, a *separate* field from `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used only for secret selection) and `repository.full_name` (used only for repository/stack resolution and all subsequent writes) are never checked to agree, a party who controls a valid webhook secret for OrgA (e.g., they are an org owner who registered their own GitHub App pointed at this shared Shipit instance's `/webhooks` endpoint, per `docs/setup.md`'s "Using Multiple Github Applications" section) can:
1. Set `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` authenticates with OrgA's known secret.
2. Set `repository.full_name` to `"OrgB/some-repo"` — a repository/stack they do not control, tracked under a different GitHub App/organization on the same Shipit instance.
3. Sign the crafted payload with OrgA's secret and POST it to `/webhooks`.

The signature check passes (it only validates the raw bytes against OrgA's secret), and the handler then acts on OrgB's stack: `PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` on OrgB's stacks, `PullRequest::OpenedHandler`/`ReopenedHandler`/etc. create or unarchive `ReviewStack`s, and `StatusHandler`/`CheckSuiteHandler` write commit statuses/check runs for OrgB's commits — all key mechanisms that gate or trigger continuous-deployment/merge-queue behavior.

### Impact Explanation
This is a cross-organization/cross-repository write: an actor authenticated only for OrgA's webhook channel can inject state-changing GitHub events (pushes, PR open/close/label, statuses, check-suite results) against OrgB's stacks that they have no authorization over on the same Shipit instance. Depending on stack configuration (continuous deployment, merge queue, review-stack provisioning), this can trigger unauthorized syncs, review-stack creation/archival, or influence deploy/merge gating signals for a repository outside the attacker's authorized scope — matching the "cross-repository writes" High-impact category.

### Likelihood Explanation
Exploitation requires the attacker to legitimately hold a webhook secret for at least one organization configured on the shared Shipit instance (a realistic scenario in any multi-tenant/multi-org Shipit deployment as explicitly documented in `docs/setup.md`), and for the instance to track a stack belonging to a different organization. No secret guessing, TLS interception, or social engineering is needed — only crafting a JSON body whose `repository.owner.login`/`organization.login` and `repository.full_name` refer to different organizations, which is entirely within the attacker's control as the message author.

### Recommendation
- After signature verification, re-derive the authenticating organization and assert that `repository.full_name`'s owner matches `repository_owner` (or `organization.login`) used for secret selection; reject the webhook otherwise.
- Alternatively, pass the authenticated organization explicitly into each `Handler`, and have `Handler#stacks`/`#repository_name` scope lookups to that organization instead of trusting the payload's `repository.full_name` in isolation.

### Proof of Concept
```
# Multi-org secrets.yml:
# github:
#   OrgA: { webhook_secret: "orgA-secret", ... }
#   OrgB: { webhook_secret: "orgB-secret", ... }   <- tracked, attacker not authorized

POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(body, "orgA-secret")>

body = {
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },      # selects OrgA's secret for verify_signature
    "full_name": "OrgB/target-repo"    # actually resolved/written to by PushHandler
  }
}
```
`WebhooksController#verify_signature` authenticates using OrgA's secret and succeeds; `PushHandler#process` then resolves `Repository.from_github_repo_name("OrgB/target-repo")` via `Handler#stacks`/`#repository_name` and calls `stack.sync_github(expected_head_sha: ...)` on OrgB's stack, a repository the attacker never authenticated for.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
