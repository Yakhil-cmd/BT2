### Title
Webhook organization used for HMAC secret selection is never bound to the repository/commit the handler mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration (and thus the HMAC secret) used to validate an inbound webhook based on a field read from the *same unverified JSON body* it is about to validate [1](#0-0) . The value used for that lookup — `repository_owner`, taken from `params.dig('repository','owner','login')` — is never subsequently cross-checked against the fields the downstream handler actually acts on (`repository.full_name` in `PushHandler`, or a bare `sha` in `StatusHandler`) [2](#0-1) . This breaks the intended binding: *organization whose secret authenticated the request* == *organization/repository the handler mutates*.

### Finding Description
Shipit is multi-tenant at the webhook layer: `config/secrets.yml` defines a separate `github:` entry (with its own independent `webhook_secret`) per organization [3](#0-2) . `WebhooksController#verify_signature` picks which of these secrets to validate against using `repository_owner`, a value read straight out of the untrusted request body, then verifies the HMAC over the raw body using that org's secret [4](#0-3) :

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

Once the signature is accepted, the full parsed body is forwarded unchanged to the event handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .

Handlers independently derive the target of the mutation from other fields of that same body, without any re-check that they belong to the organization that was cryptographically authenticated:

- `Handler#repository_name` resolves the target purely from `payload.dig('repository', 'full_name')` [6](#0-5) , a sibling field of `repository.owner.login` inside the same JSON object but never compared to it.
- `PushHandler#process` uses that resolution to run `stack.sync_github(...)` against whatever `Stack` matches `repository.full_name` [7](#0-6) .
- `StatusHandler#process` is even weaker: it matches purely on `params.sha` globally across the whole Shipit installation — `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — with no repository/organization scoping whatsoever [8](#0-7) .

Because nothing ties `repository_owner` (used only for HMAC-secret selection) to `repository.full_name`/`sha` (used for the actual write), an administrator of *any one* organization configured in the same Shipit instance — who legitimately knows only their own org's `webhook_secret` — can hand-craft a JSON body where `repository.owner.login` names their own org (so the signature check passes) while `repository.full_name`/`sha` names a commit or repository belonging to a completely different tenant/stack configured in the same Shipit deployment.

### Impact Explanation
`StatusHandler` writes a GitHub-style status onto any commit that matches the given `sha`, regardless of stack/repository ownership. Shipit's continuous delivery / merge-gating logic (`app/jobs/shipit/continuous_delivery_job.rb`, `app/models/shipit/commit.rb`) consumes these statuses to decide whether a commit is "green" and eligible for automatic deployment. An attacker who controls one tenant org's webhook secret could therefore forge a passing CI status for a commit belonging to a different, unrelated stack, potentially causing an unauthorized/automated deploy to proceed without the real CI having passed for that repository — matching the "unauthorized deploy" impact class. `PushHandler` similarly lets one tenant force a `GithubSyncJob`/sync against a `Stack` outside their own repository. This is a direct instance of the required binding-break pattern: "an organization that authenticated versus the repository that is written."

### Likelihood Explanation
Exploitation requires the attacker to control the `webhook_secret` of *any one* GitHub organization already configured in the shared Shipit instance (a realistic scenario for multi-tenant Shipit deployments serving several orgs/teams), but does **not** require GitHub write access to the victim repository, a Shipit session, or an `ApiClient` token — only the ability to POST a crafted JSON body to the shared `/webhooks` endpoint. Given Shipit explicitly supports multiple `github:` orgs in one instance, this is a credible boundary the engine is expected to enforce but does not.

### Recommendation
After signature verification, re-derive `repository_owner`/organization strictly from the same trust anchor used to select the secret, and have every handler (`Handler#repository_name`, `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) reject or scope its lookups to stacks whose `Repository#owner` matches the authenticated organization, instead of trusting unrelated fields (`repository.full_name`, bare `sha`) from the same unauthenticated body split across different lookups.

### Proof of Concept
1. Attacker administers `org-attacker`, one of several organizations configured under `github:` in this Shipit instance's `secrets.yml`, and therefore knows `org-attacker`'s `webhook_secret`.
2. Attacker crafts a `status` webhook payload:
```json
{
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-attacker/some-repo" },
  "sha": "<sha of a commit belonging to victim-org/victim-repo's stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-attacker_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'org-attacker')` and successfully verifies the signature [1](#0-0) .
5. `StatusHandler#process` ignores the `repository` field entirely and applies the forged "success" status to any commit in the whole instance matching that `sha`, regardless of which org/repo it belongs to [8](#0-7) , potentially unblocking continuous deployment on `victim-org/victim-repo`'s stack.

Note: I was unable to fully trace the exact code path from `Commit#create_status_from_github!` through `ContinuousDeliveryJob` to a triggered deploy before running out of tool iterations (I only located the files by name/grep, not their full contents), so the final "auto-deploy" consequence is inferred from Shipit's documented continuous-deployment feature rather than a line-by-line confirmed trace. The organization/repository binding break itself, however, is fully confirmed in the cited controller and handler code.
