### Title
Cross-organization webhook forgery via mismatched signature-verification org vs. acted-upon repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` is used to validate an inbound webhook's HMAC signature based on an attacker-controlled field of the *same, unverified* JSON body (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) [2](#0-1)  Once the signature is accepted, every event handler resolves the actual `Repository`/`Stack` to act on using a *different* field of the same body — `repository.full_name` — with no check that it is consistent with the organization that was used to authenticate the request. [3](#0-2)  In a multi-organization deployment (`Shipit.github(organization:)` actually differentiates per-org secrets when `github_default_organization` is set), this decouples "which secret proved the sender's identity" from "which repository's stack gets mutated."

### Finding Description
`Shipit.github` supports two modes: legacy single-app (`github_default_organization` nil, argument ignored) and multi-organization, where each org key under `secrets.github` has its own `webhook_secret`, and `github_app_config(organization)` is looked up by name. [4](#0-3) 

In multi-org mode, `WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` comes straight from the JSON body being verified:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) [6](#0-5) 

This means the signature is checked against whichever organization's secret the attacker *claims* via `repository.owner.login`. If the attacker is a legitimate administrator of some organization "org-a" that is also onboarded to this same Shipit instance (and therefore knows org-a's own `webhook_secret`, which is a routine, low-privilege credential they were handed to configure their own webhook), they can sign a payload with org-a's secret while setting an unrelated `repository.full_name`.

After signature verification passes, `create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, all of which resolve the target repository purely via `payload.dig('repository', 'full_name')`: [3](#0-2)  for example `PushHandler#process` looks up stacks for `stacks.not_archived.where(branch:)` and calls `stack.sync_github(expected_head_sha: params.after)`. [7](#0-6)  `Repository.from_github_repo_name` simply splits the string on `/` and does a DB lookup — it never cross-checks it against the org that authenticated the request. [8](#0-7) 

The break in the trust binding: **the organization whose secret authenticated the webhook ≠ the repository whose stack is written to**, because the two are read from independent, both attacker-controlled fields of the same unauthenticated JSON body, and only one of them (`repository.owner.login`/`organization.login`) is bound to the signature check.

### Impact Explanation
An attacker who legitimately owns/administers one organization connected to a shared, multi-org Shipit instance can forge webhook events that are attributed to and act on a completely different organization's repositories/stacks they have no relationship to and no other Shipit credential for. Depending on the event type this enables:
- `push` → forces `GithubSyncJob`/deploy-spec re-caching for a victim stack with an attacker-controlled `expected_head_sha`. [7](#0-6) 
- `pull_request` (opened/closed/reopened/labeled/unlabeled) → archives/unarchives victim review stacks. [9](#0-8) 
- `status`/`check_suite` → injects commit statuses / triggers `RefreshCheckRunsJob` for victim commits, which can influence deployability/merge decisions.

This is a cross-repository/cross-organization write performed by an outside party with no authorization over the victim org, matching the "Critical: cross-repository writes / unauthorized deploy/rollback/merge" impact tier.

### Likelihood Explanation
This requires: (1) the Shipit instance to be configured in multi-organization mode (multiple `webhook_secret`s under distinct org keys in `secrets.github`), and (2) the attacker to legitimately control at least one of those organizations (a routine, low-privilege scenario for any org onboarded to a shared Shipit deployment — not a Shipit session, `ApiClient` token, or the shared `api_clients_secret`). Given those preconditions, exploitation only requires crafting one HTTP request; no other Shipit-side control validates the consistency between the authenticating org and the acted-upon repository.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after determining the organization used to verify the signature, enforce that every repository referenced in the payload (`repository.full_name`, and any repository fields consumed by handlers) belongs to that same, verified organization before dispatching to handlers — e.g., reject the payload if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.github`, `org-a` and `org-b`, each with its own `webhook_secret`. `org-a`'s webhook is legitimately administered by the attacker for their own low-value repo; `org-b/victim-repo` is a tracked stack unrelated to the attacker.
2. Attacker builds a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a's webhook_secret, body)` — a secret they legitimately possess for their own org.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and the signature validates successfully. [1](#0-0) 
5. `create` dispatches to `PushHandler`, which resolves the target stack via `full_name = "org-b/victim-repo"` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `org-b`'s stack — a stack the attacker has no legitimate access to. [7](#0-6)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
