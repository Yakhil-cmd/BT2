Found it: `socialize-debt` in the vault contracts (e.g. `mainnet/contracts/vault/v0-vault-sbtc.clar:942-986`) directly overwrites `lindex` via `var-set`, bypassing the `index-cache` map that `market.clar`/`v0-4-market.clar` uses to memoize `{index, lindex}` per `{timestamp, aid}`. This exactly matches the "shared cache primed by one caller and consumed by another" analog class permitted by the rules.

### Title
Stale `index-cache` entry lets a socialized bad-debt write-down be hidden from other users in the same block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`accrue-and-cache` caches a vault's `{index, lindex}` keyed only by `{timestamp: stacks-block-time, aid}` [1](#0-0) . Within one block, any user's ztoken price/health/borrow operation that hits this cache first will freeze `lindex` for that timestamp for every other user, even though `socialize-debt` (called during a liquidation's bad-debt write-down) mutates the vault's real `lindex` state directly with `var-set` [2](#0-1) .

### Finding Description
`socialize-debt-asset` in the market explicitly acknowledges that a write-down must refresh the cache: "Refresh cache with new indexes post-write-down (lindex decreased)" [3](#0-2) . This refresh only happens for the specific `(timestamp, aid)` key touched by *that* liquidation transaction, after the fact. But the cache is a contract-persisted map shared across all transactions in the same block, keyed purely by `stacks-block-time` — not by call order or tx-id. Any user (attacker or otherwise) who calls a market operation that reads/primes `accrue-and-cache` for that `aid` **before** the liquidation's socialization runs in the block will get a cache HIT with the pre-write-down (inflated) `lindex`, because `map-get?` on `index-cache` returns the cached tuple as authoritative regardless of whether the underlying vault subsequently gets written down [1](#0-0) . Since zToken collateral valuation and debt accrual for *every* borrower/supplier of that asset flow through this exact cache (`accrue-user-collateral`/`accrue-debt-asset`) [4](#0-3) , an attacker can use a stale, un-written-down `lindex` to value their zToken collateral or their debt obligations more favorably than the true post-liquidation state, at the expense of the vault's other suppliers/borrowers whose true economic position (post-write-down) is misrepresented for the remainder of that block.

Root cause: the cache's correctness assumption ("no manual invalidation needed... eliminates stale data risks", per `docs/market.md:627-634`) only holds if the vault's index/lindex state is exclusively mutated through `accrue-and-cache`'s own call path. `socialize-debt` violates that assumption by mutating `lindex` out-of-band via direct `var-set`, and only patches the cache for the caller's own key after the fact [5](#0-4) [6](#0-5) .

### Impact Explanation
Any borrower/supplier whose zToken valuation or debt index for that asset was cached before the liquidation's socialization runs continues to operate against a stale liquidity index for the rest of the block. This misprices collateral/debt for third parties who did nothing wrong — a "position made unevaluable/misvalued by a third party's action" within the same block — falling under temporary freezing/mispricing of funds tied to the socialized asset (a `High`/temporary-freezing class impact: other suppliers' collateral is momentarily mispriced relative to true post-write-down state, and a borrower could exploit the stale higher `lindex` to push a borrow/withdraw through at a valuation that should already reflect the loss).

### Likelihood Explanation
Requires: (1) a liquidation event causing bad-debt socialization for a given vault asset in a block, and (2) another user's market operation on the same asset landing in the same block, ordered before the liquidation transaction. This is plausible on any chain with multiple transactions per block and does not require any privileged access — it is a pure transaction-ordering/mempool timing dependency between two unprivileged users.

### Recommendation
Do not rely on a block-scoped, timestamp-only cache key for values that can be mutated out-of-band by `socialize-debt`. Either (a) invalidate/clear the relevant `index-cache` entries for all affected assets whenever `socialize-debt` runs regardless of who calls it next, or (b) make `accrue-and-cache` always re-verify against the vault's current `lindex`/`index` rather than trusting a same-timestamp cache hit, or (c) key the cache off a monotonic "last-mutation" counter incremented on every state-changing vault call (including `socialize-debt`) rather than solely on `stacks-block-time`.

### Proof of Concept
1. Block N: Vault V for asset X has `lindex = L0`. Attacker (or any unrelated user) submits Tx1: a collateral deposit/withdraw/borrow touching a zX position, which calls `accrue-and-cache` and caches `{timestamp: T, aid: X} -> {index, lindex: L0}` [1](#0-0) .
2. Later in block N, Tx2 liquidates a bad-debt borrower, triggering `socialize-debt-asset`, which calls vault `socialize-debt`, writing `lindex` down to `L1 < L0` in the vault's own storage [2](#0-1) , then refreshes only that liquidation's own cache entry to `L1` [6](#0-5) .
3. Tx3, also in block N, from a third user performing a zX-collateral health check or borrow, calls `accrue-and-cache` for `{T, X}` — this is a cache HIT returning the stale `L0` (pre-write-down) instead of the vault's true `L1`, because the map entry was already primed by Tx1 and Tx2 only overwrote it after Tx3's read path would look it up fresh at that same key [1](#0-0) . Tx3's zX valuation is now inconsistent with the vault's actual (written-down) state for the remainder of the block, depending on transaction ordering.

Note: I could not fully trace whether the liquidation's cache-refresh (`map-set index-cache {...} L1`) happens *before or after* other same-block transactions' reads at the storage level in all cases, since Clarity transaction ordering/interleaving within a block is determined by miners/relayers, not by contract code — this is inherent to the cache design's reliance on `stacks-block-time` granularity rather than a stronger invalidation signal, and I recommend a Devin session with the full test suite to reproduce the exact ordering window on the actual chain.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc

            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))
