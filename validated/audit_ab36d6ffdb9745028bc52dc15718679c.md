### Title
Unbounded oracle-address loop in `data_feed`/`in_data_feed` formula evaluation causes uncapped CPU/I/O consumption per AA execution - (File: formula/evaluation.js, data_feeds.js)

### Summary
The `data_feed[[...]]` and `in_data_feed[[...]]` oscript operators let an AA formula look up a data feed value across a list of "oracle" addresses. The address list is built by splitting a runtime string on `:` with no limit on the number of resulting addresses, and each address is then looked up sequentially against the key-value store. Unlike the ImageMagick `ReadOneMNGImage` bug (a loop driven by an attacker-controlled frame count with no bound, causing CPU exhaustion), this is a loop driven by an attacker-controlled address count with no bound and no proportional gas/complexity accounting.

### Finding Description
When evaluating `data_feed`/`in_data_feed`, the formula engine takes the evaluated `oracles` value and splits it on `:`: [1](#0-0) [2](#0-1) 

The only checks performed are that every resulting address is a syntactically valid address (`ValidationUtils.isValidAddress`) — there is no cap on `arrAddresses.length`. This differs from `readDataFeedValueByParams` (a separate, unrelated call path) which explicitly caps oracle count: [3](#0-2) 

The static formula validator (`formula/validation.js`) that runs before evaluation also does not bound the oracle count. It only validates the literal address format when the value happens to be a compile-time string constant, and even leaves the per-address complexity charge commented out: [4](#0-3) 

Because `oracles` is evaluated as an arbitrary expression (not necessarily a literal), it can be built from AA state vars or from `trigger.data`, i.e. attacker-supplied unit data, at evaluation time — bypassing whatever static length limits apply to literal strings in the source code.

Once the address array is built, both `dataFeeds.readDataFeedValue` and `dataFeeds.dataFeedExists` iterate over it with `async.eachSeries`, and for the AA case additionally scan the entire `storage.assocUnstableMessages` map per oracle-search cycle: [5](#0-4) [6](#0-5) [7](#0-6) 

Each iteration performs a real LevelDB `createReadStream`/`createKeyStream` query: [8](#0-7) [9](#0-8) 

Crucially, the AA "complexity"/"count_ops" gas metering — the mechanism ocore uses to bound the amount of work an AA trigger can force nodes to do (analogous to `foreach`/`map` being capped at 100 iterations via `readCount`, see `formula/validation.js:1458-1484`) — is not charged per oracle address for `data_feed`/`in_data_feed`. The `complexity += addresses.length` line that would have made cost proportional to the number of oracles is explicitly commented out (`formula/validation.js:47`). So a single `data_feed`/`in_data_feed` op, priced at fixed low complexity, can force an arbitrarily large number of sequential DB scans.

### Impact Explanation
Every full node that validates/executes the AA response to the triggering unit runs the same unbounded oracle loop, each element requiring at least one real disk-backed key/read stream operation. An attacker who can post a trigger unit to any AA whose formula forwards attacker-influenced oracle strings into `data_feed`/`in_data_feed` (a common oscript pattern for prediction-market/oracle-consumer AAs) can inflate a single trigger into hundreds or thousands of DB lookups performed synchronously by every validating node, well beyond what the fixed complexity/op-count budget was designed to allow. This is a network-wide CPU/I/O amplification: it degrades the ability of the network to timely validate/confirm new units and can be repeated cheaply by any unprivileged unit/trigger poster, matching the "node unable to confirm new units" bar for a Medium/High finding, and mirrors the CVE's "large loop and CPU consumption" root cause.

### Likelihood Explanation
Likelihood is limited by the fact that the exploitable amplification only manifests for AAs that pass attacker-controlled data straight into `oracles` of `data_feed`/`in_data_feed` — this is a common but not universal oscript pattern (oracle/prediction-market style AAs). No special privilege is needed beyond being able to author or trigger such an AA (any unprivileged unit/trigger poster); an attacker could also deploy their own AA implementing this pattern and repeatedly trigger it themselves to burden the network, so the bug is reachable without depending on a third-party AA's willingness to forward untrusted data.

### Recommendation
- Enforce an explicit maximum number of oracle addresses (e.g. the same limit of 10 already used in `readDataFeedValueByParams`) in both `formula/validation.js` (static check) and `formula/evaluation.js` (runtime check after the expression is evaluated, since the value may not be a literal).
- Re-enable and scale the `complexity`/`count_ops` charge proportionally to `addresses.length` (uncomment and fix the `complexity += addresses.length` logic in `formula/validation.js`), so runtime cost tracks the number of DB operations actually performed.
- Apply the same cap consistently to the `dataFeedExists`/`readDataFeedValue` low-level functions in `data_feeds.js` as a defense-in-depth measure, independent of the caller.

### Proof of Concept
1. Deploy (or use an existing) AA whose formula does e.g.
   `data_feed[[oracles=trigger.data.oracles, feed_name='x']]`
   or `in_data_feed[[oracles=trigger.data.oracles, feed_name='x', feed_value=1]]`.
2. Send a trigger unit to that AA with `trigger.data.oracles` set to a colon-joined string of many syntactically valid addresses (e.g. hundreds/thousands of distinct valid base32 addresses), constrained only by the unit's overall payload-size limits, not by any oracle-count-specific limit.
3. On execution, `formula/evaluation.js`'s `data_feed`/`in_data_feed` handler splits this into `arrAddresses` with no length check and calls `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists`, which sequentially issues one LevelDB stream query (and, for the AA in-flight case, a full scan of `storage.assocUnstableMessages`) per address — all charged at the same fixed complexity cost as a single-oracle lookup.
4. Repeating this trigger cheaply forces every validating node to perform the same large number of DB operations per unit, amplifying attacker cost into disproportionate node-side CPU/I/O work.

Note: I was not able to fully trace how large a `trigger.data` string field is permitted to be before other unit-size limits (`MAX_UNIT_LENGTH`, message size checks) would cap the number of embeddable oracle addresses; this affects the maximum achievable amplification factor per unit but does not change the root-cause finding that the oracle-count loop itself is unbounded and unpriced.
