### Title
Attacker-controlled submodule recursion in tracked repository causes persistent sync-timeout failures and crash-loop (`main.go`: `configureWorktree`, `SyncRepo` loop)

### Summary
The `[M-15]` report describes a fixed resource cap (`MAX_DELEGATES = 1024`) that, combined with a hard per-block gas ceiling, allows an attacker to construct state that makes a specific victim's operation permanently unexecutable. The closest reachable analog in `git-sync` is the fixed, single-shot `--sync-timeout` (`context.WithTimeout` in `main.go:1054`) applied to the entire `SyncRepo` call, including `git submodule update --init --recursive` in `configureWorktree` (`main.go:1733-1747`). Because submodule recursion depth/count and history size are entirely attacker-controlled content of the tracked repository (an attacker who can push a commit to the synced repo, e.g. via a merged PR, a compromised branch, or an upstream the operator points `--repo` at), the attacker can craft a commit whose `.gitmodules` tree requires more wall-clock time to clone/update than `--sync-timeout` allows, on every single sync attempt — never succeeding regardless of retries, mirroring the "always exceeds the resource cap" nature of the original finding.

### Finding Description
`SyncRepo` (`main.go:1858-1999`) is invoked from the main loop under a single `context.WithTimeout(context.Background(), *flSyncTimeout)` (`main.go:1054`). This context is threaded into every git subprocess call for that sync attempt, including `configureWorktree`, which runs: [1](#0-0) 
`git submodule update --init --recursive` recurses into every submodule and, transitively, every nested submodule listed in `.gitmodules` at the synced commit. The content and structure of `.gitmodules` — including submodule count, nesting depth, and target repository sizes — is fully determined by whoever can push to the tracked repository; `git-sync` performs no validation, count limit, or depth limit on submodules before executing this command, unlike the depth/filter guards it does apply to the top-level fetch (`main.go:2001-2029`, `fetch`).

If a pushed commit introduces enough submodules (or a submodule chain with large enough combined clone cost) that the resulting `git submodule update --recursive` cannot finish within `--sync-timeout`, `ctx` will be canceled mid-operation and `git.Run` will return an error for every subsequent sync attempt as long as that commit remains the target ref — the operation is deterministic and repo-content-bound, not transient. This is analogous to the report's core mechanism: a resource cap (`MAX_DELEGATES` / `--sync-timeout`) that is fine under normal conditions but can be driven past its ceiling by attacker-supplied state that a victim (the git-sync sidecar / consuming pod) cannot avoid processing, because it must fetch and check out whatever the tracked ref points to.

The failure path is handled by: [2](#0-1) 
Each failure increments `failCount`; if `--max-failures` is reached, `main.go` calls `os.Exit(1)` (`main.go:1059-1062`), which under Kubernetes causes the sidecar container to crash-loop indefinitely, since the same oversized commit will be re-fetched and re-attempted on every restart.

### Impact Explanation
This results in **persistent sync denial**: the consuming application never receives the update (or, if it's the very first sync, never receives any content at all, since `setRepoReady()` and the symlink publish only happen after a successful cycle — see `main.go:1121-1979`). If `--max-failures` is configured, the sidecar enters a permanent crash-loop, which in most Kubernetes deployments (sidecar container) drags the whole pod into `CrashLoopBackOff`, amplifying the denial-of-service from "stale content" to "pod unavailable." This matches the accepted impact category of persistent sync denial / sustained crash caused by attacker-pushed content that a victim `git-sync` deployment cannot avoid processing once it is configured to track that ref/branch.

### Likelihood Explanation
Likelihood is **Low-to-Medium** and conditioned on realistic preconditions: the attacker must be able to get a commit merged/pushed into the branch or ref that a given `git-sync` deployment tracks (e.g., via a permissive CI merge policy, a compromised contributor account, or a public repo where the victim points `--repo` at an untrusted upstream/fork that later gets updated). This is the same "reachable, unprivileged-relative-to-the-sidecar" trust model the original report relies on (an attacker delegating to a victim's NFT without the victim's consent). No credential leak, no privileged repo access to the sidecar itself, and no exploitation of standard cryptographic primitives is required — only the ability to introduce a specific tree/`.gitmodules` structure into the tracked history.

### Recommendation
- Bound submodule recursion: add an explicit cap on submodule count/depth (e.g., refuse or warn when `.gitmodules` exceeds a configurable maximum number of entries, or drop `--recursive` beyond a configurable depth) before invoking `git submodule update --init --recursive` in `configureWorktree` (`main.go:1733-1747`).
- Apply `--depth`/`--filter` semantics to submodule updates by default, not just top-level fetch, to reduce worst-case per-submodule clone cost.
- Decouple `--sync-timeout` enforcement so that a single oversized/malicious commit does not necessarily trigger `--max-failures`-driven `os.Exit(1)` (e.g., distinguish "content too large for configured timeout" from a transient network failure, and surface it as a clear, non-fatal, retryable configuration/content error rather than crash-looping the container).
- Document that `--sync-timeout` must be sized to the worst-case (not average-case) submodule tree the operator is willing to tolerate, since it currently bounds the entire recursive submodule checkout in one shot.

### Proof of Concept
1. Operator configures `git-sync --repo=<tracked-repo> --submodules=recursive --sync-timeout=60s` (default-ish timeout) against a repository the attacker can contribute to.
2. Attacker pushes a commit to the tracked branch that adds `.gitmodules` entries for a large number of independent submodules (or a chain of nested submodules), each pointing to reachable but sizable repositories, such that a full `git submodule update --init --recursive` clone from cold cache measurably exceeds 60s (verifiable ahead of time by the attacker running the same command locally against their crafted commit).
3. On the victim's next poll cycle, `SyncRepo` (`main.go:1861`) calls `fetch` (succeeds quickly, since only the top-level ref changes), then `createWorktree`, then `configureWorktree` (`main.go:1943`), which invokes the submodule update; the shared `ctx` deadline set in the main loop (`main.go:1054`) expires mid-recursion and `git.Run` returns a context-deadline error.
4. Every subsequent poll repeats the same failure because the target commit hash is unchanged and deterministic; `failCount` increments each cycle (`main.go:1057`), and once it reaches `--max-failures`, the process calls `os.Exit(1)` (`main.go:1059-1062`), causing the sidecar to crash-loop for as long as the malicious commit remains the head of the tracked ref — a persistent denial of the sync function that no retry period will resolve without operator intervention (e.g., raising `--sync-timeout`, reverting the commit, or disabling submodules).
