### Title
Cross-repository status forgery via SHA-only lookup enqueues `ContinuousDeliveryJob` for a victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no scoping to the repository/stack named in the signed webhook payload, then writes a `Status` on every matching `Commit` across the entire installation. Because git commit SHAs are shared identically between a repository and any of its forks (or can be crafted to collide when full commit content is known), an attacker who owns any repository can sign a `status` webhook for their own repo but have Shipit apply the `success` status to a commit belonging to a completely different, victim-owned stack, satisfying `Commit#schedule_continuous_delivery`'s guard and enqueuing `ContinuousDeliveryJob` for that victim stack.

### Finding Description
The broken binding: `webhook.repository.full_name == commit.stack.repository.full_name` is assumed but never enforced. `WebhooksController#verify_signature` only checks that the payload's `repository.owner.login` corresponds to a GitHub organization for which the signature is valid [1](#0-0) . It never checks that the `sha` referenced in the payload actually belongs to a commit in *that* repository.

`StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This query is global across the `commits` table — the only DB index involving `sha` is `(stack_id, sha)`, not a unique global index on `sha` alone, so multiple stacks (arbitrary repositories) can legitimately contain `Commit` rows with the identical `sha` value, most commonly because one repository is a fork of another and shares commit history. `create_status_from_github!` calls `add_status`, which fires `Status.create!` and triggers `after_commit :schedule_continuous_delivery` on `Status`, delegating into `Commit#schedule_continuous_delivery` [3](#0-2) .

`Commit#schedule_continuous_delivery` gates on `deployable? && stack.continuous_deployment? && stack.deployable?` [4](#0-3) , where `deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [5](#0-4) . The attacker fully controls `state`/`context` in their own signed payload (`StatusHandler` params schema only requires `sha`/`state`, and accepts `context`) [6](#0-5) , so they can supply `state: 'success'` with whatever `context` the victim stack requires, driving `success?` true on the victim's commit and passing the guard.

Exploit flow: attacker forks (or otherwise obtains a repository sharing a historical commit SHA with) the victim's tracked repository, owns and can sign webhooks for their fork, and POSTs `/webhooks` with `X-Github-Event: status`, a valid signature for their own org, `repository.owner.login` = attacker org, and `sha` = the shared commit SHA, `state: success`, matching `context`. `verify_signature` passes (attacker's own org signature is valid) and `drop_unhandled_event`/`ExplicitParameters` do not check repository ownership of the `sha`. `StatusHandler#process` then finds and updates the victim's `Commit` (in the victim's unrelated stack) as well as the attacker's own, and if the victim stack has `continuous_deployment: true` and is otherwise `deployable?`, `ContinuousDeliveryJob.perform_later(stack)` is enqueued for the victim's stack — a repository the attacker's webhook never named and never proved ownership of.

### Impact Explanation
This is a payload for one repository (the attacker's) mutating another repository's (the victim's) `Commit`/`Status` records and triggering `ContinuousDeliveryJob`, which under `Stack#trigger_continuous_delivery` can lead to an actual unauthorized deploy of the victim stack. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The blast radius spans any stack in the installation whose tracked repository shares commit history (forks) with an attacker-controlled repository — a common, low-cost precondition for public open-source projects mirrored/forked by Shipit.

### Likelihood Explanation
The attacker only needs: (1) to own/control a GitHub repository that shares at least one commit SHA with the victim's tracked repository (trivially achieved by forking the victim's public repo — forks retain identical SHAs for shared history), and (2) the ability to trigger or forge a signed `status` event from that repository (e.g., via their own GitHub App/CI integration on the fork, since GitHub itself will sign and deliver status events for repos the attacker owns). No Shipit credentials, sessions, or `Shipit.github_teams` membership are required. The victim stack must have `continuous_deployment: true` and be otherwise deployable — a common configuration for CD pipelines. This is repeatable per commit SHA and per victim stack.

### Recommendation
Scope the `StatusHandler` (and analogous `check_suite`/`check_run` handlers) commit lookup to the repository named in the signed webhook payload, e.g. `Commit.joins(:stack).where(sha: params.sha, stack: { repository: verified_repository })`, rather than a bare `Commit.where(sha: ...)` across all stacks.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook signed only by attacker's org cannot enqueue ContinuousDeliveryJob for a victim stack" do
  attacker_repo_owner = 'attacker-org'
  victim_stack = shipit_stacks(:shipit) # e.g. repo 'shopify/shipit-engine'
  victim_stack.update!(continuous_deployment: true)
  shared_sha = shipit_commits(:first).sha
  victim_commit = shipit_commits(:first) # belongs to victim_stack

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => victim_stack.required_statuses.first || 'ci/travis',
    'repository' => { 'owner' => { 'login' => attacker_repo_owner } }
  }

  # Signature verified only for attacker_repo_owner's org, never for victim_stack's org
  Shipit.expects(:github).with(organization: attacker_repo_owner).returns(stub(verify_webhook_signature: true))

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)
  end
  # asserts equality: stack passed to ContinuousDeliveryJob.perform_later must equal
  # the stack whose org actually signed the webhook (attacker_repo_owner-owned stack), never victim_stack
end
```
The test demonstrates the two sides of the equality — `attacker-signed org` vs. `victim_stack.repository.owner` — never match, yet without a repository-scoped fix, `StatusHandler#process`'s bare `Commit.where(sha:)` lookup causes the write (and resulting `ContinuousDeliveryJob` enqueue) to land on `victim_commit`/`victim_stack` regardless.
