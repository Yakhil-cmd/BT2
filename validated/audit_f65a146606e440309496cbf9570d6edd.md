## Analog Found

### Title
Missing cosigner-authorization check lets any paired device solicit signing on a shared/multisig address it does not control - (File: wallet.js)

### Summary
The CVE describes a Discord bot cog that let a user with limited privileges cause the bot to execute a command "as" a different, more privileged user because the code never verified that the entity issuing the command was actually authorized to act for the target identity. The closest reachable analog in ocore is in the wallet device-message handler for the `"sign"` subject: a paired device (a reachable, low-trust actor explicitly in scope per the rules) can request that a local wallet sign an arbitrary unit on behalf of *any* address the wallet recognizes as local — including shared/multisig addresses the requesting device is not actually a cosigner of — because the check that would enforce "sender is a cosigner of this address" is explicitly disabled.

### Finding Description
In `wallet.js`, `handleMessageFromHub` processes device messages from any known correspondent (`from_address = objectHash.getDeviceAddress(device_pubkey)`), and for the `"sign"` subject it calls `findAddress(body.address, body.signing_path, ...)`.

In the `ifLocal` branch, the code contains an explicitly disabled check that would have verified the sender is actually a registered cosigner of the target shared address:
```
ifLocal: function(objAddress){
    // the commented check would make multilateral signing impossible
    //db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();
        ...
        eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path);
``` [1](#0-0) 

By contrast, the sibling `ifRemote` branch (used when the target key lives on another device) *does* perform this check before forwarding:
```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request for address "+body.address+", path "+body.signing_path);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
``` [2](#0-1) 

This asymmetry means that when the target address's signing key happens to be local to the device receiving the message, *no* verification is performed that the requester (`from_address`) is actually one of the legitimate cosigners/other-cosigners of that shared address (`shared_address_signing_paths`) or wallet (`extended_pubkeys`/`wallet_signing_paths`). Any correspondent that is merely paired with the victim's device (a "paired device", one of the explicitly in-scope actors) can send a `"sign"` request naming any address the victim's wallet locally controls — a personal single-sig address, or a shared/multisig address the requester was never added to — and the wallet will accept it (`callbacks.ifOk()`) and raise a `signing_request` event asking to sign the attacker-supplied `unsigned_unit`, impersonating a legitimate cosigning counterparty for that address.

### Impact Explanation
If the application built on top of `ocore` (wallet UI, bot, or automated signer) trusts the `signing_request` event to represent a legitimate cosigner/counterparty request for the named shared address — the assumption the disabled check was originally meant to enforce — an unauthorized correspondent can impersonate a real cosigner and solicit approval of an attacker-crafted transaction against a shared address, or solicit signing of arbitrary transactions on the victim's own personal address, without ever having been added as a signer. This mirrors the CVE's core defect: the party that should be authenticated as "the legitimate co-actor" for a given identity/address is not actually verified, letting a lower-privileged, merely-paired actor act with the privilege implicitly reserved for actual cosigners.

### Likelihood Explanation
Any device that has been paired with the victim (a normal, low-friction operation) can immediately exploit this — no cosigner relationship, wallet membership, or elevated privilege is required. The vulnerable code path is reached unconditionally whenever a `"sign"` message names a locally-known address, which is the common case for the wallet's core multisig/shared-address feature.

### Recommendation
Restore (in a form compatible with legitimate multilateral signing) the cosigner-authorization check in the `ifLocal` branch: verify that `from_address` is listed as a signer/cosigner for the shared address (`shared_address_signing_paths`) or as a member device of the wallet (`extended_pubkeys`/`wallet_signing_paths`) — analogous to the check already performed in the `ifRemote` branch — before accepting the `"sign"` request and raising `signing_request`.

### Proof of Concept
1. Device X pairs with victim device V (via `pairing` subject) — no cosigning relationship is created, X is only a `correspondent_devices` entry.
2. X sends a `hub/message` to V with `subject: "sign"`, `body.address` = one of V's known local addresses (`my_addresses` or a shared address in `shared_address_signing_paths` that X is not part of), and a crafted `unsigned_unit`.
3. `handleMessageFromHub` → `case "sign"` → `findAddress` resolves the address as local → `ifLocal` is invoked; the cosigner check is commented out, so `callbacks.ifOk()` fires and `signing_request` is emitted with `from_address = X`, asking to sign the attacker-supplied unit — despite X never having been registered as a cosigner of that address.
