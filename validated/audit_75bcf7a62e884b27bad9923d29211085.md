### Title
Hookify PreToolUse/PostToolUse/Stop hook executors silently fail open (auto-allow) on any load or evaluation error instead of denying - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The `hookify` plugin's hook executors (`pretooluse.py`, and by the same pattern `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) are meant to enforce user-authored deny/block rules (`.claude/hookify.*.local.md`) before a tool such as `Bash` or `Write` runs. Structurally, this is the same class of bug as the reported `EntropyGenerator.getNextEntropy()` issue: a security-relevant decision path that can be reached in a state where the underlying data/engine has not been successfully initialized, and instead of refusing the action (revert/deny), the code returns a default "safe" value (`0` entropy / empty `{}` decision → effectively "allow").

### Finding Description
`plugins/hookify/hooks/pretooluse.py` is invoked by Claude Code as a `PreToolUse` hook before every `Bash`/`Edit`/`Write`/`MultiEdit` tool call. Its control flow is: [1](#0-0) 

If the `hookify.core.config_loader`/`rule_engine` modules fail to import (e.g. `CLAUDE_PLUGIN_ROOT` unset, path not yet on `sys.path`, partially-initialized plugin install, transient filesystem issue), the script prints an error message and calls `sys.exit(0)` — the exit code Claude Code hooks treat as "no objection" — instead of denying the tool call.

The same fail-open behavior is repeated in the main evaluation path: [2](#0-1) 

Any exception raised while loading rule files (`load_rules`) or evaluating them (`RuleEngine.evaluate_rules`) is caught by the blanket `except Exception` and converted into an *allow* (`sys.exit(0)` in the `finally` block, with only a `systemMessage` — not a `permissionDecision: "deny"` — in the JSON body). This mirrors the reported bug's root cause exactly: a security-relevant read (`entropySlots[...]` / hookify rules) that has not been reliably populated returns a benign-looking default (`0` / `{}`) rather than causing the caller to fail closed.

`config_loader.load_rules()` compounds this: any single malformed/unreadable rule file is silently skipped (`continue`) rather than aborting the whole load, so a corrupted or half-written `.claude/hookify.*.local.md` (e.g., a rule file being edited concurrently, or one with a YAML parsing bug in the hand-rolled `extract_frontmatter` parser) silently drops that specific block rule instead of surfacing an error that would cause the hook to fail closed: [3](#0-2) 

### Impact Explanation
Hookify is explicitly documented and marketed as a way for a user to block dangerous tool calls (destructive `rm -rf`, writes to `.env`, path traversal, etc. — see the plugin's own hook-development skill examples). If the rule engine cannot load or evaluate (transient import/path issue, a bug in the custom mini-YAML parser, a race with a rule file being written, or any other exception the developer didn't anticipate), the hook still returns exit code `0` with no `permissionDecision: "deny"`, so Claude Code proceeds to execute the tool call as if no hookify rule applied at all. This silently defeats a user-configured safety guardrail exactly at the moment it's needed (an error condition, often correlated with unusual/edge-case input that is itself more likely to be the dangerous command a rule was meant to catch), without any visible failure other than a stderr/systemMessage note that most users will not notice mid-session. This is a "fail-open on error" trust-boundary bug in an unprivileged, user-facing command-approval mechanism, directly analogous to the reported uninitialized-entropy-returns-zero-instead-of-reverting bug class.

### Likelihood Explanation
This path is reached whenever the hookify plugin is enabled and any of the following occur: `CLAUDE_PLUGIN_ROOT` is unset/misconfigured, the plugin package layout changes across an update, a user's rule `.md` file has a frontmatter/YAML edge case the hand-written parser mishandles, or any unforeseen exception occurs in rule loading/evaluation. Given the code explicitly wraps essentially all failure modes (`ImportError`, `IOError/OSError/PermissionError`, `ValueError/KeyError/AttributeError/TypeError`, and finally a bare `except Exception`) with "allow and log," the fail-open branch is easily reachable in normal operation (e.g., editing a rule file mid-session, a typo in frontmatter) rather than requiring an attacker-controlled race condition — comparable to or more likely than the original report's "timeframe before writeEntropyBatch completes" scenario.

### Recommendation
Change the fail-open defaults to fail-closed for security-relevant paths:
- On `ImportError` in `pretooluse.py` (and the sibling `posttooluse.py`, `stop.py`, `userpromptsubmit.py`), if the event is a blocking-capable event (`PreToolUse`), return `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "ask"}}` (or `"deny"`) instead of `sys.exit(0)` with no decision, so a broken hookify install prompts the user rather than silently no-oping.
- In the generic `except Exception` handler in `main()`, distinguish "rule failed to parse" (safe to skip that rule, warn) from "rule engine itself failed to run" (should not silently allow) — the latter should surface as `ask`/`deny`, not a bare exit 0.
- In `config_loader.load_rules()`, consider surfacing a hard failure (non-zero rule count expected but zero loaded due to errors) distinctly from "no rules configured," so the executor can decide to fail closed only when it looks like something broke versus when there are legitimately no rules.

### Proof of Concept
1. Configure a hookify `block` rule, e.g. `.claude/hookify.block-rm.local.md` with `action: block` on `Bash` commands matching `rm -rf`.
2. Break `hookify.core.rule_engine` in a way that raises during import (e.g., rename `hookify.core.rule_engine` temporarily, or introduce a syntax error, or simulate `CLAUDE_PLUGIN_ROOT` being unset for this invocation) — this reproduces the `except ImportError` path at [1](#0-0) .
3. Run a `Bash` tool call containing `rm -rf /some/path`.
4. Observe the hook prints `{"systemMessage": "Hookify import error: ..."}` and exits `0` — Claude Code proceeds to execute the destructive command with no permission prompt and no denial, even though a `block` rule targeting exactly this command exists and is enabled.

Note: I was unable to fully verify from the indexed contents alone how Claude Code's core hook-decision engine (closed-source, not present in this repo) treats a `PreToolUse` hook that exits `0` with a `systemMessage` but no `hookSpecificOutput.permissionDecision` — the analysis above assumes (consistent with the documented hook protocol in `plugins/plugin-dev/skills/hook-development/SKILL.md`) that this is treated as "no opinion" / effectively allow, which is the standard behavior in the published hook protocol referenced in this repo's own documentation. def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```
