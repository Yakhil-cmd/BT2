## Title
Missing authorization check allows any paired correspondent to silently register themselves as a co-signer of a shared (multisig) address containing the victim's own address - ([File: wallet_defined_by_addresses.js])

### Summary
The `"new_shared_address"` device-message handler in `wallet_defined_by_addresses.js` (`handleNewSharedAddress`) accepts and permanently installs a new shared-address definition sent by any known correspondent, without verifying that the local user ever initiated or approved participation in that shared address. This mirrors the CloudExplorer Lite flaw (CVE-2023-32311) where a user could add themselves to an organization/workspace because no permission check validated that the requesting party was actually authorized to make the membership change.

### Finding Description
The intended, safe workflow for creating a shared (multisig) address is:
1. `"create_new_shared_address"` → triggers a UI confirmation dialog (`eventBus.emit("create_new_shared_address", ...)`), requiring explicit user approval and choice of the user's own member address. [1](#0-0) 
2. `"approve_new_shared_address"` → collects approvals from all participating devices. [2](#0-1) 
3. Only after all approvals are gathered does the wallet build the final definition and broadcast `"new_shared_address"` to all members. [3](#0-2) 

However, the `"new_shared_address"` message is also handled directly and unconditionally as its own network message type: [4](#0-3) 

The handler `handleNewSharedAddress` performs only structural/cryptographic sanity checks — that the definition hashes to the given address, that signer addresses are syntactically valid, and that signer paths match `["address", ...]` leaves in the definition — but never verifies that a corresponding `pending_shared_addresses`/approval record exists, i.e. it never checks that *this* device or its user ever solicited, reviewed, or approved becoming part of this shared address: [5](#0-4) 

The only "membership" check performed, `determineIfIncludesMeAndRewriteDeviceAddress`, merely checks whether one of the addresses named in the attacker-supplied definition happens to already exist among the victim's own `my_addresses` or `shared_addresses` — addresses which are public information (e.g. seen in past payments): [6](#0-5) 

If that check passes, `addNewSharedAddress` is called unconditionally, silently inserting the attacker-crafted definition into the `shared_addresses`/`shared_address_signing_paths` tables, emitting `"new_address"`, watching the address (`addLightWatchedAddress` in light mode), and forwarding private-payment chains related to that address to the attacker's device as a "co-signer": [7](#0-6) [8](#0-7) 

Because `"new_shared_address"` is not in the whitelist restricted to unconfirmed correspondents, the attacker only needs to be a known/paired correspondent (which any user can achieve by exchanging a single pairing message) — no proof that the victim ever agreed to the multisig relationship is required: [9](#0-8) 

### Impact Explanation
An attacker who is (or becomes) a correspondent of the victim can craft a definition such as `["or",[["address", victim_address], ["address", attacker_address]]]` and push it via `"new_shared_address"`. Because the victim's address is already known/public, this passes `determineIfIncludesMeAndRewriteDeviceAddress`, and the victim's wallet silently records the new address as a legitimate shared/multisig address it controls, without ever showing the "create_new_shared_address" consent dialog that the protocol otherwise requires. Funds sent by the victim (or by third parties who query the wallet and see it listed as a wallet-controlled shared address) to this bogus "joint" address can then be spent unilaterally by the attacker through the independent `["address", attacker_address]` branch — resulting in unauthorized spending/loss of funds the victim believed were protected by a genuine multi-party arrangement. Additionally, because the address is registered as a shared address, subsequent private-payment chains involving it are automatically forwarded to the attacker's device, leaking private payment data to an unauthorized "cosigner".

### Likelihood Explanation
Likelihood is high: the only prerequisite is that the attacker be a paired correspondent of the victim (trivially achievable via any pairing interaction, e.g. as a merchant, support bot, or an already-added contact), and that they know one public address the victim controls (visible from any past on-chain transaction). No cryptographic secret of the victim is required, and the handler performs no check that the victim ever initiated or consented to this particular shared address.

### Recommendation
`handleNewSharedAddress` should reject unsolicited shared-address definitions: require that a matching `pending_shared_addresses`/approved-signing-path record exists for the definition (i.e., the address was actually proposed via `create_new_shared_address` and approved by the local user) before calling `addNewSharedAddress`, or otherwise require explicit user confirmation before persisting a new shared address that references one of the user's own addresses. At minimum, the local device address bound to "my" address in the incoming definition must have been the one that solicited or approved this address, not merely inferred to match.

### Proof of Concept
1. Attacker pairs with victim's wallet device (standard pairing flow) so that `correspondent_devices` contains the attacker's device.
2. Attacker learns victim's on-chain address `V` (public, from any observed transaction).
3. Attacker builds `arrDefinition = ["or", [["address", "V"], ["address", "A"]]]` (where `A` is attacker's own address) and computes `shared_address = chash160(arrDefinition)`.
4. Attacker sends a device message:
```
{
  subject: "new_shared_address",
  body: {
    address: shared_address,
    definition: arrDefinition,
    signers: {
      "r.0": { address: "V" },
      "r.1": { address: "A", device_address: <attacker_device_address> }
    }
  }
}
```
5. Victim's `handleMessageFromHub` routes this to `walletDefinedByAddresses.handleNewSharedAddress`, which passes all structural checks, finds `V` in the victim's `my_addresses`, and calls `addNewSharedAddress` — silently persisting the shared address and treating the attacker as a legitimate cosigner, with no dialog ever shown to the victim.
6. Any funds later paid to `shared_address` (e.g. by the victim treating it as a secure joint address, or by a third party who queries the victim's wallet listing) can be spent unilaterally by the attacker via the `["address","A"]` branch.

				function(rows){

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
