### Title
Unhandled exception in `readDataFeedValue` candidate-sorting during AA `data_feed()` evaluation crashes trigger handling instead of failing gracefully - ([File: data_feeds.js])

### Summary
`formula/evaluation.js`'s `data_feed` and `in_data_feed` operators call `dataFeeds.readDataFeedValue()` while evaluating an AA formula triggered by any user-posted unit ` [1](#0-0) `. When the `bAA` flag is true, `readDataFeedValue` scans `storage.assocUnstableMessages` for candidate data-feed values from other pending/unstable AA units, and if more than one ambiguous candidate remains after filtering (equal `latest_included_mc_index` and `level`, `bIncludeAllUnstable` false), it hits `arrCandidates.sort(...)` whose comparator does `throw Error("can't sort candidates ...")` instead of returning an error via callback ` [2](#0-1) `.

### Finding Description
This is the same bug class as the Sherlock M-10 finding: a value-lookup helper invoked inside a loop/aggregation path throws synchronously under a specific, reachable data condition, and the caller has no way to catch it gracefully because the throw happens outside any `try/catch`-guarded control flow — it directly propagates up as an uncaught JS exception.

Concretely:
- `readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ifseveral, ...)` is called from the AA formula evaluator for the `data_feed[...]` construct with `unstable_opts = bAA` (true when evaluating inside an AA trigger response) ` [3](#0-2) `.
- Inside `readDataFeedValue`, when `bIncludeUnstableAAs` is true, it builds `arrCandidates` from every currently-unstable unit's `data_feed` messages whose author intersects the requested oracle address list and whose value matches ` [4](#0-3) `.
- If more than one candidate remains and `ifseveral !== 'abort'`, the code tries to `.sort()` them by `latest_included_mc_index` then `level`; if `bIncludeAllUnstable` is false (i.e., a specific AA data-feed lookup, not "all_unstable") and two candidates still tie on both fields, the sort comparator throws `Error("can't sort candidates ...")` synchronously ` [2](#0-1) `.
- This throw happens inside a plain (non-async) function called synchronously from the AA evaluator's `data_feed` case, which itself is invoked from `aa_composer.handleTrigger`'s deeply nested callback chain (`evaluateAA` → `formulaParser.evaluate` → operator dispatch) ` [5](#0-4) `. Unlike other error paths in the evaluator that call `setFatalError(...)`/`cb(err)` to gracefully bounce the trigger ` [6](#0-5) `, this specific throw bypasses that mechanism entirely.

An attacker who controls an AA (or arranges two independent AAs/oracle authors) can trigger this condition deterministically: post two units in the same processing window (both still unstable, thus present in `storage.assocUnstableMessages`) from different author addresses that are both included in the `oracles` list of a `data_feed[...]` call, each posting the same feed value at the same `latest_included_mc_index` and `level`. Any AA whose code performs such a `data_feed[[oracles="A:B", ...]]` lookup (without `ifseveral: "abort"`, which would otherwise return an error cleanly) while both candidate units are unstable will trigger the throw during trigger handling.

### Impact Explanation
Because the throw is not routed through `setFatalError`/callback-based error handling used everywhere else in the formula evaluator, it manifests as an uncaught exception during AA trigger processing (`handleTrigger`/`writer.js` unit-processing pipeline) rather than a clean bounce of the AA response. Depending on how far up the call stack this propagates, this can crash the node process handling unit validation/AA execution (a denial-of-service of AA processing for that node), or at minimum cause nodes to disagree on whether the triggering unit is validly processed — since some nodes might hit the ambiguous-candidate window and crash/fail while others (processing slightly later, after one of the units stabilizes) succeed. This matches the "node unable to confirm new units" / "node disagreement on validity" impact classes: a single posted pair of units can make AA-trigger processing for a reachable `data_feed()` formula fail catastrophically instead of bouncing gracefully.

### Likelihood Explanation
The condition requires: (a) an AA (or oracle-consuming contract) that calls `data_feed[[oracles="ADDR1:ADDR2", ...]]` (or the `in_data_feed` variant) referencing multiple oracle addresses without `ifseveral: "abort"`, and (b) two unstable data-feed-posting units from those addresses landing at the identical `latest_included_mc_index` and `level` with matching feed values. This is a narrow but fully attacker-controllable timing condition — an attacker who controls (or colludes with) the oracle addresses referenced by a target AA can deliberately post two units meeting these exact tie conditions before either stabilizes, deterministically reaching the throw. Likelihood is Medium: it requires a specific AA using multi-oracle `data_feed` lookups, but once such an AA exists, the trigger is fully reproducible.

### Recommendation
Do not `throw` inside the `arrCandidates.sort()` comparator in `readDataFeedValue` (or `dataFeedExists`'s analogous unstable-candidate scan). Instead, detect the ambiguous-tie condition before/after sorting and route it through the normal `objResult.bAbortedBecauseOfSeveral = true` / `handleResult(objResult)` path (the same path already used for the `ifseveral === 'abort'` case), so ambiguous candidates cause the formula evaluator to receive a normal "several values found" error via `setFatalError`, which cleanly bounces the AA response instead of crashing.

### Proof of Concept
1. Deploy an AA whose formula includes `data_feed[[oracles="ORACLE_A:ORACLE_B", feed_name="price"]]` (no `ifseveral` param, defaults to `"last"`).
2. Have `ORACLE_A` and `ORACLE_B` each post a `data_feed` message with the same `feed_name`/value in two separate units that:
   - are both still unstable at the time of AA trigger evaluation (present in `storage.assocUnstableMessages`),
   - share the same `latest_included_mc_index` and the same DAG `level`.
3. Send a trigger unit to the AA that causes it to evaluate the above `data_feed[...]` expression while both oracle units remain unstable.
4. `readDataFeeds.readDataFeedValue` is invoked with `unstable_opts = bAA = true`; `arrCandidates` ends up with 2 entries tied on `latest_included_mc_index` and `level`; `bIncludeAllUnstable` is false (since `unstable_opts` is `true`, not the string `'all_unstable'`); the `.sort()` comparator executes `throw Error("can't sort candidates ...")`, propagating as an uncaught exception out of the AA-trigger-processing call chain instead of gracefully bouncing the trigger unit.
