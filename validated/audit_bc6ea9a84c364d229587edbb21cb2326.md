### Title
Webhook organization/repository confusion allows unauthenticated forged GitHub events against arbitrary tracked stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* `GitHubApp` (and thus which HMAC secret) to verify a webhook against using an **untrusted field taken from the same unauthenticated JSON body** it is trying to validate, while the event handlers act on a **different** field of that same body to decide which `Repository`/`Stack` to mutate. When any configured GitHub organization has no `webhook_secret` set (an explicitly documented, supported configuration), signature verification is skipped entirely for that organization, letting an attacker "authenticate" as that unsecured org while directing the payload's actual effects at a completely different, secured organization's repository.

### Finding Description
`verify_signature` resolves the verifying app from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params.dig('repository','owner','login')` or `params.dig('organization','login')` — both attacker-supplied at this point, before any signature has been checked. That value selects `Shipit.github(organization: repository_owner)`, whose secret then verifies the HMAC: [3](#0-2) 

Critically, `verify_webhook_signature` **short-circuits to `true` when `webhook_secret` is blank** (`return true unless webhook_secret`). Blank/`nil` webhook secrets are an explicitly documented and shipped configuration option, not a misuse of the engine: [4](#0-3) [5](#0-4) 

Meanwhile, once past this check, the event handlers do **not** use `repository_owner` at all — they resolve the target repository from a separate field, `repository.full_name`: [6](#0-5) 

and `PushHandler`/`StatusHandler` act on whatever stacks/commits match that `full_name`: [7](#0-6) [8](#0-7) 

This breaks the trust binding `organization-that-authenticated == organization/repository-that-is-acted-upon`. In a multi-org Shipit instance (the engine natively supports per-organization GitHub App configs, as shown in `secrets_double_github_app.yml`), if org `Unsecured` has no `webhook_secret` while org `Secured` does, an attacker can:
1. Set `repository.owner.login` (or `organization.login`) = `"Unsecured"` so `verify_signature` selects the app with the blank secret and unconditionally passes.
2. Set `repository.full_name` = `"Secured/actually-tracked-repo"` so the handler resolves and mutates the real, secured stack.

No knowledge of `Secured`'s webhook secret, no session, no API token, and no repository access is required — only knowledge that some organization in the deployment lacks a webhook secret, which is itself a documented default (`webhook_secret: # nil`).

### Impact Explanation
This crosses an authentication boundary the engine relies on: the per-organization webhook secret is meant to prove the request originated from GitHub for *that* organization's repositories, but the code lets the unauthenticated payload pick which secret gets checked and then acts on unrelated payload data. Concretely exploitable handlers:
- `StatusHandler` lets the attacker inject arbitrary commit statuses (`state`, `description`, `target_url`, `context`) for **any SHA on any tracked stack**, which Shipit uses as part of deploy-readiness/CI-gating signals — this can be used to force a target commit to appear "green" and push it toward an unauthorized deploy.
- `PushHandler` can force `GithubSyncJob` to run against arbitrary tracked stacks the attacker has no access to.

This matches the "unauthorized deploy" / cross-organization-write class of impact called out in the rules.

### Likelihood Explanation
Requires only: (a) a multi-organization Shipit deployment (an explicitly supported configuration), and (b) at least one configured organization without a `webhook_secret` (also explicitly documented/shipped as a valid value). No credentials, tokens, or privileged accounts are needed — any internet client can POST to `/webhooks` (or the mounted equivalent) with a crafted JSON body and mismatched `owner.login` vs `full_name`.

### Recommendation
- Do not let the request itself choose which secret verifies the request. Compute the target `Repository`/`Stack` first using the same field used to select the signing organization (or vice-versa), and reject the request if `repository.full_name`'s owner does not match the organization whose key was used for verification.
- Do not treat a blank `webhook_secret` as "verification passes." At minimum, require that if any organization is configured without a secret, requests for that organization cannot be used to reach handlers that resolve to a *different* organization's repositories; ideally, fail closed (reject) rather than fail open when no secret is configured, or require operators to explicitly opt into unsigned webhooks per-organization with an isolating mechanism (e.g. only match repos under that same org).

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "Secured/actually-tracked-repo",
    "owner": { "login": "Unsecured" }
  }
}
```
If `Shipit.github(organization: "Unsecured")` has no `webhook_secret` configured, `verify_webhook_signature` returns `true` for any signature value, and `PushHandler` proceeds to enqueue `GithubSyncJob` for stacks under `Secured/actually-tracked-repo`, despite the request never being validated against `Secured`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
