### Title
Webhook signature verified against a self-reported organization while all handlers act on a separately-reported repository full name, permitting cross-organization event injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret used to validate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body itself, then verifies the raw body's HMAC against that org's configured `webhook_secret`. Every webhook handler that actually mutates state, however, resolves the target `Repository`/`Stack` using a *different* field of the same body — `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Because the field used to pick "who authenticated" (`repository.owner.login`) and the field used to pick "what gets written" (`repository.full_name`) are never cross-checked against each other, anyone who legitimately knows the webhook secret for *one* configured GitHub organization can craft a payload that authenticates as that organization while acting on another organization's repository/stack.

### Finding Description
`Shipit` supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` (`docs/setup.md:182-209`, `lib/shipit.rb:170-200`). The webhook signature check is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

This value is used only to pick *which* app config/secret to validate the HMAC against (`Shipit.github(organization: repository_owner)`). Once the signature check passes, the entire raw body — including a completely different field, `repository.full_name` — is handed unmodified to the handlers: [3](#0-2) 

Every handler resolves the actual `Repository`/`Stack` to mutate via `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

There is no assertion anywhere that `repository.owner.login` (the field that picked the verifying secret) equals the owner encoded in `repository.full_name` (the field that picks the repository actually written to). Because the entire raw body is HMAC-signed with a single secret, this is exploitable specifically in the documented multi-organization deployment mode: the operator of one onboarded GitHub organization (`OrgA`) legitimately possesses `OrgA`'s `webhook_secret` (they created the GitHub App and configured that secret themselves, per `docs/setup.md`). That admin can POST directly to `/webhooks` (not via GitHub) with:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` resolves `OrgA`'s app and its known secret,
- `repository.full_name = "OrgB/victim-repo"` and event-specific fields, matching the target victim stack tracked in the same Shipit instance,
- a valid `X-Hub-Signature` computed with `OrgA`'s own secret over the full crafted body.

The signature check passes (it only proves the body was signed with `OrgA`'s secret — it says nothing about which repository the body claims to describe), and the handler dispatch proceeds to act on `OrgB`'s repository/stack using attacker-controlled payload content.

### Impact Explanation
Depending on the injected event type this breaks the "organization that authenticated vs. repository that is written" binding and enables cross-repository/cross-organization state changes without any authorization over the victim organization:
- `push` → `PushHandler` calls `stack.sync_github(expected_head_sha: ...)` on the victim stack, injecting an attacker-chosen SHA as the "head" to sync toward.
- `status` → forged commit statuses on victim commits (subject to further checks in `StatusHandler`, not fully enumerated here, but the routing/target-selection flaw exists independent of that handler's own logic).
- `pull_request` events → can archive/unarchive victim review stacks, mutate victim `PullRequest` records, or trigger review-stack provisioning tied to attacker-controlled data (`app/models/shipit/webhooks/handlers/pull_request/*.rb`).

This is a cross-repository write achieved purely by exploiting the mismatch between the authentication-selection field and the target-selection field of the same payload; it does not require compromising the victim organization's own webhook secret. This satisfies the "cross-repository writes" / "unauthorized deploy-adjacent action" impact bar for a High/Critical-class finding in the analog rules.

### Likelihood Explanation
Exploitability requires the Shipit deployment to be configured for **multiple GitHub organizations** sharing one instance (an explicitly documented and supported configuration, `docs/setup.md:182-209`), and requires the attacker to be a legitimate admin/owner of at least one onboarded organization's GitHub App (i.e., someone who knows that organization's own `webhook_secret`). This is a realistic trust boundary in shared/multi-tenant Shipit deployments: onboarding a new low-trust organization's app grants that organization's admin the ability to forge events against every other organization hosted on the same instance, which is not something the "member of `Shipit.github_teams`" or "repository write access" gates prevent, since the webhook endpoint is unauthenticated aside from HMAC.

### Recommendation
When resolving which GitHub App/secret to use in `WebhooksController#verify_signature`, and when handlers resolve the target `Repository` via `repository.full_name`, cross-check that the owner encoded in `repository.full_name` (or `organization.login`) matches the `repository_owner`/organization whose secret validated the signature. Reject events where the two disagree (e.g., `head(422)` if `full_name.split('/').first.casecmp(repository_owner) != 0`).

### Proof of Concept
1. Deploy Shipit with two organizations configured per `docs/setup.md`'s "Using Multiple Github Applications" section: `OrgA` (secret known to the PoC author, e.g. because they administer `OrgA`'s GitHub App) and `OrgB` (hosting a real tracked stack, e.g. `OrgB/victim-repo`).
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and the signature above.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully (correct secret for `OrgA`). `Shipit::Webhooks.for_event('push')` dispatches `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — a write triggered entirely by an `OrgA`-authenticated request against an unrelated organization's tracked repository.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
