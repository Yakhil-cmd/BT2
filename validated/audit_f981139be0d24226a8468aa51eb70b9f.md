## Title
AAs Can Receive Fixed-Denomination (Indivisible) Assets But Can Never Send Them Back, Permanently Locking Funds - (File: ocore/aa_composer.js)

### Summary
This is the closest analog to the ERC-721 lock-up bug class in the reported issue. In the Linea report, the token bridge accepts an asset type (ERC-721) on the deposit path but the withdrawal path silently uses an ERC-20-only primitive (`transfer`) that reverts for that type, permanently trapping the token. In ocore, an Autonomous Agent (AA) can receive any asset — including a `fixed_denominations` (indivisible/NFT-like) asset — as trigger output, and that balance is happily credited to the AA's `aa_balances`/state, but the AA's only outbound path (`payment` messages produced from its formulas) silently drops any message that references a `fixed_denominations` asset, so the AA can never send it back out.

### Finding Description
When a trigger unit sends a `fixed_denominations` asset to an AA, `updateInitialAABalances` credits it into the AA's balance without restriction on asset type [1](#0-0) . The AA's formula/getter machinery even lets scripts read `asset[...]` fields and trigger amounts for any asset type, with no distinction that would prevent an AA developer from believing that asset can also be paid back out.

However, when `sendUnit` builds the response messages, any `payment` message whose asset is `fixed_denominations` is explicitly skipped during the completion pass (`if (objAsset.fixed_denominations) // will skip it later return cb();`) [2](#0-1)  and then unconditionally filtered out of the message list before it's ever included in the outgoing unit:

```
messages = messages.filter(function (message) { return (message.app !== 'payment' || !message.payload.asset || !assetInfos[message.payload.asset].fixed_denominations); });
``` [3](#0-2) 

If this filtering empties the message list, the AA simply produces an empty response and "eats" the coins with no error surfaced to the trigger author: [4](#0-3) 

There is no corresponding validation-time check in `aa_validation.js` that rejects an AA definition attempting to pay out a `fixed_denominations` asset — the `payment` message payload validation only checks that `asset` is a valid string/hash or formula, without regard to asset type [5](#0-4) . So an AA author can unknowingly (or a triggering user relying on an AA that expects to be able to relay assets) write/trigger an AA that accepts an NFT-like asset, updates internal balances/state as if it can be forwarded, and then discovers the payout silently vanishes from the response — exactly analogous to the bridge accepting an ERC-721 on deposit and reverting/being unable to send it back on withdrawal, except here it is silently dropped rather than reverted, which is worse: the unit still gets saved/accepted (assuming other messages remain), and the received `fixed_denominations` coins remain stuck in the AA's balance forever with no code path able to relay them out via a `payment` message.

### Impact Explanation
Any coins of a `fixed_denominations` asset sent into an AA as part of a trigger (or as change/relayed balance) become permanently unspendable by that AA. Since AAs cannot cosign or otherwise release funds except via `payment` messages emitted from their own formula evaluation, this constitutes a permanent freezing of AA-held funds — matching the "AA fund loss or freezing" bug class explicitly called out as acceptable impact. Any DeFi/exchange/vault AA design that naively supports indivisible/NFT-like assets (or is triggered by mistake with one) will silently and irrecoverably lock user funds inside the AA, with no error, no bounce, and no recovery path in-protocol.

### Likelihood Explanation
Likelihood is moderate: this requires an AA to be designed or triggered with a `fixed_denominations` asset, which is a less common asset type in practice, but nothing in AA validation prevents this, and an attacker or a naive AA author could easily trigger it: any user can define a `fixed_denominations` asset and simply send it to an existing AA's address (attacker fully controls trigger construction), or design an AA that is supposed to forward received assets without special-casing indivisible ones. No privileged access is required — a single trigger sender or asset issuer can create and exploit this at will.

### Recommendation
- In `aa_validation.js`, reject AA definitions whose `payment` messages could reference a `fixed_denominations` asset, or require an explicit runtime check/bounce with a clear error instead of silent message dropping.
- In `aa_composer.js`'s `sendUnit`, instead of silently filtering out `payment` messages for `fixed_denominations` assets (lines 1323-1361), bounce the trigger with an explicit error such as "AAs cannot send fixed-denominations assets" so triggering users are not misled into believing their assets were processed, and so AA authors discover the limitation during development/testing rather than in production.
- Consider tracking whether the trigger sent any `fixed_denominations` asset to the AA and bounce/reject such triggers upfront (mirroring the report's suggestion to reject the offending asset type before funds are even accepted), rather than allowing them to be silently absorbed into `aa_balances`.

### Proof of Concept
1. Define a `fixed_denominations` (indivisible) asset `X` with `denominations` set, e.g. `{app:"asset", payload:{fixed_denominations:true, denominations:[{denomination:1000}], is_private:false, ...}}` — validated via `validateAssetDefinition` in `validation.js` [6](#0-5) .
2. Deploy an AA whose logic, upon receiving any asset, attempts to forward the exact amount received back to the trigger address via a `payment` message referencing `trigger.output[[asset=X]]`'s asset (matching the pattern validated in `aa_validation.js` case `'payment'`) [5](#0-4) .
3. Send a trigger unit paying asset `X` (indivisible coin of denomination 1000) to the AA address. `updateInitialAABalances` credits the AA's balance for asset `X` with no restriction [1](#0-0) .
4. When the AA's formula produces a `payment` message for asset `X`, `sendUnit` marks it to "skip it later" [2](#0-1)  and then filters it out entirely before constructing the response unit [3](#0-2) .
5. If no other messages remain, the AA emits an empty/successful response with no error to the trigger author (`handleSuccessfulEmptyResponseUnit`) [4](#0-3) , while asset `X`'s balance remains permanently held in the AA's `aa_balances`, unreachable by any future `payment` message for that asset.

**Uncertainty note:** I was not able to fully trace whether any alternate mechanism (e.g., a special getter/state-var path, or an explicit design decision documented elsewhere such as AA developer docs) exists to intentionally forbid AAs from ever accepting `fixed_denominations` assets in the first place (which would reduce this to a documented limitation rather than a silent fund-lock bug). The index does not show any trigger-time rejection of `fixed_denominations` assets sent to an AA, only the silent drop on the outbound side. If such upfront rejection exists elsewhere in the codebase not surfaced by search, this would reduce, but not eliminate, the risk, since AAs could still accumulate such assets via internal relaying scenarios.
