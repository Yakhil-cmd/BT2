### Title
Cross-stack `Status` forgery via unscoped `sha` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, with no scoping to the repository/organization that authenticated the webhook. Any commit in the entire Shipit instance sharing that SHA — regardless of stack or owning organization — receives the forged status, which can flip `Commit#deployable?` to true and trigger `Stack`-level continuous delivery scheduling for a stack the requester never verified ownership of.

### Finding Description
The binding that should hold: `webhook.authenticated_organization == commit.stack.repository.owner` for every `Commit` mutated by the handler. That binding is never checked.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the *payload's* `repository.owner.login` (or `organization.login`) — i.e., it proves the payload was signed with the secret configured for that org's own GitHub App installation. It does not tie the verification to any specific repository or stack beyond that org lookup.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, unscoped-by-repository query. `params.repository` (full_name/owner) from the payload is never consulted here.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) persists the status using the **found commit's own `stack_id`**, not any ID derived from the requesting webhook's repository.
- `Status` has `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`), which calls `commit.schedule_continuous_delivery`, enqueuing `ContinuousDeliveryJob` for `commit.stack` — the victim stack.
- `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) becomes true once a `success` status lands on a previously-`pending` commit, satisfying `success? && !blocked?` (assuming no lock and no blocking statuses upstream).

Root cause: signature verification authenticates "this payload came from a legitimate GitHub App installation for org X," but the handler's data-access layer (`Commit.where(sha:)`) has no per-request scoping to org/repository X. It implicitly trusts that a SHA collision across stacks cannot happen, but SHAs are content hashes of arbitrary attacker-controlled trees/commit metadata (author, committer, timestamps, message, parent), and are trivially reproducible: forking a public victim repository preserves identical commit SHAs for shared history, and an attacker can also fabricate a commit object with an identical SHA to a known victim commit if they can control all the hashed fields (tree, parents, author/committer identities and timestamps, message) — all of which are public/guessable for an open-source victim commit.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) only ensure the payload is well-formed and signed by *some* legitimate org's app; none of them re-validate that the `sha` being processed belongs to a commit whose `stack.repository` matches the requesting payload's `repository`.

### Impact Explanation
An attacker who controls (or can post GitHub Apps-authenticated statuses to) any repository connected to a Shipit-configured GitHub organization — even a low-privilege, unrelated tenant in a multi-org Shipit deployment, or simply a public fork of the victim's repo — can write a `Status` record for a **different** stack's commit, without that stack's organization ever authorizing the request. If the victim stack has `continuous_deployment` enabled and the affected commit was `pending`, this write causes `ContinuousDeliveryJob` to be enqueued for the victim stack, resulting in an unauthorized deploy execution on the victim's deploy host. This is a cross-tenant, repeatable, record-for-repository-that-did-not-authenticate-it issue and matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: (1) a Shipit instance configured with multiple GitHub organizations/apps (documented and supported per `docs/setup.md` "Using Multiple Github Applications"), or a scenario where the victim repo has been forked (sharing SHAs) into another org tracked by the same Shipit instance; (2) attacker has legitimate, low-privilege push/API access to at least one repo/org wired into the same Shipit instance so a genuinely-signed `status` webhook fires; (3) attacker can produce or reference a commit SHA identical to one in the victim's stack (feasible via forking public history, or by controlling all hashed commit fields); (4) victim stack has `continuous_deployment` enabled and the target commit is `pending`. This requires a specific multi-tenant/shared-history configuration, which is plausible but not universal — it is a real, exploitable engine-code flaw, but likelihood is bounded by needing a genuine SHA match and a legitimately signed webhook from *some* org onboarded to the same Shipit deployment.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and any similar handler) to the repository that authenticated the webhook, not merely the SHA. E.g., resolve `Repository.from_github_repo_name(params.repository.full_name)`, restrict to `repository.stacks`, and only update `Commit` records under those stacks (or verify `commit.stack.repository.github_repo_name == params.repository.full_name` before calling `create_status_from_github!`).

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "status webhook from an unrelated repository forges a status/deploy on a foreign stack" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, repo "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, state: "pending", ...)

  attacker_payload = Shipit::Webhooks::Handlers::StatusHandler.new(
    OpenStruct.new(sha: victim_commit.sha, state: "success", description: nil,
                   target_url: nil, context: "ci/forged", created_at: Time.now.to_s,
                   repository: { full_name: "attacker/unrelated-repo" })
  )

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack: victim_stack]) do
    attacker_payload.call(attacker_payload.params) # simulate authenticated webhook from attacker's own org
  end

  assert victim_commit.reload.deployable?
end
```
This demonstrates the binding `requesting_repository == commit.stack.repository` is never enforced: the equality `"attacker/unrelated-repo" == victim_commit.stack.repository.full_name` is false both before and after, yet the write and job enqueue still occur against `victim_stack`.
