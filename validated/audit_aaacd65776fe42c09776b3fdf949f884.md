### Title
Cross-repository commit-status forgery due to missing repository scoping in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a signature against based on the *organization* derived from the payload (`repository.owner.login` / `organization.login`), then dispatches the fully-parsed JSON payload to the registered handler for the event type. `StatusHandler`, unlike its sibling handlers (`PushHandler`, `CheckSuiteHandler`), never checks which repository the event belongs to before writing the status onto a `Commit` — it looks the commit up globally by SHA alone. This breaks the trust binding between "the repository whose webhook was authenticated" and "the repository/stack whose commit status is actually written."

### Finding Description
Signature verification only proves the payload was signed with the secret of *some* organization identified by `repository_owner`: [1](#0-0) 

The controller then hands the raw, still-unscoped payload to whichever handler is registered for the event: [2](#0-1) 

All other webhook handlers that touch data belonging to a `Stack`/`Repository` explicitly scope their queries through the base `Handler#stacks` helper, which filters by `repository.dig('repository','full_name')`: [3](#0-2) 

For example, `PushHandler` and `CheckSuiteHandler` both scope through `stacks`: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores the `repository` field entirely and resolves the target `Commit` purely by SHA, across every `Stack`/repository tracked by the whole Shipit instance: [6](#0-5) 

`Commit#create_status_from_github!` then creates a `Status` record tied to that commit's `stack_id`, and status changes can trigger `deployable_status` hook emission and influence whether a commit is considered CI-passing/deployable: [7](#0-6) 

**The broken binding, stated as an equality that fails:**
`organization authenticated by verify_signature (repository_owner)` ≠ `repository/stack whose Commit status is written by StatusHandler (no repository check at all)`.

Because `Commit` rows are content-addressed by `sha` and a git SHA does not encode which repository it came from, any two repositories that share commit history (a fork of a tracked repository, a repository created from the same history, or any repository whose commits happen to coincide with a tracked repo's SHA) can be used to inject arbitrary status payloads (`state`, `context`, `description`, `target_url`, `created_at`) onto a commit belonging to a *different*, unrelated stack — as long as the attacker can get GitHub to deliver ANY validly-signed `status` webhook event under an organization that Shipit already trusts (e.g., by being a collaborator/CI integration on one repository under that GitHub App installation, or on a fork).

### Impact Explanation
This directly enables cross-repository writes: an attacker with the ability to trigger a legitimately-signed `status` event for one repository can plant/forge commit statuses on a completely different stack's commit purely by matching SHA. Commit statuses are used by Shipit to gate whether a commit is CI-passing/deployable and are broadcast via the `deployable_status`/`commit_status` hooks that downstream automation (merge queues, auto-deploy, external CI dashboards) may rely on. Forging a `success` status for a commit that never actually passed CI in the tracked repository can lead to an unauthorized deploy decision being made on stale/false CI information — matching the Critical-tier "cross-repository writes / unauthorized deploy" impact class.

### Likelihood Explanation
Exploitation requires the attacker to be able to cause GitHub to deliver a validly-signed `status` webhook event for the organization Shipit trusts (e.g., they have push/CI access on one repository under that installation, or the two repositories are forks sharing commit SHAs). This is a realistic scenario in organizations that self-host public/open-source projects with Shipit, or run many stacks/repos under one GitHub App installation. No Shipit credentials, API tokens, or session access are required — only the ability to trigger an authentic webhook for any repo under the trusted org, which is a much weaker requirement than the write access needed to reach the target stack directly.

### Recommendation
Update `StatusHandler#process` to scope the `Commit` lookup by the webhook's own `repository.full_name`, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more directly, join `Commit` through `stack: { repository: ... }` matching `payload.dig('repository', 'full_name')` before applying the status, so a status event can never affect a commit outside the repository that was actually the subject of the signed webhook.

### Proof of Concept
1. Shipit is configured with a single GitHub App installed on organization `acme-org`, tracking two independent repositories as stacks: `acme-org/public-app` (public, forkable) and `acme-org/internal-app` (privileged, deploy-gated by CI status).
2. An external contributor forks `acme-org/public-app` to their own account and, without modifying it, has their fork's CI system (or manually via the GitHub Statuses API against their own fork, which GitHub still delivers as an org-scoped `status` webhook if the App is installed with access) post a `status` webhook whose `sha` happens to equal a commit SHA that also exists (unmodified) in `acme-org/internal-app`'s history (a shared common ancestor commit or unmodified file/commit is a plausible/reachable scenario for forks or mono-repo splits).
3. `WebhooksController#verify_signature` validates the signature against `acme-org`'s webhook secret — this succeeds because the event is a genuine webhook from GitHub for that org's App installation.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the commit row belonging to the `internal-app` stack (since `Commit` lookup is global, unscoped by repository), and calls `commit.create_status_from_github!(params)` — writing an attacker-chosen `state` (e.g., `"success"`), `context`, and `description` onto `internal-app`'s commit, even though no CI ever ran against `internal-app`.
5. This forged status can flip the commit's CI/deployable state for `internal-app`, potentially unblocking or misleading an unauthorized deploy decision — with the attacker never having had write access to `internal-app` at all.
