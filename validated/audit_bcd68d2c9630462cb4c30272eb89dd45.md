### Title
Unfiltered PR label names become process environment variables reaching `PTY.spawn`, enabling `GIT_EXEC_PATH` injection - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the process environment with no allowlist, and that merged hash flows unfiltered through `TaskCommands#env` / `Command#unbundled_env` into `PTY.spawn`. An unprivileged fork PR author who can attach a label such as `git_exec_path` to their own PR can therefore inject `GIT_EXEC_PATH` (or any other env var name) into the environment of every command Shipit runs against that review stack, including the `fetch` step's `git` invocations.

### Finding Description
The broken binding is: *the set of environment variable keys passed to `Command#start` should equal only keys explicitly whitelisted by `deploy_spec` (`deploy_variables`/`rollback_variables`) or hard-coded Shipit constants — it does not*.

- `ReviewStack#env` takes `super` (the base stack env) and merges in `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" } }` with **no key filtering at all**: [1](#0-0) 
- Labels are captured straight from the webhook body by `LabelCapturingHandler#capture_labels`, which only validates that `name` is a `String` — no character or key restriction: [2](#0-1) [3](#0-2) 
- `TaskCommands#env` merges `@stack.env` (the polluted `ReviewStack#env`) into the environment used to build every `Command`, including fetch/deploy steps, and only later layers `deploy_spec.machine_env`/`@task.env` on top — it never calls `EnvironmentVariables#permit`: [4](#0-3) 
- `EnvironmentVariables#permit` (the only sanitizer in the codebase) is exclusively invoked via `DeploySpec#filter_deploy_envs` / `filter_rollback_envs`, not on the base stack/task env: [5](#0-4) [6](#0-5) 
- `Command#unbundled_env` merges `@env.stringify_keys` directly onto `BASE_ENV`/`PATH` with no key denylist, and this is what's handed to `PTY.spawn` in `Command#start`: [7](#0-6) [8](#0-7) 

Exploit flow: with `provisioning_behavior=allow_with_label`, the attacker opens a fork PR and applies a label (assumed reachable per the threat model) whose name uppercases to `GIT_EXEC_PATH`, pointing at a path inside their own repository checkout where they've committed a malicious `git-remote-https` (or other `git-*`) executable. When Shipit runs the `fetch` step's `git` subcommands for that review stack, `GIT_EXEC_PATH` is present in the spawned process's environment, causing git to resolve internal subcommands from the attacker-controlled directory instead of the trusted git installation, executing attacker code on the deploy host.

None of the existing guards intercept this: `verify_signature`/webhook HMAC validation only proves the webhook came from GitHub for that repository — it says nothing about which label names are safe; the `ExplicitParameters` schema for `LabelCapturingHandler` validates types (`String`) but not content; and `EnvironmentVariables#permit` is never invoked on the path that builds `ReviewStack#env`/`TaskCommands#env`.

### Impact Explanation
This is Critical — arbitrary command execution on the Shipit deploy host via `Command`/`PTY.spawn`, achieved by an unprivileged fork PR author against their own review stack. Since review stacks run on the shared deploy host with the same execution primitives as production deploys, a successful `GIT_EXEC_PATH` hijack (or hijack of other dangerous vars like `PATH`, `GIT_SSH`, `BUNDLE_GEMFILE`, etc., all equally unfiltered) yields host-level RCE, from which an attacker could pivot to secrets (`GITHUB_TOKEN`, deploy credentials) and other repositories' stacks/tasks running on the same host. It is repeatable for any repository configured with `allow_with_label` review stacks.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior: allow_with_label` (or any mode where an unprivileged/fork PR can reach an active stack and label events are processed). The attacker needs only to open a PR from their fork and get a label with the target name attached (per the given threat model, this is an attacker-reachable action). No Shipit session, API token, or GitHub secret is required — the webhook is a legitimate, GitHub-signed event for the attacker's own PR/repo. This makes the attack low-cost and fully repeatable.

### Recommendation
Do not merge PR label names into the process environment unfiltered. Either drop `ReviewStack#env`'s label-to-env-var behavior entirely, or route it through an explicit allowlist (e.g., `EnvironmentVariables#permit` with a fixed, non-security-sensitive variable list) and additionally hard-block reserved/dangerous variable names (`GIT_EXEC_PATH`, `PATH`, `LD_PRELOAD`, `GIT_SSH`, `BUNDLE_*`, etc.) anywhere user/webhook-controlled values are merged into `Command`'s env, including in `Command#unbundled_env`.

### Proof of Concept
Minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/command_test.rb`):
1. Build a `ReviewStack` with an associated `PullRequest` whose `labels` include `"git_exec_path"`.
2. Assert `review_stack.env["GIT_EXEC_PATH"] == "true"` (left side: attacker-controlled label; right side: env key actually present) — proving the equality "no fork-controllable key reaches env" is violated.
3. Build a `TaskCommands`/`Command` for the `fetch` step with `chdir` and `env: task_commands.env`, stub `PTY.spawn`, and assert the third positional/`chdir:` kwarg env hash passed to `PTY.spawn` contains `"GIT_EXEC_PATH" => "true"`.
4. Confirm no call to `EnvironmentVariables#permit` filters this key before it reaches `Command#unbundled_env`.
