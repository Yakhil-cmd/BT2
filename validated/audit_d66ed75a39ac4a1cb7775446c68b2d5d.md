### Title
Front-runnable split liquidation bypasses bad-debt socialization, leaving unrecoverable debt on the books - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
The `liquidate` function decides whether to write off (socialize) a borrower's remaining bad debt using a snapshot of the borrower's collateral list taken at the start of that single transaction, plus an estimate (`other-debt-repayable`) of whether the borrower's *other*, untouched collateral assets could still cover the remaining debt. This check is evaluated independently, per call, per collateral asset. The codebase's own comment on `liquidate-multi` — *"Prevents front-running attacks that prevent bad debt socialization"* — confirms the developers identified that sequential, non-atomic `liquidate()` calls on the same borrower's different collateral assets can race each other and defeat this check, but the fix was only applied to the batch path, leaving the permissionless single-call `liquidate()` exploitable.

### Finding Description
In `liquidate`, once the target collateral asset is fully seized (`coll-removed`/remaining == 0), the contract only triggers `socialize-debt-asset` (bad-debt write-down against the vault, which reduces `lindex`/`total-borrowed` for all suppliers) if `no-collateral-left` is true: [1](#0-0) 

`no-collateral-left` is true only if the borrower had a single collateral asset, or if the *other* collateral assets the borrower held (as counted at the very start of this transaction, via `pos-full`/`position`) could not plausibly repay the remaining debt (`other-debt-repayable == 0`): [2](#0-1) 

This estimate is computed purely from state visible to *this* call — it has no knowledge of another `liquidate()` transaction targeting a different collateral asset of the same borrower that is pending or lands in the same block. Because `liquidate()` is fully permissionless (anyone can call it, targeting any borrower/collateral/debt asset triple) and is not required to go through the atomic `liquidate-multi`, an attacker can deliberately split what should be one atomic "seize all remaining collateral, then socialize" operation into two independent `liquidate()` transactions (one per collateral asset) and control their relative ordering (front-running/back-running an honest liquidator). Each individual call can each independently conclude "the other collateral can still cover the debt" (or vice versa) and skip socialization, while after both transactions land the borrower is left with zero collateral and un-repaid debt that was never socialized to the vault.

The batch function `liquidate-multi` exists specifically to close this gap by liquidating multiple asset pairs for one position atomically: [3](#0-2) 

...but nothing prevents liquidators (or a griefing third party) from using the unprotected single-call path instead, which the codebase's own comment acknowledges is racy.

### Impact Explanation
When socialization is skipped, the debt remains recorded against a borrower with no seizable collateral. This debt continues to accrue interest in the vault's index math even though it can never actually be repaid, distorting `total-borrowed`/utilization/APY for every other supplier in that vault and permanently misstating the amount of assets truly available to withdraw. This is a **temporary (and, if enough positions accumulate this way, permanent) freezing of funds** belonging to unrelated suppliers of the debt vault — an unprivileged third party distinct from both the attacker and the liquidated borrower — matching the in-scope "socialization charged to all suppliers" / "ordering dependence between two users in one block" categories.

### Likelihood Explanation
The attack requires no privileged role: `liquidate()` is public, and any account can watch the mempool for a liquidation of a multi-collateral position and submit a second `liquidate()` call on a different collateral asset of the same borrower, ordered so that each call's `other-debt-repayable` estimate is calculated without seeing the other pending call. This is a pure ordering/race condition, costing the attacker only gas, and the project's own code comments show the team was already aware of the underlying race for the batch path but did not close it for the single-call path.

### Recommendation
- Do not rely on a same-transaction snapshot (`pos-full`/`position`) to estimate whether "other" collateral can cover remaining debt; instead, when the target asset's remaining balance hits zero, re-fetch the borrower's full, current position after all state writes from this call, and iterate over all remaining collateral assets to make a definitive, up-to-date determination before deciding to skip socialization.
- Alternatively, restrict/deprecate the single-asset `liquidate()` entry point for positions with multiple collateral assets in favor of `liquidate-multi`, or add a separate, permissionless "finalize/reconcile" function that anyone can call to force socialization of debt once a position is verified (via a fresh read) to have zero collateral, regardless of how the collateral was removed.

### Proof of Concept
1. Borrower has two collateral assets: sBTC (large value) and STX (small/dust value), and a large USDC debt, at 95% LTV (full liquidation eligible).
2. Honest Liquidator B prepares `liquidate(borrower, sBTC-ft, USDC-ft, debtAmount, ...)`, expecting `no-collateral-left` to be false because STX collateral still exists and (at current state) looks capable of covering the remainder, so B does not expect socialization from this call and plans a follow-up.
3. Attacker A, watching the mempool, submits `liquidate(borrower, STX-ft, USDC-ft, dustDebtAmount, ...)` first, seizing the STX collateral in a separate transaction ordered ahead of B's transaction (or interleaved), each transaction only observing the position snapshot as it existed at its own start.
4. After both transactions land: sBTC is fully seized (B's tx) and STX is fully seized (A's tx). At no point did either individual call's `no-collateral-left` check see the OTHER seizure already having emptied all collateral, so `socialize-debt-asset` may never fire in either transaction for the remaining unpaid debt, even though the borrower ends the block with zero collateral and non-zero debt.
5. That leftover debt now sits permanently on the books, accruing phantom interest and corrupting the vault's `total-borrowed`/utilization accounting used by all suppliers, since `vault-socialize-debt` (the only mechanism to reduce `lindex`/`total-borrowed` for uncollateralized debt) was never invoked.
