### Title
Webhook signature verifies the sender's organization secret, not the repository the payload claims to write to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / webhook secret to validate a signature against using `repository_owner`, which is read from `payload.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . But the handlers that actually act on the payload (create/sync stacks, write commit statuses, etc.) resolve the target repository from a *different* field, `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing in the engine enforces that `repository.owner.login` (the org whose secret authenticated the request) matches the owner encoded in `repository.full_name` (the repo whose stacks/commits get mutated).

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and verifies the raw request body against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) . Shipit supports multiple onboarded GitHub organizations, each with its own independent `webhook_secret` (see the multi-org config sample) [4](#0-3) , and `verify_webhook_signature` is a pure HMAC check scoped to whichever org's secret was looked up [5](#0-4) .

Every default handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) inherits from `Handler`, which locates the target `Repository`/`stacks` using `repository_name = payload.dig('repository', 'full_name')` [6](#0-5) , and `Repository.from_github_repo_name` simply splits that string on `/` and looks the row up [7](#0-6) .

Because `repository.owner.login` (used for signature routing) and `repository.full_name` (used for the actual mutation target) are two independent, attacker-controlled JSON fields in the same signed body, an attacker who legitimately administers/owns *any* organization onboarded to the same Shipit instance (and therefore knows that org's `webhook_secret`, e.g. because they can trigger real deliveries from their own repo) can craft a payload where:
- `repository.owner.login` = `"attacker-org"` (so `verify_signature` uses attacker-org's own known secret and passes), and
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler mutates/creates data for a completely unrelated stack).

This breaks the intended binding: *"the organization that authenticated" == "the repository that is written."*

### Impact Explanation
The concrete blast radius depends on the handler, but is strongest for `StatusHandler`: commit statuses (`state`, `description`, `target_url`, `context`) are written to the matched commit verbatim from the payload, as shown by the controller test asserting the created `Status` record mirrors the payload fields exactly [8](#0-7) , with no independent GitHub API re-verification of the status content. Shipit's merge-queue/continuous-deployment features gate merges/deploys on required commit statuses reaching a "success" state, so an attacker able to forge a `success` status for a victim repository's commit (while authenticating with their own, unrelated org's webhook secret) can help unblock an unauthorized merge or deploy for a stack they do not control — a cross-repository write and potential unauthorized deploy/merge.

The `PushHandler` path is less impactful in isolation: it can trigger `GithubSyncJob` for a victim `Stack`, but that job re-fetches commits from the real GitHub API via the stack's own credentials (`stack.github_api`) rather than trusting payload content [9](#0-8) , so it cannot inject fabricated commits — it can only force/annoy a resync, which does not meet the Critical/High bar on its own.

### Likelihood Explanation
Exploitability requires only that the attacker control a repository/organization already onboarded to the target Shipit instance (a routine, low-privilege condition for a multi-tenant deployment automation tool, and explicitly not one of the excluded prerequisites such as a Shipit session, `ApiClient` token, or repository write access to the *victim* repo). Crafting the JSON body and computing an HMAC with a secret the attacker legitimately knows is trivial.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, require that the organization used to select the webhook secret is cryptographically bound to the same repository the handler subsequently mutates — e.g., derive both the secret lookup and the mutation target from the same, single-sourced field (`repository.full_name`), and additionally validate that the resolved `Repository`/`Stack`'s configured GitHub owner matches `repository_owner` before allowing the handler to run. Reject events where these do not match.

### Proof of Concept
1. Attacker legitimately owns `attacker-org`, onboarded to the shared Shipit instance, and knows `attacker-org`'s `webhook_secret` (obtained by observing a real webhook delivery to their own repo, or being a maintainer with a GitHub App install).
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim-repo-real-commit-sha>",
  "state": "success",
  "description": "forged",
  "target_url": "https://attacker.example",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and the signature validates successfully [1](#0-0) .
5. `StatusHandler` (via `Handler#repository_name`) resolves `victim-org/victim-repo` and writes the forged `success` status onto the victim's commit, exactly as demonstrated by the existing test that shows payload fields flow straight into the created `Status` record [8](#0-7) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
