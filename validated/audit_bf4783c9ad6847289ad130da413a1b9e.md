### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table, with no repository/stack scoping, unlike every other webhook handler which scopes via `Repository.from_github_repo_name(repository_name)`. Since `sha` is only unique per `(sha, stack_id)` (not globally), a shared git ancestor sha between a victim repository and any other repository whose webhook is legitimately signed (e.g., a fork owned by the attacker) lets an attacker write a `Status` record onto the victim's `Commit` row for that sha, flipping `Commit#blocked?`/`#deployable?` and letting `Stack#next_commit_to_deploy` select a commit that should still be blocked.

### Finding Description
The broken binding is: **`webhook signer’s repository == the repository whose Commit record receives the status`**. `verify_signature` only proves the payload's HMAC matches the webhook secret configured for `repository_owner` (the org named in the payload) — it says nothing about which `Commit` rows get mutated. [4](#0-3) 

`StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [3](#0-2) 

This is a global, unscoped query. The `commits` table's uniqueness constraint is `(sha, stack_id)`, not `sha` alone: [5](#0-4)  — meaning distinct stacks/repositories can legitimately hold separate `Commit` rows sharing the same `sha` (e.g., two Shipit-tracked repositories that share git ancestry, such as a fork of the victim's repo, both syncing the same pre-divergence commits via `GithubSyncJob`). [6](#0-5) 

Contrast with `Handler#stacks` and `PushHandler#process`, which correctly resolve the target stacks strictly through the payload's `repository.full_name`: [1](#0-0) [2](#0-1) . `StatusHandler` skips this helper entirely, so a correctly-signed status webhook from the attacker's own (legitimately Shipit-tracked) repository/org is applied to *every* `Commit` row anywhere in the database sharing that sha, including one belonging to the victim's stack.

Exploit flow: attacker owns/administers a repository forked from (or sharing history with) the victim's repository, and that repository is itself onboarded to the same Shipit instance (a realistic multi-tenant precondition — Shipit supports multiple orgs via `Shipit.github(organization:)` / `secrets.github`). [7](#0-6)  The attacker uses GitHub's real status API against their own fork on the shared ancestor sha (a legitimate operation on a commit that genuinely exists in their repo), causing GitHub to deliver a webhook correctly signed with their own org's `webhook_secret`. [8](#0-7)  `verify_signature` passes because it only checks the attacker's own org's secret against the attacker's own payload. `StatusHandler#process` then finds and mutates the victim's `Commit` row with the same sha, calling `commit.create_status_from_github!(params)` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)`, writing a `success` status under the victim's `stack_id` for the guessed blocking context (e.g. `ci/travis`). [9](#0-8) 

This flips `Status::Common#blocking?` to false for that context on the shared commit: [10](#0-9) , which flips `Commit#blocked?` to false for the next undeployed commit: [11](#0-10) , making it `deployable?`: [12](#0-11) , and `Stack#next_commit_to_deploy`/`trigger_continuous_delivery` then selects and deploys it. [13](#0-12) [14](#0-13) 

None of the listed guards prevent this: `verify_signature` authenticates the *sender's own org*, not the *target commit's owning repository*; there is no `ExplicitParameters` field or `drop_unhandled_event` check tying `repository.full_name` to the resolved `Commit`; `require_permission!`/`User#authorized?` are irrelevant since this is an unauthenticated webhook path; model validations don't enforce sha uniqueness across stacks (by design, to support forks/shared history).

### Impact Explanation
An attacker who controls any GitHub repository onboarded to the same multi-tenant Shipit instance (their own fork or any repo sharing git history with the victim) can write arbitrary `Status` rows onto a foreign stack's commit, bypassing the explicit `ci.blocking` deployment safety gate and causing an unauthorized/unsafe deploy to proceed on a victim stack. This is a payload for one repository mutating another's commit/stack state, leading to an unauthorized deploy — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is repeatable against any victim stack that shares any commit sha with a repository the attacker controls (most commonly via forking), and scales to any number of such shared-history repositories on the instance.

### Likelihood Explanation
Preconditions: (1) a multi-tenant Shipit deployment where multiple GitHub orgs/repos are onboarded (each with distinct `webhook_secret`, per `Shipit.github(organization:)`), (2) the victim stack configures `ci.blocking` for a context name the attacker can guess or observe (commonly a well-known CI context like `ci/travis` or `ci/circleci`), (3) attacker forks/owns a repository whose commit history overlaps with the victim's undeployed range. All of these are realistic in open-source or shared-infra Shipit setups. The attacker's cost is low: fork the repo, and use ordinary GitHub API calls to set a status on a real commit in their own fork — no secrets, no privileged Shipit role, no signature forgery required. This is fully repeatable and requires no timing tricks.

### Recommendation
Scope `StatusHandler#process` by the webhook's `repository.full_name`, mirroring `Handler#stacks`/`PushHandler`: resolve the target `Repository`/`Stack`s from the payload first, then restrict the `Commit` lookup to `stacks.commits.where(sha: params.sha)` (or equivalently filter by `stack_id` in the resolved repository's stacks) instead of a bare `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook for a repository does not mutate a commit belonging to another stack sharing the same sha" do
  victim_stack = shipit_stacks(:soc)              # has ci.blocking configured
  blocking_commit = shipit_commits(:soc_second)
  blocking_commit.statuses.delete_all
  target_commit = shipit_commits(:soc_third)

  assert_predicate blocking_commit, :blocking?
  refute_predicate target_commit, :deployable?    # baseline: blocked

  # attacker's repo/stack shares the same sha as blocking_commit (e.g. fork ancestor)
  other_stack = shipit_stacks(:shipit)
  attacker_commit = other_stack.commits.create!(
    sha: blocking_commit.sha, author: shipit_users(:walrus), committer: shipit_users(:walrus),
    authored_at: Time.now, committed_at: Time.now, message: "shared ancestor"
  )

  payload = { 'sha' => blocking_commit.sha, 'state' => 'success', 'context' => 'ci/travis',
              'repository' => { 'full_name' => other_stack.github_repo_name,
                                 'owner' => { 'login' => other_stack.repository.owner } } }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  refute_predicate blocking_commit.reload, :blocking?   # BUG: victim's blocking commit unblocked
  assert_predicate target_commit.reload, :deployable?    # BUG: previously blocked commit now deployable
end
```
Both sides of the equality (`attacker's authenticated repository` vs `repository owning the mutated Commit row`) diverge: the handler mutates `blocking_commit` (belonging to `victim_stack`) even though the signed webhook belongs to `other_stack`'s repository.
