Confirmed root cause: the signature-verification key selection and the actual repository/stack acted upon are bound to two different fields of the same unverified JSON body, so a valid signature from one organization's webhook secret can be replayed to drive actions against a *different* repository's stacks.

### Title
Webhook signature is verified against `repository.owner.login`, while the handler dispatches on `repository.full_name` from the same unverified body - cross-organization / cross-repository stack sync - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization (and thus which `webhook_secret` to HMAC-verify against) using `repository_owner`, which is read straight out of the untrusted JSON body via `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . Once the signature is accepted, the entire raw body — including a `repository.full_name` field that is never covered by that owner-scoped selection — is handed unchanged to the event handlers [3](#0-2) . Handlers such as `PushHandler` resolve the target `Stack`s purely from `repository.full_name` [4](#0-3) [5](#0-4) .

### Finding Description
The verified binding should be: `signature(webhook_secret[org]) == HMAC(body)` AND `org == owner(repository acted upon)`. In this engine, the second half of that equality is never enforced — `repository_owner` (used to select which org's secret validates the signature) and `repository_name`/`full_name` (used to select which `Stack`s are synced) are two independent fields read from the same attacker-controlled JSON, with no cross-check that they refer to the same repository.

Concretely: any GitHub organization that is a legitimate Shipit-configured tenant (i.e., has a `Shipit.github(organization:)` entry with a known `webhook_secret`, per `config/secrets*.yml`) can compute a valid `X-Hub-Signature` for an arbitrary payload of its own choosing, because the secret is a shared, static per-org value used purely for HMAC, not tied cryptographically to repository identity within the org, and — critically — the org used for verification is *itself* attacker-supplied in the JSON (`repository.owner.login`) rather than derived from any authenticated channel. An attacker who controls org A's webhook secret can therefore submit a `push` (or other) webhook where `repository.owner.login == "orgA"` (so `verify_signature` selects and validates against orgA's secret) but `repository.full_name == "orgB/some-repo"` (a repository belonging to a different, victim organization tracked by the same Shipit instance). `PushHandler` will then locate `orgB/some-repo`'s stacks via `Repository.from_github_repo_name(repository_name)` and call `stack.sync_github(expected_head_sha: params.after)`, triggering a sync/deploy-eligible state change on a stack the attacker does not own, using a signature that was never actually validated against that org's secret.

### Impact Explanation
This breaks the trust boundary between "organization that authenticated the webhook" and "repository whose Shipit stacks are mutated," letting a party who only controls one tenant's webhook secret cross-write into another tenant's stack state (queueing syncs, updating `expected_head_sha`, and other webhook-driven side effects for `check_suite`, `status`, `pull_request`, `membership` handlers which all resolve via the same unauthenticated `repository.full_name`/`organization.login` fields). On a multi-organization Shipit deployment (the engine explicitly supports multiple GitHub orgs, see `secrets_double_github_app.yml`), this is a cross-repository/cross-tenant write achieved purely by crafting a JSON body, without needing the victim org's secret at all.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with more than one GitHub organization/app (a documented, supported configuration), and (2) the attacker possessing a valid webhook secret for *any one* of those configured organizations (e.g., because they are an admin of a lesser-trusted org onboarded to the same instance). Given those two preconditions — no GitHub App private key, no `api_clients_secret`, no session, and no access to the victim org's secret is needed — the attack is a single crafted HTTP POST.

### Recommendation
After locating the handler's target repository/stacks, re-derive the organization from the actually-acted-upon repository (`repository.full_name`'s owner, or the `Stack`/`Repository` record's own known owner) and confirm it matches the organization whose secret validated the signature; reject the webhook if they diverge. Alternatively, bind webhook secrets per-repository (not per top-level org) and verify against the same field used for repository resolution.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as shown in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, who knows `OrgA`'s `webhook_secret` (e.g., is a member/admin of OrgA), crafts a push payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Computes `X-Hub-Signature: sha1=<hmac_sha1(OrgA_webhook_secret, body)>` and sends it as `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully [1](#0-0) .
5. `PushHandler` resolves stacks from `full_name = "OrgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on OrgB's stack [5](#0-4) , even though the signature was never validated using OrgB's secret.
