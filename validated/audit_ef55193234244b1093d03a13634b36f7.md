### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone, with no scoping to the repository that was actually authenticated by `verify_signature`. Because `Commit#create_status_from_github!` writes the status against whatever `Commit` record matches the SHA — regardless of which stack/repository it belongs to — a status event that is legitimately signed for repository A can update a commit belonging to repository B's stack, as long as the same SHA exists in both (which is guaranteed for a PR head commit shared between a fork and its upstream target).

### Finding Description
The broken binding is:
`params.dig('repository','full_name')` (the repository verified by `WebhooksController#verify_signature` via `Shipit.github(organization: repository_owner)`) **==** `commit.stack.repository` (the repository whose `MergeRequest`/`Commit` record actually gets mutated).

Trace:
1. `WebhooksController#verify_signature` resolves the GitHub App config using `repository_owner = params.dig('repository','owner','login')` and calls `github_app.verify_webhook_signature`, which only proves the payload was genuinely signed for *that* organization/app installation. [1](#0-0) [2](#0-1) 
2. `StatusHandler#process` then executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is **global across all stacks**, with no `WHERE stack.repository = ...` or any check that `commit.stack.repository` matches the verified `repository_owner`/`full_name` from the payload. [3](#0-2) 
3. `Commit#create_status_from_github!` writes the new status via `statuses.replicate_from_github!(stack_id, github_status)` using the *matched commit's* `stack_id`, not any stack tied to the verified organization. [4](#0-3) 
4. `add_status` calls `stack.schedule_merges if new_status.pending? || new_status.success?`, which drives `ProcessMergeRequestsJob` to re-evaluate `MergeRequest#all_status_checks_passed?` for the pending merge-queue entry in the *victim* stack. [5](#0-4) 

Root cause: a git commit SHA is a content hash, not a repository-scoped identifier. When an attacker opens a PR from their own fork against stack B's repository, the identical commit object (same SHA X) exists both in the attacker's fork and in stack B's `Commit` table (created when the PR was tracked). The attacker only needs a validly-signed `status` webhook for *their own* repository/org carrying SHA X — signature verification succeeds because it is genuinely signed for the attacker's own org — but `StatusHandler#process` never restricts the update to commits under that org's stacks. This lets the attacker's self-controlled CI green-light the required status context on the victim's commit, satisfying `MergeRequest#all_status_checks_passed?` and triggering `merge_request.merge!` → `stack.github_api.merge_pull_request` on stack B.

No other guard intervenes: `drop_unhandled_event` and `check_if_ping` are unrelated; `ExplicitParameters` (`params.sha`, `params.state`, `params.context`) validates only shape, not repository ownership; there is no `require_permission!`/`stacks` scope check inside `StatusHandler` or `Commit#create_status_from_github!`.

### Impact Explanation
An attacker with no relationship to stack B's repository (not a maintainer, no Shipit session/token, no repo secrets) can force a specific commit's CI status/check-run state in an arbitrary victim stack, as long as they can get a SHA match (trivially achievable for their own open PR against that stack, since the fork and PR share the identical commit object). This satisfies merge-queue required status checks and results in `merge_request.merge!` calling `stack.github_api.merge_pull_request`, i.e., an **unauthorized merge of attacker-controlled code into a repository the attacker does not control** — matching the "Critical: unauthorized merge" category. The attack is repeatable against any stack with `merge_queue_enabled: true` that shares a commit SHA with an attacker-controlled repository (i.e., any stack for which the attacker can open a pull request from a fork).

### Likelihood Explanation
Preconditions: stack B has `merge_queue_enabled: true` and a pending `MergeRequest` whose head SHA is X; a required status context name is known to the attacker (usually public, e.g., from `.shipit.yml`/branch protection). The attacker needs the capability to emit a genuinely-signed `status` webhook for a repository they own with that SHA and context — this is achievable by pushing the PR branch to their own repository/fork and running their own CI (or manually hitting GitHub's Statuses API) against SHA X in a repo where they control a valid GitHub webhook/App integration recognized by Shipit's `Shipit.github(organization:)` config. Cost is low and fully repeatable once the attacker has any repository Shipit recognizes for signature verification. The core code defect (missing repository scoping in `Commit.where(sha:)`) is unconditionally present regardless of exact GitHub App installation topology.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers, e.g. check-run handlers) to the repository named in the verified payload, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id }).each { ... }`, so a status can only mutate commits belonging to stacks whose repository matches the organization/repository that was cryptographically verified in `verify_signature`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `stack_a` (repository `attacker/fork`) and `stack_b` (repository `victim/repo`, `merge_queue_enabled: true`).
2. Create `commit_b = Commit.create!(stack: stack_b, sha: 'X...')` and a pending `MergeRequest` on `stack_b` with `head_commit: commit_b`.
3. Also create `commit_a = Commit.create!(stack: stack_a, sha: 'X...')` (same SHA, simulating the shared fork commit).
4. Build `params` for `StatusHandler` with `sha: 'X...'`, `state: 'success'`, `context: <required_context_of_stack_b>` — representing a payload whose `repository` field is `attacker/fork` (i.e., only `stack_a`'s org was verified by `verify_signature`).
5. Call `StatusHandler.new.process` (or `.call(params)`).
6. Assert-both-sides-of-binding:
   - Before: `commit_b.status.pending?` is true, `merge_request.all_status_checks_passed?` is false.
   - After: assert that `commit_b.reload.statuses.last.state == 'success'` is **true** — proving stack B's commit was updated despite the verified payload only authenticating stack A's repository — i.e. `payload_repository (attacker/fork) != commit_b.stack.repository (victim/repo)` yet the write still occurred.
7. Stub `stack_b.github_api` and expect `:merge_pull_request` to be called via `ProcessMergeRequestsJob.perform_now` after step 5, confirming `merge_request.merge!` fires from the forged cross-stack status.
