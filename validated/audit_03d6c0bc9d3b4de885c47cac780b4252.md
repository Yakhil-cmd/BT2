### Title
Assets with `cosigned_by_definer=true` permanently freeze all holders' funds if the immutable `definer_address` becomes unable to co-sign - ([File: validation.js])

### Summary
Obyte custom assets support a `cosigned_by_definer` flag that is fixed forever at asset-definition time and enforced at the consensus/validation layer for every subsequent transfer. Unlike the reported `STADIUM_ADDRESS` bug where a single hardcoded, non-updatable recipient address can permanently block a required commission transfer, here a single hardcoded, non-updatable *cosigner* address (`objAsset.definer_address`) is required on **every** payment message of the asset, for **every** holder, forever. If that address becomes unusable (private key lost/compromised, or the address is otherwise unable to produce a valid authentifier), all current and future holders of the asset lose the ability to move their own funds, with no protocol-level recovery path.

### Finding Description
When an asset is defined with `cosigned_by_definer: true`, the asset's `definer_address` is derived from the single author of the `asset` definition unit and stored immutably in the `assets` table (`writer.js` inserts `asset.cosigned_by_definer` and no update path exists for `definer_address`) [1](#0-0) .

This flag is validated at the consensus level in `validatePayment`: every payment message for the asset (including transfers made by third-party holders who have no relationship with the definer) must include `objAsset.definer_address` among the unit's authors, or the unit is rejected: [2](#0-1) 

The same hardcoded dependency is enforced client-side when composing transactions, both for divisible and indivisible assets: [3](#0-2) [4](#0-3) 

There is no mechanism anywhere in the protocol to update, rotate, or bypass `definer_address` for an already-issued asset. It is set once at issuance (single author of the `asset` message) and is baked permanently into every future validation of that asset's payments, exactly like the immutable `STADIUM_ADDRESS` in the reported Solidity bug, except the blast radius is larger: instead of freezing one Distributor's commission, it can freeze the entire circulating supply of the asset for every holder, not just the definer.

If the `definer_address`'s private key is lost, or the address is an address definition (e.g., an AA address, a multisig requiring a lost cosigner, or any authentifier) that can no longer produce a valid signature/authentifier for new units, then:
- No holder of the asset (including the definer) can ever again produce a valid, cosigned payment unit for that asset.
- Because AAs cannot cosign (`cosigned_by_definer must be false because AA can't cosign` is enforced only when the *AA itself* defines the asset, not when a third party's asset definer address later becomes unreachable) [5](#0-4) , there's no way for an AA-based rescue/migration flow to work around the missing cosigner either.
- The condition is permanent and irreversible at the protocol layer: `objAsset.definer_address` is read from `assets` table state that is fixed by the original `asset` unit hash and never updated.

### Impact Explanation
This causes irreversible freezing of funds for every current and future holder of the asset — not merely the definer, but every third party who received or holds the token. Given assets can be freely transferred among wallets, exchanges, or AAs, an entire class of tokens (custom asset instances configured with `cosigned_by_definer=true`) can become permanently unspendable network-wide once the definer's key/address becomes unusable, satisfying "AA fund loss or freezing" / permanent lock of assets.

### Likelihood Explanation
Any user or business can define an asset with `cosigned_by_definer=true` (e.g., to require compliance sign-off on every transfer, similar in spirit to a "commission"/gatekeeper requirement). The only precondition for triggering the freeze is loss/compromise/unavailability of the definer's private key or address — a routine real-world occurrence (lost seed, compromised key, address expiry/policy change), making this readily reachable without requiring any additional exploit against the protocol itself.

### Recommendation
Add a protocol-supported migration path for the `definer_address` co-signing requirement, for example:
- Allow the current `definer_address` (while still functional) to publish a signed "definer address update" message that changes which address is required for cosigning going forward, analogous to `asset_attestors` updates already supported for attestor lists.
- Alternatively, allow disabling `cosigned_by_definer` via a similar definer-signed update once certain conditions are met, so holders are not permanently at the mercy of a single immutable address.
- At minimum, document this as an explicit, severe risk for asset issuers so they use durable multisig/AA-backed definer addresses instead of single-key addresses, and consider adding tooling/warnings when defining assets with `cosigned_by_definer=true`.

### Proof of Concept
1. Address `D` authors an `asset` definition unit with `cosigned_by_definer: true`, `is_transferrable: true`. `D` becomes `objAsset.definer_address`, stored permanently by `writer.js` [1](#0-0) .
2. Asset is distributed to holders `H1`, `H2`, ... via ordinary payments.
3. `D` loses access to its private key (e.g., device lost, seed corrupted).
4. `H1` attempts to transfer asset to `H2`. `composeDivisibleAssetPaymentJoint` requires `D` among `arrPayingAddresses`/`signing_addresses` or refuses to compose [3](#0-2) ; even if a client bypasses this and submits a unit without `D` as author, `validatePayment` rejects it at consensus level with `"must be cosigned by definer"` [2](#0-1) .
5. Because `D` can never again produce a valid signature, this rejection is permanent: the entire supply of the asset held by all parties becomes permanently untransferable/unspendable, with no on-protocol recovery mechanism.
