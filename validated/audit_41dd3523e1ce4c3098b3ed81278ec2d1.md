### Title
`StatusHandler` mutates commit CI status without repository binding, unlike every other webhook handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other webhook handler (`PushHandler`, `CheckSuiteHandler`, `PullRequest::OpenedHandler`, etc.) scopes its side effects through `stacks`, which resolves via `Repository.from_github_repo_name(repository_name)` and falls back to `Stack.none`/`NullRepository` when the payload's repository is unknown to Shipit. `Shipit::Webhooks::Handlers::StatusHandler#process` never requires or reads `payload['repository']` at all and never calls `Repository.from_github_repo_name`; it looks up commits solely by `Commit.where(sha: params.sha)` across the entire database and mutates their statuses.

### Finding Description
The binding that holds everywhere else in the webhook layer is:
`Repository.from_github_repo_name(payload['repository']['full_name'])` == the `Repository` (or `NullRepository`) that gates which `stacks`/`commits` a handler is allowed to touch. [1](#0-0) [2](#0-1) 

`StatusHandler` breaks this binding entirely: [3](#0-2) 

Its `params` schema requires only `sha`, `state`, and optional descriptive fields — no `repository` block — and `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, an unscoped, database-wide lookup by SHA alone. Compare to `PushHandler`/`CheckSuiteHandler`, which restrict all effects to `stacks` derived from the payload's declared repository: [4](#0-3) [5](#0-4) 

Root cause: git commit SHAs are content-addressed identifiers computed from tree, parent(s), author, committer, and message — they carry no repository identity. An attacker who can observe a public/target commit's metadata (visible via the Shipit UI, GitHub UI, or the tracked repo itself) can reconstruct byte-identical commit content in a repository they control, producing an identical SHA. Requesting/triggering a `status` event on their own repository (properly signed by GitHub using the org-level webhook secret registered for GitHub-App verification, per this question's precondition) causes `verify_signature` to pass, because `verify_signature` only checks the signing organization, not which repository within that org is authorized to affect which stack: [6](#0-5) 

`StatusHandler#process` then finds the victim `Commit` purely by matching SHA and writes a new `Status` record via `commit.create_status_from_github!`, which can flip commit state and enqueue `ProcessMergeRequestsJob` / advance continuous-deployment logic for the *victim's* stack: [7](#0-6) 

Existing guards do not stop this: `verify_signature` authenticates the org, not the repository-to-stack binding; `drop_unhandled_event` and `ExplicitParameters` only validate that required fields (`sha`, `state`) are present, not that a `repository` claim matches an existing `Repository`; and the `Repository.from_github_repo_name` / `NullRepository` pattern that protects every other handler is simply absent from `StatusHandler`.

### Impact Explanation
A payload whose declared `repository.full_name` is entirely unknown to Shipit (or entirely omitted) can still cause a real write against a tracked victim `Commit`/`Stack`: a forged/attacker-controlled CI status is recorded for a commit belonging to a different tenant's repository and stack. This can flip the commit's aggregate CI state (`unknown → pending/success/failure/error`), trigger `deployable_status` webhooks, and enqueue `ProcessMergeRequestsJob`, which can influence auto-merge/continuous-deployment decisions for the victim stack — this is a payload for one repository mutating another's commit/stack, matching the Critical "cross-tenant mutation" category. This is repeatable against any commit SHA the attacker can reconstruct or otherwise learn, in any Shipit-tracked repository under an org that shares a GitHub App / webhook secret registration, without ever adding a `Repository` record for the attacker's own repo.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository under an org for which Shipit has registered a GitHub App / webhook secret (so GitHub will produce a validly-signed webhook that passes `verify_signature`), and (b) knowledge of a target commit's exact tree/parent/author/committer/message metadata sufficient to reproduce the identical SHA (feasible for public commits, or for any commit whose metadata the attacker can otherwise observe, e.g., through the Shipit UI itself). No Shipit session, API token, or secret key is required. The attack is cheap and repeatable — each reconstructed-SHA commit pushed to the attacker's repo generates one status event per push/CI run, and the handler applies it unconditionally to every `Commit` row sharing that SHA anywhere in the database.

### Recommendation
Scope `StatusHandler` the same way as the other handlers: require `repository.full_name` in the `params` schema, resolve `Repository.from_github_repo_name(params.repository.full_name)` (falling back to `NullRepository`/`Stack.none` on miss), and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent stack-scoped query) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Set up a victim `Stack`/`Repository`/`Commit` fixture (e.g. `shipit_commits(:first)`, belonging to `shipit_stacks(:shipit)` under repository `shopify/shipit-engine`).
2. Build a signed `status` webhook payload where `payload['repository']['full_name']` = `"attacker-org/unknown-repo"` (no matching `Repository` record exists for it), `payload['sha']` = the victim commit's real `sha`, and `state` = `"success"`.
3. Stub/allow `Shipit.github(organization: 'attacker-org')` (or whatever org key `repository_owner` resolves to) to return a `GithubApp` whose `verify_webhook_signature` returns `true`, simulating a legitimately signed but Shipit-unknown-repository payload.
4. Assert the binding before the request: `assert_nil Shipit::Repository.from_github_repo_name('attacker-org/unknown-repo')`.
5. POST to `/webhooks` with `X-Github-Event: status` and the payload above.
6. Assert `assert_difference('commit.statuses.count', 1) { post :create, body: payload, as: :json }` — proving the victim commit's statuses count incremented despite the claimed repository never existing as a `Repository` record, in contrast to the `NullRepository`/`Stack.none` no-op behavior exhibited by `PushHandler`/`PullRequest::OpenedHandler` under the same unknown-repository condition (see existing test `"create github repository which is not yet present in the datastore"` in `test/controllers/webhooks_controller_test.rb:12-21`, which shows push events are no-ops for unknown repos while status events are not).     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
