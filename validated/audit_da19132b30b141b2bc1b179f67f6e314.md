### Title
Unauthenticated `stack_id` param bypasses referrer URL_PATTERN in `MergeStatusController#check` - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController#stack` prefers `params[:stack_id]` and calls `Stack.from_param!` directly, skipping the `ReferrerParser`'s `URL_PATTERN` check entirely whenever `stack_id` is supplied. Since `check` (and `show`) skip authentication, any unauthenticated caller can pass `stack_id=owner/repo/environment` and retrieve that stack's coarse merge/CI status without ever presenting a matching `https://github.com/...` referrer.

### Finding Description
The claimed binding is: presence of a valid `github.com/.../pull/N` referrer == the only way to select a stack for `check`/`show`. This does not hold: `stack` (`app/controllers/shipit/merge_status_controller.rb:62-81`) checks `if params[:stack_id]` first and, when present, calls `Stack.from_param!(params[:stack_id])` directly — the `referrer_parser`/`URL_PATTERN` branch is only reached when `stack_id` is absent. `Stack.from_param!` (`app/models/shipit/stack.rb:515-525`) splits the string on `/` into `owner`, `name`, `environment` and does a direct lookup with no ownership or referrer check. `check` (`app/controllers/shipit/merge_status_controller.rb:39-50`) is listed in `skip_authentication only: %i[check show]` (`app/controllers/shipit/merge_status_controller.rb:5`), so `force_github_authentication` never runs for this action, and no session, token, or GitHub credential is required. `stack_status` invokes `stack.merge_status`, returning `locked`/`failure`/`backlogged`/`success`.

Exploit request: anonymous `GET /merge_status/check?stack_id=org/repo/production&format=json` (or `.html`). This directly reaches `Stack.from_param!` for any owner/repo/environment triple the attacker chooses to guess, with no relation to any pull request or referrer at all.

### Impact Explanation
An unauthenticated caller can enumerate `stack_id` values (owner/repo/environment) and learn whether a stack is `locked`, `failure`, `backlogged`, or `success` — a coarse merge/CI-readiness signal — for any stack hosted on the Shipit instance, not limited to repositories they can open pull requests against. This matches "unauthenticated read of stack state" (High severity category). It does not expose task logs, deploy output, secrets, or allow any write/mutation — `merge_status` returns only a status string, so it stays within read-only disclosure of stack readiness, not full task/deploy stream content.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host are required: no session, API token, GitHub App key, or team membership. The attacker needs only to guess or learn an `owner/repo/environment` triple, which is often predictable (`production` is the default environment, and repo names/owners are frequently public). The request is trivially repeatable against any number of stacks.

### Recommendation
In `MergeStatusController#stack`, remove the `params[:stack_id]` direct-lookup branch (or restrict it to the authenticated/internal-use case that requires a valid referrer as well), so that stack selection always goes through `referrer_parser` and its `URL_PATTERN` validation regardless of whether `stack_id` is present.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb
test "GET check with stack_id bypasses referrer restriction for anonymous caller" do
  session.delete(:user_id)
  stack = shipit_stacks(:shipit) # fixture stack never referenced by this session/referrer
  get :check, params: { stack_id: stack.to_param }, format: :json
  assert_response :success
  body = JSON.parse(response.body)
  assert_equal stack.merge_status(backlog_leniency_factor: 1.0), body['stack_status']
end
```
This demonstrates that `check`, with no `referrer` param and no session, returns `stack_status` for a stack selected purely via `stack_id`, proving the referrer/URL_PATTERN restriction is bypassed.
