### Title
Webhook forgery via organization/repository binding confusion enables cross-repository sync and deploy triggering - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a GitHub webhook using the organization derived from `repository.owner.login` (or `organization.login`) in the JSON body, but the handlers that act on the payload (e.g. `PushHandler`) select the `Stack`/`Repository` to operate on using a *different* field: `repository.full_name`. Because both fields live inside the same attacker-controlled request body that is signed as a whole, an attacker who legitimately controls the webhook secret for **any one organization** configured in this Shipit instance can forge a payload where `repository.owner.login` names their own organization (so the signature check passes with a secret they know) while `repository.full_name` names a stack belonging to a **different** organization/repository. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the authorizing organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

The signature is verified using `SecureCompare.secure_compare` against `webhook_secret` for that derived organization: [3](#0-2) 

Once verification succeeds, `create` dispatches the *entire raw payload* to the registered handler for the event: [4](#0-3) 

However, the base `Handler` class (and thus every handler, e.g. `PushHandler`) resolves the target `Stack`/`Repository` using a completely independent JSON path, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` performs a straight DB lookup on `owner`/`name` parsed from that field with no cross-check against the organization used to select the webhook secret: [7](#0-6) 

Since the whole `raw_post` (the JSON body, including both `repository.owner.login` and `repository.full_name`) is what gets HMAC-signed, an attacker who legitimately knows the webhook secret for organization `attacker-org` (e.g., because they administer a GitHub App/organization that this Shipit instance is configured to serve) can construct a payload with `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`) — satisfying `verify_signature` — while setting `repository.full_name = "victim-org/victim-repo"`. The handler then acts on the victim's `Stack`/`Repository`, which the attacker does not control at all.

### Impact Explanation
This breaks the trust boundary between "which organization's credentials authorized this webhook" and "which repository's stack gets acted upon." Concretely, with `PushHandler`, the forged payload causes `stack.sync_github(expected_head_sha: params.after)` to run against a victim's stack: [6](#0-5) 
This can force GitHub history synchronization and, depending on stack configuration (continuous delivery/auto-merge/deploy jobs triggered off synced commits), can influence deploy scheduling for a repository the attacker does not own — an unauthorized-action condition (High) since it lets an attacker cross the organizational boundary of a completely different, unrelated repository using only their own legitimately-issued webhook secret. It does not, on its own, grant `GITHUB_TOKEN` exfiltration or RCE, but it does allow cross-organization interference with stack state/sync that should require repository-specific authorization.

### Likelihood Explanation
Requires the attacker to control a webhook secret for at least one organization onboarded to the shared Shipit instance (a realistic scenario in multi-tenant Shipit deployments where multiple GitHub orgs share one Shipit installation) but nothing else — no compromise of the victim org's credentials, no repository write access to the victim repo, and no privileged Shipit account. This satisfies the "unprivileged attacker" bar since the attacker only needs standing as an authenticated (but unrelated) organization, not the target one.

### Recommendation
Bind the two fields together: after `verify_webhook_signature` succeeds for organization `O`, require that `repository.owner.login`/`organization.login` used to select the secret is the *same* value used to resolve the target `Stack`/`Repository` in `Handler#stacks`/`#repository_name`. Reject (422) any payload where the two disagree, rather than trusting `repository.full_name` independently of the authenticated organization.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is configured in this Shipit instance with `webhook_secret = S`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC matches (attacker knows `S`) — request is accepted.
5. `PushHandler#stacks` resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, looks up that `Repository`/`Stack`, and calls `stack.sync_github(expected_head_sha: ...)` — acting on a repository outside the authenticated organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
