### Title
Same L1 Bitcoin lockup output can be replayed across multiple `verify-l1-lockups` calls to double-count sats credited to a bond - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`verify-l1-lockups` proves that a staker locked BTC on Bitcoin L1 and credits the corresponding sat amount to a `protocol-bonds` entry. The de-duplication of Bitcoin outpoints (`txid`/`output-index`) is only tracked in a `seen-outpoints` accumulator that lives for the lifetime of a single call's `fold` over `validate-l1-lockup`, and is never persisted to contract storage.

### Finding Description
`verify-l1-lockups` builds an accumulator `{ sum, seen-outpoints, ... }` and folds `validate-l1-lockup` over the caller-supplied list of Bitcoin outputs: [1](#0-0) 

Inside `validate-l1-lockup`, duplicate detection is done purely against the in-memory `seen-outpoints` list carried through the fold: [2](#0-1) 

and it is appended to only within that same fold call: [3](#0-2) 

Nothing in this function (or any map I could locate, e.g. `staker-shares-staked-for-cycle`, `total-shares-staked-for-cycle`) persists the set of Bitcoin outpoints that have already been credited across different calls/transactions. `ERR_DUPLICATE_LOCKUP_OUTPOINT` only prevents including the *same* outpoint twice within *one* call's `outputs` list (max 10 entries). There is no contract-level map keyed on `{txid, output-index}` that is checked/updated to prevent the exact same Bitcoin lockup transaction output from being submitted again in a subsequent call (e.g. a second `register-for-bond`/rollover call, or a call for a different bond-index/reward cycle), since the merkle proof and script checks are stateless re-verifications of the same immutable Bitcoin history each time.

This breaks the intended equality that "sats credited via an L1 proof == sats actually locked on Bitcoin, counted once." A staker (or any account able to invoke the bond-registration path that calls `verify-l1-lockups`) can present the identical BTC lockup proof multiple times, each time incrementing `total-shares-staked-for-cycle` / `signer-shares-staked-for-cycle` / bond totals by the same sats amount without any additional BTC ever being locked.

### Impact Explanation
This is a double-counting of a commitment: STX/sBTC reward shares and bond utilization are computed off `total-shares-staked-for-cycle` and `signer-shares-staked-for-cycle`, which would now reflect BTC that was never actually re-locked. This inflates the staker's/bond's claimed stake, letting them draw a disproportionate share of sBTC rewards (see `calculate-bond-rewards`/`compute-earned-rewards` which key off these staked-sats totals) relative to actual backing BTC — a Critical-class double-counting of a commitment / theft of unbacked rewards.

### Likelihood Explanation
Likelihood depends on whether the public entry point that calls `verify-l1-lockups` (`register-for-bond`, not present in the excerpted portion of `pox-5.clar` I could inspect) itself maintains an independent, persisted map of used outpoints before calling `verify-l1-lockups`, or otherwise constrains a given BTC lockup to be attached to exactly one bond registration for the life of the contract. I was not able to locate such a map in the reachable portion of the file within the available tool budget, so I cannot fully confirm whether an extra guard exists outside `verify-l1-lockups`/`validate-l1-lockup`. This uncertainty should be resolved by inspecting the full `register-for-bond` implementation and any `used-lockup`/`credited-outpoints`-style persistent map in `pox-5.clar`.

### Recommendation
Persist every Bitcoin outpoint that has been credited (e.g. a `define-map credited-l1-outpoints { txid: (buff 32), output-index: uint } bool`) and assert non-membership before crediting sats, updating the map on success, so the same L1 lockup transaction output can never be counted more than once across the contract's lifetime, not just within a single call's fold.

### Proof of Concept
Conceptual PoC (contingent on confirming no external persisted-outpoint guard exists in `register-for-bond`):
1. Staker locks 1 BTC output on L1 to the timelock script derived from `construct-lockup-output-script`.
2. Staker calls the bond-registration function once, passing the lockup in `outputs`; `verify-l1-lockups`/`validate-l1-lockup` verify the merkle proof/script/amount and credit `sum` sats to the bond, updating `total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle`.
3. Staker calls the same registration path again (e.g., for a new bond-index or a rollover) with the *same* Bitcoin transaction/output/merkle proof. Because `seen-outpoints` was only local to the previous call, `validate-l1-lockup` re-verifies the (still valid, unchanged) Bitcoin proof and credits the same sats a second time, with no new BTC locked.
