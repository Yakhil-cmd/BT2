## Title
A user's fresh Pyth price submission can grief another user's `borrow`/`liquidate`/`collateral-add` transaction via the shared global `timestamps` map - ([File: local-testing/contracts/pyth/contracts/pyth-storage-v4.clar], [File: local-testing/contracts/market/market.clar])

### Summary
`market.clar` lets any caller attach an optional `price-feeds` bundle to `borrow`, `collateral-add`, `collateral-remove`, and `liquidate` so a stale on-chain price can be atomically refreshed. That bundle is written through `write-feed`/`write-feeds` into `pyth-storage-v4`'s global `write-batch-entry`, which enforces `is-price-update-more-recent` against a single, asset-wide `timestamps` map shared by every caller in the protocol. Whoever's price update lands first for a given `price-identifier` in a block "wins" the map; any other user whose independently-valid (non-stale) but comparatively older `publish-time` update is submitted afterward has their entire market transaction reverted with `ERR-PRICE-FEED-UPDATE-FAILED`, even though their price data was perfectly fresh on its own terms. ### Finding Description
`write-feeds` folds over the caller-supplied list of Pyth update blobs and calls `write-feed` for each, which forwards to `pyth-oracle-v4::verify-and-update-price-feeds` → `pyth-storage-v4::write` → `write-batch-entry`: [4](#0-3) 

`write-batch-entry` asserts the submitted `publish-time` is strictly greater than the value currently in the global `timestamps` map for that `price-identifier` — a map keyed only by asset identifier, not by caller: [5](#0-4) [3](#0-2) 

If that check fails, `write-batch-entry` returns `ERR_NEWER_PRICE_AVAILABLE`. Back in `market.clar`, `write-feed` treats any non-success result from the pyth call as `ERR-PRICE-FEED-UPDATE-FAILED`, and because `write-feeds` is the very first `let`-binding evaluated in `borrow`, `collateral-add`, `collateral-remove`, and `liquidate`, that error propagates and aborts the entire user transaction: [6](#0-5) [7](#0-6) 

**Attacker/victim/shared state:** Attacker = Alice, an unprivileged user who calls any market function with a `price-feeds` argument (e.g., her own `collateral-add` with a minimal amount) carrying the newest available Pyth update for an asset (BTC, STX, USDC, etc.). Victim = Bob, who has independently built a transaction (e.g., `liquidate` on an unhealthy borrower, or his own `borrow`) with a `price-feeds` bundle whose `publish-time` is valid and within the staleness window, but numerically older than the one Alice just committed. Shared state = the single global `timestamps` (and `prices`) map per `price-identifier` in `pyth-storage-v4.clar`, consumed by `is-price-update-more-recent` for every subsequent caller regardless of who they are.

**Victim outcome without attacker's tx:** Bob's `write-feed` call succeeds (his `publish-time` is newer than the stored one), the price is written, and his `borrow`/`liquidate`/`collateral-add` proceeds to evaluate health/liquidation logic normally.

**Victim outcome with attacker's tx:** Because Alice's update already advanced `timestamps` for that identifier past Bob's `publish-time`, Bob's `write-batch-entry` call reverts with `ERR_NEWER_PRICE_AVAILABLE`, `write-feed` maps that to `ERR-PRICE-FEED-UPDATE-FAILED`, and Bob's whole transaction reverts — with no fallback to simply use the already-fresh on-chain price and continue.

This is a self-inflicted revert bug: the on-chain price *was* already fresh enough (Alice's update satisfies staleness for the same asset), yet the code chooses to hard-fail the caller instead of treating "someone already updated it more recently" as a benign no-op.

### Impact Explanation
This lands as **temporary freezing of funds**: a liquidator's `liquidate` call, or a borrower's own `borrow`/`collateral-add`/`collateral-remove` call, can be made to revert purely due to price-feed submission ordering that any unrelated, unprivileged account controls (simply by broadcasting a newer legitimate Pyth update attached to their own unrelated call). Repeated or targeted griefing against a specific victim (e.g., against a liquidator racing to liquidate an unhealthy borrower before the borrower can rescue their position, or the borrower himself as he tries to top up collateral) can delay the completion of time-sensitive operations, extending the window during which a distressed position accrues bad debt or a legitimate borrow/collateral action cannot go through.

### Likelihood Explanation
Likelihood is moderate-to-high: any address can trigger the griefing effect for free by submitting a fresh, publicly available Pyth price update through any of their own unrelated market calls that accept `price-feeds` (no special permission, no cost beyond normal tx fees, and Pyth updates are public data anyone can fetch). It requires transaction ordering within roughly the same period the victim's bundle remains "not yet the newest," which is realistic in mempool/ordering races, especially around liquidations where multiple parties are actively watching the same position.

### Recommendation
Change `write-feed`/`write-batch-entry` handling so that an `ERR_NEWER_PRICE_AVAILABLE` result (or equivalent "already fresher price on-chain") is treated as a successful no-op rather than a hard failure that aborts the caller's transaction — i.e., only fail the caller's transaction if the resulting on-chain price for that identifier is actually stale per `max-staleness`/`stale-price-threshold`, not merely because someone else's update landed first. This preserves the staleness protection ‑ which is the intended safety property — while removing the caller-visible dependency on price-feed submission ordering between unrelated users.

### Proof of Concept
1. Charlie (liquidator) prepares `liquidate(borrower, ..., price-feeds: [btcUpdateA])` where `btcUpdateA.publish-time = T1` and `T1` is within the staleness window relative to the current block.
2. Before Charlie's transaction is mined, Alice — an unrelated user — calls `collateral-add` (or any market function accepting `price-feeds`) on her own position with `price-feeds: [btcUpdateB]` where `btcUpdateB.publish-time = T2 > T1` (also valid/fresh). This call succeeds and sets `pyth-storage-v4::timestamps[BTC] = T2`.
3. Charlie's transaction is now processed: `write-feed(btcUpdateA)` → `pyth-storage-v4::write-batch-entry` → `is-price-update-more-recent(BTC, T1)` evaluates `T1 > T2`, which is `false` → returns `ERR_NEWER_PRICE_AVAILABLE`.
4. `write-feed` converts this to `ERR-PRICE-FEED-UPDATE-FAILED`, `write-feeds` propagates it, and Charlie's entire `liquidate` call reverts — even though the BTC price on-chain (from Alice's update) was perfectly fresh and Charlie's liquidation would otherwise have succeeded. [3](#0-2) [8](#0-7)

(define-private (write-batch-entry (entry {
		price-identifier: (buff 32),
		price: int,
		conf: uint,
		expo: int,
		ema-price: int,
		ema-conf: uint,
		publish-time: uint,
		prev-publish-time: uint,
	}))
	(let ((stale-price-threshold (contract-call? .pyth-governance-v3 get-stale-price-threshold))
			(latest-stacks-timestamp (unwrap! (get-stacks-block-info? time (- stacks-block-height u1)) ERR_STALE_PRICE))
			(publish-time (get publish-time entry)))
		;; Ensure that we have not processed a newer price
		(asserts! (is-price-update-more-recent (get price-identifier entry) publish-time) ERR_NEWER_PRICE_AVAILABLE)
		;; Ensure that price is not stale
		(asserts! (>= publish-time (+ (- latest-stacks-timestamp stale-price-threshold) STACKS_BLOCK_TIME)) ERR_STALE_PRICE)
		;; Update storage
		(map-set prices 
			(get price-identifier entry) 
			{
				price: (get price entry),
				conf: (get conf entry),
				expo: (get expo entry),
				ema-price: (get ema-price entry),
				ema-conf: (get ema-conf entry),
				publish-time: publish-time,
				prev-publish-time: (get prev-publish-time entry)
			})
		;; Emit event
		(print {
			type: "price-feed", 
			action: "updated", 
			data: entry
		})
		;; Update timestamps tracking
		(map-set timestamps (get price-identifier entry) (get publish-time entry))
