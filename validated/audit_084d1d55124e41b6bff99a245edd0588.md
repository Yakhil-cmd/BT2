Based on my investigation, I found a strong analog to CVE-2024-24420's pattern (an attacker-reachable, uncaught exception/assertion on a maliciously crafted message causing a DoS).

### Title
Remote DoS via uncaught exception in `decryptPackage()` on `hub/message` with unrecognized ephemeral key - (File: `device.js`)

### Summary
`decryptPackage()` throws an unhandled `Error` inside a `setTimeout` callback whenever an incoming device message's `encrypted_package.dh.recipient_ephemeral_pubkey` does not match any of the node's known keys (current temp key, previous temp key, or permanent key). This throw is not wrapped in any `try/catch` reachable from the event loop, so it becomes an uncaught exception that crashes the node process — the same bug class as CVE-2024-24420 (a reachable assertion/uncaught error triggered by a crafted packet from an untrusted peer, causing a DoS).

### Finding Description
`handleJustsaying()` processes `hub/message` justsayings from the hub with only shallow structural checks and a self-consistent signature check (the attacker signs the message with their own freely-generated keypair/pubkey, so the check does not require any pre-existing trust relationship): [1](#0-0) 

It then calls `decryptPackage(objDeviceMessage.encrypted_package)` [2](#0-1)  before any check of whether the sender is a known correspondent (that check happens later, at line 204 for the `handleMessage` continuation) [3](#0-2) .

Inside `decryptPackage()`, the recipient key lookup compares `objEncryptedPackage.dh.recipient_ephemeral_pubkey` (fully attacker-controlled) against the node's own public temp/prev-temp/permanent keys. If it matches none of them, the function logs and throws inside a `setTimeout`, which is not caught by any enclosing `try/catch` in the call chain: [4](#0-3) 

Because the throw occurs asynchronously in a timer callback rather than synchronously inside the `try { var json = decryptPackage(...) } catch(e) { ... }` block at the call site [2](#0-1) , the calling function's catch cannot intercept it — it surfaces as a Node.js uncaught exception.

### Impact Explanation
An uncaught exception of this kind, absent a resilient top-level `uncaughtException` handler that safely no-ops, terminates the Node.js process. This matches the "network unable to confirm new units" / node-crash impact class accepted by the validation rules: any node/hub-connected wallet that receives such a crafted `hub/message` justsaying can be forced offline, requiring a restart. I was unable to fully verify from the available index whether `network.js`'s `uncaughtException` handling (referenced in `network.js`, not fully retrievable in this session) intercepts and neutralizes this specific throw or lets the process exit — this should be confirmed by reading `network.js` in full before treating this as conclusively exploitable.

### Likelihood Explanation
Reaching this path only requires: (1) knowing the target's `my_device_address` (public, exchanged during pairing/correspondence and needed to route messages through the hub), (2) crafting a self-signed `objDeviceMessage` with an arbitrary/garbage `dh.recipient_ephemeral_pubkey`, `iv`, `authtag`, and `encrypted_message`. No prior pairing, no valid decryption, and no privileged access is required — this fits the "paired device"/unprivileged-message-sender reachability the rules permit, and arguably requires even less trust since the correspondent-known check happens after decryption is attempted.

### Recommendation
Wrap the `setTimeout(() => { throw Error(...) }, 100)` in `decryptPackage()` with a safe error path (e.g., emit a `nonfatal_error` event as already done in the commented-out line, or simply `return null`) instead of throwing asynchronously and uncatchably. Move the correspondent-known check before attempting decryption where feasible, and ensure all message-parsing failure paths return an error value rather than throw outside of the caller's `try/catch` scope.

### Proof of Concept
1. Determine the victim's `my_device_address` (already required to address any device message to them).
2. Generate an attacker keypair; compute `pubkey`, sign the `objDeviceMessage` payload with it to pass `ecdsaSig.verify` (self-consistent check, does not require the hub or a whitelisted correspondent). [5](#0-4) 
3. Set `encrypted_package.dh.recipient_ephemeral_pubkey` to an arbitrary base64 string that is guaranteed not to equal the victim's current temp, previous temp, or permanent public keys (these are unknown to the attacker anyway).
4. Submit the justsaying `hub/message` with this crafted `objDeviceMessage` via the hub to the victim node.
5. The victim's `decryptPackage()` hits the "unknown key" branch and throws inside `setTimeout`, crashing the node process. [6](#0-5)
