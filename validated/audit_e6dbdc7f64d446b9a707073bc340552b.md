## Title
Webhook signature-verification organization is derived from an attacker-controlled JSON field that differs from the field used to resolve the target repository/stack, allowing cross-organization forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to use for HMAC verification by reading `repository_owner`, which is parsed straight out of the untrusted request body (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`). Once the signature check passes, the same untrusted body is handed to the event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`), which resolve the actual `Repository`/`Stack` to act on using a *different* field of the same body: `payload.dig('repository', 'full_name')` in `Handler#repository_name`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This chooses the HMAC secret/config keyed by whatever `repository.owner.login` (or `organization.login`) the request body claims — a value fully controlled by whoever sends the POST, since it is part of the JSON payload being signed, not metadata Shipit derives independently (e.g. from a URL path or App installation context).

Once verification passes, the raw parsed body is dispatched to handlers such as `PushHandler`/`StatusHandler`, which resolve the repository to mutate through `Handler#repository_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`repository.owner.login` (used to pick the signing secret) and `repository.full_name` (used to pick the repository/stack that gets written to, e.g. via `stack.sync_github` in `PushHandler#process`) are two independent, attacker-supplied fields in the same JSON body: [3](#0-2) 

In a multi-organization Shipit deployment (`Shipit.github(organization: ...)` — documented and supported via the per-org `github:` config keyed by organization name, see `docs/setup.md` "Using Multiple Github Applications"), an attacker who legitimately controls one configured organization's GitHub App/webhook (i.e., knows that organization's `webhook_secret`) can craft a payload where `repository.owner.login`/`organization.login` names *their own* org (so the correct, known secret is selected and the HMAC check passes) while `repository.full_name` names a *victim* organization's repository. The signature check only binds the payload to "some org whose secret matches," not to "the org that the repository-mutating field claims." Since the handlers never cross-check `repository_owner` (the authenticated org) against `repository.full_name`'s owner (the org whose Stack/Repository actually gets modified), the equality `authenticated organization == organization of the repository written` is not enforced.

This is the direct engine analog of the reported bug class: a value the code trusts as authorized (`repository_owner`, gating which secret validates the signature) is not the same value that determines what is actually written (`repository.full_name`, driving `Repository.from_github_repo_name` and subsequent `Stack` mutation).

### Impact Explanation
If exploitable, this allows an attacker who is a legitimate collaborator of any one org configured in a multi-org Shipit instance to forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) against a completely different org's repositories/stacks that are also configured in the same Shipit instance — e.g. injecting forged `push` events to trigger `GithubSyncJob`/`stack.sync_github` against a repository they don't own, or forged `status`/`check_suite` events to manipulate deploy-blocking CI state on a victim's stack. This crosses a cross-repository boundary and can influence deploy/rollback decisions, matching the High-impact category ("escalation... unauthenticated read of stack state... " territory) and potentially contributing to an unauthorized deploy if combined with status/check manipulation.

### Likelihood Explanation
This requires the instance to be configured with multiple GitHub organizations (a documented, supported configuration) and requires the attacker to know a valid webhook secret for at least one configured org — which is plausible for an actor who administers or has appropriate access to one org's GitHub App settings but not the victim org's. This is a real, non-privileged-account precondition for the attacker relative to the *victim* organization, distinguishing it from scenarios requiring a Shipit session, `ApiClient` token, or the victim's own secret.

### Recommendation
After selecting the signing organization from `repository_owner`, verify that the same organization matches the owner embedded in `repository.full_name` (and `organization.login` if present) before dispatching to handlers; reject the webhook if they diverge.

### Proof of Concept
Conceptual (cannot be fully executed without a live multi-org Shipit deployment and a legitimate attacker-owned org secret):
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with their own `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. Attacker crafts a `push` JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/some-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` → `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes using the attacker's own secret.
5. `PushHandler#process` resolves the target `Repository`/`Stack` via `repository.full_name` = `"victim-org/some-repo"` and calls `stack.sync_github`, acting on the victim's stack despite the signature only proving control of `attacker-org`'s secret. [4](#0-3) [2](#0-1) [3](#0-2)

      github_app = Shipit.github(organization: repository_owner)
