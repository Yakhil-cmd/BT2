The OpenEXR bug is a C++-specific memory-safety defect: a signed `int64_t` subtraction (`stream_sz - nend`) produces a negative value that implicitly converts to an unsigned `size_t`, which is then passed directly to `memcpy`, causing an out-of-bounds heap read  .

I searched for equivalent patterns in polkadot-sdk — length/size calculations derived from subtraction that feed directly into a raw copy without bounds validation. All comparable Rust code paths I found use safe, checked constructs rather than raw pointer arithmetic feeding `memcpy`-equivalents:

- `substrate/frame/contracts/src/wasm/runtime.rs` bounds-checks sandbox memory reads/writes via `memory.get(ptr..ptr + len)` which returns `None` (converted to `Error::OutOfBounds`) rather than wrapping to a huge unsigned value [1](#0-0) .
- `substrate/frame/support/src/storage/stream_iter.rs`'s `StorageInput` uses `saturating_sub` and explicit length checks (`Not enough data to fill the buffer`) rather than raw signed-to-unsigned conversions before copying [2](#0-1) .
- `cumulus/primitives/core/src/parachain_block_data.rs`'s `PrependBytesInput::read` uses `saturating_sub`/`saturating_add` for its remaining-length arithmetic, avoiding underflow entirely [3](#0-2) .
- `substrate/frame/revive`'s EVM-compatibility code (`EXTCODECOPY`) previously halted on offset overflow and was fixed to saturate rather than wrap, which is the opposite failure mode (a fix for a DoS/behavioral mismatch, not a memory-safety bug) [4](#0-3) .

In Rust, this specific bug class — a negative signed value silently reinterpreted as an enormous unsigned length that is then used to perform an out-of-bounds raw memory copy — is structurally prevented by the language: slice indexing/copy operations (`copy_from_slice`, `[a..b]`) panic on invalid ranges rather than trusting an attacker-derived length like C++'s `memcpy` does, and the codebase's numeric code consistently uses `saturating_sub`/`checked_sub`/bounds-checked `.get()` rather than raw signed subtraction feeding a copy. I found no reachable user-entry (extrinsic, XCM message, contract call) where an attacker-controlled length passes through an equivalent unchecked signed-to-unsigned conversion directly into a raw memory copy, so there is no demonstrable analog of this OpenEXR vulnerability in this codebase.

			}

		// anymore.

		}

		let end = self.buffer_pos + into.len();
