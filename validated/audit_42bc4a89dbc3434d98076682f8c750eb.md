The Nextcloud CVE describes a system where a **secret bearer token** (derived deterministically from a hash function instead of secure randomness) grants unauthorized access to a resource — i.e., unprivileged knowledge of a predictable value substitutes for proper authentication.

FRAME's authorization model doesn't have an analogous class of "secret capability tokens." Every hash-derived identifier I found in the codebase is a **public, content-addressed identifier**, not a secret used for access control:

- `pallet-preimage`'s `note_preimage`/`request_preimage` use `T::Hashing::hash(&preimage)` purely as a content-addressed lookup key; anyone can compute and note any preimage, and access decisions are gated by `ensure_signed`/`ManagerOrigin`, not by knowledge of the hash. [1](#0-0) 
- `pallet-recovery`'s `InheritorTicketOf`/`AttemptTicketOf` ("tickets") are storage-deposit `Consideration` handles (`IdentifiedConsideration`), not secret authentication tokens — control over a recovered account is checked via `ensure!(maybe_inheritor == inheritor, Error::<T>::NotInheritor)` on the caller's `AccountId`, not by presenting any hash-derived value. [2](#0-1) [3](#0-2) 
- Storage hashers (`Twox128`, `Blake2_128Concat`, etc.) and multisig/call hashes are explicitly public identifiers used for storage-key derivation or call identification, never treated as unguessable secrets. [4](#0-3) 

Since FRAME extrinsics authenticate via signed origins (`ensure_signed`, proxy/multisig signer binding) rather than via possession of a hash-derived "token," there is no reachable unprivileged entry point where an attacker could compute a predictable secret and use it to bypass authorization the way the Nextcloud Calendar participant tokens did. This bug class does not have a genuine analog in the scoped production code.
