### Title
Webhook signature verified against attacker-chosen organization while payload's repository field drives writes to a different repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against based on an unauthenticated, attacker-supplied field of the very payload being verified (`repository.owner.login` / `organization.login`). Nothing then re-checks that this same field matches the repository that the event handlers actually act on (`repository.full_name`, `repository.owner.login` used deeper in webhook handlers to resolve the target `Stack`/`Repository`). This breaks the binding: *organization that authenticated == repository that is written*.

### Finding Description
`verify_signature` resolves the signing secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the JSON body the attacker controls (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`), and is used to pick which `Shipit.github(organization: repository_owner)` config (and thus which per-organization `webhook_secret`) verifies `X-Hub-Signature`: [3](#0-2) 

Shipit supports multiple GitHub orgs, each with its own independently-configured `webhook_secret`, as shown in the sample secrets file: [4](#0-3) 

Once the signature check passes, the entire raw JSON body is parsed and dispatched, unmodified, to the registered event handlers: [5](#0-4) 

The handlers (push sync jobs, pull-request handlers, commit-status handlers, etc.) locate the target `Repository`/`Stack` using other fields of the same JSON body (e.g. `repository.full_name`), as seen across the pull request handler family:



Because the signature is only checked to be *a* valid signature for *some* organization's secret — the one named by `repository_owner`/`organization.login` in the same forgeable payload — there is no cryptographic guarantee that the org whose secret validated the request is the same org/repository that the handler subsequently writes to. An attacker who controls (or has installed the Shipit GitHub App on) their own organization "org-A" knows `org-A`'s `webhook_secret`. They can craft a payload where `organization.login`/`repository.owner.login` is `"org-A"` (to select the correct secret) while `repository.full_name` (or nested repository object used by the handler to resolve the actual `Stack`) points at `"org-B/victim-repo"`, a completely different tenant's repository configured on the same multi-tenant Shipit instance. HMAC-SHA1 is computed correctly with `org-A`'s secret over the full raw body, so `verify_webhook_signature` returns `true`, and the forged event is then processed against `org-B`'s stack.

### Impact Explanation
This allows an attacker who legitimately controls one tenant organization on a multi-tenant Shipit deployment to inject forged, "signature-valid" webhook events that are processed as if they originated from a different, victim organization/repository. Depending on which handler is targeted, this can:
- Trigger `GithubSyncJob` against a victim stack, changing perceived commit/branch state used for deploy gating.
- Feed forged `pull_request`/`status`/`check_suite` payloads that influence merge-queue and CI-gating decisions (`MergeRequest#merge!`, `StatusChecker`), potentially causing an unauthorized merge or unlocking a deploy on the victim's repository.
This crosses a repository trust boundary without requiring any credential belonging to the victim organization, satisfying the "cross-repository writes"/"unauthorized deploy or merge" bar.

### Likelihood Explanation
Exploitability requires the attacker to control at least one organization/App installation on the same multi-tenant Shipit instance (a low bar for anyone who can create a GitHub org and get the shared Shipit App installed on it, or who already has legitimate but limited access to one tenant). No access to the victim's secret, session, or `ApiClient` token is required — only the ability to craft an arbitrary HTTP POST to the public `/webhooks` endpoint with a validly-signed-for-a-different-org payload.

### Recommendation
After verifying the HMAC signature for the organization selected by `repository_owner`, re-validate that every repository/organization reference used later by the dispatched handlers (`repository.full_name`, `repository.owner.login`, `organization.login`) is consistent with the organization whose secret actually verified the signature, and reject the webhook otherwise. Alternatively, resolve the target `Repository`/`Stack` strictly from the verified organization instead of re-parsing repository identity independently inside each handler.

### Proof of Concept
1. Attacker controls organization `org-A` on a multi-tenant Shipit instance and knows `org-A`'s configured `webhook_secret` (e.g., by installing/configuring the Shipit GitHub App on their own org, a self-service action GitHub allows).
2. Attacker crafts a JSON payload for a `push`/`pull_request`/`status` event where:
   - `organization.login` (or `repository.owner.login`) = `"org-A"`
   - `repository.full_name` = `"org-B/victim-repo"` (the actual target used by `Shipit::Webhooks` handlers to resolve the `Stack`)
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org-A_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event` set accordingly.
4. `WebhooksController#verify_signature` computes `repository_owner == "org-A"`, calls `Shipit.github(organization: "org-A").verify_webhook_signature(...)`, which succeeds because the signature was computed with `org-A`'s real secret.
5. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs with `params['repository']['full_name'] == "org-B/victim-repo"`, causing the handler to act on `org-B`'s stack despite the request never being signed by `org-B`.

Note: I was not able to fully retrieve the exact push/status handler source (only the pull_request handler family and `handler.rb` were confirmed via search) to show the literal `Stack.from_repo_name`/lookup line; a Devin session with full file access should confirm the exact lookup call used by the push/status/check_suite handlers to complete this PoC end-to-end.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
