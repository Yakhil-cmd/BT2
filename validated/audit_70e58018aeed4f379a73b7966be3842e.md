### Title
Webhook signature verification is keyed by an attacker-controlled `repository.owner.login`/`organization.login` field while the actual write action is keyed by the unrelated `repository.full_name` field, letting an org with no `webhook_secret` configured act as a skeleton key for any other org's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC `webhook_secret`) to verify the incoming webhook against, based on `repository_owner`, a value read directly out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The event handlers that actually mutate state (sync a stack, add team memberships, close/archive review stacks, etc.) instead key off a *different* field in the same body: `repository.full_name` (owner/repo pair) via `Shipit::Webhooks::Handlers::Handler#repository_name`. `GitHubApp#verify_webhook_signature` also short-circuits to `true` whenever `webhook_secret` is blank for the selected org. Because Shipit explicitly supports multiple independently configured GitHub orgs (see `docs/setup.md` "Using Multiple Github Applications" and `Shipit.github_app_config`), any org in that config without a `webhook_secret` set becomes a global bypass: an attacker can craft a payload whose `repository.owner.login` names the secret-less org (satisfying `verify_signature`), while `repository.full_name` names a totally different org/repo that Shipit actually tracks and acts on.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes `repository_owner` purely from body content: [1](#0-0) [2](#0-1) 
- `Shipit.github(organization: repository_owner)` resolves to whatever config block matches that attacker-supplied login, per `github_app_config`: [3](#0-2) 
- `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatic success, regardless of the signature header supplied: [4](#0-3) 
- After verification passes, `WebhooksController#create` dispatches the *entire* raw payload to handlers, unrelated to which org was used for verification: [5](#0-4) 
- Every handler's targeting logic (`stacks`, `repository`) reads `repository.full_name`, a separate JSON field from the one used for signature-org selection: [6](#0-5) [7](#0-6) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository being written to**. Instead, Shipit verifies against `owner.login` but writes against `full_name`, two independently attacker-controlled fields inside the same unauthenticated JSON body. `docs/setup.md` documents multi-org deployments where each org configures its own (optional) `webhook_secret`: [8](#0-7) 

If even one configured organization omits `webhook_secret` (which the setup docs mark as optional/nilable in every example, e.g. `webhook_secret: # nil`), that organization's name becomes a universal, secret-free key: submit `repository.owner.login: "<org-without-secret>"` to pass `verify_signature`, but set `repository.full_name: "other-org/other-repo"` to make the push/pull_request/membership/status/check_suite handlers act on stacks belonging to a completely different, secret-protected organization.

### Impact Explanation
This breaks the trust boundary between "which org authenticated this webhook" and "which repository is mutated," letting an unauthenticated attacker who only knows the name of any secret-less org in the deployment:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha:)` for another org's stacks (spoofed sync state).
- Trigger `MembershipHandler` to add/remove memberships (`Team`/`Membership` records) using attacker-supplied `organization.login`/`member.login`.
- Trigger PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) to archive/unarchive review stacks or update pull-request state for repositories in a different, secret-protected org.
- Feed forged `status`/`check_suite` payloads that flip `Commit` deployable/commit-status state used to gate deploys.

Since Shipit gates deploys on commit/CI status and review-stack lifecycle on these very webhook events, this is a route to an unauthorized deploy-adjacent state change (e.g., marking a commit deployable, unarchiving a review stack) without ever possessing any org's real `webhook_secret`, `GITHUB_TOKEN`, or session — matching the "unauthorized deploy/rollback" and "cross-repository writes" impact classes.

### Likelihood Explanation
Requires only: (1) knowledge that the deployment configures multiple GitHub organizations (documented, common pattern per `docs/setup.md`), and (2) that at least one configured organization has not set `webhook_secret` — which every example/config file in this repo (`config/secrets.development.example.yml`, `secrets.development.shopify.yml`, `secrets_double_github_app.yml`'s `OrgTwo`) shows as the default/typical state (`webhook_secret: # nil`). No credentials, session, or GitHub App private key are needed; the endpoint (`POST /webhooks`) is unauthenticated by design and is meant to be internet-reachable.

### Recommendation
Bind the org used for signature verification to the org that handlers act on: verify the signature using the org derived from the *validated* `repository.full_name`/owner (not a separately-read field), and reject payloads where `repository.owner.login`/`organization.login` and `repository.full_name`'s owner segment disagree. Additionally, do not silently treat a blank `webhook_secret` as "verified" — require an explicit opt-in (e.g., `webhook_secret: false`/disabled flag) to skip verification, so a merely-unset secret in one org config cannot become a bypass for all other configured orgs.

### Proof of Concept
1. Deploy Shipit with the multi-org config shown in `docs/setup.md` (`docs/setup.md:182-209`): org `secretless-org` (no `webhook_secret` set) and org `victim-org` (has `webhook_secret` set and a tracked stack `victim-org/victim-repo`).
2. Send `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "secretless-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "secretless-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid signature required.
4. `PushHandler#process` uses `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` to look up and mutate `victim-org`'s stack, even though no `victim-org` secret was ever presented.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
