The CVE-2024-26824 bug is a Linux kernel-specific double-free/bogus-free bug in `algif_hash`'s scatterlist (SGL) management when hashing a zero-length message through the AF_ALG socket interface — it's rooted in C-style manual memory management where an SGL is conditionally allocated but unconditionally freed on an error path.

I searched the Polkadot SDK codebase for analogous hashing entry points (`substrate/frame/contracts/src/wasm/runtime.rs` `compute_hash_on_intermediate_buffer`, `substrate/frame/revive/src/vm/pvm/env.rs` hash host functions, `substrate/frame/revive/src/vm/evm/instructions/system.rs` `keccak256`, and `substrate/frame/support/src/hash.rs` storage hashers) and found no equivalent pattern of a manually-allocated/conditionally-freed buffer or scatter-gather list. [1](#0-0) [2](#0-1) 

These all operate on Rust slices/`Vec<u8>` with RAII-based ownership — there is no manual "free on error path" logic that could double-free or free unallocated memory, because Rust's ownership/drop semantics eliminate this entire bug class by construction. Zero-length inputs (`n = 0` in the benchmarks, or `len == 0` in `keccak256`) are handled as ordinary slice operations without any conditional allocation/free pairing that could go out of sync. [3](#0-2) 

No FRAME/XCM/contracts/revive code path exhibits the "allocate conditionally, free unconditionally" defect that caused the kernel CVE, so there is no demonstrable analog here.

pub fn keccak256<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	let ([offset], top) = interpreter.stack.popn_top()?;
	let len = as_usize_or_halt::<E::T>(*top)?;
	interpreter
		.ext
		.frame_meter_mut()
		.charge_or_halt(RuntimeCosts::HashKeccak256(len as u32))?;

	let hash = if len == 0 {
		H256::from(KECCAK_EMPTY)
	} else {
		let from = as_usize_or_halt::<E::T>(offset)?;
		interpreter.memory.resize(from, len)?;
		H256::from(keccak_256(interpreter.memory.slice_len(from, len)))
	};
	*top = U256::from_big_endian(hash.as_ref());
	ControlFlow::Continue(())
}
