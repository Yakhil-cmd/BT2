### Title
Webhook signature verification is keyed on an attacker-controlled organization field that is decoupled from the repository the event actually writes to - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/secret to verify a webhook against using `repository_owner`, a value read straight out of the unauthenticated, attacker-supplied JSON body. The event handlers, however, resolve *which* `Stack`/`Repository` to act on using a different field from that same body (`repository.full_name`). Because these two fields are never checked against each other, and because signature verification is a no-op when the selected organization has no `webhook_secret` configured, an attacker can pick an unprotected (or attacker-known) organization for verification while pointing the actual write-path at a fully protected repository/stack.

### Finding Description
`verify_signature` derives the organization used to fetch the verifying `GitHubApp` purely from the request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config and instantiates a `GitHubApp` for it: [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as "verified": [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the same raw payload to handlers: [5](#0-4) 

Each `Handler` resolves the target stacks from a *different* payload field — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

So the binding that should hold is: *organization authenticated (`repository.owner.login`) == organization of the repository written to (`repository.full_name`'s owner)*. Nothing in the controller or `Handler` base class enforces this equality — the two fields are read independently from a body the attacker fully controls (this endpoint requires no session, `ApiClient` token, or prior authentication; that's precisely what `verify_signature` is meant to establish). An attacker can therefore submit a JSON body where `repository.owner.login` names an organization configured in `Shipit.github_app_config` without a `webhook_secret` (so `verify_webhook_signature` short-circuits to `true`), while `repository.full_name` names an entirely different, fully-secured victim repository whose stacks actually get acted upon, e.g. `PushHandler#process` triggering `stack.sync_github` or `StatusHandler#process` writing commit statuses: [7](#0-6) [8](#0-7) 

This mirrors the report's bug class exactly: a field ("`lastCumulativeRate`"/here, "the repository actually acted on") is used in the write path while a *different*, stale/unrelated instance of conceptually the same value ("the organization used to compute/verify" ) is what gates the authorization check — the two are never reconciled before the privileged write happens.

### Impact Explanation
This lets an unauthenticated network attacker forge webhook events (push, status, check_suite, pull_request, membership) that are accepted as "verified" for any organization in the multi-tenant `secrets.github` config that lacks a `webhook_secret`, and use that acceptance to drive writes against a completely different, secured repository's stacks (triggering syncs, forcing commit statuses, or other webhook-driven state changes) — a cross-repository/cross-organization write achieved by defeating the intended authentication boundary.

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint (no session, token, or GitHub credentials) and requires the deployment's `secrets.github` to contain at least one organization entry without `webhook_secret` set — a configuration state the code explicitly supports (`return true unless webhook_secret`) rather than rejects, making it a realistic operational scenario in multi-organization installs rather than a purely theoretical edge case.

### Recommendation
Bind the signature-verification organization to the same repository/organization the handler will act on: derive `repository_owner` and `repository_name` once, verify the owner of `repository.full_name` matches `repository.owner.login`/`organization.login` before trusting either, and reject (or require an explicit `webhook_secret`) for any organization in `Shipit.github_app_config` that has none configured rather than treating a missing secret as automatically verified.

### Proof of Concept
1. Configure `secrets.github` with two orgs: `victim-org` (has `webhook_secret` set, owns stack `victim-org/victim-repo`) and `unsecured-org` (no `webhook_secret` configured).
2. POST to `/webhooks` with `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "unsecured-org" } },
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>"
}
```
3. `repository_owner` resolves to `unsecured-org`; `Shipit.github(organization: 'unsecured-org').verify_webhook_signature` returns `true` because `webhook_secret` is blank, bypassing verification entirely.
4. `Shipit::Webhooks::Handlers::PushHandler` resolves stacks via `repository.full_name` = `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, despite the request never having proven possession of `victim-org`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
