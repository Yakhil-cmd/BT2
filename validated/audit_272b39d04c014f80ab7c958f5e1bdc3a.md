### Title
Unauthorized STX theft via forged `PreStxOp.output` and unauthenticated `TransferStxOp.sender` - ([File: stackslib/src/chainstate/burn/operations/transfer_stx.rs])

### Finding Description
The broken equality: `sender_who_authorized_the_transfer == sender_field_used_by_run_stx_transfer`. In this flow, the two diverge — the STX debited belongs to the victim, but no key belonging to the victim ever signed anything.

`TransferStxOp::parse_from_tx` (lines 126-195) takes `sender: &StacksAddress` as an externally-supplied parameter and copies it verbatim into the resulting op: `sender: sender.clone()` [1](#0-0) . This `sender` value is resolved by the burnchain-op processing code from the linked `PreStxOp`'s `output` field (found via `get_sender_txid`, which requires only that the `TransferStxOp`'s first input spends vout=1 of the referenced `PreStxOp` transaction) [2](#0-1) .

The `PreStxOp.output` value itself is derived purely from parsing the *first output address* of the `PreStxOp` Bitcoin transaction — a value the transaction's creator can set to any address at all, including a victim's, without needing the victim's private key (Bitcoin lets anyone pay to any address). Nothing in this code path verifies that the party constructing the `PreStxOp`/`TransferStxOp` pair actually controls the private key corresponding to `output`/`sender`.

`TransferStxOp::check` performs no authorization check whatsoever — it only validates that the amount is non-zero and that sender != recipient: [3](#0-2) . There is no signature check, no requirement that the `sender`/`output` address be tied to the actual Bitcoin input signer of the `PreStxOp` transaction.

Attack: attacker funds a Bitcoin transaction (their own inputs) that acts as the `PreStxOp`, setting vout[0] = victim's Stacks-mapped Bitcoin address (arbitrary, attacker doesn't need victim's key) and vout[1] = an address the attacker controls. The attacker then submits a second Bitcoin transaction (the `TransferStxOp`) spending vout=1 (which the attacker can sign, since they created and control that output), with `recipient` = attacker's address and `transfered_ustx` = victim's balance. `TransferStxOp::parse_from_tx` sets `sender = pre_stx.output` = victim's address; `check()` passes trivially; `process_transfer_ops` then calls `run_stx_transfer(sender=victim, recipient=attacker, amount)`, debiting the victim's real STX balance with zero Stacks-level authorization.

### Impact Explanation
Complete, permission-less theft of any unlocked STX balance held by any Stacks address, limited only by the attacker's ability to construct two ordinary Bitcoin transactions with their own funds. This is repeatable against any victim address with an unlocked balance, and matches the Critical impact category (theft of unlocked STX with no valid authorization).

### Likelihood Explanation
Preconditions are minimal: the victim must have `transfered_ustx` of spendable/unlocked STX, and the attacker needs enough of their own BTC to fund two low-value Bitcoin transactions (op-return-carrying PreStxOp + spend of vout1). No cycle-phase or membership-state constraints apply since this bypasses Stacks-level PoX/staking logic entirely — it operates purely at the burnchain-op layer. Cost to the attacker is just Bitcoin transaction fees, and the attack is fully repeatable against any address with a known balance.

### Recommendation
Require that the `output` (and thus the derived `sender`) of a `PreStxOp` be provably controlled by the transaction creator — e.g., require it match the Bitcoin address that signed the `PreStxOp`'s own input(s) (self-send enforcement), or require `TransferStxOp`/`StackStxOp` operations to additionally validate a real Stacks-level signature/authorization from `sender` before `run_stx_transfer` executes the debit.

### Proof of Concept
Rust integration test plan (burnchain op harness):
1. Create victim account with balance `B` STX; do not give the test attacker any key material for the victim.
2. Craft a `PreStxOp`-equivalent Bitcoin transaction from attacker-owned inputs with `vout[0].address = victim_btc_address` (mapping to victim's `StacksAddress`) and `vout[1].address = attacker_btc_address`.
3. Craft a `TransferStxOp` Bitcoin transaction whose input spends `vout=1` of the transaction from step 2 (signed with the attacker's key), with `recipient = attacker_address`, `transfered_ustx = B`.
4. Feed both transactions through the normal burnchain-op parsing/processing pipeline (`PreStxOp::from_tx` → `TransferStxOp::from_tx` → `TransferStxOp::check` → `Chainstate::process_transfer_ops`).
5. Assert: victim's `stx_balance` decreases by `B` and attacker's balance increases by `B`, and assert no Stacks-signed transaction or victim-owned Bitcoin key was ever used in the process — proving the equality "funds moved == funds the victim authorized" is broken (LHS = B, RHS = 0).

        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {

                    Ok(txid)
                }

                Err(op_error::InvalidInput)
            }
        }
    }

    pub fn check(&self) -> Result<(), op_error> {
        if self.transfered_ustx == 0 {
