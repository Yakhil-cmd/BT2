### Title
Webhook signature verification is scoped to the wrong organization, allowing a repository/commit-status forgery across tenants - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The reported bug class is "one field is used to compute the sensitive result while a different, unverified field is the one actually acted upon." The same shape exists in `WebhooksController`: the field used to select *which organization's secret verifies the HMAC* (`repository.owner.login` / `organization.login`) is not the same field used to decide *which repository/stack/commit is mutated* (`repository.full_name`, or in the `status` event, a bare `sha` with no repository scoping at all).

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization whose `webhook_secret` will validate the HMAC using: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` selects a distinct `GithubApp` (and its own `webhook_secret`) per organization, as configured in `config/secrets*.yml` (multiple orgs, each with its own `webhook_secret`, are explicitly supported — see `test/dummy/config/secrets_double_github_app.yml`). Once the HMAC check passes for that org, the entire raw payload — untouched — is handed to the event handlers: [3](#0-2) 

The handlers, however, never re-check that `repository.owner.login` matches the repository they act on. `Handler#repository_name` (and thus `#stacks`) is derived independently from `repository.full_name`: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` use that `stacks` lookup (by `full_name` only, not by owner), so nothing prevents `repository.owner.login` (used for signature selection) from disagreeing with `repository.full_name` (used for target selection): [5](#0-4) [6](#0-5) 

`StatusHandler` is worse: it doesn't consult repository/stack scoping at all — it matches purely on a global `sha`: [7](#0-6) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

**Binding broken:** `organization authenticated (repository.owner.login used to pick the webhook_secret) != repository/stack acted upon (repository.full_name / bare sha used to pick the target)`.

An attacker who legitimately administers Organization B's own GitHub App inside a shared/multi-tenant Shipit deployment (they know Org B's `webhook_secret` because they configured it) can craft a `status` (or `push`/`check_suite`) webhook body where `repository.owner.login` = `"OrgB"` (so `verify_signature` succeeds against Org B's secret) while the substantive fields (`sha`, or `repository.full_name`) reference a stack that belongs to Org A, which the attacker has no access to. The signature only proves "this request is authentic for Org B," yet the handler executes an action against Org A's tracked commits/stacks.

### Impact Explanation
This lets an attacker with no privileges on Org A's repository forge a `status` webhook that sets an arbitrary commit status on any tracked commit across the whole Shipit instance (`Commit#create_status_from_github!`), and forge `push`/`check_suite` events that trigger `stack.sync_github` or check-run refresh cycles for stacks they do not own. Because commit statuses gate CI-required checks used by the merge queue and deploy readiness logic (`ci.require`, `merge.require` in `shipit.yml`), this is a cross-tenant write that can unblock or manipulate the conditions that permit merges/deploys on a repository the attacker does not control — matching the "cross-repository writes / unauthorized deploy or merge" high-impact category.

### Likelihood Explanation
Requires the attacker to control at least one legitimate organization/GitHub App wired into the same shared Shipit instance (a realistic, unprivileged-relative-to-other-tenants scenario, since `config/secrets*.yml` explicitly supports multiple independent organizations sharing one Shipit deployment). No GitHub write access to the victim org, no `ApiClient` token, and no session is needed — only a raw HTTP POST with a body the attacker fully controls and a signature computed with their own secret.

### Recommendation
Bind the two fields together: verify the webhook signature using the organization derived from the *same* repository object that handlers act on (`repository.full_name`'s owner), and have every handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc.) confirm that the resolved `Repository`/`Stack`'s owner matches the organization whose secret validated the signature, rejecting the event otherwise. `StatusHandler` in particular should scope its `Commit` lookup by the stack/repository derived from the verified organization rather than a bare, globally-unscoped `sha`.

### Proof of Concept
1. Attacker controls Org B's GitHub App inside a shared Shipit instance and knows Org B's `webhook_secret` (from `secrets.yml`, e.g. as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<sha of a commit tracked under Org A's stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using Org B's `webhook_secret` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgB"`, fetches Org B's `GithubApp`, and the HMAC validates successfully. [1](#0-0) 
5. `StatusHandler#process` then updates the status of the commit belonging to Org A's stack, entirely unrelated to the organization that actually authenticated the request. [7](#0-6) 

Note: I was unable to fully trace `Commit#create_status_from_github!` and `Stack#sync_github` implementations, and the `Shipit.github_teams` authorization code in `lib/shipit.rb`, in the time available due to tool-call limits — a full review of those methods (in `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb`) would be needed to precisely enumerate every downstream consequence (e.g., exact effect on merge-queue admission and deploy gating).
