### Title
Webhook signature verification selects the signing organization from a payload field independent of the field used to target the repository/stack, allowing cross-organization forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to validate a delivery against using `repository_owner`, but the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` from a different field (`repository.full_name`). An attacker who legitimately controls (or has been issued) the webhook secret for one configured GitHub organization in a multi-tenant Shipit deployment can craft a payload whose `repository.owner.login` matches their own org (so the signature check passes with their known secret) while `repository.full_name` points at a repository belonging to a *different* organization also configured in the same Shipit instance. Nothing re-validates that the two fields agree, so the forged, correctly-signed webhook is processed against the unrelated organization's stack.

### Finding Description
`Shipit.github(organization:)` supports a per-organization config map (`secrets.github[org][:webhook_secret]`), and the controller selects the verification key from the payload itself, not from any pre-established relationship with the stack being acted on: [1](#0-0) [2](#0-1) 

`Shipit.github` looks up the per-org config and, when found, instantiates a `GitHubApp` whose `verify_webhook_signature` simply HMACs the raw body with that org's own secret: [3](#0-2) [4](#0-3) 

Once the signature is accepted, `create` dispatches the raw parsed payload to handlers, none of which re-check `repository_owner`; they instead resolve the acted-upon repository from `repository.full_name`: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is: `organization whose secret authenticated the request == organization owning the repository/stack that gets acted on`. Because `repository_owner` (`repository.owner.login`/`organization.login`) and `repository.full_name` are two independent fields inside the same JSON body, and the attacker who owns one org's genuine webhook secret can freely construct and correctly sign *any* JSON body, they can set these two fields inconsistently: sign with their own org's secret while pointing `repository.full_name` at a stack belonging to a different org configured on the same Shipit instance. The signature check only proves "this body was signed with organization A's secret" — it does not prove "this body's target repository belongs to organization A."

### Impact Explanation
An operator/admin holding legitimate webhook credentials for only one organization in a multi-tenant Shipit deployment can forge webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`) that are processed as if they originated from GitHub for an entirely different organization's repository. For `push`, this drives `stack.sync_github(expected_head_sha:)` via `GithubSyncJob`, which updates commit history and can trigger CI-status-driven or continuous-deployment logic on a stack the attacker has no legitimate access to — an unauthorized cross-repository/cross-organization write and potential unauthorized deploy trigger, crossing exactly the org-authenticated-vs-repo-written boundary the rules call out.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with the multi-organization GitHub config schema (`secrets.github` keyed by organization) and (2) the attacker holding a legitimate webhook secret for at least one of those organizations. Given those preconditions — which are just "attacker administers one of several orgs onboarded to a shared Shipit instance," not a privileged Shipit account or GitHub App key compromise — constructing the mismatched payload and signing it is trivial (no signature-forging needed, it's their own valid key).

### Recommendation
After signature verification, re-derive the acted-upon repository/organization from the same field used to select the verification key (or vice-versa) and reject the webhook if they disagree — i.e., assert `repository.full_name.split('/').first == repository_owner` (case-insensitively) before dispatching to handlers, mirroring the buffer-first-then-fallback principle from the analog report: validate the trusted/verified scope before acting on the broader payload-derived target.

### Proof of Concept
1. Shipit is configured with two organizations, `orga` and `orgb`, each with its own `webhook_secret`, and both have repositories/stacks registered.
2. Attacker controls `orga`'s webhook secret (e.g., is the GitHub org admin who configured Shipit for `orga`).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "orgb/target-repo", "owner": { "login": "orga" } }
}
```
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC(orga_webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orga")` (from `repository.owner.login`), verifies successfully against `orga`'s secret.
6. `PushHandler` resolves the target via `payload.dig('repository','full_name')` → `"orgb/target-repo"`, finds `orgb`'s stack, and calls `stack.sync_github(expected_head_sha: ...)`, acting on `orgb`'s stack despite the request only being authenticated as `orga`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
