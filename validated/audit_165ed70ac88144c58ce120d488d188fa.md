Found the relevant analog: `checkUpstreamProvenance` in `pkg/cmd/skills/install/install.go` derives its trust decision (whether to redirect installation to an "upstream" repository) entirely from **attacker-controlled content in the skill file being installed** — the same class of flaw as the `drawRandomNumber()` bug, where a parameter fully controlled by the calling/attacking party determines a security-relevant outcome that should instead depend on independently-verified data.

### Title
Upstream skill redirect decision is driven entirely by attacker-controlled `github-repo` frontmatter metadata - ([File: pkg/cmd/skills/install/install.go])

### Summary
`gh skill install` fetches a skill's `SKILL.md`, parses attacker-supplied YAML frontmatter, and uses the `github-repo` metadata field found there to decide whether to redirect the install to a different ("upstream") repository. Because this metadata lives inside the very file being installed — content fully controlled by whoever publishes the skill — a malicious skill author can freely set `github-repo` to point anywhere, influencing where `gh` subsequently fetches and installs code from, similarly to how the `_slots` parameter in the reported `drawRandomNumber()` bug let a caller manipulate a value (`lastDrawEligibleCount`) that should have been derived from trusted state.

### Finding Description
In `checkUpstreamProvenance` [1](#0-0) , the function fetches the skill's `SKILL.md` contents from the repository being installed, parses the frontmatter, and reads `existingRepo, _ := result.Metadata.Meta["github-repo"].(string)`. If this value differs from the current repo URL, it is parsed into a `ghrepo.Interface` via `source.ParseRepoURL(existingRepo)` and returned as the "upstream" redirect target. This whole chain is driven by a value the skill author wrote into their own published file — there is no cryptographic binding, ownership check, or independent verification that the claimed upstream repository has any real relationship to the skill.

When `opts.Upstream` is true (the `--upstream` flag), the redirect happens automatically and silently: `fmt.Fprintf(opts.IO.ErrOut, "Redirecting install to %s...\n", upstreamLabel); return upstreamRepo, true, nil` [2](#0-1) . Back in `installRun`, this causes `opts.repo`, `opts.SkillSource`, `opts.version`, and `opts.Pin` to all be overwritten and the function to recurse against the attacker-nominated repository: `opts.repo = upstreamRepo; opts.SkillSource = ghrepo.FullName(upstreamRepo); opts.version = ""; opts.Pin = ""; return installRun(opts)` [3](#0-2) . Note that `opts.Pin = ""` — even if the user tried to pin the install to a known-good ref, an attacker-controlled redirect silently discards that pin.

In non-interactive mode without `--upstream`, `gh` proceeds to install from the re-publisher anyway (safe default), but the metadata is still fully attacker-controlled and used to decide UI hints/behavior.

This mirrors the halborn finding's root cause: a party who should have no special authority (the skill publisher, analogous to the unprivileged caller of `drawRandomNumber()`) supplies a parameter (`github-repo` frontmatter, analogous to `_slots`) that materially changes the trust-relevant outcome (which repository code is fetched/installed from, analogous to which draw result is recorded) without any independent verification.

### Impact Explanation
If a user runs `gh skill install <attacker-repo> <skill> --upstream` (or interactively selects the "upstream" option, which the attacker can make attractive/plausible by naming a well-known, legitimate-looking repo in the frontmatter), `gh` will fetch and install skill files from a repository entirely chosen by the attacker's frontmatter content, not by the user's actual input or any verified provenance. Since skills are already documented as executable/untrusted content that "may contain prompt injections, hidden instructions, or malicious scripts" [4](#0-3) , this effectively lets one untrusted party's static file content redirect installation to another attacker-controlled repository of the attacker's choosing, and silently clears any `--pin` the user specified, weakening a defense the user explicitly opted into.

### Likelihood Explanation
Requires the user to run `gh skill install ... --upstream` against a repository the attacker controls (or interactively pick "upstream" from a prompt whose label the attacker also controls, since `upstreamLabel` is derived from the same attacker-supplied `github-repo` value). This fits the "malicious normal user/content publisher" attacker profile with no privileged access — the same profile as the original PrizePool report, where any unprivileged caller could pass a crafted parameter.

### Recommendation
Do not derive redirect targets purely from unauthenticated content embedded in the artifact being installed. If upstream-provenance redirection is desired, verify the claimed relationship independently (e.g., via a signed attestation, `github-tree-sha`/commit ancestry check against the actual upstream, or requiring the upstream repo to itself reference the re-publisher) before trusting the frontmatter. At minimum, preserve the user's explicit `--pin` across a redirect rather than clearing it, and make the redirect decision explicit even under `--upstream` (e.g., an additional confirmation showing the exact untrusted metadata value the decision came from).

### Proof of Concept
1. Attacker publishes a skill repository `attacker/skills-repo` containing `skills/git-commit/SKILL.md` with frontmatter:
```yaml
---
name: git-commit
metadata:
  github-repo: https://github.com/attacker/second-stage-repo
  github-tree-sha: <sha>
  github-path: skills/git-commit
---
```
This is exactly the pattern exercised by `republishedContent` in the test suite [5](#0-4) .
2. Victim runs `gh skill install attacker/skills-repo git-commit --upstream --pin v1.0.0`.
3. `checkUpstreamProvenance` reads `github-repo` from the attacker's file and returns `attacker/second-stage-repo` as the upstream target [6](#0-5) .
4. `installRun` recurses with `opts.repo` swapped to `attacker/second-stage-repo`, `opts.Pin` reset to `""` (the user's pin is discarded) [7](#0-6) .
5. The victim ends up installing content from a second attacker-chosen repository instead of the one they explicitly typed, with their pin protection silently bypassed.

```go
func checkUpstreamProvenance(opts *InstallOptions, client *api.Client, hostname string, skill discovery.Skill, commitSHA string) (ghrepo.Interface, bool, error) {
	u, err := safeurl.JoinPath("repos", opts.repo.RepoOwner(), opts.repo.RepoName(), "contents", skill.Path+"/SKILL.md")
	if err != nil {
		return nil, false, err
	}
	u.SetQuery("ref", commitSHA)
	var fileResp struct {
		Content  string `json:"content"`
		Encoding string `json:"encoding"`
	}
	if err := client.REST(hostname, "GET", u.String(), nil, &fileResp); err != nil {
		return nil, false, nil //nolint:nilerr // best-effort check; failing to fetch is not fatal
	}
	if fileResp.Encoding != "base64" {
		return nil, false, nil
	}
	decoded, decodeErr := io.ReadAll(base64.NewDecoder(base64.StdEncoding, strings.NewReader(fileResp.Content)))
	if decodeErr != nil {
		return nil, false, nil //nolint:nilerr // best-effort; decode failure is not fatal
	}
	content := string(decoded)

	result, parseErr := frontmatter.Parse(content)
	if parseErr != nil || result.Metadata.Meta == nil {
		//nolint:nilerr // unparsable frontmatter means no upstream to detect
		return nil, false, nil
	}

	existingRepo, _ := result.Metadata.Meta["github-repo"].(string)
	if existingRepo == "" {
		return nil, false, nil
	}

	currentRepoURL := source.BuildRepoURL(hostname, opts.repo.RepoOwner(), opts.repo.RepoName())
	if existingRepo == currentRepoURL {
		return nil, false, nil
	}

	upstreamRepo, parseErr := source.ParseRepoURL(existingRepo)
	if parseErr != nil {
		//nolint:nilerr // invalid repo URL means we can't redirect; install normally
		return nil, false, nil
	}

	cs := opts.IO.ColorScheme()
	upstreamLabel := ghrepo.FullName(upstreamRepo)
	repoSource := ghrepo.FullName(opts.repo)

	fmt.Fprintf(opts.IO.ErrOut, "%s This skill was originally published in %s\n", cs.WarningIcon(), upstreamLabel)

	if opts.Upstream {
		fmt.Fprintf(opts.IO.ErrOut, "Redirecting install to %s...\n", upstreamLabel)
		return upstreamRepo, true, nil
	}
```
