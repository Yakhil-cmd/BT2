### Title
API-scoped tokens can read CCMenu status for stacks outside their authorized scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces stack-level authorization scoping for `ApiClient` tokens that carry a `stack_id`, but `Api::CCMenuController` overrides the `stack` resolver and bypasses that scoping, letting a stack-scoped token read CCMenu deploy status for any stack.

### Finding Description
`ApiClient` supports being scoped to a single stack (`belongs_to :stack, optional: true`) [1](#0-0) , and this scoping is the authorization boundary that `Api::BaseController` is supposed to enforce for every API endpoint:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

The `stacks` scope restricts a stack-scoped client to only the stack it authorizes, and `stack` looks up `params[:stack_id]` within that restricted scope so an out-of-scope `stack_id` raises `RecordNotFound` (mirrored by the test verifying "an api client scoped to a stack will only see that one stack") [3](#0-2) .

`Api::CCMenuController`, however, redefines `stack` to resolve directly from the unscoped `Stack` model, completely bypassing `current_api_client.stack_id` binding:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

The controller still declares `require_permission :read, :stack` [5](#0-4) , but that check only verifies the token carries the `read:stack` permission string via `ApiClient#check_permissions!`; it never verifies that the specific `stack_id` param matches the stack the token is bound to [6](#0-5) . This breaks the binding: `stack a token authorises` (`current_api_client.stack_id`) `≠ stack it touches` (`params[:stack_id]` resolved against the unscoped `Stack` relation).

### Impact Explanation
A token created with `permissions: %w[read:stack]` and scoped to one stack (as exercised by the `here_come_the_walrus` fixture, which sets `stack: shipit`) [7](#0-6)  can be replayed against `Api::CCMenuController#show` with a different `stack_id` to read deploy status/output for any other stack in the installation, since the controller's `stack` lookup ignores the client's `stack_id` restriction entirely. This is an unauthorized read of stack/deploy state outside the token's authorized scope.

### Likelihood Explanation
Any holder of a stack-scoped, `read:stack`-permissioned API token can trivially trigger this by changing the `stack_id` request parameter; no additional privilege, race condition, or complex setup is required.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so stack-scoped tokens cannot reach stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to Stack A with `permissions: ['read:stack']` (e.g. as done for the `here_come_the_walrus` fixture) [7](#0-6) .
2. Authenticate to `GET /api/stacks/:stack_id/ccmenu` using that token but supply the `stack_id` of Stack B (a different stack the token is not scoped to).
3. `authenticate_api_client` succeeds and `require_permission :read, :stack` passes because the token has `read:stack` [8](#0-7) .
4. `stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scoping [4](#0-3) , and the response renders Stack B's latest deploy status/output — data the token was never authorized to read.
