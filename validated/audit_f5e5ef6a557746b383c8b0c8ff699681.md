### Title
Webhook signature verification authenticates the wrong organization relative to the repository actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / HMAC secret to check using `repository.owner.login` (or `organization.login`) from the untrusted JSON body, but the event handlers that actually mutate state (create commit `Status`es, enqueue `GithubSyncJob`, create `Team`/`User` records, etc.) resolve their target `Repository`/`Stack` from a *different* field of the same body: `repository.full_name`. These two fields are never cross-checked, so the "organization whose secret authenticated the request" is not bound to the "repository that gets written to," exactly analogous to `maxSupply`/`currentSupply` being tracked as independent, unsynchronized values in the reported bug class.

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

The secret used is looked up per-organization, and critically, verification is a no-op when that organization has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret` is documented as optional per organization: [4](#0-3) 
and multi-organization configuration (some orgs with secret, some without) is a first-class, documented setup: [5](#0-4) 

Once `verify_signature` passes (because it validated against `repository.owner.login`'s — possibly secret-less — org), the actual handler dispatched by `Webhooks.for_event(event)` resolves the target repository from an *unrelated* payload field, `repository.full_name`, with no re-check against the org used for authentication: [6](#0-5) [7](#0-6) 

So the binding that should hold — `verified_organization == owner(repository_acted_upon)` — is never enforced. An attacker only needs to know (or control) any organization configured on the instance without a `webhook_secret`, set `repository.owner.login`/`organization.login` to that organization's name, and set `repository.full_name` to any *other* repository already tracked as a `Stack` in Shipit. `verify_webhook_signature` returns `true` unconditionally for the spoofed org, and the handler (e.g. `PushHandler`, `StatusHandler`, `MembershipHandler`) then acts on the real target stack: [8](#0-7) [9](#0-8) 

`StatusHandler` in particular lets the attacker forge a `Status` (CI result) with attacker-chosen `state`/`context`/`description` for arbitrary commits of the real target stack, exactly as demonstrated in the existing controller test that posts a `status` payload independent of any binding to the signing org: [10](#0-9) 

### Impact Explanation
This crosses the required "organization that authenticated versus the repository that is written" boundary from the rules. Concretely, an unprivileged external attacker can:
- Forge successful CI `Status`es on arbitrary commits of any stack tracked by the instance, which can gate/trigger continuous deployment or merge decisions that rely on green statuses.
- Force `GithubSyncJob` invocations with an attacker-chosen `expected_head_sha` for arbitrary tracked stacks via the push handler.
- Trigger `membership`/`pull_request` handlers against repositories the attacker does not control, creating spurious `Team`/`User` records or capturing labels used by review-stack provisioning logic.

This can lead to an unauthorized deploy decision being made on the real target stack (status spoofing feeding a continuous-delivery gate), which is explicitly one of the accepted "Critical" impacts.

### Likelihood Explanation
No credentials, session, or GitHub write access are required. All that's needed is: (a) the target Shipit instance hosts more than one GitHub organization, or a single organization configured without a `webhook_secret` (both explicitly supported/documented configurations), and (b) knowledge of that organization's login name (public information) and the target repository's `owner/name` (also public). The attacker sends a single crafted HTTP POST to `/webhooks` with a mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
Bind the authenticated organization to the repository being mutated: after `verify_signature` succeeds, require that `repository.full_name`'s owner segment equals the organization used to select the webhook secret (`repository_owner`), rejecting the request otherwise. Additionally, do not treat a missing `webhook_secret` as an implicit "always verified" for cross-org payload fields — at minimum, log/alert and restrict handlers to only the organization the secret was actually validated against.

### Proof of Concept
1. Shipit is configured with two organizations, e.g. `attacker-controlled-org` (no `webhook_secret` set, matching the documented "optional" secret) and `victim-org` (has a tracked `Stack` for `victim-org/prod-repo`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<commit sha belonging to victim-org/prod-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/prod-repo",
    "owner": { "login": "attacker-controlled-org" }
  }
}
```
3. `verify_signature` looks up `Shipit.github(organization: 'attacker-controlled-org')`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (absent/garbage) `X-Hub-Signature` header — see [11](#0-10) .
4. `StatusHandler` resolves the commit purely by `sha` (no repo/org check) and records a forged "success" status on `victim-org/prod-repo`'s commit — see [9](#0-8) , enabling downstream logic that gates deploys on green status to proceed based on a forged signal.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
