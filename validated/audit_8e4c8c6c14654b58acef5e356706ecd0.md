### Title
Session fixation on GitHub OAuth login — authenticated session is not rotated after login - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` upgrades the *existing* session to an authenticated one by writing `session[:user_id]` and `session[:authenticated] = true`, but never calls `reset_session` (or otherwise rotates the session id) after a successful OAuth login. `reset_session` is only invoked from `#logout`. This breaks the binding between "the GitHub identity that completed OAuth" and "the session/cookie that is subsequently trusted as that user," because the session identifier that becomes authenticated can be one that existed — and was known — before authentication took place.

### Finding Description
The OAuth callback action is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

`sign_in_github` correctly derives the `User` record from the OmniAuth `auth` hash returned by GitHub's OAuth code exchange: [2](#0-1) 

However, the resulting `session[:user_id]`/`session[:authenticated]` values are written into whatever session the browser presented on the request — no `reset_session` call regenerates the session id before granting authenticated status. `reset_session` exists in the codebase only in `#logout`, confirming it was never wired into the login path: [3](#0-2) 

Rails' `CookieStore`/`redis-session-store`-style sessions do not implicitly rotate the session identifier on a plain `session[...] =` write; only an explicit `reset_session` (or `session.regenerate_id` under newer Rails) changes the id. Because Shipit relies on `session[:authenticated]` (consumed by `UserRequiredMiddleware`, per the comment in the callback action) to gate access to authenticated areas, an attacker who can get a victim's browser to adopt an attacker-chosen (or otherwise attacker-known) session id before the victim completes GitHub OAuth ends up with a session that becomes fully authenticated as the victim once the victim logs in — without ever needing the victim's GitHub credentials, `github_access_token`, or any other secret.

### Impact Explanation
This is a classic session-fixation vulnerability, which maps directly onto the "GitHub identity vs. the `User` bound to the session" binding in scope and is explicitly enumerated as a High-impact analog ("session fixation / forced OAuth completion"). If an attacker can seed a victim's session cookie (e.g., cookie tossing from a shared/parent domain, a session id leaked via referrer/logs, or any mechanism that lets the attacker learn/set the session id before login), the attacker's pre-known session id becomes authenticated as the victim's `Shipit::User` after the victim signs in through GitHub. This grants the attacker full access to the victim's authenticated Shipit session — including triggering deploys/rollbacks/tasks and viewing stack state — without ever touching a webhook secret, API client token, or GitHub credential.

### Likelihood Explanation
Exploitation requires the attacker to get a session id into the victim's browser prior to login (a standard fixation precondition, e.g. cookie tossing on a shared parent domain, or the id being observable/settable through some out-of-band channel), then have the victim complete the GitHub OAuth flow. This is a well-understood attack class for apps that don't rotate sessions on login, and no cryptographic secret needs to be broken to carry it out — it relies purely on the absence of session-id rotation in the callback path, which is directly confirmed in the code (`reset_session` present only in `#logout`).

### Recommendation
Call `reset_session` (or `session.regenerate_id` while preserving `omniauth.origin`) at the start of `GithubAuthenticationController#callback`, before writing `session[:user_id]` and `session[:authenticated]`, so a fresh session id is issued at the moment of authentication and any pre-existing (potentially attacker-fixated) session is discarded.

### Proof of Concept
1. Attacker obtains/sets a specific session cookie value in the victim's browser for the Shipit host (e.g., via a subdomain that can set cookies for the parent domain, or by observing an unauthenticated `_session_id` issued by the app and getting the victim to use it, e.g. via a crafted link that carries the cookie via response headers on a same-site subdomain).
2. Victim visits Shipit and completes the GitHub OAuth login flow (`GET/POST /github/auth/github/callback`).
3. `GithubAuthenticationController#callback` sets `session[:user_id]` and `session[:authenticated] = true` on the *same* session id the attacker fixated, since no `reset_session` occurs. [4](#0-3) 
4. Attacker reuses the fixated session cookie and is now recognized by `UserRequiredMiddleware` as the authenticated victim, gaining access to the victim's stacks, deploy triggers, and task history without any credential of their own.
