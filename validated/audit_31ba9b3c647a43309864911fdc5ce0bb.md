### Title
Frontmatter parser silently drops entire `conditions` list on indented key, causing `Rule.conditions == []` and disabling `block` rules - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter`'s hand-rolled YAML parser only recognizes a top-level key when `indent == 0` [1](#0-0) . If the `conditions:` key line (or any top-level key) is indented by even one space, none of the parser's branches match that line or any of its nested `-` list items, so the whole block is silently discarded with no error. This produces `frontmatter` with no `conditions` key, which flows into `Rule.from_dict` leaving `conditions == []` [2](#0-1) , which then makes `RuleEngine._rule_matches` short-circuit to `False` for every input [3](#0-2) , i.e. the rule is permanently a no-op regardless of `action: block`.

### Finding Description
The parser's state machine has three mutually exclusive branches: a top-level key detector (`indent == 0 and ':' in line`), a list-item detector (`stripped.startswith('-') and in_list`), and a dict-continuation detector (`indent > 2 and in_dict_item`) [4](#0-3) . There is no `else` clause and no fallback/error handling for lines that match none of these — such lines are silently ignored.

Because the top-level-key branch requires `indent == 0` exactly, a `conditions:` line with any leading whitespace never sets `current_key`/`in_list = True`. Consequently, every subsequent `- field: ...` item under it fails the `in_list` guard in the list-item branch and also fails the `in_dict_item` guard in the continuation branch, so those lines are dropped too. The end result is that `frontmatter` never gets a `conditions` entry at all, even though the file author wrote N intended condition dicts. `Rule.from_dict` then leaves `conditions = []` (and falls through to the legacy `pattern` field, which is typically absent in a conditions-based rule) [5](#0-4) . No exception is raised anywhere in this path (`load_rule_file` only catches parsing exceptions, but this failure mode raises none) [6](#0-5) , so the rule loads "successfully" but is permanently inert: `RuleEngine._rule_matches` returns `False` on the very first check due to the `if not rule.conditions: return False` guard [7](#0-6) .

Rule files (`.claude/hookify.*.local.md`) are ordinary repository content — they can arrive via a plugin install, a shared config, or a pull request adding/editing a security guardrail (e.g., "block `rm -rf`" or "block `curl | sh`"). An attacker (or a careless contributor) supplying such a file with one stray leading space before `conditions:` produces a file that is visually indistinguishable from a working blocking rule in a code review, yet it never blocks anything and prints no warning to indicate the rule is broken.

### Impact Explanation
This is a silent security-control bypass: a rule file intended to `block` dangerous Bash commands (or dangerous file edits) is rendered completely inert without any diagnostic output. A reviewer or user who reads the rule's YAML/markdown and its `action: block` field would reasonably believe the guardrail is active, when in fact `RuleEngine.evaluate_rules` will never place it into `blocking_rules` for any input [8](#0-7) . This directly undermines the hookify plugin's core trust boundary (its only job is to intercept and block dangerous tool calls), enabling dangerous commands to execute that the maintainer believed were blocked.

### Likelihood Explanation
Trivial to trigger — it requires only a single leading space before a top-level key in a hookify rule's YAML-like frontmatter, which is a natural typo/formatting variance (e.g., from an editor auto-indent, copy-paste from a nested example, or a crafted PR). No special privileges, secrets, or social engineering beyond a normal PR/plugin contribution are needed. The failure is completely silent (no stderr warning, no exception), making it highly likely to go unnoticed and highly repeatable/deterministic given the exact input.

### Recommendation
Rewrite `extract_frontmatter` to use a real YAML parser (e.g., `yaml.safe_load`) instead of a hand-rolled indentation state machine, or at minimum: (1) normalize/strip leading indentation robustly rather than requiring `indent == 0`, (2) add an explicit `else` branch that raises/logs a parse error for any line matching none of the recognized patterns, and (3) add a post-load invariant check in `load_rule_file`/`Rule.from_dict` that warns (or refuses to load) when `action == 'block'` but `conditions == []` and no legacy `pattern` is present, since a block rule with zero conditions is inherently a misconfiguration.

### Proof of Concept
Unit test for `extract_frontmatter`/`Rule.from_dict`:
```python
content = """---
name: block-rm-rf
enabled: true
event: bash
action: block
 conditions:
  - field: command
    operator: regex_match
    pattern: "rm -rf"
---
Dangerous rm -rf blocked!
"""
fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Expected (intended) behavior: 1 condition present
assert len(rule.conditions) == 1

# Actual behavior with the bug: conditions is empty
# assert rule.conditions == []  # demonstrates the defect

engine = RuleEngine()
result = engine.evaluate_rules([rule], {
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"}
})
# Expected: result contains a "deny"/block decision
# Actual: result == {} because _rule_matches short-circuits on empty conditions
assert result != {}
```
A fuzz test should generate `conditions:` blocks with N randomized valid dict items (N ∈ [1,5]) and randomize the leading indentation of the top-level `conditions:` key line between 0 and 3 spaces, then assert `len(Rule.from_dict(extract_frontmatter(content)[0], "").conditions) == N` for every indentation value — this assertion fails whenever indentation ≠ 0.

```python
def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
    except UnicodeDecodeError as e:
        print(f"Error: Invalid encoding in {file_path}: {e}", file=sys.stderr)
        return None
    except Exception as e:
        print(f"Error: Unexpected error parsing {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
        return None
```
