### Title
Integer-overflow-style precision loss in indivisible-asset denomination cap validation allows supply inflation - ([File: validation.js])

### Summary
`validateAssetDefinition` computes the total capped supply of a fixed-denomination asset by multiplying two attacker-controlled, unbounded "integers" (`count_coins` and `denomination`) and summing the results as ordinary JS floating-point numbers, then compares that sum against the declared `cap`. Because JS numbers are IEEE-754 doubles, this multiplication/summation can silently lose precision (the JS analog of a native integer overflow) once the true product exceeds `Number.MAX_SAFE_INTEGER` (2^53), letting a crafted denomination table pass the "cap matches sum of denominations" check while the real, mathematically exact issuable supply differs from the validated cap.

### Finding Description
In `validateAssetDefinition` (validation.js), for each entry in `payload.denominations`: [1](#0-0) 
- `denomInfo.denomination` is checked only with `isPositiveInteger` and is bounded by `MAX_CAP` **only** when `mci >= constants.pemCurvesFixMci` (a conditional, historically absent guard): [2](#0-1) 
- `denomInfo.count_coins` is checked only with `isPositiveInteger`, with **no upper bound at all**: [3](#0-2) 
- `isPositiveInteger`/`isInteger` merely check `Number.isFinite` and `Math.floor(x) === x`; they do not reject huge doubles (e.g. `1e20`), which trivially satisfy `Math.floor(x) === x` even though they cannot represent every integer value exactly: [4](#0-3) 
- The running total is accumulated as a plain JS float: `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;` and later compared for exact equality against `payload.cap`: [5](#0-4) 

Because `count_coins` has no upper bound and `denomination` is unbounded pre-`pemCurvesFixMci` (and even post-fix is only capped at `MAX_CAP`, still large), an attacker who defines the asset (asset issuer, an unprivileged unit poster) can choose `count_coins`/`denomination` pairs across multiple denomination entries such that:
1. Each individual `denomInfo.denomination` and `count_coins` passes its own bound check.
2. The floating-point sum `total_cap_from_denominations` rounds, due to double-precision loss, to a value that collides with an attacker-chosen `cap` that is itself a legitimate, `MAX_CAP`-bounded number.

This breaks the invariant the code intends to enforce — that the declared `cap` for a fixed-denomination asset equals the exact sum of `denomination × count_coins` across all denominations. Downstream, `count_coins` is the value other code paths rely on to bound how many coins of a given denomination can ever be issued (`indivisible_asset.js`, `storage.js`, `writer.js` all reference `count_coins`). If the validated/declared `cap` no longer matches the true mathematical total implied by the denomination table, nodes constructing or validating indivisible-asset issuances against this asset definition can end up with a mismatched notion of the asset's true maximum supply, which is exactly the bug class described in CVE-2021-30952 (integer overflow from insufficient input validation leading to memory/logic corruption) — here manifested as a numeric-precision overflow in a financial invariant.

### Impact Explanation
This is reachable by any asset issuer posting an `asset` definition message — no privileged role required. If exploited, it allows the sum-of-denominations cap check to be defeated, meaning the asset's declared `cap` (used by other nodes/wallets to reason about maximum supply) does not actually bound the sum of per-denomination coin allotments correctly. This is a supply-integrity violation for a capped indivisible asset, matching the "asset issuance ... supply inflation" impact category.

### Likelihood Explanation
Exploiting IEEE-754 double rounding to force two different computations to coincide is a known, practical technique (not a theoretical corner case) once operands routinely exceed `Number.MAX_SAFE_INTEGER`; here `count_coins` is fully unbounded and `denomination` can be very large, especially for units defined before `pemCurvesFixMci`. Constructing a colliding pair of denomination-table entries requires only ordinary floating-point math (no cryptographic difficulty) and a single asset-definition message.

### Recommendation
- Enforce hard upper bounds on both `denomInfo.denomination` and `denomInfo.count_coins` (e.g., both ≤ `constants.MAX_CAP`) unconditionally, not gated by `pemCurvesFixMci`.
- Compute `count_coins * denomination` and the running total using an arbitrary-precision/BigInt or `Decimal` type (as already used elsewhere in the codebase, e.g. `formula/evaluation.js`), and only cast to a JS number after confirming the exact value is representable and ≤ `MAX_CAP`.
- Reject the asset definition if any intermediate or accumulated product cannot be exactly represented as a JS safe integer.

### Proof of Concept
Conceptually: pick `count_coins`/`denomination` value pairs (each individually valid per `isPositiveInteger` and, if `mci` is below `pemCurvesFixMci`, unbounded by `MAX_CAP`) such that the true product of one denomination row is astronomically larger than a second, and the JS float sum of all rows rounds (due to 53-bit mantissa precision loss) to equal an attacker-chosen `cap` value that itself is a normal, in-range number. Post this as the `outputs`/`asset` payload of a unit defining a `fixed_denominations` asset; `validateAssetDefinition` at validation.js:2778-2791 will accept it because `total_cap_from_denominations === payload.cap` numerically, even though the exact mathematical sum differs — the code path never verifies exactness, only IEEE-754 equality.
