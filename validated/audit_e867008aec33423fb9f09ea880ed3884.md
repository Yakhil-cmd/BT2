### Title
Unhandled `MathOverflow` panic in interest accrual permanently freezes a saturated market — every verb panics, suppliers' funds are locked forever - (File: contracts/pool/src/cache/scale.rs)

### Summary
Like the Multer crash (an unhandled exception on a reachable path that takes down the process), the pool's interest accrual contains an unchecked-result conversion that panics with `GenericError::MathOverflow` when a market's RAY-scaled debt/supply value crosses `i128::MAX` — which happens *before* the `MAX_BORROW_INDEX_RAY` (10^36) index cap engages. Because `interest::global_sync` runs at the top of every mutating pool entrypoint (`supply`, `withdraw`, `borrow`, `repay`, `seize`, `flash_loan`, `claim_revenue`, `net_settle`, `recapitalize`), once the value ceiling is hit every subsequent call on that market panics. The market is permanently bricked: no repayment, no withdrawal, no liquidation, no recapitalization. All supplier funds in that market are frozen forever.

### Finding Description
Every market mutation follows `Cache::load → interest::global_sync → mutate → guards → commit` (contracts/pool/README.md:159-167). Accrual computes unscaled values via `scaled_to_original`/`mul_div_half_up` in `contracts/pool/src/cache/scale.rs`, which panics via `panic_with_error!(env, GenericError::MathOverflow)` when the `i128` result overflows (common/src/math/fp_core.rs:108-118).

The borrow index is capped at `MAX_BORROW_INDEX_RAY = 1e36`, but the value ceiling `i128::MAX ≈ 1.7e38` is only ~170× the 1e36-ray value of a 1-billion-whole-token market. On an 18-decimals market at the XLM curve's steep segment (~98% utilization), the index grows past 170× and the next accrual overflows — so the panic fires *before* the index cap can stop growth. The repository's own test demonstrates the resulting permanent freeze: `update_indexes`, `withdraw`, and `repay` all revert with `MathOverflow`, and the test notes "Every verb accrues first, so the market freezes: no repay, no withdraw, no liquidation. The index cap never engages" (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-356).

Reachability is fully unprivileged: the token-to-RAY input maximum is ~170 billion whole tokens (`i128::MAX / 10^(27-d)`, docs/reference/formulas.md:429), so an attacker can `supply` ~1 billion tokens and `borrow` ~98% through the controller's public `supply`/`borrow` entrypoints with collateral in another market. The panic then triggers on the next accrual — callable by anyone via `update_indexes` — and permanently poisons the market, since accrual is not optional and no recovery entrypoint bypasses `global_sync`.

### Impact Explanation
Permanent freezing of funds. Once the market's RAY-scaled value exceeds `i128::MAX`, every pool verb on that market panics during accrual, including `recapitalize` and liquidation-driven `seize`. There is no administrative or governance path that skips accrual, so all supplied principal and accrued yield in the market is locked forever — matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Requires whale-scale capital (~a billion whole tokens of an 18-decimal asset, within the protocol's own admitted cap domain) plus collateral to open a ~98%-utilization borrow, and sustained accrual at the curve's steep segment until scaled value crosses `i128::MAX`. The repo's test shows this occurs after on the order of years at 200%-cap APR and never at the index cap. Because the state is permanent once crossed and any caller (including the attacker via `update_indexes`) can trigger the fatal accrual, the cost is capital and time rather than privilege — consistent with Medium severity under the Critical/High/Medium-only rule. Note: docs/reference/formulas.md:434-437 documents value overflow as an arithmetic limit, which may weigh toward a documented-limitation rejection, but the permanent freeze is a concrete loss scenario, not an explicit ADR trade-off.

### Recommendation
Make accrual saturate rather than panic: in `contracts/pool/src/cache/scale.rs`'s unscaling path (and the `mul_div_*` calls used by `interest::global_sync`), clamp the computed value to `i128::MAX` — mirroring `mul_div_floor_saturating` (common/src/math/fp_core.rs:180-201) — or clamp the borrow index earlier so scaled values provably stay inside `i128` before value overflow. Alternatively, add a guarded accrual path for exits/liquidations that caps the index at the point where unscaling still fits, so repayment and withdrawal can proceed even after the ceiling is reached.

### Proof of Concept
See the repository's own regression test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361):

1. Attacker supplies `BILLION * 10^18` base units of an 18-decimal market (within cap after `lift_caps`), supplies collateral elsewhere, borrows 98% (`t.borrow_raw(ALICE, "BIG18", debt)`).
2. Time advances at high utilization; eventually `t.try_update_indexes_for(&["BIG18"])` returns `Err(MathOverflow)` — an unprivileged call that bricks the market.
3. Assertions prove permanence: `t.try_withdraw_raw(BOB, "BIG18", 1)` → `MATH_OVERFLOW`, `t.try_repay(ALICE, "BIG18", 1.0)` → `MATH_OVERFLOW`, and `last.borrow_index < MAX_BORROW_INDEX_RAY` confirms the value cliff precedes the index cap, so accrual keeps overflowing on every call — repay, withdraw, and liquidation are all permanently dead.
