### Title
Cross-organization CI status forgery via `StatusHandler` breaks the webhook-org-authenticated / repository-written binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the secret configured for the organization named in the payload, but the `status` event handler applies the verified payload to *any* commit in the entire Shipit install matched only by `sha`, without checking that the commit's stack/repository belongs to the organization whose secret validated the request. This breaks the required binding: `organization authenticated by signature == repository/stack written to`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate the signature against using a field taken directly from the untrusted request body: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, i.e. attacker-controlled content of the raw body that is itself covered by the HMAC. This only proves the request was signed with *some* configured organization's `webhook_secret` — the organization named by that same attacker-supplied field. Nothing then re-checks that the resource the event handler subsequently writes to actually belongs to that authenticated organization.

The dispatched `status` event handler ignores the repository entirely: [3](#0-2) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Unlike `PushHandler` and `CheckSuiteHandler`, which scope their effects through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [4](#0-3) 

`StatusHandler` never calls `stacks`/`repository_name` at all, so it matches on `sha` globally across every `Commit` row in the database, regardless of which `stack`/`Repository`/organization owns that commit.

Consequently, anyone who possesses a legitimate `webhook_secret` for **any** organization/App configured in this Shipit instance (a normal, low-privilege capability for organization admins in a multi-org deployment, since `Shipit.github(organization:)` supports per-organization apps/secrets) can sign an arbitrary `status` payload with `repository.owner.login` set to their own org (so `verify_signature` passes), while setting `sha`, `state`, `target_url`, `description`, and `context` to values that target a commit belonging to a **completely different** organization's stack — because `StatusHandler#process` never checks which repository/organization the matched `Commit` actually belongs to.

### Impact Explanation
`Commit#create_status_from_github!` feeds directly into `Commit#status`/`Status::Group`, which drives `deployable?`: [5](#0-4) 

```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
```

and `add_status` triggers `stack.schedule_merges` and continuous delivery when the injected status transitions to `success`: [6](#0-5) 

An attacker who holds only their own organization's webhook secret can therefore forge a `success` CI status for a commit that belongs to an unrelated victim organization's stack, marking it `deployable?` and, if `continuous_deployment?` is enabled, causing Shipit to auto-merge/auto-deploy that commit — an unauthorized deploy triggered purely by a cross-organization identity mismatch that the engine's own signature-verification logic fails to bind to the write target. This matches the "unauthorized deploy" High/Critical impact category (escalation across organization boundary into deploy/merge decisions).

### Likelihood Explanation
Exploitability requires only holding a valid `webhook_secret` for *some* organization app configured on the shared Shipit instance — a routine, low-privilege capability in any multi-tenant Shipit deployment (each org's GitHub App admin has this secret by design) and not a privileged Shipit account, `ApiClient` token, or `github_access_token`. No repository write access to the victim organization is required. The only additional requirement is that the victim commit's `sha` is known/guessable (SHAs are routinely public in commit histories, PR pages, CI logs, etc.), so likelihood is moderate-to-high in any environment hosting multiple organizations behind one Shipit instance.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository authenticated by the webhook (via `stacks`, as `PushHandler` and `CheckSuiteHandler` already do), e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`. More generally, `WebhooksController#verify_signature` should ensure the organization used to validate the signature is cross-checked against the repository/stack that every handler subsequently mutates, rather than trusting an attacker-supplied field in the same unauthenticated body to select the verification key.

### Proof of Concept
1. Attacker controls (or is an admin of) `attacker-org`, which has a legitimately configured Shipit GitHub App with a known `webhook_secret`.
2. Victim organization `victim-org` has a Shipit-tracked stack/repository with a pending commit `abc123...` awaiting a passing CI status before merge/deploy.
3. Attacker crafts a JSON body:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully validates the signature (it is a legitimately signed request for `attacker-org`).
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: 'abc123...')` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged `success` status onto `victim-org`'s commit, potentially making it `deployable?` and triggering auto-merge/continuous deployment.
