### Title
Asset definer can freeze already-held tokens of a `spender_attested` asset at will, with no timelock, via unrestricted `asset_attestors` updates - (File: validation.js)

### Summary
For any asset created with `spender_attested: true`, the asset definer alone controls the list of "attestors" whose attestations determine which addresses are allowed to hold/spend the asset. The definer can replace this attestor list at any time, in a single unit, with no delay or timelock, and every subsequent payment validation immediately enforces the new list against pre-existing balances. A holder who was previously attested (and legitimately received/held funds) can be silently frozen out the moment the definer publishes a new attestor list that excludes the attestors who vouched for that holder — mirroring the "chain owner can rug pull user funds via a single unrestricted privileged call" pattern from the referenced report, but here applied to fund freezing/loss instead of direct fund extraction.

### Finding Description
When defining an asset, `spender_attested` assets require ongoing attestor-list maintenance controlled exclusively by the `definer_address`: [1](#0-0) 

`validateAttestorListUpdate` only checks that the sole author is the asset's `definer_address` and that the attestor list is well-formed — there is no cooldown, timelock, minimum-notice period, governance quorum, or protection for addresses that are already holding balances of the asset.

This attestor list is then used at spend-time to authorize every input and output address of a `spender_attested` asset: [2](#0-1) [3](#0-2) [4](#0-3) 

Because the check is evaluated against the *current* (last-ball-stable) attestor list rather than the list that was in effect when the holder acquired the funds, the definer can retroactively strip attestation from a previously-attested holder simply by publishing a new `asset_attestors` message that drops that holder's attestor(s) — instantly turning any of that holder's outstanding coins into unspendable, permanently frozen balances. Conversely a spender_attested asset with `issued_by_definer_only` still lets the definer re-attest itself and re-issue, so the definer's own funds are never trapped — only third-party holders are exposed.

`readAsset`/`loadAssetWithListOfAttestedAuthors` always resolve to the latest stable attestor list at validation time, confirming there is no grandfathering of previously valid attestations: [5](#0-4) 

### Impact Explanation
This lets a single unprivileged-but-trusted actor (the asset issuer/definer — reachable by anyone who issues a `spender_attested` asset, exactly the "asset issuer" role explicitly in scope) unilaterally and instantly freeze other users' already-received funds in that asset, with zero notice or delay. This is a direct "AA/asset fund loss or freezing" impact, matching the accepted impact categories, and is architecturally the same root cause as the referenced finding: an unrestrained, non-timelocked privileged action (`getFunds()` there, `asset_attestors` update here) that can be exercised against funds users already hold, damaging trust in any oscript-based product (DeFi/DEX/AA) built on top of `spender_attested` assets.

### Likelihood Explanation
Likelihood is Medium: it requires the asset's own definer to act maliciously or carelessly (analogous to the SKALE chain-owner/admin precondition explicitly accepted at Medium severity by the C4 judge), but no cooperation from any other party, hub, or node operator is needed — the definer alone can post a single `asset_attestors` unit at any time to freeze arbitrary previously-attested holders.

### Recommendation
Consider adding either: (1) a timelock/delay before an `asset_attestors` update takes effect against payments involving addresses that were attested under the previous list, or (2) grandfathering — validating spend authorization against the attestor list in effect at the time the spent output was created rather than the current list, so that funds already legitimately acquired cannot be retroactively frozen by later definer action.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true`, initial `attestors: [X]`.
2. Attestor X attests address `H` (a normal user).
3. Definer (or via an AA using this asset) sends/issues asset A tokens to `H`; validation passes because `H` is in `arrAttestedAddresses` (validation.js:2115-2121).
4. Definer posts an `asset_attestors` message for asset A with a new list that no longer includes attestor `X` (or an attestor list that never attests `H`) — this is accepted per `validateAttestorListUpdate` (validation.js:2829-2848), the only check being that the definer is the sole author.
5. `H` attempts to spend the previously received tokens. `validatePayment` recomputes `arrAttestedAddresses` from the *new* list, `H` is no longer included, and the spend fails with `"owner address is not attested"` (validation.js:2118-2119, 2432, 2506) — `H`'s funds are now permanently frozen, at the definer's sole discretion and without any warning period.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
