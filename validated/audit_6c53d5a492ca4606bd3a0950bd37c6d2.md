### Title
Webhook signature verification is keyed on `repository.owner.login` while event handlers act on the unrelated `repository.full_name` field, allowing an unauthenticated cross-repository/cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks which `GitHubApp`'s HMAC secret to check the request against using the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), while the actual handlers dispatched in `#create` act on a completely independent attacker-controlled field, `repository.full_name`. Because a GitHub App's `webhook_secret` is documented as optional, any organization configured without one causes `GitHubApp#verify_webhook_signature` to unconditionally return `true`. This lets an unauthenticated caller pick an unsecured/no-secret organization for the "authenticating" field while pointing the "acting" field (`repository.full_name`) at a completely different, secured stack/repository, breaking the binding between the organization that authenticated the webhook and the repository that is actually written.

### Finding Description
`verify_signature` resolves the organization purely from the payload: [1](#0-0) [2](#0-1) 

The signature check itself is a no-op when the resolved app has no configured secret: [3](#0-2) 

`webhook_secret` is explicitly documented as optional per organization, and multi-organization Shipit deployments configure a separate `GitHubApp` (and separate `webhook_secret`) per top-level organization key: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (either because the selected org has no secret, or any other bypass), `#create` re-parses the exact same attacker-supplied body and dispatches it to event handlers keyed only by event type - it never re-checks `repository.owner.login` against anything: [6](#0-5) 

The handlers resolve the *actual* target of the mutation using `repository.full_name`, a field completely independent of `repository.owner.login`: [7](#0-6) [8](#0-7) 

Because nothing enforces `repository.owner.login == owner-portion-of(repository.full_name)`, an attacker can craft a JSON body where `repository.owner.login` (or `organization.login`) names an organization configured in Shipit without a `webhook_secret` (satisfying/bypassing `verify_signature`), while `repository.full_name` names an entirely different, secured organization/repository whose stacks actually get mutated (push-triggered sync, commit status updates, PR review-stack archive/unarchive/create, check-suite refresh, etc.).

**Binding broken:** *organization that authenticated* (`repository.owner.login` used to select the verifying `GitHubApp`) `≠` *repository that is written* (`repository.full_name` used by every `Webhooks::Handlers::Handler` subclass to locate the `Stack`/`Repository` to mutate).

### Impact Explanation
This allows unauthorized cross-repository/cross-organization writes without any credential: an attacker who identifies (or controls) one Shipit-configured organization lacking a `webhook_secret` can forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`) targeting any *other* configured repository's stacks - triggering deploy-relevant state changes such as `stack.sync_github`, commit `Status` creation, PR review-stack archive/unarchive, or team/membership creation - for repositories/organizations they have no relationship with. This matches the "cross-repository writes" / "unauthorized deploy trigger surface" Critical impact bucket, since it can influence which commits are considered deployable and can create/destroy review stacks for a victim organization's repository.

### Likelihood Explanation
Requires only that a Shipit deployment host multiple GitHub organizations and that at least one configured organization omits `webhook_secret` (explicitly documented as optional, so realistic in practice, especially for a freshly-added org during onboarding). No authentication, GitHub App private key, or `webhook_secret` knowledge is needed by the attacker for the org they aren't targeting - they only need to know or guess that one configured org has no secret and any target repo's `full_name`. The `/webhooks` endpoint is public and unauthenticated by design (`skip_before_action :verify_authenticity_token`, no `Shipit::Authentication`).

### Recommendation
Bind the field used to select the verifying `GitHubApp` to the same field used by handlers to determine the mutation target - i.e., derive the verifying organization from `repository.full_name`'s owner segment (or vice versa, require they match) before dispatching to handlers. Additionally, consider making `webhook_secret` mandatory (rejecting configuration/requests when absent) rather than treating an absent secret as "always verified".

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `attacker-org` (no `webhook_secret` set) and `victim-org` (has `webhook_secret`, and owns a tracked repository/stack in Shipit).
2. Send an unauthenticated POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb` lines 24-30, `lib/shipit/github_app.rb` lines 76-83) - regardless of the (possibly missing) `X-Hub-Signature` header.
4. `#create` re-parses the same body and dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` - mutating `victim-org`'s stack state despite the request never being validated against `victim-org`'s secret.

```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
