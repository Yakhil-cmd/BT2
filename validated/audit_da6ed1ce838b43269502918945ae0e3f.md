## Analog Found

### Title
NULL/undefined-property dereference (TypeError) on a valid unit's payment message crashes the full node during dry-run trigger handling - (File: network.js)

### Summary
The xpdf CVE is a NULL-pointer dereference reachable by feeding a crafted-but-otherwise-acceptable file to a stream parser that accesses a field without verifying it exists, crashing the process. The analogous ocore pattern is in `network.js`'s `ifOk` callback of `handleJoint`, which — for units carrying an AA-trigger payment — blindly dereferences `msg.payload.outputs` on every message whose `app === 'payment'`, without checking that `payload` exists.

### Finding Description
When `conf.bDryRunNewTriggers` is enabled, after a unit passes full validation, the code computes the addresses that will receive AA triggers: [1](#0-0) 

```js
if (conf.bDryRunNewTriggers && !conf.bLight && !objJoint.ball && objValidationState.count_primary_aa_triggers) {
    const outputAddresses = objJoint.unit.messages
        .filter(msg => msg.app === 'payment')
        .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
    ...
```

The filter only checks `msg.app === 'payment'`; it does not check `msg.payload_location` or the presence of `msg.payload`. Per protocol, a `payment` message may legitimately have `payload_location: "none"` together with a `spend_proofs` array instead of an inline `payload` — this is exactly how private/asset payments with spend proofs are represented, and `validation.js` explicitly allows and requires this shape: [2](#0-1) 

and unit-level validation confirms `payload` must be *absent* for non-inline payment messages: [3](#0-2) 

So a unit that simultaneously (a) triggers an AA with a public "base" payment message, and (b) carries a second `payment` message for a different asset with `payload_location: "none"` and `spend_proofs` (no `payload` field) is a fully valid, protocol-conforming unit that passes `validate()`. When such a unit is processed in `ifOk`, `msg.payload` is `undefined` for the second message, and `msg.payload.outputs` throws `TypeError: Cannot read properties of undefined (reading 'outputs')` — the same class of bug as the CVE: an unchecked field access on attacker-influenced data causing a crash, rather than a deliberate rejection path.

### Impact Explanation
This code executes inside `ifOk`, declared as `async function(objValidationState, validation_unlock)`. A synchronous throw inside an `async function` becomes a rejected Promise. Because `handleJoint` never attaches a `.catch()` to this async callback's invocation (it is invoked as a plain callback, not awaited), the rejection becomes an unhandled promise rejection. In default Node.js behavior (and unless ocore's `start.js`/main entry explicitly ignores unhandled rejections), an unhandled rejection either crashes the process or leaves the mutex/lock (`validation_unlock()`/`unlock()` were never called) permanently held, since the exception happens before `writer.saveJoint` and `validation_unlock()`/`unlock()`/`callbacks.ifOk()` are reached. Either outcome — process crash or a permanently stuck write-mutex — halts the node's ability to save/relay/confirm any further units, i.e., a denial-of-service reachable by any unprivileged unit poster who can craft a two-message unit (one AA-triggering payment + one spend-proof payment). This matches the required impact class: "a network unable to confirm new units" on any node running with `conf.bDryRunNewTriggers = true`.

### Likelihood Explanation
Likelihood is bounded by the fact that this path is only active when `conf.bDryRunNewTriggers` is truthy and `conf.bLight` is false (full/hub nodes with the feature enabled). Given that, exploitation only requires posting a single ordinary, protocol-valid unit: a payment to an AA address (any positive base amount) plus a second `payment` message on any existing asset spent via `spend_proofs`/private payload — no privileged position, no malicious peer/hub role, and no exotic OS-level input is required, matching the report's requirement of reachability "from a single posted unit."

### Recommendation
Guard the `reduce` to only consider payment messages that actually carry an inline payload, e.g.:
```js
.filter(msg => msg.app === 'payment' && msg.payload && Array.isArray(msg.payload.outputs))
```
Additionally wrap the whole `ifOk` async body (or specifically the dry-run block) in a `try { ... } catch (e) { ... }` that still calls `validation_unlock()`/`unlock()` on failure, so that any future oversight of this kind degrades gracefully (e.g., skips the dry run and logs) instead of crashing the node or leaking a stuck lock.

### Proof of Concept
1. Set `conf.bDryRunNewTriggers = true` on a target full node.
2. Create an address `AA1` that is a valid AA (any trivial AA definition), and post an initial-payment/definition unit for it as usual so it's registered as an AA.
3. Compose a unit `U` with authors of an ordinary wallet address that:
   - Message 1: `app: "payment"`, `payload_location: "inline"`, base-asset payment with an output to `AA1` (this is what sets `objValidationState.count_primary_aa_triggers` truthy).
   - Message 2: `app: "payment"`, `payload_location: "none"`, referencing a previously-issued/held asset the sender owns, together with a valid `spend_proofs` entry (as used for private-asset spends) — no `payload` field present.
4. Sign and submit `U` to the target node (as a normal unprivileged wallet submission, `bPosted = true`).
5. `U` passes `validate()` because both messages independently satisfy `validateMessage`/`validateInlinePayload` rules.
6. In `ifOk`, `objJoint.unit.messages.filter(msg => msg.app === 'payment')` includes both messages; `msg.payload.outputs` throws `TypeError` for message 2, occurring inside the `async` `ifOk` function before `validation_unlock()` is invoked, producing an unhandled promise rejection / stuck write mutex on the target node.

*Note: I could not execute this in a live environment, so I have not empirically confirmed whether ocore's process entry point (outside the indexed files) installs a global `unhandledRejection` handler that would either crash the process or merely log — this affects whether the ultimate impact is a full crash vs. a permanently stuck validation lock (which itself still blocks confirmation of new units via the write mutex). Both outcomes satisfy the required "network unable to confirm new units" impact class.*
