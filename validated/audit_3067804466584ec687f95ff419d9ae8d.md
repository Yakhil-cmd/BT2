### Title
CCMenu URL token authorizes a single stack but touches every stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
The upstream report describes a "trust binding" violated when a token/asset that the system believes is scoped to one entity is actually able to act on another (an upgradeable ERC20 whose supported semantics silently diverge from what the system assumes). The corresponding binding in Shipit is: `stack a token authorises == stack it touches`. `CCMenuUrlController#client` mints an `ApiClient` intended for a single stack's CI status page, but never records that stack on the client, so the resulting `read:stack` token is unscoped and works against any stack.

### Finding Description
`CCMenuUrlController#fetch` builds a per-stack "CCMenu URL" and hands out a token for it: [1](#0-0) 

The `client` method creates (or reuses) an `ApiClient` with `permissions: %w[read:stack]` but **does not set `stack:`**, so `stack_id` is left `nil` on the record. `ApiClient` explicitly allows this (`belongs_to :stack, optional: true`): [2](#0-1) 

`Api::BaseController#stacks`, the scoping helper used by essentially every other API controller, treats a client with no `stack_id` as authorized for **all stacks**: [3](#0-2) 

`Api::CCMenuController` compounds this by not even using the `stacks`-scoped helper: it overrides `stack` to resolve directly from `params[:stack_id]` with no ownership check at all, and it authenticates purely via `params[:token]`: [4](#0-3) 

So the "stack the token was minted for" (encoded only in the URL query string given to the browser) and "the stack the token actually authorizes" are two different things — the model itself has no such binding (`stack_id` is nil), and no controller ever checks it. Any holder of a CCMenu token generated for stack A can substitute any other `stack_id` in the URL/params and read state for stack B, C, etc.

### Impact Explanation
Because the minted token carries `read:stack` and is unscoped, it is accepted by every other controller that only requires `read:stack`, not just `Api::CCMenuController`: `Api::StacksController`, `Api::CommitsController`, `Api::MergeRequestsController`, `Api::OutputsController`, and the `read` actions of `Api::TasksController` (task listing/show): [5](#0-4) 

This grants an unauthorized read of stack state, deploy/task metadata, and (via `OutputsController`) deploy/task output streams across the entire Shipit instance from a single leaked CCMenu URL that a legitimate user was only meant to expose for one CI dashboard integration — matching the "unauthenticated/unauthorized read of stack state, task streams, or deploy output" High-impact category.

### Likelihood Explanation
CCMenu URLs are designed to be embedded in third-party CI-status tools/widgets (their query string carries the auth token in plaintext), so they are inherently more exposed to leakage (browser history, proxies, logs, shared dashboards, CI aggregator configs) than a normal `ApiClient` token created through the authenticated `api_clients` UI. Any authenticated Shipit user with `settings` access to a single stack can generate such a token via `CCMenuUrlController#fetch`, and no special privilege is required to exploit the missing scope once a token is obtained — likelihood is High.

### Recommendation
Set `stack:` explicitly when creating the CCMenu `ApiClient` (`ApiClient.create_with(permissions: %w[read:stack], stack:)`), and make `Api::CCMenuController#stack` (and ideally any client with a non-nil `stack_id`) use the same `stacks`-scoped lookup as `Api::BaseController#stack` instead of `Stack.from_param!` directly, so a stack-scoped token can never resolve a different stack.

### Proof of Concept
1. As an authenticated Shipit user with access to stack `org/repo-a/production`, visit the CCMenu URL flow, causing `GET /ccmenu/org/repo-a/production` → `CCMenuUrlController#fetch` to create/find an `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and `stack_id: nil`, returning a token `T`. [6](#0-5) 
2. Using token `T`, request `GET /api/org/repo-b/production/ccmenu?token=T` (a stack the user was never granted access to). `Api::CCMenuController#authenticate_api_client` accepts `T` via `ApiClient.authenticate`, and `#stack` resolves `repo-b/production` directly with no ownership check. [7](#0-6) 
3. The response renders `repo-b/production`'s build/deploy status. The same token `T` also succeeds against `GET /api/org/repo-b/production/deploys`, `/commits`, `/tasks`, etc., since `stacks` treats a nil `stack_id` client as authorized for `Stack.all`. [8](#0-7)

```ruby
module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }
```
