### Title
Webhook signature is verified against `repository.owner.login` while event routing trusts the unrelated `repository.full_name` field, allowing cross-repository stack writes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
Shipit's webhook signature verification selects which GitHub App/organization secret to check against based on `repository.owner.login` (or `organization.login`), but every event handler subsequently identifies the target `Stack`/`Repository` using the completely separate `repository.full_name` field of the same JSON body. These two fields are never cross-checked for consistency, so a payload whose `repository.owner.login` matches an organization the attacker legitimately controls (and can therefore sign with a valid `X-Hub-Signature`) can carry a `repository.full_name` pointing at a different, victim-owned repository/stack. This breaks the intended binding "the organization whose secret authenticated the request == the repository the request is allowed to mutate."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret using only the owner login found in the payload: [1](#0-0) [2](#0-1) 

This uses `params.dig('repository', 'owner', 'login')` (with a fallback to `organization.login`) purely to look up `Shipit.github(organization: repository_owner)` and verify the HMAC signature with that organization's `webhook_secret`. This is exactly the intended design for multi-tenant/multi-org configurations (`config/secrets.development.example.yml` shows the `github: { someorg: {...}, someotherorg: {...} }` shape), so an attacker who has been granted (or has stood up) their own GitHub organization/App wired into this same Shipit instance possesses a valid `webhook_secret` for *their own* `repository.owner.login`.

Once `verify_signature` passes, `create` dispatches the entire raw payload to the handlers without re-validating that the org used for signing matches the repository actually being acted on: [3](#0-2) 

Every handler resolves the target stack from `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 

For example, `PushHandler` triggers `stack.sync_github` for any stack matching the resolved repository/branch: [5](#0-4) 

and `CheckSuiteHandler` schedules check-run refreshes for commits in stacks resolved the same way: [6](#0-5) 

Because `repository.owner.login` (used for cryptographic verification) and `repository.full_name` (used for authorization/target-selection) are independent, attacker-controlled fields of the same unsigned-until-verified JSON body, an attacker can construct a payload where these two fields disagree: `repository.owner.login = "attacker-org"` (so the signature check passes against the attacker's own configured secret) but `repository.full_name = "victim-org/victim-repo"` (so the handler acts on the victim's stack).

The equality that should hold is:
`organization_that_authenticated_the_signature == organization_owning_the_repository_the_handlers_write_to`

but the code instead enforces only:
`organization_that_authenticated_the_signature == repository.owner.login (attacker-controlled)`
while
`repository_the_handlers_write_to == repository.full_name (also attacker-controlled, independently)`

with no check that `repository.full_name`'s owner segment equals `repository.owner.login`.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" boundary called out as Critical impact: an attacker who legitimately controls a webhook secret for one organization/repository configured on the Shipit instance can forge signed webhook deliveries that drive Shipit's internal state (triggering GitHub syncs, scheduling deploy-relevant check-run refreshes, creating commit statuses via `StatusHandler`, opening/merging pull-request-driven review stacks via the `pull_request/*` handlers) for a *different* organization's/repository's stacks that they have no legitimate access to. Depending on which handler is exercised, this can desynchronize a victim stack's known commits, spoof check-run/status state used to gate deploys, or manipulate review-stack/merge-queue handlers tied to `repository.full_name`, i.e., an unauthorized influence over another repository's deploy pipeline.

### Likelihood Explanation
Requires the attacker to already have one legitimate, signed webhook channel into the same Shipit instance (their own org/app configuration) — this is realistic for any Shipit deployment onboarding multiple organizations/teams, which is the explicit multi-org support shown in `config/secrets.development.example.yml`. No GitHub App private key, `api_clients_secret`, or session is needed; only knowledge of one's own already-provisioned `webhook_secret`, which by design an org admin has legitimate access to. The forgery itself is a simple crafted JSON body with mismatched `owner.login` vs `full_name`.

### Recommendation
After signature verification, re-derive the authorized organization strictly from `repository.full_name`'s owner segment (or equivalently, derive `repository_owner` once and require the same field be used both for secret selection and for feeding to `Repository.from_github_repo_name` in every handler), rejecting any payload where `repository.owner.login` and the owner segment of `repository.full_name` disagree. Alternatively, look up the target `Repository`/`Stack` first and confirm its owner matches the `repository_owner` used for signature verification before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `attacker-org` and `victim-org`, each with its own App/`webhook_secret` (per the multi-org config format).
2. Attacker crafts a JSON body for a `push` event:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeef",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker signs this exact byte string with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org` [2](#0-1)  loads `Shipit.github(organization: "attacker-org")`, and the HMAC check succeeds because the attacker signed with the correct secret for that org [1](#0-0) .
5. `create` then calls `PushHandler.call(params)` with the full payload [3](#0-2) .
6. `PushHandler#process` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` [4](#0-3)  and triggers `stack.sync_github(expected_head_sha: "deadbeef")` on the victim's stack [5](#0-4) , even though the attacker has no authorization over `victim-org`.

Note: I was unable to fully trace `Shipit.github(organization:)`'s exact multi-org lookup implementation in `lib/shipit.rb` within the remaining tool budget; the analysis assumes it selects a distinct secret per configured organization as documented in `config/secrets.development.example.yml`'s commented multi-org block, which is consistent with all observed call sites (`repository_owner` lookup by organization name).
