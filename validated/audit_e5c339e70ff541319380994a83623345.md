## Title
AA `foreach`/`map`/`filter`/`reduce` complexity/count_ops accounting understates real cost when callback body has zero complexity — analog of the LiquidJS `renderLimit` empty-body bypass - ([File: formula/validation.js])

### Summary
The AA (Autonomous Agent) formula validator's cost accounting for the `foreach`/`map`/`filter`/`reduce` operators charges a flat `1` unit of complexity — instead of `count * funcProps.complexity` — whenever the callback function's own body evaluates to zero complexity, and adds `count * funcProps.count_ops` to `count_ops` which is likewise `0` for a zero-cost callback body. This is structurally identical to the reported LiquidJS bug class: a loop-driving construct whose per-iteration cost accounting is skipped/degenerate when the loop body is trivial (empty or side-effect free from the accounting's point of view), letting the DoS guard (`MAX_COMPLEXITY`/`MAX_OPS`) be satisfied on paper while the actual evaluator (`formula/evaluation.js`) still performs the full iteration count worth of work at execution time.

### Finding Description
In `formula/validation.js`, the static validator computes a `complexity` and `count_ops` budget for every AA formula before it can ever be attached to a definition or trigger-executed. For iteration constructs: [1](#0-0) 

```
readCount(count_expr, (err, count) => {
    ...
    readFuncProps(func_expr, (err, funcProps) => {
        ...
        complexity += (funcProps.complexity === 0) ? 1 : count * funcProps.complexity;
        count_ops += count * funcProps.count_ops;
        ...
    });
});
```

`funcProps.complexity` and `funcProps.count_ops` are derived from statically parsing the callback body via `parseFunctionDeclaration`: [2](#0-1) 

A callback body composed purely of "free" operations from the validator's perspective (e.g. `local_var` references, literals, `otherwise`, `ternary` over already-evaluated locals, or any op the validator does not charge complexity/ops for) can be crafted with `complexity === 0` and `count_ops === 0`. Because of the `(funcProps.complexity === 0) ? 1 : ...` branch, the validator then adds only `1` to `complexity` no matter how large `count` is, and `count_ops += count * 0 = 0`.

At actual evaluation time, `formula/evaluation.js`'s `foreach`/`map`/`filter`/`reduce` handler iterates the real elements of the operand collection with `async.eachOfSeries`, invoking the callback once per element and doing real per-element work (array pushes, object field assignment, `toJsType`/`cloneDeep`, wrappedObject bookkeeping): [3](#0-2) [4](#0-3) 

The number of iterations is bounded only by `arrElements.length <= count` (`readCount`), not by the complexity/`count_ops` limits, which is exactly the LiquidJS pattern: the loop-driving construct (`for`/`foreach`) re-invokes an inner render/evaluate routine once per element, and the per-iteration accounting is elided precisely when the body is judged "empty"/"zero-cost", allowing the attacker to pick an arbitrarily large iteration count while the safety-limit variable (`complexity`/`renderLimit`) is never actually charged proportional to the real work.

### Impact Explanation
`MAX_COMPLEXITY` and `MAX_OPS` are the primary DoS defenses gating what formulas can be included in AA definitions and executed on trigger, exactly as `renderLimit` is documented as LiquidJS's DoS defense. Any address (unprivileged AA author) can define an AA whose formula contains a `foreach`/`map`/`filter`/`reduce` call with a zero-complexity callback body over a large collection (up to whatever `count`/object-size limits allow), causing the AA to pass `validateFormula` cheaply (`complexity` and `count_ops` barely increase) yet consume real CPU/time proportional to the true collection size when any user later sends a trigger to that AA. Because AA evaluation happens synchronously inside unit/trigger validation on every node that processes the triggering unit, this can slow down or stall validation for all nodes (availability impact), matching the CWE-400 classification of the source report. It does not directly cause double-spend, inflation, or fund loss, but it does threaten a node's ability to validate/confirm new units in a timely manner when the AA is invoked, and repeated invocation amplifies the effect across the network.

### Likelihood Explanation
Likelihood is moderate-to-high for a determined attacker: defining and posting an AA is unprivileged (any user can post an AA definition unit), and constructing a callback body that the validator computes as zero-complexity while still doing real per-element work in the evaluator (e.g., relying on default `map`/`filter` behavior that doesn't invoke any charged operator in the body, such as a trivial identity/local-var callback) is plausible given the operator-by-operator complexity model in `validation.js`. The actual bound is the collection size (`count`/array length), which is itself limited elsewhere (object-size / string-length caps), so the real magnitude of the bypass depends on those caps — this could not be fully quantified without executing the code, but the accounting gap itself is clearly present in the source.

### Recommendation
Remove the `(funcProps.complexity === 0) ? 1 : ...` special case in `formula/validation.js` (line 1030) and instead always charge at least `count * max(funcProps.complexity, epsilon-per-iteration-cost)` plus a fixed per-iteration overhead reflecting the minimum unavoidable cost of iterating (array/object bookkeeping, key lookup, `cloneDeep`, etc.) done by `evaluation.js`'s loop, regardless of whether the callback body itself contains zero "chargeable" operators. Likewise ensure `count_ops` is charged with a nonzero per-iteration floor rather than `count * 0`. This keeps the complexity/ops budget an accurate upper bound of real per-iteration work as originally intended by `MAX_COMPLEXITY`/`MAX_OPS`, mirroring the LiquidJS fix of never skipping the per-iteration limiter check regardless of body content.

### Proof of Concept
Conceptual PoC (not executed against the live repo, based on code inspection):
```
$f = ($x) => $x;   // callback body is a bare local_var reference: complexity=0, count_ops=0
$ar = <a large array/collection, up to the max allowed size>;
$r = map($ar, <count>, $f);
```
Per `formula/validation.js:1030`, since `funcProps.complexity === 0`, the AA's total `complexity` only increases by `1` (and `count_ops` by `0`) regardless of `<count>`, so `validateAADefinition`/`validateFormula` (`aa_validation.js:551-571`) will accept an AA whose `map` operates over the maximum allowed collection size essentially for free from the safety-limit's point of view. At execution time, `formula/evaluation.js`'s `map` handler (lines 2345-2469) still performs one `async.eachOfSeries` iteration and callback invocation per actual element, so the AA's real per-trigger execution cost scales with the true collection size — a cost the `MAX_COMPLEXITY`/`MAX_OPS` gate was supposed to bound but does not in this case.
