### Title
Unbounded `attested` attestor list in address definitions causes uncapped-cost validation and repeated DoS-prone attestor filtering - (File: definition.js)

### Summary
The `attested` operator in address/asset spending-condition definitions accepts an arbitrary-length array of attestor addresses (`arrAttestors`) with no upper bound, while the definition's global complexity/op counters treat the whole `attested` clause as a single unit of cost regardless of how many attestors it lists. This mirrors the NFTX report's root cause: an attacker-controlled, unbounded collection is iterated in a hot path without the cost of iteration being reflected in the safety limits meant to bound execution cost.

### Finding Description
`validateDefinition()` in `definition.js` increments `complexity`/`count_ops` once per call to `evaluate()`, i.e. once per opcode node, and enforces `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` on that count. [1](#0-0) 

When the opcode is `attested`, the code only checks that `arrAttestors` is a non-empty array and that every element is a valid address; there is no cap on `arrAttestors.length` and no additional complexity charge for the size of the array: [2](#0-1) 

This is asymmetric with how the same kind of list is treated elsewhere: asset definitions explicitly cap attestor/denomination-like lists via `checkAttestorList` and `MAX_DENOMINATIONS_PER_ASSET_DEFINITION`, and the `in data feed` operator explicitly adds complexity per extra oracle address (`complexity += arrAddresses.length-1`): [3](#0-2) 

No equivalent `complexity += arrAttestors.length - 1` (or a length cap) exists for `attested`. Once such a definition is accepted (a single "op" costs 1 towards `MAX_OPS`/`MAX_COMPLEXITY`), it becomes the permanent spending condition for that address. Every subsequent unit signed by that address re-runs `validateAuthentifiers()`, which evaluates the `attested` branch and forwards the entire attestor array to `storage.filterAttestedAddresses()`: [4](#0-3) 

`filterAttestedAddresses` builds a query using the full attestor list, so its cost scales with the (attacker-chosen, effectively unbounded) size of `arrAttestors`. Because the definition is validated once but evaluated on every future unit from that address (and any unit is validated by every full node that receives it), this is directly analogous to the NFTX `distribute()` bug: an unprivileged actor (anyone defining an address, e.g. a shared-address/AA author or wallet owner) can grow an internal list without bound, and that list is walked/queried on a hot, unavoidable path (unit validation) whose cost is not capped by the safety counters designed for exactly that purpose.

### Impact Explanation
Definitions and their conditions are evaluated by every node validating units signed by (or referencing) the affected address, including witnesses and light-vendor nodes that need to check the definition before accepting a unit into the DAG. A pathologically large `attested` attestor array increases the cost (loop iterations, and the size/complexity of the SQL `IN` clause built in `filterAttestedAddresses`/`readDefinitionByAddress` consumers) of validating every future unit from that address, without being throttled by `MAX_COMPLEXITY`/`MAX_OPS`, which were specifically designed to bound the cost of definition evaluation. In the worst case this degrades validation throughput for units touching that address/asset condition and can be used to grief nodes that must validate such units (e.g., during catch-up or witnessing), a resource-exhaustion condition consistent with "network unable to confirm new units" in that address's usage.

### Likelihood Explanation
Likelihood is limited by the fact that: (1) a normal address definition with a huge `attested` array is unusual and requires the attacker to intentionally construct and register such a definition; (2) unit size limits (`MAX_UNIT_LENGTH`-style caps enforced elsewhere) put a practical ceiling on how large the attestor array embedded directly in a definition/unit can be, since the whole definition/unit payload must fit within normal unit-size constraints. This bounds the attack's severity compared to the NFTX case (where the receiver list could grow indefinitely across many separate transactions). Still, the missing per-element complexity accounting is a genuine gap relative to the pattern used elsewhere in the same file (`in data feed`), and it is reachable by any address definer without special privilege.

### Recommendation
Add an explicit cap on `arrAttestors.length` for the `attested` operator (mirroring `checkAttestorList` used for asset definitions) and charge complexity proportional to the attestor-list size (as already done for `in data feed`'s oracle list, e.g. `complexity += arrAttestors.length - 1`) in both `validateDefinition()` and `validateAuthentifiers()`'s `evaluate()` for the `attested` case. This ensures the MAX_COMPLEXITY/MAX_OPS safety limits actually bound the cost of `attested` clauses proportionally to their size, consistent with how other unbounded collections in definitions are treated.

### Proof of Concept
1. Construct an address definition `['attested', ['this address', arrAttestors]]` where `arrAttestors` contains the maximum number of valid-looking BASE32 addresses that still fits within the unit-size limits for a definition-bearing unit.
2. Post a unit defining an address (or an asset's `spender_attested`/`transfer_condition`) with this definition; `validateDefinition()` accepts it because `complexity`/`count_ops` only increase by 1 for the whole `attested` node regardless of `arrAttestors.length`. [2](#0-1) 
3. Have the address sign and broadcast subsequent units. Each validating node calls `validateAuthentifiers()` → `evaluate()` → case `'attested'`, which passes the full (large) `arrAttestors` array to `storage.filterAttestedAddresses()` on every single validation. [4](#0-3) 
4. Measure the added per-unit validation cost (larger `IN (...)` clause construction/query) across many units from this address, compared to a normal small attestor list, to demonstrate the unbounded, uncharged cost growth.
