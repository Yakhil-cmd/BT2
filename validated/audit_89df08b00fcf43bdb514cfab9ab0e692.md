### Title
Pool creation front-running: attacker can hijack a victim's `initialize`/`initialize_with_permission` call to seize the pool-creator role and set the initial price - ([File: programs/cp-swap/src/instructions/initialize.rs])

### Summary
The pool's identity PDA (`pool_state`) is fully deterministic from public inputs — `amm_config`, `token_0_mint`, and `token_1_mint` — with no submitter-specific salt [2](#0-1) . This mirrors the report's bug class: a value that should uniquely commit to its submitter (the OpenQ `bountyId`) is instead fully attacker-computable and reusable, letting anyone front-run the legitimate submitter for the same slot.

### Finding Description
`create_pool` derives the pool PDA solely from `amm_config`, `token_0_mint`, and `token_1_mint`, and allocates it via `create_or_allocate_account`, failing with `NotApproved` if the account is already allocated [3](#0-2) . Since `token_0_mint`, `token_1_mint`, and the `amm_config_index`-derived `amm_config` are all public, any observer of a pending `initialize` (or `initialize_with_permission`) transaction in the mempool can precompute the exact same PDA and submit their own `initialize` call with the same token pair (but attacker-chosen `init_amount_0`/`init_amount_1`, i.e., attacker-chosen initial price) and land it first.

The instruction sets `pool_state.pool_creator` to whoever's transaction succeeds [4](#0-3) , and the initial liquidity/ratio is derived directly from the caller-supplied `init_amount_0`/`init_amount_1` [5](#0-4) . The `pool_creator` role is not a cosmetic field — it is checked with `address = pool_state.load()?.pool_creator` as the sole signer authorization for `collect_creator_fee`, which sweeps `creator_fees_token_0`/`creator_fees_token_1` accrued from all subsequent swaps on that pool to the creator's own token accounts [6](#0-5) .

Consequently, front-running achieves two effects:
1. **Denial of service**: the victim's original `initialize` transaction reverts with `NotApproved` since the PDA is no longer system-owned.
2. **Value/role hijack**: the attacker becomes the exclusive, permanent `pool_creator` for that token pair at whatever price ratio they choose, and can then claim the ongoing stream of creator fees generated by unrelated future traders/LPs — funds the intended legitimate creator would otherwise have received.

### Impact Explanation
This satisfies the Medium bar of "unauthorized privileged effect": the attacker seizes the privileged `pool_creator` role tied irrevocably to a specific token pair (no way for the legitimate creator to reclaim it, since the pool PDA and mint pair are unique per `amm_config`), diverting future creator-fee revenue from all subsequent swap activity to the attacker. It also forces legitimate pool creators' transactions to fail deterministically, a repeatable griefing vector against any project trying to bootstrap a pool for a known token pair.

### Likelihood Explanation
Highly likely to be exploitable in practice: the pool PDA seeds are fully public before the transaction lands (mint addresses are known ahead of time for any anticipated listing), and Solana's mempool/leader scheduling allows straightforward transaction replication with higher priority fees, requiring no privileged access — any unprivileged actor submitting `initialize`/`initialize_with_permission` can be targeted.

### Recommendation
Bind pool creation to the submitter, e.g., include the creator's pubkey (or a creator-chosen salt/nonce) in the `pool_state` PDA seeds so the same `(amm_config, token_0_mint, token_1_mint)` pair can't be squatted by a different signer, or require the initializer to pre-commit (e.g., via a commit-reveal scheme) so the attacker cannot copy the exact parameters and win the race. At minimum, decouple `pool_creator`/creator-fee rights from "whoever's `initialize` call happens to land first" for a given deterministic PDA.

### Proof of Concept
1. Victim broadcasts `initialize(init_amount_0=X, init_amount_1=Y, ...)` for `(token_0_mint=A, token_1_mint=B)` under `amm_config` index 0.
2. Attacker observes the pending transaction, computes the same `pool_state` PDA via `find_program_address([POOL_SEED, amm_config, A, B])` [7](#0-6) .
3. Attacker submits their own `initialize` call for the same `(A, B, amm_config)` with a higher priority fee and attacker-chosen `init_amount_0`/`init_amount_1`, landing first.
4. Attacker's transaction succeeds: `create_pool` allocates the PDA [8](#0-7) , and `pool_state.initialize(...)` records the attacker as `pool_creator` with the attacker's chosen initial ratio [4](#0-3) .
5. Victim's original transaction now fails at `create_pool`'s `pool_account_info.owner != &system_program::ID` check, returning `NotApproved` [9](#0-8) .
6. Going forward, only the attacker (as `pool_creator`) can call `collect_creator_fee` to sweep accumulated creator fees from all trading on this pool [1](#0-0) .

pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);
    }

    token::create_or_allocate_account(
        &crate::id(),
        payer.to_account_info(),
        system_program.to_account_info(),
        pool_account_info.clone(),
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
            &[bump],
        ],
        PoolState::LEN,
    )?;
