### Title
Cross-tenant `Status` write via SHA-only lookup in `StatusHandler#process` - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` correctly authenticates that a webhook was signed by the GitHub App belonging to the organization named in the payload's `repository.owner.login`, but that authentication only proves who sent the payload, not which `Commit` rows may be mutated. `StatusHandler#process` then resolves the target rows with `Commit.where(sha: params.sha)`, a global query with no repository/stack scoping, so a correctly signed webhook from organization W1 can write a `Status` against a `Commit` that belongs to an unrelated stack/repository R2, as long as the two share the same commit SHA.

### Finding Description
The broken binding, stated explicitly: the binding `repository_owner` (used in `Shipit.github(organization: repository_owner).verify_webhook_signature`, [1](#0-0)  and [2](#0-1) ) is supposed to equal the repository owning every `Commit` mutated by the handler that processes the same payload. It does not: `StatusHandler#process` never re-derives or checks a repository/owner at all — it selects rows purely by `sha`: [3](#0-2) 

`Commit.where(sha: params.sha)` is a table-wide, cross-stack, cross-repository query (no `stack_id`/`repository` predicate). Each matching row then gets `commit.create_status_from_github!(params)` called on it, which appends a `Status` scoped to *that commit's own* `stack_id`, not to any stack tied to the verified `repository_owner`: [4](#0-3) 

Root cause: the webhook signature check authenticates "this payload was signed with the webhook secret configured for org X's `GithubApp`," but the handler that consumes the payload assumes (without verifying) that any commit sharing the claimed `sha` must belong to org X's stack. Commit SHAs are content-addressed and routinely identical across forks, mirrors, or repositories that share history (e.g., a public upstream repo and any of its forks share unmodified commit SHAs). An attacker who legitimately administers their own GitHub organization/repo that is configured in Shipit (and therefore knows/controls the webhook secret Shipit expects for that org, since they set up the GitHub webhook pointing at `/webhooks`) can send a `status` event whose `sha` field is copied from a commit that also exists (unmodified) in a victim repository R2's history. `verify_signature` passes because the signature matches W1's own secret; `drop_unhandled_event` passes because `status` is a handled event; the `ExplicitParameters` schema only requires `sha`/`state` types, not repo identity. `StatusHandler#process` then finds and mutates R2's `Commit` row, appending a `Status` under R2's stack.

Existing guards do not close this gap: `verify_signature` never inspects which stacks/commits will be touched, and no handler-level check exists tying `params.dig('repository', 'full_name')` to the `stack`/`repository` of the commits being matched.

### Impact Explanation
An attacker with a legitimately configured (but otherwise unprivileged) GitHub organization can inject `Status` rows onto arbitrary commits in any other tenant's stack, provided a SHA collision (shared commit) exists — which is common for open-source upstream/fork relationships or any repositories sharing git history. Because `Commit#status` drives `deployable?`, `blocked?`, `schedule_continuous_delivery`, and `Hook.emit(:deployable_status, ...)`, a forged "success" status can make an otherwise-non-deployable commit in R2 appear deployable, potentially triggering continuous deployment or unblocking a merge in a tenant the attacker never authenticated against. This is a cross-tenant data-mutation/authentication-boundary issue matching the Critical category ("a payload for one repository mutating another's ... commit ... unauthorized deploy").

### Likelihood Explanation
Preconditions: the attacker must administer at least one GitHub org/repo that is already configured in Shipit with a known webhook secret (a normal, unprivileged onboarding step for any Shipit tenant), and must find/produce a commit SHA that also exists in a target repository's history (trivial for forks of public repos, or repositories that mirror/vendor commits). No GitHub App private key, `secret_key_base`, or victim's `webhook_secret` is needed. The request is a single POST to `/webhooks` with a valid `X-Hub-Signature` computed from the attacker's own known secret — fully repeatable and scriptable against any SHA the attacker can predict.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving objects purely by `sha`) to commits belonging to the repository asserted in the payload, e.g. join through `Stack`/`Repository` and filter by `repository.owner == repository_owner && repository.name == params.dig('repository','name')` before calling `create_status_from_github!`, rather than matching `sha` globally across all tenants.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status webhook signed for org W1 cannot mutate commit belonging to stack owned by org R2" do
  # Arrange: two stacks/repos with a commit sharing the same sha (simulating a fork/shared-history collision)
  w1_repo = shipit_repositories(:shipit) # configured org with known webhook_secret in test fixtures
  r2_stack = create_stack(repository: create_repository(owner: 'r2-org', name: 'private-repo'))
  shared_sha = 'a' * 40
  r2_commit = r2_stack.commits.create!(sha: shared_sha, author: AnonymousUser.new)

  payload = {
    'state' => 'success',
    'sha' => shared_sha,
    'context' => 'ci/attacker',
    'repository' => { 'owner' => { 'login' => w1_repo.owner }, 'name' => w1_repo.name }
  }.to_json

  before_count = r2_commit.statuses.count

  post '/webhooks', params: payload,
       headers: {
         'X-Github-Event' => 'status',
         'X-Hub-Signature' => "sha1=#{OpenSSL::HMAC.hexdigest('sha1', w1_repo_webhook_secret, payload)}",
         'CONTENT_TYPE' => 'application/json'
       }

  assert_response :ok
  # Binding check: signature was verified for W1's org, yet R2's commit was mutated
  assert_equal before_count + 1, r2_commit.reload.statuses.count
end
```
This demonstrates that a webhook signed with W1's own (legitimately known) secret results in a `Status` write on R2's `Commit`, confirming the divergence between the authenticated `repository_owner` and the repository actually mutated.
