## Title
`pending_delegator_rewards` is never decremented after block-reward distribution, allowing the same deposited reward pool to be redistributed every epoch — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

## Summary
Agave's SIMD-0123 block-revenue-sharing feature lets a `VoteStateV4` account accumulate a `pending_delegator_rewards` balance via `DepositDelegatorRewards`, and each epoch a proportional share of that balance is paid out to delegated stake accounts as `block_reward`. The code that reads and spends `pending_delegator_rewards` to compute the per-stake payout never writes back a reduced value to the vote account, and there is no other mutation site that decrements the field. This mirrors the reported bug class: a cached "amount owed" value is used to authorize a payout but is never reset/consumed, so the same balance can be paid out again in later epochs.

## Finding Description
`add_pending_delegator_rewards` is the only mutator of the `pending_delegator_rewards` field, called from `deposit_delegator_rewards` to increment the balance when lamports are deposited: [1](#0-0) [2](#0-1) 

During epoch-reward calculation, `calculate_block_reward` reads `vote_state.pending_delegator_rewards()` and computes a per-stake share of it (`pending_delegator_rewards * stake / total_active_stake`, clamped to `pending_delegator_rewards`), but only *reads* the value — it never writes an updated (reduced) value back to the vote account: [3](#0-2) 

This function is invoked once per stake delegation, per epoch, inside `calculate_stake_rewards_and_commissions`, using the *same* `pending_delegator_rewards` snapshot cached in `cached_vote_accounts.distribution_epoch_vote_accounts` for every stake account being iterated, and every epoch this calculation runs again from the still-unmodified on-chain field: [4](#0-3) 

The resulting `block_reward` is credited directly to each stake account's lamport balance during distribution: [5](#0-4) 

and the block-reward totals are only used to update the epoch-rewards sysvar bookkeeping and capitalization for burned amounts — capitalization is increased only by `stake_reward_lamports_minted` (inflation), not by `block_reward_lamports_distributed`, implying the design assumes the block-reward lamports are debited from the vote account's already-deposited balance: [6](#0-5) 

I searched exhaustively for any statement that decrements `pending_delegator_rewards` or debits the vote account's lamports in the calculation/distribution path (`checked_sub` on the field, subtraction assignment, or a corresponding lamport debit in `distribution.rs`/`calculation.rs`) and found none — the only place `pending_delegator_rewards` is decremented at all is in `withdraw`, which merely uses it as a *reserve floor* to prevent withdrawing below it, not to consume it: [7](#0-6) 

Because the field is never reduced (and the vote account's lamports are never explicitly debited by the amount distributed as `block_reward`), the exact same `pending_delegator_rewards` balance is available to be redistributed as `block_reward` again on every subsequent epoch boundary for as long as `block_revenue_sharing` is active and the vote account remains delegated — a direct analog of "cached reward never reset, so it can be claimed multiple times."

## Impact Explanation
Each epoch, delegated stakers can receive a "new" block-reward payout computed from a `pending_delegator_rewards` figure that was never reduced by the previous epoch's payout. Since stake accounts are credited real lamports via `checked_add_lamports` in `build_updated_stake_reward`, and capitalization accounting in `distribute_epoch_rewards_in_partition` does not appear to debit the vote account or subtract `block_reward_lamports_distributed` from anywhere backing it, this results in lamports effectively being minted/duplicated out of a single deposit across many epochs — a concrete lamport-theft/inflation bug in the reward distribution path, not merely a bookkeeping cosmetic issue.

## Likelihood Explanation
This triggers automatically, without any adversarial input, whenever `block_revenue_sharing` and `custom_commission_collector`/`commission_rate_in_basis_points` features are enabled and any vote account has a non-zero `pending_delegator_rewards` (deposited via the normal `DepositDelegatorRewards` instruction). It requires no privileged validator/operator behavior — it is a pure protocol-logic flaw in every reward-calculation epoch.

## Recommendation
After computing and successfully distributing `block_reward` for a stake delegation in `calculate_block_reward`/`calculate_stake_rewards_and_commissions`, the amount actually distributed for a given vote account must be subtracted from that vote account's `pending_delegator_rewards` field (and the vote account's lamports debited correspondingly) as part of the same epoch's reward-commission/distribution flow, so subsequent epochs only distribute the remaining un-paid balance.

## Proof of Concept
Not independently executed; based on static analysis of the reward-calculation and distribution code paths in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` and `distribution.rs`, exhaustive search found no decrement of `pending_delegator_rewards` or corresponding vote-account lamport debit anywhere in the block-reward computation/distribution flow, only the additive `add_pending_delegator_rewards` mutator used by `DepositDelegatorRewards`.

Note: due to index size limits, some file contents (e.g., the full `redeem_delegation_rewards` implementation and any related vote-account state mutation helper files not indexed) could not be inspected in this session. I recommend starting a full Devin session with complete repository access to confirm there is truly no offsetting decrement/debit logic before treating this as fully validated.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
