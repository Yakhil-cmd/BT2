### Title
`check_suite` webhook signature verified against attacker-chosen `repository.owner.login` while `CheckSuiteHandler` mutates the stack resolved from a different `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using `repository.owner.login` from the JSON body, but `Shipit::Webhooks::Handlers::Handler#stacks` (used by `CheckSuiteHandler`) resolves the target repository/stack using the independent `repository.full_name` field from the same body. Because these two fields are never cross-checked, an attacker who owns/controls a GitHub org with no configured `webhook_secret` can forge a `check_suite` payload that "authenticates" under their own org while acting on any victim stack, including one flagged as a production environment.

### Finding Description
The broken binding is the implicit assumption:
`repository.owner.login == owner(repository.full_name)`

This is never enforced. Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to select the `GitHubApp` instance whose `webhook_secret` verifies the HMAC: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that organization has no `webhook_secret` configured: `return true unless webhook_secret` [3](#0-2) . So an attacker who names an org with no secret configured in `repository.owner.login` gets automatic signature "verification" regardless of the actual `X-Hub-Signature` header.
- After verification, `WebhooksController#create` parses the same raw body and dispatches to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `Handler#stacks` and `Handler#repository_name` resolve the target repository from a *different* field: `payload.dig('repository', 'full_name')` [5](#0-4) .
- `CheckSuiteHandler#process` uses that `stacks` scope, filters by attacker-supplied `params.check_suite.head_branch`, and for matching stacks reschedules check-run refresh for commits matching attacker-supplied `params.check_suite.head_sha`: `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!) }` [6](#0-5) .

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: check_suite`, a body where `repository.owner.login` = an org with no `webhook_secret` set in Shipit config (or an org attacker actually controls and knows the secret for), and `repository.full_name` = `"victim-org/victim-repo"` (the production stack the attacker wants to affect), along with `check_suite.head_branch` matching the victim stack's branch and `check_suite.head_sha` matching a commit on that stack. The signature check passes (verified against the wrong/absent secret), and `CheckSuiteHandler` then queries and mutates the victim's stack/commits keyed off `full_name`, not `owner.login`.

Existing guards do not catch this: `drop_unhandled_event` only checks event type presence, `ExplicitParameters` (`CheckSuiteHandler.params`) only validates `head_sha`/`head_branch` types/presence — not repository consistency, and there is no code anywhere that compares `repository.owner.login` against the owner segment of `repository.full_name`.

### Impact Explanation
This is a cross-tenant payload: a webhook that authenticates as (or is waved through for) organization A causes writes/scheduling against organization B's stack/commits, specifically triggering `schedule_refresh_check_runs!` on commits belonging to a victim production-environment stack. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." The direct effect of `CheckSuiteHandler` is scheduling a check-run refresh job (not directly a deploy/merge), but it demonstrates the underlying primitive — arbitrary handlers keyed by `full_name` are reachable with a signature verified against an attacker-controlled owner — and is repeatable against any repository the attacker can guess/know the `full_name` and branch/SHA for, across all other `check_*`-family or similar handlers that key exclusively off `repository.full_name`.

### Likelihood Explanation
Preconditions: the attacker needs (a) an org name to place in `repository.owner.login` that either has no `webhook_secret` configured in Shipit (`Shipit.github(organization: ...)` config) or one whose secret is known to them, and (b) knowledge of the victim's exact `repository.full_name`, stack `branch`, and a commit `sha` already known/synced on that stack (obtained from public GitHub activity, since these are typically public repo/commit identifiers). No Shipit session, API token, or GitHub App secret is required. This is a single unauthenticated HTTP POST, fully repeatable and scriptable against any stack whose full_name/branch/sha triplet is known.

### Recommendation
Cross-validate `repository.owner.login` against the owner segment of `repository.full_name` before dispatching to handlers, and reject the request if they mismatch. Additionally, `GitHubApp#verify_webhook_signature`'s "trust unconditionally when no secret is configured" behavior should not be used to select which repository's stacks get mutated — the resolved organization used for signature verification must be the same one used to resolve `stacks`/`repository_name` in `Handler`.

### Proof of Concept
minitest (`test/controllers/webhooks_controller_test.rb` style, hypothetical since `test/**` is out of scope for fix but valid for demonstrating the equality break):
1. Configure two orgs in `Shipit.github_configs`: `"attacker-org"` with no `webhook_secret`, and implicitly a victim stack `Shipit::Stack` for `"victim-org/victim-repo"` with `environment: "production"`, `branch: "master"`, and a `Shipit::Commit` with a known `sha`.
2. Assert binding before: `repository_owner == owner(repository.full_name)` should be `"attacker-org" == "victim-org"` → false, i.e., the values already diverge in the crafted payload.
3. POST to `/webhooks` with header `X-Github-Event: check_suite`, no/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "check_suite": {"head_branch": "master", "head_sha": "<victim commit sha>"}
}
```
4. Assert response is `200 OK` (signature verification passed since `attacker-org` has no secret).
5. Assert the victim commit's `schedule_refresh_check_runs!` was invoked / job enqueued, proving a payload "authenticated" under `attacker-org` mutated `victim-org`'s stack — confirming the equality claimed safe (`repository_owner` gates access to `repository.full_name`'s resources) is false.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
