### Title
Membership webhook signature verification keyed on `repository.owner.login` while team/authorization data is taken from a separate, unbound `organization.login` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using `repository.owner.login`, falling back to `organization.login` only if `repository` is absent. `MembershipHandler#process`, however, never reads `repository.owner.login` at all — it independently trusts a separate `organization.login` field in the same JSON body to decide which `Team` gets created/updated and which `User` is added to it. Because these are two different keys in the same attacker-controlled JSON body, and only one of them is covered by the signing organization's secret in a *binding* way (the code never asserts they must be equal), a webhook signed with an organization's own webhook secret can carry a forged `organization.login` pointing at a different, victim organization.

### Finding Description
`verify_signature` derives the signing organization as: [1](#0-0) 
```
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses this to pick the `GitHubApp`/secret used to verify `X-Hub-Signature`: [2](#0-1) 

`MembershipHandler#process`, invoked afterwards on the *same* raw JSON body, reads `params.organization.login` directly — a field that is completely independent from `repository.owner.login` and is never cross-checked against it: [3](#0-2) 

The handler's parameter schema does not even require a `repository` key: [4](#0-3) 

Because `verify_signature` prefers `repository.owner.login` over `organization.login` when both are present, an attacker who legitimately controls a GitHub organization that is *also* integrated with this Shipit instance (and therefore knows/controls that organization's `webhook_secret`) can submit a `membership` event where:
- `repository.owner.login` = their own organization (so the HMAC is verified successfully with a secret they know), and
- `organization.login` = an unrelated, victim organization (e.g. one used in `Shipit.github_teams` for access control).

`MembershipHandler` will then create or reuse a `Team` (keyed by GitHub's numeric `team.id`, via `Team.find_or_create_by!(github_id: params.team.id)`) under the victim's organization name and add an attacker-chosen `member.login` to it: [5](#0-4) [6](#0-5) 

If the targeted `github_id` matches a `Team` record already used to gate access via `Shipit.github_teams`/`oauth.teams`, the attacker's user gets added as a member of that authorization-relevant team: [7](#0-6) [8](#0-7) 

This breaks the trust binding: `organization that authenticated the request` (`repository.owner.login`, resolved to a secret the attacker legitimately knows) `≠` `organization whose team-membership/authorization data is written` (`organization.login`), yet the code treats the latter as fully trusted once the former's signature check passes.

### Impact Explanation
A successful forgery lets an attacker who controls one organization integrated with a multi-tenant Shipit deployment inject `Team`/`Membership` records for a *different* organization, and add themselves (or any GitHub login) to a team. If that team is one of the teams configured in `Shipit.oauth.teams` (used by `User#authorized?` to gate access to the entire Shipit application), this is an escalation into `Shipit.github_teams` authorization — one of the explicitly in-scope High-severity impacts.

### Likelihood Explanation
This requires the attacker to be a legitimate administrator/webhook-secret holder of *some* organization onboarded to the same Shipit instance (a realistic scenario for shared/multi-tenant deployments where many orgs' GitHub Apps point at one Shipit host), plus knowledge or discovery of the target team's numeric GitHub `team.id` (which may be enumerable/discoverable via GitHub's public APIs or leaked in prior webhook traffic). It does not require the victim organization's `webhook_secret`, a Shipit session, or an `ApiClient` token — only a webhook secret the attacker is legitimately entitled to for their own org.

### Recommendation
Bind the organization used for signature verification to the exact organization used by every handler for writes. Concretely:
- In `MembershipHandler`, cross-validate `params.organization.login` against the organization actually used to verify the signature (pass the verified organization from the controller into the handler, or require `repository.owner.login`/`organization.login` be identical and use only one canonical field for both signing-secret selection and business logic).
- More generally, do not let webhook handlers read organization/repository identifiers from fields that were not the ones used to select the verifying secret.

### Proof of Concept
1. Attacker's own org `attacker-org` is installed on the shared Shipit instance with a known `webhook_secret_attacker`.
2. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_attacker, body)` for the following body:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. POST to `/webhooks` with header `X-Github-Event: membership` and the computed signature.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies successfully using `webhook_secret_attacker` (known to the attacker). [2](#0-1) 
5. `MembershipHandler#process` runs, using `params.organization.login` = `"shopify"` and `params.team.id` = `<victim_team_github_id>`, adding `attacker` to that team. [9](#0-8) 
6. If that team is part of `Shipit.oauth.teams`, `attacker`'s Shipit `User#authorized?` now returns `true`, granting access to the Shipit application.

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
