### Title
DoS of AA "send-all" asset payments via unbounded dust-output aggregation with no size cap for non-base assets - (File: `aa_composer.js`, `validation.js`)

### Summary
Mellow's M-7 shows the general bug class: aggregating token balances across a set of unfiltered sources (subvaults) and forcing an operation to touch *all* of them lets an attacker with a trivial, unprivileged deposit make future legitimate operations revert, freezing funds. In `ocore`'s Autonomous Agent (AA) engine, the same class of bug exists when an AA composes a "send-all" payment in a non-base asset: the code that gathers the AA's spendable outputs for that asset applies no minimum-amount (dust) filter — unlike the base-asset case, which explicitly filters dust — and the "send-all" loop is required to consume every matching output to compute the correct total. Combined with the fact that the "too many inputs" validation limit is explicitly bypassed for AA-generated units, an unprivileged attacker can flood an AA address with many minimal-amount outputs of a targeted asset, permanently breaking that AA's ability to compose a valid "send-all" response for that asset (unit becomes oversized / cannot be completed), causing indefinite freezing of the AA's asset funds — mirroring the "DoS in redemption due to unchecked asset aggregation" pattern from the source report.

### Finding Description
When an AA response contains a payment message whose output has no explicit `amount` (the oscript "send all of this asset" idiom), `completePaymentPayload()` in `aa_composer.js` must sum up *every* unspent output of that asset sitting at the AA's address in order to compute the correct total to send. This traversal is driven by `readStableOutputs()`/`readUnstableOutputsSentByAAs()`: [1](#0-0) 

Note the dust-filtering asymmetry in the WHERE clause: for the **base asset** a minimum amount (`amount>=FULL_TRANSFER_INPUT_SIZE`) is enforced specifically "to prevent dust attack: spamming the AA with very small outputs", but for **any other asset** (`asset=...`) there is no minimum-amount condition at all — every output, no matter how small, is selected.

The consumption loop that drives the aggregation does not stop early when a `send_all_output` is present — it must iterate through every row returned to correctly compute the total balance: [2](#0-1) 

Normally, the number of inputs a payment message may contain is capped: [3](#0-2) 

However this cap is explicitly skipped for AA-authored units (`!objValidationState.bAA`), so nothing in validation prevents an AA-generated payment from consuming an unbounded number of tiny asset inputs that were forced onto it during composition.

### Impact Explanation
Because dust filtering is absent for non-base assets and the input-count safety valve is disabled for AAs, an unprivileged attacker can post many minimal-value transfers of an arbitrary asset to any AA address. Any AA that later performs a legitimate "send all of asset X" response (a common oscript pattern, e.g. paying out a full balance to a user) will be forced by `completePaymentPayload()` to include every single dust output as an input in that response's payment message, regardless of how many there are. This inflates the resulting unit's size/oversize fee and can make it impossible for the AA to successfully compose and save a valid response unit, causing that AA's asset "send-all"/withdrawal functionality to bounce or fail indefinitely — permanently freezing the AA's funds in that asset, the same "AA fund loss or freezing" impact category as Mellow's redemption DoS.

### Likelihood Explanation
Any address (no special privileges) can issue or hold small quantities of any transferable asset and send arbitrarily many minimal-amount outputs to a target AA address at negligible cost — the codebase's own comment confirms the developers were aware of, and explicitly guarded against, exactly this dust-flood pattern for the base asset, but the same guard was not applied to other assets. This makes the attack straightforward to mount against any AA that implements a "send all of asset X" payout, requiring only ordinary posted units, no elevated access.

### Recommendation
Apply the same dust-filtering principle used for the base asset to non-base assets in `readStableOutputs()`/`readUnstableOutputsSentByAAs()` — e.g., ignore/aggregate below-threshold asset outputs separately from the ones used to satisfy `send_all`, or cap/paginate the number of inputs an AA-generated payment message may include (removing or bounding the `!objValidationState.bAA` exemption in `validatePaymentInputsAndOutputs()`), and provide an AA-callable mechanism to sweep/consolidate accumulated dust without needing to include it all in a single response unit.

### Proof of Concept
Conceptual PoC (not executed): 
1. Attacker issues or holds asset `A` and repeatedly sends thousands of 1-unit outputs of asset `A` to AA address `X`.
2. A user later triggers AA `X`'s "withdraw all of asset A" branch, whose oscript issues a payment message with an output `{address: user, amount: undefined}` for asset `A` (send-all semantics).
3. `completePaymentPayload()` queries `readStableOutputs()`/`readUnstableOutputsSentByAAs()` with no minimum-amount filter for asset `A`, and because `send_all_output` is set, `iterateUnspentOutputs()` never breaks early — it must consume all thousands of dust outputs as inputs.
4. The resulting payment message payload grows unbounded; because `validatePaymentInputsAndOutputs()` skips the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check for AA units, this is not rejected at that layer, but the ballooning unit size/oversize fees (or other size constraints during unit save/broadcast) cause the response composition/save to fail, bouncing the trigger and leaving the "withdraw all of asset A" feature permanently broken for AA `X`.
