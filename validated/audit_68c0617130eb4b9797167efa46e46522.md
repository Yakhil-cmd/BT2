### Title
Cross-organization webhook signature confusion allows forging repository state (statuses, pushes) for repositories outside the attacker's authenticated GitHub organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an incoming webhook against using a field (`repository.owner.login` / `organization.login`) taken directly from the unauthenticated JSON body, while every `Webhooks::Handlers::Handler` subclass independently resolves the repository to mutate using a *different* field from that same unauthenticated body (`repository.full_name`). Because the HMAC signature only proves the body matches *some* configured organization's secret, and never binds that secret to the `full_name` actually acted upon, a party who legitimately controls one Shipit-configured organization's webhook secret can forge a payload that authenticates as their own org but writes state (pushes, commit statuses) into a completely different org's repository.

### Finding Description
`verify_signature` computes the organization used for HMAC lookup purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: ...)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key, and Shipit explicitly supports multiple organizations behind the same `/webhooks` endpoint, each with its own secret: [3](#0-2) 

`verify_webhook_signature` merely checks that the raw body was HMAC-signed with the secret belonging to whichever organization was named in the body: [4](#0-3) 

After signature verification succeeds, `create` dispatches the same raw, unauthenticated JSON body to handlers: [5](#0-4) 

Every handler resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a field that was never checked against, or tied to, the organization used to select the verifying secret: [6](#0-5) 

For example, `PushHandler` triggers `stack.sync_github` for whatever stacks belong to `repository_name`: [7](#0-6) 

The `status` event handler creates a `Status` record for a commit resolved the same way, and that status directly gates deployability: [8](#0-7) [9](#0-8) 

**Equality broken:** the engine implicitly assumes `verified_org(payload) == owning_org(repository.full_name)`. Before the attack, both sides are equal for legitimate GitHub-originated webhooks (GitHub itself keeps `repository.owner.login` consistent with `repository.full_name`). After a forged POST, an attacker who owns org A's `webhook_secret` sets `organization.login`/`repository.owner.login = "orgA"` (so `verify_signature` picks and matches org A's secret) but sets `repository.full_name = "orgB/victim-repo"` (so the handler mutates org B's data). The signature check never re-validates that the two fields agree, so the binding is broken.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. A party who is merely a legitimate operator/owner of one org configured in a multi-org Shipit deployment (i.e., someone who knows their own org's GitHub App `webhook_secret` — not a Shipit session, not an `ApiClient` token, not the app's `GITHUB_TOKEN`) can:
- Inject fabricated `push` events for a foreign org's repository, triggering `sync_github`/stack updates for stacks they have no authorization over.
- Inject fabricated `status` events (e.g. state `success`) for a foreign org's commit, which is used by `Commit#deploy_state` to gate whether a commit is deployable — enabling an unauthorized deploy of another organization's stack.

This matches the "cross-repository writes" / "unauthorized deploy" Critical impact bucket, achieved without any Shipit session, API token, or the host GitHub App's private key/`GITHUB_TOKEN` — only knowledge of one legitimately-configured org's webhook secret in a multi-org deployment.

### Likelihood Explanation
Requires: (1) Shipit configured in the multi-organization mode illustrated by `config/secrets.development.shopify.yml` (more than one org's `webhook_secret` behind the single `/webhooks` endpoint), and (2) the attacker legitimately controlling/knowing one such org's webhook secret (e.g., a semi-trusted org onboarded onto a shared Shipit instance). Given that Shipit explicitly documents and supports this multi-tenant configuration shape, this is a realistic deployment pattern, and the exploit itself is a single crafted HTTP POST with a valid HMAC for the attacker's own org and a mismatched `full_name`.

### Recommendation
After `verify_signature` succeeds, derive the organization consistently and validate that the resolved handler's `repository_name`/`full_name` actually belongs to the same organization whose secret was used to verify the signature (e.g., require the owner segment of `repository.full_name` to equal the verified `repository_owner`), rejecting the request otherwise.

### Proof of Concept
1. Shipit is configured with two orgs, `orgA` and `orgB`, each with distinct `webhook_secret`s, per the pattern in `config/secrets.development.shopify.yml`.
2. Attacker (who administers/knows `orgA`'s GitHub App and its `webhook_secret`) crafts a JSON body:
```json
{
  "organization": {"login": "orgA"},
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and the signature matches, so the request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. The corresponding status handler resolves `Repository.from_github_repo_name("orgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and writes a `success` status for the victim's commit, which `Commit#deploy_state` treats as a green light for deployment — despite the attacker never having any relationship to `orgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
