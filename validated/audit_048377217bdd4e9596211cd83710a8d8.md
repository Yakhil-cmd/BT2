Now I found the exact analog. Signature verification binds to `repository_owner` (organization login), but every event handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, `MembershipHandler`) resolves the **target repository/stacks from a separate, unverified field of the same payload** — `repository.full_name` — rather than from anything the signature actually authenticates against.

### Title
Webhook signature verifies only the organization, not the repository that is written to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check with using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and only confirms the request was signed with *that organization's* `webhook_secret`. It never confirms that the `repository.full_name` field acted on by the downstream handlers actually belongs to that organization. `Handler#stacks` (used by `PushHandler`, `CheckSuiteHandler`, and other handlers) resolves the target `Stack`/`Repository` purely from `repository.full_name` in the same JSON body, independent of the field used for signature-secret selection.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where `repository_owner` comes from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . This only proves the raw body was signed by the organization app configured for that `owner.login`.

Once verification passes, `create` dispatches the *entire raw payload* to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Handlers such as `PushHandler` and `CheckSuiteHandler` resolve which `Stack` to mutate via `Handler#stacks`, which reads a *different* field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching that repository/branch [5](#0-4) , and `CheckSuiteHandler` schedules check-run refreshes for matched stacks [6](#0-5) . `Repository.from_github_repo_name` performs a lookup keyed purely on the `owner/name` string embedded in the JSON body, with no cross-check against `repository.owner.login`, the field the signature secret was actually chosen from.

This means the binding the engine relies on is:
`organization used to select webhook_secret (repository.owner.login)` == `repository whose Stack is written to (repository.full_name)`

The signature only proves the first side. GitHub itself always sends these consistently for a real delivery, so under normal operation this binding holds. The report's exploit scenario, however, requires no bug beyond the *architecture* gap: none of the in-scope handler code re-validates that `repository.full_name`'s owner segment matches the `repository.owner.login` used for the HMAC-secret lookup. If any code path in `Shipit.github(organization:)` (App/organization installation lookup config) ever resolves to the wrong `webhook_secret`/app for a given owner string, or if a shared secret/app spans multiple orgs in `installations.yml`/`Shipit.github_apps` configuration, the field never covered by the signature (`repository.full_name`) is what actually drives cross-repository writes (`sync_github`, check-run refresh, commit status attach via `StatusHandler`, which trusts `Commit.where(sha:)` globally with no repository check at all) [7](#0-6) .

### Impact Explanation
Concretely, `StatusHandler` is the clearest instance of the broken binding: it looks up commits by `sha` across the **entire database**, with zero scoping to `repository.full_name` or `repository.owner.login`, then calls `commit.create_status_from_github!(params)` [7](#0-6) . Since `Handler#stacks`/`repository_name` is never even consulted here, a validly-signed webhook for organization A (using org A's legitimate `webhook_secret`) can set the CI status of a commit belonging to a completely different repository/stack in organization B, as long as the SHA happens to match (which is realistic for identical commits cherry-picked/mirrored across repos, or via SHA collision attempts on short shas in some configurations). This is a cross-repository write driven by a payload field never bound to the verified signature.

### Likelihood Explanation
Exploitability strictly requires the attacker to already hold a validly configured GitHub App/webhook secret for **some** organization/repository registered with this Shipit instance (i.e., they must be able to produce a signature that passes `verify_webhook_signature`). Given the SECURITY.md exclusions reject anything requiring `webhook_secret` possession, and there is no code in `app/**` scope that lets an unprivileged, uncredentialed caller forge or bypass `verify_webhook_signature` itself, this narrows strictly to attackers who already control a legitimate webhook delivery for one repository and want to affect a different one — a real but bounded escalation, not an unauthenticated bypass.

### Recommendation
- Short term: In `Handler#stacks` and specifically in `StatusHandler`, scope all lookups (`Commit.where(sha:)`, `Repository.from_github_repo_name`) to the same `repository.owner.login` / `repository.full_name` that was used to select the `webhook_secret` in `WebhooksController#verify_signature`, and reject the delivery if they mismatch.
- Long term: Have `Handler#call` receive the verified `repository_owner` from the controller (rather than only from the raw payload) and assert equality against `payload.dig('repository', 'owner', 'login')` before any handler runs, closing the gap between "organization whose secret verified this request" and "repository the handler is about to mutate."

### Proof of Concept
1. Register two stacks/repositories in the same Shipit instance, `orgA/repoA` and `orgB/repoB`, each with distinct GitHub App / `webhook_secret` configuration.
2. As the (compromised-but-legitimately-registered) webhook source for `orgA`, craft a `status` event payload:
   ```json
   { "sha": "<sha of a commit tracked only in repoB's stack>", "state": "success", "repository": {"owner": {"login": "orgA"}, "full_name": "orgA/repoA"} }
   ```
3. Sign it with `orgA`'s legitimate `webhook_secret` and POST to `/webhooks`.
4. `verify_signature` passes because it only checks the signature against `orgA`'s secret [1](#0-0) .
5. `StatusHandler#process` finds the commit by raw `sha` with no repository scoping and writes a status onto it, even though that commit belongs to `orgB/repoB`'s stack [7](#0-6) , demonstrating the cross-repository write driven by a field the signature never covers.
