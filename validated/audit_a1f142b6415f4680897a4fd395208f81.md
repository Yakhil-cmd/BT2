### Title
Recipient-Controlled Revert in `handleKLAYTransfer` Permanently Locks Bridged KAIA and Blocks Bridge Nonce Progression — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge delivers KAIA to the recipient via a low-level `.call.value()`, then hard-reverts the entire transaction if the call fails. Because the nonce-accounting state changes (`handleNoncesToBlockNums`, `_updateHandleNonce`) are written before the external call and are rolled back on revert, a recipient contract that refuses KAIA permanently prevents that bridge nonce from ever being settled. The Go-level event processor stops on the first error and re-queues all remaining events, so every subsequent cross-chain transfer is also blocked.

---

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` follows this sequence:

1. Nonce guard (`_lowerHandleNonceCheck`) — line 75
2. Operator vote (`_voteValueTransfer`) — line 77
3. State writes: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[N] = blockNum`, `_updateHandleNonce(N)` — lines 81–84
4. Emit event — lines 86–96
5. **External call**: `(bool ok, ) = _to.call.value(_value)("")` — line 98
6. **Hard revert**: `require(ok, "handleKLAYTransfer: transfer failed")` — line 99 [1](#0-0) 

Because step 6 reverts the entire transaction, all state changes from steps 2–4 are also rolled back. `handleNoncesToBlockNums[N]` is never durably set to a non-zero value, so `_updateHandleNonce` can never advance `lowerHandleNonce` past N. [2](#0-1) 

The `lowerHandleNonce` advancement loop requires `handleNoncesToBlockNums[i] > 0` for every consecutive i starting from `lowerHandleNonce`. A permanently-zero entry at N breaks the chain forever. [3](#0-2) 

At the Go relay layer, `processingPendingRequestEvents` stops and re-queues all remaining events on the first error: [4](#0-3) 

Gas estimation for `handleKLAYTransfer` will fail (the simulated call reverts), so `handleRequestValueTransferEvent` returns an error, and every nonce ≥ N is re-queued indefinitely.

### Impact Explanation

| Asset / State | Effect |
|---|---|
| User's KAIA on source chain | Permanently locked in source bridge — `requestKLAYTransfer` already consumed `msg.value`; no refund path exists |
| Destination bridge KAIA | Not consumed (stays in bridge), but the corresponding source-side KAIA is unrecoverable |
| `lowerHandleNonce` | Permanently stuck at N; `recoveryBlockNumber` never advances past block N−1 |
| All subsequent bridge transfers (nonces > N) | Blocked at Go relay level; `processingPendingRequestEvents` never processes them |

The source-chain KAIA is irrecoverably locked because `_requestKLAYTransfer` has no refund mechanism — it simply emits an event and increments `requestNonce`. [5](#0-4) 

---

### Likelihood Explanation

The `_to` address is fully user-controlled via `requestKLAYTransfer`: [6](#0-5) 

Any user can:
1. Deploy a contract with no payable fallback (or one that explicitly `revert()`s).
2. Call `requestKLAYTransfer(_to=maliciousContract, ...)` with any non-zero KAIA amount.
3. The destination-side `handleKLAYTransfer` will revert on every attempt, permanently blocking the bridge.

The attacker sacrifices only the bridged KAIA amount (plus fees) to permanently DoS the bridge for all users. No privileged access is required.

---

### Recommendation

Apply the **pull-over-push** pattern: instead of reverting when the KLAY delivery fails, credit the amount to a claimable mapping and advance the nonce regardless.

```solidity
mapping(address => uint256) public pendingWithdrawals;

function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) return;

    _setHandledRequestTxHash(_requestTxHash);
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
    _updateHandleNonce(_requestedNonce);

    emit HandleValueTransfer(...);

    (bool ok, ) = _to.call.value(_value)("");
    if (!ok) {
        // Nonce already advanced; store for later claim
        pendingWithdrawals[_to] = pendingWithdrawals[_to].add(_value);
    }
}

function claimKLAY() external nonReentrant {
    uint256 amount = pendingWithdrawals[msg.sender];
    require(amount > 0, "nothing to claim");
    pendingWithdrawals[msg.sender] = 0;
    (bool ok, ) = msg.sender.call.value(amount)("");
    require(ok, "claim failed");
}
```

This mirrors the fix described in the external report: settle the accounting unconditionally, and let the recipient claim their funds separately.

### Proof of Concept

1. Deploy a malicious recipient contract on the destination chain:
   ```solidity
   contract MaliciousRecipient {
       // No payable fallback — all KAIA transfers revert
   }
   ```

2. On the source chain, call:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(
       address(maliciousRecipient), 1 ether, ""
   );
   ```
   This locks 1 KAIA in the source bridge and emits `RequestValueTransfer` with nonce N.

3. Bridge operators observe the event and call `handleKLAYTransfer` on the destination bridge with `_to = maliciousRecipient`. The call at line 98 returns `ok = false`; line 99 reverts the transaction. All state changes (including `handleNoncesToBlockNums[N]`) are rolled back.

4. Every subsequent operator retry reverts identically. `lowerHandleNonce` stays at N.

5. In `processingPendingRequestEvents`, `handleRequestValueTransferEvent` returns an error for nonce N; the function re-queues nonces N, N+1, N+2, … and returns. No further cross-chain transfer is ever processed. [7](#0-6) [8](#0-7)
