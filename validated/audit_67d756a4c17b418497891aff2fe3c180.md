### Title
PSM `mint`/`redeem` do not validate actual transferred amount against expected amount when the external asset is deflationary (fee-on-transfer) - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm`'s `mint` and `redeem` extrinsics compute the internal-asset amount to mint/burn from the *requested* external amount (`external_amount`/`internal_amount`), then call `T::Fungibles::transfer(...)` and mint/burn based on that pre-computed value, without inspecting the actual amount returned by `transfer`. `T::Fungibles` is a generic, runtime-configurable `fungibles::Mutate` implementation — if the configured external asset is deflationary (charges a fee/burn on transfer, e.g. a rebasing or fee-on-transfer wrapped asset), the PSM reserve receives less than `effective_external`, but the user is still minted `internal_to_user` computed from the full requested amount, silently under-collateralizing the internal stablecoin's debt.

### Finding Description
In `mint()`: [1](#0-0) 
the pallet calls `T::Fungibles::transfer(external_asset, &who, &psm_account, effective_external, Preservation::Expendable)?` and immediately proceeds to `T::Fungibles::mint_into(internal_asset, &who, internal_to_user)?`, recording `new_debt` based on `internal_equivalent`, which is derived purely from the **requested** `external_amount`. The return value of `transfer` (the actual amount moved) is discarded — only the `?` for error propagation is used.

Similarly in `redeem()`: [2](#0-1) 
the external asset is transferred out of the PSM reserve to the user based on `external_out`, computed from the internal amount burned, again without checking the actual transferred amount returned by `T::Fungibles::transfer`.

This mirrors the reported bug class exactly: a `transferFrom`/`transfer` call whose actual delivered amount can differ from the requested amount is trusted at face value for subsequent accounting (minting shares/tokens). The `Config::Fungibles` type is a generic associated type (`T::Fungibles: fungibles::Mutate<...>`), so whether an actual "deflationary" external asset can be registered depends entirely on which runtime configures `pallet-psm` and which asset backend it points `T::Fungibles` at. The upstream `pallet-assets`/`fungibles` trait implementations bundled in this repository (`substrate/frame/assets/src/functions.rs`, `do_transfer`) explicitly guarantee the transferred amount is never *less* than requested — dust adjustments only make it *equal or greater* — [3](#0-2)  so with a standard `pallet-assets` backend this path is safe. `substrate/frame/asset-conversion/ops/src/lib.rs` shows the defensive pattern that PSM is missing: it explicitly checks `balance2 == T::Assets::transfer(...)` and errors with `Error::<T>::PartialTransfer` if the actual and expected amounts diverge [4](#0-3) .

### Impact Explanation
I could not find or confirm a deflationary/fee-on-transfer `fungibles::Mutate` implementation actually wired into any production PSM runtime configuration in this snapshot of the repository, nor evidence that pallet-psm is deployed with an external asset backend other than standard `pallet-assets`. Without such a backend, the vulnerability is not reachable, because `pallet-assets::do_transfer` never returns less than requested. This is a design-level missing invariant check (unlike `asset-conversion-ops`, which defends against `PartialTransfer`), but I was unable to demonstrate a concrete reachable "deflationary external asset" configuration for PSM within the scope and time available.

### Likelihood Explanation
Low/uncertain — this requires a governance/config-time decision (`add_external_asset`) to approve a non-standard, deflationary `fungibles`-backed asset as a PSM external asset. This is a privileged, config-only precondition (asset approval is presumably restricted, and the finding partly hinges on speculative asset-backend behavior not proven present in this codebase), which falls into the categories the scan explicitly asks to reject ("privileged prerequisites", "config-only" findings) unless a genuinely permissionless, real deflationary asset path is shown.

### Recommendation
If not already covered, `pallet-psm::mint`/`redeem` should check the actual amount returned by `T::Fungibles::transfer` against the expected/effective amount (mirroring the `PartialTransfer` guard in `asset-conversion-ops`) before minting/burning internal-asset amounts derived from the requested value, to remain safe regardless of what asset backend a runtime plugs into `T::Fungibles`.

### Proof of Concept
Not executed. I was unable to construct or verify a concrete, permissionless reproduction: doing so would require (a) a runtime that actually registers a deflationary/fee-charging asset as a PSM external asset (an admin/governance action, not a user-triggerable step), and (b) a fungibles backend in this workspace that implements such fee-on-transfer semantics, which I did not find evidence of. Given the required privileged/config-only precondition and the lack of a demonstrated reachable deflationary asset backend, I cannot confirm this as an exploitable, in-scope finding per the strict criteria (reject config-only/privileged-prerequisite findings). Reporting this as a **Low-confidence, currently-unconfirmed** analog rather than a verified Medium/High finding.
