### Title
Webhook signature verification is bound to `repository.owner.login`, but every event handler acts on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, which is read straight out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). Every default webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers), however, determines which `Repository`/`Stack` to act on using a *different* field from the same body: `repository.full_name`. Because these two fields are never checked for consistency, and because Shipit explicitly supports hosting multiple independent GitHub organizations behind one instance (each with its own `webhook_secret`), a payload can be signed with the secret belonging to organization/repo A (`repository.owner.login = "A"`) while `repository.full_name` names a completely unrelated repository belonging to organization B. The signature check passes (it only validates against A's secret), and the handler then mutates state for B's stack.

### Finding Description
`WebhooksController#verify_signature` computes the signing organization purely from attacker-supplied payload data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization configuration (`app_id`, `webhook_secret`, etc.) from `secrets.github`, explicitly supporting multiple GitHub orgs on one Shipit deployment: [3](#0-2) 

`GitHubApp#verify_webhook_signature` verifies the HMAC using *only* the secret belonging to the organization resolved above; if that organization has no `webhook_secret` configured, verification is skipped entirely (`return true unless webhook_secret`): [4](#0-3) 

Once the signature is "verified" for organization A, the raw body is handed unmodified to all registered handlers for the event: [5](#0-4) 

Every handler resolves the target `Repository`/`Stack` from `repository.full_name` — a field that is never cross-checked against `repository.owner.login`: [6](#0-5) [7](#0-6) 

The trust binding that should hold is: `organization whose secret authenticated the payload == organization owning the repository the handler writes to`. That binding is broken because the two values come from independent, attacker-controlled JSON fields, and nothing enforces `full_name.split('/').first == owner.login`.

### Impact Explanation
On any Shipit deployment configured for multiple GitHub organizations (as documented and directly supported via `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github_app_config`), an attacker who can produce (or does not need, if that org's `webhook_secret` is unset/`nil`) a valid signature for **any one** configured organization can forge webhook events that are processed against **any other** organization's stacks, entirely bypassing that other organization's own webhook secret. Concretely:
- A forged `push` event lets an attacker cause `PushHandler#process` to invoke `stack.sync_github(expected_head_sha: ...)` on an arbitrary stack belonging to a different organization than the one whose secret signed the request — this is a cross-repository write triggered without ever knowing the target organization's own webhook secret.
- The same class of confusion applies to `status`, `check_suite`, and `pull_request` handlers, all of which resolve targets via `repository.full_name` while only the (unrelated) `repository.owner.login`/`organization.login` field is authenticated.

This crosses the "organization that authenticated versus the repository that is written" trust boundary called out as in-scope, and results in a cross-organization/cross-repository write against Shipit's own state and (via `sync_github`) triggers real GitHub API interactions using that other organization's installed credentials.

### Likelihood Explanation
Exploitability requires:
1. The instance to be configured for multiple GitHub organizations (an explicitly supported and documented configuration — `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`).
2. The attacker to control (or have) a valid signature for at least one of the configured organizations — trivially true if any org has `webhook_secret` unset (`nil`, which `verify_webhook_signature` treats as "always verified"), or if the attacker is a legitimate integrator/maintainer of one org's repo but not another's.

Given that Shipit is designed to host many orgs/repos behind one set of secrets, and one weak/absent `webhook_secret` on any single org compromises isolation for all others, this is a realistic misconfiguration-triggered but architecturally-rooted issue rather than a purely theoretical one.

### Recommendation
Bind signature verification to the same identity used for dispatch: after parsing the payload, require that the organization/owner embedded in `repository.full_name` matches the organization resolved for signature verification (`repository.owner.login`/`organization.login`), and reject the webhook (422) if they differ. Alternatively, encode the target organization in the webhook delivery URL/path (per-org endpoint) rather than deriving it from the payload body, so the verification key can never be chosen by attacker-controlled JSON.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Craft a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
3. Sign the raw body with `OrgB`'s `webhook_secret` (or omit signing if `OrgB` has no `webhook_secret` configured) and send it as an `X-Github-Event: push` webhook.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgB"`, looks up `Shipit.github(organization: "OrgB")`, and verifies successfully using `OrgB`'s secret (or unconditionally if unset).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgA/victim-repo")` (from `repository.full_name`), matches the branch, and calls `stack.sync_github(expected_head_sha: ...)` on `OrgA`'s stack — a write triggered without ever presenting `OrgA`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
