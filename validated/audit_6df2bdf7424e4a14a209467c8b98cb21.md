### Title
Security-review detection bypass via cross-edit content splitting in `MultiEdit` — concatenation without boundary markers ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`extract_content_from_input()` in `security_reminder_hook.py` and the structurally identical `_extract_field()` in `plugins/hookify/core/rule_engine.py` build the text that gets scanned for secrets/dangerous-content patterns by joining every `MultiEdit` sub-edit's `new_string` with a single space (`" ".join(...)`), discarding the fact that each edit lands at a distinct, unrelated `old_string` location in the file. Because the join point is not a real token/word boundary, a sensitive literal split across two adjacent edits reassembles into a *different* string at scan time than what actually lands in the file, letting the detector's regex miss a pattern it was designed to catch — the same "concatenation without separators breaks positional/boundary assumptions used by a security check" defect described in the report for `BaseRouter._getRawData()`.

### Finding Description
`extract_content_from_input()` is the content extractor feeding the secret/PII-in-code detection path used by the security-guidance PreToolUse/PostToolUse review hooks: [1](#0-0) 
For `MultiEdit`, all `edits[i].new_string` values are concatenated with `" ".join(...)` into one flat string before it is checked against detection regexes elsewhere in the hook pipeline. The same defective join exists independently in the `hookify` plugin's rule engine, which is explicitly used to build user-authored PreToolUse block/warn rules over `new_text`/`content` fields: [2](#0-1) 

The root cause mirrors the report exactly: multiple logically distinct segments (here, per-edit `new_string` fragments destined for different, non-adjacent file offsets) are concatenated into a single buffer that a downstream matcher (regex `contains`/`regex_match`, or the LLM secret-scan prompt) treats as one contiguous string, with only a single space as an arbitrary, attacker-influenceable separator. Because `MultiEdit`'s `edits` array and each edit's `old_string`/`new_string` are fully attacker-controlled input (the model itself can be steered by prompt injection from file content, or a user/task description can request this shape of edit), a security-relevant token can be split so it doesn't survive concatenation as a contiguous match, e.g. an edit inserting `sk-` in one location and the remaining secret suffix in a different, unrelated edit — the joined check string becomes `"sk- <other unrelated text> {suffix}"`, which no longer contains the literal secret pattern, even though the final file on disk does contain it once the edits are applied independently at their own offsets. This is structurally identical to the report's core claim: "the `_getRawData()`/`_checkSignature()` cannot distinguish between different logical splits because concatenation always produces the same flat stream" — here, the flat stream after concatenation is decoupled from the flat stream that will actually exist in the file, because each edit is independently applied at its own `old_string` location rather than being written back-to-back.

### Impact Explanation
This is a detection-bypass in a hook-based trust boundary (listed as an acceptable category): it allows a maliciously or accidentally split multi-edit write to introduce secrets, hardcoded credentials, or other flagged content into a file while evading the pattern-matching gate that `security-guidance`'s hooks and user-authored `hookify` rules rely on to warn/block such writes. The severity is bounded — these are best-effort, advisory-style detectors (`warn`/`block` hook decisions, not a hard sandbox boundary), and the bypass only defeats detection, not the write itself; the actual security consequence is limited to secrets/dangerous-content slipping past a review/警示 layer rather than a direct sandbox or permission-model escape.

### Likelihood Explanation
Reachable by any Claude Code session invoking `MultiEdit` with multiple edits whose `new_string` values are crafted (directly by the user, or indirectly via prompt injection influencing the model) to split a flagged pattern across edit boundaries. No special privileges are required beyond normal tool use, and the joining logic is deterministic and easy to reason about once the extractor's behavior is known.

### Recommendation
Do not build one flat string across unrelated `MultiEdit` edits for pattern matching. Either (a) run detection independently per-edit (`new_string` alone, not joined with siblings), or (b) if a combined view is needed, join with an unambiguous, out-of-band delimiter per edit and run the regex per-segment rather than over the joined blob, and separately re-check the fully materialized post-edit file content (post-application) rather than relying on the concatenated `edits[].new_string` values. def extract_content_from_input(tool_name, tool_input):
    """Extract content to check from tool input based on tool type."""
    if tool_name == "Write":
        return tool_input.get("content", "")
    elif tool_name == "Edit":
        return tool_input.get("new_string", "")
    elif tool_name == "MultiEdit":
        edits = tool_input.get("edits", [])
        if edits:
            return " ".join(edit.get("new_string", "") for edit in edits)
        return ""
    return ""
