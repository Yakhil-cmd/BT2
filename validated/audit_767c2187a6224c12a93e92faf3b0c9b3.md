### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by SHA (`Commit.where(sha: params.sha)`) with no repository scoping, unlike the base `Handler#stacks` helper which correctly scopes by `payload.dig('repository', 'full_name')`. Any status webhook that passes signature verification for *some* organization can therefore mutate the CI status of a commit belonging to *any* stack/repository in the Shipit instance that happens to share that SHA, including a victim stack with `continuous_deployment` enabled, causing `ContinuousDeliveryJob`/merge-queue behavior to be driven by attacker-controlled data.

### Finding Description
The broken binding is: `status.repository == commit.stack.repository` is assumed but never enforced. `StatusHandler#process` reads only `params.sha`/`params.state`/`params.context` and calls: [1](#0-0) 

—it never consults `payload.dig('repository', 'full_name')`, even though the parent `Handler` class already exposes a `stacks` helper that does exactly this scoping for other handlers: [2](#0-1) 

`WebhooksController#verify_signature` only authenticates that the payload was signed with the secret belonging to the `repository_owner`'s (organization's) GitHub App — it says nothing about *which repository under that org* sent the event: [3](#0-2) 

Once the signature check passes, `commit.create_status_from_github!(params)` is invoked on every `Commit` row with a matching `sha` across the entire database, regardless of stack/repository: [4](#0-3) 

That in turn calls `add_status`, which fires `deployable_status`/`commit_status` hooks and schedules merges/continuous delivery: [5](#0-4) 

And `Status#schedule_continuous_delivery` unconditionally checks only the "commit" and its stack's CD flag — not which repository authenticated the write: [6](#0-5) [7](#0-6) [8](#0-7) 

Exploit flow: an attacker who owns (or has installed the Shipit GitHub App into) any repository under an organization configured in Shipit's `github` secrets can send a legitimately-signed `status` webhook — signature is computed over the org-level `webhook_secret`, not the repository — with an arbitrary `sha`, `context: ci/circleci`, `state: failure` (or `success`). If that SHA also exists in `Commit` rows belonging to a *different*, victim stack that has `continuous_deployment` enabled and requires `ci/circleci` as a status check (e.g. shared commit history from a fork/mirror/rebase, or a monorepo split into multiple tracked stacks), `StatusHandler` will write the forged status onto the victim's commit and immediately fire the deployability/CD machinery for that victim stack — with no cross-check that the webhook's `repository.full_name` matches `commit.stack.repository`.

Existing guards do not stop this: `verify_signature` validates org-level authenticity only; `drop_unhandled_event`/`check_if_ping` are irrelevant; the `ExplicitParameters` schema in `StatusHandler.params` validates types only, not repository identity; there is no `require_permission!`/`stacks` scoping call anywhere in `StatusHandler#process`.

### Impact Explanation
A `status` webhook validly signed for repository/org A can flip CI state and trigger/block deploys, rollbacks, or merges for a stack tracking a completely different repository B, as long as both share a commit SHA. This is "a payload for one repository mutating another's stack/commit," which the rules classify as Critical. The blast radius spans every stack in the instance whose commits share a SHA with any repo an attacker can obtain webhook signing rights for (their own repo/org under the same Shipit config, or any org configured in Shipit's multi-org `github` secrets section). Repeatable per request, with no rate limiting to prevent repeated forced flips.

### Likelihood Explanation
Preconditions: (1) attacker must be able to trigger a validly-signed `status` webhook — trivial if they own a GitHub repo under an org that Shipit trusts (installs the same GitHub App, or is one of the orgs in a multi-org secrets config) since GitHub App webhook secrets are shared across all repos/installations of that app, not scoped per-repo; (2) the target SHA must exist in the victim's `Commit` table, which happens naturally with forks, mirrors, monorepo-to-multi-stack splits, or cherry-picked/rebased shared history — all common Shipit deployment topologies. Attacker cost is a single HTTP POST with a crafted JSON body; no Shipit session, API token, or GitHub credentials for the victim repo are needed.

### Recommendation
Scope `StatusHandler#process` the same way other handlers scope via `stacks`/`repository_name`: only update `Commit`s belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an explicit `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or extend `webhooks_controller_test.rb`):
1. Create two stacks/repositories, `owner/repo-a` (attacker's, org `orgA`) and `owner/repo-b` (victim, org `orgB` or same org), each with its own `GithubHook`/webhook secret setup.
2. Create a `Commit` with `sha: "deadbeef..."` under victim stack `repo-b`, and set `repo-b.continuous_deployment = true` with a `required_status` of `ci/circleci`.
3. Send `POST /webhooks` with `X-Github-Event: status`, a valid signature for `orgA` (attacker's org), and body `{"repository": {"full_name": "owner/repo-a", "owner": {"login": "orgA"}}, "sha": "deadbeef...", "state": "failure", "context": "ci/circleci"}`.
4. Assert before/after: `commit(sha: "deadbeef...", stack: repo-b).statuses.count` increased and `commit.state == 'failure'` even though `payload['repository']['full_name'] != repo-b.repository.full_name` — proving the equality `status.repository == commit.stack.repository` is violated.
5. Additionally assert `ContinuousDeliveryJob`/merge scheduling behavior changed for `repo-b` as a result of the attacker-controlled webhook for `repo-a`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
