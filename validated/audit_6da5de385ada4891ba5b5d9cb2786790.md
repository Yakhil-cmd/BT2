### Title
Missing `return` after error path causes duplicate processing of an unhandled private payment chain - ([File: network.js])

### Summary
In `network.js`, the light-client `handleSavedPrivatePayments()` function's inner `validateAndSave` closure has an error-handling path that fails to `return` after taking its error branch. This lets execution fall through to code that deletes/validates the same in-flight private payment record a second time and completes the outer `async.each` callback (`cb`) twice for one row, the same "free the same resource twice on an error path" pattern as the CVE (which double-freed the same symmetric key object on an NSS decoder error path).

### Finding Description
`handleSavedPrivatePayments()` iterates over rows in `unhandled_private_payments` and, for each one, calls a locally-defined `validateAndSave` function: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...});
};
```

If `objectHash.getBase64Hash()` throws, the `catch` branch calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` [2](#0-1)  which deletes the DB row and then invokes `cb()` — the `async.each` iterator's completion callback for this row. Because there is no `return` statement after this call, execution continues past the `catch` block: `json_payload_hash` is `undefined`, a bogus `key` is built, and `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` is invoked anyway. That call's `ifOk`/`ifError` handlers themselves eventually call `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` again [3](#0-2) , invoking `cb()` a second time for the very same row while also re-processing the same private-chain payload through the asset validation/save path a second time concurrently with the first (already-in-flight) resolution path.

This is structurally the same bug class as CVE-2024-11704: on an exceptional/error branch, a resource that has already been "released" (the queue row deleted, the iterator's callback invoked) is used/released again instead of the function returning immediately. In `async.eachSeries`/`async.each`, invoking the per-item callback twice corrupts the control-flow bookkeeping of the iterator (which is not designed to be re-entered for the same item), and here it additionally causes `validateAndSavePrivatePaymentChain` (indivisible/divisible private-asset validation and DB commit logic) to run a second time for a chain whose completion has already been signaled/deleted.

### Impact Explanation
Double-invoking the completion callback of `async.each`/`async.eachSeries` is undefined behavior in the `async` library and can result in the iteration's final callback (`unlock()` and `eventBus.emit('new_my_transactions', ...)`) firing prematurely or being re-entered while other rows are still being processed, and it can cause `assocNewUnits` bookkeeping to be manipulated inconsistently. More importantly, `privatePayment.validateAndSavePrivatePaymentChain` is invoked and allowed to fully run (opening its own `BEGIN`/`COMMIT` transaction and calling `assetModule.validateAndSavePrivatePaymentChain`) even though the row backing this private payment chain has already been deleted from `unhandled_private_payments` and the caller has already been told (via `sendResult`) that processing errored out. This creates a state where a private-asset chain can be committed to the local wallet's outputs table via a code path the node believes has already terminated with an error, opening the door to duplicate crediting of a private-asset output or a mismatch between the wallet's recorded private-payment state and what has actually been validated/saved, since normal duplicate-detection in `private_payment.js`'s SELECT-then-INSERT check (lines 62-107) is inherently racy for two overlapping invocations of the same chain triggered by this callback-doubling.

### Likelihood Explanation
Triggering the `catch` requires an attacker (a private-payment counterparty forwarding a chain to a light wallet) to construct a `payload` for the head private element whose JSON canonicalization via `getJsonSourceString`/`getSourceString` throws — e.g. by including a value type not supported by the deterministic JSON serializer (this path is reachable purely from a posted/forwarded private payment chain, with no special privileges). Because `handleSavedPrivatePayments` runs on a light wallet whenever it processes rows saved from `unhandled_private_payments` (populated by any correspondent sending it a private-payment JSON), this is reachable by any private-payment counterparty without cooperation of a hub or node operator.

### Recommendation
Add a `return` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave` (in `handleSavedPrivatePayments`, `network.js`), matching the pattern used correctly elsewhere in the codebase (e.g., `wallet.js` line ~1031, `return cb("head priv element hash failed " + e.toString());`), so the function does not fall through to re-validate/re-save the chain and does not invoke the `async.each` item callback (`cb`) a second time.

### Proof of Concept
1. As a private-payment counterparty (or hub relaying between light wallets), craft a private payment chain (`arrPrivateElements`) whose head element's `payload` contains a value that causes `getJsonSourceString`/`getSourceString` to throw when hashed (e.g., an unsupported/invalid type nested in the payload object that the deterministic JSON serializer rejects).
2. Deliver it to a light wallet so it is queued into `unhandled_private_payments` (via `handleOnlinePrivatePayment` -> `savePrivatePayment`).
3. Trigger `handleSavedPrivatePayments()` (called periodically/after joint retrieval) to process the saved row.
4. Observe that `getBase64Hash` throws inside `validateAndSave`, `deleteHandledPrivateChain(...)` is called (deleting the row and calling `cb()` once), but execution falls through and `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` still runs, eventually calling `deleteHandledPrivateChain(...)`/`cb()` a second time — demonstrating the double free/double-callback of the same per-row completion resource on the error path.

Note: I was unable to verify the exact conditions under which `getJsonSourceString`/`getSourceString` throw (i.e., precisely which payload shapes are rejected), since that logic lives in `string_utils.js` and was only partially covered by the indexed snippets I could retrieve; a full Devin session with complete file access would be needed to construct a concrete failing payload and confirm end-to-end exploitability (e.g., whether the re-entrant `async.each` callback truly causes observable node-level state corruption versus being silently absorbed by the `async` library version in use).
