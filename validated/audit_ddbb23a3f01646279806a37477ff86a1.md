### Title
Rule discovery in `load_rules()` is bound to ambient CWD instead of the trusted workspace root, allowing rule-file substitution - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`load_rules()` builds its glob pattern purely from a relative path and the process's ambient working directory: [1](#0-0) 

```python
pattern = os.path.join('.claude', 'hookify.*.local.md')
files = glob.glob(pattern)
```

There is no reference to any validated workspace root. Every hook entry point (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules()` directly without first resolving or `chdir`-ing to a trusted root: [2](#0-1) . The plugin's own documented convention elsewhere in the repo explicitly establishes `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PROJECT_DIR` as the correct binding to a trusted directory before doing repo-relative file lookups, e.g. `cd "$CLAUDE_PROJECT_DIR" || exit 1` before reading project config: [3](#0-2) . `config_loader.py`'s `load_rules()` does not follow this pattern and instead trusts `glob.glob()`'s relative-path resolution against whatever the current process CWD happens to be at hook-invocation time.

Because rule discovery is state (CWD) bound rather than root-bound, if the hook process is ever invoked, or the CWD drifts, from a subdirectory of the workspace that contains an attacker-authored `.claude/hookify.*.local.md` (e.g., a nested repository, a cloned dependency, or a submodule under attacker control), `load_rules()` will silently load and enforce the attacker's rule set (or an empty/disabled one) instead of the workspace-root-approved rules. Nothing in `load_rule_file()` or `Rule.from_dict()` validates rule provenance, file location, or cross-checks against an expected root-anchored path — enabled/disabled state and blocking behavior come entirely from unauthenticated frontmatter in whatever file the glob happens to match: [4](#0-3) .

### Impact Explanation
If an attacker can influence the hook process's working directory (or plant content that is read from a location other than the true, approved workspace root), they can neutralize the user's Bash/file-guard rules (e.g., a rule with `action: block` for `rm -rf` or a `command` regex) by shipping their own `hookify.*.local.md` with `enabled: false` or with narrower/incorrect conditions. This directly downgrades the hookify plugin's PreToolUse/PostToolUse/Stop enforcement, enabling execution of commands that should have been blocked — a workspace-confinement / trust-boundary bypass in the guard mechanism itself.

### Likelihood Explanation
This requires two things to hold simultaneously: (1) an attacker-controlled `.claude/hookify.*.local.md` exists in some subdirectory reachable within or alongside the trusted workspace, and (2) the hook process's CWD is not reliably pinned to the workspace root when `load_rules()` executes. Point (2) is plausible but not confirmed from static analysis alone — I could not verify from the indexed files whether the actual Claude Code host process guarantees CWD == project root for every hook invocation in all execution contexts (e.g. IDE integration, nested plugin invocation, or persistent-shell state bleed). The code itself provides no defense-in-depth against this scenario, which is the concrete, provable weakness, independent of how likely a CWD drift is in practice.

### Recommendation
Anchor rule discovery to an explicit, trusted root rather than ambient CWD:
- Resolve the workspace root once via `CLAUDE_PROJECT_DIR` (following the same convention already used elsewhere in the codebase) and pass it explicitly into `load_rules(root_dir=...)`.
- Build the glob pattern with `os.path.join(root_dir, '.claude', 'hookify.*.local.md')` instead of a bare relative path.
- Fail closed (or at minimum log/refuse) if `CLAUDE_PROJECT_DIR` is unset or does not match an expected canonical path, rather than silently falling back to `os.getcwd()`.

### Proof of Concept
Integration test plan:
1. Create `workspace_root/.claude/hookify.bash.local.md` containing a rule with `action: block` for `rm -rf`.
2. Create `workspace_root/nested/.claude/hookify.bash.local.md` containing a conflicting rule with the same `name` but `enabled: false`.
3. Call `load_rules(event='bash')` twice: once with CWD = `workspace_root`, once with CWD = `workspace_root/nested`.
4. Assert that in both cases the returned `Rule` list is identical and matches only the `workspace_root/.claude` rule (i.e., the block rule with `enabled: true`), proving discovery is root-bound.
5. Current behavior (expected to fail this assertion): from `workspace_root/nested`, `load_rules()` returns the attacker's disabled/neutered rule set instead of the workspace-root rule set, because `glob.glob('.claude/hookify.*.local.md')` resolves against `os.getcwd()`.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
