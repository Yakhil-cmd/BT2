### Title
Webhook Signature Verified Against Attacker's Own Organization, But Handlers Act On An Unrelated `repository.full_name` — Cross-Organization Stack Forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify a webhook against using `repository_owner`, a value read straight out of the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`). Every webhook `Handler` (push, pull_request/*), however, decides **which stack/repository to actually mutate** using a *different* field from the very same body: `repository.full_name`. Nothing enforces that these two fields agree, so on a multi-organization Shipit deployment, a party that legitimately controls one configured GitHub organization can forge a webhook whose signature verifies against their own known secret while pointing `repository.full_name` at a different organization's repository, causing Shipit to sync, provision, or archive that victim stack.

### Finding Description
`WebhooksController#verify_signature` in [1](#0-0)  computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is defined as: [2](#0-1) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This value, taken from the attacker-controlled JSON body, is used purely to pick *which organization's secret* should validate the HMAC (`lib/shipit/github_app.rb#verify_webhook_signature`). It proves only that the sender knows the webhook secret belonging to whatever organization `repository.owner.login` names — it says nothing about which repository is actually described elsewhere in the same payload.

Every `Handler` subclass, however, resolves the repository/stack to operate on from a **separate** field, `repository.full_name`:
- Base class: [3](#0-2) 
- `PushHandler#process` (uses `stacks` from the base class, i.e. `repository.full_name`): [4](#0-3) 
- `PullRequest::OpenedHandler` resolves `repository` independently via `params.repository.full_name`: [5](#0-4) 
- Same pattern in `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `AssignedHandler`, `EditedHandler` (all derive `repository`/`stack` purely from `params.repository.full_name`), e.g. [6](#0-5) 

At no point does any handler or the controller assert that `repository.owner.login` (the field that picked the verifying secret) matches the owner segment embedded in `repository.full_name` (the field that picks the acted-upon repository). Real GitHub payloads always keep these consistent, but Shipit itself never checks it — the binding "the organization whose secret validated this request" == "the organization whose repository is being written to" is never enforced.

On a Shipit instance configured for multiple GitHub organizations (an explicitly documented, supported configuration — see `docs/setup.md` / `config/secrets.development.example.yml` multi-org schema, `lib/shipit.rb#github_organizations`), each tenant organization installs its own GitHub App and knows its own `webhook_secret`. Because the HMAC only proves knowledge of *a* secret associated with the (attacker-chosen) `repository.owner.login`, any one tenant can:
1. Craft a JSON body with `repository.owner.login` = their own org (e.g. `org-A`), and `organization.login` absent so the same field is reused.
2. Set `repository.full_name` = `"org-B/victim-repo"`, an unrelated tenant's repository.
3. Sign the raw body with `org-A`'s own webhook secret (which they legitimately know since they own that GitHub App installation) and send it to the shared `/webhooks` endpoint.
4. `verify_signature` succeeds (it validates against `org-A`'s secret, matching `repository.owner.login`).
5. The dispatched handler ignores `repository.owner.login` entirely and instead resolves the target stack from `repository.full_name` = `org-B/victim-repo`, acting on `org-B`'s stack.

### Impact Explanation
Depending on which webhook event/handler is exploited this yields cross-repository writes against a different tenant's stack without any credential for that tenant:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` against the victim stack.
- `PullRequest::OpenedHandler` calls `ReviewStackAdapter#find_or_create!`, which creates a brand-new Review Stack for the victim's repository and enqueues it for provisioning (`ReviewStackProvisioningQueue.add(stack)`), per [7](#0-6)  — provisioning executes the victim repository's own deploy/provision scripts as a Shipit task.
- `PullRequest::ClosedHandler`/`LabeledHandler` call `archive!`/`deprovision` on the victim's review stack ( [8](#0-7) ), which deprovisions (runs deprovision steps) against the victim stack.

Triggering provisioning/deprovisioning of a stack is functionally equivalent to forcing an unauthorized deploy/rollback-class task execution on a repository the attacker has no legitimate access to — this is a cross-tenant, cross-repository write, which maps to the Critical impact bucket ("cross-repository writes, or an unauthorized deploy, rollback").

### Likelihood Explanation
Requires the attacker to be an unprivileged-but-legitimate tenant on a shared, multi-organization Shipit deployment (i.e., they run their own GitHub org/App that is one of several configured under `secrets.yml`'s multi-org `github:` schema). This is a documented, supported deployment mode, not a misconfiguration outside the engine's own code. No GitHub-side webhook secret theft, no Shipit session, and no `ApiClient` token are needed — only knowledge of the attacker's own, legitimately-issued webhook secret, which they inherently possess as a tenant of the shared instance. Likelihood is therefore realistic in any multi-org Shipit deployment.

### Recommendation
After signature verification succeeds, additionally verify that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) is consistent with the owner segment of every repository-identifying field the handlers subsequently trust (`repository.full_name`). Concretely:
- In `WebhooksController`, derive a single canonical "authenticated organization" from the verified request and pass it down to handlers.
- In `Handler#stacks` / `Handler#repository_name` and all per-handler `repository` resolution methods, reject (or scope the lookup) if the owner segment of `repository.full_name` does not match the organization that successfully verified the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `org-A` and `org-B`, each with its own GitHub App and `webhook_secret` (per the documented multi-org `secrets.yml` schema).
2. As the operator/owner of `org-A` (an unprivileged party with respect to `org-B`), craft a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "full_name": "org-B/victim-repo",
    "owner": { "login": "org-A" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-A's webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-A"`, fetches `Shipit.github(organization: "org-A")`, and the signature verifies successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method (inherited from `Handler`) looks up `Repository.from_github_repo_name("org-B/victim-repo")` — `org-B`'s stack — and calls `stack.sync_github(expected_head_sha: "deadbeef")`, an action the `org-A` tenant has no authorization to trigger.
