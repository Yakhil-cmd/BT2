### Title
ERC20 Asset Transactor is incompatible with "revert on zero transfer" ERC20 tokens, allowing a single XCM leg to abort message processing - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` unconditionally call the Solidity `IERC20::transfer` function on the underlying contract for *any* matched amount, including `0`, without a short-circuit for a zero amount. This mirrors the exact bug class from the referenced Sherlock report (`WrappedAerodromeAM` calling `safeTransfer` with a zero fee against a "revert on zero value" ERC20), except here the caller is the Polkadot SDK XCM executor rather than an AMM contract. ### Finding Description
`ERC20Transactor` is a `TransactAsset` implementation added to let XCM operate on arbitrary ERC20 contracts deployed under `pallet-revive`, matched by `AssetId`s of the form `{parents:0, interior: AccountKey20{key,...}}` (see `prdoc/stable2506/pr_7762.prdoc`). Both entry points:

- `withdraw_asset_with_surplus` (invoked by `WithdrawAsset`/reserve-transfer legs)
- `deposit_asset_with_surplus` (invoked by `DepositAsset`, including `Wild(All)`/`Wild(AllCounted(n))` filters used for `RefundSurplus`, `DepositAsset` after fee-exchange, and reserve/teleport deposit legs)

both take `(asset_id, amount)` from `Matcher::matches_fungibles(what)` and immediately construct an ERC20 `transfer(to, value)` call via `pallet_revive::Pallet::<T>::bare_call`, with **no `if amount == 0 { return Ok(...) }` fast path** before invoking the external contract. Contrast this with the native `fungible`/`fungibles` transactors (`FungibleTransferAdapter`, `FungiblesTransferAdapter`) that delegate to `pallet_balances`/`pallet_assets`, whose internal transfer implementations already special-case zero amounts as no-ops (as seen throughout the codebase, e.g. `register_relayer_reward`, `make_payout`, `do_reward_payout`, all of which `return`/no-op on `amount.is_zero()`).

Because the ERC20 contract is attacker-deployed and arbitrary (that is the entire point of the feature — "any chain uses pallet-revive... you can support ERC20s"), a token author can implement `transfer` to `require(value != 0)` (a documented "weird ERC20 behaviour" class explicitly called out by the Sherlock report). When such a token is registered as an XCM asset on Asset Hub (or any chain using this transactor), any XCM program that ends up calling `withdraw_asset`/`deposit_asset` with a `0`-valued leg for that asset — e.g. a multi-asset transfer where fee deduction leaves an exact-zero remainder, or a `RefundSurplus`/`DepositAsset(Wild(All))` step that tries to return a zero leftover of that ERC20 — will have the underlying `bare_call` revert, causing `XcmError::FailedToTransactAsset("ERC20 contract reverted")`.

### Impact Explanation
A failed `TransactAsset` step causes the XCM instruction to error, which aborts execution of the remainder of the program. Depending on the surrounding barrier/error-handling configuration this can:
- Cause legitimate, otherwise-successful multi-asset XCM messages (e.g. teleports/reserve-transfers bundling a zero-value ERC20 leftover, or a compound `ExchangeAsset` + `DepositAsset(Wild(All))` sequence) to fail entirely, trapping other assets in `AssetTrap` and requiring manual claim.
- Result in denial-of-service on any XCM flow that happens to produce a `0` amount for that specific ERC20 asset id, without any privileged actor involved — this is purely a function of a registered token's `transfer()` implementation and a normal, permitted XCM execution path (`pallet_xcm::execute`/`send`/reserve-transfer, or `Transact`-driven register/send flows as exercised in `snowbridge_v2_inbound.rs`).

This does not directly cause theft or unbacked issuance; it is availability/DOS-class, matching the "Medium" classification the original report received in the Sherlock contest.

### Likelihood Explanation
Reaching a literal `0`-valued leg for a specific asset in a real XCM program is plausible (fee arithmetic remainders, `RefundSurplus`, `Wild(All)`/`Wild(AllCounted)` deposit filters that happen to match an asset holding of exactly zero, or an `ExchangeAsset` that produces a zero `want` for one asset) but is not the primary/most obvious path — it requires either coincidental zero remainders or a crafted multi-asset XCM program. Given ERC20 asset support via `pallet-revive` is a newly introduced feature (`pr_7762.prdoc`) and there is no test in the codebase asserting zero-amount handling for `ERC20Transactor` (unlike the extensive zero-amount tests found for `pallet-balances`/`pallet-assets`/`transaction-payment`), likelihood is assessed as **Low-Medium**: plausible but requires a specific asset/token composition (an externally-registered ERC20 that reverts on zero transfer) plus a program producing a zero leg for exactly that asset.

### Recommendation
Add a zero-amount short-circuit in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` before invoking `bare_call`, mirroring how native `fungible`/`fungibles` implementations no-op on zero:

```rust
if amount == 0 {
    return Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(0))), weight_limit));
}
```
and similarly for the deposit path returning `Ok(Weight::zero())` without contacting the contract.

### Proof of Concept
No executable PoC was run. This is a code-level analog derived by comparing `erc20_transactor.rs`'s unconditional `IERC20::transfer` call (no `amount == 0` guard) against the confirmed pattern in the source report, and against the codebase's own convention of explicitly guarding zero amounts before any external transfer (`register_relayer_reward`, `make_payout`, `do_reward_payout`, `payout_tip`, etc.). I was not able to fully trace, within the remaining tool budget, a concrete XCM program/asset-id/fee-arithmetic combination in this repository that provably drives `amount == 0` through this exact transactor in a live runtime configuration (e.g. Asset Hub Westend's XCM config), nor did I find or run an integration test exercising this path. This should be treated as a **plausible design gap requiring further reproduction** (constructing an XCM program that yields a `0` fungible leg for an ERC20-backed asset id, executed via `pallet_xcm::execute`/reserve-transfer against a runtime with `ERC20Transactor` wired into `AssetTransactors`) before being escalated with full confidence.
