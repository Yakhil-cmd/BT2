### Title
Webhook signature is verified against an organization secret chosen from unverified payload data, while status/commit updates are applied without any organization or repository scoping — allowing cross-organization forgery of CI statuses and unauthorized merges - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to verify the HMAC signature against by reading `repository.owner.login` out of the **unverified** JSON body itself, not from any authenticated source. Once the signature check passes (using whichever org's secret matched the body), several handlers — most critically `StatusHandler` — process the payload with no organization or repository binding at all, applying attacker-supplied CI status data to any `Commit` row in the entire Shipit installation that matches the given `sha`, regardless of which org/repo it actually belongs to. This breaks the equality: `organization whose secret authenticated the request == organization that owns the data being written`.

### Finding Description
In a multi-org Shipit deployment (explicitly supported and documented, e.g. `config/secrets.development.shopify.yml` configures multiple orgs each with its own `app_id`, `private_key`, and `webhook_secret`), the webhook signature check is: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

This value is used only to pick which org's `webhook_secret` to HMAC-verify the raw payload against — nothing cryptographically ties the verified secret to any specific repository or organization identity beyond a JSON field the attacker also controls.

After verification, event handlers extract the actual acted-upon repository from a *different* field of the same untrusted body, `repository.full_name`: [3](#0-2) 

Nothing enforces that `repository.owner.login` (used for secret selection) matches `repository.full_name` (used for data lookups) — they are independent fields inside the same forgeable JSON document.

The worst case is `StatusHandler`, which doesn't even use `repository_name`/`stacks` scoping — it looks up commits **globally** by sha across the entire installation: [4](#0-3) 

That status is then consulted by `MergeRequest#all_status_checks_passed?`: [5](#0-4) 

and, if satisfied, `ProcessMergeRequestsJob` calls `merge_request.merge!`, which performs a real GitHub merge via the app's GitHub credentials: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who legitimately controls a GitHub App/webhook installation for **any one** organization configured in a multi-org Shipit instance (e.g., their own org, if the operator hosts Shipit for multiple tenants/orgs) can:
1. Sign a forged webhook payload with their own org's `webhook_secret`.
2. Set `repository.owner.login` to their own org (so the correct secret is selected and verification passes).
3. Set the `status` event's `sha` field to the head commit sha of a pull request belonging to a **different** organization's stack.
4. Have Shipit record a fabricated "success" CI status against that foreign commit, satisfying `all_status_checks_passed?` and causing Shipit to auto-merge that PR using the app's GitHub credentials — an unauthorized cross-organization merge.

This matches the Critical impact bucket: "cross-repository writes, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitability requires only that: (a) the operator uses Shipit's supported multi-organization configuration (a documented, first-class feature), and (b) the attacker controls the webhook secret for at least one of the configured organizations (e.g., they administer their own org's GitHub App installation pointed at the shared Shipit instance). No GitHub write access to the victim org, no Shipit session, and no `ApiClient` token are required — only knowledge of one legitimate org secret already reachable to the attacker by design. This is a realistic scenario for any shared/multi-tenant Shipit deployment.

### Recommendation
- Verify the webhook signature using the secret associated with the organization that is actually acted upon (`repository.full_name`'s owner), not a value pulled from an as-yet-unverified field of the same payload — or verify against all configured secrets and require the matching org to equal the org embedded in `repository.full_name`.
- Scope `StatusHandler` (and any other handler) to only update commits/stacks belonging to the repository identified in the verified payload, mirroring the scoping already done via `Handler#stacks` in other handlers, instead of a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` and `attacker-org`, each with distinct `webhook_secret`s (per documented multi-org config).
2. As an administrator of `attacker-org`'s installed GitHub App, compute `X-Hub-Signature` for a crafted JSON body using `attacker-org`'s known `webhook_secret`.
3. Craft the body as a `status` event:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" },
  "sha": "<head sha of a real PR in victim-org/real-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. POST to `/webhooks` with `X-Github-Event: status` and the computed signature.
5. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and verifies successfully with the attacker's own secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (owned by `victim-org/real-repo`), and creates a success `Status` on it — independent of the `attacker-org` values in `repository`.
7. When `ProcessMergeRequestsJob` next runs, the victim's pending merge request now passes `all_status_checks_passed?` and is merged via the app's GitHub credentials, without any legitimate CI success or victim-org authorization.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
