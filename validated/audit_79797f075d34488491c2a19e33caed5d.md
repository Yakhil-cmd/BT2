### Title
Replay of a stale but validly-signed GitHub `membership` "added" webhook re-instates a since-revoked `Membership`, re-granting `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`User#authorized?` grants access based solely on whether a local `Membership` row exists for a team in `Shipit.github_teams`. `WebhooksController#verify_signature` validates only an HMAC of the raw body with no timestamp or nonce, so a previously legitimate, captured `membership` "added" webhook payload+signature pair remains valid forever and can be resent at will. If an operator later removes the user from the GitHub team (deleting the local `Membership` via a "removed" event or `refresh_members!`), replaying the old "added" payload causes `Team#add_member` to recreate the `Membership`, restoring authorization the user no longer has on GitHub.

### Finding Description
The binding that must hold is: `Membership.exists?(team_id: t.id, user_id: u.id) == <u is currently a member of team t on GitHub>`. Nothing in this engine enforces that equality once a signed payload has been observed.

Path: `POST /webhooks` → `Shipit::WebhooksController#verify_signature` calls `Shipit.github(organization:).api.verify_webhook_signature`(the `GitHubApp#verify_webhook_signature`) [1](#0-0)  which is a pure `OpenSSL::HMAC.hexdigest` comparison over `webhook_secret` and the raw request body, with no timestamp, delivery-id, or nonce check [2](#0-1) . Any exact `(body, X-Hub-Signature)` pair that was ever valid stays valid indefinitely and is trivially resendable by anyone who observed it (e.g., via logs, a proxy, a leaked webhook delivery, or GitHub's own webhook redelivery UI accessible to repo/org admins other than the operator, or any party who captured the wire traffic through legitimate access at the time it was sent).

Once past signature verification, `MembershipHandler#process` runs `team.add_member(member)` for an `added` action [3](#0-2) , and `Team#add_member` is `members.append(member) unless members.include?(member)` [4](#0-3) . This check is only against the *current local* `members` association, not against GitHub's current state. So:
- Replaying the *same* "added" event twice while the membership is still present is a no-op: `members.include?(member)` is true, so no new row is created, and even if it were attempted, `Membership` has a DB-level uniqueness validation on `user_id` scoped to `team_id` [5](#0-4) . This part of the question is **not** exploitable — confirmed by the existing test `":membership can append an user twice"` asserting `assert_no_difference` [6](#0-5) .
- However, if the `Membership` row has since been deleted (operator removed the user from the GitHub team, delivered as a `removed` event, or via `Team#refresh_members!` reassigning `self.members`), `members.include?(member)` becomes false. Replaying the old, captured "added" payload+signature then passes `verify_signature` and causes `team.add_member(member)` to recreate the `Membership`, re-granting the user access via `User#authorized?`, which is `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) .

No control in this codebase closes this gap: `drop_unhandled_event` and `check_if_ping` are irrelevant to this flow [8](#0-7) ; the `ExplicitParameters` schema in `MembershipHandler` only validates payload shape, not freshness [9](#0-8) ; and `verify_webhook_signature` performs no replay protection whatsoever.

### Impact Explanation
A replayed "added" event re-creates a `Membership` row for a user who has been removed from the corresponding GitHub team, causing `User#authorized?` to return `true` when it should be `false`. This is an escalation into `Shipit.github_teams` authorization for that specific user/team pair — matching the High severity category ("escalation into `Shipit.github_teams` authorization"). The blast radius is limited to organizations/teams for which the attacker has captured a prior valid "added" webhook delivery for a user later removed; it does not cross-contaminate unrelated repositories/stacks, and does not directly yield RCE, token exfiltration, or unauthorized deploys by itself, though restored authorization could subsequently be leveraged for actions gated by `authorized?`.

### Likelihood Explanation
Preconditions: (1) the attacker must have captured one genuine `membership`/`added` webhook delivery body and its matching `X-Hub-Signature` for the target org/team/user (e.g., from logs, a compromised log sink, GitHub's redelivery history visible to someone with lesser access, or network capture at the time of legitimate delivery — none of these require Shipit or GitHub secrets); (2) the target user must subsequently be removed from the GitHub team so the local `Membership` no longer exists. Given those, the replay itself is a single unauthenticated HTTP POST to `/webhooks` with the exact captured body and header — trivial and infinitely repeatable as long as the org's `webhook_secret` doesn't rotate. The main constraint is obtaining the captured payload in the first place, which is outside Shipit's control but the vulnerability is that Shipit provides no defense (timestamp/nonce/delivery-id tracking) once that payload is observed.

### Recommendation
Add replay protection to the webhook verification path: track and reject previously-seen `X-GitHub-Delivery` IDs (GitHub sends a unique delivery ID per event) within a bounded window, and/or reject payloads whose age (if a timestamp is embedded/available) exceeds a threshold. Additionally, `Team#add_member`/`MembershipHandler` could authoritatively query current GitHub team membership (or rely on periodic `refresh_members!` reconciliation) rather than trusting an "added" event as sufficient proof of current state.

### Proof of Concept
minitest plan (extends `test/controllers/webhooks_controller_test.rb`):
1. Build `membership_params` with `action: 'added'`, `member: { login: 'bob' }`, and a valid team; compute the correct raw JSON body and a real `X-Hub-Signature` (as done via `Shipit.github(organization: 'shopify').api.verify_webhook_signature` stubbing, or using the real HMAC as in the `"verifies webhook signature"` test).
2. POST it once: assert `assert_difference -> { Membership.count }, 1` and `assert_response :ok` — membership created (baseline, same as `":membership can append an user twice"`/`":membership can append an user membership"` tests) [10](#0-9) .
3. Simulate operator-side revocation without a Shipit "removed" webhook: directly `team.members.delete(member)` (or `Membership.find_by(team:, user: member).destroy`) to mimic GitHub-side removal not yet reconciled locally.
4. Re-POST the **identical captured body and signature** from step 1 (same bytes, same header) to `/webhooks`.
5. Assert `assert_difference -> { Membership.count }, 1` again and `assert_response :ok`, and assert `member.reload.teams.include?(team)` is true and `member.authorized?` is true — demonstrating the stale, previously-legitimate payload re-instates authorization after real-world revocation, with the equality `Membership.exists?(...) == <current GitHub membership>` now false (Membership exists, GitHub membership does not).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
