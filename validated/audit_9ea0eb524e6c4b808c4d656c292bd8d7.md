### Title
Webhook signature verification is scoped to a different repository owner than the one the event handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `Shipit::GitHubApp` (and thus which `webhook_secret`) is used to validate the HMAC signature based on `repository_owner`, a value taken from `params.dig('repository','owner','login')` or, if that's absent, from the unrelated top-level `params.dig('organization','login')` field. Once verification passes, the full raw payload is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and every handler (`PushHandler`, pull-request handlers, etc.) determines the repository/stack to act on from a completely different field — `payload.dig('repository','full_name')` (`Handler#repository_name`). Nothing binds these two fields together.

### Finding Description
The equality that should hold is:

`organization used to select verify_webhook_signature's secret == organization that owns the repository the handler mutates`

In `verify_signature`: [1](#0-0) [2](#0-1) 

the org used to pick the `GitHubApp` (and therefore the `webhook_secret` used in the HMAC check) is `repository.owner.login`, falling back to the sibling top-level `organization.login` key when `repository.owner` is absent.

`GitHubApp#verify_webhook_signature` trivially returns `true` when that org's `webhook_secret` is blank: [3](#0-2) 

This is a legitimate, documented configuration state — the setup docs show `webhook_secret` as an optional field for every org in the multi-org schema: [4](#0-3) [5](#0-4) 

Once the request clears `verify_signature`, the base `Handler` class (used by `PushHandler` and every other webhook handler) resolves the repository to act on independently, from a different JSON path: [6](#0-5) [7](#0-6) 

Because `repository.owner.login`/`organization.login` (used only for signature-secret selection) and `repository.full_name` (used to look up the `Repository`/`Stack` to mutate) are two independent, attacker-controlled fields in the same unsigned-until-verified JSON body, an attacker can craft a payload where:
- `repository.owner.login` is omitted and `organization.login` is set to any org configured on the instance that happens to have no `webhook_secret` set (or, in a multi-org install, any org an admin has not yet configured a secret for) — causing `verify_webhook_signature` to short-circuit to `true` regardless of the actual (garbage or missing) `X-Hub-Signature`.
- `repository.full_name` is set to `"any-other-org/any-tracked-repo"`, pointing at a stack belonging to a completely different, properly-secured organization.

`PushHandler#process` then resolves stacks via `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)` on them, enqueuing `GithubSyncJob` for a repository the attacker was never authenticated against: [8](#0-7) 

`GithubSyncJob` fetches commits, appends them to the stack, and (when nothing changed) still triggers `CacheDeploySpecJob`; appended commits feed directly into `Stack#next_commit_to_deploy` / `trigger_continuous_delivery`, which is exercised in the test suite as the mechanism that actually schedules a `Deploy`: [9](#0-8) 

So a forged, effectively-unverified push event for a victim organization's repository can inject attacker-chosen commit metadata into that stack's commit history and can trigger the stack's continuous-delivery deploy pipeline, entirely bypassing the intended per-organization HMAC binding.

### Impact Explanation
This breaks the "organization that authenticated" vs. "repository that is written" binding required by the rules. The practical outcome is an unauthenticated request causing `GithubSyncJob`/`stack.sync_github` to run against a stack in an organization the request was never validated for, and (via continuous delivery) potentially triggering an unauthorized deploy — a Critical impact per the stated criteria ("an unauthorized deploy, rollback or merge"), reachable without any Shipit session, `ApiClient` token, `webhook_secret`, or repository write access.

### Likelihood Explanation
Exploitability is conditioned on the instance running the multi-org `secrets.github` schema with at least one configured organization lacking a `webhook_secret` — a state the engine's own code and shipped example configs treat as normal/supported (`webhook_secret: # nil`), not as a hardening requirement. Given that, no credential, token, or session is needed by the attacker; a single crafted HTTP POST to the public webhooks endpoint suffices, since `WebhooksController` is not behind any authentication before `verify_signature` runs.

### Recommendation
Bind signature verification to the same repository identity that handlers subsequently act on: derive `repository_owner` strictly and only from `repository.full_name`'s owner segment (the same field `Handler#repository_name` uses), reject payloads where `repository.owner.login` is absent instead of falling back to the sibling `organization.login` key, and additionally validate — after signature verification — that every handler's resolved `Repository`/`Stack` actually belongs to the organization that was authenticated in `verify_signature`, rejecting or dropping events where they diverge.

### Proof of Concept
1. Configure Shipit with the multi-org `secrets.github` schema (as in `config/secrets.development.shopify.yml`) with two orgs: `attacker-org` (no `webhook_secret` set) and `victim-org` (has `victim/app` tracked as a Shipit stack, with `webhook_secret` set).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and an arbitrary/garbage `X-Hub-Signature`, and JSON body:
   ```json
   {
     "organization": { "login": "attacker-org" },
     "repository": { "full_name": "victim-org/app" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>"
   }
   ```
   Note `repository.owner` is omitted, so `repository_owner` in the controller resolves to `attacker-org` (via the `organization.login` fallback) — `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
3. `Shipit::Webhooks.for_event('push')` runs `PushHandler` with the full payload; `Handler#repository_name` reads `payload.dig('repository','full_name')` = `"victim-org/app"`, resolves the real victim stack, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`.
4. `GithubSyncJob` runs against the victim's stack, and depending on continuous-delivery configuration, can trigger `Deploy` scheduling for that stack — all without ever supplying `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
