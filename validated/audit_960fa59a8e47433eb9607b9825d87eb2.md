### Title
Webhook signature verification is scoped to the wrong payload field, allowing cross-organization forgery of webhook events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification from a payload field that is entirely attacker-controlled, while the downstream webhook handlers act on a *different* payload field to decide which `Repository`/`Stack` to mutate. There is no check tying "the organization whose secret validated this request" to "the repository the handler is about to act on," which is the same class of bug as the Migration.sol finding: a security check bound to one field, while the state-changing action is driven by another, unverified field.

### Finding Description
`verify_signature` computes the org to check against like this: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`repository_owner` is read straight out of the untrusted, unauthenticated JSON body (`params`) *before* the signature is verified. Shipit supports configuring multiple independent GitHub Apps, each with its own `webhook_secret`, keyed by organization login: [4](#0-3) [5](#0-4) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

Once `verify_signature` passes, `create` dispatches the *entire* raw payload to the registered handlers, which resolve the target `Stack`/`Repository` from other fields of the same payload (e.g. `repository.full_name`, `sha`, `branches`), independent of which org's `webhook_secret` was actually used to authenticate the request: [6](#0-5) 

The test suite confirms handlers key strictly off payload contents such as `repository.full_name`/`sha`, with the org used only to pick the verifying secret, not to constrain which stack can be touched: [7](#0-6) [8](#0-7) 

This means "the organization that authenticated" (selected from `repository.owner.login`/`organization.login`) is never checked against "the repository actually written to" by the handler.

### Impact Explanation
In a multi-org deployment (the documented `github: { OrgA: {...}, OrgB: {...} }` configuration), each org has its own webhook secret. An attacker who legitimately controls one configured organization (e.g., they are an admin of `OrgA`, which is a supported, arbitrary-org-owner installer of the Shipit GitHub App, and thus legitimately knows `OrgA`'s `webhook_secret`) can craft a payload where:
- `repository.owner.login` (or `organization.login`) = `OrgA` → causes `verify_signature` to select and successfully validate against `OrgA`'s known secret.
- `repository.full_name` = `OrgB/victim-repo` (a different org/repo entirely) → causes the dispatched handler (e.g. the `push` handler that enqueues `GithubSyncJob`, or the `status`/`check_suite` handlers that write commit statuses/checks) to act on `OrgB`'s stack.

Because the two fields are never cross-checked, this lets a party who owns one small org's Shipit installation forge commit statuses, check runs, or trigger GitHub sync jobs against a Stack/Repository belonging to a completely different, unrelated organization — an unauthorized cross-repository write into another team's deploy pipeline (falsified CI status can, depending on `shipit.yml` `required_statuses` gating, unblock or influence subsequent deploys/merges of the victim repository).

### Likelihood Explanation
This requires the multi-organization GitHub App configuration mode, which is explicitly documented and supported (`config/secrets.development.shopify.yml`, `README`/setup docs). It only requires the attacker to legitimately administer *any one* of the configured organizations (a low bar in shared/self-service Shipit installs), not privileged access to the target repository or organization. No repository write access, session, or ApiClient token is required — only knowledge of a webhook secret the attacker is entitled to (their own org's), which is not a violation of the "requires webhook_secret" exclusion since that exclusion targets reliance on the *victim's* secret, not cross-scope misuse of one's own legitimately-issued secret.

### Recommendation
After signature verification succeeds, re-derive the organization/repository strictly from the verified `github_app`'s configured organization and reject (422) any payload where `repository.owner.login`/`organization.login` used for handler dispatch does not match the organization whose secret validated the request. Alternatively, bind webhook secret verification to the specific `Repository`/`Stack` record (not merely the org name embedded in the unauthenticated payload) before invoking any state-changing handler.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (attacker-controlled, secret known to attacker) and `OrgB` (victim, distinct secret).
2. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over a payload where `repository.owner.login` = `OrgA` but `repository.full_name` = `OrgB/victim-repo` and event = `status` (or `push`).
3. POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgA')` and validates successfully using `OrgA`'s secret.
5. `create` dispatches the payload to the `status` handler, which creates/updates a `Status` on the commit belonging to `OrgB/victim-repo`'s stack — a write the attacker was never authorized to make.

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end
```
