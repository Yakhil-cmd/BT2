### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` vs `repository.full_name` binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to verify the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` [1](#0-0) . Once the signature check passes, the actual event handlers resolve the target `Repository`/`Stack` using a *different* field from the same untrusted payload: `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing in the controller or in `Repository.from_github_repo_name` cross-checks that `full_name`'s owner segment actually matches the `owner.login` value that was used for signature verification [3](#0-2) .

### Finding Description
Multi-organization Shipit deployments configure one `webhook_secret` per GitHub organization, looked up via `Shipit.github_app_config(organization)` and keyed by `Shipit.github(organization:)` [4](#0-3) . `verify_signature` picks the secret to use purely from `repository_owner` (or `organization.login` fallback), computed before the signature has been checked:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Once `verified` is true, `create` dispatches the whole raw payload to handlers such as `PushHandler`, `OpenedHandler`, `LabeledHandler`, etc. These handlers independently derive the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` [2](#0-1) [6](#0-5) , and `Repository.from_github_repo_name` simply splits that string on `/` to look up owner/name with no relation to `repository.owner.login` [3](#0-2) .

This breaks the binding: `organization that authenticated the signature == repository that is written`. In a genuine GitHub webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always the same value, so this divergence never occurs naturally — but the engine never enforces it. An attacker who legitimately controls (or has been granted) an organization "OrgA" registered in Shipit's multi-org config, and therefore can produce a validly-signed webhook using OrgA's `webhook_secret` (e.g., by triggering a real event from their own repository, or by knowing/leaking their own org's configured secret which is scoped to them), can instead craft a payload where:
- `repository.owner.login = "OrgA"` (used only to pick the verification secret)
- `repository.full_name = "OrgB/victim-repo"` (used by the handler to pick the target Stack)

The signature computed over the full raw body with OrgA's secret is valid, `verify_signature` passes, and the handler then acts on `OrgB/victim-repo`'s stacks — for example, triggering `stack.sync_github(expected_head_sha:)` [7](#0-6) , or archiving/unarchiving/provisioning review stacks belonging to a repository the attacker does not own [8](#0-7) [9](#0-8) .

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker with only one legitimate organization's webhook-signing capability can forge webhook events that are accepted as authentic for a completely different organization/repository's stacks (e.g., forcing a resync to an attacker-chosen `expected_head_sha`, or archiving/provisioning review stacks for a victim repository). This matches the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires the attacker to already control (or otherwise be able to produce validly-signed webhooks from) at least one organization registered in the same multi-org Shipit deployment — a precondition specific to multi-tenant configurations using the per-organization `github_app_config` scheme. Within that precondition, no further privilege (no Shipit session, no API token) is needed; only crafting a JSON payload with divergent `owner.login` and `full_name` fields and a valid signature computed over it with the attacker-controlled organization's secret. Given multi-org Shipit setups exist and are explicitly supported (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS`), this is realistic in that class of deployment, though it does not apply to a single-organization Shipit instance where there's only ever one webhook secret.

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, enforce that the organization used to select and validate the webhook secret matches the owner segment of `repository.full_name` (and `organization.login` where present) before dispatching to handlers. Reject the request (422) if they diverge.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub config, i.e. `secrets.github` keyed by organization (`OrgA`, `OrgB`), each with its own `webhook_secret` [10](#0-9) .
2. Attacker controls "OrgA" (registered in Shipit) and can obtain a valid HMAC signature for arbitrary payload bytes signed with OrgA's `webhook_secret` (e.g. by triggering push events on their own OrgA repo and observing GitHub's `X-Hub-Signature`, or via any legitimate channel that produces a signed payload for OrgA).
3. Craft payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Sign the exact raw body with OrgA's `webhook_secret` and send as `X-Hub-Signature`, with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully [11](#0-10) .
6. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stacks [7](#0-6)  — an unauthorized cross-organization write, despite the attacker never having authenticated as, nor holding any credential for, OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
