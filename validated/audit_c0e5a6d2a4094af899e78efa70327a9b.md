Based on my research, I've identified a strong analog to the CVE-2020-12059 bug class (malformed/incomplete attacker-supplied input reaching an unchecked property/array access before full structural validation, causing an unhandled exception that crashes the whole process).

### Title
Unvalidated `payload.outputs` in AA trigger extraction can crash the whole node process - (File: `aa_composer.js`)

### Summary
`aa_composer.getTrigger()` extracts payment outputs from a unit's messages to build the AA trigger object, but it dereferences `payload.outputs` as an array without first checking that it actually is an array or even present. Crucially, `validateAATrigger()` is executed in `validation.js`'s `async.series` pipeline *before* `validateMessages()` (which is what normally enforces that a `payment` message's `payload.outputs` is a well-formed array) [1](#0-0) . Because the schema of `objUnit.messages[].payload` is attacker-controlled JSON at this point in validation, a unit whose `payment` message has a missing, `null`, or non-array `outputs` field can reach the unchecked `.forEach()` call and throw a raw `TypeError`.

### Finding Description
`getTrigger()` only checks that `message.app === 'payment' && message.payload` is truthy before calling `payload.outputs.forEach(...)`: [2](#0-1) 

It never validates that `payload.outputs` is actually an `Array`. Compare this with the equivalent output-building code inside `handleTrigger`, which explicitly checks `!Array.isArray(payload.outputs)` before iterating [3](#0-2) ; that defensive check is absent from `getTrigger()`.

Any thrown exception that is not caught by a `try/catch` and not passed through the `validate()` `async.series` error-callback chain propagates up as an uncaught exception. `network.js` installs a global handler that intentionally **re-throws** to crash the process rather than let it continue in a possibly inconsistent state: [4](#0-3) 

This is architecturally analogous to the Ceph RGW bug: malformed attacker input (there, tagging XML; here, a malformed `payment` message payload) reaches code that assumes a well-formed structure before validation is complete, dereferences a missing/incorrectly-typed field, and crashes the whole server process.

### Impact Explanation
A successful trigger of this bug crashes the entire ocore node process (hub, full node, or witness), not just the invalid unit. Since `process.on('uncaughtException')` deliberately re-throws to terminate the process, this results in denial of service for the whole node — it becomes unable to validate, relay, or confirm any further units until manually restarted. This matches the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
`getTrigger()` is invoked from `network.js` while handling units in flight — e.g. in the dry-run path executed right in `handleJoint`'s `ifOk` callback (`aa_composer.getTrigger(objJoint.unit, address)` at `network.js:1278`) and, based on call-site count and the pipeline ordering (`validateAATrigger` before `validateMessages`), from the AA-trigger-detection path in `validation.js`. An unprivileged peer can post (via `handlePostedJoint`/`handleOnlineJoint`) a unit whose `payment` message targets an AA address and has `payload = {asset: 'base'}` (no `outputs` key) or `payload.outputs` set to a non-array (e.g., a string or number) — a single-author unit with no valid authentifiers is exactly what is treated as a "possible AA" trigger candidate at `validation.js:150` [5](#0-4) . This makes the path reachable by any unprivileged unit poster without special node cooperation.

I was not able to directly view the full body of `validateAATrigger()` in `validation.js` (only its call site and location in the pipeline were confirmed), so the exact internal call chain from `validateAATrigger` to `getTrigger` is inferred from code structure and naming rather than fully confirmed by direct inspection — this is the main remaining uncertainty in the analysis.

### Recommendation
Add an explicit `Array.isArray(payload.outputs)` check (and reject/skip the message if it fails) in `aa_composer.getTrigger()` before calling `.forEach()`, mirroring the defensive check already present later in `handleTrigger`/`sendUnit`. More broadly, ensure any code that runs before full message-schema validation (as `validateAATrigger` does, ahead of `validateMessages`) treats all `payload` fields as untrusted and performs type/shape checks before use.

### Proof of Concept
1. Construct (or have a light client / peer post) a unit with:
   - A single author with no `authentifiers` and no `content_hash` (so it is treated as a "possible AA" trigger, per `validation.js:150`).
   - A `messages` array containing one message: `{ app: 'payment', payload: { asset: 'base' } }` — i.e. omit the `outputs` field entirely (or set it to `null`/a string).
2. Submit this unit to a node via the normal joint-posting/broadcast path (`handlePostedJoint` / `handleOnlineJoint` in `network.js`).
3. During validation/trigger-detection processing, `getTrigger()`'s `payload.outputs.forEach(...)` throws `TypeError: Cannot read properties of undefined (reading 'forEach')` (or similar), which is not caught, propagates to `process.on('uncaughtException')`, and crashes the entire node process.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
