### Title
Webhook `status` events write commit statuses across all repositories regardless of the authenticated organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` binds trust to a single GitHub organization — the one identified by `repository.owner.login` (or `organization.login`) in the incoming payload — by looking up that organization's webhook secret and validating the HMAC signature against it. However, `StatusHandler#process`, which handles the resulting `status` webhook event, updates commit statuses by a bare `sha` lookup across the *entire* `Commit` table, with no scoping to the repository/organization that was actually authenticated. This breaks the intended binding: `organization authenticated == repository written`.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for signature verification purely from the payload itself: [1](#0-0) [2](#0-1) 

The signature is checked using `Shipit.github(organization: repository_owner).verify_webhook_signature`, i.e. trust is scoped to whichever organization's GitHub App config matches `repository.owner.login` from the payload. Once that check passes, the raw JSON is dispatched to registered handlers for the event type with no further validation of which repository the payload actually concerns: [3](#0-2) 

For `status` events, `StatusHandler#process` looks up commits solely by their `sha`, with **no filter on repository or stack**: [4](#0-3) 

Contrast this with `PushHandler#process`, which correctly scopes affected stacks: `stacks.not_archived.where(branch:)` — `stacks` is derived from the repository identified in the payload: [5](#0-4) 

`StatusHandler` has no equivalent scoping. `Commit.where(sha: params.sha)` matches every `Commit` row in the entire Shipit instance sharing that sha — across every stack, repository, and organization — and calls `create_status_from_github!` on each. This means: the *organization whose webhook secret authenticated the request* is not the same as *the repository/stack whose commit status gets mutated*.

### Impact Explanation
An attacker who controls (or is a legitimate, unprivileged contributor able to trigger CI/status events on) any GitHub organization/repository that this Shipit instance is configured to track can send/trigger a `status` webhook signed with **that org's own webhook secret** (which they may know, since they administer that org's GitHub App, or which may be unset/blank — `verify_webhook_signature` returns `true` when no `webhook_secret` is configured, per `lib/shipit/github_app.rb`). By setting the `sha` field to a commit sha belonging to a *different* tracked stack/organization, the attacker can inject an arbitrary CI status (e.g. `success`) onto a commit they do not control and have no push access to.

This directly undermines `Commit#deployable?` and `MergeRequest#all_status_checks_passed?`, both of which gate deploys and PR auto-merges on commit status. Forging a passing status on another organization's commit can cause Shipit to treat an unreviewed/failing commit as deployable, triggering an unauthorized continuous deployment or an unauthorized pull-request merge on a repository the attacker never authenticated against — matching the Critical impact category of "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own organization/repository being one of the (possibly many) organizations configured in `config/secrets.yml` under `github:` for this Shipit instance, and (2) the ability to trigger a `status` event for their own repository (trivial — any push or CI run naturally generates one, or the attacker can directly call GitHub's Create Status API against their own repo). No access to another organization's secrets, tokens, or repository is needed. The `sha` collision with a target commit is the main practical constraint, but Shipit environments commonly track many repositories/organizations behind a single instance, and commit shas for well-known base commits (e.g., shared open-source dependencies, forked repos, or repos mirrored/forked from the target) can realistically coincide.

### Recommendation
Scope `StatusHandler#process` (and any other handler that resolves state by `sha` alone) to the stacks/repositories that belong to the authenticated repository from the payload — mirroring the approach used in `PushHandler`, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` where `stacks` is derived from the verified `repository.full_name`/`repository.owner.login`, rather than a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Attacker administers (or has commit/status-creation rights on) `github.com/attacker-org/decoy-repo`, which is registered as a Shipit-tracked repository (`Repository` with `owner: "attacker-org"`).
2. Shipit's `config/secrets.yml` (per `docs/setup.md`'s multi-org format) has a `webhook_secret` configured (or left blank, per `lib/shipit/github_app.rb` `verify_webhook_signature` returning `true` when blank) for `attacker-org`.
3. Attacker identifies a target commit `sha` belonging to a different, unrelated Shipit-tracked stack (`victim-org/victim-repo`) that they want marked as deployable — e.g. because it's currently pending/failing CI.
4. Attacker triggers (or replays, signed with `attacker-org`'s secret) a GitHub `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "name": "decoy-repo" }
}
```
5. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"` and validates the signature against `attacker-org`'s webhook secret — which the attacker controls/knows — so the signature check passes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit in `victim-org/victim-repo`, and calls `create_status_from_github!`, marking it `success` even though the request was never authenticated for `victim-org`.
7. If `victim-org/victim-repo`'s stack has `continuous_deployment: true` or an open merge request awaiting this status, Shipit will treat the commit as deployable/mergeable and trigger deployment or merge it, per `Stack#trigger_continuous_delivery` / `MergeRequest#all_status_checks_passed?`.
