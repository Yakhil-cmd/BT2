### Title
Open redirect via unsanitized `omniauth.origin` in `GithubAuthenticationController#callback` - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` redirects the browser to `request.env['omniauth.origin']` with no validation that the value is a local path. Since the origin is populated by OmniAuth from the `origin` query parameter supplied on the initial `/github/auth/github?origin=...` request, an attacker can force a victim's browser, immediately after completing GitHub sign-in on Shipit, to be redirected to an attacker-controlled external URL.

### Finding Description
The broken binding is: `redirect_target_approved_at_request_phase == redirect_target_executed_at_callback`. The engine never enforces this equality to be restricted to same-origin/local paths.

Code path:
- `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb:24,32` builds the login URL with `origin: request.original_url` for internal redirects, but this is only the *legitimate* usage — nothing stops an attacker from directly hitting the OmniAuth entry point with their own `origin` value: `/github/auth/github?origin=https://evil.example`.
- OmniAuth's strategy (external gem, mounted by this engine) persists this `origin` param through the request phase and restores it into `request.env['omniauth.origin']` on `callback_phase`.
- `Shipit::GithubAuthenticationController#callback` (`app/controllers/shipit/github_authentication_controller.rb:8`) reads this value directly: `return_url = request.env['omniauth.origin'] || root_path`, performs sign-in (`sign_in_github`, line 13), sets `session[:authenticated] = true` (line 18), and then calls `redirect_to(return_url)` (line 20) with **no scheme/host filtering, no `_sanitize_url`, no allow-list, no `local?`/`same_origin?` check**.
- No other guard in the codebase (`force_github_authentication`, `require_permission!`, model validations) constrains this value — those guards protect stack/team authorization, not the OAuth redirect target.

Exploit flow: attacker sends victim a link to `/github/auth/github?origin=https://evil.example`. Victim completes the real GitHub OAuth consent (their own credentials, own session). On `callback`, Shipit creates a legitimate authenticated session for the victim and then unconditionally redirects the fully-authenticated browser off Shipit's origin to `https://evil.example`.

### Impact Explanation
This does not leak a Shipit session cookie directly (cookies are not included in cross-site navigation via `Location` redirects, and are typically `HttpOnly`), so the "steal a subsequently-issued cookie via referrer" claim in the question is not substantiated by the code. What is confirmed is: forced completion of the OAuth flow terminating on an attacker-chosen page immediately after authentication, which matches the "session fixation / forced OAuth completion" High-severity category — it enables convincing phishing (the victim believes they just "logged into Shipit" and lands on an attacker page that can request credentials, serve malware, or set up further social-engineering) and is repeatable against any victim without any Shipit privileges. It does not, on its own, grant access to another repository/stack's data, execute commands, or expose secrets.

### Likelihood Explanation
Trivial to trigger: no Shipit secrets, no privileged role, and no non-standard configuration required — just crafting a link with an `origin` query parameter and getting any GitHub user (who already has an account usable with the configured GitHub OAuth app) to click it. Cost to attacker is negligible and the attack is repeatable against any victim.

### Recommendation
Validate `return_url` before redirecting — only allow relative paths within the Shipit engine's routes (e.g., reject absolute URLs / URLs with a `host` different from `request.host`, or maintain an explicit allow-list), similar to Rails' `_sanitize_returning_url`/`url_for(only_path: true)` pattern, and fall back to `root_path` for anything that fails validation.

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback does not redirect to an attacker-controlled absolute URL" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(raw_info: OmniAuth::AuthHash.new(
      id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
      login: 'shipit-user', avatar_url: 'https://example.com',
      api_url: 'https://github.com/api/v3/users/shipit-user'
    ))
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://evil.example'

  get :callback

  # Binding under test: approved redirect target (root_path/local) == executed redirect target
  refute_equal 'https://evil.example', @response.location
  assert_match %r{\A/}, @response.location # must be a local path, not an absolute external URL
end
```
Currently, with the unmodified controller, this test fails because `@response.location == 'https://evil.example'`, confirming the open redirect. [1](#0-0) [2](#0-1)

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
