### Title
Cross-repository status webhook forgery triggers unauthorized `Shipit.user`-attributed continuous delivery deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone (`Commit.where(sha: params.sha)`) with no scoping to the repository that actually sent the webhook, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which correctly restrict to `stacks` derived from `payload.dig('repository', 'full_name')`. An attacker who owns any Shipit-integrated repository can send a genuinely GitHub-signed `status` webhook naming a victim repository's commit SHA (public, discoverable info) with `state: "success"`, causing a `Status` to be created on the victim's commit, which cascades into an autonomous, `Shipit.user`-attributed deploy on a stack the attacker neither owns nor operates.

### Finding Description
The broken binding: `repository_owner_of(webhook) == repository_owner_of(commit.stack)` — the code never checks this and it can be false.

Path:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository', 'owner', 'login')`). This only proves the request was legitimately signed *for that org* — it says nothing about which commit/stack the payload is allowed to touch. [1](#0-0) 
- `StatusHandler#process` then does a completely unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1) 
- Compare with `CheckSuiteHandler`/`PushHandler`, which correctly scope via the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) before touching any commit. [3](#0-2) [4](#0-3) 

- Creating the `Status` record fires `after_commit :schedule_continuous_delivery` → `commit.schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` if the stack is `continuous_deployment?` and deployable. [5](#0-4) [6](#0-5) 
- `ContinuousDeliveryJob#perform` calls `stack.trigger_continuous_delivery`, which (per the question, consistent with `Stack#build_deploy`/`#trigger_deploy` patterns) runs `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` — a deploy owned by `Shipit.user`, not any operator. [7](#0-6) 

Exploit request: attacker POSTs a `status` event to `/webhooks` (X-Github-Event: status, correctly HMAC-signed with the attacker's own org's webhook secret) with body `{"sha": "<victim commit sha>", "state": "success", "repository": {"owner": {"login": "<attacker-org>"}}, ...}`. `repository_owner` used for signature verification is the attacker's own org, so `verify_webhook_signature` passes with a secret the attacker legitimately knows. `StatusHandler` never checks that this SHA belongs to a commit under `attacker-org`'s repository — it matches by SHA only, globally.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate authenticity of the sender and shape of the payload; none of them, nor any model validation, check that the commit being mutated belongs to the repository that authenticated the request. This is a genuine "payload for one repository mutating another's stack/commit" bug, not a configuration issue — even with `webhook_secret` correctly configured everywhere, the vulnerability is exploitable by any onboarded external repo owner against any other stack's public commit SHA.

### Impact Explanation
An attacker who controls (or merely has webhook-signing capability for) one Shipit-tracked repository can inject fabricated CI status onto commits of a *different* stack/repository, and if that victim stack has continuous deployment enabled, cause an unauthorized deploy to be enqueued and executed, attributed to the privileged `Shipit.user` system account rather than any operator who reviewed/approved it. This is a cross-tenant integrity break (payload for repo A mutating stack/commit/deploy of repo B) and an unauthorized-deploy trigger — both explicitly listed Critical impact categories. It is repeatable against any victim stack whose commit SHAs are discoverable (trivial for public repos) and requires no GitHub secrets, sessions, or API tokens belonging to the victim.

### Likelihood Explanation
Preconditions: attacker needs some Shipit-integrated repository under their control (to legitimately sign a webhook with a secret they know) and the victim stack must have `continuous_deployment: true` and be otherwise deployable (no concurrent task, within schedule window). No knowledge of the victim's webhook secret, API tokens, or session is required — only the victim commit's public SHA. This is low-cost, fully automatable, and repeatable against any number of target stacks in the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from `payload.dig('repository', 'full_name')` and restrict the commit lookup to `stack.commits.where(sha: params.sha)` for each stack in that scope, rather than a global `Commit.where(sha:)` query.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from an unrelated repository must not create a status on another stack's commit" do
  victim_stack = shipit_stacks(:shipit)              # continuous_deployment: true, deployable
  victim_commit = victim_stack.commits.last
  attacker_owned_org = "attacker-org"                # legitimately integrated, different repo

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => attacker_owned_org } }
  }.to_json

  # signature legitimately computed with attacker-org's own known webhook secret
  Shipit.github(organization: attacker_owned_org).stubs(:verify_webhook_signature).returns(true)

  assert_no_difference 'victim_commit.statuses.count' do
    assert_no_enqueued_jobs only: ContinuousDeliveryJob do
      post :create, body:, as: :json
    end
  end
  # Currently FAILS: a Status IS created and ContinuousDeliveryJob IS enqueued for victim_stack,
  # then perform(victim_stack) results in Deploy.last.user == Shipit.user
  # with no operator (User) ever having approved or triggered it.
end
```
