### Title
Cross-tenant `PullRequest#github_pull_request` overwrite via organization/repository binding mismatch in `EditedHandler` - (File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload against the GitHub App secret of the organization named in `repository.owner.login` (or `organization.login`), but `EditedHandler#pull_request` resolves and mutates a `PullRequest` using an entirely different field, `repository.full_name`, taken from the same attacker-supplied JSON body. Nothing ties these two fields together, so a payload signed under one organization's secret can reference and mutate a different organization's repository/PR.

### Finding Description
The broken binding is: `repository_owner (used to select the HMAC verification key)` == `owner_of(repository.full_name) (used to select the PullRequest row that gets overwritten)`. This is false in general because both values come from the same freely attacker-controlled JSON body and are never cross-checked.

Trace:
- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then verifies the raw POST body's HMAC against that organization's `webhook_secret`. [1](#0-0) [2](#0-1) 
- Once signature verification passes, `Webhooks.for_event('pull_request')` dispatches to `EditedHandler.call(params)`, and `EditedHandler#process` calls `pull_request.update(github_pull_request: params.pull_request)` when a matching row is found. [3](#0-2) 
- `EditedHandler#pull_request` and `#repository` locate the target row purely from `params.repository.full_name`, joined through `stack: :repository`, with no reference back to `repository_owner`/the organization that was authenticated. [4](#0-3) 

Because `repository.owner.login` and `repository.full_name` are independent keys inside the same JSON body that the attacker fully controls, an attacker who can produce a validly-signed payload for "their org" can put the victim's `full_name` (e.g., `"victim-org/victim-repo"`) in the body while keeping `repository.owner.login`/`organization.login` set to their own org so `verify_signature` resolves the correct (attacker-known) secret. The `ExplicitParameters` schema in `EditedHandler` only checks types/presence of fields, not that `full_name`'s namespace matches `repository_owner`, so it does not close this gap. `drop_unhandled_event` only checks that a handler is registered for the event and provides no authorization semantics.

### Impact Explanation
A successful request lets an attacker who controls one organization/repository silently rewrite the cached GitHub data (`title`, `head.sha`, `head.ref`, etc.) on an arbitrary victim `PullRequest` row belonging to a different organization/repository, as long as they know the victim's PR `number` and repo `full_name` (both public information on GitHub). This is a cross-tenant write of attacker-controlled commit-ref data into another tenant's stack, matching the "payload for one repository mutating another's stack/commit/task" Critical category, since `github_pull_request['head']['sha']` can subsequently be trusted by merge/deploy logic. This is repeatable against any victim repository/PR number for as long as the attacker's own org signature remains valid.

### Likelihood Explanation
The attack requires the attacker to be able to produce a request whose HMAC signature verifies for some organization known to Shipit (their own, per the question's stated precondition) and requires a pre-existing `PullRequest` row for the victim repo/number, joined via `stack: :repository`. Given that precondition, the attacker only needs to know the victim repository's `full_name` and PR `number`, both of which are public on GitHub, making exploitation low-cost and fully repeatable.

### Recommendation
In `EditedHandler` (and the sibling `PullRequest` handlers using the same `stacks: {repositories: {id: ...}}` pattern), verify that the authenticated `repository_owner` used in `WebhooksController#verify_signature` matches the owner segment of `params.repository.full_name` before performing any lookup/update — e.g., pass the verified organization through to the handler and assert `repository.owner_login == params.repository.full_name.split('/').first` (or equivalent) prior to calling `pull_request.update`.

### Proof of Concept
Minitest plan (models/webhooks/handlers/pull_request/edited_handler_test.rb-style, or controller-level):
```ruby
test "cross-tenant edited webhook must not overwrite a PullRequest belonging to a different organization" do
  victim_pr = shipit_pull_requests(:review_stack_review) # fixture PR belonging to victim repo/org
  victim_full_name = victim_pr.stack.repository.full_name
  victim_number = victim_pr.number

  payload = payload_parsed(:pull_request_opened)
  payload["action"] = "edited"
  payload["number"] = victim_number
  payload["repository"]["full_name"] = victim_full_name          # points at victim repo
  payload["repository"]["owner"]["login"] = "attacker-org"       # authenticated org != victim org
  payload["pull_request"]["head"]["sha"] = "attacker-controlled-sha"

  # Simulate verify_signature succeeding under attacker-org's own (attacker-known) secret
  Shipit.github(organization: "attacker-org").stubs(:verify_webhook_signature).returns(true)

  assert_no_changes -> { victim_pr.reload.github_pull_request.dig("head", "sha") } do
    post :create, body: payload.to_json, as: :json
    @request.headers['X-Github-Event'] = 'pull_request'
  end
  # Equality under test: repository_owner ("attacker-org") == owner_of(victim_full_name) ("victim-org") must be false,
  # and the fix must ensure the update is rejected in that case.
end
```
This test asserts that when `repository_owner` (the org that authenticated the request) differs from the owner encoded in `repository.full_name`, `github_pull_request['head']['sha']` on the victim PR must remain unchanged; under the current code it changes to the attacker-controlled value.
