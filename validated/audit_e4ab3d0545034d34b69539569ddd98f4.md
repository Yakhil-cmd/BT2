### Title
Definer-controlled attestor list re-evaluated at spend time freezes previously-held `spender_attested` asset balances (including AA-held funds) - ([File: validation.js])

### Summary
For assets defined with `spender_attested: true`, the check "is the spender currently attested" is evaluated against the *latest* attestor list at spend time rather than pinned to the state when the funds were received. The definer can publish a new `asset_attestors` list at any time via a single-authored `asset_attestors` unit, dropping addresses (or AA addresses) that were previously eligible. Any balance already legitimately held by a now-dropped address becomes permanently unspendable, exactly mirroring the Revert-lend pattern where an admin-adjustable "eligibility" parameter, when changed after the fact, breaks a core downstream function (there: liquidation; here: spending) for positions/holdings that already exist.

### Finding Description
An asset's attestor list is not fixed at asset definition; it can be updated later by the definer through the `asset_attestors` message, validated by `validateAttestorListUpdate`, which only requires the new list be non-empty and sorted — it does not preserve or reconcile previously-attested holders: [1](#0-0) 

When any payment of this asset is validated (public or private, including AA-triggered spends), the eligibility of the *spender* (owner of the input being spent) is checked against the attestor list that is current as of `last_ball_mci` at validation time, not the list that was current when the coin was received: [2](#0-1) [3](#0-2) [4](#0-3) 

`storage.filterAttestedAddresses` / `loadAssetWithListOfAttestedAuthors` compute "currently attested" strictly from the latest attestor-list unit and the attestation records that postdate it, with no fallback to a "grandfathered" state: [5](#0-4) 

The wallet composer path enforces the identical rule when building a spend, so even honest, legitimately-funded holders (or AA addresses) cannot construct a valid spending unit once dropped from the attestor list: [6](#0-5) 

This is structurally the same bug class as the Revert `collateralFactor` issue: a mutable, definer/admin-controlled "is this address/token still allowed" flag is consulted at the time of a later, unrelated operation (spend vs. liquidation) rather than being scoped to when the position was created, so legitimate value that already exists in the system can be stranded by a later, ordinary admin action.

### Impact Explanation
Once an address (a regular wallet or an Autonomous Agent) is removed from an asset's attestor-verified set, any balance of that `spender_attested` asset it already holds becomes permanently frozen: it can never again pass `validatePaymentInputsAndOutputs`'s attestation check, and there is no path to reinstate historical eligibility for a specific unspent output. If the frozen holder is an AA, this is a direct, unrecoverable AA fund loss/freezing scenario — the AA's balance in that asset is stuck in its address forever, and any AA logic (bounce/return payments, DeFi payouts, etc.) that depends on being able to move that balance will fail from that point on. This matches the "AA fund loss or freezing" impact class validated for this report.

### Likelihood Explanation
Likelihood is Medium: updating the attestor list is a completely normal, expected administrative operation for `spender_attested` assets (e.g., to add/drop compliance oracles or revoke a compromised attestor), performed by a single author (the asset definer) with a simple `asset_attestors` message — no special privileges beyond being the original definer, and no cooperation from the affected holder is required. Any definer who rotates or prunes their attestor set will, as an unavoidable side effect, freeze the balances of everyone who was attested only under the old list and has not yet spent.

### Recommendation
Decouple "attested at issuance/receipt time" from "attested at spend time," e.g., by recording the specific attestor-list version (or attestation record) that legitimized each output when it was created and permitting a spend if the input satisfies *either* the currently active list *or* the list version, in effect when the output was received. Alternatively, provide an explicit, definer-controlled migration/grace mechanism (similar to a "revoke with grandfathering window") so that changing the attestor set cannot retroactively strand already-issued value.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true` and attestor list `[X]`.
2. Attestor `X` attests address `H` (or AA address `H`); `H` receives outputs of asset A via a normal payment — validated successfully per `validatePaymentInputsAndOutputs` because `H` is in `arrAttestedAddresses` computed from the list `[X]` (storage.js `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors`).
3. Definer later posts an `asset_attestors` message replacing the list with `[Y]` (validated by `validateAttestorListUpdate`, which has no requirement to preserve previously-attested addresses).
4. `H` now attempts to spend its existing asset A balance. `validatePayment`/`validatePaymentInputsAndOutputs` recomputes `arrAttestedAddresses` from the new list `[Y]`; since `H` is not attested by `Y`, the check `objAsset.arrAttestedAddresses.indexOf(owner_address) === -1` fails and the payment is rejected with "owner address is not attested" (validation.js lines 2506-2507), for every future attempt, permanently. function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
