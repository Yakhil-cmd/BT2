### Title
Webhook signature verified against `repository.owner.login` while all event handlers act on the unauthenticated `repository.full_name` field, enabling cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to check the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. Once the signature is accepted, the raw payload is dispatched unchanged to the event handler via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and every `Shipit::Webhooks::Handlers::Handler` resolves the target `Repository`/`Stack` using a **different** field of the same payload: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so the organization whose secret authenticated the request is not guaranteed to be the repository the handler subsequently writes to. [1](#0-0) [2](#0-1) 

### Finding Description
`verify_signature` uses the attacker-suppliable `repository_owner` to look up the `GitHubApp` and thus the secret it verifies against: `Shipit.github(organization: repository_owner)` → `github_app.verify_webhook_signature(...)`. [3](#0-2) [4](#0-3) 

Crucially, `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically verified, returning `true` unconditionally when no secret is configured: [5](#0-4) 

The setup documentation explicitly marks `webhook_secret` as **optional**, so a multi-organization deployment with one org lacking a secret is a documented, valid configuration, not a misuse of the engine: [6](#0-5) 

After `verify_signature` passes, the controller forwards the *entire, unauthenticated* payload to handlers: [7](#0-6) 

Every handler resolves the affected `Stack`s purely from `payload.dig('repository', 'full_name')`, which is never checked against the `repository.owner.login` value used for signature verification: [2](#0-1) [8](#0-7) 

For example, the push handler uses this repository resolution to trigger a GitHub sync against a stack: [9](#0-8) 

Binding broken (as equality): the organization that authenticated the request (`Shipit.github(organization: repository.owner.login)`, secured — or unsecured — per-org via `webhook_secret`) must equal the repository that is written (`Repository.from_github_repo_name(repository.full_name)`), but the engine never enforces `repository.owner.login == repository.full_name.split('/').first`.

**Before the attack:** an unprivileged internet requester holds no Shipit session, no `ApiClient` token, and no GitHub write access to any tracked repository.
**After the attack:** by crafting one raw POST to `/webhooks` with `X-Github-Event: push`, setting `repository.owner.login` to any organization configured in `secrets.github` **without** a `webhook_secret` (a documented-optional field), and setting `repository.full_name` to any *other* tracked org/repository, the requester causes `verify_signature` to pass (because `verify_webhook_signature` short-circuits to `true` for that org) while the push handler executes `stack.sync_github(expected_head_sha: params.after)` against stacks belonging to the unrelated, "protected" repository — with an attacker-chosen `after` SHA.

### Impact Explanation
This is an unauthenticated, cross-repository write: an attacker with no credentials for the target repository can inject synthetic GitHub events (push, status, check_suite, membership, etc.) that Shipit will process as if they legitimately originated from the target org/repository, because the field used to select the verifying secret is not the field used to select the affected `Stack`/`Repository`/`Team`. This satisfies the Critical impact criterion of cross-repository writes / unauthorized deploy-adjacent action, since `sync_github` drives subsequent deploy eligibility (`expected_head_sha`) for the target stack. The `membership` handler compounds this: it lets the same unauthenticated payload create/modify `Team` and `Membership` records (`find_or_create_team!`, `team.add_member(member)`), which is the basis for `Shipit.github_teams` authorization used to gate access to the whole application. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
The attack requires only a single unauthenticated HTTP POST to the public `/webhooks` endpoint with a hand-crafted JSON body; no signature is even needed if any configured organization has no `webhook_secret` set, which the docs explicitly present as an acceptable, optional configuration. In deployments using `secrets_double_github_app.yml`-style multi-org configuration (as shown in the repo's own test fixtures), the risk of at least one org omitting the secret is realistic. [12](#0-11) 

### Recommendation
Bind the field used for signature verification to the field used for repository resolution: after selecting the GitHub App via `repository.owner.login`, require that `repository.full_name` starts with that same owner (case-insensitively) before dispatching to any handler, and reject (422) on mismatch. Additionally, treat a missing `webhook_secret` as a configuration error rather than "verified" in `GitHubApp#verify_webhook_signature`, or at minimum log/alert loudly and refuse cross-org lookups when no secret is present.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `OrgA` (no `webhook_secret`) and `OrgB` (tracked repository `OrgB/target-repo` with a real stack).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
No `X-Hub-Signature` needs to be correct, because `verify_webhook_signature` returns `true` unconditionally for `OrgA` (blank secret) — see `lib/shipit/github_app.rb` lines 76-83.
3. `verify_signature` passes; `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/target-repo")` (per `app/models/shipit/webhooks/handlers/handler.rb` lines 30-38) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — a repository the attacker never had credentials for.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
