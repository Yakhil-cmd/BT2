### Title
Old credentials are never revoked from git's credential cache/store when git-sync rotates auth tokens - ([File: main.go])

### Summary
`git-sync`'s `StoreCredentials` function only ever calls `git credential approve` to install new credentials; there is no corresponding `git credential reject` call anywhere in the codebase for the URL/credential being replaced. Every credential-rotation path (GitHub App token refresh, `--askpass-url` callback, `--credential`/password-file re-read) funnels through this same one-way "approve" operation, so a previously valid username/password (or GitHub App installation token) can remain usable via git's credential helper even after git-sync has moved on to a new one — directly analogous to the `AmoManager` report where a replaced value keeps its granted access because the revoke step is missing.

### Finding Description
`StoreCredentials` builds a `url=/username=/password=` blob and pipes it to `git credential approve`, but never calls `git credential reject` for the prior value: [1](#0-0) 

This function is the sole credential-installation primitive, and it is called from every rotation path with no “previous credential” bookkeeping or revocation:
- Static `--credential`/password-file entries, re-read every sync cycle to "pick up token rotation" — each refresh just re-`approve`s, it never rejects the old password value it replaces: [2](#0-1) 
- `--askpass-url`, which is documented as returning dynamic/rotating credentials on each sync, calls `StoreCredentials` with whatever the URL returns, again without rejecting the prior value: [3](#0-2) 
- GitHub App token refresh mints a new short-lived installation token and stores it via the same `StoreCredentials` call, leaving the previous token's cache/store entry untouched: [4](#0-3) 

The default credential backend configured by git-sync is `credential.helper = cache --timeout 3600` (an in-memory daemon with a fixed TTL, not tied to git-sync's own rotation cadence): [5](#0-4) 

Because git-sync never issues `git credential reject`, the credential helper (whether the default `cache` daemon or a user/operator-configured `store` file backend set via `--git-config`) is never told that an old value is invalid. Depending on the git credential-matching rules (by protocol+host, optionally +path/username), the previous token can persist in the helper's backing store/socket for up to its own timeout (3600s by default for `cache`, indefinitely for `store`) independent of how frequently git-sync itself refreshes/rotates credentials.

### Impact Explanation
If an upstream token is rotated because the old one is suspected compromised or expired (e.g., GitHub App installation token refresh, `--askpass-url` returning a freshly minted token), git-sync's own credential store/cache is not scrubbed of the old value. Any other process able to talk to the same `git credential-cache` daemon socket (same UID/namespace) or read the same on-disk `store` file during the retention window can still authenticate as the old credential to the remote — this is a credential/token-disclosure and stale-authorization issue analogous to the reported "old AmoManager retains allowance" bug: replacement of the trusted actor/value does not revoke the old one's access.

### Likelihood Explanation
This is reachable purely through git-sync's normal, intended credential-rotation flows — no attacker-controlled repo content or malicious ref is needed to trigger the missing-revocation condition; it fires on every legitimate rotation event (password-file update, askpass response change, GitHub App token refresh). The actual exploitation (another process reading the cache/store) requires local access to the same host/namespace as the credential helper backend, which is the realistic threat model for sidecar credential leakage bugs of this class.

### Recommendation
After successfully storing a new credential for a URL, explicitly reject the previous one for that URL before/after approving the new value, e.g. add a `RejectCredentials(ctx, url, oldUsername, oldPassword)` call (`git credential reject`) in `StoreCredentials`'s callers whenever the credential for a given URL changes, and track the last-stored credential per URL so it can be invalidated on rotation: [1](#0-0) 

### Proof of Concept
1. Run git-sync with `--github-app-*` flags (or `--askpass-url`) so `refreshCreds` periodically calls `RefreshGitHubAppToken`/`CallAskPassURL`, each of which calls `StoreCredentials` → `git credential approve` with a new token for the same repo URL. [6](#0-5) 
2. Observe that no `git credential reject` is ever issued for the token that was active before the refresh. [4](#0-3) 
3. On the host, query the credential helper backend directly (`git credential fill` against the same URL, or inspect the `cache` daemon socket / `store --file` contents) shortly after a token rotation: the previous token entry is still present/usable until its own TTL/backend lifecycle expires, independent of git-sync having replaced it.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
