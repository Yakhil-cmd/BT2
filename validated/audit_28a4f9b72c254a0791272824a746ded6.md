### Title
Cross-repository commit status injection via unscoped `StatusHandler` breaks the webhook-organization-to-repository binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against a *specific organization's* `webhook_secret`, selected using `repository_owner` (`params.dig('repository','owner','login')`), which is itself taken from the unauthenticated JSON body before the signature is even checked structurally per-field. Once the HMAC passes, the event is dispatched to a handler. Every other repository-scoped handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) re-derives the target `Repository`/`Stack` from `payload.dig('repository','full_name')` via `Repository.from_github_repo_name` and filters further (branch, stack membership) before writing anything. `StatusHandler`, however, never consults `repository`/`stacks` at all: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, a global, cross-repository, cross-organization lookup keyed only on `sha`.

### Finding Description
The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login) == organization owning the repository/stack that is written to`.

For `push`, `check_suite`, and `pull_request` events this binding is enforced because the handler scopes its side effects through `stacks`/`repository`, which is built from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [1](#0-0) [2](#0-1) [3](#0-2) 

But `StatusHandler` breaks this pattern completely — it never touches `repository`, `stacks`, or anything derived from the payload's `repository` object; it only requires `sha`/`state`/etc. and performs a global `Commit.where(sha:)` lookup across the entire Shipit instance: [4](#0-3) 

Meanwhile, `verify_signature` picks which organization's secret to validate against using a *different* payload field (`repository.owner.login`), not `repository.full_name`: [5](#0-4) 

Since Shipit supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret` (confirmed by the multi-org secrets fixture with `OrgOne`/`OrgTwo` each having distinct webhook secrets and GitHub Apps): [6](#0-5) 

an operator/admin of one onboarded, low-trust organization (`OrgA`, which legitimately possesses its own valid `webhook_secret` because it is a registered tenant of this Shipit instance) can send a `status` webhook whose signature is valid for `OrgA` (`repository.owner.login: "OrgA"`, HMAC computed over the whole raw body with `OrgA`'s secret) but whose `sha` value corresponds to a commit that actually belongs to a stack/repository owned by a completely different, more privileged organization (`OrgB`). `StatusHandler` performs no check that the commit's `stack.repository` belongs to the organization that authenticated the request, so it will happily call `commit.create_status_from_github!(params)` on `OrgB`'s commit.

This directly flows into `Commit#create_status_from_github!` → `add_status`, which recomputes `status`/`deployable?` and can trigger `stack.schedule_merges` and `ContinuousDeliveryJob` for `OrgB`'s stack: [7](#0-6) [8](#0-7) [9](#0-8) 

By forging a `success` status with an attacker-chosen `context`, the attacker can flip `deployable?` to true on `OrgB`'s pending commit (bypassing real CI/required-status gating) and, if `OrgB`'s stack has `continuous_deployment?` enabled, trigger an unauthorized deploy of `OrgB`'s stack. This is a cross-repository write and can result in an unauthorized deploy — matching the report's core bug class of "a field/organization the signature check covers vs. a repository/commit that ends up being written," analogous to `params.incoming` being unused in the original Solidity report while `params.encumber` (attacker controlled) drove the state change.

### Impact Explanation
This is High/Critical depending on downstream configuration: an onboarded, low-privileged organization can inject/spoof commit statuses for any commit SHA colliding across the entire multi-tenant Shipit instance, without needing access to the victim organization's repository, webhook secret, or GitHub App. Combined with `deployable?`/`schedule_continuous_delivery`, this can cause an **unauthorized deploy** of another organization's stack (matches "unauthorized deploy" impact criterion), and at minimum allows CI/required-status bypass and injection of misleading state into an unrelated stack's commit history/hooks (`Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`), which can itself be consumed by downstream automation.

### Likelihood Explanation
Likelihood is meaningfully high in any multi-tenant deployment (which the engine explicitly supports, per the multi-org secrets fixtures) because:
- The attacker only needs a `webhook_secret` for *any one* organization already registered with this Shipit instance (trivial for them to obtain since they administer that org's own GitHub App integration).
- SHA collision across repositories is not required to be exact-match forgery of another org's real commit — the attacker can wait for a commit with a known SHA to appear in the target stack (SHAs are public via GitHub) and then post a forged `status` webhook for that exact SHA.
- No additional secrets, session, or repository write access to the victim org is needed — only knowledge of the victim's commit SHA, which is public.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve the target repository from `payload.dig('repository','full_name')` via `Repository.from_github_repo_name`, then constrain the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent join through `stack: :repository`) so a status can only ever be written to a commit belonging to the stack(s) of the repository that the verified organization actually owns.

### Proof of Concept
1. Shipit instance is configured with two GitHub Apps/organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls the GitHub App/webhook secret for `OrgA` (legitimately, as an admin of `OrgA`'s own integration).
3. Attacker observes (via public GitHub) that `OrgB/private-repo`'s stack has a pending commit with SHA `abcd1234...` awaiting a passing CI status before it becomes deployable/auto-deployed.
4. Attacker POSTs to `/github/webhooks` with `X-Github-Event: status`, body:
```json
{
  "sha": "abcd1234...",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "full_name": "OrgA/some-owned-repo", "owner": { "login": "OrgA" } }
}
```
signed with `OrgA`'s real `webhook_secret` via `X-Hub-Signature`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature against `OrgA`'s secret.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` globally, matches `OrgB`'s commit, and calls `commit.create_status_from_github!(params)`, injecting the forged `success` status onto `OrgB`'s commit — with no verification that `OrgB` corresponds to the authenticated `OrgA`.
7. If that flips the commit to `deployable?` and `OrgB`'s stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` triggers `ContinuousDeliveryJob`, deploying `OrgB`'s stack based on the attacker-forged status.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
