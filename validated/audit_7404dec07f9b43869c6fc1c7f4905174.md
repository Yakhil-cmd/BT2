### Title
First-deposit / donation share-price inflation in the Uniswap-like market-maker AA template - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The bundled example AA `uniswap_like_market_maker.oscript` computes the price/ratio used to mint and redeem its liquidity-share asset (`mm_asset`) from the AA's raw on-chain `balance[...]` rather than from an internally accounted total. Because `balance[base]`/`balance[asset]` are credited to the AA automatically for *any* payment received — independent of whether the payment matches the "invest" case and independent of whether `mm_asset_outstanding` is updated — an attacker can donate funds directly to the AA address to distort the ratio used for share issuance/redemption. This is the same root-cause pattern as the dTRINITY dLEND "first deposit inflation attack": price/exchange-rate math derived from spendable balance instead of tracked liabilities.

### Finding Description
In the "invest in MM" case, the share price is derived purely from the AA's live balances: [1](#0-0) 

- `$asset_balance`/`$bytes_balance` are computed from `balance[$asset]` / `balance[base]` minus the current trigger's own outputs.
- If either is zero, it's treated as the "initial deposit" and `$issue_amount = balance[base]` (the entire byte balance the AA now holds, not just the sender's contribution), and `mm_asset_outstanding` is incremented by exactly that.
- Otherwise, shares are minted proportional to `trigger.output[[asset=base]] / $bytes_balance` applied to `var['mm_asset_outstanding']`.

Crucially, `balance[...]` reflects the AA's total ledger balance, which is updated unconditionally as soon as any payment unit reaches the AA — before any case in `messages.cases` is even evaluated: [2](#0-1) [3](#0-2) 

and the `balance[asset]` formula operator reads exactly this same live, mutable balance: [4](#0-3) 

Because there is no requirement that every byte/asset unit sent to the AA go through the "invest" case (a sender can just pay bytes/asset to the AA's address with data that doesn't satisfy any `if` condition, or send it alongside a trigger that matches a *different* case), an attacker can inflate `balance[base]` or `balance[$asset]` without correspondingly inflating `var['mm_asset_outstanding']`. The divest/exchange cases also key off these same raw balances: [5](#0-4) 

### Impact Explanation
An attacker who front-runs the very first real deposit (or donates immediately after outstanding shares are reset to a small amount) can:
1. Make a minimal deposit to become the first depositor and receive `$issue_amount = balance[base]` shares for a tiny outlay (only their own tiny contribution counts if `$asset_balance`/`$bytes_balance` are both zero — but the value backing those shares can later be pumped by direct donation).
2. Directly donate raw bytes/asset to the AA address (bypassing the "invest" case, e.g. via a payment not matched by any case, or piggy-backed inside a trigger matching a different branch) to inflate `balance[base]`/`balance[$asset]` without minting new `mm_asset` shares.
3. This skews `$current_ratio`/`$investor_share_of_prev_balance` for subsequent legitimate depositors, causing them to receive disproportionately few shares for their contribution (rounding to zero in the extreme case), while the attacker's existing shares appreciate against the donated funds. The attacker then redeems shares via the "divest MM shares" case to extract value contributed by later depositors — a direct AA fund loss for other users, analogous to the $257k drained in the dTRINITY incident via inflated exchange-rate manipulation.

### Likelihood Explanation
This requires no privileged access: any address can post a trigger unit to the AA, and any address can send a plain payment to the AA's address. The AA balance is updated unconditionally on receipt regardless of trigger matching, as shown in `aa_composer.js`. This is a template shipped with ocore for AA authors to reference/copy, so any deployment that reuses this pattern verbatim or with similar "ratio from live balance" logic is exposed to this class of attack the moment liquidity is thin (e.g., right after asset creation/first deposit, or right after a large divest that shrinks `mm_asset_outstanding` to zero/near-zero).

### Recommendation
Track pooled reserves in explicit state variables (e.g., `var['reserve_base']`, `var['reserve_asset']`) that are updated only by the AA's own logic on each accepted invest/divest/swap message, and use those tracked reserves — not raw `balance[...]` — for all ratio/share-price calculations. Reject or explicitly account for any payment that doesn't match a recognized case (e.g., bounce unmatched deposits, or fold them into state) so unaccounted donations cannot distort `$current_ratio`/`$investor_share_of_prev_balance`. Additionally, guard the "initial deposit" branch so the first depositor's share issuance is bound to their own contribution rather than the AA's total (possibly donation-inflated) balance.

### Proof of Concept
1. Deployer defines the AA and issues `mm_asset` (`trigger.data.define`).
2. Attacker sends a payment to the AA address containing base bytes that does not satisfy the "invest" `if` condition (e.g. with no asset output and value ≤ `1e5`, or as a separate payment message alongside an unrelated trigger), inflating `balance[base]` while `mm_asset_outstanding` stays 0.
3. Attacker then triggers "invest in MM" with a minimal deposit while `$asset_balance == 0` (first real invest via the case): `$issue_amount = balance[base]` now includes the previously donated, unaccounted bytes, letting the attacker mint shares priced against inflated reserves.
4. A legitimate investor later invests through the same case; `$bytes_balance` (denominator) already includes the attacker's donation, so `$investor_share_of_prev_balance` and the resulting `$issue_amount` are diluted relative to the victim's real contribution.
5. Attacker calls "divest MM shares" to redeem `mm_asset` at the inflated `balance[$asset]`/`balance[base]` ratio, extracting value contributed by the victim. [6](#0-5) [5](#0-4)
