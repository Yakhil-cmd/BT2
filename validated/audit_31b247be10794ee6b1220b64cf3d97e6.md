### Title
Webhook signature is verified against the organization in `repository.owner.login`, but handlers act on the repository named in `repository.full_name` - allowing cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload against using `repository_owner` (`params.dig('repository', 'owner', 'login')`), while every downstream `Shipit::Webhooks::Handlers::Handler` resolves the repository to mutate using a *different* field, `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so in a multi-organization Shipit deployment (a documented, supported configuration) an attacker who controls the webhook secret for *their own* onboarded organization can forge a payload where `repository.owner.login` names their own org (so the signature check passes) while `repository.full_name` names a repository belonging to a completely different, victim organization tracked by the same Shipit instance.

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature == organization of the repository the handler writes to`. Concretely:

- `WebhooksController#verify_signature` fetches the GitHub App config for the org derived from the payload and verifies the raw body's HMAC against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

- Once verified, the controller dispatches the **entire, unmodified `params`** to every registered handler for the event, with no re-binding of the payload to the org that was actually authenticated: [3](#0-2) 

- Every handler (`PushHandler`, `StatusHandler`'s repo-scoped siblings, `PullRequest::*Handler`, etc.) independently derives the target repository from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`#repository_name`, or `Repository.from_github_repo_name`, which simply splits the string on `/` and looks up `owner`/`name` in the DB: [4](#0-3) [5](#0-4) 

- `Shipit.github(organization:)` looks up an independent secret/App per organization when the multi-app config schema is used (documented as "Using Multiple Github Applications"), meaning distinct orgs legitimately have distinct, mutually unknown webhook secrets: [6](#0-5) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the repository actually modified) are two independent, attacker-controlled JSON fields in the same signed body, an attacker who legitimately owns/installs a GitHub App for OrgA on the shared Shipit instance knows OrgA's `webhook_secret`. They can therefore sign a JSON payload where `repository.owner.login = "OrgA"` (so `verify_webhook_signature` succeeds against OrgA's secret) but `repository.full_name = "OrgB/victim-repo"` (a repository belonging to OrgB, a different tenant tracked by the same instance). GitHub itself would never emit such an inconsistent payload, but the controller does not enforce that consistency — it only checks the signature over the raw bytes, and handlers trust `full_name` blindly.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written," letting an attacker with legitimate credentials for one tenant organization forge webhook events (`push`, `status`, `pull_request`, `check_suite`, `membership`) attributed to a different organization's repositories/stacks on a shared Shipit instance. Depending on which handler is targeted this can:
- Trigger `GithubSyncJob`/`sync_github` for another org's `Stack` with an attacker-chosen `expected_head_sha`, via `PushHandler#process`.
- Inject fabricated commit statuses via `StatusHandler#process` (`Commit#create_status_from_github!`), potentially unblocking a merge or deploy gate for a victim org's stack.
- Create/archive/unarchive review stacks for a victim org's repository via the `PullRequest::*Handler`s.

This is a cross-repository-write/cross-tenant integrity violation of the class explicitly listed as in-scope ("an organization that authenticated versus the repository that is written").

### Likelihood Explanation
Requires the Shipit deployment to use the multi-organization GitHub App configuration (a documented, first-class feature) and requires the attacker to be an owner/installer of one of the configured tenant organizations' GitHub Apps — not a Shipit account, not a `GITHUB_TOKEN`, and not access to the victim org. This is a realistic scenario for shared/hosted Shipit instances serving multiple organizations or customers, matching the "unprivileged attacker" bar (attacker only needs a GitHub org of their own that has been onboarded).

### Recommendation
After determining `repository_owner` for signature verification, re-validate that every handler operates only on repositories whose owner matches the authenticated organization — e.g., pass the authenticated organization down to `Handler` and assert `repository.owner.casecmp(authenticated_organization) == 0` before any handler acts, or reject payloads where `repository.owner.login` doesn't match the prefix of `repository.full_name`.

### Proof of Concept
1. Deploy Shipit with the multi-org config schema, onboarding `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own `webhook_secret`, as documented.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` using OrgA's known secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds since the signature matches OrgA's secret.
5. `PushHandler.call(params)` runs `Repository.from_github_repo_name("OrgB/victim-repo")`, finds the real `OrgB` stack, and enqueues `GithubSyncJob` for it with the attacker-supplied `expected_head_sha`, despite the request never being authenticated against `OrgB`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
