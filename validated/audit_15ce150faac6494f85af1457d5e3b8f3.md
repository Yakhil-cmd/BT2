### Title
Permissionless front-running of `coin_registry::new_currency` permanently bricks legitimate `Currency<T>` registration - (File: `crates/sui-framework/packages/sui-framework/sources/registries/coin_registry.move`)

### Summary
`sui::coin_registry::new_currency<T>` lets **any caller** claim the canonical, deterministic `Currency<T>` slot for **any** type `T` that merely has the `key` ability — no ownership of `T`, no witness, no capability tied to the module that defines `T` is required. Because the slot is a `derived_object::claim` keyed only by `CurrencyKey<T>()`, the first successful call permanently reserves that `(CoinRegistry, T)` address; every subsequent call — including from the legitimate token issuer — aborts with `ECurrencyAlreadyExists`. This is the same root cause as the AutoRoller/Sense H‑4 report: an unprivileged party can pre-claim a deterministic, shared "one-slot-per-key" resource that a legitimate protocol actor will need later, permanently bricking that actor's ability to complete initialization.

### Finding Description
`new_currency` is declared as:
```move
public fun new_currency<T: /* internal */ key>(
    registry: &mut CoinRegistry,
    decimals: u8, symbol: String, name: String, description: String, icon_url: String,
    ctx: &mut TxContext,
): (CurrencyInitializer<T>, TreasuryCap<T>) {
    assert!(!registry.exists<T>(), ECurrencyAlreadyExists);
    ...
    let currency = Currency<T> {
        id: derived_object::claim(&mut registry.id, CurrencyKey<T>()),
        ...
``` [1](#0-0) 

The only gate is `assert!(!registry.exists<T>(), ...)`, which itself is just `derived_object::exists(&registry.id, CurrencyKey<T>())` [2](#0-1) . Unlike the deprecated `coin::create_currency`, which enforces `sui::types::is_one_time_witness(&witness)` to guarantee a single, module-gated creation event [3](#0-2) , `new_currency<T>` takes **no witness at all** — `T: key` is satisfiable by any public struct with `key` that anyone can name as a type argument, whether or not they authored the module that defines it.

`derived_object::claim` is documented to be a one-shot, permanent reservation: "Tries to create an object twice with the same parent-key combination" aborts with `EObjectAlreadyExists`, and "the marker exists even after deletion" [4](#0-3) . The framework's own security-review checklist explicitly calls out this exact bug class: *"Adding a DF whose (name,type) already exists aborts; a predictable derived address can be pre-funded before the object exists... Exploit: overwrite or block another user's slot; pre-create / pre-send to a derived address to hijack initialization, or front-run object creation"* [5](#0-4) .

This maps directly onto the AutoRoller bug: in the Sense finding, an untrusted caller could pre-create a `(adapter, maturity)` Series/Space-pool slot that the legitimate AutoRoller would later need, causing the legitimate roll to permanently revert. Here, an untrusted caller can pre-create the `(CoinRegistry, T)` `Currency` slot for any coin type before its real issuer calls `new_currency`, causing the issuer's subsequent, legitimate call to permanently revert with `ECurrencyAlreadyExists`, since `derived_object`/`coin_registry` provide no mechanism to release, override, or dispute a squatted slot.

### Impact Explanation
`CoinRegistry` at `0xc` is documented as the canonical, system-wide source of coin metadata used by wallets, explorers, and on-chain consumers [6](#0-5) . Any unprivileged address can:
1. Watch the mempool/public code of a soon-to-publish package (or predict a common struct name) for a type `T` with `key`.
2. Call `coin_registry::new_currency<T>(registry, ...)` first, permanently claiming `Currency<T>`'s derived address with attacker-chosen (bogus) `name`/`symbol`/`decimals`/`icon_url`, and obtaining a decoy `TreasuryCap<T>`.
3. When the legitimate project later calls `new_currency<T>` (the officially recommended, "standard creation" flow per the docs [7](#0-6) ) it aborts with `ECurrencyAlreadyExists` forever — there is no admin override, no re-claim, no dispute path in this module.

This is "harmful smart-contract behavior" against the canonical system registry that Sui promotes as the standard onboarding path for new coins: it permanently denies a legitimate project the ability to register accurate canonical metadata for their coin type, and can seed the ecosystem's index/RPC layer with attacker-controlled bogus metadata (name/symbol/icon) associated with that type indefinitely. This falls within the allowed "harmful smart-contract behavior" / "permanent" class of impacts reachable purely from unprivileged public input, with no reliance on malicious validators, peers, or governance.

### Likelihood Explanation
High. The only requirement is knowing the fully-qualified type name `T` of an upcoming coin before its owner calls `new_currency`. Type names are often predictable (e.g., `PACKAGE::module::COIN`) or observable from a package that has already been published but has not yet called `new_currency` (a very common two-step flow, since `new_currency` "can be called from the module that defines `T` any time after it has been published" [8](#0-7) ). No special capability, gas advantage, or validator collusion is required — a single PTB call from any address suffices.

### Recommendation
Gate `new_currency<T>` the same way `new_currency_with_otw` is gated (require a one-time-witness or some other proof that the caller is authoritative for `T`), or require the caller to already hold a capability that only the defining module could have issued (e.g. a `Publisher` for the package that defines `T`, verified via `sui::package::from_module`/`from_package`). Alternatively, allow re-claiming/overwriting a `Currency<T>` slot that was created without a matching authority proof once the legitimate authority appears, with clear precedence rules.

### Proof of Concept
1. Observe (or predict) that package `P` will soon publish module `P::coin::MY_COIN` with `public struct MY_COIN has key { id: UID }` intended for canonical registration via `coin_registry::new_currency`.
2. Before `P`'s deployer calls `new_currency`, an attacker calls:
   ```move
   let (init, cap) = coin_registry::new_currency<P::coin::MY_COIN>(
       registry, 0, b"SCAM".to_string(), b"Scam".to_string(), b"".to_string(), b"".to_string(), ctx
   );
   coin_registry::finalize(init, ctx); // shares bogus Currency<MY_COIN>
   ```
   This succeeds because `T: key` is the only bound checked [9](#0-8)  and permanently claims the derived slot via `derived_object::claim` [10](#0-9) .
3. `P`'s deployer subsequently calls `coin_registry::new_currency<P::coin::MY_COIN>(...)`; this now hits `assert!(!registry.exists<T>(), ECurrencyAlreadyExists)` and aborts permanently — there is no code path to reclaim or override the slot.

**Caveat / unverified extension:** I was not able to confirm within the tool budget whether `coin::new_treasury_cap<T>` (used internally by `new_currency`) enforces any uniqueness/witness check on the `Supply<T>` it constructs. If it does not, the attacker's decoy `TreasuryCap<T>` obtained in step 2 could represent a second, independent `Supply<T>` for an already-in-use coin type, which would be a materially more severe (Critical, fund-integrity) issue than the DoS documented above. This part of the analysis is flagged as unconfirmed and would need direct inspection of `sui::coin::new_treasury_cap`'s implementation to validate.

/// Tries to create an object twice with the same parent-key combination.
#[error(code = 0)]
const EObjectAlreadyExists: vector<u8> = b"Derived object is already claimed.";

/// Added as a DF to the parent's UID, to mark an ID as claimed.
public struct Claimed(ID) has copy, drop, store;

/// An internal key to protect from generating the same UID twice (e.g. collide with DFs)
public struct DerivedObjectKey<K: copy + drop + store>(K) has copy, drop, store;

/// The possible values of a claimed UID.
/// We make it an enum to make upgradeability easier in the future.
public enum ClaimedStatus has store {
    /// The UID has been claimed and cannot be re-claimed or used.
    Reserved,
}

/// Claim a deterministic UID, using the parent's UID & any key.
public fun claim<K: copy + drop + store>(parent: &mut UID, key: K): UID {
    let addr = derive_address(parent.to_inner(), key);
    let id = addr.to_id();
    assert!(!df::exists(parent, Claimed(id)), EObjectAlreadyExists);
    df::add(parent, Claimed(id), ClaimedStatus::Reserved);
    object::new_uid_from_hash(addr)
}
