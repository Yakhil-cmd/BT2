### Title
Automatic rollback-on-abort forwards deploy-permitted environment variables into rollback execution without re-validating them against the stack's `rollback` allow-list - (File: `app/models/shipit/deploy.rb`)

### Summary
When a running deploy is aborted with the "rollback on abort" option, Shipit automatically triggers a rollback and reuses the aborted deploy's already-permitted environment hash as the rollback's environment. That hash was filtered against `deploy.variables` (the deploy allow-list) at deploy-creation time, but it is never re-filtered against `rollback.variables` (the rollback allow-list) before being written to the new `Rollback` record and interpolated into rollback shell steps. This mirrors the CDP.sol bug class: a value that is valid/verified for one context (`_currentTotalDebt` covering only new yield in `update`; here, "permitted for deploy") is carried forward into another context (`totalCredit`; here, "spawned as rollback env") without re-deriving/re-validating it against the binding that is supposed to hold in that second context.

### Finding Description
`Stack#build_deploy` explicitly sanitizes deploy input through the deploy allow-list: [1](#0-0) 

`DeploySpec` defines two separate allow-lists on purpose — `deploy_variables`/`filter_deploy_envs` and `rollback_variables`/`filter_rollback_envs` — and the README documents that operators are expected to configure a different, typically more restrictive, set of variables for `rollback`: [2](#0-1) 

Both API and UI rollback-creation paths correctly enforce this second, independent binding before building a rollback: [3](#0-2) 

However, the *automatic* rollback path taken when a deploy is aborted with `rollback_once_aborted: true` does not go through `filter_rollback_envs` at all. `Deploy#trigger_revert_if_required` takes `env:` (i.e. `self.env`, the deploy's own already-deploy-filtered hash) and hands it straight to `trigger_rollback`/`trigger_revert`: [4](#0-3) 

`trigger_rollback` and `build_rollback` accept that `env` verbatim and persist it on the new `Rollback` with no allow-list check: [5](#0-4) 

The `Rollback` task's environment is later merged into the actual shell execution environment and can be interpolated into `rollback` steps defined in `shipit.yml` (`$VARNAME` substitution via `EnvironmentVariables#interpolate`), so any key that passed the *deploy* allow-list check reaches rollback execution even if the stack's `shipit.yml` explicitly excludes it from `rollback.variables`.

The equality that should hold but is broken:
`env keys reaching rollback execution == env keys permitted by stack.rollback_variables`
Instead, on this path: `env keys reaching rollback execution == env keys permitted by stack.deploy_variables` (a different, attacker-influenced set).

### Impact Explanation
This breaks the deployment-trust binding between "an environment key permitted [for deploy]" and "an environment key spawned [into rollback execution]," the exact analog class called out in the rules (permitted vs. spawned environment key). `shipit.yml` maintainers use separate `deploy.variables`/`rollback.variables` lists specifically to restrict which caller-supplied values may flow into rollback shell steps (rollback scripts are often more dangerous/irreversible, e.g. destructive migrations, forced restores). A user who is authorized to trigger deploys (same authorization level needed either way) can set a deploy-only variable to a value that would be rejected outright if submitted directly for a rollback, then abort the deploy with the rollback flag, causing that value to be silently forwarded into rollback step execution/interpolation — bypassing the repository owner's intended, config-defined environment isolation between deploy and rollback contexts. Depending on how the stack's `rollback` steps interpolate `$VARIABLE` values into shell commands, this can escalate to injection of attacker-chosen strings into commands that the `shipit.yml` author never intended to be reachable from that variable's value space.

This does not, by itself, cross a session/token privilege boundary (the same actor already has deploy permission on the stack), so it falls short of the strict "unauthorized deploy/rollback by a different principal" bar, but it does defeat a specific input-validation binding the engine advertises (`EnvironmentVariables::NotPermitted` enforcement) for exactly this environment-key-scoping purpose.

### Likelihood Explanation
Reaching this path requires: (1) permission to trigger a deploy with a custom `env` value that is on `deploy.variables` but not on `rollback.variables` (both web and API deploy-creation flows already enforce only the deploy-side filter), and (2) permission to abort that deploy with `rollback_once_aborted: true`. Aborting with rollback is exposed via `TasksController#abort` (web, session-authenticated) and `Api::TasksController#abort` (API, `deploy:stack` permission) — the same or lower bar than triggering the deploy itself. No secret, additional token, or elevated GitHub permission is required beyond what's already needed to operate the stack normally, making this straightforward to trigger for any user who can already deploy/abort on the target stack.

### Recommendation
Re-filter the environment before it is used to build the automatic rollback:
- In `Deploy#trigger_revert_if_required`, replace the raw `env:` with `stack.filter_rollback_envs(env)` (or equivalent) before calling `rollback_once_aborted_to.trigger_rollback` / `trigger_revert`.
- Alternatively/also, enforce the allow-list check inside `Deploy#build_rollback`/`Rollback` itself (defense in depth), so every code path that constructs a `Rollback` is guaranteed to only carry variables permitted by `stack.rollback_variables`, matching the pattern already used by the API and UI rollback controllers.

### Proof of Concept
1. Configure a stack's `shipit.yml` with `deploy.variables` including `RISKY_VAR` but `rollback.variables` that does **not** include `RISKY_VAR` (rollback steps interpolate `$RISKY_VAR` or otherwise trust its absence).
2. As a user authorized to deploy the stack, trigger a deploy with `env: { "RISKY_VAR" => "<attacker-controlled-value>" }` — accepted because `RISKY_VAR` is permitted by `filter_deploy_envs`. [1](#0-0) 
3. While the deploy is running, call `abort` with `rollback: true` (web `TasksController#abort` or API `Api::TasksController#abort`), setting `rollback_once_aborted: true`.
4. On the `aborted!` transition, `trigger_revert_if_required` fires and forwards `self.env` (containing `RISKY_VAR`) directly into `trigger_rollback`/`trigger_revert`, bypassing `filter_rollback_envs`. [4](#0-3) 
5. The resulting `Rollback` task executes with `RISKY_VAR` present/interpolated in its shell steps, even though the stack's `shipit.yml` never authorized `RISKY_VAR` for rollback.

**Uncertainty**: I could not directly view the state-machine transition wiring in `app/models/shipit/deploy.rb` (the `aborted!` event handler) or `app/models/shipit/task.rb`'s `abort!` method in full due to tool call limits reached in the final iteration, so the exact call sequence from `abort!` → `aborted!` → `trigger_revert_if_required` is inferred from the test suite (`test/models/deploys_test.rb`, e.g. "transitioning to aborted schedule a rollback...") and the method bodies already retrieved, rather than fully re-verified line-by-line in this session.

      rollback = build_rollback(user, env:, force:)
      rollback.save!

      if lock
        lock_reason = "A rollback for #{rollback.since_commit.sha} has been triggered. " \
