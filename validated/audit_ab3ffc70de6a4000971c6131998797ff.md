### Title
Unsynchronized concurrent AA dry-run/trigger execution mutating shared in-memory caches - race condition analogous to CVE-2017-3158 - ([File: aa_composer.js])

### Summary
`dryRunPrimaryAATrigger()` and `handlePrimaryAATrigger()` (the real trigger executor) both mutate the same process-wide, unsynchronized JS caches (`storage.assocUnstableUnits`, `storage.assocCachedAssetInfos`, `storage.assocUnstableMessages`, `storage.assocBestChildren`) while running on independent DB connections/transactions. Unlike `handleAATriggers()`, which is serialized with `mutex.lock(['aa_triggers'], …)` [1](#0-0) , `dryRunPrimaryAATrigger()` takes **no mutex at all** [2](#0-1) . It is reachable directly and repeatedly by any unprivileged party: from the `light/dry_run_aa` network command [3](#0-2)  and automatically for every ordinary posted unit that pays an AA when `conf.bDryRunNewTriggers` is enabled, right before the unit is actually saved [4](#0-3) .

### Finding Description
The Guacamole race condition (CVE-2017-3158) allowed unsynchronized concurrent writes of printed blocks to overlap in a shared, statically-allocated buffer, corrupting a length field and causing out-of-bounds writes to attacker-observable/controlled shared state.

The analogous pattern in ocore is `aa_composer.js`'s handling of AA-trigger evaluation state. `handleTrigger()` (shared by real trigger processing, dry runs, and "air" estimates) directly reads and mutates long-lived, process-global caches owned by `storage.js`:
- `storage.assocUnstableUnits` / `assocStableUnits` (used and cleaned up by `revertResponsesInCaches()`) [5](#0-4) 
- `storage.assocCachedAssetInfos` populated by `readAssetInfo()` while validating AA-issued asset/payment messages [6](#0-5) 
- `storage.assocUnstableMessages` populated during unit save (`data_feed`/`definition`/`system_vote*`) [7](#0-6) 

The *real* pathway (`handleAATriggers` → `handlePrimaryAATrigger`) is serialized behind the `mutex.lock(['aa_triggers'])` key [8](#0-7) , and unit validation/writing is separately serialized behind `mutex.lock(arrAuthorAddresses)` and `mutex.lock(['write'])` [9](#0-8) [10](#0-9) . However `dryRunPrimaryAATrigger()` bypasses all of these locks: it opens its own DB connection/transaction and calls `handleTrigger()` with `bDryRun:true`, mutating the very same in-memory caches used by the locked, real code paths, then attempts to undo the effect afterward with `revertResponsesInCaches()` and `batch.clear()` [11](#0-10) . Because `revertResponsesInCaches()` only pops units that were pushed to `storage.assocUnstableUnits` by *this specific* dry run (via `objFirstUnit.parent_units`) and is not synchronized with any lock, an attacker able to trigger overlapping `light/dry_run_aa` requests (unauthenticated, callable repeatedly and concurrently by any light client per the handler in `network.js`) or trigger this via crafted units when `bDryRunNewTriggers` is set, can interleave writes to `assocUnstableUnits`/`assocBestChildren`/`assocCachedAssetInfos` from multiple in-flight dry runs and from the concurrently executing real trigger/validation pipeline. Because Node.js callbacks interleave at I/O boundaries (each `conn.query` yields the event loop), two independent `handleTrigger()` invocations for the *same or dependent AA address* can race: one dry run's `revertResponsesInCaches` can delete/forget a unit that a different, still-in-flight real (or another dry-run) trigger execution just inserted into `storage.assocUnstableUnits` and is still reading (e.g., `is_free`/`parent_units` fields), or a dry-run's cached `readAssetInfo` result (cached whenever `is_stable`, independent of whether the underlying transaction commits) can be read by a concurrently-validating real unit that trusts the cache to reflect asset cap/definition state.

This is directly analogous to the Guacamole bug class (CWE-362): two logically independent, unsynchronized writers touch the same shared mutable structure that is subsequently trusted to determine correctness of further processing (there: buffer length; here: unstable-unit/asset cache consistency that downstream AA balance/state and asset validation logic depends on).

### Impact Explanation
If the shared caches (`assocUnstableUnits`, `assocBestChildren`, `assocCachedAssetInfos`) become inconsistent due to interleaved dry-run/real-trigger mutation and reversion, downstream logic that trusts these caches for AA balance computation, `is_free` best-child bookkeeping, and asset cap/definition data can compute incorrect AA fund balances, permit incorrect state-var persistence, or cause `throw Error(...)` crashes that halt the node (e.g., `handlePrimaryAATrigger`'s `if (!objUnitProps) throw Error(...)`) — a network-wide denial of confirmation for new AA-driven units, or AA fund loss/freezing from a corrupted internal ledger view. This satisfies "AA fund loss or freezing" / "node disagreement on validity or stability" criteria.

### Likelihood Explanation
Medium. `light/dry_run_aa` is callable by any (light) client without special privilege and provides direct, repeatable, attacker-controlled triggering of `dryRunPrimaryAATrigger()` concurrently with normal network traffic (real AA triggers via `handleAATriggers()`, or other concurrent dry runs). The `bDryRunNewTriggers` config path additionally exercises this on every ordinary posted unit paying an AA. Actually forcing a harmful interleaving requires precise timing across async DB callback boundaries, which is feasible but not trivial to engineer deterministically — hence medium rather than high likelihood.

### Recommendation
Serialize `dryRunPrimaryAATrigger()` (and `estimatePrimaryAATrigger()`, which has the same pattern) behind the same or a compatible mutex key used by `handleAATriggers`/`handlePrimaryAATrigger` (e.g. `mutex.lock(['aa_triggers', address])`), or otherwise ensure dry-run cache mutations are fully isolated (e.g., operate on a deep-cloned view of the relevant cache subset rather than the shared global objects) so that concurrent dry runs and real trigger execution cannot observe or revert each other's in-memory cache writes.

### Proof of Concept
1. Enable AA balance-affecting workload: deploy an AA address `A` that consumes payments.
2. Issue two near-simultaneous `light/dry_run_aa` requests (or one `light/dry_run_aa` request racing a genuine posted unit triggering `A` while `conf.bDryRunNewTriggers` is set) targeting the same AA address `A`, both causing `handleTrigger()` to push into `storage.assocUnstableUnits` via child/secondary trigger execution.
3. Because neither call path is protected by `mutex.lock(['aa_triggers'])`, the two `handleTrigger()`/`revertResponsesInCaches()` invocations interleave: dry run #1's `revertResponsesInCaches` can `storage.forgetUnit()` an entry that dry run #2 (or the real trigger) still relies on, or dry run #2's balance/state computation can read a half-reverted `assocCachedAssetInfos`/`assocUnstableUnits` entry.
4. Observe either a thrown `Error` (`"handlePrimaryAATrigger: unit ... not found in cache"` at aa_composer.js:106) crashing the node process, or divergent AA balance/state-var results returned to concurrent callers, demonstrating cache corruption from the unsynchronized concurrent writers.
