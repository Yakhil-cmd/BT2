### Title
Cross-tenant commit status forgery via webhook signature/payload mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves the target `Commit` purely by `sha`, with no scoping to the repository/organization whose signature was actually verified. Because `WebhooksController#verify_signature` derives the signing organization from the same attacker-controlled JSON body it is verifying, an attacker who owns any org onboarded in Shipit can sign a payload with their own `webhook_secret` while pointing `sha` at a commit belonging to an unrelated victim stack.

### Finding Description
The broken binding is:
`verified_org(payload) == owner_org(commit_targeted_by(payload.sha))`

which the code never enforces — it should hold but does not.

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to select the `GitHubApp` instance (`Shipit.github(organization: repository_owner)`) whose `webhook_secret` is used to verify `X-Hub-Signature` [2](#0-1) . Both `repository_owner` and the HMAC-signed body are fields the requester fully controls — nothing ties the org name in `repository.owner.login` to any other part of the payload.
- Once the signature check passes for the attacker's own org, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query is global across the entire `commits` table — it is not scoped by `stack_id`, repository, or the `repository_owner` that was just verified.
- `create_status_from_github!` calls `add_status`, which creates a new `Status` row and fires `Hook.emit(:commit_status, ...)` / `:deployable_status`, and can trigger `stack.schedule_merges` [4](#0-3) [5](#0-4)  — i.e., it can change a victim stack's deployability/merge state.

Exploit flow: attacker owns/administers org `attacker-org`, which is legitimately onboarded in Shipit (has its own `webhook_secret` configured, e.g. via the GitHub App installed on the attacker's own repo). Attacker crafts a `status` event JSON body with `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")` and its real `webhook_secret` are used) but `sha` set to a commit SHA that belongs to a victim stack/repo entirely unrelated to `attacker-org` (obtained from the victim's public GitHub commit history). Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker_org_webhook_secret, raw_body)` using their own legitimately-known secret, sets `X-Github-Event: status`, and POSTs to `/webhooks`. `verify_signature` passes because the signature matches `attacker-org`'s secret; `drop_unhandled_event` passes because `status` is a handled event; `StatusHandler` then finds the victim's `Commit` (matched purely by sha, irrespective of org) and writes an attacker-chosen status/state onto it.

Existing guards do not stop this: `verify_signature` only proves "this body was signed by some onboarded org's secret," never "the org whose commit is being mutated." `drop_unhandled_event` and `check_if_ping` are irrelevant to this. No `ExplicitParameters` schema, model validation, or authorization check ties `sha` to `repository_owner`.

### Impact Explanation
An unprivileged attacker (owner of one legitimately-onboarded, unrelated repo/org) can inject arbitrary commit statuses (`state`, `description`, `target_url`, `context`) onto any commit in any other tenant's stack in the same Shipit instance, as long as they know a target SHA (public GitHub data). This can flip a victim commit from failing to "success," influencing `deployable?`/`blocked?` logic and `schedule_continuous_delivery`, potentially enabling an unauthorized deploy/merge on the victim's stack — a cross-tenant "payload for one repository mutating another's stack/commit," matching the Critical impact category. It is fully repeatable against any commit sha and any stack hosted by the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker only needs (a) one org/repo legitimately onboarded into the same Shipit instance (a normal, unprivileged capability — e.g., any GitHub org for which the operator installed the GitHub App/webhook, which the attacker administers), giving them a valid `webhook_secret` for computing signatures, and (b) a target victim commit sha (obtainable from public GitHub history of the victim repo). No Shipit session, API token, or victim secret is required. The attack is a single crafted HTTP POST to the public `/webhooks` endpoint, fully scriptable and repeatable.

### Recommendation
Scope the commit lookup (and every webhook handler that looks up records solely by attacker-suppliable fields such as `sha`) to the repository/org that was actually verified: e.g., join through `Stack` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repo_owner: repository_owner, repo_name: params.dig('repository','name') })`, or otherwise assert `commit.stack.repository_owner == repository_owner` (from the verified payload) before calling `create_status_from_github!`. More generally, `verify_signature` should authenticate the request against the concrete repository the event claims to describe, and every downstream handler should re-validate that the resolved model actually belongs to that same repository before mutating it.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Seed two orgs' GitHub App configs in `Shipit.github_apps`/secrets: `attacker-org` (webhook_secret A, real config attacker legitimately owns) and `victim-org` (webhook_secret B, unknown to attacker).
2. Create `victim_stack = Stack.create!(repo_owner: "victim-org", repo_name: "victim-repo", ...)` and `victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)`.
3. Build JSON body: `{ "repository" => { "owner" => { "login" => "attacker-org" } }, "sha" => victim_commit.sha, "state" => "success", "context" => "ci/attacker" }`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "webhook_secret_A", body)` (the attacker's own, legitimately-known secret for `attacker-org`).
5. POST to `/webhooks` with headers `X-Github-Event: status`, `X-Hub-Signature: signature`.
6. Assert `response.status == 200` (or whatever success code `head(:ok)` returns).
7. Assert `victim_commit.reload.statuses.last.state == "success"` and `context == "ci/attacker"` — i.e., the victim's commit, belonging to a stack the attacker never authenticated for, was mutated using only the attacker's own org's signature.
8. Assert the equality claimed by the binding fails: `verified_org == "attacker-org"` while `mutated_commit.stack.repo_owner == "victim-org"`, proving the two sides diverge with no guard catching it.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      end
      new_status
