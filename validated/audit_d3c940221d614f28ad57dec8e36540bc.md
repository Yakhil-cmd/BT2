## Title
Validation of AA-trigger units mixes a per-unit deterministic value (`last_ball_mci`) with a node-local, time-varying value (`getMinRetrievableMci()`), letting the same unit be judged valid by one node and permanently invalid by another - (File: `validation.js`, `storage.js`)

### Summary
Several protocol-upgrade gates in ocore are supposed to be decided solely by the `last_ball_mci` that is embedded in the unit itself (fixed once the unit is composed, since it is derived from the unit's own `last_ball_unit`). However, a subset of the `pemCurvesFixMci` gates - most notably the `max_aa_responses === 0` check in `validateAATrigger` - additionally consult `storage.getMinRetrievableMci()`, a value that is local to each node and advances asynchronously as that node's own main-chain stabilization progresses. This reproduces the reported bug class: a unit that is valid under the rules tied to its own embedded configuration can become permanently invalid depending on when/where it is validated, purely because of a mutable node-local variable that is not part of the unit and not agreed upon at the moment the unit is broadcast.

### Finding Description
`objValidationState.last_ball_mci` is derived deterministically from the unit's own `last_ball_unit` field, which is fixed by the composer at unit-creation time [1](#0-0) . Because of this, upgrade gates that key exclusively off `objValidationState.last_ball_mci` (e.g. the version/witness/oversize-fee/tps-fee rules) give the same verdict for the same unit content regardless of when or by whom it is validated [2](#0-1) .

`validateAATrigger`, however, does not rely solely on this embedded, unit-fixed value. For the `max_aa_responses === 0` check it ORs in `storage.getMinRetrievableMci()`:

```js
if (objUnit.max_aa_responses === 0 && (objValidationState.last_ball_mci >= constants.pemCurvesFixMci || !objValidationState.hasBall && storage.getMinRetrievableMci() >= constants.pemCurvesFixMci))
    return callback(`max_aa_responses=0 is not allowed`);
``` [3](#0-2) 

The same pattern (`mci >= constants.pemCurvesFixMci || require('../storage.js').getMinRetrievableMci() >= constants.pemCurvesFixMci`) is reused pervasively in the oscript/formula evaluator for AA definitions and triggers (array/dictionary literal length limits, `delete` selector limits, `search_param_list` field limits, etc.) [4](#0-3) [5](#0-4) .

`getMinRetrievableMci()` returns `min_retrievable_mci`, a purely node-local, time-varying counter that is advanced whenever *that node's own* main-chain stabilization crosses a new point:

```js
function getMinRetrievableMci(){
    return min_retrievable_mci;
}
function updateMinRetrievableMciAfterStabilizingMci(conn, batch, _last_stable_mci, handleMinRetrievableMci) {
    ...
    min_retrievable_mci = last_ball_mci;
    ...
}
``` [6](#0-5) 

This variable is updated from `main_chain.js` as each node individually finishes processing `markMcIndexStable` for a newly-stabilized MCI [7](#0-6) . Because stabilization of a given MCI is discovered and processed independently, and at different wall-clock moments, by every node on the network (full nodes, catching-up nodes, and light-serving nodes each advance their local main-chain view at their own pace), two nodes that both consider themselves "caught up" can transiently have different values of `min_retrievable_mci` at the exact real-time moment a newly-broadcast AA-trigger unit reaches them.

Consequently, for a trigger unit `U` whose own embedded `last_ball_mci` is *below* `constants.pemCurvesFixMci` (so the old, permissive rule "an AA trigger may explicitly set `max_aa_responses=0`" should legitimately still apply to it), one node — whose local `min_retrievable_mci` has already crossed `pemCurvesFixMci` — will call `callback("max_aa_responses=0 is not allowed")` and reject `U` as **permanently invalid** (`ifUnitError`, not a transient/retryable error), while another node whose local `min_retrievable_mci` has not yet crossed that threshold will accept and stabilize `U`. This is exactly the "config valid when the transaction was composed, invalid by the time/place it is processed" pattern from the reported bug class, but manifesting here as **node disagreement on unit validity**, because the deciding variable is not embedded in the unit and not the same for every validator.

### Impact Explanation
If different full nodes reach different conclusions about whether a broadcast AA-trigger unit is valid, the network can diverge on which units are part of the stable DAG: nodes that accepted the unit will build on it and include its outputs/state changes, while nodes that rejected it will not relay it and will never include it in their view of stability. This is a node-disagreement-on-validity condition that can stall confirmation of otherwise legitimate AA triggers, and — if the divergence is not eventually reconciled by other consensus mechanics — can leave the sender's payment permanently unconfirmable on some subset of nodes while their inputs are considered spent by others, i.e. exactly the "staker's funds locked" outcome from the referenced report, translated to an ocore AA-trigger sender.

### Likelihood Explanation
`pemCurvesFixMci`-gated behavior applies broadly (payment-to-AA triggers, oscript literal/selector-length limits, `search_param_list` limits used inside AA definitions) [4](#0-3) , so many ordinary AA interactions pass through code paths that consult `getMinRetrievableMci()`. Since `min_retrievable_mci` advances on every node independently as new MCIs stabilize, and stabilization propagation across the network is not instantaneous, any unit created near the `pemCurvesFixMci` boundary (or, more generally, any unit whose embedded `last_ball_mci` is a few MCIs behind the current tip when nodes are not perfectly synchronized) is exposed to this race. The condition is deterministic and reproducible in a controlled two-node setup (one node artificially delayed in processing stabilization) rather than requiring an adversary.

### Recommendation
Base all upgrade-activation decisions solely on the unit's own embedded `last_ball_mci` (the value already used for the primary gate), and remove the additional `storage.getMinRetrievableMci()` disjunct from `validateAATrigger` and from the analogous checks in `formula/validation.js`/`formula/evaluation.js`. If the `getMinRetrievableMci()` fallback exists to compensate for units lacking a full `last_ball` (e.g., `!objValidationState.hasBall`), replace it with a value that is guaranteed to be identical for every fully-synced node (such as the globally-agreed `last_stable_mci`/its corresponding last-ball MCI) rather than a node-local pruning cursor, or defer the decision entirely to when the ball is known and `last_ball_mci` can be computed unambiguously.

### Proof of Concept
1. Start two full nodes, A and B, both synced to the same DAG state.
2. Have node A finish processing `markMcIndexStable` for MCI `pemCurvesFixMci` (advancing its local `min_retrievable_mci` past the threshold) while node B has not yet finished processing that same MCI (its `min_retrievable_mci` is still below the threshold) — achievable by adding an artificial delay in B's `updateRetrievable` callback or by observing natural propagation delay under load.
3. Compose an AA-trigger unit `U` whose `last_ball_unit` references a ball with `main_chain_index < pemCurvesFixMci` and explicitly set `max_aa_responses = 0` via `composeJoint`'s `params.max_aa_responses` [8](#0-7) .
4. Broadcast `U` to both A and B before B catches up.
5. Observe that A executes `validateAATrigger` with `storage.getMinRetrievableMci() >= constants.pemCurvesFixMci` true and returns the permanent error `"max_aa_responses=0 is not allowed"` [9](#0-8) , rejecting `U`, while B (whose `min_retrievable_mci` has not crossed the threshold yet) accepts and stabilizes `U`, demonstrating divergent validity verdicts for the identical unit.
