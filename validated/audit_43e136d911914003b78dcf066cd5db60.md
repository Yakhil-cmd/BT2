### Title
Cross-tenant `Shipit::Team` membership injection via webhook `team.id` reuse - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves a `Shipit::Team` solely by `github_id`, and `MembershipHandler#process` then adds the payload's `member` to that team unconditionally. Because the webhook signature check only proves the payload was signed by the organization named in `organization.login` (which must match the actual signer for verification to succeed), an org whose webhook is legitimately configured on this Shipit instance can send a `membership` webhook naming its own org but with a `team.id` equal to a `Team` record's `github_id` that actually belongs to a different, already-onboarded organization, causing an attacker-chosen GitHub login to be added as a member of that other organization's team.

### Finding Description
The broken binding is: `Team#organization` (set once at creation) must equal `params.organization.login` (the organization asserted in the current, freshly-verified webhook) for every mutation of that `Team`, but the code never re-checks this.

Trace:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('organization', 'login')` for membership events (no `repository` key exists in this payload) and calls `Shipit.github(organization: repository_owner)` to pick the `GitHubApp`/`webhook_secret` used to verify `X-Hub-Signature`. [1](#0-0) [2](#0-1) 
- Because the secret used to verify is looked up by `organization.login` itself, for the signature to pass, `organization.login` in the payload must equal the org whose secret actually signed it — call this ATTACKER_ORG, an organization already configured in `secrets.github` on this instance. [3](#0-2) 
- Once verified, `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The block only runs on *creation*; for an existing `Team` row (belonging to VICTIM_ORG), the lookup matches purely on `github_id` and returns the victim's row untouched, ignoring the attacker-supplied `organization.login`. [4](#0-3) 
- `MembershipHandler#process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))` unconditionally on `'added'`, with no check that `team.organization == params.organization.login`. [5](#0-4) 
- `Team#add_member` simply appends the member to `members` via the `memberships` association with no organization re-validation. [6](#0-5) 

Exploit flow: ATTACKER_ORG is an org already configured (with its own `webhook_secret`) on the shared Shipit instance. Its administrator knows this secret (they had to enter it into GitHub's webhook UI to wire up the integration). They send a signed `membership` webhook with `organization.login: 'ATTACKER_ORG'`, `action: 'added'`, `team.id` set to the numeric `github_id` of a `Team` row known to belong to VICTIM_ORG (team IDs are discoverable via GitHub's API), and `member.login` set to any GitHub login they control. `verify_signature` passes because the payload's asserted organization matches the actual signer. `find_or_create_team!` returns VICTIM_ORG's existing `Team` row. `process` adds the attacker's chosen user as a member of VICTIM_ORG's team.

None of the existing guards catch this: `verify_signature` authenticates *which organization sent the request*, not *which team/organization the payload's `team` object may claim to belong to*; the `ExplicitParameters` schema only validates types/presence, not cross-tenant ownership; there is no `require_permission!`/`stacks` scope check in this webhook path.

### Impact Explanation
A trusted-but-malicious tenant (an org onboarded to a shared Shipit instance) can inject an arbitrary GitHub login into another tenant's `Shipit::Team` membership list, purely by guessing/observing that team's numeric GitHub `github_id`. Since `Shipit.github_teams` and team membership are used to gate authorization (e.g., deploy/rollback permission checks against `Shipit.github_teams`), this is an escalation into that authorization boundary — matching the audit's "High: escalation into `Shipit.github_teams` authorization" category. The attack is repeatable against any team whose `github_id` the attacker can learn, and the blast radius spans all organizations sharing the same Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment where the attacker legitimately administers one onboarded organization (and thus holds that org's own `webhook_secret`, which is a normal, necessary part of setting up the GitHub webhook), and (2) a pre-existing `Shipit::Team` row for the victim organization with a known/guessable `github_id`. Both preconditions are realistic in a shared/multi-tenant Shipit installation, and GitHub team IDs are visible via the GitHub API to org members or via existing Shipit data. No Shipit session, GitHub App private key, or `api_clients_secret` is needed — only the attacker's own, legitimately-provisioned org webhook secret.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and anywhere else that looks up `Team` by `github_id` from webhook payloads), verify that an existing record's `organization` matches `params.organization.login` before mutating it; if it doesn't match, drop/reject the event (e.g., raise or no-op) rather than silently operating on a different tenant's team. Consider also re-deriving/validating team ownership against `Shipit.github(organization:)` config scoping so that a webhook verified for one organization can never mutate another organization's `Team`/`Membership` rows.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (concept)
test "membership webhook cannot add a member to a team owned by a different organization" do
  victim_team = Shipit::Team.create!(
    github_id: 4242,
    name: 'victims',
    slug: 'victims',
    api_url: 'https://api.github.com/teams/4242',
    organization: 'victim-org'
  )

  payload = {
    'action' => 'added',
    'team' => { 'id' => 4242, 'name' => 'victims', 'slug' => 'victims', 'url' => victim_team.api_url },
    'organization' => { 'login' => 'attacker-org' }, # signed with attacker-org's own webhook_secret
    'member' => { 'login' => 'attacker-controlled-user' }
  }

  assert_no_difference -> { Shipit::Membership.count }, "membership must not be created across tenant boundary" do
    Shipit::Webhooks::Handlers::MembershipHandler.call(payload)
  end

  # binding check: team.organization ('victim-org') != payload organization.login ('attacker-org')
  assert_equal 'victim-org', victim_team.reload.organization
  refute_equal 'attacker-org', victim_team.organization
  refute victim_team.members.exists?(login: 'attacker-controlled-user')
end
```
This test currently fails against the shipped code (a `Membership` linking `attacker-controlled-user` to `victim_team` is created), demonstrating the cross-tenant write.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
