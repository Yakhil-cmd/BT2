### Title
System TPS-fee parameters can be voted into a combination that makes `validateTpsFee` permanently unsatisfiable, blocking unit confirmation - (File: validation.js)

### Summary
`validateTpsFee` in `validation.js` rejects a unit with a **permanent** (non-transient) `ifUnitError` whenever the paid `tps_fee` plus the address's `tps_fees_balance` is below `min_tps_fee`, a value computed from three independently-votable system parameters: `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier`. These parameters are set through `system_vote`/`system_vote_count` messages that any balance-holding address can send, and are aggregated by `countVotes()` in `main_chain.js`. Similar to the reported `AuctionBase._processBid` bug — where two independently configurable values (`universeExtendableBy()` and `_paymentWindow`) could be combined into a permanently-false inequality that blocked all future bids — the ocore TPS-fee formula combines `base_tps_fee` and `tps_interval` exponentially in a way that a technically "valid" (in-bounds) but poorly chosen combination drives `min_tps_fee` to an extreme value, causing essentially all future units to fail the same hard-coded inequality and get permanently rejected.

### Finding Description
`getLocalTpsFee`/`getFinalTpsFee` in `storage.js` compute: [1](#0-0) 
```
tps_fee_per_unit = round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1))
```
`validation.js`'s `validateTpsFee` then enforces, as a hard (non-transient) unit error: [2](#0-1) 

The bounds enforced on these parameters when they are voted in via `system_vote` are only: [3](#0-2) 
- `tps_interval` ≥ 0.1
- `base_tps_fee` ≤ 1e8
- `tps_fee_multiplier` between 1 and 1000

No upper bound exists on `base_tps_fee` other than 1e8, and no lower bound tighter than 0.1 exists for `tps_interval`. Because the fee grows as `exp(tps / tps_interval)`, a combination at the edges of these allowed ranges (e.g., `tps_interval = 0.1`, `base_tps_fee = 1e8`, `tps_fee_multiplier = 1000`) makes `min_tps_fee` explode for even modest local congestion (`tps` measured over recent units), since `tps/tps_interval` becomes very large very quickly. Any unit whose `tps_fees_balance` cannot cover this astronomically large `min_tps_fee` is rejected permanently via `ifUnitError`, not merely deprioritized. This mirrors the reported bug exactly: two configurable "safety" values are combined via a formula whose acceptable ranges were chosen independently, so an in-range (not malicious, not out-of-range) but poorly chosen combination flips the inequality into a state where it can no longer be satisfied by ordinary future traffic — effectively locking out unit confirmation, the direct network-level analog of the auction contract being unable to accept any further bids.

The vote weight is aggregated purely by address balance (`voter_balances`) with the median rule in `countVotes`, so this is not restricted to a privileged "operator"; any set of coin holders whose combined weight reaches the median can drive these parameters to the problematic combination, satisfying the "reachable by an unprivileged actor" requirement (via ordinary `system_vote` unit messages, not via any hub/peer/network-level attack). [4](#0-3) 

### Impact Explanation
If `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` are voted into an extreme (but individually in-bounds) combination, `min_tps_fee` for units posted during any period of even mild congestion becomes unaffordable, and `validateTpsFee` rejects such units with a hard `ifUnitError` rather than a transient/soft error. This is functionally equivalent to a network unable to confirm new units — the exact "Accept" criterion in the validation rules for this class of bug ("a network unable to confirm new units").

### Likelihood Explanation
Likelihood depends on whether the voting economics (median-of-balance) can realistically converge on such an extreme parameter set; this requires coordinated or accidental voting by holders representing sufficient balance weight, analogous to the "system was accidentally configured" root cause in the original report. The protocol only bounds the vote inputs at a coarse per-parameter level; it never validates the resulting *combination*'s effect on the derived `min_tps_fee` formula, so the safety property (the fee formula stays practically satisfiable) is not actually enforced by the individual bounds chosen.

### Recommendation
Add a joint sanity check when validating `system_vote`/`system_vote_count` payloads for `base_tps_fee`/`tps_interval`/`tps_fee_multiplier` (and/or when applying the median result in `countVotes`) that bounds the worst-case `min_tps_fee` for a reasonable congestion level, similar to how the auction fix moved the safety-window check to validate the *combined* configuration rather than relying on independently-bounded inputs. Consider also downgrading unaffordable `tps_fee` shortfalls to a transient/soft rejection (as is already done for `min_acceptable_tps_fee` with the OP bypass) rather than a permanent `ifUnitError`, so that a bad parameter combination degrades throughput instead of permanently blacklisting affected units.

### Proof of Concept
1. Enough balance-weighted addresses submit `system_vote` units setting `tps_interval = 0.1`, `base_tps_fee = 1e8`, `tps_fee_multiplier = 1000` (all individually pass the bound checks in `validation.js` lines 1893-1907).
2. `countVotes()` in `main_chain.js` computes the balance-weighted median and applies these values to `storage.systemVars`. [4](#0-3) 
3. Once local `tps` rises even slightly, `getLocalTpsFee`/`getFinalTpsFee` compute an extremely large `min_tps_fee` due to the `exp(tps/tps_interval)` term. [1](#0-0) 
4. Any newly posted unit whose `tps_fee` and `tps_fees_balance` cannot cover this inflated `min_tps_fee` is permanently rejected by `validateTpsFee`'s hard error path. [2](#0-1)
