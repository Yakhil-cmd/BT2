### Title
Assert-based validator panic in `build_updated_stake_reward` when a stake account's delegation is legitimately mutated (e.g. via `Merge`) between epoch-reward calculation and partitioned distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` re-reads the stake account from the *current* `stakes_cache` at distribution time and, when `relax_post_exec_min_balance_check` (`adjust_delegations_for_rent`) is not active, asserts via a hard `assert_eq!` that `current_delegation.stake + stake_reward == pre-computed_new_delegation.stake`. Because reward calculation happens once at the epoch boundary but distribution is deferred over multiple blocks/partitions, an attacker who owns the stake account (and a second compatible stake account) can issue an ordinary `Merge` instruction on their own stake pubkey before its partition is distributed, changing `delegation.stake` in the stakes cache and violating this invariant.

### Finding Description
Reward calculation happens once at the epoch boundary (`compute_new_epoch_caches_and_rewards` → `calculate_rewards` → `calculate_stake_rewards_and_commissions` → `redeem_delegation_rewards`), producing a `PartitionedStakeReward` per stake pubkey whose `inflation.stake` field already encodes the *pre-computed* post-reward `delegation.stake` value [1](#0-0) .

Distribution of these pre-computed rewards is deferred across `num_partitions` subsequent blocks (`REWARD_CALCULATION_NUM_BLOCKS` + partition index), giving a window during which the account can still be mutated by ordinary, authorized stake-program instructions [2](#0-1) [3](#0-2) .

When each partition is finally applied, `build_updated_stake_reward` loads the **current** state of the account from `stakes_cache_accounts` (not a snapshot taken at calculation time) [4](#0-3) . When the `relax_post_exec_min_balance_check` feature is inactive, the code hard-asserts that the *current* delegation stake plus the pre-computed reward equals the *pre-computed* new delegation stake:

```
} else {
    let expected_delegation = stake
        .delegation
        .stake
        .saturating_add(partitioned_stake_reward.inflation.stake_reward);
    assert_eq!(
        expected_delegation, new_stake.delegation.stake,
        "stake reward delegation must be consistent with the updated stake account \
         lamport balance"
    );
}
``` [5](#0-4) 

This is a hard `assert_eq!` (not a recoverable `Result`), so any mismatch panics the validator inside `store_stake_accounts_in_partition`, which runs unconditionally during block processing for every validator replaying the block [6](#0-5) .

An attacker can trivially change `stake.delegation.stake` for a pubkey with a pending reward without violating any stake-program authority/rent checks: they own a stake+withdraw authority for the reward-pending account and legitimately own a second, compatible stake account delegated to the same validator. Issuing `Merge` (a fully authorized, unprivileged instruction, confirmed reachable and legal even for freshly-activated stakes in `stake_merge_immediately_after_activation`) between the calculation block and the account's specific distribution partition/block increases the *current* `delegation.stake` for the reward-pending pubkey via `StakesCache::upsert_stake_delegation` [7](#0-6) , without going through the withdrawal restrictions that would otherwise bound lamport movement. When the deferred reward is later applied, `stake.delegation.stake` (now larger, post-merge) plus `stake_reward` no longer equals the stale `new_stake.delegation.stake` computed before the merge, tripping the `assert_eq!` and panicking every validator that processes/replays that block.

This is not blocked by any existing signer/authority/rent/epoch guard because `Merge` is a perfectly legal, unprivileged stake-program instruction; the vulnerability lies purely in the reward-distribution code assuming the stakes-cache snapshot used at calculation time remains unchanged until the deferred distribution block, which is false whenever more than one distribution partition/block separates calculation from a given account's payout (`num_partitions` can be many blocks for large validator sets, cf. `get_reward_distribution_num_blocks`).

### Impact Explanation
A successful trigger causes an `assert_eq!` panic inside bank block processing, on every node replaying the block (this is deterministic, not merely local mis-accounting) — matching the explicitly in-scope "epoch-boundary halt" impact category. It is a consensus-halting/cluster-wide denial-of-service bug reachable purely through unprivileged, ordinary stake instructions issued by a normal user with authority over their own stake accounts. (Note: whether `relax_post_exec_min_balance_check` is currently activated on mainnet-beta could not be confirmed from the code alone — it is a feature-gated `assert_eq!` path, so the bug only manifests on clusters/epochs where this feature is *not yet* activated. This is a live gap in the code regardless of current feature-activation status and needs to be fixed for any cluster/genesis where the feature is inactive.)

### Likelihood Explanation
Preconditions: attacker needs (1) a stake account with a pending, not-yet-distributed inflation reward, and (2) any second stake account they control that is `Merge`-compatible with the first (same voter pubkey, compatible lockup/authorities, activation states allowed by `MergeKind`). Both are attainable by any user with minimal stake. The number of blocks between reward calculation and a specific account's distribution partition scales with the number of stake accounts on the cluster (`get_reward_distribution_num_blocks`), so on any moderately sized validator set there are multiple blocks of exploitable window per epoch. This makes the attack fully repeatable every epoch and requires no validator/leader/gossip control — only ordinary transaction submission.

### Recommendation
- Snapshot (or otherwise fence) the reward-pending stake accounts' delegation state at calculation time and validate against that snapshot instead of the live `stakes_cache_accounts` at distribution time, or
- Replace the `assert_eq!` in `build_updated_stake_reward`'s non-`adjust_delegations_for_rent` branch with a recoverable `DistributionError` variant (mirroring the `Err(...) => burn/skip` path already used for `AccountNotFound`/`ArithmeticOverflow`) so a legitimately-mutated account results in the reward being burned/logged instead of panicking the validator, and
- Consider blocking/queuing `Merge` (and any other instruction that mutates `delegation.stake`) for accounts with an outstanding partitioned reward, or making `build_updated_stake_reward` tolerant of externally-changed delegation amounts by re-deriving `new_stake.delegation.stake` from the current cache value plus the reward rather than asserting equality with the stale pre-computed value.

    //    (not partition 0). Fund and construct a second, Merge-compatible

    //    processed via distribute_partitioned_epoch_rewards ->
    //    distribute_epoch_rewards_in_partition -> store_stake_accounts_in_partition
    //    -> Bank::build_updated_stake_reward.

    // Expected (buggy) result: the process panics with
    // "stake reward delegation must be consistent with the updated stake account lamport balance"
    // instead of returning Ok/Err gracefully.

    fn upsert_stake_delegation(
        &mut self,
        stake_pubkey: Pubkey,
        stake_account: StakeAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        debug_assert_ne!(stake_account.lamports(), 0u64);
        let delegation = stake_account.delegation();
        let voter_pubkey = delegation.voter_pubkey;
        let stake = delegation_effective_stake(
            delegation,
            self.epoch,
            &self.stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        match self.stake_delegations.insert(stake_pubkey, stake_account) {
            None => {
                self.add_delegated_stake(voter_pubkey, stake);
                self.vote_accounts.add_stake(&voter_pubkey, stake);
            }
            Some(old_stake_account) => {
                let old_delegation = old_stake_account.delegation();
                let old_voter_pubkey = old_delegation.voter_pubkey;
                let old_stake = delegation_effective_stake(
                    old_delegation,
                    self.epoch,
                    &self.stake_history,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
                if voter_pubkey != old_voter_pubkey || stake != old_stake {
                    self.sub_delegated_stake(&old_voter_pubkey, old_stake);
                    self.add_delegated_stake(voter_pubkey, stake);
                    self.vote_accounts.sub_stake(&old_voter_pubkey, old_stake);
                    self.vote_accounts.add_stake(&voter_pubkey, stake);
                }
            }
        }
    }
