### Title
Address-existence and cosigner-topology disclosure via the wallet "sign" device message - ([File: wallet.js])

### Summary
The `sign` message handler in `wallet.js` lets any paired device request a signature for an arbitrary address, and the response path taken (`ifLocal`, `ifRemote`, `ifMerkle`, `ifUnknownAddress`) is fully observable by the requester, disclosing whether the recipient's wallet holds a given address, which other device co-signs it, and its device topology — analogous to CVE-2019-9866's information-disclosure class, but here reachable from an unprivileged paired device rather than requiring elevated GitLab access. [1](#0-0) 

### Finding Description
The `case "sign":` branch of `handleMessageFromHub` accepts `{address, signing_path, unsigned_unit}` from any paired device (`from_address` is simply the sender's device address derived from its pubkey, with no additional authorization check on whether that device is entitled to know anything about `body.address`). [2](#0-1) 

After basic structural validation, the handler calls `findAddress(body.address, body.signing_path, {...})` and branches into four mutually-exclusive, externally distinguishable outcomes:
- `ifLocal`: the address is one of the recipient's own local wallet addresses — triggers `callbacks.ifOk()` and (for real units) kicks off validation/signing flow.
- `ifRemote`: the address belongs to a *different* device; the code reveals `other_device_addresses` topology, checks that `from_address` is a listed cosigner, and if it isn't, returns the explicit error `"you are not listed as a cosigner for this address "+body.address`. If it is, it forwards the request to `device_address` (the actual signer) — thereby disclosing which device address actually holds that share of a shared/multisig address.
- `ifMerkle`: replies with `"there is merkle proof at signing path "+body.signing_path`.
- `ifUnknownAddress`: replies `"not aware of address "+body.address+" but will see if I learn about it later"`. [3](#0-2) 

Each of these four outcomes is a distinct, attacker-observable response (`callbacks.ifOk()` vs. specific `ifError` text), so a malicious paired device can probe arbitrary addresses and, purely from the response, learn:
1. Whether an address is hosted locally on the victim's device.
2. Whether it's a shared/multisig address hosted on a *different* device, and, when the querying device happens to be (or claims via other means to be) a listed cosigner, which device address actually signs for it.
3. Whether the address is entirely unknown to the wallet.

This is a wallet/device-message handling oracle within the meaning of the "wallet and contract message handling" reachable surface listed in scope, driven purely by an unprivileged paired device sending crafted `sign` messages — no malicious hub/peer, no light-proof-serving path, and no privileged access is required, matching the GitLab CVE's information-disclosure bug class (unauthorized party learns internal state it should not see) mapped onto ocore's device-pairing/wallet layer.

### Impact Explanation
An adversarial paired device (any device the victim has ever paired with, e.g. via a chat link or textcoin exchange) can enumerate victim's local/shared addresses and multisig device topology without needing to intercept any wallet secret. This does not directly cause fund loss but is a genuine information-disclosure primitive: it lets an attacker map out which addresses are locally controlled, which are shared, and the identity of co-signing devices for shared/multisig addresses — useful reconnaissance for targeted social-engineering, deanonymization of otherwise-private counterparties in a multi-device wallet setup, or timing further attacks against a specific cosigner device once identified. Because it reveals address-existence and cosigner routing across the whole device's known addresses (not resource exhaustion, not just one unit), it rises above a "low/no-impact" leak.

### Likelihood Explanation
Likelihood is high for anyone the victim has paired with (a common, low-trust relationship, since pairing links are often shared in chat or via textcoins): the attacker only needs to send `sign` messages with varying `address` values and observe the callback outcome — no cryptographic material, private keys, or race conditions are required. The check is purely a message-response oracle in existing, always-reachable code.

### Recommendation
- Do not disclose more information than necessary in the `ifRemote`/`ifMerkle`/`ifUnknownAddress` branches to devices that are not already known cosigners of `body.address`; return a single generic error such as `"cannot process this request"` unless the sender is verified to be part of the address's own signer set (as the already-present but *commented-out* check at wallet.js suggested doing).
- Rate-limit/throttle `sign` requests per device address to reduce address-enumeration efficiency.
- Avoid leaking `other_device_addresses`/cosigner device identities to any requester that has not already been established (via the address definition/shared-address record) as an authorized cosigner.

### Proof of Concept
1. Attacker device pairs with victim device (standard, low-privilege pairing).
2. Attacker repeatedly sends `{subject: "sign", body: {address: "<candidate BASE32>", signing_path: "r", unsigned_unit: {authors:[{address:"<candidate>"}], messages:[...] } } }` device messages for a list of candidate addresses.
3. For each candidate address, observe the callback result:
   - `callbacks.ifOk()` with no forwarded error → address is local to the victim's wallet.
   - error text `"you are not listed as a cosigner for this address ..."` → address is remote/shared and hosted elsewhere, cosigners exist.
   - error text `"not aware of address ... but will see if I learn about it later"` → address unknown to victim wallet.
   - error text `"there is merkle proof at signing path ..."` → address exists but is behind a merkle-proof path.
4. Aggregate results across many candidate addresses to reconstruct which addresses the victim device knows about, and their type/topology. [3](#0-2) 

Note: this finding could not be further validated against the exact `findAddress` implementation body itself (only its call site and callback branches were retrievable via search); the four-branch outward-facing behavior above is confirmed directly from the `sign` handler code, which is sufficient to establish the oracle even without inspecting `findAddress`'s internals.
