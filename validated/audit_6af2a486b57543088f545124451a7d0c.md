### Title
Untrusted `hookify.*.local.md` rule can crash `evaluate_rules()`, fail-open and silently disable a legitimate blocking rule from another file - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine.evaluate_rules()` iterates all loaded rules in a single flat loop with no per-rule exception isolation. If evaluating any one rule (e.g. via `_check_condition`/`_extract_field`) raises an unhandled exception, the exception propagates out of `evaluate_rules()` into the hook script's outer `except Exception` handler, which unconditionally treats the failure as "allow the operation." This means a single malformed/attacker-crafted rule file can neutralize *all* other rules evaluated in that batch, including a legitimate `block` rule loaded from a separate, trusted `hookify.*.local.md` file.

### Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` globs all `.claude/hookify.*.local.md` files (`glob.glob` order is filesystem-dependent/unordered) and merges every enabled rule from every file into one flat list [1](#0-0) . This list is passed as-is into `RuleEngine.evaluate_rules()`.

`evaluate_rules()` then loops over `rules` and calls `self._rule_matches(rule, input_data)` for each rule with no `try/except` around the per-rule check [2](#0-1) . `_rule_matches` calls `_check_condition`, which calls `_extract_field` and then applies the configured operator to the extracted value [3](#0-2) . Neither `_check_condition` nor `_extract_field` guards against type errors — e.g. the `MultiEdit` branch does `' '.join(e.get('new_string', '') for e in edits)` without validating that each `e` is a dict [4](#0-3) , and operators such as `contains`/`starts_with`/`ends_with` apply string-only semantics to `pattern`/`field_value` without type checks [5](#0-4) .

Any such exception (e.g. `AttributeError`/`TypeError`) is not caught inside the `for rule in rules` loop, so it aborts `evaluate_rules()` entirely — before `blocking_rules`/`warning_rules` accumulated so far are ever returned. All hook entry points (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) wrap the whole evaluation in a single outer `try/except Exception` that, on any failure, emits a generic `{"systemMessage": "Hookify error: ..."}` with no `hookSpecificOutput.permissionDecision`, and always `sys.exit(0)` — i.e., fail-open/allow [6](#0-5) .

Because `load_rules()` merges rules from *all* matching files into one list before evaluation, and `evaluate_rules()`'s loop is not per-file or per-rule isolated, a crash while evaluating a rule from one untrusted `hookify.*.local.md` file prevents evaluation of rules — including legitimate `block` rules — defined in a completely separate, unrelated `hookify.*.local.md` file, purely due to loop position (which itself depends on unordered `glob.glob` results).

### Impact Explanation
This breaks the fail-closed guarantee implied by hookify's `action: block` mechanism: content that is supposed to deny a dangerous tool call (e.g. destructive `Bash` commands or arbitrary file writes) can be silently skipped because an unrelated rule file threw an exception during evaluation. The practical effect is a trust-boundary bypass of the enforcement layer: an attacker who can get any rule file evaluated alongside the legitimate one (e.g., by contributing/planting a `.claude/hookify.*.local.md` file in a shared or untrusted repository) can suppress a maintainer's genuine safety-blocking rule, allowing an otherwise-blocked dangerous command or file operation to proceed unauthorized. This matches an approval-bypass / unauthorized-command-execution class of impact for the hook enforcement surface.

### Likelihood Explanation
The architectural flaw is unconditionally present and confirmed by code: no per-rule try/except in `evaluate_rules()`'s loop [2](#0-1) , and fail-open outer handlers in every hook entry point [7](#0-6) [8](#0-7) . However, actually *triggering* the exception purely from attacker-controlled rule-file content (frontmatter alone, without depending on the shape of the real tool's `tool_input` at evaluation time) is less certain: the custom YAML-like parser in `extract_frontmatter` always coerces `Condition.field/operator/pattern` to strings [9](#0-8) , so most crash paths (like the cited MultiEdit `edits` type error) require the *actual* tool call's `tool_input` to contain malformed data, which is normally schema-validated by Claude Code's tool-calling layer rather than attacker-authored content. This means the exact PoC mechanism in the question (malformed `edits`) has a plausibility gap, though the general class of "any rule-evaluation exception fails open and skips other rules" is fully verified and exploitable given any crash-inducing input reaches `_check_condition`/`_extract_field`.

### Recommendation
Wrap each rule's evaluation individually in `evaluate_rules()`'s loop (e.g. `try: ... except Exception: log and treat as non-matching`) so a single bad rule cannot suppress evaluation of the rest. Additionally, reconsider the fail-open default in the hook scripts' outer exception handlers — at minimum, distinguish "no rules matched" from "rule evaluation errored," and avoid silently allowing operations when a `block`-type rule's evaluation was aborted by an exception in a different rule.

### Proof of Concept
Integration test (`plugins/hookify/core/rule_engine.py`):
1. Construct `rule_legit = Rule(name="legit-block", enabled=True, event="file", action="block", tool_matcher="MultiEdit", conditions=[Condition(field="file_path", operator="regex_match", pattern=r".*\.env$")], message="blocked")`.
2. Construct `rule_crash` = a rule matching the same/any invocation whose condition field is `new_text`/`content` for `tool_matcher="MultiEdit"` (triggers `_extract_field`'s MultiEdit branch at lines 249-252).
3. Call `RuleEngine().evaluate_rules([rule_crash, rule_legit], input_data)` where `input_data["tool_input"]["edits"]` contains a non-dict element (e.g. a string) to force `AttributeError` inside `_extract_field`.
4. Assert (currently failing): the returned dict should still contain `hookSpecificOutput.permissionDecision == "deny"` from `rule_legit`, or at minimum the call must not raise/short-circuit silently to `{}`/allow.
5. Currently, the exception propagates out of `evaluate_rules()` uncaught, demonstrating that `rule_legit`'s block decision is never returned/enforced.

    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns

    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
