### Title
Cross-organization forged webhook accepted because signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the unrelated `sha`/`repository.full_name` fields in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from `repository.owner.login` (falling back to `organization.login`), then, once verified, dispatches the *entire* parsed payload to handlers such as `StatusHandler`, which act on other attacker-controlled fields (`sha`) that are never checked against the organization used for verification. [1](#0-0) 

### Finding Description
`verify_signature` computes `repository_owner` from the payload itself (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`), looks up `Shipit.github(organization: repository_owner)`, and verifies the raw HMAC signature against that organization's `webhook_secret`: [2](#0-1) [3](#0-2) 

Once verification succeeds, `create` hands the *same, attacker-crafted* JSON body to every registered handler for the event, unmodified: [4](#0-3) 

Because HMAC verification is only "is this body signed by organization X's secret", nothing prevents the body from *also* containing fields that reference a completely different organization/repository. For example, `StatusHandler` (event `status`) looks up commits purely `Commit.where(sha: params.sha)` — global across the whole Shipit install, with no scoping by the `repository_owner` that was used for the signature check: [5](#0-4) 

Similarly, the base `Handler` class resolves the target `Stack`(s) from `payload.dig('repository', 'full_name')` (an independent field, unrelated to `repository.owner.login` used for auth) via `Repository.from_github_repo_name`: [6](#0-5) [7](#0-6) 

This breaks the trust binding: **organization authenticated (`repository.owner.login`, secret X) == repository/commit acted upon (`repository.full_name` / `sha`, arbitrary)**. Anyone who legitimately controls (or has compromised) the `webhook_secret` for *any single organization* configured in the Shipit instance can forge a payload where `repository.owner.login`/`organization.login` names their own (low-value) org — so the HMAC check passes with their known secret — while `sha`, `repository.full_name`, `state`, `description`, `target_url` reference a commit/stack belonging to a *different, unrelated organization or repository* also hosted on the same Shipit instance. The signature only proves the sender knows organization X's secret; it does not bind the payload's semantic target (`sha`/`full_name`) to organization X.

Multi-tenant configuration is explicit and documented/supported (`config/secrets.development.shopify.yml`, `template.rb` show multiple orgs each with independent `webhook_secret`): [8](#0-7) 

### Impact Explanation
Using only knowledge of one tenant organization's `webhook_secret` (no Shipit session, no `ApiClient` token, no GitHub repository write access to the victim repo required), an attacker can forge `status` webhooks that set arbitrary CI status (`state`, `description`, `target_url`, `context`) on **any commit sha tracked by any stack in the entire Shipit instance**, including victim organizations they have no access to. Since Shipit's merge/deploy gating (`ignore_ci`, deployable-status checks, continuous deployment) relies on commit statuses recorded via this exact code path, an attacker can mark an arbitrary commit belonging to another org's repository as passing/green, potentially causing an **unauthorized deploy** of that commit if continuous deployment or deploy-blocking-on-status logic depends on it. This matches the "High" impact bucket: escalation into cross-tenant state manipulation leading to unauthorized deploy.

### Likelihood Explanation
Requires the attacker to know/control one organization's `webhook_secret` configured on the same multi-tenant Shipit instance (e.g., they operate that org's GitHub App integration, or the secret was set up/rotated by them, or it leaked) — a lower bar than requiring access to the *victim* org's credentials. Given the engine explicitly supports and documents multiple orgs sharing one Shipit deployment with independently issued secrets, this is a realistic configuration, and the vulnerable code path (`verify_signature` keying off payload-controlled `repository.owner.login`, and `StatusHandler` doing a global, unscoped `Commit.where(sha:)` lookup) is exactly as shown above with no additional mitigating checks.

### Recommendation
- In `verify_signature`, do not trust `params.dig('repository','owner','login')`/`organization.login` alone to select the verification key; after selecting the org's app, re-derive and enforce that the resolved organization actually owns the `repository.full_name` referenced in the same payload before dispatching to handlers.
- In `StatusHandler#process`, scope the `Commit.where(sha: params.sha)` lookup by the repository/organization that was authenticated for the request (e.g., restrict to commits whose stack's `Repository#owner` equals `repository_owner`), rather than searching all commits system-wide.
- More generally, thread the authenticated organization from `WebhooksController` into `Handler` so every handler can assert `repository.full_name`'s owner matches the organization whose secret validated the request.

### Proof of Concept
1. Shipit instance configured with two tenant orgs, `attacker-org` (secret known to the attacker, e.g. they administer that org's GitHub App) and `victim-org` (unrelated, higher-value repo/stack tracked by the same Shipit instance).
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha tracked by victim-org/repo stack>",
     "state": "success",
     "description": "forged",
     "context": "ci/forged",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, attacker-org's webhook_secret)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s webhook secret, and the HMAC matches → request accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb:21-23`), finds the victim commit (global lookup, no org scoping), and calls `create_status_from_github!`, recording a forged "success" status on a commit the attacker never had write access to — potentially unblocking an automatic/continuous deploy of that commit in `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
