### Title
Signature verification is bound to `repository.owner.login`/`organization.login` but handlers act on the independent `repository.full_name` field, letting a webhook authenticated for one (secret-less) organization forge status/push events for any other organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC against using `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`), while every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, PR handlers, etc.) resolves the target `Stack`/`Commit` using the unrelated `repository.full_name` field from the same attacker-supplied JSON body. Nothing binds these two fields together, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when an organization has no `webhook_secret` configured (an explicitly optional setting per `docs/setup.md`). This breaks the equality "organization whose signature was verified" == "repository that is actually written to."

Because `repository.owner.login` (used to pick the verifying GitHub App/secret) and `repository.full_name` (used by handlers to pick the actual `Repository`/`Stack`, or `sha` used to pick the `Commit` irrespective of repository at all in `StatusHandler`) are independent, attacker-controlled fields in the same POST body, an attacker only needs a webhook-secret-less (or otherwise attacker-controlled) organization entry to be routed successfully, then can set `repository.full_name` (or just `sha`, for `status` events) to reference a completely different, secret-protected organization's stack.

### Impact Explanation
This crosses an authentication boundary: it lets an unauthenticated internet caller (no `ApiClient` token, no GitHub credentials, no repository write access) inject forged GitHub events — most critically forged commit statuses (`status` event) for arbitrary SHAs — into any stack tracked by the Shipit instance, without ever proving the request originated from GitHub for that stack's organization. Since Shipit gates deploys on required CI statuses (`ci.require`/`ci.blocking` in `shipit.yml`, enforced via `Commit#create_status_from_github!` and the deploy-spec's status checks), forging a `success` status for a commit satisfies the impact category "unauthorized deploy." It can also forge `push` events to trigger `GithubSyncJob` against arbitrary stacks, and forge `pull_request`/`membership` events against unrelated organizations' repositories, all mediated by the engine's own `GITHUB_TOKEN`-bearing GitHub App for the *targeted* org even though the *attacker's* request was only "authenticated" (or not authenticated at all) for a different org.

### Likelihood Explanation
Feasible for any deployment that manages more than one GitHub organization (a first-class, documented feature — "Using Multiple GitHub Applications") where at least one organization omits `webhook_secret` (explicitly documented as optional). No credentials, tokens, or GitHub App secrets are required from the attacker for that organization's requests to pass `verify_signature`, and no code ties the verified/authenticated organization to the repository or commit the handler subsequently acts on.

### Recommendation
After resolving `repository_owner`/selecting the GitHub App used for verification, require that `repository.full_name` (and, for `StatusHandler`, the resolved `Commit#stack.repository`) actually belongs to that same verified organization before dispatching to handlers; reject events where they disagree. Additionally, require a `webhook_secret` for every configured GitHub App and refuse to accept webhooks for organizations that lack one, rather than defaulting `verify_webhook_signature` to `true`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (no `webhook_secret` set, per docs this is legal) and `orgB` (has `webhook_secret`, hosts a real, CI-gated production stack).
2. Attacker sends, unauthenticated, no valid `X-Hub-Signature` required:
```
POST /webhooks
X-Github-Event: status

{
  "sha": "<sha of a commit under review in orgB's stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/anything" }
}
```
3. `repository_owner` = `"orgA"` → `Shipit.github(organization: "orgA")` has no `webhook_secret` → `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`) → request passes with HTTP 200.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — global, unscoped to any organization — and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto `orgB`'s commit.
5. If that status satisfies `orgB`'s `ci.require`/`ci.blocking` configuration, the commit becomes eligible for an unreviewed, unauthorized deploy through Shipit's normal deploy/merge-queue flow.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
