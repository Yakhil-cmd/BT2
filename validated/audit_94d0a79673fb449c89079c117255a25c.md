### Title
Cross-repository commit-status forgery via organization-scoped signature vs. globally-scoped write - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the `GitHubApp`/`webhook_secret` selected by the *organization* named in the payload's `repository.owner.login` (or `organization.login`) field, but the handlers that consume the same payload act on a *different, unchecked* field: `repository.full_name` for most handlers, and, in the case of `StatusHandler`, on nothing at all — it matches purely by commit `sha` across the entire database. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` config (and thus the `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

This engine explicitly supports multiple, independently-secreted GitHub App installations, one per organization, each with its own `webhook_secret` known to that organization's own Shipit administrator: [3](#0-2) 

Once the signature check passes (using the secret of whichever organization the attacker names in `repository.owner.login`), the full, otherwise-unvalidated JSON body is dispatched to every registered handler for the event: [4](#0-3) 

The base `Handler` class derives the repository to operate on from a *separate* field, `repository.full_name`, which is never cross-checked against the organization used for signature verification: [5](#0-4) 

`StatusHandler` goes further and ignores the repository entirely, resolving target `Commit` rows by `sha` alone, globally across the whole instance: [6](#0-5) 

So a party that legitimately owns/administers one onboarded organization's GitHub App (and therefore knows that organization's own `webhook_secret`, which they configure themselves in the multi-org setup) can craft an arbitrary HTTP POST to `/webhooks` with a valid `X-Hub-Signature` for their own organization, while the JSON payload's `sha` (for `status` events) or `repository.full_name` (for `push`/`pull_request` events) references a commit or repository belonging to a completely different, unrelated tenant of the same Shipit instance.

### Impact Explanation
This is a concrete cross-repository write: the organization whose credential (webhook secret) is verified is not the same as the repository/commit whose state is mutated. Commit statuses recorded via `commit.create_status_from_github!` are the exact signal Shipit uses to reflect CI/build state for a commit and to gate its deployability in the UI/pipeline. An attacker who controls one legitimate tenant of a multi-org Shipit deployment can forge success/failure statuses on arbitrary commits belonging to other tenants' repositories, and — via `full_name`-driven handlers — trigger sync/pull-request-provisioning actions (e.g. `PushHandler`'s `stack.sync_github`, review-stack provisioning/archiving) against stacks they do not own, without ever holding a session, `ApiClient` token, or repository write access on the victim organization. This falls squarely in the "cross-repository writes" / unauthorized deploy-adjacent impact category, since falsified commit status is a primary input to deploy eligibility.

### Likelihood Explanation
Likelihood is high in any deployment using the documented multi-organization GitHub App configuration (a supported, documented feature), since the only prerequisite is administering one legitimate onboarded organization — no compromise of the victim organization, no GitHub App private key, and no Shipit session/API token are required. The signature check by design only proves "this request was signed by *some* configured organization's secret," never that the payload content stays scoped to that organization's repositories.

### Recommendation
After `verify_signature` succeeds, re-derive the acting organization from the verified `GitHubApp`/config and require that every repository-scoped field in the payload (`repository.full_name`, and for `StatusHandler`, the resolved `Commit`'s owning `Repository`) belongs to that same organization before any handler mutates state. Reject the webhook (422) on mismatch instead of trusting unrelated payload fields for authorization decisions.

### Proof of Concept
1. Configure/operate two organizations on the same Shipit instance per the documented multi-org setup, e.g. `attacker-org` (secret `S_A`, known to the attacker) and `victim-org` (a genuine tenant, unrelated repository containing commit `deadbeef` with an existing `Commit` row).
2. Craft a `status` event body:
   ```json
   { "sha": "deadbeef", "state": "success", "context": "ci/tests",
     "repository": { "owner": { "login": "attacker-org" } } }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC_SHA1(S_A, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` → `"attacker-org"`, loads `attacker-org`'s `GitHubApp`, verifies with `S_A` → succeeds.
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef")`, matching `victim-org`'s commit regardless of the authenticated organization, and writes a forged CI status onto it.

      verified = github_app.verify_webhook_signature(
