### Title
Webhook `status` events forge CI checks on arbitrary tracked commits regardless of the authenticating organization - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`), but the `status` event handler never checks that the commit it updates belongs to that same organization/repository. Combined with the fact that a webhook secret is optional per organization, this breaks the binding: *organization that authenticated the request* == *repository/commit the request is allowed to write to*.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/organization config to use purely from the payload itself: [1](#0-0) [2](#0-1) 

The signature check for that organization is a no-op if no `webhook_secret` is configured for it: [3](#0-2) 

Per-organization `webhook_secret` is documented/templated as optional (`# nil` by default): [4](#0-3) 

Once verification passes, the raw JSON body is dispatched to the registered handler for the event with no further authorization: [5](#0-4) 

Most handlers (`PushHandler`, `CheckSuiteHandler`) at least scope their side effects to a `Repository` derived from `payload.dig('repository', 'full_name')`: [6](#0-5) [7](#0-6) 

But `StatusHandler` performs a completely global lookup by SHA, with no repository/organization scoping whatsoever: [8](#0-7) 

This means the `repository.owner.login` value used to select the authenticating organization is disconnected from the effect of the request: any commit anywhere in the Shipit database whose SHA matches `params.sha` gets a new `CommitStatus` created, regardless of which "authenticated" organization the request claims to originate from.

### Impact Explanation
An unprivileged attacker who knows (or can guess) the SHA of a commit tracked by a *victim* stack (SHAs are public git history, easily obtainable from GitHub) can:
1. Craft a `status` webhook payload with `repository.owner.login` set to any GitHub organization configured in this Shipit instance that has **no `webhook_secret` set** (verification trivially returns `true` for that org, requiring no secret knowledge at all).
2. Set `sha` to the victim commit's SHA (belonging to a different, unrelated, secured organization/repository) and `state: "success"` with a `context` matching one of the stack's `ci.require` statuses.
3. POST this to `/webhooks`.

Because `StatusHandler#process` matches purely on `Commit.where(sha: params.sha)` with no ownership check, this forges a passing CI status on the victim's commit. If the stack has continuous deployment enabled and `ci.require` is satisfied only by this forged status, this can trigger an **unauthorized deploy** — matching the explicit Critical-impact criterion in this exercise ("an unauthorized deploy, rollback or merge"). No `ApiClient` token, GitHub App private key, repository write access, or privileged account is required — only knowledge of one organization in the install that has no webhook secret configured (an explicitly supported/optional configuration) and a public commit SHA.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment where at least one configured organization omits `webhook_secret` (shown as the default/optional template value). No authentication, session, or token is needed; the only prerequisite is knowledge of a target commit SHA, which is public GitHub data. The attack is a single unauthenticated HTTP POST.

### Recommendation
- In `StatusHandler#process`, scope the commit lookup to the repository/stack derived from the payload (as `PushHandler`/`CheckSuiteHandler` already do via `Handler#stacks`/`repository_name`), rather than a bare global `Commit.where(sha:)`.
- Cross-check that the organization used to authenticate the webhook (`repository_owner`) actually owns the repository referenced by the event payload before dispatching to any handler, rather than trusting them independently.
- Require `webhook_secret` to be present for all configured organizations (fail closed instead of `return true unless webhook_secret` in `GithubApp#verify_webhook_signature`).

### Proof of Concept
1. Configure two GitHub orgs in `secrets.yml`: `attacker-org` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`, has a tracked stack with `ci.require: ["ci/build"]`).
2. Find a public commit SHA `abc123` on `victim-org/app` that Shipit has already synced (`Commit` record exists).
3. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` needed, and body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/decoy"},
  "sha": "abc123",
  "state": "success",
  "context": "ci/build",
  "target_url": "https://example.com",
  "created_at": "2026-09-01T00:00:00Z"
}
```
4. `WebhooksController#verify_signature` resolves `attacker-org`'s config, which has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")` (matches the victim's commit) and calls `create_status_from_github!`, creating a passing `ci/build` status on the victim's commit — satisfying `ci.require` and potentially triggering an unauthorized deploy on `victim-org/app`, an organization the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
