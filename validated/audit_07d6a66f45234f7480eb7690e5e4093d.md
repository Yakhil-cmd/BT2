### Title
Webhook signature verification selects the HMAC secret by an org field the signature never covers, allowing cross-organization forgery of GitHub events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-org Shipit deployments, `WebhooksController#verify_signature` picks which `webhook_secret` to check the `X-Hub-Signature` against based on `repository_owner`, a value read straight out of the untrusted, not-yet-verified request body. The rest of the pipeline, however, identifies the target repository/stack using a *different* field of the same untrusted body (`repository.full_name`). Because the field used to select the verification key is not the field used to select the acted-upon repository, an attacker who legitimately controls the webhook secret for *any one* configured GitHub organization on the instance can forge a signed payload that is verified under their own org's secret while its `repository.full_name` field points at a stack belonging to a different, unrelated organization/repository on the same Shipit instance.

### Finding Description
`Shipit::WebhooksController#verify_signature` does: [1](#0-0) 

`repository_owner` is derived purely from the raw JSON body before any signature check occurs: [2](#0-1) 

`Shipit.github(organization: repository_owner)` is used to look up the `GitHubApp` (and therefore the `webhook_secret`) that will validate the HMAC, per the multi-org config schema documented in `docs/setup.md` and implemented in `Shipit.github` / `Shipit.github_app_config`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only proves that *some* org's configured secret matches the signature over the raw body — it says nothing about which repository the body actually claims to act on: [4](#0-3) 

Once verification passes, the handler dispatch ignores `repository.owner.login` entirely and instead resolves the target stacks from `repository.full_name`: [5](#0-4) 

`PushHandler`, for example, uses that repository resolution to enqueue a real sync against matching stacks: [6](#0-5) 

This breaks a deployment-trust binding: the equality that must hold is `organization that authenticated the signature == organization of the repository actually written to`. The controller only guarantees `organization named in repository.owner.login (chosen by the attacker) == organization whose secret validated the HMAC`. It never checks `repository.owner.login == repository.full_name`'s organization, and downstream code never re-derives the organization from `full_name` to cross-check it against the org used for signature verification.

### Impact Explanation
On a Shipit instance configured with multiple GitHub organizations (the documented "Using Multiple GitHub Applications" setup), each org has its own independent `webhook_secret`. Any principal who can obtain/know the webhook secret for one configured org (e.g., an admin of a low-trust org/app registered on the same Shipit instance, or anyone who can read that org's webhook config) can:
1. Craft a JSON body with `repository.owner.login` set to their known org (so `Shipit.github` selects the secret they know) but `repository.full_name` set to `<victim-org>/<victim-repo>`, plus `ref`/`after` fields naming an arbitrary commit SHA.
2. Sign the raw body with the known secret to pass `verify_signature`.
3. Send it as a `push` event; `PushHandler` resolves stacks via `repository.full_name` and calls `stack.sync_github(expected_head_sha: ...)` on the victim org's stack, causing Shipit to fast-forward/queue a build against an attacker-chosen commit SHA for a repository the attacker's credentials were never meant to touch.

This is a cross-organization write into stack/deploy state driven by forged, cross-boundary-trusted webhook input, matching the "Critical: cross-repository writes / unauthorized deploy" impact class, since it can trigger sync/build/merge-queue side effects against repositories outside the authenticating organization's boundary.

### Likelihood Explanation
Exploitability requires the attacker to already possess a valid `webhook_secret` for at least one org configured on the same Shipit instance — this is realistic in shared, multi-tenant Shipit deployments where different teams/orgs each administer their own GitHub App but share one Shipit instance (the exact scenario `docs/setup.md`'s "Using Multiple GitHub Applications" section documents as supported). No GitHub write access, `ApiClient` token, or Shipit session is required — only knowledge of one org's webhook secret and the ability to POST to `/webhooks`.

### Recommendation
After signature verification succeeds, re-derive the organization from `repository.full_name` (or `organization.login`) and require it to match the organization whose secret validated the signature (i.e., cross-check `repository_owner` against the org portion of `repository.full_name`) before dispatching to handlers, rejecting the request with `422` if they diverge. Alternatively, iterate over all configured `webhook_secret`s and require a positive match to be tied to the org that owns the repository named in `full_name`, rather than trusting attacker-supplied `repository.owner.login` to select the verification key in the first place.

### Proof of Concept
Given a multi-org config like `test/dummy/config/secrets_double_github_app.yml` with `OrgOne` (secret known to attacker) and `OrgTwo` (victim, contains the target stack):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, body)>

body = {
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgOne" },      # selects the secret the attacker knows
    "full_name": "OrgTwo/victim-repo"    # actually acted upon by PushHandler
  }
}
```

`verify_signature` computes the HMAC using `Shipit.github(organization: "OrgOne")`'s secret (known to the attacker) against the raw body and it matches, so the request passes. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim stack — despite the request never having been signed by anything belonging to `OrgTwo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
