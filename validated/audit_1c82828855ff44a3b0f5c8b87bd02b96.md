### Title
Webhook signature verification and event routing are bound to different, mutually unvalidated repository identifiers, allowing cross-repository event forgery in multi-organization deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization `Shipit.github` configurations, the webhook signature check selects a per-organization HMAC secret using `repository.owner.login`/`organization.login` from the **unverified** request body, while the code that actually consumes the payload to locate a `Stack`/`Repository` and mutate state (`sync_github`, commit statuses, PR/review-stack archival, etc.) uses a **different unverified field**, `repository.full_name`. These two fields are never cross-checked against each other, so the identity used to select the verification key is not the identity that is acted upon.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to verify against using an attacker-controlled field taken straight from the still-unparsed/unverified JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-org config and, if that org's `webhook_secret` is blank, `GitHubApp#verify_webhook_signature` **short-circuits to `true`**: [3](#0-2) 

Meanwhile, every event handler locates the target `Repository`/`Stack` using an entirely separate field, `payload.dig('repository', 'full_name')`, that was never covered by the signature/organization check: [4](#0-3) [5](#0-4) 

This breaks the equality binding: `organization authenticated (repository.owner.login) == repository written (repository.full_name)`. In a multi-org install (`Shipit.github_organizations` > 1, as documented in `docs/setup.md` and `config/secrets.development.shopify.yml`), an attacker can craft a payload where `repository.owner.login` names an organization configured in `secrets.github` **without** a `webhook_secret` set (verification trivially passes), while `repository.full_name` names a real, secured repository/stack belonging to a *different*, properly-secreted organization. The handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `app/controllers/shipit/webhooks_controller.rb:12`) then processes the forged event against the real stack.

### Impact Explanation
This allows an unauthenticated external attacker to forge GitHub webhook events (`push`, `status`, `pull_request`, `check_suite`, `membership`, etc.) against any stack/repository configured under a *different*, secured organization, as long as at least one configured organization in the same Shipit instance has no `webhook_secret`. Concretely this can:
- Force `GithubSyncJob` to run for an arbitrary stack (`PushHandler#process` → `stack.sync_github`), influencing what Shipit believes is the latest ref/commit to deploy.
- Forge commit statuses (`status` handler) that gate CI-required deploys (`ci.require` in `shipit.yml`), potentially enabling an "unauthorized deploy" by satisfying CI status checks that were never actually run.
- Archive/unarchive review stacks or manipulate PR-driven state via the `pull_request`/label handlers for repositories the attacker does not control.

This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope, and can lead to an unauthorized deploy path (fake CI status → deploy proceeds), which matches the Critical/High impact bar.

### Likelihood Explanation
Requires: (1) a multi-organization `Shipit.github` configuration (explicitly supported, see `config/secrets.development.shopify.yml` and `docs/setup.md`), and (2) at least one configured organization with a blank/unset `webhook_secret`. This is a realistic, documented configuration state — `webhook_secret` is commented as optional/`# nil` in the example multi-org secrets files (`config/secrets.development.shopify.yml:9,18`). No credentials, tokens, or repository access are needed by the attacker; only network access to the public `/github/webhooks` endpoint.

### Recommendation
Bind the signature-verification key and the payload's acted-upon repository to the same field: derive the organization used for `Shipit.github(organization:)` lookup from the same `repository.full_name`/`repository.owner.login` pair that handlers use, and reject (or additionally re-verify) if they disagree. Consider also requiring `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), so a misconfigured/unsecured organization cannot be used as a bypass vector for events targeting other organizations' repositories.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `secured-org` (has `webhook_secret` set) and `unsecured-org` (no `webhook_secret`), with a real Shipit `Stack` tracking `secured-org/real-repo`.
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/real-repo"
  }
}
```
No `X-Hub-Signature` needs to be valid for `secured-org`'s secret — `verify_signature` looks up `unsecured-org`'s (blank) secret via `repository_owner`, and `verify_webhook_signature` returns `true` unconditionally.
3. `PushHandler` resolves the target stack via `repository.full_name` = `secured-org/real-repo`, which is unaffected by the forged `owner.login`, and enqueues `GithubSyncJob` for the real, secured stack — a fully forged, unauthenticated webhook event accepted against a protected repository.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
