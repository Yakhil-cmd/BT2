## Confirmed vulnerability: cross-organization webhook forgery via signature/handler binding mismatch

### Title
Webhook signature verification is scoped by `repository.owner.login`, but event handlers resolve state by an unrelated `repository.full_name`/`sha` field — allowing cross-organization forged deploy-status and push events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multiple GitHub App configurations, one per organization, each with its own `webhook_secret`. `WebhooksController#verify_signature` selects *which* app's secret to verify the HMAC signature against using an attacker-controlled field from the unauthenticated payload — `repository.owner.login` (or `organization.login`). Once the signature check passes, the actual event handlers act on a *different* attacker-controlled field (`repository.full_name` for push/pull_request handlers, or a bare `sha` with no repository scoping at all for the `status` handler). Because the field used to select/verify the signing secret is never checked against the field the handler actually acts on, an attacker who legitimately controls a GitHub organization/App installed on this Shipit instance can forge events that are attributed to a different repository/stack.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read straight from the unverified JSON body and used to pick which organization's `webhook_secret` will validate the HMAC (`Shipit.github(organization:)` looks up per-org config in `lib/shipit.rb#github_app_config`). [2](#0-1) 

After the signature is accepted, `Webhooks.for_event(event)` dispatches the same raw `params` to handlers that resolve the *target* repository/commit from a different, independently-attacker-controlled field:

- `PushHandler`/PR handlers resolve target via `payload.dig('repository', 'full_name')` (a separate JSON key from `repository.owner.login` used for auth): [3](#0-2) 

- `StatusHandler` doesn't even reference repository/organization at all — it matches by `sha` globally across every stack:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

This breaks the required equality: **organization that authenticated the request (`repository.owner.login`, used to select the verifying `webhook_secret`) must equal the repository/commit that is actually written (`repository.full_name` / bare `sha`, used by the handler)**. Nothing enforces this. `test/dummy/config/secrets_double_github_app.yml` confirms the multi-org config model (`OrgOne`, `OrgTwo`, each with distinct `webhook_secret`), and `test/fixtures/shipit/github_hooks.yml` shows per-repo/org secrets — this is a supported, documented deployment mode. [5](#0-4) 

### Impact Explanation
An attacker who legitimately controls (or has installed) a GitHub App/organization configured in Shipit's multi-org `secrets.github` map (a normal, low-privilege scenario — e.g. their own org's repos are also tracked by the same Shipit instance) knows their own `webhook_secret` and can compute a valid HMAC-SHA1 signature for any payload body. They can:

1. Set `repository.owner.login` (or `organization.login`) to their own org name so `verify_signature` selects their own known secret and passes.
2. Set `repository.full_name` (push/pull_request events) or `sha` (status events, targeting any commit sha they can observe on a victim's public repo) to reference a victim stack/commit tracked by the same Shipit instance.

This lets the attacker:
- Forge `status` webhook events to mark an arbitrary victim commit as `success` via `Commit#create_status_from_github!`, which feeds directly into `Commit#deployable?` and `Commit#blocked?` — the gating logic used to decide whether a commit may be deployed and whether continuous deployment/merges proceed (`stack.schedule_merges` is triggered on success). [6](#0-5) [7](#0-6) 
- Forge `push` events to trigger `stack.sync_github` for a victim stack's branch, and forge `pull_request` events to archive/create/unarchive victim review stacks.

Forcing CI status to `success` on a commit that never actually passed CI directly enables an **unauthorized deploy** (a commit becomes `deployable?` purely from the forged status), which matches the "Critical" impact bar in scope (unauthorized deploy). It requires no Shipit session, API token, or write access to the victim's repository — only that the attacker's own org is one of the organizations configured in Shipit's `secrets.github`.

### Likelihood Explanation
Requires: (a) the Shipit instance is configured with the documented multi-org GitHub App schema (multiple orgs each with a distinct `webhook_secret`), and (b) the attacker has a webhook secret for at least one configured organization — which is the case whenever any customer/team onboards their own org into a shared Shipit instance, a supported and documented topology. The webhooks endpoint is a single global route (`/webhooks`) not scoped per organization, so nothing else prevents cross-org payloads from reaching handlers for other orgs' stacks. No social engineering, TLS interception, or privileged credentials are needed — likelihood is moderate-to-high in any multi-tenant Shipit deployment.

### Recommendation
- After signature verification succeeds for a given `repository_owner`/organization, re-derive the target repository from the same trusted field and enforce that any repository referenced by the handler (`repository.full_name`, or the repository owning a `sha`) belongs to that same verified organization before acting.
- For `StatusHandler` specifically, scope the `Commit.where(sha: ...)` lookup to commits whose stack belongs to the verified organization, not a global sha lookup.
- Consider moving to per-organization webhook endpoints (e.g. `/webhooks/:organization`) so the URL segment, not an unauthenticated body field, determines which secret is used, and reject requests where the payload's `repository.owner.login` disagrees with the endpoint's organization.

### Proof of Concept
Given Shipit configured with `secrets.github` containing `AttackerOrg` (webhook_secret known to attacker, installed on `attacker-org/some-repo`) and `VictimOrg` (webhook_secret unknown, owns tracked stack `victim-org/app` with commit `abc123` pending CI):

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, body)>

{
  "sha": "abc123",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
- `verify_signature` computes `repository_owner = "AttackerOrg"`, looks up `AttackerOrg`'s app/secret, verifies successfully (attacker knows this secret).
- `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the victim's commit (no org/stack scoping), and calls `create_status_from_github!`, marking it `success` — regardless of the fact the signature was verified against `AttackerOrg`, not `VictimOrg`.
- The victim commit is now `deployable?` and can be shipped/merged by anyone with normal deploy rights on that stack, or auto-deployed under continuous deployment, without ever passing real CI.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
