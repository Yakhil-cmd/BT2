## Title
Stack-Scoped API Client Bypasses Its Own Authorization Scope in `CCMenuController#stack` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` binds the set of stacks an `ApiClient` may act on to the token's own `stack_id` scope via the `stacks` helper, and every standard API controller resolves the requested resource through that scoped relation. `Shipit::Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, breaking the binding "stack a token authorizes == stack it touches."

### Finding Description
`BaseController#stacks` is the authorization boundary that limits a stack-scoped `ApiClient` to only the stack it was created for: [1](#0-0) 

`ApiClient#stack_id?`/`stack_id` come from the `belongs_to :stack, optional: true` association, and every properly-scoped API controller (e.g. `Api::StacksController`, `Api::TasksController`) resolves the requested record through `stacks.from_param!(...)`, so a token scoped to stack A can never resolve a `Stack` record for stack B — `stacks.from_param!` raises `ActiveRecord::RecordNotFound` because the relation is pre-filtered.

`CCMenuController`, however, defines its own `#stack` method that calls `Stack.from_param!` directly on the model class, not on the scoped `stacks` relation: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, which only checks that the token includes the `read:stack` permission string — it does not check which stack the token is scoped to: [3](#0-2) [4](#0-3) [5](#0-4) 

So the equality that should hold — "the stack a token is authorized for" == "the stack the controller acts on" — is broken specifically in this controller: any `ApiClient` with `permissions: ['read:stack']`, regardless of its `stack_id` scope, can request `GET /api/stacks/:stack_id/ccmenu` for **any** stack in the installation, not just the one it was scoped to. This directly parallels the reported bug class: one code path (`BaseController#stack`) correctly enforces the binding, while a sibling code path (`CCMenuController#stack`) silently omits it, just as `graduateToken()` called the necessary configuration step while `launchV4Pool()` omitted it.

Note that `CCMenuController` also overrides `authenticate_api_client` to accept a `?token=` query-string parameter in addition to Basic Auth, which is how `ccmenu_url_url` tokens (created scoped to a single stack, `permissions: %w[read:stack]`) are meant to be consumed by CI dashboard tools: [6](#0-5) [7](#0-6) 

This confirms the intended design: CCMenu tokens are meant to be narrowly scoped to a single stack, embedded in a URL that may be shared with third-party CI dashboard software (CCTray-compatible tools). The `#stack` override defeats that scoping, turning a single-stack read token into a token that can read `deploys_and_rollbacks`/lock status for every stack in the Shipit instance.

### Impact Explanation
This is unauthenticated (relative to the intended scope) read of stack state/deploy status: an actor in possession of a legitimately-issued, stack-scoped `ApiClient` token (e.g. obtained from a shared/leaked CCMenu URL for one stack, which is explicitly designed to be embedded in third-party dashboard tools) can enumerate and read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) for every stack in the Shipit deployment, not just the one it was authorized for. This matches the in-scope impact category "unauthenticated read of stack state, task streams or deploy output" via escalation beyond `Shipit.github_teams`/`ApiClient` authorization scoping.

### Likelihood Explanation
High likelihood: CCMenu URLs (containing the token) are explicitly designed by `CCMenuUrlController#client` to be distributed to external CI dashboard tooling, increasing the chance such tokens leak or are shared more broadly than intended. Exploiting the bug requires no special access beyond possessing any valid `ApiClient` token with `read:stack` permission (even ones intentionally scoped to a single stack) and knowing/guessing another stack's `stack_id` (owner/name/environment), which is often predictable or discoverable.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the record through the scoped `stacks` relation instead of the bare `Stack` model, mirroring `BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the same authorization binding used by every other stack-scoped API endpoint.

### Proof of Concept
1. As a legitimate user, request a CCMenu URL for stack A: `GET /*stack_id_A/settings` → `CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` scoped to stack A with `permissions: ['read:stack']` and returns a URL containing `?token=<A-scoped-token>`. [8](#0-7) 
2. Using that same `<A-scoped-token>`, send `GET /api/stacks/*stack_id_B/ccmenu?token=<A-scoped-token>` for an unrelated stack B.
3. `authenticate_api_client` accepts the token via query string and authenticates successfully as the stack‑A‑scoped client. [7](#0-6) 
4. `require_permission :read, :stack` only checks the `read:stack` permission string is present — it passes. [5](#0-4) 
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` (not the scoped `stacks` relation), so stack B's data is returned successfully, in the response XML, even though the token was only ever supposed to authorize reads of stack A. [9](#0-8)
