### Title
Duplicate-pubkey collapse in `r of set` / `weighted and` allows a single signature to satisfy multiple slots — ([File: definition.js])

### Summary
ElectrumSV's "accumulator multisig" bug allowed a single private key/signature to be counted toward multiple required-signature slots because the locking script did not enforce that each satisfied slot corresponded to a distinct key. `ocore`'s `validateAuthentifiers`/`validateDefinition` in `definition.js` has the same structural weakness: the multisig-like operators `r of set` and `weighted and` count how many branches evaluate to `true` without ever checking that the `pubkey` values used in the satisfied `sig` branches are distinct.

### Finding Description
`validateDefinition` only checks structural constraints on `r of set`/`weighted and` (positive `required`, array `set`, `set.length>=2`, etc.) — it never verifies uniqueness of `pubkey` across the sibling `sig`/`hash` leaves of the set: [1](#0-0) [2](#0-1) 

During evaluation, `validateAuthentifiers`'s `r of set` handler simply increments `count` for every branch whose `evaluate()` call resolves `true`, and the `sig` leaf handler verifies the signature supplied at that specific path against the `args.pubkey` for that leaf, independent of any other leaf: [3](#0-2) 

Because a `secp256k1` signature is deterministic/verifiable purely as `(message, signature, pubkey)` with no binding to "this slot only," if an address definition contains the same `pubkey` in two or more branches of an `r of set`/`weighted and`/`and` set (whether by mistake or by a malicious co-designer of a shared address), the *same* signature value can be copied into the `assocAuthentifiers` map at multiple paths and will independently verify `true` at each of those paths, inflating `count`/`weight` well beyond the number of distinct keys that actually signed.

This is directly analogous to the shared/multisig address creation flow in `wallet_defined_by_addresses.js`. A shared address definition is proposed by one device (`handleNewSharedAddress`) and the sanity checks it performs only validate `["address", ...]` leaves via `extractAddressPathsFromDefinition`, which does not traverse into `sig` leaves at all — it only records paths for `address`, `hash`, and `in merkle` ops: [4](#0-3) [5](#0-4) 

That means a co-signer who proposes an `r of set`/`weighted and` shared-address definition (e.g. mimicking `createMultisigWallet`'s template pattern) can plant the same raw `pubkey` (their own) at two different `sig`-leaf paths inside the set, and the recipient-side validation in `handleNewSharedAddress` has no mechanism to detect this duplication, because it never inspects `sig` pubkeys — only `address` references: [6](#0-5) 

### Impact Explanation
If a shared/multisig address is created this way (or an application constructs an `r of set`/`weighted and` definition with duplicate pubkeys, e.g. via a bug in a wallet-generation template), the actual number of distinct private keys required to spend from that address can be lower than the nominal `required` threshold the other cosigners believe they agreed to. A malicious cosigner who owns just one of the "distinct-looking" keys could satisfy two or more counted slots with one signature, letting them single-handedly (or with fewer real cosigners) authorize spends from funds that were supposed to require a higher threshold of independent approvals — i.e., unauthorized spending of a shared address's funds, structurally identical to the ElectrumSV "accumulator multisig" theft (the attacker there similarly exploited a `M-of-N` locking script that failed to bind each signature check to a unique key/slot).

### Likelihood Explanation
Exploitation requires the attacker to control (or convince cosigners to accept) an address definition in which the multisig operator's set contains a duplicated `pubkey`. This is reachable by any paired device or wallet co-participant during shared-address setup (`handleNewSharedAddress`/`createNewSharedAddress`), since neither `validateDefinition` (in `definition.js`) nor the shared-address-specific sanity checks (in `wallet_defined_by_addresses.js`) reject duplicate `sig` pubkeys within `r of set`/`weighted and`/`and` constructs. The likelihood is Medium: it requires either a crafted malicious proposal accepted by unsuspecting cosigners, or an application/template bug that produces duplicate pubkeys (e.g., two devices deriving the same key material), rather than a purely remote, no-interaction attack.

### Recommendation
- In `validateDefinition` (`definition.js`), when validating `r of set`, `weighted and`, and `and`/`or` sets, collect the `pubkey` (and `hash`) values used by all `sig`/`hash` leaves nested transitively under that set and reject the definition if any duplicate `pubkey` appears among sibling slots that are meant to be independently counted.
- In `wallet_defined_by_addresses.js`'s `handleNewSharedAddress`, extend `extractAddressPathsFromDefinition` (or add a parallel traversal) to also collect `sig` pubkeys, and reject shared-address proposals whose `r of set`/`weighted and` sets contain duplicate pubkeys.
- Consider enforcing this uniqueness check generally at definition-validation time for any address (not just shared addresses), since duplicate-pubkey `r of set` structures have no legitimate use case and only serve to misrepresent the effective signature threshold.

### Proof of Concept
1. Construct an address definition: `["r of set", {required: 2, set: [["sig",{pubkey:P1}], ["sig",{pubkey:P1}], ["sig",{pubkey:P2}]]}]` where `P1` is controlled solely by the attacker and `P2` by an honest cosigner who believes 2 independent signers are required.
2. Propose this as a shared address via `handleNewSharedAddress`; `extractAddressPathsFromDefinition` only inspects `address`/`hash`/`in merkle` leaves, so it never flags the duplicated `sig` pubkey, and the definition passes `validateAddressDefinition`/`validateDefinition` unchanged.
3. To spend, the attacker signs once with the private key for `P1` and copies that identical signature into both `r.0` and `r.1` authentifier slots in `assocAuthentifiers`.
4. `validateAuthentifiers`'s `r of set` handler evaluates each `sig` leaf independently via `ecdsaSig.verify(unit_hash_to_sign, signature, pubkey)`; both leaves verify `true` against `P1`, `count` reaches `2`, satisfying `required=2` without any input from the honest cosigner holding `P2` — the attacker unilaterally spends funds intended to require two independent parties.

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}
