### Title
Missing synchronization in dry-run AA trigger execution allows shared unit/balance cache corruption (TOCTOU on shared state) - ([File: aa_composer.js])

### Summary
`aa_composer.dryRunPrimaryAATrigger()` (aa_composer.js:272-306) mutates the same shared, non-transactional in-memory unit caches and on-disk AA balance/storage rows that the real AA-trigger execution path uses, but — unlike the real path — it never acquires the `'write'` or `'aa_triggers'` mutexes that the codebase otherwise relies on whenever these shared structures are touched.

### Finding Description
`dryRunPrimaryAATrigger` is invoked directly from `network.js:1271-1281`, inside the `ifOk` callback of `handleJoint` validation, whenever `conf.bDryRunNewTriggers` is enabled and a newly submitted unit has an output to an AA address — i.e., triggerable by any unprivileged unit poster: [1](#0-0) 

It takes its own DB connection, opens a `BEGIN` transaction, and calls `handleTrigger()`: [2](#0-1) 

`handleTrigger` (via `validateAndSaveUnit`) calls `writer.saveJoint()`, which *synchronously* mutates process-wide caches such as `storage.assocUnstableUnits` and `storage.assocBestChildren`, and issues real `UPDATE`/`INSERT` statements against `aa_balances` and `aa_addresses` before the transaction is later rolled back: [3](#0-2) [4](#0-3) 

After the trigger completes, the caller must manually "un-free" these units by calling `revertResponsesInCaches`, which explicitly reaches into `storage.assocUnstableUnits` and calls `storage.forgetUnit`/`fixIsFreeAfterForgettingUnit` to undo the in-memory mutation that `saveJoint` performed: [5](#0-4) [6](#0-5) 

By contrast, the real AA-trigger execution path (`handleAATriggers`) always wraps this exact class of cache/DB mutation in the `'aa_triggers'` mutex: [7](#0-6) 

`dryRunPrimaryAATrigger` takes no equivalent lock. Because `storage.assocUnstableUnits`, `storage.assocBestChildren`, and the `aa_balances`/`aa_addresses.storage_size` rows are shared, mutable, process-global state (not connection-local), a real AA trigger execution that becomes eligible concurrently (e.g., triggered by a separate unit's stabilization via `writer.saveJoint` → `handleAATriggers`, writer.js:724-727) can read or write these same structures while the dry run has temporarily inserted a "phantom" response unit and balance delta that will shortly be rolled back and forgotten. This is structurally analogous to the CVE-2019-2215 bug class: an object's lifetime (creation → temporary live window → teardown/"free") is managed by one code path without synchronization against a second, concurrently-reachable code path that can observe or act on the object during that window.

### Impact Explanation
If the phantom (soon-to-be-rolled-back) unit or balance state produced by the dry run is observed by the real trigger-processing path during the unsynchronized window (e.g., a secondary trigger or balance read using the corrupted `assocBalances`/`assocUnstableUnits`/`assocBestChildren` snapshot), this can lead to state divergence between the in-memory caches and the database, incorrect AA balance bookkeeping, or a crash/`throw Error` path (several of the touched functions `throw` on unexpected cache state, e.g. `storage.js` "different props" and "trying to forget stable unit" assertions), which would manifest as node disagreement on AA state/validity or, in the worst case, an inconsistent balance being used to authorize a payment, i.e. fund loss/freezing for the AA.

### Likelihood Explanation
This requires `conf.bDryRunNewTriggers` to be enabled and requires a specific timing overlap between an unprivileged user's submitted unit (targeting an AA) and a separate, naturally occurring stabilization-triggered AA execution. I was not able to fully confirm, within the scope of this analysis, whether the surrounding `db`/mutex plumbing (e.g. connection pool serialization) incidentally prevents this interleaving in practice, so likelihood/exploitability could not be conclusively established.

### Recommendation
Wrap `dryRunPrimaryAATrigger`'s entire operation (connection acquisition through `revertResponsesInCaches`) in the same `'aa_triggers'` (and/or `'write'`) mutex used by `handleAATriggers`, so that dry-run cache/DB mutations can never interleave with real AA trigger execution or with each other.

### Proof of Concept
Not independently verified end-to-end due to the need to confirm actual interleaving is possible given the connection-pool/mutex plumbing; the structural absence of locking in `dryRunPrimaryAATrigger` compared to `handleAATriggers` is confirmed by direct code inspection (cited above), but a concrete reproducible double-spend/fund-loss scenario was not fully traced within the available investigation budget.

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
