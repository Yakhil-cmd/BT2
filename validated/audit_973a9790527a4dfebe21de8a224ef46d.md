### Title
Cross-repository status forgery via sha-only commit lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` locates commits to update purely by `sha`, without checking that the webhook's `repository.full_name` matches the stack that owns the commit. Because a forked repository shares commit SHAs with its upstream, an attacker who owns a fork (and can legitimately set commit statuses on their own repo) can cause GitHub to deliver a validly-signed "status" webhook that flips the `deploy_state` of a completely different, victim-owned stack's commit from `'blocked'`/`'pending'` to `'allowed'`.

### Finding Description
The binding that should hold is:

`UndeployedCommit.new(victim_commit).deploy_state == f(Status rows created only from webhook payloads where payload['repository']['full_name'] == victim_stack.repository.full_name)`

In the actual code this binding is broken. `StatusHandler#process` does: [1](#0-0) 

i.e. `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never calls the base `Handler#stacks`/`repository_name` scoping helper that other handlers use to constrain processing to the repository named in the payload: [2](#0-1) 

`Commit#create_status_from_github!` then creates a `Status` scoped to the commit's own `stack_id` (from the `Commit` row being iterated, not from the payload), so once a wrong `Commit` row is selected, a real, persisted `Status` is attached to it: [3](#0-2) [4](#0-3) 

`UndeployedCommit#deploy_state` and `Commit#deployable?`/`status` are computed purely from these `Status` rows, with no cross-check against which repository actually authenticated the sha: [5](#0-4) [6](#0-5) 

Signature verification only proves the payload came from a GitHub organization Shipit trusts (`Shipit.github(organization: repository_owner)`), it does not prove the sha named in the payload actually belongs to that repository's commit graph as tracked by the victim stack: [7](#0-6) [8](#0-7) 

**Exploit flow:**
1. Attacker forks (or otherwise gains write access to) a repository whose commit history overlaps with a Shipit-tracked victim repository (a normal GitHub fork preserves upstream commit SHAs) — this is a wholly unprivileged action.
2. If the GitHub App/webhook covering the attacker's repository is already configured for the organization/account it lives under (e.g., the app is installed org-wide, or the attacker's own account has installed a public Shipit-integrated GitHub App on their fork), the attacker calls the real GitHub Statuses API (`POST /repos/{attacker}/{fork}/statuses/{sha}`) on a commit whose SHA is shared with the victim repository — an action fully within the attacker's rights over their own repo.
3. GitHub genuinely and correctly signs and delivers the resulting `status` webhook to Shipit using the real, legitimate webhook secret (no secret is ever known or needed by the attacker).
4. `StatusHandler#process` matches `Commit.where(sha: ...)` across **all** stacks, finds the victim stack's `Commit` row with the same sha, and creates a `Status` on it using `commit.stack_id` (the victim's), turning the dashboard state to `allowed`.
5. A legitimate victim-stack team member, trusting the now-green dashboard, clicks deploy, reaching `Api::DeploysController#create` → `Stack#trigger_deploy` → `Command#start`, executing real deploy commands against the victim host using the app's `GITHUB_TOKEN`.

No existing guard stops this: `verify_signature` only authenticates the sending organization, not the sha-to-repository binding; `drop_unhandled_event` is irrelevant (the `status` event is handled); the `ExplicitParameters` schema for `StatusHandler` validates only `sha`/`state` types, not repository ownership; and `StatusHandler`, unlike other handlers, never consults `repository_name`/`stacks`.

### Impact Explanation
A single forged (but cryptographically genuine) status delivery causes a `Status` record to be persisted against a victim stack's commit purely because of sha collision, silently overriding CI-derived deploy safety state (`'blocked'`/`'pending'` → `'allowed'`). This is repeatable against any Shipit-tracked repository that shares commit history with a repository the attacker controls (fork scenario is the common case), and drives an unauthorized deploy on the victim host once a legitimate operator acts on the falsified dashboard — matching the Critical category ("a payload for one repository mutating another's stack/commit... or an unauthorized deploy").

### Likelihood Explanation
Requires: (a) the target Shipit-tracked repository has a fork or sibling repo the attacker legitimately owns/administers, sharing at least one commit SHA (trivial via forking), and (b) the attacker's repo is covered by a GitHub App/webhook installation whose signature Shipit's `Shipit.github(organization: repository_owner)` accepts (e.g., organization-wide app installation, or a public app the attacker installs on their own account) — no Shipit or GitHub secret needed. Given how common org-wide GitHub App installs are, and that forking preserves SHAs by design, this is a low-cost, repeatable attack requiring no privileged Shipit access.

### Recommendation
In `StatusHandler#process`, scope commit lookup by both `sha` and the payload's repository, mirroring the base `Handler#stacks`/`repository_name` helper used by other handlers, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently filter `Commit.where(sha: params.sha)` down to commits whose `stack.repository` matches `Repository.from_github_repo_name(payload.dig('repository','full_name'))`.

### Proof of Concept
Minitest test plan (model-level, no live GitHub):
1. Create two `Stack`/`Repository` fixtures, `victim_stack` (repo `victim/app`) and `attacker_stack` (repo `attacker/fork`), each with a `Commit` sharing the same `sha` value (simulating a forked commit).
2. Set up `victim_commit` with no successful status (state `'pending'` or `'blocked'`), and assert `UndeployedCommit.new(victim_commit, index: 0).deploy_state` returns `'pending'`/`'blocked'`.
3. Build a webhook-shaped payload naming `attacker/fork` as `repository.full_name` with the shared `sha` and `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as the engine test suite does elsewhere via `GithubHook.any_instance.stubs(:verify_signature).returns(true)`).
5. Reload `victim_commit` and assert `UndeployedCommit.new(victim_commit, index: 0).deploy_state == 'allowed'`, proving the binding `deploy_state(victim_commit) == f(status rows scoped to victim repo)` is violated by a payload naming a different repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
