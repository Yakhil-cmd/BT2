### Title
Webhook signature scoping mismatch allows cross-organization status/commit spoofing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and therefore which `webhook_secret`) to validate an inbound HMAC signature against by reading `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) out of the **attacker-controlled JSON body itself**, not out of any independently trusted source. [1](#0-0) [2](#0-1)  Separately, the webhook handlers that actually act on the payload (e.g. `PushHandler`, `StatusHandler` via `Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a different field of the same attacker-controlled JSON body. [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
`GitHubApp#verify_webhook_signature` explicitly bypasses verification whenever the org's configured `webhook_secret` is blank: `return true unless webhook_secret`. [6](#0-5)  This is a legitimate configuration option (per `docs/setup.md`, `webhook_secret` is described as "optional").

The binding that should hold is: **the organization whose credential authenticated the request == the organization/repository being written to**. In this codebase that equality is never enforced — the controller derives the authenticating organization from `repository.owner.login` in the JSON body, while the handlers act on `repository.full_name` from that same body, and nothing cross-checks that the two point to the same tracked repository, nor is `repository.owner.login` derived from a cryptographically-bound identity.

Exploit path:
1. Suppose the Shipit deployment tracks two GitHub organizations/App configs, `victim-org` (properly configured with a non-blank `webhook_secret`) and `attacker-org` (configured, but with a blank `webhook_secret` — a valid, documented configuration since the secret is optional).
2. An unauthenticated attacker POSTs directly to `/webhooks` with `X-Github-Event: push` (or `status`) and a JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/some-tracked-repo"`.
3. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and calls `verify_webhook_signature`, which returns `true` unconditionally because `attacker-org`'s `webhook_secret` is blank — no signature check is actually performed against the real sender. [1](#0-0) 
4. The request passes the `before_action`, and `Shipit::Webhooks.for_event(event)` handlers are invoked with the full, attacker-crafted `params`, including `repository.full_name = "victim-org/some-tracked-repo"`. [7](#0-6) 
5. `Handler#stacks` / `Handler#repository_name` resolve the tracked stacks strictly from `repository.full_name`, with no relation to which org actually authenticated: `Repository.from_github_repo_name(repository_name)`. [3](#0-2) 
6. For the `status` event, `StatusHandler#process` finds any `Commit` matching the attacker-supplied `sha` and calls `commit.create_status_from_github!(params)` with an attacker-chosen `state`/`context`, letting the attacker forge a "success" CI status on any commit of any tracked stack, regardless of which org that repository belongs to. [5](#0-4)  For `push`, the attacker can force a `GithubSyncJob`/`sync_github` call with an arbitrary `expected_head_sha` against a victim stack, all without any real webhook secret from that org. [8](#0-7) 

Note: because `verify_webhook_signature` returns `true` for *any* org with a blank secret irrespective of which org is really configured that way, the same class of confusion also applies whenever any tracked org intentionally leaves `webhook_secret` unset (a documented, supported configuration) — every other tracked org's data is then reachable through it.

### Impact Explanation
This crosses a credential boundary the rules identify explicitly ("an organization that authenticated versus the repository that is written"). Forged CI statuses can flip `required_statuses`/`blocking_statuses` checks used to gate deploy eligibility (`Commit#deployable?`, `DeploySpec#required_statuses`), which can enable an unauthorized deploy to proceed by making an otherwise-blocked commit appear CI-green — this aligns with the "unauthorized deploy" Critical impact category. Even absent that chained effect, being able to inject/alter commit statuses and trigger sync jobs on repositories belonging to organizations the attacker has no relationship to is an unauthenticated write into stack state, satisfying the "cross-repository writes" criterion.

### Likelihood Explanation
Requires no session, `ApiClient` token, GitHub App key, or repository write access — it is a plain unauthenticated POST to the public `/webhooks` endpoint. It is contingent on the deployment having at least one tracked GitHub organization configured with a blank `webhook_secret` (an explicitly supported, documented configuration in `docs/setup.md`, and the exact scenario `GitHubApp#verify_webhook_signature` special-cases), while other tracked organizations use a real secret. This is a plausible real-world setup (e.g. staging/dev orgs left without a secret) rather than a purely theoretical one, but it is conditional on that configuration choice, which somewhat limits universal applicability.

### Recommendation
Do not select the verifying `webhook_secret` from attacker-controlled payload fields at all when one is available; if any org is intentionally configured without a `webhook_secret`, its "verified" status must never be allowed to authorize actions against a *different* org/repository. Concretely: after signature verification, re-derive and enforce that `repository.owner.login` used for verification equals the owner embedded in `repository.full_name` used by the handlers (reject on mismatch), and/or refuse to treat a webhook as "verified" for organizations lacking a configured secret unless the target repository also belongs to that same secret-less org. Consider making `webhook_secret` mandatory for any org whose repositories are tracked in production.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim-tracked-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "attacker-org-with-blank-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
Given `Shipit.github(organization: "attacker-org-with-blank-secret")` has `webhook_secret` unset, `verify_webhook_signature` short-circuits to `true` (`lib/shipit/github_app.rb:76-77`), the request passes `before_action :verify_signature`, and `StatusHandler#process` creates a forged status on the victim commit found purely by `sha`, entirely independent of the "authenticating" `attacker-org-with-blank-secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
