### Title
Webhook signature verification keyed on `repository.owner.login` while handlers act on `repository.full_name` allows cross-organization stack sync forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from the attacker-controlled JSON body (`params.dig('repository','owner','login')`), while the event handlers (e.g. `PushHandler`) resolve the actual `Repository`/`Stack` to act on using a different field of the same attacker-controlled body: `payload.dig('repository','full_name')`. Because the field used for authentication and the field used for authorization/dispatch are not the same, and nothing enforces that `repository.full_name` is consistent with `repository.owner.login`, a party who legitimately controls the webhook secret for one configured GitHub organization can forge a signature that Shipit accepts, while making the payload's `repository.full_name` point at a stack belonging to a *different* configured organization/repository, causing Shipit to sync/act on a stack it was never authorized to touch for that organization.

### Finding Description
Multi-org Shipit installations configure one `GitHubApp` (and one `webhook_secret`) per GitHub organization: [1](#0-0) , [2](#0-1) .

The webhook signature check picks the org/secret to verify against from `repository_owner`, computed purely from the JSON body: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` just checks the HMAC of the raw body against the secret configured for that org: [5](#0-4) 

After signature verification passes, the *same untrusted body* is dispatched to handlers as `params`, and handlers resolve the target repository/stack from a **different** JSON key, `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Equality being broken: `signature verified for organization = payload["repository"]["owner"]["login"]` should imply `stack acted upon belongs to that same organization`, but the engine actually enforces `stack acted upon = Repository.from_github_repo_name(payload["repository"]["full_name"])`, an independent, attacker-supplied string. Nothing ties `full_name`'s owner segment to `owner.login`, and both come from the same attacker-controlled raw JSON body used to compute the signature. An attacker who is a legitimate admin/webhook-owner of organization `A` (and therefore possesses `A`'s `webhook_secret`, e.g. because Shipit is deployed for multiple orgs including one they administer) can produce a validly-signed request where `repository.owner.login = "A"` (used only for secret selection) but `repository.full_name = "B/victim-repo"` (used for the actual sync action), causing `PushHandler` to run `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` against org `B`'s stack.

### Impact Explanation
`sync_github` enqueues `GithubSyncJob`, which fetches commits from GitHub for the stack and appends them to Shipit's commit history/state, and can mark stacks accessible/inaccessible: [8](#0-7) , [9](#0-8) . Because Shipit ties automated/continuous deployment to the synced commit history (`continuous_deployment`, `undeployed_commits`), an attacker able to trigger a cross-org sync for a victim stack could influence when/what commit is considered the deployable head for another organization's stack, potentially triggering unintended automated deploys for a repository/organization the attacker does not otherwise control. This is a cross-tenant authorization bypass on the webhook trust boundary (organization that authenticated the request ≠ repository/stack actually acted on).

### Likelihood Explanation
Exploitation requires the attacker to already possess a valid `webhook_secret` for at least one org configured in the multi-org Shipit deployment — realistically, this applies to an org admin/webhook owner for a *different, legitimately connected* organization within the same Shipit instance (a lower-privileged, but still credentialed, actor relative to other orgs on the same install). This is only reachable when Shipit is configured with `Using Multiple Github Applications` (multi-org secrets, as documented), which is a supported and real deployment pattern [1](#0-0) . Within that configuration, no additional secrets or session are required beyond the one webhook secret the attacker already legitimately has for their own org, and no other check ties `repository.full_name` to `repository.owner.login`.

### Recommendation
Verify the signature using the same repository identity that handlers use to select the target stack (i.e., derive the org for secret selection from `repository.full_name`'s owner segment, or otherwise cryptographically bind the two), and additionally validate in `Handler#stacks` / `PushHandler#process` that the resolved `Repository`'s owner matches the organization whose secret validated the signature before acting on it.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, `A` and `B`, each with stacks and a distinct `webhook_secret_A` / `webhook_secret_B` (per `docs/setup.md` multi-org config).
2. As an entity that legitimately owns `webhook_secret_A` (e.g., configured a webhook against org `A`'s repo), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(webhook_secret_A, raw_body)`.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "A")` and validates successfully against `webhook_secret_A`. [10](#0-9) 
6. `PushHandler#process` resolves `stacks` from `repository.full_name = "B/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on org `B`'s stack — despite the signature only proving knowledge of org `A`'s secret. [11](#0-10)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks

        params do
          requires :ref
          requires :after

        def process

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
