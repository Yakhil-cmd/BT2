### Title
Concurrent KIP-71 Bound Votes in the Same Epoch Can Invert `LowerBoundBaseFee > UpperBoundBaseFee`, Permanently Corrupting the Base Fee Mechanism — (`kaiax/gov/headergov/impl/header.go`)

---

### Summary

The `checkConsistency` function in `kaiax/gov/headergov/impl/header.go` validates each KIP-71 base-fee bound vote in isolation against the **currently-ratified** value of the other bound. Because header governance collects all votes across an entire epoch and ratifies them together at the epoch boundary, two votes cast in the same epoch — one raising `LowerBoundBaseFee` and one lowering `UpperBoundBaseFee` — can each pass the per-vote check while their combined ratification produces `LowerBoundBaseFee > UpperBoundBaseFee`. This inverts the EIP-1559-style fee mechanism in `NextMagmaBlockBaseFee`, permanently locking the base fee in a state where high gas demand drives the fee **down** and low demand drives it **up**, corrupting every subsequent fee charge until governance issues a corrective vote.

---

### Finding Description

`checkConsistency` enforces the bound relationship with two independent guards:

```go
// kaiax/gov/headergov/impl/header.go  lines 179-192
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads CURRENT ratified state
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)          // reads CURRENT ratified state
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
```

Each guard reads `h.GetParamSet(blockNum)`, which returns the **already-ratified** parameter set, not the pending votes accumulating in the current epoch. The epoch ratification path in `getExpectedGovernance` collects every vote cast in the previous epoch and applies them all at once:

```go
// kaiax/gov/headergov/impl/header.go  lines 218-233
for _, voteBlock := range sortedVoteBlocks {
    vote := prevEpochVotes[voteBlock]
    govs.Add(string(vote.Name()), vote.Value())   // both bounds applied together
}
```

There is no cross-vote consistency check at ratification time. The invariant `LowerBoundBaseFee ≤ UpperBoundBaseFee` is therefore only enforced per-vote against the pre-epoch state, not against the post-epoch state that will actually be written.

---

### Impact Explanation

Once `LowerBound > UpperBound` is ratified, `NextMagmaBlockBaseFee` in `params/kip71_config.go` enters a permanently broken state. The clamping block at lines 82–86 forces `parentBaseFee` to either `UpperBound` or `LowerBound` for every possible input value (because the two ranges now overlap completely):

```go
// params/kip71_config.go  lines 82-86
if parentBaseFee.Cmp(upperBoundBaseFee) >= 0 {
    parentBaseFee = upperBoundBaseFee   // any value ≥ upper → upper (the smaller number)
} else if parentBaseFee.Cmp(lowerBoundBaseFee) <= 0 {
    parentBaseFee = lowerBoundBaseFee   // any value < upper → also ≤ lower → lower (the larger number)
}
```

The shortcut guards at lines 94 and 112 then immediately return the clamped value without further adjustment:

- **High gas usage** (`parentGasUsed > gasTarget`): `parentBaseFee` is clamped to `UpperBound` (the smaller value) and the shortcut at line 94 returns it immediately → fee is **minimized** when demand is high.
- **Low gas usage** (`parentGasUsed < gasTarget`): `parentBaseFee` is clamped to `LowerBound` (the larger value) and the shortcut at line 112 returns it immediately → fee is **maximized** when demand is low.

This is a complete inversion of the intended EIP-1559 fee market. Every transaction fee charged to users is wrong for as long as the inverted bounds remain in effect. The corruption is persistent across all subsequent blocks until a corrective governance vote is ratified in a later epoch.

---

### Likelihood Explanation

**`none` governance mode**: Any two council members can independently cast conflicting bound votes in the same epoch. No coordination or privileged access beyond council membership is required.

**`single` governance mode** (Mainnet/Kairos): The governing node must cast two votes in the same epoch — one for each bound — that together invert the relationship. This can occur accidentally (e.g., a multi-step parameter migration where the operator intends to narrow the range but issues both votes in the same epoch) or intentionally. The code provides no guard against it in either mode.

---

### Recommendation

Add a cross-bound consistency check at ratification time inside `getExpectedGovernance` (or equivalently in `VerifyGov`) that rejects any epoch governance payload where the resolved `LowerBoundBaseFee ≥ UpperBoundBaseFee`. Additionally, strengthen the per-vote check to also reject a new `LowerBoundBaseFee` vote if any pending same-epoch vote has already lowered `UpperBoundBaseFee` below the proposed value, and vice versa.

At minimum, add a post-ratification guard:

```go
// After assembling govs in getExpectedGovernance:
newLower, hasLower := govs[gov.Kip71LowerBoundBaseFee]
newUpper, hasUpper := govs[gov.Kip71UpperBoundBaseFee]
currentParams := h.GetParamSet(blockNum)
resolvedLower := currentParams.LowerBoundBaseFee
resolvedUpper := currentParams.UpperBoundBaseFee
if hasLower { resolvedLower = newLower.(uint64) }
if hasUpper { resolvedUpper = newUpper.(uint64) }
if resolvedLower > resolvedUpper {
    // drop or reject the offending vote(s)
}
```

### Proof of Concept

**Initial state**: `LowerBound = 25 gwei`, `UpperBound = 750 gwei`

**Epoch K, block N**: Vote `kip71.lowerboundbasefee = 500 gwei`
- Check: `500 > 750`? → **No** → vote accepted ✓

**Epoch K, block M** (M ≠ N, same epoch): Vote `kip71.upperboundbasefee = 400 gwei`
- Check: `400 < 25`? → **No** → vote accepted ✓

**Epoch K+1 boundary**: Both votes ratified together → `LowerBound = 500 gwei`, `UpperBound = 400 gwei`

**Next block with high gas usage** (`parentGasUsed > gasTarget`):
- `parentBaseFee` clamped to `UpperBound = 400 gwei` (line 82–83 of `params/kip71_config.go`)
- Shortcut at line 94: `parentBaseFee == upperBoundBaseFee` → return `400 gwei`
- **Result**: fee is at its minimum despite high demand — inverted behavior

**Next block with low gas usage** (`parentGasUsed < gasTarget`):
- `parentBaseFee` clamped to `LowerBound = 500 gwei` (line 84–85)
- Shortcut at line 112: `parentBaseFee == lowerBoundBaseFee` → return `500 gwei`
- **Result**: fee is at its maximum despite low demand — inverted behavior

The base fee is permanently stuck oscillating between 400 and 500 gwei with inverted incentives, corrupting all KAIA fee charges until a corrective governance vote takes effect in a subsequent epoch. [1](#0-0) [2](#0-1) [3](#0-2)
