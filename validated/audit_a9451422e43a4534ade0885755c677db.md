### Title
CLStakingInfo Overwrite in `consolidateNodes()` Silently Drops CL Pool Staking Rewards — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidateNodes()` in `kaiax/staking/staking_info.go` assigns `cmap[r].CLStakingInfo = clsi` (line 157) when attaching consensus-liquidity data to a consolidated validator node. When a validator has registered two NodeIds in AddressBook that share the same `RewardAddr`, and both NodeIds have separate entries in CLRegistry, the second `CLStakingInfo` silently overwrites the first. The first CL pool's staking amount is permanently dropped from every downstream reward calculation for that block, causing it to receive zero KAIA reward.

---

### Finding Description

`consolidateNodes()` first builds a map `cmap[RewardAddr] → consolidatedNode` by aggregating all AddressBook entries that share a `RewardAddr` (staking amounts are correctly summed). It then attaches CLStakingInfo entries by looking up each `CLNodeId` in the `nToR` map:

```go
// kaiax/staking/staking_info.go lines 151-159
if len(si.CLStakingInfos) > 0 {
    for _, clsi := range si.CLStakingInfos {
        if r, ok := nToR[clsi.CLNodeId]; ok {
            // One CLStakingInfo per validator is guaranteed by CLRegistry.
            cmap[r].CLStakingInfo = clsi   // ← plain assignment, not accumulation
        }
    }
}
```

The comment asserts "One CLStakingInfo per validator is guaranteed by CLRegistry." However, the CLRegistry maps by `CLNodeId` (node address), not by `RewardAddr`. The AddressBook explicitly supports multiple NodeIds sharing one `RewardAddr` — this is the entire purpose of the consolidation step. If NodeIds N1 and N3 both resolve to `RewardAddr R1` via `nToR`, and both have separate CLRegistry entries, the loop processes them sequentially:

1. `cmap[R1].CLStakingInfo = (N1, P1, A_CL1)` — first CL stored
2. `cmap[R1].CLStakingInfo = (N3, P2, A_CL2)` — **overwrites**, P1 and A_CL1 are gone

The test suite explicitly exercises this path and acknowledges the overwrite:

```go
// kaiax/staking/staking_info_test.go lines 258-267
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
{CLNodeId: n3, CLPoolAddr: clPool2, CLStakingAmount: clStakingAmount2},
// expectedConsolidated: CLStakingInfo = {n3, clPool2, clStakingAmount2}  ← clPool1 dropped
```

The "not feasible in real" comment is an unverified assumption. The CLRegistry has no knowledge of AddressBook's `RewardAddr` grouping and cannot enforce a "one CL per RewardAddr" invariant.

---

### Impact Explanation

After the overwrite, every downstream consumer of `ConsolidatedNodes()` operates on corrupted data:

**`assignStakingRewards` / `assignStakingRewardsFlex`** (`kaiax/reward/impl/getter.go` lines 488–534 / 421–484):

```go
cnTotalStakingAmount := cn.StakingAmount
if isPrague && cn.CLStakingInfo != nil {
    cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount  // only A_CL2, A_CL1 missing
}
totalExcessInt += cnTotalStakingAmount - minStake
```

The validator's proportional share of staking rewards is computed using `A_CL2` only; `A_CL1` is excluded from `totalExcessInt`, understating the validator's weight relative to all other validators.

**`Split()`** (`kaiax/staking/staking_info.go` lines 169–187):

```go
clAmount := new(big.Int).Mul(clAmountBig, amount)
clAmount = clAmount.Div(clAmount, totalAmount)  // totalAmount = StakingAmount + A_CL2 only
```

The reward is split between `RewardAddr` and `P2` only. `P1` receives **zero KAIA** for every block, despite having staked funds in CLRegistry.

Concrete loss: if `A_CL1 = 5 000 000 KAIA` and the staking reward budget is 2.56 KAIA/block, `P1` loses its entire proportional share every block. The lost amount is redistributed to other validators, constituting an unauthorized reward redistribution affecting system-managed KAIA.

---

### Likelihood Explanation

**Trigger conditions:**
1. A validator registers two or more NodeIds in AddressBook with the same `RewardAddr` (explicitly supported by the protocol — the consolidation feature exists for this reason).
2. Two or more of those NodeIds have separate entries in CLRegistry (each NodeId can independently register a CL pool).

Neither condition requires privileged access or majority-validator collusion. A single validator controlling two NodeIds and two CL pools can reach this state through normal protocol operations. The CLRegistry does not cross-reference AddressBook `RewardAddr` groupings.

---

### Recommendation

Replace the plain assignment with an accumulation. Since `consolidatedNode.CLStakingInfo` is a single pointer, the fix requires either:

1. **Sum the amounts, pick one pool address** (lossy but simple):
   ```go
   if existing := cmap[r].CLStakingInfo; existing != nil {
       existing.CLStakingAmount += clsi.CLStakingAmount
   } else {
       cmap[r].CLStakingInfo = clsi
   }
   ```
2. **Store a slice of CLStakingInfos per consolidated node** and update `Split()` to iterate over all of them, distributing rewards to each pool proportionally.
3. **Enforce the invariant at the CLRegistry contract level** by rejecting registration of a `CLNodeId` whose `RewardAddr` (as looked up in AddressBook) already has a registered CL entry.

Option 2 is the most correct and mirrors how `StakingAmount` is already accumulated across multiple NodeIds.

---

### Proof of Concept

Given:
- AddressBook: `NodeIds=[N1,N3]`, `RewardAddrs=[R1,R1]`, `StakingAmounts=[10M,10M]`
- CLRegistry: `{CLNodeId:N1, CLPoolAddr:P1, CLStakingAmount:5M}`, `{CLNodeId:N3, CLPoolAddr:P2, CLStakingAmount:5M}`
- `MinimumStake=5M`, staking reward budget = 1e18 kei

**Current (buggy) execution:**

`consolidateNodes()` produces: `CN_R1 = {[N1,N3], R1, StakingAmount=20M, CLStakingInfo=(N3,P2,5M)}`

`assignStakingRewards`:
- `cnTotalStakingAmount = 20M + 5M = 25M` (A_CL1=5M missing)
- `totalExcessInt = 25M - 5M = 20M`
- `reward = 1e18 * 20M / 20M = 1e18`
- `Split(1e18)`: `clAmount = 5M/(20M+5M) * 1e18 = 0.2e18` → P2 gets 0.2e18, R1 gets 0.8e18
- **P1 receives 0**

**Correct execution** (if both CLs were accumulated):
- `cnTotalStakingAmount = 20M + 5M + 5M = 30M`
- `totalExcessInt = 30M - 5M = 25M`
- `reward = 1e18 * 25M / 25M = 1e18`
- P1 and P2 each receive their proportional share; R1 receives the remainder

P1 loses `≈0.167e18 kei` per block. Over 86 400 blocks/day this is a material, persistent loss of KAIA staking rewards. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
