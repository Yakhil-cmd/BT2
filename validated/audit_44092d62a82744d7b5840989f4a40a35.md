### Title
Cross-tenant `Team`/`User` membership hijack via unscoped `github_id` lookup and login-only `User` resolution in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves the target `Team` purely by the attacker-supplied numeric `params.team.id` and resolves the target `User` purely by the attacker-supplied `params.member.login`, without ever checking that the verified webhook's organization actually owns that `Team` or that the named `member.login` is a real member of that team/org. Because `verify_signature` only proves the request was signed with *some* org's `webhook_secret`, not that the payload content is truthful, a webhook legitimately signed with org A's secret can mutate `Team` memberships belonging to org B, or silently attach/detach an unrelated, pre-existing global `Shipit::User` (matched only by login string) to/from a team.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`verified_organization(payload) == team.organization` AND `member.login corresponds to a real GitHub member of that team` — the code enforces neither.

Path:
- `WebhooksController#verify_signature` selects the HMAC key via `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the JSON body (`params.dig('organization','login')` for membership events), and checks the signature against the raw body [1](#0-0) . This only proves "signed with organization X's configured secret" — it does not constrain any other field in the body, including `team.id` or `member.login`.
- `MembershipHandler#process` then does:
```ruby
team = find_or_create_team!
member = User.find_or_create_by_login!(params.member.login)
``` [2](#0-1) 
- `find_or_create_team!` looks up by `github_id: params.team.id` alone; if a `Team` with that id already exists (regardless of which org it belongs to), it is returned unchanged, and `team.organization` is only set inside the `create` block, never re-validated against `params.organization.login` on the found path [3](#0-2) .
- `User.find_or_create_by_login!` looks up by `login` alone; if a `User` row with that login already exists, it is returned with **no** call to GitHub to confirm it's actually the org's member — the `github.api.user(login)` call only happens inside the `create` block, i.e. only for brand-new users [4](#0-3) . `User` rows are explicitly designed as global (comment: "Users are global, any app can be used") and are keyed only by `login`, not scoped per organization.
- `Team#add_member`/`members.delete` then mutate `Membership` rows unconditionally [5](#0-4) .

Attacker request: attacker legitimately possesses the `webhook_secret` for their own configured org ("attackerorg") in a multi-org `Shipit.github(organization:)` setup [6](#0-5) . They POST directly to `/webhooks` (not via real GitHub delivery — nothing ties the payload to an actual GitHub event) with `X-Github-Event: membership`, `organization.login: "attackerorg"` (so `verify_signature` picks and passes with attackerorg's own secret), `team.id` set to the numeric `github_id` of an existing `Shipit::Team` belonging to a *different* org, and `member.login` set to the login of an existing `Shipit::User` (e.g., a currently-active Shipit operator). Because `find_or_create_team!` matches only on `github_id` and `find_or_create_by_login!` matches only on `login`, the handler resolves both to the real, pre-existing cross-tenant records and executes `team.add_member(member)` or `team.members.delete(member)` on them.

Existing guards fail specifically because: `verify_signature` authenticates *who sent the request*, not *what the request claims about team/organization ownership*; `ExplicitParameters` only validates types/presence, not cross-referential integrity between `organization.login`, `team.id`, and `member.login`; and no code path re-confirms team-organization or team-membership truth via the GitHub API when records already exist.

### Impact Explanation
An attacker who legitimately owns one org's webhook integration can, with a single POST request per target, add an arbitrary existing Shipit user to (or remove them from) any `Team` in the system that they can identify by its numeric `github_id`, regardless of that team's real organization. This directly matches the explicitly in-scope Critical category "a payload for one repository mutating another's stack, commit, task or team," and also the High category "escalation into `Shipit.github_teams` authorization" since `Team` membership feeds `User#authorized?` [7](#0-6) . The attack is repeatable against any team whose `github_id` the attacker can learn or guess, and against any user whose login they know (logins are public GitHub identifiers), with no live GitHub involvement.

### Likelihood Explanation
Requires a multi-org `Shipit.github(organization:)` deployment where the attacker legitimately controls one org's `webhook_secret` (a documented, supported configuration per `docs/setup.md`'s "Using Multiple Github Applications" section and `test/dummy/config/secrets_double_github_app.yml`). No Shipit session, API token, or other org's secret is needed. The only "unknowns" the attacker must obtain are a target `Team`'s numeric `github_id` and a target `User`'s `login` — both are low-entropy/discoverable values (sequential GitHub IDs, public logins), not secrets. Cost per attack: one crafted HTTP POST.

### Recommendation
In `find_or_create_team!`, require that an already-found `Team`'s `organization` equals `params.organization.login` (reject/raise otherwise) instead of silently reusing any team matched purely by `github_id`. In `MembershipHandler#process`, scope `User.find_or_create_by_login!` lookups/writes to only operate within the context of the verified organization (e.g., re-verify membership via the org's GitHub API before mutating, or restrict the found `User` to one already associated with that org's team), rather than trusting an unauthenticated `member.login` string against the global `users` table.

### Proof of Concept
minitest plan (in the style of `test/controllers/webhooks_controller_test.rb`, using multi-org fixtures similar to `test/dummy/config/secrets_double_github_app.yml`):
1. Configure two orgs, `OrgOne` (victim) and `OrgTwo` (attacker), each with its own `webhook_secret`.
2. Create `shipit_teams(:orgone_team)` with `organization: "OrgOne"`, `github_id: 999`, and a member `shipit_users(:victim_operator)` (login `"victim"`).
3. As the attacker, build a membership payload: `{ action: 'added', team: { id: 999, name: 'x', slug: 'x', url: 'http://x' }, organization: { login: 'OrgTwo' }, member: { login: 'victim' } }`, sign it with `OrgTwo`'s `webhook_secret`, and POST to `/webhooks` with `X-Github-Event: membership`.
4. Assert `response.status == :ok` (signature verified for OrgTwo).
5. Assert, **before**: `shipit_teams(:orgone_team).organization == "OrgOne"` and `shipit_teams(:orgone_team).members` state is known/unchanged for the victim.
6. Assert, **after**: `Team.find_by(github_id: 999).organization == "OrgOne"` still (team was not re-created for OrgTwo) yet `Team.find_by(github_id: 999).members.include?(shipit_users(:victim_operator))` has flipped according to the `added`/`removed` action — demonstrating a payload signed for `OrgTwo` mutated `OrgOne`'s team membership for an existing global `User` with no real GitHub membership change having occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
