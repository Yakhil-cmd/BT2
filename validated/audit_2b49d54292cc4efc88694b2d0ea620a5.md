### Title
`review_stacks_enabled` is bypassed for `prevent_with_label`/`allow_with_label` repositories, allowing unbounded review-stack creation via repeated PR opens - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` is intended to require `repository.review_stacks_enabled == true` before any review stack is provisioned, but a Ruby operator-precedence error scopes that check to only the `allow_all` branch. Because `&&` binds tighter than `||`, the `prevent_with_label` (and `allow_with_label`) branches are evaluated independently of `review_stacks_enabled`, so any repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` still auto-creates and provisions a distinct review stack for every PR opened without the bypass label.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold for `provision?` to return `true` under any behavior.

Actual code in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby precedence (`&&` before `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So `review_stacks_enabled` only gates the `allow_all` term; the `allow_with_label` and `prevent_with_label` terms are entirely independent of it. Any repository configured with `provisioning_behavior: prevent_with_label` (regardless of `review_stacks_enabled`) will return `true` from `provision?` for every PR that lacks the bypass label.

`process` then calls `ReviewStackAdapter#find_or_create!`, which for a new PR number calls `create!`, persisting a new `Stack`/`ReviewStack` with `environment: "pr#{params.number}"` and `branch: params.pull_request.head.ref`, and immediately enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

Each such stack independently drives the deploy pipeline (executes the PR branch's `shipit.yml` tasks with `GITHUB_TOKEN` in the task environment). The same unguarded pattern also exists in `ReopenedHandler#unarchive?`: [3](#0-2) 

Existing tests only cover the `allow_all` branch with `review_stacks_enabled: false`: [4](#0-3) 
and never assert that `prevent_with_label`/`allow_with_label` are also gated by `review_stacks_enabled: false`, so the divergence is untested and unguarded by any other check (`respond_to_pull_request_opened?` only additionally checks `params.action == "opened"`).

### Impact Explanation
On any repository whose operator has set `provisioning_behavior: prevent_with_label` (a legitimate, common configuration) but left `review_stacks_enabled: false` intending review stacks to be fully disabled, an unprivileged attacker opening PRs without the bypass label triggers unauthorized `Stack` creation and provisioning execution — running attacker-controlled branch content (`shipit.yml`) with `GITHUB_TOKEN` in the task environment — once per opened PR number, with no bound other than how many PRs can be opened. This is an authorization-bypass leading to unauthorized deploy/provision task execution, matching the Critical category ("unauthorized deploy... execution" / RCE-adjacent task execution on the deploy host).

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`) while `review_stacks_enabled` is `false` — a plausible but non-default combination that an operator could reach when disabling review stacks without also reverting behavior mode. No secrets or privileged roles are required from the attacker: opening a PR and controlling its label state is sufficient, and this can be repeated for every new PR number to multiply the effect.

### Recommendation
Fix the precedence bug by parenthesizing the `review_stacks_enabled` check across the whole expression, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no bypass label -> prevent_with_label term is true

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Currently `Shipit::Stack.count` grows by 1 despite `review_stacks_enabled == false`, confirming the bypass; looping this with distinct `payload["number"]`/`payload["pull_request"]["number"]` values demonstrates unbounded growth as described in the question.
