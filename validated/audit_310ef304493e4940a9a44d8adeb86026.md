The webhook signature-verification binding is: `WebhooksController#verify_signature` authenticates a payload against the GitHub organization derived from `repository.owner.login` (or `organization.login`) in the payload [1](#0-0) , using a per-organization `webhook_secret` looked up via `Shipit.github(organization: repository_owner)` [2](#0-1) . However, `StatusHandler#process` — invoked with the same raw payload after signature verification succeeds — resolves target `Commit` records purely by SHA, with **no scoping to the repository/organization that was actually authenticated**: [3](#0-2) 

This breaks the binding "organization that authenticated == repository that is written": every other handler (`PushHandler`, `CheckSuiteHandler`) scopes its writes through `stacks`, which is derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))` in the base `Handler` class [4](#0-3) , tying the mutation back to the repository named in the (verified) payload. `StatusHandler`, however, ignores `repository_name`/`stacks` entirely and does a global `Commit.where(sha: params.sha)` lookup, so a `status` webhook validly signed for organization/repository A can mutate the CI/status state of a `Commit` row belonging to a completely different `Stack`/`Repository`/organization B, as long as the two happen to share (or collide on) a commit SHA — e.g. any repository fork/mirror relationship, a shared upstream commit imported into multiple Shipit stacks, or a repository that was renamed/transferred so an old `full_name` SHA still exists in Shipit's DB under the new owner while a differently-configured org keeps sending statuses for the same SHA.

### Title
Cross-repository commit status forgery via unscoped SHA lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook against the GitHub organization/repository named in the payload's `repository.owner.login`, but `StatusHandler#process` then writes the resulting CI status to any `Commit` in the database matching the given SHA, without checking that the commit belongs to a `Stack`/`Repository` associated with that authenticated organization.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) based on `repository_owner`, extracted from the payload's `repository.owner.login` (falling back to `organization.login`) [5](#0-4) . Once the signature checks out for that organization, `create` dispatches the entire raw payload to every registered handler for the event type [6](#0-5) .

The base `Handler` class provides a `stacks` helper that correctly re-derives the target repository from the payload's `repository.full_name` via `Repository.from_github_repo_name` [4](#0-3) , and `PushHandler`/`CheckSuiteHandler` use this `stacks` scope to constrain all writes to the correct repository/organization [7](#0-6) [8](#0-7) .

`StatusHandler#process`, however, bypasses `stacks`/`repository_name` entirely and performs a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Since `Commit` rows are not namespaced by the sending repository at the point of lookup, a validly-signed `status` event from organization/repository A will update the status of every `Commit` row across all stacks in the Shipit instance that happen to share that SHA — regardless of which organization's `webhook_secret` authenticated the request. This is exactly the binding break called out in the analog rules: "an organization that authenticated versus the repository that is written" — the equality `authenticated_org(payload) == repository_of(commit_written)` does not hold.

### Impact Explanation
Commit statuses gate deployability checks in Shipit (`deployment_checks_passed?`/CI status gating referenced throughout `Stack`/`Commit` models). An attacker who legitimately controls one Shipit-tracked repository/organization (and can therefore produce genuinely GitHub-signed `status` webhooks for their own repo) can forge a "success" status against a commit SHA that also exists in a different stack they do not control, potentially satisfying that other stack's CI-gate for deploy eligibility and enabling an unauthorized deploy in a repository/organization the attacker has no legitimate access to. This matches the "High" bucket (escalation across a repository/authorization boundary) and can reach "Critical" (unauthorized deploy) if the forged status is what gates deployability for the victim stack.

### Likelihood Explanation
Requires the attacker to already be a legitimate, authenticated party for some Shipit-tracked repository/organization (able to trigger real signed `status` webhooks), and requires a shared/colliding commit SHA between their repository and the victim's — realistic for forked/mirrored repositories, shared upstream monorepos tracked as multiple Shipit stacks, or repositories that were renamed/transferred while old commit rows persist. This is a plausible but not universally trivial precondition, consistent with the "Low but concerning" likelihood pattern of the source report.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to the repository named in the current payload, mirroring `PushHandler`/`CheckSuiteHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)` before matching by SHA, so a status update can never cross into a `Commit` belonging to a different, unauthenticated repository/organization.

### Proof of Concept
1. Attacker owns `attacker-org/repo`, which has the Shipit GitHub App installed with a legitimate `webhook_secret`; a Shipit stack also tracks `victim-org/repo` which happens to contain a commit with SHA `abc123...` (e.g., a shared upstream commit or fork history).
2. Attacker crafts a real GitHub `status` event on `attacker-org/repo` for a commit with the same SHA `abc123...` (achievable by cherry-picking/pushing the identical tree+commit metadata, or exploiting a forked/shared-history repo pair), setting `state: success`.
3. GitHub signs this webhook with `attacker-org`'s `webhook_secret`; `WebhooksController#verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and the signature is valid, so the request passes.
4. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which returns the `Commit` row belonging to `victim-org/repo`'s stack as well, and calls `create_status_from_github!` on it, marking the victim's commit as CI-passing without any check tying the update to the authenticated `attacker-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
