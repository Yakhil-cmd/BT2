### Title
Membership webhook handler binds team membership by `team.id` without validating the authenticating organization, allowing escalation into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The `SolidlyV3AMO.addLiquidity()` bug computes a critical value (`liquidity`) using a scope broader than the actual position it should be bound to (pool-wide state instead of the tick-range position), letting an attacker who controls an unrelated LP position corrupt calculations for a stack they don't own. The analogous binding break in shipit-engine is in the GitHub `membership` webhook flow: the signature that authenticates a webhook is verified against the *organization* derived from the payload, but the handler that mutates authorization state (`Team`/`Membership` records) looks up the target `Team` purely by GitHub's numeric `team.id`, never re-checking that the found team actually belongs to the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` picks which organization's webhook secret to use for HMAC verification straight from the unverified request body: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub organizations, each with its own `app_id`/`webhook_secret`, configured side-by-side under a shared `github:` key, as documented and exercised in tests: [3](#0-2) [4](#0-3) 

Once a webhook is verified against *the org that signed it*, `MembershipHandler#process` mutates global authorization state keyed only by GitHub's numeric team id, and only sets `team.organization` on first creation of the row — it is never re-validated against the org that authenticated the request: [5](#0-4) 

`Shipit.github_teams` (the set of teams that gate access to the entire application) is built by resolving configured `handle`s to real `Team` rows with their true GitHub `github_id`: [6](#0-5) 

And `User#authorized?` grants full application access purely based on `Membership` rows pointing at those team ids: [7](#0-6) 

Because `find_or_create_team!` finds an existing `Team` by `github_id` alone, a `membership` webhook whose signature was validated using *organization A*'s secret can still write a `Membership` row onto a `Team` record whose true `organization` is *organization B* (the org gating `Shipit.github_teams`), and can name an arbitrary `member.login` (auto-vivified via `User.find_or_create_by_login!`) to add to that team: [8](#0-7) 

This is precisely the pattern called out in the rules: "an organization that authenticated versus the repository [here, `Team`] that is written" — the org used to verify the HMAC signature is never re-checked against the org actually being mutated.

### Impact Explanation
If exploited, an actor who only controls a GitHub organization/App installation that is *not* one of the org(s) whose team(s) gate `Shipit.github_teams` can add an arbitrary GitHub login as a member of the authorization-gating `Team` row (by targeting its known/discoverable numeric `github_id`), directly satisfying `User#authorized?` and bypassing the `force_github_authentication` check used across the whole engine (`Shipit::Authentication`). This is an escalation into `Shipit.github_teams` authorization — explicitly listed as a High-severity impact in the rules. [9](#0-8) 

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub organizations (a documented, supported deployment mode), (2) attacker controls at least one of those organizations' GitHub App/webhook secret (their own org, not a privileged Shipit-side credential), and (3) attacker knows/derives the numeric `github_id` of the target authorization `Team` (obtainable via the GitHub API for teams they can observe, or via prior legitimate webhook traffic/logs). No `ApiClient` token, `webhook_secret` of the *victim* org, or Shipit session is required — only possession of a *different* org's own webhook credentials, which is a materially weaker requirement than the excluded categories.

### Recommendation
In `MembershipHandler#find_or_create_team!`, re-verify that the located (or newly created) `Team#organization` matches the organization that authenticated the current webhook request (i.e., the value used in `WebhooksController#verify_signature` to select the signing `GitHubApp`), and reject/no-op the mutation if they differ. More generally, thread the authenticated organization through to every webhook handler and assert it against any payload field used to select records to mutate, rather than trusting payload-derived identifiers (`team.id`, `repository.full_name`, etc.) in isolation from the signature-verified scope.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs: `VictimOrg` (whose team `VictimOrg/developers`, `github_id = 100`, is in `Shipit.github_teams`) and `AttackerOrg` (attacker's own GitHub App/installation, whose `webhook_secret` the attacker knows because they configured it).
2. Attacker computes a valid `X-Hub-Signature` using `AttackerOrg`'s webhook secret over a crafted `membership` payload:
```json
{
  "action": "added",
  "team": { "id": 100, "name": "developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "AttackerOrg" },
  "member": { "login": "attacker-github-login" }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` → `"AttackerOrg"` (no `repository` key in a membership payload), fetches `AttackerOrg`'s `GitHubApp`, and successfully verifies the signature because it was signed with `AttackerOrg`'s known secret.
4. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 100)`, finds the existing `VictimOrg/developers` row (already present because it's in `Shipit.github_teams`), and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
5. `attacker-github-login`'s `Shipit::User#authorized?` now returns `true` (member of a `Shipit.github_teams` team id), granting full access to the Shipit instance without ever authenticating against `VictimOrg`.

**File:** app/models/shipit/webhooks/handlers/membership_handler.rb (L22-43)
```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
