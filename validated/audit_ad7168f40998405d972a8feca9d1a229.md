### Title
Webhook signature is scoped to `repository.owner.login`, but `status` events are applied globally by commit SHA with no repository check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the HMAC signature against using the attacker-influenced field `repository.owner.login` from the JSON body, but `StatusHandler#process` — the code that actually writes state — looks up commits by SHA alone, with no scoping to the organization or repository that was authenticated. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against based on a field taken from the untrusted JSON payload itself: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

So the only thing HMAC-verified is: "this payload was signed with the secret configured for the organization named in `repository.owner.login`." Anyone who legitimately controls a GitHub App/webhook secret for *any* organization onboarded onto this Shipit instance (a normal, unprivileged tenant in a multi-org deployment, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section) can produce a validly-signed payload as long as `repository.owner.login` matches their own org.

The payload is then dispatched to handlers based only on `X-Github-Event`, with no re-check that `repository.owner.login` matches whatever repository/stack the handler subsequently acts on: [3](#0-2) 

Most handlers key their affected `Stack`/`Repository` off `repository.full_name` (a different, independently attacker-controlled field in the same payload), via the shared `Handler#repository_name`/`#stacks` helpers: [4](#0-3) 

For `push`, the impact is limited because `PushHandler` merely triggers `GithubSyncJob`, which re-fetches real commit data from GitHub's API for the resolved stack rather than trusting payload commit content: [5](#0-4) [6](#0-5) 

But `StatusHandler` is much worse: it doesn't even use `repository.full_name`/`repository.owner` to scope its write. It looks up commits **globally by SHA** and directly persists attacker-supplied state/description/context/target_url onto them: [7](#0-6) 

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit.where(sha:)` is not scoped to any stack, repository, or organization — it can match a commit belonging to a completely different organization/repository than the one whose secret was used to sign the request. This is the exact analog to the report's bug class: the field that is cryptographically bound/verified (`repository.owner.login` → webhook secret) is not the same field that determines what gets written (`sha`, unscoped by repository at all).

### Impact Explanation
An attacker who is a legitimate, unprivileged tenant of a shared/multi-org Shipit instance (owns their own GitHub organization/App with its own `webhook_secret`, exactly as documented for "Using Multiple Github Applications") can sign a forged `status` webhook with their own org's secret while setting `sha` to the SHA of a commit belonging to a victim's stack in a *different* organization on the same instance (commit SHAs of public commits/PRs are typically discoverable). Doing so lets the attacker inject a fabricated `success` status for whatever `context` string the victim's `shipit.yml` requires for deployability, directly influencing `Commit#deployable?` (`success? && !blocked?`) gating in the victim's stack: [8](#0-7) 

If the victim stack has continuous delivery or manual deploy relying on that check, this results in an unauthorized deploy being allowed to proceed against attacker-supplied approval state — a cross-tenant integrity break with no access to the victim's credentials, `webhook_secret`, or repository required. This matches the "Critical - unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires the deployment to host multiple GitHub organizations under one Shipit instance (an explicitly documented, supported configuration) and requires the attacker to know a target commit SHA in the victim stack (feasible for public repositories or via any read access to the victim repo's commit history/PRs). Given these conditions, exploitation needs only the attacker's own valid webhook secret — something every onboarded org possesses — with no cross-tenant privilege needed.

### Recommendation
Bind the verified organization to the object actually mutated: derive the acting `Repository`/`Stack` scope from the same field whose signature was checked (`repository.owner.login`/`repository.full_name`), and reject/ignore any handler action (especially `StatusHandler`) whose target `Commit`'s stack/repository does not belong to that verified organization. At minimum, `StatusHandler#process` should scope `Commit.where(sha:)` to commits under stacks whose repository owner matches the authenticated `repository_owner`, mirroring the `stacks`/`repository_name` scoping already used in the base `Handler` class.

### Proof of Concept
1. Attacker operates their own GitHub organization `attacker-org`, with a GitHub App installed and its own `webhook_secret` configured in the shared Shipit instance (legitimate multi-tenant setup).
2. Attacker learns the SHA of a not-yet-deployed commit `<victim_sha>` in `victim-org/victim-repo`, a stack requiring CI context `ci/required`.
3. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<victim_sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/anything" }
}
```
   and `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and verifies successfully because the attacker legitimately owns that secret.
5. `StatusHandler#process` executes `Commit.where(sha: "<victim_sha>")`, finds the victim's commit (unscoped to organization/repository), and calls `create_status_from_github!`, marking it `success` for `ci/required` — potentially unlocking deploy for `victim-org/victim-repo` despite the attacker having no access to that organization.
