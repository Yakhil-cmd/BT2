### Title
Cross-Organization Webhook Forgery via Owner/Full-Name Binding Mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate an inbound webhook against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body itself. However, every event `Handler` (e.g. `PushHandler`, the `PullRequest` handlers, `MembershipHandler`) resolves the actual `Repository`/`Stack`/`Team` to mutate using a *different* field of the same attacker-controlled payload: `repository.full_name` (or `organization.login` for membership events). Because these two fields are never cross-checked, an unprivileged attacker who can produce a webhook accepted for *any* configured GitHub organization can direct its effects at a repository/stack belonging to a *completely different* organization.

### Finding Description
The webhook signature check is: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the JSON payload (`repository.owner.login`, falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` is used only to pick the `GitHubApp` config to verify against: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is unset (`nil`/blank) — a state that is explicitly documented and shipped as a valid configuration in multi-org setups: [4](#0-3) 

Meanwhile, the base `Handler` class and every concrete handler (`PushHandler`, `PullRequest::*Handler`) resolve the repository to act on from the *independent* `repository.full_name` field of the same payload: [5](#0-4) [6](#0-5) 

For the `membership` event, `MembershipHandler` similarly uses `params.organization.login` to find/create a `Team` and modify its membership, independent of whatever organization's secret validated the request: [7](#0-6) 

The `/webhooks` endpoint is mounted without any Shipit authentication concern (`WebhooksController < ActionController::Base`, no session, no `ApiClient` token required): [8](#0-7) 

This is the exact bug class from the external report: the array/field that is verified (`repository.owner.login`, used to pick and validate against a specific org's secret) is not the same array/field that is actually acted upon (`repository.full_name` / `organization.login`, used to select the repository, stack, or team to mutate). The equality that should hold — "the organization whose secret authenticated this request" == "the organization/repository the request is allowed to affect" — is never enforced.

### Impact Explanation
In any Shipit install configured for multiple GitHub organizations (the documented multi-org schema in `config/secrets.development.shopify.yml`/`docs/setup.md`) where at least one organization has no `webhook_secret` configured (an explicitly supported, documented state), an unauthenticated, unprivileged attacker can:
- Send a forged `push` webhook with `repository.owner.login` set to the org with no secret and `repository.full_name` set to a stack under a secured organization, causing `Stack#sync_github` to run with an attacker-chosen `expected_head_sha`.
- Send a forged `membership` webhook with `organization.login` pointing at the secret-less org while granting/revoking membership on a `Team` tied to `Shipit.github_teams` for a different, security-critical organization, directly affecting `Shipit::Authentication#force_github_authentication`'s authorization check.
- Manipulate PR-driven review-stack provisioning/archival (`PullRequest::OpenedHandler`, `ClosedHandler`, etc.) for repositories under organizations whose webhook secret the attacker never possessed.

This crosses the "organization authenticated vs. repository/organization acted upon" trust boundary and can escalate into unauthorized stack manipulation and `Shipit.github_teams` authorization tampering — meeting the High-impact bar (escalation into `Shipit.github_teams` authorization / unauthorized stack state changes) without any credential, session, or webhook secret being required for the target organization.

### Likelihood Explanation
Likelihood is limited to deployments that (a) configure multiple GitHub organizations, and (b) leave at least one of them with no `webhook_secret` — both of which are officially documented and shipped example configurations, not misconfigurations flagged anywhere in the codebase or docs. No credential, session, or prior access is needed by the attacker for the secret-less organization; only knowledge of the target stack's `full_name` is required, which is public.

### Recommendation
Bind the organization used for signature verification to the organization actually mutated by each handler: derive/validate that `repository.full_name`'s owner segment (or `organization.login` for org-scoped events) matches the `repository_owner` that was used to select and verify the webhook secret, and reject the request if they differ. Additionally, consider requiring a non-blank `webhook_secret` for every configured organization in production, or independently deriving the target repository's own configured secret (from the `Repository`/`Stack` record) rather than trusting an attacker-suppliable `owner.login` field for secret selection.

### Proof of Concept
Given a Shipit config:
```yaml
production:
  github:
    open-org:            # no webhook_secret configured
      app_id: ...
      installation_id: ...
    secured-org:          # webhook_secret: "s3cr3t"
      webhook_secret: s3cr3t
      app_id: ...
      installation_id: ...
```
An attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "secured-org/critical-repo",
    "owner": { "login": "open-org" }
  }
}
```
`repository_owner` resolves to `open-org`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no `webhook_secret`), so `verify_signature` passes with no `X-Hub-Signature` header at all. `Shipit::Webhooks.for_event('push')` then invokes `PushHandler`, which resolves stacks via `payload.dig('repository','full_name')` = `secured-org/critical-repo`, triggering `stack.sync_github(expected_head_sha: 'deadbeef...')` against a repository under `secured-org`, whose webhook secret the attacker never had.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
