### Title
Cross-organization forged CI status via webhook signature/target mismatch enables unauthorized merge - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the request signature against using `repository_owner` (derived from the payload's `repository.owner.login`), but `StatusHandler#process` writes a commit status by looking up `Commit.where(sha: params.sha)` globally, with no scoping back to the organization/repository that was actually authenticated. This breaks the binding "organization authenticated == repository/commit written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config with `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that org's `webhook_secret`: [1](#0-0) 

`repository_owner` is read straight from the untrusted JSON body: [2](#0-1) 

Once the signature is accepted, the controller dispatches to handlers using only the raw parsed payload — the org used for verification is never passed along or re-checked: [3](#0-2) 

Most handlers scope their writes through `Repository.from_github_repo_name(repository_name)` (which does use `payload.dig('repository','full_name')`, itself attacker-controlled but at least consistent inside a single handler): [4](#0-3) 

However, `StatusHandler` does not use that scoping at all — it looks up commits **globally by sha**, independent of any repository or organization: [5](#0-4) 

`Commit#create_status_from_github!` then directly creates a `Status` record and, if the resulting state becomes `pending` or `success`, calls `stack.schedule_merges`, which drives the merge-queue evaluation for that commit's actual stack: [6](#0-5) [7](#0-6) 

Shipit explicitly supports hosting multiple, independently-controlled GitHub organizations off a single instance, each with its own GitHub App and its own `webhook_secret`: [8](#0-7) 

Because signature verification is keyed only on `repository.owner.login` from the payload, and `StatusHandler` never checks that field before writing, an admin of **any one** of the onboarded organizations (who legitimately knows their own org's `webhook_secret`) can send a `status` event whose `repository.owner.login` is their own org (so it authenticates), while `sha` names a commit belonging to a completely different organization's stack. The forged status is written to that unrelated commit regardless of organizational boundary.

The equality broken is:
`organization that authenticated (repository.owner.login used to pick webhook_secret)` ≠ `commit/repository actually written (Commit.where(sha:) with no owner check)`.

### Impact Explanation
A forged `success` status on a victim stack's pull-request head commit can satisfy `MergeRequest#any_status_checks_missing?/any_status_checks_failed?`, which are evaluated via `StatusChecker`/`stack.cached_deploy_spec.required_statuses` before `reject_unless_mergeable!` and `merge!` run: [9](#0-8) [10](#0-9) 

If required CI statuses are faked as passing, Shipit's merge queue will call `stack.github_api.merge_pull_request(...)`, i.e. perform an **unauthorized merge** into a repository/organization the attacker does not control — matching the Critical "unauthorized deploy, rollback, or merge" impact category. It can also make a blocked commit `deployable?` (since `deployable?` depends on `success?`/`blocked?` derived from status), potentially triggering continuous deployment.

### Likelihood Explanation
Requires a Shipit instance configured for multiple organizations (a documented, supported configuration) where the attacker legitimately administers one org's GitHub App (and thus knows that org's `webhook_secret`), and knows/guesses the target commit's SHA (visible on any public PR, or leaked via other Shipit endpoints). No Shipit account, `ApiClient` token, or GitHub token for the victim org is needed — only the ability to POST a crafted, correctly-signed `status` webhook. This is a realistic likelihood in any multi-tenant Shipit deployment.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already scope via `Handler#stacks`), restrict the commit lookup to the stack(s)/repository actually associated with the authenticated organization, e.g. filter `Commit.where(sha: params.sha)` through `stacks` (which is derived from `payload.dig('repository','full_name')`) instead of an unscoped, global lookup. Additionally, have `WebhooksController#verify_signature` pass the verified organization down to handlers, and have every handler assert that the repository/organization referenced in the payload used for its writes matches the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`, e.g. `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with an installed GitHub App, per the documented multi-org setup.
2. As an admin of `attacker-org`'s GitHub App, obtain/know `S_A` (you configured it).
3. Identify a commit SHA belonging to an open pull request in a `victim-org` stack tracked by the same Shipit instance (e.g., from the public PR page).
4. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim PR head sha>",
  "state": "success",
  "context": "<required ci context for victim stack>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
signed with `HMAC-SHA1(S_A, body)` in `X-Hub-Signature`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies successfully against `S_A`.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and finds the victim commit (unscoped by org), creating a forged `success` status on it and triggering `stack.schedule_merges`, which can result in `MergeRequest#merge!` merging the victim's pull request without their authorization.

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
