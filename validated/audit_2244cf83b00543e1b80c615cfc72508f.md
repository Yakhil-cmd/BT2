### Title
Pull request labels can override any deploy environment variable (including `GIT_ASKPASS`) via `ReviewStack#env` label merge - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every PR label name (upcased, value `"true"`) into the stack's environment hash with no reserved-key filtering, and this hash is merged into `TaskCommands#env` right after `base_env`/`Commands#env` is computed. A PR label whose upcased form is `GIT_ASKPASS` (or `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `PATH`, etc.) silently clobbers the corresponding value that `Commands#base_env` set, because nothing downstream restores those specific reserved keys.

### Finding Description
The binding that must hold is: `TaskCommands#env['GIT_ASKPASS'] == Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s` (the path `Commands#base_env` sets at [1](#0-0) ) whenever `Shipit.use_git_askpass?` is true.

The code path:
1. `Commands#env` returns `base_env`, which sets `env['GIT_ASKPASS']` to the real git-askpass script path when `Shipit.use_git_askpass?` [2](#0-1) .
2. `TaskCommands#env` calls `super` (that `base_env`) and then `.merge(@stack.env)` before any of the later, fixed-key merges [3](#0-2) .
3. For a `ReviewStack`, `@stack.env` is `ReviewStack#env`, which merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` on top of the base stack env [4](#0-3) . There is no allow-list or reserved-key check — any label name is accepted verbatim.
4. `pull_request.labels` is populated directly from the webhook payload with no filtering: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` in `LabelCapturingHandler#capture_labels` [5](#0-4) , triggered on `opened`, `labeled`, `unlabeled`, and `reopened` events [6](#0-5) .
5. Because `.merge(@stack.env)` happens at line 35 of `task_commands.rb` and none of the subsequent merges (`SHIPIT_USER`, `EMAIL`, …, `deploy_spec.machine_env`, `@task.env`) touch `GIT_ASKPASS`, a label `GIT_ASKPASS` permanently overwrites the path with the literal string `"true"` in the final env hash passed to `Command#start`'s `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` [7](#0-6) .
6. Existing guards (`verify_signature`, `ExplicitParameters` schema on `LabelCapturingHandler`, model validations) only ensure the webhook payload is well-formed and signed by the *owning* org's secret — none of them restrict label content or reserve environment-variable names, so they do not prevent this collision.

The test at [8](#0-7)  already demonstrates that arbitrary label names (`"wip"`, `"bug"`) become uppercased env keys with value `"true"`, confirming the exact merge mechanism used for the exploit (`"GIT_ASKPASS"` would behave identically).

### Impact Explanation
When `Shipit.use_git_askpass?` is enabled, this lets a PR label author force `GIT_ASKPASS=true` for any git operation over HTTPS run for that review stack's deploy (`git fetch`, `git clone`, `checkout`, deploy steps). The `true` binary exits with a fixed output and no credential prompt handling, meaning the `git-askpass` script that normally supplies `GITHUB_USER`/`GITHUB_TOKEN` to git is bypassed. Depending on git's fallback behavior, this can cause authentication to fail (denial of a legitimate deploy) or, in some git/credential-helper configurations, cause git to fall back to other credential sources/prompts than the sandboxed askpass script — undermining the intended controlled credential injection design. Beyond `GIT_ASKPASS`, the same technique lets a label overwrite `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `PATH`, `HOME`, `BUNDLE_PATH`, `TASK_ID`, `GIT_COMMITTER_NAME/EMAIL`, etc., since no key is protected. This is scoped to the attacker's own review-stack (their own fork/PR), so blast radius is confined to the tenant/stack tied to that PR, not cross-tenant; the severity is best characterized as environment/credential-handling integrity issue for that stack's deploy commands rather than cross-repository compromise.

### Likelihood Explanation
Preconditions: `Shipit.use_git_askpass?` must be true (config-dependent), review stacks must be enabled for the repository, and the attacker's PR must carry the label at "opened"/"labeled" time. The security-audit's stated threat model explicitly grants "label their own PR" as an attacker capability, in which case exploitation is trivial and repeatable per PR (add/remove the label to toggle the collision at will, or apply similar collisions against other reserved env keys). No secrets are required; only a labelable PR against a repository with review stacks + git-askpass enabled.

### Recommendation
In `ReviewStack#env` (or a shared spot before it's merged into `TaskCommands#env`), reject or namespace label-derived environment keys that collide with reserved/base environment variable names (e.g., `GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `PATH`, `HOME`, `SHIPIT_USER`, `TASK_ID`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`, `EMAIL`, `IGNORED_SAFETIES`). Alternatively, re-apply `base_env`'s critical keys (`GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`) as the last merge in `TaskCommands#env`/`Command#start` so they cannot be shadowed by any downstream (label, `machine_env`, or `@task.env`) source, or prefix label-derived keys (e.g. `LABEL_<NAME>`) instead of using the raw uppercased label name.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing test file)
test "#env: a GIT_ASKPASS-named PR label overrides the base askpass path" do
  Shipit.stubs(:use_git_askpass?).returns(true)
  expected_askpass_path = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s

  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["GIT_ASKPASS"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  assert_equal expected_askpass_path, Shipit::Commands.for(stack).send(:base_env)['GIT_ASKPASS']
  refute_equal expected_askpass_path, env['GIT_ASKPASS']
  assert_equal "true", env['GIT_ASKPASS']
end
```
This confirms the binding `TaskCommands#env['GIT_ASKPASS'] == base_env['GIT_ASKPASS']` is broken solely by attacker-controlled PR label content.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env

    end
