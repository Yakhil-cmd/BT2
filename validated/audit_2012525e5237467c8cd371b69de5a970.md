### Title
AA batch payment response bounces (and loses all outputs) entirely if a single recipient address is invalid — ([File: aa_composer.js])

### Summary
Across V3's `SpokePool.sol` refund leaf pushes tokens to every recipient in a batch in a single transaction; if the token blacklists one recipient, the ERC20 transfer to that address reverts, and *all* recipients in that leaf lose their refund, even though most addresses were perfectly valid. The same all-or-nothing "batched push" failure mode exists in ocore's Autonomous Agent (AA) response engine: when an AA sends a single response unit containing a `payment` message with multiple outputs, the entire message (and the entire response, including unrelated state changes and other payment messages) is validated and constructed as one atomic operation. If even one output address in that batch is malformed/invalid, the whole trigger bounces via `bounce(err)` and none of the outputs — valid or invalid — are paid.

### Finding Description
When `handleTrigger()` builds an AA's response unit, all `payment` messages produced by the AA template are processed together in `sendUnit()`. Every output in every payment message is validated as a batch: [1](#0-0) 

```
if (!Array.isArray(payload.outputs))
    return bounce("outputs must be array");
if (!payload.outputs.every(o => ValidationUtils.isValidAddress(o.address)))
    return bounce("invalid addresses in outputs");
```

Because `.every()` is used, a single bad address (`o.address`) anywhere among *all* outputs in the message causes `bounce(err)` to be invoked for the whole response. `bounce()` rolls back all the AA's balance/state changes for the trigger (via `ROLLBACK TO SAVEPOINT initial_balances`) and produces a bounce unit instead of the intended payment unit: [2](#0-1) 

This means every other, perfectly legitimate output address that was supposed to be paid in the same trigger response (e.g., in a multi-recipient distribution, dividend/ICO-milestone payout, or vesting AA that iterates over a list of addresses derived from `trigger.data` or previous state) receives nothing, and the trigger only gets a bounce message back (with the trigger amount minus bounce fees returned to the trigger's original sender), not the payout the AA was supposed to make. This is functionally identical to the reported Across bug: pushing funds to a batch of addresses in one atomic operation such that one bad/blacklisted/malformed address blocks payment to everyone else in the batch.

Sample AA scripts in the repo confirm the common pattern of building multi-output payment messages driven by external/trigger-supplied data (e.g., `test/samples/sending_prepared_objects_through_trigger_data.oscript` builds outputs directly from `trigger.data.output`/`trigger.data.payment`), which is exactly the vector by which a malformed address can be introduced into a batch by an unprivileged trigger sender. [3](#0-2) 

### Impact Explanation
An AA that pays out to multiple addresses in one payment message (common pattern for airdrops, dividend distribution, ICO refunds/milestones, DEX/market-maker payouts to multiple LPs, etc.) can have its entire distribution blocked by a single bad output address supplied via trigger data or computed from stored/external addresses. Legitimate recipients in the same batch are denied their funds for that trigger execution (the AA keeps/holds the funds instead, or they are returned only to the triggering address, not the intended recipients), representing AA fund freezing/misdirection for uninvolved third parties. If the offending address is a stored state variable (e.g., previously registered by a user), this can also become a persistent denial-of-service: every subsequent AA invocation that includes that address in a batched payment will keep bouncing, freezing funds for all other legitimate participants in that batch indefinitely.

### Likelihood Explanation
Any unprivileged party who can post a trigger unit that the AA evaluates (e.g., contributing to a fund, registering an address, or the AA merely iterating a state-stored list of participant addresses) can supply/queue a payment output that is not a syntactically valid address (a typo, wrong network address, or address that fails ocore's `isValidAddress` chash/length checks). Whether triggered accidentally or intentionally by a malicious participant seeking to disrupt payouts to others, no special privileges are required, and the AA logic does not need to be "buggy" beyond using multiple outputs in one payment message driven by potentially externally-influenced data — a widespread and encouraged pattern in oscript AA design (batched payouts save fees).

### Recommendation
- Validate each recipient address for a batched payment individually before merging it into a shared payment message; when an individual output fails validation, skip/exclude only that output (and optionally emit a `response`/state record noting the skipped payout) rather than failing the entire message via `Array.prototype.every`.
- Where an AA template's logic distributes funds to externally-supplied or state-stored addresses in bulk, encourage/enforce (via `aa_validation.js` guidance or oscript best practices) a pull-based claim pattern instead of push-based batched payment outputs, mirroring the "pull over push" fix direction Risk Labs applied to Across V3.
- Consider making `sendUnit()`'s output-address validation per-output (drop bad outputs and log them) rather than short-circuiting the whole trigger response with `bounce()`, at least for the "invalid addresses in outputs" case at `aa_composer.js:1268-1269`.

### Proof of Concept
1. Deploy an AA whose response messages array contains a single `payment` app message with outputs built from a list including at least one attacker/user-supplied address that is not `ValidationUtils.isValidAddress`-compliant (e.g., a mistyped or malformed address string embedded via `trigger.data`, similar to `test/samples/sending_prepared_objects_through_trigger_data.oscript`).
2. Trigger the AA so its evaluated `messages` produce a payment message with several outputs, one of which has the malformed address.
3. In `sendUnit()`, the check `payload.outputs.every(o => ValidationUtils.isValidAddress(o.address))` at `aa_composer.js:1268` fails for the whole message, calling `bounce("invalid addresses in outputs")`.
4. Observe that `bounce()` rolls back to the initial-balances savepoint (`aa_composer.js:1780-1783`) and produces a bounce response instead of the payment — none of the other, valid-address outputs in the batch receive their intended funds for that trigger. [4](#0-3) [2](#0-1)
