## Analysis

I traced the bug class from the samlify report — unescaped/undelimited concatenation of attacker-controlled fields into a structure that is later hashed and trusted for integrity/authenticity — to `object_hash.js` and its callers. The core canonicalization function `getSourceString` in `string_utils.js` explicitly guards against this by rejecting any string or key containing the `\x00` join separator before concatenating, which prevents ambiguous boundaries between fields: [1](#0-0) 

However, `prosaic_contract.js` bypasses this safe canonicalization entirely and builds the contract commitment hash by raw string concatenation with **no delimiter at all** between the attacker-controlled `title` and `text` fields: [2](#0-1) 

Notably, `arbiter_contract.js` already contains a fix for what looks like the exact same class of issue — it defines a `DELIMITER = "[|#|]"` constant and a `NEW_HASH_DATE` migration marker, indicating maintainers previously recognized and patched an equivalent undelimited-concatenation hash weakness for arbitrated contracts: [3](#0-2) 

But `prosaic_contract.js`'s `getHash`/`getHashV1` were never migrated to use a delimiter, leaving the same weakness live for prosaic (non-arbitrated) contracts.

### Title
Undelimited Field Concatenation in Prosaic Contract Hash Allows Content Substitution After Commitment - (File: prosaic_contract.js)

### Summary
`prosaic_contract.js`'s `getHash()` and `getHashV1()` compute a peer-shared contract commitment hash as `sha256(title + text + creation_date)` with no separator between `title` and `text`. Because there is no delimiter, two different `(title, text)` pairs can produce an identical concatenated string and therefore an identical hash (e.g. `title="Pay A"`, `text="mount:100"` vs `title="Pay Amount"`, `text=":100"`). This is the same bug class as the samlify report: values are inserted into a structure without proper boundary-preserving encoding, so an attacker can make two semantically different payloads collide into the same "signed"/committed value.

### Finding Description
`createAndSend()` computes `objContract.hash = getHash(objContract)` (via the analogous call pattern in `arbiter_contract.js`, and `getHashV1`/`getHash` in `prosaic_contract.js`) purely from concatenated `title`+`text`+`creation_date` strings, with no length-prefixing or separator: [2](#0-1) . This hash is then used as the durable identifier/commitment for the contract: it is stored as the primary lookup key (`getByHash`), sent to the peer device as `prosaic_contract_offer`/`prosaic_contract_response`, and — critically — verified against on-chain data when a signing unit is later observed: `handleReceivedSigningUnit()` accepts a unit as proof of signing the contract solely if `payload.contract_text_hash === contract.hash` [4](#0-3) . Because the hash function does not disambiguate the title/text boundary, a counterparty (an unprivileged AA/contract counterparty, in-scope per the rules) can present one `(title, text)` pair for display/agreement and later substitute another colliding `(title, text)` pair that hashes identically, while both `getHash`/`getHashV1` and the on-chain `contract_text_hash` field remain unchanged and appear valid.

### Impact Explanation
The prosaic-contract hash is the sole cryptographic anchor tying a human-readable agreement to an on-chain commitment (`payload.contract_text_hash`) and to peer-to-peer confirmation messages. A malicious counterparty controlling `title`/`text` can construct a colliding second contract body and later claim (or get accepted by tooling/other party's records) that the differently-worded contract is the one actually committed to, since the stored/verified `hash` is identical. In flows that gate fund release or dispute resolution on the recorded contract hash (this contract type shares the funding/charge mechanics used by `arbiter_contract.js`, which already treats this as security-relevant enough to add a `DELIMITER`), this can be leveraged to dispute or misrepresent agreed terms after signature/commitment, undermining the integrity guarantee the hash is meant to provide.

### Likelihood Explanation
Exploitation only requires one of the two contracting parties (a normal wallet user acting as `peer_device_address` counterparty) to choose `title`/`text` values with knowledge of this weakness — no special privileges, network position, or third-party compromise needed. Constructing a colliding pair is trivial (move any suffix of `title` into the prefix of `text`, or vice versa).

### Recommendation
Apply the same fix already used in `arbiter_contract.js` (its `DELIMITER = "[|#|]"`) to `prosaic_contract.js`: insert an unambiguous, reserved delimiter (or field-length-prefixing, or use `string_utils.getSourceString`/`getJsonSourceString`, which already guards against separator-injection) between `title`, `text`, and `creation_date` before hashing in both `getHash()` and `getHashV1()`, and provide a migration path (analogous to `NEW_HASH_DATE`) for contracts hashed under the old, ambiguous scheme.

### Proof of Concept
```js
const prosaic_contract = require('./prosaic_contract');
const c1 = { title: 'Pay A', text: 'mount:100', creation_date: '2026-01-01 00:00:00' };
const c2 = { title: 'Pay Amount', text: ':100', creation_date: '2026-01-01 00:00:00' };
console.log(prosaic_contract.getHash(c1) === prosaic_contract.getHash(c2)); // true — collision despite different title/text
```

**Note on completeness:** I was not able to fully trace every call site of `getHash`/`getHashV1` in `wallet.js` (23 matches for related terms) within the remaining tool budget, so I cannot confirm every downstream consequence (e.g., exact arbiter/escrow fund-release logic reachable from a prosaic contract vs. arbiter contract). The finding is grounded in the concrete code shown above; a full audit of all `wallet.js` prosaic/arbiter contract handling would be needed to enumerate every exploitable downstream effect.
