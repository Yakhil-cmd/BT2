This confirms the full attack chain: `StatusHandler#process` finds commits **globally by SHA only** (`Commit.where(sha: params.sha)`), with no scoping to the repository/organization used for signature verification, and injects a fabricated CI status via `commit.create_status_from_github!(params)`, which triggers `ProcessMergeRequestsJob` on success/pending transitions [1](#0-0) [2](#0-1) .

### Title
Webhook signature is verified against an attacker-chosen organization while the event is applied to any repository/commit referenced in the payload, enabling forged CI status / unauthorized ship - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) is used to validate the inbound signature based on `repository_owner`, a value read straight out of the unauthenticated JSON body. The event handlers that subsequently execute the webhook (e.g. `StatusHandler`, `PushHandler`) do not re-check that this same organization/owner matches the repository or commit they act on. This breaks the intended binding "organization whose secret authenticated the request == repository/commit that gets written."

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) . This field is taken directly from the attacker-supplied JSON payload before any signature has been validated.

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: `return true unless webhook_secret` [4](#0-3) . Shipit explicitly supports multi-organization deployments where each org has its own, individually optional, `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`) [5](#0-4) [6](#0-5) .

After the signature gate, `create` dispatches the *entire, attacker-controlled* payload to handlers using data that has no relation to `repository_owner`:
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global** lookup by SHA across the whole Shipit instance, with no organization or repository scoping at all [7](#0-6) .
- `PushHandler`/`Handler#stacks` resolve the target repository via `payload.dig('repository', 'full_name')` [8](#0-7) , a field independent from `repository.owner.login` used for signing.

Because `full_name`/`sha` and `repository.owner.login` are two unrelated fields inside one JSON body that the attacker fully controls, nothing forces them to refer to the same repository. An attacker who knows (or registers) any organization configured in Shipit with a blank `webhook_secret` can set `repository.owner.login` to that org to bypass the signature check unconditionally, while pointing `repository.full_name`/`sha` at a completely different, secret-protected organization's stack/commit.

### Impact Explanation
This yields an unauthenticated write into another tenant's deploy pipeline: injecting a forged `success` status via `StatusHandler` for an arbitrary commit SHA drives `Commit#create_status_from_github!` → `Status#schedule_continuous_delivery`/`enable_ci_on_stack`, which enqueues `ProcessMergeRequestsJob` [9](#0-8)  and can satisfy CI/deployability gating used by the merge queue and continuous deployment, leading to an unauthorized merge or deploy of a commit the attacker never had legitimate CI results for. This matches the required High/Critical impact category of "an unauthorized deploy, rollback or merge" via escalation across a trust boundary that the signature check was supposed to enforce.

### Likelihood Explanation
Exploitability requires only that the Shipit multi-org configuration include at least one organization with no `webhook_secret` set (an explicitly documented, supported, optional configuration) and that the attacker know/guess that organization's login and the target victim's commit SHA/repository full name (both discoverable from public GitHub activity). No GitHub credentials, Shipit session, or API token are required — only an HTTP POST to `/webhooks`.

### Recommendation
After resolving `repository_owner`/`github_app` and verifying the signature, re-derive the organization from every field the handlers will actually act on (`repository.full_name`, and any `sha`/commit lookups) and reject the request if they don't match the organization whose secret validated the signature. Additionally, `StatusHandler` should scope its `Commit.where(sha:)` lookup to commits belonging to the verified organization/repository rather than searching globally, and `verify_webhook_signature` should not silently accept unsigned payloads for organizations that omit `webhook_secret` when other organizations are configured with one, or should require the accompanying `X-Hub-Signature` matches the actual repository being written to, not just the `repository.owner.login` field.

### Proof of Concept
1. Shipit is configured with `github: { victim-org: { webhook_secret: <secret> }, empty-org: { webhook_secret: nil } }` (per `docs/setup.md`'s multi-org schema).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, with body:
```json
{
  "repository": { "owner": { "login": "empty-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha needing green CI>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "empty-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — request passes with a 200/`head(:ok)`.
4. `StatusHandler.call` runs `Commit.where(sha: params.sha)` and finds the victim's commit (global lookup, no org check), creating a forged `success` status, potentially enabling `victim-org/victim-repo`'s merge queue/deploy gating to treat the commit as CI-green.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
