### Title
Webhook signature verification is keyed by an attacker-controlled `repository.owner.login` while event handlers act on a separate, independently attacker-controlled `repository.full_name` — allowing forged GitHub events for any onboarded stack via any tenant with no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which tenant's HMAC secret to check against using `repository_owner`, a field read straight out of the unauthenticated request body, and only *then* dispatches the same body to handlers that resolve the target stack from a *different* body field, `repository.full_name`. Nothing ties these two fields together, so they don't have to refer to the same repository. Any Shipit deployment that hosts more than one GitHub organization/app config, where at least one configured organization has no `webhook_secret` (explicitly documented as "optional"), lets an attacker "authenticate" as that unprotected organization while making the payload act on a repository belonging to a fully-protected organization.

### Finding Description
`verify_signature` derives the organization used for signature verification purely from the JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository','owner','login')` (falling back to `organization.login`). That value picks the `GitHubApp` instance whose `webhook_secret` is used to validate `X-Hub-Signature`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank (`return true unless webhook_secret`) — a state the project's own setup docs describe as a supported, "optional" configuration: [4](#0-3) 

Once `verify_signature` passes, `create` dispatches the *entire same raw body* to the registered handler for the event: [5](#0-4) 

But every handler resolves the target repository/stack from a completely different JSON key, `repository.full_name`, via `Repository.from_github_repo_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

Because the raw POST body is attacker-supplied and unauthenticated at this stage, `repository.owner.login` (used to select the verification secret) and `repository.full_name` (used to select the actually-acted-upon stack) are two independent, uncorrelated strings — the controller never checks that `full_name` starts with `repository_owner`. This is exactly the binding the report's bug class targets: "an organization that authenticated versus the repository that is written." A field (`repository.full_name`) that drives real state changes (syncing commits, closing/merging PRs, updating commit statuses, archiving/unarchiving review stacks) is never covered by, or reconciled with, the field that the signature check actually authenticates.

### Impact Explanation
Any organization onboarded into a multi-tenant Shipit install with no `webhook_secret` configured becomes a skeleton key for forging authenticated-looking webhooks against *every other organization's repositories* also hosted on the same instance. By POSTing to `/webhooks` with `repository.owner.login` set to the secret-less org and `repository.full_name` set to `victim-org/victim-repo`, an attacker can:
- Trigger `PushHandler` → `stack.sync_github` on a victim stack, ingesting attacker-chosen SHAs into commit history tracking (`GithubSyncJob`), [8](#0-7) 
- Trigger `PullRequest::ClosedHandler`/`ReopenedHandler`/`LabeledHandler` to archive/unarchive victim review stacks, [9](#0-8) 
- Forge `status` events to fabricate commit statuses that feed the merge queue's mergeability checks, potentially enabling an unauthorized merge via `ProcessMergeRequestsJob`. [10](#0-9) 

This crosses the "unauthorized deploy/rollback/merge" and "escalation into authorization scoping" impact bar since it lets an attacker spoof state-changing GitHub events for repositories they have no access to, using only knowledge that *some* tenant on the instance omitted a webhook secret.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: it requires the Shipit operator to run a multi-tenant instance (multiple `Shipit.github` organizations configured) where at least one has no `webhook_secret`. The project's own documentation frames `webhook_secret` as *optional*, and the shipped `config/secrets.development.shopify.yml` template leaves it `nil` by default, so this is a realistic, encouraged-by-defaults misconfiguration rather than a purely theoretical one — same class of "confirmed but currently low probability" acknowledged for the referenced Gravity Bridge finding. The root cause, however — the complete lack of binding between the field used for authentication and the field used for authorization/target-selection — is a genuine code defect independent of whether any given deployment currently has a secret-less org.

### Recommendation
Enforce that the organization used to select the signing secret and the organization embedded in `repository.full_name` (and `organization.login` for org-scoped events) are the same value before dispatching to handlers, e.g., re-derive `repository_owner` from the same field handlers use, or explicitly assert `repository.full_name.split('/').first == repository_owner`. Additionally, treat a blank `webhook_secret` as "require no signature only for events scoped to that organization," not as a blanket bypass that can be invoked through payload fields the attacker fully controls.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (has `webhook_secret` set) and `test-org` (no `webhook_secret`, matching the documented "optional" setup and the shipped dev secrets template).
2. Attacker sends, without any valid GitHub signature:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-already-present-upstream>",
  "repository": {
    "owner": { "login": "test-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` computes `repository_owner = "test-org"`, loads `Shipit.github(organization: "test-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature`. [3](#0-2) 
4. `create` runs `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github` on the victim stack that belongs to the fully-secured `victim-org`. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
