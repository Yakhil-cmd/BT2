### Title
Stale controller delegate regains account authority after NFT ownership round-trip - (File: contracts/controller/src/storage/account.rs)

### Summary
Controller account delegates are stored as a single `DelegateGrant` stamped with the granting owner rather than being permanently invalidated when the position NFT changes hands. [1](#0-0)  A transfer makes the old grant inactive because `get_delegates` filters by the current NFT owner, but the grant remains in persistent storage and becomes active again if that original owner later regains the same NFT. [1](#0-0)  The stale delegate can then satisfy the shared owner-or-delegate authorization check and perform owner-level account operations without fresh authorization from the returning owner. [2](#0-1) 

### Finding Description
`DelegateGrant` contains only `granted_by` and `delegates`; it has no ownership generation, expiry, revocation epoch, or tombstone recording that the NFT ever left the granting owner. [3](#0-2)  `get_delegates` reads that entry and returns the delegate list whenever `granted_by == current_owner`, but leaves the entry unchanged when ownership differs. [1](#0-0) 

The only cleanup path for a mismatched grant is `remove_delegate`, which deletes the entry when the grant's `granted_by` differs from the caller-resolved current owner. [4](#0-3)  Calling that function requires the caller to authenticate and currently own the account NFT, so removal depends on the intermediate owner noticing and explicitly purging an invisible stale grant. [5](#0-4) 

Because the NFT token ID is the controller account ID, transferring the NFT transfers control of the same account rather than creating a new account ID. [6](#0-5)  If account `A` grants delegate `D`, then transfers NFT `A` to `B`, and `A` later receives NFT `A` back, the persisted `DelegateGrant { granted_by: A, delegates: [D] }` again matches the current owner and `D` is treated as an active delegate. [1](#0-0) 

### Impact Explanation
Once the NFT returns to the original owner, the stale delegate again passes `require_owner_or_delegate` without any new signature or delegation transaction from that owner. [2](#0-1)  A malicious delegate can then use owner/delegate-gated controller operations on the returned account, with `caller` set to the stale delegate and `account_id` set to the returned NFT/account ID; the strongest impact is withdrawal or borrowing against the victim's collateral through `withdraw`/`borrow`, resulting in theft or encumbrance of the victim's funds. [7](#0-6) 

The loss is not bounded by the delegation duration because `DelegateGrant` has no expiry field and survives ownership transitions in persistent storage. [3](#0-2) 

### Likelihood Explanation
The attacker must first be registered as an active position manager and be delegated by the original owner, which requires the owner's authorization. [8](#0-7)  The exploit also requires an ownership round-trip on the same NFT while the intermediate owner never calls `remove_delegate` to purge the stale entry. [4](#0-3) 

Those preconditions are plausible for accounts temporarily moved between wallets, custody arrangements, marketplaces, or contracts and later returned to the original address, especially because the stale grant is not visible as an active grant while another owner holds the NFT. [1](#0-0)  After the round-trip, a single delegate transaction can trigger the unauthorized account action. [2](#0-1) 

### Recommendation
Permanently invalidate controller delegation grants on the first ownership change, rather than merely filtering them by the current owner. [1](#0-0)  Concretely, add an ownership epoch or transfer hook that clears `ControllerKey::Delegates(account_id)` whenever the NFT owner changes, or record an irrevocable tombstone for the prior owner so the same `granted_by` value cannot reactivate after an ownership round-trip. [9](#0-8)  At minimum, purge mismatched grants during every account-owner resolution path instead of only when the new owner explicitly calls `remove_delegate`. [4](#0-3) 

### Proof of Concept
1. `A` owns position NFT/account ID `X` and calls `controller::add_delegate` with `caller=A`, `account_id=X`, and `delegate=D` while `D` is an active manager; this stores `DelegateGrant { granted_by: A, delegates: [D] }` under `Delegates(X)`. [10](#0-9) [11](#0-10) 
2. `A` calls `position-nft::transfer` with `from=A`, `to=B`, and `token_id=X`; the controller delegate entry remains stored, but `get_delegates(X, B)` returns an empty list because `granted_by` is still `A`. [6](#0-5) [1](#0-0) 
3. `B` does not call `remove_delegate`, so the mismatched grant is not deleted. [4](#0-3) 
4. `B` transfers NFT `X` back to `A`; `get_delegates(X, A)` again returns `[D]` because the stale grant still has `granted_by=A`. [1](#0-0) 
5. `D` submits a delegate-gated controller action such as `borrow` or `withdraw` with `caller=D`, `account_id=X`, and a valid asset/amount drawn from the returned account; `is_owner_or_delegate` accepts `D` without fresh authorization from `A`. [2](#0-1)

/// Returns grants stamped by `owner`, or an empty list. Ownership changes
/// invalidate a previous owner's grants without deleting them.
pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
        .filter(|grant| grant.granted_by == *owner)
        .map(|grant| grant.delegates)
        .unwrap_or_else(|| Vec::new(env))
```

/// Adds a delegate, enforcing `MAX_DELEGATES`; returns false for duplicates.
/// Overwrites stale grants with a list stamped by the current owner.
pub(crate) fn add_delegate(
    env: &Env,
    account_id: u64,
    owner: &Address,
    delegate: &Address,
) -> bool {
    let mut delegates = get_delegates(env, account_id, owner);
    if delegates.contains(delegate) {
        return false;
    }
    assert_with_error!(
        env,
        delegates.len() < MAX_DELEGATES,
        GenericError::RegistryCapReached
    );
    delegates.push_back(delegate.clone());
    set_delegates(env, account_id, owner, &delegates);
    true
```

pub(crate) fn remove_delegate(
    env: &Env,
    account_id: u64,
    owner: &Address,
    delegate: &Address,
) -> bool {
    let key = ControllerKey::Delegates(account_id);
    let Some(grant) = get_user::<DelegateGrant>(env, &key) else {
        return false;
    };
    if grant.granted_by != *owner {
        env.storage().persistent().remove(&key);
        return false;
    }

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);

**Transfer cannot be used to escape debt.** The token carries the account, and
the account carries both collateral and debt. The controller keys every
solvency check on `account_id`, not on holder identity, so an underwater
position stays liquidatable after transfer, and the new holder can withdraw only
what leaves the debt covered by LTV-weighted collateral.

**Approval hands over the whole account.** `approve` and `approve_for_all` let
another address move the position, and moving the position moves the collateral
and the debt with it. See
[Account authority](../../docs/explanation/threat-model.md#account-authority)
in the threat model.

**Delegates lapse on transfer.** The controller stores a `DelegateGrant`
stamped with the `granted_by` address. `get_delegates` returns an empty list
unless `granted_by` equals the current NFT owner, so a transfer disables the
old holder's delegates immediately. The stale grant stays in storage and
re-arms if the token returns to `granted_by`. The next holder's `add_delegate`
overwrites it and `remove_delegate` deletes it.
