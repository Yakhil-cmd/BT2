### Title
Uncaught `throw Error` in indivisible-asset private-payment validation crashes the counterparty node — ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` assumes that `objValidationState.src_coin` and its sub-fields are always properly populated before validating a `transfer` input of a private, fixed-denomination (indivisible) asset. When these assumptions are violated it does not return a normal validation error through the `callback`, but instead executes a synchronous `throw Error(...)`, which is not caught anywhere in the call chain that a remote private-payment counterparty controls. This mirrors the `golang.org/x/crypto` CertChecker bug class: a client-supplied message reaches a code path that dereferences/uses an object assumed to be pre-populated by a trusted internal step, and when that assumption fails the process panics (in Node.js terms, an uncaught synchronous throw from inside a DB-callback crashes the process) instead of cleanly rejecting the input.

### Finding Description
For private indivisible-asset transfers, `objValidationState.src_coin` is supposed to be set by `indivisible_asset.js`'s `validatePrivatePayment()` before calling `validation.validatePayment(...)`: [1](#0-0) 

That value is populated from `objPrevPrivateElement`, i.e., the *previous* element in the chain, which is data sent to us by a private-payment counterparty (the sender of a private indivisible-asset payment) over the network / device-message private-payment flow, not from anything the local node has independently verified against the DAG at the point `validatePaymentInputsAndOutputs` runs: [2](#0-1) 

Deep inside `validatePaymentInputsAndOutputs()`, for the `transfer` case of a private, fixed-denomination asset, the code trusts that `src_coin` is fully formed and, if any of these invariants fail, throws synchronously instead of calling `cb`/`callback` with an error string: [3](#0-2) 

```
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
    ...
```

Every other failure mode in this same function returns a graceful error via `callback(...)`/`cb(...)` (see the surrounding lines throughout `validatePaymentInputsAndOutputs`, e.g. lines 2151-2200, 2443-2508), which is the correct, safe pattern (analogous to CertChecker correctly *returning an error* for other malformed inputs). Only these four `src_coin`-related checks deviate from that pattern and `throw` instead — precisely the "callback/precondition not checked → crash" class described in the advisory (there IsUserAuthority/IsHostAuthority being nil and invoked instead of validated first; here `src_coin`/`src_output`/`denomination`/`amount` being absent/malformed and dereferenced instead of gracefully rejected).

The remaining upstream checks in `validatePrivatePayment` guard against `null`/missing `objPrevPrivateElement.output`/`.blinding` and missing `payload.outputs`, but they do not guard against every combination that ultimately reaches this code — e.g., `prev_hidden_output.amount` (used to build `src_coin.amount`) is taken directly from the attacker-supplied `objPrevPrivateElement.payload.outputs[input.output_index]` without a positive-integer check: [1](#0-0) 
If `prev_hidden_output.amount` is `0`, negative, a string, `null`, or missing while `output_index` still resolves to a truthy-but-non-numeric entry, `src_coin.amount` fails `isPositiveInteger` at line 2423 and the process throws, uncaught, inside the `conn.query` callback stack (no `try/catch` around this branch in `validatePaymentInputsAndOutputs` or in its callers `getSavingCallbacks`/`private_payment.js`/`network.js`'s private-payment handlers).

This throw happens inside a nested async callback originating from `async.forEachOfSeries`/`conn.query`, so it cannot be caught by any `try/catch` in the calling functions — it propagates to the top of the event loop and terminates the Node.js process for anyone (full node or wallet/hub) that processes this malicious private payment chain, e.g. via `network.handleOnlinePrivatePayment` → `private_payment.validateAndSavePrivatePaymentChain` → `indivisible_asset.validateAndSavePrivatePaymentChain` → `validatePrivatePayment` → `validation.validatePayment` → `validatePaymentInputsAndOutputs`: [4](#0-3) [5](#0-4) 

### Impact Explanation
Any private-payment counterparty (a party who is sent a private indivisible-asset payment chain, e.g. a wallet, hub, or full node acting as a private-payment recipient/cosigner) can be crashed by a single crafted private-payment chain element with a malformed prior output amount. This is a remotely triggerable denial-of-service against the node/wallet process handling the private payment — consistent with "a network unable to confirm new units"/service disruption class impacts, since the crashing process may be a full node providing consensus/relay services, not merely a client UI. Because the throw occurs deep in async DB callbacks, it cannot be caught by the caller's `async.series`/`try/catch` wrapping, and the process terminates.

### Likelihood Explanation
The private-payment protocol accepts payment chains directly from counterparties over the network (`network.js: handleOnlinePrivatePayment`) and from wallet API surfaces, with only partial structural validation of `objPrevPrivateElement` before its fields are propagated into `objValidationState.src_coin`. Constructing a chain where `prev_hidden_output.amount` is non-positive/non-integer while all other shallow checks pass is straightforward for an attacker fully controlling the private-payment payload, making this a low-complexity, single-message DoS.

### Recommendation
In `validatePaymentInputsAndOutputs()` (validation.js, lines 2415-2424), replace the `throw Error(...)` calls guarding `src_coin`/`src_output`/`denomination`/`amount` with graceful `cb("...")` error returns (same pattern used everywhere else in this function). Additionally, in `indivisible_asset.js`'s `validatePrivatePayment()`, validate that `prev_hidden_output.amount` is a positive integer (and that `src_output.blinding`/`address` are well-formed) before constructing `objValidationState.src_coin`, rejecting the private payment with a normal validation error instead of allowing malformed data to reach the throwing code path.

### Proof of Concept
1. As a private-payment sender, construct a 2-element private indivisible-asset payment chain (`arrPrivateElements`) for a fixed-denomination private asset.
2. In the head element's `payload.outputs[output_index]` (the "previous" hidden output referenced by the transfer input), set `amount` to `0` or a negative number or omit it, while keeping `blinding`/`address`/`output` structurally present so the earlier `!objPrevPrivateElement.output.blinding` / `!objPrevPrivateElement.payload.outputs` checks in `indivisible_asset.js` (lines 102-105) pass.
3. Send this chain to a peer node/wallet as an online private payment via `network.handleOnlinePrivatePayment` (or the wallet's private-chain handling API).
4. The victim calls `validation.validatePayment` → `validatePaymentInputsAndOutputs`; `objValidationState.src_coin.amount` fails `isPositiveInteger`, hitting `throw Error("no src coin amount")` at validation.js line 2423, inside a `conn.query` callback with no enclosing `try/catch`, crashing the victim's Node.js process.
