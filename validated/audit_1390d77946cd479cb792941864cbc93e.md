### Title
Uncaught `throw Error` in address-definition evaluation crashes node on a single crafted unit - (File: definition.js)

### Summary
`definition.js`'s `validateAuthentifiers()` → `evaluate()` contains two branches (`'definition template'` and `'seen'`) that use a hard, synchronous `throw Error(...)` instead of returning an error through the callback chain used everywhere else in this function (`cb2(false)` / `cb2(err)`). Because this `throw` happens inside an async `conn.query` callback, it is not caught by any surrounding `try/catch`, propagates out of the async stack, and reaches Node's top-level. `network.js` installs `process.on('uncaughtException', ...)` which explicitly re-throws to crash the process (`throw err; // crash the process to avoid ending up in an inconsistent state`). This is the same bug class as CVE-2021-32438 (a crafted input reaching an unguarded dereference/assumption that aborts the whole program) - here the crash is triggered purely by validating a single posted unit signed by an address whose definition contains one of these ops.

### Finding Description
`validateAuthentifiers()` is invoked for every unit during normal unit validation (`validateAuthors` → `validateAuthor` → `validateAuthentifiers`), to check that a unit's authentifiers satisfy the address's spending-definition. [1](#0-0) 

Inside its `evaluate()` function, most ops report failures via the async callback `cb2(...)`. However the `'definition template'` op throws synchronously when the referenced template unit isn't found with exactly one stable row at or before the validating unit's `last_ball_mci`: [2](#0-1) 

and the `'seen'` op throws synchronously when `filter.what` is anything other than `'input'`/`'output'`: [3](#0-2) 

Both throws occur inside the `conn.query(...)` result callback (`'definition template'`) or directly in `evaluate()` (`'seen'`), which is called from deep inside `async.eachSeries`/`async.series` chains rooted in `validation.validate()` (`validateAuthors` → `validateAuthor` → `Definition.validateAuthentifiers`). None of `validateAuthentifiers`, `validateAuthor`, `validateAuthors`, or `validate()` wrap this evaluation in a `try/catch` — unlike the sibling `validateDefinition()` function used at *definition-set* time, whose `evaluate()` always reports errors via `cb(err)` instead of throwing.

Once thrown, the exception unwinds through the mutex/async machinery in `network.js`'s `handleJoint`/`mutex.lock` call stack and is not caught anywhere, so it becomes an uncaught exception at the process level. `network.js` registers: [4](#0-3) 

which deliberately re-throws to crash the whole node process.

For the `'definition template'` path in particular, the crash is fully attacker-controlled and reachable by an unprivileged unit poster:
1. An attacker (or address owner) defines an address whose spending condition includes `['definition template', [<template_unit>, {...}]]`, referencing a `definition_template` message the attacker also controls/posts.
2. The attacker crafts and posts a unit from that address at a moment where the referenced `<template_unit>` is not yet stable at or before the new unit's `last_ball_mci` (e.g., by choosing a `last_ball`/`last_ball_unit` earlier than the template's stabilization, or referencing a unit that never stabilizes/exists as a `definition_template`).
3. Every node that validates this unit executes `evaluate()` → the `SELECT ... WHERE unit=? AND app='definition_template' AND main_chain_index<=? ... AND is_stable=1` query returns 0 rows, hitting `throw Error("not 1 template")`.
4. The throw is uncaught, and via `network.js`'s `uncaughtException` handler the node process crashes.

This affects every full node that receives and validates the malicious unit (via `handleSavedJoint`/`handlePostedJoint` → `handleJoint` → `validation.validate` → `validateAuthentifiers`), which is a broader remotely-triggerable node crash than a purely local DoS.

### Impact Explanation
A successful trigger crashes the Node.js process on every full node that attempts to validate the crafted unit (posted directly or received via gossip/relay), because the top-level `uncaughtException` handler intentionally rethrows to kill the process. Repeated posting of such units (or broad propagation before nodes restart/blacklist the sender) can be used to repeatedly crash validating nodes, i.e., a network unable to reliably confirm new units while affected nodes are down/restarting. This matches the "network unable to confirm new units" / node-disagreement-adjacent impact class requested, and is reachable purely from a single posted unit authored by an address the attacker controls (no privileged role required).

### Likelihood Explanation
Medium-to-high for an attacker willing to set up the preconditions once: they must (a) control an address whose definition uses the `'definition template'` (or `'seen'` with malformed `what`) op, and (b) craft a unit whose `last_ball_mci` makes the referenced template not-yet-stable, or force `filter.what` outside `{'input','output'}` (the latter requires the JSON definition to somehow contain something other than 'input'/'output' — this is normally rejected at `validateDefinition` time via `getFilterError`, so the `'seen'` throw path is largely defense-in-depth and not independently reachable by an attacker with a definition that has already passed `validateDefinition`; the `'definition template'` throw is the practically exploitable one because timing/stability of the referenced unit is not statically checked at definition-registration time). The `'definition template'` op is rarely used in practice, but nothing in `validateDefinition()` prevents referencing an unstable/soon-to-exist template, so the crash condition is fully within attacker control once the address/definition is set up.

### Recommendation
Convert both `throw Error(...)` statements in `definition.js`'s `validateAuthentifiers()`/`evaluate()` (the `'definition template'` and `'seen'` cases) into normal error propagation via the callback (`cb2` and ultimately `cb(err)`), consistent with how `validateDefinition()`'s `evaluate()` reports all other invalid conditions. At minimum, wrap the `conn.query` callback body in `try/catch` and forward failures through `cb2`/`fatal_error` instead of throwing, so that malformed or transiently-unstable references cause unit validation to fail gracefully (`ifUnitError`) rather than crashing the process. Additionally, consider auditing other `throw Error(...)` occurrences reachable from `validateAuthentifiers`'s `evaluate()` for the same pattern.

### Proof of Concept
1. Post/define address `A` with spending definition:
   `["definition template", ["<TEMPLATE_UNIT>", {}]]` combined with a `sig` branch as required by `validateDefinition`.
2. Post a `definition_template` message in unit `<TEMPLATE_UNIT>` from any address, but do not let it stabilize (or reference a unit id that never becomes a stable `definition_template`).
3. From address `A`, construct and broadcast a payment unit whose `last_ball`/`last_ball_unit` corresponds to an MCI at or before `<TEMPLATE_UNIT>`'s eventual stabilization (or simply reference a unit that is not `is_stable=1` with `app='definition_template'`).
4. Any full node that validates this unit executes `validateAuthentifiers` → `evaluate()` → `'definition template'` case; the `SELECT` returns 0 rows, triggering `throw Error("not 1 template")` inside the `conn.query` callback at [5](#0-4) , which is uncaught and crashes the node via the handler at [4](#0-3) .
