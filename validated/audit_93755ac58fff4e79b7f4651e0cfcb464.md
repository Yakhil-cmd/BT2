### Title
Unsanitized contract `debug_message` buffer is logged verbatim to the node terminal, enabling ANSI/terminal escape-sequence injection - ([File: substrate/frame/contracts/src/exec.rs])

### Summary
`pallet-contracts`'s `debug_message` host function lets any contract (deployable/callable by any unprivileged signed account) append attacker-chosen UTF-8 bytes to an in-memory debug buffer during an RPC `bare_call`/`bare_instantiate`. When the call stack completes, the entire buffer is written unmodified to the node's log/terminal output via `log::debug!`. The message content is never filtered for ANSI/control escape sequences before being handed to `tracing`/`sc_tracing`, which itself performs no escaping and writes the field text straight to stderr/stdout, exactly analogous to Git's sideband message being printed unfiltered to the terminal (CVE-2024-52005).

### Finding Description
Any account can upload and instantiate a contract, then invoke the `debug_message` host function with arbitrary bytes: [3](#0-2) 

The bytes are validated only as UTF-8 (`core::str::from_utf8`), with no restriction on control characters, and appended to `DebugBufferVec`: [4](#0-3) 

At the end of the outermost call frame the accumulated buffer is emitted directly through the logging macro that a node operator watches on their terminal: [5](#0-4) 

The `pallet-contracts` `ContractResult::debug_message` doc explicitly instructs clients to "just display it as-is", reinforcing that no sanitization is expected downstream either: [6](#0-5) 

On the logging-formatter side, `EventFormat::format_event_custom` writes the log record's fields (which contain the raw debug-buffer text) straight into the writer without stripping escape sequences: [1](#0-0) 

That buffered output is then flushed verbatim to the OS-level stderr stream by `StderrWriter::write`, whose own doc comment acknowledges it is printing "untrusted user input": [2](#0-1) 

The root cause mirrors the Git CVE precisely: text originating from an untrusted, remote/attacker-controlled source (there: the Git server's sideband channel; here: a permissionlessly-deployed contract's debug buffer) is forwarded to a terminal that interprets ANSI escape codes, with no filtering step anywhere in the pipeline (host function → pallet-contracts → tracing formatter → stderr writer).

### Impact Explanation
If a node operator/developer enables `runtime::contracts=debug` logging (a documented, common debugging workflow, cf. `substrate/frame/contracts/README.md`) and issues an RPC `bare_call`/`bare_instantiate` against a maliciously crafted contract (e.g. supplied by a third party, discovered on a testnet, or used as a support/bug-report reproduction step), the attacker's debug-message payload can contain ANSI escape sequences that:
- Hide or rewrite subsequent terminal output (e.g. make error output disappear or show fabricated "success" text).
- Move the cursor / clear the screen to hide malicious content.
- On some terminal emulators, inject OSC sequences that alter window titles, or in vulnerable terminal emulators, trigger further terminal-level exploits.

This is a client/operator-side terminal-spoofing/social-engineering vector rather than a consensus or fund-safety bug — it cannot mint funds, bypass dispatch, or corrupt state — so it is bounded to Low/Medium severity in the FRAME/pallet-contracts context, unlike the "High" rating Git received (Git's case additionally covered `clone`/`fetch` executed non-interactively against arbitrary untrusted remotes, a broader attack surface).

### Likelihood Explanation
Reaching this code path requires only permissionless contract deployment/execution (no privileged role, no governance, no stolen keys — satisfying the "real user entry" requirement), but it is only observable when a human operator (a) has intentionally raised the `runtime::contracts` log target to `debug`, and (b) is watching the interactive terminal (not a piped/aggregated log collector, which typically neutralizes escape sequences). This is a realistic but narrow window (contract debugging sessions), so likelihood is Low-to-Medium.

### Recommendation
Sanitize/strip ANSI escape and other terminal control sequences from the contract debug buffer before it is logged in `Stack::pop_frame` (`substrate/frame/contracts/src/exec.rs`), and/or have the `sc_tracing` `EventFormat`/`StderrWriter` pipeline escape non-printable/control bytes (e.g. render them as `\xNN`) for any field data before writing to a TTY, mirroring the fix direction taken by Git for CVE-2024-52005 (filtering "remote:" sideband text before printing to the terminal).

### Proof of Concept
Not independently executed in this environment (no filesystem/terminal access available in Ask mode); the reachability and missing-sanitization guards were verified purely via source inspection:
1. `substrate/frame/contracts/src/wasm/runtime.rs:2301-2317` — `debug_message` host call accepts arbitrary bytes from contract memory, checked only for UTF-8 validity.
2. `substrate/frame/contracts/src/exec.rs:1533-1548` — bytes appended verbatim to `DebugBufferVec`.
3. `substrate/frame/contracts/src/exec.rs:1149-1156` — full buffer logged via `log::debug!` with no filtering.
4. `substrate/client/tracing/src/logging/event_format.rs:86-100` and `substrate/client/tracing/src/logging/stderr_writer.rs:196-208` — the tracing formatter and stderr writer forward the text unmodified to the terminal.

A minimal reproduction (not run here) would deploy a WASM contract analogous to the existing test fixture `debug_message_works.rs` but with a payload containing an ANSI escape sequence (e.g. `\x1b[2K\rFAKE: transaction succeeded`), invoke it via `bare_call` with `DebugInfo::UnsafeDebug` while running the node with `-lruntime::contracts=debug` on an interactive TTY, and observe that the escape sequence is interpreted by the terminal rather than displayed literally — following the same test pattern already used in `substrate/frame/contracts/src/tests.rs:2136-2150` (`debug_message_works`), just substituting the payload.

	fn write(&mut self, input: &[u8]) -> Result<usize, std::io::Error> {
		let buffer = self.buffer.as_mut().expect("buffer is only None after `drop`; qed");
		if buffer.len() + input.len() >= EMERGENCY_FLUSH_THRESHOLD {
			// Make sure we don't blow our memory budget. Normally this should never happen,
			// but there are cases where we directly print out untrusted user input which
			// can potentially be megabytes in size.
			emergency_flush(buffer, input);
		} else {
			buffer.extend_from_slice(input);
		}
		Ok(input.len())
	}
