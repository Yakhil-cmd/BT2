### Title
Cross-Organization Webhook Authentication Confusion Leading to Unauthorized Review-Stack Provisioning — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook using an *organization* identifier extracted from the payload (`repository.owner.login`, falling back to `organization.login`), then looks up that organization's GitHub App `webhook_secret` to validate the HMAC signature. Once the signature check passes, the individual event handlers (e.g. `PushHandler`, `PullRequest::OpenedHandler`) independently re-read a *different* field — `repository.full_name` — from the same unsigned-but-now-"trusted" JSON body to decide **which repository/stack** to act on. Because these two fields are never cross-validated against each other, a party that legitimately owns a GitHub App installation for *their own* organization (and therefore genuinely knows that org's `webhook_secret`) can self-sign an arbitrary payload where `repository.owner.login`/`organization.login` names their own org (so signature verification succeeds) while `repository.full_name` names a **victim organization's repository**. This breaks the binding "organization authenticated == repository written."

### Finding Description
The controller's authentication step is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

This is only meaningful in the documented multi-organization configuration, where each GitHub org has its own `app_id`/`webhook_secret` under `Shipit.github(organization: ...)`. [3](#0-2)

Because `owner.login`/`organization.login` (used for authentication) and `full_name` (used for repository resolution/write) are independent, attacker-controlled JSON fields, an attacker who legitimately administers a GitHub App for `attacker-org` (and thus genuinely knows `attacker-org`'s `webhook_secret`) can:
1. Craft a JSON body with `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`) so `verify_signature` selects and validates against the attacker's own, legitimately-known secret.
2. Set `repository.full_name = "victim-org/victim-repo"` in the same body.
3. Sign the whole raw body with the attacker's own `webhook_secret` and POST it to the shared `/webhooks` endpoint.

The signature check passes (it's genuinely correct for `attacker-org`), but every downstream handler acts on `victim-org/victim-repo` because it trusts `full_name` without checking it belongs to the org that was actually authenticated.

### Impact Explanation
This directly triggers writes and deploy-adjacent actions on a repository/stack the attacker was never authenticated for, satisfying the "cross-repository writes" / "unauthorized deploy" High/Critical bar:
- `PushHandler` can force a `sync_github` resync against arbitrary target stacks. [7](#0-6) 
- `PullRequest::OpenedHandler`/`ReviewStackAdapter` can create a brand-new `ReviewStack` scoped to the victim's repository and immediately enqueue it for **provisioning/deployment** (`ReviewStackProvisioningQueue.add`) using an attacker-chosen branch name and PR number, without ever having write access to the victim repository or the victim's GitHub App credentials. [6](#0-5) 
- Other PR handlers (`ClosedHandler`, `UnlabeledHandler`, etc.) can archive/unarchive/deprovision victim review stacks the same way, since they all resolve `repository` via `params.repository.full_name` post-authentication. [8](#0-7) 

Note: `MembershipHandler` is not exploitable this way because its team/organization data is keyed off the same `organization.login` field used for authentication, so it does not exhibit this particular binding break. [9](#0-8) 

### Likelihood Explanation
Requires: (1) the deployment to be configured with multiple GitHub organizations sharing one Shipit instance (a documented, supported configuration), and (2) the attacker to control/administer a legitimate GitHub App installed for one of those organizations, giving them genuine knowledge of that org's `webhook_secret`. Given that condition, no further privileges (no Shipit session, no `ApiClient` token, no victim repository access) are needed — only the ability to POST a crafted, self-signed JSON body to the shared `/webhooks` endpoint.

### Recommendation
After resolving `github_app` via `repository_owner` and verifying the signature, re-validate that the same authenticated organization matches the owner encoded in `repository.full_name` (and `organization.login` for org-level events) before any handler is allowed to act on that repository. Reject the webhook (422) if `repository.full_name`'s owner segment does not match the organization whose secret validated the signature.

### Proof of Concept
Given a Shipit instance configured with two GitHub orgs `attacker-org` (secret `S_A`, known to the attacker as its legitimate GitHub App admin) and `victim-org` (secret `S_V`, unknown to attacker):

```
POST /webhooks HTTP/1.1
X-Github-Event: pull_request
X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>

body = {
  "action": "opened",
  "number": 999,
  "pull_request": {
    "id": 1, "number": 999, "url": "...", "title": "x", "state": "open",
    "additions": 0, "deletions": 0,
    "head": { "sha": "deadbeef", "ref": "malicious-branch" },
    "user": { "login": "attacker" },
    "assignees": [], "labels": []
  },
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  },
  "sender": { "login": "attacker" }
}
```
`verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates the signature against `S_A` — success, since the attacker legitimately signed with their own secret. `OpenedHandler#repository` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")`, and if that repository has review stacks enabled with `allow_all` provisioning, a new `ReviewStack` for branch `malicious-branch` is created and queued for provisioning against `victim-org/victim-repo` — despite the request never being authenticated for `victim-org`.
