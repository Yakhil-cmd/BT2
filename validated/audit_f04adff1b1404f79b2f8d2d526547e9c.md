### Title
API token stack-scope bypass in CCMenu status endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper defined in `Shipit::Api::BaseController` in a way that discards the stack-scoping enforced for every other API endpoint. This breaks the equality that should hold between "the stack(s) an `ApiClient` token is authorized for" and "the stack whose data the request actually returns," allowing a token scoped to one stack to read deploy/task status information for any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the scoping contract used by all API controllers: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id` set, and `stack` resolves `params[:stack_id]` only within that restricted relation via `stacks.from_param!`.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this relation entirely: [2](#0-1) 
Instead of calling `stacks.from_param!`, it calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model. The controller still declares `require_permission :read, :stack`, but `ApiClient#check_permissions!` only checks that the token's `permissions` array contains `"read:stack"` — it never checks which stack the permission applies to: [3](#0-2) 

The equality that should hold is:
`{stacks the ApiClient.stack_id authorizes} == {stack actually rendered by CCMenuController#show}`

Before the request: a token created with a specific `stack_id` (e.g. stack A) is meant to only ever resolve to stack A via `BaseController#stacks`/`#stack`.
After the request: because `CCMenuController#stack` ignores `current_api_client.stack_id` and resolves any `params[:stack_id]` against the global `Stack` table, the same token can be replayed with a different `stack_id` value and will successfully authenticate (permission check passes because it only checks the permission name, not the scope) and return that other stack's CI/deploy status.

The `show` action then renders deploy state for whatever stack was resolved: [4](#0-3) 

Every other API controller (`TasksController`, `RollbacksController`, `OutputsController`, `HooksController`, `LocksController`, `StacksController`) consistently calls the inherited `stack`/`stacks` helpers and is therefore correctly scoped; `CCMenuController` is the sole outlier that redefines `stack` to query `Stack` directly.

### Impact Explanation
This is a High severity authorization-scope escalation: an `ApiClient` token deliberately scoped by an operator to a single stack (e.g. issued to a CI system that should only see one repository/environment's deploy status) can be used to read deploy/task state (`latest_deploy`, running status, task id/end time) for **any** stack in the Shipit installation simply by changing the `stack_id` in the request path, with no additional credential required. This matches the "escalation into authorization... unauthenticated/out-of-scope read of stack state, task streams or deploy output" impact category, since it defeats the per-token stack authorization boundary that the rest of the API enforces.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a documented, supported feature via `ApiClient#stack_id`). Exploitation requires only a valid token with `read:stack` permission (which is the normal permission granted to any read-capable client) and knowledge/guessing of another stack's `id` or `repo_owner/repo_name/environment/branch` (which `Stack.from_param!` also accepts) — no privileged access, signing key, or session is needed beyond the token itself, which is exactly the class of "unprivileged-attacker analog" in scope here (the attacker already legitimately holds a scoped token but crosses its authorized stack boundary).

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and use the inherited, scoped `stack`/`stacks` methods from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`), so CCMenu lookups are constrained the same way as every other API endpoint. If the override exists to support an alternate authentication mechanism (`authenticate_api_client` via `params[:token]`), keep that but restore the scoped lookup for `stack`.

### Proof of Concept
1. Operator creates two stacks, A and B, and issues an `ApiClient` token scoped to stack A only (`ApiClient.create!(stack: stack_a, permissions: ['read:stack'], ...)`), intending the token to only ever see stack A's status.
2. Using that same token, request:
   `GET /shipit/api/stacks/<stack_a_id>/ccmenu?token=<token>` → succeeds, returns stack A's status (expected).
3. Replay with stack B's id:
   `GET /shipit/api/stacks/<stack_b_id>/ccmenu?token=<token>`
   - `authenticate_api_client` authenticates the token successfully.
   - `require_permission :read, :stack` passes because the token has `"read:stack"` in `permissions` (permission name is not stack-specific).
   - `stack` resolves via `Stack.from_param!(params[:stack_id])` against the whole `Stack` table, returning stack B regardless of `current_api_client.stack_id`.
   - The response renders stack B's `latest_deploy`/status, which the token was never authorized to access. [5](#0-4) [6](#0-5)

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
```
