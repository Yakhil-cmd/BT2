### Title
`ReopenedHandler#unarchive?` re-provisions review stacks on repos with `review_stacks_enabled: false` due to operator-precedence bug - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (...)`, where `&&` binds tighter than `||`, so `review_stacks_enabled` only gates the first disjunct. Unlike `OpenedHandler#provision?` (same bug but that's out of scope for this question) and unlike `LabeledHandler`/`UnlabeledHandler`, which additionally gate the whole decision at `respond_to_label_change?` with a top-level `repository.review_stacks_enabled &&`, `ReopenedHandler#respond_to_pull_request_reopened?` performs no such outer gate — it calls `unarchive?` directly with nothing else checking `review_stacks_enabled`.

### Finding Description
The claimed binding is: `unarchive? == true` should require `repository.review_stacks_enabled == true` for every path, i.e. `unarchive? → review_stacks_enabled == true`.

Actual code, [1](#0-0) :
```ruby
def respond_to_pull_request_reopened?
  params.action == "reopened" &&
    unarchive?
end

def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Ruby operator precedence makes `&&` bind before `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

The second and third disjuncts are entirely independent of `review_stacks_enabled`. If a repository has `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (or `prevent_with_label`), `unarchive?` can still return `true` purely from the label-based term, with no `review_stacks_enabled` check anywhere in the call chain — `respond_to_pull_request_reopened?` doesn't check it either, unlike `LabeledHandler#respond_to_label_change?`/`UnlabeledHandler#respond_to_label_change?`, which both explicitly AND `repository.review_stacks_enabled` at the top level ( [2](#0-1) ).

Exploit flow: an attacker who owns/forks a repo pointed at this Shipit instance (or any repo already onboarded to Shipit with an existing archived review stack) sends a `pull_request` webhook with `action: reopened` for a PR whose branch maps to an existing archived `ReviewStack` (`environment: "pr#{number}"`), and whose labels include the repo's `provisioning_label_name` (attacker fully controls PR labels on their own PR). `ReopenedHandler#process` then calls `stack.unarchive!` via `ReviewStackAdapter#unarchive!`, which invokes `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.unarchive!(*args)` ( [3](#0-2) ), re-queueing the stack for provisioning/deployment even though the operator explicitly disabled review stacks for that repository.

Existing guards do not stop this: `verify_signature`/webhook signature checks are unrelated to this logic bug (out of scope per the question, which is specifically about the `unarchive?` boolean), `params` schema validation only validates payload shape, and there is no additional `review_stacks_enabled` check anywhere else in `ReopenedHandler`. The `stack` lookup is scoped to `repository.review_stacks` (an existing DB association) — it does not re-check the `review_stacks_enabled` flag at the DB layer.

### Impact Explanation
This causes an unauthorized re-provisioning/re-execution: `Shipit::ReviewStackProvisioningQueue.add(stack)` queues the archived stack for provisioning and `stack.unarchive!` flips it back to active, both intended to be gated by `review_stacks_enabled` at the repository level. This matches "Critical - unauthorized deploy" impact category since re-provisioning a review stack drives execution of `shipit.yml`-defined steps for that stack's branch/environment on the deploy host, and it happens on a repository whose operator explicitly disabled the review-stacks feature. The blast radius is scoped to review stacks that already exist for the targeted repository (must have been created earlier while `review_stacks_enabled` was true, or during any window it was enabled) and does not cross into other repositories' stacks, since `ReviewStackAdapter` scope is `repository.review_stacks`.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled: false` currently but `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`, and must have at least one existing archived `ReviewStack` for a PR number the attacker controls (either from a prior period when review stacks were enabled, or via a race/config change). Attacker cost is low — controlling PR labels and reopening a PR are unprivileged, unauthenticated-webhook-level actions consistent with the threat model. This is realistic in a operational scenario where an admin disables review stacks (e.g., to pause the feature) but stale archived stacks remain in the DB — reopening the PR silently resurrects deployment activity contrary to the admin's intent.

### Recommendation
Fix operator precedence to ensure `review_stacks_enabled` gates every disjunct, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Alternatively, add an explicit `repository.review_stacks_enabled &&` gate in `respond_to_pull_request_reopened?`, mirroring `LabeledHandler#respond_to_label_change?`/`UnlabeledHandler#respond_to_label_change?`. Apply the same fix to `OpenedHandler#provision?`, which has the identical bug pattern.

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` style, mirroring existing fixtures used there, e.g. [4](#0-3) ):

```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with matching provisioning label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  # Explicit binding check: review_stacks_enabled must be false
  assert_equal false, repository.reload.review_stacks_enabled

  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::ReviewStackProvisioningQueue.expects(:add).never
  Shipit::Stack.any_instance.expects(:unarchive!).never

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived when review_stacks_enabled is false"
end
```
Running this against the current code is expected to fail: `unarchive?` returns `true` from the `allow_with_label? && has_label?` disjunct regardless of `review_stacks_enabled`, so `ReviewStackProvisioningQueue.add` and `stack.unarchive!` are invoked and the assertion `stack.reload.archived?` fails, demonstrating the vulnerability.
