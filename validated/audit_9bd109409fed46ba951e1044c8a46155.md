### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The signing-organization check and the repository-targeting logic read two different, independently attacker-controlled fields from the same unauthenticated JSON payload. Because the HMAC only covers "does this body match a secret for *some* organization," and the org used to pick that secret is not the org whose repository actually gets acted upon, a party holding a legitimate webhook secret for org A can forge events that are processed against a completely different org/repo (org B) as if GitHub had sent them.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload itself and uses it only to choose which `GitHubApp`/`webhook_secret` to validate the signature with: [1](#0-0) [2](#0-1) 

Once the signature is deemed "verified" (i.e., it matches *some* org's secret), the raw `params` are handed unchanged to the registered handler: [3](#0-2) 

All handlers (e.g. `PushHandler`) resolve which `Repository`/`Stack` to operate on via `Handler#repository_name`, which reads `repository.full_name` - a completely separate JSON field from `repository.owner.login`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` just splits `owner/name` and does a lookup with no cross-check against the org that was used for signature verification: [6](#0-5) 

The broken equality is:
`organization used to select webhook_secret for HMAC verification` **≠** `repository.full_name owner used to locate and mutate the Repository/Stack`.

An attacker who legitimately controls (or has been granted) a GitHub App installation/webhook secret for org A (e.g., they run their own low-trust integration/org on the same Shipit instance) can craft a POST to `/github/webhooks` with:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
signed with org A's `webhook_secret`. `verify_signature` resolves `Shipit.github(organization: "orgA")` (matching the attacker's own secret) and the signature passes. `PushHandler#process`, however, looks up stacks belonging to `orgB/victim-repo` and calls `stack.sync_github(expected_head_sha: params.after)`, causing GitHub sync/deploy-eligibility state for org B's stack to be driven by data the attacker fully controls, without ever having any credential, membership, or access to org B.

### Impact Explanation
This crosses a repository/organization trust boundary: a party authenticated only as "some organization with a configured webhook secret" can inject fabricated push/status/check_suite/membership events that mutate the state (commits, sync status, statuses, team membership via `membership_handler`) of a *different* organization's `Repository`/`Stack` records that they were never granted access to. This is a cross-repository, cross-organization write driven entirely by unauthenticated/unauthorized payload content, matching the "cross-repository writes" Critical-impact category, since it can influence which commit is considered deployable/synced and thus indirectly what gets deployed for a repo the attacker does not own.

### Likelihood Explanation
Requires only that the attacker possess *any* valid `webhook_secret`/GitHub App configured in `Shipit.github` for at least one organization on the instance (a legitimate but low-trust tenant on a multi-org Shipit deployment) - no session, no `ApiClient` token, and no access to the victim org is needed. This is a realistic configuration for any Shipit install onboarding multiple organizations, so likelihood is Medium-High for such deployments.

### Recommendation
After `verify_signature` succeeds, re-derive the organization strictly from the same field used for repository resolution (`repository.full_name`'s owner segment, or `organization.login`) and reject the request (422) if it doesn't match the organization whose secret validated the HMAC. Alternatively, have handlers only operate on repositories belonging to the verified `repository_owner`, never trusting `full_name`'s owner component independently.

### Proof of Concept
1. Attacker controls org `orgA` with a configured `webhook_secret` in `Shipit.github`.
2. Attacker computes `sha1=HMAC(webhook_secret_orgA, body)` for a body:
   `{"ref":"refs/heads/main","after":"<attacker_sha>","repository":{"owner":{"login":"orgA"},"full_name":"orgB/victim-repo"}}`
3. POST to `/github/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` picks `Shipit.github(organization: "orgA")`, validates successfully.
5. `PushHandler` looks up `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker_sha>")` on `orgB`'s stacks, despite the attacker having no relationship to `orgB`.
