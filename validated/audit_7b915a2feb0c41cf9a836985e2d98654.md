### Title
Webhook signature verification authenticates the payload's `repository.owner.login` (or `organization.login`) but handlers act on the independently-supplied `repository.full_name`, letting an attacker holding *any* configured organization's webhook secret forge events for a *different* organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner`, a value read straight out of the (still-unverified) JSON body (`params.dig('repository','owner','login')` or `organization.login`) via `Shipit.github(organization: repository_owner)`. Once the HMAC check passes, every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack`/`Repository` it will mutate using a *different* field from the same body: `payload.dig('repository', 'full_name')` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing ties these two fields together, so the org whose secret authenticated the request is never required to equal the org whose repository is actually acted upon.

### Finding Description
- `verify_signature` picks the GitHub App/secret to validate with by organization login taken from the payload: [1](#0-0) [2](#0-1) 

- Once verification succeeds with that secret, the handler dispatch for the event runs against the full raw JSON body: [3](#0-2) 

- Every handler subclassing `Handler` resolves which stacks to mutate from `repository.full_name`, a completely separate field of the same body: [4](#0-3) 

- `PushHandler`, for example, uses that `stacks` scope to trigger `sync_github` for any matching non-archived stack: [5](#0-4) 

Shipit explicitly supports hosting multiple independent GitHub organizations/Apps in one instance, each with its own `webhook_secret`: [6](#0-5) 

Because `verify_signature` only checks that the HMAC matches *some* configured org's secret (chosen by `repository.owner.login`), and the handlers key off `repository.full_name` without cross-checking it against that same owner, an attacker who legitimately administers the GitHub App/webhook for Organization A (a tenant on the shared Shipit instance) can craft a webhook body where `repository.owner.login`/`organization.login` = "orgA" (so the signature validates with the secret they know) while `repository.full_name` = "orgB/some-other-repo" (a stack belonging to a different tenant, Organization B, on the same Shipit instance). The signature check passes using orgA's secret, but the handler acts on orgB's stack.

The binding broken is exactly analogous to the reported bug class: *the organization that authenticated the request ≠ the repository that is actually written to.*

### Impact Explanation
This is not merely a `push`-triggered sync. The same `Handler#stacks`/`repository_name` resolution is used by `StatusHandler` and `CheckSuiteHandler`, which record CI/check results (`commit_status`, `check_suite`) on arbitrary commits of the victim's stacks. Shipit's deploy-gating logic (required statuses/checks, `ignore_ci`) consumes these records to decide whether a commit is deployable. By forging `status`/`check_suite` events attributed to a victim organization's repository while authenticating with their own organization's webhook secret, an attacker can mark arbitrary commits on another tenant's stack as passing CI, directly enabling an unauthorized deploy of that stack — squarely within the "unauthorized deploy" Critical-impact category. This requires no Shipit session, `ApiClient` token, `api_clients_secret`, private key, or GitHub write access to the victim's repository — only administration of their own (legitimately obtained) GitHub App/org webhook secret on the shared multi-tenant Shipit instance.

### Likelihood Explanation
Exploitability depends on the deployment being multi-tenant (multiple orgs configured under `Shipit.github`, as the shipped example config demonstrates). In that common configuration, any tenant admin can immediately forge signed events attributed to any other tenant's repositories, since the only per-request check is "does this HMAC match some configured secret for the login in the payload" — there is no verification that the signing org's real GitHub identity matches the `repository.full_name` acted upon.

### Recommendation
In `WebhooksController#verify_signature`/handler dispatch, after selecting the GitHub App by `repository_owner`, re-derive `repository_owner` from `repository.full_name` (or vice versa) and reject the request (422) if they don't match. Alternately, have `Handler#repository_name`/`#stacks` cross-validate that the resolved `Repository`'s owner equals the `repository_owner`/organization used for signature verification before performing any mutation.

### Proof of Concept
1. Attacker administers Organization A's GitHub App installed on Shipit (knows `webhook_secret_A`), a legitimate, unprivileged capability relative to Organization B.
2. Attacker crafts a `status` (or `push`/`check_suite`) webhook JSON body:
   ```json
   {
     "sha": "<victim-commit-sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, validates successfully against `webhook_secret_A`.
5. `StatusHandler` (subclass of `Handler`) resolves `stacks` via `repository.full_name` = `"orgB/victim-repo"`, and records the forged `"success"` status on the victim commit, satisfying deploy-gating checks for Organization B's stack — enabling an unauthorized deploy without ever touching Organization B's credentials.
