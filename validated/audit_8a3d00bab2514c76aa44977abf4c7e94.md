### Title
Uncaught exception inside a mutex-locked write/AA-trigger critical section permanently starves the lock, freezing all future unit writes / AA execution across the node - (File: writer.js, aa_composer.js, mutex.js)

### Summary
The Spring AMQP finding describes a resource ("link credit") that is consumed on every failed delivery and is never replenished when the container-level `ErrorHandler` swallows the exception, so after `initialCredits` failures the listener silently stalls while still reporting itself as running. The structural bug class is: *a bounded, serialized resource is permanently consumed on an exception path that bypasses the normal release/replenish logic, causing silent, total stall of a queue while the process looks healthy.*

`ocore`'s `mutex.js` implements exactly such a bounded, serialized resource: a named lock key (e.g. `"write"`, `"aa_triggers"`, `"handleJoint"`) is held by exactly one job at a time, and is only released when the job explicitly calls the `unlock` callback handed to it in `exec()`. If the locked function throws synchronously instead of calling `unlock()`, `release(arrKeys)` is never invoked and the key stays in `arrLockedKeyArrays` forever, so every subsequent job requiring that key queues in `arrQueuedJobs` and is never run.

`writer.saveJoint()` (all node-wide unit writes) and `aa_composer.handlePrimaryAATrigger()` (all AA trigger execution, invoked once per stabilized MCI for every unhandled trigger) both run their entire body while holding such a lock (`"write"` and `"aa_triggers"` respectively), and both contain many `throw Error(...)` statements reachable from attacker-influenced unit content that fire before the corresponding `unlock()` call is reached.

### Finding Description
`mutex.exec()` only releases a lock key through the `unlock` closure passed into the protected function: [1](#0-0) 

`writer.saveJoint()` acquires the `"write"` lock once at the top and calls `unlock()` only at the very end of its callback chain, hundreds of lines and many asynchronous steps later: [2](#0-1) [3](#0-2) 

Between lock acquisition and the final `unlock()`, `writer.js` contains numerous `throw Error(...)` statements executed synchronously inside DB-callback closures, e.g. the src-output resolution logic for multi-authored payment inputs: [4](#0-3) 

Any of these throws (`"multiple src outputs found"`, `"src output not found"`, `"asset doesn't match"`, `"denomination doesn't match"`, `"src output address not among authors"`, plus ~29 other `throw Error` sites in the file) escapes the synchronous call stack that originated inside `mutex.exec()`'s `proc(...)` invocation, so `unlock()` for the `"write"` key is never called and `release(["write"])` never runs.

Because `writer.saveJoint()` is the single choke point used to persist every unit accepted by the node — normal payments, asset issuance/transfer, AA responses (`aa_composer.js` line 1831 calls `writer.saveJoint` while itself under the `"aa_triggers"` lock) — permanently starving the `"write"` key stalls **all** future unit writes network-wide: `mutex.lock(["write"], ...)` calls from `network.js`, `composer.js`, `divisible_asset.js`, `indivisible_asset.js`, `joint_storage.js`, `main_chain.js`, etc. all queue forever in `arrQueuedJobs` and are never serviced.

The same pattern exists in `aa_composer.js`: `handleAATriggers()` takes the `"aa_triggers"` lock and only calls `unlock()` in the final callback of the `async.eachSeries` loop: [5](#0-4) 
`handlePrimaryAATrigger()`, invoked per row inside that locked series, itself contains a `throw Error` reachable if cached unit props are missing: [6](#0-5) 
and it delegates to `handleTrigger()`, which contains dozens of additional `throw Error(...)` calls (e.g. `validateAndSaveUnit`'s `ifJointError`/`ifTransientError`/`ifNeedHashTree`/`ifNeedParentUnits` handlers) that fire while the internally composed AA-response unit is (re)validated — all still inside the `"aa_triggers"` lock: [7](#0-6) 

Any such throw during AA-trigger processing leaves the `"aa_triggers"` key permanently locked, so `handleAATriggers()` is never called again for any future stabilized MCI (it is invoked from `writer.js` and `main_chain.js` after every stabilization), permanently freezing execution of every AA in the system, not just the one that misbehaved.

### Impact Explanation
Both scenarios collapse to the same outcome contemplated by the validation criteria — "a network unable to confirm new units" and "AA fund loss or freezing": once the `"write"` (or `"aa_triggers"`) lock is orphaned, the node keeps its process alive, keeps accepting P2P connections, and continues to respond to non-write requests, but it can never again persist a new unit or execute a pending AA trigger. This is a silent, total halt of core consensus-relevant functionality that is indistinguishable from a healthy node from the outside (mirroring the `isRunning() == true` while stalled behavior in the original report), until an operator notices and restarts the process. Funds already routed into `aa_triggers` cannot be processed (frozen), and no unit — from any user — can be confirmed thereafter.

### Likelihood Explanation
Reaching one of these `throw` statements requires attacker-controlled unit/trigger content to violate an invariant that `writer.js`/`aa_composer.js` assume was already enforced by `validation.js`, but which is checked again independently at write time from the live DB state (e.g. `determineInputAddressFromSrcOutput`'s src-output lookups, or `handlePrimaryAATrigger`'s stable-unit cache lookup). Any TOCTOU gap between validation and write (concurrent writers, cache eviction, edge cases in multi-author payment composition, or an oscript-composed AA response that trips an unexpected validation branch such as `ifTransientError`/`ifNeedHashTree`) is sufficient to trigger a permanent lock leak. Given the sheer number of `throw Error` call sites (30+ in `writer.js` alone, more than a dozen reachable from `handleTrigger`) executed while holding a global serialization lock, and the fact that these are ordinary defensive assertions rather than hardened, mutex-safe error paths, the likelihood that at least one is reachable by adversarial unit/trigger crafting is non-negligible, matching a Medium severity classification consistent with the CVSS 6.5 of the analog.

### Recommendation
Wrap the entire body of `writer.saveJoint()` and `aa_composer.handleAATriggers()`/`handlePrimaryAATrigger()`/`handleTrigger()` so that any thrown exception is guaranteed to route through the `unlock()` callback before propagating (e.g., a top-level `try/catch` around the locked `proc` in `mutex.exec()` that always calls `unlock()` on catch and rethrows afterward, or wrapping each locked callback body in a `try { ... } catch(e) { unlock(); throw e; }`). Alternatively, make `mutex.exec()` itself defensive: install a `try/finally`-style guarantee that `release(arrKeys)` runs even if `proc` throws synchronously, and surface a diagnosable error rather than silently orphaning the lock.

### Proof of Concept
Conceptual PoC (cannot be executed without live test infra):
1. Craft a multi-authored unit whose `payment` message references a `transfer` input (`unit`, `message_index`, `output_index`) that passes `validation.js`'s checks at validation time but, due to a race with a concurrent conflicting write or a stale/evicted cache entry, no longer matches a single unspent output row when `writer.saveJoint()`'s `determineInputAddressFromSrcOutput` re-queries the DB.
2. When `writer.saveJoint()` executes this code under the `"write"` mutex lock, the query returns 0 or >1 matching rows and `throw Error("src output not found")` (or `"multiple src outputs found"`) is thrown synchronously inside the DB callback.
3. Because this throw occurs inside `mutex.exec()`'s `proc(unlock)` invocation without ever calling `unlock`, `release(["write"])` is never called; `"write"` remains in `arrLockedKeyArrays` forever.
4. Every subsequent `mutex.lock(["write"], ...)` call anywhere in the node (any new payment, asset transfer, AA response) is pushed into `arrQueuedJobs` and never executed — the network can no longer confirm any new units.
