### Title
Webhook Signature Verified Against `repository.owner.login`, But Event Handlers Dispatch On the Independent `repository.full_name` Field — Cross-Organization Forged Webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook's HMAC against using the organization login embedded in the payload's `repository.owner.login` (or `organization.login`) field. All event handlers, however, resolve the target `Repository`/`Stack` to act on using a *different*, independently-controlled payload field: `repository.full_name`, parsed with a naive `owner/name` split and no cross-check against the organization that produced a valid signature.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) 

`repository_owner` extracts the org login used to fetch `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is used to HMAC-verify the *entire* raw request body via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once the signature check passes, `create` dispatches the full, attacker-authored payload to handlers: [4](#0-3) 

Every handler resolves the target repository independently via `Handler#repository_name`, which reads `repository.full_name` — a completely separate JSON path from the one used for signature/org selection: [5](#0-4) 

`Repository.from_github_repo_name` then does a plain string split and DB lookup with no verification that the org portion matches the org whose secret validated the signature: [6](#0-5) 

Shipit is explicitly multi-tenant: `config/secrets*.yml` supports multiple independently configured GitHub orgs, each with its own `webhook_secret`, as shown in the fixture configuration: [7](#0-6) 

**The broken binding (as an equality):**
`organization whose webhook_secret validated the HMAC (derived from repository.owner.login / organization.login)` == `organization that owns the repository the handler actually writes to (derived from repository.full_name)`.

Before the attack: for a legitimate GitHub-originated webhook, these two fields are always consistent because GitHub itself populates the payload.

After the attack: an entity that controls (or has obtained) the `webhook_secret` for **any one** organization configured in the Shipit instance (e.g. `OrgOne`) can hand-craft a raw JSON payload where `repository.owner.login = "OrgOne"` (so `verify_signature` picks `OrgOne`'s secret and the HMAC passes) while `repository.full_name = "OrgTwo/some-repo"` (an entirely different, unrelated tenant's repository tracked by the same Shipit instance). The handler layer never re-validates that `full_name`'s owner segment matches the organization that authenticated the request.

### Impact Explanation
This is a cross-tenant confused deputy: an attacker who legitimately controls one org's GitHub App webhook secret in a multi-org Shipit deployment can forge `push`, `status`, `check_suite`, `pull_request`, or `membership` events attributed to a different organization's repository/stack that they do not control. Depending on the handler, this can:
- Trigger `GithubSyncJob` / `stack.sync_github` for another tenant's stack via `PushHandler`.
- Inject or manipulate commit statuses on another tenant's commits via `StatusHandler`, potentially unblocking CI-gated deploys.
- Drive `pull_request` handlers that affect merge-queue state and review-stack provisioning for repositories outside the attacker's organization.

This is a cross-repository/cross-tenant write achieved purely by forging a webhook body, without needing the target organization's own webhook secret — matching the "Critical: cross-repository writes" impact bucket.

### Likelihood Explanation
Requires only that the attacker possesses (or can regenerate, as an admin of their own GitHub App/organization) the `webhook_secret` for **any one** tenant configured in the shared Shipit instance — a credential they legitimately hold for their own org, not a privileged Shipit credential and not the target org's secret. In any multi-org Shipit deployment (explicitly supported per `secrets_double_github_app.yml`), this is directly exploitable with a crafted HTTP POST to `/webhooks` and does not require a Shipit session, API token, or GitHub write access on the victim repository.

### Recommendation
After successfully identifying the organization/secret used for HMAC verification, require every handler's `repository_name`/`Repository.from_github_repo_name` resolution to enforce that the repository's owner matches the organization that authenticated the request (i.e., derive the target repo strictly from the same organization used in `verify_signature`, or explicitly assert `full_name.split('/').first == repository_owner` before dispatching to handlers).

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with a stack/repository tracked (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an entity that knows `OrgOne`'s `webhook_secret` (e.g. an `OrgOne` GitHub App admin), craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC_SHA1(OrgOne_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully verifies the signature [1](#0-0) .
6. `PushHandler#process` resolves `stacks` via `repository_name` = `"OrgTwo/victim-repo"` [5](#0-4)  and triggers `stack.sync_github` on `OrgTwo`'s stack — despite the request never being authenticated by `OrgTwo`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
