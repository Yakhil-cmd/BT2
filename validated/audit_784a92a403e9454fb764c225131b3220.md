### Title
Webhook signature is verified against `repository.owner.login`, but events are processed against an unbound `repository.full_name` / `sha`, allowing cross-tenant status/stack forgery — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the `webhook_secret` used to verify `X-Hub-Signature`) using `repository_owner`, a value read directly from the unverified JSON payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Once the signature check passes, the *entire raw payload* — including fields never covered by the owner-based key selection — is dispatched to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

Handlers do not re-verify that the field they act on belongs to the organization whose secret was used to authenticate the request:
- The generic `Handler` base class resolves the target `Stack`s via `payload.dig('repository', 'full_name')`, a *different* payload field than the one used for signature-key selection (`repository.owner.login`). [4](#0-3) 
- `StatusHandler` is worse: it does not scope by repository or organization at all — it looks up commits globally by `sha` across the whole Shipit instance and calls `commit.create_status_from_github!(params)`. [5](#0-4) 

This is the same bug class as the UniV3 report: the value that is cryptographically bound/authenticated (`repository.owner.login`, checked against a webhook secret) is not the value the code subsequently trusts and acts upon (`repository.full_name` for stack lookup, or a bare `sha` for status creation). The equality that should hold — "organization whose secret signed the request == organization/repository the handler writes to" — is never enforced.

### Finding Description
Shipit explicitly supports multiple, independently configured GitHub Apps/organizations sharing one webhook endpoint, each with its own `webhook_secret`: [6](#0-5) [7](#0-6) 

For every inbound webhook, `verify_signature` picks the `GitHubApp` (and therefore the secret) solely from the attacker-suppliable `repository.owner.login` (or `organization.login`) field of the JSON body:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [8](#0-7) 

Because the attacker fully controls the raw JSON body (it's just re-parsed with `JSON.parse(request.raw_post)`), they can pick which organization's secret is used for verification simply by setting `repository.owner.login` to an organization they legitimately control (i.e., their own tenant registered in a multi-org Shipit deployment, whose `webhook_secret` they configured themselves and therefore know). The rest of the payload — `repository.full_name`, `sha`, `check_suite.head_sha`, etc. — is never checked against that same organization.

Concretely:
- `Handler#stacks` resolves the affected `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, independent of `repository.owner.login` used for signing. [4](#0-3) 
- `StatusHandler#process` performs `Commit.where(sha: params.sha)` with no repository/organization scoping whatsoever, then calls `commit.create_status_from_github!(params)` on whatever commit(s) match that SHA, anywhere in the Shipit instance. [9](#0-8) 
- `create_status_from_github!` persists a GitHub-style status (`state`, `context`, etc.) onto the commit. [10](#0-9) 
- That status feeds directly into deploy-gating logic: `Commit#deployable?` requires `success? && !blocked?`, and `blocked?`/`blocking?` are computed straight from the stored `Status` records. [11](#0-10) [12](#0-11) 
- A transition to a passing/blocking-clearing state also enqueues `ProcessMergeRequestsJob` for the affected stack, i.e. it can push the merge queue forward. [13](#0-12) 

Similarly, `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers all key off `repository.full_name` (or `params.repository.full_name`) to resolve the target `Stack`/`Repository`, none of which is checked against the verified `repository.owner.login`. [14](#0-13) [15](#0-14) [16](#0-15) 

### Impact Explanation
Any tenant of a multi-organization Shipit deployment — who legitimately knows only their own organization's `webhook_secret` (because they configured that GitHub App installation themselves) — can forge a validly-signed webhook whose `repository.owner.login` matches their own org (so signature verification passes), while every other field in the body (`repository.full_name`, `sha`, `check_suite.head_sha`, etc.) targets a completely different, victim organization/repository tracked by the same Shipit instance.

The most severe consequence is via `status` events: because `StatusHandler` performs no repository/owner scoping at all, an attacker can fabricate a `success` status for any commit SHA anywhere in the instance (SHAs of victim commits are typically public on GitHub). This directly manipulates `Commit#deployable?` and blocking-status computation, which can unblock/trigger automatic continuous delivery or merge-queue progression for a repository the attacker has no access to — i.e., an unauthorized deploy/merge action on another tenant's stack, without the attacker ever needing that tenant's GitHub credentials, `ApiClient` token, or write access to the victim repository. This matches the "unauthorized deploy" / "cross-repository writes" Critical-impact category.

### Likelihood Explanation
This requires: (1) the host deployment uses Shipit's documented multi-organization GitHub App configuration (explicitly supported and documented), and (2) the attacker controls at least one such organization's own webhook secret — which is true by construction, since any tenant configuring their own GitHub App knows their own secret. No privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is required; the attacker only needs to know a target commit SHA, which is generally public information on GitHub. This is a realistic, low-effort attack path for any registered multi-tenant deployment.

### Recommendation
Bind the fields the handlers act upon to the field used for signature verification: after resolving `github_app`/`organization` from `repository.owner.login`, `WebhooksController` (or each `Handler`) should re-derive the repository/stack from that same verified organization and reject/ignore the payload if `repository.full_name`'s owner segment does not match `repository_owner`. `StatusHandler` in particular must scope its `Commit` lookup by the repository (and by extension the verified organization), not merely by `sha`, before applying `create_status_from_github!`.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config: `OrgA` (attacker-controlled tenant, webhook_secret known to attacker) and `OrgB` (victim org, tracked stacks/commits) both configured under `Shipit.github`. [6](#0-5) 
2. Attacker observes a commit SHA on a victim `OrgB` repository stack tracked by Shipit (public GitHub SHAs are easily discoverable).
3. Attacker crafts a `status` webhook JSON body:
   ```json
   { "repository": {"owner": {"login": "OrgA"}}, "sha": "<victim-sha>", "state": "success", "context": "ci/blocking-check" }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` — a value they can legitimately compute because they own `OrgA`'s secret.
5. POST to `/github/webhooks` (or the mounted webhook path) with `X-Github-Event: status`.
6. `verify_signature` resolves `github_app = Shipit.github(organization: "OrgA")` and confirms the signature — passes. [1](#0-0) 
7. `StatusHandler#process` runs `Commit.where(sha: "<victim-sha>")` — finds the victim's commit in `OrgB`'s stack (no ownership check) — and calls `commit.create_status_from_github!(params)`, marking it `success`. [9](#0-8) 
8. `Commit#deployable?`/`blocked?` now reflect the forged status, potentially unblocking deploy/merge automation for `OrgB`'s stack that the attacker has no legitimate access to. [11](#0-10)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
