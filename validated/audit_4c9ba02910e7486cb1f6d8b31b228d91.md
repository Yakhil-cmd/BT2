### Title
Webhook signature verification is keyed on `repository.owner.login`, but the resulting GitHub App identity is trusted implicitly across all its configured organizations while the acted-upon repository is taken from `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to use for verifying `X-Hub-Signature` by looking up `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository', 'owner', 'login')`. This selects a `GithubApp` config among possibly several configured organizations (see `test/dummy/config/secrets_double_github_app.yml`, which shows Shipit supporting multiple, independently configured organizations, e.g. `OrgOne`/`OrgTwo`). The handler that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`) resolves the target `Repository`/`Stack` using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. ### Finding Description
The equality that this control is supposed to enforce is:

`organization authenticated via verify_webhook_signature == organization that owns the repository being written to`

In practice the code breaks this down into two independent lookups against the *same* raw JSON body:
1. `repository_owner` (`repository.owner.login` or `organization.login`) is used only to pick *which webhook secret* to verify the signature with (`Shipit.github(organization: repository_owner)` → `github_app.verify_webhook_signature`). [1](#0-0) 
2. `repository.full_name` is used later by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) to look up the actual `Repository`/`Stack` to mutate. [3](#0-2) [4](#0-3) 

Because Shipit can be configured with multiple GitHub App installations/organizations (`test/dummy/config/secrets_double_github_app.yml` demonstrates two orgs, `OrgOne` and `OrgTwo`, each with their own `webhook_secret`/`private_key`), the signature-verification step trusts *whichever organization's secret validates the raw body*, but never checks that this organization actually owns the repository named in `repository.full_name` that the handlers subsequently act on. `verify_webhook_signature` in `lib/shipit/github_app.rb` returns `true` unconditionally when `webhook_secret` is blank for that org's config, and otherwise only proves the sender knows *that particular org's* secret — it says nothing about which repository the payload claims to touch. [5](#0-4) 

This matches the bug class described in the external report: the code computes/verifies against one attribute of the data structure (here, the org used to pick the HMAC key) while the state-mutating logic downstream consumes a *different, unverified-for-consistency* attribute of the same structure (the repository's `full_name`). In the Saddle Finance report, `idealBalance` was computed from `self.balances` (pre-trade, unadjusted) instead of `_xp(self, newBalances)` (the actual post-trade/decimals-adjusted balances used to compute fees on), i.e., two logically-related-but-distinct values were conflated. Here, "the organization whose key validates the payload" and "the organization whose repository is subsequently written to" are treated as if verifying the former also authorizes the latter, when they are two independent JSON fields with no cross-check.

### Impact Explanation
If any org with a webhook configured on this Shipit instance has a weak or blank `webhook_secret` (or an attacker otherwise obtains that org's `webhook_secret`, e.g. through misconfiguration on one of several tenants), they can forge a payload whose `repository.owner.login` matches that weak/known org but whose `repository.full_name` names a *stack belonging to a different, better-secured organization*. Because `verify_signature` only checks the org derived from `repository.owner.login`, and the handler layer trusts `repository.full_name` independently, this would let an attacker who only controls one organization's webhook secret drive github-sync / status / check-run behavior against another organization's `Stack` (cross-organization webhook confusion), which is the "organization authenticated versus the repository that is written" trust binding called out as in-scope.

Concretely, `PushHandler` would call `stack.sync_github(expected_head_sha: params.after)` on any not-archived stack matching the branch of the spoofed `repository.full_name`/`ref`, and `StatusHandler`/`CheckSuiteHandler` would write commit statuses/check runs for commits under the spoofed repository — all without ever verifying that the org used for signature verification actually owns that repository.

### Likelihood Explanation
This requires the operator to have configured Shipit with **multiple** GitHub organizations/apps (a supported, documented configuration per `test/dummy/config/secrets_double_github_app.yml`) and for at least one of those organizations to have a weak, blank, or otherwise attacker-known `webhook_secret`. It is not exploitable in the common single-organization deployment, since there the only org whose secret can verify the signature also happens to be the one that owns the repositories. This is a real gap in the code's design (no explicit repository-ownership check tying the verified org to the acted-upon `repository.full_name`), but its likelihood in a real deployment is conditional on multi-org configuration plus a weak/leaked secret for one tenant — I could not find any code path that cross-validates that `repository.owner.login` matches the organization owning the repository named by `repository.full_name` before dispatching to handlers, so the gap itself is confirmed, but a fully weaponized single-request PoC also requires that operator misconfiguration.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after successfully verifying the signature, additionally verify that `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))&.owner`/organization matches `repository_owner` used to select the verifying `GithubApp`, and reject (422) the request if they diverge. This closes the gap where the org used to validate the HMAC and the org whose repository is subsequently written to are allowed to differ.

### Proof of Concept
Conceptual PoC (cannot be executed without a live multi-org deployment and cannot be validated beyond static review with tools available in this session):
1. Configure Shipit with two orgs as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (attacker-known/weak `webhook_secret`) and `OrgTwo` (victim org, strong secret, owns a tracked `Stack`).
2. Craft a `push` webhook payload where `repository.owner.login = "OrgOne"` (or `organization.login = "OrgOne"`) but `repository.full_name = "OrgTwo/victim-repo"` and `ref`/`after` point at attacker-controlled values.
3. Sign the raw body with `OrgOne`'s `webhook_secret` and send it to `POST /github/webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully validates the signature against `OrgOne`'s secret. [1](#0-0) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository', 'full_name')` = `"OrgTwo/victim-repo"` and calls `stack.sync_github` on `OrgTwo`'s stack. [4](#0-3) [3](#0-2) 

This is stated as a design-gap PoC derived from reading the verification and handler code paths; I was not able to run it in this environment, and did not find any compensating cross-org check in `app/controllers/shipit/webhooks_controller.rb` or `app/models/shipit/webhooks/handlers/handler.rb` that would prevent it.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
