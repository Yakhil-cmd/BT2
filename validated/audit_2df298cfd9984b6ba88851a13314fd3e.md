### Title
Missing Zero-Address Validation in Bridge KLAY Transfer Allows Permanent Burning of Bridge Reserves — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`BridgeTransferKLAY.sol` does not validate that the recipient address `_to` is non-zero in `_requestKLAYTransfer`. Any user can call `requestKLAYTransfer(address(0), ...)`, which locks their KLAY in the source bridge and causes the bridge operator to relay a `handleKLAYTransfer` call with `_to = address(0)` on the destination chain. In Solidity 0.5.6, a low-level `.call.value()` to `address(0)` succeeds silently, permanently burning KLAY from the destination bridge's reserves and consuming the handle nonce.

### Finding Description

`_requestKLAYTransfer` performs only two checks before emitting the `RequestValueTransfer` event and incrementing `requestNonce`:

```solidity
require(isRunning, "stopped bridge");
require(msg.value > _feeLimit, "insufficient amount");
```

There is no `require(_to != address(0))` guard. [1](#0-0) 

The public entry point `requestKLAYTransfer` passes `_to` directly to `_requestKLAYTransfer` without any validation: [2](#0-1) 

On the destination chain, `handleKLAYTransfer` executes the transfer via a low-level call:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

In Solidity 0.5.6, `address(0).call.value(x)("")` returns `(true, "")` because `address(0)` has no code — the call succeeds and the KLAY is permanently burned. The nonce is marked handled and cannot be replayed. [3](#0-2) 

The bridge operator in `node/sc/bridge_manager.go` relays all `RequestValueTransfer` events without filtering for zero-address recipients, passing `to` directly from the event into `HandleKLAYTransfer`: [4](#0-3) 

By contrast, `handleERC20Transfer` and `handleERC721Transfer` are protected because the underlying OpenZeppelin ERC20 `safeTransfer` and ERC721 `transferFrom` both revert on `address(0)`. Only the native KLAY path uses a raw low-level call that silently accepts `address(0)`. [5](#0-4) 

### Impact Explanation

An attacker (or any user) can repeatedly call `requestKLAYTransfer(address(0), value, extraData)` on the source chain, locking KLAY in the source bridge and causing the bridge operator to burn an equal amount of KLAY from the destination bridge's reserves. This depletes the destination bridge's KLAY liquidity, preventing legitimate users from completing their withdrawals. The handle nonce is consumed for each such request, and the burned KLAY is unrecoverable.

### Likelihood Explanation

The trigger is fully unprivileged — any externally owned account can call `requestKLAYTransfer` with `_to = address(0)`. The attacker sacrifices their own KLAY (locked on the source chain) to execute the attack, making it a griefing vector. The bridge operator has no on-chain mechanism to reject zero-address handle requests once the source-chain event is emitted.

### Recommendation

Add a zero-address guard in `_requestKLAYTransfer`:

```solidity
require(_to != address(0), "zero recipient address");
```

Equivalently, add the same guard in `requestKLAYTransfer` before delegating to `_requestKLAYTransfer`. The same guard should be added to `_requestERC20Transfer` and `_requestERC721Transfer` for defense-in-depth, even though the underlying token contracts currently revert on zero-address transfers.

### Proof of Concept

1. Deploy source and destination bridge contracts in lock/unlock mode (`modeMintBurn = false`).
2. Fund the destination bridge with 100 KLAY via `chargeWithoutEvent`.
3. Call `requestKLAYTransfer(address(0), 10 ether, "0x")` on the source bridge with `msg.value = 10 ether`.
4. The source bridge emits `RequestValueTransfer(KLAY, attacker, address(0), address(0), 10e18, 0, 0, "0x")`.
5. The bridge operator calls `handleKLAYTransfer(txHash, attacker, address(0), 10e18, 0, blockNum, "0x")` on the destination bridge.
6. `address(0).call.value(10e18)("")` returns `(true, "")` — 10 KLAY is burned from the destination bridge.
7. Destination bridge balance drops from 100 KLAY to 90 KLAY; nonce 0 is permanently consumed.
8. Repeat to drain the destination bridge reserves entirely.
