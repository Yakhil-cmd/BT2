### Title
Cross-repository status webhook forges deployable? on victim's commit via unscoped sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire database, without verifying that the sha belongs to the repository that authenticated the webhook. Because git commit SHAs are content-addressed and independent per repository, any GitHub org/repo can legitimately emit a signed `status` webhook for a sha that happens to match a commit belonging to a different, unrelated stack, flipping that victim commit's `Commit#deployable?` to `true`.

### Finding Description
The broken binding: the question states it as `repository_that_authenticated_webhook == repository_owning_the_matched_commit`, but the code never enforces this. `WebhooksController#verify_signature` only proves the payload was signed by the GitHub App belonging to `repository_owner` from the payload itself [5](#0-4) , i.e. it authenticates "this payload really came from GitHub for org X," not "org X owns the sha inside this payload." `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) , matching by `sha` alone with zero use of the `stacks`/`repository_name` scoping helper that every other repository-bound handler (`PushHandler`, `CheckSuiteHandler`) correctly uses [2](#0-1) .

Exploit flow: attacker owns `attacker/evil`, a legitimate GitHub repo with the Shipit GitHub App installed on their own org/account (satisfying `verify_signature` for `repository_owner = attacker`). They construct a commit (e.g., an empty-tree/no-diff commit with matching tree, parent, author, committer, and timestamps) whose SHA1 equals the victim stack's currently pending, unblocked commit — this is not a hash collision but an intended property of Git's content-addressing, fully reproducible by anyone who can see the victim commit's metadata (public repos, GitHub API). Attacker pushes this to their repo and fires a real `status` webhook with `state=success` from `attacker/evil`. `WebhooksController#verify_signature` passes because the signature is valid for `attacker`'s own installation. `StatusHandler#process` finds the victim's `Commit` row purely by matching `sha`, and calls `commit.create_status_from_github!(params)` [6](#0-5) , creating a `success` `Status` on the victim's stack for that commit. `Commit#deployable?` [7](#0-6)  then evaluates `success?` true, flipping `deployable?` from false to true for a commit the attacker never had review/CI control over in the victim repo.

None of the listed guards prevent this: `verify_signature` authenticates the sender org, not sha ownership; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of `sha`/`state`, not repository binding; `force_github_authentication`, `User#authorized?`, `require_permission!`, and `Shipit.github_teams` are irrelevant since this is an unauthenticated webhook path with no session/API client involved.

### Impact Explanation
A `status` webhook signed by one GitHub organization/installation writes a `Shipit::Status` row onto a `Commit` belonging to a completely different stack/repository, directly flipping `Commit#deployable?` to `true` [7](#0-6) . This is a payload for one repository mutating another repository's commit/stack state, which the rubric classifies as Critical. Downstream, `deployable?` gates `require_ci` deploy checks in `Api::DeploysController#create` [8](#0-7)  and drives continuous-delivery/merge automation (`add_status` schedules `stack.schedule_merges`, hooks fire `deployable_status`) [9](#0-8) , so a forged success status can enable an unauthorized deploy-readiness state or auto-merge trigger on a victim stack the attacker has no access to. The attack is repeatable against any victim commit whose sha the attacker can reproduce, and works across arbitrary unrelated tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: victim commit's `stack.ignore_ci?` is false and it's currently pending/unblocked (as stated). Attacker needs only their own GitHub repo with the Shipit GitHub App/webhook installed (a normal, unprivileged action any GitHub user can take by installing the app or configuring a webhook on their own repo, if Shipit's multi-org support is enabled) and the ability to construct a commit with identical git-object content/metadata to the victim's pending commit — feasible whenever that metadata is knowable (public commit, or a commit an attacker can otherwise infer author/committer/timestamps/parents/tree for). No secrets, sessions, or privileged roles required. This is fully attacker-controlled and repeatable per target commit.

### Recommendation
Scope `StatusHandler#process` to only update commits within the repository that authenticated the webhook, mirroring `PushHandler`/`CheckSuiteHandler`: query through `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` (or equivalent using `stacks.flat_map(&:commits).select`) instead of the global `Commit.where(sha: params.sha)`, ensuring the matched commit's `stack` belongs to the `Repository` resolved from the webhook payload's `repository.full_name`.

### Proof of Concept
In a minitest under `test/models/webhooks/handlers/status_handler_test.rb` (or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repositories: `victim/repo` (with a pending, unblocked `Commit` `victim_commit` with `sha: SHARED_SHA`, `stack.ignore_ci == false`) and `attacker/evil` (a `Repository`/`Stack` fixture representing the attacker's own repo, also containing a `Commit` with the same `sha: SHARED_SHA` — simulating the reproduced git object).
2. Assert precondition: `refute victim_commit.deployable?` (state is pending, not success).
3. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call({'sha' => SHARED_SHA, 'state' => 'success', 'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker' } } })` (bypassing signature verification, since it's a model-level test of the handler as `StatusHandler.call` is called post-verification in the real controller flow).
4. Reload `victim_commit` and assert `assert victim_commit.deployable?` — demonstrating the sha-scoped, repository-agnostic lookup let a webhook claiming to be from `attacker/evil` flip `deployable?` on a commit belonging to `victim/repo`.
5. As a regression check for the fix, after scoping is added, assert the same webhook no longer changes `victim_commit`'s status/`deployable?` state (`refute victim_commit.reload.deployable?`), confirming the sha match is now constrained to `attacker/evil`'s own stack.
