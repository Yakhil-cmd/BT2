### Title
Webhook signature is verified against the organization's secret from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, letting an onboarded org forge events against any other repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the direct structural analog of the "approve() doesn't return what the caller assumes" bug class: the code assumes two different reads of the same payload agree with each other and never enforces that binding. Shipit's webhook signature check authenticates *which organization's secret was used*, but the handlers that decide *which repository/stack gets acted upon* read a completely separate JSON field that is never covered by that authentication check.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, which is read as `params.dig('repository', 'owner', 'login')`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` supports a multi-tenant configuration where each organization has its own independent `webhook_secret`, looked up via `github_app_config(organization)`: [3](#0-2) 

Once the signature passes, the raw JSON `params` are dispatched to registered handlers unmodified: [4](#0-3) 

But every handler built on `Shipit::Webhooks::Handlers::Handler` determines the target `Repository`/`Stack` using a *different* field of the same payload: `payload.dig('repository', 'full_name')`, not `repository.owner.login`: [5](#0-4) 

This same pattern is repeated explicitly in the pull-request handlers, e.g. `closed_handler.rb` resolves the acted-upon repository from `params.repository.full_name`: [6](#0-5) 

Nothing in the request pipeline checks that `repository.owner.login` (the value used to pick the signing secret) matches the owner encoded in `repository.full_name` (the value used to pick the target repository). The HMAC only proves the payload bytes were signed with *some* organization's configured secret - it says nothing about whether the repository object embedded in that payload actually belongs to that organization.

The binding that is broken, expressed as an equality that the code implicitly assumes but never enforces:
`organization_that_authenticated (repository.owner.login) == organization_of_repository_acted_on (repository.full_name.split('/').first)`

### Impact Explanation
An entity that has legitimately onboarded its own GitHub organization to a shared/multi-tenant Shipit instance (and therefore knows its own `webhook_secret`, exactly the role of an unprivileged-but-onboarded org admin - analogous to the ERC20 token holder who doesn't need special privilege to call `approve`) can craft a POST to `/webhooks` where:
- `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` picks their own known secret and the HMAC check passes),
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler resolves the real `Repository`/`Stack` belonging to a completely unrelated organization also hosted on the same Shipit instance).

Because `Repository.from_github_repo_name` and the various handler classes trust `full_name` unconditionally once the signature validates, this allows a cross-organization write into the victim's `Stack`/`Repository` state: e.g. forging `status` events to satisfy `ci.require`/`ci.blocking` checks that gate real deploys, forging `pull_request` closed/labeled/opened events to archive or otherwise mutate the victim's review stacks, or triggering `GithubSyncJob`/`RefreshCheckRunsJob` against the victim stack. Forged CI-status writes that satisfy deploy gating checks can lead to an unauthorized deploy - squarely in the Critical/High impact bucket (unauthorized deploy, cross-repository writes).

### Likelihood Explanation
This requires the deployment to actually be configured multi-tenant (multiple organizations each with their own `github.<org>.webhook_secret` entry, as supported by `github_app_config`/`github_organizations`). In that configuration, any organization admin who legitimately possesses their own webhook secret can reach this without any Shipit session, API token, or elevated privilege - purely by POSTing to the public `/webhooks` endpoint, matching the "unprivileged attacker" requirement. In a single-tenant deployment (one global `secrets.github` block, `github_default_organization` nil) this specific analog collapses because there is only one secret and no meaningful "organization that authenticated" distinct from "the app," so exploitability depends on the multi-tenant config path being used.

### Recommendation
After signature verification, cross-check that the organization implied by `repository.full_name` (or `organization.login` for org-scoped events) matches `repository_owner`/the organization whose secret validated the signature, and reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository` using `repository_owner` (the authenticated field) rather than trusting `full_name` independently in `Handler#repository_name`.

### Proof of Concept
1. Onboard organization `attacker-org` to the shared Shipit instance with its own configured `webhook_secret` (`S_attacker`), as an ordinary org admin would.
2. Build a `push` (or `pull_request`/`status`) webhook JSON body where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"` (a repository already tracked by Shipit for another tenant)
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, raw_body)>` using the known `S_attacker`.
4. POST to `/webhooks` with `X-Github-Event` set accordingly.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC check passes because it was signed with the correct (attacker's own) secret.
6. The dispatched handler calls `Repository.from_github_repo_name("victim-org/victim-repo")` and mutates/enqueues jobs against the victim's real `Stack`, even though the request was authenticated only for `attacker-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
