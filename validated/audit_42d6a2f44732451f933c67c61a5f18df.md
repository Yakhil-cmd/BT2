### Title
Unauthenticated `sender` binding in `StackStxOp`/`PreStxOp` allows an attacker to force-lock a victim's full STX balance with an attacker-chosen `reward_addr` and `num_cycles` - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::get_sender_txid` only validates that the `StackStxOp` Bitcoin transaction spends `vout == 1` of a prior `PreStxOp` transaction's `txid`; it never checks that the entity constructing either Bitcoin transaction possesses the private key of the Stacks address recorded in `PreStxOp.output`. Because `PreStxOp.output` is arbitrary attacker-chosen data in the `PreStxOp`'s own OP_RETURN/output encoding, an attacker who owns none of the victim's STX can name the victim as `sender`, and `process_stacking_ops` will then invoke `stack-stx` as if the victim authorized it, using attacker-chosen `stacked_ustx`, `num_cycles`, and `reward_addr`.

### Finding Description
The claimed equality is: **the party who chooses the reward-cycle lock duration (`num_cycles`) and the reward Bitcoin address (`reward_addr`) for a `stack-stx` lock == the STX owner who authorized locking their funds (`sender`)**.

Trace of the code path:
1. `PreStxOp::parse_from_tx` sets `output` directly from `outputs.get(0).address` of the raw Bitcoin transaction with no signature or proof-of-ownership check tying that address to the transaction's actual signer/inputs: [1](#0-0) 
2. When a `StackStxOp` Bitcoin transaction is decoded, `StackStxOp::get_sender_txid` only enforces that input 0 references `vout == 1` of some prior txid - it never verifies any relationship between the signer of this input and the `PreStxOp.output` address: [2](#0-1) 
3. `burnchain.rs` resolves `sender` purely as `pre_stack_stx.output` (attacker-controlled data from step 1) and feeds it into `StackStxOp::from_tx`: [3](#0-2) 
4. `StackStxOp::parse_from_tx` takes `reward_addr` from the `StackStxOp` transaction's own first output (again fully attacker-controlled), and `stacked_ustx`/`num_cycles` from the OP_RETURN payload (attacker-controlled): [4](#0-3) 
5. `StacksChainState::process_stacking_ops` then invokes the active PoX contract's `stack-stx` entry point with `tx-sender` forced to `sender` (the attacker-named victim address), under `ResourceBudget::unlimited()`, bypassing normal transaction signature/nonce authentication entirely: [5](#0-4) 
6. Inside `stack-stx` (pox-4/pox-5), the only authorization gate is a balance check on `tx-sender`, with no signature or consent check from the actual STX owner: [6](#0-5) 

Root cause: the "sender" identity for burnchain-triggered `stack-stx` calls is derived solely from Bitcoin-transaction structure chosen entirely by whoever crafts the `PreStxOp`/`StackStxOp` pair, with zero cryptographic binding to the named Stacks account's private key. None of `check-pox-lock-period`, `verify-signer-key-grant` (only gates `signer_key`, not `sender`), or the `<=`/balance guards address this, because they all assume `tx-sender` was already authenticated - an assumption that holds for normal signed Stacks transactions but not for this burn-op path.

Attacker's exact call: attacker crafts a Bitcoin transaction #1 (`PreStxOp`) whose first output decodes to the victim's Stacks address, using attacker's own UTXOs to pay for/sign it. Attacker then crafts Bitcoin transaction #2 (`StackStxOp`) that spends `vout=1` of transaction #1, with OP_RETURN payload `stacked_ustx = victim_full_balance`, `num_cycles = N` (attacker's choice), and first output = attacker-controlled Bitcoin/PoX address. No signature from the victim's Stacks key is anywhere required.

### Impact Explanation
The victim's entire spendable STX balance is locked via the PoX contract's internal `stx-lock`/`stx-account` mechanism as if the victim had called `stack-stx` themselves, for a lock duration chosen by the attacker, with the reward-eligible PoX address set to one the attacker controls, so any BTC rewards for that cycle's signer slot accrue to the attacker instead of the victim. This is a permanent-until-unlock-height freeze of victim funds combined with a reward-destination hijack, matching "Critical - permanent freezing of staked STX" and "reward slots ... exceeding locked value" (since the victim never authorized or benefits from the lock). It is repeatable against any address with a positive STX balance that is not already stacking or delegating, at the cost of only a small Bitcoin transaction fee.

### Likelihood Explanation
Preconditions: the victim address must have a non-zero STX balance, must not currently be in `stacking-state`, and must not be delegating (`get-check-delegation` is none) - both routine states for the vast majority of STX holders. No reward-cycle/prepare-phase gating exists in `pox-4.clar`/`pox-5` that specifically blocks this path, and the attack requires only ordinary Bitcoin transaction construction skills plus a small amount of BTC for fees, well within the stated attacker capability of "craft burnchain stacking ops from their own Bitcoin inputs." This makes the attack cheap, fully attacker-controlled in timing, and repeatable against many victim addresses.

### Recommendation
Require the `StackStxOp`/`PreStxOp` `sender` to be authenticated against the actual Bitcoin input signer (e.g., derive `sender` from the public key(s) that signed the `PreStxOp`/`StackStxOp` inputs, as is already done for `VoteForAggregateKeyOp::get_sender_pubkey`, rather than trusting an arbitrary declared output address), or require an explicit Stacks-signature attestation from the named `sender` address to be embedded and checked before `process_stacking_ops` executes the `stack-stx` call on their behalf.

### Proof of Concept
Rust integration test plan (extending existing tests in `stackslib/src/burnchains/tests/db.rs` and `stackslib/src/chainstate/stacks/db/blocks.rs` stacking-ops tests):
1. Create `victim_addr` (funded via genesis/faucet, never used for stacking) and `attacker_addr`/`attacker_btc_keys` (attacker's own Bitcoin keys, no STX at `victim_addr`).
2. Build a `PreStxOp` Bitcoin transaction signed/funded entirely by the attacker, with `output = victim_addr`.
3. Build a `StackStxOp` Bitcoin transaction spending `vout=1` of the `PreStxOp` txid, signed by the attacker, with OP_RETURN `stacked_ustx = victim's full balance`, `num_cycles = attacker_chosen_N`, and first output = `attacker_btc_pox_addr`.
4. Feed both burnchain ops through `StacksChainState::process_stacking_ops` in a test chainstate.
5. Assert before/after: `stx-account(victim_addr).locked == victim_full_balance` and `stx-account(victim_addr).unlock-height == burn_height + N*cycle_length` (LOCK CONSERVATION/SINGLE UNLOCK violated because victim never called `stack-stx`).
6. Assert `get-stacker-info(victim_addr).pox-addr == attacker_btc_pox_addr` (reward address diverges from the STX owner's choice).
7. Advance chain to the relevant reward cycle and assert PoX/burnchain rewards for that cycle's slot for `attacker_btc_pox_addr` are payable to the attacker, while `victim_addr`'s STX remains locked and inaccessible to the victim until `unlock-height`.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
