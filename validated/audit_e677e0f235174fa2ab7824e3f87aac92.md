### Title
`ReviewStack#env`'s PR-label-derived keys bypass `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` and reach `TaskCommands#env` unfiltered - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::DeploySpec#filter_deploy_envs`/`filter_rollback_envs` are only ever applied to the persisted `Task#env` value at deploy/rollback-creation time in `Stack#build_deploy`, never to the value returned by `Stack#env`/`ReviewStack#env`. `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` injects one `LABEL_NAME.upcase => "true"` pair per PR label) directly into the process environment with no allowlist check, so any label an attacker can attach to their own PR becomes an arbitrary-named environment variable for every task run against that review stack.

### Finding Description
The claimed binding is: `Command#unbundled_env keys == filter_deploy_envs(@task.env) ∪ deploy_spec.machine_env` (with no unfiltered `@stack.env` contribution). Tracing `TaskCommands#env`: [1](#0-0) 

shows the actual composition is `super (base_env) .merge(@stack.env) .merge({SHIPIT_USER, EMAIL, ...}) .merge(deploy_spec.machine_env) .merge(@task.env)`. `@stack.env` for a `ReviewStack` is: [2](#0-1) 

which merges `Stack#env`'s base keys with one entry per `pull_request.labels` element (`LABEL.upcase => "true"`), with no filtering against `deploy_variables`/`rollback_variables`.

`filter_deploy_envs`/`filter_rollback_envs` are defined as thin wrappers around `EnvironmentVariables#permit(deploy_variables)`: [3](#0-2) 

but the only call sites are `Stack#build_deploy`, which filters the env supplied when *creating* a `Deploy` record (i.e., what becomes `@task.env`): [4](#0-3) 

and `Stack#trigger_task`, which filters via `definition.filter_envs`. Neither this filtering nor any other call to `filter_deploy_envs`/`filter_rollback_envs` touches `Stack#env`/`ReviewStack#env`. So `@stack.env`'s label-derived keys reach `TaskCommands#env` (and therefore `Command#unbundled_env` / `PTY.spawn`) completely unfiltered, contradicting the claimed binding.

Attacker path: an unprivileged GitHub user who owns/controls a repository that has a `ReviewStack` configured in Shipit opens or updates a pull request and attaches a label with an arbitrary name (e.g., `RUBYOPT`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`, or any variable name of the attacker's choosing). GitHub's `pull_request` webhook (`labeled`/`opened`/`reopened`/`unlabeled` actions) is handled by `LabelCapturingHandler#capture_labels`, which stores `pull_request.labels.map(&:name)` verbatim on the `PullRequest` record: [5](#0-4) 

No allowlist or format restriction is applied to label names at capture time. On the next deploy/rollback/task for that review stack, `ReviewStack#env` re-derives the injected variable and it flows unfiltered into `TaskCommands#env`, landing in the shell environment used by `Command`/`PTY.spawn` on the deploy host, ahead of (and potentially overridable-but-also-able-to-precede) `deploy_spec.machine_env` and `@task.env`. Existing guards (`verify_signature`, `ExplicitParameters` schema requiring `labels.name` be a `String`, `Repository` validations) only constrain webhook authenticity and payload shape - none of them constrain the label *name* to the deploy spec's declared `deploy`/`rollback` variables, so they do not close this gap.

### Impact Explanation
An attacker who controls a repository with an active `ReviewStack` can set an arbitrary-named environment variable (value fixed to `"true"`) in the process environment of every deploy/task command run for that stack, without it being declared in `deploy.variables`/`rollback.variables` in `shipit.yml`. If the injected variable name collides with a security-sensitive one not otherwise set by `deploy_spec.machine_env` or `@task.env` (e.g. `RUBYOPT`, `GIT_SSH_COMMAND`, `BUNDLE_GEMFILE`, `LD_PRELOAD`), this can influence or hijack execution of `git`/`bundler`/deploy-step commands invoked via `Command`/`PTY.spawn` on the deploy host, which matches the Critical category ("RCE on the deploy host via `Command`/`PTY.spawn`"). The blast radius is scoped to the attacker's own repository's review stacks (each ReviewStack derives from its own PR), so it is not a cross-tenant stack takeover, but it is fully repeatable per pull request/label the attacker controls.

### Likelihood Explanation
Preconditions: the target repository must have Shipit review stacks enabled and a valid webhook configured (standard Shipit setup, not attacker-controlled secrets). The attacker needs only the ability to label a pull request in a repository they control - trivial and requires no Shipit credentials, session, or API token. This is low-cost and fully repeatable on demand.

### Recommendation
Apply `deploy_spec.filter_deploy_envs` / `filter_rollback_envs` (or an equivalent allowlist keyed off `deploy_variables`/`rollback_variables`) to `Stack#env`/`ReviewStack#env`'s contribution before it is merged in `TaskCommands#env`, or stop merging raw `@stack.env` into the task environment and instead route all PR/label-derived values through the same `VariableDefinition`-validated path used for `@task.env`.

### Proof of Concept
In `test/lib/shipit/task_commands_test.rb` (or a new test), construct a `ReviewStack` with a `pull_request` whose `labels` include an arbitrary name not present in the stack's `deploy_spec.deploy_variables` (e.g. `["RUBYOPT"]`), build a `Deploy`/`Task` against it, and assert:

```ruby
env = Shipit::TaskCommands.new(task).env
assert_not_includes deploy_spec.deploy_variables.map(&:name), "RUBYOPT"
assert_equal "true", env["RUBYOPT"] # currently passes -> unfiltered injection confirmed
```

The second assertion currently succeeds even though `"RUBYOPT"` is absent from `deploy_variables`, demonstrating that `filter_deploy_envs` is never applied to this contribution.
