### Title
Webhook signature verification selects the signing organization from an unauthenticated payload field, decoupled from the repository the event handler actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App's `webhook_secret` to HMAC-verify against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unauthenticated JSON body, before the signature has been checked. The event handlers that subsequently mutate state (e.g. `PushHandler`, `StatusHandler`, any handler inheriting from `Shipit::Webhooks::Handlers::Handler`) instead resolve the target `Repository`/`Stack` from a *different* attacker-controlled field, `repository.full_name`. Nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository being written to.

### Finding Description
In a multi-organization Shipit deployment (explicitly supported — `Shipit.github_app_config`/`Shipit.github_organizations` in `lib/shipit.rb:170-200`, one `GitHubApp`/`webhook_secret` per configured org), the controller does:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the raw, unverified body (`params` is parsed JSON of `request.raw_post`) purely to decide which org's `webhook_secret` to HMAC against; it never has to agree with anything else in the payload.

`GitHubApp#verify_webhook_signature` just checks that the signature matches `HMAC(secret_for(repository_owner), raw_body)`: [2](#0-1) 

Once verification passes, `Handler#process` (and subclasses like `PushHandler`) resolve the actual `Repository`/`Stack` to act on using a *separate* field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every matched, non-archived stack: [4](#0-3) 

The binding that should hold is:
`organization(repository.owner.login) == organization(repository.full_name.split('/').first)`

This equality is never checked. An attacker who legitimately owns/administers one Shipit-configured GitHub organization ("attacker-org", with its own known `webhook_secret`) can craft a webhook JSON body where `repository.owner.login = "attacker-org"` (so the signature is computed and verified against a secret they know) while `repository.full_name = "victim-org/victim-repo"` (the value the handler actually uses to look up and mutate state). The HMAC covers the raw body bytes, not any semantic binding between these two fields, so a validly-signed-by-attacker payload can still target another organization's `Stack`.

### Impact Explanation
This lets an authenticated-as-attacker (but not authorized-for-victim) party inject GitHub events — `push` (triggering `GithubSyncJob`/commit ingestion), `status` (writing commit `Status` rows used for deploy gating), `check_suite`, `membership`, `pull_request`/review-stack provisioning — against a victim stack/repository they do not own, entirely with payload content they fully control (fake SHAs, fake CI statuses, fake labels driving `archive!`/`unarchive!`). Fabricated `status`/`check_suite` events can flip deploy-gating checks (`respond_to_pull_request_opened?`, provisioning label checks) and influence merge/deploy decisions on the victim's stack. This crosses the "unauthorized... deploy" / cross-repository-write class of impact described in the rules.

### Likelihood Explanation
Requires the Shipit instance to host more than one GitHub organization (a documented, supported configuration in `lib/shipit.rb#github_app_config`/`#github_organizations`) and for the attacker to control at least one of those configured organizations' webhook secret (e.g., by being an admin of one org onboarded to the shared Shipit instance while targeting another org's stack on the same instance). This is a realistic scenario for shared/central Shipit deployments serving multiple orgs, but not applicable to single-organization deployments where the attacker has no way to obtain a valid `webhook_secret` at all.

### Recommendation
Verify the signature using the secret resolved from the *same* field the handler will trust for repository/organization resolution, and reject the request if `repository.owner.login` (or `organization.login`) does not match the owner segment of `repository.full_name` used by `Handler#repository_name`. Alternatively, resolve the signing GitHub App strictly from the `Repository`/`Stack` record already provisioned in Shipit's database (looked up via `repository.full_name`) rather than from a raw, unauthenticated payload field, so the org whose secret authenticates the request is always the org that owns the mutated resource.

### Proof of Concept
1. Shipit is configured with two orgs: `attacker-org` (secret known to attacker, e.g., they installed/administer the GitHub App) and `victim-org` (hosts a real `Stack` for `victim-org/victim-repo`).
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, raw_body)` themselves (they know this secret) and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and the HMAC matches → request passes verification (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) on the victim's stack — despite the request never being signed by `victim-org`'s GitHub App.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
