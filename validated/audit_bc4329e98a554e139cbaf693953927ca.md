## Title
Attacker-Triggered Uncaught `throw` in `aa_composer.js` During Deterministic AA Trigger Processing Causes Full Node Crash / Consensus Halt - (File: aa_composer.js)

### Summary
`aa_composer.handleTrigger()` and its helpers (`getTrigger`, `pickParents`, `handlePrimaryAATrigger`) contain multiple bare `throw Error(...)` statements that fire while processing an AA trigger — a unit that **any unprivileged user can post** simply by sending a payment/data message to an Autonomous Agent address. This mirrors the wire-webapp bug class (CVE-2022-39380): a piece of attacker-controlled content passes an earlier "shape" check but later trips an unhandled exceptional condition deep inside a rendering/processing pipeline, and because the error is never caught, it aborts the whole pipeline rather than being reported as a normal validation failure.

### Finding Description
AA triggers are processed from `handleAATriggers()`, which is invoked synchronously from the unit-writing/stabilization path in `writer.js` (`await aa_composer.handleAATriggers();`) every time a main-chain index stabilizes and a trigger is queued: [1](#0-0) 

`handleAATriggers()` iterates over queued triggers and calls `handlePrimaryAATrigger`, which calls `getTrigger()` and `handleTrigger()`: [2](#0-1) 

`getTrigger()` unconditionally throws when its output-selection logic can't find money sent to the receiving address: [3](#0-2) 

`handleTrigger()` itself throws in several places reachable from attacker-controlled AA definitions/state, e.g. when following a `base_aa` redirection whose target definition cannot be read: [4](#0-3) 
and inside `pickParents()`, which throws if an internally-computed invariant about `latest_included_mc_index` doesn't hold for the AA-response chain: [5](#0-4) 
`handleSecondaryTriggers()` also throws unconditionally if secondary triggers occur while the primary trigger is bouncing: [6](#0-5) 
and `handlePrimaryAATrigger`'s completion callback throws if a stable unit isn't found in the in-memory cache or if the RocksDB batch write fails: [7](#0-6) 

None of these `throw` statements are wrapped in a `try/catch` anywhere along the call chain from `writer.saveJoint()` → `main_chain.advanceMcStability()` → `aa_composer.handleAATriggers()` → `handlePrimaryAATrigger()` → `handleTrigger()`. Because these functions are deeply nested inside `async.eachSeries`/callback chains and only the outer call is `await`-ed, a synchronous `throw` fired from inside a callback becomes an **unhandled exception** that is not caught by the `await`, and in Node.js crashes the process (or, for unhandled promise rejections, does the same depending on Node version/flags).

Crucially, the trigger itself is fully attacker-controlled: any unprivileged user can post a unit that (a) sends a payment to an AA address whose current definition uses `base_aa`, or (b) creates conditions where cached/in-memory unit props are inconsistent with what `handlePrimaryAATrigger` expects (e.g. `storage.assocStableUnits[unit]` not yet populated due to a race, or an intentionally malformed getTrigger fallthrough). Because AA definitions and their `base_aa`/state logic can be defined and then redefined/removed in later units, an attacker can construct a scenario (posting a trigger to an AA whose base has been changed or removed) where the "should never happen" assumption baked into a `throw` actually happens, on every full node in the network simultaneously, since AA trigger execution is deterministic and run by all nodes as soon as the relevant MCI stabilizes.

### Impact Explanation
An unhandled exception during the deterministic AA-trigger execution path crashes the node process running `handleAATriggers()`. Since this logic is executed **synchronously with unit stabilization**, on every full node processing the DAG, a single malicious trigger crafted to hit one of these `throw` paths would crash every full node in the network as soon as the triggering unit and its MC stabilize — this is a network-wide denial of service that halts confirmation of new units for the whole network until the code is patched and old, stuck units are reprocessed, directly matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Reaching one of these `throw` statements requires crafting a specific AA/trigger state (e.g., certain `base_aa` chains, or races between AA redefinition and trigger arrival), which requires non-trivial understanding of AA composer internals, but no special privilege — only the ability to define an AA and post a payment/data unit to it, both fully available to any unprivileged user. Given the number of "should not happen" `throw` invariants scattered through `handleTrigger`/`getTrigger`/`pickParents`/`handlePrimaryAATrigger`, at least one edge case is plausibly reachable via a carefully sequenced AA definition + trigger, similar in spirit to how the wire-webapp bug required a specific combination of Markdown constructs to trip an unhandled parser branch.

### Recommendation
- Wrap the entire `handleAATriggers()` → `handlePrimaryAATrigger()` → `handleTrigger()` execution chain in a top-level `try/catch` that converts unexpected internal errors into a graceful bounce or a logged, recoverable failure rather than a process-crashing `throw`.
- Replace defensive "should never happen" `throw` statements in `getTrigger`, `pickParents`, and `handleSecondaryTriggers` with explicit validation earlier in the pipeline (at AA-definition/trigger-validation time) so malformed states are rejected before they reach unrecoverable code paths.
- Add integration/fuzz tests that post triggers against `base_aa` chains with missing/removed base definitions and against secondary-trigger/bounce races to confirm the composer degrades gracefully (e.g., bounces the trigger) instead of throwing.

### Proof of Concept
1. Define AA `X` with `base_aa` pointing to address `B`.
2. In a way that abuses timing/redefinition rules for `B` (e.g., `B`'s stored AA definition becomes unreadable via `readAADefinition` for the relevant `mci` due to a redefinition/removal edge case), post a payment trigger unit to `X`.
3. When the triggering unit's MCI stabilizes, all full nodes execute `aa_composer.handleAATriggers()` → `handleTrigger()`, which calls `storage.readAADefinition(conn, template.base_aa, mci, ...)`; if `arrBaseDefinition` is falsy, the code executes `throw Error("base AA not found: " + template.base_aa);` [8](#0-7)  uncaught, crashing every node's process simultaneously and halting the network's ability to confirm subsequent units.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
