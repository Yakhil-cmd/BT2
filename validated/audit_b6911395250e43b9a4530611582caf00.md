### Title
Team‑reuse due to missing `team.organization == params.organization.login` check combined with signature/handler field divergence enables cross‑organization membership escalation - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves a `Team` solely by `github_id` and never asserts that the resolved (possibly pre‑existing) team's `organization` matches the `organization.login` verified for the current request, then unconditionally calls `team.add_member(member)`. Because the controller's signature check and the handler's organization field are derived independently, an attacker who owns a legitimate GitHub organization (and therefore knows its own valid webhook secret) can submit a `membership` webhook whose signature is verified against their own org while the payload's `organization.login`/`team.id` reference a different, victim organization/team, silently attaching an attacker-controlled user to that victim team.

### Finding Description
The claimed binding is: `team.organization` (as persisted) **==** `params.organization.login` (as verified for the current request). Tracing the code shows this equality is never checked: [1](#0-0) 

`find_or_create_by!(github_id: params.team.id)` only runs the block (which sets `team.organization`) when creating a *new* record. If a `Team` with that `github_id` already exists, the existing row is returned as‑is — no comparison is made between the stored `organization` and the current payload's `organization.login` — and processing continues straight to: [2](#0-1) 

`team.add_member(member)` then unconditionally appends the membership: [3](#0-2) 

The exploit path that lets an attacker reach this with a *valid* signature exploits a second divergence in the controller. `verify_signature` derives the organization used to pick the webhook secret from `repository.owner.login` first, only falling back to `organization.login` if no `repository` key is present: [4](#0-3) 

The `MembershipHandler` params schema does not require or forbid a `repository` key — it only requires `action`, `team`, `organization`, `member`: [5](#0-4) 

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with the attacker's own organization's webhook secret (which they legitimately possess, since they own that org and installed Shipit's webhook there), and a JSON body containing:
- `"repository": {"owner": {"login": "attacker-org"}}` — read only by `repository_owner` for the signature check, so `Shipit.github(organization: "attacker-org")` is used and the attacker's own valid signature passes.
- `"organization": {"login": "victim-org"}` and `"team": {"id": <victim team's known github_id>, ...}` — read only by `MembershipHandler`, which never re-validates them against the verified organization.
- `"member": {"login": "attacker-controlled-account"}`, `"action": "added"`.

Because `find_or_create_team!` finds the pre-existing victim `Team` row (matched purely by `github_id`) without checking `team.organization == params.organization.login`, and `add_member` performs no additional authorization check, the attacker's chosen member is silently added to the victim's team — a team that may be present in `Shipit.github_teams` and thus confer elevated authorization.

None of the existing guards prevent this: `verify_signature` only proves the payload was signed by *some* org the attacker controls, not that the `organization`/`team` fields in the payload belong to that org; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross‑field/organization consistency; there is no `Repository`, `Stack`, or `require_permission!` check in this webhook path since membership events are not scoped to a repository.

### Impact Explanation
A successful request adds an attacker-chosen GitHub account as a member of an arbitrary pre-existing `Shipit::Team` row, independent of the organization whose secret validated the request. If that team's handle is listed in `Shipit.github_teams`, the attacker (or their accomplice account) gains the authorization tier granted to members of `Shipit.github_teams`, which per `Shipit::User` gates elevated privileges. This is repeatable against any `Team` github_id already known/tracked by the Shipit instance and is not limited to a single tenant — any organization the attacker legitimately controls can be used as the trusted signer while targeting any other tracked team. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category.

### Likelihood Explanation
Preconditions: the attacker must own/administer some GitHub organization that has Shipit's webhook installed (so they know a valid webhook secret for `Shipit.github(organization: attacker-org)`), and must know or guess the numeric `github_id` of a target team already present in Shipit's `teams` table (team IDs are often discoverable via GitHub's team API for teams the attacker can view, or via prior legitimate Shipit activity). No Shipit session, API token, or victim secret is required — only the attacker's own valid webhook secret and knowledge of a target `github_id`/organization login. The request is a single HTTP POST and fully repeatable/scriptable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that when an existing `Team` is found by `github_id`, its `organization` equals the currently verified `params.organization.login` (and ideally that this login also equals the organization used to verify the webhook signature, i.e. `repository_owner`), rejecting/logging mismatches instead of proceeding. Additionally, fix `WebhooksController#repository_owner` to not allow a spoofable `repository.owner.login` fallback that diverges from the `organization.login` actually consumed by downstream handlers, or require handlers to assert equality between the two fields explicitly.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (illustrative)
test "find_or_create_team! reuses an existing team regardless of organization mismatch" do
  victim_team = Shipit::Team.create!(
    github_id: 999, organization: "victim-org", name: "Committers", slug: "committers"
  )

  payload = {
    "action" => "added",
    "team" => { "id" => 999, "name" => "Committers", "slug" => "committers", "url" => "https://x" },
    "organization" => { "login" => "attacker-org" }, # mismatched org, never checked
    "member" => { "login" => "mallory" }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  # Binding under test: victim_team.organization ("victim-org") == payload["organization"]["login"] ("attacker-org")
  refute_equal victim_team.organization, payload["organization"]["login"]

  # Yet the pre-existing victim team was reused and mutated
  assert_equal victim_team, Shipit::Team.find_by(github_id: 999)
  assert Shipit::Membership.exists?(team: victim_team, user: Shipit::User.find_by(login: "mallory"))
end
```
This demonstrates the exact code-level flaw: `find_or_create_team!` never asserts `team.organization == params.organization.login`, allowing reuse of an existing team row for a mismatched/forged organization and silent membership escalation.
