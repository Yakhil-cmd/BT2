### Title
`calculate-rewards` attributes all pending sBTC rewards to whichever half-cycle happens to be active at call time, mis-crediting stakers from skipped cycles - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`calculate-rewards` in `pox-5.clar` is a permissionless, unprivileged public function that computes "the current distribution cycle" purely from elapsed burn-block-height at call time, exactly the "current epoch derived from elapsed time" pattern that caused M-3 in the external report. When the function is not called in every half-cycle window, all sBTC rewards that accrued across the skipped windows get permanently and irreversibly attributed to a single `stx-cycle`/bond period — the one immediately preceding the call — rather than split across the periods in which they actually accrued.

### Finding Description
`calculate-rewards` computes: [1](#0-0) 

`calculation-height` is derived from `current-distribution-cycle`, itself computed from `burn-block-height` at call time: [2](#0-1) 

The only guard against repeated computation is `(> calculation-height last-calc)` — this only prevents re-running the same window twice; it never checks that the immediately preceding half-cycle was the one processed in the previous call, i.e. it does not detect or reject skipped windows. `gross-accrued-rewards` is computed as `get-new-rewards`, which is *all* sBTC received since the last computation, regardless of how many half-cycles have elapsed: [3](#0-2) 

This entire `gross-accrued-rewards` amount (potentially spanning many skipped half-cycles) is then distributed to bonds and stakers using only `stx-cycle` (the reward cycle containing the *current* calculation-height) as the accounting bucket: [4](#0-3) 

Per-cycle share totals (`get-total-shares-staked-for-cycle`) are recorded historically per specific reward-cycle, so stakers who were staked in the skipped cycles are never credited via `rewards-per-token-for-cycle` for those cycles (their entries remain unset for that period), while whichever stakers happen to have shares recorded under `stx-cycle` (the current cycle at call time) receive the full lump sum of multi-cycle-accrued rewards, even if their stake only began in the current cycle.

### Impact Explanation
This breaks the reward-accounting equality that "each reward-cycle's stakers only receive rewards that accrued while they were staked." Rewards actually earned by past stakers (during skipped windows) are permanently lost to them (their `rewards-per-token-for-cycle` entries for those past cycles never get set, and once the map is written for `stx-cycle`, `last-reward-compute-height` advances past those windows, so they can never be retroactively computed) while stakers active only in the "current" cycle at call time are credited (and can withdraw via `claim-rewards`/`claim-staker-rewards-for-signer`) rewards they never earned. This is a double-counting / unearned sBTC reward payout for the "current" cycle's stakers and a permanent freezing of rewards owed to earlier-cycle stakers — matching the Critical impact bucket (sBTC rewards paid that were not earned, and permanent freezing of value never later paid to the rightful stakers).

### Likelihood Explanation
The trigger condition — `calculate-rewards` not being called in every half-cycle window — requires no privileged access; it is a permissionless public function, and there is no automatic/enforced-per-window invocation in the contract itself (the CalculateRewards test harness comment even acknowledges "Callable once per half-cycle," implying no on-chain guarantee it *is* called every half-cycle). Any delay in calling it (network congestion, lack of an incentivized keeper, or a staker strategically waiting to stake right before calling it themselves) causes the misattribution. An attacker seeking to profit only needs to observe that `calculate-rewards` hasn't been called for a while, then stake right at the start of the "current" half-cycle and call `calculate-rewards` themselves (permissionless) to sweep multiple cycles' worth of rewards into the cycle where their stake is recorded.

### Recommendation
`calculate-rewards` should iterate/settle each un-computed half-cycle/reward-cycle window individually (walking forward from `last-reward-compute-height` cycle-by-cycle) rather than assuming exactly one window has elapsed since the last call, similar to the report's recommendation of requiring an explicit target epoch/cycle and validating it against the sequence of already-resolved cycles instead of implicitly trusting a single "current" value derived from elapsed time.

### Proof of Concept
1. Let reward cycle length be `L`, half-cycle (distribution) length `L/2`. Suppose staker A stakes with the signer for distribution window D1, and `calculate-rewards` is *not* called during D1 or D2 (e.g., no keeper bothers, or it's deliberately skipped).
2. sBTC keeps arriving into the contract during D1 and D2 (protocol yield deposits); `get-new-rewards` accumulates the sum across both windows.
3. Staker A unstakes / exits before D3 begins. Attacker B stakes right as D3 begins, using `stake`/`register-for-bond` to register non-trivial shares for the cycle containing D3.
4. Attacker B calls `calculate-rewards` while burn-block-height is inside D3. `current-distribution-cycle` resolves to D3's index; `calculation-height` = start of D3 minus 1; `stx-cycle` = reward-cycle containing that height.
5. All of D1+D2's accrued `gross-accrued-rewards` is distributed using `get-total-shares-staked-for-cycle(stx-cycle, ...)`, which reflects only B's shares (recorded for the cycle containing D3), giving B (and any other D3 stakers) a `rewards-per-token-for-cycle` credit for rewards that were actually earned while A was staked in D1/D2.
6. B calls `claim-rewards`/`claim-staker-rewards-for-signer` and receives sBTC payouts sourced from D1/D2's yield, which A can never claim because `last-reward-compute-height` has moved past D1/D2 and their `rewards-per-token-for-cycle` entries were never populated for that period.
