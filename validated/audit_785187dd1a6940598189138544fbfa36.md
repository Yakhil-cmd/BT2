### Title
Webhook signature check authenticates the wrong organization's secret against a repository chosen from an unverified payload field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook against based on `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), while every `Handler` subclass resolves the actual repository/stack to act on from a separate, independently-controlled field, `payload.dig('repository', 'full_name')`. Because the HMAC signature only proves the payload was signed by *some* valid webhook secret known to the sender, not that the signing organization matches the `full_name` acted upon, an attacker who knows (or controls) the webhook secret of any one organization configured on the instance can forge events that are processed against a different organization's repository.

### Finding Description
`verify_signature` computes the signing app from an attacker-controlled JSON field: [1](#0-0) [2](#0-1) 

This looks up `Shipit.github(organization: repository_owner)` which, in the multi-org configuration schema, resolves a distinct `webhook_secret` per organization key: [3](#0-2) 

Signature verification itself only checks the raw body against that one organization's secret: [4](#0-3) 

Once verification passes, `create` dispatches the *entire raw payload* to handlers without any re-validation that the signing organization matches the repository referenced inside it: [5](#0-4) 

Every handler then determines the target repository from a completely different, independent JSON key — `repository.full_name` — with no cross-check against `repository.owner.login`/`organization.login` used earlier for signature selection: [6](#0-5) [7](#0-6) 

This is the binding violated: **organization that authenticated (`repository.owner.login`/`organization.login`, used to pick the verifying `webhook_secret`) ≠ repository that is written (`repository.full_name`, used by `Repository.from_github_repo_name` to locate the `Stack`/`Commit` acted upon)**. The signature only proves "signed with organization X's secret"; it never proves "this payload's `repository.full_name` belongs to organization X."

Concretely: on a Shipit instance configured with the multi-org schema (`secrets.github.<org>.webhook_secret`), a user who legitimately controls one configured organization's GitHub App/webhook secret (e.g., they administer their own org's onboarded GitHub App, which is a normal, unprivileged setup step, not a Shipit session or repository write access) can build an arbitrary JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`, HMAC-sign the exact raw body with `attacker-org`'s known secret, and POST it to `/webhooks`. `verify_signature` succeeds (it only checks the signature against `attacker-org`'s secret), and the handler for the event then locates and mutates state belonging to `victim-org/victim-repo`.

### Impact Explanation
Depending on the event forged, this crosses into the engine's own trust boundaries without any credential belonging to the victim organization:
- `status` events let the attacker inject `Commit#create_status_from_github!` records for arbitrary SHAs on the victim's tracked commits — [8](#0-7)  — forging CI/commit statuses that Shipit uses to gate deployability/mergeability of the victim's stack.
- `push` events cause `GithubSyncJob` to be enqueued for the victim stack with an attacker-chosen `expected_head_sha`, as shown in the push handler test flow — [9](#0-8)  — letting the attacker drive Shipit's internal notion of the victim repository's HEAD/sync state.

Both are cross-repository writes into a repository the forger does not control and was never authenticated against, satisfying the report's "Critical" bucket (cross-repository writes / unauthorized deploy path) once combined with a deploy trigger, and at minimum the "High" bucket (unauthenticated write/mutation of stack/commit state for a repository outside the caller's authenticated organization).

### Likelihood Explanation
Requires only: (1) the target Shipit instance to use the multi-organization `secrets.github` schema (documented, supported configuration — [10](#0-9) ), and (2) the attacker to legitimately know/hold one configured organization's `webhook_secret` (e.g., their own org's GitHub App they set up per `docs/setup.md`, which is explicitly an unprivileged, self-service action). No repository write access, Shipit session, or `ApiClient` token to the victim org is needed — only the ability to sign an arbitrary HTTP POST to the shared `/webhooks` endpoint, which is unauthenticated aside from this per-payload signature check.

### Recommendation
After `verify_signature` selects the signing organization, re-derive/validate `repository.full_name` (and any other repository/org identifiers used later by handlers) against that same signing organization before dispatching to `Shipit::Webhooks.for_event`. Reject payloads where `repository.full_name`'s owner segment does not match `repository_owner` used for signature verification.

### Proof of Concept
1. Configure Shipit with the multi-org schema, e.g. `secrets.github.attacker-org.webhook_secret = "s1"` and `secrets.github.victim-org.webhook_secret = "s2"` (attacker only knows `s1`, from operating their own onboarded GitHub App/org as documented in `docs/setup.md`).
2. Attacker builds body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<attacker-chosen sha already known to exist>",
  "state": "success"
}
```
3. Attacker computes `sha1=HMAC-SHA1(s1, body)` and sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<computed>
```
4. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and `verify_webhook_signature` succeeds because it was signed with `s1` [11](#0-10) .
5. `StatusHandler#process` runs on `params.sha`, creating a forged status on the victim's commit, matched purely via `repository.full_name` inside the same body — [8](#0-7)  — with no cross-check that `victim-org` ever authorized `attacker-org`'s secret to speak for it.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
