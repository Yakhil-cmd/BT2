### Title
Address `hash` authentifier commits to an unsalted, un-bound SHA-256 preimage, enabling cross-context secret reuse and offline/precomputation cracking - (File: definition.js)

### Summary
The `['hash', {algo:'sha256', hash:'base64'}]` address/authentifier primitive (`definition.js`, `case 'hash'` in `evaluate`/`validateAuthentifiers`, and the corresponding validation branch in `validateDefinition`) verifies a spending condition solely by checking `sha256(secret) === stored_hash`, with no per-address, per-unit, or per-path salt/binding. [1](#0-0) [2](#0-1) 

### Finding Description
The `hash` authentifier is validated identically to the CVE-2023-27580 bug class: a security credential (the preimage/"password") is checked against a fast, unsalted, single-round hash (`crypto.createHash("sha256")`), with no domain separation tying the commitment to the specific address, unit, or definition path:

```js

    if (!assocAuthentifiers[path] || typeof assocAuthentifiers[path] !== 'string')
        return cb2(false);
    arrUsedPaths.push(path);
    var algo = args.algo || 'sha256';
    if (algo === 'sha256'){
        var res = (args.hash === crypto.createHash("sha256").update(assocAuthentifiers[path], "utf8").digest("base64"));
``` [3](#0-2) 

Contrast with the `sig` authentifier just above it, which cryptographically binds the authentifier to the specific unit being signed via `objValidationState.unit_hash_to_sign`: [4](#0-3) 

The `hash` authentifier has no such binding — `args.hash` is a bare, context-free commitment of a secret string. This mirrors the "password shucking" root cause: because the hash of the secret is computed the same way everywhere (no salt derived from the address, unit, or definition), the same commitment `sha256(secret)` can be:
1. Precomputed/rainbow-tabled offline for any low/medium-entropy secret chosen by a user, since SHA-256 is single-round and extremely fast (billions/sec on commodity hardware), unlike a salted, memory/CPU-hard KDF.
2. Reused verbatim across multiple, unrelated addresses/definitions that happen to specify the same `hash` value — an attacker who recovers the preimage for one on-chain commitment (e.g. by cracking a weak secret, or by observing the revealed preimage in a confirmed unit's `authors[].authentifiers`, which are fully public on the DAG) can immediately reuse the identical secret to satisfy the `hash` clause of any other address definition that references the same `hash` value, with no unit-specific or address-specific binding to prevent it.

This is directly analogous to GHSA-c5vj-f36q-p9vg: Shield hashed passwords with an unsalted SHA-384 pre-hash before bcrypt, so a leaked pre-hash from any source let an attacker crack it without ever seeing the real password, and the crackable material could be attacked/reused across contexts. Here, ocore's `hash` authentifier is the DAG-native analog: it is an unsalted, single-pass hash used as the sole spending authorization, reachable by any unit poster who defines or uses an address containing a `hash` clause.

### Impact Explanation
If an address (reachable by any unprivileged unit poster, e.g. a shared/multisig address, an escrow, or an AA-adjacent hash-lock scheme) is defined with a `hash` clause and the underlying secret is anything short of full cryptographic entropy (which the primitive does nothing to enforce or discourage), an attacker can:
- Precompute/crack the preimage offline with no salt-derived slowdown, then construct a unit satisfying the `hash` authentifier and spend the locked funds — concrete unauthorized spending.
- Observe a revealed preimage in one confirmed unit (authentifiers are public once broadcast) and immediately reuse it to unlock any other output/address whose definition uses the identical `hash` value, since the check has no unit/address binding — again resulting in unauthorized spending of funds the attacker does not own.

### Likelihood Explanation
Any unprivileged party can author an address definition containing `['hash', {...}]` and can also be the attacker probing/cracking such definitions used by others (e.g. hash-locked escrow/atomic-swap style constructions built with ocore's definition language). No special privilege, hub/peer trust, or node compromise is required — the entire condition is evaluated purely from unit content in `validateAuthentifiers`, which every full node runs during ordinary consensus validation. The only prerequisite is that some legitimate user picks a `hash` secret with insufficient entropy or reuses a hash value across contexts, both of which the codebase neither validates against nor warns about.

### Recommendation
- Bind the `hash` authentifier's digest computation to unit/address-specific context (e.g. hash `address + path + secret`, or include `last_ball_unit`/`unit_hash_to_sign` material) so the same secret cannot satisfy commitments in unrelated definitions/units.
- Require or recommend a memory/CPU-hard KDF (e.g. scrypt/Argon2) rather than a single SHA-256 pass when secrets may be low-entropy, or explicitly document that `hash` authentifiers must only be used with full-entropy (32-byte random) secrets, never passwords/PINs.
- Consider deprecating raw `sha256` usage for authentifiers in favor of a salted primitive, mirroring the Shield fix (which moved away from unsalted pre-hashing entirely).

### Proof of Concept
1. Alice defines address `A` with definition `['hash', {algo:'sha256', hash: sha256("mysecret")}]` and funds it.
2. Bob defines an unrelated address `B` with the exact same `hash` value (either by copying, by coincidence of using the same human-chosen phrase, or via a service that recommends secrets) and funds it.
3. Attacker either (a) offline-precomputes `sha256` over a dictionary/rainbow table and finds `"mysecret"` matching the public `hash` in either address's definition (published in `definition.json` or referenced on-chain), or (b) waits for Alice to spend from `A` (revealing `"mysecret"` in the confirmed unit's `authentifiers`, which is public data on all full nodes).
4. Attacker immediately composes and broadcasts a unit spending from `B` using authentifier `{[path]: "mysecret"}`, which passes validation in `definition.js`'s `case 'hash'` block since the check only compares `sha256(secret)` to the stored value with no address/unit binding.
5. Result: attacker performs unauthorized spending of `B`'s funds using a secret they never legitimately possessed.
