### Title
Webhook organization used for signature verification is decoupled from the repository actually acted upon, letting a forged event target a different stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate an inbound webhook against based on `repository_owner`, a value parsed straight out of the untrusted request body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every event `Handler` subclass, however, resolves the `Stack`/`Repository` to act on using a *different* field of that same untrusted body: `payload.dig('repository', 'full_name')`. These two fields are never checked for consistency, and `GitHubApp#verify_webhook_signature` additionally short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured.

### Finding Description [1](#0-0)  resolves the signing organization purely from body content (`repository_owner`), then calls [2](#0-1) , which returns `true` unconditionally when `webhook_secret` is blank for that organization (a supported, documented configuration state, as shown in [3](#0-2) ).

Once the controller accepts the request, event processing dispatches to a `Handler` (e.g. `PushHandler`, `StatusHandler`), which locates the target `Stack` via `Handler#stacks`/`#repository_name`, reading `payload.dig('repository', 'full_name')`: [4](#0-3) 

`PushHandler#process` then directly triggers a GitHub sync for any stack whose branch matches, using an attacker-supplied `after` SHA: [5](#0-4) 

The binding that should hold is: *organization authenticated by the signature check* == *organization/repository the handler actually mutates*. Because the controller derives the "authenticated" organization from `repository.owner.login`/`organization.login` while the handler derives the acted-upon repository from the independent `repository.full_name` field, these two are never required to agree. An attacker can submit a raw POST to the public `/webhooks` endpoint (no session, no API token needed — `WebhooksController < ActionController::Base` with `skip_before_action :verify_authenticity_token`) where:
- `repository.owner.login` is set to an organization that has no `webhook_secret` configured (or one the attacker controls), making `verify_signature` pass trivially, while
- `repository.full_name` is set to `victim-org/victim-repo`, a stack tracked under a completely different, secret-protected GitHub organization.

The handler then acts on the victim stack (e.g. `stack.sync_github(expected_head_sha: params.after)` for a push event, or forging commit statuses via `StatusHandler`), even though the request was never authenticated for that organization/repository.

This mirrors the analog pattern in the reference report: a check (`safeTransferFrom`/`settleAuction`'s AND-instead-of-OR) validates one thing while a downstream operation acts on an entity whose critical precondition was never actually verified together with the field that was checked.

### Impact Explanation
This allows an unauthenticated attacker to trigger `Stack#sync_github` and other webhook-driven side effects (queued jobs like `GithubSyncJob`, `RefreshCheckRunsJob`, commit status creation) for a stack/repository belonging to a different, unrelated GitHub organization than the one whose signature check actually passed. If continuous deployment is enabled and `sync_github` trusts the supplied `expected_head_sha` before independently re-verifying against the GitHub API, this could enable spoofed commit/status data or unauthorized deploy triggers on a victim stack — an authorization-boundary violation (organization A authenticates, organization B's repository is written), matching the "unauthorized deploy" / "unauthenticated read/write of stack state" impact tier.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly supported, as shown by the sample multi-org secrets config) where at least one configured organization has no `webhook_secret` set, or where the attacker independently knows any one organization's secret; and (2) that the victim stack lives under a different organization in the same Shipit instance. This is a plausible but non-default configuration dependent on operator setup; it is not exploitable against a single-organization Shipit deployment, since `Shipit.github` ignores the `organization:` argument entirely when only one org is configured (`github_default_organization.nil?`).

### Recommendation
Bind the signature-verification organization to the same identity used for repository/stack resolution: derive `repository_owner` and the handler's repository lookup from the same canonical field, and reject any request where the organization used to select the `webhook_secret` does not match the owner of the `repository.full_name` used to locate the `Stack`. Do not allow `verify_webhook_signature` to short-circuit to `true` for organizations without a configured secret unless that is an explicit, intentional opt-out enforced per-repository rather than inferred from attacker-controlled payload content.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `org-open` (no `webhook_secret`) and `org-victim` (has `webhook_secret` and hosts stack `org-victim/app`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "org-open" }, "full_name": "org-victim/app" },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
3. `WebhooksController#verify_signature` computes `repository_owner == "org-open"`, calls `Shipit.github(organization: "org-open").verify_webhook_signature(...)`, which returns `true` immediately because `org-open` has no `webhook_secret` (see `lib/shipit/github_app.rb` line 77).
4. `PushHandler#process` resolves `repository_name` as `"org-victim/app"` and finds the `Stack`, then calls `stack.sync_github(expected_head_sha: "deadbeef...")` for a stack that never belonged to the "verified" organization.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
