### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login`, but event handlers act on the unverified `repository.full_name` field, allowing cross-organization webhook forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')`). Once the signature is verified, `Handler#stacks` (used by `PushHandler` and other handlers) resolves the target `Stack`/`Repository` using a completely different, unverified field: `payload.dig('repository', 'full_name')`. Because the HMAC only covers the raw request body and not any specific relationship between these two fields, an attacker who legitimately controls a webhook secret for one onboarded GitHub organization can forge a payload where `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` names a repository belonging to a different organization/stack configured in the same Shipit instance.

The secret used to verify the HMAC is selected per-organization via `Shipit.github(organization: repository_owner)`, which is documented and implemented for multi-org GitHub App configurations: [3](#0-2) 

After the signature check passes, `Hook`/event dispatch calls into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb` line 12). Handlers such as `PushHandler` resolve which `Stack`(s) to act on using `Handler#stacks`, which reads an entirely different payload field: [4](#0-3) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

The HMAC signature covers the raw JSON body as a whole, but the verification step's *choice of which secret to check against* depends on `repository.owner.login`, while all downstream repository/stack resolution depends on `repository.full_name`. Nothing in the code enforces that `full_name`'s owner segment matches `owner.login`. This is the same class of bug as the reported `ChainlinkAtlasWrapper` issue: a field that is consumed by downstream logic (`roundId` in the oracle case, `repository.full_name` here) is not actually covered/bound by the verification step (the wrapper always echoing BASE_FEED's `roundId`; here, the signature only proves knowledge of *an* org's secret, not that the org's identity matches the specific repository being acted upon).

### Impact Explanation
In a Shipit deployment using the documented multi-organization GitHub App configuration (`docs/setup.md` "Using Multiple Github Applications" section), an attacker who has (legitimately or through compromise) the ability to produce a validly-signed webhook for *any one* onboarded organization can forge `push`, `status`, `check_suite`, `pull_request`, etc. events that are attributed by signature-selection to their own org but that name a `repository.full_name` belonging to a different organization/stack tracked by the same Shipit instance. Since `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` and `GithubSyncJob` performs real GitHub API calls (using that *target* stack's own configured GitHub App credentials) and can queue continuous-delivery deploys, this allows an attacker to trigger unauthorized syncs/deploys against a repository/stack they were never granted webhook access to — a cross-repository/cross-organization authorization bypass and potential unauthorized deploy trigger.

### Likelihood Explanation
Exploitability depends on: (1) the Shipit instance being configured for multiple GitHub organizations (documented, supported feature), and (2) the attacker having a valid webhook secret for at least one of those organizations. This is a lower bar than compromising the victim organization's own webhook secret, but it still requires webhook-secret-level access to *some* org in the instance, which is a privileged credential. Per the scope rules this is not "requiring an ApiClient token" or "GitHub App private key" — it only requires one org's `webhook_secret`, a credential explicitly distinct from the target stack's. Given the explicit multi-org support and the clear divergence between `repository_owner` (verification) and `repository_name` (all handler logic), this is a concrete, reachable design flaw rather than a theoretical one.

### Recommendation
Enforce that the organization used to select/verify the webhook signature is the same organization embedded in every field the handler subsequently trusts. Concretely:
- Derive `repository_owner` and `repository_name` from the same normalized source, and after signature verification, re-validate that `payload.dig('repository','full_name')`'s owner segment equals `repository_owner` (case-insensitively) before dispatching to handlers.
- Alternatively, pass the already-verified `organization` explicitly into each `Handler` and have `Handler#stacks` scope `Repository.from_github_repo_name` lookups to repositories belonging to that verified organization only, rejecting any event where the derived owner doesn't match.

### Proof of Concept
1. Configure Shipit with two organizations, `org-attacker` and `org-victim`, each with their own `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications").
2. Attacker controls `org-attacker`'s webhook secret (e.g., is an admin of that GitHub App/org, or the secret otherwise leaked/is theirs).
3. Attacker crafts a `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "org-victim/victim-repo",
       "owner": { "login": "org-attacker" }
     }
   }
   ```
4. Attacker signs the raw payload with `org-attacker`'s `webhook_secret` and sends it to `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<hmac>`.
5. `WebhooksController#verify_signature` computes `repository_owner` = `"org-attacker"`, fetches `Shipit.github(organization: "org-attacker")`, and the HMAC verifies successfully (since it was actually signed with that org's secret).
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-victim/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — enqueuing `GithubSyncJob` against the victim's stack, despite the signing credential belonging only to `org-attacker`.

Note: I was unable to view `Repository.from_github_repo_name` or `PushHandler`'s exact matching logic in full within the indexed context (only `grep` hits were available, not full file contents), so I could not 100% confirm the absence of any additional owner-matching guard elsewhere in `Repository` or `Stack`. If such a guard exists there, it would mitigate this specific PoC; a full code review (e.g., via a Devin session with full repo access) of `app/models/shipit/repository.rb` is recommended to confirm.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
