**Analysis:**

`TableResolver::resolve_table_entry_bytes_with_layout` calls `StateKey::table_item(&(*handle).into(), key)`, which stores the full byte slice via `key.to_vec()` into `StateKeyInner::TableItem { handle, key }` [1](#0-0) [2](#0-1) . There is no truncation of the key: it is copied in full as a `Vec<u8>` and stored/compared as such in `StateKeyInner` and in the interning `TwoKeyRegistry`, whose actual equality/lookup is a `HashMap<Vec<u8>, Weak<Entry>>` keyed on the complete byte vector [3](#0-2) [4](#0-3) .

The `hash_address_and_name` function used in `StateKeyRegistry::table_item` is only used to pick a *shard index* (`% self.table_item_shards.len()`) for the registry, not as the key for equality/dedup — collisions there only affect performance (which shard bucket is used), not correctness, because the shard's inner `HashMap` still keys on the full `Vec<u8>` [5](#0-4) .

Separately, `nonce_validation.move`'s replay table does not pass attacker-controlled raw nonce bytes as the Move-native table key at all. The `NonceHistory.nonce_table: Table<u64, Bucket>` is keyed by `bucket_index = sip_hash_from_value(&nonce_key) % NUM_BUCKETS`, a `u64` — the actual `(sender_address, nonce)` uniqueness check happens inside the `Bucket`'s `BigOrderedMap<NonceKey, u64>` in Move logic, not via the raw `StateKey::table_item` bytes [6](#0-5) . So even if there were a state-key collision, it would collapse many buckets to the same `Table<u64, Bucket>` entry, not silently equate two distinct `(address, nonce)` pairs — the `BigOrderedMap` comparison inside the `Bucket` still distinguishes them by full struct equality.

No path exists for an unprivileged caller to cause two distinct nonces to be treated as the same replay-detection entry via this conversion.
