### Title
Cross-stack CCMenu authorization bypass via unscoped `Stack.from_param!` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` overrides `Shipit::Api::BaseController#stack` and resolves the target stack via `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` relation, instead of `stacks.from_param!(params[:stack_id])` which is scoped to `current_api_client.stack_id`. Any valid `ApiClient` token restricted to one stack can therefore read CCMenu status data for any other stack by simply changing the `stack_id` route param.

### Finding Description
The binding that must hold is: `stack.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` is true. In `Api::BaseController`, `stacks` enforces this: [1](#0-0)  — `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` calls `stacks.from_param!`, so `from_param!` raises `RecordNotFound` for any stack outside that scope.

`CCMenuController` overrides `stack` and bypasses this entirely: [2](#0-1)  — it calls `Stack.from_param!(params[:stack_id])` directly on the global `Stack` relation, never consulting `current_api_client.stack_id`.

The only other check in the request path is the permission check declared via `require_permission :read, :stack`: [3](#0-2)  which calls `current_api_client.check_permissions!(:read, :stack)`. That method only checks whether `"read:stack"` is present in the client's `permissions` array — it never compares stack identities: [4](#0-3) . So a client created with `stack: stack_a, permissions: %w[read:stack]` passes this check for a request targeting stack B's `stack_id`, and `#show` renders stack B's latest deploy/rollback data: [5](#0-4) .

Exploit flow: attacker legitimately obtains a token for stack A (e.g., via `CCMenuUrlController#fetch`), then issues `GET /api/stacks/<stack_B_to_param>/cc_menu.xml?token=<A's token>`. `authenticate_api_client` in `CCMenuController` sets `@current_api_client` successfully via `ApiClient.authenticate(params[:token])`: [6](#0-5) . `require_permission!` passes because the client has `read:stack`. `stack` resolves to stack B despite `current_api_client.stack_id == stack_a.id`, and the response leaks stack B's build/task status.

Existing test coverage never exercises the cross-stack scenario — all current tests use `@client` with `stack_id` matching `@stack` or unscoped: [7](#0-6) , so the divergence is untested and unguarded.

### Impact Explanation
An attacker holding a token scoped to one stack (obtainable legitimately for any stack they can view, including public/anonymous-readable stacks) can read CCMenu XML for arbitrary other stacks: build/task ids, timestamps, and running/failure state. This is a per-tenant confidentiality bypass — repeatable against any guessable/discoverable `stack_id`/slug across the whole install, matching "High - unauthenticated read of stack state" (the attacker is authenticated as a legitimate client for stack A, but unauthenticated for stack B).

### Likelihood Explanation
Preconditions are low-cost and entirely attacker-controllable: obtain a stack-scoped token via the legitimate `CCMenuUrlController#fetch` flow (no privilege needed beyond viewing one stack), then guess or discover another stack's slug/id (stack indexes are typically listable). No secrets, GitHub credentials, or elevated roles are required. The request is a single unauthenticated-cost GET and is fully repeatable against any number of target stacks.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `Api::BaseController`, i.e. replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])`, removing the override (or making it call `super`) so the `current_api_client.stack_id` scoping is enforced identically to every other API controller.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (or an integration test):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar2'), branch: 'main')`, giving stack_b a deploy/task with distinguishing state.
2. Create `client = ApiClient.create!(stack: stack_a, creator: shipit_users(:walrus), name: 'scoped', permissions: %w[read:stack])`.
3. Assert precondition: `assert_equal stack_a.id, client.stack_id`; `refute_equal stack_a.id, stack_b.id`.
4. `get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }`.
5. Assert `response.status == 200` and the XML payload's `name`/build data corresponds to `stack_b`, e.g. `assert_payload 'name', stack_b.to_param`, while `client.stack_id` still equals `stack_a.id` — demonstrating `stack.id != current_api_client.stack_id` yet a successful, data-bearing 200 response, violating the intended binding enforced elsewhere by `Api::BaseController#stacks`.
