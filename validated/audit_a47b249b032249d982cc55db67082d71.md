### Title
Webhook signature verification is unconditionally bypassed when `webhook_secret` is unset, allowing unauthenticated forgery of GitHub events - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever no `webhook_secret` is configured for the organization, instead of rejecting the request. This mirrors the H-30 root cause: a value left at its default/absent state (`delegate == address(0)` in Astaria, `webhook_secret == nil` here) causes a signature-verification routine to unconditionally accept the request instead of failing closed, breaking the binding between "the GitHub organization that actually signed the payload" and "the organization/repository the payload claims to be from."

### Finding Description
`WebhooksController#verify_signature` is the only gate protecting `POST /webhooks`: [1](#0-0) 

It delegates the actual check to `GitHubApp#verify_webhook_signature`: [2](#0-1) 

`return true unless webhook_secret` means that if the app for the target organization (resolved from the attacker-supplied `repository.owner.login` in the payload, see `repository_owner`) has no `webhook_secret` configured, **every** signature is accepted, no matter what (or nothing) is sent in `X-Hub-Signature`. `webhook_secret` is explicitly documented as *optional*: [3](#0-2) 
and both the example and test configs ship with it unset by default (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

This is structurally identical to the Astaria bug: an authentication check that is supposed to prove "this request really came from GitHub for this organization" degrades to `true` for the unset/default configuration value, letting anyone assert to be GitHub for that org.

### Impact Explanation
Once signature verification is bypassed, an unauthenticated attacker can `POST` arbitrary, fully-controlled JSON to `/webhooks` and have it dispatched to the registered handlers as if GitHub had sent it, e.g.:
- `StatusHandler`, which blindly persists an attacker-chosen commit status for any matching `sha` already known to Shipit: [6](#0-5) 
Forged "success" CI statuses feed directly into deploy gating logic (`require_ci`/`deployable?` checks in `DeploysController#create` and `Stack#trigger_continuous_delivery`), which can result in an **unauthorized deploy** of a commit that never actually passed CI — this meets the "High" impact bar defined in the rules (unauthorized deploy).
- `PushHandler`, which re-syncs a stack against a forged `after` SHA: [7](#0-6) 

I could not fully verify within the available index whether `MembershipHandler` also creates/links `Membership` records that would directly grant `Shipit.github_teams` authorization to an attacker-controlled `User` (only its creation of `User`/`Team` records was visible from test names); if it does, this same bypass would additionally satisfy the "escalation into `Shipit.github_teams` authorization" High-impact criterion. That specific chain is noted as unverified.

### Likelihood Explanation
This requires no credentials, no GitHub App private key, no session, and no repository access — only that the target organization's `webhook_secret` is left unset, which is the explicitly documented default/optional configuration. Any deployment following the documented "optional" guidance for `webhook_secret` is exposed. This is analogous to the accepted-as-High Astaria finding, which likewise required only the (equally legitimate/optional) absence of a delegate.

### Recommendation
Fail closed instead of open: reject (`head 422`) webhook deliveries when `webhook_secret` is not configured for the organization, or require `webhook_secret` to be mandatory at app-config validation time rather than optional.

### Proof of Concept
1. Configure (or find) a Shipit deployment where an organization's GitHub App entry has no `webhook_secret` set (the documented default).
2. Without any valid `X-Hub-Signature`, `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{"sha":"<existing commit sha>","state":"success","context":"ci/build","repository":{"owner":{"login":"<org>"}}}
```
3. `GitHubApp#verify_webhook_signature` returns `true` (webhook_secret blank), the request passes `verify_signature`, and `StatusHandler#process` persists the forged "success" status via `commit.create_status_from_github!(params)`, potentially unblocking `require_ci`-gated or continuous deployment of that commit.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
