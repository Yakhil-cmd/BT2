### Title
Stale storage-root proof allows bypassing a subsequently-increased proxy delay - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::do_remote_proxy` validates a `ProxyDefinition` by proving it existed in remote-chain storage at *some* block whose root is still retained in `BlockToRoot`, then checks only `def.delay.is_zero()` on that historically-proved definition. Because `BlockToRoot` retains up to `MaxStorageRootsToKeep` historical roots, an attacker can submit a proof anchored to an *older* block where the remote proxy still had `delay = 0`, even though the remote proxy owner has since raised the delay to a non-zero value, and get immediate (non-timelocked) execution.

### Finding Description
`do_remote_proxy` takes an arbitrary `block` from the caller-supplied `RemoteProxyProof::RelayChain { proof, block }`, looks it up in `BlockToRoot` (a bounded, sliding window of the last `MaxStorageRootsToKeep` block→root mappings), and uses whatever root corresponds to that block to verify the merkle proof: [1](#0-0) 

Any block still present in the window is accepted — there is no requirement that `block` be the *latest* known root, nor any check that the proved `ProxyDefinition` reflects the *current* remote state. After decoding the proof, the only timelock-related check performed is: [2](#0-1) 

This checks the `delay` field of the proxy definition *as it existed at the proved block*, not the current remote definition. `BlockToRoot` is pruned only relative to the newest observed block, via a sliding window of size `MaxStorageRootsToKeep`: [3](#0-2) 

Exploit flow:
1. Remote chain: proxy relationship created with `delay = 0` at remote block `B1`. Attacker (the delegate) captures a valid storage proof + observes/obtains the corresponding root (which becomes available locally via `on_validation_data`).
2. Remote chain: the `real` account owner later raises the delay (`pallet_proxy::add_proxy`/equivalent) to `delay > 0` at block `B2 > B1`, intending to require an announcement/timelock for all future proxy calls (e.g., because they no longer trust the delegate for instant execution, or as a security hardening measure).
3. As long as the parachain has not advanced more than `MaxStorageRootsToKeep` relay blocks past `B1` (i.e., `B1`'s root is still in `BlockToRoot`), the attacker submits `remote_proxy(real, None, call, RemoteProxyProof::RelayChain { proof: <old proof>, block: B1 })`.
4. `do_remote_proxy` looks up `B1`'s still-present root, the old proof verifies against it, decodes the stale `ProxyDefinition{ delay: 0, ... }`, passes `ensure!(def.delay.is_zero(), ...)`, and immediately dispatches `call` as `real` via `Self::do_proxy` — completely bypassing the delay/announcement mechanism the account owner just configured.

None of the pallet's existing checks catch this: `UnknownProofAnchorBlock` only fails if the block isn't in the window at all; `InvalidProof`/`ProxyDefinitionDecodingFailed`/`DidNotFindMatchingProxyDefinition` only fail on malformed/mismatched proofs — a syntactically and cryptographically *valid* stale proof passes all of them. The design intentionally supports proofs anchored to older-but-still-retained roots (see the `MaxStorageRootsToKeep` doc comment describing this as allowing "the proof [to] be" older), but this feature directly conflicts with the delay/timelock invariant: any change made to a proxy definition on the remote chain is not binding locally until the entire retention window has rolled over, and until then the *most permissive definition observed within the window* remains exploitable.

### Impact Explanation
Any parachain account (`real`) that relies on the local `pallet_remote_proxy` bridge to mirror its remote proxy authorizations can have a just-tightened delay/timelock retroactively bypassed by a delegate holding an old, still-window-valid proof. This defeats the announcement/delay security control entirely for a window of `MaxStorageRootsToKeep` remote blocks after the owner raises the delay, allowing the delegate to execute arbitrary calls (subject to `InstanceFilter`) on behalf of `real` immediately instead of being forced through the multi-block announcement/timelock the owner just enabled. Since proxy calls can move/spend assets or manage further permissions (bounded by the `InstanceFilter`), this is a concrete authorization/timelock-bypass impact on a real account's assets and permissions.

### Likelihood Explanation
Feasible and fully attacker/user-controlled: it requires only (a) the attacker/delegate already had a `delay = 0` proxy relationship with `real` at some point, (b) the storage proof for that block, and (c) submission before the local `BlockToRoot` window (bounded by `MaxStorageRootsToKeep`, refreshed every relay block via `on_validation_data`) rolls past that block. The attacker fully controls timing of step 3 (submit immediately after learning of the delay change, well within the retention window), and capturing/retaining an old proof/root pair requires no privileged access — any observer of the remote chain state can construct it. The scenario is directly reproducible in the pallet's own test harness, as shown by `clean_up_works_and_old_blocks_are_rejected`, which demonstrates old roots remain valid for reuse until evicted by the sliding window: [4](#0-3) 

### Recommendation
Enforce that the proof must be anchored to the *most recent* known root (or reject the block/anchor if a strictly newer root already commits to a definition for the same `(real, delegate)` pair), rather than accepting any block still present in the sliding window when `delay.is_zero()` gates immediate execution. At minimum, require non-zero-delay definitions to always go through the announcement path regardless of which historical root is proved, and/or shrink the acceptable staleness for zero-delay proofs to zero (only the newest root), while still allowing older roots for delayed executions that must be announced and waited out separately.

### Proof of Concept
Rust unit test extending `pallets/remote-proxy/src/tests.rs`:
1. Create pure proxy for account `1` with `delay = 0` at block `N1`; capture `proof0`/`root0` via `sp_state_machine::prove_read` on `Proxy::Proxies` key, matching the pattern in `remote_proxy_works`.
2. Advance the remote/local externalities: update the proxy definition's delay to `delay = 5` (e.g. via `Proxy::add_proxy` with a delay, replacing the entry) at a later block `N2`, without advancing the parachain past `MaxStorageRootsToKeep` blocks since `N1`.
3. Manually set `BlockToRoot` to include both `(N1, root0)` and `(N2, root_new)` (simulating retained window), mirroring how `on_validation_data` accumulates entries as in `clean_up_works_and_old_blocks_are_rejected`.
4. Call `RemoteProxy::remote_proxy(RuntimeOrigin::signed(1), anon, None, call, RemoteProxyProof::RelayChain { proof: proof0, block: N1 })`.
5. Assert this call succeeds (`assert_ok!`) and the inner `call` (e.g., `Balances::transfer_allow_death`) executes immediately — proving the raised delay from step 2 was bypassed using the stale `N1` proof, in direct violation of the "timelock enforcement must not be bypassable via stale valid proofs" invariant.

			BlockToRoot::<T, I>::mutate(|roots| {
				let delete_up_to =
					block.clone().saturating_sub(T::MaxStorageRootsToKeep::get().into());

				while roots.first().is_some_and(|f| f.0 <= delete_up_to) {
					roots.remove(0);
				}

				// We always remove all the old items before, thus there should always be space in
				// the vector.
				let _res = roots.try_push((block, hash));
				debug_assert!(_res.is_ok());
			});
