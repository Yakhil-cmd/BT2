### Title
Fee-on-Transfer ERC20 Tokens Cause Bridge Reserve Drain via Inflated `RequestValueTransfer` Amount — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

The Kaia service-chain bridge's ERC20 transfer logic assumes that the amount specified by the caller equals the amount actually received by the bridge contract. When a fee-on-transfer ERC20 token is registered, the bridge receives fewer tokens than `_value + _feeLimit`, but emits `RequestValueTransfer` with the full `_value`. The counterpart bridge then releases the full `_value` to the recipient, permanently draining the bridge's token reserves by the token-level fee on every cross-chain transfer.

### Finding Description

In `BridgeTransferERC20.sol`, the 2-step entry point `requestERC20Transfer` pulls `_value + _feeLimit` from the caller: [1](#0-0) 

If the ERC20 token charges a transfer fee internally (fee-on-transfer), the bridge receives `(_value + _feeLimit) × (1 − token_fee_rate)` — strictly less than `_value + _feeLimit`. Control then passes to `_requestERC20Transfer`, which calls `_payERC20FeeAndRefundChange` to pay the bridge's own fee and refund the remainder of `_feeLimit` to the user: [2](#0-1) 

These internal `safeTransfer` calls also lose value to the token's fee. After both deductions, the bridge holds strictly less than `_value` tokens. Despite this, `_requestERC20Transfer` emits `RequestValueTransfer` with the original, unverified `_value`: [3](#0-2) 

The same flaw exists in the 1-step path. `ERC20ServiceChain.requestValueTransfer` transfers `_amount + _feeLimit` to the bridge and then calls `onERC20Received` with the original `_amount`: [4](#0-3) 

`onERC20Received` forwards `_value` unchanged into `_requestERC20Transfer`: [5](#0-4) 

On the counterpart chain, bridge operators call `handleERC20Transfer` with the `_value` read from the `RequestValueTransfer` event, and the counterpart bridge releases the full `_value` to the recipient: [6](#0-5) 

The source bridge has committed to backing `_value` tokens but only holds `_value × (1 − token_fee_rate)^n` (where `n` accounts for multiple internal transfers). The deficit is permanent and accumulates with every cross-chain transfer.

### Impact Explanation

In **lock/unlock mode** (the default, `modeMintBurn = false`): the source bridge's token reserve is drained by the token-level fee on every `requestERC20Transfer` call. After enough transfers, the source bridge cannot honour unlock requests from the counterpart chain, causing `handleERC20Transfer` to revert and permanently locking funds for legitimate users.

In **mint/burn mode**: `_requestERC20Transfer` calls `ERC20Burnable(_tokenAddress).burn(_value)` after receiving fewer than `_value` tokens. If the bridge's balance is insufficient, the burn reverts and the transaction fails — a denial-of-service. If the bridge has residual balance from other sources, it burns more than it received, destroying tokens it did not own.

The corrupted value is the `_value` field emitted in `RequestValueTransfer`: it is inflated relative to the tokens actually held by the bridge, causing the counterpart bridge to release more than the source bridge received.

### Likelihood Explanation

**Medium.** A fee-on-transfer token must be registered with the bridge by the bridge owner. However:
- The bridge's `registerToken` function imposes no restriction on token type or fee behaviour.
- A token that has no fee at registration time can enable fees later (the USDT/USDC precedent cited in the original report applies equally here).
- Once such a token is registered and in use, any unprivileged user can trigger the drain by calling `requestERC20Transfer` or `requestValueTransfer` on the token.

### Recommendation

After each `safeTransferFrom` / `transfer` call into the bridge, measure the actual received amount using a before/after balance check:

```solidity
uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(before);
```

Pass `actualReceived` (minus the bridge's own fee) as the bridged amount into `_requestERC20Transfer` and emit it in `RequestValueTransfer`, so the counterpart bridge releases only what the source bridge actually holds. Apply the same pattern inside `_payERC20FeeAndRefundChange` for the fee-payment and refund transfers.

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` that deducts 1% on every transfer.
2. Register `FeeToken` on both the source and counterpart bridges (lock/unlock mode).
3. Alice calls `requestERC20Transfer(FeeToken, Bob, 1000, 0, "")` after approving 1000 tokens.
4. Bridge executes `safeTransferFrom(Alice, bridge, 1000)` → bridge receives 990 (1% fee deducted).
5. `RequestValueTransfer` is emitted with `_value = 1000`.
6. Counterpart bridge operators call `handleERC20Transfer(..., 1000, ...)`.
7. Counterpart bridge executes `safeTransfer(Bob, 1000)` → Bob receives 990 (another 1% fee), counterpart bridge balance decreases by 1000.
8. Source bridge holds 990 but has committed to backing 1000 — a 10-token deficit per transfer.
9. After 100 such transfers, the source bridge is short 1000 tokens and cannot service the next unlock from the counterpart chain.

            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);

            return fee;
