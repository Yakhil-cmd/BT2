### Title
Missing webhook_secret causes signature bypass, allowing cross-organization Team hijack via `MembershipHandler#find_or_create_team!` - (File: lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever the configured organization has no `webhook_secret`, and `WebhooksController#verify_signature` selects the `GitHubApp` instance purely from the attacker-controlled `repository`/`organization` login in the JSON body. Combined with `MembershipHandler#find_or_create_team!` looking up teams only by `github_id` (never validating that the payload's `organization.login` actually owns that `github_id`), an attacker who controls or names any Shipit-configured organization with a blank `webhook_secret` can forge a `membership` event for a *different*, privileged team and add themselves as a member.

### Finding Description
The broken binding is: **the organization whose (absent) `webhook_secret` "verified" the request == the organization that actually owns `Team#github_id == params.team.id` in `Shipit.github_teams`.** These are never checked to be equal.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` directly from attacker-supplied JSON (`params.dig('repository','owner','login') || params.dig('organization','login')`) and calls `Shipit.github(organization: repository_owner)` [1](#0-0) .
- `GitHubApp#verify_webhook_signature` short-circuits `return true unless webhook_secret` [2](#0-1) . If the config entry for that organization has no `webhook_secret` (a real but incompletely-configured `GithubHook::Organization`/app entry), any body is "verified" with no HMAC needed.
- `WebhooksController#create` then dispatches to `Shipit::Webhooks.for_event('membership')` → `MembershipHandler#process` [3](#0-2) [4](#0-3) .
- `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`, matching solely on the attacker-supplied `github_id` — it does not check that `params.organization.login` matches `team.organization` for an already-existing team [5](#0-4) . If team 48 already exists (e.g., a Shipit-privileged team used in `Shipit.github_teams`, see `Team.find_or_create_by_handle` / `Shipit#github_teams` [6](#0-5) [7](#0-6) ), it is looked up and returned regardless of which organization's (unauthenticated) request triggered the lookup.
- `team.add_member(User.find_or_create_by_login!('attacker'))` then creates the `Membership` [8](#0-7) .

Attacker request: `POST /webhooks` with `X-Github-Event: membership`, no `X-Hub-Signature`, body `{action:'added', team:{id:48,...}, organization:{login:'attacker-org'}, member:{login:'attacker'}}`, where `attacker-org` is a configured Shipit organization whose `webhook_secret` is blank.

Existing guards fail because: `verify_signature`'s only failure mode is `GithubOrganizationUnknown` (an org not configured at all) — a *configured-but-secretless* org passes cleanly [9](#0-8) ; `ExplicitParameters` schema in `MembershipHandler` validates types/presence only, not organization ownership [10](#0-9) ; and `find_or_create_by!` has no organization-scoping in its lookup clause.

### Impact Explanation
This is an authentication-bypass / cross-tenant privilege-escalation into `Shipit.github_teams`: an unprivileged attacker with no GitHub credentials for the target organization can be added as a member of any pre-existing Team record by guessing/knowing its `github_id`, provided any other Shipit-configured GitHub App entry lacks a `webhook_secret`. Since `Shipit.github_teams` gates OAuth-based authorization (`User#authorized?`), this can escalate the attacker into privileged Shipit roles — matching the High severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any `github_id` the attacker can discover, and requires no interaction from the real team's organization.

### Likelihood Explanation
Requires: (1) at least one Shipit-configured organization entry with a missing/blank `webhook_secret` (a real, not-hypothetical multi-org misconfiguration documented in `docs/setup.md`'s "Using Multiple Github Applications" pattern), and (2) knowledge of a target `github_id` for a privileged team (team IDs are often discoverable via GitHub's public API). Attacker cost is a single unauthenticated HTTP POST; no secrets or sessions needed.

### Recommendation
In `MembershipHandler#find_or_create_team!`, when the team already exists, verify `team.organization == params.organization.login` before proceeding (reject/no-op otherwise). Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in production — this should be a hard configuration error, not a permissive default.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership from an org with no webhook_secret cannot hijack another org's team" do
  privileged_team = shipit_teams(:shopify_developers) # existing team, e.g. github_id 48, organization: 'shopify'
  attacker_org_config = { webhook_secret: nil } # attacker-org configured but secretless
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(GitHubApp.new('attacker-org', attacker_org_config))

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }.to_json

  post :create, body: body, as: :json

  refute Membership.exists?(team_id: privileged_team.id, user: User.find_by(login: 'attacker')),
    "attacker was added to privileged_team owned by 'shopify' via an unverified 'attacker-org' webhook"
end
```
Both sides of the binding — `privileged_team.organization` (`'shopify'`) and the request's `organization.login` (`'attacker-org'`) — diverge, yet the current code allows the membership write to proceed, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
