### Title
Emergency OP-list vote count uses each node's local, unsynchronized view of unstable `system_vote` messages, causing nodes to disagree on the resulting OP list - ([File: main_chain.js])

### Summary
The audit report describes a scenario where a privileged process (L2 migration) takes an authoritative "snapshot" of participant state while assuming no concurrent activity is possible (assuming the Auction is fully paused), but an unprivileged actor's in-flight action (a bid) is not reflected in that snapshot, leading to loss of funds. The structurally identical root cause exists in ocore's **emergency OP-list vote-count mechanism**: it builds an authoritative, irreversible "snapshot" of votes (`getUnstableVotes`) purely from each node's local, transient view of not-yet-stable units (`storage.assocUnstableMessages`), which is guaranteed to differ across nodes, yet the result is written as a hard consensus parameter (`system_vars.op_list`) that all subsequent validation depends on.

### Finding Description
`applyEmergencyOpListChange()` ( [1](#0-0) ) is invoked from `writer.js` every time **any single unprivileged unit** carrying a `system_vote_count` message for subject `op_list` is locally validated with `sequence==='good'` — *before that unit itself has become stable*: [2](#0-1) 

If the last stable MC unit is older than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) relative to the trigger unit's timestamp, the node proceeds to recompute the OP list via `countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp)`.

Inside `countVotes`, when `is_emergency` is set, the vote set is not limited to stable, network-agreed `op_votes`; it is extended with **unstable** votes pulled from `getUnstableVotes()`: [3](#0-2) 

`getUnstableVotes` iterates `storage.assocUnstableMessages`, a purely local, non-consensus, node-specific cache of messages belonging to units that have not yet stabilized (and are still subject to reordering/removal, or elimination by better-sequenced competitors). This set is a function of what a given node has happened to receive and locally judge `sequence==='good'` at the moment the trigger unit is processed — it is not derived from any consensus-confirmed, all-nodes-identical checkpoint. Two honest, fully-synced nodes can (and, given normal p2p propagation delay, routinely will) hold different subsets of unstable `system_vote` messages at the moment they each independently execute this code path, because:
- The triggering unit ("system_vote_count") itself can arrive and be validated at different real times on different nodes.
- Whether a competing/rival unit is currently assigned `sequence='good'` in `assocUnstableUnits` for a still-unstable unit is a temporary, node-local judgment that is revisited/finalized only once the unit stabilizes.

The resulting vote tally (`op_rows`, weighted by voter balances, `constants.COUNT_WITNESSES` = 12 addresses) is then written directly into `storage.systemVars.op_list` and persisted with a fixed `vote_count_mci` key using `REPLACE INTO system_vars` (`is_emergency` path overwrites unconditionally, no compare-and-swap against a globally agreed value): [4](#0-3) [5](#0-4) 

`system_vars.op_list`/`storage.getOpList(mci)` is subsequently used as the canonical Order-Provider list for MC-stability determination and unit validation across the whole node (`storage.getOpList` / `getSystemVar`): [6](#0-5) 

Because the emergency snapshot (the set of "in-flight"/unstable votes) is not a globally agreed value but a node-local artifact of network timing, two nodes can legitimately compute two different 12-address OP lists for the same `vote_count_mci`, exactly mirroring the external report's core defect: a privileged/irreversible action (writing new consensus parameters) is derived from a "paused"/"frozen" snapshot that in reality still has in-flight, unsynchronized state (unstable votes from unprivileged posters) that differs between observers.

### Impact Explanation
Divergent OP lists mean different nodes disagree on which addresses are witnesses/order providers for stability and validity purposes going forward. This is a direct instance of "node disagreement on validity or stability" — the strongest listed acceptable impact. Concretely:
- Units that are valid (stable, well-witnessed) per one node's OP list can be judged non-serial/invalid per another node's OP list, splitting the network.
- Because the emergency mechanism is specifically designed to fire only when the network is "stuck" (no MCI progress for 3+ days), it is exactly in this fragile state that the divergence is most likely to be triggered by ordinary unprivileged users racing to submit `system_vote`/`system_vote_count` messages, worsening rather than resolving the stuck condition, or causing a silent, permanent fork.
- Since `system_vote_count` requires no special permission (`objValidationState.bAA` check merely forbids AAs from sending it, but any regular address may) and validation places no restriction on which/how many addresses may trigger it ( [7](#0-6) ), this is fully reachable by an unprivileged unit poster, matching the reachability constraints of this analysis.

### Likelihood Explanation
The condition requiring "network stuck for `EMERGENCY_OP_LIST_CHANGE_TIMEOUT`" limits how often the code path activates, but once the network is stuck, any user can submit `system_vote_count` for `op_list`, and the propagation-delay-driven divergence of `assocUnstableMessages` between nodes is a routine occurrence, not a rare edge case, especially under exactly the network stress that leads to "being stuck" in the first place (this is corroborated by an in-repo bug-workaround for testnet: `initial_votes.js` lines 9-28 patch a previously observed real 13-vs-12 OP divergence bug related to this same voting subsystem). The precondition (prolonged main-chain stall) is rare in normal operation but is the exact scenario this mechanism exists to handle, so likelihood should be assessed as tied to that stall condition rather than everyday use.

### Recommendation
- Base the emergency vote-count snapshot on a value that is provably identical across all nodes rather than each node's local `assocUnstableMessages` cache — e.g., require the counted votes to reference stable, ball-referenced units only, or derive the "unstable" vote set deterministically from data already committed to and cryptographically referenced by the triggering `system_vote_count` unit itself (so any two nodes validating the same unit compute the same set).
- Alternatively, require the emergency OP-list result to be re-validated/confirmed via a subsequent stability check (e.g., only apply the emergency-derived `op_list` once the vote-count trigger unit and referenced votes are themselves stable), removing the dependency on pre-stability, node-local state.
- Add a network-wide consistency check (e.g., embedding a merkle root or content hash of the exact vote set used into the `system_vote_count` unit itself) so divergence can be detected and rejected rather than silently accepted.

### Proof of Concept
1. Network stalls (no MCI advances) for > `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) — a condition this feature is explicitly built to handle.
2. Multiple unprivileged users submit `system_vote` (op_list) units close to `EMERGENCY_COUNT_MIN_VOTE_AGE` in age, propagating through the p2p network with normal, non-uniform delay.
3. User A submits a `system_vote_count` unit for subject `op_list`. Due to propagation timing, Node 1 has already received and marked `sequence='good'` for votes V1..V5 in its `assocUnstableMessages`, while Node 2 has only received V1..V4 (V5 not yet arrived, or still competing for sequence assignment).
4. Both nodes independently satisfy the timeout check in `applyEmergencyOpListChange` ( [1](#0-0) ) and call `countVotes(..., is_emergency=1, ...)`.
5. `getUnstableVotes()` returns different vote sets on Node 1 vs Node 2 ( [3](#0-2) ), so the weighted-by-balance top-12 OP addresses computed in the `op_list` branch of `countVotes` differ between the two nodes ( [4](#0-3) ).
6. Each node `REPLACE`s its own, differing `op_list` into `system_vars` for the same `vote_count_mci` and updates its in-memory `storage.systemVars.op_list` ( [5](#0-4) ), which is subsequently used by `storage.getOpList`/`getSystemVar` for validating all future units — causing the two nodes to permanently disagree on which units/witness sets are valid.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}

function getSystemVar(subject, mci) {
	for (let { vote_count_mci, value } of systemVars[subject])
