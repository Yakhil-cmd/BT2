### Title
Cross-organization Team write via `repository`/`organization` field mismatch in membership webhook - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to authenticate a webhook from `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')` only when no `repository` key is present [1](#0-0) . `MembershipHandler#find_or_create_team!` instead uses `params.organization.login` exclusively to set `team.organization` on a newly created `Team` row [2](#0-1) . Because the controller parses the raw request body with no schema restriction before dispatching to the handler, an attacker can add an arbitrary `repository` object to a `membership` event body so that the org used for signature verification differs from the org persisted onto the `Team`.

### Finding Description
The binding the code implicitly assumes is:
`repository_owner` (used by `verify_signature` to pick the `GitHubApp`) == `organization.login` (used by `find_or_create_team!` to set `team.organization`).

Trace:
1. `WebhooksController#create` parses the raw JSON body with no shape restrictions: `params = JSON.parse(request.raw_post)` [3](#0-2) .
2. `verify_signature` (a `before_action`) computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and uses it to fetch a `GitHubApp` via `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(...)` [4](#0-3) .
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) .
4. `MembershipHandler` is then invoked on the same raw body and writes `team.organization = params.organization.login` on `Team.find_or_create_by!(github_id: params.team.id)` [2](#0-1) .

GitHub's real `membership` event payload does not include a `repository` key, so in the legitimate flow `repository_owner` falls back to `organization.login` and the two values naturally coincide. However, nothing in the controller or `MembershipHandler`'s `ExplicitParameters` schema forbids an attacker-crafted body from including an extra top-level `repository` key alongside `organization`, `team`, and `member`. Since the controller reads `repository_owner` from the raw parsed hash before any handler-level schema validation runs, this extra key is honored for GitHubApp selection while being entirely ignored by the handler that performs the write.

Exploit flow:
- Attacker POSTs directly to `/webhooks` with header `X-Github-Event: membership` and a JSON body: `{"action":"added","team":{"id":999,"name":"n","slug":"s","url":"u"},"organization":{"login":"victim-org"},"member":{"login":"attacker"},"repository":{"owner":{"login":"attacker-org"}}}`.
- If Shipit has a configured `GitHubApp` for `attacker-org` whose `webhook_secret` is blank/unset, `verify_webhook_signature` returns `true` regardless of the (attacker-controlled, arbitrary) `X-Hub-Signature` header.
- `MembershipHandler` then executes and persists a new `Team` row with `organization: "victim-org"`, `github_id: 999`, entirely from unverified attacker-supplied data, and adds the attacker's own GitHub login as a member of that team via `team.add_member(member)` [6](#0-5) .

None of `drop_unhandled_event`, the `ExplicitParameters` schema on `MembershipHandler`, or `verify_signature` check that the two organization-bearing fields agree; the schema only requires `organization.login` to be a String, it does not compare it against `repository.owner.login` or forbid extra keys.

### Impact Explanation
This lets an attacker forge a `Team` record falsely attributed to an organization (`victim-org`) they do not control, and immediately add themselves as a member of that team. If `Shipit.github_teams` or any authorization logic keys off `Team#organization` + membership to grant privileges (e.g., counting members of a named team within an org toward admin/deploy authorization), this is a path toward unauthorized privilege escalation for a victim organization's namespace — matching the High-severity category "escalation into `Shipit.github_teams` authorization." It is repeatable for any `github_id`/`organization.login` pair the attacker chooses, as long as `Team.find_or_create_by!(github_id:)` targets an unclaimed `github_id`, and is limited to `membership` events (other event handlers were not verified here).

### Likelihood Explanation
Exploitation requires:
1. The attacker can send arbitrary raw HTTP POSTs to `/webhooks` (per the threat model, this is trivially available — no session/token/secret needed).
2. The Shipit deployment must have a `GitHubApp` configured for some organization (`attacker-org`) with a blank/unset `webhook_secret` — a plausible but non-default operator misconfiguration; without this precondition `verify_webhook_signature` will reject the forged signature.
3. `attacker-org` need not be related to `victim-org` at all — the attacker just needs any org entry in Shipit's config with a missing secret.

Given precondition (2) is a configuration weakness rather than something the attacker controls directly, likelihood is conditional but the underlying code defect (silently trusting unmatched org fields across two different purposes) is present regardless of configuration.

### Recommendation
- Ensure `verify_signature` and any downstream handler use the **same** organization-derived value consistently, and reject a request if a handler-relevant `organization.login` disagrees with `repository.owner.login` when both are present.
- Do not allow `GitHubApp#verify_webhook_signature` to silently accept unsigned traffic when `webhook_secret` is blank — treat blank secret as a configuration error (fail closed) rather than "verified."
- In `MembershipHandler`, derive the authenticated organization strictly from the same value used for signature verification (i.e., from the value the `before_action` verified), not from an independently attacker-controlled JSON field.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative addition)
test "membership webhook cannot bind org from unverifying repository owner" do
  # Precondition: Shipit.github_apps has 'attacker-org' configured with blank webhook_secret
  Shipit.stubs(:github_apps).returns({
    'attacker-org' => Shipit::GitHubApp.new('attacker-org', { webhook_secret: nil }),
  })

  payload = {
    action: 'added',
    team: { id: 999, name: 'n', slug: 's', url: 'u' },
    organization: { login: 'victim-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } },
  }.to_json

  post shipit.github_authenticated_hooks_path,
       params: payload,
       headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => 'sha1=deadbeef', 'Content-Type' => 'application/json' }

  assert_response :ok
  team = Shipit::Team.find_by(github_id: 999)
  assert team.present?
  assert_equal 'victim-org', team.organization # binding broken: verified as attacker-org, persisted as victim-org
end
```
