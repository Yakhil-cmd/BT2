### Title
StatusHandler#process matches commits by `sha` alone across all stacks, allowing an org-A-verified status webhook to mutate org-B's Commit row - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on repository/stack, even though `Commit#sha` is only unique per `(sha, stack_id)`, not globally. Since `WebhooksController#verify_signature` only proves the payload came from `repository_owner`'s GitHub org, but the handler never re-checks that the matched `Commit`'s `stack.repository` equals that same org/repo, any commit sha shared across two different stacks (e.g. via a fork sharing git history) will have its status mutated regardless of which org's signature validated the request.

### Finding Description
The broken binding, stated explicitly: the code should enforce
`commit.stack.repository.owner == payload.repository.owner (the org whose signature was verified)`
for every `Commit` mutated by a `status` webhook. It does not.

Trace of the path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, at [1](#0-0) . This only proves the HTTP request's HMAC matches that particular org's webhook secret - it never scopes what data the handler is allowed to touch.
- `Handler#call` / `#initialize` just parses `params` via `ExplicitParameters`, at [2](#0-1) . The base `Handler` class does provide a `stacks` helper that resolves `Repository.from_github_repo_name(repository_name)&.stacks`, at [3](#0-2) , which is exactly the repository-scoping primitive other handlers should use.
- `StatusHandler#process`, however, bypasses this scoping entirely and queries `Commit.where(sha: params.sha)` globally, then calls `commit.create_status_from_github!(params)` on every match: [4](#0-3) .
- `Commit#create_status_from_github!` unconditionally writes a `Status` row tied to that commit's own `stack_id`: [5](#0-4) .
- The DB-level uniqueness constraint on commits is `(sha, stack_id)`, confirming the same `sha` is expected/allowed to exist under multiple different `stack_id`s (and therefore multiple different repositories/owners): [6](#0-5) .

Exploit flow: An attacker who owns/controls repository `attacker/fork` (a public fork of `victim-org/private-or-other-repo`) has legitimate GitHub webhook signing rights for their own repo. Any commit sha shared between the fork and the upstream repo (i.e., any commit that predates the fork, which is the vast majority of a repo's history and is publicly known) exists identically in both `victim-org`'s Shipit stack and the attacker's own stack (if the attacker's fork is also onboarded as a Shipit stack, or even if the attacker just knows the sha and it matches a commit already present under `victim-org`'s stack from before/regardless of forking). The attacker sends a `status` event webhook, signed with their own repo/org's webhook secret, naming that shared `sha`. `verify_signature` legitimately authenticates this as coming from the attacker's own org. `StatusHandler#process` then finds ALL `Commit` rows with that `sha`, including `victim-org`'s row belonging to a stack/repository the attacker never authenticated for, and writes a forged status (state, description, target_url, context) onto it via `create_status_from_github!`.

Why existing guards don't stop this: `verify_signature` only validates who sent the request, not which records the handler is permitted to touch. `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler.params` only validate presence/shape of `sha`, `state`, etc. - they do not require or check `repository.full_name` against the matched commit's stack. Unlike other handlers that use the `Handler#stacks` helper (scoped by `repository_name`), `StatusHandler` never calls it.

### Impact Explanation
A forged/unauthorized `Status` row (state, description, target_url, context) is written against a `Commit` belonging to a stack/repository the attacker never proved ownership of. Because commit statuses drive `Commit#deployable?`, CI-gating (`blocked?`), and can trigger `ProcessMergeRequestsJob` / continuous-deployment merges (per `test/models/commits_test.rb` behavior around `add_status`), a forged "success" status from an unrelated, attacker-controlled org can unblock or trigger downstream automated actions (merge requests, continuous deploys) on a victim org's stack. This is a cross-tenant write triggered by a payload verified under a different, unprivileged organization - matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions: (1) the same commit `sha` must exist as a `Commit` row under two different stacks/repos - realistic via GitHub forking, since forked repos retain identical shas for shared history, and Shipit syncs commits into its DB per-stack via its normal GitHub sync jobs; (2) attacker needs a repo (their own fork, or any repo) onboarded as a Shipit stack so they can send a validly-signed webhook. No secrets, sessions, or privileged roles are required - the attacker only needs to control a GitHub repository (fork) and be able to trigger/emit a `status` webhook from it (e.g., via their own CI or by directly POSTing a signed payload if they control the webhook secret for their own repo, which they legitimately do). This is repeatable against any victim stack that shares any commit sha with an attacker-reachable repo, which is common because of forking.

### Recommendation
Scope `StatusHandler#process` to the verified repository, mirroring the `Handler#stacks` helper pattern used elsewhere: resolve `stacks` (or `stack_ids`) from `payload.dig('repository', 'full_name')`, and restrict the query to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or `stack: stacks`) before calling `create_status_from_github!`. This enforces `commit.stack.repository == verified repository` for every mutated row.

### Proof of Concept
Minitest plan (model/handler-level, no live GitHub):
```ruby
test "StatusHandler#process does not mutate commits belonging to a different repository" do
  org_a_repo = shipit_repositories(:org_a_repo) # full_name "org-a/repo"
  org_b_repo = shipit_repositories(:org_b_repo) # full_name "org-b/repo"
  stack_a = org_a_repo.stacks.first
  stack_b = org_b_repo.stacks.first

  shared_sha = "deadbeef" * 5
  commit_a = stack_a.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")
  commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/forged',
    'repository' => { 'full_name' => org_a_repo.full_name, 'owner' => { 'login' => 'org-a' } }
  }

  # Binding under test:
  # commit_b.stack.repository.owner ("org-b") should NOT equal verifying org ("org-a")
  assert_not_equal commit_b.stack.repository.owner, 'org-a'

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_b.reload
  # FAILS today: commit_b receives a status even though the webhook was verified for org-a
  assert_equal 0, commit_b.statuses.where(context: 'ci/forged').count,
    "commit belonging to a different repository/org must not receive a status from a webhook verified under another org"
end
```
This demonstrates that `Commit.where(sha: params.sha)` in [4](#0-3)  matches `commit_b` and calls `create_status_from_github!` on it despite the payload's `repository.owner` being `org-a`, proving the cross-tenant write.
