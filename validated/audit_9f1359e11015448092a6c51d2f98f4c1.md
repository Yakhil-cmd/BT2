### Title
Unauthenticated DoS via unguarded `throw` on `definition template` lookup mismatch during signature validation - (File: definition.js)

### Summary
`Definition.validateAuthentifiers()`'s inner `evaluate()` function handles the `'definition template'` address-definition opcode by querying the referenced `definition_template` unit and directly asserting `rows.length === 1` with an unguarded `throw Error("not 1 template")` if the assumption fails, rather than returning a graceful validation error through the `cb()` callback chain like every other opcode in the file does.

### Finding Description
When validating a posted unit's signatures, `validateAuthor()` in `validation.js` calls `Definition.validateAuthentifiers()` for every author of every incoming unit [1](#0-0) . Inside `validateAuthentifiers`, `evaluate()` re-resolves any `'definition template'` node in the address definition tree with the query:
```
SELECT payload FROM messages JOIN units USING(unit)
WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1
```
and immediately does `if (rows.length !== 1) throw Error("not 1 template");` before parsing the payload [2](#0-1) .

This is inconsistent with the sibling function `validateDefinition()` (used earlier in the very same call for structural checks), which performs the identical query but treats a non-1 row count as an ordinary, recoverable validation failure: `return cb("template not found or too many")` [3](#0-2)  (equivalently in `definition.js` lines 306-343 as shown by the "definition template" case there).

Because `validateDefinition()` and `validateAuthentifiers()` are two independent async database round-trips performed at different points during the same `validate()` call, node.js's single-threaded event loop can interleave other unit/joint processing between them. If the referenced `definition_template` unit's stability/sequence state changes between the first ("safe") lookup and the second ("unsafe") lookup — e.g., because a concurrently-processed conflicting/double-spending unit flips its `sequence` away from `'good'`, or because it becomes/ceases to be stable — the second query in `evaluate()` can return zero or more-than-one rows and hit the bare `throw`.

This throw happens inside an asynchronous `conn.query` callback, outside of any `try/catch` that funnels it back into `validate()`'s `callbacks.ifUnitError/ifJointError` machinery, so it propagates as an uncaught exception. `network.js` intentionally rethrows any uncaught exception to crash the whole node process to "avoid ending up in an inconsistent state" [4](#0-3) .

### Impact Explanation
Any full node processing a unit whose address definition references a `'definition template'` node can be crashed by an attacker who can arrange for the referenced template unit's stability/sequence to change concurrently with validation of the crafted unit (e.g., by simultaneously posting a conflicting/double-spending unit touching the template unit's author chain). This is a network-wide, unauthenticated DoS: an unprivileged unit poster can knock full nodes offline, which threatens the network's ability to confirm new units if repeated against enough nodes.

### Likelihood Explanation
Exploitation requires the attacker to win a timing race between two DB round-trips inside a single `validate()` call, by injecting a second unit that flips the referenced template unit's `sequence`/`is_stable` status. This is a template/definition-template feature that must actually be used by some address, and the attack needs to be timed against another node's processing of the crafted unit, which is feasible for an attacker who controls timing of their own broadcasts but not guaranteed on the first attempt; it can be retried at low cost until it lands, since posting units is unprivileged and cheap.

### Recommendation
Make the `'definition template'` handling in `Definition.validateAuthentifiers()`'s `evaluate()` consistent with `validateDefinition()`: replace the unguarded `throw Error("not 1 template")` at `definition.js:812` with a graceful `return cb2(false)` (or equivalent recoverable failure) so any race/inconsistency degrades to "authentifier verification failed" instead of crashing the process. More generally, audit all `throw Error(...)` statements reachable from data races between two DB reads of attacker-influenced state within the same `validate()`/`validateAuthentifiers()` call and replace them with graceful validation failures.

### Proof of Concept
1. Define an address `A` whose definition includes `['definition template', [T, {...}]]`, where `T` is a `definition_template` unit posted by an author whose address also has other units in flight.
2. Post a unit `U1` signed by `A` that exercises this definition path (so `validateAuthentifiers` will be invoked and will re-query `T`'s status).
3. Concurrently (interleaved in the event loop while `U1` is mid-validation, i.e., between `validateAuthor`'s initial structural `validateDefinition` pass and the later `validateAuthentifiers` signature-evaluation pass), broadcast a second unit `U2` that conflicts with/double-spends against the author chain of `T`, causing `T`'s `sequence` or `is_stable` value to change on the target node before the second query in `evaluate()` runs.
4. On the target node, the second `conn.query` callback for the `'definition template'` case in `definition.js:806-818` receives `rows.length !== 1` and executes the unguarded `throw Error("not 1 template")`, which is not caught inside `validate()`'s async chain and reaches `process.on('uncaughtException', ...)` in `network.js`, crashing the node process.
