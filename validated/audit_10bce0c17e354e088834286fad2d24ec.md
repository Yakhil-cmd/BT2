### Title
`RuleEngine._check_condition` raises on non-string `tool_input` fields, causing hookify's PreToolUse hook to fail open and silently allow blocked commands - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._extract_field` only coerces field values to `str` when the condition's `field` name is a literal key of `tool_input` (e.g. `command`); for the documented alias fields `new_text`/`old_text`/`file_path`/`content` (Write/Edit/MultiEdit) and the `command` fallback path for Bash, it returns the raw `tool_input` value without any type check. `_check_condition` then calls `.startswith()`/`.endswith()` or `pattern in field_value` on that raw value. If the value is not a `str` (e.g. a dict/list/int), these calls raise `AttributeError`/`TypeError`, which propagates uncaught through `_rule_matches` and `evaluate_rules` up to the hook script's top-level `except Exception` handler in `pretooluse.py`, which returns a plain `systemMessage` response with no `permissionDecision: deny` - i.e. an "allow" outcome - even though a configured `block` rule should have fired.

### Finding Description
The call chain is `pretooluse.py:main()` → `RuleEngine.evaluate_rules` → `_rule_matches` → `_check_condition` → `_extract_field`.

In `_extract_field` [1](#0-0) , direct dict-key lookups are safely coerced with `str(value)`. However, the alias/special-case branches for Bash (`command`), Write/Edit (`content`, `new_text`/`new_string`, `old_text`/`old_string`, `file_path`) and MultiEdit return `tool_input.get(...)` values (or a `' '.join(...)` over them) directly, with no `isinstance`/`str()` guard [2](#0-1) .

`_check_condition` then applies string-only operators to whatever value comes back: `pattern in field_value`, `field_value.startswith(pattern)`, `field_value.endswith(pattern)` [3](#0-2) . Only `regex_match` has its own local exception handling via `_regex_match`'s `try/except re.error` [4](#0-3) ; the other operators are unguarded, so a non-`str` field value (e.g. `new_string` being a list/dict) raises `AttributeError`/`TypeError` inside `_check_condition`.

This exception propagates out of `_rule_matches` and `evaluate_rules` (neither wraps the per-rule evaluation in try/except) all the way to `pretooluse.py:main()`'s top-level handler: [5](#0-4) 
That handler emits `{"systemMessage": f"Hookify error: {str(e)}"}` with no `hookSpecificOutput.permissionDecision` and no `decision: block` key, which Claude Code's PreToolUse contract treats as "no opinion / allow", then `sys.exit(0)`. Crucially, because the exception aborts `evaluate_rules` entirely, **every other rule in the loop - including a legitimate `action: block` rule matching, say, `rm -rf` - also never gets evaluated**, since the loop in `evaluate_rules` [6](#0-5)  is a single flat loop with no per-rule isolation.

### Impact Explanation
This defeats hookify's core security purpose: a configured `block` rule (e.g. blocking dangerous `rm -rf`, blocking hardcoded secrets in edits) can be silently bypassed for the entire hook invocation if any single condition being evaluated in that batch encounters a non-string field value, because the whole rule-evaluation pass throws and the top-level catch defaults to allow. This is a fail-open defect in a security enforcement mechanism (PreToolUse hook), matching a trust-boundary/approval-bypass class of impact - a would-be blocked Bash/Edit/Write/MultiEdit operation proceeds instead of being denied.

### Likelihood Explanation
Reliably reproducible in isolation by calling `RuleEngine.evaluate_rules`/`_check_condition` directly with a crafted `tool_input` where an aliased field (`new_string`, `old_string`, `file_path`, or an item of MultiEdit's `edits` list) is a non-string JSON value. Whether an external attacker can force Claude Code itself to emit such a malformed tool call (rather than a normal string-valued tool call enforced by the tool's own JSON schema) is not established from this repo alone; the surrounding hook infrastructure otherwise assumes/expects string arguments. The concrete, demonstrated flaw is the fail-open exception-handling design in `pretooluse.py`/`rule_engine.py`, independent of how the malformed value is introduced.

### Recommendation
- In `_extract_field`, coerce every returned value with the same `isinstance(value, str)`/`str(value)` treatment currently only applied to the direct-key path (lines 196-200), so `_check_condition` never receives a non-`str`.
- Wrap each rule's evaluation in `_rule_matches`/`evaluate_rules` in a per-rule `try/except`, logging the failure and treating that specific rule as "did not evaluate cleanly" without aborting evaluation of the remaining rules.
- In `pretooluse.py` (and the other hook scripts), when an exception occurs during rule evaluation, fail closed for `block`-configured rules (e.g. deny by default, or at minimum surface a clear warning) rather than defaulting to full allow with only a `systemMessage`.

### Proof of Concept
Unit test against `RuleEngine` directly:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_non_string_field_does_not_silently_bypass_block_rule():
    rule = Rule(
        name="block-secret",
        enabled=True,
        event="file",
        action="block",
        conditions=[Condition(field="new_text", operator="starts_with", pattern="SECRET")],
        message="blocked",
    )
    engine = RuleEngine()
    # new_string is a list instead of str (type confusion)
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Edit",
        "tool_input": {"file_path": "x.py", "new_string": ["SECRET", "leak"], "old_string": ""},
    }
    result = engine.evaluate_rules([rule], input_data)
    # Must never silently return {} (allow) due to an internal crash;
    # either raise loudly for the caller to handle, or still produce a deny.
    assert result != {}
```
Expected today: `evaluate_rules` raises `AttributeError: 'list' object has no attribute 'startswith'` uncaught inside `_check_condition`, and when driven through `pretooluse.py`'s `main()` with this `input_data` on stdin, the process exits 0 printing `{"systemMessage": "Hookify error: ..."}` with no `permissionDecision: deny` - demonstrating the fail-open bypass at the hook boundary.
