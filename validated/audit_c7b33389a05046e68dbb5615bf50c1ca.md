### Title
Unauthenticated Bridge P2P Peer Can Inject Arbitrary JSON-RPC Calls Into Main Bridge's Internal RPC Server — (`node/sc/main_bridge_handler.go`)

### Summary

`MainBridgeHandler.handleCallMsg` forwards the raw bytes of any `ServiceChainCall` P2P message verbatim to the main bridge's internal `rpcConn` pipe with zero content inspection or caller authentication. Any peer that passes the trivially-satisfiable bridge handshake (public network/chain-ID/TD/head values) can inject arbitrary JSON-RPC method calls into the isolated `mb.rpcServer` that has all public `klay`/`kaia` APIs registered.

### Finding Description

**Setup of the internal RPC server** (`mainbridge.go` lines 153–156):

```go
mb.rpcServer = rpc.NewServer()
p1, p2 := net.Pipe()
mb.rpcConn = p1
go mb.rpcServer.ServeCodec(rpc.NewCodec(p2), 0)
```

`mb.rpcConn` (p1) is the write-end of an in-process pipe; the RPC server reads from p2. [1](#0-0) 

**APIs registered on `mb.rpcServer`** (`mainbridge.go` lines 239–255): every API with `Public: true` and namespace `klay` or `kaia` is registered — this includes transaction-submission methods such as `klay_sendTransaction` / `kaia_sendTransaction`. [2](#0-1) 

**The vulnerable handler** (`main_bridge_handler.go` lines 86–102):

```go
func (mbh *MainBridgeHandler) handleCallMsg(p BridgePeer, msg p2p.Msg) error {
    data := make([]byte, msg.Size)
    err := msg.Decode(&data)
    ...
    _, err = mbh.mainbridge.rpcConn.Write(data)   // ← no content check
    ...
}
```

The raw P2P payload is written directly to the RPC pipe. There is no JSON schema validation, no method allow-list, and no authentication token check. [3](#0-2) 

**Dispatch path** (`main_bridge_handler.go` lines 48–57): `HandleSubMsg` routes `ServiceChainCall` (opcode `0x06`) straight to `handleCallMsg`. [4](#0-3) 

**Handshake is trivially satisfiable** (`mainbridge.go` line 376): the bridge handshake only checks `networkId`, `chainID`, `td`, and `head` — all values that are publicly observable on-chain. No cryptographic proof of identity is required. [5](#0-4) 

### Impact Explanation

An attacker who can reach the bridge P2P port (`MainBridgePort`) can:

1. Pass the handshake using public chain metadata.
2. Send a `ServiceChainCall` message whose payload is a crafted JSON-RPC request, e.g.:
   ```json
   {"jsonrpc":"2.0","method":"klay_sendTransaction",
    "params":[{"from":"<bridge_operator_addr>","to":"<attacker>","value":"0x..."}],
    "id":1}
   ```
3. The payload is written verbatim to `rpcConn`, processed by `mb.rpcServer`, and — because the bridge operator account must be unlocked for normal bridge operation — the transaction is signed and submitted to the main chain.

This constitutes **unauthorized KAIA transfer** from the bridge operator account. The claim's specific mention of `personal_*` / `admin_*` / `eth_*` is incorrect — those namespaces are not registered on `mb.rpcServer`. The real exploitable surface is the public `klay`/`kaia` APIs, most critically `klay_sendTransaction` / `kaia_sendTransaction`.

### Likelihood Explanation

- The bridge P2P port is a network-accessible service endpoint; any host that can reach it qualifies.
- The handshake requires only public information.
- Bridge operator accounts are routinely kept unlocked during bridge operation, making `klay_sendTransaction` exploitable without any additional precondition controlled by the attacker.

### Recommendation

1. **Method allow-list**: before writing to `rpcConn`, parse the JSON-RPC `method` field and reject anything outside a narrow set of read-only or explicitly bridge-required methods.
2. **Shared secret / HMAC**: require bridge peers to include a pre-shared token in `ServiceChainCall` messages; verify it before forwarding.
3. **Separate RPC server**: do not register transaction-submission APIs (`klay_sendTransaction`, etc.) on `mb.rpcServer`; restrict it to the minimal read-only surface the bridge actually needs.

### Proof of Concept

```go
// 1. Dial the main bridge P2P port and complete the trivial handshake
//    (networkId, chainID, td, head are all public).
// 2. Encode a crafted JSON-RPC payload via RLP and send it as ServiceChainCall (0x06).
payload := []byte(`{"jsonrpc":"2.0","method":"klay_sendTransaction",` +
    `"params":[{"from":"0x<bridge_operator>","to":"0x<attacker>","value":"0xDE0B6B3A7640000"}],` +
    `"id":1}`)
p2p.Send(rw, ServiceChainCall, payload)
// 3. Read the ServiceChainResponse; assert it contains a transaction hash,
//    confirming the call was executed with node authority.
```

The `handleCallMsg` function writes `payload` to `rpcConn` without inspection, the internal `rpcServer` dispatches `klay_sendTransaction`, and — with the bridge operator account unlocked — the transfer executes on the main chain. [3](#0-2) [2](#0-1)

func (mbh *MainBridgeHandler) handleCallMsg(p BridgePeer, msg p2p.Msg) error {
	logger.Trace("mainbridge writes the rpc call message to rpc server", "msg.Size", msg.Size, "msg", msg)
	data := make([]byte, msg.Size)
	err := msg.Decode(&data)
	if err != nil {
		logger.Error("error in mainbridge message handler", "err", err)
		return err
	}

	// Write to RPC server pipe
	_, err = mbh.mainbridge.rpcConn.Write(data)
	if err != nil {
		logger.Error("failed to write to the rpc server pipe", "err", err)
		return err
	}
	return nil
}
