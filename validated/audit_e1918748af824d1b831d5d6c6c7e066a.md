### Title
Cross-organization commit-status forgery via webhook signature/repository binding mismatch - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, a value read straight out of the still-unverified JSON body. Once the signature check passes (using whichever organization's secret matched), the `status` event handler processes the same body but never re-checks that the acted-upon resource belongs to that organization — it looks up commits globally by SHA. This breaks the equality "organization whose secret authenticated the request" == "repository/commit that gets written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config purely from an attacker-supplied field of the JSON payload: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, taken from the raw body before any cryptographic check has occurred; it is only used to decide *which* organization's `webhook_secret` (`Shipit.github(organization: repository_owner)`) must match the `X-Hub-Signature` header, via `GithubApp#verify_webhook_signature`: [3](#0-2) 

For most webhook handlers this is harmless because the handler independently re-derives the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` and scopes all queries to that repository, e.g.: [4](#0-3) [5](#0-4) 

However, `StatusHandler` — used for the `status` event that Shipit relies on for CI gating (`ci.require`) — does not perform this scoping at all. It looks up commits **globally, by SHA only**, with no relation to `repository.full_name` or `repository.owner.login`: [6](#0-5) 

So the binding actually enforced is:
`verify_signature` binds *(request, X-Hub-Signature)* to *(organization named in `repository.owner.login`)*, while `StatusHandler#process` binds *(request body)* to *(any `Commit` row in the database whose `sha` matches, across all organizations/stacks)*. These are two different objects derived from the same untrusted body, and nothing forces them to refer to the same organization/repository.

### Impact Explanation
An attacker who legitimately controls (or is granted access to configure) any single organization that Shipit is configured to trust — i.e., they know that organization's `webhook_secret` (a standard, low-privilege GitHub App installation credential for their own org/repo, not a Shipit credential) — can craft an arbitrary `status` event body:
- `repository.owner.login` = their own organization (so `verify_signature` selects and matches their known secret),
- `sha` = the SHA of a commit belonging to a *different*, more sensitive stack managed by the same Shipit instance,
- `state` = `success`, `context` = whatever CI context that target stack's `shipit.yml` `ci.require` expects.

Because `StatusHandler` never checks that the commit's stack/repository corresponds to the organization that authenticated the webhook, this HMAC-valid-but-cross-tenant payload will create a fake passing `CommitStatus` on the victim commit (`commit.create_status_from_github!(params)`), satisfying `ci.require` checks and enabling an unauthorized deploy/merge of a commit that never actually passed CI in the target repository. This matches the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Exploitability requires only that the attacker controls one organization/app installation registered in Shipit's `github:` configuration (a realistic scenario for any Shipit instance managing multiple orgs/teams with differing trust levels), plus knowledge of that org's SHA of a target commit (visible via GitHub's public/commit API in many setups). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only the ability to send an HTTP POST with a correctly-HMAC'd body to the shared `/webhooks` endpoint.

### Recommendation
`StatusHandler` (and any other handler mutating state) must scope its lookup to the repository/stack whose organization matches the one that authenticated the webhook signature — i.e., resolve the commit via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`-derived stacks, and additionally verify that this repository's owner equals the `repository_owner` value used during signature verification, rather than querying `Commit` unscoped by SHA alone.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` (attacker-controlled) and `org-b` (victim, more sensitive), each with its own `webhook_secret` in `secrets.yml`.
2. Attacker obtains a commit SHA `S` belonging to a stack under `org-b/high-value-repo` that requires CI context `ci/tests` before deploy.
3. Attacker builds JSON body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/attacker-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac using org-a's known webhook_secret>` over this exact body, per `Hook::DeliverySigner`/`GithubApp#verify_webhook_signature` logic.
5. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` = `org-a`, fetches `org-a`'s app, and the signature validates successfully.
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the victim commit under `org-b`, and calls `create_status_from_github!`, marking `ci/tests` as `success` for a commit the attacker never had CI access to — satisfying `ci.require` for the victim stack. [7](#0-6) [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```
