### Title
Single-step address_definition_change with no propose/confirm allows irreversible address bricking - (File: validation.js, composer.js)

### Summary
Obyte's `address_definition_change` mechanism changes an address's signing "owner" (its definition/authentifier set) in a single, immediately-binding step — the same anti-pattern flagged in the analog `TimeLock.changeOwner` report. A wallet or AA-controlled address posts a message containing only a `definition_chash` (the hash of a new definition array); the actual definition array isn't required until the next spend. If the committed `definition_chash` does not correspond to any definition the poster can produce (wrong hash, corrupted/lost new keyset, or a bugged wallet computing the chash incorrectly), the address is permanently and irreversibly bricked once the change becomes stable — exactly the "no _newOwner validity check, no way back" scenario described in the report, except here the "owner" is the address's authentication definition, and the impact is the address's own funds becoming permanently frozen.

### Finding Description
`composeDefinitionChangeJoint(from_address, definition_chash, signer, callbacks)` in `composer.js` builds an `address_definition_change` message from nothing but a `definition_chash` string: [1](#0-0) 

Server-side, `validateInlinePayload`'s `"address_definition_change"` case only checks the payload shape and that `definition_chash` is a syntactically valid base32 address/chash — there is no check that the chash corresponds to a definition array the message author actually possesses or has revealed anywhere: [2](#0-1) 

Once this message becomes part of a unit and that unit stabilizes, `readDefinitionChashByAddress` / `storage.readDefinitionByAddress` treat this new `definition_chash` as authoritative for the address going forward (the old definition is retired): [4](#0-3) 

Crucially, unlike a two-step (propose/confirm) design, the change cannot be corrected once posted: `checkNoPendingChangeOfDefinitionChash` in `validation.js` forbids the address from posting *any* further unit (including a corrective definition change) while the previous change is still unstable/pending: [3](#0-2) 

So the sequence is:
1. Address owner (or an AA/wallet script acting on the address's behalf) posts `address_definition_change` with `definition_chash = H(D)`.
2. Before the unit stabilizes, the owner cannot fix a mistake by sending a corrective message from the same address (blocked by `checkNoPendingChangeOfDefinitionChash`).
3. Once stable, the address's canonical definition is permanently `H(D)`. If the owner cannot produce `D` (typo, wrong hash computed by a buggy signer/wallet, hash of an address they don't control, etc.), no future unit can ever be authored from that address again — because `validateAuthor`'s `handleDuplicateAddressDefinition`/`ifDefinitionNotFound` path in `validation.js` requires the revealed `definition` to hash exactly to the stored `definition_chash`. [5](#0-4) 

This mirrors the reported `TimeLock.changeOwner` pattern precisely: a privileged-role/ownership change is committed in a single irrevocable step with no "propose new value → confirm from new value" safety net, so a single bad input permanently locks out the legitimate controller.

### Impact Explanation
Any bytes, assets, or AA-issued tokens held at the affected address become permanently inaccessible — nobody can ever again produce a valid signature/authentifier set for that address, since the stored `definition_chash` cannot be satisfied. This is a concrete, irreversible fund-freezing event scoped exactly to "address definitions and authentifiers" reachable by an ordinary unprivileged unit poster (the address owner) via a single posted unit, matching the allowed "AA fund loss or freezing" / address-definition impact class. Given that address definition changes are also used to rotate AA-controlled multisig/cosigner sets and shared addresses, a single malformed `definition_chash` (e.g., from wallet software incorrectly computing `objectHash.getChash160` on the intended new definition) can permanently freeze funds belonging to a shared/multi-party address.

### Likelihood Explanation
Medium likelihood: this requires user/wallet error (miscomputing or mistyping `definition_chash`) rather than an external attacker, matching the "Medium" severity of the original TimeLock finding, which is also a self-inflicted-mistake class of bug. It is realistically reachable any time a wallet, script, or AA composes an `address_definition_change` and the definition_chash is derived incorrectly (bug in signer implementation, wrong variable substitution in a template, or a user manually constructing the message).

### Recommendation
Introduce a two-step, propose/confirm flow analogous to the recommended `TimeLock` fix:
1. Require the `address_definition_change` message to include the full candidate `definition` array (not just its chash) so the protocol/wallet can validate the definition (via `Definition.validateDefinition`) *before* committing to the chash, rejecting invalid/inconsistent definitions outright.
2. Alternatively, keep the current commit-then-reveal design but add a decoupled "cancel-if-not-revealed-within-N-mci" fallback (a change reverts to the previous definition automatically if the corresponding definition is never revealed by a controllable deadline), giving the owner a bounded recovery window instead of permanent lockout.

### Proof of Concept
1. Owner of address `A` (definition `D0`) uses a wallet/AA to compose an `address_definition_change` message with `definition_chash = X`, where `X` is not `objectHash.getChash160(D1)` for any definition `D1` the owner can produce (e.g., due to a hashing bug, wrong template substitution, or a copy/paste error) — see `composer.js:85-87` where only the chash is embedded, and `validation.js:1719-1745` where only chash format is checked.
2. The unit is broadcast and accepted (validation only checks `isValidAddress(payload.definition_chash)`), then stabilizes.
3. Owner attempts to spend from `A` in a later unit and supplies `objAuthor.definition = D1`; `validateAuthor`'s `handleDuplicateAddressDefinition`/definition-check path (`validation.js:1464-1483`) rejects it because `getChash160(D1) !== X`, and since `D` producing `X` is unknown, no valid unit can ever be authored from `A` again — all funds at `A` are permanently frozen.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
