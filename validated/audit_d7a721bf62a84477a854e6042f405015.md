### Title
`StatusHandler#process` writes GitHub statuses onto commits by SHA alone, without checking that the SHA belongs to the webhook's authenticated repository, letting one tenant's status webhook mutate another tenant's `Commit`/`blocked?` state - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no filter on the repository/stack that authenticated the webhook. Because `Status#blocking?` and `Commit#blocked?`/`deployable?` are computed per-stack from `stack.blocking_statuses` and `Status.context`, an attacker who controls any Shipit-onboarded repository can push a `status` webhook for a SHA that happens to also exist as a commit row in a victim Stack, and inject a status (e.g. `state: failure`, `context` matching the victim's `blocking_statuses`) that corrupts `blocked?`/`deployable?` evaluation for the victim's newer undeployed commits.

### Finding Description
The broken binding is: **repository authenticated by webhook == repository whose commit/status is mutated**. This should hold as `webhook.repository.full_name == commit.stack.repository.full_name`, but the code never enforces it for the `status` event.

- `app/controllers/shipit/webhooks_controller.rb:24-49` (`verify_signature`) authenticates the webhook only against the *organization* (`Shipit.github(organization: repository_owner)`), matching the HMAC signature computed with that org's configured `webhook_secret`. It does not verify that the specific `sha`/commit referenced in the payload belongs to the authenticated repository.
- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ```
  This is the only handler in the codebase that does **not** scope its work through `Repository.from_github_repo_name(repository_name)` (compare to `pull_request/opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, `labeled_handler.rb`, which all resolve `repository` from `params.repository.full_name` before acting). `StatusHandler` doesn't even declare `repository` in its `params` schema at all (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` only) — the payload's repository field is completely ignored for authorization purposes and is only used upstream by the controller to pick which org's HMAC secret to check.
- `commit.create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` in `app/models/shipit/commit.rb:165-169` writes a `Status` row scoped to `commit.stack_id` — i.e., the *victim* stack's id, using attacker-controlled `state`/`context`/`target_url`/`description` from the payload.
- `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) is `!success? && commit.blocking_statuses.include?(context)`, where `commit.blocking_statuses` delegates to `stack.blocking_statuses` (`app/models/shipit/commit.rb:57-58`, `app/models/shipit/deploy_spec.rb:202-204`) — i.e., the **victim stack's** configured blocking contexts.
- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) scans `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` — if the attacker's injected status on the shared older commit satisfies `blocking?` under Stack A's own `blocking_statuses` config, every newer undeployed commit on Stack A becomes blocked (`deployable?` in `commit.rb:227-229` also flips).

**Exploit flow:** Attacker owns/controls Repository B, already onboarded to the same Shipit instance (any org with a configured GitHub App/webhook secret qualifies; per the rules the attacker is "any GitHub user who can... emit webhooks from a repository they own"). A commit with SHA `S` exists both in Repository B's history and, coincidentally or via shared history (fork, mirror, cherry-pick, subtree merge, monorepo split), as a `Commit` row in Victim Stack A (Repository A) with `id` older than Stack A's newer undeployed commits. Attacker sends a `status` webhook, signed correctly for their own org/repo, with `sha: S`, `state: "failure"`, `context: <one of Stack A's blocking_statuses>`. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` finds **all** `Commit` rows with `sha: S` — including Stack A's — and writes a `Status` on each, `stack_id` set to each commit's own `stack_id` (Stack A's id for that row). Stack A's `blocked?`/`deployable?` now evaluates as blocked for all of Stack A's undeployed commits newer than `S`, without any request ever authenticating against Repository A.

Existing guards do not catch this: `verify_signature` only checks org-level HMAC, not per-commit repository ownership; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` doesn't require or validate `repository.full_name` at all; there is no `require_permission!`/`stacks` scope check in this handler (unlike the PR handlers that call `Repository.from_github_repo_name`).

### Impact Explanation
An attacker fully controlling only their own (onboarded) repository can write `Status` rows against a completely different tenant's `Commit`/`Stack`, and through `Status#blocking?` → `Commit#blocked?`/`deployable?`, block or unblock deploys and CI-gated merges for a stack they do not own, control, or have any Shipit permission on. This is a payload for one repository mutating another repository's stack/commit state, matching the "Critical" impact category explicitly listed in the rules ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any commit SHA collision the attacker can arrange or discover across tenants sharing this Shipit instance, and blast radius scales with however many onboarded repositories/stacks the Shipit host serves.

### Likelihood Explanation
Preconditions: the attacker's own repository/org must already be onboarded to the Shipit instance with a valid webhook secret (a normal, low-cost setup for anyone able to add a repo, common in internally-hosted multi-tenant Shipit deployments); Victim Stack A must have `blocking_statuses` configured via `deploy_spec` (`ci.blocking` in `shipit.yml`); and a SHA must be shared between the attacker's repo and a commit already ingested into Stack A's undeployed range (realistic via forks, mirrors, subtree merges, or repos with intentionally shared history/monorepo splits — common in organizations that mirror or fork internal repos). No Shipit session, API token, or GitHub secret for the victim is required, only the attacker's own legitimate webhook credentials. The attack is a single unauthenticated-to-the-victim HTTP POST and is fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the pattern used by the pull-request handlers: require `repository.full_name` in the `params` schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `repository.stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently join through `stacks`/`Stack` scoped to that repository) before calling `create_status_from_github!`. Reject/no-op if the resolved repository has no matching stack, exactly as `Handler#stacks` already does for other handlers.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`), no live GitHub:

1. Set up two stacks/repositories in fixtures: `stack_victim` (Repository A) with `cached_deploy_spec` containing `ci.blocking: ['soc/compliance']`, and `stack_attacker` (Repository B), representing a different tenant/org.
2. Create a shared `Commit` SHA `S` as an older commit in `stack_victim`'s undeployed range (`older_commit`), and a newer commit `newer_commit` in `stack_victim` (both `reachable`, `newer_commit.id > older_commit.id > stack_victim.last_deployed_commit.id`). Also create a `Commit` row with the same `sha: S` belonging to `stack_attacker`.
3. **Binding before:** assert `newer_commit.blocked? == false` (no blocking status yet on `older_commit`).
4. Simulate the attacker's authenticated webhook for `stack_attacker`'s org/repo (stub/mimic `GithubApp#verify_webhook_signature` to return true, as existing tests do via `GithubHook.any_instance.stubs(:verify_signature).returns(true)` or by computing a valid HMAC for the attacker's org secret) with body `{ sha: S, state: 'failure', context: 'soc/compliance', repository: { owner: { login: attacker_org } } }`, dispatched through `POST /webhooks` with `X-Github-Event: status`.
5. **Binding after:** reload `older_commit` (the victim's row with sha `S`) and assert a `Status` with `state: 'failure', context: 'soc/compliance'` was created with `stack_id: stack_victim.id`; assert `older_commit.reload.blocking? == true`; assert `newer_commit.reload.blocked? == true` and `newer_commit.deployable? == false`.
6. Assert the equality `webhook.repository.full_name == commit.stack.repository.full_name` is false for the written `Status` (attacker's repo ≠ `stack_victim`'s repo), demonstrating the cross-tenant write despite no authentication ever occurring against `stack_victim`'s repository/org.
