### Title
Webhook signature verified against attacker's own GitHub organization while stack lookup uses an unrelated `repository.full_name`, enabling cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC signature with by reading `repository.owner.login` from the untrusted JSON body, but the actual event handlers that mutate state (sync commits, create statuses, trigger deploys) select the target `Stack`/`Repository` using a *different* field from the same body, `repository.full_name`, with no check that the two are consistent.

### Finding Description
`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per GitHub organization from `secrets.github`, keyed by organization name [1](#0-0) . This means an operator can run Shipit for multiple organizations, each with its own webhook secret that the respective organization's admins configure on their own GitHub App/webhook.

`WebhooksController#verify_signature` determines which organization's secret to verify against purely from the JSON payload: [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`. Once the signature check passes, `Handler#stacks`/`Handler#repository_name` locate the target `Repository`/`Stack` using a **separate** field from the same payload, `repository.full_name`: [3](#0-2) 

Nothing enforces that `repository.full_name` actually belongs to the organization named in `repository.owner.login`. Since the entire raw POST body is attacker-supplied JSON (Shipit only checks the HMAC signature over the whole body, not GitHub's own delivery), an attacker who controls one organization onboarded to this Shipit instance (and therefore knows/controls that organization's webhook secret) can freely set `repository.owner.login` to their own organization while setting `repository.full_name` to any other organization/repository already configured in Shipit. The signature will be verified successfully using the attacker's own organization's secret, but the resulting `Handlers::PushHandler`/`StatusHandler`/`CheckSuiteHandler` will operate on the victim organization's `Stack` (e.g. `PushHandler#process` calling `stack.sync_github` and enqueuing `GithubSyncJob`, which fetches commits via `stack.github_api`, the victim's own GitHub credentials) [4](#0-3) .

The engine's own tests demonstrate the two fields are independently controlled in the payload and treated separately by the controller's org lookup versus the handlers' repository lookup: the "unknown github organization" test overwrites only `payload["repository"]["owner"]["login"]` while `repository.full_name` remains untouched [5](#0-4) .

This is the exact class of bug described in the report: two related fields (here, "organization that authenticated" vs. "repository that is written") are accepted together but never cross-validated, so the wrong record ends up being trusted/mutated.

### Impact Explanation
An attacker who legitimately controls one Shipit-registered GitHub organization (and thus its own webhook secret) can forge signed webhook deliveries that are attributed to and processed against a completely different, victim organization's stacks. This enables:
- Injecting arbitrary commit SHAs into a victim `Stack`'s commit history via `PushHandler` → `GithubSyncJob` → `stack.sync_github`, which can trigger continuous-deployment/auto-deploy flows on the victim stack.
- Forging CI `Status`/`check_suite` events against arbitrary victim commits (`StatusHandler`, `CheckSuiteHandler`), which can satisfy merge/deploy gating checks.

This qualifies as cross-repository writes/an unauthorized deploy path, a Critical-severity impact under the engine's own trust boundary (no repository write access, GitHub App key, or Shipit session should be able to write into another organization's stacks).

### Likelihood Explanation
Requires the attacker to control a GitHub organization already onboarded to the same Shipit instance (i.e., have a legitimate low-privilege tenant relationship), which is a realistic multi-tenant deployment scenario documented by the `github_app_config`/per-organization secrets design. No GitHub App private key, Shipit session, or `ApiClient` token is needed — only the ability to sign an arbitrary HTTP body with the attacker's own onboarded organization's webhook secret and POST it to the shared `/webhooks` endpoint.

### Recommendation
After verifying the HMAC signature, re-derive the organization from the same field used for stack/repository resolution (`repository.full_name`'s owner segment, or `organization.login` for org-level events) and reject the webhook (422) if it does not match `repository_owner` used for signature verification. Alternatively, verify the signature using the organization actually implied by `repository.full_name`, not a separately-read `owner.login` field.

### Proof of Concept
1. Attacker administers `attacker-org`, which is configured in Shipit's `secrets.github` with its own `webhook_secret` (known to the attacker as the org's GitHub App/webhook administrator).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` reads `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully [6](#0-5) .
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `stacks` helper resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for the victim's stacks on the target branch [3](#0-2) [4](#0-3) , causing writes/actions against `victim-org`'s stack despite the request only ever being authenticated as `attacker-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
