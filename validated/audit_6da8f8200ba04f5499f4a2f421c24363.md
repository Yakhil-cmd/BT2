### Title
Stack-scoped API token can read the CI status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient` token and the `Stack` it is allowed to touch: `stack_id_token == stack_acted_on`. `Shipit::Api::CCMenuController` breaks this binding by resolving the target stack directly from the request parameter instead of through the token-scoped `stacks` relation, allowing a token restricted to one stack to read CI/deploy status of any other stack.

### Finding Description
`BaseController` defines the canonical scoping mechanism for every API endpoint: [1](#0-0) 

Here, `stacks` is deliberately restricted to `current_api_client.stack_id` when the authenticated `ApiClient` carries one, and `stack` is derived from that restricted relation via `stacks.from_param!`. This is the intended equality: **`current_api_client.stack_id (if present) == stack being acted on`**.

`CCMenuController`, however, overrides the `authenticate_api_client` method to accept a bare `params[:token]` (instead of the `Authorization` header used elsewhere) and overrides `stack` to bypass the scoped relation entirely: [2](#0-1) 

Because `stack` calls `Stack.from_param!(params[:stack_id])` directly (unscoped `Stack`, not the token-scoped `stacks`), any valid `read:stack` token — regardless of the specific `stack_id` it was minted for — can be used to fetch the CCMenu XML of an arbitrary other stack simply by changing the `stack_id` route/path segment. `require_permission :read, :stack` only checks that the `"read:stack"` string is present in `ApiClient#permissions` via `check_permissions!`; it never checks stack identity: [3](#0-2) 

The `ApiClient` model explicitly supports a `stack_id`-restricted client (`belongs_to :stack, optional: true`, and the `stacks` scoping logic in `BaseController` exists specifically to honor it): [4](#0-3) 

`CCMenuController` is the only controller under `app/controllers/shipit/api/` that defines a private `stack`/`authenticate_api_client` override that departs from the shared, scoped implementation, so it is the single leak point that defeats this invariant engine-wide.

### Impact Explanation
This breaks the "a stack a token authorises versus a stack it touches" trust binding called out in scope. The CCMenu XML response exposes stack activity, last build status/label/time and web URL: [5](#0-4) 

Any holder of a valid, narrowly-scoped `read:stack` token (for example a CCMenu token generated for one project and pasted into a CI dashboard, per `CCMenuUrlController`) can pivot and use that same token to read deploy/build state of every other stack in the Shipit instance, which is an unauthenticated (out-of-scope) read of stack state — matching the specified High-impact category.

### Likelihood Explanation
No special privilege beyond possession of any `read:stack`-scoped API token is required, and CCMenu tokens are routinely embedded in URLs distributed to third-party CI dashboards, increasing exposure. The bypass requires only changing the `stack_id` path parameter of the CCMenu route; no cryptographic material needs to be forged since the attacker already has a legitimately signed token.

### Recommendation
Remove the private `stack` override in `CCMenuController` (or reimplement it using the inherited, scoped `stacks` relation from `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`) so that a stack-restricted `ApiClient` cannot resolve a stack outside of its `stack_id`.

### Proof of Concept
1. Create/receive a CCMenu URL for Stack A via `CCMenuUrlController#fetch`, which mints an `ApiClient` token with `permissions: ['read:stack']` and (per the intended scoping model) is meant to be limited to Stack A's `stack_id`.
2. Send `GET /api/<owner_b>/<repo_b>/<env_b>/ccmenu.xml?token=<token_for_stack_a>` for a different Stack B.
3. `authenticate_api_client` succeeds using the query-string token; `require_permission :read, :stack` passes because the token has `read:stack`. `stack` resolves Stack B directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction, and the controller renders Stack B's build status/label/URL to a caller who was only ever authorized for Stack A.
