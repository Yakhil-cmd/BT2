### Title
Webhook signature is validated against the organization named in the payload, not the repository the handlers actually act on, allowing cross-tenant / cross-repository forgery in multi-org Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`) from the untrusted JSON body. Every webhook `Handler`, however, resolves the *target* repository/stack using a different field from that same untrusted body: `repository.full_name`. Because Shipit officially supports hosting multiple, independently-configured GitHub organizations behind a single webhook endpoint, each with its own `webhook_secret`, an attacker who legitimately controls one onboarded organization can produce a validly-signed request whose "authenticating" field points at their own org while the "acted-upon" field points at a victim organization's repository.

### Finding Description
- `WebhooksController#verify_signature` picks the signing secret via `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and validates the raw body against that organization's secret through `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- Once verified, `create` forwards the *entire raw payload* (unmodified) to the event handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
- The base `Handler` class, used by `PushHandler` and others, resolves the target repository/stack from a *different* field of the same payload: `payload.dig('repository', 'full_name')`. [4](#0-3) 
- `PushHandler` uses that `stacks` scope to enqueue a sync to an attacker-supplied SHA on the branch derived from `ref`: `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }`. [5](#0-4) 
- Multi-organization configuration is a first-class, documented deployment mode: each organization has its own independent `webhook_secret`, `app_id`, `private_key`, etc. [6](#0-5) [7](#0-6) 
- `Shipit.github(organization:)` looks up the app/secret purely by the organization name key present in config, with no cross-check that the organization actually owns the repository referenced elsewhere in the payload. [8](#0-7) 

The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handler subsequently mutates`

but the code enforces:
`repository.owner.login (used for signature secret selection) != repository.full_name's owner (used for target repository lookup)`
with no equality check between them.

### Impact Explanation
In a multi-tenant Shipit instance, an attacker who is a legitimate (but unprivileged w.r.t. other tenants) member/admin of one onboarded GitHub organization ("OrgTwo") knows or can obtain their own org's `webhook_secret` (it is handed to the org admin when the GitHub App webhook is configured for that org, per `docs/setup.md`). They can craft an arbitrary JSON body and POST it directly to the shared `/webhooks` endpoint with:
- `repository.owner.login` = `"OrgTwo"` (their own org, used for signature verification)
- `repository.full_name` = `"OrgOne/victim-repo"` (a completely unrelated organization's repository, used by the handler)
- a valid `X-Hub-Signature` computed with OrgTwo's own secret.

`verify_signature` succeeds because it validates against OrgTwo's secret using OrgTwo's own name. `PushHandler` then resolves stacks belonging to `OrgOne/victim-repo` and forces a sync to an attacker-chosen `expected_head_sha`, i.e., an unauthorized write/sync targeting a repository/stack the attacker has no legitimate access to — a cross-repository/cross-tenant forgery of GitHub events. Depending on stack configuration (e.g., continuous deployment), this can escalate into an unauthorized deploy or rollback being scheduled for a victim organization's stack, matching the Critical "cross-repository writes / unauthorized deploy" bucket.

### Likelihood Explanation
Multiple onboarded organizations sharing one Shipit instance is an explicitly documented and supported configuration, not an edge case. Any org admin onboarded into such a deployment already legitimately possesses their own org's webhook secret, and the webhook endpoint accepts arbitrary raw JSON bodies without validating internal consistency between the "owner" field used for authentication and the "full_name" field used for authorization of the target. No GitHub delivery is required — a direct POST to `/webhooks` with a self-signed body is sufficient.

### Recommendation
Enforce that the organization used to select/verify the webhook signature is the same organization that owns the repository referenced by `repository.full_name` before dispatching to handlers. E.g., derive the owner strictly from `full_name.split('/').first` (or verify it matches `repository.owner.login`), and reject the request (422) if they disagree. Alternatively, look up the target `Repository`/`Stack` first and verify the signature using that specific repository's configured organization secret rather than trusting an organization name supplied independently in the payload.

### Proof of Concept
```
# Attacker legitimately administers OrgTwo (webhook_secret = "orgtwo-secret")
body = {
  "ref" => "refs/heads/master",
  "after" => "<attacker-chosen-sha>",
  "repository" => {
    "owner" => { "login" => "OrgTwo" },       # used by verify_signature -> picks OrgTwo's secret
    "full_name" => "OrgOne/victim-repo"        # used by Handler#repository_name -> victim's stack
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "orgtwo-secret", body)

POST /webhooks
X-Github-Event: push
X-Hub-Signature: <signature>
body: <body>

# verify_signature: repository_owner -> "OrgTwo" -> validates against OrgTwo's secret -> passes
# PushHandler: repository_name -> "OrgOne/victim-repo" -> enqueues stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")
#  for a stack the attacker has no access to.
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
