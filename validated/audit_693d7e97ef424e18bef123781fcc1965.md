### Title
Cross-organization webhook confusion via signature-key selection on unverified payload data - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* HMAC secret to verify a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified request body, then hands the *entire* raw body — including a separately-controlled `repository.full_name` field — to handlers that decide which `Stack`/`Repository` to act on. The field used to select the trust context (which org's secret proves authenticity) is never bound to, or cross-checked against, the field the handlers actually act on. This mirrors the report's root cause: signed data lacks a canonical, verified "domain" (contract/organization) that the consuming logic is required to match against.

### Finding Description
`Shipit.github(organization:)` supports a multi-organization deployment where each GitHub organization has its own `webhook_secret` configured independently in `secrets.yml` [1](#0-0) . `WebhooksController#verify_signature` derives the organization used to look up that secret purely from the JSON body itself, before any signature has been validated: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` then just checks that the raw body matches an HMAC computed with whatever secret was selected for that attacker-supplied organization name: [4](#0-3) 

Once verification "succeeds," `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full parsed body to the handler for the `X-Github-Event` header [5](#0-4) . Every handler resolves the target repository/stack from a *different* field in the same body — `repository.full_name` — not the `repository.owner.login`/`organization.login` value that was used to pick the signing secret: [6](#0-5) [7](#0-6) 

In a legitimate GitHub webhook these two fields are always consistent (`full_name` = `"<owner.login>/<repo>"`), because GitHub itself populates the whole `repository` object. But nothing in the code enforces that consistency — the signature only proves "this byte stream was HMAC'd with organization X's secret," not "the repository referenced inside this byte stream belongs to organization X." An attacker who legitimately administers a GitHub organization onboarded to this same multi-tenant Shipit instance (and therefore knows/possesses their own org's `webhook_secret`, which they had to paste into their own GitHub App's webhook configuration) can construct a payload where `repository.owner.login` (or `organization.login`) is their own org (so the secret lookup and HMAC check pass), while `repository.full_name` names a stack belonging to a completely different, unrelated organization also hosted on the instance.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." A cross-tenant attacker with knowledge only of their own org's webhook secret can:
- Forge a `push` event naming a victim org's `repository.full_name`/`ref`/`after`, causing `PushHandler#process` to call `stack.sync_github(expected_head_sha: ...)` on the victim's stack [8](#0-7) , forcing an unauthorized sync/deploy trigger against a repository they have no access to.
- Forge `status` events to inject fabricated CI status onto a victim's commits (`StatusHandler#process`) [9](#0-8) , which can be used to make an untested/malicious commit appear green and eligible for merge/deploy in the victim's merge queue.
- Forge `pull_request`/`check_suite` events against a victim's review stacks by supplying a victim `repository.full_name` while authenticating with the attacker's own org secret.

This is a cross-repository/cross-organization write achieved by exploiting an unauthenticated-until-verified field to select the verification key, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the operator to run a multi-organization Shipit deployment (explicitly supported and documented, see `github_app_config`/`github_organizations` in `lib/shipit.rb`) and requires the attacker to be a legitimate administrator of at least one onboarded organization (so they know that org's `webhook_secret`, which they themselves configured in their GitHub App settings). No repository write access, Shipit account, session, or API token is needed for the target org — only knowledge of one's *own* org's already-known secret and the ability to POST an arbitrary body to `/webhooks`. This is a realistic, reachable configuration for any Shipit instance shared across several GitHub organizations, which is exactly the use case the multi-org config schema exists for.

### Recommendation
Bind the signature-selection context to the field actually consumed by the handlers, e.g.:
- After selecting `repository_owner` for secret lookup, re-derive it from a canonical field and reject the request if `repository.full_name`'s owner segment (or `organization.login`) does not match the organization whose secret validated the signature.
- Alternatively, do not trust any body field to select which secret to verify against; instead resolve the expected organization from Shipit's own `Repository`/`Stack` records looked up by `repository.full_name`, and verify the signature only with that resolved organization's secret — never letting the payload itself choose its own trust anchor.
- More generally, follow the report's EIP-712-style recommendation adapted to webhooks: treat the signed payload as strictly typed per event and require the org/repo identity used for verification to be independently re-derived and compared, not read out of the same unauthenticated JSON that is later acted upon.

### Proof of Concept
1. Shipit is deployed with two organizations configured, `orgA` (attacker-administered) and `orgB` (victim), each with distinct `webhook_secret`s in `secrets.yml`, per `github_app_config` [10](#0-9) .
2. Attacker, as `orgA`'s GitHub App admin, knows `orgA`'s `webhook_secret` (they entered it into GitHub's App webhook settings themselves).
3. Attacker builds a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)`.
5. POST to `/webhooks` with `X-Github-Event: push`.
6. `verify_signature` resolves `repository_owner` = `"orgA"` from the body, fetches `orgA`'s `GitHubApp`, and `verify_webhook_signature` succeeds because the HMAC matches `orgA`'s secret [2](#0-1) .
7. `PushHandler` resolves `stacks` via `payload.dig('repository', 'full_name')` = `"orgB/victim-repo"` [6](#0-5) , and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `orgB`'s stack — an org the attacker never authenticated against.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
