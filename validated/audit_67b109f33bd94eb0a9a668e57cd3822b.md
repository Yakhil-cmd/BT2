### Title
Missing `return` after hash-calculation exception in `handleSavedPrivatePayments` causes double completion / crash-prone processing of private payment chains - (File: network.js)

### Summary
`network.js`'s `handleSavedPrivatePayments()` processes private-payment chains that a paired device (an untrusted private-payment counterparty) sent via `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`. Inside its `validateAndSave` closure, a `try/catch` around `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` fails to `return` after handling the exception, so execution falls through and continues to use the now-undefined `json_payload_hash` and to invoke `privatePayment.validateAndSavePrivatePaymentChain(...)` a second time for the same queued item.

### Finding Description
`handleSavedPrivatePayments` iterates queued `unhandled_private_payments` rows with `async.each` and, per row, calls the local `validateAndSave` function: [1](#0-0) 

If `getBase64Hash` throws (e.g. because the attacker-controlled `payload` stored in `unhandled_private_payments.json` cannot be canonicalized/stringified by `getJsonSourceString`, such as through structures containing values that break `string_utils`'s canonical stringifier), the `catch` block sends an error result and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which itself eventually invokes the `async.each` iteratee callback `cb`. Execution then continues past the `catch` block (no `return`), builds `key` using the undefined `json_payload_hash`, and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again. That second call's callbacks (`ifOk`/`ifError`/`ifWaitingForChain`) each also eventually call `deleteHandledPrivateChain(..., cb)` or otherwise resolve, resulting in `cb` for the same `async.each` item being invoked more than once.

This is directly analogous to the CVE's bug class: unexpected/malformed input to a message-processing entry point is not fully handled, and the code proceeds past an error path instead of terminating that unit of work, corrupting internal async control flow. The private-payment path is reachable by any paired device sending private payment chains via `wallet.js`'s `handlePrivatePaymentChains` (called from `handleMessageFromHub`), which queues the payload into `unhandled_private_payments` and later triggers `handleSavedPrivatePayments`. [2](#0-1) [3](#0-2) 

Double-invocation of an `async.each` iteratee callback is undefined behavior in the `async` library and can throw ("Callback was already called") or otherwise corrupt the mutex-guarded queue processing (`mutex.lock(["saved_private"], ...)`), which can leave the `saved_private` mutex lock in an inconsistent state or throw an uncaught exception in the callback chain, since none of the surrounding code wraps this in a try/catch that would gracefully recover.

### Impact Explanation
An attacker who is a paired device (private-payment counterparty) can repeatedly send crafted private-payment chains whose payload triggers the `getBase64Hash` exception. Each occurrence risks double-firing the `async.each` iteratee callback for `handleSavedPrivatePayments`, which can throw an uncaught exception or desynchronize the `saved_private` mutex used to serialize private-payment processing. Because this mutex gates all future processing of queued private payments, a stuck/corrupted lock state can prevent the node from ever processing new private-payment chains again — a persistent denial of service for that node's private-payment/wallet functionality, matching "network unable to confirm new units" for this transaction class.

### Likelihood Explanation
Reaching this path requires only being a paired device (already a permitted attacker role) sending a private-payment offer/chain with a payload that fails canonical stringification. No node/hub compromise or privileged access is needed. However, I could not fully confirm (due to index limits) the exact conditions under which `getJsonSourceString`/`getSourceString` throws for a chain payload that otherwise passes the shallow structural checks in `handlePrivatePaymentChains`, so likelihood is assessed as plausible but not fully proven end-to-end.

### Recommendation
Add a `return` statement immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `handleSavedPrivatePayments`'s `validateAndSave` function so execution does not fall through to reuse `json_payload_hash` or re-invoke `validateAndSavePrivatePaymentChain` for the same private-payment row. Additionally, audit `deleteHandledPrivateChain` and its callback (`cb`) usage to ensure it can never be invoked twice for the same `async.each` item.

### Proof of Concept
1. As a paired device, send a `private_payment_chains` (`chains`) message via the device-messaging protocol handled by `wallet.js:handlePrivatePaymentChains`, with a `payload` that passes the shallow field checks (`isNonemptyObject`, `isNonemptyString`, etc.) but contains a value that causes `string_utils.getJsonSourceString` (invoked from `object_hash.getBase64Hash(..., true)`) to throw when canonicalizing (I could not verify the exact malformed value from the available index; this needs to be confirmed against `string_utils.js`'s implementation in a full checkout).
2. The chain gets queued into `unhandled_private_payments`.
3. When `handleSavedPrivatePayments` processes it, `getBase64Hash` throws, the `catch` block executes `deleteHandledPrivateChain(...)` (calling `cb`) without returning, then falls through and calls `validateAndSavePrivatePaymentChain` again, which will itself resolve and call `cb` a second time — observable via duplicate `cb()` invocation errors from the `async` library or via the `saved_private` mutex becoming stuck, blocking further private-payment processing.
