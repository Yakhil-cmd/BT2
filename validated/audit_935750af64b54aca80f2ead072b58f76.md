This confirms the multi-organization config schema (`Shipit.github(organization:)`, `github_app_config`, `TOP_LEVEL_GH_KEYS`) that lets a single Shipit deployment serve multiple GitHub organizations, each with its own `webhook_secret`. This is the exact setup needed for the analog binding-break.

### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event is applied to the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the `X-Hub-Signature` against using `repository_owner`, taken from the JSON body itself (`params.dig('repository','owner','login')` or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, the entire raw payload is handed unmodified to the event handlers [3](#0-2) . Every handler (`PushHandler`, `StatusHandler`, the `PullRequest::*Handler` family, etc.) determines which `Repository`/`Stack`/`Commit` to mutate using a *different* field of the same payload: `payload.dig('repository', 'full_name')` [4](#0-3) , or in the `StatusHandler` case, no repository field at all - it matches purely on `sha` across every `Commit` in the database, regardless of which stack/repository owns it [5](#0-4) .

### Finding Description
The binding that should hold is:
`organization whose webhook_secret authenticated the request == owner of the repository the handler mutates`

Shipit supports a multi-organization GitHub App configuration schema (`Shipit.github(organization:)`, `github_app_config`, `TOP_LEVEL_GH_KEYS`) where each organization key in `secrets.github` carries its own independent `webhook_secret` [6](#0-5) . The `HMAC-SHA1` signature is verified with `GitHubApp#verify_webhook_signature`, keyed on whichever organization's secret was looked up via `repository_owner` [7](#0-6) .

Nothing in `WebhooksController#create` or in `Handler#repository_name`/`Handler#stacks` cross-checks that the `repository.owner.login` used for signature selection matches the owner encoded in `repository.full_name` used for locating the target `Repository` [4](#0-3) , or that the commit `sha` in a `status` event actually belongs to the org that signed the request (`StatusHandler` performs no repository check whatsoever) [5](#0-4) .

Given a multi-org deployment (organizations `org-a` and `org-b`, each with a Shipit-managed repository and its own `webhook_secret`), a party with legitimate webhook delivery for `org-a` (i.e., who knows `org-a`'s `webhook_secret`, such as anyone who can trigger real GitHub events for repos under `org-a`, or has extracted that secret through org-a's own webhook infrastructure) can craft a JSON body where:
- `repository.owner.login` = `org-a` (so `Shipit.github(organization: "org-a")`'s secret is used to verify the HMAC and the check passes with a correctly-signed body), and
- `repository.full_name` = `org-b/some-repo` (a completely different repository/organization Shipit also manages).

`PushHandler`, `Assigned/Closed/Labeled/Opened/Reopened/Unlabeled` PR handlers, and `CheckSuiteHandler` all resolve the acting `Repository` via `full_name`, so the forged event is applied to `org-b`'s stack: it can trigger `GithubSyncJob`, archive/unarchive review stacks, or flip provisioning behavior on a repository the caller never had a valid webhook for [8](#0-7) [9](#0-8) . `StatusHandler` is worse: since it matches only by `sha` with no repository/org filter at all, any org's valid webhook secret can be used to inject a fabricated commit status (`state`, `target_url`, `description`, `context`) onto *any* commit tracked by *any* stack in the entire Shipit instance, as long as the sha string happens to match [5](#0-4) .

### Impact Explanation
Commit statuses gate deployability (`Commit#deployable?`) in Shipit; forging a `success` status for a foreign org's commit via a stolen/known sibling-org webhook secret can enable an unauthorized deploy to proceed under Shipit's own semantics. Triggering `GithubSyncJob`/archive-unarchive actions on stacks belonging to a different organization than the one whose secret was used to authenticate constitutes cross-repository writes performed by the deploy host using its own GitHub credentials, without the caller ever holding write access, a Shipit session, or the target organization's `webhook_secret`. This matches the Critical-tier impact category: "cross-repository writes" and, via the falsified `success` status enabling deploy gating bypass, "an unauthorized deploy."

### Likelihood Explanation
Exploitation requires a real, valid `webhook_secret` for at least one organization configured on the Shipit instance (e.g., an org that has legitimately configured a Shipit webhook), which is a realistic scenario for any multi-tenant/multi-org Shipit deployment (this is exactly the deployment mode the multi-org config schema in `lib/shipit.rb` exists to support). No repository write access, GitHub App private key, Shipit session, or `ApiClient` token is required — only knowledge of one org's HMAC secret, which by design is meant to authorize events *for that org's repositories only*, not for arbitrary other repositories hosted on the same Shipit instance.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, and in `Shipit::Webhooks::Handlers::Handler`, ensure the organization/owner used to select and verify the webhook secret is the same one embedded in the repository/stack the handler subsequently mutates. Concretely: derive the acting repository's owner from the same value that gated signature verification (or verify `payload.dig('repository','full_name')`'s owner segment equals `repository_owner` before dispatching to handlers), and fix `StatusHandler` to scope its `Commit` lookup by the repository/stack associated with the authenticated organization rather than a bare, org-agnostic `sha` match.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (webhook_secret `SECRET_A`) and `org-b` (webhook_secret `SECRET_B`), each with a Shipit stack for one of their repositories.
2. As a holder of `SECRET_A` (e.g., someone able to deliver real webhooks for `org-a`), craft a `push` (or `pull_request`) JSON payload where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/target-repo"`.
3. Sign the raw body with `SECRET_A` and send it as `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature [1](#0-0) .
5. The handler (e.g., `PushHandler`) resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")` and triggers `stack.sync_github` on `org-b`'s stack — despite the request never having been signed with `org-b`'s secret [4](#0-3) [8](#0-7) .
6. For an even stronger primitive, send a `status` event signed with `SECRET_A` containing the `sha` of a real, undeployed commit belonging to `org-b`'s stack with `state: "success"`; `StatusHandler` writes the status with no ownership check at all, potentially unblocking a deploy gated on CI status [5](#0-4) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
