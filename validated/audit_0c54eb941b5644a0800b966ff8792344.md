### Title
Forged `status` webhook via no-secret organization bypasses signature verification and writes commit status for any stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` instance to validate against using the attacker-controlled `repository.owner.login` field, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's config has no `webhook_secret`. Because `StatusHandler` then processes the forged `status` payload with `Commit.where(sha: params.sha)` — with zero scoping to the org/repo/stack that "authenticated" the request — an attacker can forge a fully valid `status` webhook for any commit sha in the entire Shipit installation, not just for the no-secret org.

### Finding Description
The broken binding: the code implicitly assumes `authenticated_organization == affected_organization`, i.e. that a webhook accepted as authentic for organization `X` can only mutate records belonging to `X`. In reality `authenticated_organization` (attacker-chosen via `repository.owner.login`, used only to pick the verifying secret) and `affected_organization` (implicitly "any stack containing a commit with this sha") are never compared.

Path:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` [1](#0-0)  and fetches `Shipit.github(organization: repository_owner)` to verify the signature [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved org's config has no `webhook_secret`: `return true unless webhook_secret` [3](#0-2) . `@webhook_secret` is set directly from `@config[:webhook_secret].presence` per-organization [4](#0-3) .
3. Once `head(422)` is skipped, `WebhooksController#create` dispatches to all handlers for the event with the raw, attacker-forged JSON body [5](#0-4) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query across the entire `commits` table, matching any commit with that sha regardless of which stack/repo it belongs to [6](#0-5) .
5. `Commit#create_status_from_github!` writes a `Status` record and triggers `add_status`, which emits `commit_status`/`deployable_status` hooks and calls `stack.schedule_merges` — potentially unblocking deploys/merges gated on CI status [7](#0-6) [8](#0-7) .

Attacker request: `POST /webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` (or any garbage), body `{"repository":{"owner":{"login":"<org-without-secret>"}},"sha":"<victim-sha>","state":"success", ...}`. `<org-without-secret>` must be a name present in `Shipit.github_organizations` (i.e., configured in the app's `secrets.github`) whose config omits `webhook_secret` — this is a Shipit operator misconfiguration, not a per-repo/per-stack property, but once it exists it is globally exploitable against every commit sha in the database, including shas belonging to stacks under completely different, properly-secret-protected organizations.

No existing guard catches this: `drop_unhandled_event` only checks the event is registered, `verify_signature` is the only auth check and is bypassed by design when `webhook_secret` is blank, and `StatusHandler`'s `ExplicitParameters` schema validates payload shape only, not repository ownership.

### Impact Explanation
An attacker who identifies (or knows of) one misconfigured no-secret organization can forge CI status for any commit sha across all stacks in the Shipit instance, including stacks belonging to organizations that do have `webhook_secret` configured — this is "a payload for one repository mutating another's stack/commit," matching the Critical impact category (authentication bypass leading to cross-tenant state mutation). Forged success statuses can make `deployable?` return true prematurely, unblocking `stack.schedule_merges` and downstream deploy/merge automation gated on CI. The attack is fully repeatable per request and requires no privileges.

### Likelihood Explanation
Requires only that the Shipit deployment has at least one organization configured under `secrets.github` without a `webhook_secret` — a plausible but non-default operator misconfiguration (e.g., during onboarding of a new org before rotating in a secret). Given that precondition, exploitation cost is a single unauthenticated HTTP POST with no signature; attacker needs to know/guess a target commit sha, which is often publicly discoverable via GitHub itself. Fully repeatable and requires no interaction with the Shipit UI or credentials.

### Recommendation
- Reject webhooks outright (`head(422)`) when the resolved org's config has no `webhook_secret`, rather than treating blank secret as "trust unconditionally," in `GitHubApp#verify_webhook_signature`.
- Additionally, scope `StatusHandler` (and other handlers) to the commit's/stack's own repository/org — verify that `params.dig('repository','full_name')` matches `commit.stack.github_repo_name` before applying `create_status_from_github!`, so that even a legitimately-authenticated webhook for org `X` cannot mutate commits belonging to a different repository.

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Configure `Shipit.stub(:github_organizations, ['secretorg', 'nosecretorg'])` and stub `Shipit.github(organization: 'nosecretorg')` to return a `GitHubApp` built with `config` that omits `webhook_secret`, while `Shipit.github(organization: 'secretorg')` has one configured.
2. Create a `victim_stack` under `secretorg/repo` with a `commit` of a known `sha`.
3. POST to `/webhooks` with header `X-Github-Event: status`, no/garbage `X-Hub-Signature`, and body `{"repository":{"owner":{"login":"nosecretorg"}}, "sha": "<victim sha>", "state": "success", "context": "ci"}`.
4. Assert response is `200 OK` (not `422`), proving `verify_signature` did not reject the forged request meant to "belong" to `nosecretorg`.
5. Assert `victim_stack.commits.find_by(sha: "<victim sha>").statuses.last.state == "success"` — i.e., a forged status was written to a commit belonging to `secretorg`, an org whose webhook secret was never presented, demonstrating `authenticated_organization("nosecretorg") != affected_organization("secretorg")`.
