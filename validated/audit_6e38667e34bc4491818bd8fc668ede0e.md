### Title
InitializeBuffer instruction lacks signer/authority verification, allowing front-running of upgrade authority takeover - (File: programs/bpf_loader/src/lib.rs)

### Summary
The `bpf_loader_upgradeable` program's `InitializeBuffer` instruction handler sets a buffer account's authority from an arbitrary, unsigned instruction-account key, with no check that the caller or any related party has signed. This mirrors the reported Solidity pattern where an unprotected `initialize()`/`reinitializer(1)` function lets anyone claim ownership by calling it first, since the only guard is a one-time state check (`Uninitialized`), not an access-control/signature check.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` as follows: [1](#0-0) 

```
UpgradeableLoaderInstruction::InitializeBuffer => {
    instruction_context.check_number_of_instruction_accounts(2)?;
    let mut buffer = instruction_context.try_borrow_instruction_account(0)?;

    if UpgradeableLoaderState::Uninitialized != buffer.get_state()? {
        ic_logger_msg!(log_collector, "Buffer account already initialized");
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    let authority_key = Some(*instruction_context.get_key_of_instruction_account(1)?);

    buffer.set_state(&UpgradeableLoaderState::Buffer {
        authority_address: authority_key,
    })?;
}
```

The only gate is `UpgradeableLoaderState::Uninitialized != buffer.get_state()?` — a "has this been initialized yet" check analogous to Solidity's `reinitializer(1)`/`initializer` guard flagged in the report. There is **no signer check on the buffer account** and **no signer check on the authority account** (account index 1 is never required to be a signer). This is confirmed by the unit test itself, which builds the `InitializeBuffer` instruction with both accounts marked `is_signer: false`: [2](#0-1) 

Compare this to sibling instructions in the same match statement, `Write` and `DeployWithMaxDataLen`, which explicitly verify `is_instruction_account_signer` for the authority before honoring it: [3](#0-2) [4](#0-3) 

`InitializeBuffer` deliberately omits this check — presumably because the tooling always bundles `CreateAccount` (which pays rent and sets the loader as owner, requiring the buffer keypair's signature) and `InitializeBuffer` into the *same* transaction via `solana_loader_v3_interface::instruction::create_buffer`, as seen in the reference test: [5](#0-4) 

Because a Solana transaction executes atomically, bundling both instructions in one transaction closes the window. However, nothing in `InitializeBuffer`'s own logic enforces this invariant. If the two steps are ever split across separate transactions — e.g., a buffer account created in one transaction (funded and owned by the loader, but left `Uninitialized`) and initialized in a later transaction (a pattern explicitly supported by the CLI's "resume/reuse an existing buffer" flow, where a pre-existing buffer pubkey can be supplied without necessarily re-running `create_buffer` atomically) — any unrelated party who observes the buffer's public key (e.g., from the pending `CreateAccount` transaction, from an RPC-visible unconfirmed transaction, or simply because the pubkey was shared out-of-band before initialization) can submit their own `InitializeBuffer` instruction naming *their own* pubkey as the authority. Since account index 1 requires no signature, the attacker does not even need to control a matching private key beyond the transaction fee-payer's — they can name any pubkey as the future authority, or name themselves and thereby gain control of a buffer account whose rent was paid by someone else.

### Impact Explanation
An attacker who wins this race becomes the recorded `authority_address` on the `Buffer` account. As the recognized authority, they can then:
- Call `Write` to inject arbitrary program bytes into the buffer (verified by `authority_address == authority_key` and the authority's signature at that stage — a check that only matters because the authority was set unilaterally by the attacker in `InitializeBuffer`).
- Potentially force `DeployWithMaxDataLen`/`Upgrade` to fail for the legitimate deployer (denial of service on the buffer, since the account will be stuck as `AccountAlreadyInitialized` with an attacker-controlled authority, requiring the victim to abandon the account and its rent), or, if the attacker also controls other legitimate onward steps, hijack deployment of a program to that buffer.

This does not cause direct unsigned lamport transfer, but it is a concrete privilege-hijack over program-deployment infrastructure reachable by any transaction sender, matching the report's core class ("initializer front-run leading to unauthorized ownership/authority takeover").

### Likelihood Explanation
Exploitability depends entirely on whether `CreateAccount` and `InitializeBuffer` are ever submitted as two separate transactions rather than atomically bundled. In the reviewed CLI/test code paths (`program-test/tests/builtins.rs`, `cli/src/program.rs` buffer creation flow), the standard `create_buffer` helper bundles both instructions into one transaction and signs with the buffer keypair for account creation, which prevents front-running in that flow. I was not able to fully confirm within the available index whether any supported CLI/SDK code path (e.g., a resumed/partial deploy using a previously-created but not-yet-initialized buffer, or a custom integrator directly composing instructions) ever splits these two instructions across transactions in agave's own tooling. This uncertainty limits confidence that the vulnerability is reachable through a fully "in-scope, unprivileged, single-transaction" path as strictly required — the missing signer check is real and verifiable, but a concrete two-transaction exploitation scenario using only agave's own shipped tooling could not be fully confirmed with the tools available.

### Recommendation
Require the authority account (index 1) to be a signer in `InitializeBuffer`, matching the pattern already used for `Write` and `Upgrade`. Alternatively/additionally, require the buffer account (index 0) itself to be a signer at initialization time (as `CreateAccount` already does), so that only the party that created (and paid rent for) the buffer, or an explicitly consenting authority, can set its authority.

### Proof of Concept
1. Party A creates a buffer account via `system_instruction::create_account` with the loader as owner (a separate transaction, or the account was otherwise created but left `Uninitialized`), intending to later call `InitializeBuffer` with `authority = A`.
2. Before A's `InitializeBuffer` transaction lands, attacker B observes the buffer pubkey (public in A's pending `CreateAccount` transaction or otherwise known) and submits `InitializeBuffer` naming the same buffer account (index 0, not required to be a signer) and `authority_key = B` (index 1, not required to be a signer):
   ```
   UpgradeableLoaderInstruction::InitializeBuffer
   accounts: [buffer (writable, not signer), B's pubkey (not signer)]
   ```
3. Per `programs/bpf_loader/src/lib.rs:158-172`, since the buffer's state is still `Uninitialized`, B's transaction succeeds and sets `authority_address = Some(B)`.
4. A's later `InitializeBuffer` transaction now fails with `InstructionError::AccountAlreadyInitialized` (`programs/bpf_loader/src/lib.rs:162-165`), and B is the sole recognized authority able to `Write` to and later deploy from the buffer that A funded.
