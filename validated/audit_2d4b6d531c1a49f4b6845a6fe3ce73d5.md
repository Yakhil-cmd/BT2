### Title
`register-for-bond`'s L1 BTC lockup verification lacks a global outpoint registry, allowing the same Bitcoin lockup UTXO to be reused across multiple bond registrations - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond` accepts a proof of an on-chain Bitcoin timelock (`btc-lockup: (response {...} uint)`) and, when it validates, credits the staker with `sats-total` sBTC-equivalent stake without ever moving real sBTC (the L1 path). The proof's per-output dedup (`seen-outpoints`) is scoped only to the single call via `verify-l1-lockups`/`validate-l1-lockup`, and is never persisted to contract storage.

### Finding Description
`register-for-bond` computes `sats-total` for the L1 path by calling `verify-l1-lockups`, which folds over the caller-supplied `outputs` list with `validate-l1-lockup`: [1](#0-0) 

`validate-l1-lockup` checks that each output's script/amount matches the expected timelock output derived from `construct-lockup-output-script`, verifies the Bitcoin block header and merkle proof, and rejects duplicate `(txid, output-index)` pairs — but only within `seen-outpoints`, a fold accumulator that starts empty on every call: [2](#0-1) [3](#0-2) 

There is no `define-map` in `pox-5.clar` that records previously-consumed L1 lockup outpoints across separate transactions (confirmed by searching the contract for a persisted "used outpoints" map — none exists). The only per-call dedup structure, `seen-outpoints`, is discarded once `register-for-bond` returns.

Because `sats-total` derived from the L1 path is used directly to compute the staker's bond share (`amount-sats`, `protocol-bonds-total-staked`, signer cycle shares) with no sBTC ever transferred (the `new-sbtc` on the L1 path is `u0`, so `roll-sbtc` moves nothing): [4](#0-3) 

...a single genuine Bitcoin timelock output can be replayed as proof for multiple `register-for-bond` calls — either by the same staker for sequential/rolled-over bonds, or (since `staker` is a parameter baked into the expected script hash rather than an enforced uniqueness key at the contract level) reused once a bond ends and a new bond opens. Each successful replay credits `sats-total` sats of bond stake/signer weight/reward share without any additional BTC being locked, breaking the equality between sats credited by an L1 proof and sats actually locked on Bitcoin.

### Impact Explanation
This falls under the Critical impact category: "sats credited by an L1 proof that were never locked on Bitcoin" and "double-counting a commitment or reward." An attacker with one genuine, still-unspent Bitcoin timelock UTXO can register multiple pox-5 bonds (across different `bond-index` values or after each bond's lifecycle) using that same proof, inflating their `amount-sats` share of signer/bond rewards and total-staked accounting without committing additional BTC collateral — effectively minting phantom sBTC-equivalent stake and diluting/misallocating rewards derived from `total-sbtc-staked` and `protocol-bonds-total-staked`.

### Likelihood Explanation
Moderate-to-high likelihood, contingent on validation. `register-for-bond` is a public, unprivileged, permissionless entry point; the only gate is being on a bond's `allowlist`, which is expected for any legitimate participant and does not restrict re-use of the same lockup proof. Because `bond-start-height`/`bond-index` differ between calls and the check `existing-membership`/`existing-stake` gates re-registration for the *same* staker on an *active/overlapping* bond, but does not track *which specific Bitcoin outpoints have already been consumed contract-wide*, replay is plausible whenever a staker cycles through bond periods or is allow-listed on multiple bonds. This needs to be validated end-to-end against the full bond life-cycle state machine (`update-bond-registration`, `stake`, rollovers) to confirm no other implicit global gate exists, since I could not find one in the reachable contract code.

### Recommendation
Persist consumed L1 lockup outpoints in a durable contract map (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`), checked and inserted inside `validate-l1-lockup` (or immediately after `verify-l1-lockups` succeeds in `register-for-bond`), so that once a Bitcoin UTXO has been used to justify a bond registration it can never be credited again for any staker or bond, for the life of the contract (or at minimum until the corresponding `unlock-burn-height` has passed and the L1 exit has been confirmed on-chain, if replay-after-unlock is intended to be permitted through a separate re-proof path).

### Proof of Concept
1. Staker A locks BTC in the canonical pox-5 timelock P2WSH via a real Bitcoin transaction (`txid`, `output-index`, `amount`, `unlock-burn-height`), matching `construct-lockup-output-script(staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes)`.
2. Staker A calls `register-for-bond(bond-index=0, ..., btc-lockup=ok({outputs:[thisOutput], staker-unlock-bytes}))`. `verify-l1-lockups`/`validate-l1-lockup` succeed (block header/merkle proof/script/amount all check out), crediting `sats-total = amount` sats of bond stake, and `total-sbtc-staked`/bond cycle shares are updated — without any sBTC custody transfer (`new-sbtc = u0`).
3. Once bond 0's term completes/rolls over per the contract's own overlap rules (or on a second, disjoint bond that Staker A is separately allow-listed for), Staker A calls `register-for-bond(bond-index=1, ..., btc-lockup=ok({outputs:[thisSameOutput], ...}))` submitting the *exact same* Bitcoin `tx`/`output-index`/`header`/merkle proof.
4. Because `seen-outpoints` only dedups within the single call's `outputs` list and no contract-wide map records that this outpoint was already consumed by the bond-0 registration, `validate-l1-lockup` succeeds again, crediting `sats-total` a second time for bond 1 from the *same* underlying locked BTC — double-counting the L1 collateral across two independent bond commitments and their reward accounting.
