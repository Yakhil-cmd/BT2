### Title
Cross-tenant `Team`/`Membership` escalation via unchecked `team.id` provenance in `membership` webhooks - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` only proves that a `membership` webhook was signed by *some* organization configured in `Shipit.secrets.github`; it never checks that the `team.id` referenced inside that same payload actually belongs to the signing organization. `MembershipHandler#find_or_create_team!` then trusts `params.team.id` blindly and, because it uses `find_or_create_by!` (which only assigns attributes on the create branch), silently returns any pre-existing `Team` row with that `github_id` — including a privileged team already seeded via `Shipit.github_teams`/`Team.find_or_create_by_handle` — and adds the attacker-controlled `member.login` to it.

### Finding Description
The broken binding is: `Team.organization` (the org that truly owns `github_id`) `==` `repository_owner` (the org whose `webhook_secret` signed the request). This equality is never verified.

- `verify_signature` derives `repository_owner` purely from self-reported payload fields, and for `membership` events (no `repository` key) falls back to `params.dig('organization','login')`: [1](#0-0) [2](#0-1) 
It looks up `Shipit.github(organization: repository_owner)` and checks the HMAC signature against *that* org's `webhook_secret`. If the signer legitimately controls an org that is one of the configured tenants in `Shipit.secrets.github` (a multi-org setup, see `github_app_config`), the signature check passes — it proves only "this payload was signed by org B", never "the `team.id` inside this payload belongs to org B".
- `MembershipHandler#find_or_create_team!` then does: [3](#0-2) 
`find_or_create_by!` only executes the block when a new record is created. If a `Team` row for that `github_id` already exists (e.g. seeded once via `Shipit.github_teams`, which itself calls `Team.find_or_create_by_handle`): [4](#0-3) [5](#0-4) 
the lookup returns the existing (target org's) `Team` untouched — the mismatched `organization` value in the forged payload is silently discarded.
- `MembershipHandler#process` then adds the attacker's own `User` (created from the attacker-controlled `member.login`) into that team: [6](#0-5) [7](#0-6) 
- `User#authorized?` then flips true for the attacker because it only checks team membership by id, with no organization cross-check: [8](#0-7) 

No other guard intervenes: `drop_unhandled_event` only checks the event type is handled, `ExplicitParameters` (`params do ... end` in `MembershipHandler`) only validates types/presence of `team.id`, `organization.login`, `member.login`, not cross-referencing them against the signing org, and `Team#github_team=`/`add_member` perform no ownership re-verification either.

### Impact Explanation
A signer who legitimately owns any organization configured as a Shipit tenant (with its own valid `webhook_secret`) can add an arbitrary GitHub login of their choosing as a member of any other tenant's privileged `Team` row, as long as they know or can guess/brute-force that team's `github_id`. This directly grants `Shipit.github_teams` authorization (`User#authorized?` flips true) across organizational boundaries — the exact "escalation into `Shipit.github_teams` authorization" category (High). It is repeatable per-target-team and requires no interaction with the victim org.

### Likelihood Explanation
The attack is only reachable if the Shipit deployment is configured with more than one trusted GitHub org in `secrets.github` (a supported but non-default configuration, per `github_app_config`/`github_organizations`), and the attacker legitimately controls one of those onboarded orgs' `webhook_secret`. A truly anonymous internet attacker with no relationship to any tenant of the target Shipit instance cannot obtain a `webhook_secret` this instance will accept — `secrets.github` is a static, operator-managed Rails-credentials structure, not self-service; there is no code path found that lets an arbitrary new org register itself and obtain a trusted `webhook_secret` without operator action. So the realistic threat is one already-onboarded tenant escalating into another already-onboarded tenant's privileged team, which is still a meaningful cross-tenant isolation failure in multi-org deployments, but it requires the attacker to already possess a "privileged" role (a Shipit-recognized org's webhook secret) rather than being a fully anonymous unprivileged actor as the strict threat model demands. Additionally, real GitHub.com team ids are globally-unique sequential integers (not scoped/colliding per org), so exact `github_id` collision requires either guessing an existing numeric id or a GitHub Enterprise Server install where ids may collide more easily — this is an external factual assumption, not something enforced or refuted by this codebase.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that any existing `Team` matched by `github_id` has `organization == params.organization.login` before reusing it (raise / drop the event on mismatch instead of silently returning the pre-existing row). More generally, `verify_signature` should ensure that all organization-identifying fields referenced by a handler's payload (not just the top-level `organization.login`) are consistent with the signing tenant before any handler runs.

### Proof of Concept
Minitest integration test outline for `test/controllers/webhooks_controller_test.rb` style setup (not included here per scope, but structure to hand to engineering):
1. Configure two tenants in `Shipit.secrets.github`, org `"tenant-a"` and org `"tenant-b"`, each with distinct `webhook_secret`.
2. Seed a privileged `Team` for `tenant-a` with `github_id: 42`, and add it to `Shipit.github_teams`.
3. Build a `membership` webhook JSON body with `organization.login = "tenant-b"`, `team.id = 42`, `team.name/slug/url` arbitrary, `action: "added"`, `member.login = "attacker"`.
4. Sign the raw body with `tenant-b`'s `webhook_secret` and POST to `/webhooks` with header `X-Github-Event: membership`.
5. Assert response is `200`.
6. Assert `Shipit::Team.find_by(github_id: 42).organization == "tenant-a"` (unchanged) BUT `Shipit::Team.find_by(github_id: 42).members.exists?(login: "attacker")` is `true`.
7. Assert `Shipit::User.find_by(login: "attacker").authorized?` is `true`.

Both sides of the equality (`Team#organization == "tenant-a"` vs. signing org `"tenant-b"`) diverge after the request, proving the provenance binding is broken.
