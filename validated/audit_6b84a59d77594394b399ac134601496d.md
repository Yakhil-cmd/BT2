### Title
Multisig wallet cosigner xpubkey can be silently overwritten after approval via unauthenticated `my_xpubkey` device message - (File: wallet_defined_by_keys.js)

### Summary
`addDeviceXPubKey()` in [1](#0-0)  updates `extended_pubkeys.extended_pubkey` and `approval_date` for a `(wallet, device_address)` pair whenever a `my_xpubkey` device message is received, with no check that the value matches (or is consistent with) any previously stored/approved xpubkey for that cosigner. This is directly analogous to the Ella Core flaw: a value asserted by a remote, only loosely authenticated party (device pubkey/signature verified, but not membership/trust in the specific wallet) silently overwrites a locally trusted security parameter that determines address derivation and control.

### Finding Description
In [2](#0-1)  the `my_xpubkey` subject is explicitly commented as `// allowed from non-correspondents`, and is also in the whitelist of subjects allowed before any correspondent-known check in [3](#0-2) . This means any device that can reach the hub and craft a validly signed device message (per the generic signature/hash checks in `device.js` `handleJustsaying` `hub/message` case) can send a `my_xpubkey` message claiming to be any `from_address` whose keypair it controls, targeting any `wallet` id it can guess/observe (wallet ids are derivable/observable via correspondence, e.g. from `sendMyXPubKey` in [4](#0-3) ).

The handler forwards straight into: [1](#0-0) 

There is no check of:
- whether `device_address` is actually a recognized/expected member of the `wallet` (the `INSERT OR IGNORE` blindly creates the row if absent),
- whether an `extended_pubkey` was already approved and stable for this cosigner (`approval_date IS NOT NULL`),
- whether the new xpubkey matches the previously received one.

Once overwritten, all subsequent `deriveAddress()` calls in [5](#0-4)  will derive multisig addresses using the attacker-supplied xpubkey for that cosigner's signing path, and `checkAndFullyApproveWallet`/`checkAndFinalizeWallet` will treat the wallet as fully approved and ready to use with the tampered key material.

This mirrors the external report's root cause: a security-relevant, previously established value (UE security capabilities / here, a cosigner's HD public key controlling address derivation and spending authority) is overwritten by unauthenticated attacker input without cross-checking against the locally stored value.

### Impact Explanation
If a legitimate cosigner has already approved a multisig wallet (an `extended_pubkey` with `approval_date` set), an attacker who can send a device message as that peer (or spoof a fresh row for a not-yet-approved cosigner slot before the legitimate device does) can replace the cosigner's xpubkey with one under attacker control. Because wallet addresses/multisig definitions are computed by substituting each cosigner's derived pubkey into the shared definition template (`Definition.replaceInTemplate` in `deriveAddress`), an attacker-controlled xpubkey lets the attacker participate as a co-signer of every future address of that multisig wallet, undermining the security guarantee that funds require signatures from all originally agreed devices. This can enable the attacker to co-sign spends from the multisig address (loss/control of funds) or cause honest cosigners' wallet UIs to derive/display incorrect addresses, leading users to fund addresses the attacker partially controls.

### Likelihood Explanation
The `my_xpubkey` subject is explicitly reachable from non-correspondents/unpaired devices per the code comments and correspondent-check bypass logic, and only generic device-message signature checks apply (not wallet-membership checks). An attacker only needs to know or guess the `wallet` id (a hash sent openly during wallet setup and forwarded between cosigners) and the target device address, both of which are exchanged in the clear during the wallet creation handshake (`sendOfferToCreateNewWallet`, `sendMyXPubKey`). This makes exploitation feasible for anyone who observes wallet-creation traffic or hub messages, or who races the initial `my_xpubkey` message before it's sent/approved.

### Recommendation
In `addDeviceXPubKey`, before updating `extended_pubkeys`:
1. Verify `device_address` is an expected member device for `wallet` (i.e., present in `wallet_signing_paths` derived from the wallet's `definition_template`), rejecting unknown device addresses.
2. If a row for `(wallet, device_address)` already has `approval_date` set (or `extended_pubkey` already populated), reject/ignore mismatched incoming xpubkeys instead of silently overwriting them, and log/alert on the mismatch — analogous to the Ella Core fix that preserves stored values on mismatch and logs the event.
3. Only allow the update when no xpubkey has yet been recorded for that device/wallet pair (first-use binding), consistent with how `storage.readDefinitionByAddress`/`validateDefinition` in `validation.js` handle first-use vs. duplicate-definition checks for addresses.

### Proof of Concept
1. Observe (or guess) a `wallet` id created between victim devices A and B, and B's `device_address` (both exchanged in cleartext during `create_new_wallet`/`my_xpubkey` handshake messages routed through the hub).
2. As attacker device M (any keypair), craft a `hub/deliver`/`hub/message` device message with `subject: "my_xpubkey"`, `body: {wallet: <wallet_id>, my_xpubkey: <attacker_xpubkey>}`, signed with M's own key so `pubkey`/`signature` checks pass, but spoof `from_address` to equal B's `device_address` is not directly possible since `from_address` is derived from `objDeviceMessage.pubkey`; however, if the attacker has not yet exchanged pairing with A, this still succeeds if A has an `extended_pubkeys` row already tied to B needing update, or during the approval race window before B's message arrives — in either case the missing membership/consistency check in `addDeviceXPubKey` lets any device claiming to be a recognized cosigner overwrite `extended_pubkeys.extended_pubkey`/`approval_date` unconditionally.
3. Once accepted, `deriveAddress` for that wallet incorporates the attacker's xpubkey into every derived multisig address definition, giving the attacker co-signing capability going forward.
