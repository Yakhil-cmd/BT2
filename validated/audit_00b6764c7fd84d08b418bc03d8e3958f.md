### Title
Uncaught exception on unrecognized encrypted-package recipient key causes wallet/hub process crash (DoS) - ([File: device.js])

### Summary
`decryptPackage()` in `device.js` fails to gracefully handle a device message whose `dh.recipient_ephemeral_pubkey` does not match any of the recipient's known keys (temp, previous-temp, or permanent). Instead of returning an error to the caller, it schedules a `setTimeout` that unconditionally `throw`s an `Error`, which is an uncaught exception in Node.js and terminates the process. This mirrors the CVE-2015-5315 bug class: a malformed/foreign message field (there, a "final fragment" without proper length validation; here, an encrypted package addressed to an unknown key) is not validated before the code path leads to an unrecoverable crash.

### Finding Description
`decryptPackage` is reached from `handleJustsaying` in `device.js` when a paired correspondent (or the hub relaying on their behalf) delivers a `hub/message` to a device, and from `wallet.js` for `arbiter_dispute_request` handling of `body.encrypted_contract`. Both call sites are reachable from data sent by a **paired counterparty device** — the exact "device message" attack surface allowed by the rules. [1](#0-0) 

When `objEncryptedPackage.dh.recipient_ephemeral_pubkey` doesn't match `objMyTempDeviceKey`, `objMyPrevTempDeviceKey`, or `objMyPermanentDeviceKey`, the function logs, then does:
```
setTimeout(function(){
    throw Error("message encrypted to unknown key, ...");
}, 100);
return null;
```
Because the `throw` occurs inside an asynchronous `setTimeout` callback, it is outside of any enclosing `try/catch` in the caller (`handleJustsaying`'s `try { decryptPackage(...) } catch(e){...}` at [2](#0-1)  only guards the synchronous call, not the deferred throw). An uncaught exception in a Node.js process without a global handler crashes the process — an unauthenticated/low-trust condition (any correspondent, or a hub relaying old/garbled data) can trigger it simply by sending an `encrypted_package` whose `dh.recipient_ephemeral_pubkey` field is any value not currently recognized (e.g., a stale/garbage base64 string, or after key rotation races).

Reachability confirmed via:
- `handleJustsaying` (`hub/message`) in `device.js`, invoked for any device message delivered through the hub after only signature/hash checks on the outer envelope (not on the `dh` fields' correctness against the local keys): [3](#0-2) 
- `hub/deliver` handling in `network.js`, which only checks that `recipient_ephemeral_pubkey` is one of the pubkeys registered for the target device address in the DB (permanent or last-known temp), but that DB row can be stale (temp key rotates, wrong package, or an attacker deliberately submits an old cached temp pubkey) relative to the live in-memory keys checked in `decryptPackage`: [4](#0-3) 
- `wallet.js` also calls `device.decryptPackage(body.encrypted_contract)` directly on attacker-controlled `arbiter_dispute_request` body content from a correspondent, with only a `try/catch` around the synchronous call, same crash exposure: [5](#0-4) 

### Impact Explanation
Triggering this condition kills the wallet/hub Node.js process (uncaught exception is fatal unless a global `process.on('uncaughtException')` handler exists and is not shown near this code). For a hub or an always-online node acting as its own hub, this is a denial-of-service that halts message delivery/relay and any node functions running in that process, preventing further unit posting/confirmation activity handled by that process until it is restarted — analogous to the wpa_supplicant DoS where a malformed fragment causes process termination. Any paired correspondent device (an already-trusted but not necessarily benign counterparty, per the allowed threat model of "paired device") can send a message causing this, and it does not require breaking any cryptography — merely supplying a `recipient_ephemeral_pubkey` value that doesn't match current in-memory keys.

### Likelihood Explanation
High: the condition is trivially reachable by any established correspondent (pairing is a normal, low-barrier relationship) or by exploiting temp-key rotation races, and requires no cryptographic break — just an out-of-band or stale `recipient_ephemeral_pubkey` value in an otherwise well-formed, validly-signed envelope (only the outer signature is checked, not the recipient-key correctness before this crash path is reached).

### Recommendation
Do not `throw` inside the `setTimeout` callback. Instead, emit a `nonfatal_error` event (the code already has this commented out) or otherwise handle the condition without executing an unguarded `throw` that isn't caught by any handler. If the crash is desired for genuine key-mismatch bugs during development, gate the `throw` so it cannot be triggered by a remote peer (e.g., only log/report telemetry, and never terminate the process based on unauthenticated network input).

### Proof of Concept
1. Pair two devices (A, B) so B is a correspondent of A.
2. From B, construct a `hub/deliver`/`hub/message` device message addressed to A with a syntactically valid `encrypted_package` (correct `iv`, `authtag`, `encrypted_message` types) but with `dh.recipient_ephemeral_pubkey` set to an arbitrary/stale base64 pubkey value (not A's current temp/prev-temp/permanent key), and a valid signature over the outer message signed with B's real key.
3. Deliver this message through the hub to A (or directly if A is self-hosted hub) via the normal `hub/deliver` → `hub/message` flow.
4. `decryptPackage` executes the `else` branch and schedules `setTimeout(() => { throw ... }, 100)`.
5. After 100ms, the uncaught exception propagates in the Node.js event loop and crashes A's process, since it originates outside of the enclosing `try/catch` context of `handleJustsaying`.
