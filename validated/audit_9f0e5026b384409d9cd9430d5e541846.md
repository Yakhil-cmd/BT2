Based on my investigation, I found the analogous pattern in the "attested" address-definition condition: an unbounded array of attestor addresses (`arrAttestors`) is embedded in an address/asset definition, validated once, and then re-evaluated in full on every subsequent unit that uses the definition, with the entire array passed into a SQL `IN(?)`/`attestor_address IN(...)` clause each time.

### Title
Unbounded attestor list in "attested" address/asset definitions causes repeated, unbounded-cost re-validation - (File: definition.js)

### Summary
The `attested` definition operator accepts an arbitrary-length array of attestor addresses (`arrAttestors`) with only an "at least one" check (`isNonemptyArray`), no upper bound. This array becomes part of a permanent address or private-asset spending condition, and is fully re-evaluated (and used in a SQL query) every single time any unit is validated against that address/asset, unlike a one-time setter.

### Finding Description
In `definition.js`, the validation of the `attested` operator only checks that `arrAttestors` is nonempty and that each element is a valid address, with no maximum size enforced: [1](#0-0) 

This is unlike other list-bearing operators (`search_param_list`, `array`, `dictionary`, function argument lists, `log` params, `remote_func_call` arguments) that are explicitly capped at small numbers (5, 30, or 100 elements) once past the `pemCurvesFixMci` upgrade: [2](#0-1) [3](#0-2) 

The `attested` operator has no equivalent cap. It is embedded permanently in an address definition or asset spending condition. Every time that address signs a unit, or every time the asset condition is checked, `validateAuthentifiers` re-evaluates the definition tree, including the `attested` node, by calling `storage.filterAttestedAddresses` with the full `arrAttestors` list: [4](#0-3) 

`filterAttestedAddresses` builds a SQL query with `attestor_address IN(?)` bound to the entire array: [5](#0-4) 

The address-definition complexity limiter (`MAX_COMPLEXITY`/`MAX_OPS`) counts the `attested` node itself as O(1) complexity (`evaluate` increments `complexity` and `count_ops` by 1 per definition node), independent of the size of `args`/`arrAttestors`: [6](#0-5) 

So an attacker can post a unit defining an address (or asset) whose definition contains `['attested', ['SOME_ADDR', [addr1, addr2, ..., addrN]]]` with an arbitrarily large `N`, paying only the normal complexity cost of a single definition node, while every future validation of a unit signed by that address (or spending that asset) must re-run a query with an `N`-sized `IN()` list and re-walk the whole array in JS.

### Impact Explanation
Because address/asset definitions are immutable once disclosed and are re-validated on every future spend, this is a repeated-cost DoS rather than a one-off gas spike: each unit signed by the crafted address (or referencing the asset) forces every validating node to execute a query and evaluation proportional to the attacker-chosen `N`. With a sufficiently large attestor list, this can materially slow down or stall validation of units from/about that address across the whole network of full nodes re-validating the DAG, which maps to "a network unable to confirm new units" in a targeted sense — nodes validating units touching this address suffer disproportionate CPU/DB cost per unit, unbounded by the normal complexity accounting.

### Likelihood Explanation
Reachable by any unprivileged user: defining an address (via `author.definition` in a normal unit) or an asset's spending condition with an `attested` clause is a standard, permitted operation; no special privilege is required. The attacker only needs to construct a large but valid array of base32 addresses (they need not be real/active attestors) to inflate `arrAttestors`. The complexity/ops accounting does not scale with array size for this operator, so normal complexity limits do not deter it.

### Recommendation
Add an explicit, small upper bound (similar to the 5/30/100 limits used elsewhere) on the length of `arrAttestors` in the `attested` (and `has definition change`'s `arrAttestors`-like lists, if any) validation in `definition.js`, and factor `arrAttestors.length` into `complexity`/`count_ops` so the definition's cost scales with the true evaluation cost, consistent with how `search_param_list`, arrays, and function-argument lists are already bounded.

### Proof of Concept
1. Attacker constructs a new address definition (or asset spending condition) of the form `['attested', ['this address', [addr1, addr2, ..., addr_N]]]` where `N` is very large (e.g., tens of thousands of valid-format addresses).
2. This passes `validateDefinition`/`validateAuthentifiers` validation in `definition.js` since only `isNonemptyArray` and per-element `isValidAddress` checks are performed — no length cap exists for this operator (contrast with `search_param_list`'s `arrPairs.length > 5` check).
3. Attacker posts a unit establishing this definition, then signs/spends with this address (or asset) repeatedly.
4. Every node validating any such unit calls `storage.filterAttestedAddresses`, which executes `attestor_address IN(?)` with the full `N`-element array, imposing disproportionate query/evaluation cost on every validator for every future unit touching this address/asset — with no complexity-limit throttling because the `attested` node's counted complexity is O(1) regardless of `N`.

		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
