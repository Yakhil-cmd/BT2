### Title
Atomic secondary-trigger cascades allow flashloan-style, all-or-nothing manipulation of balance/threshold-driven AA logic (e.g. bonding-curve "graduation" and ICO-style thresholds) - (File: `aa_composer.js`)

### Summary
The Virtuals report shows that `Bonding.sol::unwrapToken()` has no time-based restriction, so a buy → graduate → unwrap → sell loop can be closed atomically in one transaction using a flashloan, letting an attacker force premature "graduation" and manipulate reward accounting without any real, sustained liquidity risk. The Obyte analog is architectural: `aa_composer.js` allows one primary trigger unit to synchronously fan out into an unbounded chain of secondary AA triggers (`handleSecondaryTriggers`), and if *any* AA in that chain bounces, the *entire* chain (including all balance/state changes already applied to every AA touched) is atomically rolled back via `revert()`. Any AA whose logic uses another AA's live `balance[address][asset]` or `var[address][name]` (read through `formula/evaluation.js`) to decide a threshold-crossing, irreversible action (mint bonding-curve shares, finalize an ICO/milestone, "graduate" a pool) can have that live value manipulated by a temporary deposit/withdraw performed entirely inside the same atomic unit-processing cascade, with automatic full reversal if the attacker's own repayment step fails — mirroring the zero-capital-risk flashloan loop in the original report.

### Finding Description
`aa_composer.js` processes a primary trigger and, whenever the response payment targets another AA address, immediately and synchronously invokes that AA as a "secondary trigger" within the *same* call to `handleTrigger`, before the primary response unit is finally committed: [1](#0-0) 

If any AA further down the chain bounces, the whole call chain is unwound as a unit: [2](#0-1) 

Balances updated by every hop in the chain (`updateFinalAABalances` / `sendDummyUnit`) are kept in `objValidationState.assocBalances`, which is exactly what the `balance[address][asset]` formula operator reads live, even for *other* AA addresses in the same cascade: [3](#0-2) [4](#0-3) 

The bundled reference template `uniswap_like_market_maker.oscript` demonstrates the exact bonding-curve pattern the report attacks: shares (`mm_asset`) are minted proportionally to a live balance ratio, and the constant-product exchange price is computed directly from `balance[$asset]`/`balance[base]` read at trigger time: [5](#0-4) [6](#0-5) 

Because a single posted unit can drive an arbitrarily deep, fully atomic, fully reversible chain of AA calls (as shown by the "chain of AAs" and "AA with generated definition..." tests), an attacker-controlled pair of AAs (a "lender" AA and a target bonding-curve/threshold AA) can, in one unit:
1. have the lender AA forward funds to the bonding-curve AA to cross its mint/graduation threshold and update `var['mm_asset_outstanding']` (or an ICO's `var['total']`/`finished` flag) based on the momentarily inflated `balance[...]`,
2. immediately divest/withdraw in the same cascade,
3. forward the proceeds back to the lender AA to "repay" it,
all while the whole operation remains atomically revertible if step 3 fails — exactly the zero-risk, no-time-restriction property that the C4 report exploited in `unwrapToken()`. [7](#0-6) [8](#0-7) 

### Impact Explanation
Any AA that treats "funds currently sitting in my balance" or another AA's live balance/state var as proof of durable community support (bonding-curve graduation, ICO fundraising completion, LP-value used for reward distribution) can be forced into a state transition it should not have reached, and can permanently record inflated share/LP counts (`var['mm_asset_outstanding']`, `var['total']`, `finished`) before unwinding its own temporary deposit — this is a supply/valuation-inflation class impact, analogous to "premature graduation" and "reward distribution manipulated" in the original report, achievable purely through ocore's own atomic secondary-trigger and full-chain-revert semantics with no time-based safeguard between the manipulating deposit and its reversal.

### Likelihood Explanation
This requires no privileged access: any user can post a single unit with a `data` trigger to an AA they wrote (or a public AA following the shipped `uniswap_like_market_maker.oscript`/ICO-style template pattern) that forwards payments to a second self-authored AA and back. The mechanism (chained secondary triggers, all-or-nothing atomic revert) is a documented, tested core feature (`handleSecondaryTriggers`, `revert()`), not an edge case, so any AA author who relies on point-in-time `balance[...]` reads for threshold/graduation logic is exposed whenever their AA can be paid into by another AA.

### Recommendation
- For AA templates/patterns that use point-in-time balance ratios or outstanding-share counters as thresholds (bonding curves, ICO/milestone finalization, LP-value based reward eligibility), require that qualifying deposits be confirmed as stable (i.e., checked against `is_stable`/finalized state across multiple main-chain indices) before being counted toward a threshold, rather than trusting the same-unit `balance[...]`/`var[...]` snapshot.
- Consider documenting/warning in the AA authoring guidance that a chain of secondary triggers is atomic and fully reversible, so any developer-authored AA doing threshold/valuation logic based on `balance[address][asset]` of itself or another AA must not treat that value as economically committed until it survives past the current trigger's atomic cascade.

### Proof of Concept
1. Author AA1 (bonding-curve style, per `uniswap_like_market_maker.oscript`): on receiving `>1e5` bytes plus the paired asset, computes `$issue_amount` from `balance[$asset]`/`balance[base]` and mints/records `var['mm_asset_outstanding']`, then supports an immediate "divest" case that pays back proportional shares.
2. Author AA2 ("lender") that, upon receiving a payment with `trigger.data.borrow`, forwards funds to AA1 with `trigger.data` instructing an immediate divest-after-invest, then expects AA1 to forward the divested proceeds back to AA2 as "repayment".
3. Post a single unit paying AA2; this triggers AA1 as a secondary trigger (invest → mint shares against the momentarily-inflated `balance[...]`), then AA1's divest branch fires (within the same cascade or a further secondary hop) forwarding funds back to AA2.
4. If AA2's repayment check fails, `bounce()`/`revert()` unwinds the entire chain at zero cost to the attacker (per `handleSecondaryTriggers`'s `revert` path); if it succeeds, `var['mm_asset_outstanding']` (or an ICO's `finished`/`total`) is left inflated based on capital that was present for only the duration of one atomic unit-processing cascade — reproducing the report's "buy → graduate → unwrap → sell, repay flashloan" pattern without any of ocore's own core validation rejecting it. 				saveStateVars();
				addUpdatedStateVarsIntoPrimaryResponse();

			}

				throw Error("secondary triggers while bouncing");
			async.eachSeries(
				rows,
				function (row, cb) {
					var child_trigger = getTrigger(objUnit, row.address);
					child_trigger.initial_address = trigger.initial_address;
					child_trigger.initial_unit = trigger.initial_unit;
					if ("max_aa_responses" in trigger && mci >= constants.pemCurvesFixMci) // propagate the cap set on the primary trigger to secondary triggers

					var child_trigger_opts = { ...trigger_opts };
					child_trigger_opts.trigger = child_trigger;

					child_trigger_opts.arrDefinition = arrChildDefinition;
					child_trigger_opts.address = row.address;
					child_trigger_opts.bSecondary = true;
					child_trigger_opts.onDone = function (objSecondaryUnit, bounce_message) {
						if (bounce_message)
							return cb(bounce_message);

				},
				function (err) {
					if (err) {
						// revert
