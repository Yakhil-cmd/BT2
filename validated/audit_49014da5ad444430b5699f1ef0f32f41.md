### Title
Account spending authority binds to the NFT's original minter, not the current NFT owner, so a seller retains full control of a transferred position - (File: contracts/controller/src/account.rs)

### Summary
The OAuth2 bug class is an authorization grant that is not bound to the principal it was issued for, letting one party inject and consume another's authorization. The lending analog lives in the controller's account-authority check: `is_owner_or_delegate` / `require_owner_or_delegate` compare the caller against `Account.owner`, a field written once at account creation in `create_account_with`, while the position NFT — the actual ownership instrument — is freely transferable through the stock OpenZeppelin `NonFungibleToken` implementation with no transfer hook back into the controller. After a transfer, the seller keeps spending authority over the buyer's position.

### Finding Description
- `Account.owner` is set to the minter at creation and stored in the account record (`create_account_with`, `account.rs` lines 62–70). Nothing in the position NFT contract can update it: `PositionNft` exposes only the stock OZ `contracttrait` impl (`contract.rs` lines 131–173, 172) plus controller-gated `mint`/`burn`/`upgrade`; there is no `transfer`/`approve` override that could notify or resync the controller.
- `require_owner_or_delegate` (`account.rs` lines 115–140) is the guard on every value-moving verb (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend` — per `scripts/permissionless_entrypoints.txt` lines 49–56). Its first check is `caller == owner`, where `owner` is the stale stored field.
- The codebase itself proves the two notions diverge: sensitive verbs use `require_account_owner` (`account.rs` lines 142–148), which deliberately re-reads the live NFT owner via `storage::account_owner` rather than trusting `Account.owner` — an explicit acknowledgment that the stored owner can differ from the current NFT holder. The delegate map is also keyed by the stored owner (`get_delegates(env, account_id, owner)`, line 126).
- So the "authorization code" (the owner check backing every spending verb) remains bound to the original grantee after the underlying token changes hands — the direct analog of an authorization code not bound to the client that requested it.

### Impact Explanation
A user sells or transfers a funded position NFT (e.g., OTC sale of a leveraged account). The buyer becomes `owner_of(token_id)` and can pass `require_account_owner`, but the seller still passes `require_owner_or_delegate` on every account it ever owned. The seller calls `withdraw` to pull all collateral, or `borrow` to draw debt up to the threshold and walk away with the proceeds, leaving the buyer holding an insolvent or emptied account. This is theft of user funds reachable by any unprivileged address that legitimately owned the account once — no privilege, leaked key, or oracle manipulation required. Delegates added by the old owner also survive, since they are stored under `(account_id, old_owner)` and the check reads that exact slot.

### Likelihood Explanation
Position NFTs are designed to be transferable (standard `transfer`/`approve`/`transfer_from` come from the enumerable NFT trait), so secondary-market or wallet-rotation transfers are an intended flow. Any legitimate sale, gift, or wallet migration of a position NFT creates a window where the prior holder can drain the position. The attack requires no timing advantage — the stale grant persists indefinitely until `Account.owner` is overwritten, and no code path shown performs that overwrite on transfer.

### Recommendation
Bind spending authority to the live NFT owner, mirroring `require_account_owner`: in `is_owner_or_delegate`/`require_owner_or_delegate`, resolve `owner` via `storage::account_owner(env, account_id)` (the NFT's `owner_of`) instead of the cached `Account.owner`, and key delegate lookups under the live owner. Alternatively, resync `Account.owner` at the top of every account mutator, or override NFT `transfer`/`transfer_from` to notify the controller (requires a controller callback or making the NFT non-transferable). Note one caveat: if some unindexed helper resyncs `Account.owner` from the NFT on every account load, the exposure narrows to paths that skip it — that resync behavior should be confirmed before shipping a fix.

### Proof of Concept
1. Alice calls `controller::supply(0, spoke, usdc, ...)` which mints account `N` with `Account.owner = Alice` and NFT `N` to Alice.
2. Alice calls `position_nft::transfer(Alice, Bob, N)` (stock OZ entrypoint, no controller hook). `owner_of(N)` is now Bob; `Account.owner` remains `Alice`.
3. Alice calls `controller::withdraw(N, ...)`: `caller.require_auth()` passes with her signature, `require_owner_or_delegate` sees `caller == account.owner == Alice` and proceeds, moving Bob's collateral to Alice.
4. Bob can pass `require_account_owner` (for `add_delegate`, `renew_account`) but cannot stop Alice, and `remove_delegate` cannot help since Alice's authority is the owner slot itself, not a delegate entry.
