Unauthenticated identity spoofing via `X-Shipit-User` header lets a low-privilege `ApiClient` attribute deploys/rollbacks/aborts to arbitrary users - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Api::BaseController#identify_user` resolves `current_user` solely from the attacker-supplied `X-Shipit-User` header, looked up by case-insensitive login match, with no check that the value matches the authenticated `current_api_client.creator`. Any holder of a valid but low-privilege `ApiClient` basic-auth token can impersonate any existing Shipit user for deploy, rollback, task-trigger, and task-abort attribution.

### Finding Description
The intended binding is `current_user_identity == authenticated_identity_of_the_request`, i.e. `current_user.login == current_api_client.creator.login` (or `current_user` should be constrained to identities the presenting `ApiClient` is authorized to act as). Instead: [1](#0-0) 

`identify_user` reads `request.headers['X-Shipit-User']` and performs `User.where('lower(login) = ?', user_login.downcase).first` — a raw, unauthenticated, attacker-controlled lookup that never references `current_api_client` or `current_api_client.creator`.

`authenticate_api_client` only validates that the bearer token maps to *some* `ApiClient` record via `ApiClient.authenticate(token)`, which is unrelated to who `current_user` becomes: [2](#0-1) 

`ApiClient` has a `creator` association (`belongs_to :creator, class_name: 'User'`) that exists precisely to record which user issued/owns the token, but it is never consulted when resolving `current_user`: [3](#0-2) 

`require_permission!` only checks scope/operation permissions on the `ApiClient` (`read:stack`, `deploy:stack`, etc.), not identity: [4](#0-3) 

The spoofed `current_user` then flows directly into audit-significant actor fields in multiple controllers:
- `Api::DeploysController#create` passes `current_user` as the deploy's actor: [5](#0-4) 
- `Api::RollbacksController#create` passes `current_user` as the rollback/abort actor: [6](#0-5) 
- `Api::TasksController#trigger`/`#abort` pass `current_user` as the task actor: [7](#0-6) 

**Exploit flow:** An attacker obtains any valid `ApiClient` token scoped only with `deploy:stack` for a stack they're legitimately allowed to deploy (e.g., a CI service account token, or their own low-privilege token). They send `POST /api/stacks/:id/deploys` with `Authorization: Basic <valid-token>` and header `X-Shipit-User: <victim-login>`. `authenticate_api_client` accepts the request based on the token alone; `identify_user` then resolves `current_user` to the victim by login string match, and the resulting `Deploy`/`Task` record is attributed to the victim rather than the actual token holder — corrupting the audit trail and potentially interacting with any UI/authorization logic that trusts `current_user` for display or downstream checks (e.g., `aborted_by`, `Task#user`).

No guard in `authenticate_api_client`, `require_permission!`, `ApiClient#check_permissions!`, or `ExplicitParameters` schemas cross-checks the header against `current_api_client.creator`. `force_github_authentication`/`User#authorized?` are irrelevant here since this is the API basic-auth path, not the session/OAuth path.

### Impact Explanation
This is an authentication/attribution bypass on the API path: an unauthorized actor (holder of any valid API token, regardless of scope) can cause `Task`, `Deploy`, and `Rollback` records — and the actual `PTY.spawn`-backed deploy/rollback commands they trigger — to be attributed to an arbitrary victim user of the attacker's choosing. This satisfies the Critical category "an unauthorized deploy, rollback ... " both because the action is genuinely executed (real deploy/rollback commands run) and because the audit trail (who did it) is forged, which can be used to frame another user, evade accountability, or interact with any downstream code that keys behavior off `current_user.login`. It is repeatable against any stack the presenting `ApiClient` has permission for, against any existing Shipit user login.

### Likelihood Explanation
Preconditions are modest: the attacker needs *any* valid `ApiClient` token with the relevant `permissions` scope (`deploy:stack`, `read:stack`, etc.) — this could be their own legitimately-issued low-privilege token (e.g., a personal CI token), not a stolen high-privilege secret. No GitHub credentials, `api_clients_secret`, `secret_key_base`, or webhook secret are required. Sending an extra HTTP header is trivial and requires no special tooling. This is highly feasible and fully repeatable.

### Recommendation
Remove trust in the raw `X-Shipit-User` header, or bind it to the authenticated `ApiClient`: only allow `identify_user` to resolve to `current_api_client.creator` (ignore the header entirely for `ApiClient`s that aren't otherwise trusted), or require that `X-Shipit-User` matches `current_api_client.creator.login` before honoring it, rejecting the request otherwise. If impersonation is an intended feature for specific privileged/service clients, gate it behind an explicit `ApiClient` permission (e.g., `impersonate:user`) rather than accepting any header value unconditionally.
