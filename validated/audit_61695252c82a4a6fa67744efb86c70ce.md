### Title
Cross-repository/stack commit-status injection via unscoped `sha` lookup in webhook `status` handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook only against the **organization** derived from the payload's `repository.owner.login` (or `organization.login`) field, by selecting that org's `Shipit.github(organization: repository_owner)` app config and checking the HMAC signature against it. [1](#0-0)  Once the signature is accepted, the raw `params` (including the attacker/organization-controlled `sha` field) are handed unfiltered to the matching event handler. [2](#0-1) 

The `status` event handler, however, never re-checks that the commit being updated belongs to a stack/repository owned by the organization that was actually authenticated. It looks the commit up **globally**, by `sha` alone:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

The `sha` column has a non-unique composite index on `(stack_id, sha)` rather than a global uniqueness constraint, confirming the schema's intent that shas are scoped per stack, while this handler ignores that scoping entirely. [4](#0-3) 

### Finding Description
This is the direct analog of the reported bug class: a verification step ("organization authenticated by the HMAC signature") that does not cover a field actually acted upon ("commit rows written, selected purely by `sha`, spanning every stack/repository in the installation"). Just as `mintlvlUSD` failed to bound the equal-decimals case with a slippage check, `StatusHandler#process` fails to bound the "match on `sha` across all stacks" case with an owning-repository/stack check.

Concretely:
- `verify_signature` picks the webhook secret using `repository_owner` from the payload, and only confirms the payload was HMAC-signed by *that* organization's registered GitHub App/webhook secret. [5](#0-4) 
- The equality it establishes is: `signing_org == claimed_repository_owner`.
- It does **not** establish: `claimed_repository_owner == repository_owner_of_every_commit_row_touched_by_the_handler`.
- `StatusHandler` breaks that missing binding by resolving the target `Commit` rows solely via `Commit.where(sha: params.sha)`, with no `stack_id`/`repository` filter tying the write back to the authenticated organization's repository. [3](#0-2) 

Any organization/repository that is legitimately registered as a Shipit stack (i.e., any tenant onboarded onto this Shipit instance — which, per the engine's own design, is intended to host many independent teams/repos) can therefore send a completely genuinely-signed `status` webhook from its own repository, but with an arbitrary `sha` value copied/guessed from a commit belonging to a *different* organization's stack. Shipit will happily attach that (attacker-controlled) CI status to the foreign commit.

### Impact Explanation
Writing an attacker-controlled `Status` onto a foreign commit is not cosmetic: `Commit#create_status_from_github!` → `add_status` recomputes `state`, and if the new status flips a commit from pending/unknown to `success` (or vice versa to unblock a previously failing/blocking check), it emits `commit_status`/`deployable_status` hooks and, critically, calls `stack.schedule_merges if new_status.pending? || new_status.success?`. [6](#0-5)  For stacks with continuous deployment/merge-queue enabled, this can cause an **unauthorized deploy** of a commit that never actually passed CI in that organization's real pipeline — a cross-tenant integrity break that matches the "unauthorized deploy" Critical-impact category in scope. At minimum it allows one tenant to corrupt CI/status state (and thus deploy gating decisions) of another tenant's stack, which is an authorization boundary violation between the "organization the signature authenticates" and "the repository/stack whose commit rows get written."

### Likelihood Explanation
Exploitability only requires the attacker to control (or register) one legitimate Shipit-tracked repository/organization — not any secret belonging to the victim organization. The attacker needs to know or predict a target commit's `sha` in the victim stack (shas are often discoverable — e.g., via public repos, PR links, Shipit's own read-access UI/API for stacks the attacker can view, or CI logs) and craft a `status` webhook payload with that `sha`. Because the vulnerable lookup is a simple `WHERE sha = ?` with no scoping, and 40-character git SHAs are effectively opaque but not secret, this is a plausible, low-friction attack for any multi-tenant Shipit deployment where independent teams/orgs each own their own repos/webhooks. It's classified low/moderate rather than trivially widespread only because it requires a targeted matching `sha`, but no privileged credentials, session, or secret are required beyond what a legitimate (even low-trust) tenant already has.

### Recommendation
Scope the commit lookup (and every other webhook handler resolving records purely from payload identifiers) to the repository/stack implied by the *verified* organization, e.g.:

```ruby
def process
  return unless params.repository # or organization from the signed payload
  Commit.joins(:stack).merge(Stack.where(repository: matching_repository)).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

More generally, `WebhooksController` should pass along the authenticated `repository_owner` (and ideally the specific repository) to every handler, and each handler that mutates `Commit`/`Stack` records must filter by that authenticated repository instead of trusting an unscoped `sha`/other identifier taken straight from the payload.

### Proof of Concept
1. Attacker registers/controls `attacker-org/attacker-repo` as a real Shipit stack with a valid, correctly configured GitHub App/webhook secret for `attacker-org`.
2. Victim organization `victim-org` has a separate stack tracking commit `sha = abcdef123...` currently in `pending`/`failure` state (blocking deploys/merge queue).
3. Attacker (from their own genuinely signed webhook delivery infrastructure, or by directly calling GitHub's re-deliver/test-webhook feature for their own repo) sends a `status` event payload:
   ```json
   { "sha": "abcdef123...", "state": "success", "context": "ci/attacker", "repository": {"owner": {"login": "attacker-org"}} }
   ```
   signed with `attacker-org`'s legitimate webhook secret.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and successfully verifies the HMAC signature (it is genuinely from `attacker-org`). [5](#0-4) 
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: 'abcdef123...')` — matching the victim's commit — and calls `create_status_from_github!`, creating a `success` status attributed to the forged payload, on a stack the attacker has no authorization over. [3](#0-2) 
6. If `victim-org`'s stack has continuous deployment enabled, `add_status` triggers `stack.schedule_merges`, potentially initiating a deploy of that commit despite it never passing the victim's real CI. [6](#0-5) 

Note: I was unable to fully trace `schedule_merges` → `ContinuousDeliveryJob` → actual deploy trigger within the remaining tool budget (the final `read_file` calls for `stack.rb` lines 120–241 and the rest of `commit.rb` did not return before this response had to be produced), so the exact automatic-deploy path from `schedule_merges` should be independently verified against `app/models/shipit/stack.rb` and `app/jobs/shipit/continuous_delivery_job.rb` before treating "unauthorized deploy" as fully proven end-to-end; the cross-tenant status-write itself, however, is confirmed directly from the cited handler code.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
