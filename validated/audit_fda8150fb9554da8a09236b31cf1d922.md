## Analog Found

### Title
Unsigned front-running of `SystemInstruction::InitializeNonceAccount` permanently seizes nonce authority, enabling unsigned lamport theft - (`programs/system/src/system_instruction.rs`)

### Summary
`InitializeNonceAccount` sets the durable-nonce `authority` field from unchecked instruction data with **no requirement that the target account, its intended owner, or the supplied authority ever sign the transaction**. Because the transition only fires once (`Uninitialized -> Initialized`), any unprivileged sender can race a legitimate owner's initialization transaction, permanently plant themselves as the nonce authority, and subsequently drain the account's lamports via `WithdrawNonceAccount`, which only requires the (now attacker-controlled) `authority` to sign — not the account's own keypair.

### Finding Description
`initialize_nonce_account` transitions state solely based on whether the account is currently `Uninitialized`, taking the `authorized` pubkey directly from instruction data with zero signer verification: [1](#0-0) 

This is dispatched from `system_processor.rs` without any signer check on account index 0 (the nonce account) or on the caller-supplied `authorized` pubkey — contrast this with `allocate`/`assign`/`create_account`, which explicitly require the "to" address to be present in `signers`: [2](#0-1) [3](#0-2) 

Once `State::Initialized` is set, any later legitimate `InitializeNonceAccount` call on the same account is rejected outright: [4](#0-3) 

This is precisely the bug-class described in the report: a privileged field (`delegate` there, `authority` here) is written under a "first write wins" rule with no check that the writer is the account's actual owner/controller, and once set, the legitimate party's later correct transaction is rejected, permanently locking in the attacker's value.

The stolen `authority` is not cosmetic — `WithdrawNonceAccount` (and `AdvanceNonceAccount`) trust `data.authority` as the sole signer requirement to move funds out of the account: [5](#0-4) 

Accounts reach the exploitable "funded but Uninitialized System-owned, not-yet-initialized" state via legitimate flows that don't require the account's own signature at initialization time, e.g. `CreateAccountWithSeed`/`AllocateWithSeed` (only the `base` key signs, not the derived address) or `CreateAccountAllowPrefund` (the "to" account itself must sign per instruction accounts, but a prefunded/pre-existing account visible on-chain before its owning transaction lands is still an observable, attackable window). In all such flows, any account that is publicly known to be about to become a nonce account (address is derivable/observable pre-confirmation) is a race target.

### Impact Explanation
An attacker who successfully front-runs `InitializeNonceAccount`:
1. Becomes the nonce `authority` without ever signing with, or possessing, the nonce account's own key.
2. Can call `WithdrawNonceAccount`, signing only as `authority`, to drain the account's lamports to an address of their choosing — concrete unsigned fund theft.
3. Permanently blocks the legitimate owner's own initialization attempt (`InvalidAccountData`), mirroring the report's "brick the true owner from correcting the state" pattern, until the victim recognizes the compromise (there is no owner-side recovery instruction besides accepting the loss).

### Likelihood Explanation
This requires only a single unprivileged transaction sent by the attacker ahead of the legitimate initializer, targeting a nonce-account address that is either derivable in advance (via `create_with_seed`) or observable on-chain in a funded-but-uninitialized state before the owner's initializing transaction lands (a classic front-run race, reachable by any network participant/leader-adjacent actor, not requiring any special privilege). No cryptographic signature over the target account is needed at any point in the attack.

### Recommendation
Require the nonce account itself (or an appropriate signer bound to its creation, e.g. the `base` key used for seed-derived accounts) to be a signer in `InitializeNonceAccount`, matching the signer discipline already enforced in `allocate`/`assign`/`create_account`. Alternatively, require the `authorized` pubkey to equal the transaction's designated creator/base key unless explicitly delegated by a signed instruction.

### Proof of Concept
1. Victim intends to create a durable-nonce account at address `N` (e.g. derived via `Pubkey::create_with_seed(base, seed, system_program::id())`) and sends `CreateAccountWithSeed`/prefund transaction that funds `N` to rent-exemption but does not yet call `InitializeNonceAccount` in the same atomic transaction.
2. Attacker observes `N` on-chain (funded, owned by `system_program`, `State::Uninitialized`) and submits `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` with `N` as instruction account 0 (writable, `is_signer` not required by the processor) before the victim's own `InitializeNonceAccount` transaction lands.
3. `initialize_nonce_account` in `programs/system/src/system_instruction.rs` succeeds because the only preconditions are `account.is_writable()` and `State::Uninitialized`; `attacker_pubkey` becomes `data.authority`.
4. Victim's later `InitializeNonceAccount(victim_pubkey)` on `N` now hits `State::Initialized(_) => Err(InstructionError::InvalidAccountData)` and is permanently rejected.
5. Attacker submits `SystemInstruction::WithdrawNonceAccount(lamports)` signing only with their own keypair (matching `data.authority`), draining `N`'s lamports to an address they control — fund theft without ever holding `N`'s private key.

fn allocate(
    account: &mut BorrowedInstructionAccount,
    address: &Address,
    space: u64,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !address.is_signer(signers) {
        ic_msg!(
            invoke_context,
            "Allocate: 'to' account {:?} must sign",
            address
        );
        return Err(InstructionError::MissingRequiredSignature);
    }

    // if it looks like the `to` account is already in use, bail
    //   (note that the id check is also enforced by message_processor)
    if !account.get_data().is_empty() || !system_program::check_id(account.get_owner()) {
        ic_msg!(
            invoke_context,
            "Allocate: account {:?} already in use",
            address
        );
        return Err(SystemError::AccountAlreadyInUse.into());
    }

    if space > MAX_PERMITTED_DATA_LENGTH {
        ic_msg!(
            invoke_context,
            "Allocate: requested {}, max allowed {}",
            space,
            MAX_PERMITTED_DATA_LENGTH
        );
        return Err(SystemError::InvalidAccountDataLength.into());
    }

    account.set_data_length(space as usize)?;

    Ok(())
}

fn assign(
    account: &mut BorrowedInstructionAccount,
    address: &Address,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    // no work to do, just return
    if account.get_owner() == owner {
        return Ok(());
    }

    if !address.is_signer(signers) {
        ic_msg!(invoke_context, "Assign: account {:?} must sign", address);
        return Err(InstructionError::MissingRequiredSignature);
    }

    account.set_owner(&owner.to_bytes())
}
