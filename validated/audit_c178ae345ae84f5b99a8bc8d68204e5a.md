### Title
Permanent DoS of AA Fund-Distribution Logic via Unconditional Reversion on Any Secondary-AA Failure - (File: `aa_composer.js`)

### Summary
Obyte's Autonomous Agent (AA) execution engine cascades a primary AA's payment outputs into "secondary triggers" whenever an output address is itself an AA. This cascade is implemented in `handleSecondaryTriggers()`/`revert()` in `aa_composer.js`. If *any single* address in the (potentially attacker- or governance-supplied) set of payment destinations is itself an AA that unconditionally bounces, the framework reverts the *entire* primary response and bounces the whole trigger — with no mechanism to skip, tolerate, or later remove the bad destination, since AA code and any state committed to it are immutable. This is the same bug class as the `ProtocolShareReserve._releaseFund()` report: iterating over a set of "destination" addresses and calling into them, where one incorrect/misbehaving destination causes the whole distribution operation to permanently fail, with no way to fix the array afterward.

### Finding Description
When a primary AA sends a payment whose output address belongs to another AA, `handleTrigger()` collects `arrOutputAddresses` and calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)`: [1](#0-0) 

For every AA address found among the outputs, a secondary trigger is executed via `async.eachSeries`, and the very first failure (`bounce_message`) short-circuits the loop: [2](#0-1) 

Crucially, the error handler does **not** skip or isolate the failing destination — for the primary trigger it calls `revert()`, which unconditionally rolls back *all* state changes and responses accumulated so far (from the primary AA and any other, well-behaved, secondary AAs already processed in the same chain), and then bounces the whole unit: [3](#0-2) 

Just like `ProtocolShareReserve._releaseFund()` iterating a `DistributionConfig` array and calling `updateAssetsState()` on each entry — where one entry lacking that interface reverts the whole distribution — `handleSecondaryTriggers()` iterates over the set of AA destinations derived from a payment message and executes each one, where a single misbehaving/incompatible destination AA (one that always bounces for the relevant trigger shape) reverts the *entire* operation, not just the failing leg. AA definitions in Obyte are content-addressed and immutable once deployed (analogous to the report's "Venus Treasury… not upgradable" destination), and there is no built-in provision in `aa_composer.js` to exclude a known-bad destination from future distributions, and no way to "unregister" a destination once an AA's own state or logic has locked it in (e.g., an AA that stores a list of profit-share/payout addresses in a `state` var and forwards funds to all of them on every trigger).

### Impact Explanation
Any AA design pattern that fans out payments to a set of stored/derived destination addresses (revenue-sharing AAs, proxy/forwarder AAs, multi-recipient payout AAs) is exposed: if one destination is (or later becomes reachable as) a broken AA that bounces, every future trigger that would route funds through that destination causes the *entire* AA response chain to revert and bounce, permanently disabling the AA's core payout/distribution functionality for all users, not just the party that supplied the bad address. Because AA code/state cannot be patched, this is a durable freeze of AA funds/functionality — consistent with the "AA fund loss or freezing" impact class.

### Likelihood Explanation
The chain is reachable by any unprivileged AA trigger sender: composing a trigger whose payment output routes (directly, or via an AA's own logic) to an address controlled by, or already fixed as, a misbehaving AA is sufficient to trip `revert()`. AAs that store payout destinations in persistent `state` vars (a common, documented oscript pattern for revenue-sharing/forwarder templates) are permanently vulnerable once such a destination is added, since neither the AA logic nor `aa_composer.js` provides isolation or removal of a single failing leg of a multi-destination payout.

### Recommendation
In `handleSecondaryTriggers()`, provide an opt-in mechanism for a primary AA to tolerate/skip a failing secondary AA trigger instead of unconditionally calling `revert()` for the whole chain (e.g., an explicit flag per-message or per-output indicating "best-effort" delivery), so a single incompatible/broken downstream AA cannot cascade into a full rollback of an otherwise-successful trigger. At minimum, document this cascading-revert behavior prominently so AA authors avoid storing unremovable/unvalidated destination-address lists that are iterated over for payouts.

### Proof of Concept
1. Deploy AA `B` that always bounces for any trigger it receives (e.g., `bounce('always fail')` unconditionally, or lacking a payment message that returns funds so the framework itself decides "no messages after filtering").
2. Deploy AA `A` designed as a "distributor": on trigger, it stores address `B` (among others) in a state var array during an initial governance-like `define` trigger, and on every subsequent distribution trigger sends a `payment` message with outputs to every stored address, including `B`.
3. Send any subsequent trigger to `A` that includes `B` among the computed output addresses.
4. `handleTrigger()` → `handleSecondaryTriggers()` runs `B`'s trigger, which bounces; `async.eachSeries`'s final callback receives `err` and, since the outer call is not itself secondary, invokes `revert()`, rolling back all of `A`'s state changes and responses and bouncing the entire unit [4](#0-3) .
5. Every future trigger to `A` that routes any payment to `B` reproduces this revert, and because `A`'s definition/state cannot be amended to drop `B` from its destination set without new AA logic (impossible for an already-deployed AA), the distribution functionality of `A` is permanently broken for all users whose flows touch `B`.
