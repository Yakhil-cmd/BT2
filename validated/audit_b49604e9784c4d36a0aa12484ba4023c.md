### Title
Excess deposit sent to `AddressRegistrar::register` is permanently locked with no withdrawal mechanism - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `#[payable]` `register` function in the `AddressRegistrar` contract only refunds the attached deposit when the target storage slot is already occupied (address collision). When the address is not yet registered (the normal, successful path), any deposit amount above the storage cost required to store the new entry is silently retained by the contract and there is no function anywhere in the contract to withdraw or sweep that excess balance.

### Finding Description
`register` is marked `#[payable]` and computes the exact `required_deposit` needed to cover the storage cost of the new `(address, account_id)` entry: [1](#0-0) 

It validates that `given_deposit >= required_deposit`, but never compares the two amounts for equality nor refunds the difference. In the `Entry::Occupied` branch (collision) the full attached deposit is refunded to the caller via a promise transfer: [2](#0-1) 

But in the `Entry::Vacant` branch — the success path that actually stores the mapping — the deposit is simply consumed with no refund logic for any amount exceeding `required_deposit`: [3](#0-2) 

The contract exposes only `new`, `register`, `lookup`, and `get_address` — there is no owner/admin `withdraw` or similar function capable of moving the contract's NEAR balance back out: [4](#0-3) [5](#0-4) 

Any caller who attaches more than the exact `required_deposit` on a successful `register` call has the excess permanently trapped in the contract's balance, exactly the "unnecessary payable function with no way to withdraw" bug class described in the report (there, `withdraw`/`claimInterest` accepted unused `msg.value`; here, `register` accepts and keeps unused excess `attached_deposit`).

### Impact Explanation
This causes concrete, permanent loss of user funds (NEAR tokens) with no recovery mechanism, matching the "concrete token... theft/loss" and "unauthorized state or balance change" impact bar. Every over-deposit from every caller accumulates in the contract account and can never be retrieved by anyone, including the original depositor or the contract owner.

### Likelihood Explanation
`register` is a public, unprivileged, permissionless method callable by any account via a standard `FunctionCall` action/transaction; the only way to avoid the loss is for every caller to compute `required_deposit` perfectly and attach exactly that amount, which is error-prone (e.g. wallets/dApps commonly attach round, conservative deposit amounts to be safe against underpayment). This makes accidental fund loss likely in practice for typical integrations.

### Recommendation
In the `Entry::Vacant` branch of `register`, compute `given_deposit.saturating_sub(required_deposit)` and, if nonzero, issue a refund transfer to `env::predecessor_account_id()` (mirroring the pattern already used in the `Entry::Occupied` branch), or add an owner-only `withdraw_excess` function to sweep any balance above the storage-staking requirement.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `new()`.
2. Compute `required_deposit` for a given `account_id` (per the formula in `register`: `20 + account_id.len()` bytes × `storage_byte_cost`).
3. Call `register(account_id)` attaching a deposit strictly greater than `required_deposit` (e.g. 2× or a round number like `1 NEAR`).
4. Observe the call succeeds (`Entry::Vacant` path), the mapping is stored, and the contract's account balance increases by the full attached deposit rather than only `required_deposit`.
5. Confirm there is no method on the contract that can move the excess balance back out — the funds are permanently stuck.

    /// Attempt to look up the account ID associated with the given address.
    /// If an entry for that address is found then the associated account id
    /// is returned, otherwise `None` is returned. Use the `register` method
    /// to add entries to the map.
    /// This function will panic if the given address is not the hex-encoding
    /// of a 20-byte array. The `0x` prefix is optional.
    pub fn lookup(&self, address: String) -> Option<AccountId> {
        let address = {
            let mut buf = [0u8; 20];
            hex::decode_to_slice(address.strip_prefix("0x").unwrap_or(&address), &mut buf)
                .unwrap_or_else(|_| env::panic_str("Invalid hex encoding"));
            buf
        };
        self.addresses.get(&address).cloned()
    }

    /// Computes the address associated with the given `account_id` and
    /// returns it as a hex-encoded string with `0x` prefix. This function
    /// does not update the mapping stored in this contract. If you want
    /// to register an account ID use the `register` method.
    pub fn get_address(&self, account_id: AccountId) -> String {
        let address = account_id_to_address(&account_id);
        format!("0x{}", hex::encode(address))
    }
}
