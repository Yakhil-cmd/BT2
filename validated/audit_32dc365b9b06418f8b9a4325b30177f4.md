### Title
Missing authority signer/ownership check in `InitializeBuffer` allows frontrunning of buffer account initialization - (File: programs/bpf_loader/src/lib.rs)

### Summary
The BPF Loader Upgradeable's `InitializeBuffer` instruction sets the buffer authority to whatever account is passed as instruction account index 1, without requiring that account to sign the transaction, and without any check that the caller is the account that originally allocated/funded the buffer. This mirrors the reported Solidity issue where `initialize()` is a separate, unauthenticated call that can be frontrun to seize ownership of a freshly deployed-but-uninitialized contract.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` as follows: [1](#0-0) 

The only guard is that the target buffer account must currently be `UpgradeableLoaderState::Uninitialized`; there is no signer check on the buffer account (index 0) and no signer requirement on the authority account (index 1) that is being recorded as `authority_address`. Compare this to the `Write` instruction handler immediately below it, which explicitly checks `instruction_context.is_instruction_account_signer(1)?` for the authority before allowing a write: [2](#0-1) 

Buffer accounts are ordinary keypair accounts created via the System Program's `CreateAccount` (owned by `bpf_loader_upgradeable`, left in `Uninitialized` state) and then initialized with a separate `InitializeBuffer` instruction — this is visible in the reference client flow in `runtime/src/loader_utils.rs`: [3](#0-2) 

If a client submits the `CreateAccount` instruction for the buffer as its own transaction (or as an instruction that completes before the follow-up `InitializeBuffer` transaction lands), the buffer account exists on-chain, owned by `bpf_loader_upgradeable`, in the `Uninitialized` state, but with no protection tying its subsequent initialization to the original creator. Any unrelated transaction sender can submit their own `InitializeBuffer` instruction naming the legitimate buffer address at index 0 and their own pubkey (or any pubkey) at index 1 as "authority," because neither account needs to sign. The check only fails if the account is already initialized — it never verifies that the caller has any relationship to the account's creation. Whoever's `InitializeBuffer` instruction lands first wins the authority slot, exactly as in the reported case where whoever calls `initialize()` first on the proxy gains ownership.

### Impact Explanation
Winning the race for `InitializeBuffer` grants the attacker (or any third party) the `authority_address` on the buffer, which is required to subsequently `Write` program bytes into the buffer and to `SetAuthority`/`Close` it. This lets an attacker hijack a buffer intended for a legitimate program deployment, blocking the real deployer (denial of service on the deployment pipeline) or substituting their own authority so that a follow-on `DeployWithMaxDataLen`/`Upgrade` uses attacker-controlled buffer contents, potentially resulting in a malicious program being deployed under attacker control instead of the legitimate one. This does not itself move funds or corrupt consensus, but it can hijack the authority over a program-deployment primitive that an unprivileged transaction sender can reach entirely with ordinary instructions (`CreateAccount` + `InitializeBuffer`), matching the "CPI privilege propagation" / account state hijack pattern called out in-scope.

### Likelihood Explanation
Exploitation requires only observing a pending `CreateAccount` for a to-be-buffer account (visible once broadcast, before `InitializeBuffer` for it lands) and racing an `InitializeBuffer` transaction ahead of the legitimate one — no signatures from the victim are needed, and no special privileges are required. This is directly analogous to and as easy as the reported frontrunning of `initialize()` on the EVM proxy pattern. Likelihood is reduced somewhat in practice because most tooling (e.g. CLI `program deploy`/`write-buffer`) issues the `CreateAccount` + `InitializeBuffer` pair in the same transaction/message when possible, but the protocol itself provides no enforcement preventing separate submission, and any workflow (custom tooling, RPC batching, retried transactions) that splits them is exploitable.

### Recommendation
Require the authority account (and/or the buffer account) to be a signer on `InitializeBuffer`, or bind initialization to the same transaction that creates the account (e.g., by requiring the account's `CreateAccount` payer/signer to co-sign `InitializeBuffer`), so a third party cannot claim authority over a buffer account it did not create.

### Proof of Concept
1. Legitimate deployer sends transaction A: `system_instruction::create_account(payer, buffer_pubkey, lamports, size, &bpf_loader_upgradeable::id())`, creating the buffer account in `Uninitialized` state (owned by `bpf_loader_upgradeable`).
2. Attacker observes transaction A land (or observes it in-flight) and, before the deployer's follow-up `InitializeBuffer` transaction confirms, submits transaction B: an `InitializeBuffer` instruction with account 0 = `buffer_pubkey`, account 1 = `attacker_pubkey` (not signed).
3. `process_loader_upgradeable_instruction`'s `InitializeBuffer` branch [1](#0-0)  succeeds because the buffer is still `Uninitialized`; it sets `authority_address = Some(attacker_pubkey)`.
4. The deployer's own `InitializeBuffer` transaction now fails with `AccountAlreadyInitialized`, and the attacker is the sole authority able to `Write` to, `SetAuthority` on, or `Close` the buffer — hijacking the deployment buffer intended for the legitimate program.
