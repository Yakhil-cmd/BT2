### Title
Uncaught exceptions in oscript/AA formula evaluation crash the node on a crafted AA trigger unit - (File: formula/evaluation.js, aa_composer.js, network.js)

### Summary
The free5GC advisory describes a crafted network message that reaches an insufficiently defensive code path and causes a process crash (DoS). The analogous reachable surface in `ocore` is oscript/AA formula evaluation: `formula/evaluation.js` and `aa_composer.js` contain numerous `throw Error(...)` statements inside the AA trigger/formula evaluation pipeline that are invoked from asynchronous callbacks rather than being funneled through the `setFatalError`/`callback(err)` error path. Because `network.js` installs a global `uncaughtException` handler that deliberately re-throws to kill the process (`process.on('uncaughtException', ... throw err;)`), any oscript path that throws synchronously instead of returning a formula error is a reachable node-wide denial-of-service triggered by an ordinary AA trigger unit or AA definition author — no privileged/peer/operator access required.

### Finding Description
`exports.evaluate` in `formula/evaluation.js` begins with hard `throw Error(...)` guards that execute unconditionally before any try/catch wrapping in the calling code: [1](#0-0) 

Likewise, deep inside `aa_composer.js`'s `replace()` function (used to resolve every formula field of an AA definition/messages against a trigger), an unexpected value shape falls through to `throw Error('unknown type of value in ' + name)`: [2](#0-1) 

Other structural checks in `handleTrigger` also `throw Error` directly (e.g., mismatched trigger_opts, missing base AA, bad AA definition shape) instead of surfacing an oscript-level validation error: [3](#0-2) 

These calls happen from `formulaParser.evaluate(opts, [], xpath, function (err, res) {...})` call sites spread across `replace()`, `evaluateAA()`, and `executeStateUpdateFormula()`, all invoked asynchronously while a unit is being validated/executed as a primary or secondary AA trigger: [4](#0-3) [5](#0-4) 

Unlike the rest of the evaluator, which carefully routes runtime formula errors through `setFatalError(...)` so they surface as `callback(err, null)` and get bounced gracefully, these specific `throw Error` statements bypass that mechanism. If they fire inside an `async`/`setImmediate`-deferred callback (as most formula evaluation is), the exception escapes the call stack that contains the `try/catch` (if any) and becomes an uncaught exception at the process level.

`network.js` explicitly treats any uncaught exception as fatal and crashes the whole node: [6](#0-5) 

This exactly mirrors the CWE-94/DoS bug class in the advisory: a remotely-supplied, attacker-crafted message (here, a posted unit that is a primary AA trigger, or a newly defined AA whose definition/getters/messages are evaluated against attacker-controlled trigger data) reaches a code path that is validated with the expectation of "return an error", but instead throws synchronously and crashes the process.

### Impact Explanation
If a reachable input can cause one of these `throw Error` statements to execute inside an async formula-evaluation callback (rather than being caught synchronously before the event loop returns), the throw becomes an uncaught exception, and `network.js`'s handler intentionally kills the process. Since AA triggers are processed automatically whenever a unit pays to an AA address, an unprivileged unit poster can craft a payment/trigger unit (or deploy a malicious AA definition that misbehaves against ordinary triggers) that crashes every full node that processes it — a network-wide "unable to confirm new units" condition, which the validation rules for this analog scan classify as impactful (node disagreement / inability to process units is explicitly in scope).

### Likelihood Explanation
Likelihood is Medium: reaching one of these specific `throw Error` lines (as opposed to the vast majority of malformed inputs, which are correctly caught by `setFatalError`/oscript-level validation in `formula/validation.js` before execution) requires finding a state/formula shape that the pre-execution `validate()` pass in `formula/validation.js` accepts as syntactically/semantically legal but that nonetheless drives `evaluation.js`/`aa_composer.js` into one of the unguarded throw branches at runtime (e.g., a mismatch between validated AST shape and actual runtime value, or a state produced only by state-var mutation not visible to the static validator). This is a real but non-trivial to pinpoint interaction between the static formula validator and the dynamic evaluator/composer, and it does not require any privileged access — only posting a unit or defining an AA.

### Recommendation
- Replace the direct `throw Error(...)` calls inside `formula/evaluation.js`'s `exports.evaluate` (lines 93–98) and `aa_composer.js`'s `replace()`/`handleTrigger()` internal helpers with the existing `setFatalError`/`callback(err)` pattern so that any anomaly during trigger/formula processing degrades to a bounced AA response or unit rejection instead of crashing the process.
- Wrap all top-level invocations of `formulaParser.evaluate`, `handleTrigger`, and `replace` in `aa_composer.js` with try/catch, converting any synchronous throw into a call to `onDone`/`callback` with an error, mirroring how parser errors are already handled (`formula/evaluation.js` lines 108–121).
- Add fuzz/property tests exercising `aa_composer.handleTrigger` and `formula/evaluation.js` with adversarial trigger payloads (deeply nested/odd-typed `trigger.data`, edge-case timestamps, malformed state vars) to find and eliminate any other reachable unguarded throws in this pipeline.

### Proof of Concept
Concrete field-level proof of concept could not be fully constructed within the scope of this Ask session: pinpointing which state/formula input actually reaches the unguarded throw in `aa_composer.js:872` (`replace()`'s `else throw Error('unknown type of value in ' + name)`) versus the many correctly-guarded runtime errors requires deeper tracing of what "value" shapes are possible when an AA's definition/messages are dynamically constructed via nested `{...}` formulas returning objects/functions, which is beyond what could be verified with the available read-only search tools. A Devin session with full codebase and test-execution access would be needed to confirm a concrete triggering AA definition + trigger unit that reaches this branch (or one of the other 48 `throw Error` sites in `formula/evaluation.js`) from asynchronous evaluation.
