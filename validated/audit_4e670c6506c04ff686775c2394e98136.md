### Title
Unrecoverable Node Crash / Chain Halt via Malformed `system_vote_count` for `op_list` - (File: `main_chain.js`)

### Summary
The v4 OP-list voting mechanism in `main_chain.js`'s `countVotes()` function asserts that exactly `constants.COUNT_WITNESSES` (12) distinct OP addresses receive votes when a `system_vote_count` message for `op_list` becomes stable, throwing an uncaught `Error` if this invariant is violated. This mirrors the Zetachain finding's root cause class: a state-transition path whose failure mode is a hard halt requiring out-of-band manual recovery, reachable through an ordinary, unprivileged action (posting a unit), rather than a validated, recoverable error path.

### Finding Description
Any unprivileged unit author can compose and broadcast a `system_vote_count` message with `payload: 'op_list'` [1](#0-0) . Validation of this message only checks that the subject string is one of the known subjects; it does not verify that a sufficient/valid quorum of `op_list` votes currently exists [1](#0-0) .

Once such a unit stabilizes, `markMcIndexStable()` calls `countVotes(conn, mci, 'op_list')` [2](#0-1) . Inside `countVotes`, the OP addresses are tallied from `op_votes`/`voter_balances`, truncated to `LIMIT constants.COUNT_WITNESSES`, and then the code enforces:
```
if (ops.length !== constants.COUNT_WITNESSES)
    throw Error(`wrong number of voted OPs: ` + ops.length);
``` [3](#0-2) 

This throw is unhandled by any surrounding `try/catch` in the call chain (`markMcIndexStable` → `stabilizeMci`/`writer.saveJoint`), so it will propagate as an uncaught exception/rejected promise inside the deterministic MC-stabilization logic that every full node executes identically once the triggering unit becomes stable.

Because MC stabilization is deterministic and mandatory for all full nodes to keep processing new units (it is invoked from `writer.js`'s `saveJoint` pipeline right after balls/units are written) [4](#0-3) , a single instance of an insufficient/split `op_list` vote count (which can arise from something as mundane as one voter's balance moving, ties splitting the top-12, or fewer than 12 distinct OPs ever receiving qualifying votes at the time the counter unit stabilizes) will cause **every node in the network** to throw the same uncaught error at the same MCI, simultaneously stalling further stabilization network-wide. Unlike the emergency-path `applyEmergencyOpListChange`, which is gated by a 3-day timeout (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT`) and a minimum vote age (`EMERGENCY_COUNT_MIN_VOTE_AGE`) [5](#0-4) [6](#0-5) , the ordinary manually-triggered `system_vote_count` path has no such safety valve — anyone can trigger the vote count at will by posting the message, and the resulting condition throws instead of failing gracefully (e.g. by simply skipping the count or emitting a validation-time error before stabilization).

This is structurally analogous to the Zetachain "Observer Can Temporarily Halt Chain" bug: a single, ordinary, low-privilege event (slashing one observer / posting one `system_vote_count`) flips the whole network into a state that cannot make further progress without manual intervention, and there is no automated graceful degradation.

### Impact Explanation
If triggered, every full node crashes or halts on `countVotes()` while processing the same stabilizing unit, since the code path is deterministic and mandatory. Because unit processing for that MCI can never complete cleanly, no further units can become stable, and the network is left unable to confirm new units — a hard denial-of-service against the entire DAG, not just a single node. Recovery would require manual patching/restart or a hotfix release across the whole node fleet, matching the "large amount of downtime requiring manual multi-step recovery" impact class described in the report.

### Likelihood Explanation
Likelihood is moderate to high: `system_vote_count` for `op_list` is a permissionless action available to any unit author with an eligible address, and the "exactly 12 distinct OPs voted" invariant can be violated simply by natural vote churn (ties at the 12th position, balance movement causing exactly 12 candidates to not resolve deterministically, or too few distinct addresses having current votes) — none of which require deliberate exploitation, only a poorly timed vote-count trigger. An attacker could deliberately engineer this by manipulating vote timing/tie conditions to intentionally trigger the crash at will.

### Recommendation
Replace the `throw Error(...)` in `countVotes()`'s `op_list` branch with a graceful failure path (e.g., skip the vote count for this MCI, or record the vote count attempt as a no-op) instead of throwing, so that a malformed/insufficient vote-count trigger cannot crash the stabilization pipeline. Additionally, validate at message-submission time (in `validateInlinePayload` for `system_vote_count`) whether the required quorum currently exists, and reject the unit at the mempool/validation level rather than allowing it to be included and later crash deterministic stabilization logic for all nodes.

### Proof of Concept
1. Arrange (or wait for) the `op_votes`/`voter_balances` state such that fewer or more than exactly 12 distinct OP addresses currently qualify under the `GROUP BY op_address ORDER BY total_balance DESC ... LIMIT constants.COUNT_WITNESSES` query in `countVotes` [7](#0-6)  — e.g., a tie at the 12th/13th position, or a period where only 11 distinct OPs have active votes.
2. Any address posts a unit containing `{app: 'system_vote_count', payload: 'op_list'}` [1](#0-0) .
3. When this unit stabilizes, `markMcIndexStable` invokes `countVotes(conn, mci, 'op_list')` [2](#0-1) , which computes `ops.length !== 12` and throws `Error("wrong number of voted OPs: " + ops.length)` [8](#0-7) .
4. Because this occurs inside the deterministic, mandatory `saveJoint` → `markMcIndexStable` pipeline run by every full node [4](#0-3) , all nodes throw identically at the same MCI, and no further units can be confirmed until a manual fix is deployed.
