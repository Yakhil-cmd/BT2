### Title
Type confusion in `sig` authentifier evaluation via missing string-type check on `assocAuthentifiers[path]` - (File: definition.js)

### Summary
`definition.js`'s `evaluate()` function, in the `case 'sig'` branch, reads `assocAuthentifiers[path]` and only checks truthiness (`if (!signature) return cb2(false)`) before passing it directly to `ecdsaSig.verify()`, unlike the sibling `case 'hash'` branch a few lines below which explicitly checks `typeof assocAuthentifiers[path] !== 'string'`. This mirrors the OpenSSL `PKCS7_digest_from_attributes()` pattern: a value is consumed according to an assumed type without validating that type first.

### Finding Description
In `definition.js`, the address/asset spending-condition evaluator has: [1](#0-0) 

Compare this to the `hash` op right below it, which explicitly requires a string: [2](#0-1) 

The `sig` branch is missing the analogous `typeof signature !== 'string'` check. `assocAuthentifiers` is the `authentifiers` map supplied by whoever presents the definition and authentifiers to be evaluated. In the normal DAG-unit path, `validateAuthor()` in `validation.js` pre-validates that every entry of `objAuthor.authentifiers` is a nonempty string: [3](#0-2) 
and `signed_message.js`'s `validateSignedMessage()` performs an equivalent check for signed packages/AA triggers before calling `Definition.validateAuthentifiers`: [4](#0-3) 

However, the `sig` evaluator itself has no such guarantee independent of its callers — it is a shared, recursively-invoked function (`'or'`, `'and'`, `'r of set'`, `'weighted and'` all recurse into `evaluate()`), and the only enforced invariant at the point of use is `!signature` (falsy check), not `typeof signature === 'string'`. If `signature` is not a string, execution falls into `signature[0] === "-"` (which is safe on any indexable value) and then into `ecdsaSig.verify(objValidationState.unit_hash_to_sign, signature, args.pubkey)`, defined in `signature.js`: [5](#0-4) 
`Buffer.from(b64_sig, "base64")` behaves very differently depending on the *type* of `b64_sig`: if it is a number, `Buffer.from(N, 'base64')` allocates an all-zero buffer of length N (up to Node's buffer size limits, potentially causing large-allocation Denial-of-Service); if it is an array, it's read as raw byte values (encoding argument ignored); if it is an object, `Buffer.from` throws a `TypeError`, which is caught by the existing `try/catch` in `verify()` and treated as `false` (safe). So the immediately-reachable crash risk here is limited: numeric/array signature values do not throw, and object values are already caught. The `Buffer.from` API happens to defensively handle most non-string inputs, which limits (but does not fully eliminate) exploitability of this missing type check compared to the classic ASN1_TYPE union dereference in OpenSSL.

### Impact Explanation
Best case for an attacker: supplying a large integer as `signature` value in an authentifiers map for a nested `sig` clause could force a large zero-filled `Buffer.from(N, 'base64')` allocation inside signature verification, which is invoked while validating units, AA triggers, and signed packages/private-payment authorizations. This is a potential resource-exhaustion / DoS vector rather than a null/invalid-pointer crash, since Node's `Buffer.from` guards against the classic type-confusion crash that plagues the C-based ASN1_TYPE union access in OpenSSL.

### Likelihood Explanation
Low-to-moderate. All primary attack surfaces (`validateAuthor` for units, `validateSignedMessage` for signed packages/AA triggers) already enforce `authentifiers[path]` is a nonempty string before `Definition.validateAuthentifiers` is invoked, closing off the most direct route. Reaching the unguarded `sig` case with a non-string value would require a caller of `Definition.validateAuthentifiers` that does not pre-validate `assocAuthentifiers` values as strings (e.g., a caller feeding `assocAuthentifiers` from device-message pairing flows or partially-parsed private-payment element data, if any such path exists uses raw JSON without this pre-check). No such alternate caller lacking the string check was found within the explored code; both discovered call sites (`validation.js`'s `validateAuthor` and `signed_message.js`'s `validateSignedMessage`) enforce the invariant already.

### Recommendation
For defense-in-depth and consistency with the `hash` branch, add an explicit type check in the `sig` case of `definition.js`:
```js
var signature = assocAuthentifiers[path];
if (!signature || typeof signature !== 'string')
    return cb2(false);
```
This removes reliance on every current and future caller of `Definition.validateAuthentifiers`/`Definition.validateDefinition` to pre-validate `assocAuthentifiers` values, eliminating the type-confusion risk at its root, analogous to how the OpenSSL fix validates the ASN1_TYPE tag before accessing the union member.

### Proof of Concept
Not conclusively demonstrable as a crash within the explored codebase: both discovered entry points (`validateAuthor` in `validation.js:1157-1162` and `validateSignedMessage` in `signed_message.js:173-180`) already enforce that authentifier values are nonempty strings before reaching `definition.js`'s `sig` evaluator, and `signature.js`'s `verify()` wraps `Buffer.from` in a try/catch that absorbs `TypeError` on object inputs. A concrete unauthorized-spending or DoS PoC would require identifying a caller path that invokes `Definition.validateAuthentifiers` with attacker-controlled, non-string `assocAuthentifiers` values — such a path was not found in the reviewed code, so this should be treated as a hardening recommendation rather than a confirmed exploitable vulnerability.
