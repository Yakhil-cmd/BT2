### Title
API `Api::CCMenuController#stack` bypasses per-token stack scoping, letting a stack-scoped `ApiClient` read any other stack's build/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`) can only resolve a `Stack` that matches its own `stack_id`, via `stacks.from_param!(params[:stack_id])`. `Api::CCMenuController` overrides the `stack` helper with `Stack.from_param!(params[:stack_id])`, which looks up any stack by the URL-supplied identifier without checking `current_api_client.stack_id`. Because authentication for this controller also accepts the token as an unauthenticated query-string parameter (`params[:token]`), the binding between "the stack a token authorizes" and "the stack the request actually touches" is broken specifically for this endpoint.

### Finding Description
`Api::BaseController` defines the authorization-scoping contract used by every other stack-nested API endpoint: [1](#0-0) 

`current_api_client.stack_id?` restricts the resolvable `Stack` set to the one stack the client was created for; `from_param!` then raises `RecordNotFound` for any other stack id, which is exactly the check exercised in `test "an api client scoped to a stack will only see that one stack"`.

`Api::CCMenuController`, however, redefines `stack` independently of the base implementation: [2](#0-1) 

`Stack.from_param!(params[:stack_id])` resolves against the entire `Stack` table, with no reference to `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the token has the `read:stack` permission string in its `permissions` array — it does not check which stack the permission was scoped to (`ApiClient#check_permissions!` only inspects `permissions`, never `stack_id`): [3](#0-2) 

So the equality that should hold — "stack authorized by the token" == "stack touched by the request" — is broken for this one controller: a token minted with `stack_id: <A>` and `permissions: ['read:stack']` authorizes reads only on stack A, but `CCMenuController#show` will happily serve build/deploy status for any stack B supplied in the `stack_id` route segment.

This is reachable by an unprivileged holder of any valid `read:stack`-scoped token, including tokens that are explicitly meant to be narrowly scoped (e.g. the `here_come_the_walrus`-style scoped clients exercised in `test/controllers/api/stacks_controller_test.rb`, or tokens generated by `CCMenuUrlController`, which itself demonstrates the intended mechanism of authenticating via the `token` query parameter): [4](#0-3) 

### Impact Explanation
This matches the "stack a token authorizes vs. stack it touches" binding class. The concrete impact is unauthenticated-scope-widened read of stack state: a token that was only supposed to authorize CI/build status queries for one specific stack can be used to read the last-build status, label, activity and web URL for any other stack in the Shipit instance, including ones the token holder has no legitimate access to. This is an authorization scope-escape / unauthorized read of stack state — matching the "High" impact bucket ("escalation ... or unauthenticated read of stack state ... or deploy output").

### Likelihood Explanation
Medium. It requires possession of *any* valid `read:stack` API token scoped to a single stack (not admin-level, not the target stack's own token) — such tokens are routinely distributed to third-party integrations/CI dashboards for a single stack via the CCMenu feature itself (`ccmenu_url_controller.rb`) or via the general `ApiClient` management UI (`app/controllers/shipit/api_clients_controller.rb`), and the attack requires only changing the `stack_id` URL segment on a request that is otherwise identical to the legitimate flow, no additional secrets or privileges needed.

### Recommendation
Make `Api::CCMenuController#stack` use the same scoped resolution as `Api::BaseController` (`stacks.from_param!(params[:stack_id])`, i.e. remove the local override or delegate to the inherited `stacks` helper) so the `current_api_client.stack_id` scoping is enforced consistently across all controllers, including this one.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id: <stack_A.id>` with `permissions: ['read:stack']` (this is the normal shape of a CCMenu/dashboard token, see `ccmenu_url_controller.rb`).
2. As an attacker who only knows this token (but not stack B's data), issue:
   `GET /api/stacks/<other-org>/<other-repo>/<other-env>/ccmenu?token=<the_scoped_token>`
3. Compare with the equivalent request on, e.g., `GET /api/stacks/<stack_A_owner>/<stack_A_repo>/<stack_A_env>?...` via `Api::StacksController#show`, which correctly returns 404/`RecordNotFound` for stack B because it relies on the inherited, scoped `stack` method — while `CCMenuController#show` returns HTTP 200 with stack B's build XML, because it bypasses the scoping. (Existing coverage of the scoping contract itself is at `test/controllers/api/stacks_controller_test.rb` "an api client scoped to a stack will only see that one stack"; note that `test/controllers/api/ccmenu_controller_test.rb` never exercises a stack-scoped client against a foreign `stack_id`, so this gap is untested.)

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
