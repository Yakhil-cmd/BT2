### Title
Webhook organization used for signature verification is decoupled from the repository actually written to, enabling cross-organization forgery of pushes and commit statuses - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The external report's core pattern — a permission/authorization check performed against one identity while a destructive action is executed against a different, unchecked target — has a direct analog in Shipit's webhook pipeline. `WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the request against using `repository.owner.login` (or `organization.login`) from the JSON body, while every `Handler` subclass resolves the actual `Repository`/`Stack` it acts on from a completely different field of the same body: `repository.full_name`. Nothing ties these two fields together, so in a multi-organization Shipit deployment, an attacker who legitimately controls one onboarded organization's webhook secret can forge a payload whose `owner.login`/`organization.login` names their own org (so the signature check passes with a secret they know) while `repository.full_name` names a repository belonging to a different organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the org used to pick the verification secret like this: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config/secret keyed by that string, confirming multi-tenant support where distinct organizations have distinct secrets: [3](#0-2) 

Every webhook `Handler`, however, resolves the record it mutates using a *different* payload field, `repository.full_name`, with no cross-check against the organization used above: [4](#0-3) 

`PushHandler`, for example, uses that lookup to enqueue a resync with an attacker-supplied `expected_head_sha` for any stack matching the forged `full_name`/branch: [5](#0-4) 

This is the same class of bug as the reported `kill()` issue: a check is bound to one identifier (the organization whose secret validates the HMAC) while the effect is bound to a different, attacker-controlled identifier (the repository named inside the same signed body). Because the HMAC only proves "this body was signed by *some* org's secret that the attacker knows," and the code never asserts that the *signing* org equals the *acted-upon* repository's org, the binding `organization_that_signed == repository_that_is_written` is broken.

### Impact Explanation
Before the attacker's request: only GitHub, holding the org-specific `webhook_secret`, can produce valid webhook traffic that causes `Handler` subclasses to act on that org's repositories/stacks. After the forged request: any org onboarded into the same multi-tenant Shipit instance (attacker's own org, whose secret they legitimately possess) can produce webhook traffic that is verified successfully and then dispatched against a victim organization's `Repository`/`Stack`, because the dispatch logic keys off `repository.full_name`, a field never checked against the verifying organization. This is a cross-repository/cross-organization write with no repository access, no Shipit session, and no privileged account required from the attacker on the victim side — matching the Critical "cross-repository writes" criterion. It also touches statuses (via the same `Handler#repository_name` pattern used elsewhere in the handlers directory) which factor into deploy gating (`deployable_status`), raising the possibility of influencing deploy readiness signals on a repository the attacker does not own.

### Likelihood Explanation
Exploitability depends entirely on Shipit running in a multi-organization configuration where more than one organization is registered under `secrets.github` (i.e., `github_default_organization` is non-nil, per `github_app_config`). In that configuration, any onboarded organization is, by design, a mutually distrusting tenant from the others' perspective, yet this code path lets one forge effects on another's repositories using only its own credentials — no social engineering, no token theft, no privileged Shipit account needed. Likelihood is high specifically for multi-tenant deployments; it is not exploitable in single-organization deployments since there is only one secret and thus only one valid "identity" to forge from.

### Recommendation
After verifying the HMAC signature, assert that the organization determined for signature verification (`repository.owner.login` / `organization.login`) actually matches the organization portion of `repository.full_name` used by `Handler#repository_name` before dispatching to any handler. Reject the webhook (422) on mismatch. This restores the binding between "who is authenticated to speak for an org" and "which repository/stack is mutated."

### Proof of Concept
1. Shipit is configured with at least two organizations in `secrets.github`: `victim-org` (secret unknown to attacker) and `attacker-org` (secret known to the attacker, e.g., because the attacker legitimately administers that org's GitHub App integration).
2. Attacker crafts a `push` webhook JSON body:
   - `repository.owner.login` = `"attacker-org"` (or `organization.login` = `"attacker-org"`)
   - `repository.full_name` = `"victim-org/victim-repo"`
   - `ref` = `"refs/heads/master"`, `after` = attacker-chosen sha
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` over the raw body using `attacker-org`'s known `webhook_secret`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, calls `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because the attacker used the correct secret for that org. [6](#0-5) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, unrelated to the `attacker-org` identity that passed verification, and enqueues `GithubSyncJob` against `victim-org/victim-repo`'s stacks with the attacker-supplied `expected_head_sha`.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
