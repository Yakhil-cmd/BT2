Based on my analysis, I've confirmed the mechanism in `aa_composer.js` where an atomic AA response bounces entirely if any single payment message fails during composition (e.g., due to a private/unusable asset), and the AA trigger validator only checks that an asset *exists*, not whether it is transferable/private. This is a valid analog to the reported bug class.

### Title
An attacker can permanently DoS an AA's shared/atomic payout by causing it to record or attempt to send a private asset, bouncing the entire multi-recipient response - (File: `aa_composer.js`)

### Summary
`DepositManagerV1.fundBountyToken` in the original report accepts any non-whitelisted token once a numeric limit isn't reached, letting an attacker seed a bounty with a malicious, non-transferable token; later, an atomic multi-token claim payout reverts entirely because that one token can't be moved. The analogous root cause exists in ocore's AA composer: `validateAATriggerObject` only checks that an asset referenced in `trigger.outputs` exists in the `assets` table — it never checks `is_private`, `issued_by_definer_only`, `spender_attested`/`attestors`, or transferability [1](#0-0) . If AA logic later attempts to compose a `payment` message using that same (attacker-chosen) asset as part of a single atomic response that also pays out to other unrelated recipients, `sendUnit`'s per-message `async.eachSeries` loop fails the *entire* unit composition on the first bad asset via `cb("sending private asset from AA")`, which propagates to `bounce(err)` for the whole trigger response [2](#0-1) .

### Finding Description
When an AA composes a response with multiple `payment` messages (e.g., paying several recipients or several asset types in one atomic unit, mirroring OpenQ's tiered-percentage/atomic bounty payout), `sendUnit` iterates all messages with `async.eachSeries`. For each asset payment it loads the asset via `storage.loadAssetWithListOfAttestedAuthors` and, if `objAsset.is_private`, immediately errors with `"sending private asset from AA"` [3](#0-2) . Any error from this loop is passed straight to `bounce(err)`, which discards all state changes and all other payment messages in that same response — not just the one referencing the bad asset [4](#0-3) .

Crucially, the up-front trigger validation (`validateAATriggerObject`) that runs when an unprivileged sender posts a unit triggering an AA does not reject private, non-transferable, or otherwise unusable assets — it only confirms the asset id exists in the `assets` table [5](#0-4) . Since anyone can define a new private asset via an `asset` app message (`is_private: true`), an attacker can freely mint such an asset and reference/route it into an AA's state or trigger outputs. If the AA's oscript later re-uses that asset id (recorded in `var[...]` state, e.g. as a "team asset" or "payout asset" analogous to the sample patterns in `test/samples/*.oscript`) to construct a shared, multi-party payment message, every future attempt to execute that payout will hit the same `is_private` check and bounce the *whole* response, including payments legitimately owed to other, unrelated parties bundled in the same unit.

Because the underlying asset definition is immutable once posted (privacy cannot be revoked), this is a permanent, unrecoverable block: state changes are rolled back on every bounce (`revert`/`bounce` restore `stateVars`/`assocBalances` and clear the pending unit) [6](#0-5) , so retries always reach the same failure.

### Impact Explanation
This matches the "High" impact class from the source report: an unprivileged actor can force a recurring or shared claim/payout logic in an AA to be permanently unable to complete, freezing funds legitimately owed to other, uninvolved recipients whose payment happens to be batched in the same atomic response as the poisoned asset. Unlike a simple failed trigger (which only affects the attacker's own funds), this can block payouts to third parties whenever an AA's design pools multiple beneficiaries' payments into one atomic unit conditioned on shared state that references a user/attacker-influenced asset id.

### Likelihood Explanation
Likelihood is Medium-to-High for AAs of this design pattern (multi-recipient atomic payout keyed off a stored/selected asset id), since: (1) creating a private asset is a single, cheap, unprivileged `asset` message any address can post; (2) the AA/trigger-validation layer performs no privacy/transferability check on assets referenced by triggers [7](#0-6) ; (3) the failure is deterministic and irreversible once the bad asset id is embedded in shared AA state.

### Recommendation
- In `validateAATriggerObject`, when checking that referenced assets exist, also load each asset's properties and reject (or flag) assets that are `is_private` or otherwise unsuitable for AA-mediated transfer, similar to the explicit check already performed inside `sendUnit` at message-composition time [3](#0-2) .
- In `sendUnit`, avoid letting a single bad payment message abort the entire multi-message unit; instead, drop/skip the offending message (as is already done for `fixed_denominations` assets, which are filtered out rather than causing a full bounce) [8](#0-7)  and [9](#0-8) , or provide AA authors with an oscript-level way to validate asset transferability/privacy before committing it to shared state.

### Proof of Concept
1. Attacker posts an `asset` definition unit with `is_private: true` (and, per validation rules, `auto_destroy` + non-transferrable, since private+divisible assets must be auto-destroy/non-transferrable) — a normal, unprivileged action.
2. Attacker (or any user) triggers a shared AA whose logic stores a caller-influenced or externally-supplied asset id into persistent state to be used later for a pooled/batched payout to multiple beneficiaries (pattern seen in `test/samples/51_attack_game.oscript`'s `team_asset`/`var['team_' || ...]` style state, and `futures_contract.oscript`'s asset-based payout cases).
3. `validateAATriggerObject` accepts the trigger because it only checks the asset exists, not its privacy/transferability [1](#0-0) .
4. When the AA later executes the batched payout case that emits a `payment` message for that asset alongside payment messages for other legitimate recipients, `sendUnit`'s `async.eachSeries` hits `objAsset.is_private` and returns `cb("sending private asset from AA")` [3](#0-2) , which triggers `bounce(err)` for the entire response [4](#0-3) , reverting all outputs in that unit, including those meant for uninvolved parties.
5. Because the asset's `is_private` flag can never be changed, every subsequent attempt to trigger the same payout logic bounces identically, permanently freezing the pooled funds/claim for all affected beneficiaries.
