### Title
Cross-organization commit-status forgery via unbound webhook-signature/commit-lookup scope - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret is used to validate an incoming webhook's HMAC based on an *unauthenticated* field of the very payload it is about to verify — `repository.owner.login` (or `organization.login`) — while the handler that actually acts on the payload (`StatusHandler#process`) looks up the target `Commit` globally by `sha` with no scoping to the organization/repository that was used to validate the signature. This breaks the intended binding: `organization that authenticated == repository/commit that gets written`. [1](#0-0) [2](#0-1) 

### Finding Description
`verify_signature` resolves `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the JSON body (`params.dig('repository','owner','login')` / `params.dig('organization','login')`), then verifies the raw body's `X-Hub-Signature` against that organization's `webhook_secret`: [3](#0-2) [4](#0-3) 

Shipit is explicitly designed to host multiple independent GitHub organizations, each with its own App and `webhook_secret`, as shown in the secrets template: [5](#0-4) 

Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the same raw JSON to a handler. `StatusHandler`, however, does not re-check that the commit it updates belongs to the organization/repository whose secret validated the request — it matches purely on `sha` across the whole database: [2](#0-1) [6](#0-5) 

An operator of any single organization configured in Shipit (an "unprivileged" actor with respect to every *other* org's stacks) knows their own org's `webhook_secret` (they created/manage that GitHub App). Since the signature-selection field (`repository.owner.login`) and the state-mutating field (`sha`, and `Commit#stack` resolved from it) are independent, attacker-controlled fields inside the same signed body, the attacker can:

1. Build a payload with `repository.owner.login` = "attacker-org" (their own configured org) so `Shipit.github(organization: 'attacker-org')` is selected.
2. Sign the whole raw body with `attacker-org`'s known `webhook_secret` — this passes `verify_webhook_signature` legitimately since the attacker controls both the secret and the body.
3. Set `sha` in that body to the SHA of an actual undeployed commit belonging to an entirely different organization/stack hosted on the same Shipit instance.
4. `StatusHandler#process` finds `Commit.where(sha: params.sha)` — with no organization/repository filter — and calls `create_status_from_github!`, injecting a fabricated `success` status for that foreign commit.

### Impact Explanation
`Commit#deployable?` and continuous-delivery scheduling depend directly on the injected status: [7](#0-6) [8](#0-7) 

By forging a passing CI status (or bypassing `ci.require`/blocking checks) on a commit belonging to a stack the attacker has no legitimate relationship to, the attacker can make that commit `deployable?` — enabling continuous delivery to auto-ship it, or letting a human reviewer on that stack proceed to deploy code that never actually passed the required CI checks defined by that repository's `shipit.yml`. This is an unauthorized-deploy-enabling primitive achieved purely by knowing a *different, unrelated* organization's webhook secret, satisfying the "authorized deploy/ship" high-impact bucket.

### Likelihood Explanation
Requires only: (a) the attacker legitimately controls one GitHub App/organization already configured in the shared Shipit instance (a common multi-tenant setup, as documented), and (b) knowledge of a target commit SHA on another stack, which is public GitHub information. No Shipit session, API token, or the target org's own webhook secret is needed — the only credential used is the attacker's own, valid for their own org. This is a realistic misconfiguration risk in any multi-org Shipit deployment.

### Recommendation
Bind the two lookups: after selecting the organization via `repository_owner` for signature verification, the handler layer must verify that the resolved `Commit`'s `stack.repository` (or `github_repo_name`) actually belongs to that same verified organization before mutating status/check-run state. Concretely, pass the verified `repository_owner` (or the full `repository.full_name` used for verification) into `Handler`/`StatusHandler` and scope `Commit.where(sha: ...)` to commits whose `stack.repository.owner` matches it, rejecting/ignoring any mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` (attacker-controlled webhook secret `secretA`) and `orgB` (victim stack, unrelated secret).
2. Craft JSON body:
```json
{
  "sha": "<sha of an undeployed commit belonging to orgB's stack>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` using the attacker's own known `secretA`.
4. POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves org via `repository.owner.login = "orgA"`, verifies against `secretA` — passes.
6. `StatusHandler#process` finds orgB's commit by `sha` (global lookup) and creates a `success` status on it, potentially flipping `deployable?` to `true` for a commit the attacker has no authorization over.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
