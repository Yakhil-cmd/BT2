### Title
Attackers can drain an Aquarius LP market to poison liquidation and collateral withdrawals - ([File: contracts/controller/src/risk/totals.rs](contracts/controller/src/risk/totals.rs))

### Summary

A borrower can add a small Aquarius LP position to an account and then reduce the backing Aquarius pool below its configured `min_pool_value_wad`. The LP oracle rejects the position, and because liquidation and cleanup price every collateral and debt leg in the account, the single unavailable LP leg causes the entire operation to revert. This also blocks withdrawals that must evaluate post-withdrawal solvency.

### Finding Description

`liquidate` is permissionless and calls `build_liquidation_plan` before repayment or seizure. [1](#0-0)  Risk calculation loads every hub asset in both position maps and obtains prices for each collateral position. [2](#0-1)  `Context::load_markets` fetches all unique token prices before market indexes. [3](#0-2) 

The Aquarius provider computes total pool value and returns `InsufficientAquariusLiquidity` whenever it is below `lp.min_pool_value_wad`. [4](#0-3)  Consequently, a listed LP token becomes unpriceable after its external pool is drained, rather than merely receiving a low price.

Supply does not require a current valuation before transferring and crediting the position; it only requires the listed spoke asset and measured pool receipt. [5](#0-4)  An account owner can therefore plant a dust LP leg while the LP oracle is healthy, then use retained LP shares to withdraw liquidity from the underlying Aquarius pool.

`clean_bad_debt` uses the same account-wide risk totals before socializing debt, so the poisoned leg also blocks permissionless cleanup. [6](#0-5)  Normal withdrawals settle the requested legs but then run `enforce_post_pool_solvency`, which prices the remaining poisoned position. [7](#0-6) 

### Impact Explanation

An underwater account can make every `liquidate` call fail, regardless of the debt leg offered or the `SeizeMode` selected. `Credit` mode does not bypass the issue because valuation still requires all collateral prices. If the debt later becomes bad debt, `clean_bad_debt` fails for the same reason, leaving the insolvency active and delaying loss socialization.

The borrower’s collateral can also be temporarily frozen because withdrawals with outstanding debt fail during the post-pool solvency calculation. The freeze lasts until liquidity is restored above `min_pool_value_wad` or governance changes the oracle/listing configuration.

This is a Medium-severity availability issue: it can temporarily prevent liquidation and cleanup and allow debt to accrue into bad debt, but it requires influence over the referenced Aquarius pool’s liquidity and does not directly mint shares or steal pool funds.

### Likelihood Explanation

The entrypoints are permissionless: the attacker calls `supply` with a listed LP `HubAssetKey`, borrows through `borrow`, and independently removes liquidity from the referenced Aquarius pool using LP tokens the attacker owns. Any liquidator calling `liquidate(liquidator, account_id, debt_payments, seize_mode)` then reaches the unavailable price before state changes.

The attack requires an Aquarius LP listing, an account with debt, and enough external LP share ownership or market influence to push pool value below its configured floor. For thinly backed LP collateral this can be economically feasible; for deep pools the cost may exceed the benefit. No privileged role, malformed contract input, oracle dishonesty, or leaked key is required.

### Recommendation

Do not let an unavailable dust collateral leg disable an entire liquidation. Prefer one of:

- Value missing collateral at zero for liquidation eligibility, while still preventing that leg from being seized or counted toward liquidation proceeds.
- Plan liquidation only over collateral legs with valid prices and explicitly exclude unpriceable legs from the pro-rata allocation.
- Add a fallback path that permits `SeizeMode::Credit` only when the position count and unchanged frozen leg can be handled safely.
- Permit permissionless cleanup to bypass collateral valuation for legs that are provably zero-valued or unavailable, while retaining strict debt valuation.

Any fix must ensure the unpriceable collateral cannot be counted as backing and cannot be awarded to a liquidator.

### Proof of Concept

The repository already contains a regression demonstrating the same failure shape: `supply` accepts a position while its feed is stale, after which `liquidate`, `clean_bad_debt`, and `withdraw` all fail with `PRICE_FEED_STALE`. [8](#0-7)  Once the feed is restored, the same liquidation succeeds. [9](#0-8) 

For the Aquarius variant:

1. Configure/list an `AquariusLp` collateral whose pool is just above `min_pool_value_wad`.
2. From borrower `A`, call:
   - `supply(A, 0, spoke_id, [(lp_hub_asset, dust_amount)])`
   - `supply(A, account_id, spoke_id, [(other_collateral, enough_collateral)])`
   - `borrow(A, account_id, [(debt_asset, debt_amount)], None)`
3. Using retained LP tokens outside the lending account, withdraw underlying liquidity from the referenced Aquarius pool until its computed value is below `min_pool_value_wad`.
4. Any liquidator calls `liquidate(L, account_id, [(debt_asset, amount)], SeizeMode::Transfer)` or `SeizeMode::Credit(0)`. The call fails before token movement when `aquarius::read` returns `InsufficientAquariusLiquidity`.
5. A subsequent `clean_bad_debt(C, account_id)` fails at the account-wide risk calculation for the same unavailable price.
