### Title
Webhook signature key-selection uses an unverified payload field, letting an org authenticated by its own secret forge events for repositories owned by other organizations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using a value pulled straight out of the still-unverified JSON body, while the handlers that subsequently act on the delivery key off a different field of that same body. In a multi-organization Shipit deployment this breaks the intended binding "organization whose secret authenticated the request == organization/repository the request is allowed to act on."

### Finding Description
`verify_signature` computes the signing organization from the raw, not-yet-verified payload: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository','owner','login')`, a value fully controlled by whoever crafts the HTTP body. It is used only to pick which `GitHubApp`/`webhook_secret` (via `Shipit.github(organization: repository_owner)` and `github_app_config`) the HMAC signature is checked against: [3](#0-2) 

Once the signature validates against *that* organization's secret, the entire body is handed unmodified to the handlers, which independently derive the target repository from `payload.dig('repository','full_name')`: [4](#0-3) 

Nothing cross-checks that `repository.full_name`'s owner matches `repository.owner.login`. Because the HMAC signature covers the raw body verbatim, whoever *creates* the signature (i.e., anyone who legitimately knows one organization's `webhook_secret`, such as an admin of that org's own GitHub App installation) can freely choose any content for `repository.full_name` while keeping `repository.owner.login` equal to their own org, so the signature still validates. The handler then processes the payload as if it originated from the repository/organization named in `full_name`, which may belong to a completely different, unrelated tenant of the same Shipit instance.

This is the same defect class as the reported `Vault::updateVaultAndCreditDelegationWeight` bug: a value used to authorize/scope an operation (weight per market / signing organization) is not tied to the value that the operation actually acts on (total assets / target repository), breaking an implicit one-to-one binding the system relies on for safety. Here the broken equality is:
`organization whose secret validated the signature == organization owning the repository the handlers act on`.

### Impact Explanation
In any Shipit deployment configured with `secrets.github` keyed by multiple organizations (the documented multi-org config path via `github_app_config`/`github_organizations`), a party that legitimately controls one tenant's GitHub App webhook secret can forge webhook deliveries that Shipit will treat as authentic for a *different* tenant's repositories/stacks. Depending on which event type is forged this can:
- Trigger `GithubSyncJob` and stack synchronization for stacks belonging to another organization (`PushHandler`) [5](#0-4) 
- Archive/unarchive or trigger provisioning/deprovisioning of review stacks belonging to another organization's repository via the `PullRequest` handlers (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), all of which resolve the target repository purely from `repository.full_name` [6](#0-5) 
- Create commit statuses or mutate `PullRequest`/label state for that foreign stack.

This crosses a tenant/organization boundary without possessing the victim organization's credentials, secrets, or Shipit session - only knowledge of *any one* configured organization's webhook secret is required. That satisfies the "cross-repository writes" / unauthorized-state-mutation bar for High-severity impact under the program's rules, since it lets one tenant force state changes (stack archiving, sync, review-stack provisioning) on a repository outside its authorization scope.

### Likelihood Explanation
Exploitability requires: (1) a Shipit instance configured for multiple organizations sharing one deployment (the documented multi-org config path), and (2) the attacker possessing the webhook secret for at least one of those organizations - which is a normal, expected credential for any tenant onboarded onto the shared instance, not a privileged Shipit account, `ApiClient` token, or `GITHUB_TOKEN`. Given that, forging the payload is a simple HTTP request with a self-computed HMAC; no other engine flaw or race condition is needed. Likelihood is moderate-to-high specifically for multi-tenant deployments of this engine.

### Recommendation
Bind the field used to select the verification secret to the field(s) actually acted upon:
- After signature verification succeeds, re-derive `repository_owner`/`organization` strictly from the verified body and require that `repository.full_name`'s owner segment matches `repository.owner.login` (or `organization.login`) before dispatching to handlers, rejecting mismatches with `422`.
- Alternatively, verify the signature against *all* configured organizations' secrets rather than the one implied by attacker-controlled data, and only proceed if the org actually owning the target repository (looked up from Shipit's own `Repository` records, not from the payload) is the one whose secret matched.
- Add a regression test asserting that a payload signed with org A's secret but naming a repository owned by org B is rejected.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` under `secrets.github` (multi-org schema per `Shipit.github_app_config`).
2. As someone who legitimately possesses `org-a`'s webhook secret, craft a JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeef...",
     "repository": {
       "owner": { "login": "org-a" },
       "full_name": "org-b/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a secret, body)>` and send it with `X-Github-Event: push` to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and validates the signature successfully against `org-a`'s secret.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `Handler#repository_name` reads `payload.dig('repository','full_name')` = `"org-b/victim-repo"`, and `GithubSyncJob` runs for `org-b`'s stacks - despite the request never being authenticated by anything belonging to `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
