### Title
`GetCurrentLogin` returns unsanitized GraphQL `viewer.login` field allowing terminal escape-sequence injection - ([File: pkg/cmd/auth/shared/login_flow.go])

### Summary
`GetCurrentLogin` decodes the GraphQL response's `data.viewer.login` field and returns it verbatim without any validation or sanitization. The value is later written to the terminal via `fmt.Fprintf(opts.IO.ErrOut, "%s Logged in as %s\n", cs.SuccessIcon(), cs.Bold(username))` in `Login`, and is also passed to `authCfg.Login`/`cfg.Login` for storage.

### Finding Description
`GetCurrentLogin` unmarshals the JSON response into `result.Data.Viewer.Login` and returns it directly with no length limit, character filtering, or control-sequence stripping: [1](#0-0) 

That returned `username` is then interpolated into terminal output via `cs.Bold(username)`: [2](#0-1) 

and also into `pkg/cmd/auth/login/login.go`'s token-based login path, again unsanitized before being persisted with `authCfg.Login`: [3](#0-2) 

The codebase does have an established pattern for sanitizing untrusted API content before display (e.g. `internal/text` sanitization helpers used in `pkg/cmd/gist/view/view.go`, `pkg/cmd/pr/diff/diff.go`, `pkg/iostreams/untrusted.go`), but `GetCurrentLogin` does not apply any of these to the `viewer.login` value.

Downstream storage in `internal/config/config.go`'s `AuthConfig.Login` uses the username only as a structured config-tree key (`c.cfg.Set([]string{hostsKey, hostname, usersKey, username, oauthTokenKey}, token)`) and as a keyring "account" parameter (`keyring.Set(keyringServiceName(hostname), username, token)`): [4](#0-3) 

These are not raw filesystem path concatenations — the go-gh config library and OS keyring backends do not interpret `username` as a filesystem path component that could be used for traversal. So the "path-breaking / credential storage path manipulation" half of the question is not substantiated: no reachable code constructs a file path by directly concatenating `username`.

The realistic reachable impact is the terminal output path: an unsanitized attacker-controlled string is printed directly to `opts.IO.ErrOut`.

### Impact Explanation
Because `viewer.login` is written unsanitized to the terminal, a malicious/compromised host that a victim points `gh` at (via `--hostname` or `GH_HOST`) could return a `login` field containing ANSI/VT100 escape sequences. Depending on the victim's terminal emulator, this could manipulate terminal state (e.g., overwrite prior output, manipulate the title bar, or in vulnerable/legacy terminal emulators trigger more exotic behaviors). This maps to a low-severity "terminal escape-sequence / spoofed output" class finding, not credential/token exfiltration or file write, since the storage sinks are non-path-based (config tree keys, keyring accounts).

### Likelihood Explanation
This requires the victim to explicitly authenticate against a self-hosted or otherwise attacker-controlled GitHub Enterprise-style host (precondition explicitly permitted by the rules), and for that host's GraphQL endpoint to return a crafted `viewer.login`. This is a narrow but concrete precondition (not applicable to standard github.com auth flows, since GitHub's real API constrains login format), making exploitation feasible only in the self-hosted/compromised-host scenario.

### Recommendation
Sanitize (or reject) the `viewer.login` value in `GetCurrentLogin` before returning it — e.g. apply the same control-sequence stripping used elsewhere in the codebase (`internal/text` sanitization helpers / `pkg/iostreams/untrusted.go`) and/or validate the login against GitHub's known username character set (alphanumeric and hyphens) before using it for display or storage.

func (c *AuthConfig) Login(hostname, username, token, gitProtocol string, secureStorage bool) (bool, error) {
	// In this section we set up the users config
	var setErr error
	if secureStorage {
		// Try to set the token for this user in the encrypted storage for later switching
		setErr = keyring.Set(keyringServiceName(hostname), username, token)
		if setErr == nil {
			// Clean up the previous oauth_token from the config file, if there were one
			_ = c.cfg.Remove([]string{hostsKey, hostname, usersKey, username, oauthTokenKey})
		}
	}
	insecureStorageUsed := false
	if !secureStorage || setErr != nil {
		// And set the oauth token under the user for later switching
		c.cfg.Set([]string{hostsKey, hostname, usersKey, username, oauthTokenKey}, token)
		insecureStorageUsed = true
	}

	if gitProtocol != "" {
		// Set the host level git protocol
		// Although it might be expected that this is handled by switch, git protocol
		// is currently a host level config and not a user level config, so any change
		// will overwrite the protocol for all users on the host.
		c.cfg.Set([]string{hostsKey, hostname, gitProtocolKey}, gitProtocol)
	}

	// Create the username key with an empty value so it will be
	// written even when there are no keys set under it.
	if _, getErr := c.cfg.Get([]string{hostsKey, hostname, usersKey, username}); getErr != nil {
		c.cfg.Set([]string{hostsKey, hostname, usersKey, username}, "")
	}

	// Then we activate the new user
	return insecureStorageUsed, c.activateUser(hostname, username)
}
