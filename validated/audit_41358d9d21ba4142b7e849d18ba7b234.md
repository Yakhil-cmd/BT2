### Title
Webhook signature verification binds to attacker-controlled organization, not to the repository the event handlers act on - allows forging build/CI status and sync events for stacks belonging to other organizations ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit` supports a multi-tenant configuration where multiple GitHub organizations, each with its own webhook secret, are configured under `secrets.github` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using a field taken from the same untrusted JSON body it is trying to authenticate, and the downstream event handlers then act on a *different* field of that same untrusted body to decide which repository/stack to mutate. Nothing ties the two together, so a party who legitimately controls one onboarded GitHub organization (and therefore genuinely knows that organization's webhook secret) can forge a validly-signed webhook whose `repository` object names a completely unrelated tracked repository/stack belonging to a different organization.

### Finding Description
`verify_signature` computes the signing key from the payload itself: [2](#0-1) 

`repository_owner` is read straight out of the not-yet-verified body: [3](#0-2) 

Once `verify_webhook_signature` passes (which it will, if the requester knows *any* configured organization's `webhook_secret` — a secret they legitimately possess if they administer that organization's Shipit-tracked repos), `create` re-parses the same raw body and dispatches it to handlers unmodified: [4](#0-3) 

The handlers determine the repository/stack to act on from a *different* key of the same attacker-supplied JSON, `repository.full_name`, with no cross-check against `repository.owner.login` (the field used to pick the secret): [5](#0-4) 

Nothing in `verify_signature` or in `Handler#repository_name`/`#stacks` enforces `repository.full_name` starts with `repository.owner.login`. The equality that should hold — *organization whose secret authenticated the request == organization owning the repository the handler mutates* — is never checked.

The `StatusHandler` amplifies this: it does not scope by repository/stack at all, matching purely by commit SHA across the entire installation: [6](#0-5) 

and `PushHandler` uses `stacks` (derived from the attacker-chosen `repository.full_name`) to enqueue a sync against any non-archived stack on that repository/branch: [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate member/owner of one GitHub organization onboarded into a shared, multi-tenant Shipit instance (and thus genuinely knows that organization's `webhook_secret`) can send a payload signed with their own secret but with `repository.full_name` (and `sha`, `state`, etc.) pointing at a stack belonging to a *different, unrelated organization*. This lets them:
- Inject arbitrary `Status` records (`state: success/failure`, `context`, `target_url`) for any commit SHA tracked anywhere in the Shipit install via `StatusHandler`, which is exactly the signal that gates auto-merge/continuous-delivery decisions elsewhere in the app (e.g. `Shipit::ContinuousDeliverySchedule`, commit checks).
- Trigger `GithubSyncJob` for arbitrary tracked stacks/branches via `PushHandler`.
- Force archive/unarchive of review stacks belonging to another repository via the `pull_request` handlers, all of which key off `Handler#repository_name` (`payload.dig('repository', 'full_name')`).

This crosses an organizational trust boundary the engine is supposed to enforce (per-organization webhook secrets exist specifically to isolate tenants) and can influence deploy-gating status data for a repository the attacker does not control — landing in the "unauthorized deploy" / cross-tenant-write impact class.

### Likelihood Explanation
Requires the attacker to be an authorized user of at least one organization already configured in the multi-tenant Shipit instance (a realistic scenario for shared internal deploy tooling used by many teams/orgs), plus knowledge of that repository/stack's existence and target commit SHA in the victim organization (discoverable via public GitHub activity). No Shipit session, API token, or GitHub App credentials of the victim organization are needed — only a raw HTTP POST with a correctly-HMAC'd body using the attacker's own known secret.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after determining `repository_owner` and validating the signature for that organization, re-validate that every repository-scoped field the handlers subsequently act on (`repository.full_name`'s owner segment, `organization.login`, etc.) actually belongs to that same authenticated organization before dispatching to handlers. Additionally, `StatusHandler` should scope `Commit.where(sha:)` lookups to commits/stacks belonging to the authenticated organization/repository rather than matching globally by SHA.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is configured in `secrets.github[:attacker-org][:webhook_secret] = S`, onboarded to the same shared Shipit instance as `victim-org/victim-repo`.
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` using their own known secret `S`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")`, verifies successfully against `S`.
5. `StatusHandler#process` runs `Commit.where(sha: "<victim commit sha>")`, finds the victim's commit (tracked under `victim-org/victim-repo`, unrelated to `attacker-org`), and creates a forged `success` status on it, independent of which organization's secret validated the request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
