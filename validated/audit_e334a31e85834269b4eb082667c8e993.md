### Title
Broken Access Control in Wallet Device-Message Handler Allows Any Correspondent to Solicit Signatures on a Shared/Multisig Address Without Verifying Cosigner Membership - (File: `wallet.js`)

### Summary
In the ToolJet CVE, an API endpoint authorized a tenant-scoped operation using an untrusted request parameter (`:organizationId`) instead of verifying the caller's actual membership, letting any authenticated user act against another tenant's resources. The analogous flaw in `ocore` is in the paired-device message handler `handleMessageFromHub` (`wallet.js`), specifically the `"sign"` case: when the target address is a *local* address (`ifLocal`), the code proceeds to accept and broadcast the signing request without ever verifying that the requesting device (`from_address`) is actually a registered cosigner of that address's wallet/shared address — the only check that would have enforced this is explicitly commented out.

### Finding Description
The `"sign"` message type in `wallet.js` lets one paired device ask another device to co-sign a unit at a given `address`/`signing_path` — used for multisig wallets and multilateral (shared-address) signing. After basic structural validation of the unit and payloads, the code branches on `findAddress(body.address, body.signing_path, ...)`. In the `ifLocal` branch (meaning the target address is one that the *recipient* device locally controls, e.g. a shared/multisig address it co-owns), the intended authorization check — confirming that `from_address` (the sender of the network message) is actually listed as one of the wallet's/shared address's cosigning devices — is present only as a comment: [1](#0-0)

Once accepted, the handler emits the `signing_request` event with the attacker-supplied unsigned unit/private payloads, which the recipient application (wallet UI or automated/headless signer) is expected to act on — either popping a confirmation dialog or, in the `ifRemote` proxy branch (which *does* check `other_device_addresses.includes(from_address)` at line 377), forwarding to a real cosigner. This asymmetry mirrors the ToolJet flaw exactly: the security-relevant identifier that should be authenticated against caller identity/membership (here, "is `from_address` an authorized cosigner of `body.address`'s wallet") is trusted implicitly rather than verified, because the surrounding function only validates that the address/unit are *well-formed*, not that the *sender* is entitled to request the operation.

### Impact Explanation
Any paired correspondent device (an "unprivileged" peer from the recipient's perspective, analogous to another tenant's user in ToolJet) can send a `sign` message referencing a shared/multisig address that the recipient locally co-owns, with `signing_path` set to any authentifier slot, and have the recipient device unconditionally accept the request, run unit validation, and fire a `signing_request` event carrying the attacker-crafted `objUnit` and `assocPrivatePayloads`, even though the sender is not a listed cosigner (`wallet_signing_paths.device_address`) for that wallet. For automated/headless multisig signers (a legitimate real-world ocore deployment pattern), this can result in that signer processing and potentially auto-approving spend requests on behalf of a shared wallet solicited by a device that is not one of the wallet's actual members, leading to unauthorized signing/spending flows from that shared address, analogous to how ToolJet's flaw let a caller manipulate resources belonging to another tenant despite passing basic header/path validation.

### Likelihood Explanation
Exploitation only requires that the attacker be a paired correspondent device of the target (a low bar — pairing is often done broadly, e.g. for exchange/service-facing multisig or arbiter setups) and that the target device locally hosts the private key material for the referenced shared/multisig address (a common configuration for multisig wallet members). No special network position, hub compromise, or protocol violation is needed — only a legitimately paired device sending a normally-shaped `sign` message with an address/`signing_path` it does not actually co-sign for.

### Recommendation
Restore and enforce the commented-out ownership/cosigner check in the `ifLocal` branch of the `"sign"` case in `wallet.js`: before accepting the request and emitting `signing_request`, query `wallet_signing_paths`/`shared_address_signing_paths` to confirm `from_address` is actually a registered device for the wallet or shared address the `body.address`/`body.signing_path` resolves to, mirroring the check already performed in the `ifRemote` branch (`other_device_addresses.includes(from_address)`).

### Proof of Concept
1. Device A pairs with Device B (a normal correspondent pairing, not a cosigner relationship).
2. Device B hosts a shared/multisig address `S` whose actual cosigners are devices `X` and `Y` (not `A`).
3. Device A sends Device B a `"sign"` device message: `{address: S, signing_path: "r.0", unsigned_unit: {...attacker-crafted unit...}}`.
4. In `handleMessageFromHub`, `findAddress(S, "r.0", ...)` resolves `ifLocal` (since B holds signing material for `S`). The disabled check that would verify `A` is a cosigner of `S` never executes.
5. Device B accepts the request (`callbacks.ifOk()`), validates the unit, and emits `signing_request`, which the receiving application (e.g., a headless/automated multisig signer) may act upon, without any confirmation that Device A had any legitimate right to request a signature on `S`'s behalf — an authorization bypass analogous to the ToolJet cross-tenant access flaw.
