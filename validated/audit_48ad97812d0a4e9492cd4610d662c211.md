### Title
Global `Commit.where(sha:)` in status webhook lets any org forge a CI status on another org's commit — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` mutates every `Commit` row matching a webhook-supplied `sha` with no filter on repository or stack, while `WebhooksController#verify_signature` only proves the request was signed by the org named in the payload's `repository.owner.login`. Because the `commits` table indexes `sha` only per `(stack_id, sha)` and not globally unique, and git SHAs are attacker-craftable content hashes, an attacker who controls their own org's webhook secret can post a `status` event whose `sha` also matches a commit belonging to an unrelated victim stack, and Shipit will write an attacker-controlled `Status` (state/description/context/target_url) onto the victim commit.

### Finding Description
The broken binding is: `organization_that_signed_payload` (`attacker`, verified in `Shipit::WebhooksController#verify_signature` via `Shipit.github(organization: repository_owner).verify_webhook_signature`, using `repository_owner` read straight from `params.dig('repository','owner','login')`) should equal `organization_owning_every_Commit_row_mutated_by_StatusHandler#process`. It does not, because `process` only scopes by `sha`: [1](#0-0) 

and `verify_signature` never re-checks that the commits actually returned by that query belong to the same repository/org that was cryptographically verified: [2](#0-1) 

`create_status_from_github!` then writes the attacker-supplied fields directly: [3](#0-2) [4](#0-3) 

Exploit flow: attacker registers a legitimate GitHub App / webhook on their own org `attacker` (a precondition they fully control), pushes/crafts a commit in `attacker/evil` whose SHA byte-for-byte matches a SHA already stored for `victim/prod` (feasible for commits with no unique per-repo salt in their hashed content — e.g. identical parentless/empty-tree commits, or commits copied with preserved author/committer timestamps and message), then POSTs to `/webhooks`:
```
X-Github-Event: status
{sha: <shared_sha>, state: 'success', context: 'ci/travis', repository: {owner: {login: 'attacker'}}}
```
signed with the attacker's own `webhook_secret`. `verify_signature` succeeds (it is genuinely attacker's org and attacker's valid signature). `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, which is a raw, global, unscoped lookup — it will match and mutate the row for `victim/prod`'s commit too, since the `commits` table is only indexed/scoped per `(stack_id, sha)` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally unique — meaning the schema itself anticipates the same SHA legitimately existing across multiple stacks, but the handler doesn't disambiguate which stack the *verified* payload is entitled to write to.

Existing guards do not catch this: `verify_signature` authenticates "a request from org attacker for repository attacker/evil," not "a request entitled to write status for the specific commit sha it references." No code path cross-checks `params.dig('repository','full_name')` (or owner) against `commit.stack.repository.owner`/`full_name` before calling `create_status_from_github!`.

### Impact Explanation
This is a cross-repository write into another tenant's `Status` table with fully attacker-controlled `state`, `context`, `description`, and `target_url`, forging green CI (`state: 'success'`) for a commit the attacker never controls in `victim/prod`. `Status#after_create` fires `enable_ci_on_stack` and `schedule_continuous_delivery`/`ProcessMergeRequestsJob`, and forged "success" statuses feed `MergeRequest#reject_unless_mergeable!` / `all_status_checks_passed?` via `StatusChecker`, directly influencing merge-queue and deploy-gating decisions on the victim stack. This matches the "payload for one repository mutating another's stack/commit" Critical category. It's repeatable against any victim stack whose tracked commit SHAs the attacker can predict or reproduce (e.g., by mirroring public commits into their own repo, or by both repos sharing an initial/empty-tree commit — common in generated boilerplate).

### Likelihood Explanation
Preconditions are entirely attacker-controlled: the attacker only needs their own GitHub App install/webhook secret for `attacker` (no victim secret needed) and the ability to construct a commit whose SHA matches a real commit tracked by the victim (feasible for content-identical commits, e.g. identical author/committer/message/timestamp/tree with no parent, or by directly copying a public commit's exact metadata into their own history). No Shipit session, API token, or victim secret is required — this is a pure unauthenticated-HTTP attack against `/webhooks`. Feasibility is moderate: it depends on the attacker being able to reproduce an exact SHA the victim tracks, which is trivial if the victim's commit is public (attacker just needs their own repo to contain a commit with identical hashed content, which git allows regardless of which repo it lives in).

### Recommendation
Scope `StatusHandler#process` (and the analogous check_run/push handlers) to only mutate commits belonging to the stack(s)/repository that the verified webhook payload actually names, e.g. join through `Commit -> Stack -> Repository` and filter by `repository.owner`/`full_name` matching `params.dig('repository','full_name')` before calling `create_status_from_github!`. Reject or ignore matches where the commit's owning repository does not match the authenticated repository from the payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (or webhooks_controller_test.rb)
test "status webhook from an unrelated org cannot forge a status on another repository's commit" do
  victim_commit = shipit_commits(:first) # belongs to stack 'shipit/shipit' fixture, e.g.
  attacker_repo_owner = 'attacker'

  # Precondition: attacker crafts/collides a commit sha matching victim_commit.sha in their own repo
  shared_sha = victim_commit.sha

  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'owner' => { 'login' => attacker_repo_owner }, 'full_name' => 'attacker/evil' }
  }.to_json

  # Signature verified only against attacker's own org secret
  Shipit.github(organization: attacker_repo_owner).stubs(:verify_webhook_signature).returns(true)

  request.headers['X-Github-Event'] = 'status'

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end
  # Binding check: the org that signed (attacker) must not be able to write
  # to Commit rows owned by a different repository/org (victim's stack owner).
  assert_not_equal attacker_repo_owner, victim_commit.stack.repository.owner
end
```
Currently this test would fail (i.e., `victim_commit.statuses.count` increases by 1) against the unpatched `StatusHandler#process`, demonstrating the cross-tenant write; after adding repository/stack scoping in `process`, the assertion should hold.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
