### Title
Webhook organization authenticated by signature does not match the repository/stack acted upon by event handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) to validate an inbound webhook against based on one field of the untrusted payload (`repository.owner.login`, falling back to `organization.login`), while the event handlers that actually act on the payload pull the target repository from a *different* payload field (`repository.full_name`). Nothing ties these two together, so a valid signature from Organization A's secret does not guarantee the payload's `repository.full_name` belongs to Organization A.

### Finding Description
`verify_signature` resolves the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

It then looks up `Shipit.github(organization: repository_owner)` and verifies the raw body's HMAC against that organization's `webhook_secret`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` hands the *entire untrusted payload* to the registered handlers: [4](#0-3) 

Handlers such as `PushHandler` resolve the `Stack`/`Repository` to act on from a separate field of the same payload, `repository.full_name`, with no cross-check against the organization whose secret authenticated the request: [5](#0-4) [6](#0-5) 

This is exactly the class of bug the report describes generalized to this codebase: a check is performed (HMAC verification), but a field that materially changes the effect of the operation (`repository.full_name`, i.e., which org's `Stack` gets synced) is never covered by that check's authorization semantics — it's covered by the raw bytes of the HMAC, but the code never asserts that the *authenticated organization* equals the *organization the write is applied to*. Shipit explicitly supports multiple GitHub organizations, each with its own independent `webhook_secret`, in a single instance: [7](#0-6) [8](#0-7) 

Additionally, if an organization has no `webhook_secret` configured at all, `verify_webhook_signature` short-circuits and accepts *any* signature for that organization's requests: [9](#0-8) 

### Impact Explanation
In a shared/multi-tenant Shipit deployment, a user who legitimately controls one configured GitHub organization (Org A) — and therefore knows or can set its `webhook_secret` — can craft a fully custom JSON payload, sign it correctly with Org A's secret, but populate `repository.full_name` (and other handler-consumed fields) with an entirely different organization's (Org B) repository name. `verify_signature` only validates that the raw body is unmodified relative to Org A's key; it never validates that the repository referenced inside that body actually belongs to Org A. The handler layer then blindly trusts `repository.full_name` to locate `Repository`/`Stack` records and perform writes/actions (e.g., `PushHandler` invoking `stack.sync_github`, or other handlers updating commit statuses, check runs, or team/membership records tied to Org B's stacks) — none of which Org A is authorized to touch. This crosses the repository/organization authorization boundary using credentials scoped to a different tenant, satisfying the "cross-repository writes" / unauthorized-action impact class.

### Likelihood Explanation
Exploitability requires the attacker to already control a legitimate, configured GitHub organization/App within the same Shipit instance (or to target an organization whose `webhook_secret` is unset, which the code treats as "always verified"). This is a realistic scenario for any Shipit installation serving more than one organization/tenant (the documented "Using Multiple Github Applications" setup), and requires no privileged Shipit session, API token, or GitHub access to Org B — only the ability to send an HTTP POST to `/webhooks` with a payload signed by a key the attacker already legitimately possesses.

### Recommendation
After successful signature verification, re-derive the organization strictly from the same field used to select the verifying secret, and reject (or scope) any handler processing where `repository.full_name`'s owner (or `organization.login`) does not match `repository_owner` used in `verify_signature`. Do not allow handlers to resolve `Repository`/`Stack` records purely from payload content that falls outside the field set validated as "belonging" to the authenticating organization. Also disallow the "treat as verified" fallback when `webhook_secret` is blank for organizations expected to receive external webhooks in a multi-tenant configuration.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org config).
2. As the owner/admin of `org-a`, compute `sha1=HMAC(org_a_webhook_secret, raw_body)` for a custom `push` payload where `raw_body`'s `repository.owner.login` = `"org-a"` (so `verify_signature` resolves and validates against `org-a`'s secret) but `repository.full_name` = `"org-b/some-private-repo"`.
3. POST this payload with header `X-Hub-Signature: sha1=<computed>` and `X-Github-Event: push` to `/webhooks`.
4. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) succeeds because the HMAC matches `org-a`'s secret over the exact bytes sent.
5. `PushHandler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves `Repository.from_github_repo_name("org-b/some-private-repo")` and calls `stack.sync_github` on Org B's stack — an action Org A never had credentials or authorization to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
