### Title
Unvalidated Peer-Supplied StakingInfo Poisons DB Cache, Corrupting Reward Distribution and Proposer Selection — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

---

### Summary

During fast-sync, staking information received from a remote peer is accepted and written to the persistent database with **no content validation** against the actual on-chain AddressBook state. Because `GetStakingInfo` gives the DB-cached value unconditional priority over state-derived values (before the Kaia hardfork), a malicious peer can permanently inject fabricated `StakingAmounts`, `RewardAddrs`, and `NodeIds` into the local node's staking DB. The corrupted values are then used verbatim for proposer-list generation and KAIA reward distribution.

---

### Finding Description

**Invariant that must hold:** `StakingInfo` stored at key `sourceNum` in the DB must faithfully reflect the AddressBook contract state at block `sourceNum`. This is the only source of truth for validator weights and reward addresses.

**Where the invariant is broken — `DeliverStakingInfos` in `queue.go`:**

```go
// datasync/downloader/queue.go  line 956-958
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil   // ← always passes; no content check
}
```

The `validate` callback receives the corresponding `*types.Header` (which carries the state root) but performs zero verification of the staking payload against it. Every `P2PStakingInfo` delivered by any peer is accepted unconditionally. [1](#0-0) 

**Where the poisoned value is persisted — `commitFastSyncData` in `downloader.go`:**

```go
// datasync/downloader/downloader.go  line 1881-1884
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum,
        staking.ToStakingInfo(result.StakingInfo))
}
```

The fabricated `StakingInfo` is written directly to the miscDB without any cross-check against the block's state root. [2](#0-1) 

**Where the poisoned DB value takes priority — `GetStakingInfo` in `getter.go`:**

```go
// kaiax/staking/impl/getter.go  line 57-63
if !isKaia {
    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
        s.stakingInfoCache.Add(sourceNum, si)
        return si, nil   // ← DB wins; state is never consulted
    }
}
```

Before the Kaia hardfork, if a DB entry exists it is returned immediately. The state-derived path (`getFromStateByNumber`) is never reached, so the fabricated values are used for all downstream consumers. [3](#0-2) 

**The same unvalidated write path exists in `SyncStakingInfo` (admin API):**

```go
// datasync/downloader/downloader.go  line 677
d.stakingModule.PutStakingInfoToDB(stakingInfo.BlockNum, staking.ToStakingInfo(stakingInfo))
```

The only check performed is that the requested block hash exists in the canonical chain; the *content* of the returned staking info is never verified against the state at that block. [4](#0-3) 

**Downstream consumers of the corrupted value:**

- `assignStakingRewards` uses `StakingAmounts` and `RewardAddrs` to distribute KAIA block rewards. [5](#0-4) 
- `calcBaseProposers` uses `StakingAmounts` to build the weighted proposer list. [6](#0-5) 

---

### Impact Explanation

A malicious peer that serves a syncing node during fast-sync can inject a `P2PStakingInfo` payload that:

1. **Inflates its own `StakingAmounts`** → receives a disproportionate share of staking rewards and a higher proposer-selection weight, redirecting KAIA block rewards to an attacker-controlled `RewardAddr`.
2. **Deflates or zeroes other validators' `StakingAmounts`** → those validators receive no staking rewards for the affected interval.
3. **Substitutes arbitrary `RewardAddrs`** → redirects reward payments to attacker-controlled addresses.

The corrupted DB entry persists across restarts and is used for every block in the affected staking interval (up to `StakingInterval` blocks, e.g. 86 400 blocks on mainnet), causing sustained incorrect KAIA reward distribution.

---

### Likelihood Explanation

- **Trigger:** Any peer the syncing node connects to during fast-sync. No special privilege is required; a single malicious peer in the P2P network suffices.
- **Precondition:** The victim node must be performing fast-sync (common for new nodes or nodes recovering from state loss).
- **Persistence:** Once written, the DB entry is not overwritten by normal block processing (the DB path is taken first), so the corruption survives until the entry is explicitly deleted or the Kaia hardfork activates.
- **Detection difficulty:** The node logs only `"Imported new staking information"` with no integrity check, making silent corruption easy.

---

### Recommendation

1. **Validate staking info content against the block state root.** In `DeliverStakingInfos`, replace the stub `validate` function with a check that re-derives the expected `StakingInfo` from the header's state root and compares it to the received payload (or at minimum verifies a cryptographic commitment).

2. **In `SyncStakingInfo`, verify the received payload against the local state** at the canonical block before calling `PutStakingInfoToDB`.

3. **Remove the unconditional DB-first priority** in `GetStakingInfo`, or add a periodic integrity re-check that re-derives staking info from state and overwrites any DB entry that diverges.

---

### Proof of Concept

```
1. Victim node V starts fast-sync.
2. Attacker controls peer P and registers with V.
3. V requests staking info for block hashes [h_1000, h_2000, ...].
4. P responds with P2PStakingInfo{BlockNum: 1000,
       CouncilStakingAmounts: [999_000_000, 1, 1, 1],   // attacker inflated
       CouncilRewardAddrs:    [attacker_addr, ...]}
5. DeliverStakingInfos validate() returns nil → payload accepted.
6. commitFastSyncData calls PutStakingInfoToDB(1000, fabricated_si).
7. V completes sync and begins processing blocks 2001–3000.
8. GetStakingInfo(2001) → sourceNum=1000 → ReadStakingInfo(DB, 1000) → returns fabricated_si.
9. assignStakingRewards distributes staking rewards proportional to fabricated amounts:
       attacker_addr receives ~100% of staking rewards for the entire interval.
10. Legitimate validators receive near-zero staking rewards for blocks 2001–3000.
```

The corrupted `StakingAmounts` at `sourceNum=1000` are used for all blocks in `[2001, 3000]`, causing unauthorized KAIA reward distribution to the attacker's address for the full staking interval.

func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining

```markdown

In "SelectWeightedRandomProposer", a proposer list is pre-generated every proposer interval block. A single validator can appear multiple times in the list. Higher the staking amount more frequently the validator appears in the list. The list is randomized using a deterministic PRNG.

Note that the removevalidator vote removes validators from the proposer list. The purpose is not to give the removed validator a chance to be selected as a proposer.

**proposer list generation**

Given "proposer update block" in which all the information below (qualified validators, staking info, block hash) is based on,
1. Adjust the staking amounts of the qualified validators.
    - $S_i = \text{Round}({S_i}^{1/G})$ if Gini option is enabled.
    - $S_i = S_i$ (unchanged) if Gini option is disabled.
    - Gini option is controlled by the `reward.useginicoeff` parameter.
    - G is the Gini coefficient of the staking amounts that are no less than the minimum staking amount (i.e. `G = stakingInfo.Gini(minStake)`).
1. Calculate the total staking amount of the qualified validators. Use the Gini-adjusted amounts, if enabled.
    - $TS = \sum{S_i}$
1. Calculate the percentile weight (integers 1 to 100) of the qualified validators. Every validator has a nonzero chance.
    - $W_i = \text{max}\left(1, \text{round}\left(\frac{100S_i}{TS}\right)\right)$ if TS > 0
    - $W_i = 0$ if TS = 0
1. Construct the "proposer list" where each validator appears $W_i$ (could be 0) times. If the proposer list is empty, put each validator once.
    - $PL = \text{repeat}(0, W_0) || ... || \text{repeat}(k, W_k)$ if $\sum{W_i} > 0$
    - $PL = 0, 1, ..., k$ if $\sum{W_i} = 0$
    - where $\text{repeat}(v,n) = v, v, ..., v\ \ (n\text{ times})$
1. PRNG seed is the first 15 hex digits (nibbles) of proposer update block's hash (updateHash)
```
