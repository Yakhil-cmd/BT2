### Title
Missing `return` after caught exception causes double-completion and continued processing of an already-deleted private payment chain - ([File: network.js])

### Summary
`validateAndSave()` inside `handleSavedPrivatePayments()` in `network.js` mirrors the FreeRDP bug class: a resource is finalized/released on an error path, but execution falls through and the code keeps using the same (now-invalidated) state, exactly like `urb_select_interface` freeing the USB config on error and later code still dereferencing it.

### Finding Description
In `handleSavedPrivatePayments()`, each row from `unhandled_private_payments` is processed by an inner `validateAndSave` closure: [1](#0-0) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (attacker-controlled `payload` originating from a peer/private-payment counterparty via `JSON.parse(row.json)`), the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which deletes the DB row for this chain and invokes the `async.each` iteration callback `cb` — finalizing this chain's handling, analogous to freeing the resource.

However, there is no `return` after the `catch` block, so execution falls through to compute `key` using the now-undefined `json_payload_hash` and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` anyway: [2](#0-1) 

This is the “dereference after free” analog: the chain data (`row`, `arrPrivateElements`) whose DB record was just deleted and whose iteration was already completed is used a second time. Whichever branch (`ifOk`, `ifError`, `ifWaitingForChain`) fires from this second call will invoke `cb` again and, in the `ifOk`/`ifError` branches, call `deleteHandledPrivateChain(...)` a second time: [3](#0-2) 

Calling the `async.each` iteratee callback twice for the same item is undefined behavior in the `async` library (can cause the outer completion callback to fire early/twice, corrupting the `saved_private` mutex lifecycle and the `assocNewUnits`/`new_my_transactions` bookkeeping across the batch of chains being processed in parallel).

### Impact Explanation
`handleSavedPrivatePayments` runs under the `["saved_private"]` mutex and iterates all pending private payment chains for the wallet in parallel via `async.each`. Double-invoking `cb` for one poisoned chain can cause the batch's final callback to run prematurely relative to other chains still being validated, releasing the `saved_private` lock while sibling `validateAndSavePrivatePaymentChain` calls (each of which itself does `db.takeConnectionFromPool` + `BEGIN`/`COMMIT`) are still in flight. This risks concurrent/overlapping processing of the wallet's private-payment inbox, which can lead to duplicate acceptance/inconsistent bookkeeping of private outputs (private assets are the ones subject to double-spend/duplicate-crediting risk since their state lives outside the public DAG's normal input-locking flow) and to node disagreement about which private chains were saved. This satisfies the "AA/wallet fund loss or freezing / node disagreement on validity" bar because it is a private-payment counterparty (explicitly an allowed attacker) supplying `payload` content that fails `objectHash.getBase64Hash` (e.g., a payload shape that the hasher rejects), directly reachable without needing a malicious peer/hub/node role.

### Likelihood Explanation
The trigger requires only that `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throw for some crafted head-element payload sent as a private payment to a wallet — a private-payment counterparty fully controls `arrPrivateElements[0].payload` since it is attacker-supplied JSON forwarded from `handleOnlinePrivatePayment`/`sendPrivatePaymentToWs` into `unhandled_private_payments.json`. I was not able to fully verify from the indexed code which specific payload shapes make `objectHash.getBase64Hash` throw (the `objectHash.js` implementation was not retrievable within index limits), so likelihood should be treated as plausible but unconfirmed pending direct code review of `objectHash.getBase64Hash`.

### Recommendation
Add a `return` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave` (network.js, around line 2476) so that once the chain is finalized/deleted and `cb` invoked, no further code in the closure executes:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
1. As a device/peer acting as a private-payment counterparty, send a `private_payment` justsaying message (handled by `handleOnlinePrivatePayment`) whose head element's `payload` is a value that causes `objectHash.getBase64Hash(payload, true)` to throw (exact payload shape unconfirmed — requires inspecting `objectHash.js`, not available in the indexed context).
2. The payment is queued into `unhandled_private_payments` (`savePrivatePayment` in network.js:2390-2402) and later picked up by `handleSavedPrivatePayments()`.
3. In `validateAndSave()`, `getBase64Hash` throws; the `catch` block deletes the row and calls `cb` once, but without a `return`, execution proceeds to also call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which will asynchronously invoke `cb` a second time for the same `async.each` item, and re-invoke `deleteHandledPrivateChain` on an already-deleted row — demonstrating the double-completion/continued-use-after-finalization bug.
