### Title
Webhook signature verification is keyed by an attacker-controlled organization field while status/commit handlers act on globally-scoped SHAs, allowing cross-repository/cross-organization status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/`webhook_secret` to verify the HMAC against using an attacker-supplied payload field (`repository.owner.login` or `organization.login`), rather than tying that verification to the specific repository/stack the event will actually mutate. Handlers such as `StatusHandler` then act on `Commit.where(sha: params.sha)` with no scoping whatsoever to the organization/repository that was authenticated. In a multi-tenant Shipit deployment (the officially documented "Using Multiple GitHub Applications" configuration), this breaks the equality "organization that authenticated == repository/stack that is written."

### Finding Description
`WebhooksController#verify_signature` picks the signing secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is taken directly from the untrusted, attacker-supplied payload body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). In a multi-org configuration (documented in `docs/setup.md` "Using Multiple Github Applications"), each organization has its *own* `webhook_secret` looked up via `Shipit.github_app_config(organization)`: [3](#0-2) 

Once the HMAC check passes for *that* organization's secret, the raw JSON body is dispatched to handlers with no further tie-back to `repository_owner`. `Handler#stacks` scopes push/check-suite handling by `repository.full_name` (a separate, independently attacker-controlled field within the same signed body): [4](#0-3) 

More critically, `StatusHandler` does not scope by repository/stack at all — it matches on SHA across the *entire* instance: [5](#0-4) [6](#0-5) 

Because the secret used to authenticate the request is selected by a value the attacker also supplies (`repository.owner.login`/`organization.login`), and the downstream handler does not re-derive/verify that the acted-upon commit belongs to that same authenticated organization, an entity that legitimately administers one onboarded GitHub organization (and therefore possesses that organization's own `webhook_secret`, which they configure themselves when registering their App per `docs/setup.md`) can produce a validly-signed webhook body whose `repository.owner.login`/`organization.login` matches their own org, while other payload content (`sha`, `state`) targets a commit that actually belongs to a *different* tenant's stack. `StatusHandler` will happily call `create_status_from_github!` on that foreign commit, injecting a forged CI status (e.g., `success`).

This directly maps to the required binding-break class: "an organization that authenticated versus the repository that is written."

### Impact Explanation
A forged `success` status on a victim's commit can satisfy `ci.require`/blocking-status checks used by `Commit#deployable?` and `stack.schedule_merges`, potentially triggering the continuous-delivery job or merge-queue advancement for a commit that never actually passed CI in the victim's repository: [7](#0-6) [8](#0-7) 

This is an unauthorized-deploy-enabling primitive (forged CI approval leading to deploy/merge-queue progression on a stack outside the attacker's own organization) — matching the "unauthorized deploy" High-impact category, contingent on the deployment running the documented multi-org configuration.

### Likelihood Explanation
This requires: (1) the Shipit instance to be configured for multiple GitHub organizations as documented, and (2) the attacker to legitimately control (or be an admin of) one onboarded organization whose `webhook_secret` they know, while targeting a commit SHA belonging to another tenant's stack (SHA is often guessable/public, e.g., via public GitHub commit history). This is a real, low-effort exploitation path once the multi-tenant precondition holds, but is not universally exploitable in the common single-organization deployment, since in that case there is only one `webhook_secret` and no cross-org authentication decision is being made from attacker data. I was not able to fully verify within the given time whether any additional constraint elsewhere (e.g. `Repository`/`Stack` uniqueness or a repository-scoped API client) further restricts which stacks a given `webhook_secret`-holder can influence via the `status` event; this should be validated further.

### Recommendation
Scope every webhook handler's targets by the authenticated organization, not solely by attacker-supplied `repository.full_name`/`sha`. Concretely: after `verify_signature` succeeds for organization `O`, pass `O` into `Shipit::Webhooks.for_event` handlers and have `StatusHandler`/`Handler#stacks` restrict lookups to `Repository.where(owner: O)` (or equivalent), rejecting any event whose `repository.owner.login` does not match the authenticated organization.

### Proof of Concept
Conceptual PoC (requires the documented multi-org configuration):
1. Attacker is an admin of Org A, onboarded to the shared Shipit instance, and knows Org A's `webhook_secret` (self-configured per `docs/setup.md`).
2. Attacker discovers/guesses a commit SHA `X` belonging to a stack in Org B (victim), e.g. from the public repository's commit history.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{"repository":{"owner":{"login":"OrgA"},"full_name":"OrgA/some-repo"},"sha":"X","state":"success"}`, HMAC-signed with Org A's `webhook_secret` in `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the signature verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: "X")`, which matches the victim's commit in Org B regardless of the authenticated organization, and creates a forged `success` status on it via `Commit#create_status_from_github!`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
