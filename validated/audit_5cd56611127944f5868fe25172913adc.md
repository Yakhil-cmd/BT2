## Title
Webhook signature verification is keyed by an attacker-controlled organization field that is decoupled from the repository field actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate a payload against using an organization value taken directly from the unauthenticated JSON body, while the actual `Repository`/`Stack` that the handler subsequently writes to is looked up from a *different* field of that same body. Because these two fields are never cross-checked against each other, the "organization that authenticated" and the "repository that is written" can be made to diverge.

### Finding Description
`verify_signature` computes the organization used for HMAC verification as:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

and then verifies against that org's secret:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

Critically, `GitHubApp#verify_webhook_signature` unconditionally passes when no secret is configured for that org: `return true unless webhook_secret`. [3](#0-2) 

Meanwhile, every event handler (`Handler#stacks`, used transitively by `PushHandler`, and the `repository` method in the pull-request handlers) resolves the actual `Repository`/`Stack` to mutate from a completely separate JSON field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`repository.owner.login` (used for authentication) and `repository.full_name` (used to select the target Stack) are never compared. If Shipit is configured with multiple GitHub organizations (a documented supported configuration, see `docs/setup.md` "Using Multiple Github Applications") [5](#0-4)  and any one of them has a blank/unset `webhook_secret` (shown as a normal/legacy configuration state in the shipped config samples) [6](#0-5) , an unauthenticated attacker can:

1. Set `repository.owner.login` (or `organization.login`) to the name of the org with the blank secret, causing `verify_webhook_signature` to short-circuit to `true` with no signature check at all.
2. Set `repository.full_name` to the full name of an entirely different, properly-secured repository/stack registered in Shipit.
3. Send this forged payload to the single shared `/webhooks` endpoint — nothing in the routing or controller ties the webhook to a specific org or repo before the body is parsed.

The equality that should hold but doesn't:
`organization authenticated by verify_signature` == `owner of the repository whose Stack is mutated by the handler`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out in scope. Concretely, `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to the targeted (unauthenticated) repository [7](#0-6) , and PR-based handlers can archive/unarchive/create review stacks or mutate labels for any repository whose `full_name` the attacker supplies [8](#0-7) . These are stack-state mutations and forced sync operations triggered without possessing that repository's/organization's actual webhook secret — a bypass of the intended per-organization authentication boundary that gates who can drive Shipit's github-sync/deploy-adjacent state machine for a given repository.

### Likelihood Explanation
Exploitability requires only that at least one organization entry in `Shipit.secrets.github` has a blank `webhook_secret` — which the project's own sample/dev configs (`config/secrets.development.shopify.yml`) and its documented multi-org setup show is an accepted, non-exceptional configuration. No credentials, tokens, or sessions are required; the attacker only needs network access to the public webhooks endpoint and knowledge of two strings already public in Shipit's UI/URLs: an org name with no secret configured, and the target repo's `owner/name`.

### Recommendation
Bind the authenticated organization to the repository being acted upon: after `verify_signature` succeeds, re-derive the handler's target repository owner strictly from the same trusted `repository_owner` value used for signature verification (or verify that `payload.dig('repository','full_name')`'s owner segment matches `repository_owner`) before dispatching to handlers. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in production — require an explicit signed-off "no secret" configuration flag, or reject unsigned webhooks outright once any organization is configured with a secret.

### Proof of Concept
1. Configure Shipit with two orgs: `LegacyOrg` (no `webhook_secret`) and `SecureOrg` (has a real, secret-protected repo `SecureOrg/prod-app` with an active Stack).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "LegacyOrg" }, "full_name": "SecureOrg/prod-app" }
}
```
3. `verify_signature` computes `repository_owner == "LegacyOrg"`, loads `Shipit.github(organization: "LegacyOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking `X-Hub-Signature` at all.
4. `PushHandler` resolves `Repository.from_github_repo_name("SecureOrg/prod-app")` and enqueues `sync_github` against `SecureOrg`'s real stack, entirely bypassing the intended per-org authentication for `SecureOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
