## Confirmed: `StatusHandler` confirms exploit path

The `StatusHandler` at `app/models/shipit/webhooks/handlers/status_handler.rb:1-25` looks up commits purely by `sha` — it has **no scoping to the repository/organization that the signature was verified against** — and calls `commit.create_status_from_github!(params)` for every matching commit across the entire database, regardless of stack/org.

### Title
Webhook signature is verified against `repository.owner.login`, but events are processed for the repository named in `repository.full_name`/`sha` with no cross-check, allowing a tenant with a legitimate multi-org GitHub App secret to forge webhook events for other orgs' stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (`Shipit.github_organizations`), each org has its own distinct `webhook_secret`/`app_id`/`private_key` (`test/dummy/config/secrets_double_github_app.yml:1-41`). `WebhooksController#verify_signature` selects *which* org's secret to verify the HMAC against solely from `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . Once the signature check passes, `create` re-parses the raw body and dispatches it, unmodified, to handlers [2](#0-1) . The handlers never re-validate that the org that signed the request actually owns the repository/commit they act on — `Handler#stacks` resolves purely from `payload.dig('repository', 'full_name')` [3](#0-2) , and `StatusHandler#process` resolves purely from `params.sha`, globally, with no repository/stack scoping at all [4](#0-3) .

### Finding Description
The binding that should hold is: **organization authenticated (the `webhook_secret` used to pass `verify_webhook_signature`) == organization/repository actually written by the handler.** This binding is broken:

- `Shipit.github(organization:)` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) keyed on the `repository_owner` field taken from the attacker-controlled JSON body [5](#0-4) .
- Because a tenant with their own legitimately-configured GitHub App (their own `webhook_secret`, known to whoever operates that org's app) can compute a valid `X-Hub-Signature` for **any** raw body of their choosing, they can set `repository.owner.login` = their own org (so `verify_signature` authenticates the request against their own known secret) while setting every other field used by the handlers (`repository.full_name`, `sha`, `pull_request.number`, `team.id`, etc.) to values belonging to a **different**, unrelated org configured in the same Shipit instance.
- `StatusHandler` is the clearest amplifier: it looks up commits with `Commit.where(sha: params.sha)` with zero repository/org filtering and calls `commit.create_status_from_github!(params)` [6](#0-5) . Any commit sha across any stack in the whole Shipit instance can have an arbitrary CI status (`state`, `context`, `description`) injected by an attacker who owns valid credentials for just one unrelated org's GitHub App.
- `Commit#deployable?` gates whether the commit can be shipped: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [7](#0-6) . By injecting a forged `success` status for the required CI context on a victim stack's commit, an attacker satisfies `required_statuses`/`ci.require` (`app/models/shipit/deploy_spec.rb:194-196`) and `deployable?` becomes true for a commit that never actually passed CI, and merges/deploys can then be triggered (`stack.schedule_merges` is invoked from `add_status` when the new state is `pending`/`success`, per `app/models/shipit/commit.rb:379-384`).

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding and results in **an unauthorized deploy**: an attacker who legitimately controls credentials for one tenant org in a multi-org Shipit install can forge a passing CI status for a commit belonging to a completely different, higher-trust org's stack, causing `deployable?` to return true and the merge queue / a subsequent deploy to proceed on unvetted code. This satisfies the Critical impact bar ("an unauthorized deploy"). It also enables broader cross-tenant writes (membership changes, PR-driven review-stack archive/unarchive, push-triggered sync) since none of the webhook handlers re-verify that the authenticated organization matches the resource being mutated.

### Likelihood Explanation
Requires the host application to configure Shipit's multi-organization GitHub App feature (`docs/setup.md:182-209`) with more than one tenant/org sharing the same Shipit instance and `/webhooks` endpoint — a documented, supported configuration, not a hypothetical. Any actor who is trusted enough to hold one org's `webhook_secret` (i.e., who administers that org's GitHub App, a low-privilege trust level relative to the victim org) can exploit this with a single crafted HTTP POST; no GitHub push access, session, or `ApiClient` token to the victim org is needed.

### Recommendation
After (or instead of) verifying the HMAC, the webhook handlers must verify that the organization/app that signed the request actually owns the resource being mutated: e.g., derive the target repository/stack's owning organization from the DB (`Repository#owner`) and assert it equals the `organization` whose secret validated the signature, rejecting the request otherwise. `StatusHandler` in particular should filter `Commit.where(sha: params.sha)` down to commits whose `stack.repository.owner` matches the authenticated organization before calling `create_status_from_github!`.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own GitHub App/`webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the operator/admin of `OrgOne` (who legitimately knows `OrgOne`'s `webhook_secret`), craft a `status` event payload:
   ```json
   {
     "sha": "<victim commit sha belonging to OrgTwo/production-app>",
     "state": "success",
     "context": "<OrgTwo's required CI context>",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgOne/decoy" }
   }
   ```
3. Sign the raw body with `OrgOne`'s `webhook_secret` and POST it to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `OrgOne`'s `GitHubApp`, and the signature validates successfully [8](#0-7) .
5. `StatusHandler#process` finds the commit by `sha` (belonging to `OrgTwo`) and records a forged `success` status on it [4](#0-3) , flipping `OrgTwo`'s commit to `deployable?` and potentially triggering an unauthorized merge/deploy.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
