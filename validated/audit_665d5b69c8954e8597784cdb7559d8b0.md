### Title
Cross-stack read via stack-scoped API token in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` restricts every `ApiClient` to its authorized stack by routing all stack lookups through the `stacks` scope method, but `Api::CCMenuController` overrides `#stack` to bypass that scope entirely, letting a token scoped to one stack read deploy status for any other stack.

### Finding Description
The engine's intended binding is: **the stack a token authorizes == the stack a token can touch**. `Api::BaseController#stacks` enforces this by scoping the model query to `current_api_client.stack_id` when the client is stack-scoped: [1](#0-0) 

Every well-behaved controller (`Api::StacksController`, `Api::DeploysController`, `Api::ReleaseStatusesController`, etc.) resolves the requested stack through this scoped `stacks`/`stack` helper, so a client created with a `stack_id` (e.g. fixture `here_come_the_walrus`) can never resolve a `Stack` object outside its assigned stack: [2](#0-1) [3](#0-2) 

`Api::CCMenuController`, however, overrides `#stack` to bypass the scoped helper and resolve directly against the global `Stack` model using only the URL parameter, with no reference to `current_api_client.stack_id`: [4](#0-3) 

Permission enforcement in this engine is purely operation:scope string matching and never checks which specific stack row is being accessed: [5](#0-4) 

Because `require_permission :read, :stack` only checks that `'read:stack'` is present in `permissions`, and the `stack` method resolution is the *only* place stack-scoping is enforced, `CCMenuController`'s override removes the only enforcement point. Route `/api/stacks/*stack_id/ccmenu` (`get '/ccmenu' => 'ccmenu#show'`) accepts an arbitrary `stack_id`: [6](#0-5) 

**Before the crossing:** a stack-scoped `ApiClient` (`stack_id = A`) with `read:stack` permission can only enumerate/read stack `A` through every other API endpoint, matching `stacks_controller_test.rb`'s "an api client scoped to a stack will only see that one stack" assertion.
**After hitting `ccmenu#show` with `stack_id = B`:** the same token successfully authenticates (`authenticate_api_client` only checks the Basic-Auth/query token, not stack ownership) and `stack` resolves to `Stack B` directly via `Stack.from_param!`, returning `B`'s deploy status/activity XML — breaking the `stack authorized == stack touched` binding.

### Impact Explanation
This is an authorization-scope escape: a token deliberately restricted by its creator to one stack can read live deploy state (latest deploy, running status, build status/label/time, web URL) for any other stack in the installation, including stacks the token owner was never granted access to. This maps to the "unauthenticated read of stack state" class of High-severity finding in an authenticated context (a credential is misused outside its authorized scope rather than skipping authentication altogether), and demonstrates the exact cross-stack confinement break the report's bug class targets.

### Likelihood Explanation
Trivial to trigger: any holder of a valid, narrowly-scoped `ApiClient` token (e.g. a CCMenu widget URL generated for one project, see `CCMenuUrlController`) can simply change the `stack_id` path segment on the `ccmenu` request to any other known stack path (`owner/repo/env`), which are not secret. No additional privilege or race condition needed.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` and resolve the stack through the inherited, scoped `stacks`/`stack` helper from `Api::BaseController` so stack-scoped tokens are confined exactly as they are in every other API controller. If `ApiClient.authenticate(params[:token])` needs to stay for query-string auth, keep it, but stack resolution must go through `stacks.from_param!(params[:stack_id])`.

### Proof of Concept
1. Create two stacks, A and B.
2. Create an `ApiClient` scoped to stack A (`stack: A`) with permission `read:stack` (mirrors fixture `here_come_the_walrus`).
3. Using that client's `authentication_token`, request `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token>`.
4. Observe HTTP 200 with stack B's deploy/activity XML returned, despite the token only being authorized for stack A — contrast with `GET /api/stacks?...` on the same token, which (per `stacks_controller_test.rb:217-223`) is correctly restricted to stack A only.
