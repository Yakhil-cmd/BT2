### Title
`check_suite` webhook can mutate a stack belonging to a different organization than the one whose secret authenticated the request - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC-verifying `GitHubApp` using `repository.owner.login`, while `Shipit::Webhooks::Handlers::Handler#stacks` resolves the repository/stack to mutate using the independent `repository.full_name` field. Because these two fields are never cross-checked, an attacker who controls an org configured in Shipit without a `webhook_secret` can forge a `check_suite` event whose `repository.owner.login` names that no-secret org while `repository.full_name` points at a completely different, secret-protected victim repository, causing `CheckSuiteHandler` to act on the victim's stack.

### Finding Description
The broken binding: the code implicitly assumes `params.repository.owner.login == owner_of(params.repository.full_name)`, but no validation enforces this.

- `WebhooksController#verify_signature` picks the GitHub App config via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`): [1](#0-0) 
- `GitHubApp#verify_webhook_signature` trivially returns `true` when that org has no configured secret: `return true unless webhook_secret`: [2](#0-1) 
- If the named org is entirely unknown to Shipit, `Shipit.github(organization:)` raises `GithubOrganizationUnknown` and the request is rejected with 422 — so the attacker must name a *configured* org that simply lacks a `webhook_secret`.
- Once signature verification passes, `WebhooksController#create` dispatches the full parsed `params` (including the untouched `repository.full_name`) to `Shipit::Webhooks.for_event(event)` handlers: [3](#0-2) 
- `Handler#stacks` (base class used by `CheckSuiteHandler`) resolves the target stacks purely from `payload.dig('repository', 'full_name')`, independent of whatever org authenticated the request: [4](#0-3) 
- `CheckSuiteHandler#process` then selects stacks by `params.check_suite.head_branch` and, for matching commits by `head_sha`, calls `schedule_refresh_check_runs!`, enqueuing `RefreshCheckRunsJob` against the victim stack/commit: [5](#0-4) [6](#0-5) 

**Exploit flow**: Attacker owns/configures an org `no-secret-org` that is registered in Shipit's GitHub app config but has no `webhook_secret` set. Attacker POSTs to `/webhooks` with header `X-Github-Event: check_suite`, body `{"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"check_suite":{"head_branch":"main","head_sha":"<victim commit sha>"}}`. `verify_signature` looks up `Shipit.github(organization: "no-secret-org")`, finds no secret, and accepts the request unconditionally (any or no `X-Hub-Signature`). The handler then resolves stacks for `victim-org/victim-repo` and enqueues a check-run refresh for the named commit on the victim's stack — a mutation on a repository that did not authenticate the request.

**Why guards fail**: `verify_signature` only guarantees the payload was accepted *by the org named in `repository.owner.login`*; it never confirms that `repository.full_name` belongs to that same org, and `ExplicitParameters`/`drop_unhandled_event` do not perform any such cross-field check either.

### Impact Explanation
This breaks the stated invariant — "a `check_suite` event only affects the repository/stack whose secret authenticated it" — regardless of `continuous_deployment` setting, and matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." The direct, demonstrable effect is that `RefreshCheckRunsJob` is enqueued and executed against the victim's real commit, pulling live check-run state from GitHub via `stack.github_api.check_runs(...)` and writing `CheckRun` records for the victim stack: [7](#0-6) . This is repeatable against any stack/repository whose `full_name` the attacker names, as long as one Shipit-configured org lacks a `webhook_secret`.

Note on the specific `ContinuousDeliveryJob` amplification claimed in the question: `Commit#schedule_continuous_delivery` is only invoked from the `after_commit ... on: :create` hook when a brand-new `Commit` row is created [8](#0-7) [9](#0-8) . `CheckSuiteHandler` only calls `schedule_refresh_check_runs!` on already-existing commits — it does not create commits and does not directly re-invoke `schedule_continuous_delivery`. I could not find code in the traced files that re-triggers continuous delivery purely from a check-run refresh. So while the cross-tenant authentication bypass and the unauthorized `CheckRun`/job-scheduling mutation on the victim stack are confirmed, the additional claim that this specific handler directly forces an unauthorized deploy via `ContinuousDeliveryJob` is not established by the code paths I traced (`check_run.rb`'s exact update logic was not fully inspected, so this residual path is unconfirmed rather than disproven).

### Likelihood Explanation
Requires that at least one org configured in Shipit's GitHub app settings has no `webhook_secret` set (an operational/config precondition, since `webhook_secret` is optional per `GitHubApp#initialize`) [10](#0-9) . Given that precondition, the attack costs a single unauthenticated HTTP POST with no valid signature required, is fully repeatable, and can target any repository full_name resolvable via `Repository.from_github_repo_name`.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, cross-validate that the owner embedded in `repository.full_name` matches `repository.owner.login` (or, more robustly, resolve the repository/stack first, then verify the signature using the `GitHubApp` for that resolved repository's actual organization, not the attacker-supplied `owner.login`). Additionally, consider rejecting webhook configs that have no `webhook_secret` rather than treating them as auto-verified.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb`, add a test using `test/dummy` fixtures with two configured orgs where one org config omits `webhook_secret`:
1. Configure `Shipit.github_apps` (or equivalent test config) with `victim-org` having a `webhook_secret` and `attacker-org` having none.
2. Create a `Stack` for `victim-org/victim-repo` with `continuous_deployment: true`, `branch: "main"`, and a `Commit` with a known `sha`.
3. `assert_equal params.dig('repository','owner','login'), owner_of(params.dig('repository','full_name'))` should be checked BEFORE tracing — assert this equality currently is NOT enforced anywhere in the code.
4. POST to `/webhooks` with `X-Github-Event: check_suite`, no valid `X-Hub-Signature` (or an arbitrary one), and body: `{"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"check_suite":{"head_branch":"main","head_sha":"<commit sha>"}}`.
5. Assert response is `200 OK` (not `422`), and assert (via `assert_enqueued_with` or job mock) that `RefreshCheckRunsJob` was enqueued for the victim's commit — proving that a payload "signed" by `attacker-org`'s (non-existent) secret mutated `victim-org`'s stack state.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
