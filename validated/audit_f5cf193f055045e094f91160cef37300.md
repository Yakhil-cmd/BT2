### Title
ApiClient stack-scoping bypass in CCMenu endpoint allows cross-stack read access - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` binds every API endpoint's notion of "stack" to the authenticated `ApiClient`'s `stack_id` via the `stacks` scope [1](#0-0) . `Api::CCMenuController`, however, overrides `stack` to look it up directly with `Stack.from_param!(params[:stack_id])`, bypassing that scope entirely [2](#0-1) . This breaks the same class of binding described in the source report: a value (`stack_id` scope) that is supposed to gate what a credential can touch is checked at authentication/authorization time but a different, unconstrained value (`params[:stack_id]`) is what actually gets acted upon at execution time.

### Finding Description
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true`) and `PERMISSIONS` include `read:stack` [3](#0-2) . The intended enforcement of that scoping lives in `Api::BaseController#stacks`, used by every other API controller's `#stack` helper (e.g., `Api::StacksController#stack` at `stacks.from_param!(params[:id])`) [1](#0-0) .

`Api::CCMenuController` requires only `:read, :stack` permission and defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id` [4](#0-3) . `require_permission :read, :stack` only checks that the `read:stack` permission bit is present on the token; it performs no per-stack ownership check [5](#0-4) . As a result, any `ApiClient` token that carries `read:stack` — even one deliberately created and scoped to a single, low-sensitivity stack (as is done automatically by `CCMenuUrlController#client`, which mints a `read:stack`-scoped token for whatever stack the current user is viewing) — can be replayed against `/api/*/ccmenu?stack_id=<any-other-stack>` to read that other stack's latest deploy/task status, regardless of the token's intended stack binding.

The `stacks` scoping mechanism (`ApiClient.stack_id` limiting `Stack.where(id: ...)`) is the equality that should hold: `token.authorized_stacks == token.touched_stack`. `CCMenuController` breaks it: `token.authorized_stacks = {bound_stack}` while `token.touched_stack = params[:stack_id]` (attacker-controlled, unconstrained).

### Impact Explanation
This matches the "High" bucket: "unauthenticated read of stack state, task streams or deploy output" via authorization scope confusion — a `read:stack`-scoped token minted for one stack can be used to read the status/output-adjacent data (`latest_deploy`, its id and end time, running state) of any other stack in the installation, including stacks the token was never meant to see. This is a genuine authorization-scope bypass reachable purely by an entity holding *any* valid, narrowly-scoped `read:stack` API token, not requiring elevated GitHub or Shipit privileges beyond that one token.

### Likelihood Explanation
Every stack page in the UI auto-provisions a scoped CCMenu `ApiClient` for its viewer (see `CCMenuUrlController#client`, which creates `permissions: %w[read:stack]` clients bound to a specific stack and exposes the token in a query string URL) [6](#0-5) . These URLs are designed to be handed to third-party CI dashboard tools (CCMenu clients) and are not treated as highly sensitive since they're meant to be stack-scoped. Any holder of such a URL/token (which is explicitly designed to leave Shipit's trust boundary) can trivially pivot to any other stack ID by editing the query string, since the controller never validates the token's stack binding.

### Recommendation
Change `Api::CCMenuController#stack` to use the same scoped lookup as every other API controller, i.e., resolve through `stacks.from_param!(params[:stack_id])` (delegating to `Api::BaseController#stacks`) rather than an unscoped `Stack.from_param!`, so a `read:stack` token bound to a specific stack can never resolve a different stack.

### Proof of Concept
1. As a logged-in Shipit user, visit any stack page; the UI calls `CCMenuUrlController#fetch`, which creates (or reuses) an `ApiClient` scoped to `stack: <stack_A>` with `permissions: ['read:stack']` and returns a URL `.../api/<stack_A>/ccmenu.xml?token=<token>` [7](#0-6) .
2. Take the `token` value from that URL (it is a self-contained signed `ApiClient` id, valid for that client regardless of the URL's `stack_id` path segment).
3. Send `GET /api/<stack_B>/ccmenu.xml?token=<token>` for an arbitrary other stack `stack_B`.
4. `authenticate_api_client` in `Api::CCMenuController` accepts the token (it only checks the signature/id, not the stack in the URL) [8](#0-7) ; `require_permission :read, :stack` passes because the token has `read:stack`; `stack` resolves `stack_B` via unscoped `Stack.from_param!`, and `show` renders `stack_B`'s latest deploy/task data — data the token was never authorized to see [9](#0-8) .

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))

      render(json: { ccmenu_url: uri.to_s })

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])

    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
