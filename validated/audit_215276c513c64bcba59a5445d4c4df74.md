### Title
Malicious secondary-AA recipient can force revert of an entire primary AA response, freezing/blocking payouts to co-recipients - (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `handleTrigger()` automatically executes a "secondary trigger" whenever an AA response sends a payment output to an address that happens to be a registered Autonomous Agent. If any one of these secondary AA calls bounces, the entire *primary* trigger's response (including all its already-computed state changes and payments to *other*, unrelated recipients) is rolled back and converted into a bounce. This mirrors the reported ERC677 callback issue: a single malicious "receiver" can unilaterally block a shared payout flow for everyone else.

### Finding Description
When a primary AA sends a response unit with payment outputs to several addresses in `sendUnit()`, every recipient address that is a registered AA is automatically fed a "secondary trigger" via `handleSecondaryTriggers()`: [1](#0-0) 

The results of all secondary triggers are awaited with `async.eachSeries`, and if **any** of them returns an error (i.e. the secondary AA bounces), the callback does not merely mark that one recipient as failed — it calls `revert()` on the whole primary chain: [2](#0-1) 

`revert()` discards *all* accumulated responses (`arrResponses.splice(0, arrResponses.length)`), rolls the database back to the savepoint taken before the primary trigger started (`ROLLBACK TO SAVEPOINT initial_balances`), clears the write batch, and then bounces the original trigger back to its sender: [3](#0-2) 

Because any address that is a registered AA is deterministically routed through this secondary-trigger mechanism (there is no way for the sending AA to opt out for a specific output, and any unprivileged user can permissionlessly post an `autonomous agent` definition unit to create such an address), a single crafted, "always-bouncing" AA can be inserted as one of the output recipients of a shared distribution/service AA. As long as that malicious AA keeps bouncing (e.g. by intentionally failing a required check, an oscript `bounce()`/error condition, or insufficient balance to cover its own `bounce_fees`), it forces the *entire* primary AA execution — including payouts meant for unrelated, legitimate recipients — to be discarded and converted into a bounce of the whole trigger.

This is directly analogous to the ERC677 `transferAndCallFrom` callback issue in the report: a designated "receiver" is given the power to make a downstream, shared operation fail for every other participant, instead of only failing for itself.

### Impact Explanation
Any Autonomous Agent that batches multiple payment recipients into a single response (e.g., referral/commission payouts, reward/fee distribution, lottery/auction settlement, multi-party splits where a recipient address is supplied by an untrusted party such as a trigger's `data`) can be permanently denied from ever completing that distribution if one of the recipients is (or is later replaced/pointed to) a maliciously crafted AA that always bounces. Because the whole primary response — not just the message to the bad recipient — is reverted, funds that were meant to reach legitimate users never leave the distributing AA (fund freezing for legitimate users), and every retry can be griefed the same way as long as the attacker keeps their AA in a bouncing state. This matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Reachable by any unprivileged party: defining a new AA is a normal, permissionless unit post, and getting that AA's address included among an existing distributing AA's payment outputs is common in typical AA designs (referral addresses, registered participants, user-specified recipients in trigger data). No special privilege, node cooperation, or network-level attack is required — only crafting an AA definition that deterministically fails/bounces and getting it registered as one of the output addresses of the victim AA's response.

### Recommendation
Consider not propagating a single secondary-AA bounce into an unconditional revert of the entire primary chain. Options include: isolating a secondary AA's failure to only its own share (already-computed messages to other addresses proceed, with the failed AA's fee/portion returned to the AA-of-origin instead of the whole chain reverting), or providing AA authors an explicit primitive to send "fire-and-forget" payments that do not trigger cascading reverts of the caller's own state changes when the target's secondary execution bounces.

### Proof of Concept
1. Attacker posts unit defining `MaliciousAA` whose logic always fails (e.g., a state formula that always throws, or a message set requiring more `bounce_fees` than it can ever pay).
2. Attacker interacts with `VictimAA`, a service AA that on some trigger distributes payments to multiple addresses in one response (e.g., `outputs: [{address: userA}, {address: userB}, {address: "{trigger.data.referrer}"}]`), and supplies `trigger.data.referrer = MaliciousAA_address`.
3. `VictimAA`'s response unit is composed and validated in `sendUnit()`; `handleSecondaryTriggers()` is invoked for `MaliciousAA` (aa_composer.js:1702-1741) alongside any other AA-addressed outputs.
4. `MaliciousAA` bounces (`onDone(objSecondaryUnit, bounce_message)` returns an error), triggering `async.eachSeries`'s error callback at aa_composer.js:1743-1749, which calls `revert()`.
5. `revert()` (aa_composer.js:1759-1783) discards `arrResponses`, rolls back to `SAVEPOINT initial_balances`, and bounces the entire trigger — `userA` and `userB` receive nothing even though their portions of `VictimAA`'s logic executed successfully before the `MaliciousAA` secondary trigger was invoked.
6. Repeating the same trigger with the same malicious referrer address reproduces the failure indefinitely, permanently denying `VictimAA`'s distribution to legitimate parties whenever the attacker's address is included.
