### Title
Griefing via pre-funded address blocking `CreateAccount`/`CreateAccountWithSeed` - (File: `programs/system/src/system_processor.rs`)

### Summary
The external report describes a front-running griefing pattern: an attacker observes a pending "create identity at address X" transaction and races it, causing the legitimate transaction to permanently revert due to an "already in use" check. The System Program's legacy `CreateAccount` / `CreateAccountWithSeed` instructions in agave contain the same bug class: they reject creation whenever the target account already holds `lamports > 0`, and any unprivileged user can pre-fund an arbitrary, publicly-derivable address (e.g. via `Transfer`, or simply by sending SOL to a known PDA/derived address) before the legitimate creation transaction lands, permanently blocking that specific address from ever being created via these instructions.

### Finding Description
`create_account` in `system_processor.rs` treats any positive lamport balance on the destination account as proof of prior use and unconditionally fails: [1](#0-0) 

Because destination addresses for `CreateAccount` (and especially `CreateAccountWithSeed`, whose `base`/`seed`/`owner` are public instruction fields visible in the mempool) are deterministic and computable off-chain, an unprivileged attacker who observes or predicts a pending creation transaction can submit a plain `Transfer` (or any other operation depositing lamports) to that exact address first. Once the address holds `lamports > 0`, every subsequent `CreateAccount`/`CreateAccountWithSeed` targeting it fails with `SystemError::AccountAlreadyInUse`, exactly mirroring the reported Solidity bug where a predictable `accountId` is squatted before the legitimate call lands.

`Address::create` confirms that `CreateAccountWithSeed`'s destination address is fully determined by attacker-visible/public inputs (`base`, `seed`, `owner`), not just a private-key-controlled destination signer: [2](#0-1) 

Notably, agave's own maintainers already recognized and fixed this exact griefing class by adding a dedicated `CreateAccountAllowPrefund` instruction, which explicitly skips the zero-lamport check and is documented as being for accounts that were "already had rent paid in whole or in part before creation": [3](#0-2) [4](#0-3) 

This is gated behind the `create_account_allow_prefund` feature flag: [5](#0-4) 

The corresponding regression test confirms the original (still-reachable) failure mode for pre-funded/populated destination accounts: [6](#0-5) [7](#0-6) 

The legacy `CreateAccount` and `CreateAccountWithSeed` instruction variants remain in the dispatch table unchanged and are still used by CLI tooling (nonce/stake account creation) and countless deployed on-chain programs that have not migrated to the prefund-tolerant variant: [8](#0-7) [9](#0-8) 

### Impact Explanation
Any unprivileged transaction sender can permanently deny address-creation for any legacy `CreateAccount`/`CreateAccountWithSeed` target whose address is predictable (derived PDAs, seed-based accounts such as nonce/stake accounts created via CLI, or any program that computes destination addresses deterministically off-chain and funds them with the legacy instruction). This is a pure griefing/DoS vector — no funds are stolen, but legitimate users' account-initialization flows can be repeatedly blocked with a single low-cost `Transfer`, matching the "Griefing" impact category of the original report. It does not itself cause consensus divergence or fund theft, so it falls short of a critical/high fund-loss or halt-class bug, but it is a concretely reachable, transaction-triggered logic flaw with real operational impact, which is why agave shipped `CreateAccountAllowPrefund` as a mitigation while leaving the vulnerable legacy path intact.

### Likelihood Explanation
High for any program/tooling still using the legacy `CreateAccount`/`CreateAccountWithSeed` path (e.g., CLI-driven nonce and stake account creation shown above) where the destination address can be computed by a third party before the creation transaction is confirmed. The attack requires no special privileges — only the ability to send a standard `Transfer` instruction to the predicted address before the victim's transaction lands, which is trivially achievable given Solana's public mempool/gossip of pending transactions.

### Recommendation
Where destination addresses are derivable ahead of time (seed-based or PDA-style accounts), callers/programs should use the prefund-tolerant `CreateAccountAllowPrefund` instruction (already implemented and gated by `create_account_allow_prefund`) instead of the legacy `CreateAccount`/`CreateAccountWithSeed`, and this feature should be fully activated cluster-wide. For programs building on top of the System Program, `create_account` helpers should be updated to prefer the prefund-allowing variant by default, and documentation for `CreateAccount`/`CreateAccountWithSeed` should explicitly warn integrators about the address pre-funding griefing vector so tooling (like the CLI nonce/stake creation paths) can be migrated.

### Proof of Concept
1. Attacker observes (or independently derives) the destination address `to` that a victim intends to use in a pending `CreateAccount` or `CreateAccountWithSeed` transaction (e.g., a `base`/`seed`/`owner`-derived nonce account address as constructed in `cli/src/nonce.rs`).
2. Attacker submits a standard `system_instruction::transfer` sending 1 lamport to `to`, and gets it included before the victim's transaction.
3. When the victim's `CreateAccount`/`CreateAccountWithSeed` transaction executes, `create_account` observes `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, exactly as exercised by the existing test `test_create_already_in_use`: [7](#0-6) 
4. The victim's account-creation intent is permanently blocked for that specific address unless they discover and switch to the `CreateAccountAllowPrefund` instruction path.

        address: &Pubkey,
        with_seed: Option<(&Pubkey, &str, &Pubkey)>,

        let base = if let Some((base, seed, owner)) = with_seed {
            // The conversion from `PubkeyError` to `InstructionError` through
            // num-traits is incorrect, but it's the existing behavior.
            let address_with_seed =
                Pubkey::create_with_seed(base, seed, owner).map_err(|e| e as u64)?;
            // re-derive the address, must match the supplied address
            if *address != address_with_seed {
                ic_msg!(
                    invoke_context,
                    "Create: address {} does not match derived address {}",
                    address,
                    address_with_seed
                );
                return Err(SystemError::AddressWithSeedMismatch.into());
            }
            Some(*base)
        } else {
            None
        };

        Ok(Self {
            address: *address,
            base,
        })
    }

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
