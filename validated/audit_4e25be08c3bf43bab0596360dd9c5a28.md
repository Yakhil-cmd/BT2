### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` never references `Shipit.github_teams`, `current_user`, or any `ApiClient`/session concept, and contains no authorization predicate at all. It resolves target `Commit` rows by SHA alone, globally across every stack in the database, and calls `create_status_from_github!` on each match, letting a signed webhook from one repository mutate commit status state belonging to an unrelated stack/repository that shares the same SHA.

### Finding Description
The broken binding: the code implicitly assumes `commit.sha == params.sha` implies `commit.stack.repository == payload['repository']`. This is false — `Commit#sha` is a global git SHA with no repository binding, and the `commits` table is only indexed on `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not constrained to a single stack per SHA.

Code path:
- `Shipit::WebhooksController#create` parses the raw payload and dispatches to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` only proves the payload was signed by the GitHub App belonging to `repository_owner` (the sender's own org/repo) — it does not restrict which Shipit stacks the payload may affect [2](#0-1) .
- `Handler` exposes a `stacks` helper that properly scopes by `Repository.from_github_repo_name(repository_name)` for other handlers [3](#0-2) , but `StatusHandler#process` does not use it:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

There is no `authorized?`, no `require_permission!`, no `stacks` scoping, and `deployable?` is never consulted here (it's used elsewhere purely for deploy gating, not for this write path) — confirming the "zero authorization predicate" claim. Grepping the class shows its only methods are `params` (schema) and `process`; no method with an authorization-related name exists.

Exploit flow: an attacker forks a public repository tracked by a victim Shipit stack (forks share identical commit SHAs with upstream because git history is copied verbatim). The attacker triggers (or has GitHub trigger) a genuinely signed `status` webhook from their own fork/repo for a SHA that is shared with the victim's tracked commit history. `verify_signature` passes because the signature is valid for the attacker's own repository owner. `StatusHandler#process` then finds the `Commit` row belonging to the *victim's* stack (same SHA, different stack_id) and calls `create_status_from_github!`, injecting attacker-controlled `state`/`description`/`context`/`target_url` into the victim's stack, which can flip `deployable?` (since `Commit#deployable?` depends on `success?`/`blocked?` derived from `Status` records created here) [5](#0-4)  and can trigger downstream `schedule_continuous_delivery` / merge automation [6](#0-5) .

Existing guards do not prevent this: `verify_signature` authenticates the sender's own org, not the target stack; `drop_unhandled_event` only filters by event type; `ExplicitParameters` schema only validates shape, not ownership; there is no model-level uniqueness constraint tying a SHA to a single repository.

### Impact Explanation
An attacker with no Shipit session, no API token, and no team membership can write fabricated CI/status records (and therefore influence deployability/blocking and continuous-delivery/merge automation) for a stack belonging to a completely different, unrelated tenant repository, by exploiting SHA collisions inherent to forked repositories. This is a cross-tenant write ("a payload for one repository mutating another's stack, commit ... task") and can lead to an unauthorized deploy/merge decision being influenced by forged status data — matching the Critical impact category.

### Likelihood Explanation
Preconditions: the victim's Shipit instance must track a repository that has public forks (extremely common for open-source projects), and the attacker must own/control a fork or repo where the same GitHub App is installed (already assumed in scope as an attacker capability — "emit webhooks from a repository they own"). No secrets, no privileged role, and no social engineering are required; the attacker only needs a shared commit SHA, which is trivially obtainable from any public fork or by cherry-picking/copying a target commit's exact tree/parent/author/timestamp. The attack is repeatable against any commit whose SHA is known and matches across stacks.

### Recommendation
Scope the SHA lookup to the webhook's originating repository, mirroring the pattern already used by `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This binds the mutation to `Repository.from_github_repo_name(repository_name)` derived from the verified payload, closing the cross-tenant write.

### Proof of Concept

# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "StatusHandler#process has no authorization predicate" do
          method_names = StatusHandler.instance_methods(false) + StatusHandler.private_instance_methods(false)
          refute method_names.any? { |m| m.to_s =~ /authoriz|permission|require_permission/ }
        end

        test "cross-repository SHA collision writes a status to an unrelated stack" do
          victim_stack = shipit_stacks(:shipit) # tracks "shopify/shipit-engine"
          attacker_stack = Stack.create!(repository: Repository.create!(owner: 'attacker', name: 'evil-fork'))

          shared_sha = 'a' * 40
          victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'shared')
          attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'shared')

          payload = {
            'sha' => shared_sha, 'state' => 'success',
            'repository' => { 'full_name' => 'attacker/evil-fork', 'owner' => { 'login' => 'attacker' } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.call(payload)
          end
        end
      end
    end
  end
end
```
This demonstrates the class has no authorization method, and that a status attributable to the attacker's own (verified) repository is written onto the victim's unrelated stack commit purely via SHA equality.
