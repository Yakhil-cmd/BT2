This confirms the binding-mismatch bug class in a multi-organization Shipit deployment.

### Title
Webhook signature verification authenticates an organization but downstream handlers act on a different, attacker-supplied repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/webhook secret to verify against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [1](#0-0) . Once the HMAC is validated with that organization's secret via `Shipit.github(organization: repository_owner).verify_webhook_signature` [2](#0-1) , the full raw JSON body is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Every handler then resolves the target `Stack`/`Repository` using a *different* field of the same payload: `payload.dig('repository', 'full_name')` [4](#0-3)  (used identically in `PushHandler`, `PullRequest::*Handler`, etc. [5](#0-4) [6](#0-5) ). Nothing in the code enforces that `repository.owner.login` (used to select the signing secret) is consistent with `repository.full_name` (used to select the stack/repo that gets mutated) — both are attacker-controlled JSON fields inside the same signed body.

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` via `Shipit.github(organization:)` / `github_app_config` [7](#0-6) . `GitHubApp#verify_webhook_signature` only checks that the HMAC-SHA1 of the raw body matches using that single organization's secret [8](#0-7) ; it performs no validation of the payload's internal consistency.

The binding that should hold is:
`organization whose secret validated the signature == organization that owns the repository being mutated`

In practice the code implements:
`organization used to select the secret (repository.owner.login) != repository used to look up/mutate the Stack (repository.full_name)`

Since `repository.owner.login` and `repository.full_name` are two independent JSON fields inside the same HTTP body, an entity that legitimately controls one organization's `webhook_secret` (e.g., an admin of Organization A in a Shipit instance that also hosts Organization B) can craft a POST to `/github/webhooks` with:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
computing `X-Hub-Signature` with Organization A's `webhook_secret`. `verify_signature` will select `Shipit.github(organization: "orgA")` (because `repository_owner` == "orgA") and the signature will validate. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` [9](#0-8)  and calls `stack.sync_github(expected_head_sha: params.after)` on Organization B's stack [10](#0-9)  — a write against a repository/organization the attacker's credentials were never authorized for.

The same disconnect exists for `pull_request` events (`ClosedHandler`, `OpenedHandler`, `Labeled/UnlabeledHandler`), which archive/unarchive/create review stacks based on `params.repository.full_name` [11](#0-10) , and for `status`/`check_suite` handlers that update commit statuses/check runs used to gate merges and deploys.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope. An attacker who is a legitimate admin/holder of one organization's webhook secret in a multi-tenant Shipit deployment can forge state-changing events (push syncs, review-stack archive/unarchive, commit status writes) against a repository/stack belonging to a completely different organization they have no authorization over — a cross-repository/cross-tenant write. Depending on downstream logic (status-driven merge gating, `sync_github`, review-stack provisioning/deprovisioning), this can materialize as unauthorized stack state changes, forged commit statuses, or triggering syncs/rollback-adjacent stack mutations on another organization's repository, matching the "cross-repository writes" / "unauthorized deploy, rollback" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to already control a valid `webhook_secret` for at least one organization configured in the multi-org Shipit deployment (i.e., they are a GitHub org admin/owner for that org, which is how webhook secrets are set and viewed). No Shipit session, `ApiClient` token, or GitHub App private key is needed — only knowledge of one org's webhook shared secret, which the rules treat as a valid unprivileged-attacker capability distinct from repository-write access on the target org. The attack requires only crafting one HTTP POST with a correctly computed HMAC; multi-organization webhook configurations (`test/dummy/config/secrets_double_github_app.yml`) confirm this deployment mode is explicitly supported.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), after signature verification, assert that the resolved `repository_owner` used to select the webhook secret matches the owner segment of `payload.dig('repository', 'full_name')` before dispatching to handlers; reject the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` strictly from the same organization context that authenticated the request rather than independently trusting `repository.full_name`.

### Proof of Concept
1. Deploy Shipit with two organizations configured, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), including Organization A ("orgA", attacker-controlled) and Organization B ("orgB", victim, hosting a tracked `Stack`/`Repository`).
2. Attacker builds a JSON body:
```json
{"ref":"refs/heads/main","after":"<sha>","repository":{"owner":{"login":"orgA"},"full_name":"orgB/target-repo"}}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and sends `POST /github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "orgA"`, calls `Shipit.github(organization: "orgA").verify_webhook_signature(...)`, which succeeds because the HMAC was computed with orgA's real secret [2](#0-1) .
5. `PushHandler` resolves `Repository.from_github_repo_name("orgb/target-repo")` and runs `stack.sync_github` for Organization B's stack even though the request was never authenticated against Organization B's secret [10](#0-9) [12](#0-11) .

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
