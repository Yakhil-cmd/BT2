### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in status webhook - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` writes a `Status` onto every `Commit` row in the database that matches the `sha` given in a `status` webhook payload, without checking that the payload's `repository` matches the `Stack`/`Repository` that owns that commit. Since the webhook signature is only verified against the *organization named in the attacker's own payload* (which the attacker controls), an attacker who can produce a colliding sha (fork, shared base commit, or identical patch) can inject a forged `success` status onto a victim `Commit`, causing `MergeRequest#all_status_checks_passed?` to return true and `ProcessMergeRequestsJob` to call `stack.github_api.merge_pull_request` for a repository the attacker never authenticated against.

### Finding Description
The broken binding, stated explicitly: the request is authenticated as `organization = payload.dig('repository','owner','login')` (attacker-controlled, verified via `Shipit.github(organization: repository_owner).verify_webhook_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30`), but the write target is `commit.stack.organization` for *every* `Commit` whose `sha` matches, taken from `Commit.where(sha: params.sha)` in `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`organization = payload.repository.owner.login` never equals `commit.stack.organization` in general — no code path enforces that equality here.

Compare with `Shipit::Webhooks::Handlers::PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17), which correctly scopes writes through `stacks`, itself derived from `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38). `StatusHandler` is defined on the same `Handler` base class and has the same `stacks`/`repository_name` helpers available, but never calls them — it queries the global `Commit` table directly by `sha` only.

Exploit flow:
1. Attacker forks or otherwise obtains a commit whose sha is identical to the victim's `MergeRequest#head` sha (trivial via fork+identical patch, or shared history before divergence).
2. Attacker's own GitHub repository (which they administer, with its own valid webhook secret/App installation) emits a real, correctly-signed `status` event with `state: success`, `context` equal to one of the victim stack's `merge.require` contexts, and `sha` equal to the victim's head sha.
3. `WebhooksController#verify_signature` verifies this using `Shipit.github(organization: repository_owner)` where `repository_owner` is the attacker's own org — this succeeds because the attacker legitimately owns that org/app installation.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim's `Commit` row (same sha, different stack/organization), and calls `commit.create_status_from_github!(params)`, creating a `Status` scoped to the victim's `stack_id` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`).
5. `Status#schedule_continuous_delivery` / commit state transition enqueues `ProcessMergeRequestsJob` (see `test/models/commits_test.rb:763-777`), which calls `merge_request.all_status_checks_passed?` → `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` — now true because of the forged status.
6. `ProcessMergeRequestsJob#perform` calls `merge_request.merge!`, which calls `stack.github_api.merge_pull_request(...)` for the **victim's** repository (app/models/shipit/merge_request.rb:164-176), authorized using Shipit's own stored credentials for the victim organization — despite the attacker never proving control over that organization's webhook secret.

Existing guards do not prevent this: `verify_signature` only proves the request came from *some* organization whose webhook secret matches — it says nothing about which `Commit`/`Stack` the payload is allowed to affect. `ExplicitParameters` schema on `StatusHandler` only validates types (`sha`, `state`, etc.), not repository ownership. No repository/stack scoping is applied anywhere in `StatusHandler#process`.

### Impact Explanation
An attacker can inject an arbitrary passing (or failing) CI status onto any `Commit` row in the Shipit installation, for any stack, as long as they can reproduce the sha of the target commit and know one of its `merge.require`/`ci.require` contexts (visible in the victim's public `shipit.yml`/PR checks). The most severe consequence is triggering `stack.github_api.merge_pull_request` — an unauthorized merge — on a repository/organization the attacker does not control, using Shipit's own stored GitHub App credentials for that victim organization. This is a genuine unauthorized-merge / cross-tenant write vulnerability (matches the "Critical: a payload for one repository mutating another's stack/commit... an unauthorized merge" category), and is repeatable against any victim stack/commit sha the attacker can reproduce.

### Likelihood Explanation
Preconditions: (1) attacker controls any GitHub repository with a legitimately configured webhook (their own org/app installation — no victim secret needed); (2) a victim `MergeRequest` is `pending` with a head commit lacking one of the stack's required status contexts; (3) attacker can produce a commit with the identical sha (forking a public repo and reusing/replaying the same tree+parent+commit metadata reproduces the same sha exactly, or reusing a shared ancestor sha before divergence — both realistic for public open-source Shipit-managed repos). No Shipit credentials, sessions, or `Shipit.github_teams` membership are required. Cost is low: one crafted webhook POST from an attacker-owned repository.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to only commits belonging to stacks under the reporting repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently look up via `Repository.from_github_repo_name(repository_name)` (already available via the `stacks`/`repository_name` helpers on `Handler`) before matching by sha, mirroring the pattern used in `PushHandler#process` and `CheckSuiteHandler`.
