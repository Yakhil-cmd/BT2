### Title
Rounding of `earned_headers_commission_share` distribution to zero causes permanent loss of headers commission - (File: `headers_commission.js`)

### Summary
`headers_commission.js` splits a payer unit's `headers_commission` among multiple `earned_headers_commission_recipients` using `Math.round(full_amount * share / 100.0)` for each recipient independently, with no error-carry-forward. When a recipient's configured percentage share is small relative to the payer's `headers_commission`, the per-recipient rounded amount truncates to `0`, and that fraction of the commission is never inserted into `headers_commission_contributions`/`headers_commission_outputs`. The bytes are silently lost rather than distributed, directly mirroring the `LQTYStaking.increaseF_Collateral` rounding-to-zero bug where `_collFee.mul(DECIMAL_PRECISION).div(totalLQTYStaked)` truncates to zero and the fee is never credited to `F_Collateral`.

### Finding Description
Any unit author can (via `composer.js`) freely define `earned_headers_commission_recipients`, an array of `{address, earned_headers_commission_share}` entries whose shares must sum to 100 (enforced in `validation.js`'s `validateHeadersCommissionRecipients`) [1](#0-0) . This structure is attached to a normal, unprivileged unit — no special privilege is required to set it, and `composer.js` even auto-creates one when multiple authors sign a unit [2](#0-1) .

Later, when the main chain stabilizes, `calcHeadersCommissions` in `headers_commission.js` distributes the `headers_commission` earned by a unit to the configured recipients:

```
var share = objUnit.assocEarnedHeadersCommissionRecipients[address];
var amount = Math.round(full_amount * share / 100.0);
arrValuesRAM.push("('"+payer_unit+"', '"+address+"', "+amount+")");
``` [3](#0-2) 

and, for the non-`bFaster` SQL comparison path, the same rounding is applied a second time:
```
var amount = (row.earned_headers_commission_share === 100) 
    ? full_amount 
    : Math.round(full_amount * row.earned_headers_commission_share / 100.0);
``` [4](#0-3) 

The MySQL-only fast path uses the same unguarded rounding formula directly in SQL:
```
ROUND(punits.headers_commission*earned_headers_commission_share/100.0) AS hc
``` [5](#0-4) 

`headers_commission` values are typically small (tens of bytes, derived from unit header size), so if an author defines multiple recipients with small percentage shares (e.g. splitting 100% across several addresses at 1–5% each), `full_amount * share / 100.0` easily evaluates below `0.5` and rounds to `0` for those recipients. There is no analogous "remainder tracking" variable (like `lastLQTYError` in the LQTYStaking mitigation) to carry the truncated fraction forward or to the next distribution — the rounded-away commission is simply never written to `headers_commission_contributions`, and consequently never appears in `headers_commission_outputs` (built by `SUM(amount)` over these contributions) [6](#0-5) . The bytes that were nominally the payer's `headers_commission` for that unit disappear from circulation for any recipient — they are neither credited to the intended recipient nor to anyone else, and unlike a legitimate spend they can never be recovered.

This is structurally identical to the reported LQTYStaking issue: a fee is computed and multiplied by a fractional share/ratio, divided/rounded down, and if the result is below the rounding threshold, the entire amount for that recipient is lost with no compensating accumulator.

### Impact Explanation
Because `headers_commission` for typical units is small (dozens of bytes) and shares can be freely chosen down to 1% granularity by the paying/child unit author, an attacker (or any legitimate multi-author group) can trivially configure `earned_headers_commission_recipients` shares such that most or all of the commission attributable to a unit rounds down to zero for every recipient. This causes deterministic, permanent loss of protocol-native currency (bytes) that should have been paid out as commission — a supply-shrinkage bug reachable by any unprivileged unit poster who defines multiple headers-commission recipients, without requiring any counterparty cooperation, hub/witness collusion, or privileged access.

### Likelihood Explanation
High likelihood: `earned_headers_commission_recipients` is a standard, publicly documented and user-controllable unit field (required whenever a unit has multiple authors, and optional otherwise) [7](#0-6) . Choosing small percentage shares (e.g., splitting 100% into several ~1-10% shares) is trivial and requires no special conditions beyond composing a normal unit — no race condition, no reliance on other actors, and it is deterministic every time the affected unit wins headers commission from a descendant.

### Recommendation
Apply the same error-carrying technique recommended for the LQTYStaking finding: track a `last_headers_commission_error` (per payer_unit or globally) analogous to `lastLQTYError`, so that the rounding remainder from `Math.round(full_amount * share / 100.0)` is added back into the numerator on the next distribution instead of being discarded, or ensure that the sum of rounded per-recipient amounts is reconciled against `full_amount` (e.g., allocate any residual to the last recipient) before insertion into `headers_commission_contributions`. Apply the identical fix to the raw SQL `ROUND(...)` computation in the MySQL fast path.

### Proof of Concept
1. Compose and post a unit `U1` (via `composer.js`) with two authors, `A` and `B`, and set `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 3}, {address: B, earned_headers_commission_share: 97}]` — this satisfies `validateHeadersCommissionRecipients`'s "sum to 100" rule.
2. Let `U1` become a payer unit with a small `headers_commission` (e.g., `headers_commission = 15`, a realistic size-based value for a small unit).
3. When a descendant unit wins the headers commission from `U1`, `calcHeadersCommissions` computes, for recipient `A`: `Math.round(15 * 3 / 100.0) = Math.round(0.45) = 0`.
4. No row is inserted into `headers_commission_contributions` for `A`, and the `0.45` bytes destined for `A` are permanently unrecoverable — not credited to `A`, `B`, or anyone else, and not tracked by any error-accumulator variable in `headers_commission.js`.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
