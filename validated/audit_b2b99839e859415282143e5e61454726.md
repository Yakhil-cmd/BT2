### Title
Asset issuer can permanently freeze user funds in AAs by manipulating `spender_attested` attestor lists on a shared payment message - ([File: validation.js])

### Summary
An asset issuer who defines an asset with `spender_attested: true` controls the list of attestors that determine which addresses are allowed to receive that asset. When an autonomous agent (AA) composes a single `payment` message that pays out to multiple addresses in one message (e.g. a withdrawal to the user together with a fee/commission output to another party), validation requires that **every** output address in that message be attested, or the whole message — and therefore the whole unit/AA response — is rejected. An issuer can exploit this by never attesting (or later de-attesting) one of the co-located recipient addresses, causing all AA responses that bundle that address with a legitimate user withdrawal to bounce forever, freezing the user's funds inside the AA. This mirrors the Putty `withdraw()` bug where a poisoned fee-recipient transfer caused the entire withdrawal transaction to revert, permanently locking user funds.

### Finding Description
`validatePaymentInputsAndOutputs` in `validation.js` collects all output addresses in a payment message into `arrOutputAddresses` [1](#0-0) . Later, if the asset is `spender_attested`, the code checks `storage.filterAttestedAddresses` against the **entire** `arrOutputAddresses` list for the message, and fails the whole message if not all output addresses are attested: [2](#0-1) 

This is an all-or-nothing check scoped to the full set of output addresses within one payment message, not per-output. Consequently, if an AA (very commonly seen in these oscript patterns, e.g. `sell_asset_for_bytes.oscript`, `order_book_exchange.oscript`, `a_bank_without_percent.oscript`) sends a `spender_attested` asset in a single payment message with multiple outputs — for example, paying the withdrawing user and simultaneously paying a fee/commission/DAO address in the same message — then if the fee/commission address is not (or is no longer) attested by the issuer's attestor list, the *entire* message fails validation with `"some output addresses are not attested"`, which bounces the whole AA response, including the legitimate user output.

The issuer fully controls the attestor list via `asset_attestors` messages (`storage.loadAssetWithListOfAttestedAuthors` / `readAsset`'s `addAttestorsIfNecessary` reads the latest published attestor list for the asset) [3](#0-2) . An issuer who initially attests a fee-collection address (to make the AA usable) can later publish an updated attestor list that drops that address, or simply never attest an address baked into shared AA logic, thereby weaponizing the mandatory-attestation-for-all-outputs rule to bounce every future combined payment message and lock any user output bundled with it.

### Impact Explanation
Because AA execution is atomic (a bounced message discards the entire response and rolls back state changes), any AA that combines a spender-attested-asset payout to a user with a payout to another fixed address (fee collector, admin, DAO, counterparty) in the same `payment` message is vulnerable: the asset issuer can unilaterally and permanently prevent any such AA response from ever succeeding, freezing user assets/funds held by the AA indefinitely. This is analogous to the "Assets not at direct risk directly, but availability of the protocol/funds recovery could be permanently impacted" medium/high classification used for the referenced Putty finding — funds become stuck with no recovery path, since the issuer, not the AA author or the user, controls the attestation gate.

### Likelihood Explanation
Requires the AA to use a `spender_attested` asset and to combine a user-facing payout with a payout to another fixed address within the same payment message — a common and natural pattern for AAs that need to charge a fee or split proceeds (seen repeatedly in the sample oscripts in this codebase). It also requires the issuer to be adversarial or to change attestation policy after the AA/asset is adopted, similar to the "owner sets fee recipient to a griefing address" precondition in the original report. Likelihood is therefore conditional on external assumptions (a malicious/negligent issuer) but does not require any special privilege beyond normal asset-issuer capabilities that are explicitly permitted by the protocol.

### Recommendation
- Avoid all-or-nothing validation for `spender_attested` assets across multiple recipients in a single message; if per-output attestation checks are infeasible, document/require AA authors to send `spender_attested` assets to a single recipient per payment message so an issuer cannot hold hostage unrelated outputs.
- Consider decoupling "fee"/secondary-recipient outputs from the user's primary withdrawal output into separate payment messages (or separate AA responses/state-based withdrawal patterns), so failure of the attestation check for one output does not block the other, mirroring the recommended "pull payment" pattern from the original report.
- Consider allowing partial validation/rejection of only the specific unattested output rather than bouncing the entire message, if backward compatible with the protocol's atomicity guarantees.

### Proof of Concept
1. Issuer defines asset `X` with `spender_attested: true` and initially attests both `UserAddr` and `FeeAddr`.
2. An AA is deployed whose payout logic, in one `payment` message, sends asset `X` to `trigger.address` (the withdrawing user) and simultaneously to `FeeAddr` (fee collector), e.g. as in the multi-output patterns seen in `order_book_exchange.oscript` / `things_registry_and_marketplace.oscript` combined-output style messages [4](#0-3) .
3. Users deposit/trade normally; AA holds balances of asset `X` for withdrawal.
4. Issuer publishes a new `asset_attestors` list that no longer includes `FeeAddr` (or never attested it in the first place).
5. Any subsequent AA trigger that would produce the combined payment message (user withdrawal + fee to `FeeAddr`) fails validation at `validatePaymentInputsAndOutputs` with `"some output addresses are not attested"` [2](#0-1) , causing the AA response to bounce.
6. Because AA state changes are atomic and rolled back on bounce, the user can never withdraw their `X` balance through this code path, and funds remain stuck in the AA indefinitely — with no alternative single-output path for retrieval.
