### Title
CCMenu token is not stack-scoped and `Api::CCMenuController#stack` bypasses the `stacks` scoping helper, allowing any CCMenu token to read any stack - (File: `app/controllers/shipit/ccmenu_url_controller.rb`, `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `read:stack` permission but never sets `stack:`, so `stack_id` is `nil` on the token. Independently, `Api::CCMenuController` overrides the base `stack` method to call `Stack.from_param!(params[:stack_id])` directly instead of using `BaseController#stacks`/`#stack`, which is the only place that enforces `current_api_client.stack_id`. Either defect alone is enough for the same token to read every stack in the installation.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` (the token should only ever resolve the one stack it was minted for). Tracing the code:

- `CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) creates/finds an `ApiClient` via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. `stack:` is never passed, so `ApiClient#stack_id` is `nil` for this client (`app/models/shipit/api_client.rb:8`).
- `Api::CCMenuController#authenticate_api_client` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) does `ApiClient.authenticate(params[:token])`, which only verifies the signed id (`ApiClient.authenticate`, `app/models/shipit/api_client.rb:24-27`) - it never checks `stack_id`.
- `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) overrides `BaseController#stack`, which normally would scope through `stacks` (`app/controllers/shipit/api/base_controller.rb:74-80`, which does `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`). Instead, `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly, entirely bypassing the `stacks` scoping helper.
- `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`) only calls `check_permissions!` (`app/models/shipit/api_client.rb:38-45`), which checks the string `"read:stack"` is in `permissions` - it never checks stack identity.

So two independent breaks compound: (1) the minted client has no `stack_id` at all, and (2) even if it did, `CCMenuController#stack` doesn't consult it. The attacker's exact request: authenticate a normal Shipit session, `GET /stacks/:A/cc_menu_url` to obtain `ccmenu_url` containing `client.authentication_token`. That URL is later exposed publicly (its designed purpose - a public CI dashboard badge). Anyone in possession of that URL can then request `GET /api_endpoint(...)/stacks/:B/cc_menu.xml?token=<token>` for any other stack `B` and get its `show` XML (deploy status, branch, last build info) - full stack read.

None of the listed guards stop this: `require_permission!` only checks the permission string, not stack binding; `stacks`/`current_api_client.stack_id` scoping exists in the codebase but is not used by `CCMenuController#stack`; there is no model validation tying the token to a specific stack.

### Impact Explanation
Any holder of a single leaked CCMenu URL (which is explicitly designed to be embedded in third-party/public CI dashboards) can read the deploy/build status of every stack in the Shipit installation, not just the one it was generated for. This is unauthenticated/unauthorized read of stack state across tenants - matches the "High: unauthenticated read of stack state, task streams or deploy output" category. The blast radius is the entire multi-tenant installation (every stack, every repository) from one leaked URL, repeatable indefinitely since the token has no expiry and no revocation tied to stack scope.

### Likelihood Explanation
Preconditions are trivial and match the intended workflow: the attacker only needs a normal Shipit browser session (any operator, or a phished one) to visit the standard `GET /stacks/:id/cc_menu_url` endpoint - no privileged role, no secrets, no GitHub token needed. CCMenu URLs are explicitly meant to be pasted into external dashboards (e.g., CCTray-compatible tools), so leakage into a public/less-trusted context is the expected and documented use case, not a hypothetical. Exploiting it is a single unauthenticated HTTP GET with a different `stack_id` and the same token.

### Recommendation
- In `CCMenuUrlController#client`, mint the `ApiClient` bound to the specific stack: `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(...)`.
- In `Api::CCMenuController`, remove the local `stack` override and use the inherited `BaseController#stack`/`#stacks` so `current_api_client.stack_id` scoping is enforced, or explicitly assert `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a CCMenu token for stack A cannot be used to read stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: "main")

  # Simulate CCMenuUrlController#client: token minted with no stack scoping
  client = ApiClient.create!(creator: @user, name: 'CCMenu Client', permissions: %w[read:stack])
  token = client.authentication_token

  get :show, params: { stack_id: stack_b.to_param, token: token }

  assert_response :ok
  assert_payload 'name', stack_b.to_param
  # Demonstrates: current_api_client.stack_id (nil) == stack.id (stack_b.id) is falsely treated as authorized
  # Assert the broken binding explicitly:
  refute_equal client.stack_id, stack_b.id
end
```
This demonstrates that a token whose `stack_id` does not equal the requested stack's id (indeed, `stack_id` is `nil`) is still accepted and returns stack B's data, proving the binding `current_api_client.stack_id == stack.id` is not enforced.
