### Title
Cross-organization/repository forgery of commit statuses via webhook signature verification not binding to the affected repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary

### Finding Description
The reported bug class is a *trust-binding mismatch*: a value that is verified/authorized does not cover the value that is actually acted upon. In VaultV2 this was "assets synced" vs "assets actually used to compute shares." In Shipit-engine the analogous binding break is: **the organization whose webhook secret authenticated the request** vs **the repository/commit that the handler actually mutates**.

`WebhooksController#verify_signature` selects which `GithubApp` (and therefore which `webhook_secret`) to verify the HMAC signature against using a field pulled straight out of the *unverified* JSON body: [1](#0-0) [2](#0-1) 

Once the signature check passes for that organization, the raw payload is handed unmodified to every registered handler: [3](#0-2) 

Crucially, `StatusHandler` — which creates a GitHub CI status on a `Commit` — never checks the `repository` field at all; it resolves the target purely by commit SHA, globally, across every stack/repository hosted by the Shipit instance: [4](#0-3) 

Compare this to `PushHandler`/base `Handler`, which *do* scope by repository, but via a **different** payload field (`repository.full_name`) than the one used for signature routing (`repository.owner.login` / `organization.login`): [5](#0-4) [6](#0-5) 

So the equality that should hold but doesn't is:

`organization that produced a verifiable signature == organization/repository whose data the handler mutates`

Because `verify_signature` only proves "this payload was signed by *some* onboarded organization's secret," and `StatusHandler` performs no repository-scoping check whatsoever, any organization onboarded to a shared/multi-tenant Shipit instance can send a validly-signed `status` webhook (signed with *its own* legitimate `webhook_secret`) that targets a commit SHA belonging to a completely different organization's repository/stack.

### Impact Explanation
CI status (`ci.require`, `ci.blocking`) is used by Shipit to gate deploys and merges (see `README.md` CI section and `Stack`/merge-queue logic). An attacker who legitimately controls one onboarded GitHub organization (and thus can trigger a validly-signed webhook against Shipit) can forge a `status` event for an arbitrary commit SHA belonging to a *victim* organization's repository, setting `state: success` for a required status context. This can satisfy `ci.require` checks the attacker has no authorization over, enabling an **unauthorized deploy** of a victim stack — a cross-repository write outside the attacker's own scope, without ever obtaining write access to the victim repository, an `ApiClient` token, or the victim's `webhook_secret`.

### Likelihood Explanation
Exploitation only requires the attacker to control one legitimate GitHub organization/repository already onboarded onto the same (multi-tenant) Shipit instance — a materially lower privilege bar than compromising the victim's repo or webhook secret. The forged request is a single, deterministically-signed HTTP POST to `/webhooks` with `X-Github-Event: status`; no race condition, timing, or MEV competition is required, unlike the referenced `realizeLoss` fix window in the source report.

### Recommendation
`StatusHandler` (and any other handler that does not derive its target strictly from `repository.full_name` scoped to `Repository.from_github_repo_name`) must validate that the commit/stack being mutated belongs to the same repository identified by the field used in `verify_signature`. More generally, `WebhooksController#verify_signature` should bind the verified organization to the specific `repository.full_name` in the same payload (e.g., re-derive and cross-check `repository.owner.login` against `repository.full_name`'s owner segment, and require handlers to scope all lookups — including `StatusHandler`'s `Commit.where(sha:)` — through `Repository`/`Stack` ownership) so that the entity that authenticated the request is exactly the entity whose data can be written.

### Proof of Concept
1. Attacker onboards (or already administers) organization `attacker-org` on the shared Shipit instance, giving them a valid `webhook_secret` for `attacker-org` via `Shipit.github(organization: 'attacker-org')`.
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim-org/victim-repo commit sha>",
  "state": "success",
  "context": "required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker signs it with `attacker-org`'s `webhook_secret` (HMAC-SHA1) and POSTs to `/webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GithubApp`, and the signature matches → request passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, which matches the victim's commit (no repository check), creating/overwriting a `success` status for `required-check` on the victim's commit — potentially unblocking `ci.require` gates and enabling an unauthorized deploy of `victim-org/victim-repo`.

Note: I was unable to fully inspect `lib/shipit.rb`'s `Shipit.github`/multi-organization app registry due to running out of tool iterations, so I could not conclusively confirm from code whether the deployed configuration always supports multiple organizations with distinct `webhook_secret`s versus a single global secret; the vulnerability is contingent on a multi-tenant/multi-organization Shipit deployment (which the `organization:` keyword argument and per-organization `GithubApp` instantiation in `lib/shipit/github_app.rb` strongly suggest is a supported configuration). If confirmation of this configuration detail is needed, a Devin session with full repository access should inspect `lib/shipit.rb` and any `config/initializers/shipit.rb` examples.
