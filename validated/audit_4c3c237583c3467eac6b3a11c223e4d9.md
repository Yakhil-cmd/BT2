## Analysis

This is a case where I can confirm a valid analog. Here's the writeup.

### Title
Stack-scoped API tokens can read the deploy status of any stack via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` may only ever resolve `stack` to the single `Stack` it was issued for. `Shipit::Api::CCMenuController` overrides that `stack` accessor and resolves the stack directly from the URL parameter instead, completely bypassing the scoping check. A token that is authorized for exactly one stack (e.g. `read:stack` scoped to `shipit`) can therefore be replayed against `/stacks/:stack_id/ccmenu.xml` for any other stack to read its deploy/task state.

### Finding Description
`BaseController` defines the trust binding between the authenticated `ApiClient` and the stacks it is allowed to touch: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped, and `stack` (used by every other API controller such as `DeploysController`, `RollbacksController`, `StacksController`) resolves through that scoped relation, so `from_param!` can never return a stack outside the token's `stack_id`.

`CCMenuController`, however, re-defines `stack` to bypass this relation entirely: [2](#0-1) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(operation, scope)`, which checks the `permissions` array on the token but never checks `stack_id`: [3](#0-2) [4](#0-3) 

So the equality that should hold — `stack a token authorizes == stack a token touches` — is broken specifically in this controller: the token is verified to carry the `read:stack` permission and to be scoped to stack `A` (per its `stack_id` column, see fixture `here_come_the_walrus` scoped to `shipit`), but the `stack_id` URL parameter it "touches" is never checked against that scope, letting it act on stack `B`.

### Impact Explanation
Any holder of a stack-scoped API token (with the minimal `read:stack` permission, intended to only view CCMenu status for one stack) can use it to enumerate/read the CCMenu deploy status — including last build status, activity, and label — of every other stack in the Shipit instance. This is an unauthorized cross-stack read of stack/deploy state, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" (here more precisely: read of state outside the token's authorized scope).

### Likelihood Explanation
Any legitimate, low-privilege, single-stack-scoped API token (a common configuration pattern, e.g. for CI dashboards) is sufficient; no additional secret or privilege is required beyond a token that was already issued for a completely unrelated purpose scoped to a different stack. This is a straightforward parameter substitution attack (`stack_id` in the URL) against an authenticated, but narrowly-scoped, credential.

### Recommendation
Remove the `stack` override in `CCMenuController` and let it inherit `BaseController#stack`/`#stacks`, so CCMenu status lookups are constrained the same way as every other API endpoint (`stacks.from_param!(params[:stack_id])`), enforcing that the resolved stack is always within `current_api_client.stack_id` when the token is scoped.

### Proof of Concept
1. Issue (or obtain) an `ApiClient` scoped to `stack_id = shipit` with permission `read:stack` (e.g. fixture `here_come_the_walrus`).
2. Authenticate with that token's `authentication_token` via HTTP Basic auth against `GET /api/stacks/:other_stack_id/ccmenu.xml`, where `other_stack_id` is any stack the token was never granted access to.
3. Because `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly (ignoring `current_api_client.stack_id`), the request succeeds and returns the CCMenu XML (`lastBuildStatus`, `activity`, etc.) for the unrelated stack, whereas the equivalent request against `DeploysController#index` for the same stack would be scoped/blocked.
