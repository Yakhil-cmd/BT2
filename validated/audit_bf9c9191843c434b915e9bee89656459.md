### Title

Caller-selected flash-position receiver can execute unauthorized wallet transfers beneath the caller’s authorization - (File: `contracts/controller/src/strategies/flash_position.rs`)

### Summary

`flash_position` accepts a caller-selected Wasm contract as `receiver` and invokes its `execute_flash_position` callback while the submitted caller authorization is active. [1](#0-0)  Because the receiver is arbitrary production code reached through a public, unprivileged entrypoint, it can request additional token transfers from `initiator` during the callback. [2](#0-1) 

### Finding Description

`process_flash_position` first authorizes `caller`, then permits any Wasm receiver other than the controller and pool; it does not require the receiver to be trusted, listed, or restricted to the flash-position callback. [3](#0-2) [4](#0-3) 

The controller mints the requested debt, transfers the measured proceeds to that receiver, and then invokes `execute_flash_position` with `caller` exposed as `initiator`. [5](#0-4) [6](#0-5)  A malicious receiver can therefore call an unrelated token’s `transfer(initiator, attacker, amount)` while executing beneath the caller’s `flash_position` authorization; transaction simulation records that call as an authorization child, and signing the complete tree permits it. [2](#0-1) 

The receiver only has to return enough declared collateral to satisfy the configured minimum and leave the account solvent, so the malicious transfer is not bounded by the flash-position amount or by the declared markets. [7](#0-6) [8](#0-7) 

### Impact Explanation

A malicious transaction builder can cause theft of unrelated user tokens held outside the lending protocol, not merely the flash-positioned asset. [9](#0-8)  The callback can also satisfy the operation legitimately afterward, leaving the victim with a solvent position and therefore no protocol-level indication that the unrelated wallet transfer was unintended. [7](#0-6) 

### Likelihood Explanation

The attack requires the victim to submit a prepared transaction whose simulated authorization tree includes the malicious nested transfer. [9](#0-8)  This is plausible when a wallet or integrator presents `receiver`, `data`, or nested authorization details insufficiently, but a wallet that clearly displays and rejects unexpected child transfers can prevent it. [10](#0-9) 

### Recommendation

Do not invoke caller-selected arbitrary contracts while the `caller` authorization is active; restrict `receiver` to protocol-approved implementations or a fixed trusted callback adapter. [4](#0-3)  If arbitrary composability is retained, transaction preparation must reject any authorization tree containing calls other than the expected protocol and token movements, though this does not eliminate the contract-level exposure. [2](#0-1) 

### Proof of Concept

1. Deploy a malicious receiver whose `execute_flash_position` transfers an unrelated wallet token from `initiator` to the attacker, then transfers enough declared collateral to `controller`. [9](#0-8) 
2. Prepare `flash_position` for a victim-controlled account with:
   - `caller = victim`
   - `account_id = existing_account_id`
   - `mode = PositionMode::Long` or another accepted strategy mode
   - `debt = HubAssetKey { hub_id, asset: listed_debt_token }`
   - `receiver = malicious_receiver`
   - `collaterals = [(HubAssetKey { hub_id, asset: attacker_funded_collateral }, minimum)]`
   - `data` containing the victim token, attacker destination, and amount. [1](#0-0) 
3. Simulate the transaction. The malicious receiver’s `token.transfer(victim, attacker, amount)` appears as an additional authorization child under the victim’s `flash_position` entry. [3](#0-2) [2](#0-1) 
4. If the victim signs that generated tree, the callback steals the unrelated token, supplies the declared collateral, and the controller finalizes the account normally. [7](#0-6) [8](#0-7)

fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
