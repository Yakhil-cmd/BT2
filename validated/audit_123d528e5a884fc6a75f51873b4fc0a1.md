### Title
Webhook signature verified against `repository.owner.login`'s org secret while stack mutation is keyed on independently-controlled `repository.full_name`, allowing cross-tenant `GithubSyncJob` triggering - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC against using `repository_owner`, which reads `params.dig('repository','owner','login')`. `Webhooks::Handlers::PushHandler` (via `Handler#stacks`/`#repository_name`) instead resolves the target stack using `payload.dig('repository','full_name')`. These are two independent JSON fields with no cross-validation, so an attacker who controls an org with its own valid `webhook_secret` can sign a payload whose `full_name` points at a victim repository.

### Finding Description
The broken binding: the question claims `organization_that_signed == organization_of_full_name` is required but never enforced. Concretely:

- `repository_owner` used for signature selection: `params.dig('repository', 'owner', 'login')` [1](#0-0)  feeds `Shipit.github(organization: repository_owner)` and `verify_webhook_signature` [2](#0-1) .
- The repository whose stacks get mutated is resolved from `payload.dig('repository', 'full_name')` in `Handler#repository_name`/`#stacks` [3](#0-2) , consumed by `PushHandler#process` which calls `stack.sync_github(expected_head_sha: params.after)` for matching branch [4](#0-3) .
- `Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up by `owner`/`name` — it does not check that this owner matches `repository_owner` used to select the verifying secret [5](#0-4) .

Attack: attacker configures `webhook_secret` for `Shipit.github(organization: 'attacker-org')` (a precondition granted by the prompt: multi-org `github:` config with attacker owning `attacker-org`). Attacker POSTs to `/webhooks` with `X-Github-Event: push`, body:
```json
{"repository":{"owner":{"login":"attacker-org"},"full_name":"shopify/shipit-engine"},"ref":"refs/heads/master","after":"<attacker-chosen sha>"}
```
signed with `X-Hub-Signature` computed using attacker-org's own secret. `verify_signature` looks up `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and `verify_webhook_signature` succeeds because the attacker legitimately owns that secret. `#create` then dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("shopify/shipit-engine")` → the real Shopify stack, and enqueues `GithubSyncJob` for it with attacker-controlled `expected_head_sha`.

No guard exists anywhere in this path that ties the two lookups together: `verify_signature` never reads `full_name`, and `PushHandler`/`Handler#stacks` never checks `repository_owner`. The existing test suite only exercises the case where owner-login and full_name's owner match (`repository_params` in tests always uses `shopify`) [6](#0-5) , so this divergence is untested and unguarded.

### Impact Explanation
This lets any GitHub org owner with a configured `webhook_secret` in a multi-org Shipit deployment forge a signed push event that mutates another tenant's `Stack`/`Commit` records via `GithubSyncJob.perform_later(stack_id:, expected_head_sha:)`, on any repository/branch combination they can guess or discover (repository full names and branch names are typically public). This is repeatable per request and applies to every handler that resolves `stacks`/`repository` from `payload.dig('repository','full_name')` (also affects PR-based handlers: `ClosedHandler`, `LabeledHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `EditedHandler`, all sharing the same pattern) [7](#0-6) . This matches "a payload for one repository mutating another's stack/commit" — Critical.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where more than one GitHub organization is configured with its own `webhook_secret` (a documented, supported configuration for hosting multiple orgs' repos on one Shipit instance). The attacker needs no privilege on the victim's repository or Shipit instance — only ownership of any other configured org with a webhook secret, which they legitimately possess. Cost is a single crafted HTTP POST; fully repeatable.

### Recommendation
In `PushHandler`/`Handler` (and all similar handlers), verify that the organization derived from `payload.dig('repository','full_name')` matches the `repository_owner` used during signature verification before resolving/mutating stacks — e.g., pass the verified `repository_owner` through to handlers and assert `repository.owner == repository_owner` (case-insensitively) before proceeding, rejecting mismatches with 422.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push signed by attacker-org's secret must not sync shopify's stack" do
  stack = shipit_stacks(:shipit) # owned by 'shopify'

  payload = {
    repository: { owner: { login: 'attacker-org' }, full_name: stack.repository.full_name },
    ref: 'refs/heads/master',
    after: 'deadbeef' * 5
  }.to_json

  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = 'sha1=attacker-signed'

  assert_no_enqueued_jobs(only: GithubSyncJob) do
    post :create, body: payload, as: :json
  end
end
```
Before the fix, this test fails: `GithubSyncJob` is enqueued for `stack.id` despite the signature belonging to `attacker-org`, not `shopify`.
