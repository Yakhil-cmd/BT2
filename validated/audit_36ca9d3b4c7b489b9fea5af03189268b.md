### Title
Cross-repository status forgery via unscoped commit lookup in `StatusHandler` combined with optional webhook signature verification - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` resolves the target commit purely by SHA against the entire `Commit` table, without ever checking that the SHA belongs to the repository named in the same payload. The only gate in front of this handler, `WebhooksController#verify_signature`, selects which organization's secret to validate against using an attacker-supplied field (`repository.owner.login`), and that gate is a no-op whenever that organization has no `webhook_secret` configured — a state the project's own setup docs describe as optional/default. This breaks the intended binding "organization whose signature was verified == repository/stack that gets written," letting an unauthenticated caller inject a forged CI status onto a commit belonging to a stack/organization that was never actually authenticated.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against solely from the JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is taken directly from the untrusted payload (`params.dig('repository','owner','login')` or the `organization.login` fallback), and `Shipit.github(organization: repository_owner)` is looked up for that value. `GithubApp#verify_webhook_signature` then does: [3](#0-2) 

`return true unless webhook_secret` means signature verification is a complete no-op for any configured organization that has no webhook secret set — and `docs/setup.md` explicitly documents the webhook secret as **optional**: [4](#0-3) 

Once past this gate (trivially, for an org with no secret, or for any org whose secret the caller controls), the `status` event is dispatched to `StatusHandler`: [5](#0-4) 

Unlike every other handler in the codebase (`PushHandler`, `PullRequest::*Handler`, etc.), which resolve their target scope through `Handler#stacks`/`#repository_name`, i.e. `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [6](#0-5) 

`StatusHandler#process` never calls `repository_name`/`stacks` at all — it queries `Commit.where(sha: params.sha)` globally across the entire installation, and applies the caller-supplied `state`/`description`/`context` to every matching commit regardless of which repository/organization it belongs to: [7](#0-6) 

`Commit#create_status_from_github!` creates a `Status` record with attacker-controlled `state`, which on `after_create` immediately runs `enable_ci_on_stack` and schedules continuous delivery for that commit's *actual* stack — a stack that has no relation to the organization/repository that the (possibly nonexistent) signature check was performed against: [8](#0-7) [9](#0-8) 

The broken binding, stated as an equality that the code fails to enforce:
`organization authenticated via verify_signature(repository.owner.login)` ≠ `stack/commit actually mutated by StatusHandler (any Commit.sha in the DB)`.

Before the attacker's request: only genuine GitHub webhook deliveries for a given organization/repository (protected by that org's secret) can create `Status` records for that organization's commits.

After the attacker's request: any caller who can reach `/webhooks` with the `status` event header, and for whom `Shipit.github(organization: <attacker-chosen-org-with-no-secret>)` resolves, can create a `Status` (including `state: "success"`) attached to **any** commit SHA present anywhere in the Shipit database — including commits belonging to stacks under organizations that do have proper webhook secrets configured, since the SHA lookup performs no repository/organization scoping whatsoever.

### Impact Explanation
A forged `success` status flips `Commit#state` for CI/deployability purposes and immediately triggers `enable_ci_on_stack` and `schedule_continuous_delivery` on the owning stack. On stacks with continuous delivery/auto-merge enabled, this can cause a commit that never actually passed CI to be auto-deployed or auto-merged — an unauthorized deploy achieved purely through an unauthenticated HTTP request, satisfying the "unauthorized deploy" High-impact bucket.

### Likelihood Explanation
Reachability requires only: (a) at least one GitHub organization configured on the Shipit instance without a `webhook_secret` (a state the project's own setup documentation presents as optional/acceptable), and (b) the ability to send an HTTP POST to `/webhooks` with `X-Github-Event: status` — no session, no `ApiClient` token, and no possession of any secret is required for that organization. This is a documented, supported configuration path rather than a misuse of the engine, and the vulnerable code path (`StatusHandler`) is unconditionally reachable via the public webhook route once the trivial signature gate is bypassed.

### Recommendation
`StatusHandler` (and any other handler that resolves targets by content-derived keys such as commit SHA) must scope its lookup through the same `repository_name`/`stacks` resolution used by every other handler, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })`, rather than a global `Commit.where(sha: ...)`. Additionally, `verify_webhook_signature` should not silently pass when `webhook_secret` is blank for organizations that are expected to be authenticated; at minimum this optionality should be removed or explicitly and loudly flagged as insecure in the documentation, and webhook processing should always additionally verify that the payload's `repository.full_name`/`owner.login` matches the resource being mutated.

### Proof of Concept
1. Configure (or find already configured) Shipit with at least two GitHub organizations, where org `no-secret-org` has no `webhook_secret` set (per `docs/setup.md`, this is a supported/optional configuration) and org `victim-org` owns a Stack containing commit `deadbeef...` that is pending CI.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "no-secret-org" } },
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` value needs to be valid because `verify_webhook_signature` returns `true` unconditionally for `no-secret-org` (`lib/shipit/github_app.rb:76-83`).
3. `WebhooksController#create` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: "deadbeef...")` — matching the commit under `victim-org`'s stack regardless of the `no-secret-org` context used for signature routing — and calls `commit.create_status_from_github!`, creating a `success` `Status` for that commit.
4. The `Status` `after_create` callback enables CI and schedules continuous delivery for `victim-org`'s stack, potentially triggering an unauthorized deploy of a commit that never passed real CI.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
