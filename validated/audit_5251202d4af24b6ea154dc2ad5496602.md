## Finding

### Title
Scoped API token can read CCMenu status for any stack, not just the one it is authorized for - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` authenticates a request with an `ApiClient` token and then fetches the target `Stack` via its own private `stack` method, which calls `Stack.from_param!(params[:stack_id])` directly instead of using the scoped lookup provided by `Api::BaseController`. This breaks the equality that should hold: `ApiClient#stack_id == stack_id_touched_by_request`.

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting resource resolution: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is bound to a specific stack (`stack_id?`), and `stack` resolves `params[:stack_id]` only within that restricted set.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It authenticates with `ApiClient.authenticate(params[:token])` (same as base) but then resolves the stack with `Stack.from_param!(params[:stack_id])`, an unscoped, engine-wide lookup. The only authorization check performed is `require_permission :read, :stack`, which only verifies that the client's `permissions` array contains the string `"read:stack"` — it does not verify which stack the client is scoped to: [3](#0-2) 

So the binding "a stack a token authorizes" (`ApiClient#stack_id`) is never checked against "a stack the request touches" (`params[:stack_id]` used by `Stack.from_param!`). This is analogous to the reported `BondToken::increaseIndexedAssetPeriod` bug class: a scoping/state field (auction success vs. failure state, here `stack_id` scoping) exists but is not actually enforced/consulted at the point where a privileged action (crediting shares/reading stack state) occurs — the code always acts as if the token were unscoped ("succeeded"/global), regardless of whether it truly is.

Before the request: an `ApiClient` created with `stack_id` set to Stack A and `permissions: ['read:stack']` is intended to only ever operate on Stack A (this is precisely how `ApiClient` scoping and `Api::BaseController#stacks`/`#stack` are designed to work, as exercised by the CCMenu-scoped client fixture, e.g. `here_come_the_walrus`).
After the request: that same token, when sent to `Api::CCMenuController#show` with an arbitrary `stack_id` param (e.g. Stack B, to which the client was never granted access), successfully renders Stack B's CCMenu XML (deploy/rollback status, last build label, etc.), because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
This allows a holder of a stack-scoped, `read:stack`-only API token (a low-privilege credential, e.g. the one auto-generated for the "CCMenu Client" via `CCMenuUrlController#client`) to read deploy/rollback status and build information for any stack in the installation, not just the one the token was scoped to. This is an unauthenticated-relative-to-target-stack read of stack state / deploy output, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" defined in scope, since the token is authenticated but not authorized for the stack it is reading.

### Likelihood Explanation
High likelihood for any deployment that issues stack-scoped API clients (this is a first-class, documented feature of `ApiClient#stack_id`) and exposes the CCMenu URL feature (`CCMenuUrlController`/`api_stack_ccmenu_url`). An attacker who obtains any single scoped, `read:stack` token (e.g. from a leaked CCMenu URL for one stack) can trivially enumerate other stacks and read their status by only changing the `stack_id` path/query parameter — no additional secret or privilege is required.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the scope-aware `stacks` collection from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that a stack-scoped `ApiClient` can never resolve a stack outside its `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: 'x', stack: stack_a, permissions: ['read:stack'])`, and get its `authentication_token`.
2. Send `GET /api/*stack_id/cc.xml?token=<token>` (routed to `Api::CCMenuController#show`) with `stack_id` set to Stack B's param (a stack the client was never scoped to).
3. Observe the request succeeds with `200 OK` and renders Stack B's deploy/rollback status, even though the token is only supposed to authorize reads on Stack A — confirmed by the fact that `CCMenuController#stack` at [4](#0-3)  never filters by `current_api_client.stack_id`, unlike `Api::BaseController#stack`/`#stacks` at [1](#0-0) .
