### Title
Cross-tenant Team membership escalation via `Team.find_or_create_by!(github_id:)` in membership webhook handler - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by `params.team.id` (the GitHub team id) using `find_or_create_by!`, without ever checking that the found `Team#organization` matches the organization whose `webhook_secret` verified the request. An attacker who legitimately controls the webhook secret for Org A can submit a `membership`/`added` event naming an already-existing Team belonging to Org B, and `team.add_member(member)` will mutate Org B's team even though Org B's secret was never used to authenticate the request.

### Finding Description
The binding that should hold is: `organization_that_signed_request == Team#organization_of_row_mutated`. In `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`), the org used to select the verifying `webhook_secret` is `repository_owner`, which for membership events is read straight from the untrusted payload: `params.dig('organization', 'login')` [1](#0-0) . The signature is verified via `Shipit.github(organization: repository_owner).verify_webhook_signature` [2](#0-1) , which only proves the request was signed with *that org's* secret — an attacker controlling Org A's own installation can compute this correctly.

Once verified, `MembershipHandler#process` calls `find_or_create_team!`, which does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [3](#0-2) 

`find_or_create_by!` performs a `find_by(github_id:)` first; if a `Team` with that `github_id` already exists (e.g., previously created from Org B's own legitimate membership events), the block is never invoked, so `team.organization` is never checked or re-set. The org name asserted in the current (Org A-signed) payload is discarded, and `process` proceeds to call `team.add_member(member)` [4](#0-3)  on Org B's `Team` row, with `member` resolved via `User.find_or_create_by_login!(params.member.login)` — a GitHub login the attacker also fully controls in the payload.

No guard in this path re-derives or checks organizational ownership of the found `Team`: `verify_signature` only authenticates "org A sent this", `drop_unhandled_event`/`check_if_ping` are irrelevant, and `Team` has no validation tying `github_id` to `organization` at write time in this handler. `Team#add_member` performs no authorization check either [5](#0-4) .

### Impact Explanation
An attacker who legitimately manages one org's GitHub App/webhook integration can add an arbitrary GitHub-login user (including a user under their control) as a member of another organization's `Team` row in Shipit's database, without ever authenticating as that other org. Since `Shipit.github_teams` resolves configured oauth teams to `Team` records via `find_or_create_by_handle` and `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , if the targeted Org B `Team` is one of the configured authorization teams, this is a direct escalation into `Shipit.github_teams` authorization, letting the attacker's chosen user gain access to Shipit (High/Critical depending on which team is targeted) purely because a numeric `github_id` collided/was guessed. This is repeatable against any pre-existing `Team` row whose `github_id` the attacker can learn or guess, from any org whose webhook secret they hold.

### Likelihood Explanation
Requires: (1) attacker legitimately controls at least one org's Shipit GitHub App installation/webhook secret (a real, supported multi-org deployment, as shown by `test/dummy/config/secrets_double_github_app.yml`), (2) a target `Team` row for a different org already exists in Shipit's DB (created from that org's own prior legitimate membership sync), and (3) attacker knows/guesses that team's numeric GitHub `github_id`. Cost is low — a single crafted, self-signed HTTP POST to `/webhooks` with `X-Github-Event: membership`; no interaction with the victim org or GitHub needed.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team#organization` matches `params.organization.login` from the authenticated payload (i.e., match the same organization used in `verify_signature`), and reject/raise (or scope the `find_by` to `organization:`) when they diverge, e.g.:
```ruby
Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
  team.github_team = params.team
end
```
and additionally have `WebhooksController` derive `repository_owner` from a value it can independently trust to prevent payload-controlled secret selection.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot hijack another org's team via matching github_id" do
  org_a = 'org-a'
  org_b_team = shipit_teams(:shopify_developers) # belongs to organization: "shopify"

  request.headers['X-Github-Event'] = 'membership'
  # signed with org_a's real webhook_secret (attacker legitimately controls org_a)
  Shipit.github(organization: org_a).stubs(:verify_webhook_signature).returns(true)

  payload = {
    action: 'added',
    team: { id: org_b_team.github_id, name: org_b_team.name, slug: org_b_team.slug, url: org_b_team.api_url },
    organization: { login: org_a },
    member: { login: 'attacker-controlled-user' }
  }.to_json

  assert_no_difference -> { Team.count } do
    post :create, body: payload, as: :json
  end

  org_b_team.reload
  # BROKEN: member added to org_b's team despite request only being authenticated for org_a
  assert org_b_team.members.exists?(login: 'attacker-controlled-user')
end
```
This demonstrates that `org_a`'s signature (the only thing actually verified) does not equal `org_b_team.organization` (the row actually mutated), confirming the binding is broken.
