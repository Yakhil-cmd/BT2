### Title
Webhook signature is verified against the organization claimed in one payload field while every event handler acts on the repository named in a different, unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a delivery against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Verification itself is done via `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . Once verified, every registered handler is invoked and derives the target `Repository`/`Stack` from a *different* field of the same JSON body: `payload.dig('repository', 'full_name')` in `Handler#repository_name` [3](#0-2) . Nothing in the request path asserts that the owner used to pick the verification secret is the same organization that owns the repository the handler will actually mutate.

### Finding Description
Shipit explicitly supports configuring more than one GitHub App/organization on a single instance, each with its own `webhook_secret`, as documented in `config/secrets.development.example.yml` (the commented-out multi-org schema with independent `webhook_secret` per org) [4](#0-3) .

For a single incoming HTTP POST to `/webhooks`:
1. `repository_owner` is read from the untrusted, attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`) [1](#0-0) .
2. That value selects the `GitHubApp` instance (and thus the HMAC secret) used to verify `X-Hub-Signature` against the raw POST body [2](#0-1) [5](#0-4) .
3. If verification succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs unconditionally against the full parsed body [6](#0-5) .
4. Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*`) resolves the affected `Stack`/`Repository` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [3](#0-2) , and `MembershipHandler` resolves/creates a `Team` from `params.organization.login` and grants membership from `params.member.login` [7](#0-6) .

The binding that should hold — "organization whose secret authenticated the request" == "organization/repository the handler is about to act on" — is never checked. Since the entire raw body is HMAC-signed, an attacker cannot forge a payload without *some* valid secret, but the vulnerability is that a payload only needs to be self-consistent with **one org's secret**, not with the org actually being acted upon. Any org independently onboarded onto this shared instance (each configured with only its own webhook secret, its own admin having no Shipit session, API token, or private key for any other org) can sign a JSON body whose `repository.owner.login`/`organization.login` is their own org (so `verify_signature` picks their own valid secret) while `repository.full_name` (for push/status/check_suite/pull_request) or `member.login` + team fields (for membership) reference a different org's repository/team entirely.

### Impact Explanation
- Forged `push` events let an attacker-controlled org trigger `stack.sync_github(expected_head_sha: ...)` on stacks belonging to a repository owned by a different organization [8](#0-7) , causing unauthorized deploy pipeline activity (sync/queueing) for a repo the attacker does not own.
- Forged `status` events can inject fake CI states for arbitrary commits/repos, which — combined with Shipit's `ci.require` gating described in `README.md` — can be used to make an unrelated commit appear CI-green and eligible to deploy/merge, i.e., an unauthorized ship.
- Forged `membership` events let the attacker add an arbitrary GitHub login (including their own, under an org login string they control) to a `Team` whose `github_id`/`organization` fields are attacker-chosen, potentially colliding with or spoofing a team that maps into `Shipit.github_teams`, escalating into the authorization check used by `User#authorized?` [9](#0-8)  and `force_github_authentication` [10](#0-9) .

This satisfies the "High" bar (escalation into `Shipit.github_teams` authorization, unauthorized ship/deploy) without requiring any Shipit session, API token, webhook secret belonging to the victim org, or GitHub App private key — only requiring the attacker to control one org independently configured on the same shared Shipit instance.

### Likelihood Explanation
Requires the deployment to host more than one GitHub organization behind the same Shipit instance — an explicitly documented and supported configuration (`config/secrets.development.example.yml`). In that topology, exploitation requires no privileged credential relative to the victim organization; only knowledge of the attacker's own org's webhook secret is needed, which the attacker (as an admin of their own onboarded org) already has by design. I cannot verify from static analysis alone whether any deployed instance actually enables multi-org config in practice, but the code path itself imposes no cross-check regardless of topology.

### Recommendation
After `verify_webhook_signature` succeeds for `repository_owner`, re-derive the organization from the field(s) each handler will actually act on (`repository.full_name`'s owner segment, `organization.login`, `member`/`team` context) and reject the request (422) if it does not match the organization whose secret validated the signature. Alternatively, embed/validate the expected organization as part of the webhook URL or as a required, separately-authenticated field rather than trusting a same-payload cross-reference.

### Proof of Concept
1. Shipit instance is configured with two orgs, `attacker-org` (attacker is an org owner and knows its `webhook_secret`) and `victim-org` (hosts the repo/stack targeted).
2. Attacker crafts a `push` webhook JSON body:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/some-repo"`
   - `ref = "refs/heads/main"`, `after = "<arbitrary sha>"`
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')`, which succeeds because the signature matches `attacker-org`'s secret [2](#0-1) .
5. `PushHandler.call(params)` resolves stacks via `Repository.from_github_repo_name('victim-org/some-repo')` and calls `stack.sync_github(expected_head_sha: ...)` on `victim-org`'s stack [8](#0-7) , despite the request never being signed by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
