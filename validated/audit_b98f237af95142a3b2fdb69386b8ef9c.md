### Title
Webhook signature verification is keyed by `repository.owner.login` while the acted-upon repository is resolved independently from `repository.full_name`, allowing cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . That signature check only proves the request was signed by the org selected via that single field. Every downstream handler, however, resolves the actual target using a *different* field, `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name` and `Repository.from_github_repo_name` [2](#0-1) [3](#0-2) . Nothing in the code cross-checks that `repository.owner.login` (the field the signing org/secret was chosen from) actually matches the owner segment of `repository.full_name` (the field that determines which `Stack`/`Repository` is mutated).

### Finding Description
This mirrors the reentrancy report's root cause: two different state fields are supposed to be bound together, but only one is checked while the other is trusted implicitly for the critical effect.

- `verify_signature` picks the `github_app` (and therefore the `webhook_secret` used in the HMAC check) using `repository_owner`: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .
- The signature itself is computed over the *entire* raw JSON body with `verify_webhook_signature`, so an attacker who legitimately controls (or has the webhook secret for) one configured GitHub organization/app can craft and correctly sign an arbitrary JSON payload for their own org [5](#0-4) .
- Once `verify_signature` passes (because it validated against the attacker's own org's secret, matched via `repository.owner.login`), the handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) processes the payload using `repository.full_name` from the same attacker-controlled JSON body [6](#0-5) .
- `Handler#stacks` / `#repository_name` resolve the target `Repository` purely from `repository.full_name`, with no re-validation that its owner matches the org whose secret validated the signature [2](#0-1) .

Equality that should hold but is broken:
`organization authenticated by verify_signature (repository.owner.login / organization.login)` **≠** `repository/stack actually written to (repository.full_name)`.

In a single-organization deployment this gap is not exploitable because there is only one webhook secret and `Repository.from_github_repo_name` will simply fail to find a matching repo if the attacker doesn't also control a real Shipit-tracked repo. But in the documented multi-organization configuration (`config/secrets.development.example.yml` shows this schema is supported) [7](#0-6) , any org onboarded to the same Shipit instance can forge signed events whose `repository.full_name` names a *different* org's tracked repository, because the signature check never binds the verified org to the field the handlers actually trust.

### Impact Explanation
An attacker who is a legitimate (but unprivileged relative to other orgs) member/owner of one GitHub org configured in Shipit's `github:` multi-org secrets can:
- Obtain a validly-signed webhook for their own org, then substitute `repository.full_name` to point at another org's stack.
- Trigger `PushHandler#process` to force `stack.sync_github(expected_head_sha: ...)` on someone else's stack/branch [8](#0-7) , or `StatusHandler`/`CheckSuiteHandler` to inject fabricated commit statuses/check-run refresh triggers against commits that belong to another org's repository [9](#0-8) [10](#0-9) .
- Fabricated/forged commit statuses can influence deploy gating (Shipit typically requires green CI status before allowing a deploy), which can escalate into an unauthorized/incorrectly-approved deploy for a stack the attacker does not own — this crosses the "unauthorized deploy" impact bar. It is a cross-organization write achieved purely by exploiting the field mismatch between authentication and effect.

This is rated **High** because it requires the deployment to have multiple GitHub organizations configured (a supported, documented configuration) and requires the attacker to already have legitimate webhook-signing capability for at least one onboarded org — it is not an anonymous, zero-privilege bug, but it does cross an organizational trust boundary that Shipit is supposed to enforce.

### Likelihood Explanation
Likelihood is **Medium**: it only manifests in multi-org Shipit deployments, and the attacker must be able to trigger (or replay/forge, given they know their org's `webhook_secret`) a webhook delivery. Given that the multi-org config format is explicitly documented and supported, this is a realistic deployment topology, but not the default single-org setup most instances run.

### Recommendation
In `WebhooksController#verify_signature` (and/or in `Shipit::Webhooks::Handlers::Handler`), after establishing which `github_app`/organization validated the signature, assert that the owner segment of `repository.full_name` (or `organization.login` for org-scoped events) equals the `repository_owner` value used to select that `github_app`. Reject the webhook (422) on mismatch. Alternatively, scope `Repository.from_github_repo_name` lookups to only repositories belonging to the verified organization.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App/`webhook_secret`, per the documented multi-org schema [7](#0-6) .
2. Attacker is a legitimate member/admin of `org-a` and thus can obtain (or, if `org-a`'s webhook delivery is attacker-controllable, directly compute) a valid HMAC signature using `org-a`'s `webhook_secret`.
3. Attacker crafts a `push` (or `status`/`check_suite`) JSON payload where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"`, and signs it with `org-a`'s secret.
4. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, loads `Shipit.github(organization: "org-a")`, and the signature check passes [4](#0-3) .
5. `WebhooksController#create` dispatches to `PushHandler`/`StatusHandler`, which resolve the target repository from `repository.full_name = "org-b/victim-repo"` [2](#0-1) , causing Shipit to act on `org-b`'s stack despite only `org-a`'s signature having been verified.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
