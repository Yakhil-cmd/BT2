### Title
Unvalidated `creator` account in `InitializeWithPermission` allows setting pool creator to an unreachable address, permanently freezing creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`InitializeWithPermission` accepts `creator` as a bare `UncheckedAccount<'info>` with no constraint tying it to the transaction signer or to any non-default/reachable address. This value is stored verbatim as `pool_creator` in `PoolState` and later used as the sole authorization key in `collect_creator_fee`, mirroring the reported Solidity pattern where an access-control-critical address (`controller().collateral()`) is used without validating it is a legitimate, reachable address.

### Finding Description
In `InitializeWithPermission`, `creator` is declared with no `address`, `constraint`, or signer requirement: [1](#0-0) 

This raw pubkey is written directly into `PoolState.pool_creator` via `pool_state.initialize(...)`: [2](#0-1) 

`pool_creator` subsequently gates `CollectCreatorFee`, which requires the `creator` account to both match `pool_state.pool_creator` **and** be a `Signer`: [3](#0-2) 

If `pool_creator` is set to `Pubkey::default()` (or any other address with no corresponding private key, e.g. a foreign program ID or PDA with no signer authority), it can never satisfy the `Signer` constraint in `collect_creator_fee`, so accrued creator fees can never be collected through that path. The permissionless variant, `CollectCreatorFeePermissionless`, only requires `creator` to match the stored `address` (no signer needed) and mints/uses an ATA owned by that address: [4](#0-3) [5](#0-4) 

If `pool_creator == Pubkey::default()`, this instruction succeeds and sends the creator's share of fees to an ATA owned by the System Program ID — an address with no private key and thus no way for anyone to ever withdraw the tokens from that ATA. The result is that creator fees continue to accrue in the pool but the value transferred out via the permissionless path lands in a dead/unreachable token account, permanently locking those funds, directly analogous to the reported bug class (access-control address consumed without validating it is non-zero/valid, exploitable due to trusting a caller-supplied address).

### Impact Explanation
Every swap that accrues `creator_fees_token_0`/`creator_fees_token_1` for a pool created via `initialize_with_permission` with a null/unreachable `creator` results in funds that are either (a) stuck in `pool_state` forever because `collect_creator_fee` can never be signed for that address, or (b) transferred via `collect_creator_fee_permissionless` into an ATA owned by an address nobody controls, permanently freezing LP/creator funds. This matches the "permanent freezing of user or LP funds" acceptance bar.

### Likelihood Explanation
Reaching `initialize_with_permission` requires the transaction's `payer` to already hold a `Permission` PDA created via `create_permission_pda` (an admin-gated instruction restricted to `crate::admin::ID` or `crate::create_permission_pda_owner::ID`): [6](#0-5) 

So the vulnerability is only reachable by an address the protocol has already whitelisted as a permitted pool creator — not a fully unprivileged, arbitrary swapper as required by the scan rules. This is not a compromise of an admin/owner signer itself, but it is gated behind an admin-granted permission rather than being open to any wallet, which weakens (but does not eliminate) the practical likelihood: any permissioned creator (deliberately or by mistake, e.g. passing an all-zero or unintended address in `creator`) can trigger permanent fee lock without any additional privilege beyond the pre-granted permission.

### Recommendation
Add an explicit non-default check on `creator` in `InitializeWithPermission`, e.g. `require_keys_neq!(creator.key(), Pubkey::default())`, and consider requiring `creator` to be a `Signer` (as in the unrestricted `Initialize` path) or otherwise proving reachability of the address before persisting it as `pool_creator`.

### Proof of Concept
1. Admin creates a `Permission` PDA for `payer` via `create_permission_pda`.
2. `payer` calls `initialize_with_permission`, passing `creator = Pubkey::default()` (or any address they don't control) as the `creator` account — no constraint rejects this.
3. `pool_state.pool_creator` is set to that address via `pool_state.initialize(...)` [2](#0-1) .
4. Swaps accrue `creator_fees_token_0/1` in `PoolState`.
5. `collect_creator_fee` can never succeed (no signer exists for `Pubkey::default()`); `collect_creator_fee_permissionless` succeeds but sends tokens to an ATA owned by `Pubkey::default()`, which is permanently inaccessible — funds are frozen forever.
