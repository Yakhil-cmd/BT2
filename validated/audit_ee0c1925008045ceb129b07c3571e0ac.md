### Title
A dust borrow or withdrawal can persistently DoS withdrawals sized at (or near) the pool's entire cash reserve, since `withdraw` reverts instead of paying what is available — ([File: contracts/pool/src/ops/withdraw.rs])

### Summary

The pool requires the full requested withdrawal payout to fit inside `cash`; if `net_transfer > cash` the call reverts with `InsufficientLiquidity`. There is no partial-fulfillment fallback. A user who withdraws "everything available" (the withdraw-all sentinel `i128::MAX` resolves `net_transfer` to the position's entire floor value, which in a fully-supplied market equals total cash) can be frontrun by an attacker who draws down cash by a dust amount — via `borrow` of 1 base unit, a dust `withdraw`, or a dust `flash_loan` — making the victim's transaction revert. Because the attacker can keep a dust borrow open indefinitely (repaying and re-borrowing as needed), near-maximal withdrawals of a fully-utilized market can be blocked continuously.

### Finding Description

In `contracts/pool/src/ops/withdraw.rs`, `gate_and_debit` calls `cache.require_reserves(net_transfer)` before `debit_cash`:

```rust

    cache.require_reserves(net_transfer);
    ...
    cache.debit_cash(net_transfer);
}
``` [1](#0-0) [2](#0-1) 

`require_reserves` is a strict `cash >= amount` assert that panics with `CollateralError::InsufficientLiquidity` (112). The withdraw-all path (`amount == 0` at the controller, mapped to `WITHDRAW_ALL_SENTINEL = i128::MAX`, passed through as `entry.action.amount == i128::MAX`) resolves to the position's full floor value — there is no clamping to available cash. [3](#0-2) [4](#0-3) 

Attack flow:

1. Market `USDC` on hub H has `cash = C` and a supplier Alice whose whole supply position's floor value equals `C` (e.g., the last/only large supplier in a fully-utilized market, or one whose exit would drain the pool).
2. Alice calls `controller.withdraw(account_id, payments)` with a `0` leg → sentinel → `net_transfer = C`.
3. Attacker Bob (unprivileged, needs only minimal collateral and a `min_borrow_collateral_usd`-satisfying position, or just a dust supply position to withdraw from) frontruns with `controller.borrow` for `amount = 1` base unit (or withdraws/flash-loans 1 unit). Pool cash becomes `C - 1`. Bob's borrow is legal: `require_reserves`, `require_liquidation_buffer`, and `require_utilization_below_max` all pass for a dust draw. [5](#0-4) 
4. Alice's withdraw now computes `net_transfer = C > cash = C - 1` → `require_reserves` panics → the whole controller transaction reverts.
5. Bob can repeat: he needs to keep only `>= (net_transfer_target) - cash` units of the pool's cash "missing". For a victim who insists on withdrawing the entire pool balance, a single 1-unit open borrow held indefinitely suffices — every retry reverts while the dust borrow (or any dust claim on cash) stands.

The same mechanism also DoSes `borrow` calls sized at the full available draw (`require_reserves` + `require_liquidation_buffer` in `mint_debt`) and `flash_loan` calls for all available liquidity (`ops/flash.rs` runs `require_reserves`), but the strongest case is the supplier whose withdraw-all transaction can be persistently blocked by a dust borrow the attacker leaves outstanding.

### Impact Explanation

Temporary freezing of user funds: a supplier whose withdrawal target is at or near the pool's cash boundary cannot exit while an attacker maintains a dust-sized draw on cash. Shares are never burned and tokens never move — the revert is total, so there is no graceful partial exit unless the victim manually re-sizes the request below the new cash level, which the attacker can again dust-gap. The griefing cost is negligible: borrowing 1 base unit accrues essentially zero interest, and a dust supply withdrawal is free. In a thinly-liquided market this effectively locks the largest supplier(s) out of exit for as long as the attacker wishes.

### Likelihood Explanation

Moderate. It requires a victim who requests withdrawal of (almost) the entire remaining cash — common for the dominant supplier of a small market or when utilization is near 100% and the pool is nearly drained. No privileged role, no oracle manipulation, and no large capital is needed; the griefer only needs enough collateral to open a 1-unit borrow (or already own dust supply). On the other hand, the attack only blocks edge-sized withdrawals, not all withdrawals, and the victim can usually exit partially — hence medium severity rather than high.

### Recommendation

Adopt the "sell available amount" mitigation rather than the revert:

- In `resolve_close_or_partial`/`gate_and_debit`, when `net_transfer > cash` for a withdraw-all request (`amount == i128::MAX`), clamp the payout to `cash` instead of reverting — i.e., burn the shares but cap the transfer at available reserves (or add a `min_out` parameter on the controller `withdraw` so users bound acceptable shortfall).
- Alternatively, for borrows, cap `amount` at the maximum drawable (`cash - reserved` after `require_liquidation_buffer`) or revert with a distinct, catchable condition; for flash loans, similarly clamp or expose the max-loanable amount.
- A minimum-operation-size check (rejecting sub-dust borrows/withdrawals, analogous to `*RoundsToZeroShares` guards) would raise the griefer's cost but does not remove the revert-at-boundary hazard on its own.

### Proof of Concept

```text
1. Alice supplies 1,000 USDC to hub H market M → pool cash = 1_000 * 10^7.
   (Other suppliers' utilization is 0 so Alice's claim ≈ all cash.)
2. Alice submits controller.withdraw(acct, [(hub_asset, 0)])  // 0 = withdraw-all sentinel
   → pool resolves net_transfer = 1_000 * 10^7 == cash → would succeed.
3. Bob frontruns with controller.borrow(acct_bob, [(hub_asset, 1)])  // 1 base unit
   → mint_debt passes require_reserves(1), buffer, utilization; cash = 1_000*10^7 - 1.
4. Alice's withdraw: resolve_withdrawal(i128::MAX, pos) → net_transfer = 1_000*10^7;
   require_reserves(1_000*10^7) vs cash = 1_000*10^7 - 1 → panics InsufficientLiquidity (112).
5. Bob repays 1 unit + accrued interest and re-borrows 1 unit on each retry, or simply
   leaves the dust borrow open: every withdraw-all by Alice reverts indefinitely.
```

pub(crate) fn mint_debt(env: &Env, cache: &mut Cache, position: &mut Ray, amount: i128) {
    require_positive_amount(env, amount);
    cache.require_reserves(amount);
    guards::require_liquidation_buffer(env, cache, amount);

    let minted = cache.calculate_scaled_borrow(amount);

    assert_with_error!(
        env,
        minted.raw() > 0,
        GenericError::BorrowRoundsToZeroShares
    );

    *position = position.checked_add(env, minted);
    cache.mint_debt(minted);
    guards::require_utilization_below_max(env, cache);
}
