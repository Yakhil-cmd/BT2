### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while every event handler acts on the independent `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC `webhook_secret`) to verify a webhook against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once verification passes, every downstream `Handler` (push, status, check_suite, pull_request, etc.) determines *which stack/repository to act on* using a different, independently attacker-controlled field of the same JSON body: `payload.dig('repository', 'full_name')`. No code enforces that these two fields refer to the same repository/organization.

### Finding Description
This is the same bug class as the `SFT418Core._claim()` finding: an action is authorized against one identifier (the field checked/signed) while the actual operation executes against a different identifier drawn from the same untrusted input, with no equality constraint binding them.

- Verification field: `repository_owner` in `app/controllers/shipit/webhooks_controller.rb:59-62`, used to pick the GitHub App/secret in `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) via `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

- Action field: every `Handler` subclass resolves the target repository/stack from `payload.dig('repository', 'full_name')`, e.g. `app/models/shipit/webhooks/handlers/handler.rb:36-38`, and pull-request handlers repeat this via `params.repository.full_name` (e.g. `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`). [3](#0-2) 

- The `verify_webhook_signature` implementation itself makes the situation exploitable: `return true unless webhook_secret` — if any configured GitHub App/organization has no `webhook_secret` set, signature verification is trivially bypassed for requests presenting that organization's identity. [4](#0-3) 

- The docs and multi-org fixture both confirm `webhook_secret` is an *optional* setting, i.e., this is a supported deployment configuration, not a misuse: `**github.webhook_secret** If you've set a webhook secret during the App creating, you should copy it here.` and the test fixture `test/dummy/config/secrets_double_github_app.yml` explicitly configures `OrgTwo` with `webhook_secret: # nil`. [5](#0-4) [6](#0-5) 

**Equality that should hold but doesn't:** `repository_owner` (the org whose secret authenticated the request) == the owner encoded in `repository.full_name` (the repo the handler mutates). Before an attacker's crafted request: an unauthenticated caller can only satisfy the signature check for the org whose secret they know (or for any org configured without a secret). After the crafted request: the same caller can make `WebhooksController#create` dispatch a fully "verified" event (`app/controllers/shipit/webhooks_controller.rb:10-15`) whose `repository.full_name`/`sha`/`state`/`branches` point at an entirely different organization's stack, because nothing checks `repository.full_name`'s owner against `repository_owner`. [7](#0-6) 

### Impact Explanation
In a multi-organization Shipit deployment (the documented/supported configuration shown by `secrets_double_github_app.yml` and `Shipit.github_organizations`/`github_app_config` in `lib/shipit.rb:190-200`), if any single configured organization omits its `webhook_secret` (explicitly allowed by the setup docs), an unauthenticated internet client can:
- Set `X-Github-Event: status`, `repository.owner.login` = the secret-less org, and `repository.full_name`/`sha` = a commit belonging to an entirely different, victim organization's stack, causing `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) to fabricate a passing CI status on that victim commit.
- A forged passing status can satisfy `MergeRequest#reject_unless_mergeable!`/CI requirements, leading `ProcessMergeRequestsJob` to call `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request(...)` — an **unauthorized merge**, which is explicitly listed as a Critical impact. [8](#0-7) 
- The same field confusion lets an attacker trigger `GithubSyncJob`/`RefreshCheckRunsJob` (via `push`/`check_suite` events) for arbitrary victim stacks, and cause `Commit.create_status_from_github!` writes against a stack the attacker was never authorized to touch — an escalation of trust bound to `repository_owner`.

### Likelihood Explanation
Likelihood is **conditional but realistic**: it requires only that the deployment operate multiple GitHub App organizations (a documented, supported feature) and that at least one configured organization's `webhook_secret` be left unset (explicitly "optional" per the setup docs and demonstrated in the repo's own multi-org fixture). Given `webhook_secret` is optional and the docs never warn that omitting it on any one org undermines signature checks for *all* other orgs' repositories, this is a plausible operational configuration, not a contrived edge case. No credentials, session, or API token are required by the attacker — only a raw HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind the field used for signature verification to the field used for processing: require that `repository.owner.login` (or `organization.login`) match the owner portion of `repository.full_name` before dispatching to handlers, e.g.:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified && repository_owner_matches_full_name?
  ...
end

def repository_owner_matches_full_name?
  full_name = params.dig('repository', 'full_name')
  return true if full_name.blank?

  full_name.split('/', 2).first&.casecmp?(repository_owner)
end
```

Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-organization mode; require a webhook secret for every organization once more than one GitHub App is configured, or refuse to route any event whose claimed `repository_owner` differs from the app that would ultimately process the payload.

### Proof of Concept
Given a Shipit instance configured with two GitHub Apps, `OrgSecure` (with a `webhook_secret`) and `OrgNoSecret` (with `webhook_secret` left blank, as in `test/dummy/config/secrets_double_github_app.yml`), and `OrgSecure/victim-repo` is a real deployed stack:

1. Attacker sends, without any valid `X-Hub-Signature` (or any bogus value):
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgSecure/victim-repo" },
  "sha": "<victim commit sha awaiting required CI>",
  "state": "success",
  "context": "ci/required-check",
  "created_at": "2026-09-01T00:00:00Z"
}
```
2. `verify_signature` computes `repository_owner = "OrgNoSecret"`, loads `Shipit.github(organization: "OrgNoSecret")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `WebhooksController#create` then dispatches the event to `StatusHandler`, which looks up the commit by `sha` regardless of which org it belongs to, and calls `commit.create_status_from_github!(params)`, forging a passing status on `OrgSecure/victim-repo`'s commit — a repository the attacker's payload never had a valid signature for.

This exact wiring (`WebhooksController#verify_signature` vs. `Handler#repository_name`/handler-specific `full_name` lookups) is confirmed directly from source; the multi-organization/optional-secret configuration is confirmed from `docs/setup.md` and the repo's own fixture, though I was not able to execute the actual HTTP request against a running instance to observe the end-to-end effect — this analysis is based on static code review of the cited files.
