### Title
Vote account `UpdateCommissionBps(BlockRevenue)` allows unrestricted, undelayed commission rug that misattributes stakers' block-revenue rewards - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
This maps to the "cred creator" fee-rug bug class: a privileged authority increases a revenue-share fee at will, with no timelock and no opportunity for unprivileged stakeholders to react, causing them to lose funds they would otherwise have received. In Agave, the analogous privileged authority is the vote account's authorized withdrawer, and the unprivileged victims are the delegators/stakers whose block-revenue rewards are split by that commission.

### Finding Description
The legacy `UpdateCommission` instruction enforces a timing rule (`is_commission_update_allowed`) that blocks commission *increases* outside the first half of an epoch, specifically to stop "last-minute commission rugs" [1](#0-0) . Separately, `redeem_delegation_rewards` deliberately uses a *one-epoch-delayed* snapshot of vote-account commission (`snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`) for inflation-reward commission, explicitly to "delay the effect of commission updates by at least one full epoch" [2](#0-1)  and this delay mechanism is documented as preventing "last minute commission rugs" [3](#0-2) .

However, the newer `UpdateCommissionBps` instruction with `CommissionKind::BlockRevenue` explicitly removes any timing restriction: the code comment states "No commission update rule, per SIMD-0249 and SIMD-0291," and the function only checks the authorized-withdrawer signature before setting the new commission immediately [4](#0-3) . The processor dispatches this instruction with only a feature-gate check and no additional timing constraint [5](#0-4) .

Block-revenue reward calculation (`calculate_block_reward`) is invoked directly against `cached_vote_accounts.distribution_epoch_vote_accounts` — the live, end-of-epoch vote-account snapshot — rather than through the one-epoch-delayed `snapshot_epoch_vote_accounts` path used for inflation-reward commission [6](#0-5) . This means a vote account's authorized withdrawer can set `block_revenue_commission_bps` to its maximum value at any point—including immediately before the end of the epoch when block-revenue rewards are computed—capturing 100% of what would otherwise be shared with delegators, with no delay window in which stakers could react (e.g., deactivate their stake).

### Impact Explanation
If confirmed unmitigated, this results in misattributed rewards: unprivileged delegators' expected share of block-revenue rewards is redirected to the vote account commission collector without any advance notice or timelock, unlike the equivalent inflation-commission path which is explicitly delayed by a full epoch for this exact reason.

### Likelihood Explanation
The `UpdateCommissionBps` instruction requires only the vote account's authorized-withdrawer signature and is unconditionally allowed once the relevant features (`commission_rate_in_basis_points`, `delay_commission_updates`, `block_revenue_sharing`) are active [5](#0-4) ; there is no on-chain restriction preventing the withdrawer from calling it in the same slot/epoch as reward calculation.

### Recommendation
Route the `BlockRevenue` commission through the same one-epoch-delayed snapshot mechanism (`snapshot_epoch_vote_accounts`) already used for inflation-reward commission bps in `redeem_delegation_rewards`, or otherwise reinstate a timing restriction analogous to `is_commission_update_allowed` for `CommissionKind::BlockRevenue` updates, so that block-revenue commission changes cannot affect rewards for the epoch in which they are made.

### Proof of Concept
Not independently confirmed against a full runtime trace; based on the code paths cited above, an authorized withdrawer could: (1) call `UpdateCommissionBps` with `kind: CommissionKind::BlockRevenue` and `commission_bps: 10000` late in an epoch; (2) have this take immediate effect in vote state per `update_commission_bps` [7](#0-6) ; (3) have `calculate_block_reward` read this updated value directly from `distribution_epoch_vote_accounts` at reward-calculation time [6](#0-5)  before any delegator could react. I was unable to fully trace `calculate_block_reward`'s internal implementation to verify whether an additional, unseen delay mechanism exists there; this should be verified directly in the full source before treating this as conclusively exploitable.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
