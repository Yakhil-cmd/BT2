### Title
Attacker-controlled secondary AA can force revert of an entire multi-recipient AA distribution, causing loss/freezing of legitimate co-recipients' funds - (File: aa_composer.js)

### Summary
When a primary AA trigger fans out payments/state changes to multiple secondary AAs in one response, `handleSecondaryTriggers()` executes each secondary AA sequentially and, if *any* secondary AA bounces, the *entire* primary trigger execution — including every already-successful secondary AA call and the primary AA's own state changes — is rolled back via `revert()`. An attacker who controls (or gets listed as) just one of the destination AAs in a fan-out can make that one AA always bounce cheaply, forcing the whole atomic chain to fail and denying payment/state updates to all the other, unrelated, legitimate parties in the same distribution.

### Finding Description
`handleSecondaryTriggers()` looks up every AA address that received an output from the current response unit and calls `handleTrigger()` on each of them in sequence with `async.eachSeries`: [1](#0-0) 

If any of these child triggers bounces, the series callback does not simply skip that one leg — for the primary AA it calls `revert()`, unconditionally undoing the whole chain: [2](#0-1) 

`revert()` restores the database to the savepoint taken before any of the primary trigger's balance updates, clears the KV batch, and discards all previously produced (and otherwise valid) responses in `arrResponses`, before finally bouncing the primary trigger: [3](#0-2) 

Crucially, forcing a secondary AA to bounce is essentially free for the attacker: secondary triggers are exempt from the requirement to cover bounce fees and never send a bounce response or change state when bounced: [4](#0-3) [5](#0-4) 

So an attacker can deploy a trivial AA whose code unconditionally calls `bounce(...)`. Any legitimate "distributor"/"router"/"payout-splitting" AA design that sends outputs to a set of AA addresses in a single response (e.g., forwarding rewards, settling multiple counterparties, or paying out to AA addresses supplied via `trigger.data`) is vulnerable: as soon as the attacker's always-bouncing AA is one of the fan-out destinations, `handleSecondaryTriggers` will hit it and trigger `revert()`, wiping out every other secondary AA response and the primary AA's state changes that were already computed correctly in the same execution — exactly analogous to the reported OpenQ bug where one malformed ERC20 transfer reverts an entire multi-token/NFT claim that bundles independent transfers atomically.

### Impact Explanation
This allows a single malicious/misbehaving AA participant to deterministically and repeatably block legitimate fund distribution or state commits to other, unrelated parties whenever it is included (or includable, e.g. via attacker-influenced trigger data) as one of the fan-out recipients of a primary AA. Because the primary AA's own state updates are also rolled back, any AA logic that relies on marking something as "processed"/"paid" before fanning out to secondary AAs is repeatedly retried and permanently unable to complete, effectively freezing funds held by that AA for all legitimate counterparties as long as the attacker keeps including/triggering the poisoned destination. This matches the "AA fund loss or freezing" impact category.

### Likelihood Explanation
Likelihood is high for any AA pattern that fans out to attacker-influenceable AA addresses (common for generic routers, reward splitters, DEX/AMM settlement AAs paying multiple maker/taker AAs, or any AA accepting a list of destination AAs from `trigger.data`). The attacker only needs to define one cheap, always-bouncing AA and ensure it is one of the destinations of a targeted primary AA's response — no privileged access, no special timing, and no cost beyond a normal trigger unit.

### Recommendation
Do not let a single secondary-AA bounce force reversion of already-successful, independent secondary AA calls and the primary AA's own state. Consider isolating each secondary trigger's execution (e.g., per-destination savepoints) so a bounce in one branch only reverts that branch's effects, or require AA authors to explicitly acknowledge that fan-out to externally-influenceable AA addresses is all-or-nothing, and provide/encourage a "try/catch"-style oscript primitive for calling other AAs that isolates failures instead of relying on `handleSecondaryTriggers`'s blanket `revert()` on any child bounce.

### Proof of Concept
1. Attacker deploys `evil_aa`: `['autonomous agent', { messages: [{ app: 'state', state: '{ bounce("always fail"); }' }] }]`. Since it unconditionally bounces and is a secondary trigger, it pays no bounce fee and needs no state (see `aa_composer.js:1850-1859`, `923-927`).
2. Attacker interacts with a legitimate "distributor" AA whose logic, per trigger, forwards portions of a received payment to a set of AA addresses (either hard-coded plus attacker-specified, or fully specified via `trigger.data`), including `evil_aa` as one destination — for instance, by being a listed beneficiary or by supplying `evil_aa`'s address in trigger data accepted by the distributor.
3. On execution, the distributor AA computes valid outputs/state and calls `sendUnit()`, producing a response unit whose outputs include a payment to `evil_aa` among other, unrelated, legitimate AAs.
4. `handleSecondaryTriggers()` (`aa_composer.js:1702-1757`) invokes each destination AA via `async.eachSeries`. When it reaches `evil_aa`, that trigger bounces, and the series' final callback calls `revert()` because the current context is the primary trigger (`aa_composer.js:1743-1750`).
5. `revert()` rolls back to the `initial_balances` savepoint and discards all responses collected so far (`aa_composer.js:1759-1783`), so every other legitimate destination AA that had already been successfully processed in this same batch loses its payment/state update, and the primary distributor AA's own state changes are undone — even though those parts of the logic were entirely correct and unrelated to `evil_aa`.
