### Title
Webhook signature is verified against the organization named in the payload, but event handlers act on a different, unchecked repository field — allowing cross-tenant webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
On multi-organization Shipit installations (`Shipit.github_organizations` with a per-org `secrets.github.<org>.webhook_secret`), `WebhooksController#verify_signature` selects which organization's HMAC secret to validate the request against by trusting an *unverified* field of the incoming JSON payload (`repository.owner.login`, or `organization.login` as fallback), and only afterwards does it hand the *entire raw payload* to the event handler. The handler then derives the actual repository/stack to mutate from a *different* payload field (`repository.full_name`), which is never cross-checked against the organization used to pick the verification secret. This breaks the intended binding "organization whose secret authenticated this request == repository being written to."

### Finding Description
`WebhooksController#verify_signature` computes the signing organization purely from request body content: [1](#0-0) [2](#0-1) 

It then fetches the `GitHubApp` configured for that organization and validates the signature with that org's own `webhook_secret`: [3](#0-2) 

Crucially, `verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: [4](#0-3) 

Once verification passes, `WebhooksController#create` dispatches the *raw, unmodified* payload to handlers: [5](#0-4) 

Handlers, however, resolve the target `Stack`/`Repository`/`Commit` from a completely independent field, `repository.full_name`, via `Handler#repository_name`/`#stacks`: [6](#0-5) [7](#0-6) 

`PushHandler` (enqueues a `GithubSyncJob` for the matched stacks/branch) and `CheckSuiteHandler`/`StatusHandler` (creates a commit status / schedules check-run refresh) all operate exclusively on `stacks`/`Commit.where(sha:)`, i.e. on data keyed by `repository.full_name`, not on `repository.owner.login`: [8](#0-7) [9](#0-8) [10](#0-9) 

Nothing in this path asserts `repository.owner.login == repository.full_name.split('/').first`. An attacker who is a legitimate GitHub webhook sender for *one* organization/repository configured on the Shipit instance (i.e., they can produce a validly-signed delivery for `repository.owner.login = "attacker-org"`, using that org's own `webhook_secret`, which they know because it's their own org's App/webhook) can set `repository.full_name` in the JSON body to `"victim-org/victim-repo"`. The signature check passes (it only checks `owner.login`'s secret against the raw body — HMAC covers the byte content, but the attacker controls the entire byte content since they crafted the payload and signed it with their own secret), and the handler then acts on the victim repository's stacks/commits.

This is the direct structural analog of the reported "MEV/front-running" class of bug: the verified/authenticated dimension (`organization` used to select the secret) and the acted-upon dimension (`repository.full_name` used to select the mutated resource) are two different fields of the same payload with no equality enforced between them — exactly the "organization that authenticated versus the repository that is written" binding called out in scope.

### Impact Explanation
This allows an attacker who legitimately controls webhook delivery for any one organization/repository configured in a multi-org Shipit deployment to forge `push`, `status`, and `check_suite` events for a *different, unrelated* repository/stack they do not control:
- `PushHandler` enqueues `GithubSyncJob` for the victim's stack, forcing an unrequested sync against an attacker-chosen `expected_head_sha`.
- `StatusHandler` allows fabricating commit statuses (`create_status_from_github!`) on arbitrary victim commits, which can influence CI-gated deploy checks (`ci.require`) used to decide whether a deploy is allowed.
- `CheckSuiteHandler` schedules check-run refreshes for victim commits.

Because Shipit's deploy safety gating (`ci.require`) is driven by `Status` rows populated exactly through this webhook path, an attacker able to inject forged, "verified" statuses for a victim's commit could clear/pollute CI gating for repositories that are not theirs, contributing to an unauthorized deploy decision. This crosses a repository trust boundary without any repository write access or Shipit session — matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
This requires the target Shipit instance to be configured with the multi-organization `secrets.github` schema (`github_default_organization` non-nil) and for the attacker to control (or be an authorized webhook sender for) at least one of the configured organizations/repositories — a realistic scenario for shared/multi-tenant Shipit deployments serving several GitHub orgs. No Shipit session, API token, or GitHub App private key is needed; only the ability to deliver a signed webhook for one's own org, which is inherent to owning/administering that org's repository. Likelihood is Medium: it needs a multi-org configuration and the attacker's own org onboarded to the same Shipit instance, but requires no privileged secret beyond what the attacker's own org already possesses.

### Recommendation
In `Handler#repository_name` / `Handler#stacks`, or in `WebhooksController#verify_signature`, enforce that the organization used to select the verifying `webhook_secret` matches the owner encoded in `repository.full_name` (and `organization.login` when present) before dispatching to handlers — i.e. assert `repository_owner == payload.dig('repository', 'full_name')&.split('/')&.first` and reject (422) on mismatch. Additionally, avoid unconditionally trusting requests when an org has no `webhook_secret` configured — either require a secret for every configured organization or fail closed instead of returning `true` from `verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `attacker-org` (secret known/owned by the attacker) and `victim-org` (hosting a tracked stack/repository).
2. Attacker crafts a webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and sends it with `X-Github-Event: push` to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature against the attacker's own known secret (see `app/controllers/shipit/webhooks_controller.rb#L24-L30`, `lib/shipit/github_app.rb#L76-L83`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (see `app/models/shipit/webhooks/handlers/handler.rb#L32-L38`, `app/models/shipit/repository.rb#L53-L56`) and enqueues `GithubSyncJob` for the victim stack with the attacker-supplied `expected_head_sha` — despite the request never having been signed by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
