### Title
Cross-organization webhook signature confusion allows unauthorized writes to stacks of other organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` verifies an incoming webhook's HMAC signature against the GitHub App config selected by the **organization** name derived from the payload, but the handlers that actually mutate state select the **repository/stack to act on** using a completely different, unchecked payload field (`repository.full_name`). In a multi-organization Shipit deployment, an attacker who legitimately administers the GitHub App for one configured organization can produce a validly-signed webhook body (using their own org's `webhook_secret`) whose `repository.owner.login`/`organization.login` matches their org (satisfying signature verification) while `repository.full_name` names a repository belonging to a *different* organization configured on the same Shipit instance. The handler then acts on that unrelated repository's stack.

### Finding Description
Signature verification is keyed off `repository_owner`, computed from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp` (and its `webhook_secret`) configured for that specific organization — Shipit explicitly supports multiple, independently-secreted organizations (`somegithuborg`, `someothergithuborg`), each with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the raw, attacker-suppliable JSON body to handlers: [5](#0-4) 

Every handler resolves the target Repository/Stack purely from `payload.dig('repository', 'full_name')`, with no cross-check against the organization value that was actually used to verify the signature: [6](#0-5) 

For example `PushHandler` finds and mutates stacks solely by `full_name`-derived repository and branch, then forces a git sync: [7](#0-6) 

Similarly, pull-request handlers archive/unarchive review stacks or update PR records for whatever `repository.full_name` says, again independent of the organization that authenticated the request: [8](#0-7) [9](#0-8) 

**The broken binding, as an equality that must hold but doesn't:**
`organization used to verify signature (repository.owner.login / organization.login)` == `organization implied by repository.full_name used to select the stack that is written`.

Before the attacker's request: for genuine GitHub-originated webhooks these two values are always consistent (GitHub itself fills in a coherent payload), so the mismatch never manifests. After the attacker's crafted request: the attacker (who legitimately administers Org A's GitHub App and therefore knows Org A's `webhook_secret`) sets `repository.owner.login` (or `organization.login`) = `"OrgA"` so `verify_signature` succeeds, but sets `repository.full_name` = `"OrgB/some-repo"` — a repository/stack that belongs to a different, unrelated organization also configured on the same multi-tenant Shipit instance. The handler layer never re-validates that `full_name`'s owner matches the verified `repository_owner`, so it operates on OrgB's stack under an identity check that only proved OrgA membership.

### Impact Explanation
This breaks the deployment-trust boundary between tenants of a multi-organization Shipit instance: an entity that only proved control of Organization A's webhook secret can force cross-repository writes on Organization B's stacks — triggering `sync_github`/deploy state changes (`PushHandler`), archiving/unarchiving review stacks (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), or corrupting pull-request records (`AssignedHandler`, `EditedHandler`) for a repository/organization the attacker has no legitimate relationship with. This matches the "Critical: cross-repository writes / unauthorized deploy" impact tier.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one organization (documented, supported multi-tenant configuration in `config/secrets*.yml`) and that the attacker legitimately administers or can register the GitHub App/webhook for at least one of those organizations — no access to any other tenant's secret, no repository write access on the target, and no session/API token is needed. Given Shipit is explicitly designed to host multiple orgs sharing one instance, this is a realistic configuration.

### Recommendation
After signature verification, re-derive the organization from the same trusted `repository_owner`/`organization.login` value and require that `Repository.from_github_repo_name(payload.dig('repository','full_name'))` belongs to that same verified organization before invoking any handler; reject the webhook (422) on mismatch instead of trusting `full_name` blindly in `Shipit::Webhooks::Handlers::Handler#stacks`.

### Proof of Concept
1. Shipit instance is configured with two organizations, `OrgA` (attacker-administered GitHub App, secret `S_A`) and `OrgB` (victim org, secret `S_B`), each with stacks tracked by Shipit — see `config/secrets.development.shopify.yml` supporting multiple orgs.
2. Attacker builds a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` — valid because they legitimately know `S_A`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature checks out (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and calls `stack.sync_github(expected_head_sha: ...)` on OrgB's stack — a write the attacker was never authorized to trigger, using only OrgA's credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
