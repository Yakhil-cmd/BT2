### Title
Clickjacking of `MergeStatusController#show` allows attacker to force a victim to enqueue an attacker-chosen `stack_id`/PR `number` for merge - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`MergeStatusController#show` sets `X-Frame-Options: ALLOWALL` and cookies are forced to `SameSite=None` by `Shipit::SameSiteCookieMiddleware`, so the page can be framed cross-site with the victim's session cookie attached. Both the `stack_id` used to render the page and the `number` used to build the "Add to merge queue" form action are taken from attacker-controlled query parameters (`params[:stack_id]`, `params[:referrer]`), so a click inside the framed, genuine form results in `PUT /merge_status/*stack_id/pull/:number` executing `MergeRequest.request_merge!(stack, params[:number], current_user)` for a stack/PR the victim never chose.

### Finding Description
The claimed binding is: `stack_id/number submitted in the enqueue PUT` == `stack_id/PR the victim actually intended to enqueue`. This binding is broken.

`MergeStatusController#show` explicitly disables frame protection and only checks `current_user.logged_in?`, with no per-stack authorization: [1](#0-0) . The `stack` resolution method takes `params[:stack_id]` verbatim via `Stack.from_param!`, or falls back to `referrer_parser.repo_owner`/`repo_name`/`branch`, all attacker-supplied query parameters: [2](#0-1) . The rendered "Add to merge queue" form's action URL is built from `enqueue_merge_request_path(stack, pull_request_number)`, where `pull_request_number` is parsed only from `params[:referrer]` (an arbitrary GitHub PR URL string, matched by a regex, not validated against `stack`): [3](#0-2) [4](#0-3) . Note `stack_id` and `number` are derived independently from two unrelated attacker-controlled parameters, so an attacker can point them at any Shipit-tracked stack and any PR number of their choosing.

`enqueue` performs no additional per-stack authorization (no `require_permission!`) beyond the fact that `current_user` must be logged in generally: [5](#0-4) , and calls `MergeRequest.request_merge!` which stamps `merge_requested_by: user.presence` from whatever `current_user` the session resolves to: [6](#0-5) .

`protect_from_forgery with: :exception` at the `ShipitController` level does not stop this: [7](#0-6) , because the CSRF token embedded in the form is the *genuine* token issued by the real app inside the framed `GET /merge_status` response for the victim's own session - the attacker never needs to read or forge it; they only need the victim to click the real button rendered inside a hidden/overlaid iframe (classic clickjacking). `Shipit::SameSiteCookieMiddleware` forces `SameSite=None` on all secure cookies, which is what makes the victim's session cookie present at all in this third-party-framed context: [8](#0-7) .

Exploit flow:
1. Attacker hosts a page with an invisible/transparent iframe pointing to `https://shipit-host/merge_status?stack_id=<any-tracked-repo>/<branch>&referrer=https://github.com/<attacker-org>/<attacker-repo>/pull/<N>` (their own PR, or any number).
2. A logged-in Shipit user (victim) visits the attacker's page; the iframe loads with the victim's session cookie due to `ALLOWALL` + `SameSite=None`.
3. The genuine "Add to merge queue" button is rendered, targeting the attacker's chosen `stack_id`/`number`.
4. Victim is lured (via UI redressing) into clicking through the iframe, submitting the real `PUT` with a valid CSRF token for their own session.
5. `MergeRequest.request_merge!(stack, number, current_user)` executes, enqueuing the attacker-chosen PR for merge, with `merge_requested_by` set to the victim.

No existing guard intercepts this: `show`/`check` intentionally `skip_authentication` for embedding, CSRF succeeds because the token is real, and `enqueue` has no check that the requester actually intended this specific `stack`/`number` pairing or is authorized for that specific stack.

### Impact Explanation
An unprivileged, external attacker (owning nothing but a GitHub PR and a webpage) can cause an arbitrary logged-in Shipit user's session to enqueue the attacker's own pull request into any Shipit-managed repository's merge queue, falsely attributing the action (`merge_requested_by`, and the eventual `Merge-Requested-By` commit trailer via `merge_message`) to the victim: [9](#0-8) . If CI on the attacker's own PR/branch passes (attacker fully controls their own repo's CI) and the stack has `merge_queue_enabled`, this can progress to an actual GitHub merge performed with Shipit's own GitHub App credentials via `MergeRequest#merge!`, i.e., an unauthorized merge executed under the guise of a legitimate team member's authorization. This matches the Critical category "an unauthorized deploy, rollback or merge." It is repeatable against any stack the attacker can name and any victim who can be lured to click, and is not scoped to a single repository/tenant.

### Likelihood Explanation
Preconditions: Shipit must be deployed with a session-authenticated user base (default), the merge-status widget/browser-extension feature must be reachable at `/merge_status` (default route), and a victim with an active Shipit session must be tricked into clicking inside a disguised iframe. No Shipit or GitHub secret is required by the attacker; cost is a single crafted webpage and standard clickjacking social engineering to get one click. This is realistically feasible and repeatable per-request/per-victim.

### Recommendation
- Do not set `X-Frame-Options: ALLOWALL` (or an equivalent permissive `Content-Security-Policy: frame-ancestors *`) on `MergeStatusController#show`; restrict framing to the specific first-party browser-extension origin only, or require an additional signed/scoped token proving the request originated from the extension.
- Do not derive the `stack`/PR `number` used to build the mutating enqueue/dequeue form purely from unauthenticated GET query parameters; validate that the resolved PR (`referrer`) genuinely belongs to the resolved `stack`'s repository before rendering the action buttons.
- Add explicit per-stack authorization (`require_permission!`) in `MergeStatusController#enqueue`/`#dequeue`, not just "logged in."
- Consider requiring a fresh, action-specific confirmation (e.g., re-render with a nonce tied to the specific stack+PR pair) rather than trusting a long-lived framed GET's form.

### Proof of Concept
Minitest plan under `test/controllers/merge_status_controller_test.rb` (extending the existing test file):

```ruby
test "enqueue can be triggered with attacker-chosen stack/number sourced from a framed GET, independent of victim intent" do
  victim = shipit_users(:walrus) # logged-in victim
  session_stub_login(victim)

  # Simulate the framed GET whose form target is fully attacker-controlled via query params
  get :show, params: {
    stack_id: "attacker-org/attacker-repo/master",
    referrer: "https://github.com/attacker-org/attacker-repo/pull/999"
  }
  assert_equal "ALLOWALL", response.headers["X-Frame-Options"]

  # Assert the rendered form target matches the attacker's chosen stack/number, not anything the victim selected
  assert_select "form[action=?]", enqueue_merge_request_path("attacker-org/attacker-repo/master", 999)

  # Simulate the victim's click: same session, PUT to the attacker-chosen path with valid CSRF token
  MergeRequest.expects(:request_merge!).with(
    stacks(:attacker_repo_master), 999, victim
  )
  put :enqueue, params: { stack_id: "attacker-org/attacker-repo/master", number: 999 }

  assert_response :success
end
```

Both sides of the equality checked: "`stack_id`/`number` submitted" (`attacker-org/attacker-repo/master`, `999`) vs "what the victim intended to enqueue" (unknown/unrelated PR on the attacker's page) — they diverge, confirming the vulnerability, while `current_user` correctly still resolves to `victim`, confirming identity attribution is intact but action targeting is not.
