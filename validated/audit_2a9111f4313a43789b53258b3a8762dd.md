### Title
Webhook organization used for signature verification is disconnected from the organization/repository the webhook handlers act on, allowing signature bypass to forge cross-repository events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify a webhook against using `repository.owner.login` taken from the untrusted JSON body itself. Every subsequent handler (`PushHandler`, `MembershipHandler`, `PullRequest::*Handler`) instead acts on `repository.full_name` / `organization.login`, also taken from that same untrusted body but not required to match the field used for verification. When Shipit is configured for multiple GitHub organizations (as documented and tested in `test/dummy/config/secrets_double_github_app.yml`) and any one of those organizations has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` unconditionally returns `true` for events "belonging" to that organization, letting an attacker forge a signature-free payload that names the unprotected org in `repository.owner.login` while pointing the handler-consumed `repository.full_name`/`organization.login` at a completely different, secret-protected org/repository.

which builds the verifying `GitHubApp` from `repository_owner`, itself parsed straight from the request body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an absent `webhook_secret` as "always verified": [3](#0-2) 

Multi-organization configuration is an explicitly supported/documented feature, and per-org `webhook_secret` is independently optional for each org: [4](#0-3) 

Once `verify_signature` passes (bypassed for the org with no secret), the same raw payload is dispatched to handlers, none of which re-check that the repository/organization they operate on matches the one used to select the verifying key. They instead re-parse independent fields from the same attacker-controlled body:
- `Handler#repository_name` used by `PushHandler` to find the `Stack`/`Repository` to sync: [5](#0-4) [6](#0-5) 
- `MembershipHandler` uses `params.organization.login` and `params.team` to create/find a `Team` and add/remove members, independent of the org used for signature verification: [7](#0-6) 

Because `repository.owner.login` (used for auth) and `repository.full_name`/`organization.login` (used for the actual write) are two independently-controlled fields in the same unsigned/attacker-produced JSON body, and because "no secret configured" causes verification to succeed for *any* signature (including none), an attacker can:
1. Craft a webhook body with `repository.owner.login` = `<org-with-no-webhook_secret>` (or omit signature entirely if none of the orgs enforce a secret) so `verify_signature` passes trivially.
2. Set `repository.full_name` to a Shipit-tracked repository belonging to a *different*, secret-protected organization, or set `organization.login` in a `membership` payload to a `Shipit.github_teams` handle.
3. POST this to `/webhooks`; `PushHandler` will call `stack.sync_github(expected_head_sha: params.after)` for the targeted stack, or `MembershipHandler` will add an attacker-chosen `login` as a member of a team that may satisfy `Shipit.github_teams` authorization (`User#authorized?`): [8](#0-7) 

This is the same class of bug as the report: a value is authenticated (the organization used to pick the signing key) while a *different* value drives the privileged action (the repository/organization actually written to), breaking the equality `verified_organization == acted_upon_repository_organization`.

### Impact Explanation
Depending on which handler is reached, the impact ranges from triggering unauthorized syncs/deploy-relevant state changes on arbitrary tracked repositories (`push`/`status`/`check_suite` events forging commit SHAs and CI status against a stack the attacker does not control) to escalating a fabricated user into `Shipit.github_teams`, which is used by `Authentication#force_github_authentication` to gate access to the whole Shipit instance. Both are explicitly listed impact categories: "an unauthorized deploy, rollback" and "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Exploitability requires an operator to have configured Shipit with multiple GitHub organizations (a documented, supported configuration) where at least one org's `webhook_secret` is left unset — a realistic and easy-to-hit misconfiguration since `webhook_secret` is marked optional in `docs/setup.md` and the example secrets templates ship with `webhook_secret: # nil`. No authenticated session, API token, or GitHub write access is required — only knowledge of the public `/webhooks` endpoint and the name of one configured organization without a secret.

### Recommendation
Do not select the verification key from attacker-controlled payload fields alone; instead, after choosing the `GitHubApp` for the claimed organization, verify that all identifiers relied upon by handlers (`repository.full_name`'s owner, `organization.login`, `team.organization`) belong to that same verified organization before dispatching to handlers. Additionally, do not allow `verify_webhook_signature` to silently succeed when `webhook_secret` is unset for one org while other orgs are configured with secrets — require a secret whenever more than one organization is configured, or reject webhooks for organizations without configured secrets rather than treating them as automatically verified.

### Proof of Concept
1. Configure Shipit for two GitHub orgs, e.g. `OrgOne` (has `webhook_secret`) and `OrgTwo` (no `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Send `POST /webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/protected-repo" }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "OrgTwo").verify_webhook_signature` returns `true` unconditionally (empty `webhook_secret`).
3. `WebhooksController#verify_signature` passes, and `PushHandler` looks up `Repository.from_github_repo_name("OrgOne/protected-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, affecting the `OrgOne`-protected stack despite the request never being validated against `OrgOne`'s secret.

Note: I was unable to fully trace `Shipit.github(organization:)`'s exact multi-org lookup implementation (the search results for its definition were truncated before this could be confirmed), so the precise mechanics of organization resolution when only a single org is configured could not be independently verified within this session — the finding is anchored specifically to the documented and tested multi-organization configuration path.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
