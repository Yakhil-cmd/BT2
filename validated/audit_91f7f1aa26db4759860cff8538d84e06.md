### Title
Cross-organization CI status forgery via webhook signature/repository binding mismatch enables unauthorized deploy triggering - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The yVault report describes a class of bug where a critical state-changing operation trusts an attacker-influenced value that was never itself validated against the value that was actually authenticated/checked (the donation vs. the share-price computation). In Shipit, the webhook pipeline has the analogous flaw: `WebhooksController#verify_signature` authenticates a webhook using the **organization** derived from the payload (`repository.owner.login` / `organization.login`) to pick the corresponding `GitHubApp` secret [1](#0-0) , but the handler that actually performs the write — `StatusHandler` — never re-checks that binding: it looks up and mutates `Commit` records purely by `sha`, with **no scoping to the repository/organization that was authenticated**.

### Finding Description
`verify_signature` fetches the `GitHubApp` for `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), and uses that app's `webhook_secret` to validate the HMAC signature: [2](#0-1) . This only proves the request was signed by *some* organization's configured GitHub App/secret in this Shipit installation — in a multi-organization deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications") an attacker who legitimately controls one tenant organization (Org B) can produce a validly-signed payload.

Once the signature check passes, `WebhooksController#create` dispatches the parsed JSON to all registered handlers for the event with no further binding to the authenticated organization: [3](#0-2) .

`StatusHandler` then performs the write using only the `sha` field from the same attacker-controlled body, with no repository/owner filter whatsoever: [4](#0-3) 

Because `Commit.where(sha: params.sha)` is global across the entire Shipit instance (all stacks/repositories), a commit SHA belonging to Org A's repository will be matched and updated even though the request was only authenticated as coming from Org B.

The same class of binding gap also exists in the other handlers, which resolve the target `Stack`/`Repository` via `payload.dig('repository', 'full_name')` — a second, independent field of the same untrusted body — rather than the `repository_owner` value that was actually used to select the verifying secret: [5](#0-4)  and e.g. [6](#0-5) . `StatusHandler` is the most severe instance because it doesn't even use `full_name`, so no coincidental consistency check exists at all.

**Binding broken (as an equality):** `organization authenticated by verify_signature (repository_owner)` should equal `organization owning the resource written by the handler`, but Shipit never enforces `verified_org == commit.stack.repository.owner`.

### Impact Explanation
An attacker holding legitimate but low-privilege webhook credentials for one organization/tenant (Org B) on a shared Shipit instance can forge a `status` webhook event that fabricates a `success` CI status on any commit SHA in **any other organization's** repository tracked by the same Shipit instance (Org A), via `Commit#create_status_from_github!`. If Org A's stack relies on commit status for `deployable?` checks (merge queue gating, continuous deployment gating), this can cause an unauthorized deploy or merge to occur on Org A's stack without any legitimate CI having passed and without the attacker ever holding credentials for Org A. This matches the "unauthorized deploy, rollback, or merge" / "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Requires the attacker to be a legitimate, credentialed tenant of a multi-organization Shipit deployment (a real, supported configuration per `docs/setup.md`), and requires knowledge of a target commit SHA (routinely public on GitHub). No repository write access, `ApiClient` token, or privileged Shipit account is needed — only the webhook signing secret for the attacker's own organization, which the attacker is entitled to possess. This is a realistic scenario for any Shipit instance shared across multiple orgs/teams.

### Recommendation
- In `WebhooksController`, after determining the verified `repository_owner`, thread that value through to handlers and require every handler that mutates state (`StatusHandler`, `PushHandler`, `CheckSuiteHandler`, PR handlers) to scope its lookup to a `Repository`/`Stack` whose `owner` matches the verified organization, rejecting the event otherwise.
- Specifically fix `StatusHandler#process` to filter `Commit` by the owning repository (joined through `stack: :repository`) matching `repository_owner`, not just by bare `sha`.
- More generally, make `repository_name`/`repository_owner` resolution a single trusted value computed once from the verified context, rather than two independently-read, unverified fields (`repository.full_name` in handlers vs. `repository.owner.login`/`organization.login` in the controller) from the same JSON body.

### Proof of Concept
1. Shipit instance configured with two orgs, `OrgA` (victim) and `OrgB` (attacker's own org), per `docs/setup.md`'s multi-app setup, each with its own `webhook_secret`.
2. Attacker legitimately knows `OrgB`'s webhook secret (it is their own GitHub App).
3. Attacker crafts a `status` event body:
```json
{
  "sha": "<victim-commit-sha-in-OrgA-repo>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/attacker-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgB_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "OrgB"`, fetches `Shipit.github(organization: "OrgB")`, and successfully verifies the signature (app/controllers/shipit/webhooks_controller.rb:24-30).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `OrgA`'s stack (no owner filter applied), and calls `create_status_from_github!`, marking it `success`.
7. If `OrgA`'s stack has continuous deployment or a merge queue gated on that status context, the forged green status can trigger an unauthorized deploy or merge — achieved entirely with `OrgB`'s own credentials.
