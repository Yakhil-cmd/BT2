### Title
Webhook signature verification is keyed off an unverified payload field, letting a secret‑less organization forge status/push events for repositories/commits belonging to any other tracked stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body [1](#0-0) . The handlers that actually act on the payload, however, read a *different* field - `repository.full_name` in `Handler#repository_name` [2](#0-1) , or nothing repository-scoped at all in `StatusHandler`, which matches purely on `sha` across the entire `commits` table [3](#0-2) . There is no code anywhere that checks these two values are consistent. Combined with the fact that `webhook_secret` is documented and explicitly supported as optional/blank per organization - `verify_webhook_signature` returns `true` unconditionally when no secret is configured [4](#0-3)  - this breaks the binding "the organization that authenticated == the repository/commit that is written."

### Finding Description
`Shipit::WebhooksController` is mounted with no authentication other than the per-organization webhook signature:

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` is looked up by an attacker-controlled string, and multi-organization deployments (a documented, supported configuration - see `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml`) allow each organization to have its own, independently configured `webhook_secret`, which is explicitly optional ("Webhook secret (optional)" in `docs/setup.md`). When it is `nil`, `verify_webhook_signature` short-circuits to `true`:

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

So any unauthenticated caller can pick an organization entry that has no secret configured, put that organization's login in `repository.owner.login`/`organization.login` to sail through `verify_signature`, and then put **any other value** in `repository.full_name` (the field every `Handler` subclass actually uses to resolve the target `Repository`/`Stack`) [2](#0-1) , or in the `status` handler simply supply an arbitrary `sha` that exists on a totally different repository's commit, since the lookup is global and repo-unscoped:

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

The "equality" the engine is supposed to enforce is:
`organization authenticated by verify_signature == organization that owns the repository/commit being mutated by the handler`

Before the attack: only GitHub itself, holding the correct per-org `webhook_secret`, can produce a signature that `verify_signature` accepts for a given org, and that org's real webhooks only ever reference that org's own repositories.
After the attack: an attacker who only knows that *some* tracked organization (Org A) has no `webhook_secret` configured can send an arbitrarily-crafted, unsigned-effectively request whose `repository.owner.login` = "Org A" (to pass `verify_signature`) but whose `repository.full_name`/`sha` targets a completely different, unrelated organization's (Org B) stack/commit - something `verify_signature` never checks.

### Impact Explanation
Via `StatusHandler`, an attacker can inject an arbitrary `state`/`context`/`description` "status" onto any commit anywhere in the database purely by SHA, regardless of which organization/repository that commit belongs to. Shipit's merge queue and required-CI (`ci.require`) gating rely on these `Status` rows to decide if a commit is safe to merge/deploy. Forging a green status for a required context on a commit that actually failed or was never checked can let a pending commit pass the merge queue's status validation and be merged/deployed - an unauthorized deploy/merge, matching the Critical-impact bucket ("an unauthorized deploy, rollback or merge"). Via `PushHandler`, an attacker can also force `GithubSyncJob` to run for stacks of an org they don't control (cross-repository interaction), although since the actual commit fetch still goes through the real org's own GitHub credentials this is a secondary/lower-severity effect.

The practical trigger condition (an organization configured without `webhook_secret`) is not hypothetical misconfiguration outside the documented setup - `docs/setup.md` explicitly calls the webhook secret "(optional)", and the engine's own test fixtures (`test/dummy/config/secrets_double_github_app.yml`) ship two organizations both configured with `webhook_secret: # nil`, i.e., this is a tested, supported configuration shape, not an unsupported deployment.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (documented/supported), and (2) at least one tracked organization configured without a `webhook_secret` (documented as optional). Given those two documented conditions, exploitation requires no credentials, no session, no API token, and no knowledge of any secret - just an HTTP POST to the public `/webhooks` endpoint with attacker-chosen JSON. This is a low-effort, unauthenticated attack once the environmental precondition holds.

### Recommendation
Cross-check that the organization used to select/verify the webhook signature is the *same* organization that owns the repository referenced by the payload fields the handlers actually act on (`repository.full_name`, and any `sha`-based lookups should be scoped to a repository derived from the verified organization, not searched globally). Additionally, consider disallowing/warning on organizations configured with a blank `webhook_secret` in multi-org deployments, since a blank secret for any one org effectively disables authentication for every incoming webhook whose forged `owner.login`/`organization.login` selects that org.

### Proof of Concept
Assume a Shipit instance tracks two GitHub orgs: `OrgA` (configured with `webhook_secret: nil`, per the documented optional setting) and `OrgB` (a securely configured org with tracked stacks/commits).

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<real sha of a pending commit belonging to an OrgB-owned stack>",
  "state": "success",
  "context": "required-ci-check",
  "description": "forged",
  "repository": { "owner": { "login": "OrgA" } }
}
```

`WebhooksController#repository_owner` resolves to `"OrgA"` [5](#0-4) ; `Shipit.github(organization: "OrgA")` has `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/incorrect) `X-Hub-Signature` header [4](#0-3) . The request is accepted and dispatched to `StatusHandler`, which finds the commit purely by `sha` - with no relation whatsoever to `OrgA` - and creates a forged `success` status on it [3](#0-2) , potentially satisfying `OrgB`'s required-status gate for merge/deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
