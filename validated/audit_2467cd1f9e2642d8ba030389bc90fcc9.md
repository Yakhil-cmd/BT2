### Title
Malicious swap routes can drain unrelated caller wallet tokens through Soroban authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

An attacker can craft a controller swap route that causes a malicious route venue to call `token.transfer(caller, attacker, amount)` while the caller’s top-level authorization is active. [1](#0-0) [2](#0-1) 

Because route venues are selected from caller-provided route data rather than restricted to immutable protocol-approved contracts, the stolen asset need not be part of the lending operation or even listed by the protocol. [3](#0-2) [4](#0-3) 

### Finding Description

Controller strategy entrypoints authenticate the caller with `caller.require_auth()` and then verify that the caller owns or delegates the target account. [5](#0-4) [6](#0-5) 

For `swap_collateral`, the controller withdraws account collateral into its own custody and invokes the swap path with caller-provided opaque `swap` bytes. [7](#0-6) [8](#0-7) 

The same route mechanism is reachable from `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [9](#0-8) [10](#0-9) [11](#0-10) 

`swap_tokens` validates only that the route is nonempty, authorizes the intended controller-held input transfer, invokes the configured router, and checks only the input spend and positive output receipt. [12](#0-11) [13](#0-12) 

It does not inspect the route’s venue addresses or restrict which contracts execute beneath the caller-authorized root invocation. [14](#0-13) [3](#0-2) 

Soroban simulation records a nested `token.transfer(caller, attacker, amount)` under the caller’s `swap_collateral` authorization, and enforced authorization accepts that transfer once the caller signs the poisoned tree. [15](#0-14) [16](#0-15) 

### Impact Explanation

A malicious route can steal any token balance held directly by the caller while still delivering enough swap output to satisfy the controller’s measured-output check. [17](#0-16) [18](#0-17) 

The test demonstrates theft of a completely unlisted wallet token while the collateral swap itself succeeds normally. [19](#0-18) [20](#0-19) 

This is theft of user funds beyond the amount intentionally supplied to the swap. [1](#0-0) 

### Likelihood Explanation

The attacker cannot invoke this path directly against another account because `require_owner_or_delegate` limits the strategy to the account owner or an active delegate. [21](#0-20) 

The practical attack is therefore a malicious quote or route payload that induces the victim to sign the authorization produced by simulation. [22](#0-21) 

Since the exploit requires victim authorization but permits an unprivileged attacker to prepare the malicious venue and route, the finding is best classified as High severity. [23](#0-22) [16](#0-15) 

### Recommendation

Do not invoke caller-controlled venue contracts while the account owner’s authorization is active. [24](#0-23) 

Restrict route venue addresses to governance-approved, immutable pool contracts and reject routes whose address registry contains any unapproved executable venue. [25](#0-24) [3](#0-2) 

Until that invariant is enforced, clients must decode the complete route and reject any simulated authorization tree containing children other than the expected token pull. [26](#0-25) 

### Proof of Concept

1. Deploy a malicious pool contract configured with the victim address, an unrelated token held by the victim, the attacker recipient, and the victim’s full balance. [27](#0-26) 

2. Build a swap payload whose pool registry entry points to the malicious contract while retaining normal `token_in` and `token_out` assets and a fair minimum output. [23](#0-22) 

3. Ask the victim to execute `swap_collateral(caller, account_id, current, amount, new, swap)` with that payload. [28](#0-27) 

4. During simulation, the malicious venue’s `token.transfer(victim, attacker, amount)` is recorded as a child of the victim’s `swap_collateral` authorization. [29](#0-28) 

5. Once the victim signs that tree, the malicious transfer succeeds, the unrelated wallet token reaches the attacker, and the fair swap output is still deposited. [16](#0-15)
