### Title
Webhook signature is verified against `repository.owner.login` while writes are routed by the untied `repository.full_name` field, enabling cross-organization/cross-repository unauthenticated writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App configuration (and thus which `webhook_secret`) to validate a webhook against using `repository.owner.login` from the *unverified* JSON body, but every event handler routes its side effects (stack sync, commit statuses, membership changes, etc.) using a separate field of the same body, `repository.full_name`. Nothing binds these two fields together, and `GithubApp#verify_webhook_signature` trivially returns `true` when the selected organization has no `webhook_secret` configured. An attacker who can reach the webhook endpoint of any org configured *without* a secret can forge a payload whose `repository.full_name` points at a stack belonging to a *different*, secret-protected organization/repository, causing unauthenticated writes to that victim stack.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to check against purely from the payload: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no configured `webhook_secret`: [3](#0-2) 

Once the request passes this check (trivially, for an org with a blank secret), `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw parsed payload to handlers. Every handler resolves the *repository/stack it mutates* independently, from `repository.full_name`, not from the `repository.owner.login`/`organization.login` that was used to pick the signing secret: [4](#0-3) 

For example, `PushHandler` uses this to find and sync stacks: [5](#0-4) 

This breaks the intended equality **"organization authenticated == repository/stack written."** The authentication boundary is `repository.owner.login` (used only to select `webhook_secret`); the write boundary is `repository.full_name` (used to look up `Repository`/`Stack`). Because the JSON body is attacker-controlled prior to verification and these two fields are never cross-checked, an attacker only needs one org on the Shipit instance configured without a `webhook_secret` (an explicitly supported, optional configuration per `docs/setup.md`, "If you've set a webhook secret ... you should copy it here") to forge events that mutate any *other* org's/repo's stacks that ARE protected by a real secret.

### Impact Explanation
This yields cross-repository/cross-organization writes without any valid signature for the targeted repository: forged `push` events can trigger `stack.sync_github` (and thus deploy pipeline state changes) for a victim stack, forged `status`/`check_suite` events can inject fake commit statuses/check runs affecting deployability decisions, and forged `membership` events can create/delete `Team`/`Membership` records, all while nominally authenticating only against an unrelated, secret-less organization. This matches the "cross-repository writes" / "unauthorized deploy" high-impact category.

### Likelihood Explanation
Requires no credentials: only that the Shipit instance has at least one configured GitHub organization without a `webhook_secret` set (a documented, optional field) and that the attacker knows or guesses a target repository's `full_name`. No repository write access, API token, or session is needed — only network reachability to `POST /github/webhooks` with a crafted `X-Github-Event` header and JSON body, and a matching (or absent) signature for the org chosen via `repository.owner.login`.

### Recommendation
Bind signature verification to the exact repository being mutated, not just its stated owner: derive the org/repo used for handler dispatch from the same value validated by the signature, and reject any request where `repository.full_name`'s owner does not match `repository_owner`. Additionally, make `webhook_secret` mandatory (fail closed) for every configured organization instead of allowing `verify_webhook_signature` to return `true` when it is blank.

### Proof of Concept
1. Configure two GitHub orgs on the Shipit instance: `secured-org` (has `webhook_secret` set, owns `secured-org/prod-repo` with an active `Stack`) and `open-org` (no `webhook_secret` configured, exists on the same instance for any legitimate reason).
2. As an unauthenticated attacker, `POST /github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "attackercontrolledsha",
  "repository": {
    "full_name": "secured-org/prod-repo",
    "owner": { "login": "open-org" }
  }
}
```
3. `WebhooksController#repository_owner` returns `"open-org"`; `Shipit.github(organization: "open-org")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header — see [6](#0-5) .
4. `PushHandler#process` ( [5](#0-4) ) resolves `repository_name` as `"secured-org/prod-repo"` via `Handler#repository_name` ( [7](#0-6) ) and calls `stack.sync_github(expected_head_sha: "attackercontrolledsha")` on the victim's protected stack — an unauthenticated write despite `secured-org` having a real webhook secret configured.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
