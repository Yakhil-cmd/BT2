### Title
Webhook signature is verified per-organization but `StatusHandler` writes commit statuses unscoped by repository, allowing cross-repository status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the `webhook_secret` of whichever organization is named in the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) . That authenticated identity is `repository_owner`, computed purely from payload fields [2](#0-1) . Once the signature passes, the raw payload is dispatched to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . However, `StatusHandler#process` never re-checks that the commit being updated actually belongs to a stack tied to the verified repository/organization — it resolves target records with a global, unscoped query: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . This breaks the equality that should hold: `organization authenticated by verify_signature == organization/repository whose Commit rows are written`.

### Finding Description
The base `Handler` class does provide a repository-scoping helper, `stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` where `repository_name` is `payload.dig('repository', 'full_name')` [5](#0-4) . `PushHandler`, for instance, correctly uses this scoping before acting on any stack [6](#0-5) . `StatusHandler`, by contrast, ignores `stacks`/`repository_name` entirely and looks up commits by SHA across the whole instance-wide `Commit` table, which spans every `Stack`, every `Repository`, and (because `Shipit.github` is keyed per organization) potentially multiple independently-configured GitHub organizations sharing a single Shipit deployment [4](#0-3) .

Because git commit SHAs are content-addressed, identical SHAs legitimately occur across repositories that share history (forks, mirrors, cherry-picked/rebased commits with identical tree/parent/author/timestamp data). Any GitHub organization/repository configured in this Shipit instance can trigger a real, correctly-signed `status` webhook (e.g., via the GitHub Statuses API, or CI configured on that repo) whose payload's `sha` happens to match a commit that also exists in a different, more sensitive stack belonging to a different organization. `WebhooksController` only proves the payload was genuinely sent by *some* configured organization's GitHub — it does not, and cannot, prove that organization owns the commit being mutated. `StatusHandler` then blindly applies the status to every `Commit` row across the database with that SHA, regardless of which repository/organization owns it.

### Impact Explanation
Commit statuses drive Shipit's CI/status-check gating for merges and deploys (surfaced through `Commit#create_status_from_github!`, `Status`, and `Status::Group`, per [7](#0-6)  and related status models). By forging (via a legitimately-signed but attacker-influenced) status webhook from one onboarded, lower-trust repository, an attacker can inject a fabricated `success`/`failure` status onto a commit belonging to an entirely different repository/stack that they have no access to, because the write is not scoped to the verified organization. This is a cross-repository write: the authorization boundary is "webhook signed by organization X" but the effect crosses into "commit belonging to organization Y's stack," directly matching the required binding-break class (organization authenticated vs. repository written) and the "cross-repository writes" impact criterion.

### Likelihood Explanation
Exploitation requires the attacker to control (or have webhook-triggering privileges on, e.g. via the Statuses API) at least one repository already onboarded into the shared Shipit instance, and for a SHA collision/reuse to exist between their repository and the target stack's commit history (realistic for forks, mirrors, or shared upstream history — a common pattern in monorepo/fork-based engineering workflows that Shipit is designed to serve). No `ApiClient` token, session, or GitHub App private key is needed; only a standard, correctly-signed webhook from an already-integrated repository is required, which is within the unprivileged-attacker model defined by the rules (the attacker never needs privileged access to the *victim* repository).

### Recommendation
`StatusHandler` (and any other handler that queries records independent of `stacks`) must scope its writes to the repository/organization actually verified by `WebhooksController#verify_signature`, e.g., by joining through `Commit -> Stack -> Repository` and filtering to `repository_name` (or the verified `repository_owner`) before calling `create_status_from_github!`, mirroring the pattern already used by `Handler#stacks` and `PushHandler`.

### Proof of Concept
1. Attacker's own repository `attacker-org/repo-x` is legitimately onboarded as a Stack in the shared Shipit instance (e.g., a low-trust internal fork).
2. Attacker crafts a commit in `repo-x` whose tree/parents/author/committer timestamps are identical to a commit already present in the victim's stack `victim-org/critical-repo` (achievable when the repos share history, e.g. a fork/mirror relationship) — the resulting SHA is identical in both.
3. Attacker uses the GitHub Statuses API (which they legitimately control for `repo-x`) to set a `success` status on that commit in `repo-x`. GitHub sends a `status` webhook to Shipit, correctly signed with `attacker-org`'s real `webhook_secret`.
4. `WebhooksController#verify_signature` verifies the signature against `Shipit.github(organization: 'attacker-org')` and passes [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` unscoped, matches the commit row belonging to `victim-org/critical-repo`'s stack, and calls `create_status_from_github!`, writing an attacker-controlled `success` status onto the victim's commit [4](#0-3) .
6. If `victim-org/critical-repo`'s deploy pipeline gates on that status context, the forged status can unblock or influence a deploy decision on a stack the attacker never had access to — a cross-repository write achieved purely by owning an unrelated, lower-privileged repository.
