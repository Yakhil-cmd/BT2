### Title
Webhook signature verification uses the unverified payload's own organization claim, allowing cross-organization Team-membership forgery and OAuth authorization escalation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC secret) to validate a webhook against by reading the organization straight out of the *unverified* request body, then validates the signature against that same body. `Shipit::Webhooks::Handlers::MembershipHandler` subsequently looks up the `Team` to mutate purely by the numeric `team.id` claimed in that same untrusted body, without re-checking that the claimed `organization.login` matches the `organization` already recorded on that `Team`. This mirrors the reported bug class: a field (`_fromChain` / here, "which org produced this webhook") is trusted and acted upon without being cryptographically bound to the data it authorizes.

### Finding Description
`verify_signature` computes the org used for verification from the JSON payload itself, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

For the `membership` event, there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` — an attacker-controlled string. Because Shipit supports multiple installed GitHub Apps (one per organization, each with its own `webhook_secret`, as documented), an attacker who has installed their own Shipit-compatible GitHub App on an organization they control (`attacker-org`) legitimately knows that org's `webhook_secret`. They can therefore craft an arbitrary raw JSON body, set `organization.login` to `attacker-org`, and produce a valid `X-Hub-Signature` for it themselves — `verify_signature` passes because it only checks "was this body signed by whoever claims to be `attacker-org`", not "is this event actually about `attacker-org`'s resources."

The `MembershipHandler` then processes the (correctly-signed-by-attacker-org) payload and finds the `Team` to modify solely by GitHub's numeric team id, ignoring that the request came from a different verified organization than the one that actually owns that team: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` finds any existing `Team` row with that `github_id`, regardless of which organization the signature was actually verified against. Once found, `team.add_member(member)` adds the attacker-specified `member.login` (auto-vivified via `User.find_or_create_by_login!`) to that team.

This directly affects authorization: `User#authorized?` grants access whenever the user is a member of any team in `Shipit.github_teams`: [4](#0-3) 

So the equality that should hold — "organization whose signature was verified" == "organization owning the team/resource being mutated" — is broken. The webhook endpoint is public/unauthenticated by design (it exists specifically to receive unauthenticated GitHub calls), so this requires no Shipit session, API token, or GitHub write access to the victim's repositories — only that the attacker controls one organization/GitHub App that is also configured in this Shipit instance's `secrets.yml` (the documented [multi-organization setup](docs/setup.md#using-multiple-github-applications)). [5](#0-4) 

The same organization/full_name split also affects `Handler#stacks`, which resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` while the signature was checked against `payload.dig('repository', 'owner', 'login')` — two different sub-fields of the same untrusted body: [6](#0-5) 

### Impact Explanation
Adding an attacker-controlled GitHub login to a `Team` referenced by `Shipit.github_teams` escalates that login into `Shipit`'s OAuth-team authorization gate (`User#authorized?`), which is explicitly listed as a High-severity impact ("escalation into `Shipit.github_teams` authorization"). Once authorized, the attacker can log in via OAuth as that GitHub user and gain full Shipit UI/API access, including triggering deploys/rollbacks on stacks the team is scoped to.

### Likelihood Explanation
Exploitability requires only that the attacker's own organization (with its own GitHub App and `webhook_secret`) is one of the organizations configured in this Shipit instance — a legitimate, self-service setup step documented for multi-org support — plus knowledge of the numeric GitHub `team_id` used for the target authorization team (discoverable via GitHub's public/semi-public team APIs, or simply by causing the membership event for the real team once and observing/replaying the `github_id`). No repository write access, session, or API token to the victim org is needed, since the endpoint is intentionally unauthenticated and only signature-gated.

### Recommendation
Do not select the verification org from the same untrusted payload field family used later for business logic. Specifically:
- Bind the org actually used to look up resources (`Team#organization`, `Repository#owner`) to the org that was cryptographically verified, and reject the webhook if they diverge, in `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb`) and in `Handler#stacks`/`Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb`).
- In `Team.find_or_create_by!(github_id: params.team.id)`, also scope the lookup by the organization verified during signature check, not just the numeric id.
- Consider passing the verified organization from `WebhooksController` down to handlers explicitly, instead of letting handlers re-derive it from the raw payload.

### Proof of Concept
1. Operator configures Shipit with two organizations in `config/secrets.yml` per the documented multi-org setup: `target-org` (owns the real authorization team, e.g. GitHub team id `555`, `organization: "target-org"`, referenced in `Shipit.github_teams`) and `attacker-org` (installed by the attacker, who therefore knows `attacker-org`'s `webhook_secret`).
2. Shipit already has a `Team` row with `github_id: 555, organization: "target-org"` (created earlier via a legitimate membership webhook, or provisioned directly).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 555, "name": "Developers", "slug": "developers", "url": "https://api.github.com/..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker" }
}
```
   signing it with `attacker-org`'s own `webhook_secret` (which the attacker legitimately possesses) as `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"` (see `app/controllers/shipit/webhooks_controller.rb:59-62`) and verifies successfully since the signature matches `attacker-org`'s secret.
5. `MembershipHandler#process` finds the existing `Team` with `github_id: 555` (the real `target-org` team) and calls `team.add_member(User.find_or_create_by_login!("attacker"))` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`).
6. `attacker` is now a member of a team in `Shipit.github_teams`; `User#authorized?` returns `true` for that account (`app/models/shipit/user.rb:80-82`), granting them OAuth-authorized access to Shipit.

          team = find_or_create_team!

          case params.action
          when 'added'
            team.add_member(member)

          end
        end

        end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
