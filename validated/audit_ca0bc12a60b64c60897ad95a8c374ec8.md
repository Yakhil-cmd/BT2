### Title
Webhook signature verification is keyed to `repository.owner.login`/`organization.login`, but every handler resolves its target Stack/Repository from the unauthenticated `repository.full_name` field, allowing an attacker who controls one configured GitHub organization's webhook secret to forge events against a different repository's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner` (`repository.owner.login`, falling back to `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Stack`/`Repository` to act on using a completely different, unauthenticated field: `repository.full_name`. Because nothing binds these two fields together, a party who knows the webhook secret for organization "B" (e.g. an admin of a second organization onboarded onto the same multi-tenant Shipit instance) can forge a raw HTTP POST whose HMAC is computed with organization B's secret but whose `repository.full_name` points at a stack belonging to organization A, causing Shipit to sync/act on a repository the forger does not control.

**The broken binding (equality that should hold but doesn't):**
`organization_that_authenticated(repository.owner.login) == organization_of(repository.full_name)`

This is exactly the analog class called out in the rules: "an organization that authenticated versus the repository that is written." Nothing in `verify_signature` or in `WebhooksController#create` cross-checks that the `full_name` used by the handlers actually belongs to the organization whose secret validated the signature.

### Impact Explanation
In a multi-organization Shipit deployment (`Shipit.github_organizations` returning more than one org, each with an independently configured GitHub App/webhook secret — a documented, supported configuration in `lib/shipit.rb`/`docs/setup.md`), any party who is a legitimate admin of Organization B's GitHub App (and therefore knows Organization B's `webhook_secret`) can:
1. Craft a raw JSON payload with `repository.owner.login = "org-b"` (so `verify_signature` picks Org B's app/secret) and HMAC-sign it themselves with Org B's known secret, bypassing GitHub entirely (this is a direct HTTP POST to the engine's webhook endpoint, not a replay of a real GitHub-signed webhook).
2. Set `repository.full_name = "org-a/some-private-repo"` — a repository belonging to a different, unrelated organization A that they have no access to.
3. Send this to `POST /github_hooks` (or whichever action maps to `create`).

Because `verify_signature` succeeds (signature matches Org B's secret) and `PushHandler#stacks` resolves the target purely from `full_name`, Shipit will invoke `stack.sync_github(expected_head_sha:)` for `org-a/some-private-repo`'s stacks, even though the forger has no legitimate relationship to Organization A's repository. If continuous-deployment is enabled for that stack, this cross-organization forced sync can lead to unintended/unauthorized deploy activity being triggered on Organization A's stack, and it certainly allows an unauthenticated-with-respect-to-Org-A write into Org A's stack/commit state — a cross-repository write triggered without the corresponding organization's authorization, matching the report's stated Critical-tier impact bucket ("cross-repository writes... or an unauthorized deploy").

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations, each with a webhook secret known to a different, mutually-untrusted party (Shipit explicitly supports and documents this via `github_app_config`/`TOP_LEVEL_GH_KEYS`, `docs/setup.md`). Given that setup, the exploit requires no privileged Shipit session, `ApiClient` token, or GitHub write access to the target repository — only knowledge of one's own organization's configured webhook secret and the ability to POST arbitrary JSON directly to the public webhook endpoint. That is a normal amount of access for an org admin who is *not* trusted with Org A's data, making this a medium-likelihood, unprivileged-attacker path.

### Recommendation
Bind the field used for authentication to the field used for repository resolution: after `verify_signature` determines `repository_owner`, handlers (or the controller) should verify that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` before dispatching to handlers, e.g. reject the request (422) if `full_name.split('/').first.casecmp?(repository_owner)` is false. Alternatively, have `Repository.from_github_repo_name`/`Handler#repository_name` derive the owner strictly from the same authenticated field used in `verify_signature`, rather than trusting an independent, unauthenticated `full_name` string.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`, `lib/shipit.rb#github_app_config`).
2. As an admin of `org-b` (knows `org-b`'s `webhook_secret`), craft:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen or arbitrary sha>",
  "repository": {
    "owner": { "login": "org-b" },
    "full_name": "org-a/private-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-b-secret, payload)>` and set `X-Github-Event: push`.
4. POST the payload to the Shipit webhook endpoint.
5. `verify_signature` resolves `Shipit.github(organization: "org-b")` and successfully verifies the signature using `org-b`'s secret [8](#0-7) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-a/private-repo")` [9](#0-8)  and enqueues `GithubSyncJob` for Org A's stack, even though the signature only proves control of Org B.

**Note:** I was unable to fully verify the internal implementation of `Stack#sync_github` (only its call sites and `GithubSyncJob#perform` were inspected) or how `Stack.trigger_deploy`/continuous-delivery scheduling reacts to a forced sync in this exact scenario, since these deeper code paths were not returned in full by the indexed search. If precise confirmation of downstream deploy automation is needed, a Devin session with full repository access would be required to trace `Stack#sync_github` and the continuous-delivery scheduler in full.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
