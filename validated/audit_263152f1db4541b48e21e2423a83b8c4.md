### Title
Membership webhook signature verification uses attacker-controlled `organization.login`, decoupled from the numeric `team.id` being mutated, allowing cross-tenant team membership injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret`) used to authenticate a `membership` event via `repository_owner`, which for this event type falls back to the attacker-controlled `organization.login` field in the payload. `MembershipHandler#process` then mutates the `Team`/`Membership` graph keyed only on the numeric `team.id`, with no check that the verifying organization actually owns that team, letting an attacker who registers their own org in Shipit's multi-tenant config forge a signed webhook that adds an arbitrary GitHub login as a member of any pre-existing team recorded in the database — including a victim team used in `Shipit.github_teams` authorization.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`Shipit.github(organization: repository_owner).organization == Team.find_by(github_id: params.team.id).organization`

- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . For a `membership` event there is no `repository` key, so this falls back entirely to the attacker-supplied `organization.login`.
- `verify_signature` then does `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)` [2](#0-1) . Since the attacker owns `attacker-org` and it is registered in Shipit's multi-tenant config with its own `webhook_secret`, `verify_webhook_signature` (HMAC-SHA1 compare against that org's own secret) succeeds [3](#0-2) , even though the payload's `team.id` has nothing to do with `attacker-org`.
- `MembershipHandler#process` then runs: `team = find_or_create_team!` looks up `Team.find_or_create_by!(github_id: params.team.id)` [4](#0-3) . If a team with that `github_id` already exists (created earlier by a legitimate webhook from the real owning org), the creation block is skipped and `team.organization` is left untouched — but the handler proceeds to `member = User.find_or_create_by_login!(params.member.login)` and `team.add_member(member)` [5](#0-4) , which appends a new `Membership` row for an attacker-chosen login into that pre-existing team, unconditionally [6](#0-5) .
- That team may be one of `Shipit.github_teams`, which is the exact set checked by `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [7](#0-6) , and `Shipit.github_teams` is populated independently via `github.oauth_teams` (default org's OAuth config), decoupled from the per-org `Shipit.github(organization: ...)` webhook verification path used here [8](#0-7) .
- No code in this path re-validates that `params.organization.login` matches the `organization` column already stored on the found `Team`, so the entity that authenticated the webhook (`attacker-org`) is never checked against the entity actually being mutated (the pre-existing team, and by extension its owning org). `require_permission!`/`force_github_authentication` are irrelevant here since `WebhooksController` doesn't use them; `drop_unhandled_event` only filters unregistered event types, not payload ownership.

The question's proposed proof (asserting `team.organization != 'attacker-org'`) does not hold as stated, because `find_or_create_by!`'s block only executes on record creation — an already-existing team's `organization` column is left as-is. However, the underlying primitive is real and arguably worse: the attacker doesn't need to change the `organization` column, they just need `team.add_member` to succeed, which it does unconditionally for any already-registered team `github_id`, regardless of which org's secret verified the request.

### Impact Explanation
An attacker who registers their own organization in Shipit's multi-tenant GitHub config can forge `membership` webhooks signed with their own known `webhook_secret` and add an arbitrary GitHub login (including a login they control that has no real GitHub membership in the victim org/team) as a `Membership` of any team already present in Shipit's database by numeric `github_id`. If that team is one of `Shipit.github_teams`, the injected user passes `User#authorized?` and gains full access to every stack in the Shipit instance — deploys, rollbacks, task streams — matching the "escalation into `Shipit.github_teams` authorization" High-severity category. The attack is repeatable against any team whose `github_id` the attacker can obtain (team IDs are visible via GitHub's team API/URLs and are not secret), and it is cross-tenant: an org that never granted the attacker anything is the one whose access-control team gets polluted.

### Likelihood Explanation
Preconditions required: (1) Shipit is configured in multi-tenant mode with more than one organization's `GithubApp`/`webhook_secret`; (2) the attacker's own GitHub org is one of the registered tenants (plausible in open, self-service multi-tenant deployments, but requires operator-approved onboarding in most real deployments — this is the main limiting factor); (3) the target team's numeric `github_id` must already exist in Shipit's DB (created by a prior legitimate `membership` webhook) and be discoverable by the attacker. Given these, attacker cost is low: one crafted HTTP POST, self-signed with a secret they legitimately possess for their own org. Feasibility depends heavily on precondition (2), which requires the operator to have onboarded the attacker's org as a tenant — this is a nontrivial precondition in most single/dual-tenant Shipit deployments, but the code contains no defense against it, so it should be treated as a real gap for any environment where tenant onboarding is easy or self-service.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally for any handler acting on a payload where the verifying organization can diverge from the payload's referenced entity), verify that `params.organization.login.casecmp?(team.organization)` before performing any mutation (`add_member`/`delete`), and reject/no-op if they don't match. More fundamentally, `WebhooksController#repository_owner` should not silently trust `organization.login` as equivalent to `repository.owner.login` for authorization-sensitive events like `membership`; handlers that mutate team membership should independently re-assert that the authenticated org matches the team's recorded org before writing.

### Proof of Concept
```ruby
test "membership webhook cannot add a member to a team owned by a different, already-registered organization" do
  # Precondition: team already exists, created by legitimate webhook from victim org
  victim_team = shipit_teams(:some_team) # organization: "victim-org", github_id: 12345

  # Attacker owns "attacker-org", registered in Shipit's multi-tenant config with its own webhook_secret
  payload = {
    action: "added",
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: "attacker-org" },
    member: { login: "attacker-controlled-login" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_org_webhook_secret, payload)

  post shipit.github_webhooks_path,
       params: payload,
       headers: { "X-Github-Event" => "membership", "X-Hub-Signature" => signature, "Content-Type" => "application/json" }

  assert_response :ok

  # Assert the binding: verifying org != team's actual owning org, yet membership was still written
  assert_not_equal "attacker-org", victim_team.reload.organization
  assert victim_team.members.exists?(login: "attacker-controlled-login"),
         "attacker was able to inject membership into victim-org's team despite signing with attacker-org's own secret"

  # Assert downstream authorization impact
  injected_user = Shipit::User.find_by(login: "attacker-controlled-login")
  assert injected_user.authorized?, "injected user now passes Shipit.github_teams authorization check"
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
