### Title
`ProxyType::NonTransfer` fail-open `is_superset` wildcard lets a non-transfer proxy self-escalate to `OnDemandOrdering` / `Auction` sub-proxies and reach calls its own filter denies - ([File: polkadot/runtime/rococo/src/lib.rs])

### Summary
`pallet_proxy` authorizes `add_proxy`/`remove_proxy` purely through `ProxyType::is_superset`, never consulting `filter` for that decision [1](#0-0) . Parity already fixed and regression-tested exactly this bug class on Asset Hub Westend, where `NonTransfer` falsely declared itself a superset of `Governance` while its filter denied calls `Governance` admitted [2](#0-1) [3](#0-2) . The relay-chain runtimes (`polkadot/runtime/rococo`, `polkadot/runtime/westend`, and `substrate/frame/staking-async/runtimes/rc`) still use the older, unhardened wildcard `(ProxyType::NonTransfer, _) => true` instead of an explicit allow-list, so the same invariant violation persists there for at least two proxy types whose filters `NonTransfer` does not fully admit.

### Finding Description
In `polkadot/runtime/rococo/src/lib.rs`, `ProxyType::is_superset` states:
```
(ProxyType::NonTransfer, _) => true,
``` [4](#0-3) 
i.e. `NonTransfer` claims to be a superset of *every* other `ProxyType`, including `ProxyType::OnDemandOrdering` and `ProxyType::Auction`.

`ProxyType::OnDemandOrdering`'s filter admits `RuntimeCall::OnDemandAssignmentProvider(..)` unconditionally [5](#0-4) . `NonTransfer`'s own filter never lists `RuntimeCall::OnDemandAssignmentProvider` at all [6](#0-5) , so `ProxyType::NonTransfer.filter(&on_demand_call)` returns `false` — `NonTransfer` is explicitly denied all on-demand-order calls, yet `is_superset` says it dominates `OnDemandOrdering`.

Similarly, `ProxyType::Auction`'s filter admits `RuntimeCall::Registrar { .. }` (every variant, unqualified) [7](#0-6) , while `NonTransfer`'s filter only admits `Registrar::register`, `deregister`, and `reserve`, with an explicit comment "Specifically omitting Registrar `swap`" [8](#0-7) .

Because `pallet_proxy::do_proxy` gates `add_proxy`/`remove_proxy` only on `def.proxy_type.is_superset(proxy_type)` [1](#0-0) , a delegate who only holds a `NonTransfer` proxy over a victim account can:
1. Call `Proxy::add_proxy(origin=proxy-acting-as-real, delegate, ProxyType::OnDemandOrdering, delay)` through the existing `NonTransfer` proxy — allowed, since `is_superset` returns `true` for `(NonTransfer, OnDemandOrdering)`.
2. Immediately use the newly created `OnDemandOrdering` proxy relationship to dispatch `OnDemandAssignmentProvider` calls as the real account — calls that `NonTransfer`'s own `filter` fully denies.

The same mechanism lets a `NonTransfer` delegate add an `Auction` sub-proxy and then call `paras_registrar::swap`, which `NonTransfer` explicitly omits.

### Impact Explanation
`ProxyType::NonTransfer` is documented and designed so a delegate cannot move the delegator's funds/assets (`Balances`, `Assets`, etc. are denied) [6](#0-5) . The on-demand assignment provider pallet's order-placement extrinsics (`place_order_allow_death` / `place_order_keep_alive`) withdraw the caller's balance to pay for coretime purchases [9](#0-8) . A delegate restricted to `NonTransfer` should never be able to trigger those withdrawals, but via the `is_superset` escalation path it can, defeating the security boundary the proxy type was created to enforce. This is the same class of bug as GHSA-9jcq-jf57-c62c: a principal holding a narrow-scope credential (`NonTransfer` proxy) reaches functionality gated to a broader scope (`OnDemandOrdering`/`Auction`) that a supposedly-authoritative check (`is_superset`) fails to actually confine.

### Likelihood Explanation
The `add_proxy` call itself only requires the existing `NonTransfer` proxy relationship (no root, no governance, no privileged role) and pays the normal `ProxyDepositBase`/`ProxyDepositFactor` reserve — the same cost any legitimate proxy delegate already pays. Once the sub-proxy exists, invoking the escalated call is a single ordinary signed extrinsic. This mirrors exactly the pattern Parity already accepted and fixed for `NonTransfer`/`Governance` on Asset Hub Westend (`prdoc/pr_12769.prdoc`), which is strong evidence the maintainers consider this class of bug real and exploitable, not theoretical.

### Recommendation
Replace the wildcard `(ProxyType::NonTransfer, _) => true` in `polkadot/runtime/rococo/src/lib.rs`, `polkadot/runtime/westend/src/lib.rs`, and `substrate/frame/staking-async/runtimes/rc/src/lib.rs` with an explicit allow-list of only those proxy types whose `filter` is a true subset of `NonTransfer`'s filter — the same remediation pattern already applied to `asset-hub-westend-runtime` in `prdoc/pr_12769.prdoc` (`(NonTransfer, Collator | Staking | NominationPools | StakingOperator) => true`). Add a lattice regression test analogous to `proxy_type_superset_relation_matches_call_filters` for these runtimes to prevent recurrence.

### Proof of Concept
Reproduction sketch (not executed — ask-mode has no terminal/test-runner access, so this is a manual trace, not a run test result):
1. In a `rococo`-runtime integration test, let account `A` grant account `B` a `ProxyType::NonTransfer` proxy via `Proxy::add_proxy(A, B, ProxyType::NonTransfer, 0)`.
2. As `B`, call `Proxy::proxy(B, A, None, RuntimeCall::OnDemandAssignmentProvider(place_order_allow_death{..}))` directly — expect `CallFiltered`, confirming `NonTransfer.filter` denies it.
3. As `B`, call `Proxy::proxy(B, A, None, RuntimeCall::Proxy(add_proxy{ delegate: B, proxy_type: OnDemandOrdering, delay: 0 }))` — expect this to succeed, because `pallet_proxy::do_proxy`'s embedded filter only blocks `add_proxy`/`remove_proxy` `if !def.proxy_type.is_superset(proxy_type)`, and `NonTransfer.is_superset(&OnDemandOrdering) == true`.
4. As `B`, call `Proxy::proxy(B, A, None, RuntimeCall::OnDemandAssignmentProvider(place_order_allow_death{..}))` again — now dispatched with `def.proxy_type == OnDemandOrdering`, whose filter admits the call, so `A`'s balance is withdrawn despite `B` only ever having been granted `NonTransfer`.

I could not execute this locally in this session (no code-execution tool in ask-mode); the escalation path itself (`is_superset` wildcard vs. `filter` mismatch) is directly confirmed by reading the cited source, and its exploitability pattern is corroborated by the maintainers' own fix/test for the structurally identical `NonTransfer`/`Governance` case. Whether this specific relay-chain gap qualifies for the live Polkadot bug-bounty program (versus being treated as a lower-severity/duplicate-class issue given the already-published fix elsewhere) should be confirmed against the current bounty scope before submission.

	fn is_superset(&self, o: &Self) -> bool {
		match (self, o) {
			(x, y) if x == y => true,
			(ProxyType::Any, _) => true,
			(_, ProxyType::Any) => false,
