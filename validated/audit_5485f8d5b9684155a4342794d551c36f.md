## Title
Webhook signature verification is keyed by an attacker-controlled `repository.owner.login` field that is decoupled from the `repository.full_name` field actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read directly out of the *unverified* JSON body. The handlers that subsequently act on the webhook (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a *different* field of the same unverified body, `repository.full_name`. Because the HMAC only proves the payload was signed with the secret belonging to whichever organization `repository.owner.login` names, and does not bind that value to `repository.full_name`, an attacker can pick which org's secret is checked while the actual write target is a different repository/org.

### Finding Description
`verify_signature` computes the verification key before the signature has been validated: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` — pure attacker-supplied JSON, read before any cryptographic check. This value is used to fetch the `GitHubApp` instance for that org, whose `webhook_secret` is then used to verify the HMAC: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the selected org's `webhook_secret` is blank/unconfigured (`return true unless webhook_secret`). Multiple documented/sample configs show `webhook_secret` left `nil` for some orgs (e.g. `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`). In a multi-org deployment, if *any* configured organization has no `webhook_secret` set, an attacker can set `repository.owner.login` to that org name to make signature verification a no-op, while setting `repository.full_name` to a *different* org/repo whose Stack they want to affect.

The handler that performs the actual write does not re-check the owner used for verification — it only looks at `repository.full_name`: [4](#0-3) [5](#0-4) 

This is the same class of bug as the H-03 finding: the field that is verified (`repository.owner.login`, used to choose the signing key) is not the field that is acted upon (`repository.full_name`, used to select the `Stack`), so the "signature covers the payload" trust binding is broken — `verified_org == repository.owner.login` while `acted_on_repo == repository.full_name`, and nothing forces `repository.owner.login` to be the owner of `repository.full_name`.

### Impact Explanation
An unauthenticated network attacker who knows (or guesses) that some configured GitHub organization in the Shipit deployment has no `webhook_secret` set (which the engine's own sample/default configs demonstrate is a supported and common state) can forge a `push`/`status`/`check_suite` payload for a *different, secret-protected* org/repo's Stack, set `repository.owner.login` to the unsecured org to bypass signature verification, and set `repository.full_name` to the victim Stack. This can trigger `GithubSyncJob`, spoof commit `Status`, or otherwise cause the engine to act on the targeted stack as if GitHub had sent the event, without possessing that org's real `webhook_secret`. Depending on the handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`), this can enqueue syncs and spoof CI status that gates automatic deploys — an unauthorized-deploy-adjacent write.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (supported natively, see `github_app_config`/`github_organizations` in `lib/shipit.rb`), and (2) at least one configured org with no `webhook_secret`. This is a realistic operational state since the shipped example configs explicitly leave `webhook_secret` blank, and nothing in the engine enforces that all orgs configure a secret. No credentials, sessions, or repository access are required — only a raw HTTP POST to `/webhooks` is needed. [6](#0-5) [7](#0-6) 

### Recommendation
Bind the field used to select/verify the signing key to the field used to act on the payload: derive the verification organization strictly from `repository.full_name`'s owner segment (or require they match and reject mismatches), and require `verify_webhook_signature` to fail (not pass) when the resolved org's `webhook_secret` is unset if that org's repositories are ever expected to be integrity-protected — or, at minimum, reject events where `repository.owner.login` does not match the owner segment of `repository.full_name` before any handler runs.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `secured-org` (has `webhook_secret: <secret>`, owns a tracked Stack `secured-org/app`) and `open-org` (has `webhook_secret:` left blank, per the shipped sample configs).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secured-org/app"
  }
}
```
3. `repository_owner` resolves to `open-org`; `Shipit.github(organization: 'open-org')` returns a `GitHubApp` whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `PushHandler#process` then uses `repository.full_name` = `secured-org/app` to find the real `Stack` and enqueue `sync_github(expected_head_sha: 'attacker-chosen-sha')`, affecting the secured org's stack without ever presenting `secured-org`'s webhook secret. [8](#0-7) [4](#0-3)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
