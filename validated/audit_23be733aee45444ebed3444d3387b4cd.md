### Title
Webhook signature verification keys on attacker-controlled `repository.owner.login` while handlers act on unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`Shipit.github_organizations`, per-org `webhook_secret`/`app_id` config as documented in `docs/setup.md` "Using Multiple Github Applications"), `WebhooksController#verify_signature` selects which organization's HMAC secret to verify against using a field taken from the *unauthenticated* request body, while the event handlers subsequently act on a *different* field of that same unauthenticated body to decide which repository/stack to mutate. This breaks the binding "the organization whose secret authenticated the request" == "the repository that is written."

### Finding Description
`verify_signature` picks the `GitHubApp` (and therefore the HMAC secret) using `repository_owner`, itself derived only from the JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config/secret purely from this attacker-supplied string: [3](#0-2) 

The signature check itself is a plain HMAC-SHA1 comparison against the raw body, with no binding to any specific repository — it only proves "this body was signed with organization X's secret", not "this body legitimately describes organization X's repositories": [4](#0-3) 

After this check passes, `create` re-parses the same body and dispatches to handlers keyed by `X-Github-Event`, none of which re-check `repository.owner.login` against anything — they all resolve the target repository from `repository.full_name`, an independent field of the same attacker-controlled JSON: [5](#0-4) [6](#0-5) [7](#0-6) 

Nothing anywhere ties `repository.owner.login`/`organization.login` (used to pick the verification secret) to `repository.full_name` (used to pick the mutated stack/commit). An attacker who legitimately administers Organization A's GitHub App integration configured in this Shipit instance (and thus knows Organization A's `webhook_secret`, which they configured themselves per the multi-org setup docs) can:
1. Build a JSON payload with `repository.owner.login` = `"org-a"` (their own org, so the correct secret is selected) but `repository.full_name` = `"org-b/victim-repo"` (a repository belonging to a different organization onboarded to the same Shipit instance).
2. Sign the raw body with Organization A's `webhook_secret` and send it to `/github/webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, etc.).
3. `verify_signature` computes HMAC using Organization A's secret (matched via the attacker-chosen `repository_owner`) and it validates successfully.
4. The dispatched handler (e.g. `PushHandler`) then looks up stacks purely from `repository.full_name` = `org-b/victim-repo`, and calls `stack.sync_github(expected_head_sha: params.after)` for a repo the attacker does not control.

### Impact Explanation
This crosses an organization boundary that the signature check is supposed to enforce. Concretely reachable handlers using only `repository.full_name` (never checked against the signing org):
- `PushHandler` — forces `sync_github` with an attacker-chosen `expected_head_sha` for any stack under any onboarded org/repo.
- `StatusHandler` — creates a commit status (CI status) for an arbitrary `sha`/repo (`Commit.where(sha:).create_status_from_github!`), which Shipit's merge/deploy gating relies on for CI-based safety checks, enabling status/CI spoofing that can influence whether a commit is eligible for merge or deploy.
- `CheckSuiteHandler` — schedules check-run refresh for arbitrary stacks/commits.

This is a High-severity cross-organization authorization boundary bypass: it lets a user who is legitimately authorized only for Organization A's webhook integration inject events that are processed as though they came from Organization B, escalating into stack/commit state that gates deploys for repositories the attacker has no access to. It matches the required-impact class of "escalation ... unauthenticated read/write of stack state ... via a mismatched trust binding" (the org that authenticated ≠ the repository that is written).

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where multiple GitHub organizations each have their own App/`webhook_secret` configured (explicitly documented and supported), and requires the attacker to control (or know) one organization's webhook secret — a realistic scenario for any organization admin who is not privileged with respect to other tenants on the same Shipit instance. No GITHUB_TOKEN, ApiClient token, or repository write access to the victim org is needed; only knowledge of one's own org's webhook secret, which is by design available to that org's admins.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC, cross-check that `repository.owner.login` (or `organization.login`) actually matches the owner segment of `repository.full_name` used by the handlers before dispatching, or better, have `Handler#repository_name`/each handler validate that the resolved repository's owner matches the organization whose secret verified the payload. Reject (422) any payload where these two org identifiers diverge.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org-a` (secret known to the attacker, who administers `org-a`'s GitHub App) and `org-b` (a different tenant's private repo `org-b/victim-repo`, unrelated stack configured in this Shipit instance).
2. Attacker crafts:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secret_org_a, raw_body)>`.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `secret_org_a`, and the HMAC matches → 200 processing proceeds.
6. `PushHandler` resolves stacks via `repository.full_name` = `"org-b/victim-repo"` and triggers `GithubSyncJob` for that stack with the attacker-chosen `expected_head_sha`, despite the request never being signed by `org-b`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
