This confirms the critical distinction: `PushHandler#process` and `CheckSuiteHandler#process` both scope their queries through `stacks` (derived from `Repository.from_github_repo_name(repository_name)` in `Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`), tying the payload's own `repository.full_name` to the specific stacks that belong to that repository. `StatusHandler#process`, however, does not use `stacks`/`repository_name` at all — it queries `Commit.where(sha: params.sha)` globally across the entire database.

### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by matching the attacker-controlled `sha` string against the global `commits` table, with no constraint that the webhook's originating repository (used only for signature verification) matches the `stack`/`repository` that owns the matched `Commit`. An attacker who controls their own GitHub org/repo (and thus a legitimately signed webhook channel to Shipit) can forge a `success` status for a victim's blocking CI context on a victim commit sha they merely know, unblocking the victim's deploy queue.

### Finding Description
The broken binding: `webhook.repository.full_name` (used in `verify_signature` via `repository_owner`) is assumed to equal `commit.stack.repository.full_name` for the `Commit` matched in `StatusHandler#process`, but the code never enforces this equality.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) derives the GitHub App/org context strictly from the attacker-supplied payload:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is read from `params.dig('repository', 'owner', 'login')` in the *attacker's own payload*. This only proves the request was correctly signed for whatever org the attacker names in the payload — if the attacker owns that org/repo and has the Shipit GitHub App installed there, they hold a fully valid signature. It does **not** prove anything about which `Commit`/`Stack` the payload's `sha` will subsequently touch.

`Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exists precisely to scope subsequent lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, and both `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`) correctly scope through `stacks` before touching any commit. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This performs a global, repository-unscoped lookup by raw `sha` string across every stack in the Shipit instance.

Exploit flow:
1. Attacker owns/controls a GitHub org/repo `attacker/evil` with the Shipit GitHub App installed (satisfying `verify_signature` for that org).
2. Attacker learns the victim's blocking commit sha (public repos expose commit shas; Shipit stack/commit pages may also expose them) and the victim stack's `blocking_statuses` context name (defined in the victim's own `shipit.yml` `ci.blocking`, often guessable/public in the repo).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a payload whose `repository` fields are `attacker/evil` (for signature verification) but whose `sha`, `context`, and `state: 'success'` target the victim commit/context.
4. `verify_signature` passes (signed correctly for `attacker/evil`).
5. `StatusHandler#process` finds the victim `Commit` purely by `sha` match, ignoring that the webhook's repository is `attacker/evil`, and calls `create_status_from_github!` → `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`), creating a `success` `Status` row for that context on the victim's commit.
6. `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) re-evaluates `stack.commits.reachable...any?(&:blocking?)`; since `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) is `!success? && blocking_statuses.include?(context)`, the newly created success status flips the previously-blocking commit to non-blocking.
7. `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) for later, otherwise-blocked commits becomes true, unblocking the victim's deploy queue.

None of the existing guards catch this: `verify_signature` only authenticates the sender's own org, not the target of the payload's data; `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`/`state`/`context`, not repository ownership; there is no `require_permission!`, `stacks` scoping, or repository-format validation applied before the `Commit.where(sha:)` lookup.

### Impact Explanation
A payload signed for one repository (the attacker's own) mutates state (`Status` record) belonging to a different repository/stack that the attacker never authenticated against — this is exactly the "payload for one repository mutating another's stack/commit" Critical category. The immediate effect is an unauthorized deploy-queue unblock (bypassing CI/compliance gating defined by `blocking_statuses`), potentially enabling unreviewed/unsafe commits to be deployed to production for a victim tenant the attacker has no relationship with. The attack is repeatable against any victim stack/commit whose sha and blocking context the attacker can learn, and requires only that the attacker control one GitHub org with the Shipit App installed — it is not limited to one victim, so the blast radius spans all tenants sharing the same Shipit instance/GitHub App installation base.

### Likelihood Explanation
Preconditions: victim stack has non-empty `blocking_statuses` (a documented, commonly-used feature per `ci.blocking` in `shipit.yml`), and an undeployed commit currently failing/missing that context. Attacker cost is low: create/own a GitHub org or repo, install the Shipit GitHub App there (if Shipit is multi-tenant/public GitHub App style) to obtain a validly signed webhook channel, then know the victim commit sha and blocking context name — both are typically discoverable from a public repository or the Shipit UI itself. No Shipit session, API token, or webhook secret theft is required. This is directly repeatable per request/per commit.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup through the webhook's own `stacks` (as `PushHandler` and `CheckSuiteHandler` already do), e.g. resolve commits via `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or iterate `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, so a status webhook can only mutate commits belonging to the repository named in that same, signature-verified payload.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
```ruby
test "status webhook from a different repository forges a success status and unblocks a victim commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'blocking' => ['soc/compliance'] }))
  blocking_commit = shipit_commits(:soc_second) # belongs to victim_stack
  blocking_commit.statuses.create!(stack: victim_stack, state: 'failure', context: 'soc/compliance')
  later_commit = shipit_commits(:soc_third)

  assert_equal true, later_commit.blocked?

  attacker_payload = {
    'sha' => blocking_commit.sha,
    'state' => 'success',
    'context' => 'soc/compliance',
    'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker' } }
  }

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates attacker's own validly-signed request
  post :create, body: attacker_payload.to_json, as: :json

  blocking_commit.reload
  later_commit.reload
  assert_equal 'success', blocking_commit.statuses.last.state
  assert_equal false, later_commit.blocked?  # binding broken: attacker/evil's signature unblocked shipit/shipit's commit
end
```
This asserts the equality `webhook.repository.full_name ('attacker/evil') != commit.stack.repository.full_name ('shipit/shipit')` still results in a written `Status` and a `blocked?` transition from `true` to `false`, proving the missing repository-ownership check.
