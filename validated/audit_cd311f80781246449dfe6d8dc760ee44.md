### Title
Webhook signature check keyed on `repository.owner.login` while stack targeting is keyed on `repository.full_name`, allowing a secret-less-org webhook to forge syncs against unrelated victim repositories - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore whether a webhook secret is even checked) using `repository.owner.login` from the JSON body, while `Handler#stacks` selects the target stack using the independent `repository.full_name` field from the same body. Because these two fields are never cross-validated, an attacker can present a secret-less/attacker-controlled org in `repository.owner.login` (bypassing signature verification entirely) while pointing `repository.full_name` at a real victim stack, causing `PushHandler#process` to call `stack.sync_github(expected_head_sha: <attacker sha>)` on that victim's stack using the victim's own GitHub credentials.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:
`payload.dig('repository','owner','login')` (used to pick the `GitHubApp`/secret for `verify_signature`) == owner segment of `payload.dig('repository','full_name')` (used by `Handler#stacks` to resolve the target `Repository`/`Stack`).

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)`, then checks `github_app.verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that org: `return true unless webhook_secret`. [3](#0-2) 
- `Handler#stacks` resolves the target using a *different* field, `payload.dig('repository', 'full_name')`, with no reference back to `repository_owner`/the org used for verification. [4](#0-3) 
- `PushHandler#process` finds stacks by branch under that resolved repository and calls `stack.sync_github(expected_head_sha: params.after)`, where `params.after` is fully attacker-controlled (only required to be present, per the `ExplicitParameters` schema, not validated as a real/known sha). [5](#0-4) 
- `GithubSyncJob#perform` stores `expected_head_sha` and, when the real GitHub state doesn't contain it, schedules retries and always calls `stack.github_commits` (using the stack's actual installation/app credentials for the real, unrelated organization). [6](#0-5) 

Exploit: the attacker owns/controls (or names) a GitHub org `secretless-org` that is configured in Shipit but has no `webhook_secret` set (the stated precondition). They POST to `/webhooks` with header `X-Github-Event: push` and a JSON body where:
- `repository.owner.login` = `"secretless-org"` (drives `verify_signature`, which passes unconditionally because that org has no secret),
- `repository.full_name` = `"victim-org/victim-repo"` (drives `Handler#stacks`, targeting the real victim stack),
- `ref` = the victim stack's branch,
- `after` = an attacker-chosen 40-hex-char string that doesn't exist on GitHub.

Existing guards do not catch this: `verify_signature` only checks the signature against whatever org string is present in the payload; it never checks that this org matches the repository that will actually be acted on. `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/shape of `ref`/`after`, not their authenticity or relation to `repository.owner.login`. There is no model validation anywhere tying `repository.full_name`'s owner segment to the org used for signature verification.

### Impact Explanation
The attacker triggers `GithubSyncJob` for an arbitrary victim stack they do not own or control, without ever authenticating against that victim's org/webhook secret. Each request against a secret-less org (or any org whose secret they don't need to know because it's unset) lets them redirect the effect to any `owner/repo` present as a Shipit stack, causing that stack's real GitHub App credentials to be used against GitHub (`stack.github_commits`) and repeated retry scheduling with an attacker-chosen sha. This is a forged-webhook authentication bypass where a payload nominally scoped to one (unrelated, attacker-controlled) repository mutates another repository's stack state/job queue — matching the Critical category "a payload for one repository mutating another's stack" / "authentication bypass (forged webhook ... accepted)". It is repeatable against any victim stack/branch combination as long as one secret-less org exists in the Shipit configuration.

### Likelihood Explanation
Requires only: (1) at least one GitHub org configured in Shipit without a `webhook_secret` (explicitly given as a precondition), and (2) knowledge of a target stack's `owner/repo` and branch (both public information visible on the Shipit UI/GitHub). No GitHub credentials, Shipit session, or API token are needed. Cost is a single crafted HTTP POST; the mismatch between `repository.owner.login` and `repository.full_name` requires no special tooling, just hand-crafting JSON.

### Recommendation
Enforce that the organization used for signature verification matches the owner of the repository being acted upon: derive `repository_owner` and the repository used for stack lookup from the same, single source of truth (e.g., parse `repository.full_name` once and use its owner segment for both `Shipit.github(organization: ...)` lookup and stack scoping), and reject the webhook if they cannot be reconciled. Additionally, do not silently accept unsigned webhooks for orgs without a configured secret; require `webhook_secret` for every org that can register webhooks, or fail closed rather than treating a missing secret as "signature always valid."

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new test file under `test/`):
```ruby
test "a secret-less org's push payload cannot forge a sync for an unrelated victim repository" do
  victim_stack = shipit_stacks(:shipit) # real stack for e.g. "shopify/shipit-engine", branch "master"
  # configure an org "secretless-org" with no webhook_secret in Shipit.github_configs for this test

  payload = {
    ref: "refs/heads/#{victim_stack.branch}",
    after: "f" * 40, # attacker-chosen, non-existent sha
    repository: {
      owner: { login: "secretless-org" }, # used by verify_signature -> no secret -> always verified
      full_name: victim_stack.repo_owner + "/" + victim_stack.repo_name # used by Handler#stacks -> targets victim
    }
  }.to_json

  assert_no_enqueued_jobs # or specifically check GithubSyncJob is not enqueued for victim_stack
  post shipit.webhooks_path, params: payload, headers: {
    "X-Github-Event" => "push",
    "X-Hub-Signature" => "sha1=irrelevant"
  }, as: :json

  assert_response :ok
  # Assert the equality is violated: verification org != stack's actual org, yet job was enqueued for victim_stack
  assert_enqueued_with(job: Shipit::GithubSyncJob, args: [hash_including(stack_id: victim_stack.id, expected_head_sha: "f" * 40)])
end
```
This demonstrates that `repository_owner` used for `verify_signature` ("secretless-org") diverges from the org actually mutated (`victim_stack.repo_owner`), and the job is enqueued for the victim stack despite the attacker never authenticating against the victim's org.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
