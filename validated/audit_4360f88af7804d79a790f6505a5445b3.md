## Finding: Stale attestations remain valid for AA-gated permissions after the attested address changes ownership (definition change)

### Title
Stale KYC/identity attestations remain usable by a new address owner in the `attestation[...]` oscript formula, unlike the equivalent address-definition `attested` check - ([File: formula/evaluation.js])

### Summary
Ocore's own code already recognizes and mitigates the exact bug class described in the report ("a permission tied to an address persists after control of that address changes hands"): for the address-definition `attested` operator and for `spender_attested` assets, `storage.filterAttestedAddresses` explicitly discards any attestation that predates the address's most recent `address_definition_change`. However, the `attestation[...]` formula function used inside Autonomous Agent (AA) bases/formulas performs the same kind of lookup but omits this safeguard, so an attestation issued to an address remains fully valid for that address forever, even after the address's controlling keys (and thus effective "owner") have completely changed via `address_definition_change`.

### Finding Description
Ocore associates identity/KYC-style permissions with an address via the `attestation` app message, stored in the `attestations`/`attested_fields` tables keyed only by `address` and `attestor_address` [1](#0-0) .

Ownership/control of an address can be transferred at any time by posting an `address_definition_change` message, which rewrites the signing definition (keys) bound to that address while the address string itself stays the same [2](#0-1) . This is the ocore analog of a proxy-wallet "ownership transfer" — the identity (address) is unchanged, but the party in control is.

When address-definition oscript conditions reference `["attested", [address, attestors]]`, the validity check is routed through `storage.filterAttestedAddresses`, which deliberately requires the attestation's `main_chain_index` to be strictly greater than the `main_chain_index` of the address's most recent `address_definition_change`: [3](#0-2) 
This same function also gates `spender_attested` assets during payment validation [4](#0-3)  and the `attested` op inside `validateAuthentifiers` [5](#0-4) . In all these cases, an attestation issued before a definition change is correctly treated as stale/invalid once the address's control changes.

The `attestation[...]` formula function, used in AA base and formulas, implements the *same conceptual check* ("is this address attested by these attestors") but never consults `address_definition_changes` at all — it filters only on `attestor_address`, `address`, and the trigger's `mci`: [6](#0-5) 
Neither the "recent unstable AA units" query nor the "stable units" fallback query joins against `address_definition_changes` to require the attestation to postdate the address's latest key/definition change, unlike `filterAttestedAddresses`.

### Impact Explanation
AAs commonly gate deposits, trades, borrowing, minting, or transfers on `attestation[[attestors=...], address=trigger.address]` to implement KYC/whitelisting/accredited-investor checks (e.g., security-token or regulated-asset AAs). Because the formula does not invalidate attestations after the attested address's definition changes, whoever currently controls address `A` inherits any attestation ever granted to `A`, regardless of when or to whom control of `A` was transferred. A party can effectively "sell" an already-KYC'd/whitelisted address (by changing its definition to new keys) and the buyer instantly and silently gains the KYC-gated privilege, or a previously-KYC'd but now-fully-transferred address can be repurposed by an unrelated new controller to bypass identity checks that gate fund movement through the AA. This can cause unauthorized fund movement / AA fund loss for regulated or permissioned AA-based products, matching the accepted impact categories (AA fund loss, unauthorized spending).

### Likelihood Explanation
Any unprivileged AA trigger sender can exploit this: they only need to (a) control an address that was attested at some point in the past (even by someone else, since the attestation is keyed purely by address, not by the identity of who requested it), and (b) trigger the target AA. No special network position, operator privilege, or race condition is required — this is purely a logic gap reachable from a normal AA trigger.

### Recommendation
Update the `attestation[...]` formula evaluation in `formula/evaluation.js` to apply the same staleness check used by `storage.filterAttestedAddresses`: require the attestation's `main_chain_index` (and `latest_included_mc_index` for unstable AA units) to be strictly greater than the main_chain_index of the most recent `address_definition_change` for the attested `address`, both in the "recent unstable AA units" query and the "stable units" fallback query.

### Proof of Concept
1. Address `A` (controlled by keys `K1`) receives an attestation from trusted attestor `T` (e.g., `KYC=true`) — recorded in `attestations`/`attested_fields` keyed by `address=A`.
2. Controller of `A` posts an `address_definition_change` unit, replacing `A`'s definition so that it is now controlled solely by an unrelated party's keys `K2` (e.g., `A`'s seed/definition is sold, or `K1` is compromised and rotated away).
3. The new controller (`K2`) sends a trigger unit from address `A` to an AA whose formula includes `attestation[[attestors='T'], address=trigger.address]` to gate a privileged action (e.g., minting a restricted asset, withdrawing from a KYC-only pool).
4. `formula/evaluation.js`'s `attestation` case queries `attestations`/`attested_fields` filtered only by `attestor_address` and `address` [7](#0-6) , finds the old attestation for `A`, and returns `true`/the attested value — without checking that this attestation predates the definition change that handed control to `K2`.
5. The AA executes the privileged action for the new, never-attested controller, exactly mirroring the reported bug where a stale, address-bound permission survives an ownership transfer and is exploited by a party who was never actually granted it.
