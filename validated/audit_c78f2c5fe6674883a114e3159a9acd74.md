### Title
Webhook signature validated against `repository.owner.login`/`organization.login` while event dispatch trusts the unchecked `repository.full_name` field, allowing cross-organization stack forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the inbound HMAC against using one field of the JSON payload (`repository.owner.login`, falling back to `organization.login`), but the actual event processing that follows resolves the target `Repository`/`Stack` using a different, unrelated field of the very same payload (`repository.full_name`). Nothing in the code cross-checks that these two fields agree.

### Finding Description
`Shipit.github` supports multiple independent GitHub App/organization configurations, each with its own `webhook_secret` [1](#0-0) . When a webhook is delivered, `WebhooksController#verify_signature` picks the verifying secret via:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

and then verifies the whole raw body against `Shipit.github(organization: repository_owner)`'s `webhook_secret` using `verify_webhook_signature`, which is a straightforward HMAC compare [3](#0-2) .

Once the signature check passes, `create` dispatches the parsed JSON to every registered handler for the event type [4](#0-3) . Every handler resolves the target repository/stack via `Handler#repository_name`, which reads a *different* JSON path:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`Repository.from_github_repo_name` then looks up the stack purely by this `full_name` string, downcased and split on `/`, with no relation back to `repository.owner.login` [6](#0-5) . This is used directly by mutating handlers such as `push_handler.rb` (enqueues `GithubSyncJob`, which fetches and updates commit history for the resolved stack) and `status_handler.rb` (records commit statuses), as well as the pull-request handlers that archive/unarchive review stacks and capture labels based on the same `full_name`-derived repository lookup [7](#0-6) .

This is the direct analog of CVE-2021-22924: just as `Curl_ssl_config_matches` bound connection reuse to a subset of the security-relevant fields (missing blob/issuercert values) while ignoring others, Shipit's webhook trust decision is bound to `repository.owner.login`/`organization.login` while the field that actually drives which repository's state gets mutated (`repository.full_name`) is never checked for consistency with the authenticated field. An organization administrator who legitimately owns a GitHub App installation on **their own** low-privilege organization (and therefore knows its `webhook_secret` — a credential Shipit intentionally hands to each tenant) can HMAC-sign an arbitrary JSON body of their own construction (not one from real GitHub delivery) that sets `repository.owner.login` to their own org (satisfying the signature check) but sets `repository.full_name` to `"other-org/other-repo"`. The signature validates, and the handler then acts on `other-org/other-repo`'s stack.

### Impact Explanation
This breaks the binding "the organization whose credential authenticated the request" == "the repository/stack that is written," letting a tenant with only their own org's webhook secret forge push/status/pull_request events against a completely different organization's stacks — e.g. triggering `GithubSyncJob` to rewrite commit/head state, injecting forged commit statuses, or archiving/unarchiving another tenant's review stacks. In deployments that gate deploy eligibility on commit status/checks, this can be leveraged toward triggering unauthorized deploys on someone else's stack, which falls under the "unauthorized deploy" High/Critical impact bucket. It does not directly leak `GITHUB_TOKEN` but does allow cross-repository writes to state Shipit itself trusts as GitHub-sourced.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately controls one configured organization's GitHub App/`webhook_secret` (a credential explicitly designed to be tenant-owned) but has no access to any other tenant's data — this is exactly the "unprivileged attacker with a payload field acted on but never covered by the verified binding" scenario the rules describe, not a scenario requiring a Shipit session, `ApiClient` token or repository write access on the target repo.

### Recommendation
In `WebhooksController#verify_signature`, after establishing which organization's secret validated the signature, cross-check that `repository.full_name`'s owner segment (and, for handlers, the resolved `Repository#owner`) matches the authenticated `repository_owner`/`organization` before dispatching to handlers; reject (422) any payload where these disagree.

### Proof of Concept
1. Attacker administers GitHub App/org `orgA` on a shared multi-tenant Shipit instance and knows `orgA`'s `webhook_secret`.
2. Attacker crafts a `push` payload:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `sha1=HMAC(orgA_webhook_secret, raw_body)` and POSTs it to `/webhooks` with header `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, verifies successfully against `orgA`'s secret [8](#0-7) .
5. `Handler#repository_name` resolves `"orgB/target-repo"` and the push handler enqueues `GithubSyncJob` against `orgB`'s actual stack, even though `orgB` never signed or authorized this payload.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
