### Title
Webhook signature key is selected using `repository.owner.login` while event handlers act on `repository.full_name` — an attacker who controls one configured GitHub organization can forge webhook events for any other org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a delivery against based on a field read out of the *unauthenticated* request body itself (`repository.owner.login` / `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subsequently resolves the actual `Stack`/`Repository` to mutate using a *different* field from the same body (`repository.full_name`). In a multi-organization Shipit deployment (a supported, documented configuration — see `config/secrets.development.shopify.yml` and `docs/setup.md`), an attacker who legitimately controls one configured organization (and therefore legitimately knows that organization's `webhook_secret`) can sign a payload with their own org's secret while setting `repository.full_name` to point at a *different*, victim organization's repository/stack. The signature check passes (it was computed with the attacker's own valid secret), but the event handler dispatches its side effects against the victim's stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` resolves the GitHub App configuration to check the signature against using: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted, attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`), *before* the signature has been verified to belong to that organization. `Shipit.github(organization: repository_owner)` looks up the `webhook_secret` for that named organization out of `Shipit.secrets.github`, which supports multiple, independently-configured organizations (each with its own `webhook_secret`), as documented in `docs/setup.md` and shown in `config/secrets.development.shopify.yml`.

Once `verify_signature` passes, `create` parses the same raw body and dispatches it to handlers: [3](#0-2) 

Every handler (`Shipit::Webhooks::Handlers::Handler` and subclasses like `PushHandler`, `PullRequest::ClosedHandler`, `ReopenedHandler`, etc.) resolves the target repository/stack from a *different* field of the same body — `repository.full_name` — not `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because HMAC-SHA1 signs the whole raw body, an attacker who owns/administers a legitimate organization "orgA" (and thus knows orgA's real `webhook_secret`) can craft an arbitrary JSON body where `repository.owner.login == "orgA"` (used only for secret selection) but `repository.full_name == "victim-org/victim-repo"` (used by the handler to find and mutate the actual `Stack`). The controller will select and validate against orgA's secret — which succeeds, since the attacker signed it correctly — and then the handler will act on the victim org's stack.

The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization owning the repository the handler subsequently writes to`

but the code instead lets these be two independently-attacker-controlled fields of the same unauthenticated JSON body.

### Impact Explanation
This breaks cross-organization isolation in multi-org Shipit deployments: a party that only has legitimate credentials for their own configured GitHub organization can trigger `Shipit::Webhooks::Handlers::*` side effects (e.g. `PushHandler` triggering `GithubSyncJob`/commit ingestion, `PullRequest::ClosedHandler#process` calling `review_stack.archive!`, `ReopenedHandler#process` calling `stack.unarchive!`, label handlers archiving/unarchiving review stacks) against stacks belonging to a completely different, victim organization they have no relationship to. This is a cross-repository write triggered by a forged, misattributed webhook — matching the Critical impact category "cross-repository writes."

### Likelihood Explanation
Requires the operator to run a multi-organization Shipit deployment (a supported, documented feature) and requires the attacker to legitimately control at least one of the configured organizations (i.e., have their own GitHub App installation with its own `webhook_secret` on that org) — a low bar compared to needing repository write access or a Shipit `ApiClient` token on the victim org, since the attacker's privileged relationship is only with *their own* org, not the victim's.

### Recommendation
`WebhooksController#verify_signature` and each `Handler` must agree on a single, authenticated source of truth for the organization/repository the event pertains to. Concretely: after selecting the GitHub App/secret to verify against (based on `repository.owner.login`), cross-check that the resolved `Stack`/`Repository` used by handlers (`repository.full_name`) actually belongs to that same, already-authenticated organization before permitting any handler to act — reject the delivery if `repository.full_name`'s owner does not match `repository.owner.login`/`organization.login` used for signature verification.

### Proof of Concept
1. Operator configures Shipit with two organizations, `orgA` (attacker-controlled) and `orgB` (victim), each with distinct `webhook_secret`s, per the multi-org config shown in `config/secrets.development.shopify.yml`.
2. Attacker, who administers the GitHub App installed on `orgA`, knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `orgA`'s real `webhook_secret` over this exact body and POSTs it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`) and `verify_webhook_signature` succeeds, since the attacker signed with the correct `orgA` secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` (from `repository.full_name`) and enqueues `stack.sync_github(expected_head_sha: ...)` against the victim's `orgB/victim-repo` stack, causing it to sync commits/state the attacker chose, despite the attacker never having any credential tied to `orgB`.

  module Webhooks

        params do
          requires :ref
          requires :after
        end
