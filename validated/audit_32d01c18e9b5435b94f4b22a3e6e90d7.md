### Title
NULL/undefined pointer dereference on `payload.definition` in `getAllAuthorsAndOutputAddresses` — (File: `network.js`)

### Summary
`getAllAuthorsAndOutputAddresses()` iterates a unit's messages and, for the `payment` app, explicitly checks `payload` truthiness before dereferencing it, but for the `definition` app it dereferences `payload.definition[1].base_aa` without any prior check that `payload` (or `payload.definition`) actually exists, mirroring the i40e_dbg_dump_desc pattern of missing a type/kind check before dereferencing a type-specific field.

### Finding Description
In `getAllAuthorsAndOutputAddresses`, the payment branch guards the dereference with `message.app === "payment" && payload`, but the very next branch does not: [1](#0-0) 
`message.payload_location` can legitimately be `"none"` or `"uri"`, in which case `objValidationState`/`validation.js` requires `payload` to be *absent* from the message object rather than inline: [2](#0-1) 
If a `definition` app message is serialized with `payload_location` other than `"inline"` (payload omitted, referenced only by `payload_hash`), then in `getAllAuthorsAndOutputAddresses`, `message.payload` is `undefined`, so `payload.definition` throws a `TypeError: Cannot read properties of undefined (reading 'definition')`. This mirrors the CVE-2021-47501 root cause: a type-specific field is accessed based only on a tag (`message.app === 'definition'` vs. VSI type) without validating that the corresponding data structure/pointer is actually present.

### Impact Explanation
This function is called from `notifyWatchers`, which runs on every newly saved unit/joint that a node processes (including light-client and hub relay paths) to determine which addresses are affected and whether watchers/light clients need to be notified: [3](#0-2) 
An unhandled exception here in a synchronous code path executed during unit processing can crash the node process or corrupt the event flow for saved units, since there is no try/catch around the `payload.definition[1].base_aa` access. This is a node-crash-causing bug for a core validation/notification path, i.e., a network unable to reliably process/confirm new units if triggered broadly.

### Likelihood Explanation
Whether a `definition`-app message can reach this function with a non-inline `payload_location` after full unit validation is the key uncertainty. Validation code enforces (a) payload absence for non-`inline` locations, and (b) presence of a `payload` for most message apps during validation, but the exact validation branch specific to `app === "definition"` was not fully confirmed within the available context (only `asset`, `attestation`, `data`, `temp_data`, `definition_template` cases were inspected around lines 1960-2033; the `definition` case itself was not located in the search). If `payload_location` "none"/"uri" is permitted for `definition` messages (e.g., after stripping content for storage/non-serial units, similar to the `content_hash` nonserial path seen at lines 181-188), this becomes reachable from any posted unit with an author `definition` change/message.

### Recommendation
Add an explicit `payload` (and `payload.definition`) existence/shape check in the `definition` branch of `getAllAuthorsAndOutputAddresses`, consistent with the `payment` branch's `&& payload` guard, before accessing `payload.definition[1].base_aa`, and wrap the loop in defensive handling (or return early / skip the message) when payload data is not inline.

### Proof of Concept
Not independently verified — reproducing requires confirming whether the `definition` app validation path in `validation.js` (case not located in indexed context) permits `payload_location !== "inline"` for `definition` messages to pass full validation and be persisted/replayed through `notifyWatchers`. Given this open uncertainty, this cannot be confirmed as a confirmed high-confidence exploitable path without further investigation of the `definition` case handler in `validation.js`, which the available index did not surface.
