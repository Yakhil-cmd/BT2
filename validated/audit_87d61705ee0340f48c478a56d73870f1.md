### Title

Unrestricted swap-route contracts can smuggle wallet-drain authorizations into a user-signed strategy - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

A malicious route can place attacker-controlled contract code inside a controller strategy’s authorization tree and use a signed child authorization to transfer unrelated tokens from the victim’s wallet. [1](#0-0) 

### Finding Description

`swap_collateral` accepts a caller-supplied `swap: Bytes` route, authorizes the account owner or delegate, withdraws the selected collateral, and passes that route to the configured swap router. [2](#0-1) [3](#0-2) 

The controller grants the router only one exact transfer from the controller and validates the controller’s input spend and output receipt after execution. [4](#0-3) 

Those checks do not constrain contracts reached through the route or detect additional authorization children generated by those contracts. [1](#0-0) 

An attacker-controlled venue contract can therefore invoke `transfer(victim, attacker, amount)` on any token held by the victim while the enclosing strategy still returns a valid swap output. [5](#0-4) [6](#0-5) 

### Impact Explanation

The victim can lose unrelated wallet tokens in addition to the collateral intentionally routed through the strategy. [7](#0-6) 

The exploit is not bounded by `amount`, the route’s minimum output, or the controller’s final account-risk check because the malicious token transfer uses the victim’s signed authorization tree rather than spending controller-held swap input. [8](#0-7) [9](#0-8) 

This is theft of user funds and is appropriately rated Medium because it requires the victim to sign a poisoned authorization tree. [10](#0-9) 

### Likelihood Explanation

Any unprivileged attacker can deploy a route-selected contract and offer a victim a valid `swap_collateral`, `multiply`, `swap_debt`, `repay_debt_with_collateral`, or comparable strategy payload that reaches it through the configured router. [11](#0-10) [12](#0-11) 

The attack depends on user interaction and on the wallet or client failing to make an unexpected authorization child unmistakable before signing. [13](#0-12) 

The host correctly rejects the malicious transfer when the signed tree contains only the expected strategy invocation, but executes it once simulation includes and the victim signs the poisoned child. [14](#0-13) 

### Recommendation

Wallets and transaction builders must decode controller strategy routes, display every authorization subtree, and reject any controller strategy signature containing unexpected child invocations. [13](#0-12) 

For a controller-routed strategy, the expected authorization tree should not contain unrelated token transfers from the user; direct router use should contain only the expected input pull. [15](#0-14) 

Where operationally feasible, route venues should additionally be restricted to reviewed contract identities rather than arbitrary addresses supplied by the strategy payload. [16](#0-15) 

### Proof of Concept

1. The victim owns a debt-free account with `USDC` collateral and holds an unrelated token in their wallet. [17](#0-16) 

2. The attacker deploys a route-selected `RogueHopPool` initialized with `(victim, wallet_token, attacker, amount)` and implementing the router’s expected `swap` entrypoint. [18](#0-17) 

3. The malicious `swap` calls `wallet_token.transfer(victim, attacker, amount)` while the router still pays the declared fair output. [5](#0-4) [19](#0-18) 

4. The attacker supplies that route as the `swap` argument to `Controller::swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap)`. [20](#0-19) 

5. Simulation records the unrelated wallet-token transfer as a child of the victim’s `swap_collateral` authorization. [21](#0-20) 

6. If the victim signs that returned tree, execution succeeds, the strategy deposits fair `ETH` output, the victim’s unrelated wallet balance becomes zero, and the attacker receives the stolen balance. [10](#0-9)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
