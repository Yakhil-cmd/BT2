### Title
Bypass of `final-bad` output rejection when spending pruned/stripped outputs via unstable-input path - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` rejects spends of stable `final-bad` (invalid) outputs, but the check is gated on `bStableInParents`. When an input's source output has already been stripped from the local DB (pruned) and is recovered from the in-memory pruned-joint cache via `archiving.getCachedOutput()`, the code repopulates `address`/`amount`/`denomination`/`asset` but never re-validates `sequence`, and the later `sequence !== 'good'` rejection is itself only enforced when `bStableInParents` is true. A crafted unit that references an old `last_ball` (so `bStableInParents` is false for the src output) can spend an output that is known to be `final-bad`, exactly the way rsync's `xname follows` path skipped `sanitize_paths`/`daemon_filter_list` checks that were correctly applied on the primary path.

### Finding Description
In `validation.js`, when validating a `transfer` input: [1](#0-0) 

```js
var src_output = rows[0];
var bStableInParents = (src_output.main_chain_index !== null && src_output.main_chain_index <= objValidationState.last_ball_mci);
if (bStableInParents) {
    if (src_output.sequence === 'temp-bad')
        throw Error("spending a stable temp-bad output " + input.unit);
    if (src_output.sequence === 'final-bad')
        return cb("spending a stable final-bad output " + input.unit);
}
```

This is the primary "filter list" check, analogous to `daemon_filter_list` in the CVE: it rejects `final-bad`/`temp-bad` outputs — but **only** when `bStableInParents` is true (i.e. the source output's `main_chain_index <= objValidationState.last_ball_mci`).

If the referenced output's row has been stripped from the DB (address column NULL because the unit has been pruned by `updateMinRetrievableMciAfterStabilizingMci`), the code falls into the secondary/alternate recovery path, the analog of the CVE's unsanitized `xname follows`: [2](#0-1) 

```js
if (!src_output.address) {
    if (src_output.sequence === 'final-bad' && src_output.main_chain_index < storage.getMinRetrievableMci()) { // already stripped locally
        const objCachedOutput = archiving.getCachedOutput(input.unit, input.message_index, input.output_index);
        if (!objCachedOutput)
            return cb({error_code: "unresolved_dependency", arrMissingUnits: [input.unit], bRequestPrunedContent: true});
        src_output.address = objCachedOutput.address;
        src_output.amount = objCachedOutput.amount;
        src_output.denomination = objCachedOutput.denomination;
        src_output.asset = objCachedOutput.asset;
    }
    else
        return cb("output being spent " + input.unit + " not found");
}
```

`archiving.getCachedOutput()` only returns `address`/`amount`/`denomination`/`asset` from the cached pruned joint — it does not (and cannot) restore or re-derive `sequence`: [3](#0-2) 

After this fallback fills in `src_output`, `src_output.sequence` is still `'final-bad'`. The code later re-checks sequence, but again only when `bStableInParents` is true: [4](#0-3) 

```js
if (bStableInParents && src_output.sequence !== 'good')
    return cb("stable input unit "+input.unit+" is not serial");
```

Since this cache-recovery branch is only reachable in the first place when `bStableInParents` is **false** (otherwise the earlier check at line 2456-2460 would already have rejected the final-bad output), this second guard can never fire for this code path. Control then falls through to the "unstable input" branch, which only checks DAG inclusion, not validity/sequence: [5](#0-4) 

```js
if (bStableInParents)
    return checkInputDoubleSpend(cb);

// the below is for unstable inputs only.
graph.determineIfIncludedOrEqual(conn, input.unit, objUnit.parent_units, function(bIncluded){
    if (!bIncluded)
        return cb("input "+input.unit+" is not in your genes");
    checkInputDoubleSpend(cb);
});
```

`bStableInParents` is false whenever `src_output.main_chain_index > objValidationState.last_ball_mci` (or is null). Combined with the requirement `src_output.main_chain_index < storage.getMinRetrievableMci()` for entering the cache branch, the attacker needs `objValidationState.last_ball_mci < src_output.main_chain_index < storage.getMinRetrievableMci()`. This is achievable by posting a unit whose declared `last_ball` is old/stale relative to the node's current pruning frontier, while its `parent_units` DAG genuinely includes (in an unstable sub-lineage of its own authoring history) a unit that spends from a `final-bad` output that has since been pruned. The check meant to universally reject spending invalid/`final-bad` outputs (the equivalent of `daemon_filter_list`) is bypassed on this alternate, cache-based recovery path (the equivalent of unsanitized `xname follows`).

### Impact Explanation
A node can be tricked into accepting a payment input that spends a known-invalid (`final-bad`, e.g., already double-spent or otherwise rejected) output, as long as that output's containing unit has been locally pruned and the spending unit references a sufficiently old `last_ball`. This directly maps to "concrete unauthorized spending" / potential double-spend of funds that the network had already determined were not spendable, undermining consensus about output validity between nodes that still have the pruned data cached versus nodes that have purged their cache (`PRUNED_JOINT_CACHE_TTL_ms` = 1 hour), potentially causing node disagreement on unit validity.

### Likelihood Explanation
Exploitation requires crafting a unit with a carefully chosen stale `last_ball` and a parent DAG that includes a previously final-bad, now-pruned unit — this requires some care but no privileged access; it can be attempted by any unit poster. The narrow timing/pruning-window requirement (must act before the 1-hour `PRUNED_JOINT_CACHE_TTL_ms` in `archiving.js` expires, and needs `main_chain_index` values in a specific stale range) lowers likelihood somewhat but does not require any special node role.

### Recommendation
Remove the `bStableInParents` gate on the `sequence !== 'good'`/`final-bad` rejection so that the check applies unconditionally, regardless of whether the source output was resolved via the live DB row or via `archiving.getCachedOutput()`. At minimum, after populating `src_output` from the cache in `validation.js` (lines 2462-2474), explicitly re-reject if `src_output.sequence !== 'good'` before proceeding to the unstable-input branch.

### Proof of Concept
1. Node A creates and gets accepted a payment unit `U1` at MCI `Y` whose output is later determined `final-bad` (e.g., it's a losing side of a double-spend).
2. Time passes until the network's `min_retrievable_mci` exceeds `Y`; nodes strip `U1`'s content locally (`updateMinRetrievableMciAfterStabilizingMci` in `storage.js`), keeping it only in the short-lived `assocCachedPrunedJoints` cache (`archiving.js`).
3. Before the cache entry expires, the attacker crafts unit `U2` that: (a) declares `last_ball` at an old MCI `X < Y`, and (b) has `parent_units` genuinely including `U1` in its DAG lineage as an "unstable" (from the perspective of `X`) ancestor, with a `transfer` input pointing at `U1`'s stripped output.
4. During validation of `U2`, `bStableInParents` evaluates false (`Y > X`); the initial `final-bad` rejection at `validation.js:2456-2460` is skipped; `archiving.getCachedOutput()` supplies stale address/amount data; the later `sequence` check at `validation.js:2481` is also skipped because it's gated by the same false `bStableInParents`; `graph.determineIfIncludedOrEqual` succeeds because `U1` is indeed included in `U2`'s lineage — `U2` is accepted, spending an output that was supposed to be permanently invalid.

// looks up a specific output within a cached pruned joint, in the same shape as the outputs table columns we lost to stripping
function getCachedOutput(unit, message_index, output_index){
	const objJoint = getCachedPrunedJoint(unit);
	if (!objJoint)
		return null;
	const message = objJoint.unit.messages && objJoint.unit.messages[message_index];
	if (!message || message.app !== 'payment' || !message.payload)
		return null;
	const output = message.payload.outputs && message.payload.outputs[output_index];
	if (!output)
		return null;
	return {
		address: output.address,
		amount: output.amount,
		denomination: message.payload.denomination || 1,
		asset: message.payload.asset || null
	};
}
