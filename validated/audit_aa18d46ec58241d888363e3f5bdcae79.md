## Root cause

`Shipit::WebhooksController#verify_signature` binds the HMAC check to the organization named in the payload, not to the specific repository the event will actually be applied to:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` selects a per-organization `webhook_secret` from `secrets.yml` (multi-tenant config supported by `github_app_config`) [2](#0-1) . So the signature only proves "this request was signed with organization X's webhook secret" — it says nothing about which *repository row* the event payload subsequently mutates in Shipit's database.

`Shipit::Webhooks::Handlers::StatusHandler#process` then acts purely on the commit `sha` supplied in the payload, with **no repository/stack scoping at all**:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

Compare this to other handlers (`PushHandler`, `PullRequest::*Handler`), which at least scope through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any stack [4](#0-3) . `StatusHandler` skips that scoping entirely.

The written commit status feeds directly into deploy gating:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [5](#0-4) 
and `Status#after_create` triggers `schedule_continuous_delivery` [6](#0-5)  and `Commit#schedule_continuous_delivery` enqueues an actual deploy job when the stack has `continuous_deployment` enabled [7](#0-6) .

## Binding broken (equality)

`organization authenticated by HMAC` (`repository_owner` in the payload) **≠** `repository/stack whose commit status is written` (looked up solely by `sha`, global across the whole Shipit install).

Before the attacker's request: commit `sha` in victim org's stack has state `pending`/`failure`, blocking deploy.
After: attacker — who legitimately holds a valid `webhook_secret` for *any* organization configured on this shared Shipit instance — sends a `status` event with `repository.owner.login` set to their own org (passes signature check) but `sha` set to an arbitrary commit belonging to a *different* tracked repository/stack. `StatusHandler` finds `Commit.where(sha: ...)` regardless of organization and creates a forged `success` status, which can flip `deployable?` to true and trigger an unauthorized/continuous deploy.

## Analog to the external report

Same bug class as "strategist can't be revoked": a privileged binding (which org's key authorizes an action) is not actually enforced against the resource the action targets — the check is present, but scoped to the wrong entity, so the "revocation"/isolation boundary between tenants/repositories is missing entirely for this handler.

### Title
Cross-repository forged commit status via webhook signature/repository binding mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The webhook signature is verified against the organization declared in the payload (`repository.owner.login`), while `StatusHandler` applies the status update to any `Commit` matching the supplied `sha` with no check that the commit's repository/stack belongs to that organization.

### Finding Description
`WebhooksController#verify_signature` selects the HMAC secret via `Shipit.github(organization: repository_owner)` [8](#0-7) , proving only that the request was signed by *some* organization's registered GitHub App/webhook secret. `StatusHandler#process` then does `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` with zero repository scoping [3](#0-2) , unlike sibling handlers that scope through `Repository.from_github_repo_name` [4](#0-3) . On a multi-org Shipit deployment (supported by `github_app_config`/`secrets.github` keyed per organization [9](#0-8) ), any organization with a valid webhook secret can forge a status for a commit sha belonging to a stack tied to a completely different organization/repository.

### Impact Explanation
A forged `success` status can make `Commit#deployable?` return true [5](#0-4)  and, combined with `stack.continuous_deployment?`, trigger `ContinuousDeliveryJob` for a victim stack the attacker's organization has no relationship to [7](#0-6) , resulting in an unauthorized deploy — meeting the Critical impact bar (unauthorized deploy).

### Likelihood Explanation
Requires the attacker to control (or have compromised) a valid webhook secret for *any one* organization configured on the shared Shipit instance, plus knowledge of a target commit sha (shas are often public via PR/commit links). Given multi-org support is a first-class configuration (`secrets_double_github_app.yml` fixture, `github_organizations`), this is a realistic deployment topology.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already do so), scope the `Commit` lookup by repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before matching by sha, so the authenticated organization must also own the repository whose commit is being mutated.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `org-attacker` and `org-victim`, each with its own `webhook_secret` (per `github_app_config`).
2. Attacker knows `org-attacker`'s webhook secret (they administer that GitHub App installation) and knows the sha of a commit in `org-victim`'s tracked stack (e.g. from a public PR).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, `repository.owner.login = "org-attacker"`, HMAC-signed with `org-attacker`'s secret, but with `sha` set to the victim commit and `state: "success"`.
4. `verify_signature` passes (valid signature for `org-attacker`). `StatusHandler#process` finds the victim `Commit` purely by sha and creates a `success` status on it, regardless of organization mismatch [3](#0-2) .
5. If the victim stack has `continuous_deployment` enabled, `schedule_continuous_delivery` fires and deploys the (previously blocked) commit.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
