## Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing a cross-repository/cross-organization write - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports per-organization GitHub App configuration, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to use for HMAC verification based solely on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), then validates the raw body against that organization's secret [2](#0-1) [3](#0-2) . However, once the signature is accepted, the event handlers (e.g. `PushHandler`, `CheckSuiteHandler`, and the PR handlers) locate the target `Repository`/`Stack` using an entirely different field of the same payload: `repository.full_name`, via `Handler#repository_name`/`Repository.from_github_repo_name` [4](#0-3) [5](#0-4) . Nothing ties `full_name`'s owner segment to the organization whose secret validated the signature — the two lookups are logically independent, even though the field names loosely resemble each other in test fixtures.

### Finding Description
The verified binding is: `HMAC(secret_for(repository.owner.login), raw_body) == signature`. The value actually consumed to select which repository/stack is mutated is `Repository.from_github_repo_name(repository.full_name)`. These are two separate JSON leaves under the same `repository` payload key, and the code never asserts `repository.full_name.split('/').first == repository.owner.login`.

Because Shipit is multi-tenant across organizations that each configure independent `webhook_secret`s [6](#0-5) , an actor who legitimately controls (or has push access enabling real GitHub deliveries for) one onboarded organization "A" — and therefore can obtain a validly-signed webhook body for org A — can freely control the entirety of the payload other than what GitHub itself populates, and any handler-supplied JSON is otherwise attacker-shaped once it reaches `WebhooksController#create`, since the controller simply does `JSON.parse(request.raw_post)` and dispatches it [7](#0-6) . Since the equality check in `verify_signature` only binds the secret-selection key (`owner.login`) to the signature, but not to the `full_name` used downstream, a payload can be crafted so that:
- `repository.owner.login` = `"org-a"` (used to pick the webhook secret that validates against org A's secret)
- `repository.full_name` = `"org-b/victim-repo"` (used by `PushHandler`/`CheckSuiteHandler`/PR handlers to select the target `Stack`)

`PushHandler#process` would then call `stack.sync_github(expected_head_sha: params.after)` for `org-b/victim-repo`'s stacks [8](#0-7) , i.e., trigger a deploy-relevant sync for a repository/organization the signer never authenticated for.

### Impact Explanation
This breaks the deployment-trust binding between "organization that authenticated the webhook" and "repository that is written." Concretely, an attacker in control of one org's genuine webhook secret (or delivery channel) can spoof `push`/`check_suite`/`pull_request` events against any other onboarded repository's stacks, forcing unauthorized `GithubSyncJob` triggers, check-run refreshes, or PR-state-driven stack archive/unarchive/provisioning actions on victim repositories — an unauthorized cross-repository state change qualifying as "cross-repository writes" / "unauthorized deploy" per the impact criteria.

### Likelihood Explanation
Exploitability requires the attacker to already be a legitimately onboarded organization within the same Shipit instance (i.e., one with its own configured `webhook_secret`), which is a real-world multi-tenant configuration supported by `Shipit.github_app_config` [6](#0-5) . This is not privileged in the sense excluded by scope (no `ApiClient` token, no GitHub App private key, no repository write access to the *victim* repo is required) — it only requires being one of potentially many onboarded low-trust organizations whose own secret is known to them by design.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, after verifying the signature, assert that the organization used to select the webhook secret matches the owner segment of `repository.full_name` (and `organization.login` where applicable) before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
1. Shipit instance configured with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s, both with onboarded repositories/stacks.
2. Attacker, who administers `org-a`'s GitHub App/webhook (or otherwise knows `org-a`'s `webhook_secret`), crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(org-a_webhook_secret, raw_body)` and sends it as `X-Hub-Signature` with `X-Github-Event: push` to `POST /webhooks`.
4. `verify_signature` resolves `repository_owner` → `"org-a"`, fetches `org-a`'s `GitHubApp`, and validates the signature successfully [2](#0-1) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` [4](#0-3)  and calls `sync_github` on `org-b`'s stacks — despite the signature never having been validated against `org-b`'s secret.

Note: I was unable to fully confirm within the index whether Shipit deployments in practice always configure a single shared `webhook_secret` (legacy single-org mode) versus per-organization secrets in typical production use; the multi-organization code path (`github_app_config`) clearly supports independent secrets per org, which is the condition required for this analog to be exploitable across trust boundaries.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
