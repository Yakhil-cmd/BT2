Found the critical CEI violation: `borrow` calls `vault-system-borrow`, which transfers the borrowed underlying tokens to `funds-receiver` **before** the debt is recorded via `contract-call? .v0-market-vault debt-add-scaled`.

### Title
Reentrancy in `borrow` allows debt recording to be bypassed via external transfer callback before position is updated - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`borrow` sends the requested underlying asset to `funds-receiver` (via `vault-system-borrow`, which ultimately calls `send-tokens`/`contract-call? ft transfer ...`) before the corresponding scaled debt is written to `market-vault` via `debt-add-scaled`. Because the transferred asset can be any registered `<ft-trait>` implementation (including SIP-010 tokens whose `transfer` can trigger arbitrary logic in the receiving principal, e.g. via post-conditions/trait hooks or a receiver contract), the receiver can re-enter the market before its debt is persisted [1](#0-0) .

### Finding Description
In `borrow`, health checks are computed correctly, but the state-mutating order is: (1) `vault-system-borrow` — moves funds out of the vault to `funds-receiver`, then (2) `debt-add-scaled` — records the scaled debt against `account` in `market-vault` [1](#0-0) . Between step (1) and (2), control can transfer to externally-controlled code if `funds-receiver` is a contract that reacts to receiving funds (this mirrors the Trader `executeTrade` pattern where an external, less-trusted `market` contract is invoked mid-function with the position not yet finalized). During that reentrant window, the caller's on-chain debt for `asset-id` has not yet been incremented, while the funds have already left the vault. A reentrant call into `borrow` (for a different asset), `withdraw`/`collateral-remove` on the same account, or `liquidate` targeting this borrower would compute health/position using a collateral value that has not yet been debited for the just-issued loan, letting the position appear healthier than it is. The victim here is the pool of other lenders/suppliers of the vault: the vault balance is drawn down for a loan whose liability is momentarily missing from the ledger, so a second operation performed inside that window can extract more assets (e.g., a second under-collateralized borrow, or a further collateral withdrawal) than the true position would allow, socializing the shortfall onto other depositors once accounting resolves.

### Impact Explanation
This lands in the Critical bucket — theft of funds at rest — because the missing-debt window lets an attacker draw additional assets out of the shared vault liquidity beyond what their true (post-loan) health factor would allow, at the expense of other depositors/suppliers whose funds back the vault.

### Likelihood Explanation
Likelihood depends on whether any listed `<ft-trait>` implementation used as a borrowable asset can trigger callback-like logic on transfer to a contract receiver, and whether `funds-receiver` can be set to an attacker-controlled contract (the `borrow` signature explicitly allows an arbitrary `receiver` principal) [2](#0-1) . I could not fully verify within the available context whether the specific SIP-010 tokens registered as assets in this deployment support such reentrant hooks (Clarity's `contract-call?` to a `<ft-trait>` type can invoke arbitrary contract logic defined by that trait implementation), so likelihood is uncertain without confirming asset registration and trait implementations; I could not find an explicit reentrancy guard on the `market.clar`/`v0-4-market.clar` public functions (`borrow`, `repay`, `liquidate`, `withdraw`) analogous to the `in-flashloan` guard present in the vault contracts [3](#0-2) .

### Recommendation
Reorder `borrow` to persist the debt update (`debt-add-scaled`) before transferring funds out via `vault-system-borrow`, following checks-effects-interactions. Alternatively, add a protocol-wide reentrancy guard (a boolean flag on the market contract analogous to `in-flashloan`) that is asserted/set at entry of all state-mutating public functions (`borrow`, `repay`, `liquidate`, `liquidate-redeem`, `collateral-remove`/withdraw paths) and cleared at the end, so no external call made during token transfer can re-enter and observe a half-updated position.

### Proof of Concept
1. Attacker deploys a malicious SIP-010-compatible contract `Evil` and registers/uses it as `funds-receiver` in `borrow(ft, amount, (some 'Evil), price-feeds)`.
2. `market.clar`'s `borrow` passes health checks for the intended loan amount and calls `vault-system-borrow`, which transfers `amount` of the underlying token to `Evil` [4](#0-3) .
3. If the token transfer trait implementation allows `Evil` to execute logic upon receipt (e.g., via a wrapped/rehypothecated asset's trait hooks), `Evil` calls back into `market.clar` (e.g., another `borrow` for the same `account`, or `liquidate` against `account`) before `debt-add-scaled` for the first loan has executed [5](#0-4) .
4. In that reentrant call, `get-position account` / `get-notional-evaluation` compute health without the pending debt, so the second operation can pass health checks that would otherwise fail, letting the attacker over-extract vault liquidity.
5. When the original call resumes and finally records the first loan's debt, the position now understates the true liability relative to what was actually withdrawn from the vault, leaving a shortfall that is ultimately borne by other suppliers of that vault.
