### Title
Webhook signature verification is keyed by `repository.owner.login`/`organization.login` while the handlers act on the independent `repository.full_name` field, allowing cross-organization/cross-repository writes when any configured GitHub App has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to verify an inbound webhook against using `repository_owner`, derived from `params.dig('repository','owner','login')` with a fallback to `params.dig('organization','login')`. Every webhook `Handler` (`Shipit::Webhooks::Handlers::Handler#repository_name`), however, independently determines which `Repository`/`Stack` to act on using `payload.dig('repository', 'full_name')`. These two payload fields are never cross-checked against each other.

### Finding Description [1](#0-0)  shows `verify_signature` picking the GitHub App/secret purely from `repository_owner`: [2](#0-1) 

The signing check itself, in `GitHubApp#verify_webhook_signature`, short-circuits to `true` whenever the selected organization's `webhook_secret` is blank: [3](#0-2) 

Shipit explicitly supports multiple independently-configured GitHub organizations in one instance, each with its own optional `webhook_secret` (documented as optional, see `docs/setup.md`), as shown by the sample multi-org config: [4](#0-3) 

Once the (possibly secret-less) signature check passes, `Shipit::Webhooks.for_event` dispatches to handlers, e.g. `PushHandler`, all of which inherit `Handler#repository_name`/`#stacks`, which look up the target purely from `repository.full_name`, an entirely different JSON key than the one used for signature routing: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used only to pick which secret authenticates the request) and `repository.full_name` (used only to pick which `Stack` gets written to) are both attacker-supplied JSON fields in the same raw POST body, an attacker can set them to point at two different organizations. If any organization configured in this Shipit instance has no `webhook_secret` set — an explicitly supported/documented configuration — `verify_webhook_signature` returns `true` unconditionally for any payload claiming `repository.owner.login` (or `organization.login`) equal to that org, with **zero knowledge of any secret required**. The attacker then sets `repository.full_name` to any other, fully secured organization/repository tracked by the same Shipit instance, and the corresponding handler (`push`, `pull_request`, `status`, `check_suite`, `membership`) will act on that unrelated repository's `Stack`/`Repository`/`Commit` records as if it had been legitimately verified.

This is the same class of bug as the referenced report: the entity that gets "authenticated" (the organization whose secret verified the signature) is never bound to the entity that is actually acted upon (the repository named in `full_name`), exactly matching the rule's listed binding: "an organization that authenticated versus the repository that is written."

### Impact Explanation
An unauthenticated internet attacker (no session, no API token, no webhook secret, no repository access) can forge webhook deliveries to `POST /webhooks` for any repository tracked by the Shipit instance, as long as at least one configured GitHub organization in that Shipit deployment lacks a `webhook_secret` (a supported, documented configuration state). This yields cross-repository writes: creating/overwriting `Commit` `Status` records, forcing `stack.sync_github` on arbitrary tracked stacks via the push handler, and manipulating PR-driven review-stack lifecycle actions (archive/unarchive, label capture) for repositories belonging to a completely different, secured organization. This is a Critical-tier cross-repository write that bypasses the intended per-organization webhook trust boundary.

### Likelihood Explanation
Likelihood depends on at least one configured GitHub App in the Shipit instance having no `webhook_secret` set — a state the documentation explicitly presents as optional/acceptable rather than mandatory, so it is plausible in real multi-tenant deployments (e.g., during onboarding of a new org, or orgs where the operator chose not to configure a secret). No credentials, sessions, or tokens are needed to exploit it once that condition holds; the attacker only needs to know the internal `full_name` of a target repository/stack already tracked by Shipit, which is often derivable from the target's own public GitHub repo name.

### Recommendation
Bind the two identities: reject the webhook when `repository.full_name`'s owner segment does not match the `repository_owner`/organization used to select the verifying `GitHubApp`. Additionally, do not allow `verify_webhook_signature` to silently return `true` for a configured organization with a blank secret unless that behavior is an intentional, explicitly-opt-in "no verification" mode; if kept, scope its trust so it cannot be used to authorize writes to stacks belonging to other organizations (e.g., only accept payloads whose `repository.full_name` owner also matches an organization with no secret).

### Proof of Concept
Preconditions: Shipit instance configured with two orgs, e.g. `no-secret-org` (no `webhook_secret`) and `victim-org` (has stacks tracked, e.g. `victim-org/app`).

1. Attacker (fully unauthenticated) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted
Body:
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-as-a-commit>",
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/app" }
}
```
2. `WebhooksController#repository_owner` resolves to `"no-secret-org"`, `Shipit.github(organization: 'no-secret-org').verify_webhook_signature` short-circuits to `true` because `webhook_secret` is blank for that org (`lib/shipit/github_app.rb:76-77`), regardless of the actual `X-Hub-Signature` header value.
3. `Shipit::Webhooks::Handlers::PushHandler#process` looks up stacks via `repository_name` = `payload.dig('repository','full_name')` = `"victim-org/app"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), and calls `stack.sync_github(expected_head_sha: params.after)` on `victim-org`'s tracked stacks — an action the attacker was never authorized to trigger, since they hold no credential for `victim-org` at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
