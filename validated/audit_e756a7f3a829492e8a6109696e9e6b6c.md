### Title
Unvalidated `creator` account in `initialize_with_permission` permanently freezes accrued creator-fee revenue - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` records `pool_state.pool_creator` from an `UncheckedAccount` (`creator`) that carries no Anchor constraint at all — it is not required to be a signer, not required to equal `payer`, and not tied to the `permission` PDA that gates who may call the instruction. Any account holding a valid `permission` PDA can create a pool while attributing `pool_creator` to an arbitrary, uncontrolled pubkey. Because the creator-fee accounting (`creator_fees_token_0/1`) accrues automatically on every swap independent of the `pool_creator` address, setting this field to an address nobody controls permanently locks that portion of trading fees.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as: [1](#0-0) 
with no `address =`, `constraint =`, or signer requirement linking it to `payer` or to the `permission` account, which is instead derived solely from `payer.key()`: [2](#0-1) 

At the end of `initialize_with_permission`, this unchecked `creator` key is written directly into `PoolState.pool_creator` (with `enable_creator_fee = true`): [3](#0-2) 

This differs from the plain `initialize` instruction, where `creator` is a `Signer` whose associated token accounts (`creator_token_0`, `creator_token_1`, `creator_lp_token`) are explicitly bound to it, effectively forcing `creator` to be a real, funded, signing account: [4](#0-3) 

Once the pool is live, creator fees are computed purely from the trade direction and `enable_creator_fee`/`creator_fee_rate`, independent of who `pool_creator` actually is: [5](#0-4) [6](#0-5) 

These fees are then only claimable by `collect_creator_fee` (requires `creator` to sign and match `pool_state.pool_creator`) or `collect_creator_fee_permissionless` (anyone may trigger, but funds are still routed to an ATA owned by `pool_state.pool_creator`): [7](#0-6) [8](#0-7) 

If `payer` sets `creator` to an address whose private key does not exist or is unknown/unrecoverable (e.g., a burn pubkey, an unrelated program-derived address, or a throwaway keypair the caller discards), the resulting ATA can still be created and receive the swept fees via the permissionless path, but nobody can ever spend from it. Every subsequent swap through that pool continues to divert `creator_fee_rate` worth of trade fees into this unreachable account, permanently and irrecoverably.

This is analogous in bug class to CVE-2025-3580 (BIT-grafana-2025-3580): a lower-privileged actor (a `payer` who merely holds a `permission` PDA, not a true admin) is able to unilaterally and irreversibly assign/strip a privileged role (`pool_creator`, which owns a revenue stream) to/from an address it does not control, because the endpoint is missing the access-control link that should bind the privileged field to a verified signer.

### Impact Explanation
Every swap on a pool created this way silently diverts `creator_fee_rate` of the trade fee into `creator_fees_token_0`/`creator_fees_token_1` balances that can never be withdrawn, since the only two withdrawal paths route funds to an ATA owned by an uncontrollable `pool_creator` pubkey. This is a permanent freezing of swapper-paid fee funds for the entire lifetime of the pool — a growing, unrecoverable loss with no admin remediation path (there is no instruction to change `pool_creator` once set). Severity is Medium: it does not require any privileged signer, is reachable by any account with a `permission` PDA (an "unprivileged" party relative to true admin), and causes concrete, permanent value loss.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that grants `permission` PDAs broadly (e.g., to many pool-creator partners) rather than only to fully trusted operators, since `initialize_with_permission` performs no sanity check that `creator == payer` or that `creator` is a signer. A careless or malicious `payer` can trigger this in a single transaction with attacker-chosen accounts (setting `creator` to any pubkey of their choosing), requiring no special privileges beyond already holding a valid `permission` account.

### Recommendation
Add an explicit constraint binding `creator` to a verifiable, intentional value — at minimum require `creator.key() == payer.key()` (mirroring `initialize.rs`), or require `creator` to be a `Signer` so the party has demonstrably signed for and can control the account before it is recorded as `pool_creator`. Alternatively, validate that `creator` is not `Pubkey::default()` and is a native system-owned (non-PDA) address to reduce the risk of assigning creator-fee rights to an unspendable account, though requiring a real signer is the more robust fix.

### Proof of Concept
1. Attacker (or careless partner) obtains a valid `permission` PDA for `payer` via `create_permission_pda`.
2. Attacker calls `initialize_with_permission`, supplying `creator` = an arbitrary pubkey with no known private key (e.g., a freshly generated keypair whose secret is discarded, or `Pubkey::default()`), while `payer` funds the pool normally.
3. `pool_state.pool_creator` is set to this unreachable address (`initialize_with_permission.rs` line 361) with `enable_creator_fee = true`.
4. Users swap against the pool via `swap_base_input`/`swap_base_output`; each swap accrues `creator_fee` into `pool_state.creator_fees_token_0/1` per `CurveCalculator::swap_base_input`/`swap_base_output`.
5. Anyone may call `collect_creator_fee_permissionless`, which creates an ATA owned by the unreachable `pool_creator` and transfers the accrued fees there — permanently locking them, as no one holds the signing key for that ATA's owner.

        protocol_fee: u64,
        fund_fee: u64,
        creator_fee: u64,

    ) -> Result<()> {
        if !self.enable_creator_fee {
            require_eq!(creator_fee, 0)
        }
        let is_creator_fee_on_input = self.is_creator_fee_on_input(direction)?;
        match direction {
            TradeDirection::ZeroForOne => {
                self.protocol_fees_token_0 = self
                    .protocol_fees_token_0
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_0 = self.fund_fees_token_0.checked_add(fund_fee).unwrap();

                if is_creator_fee_on_input {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                }
            }
            TradeDirection::OneForZero => {
                self.protocol_fees_token_1 = self
                    .protocol_fees_token_1
                    .checked_add(protocol_fee)
                    .unwrap();

                    self.creator_fees_token_1 =

                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                }
