### Title
Uncaught exception crashes node when a validly-authenticated address definition references a "definition template" that fails a post-hoc re-check - ([File: definition.js])

### Summary
`Definition.validateAuthentifiers()` re-evaluates an address' spending-condition tree while verifying the authentifiers/signatures supplied by a unit author, AA trigger sender, or `signed_message`/`is_valid_signed_package` sender. In the `'definition template'` branch of that re-evaluation, the code throws a bare, uncaught `Error` inside an asynchronous `conn.query` callback instead of returning the error through the normal `cb2`/`fatal_error` mechanism used by every other branch (`sig`, `hash`, `address`, etc.).

### Finding Description
`definition.js` contains two structurally similar handlers for the `'definition template'` operator:

- In `validateDefinition()` (the pre-check invoked once before authentifier verification), the same query result is handled gracefully: [1](#0-0) 

- In `validateAuthentifiers()` (the actual signature/authentifier verification pass, invoked right after `validateDefinition()` succeeds), the identical query is issued again, but on an unexpected row count the code does not call back with an error — it throws: [2](#0-1) 

This throw occurs inside the callback of an asynchronous `conn.query(...)` call, which is *not* inside any synchronous `try/catch` at the point the exception is raised (JS `try/catch` cannot catch exceptions thrown from callbacks invoked after the try block has already returned). The call chain that reaches this code is used pervasively for authenticated content that reaches this function only *after* the caller has already accepted a syntactically valid signed structure — analogous to the BIND `TKEY` bug being reachable only after a valid TSIG signature is verified:

- Ordinary unit validation: `validation.js` `validateAuthor()` → local `validateAuthentifiers()` → `Definition.validateAuthentifiers()`, with no surrounding `try/catch`: [3](#0-2) 
- Off-chain signed messages used by paired-device contracts (`prosaic_contract_response`, `arbiter_contract_response`) and by AA formula's `is_valid_signed_package`/`signed_message.validateSignedMessage`: [4](#0-3) 
  Here there *is* a `try/catch`, but it only wraps the synchronous call to `Definition.validateAuthentifiers`; the throw happens later, inside the async `conn.query` callback nested several levels deep, and therefore escapes this `try/catch` as an unhandled exception in Node's event loop.

The two evaluations (`validateDefinition`'s pre-check and `validateAuthentifiers`'s re-check) query the exact same table/condition, so in the common single-connection (SQLite) case they are consistent. However, they are two independent asynchronous round-trips, and `validateAuthentifiers()` is documented in-code as being *deliberately* re-run every time specifically because referenced state (inner address definitions, redefinitions, etc.) can change between calls: [5](#0-4) 
Any divergence between the two lookups (e.g., pooled/replicated DB connections as used with MySQL, or the referenced `definition_template` unit's stability/sequence status changing between the two round-trips during a temporary fork/voiding) causes the second query to return `rows.length !== 1`, hitting the unguarded `throw Error("not 1 template")`.

### Impact Explanation
An uncaught exception thrown from inside an asynchronous database callback is not caught by any surrounding `try/catch` and becomes an unhandled exception on the Node.js event loop. Unless intercepted by a top-level `process.on('uncaughtException', ...)` handler, this terminates the Node.js process — i.e., a full node crash, exactly analogous to the BIND 9 `named` crash caused by a correctly-signed-but-malformed request reaching an unguarded code path. Because this code path is reachable through core unit validation, AA trigger evaluation (`is_valid_signed_package`), and paired-device contract signed messages, any of these actors (an unprivileged unit poster, an AA trigger sender, or a private-payment/contract counterparty) can construct a definition using `'definition template'` that is accepted by the initial `validateDefinition()` pass but reaches an inconsistent state by the time `validateAuthentifiers()` re-queries it, crashing the validating node. A network of nodes crashing on the same malicious construct would be unable to confirm new units, i.e., a network availability impact.

### Likelihood Explanation
Likelihood is limited primarily by the difficulty of reliably causing the two round-trip queries to diverge in a single-connection SQLite deployment, since `is_stable=1` rows are immutable once written. Under MySQL (which ocore explicitly supports, based on `conf.storage == "mysql"` checks throughout `validation.js`) using pooled/non-transactional reads, or during transient main-chain reorganizations that change a referenced unit's `sequence` from `'good'` to `'temp-bad'/'final-bad'` between the two lookups, the divergence becomes achievable by an attacker who controls the timing of their `definition_template`-referencing unit relative to a forking event. This is a real, unguarded code defect (throw vs. graceful callback, inconsistent with every sibling branch in the same function and with the twin implementation in `validateDefinition()`), but exploitation requires a specific timing/DB-backend condition, which is why it is rated Medium rather than High/Critical.

### Recommendation
In `definition.js`, change the `'definition template'` branch inside `validateAuthentifiers()`'s `evaluate()` (around line 811-812) to match the graceful error handling already used in `validateDefinition()`'s equivalent branch and in every other authentifier branch (`sig`, `hash`, `address`): set `fatal_error = "template not found or too many"` and call `cb2(false)` instead of throwing. Additionally, wrap the whole `conn.query` callback body in a `try/catch` that forwards any exception to `cb2(false)`/`fatal_error`, so that no future code change in this callback can again produce an unhandled exception in this async context.

### Proof of Concept
1. Attacker publishes a stable unit `U` containing a single `definition_template` message with some payload template (satisfying `validation.js`'s `"can be only one definition template"` and 2-element-array checks).
2. Attacker (or the same author) creates an address whose definition is `['definition template', ['U', {param: 'value'}]]`.
3. This address is used as an author (or asset-condition, or signed-message author) in a new unit/trigger/signed message. `validateDefinition()` runs first and succeeds because at that moment the query `SELECT payload FROM messages JOIN units USING(unit) WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND sequence='good' AND is_stable=1` returns exactly 1 row for `U`.
4. Before/while `validateAuthentifiers()`'s second, independent execution of the identical query resolves (e.g., a transient reorg voids `U`, or a MySQL replica read lags), the row count for the same query becomes `0` (or, in a race with a second `definition_template` message somehow associated with the same unit hash) not equal to `1`.
5. `evaluate()`'s `'definition template'` case at `definition.js:811-812` executes `throw Error("not 1 template")` inside the `conn.query` callback, outside of any protecting `try/catch`, causing an unhandled exception that terminates the validating node process.
