### Title
Unauthenticated `X-Shipit-User` header lets any holder of a scoped API token attribute deploys, rollbacks, task runs, locks and merges to an arbitrary GitHub identity - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`Api::BaseController` authenticates the *caller* via an HMAC-signed `ApiClient` bearer token, but resolves the *acting user* (`current_user`) from a plain, unsigned `X-Shipit-User` request header. This header is never covered by the token's signature or any other verification, so the identity used to attribute and, in one case, gate a privileged action is fully attacker-controlled while the permission/scope check still passes.

### Finding Description
`authenticate_api_client` verifies the `ApiClient` via `BasicAuth`/`ApiClient.authenticate`, which validates a `Shipit::SimpleMessageVerifier`-signed token and yields `@current_api_client`: [1](#0-0) 

Separately, `current_user` is derived purely from a client-supplied header with no cryptographic binding to the authenticated `ApiClient`: [2](#0-1) 

`ApiClient.authenticate` only proves possession of a signed token id; it carries no notion of "on behalf of user X": [3](#0-2) 

This unverified `current_user` is then passed as the "actor" into consequential domain operations that are otherwise gated only by the `ApiClient`'s coarse `permissions` list (e.g. `deploy:stack`, `lock:stack`), not by *who* the user is:

- Triggering a deploy: [4](#0-3) 
- Triggering a rollback / aborting a task: [5](#0-4) 
- Triggering/aborting a task: [6](#0-5) 
- Locking a stack: [7](#0-6) 
- Requesting a merge: [8](#0-7) 

The equality that should hold but doesn't:
`GitHub identity cryptographically authenticated for this request == User bound to actions performed in this request`

In reality: `identity used for authorization-relevant attribution = attacker-chosen X-Shipit-User header value`, while `identity that actually authenticated (i.e. that the ApiClient token proves) = whatever created that ApiClient` — these are two independent, unlinked values. Any caller holding a valid scoped `ApiClient` token (e.g. one that only has `deploy:stack`) can set `X-Shipit-User` to any existing login (e.g. an admin or a specific reviewer) and have all resulting `Task`/`Deploy`/`Rollback`/`Lock`/`MergeRequest` records, hooks, and notifications attributed to that impersonated user, with no verification that the request truly originated from them.

### Impact Explanation
This does not itself grant a *new* permission (the `ApiClient.permissions` check is still enforced), but it breaks the audit/attribution trust binding that downstream code and operators rely on for accountability of privileged actions (who locked the stack, who triggered a deploy/rollback, who aborted a task, who requested a merge). Combined with any legitimate but narrowly-scoped API token (e.g., a CI token with `deploy:stack` only), an attacker in possession of that token can falsely attribute deploys/rollbacks/locks to arbitrary GitHub users, undermining incident forensics and any policy built on `lock_author`/task actor fields. This lands as a High-severity issue: it is a broken authentication binding on a privileged, unauthenticated-read/write-adjacent identity field, analogous to the GMX report's core defect — a value that is *acted upon* (the secondary price / here, the acting `User`) without being covered by the verification mechanism that is supposed to guarantee its integrity (the oracle signature / here, the `ApiClient` token signature).

### Likelihood Explanation
Any party that already holds a valid, even narrowly-scoped, `ApiClient` bearer token (a routine, expected credential for CI systems, bots, or `ccmenu` widgets created via `CCMenuUrlController`) can trivially set an arbitrary `X-Shipit-User` header on every API call; no additional exploitation primitive is required, and this is the intended, documented mechanism (`identify_user`) rather than an edge case.

### Recommendation
Do not let an unauthenticated header determine the acting `User` for privileged domain actions. Either bind the acting identity to the `ApiClient.creator` (or a signed delegation token issued to a specific user), or require the `X-Shipit-User` header to be verified against the credential presented (e.g., signed alongside the token, or restricted to `ApiClient`s explicitly scoped to impersonate a specific user), and audit-log both the authenticated `ApiClient` and the claimed `X-Shipit-User` distinctly rather than merging them into a single trusted "current_user".

### Proof of Concept
1. Attacker is issued (or otherwise obtains) a legitimate `ApiClient` token scoped only to `deploy:stack` for a given stack (see `ApiClient::PERMISSIONS` and `check_permissions!`): [9](#0-8) 
2. Attacker sends: `POST /api/stacks/:id/deploys` with `Authorization: Basic <base64(client.authentication_token)>` and header `X-Shipit-User: admin-login`.
3. `authenticate_api_client` accepts the request (token is valid, permission `deploy:stack` present): [1](#0-0) 
4. `identify_user` resolves `current_user` to the `User` record with `login == 'admin-login'` purely from the header, with no proof the caller controls that account: [10](#0-9) 
5. `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)`, permanently recording the impersonated admin as the initiator of the deploy: [11](#0-10)

      def authenticate_api_client
        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'
        render(status: :unauthorized, json: { message: 'Bad credentials' })
      end

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
