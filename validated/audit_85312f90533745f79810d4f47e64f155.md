Confirmed: `Api::StacksController#stack` correctly uses `stacks.from_param!(params[:id])` (the api-client-scoped relation), while `Api::CCMenuController#stack` at `app/controllers/shipit/api/ccmenu_controller.rb:29-31` bypasses that scoping entirely and calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model.### Title
Api::CCMenuController scopes token permissions but not the stack it discloses build status for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` tokens minted for CCMenu integration are intentionally scoped to a single stack via `ApiClient#stack_id`, and `Api::BaseController#stacks` enforces that scoping for every other API endpoint. `Api::CCMenuController` overrides the `stack` lookup and queries `Stack.from_param!` directly, bypassing the scoping entirely, so a token authorized for one stack can be used to read the build status of any stack.

### Finding Description
`CCMenuUrlController#client` mints a stack-scoped `ApiClient` with only `read:stack` permission, tied to a specific stack via `ApiClient.create_with(...)` and consumed later by `authenticate_api_client`/`stacks`: [1](#0-0) 

The generic authorization binding is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, exposed as `stacks`, and every other API controller (e.g. `Api::StacksController#stack`) resolves the requested resource through this scoped relation: `@stack ||= stacks.from_param!(params[:id])`. [2](#0-1) [3](#0-2) 

`Api::CCMenuController`, however, defines its own `stack` method that queries the unscoped `Stack` model directly using the attacker-controlled `params[:stack_id]`, never consulting `current_api_client.stack_id`: [4](#0-3) 

`require_permission :read, :stack` only checks that the token has the `read:stack` permission string via `ApiClient#check_permissions!`, it does not check which stack the permission applies to: [5](#0-4) 

This breaks the invariant `stack a token authorizes == stack it touches`: the token is only ever supposed to authorize CCMenu reads for the one stack it was minted for, but `CCMenuController#show` will happily render any stack's status if that stack id is substituted in the URL. [6](#0-5) 

### Impact Explanation
An attacker who obtains (or is legitimately given, e.g. as a CI status-badge consumer) a CCMenu token scoped to Stack A can substitute any other `stack_id` in the CCMenu URL/query string and read Stack B's build status, last build label, and last build time — data the token was never authorized to see. This matches the "unauthenticated/unauthorized read of stack state" High-impact category: the token bypasses its own per-stack authorization scope to read state of stacks it was never granted access to.

### Likelihood Explanation
Exploitation requires only possession of any valid CCMenu token (these are handed out via URLs/query strings and are of relatively low sensitivity/scope by design, intended for a single stack's public CI status badge). No additional privilege, session, or GitHub credential is required beyond having one such token — a low bar. The request is a single unauthenticated (from the app's perspective, beyond the token) GET substituting `stack_id`.

### Recommendation
In `app/controllers/shipit/api/ccmenu_controller.rb`, remove the private `stack` override and use the scoped `stacks.from_param!(params[:stack_id])` (as `Api::StacksController` and `Api::BaseController#stack` do), so that a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id` scope.

### Proof of Concept
1. As user, visit any stack page to trigger `CCMenuUrlController#fetch`, obtaining a token scoped to Stack A (`ApiClient` with `stack_id = A.id`, `permissions = ["read:stack"]`).
2. Send `GET /api/stacks/<stack-B-owner>/<stack-B-repo>/<stack-B-env>/ccmenu?token=<tokenA>` (i.e., substitute Stack B's `stack_id` param while keeping token A).
3. `Api::CCMenuController#authenticate_api_client` authenticates token A successfully (`ApiClient.authenticate` only verifies the signed id, not the requested stack) at `app/controllers/shipit/api/ccmenu_controller.rb:33-36`.
4. `require_permission :read, :stack` passes because token A does have `read:stack` in `permissions`.
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped) to Stack B instead of being restricted to Stack A, and the response renders Stack B's `name`, `lastBuildStatus`, `lastBuildLabel`, etc. — data outside the token's authorized stack.
