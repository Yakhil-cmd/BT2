### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's `repository.full_name` matches the commit's owning stack/repository. Any GitHub `status` event whose signature validates for *some* organization can therefore create a `Status` row on a commit belonging to a completely different, unrelated stack, as long as the attacker can produce (or already knows) a commit with that exact SHA in a repository they control.

### Finding Description
The broken binding: `webhook.repository.full_name` (the repo that emitted/signed the event) should equal `commit.stack.repository.full_name` (the repo that owns the commit being updated). Trace:

- `StatusHandler` declares `state`/`description`/`target_url`/`context` as free-form `String` in its `params` block, with `sha` required, but never declares or checks `repository` [1](#0-0)  .
- `process` looks up commits by SHA globally and updates every match, without any repository/stack filter: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1)  .
- Contrast with the base `Handler` class, which other handlers use to scope work to the repository named in the payload via `stacks`/`Repository.from_github_repo_name(repository_name)` — `StatusHandler` never calls this helper [3](#0-2)  .
- `WebhooksController#verify_signature` only checks the webhook signature against the *organization* derived from the payload (`Shipit.github(organization: repository_owner)`), not against the specific repository/stack being mutated [4](#0-3)  .
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` persists `state`, `description`, `target_url`, `context` verbatim onto whatever commit matched, keyed only by `stack_id` derived from the matched commit (not from the webhook payload) [5](#0-4)  .

Exploit flow: an attacker with push/API access to any repository inside an organization that has the Shipit GitHub App installed (this can be an unrelated sandbox repo in that org — signature verification is organization-scoped, not repository-scoped) constructs a local git commit with an identical SHA to a target victim commit (feasible for public repos: git objects are content-addressed, so replaying the same tree, parents, author/committer identities and timestamps reproduces the same SHA1) and pushes it to their own repository. They then call GitHub's Statuses API on their own repo/sha with attacker-chosen `state` (one of `pending`/`success`/`failure`/`error` — the same four values `Status` validates against), `description`, and `target_url`. GitHub signs and delivers the resulting `status` webhook with `repository.full_name` = attacker's repo, but Shipit's `StatusHandler` ignores that field and matches purely on `sha`, writing a new `Status` onto the victim commit/stack.

`state` model-level validation (`Status` enum + `inclusion: { in: STATES }`) already constrains the value to GitHub's own four legitimate states, so the missing enum restriction in `ExplicitParameters` alone is not the exploitable gap [6](#0-5)  . The actual, demonstrable bug is the missing repository/stack scoping in `StatusHandler#process`.

Regarding content rendering: `description` is interpolated with `<%= %>` in a text node in `_status.html.erb`/`_group.html.erb`, which Rails auto-escapes, so HTML/script injection through `description` is neutralized [7](#0-6)  . `target_url` however is placed unescaped-of-scheme inside `href="<%= status.target_url %>"`; Rails' auto-escaping protects against attribute breakout but does not sanitize URI schemes, so a `javascript:` value would render as a clickable stored link [8](#0-7)  — a secondary, click-dependent concern, not the primary finding.

### Impact Explanation
Any unprivileged GitHub user with push/API access to one repository in an org onboarded to Shipit can write arbitrary `Status` rows (state/description/target_url/context) onto commits belonging to **any other stack/repository** tracked by that Shipit instance, as long as they can reproduce the target commit's SHA. Since `Status` rows drive CI-gating logic (`Commit#deployable?`, `blocking_statuses`, continuous delivery scheduling) [9](#0-8)  , a forged `success` status can make an undeployed, unreviewed commit appear "green" and eligible for automatic/continuous deployment on a victim stack — this is a cross-repository write that mutates another repository's stack/commit state, matching the Critical severity category. This is repeatable against any stack whose commits are guessable/reproducible (trivial for public repositories).

### Likelihood Explanation
Requires: (1) the attacker to have write/API access to at least one GitHub repository within an organization that already has the Shipit GitHub App installed (a low bar — could be any sandboxed or unrelated repo in a large org), and (2) knowledge of a target commit's exact git object metadata to reproduce its SHA (trivial for any public repository via the GitHub API). No Shipit secrets, sessions, or maintainer status are needed. This is inexpensive and repeatable against arbitrary stacks in the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the payload, mirroring the pattern used by other handlers (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`), and only update commits belonging to stacks under that repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`. Additionally, validate/sanitize `target_url` scheme (allow only `http`/`https`) before persisting or rendering it as an `href`.

### Proof of Concept
```ruby
test "status webhook from an unrelated repository must not mutate another stack's commit" do
  victim_commit = shipit_commits(:first) # belongs to shipit stack / shopify/shipit repo
  request.headers['X-Github-Event'] = 'status'

  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'description' => 'forged CI output',
    'target_url' => 'http://attacker.example/ci',
    'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: forged_payload, as: :json
  end
  # currently FAILS: a Status is created on victim_commit despite the payload
  # naming an unrelated repository, because StatusHandler#process matches
  # purely on params.sha with no repository/stack check.
end
```
Both sides of the equality to assert: `forged_payload['repository']['full_name']` ("attacker-org/unrelated-repo") vs `victim_commit.stack.repository.full_name` (e.g. "shopify/shipit") — these must differ, yet the current code still lets the write succeed, proving the binding is broken.
