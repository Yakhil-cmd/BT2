### Title
`UpdateCommissionBps` instruction removes all update-timing restrictions, allowing instant 0%→100% commission changes right before reward distribution - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The legacy `update_commission` handler in the vote program enforces a mid-epoch cutoff (`is_commission_update_allowed`) that blocks commission *increases* during the second half of an epoch, specifically to prevent "last-minute commission rug" attacks against delegators. [1](#0-0)  The newer `update_commission_bps` handler (SIMD-0291/SIMD-0123), which sets `inflation_rewards_commission_bps` and `block_revenue_commission_bps` in basis points, explicitly removes this rule: "No commission update rule, per SIMD-0249 and SIMD-0291." [2](#0-1)  This is confirmed by the in-repo test comment: "Unlike test_update_commission, SIMD-0291 has no timing restrictions... Updates are always allowed regardless of epoch position." [3](#0-2) 

### Finding Description
The vote-account authorized withdrawer can call `VoteInstruction::UpdateCommissionBps` at any slot, with any basis-point value up to 10000 (100%), and it applies immediately with no cooldown, no epoch-half restriction, and (per the dispatcher) no feature-gated delay analogous to `disable_commission_update_rule` used for the legacy path. [4](#0-3)  Compare this to `UpdateCommission`, which is explicitly gated by `is_commission_update_allowed(clock.slot, epoch_schedule)` unless the `delay_commission_updates` feature is active (in which case a full-epoch snapshot delay is used instead). [5](#0-4) 

For `InflationRewards` commission, the epoch-reward-calculation path (`calculate_stake_rewards_and_commissions` / `get_cached_vote_accounts`) mitigates this by reading the commission from a snapshot taken a full epoch earlier when `delay_commission_updates` is enabled — explicitly "to prevent last minute commission rugs." [6](#0-5)  However, this delayed-snapshot logic only ever reads `inflation_rewards_commission()` / legacy `commission()`; it does not reference `block_revenue_commission_bps` anywhere in that code path. [7](#0-6)  The `CommissionKind::BlockRevenue` variant of `update_commission_bps` can therefore be changed instantaneously with no epoch-boundary protection and no confirmed delayed-snapshot enforcement analogous to the inflation-rewards path.

### Impact Explanation
An authorized withdrawer (who is not required to be the block-producing identity and may be compromised or malicious) can front-run a reward/commission distribution by setting `block_revenue_commission_bps` (or, before the `delay_commission_updates` feature is active, `inflation_rewards_commission_bps`/legacy commission) to 10000 bps (100%) immediately before the epoch reward calculation or block-revenue distribution captures it, diverting stake rewards that should go to delegators entirely to the validator's commission account. This matches the accepted impact category of "misattributed or duplicated rewards" in the reward distribution path.

### Likelihood Explanation
Low-to-medium: requires a malicious or compromised vote-account authorized withdrawer (analogous to the "malicious or compromised admin" precondition in the original report) to time a commission-bps update against the epoch reward-calculation boundary. It does not require validator-identity/consensus-level privilege — only the vote account's withdraw-authority key, which is often held separately from the validator's voting/identity keys and can be a lower-trust delegated operator key.

### Recommendation
Apply the same protection used for `inflation_rewards_commission_bps`/`delay_commission_updates` (i.e., use a full-epoch-delayed snapshot, or enforce `is_commission_update_allowed`-style timing) uniformly to `CommissionKind::BlockRevenue` updates in `update_commission_bps`, rather than exempting all `UpdateCommissionBps` calls from any update-timing rule.

### Proof of Concept
1. Authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }` in the slot immediately preceding block-revenue reward calculation/distribution for the epoch.
2. `update_commission_bps` applies the change unconditionally — no `is_commission_update_allowed` check and no signer other than the withdraw authority is required. [8](#0-7) 
3. Because the delayed-snapshot protection in `calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards` is only wired to the inflation-rewards commission value, the newly-set 100% block-revenue commission is picked up without a one-epoch delay, and delegator stake rewards for that distribution are misattributed entirely to the commission account. [7](#0-6) 

Note: due to tool-budget limits I was unable to fully trace the exact site where `block_revenue_commission_bps` is applied to split block-revenue rewards between validator and delegators (likely inside the `DepositDelegatorRewards` instruction handling in `programs/vote/src/vote_processor.rs`), so the absence of any delay mechanism there is inferred from the explicit "no commission update rule" comment and the absence of `block_revenue_commission_bps` handling in the reward-calculation delay logic, not from directly reading the deposit/distribution function body.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
