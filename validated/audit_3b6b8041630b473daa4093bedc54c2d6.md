This is a genuine, exploitable trust-binding break, matching the "organization that authenticated versus the repository that is written" analog class.

### Title
Webhook signature is verified against the payload's claimed organization while the acted-upon repository is looked up from an independent, unverified payload field, allowing cross-organization writes on a shared Shipit instance - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to validate the HMAC signature against by reading `repository_owner` (i.e. `repository.owner.login` / `organization.login`) straight out of the still-unauthenticated JSON body. Every webhook `Handler` then independently determines *which* `Repository`/`Stack` to mutate by reading `repository.full_name`, also straight out of the same unauthenticated body [1](#0-0) . Nothing binds these two fields together, and nothing re-checks that the repository being written to actually belongs to the organization whose secret produced the valid signature.

### Finding Description
`verify_signature` picks the GitHub App/secret using attacker-suppliable data before any authentication has occurred: [2](#0-1) 

This is exactly the "add a Transfer function to get the payment" class of bug from the report: an operation (mutating state for a specific repository) is performed using a value (`repository.full_name`) that is never covered by the check that is supposed to authorize the operation (the signature, which is only proven to have been produced by the secret of `repository.owner.login`).

Shipit explicitly supports multiple GitHub organizations sharing one instance, each with its own independent `webhook_secret`, exactly as documented and tested: [3](#0-2)  and [4](#0-3) .

`Repository.from_github_repo_name` performs a global lookup by `owner/name` with no relation to which secret validated the incoming request: [5](#0-4) , and every handler uses it (directly or via `stacks`) to decide what to mutate: [6](#0-5) , [7](#0-6) , [8](#0-7) .

**Equality that should hold but doesn't:**
`organization whose secret signed the HTTP body` == `organization that owns the repository being mutated`.

Before the attacker's forged request: `repository_owner` (used to pick the verifying secret) and `repository.full_name`'s owner (used to pick the mutated `Repository`/`Stack`) are always the same, because GitHub itself sets both fields consistently in a real webhook for a given repo.

After the attacker's forged request: an attacker who is an admin of *any* one org onboarded to the shared Shipit instance (call it `OrgA`, with a known `webhook_secret_A`) can:
1. Build a JSON body with `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` selects `webhook_secret_A`.
2. Sign the raw body with `webhook_secret_A` (which `OrgA`'s admin legitimately knows/controls) to pass `verify_webhook_signature`.
3. Set `repository.full_name = "OrgB/victim-repo"` (a repository belonging to a different, more-trusted org `OrgB` also tracked by the same Shipit instance).
4. POST it to the public `/webhooks` endpoint.

The signature check passes (it only proves the body came from someone who knows `OrgA`'s secret), but the handler acts on `OrgB`'s repository/stack because `repository_name`/`from_github_repo_name` is read from the same untrusted body, unconstrained by which org actually authenticated.

### Impact Explanation
Depending on handler this yields, at minimum, unauthenticated-for-`OrgB` writes triggered by an `OrgA` credential holder:
- `push` handler triggers `stack.sync_github(expected_head_sha:)` for `OrgB`'s stacks [9](#0-8) .
- `pull_request` handlers (`opened`/`labeled`/`unlabeled`/`reopened`/`closed`) can create, archive, or unarchive `OrgB`'s review stacks based on forged pull-request data [10](#0-9) .
- `status` handler forges commit-status/CI results (`state`, `description`, `target_url`) attached to real commits, which Shipit deploy gating relies on to decide if a commit is "safe to ship" [11](#0-10) . This can be used to force a fake "success" status on a commit belonging to `OrgB`, directly influencing whether Shipit permits that commit to be deployed — an unauthorized-deploy-adjacent write across an authentication boundary.
- `membership` handler is not repository-scoped (it uses `organization.login`/`team`), but it demonstrates the same family: `verify_signature`'s org selection and the handler's own `params.organization.login` used to create/attach `Team` records are two independently-controlled fields in the same body, so `Team#organization` provenance is likewise not bound to the secret that validated the request [12](#0-11) .

This satisfies "escalation into `Shipit.github_teams` authorization" / "cross-repository writes" class impact, because a lower-trust org tenant can forge state changes (including fake CI "success" statuses that gate deploys) for a higher-trust org's repository, all while the signature check itself reports success.

### Likelihood Explanation
Requires only: (a) the deployment operator running Shipit with more than one GitHub App/organization configured (an explicitly documented and tested configuration), and (b) attacker control of the webhook secret for any one onboarded org (e.g., being an admin/maintainer of one of the smaller orgs allowed onto the shared instance) — no privileged Shipit session, `ApiClient` token, or GitHub write access to the victim org is needed. The `/webhooks` endpoint is intentionally public and unauthenticated except for this signature check.

### Recommendation
After selecting the GitHub App/secret used to verify the signature, re-derive the trusted organization login server-side (from the app/secret context that actually validated, not from the payload), and reject or hard-scope any handler action whose `repository.full_name` / `organization.login` owner does not match that trusted organization. I.e., bind the verified organization identity to every repository/organization-scoped mutation performed in `Handler#stacks`, `Repository.from_github_repo_name`, and `MembershipHandler#find_or_create_team!`, rather than trusting the same unauthenticated JSON fields for both signature-key selection and target-resource selection.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_of_OrgA, raw_body)>

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha, e.g. a benign old commit>",
  "repository": {
    "owner": { "login": "OrgA" },   // selects webhook_secret_A for verify_signature
    "full_name": "OrgB/victim-repo" // handler acts on OrgB's tracked stacks
  }
}
```
`verify_signature` computes `Shipit.github(organization: "OrgA").verify_webhook_signature(sig, raw_body)` and succeeds because the attacker (an `OrgA` admin) legitimately knows `webhook_secret_A`. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack, an action `OrgA`'s credentials were never supposed to authorize [9](#0-8) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
