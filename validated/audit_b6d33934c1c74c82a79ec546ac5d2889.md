## Title
Unbounded complexity amplification via repeated `is_valid_signed_package` calls resolving chained "address" definitions with a fresh complexity budget each time - ([File: formula/evaluation.js], [File: signed_message.js], [File: definition.js])

### Summary
The DNS advisory's root cause is that Twisted's loop-guard (`visited` set) is reset for every DNS *Question* in a message, so an attacker can multiply an otherwise-bounded per-record cost by the number of questions in a single packet, causing unbounded total work from one message. The analogous pattern in `ocore` is `oscript`'s `is_valid_signed_package()` function, which invokes `signed_message.validateSignedMessage()` → `Definition.validateAuthentifiers()` / `validateDefinition()` with a **brand-new, independent `complexity`/`count_ops` budget** (`var complexity = 0; var count_ops = 0;` inside `definition.js`'s `validateDefinition`) every time it is called [1](#0-0) . Because an AA formula/oscript trigger can call `is_valid_signed_package()` many times (each counted only once towards the *caller's* complexity budget, per `MAX_COMPLEXITY`), an attacker-supplied trigger can drive the total definition-resolution work far beyond any single `MAX_COMPLEXITY`/`MAX_OPS` cap by supplying many independent signed packages whose author address definitions are deep chains of nested `["address", X]` references.

### Finding Description
`Definition.validateDefinition()` walks an address/asset-condition definition tree and enforces `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` via a local counter incremented in `evaluate()`: [2](#0-1) 

The `"address"` operator in that same evaluator recursively resolves another address's stored definition via `storage.readDefinitionByAddress` and re-runs `evaluate()` on the nested definition, so nested/chained address definitions are fully re-walked and re-counted every time: [3](#0-2) 

`validateAuthentifiers()` first calls `validateDefinition()` (bounded by `MAX_COMPLEXITY`) and then walks the *same* tree again in a second `evaluate()` that has **no complexity/ops counter at all** and, for the `"address"` op, again fetches and recursively evaluates the nested definition: [4](#0-3) [5](#0-4) 

Both `complexity` and `count_ops` are local variables re-initialized to 0 on every call to `validateDefinition`/`validateAuthentifiers` — there is no cumulative, cross-call budget analogous to a single DNS message's total pointer-dereference count. This function is reachable from an AA trigger via the oscript builtin `is_valid_signed_package`, implemented in `formula/evaluation.js` and wired through `signed_message.validateSignedMessage()`, which itself iterates `authors` and calls `Definition.validateAuthentifiers` per author with a fresh `objValidationState.complexity = 0`: [6](#0-5) 

The AA-formula complexity accounting (`formula/validation.js` / `formula/evaluation.js`) only charges a fixed, small cost for the `is_valid_signed_package` *call itself* — it does not fold in the (potentially large) cost of the nested `Definition.validateAuthentifiers` walk it triggers. An attacker who defines several deeply-chained addresses (`A → ["address", B]`, `B → ["address", C]`, …, each near the `MAX_COMPLEXITY`/`MAX_DEPTH` limit) can post a single AA trigger unit containing a `data`/`text` message whose payload formula calls `is_valid_signed_package()` on many distinct signed packages (or the same one many times), each one independently re-resolving and re-evaluating a maximal-depth definition chain, multiplying the DB reads and recursive evaluation work by the number of calls — the same "reset the loop/complexity guard per sub-item" pattern that caused the Twisted DoS.

### Impact Explanation
Every full node evaluating the AA trigger (to determine bounce/response and to reach consensus on validity) must perform this unbounded amount of recursive definition-resolution work (DB reads via `storage.readDefinitionByAddress` plus repeated tree walks) while single-threaded/synchronous portions run, before any bounce/timeout can occur. This can stall or significantly slow down unit/AA-trigger processing across the network for that unit, causing nodes to disagree on validity if some time out differently, or a general slowdown that prevents timely confirmation of new units — matching the "network unable to confirm new units" / "node disagreement on validity" impact categories.

### Likelihood Explanation
Reaching this requires only: (1) defining several ordinary payment addresses whose definitions form a chain of `["address", <addr>]` references (each within existing `MAX_COMPLEXITY`/`MAX_DEPTH` limits, so each individually validates fine), and (2) posting an AA trigger unit (or a unit invoking such a formula) that calls `is_valid_signed_package()` multiple times referencing signed packages authored by these chained addresses. Both address-definition posting and AA-trigger posting are actions available to any unprivileged unit poster / AA trigger sender, matching the reachable-actor requirement.

### Recommendation
- Thread a shared/cumulative complexity-and-ops budget through `Definition.validateDefinition`/`validateAuthentifiers` calls that originate from `is_valid_signed_package`, charging the nested definition-resolution cost back into the calling formula's `complexity`/`count_ops` (similar to how `objValidationState.max_complexity` is already used for outer-level "custom complexity limit" checks) so repeated calls cannot bypass the global AA complexity limit.
- Cap the number of `is_valid_signed_package` (and other definition/authentifier-resolving) calls allowed per formula evaluation, or make each such call consume complexity proportional to the resolved definition's own complexity rather than a fixed constant.
- Add the missing complexity/ops accounting to the second `evaluate()` in `validateAuthentifiers` (the one lacking any counter), and cache resolved nested address definitions within a single top-level call so identical `["address", X]` lookups aren't repeatedly walked.

### Proof of Concept
Conceptual (not executed, no sandbox access):
1. Create addresses `A1 … A_N` where each `Ai`'s definition is `["address", A(i+1)]`, ending in a normal `["sig", {pubkey}]`, chained close to `MAX_DEPTH`/`MAX_COMPLEXITY`.
2. Author a signed package (or several) whose `authors[].address` is `A1` with a plausible (even invalid) signature/authentifier.
3. Deploy/trigger an AA whose formula contains: `is_valid_signed_package(pkg1, A1) || is_valid_signed_package(pkg2, A1) || ... (repeated K times)`.
4. Post a trigger unit invoking this AA. Each call independently re-resolves and re-walks the `A1→…→A_N` chain from the DB with a fresh complexity budget, so total work scales with `K × N` even though the formula's own complexity/op count stays low, well under `constants.MAX_COMPLEXITY`.

Note: I could not fully verify the exact fixed complexity cost charged for a single `is_valid_signed_package` call in `formula/evaluation.js`/`formula/validation.js` (grep found the references but I ran out of iterations before reading those exact lines), nor definitively confirm there is no additional global safeguard (e.g., a wall-clock timeout) elsewhere in AA trigger handling that would limit real-world impact. This should be verified by reading `formula/evaluation.js` and `formula/validation.js` around their `is_valid_signed_package` handling, and the AA trigger execution timeout logic, in a full Devin session before treating this as fully confirmed.
