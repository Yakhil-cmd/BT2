This confirms the exploit chain. In the multi-org configuration mode, `Shipit.github(organization:)` at [1](#0-0)  looks up a distinct `GitHubApp` (and therefore a distinct `webhook_secret`) per GitHub organization name found in the attacker-controlled payload. The `WebhooksController#verify_signature` selects which organization's config/secret to verify against using `repository_owner`, which is read directly from the unverified JSON body before any signature check: [2](#0-1) [3](#0-2) . Meanwhile, the event handlers (e.g. `PushHandler`, pull-request handlers) act on `payload.dig('repository', 'full_name')` — a separate, independently attacker-controlled field not tied to `repository_owner` — to locate the `Stack`/`Repository` to operate on: [4](#0-3) [5](#0-4) .

### Title
Webhook signature verification uses attacker-controlled `repository.owner.login` to select the signing secret, decoupled from the `repository.full_name` the handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and thus which `webhook_secret`) to validate a webhook's HMAC signature against, based on `repository_owner`, a value read straight out of the unauthenticated JSON body. The event handlers that subsequently act on the request use a different, also-unauthenticated field, `repository.full_name`, to determine which `Stack`/`Repository` in the Shipit database gets mutated. Because these two attacker-controlled fields are never bound to each other or checked for consistency, an attacker can craft a payload whose `organization`/`repository.owner.login` selects a GitHub App entry that has no `webhook_secret` configured (or one whose secret is guessable/leaked), while `repository.full_name` references an entirely different, protected repository whose stacks they want to influence.

### Finding Description
- `GitHubApp#verify_webhook_signature` explicitly treats an unconfigured `webhook_secret` as "no verification required": `return true unless webhook_secret` [6](#0-5) .
- The controller determines *which* `GitHubApp`/secret applies purely from the unverified payload's `repository.owner.login` (or `organization.login`) before the signature is ever checked: [7](#0-6) .
- In multi-org deployments (`Shipit.github_app_config`), each organization has its own independent `webhook_secret` entry, looked up by downcased org name from the payload: [1](#0-0) .
- After "verification" passes, the actual event handlers (`PushHandler`, `PullRequest::*Handler`, etc.) resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a completely separate field from the one used to select the signing secret: [4](#0-3) .

The binding that should hold is: `organization/secret used to authenticate the request == owner of the repository that is subsequently written to`. Instead the engine checks `organization used to pick a secret == payload["repository"]["owner"]["login"]` (attacker-supplied) while acting on `payload["repository"]["full_name"]` (also attacker-supplied, independently settable). Nothing forces these two fields to refer to the same repository/org.

### Impact Explanation
If the Shipit deployment is configured with multiple GitHub organizations and any one of them has no `webhook_secret` set (a state the docs present as a valid, supported configuration — see `webhook_secret: # nil` examples in `docs/setup.md` and the secrets templates), an attacker can forge a webhook: set `repository.owner.login`/`organization.login` to that unsecured org, and set `repository.full_name` to any other, secret-protected repository/stack managed by the Shipit instance. `verify_signature` will pass because `webhook_secret` is blank for the chosen org, yet the handler will process the event (e.g. `PushHandler` triggers `stack.sync_github`, pull-request handlers can archive/unarchive/provision review stacks) against the targeted repository, achieving an unauthorized action that should have required a valid GitHub-signed webhook for that repository's organization.

### Likelihood Explanation
This requires a multi-org Shipit deployment where at least one configured organization lacks a `webhook_secret` — a configuration explicitly shown as supported in `docs/setup.md` and the example secrets files. Given that setup, exploitation requires only sending a single unauthenticated HTTP POST with attacker-chosen JSON; no credentials, tokens, or GitHub access are needed.

### Recommendation
Bind signature verification to the same repository/organization the handlers act on: derive the organization used for `verify_webhook_signature` from `repository.full_name`'s owner (or otherwise cross-check that `repository.owner.login` matches the owner portion of `repository.full_name`) before dispatching to handlers. Additionally, consider refusing to treat a missing `webhook_secret` as automatically verified in multi-org configurations, and require `require(webhook_secret.present?, ...)`-style enforcement per organization rather than silently allowing unsigned webhooks.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `SecretOrg` (has `webhook_secret` set, owns the real target repository `SecretOrg/critical-repo`) and `OpenOrg` (no `webhook_secret` configured).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "SecretOrg/critical-repo",
    "owner": { "login": "OpenOrg" }
  }
}
```
No valid `X-Hub-Signature` is required (or any bogus value works) since `Shipit.github(organization: "OpenOrg")` resolves a `GitHubApp` with `webhook_secret` nil, so `verify_webhook_signature` returns `true` unconditionally.
3. `WebhooksController#create` then dispatches the `push` event to `Handlers::PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("SecretOrg/critical-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the protected repository's stacks, an action that should have required a valid webhook signature from `SecretOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
