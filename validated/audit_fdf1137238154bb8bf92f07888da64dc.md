### Title
Unbounded key-range scan in `data_feed`/`in_data_feed` evaluation lets any oracle-controlled address DoS AAs that depend on its feed - ([File: data_feeds.js])

### Summary
The reported bug class is a matching loop whose per-call cost is proportional to attacker-controlled entries that persist forever in a shared on-chain structure, letting an attacker cheaply grow that structure until any legitimate consumer's transaction becomes computationally unaffordable and reverts/blocks. In `ocore`, the closest reachable analog is the `data_feed`/`in_data_feed` oscript operators, which are evaluated for every AA trigger that references a data feed and which perform an unbounded LevelDB key-range scan (`dataFeedByAddressExists`) whose cost grows linearly with the number of feed postings an address (the "oracle") has ever made, with no cap on how many such postings a single address can create.

### Finding Description
`in_data_feed`/`data_feed` formulas call into `dataFeeds.dataFeedExists` / `dataFeeds.readDataFeedValue`, which for relational queries (`>`, `>=`, `<`, `<=`, `!=`) open a `kvstore` key stream over *all* data-feed entries for that `(address, feed_name)` pair that satisfy the value relation, and only stop early once an entry within the requested `[min_mci, max_mci]` window is found [1](#0-0) . If no entry in the requested mci window matches, the stream must be drained to completion, inspecting every single feed record ever posted by that address for that feed name and relation, before returning "not found" [2](#0-1) .

Crucially, the formula-validation stage (`formula/validation.js`, `definition.js`) only bounds the *complexity/op-count of the expression tree* itself (`MAX_COMPLEXITY`, `MAX_OPS`) [3](#0-2) [4](#0-3)  - it does not, and cannot, account for the number of key-value records that a `data_feed` op will have to scan at *evaluation* time. That runtime cost is entirely a function of how many `data_feed` app messages the referenced oracle address has posted historically, which is unbounded: any address can post an unlimited number of `data_feed` payloads over time (each stored permanently under `df\n<address>\n<feed_name>\n...` keys, see the writer/stabilization code that persists these entries forever) [5](#0-4) .

AAs commonly parameterize which address is treated as "the oracle" from trigger data (self-quoted markets, escrow/attestation-style AAs, or any AA design that lets the trigger's own address act as an oracle for itself). In such designs the attacker fully controls the address being queried, and can flood it with an arbitrarily large number of chaff `data_feed` postings whose values fall inside the scanned relation range but whose `mci` deliberately falls outside any window a legitimate future trigger would use. Every subsequent AA trigger that must resolve `data_feed[[oracles=<attacker address>, feed_name=..., min_mci=...]]` (or `in_data_feed`) is then forced to scan the entire accumulated history of postings before it can conclude the feed value is absent, mirroring the reported pattern where legitimate participants are forced to pay for iterating an attacker-inflated collection with no way to bound the cost.

### Impact Explanation
This does not directly move funds by itself, but it directly parallels the accepted impact classes: an AA relying on such a data-feed check can be forced into extremely expensive, unbounded-time evaluation on every full node validating/executing the trigger unit, well beyond what the formula's declared `complexity`/`count_ops` budget represents. Because AA response computation happens synchronously during main-chain stabilization for every node, a sufficiently large, cheaply-created backlog of chaff feed postings can (a) freeze funds in the AA by making any operation depending on that feed permanently bounce/timeout ("AA fund loss or freezing"), and (b) if evaluation stalls processing long enough across nodes, contribute to "a network unable to confirm new units" in the affected AA's execution path, since AA response processing is part of unit stabilization.

### Likelihood Explanation
Posting `data_feed` messages is a cheap, fully permissionless operation available to any unit author (byte fee only), and nothing in `data_feeds.js`, `validation.js`, or `writer.js` limits how many feed entries a single address may create over its lifetime. The only requirement for exploitation is an AA design that resolves the oracle address (fully or partially) from attacker-controlled trigger data, which is a common and encouraged AA pattern (e.g., self-service data feeds, generalized bulletin/market AAs). This makes the attack setup low-cost and repeatable, though the impact is scoped to AAs whose logic effectively lets the attacker choose the oracle address being queried — reducing but not eliminating real-world applicability.

### Recommendation
Bound the runtime cost of `data_feed`/`in_data_feed` resolution independent of formula-level complexity: e.g., impose a hard cap (`limit`) on the number of KV records inspected per `dataFeedByAddressExists`/`readDataFeedByAddress` call (returning a deterministic "too many candidates" error instead of scanning unboundedly), and/or charge formula complexity/op cost proportional to the actual number of records scanned rather than a fixed cost per `data_feed` node in `formula/validation.js`/`definition.js`.

### Proof of Concept
Not independently reproduced in this review (no execution environment available); the analysis is based on static code tracing of `data_feeds.js`, `formula/evaluation.js`, `formula/validation.js`, `definition.js`, and `main_chain.js`, mirroring the reported pattern: an attacker posts an unbounded number of cheap `data_feed` app messages from an address they control (or that an AA lets them designate as "oracle" via trigger data), causing `dataFeedByAddressExists`'s key-stream scan to grow linearly with attacker-created records and to run to completion whenever the sought mci window is deliberately excluded, imposing unbounded per-call cost on any AA trigger that resolves that feed.
