### Title
Webhook signature verified against the payload's own `repository.owner` while commit-status writes are unscoped, allowing cross-organization CI status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook signature-verification code selects which GitHub App/organization's `webhook_secret` to verify against using an untrusted field taken from the same payload it is verifying, and the `status` webhook handler that consumes that payload never re-checks that the commit it writes actually belongs to that organization/repository. This breaks the trust binding `organization that authenticated == repository/commit that is written`, analogous to the reported `quoteState`/`state` variable-confusion bug where the wrong entity was updated relative to the one that was validated.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to fetch the webhook secret directly from the untrusted JSON body: [1](#0-0) [2](#0-1) 

This only proves the request was signed with *some* configured organization's `webhook_secret`; it proves nothing about which repository/commit the rest of the payload refers to. The generic `Handler` base class does attempt to scope most events by `repository.full_name`: [3](#0-2) 

but `StatusHandler`, which processes GitHub `status` events, bypasses this scoping entirely and matches commits globally by SHA, with no repository/organization check at all: [4](#0-3) 

Because `Commit.where(sha: params.sha)` is not filtered by repository, any commit sharing that SHA in *any* stack hosted by the same Shipit instance (across any onboarded organization) will receive a forged status. The only "authentication" performed is verifying the HMAC using the webhook secret of the organization named in the attacker-controlled `repository.owner.login` field — a field that has no enforced relationship to the `sha` also supplied in the same payload.

### Impact Explanation
An entity that knows (or legitimately possesses, e.g., as an administrator of their own onboarded org's GitHub App) the `webhook_secret` for **one** organization configured in `Shipit.github` can sign an arbitrary JSON body with that secret while setting `repository.owner.login` to their own org (satisfying `verify_signature`) and `sha`/`state`/`context` to target a commit belonging to a completely different stack/organization. `StatusHandler#process` will call `commit.create_status_from_github!` and persist a fabricated `"success"` status for that foreign commit. Because `Stack#required_statuses`/`Commit#deployable?` gate continuous deployment on exactly these `CommitStatus` records (`app/models/shipit/deploy_spec.rb` `required_statuses`, `app/models/shipit/stack.rb` continuous-delivery logic), this can cause the target stack to treat an unreviewed/unsafe commit as CI-green and trigger an **unauthorized deploy** via continuous deployment — a Critical-severity outcome per the engine's own impact criteria.

### Likelihood Explanation
Exploitation requires only knowledge of a valid `webhook_secret` for any one organization onboarded to the Shipit instance — not privileged access to the target organization/repository, not a Shipit session, and not an `ApiClient` token. In any multi-tenant deployment (as the repo's own `config/secrets.development.shopify.yml` and `lib/shipit/github_app.rb` multi-org support anticipate), this is a realistic boundary: org A's webhook administrator is an "unprivileged attacker" with respect to org B's repositories/stacks, yet can forge status data for org B's commits.

### Recommendation
- In `WebhooksController#verify_signature`, after verifying the HMAC, cross-check that `repository.full_name`'s owner matches the `repository_owner` used to select the webhook secret (reject if they differ).
- In `StatusHandler#process` (and any other handler that queries by a cross-repository-ambiguous key such as SHA), scope the lookup through `stacks`/`repository_name` (as the base `Handler` class already does for other events) instead of querying `Commit` globally by `sha`.

### Proof of Concept
1. Attacker administers GitHub App/org `attacker-org`, which is configured in this Shipit instance and whose `webhook_secret` the attacker therefore knows.
2. Attacker crafts a `status` event JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" },
  "sha": "<sha of a commit belonging to victim-org/victim-repo stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")`, verifies successfully, and the request proceeds.
5. `StatusHandler#process` finds the victim's commit by SHA (ignoring the `attacker-org` scoping) and persists a forged "success" status, which the victim stack's continuous-deployment logic can subsequently treat as satisfying required CI checks, triggering an unauthorized deploy.
