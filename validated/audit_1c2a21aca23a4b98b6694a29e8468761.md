### Title
Single-Step, Irreversible Address Definition Change Enables Fund Freezing/Takeover of Multi-Signer Addresses - ([File: validation.js])

### Summary
`ocore` allows any address to change its own authentication rules (its "definition") via a single `address_definition_change` message, committed permanently and irreversibly the moment the unit becomes stable — analogous to the single-step `changeOwner` pattern flagged in the report. For addresses whose definition is composed with `or`, any one signer who can satisfy just one branch of the definition can unilaterally replace the *entire* address definition with an arbitrary `definition_chash` in one step, with no confirmation/acceptance step from the other co-owners and no way to reverse the change.

### Finding Description
The `address_definition_change` message is validated in `validateInlinePayload` with only superficial checks — it verifies the payload shape and that `definition_chash` is a validly formatted hash, but never checks that the change is agreed to by all parties who logically "own" the address, nor does it provide any mechanism to confirm/accept or revoke the change from the counterpart side: [1](#0-0) 

Once the unit signing the change is authored, only the address's *current* definition (evaluated by `validateAuthentifiers`/`evaluate` in `definition.js`) needs to be satisfied to submit the change — not unanimous consent of all “owners”. Crucially, `or` clauses are supported in definitions, and a signer who can satisfy the `or` alone is treated as sufficient authorization for anything the address does, including replacing its own definition: [2](#0-1) 

The check for whether a given authentifier path is “used” by the message is only about which signature paths are present, not about whether all parties to a shared/multisig-style `or` definition consented: [3](#0-2) 

Once broadcast and stabilized, the change is committed in a single, final step with no pending/undo window: [4](#0-3) 

From that point on, `readDefinitionChashByAddress`/`readDefinitionByAddress` treat the new `definition_chash` as authoritative for all future validation of units from that address — the old definition can never again authorize anything for that address: [5](#0-4) 

Additionally, `checkNoPendingChangeOfDefinitionChash` only prevents the *same* address from posting further units until a keychange is stable — it enforces ordering but provides no ability for another owner to contest or roll back a bad/malicious change once it becomes stable: [6](#0-5) 

Nothing in the protocol requires that the poster of `address_definition_change` actually knows/controls a definition matching the new `definition_chash` before the change takes effect — the chash is opaque and can be a typo, a hash of an unusable definition, or a hash of a definition secretly favoring one party (e.g., a definition requiring only that party's own key). This exactly mirrors the audit finding's root cause: a critical, security-relevant field (owner/definition) is changed in one irreversible step, with no acceptance step from the affected party to catch a mistaken or adversarial value.

### Impact Explanation
For addresses defined with `or`-composed conditions (a common pattern for recovery wallets, escrow, or shared control — e.g., `["or", [["sig",...],["sig",...]]]`), any single co-owner satisfying one branch can:
1. Permanently freeze the funds at the address by setting `definition_chash` to an unrecoverable/unknown hash (self or malicious griefing), locking out all co-owners including themselves — a direct "AA/wallet fund freezing" impact.
2. Unilaterally seize exclusive future control of the address by setting `definition_chash` to a definition only they control, cutting other legitimate co-owners out of an address they previously had rights to — an "unauthorized [future] spending" / hostile-takeover impact, since after stabilization only the new definition governs the address, and the excluded co-owner has no recourse.

There is no 2-step confirm/accept flow (comparable to `Ownable2Step`) that would let the other party detect and reject a malicious or erroneous `definition_chash` before it takes effect.

### Likelihood Explanation
This does not require any external attacker or malicious peer/hub — it is reachable purely by a legitimate co-signer of a shared address (an "unprivileged unit poster" from the address's own signer set) broadcasting a single, otherwise well-formed unit. Any wallet built on `or`-composed multi-owner or recovery-style address definitions using `address_definition_change` for key rotation is exposed. This is a design-level gap in the base validation logic (`validation.js`, `definition.js`, `writer.js`, `storage.js`), not a bug limited to a specific app.

### Recommendation
Introduce a two-step definition change flow at the protocol/wallet level for addresses with multiple independent authorization branches (`or`):
- Require the new definition (not just its chash) to be disclosed/pre-verified as part of the change proposal, and/or
- Require a `has definition change`/`seen definition change`-style acknowledgment from all named co-owners, or a timelocked "pending" state during which any co-owner can veto or the old definition remains valid for a grace period, mirroring `Ownable2Step`'s `pendingOwner`/`acceptOwnership` pattern.
- At minimum, wallet software constructing `or`-composed multisig/recovery definitions should document/enforce that `address_definition_change` must never be reachable by fewer than all parties (e.g., always require `and` at the definition-change-authorizing level even if spending uses `or`), but this should also be enforced/warned about at the `ocore` validation layer since it currently allows it silently.

### Proof of Concept
1. Two parties, Alice and Bob, jointly create an address with definition `["or", [aliceSigDef, bobSigDef]]`.
2. Bob (acting alone, satisfying only his `sig` branch) composes and broadcasts a unit from this address containing an `address_definition_change` message with `definition_chash` set to the chash of a definition only Bob controls (e.g., `["sig", {pubkey: bobOnlyKey}]`), per `composeDefinitionChangeJoint`: [7](#0-6) 
3. `validateInlinePayload` accepts the message because `definition_chash` is a validly-formatted hash and the message references the correct address — no check for Alice's consent: [1](#0-0) 
4. `validateAuthentifiers`/`evaluate` on the `or` definition succeeds because Bob alone satisfies one branch.
5. Once the unit stabilizes, `writer.js` commits the change to `address_definition_changes`, and `storage.readDefinitionChashByAddress` now returns Bob's new chash as authoritative for the address.
6. Alice can no longer sign for the address at all — Bob has unilaterally and irreversibly taken exclusive control, or (if he set a bogus/unknown chash) permanently frozen the funds for both parties.

Note: I could not verify wallet-layer (`headless-wallet`/GUI) safeguards outside `ocore--013` core validation code that might mitigate exposure to this pattern in practice (e.g., UI warnings before generating `or`-composed shared addresses); this analysis is scoped to the core protocol/validation logic indexed in this repository.

function readDefinitionChashByAddress(conn, address, max_mci, handle){

	if (max_mci == null || max_mci == undefined)

	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}
