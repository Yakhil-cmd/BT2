### Title
Reusable L1 BTC-lockup proof lets a staker re-credit the same UTXO to a fresh bond after rolling out, double-counting Bitcoin collateral for signer/reward shares - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 path accepts a Bitcoin SPV proof (`verify-l1-lockups` → `validate-l1-lockup`) that a specific BTC UTXO is locked to a timelock script, and credits `sats-total` sats of stake weight to the bond without ever recording, in contract state, that this particular `(txid, output-index)` has been consumed. The only de-duplication (`seen-outpoints`) is scoped to the single call's `fold` over the `outputs` list passed in that one transaction.

### Finding Description
`validate-l1-lockup` at [1](#0-0)  checks a candidate BTC outpoint against `seen-outpoints`, a list that is threaded only through the current `fold` call: [2](#0-1) . There is no persistent, globally-checked map (e.g. `used-l1-outpoints`) that marks an outpoint as spent once it has been used to credit a bond in a prior transaction. This is the same root-cause shape as the LevelMinting report: collateral "type/identity" that backs a mint is not durably recorded at the moment credit is given, so it can later be reintroduced to obtain credit it no longer (or never) exclusively backs.

Concretely: `register-for-bond` sets `protocol-bond-memberships` for `tx-sender`, keyed only by principal [3](#0-2) . A staker can later exit that bond (naturally expire, or roll via `stake`/`register-for-bond` into a non-overlapping position, both of which delete/replace the membership row as seen in the `stake` and `register-for-bond` bodies at [4](#0-3)  and [5](#0-4) ). Because `verify-l1-lockups`/`validate-l1-lockup` never marks the underlying BTC outpoint as globally consumed, the exact same SPV proof for the same still-locked (or even already-unlocked-on-L1) UTXO can be resubmitted in a subsequent `register-for-bond` call — for the same bond re-run later, or for a different bond index — as long as it still satisfies `unlock-burn-height >= minimum-unlock-height` for the new bond in `validate-l1-lockup` [6](#0-5) . The contract has no way to observe that the BTC is still actually encumbered on L1 at that moment — it only replays a stale Merkle/header proof.

The equality this breaks is: *"sats credited by an L1 proof were locked on Bitcoin at credit time and represent bond collateral exactly once."* Reusing the proof breaks this because the same BTC value can back `sats-total` shares in more than one non-overlapping bond term issued to the same principal, while the STX-side lock accounting (`pox_rollover_v5` / `pox_lock_update_v5` in `pox-locking/src/pox_5.rs`) only tracks the STX lock, not whether the sBTC/L1 collateral backing the *shares* map is still economically present.

### Impact Explanation
If exploitable, this allows a staker to obtain signer/reward shares (`protocol-bonds-total-staked`, `signer-shares-staked-for-cycle`, `staker-shares-staked-for-cycle`) in multiple successive bonds while the underlying BTC value was only actually put at risk once (or, if the L1 timelock has already expired/been spent by the time of the second submission, not at risk at all). This is a case of a locked/committed value being double-counted for reward-share purposes — classified as High under the "signing weight or reward slots exceeding locked value" criterion, since it inflates a staker's proportional claim on `get-rewards`/`calculate-rewards` sBTC payouts beyond what their real collateral justifies.

### Likelihood Explanation
Likelihood is moderate to low-confidence without deeper verification: exploiting it requires (a) rolling out of a bond that used the L1 path, and (b) resubmitting the identical SPV proof to a later `register-for-bond` call whose `minimum-unlock-height` gate still passes. I was not able to fully trace, within the available iterations, whether `verify-block-header`/`parse-block-header` or a companion mechanism elsewhere in the codebase (e.g., a `used-outpoints` persisted map outside the excerpted region, or checks performed at a different layer such as `sbtc.rs`) independently prevents cross-call replay of the same outpoint. I did not find such a mechanism in the reviewed portions of `pox-5.clar`, but the contract is large and I could not read it in full.

### Recommendation
Persist consumed L1 outpoints in a durable map (e.g. `(define-map used-l1-lockup-outpoints { txid: (buff 32), output-index: uint } bool)`) and assert non-membership in `validate-l1-lockup`, setting the entry on success. This closes the gap between "proof accepted for credit" and "collateral tracked as consumed," mirroring the LevelMinting fix of tying redemption/credit strictly to the specific collateral instance that was actually deposited/locked.

### Proof of Concept
Conceptual PoC (not executed, given tool-access limits):
1. Staker registers for `bond-index=0` via the L1 path in `register-for-bond`, submitting a valid SPV proof for BTC UTXO `(txid_A, 0)` locked until height `H` ≥ bond 0's `minimum-unlock-height`; this credits `sats-total` shares to bond 0 and sets `protocol-bond-memberships`.
2. Staker rolls out of bond 0 (via `stake`, which clears `protocol-bond-memberships` per [4](#0-3) ) once outside bond 0's overlap window.
3. A later bond (e.g. `bond-index=6`, whose `minimum-unlock-height` is still ≤ `H`) is set up; the staker calls `register-for-bond` again, resubmitting the *same* SPV proof for `(txid_A, 0)`. `validate-l1-lockup`'s checks (script hash, amount, Merkle proof, unlock height) all still pass because they only validate the historical Bitcoin block, not whether the outpoint was already consumed by a previous Stacks-side credit.
4. Bond 6 credits `sats-total` again for the same BTC, while bond 0 already counted it for cycles it wasn't fully overlapping with — resulting in the same BTC collateral counted toward reward shares across two bonds.

I was unable to confirm within this session whether a hidden replay guard exists elsewhere that would block step 3; this should be verified against the full `pox-5.clar` and any related sBTC/L1-proof helper modules before treating this as fully confirmed.
