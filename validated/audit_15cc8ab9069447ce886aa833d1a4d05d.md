### Title
Webhook signature is verified against the wrong organization key, allowing cross-organization forgery of GitHub webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but the downstream handlers that decide *which* `Repository`/`Stack` record to mutate use a *different* field of the same JSON body — `repository.full_name`. Because GitHub webhook signatures cover only the raw byte payload and Shipit never checks that `owner.login` is a prefix of `full_name`, an attacker who legitimately controls one GitHub organization (and therefore knows that organization's own `webhook_secret` in a multi-org Shipit deployment) can forge a validly-signed webhook whose `repository.full_name` points at a completely different, victim organization's repository.

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configuration (see `docs/setup.md` "Using Multiple GitHub Applications", and `test/dummy/config/secrets_double_github_app.yml`), each with its own `webhook_secret` [1](#0-0) .

`WebhooksController#verify_signature` determines *which* app's secret to verify against purely from the attacker-controlled JSON body:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The base `Handler` class, used by `PushHandler`, `StatusHandler` (via `Commit.where(sha:)` — no direct repo scoping, but other handlers), `CheckSuiteHandler`, and the `PullRequest::*` handlers, resolves the target `Repository`/`Stack` from a **different** field of the *same* payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses `stacks` (scoped by `full_name`) to trigger `stack.sync_github` [4](#0-3) , and `CheckSuiteHandler` similarly schedules check-run refreshes on stacks resolved via `full_name` [5](#0-4) . The `PullRequest::ClosedHandler`/`EditedHandler` also resolve the target `Repository` from `params.repository.full_name` [6](#0-5) .

Nothing in `verify_signature` or in the handlers asserts that `repository.owner.login` (used to pick the signing key) equals the owner segment embedded in `repository.full_name` (used to select the record to write). GitHub's real webhook payloads always keep these consistent, but Shipit accepts and signs against arbitrary attacker-supplied JSON — the signature only proves the payload came from *someone* who knows the secret for the organization named in `owner.login`, not that the `full_name` field is trustworthy for that same organization.

This is the direct analog of the reported bug class: the field that is authenticated (`repository.owner.login` picks the verification key) is not the field that is acted upon (`repository.full_name` selects the repository/stack that gets written to) — i.e. "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker who owns/administers *any* GitHub organization that has a Shipit-connected GitHub App installed (and thus knows that org's `webhook_secret`, a normal and expected credential for that organization's own admins, not a Shipit administrator secret) can craft and send a POST directly to Shipit's public `/webhooks` endpoint with:
- `X-Hub-Signature` computed using their own org's `webhook_secret`
- `repository.owner.login` = their own org (so `verify_signature` picks their own key and passes)
- `repository.full_name` = `victim-org/victim-repo` (any repo tracked by Shipit)

This lets the attacker trigger `GithubSyncJob` for a victim's stack (`PushHandler`), force check-run refresh cycles on a victim's commit (`CheckSuiteHandler`), or manipulate `PullRequest` review-stack lifecycle records (archiving review stacks, updating PR metadata) for repositories they do not control — a cross-repository/cross-organization write triggered without any legitimate credential for the victim org. This matches the "cross-repository writes" Critical impact category defined in scope.

### Likelihood Explanation
This requires the Shipit installation to be configured with multiple GitHub organizations (the documented "Using Multiple GitHub Applications" mode) where at least one organization is attacker-influenced/less trusted than others sharing the same Shipit instance — a realistic multi-tenant scenario the engine explicitly supports and documents. No privileged Shipit credentials, API tokens, or session are needed; only a webhook secret for one (any) of the configured organizations, which is routinely available to that organization's own administrators. In a single-organization deployment (the common case) this specific cross-org variant is not exploitable since there is only one key, though the underlying field-confusion (verifying on `owner.login`/`organization.login` but acting on `full_name`) remains present in the code.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization used to select the verification key (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before processing the event. Reject (422) any payload where these are inconsistent, and add tests covering multi-org deployments to ensure a webhook signed with organization A's secret cannot reference/act upon a repository under organization B.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgAttacker` and `OrgVictim`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Shipit tracks a stack for `OrgVictim/victim-repo`.
3. Attacker (who administers `OrgAttacker` and thus knows `OrgAttacker`'s `webhook_secret`) builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgAttacker_webhook_secret, raw_body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'OrgAttacker')` and successfully verifies the signature using the attacker's own known secret [7](#0-6) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('OrgVictim/victim-repo')` and calls `stack.sync_github` on the victim's stack, triggering a `GithubSyncJob` for a repository the attacker does not control [4](#0-3) [3](#0-2) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload

    end
