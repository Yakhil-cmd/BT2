### Title
Unsanitized Unicode bidi/control characters in prosaic/arbiter contract text allow visual spoofing of contract terms shown to the counterparty before signing - ([File: prosaic_contract.js])

### Summary
The GitLab advisory describes Snippets whose file content, when rendered, visually differs from its actual bytes because of unfiltered special (bidirectional-override) characters, tricking a user into executing something other than what they believe they approved. Ocore's prosaic-contract and arbiter-contract features have the same missing-sanitization pattern: the free-text `title`/`text` fields of a contract offer sent peer-to-peer are stored and displayed to the counterparty verbatim, with no check for Unicode bidirectional-override, zero-width, or other non-printable control characters, before the counterparty is asked to sign/pay into a shared address based on what they read.

### Finding Description
`prosaic_contract.createAndSend()` takes attacker-supplied `title` and `text` and stores/sends them unmodified: [1](#0-0) . On the receiving side, `wallet.js`'s `prosaic_contract_offer` handler only validates that the fields are non-empty, that addresses are valid, and that the hash and date format match — it performs no content sanitization of `title`/`text`: [2](#0-1) . The `arbiter_contract_offer` path is structurally identical: `createAndSend()` forwards attacker-controlled `title`/`text`/`amount`/`asset` fields to the peer with only a hash-based construction, no character-set restriction: [3](#0-2) .

Only the contract `title` is what gets cryptographically signed later (`objSignedMessage.signed_message != objContract.title`) — the `text` body (which typically carries the actual human-readable commercial/legal terms, amounts, and addresses) is never itself signed, only hash-matched against what the attacker sent: [4](#0-3) . Because neither field is passed through any Unicode normalization/sanitization (compare to `device.js`'s narrower stripping of `<...>` HTML tags from `device_name`, which does not address bidi/zero-width characters either): [5](#0-4) , an attacker (the contract counterparty) can embed RTL/LRO override characters (U+202A–U+202E) or zero-width joiners inside `text`/`title` so that the rendered contract in the victim's wallet UI shows different payment terms, amounts, or addresses than what is actually stored/hashed/signed. This is the same bug class as CVE-2022-0751: content is authentic per hash/signature, but its rendered appearance is deceptive.

Elsewhere in the codebase, well-formedness checks exist (`isObjectWellFormed`, `String.prototype.isWellFormed`) but they only reject lone surrogates and null bytes — they do not reject or neutralize bidirectional control characters or zero-width formatting characters: [6](#0-5) , and `validation.js` only calls this well-formedness check on the unit joint, not on device-messages like contract offers which never touch `validation.js`: [7](#0-6) .

### Impact Explanation
A malicious contract counterparty can craft a prosaic/arbiter contract offer whose displayed `text` (and, more critically for signature purposes, `title`) visually shows one set of terms (e.g., a lower payment amount, or the victim's own address as recipient) while actually differing in the underlying bytes that get hashed/signed. When the victim reviews the contract, accepts, and authorizes funding of the shared multisig address (`prosaic_contract.CHARGE_AMOUNT` / `arbiter_contract.CHARGE_AMOUNT` deposit and subsequent dispute/settlement flows), they can be induced into a financial commitment they did not intend — a form of unauthorized/tricked spending analogous to the GitLab issue where hidden command content is executed on a user's trust of what they saw. Because the arbiter/dispute-resolution flow (`arbiter_dispute_request` in wallet.js) later re-derives the hash and enforces agreement solely on the hash of `title`+`text`+`creation_date` [8](#0-7) , an arbiter resolving a dispute is equally exposed to the same rendering deception.

### Likelihood Explanation
Any device correspondent can initiate a `prosaic_contract_offer` or `arbiter_contract_offer` message toward any paired device without any special privilege — this is a standard wallet feature reachable from an unprivileged peer. Crafting bidi-override or zero-width Unicode payloads is trivial and requires no cryptographic effort, only string construction, making exploitation straightforward for any attacker willing to social-engineer a counterparty into a private p2p contract.

### Recommendation
Sanitize/normalize `title` and `text` (and related freeform fields such as `my_party_name`, `peer_party_name`, `my_contact_info`) in `prosaic_contract.js` and `arbiter_contract.js` before storage and before hash computation: strip or reject Unicode bidirectional control characters (U+202A–U+202E, U+2066–U+2069), zero-width characters (U+200B–U+200D, U+FEFF), and other non-printable characters, similar to the existing HTML-tag stripping in `device.js`. Additionally, consider signing the full `text` (not just `title`) so any hidden manipulation is cryptographically bound, and surface a warning in the UI layer when directional-override or zero-width characters are detected in contract content.

### Proof of Concept
1. Attacker (Bob) initiates a prosaic contract offer to Alice via `prosaic_contract.createAndSend()`, setting `text` to something like:
   `"Pay 100 bytes to \u202EsserddA_ecivoNyM\u202C"` — where the RLO character (U+202E) reverses the visual order of the following characters, e.g. making an address or amount rendered backwards or substituted so the displayed string looks like a legitimate small amount/known address while the actual stored string differs.
2. Alice's wallet receives `prosaic_contract_offer`, validates `body.hash === prosaic_contract.getHash(body)` (which trivially passes since Bob computed the hash over his own crafted string) — see the acceptance path at [9](#0-8)  — and stores/displays the contract text as-is.
3. Alice reviews the visually-misleading `text` in her wallet UI, believes she is agreeing to innocuous terms, and calls `respond("accepted", ...)`, subsequently funding the derived shared address per `deriveSharedAddress`/`createSharedAddressAndPostUnit` in `arbiter_contract.js` [10](#0-9) , without realizing the actual contractual terms differ from what she perceived.

function isObjectWellFormed(obj) {
	if (typeof obj !== 'object' || obj === null)
		return typeof obj === 'string' ? obj.isWellFormed() && obj.indexOf('\0') === -1 : true;

	if (Array.isArray(obj)) {
		// for-loop is faster than .every
		for (let i = 0; i < obj.length; i++) {
			if (!isObjectWellFormed(obj[i])) return false;
		}
		return true;
	}

	for (const key in obj) {
		if (Object.hasOwn(obj, key)) {
			if (!key.isWellFormed() || key.indexOf('\0') >= 0) return false;
			if (!isObjectWellFormed(obj[key])) return false;
		}
	}

	return true;
}
