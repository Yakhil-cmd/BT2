### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` writes an incoming GitHub `status` webhook to **every** `Commit` record in the database whose `sha` matches the payload, without checking that the commit belongs to the repository named in the same payload. This breaks the "organization/repository that authenticated versus the repository that is written" binding: the GitHub App/webhook signature only proves the event originates from *some* repository the app is installed on, but the code applies the write to *any* stack's commit sharing that SHA.

### Finding Description
The base `Handler` class exposes a `stacks` helper that properly scopes work to the repository named in the payload: [1](#0-0) 

Handlers like `PushHandler` and `CheckSuiteHandler` correctly use this `stacks` scope before acting: [2](#0-1) 

`StatusHandler`, however, ignores `stacks`/repository scoping entirely and looks up commits globally by `sha` alone: [3](#0-2) 

Because Git commit SHAs are content-addressed and independent of the hosting repository, an attacker who owns (or can push to) any repository whose GitHub App/webhook is registered on the same Shipit instance can reproduce a commit object with an identical SHA to one that already exists in a victim stack (e.g., by cloning a public repository's history into their own repo, or by constructing an identical commit — same tree, parents, author/committer identity and timestamps). The attacker then triggers (or fabricates via their own CI integration) a `status` webhook for that SHA from their own, legitimately-signed repository. `WebhooksController#verify_signature` only proves the payload was signed with the secret associated with the *sending* organization/repository: [4](#0-3) 

Nothing after that check re-validates that `params.sha`'s owning commit(s) belong to the same repository that was authenticated. `StatusHandler#process` therefore applies the status to any/all commits sharing that SHA, across all stacks and repositories tracked by this Shipit instance: [5](#0-4) 

That status directly feeds `Commit#create_status_from_github!` → `add_status`, which recomputes `status`/`deployable?` and can trigger continuous delivery: [6](#0-5) [7](#0-6) [8](#0-7) 

A forged "success" status for a required/blocking check can flip `deployable?` to true and, when `stack.continuous_deployment?` is enabled, schedule `ContinuousDeliveryJob`, resulting in an unauthorized deploy of a victim stack's commit that never actually passed CI.

### Impact Explanation
This crosses a repository-authorization boundary the report's bug class targets: the write target (`Commit`/`Status` of a victim stack) is never bound to the authenticated repository/organization, only to attacker-suppliable `sha`. Given a same-SHA commit, an unprivileged attacker (control of any onboarded repo) can poison CI status for a completely unrelated stack, potentially unlocking an unauthorized deploy/rollback via continuous delivery — matching the "unauthorized deploy" High-severity impact category.

### Likelihood Explanation
Exploitation requires the attacker to produce (or find) a commit with an identical SHA to one in a targeted stack from a repository they control, which is feasible for public repositories (clone/fork preserves SHAs) but not for arbitrary private target commits. This constrains likelihood to scenarios where victim repositories are public/forkable and the same content is pushed into an attacker-controlled, Shipit-onboarded repository, so it is a real but conditional cross-tenant risk rather than trivially exploitable in every deployment.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are scoped: resolve `stacks` from `payload.dig('repository', 'full_name')` and only update commits belonging to those stacks, e.g. `stacks.each { |s| s.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, mirroring the pattern already used in `Handler#stacks` and `PushHandler`/`CheckSuiteHandler`.

### Proof of Concept
1. Attacker controls `attacker-org/attacker-repo`, onboarded to the shared Shipit instance with its own legitimately configured GitHub App/webhook secret.
2. Victim stack `victim-org/victim-repo` has a pending/failing commit with SHA `deadbeef...` that gates a `continuous_deployment?`-enabled stack via a required status check.
3. Attacker reproduces an identical commit object (same tree/parents/author/committer/timestamps) with SHA `deadbeef...` inside `attacker-repo` (feasible if `victim-repo` is public and its history is cloned/re-hosted), then reports a `success` status for that SHA on `attacker-repo` via GitHub's status API.
4. GitHub sends a `status` webhook to Shipit, correctly signed for `attacker-org`.
5. `WebhooksController#verify_signature` passes (valid signature for `attacker-org`).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the victim's commit too, and calls `create_status_from_github!`, marking it `success` and potentially triggering `ContinuousDeliveryJob` for `victim-org/victim-repo` — an unauthorized deploy decision driven by a status the victim's own CI never produced.

module Shipit
  module Webhooks

      class StatusHandler < Handler

          requires :sha, String
          requires :state, String
          accepts :description, String

          accepts :created_at, String

            requires :name, String
          end

        def process
          Commit.where(sha: params.sha).each do |commit|

          end
