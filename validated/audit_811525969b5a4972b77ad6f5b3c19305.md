This confirms the multi-organization GitHub App configuration model: each GitHub organization gets its own `webhook_secret`, and `Shipit.github(organization:)` looks up the config keyed strictly by that organization name [1](#0-0) . This is the exact vulnerable binding.

### Title
Webhook signature is verified against `repository.owner.login`'s secret while handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`Shipit.github(organization:)` supports per-organization app configs with distinct `webhook_secret`s [1](#0-0) , [2](#0-1) ), `WebhooksController#verify_signature` selects which organization's secret to check the HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [3](#0-2) . Once the signature validates for that organization, the entire raw JSON payload — including a completely different `repository.full_name` — is handed unmodified to the registered handlers [4](#0-3) . Handlers such as `Handler#stacks`/`#repository_name` and `StatusHandler#process` resolve target stacks/commits purely from `payload.dig('repository', 'full_name')` or `params.sha`, with no re-check that this repository belongs to the same organization that produced the verified signature [5](#0-4) , [6](#0-5) .

### Finding Description
The trust binding that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the repository the handler acts on`

Before the attack: an attacker who administers their own GitHub organization ("OrgAttacker") has legitimately installed the Shipit GitHub App on that org and possesses/derives a valid `X-Hub-Signature` for that org's `webhook_secret` (this is normal, unprivileged self-service GitHub App installation — no Shipit credentials required).

After the attack: the attacker POSTs to `/webhooks` a JSON body whose `repository.owner.login` (or `organization.login`) is `"OrgAttacker"` — so `verify_signature` selects `Shipit.github(organization: "OrgAttacker")` and the HMAC check passes against the attacker's own secret [7](#0-6)  — while `repository.full_name` is set to a victim stack's repo, e.g. `"victim-org/victim-repo"`. Because `Handler#repository_name`/`#stacks` and `StatusHandler#process` only look at `full_name`/`sha` and never compare it against `repository_owner` used for verification [5](#0-4) , the forged event is processed as if it legitimately originated from the victim's repository.

Root cause: `verify_signature`'s scoping key (`repository.owner.login`) and the handlers' targeting key (`repository.full_name`) are two different, uncorrelated fields inside the same attacker-controlled JSON body, and only one of them is bound to the cryptographic signature check.

### Impact Explanation
Via the `status` event, `StatusHandler#process` calls `commit.create_status_from_github!(params)` for any `Commit` row matching an attacker-supplied `sha` belonging to a victim's stack [6](#0-5) . This lets an attacker who legitimately controls an unrelated GitHub organization forge a passing CI status on a victim commit. If that stack's `shipit.yml` has `ci.require` configured, a forged "success" status can satisfy the CI gate and enable an unauthorized deploy of a victim's stack — cross-repository/cross-organization write of state that gates deploys, without ever holding a Shipit session, API token, or write access to the victim repository. This meets the "unauthorized deploy" and "cross-repository writes" Critical impact bar.

### Likelihood Explanation
Likelihood is High in any Shipit deployment configured with multiple GitHub organizations (explicitly documented and supported, e.g. `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` section "Using Multiple Github Applications") [2](#0-1) . The attacker only needs their own GitHub organization onboarded to the same Shipit instance (an unprivileged, self-service action many multi-tenant Shipit setups allow), and knowledge of a target commit SHA (visible from the victim's public/private repo activity or PR).

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatching to handlers), require that `repository.owner.login` (the value used to select the verifying `webhook_secret`) matches the organization portion of `repository.full_name` used by handlers, rejecting the request with `422` otherwise. Alternatively, thread the verified `repository_owner` into each `Handler` and have `Handler#stacks`/`#repository_name` cross-check it against `payload['repository']['full_name']`'s owner before resolving stacks/commits.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgAttacker` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-org format).
2. Attacker installs the Shipit GitHub App on `OrgAttacker` (self-service) and thus knows `OrgAttacker`'s `webhook_secret`.
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgAttacker`'s `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and the signature validates [8](#0-7) .
6. `StatusHandler#process` finds the victim `Commit` by `sha` and records the forged "success" status [6](#0-5) , potentially satisfying `ci.require` and enabling deployment of the victim stack.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "signature=#{request.headers['X-Hub-Signature']}",

        "repository_owner=#{repository_owner}",
