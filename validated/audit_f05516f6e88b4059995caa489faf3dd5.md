### Title
Unauthenticated `new_shared_address` device message lets an unpaired/untrusted sender register itself as a cosigner over a shared address it does not control - ([File: wallet_defined_by_addresses.js])

### Summary
The External Report's root cause is that `CredibleAccountModule::validateUserOp()` trusts `msg.sender` to be a wallet that has actually installed the module, without verifying that the caller went through the proper `onInstall()`/authorization path, letting an arbitrary caller mutate state that should only be mutable by an authenticated, installed wallet. The analogous pattern in `ocore` is `wallet_defined_by_addresses.js::handleNewSharedAddress()`, reached via the `"new_shared_address"` device-message handler in `wallet.js`. This function validates that the *definition hashes to the claimed address* and that signer addresses match the definition's `["address", ...]` leaves, but it never verifies that the message's sender (`from_address`, derived from the paired device's pubkey) is actually one of the signers/cosigners recorded in `body.signers`, nor that the local device was ever asked to participate in creating this shared address (no corresponding `pending_shared_addresses` entry is required). Any correspondent device (or even a non-correspondent using the whitelisted-subjects loophole is not applicable here, but any paired device is enough) can push an unsolicited `new_shared_address` message and have the local wallet permanently record itself as a signing party of a multi-address wallet it never agreed to join, using the attacker's own device_address inserted into `shared_address_signing_paths`.

### Finding Description
`wallet.js` routes the `"new_shared_address"` subject straight to `walletDefinedByAddresses.handleNewSharedAddress(body, callbacks)`: [1](#0-0) 

`handleNewSharedAddress()` performs only structural checks — that the definition is a well-formed array, that it hashes to the claimed `address`, that each declared `signerInfo.address` is a valid address, and that the `signers` map is internally consistent with the leaves extracted from the definition (`extractAddressPathsFromDefinition`). It never checks that `from_address` (the identity of the device that sent this unsolicited message) corresponds to one of the `signerInfo.device_address` entries it is about to persist, nor that a `pending_shared_addresses`/`pending_shared_address_signing_paths` record exists proving that *this* device originally agreed to be part of that address's construction: [2](#0-1) 

After `determineIfIncludesMeAndRewriteDeviceAddress()` (rewrites device addresses that map to "me") and `validateAddressDefinition()` (only checks the definition is well-formed, using `Definition.validateDefinition` with an artificial `objFakeValidationState`), the call flows straight into `addNewSharedAddress()`, which unconditionally inserts the new shared address and every entry of `assocSignersByPath` — including entries pointing at the *attacker's own device_address* — into `shared_addresses` and `shared_address_signing_paths`: [3](#0-2) 

This mirrors the report's bug class exactly: a state-mutating entry point (`validateUserOp` in the report / `handleNewSharedAddress` here) is reachable by an unauthenticated/unauthorized party (any address / any paired device) and blindly trusts caller-supplied identity data (`msg.sender` / `body.signers`) to update persistent per-address bookkeeping (`moduleInitialized` / `shared_address_signing_paths`), without checking that the caller is the legitimate party that should be allowed to make that change (an installed validator wallet / an actual cosigner of the shared address who was asked to approve it).

Once accepted, `shared_address_signing_paths` is the authoritative table `wallet_defined_by_addresses.js` and related modules (`readSharedAddressCosigners`, `readAllControlAddresses`, `forwardPrivateChainsToOtherMembersOfAddresses`, `readSharedAddressPeers`, watched-address tracking) use to decide who is a legitimate cosigner/peer of a shared multi-authored address, and to decide which private-payment chains and payment forwarding should flow to which device. An attacker device can therefore inject fabricated cosigner records for an address whose definition it fully controls (it can pick any definition/pubkeys it likes, or reuse `["address", "victim_addr"]` leaves it discovers from public data), causing the target wallet to store bogus shared-address/cosigner metadata pointing at attacker-controlled device addresses.

### Impact Explanation
This corrupts a victim wallet's local, trusted table of "who is a legitimate cosigner of shared address X," which is subsequently used to:
- Decide where to forward private payment chains for that shared address (`forwardPrivateChainsToOtherMembersOfAddresses`), potentially leaking private payment details to the attacker's injected device_address.
- Determine cosigner/peer relationships used elsewhere in wallet UI/logic (`readSharedAddressCosigners`, `readAllControlAddresses`) which downstream code (e.g. signing-request routing in `wallet.js`'s `"sign"` handler `ifRemote`) trusts to decide whether a request is legitimate.
- Corrupt the local record of which addresses the wallet considers itself part of, since `shared_addresses` inserts are not idempotent-checked against the sender's authorization — an attacker can register spoofed shared addresses at will and get them permanently persisted and watched (`network.addLightWatchedAddress`), causing resource/DoS-adjacent and data-integrity problems, and set the stage for private-chain leakage to attacker-controlled devices, satisfying the "AA/wallet message-handling fund loss/freezing or unauthorized data-forwarding" impact bar analogous to the report's "unauthorized actions/fund lock."

### Likelihood Explanation
`"new_shared_address"` is one of the subjects processed for any known correspondent device without additional authorization checks in `handleMessageFromHub`, and `handleNewSharedAddress()` itself performs no sender-authorization check at all — only structural/hash validation of attacker-fully-controlled data. Any paired device (a normal, low-privilege actor in the threat model — "paired device") can trigger this by sending one message; no special timing, race, or hub/network privilege is required. This makes exploitation straightforward and reliably reachable.

### Recommendation
In `handleNewSharedAddress()` (or in `addNewSharedAddress()`), require that a corresponding, previously-created `pending_shared_addresses`/`pending_shared_address_signing_paths` record exists for the address_definition_template hash, and verify that `from_address` matches the `device_address` this device originally recorded as expecting to receive the finished address (i.e., re-use the same correlation used for `approve_new_shared_address`/`create_new_shared_address` flow) before persisting into `shared_addresses`/`shared_address_signing_paths`. Reject `new_shared_address` messages that arrive without matching prior local state, analogous to checking `moduleInitialized[msg.sender]` in the report's fix.

### Proof of Concept
1. Attacker pairs with (or is already a correspondent of) the victim device.
2. Attacker crafts an arbitrary `arrDefinition` (e.g., `["and", [["address", attacker_addr1], ["address", victim_addr]]]`) whose chash is `address`, and builds `signers` mapping signing paths to `{address: attacker_addr1, device_address: attacker_device}` and `{address: victim_addr, device_address: attacker_device}` (or any device it controls) — nothing prevents falsifying which device is claimed to control the `victim_addr` leaf since the check only verifies `signerInfo.address` structurally matches `extractAddressPathsFromDefinition`, not the true owner/device of `victim_addr`.
3. Attacker sends `{subject: "new_shared_address", body: {address, definition: arrDefinition, signers}}` via `device.sendMessageToDevice`/hub to the victim, with no prior `create_new_shared_address` handshake.
4. Victim's `handleMessageFromHub` → `handleNewSharedAddress` accepts it (all checks pass, since they only validate the attacker's self-consistent data), and `addNewSharedAddress` inserts rows into `shared_addresses` and `shared_address_signing_paths` binding the attacker's device_address as a "signer"/cosigner for this address in the victim's local database, and starts watching it — all without the victim ever approving or being asked.

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
