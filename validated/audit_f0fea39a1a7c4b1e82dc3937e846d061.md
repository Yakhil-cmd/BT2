### Title
Hookify `block` rules silently fail open on any exception during rule matching, bypassing PreToolUse blocking of dangerous commands - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The reported DODO bug is a fee-collection "security gate" that appears to succeed (a low-level call returns `success=true`) while the real underlying effect (an actual asset transfer) never occurred, letting a user bypass an enforcement mechanism the protocol relied on. The structural analog in this repository is the `hookify` plugin's `PreToolUse`/`Stop` block-rule enforcement: any exception raised anywhere inside rule loading or evaluation is swallowed and converted into a guaranteed `sys.exit(0)` / empty permission decision, i.e. the enforcement layer reports "ran successfully" while silently performing none of the blocking it was configured to do.

### Finding Description
`hookify`'s `PreToolUse` hook is the only gate standing between a configured `block` rule (e.g. "block `rm -rf`", "block writes to `.env`") and tool execution: [1](#0-0) 

Its `main()` wraps rule loading (`load_rules`) and evaluation (`RuleEngine.evaluate_rules`) in a bare `try/except Exception`, and the `finally` block unconditionally calls `sys.exit(0)` regardless of whether an exception occurred: [2](#0-1) 

The same fail-open pattern is duplicated in the `PostToolUse` and `Stop` executors: [3](#0-2) [4](#0-3) 

The only way a tool call is actually denied is if `RuleEngine.evaluate_rules` runs to completion and returns a `hookSpecificOutput.permissionDecision: "deny"` payload for a matched `action: block` rule: [5](#0-4) 

Because rule content is user-authored YAML frontmatter parsed by a hand-rolled parser (`extract_frontmatter`) rather than a real YAML library, and regex patterns from that frontmatter are compiled with `re.compile()` (`compile_regex`), any malformed rule file, encoding issue, unusual frontmatter shape, or a pathological/`re.error`-raising pattern that escapes the narrow `re.error` catch inside `_regex_match` propagates up through `evaluate_rules`, is caught by the blanket `except Exception` in `pretooluse.py`, and the script still exits `0` with no `permissionDecision` at all — silently equivalent to "no rule matched," even though a `block` rule exists and was intended to fire: [6](#0-5) [7](#0-6) 

This mirrors the root cause of M-6 precisely at the structural level: a low-level operation ("run the blocking check") returns a "successful, no-op" outcome instead of the enforcement it was meant to perform, and the caller (Claude Code's hook runner) has no way to distinguish "no rule matched" from "the rule engine crashed and skipped enforcement" — both produce exit code 0 / empty output.

### Impact Explanation
Any project relying on `hookify`'s `block` action to prevent dangerous Bash commands or sensitive file edits can have that protection silently disabled by a single malformed or adversarially-crafted rule file (or by any other unhandled exception reachable via `load_rules`/`evaluate_rules`, e.g. transcript-file races, non-string tool_input fields, or catastrophic-backtracking/`re.error` regex edge cases not covered by the narrow `except re.error`). Because the design deliberately treats "hook errored" and "hook approved" identically (`finally: sys.exit(0)`), this is a genuine fail-open condition in a local command-approval trust boundary, not merely a crash: the intended `block` protection silently vanishes for that tool call, with no user-visible signal that enforcement was skipped, allowing the previously-blocked dangerous Bash command or file write to proceed.

### Likelihood Explanation
This requires only local, unprivileged conditions already in scope for this trust boundary: an existing `.claude/hookify.*.local.md` rule file (created via the plugin's own `/hookify` command or manually) plus any of the many code paths in `config_loader.py`/`rule_engine.py` that can throw an uncaught exception (e.g. a rule's `pattern` value containing a regex the process's `re` module rejects in ways beyond `re.error`, a `transcript` field pointing at a file causing an exception type not enumerated in the specific handlers, or non-standard frontmatter shapes hitting an `AttributeError`/`TypeError` inside `Rule.from_dict`/`extract_frontmatter` that isn't one of the three enumerated exception classes in `load_rule_file`). No privilege escalation is needed — this is purely a local, deterministic code-path issue in the shipped plugin.

### Recommendation
Distinguish "no rule matched" from "rule engine failed" in `pretooluse.py` (and `posttooluse.py`/`stop.py`): on an unhandled exception during rule loading/evaluation for a `PreToolUse`/`Stop` context where `block` rules exist or could exist, fail closed (return `permissionDecision: "ask"` or surface the error to the user) rather than silently exiting 0. At minimum, tighten exception handling in `config_loader.py`/`rule_engine.py` so parsing/matching failures are exhaustively enumerated and reported distinctly from "rule engine ran cleanly and found no match," so the top-level `try/except Exception` in the hook executors is never reached for a rule that was supposed to block.

### Proof of Concept
Not independently executed (no sandbox/filesystem access in this environment), but the code path is directly traceable: create `.claude/hookify.bad.local.md` with a `block` rule whose `pattern`/`conditions` are crafted to raise an exception inside `Rule.from_dict` or `_check_condition`/`_extract_field` that is not one of the specifically-caught exception types (`IOError`, `OSError`, `PermissionError`, `ValueError`, `KeyError`, `AttributeError`, `TypeError`, `UnicodeDecodeError`, `re.error`) — for example a `conditions` list entry whose `field`/`operator` triggers a `RecursionError` or a custom exception subclass not covered by those `except` clauses inside `_regex_match`'s inner `re.compile`/`search` calls. When such an exception is raised, `RuleEngine.evaluate_rules` (called from `pretooluse.py` line 56) propagates it to the outer `try/except Exception` at lines 37–66, which prints a generic `systemMessage` and — via the `finally: sys.exit(0)` at line 70 — exits with success and no `permissionDecision`, so the tool call the `block` rule targeted proceeds unimpeded [1](#0-0) .

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content
```
