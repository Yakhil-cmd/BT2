### Title
Signature verification is scoped to the attacker-supplied `repository.owner.login`, while `StatusHandler` writes commit statuses looked up **globally by SHA** with no repository check, letting an unsigned/mis-signed webhook inject a fake CI status onto commits belonging to a completely different, secret-protected organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the HMAC signature against using an **unverified** field of the payload itself (`repository.owner.login`), before the signature has been checked. `StatusHandler`, however, never uses that organization or even the `repository.full_name` to scope its write - it looks up commits solely by `sha` across the entire database (`Commit.where(sha: params.sha)`), and calls `commit.create_status_from_github!(params)` on whatever matches. This breaks the binding "organization whose secret authenticated the request" == "repository (commit) that gets written."

### Finding Description
1. `verify_signature` derives the org used to pick the webhook secret purely from the JSON body, prior to any cryptographic check: [1](#0-0) [2](#0-1) 

2. `verify_webhook_signature` treats a blank `webhook_secret` as automatically verified: [3](#0-2) 

3. Per-organization `webhook_secret` is explicitly documented as optional, and multi-tenant configurations (multiple GitHub orgs, each with their own `webhook_secret`) are a first-class, supported configuration: [4](#0-3) [5](#0-4) 

4. Once past `verify_signature`, `Webhooks.for_event(event)` dispatches the same raw, attacker-controlled `params` hash to the relevant handler: [6](#0-5) 

5. `StatusHandler` looks up the target `Commit` purely by `sha`, with **no scoping to `repository.full_name` or the organization the signature was verified against**, unlike other handlers (e.g. `PushHandler`) which resolve `stacks` through `Repository.from_github_repo_name(repository_name)`: [7](#0-6) [8](#0-7) [9](#0-8) 

**Equality broken:** `organization whose webhook_secret authenticated the request` should equal `organization/repository whose commit status gets written`. Because (a) the org used for signature verification is selected from an unverified field and can be a different, secret-less org, and (b) `StatusHandler`'s write path ignores repository/organization entirely and matches purely on `sha`, an attacker who controls (or is a legitimate collaborator of) an org configured **without** a `webhook_secret` can forge a `status` webhook whose `repository.owner.login` names that secret-less org (satisfying `verify_signature` trivially, since `return true unless webhook_secret`), but whose `sha` field matches a commit belonging to a totally unrelated stack/repository under a **different, secret-protected** organization. `StatusHandler` will happily create/update a GitHub status for that unrelated commit.

### Impact Explanation
Commit statuses can gate deploy eligibility (`Commit#deployable?`/CI requirement checks configured in `shipit.yml`'s `ci.require`). An attacker able to author a `status` webhook body for an org that happens to have no `webhook_secret` configured can inject arbitrary "success" statuses onto commits of a different repository/organization, potentially satisfying CI gating for that other repository and enabling an unauthorized deploy of a repo the attacker has no authenticated relationship to - i.e. a cross-repository write with no relevant credential boundary enforced. This matches the report's core theme: a verification/authorization gate that can be trivially escaped (0-liquidity Uniswap position bypassing liquidation) has a structural analog here: an org-scoped signature check that is bypassable per-org, feeding into a data-write path (`StatusHandler`) that ignores the org/repo scope altogether.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment with more than one GitHub App/organization configured (a documented, supported configuration), (2) at least one configured organization left without a `webhook_secret` (explicitly optional per setup docs), and (3) the attacker being able to deliver an HTTP POST to `/webhooks` with a crafted JSON body (no GitHub-side privileges needed for the target repo - only knowledge of a target commit `sha`, which is often public). No signature-forging, no stolen secrets, and no `ApiClient`/session/GitHub write access to the *target* repository are required, only the ability to send a request to the public `/webhooks` endpoint claiming to originate from the secret-less org.

### Recommendation
- Scope every handler's write path (especially `StatusHandler`) by the verified organization/repository, not merely by `sha`; join through `Repository`/`Stack` the same way `PushHandler` does via `repository.full_name`, and reject if the resolved repository's owning organization does not match the organization whose `webhook_secret` verified the request.
- Do not allow signature verification to succeed unconditionally when `webhook_secret` is blank in a multi-organization setup; require every configured organization to set a `webhook_secret`, or at minimum tie the "verified" org identity into all downstream handler lookups so a secret-less org's requests cannot affect another org's data.

### Proof of Concept
1. Deploy Shipit with two GitHub orgs configured: `OrgA` (has `webhook_secret: nil`) and `OrgB` (has a real `webhook_secret` and owns `OrgB/target-repo`, tracked as a Shipit stack with a commit `abc123` that requires a passing CI status before deploy).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/target-repo"},
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`; since `OrgA.webhook_secret` is nil, `verify_webhook_signature` returns `true` unconditionally - request passes. [10](#0-9) 
4. `StatusHandler#process` runs `Commit.where(sha: "abc123").each { |commit| commit.create_status_from_github!(params) }`, finding and updating the status of the `OrgB/target-repo` commit, even though the request was never validated with `OrgB`'s secret. [7](#0-6) 
5. The forged "success" status can satisfy `ci.require` checks for `OrgB`'s stack, potentially unblocking an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
