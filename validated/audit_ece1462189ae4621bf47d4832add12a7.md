### Title
Unrestricted pool/token addresses in swap routes let attacker code run under the caller's authorization and drain the caller's wallet — (File: contracts/controller/src/strategies/swap.rs)

### Summary
Analog of CVE-2022-39383 (blind SSRF: "the request address of the warehouse is not restricted"): the controller's strategy entrypoints (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) forward a caller-supplied `StrategySwap` payload to the swap aggregator, which invokes whatever `pool`/`token` contract addresses the payload names. Neither the controller nor the router keeps an allowlist of hop destinations, so an attacker who supplies the route places arbitrary third-party code on the call stack beneath the victim's `require_auth`, and a `token.transfer(victim, attacker, x)` executed there joins the victim's authorization tree. This is documented behavior in `docs/explanation/threat-model.md` and proven by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` reads the router from storage, authorizes exactly one input-token transfer to it (`authorize_transfer_as_current`, line 34), and calls `router.execute_strategy(&controller, &amount_in, swap)` with the unvalidated `swap` bytes (line 37). The aggregator's `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs:34-40`) invokes `hop.pool`, an address taken verbatim from the payload's asset registry; venue adapters such as `comet::swap` call `env.invoke_contract(&ctx.hop.pool, …)` (`contracts/swap-aggregator/src/venues/comet.rs:30-34`) with no venue allowlist. The threat model states this explicitly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount" (`docs/explanation/threat-model.md:154-165`). The harness test deploys a `RogueHopPool` whose `swap` calls `token::Client::transfer(victim, attacker, WALLET_BALANCE)`, records it as a child of Alice's `swap_collateral` authorization, and shows her full balance of an unlisted token moving to the attacker while the swap itself settles "fairly" and passes all risk gates (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-72, 195-227`).

### Impact Explanation
Theft of user funds exceeding the routed amount: any token in the victim's wallet can be transferred to the attacker as a signed child of the victim's own strategy authorization. The protocol's measured-delta checks, `total_min_out`, and post-swap health gates all pass because the theft is orthogonal to the swap accounting.

### Likelihood Explanation
An unprivileged attacker only needs to originate the route a victim executes (routes are built off-chain and passed as `swap_xdr`). The theft succeeds when the victim's client signs the recorded authorization tree without inspecting children — the protocol places the burden entirely on the client ("A client must decode the route it signs and refuse an authorization tree with any other child"), and the same exposure exists on the direct `execute_strategy` path for every swap user. Medium likelihood, bounded by victim signing rather than by any on-chain control.

### Recommendation
Enforce an allowlist of venue pool addresses (per venue, governance-managed) inside `dispatch_hop`, or constrain hop targets to addresses registered in the aggregator's asset/venue registry, so payload bytes cannot name arbitrary contracts. Short of that, the controller could require the caller-supplied route to resolve only to pools attested by a venue registry, and clients/wallets should be shipped a route decoder that rejects authorization trees with children other than the single input transfer.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC: `RogueHopPool::swap` performs `token.transfer(alice, attacker, WALLET_BALANCE)` during `swap_collateral`, simulation records the transfer as a child of Alice's root auth entry, and the assertions show `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while Alice still receives the fair ETH output and the position stays healthy.
