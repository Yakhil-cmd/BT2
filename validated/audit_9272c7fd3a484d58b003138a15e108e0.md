Confirmed: there is no persistent, contract-level map in `pox-5.clar` tracking Bitcoin outpoints that have already been credited toward a bond. The only de-duplication is the `seen-outpoints` accumulator inside `validate-l1-lockup`, which is local to a single `verify-l1-lockups` fold call.

### Title
L1 lockup proof re-use across multiple bond registrations lets a staker double-count locked-BTC sats without an on-chain outpoint registry - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` accepts a list of Bitcoin timelock outputs (`btc-lockup`) as proof of an L1 BTC lock and sums their `amount` into `sats-total`, which is then credited into `protocol-bonds-total-staked` (per bond-index totals used for reward-per-share accounting) and into the staker's `protocol-bond-memberships` entry. The only anti-replay check, `seen-outpoints` in `validate-l1-lockup`, is a temporary list built and discarded within a single call's `fold`. There is no persistent map recording which Bitcoin outpoints have already been consumed by a prior `register-for-bond` call, unlike the persistent MAXMEM-style register in the zkEVM analog whose bound check was scoped to a single opcode class and never durably enforced across the full execution.

### Finding Description
`verify-l1-lockups` (<cite repo="Ellentat/stacks-core--022" path="stackslib/src/chainstate/stacks/boot/pox-5.clar" start="1981-2019" end="2019" />) folds `validate-l1-lockup` over the provided outputs, and `validate-l1-lockup` builds a `seen-outpoints` list to reject duplicates *within the same call* (<cite repo="Ellentat/stacks-core--022" path="stackslib/src/chainstate/stacks/boot/pox-5.clar" start="2072-2088" end="2088" />). This list is not persisted anywhere — it lives only in the fold accumulator and vanishes when the transaction returns.

`register-for-bond` uses the resulting `sats-total` to update global, additive state:
<cite repo="Ellentat/stacks-core--022" path="stackslib/src/chainstate/stacks/boot/pox-5.clar" start="786-801" end="801" />
```
(map-set protocol-bonds-total-staked bond-index
    (+ current-total-staked sats-total))
(try! (add-staker-to-bond-cycles tx-sender signer bond-index first-reward-cycle
    BOND_LENGTH_CYCLES sats-total))
```
Because the underlying L1 UTXO itself is never marked as consumed on the Stacks side (only the *staker identity* is bound into the timelock script via `construct-lockup-output-script`, not the specific bond-index or a one-time nonce), the same staker can present the identical Bitcoin outpoint/proof again in a later, non-overlapping `register-for-bond` call for a different bond index and have `sats-total` credited again into that new bond's `protocol-bonds-total-staked` and per-cycle share maps, while the original bond's already-finalized `protocol-bonds-total-staked` for its (ended) term is never decremented (this is by design for ended bonds, per the code comment at <cite repo="Ellentat/stacks-core--022" path="stackslib/src/chainstate/stacks/boot/pox-5.clar" start="796-801" end="801" />). The staker's real BTC lock never grew, yet the shares recorded against sBTC-reward-bearing state for the *new* bond are backed by nothing beyond a reused proof of a single, already-once-credited BTC lock.

This is the same bug class as the MAXMEM report: a value used to gate/limit state (the "already used" check) is enforced only transiently/locally (per-opcode / per-call) rather than being a durable, global invariant, so the persisted downstream accounting (MAXMEM register / `protocol-bonds-total-staked`) can be pushed into a state the intended check was supposed to prevent.

### Impact Explanation
`protocol-bonds-total-staked` and the per-cycle bond share maps (`total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle` with `bond-index`) feed directly into reward-per-token computation via `settle-rewards` / `get-rewards-per-token-for-cycle` (<cite repo="Ellentat/stacks-core--022" path="stackslib/src/chainstate/stacks/boot/pox-5.clar" start="2530-2573" end="2573" />). Inflating a bond's recorded share total with sats that were never re-locked breaks the equality between "sBTC actually locked backing a bond" and "shares entitled to sBTC rewards for that bond," letting the double-registering staker capture a share of sBTC reward distribution disproportionate to (or entirely unbacked by) BTC collateral — i.e., double-counting a commitment for reward purposes. Depending on relative pool sizes this can also dilute/temporarily freeze the correctly-earned rewards of honest co-signers in the same bond, since `rewards-per-token` is computed against an inflated total share denominator.

### Likelihood Explanation
Exploitation requires only that the staker already possesses a valid, previously-used L1 lockup proof (their own UTXO, timelock script, Merkle proof, and header) and can satisfy the normal non-overlap/rollover-window gates (`bond-overlaps-new-position?`, `verify-bond-rollover-window`) to register for a second, later, non-overlapping bond-index. Because the script binds only the staker's principal — not the specific bond-index or a per-registration nonce — nothing else in the proof format prevents resubmission. No signer, admin, or oracle key is needed; this is reachable by any unprivileged registered/allowlisted staker.

### Recommendation
Persist consumed L1 outpoints in a durable map (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`), checked and set inside `validate-l1-lockup`/`verify-l1-lockups` across all calls and all stakers/bonds, not just within a single call's fold accumulator. Alternatively, bind the timelock script itself to the specific `bond-index` (or a monotonically increasing per-staker registration nonce) so a given L1 lock can only ever satisfy one bond registration.

### Proof of Concept
1. Staker Alice locks BTC in a P2WSH output matching `construct-lockup-output-script(alice, unlock_height, staker_bytes, early_unlock_bytes)`.
2. Alice calls `register-for-bond(bondIndexA, signerA, amountUstx, ok({outputs:[thatOutput], ...}), none)`. `sats-total` is credited to `protocol-bonds-total-staked[bondIndexA]` and Alice's bond-cycle shares for bond A's 12-cycle term.
3. Once bond A's term is over (or the rollover window opens per `verify-bond-rollover-window`), Alice calls `register-for-bond(bondIndexB, signerB, amountUstx, ok({outputs:[the SAME output], ...}), none)` for a later, non-overlapping `bondIndexB`.
4. `verify-l1-lockups`/`validate-l1-lockup` re-validate the same Bitcoin proof successfully (no persistent replay check), crediting `sats-total` again into `protocol-bonds-total-staked[bondIndexB]` and bond B's per-cycle shares — from a single BTC lock that was never re-created or re-proven on-chain a second time.
