### Title
Cross-organization team-membership forgery via `membership` webhooks bypasses `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that a webhook was signed with the secret belonging to *some* organization configured in this Shipit instance (the organization named in the payload). It never proves that the GitHub object the payload subsequently mutates actually belongs to that organization. `MembershipHandler` uses this insufficiently-scoped trust to look up/create a `Team` purely by the global GitHub `team.id`, and then adds/removes members on it — letting an operator of *any* onboarded organization grant themselves membership in a `Team` that belongs to a completely different organization, including one used for `Shipit.github_teams` authorization.

### Finding Description
The equality this endpoint should preserve is:

`organization that authenticated the webhook == organization that owns the team object being written`

`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using only the organization named in the payload: [1](#0-0) 

For `membership` events (no `repository` key), that organization comes straight from the attacker-controlled body: [2](#0-1) 

This only proves "the payload was signed with organization X's `webhook_secret`" — a secret that X's own admin legitimately possesses and can use to sign an arbitrary raw body themselves (Shipit is explicitly multi-tenant: any onboarded organization owner can create their own GitHub App and register its `webhook_secret`, see `docs/setup.md`). Nothing binds the rest of the JSON body (in particular the `team.id`) to that same organization.

`MembershipHandler#process` then acts on that unverified `team.id`: [3](#0-2) 

`find_or_create_team!` looks the `Team` up (or creates it) keyed **only** by the global, cross-organization GitHub `github_id`: [4](#0-3) 

If a `Team` row for that `github_id` already exists (e.g. it was previously created for organization "victim-org"), `find_or_create_by!` returns the existing record untouched — the `organization:` assignment in the block is never applied — and `team.add_member(member)` is executed on it regardless of who signed the request: [5](#0-4) 

This local `Team`/`Membership` state is exactly what gates access to the whole application: `User#authorized?` checks membership against `Shipit.github_teams` purely from this database table, never re-verifying against GitHub itself at request time: [6](#0-5) 

So an attacker who legitimately administers **any** organization configured in this Shipit instance (attacker-org) can:
1. Discover the numeric `github_id` of the victim organization's authorization team (team IDs are plain sequential integers, visible via GitHub's public/team API or from prior webhook logs).
2. Craft a `membership` "added" JSON payload with `organization.login = "attacker-org"`, `team.id = <victim team's github_id>`, and `member.login = "attacker-account"`.
3. Sign it themselves with attacker-org's own known `webhook_secret` and POST it directly to `/webhooks` (a public, unauthenticated `ActionController::Base` endpoint that only checks the HMAC and never checks whether the actor is a member of the referenced team/org).
4. `verify_signature` accepts it (it correctly matches attacker-org's secret), and `MembershipHandler` grants "attacker-account" membership in the victim organization's authorization team inside Shipit's database — without ever touching the victim's real GitHub team.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization: an attacker with no relationship to the victim organization or team obtains full authenticated access to the target Shipit instance (deploys, rollbacks, task streams, etc. gated behind `current_user.authorized?`). This matches the explicitly accepted High-impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires only that the attacker legitimately controls or can register one organization/GitHub App in a multi-tenant Shipit deployment (the documented, supported setup path in `docs/setup.md`) — no access to the victim org, no Shipit session, and no privileged Shipit credentials are needed. GitHub team IDs are not secret. This makes the attack realistically reachable wherever Shipit is used to serve more than one organization.

### Recommendation
Scope every write performed by webhook handlers to the organization that authenticated the request, not just to a globally-unique GitHub object id:
- In `MembershipHandler#find_or_create_team!`, require `github_id: params.team.id, organization: params.organization.login` (or otherwise reject/log when an existing `Team`'s `organization` doesn't match `params.organization.login`) instead of finding purely by `github_id`.
- More generally, have `WebhooksController#verify_signature` assert that every organization-scoped identifier referenced in the payload (`team.organization`, `repository.owner.login`, etc.) is consistent with the organization whose secret validated the signature, rejecting mismatches instead of silently trusting embedded fields.

### Proof of Concept
1. Shipit instance is configured with two organizations, `attacker-org` (attacker is admin, knows its `webhook_secret`) and `victim-org` (target, uses `Shipit.github_teams` for authorization; its authorization team already exists in Shipit's `Team` table with `github_id = 999`).
2. Attacker builds the raw JSON body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-account"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, body)>` themselves and POSTs to `<shipit-host>/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` passes because it only checks the signature against `attacker-org`'s secret.
5. `MembershipHandler#find_or_create_team!` finds the existing `Team` with `github_id: 999` (victim-org's authorization team) and adds `attacker-account` to it via `team.add_member(member)`.
6. `attacker-account` logs into Shipit via GitHub OAuth; `User#authorized?` now returns `true` because of the forged `Membership` row, granting full access to victim-org's stacks/deploys.

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
