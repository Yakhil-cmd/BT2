### Title
CCMenuController#stack bypasses stack_id scoping by calling `Stack.from_param!` instead of `stacks.from_param!` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController#stacks` scopes stack lookups to `current_api_client.stack_id` when the API client is stack-restricted, and `#stack` is meant to always resolve through that scope via `stacks.from_param!`. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely skipping the `stacks` scope and the client's `stack_id` restriction.

### Finding Description
Binding that should hold: `stack == stacks.from_param!(params[:stack_id])` where `stacks == Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true [1](#0-0) .

In `Api::CCMenuController`, `#stack` is redefined to bypass this entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`#show` calls this overridden `#stack` to render deploy status for any stack resolved by `params[:stack_id]`, with no relation to `current_api_client.stack_id` [3](#0-2) .

The only authorization check present is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`, which only checks that `"read:stack"` is present in the client's `permissions` array — it never checks that the requested stack matches `current_api_client.stack_id` [4](#0-3) . So nothing else in the request path re-establishes the scoping that `#stacks` was supposed to enforce.

Attacker request: an attacker holding a legitimate CCMenu API token scoped to stack A (`current_api_client.stack_id == A.id`) sends `GET /api/stacks/:owner/:repo-for-stack-B/cc.xml?token=<their token>`. `authenticate_api_client` in `CCMenuController` successfully authenticates the client from `params[:token]` [5](#0-4) , `require_permission :read, :stack` passes because the client does have `read:stack` permission, and `#stack` resolves stack B directly from `Stack.from_param!`, with no scoping check against `current_api_client.stack_id`.

### Impact Explanation
An attacker with a valid but stack-restricted CCMenu token for repository/stack A can read CI/deploy status (`deploys_and_rollbacks`, ended_at, running state, etc.) for any other stack B in the system by supplying B's `stack_id` in the URL. This is an authorization-boundary violation: unauthenticated-for-that-resource read of stack/task/deploy state across tenants, repeatable against any stack in the instance simply by iterating `stack_id`/repo names. This matches "High - unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Preconditions: attacker needs any valid CCMenu token restricted to a single stack (these tokens are commonly embedded in CI dashboard tools and are not treated as highly sensitive credentials, but per this engine's design should not grant cross-stack read access). No GitHub secrets, webhook signatures, or session are needed — only a stack-scoped API token, which is exactly the least-privileged one the engine intends to hand out for CCMenu/CI-status widgets. The exploit is a single unauthenticated-relative-to-target-stack GET request with a different `stack_id` in the path, trivially repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to route through the scoped `stacks` relation rather than the raw `Stack` model:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Remove the override entirely if `BaseController#stack` already does this and no additional behavior is required, or alternatively remove `Stack.from_param!` usage here and always call `super`.

### Proof of Concept
minitest plan under `test/controllers/api/ccmenu_controller_test.rb` (existing file):
1. Create `stack_a` and `stack_b`.
2. Create an `ApiClient` with `stack_id: stack_a.id` and permission `read:stack`.
3. Assertion 1 (binding check via Mocha): stub/mock `Api::CCMenuController#stacks` (inherited from `BaseController`) and assert it is called (`expects(:stacks)` or verify `stacks.from_param!` is invoked) when resolving `#stack` — currently this expectation fails because `Stack.from_param!` is called on the class directly, not through `#stacks`.
4. Assertion 2 (impact check): `get :show, params: { token: client.authentication_token, stack_id: stack_b.to_param }` and assert `response.status == 200` and the rendered XML corresponds to `stack_b`, proving that a token scoped to `stack_a` can read `stack_b`'s deploy status — i.e., `stack != stacks.from_param!(params[:stack_id])` (the LHS resolves to `stack_b`, the RHS scoped relation would have raised `RecordNotFound` since `stack_b.id != current_api_client.stack_id`).
