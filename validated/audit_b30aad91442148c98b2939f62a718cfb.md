### Title
Unchecked ERC-721 `transferFrom` Return Value in `handleERC721Transfer` Permanently Consumes Bridge Nonce Without Delivering NFT — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` updates all bridge state (marks the request tx hash as handled, advances `lowerHandleNonce`/`upperHandleNonce`, emits `HandleValueTransfer`) **before** calling `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` without checking whether the transfer succeeded. For a non-standard ERC-721 token that returns `false` instead of reverting on failure, the nonce is permanently consumed and the NFT is never delivered to the recipient.

---

### Finding Description

In `BridgeTransferERC721.handleERC721Transfer`, the execution order is:

1. `_setHandledRequestTxHash(_requestTxHash)` — marks the source-chain tx as handled (irreversible)
2. `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — records block number
3. `_updateHandleNonce(_requestedNonce)` — advances `lowerHandleNonce` and `upperHandleNonce`
4. `emit HandleValueTransfer(...)` — emits the settlement event
5. `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` — **unchecked transfer** [1](#0-0) 

The `IERC721` interface declares `transferFrom` as a `void` function (no return value): [2](#0-1) 

Because the interface declares no return value, Solidity silently discards any value returned by the underlying token contract. A non-standard ERC-721 implementation that returns `false` on failure without reverting will cause the call to appear successful to the bridge, while the NFT ownership never changes.

By contrast, `BridgeTransferERC20` correctly uses `SafeERC20` for all token movements: [3](#0-2) [4](#0-3) 

The same unchecked pattern also appears in `requestERC721Transfer`, where `transferFrom` is called to pull the NFT from the user into the bridge before the cross-chain request is emitted: [5](#0-4) 

If this call silently fails, the `RequestValueTransferEncoded` event is still emitted and `requestNonce` is still incremented, causing the counterpart bridge to mint or release an NFT to the user on the destination chain without the user having deposited anything.

---

### Impact Explanation

**`handleERC721Transfer` path (delivery failure):**
- The bridge nonce for `_requestedNonce` is permanently consumed (`handleNoncesToBlockNums` entry written, `lowerHandleNonce` advanced).
- The NFT remains locked in the bridge contract indefinitely with no recovery path, since the nonce cannot be replayed (`_lowerHandleNonceCheck` and `_setHandledRequestTxHash` both guard against re-execution).
- The recipient loses their bridged NFT permanently. [6](#0-5) 

**`requestERC721Transfer` path (deposit bypass):**
- A user with a registered non-standard ERC-721 token can obtain a minted/released NFT on the counterpart chain without depositing the source-chain NFT.
- This constitutes an unauthorized cross-chain asset transfer affecting bridged NFT ownership.

---

### Likelihood Explanation

- The bridge accepts any ERC-721 token registered by the owner via `registerToken`. Once registered, any user can call `requestERC721Transfer` or trigger `handleERC721Transfer` via the operator relay.
- Non-standard ERC-721 tokens that return `false` instead of reverting are less common than non-standard ERC-20 tokens (e.g., USDT), but the bridge's permissive token registration model means any such token can be introduced.
- The `handleERC721Transfer` path is triggered by bridge operators processing legitimate cross-chain events; no attacker action is required beyond the token being non-standard.

---

### Recommendation

1. Replace the bare `transferFrom` call in `handleERC721Transfer` with `safeTransferFrom`, or add an ownership check after the transfer:
   ```solidity
   IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
   ```
2. In `requestERC721Transfer`, verify the bridge actually received the token after the `transferFrom` call:
   ```solidity
   IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
   require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "transfer failed");
   ```
3. Consider moving all state-mutating operations (nonce advancement, tx hash marking) to **after** the asset transfer succeeds, mirroring the checks-effects-interactions pattern.

---

### Proof of Concept

1. Deploy a non-standard ERC-721 token whose `transferFrom` returns `false` without reverting.
2. Have the bridge owner register this token via `registerToken`.
3. Call `requestERC721Transfer(_tokenAddress, attacker, tokenId, "")` from the attacker's address (no prior `approve` needed since `transferFrom` silently fails).
4. Observe that `RequestValueTransferEncoded` is emitted with `requestNonce` incremented, and the attacker's token is **not** in the bridge.
5. The counterpart bridge operators relay the event and call `handleERC721Transfer` on the counterpart bridge, minting or releasing an NFT to the attacker on the destination chain.
6. For the `handleERC721Transfer` path: operators call `handleERC721Transfer` with a valid nonce; the nonce is consumed and `HandleValueTransfer` is emitted, but `transferFrom` silently fails; the NFT remains in the bridge and the nonce is permanently spent. [7](#0-6) [8](#0-7)
