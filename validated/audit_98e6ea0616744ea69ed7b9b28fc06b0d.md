### Title
`handleERC721Transfer` Emits `HandleValueTransfer` and Permanently Consumes Bridge Nonce Before Confirming Token Delivery — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

### Summary

`BridgeTransferERC721.handleERC721Transfer` (non-mintBurn path) emits the `HandleValueTransfer` event and permanently advances the bridge nonce **before** calling `IERC721.transferFrom`. Unlike the ERC20 path which uses `SafeERC20.safeTransfer` (which reverts on silent failure), the ERC721 path calls raw `IERC721.transferFrom` which returns `void` — there is no return value to check. If the token's `transferFrom` silently fails (does not revert), the nonce is consumed, the event is emitted, and the off-chain bridge manager marks the request as handled — but the ERC721 token is never delivered to the recipient and is permanently locked in the bridge.

### Finding Description

In `handleERC721Transfer`, the execution order is:

1. `_setHandledRequestTxHash(_requestTxHash)` — marks the request tx as handled
2. `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — records nonce
3. `_updateHandleNonce(_requestedNonce)` — advances `lowerHandleNonce` / `upperHandleNonce`
4. `emit HandleValueTransfer(...)` — emits the event
5. `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` — actual transfer (no return value) [1](#0-0) 

Steps 1–4 are irreversible state mutations. Step 5 uses the raw `IERC721` interface whose `transferFrom` is declared `void`: [2](#0-1) 

There is no return value to check and no `SafeERC721` wrapper equivalent to the `SafeERC20` used in the ERC20 path: [3](#0-2) 

The ERC20 path uses `safeTransfer` (which reverts on silent failure) and `require(mint(...))` — both guarantee atomicity. The ERC721 path has no such guarantee.

The off-chain bridge manager's `ProcessHandleEvent` trusts the `HandleValueTransfer` event to mark nonces as handled: [4](#0-3) 

### Impact Explanation

If a registered ERC721 token's `transferFrom` silently fails (returns without reverting — possible with non-standard tokens or a token whose contract is self-destructed post-registration), the following permanent damage occurs:

- `_requestedNonce` is consumed and can never be replayed (`_lowerHandleNonceCheck` will reject it)
- `HandleValueTransfer` event is emitted, causing the off-chain bridge manager to call `MarkHandledNonce` and `UpdateLowerHandleNonce`, permanently closing the nonce window
- The ERC721 token remains locked in the bridge contract with no recovery path
- The cross-chain recipient receives nothing

This is an unauthorized loss of bridged ERC721 assets with no recovery mechanism. [5](#0-4) 

### Likelihood Explanation

The `onlyRegisteredToken` modifier restricts which tokens can be used, requiring owner-level registration. However:
- The owner may register a non-standard ERC721 token unknowingly (e.g., a token with a no-op `transferFrom` or one whose contract is later self-destructed)
- In Solidity 0.5.x, calling a function on a non-contract address (e.g., after self-destruct) succeeds silently
- The ERC20 path is protected by `SafeERC20`; the asymmetric lack of protection on the ERC721 path is a design gap that can be triggered by any registered token that deviates from the revert-on-failure convention

### Recommendation

Move the `emit HandleValueTransfer(...)` to **after** the transfer succeeds, and add a return-value check or a safe wrapper for ERC721 transfers:

```solidity
if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
} else {
    // Use safeTransferFrom or verify ownership changed
    IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
}

emit HandleValueTransfer(...);  // emit only after confirmed delivery
```

Alternatively, verify post-transfer that `ownerOf(_tokenId) == _to`.

### Proof of Concept

1. Owner registers a non-standard ERC721 token whose `transferFrom` emits no event and returns without reverting (e.g., a stub implementation).
2. A user bridges their ERC721 token from the child chain to the parent chain; the token is locked in the bridge.
3. Operators reach quorum and call `handleERC721Transfer` on the parent bridge.
4. Steps 1–4 execute: nonce consumed, `HandleValueTransfer` emitted.
5. Step 5 (`transferFrom`) silently fails — token stays in bridge.
6. Off-chain bridge manager receives `HandleValueTransfer`, calls `MarkHandledNonce` — nonce permanently closed.
7. User's ERC721 is permanently locked; no replay is possible. [6](#0-5) [7](#0-6)
