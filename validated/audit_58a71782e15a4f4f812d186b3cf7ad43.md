### Title
Signature verification keyed off unverified `repository.owner.login` lets an attacker forge status/push webhooks for any stack by targeting an org with no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to validate an inbound webhook's HMAC based on `repository_owner`, a field read straight out of the unauthenticated JSON body, while the handlers that actually act on the payload (create commits/statuses, sync branches, run jobs) key off a different field of the same untrusted body, `repository.full_name`. These two fields are never required to agree, breaking the binding: "the organization whose secret authenticated the request" == "the repository that is written."

### Finding Description
`verify_signature` derives the org used for HMAC verification from the payload itself, before any authentication has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the `GitHubApp` (and thus which `webhook_secret` is used) purely from that attacker-supplied `repository_owner` string: [3](#0-2) 

Crucially, `GitHubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as an automatic pass, independent of the signature header supplied: [4](#0-3) 

`webhook_secret` is documented and configured as an optional, per-organization value (shown as commented‑out/`nil` in example configs), so a multi-org Shipit deployment can legitimately have one organization with a secret configured and another without one: [5](#0-4) 

Once `verify_signature` passes (because it happened to resolve to an org lacking a `webhook_secret`), the controller dispatches the entire raw payload to the matching event handlers: [6](#0-5) 

Those handlers, however, resolve the target `Repository`/`Stack` from a *different* field of the same unauthenticated payload — `repository.full_name` — with no cross-check against `repository_owner`: [7](#0-6) 

So the "organization that authenticated" (`repository.owner.login`, checked against a possibly-secretless config) and "the repository that is written" (`repository.full_name`, used to look up `Repository.from_github_repo_name`) are two independent, attacker-controlled strings that are never bound together by the signature. An attacker who knows (or can enumerate) that the Shipit instance hosts at least one configured GitHub org without a `webhook_secret` can send a raw POST with `repository.owner.login` set to that secretless org (to pass `verify_signature` unconditionally) and `repository.full_name` set to an arbitrary victim `owner/repo` string that maps to a real, actively-deployed stack. No knowledge of any real webhook secret, GitHub identity, or repository access is required.

### Impact Explanation
Handlers such as `PushHandler` and `StatusHandler` act directly on the forged `repository.full_name`/commit data: [8](#0-7) 

`PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the target branch of the spoofed repository — an attacker-chosen SHA sync for a stack they have no access to. The `status` event handler similarly writes `Status` records for arbitrary SHAs/states on the victim stack's commits (verified by the controller test suite showing `status` fields flow straight from payload to `Commit#statuses`): [9](#0-8) 

Because Shipit's deploy gating relies on recorded commit `Status` state to decide whether a commit is "green"/deployable, an attacker able to forge arbitrary `success` statuses on arbitrary commit SHAs for a target stack — without possessing that stack's real webhook secret, without repository write access, and without any Shipit session or API token — can make an unreviewed/malicious commit appear CI-green, directly enabling an unauthorized deploy. This satisfies the Critical impact bar ("unauthorized deploy") because the security boundary crossed is exactly the one the report highlights: authentication material scoped to one entity (org) is not bound to the entity the write is scoped to (repository/stack).

### Likelihood Explanation
Any Shipit deployment that onboards more than one GitHub organization and leaves `webhook_secret` unset for even one of them (a state the shipped example configs explicitly support and show as valid) is exposed. The attacker needs no credentials at all — just knowledge (or a guess, since org names/config lists like the example ones are semi-public conventions) of one configured-but-secretless organization slug and the target victim's `owner/name`. No GitHub App private key, `webhook_secret`, `api_clients_secret`, session, or repository access is required, matching the "unprivileged attacker" scope of this analysis.

### Recommendation
Bind the field used to select the verifying `GitHubApp`/secret to the same field used by handlers to resolve the target repository (i.e., always derive both from `repository.full_name`'s owner segment, not a separately-read `repository.owner.login`/`organization.login` fallback), and reject requests when `repository_owner` (used for verification) does not match the owner segment of `repository.full_name`. Additionally, treat a missing `webhook_secret` for a configured organization as a hard misconfiguration (raise/alert) rather than silently returning `true` from `verify_webhook_signature`, since that behavior turns any secretless org into a permanent, blanket bypass for the whole instance.

### Proof of Concept
1. Assume the deployment's `secrets.github` has two orgs configured: `orgA` (no `webhook_secret` set, e.g. as in `config/secrets.development.shopify.yml`) and `victim-org` (has a real, secret-protected repo/stack in Shipit, e.g. `victim-org/victim-repo`).
2. POST directly to `/webhooks` (no valid signature needed) with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "victim-org/victim-repo" },
  "sha": "<attacker-chosen-sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "context": "ci/fake",
  "created_at": "2026-09-01T00:00:00Z"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/garbage) `X-Hub-Signature` header.
4. `WebhooksController#create` dispatches to `StatusHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and records a fabricated `success` status against `<attacker-chosen-sha>` on the victim stack, with zero authentication tied to `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
