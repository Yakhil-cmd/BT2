### Title
Hookify PreToolUse/PostToolUse `block` rules fail open on any evaluation error, silently disabling the configured security gate - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The `hookify` plugin lets a user define rules with `action: block` in `.claude/hookify.*.local.md` files intended to prevent dangerous Bash commands or file edits (e.g. `rm -rf`, writes to `.env`/credentials files) from executing. The hook scripts that enforce these rules (`pretooluse.py`, `posttooluse.py`, `stop.py`) wrap all evaluation logic in a broad `try/except Exception` and use a `finally: sys.exit(0)`, meaning that if rule loading or evaluation throws for any reason, the hook always exits with code `0` (the "allow" signal to Claude Code), never returning the `hookSpecificOutput.permissionDecision: "deny"` that a matching `block` rule would have produced.

### Finding Description
`RuleEngine.evaluate_rules` in `plugins/hookify/core/rule_engine.py` only returns a `permissionDecision: "deny"` when a `block`-action rule is found to match; otherwise it returns `{}` (allow) [1](#0-0) .

The `pretooluse.py` executor calls this engine inside a `try/except Exception` block, and regardless of success or failure, the `finally` clause always calls `sys.exit(0)` with the comment "ALWAYS exit 0 - never block operations due to hook errors" [2](#0-1) . The same fail-open pattern is duplicated in `posttooluse.py` [3](#0-2)  and `stop.py` [4](#0-3) .

Because `load_rules`/`load_rule_file` in `config_loader.py` already swallow file I/O and parsing errors internally (returning fewer rules rather than raising) [5](#0-4) , any *other* runtime exception during evaluation (e.g., a `ValueError`/`TypeError` in a condition operator, a bug in a custom rule the user wrote, environment issues loading `hookify.core`) is caught by the top-level `except Exception` in the hook script and converted into an "allow" result. This is the analog of the reported bug: a security-gate state (`action: block`, meant to unconditionally restrict a dangerous operation) is not actually enforced by the function invoked to apply it — the underlying `distribute`-style pass-through here is the unconditional `sys.exit(0)`.

### Impact Explanation
A rule author sets `action: block` expecting Claude Code to refuse to execute a dangerous Bash command (e.g. `rm -rf`) or edit a sensitive file (`.env`, credentials) whenever the hook is present. If the hookify evaluation path throws (malformed condition, unexpected input shape, an environment/import error not caught by the narrower except clauses upstream), the hook silently allows the operation instead of blocking it, defeating the user-configured safety control without any visible warning beyond a `systemMessage` that Claude — not the user — sees. This is a direct “security control silently bypassed under an abnormal/edge-case condition” bug, matching the SimpleShares-during-pause bug class (a state meant to prevent an action doesn't actually gate the invoked function).

### Likelihood Explanation
Moderate: the narrower exception types are already handled inside `config_loader.py`, so triggering the top-level fail-open in the hook scripts requires an evaluation-time error not anticipated by the authors (e.g., a rule condition on a field whose value isn't a string, or a future exception path in `rule_engine.py`/`RuleEngine._rule_matches` not shown here). This is lower likelihood than a always-reachable bypass, but it is a real, currently-shipped code path with an explicit "never block operations due to hook errors" design decision, so any bug or unexpected input in the block-rule evaluation logic converts a "deny" into "allow."

### Recommendation
Change the fail-safe direction for `action: block` rules: on an unexpected exception during evaluation, the hook should default to `ask`/`deny` (or at minimum surface a loud, user-visible warning) rather than unconditionally exiting `0`. If failing open is intentional for warn-only rules (to avoid blocking all tool use on a hook bug), the code should at least distinguish "no rules loaded/matched" from "evaluation crashed while blocking rules might apply," and prefer denying/asking in the latter case.

### Proof of Concept
1. Configure `.claude/hookify.block-rm.local.md` with `enabled: true`, `event: bash`, `action: block`, `pattern: rm\s+-rf`.
2. Trigger a code path in `RuleEngine.evaluate_rules`/`_rule_matches` that raises (e.g., by adding a condition whose `field` value in `tool_input` is a non-string type that a regex/`contains` operator can't handle, causing a `TypeError` not pre-validated by `config_loader.py`).
3. Observe `pretooluse.py`'s outer `except Exception` catches it, prints a `systemMessage`, and the `finally: sys.exit(0)` allows the `rm -rf` Bash command to execute — the configured `block` rule never fires.

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
