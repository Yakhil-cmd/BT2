### Title
Race Condition in One-Time Pairing Secret Consumption Allows Multiple Devices to Redeem the Same Secret - (File: `device.js`)

### Summary
The reported bug exploits a timing window where a security check ("PIN window") can be crossed to bypass an intended one-time authorization gate. The ocore equivalent is `handlePairingMessage()` in `device.js`, which validates a one-time-use `pairing_secret` and only invalidates it (deletes it) *after* already granting the requester correspondent status. Because the check-then-invalidate sequence is not atomic and not protected by any mutex/lock, two (or more) pairing requests arriving concurrently with the same one-time `pairing_secret` can both pass validation before either delete completes, letting multiple unauthorized devices pair using a secret meant for a single recipient.

### Finding Description
`handlePairingMessage` first queries whether the `pairing_secret` exists and is unexpired: [1](#0-0) 
then unconditionally inserts the sender as a confirmed correspondent, and only afterwards deletes the one-time secret (skipped entirely for permanent secrets): [2](#0-1) 

There is no `mutex.lock(...)` around this SELECT → INSERT → DELETE sequence (unlike, e.g., `validation.js`'s `mutex.lock(arrAuthorAddresses, ...)` pattern used elsewhere in the codebase for author-scoped serialization): [3](#0-2) 

Since a one-time pairing secret is expected to authorize exactly one correspondent to attach itself to the recipient device (and, in multi-device wallet flows, to become a cosigner via `handleOfferToCreateNewWallet`/`createWallet`), the missing atomicity is the direct analog of "crossing the PIN window": the intended single-use authorization gate can be crossed by a second, concurrent request before the first request's cleanup (`DELETE FROM pairing_secrets`) takes effect.

This is reachable by an unprivileged paired-device peer: anyone who obtains or intercepts the pairing QR/link (which is routinely transmitted over less-trusted channels — screenshots, shared links, chat messages) can race a legitimate pairing attempt, or simply fire multiple pairing messages back-to-back to the target device/hub before the first `DELETE` commits.

### Impact Explanation
A successful race lets an unauthorized device become a confirmed correspondent of the victim device using a secret intended for a single recipient. In the multisig/shared-wallet flow (`wallet_defined_by_keys.js`), correspondent status combined with the attacker's own device address knowledge can be leveraged to insert itself as an additional participant in wallet negotiation messages (`create_new_wallet`, `my_xpubkey`), since `handleOfferToCreateNewWallet` trusts `other_cosigners` device addresses supplied in the message body: [4](#0-3) 
An attacker device racing into correspondent status during shared-address/wallet setup can potentially insert itself as an unintended cosigner or observer in the wallet-approval handshake, leading to either freezing of the intended multisig wallet setup (denial of legitimate cosigner) or, depending on how the client UI reacts to the extra/duplicate correspondent, confusion that can be leveraged for social-engineering-free unauthorized participation in a shared address definition. This is a Medium severity issue: it breaks a stated security invariant (single-use pairing secret) via a concrete, reproducible race rather than any cryptographic break.

### Likelihood Explanation
The precondition is only knowledge of the (shared, therefore inherently more exposed) `pairing_secret`/QR code and the ability to send two device-pairing messages to the hub within the small window between the SELECT and the DELETE — well within reach of a scripted attacker with a fast connection, no privileged access, and no knowledge beyond what is included in the pairing QR/link itself.

### Recommendation
Make secret consumption atomic: perform the read-and-invalidate operation in a single non-repeatable query (e.g., `DELETE FROM pairing_secrets WHERE pairing_secret=? AND is_permanent=0 RETURNING *` or `UPDATE ... SET used=1 WHERE pairing_secret=? AND used=0`, checking affected row count) and only proceed to add the correspondent if the delete/claim actually affected a row. Alternatively, wrap the SELECT/INSERT/DELETE in `mutex.lock(['pairing_secret-' + pairing_secret], ...)` so concurrent pairing attempts for the same secret are serialized and only the first succeeds.

### Proof of Concept
1. Device A calls `startWaitingForPairing()`, obtaining a one-time `pairing_secret` intended for Device B, and shares it via QR/link. [5](#0-4) 
2. An attacker who has observed/intercepted the same secret sends a `pairing` message to Device A's hub with `{pairing_secret, device_name}` concurrently with (or immediately preceding) Device B's legitimate pairing message.
3. Both messages reach `handlePairingMessage` and execute the `SELECT ... FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date > now()` check before either has executed the corresponding `DELETE FROM pairing_secrets WHERE pairing_secret=?`. [1](#0-0) 
4. Both the attacker and Device B get inserted into `correspondent_devices` as confirmed correspondents of Device A, even though the pairing secret was intended to authorize only one recipient.
