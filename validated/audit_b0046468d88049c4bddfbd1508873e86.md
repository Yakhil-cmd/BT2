### Title
Tokens held by the controller have no withdrawal path — undeclared `flash_position` proceeds and direct transfers are permanently frozen - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The external report describes the class "a balance is credited/held by a contract but the contract exposes no function to pay it out" (the fulfillable's `beneficiaryWithdraw` exists but the manager never exposes a call that reaches it). In XOXNO Lending, the controller routinely takes token custody — it pulls liquidation repayments, flash-loan and strategy proceeds, and `flash_position` callback receipts into its own address and later forwards or refunds only the portions it explicitly accounts for. Any positive token balance that falls outside those measured flows (a callback asset the caller did not list as a refund asset, a token sent directly to the controller address, a residual left by an inexact-delivery token after a snapshot) has no withdrawal path at all: there is no sweep/rescue endpoint on the controller, so the tokens are locked in the contract forever.

### Finding Description
During `flash_position`, the controller snapshots its balance per declared refund asset and returns "only positive balance changes above pre-callback balances" to the caller; undeclared callback assets "receive neither credit nor refunds" and "there is no controller sweep endpoint" [1](#0-0) . The refund mechanism itself is `refund_controller_balance_delta`, which only pays out the delta measured against a snapshot taken inside the strategy call [2](#0-1)  — anything already sitting on the controller's balance before that snapshot, or delivered for an asset that was never snapshotted, is untouched and unrecoverable. The same applies to every custody-taking flow: `repay_debt_from_controller` snapshots the controller balance after funding and refunds only the post-repay delta [2](#0-1) , and `claim_revenue_for_asset` measures and forwards only what the pool's `claim_revenue` call delivered [3](#0-2) . Unlike the pool, which books donations as untracked excess, the controller has no bookkeeping for stray balances and no function — privileged or not — that can transfer an arbitrary token balance out.

### Impact Explanation
Permanent freezing of user funds. Any tokens that end up on the controller's address outside a measured delta — e.g., a `flash_position` callback that mints/sends an asset the caller forgot (or was unable) to declare as a refund asset, or a direct token transfer to the controller — can never be withdrawn by anyone. There is no code path that transfers an arbitrary controller-held token balance to any recipient.

### Likelihood Explanation
Low-to-moderate: it requires a user or callback to send tokens to the controller outside the measured flows, but the protocol design makes this easy to do accidentally — `flash_position` callbacks routinely deliver multiple tokens, and only declared refund assets are returned [1](#0-0) . Medium severity.

### Recommendation
Add a rescue/sweep entrypoint to the controller (e.g., `sweep(token, to, amount)` restricted to the owner, or better, permissionless but paying only balances provably unattributed) that can transfer out token balances not tied to any tracked position. At minimum, document and enforce that every callback-delivered token must be declared, and consider refunding undeclared positive deltas by default.

### Proof of Concept
1. An unprivileged user calls `flash_position` with their own Wasm receiver.
2. Inside the callback, the receiver acquires an extra token `X` (e.g., from a swap) and transfers it to the controller without listing `X` in `refund_assets` — or lists it but the delta is non-positive relative to the pre-callback snapshot.
3. The call succeeds; token `X` remains on the controller's balance. Inspecting the controller's public entrypoints shows no function capable of moving `X` out: refunds only fire for declared assets' positive deltas [1](#0-0) , and `claim_revenue` only forwards the measured pool receipt to the accumulator [3](#0-2) .
4. Equivalently, anyone can `token.transfer(user, controller_addr, amount)` directly; the controller has no recovery path, so the funds are frozen permanently.
