### Title
CCMenuController#stack bypasses ApiClient stack scoping via `Stack.from_param!` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stack` enforces per-token stack scoping by resolving the requested stack through `#stacks` (`Stack.where(id: current_api_client.stack_id)`) before calling `from_param!`. `Shipit::Api::CCMenuController` overrides `#stack` and instead calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, so a stack-restricted `ApiClient` token can read the CCMenu status of any stack, not just the one it was issued for.

### Finding Description
The intended binding is: `resolved_stack.id ∈ {current_api_client.stack_id}` whenever `current_api_client.stack_id?` is true. `BaseController` implements this via: [1](#0-0) 

`stacks` restricts the relation to the token's own `stack_id`, and `stack` resolves `params[:stack_id]` against that restricted relation, so `from_param!` raises `ActiveRecord::RecordNotFound` for any stack outside the token's scope.

`CCMenuController` inherits from `BaseController` but redefines `#stack` to bypass this scoping entirely: [2](#0-1) 

Here `Stack.from_param!` is called on the full `Stack` model (class method), not on the token-scoped `stacks` relation. `#show` then renders CCMenu deploy/status data for whatever stack was resolved: [3](#0-2) 

`require_permission :read, :stack` only checks that the token's `permissions` array contains the string `read:stack` via `ApiClient#check_permissions!`; it never checks which stack is being accessed: [4](#0-3) 

So a token created with `stack_id` set to stack A and permission `read:stack` (a properly-scoped, legitimate low-privilege token — e.g. one handed out for a CI dashboard/CCMenu integration for one team) can request `GET /:owner/:repo/:env/ccmenu.xml?stack_id=<stack-B-id>&token=<token>` (CCMenuController also swaps Basic Auth for a `params[:token]` credential, but that only changes transport, not scoping) and receive stack B's latest deploy id, timestamp and running state, even though the token was never granted `stack_id = B`.

No other guard intervenes: `authenticate_api_client` only verifies the token is valid, and no before_action re-checks `stack.id == current_api_client.stack_id`. This is exactly the divergence the question hypothesizes: every sibling controller (`Api::StacksController#stack`, etc.) correctly routes through `stacks.from_param!`, while `CCMenuController` alone calls `Stack.from_param!` unscoped.

### Impact Explanation
A stack-scoped `ApiClient` token can read deploy/task state (deploy id, completion time, running status) for any stack in the installation, not just the stack it was provisioned for. This is a tenant-isolation break across repositories/stacks sharing one Shipit instance: a token issued to team/repo A leaks operational state of team/repo B's deploys. This matches the High-severity category "unauthenticated read of stack state ... or deploy output" since the read is unauthorized for the target stack despite the token being authenticated for a different one. It is fully repeatable — the same request can be replayed against any `stack_id` in the database, and the leak applies to every stack-scoped token in the system (any legitimate consumer of a scoped CCMenu token is also an unauthorized reader of every other stack).

### Likelihood Explanation
Requires only an existing `ApiClient` record with `stack_id` set (a normal, supported configuration for scoped integrations) and the `read:stack` permission, which is the minimum expected for any CCMenu consumer. No secrets beyond the token itself are needed, and the attacker only needs to know or guess another stack's numeric id or slug (`from_param!` typically resolves by id or by `repo_owner/repo_name/environment` style param — either way it's discoverable/enumerable). Cost is a single crafted GET request; the divergence from `BaseController`'s contract is deterministic and always exploitable.

### Recommendation
Remove the `#stack` override in `Shipit::Api::CCMenuController` (or reimplement it as `stacks.from_param!(params[:stack_id])`) so it inherits/uses the token-scoped `stacks` relation exactly like `BaseController` and `Api::StacksController`. Add a regression test asserting `CCMenuController` returns 404 for a stack outside `current_api_client.stack_id`, matching the behavior of `Api::StacksController#show`.

### Proof of Concept
Minitest plan (table-driven, no live GitHub):
1. Create `stack_a` and `stack_b` (two distinct `Shipit::Stack` records).
2. Create `ApiClient` with `stack_id: stack_a.id`, `permissions: ['read:stack']`.
3. For `Api::StacksController#show`: `get api_stack_url(stack_b), params: { }` with Basic Auth using the token → assert response is `404` (via `stacks.from_param!` raising `RecordNotFound`).
4. For `Api::CCMenuController#show`: `get ccmenu-equivalent path for stack_b, params: { token: token }` → assert response is currently `200` and contains `<Project ... lastBuildStatus=...>` for `stack_b`, demonstrating the divergent (200 vs 404) outcome for the same token/stack pairing across sibling controllers.
5. Assert equality of the binding fails: `stack_b.id != current_api_client.stack_id` yet CCMenu still serves stack_b's data, proving the base scoping contract (`resolved_stack.id ∈ {current_api_client.stack_id}`) is violated only in `CCMenuController`.
