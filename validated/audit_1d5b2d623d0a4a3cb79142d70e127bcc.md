### Title
Webhook signature is validated against the organization named in an unauthenticated `repository.owner.login` field, but every default handler dispatches against a different, independently-read `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to HMAC-check the raw webhook body against by reading `repository.owner.login` (or `organization.login`) straight out of the same untrusted JSON body it is about to validate, then only compares the signature against that org's `webhook_secret`. The actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, all `PullRequest::*Handler`s, `StatusHandler`, `CheckSuiteHandler`) independently re-read `repository.full_name` from the same body to decide which `Repository`/`Stack` to act on. Nothing ties the "owner" used for signature/org selection to the "full_name" used for the actual write operation.

### Finding Description
In a multi-organization Shipit deployment (the documented pattern in `config/secrets.development.example.yml`, where each GitHub org has its own `app_id`/`webhook_secret`), each org owner is handed their own GitHub App and thus knows their own `webhook_secret` - a legitimate, unprivileged credential with respect to *other* onboarded organizations.

`verify_signature` computes the signing organization from body content: [1](#0-0) [2](#0-1) 

This only proves "the sender knows the webhook secret for whatever org is named in `repository.owner.login`" - it says nothing about `repository.full_name`, which is a sibling field in the same attacker-authored JSON body.

`create` then hands the *entire* raw JSON body to every registered handler for the event: [3](#0-2) 

Every default handler resolves its target purely from `repository.full_name`, ignoring `repository.owner.login` entirely: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the attacker crafts the entire raw body himself (this is a forged request, not a proxied GitHub delivery), he can set `repository.owner.login = "attacker-org"` (satisfies signature check, since he legitimately knows `attacker-org`'s `webhook_secret`) while setting `repository.full_name = "victim-org/victim-repo"` (used by the handler to pick the real `Stack`/`Repository`). The HMAC covers the raw bytes of the whole body, but the body's internal consistency between "owner" and "full_name" is never enforced anywhere - `verify_webhook_signature` only checks the bytes against a secret, and secret selection and target-repository selection independently trust two different JSON paths.

Binding broken (equality that should hold but doesn't):
`organization authenticated via HMAC (repository.owner.login)` ≠ `repository/stack actually written to (repository.full_name)`.

### Impact Explanation
An org owner who has been onboarded to a shared Shipit instance (and thus legitimately possesses one org's `webhook_secret`) can forge webhook deliveries that are accepted as "signed" and then act on any other onboarded organization's repositories/stacks:
- `push` event → `PushHandler` calls `stack.sync_github(expected_head_sha:)` on a victim org's stack, forcing a resync against an attacker-chosen SHA claim for a branch of a repo the attacker doesn't own.
- `pull_request` `opened`/`labeled`/etc. → `ReviewStackAdapter.find_or_create!` provisions/deploys a review stack for a victim repository the attacker doesn't control, using attacker-crafted PR/label/user metadata.
- `status`/`check_suite` → forges CI status/check results against a victim's real commits, which Shipit's deploy-safety checks may rely on to gate deploys.

This crosses an authorization boundary between organizations that is otherwise supposed to be enforced by per-org webhook secrets, enabling cross-repository writes and, via the pull-request/review-stack path, unauthorized provisioning/deploy actions against stacks the attacker's own webhook secret was never meant to authorize.

### Likelihood Explanation
Requires the target Shipit instance to be configured for multiple GitHub organizations sharing one engine instance (a documented, supported configuration), and requires the attacker to control (or have been issued) the `webhook_secret` for at least one of those onboarded orgs - a low-privilege position relative to the other orgs on the same instance. No GitHub App private key, `api_clients_secret`, or Shipit session is needed; only knowledge of one's own org's webhook secret and the ability to POST directly to `/github_webhooks` (or the mounted webhooks endpoint).

### Recommendation
Bind the two fields cryptographically/logically before dispatch:
1. Compute `repository_owner` and the handler's `repository_name` from the same verified source, and reject the request in `verify_signature`/`create` if `repository.full_name`'s owner segment does not match `repository.owner.login`/`organization.login` used to select the secret.
2. Alternatively, resolve the target `Repository` first via `full_name`, derive its actual owning organization from Shipit's own DB record (not from the payload), and use that to select the webhook secret for verification - never trust two independent fields from the same unauthenticated body for two different security decisions.
3. Add a regression test asserting a request signed with org A's secret but naming a repository owned by org B is rejected.

### Proof of Concept
1. Configure Shipit (per `config/secrets.development.example.yml`) for two organizations: `attacker-org` (attacker knows its `webhook_secret`) and `victim-org` (has a real onboarded `Stack`, e.g. `victim-org/prod-repo`).
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/prod-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker_webhook_secret, body)>` using the attacker's own known secret.
4. POST to the webhooks endpoint with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature validates successfully [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/prod-repo")` [4](#0-3)  and triggers `sync_github(expected_head_sha:)` on the victim's real stack, even though the request was only ever authenticated as belonging to `attacker-org`.
