### Title
Unchecked zero `earned_headers_commission_share` causes division-by-zero / uncaught exception in TPS-fee accounting - (File: `validation.js`, `storage.js`)

### Summary
The TPS-fee accounting logic computes a per-recipient `share = recipients[address] / 100` from the `earned_headers_commission_share` value embedded in a unit's `earned_headers_commission_recipients` field, then uses that `share` as a **denominator** (`tps_fees_balance / share`). This mirrors the Suzaku `_calculateOperatorShare()` bug class: a value that can legitimately be zero for a given input is used to divide another value without a guard, in the money/fee-accounting path that any unit-posting address can influence.

### Finding Description
In `validation.js`'s `validateTpsFee()`, the code explicitly anticipates that a recipient's share can be zero and *throws* rather than gracefully rejecting the unit: [1](#0-0) 
```
const recipients = storage.getTpsFeeRecipients(...);
for (let address in recipients) {
    const share = recipients[address] / 100;
    if (!share)
        throw Error(`invalid share for address ${address}: ${share}`);
    ...
    const tps_fee = tps_fees_balance / share + objUnit.tps_fee;
```
This is an uncaught `throw Error(...)` inside the async unit-validation pipeline rather than a `callback(err)` used everywhere else in this function for rejecting a bad unit, e.g. the surrounding rejections all use `return callback(...)`. [2](#0-1) 

The same unguarded division pattern (`tps_fees_balance / share`) appears without any zero-check at all in two other call sites that compute/report the same recipient shares:

- `storage.js` `getPaidTpsFee()`: [3](#0-2) 
- `composer.js` unit-composition logic: [4](#0-3) 

Both compute `const share = recipients[address] / 100;` and then divide by `share` with no zero-check, so if `share` is 0 the result is `Infinity`/`-Infinity`/`NaN` propagating silently into `min_tps_fee` / `paid_tps_fee` calculations, rather than crashing — creating a **discrepancy in behavior between the three code paths that all consume the same `earned_headers_commission_recipients` structure**: one throws an uncaught exception, the others silently compute `Infinity`/`NaN`.

`recipients` and their shares originate from `earned_headers_commission_recipients`, a field that any multi-authored unit (postable by an unprivileged unit poster) can set via `objUnit.earned_headers_commission_recipients`, processed through `storage.ehcr2assoc()` / `getTpsFeeRecipients()`.

### Impact Explanation
- If a unit can be crafted (or a light client/AA-triggering path can produce) a recipient with `earned_headers_commission_share = 0`, then:
  - In `validateTpsFee()`, the uncaught `throw Error` inside async validation will not be caught by the normal `callback`-based error path, causing a node-crash/unhandled-exception style denial-of-service for any node validating that unit — i.e., a unit that some/all nodes cannot process, matching the "network unable to confirm new units" and "node disagreement on validity" criteria.
  - In `getPaidTpsFee()` / `composer.js`, the same zero-share condition instead silently yields `Infinity`/`NaN` fee values with no error at all, meaning different code paths reach mutually inconsistent conclusions about the same unit's validity/fee — a consensus-relevant node-disagreement risk.
- This matches the referenced bug class exactly: a divisor derived from user/AA-controllable data that can legitimately be zero is used unguarded in a financial accounting formula, causing either permanent processing failure (crash/DoS on validation) or inconsistent computation across code paths (integrity/consensus issue), rather than a clean, deterministic rejection.

### Likelihood Explanation
`earned_headers_commission_share` is a numeric field inside `earned_headers_commission_recipients`, which is populated from unit content controllable by the unit's authors (a multi-authored unit assigning shares to co-authors/recipients). Whether the structural/basic unit-content validator elsewhere in `validation.js` rejects a literal `0` value for `earned_headers_commission_share` before reaching `validateTpsFee()`/`getPaidTpsFee()` could not be fully confirmed with the available search results, so the exact reachability of `share === 0` through normal unit posting is **not fully verified** in this investigation. However, the presence of an explicit runtime guard (`if (!share) throw Error(...)`) specifically for this value strongly indicates the developers considered a zero share reachable/possible at this stage, which is why the check exists in `validateTpsFee()` but was omitted in the two sibling call sites (`storage.js:getPaidTpsFee`, `composer.js`).

### Recommendation
- Replace the `throw Error(...)` in `validation.js`'s `validateTpsFee()` with a proper `return callback(...)` rejection so a zero-share unit is cleanly rejected rather than causing an uncaught exception during async validation.
- Add the same zero-share guard to `storage.js` `getPaidTpsFee()` and to the tps-fee computation logic in `composer.js`, ensuring all three sites treat a zero `earned_headers_commission_share` consistently (either by skipping the entry or rejecting unit composition), analogous to the "skip if total stake == 0" mitigation in Suzaku.
- Additionally confirm at the point where `earned_headers_commission_recipients` is structurally validated that `earned_headers_commission_share` is constrained to a strictly positive range (e.g., 1–100), closing off the root cause rather than only patching the division sites.

### Proof of Concept
Concrete PoC could not be constructed without confirming whether the structural unit validator permits `earned_headers_commission_share: 0` in a posted unit's `earned_headers_commission_recipients`; this requires further code review of the full `earned_headers_commission_recipients` structural-validation block in `validation.js` beyond what was retrieved in this session. Conceptually: an author posts a multi-authored unit with `earned_headers_commission_recipients: [{address: A, earned_headers_commission_share: 0}, ...]`; when this unit later becomes a headers-commission payer and `validateTpsFee()` is invoked on units earning from it, `share = 0/100 = 0` triggers the uncaught `throw Error(...)` at `validation.js:1084-1085`, while `getPaidTpsFee()`/`composer.js` computing fees for the same address instead divide by zero silently.
