### Title
RAY-denominated position value overflows `i128` during interest accrual, permanently freezing a large market before the borrow-index cap can engage - (File: common/src/rates/scaling.rs)

### Summary
The integer-overflow bug class maps directly onto XOXNO Lending's share/index accounting: `scaled_to_original` multiplies a market's total scaled supply/debt (`Ray`, 27-decimal fixed point on `i128`) by the accrual index inside every `accrue_step`. Because accrual runs before every user-facing verb, once the product `scaled_amount * index` exceeds `i128::MAX` the pool panics with `MathOverflow` on every subsequent interaction — supply, borrow, withdraw, repay, liquidate, `clean_bad_debt`, `update_indexes`. The `MAX_BORROW_INDEX_RAY` safety cap never fires because the *value* product saturates `i128` well before the *index* reaches the cap. The codebase's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the freeze end-to-end.

### Finding Description
`accrue_chunk` in `contracts/pool/src/interest.rs:39-53` calls `accrue_step` with `cache.borrowed()`/`cache.supplied()` (RAY-scaled share totals) and the current indexes. `accrue_step` internally unscales via `scaled_to_original` (`common/src/rates/scaling.rs:14-16`), i.e. `scaled.mul(env, index)` → `mul_div_half_up(scaled, index, RAY)`. The `mul_div` primitives in `common/src/math/fp_core.rs:108-143` widen the intermediate product to `I256`, but the *result* must still fit `i128`; when the RAY-valued position exceeds ~`1.7e38` the call panics with `GenericError::MathOverflow`.

The harness test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` proves it: with ~1e9 tokens of an 18-decimal asset supplied and 98% borrowed on a steep rate curve, compounding pushes the borrow index to ~170x and the next accrual panics inside `scaled_to_original` while `borrow_index < MAX_BORROW_INDEX_RAY` (asserted at lines 350-353). After that, `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW` (lines 355-356) — every verb accrues first via `global_sync`, so nothing can run. `update_indexes` itself is a permissionless entrypoint, so once the cliff is crossed any caller (or the next honest user) permanently bricks the market.

### Impact Explanation
Permanent freezing of funds plus protocol insolvency: all suppliers' principal and the borrower's collateral in that hub/spoke book become unrecoverable, liquidations cannot execute, and `clean_bad_debt`/`recapitalize` also accrue first and hit the same panic. The condition is reachable by a single unprivileged address: `supply` a whale-sized position and `borrow` near the cap, then let time pass — no privileged action, oracle manipulation, or off-chain dependency is required.

### Likelihood Explanation
Requires a very large position (on the order of 10^9 whole tokens at 18 decimals, or equivalently large RAY share totals at lower decimals) and sustained high utilization for years on a steep curve, so likelihood is low for current markets but not bounded by any cap check: `lift_caps` uses `max_cap_for_decimals`, which permits sizes that reach the cliff. Any future high-decimals, high-supply listing walks into it deterministically — the outcome depends only on market size and elapsed time, both fully attacker/user-controlled.

### Recommendation
Bound share totals so `scaled * index` can never overflow: either (a) clamp `borrow_index`/`supply_index` growth inside `accrue_step` to a cap derived from `i128::MAX / max_scaled_amount` rather than a fixed `MAX_BORROW_INDEX_RAY`, or (b) keep accrued totals below the ceiling by enforcing `require_cap_within_asset_domain`-style limits at supply/borrow time using the *worst-case index*, or (c) make `scaled_to_original` inside accrual saturate (like `mul_div_floor_saturating` already does for caps) so the market degrades instead of freezing, and socialize the shortfall explicitly.

### Proof of Concept
The repository already contains the executable PoC at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
// supply 1e9 whole tokens of an 18-decimal asset, borrow 98% of it
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// advance time until accrual panics
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// => Error(Contract, MATH_OVERFLOW); borrow_index < MAX_BORROW_INDEX_RAY
// market frozen: withdraw and repay both revert with MATH_OVERFLOW
```

Unprivileged path: `controller::supply` / `controller::borrow` to build the book, then any call to `update_indexes`, `withdraw`, `repay`, or `liquidate` triggers `global_sync` → `accrue_chunk` → `accrue_step` → `scaled_to_original` → `Ray::mul` → `MathOverflow` panic.
