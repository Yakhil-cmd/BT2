### Title
Global, unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a signed webhook from one org write CI statuses onto another org's commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the payload was signed with the secret of the organization named in the payload's `repository.owner.login`/`organization.login` (attacker-controlled field, but must match an org the attacker owns to pick the right secret) [1](#0-0) [2](#0-1) . `StatusHandler#process` then looks up commits purely by `sha` with no scoping to that repository/org at all, and mutates every matching `Commit` row regardless of which stack/org owns it [3](#0-2) .

### Finding Description
The binding that should hold is: `repository_owner` (the org whose secret verified the signature) `==` owner of the `Stack`/`Repository` that owns the `Commit` being mutated by `create_status_from_github!`. This binding is never checked.

Code path:
1. `WebhooksController#verify_signature` derives `repository_owner` from the payload body itself (`params.dig('repository','owner','login')`), and verifies the raw body's HMAC signature against `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) . An attacker who owns `org-x` can name any repository they want in this field (it's their own payload) and sign it with `org-x`'s legitimate `webhook_secret` — this step only proves "the payload came from someone possessing org-x's secret," not that it authorizes writes to any specific commit.
2. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query has no `stack_id`/repository filter — the only DB index on the column is `(stack_id, sha)`, not a global unique index on `sha` [4](#0-3) , so `Commit` rows with identical `sha` can legitimately exist under unrelated stacks/tenants.
3. `create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, which creates a `Status` on that commit and can flip its deployability state (`deployable?`, `blocked?`, continuous-delivery scheduling) [5](#0-4) [6](#0-5) [7](#0-6) .

Given the stated precondition — a `Commit` row with a matching `sha` already exists under an org-y stack (e.g., an identical commit object shared across a fork/mirror) — a signed `status` webhook from org-x, authenticated only for org-x, will still mutate org-y's `Commit`, because nothing in `verify_signature` or `StatusHandler#process` ties the verified repository identity to the target commit's owning stack.

### Impact Explanation
An attacker who controls only their own GitHub org/webhook secret can forge a CI status (`success`/`failure`) onto a commit belonging to a stack of a completely unrelated tenant, once such a sha exists in both tenants' commit tables. This directly affects `deployable?`/`blocked?` gating, which governs whether the victim's continuous-delivery pipeline treats the commit as safe to deploy — a cross-tenant write via a payload authenticated for a different repository, matching the "Critical" impact category (payload for one repository mutating another's commit/stack).

### Likelihood Explanation
This requires the specific precondition of a real sha collision (the same exact commit object present in both org-x's and org-y's Shipit-tracked repos), which is not attacker-controllable for arbitrary target commits — SHA-1 git commit hashes depend on tree/parent/author/timestamp content, so an attacker cannot force an arbitrary victim commit to collide. It becomes practically likely only in cases such as forked/mirrored repositories, shared upstream commits cherry-picked verbatim into multiple orgs' Shipit-tracked repos, or the same commit being present in two Stacks tracking the same underlying repo. Given the precondition (as stated in the question) is met, exploitation cost is low: one signed POST to `/webhooks` with the attacker's own valid secret.

### Recommendation
Scope the lookup in `StatusHandler#process` (and any other handler using bare `sha`/global lookups) to commits whose stack's repository matches the verified `repository_owner`/`repository.full_name` from the payload, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: ..., repository_name: ... })`, or otherwise authenticate the target repository at the `Commit` level before invoking `create_status_from_github!`.

### Proof of Concept
1. Create `Stack` A owned by `org-x` and `Stack` B owned by `org-y`. Create `Commit` rows on both stacks with the identical `sha` value `"deadbeef..." * 1` (same 40-char sha, different stack_id).
2. Configure `webhook_secret` for `org-x` only (as `Shipit.github(organization: 'org-x')`).
3. Build a `status` webhook JSON payload: `{"repository": {"owner": {"login": "org-x"}}, "sha": "<shared sha>", "state": "success"}`, sign it with `org-x`'s secret, and POST to `/webhooks` with header `X-Github-Event: status` and the correct `X-Hub-Signature`.
4. Assert response is `200 OK`.
5. Assert `Shipit::Commit.find_by(stack_id: stack_b.id, sha: shared_sha).statuses.reload.last.state == "success"` — i.e., a `Status` was created on org-y's commit despite the request only being authenticated for org-x.
6. Assert no equivalent authorization check exists tying `repository_owner` to `stack_b.repository_owner` anywhere in `StatusHandler#process` or `WebhooksController#verify_signature`.
