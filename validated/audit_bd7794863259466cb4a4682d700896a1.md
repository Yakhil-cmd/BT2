### Title
Cross-tenant status forgery via unscoped `sha`-only lookup in `StatusHandler#process` flips `Commit#deployable?` for another stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up target commits with `Commit.where(sha: params.sha)` — matching purely on the git SHA string with no constraint tying the result to the repository/organization that authenticated the webhook. `Commit#deployable?` (used by both `Stack#trigger_deploy`/`DeploysController#create` and the rollback-eligibility surface, e.g. `UndeployedCommit#deploy_disallowed?`, `Deploy#rollbackable?`) is computed from `success?`/`blocked?`, which read from `statuses` rows written by this handler. Because `Status.replicate_from_github!` is created with `stack_id: commit.stack_id` (the *matched* commit's own stack, not the webhook's declared repository), any stack in the installation containing a commit whose SHA collides with a SHA emitted by an attacker-controlled, signature-verified webhook gets a `Status` row injected, silently altering `deployable?` for that unrelated commit/stack.

### Finding Description
Binding claimed: `victim/prod`'s `Commit#deployable?` must be derived only from statuses that GitHub delivered *for `victim/prod`'s own repository* (i.e., `status.stack_id == webhook_authenticated_repository.stack_id`). Actual code: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` with no `stack_id`/`repository` filter tied to the webhook's authenticated organization/repository. `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` uses the *matched commit's* `stack_id`: [2](#0-1) [3](#0-2) 

`Commit#deployable?` and `#blocked?` consume this Status transparently: [4](#0-3) [5](#0-4) 

Signature verification (`verify_signature`) only proves the webhook body was signed by the GitHub App/organization named in the payload (`repository.owner.login`); it does not, and cannot, constrain which `Commit` rows in the database get matched by `sha` inside the handler: [6](#0-5) 

**Exploit flow**: git commit SHAs are content-addressed and identical across forks/clones for shared history. An attacker forks the public `victim/prod` GitHub repository (ordinary unprivileged action), preserving identical commit objects/SHAs for any commits shared with upstream. The attacker installs/authorizes Shipit's GitHub App on their own fork (or otherwise legitimately triggers a real, correctly-signed `status` webhook from their own repo, e.g. via their fork's Actions/CI posting a commit status). GitHub signs and delivers this webhook with the attacker's own organization/app credentials — a fully valid signature that `verify_signature` accepts, since it only authenticates "this event came from an app config for this organization," not "this sha belongs to this organization's tracked stacks." `StatusHandler#process` then matches `Commit.where(sha: <shared sha>)`, which returns **every** commit across the installation with that SHA — including the one under `victim/prod`'s stack — and writes a new `Status` scoped to `victim/prod`'s `stack_id`, changing `success?`/`blocked?` and therefore `deployable?` for `victim/prod`'s commit, with no interaction with `victim/prod`'s own webhook secret or repository.

None of the listed guards prevent this: `verify_signature` authenticates the sender's own org, not the sha's ownership; `drop_unhandled_event` only filters event types; the `ExplicitParameters` schema on `StatusHandler` validates `sha`/`state` shape only, not scope; `Repository` uniqueness/format validators don't constrain cross-repo commit-table lookups by sha.

### Impact Explanation
An unprivileged attacker who merely owns a fork (or any repo sharing SHAs with a target public repo) can inject fabricated CI status rows into `victim/prod`'s commit records, flipping `Commit#deployable?` for that stack. Since `deployable?` gates both deploy eligibility (`DeploysController#create`, `Stack#trigger_deploy`'s `ignored_safeties` flag) and rollback-adjacent decisions (`UndeployedCommit#deploy_disallowed?`, `Deploy#rollbackable?`, `ContinuousDeliveryJob` scheduling via `schedule_continuous_delivery`), this is a payload from one repository mutating another's stack/commit state — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. It is repeatable against any stack whose tracked repository has public history forkable by the attacker (very broad blast radius across tenants sharing a Shipit installation).

### Likelihood Explanation
Preconditions: (1) the target repository's history must be forkable/public so SHAs can be reproduced by the attacker, (2) the attacker must be able to get a genuinely-signed `status` webhook delivered from their own repo/org (standard for any GitHub App installed on a user-owned repo — no special Shipit privilege needed), (3) Shipit must already have synced the colliding commit into `victim/prod`'s `commits` table (true for any commit already pushed and tracked, e.g. `last_deployed_commit`). No Shipit secrets, sessions, or API tokens are required. Cost is low and the action is repeatable for every shared commit.

### Recommendation
Scope the `StatusHandler#process` lookup and the `Status` write to the repository/organization the webhook actually authenticated for, e.g. resolve the target `Stack`/`Repository` from the payload's `repository.full_name` and constrain `Commit.where(sha:, stack_id: matching_stack_ids)` instead of matching on `sha` alone across the whole installation; reject or ignore matches for stacks whose repository does not correspond to the authenticated organization/repository in the payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "cross-repo status payload flips deployable? for an unrelated stack's commit sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)          # victim/prod
  victim_commit = shipit_commits(:fifth)         # last_deployed_commit-like, currently not deployable
  refute_predicate victim_commit, :deployable?

  attacker_stack = shipit_stacks(:cyclimse)      # a completely different, unrelated stack/repo
  # simulate a fork sharing the same commit sha as victim_commit
  attacker_commit = attacker_stack.commits.create!(sha: victim_commit.sha, message: "shared history")

  # Webhook signature is only ever verified against the attacker's own org (cyclimse),
  # never touching victim/prod's webhook secret.
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => attacker_stack.branch }]
  }.merge('repository' => { 'full_name' => attacker_stack.repository.full_name,
                             'owner' => { 'login' => attacker_stack.repository.owner } })

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  assert_predicate victim_commit.reload, :deployable?  # flipped without victim/prod's own signal
end
```
