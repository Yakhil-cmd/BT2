## Analysis: ERC20 asset transactor trusts declared `amount`, not actual transferred/received balance

The reported bug class (deflationary/fee-on-transfer tokens breaking code that assumes "amount sent == amount received") has a concrete, reachable analog in this repo's ERC20 XCM asset transactor.

### Title
ERC20Transactor credits/debits XCM holding with the requested `amount` instead of the actually transferred ERC20 balance, enabling accounting desync for fee-on-transfer/deflationary ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the target ERC20 contract's `transfer()` and only check the boolean success return value, never the pre/post balance of the checking account or beneficiary. Any ERC20 contract that charges a fee on transfer (a legal, common pattern not prohibited by EIP-20) will return `true` while moving less than `amount`. The transactor nonetheless mints/consumes exactly `amount` worth of `AssetsInHolding`, permanently desynchronizing the shared checking-account's real ERC20 balance from the amount the XCM executor believes it holds on behalf of all users of that asset.

### Finding Description
`ERC20Transactor` is wired into production XCM configuration (`AssetTransactors` tuple in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:240-246`), reachable by any signed account via `pallet_xcm::execute`/`send` with an XCM program containing `WithdrawAsset`/`DepositAsset` referencing an asset id of the local form `{parents:0, interior: X1(AccountKey20{key})}`.

Critically, the matcher that decides which locations this transactor handles, `ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` (`cumulus/parachains/runtimes/assets/common/src/lib.rs:134-160`), accepts **any** local `AccountKey20` location — there is no allow-list of vetted ERC20 contracts. `IsLocalAccountKey20::contains` simply checks the location shape: [1](#0-0) 

This means an attacker who deploys their own arbitrary ERC20-compatible contract on `pallet-revive` fully controls the `transfer()` implementation invoked by the transactor, including implementing a deflationary/fee-on-transfer transfer function that still returns `true`.

In `withdraw_asset_with_surplus`, the code calls `IERC20::transferCall{ to: checking_address, value: amount }` on the user-controlled contract, checks only `is_success` (the boolean return), and then credits the XCM holding with the **full requested `amount`**, not the amount actually received by the checking account: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` out of the checking account to the beneficiary and, on `Ok(true)`, treats the deposit as fully successful without verifying the beneficiary's actual balance delta: [3](#0-2) 

The `TransactAsset` trait itself documents the expected invariant — "Return the actual asset(s) withdrawn, which should always be equal to `_what`" — which this implementation violates for any fee-on-transfer contract: [4](#0-3) 

### Impact Explanation
The `TransfersCheckingAccount` (a single pallet-derived account, `ERC20TransfersCheckingAccount = PalletId(*b"py/revch")`) is a shared pot backing every outstanding XCM `AssetsInHolding` credit for every ERC20 asset routed through this transactor: [5](#0-4) 

If an attacker uses a deflationary ERC20 (their own contract, or any pre-existing fee-on-transfer token that a chain operator later whitelists via this generic matcher), each `WithdrawAsset` credits the XCM holding for the full nominal `amount` while the checking account actually only receives `amount - fee`. That over-credited holding can then be moved by any subsequent XCM instruction (e.g. `DepositAsset` to a different local beneficiary, or onward transfer instructions) exactly as if it were fully backed. Repeating this drains real ERC20 balance out of the shared checking account faster than it is replenished, at the expense of other users' legitimately-backed holdings of the same asset — a direct value-extraction/theft vector against the shared reserve, and/or a denial-of-service once the checking account can no longer satisfy legitimate `deposit_asset` calls for other holders of the same asset.

### Likelihood Explanation
Reachability requires only a signed extrinsic calling `pallet_xcm::execute` (or `send`) with a `WithdrawAsset`/`DepositAsset` program — no privileged role, governance, or malicious validator/collator is needed. The matcher (`IsLocalAccountKey20`) imposes no allow-list, so the attacker can deploy their own malicious ERC20 contract on `pallet-revive` and immediately use it through this transactor. This is Medium severity: it requires the attacker (or ecosystem) to use/deploy a fee-on-transfer ERC20, but the code path is unauthenticated and directly reachable, matching the reported bug class precisely (checks success boolean/allowance-style return instead of verifying actual balance delta).

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 `balanceOf` of the checking account (and/or beneficiary) immediately before and after the `transfer` call, and credit/debit the XCM holding with the **measured delta**, not the requested `amount`. Alternatively, explicitly document and enforce (e.g., via a registration/allow-list `Contains` filter instead of `IsLocalAccountKey20`) that only ERC20 contracts verified to transfer the exact requested `value` (no fee-on-transfer/rebasing behavior) may be used with this transactor.

### Proof of Concept
Not independently executed in this session; a concrete integration test would deploy a minimal Solidity/ink! ERC20 contract on `pallet-revive` whose `transfer(to, value)` moves `value - fee` but returns `true` (analogous to existing test fixtures in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` such as `smart_contract_does_not_return_bool_fails`, which already exercises this transactor with custom contracts), register it as the asset in a `WithdrawAsset`/`DepositAsset` XCM program via `PolkadotXcm::execute`, and assert that (a) the ERC20 checking account's real `balanceOf` increases by less than `amount`, while (b) the XCM holding/`AssetsInHolding` and any downstream `DepositAsset` reflect the full `amount`. This repository provides the test scaffolding (`bare_instantiate`, `compile_module_with_type`, `ERC20TransfersCheckingAccount`) to build such a test, but I did not run it — the finding is based on static code reading of the transactor logic and its wiring, not an executed reproduction.
