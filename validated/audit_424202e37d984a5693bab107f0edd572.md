### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `repository.review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` only ANDs `repository.review_stacks_enabled` with the `provisioning_behavior_allow_all?` branch due to Ruby `&&`/`||` precedence; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`. As a result, a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will still provision a `ReviewStack` from an attacker-controlled pull request, executing that PR's `shipit.yml` via `ReviewStack#provisioner`/`Command`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold for any `ReviewStack` to be created. Tracing `provision?`: [3](#0-2) 
parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Only the first disjunct references `review_stacks_enabled`; the other two are evaluated regardless of it. `process` calls `respond_to_pull_request_opened?` → `provision?`, and if true, invokes `ReviewStackAdapter#find_or_create!`, which calls `create!`, setting `branch: params.pull_request.head.ref` (attacker-controlled) and enqueuing `Shipit::ReviewStackProvisioningQueue.add(stack)` for provisioning. [4](#0-3) [5](#0-4) 
The `ReviewStack` state machine transitions `deprovisioned → provisioning`, invoking `stack.provisioner.up`, which drives execution of the repo's `shipit.yml` steps (this ultimately reaches `Command`/`PTY.spawn` execution paths, consistent with normal review-stack provisioning flow used for `allow_all`). [6](#0-5) 
Neither `Repository` model validations nor `RepositoriesController#update_params` couple `provisioning_behavior` to `review_stacks_enabled` — an operator (or a mistaken migration/default) can leave `review_stacks_enabled: false` while `provisioning_behavior` is `allow_with_label`/`prevent_with_label`, and the code path does not re-check the flag. [2](#0-1) 
The existing test suite does not cover this exact combination — all `allow_with_label`/`prevent_with_label` tests use the default `provisioning_enabled: true`, leaving the divergence unverified. [7](#0-6) 

### Impact Explanation
If `review_stacks_enabled` is false but `provisioning_behavior` is `allow_with_label` and `provisioning_label_name` is set, an attacker who opens a PR on that repository with the matching label triggers creation and provisioning of a `ReviewStack` whose `branch` is the attacker's own head ref, leading to execution of attacker-supplied `shipit.yml` on the deploy host — RCE. Similarly, with `prevent_with_label`, any PR lacking the label auto-provisions, regardless of the "disabled" flag. This is repeatable per PR/per repository misconfigured this way and does not require any secrets.

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled: false` with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (and a `provisioning_label_name` for the label variant) — a plausible operator misconfiguration since the UI/model do not enforce that `provisioning_behavior` be irrelevant when `review_stacks_enabled` is false. Given that configuration, exploitation cost is minimal: an attacker with normal PR-opening rights on the tracked repository just opens a PR (adding a label if required).

### Recommendation
Fix operator precedence in `provision?` to gate all branches on `review_stacks_enabled`, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks when review_stacks_enabled is false even with allow_with_label and matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_equal false, repository.reload.review_stacks_enabled
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
This currently fails (a stack IS created) because `provision?` does not check `review_stacks_enabled` for the `allow_with_label` branch, proving the equality `repository.review_stacks_enabled == true` is not enforced before `ReviewStack` creation.
