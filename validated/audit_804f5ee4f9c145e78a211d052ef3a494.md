### Title
Interest accrual permanently freezes a market once `scaled_borrowed * borrow_index` overflows `i128` — the index cap never engages ([File: contracts/pool/src/interest.rs](contracts/pool/src/interest.rs))

### Summary
The pool's `global_sync` accrues interest on every entry path (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `update_indexes`, flash paths). Each accrual step multiplies the market's total scaled debt (`Ray`-scaled shares) by the newly compounded borrow index inside `scaled_to_original`/`accrue_step`. Once `borrowed_shares * borrow_index` exceeds `i128::MAX`, the multiplication panics with `GenericError::MathOverflow`. Because accrual runs *before* every state-changing operation and the stored `borrow_index`/`borrowed` values are never written down on a failed accrual, every subsequent call that touches the market panics forever: no repayments, no withdrawals, no liquidations, no `clean_bad_debt`, no `recapitalize`. The `MAX_BORROW_INDEX_RAY` cap is checked on the index itself, but the overflow occurs in the *value* multiplication well before the index reaches that cap, so the intended safety bound never engages.

### Finding Description
`global_sync` in `contracts/pool/src/interest.rs:20-33` chunks elapsed time and calls `accrue_chunk` → `accrue_step` (shared with the `update_indexes` view). `accrue_step` derives the new borrow index via `compound_interest` (`common/src/rates/compound.rs:31-51`, `MAX_COMPOUND_DELTA_MS` = 1 year, rate ≤ `MAX_BORROW_RATE_RAY` = 2 RAY → index grows up to ~e² ≈ 7.4×/year) and then computes `borrowed.mul(borrow_index)` — a `Ray` i128 multiply — to book interest. `borrowed` is the sum of RAY-scaled debt shares, i.e. `principal_units * 10^(27 - decimals)` at index ≈ 1. For low-decimal or high-supply markets this product crosses `i128::MAX` (≈ 1.7e38) while the index is still far below `MAX_BORROW_INDEX_RAY`. Since `accrue_chunk` only commits via `cache.set_borrow_index` after `accrue_step` returns, the panic leaves state untouched — but the same panic recurs on the very next call because `last_timestamp` and the indexes are unchanged and time has only advanced further. The repo's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` demonstrates exactly this: withdraw and repay both revert with `MATH_OVERFLOW`, "the market is frozen… The index cap never engages," and the comment notes the documented bound in `docs/reference/formulas.md` is wrong.

### Impact Explanation
Permanent freezing of funds in the affected market — an accepted impact class. All suppliers' collateral and all repayment/liquidation paths for that market are bricked; the market's cash can never exit, bad debt can never be cleaned, and any account whose solvency depends on that market cannot be liquidated or withdrawn through it. There is no admin recovery path in scope (recapitalize and governance ops also accrue first or cannot rewrite indexes).

### Likelihood Explanation
Reachable by a single unprivileged address using only `supply` + `borrow` + `update_indexes`: the attacker supplies a large position in a listed market, borrows near the utilization maximum to pin the rate at the steep segment of the curve (≥ ~2 RAY effective, so the index compounds ~7.4×/year), and lets accrual run. No privileged call, oracle manipulation, or third-party cooperation is needed — the panic is pure in-contract arithmetic. The capital requirement is large (billions of base units for high-decimal tokens, far less for low-decimal listings where `from_asset`'s `10^(27-decimals)` scaling inflates scaled values), and the freeze requires sustained high utilization, so it is a High-severity / lower-likelihood economic DoS rather than a free griefing vector. Once the cliff is crossed, however, the freeze is irreversible and applies to all users of the market, not just the attacker.

### Recommendation
Make accrual saturating instead of panicking: compute the interest leg with saturating/checked `I256` math and clamp `borrowed * borrow_index` (and the new index) to `MAX_BORROW_INDEX_RAY`-bounded values *before* the `scaled_to_original` multiply, or detect the would-be overflow in `accrue_step` and pin the index so the multiply stays in domain. Alternatively, gate `mint_debt`/`supply` so that `scaled_total_borrowed * MAX_BORROW_INDEX_RAY` can never overflow (cap validation at listing/borrow time via `require_cap_within_asset_domain`-style checks). The `scaled_to_original` panic on the accrual path must be unreachable for the market to remain live.

### Proof of Concept
The repository already contains the working PoC. In `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);   // ~98% utilization, unprivileged supply+borrow

// advance time; each try_update_indexes_for call runs global_sync/accrue_step
// → panic MATH_OVERFLOW inside scaled_to_original
assert_contract_error(failed, errors::MATH_OVERFLOW);
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged

// market permanently frozen: every verb accrues first and hits the same panic
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `Controller::*` → pool op → `interest::global_sync` (`contracts/pool/src/interest.rs:20`) → `accrue_chunk` → `accrue_step` → `scaled_to_original` (`common/src/rates/scaling.rs:14-16`, `scaled.mul(index)`) → `i128` overflow → `MathOverflow` panic, repeating identically on every subsequent call since no state is committed.
