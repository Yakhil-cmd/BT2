### Title
Auctioneer Signature Lacks Independent Chain Binding, Enabling Cross-Fork Replay of Bid Approvals — (`kaiax/auction/bid.go`)

---

### Summary

`ValidateAuctioneerSig` verifies the auctioneer's approval of a searcher bid by checking a signature over `GetEthSignedMessageHash(searcherSig)` — a plain `eth_sign` hash of the raw 65-byte searcher ECDSA signature bytes. This digest contains no chainID, no verifyingContract, and no other chain-specific context of its own. If Kaia undergoes a hard fork that preserves the same `chainId`, the auctioneer's signature is cryptographically identical on both chains and can be replayed on the fork without the auctioneer's knowledge or consent.

---

### Finding Description

The auctioneer's signature digest is computed in `GetEthSignedMessageHash`:

```go
func (b *Bid) GetEthSignedMessageHash() []byte {
    data := b.SearcherSig
    return crypto.Keccak256(fmt.Appendf(nil, "\x19Ethereum Signed Message:\n%d%s", len(data), data))
}
``` [1](#0-0) 

This is a standard `eth_sign` hash over the raw 65-byte `SearcherSig` bytes. The auctioneer then signs this digest:

```go
func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
    digest := b.GetEthSignedMessageHash()
    recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
    ...
}
``` [2](#0-1) 

The searcher's signature (`SearcherSig`) IS chain-bound: it is an EIP-712 signature whose domain includes `chainId` and `verifyingContract`:

```go
EIP712DomainType = "EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)"
``` [3](#0-2) 

The domain separator is built with the live `chainId` and `auctionEntryPoint` address:

```go
domain := EIP712Domain{
    ChainId:           chainId,
    VerifyingContract: verifyingContract,
    ...
}
``` [4](#0-3) 

However, the auctioneer does **not** sign the EIP-712 digest directly. It signs the raw bytes of the searcher's ECDSA output. The 65-byte `SearcherSig` is the ECDSA signature over the EIP-712 digest — it is chain-specific only because the EIP-712 digest is chain-specific. The auctioneer's own signature carries **no independent chain context**.

The bid pool enforces this validation path unconditionally:

```go
if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
    return err
}
if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
    return err
}
``` [5](#0-4) 

The on-chain `AuctionEntryPoint` contract uses the same scheme (confirmed by the mock's commented-out verification logic):

```solidity
// bytes32 digest = MessageHashUtils.toEthSignedMessageHash(auctionTx.searcherSig);
// (address recoveredSigner, , ) = digest.tryRecover(auctionTx.auctioneerSig);
``` [6](#0-5) 

---

### Impact Explanation

If Kaia undergoes a hard fork that does **not** change the `chainId` (the exact scenario described in the seed report), the following holds:

1. The EIP-712 domain separator is identical on both chains (same `chainId`, same `verifyingContract` address if the fork preserves contract addresses).
2. The searcher's EIP-712 digest is identical → `SearcherSig` bytes are identical.
3. `GetEthSignedMessageHash(searcherSig)` is identical → the auctioneer's `AuctioneerSig` is valid on both chains.

An adversary operating on the fork can replay a bid that was approved by the auctioneer on the canonical chain. The on-chain `AuctionEntryPoint` would accept the replayed `AuctioneerSig` because the digest it verifies is chain-agnostic. The searcher's nonce on the fork starts from its fork-state value, so the nonce guard does not block the replay.

The concrete corrupted value: the searcher's KAIA deposit in the `AuctionEntryPoint` contract on the fork is consumed (`_checkAndTakeBid`) and the searcher's calldata is executed (`auctionTx.to.call`) without the auctioneer having explicitly approved the bid for the fork chain.

---

### Likelihood Explanation

**Trigger**: Any Kaia hard fork that preserves `chainId` (e.g., a contentious fork where one side does not update the chain ID, as occurred with Ethereum/Ethereum Classic). The auctioneer is a semi-trusted external service; it does not need to be compromised. Any party that observed the original `AuctioneerSig` on the canonical chain (it is transmitted over P2P and via `auction_submitBid` RPC) can replay it on the fork.

**Unprivileged trigger**: The replayer only needs to call `auction_submitBid` on a fork-chain CN node with the original bid data. No key compromise is required.

---

### Recommendation

**Short term**: Replace `GetEthSignedMessageHash(searcherSig)` with an EIP-712 digest that independently binds the auctioneer's approval to `chainId` and `verifyingContract`. For example:

```
AuctioneerApproval(bytes32 searcherSigHash, uint256 chainId, address verifyingContract)
```

where `searcherSigHash = keccak256(searcherSig)`. This ensures the auctioneer's signature is invalid on any chain with a different `chainId` or a different `AuctionEntryPoint` address, even if the searcher's signature bytes are identical.

**Long term**: Audit all off-chain signature schemas in the `kaiax/auction` module for replay robustness across wallets, contracts, and chains. Document the expected domain-separation guarantees for both `SearcherSig` and `AuctioneerSig`.

---

### Proof of Concept

1. On canonical Kaia (chainId = 8217), searcher Alice submits a bid. The auctioneer signs `EthSignedMessageHash(aliceSearcherSig)` and returns `AuctioneerSig_A`.

2. Kaia forks at block N. The fork chain retains chainId = 8217 and the same `AuctionEntryPoint` address.

3. On the fork, an adversary calls `auction_submitBid` with the original bid fields, `aliceSearcherSig`, and `AuctioneerSig_A`.

4. `validateBidSigs` in `bid_pool.go` calls:
   - `ValidateSearcherSig(8217, auctionEntryPoint, version)` → passes, because the EIP-712 digest is identical (same chainId, same contract, same bid data).
   - `ValidateAuctioneerSig(auctioneer)` → passes, because `GetEthSignedMessageHash(aliceSearcherSig)` is identical and `AuctioneerSig_A` was produced over that exact digest.

5. The bid is accepted into the fork's bid pool. When the proposer builds the next block, the bid is included. The on-chain `AuctionEntryPoint` on the fork verifies the same signatures using the same scheme and executes the bid, consuming Alice's KAIA deposit on the fork without the auctioneer having approved the bid for the fork chain.

	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}
