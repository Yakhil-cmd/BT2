### Title
Unsigned webhook from an org lacking `webhook_secret` mutates a victim repository's stack via mismatched `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for signature verification solely from `repository.owner.login`, while the event handlers (e.g. `Shipit::Webhooks::Handlers::Handler#stacks`, `PullRequest::OpenedHandler#repository`) resolve the target `Repository`/`Stack` from the independent `repository.full_name` field in the same JSON body. If `AttackerOrg` is configured in `Shipit.github_apps` with no `webhook_secret` (or is otherwise resolvable without one), `GitHubApp#verify_webhook_signature` returns `true` unconditionally, and nothing ties the verified owner to the `full_name` used for the actual mutation.

### Finding Description
Binding claimed: `webhook_secret.present?` for the org used to verify == a non-nil verifier that actually authenticates the payload bytes. This fails to hold: `GitHubApp#verify_webhook_signature` at [1](#0-0)  does `return true unless webhook_secret`, so when `@webhook_secret` is `nil` (set from `@config[:webhook_secret].presence` at [2](#0-1) ), any signature — including none — is accepted.

The controller looks up the verifying app using `repository_owner`, derived from `params.dig('repository','owner','login')`: [3](#0-2) [4](#0-3) . This is the only field used for auth. Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the *entire* raw JSON body [5](#0-4) . Handlers resolve the affected repository from a completely different field, `repository.full_name`, e.g. `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` [6](#0-5) , and `PullRequest::OpenedHandler#repository` [7](#0-6) . Nothing cross-checks that `repository.owner.login` matches the owner portion of `repository.full_name`.

Attack: attacker controls (or registers, if the operator's config allows registering an org with no secret) `AttackerOrg` in `Shipit.github_apps`. They POST an unsigned request to `/webhooks` with `X-Github-Event: push` (or `pull_request`, `status`, etc.) and a body where `repository.owner.login = "AttackerOrg"` but `repository.full_name = "Victim/repo"`. `verify_signature` resolves `Shipit.github(organization: 'AttackerOrg')`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature`. The handler then resolves `Victim/repo`'s real `Stack`/`Commit`/`PullRequest` and mutates it (e.g. enqueues `GithubSyncJob`, updates commit `Status`, archives/unarchives a review stack, updates a `PullRequest`).

Existing guards do not stop this: `drop_unhandled_event` only filters by event type, not by repository identity [8](#0-7) ; `verify_signature`'s only failure mode is `GithubOrganizationUnknown`, which requires the *organization name* to be entirely absent from configuration — it does not detect owner/full_name mismatch [9](#0-8) ; the `ExplicitParameters` schemas in handlers only validate types/presence of `repository.full_name`, not its relationship to `repository.owner.login`.

### Impact Explanation
Any webhook event whose handler keys off `repository.full_name` (push → `GithubSyncJob`, `status` → `Commit#statuses`, `pull_request` opened/closed/labeled → `ReviewStackAdapter`/`PullRequest` updates) can be forged against `Victim/repo` as long as the attacker controls one organization entry in `Shipit.github_apps` with no `webhook_secret`. This is a payload-for-one-repository mutating another repository's stack/commit/task state — squarely in the Critical impact category (cross-tenant stack mutation, unauthorized deploy triggers via `GithubSyncJob`, forged commit statuses, and review-stack archive/unarchive). The blast radius spans every stack/repository configured in the same Shipit instance, not just the attacker's own org.

### Likelihood Explanation
This requires that Shipit's own configuration contains at least one organization entry with a missing/blank `webhook_secret` in `Shipit.github_apps`/secrets — a deployment/configuration precondition, not something the attacker can create from nothing unless they can register such an org themselves (e.g. if the host app allows self-service GitHub App/organization registration into `Shipit.github_apps` without enforcing a secret). Given that precondition, the exploit is trivial and free: a single unauthenticated `POST /webhooks` request, no valid signature, no session, no token, fully repeatable against any repository whose `full_name` is guessable (repository names are public).

### Recommendation
In `WebhooksController#verify_signature`, cross-validate that `params.dig('repository','owner','login')` matches the owner segment of `params.dig('repository','full_name')` before dispatching to handlers, and reject (422) on mismatch. Additionally, make `GitHubApp#verify_webhook_signature` fail closed (return `false`, not `true`) when `webhook_secret` is blank, and require every configured GitHub App/organization in `Shipit.github_apps` to have a non-blank `webhook_secret` (raise at load time otherwise) so no organization can ever bypass signature verification.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test, no WebMock/live GitHub)
test "org without webhook_secret cannot forge events for another organization's repository" do
  victim_commit = shipit_commits(:first) # belongs to 'shopify' org/stack in fixtures

  # Simulate AttackerOrg configured with no webhook_secret
  Shipit.github_apps['AttackerOrg'] = Shipit::GitHubApp.new('AttackerOrg', { app_id: 1, installation_id: 1 })

  request.headers['X-Github-Event'] = 'status'
  # No X-Hub-Signature header at all
  body = {
    sha: victim_commit.sha,
    state: 'success',
    target_url: 'https://evil.example.com',
    repository: {
      owner: { login: 'AttackerOrg' },       # attacker-controlled org, no secret
      full_name: victim_commit.stack.repository.github_repo_name # victim repo full_name
    }
  }.to_json

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: body, as: :json
  end
  # Binding check: webhook_secret.present? for 'AttackerOrg' (false) should equal
  # "a verifier that actually validates bytes" (false) -> if it currently equals true
  # (accepted) this assertion fails, proving the bypass.
end
```
If the `assert_no_difference` fails (i.e., a `Status` row is created for the victim commit), it confirms the unsigned cross-organization request was accepted and mutated victim state, proving the vulnerability.
