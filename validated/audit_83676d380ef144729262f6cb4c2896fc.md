Based on my investigation, I found a legitimate analog to the CVE's bug class ("access-control rule set documented as more restrictive than what is actually enforced, misleading operators into believing a policy is safe"). The polkadot-sdk codebase has a **directly on-point, previously-confirmed instance of exactly this bug class** in `pallet_proxy::ProxyType::NonTransfer` filters, which are implemented as deny-lists that "fail open": any call family not explicitly listed is permitted, contradicting the doc-comment "Can execute any call that does not transfer funds or assets."

This exact pattern was already found and fixed in two runtimes via [1](#0-0)  (Asset Hub Westend) and [2](#0-1)  (staking-async parachain runtime, partial fix). However, the staking-async parachain runtime's fix in pr_12922 only added `ForeignAssets`/`PoolAssets` to the deny-list — it did **not** add the other value-moving call families (`AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, `Indices::transfer`/`force_transfer`) that the sibling Asset Hub Westend fix (pr_12771) determined were required to close the same class of leak [3](#0-2) , compared with the more complete asset-hub-westend deny-list [4](#0-3) .

I was not able to confirm within the remaining tool budget whether `pallet_asset_conversion`, `pallet_revive`, `pallet_xcm`, `pallet_indices`, or `pallet_vesting` are actually instantiated in the staking-async parachain runtime's `construct_runtime!`/`RuntimeCall` enum (a grep found 35 keyword matches in the file, but I could not inspect them before running out of iterations). **This reachability check is essential and unconfirmed** — if these pallets are not part of this runtime's call enum, the leak does not exist there, and the finding would be not applicable. I cannot verify runtime wiring, so per the review method I must not force a Critical/High report on an unconfirmed premise.

### Title
Potential fail-open `ProxyType::NonTransfer` deny-list leak in staking-async parachain runtime (unconfirmed pallet inclusion) - (File: substrate/frame/staking-async/runtimes/parachain/src/lib.rs)

### Summary
`ProxyType::NonTransfer` is documented as denying "any call that does not transfer funds or assets" but is implemented as an explicit deny-list [5](#0-4) . The sibling Asset Hub Westend runtime had the identical bug class, was found to leak `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive` and `Indices::transfer`/`force_transfer` calls, and was patched in pr_12771 [6](#0-5) . The staking-async parachain runtime's own subsequent patch (pr_12922) closed only the `ForeignAssets`/`PoolAssets` gap [7](#0-6) , leaving the current deny-list at [8](#0-7)  structurally identical to the pre-pr_12771 vulnerable Asset Hub Westend list.

### Finding Description
If the staking-async parachain runtime's `RuntimeCall` enum includes `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, or `Indices` pallets (unconfirmed), a delegator who grants a `NonTransfer` proxy — believing per the doc-comment that the proxy cannot move funds — would in fact allow the proxy account to move the delegator's assets via those pallets, since `pallet_proxy::do_proxy` only consults `ProxyType::filter` and nothing else gates the call [9](#0-8) .

### Impact Explanation
If reachable, this would let a party holding a `NonTransfer` proxy (a permission a user grants believing it is value-safe) move the delegator's funds/assets — the exact impact class the maintainers treated as bounty-worthy enough to patch twice elsewhere (pr_12771, pr_12769, pr_12922).

### Likelihood Explanation
Likelihood is unconfirmed pending verification of whether the value-moving pallets in question (`AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, `Indices`) are actually part of this specific runtime's pallet set — I could not verify this before exhausting available tool calls.

### Recommendation
Verify the staking-async parachain runtime's `construct_runtime!` pallet list; if any of `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, `Indices::transfer`/`force_transfer`, or `Vesting::vested_transfer` are present, add them to the `NonTransfer` deny-list exactly as done in pr_12771, and add a regression test mirroring `non_transfer_proxy_rejects_value_moving_calls` [10](#0-9) .

### Proof of Concept
Not executed. Source-level comparison only: current deny-list at [8](#0-7)  lacks the entries added in the identical-bug-class fix at [11](#0-10) . **Reachability (whether the missing pallets exist in this runtime's `RuntimeCall`) was not confirmed** due to exhausted investigation budget — this is a "needs validation" hypothesis, not a confirmed finding, and should not be treated as proof of an exploitable defect without that verification.

			match c.is_sub_type() {

				// has.

#[test]
fn non_transfer_proxy_rejects_value_moving_calls() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// Collected rather than asserted one by one, so a regression reports every call that slipped
	// through instead of only the first.
	let mut leaked = Vec::new();
	for (name, call) in value_moving_calls() {
		if ProxyType::NonTransfer.filter(&call) {
			leaked.push(name);
		}
		// The call is otherwise well-formed and reachable by a fully permissioned proxy.
		assert!(ProxyType::Any.filter(&call), "Any must permit {name}");
	}

	assert!(
		leaked.is_empty(),
		"NonTransfer must reject calls that move funds or assets, but permitted: {leaked:?}",
	);
}
