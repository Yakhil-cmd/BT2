### Title
Webhook signature verification is scoped to the org named in an unverified payload field, while the affected data is scoped by a different, unverified field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, a value read straight out of the still-unverified JSON body (`params.dig('repository','owner','login')` or `organization.login`). Once the signature check passes, the actual event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve which `Stack`/`Commit` to mutate using a *different* field from the same unverified body: `repository.full_name` (via `Handler#repository_name` / `Repository.from_github_repo_name`). In a multi-organization Shipit deployment (`Shipit.github_organizations`, `github_app_config`), these two fields are never checked against each other.

### Finding Description
The binding that should hold is: `organization whose webhook_secret authenticated the request == organization that owns the repository being written to`. This engine breaks that equality.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb#L24-L49` computes `repository_owner` from the raw, unauthenticated JSON body (`#L59-L62`) and uses it purely to pick a `GitHubApp` config/secret: `Shipit.github(organization: repository_owner)` (`#L25`). It never re-checks that this value matches anything else in the payload. [1](#0-0) [2](#0-1) 

- `Shipit.github(organization:)` looks up per-organization webhook secrets from `Shipit.github_app_config(organization)`, each org having its own independently-configured `webhook_secret` (`lib/shipit.rb#L170-L200`, `config/secrets.development.shopify.yml`). Any GitHub organization admin who has installed the Shipit GitHub App on their **own** org (an "unprivileged" actor with respect to any other tenant of the same Shipit instance) knows/controls that org's `webhook_secret` and can compute a valid `X-Hub-Signature` for arbitrary payload bytes. [3](#0-2) 

- The signature is computed over the *entire raw body* (`request.raw_post`), so the attacker fully controls every field in that payload, including `repository.owner.login` (used only for secret selection) and `repository.full_name` (used only for target resolution). Nothing forces these two fields to refer to the same repository/org. [4](#0-3) 

- After `verify_signature` passes, `WebhooksController#create` dispatches to handlers with the raw parsed params (`app/controllers/shipit/webhooks_controller.rb#L10-L15`). Handlers derive the target purely from `repository.full_name`: [5](#0-4) 
  `Repository.from_github_repo_name` does a case-insensitive DB lookup with no relation whatsoever to which org's secret was used to verify the request: [6](#0-5) 

- Concretely, `PushHandler#process` (triggered on a forged `push` event) looks up stacks belonging to the *victim* repository (resolved from `repository.full_name`) and calls `stack.sync_github(expected_head_sha: ...)`, and `StatusHandler#process` creates a `CommitStatus` for any commit matching the attacker-chosen `sha` on the victim's `Commit` records — statuses that gate CI-required checks for deploys. [7](#0-6) [8](#0-7) 

This is the direct structural analog of the reported bug class: one authorization/authentication check binds to field A (`repository.owner.login`, used to select the verifying secret) while the operation actually performed binds to field B (`repository.full_name`, used to select the mutated repository/stack), and nothing enforces A == B, even though both A and B are inside the very payload whose integrity the signature is supposed to guarantee.

### Impact Explanation
An attacker who legitimately installs/administers the Shipit GitHub App in **their own** GitHub organization (a normal, unprivileged-with-respect-to-other-tenants scenario explicitly supported by this engine's multi-org `github:` config) can forge webhook deliveries — signed with their own org's `webhook_secret` — that name any *other* tenant's repository in `repository.full_name`. This lets them:
- Inject fake commit `status`/`check_suite` events (`StatusHandler`, `CheckSuiteHandler`) that satisfy `ci.require` gating on a victim stack, enabling an unauthorized deploy of a commit that never actually passed CI — directly reachable via `Commit#deployable?` used by `DeploysController#create` (`params.require_ci`).
- Trigger `push` events causing `GithubSyncJob`/`sync_github` to run against victim stacks with attacker-chosen `expected_head_sha`.
- Manipulate `membership`/`pull_request`/`merge_request` style webhook handlers that key off similarly-unverified cross-referenced fields, potentially affecting merge-queue state for a repository outside the attacker's org.

This crosses the "unauthorized deploy" / "cross-repository writes" bar from the rubric (Critical), because it lets an entity authenticated for org X write/mutate state belonging to repository/org Y with no shared trust boundary enforced.

### Likelihood Explanation
Requires only: (1) the target Shipit instance be configured for multiple GitHub organizations (`github:` top-level keyed by org, a documented, supported configuration — see `config/secrets.development.shopify.yml`, `docs/setup.md`), and (2) the attacker being a legitimate admin/owner of *some* org with the Shipit App installed (their own, unrelated org) so they know that org's `webhook_secret`. No access to the victim's GitHub App, tokens, or Shipit account is needed. This is a realistic scenario for any shared/multi-tenant Shipit deployment serving several organizations.

### Recommendation
After signature verification succeeds for organization `repository_owner`, re-validate that every repository-derived field the handlers act on (`repository.full_name`, `organization.login`, etc.) is actually owned by that same, already-verified organization before dispatching to handlers — e.g., assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0` (or equivalent) in `WebhooksController#verify_signature`/`#create`, rejecting the payload otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with their own `webhook_secret` (this is the documented multi-org setup in `docs/setup.md`/`config/secrets.development.shopify.yml`).
2. Attacker (an admin of `attacker-org`, having installed the Shipit GitHub App there) knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` reads `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb#L24-L30`, `lib/shipit/github_app.rb#L76-L83`).
6. `StatusHandler#process` runs against `Commit.where(sha: params.sha)` in `victim-org/victim-repo`'s stack (`Handler#stacks`/`#repository_name` uses `repository.full_name`) and creates a fabricated "success" `CommitStatus`, which can satisfy `ci.require` and enable an otherwise-blocked deploy on the victim's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
