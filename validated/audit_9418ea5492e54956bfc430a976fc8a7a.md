Confirmed: `Repository#owner` (used to derive `Shipit.github(organization: owner)` for signature verification via `WebhooksController#repository_owner`) is completely decoupled from `Commit#stack_id` resolution in `StatusHandler#process`, which looks up commits globally by `sha` with no repository/stack scoping whatsoever.

### Title
Cross-tenant Status forgery via unscoped SHA lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally with `Commit.where(sha: params.sha)` instead of scoping through the `stacks` helper (which filters by the payload's `repository.full_name`) as every other handler does. Because the webhook signature only proves the request comes from *some* org that owns a valid `webhook_secret` for the org named in the payload's `repository.owner.login`, but the commit/stack that actually receives the `Status` row is selected purely by SHA match across the entire `commits` table, an attacker with a legitimately signed webhook from their own org can create a `Status` row on a commit belonging to a completely unrelated stack/organization.

### Finding Description
The broken binding, as an equality: the code implicitly assumes
`commit.stack_id == stack_owned_by(repository_owner_that_signed_the_request)`
but the actual code guarantees no such thing — it only guarantees `commit.sha == params.sha`.

Trace:
1. `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, which only proves the *sender* controls that org's `webhook_secret`. [1](#0-0) [2](#0-1) 
2. The verified `params` are dispatched to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler`, with no further tie to the org that was verified. [3](#0-2) 
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global, unscoped** lookup by SHA, unlike `PushHandler`, `CheckSuiteHandler` and the `PullRequest` handlers, which all restrict to `stacks` (derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`). [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 
4. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, using `commit.stack_id` — the stack that actually owns that commit — regardless of which organization's webhook secret verified the request. [8](#0-7) 
5. `Status.replicate_from_github!` then writes/finds a `Status` row scoped to that unrelated `stack_id`. [9](#0-8) 

Exploit: attacker owns/controls a GitHub org "attacker-org" with its own repo installed on Shipit (so its `webhook_secret` is legitimate and known to the attacker's own GitHub App config). The attacker sends `POST /webhooks` with `X-Github-Event: status`, a signature valid for `attacker-org`, and body `{ "sha": "<victim_sha>", "state": "success", "context": "ci/travis", "repository": {"owner": {"login": "attacker-org"}} }`. If `victim_sha` matches any `Commit` row anywhere in the Shipit instance (e.g. from a public/OSS victim stack whose commit SHAs are visible on GitHub, or a fork sharing history with an unrelated stack), a `Status` is created against the victim's stack — completely bypassing any tenant boundary, since nothing in the code checks that `repository_owner` (the verified org) actually owns the repository/stack that the matched commit belongs to.

Existing guards do not prevent this: `verify_signature` only authenticates the *sender's own org*, not which stack the payload is allowed to affect; `drop_unhandled_event` passes `status` events through since a handler exists; the `ExplicitParameters` schema only validates types/shapes, not ownership; and `Status` model validations only check `state` inclusion/presence, not stack ownership. The `stacks` scoping helper that *would* have prevented this exists in `Handler` and is used by every sibling handler except `StatusHandler`.

### Impact Explanation
An attacker who is a legitimate operator of any GitHub org onboarded to this Shipit instance can inject fabricated CI `Status` rows (success/failure/pending/error, arbitrary `context`, `target_url`, `description`, `created_at`) into any other tenant's stack/commit, as long as they know or can obtain a matching commit SHA (trivial for public repos, forks sharing git history, or any commit whose SHA leaks e.g. via public CI logs, PRs, etc.). This can flip a victim commit's `state` to `success`, which per `Commit#add_status` can enqueue `ProcessMergeRequestsJob` and trigger continuous-deployment merge/deploy flows for a stack the attacker does not own — matching the "payload for one repository mutating another's stack/commit... or an unauthorized deploy" Critical category. It is fully repeatable against arbitrary stacks/commits, and blast radius spans every tenant on the shared Shipit instance since the lookup has zero repository scoping.

### Likelihood Explanation
Preconditions: the attacker only needs a Shipit-onboarded GitHub org they legitimately control (or any org whose `webhook_secret` they can obtain through normal, non-privileged GitHub App installation flow), plus knowledge of a target commit SHA — no victim secrets, sessions, or API tokens are required. This is a low-cost, highly repeatable attack: a single crafted POST per target commit, with signature computed using the attacker's own legitimate secret.

### Recommendation
Scope `StatusHandler#process` through the same `stacks` helper used by other handlers, restricting the query to commits belonging to stacks under `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the verified `repository_owner`/`repository.full_name` from the payload is the same repository whose stack(s) receive the `Status` row.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status event scoped to attacker org does not create Status on unrelated victim stack" do
          victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit)
          attacker_repo_full_name = "attacker-org/attacker-repo" # unrelated to victim_commit.stack

          payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/travis',
            'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker-org' } }
          }

          assert_no_difference -> { victim_commit.statuses.count } do
            StatusHandler.call(payload)
          end

          # Currently FAILS: StatusHandler.call creates a Status with
          # status.stack_id == victim_commit.stack_id even though the
          # verified/payload repository ("attacker-org/attacker-repo") is unrelated.
        end
      end
    end
  end
end
```
Binding assertion for the equality: before the fix, `Status.last.stack_id == victim_commit.stack_id` while `repository_owner_from_payload == "attacker-org"` and `victim_commit.stack.repository.owner != "attacker-org"` — proving the stack receiving the write is unrelated to the organization that verified the webhook signature.
