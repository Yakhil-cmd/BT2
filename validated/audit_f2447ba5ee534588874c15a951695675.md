## Analysis

The external report's bug class is: *a withdrawal function mandatorily bundles payment of the user's own principal together with payment of a reward that depends on a resource the contract does not fully control (an external wallet's balance/allowance); if that secondary, uncontrolled payment fails, the whole transaction reverts and the principal — which is otherwise fully available — becomes unreachable.*

This exact structural flaw is reproducible in ocore's Autonomous Agent (AA) execution model.

### Title
AA response atomicity lets an insufficient/uncontrolled secondary payment message permanently block an otherwise-payable principal payment in the same response - (File: aa_composer.js)

### Summary
`handleTrigger`'s `sendUnit()` in `aa_composer.js` composes all messages produced by a single AA response (e.g. a "return principal" payment and a "pay reward" payment) and processes them with `async.eachSeries`. If composing **any** payment message fails — for example because the AA does not hold enough of the reward asset at that moment — the whole flow calls `bounce(err)`, which discards all state changes and refunds nothing extra to the user, leaving the principal payment (which was fully fundable) undelivered.

### Finding Description
`sendUnit()` builds every payment message of an AA response and stops on the first failure: [1](#0-0) 

Inside `completePaymentPayload`, if the AA cannot gather enough spendable/issuable amount for a given asset output, it returns an explicit error instead of partially completing the payment: [2](#0-1) 

That error is propagated to the `async.eachSeries` final callback, which immediately calls `bounce(err)`: [3](#0-2) 

`bounce()` then rolls back **all** state variables and balances that were tentatively updated for the whole trigger, i.e. the entire response is discarded, not just the failing message: [4](#0-3) 

Consequently, any AA (e.g. a staking/vault AA implemented as an oscript, analogous to `DIAWhitelistedStaking`) that follows the common pattern of emitting, in one response, (1) a `payment` message returning the caller's principal and (2) a second `payment` message paying a reward funded from an asset balance the AA does not strictly control (a balance that can be exhausted, e.g. because rewards accrue faster than the AA is topped up, or because the reward asset is `issued_by_definer_only` by a third party) will have its principal payment blocked whenever the reward message cannot be composed. There is no mechanism in `sendUnit()`/`bounce()` to selectively drop only the failing message and still deliver the fundable one; the whole unit is bounced or nothing is sent.

### Impact Explanation
Any user who triggers such an AA to withdraw a principal that is otherwise fully backed by the AA's actual balance can be denied that principal indefinitely as long as the AA's reward-asset balance is insufficient — a state the ordinary user does not control and cannot fix (e.g. depends on other users' deposits, an external issuer, or accrual outpacing top-ups). This is a direct AA fund-freezing condition: user funds that are demonstrably present and spendable in the AA become permanently inaccessible through the withdrawal path, exactly mirroring the `unstake()`/`unstakePrincipal()` issue in the reported contract.

### Likelihood Explanation
This requires no attacker action beyond normal use of an AA authored with the common (and until now unremarkable) pattern of bundling a guaranteed payout with a conditional/variable one in a single response — a pattern explicitly supported and even shown as idiomatic in ocore's own AA samples that combine multiple `payment` messages/outputs per case. Any AA whose reward pool can be legitimately depleted (heavy but realistic operational condition, not an edge case) triggers the freeze automatically the next time a user tries to withdraw.

### Recommendation
- Document and strongly recommend (in AA authoring guidance / oscript best practices) that principal-return and reward-payment messages be split across independent trigger calls (e.g. `unstake` vs `claimReward`) rather than bundled in one atomic response, so a shortfall in reward funds cannot block already-earned principal.
- Consider providing/encourage an oscript pattern where the reward output is computed as `min(owed_reward, available_reward_balance)` so it degrades gracefully instead of causing the whole response (`bounce()` in `aa_composer.js`) to fail.
- At the framework level, no change to `sendUnit`/`bounce` atomicity is warranted (atomicity is a deliberate design guarantee), but the risk should be called out explicitly since it is not obvious from `aa_composer.js`'s behavior that a single under-funded output can void an otherwise fully payable message in the same unit.

### Proof of Concept
1. Deploy an AA whose `unstake` case, in one trigger response, emits:
   - message A: `payment` returning `trigger.data.amount` of `base` (the user's principal) to `trigger.address`.
   - message B: `payment` sending `var['reward_' || trigger.address]` of a reward asset to `trigger.address`, funded from the AA's reward-asset balance.
2. Have several users accrue reward-asset balances that exceed what remains in the AA's actual reward-asset holdings (e.g. because the reward asset is deposited externally and has been depleted, or because rewards were computed optimistically).
3. A user calls `unstake`; `sendUnit()` reaches message B, `completePaymentPayload` cannot gather enough of the reward asset, returns `"not enough funds for ... of asset ..."` (`aa_composer.js:1239`), the `async.eachSeries` callback invokes `bounce(err)` (`aa_composer.js:1346-1348`), which rolls back all balances/state (`aa_composer.js:909-945`).
4. Result: message A (principal payment), despite being fully fundable, is never sent — the user's principal remains locked in the AA until the reward-asset balance is separately replenished, with no alternative withdrawal path exposed by the AA's design.
