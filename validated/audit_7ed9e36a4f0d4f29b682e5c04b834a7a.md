### Title
Silent drop of AA "send-all" payment message on insufficient funds while state changes still commit — analog of `safeRewardTransfer` silent-loss pattern (`File: aa_composer.js`)

### Summary
In the Aura `ConvexMasterChef` finding, `safeRewardTransfer` silently sends less than the accounted amount (or nothing) when the contract is under-funded, while the depositor's accounting is not corrected — resulting in silent, non-reverting loss of funds. `aa_composer.js`'s AA response-composition logic (`sendUnit`/`completePaymentPayload`) has the same "silent short-transfer, no revert" pattern for `send-all` payment outputs: when an AA cannot cover a send-all output and self-issuance for send-all is disabled, the output — and potentially the whole payment message — is silently dropped, yet the AA still finalizes as a **successful** response and commits the `state` message's accounting changes as if the payment had gone through.

### Finding Description
An AA author writes a response formula with a `send-all` payment output (`{address: X}` with no `amount`) paired with a `state` message that updates bookkeeping (e.g., decrements a balance var, marks a claim as paid, records a payout). This is a supported, encouraged idiom (see `test/samples/payment_channels.oscript` "fraud proof" case: `outputs: [{ address: '{trigger.address}' }]`).

In `completePaymentPayload` (`aa_composer.js`), when the AA does not have enough of the asset to satisfy the send-all output and self-issuance is skipped for a lone send-all output: [1](#0-0) 
the function calls `sortOutputsAndReturn()`, which pulls the send-all output out of `payload.outputs` without any error: [2](#0-1) 

Back in the caller, if a payment message's outputs end up empty, the whole message is dropped, and if that empties out *all* messages, the trigger handling proceeds to `handleSuccessfulEmptyResponseUnit(null)` — a success path, not a bounce: [3](#0-2) 
This mirrors the identical "no messages after filtering" success path used elsewhere, which is explicitly documented as: "eat the received coins and send no response, **state changes are still performed**": [4](#0-3) 

Critically, this is not the same as the "not enough funds" case for ordinary (non send-all) outputs or for a send-all output that isn't the message's only output, which correctly propagate an error and cause `bounce()` — reverting all state changes: [5](#0-4) [6](#0-5) 

But the specific "lone send-all output, no self-issue" branch is carved out to *not* error, exactly like `safeRewardTransfer`'s "cap silently instead of reverting" behavior — the shortfall is invisible to the rest of the state-update logic, which has already computed `stateVars`/`response` under the assumption the payment message would be sent.

### Impact Explanation
Any AA whose response logic pays out with a `send-all` output as the sole output of a payment message (a documented, expected pattern — see `payment_channels.oscript`) is exposed: if the AA's tracked/available balance for that asset momentarily doesn't cover a positive amount (e.g., dust below `FULL_TRANSFER_INPUT_SIZE`, races with other still-unstable AA-to-AA transfers, or the asset genuinely has zero spendable UTXOs at that moment), the payout output is dropped entirely and no bounce occurs. The accompanying `state` message (balance debits, "already paid" flags, period/counter increments) still commits normally because these messages are computed via the AA's formula evaluation *before* `completePaymentPayload` decides funds are insufficient, and dropping the message from the `messages` array doesn't revert or re-evaluate `stateVars`. A trigger sender or counterparty relying on this AA can be marked as "paid" or have their claim balance zeroed without receiving the funds — a direct fund loss reachable purely by sending an ordinary trigger unit.

### Likelihood Explanation
Medium: this requires the AA design to combine a lone send-all output with irreversible state bookkeeping (a normal, documented pattern, as shown in the payment-channel sample), and requires the specific under-funded/self-issue-disabled condition to occur at that exact processing moment (e.g., transient balance dips from concurrently-processing but not-yet-stable AA outputs, or a genuinely zero balance being paid out as "send whatever remains"). It doesn't require attacker privilege beyond sending a normal trigger unit that causes the AA to reach this code path.

### Recommendation
Do not silently special-case the "lone send-all output" branch to swallow the shortfall. Instead:
- Either bounce (revert state) when a send-all output ends up with zero available funds and self-issuance is disallowed, consistent with how non-send-all shortfalls are already handled at `aa_composer.js:1231-1232` and `1236-1243`; or
- Make the "dropped output" condition observable to formula evaluation (e.g., re-run/adjust `stateVars` based on the actual sent amount) so accounting cannot diverge from what was actually transferred.

### Proof of Concept
1. Deploy an AA whose response is: `messages: [{app:'payment', payload:{asset:X, outputs:[{address:'{trigger.address}'}]}}, {app:'state', state:"var['paid_'||trigger.address] = true;"}]` (mirrors the `payment_channels.oscript` "fraud proof" pattern at lines 120–144 in `test/samples/payment_channels.oscript`).
2. Trigger the AA at a moment where its spendable balance of asset `X` is effectively 0 (e.g., right after the AA's only outputs of `X` have just been paid out/consumed, or where `mci >= aa3UpgradeMci` disables self-issue for the lone send-all output) so `completePaymentPayload` hits `aa_composer.js:1234-1235` and removes the send-all output, then `aa_composer.js:1349-1354` empties `messages` entirely.
3. Observe: `handleSuccessfulEmptyResponseUnit(null)` fires — the trigger is treated as a successful primary trigger, `var['paid_'||trigger.address] = true` is committed, but no payment output was ever produced, so the sender receives nothing while being marked "paid" in AA state.
