### Title
`MergeStatusController::ReferrerParser` derives repo scope from unauthenticated client-supplied `referrer` text, enabling cross-tenant stack status enumeration on `check`/`show` - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`MergeStatusController` skips authentication entirely for `check` and `show` (`skip_authentication only: %i[check show]`), and the `stack` lookup for those actions resolves the target repository purely from a regex match on the client-supplied `params[:referrer]` string via `ReferrerParser`, with no cross-check against any authenticated GitHub payload or the caller's authorization. This lets any unauthenticated (for `check`) or merely GitHub-OAuth-logged-in-but-unauthorized (for `show`) requester probe arbitrary `owner/repo` pairs and read that stack's merge status, bypassing the `Shipit.github_teams` authorization gate that normally applies to every other controller.

### Finding Description
The broken binding: the response for stack X (`stack_status`, i.e. `stack.merge_status`) should only be returned to a caller authorized on repository X (`current_user.authorized?` == true and repository X == the caller's authorized repository). Instead, the code computes `repo_owner`/`repo_name` as `equal to` `URL_PATTERN.match(params[:referrer])[1]`/`[2]` [1](#0-0)  — a value the client fully controls and which is never verified against any GitHub-signed payload, session data, or the caller's actual permissions.

Path:
1. `skip_authentication only: %i[check show]` removes the `force_github_authentication` `before_action` (which normally enforces `current_user.authorized?` against `Shipit.github_teams`) for these two actions. [2](#0-1) [3](#0-2) 
2. `stack` uses `referrer_parser.repo_owner`/`repo_name` (attacker-controlled) to query `Stack.includes(:repository).where(repositories: { owner: ..., name: ... })` and picks the production/branch-matching stack. [4](#0-3) 
3. `check` calls `stack_status` (`stack.merge_status(...)`) directly and renders it as plain text/JSON with **no login/authorization check whatsoever**. [5](#0-4) [6](#0-5) 
4. `show` requires only `current_user.logged_in?` (i.e. `session[:user_id]` maps to *any* `User` row) — it does not require `current_user.authorized?` (team membership), because that check lives inside the skipped `force_github_authentication`. [7](#0-6) [8](#0-7) 

Attacker request: `GET /merge_status/check?referrer=https://github.com/<guessed_owner>/<guessed_repo>/pull/1` (fully anonymous, no session), or `GET /merge_status?referrer=...` after completing an ordinary GitHub OAuth login that creates *any* `User` record (does not require team membership).

Existing guards that fail to prevent this: `force_github_authentication`'s `authorized?`/`Shipit.github_teams` check is bypassed by design via `skip_authentication`; there is no repository-level `require_permission!`/`check_permissions!` call in this controller (unlike `Api::BaseController#require_permission!`); `ReferrerParser` performs no signature or session validation, only a plain regex match on client text.

### Impact Explanation
An attacker (unauthenticated for `check`, or merely a self-registered GitHub OAuth user for `show`) can enumerate arbitrary `owner/repo` pairs hosted on the same Shipit instance and learn each stack's `merge_status` (`success`/`pending`/`locked`/etc.), and via `show`, the full repo-specific merge-status HTML/partial content — data intended only for callers authorized on that repository. This is a cross-tenant unauthenticated/under-authorized read of stack state, matching the High-severity category "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state." It is fully repeatable against every repository/stack on the instance since the only "check" is a client-supplied string.

### Likelihood Explanation
No secrets, tokens, or privileged roles are required for `check` — it is completely unauthenticated. For `show`, the attacker only needs to complete a normal GitHub OAuth login (which `GithubAuthenticationController#callback` performs for any GitHub identity, creating a `User` row regardless of team membership), a capability any GitHub account holder has. The attacker needs only to guess/know `owner/repo` names, which is realistic (public GitHub repos, or brute-forcing common org/repo names). Cost is a single HTTP GET per guess; fully repeatable and automatable.

### Recommendation
Require the same authorization as the rest of the app for `check`/`show`: verify `current_user.authorized?` (or an equivalent explicit repository permission check) before resolving/rendering `stack_status`, and/or require the caller to be a contributor/authorized user on the specific repository resolved from `referrer`. At minimum, do not allow `check` to run fully unauthenticated when it exposes repository-existence and merge-queue state for repos the caller has not been shown to have any relationship to.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb (conceptual addition)
module Shipit
  class MergeStatusControllerTest < ActionController::TestCase
    setup { @routes = Shipit::Engine.routes }

    test "#check leaks stack_status for arbitrary repos with no session at all" do
      session[:user_id] = nil # fully anonymous, unprivileged attacker

      Stack.all.includes(:repository).each do |stack|
        repo = stack.repository
        get :check, params: {
          referrer: "https://github.com/#{repo.owner}/#{repo.name}/pull/1",
          format: :json
        }
        assert_response :success
        body = JSON.parse(response.body)
        # Attacker with zero authentication learns this repo's real merge_status,
        # proving cross-tenant enumeration.
        assert_equal stack.merge_status(backlog_leniency_factor: 1.0), body['stack_status']
      end
    end
  end
end
```
This demonstrates the equality that should never hold for an unauthenticated caller — `response body's stack_status == stack.merge_status` for a repository the caller never authenticated against — matching for every fixture stack without any login.
