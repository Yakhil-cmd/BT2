### Title
Exact-equality "initial deposit" balance check can be griefed by dust donation (DoS/mispricing) - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The Autonomous Agent (AA) reference template `uniswap_like_market_maker.oscript` shipped in the ocore repository uses a strict equality test (`== 0`) on live AA balances to decide whether an incoming trigger is the "initial deposit" that sets the pool's starting price. An unprivileged AA trigger sender can permanently defeat this check by donating a trivially small (dust) amount of the paired asset or bytes to the AA address before the legitimate depositor's trigger is processed, mirroring the `BalLiquidityProvider` bug class where an exact-equality check on a contract's balance is griefed by a front-run/donation.

### Finding Description
In the "invest in MM" branch, the AA computes the pre-trigger balances and gates the initial-deposit logic on exact zero: [1](#0-0) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
```

`balance[$asset]` and `balance[base]` reflect the AA's current on-chain balances at the moment the trigger is processed, as maintained by `aa_balances` and updated by any payment sent to the AA address [2](#0-1) . Because any unit that pays the AA address (even a non-triggering "silently accept coins" style payment, or simply a tiny payment plus data) will update `aa_balances` before the target investor's trigger stabilizes, an attacker can keep `$asset_balance` or `$bytes_balance` from ever equaling exactly `0` by sending a minimal donation of the missing asset any time the pool balance approaches zero. This is directly analogous to the Aura finding, where `bal == _request.maxAmountsIn[i]` was defeated by sending 1 Wei to the pool before the liquidity provider's call landed — both rely on an attacker's ability to nudge a balance by a dust amount to break a strict equality gate that a legitimate, unprivileged party depends on.

### Impact Explanation
If the "initial deposit" gate can be permanently bypassed, the AA falls through to the ratio-based branch (`$current_ratio = $asset_balance / $bytes_balance; ...`) using a near-zero, attacker-influenced denominator/balance instead of treating the deposit as the price-setting first deposit. This can result in wildly distorted share issuance (`$issue_amount`) for the depositor, i.e. incorrect pricing that can cause immediate fund loss to the legitimate depositor or unfair dilution/inflation of the AA's `mm_asset` share token — a fund-loss/mispricing outcome, not merely a resource-exhaustion nuisance.

### Likelihood Explanation
The attack requires only the ability to send a minimal payment to a public AA address, something any unprivileged trigger sender can always do, and it can be repeated cheaply and indefinitely (bounded only by bounce-fee-sized payments) whenever the balance would otherwise reach exactly zero. No special privilege, timing precision beyond "before the target trigger stabilizes", or protocol-level access is needed, making this a low-cost, repeatable griefing/mispricing vector for any AA copying this common exact-equality "first depositor" idiom.

### Recommendation
Do not gate critical AA logic on exact equality to a live, externally-influenceable balance. Detect the "no prior liquidity" / initial-deposit state using AA-controlled state variables (e.g., a `var['initialized']` flag set once and never re-derived from `balance[...]`) rather than `$asset_balance == 0 OR $bytes_balance == 0`. More generally, any AA template distributed as guidance should avoid strict `==`/`!=` comparisons against `balance[...]`, `trigger.output[[...]]`-derived deltas, or other values a third party can nudge with a dust payment; use range/threshold comparisons or persisted flags instead.

### Proof of Concept
1. AA `uniswap_like_market_maker.oscript` is deployed with `mm_asset` defined and zero prior deposits (`balance[$asset] == 0`, `balance[base] == 0` net of the current trigger).
2. Attacker sends a minimal payment of `1` unit of `$asset` (or of `base`) directly to the AA address (a standalone payment, no `trigger.data.define`/invest intent needed) so that `aa_balances` for the AA now shows a non-zero `$asset` (or `base`) balance [3](#0-2) .
3. The legitimate investor then sends their intended initial deposit trigger (`trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0`).
4. Inside `init`, `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` and/or `$bytes_balance = balance[base] - trigger.output[[asset=base]]` are now non-zero due to the attacker's earlier dust payment, so `$asset_balance == 0 OR $bytes_balance == 0` is `false`.
5. Execution falls into the ratio branch, computing `$current_ratio`/`$expected_asset_amount` from the attacker-polluted, near-zero balances, producing a distorted `$issue_amount` for the legitimate depositor instead of the intended one-time initial-price-setting path.
