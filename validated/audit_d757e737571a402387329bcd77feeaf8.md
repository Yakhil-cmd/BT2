### Title
Cross-repository webhook forgery via decoupled signature-authentication and payload-authorization fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret authenticates an incoming webhook based on the `repository.owner.login` field taken from the same untrusted JSON body it is about to verify, while every `Handlers::Handler` subclass (used for `push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) decides *which Shipit `Repository`/`Stack` to mutate* using a different field from that same body: `repository.full_name`. Nothing binds these two fields together, so a party who legitimately controls the webhook secret for one configured GitHub organization can forge a payload whose `repository.full_name` points at a completely different organization's stack.

### Finding Description
`Shipit.github(organization: repository_owner)` picks a `GitHubApp` instance (and therefore a distinct `webhook_secret`, since `GitHubApp#initialize` stores `@webhook_secret = @config[:webhook_secret]` per organization) using: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature is verified with `github_app.verify_webhook_signature(header, raw_post)`, i.e. HMAC over the *whole* body using the secret selected by `repository_owner`: [3](#0-2) 

Once verification passes, `WebhooksController#create` dispatches the parsed body to handlers unchanged: [4](#0-3) 

Every handler resolves the target repository/stack from a *different* field of the same body: [5](#0-4) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, for example, uses this to enqueue a sync against whatever stacks match `repository_name`, using an attacker-supplied `after` SHA: [6](#0-5) 

Because `repository.owner.login` (used for *authentication*) and `repository.full_name` (used for *authorization*, i.e., which stack is acted on) are independent, attacker-controlled fields inside the same signed body, the equality that Shipit implicitly relies on — "the organization whose secret signed this payload" == "the repository this payload is about" — is never enforced. An actor who legitimately owns/administers **any** GitHub organization configured in this Shipit instance (and therefore legitimately knows that organization's `webhook_secret`) can set `repository.owner.login` to their own org (so their own valid secret is selected and the HMAC check passes) while setting `repository.full_name` to `victim-org/victim-repo`. The forged, correctly-signed payload is then processed by handlers as if it originated from the victim repository.

### Impact Explanation
This breaks the binding between "organization authenticated" and "repository written," matching the report's bug class (a field acted upon that isn't covered by the trust boundary it is presumed to satisfy). Concretely, an actor holding only their own org's webhook secret can:
- Trigger `GithubSyncJob`/`stack.sync_github` for a victim's stack with an attacker-chosen `expected_head_sha` via the `push` event.
- Forge `status`/`check_suite` events that fabricate commit statuses or check results for a victim's stack/commit, which can influence merge/deploy readiness gates.
- Trigger `pull_request`/`membership` handlers against a victim's repository/team.

Since deploy readiness and merge automation in Shipit are driven by commit statuses and stack state, forged statuses/syncs for a repository the attacker does not control can lead to an unauthorized deploy or corrupted deployment state for that stack — a cross-repository write into Shipit's own data model performed by an unprivileged external party. This aligns with the "High" impact class (escalation of webhook trust across repository boundaries; unauthenticated manipulation of stack/task state).

### Likelihood Explanation
Exploitability requires that the Shipit deployment is multi-tenant (multiple GitHub organizations each configured with their own webhook secret) — a documented, supported configuration, evidenced by the `GithubOrganizationUnknown` handling for unrecognized organizations: [7](#0-6) 

Any party that operates their own onboarded organization (which is by design an unprivileged, self-service action in a multi-tenant Shipit instance) can obtain a valid webhook secret for that org and use it to forge cross-organization payloads. No Shipit session, API token, or GitHub write access to the victim repository is required.

### Recommendation
After signature verification, cross-check that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to handlers. Reject the webhook if they disagree. Alternatively, resolve the target `Repository`/`Stack` strictly from the same identity that was used to select the verifying secret, rather than trusting a second, independently-controlled field of the payload.

### Proof of Concept
1. Attacker controls GitHub organization `attacker-org`, which is configured in this Shipit instance with its own `webhook_secret` `S_A` (multi-tenant setup).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` (a secret they legitimately possess) and POSTs to `/webhooks`.
4. `repository_owner` resolves to `attacker-org`, so `Shipit.github(organization: 'attacker-org')` selects the attacker's own `GitHubApp`, whose `verify_webhook_signature` succeeds because the attacker signed with their own valid secret. [1](#0-0) 
5. `PushHandler#process` (via `Handler#repository_name`) resolves the stack from `repository.full_name` = `victim-org/victim-repo` and enqueues `sync_github(expected_head_sha: params.after)` for the victim's stack — despite the request never being signed by anything belonging to `victim-org`. [5](#0-4) [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
