### Title
Malicious secondary AA can force any primary AA to revert, DoS'ing payouts to attacker-controlled addresses - (File: `aa_composer.js`)

### Summary
`handleTrigger()`'s `handleSecondaryTriggers()` treats any payment output sent by a primary AA to another AA address as a synchronous "secondary trigger" call into that AA. If the secondary AA's own execution bounces for any reason, the error is bubbled up and the *entire primary AA execution is unwound* via `revert()`. Because any user (borrower, counterparty, seller, etc.) can pre-compute and register an AA address that is designed to always bounce, and then present that address as the destination that a victim AA (e.g., a lending, auction, or marketplace AA) will pay, that user can make every legitimate trigger that would result in a payout to them permanently fail — exactly analogous to the Solidity `receive()`-revert DoS in the referenced report.

### Finding Description
When a primary AA composes a payment message whose output address belongs to another AA, `handleSecondaryTriggers()` invokes `handleTrigger()` recursively for that address with `bSecondary = true`: [1](#0-0) 

If the secondary AA's execution bounces (e.g., because its `messages` evaluate to nothing, a formula throws, a condition fails, or it purposefully has no valid response), its `onDone` callback returns a `bounce_message`, which is converted into an `err` passed to `async.eachSeries`'s final callback: [2](#0-1) 

When that `err` is present and the *primary* AA (not itself secondary) is executing, the code calls `revert()`, which restores balances/state, deletes all previously accumulated responses in `arrResponses`, rolls back the DB savepoint, and finally calls `bounce()` on the primary trigger — i.e., the whole primary AA's business logic for this trigger is discarded and the caller's unit is bounced: [3](#0-2) 

This is structurally identical to the reported Solidity issue: a party that controls the destination address of a payment made by privileged/critical logic (auction settlement, loan repayment/liquidation payout, marketplace settlement, etc.) can make that destination reject/fail the "receive," and this failure propagates back to void the entire operation rather than being isolated to the recipient. In ocore, the "receive" equivalent is an AA definition that is guaranteed to bounce (e.g., one whose `messages` template always evaluates to an empty list, or that always fails a formula check), and the "push payment" is any payment output of a primary AA directed at an address that happens to be (or is later turned into) an AA.

Any user can:
1. Compute the deterministic AA address for a definition that is guaranteed to bounce (e.g., `{ messages: [{ app: 'payment', if: 'false', payload: {...} }] }`, which evaluates to "no messages after filtering" and bounces).
2. Post that AA definition to the network in advance (as allowed by `checkNotAAs`/AA address registration flow) or ensure it becomes an AA before the victim AA tries to pay it.
3. Present this address as the counterparty/borrower/recipient address for a victim AA (a lending, auction, escrow, or marketplace-style AA) that will later attempt to pay funds to that address as part of settlement logic.
4. Whenever any legitimate user triggers the victim AA's settlement logic (which includes a payment output to the attacker's bounce-always AA as a secondary trigger), the secondary trigger bounces, causing `revert()` to unwind the entire primary trigger — the victim AA's payout/settlement never completes, and the caller's own trigger is simply bounced back (minus bounce fee).

### Impact Explanation
This allows an unprivileged attacker to permanently block completion of any AA-based protocol operation that pays out to an address the attacker controls, as long as that address is (or can be made) an AA. Practical impact:
- Escrow/marketplace/lending-style AAs that pay proceeds to a seller/borrower/counterparty address chosen by that counterparty can be indefinitely stalled by the counterparty itself, exactly mirroring the original finding's "lender can never liquidate/settle" scenario.
- Funds and state remain stuck in the victim AA (locked), and no other party calling the AA can force settlement, because every attempt reverts identically.
- The attack has effectively no cost to the attacker (bounce fees are only charged to the *original trigger sender*, not to the secondary AA that intentionally bounces), so it can be repeated indefinitely.

This maps to concrete "AA fund loss or freezing" and a legitimate operation ("a network unable to confirm new units" performing the intended state transition) being permanently blocked, matching the Medium/High bar.

### Likelihood Explanation
Any address used as a payment recipient by a primary AA (counterparty address, borrower address, bidder address, etc.) is attacker-supplied or attacker-influenced in many realistic AA designs (loans, auctions, marketplaces where the counterparty's own address receives the payout). Turning an address into an "always-bounce" AA is trivial and cheap (a minimal `oscript` definition), and the recursive secondary-trigger/`revert()` mechanism in `aa_composer.js` is a core, unconditional part of AA execution — there's no way for an AA author to opt out of this behavior for arbitrary payment outputs. Likelihood is High.

### Recommendation
Do not allow a failure of a secondary AA trigger to unconditionally void the primary AA's already-computed state changes and payments. Options:
- Treat payments to AA addresses that are not explicitly expected to be called back (i.e., plain payouts, not intentional AA-to-AA calls) as simple, unconditional transfers that do not trigger secondary execution recursion when they fail, or isolate the failure so only the secondary AA's *own* balance/state is affected (already partially attempted by restricting bounce-fee refunds to the secondary AA), rather than calling `revert()` on the whole primary chain.
- Alternatively, let AA authors mark payments as "fire-and-forget" (never propagate a bounce upward), or require that secondary-trigger failures only cause a same-behavior "bounce" of the fraction of funds sent to that specific address, without unwinding the entire primary trigger's other state changes and payments to unrelated addresses.

### Proof of Concept
1. Attacker publishes AA `Bouncer`:
```
{
  messages: [
    { app: 'payment', if: "{false}", payload: { asset: 'base', outputs: [{address: "{trigger.address}", amount: "{trigger.output[[asset=base]]}"}] } }
  ]
}
```
This AA's `messages` filter always removes the only message (because `if` is always false), so any trigger to it hits "no messages after filtering" → `handleSuccessfulEmptyResponseUnit` → if the only entry has no state changes, it still eventually calls `bounce(...)`; more directly, craft the definition so it deterministically bounces (e.g. `bounce_fees: { base: 999999999 }` with insufficient trigger output, or a formula that throws), guaranteeing `bBouncing = true` for every trigger.
2. Attacker interacts with a victim AA (e.g., a lending/escrow AA) supplying `Bouncer`'s address as the borrower/counterparty/recipient address stored in the AA's state vars.
3. Later, any user (lender, other party) triggers the victim AA's settlement/payout logic, which composes a `payment` message whose output goes to `Bouncer`'s address.
4. `handleSecondaryTriggers()` at `aa_composer.js:1702-1756` invokes `Bouncer` as a secondary trigger; it bounces, producing an `err`.
5. Because the caller AA is primary (`bSecondary === false`), `revert()` (`aa_composer.js:1759-1783`) is invoked: all state var changes and responses for the settlement are discarded, and the whole trigger simply bounces back to its sender.
6. Every subsequent attempt to settle/pay the victim AA's operation to that address fails identically, permanently freezing the associated funds/state — reproducing the referenced report's DoS at the AA layer.
