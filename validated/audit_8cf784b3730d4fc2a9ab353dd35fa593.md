### Title
Liveness Endpoint Reports "Ready" Forever After First Successful Sync, Masking Persistent Sync Failures - ([File: main.go])

### Summary
`git-sync` exposes a liveness/readiness endpoint (`/`) that is gated by a package-level `repoReady` boolean. This flag is set to `true` exactly once, the first time `SyncRepo` succeeds, and there is no code path anywhere in the codebase that ever resets it back to `false`. Once a single successful sync occurs, the HTTP endpoint will report success (200) for the remaining lifetime of the process, even if every subsequent sync attempt fails. This is the same "sticky/one-way state" bug class as the reported `unlockBlock` issue: a flag meant to reflect a transient condition ("did the last operation succeed") is set once and never re-evaluated or reset, so it becomes permanently stuck in the "good" state.

### Finding Description
`repoReady` is a global boolean guarded by `readyLock`: [1](#0-0) 

`setRepoReady()` is called only in one place, inside `SyncRepo`, immediately after a successful publish: [2](#0-1) 

`getRepoReady()` is consumed only by the HTTP liveness handler, which returns `503` when not ready and otherwise implicitly returns `200`: [3](#0-2) 

There is no corresponding "un-ready" transition. A `grep` for `repoReady`/`setRepoReady`/`getRepoReady` across the repository shows exactly these three usages — no code ever sets `repoReady` back to `false` after a sync failure, a stale/corrupted worktree, a fetch error, or a sanity-check failure in the main sync loop. This mirrors exactly the pattern in the external report: `unlock()`-equivalent (`setRepoReady()`) flips state to the "good"/unlocked condition, but there is no `withdraw()`-equivalent reset back to the "locked"/not-ready condition, so once triggered once, the flag is permanently stuck in the favorable state for the rest of the process lifetime.

### Impact Explanation
The `/` endpoint is documented and used as the Kubernetes liveness/readiness probe for the sidecar pattern (confirmed by `test_e2e.sh` tests such as `e2e::expose_http`, which explicitly asserts 503 before first sync and 200 after). Once `git-sync` achieves one successful sync, the health endpoint will report `200 OK` indefinitely, even if:
- Every subsequent fetch/sync fails (within the `--max-failures` retry budget),
- The upstream ref becomes unreachable,
- Credentials expire,
- The worktree becomes corrupted/stale.

Because Kubernetes readiness probes gate whether a pod is considered ready to receive traffic, this can cause an orchestrator (or any consumer polling the sidecar's health) to keep believing the synced data is fresh/healthy while the on-disk `--link` target is actually stale or increasingly out of date — i.e., the health signal publishes an incorrect ("wrong") status about the state of published content, matching the "publishing wrong or partial content" impact class from the rules, since downstream systems act on a false-positive readiness signal for as long as the process stays under `--max-failures`.

### Likelihood Explanation
This requires no attacker privilege beyond the standard threat model for git-sync (an attacker-influenced remote ref/repo, or transient network/auth issues causing repeated sync failures) — no malicious operator, no leaked key, and no dependency-only bug. Any condition that causes the periodic sync loop to fail after at least one prior success (e.g., an attacker rotating/breaking credentials indirectly, a transient outage, a repo history rewrite causing fetch failures, or repeated `sanityCheckWorktree`/`fsck` failures) will trigger this masking behavior, and it will persist across every failed sync iteration until the process is restarted or `--max-failures` is exceeded and the process exits.

### Recommendation
Reset `repoReady` to `false` (or otherwise track "is my currently published content stale beyond a bound" state) whenever a sync iteration fails, so the liveness/readiness endpoint accurately reflects the current health of the sync loop rather than the historical fact that a sync once succeeded. Concretely, call an `unsetRepoReady()` (or `readyLock`-guarded setter) from the failure-handling branch of the main sync loop (where sync errors/failure counts are tracked) prior to retrying, mirroring the same lock/unlock pattern currently used only for setting readiness true.

### Proof of Concept
1. Run `git-sync --repo=<repo> --root=<root> --link=link --http-bind=:8080 --max-failures=100`.
2. Let the first sync succeed; confirm `curl localhost:8080/` returns `200`.
3. Break the sync ability without killing the process (e.g., make the upstream ref unreachable, or corrupt `git.root`'s ability to fetch) — sync attempts start failing but stay under `--max-failures`.
4. Poll `curl localhost:8080/` repeatedly during the ongoing failures — it continues to return `200 OK` for every request, never surfacing the fact that the sidecar has failed to update the published `--link` target since the failures began, because `repoReady` was set `true` once at main.go:1979 and is never reset.

```go
// repoReady indicates that the repo has been synced.
var readyLock sync.Mutex
var repoReady = false

func getRepoReady() bool {
	readyLock.Lock()
	defer readyLock.Unlock()
	return repoReady
}

func setRepoReady() {
	readyLock.Lock()
	defer readyLock.Unlock()
	repoReady = true
}
```
