### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup enables out-of-order/stale deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` applies an incoming GitHub `status` webhook to every `Commit` row in the entire database that shares the payload's `sha`, without verifying that the commit actually belongs to the repository the webhook claims to originate from. Because git commit SHAs are content-addressed and portable across repositories, an attacker who controls any repository onboarded to the same Shipit instance can forge a `success` status on a *different* stack's stale/older commit, causing `Stack#next_commit_to_deploy` / `Stack#next_expected_commit_to_deploy` to select that stale commit for deployment.

### Finding Description
Broken binding: `status applies only to Commit rows whose stack.repository == payload.repository` should equal `Commit.where(sha: params.sha)` (all commits with a matching sha, across all stacks/repositories).

Code path:
- `app/controllers/shipit/webhooks_controller.rb#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event('status')`, after `verify_signature` confirms the payload is *validly signed for the organization named in the payload* (`Shipit.github(organization: repository_owner)`), see [1](#0-0) . This only proves the webhook genuinely came from GitHub for that org/repo — it says nothing about which `Commit` rows in Shipit's database the sha is allowed to affect.
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This is a global, unscoped lookup across the whole `commits` table, ignoring `Handler#stacks` (repository-derived scope) entirely. Compare with `PushHandler` and `CheckSuiteHandler`, both of which properly scope through `stacks` (derived from `payload.dig('repository', 'full_name')`) before touching any commit: [3](#0-2) [4](#0-3) . The base `Handler` class exposes exactly this scoping helper: [5](#0-4)  but `StatusHandler` doesn't use it.
- The uniqueness constraint on commits is deliberately `(sha, stack_id)`, not `sha` alone: [6](#0-5) , confirming the same sha is expected to exist across multiple stacks/repositories legitimately (forks, mirrors, multi-env stacks) — which is exactly why the status write must be repository-scoped and currently isn't.
- `Commit#create_status_from_github!` -> `add_status` writes a `Status` row scoped to `commit.stack_id` (the victim's stack) with attacker-controlled `state`/`description`/`target_url`/`context`, and triggers `stack.schedule_merges` and continuous delivery: [7](#0-6) , [8](#0-7) .
- This state feeds `Commit#deployable?`/`active?` [9](#0-8) , which is consulted by `Stack#next_expected_commit_to_deploy` (`commits.reject(&:active?)` then `find(&:deployable?)`) [10](#0-9)  and `Stack#next_commit_to_deploy` (`deployable_commits(commits_to_deploy)` over `commits.order(id: :asc)`) [11](#0-10) .

Attacker's exact action: attacker owns (or has push access to) some repository that is registered as a Shipit stack on the same Shipit instance (self-service onboarding is common; this need not be the victim's repository or org). They create a commit object identical in content (tree, parents, author/committer, timestamps, message) to a genuine older/stale commit that exists in the victim stack, so its SHA matches. They then call GitHub's own Status API against their own repository for that sha (an action fully within their own repo's privileges), which causes GitHub to deliver a genuinely signed `status` webhook to Shipit's `POST /webhooks`. `verify_signature` passes because the payload's `repository.owner.login` matches the attacker's own onboarded org, whose secret they legitimately used via a real GitHub delivery. `StatusHandler#process` then attaches the forged `success` status to the sha match in the victim's stack as well, because the lookup is global.

Existing guards fail because: `verify_signature` only authenticates "this event genuinely came from GitHub for repository X's org," not "this sha belongs to repository X." `drop_unhandled_event` and `ExplicitParameters` schema only validate presence/shape of `sha`/`state`, not repository ownership. No model validation ties a `Status` write to the `repository.full_name` in the payload.

### Impact Explanation
A successful forgery causes Shipit to mark a foreign, attacker-chosen commit in a completely unrelated stack/repository as `success`, which can make that commit `deployable?` and be selected by `next_commit_to_deploy`/`next_expected_commit_to_deploy`, resulting in Shipit deploying stale or out-of-order code for a repository the attacker never authenticated against or had access to. This is a payload for one repository mutating another's commit/stack state and can trigger an unauthorized/incorrect deploy — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It's repeatable against any stack/repository tracked by the same Shipit instance, as long as the attacker can produce (or already knows) a commit with a colliding sha reachable in the victim stack (e.g., by literally recreating the exact same historic commit object, which is trivial for public/known commits, or forking upstream so the commits are literally shared).

### Likelihood Explanation
Preconditions: a multi-tenant Shipit deployment where more than one team/repository is onboarded (typical for Shopify-style internal Shipit installs); attacker needs write/admin access to at least one such onboarded repository (their own), and a victim stack with an older/stale commit the attacker knows the sha of (trivial if it's a public commit, or if attacker forked/shares history with the victim repo). No Shipit secrets, sessions, or API tokens are required — only ordinary GitHub repository ownership and the ability to set commit statuses via the GitHub API on a repo the attacker controls, which any onboarded team member/attacker-owned repo naturally has. This is directly repeatable per victim commit/stack.

### Recommendation
Scope `StatusHandler#process` through the payload's own repository, exactly like `PushHandler`/`CheckSuiteHandler` do, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so that a status can only ever be applied to commits belonging to the repository that GitHub actually attributed the event to.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or extending `test/models/shipit/stack_test.rb`):
1. Create two stacks/repositories, `victim_stack` (repository `victim/repo`) and `attacker_stack` (repository `attacker/repo`), each with its own `Repository`.
2. In `victim_stack`, create an older undeployed commit `stale_commit` (no successful status) and a newer commit `fresh_commit` with a genuine `success` status.
   - Assert baseline: `victim_stack.next_commit_to_deploy == fresh_commit` (or nil if fresh_commit not yet passing) and `stale_commit.deployable? == false`.
3. In `attacker_stack`, create a commit `forged_commit` with `sha == stale_commit.sha` (simulating a duplicate/forked commit object), no status yet.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => stale_commit.sha, 'state' => 'success', 'repository' => { 'full_name' => 'attacker/repo' }, ...)` directly (bypassing signature verification, which is orthogonal — the point is that a legitimately-signed event for `attacker/repo` reaches this code).
5. Assert both sides of the binding:
   - Before: `stale_commit.reload.deployable? == false`.
   - After: `stale_commit.reload.deployable? == true` (forged), demonstrating `Commit.where(sha:)` wrote a `Status` onto a commit outside the event's own repository.
   - `victim_stack.next_commit_to_deploy == stale_commit` (older commit wins) instead of the true chronological candidate `fresh_commit`, proving out-of-order deploy selection caused purely by the cross-repository forged status.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
