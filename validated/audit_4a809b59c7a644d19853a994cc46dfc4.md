### Title
Silent-donation griefing of AA pool balances skews `balance[asset]`-based share/ratio formulas - ([File: aa_composer.js])

### Summary
Autonomous Agents (AAs) that compute shares, exchange ratios, or payout amounts from the live `balance[asset]`/`balance[base]` values (e.g. AMM-style or pool-style AAs such as `test/samples/uniswap_like_market_maker.oscript`) are vulnerable to the same class of bug reported in the Sherlock Surge Pool.sol issue: any user can inflate the pool's tracked balance without going through the code path that records a corresponding share issuance, causing subsequent legitimate depositors to receive fewer shares/tokens than expected.

### Finding Description
Every unit sent to an AA address is processed as a trigger, and the AA's balance is credited from the unit's outputs before the AA logic runs, via `updateInitialAABalances`/`updateFinalAABalances`, which are backed by the `aa_balances` table read by the `balance[...]` formula operator: [1](#0-0) .

Normally, if a trigger fails to match any of the `if` conditions in a `cases` construct, the AA bounces the trigger and refunds the sender (minus the bounce fee), so the balance is not left permanently inflated: [2](#0-1) . However, for AAs that use a flat `messages: [...]` array with per-message `if` conditions (rather than `cases`), a trigger that fails every message's `if` results in an empty `messages` array after filtering. In that situation ocore does **not** bounce the funds back — it explicitly "eats" them and treats it as a successful, silent state transition: [3](#0-2)  and [4](#0-3) .

This means an attacker can craft a trigger (e.g. a bare payment with no accompanying `data`, or with `data` deliberately chosen so no conditional payment message matches) that is accepted into the AA's `balance[asset]`/`balance[base]` accounting without any of the AA's own bookkeeping logic running to record the deposit against a share/ownership variable. Any other AA logic that later uses `balance[$asset]` or `balance[base]` directly as the denominator/numerator of a ratio — exactly as done in `test/samples/uniswap_like_market_maker.oscript` (`$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]`, `$current_ratio = $asset_balance / $bytes_balance`, `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`) — will compute skewed values, because the pool's real balance no longer matches the value implied by the tracked `var['mm_asset_outstanding']`/state variables.

### Impact Explanation
This is directly analogous to the reported `tokenToShares` griefing attack: an attacker permanently and cheaply distorts the balance-to-shares/ratio relationship of any AA pool contract that relies on `balance[asset]` for accounting instead of an explicitly maintained state variable for "total deposited." Legitimate depositors who invest right after such a donation receive fewer shares (or worse exchange rates) than the formula intends, and the attacker (or a colluding party) can subsequently redeem at the manipulated ratio, extracting value from other depositors. Because AAs manage real, fungible funds (bytes and issued assets), this can lead to concrete loss of user funds within any pool/AMM-style AA built on this common pattern.

### Likelihood Explanation
This requires only posting an ordinary payment unit to a target AA's address with inputs chosen so that none of its flat, `if`-guarded messages match — no special privileges, hub/node cooperation, or timing dependency beyond simple front-running of a victim's deposit transaction. Any unprivileged user can construct and send such a trigger.

### Recommendation
- AA authors relying on pool ratios should maintain an explicit state variable for "total deposited"/"total balance" instead of reading `balance[asset]` directly, updating it only through the deposit/withdraw code paths (this is a documentation/best-practice fix for AA authors, not a core bug).
- At the core level, consider making the "no messages after filtering" fallback for flat `messages` arrays bounce (refund) the trigger by default instead of silently accepting the funds, matching the behavior of the `cases` construct, so unmatched deposits cannot be silently absorbed into an AA's balance without any accounting.

### Proof of Concept
1. Deploy an AA modeled on `test/samples/uniswap_like_market_maker.oscript` pattern but using a flat `messages: [...]` array with `if` guards per message (instead of `cases`), where the "invest" message requires `trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0`.
2. Attacker sends a trigger unit with `trigger.output[[asset=$asset]] = smallAmount` and `trigger.output[[asset=base]] = 0` (or any combination that fails every message's `if`).
3. Per `aa_composer.js` lines 1868-1877, `messages` filters to empty, `handleSuccessfulEmptyResponseUnit` runs, and the funds are kept in `aa_balances` for the AA address, incrementing `balance[$asset]` — with no state variable updated to reflect this deposit.
4. A victim then calls "invest in MM" with a correct ratio computed against the pre-donation state, but the actual `balance[$asset]`/`balance[base]` used in the formula already includes the attacker's undocumented donation, causing `$current_ratio` and thus `$issue_amount` to be skewed, so the victim receives fewer/more `mm_asset` shares than the fair value of their contribution.
