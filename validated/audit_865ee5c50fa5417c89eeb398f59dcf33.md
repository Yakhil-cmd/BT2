### Title
Denial of Service via Uncaught Exception in Header Commission Size Validation - (File: validation.js)

### Summary
CVE-2017-11524 describes ImageMagick's `WriteBlob` crashing the process via an unhandled assertion failure triggered by a crafted file, before any authorization/consistency check runs. `ocore` has an analogous defect: the size-validation call for a unit's headers, `objectLength.getHeadersSize(objUnit)`, is invoked from `validate()` without a `try/catch`, while the structurally identical sibling call for payload size, `objectLength.getTotalPayloadSize(objUnit)`, immediately below it *is* wrapped in a `try/catch`. A malicious, unprivileged unit poster can trigger an uncaught exception inside `getHeadersSize` before author/message content has even been structurally validated, crashing/aborting joint processing.

### Finding Description
`validation.js` computes and checks the header size early in `validate()`, before `validateAuthors()` runs: [1](#0-0) 

`getHeadersSize()` calls `getLength()` on a clone of the unit with `messages`, `unit`, and the commission fields stripped out, but `authors` (and other yet-unvalidated fields) remain in the object: [2](#0-1) 

`getLength()` (and its recursive `_getLength`) throws plain `Error` in several cases reachable from attacker-controlled JSON content that has not yet been type-checked by `validateAuthors`/`validateMessages`, most notably a non-finite number (JSON literals such as `1e400` parse to `Infinity` in V8): [3](#0-2) 

Because `authors` is still fully attacker-controlled at the point `getHeadersSize` is invoked (the authors-array structural check and `validateAuthors` happen later, at lines 271 and in the `async.series` at line 437), a unit whose `authors` contains a deeply nested numeric field like `1e400` (e.g., inside `authentifiers` or `definition`) causes `getLength` to `throw Error("invalid number: Infinity")`. This exception is **not caught** at the `getHeadersSize` call site, unlike the immediately following `getTotalPayloadSize` call: [4](#0-3) [5](#0-4) 

The exception propagates out of the synchronous portion of `validate()`, out through `network.js`'s `validate` wrapper, which invokes `validation.validate()` with no surrounding `try/catch`: [6](#0-5) 

The code comment right before this call explicitly acknowledges that validation "otherwise ... crashed", indicating this crash path is a known, only partially mitigated hazard (host is quarantined, but the in-flight mutex-held validation work is aborted uncleanly): [7](#0-6) 

### Impact Explanation
This is a network-reachable Denial of Service: any peer or any unprivileged unit poster can broadcast (or POST via `light/...`) a syntactically valid but crafted unit whose `authors` structure contains a numeric literal that parses to `Infinity`. This throws before author/message validation completes, aborting the `mutex.lock(['handleJoint'], ...)` critical section for joint validation without going through the normal `ifUnitError`/`ifJointError` callbacks, unlike every other rejection path in `validate()`. Repeated submissions can be used to repeatedly disrupt the validation pipeline, matching the CVE's "assertion failure and application exit" DoS class, mapped here to an uncaught-exception DoS in a core validation routine reachable from a single posted unit.

### Likelihood Explanation
High reachability, moderate exploitation effort: no authentication or special privileges are needed—only the ability to submit or relay a unit. The crafted numeric literal (`1e400`-style) is trivial to construct. The asymmetric try/catch handling around `getHeadersSize` vs. `getTotalPayloadSize` strongly indicates this is an unintentional gap rather than a deliberately accepted risk.

### Recommendation
Wrap the `objectLength.getHeadersSize(objUnit)` call in `validation.js` with the same `try/catch` pattern already used for `getTotalPayloadSize`, converting any thrown error into `callbacks.ifJointError(...)` instead of letting it escape as an uncaught exception. Additionally, consider validating that all numeric leaf values in `objUnit` are finite JSON numbers as an early, generic sanity check before any size/hash computation is attempted on attacker-controlled substructures like `authors`.

### Proof of Concept
1. Craft a unit whose `authors` array includes a nested numeric field with an out-of-range JSON number literal, e.g.:
```json
{
  "authors": [{
    "address": "SOME_VALID_ADDR",
    "authentifiers": { "r": 1e400 }
  }],
  ...
}
```
2. Post/broadcast this joint so it reaches `network.js`'s `handleJoint` → `validate()` → `validation.validate(objJoint, ...)`.
3. During the synchronous header-size check, `objectLength.getHeadersSize(objUnit)` calls `getLength()`, which encounters the `Infinity` value and executes `throw Error("invalid number: Infinity")` at [8](#0-7) . Since the enclosing call at [4](#0-3)  has no `try/catch`, the exception is uncaught inside the `mutex.lock` callback invoked from [9](#0-8) , aborting normal error handling/callback flow for that validation attempt.
