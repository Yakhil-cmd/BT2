### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a signed status webhook overwrite CI state for commits in unrelated repositories - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no filter on `payload['repository']['full_name']`, and writes a `Status` to every matching `Commit` row regardless of which repository the row belongs to. Every other handler in this engine (via `Handler#stacks`) explicitly scopes to `Repository.from_github_repo_name(repository_name)`, but `StatusHandler` bypasses that helper entirely.

### Finding Description
The invariant that should hold is: `status.repository_name == commit.stack.repository.full_name` for every `Status` row created from a webhook. In `StatusHandler#process`: [1](#0-0) 

the code does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no join/filter against `payload.dig('repository', 'full_name')`. Compare this to the base class helper that every other handler uses: [2](#0-1) 

`stacks` explicitly resolves `Repository.from_github_repo_name(repository_name)` before touching any records, but `StatusHandler` never calls `stacks` at all — it goes straight to a global `Commit` query keyed only by `sha`.

`create_status_from_github!` then creates a `Status` and, via `add_status`, can flip `deployable_status`/schedule merges for whatever stack that `Commit` belongs to (`app/models/shipit/commit.rb` `add_status`, lines ~366-386), which is repository-agnostic once triggered.

Exploit precondition: `sha` is a git object id computed over an entire commit (tree, parents, author/committer identity and timestamps, message). It is not attacker-forgeable to collide with an unrelated commit's content, but it is trivially reproduced if the attacker's repository shares git history with the victim's — the canonical case is forking the victim's (often public) repository. If both the victim's stack and the attacker's fork sit in an organization for which `Shipit.github(organization: repository_owner)`'s signature check passes (i.e., the attacker has push/PR access to *any* repository under an org already onboarded to the same GitHub App/webhook secret as the victim's stack), a genuine, GitHub-signed `status` event from the attacker's own repo/branch (e.g., their fork's CI reporting `context: ci/e2e`, `state: success`) will pass `verify_signature` (which only authenticates the org, not the specific repository) and then match the shared SHA in `Commit.where(sha: ...)`, writing the status onto the victim's commit row in a completely different stack.

`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` only checks that the payload came from the claimed organization's registered GitHub App — it never checks that the `repository.full_name` in the payload matches the repository owning the `Commit` rows being updated. `drop_unhandled_event`, `ExplicitParameters` (`status_handler.rb` params block) and `force_github_authentication` are all irrelevant here since this is an unauthenticated webhook endpoint by design; none of them scope the DB write to the authenticating repository.

### Impact Explanation
A `status` webhook authenticated for repository/org A can write a `Status` row (and trigger `deployable_status` hooks / `schedule_merges`) onto `Commit` rows belonging to repository/org B, provided the two share a commit SHA (fork relationship) and both are under the same trusted GitHub organization/app installation. This directly matches the "payload for one repository mutating another's stack/commit" Critical category: it can flip a victim stack's required `ci/e2e` context to `success`, changing `deployable?`/merge eligibility and enabling unauthorized deploy/rollback/merge of the shared commit in the victim's stack. This is repeatable for every shared SHA and for every repository sharing the trusted org's webhook secret.

### Likelihood Explanation
Requires: (1) attacker has push/PR access to some repository under a GitHub organization that already has Shipit's GitHub App installed (this can be a low-value/sandbox repo, not necessarily the victim's), (2) attacker's repository shares at least one commit SHA with the victim's tracked repository (achievable by forking the victim's repository, which preserves identical git object hashes for shared history), and (3) the victim stack's `ci.require` includes the forged context (e.g. `ci/e2e`). None of these require Shipit secrets, sessions, or API tokens — only ordinary GitHub push/PR rights within an already-onboarded organization, making this feasible for an "unprivileged" contributor as defined in scope.

### Recommendation
Scope `StatusHandler#process` to the authenticating repository, mirroring `Handler#stacks`: resolve `Repository.from_github_repo_name(repository_name)` first, then update only `Commit` rows whose `stack.repository_id` matches that repository (e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or an equivalent join), rather than a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar):
1. Create two stacks/repositories, `victim/repo` and `attacker/repo`, each with a `Commit` row sharing the same `sha` (simulating a fork).
2. Set `victim` stack's `ci.require` (or equivalent config) to include `ci/e2e`.
3. Build a payload: `{ 'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/e2e', 'repository' => { 'full_name' => 'attacker/repo' } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is orthogonal to this bug).
5. Assert equality before: `victim_commit.status.state != 'success'` and `victim_commit.deployable? == false`.
6. Assert after processing: `victim_commit.reload.status.state == 'success'` and `victim_commit.deployable?` flips to `true` — proving a payload naming `attacker/repo` mutated `victim/repo`'s commit state, violating the intended per-repository isolation.
