### Title
Webhook signature verification is keyed on `repository.owner.login` while every handler acts on the independently-attacker-controlled `repository.full_name` (or `organization.login` for membership events), allowing cross-organization forgery in multi-tenant Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to HMAC-verify the request against using `repository_owner`, a value read directly out of the untrusted, attacker-suppliable JSON body (`params.dig('repository', 'owner', 'login')`). Every event handler, however, resolves the `Stack`/`Repository`/`Team` it acts on from a *different* field of that same body (`repository.full_name`, or `organization.login`/`team.id` for membership events). Because Shipit supports hosting multiple GitHub organizations behind one instance, each with its own `webhook_secret` [1](#0-0) , an administrator of *any one* onboarded organization knows their own app's webhook secret and can craft a signed payload whose `owner.login` matches their own org (so verification succeeds against their own secret) but whose `full_name`/`organization.login`/`team` fields reference a completely different, unrelated organization's stacks or teams tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the verifying `GitHubApp` from `repository_owner`: [2](#0-1)  and defines `repository_owner` as: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only proves that the raw body was HMAC-signed with the secret belonging to whichever organization `repository_owner` names — it does not tie the signature to any specific target repository being mutated: [4](#0-3) 

After verification, `WebhooksController#create` dispatches the same parsed body to handlers: [5](#0-4) 

The base `Handler` (used by `PushHandler`, `CheckSuiteHandler`, most `PullRequest` handlers) resolves the target `Stack`/`Repository` from `repository.full_name`, a field never consulted during signature selection: [6](#0-5)  and is used directly by `PushHandler#process`: [7](#0-6) 

`MembershipHandler` similarly trusts `organization.login` and `team` from the body to create/modify `Team` membership records, again independent of which org's secret was used to verify: [8](#0-7) 

`StatusHandler` writes commit statuses purely from `sha`, with no repository/organization binding check at all: [9](#0-8) 

Multi-organization configuration, where each org has an independently created/administered GitHub App and its own `webhook_secret`, is a first-class, documented Shipit feature: [1](#0-0)  and is implemented via `Shipit.github(organization:)` / `github_app_config`: [10](#0-9)  with a corresponding fixture used in tests confirming two independently secreted apps coexist in one instance: [11](#0-10) 

**Binding broken:** the organization whose secret authenticated the request (`repository.owner.login`, verified via `Shipit.github(organization: repository_owner)`) is treated as equal to the organization whose repositories/teams/stacks the payload is permitted to mutate (`repository.full_name` / `organization.login`), but the code never enforces that equality — it only checks the first field for signing and blindly trusts the second for effects.

### Impact Explanation
In a multi-org Shipit deployment (a supported, documented configuration), any GitHub organization admin who can create/administer their own GitHub App (and thus knows their own `webhook_secret`) can forge and sign a webhook whose `repository.owner.login` is their own org (passing signature verification) but whose `repository.full_name` targets a stack belonging to a different tenant organization on the same Shipit instance. This lets that attacker: trigger `GithubSyncJob`/`sync_github` on another org's stack via a forged `push` event, inject fabricated commit statuses via `status` events (which can gate/unblock CI-based deploy safety checks), or fabricate `membership`/`team` events to add themselves to a `Team` that may back `Shipit.github_teams` authorization used for login access control. This crosses the "escalation into `Shipit.github_teams` authorization" / "unauthorized deploy" boundary described as High/Critical impact for this engine, without requiring any Shipit session, API token, or the victim org's actual webhook secret.

### Likelihood Explanation
Exploitability requires only that: (1) the Shipit instance hosts more than one GitHub organization (a documented, supported deployment mode) and (2) the attacker administers/created at least one of those orgs' GitHub Apps (hence knows its `webhook_secret`) — no access to the victim organization's credentials, Shipit account, or webhook secret is needed. This is a realistic scenario for shared/managed Shipit instances serving multiple tenant orgs.

### Recommendation
After signature verification, re-derive/require that the organization implied by `repository.full_name` (or `organization.login` for membership events) matches the organization (`repository_owner`) whose secret was used to verify the signature, and reject the webhook if they diverge. Alternatively, verify the signature using the secret that corresponds to the resolved `Repository`/`Stack`'s actual configured organization rather than a value read directly from the unauthenticated portion of logic that also drives downstream effects.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` (attacker-administered, webhook secret `sA` known to attacker) and `OrgB` (victim, tracked stack `OrgB/private-repo`), per the multi-app config format shown in `docs/setup.md`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/private-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(sA, body)>` using their own known `OrgA` webhook secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner == "OrgA"`, verifies successfully against `sA` — [2](#0-1) .
6. `PushHandler` resolves stacks via `repository.full_name == "OrgB/private-repo"` and enqueues `GithubSyncJob`/`stack.sync_github` for `OrgB`'s stack — [7](#0-6)  — despite the attacker having no credentials for `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
