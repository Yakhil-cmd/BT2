This confirms the exploit chain exactly:

- `Handler#stacks` resolves the target purely from `payload.dig('repository', 'full_name')` [1](#0-0) , completely independent of `WebhooksController#repository_owner`, which selects the verifying secret from `params.dig('repository', 'owner', 'login')` [2](#0-1) .

### Title
Webhook signature verification is bound to `repository.owner.login`, not the `repository.full_name` acted upon, enabling cross-tenant status/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature with using `repository_owner`, read from the same untrusted JSON body (`params.dig('repository','owner','login')`) [5](#0-4) . Once the signature validates, the raw `params` (including a completely independent `repository.full_name` field) are handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) . Every handler resolves the actual target stack/commit from `payload.dig('repository', 'full_name')` [7](#0-6) , a field never checked against the organization whose secret validated the signature.

### Finding Description
Shipit supports multi-tenant configuration where distinct GitHub organizations each have their own `app_id`/`webhook_secret` in `secrets.yml` [8](#0-7) . The webhook endpoint is a single shared `/webhooks` route for all configured organizations. Signature verification only proves "this payload was signed by the secret belonging to whatever org the JSON claims as `repository.owner.login`" — it does not prove that the `repository.full_name` referenced elsewhere in the same JSON actually belongs to that organization.

Because `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled string fields inside the same signed JSON body, an actor who legitimately controls (or is an admin of) one onboarded, lower-trust org (e.g. `cyclimse` in the fixtures) can:
1. Set `repository.owner.login = "cyclimse"` so `Shipit.github(organization: "cyclimse")`'s webhook secret is used, sign the payload with that secret (which they legitimately possess as an admin of that org's GitHub App), and pass `verify_signature`.
2. Set `repository.full_name = "shopify/shipit-engine"` (or any other tenant's repo tracked by the same Shipit instance) so downstream handlers act on a repository/stack that has nothing to do with the org that actually authenticated the request.

This breaks the equality that should hold: `organization that authenticated == organization owning the repository being written`.

### Impact Explanation
With `StatusHandler`, the attacker can inject arbitrary commit statuses (`state`, `context`, `target_url`, `description`) for any `sha` in the entire Shipit instance [9](#0-8) . Since `ci.require` gates deploys on such statuses (per `README.md`), an attacker with no relationship to the victim's repository could mark a malicious or unreviewed commit's CI as "success," enabling an **unauthorized deploy** of that commit for a stack belonging to a completely different organization. `PushHandler` similarly can force `sync_github`/resync activity on arbitrary victim stacks. This satisfies the High-severity criterion "escalation into `Shipit.github_teams` authorization" adjacent impact — more precisely, it enables an unauthorized deploy via CI-status forgery, which is explicitly a Critical outcome per the rubric.

### Likelihood Explanation
The likelihood is bounded by requiring the attacker to be a legitimate holder of *some* onboarded organization's webhook secret in the same multi-tenant Shipit deployment — this is plausible in any Shipit instance serving multiple orgs/teams (as the fixtures `shopify`/`cyclimse` suggest is a supported and expected configuration), and requires no access to the victim org, no Shipit session, and no API client token. The only gate is knowledge of one's own org's webhook secret, which by design every onboarded org's GitHub App admin has.

### Recommendation
- After verifying the HMAC signature, additionally verify that `repository.full_name`'s owner matches the `repository_owner` (or organization) that was used to select the verifying secret before invoking any handler.
- Consider deriving the "authorized organization" once and passing it through to `Handler#stacks`/`Repository.from_github_repo_name` so the record lookup is scoped to that organization rather than trusting the raw payload's `full_name`.

### Proof of Concept
1. Attacker is an admin of GitHub org `cyclimse`, which is a legitimately configured org in Shipit's `secrets.yml` (`github.cyclimse.webhook_secret`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha tracked in shopify/shipit-engine>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "cyclimse" }, "full_name": "shopify/shipit-engine" }
}
```
3. Attacker signs the raw body with `cyclimse`'s known `webhook_secret` and sets `X-Hub-Signature` and `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "cyclimse")` (from `repository.owner.login`) and validates successfully [5](#0-4) .
5. `StatusHandler#process` finds the commit by `sha` regardless of tenant and creates a fake "success" status on the victim org's commit [3](#0-2) , potentially unlocking a deploy gated on that CI check for a repository the attacker has no access to.
