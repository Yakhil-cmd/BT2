### Title
Unauthenticated `light/dry_run_aa` request can throw an uncaught exception that crashes the full ocore node - (File: network.js, aa_composer.js)

### Summary
A single unprivileged websocket client can send a `light/dry_run_aa` request with a validly-shaped but semantically abusive `trigger` object. Certain code paths reached from this request (`aa_composer.dryRunPrimaryAATrigger` → `handleTrigger` and its helpers) use synchronous `throw Error(...)` inside asynchronous DB callbacks instead of routing errors to a callback/`bounce()`. Because these throws occur inside nested `conn.query` callbacks (not inside any `try/catch`), Node treats them as uncaught exceptions. `network.js` registers a global `process.on('uncaughtException', ...)` handler that explicitly re-throws to kill the process (`throw err; // crash the process to avoid ending up in an inconsistent state`), so the entire node - which serves all other peers/wallets sharing that process - goes down. This mirrors CVE-2022-36046: a single crafted request causes an unhandled exception that terminates the whole shared server process.

### Finding Description
The light-wallet request handler for `light/dry_run_aa` validates the trigger with `aa_composer.validateAATriggerObject` and then calls `aa_composer.dryRunPrimaryAATrigger(params.trigger, params.address, arrDefinition, ...)`: [1](#0-0) 

`validateAATriggerObject` only checks shape/type constraints (non-empty outputs, valid address, size limits, known assets, address not already an AA); it does not simulate or bound every downstream code path: [2](#0-1) 

Inside `dryRunPrimaryAATrigger` and the helpers it calls, several conditions are enforced via bare `throw Error(...)` rather than an error callback, even though they run inside asynchronous DB-query callbacks that have no surrounding `try/catch`: [3](#0-2) [4](#0-3) [5](#0-4) 

`handleTrigger` itself also throws synchronously for state mismatches (`"assocBalances and bAir do not match"`, `"bad AA definition"`, `"unexpected params"`, `"base AA not found"`, `"secondary triggers while bouncing"`), several of which are conditioned on state that can be influenced by attacker-controlled `trigger`/AA definitions combined with `bDryRun`/`bAir` options: [6](#0-5) [7](#0-6) 

Any such throw, occurring inside a `conn.query(...)` callback, is not caught by the calling code, propagates to Node's event loop as an uncaught exception, and is caught only by the global handler in `network.js`, which deliberately re-throws to crash the process: [8](#0-7) 

This handler comment ("crash the process to avoid ending up in an inconsistent state") confirms the intended behavior is a full process kill on any such internal assertion failure — exactly the "unexpected server crash" bug class in the reported CVE, but triggerable remotely by an unprivileged party instead of requiring the operator/host itself to error.

### Impact Explanation
A crash of the shared ocore process is a denial-of-service against every peer, AA, and wallet connected to that node/hub instance — the network is unable to process new units, validate AA triggers, or serve requests until manually restarted. Because full nodes and hubs serve many clients over the same process (unlike per-request isolation), a single malicious/malformed request from any connected light client can take down service for all connected parties, matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
The `light/dry_run_aa` command is reachable by any connected websocket client without special privileges — no unit needs to be posted or confirmed, and no funds are required, only a plausibly-valid `trigger` and `address` for an existing AA. `validateAATriggerObject` performs only structural checks and does not exhaustively prevent all the internal invariant violations that are enforced via `throw` further down the call chain (e.g., stale/mismatched MC state assumptions in `readLastStableMcUnit`, `readMcUnit`, `readUnit`, or definition/param combinations reaching `handleTrigger`'s throw branches). Reaching one of these specific `throw` sites in practice requires crafting an AA definition/trigger/timing combination that defeats the pre-checks, which is plausible but not trivially proven from static review alone.

### Recommendation
- Wrap `dryRunPrimaryAATrigger`, `handlePrimaryAATrigger`, `handleTrigger`, and their DB-callback bodies (`readLastStableMcUnit`, `readMcUnit`, `readUnit`, `insertFakeOutputsIntoMcUnit`) in proper error handling that routes failures to an error-first callback (`cb(err)`/`bounce(err)`) instead of throwing.
- Convert the internal-consistency `throw Error(...)` assertions reachable from `light/dry_run_aa` into `sendErrorResponse(ws, tag, ...)` responses so a single bad/edge-case client request cannot bring down the whole process.
- Reconsider the blanket `process.on('uncaughtException', ...) { throw err; }` policy in `network.js`: at minimum, distinguish exceptions originating from per-request handlers (which should just fail that request) from exceptions indicating genuinely corrupted global state.

### Proof of Concept
Conceptual PoC (requires live investigation to pin the exact trigger payload, since only static analysis was performed here):
1. Connect as a light client to a running ocore hub/full node.
2. Identify (or deploy) any AA address `A`.
3. Send `light/dry_run_aa` with `params = { address: A, trigger: { address: <valid_address>, outputs: { base: 1 } } }` while racing/timing the request so that `readLastStableMcUnit` / `readMcUnit` returns an unexpected row count (e.g., 0 or >1) due to concurrent MC rebuild activity, or by supplying a parameterized-AA `template.base_aa` combined with non-empty `params` to hit the `"unexpected params"` throw in `handleTrigger`.
4. Observe that the thrown error is uncaught by any handler in `aa_composer.js`, is caught only by `process.on('uncaughtException')` in `network.js`, and the process exits/crashes, dropping every other connected peer. [8](#0-7)

function validateAATriggerObject(trigger, handle) {
	if (!ValidationUtils.isNonemptyObject(trigger))
		return handle("no trigger");
	if (!ValidationUtils.isNonemptyObject(trigger.outputs))
		return handle("no trigger outputs");
	if (!ValidationUtils.isValidAddress(trigger.address))
		return handle("bad trigger address");
	if ("max_aa_responses" in trigger && (!ValidationUtils.isNonnegativeInteger(trigger.max_aa_responses) || trigger.max_aa_responses > constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER))
		return handle("bad trigger max_aa_responses");
	if (ValidationUtils.hasFieldsExcept(trigger, ["address", "data", "outputs", "max_aa_responses"])) // initial_address and initial_unit cannot be separately set in a primary trigger
		return handle("unexpected trigger fields");
	if (string_utils.isTooBigObj(trigger, { lengthLimit: 10e3 }))
		return handle("trigger data is too big");
	try {
		if (trigger.data)
			string_utils.getJsonSourceString(trigger.data);
	}
	catch (e) {
		return handle("invalid trigger data: " + e);
	}
	var arrAssets = Object.keys(trigger.outputs).filter(function(asset) {return asset !== 'base'});
	if (arrAssets.length >= constants.MAX_MESSAGES_PER_UNIT)
		return handle("too many assets");
	if (!ValidationUtils.isPositiveInteger(trigger.outputs.base))
		return handle("no base payment");
	if (!arrAssets.every(function(asset){return ValidationUtils.isPositiveInteger(trigger.outputs[asset])}))
		return handle("invalid output amount")

	function checkAddressIsNotAA() {
		db.query("SELECT 1 FROM aa_addresses WHERE address=?", [trigger.address], rows => {
			if (rows.length)
				return handle("trigger address must not be an AA");
			else
				return handle();
		});
	}

	if (arrAssets.length === 0)
		return checkAddressIsNotAA();
	// we have to check that assets exist otherwise foreign key constraint would fail when inserting fake outputs
	db.query("SELECT 1 FROM assets WHERE unit IN (?)", [arrAssets], function(rows) {
		if (rows.length !== arrAssets.length)
			return handle("unknown asset");
		else
			checkAddressIsNotAA();
	});
