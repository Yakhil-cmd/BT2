### Title
Stack-scoped API client bypasses stack authorization in CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by the shared `BaseController` in a way that discards the stack-scoping enforcement normally applied to `ApiClient` tokens, allowing a token that is authorized for one stack only to read build/deploy state of any other stack.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the stacks an `ApiClient` is authorized for: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` resolves `params[:stack_id]` only within that scoped relation - this is the binding: *a stack a token authorises == a stack it touches*.

`ApiClient#check_permissions!` only checks the coarse `operation:scope` string (e.g. `read:stack`); it does not itself verify which specific stack is being accessed: [2](#0-1) 
The actual per-stack restriction is enforced entirely by the `stacks`/`stack` helper in `BaseController` - it is the sole enforcement point.

`CCMenuController`, however, overrides `stack` to bypass that scoped relation and resolve the stack directly from all stacks: [3](#0-2) 
`require_permission :read, :stack` only checks for the presence of the `read:stack` permission string on the token (not stack identity): [4](#0-3) 

Because `stack` no longer goes through `current_api_client.stack_id?`-scoped `stacks`, any `ApiClient` token that merely carries the `read:stack` permission - including one that was created and is only meant to be valid for a single specific stack (`api_client.stack_id` set, as produced e.g. by `CCMenuUrlController`) - can pass an arbitrary `stack_id` to `Api::CCMenuController#show` and read another stack's build/deploy state.

Contrast this with `Api::StacksController`, which relies on the inherited, correctly-scoped `stack`/`stacks` methods: [5](#0-4) 

Equality before the exploit: `token.authorized_stacks == {stack_id}` and `token.touched_stack == {stack_id}` (enforced by `BaseController#stack`).
Equality broken by the exploit: `token.authorized_stacks == {stack_id}` while `token.touched_stack ∈ Stack.all` (any stack), because `CCMenuController#stack` never applies the `stacks` scoping.

### Impact Explanation
A leaked or otherwise obtained single-stack-scoped API token (e.g. the CCMenu token minted by `CCMenuUrlController`, which is even embedded in a query-string URL meant to be shared with third-party CI dashboard tools) can be used to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state, etc.) of every stack in the Shipit instance, not just the one it was scoped to. This is an authorization-boundary escalation matching the "escalation into stack authorization" / "unauthenticated read of stack state" class called out as High severity, since the intended per-stack authorization binding is broken by this specific endpoint.

### Likelihood Explanation
Medium/High. It requires only possession of any valid `ApiClient` token with `read:stack` permission (including the intentionally narrow, easily distributed CCMenu tokens generated per-stack via `CCMenuUrlController`), and issuing a normal authenticated request to `Api::CCMenuController#show` with a different `stack_id`. No other privilege or secret is required beyond a token that would normally only be trusted for a single stack.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it to use the inherited, scoped `stacks` relation, e.g. `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot access stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (this is exactly what `CCMenuUrlController#client` produces: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, name: 'CCMenu Client')`, then bound to stack A via the generated `ccmenu_url`).
2. Using the Basic-Auth token for that client (`client.authentication_token`), send:
   `GET /api/stacks/OtherOrg/other-repo/production/ccmenu.xml` (i.e. `stack_id` pointing to stack B, not A) via `Api::CCMenuController#show`.
3. Observe that `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` (bypassing `current_api_client.stack_id` scoping in `BaseController#stacks`) and returns stack B's data - build state for a stack the token was never authorized for is disclosed, in violation of the `stack_id` binding enforced everywhere else in the API.

module Shipit
  module Api
    class StacksController < BaseController
      require_permission :read, :stack, only: %i[index show]
      require_permission :write, :stack, only: %i[create update destroy]

      params do
        accepts :repo_owner, String
        accepts :repo_name, String
      end
      def index
        @stacks = stacks
        if params[:repo_owner] && params[:repo_name]
          full_repo_name = [repo_owner, repo_name].join('/')
          @stacks = if (repository = Repository.from_github_repo_name(full_repo_name))
                      stacks.where(repository:)
                    else
                      Stack.none
                    end
        end
        render_resources(@stacks)
      end
