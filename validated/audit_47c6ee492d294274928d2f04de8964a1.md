### Title
Assets with oracle-controlled `transfer_condition`/`issue_condition` can permanently freeze AA-held balances - ([File: validation.js])

### Summary
Any address can define a custom asset (`asset` message) with a `transfer_condition` (and/or `issue_condition`) that references an `in data feed` clause tied to one or more oracle addresses. This is functionally equivalent to a "pausable token": the asset issuer (or any oracle referenced in the condition) can, at any time, post a data-feed value that makes the condition evaluate to `false`, instantly blocking every future transfer of that asset network-wide — including transfers made by an Autonomous Agent (AA) that has already accumulated a balance of that asset. Because AA payment composition has no partial-success or retry mechanism for individual messages (a failed condition on one payment message causes the whole response to `bounce`), an AA that legitimately received such an asset as part of a trigger (e.g. a DEX, vault, or swap AA) can become permanently unable to pay that asset back out to users, freezing their funds inside the AA.

### Finding Description
When an asset is defined, its `transfer_condition`/`issue_condition` is stored and enforced on every subsequent payment of that asset in `validateAssetDefinition` / `validatePaymentInputsAndOutputs`: [1](#0-0) 

The condition is evaluated by `Definition.evaluateAssetCondition`, which supports the `in data feed` operator, allowing the condition to depend on a live oracle value: [2](#0-1) 

At authentication/spend time, this is checked the same way as an address definition's `in data feed`: [3](#0-2) 

Because the oracle(s) referenced can be the asset definer itself (or any address chosen at asset-creation time), the definer can effectively "pause" the asset at will by posting a data-feed value that makes `evaluateAssetCondition` return `false`. This is intended as a feature of ocore's asset system (like Yearn's pause mechanism being an intended safety feature), but any protocol built as an AA that accepts arbitrary/whitelisted assets from users is exposed to the same risk class described in the report: once a "pausable" asset stops satisfying its condition, output payments of that asset fail.

The critical difference from a normal user wallet is how an AA handles that failure. When an AA tries to send a payment message and the transfer condition fails at commit time (unit validation), the entire response bounces: [4](#0-3) 

The AA's payment-message assembly path validates output addresses/amounts but does not validate whether the down-stream `transfer_condition`/`spender_attested`/`is_transferrable` restrictions of the asset will actually allow the payment to be committed; it only discovers this when `validateAndSaveUnit` (full network validation) rejects the composed response unit, which forces `bounce`: [5](#0-4) [6](#0-5) 

Since the AA's balance for that asset (tracked in `aa_balances`) is only debited on a successful commit, a "paused" asset simply causes the AA response to keep bouncing whenever it tries to pay that asset out, while `bounce()` refunds only the *newly received* trigger outputs, not the asset balance the AA already holds: [7](#0-6) 

The AA's existing balance of the paused asset remains stuck in `aa_balances` indefinitely — there is no privileged "override" or emergency-withdraw path in the base protocol; the AA logic itself would need to have anticipated this exact failure mode, which most AA authors do not.

### Impact Explanation
An AA holding funds denominated in an asset whose `transfer_condition`/`issue_condition` (or `spender_attested`/attestor list) can later be manipulated by the issuer/oracle to evaluate `false` risks having that entire share of its balance permanently frozen. Any AA-based protocol (DEX/AMM, escrow, vault, staking contract) that accepts arbitrary user-supplied assets as collateral or trade input is exposed: legitimate users who deposited such an asset before the "pause" cannot get it back out through the AA, and the AA cannot route around the restriction because oscript/AA logic has no way to catch a validation failure on a single message and substitute an alternative. This matches the "AA fund loss or freezing" impact bucket.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an asset definer to intentionally embed an oracle-checked `transfer_condition`, and (2) an AA to accept and hold that asset without restricting itself to a fixed, trusted whitelist of assets. Many general-purpose AAs (e.g. generic exchange/pool AAs that let users register arbitrary assets) satisfy condition (2) by design, and asset conditions referencing data feeds are an explicitly supported, first-class ocore feature, so a malicious or compromised issuer can trigger this at will once users' funds are inside the AA.

### Recommendation
- AA authors integrating arbitrary/user-supplied assets should explicitly read and reject assets that have non-empty `transfer_condition`, `issue_condition`, or `spender_attested`/`is_transferrable=false` at accept time, using the `asset[...]` formula fields (e.g. `asset[asset].is_transferrable`) before allowing deposits.
- Consider hardening the core AA framework with best-effort handling: e.g. allow an AA to query whether a prospective outgoing asset payment would currently satisfy the asset's condition (similar to a dry-run) before committing to sending it, so the AA logic can branch instead of unconditionally bouncing and leaving balances stuck.
- Document this asset-conditions/oracle-pause risk prominently for AA developers, analogous to the "pausable token" warning recommended in the original report.

### Proof of Concept
1. Attacker (as any user) posts an `asset` definition unit with:
   - `transfer_condition: ["in data feed", [[attacker_address], "PAUSE", "=", "0"]]`
   - reasonable other fields (`is_private:false`, `is_transferrable:true`, etc.), validated per `validateAssetDefinition` (`validation.js:2725-2827`).
2. A victim AA (e.g. a swap/pool AA) is configured or coded to accept this asset from users and accumulates a balance of it in `aa_balances` after legitimate deposits.
3. Attacker posts a `data_feed` unit from `attacker_address` with `PAUSE = 1` (making the condition `PAUSE = "0"` false).
4. Any subsequent AA response message paying out this asset fails `Definition.evaluateAssetCondition` inside `validatePaymentInputsAndOutputs` (`validation.js:2643-2658`), causing `validateAndSaveUnit` to fail and the AA to `bounce()` (`aa_composer.js:909-945`), leaving the AA's balance of the asset permanently un-spendable while `PAUSE` stays set to `1`.
