### Title
Unhandled error in private-payment hash computation causes duplicate callback invocation and crash - ([File: network.js])

### Summary
`handleSavedPrivatePayments()` in `network.js` processes queued private payment chains and, in its inner `validateAndSave()` closure, wraps a hash computation in `try { … } catch (e) { … }` but never returns from the `catch` block. This mirrors the CVE-2016-2145 root cause: `am_read_post_data()`/`ap_get_client_block()` error is not checked before the code continues to use the (now invalid) result, crashing the process. Here, when `objectHash.getBase64Hash()` throws on attacker-crafted payload data, the function logs the error, deletes the chain, but then falls through and keeps executing — computing `key` from an `undefined` hash and invoking `privatePayment.validateAndSavePrivatePaymentChain()` a second time on the same malformed data, ultimately calling the `async.each` iteratee callback `cb` more than once for the same row.

### Finding Description
In `network.js`: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

`getBase64Hash()` calls `getJsonSourceString()` for canonicalization: [2](#0-1)  — this throws on payload content that fails canonicalization/type checks (unsupported types, non-finite numbers, etc.).

The `catch` block never `return`s, so after `deleteHandledPrivateChain(..., cb)` runs (which itself eventually invokes `cb`), execution proceeds to build `key` with `json_payload_hash === undefined` and calls `privatePayment.validateAndSavePrivatePaymentChain(...)` again on the same (already-deleted / malformed) chain. Each of its callback branches (`ifOk`, `ifError`, `ifWaitingForChain`) also calls `deleteHandledPrivateChain(..., cb)` or `cb()` directly: [3](#0-2) . This results in the shared `async.each` iteratee callback `cb` being invoked twice for one row — a classic double-callback bug that can throw ("Callback already called") or otherwise corrupt the mutex-guarded processing state (`mutex.lock(["saved_private"], ...)`), since `unlock()` in the `async.each` final callback may run inconsistently.

This is directly analogous to the CVE: an error condition from parsing/hashing untrusted input is detected but not properly short-circuited, so the code proceeds to operate on the invalid/partial result, leading to a crash/DoS.

### Impact Explanation
The vulnerable path is reached without any special privilege: a device paired with the victim (a normal private-payment counterparty, explicitly in scope) can send a `private_payment_chains` message via `wallet.js:handlePrivatePaymentChains` — validation there only checks shallow shape (`isNonemptyObject`, presence of `asset`, `inputs`, `outputs` arrays): [4](#0-3) . It does not deep-validate the types/values inside `payload` that `getJsonSourceString` requires to be well-formed, so a crafted payload can make `getBase64Hash` throw. Such elements can end up queued in `unhandled_private_payments` (via `savePrivatePayment`) and later processed by `handleSavedPrivatePayments` where the bug triggers: [5](#0-4) .

The result is that the crafted message can cause the victim's node/wallet process to crash or its private-payment processing mutex/queue to become stuck, preventing it from confirming/processing further private payments — a denial-of-service triggerable by any paired counterparty without authentication beyond normal pairing, matching the CVSS profile of the source CVE (network-reachable, no privileges, availability-only impact).

### Likelihood Explanation
Any device already paired with the target (a normal, expected trust relationship for exchanging private payments/textcoins) can send this message; no additional privilege escalation or race condition is required, only crafting a `payload` object that fails JSON canonicalization in `getJsonSourceString`. This makes the likelihood of triggering the bug straightforward for a malicious correspondent.

### Recommendation
Add an explicit `return` (or restructure with early exit) inside the `catch` block in `network.js`'s `validateAndSave()` so that after `deleteHandledPrivateChain(...)` is called on hash-computation failure, execution does not fall through to compute `key` and re-invoke `privatePayment.validateAndSavePrivatePaymentChain()`. Also make `deleteHandledPrivateChain` and all `cb` invocations idempotent/guarded (e.g., wrap `cb` with an "only-once" guard) to prevent any future double-callback regressions in this and similar async flows.

### Proof of Concept
1. Pair a malicious device with the victim wallet.
2. Send a `chat` device message with subject `private_payment_chains` whose `body.chains[0][0].payload` is a syntactically valid object (passing the shallow checks in `wallet.js:959-972`) but contains a value that makes `string_utils.getJsonSourceString()` throw (e.g., an unsupported type/structure not handled by the canonicalizer).
3. The chain is queued via `network.handleOnlinePrivatePayment` → `unhandled_private_payments` (light-client "waiting" path) or processed inline.
4. When `handleSavedPrivatePayments()` runs `validateAndSave()`, `objectHash.getBase64Hash(payload, true)` throws; the `catch` block runs `deleteHandledPrivateChain(..., cb)` but does not return, so `privatePayment.validateAndSavePrivatePaymentChain()` is invoked again on the same data, ultimately calling the shared `cb` a second time — triggering a double-callback error/crash or a stuck `saved_private` mutex, halting private-payment processing for the victim.

Note: I could not execute this PoC in a live environment; verification of the exact throw conditions inside `getJsonSourceString` (in `string_utils.js`) would need to be confirmed by a Devin session with code execution to craft a concrete malicious payload and observe the crash.

```javascript
function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}
```

```javascript
function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;

		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>

			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
```
