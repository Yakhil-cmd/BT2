### Title
Feature-gate for WebAuthn / SLH-DSA / SingleSender authenticators is enforced only at mempool admission, not at execution — pre-validation mismatch allows disabled-feature transactions to commit - ([File: aptos-move/aptos-vm/src/aptos_vm.rs])

### Summary
`AptosVM::check_authenticator_features` rejects `TransactionAuthenticator::SingleSender` when `SINGLE_SENDER_AUTHENTICATOR` is disabled, and rejects `AnySignature::WebAuthn`/`AnySignature::SlhDsa_Sha2_128s` when `WEBAUTHN_SIGNATURE`/`SLH_DSA_SHA2_128S_SIGNATURE` are disabled. [1](#0-0) 
This check is called exactly once, from `VMValidator::validate_transaction`, which is the mempool/API admission path. [2](#0-1) 
It is not invoked from `validate_signed_transaction`, `execute_user_transaction_impl`, or anywhere in the block-execution path (`execute_single_transaction` → `execute_user_transaction` → `execute_user_transaction_impl` → `validate_signed_transaction`).

### Finding Description
The comment on the function states it is "Called from both mempool validation and the execution paths," but a repo-wide search shows only a single call site inside `VMValidator::validate_transaction` (the mempool/API admission entry point). [3](#0-2) [4](#0-3) 

The actual execution-time re-validation function, `validate_signed_transaction`, performs its own set of feature checks (duplicate signers, keyless authenticators, AA dispatchable authentication, `TransactionPayloadV2`, orderless txns, encrypted variant) but never calls `check_authenticator_features`, so it does not re-check `SINGLE_SENDER_AUTHENTICATOR`, `WEBAUTHN_SIGNATURE`, or `SLH_DSA_SHA2_128S_SIGNATURE`. [5](#0-4) [6](#0-5) 

This means the admission rule ("no `SingleSender`/WebAuthn/SLH-DSA authenticator when the corresponding feature is disabled") is enforced only at the mempool boundary, not at the VM's own execution/prologue boundary that runs inside `execute_block`. If a transaction using a `SingleSender` authenticator with a `WebAuthn` or `SlhDsa_Sha2_128s` signature is proposed into a block by any path that bypasses `VMValidator::validate_transaction` (e.g., a validator injecting/ordering transactions directly into consensus/quorum-store without going through the local `validate_transaction` mempool gate, or a state-sync/quorum-store transaction that skips the per-mempool feature check), the transaction can still pass `validate_signed_transaction`'s prologue (signature verification via `transaction.check_signature()` succeeds independent of the feature flag) and be executed and committed, even while the feature flag is disabled network-wide.

This directly matches the "Admission Pivots" requirement that "Admission rules in mempool, vm-validator, and VM validation must agree on what is executable" and the "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit" impact category — a transaction that should be discarded at admission (feature not yet rolled out) can instead reach execution and change state.

### Impact Explanation
If the gating for `WEBAUTHN_SIGNATURE` or `SLH_DSA_SHA2_128S_SIGNATURE` is disabled network-wide (e.g., during a rollout window, or if these flags are toggled off after being enabled for testing/rollback), a transaction using that unsupported authenticator type could still be executed and committed on-chain because `execute_block` → `execute_user_transaction_impl` → `validate_signed_transaction` never re-checks these feature flags. This breaks the invariant that "Admission rules in mempool, vm-validator, and VM validation must agree on what is executable," potentially causing non-deterministic behavior across nodes with different feature-flag rollout states, or execution of authenticator types the framework/VM feature model was not yet ready to support (e.g., inconsistent gas metering paths, cryptography not yet fully verified/audited for mainnet). The severity depends on the operational likelihood of the feature-flag windows being exploited, but architecturally it is a genuine mismatch between admission and execution enforcement of an authenticator-related security gate.

### Likelihood Explanation
Exploitability requires a transaction to bypass the local `VMValidator::validate_transaction` mempool gate while still reaching block execution — for example, transactions received via inter-validator broadcast/quorum-store/consensus proposal paths that are executed directly by `AptosVMBlockExecutor::execute_block` without a fresh mempool admission check on the executing node. I was not able to fully trace every ingestion path (consensus proposal handling, quorum store batch validation, state-sync replay) within the available tool budget to confirm whether any of them independently re-invokes `check_authenticator_features` before block execution; this is the key open uncertainty. If some other layer (e.g., quorum-store transaction shuffling or consensus safety rules) does perform this check redundantly, the practical exploitability is reduced to only the theoretical VM-level guarantee. Given the explicit code comment claiming the function is called "from both mempool validation and the execution paths" — which the current code does not actually do — this looks like a real code/comment divergence introduced during a refactor, warranting confirmation and fix regardless of whether another layer currently masks it.

### Recommendation
Call `check_authenticator_features` (or an equivalent feature check) from within `validate_signed_transaction` (or `run_prologue_with_payload`), so that the check is enforced at the actual VM execution/prologue boundary used by `execute_block`, not only in the separate `VMValidator::validate_transaction` mempool path. This ensures the admission guarantee described in the function's own doc comment is actually upheld for all transaction ingestion paths, not just client-submitted transactions validated through local mempool.

### Proof of Concept
Conceptual PoC (not fully executable without additional harness access to consensus/quorum-store internals):
1. Disable `FeatureFlag::WEBAUTHN_SIGNATURE` (or `SLH_DSA_SHA2_128S_SIGNATURE`) on-chain.
2. Construct a `SignedTransaction` with a `TransactionAuthenticator::SingleSender` authenticator carrying an `AnySignature::WebAuthn` signature and a valid signature over the raw transaction (as shown in the existing test `test_webauthn_secp256r1_ecdsa`). [7](#0-6) 
3. Submit through `VMValidator::validate_transaction` directly: this call fails at `check_authenticator_features` with `FEATURE_UNDER_GATING`, confirming the admission gate works there. [4](#0-3) 
4. Bypass `validate_transaction` and instead directly invoke `AptosVM::execute_user_transaction`/`execute_block` with the same transaction (as done by `execute_single_transaction`/`AptosVMBlockExecutor::execute_block`), and observe that `validate_signed_transaction` performs no such feature check, allowing the transaction to proceed into the prologue and execution. [5](#0-4) [8](#0-7) 

This would need to be confirmed end-to-end with a full swarm/executor harness feeding the transaction directly into block execution (bypassing local mempool `validate_transaction`) to demonstrate on-chain commit while the feature flag is disabled.

    /// Rejects authenticator/signature variants whose feature flag is not yet
    /// enabled. Called from both mempool validation and the execution paths.
    fn check_authenticator_features(
        &self,
        authenticator: &TransactionAuthenticator,
    ) -> Result<(), VMStatus> {
        if !self
            .features()
            .is_enabled(FeatureFlag::SINGLE_SENDER_AUTHENTICATOR)
        {
            if let TransactionAuthenticator::SingleSender { .. } = authenticator {
                return Err(VMStatus::error(StatusCode::FEATURE_UNDER_GATING, None));
            }
        }

        let webauthn_enabled = self.features().is_enabled(FeatureFlag::WEBAUTHN_SIGNATURE);
        let slh_dsa_enabled = self
            .features()
            .is_enabled(FeatureFlag::SLH_DSA_SHA2_128S_SIGNATURE);
        if !webauthn_enabled || !slh_dsa_enabled {
            let sk_authenticators = authenticator
                .to_single_key_authenticators()
                .map_err(|_| VMStatus::error(StatusCode::INVALID_SIGNATURE, None))?;
            for auth in &sk_authenticators {
                if !webauthn_enabled && matches!(auth.signature(), AnySignature::WebAuthn { .. }) {
                    return Err(VMStatus::error(StatusCode::FEATURE_UNDER_GATING, None));
                }
                if !slh_dsa_enabled
                    && matches!(auth.signature(), AnySignature::SlhDsa_Sha2_128s { .. })
                {
                    return Err(VMStatus::error(StatusCode::FEATURE_UNDER_GATING, None));
                }
            }
        }

        Ok(())
    }

    fn sign_webauthn_transaction(
        raw_txn: &RawTransaction,
        collected_client_data: CollectedClientData,
        authenticator_data: &[u8],
        private_key: &Secp256r1EcdsaPrivateKey,
    ) -> SignedTransaction {
        let public_key = Secp256r1EcdsaPublicKey::from(private_key);

        let client_data_json = serde_json::to_vec(&collected_client_data).unwrap();
        let client_data_hash = sha256(client_data_json.as_slice());

        let signature_material = [authenticator_data, &client_data_hash].concat();
        let signature = private_key.sign_arbitrary_message(signature_material.as_slice());
        let assertion_signature = AssertionSignature::Secp256r1Ecdsa { signature };

        let partial_authenticator_assertion_response = PartialAuthenticatorAssertionResponse::new(
            assertion_signature,
            authenticator_data.to_vec(),
            client_data_json,
        );
        let public_key = AnyPublicKey::Secp256r1Ecdsa { public_key };
        let signature = AnySignature::WebAuthn {
            signature: partial_authenticator_assertion_response,
        };
        let authenticator = SingleKeyAuthenticator::new(public_key, signature);
        let account_authenticator = AccountAuthenticator::SingleKey { authenticator };
        let txn_authenticator = TransactionAuthenticator::SingleSender {
            sender: account_authenticator,
        };
        SignedTransaction::new_signed_transaction(raw_txn.clone(), txn_authenticator)
    }
