### Title
Webhook signature verification is keyed on `repository.owner.login`, but every event handler acts on the unrelated `repository.full_name` field — allowing an org with any valid webhook secret to forge events for a different org's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to validate the HMAC signature against using `repository_owner`, a field read from the *unverified* JSON body [1](#0-0) . Once the signature check passes, `Handler#stacks`/`#repository_name` resolves the actual repository to act on using a **different** field of that same unverified body: `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing ties `repository.owner.login` (used to pick the signing secret) to `repository.full_name` (used to pick the target Stack/Repository). In a multi-org Shipit deployment, whoever holds the webhook secret for OrgA can forge a signed payload whose `owner.login` is `"OrgA"` but whose `full_name` is `"OrgB/some-repo"`, causing Shipit to process the event as if it legitimately came from OrgB.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, not-yet-verified request body: [3](#0-2) 
and uses it to fetch the corresponding `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that secret and `request.raw_post` [1](#0-0) . This is the multi-org configuration path documented and tested for setups with per-organization `webhook_secret`s [4](#0-3) [5](#0-4) .

Once `head(422)` is *not* triggered, `WebhooksController#create` dispatches the same unverified `params` hash to every handler for the event [6](#0-5) . All handlers derive the repository/stack to mutate purely from `payload.dig('repository', 'full_name')`: [2](#0-1) 
which is used by `Repository.from_github_repo_name` to split "owner/name" and locate the actual `Repository`/`Stack` [7](#0-6) .

`repository.owner.login` (verified indirectly, only insofar as it selected the correct secret) and `repository.full_name`'s owner segment (acted upon) are never compared. The equality that should hold — "the organization whose secret signed this payload" == "the organization that owns the repository the handler mutates" — is not enforced anywhere in `WebhooksController` or `Handler`.

Concretely, an attacker who legitimately controls a GitHub App installed on `OrgA` (and thus knows `OrgA`'s `webhook_secret`) can:
1. Build a JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/target-repo"`, `ref`, `after`, etc.
2. Sign it with `OrgA`'s real webhook secret to compute a valid `X-Hub-Signature`.
3. POST it to `/webhooks`.

`verify_signature` looks up `Shipit.github(organization: "OrgA")`, verifies successfully (because the attacker used `OrgA`'s real secret), and the request proceeds. `PushHandler#process` then calls `stacks` — resolved from `full_name = "OrgB/target-repo"` — and executes `stack.sync_github(expected_head_sha: params.after)` for `OrgB`'s stack [8](#0-7) , enqueuing `GithubSyncJob` for a repository the attacker has no authorization over.

The same class of forgery applies to the `status`/`commit_status` handler path, which creates `Status` records that drive `schedule_continuous_delivery` and can trigger `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → an actual deploy [9](#0-8) [10](#0-9) , and to the `pull_request` handlers which create/archive Review Stacks for a repository resolved the same insecure way [11](#0-10) .

### Impact Explanation
This breaks the binding "organization that authenticated the webhook" vs. "repository that is written by the handler." In a multi-organization Shipit installation, it lets an attacker who controls one org's webhook secret forge signed events attributed to a different, unrelated org's repositories, causing Shipit to process pushes and injected CI statuses for that other org's stacks. Because CI status injection can drive `trigger_continuous_delivery` and an actual deploy for a target stack the attacker does not control, this can escalate to an **unauthorized deploy** — one of the explicitly in-scope Critical impacts. It requires a multi-org Shipit deployment where the attacker's own org is a legitimately configured (but lower-trust) GitHub App installation — this is a standard, documented configuration (`docs/setup.md`, "Using Multiple Github Applications"), not a hypothetical misconfiguration.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a Shipit instance configured with more than one GitHub organization/App (an explicitly documented and tested feature), and (b) the attacker possessing a valid webhook secret for at least one of those organizations (e.g., as an admin of that org's own GitHub App installation, which is a much lower bar than compromising the target org). Given those preconditions, forging the payload and computing a valid HMAC is trivial — no other authentication or session boundary needs to be crossed.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, enforce that the organization used to select the webhook secret matches the owner embedded in `repository.full_name` (and `organization.login` when used as fallback) before dispatching to handlers. Concretely, after locating the `Repository`/`Stack` via `full_name`, assert `repository.owner.casecmp?(repository_owner)` (or resolve the signing org strictly from the same repository object used for lookup, not two independent fields of attacker-controlled JSON) and reject the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` "Using Multiple Github Applications" / `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who controls `OrgA`'s GitHub App (and thus its `webhook_secret`), craft:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, raw_body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `stacks` from `full_name = "OrgB/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and enqueues `GithubSyncJob` for `OrgB`'s stack, despite the request never having been authenticated by anything belonging to `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
