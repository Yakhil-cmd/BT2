## Title
CCMenu API endpoint bypasses ApiClient stack-scoping, allowing cross-stack read of deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` breaks the binding between "the stack an `ApiClient` token is authorized for" and "the stack whose state is actually returned." Every other endpoint in the API resolves the target stack through the `BaseController#stack` helper, which is scoped to `current_api_client.stack_id` when the client is stack-restricted. `CCMenuController` overrides that helper to resolve the stack directly from `Stack.from_param!`, ignoring the scoping entirely.

### Finding Description
`BaseController` defines the authorization-respecting resolution: [1](#0-0) 

This ensures that a token created with a `stack_id` (i.e., scoped to one specific stack) can only resolve `stack` to that stack, and `Stack.where(id: ...)` return an empty scope for any other stack id/param, causing `from_param!` to raise `ActiveRecord::RecordNotFound` for any other stack.

`CCMenuController`, however, redefines `stack` to bypass that scoping: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`. The `require_permission :read, :stack` before_action only checks that the token carries the `read:stack` permission string; it never re-checks whether the resolved stack is the one associated with `current_api_client.stack_id`: [3](#0-2) 

The equality that should hold is:
`stack the ApiClient token authorizes == stack the endpoint returns data for`

Before this endpoint is reached, this equality is enforced everywhere else because `stack`/`stacks` in `BaseController` (used by `StacksController`, `TasksController`, etc.) always filters by `current_api_client.stack_id` when present: [4](#0-3) 

In `CCMenuController`, the equality is broken: the token only needs `read:stack` permission (which any client, even one scoped to a single unrelated stack, can hold), and `params[:stack_id]` can name any stack in the installation. The `show` action then renders that other stack's status: [5](#0-4) 

This is also reachable via the token query-string authentication path unique to this controller, which further loosens the "must be Basic Auth header" convention used elsewhere: [6](#0-5) 

### Impact Explanation
This matches the "High — unauthenticated [scope-violating] read of stack state, task streams or deploy output" impact category. An attacker holding any legitimate `read:stack`-scoped `ApiClient` token (even one intentionally restricted by its creator to a single, low-sensitivity stack via `stack_id`) can use it to read the CCTray/CCMenu XML status — `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, lock status, etc. — of any other stack in the Shipit instance, including stacks the token was never meant to see. This is precisely the class of bug the external report describes: a value ("the stack authorized," analogous to the dispute's expiration-time offset) that is checked in one code path but a different, unguarded value ("the stack param," analogous to the proposal's differing offset) is what is actually acted upon, defeating the intended restriction.

### Likelihood Explanation
Likelihood is high for anyone who already possesses a stack-scoped `ApiClient` token — a normal, documented, low-privilege credential (e.g. issued to a CI tool to only read one stack's status). No additional secrets, GitHub access, or session are required beyond the token itself, and the request is a single unauthenticated-parameter GET differing only in `stack_id`.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped resolution from `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, so that a stack-restricted `ApiClient` cannot resolve any stack outside `current_api_client.stack_id`. Remove the private `stack` override entirely (inherit the base implementation) unless there is a documented reason to diverge, and add a regression test asserting that a stack-scoped token receives a 404 (not information leakage) when querying `stack_id` params for a different stack.

### Proof of Concept
1. Create/obtain an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (a normal, restricted token as supported by `ApiClient#stack_id?` and `BaseController#stacks`).
2. Using that token's `authentication_token`, issue: `GET /api/stacks/:owner/:repo/:env/ccmenu.xml?token=<token>` (or via Basic Auth) with `stack_id` referring to Stack B, an unrelated stack the token was never scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!` (unscoped) rather than `stacks.from_param!` (scoped to `current_api_client.stack_id`), the request succeeds and returns Stack B's `lastBuildStatus`/`lastBuildLabel`/lock state in the XML response, even though the token's `stack_id` binds it only to Stack A — confirming the cross-stack read.
