### Title
CCMenu API tokens are minted without stack scoping, letting a token issued for one stack read state, tasks and deploy output of every stack - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`Shipit::CCMenuUrlController#fetch` mints an `ApiClient` token that is embedded in a single stack's public "CCMenu URL" widget, but the client is created without ever setting `stack_id`. Because `Api::BaseController` treats a client with `stack_id.nil?` as authorized for *all* stacks, this "single-stack" token actually authorizes read access to every stack, task and deploy in the Shipit instance — breaking the intended binding "stack the token authorizes == the one stack the widget URL was generated for".

### Finding Description
`CCMenuUrlController#fetch` computes the target `stack` from `params[:stack_id]` and builds a CCMenu URL for that specific stack, but the token it embeds is created like this: [1](#0-0) 

Note the `client` method never passes `stack:` (nor `stack_id:`) to `create_with`/`find_or_create_by!` — it only scopes on `creator` and `name`. The resulting `ApiClient` therefore has `permissions: ['read:stack']` and `stack_id == nil`.

`Api::BaseController` decides which stacks a client can see purely from `stack_id`: [2](#0-1) 

When `current_api_client.stack_id?` is false, the scope resolves to `Stack.all`. Since the CCMenu client always has `stack_id == nil`, its `read:stack` permission is global, not limited to the one stack the widget was generated for.

`Api::CCMenuController` further compounds this by not even using the (theoretically scoping) `stacks` helper for its own `show` action, resolving the stack directly from the URL param instead of the client's allowed scope: [3](#0-2) 

The binding that should hold is: `token.authorized_stack == stack_that_generated_the_token`. In reality: `token.authorized_stack == Stack.all` because `stack_id` was never set at mint time, and even `Api::CCMenuController` ignores stack-scoping entirely for its own endpoint. The same un-scoped token also works against `Api::StacksController#index/#show`, `Api::TasksController`, and deploy endpoints (all under `Api::BaseController`), since they all rely on the same `stacks` helper that resolves to `Stack.all` for this client.

### Impact Explanation
CCMenu URLs are designed to be shared with third-party CI status dashboards/widgets for a single stack (e.g. embedded in a public build-status badge). Any leak of that URL/token — which is explicitly designed to be pasted into external tooling — grants the holder authenticated `read:stack` access to **every** stack in the Shipit installation: full stack listings, task/deploy history, and deploy output, not just the one stack the widget was created for. This matches the "unauthenticated/uncontrolled read of stack state, task streams or deploy output" High-impact class, since a credential intended for narrow, low-sensitivity exposure ends up exposing the state of unrelated repositories/environments across the whole instance.

### Likelihood Explanation
High. This requires no attacker sophistication: any authenticated Shipit user can generate a CCMenu URL for a stack they have access to (`CCMenuUrlController#fetch`), and the resulting token is unconditionally global. No race condition or edge case is needed — the bug is deterministic and present on every single token mint through this endpoint.

### Recommendation
When minting the CCMenu API client, set `stack:` (or `stack_id:`) to the stack the URL was requested for, and include the stack in the `find_or_create_by!` lookup key (e.g. `find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`) so a distinct, stack-scoped client/token is created per stack. Additionally, `Api::CCMenuController#stack` should use the scoped `stacks.from_param!(params[:stack_id])` helper from `BaseController` instead of `Stack.from_param!`, so that even a correctly-scoped client cannot be replayed against a different `stack_id`.

### Proof of Concept
1. As any authenticated Shipit user with access to Stack A, hit `GET /stacks/:A/ccmenu_url` (`CCMenuUrlController#fetch`) to obtain `ccmenu_url` containing `token=<T>`.
2. Inspect the minted `ApiClient` record for this user: `stack_id` is `nil`, `permissions == ["read:stack"]`.
3. Using the same token `T`, call `GET /api/stacks?...` or `GET /api/stacks/:B` for an unrelated Stack B that the user has no access to. Because `current_api_client.stack_id?` is false, `stacks` resolves to `Stack.all`, and the request succeeds, returning Stack B's data.
4. Alternatively call `GET /api/stacks/:B/ccmenu.json?token=T` directly — `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` with no scoping check at all, returning Stack B's latest deploy/build status.
