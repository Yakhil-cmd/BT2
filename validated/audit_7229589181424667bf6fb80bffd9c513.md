### Title
Webhook signature verification org is decoupled from the repository/team actually written, allowing cross-organization forgery when any configured org has no `webhook_secret` — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* organization's secret to check the HMAC signature against using `repository_owner`, taken from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. The value actually acted upon by the event handlers (`Handler#repository_name` = `payload.dig('repository','full_name')`, or `MembershipHandler`'s `params.organization.login` used to create/attach a `Team`) is read independently from the same untrusted, unsigned-at-verification-time JSON body. `GithubApp#verify_webhook_signature` further returns `true` unconditionally when `webhook_secret` is blank [1](#0-0) . Shipit explicitly supports multi-organization configs where an org can be defined with `webhook_secret: # nil` [2](#0-1) .

### Finding Description
The equality that should hold is: **organization that authenticated the request == organization/repository the handler writes to**. In this engine that equality is broken:

1. `verify_signature` resolves the org via `repository_owner` and fetches that org's `GithubApp` to check the signature [3](#0-2) .
2. If that org's `webhook_secret` is unset/blank (a supported configuration, as shown in the sample multi-org secrets file), `verify_webhook_signature` short-circuits and returns `true` for *any* payload/signature pair [1](#0-0) .
3. Once past this check, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the entire, attacker-controlled JSON body to the event handler [4](#0-3) .
4. The handler's target repository is derived independently from `payload.dig('repository', 'full_name')` [5](#0-4) , and for the `membership` event, the target `Team`/organization is derived from `params.organization.login`, which is written straight into `Team#organization` (a field that gates `Shipit.github_teams` authorization) [6](#0-5) .

Because the field used to pick the verifying secret (`repository.owner.login` / `organization.login`) is never cryptographically bound to the field the handler actually acts on (`repository.full_name`, or that same `organization.login` re-used to create teams under an org with no secret), an attacker only needs the target Shipit deployment to have **one** organization configured without a `webhook_secret` (nil/blank is explicitly a valid, documented configuration state) to post arbitrary, unsigned JSON to `/webhooks` claiming to be that no-secret org while asserting membership/team data for that same org — since `MembershipHandler` trusts `params.organization.login` to create the `Team` and grant/revoke `Membership` for arbitrary GitHub logins supplied in `params.member.login` [7](#0-6) .

### Impact Explanation
`Team#organization` and its members feed into `Shipit.github_teams` group-based authorization used elsewhere in the app (e.g., to grant users elevated capabilities associated with named teams). An unauthenticated attacker who can reach `/webhooks` and knows (or discovers) that the deployment has configured at least one organization without a `webhook_secret` can forge `membership` events to add an arbitrary GitHub login as a member of any team under that org, and — because `Team.find_or_create_by!` keys only on `github_id` with no ownership check tying it back to a verified installation — escalate an arbitrary account into whatever `Shipit.github_teams` authorization that team confers. This matches the High-severity category: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Exploitability depends entirely on the deployment having at least one organization entry with an unset `webhook_secret`. This is not a hardening violation invented by us — the shipped sample secrets file (`config/secrets.development.shopify.yml`) shows this exact shape as a normal, supported configuration for multi-org Shipit installs, and `GithubApp#verify_webhook_secret`'s `return true unless webhook_secret` line makes this an intentional "no verification" fallback rather than a bug elsewhere. No credential, session, API token, or GitHub App private key is required — only network access to the public `/webhooks` endpoint and knowledge of which org (if any) in the multi-tenant instance lacks a secret, which is discoverable by simply trying an org name and observing the `422`/`200` outcome (unknown org → 422 with `GithubOrganizationUnknown`; known org without secret → normal processing regardless of signature).

### Recommendation
- Do not allow `webhook_secret` to be blank in any environment that is not explicitly a test/dev stub; fail closed (return `false`, not `true`) when no secret is configured for a production `GithubApp`.
- Bind the field used for authentication to the field used for authorization: derive `stacks`/`Team#organization` targets from the same verified org context established during `verify_signature`, rather than re-parsing `repository.full_name` / `organization.login` a second time independently in each `Handler`.
- Add a guard in `MembershipHandler#find_or_create_team!` (and `Handler#repository_name`) asserting `params.organization.login == verified_organization` (or `repository.owner.login == verified_organization`) before mutating `Team`, `Membership`, or `Stack` records.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs: `victim-org` (has `webhook_secret` set) and `test-org` (has `webhook_secret: nil`, as shown in the shipped sample config).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "test-org" },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "test-org").verify_webhook_signature` returns `true` unconditionally (blank secret) [1](#0-0) .
3. `MembershipHandler#process` creates `Team` with `organization: "test-org"` and adds `attacker-github-login` as a member [8](#0-7) .
4. If `Shipit.github_teams` (or any downstream authorization check) references `test-org` team membership for granting privileges, `attacker-github-login` now satisfies that authorization without ever authenticating to GitHub or Shipit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
