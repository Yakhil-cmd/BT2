## Title
Webhook Signature Verification is Selected by an Attacker-Controlled Organization Field That Is Never Bound to the Repository/Team the Event Actually Mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to check against using an organization name pulled straight out of the still-unverified JSON body, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever that particular organization has no `webhook_secret` configured. Because Shipit explicitly supports hosting several independent GitHub organizations from one instance, each with its own *optional* secret, the field used to pick the verifier (`repository.owner.login` / `organization.login`) is never cryptographically tied to the field the event handlers actually act on (`repository.full_name`, `team.id`, `member.login`, etc.). Any organization configured without a secret becomes a skeleton key: a request claiming to be from that org bypasses signature verification entirely while still being free to name any other tracked repository, stack, or `Team` record for the handlers to mutate.

### Finding Description
`WebhooksController#verify_signature` derives the verifying app before the signature is validated: [1](#0-0) [2](#0-1) 

`repository_owner` is read from the attacker-suppliable JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and fed into `Shipit.github(organization: repository_owner)`, which resolves per-organization app configs from `secrets.github`: [3](#0-2) 

`verify_webhook_signature` then short-circuits when that resolved app has no configured secret: [4](#0-3) 

`webhook_secret` is documented and shipped as optional in every secrets template (`config/secrets.development.example.yml`, `template.rb`, `docs/setup.md`), so it is entirely plausible/likely that at least one configured organization in a multi-org Shipit install has none configured.

Once verification passes (either because the resolved org has no secret, or trivially in any single-app setup), `Shipit::Webhooks.for_event` dispatches to handlers that read *other, independent* fields from the same body to decide what to mutate — e.g. `PushHandler` uses `repository.full_name`/`ref` to select and sync any tracked `Stack`: [5](#0-4) [6](#0-5) 

and `MembershipHandler` uses `team.id`/`member.login` to add or remove arbitrary users from any `Team` record purely by numeric `github_id`, with no scoping back to the organization that was actually authenticated: [7](#0-6) 

`Team` records gate global authorization via `Shipit.github_teams`/`User#authorized?`: [8](#0-7) [9](#0-8) 

So the equality that should hold — *the organization whose secret authenticated this request* == *the organization/repository/team the event is permitted to mutate* — is never enforced. It only holds "by construction" when every configured organization enforces a secret and GitHub itself is the only party that can produce a validly-signed body for that org. The moment any one configured org is left without a secret (which the docs call optional and multiple shipped templates default to), the binding collapses completely: a request need only claim to be `repository.owner.login`/`organization.login` = that unsecured org to skip verification, while every other field in the same JSON body — which repository/stack to sync, which team/user to add — is fully attacker-controlled and unconstrained by that org.

### Impact Explanation
This maps to the accepted High-impact category "escalation into `Shipit.github_teams` authorization" and to "unauthorized deploy/rollback" via cross-repository writes: an unauthenticated network attacker who can identify (or already knows, e.g. their own onboarded org on a shared/multi-tenant Shipit instance) one org lacking a `webhook_secret` can:
- Forge a `membership` event naming that org, but with a `team.id` equal to the `github_id` of a `Team` used in `Shipit.github_teams`, and add an arbitrary GitHub login to that privileged team — directly escalating into the application's authorization gate.
- Forge `push`/`status`/`check_suite`/`pull_request` events naming that org while pointing `repository.full_name` at any other tracked repository, triggering `GithubSyncJob`, closing/archiving review stacks, or manipulating commit statuses for stacks that belong to organizations with a properly configured secret.

### Likelihood Explanation
No session, no API token, no GitHub App private key, and no repository write access are required — the endpoint is public (`/webhooks`) by design and `verify_signature` is the *only* gate. The only precondition is that at least one organization Shipit is configured to serve has no `webhook_secret`, which the engine's own documentation and every shipped secrets template mark as optional/default-nil, making this a realistic operational state rather than a hypothetical misconfiguration outside the documented usage.

### Recommendation
- Make `webhook_secret` mandatory for every configured GitHub organization (fail fast at boot/initializer time if any org config omits it), removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.
- After signature verification succeeds, re-validate that the organization used to select the verifying app actually owns the repository/team named elsewhere in the payload (e.g., assert `repository.full_name.split('/').first == repository_owner`, and scope `MembershipHandler`'s `Team.find_or_create_by!` lookup by `organization` in addition to `github_id`) so no single field decoupling can cross organizational boundaries.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app schema; leave `webhook_secret` unset for `OrgB` (matches shipped templates' default).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "OrgB" },
  "team": { "id": <github_id of a Team referenced in Shipit.github_teams>, "name": "x", "slug": "x", "url": "https://x" },
  "member": { "login": "attacker-controlled-login" }
}
```
No `X-Hub-Signature` header is required to be valid because `Shipit.github(organization: "OrgB").verify_webhook_signature` returns `true` unconditionally (`webhook_secret` is nil for `OrgB`).
3. `MembershipHandler#process` runs unauthenticated, adding `attacker-controlled-login`'s Shipit user to the privileged `Team`, which is checked by `User#authorized?` for every future login against `Shipit.github_teams`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
```
