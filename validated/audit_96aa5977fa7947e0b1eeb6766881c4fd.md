### Title
Malformed DER Signature/Pubkey Passed to Native secp256k1 Parser Without Validation Causes Out-of-Bounds Memory Corruption in `is_valid_sig` - (File: signature.js)

### Summary
`signature.js` wraps the native N-API `secp256k1` addon (package.json pins `"secp256k1": "^4.0.3"`, native build used outside the browser bundle) [1](#0-0) . The oscript/AA formula function `is_valid_sig` lets *any* unprivileged trigger sender, AA author, or unit poster supply an attacker-controlled `signature` and `pem_key` string that is base64/hex-decoded and fed straight into `ecdsa.signatureImport()`, `ecdsa.signatureNormalize()`, and `ecdsa.ecdsaVerify()` inside `verifyMessageWithSecp256k1PemPubKey` [2](#0-1) , reached from `formula/evaluation.js`'s `is_valid_sig` case [3](#0-2) . The only pre-checks are generic (length ≤ 1024, valid hex/base64 charset) [4](#0-3) ; there is no validation of DER structural correctness before handing the buffer to the native parser, which is directly analogous to CVE-2024-0110, where `cuobjdump` passed an unvalidated, attacker-crafted ELF byte stream into a native parser and triggered an out-of-bounds write.

### Finding Description
`verifyMessageWithSecp256k1PemPubKey(message, signature, der)` slices a fixed 65-byte window out of the base64-decoded PEM DER blob (`der.slice(bitStringIdx + 3, bitStringIdx + 68)`) based on an `indexOf` match, then converts the caller-supplied `signature` into a `Buffer` and passes it unmodified to `ecdsa.signatureImport(sigBytes)` whenever its length is not exactly 64 bytes [5](#0-4) . `signatureImport` in the native `secp256k1` package parses the buffer as ASN.1 DER — a raw byte-oriented parsing routine similar in class to the vulnerable `cuobjdump` ELF parser in the CVE. Ocore performs no structural DER validation itself (no length-prefix cross-checks, no bounds checks on nested TLV fields) before invoking the native parser; it only checks the overall string is valid hex/base64 and ≤1024 characters [4](#0-3) . Any malformed/truncated/oversized nested-length DER byte sequence that satisfies "valid hex or base64" is passed straight through into native code.

This is directly reachable by:
- An AA trigger sender or unit poster invoking `is_valid_sig(message, pem_key, sig)` in an oscript/AA definition or formula, with fully attacker-controlled `sig` and `pem_key` values [6](#0-5) .
- The definitions module also references `secp256k1` for authentifier verification (`definition.js`), meaning the same class of unvalidated native parsing can occur during ordinary unit/address-definition signature validation for `sig` and multisig authentifiers.

### Impact Explanation
If the native `secp256k1` addon's DER parser exhibits an out-of-bounds read/write on malformed input (the same bug class as CVE-2024-0110), a full/hub node evaluating a hostile AA trigger or a unit's `is_valid_sig` condition could crash (denial of service — network unable to confirm new units), or in a worse case suffer memory corruption enabling code execution inside the node process, since this executes during consensus-critical unit/AA validation reachable from a single posted unit or trigger by an unprivileged party. Because validation results can differ between nodes on differently-behaving native builds/versions, this can also cause node disagreement on validity.

### Likelihood Explanation
Medium-High: `is_valid_sig` and `sig`/multisig authentifier verification are ordinary, unprivileged, reachable paths (any unit poster or AA author can invoke them), require no special permissions, and the only defense (hex/base64 charset + length checks) does not validate DER TLV structure, so a crafted "malformed but hex/base64-valid" signature byte string can reach the native parser unimpeded.

### Recommendation
- Perform strict DER structural validation (tag/length consistency, no overflow of stated lengths beyond buffer bounds, reject nested length fields exceeding remaining buffer size) before calling `ecdsa.signatureImport()` in `signature.js`'s `verifyMessageWithSecp256k1PemPubKey`.
- Pin and audit the exact native `secp256k1` addon version for known parser-safety fixes; consider routing this validation path through the browser-safe pure-JS `secp256k1/elliptic` implementation (already used for browser builds per the `package.json` `"browser"` field) which does not risk native memory corruption, or add a JS-side pre-parser that rejects any input not matching a strict, minimal DER-encoded ECDSA signature grammar.
- Add fuzz tests with truncated/oversized/deeply-nested DER buffers exercised through `is_valid_sig` and definition `sig` verification to confirm no native crash/OOB occurs.

### Proof of Concept
1. Deploy an AA (or oscript-evaluated unit) containing `is_valid_sig(message, pem_key, sig)` where `pem_key` is any valid secp256k1 PEM key (reaching the `bPostPemCurvesFix` branch) [7](#0-6) .
2. Craft `sig` as a byte string that is valid base64/hex (passes `ValidationUtils.isValidHexadecimal`/`isValidBase64`), ≤1024 chars, but is a malformed DER signature encoding (e.g., a length byte claiming more bytes than actually present, or deeply nested/oversized SEQUENCE/INTEGER length fields) [4](#0-3) .
3. Post the trigger/unit to any full node or hub. During AA/oscript evaluation, `verifyMessageWithSecp256k1PemPubKey` decodes `sig` and calls `ecdsa.signatureImport(sigBytes)` on the malformed buffer [8](#0-7) .
4. If the underlying native `secp256k1` parser is vulnerable to the same bug class as CVE-2024-0110 (unvalidated malformed byte-stream parsing), the node process crashes or exhibits memory corruption, denying consensus/validation service across the network.
