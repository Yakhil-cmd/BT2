### Title
Webhook Organization Signature Verification Is Not Bound To The Repository/Commit The Handler Actually Writes To - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against using an organization name pulled out of the *same* attacker-supplied JSON body that the event handlers later use to decide what to write. For most handlers this is merely fragile, but `StatusHandler` doesn't even scope by repository — it updates commit statuses purely by SHA across the entire install. This reproduces the report's bug class: a value the signature "authenticates" is never actually bound to the value the code acts on, letting a webhook validated for one (attacker-reachable) organization write state belonging to a completely different, unrelated repository/stack.

### Finding Description
`verify_signature` derives the organization used to select the verification secret directly from the untrusted payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a *per-organization* secret when the multi-tenant config schema is used (documented in `config/secrets.development.example.yml`, which explicitly shows organizations configured with `webhook_secret: # nil` by default): [3](#0-2) 

And `verify_webhook_signature` treats a blank secret as automatically verified: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

So in a multi-organization deployment, any organization entry left without a configured `webhook_secret` causes `verify_signature` to pass for *any* payload whose `repository.owner.login` (or `organization.login`) names that org — with no cryptographic proof required at all.

Crucially, the field used to select/verify the organization (`repository.owner.login`) is never cross-checked against the field the handlers use to decide what data to mutate. For `StatusHandler`, there isn't even a repository check — it updates commit state purely by SHA, globally: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Other handlers (`PushHandler`, `PullRequest::*Handler`) do scope by `repository.full_name`, but that field also comes from the same unauthenticated JSON body used to pick the verification secret — it is never checked to match the organization that "verified" the request: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization verified by signature == organization owning the repository/commit mutated by the handler`. Because both sides are read from the same forgeable payload with no cryptographic tie between them, and because a single blank-secret organization anywhere in the install lets signature verification trivially pass, the equality is broken: an attacker can get `verify_signature` to pass for org A (blank secret) while writing state for a repository/commit under an entirely different, properly-secured org B.

### Impact Explanation
`StatusHandler` writes commit statuses (`commit.create_status_from_github!`) that gate CI-based deploy checks (`ci.require` in `shipit.yml`) with zero repository binding — any SHA in the entire Shipit instance can be marked with an arbitrary `state`/`context`, letting an attacker with knowledge of a single blank-secret (or otherwise low-friction) organization entry in a multi-org install forge passing CI status for a victim repository's commit, and thereby help clear the way for an unauthorized deploy of that commit. `PushHandler` similarly triggers `stack.sync_github` for stacks resolved purely from the forgeable `repository.full_name`, independent of which organization's secret validated the request. This crosses the cross-repository-write / unauthorized-deploy bar the rules require for Critical/High impact.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (a documented, supported configuration) where at least one configured organization has no `webhook_secret` set — the documented example config ships with `webhook_secret: # nil` as the default value for each org block, making this a plausible real-world state rather than a contrived one. No repository write access, session, or API token is needed; only knowledge of one weakly-configured organization name, which is discoverable (e.g., via public GitHub org/App installation listings) is required to exploit the missing organization↔repository binding for a different, unrelated org's stacks.

### Recommendation
Bind the verified organization to the object being mutated: after `verify_signature` succeeds, re-derive/validate that the organization owning the resolved repository (via `Repository.from_github_repo_name`) matches `repository_owner` used for signature selection, and reject the webhook otherwise. `StatusHandler#process` should scope its `Commit` lookup to commits belonging to a repository verified to belong to the authenticated organization instead of a bare `Commit.where(sha:)` global lookup. Additionally, treat a missing/blank `webhook_secret` for any configured organization as a hard misconfiguration (refuse to boot in multi-org mode) instead of silently defaulting to "always verified."

### Proof of Concept
1. Operator configures Shipit in multi-org mode with two orgs: `victim-org` (properly configured with a strong `webhook_secret`) and `low-friction-org` (left with `webhook_secret: nil`, matching the documented default).
2. Attacker knows a commit SHA belonging to a stack under `victim-org` (commit SHAs are public on GitHub for public repos, or leak via PR/commit URLs).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "low-friction-org" } },
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
No valid `X-Hub-Signature` is even required, since `verify_webhook_signature` returns `true` for the blank secret configured for `low-friction-org`.
4. `verify_signature` passes (organization = `low-friction-org`, blank secret). `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `victim-org` commit (no repository/org check at all), and marks it with a forged passing CI status via `create_status_from_github!`, independent of the fact that `low-friction-org`, not `victim-org`, was the "authenticated" party.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
