### Title
`has_only()` oscript function fails to neutralize the regex negation delimiter `^`, allowing an AA trigger sender to invert a character-whitelist check - (File: formula/evaluation.js)

### Summary
The oscript function `has_only(str, charset)` is implemented by dynamically building a JavaScript regular-expression character class from the second (attacker-influenceable) argument and testing the first argument against it. The implementation neutralizes only the `]` delimiter (and a trailing unescaped backslash), but does not neutralize the `^` delimiter, which has special meaning only at the start of a bracket expression (negation). If `charset` begins with `^`, the semantics of the whole check silently flip from "string contains only these characters" to "string contains none of these characters," without raising any error.

### Finding Description
`has_only` is evaluated in `formula/evaluation.js`: [1](#0-0) 

The code path is:
1. `sub` (the pattern operand, `arr[2]`) is coerced to a string.
2. It is rejected only if it contains an escaped `\]` or ends in a bare `\`.
3. Any literal `]` is escaped so it cannot prematurely close the bracket expression — this is the only "delimiter neutralization" performed.
4. The (mostly) raw `sub` is spliced directly into `"^[" + sub + "]*$"` and compiled with `new RegExp(...)`.

Within a JavaScript (and POSIX) bracket expression `[...]`, the leading `^` character is a control delimiter that negates the class (`[^abc]` = "any char except a, b, c"), exactly analogous to how `;`, `(`, `)` are shell control delimiters in the referenced `fish-shop/syntax-check` advisory. The `has_only` implementation escapes `]` (to stop early class termination) but omits any handling of a leading `^`, so an attacker who controls the `charset` argument can inject `^` as the first character and completely invert the intended whitelist semantics — the same bug class as CWE-140 (improper neutralization of delimiters) applied to a regex "pattern" instead of a shell command line.

This is reachable by any unprivileged AA trigger sender whenever an AA definition's oscript/ojson code passes trigger-controlled data as the `charset` argument of `has_only` (a common validation idiom for whitelisting characters in identifiers, tickers, addresses, or other user-supplied strings inside AA logic), for example:
`has_only(trigger.data.name, trigger.data.allowed_chars)` or any formula where the second operand derives, directly or indirectly (via `concat`, state vars seeded by trigger data, etc.), from attacker-controlled input.

### Impact Explanation
When an AA relies on `has_only()` to enforce that some trigger-supplied string (e.g., a token symbol, address suffix, or key used to construct a state-variable name, an issued-asset ticker, or a destination) contains only "safe" characters before using that string in further AA logic (building `var[...]` keys, composing outgoing `payment` addresses/messages, gating asset issuance, etc.), an attacker can bypass the check entirely by prefixing the pattern with `^`. This can let unsanitized characters flow into downstream logic that assumed the whitelist held, potentially corrupting AA state-variable keys, forging distinguishable identifiers, or bypassing input-sanitization gates that protect asset-issuance/transfer or payment-composition code paths in the AA — leading to fund loss/freezing or a state divergence in the AA depending on how the AA author relied on the guarantee. The severity is inherently AA-design-dependent, but the root cause is a formula-engine correctness/security bug, not merely a documentation issue, since no fatal error is raised and the flipped check silently returns a boolean that looks legitimate to the caller.

### Likelihood Explanation
Reachable directly by posting a unit that triggers an AA whose oscript code passes trigger data (or any attacker-influenced value) as the pattern argument of `has_only` — no special privilege beyond being able to send a trigger unit is required. The likelihood of exploitation depends on how many deployed AAs use `has_only` this way, but the underlying bug in the shared formula engine is deterministic and requires no race condition, node collusion, or malicious infrastructure.

### Recommendation
In the `has_only` branch of `formula/evaluation.js`, reject (or escape) a leading `^` in `sub` the same way `]` is currently escaped/rejected, e.g. treat a leading `^` as an ordinary character by escaping it (`sub.replace(/^\^/, '\\^')`) or by rejecting patterns whose first character is `^` with `setFatalError`, consistent with the existing rejection of trailing `\` and embedded `\]`.

### Proof of Concept
Given an AA with formula logic such as:
```
has_only(trigger.data.value, trigger.data.charset)
```
A trigger sender posts `data: { value: "$;DROP", charset: "^" }`. Because `charset` starts with `^`, the engine builds `new RegExp("^[^]*$")`, which matches almost any string (any run of any characters), inverting the intended restrictive whitelist (`^[]*$` normally would match only the empty string, but `^[^]*$` matches everything) and letting `has_only` return `true` for a string that in fact violates the intended character whitelist, exactly the opposite of what the AA author expects. This can be reproduced against the evaluator directly by calling:
```js
evalFormulaWithVars({ formula: `has_only("bad$;value", "^")`, ... }, (res) => console.log(res)); // returns true, bypassing the intended whitelist
``` [1](#0-0)
