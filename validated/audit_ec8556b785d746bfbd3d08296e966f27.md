### Title
Fee-on-Transfer Token Accounting Mismatch in Service Chain Bridge Causes Undercollateralization — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and the 1-step `ERC20ServiceChain.requestValueTransfer` path both pull a caller-supplied `_value + _feeLimit` from the user but emit `RequestValueTransfer` with the full caller-supplied `_value`. When the bridged token is a fee-on-transfer token, the bridge receives fewer tokens than it records, yet the counterpart bridge releases or mints the full `_value` to the recipient. This creates a permanent deficit between the bridge's actual token balance and its outstanding obligations.

---

### Finding Description

**2-step path (`requestERC20Transfer`):**

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

`safeTransferFrom` pulls `_value + _feeLimit` from the caller. For a fee-on-transfer token, the bridge actually receives `(_value + _feeLimit) × (1 − feeRate)`. The internal `_requestERC20Transfer` then:

1. Pays the bridge's own ERC20 fee and refunds the change — totalling `_feeLimit` tokens out of the bridge's balance.
2. Emits `RequestValueTransfer` with `valueOrTokenId = _value` (the full caller-supplied amount, not the actual net received). [1](#0-0) 

After step 1, the bridge holds `(_value + _feeLimit)(1 − feeRate) − _feeLimit` tokens, which is less than `_value` by `(_value + _feeLimit) × feeRate`. The event still claims `_value` is being transferred.

**1-step path (`ERC20ServiceChain.requestValueTransfer`):**

```solidity
// ERC20ServiceChain.sol L44-47
function requestValueTransfer(uint256 _amount, address _to, uint256 _feeLimit, bytes calldata _extraData) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
```

`transfer` to the bridge delivers `(_amount + _feeLimit)(1 − feeRate)` tokens. `onERC20Received` is then called with the original `_amount` and `_feeLimit`, so the bridge processes the full nominal amounts. [2](#0-1) 

**Counterpart bridge handling:**

The off-chain relayer reads `valueOrTokenId` from the `RequestValueTransfer` event and calls `handleERC20Transfer` on the counterpart bridge with the full `_value`. [3](#0-2) 

In **lock/unlock mode**, the counterpart bridge releases `_value` tokens to the recipient, but the source bridge only holds `_value − deficit`. Repeated deposits drain the source bridge's reserves; eventually it cannot fulfill unlock requests.

In **mint/burn mode**, the source bridge burns `_value` tokens but only received `_value − deficit`. If `deficit > 0`, the bridge either reverts (if balance is insufficient) or, if the burn succeeds, the counterpart chain has minted `_value` tokens while only `_value − deficit` were deposited — a net token inflation equal to the transfer fee. [4](#0-3) 

---

### Impact Explanation

**Lock/unlock mode:** The source bridge becomes undercollateralized. The deficit grows linearly with total bridged volume. Users who attempt to bridge back last will find the source bridge unable to release their tokens — a direct loss of bridged assets.

**Mint/burn mode:** Each deposit inflates the total cross-chain token supply by the transfer fee amount. An attacker can repeatedly bridge a fee-on-transfer token to mint more tokens on the counterpart chain than were burned on the source chain, extracting value from the counterpart chain's token supply.

---

### Likelihood Explanation

Any ERC20 token with a configurable transfer fee (e.g., USDT with fee enabled, deflationary tokens) registered on the bridge triggers this automatically. No special privilege is required — any user calling `requestERC20Transfer` or `requestValueTransfer` with such a token is sufficient. The bridge has no guard against fee-on-transfer tokens.

---

### Recommendation

1. **Measure actual received amount** using a balance-before/after check in `requestERC20Transfer`:

```solidity
uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - balanceBefore;
require(actualReceived >= _value, "fee-on-transfer: insufficient received");
```

2. Use `actualReceived − _feeLimit` (or the actual net value after bridge fee) as the `valueOrTokenId` in the emitted event, so the counterpart bridge only releases what was actually deposited.

3. Alternatively, add a registry flag to block fee-on-transfer tokens from being registered as bridge tokens.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token with a 2% transfer fee. Register it on both the source and counterpart bridges in lock/unlock mode.
2. Alice calls `requestERC20Transfer(token, Bob, 1000e18, 0, "")` on the source bridge.
   - Bridge pulls `1000e18` from Alice but receives only `980e18` (2% fee).
   - `RequestValueTransfer` event emits `valueOrTokenId = 1000e18`.
3. Relayer calls `handleERC20Transfer(..., 1000e18, ...)` on the counterpart bridge.
   - Counterpart bridge transfers `1000e18` tokens to Bob.
4. Source bridge now holds `980e18` tokens but has committed `1000e18`.
5. After 50 such deposits (total committed: `50,000e18`, total held: `49,000e18`), the 50th user to bridge back will find the source bridge short by `1,000e18` tokens and be unable to withdraw. [5](#0-4) [4](#0-3) [2](#0-1)
