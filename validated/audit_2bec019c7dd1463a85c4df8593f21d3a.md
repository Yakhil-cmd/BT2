### Title
Shared `configurationNonce` Across Multiple Bridge Configuration Functions Causes Permanent Vote Invalidation — (`contracts/service_chain/bridge/BridgeOperator.sol`, `BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`)

---

### Summary

`BridgeOperator.sol` maintains a single `configurationNonce` counter shared by every configuration-type vote. Both `setKLAYFee()` and `setERC20Fee()` call `_voteConfiguration(_requestNonce)`, which requires `configurationNonce == _requestNonce` and increments `configurationNonce` on success. When two different configuration changes are voted on simultaneously with the same nonce, the first one to reach threshold permanently invalidates all pending votes for the other, mirroring the external report's shared-nonce bug class.

---

### Finding Description

`BridgeOperator.sol` declares a single global counter:

```solidity
uint64 public configurationNonce;
``` [1](#0-0) 

`_voteConfiguration` enforces strict equality against this counter and increments it on every successful vote:

```solidity
function _voteConfiguration(uint64 _requestNonce) internal returns(bool) {
    require(configurationNonce == _requestNonce, "nonce mismatch");
    bytes32 voteKey = keccak256(msg.data);
    if (_voteCommon(VoteType.Configuration, _requestNonce, voteKey)) {
        configurationNonce++;
        return true;
    }
    return false;
}
``` [2](#0-1) 

Both `setKLAYFee` and `setERC20Fee` route through this same function:

```solidity
// BridgeTransferKLAY.sol
function setKLAYFee(uint256 _fee, uint64 _requestNonce) external onlyOperators {
    if (!_voteConfiguration(_requestNonce)) { return; }
    _setKLAYFee(_fee);
}
``` [3](#0-2) 

`setERC20Fee` in `BridgeTransferERC20.sol` does the same. [4](#0-3) 

Because `voteKey = keccak256(msg.data)`, votes for `setKLAYFee` and `setERC20Fee` carry different vote keys and accumulate independently in `_voteCommon`. However, they compete for the same `configurationNonce` slot. Whichever vote reaches threshold first increments `configurationNonce`, making the other vote's nonce permanently stale.

---

### Impact Explanation

**Impact: 2 / 10**

When two configuration changes are voted on concurrently with the same nonce (e.g., operators simultaneously voting to change the KLAY fee and an ERC20 fee), the first to reach threshold succeeds and increments `configurationNonce`. All accumulated votes for the other change are permanently invalidated with `"nonce mismatch"`. Operators must detect the failure, read the new `configurationNonce`, and re-submit all votes from scratch. No bridge assets are directly at risk, but bridge fee configuration is disrupted and operators incur unexpected re-voting overhead. In a high-threshold multi-operator deployment, this can cause prolonged misconfiguration windows.

The Go-layer `SetKLAYFee` and `SetERC20Fee` helpers in `bridge_manager.go` each independently read `ConfigurationNonce` at call time and submit their transaction, with no coordination between the two calls:

```go
rn, err := bi.bridge.ConfigurationNonce(nil)
...
tx, err := bi.bridge.SetKLAYFee(auth.GenerateTransactOpts(), fee, rn)
``` [5](#0-4) 

If both `SetKLAYFee` and `SetERC20Fee` are called concurrently by different operators, both read the same `configurationNonce` value and submit votes with the same nonce, setting up the race.

---

### Likelihood Explanation

**Likelihood: 5 / 10**

The `subbridge_setKLAYFee` and `subbridge_setERC20Fee` RPC endpoints are both publicly exposed to bridge operators. In any deployment with `operatorThreshold[Configuration] > 1`, operators must coordinate votes. It is operationally normal for different operators to initiate different configuration changes in the same time window (e.g., one operator adjusting KLAY fees while another adjusts ERC20 fees). The test suite itself documents this exact scenario under the label `"vote configuration interleaved"` and notes it as a known operational hazard:

```
// Two operators accidentally voted on same nonce different configuration,
// temporarily stuck but recovers by amending the votes.
``` [6](#0-5) 

---

### Recommendation

Separate the nonce namespace per configuration function, or use a per-function nonce mapping:

```solidity
mapping(bytes4 => uint64) public configurationNonces; // selector => nonce
```

Alternatively, encode the function selector into the vote key so that votes for `setKLAYFee` and `setERC20Fee` are fully isolated and cannot consume each other's nonce slot. This matches the per-user nonce pattern used by the value-transfer side (`closedValueTransferVotes` is keyed by request nonce, not shared).

---

### Proof of Concept

Setup: threshold = 2, operators = [A, B, C].

1. Operator A calls `setKLAYFee(fee=7, nonce=0)` → 1 vote recorded for KLAY fee change at nonce 0.
2. Operator B calls `setERC20Fee(token, fee=5, nonce=0)` → 1 vote recorded for ERC20 fee change at nonce 0.
3. Operator C calls `setERC20Fee(token, fee=5, nonce=0)` → threshold reached; `_setERC20Fee` executes; `configurationNonce` becomes 1.
4. Operator B calls `setKLAYFee(fee=7, nonce=0)` → **reverts: "nonce mismatch"** because `configurationNonce == 1 != 0`.

Operator A's accumulated vote for the KLAY fee change is permanently lost. The KLAY fee change must be re-initiated with `nonce=1`, requiring all operators to re-vote from scratch. [2](#0-1) [3](#0-2) [7](#0-6)

func (bm *BridgeManager) SetERC20Fee(bridgeAddr, tokenAddr common.Address, fee *big.Int) (common.Hash, error) {
	bi, ok := bm.GetBridgeInfo(bridgeAddr)
	if !ok {
		return common.Hash{}, ErrNoBridgeInfo
	}

	auth := bi.account
	auth.Lock()
	defer auth.UnLock()

	rn, err := bi.bridge.ConfigurationNonce(nil)
	if err != nil {
		return common.Hash{}, err
	}

	tx, err := bi.bridge.SetERC20Fee(auth.GenerateTransactOpts(), tokenAddr, fee, rn)
	if err != nil {
		return common.Hash{}, err
	}

	auth.IncNonce()

	return tx.Hash(), nil
}
