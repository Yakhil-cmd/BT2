### Title
Webhook signature verification key is selected from an attacker-controlled organization field that is decoupled from the repository actually written by handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and thus which `webhook_secret`) to validate the HMAC signature against, using `repository_owner`, a value read directly out of the untrusted JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every downstream `Shipit::Webhooks::Handlers::Handler` subclass then determines which repository/stack to mutate using a *different* payload field, `payload.dig('repository','full_name')` (or, for `MembershipHandler`, `params.organization.login` for team scoping but an independently attacker-supplied `member.login`). Because Shipit supports a multi-tenant `github:` config keyed by organization (`lib/shipit.rb#github_app_config`), an attacker who knows the `webhook_secret` for *any one* configured organization can forge a payload whose `repository.owner.login` selects that known-secret organization for signature verification, while setting `repository.full_name` (or other action-determining fields) to point at a different organization/repository that the attacker does not control. ### Finding Description
The binding this analog breaks is: **organization whose secret authenticated the request == organization/repository the handler mutates**.

1. `verify_signature` extracts `repository_owner` from the raw JSON body and uses it to fetch a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`, which resolves to a per-organization `webhook_secret` when Shipit is configured in multi-tenant mode (`github_app_config`/`github_default_organization` in `lib/shipit.rb`). The signature check only proves the request was signed by *that* organization's secret — it says nothing about the rest of the payload's semantic consistency. [1](#0-0) [3](#0-2) 

2. Once the signature (computed with the organization-specific secret) passes, `WebhooksController#create` dispatches the entire raw payload, unmodified, to every registered handler for the event type. [4](#0-3) 

3. Handlers never re-check that the organization used for signature selection matches the object being written. `Handler#repository_name`/`#stacks` resolve entirely from `payload.dig('repository', 'full_name')`, an attacker-supplied string with no cryptographic tie to `repository_owner`. [2](#0-1) [5](#0-4) 

4. `MembershipHandler` similarly trusts `params.organization.login` to scope the `Team`, and `params.member.login` to add/remove membership — both are independent, attacker-chosen strings within the same signed-but-uncorrelated payload. [6](#0-5) 

The intended invariant (implicit in a genuine GitHub-originated webhook) is that `repository.owner.login` always matches the owner segment of `repository.full_name`, because GitHub itself generates that JSON. Because Shipit's controller re-derives the verification key straight from the untrusted body instead of anchoring it to a fixed, deployment-level GitHub App identity (or validating post-hoc that `repository_owner` == owner segment of `repository.full_name`), an attacker who forges the payload can violate that invariant while still passing signature verification — as long as they know the `webhook_secret` for *some* organization configured on the same Shipit instance.

### Impact Explanation
If exploited, this allows cross-organization/cross-repository writes: an attacker in control of (or who has learned the webhook secret of) one configured GitHub organization on a multi-tenant Shipit deployment can trigger `GithubSyncJob`/stack syncs, commit statuses, check-run refreshes, pull-request metadata updates, or team membership changes (`MembershipHandler#process` calls `team.add_member`/`team.members.delete`) against stacks and teams belonging to a *different* organization on the same instance, even though only one organization's secret was actually proven. This crosses the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact bar, since `MembershipHandler` can add/remove arbitrary GitHub logins from a `Team` that is used by `Shipit.github_teams` for authorization gating (`app/controllers/concerns/shipit/authentication.rb`).

### Likelihood Explanation
Low-to-moderate. It requires: (a) a multi-tenant `github:` configuration with more than one organization defined in `secrets.yml`, and (b) the attacker knowing at least one organization's `webhook_secret` (e.g., because they are a legitimate but low-trust tenant/organization admin on a shared Shipit instance, or the secret leaked for one org only). Given that condition, forging the rest of the payload is trivial since none of the fields determining the mutated object are covered by any check beyond the raw HMAC over the whole body.

### Recommendation
- Do not use an untrusted payload field to select the verification key and then allow a different, uncorrelated payload field to determine the target of the mutation.
- After signature verification, explicitly assert that the organization/owner used to select the `GitHubApp`/secret (`repository_owner`) matches the owner segment of every repository-identifying field the handlers subsequently use (e.g., `repository.full_name`, `organization.login`), and reject the webhook (422) on mismatch.
- Alternatively, bind each handler invocation to the verified organization by passing it explicitly into the handler instead of re-deriving repository/organization identity purely from the body.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` (`lib/shipit.rb#github_app_config`).
2. Attacker knows `org-a`'s `webhook_secret` (e.g., they administer the corresponding GitHub App installation for `org-a`).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over the raw body and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")`, verifies successfully because the signature was indeed produced with `org-a`'s secret. [7](#0-6) 
6. `PushHandler#process` resolves `stacks` from `payload.dig('repository','full_name')` = `"org-b/victim-repo"`, an organization the attacker never authenticated as, and triggers `stack.sync_github` for `org-b`'s stack. [8](#0-7) [9](#0-8)

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
