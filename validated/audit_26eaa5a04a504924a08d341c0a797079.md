### Title
Unscoped caller authorization lets a malicious swap venue drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` authenticates the account owner or delegate once, then executes a caller-supplied swap route through the configured router. [1](#0-0)  The controller narrowly authorizes only its own input transfer to the router, but route-selected venue code still executes beneath the caller’s top-level authorization. [2](#0-1)  A malicious venue can therefore request `token.transfer(caller, attacker, amount)` on an unrelated token; simulation attaches that transfer to the caller’s signed authorization tree, and enforcing mode executes it if the simulated tree is signed. [3](#0-2) 

### Finding Description
The vulnerable sequence is:

1. `swap_collateral` calls `require_authorized_caller`, which performs `caller.require_auth()`. [4](#0-3) 
2. It verifies that the caller controls `account_id`, withdraws collateral, and invokes `swap_tokens`. [5](#0-4) 
3. `swap_tokens` authorizes only `token_in.transfer(controller, router, amount_in)` as controller contract auth, then calls `router.execute_strategy` with the unvalidated route bytes. [2](#0-1) 
4. The router’s swap instruction takes its pool and token addresses from the route’s asset registry and dispatches execution to that route-selected pool. [6](#0-5) 
5. Because the account owner’s authorization is still the root authorization for the invocation, malicious venue code can add another `require_auth` use for that same caller—such as an unrelated-token transfer—to the authorization tree. The test fixture records the malicious transfer under the caller’s `swap_collateral` authorization. [7](#0-6) 
6. In enforcing mode, an honest authorization tree rejects the extra transfer, but signing the simulated poisoned tree permits it and moves the victim’s unrelated wallet balance to the attacker. [8](#0-7) 

This is analogous to credential forwarding across an unexpected execution domain: authorization intended for a collateral swap is extended to a different token and recipient by route-selected code.

### Impact Explanation
A successful malicious route can steal arbitrary wallet tokens held by the account owner or delegate, independent of the collateral amount being swapped. The victim can receive valid swap output and pass all controller solvency checks, so the loss is not bounded by `amount_in`, the route’s declared output, or account collateral. [9](#0-8) 

### Likelihood Explanation
Likelihood is Medium. An attacker cannot directly invoke the strategy on a victim’s account: `swap_collateral` requires the account owner or an active delegate. [10](#0-9)  Exploitation requires the victim to submit an attacker-crafted route and sign the expanded authorization tree produced by simulation. That is still realistic when routes are supplied by a quote service or interface and users do not inspect every nested authorization. The route itself remains reachable through a normal unprivileged strategy call once the owner signs it.

### Recommendation
Do not expose the caller’s root authorization to unvetted route-selected contracts. Prefer a governance-approved venue or pool allowlist so every contract reached below `execute_strategy` is known not to request sender authorization. At minimum, simulation and wallet integrations should decode the complete authorization tree and reject any child invocation other than the expected token pull. The controller should also document that `swap` bytes are untrusted code selection data, not merely routing data.

### Proof of Concept
1. The attacker deploys a route-compatible pool whose swap function executes:
   `wallet_token.transfer(victim, attacker, victim_balance)`. [3](#0-2) 
2. The attacker gives the victim a `swap_collateral` route whose venue pool is that contract while providing enough output to satisfy the strategy.
3. The victim calls:
   `swap_collateral(victim, account_id, current_usdc, amount, new_eth, malicious_route)`.
4. Simulation records `wallet_token.transfer(victim, attacker, victim_balance)` as a child of the victim’s `swap_collateral` authorization. [11](#0-10) 
5. If the victim signs that simulated tree, the unrelated wallet-token transfer succeeds and the attacker receives the victim’s full tested balance while the swap still produces valid collateral. [12](#0-11)
