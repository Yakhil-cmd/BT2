### Title
CCMenu API endpoint bypasses `ApiClient` stack scoping, allowing a stack-restricted token to read the CI/deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` implements a scoping mechanism so that an `ApiClient` created with a `stack_id` can only ever act on that one `Stack`. `Shipit::Api::CCMenuController` overrides the private `stack` helper and looks the stack up directly from `Stack`, completely bypassing that scoping. As a result, any token that is only authorized (`stack_id` set) to read one stack can be replayed against the `ccmenu` endpoint for an arbitrary other stack and will still succeed, because the permission check only verifies the `read:stack` permission string, never the stack scope.

### Finding Description
`BaseController` defines the canonical, scoped stack lookup: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client has one, and `stack` (used by every other API controller such as `Stacks`, `Tasks`, `Deploys`, etc.) always resolves through this scoped relation.

`CCMenuController` however redefines `stack` to bypass `stacks` entirely and query the unscoped `Stack` model directly: [2](#0-1) 

The controller's only authorization gate is `require_permission :read, :stack`: [3](#0-2) 

which calls `current_api_client.check_permissions!(operation, scope)`: [4](#0-3) 

This only checks that the client's `permissions` array contains `"read:stack"` — it never checks `stack_id`. `ApiClient` explicitly supports scoping a client to a single stack (`belongs_to :stack, optional: true`, `stack_id?` used elsewhere for scoping): [5](#0-4) 

The binding that is supposed to hold is: **stack a token authorizes == stack a token touches**. For every other API controller this equality is enforced via `stacks.from_param!`. For `CCMenuController` it is broken: the token only needs `read:stack` permission (global, not scope-specific) and any `stack_id` in the URL is honored, regardless of the token's own `stack_id`.

The route confirms the endpoint takes an arbitrary `stack_id` path segment supplied by the caller, not derived from the token: [6](#0-5) 

The existing test suite for this controller only ever requests the one stack the fixture client is scoped to, and never exercises cross-stack requests, so this scope-bypass is not covered: [7](#0-6) 

By contrast, the equivalent `StacksController` test suite explicitly proves that stack-scoped clients are restricted to their own stack when going through the correct `stacks`/`stack` helper: [8](#0-7) 

### Impact Explanation
An `ApiClient` record can be provisioned with a `stack_id` (as demonstrated by the `here_come_the_walrus` fixture used throughout the API test suite) specifically to hand out a narrowly-scoped, read-only credential for one stack (e.g., embedding a CI status badge/URL for a single project). Because `CCMenuController#stack` ignores that scope, possession of any token carrying `read:stack` permission is sufficient to enumerate the name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and web URL of every stack in the Shipit instance, not just the one it was issued for. This is an escalation from a narrowly-scoped credential to unauthenticated-for-that-resource read access of deploy/build state across the whole instance, matching the "escalation into...unauthenticated read of stack state...deploy output" High-impact category.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission (even one deliberately scoped to a single stack) and knowledge or guessing of another stack's `owner/repo/environment` identifier — no privileged account, GitHub credentials, or session is needed. Stack identifiers are low-entropy, human-readable strings (`owner/repo/environment`), making enumeration straightforward once a single scoped token is obtained.

### Recommendation
Remove the `stack` override in `CCMenuController` and use the inherited, scope-aware `stack`/`stacks` helper from `BaseController` (i.e., delete the private `stack` method in `app/controllers/shipit/api/ccmenu_controller.rb` so it falls back to `stacks.from_param!(params[:stack_id])`), ensuring every `ApiClient`'s `stack_id` restriction is enforced uniformly across all API endpoints.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id = A` with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`, `test/fixtures/shipit/api_clients.yml:12-17`).
2. Authenticate against `GET /api/stacks/<owner>/<repo>/<env-of-stack-B>/ccmenu` using that token (Basic auth or `?token=`), where stack B is a *different* stack the token was never granted.
3. Compare against the equivalent scoped call in `StacksController` (`GET /api/stacks/<stack-B>`), which correctly returns 404/empty because of `stacks.from_param!` scoping (see `test/controllers/api/stacks_controller_test.rb:217-223`).
4. Observe that `CCMenuController#show` returns HTTP 200 with stack B's build status XML despite the token being scoped only to stack A, confirming the scope-bypass caused by `Stack.from_param!` in `app/controllers/shipit/api/ccmenu_controller.rb:29-31`.
