### Title
Truncating division in `pox-5.clar` reward-per-token accrual permanently strands sBTC/STX bond rewards in the reserve - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar` computes a global, precision-scaled "rewards per uSTX" accumulator (`accrued-rewards-per-ustx`) each cycle by dividing total staker rewards by total staked uSTX, using a fixed `PRECISION` constant, analogous to the C4 report's `Bonding.sol` pattern of dividing a value by `10 ** decimals()` and later re-multiplying by the same factor. In both cases, integer division introduces a systematic truncation: the C4 bug caused `vaultSupply` to be inflated and dust `AgentTokens` to be permanently stuck in `FPair`; the `pox-5.clar` analog causes the per-token reward rate to be rounded down every cycle, so the sum of all individual bond-holder reward claims (each computed by multiplying `cumulative-rewards-per-ustx` by a bond's staked amount and dividing again by `PRECISION`) is strictly less than `gross-accrued-rewards` that was actually collected and removed from the "distributable" pool. The undistributed remainder is never returned to bond holders and is not folded back into `reserve-balance` on the majority-case branch (only the `no-stx-stakers` edge case adds `unallocated-staker-cut` to the reserve). This causes a permanent, unrecoverable loss of a portion of stacking/reward value that no unprivileged staker or signer can retrieve — an unbacked/impossible-to-reconcile equality between rewards collected and rewards claimable.

### Finding Description
In `pox-5.clar`'s reward-calculation routine (around lines 2191-2240), the contract computes: [1](#0-0) 

```
(stx-staker-rewards (- remaining-rewards reserve-cut))
(cycle-staked-ustx (get-total-shares-staked-for-cycle stx-cycle none))
(current-rewards-per-ustx (get-rewards-per-token-for-cycle stx-cycle none))
...
(accrued-rewards-per-ustx (if no-stx-stakers
    u0
    (/ (* stx-staker-rewards PRECISION) cycle-staked-ustx)
))
(cumulative-rewards-per-ustx (+ current-rewards-per-ustx accrued-rewards-per-ustx))
...
(reserve-deposit (+ reserve-cut unallocated-staker-cut))
(new-reserve-balance (+ cur-reserve reserve-deposit))
```

`accrued-rewards-per-ustx` is computed via integer division `(/ (* stx-staker-rewards PRECISION) cycle-staked-ustx)`, which truncates any remainder when `stx-staker-rewards * PRECISION` is not an exact multiple of `cycle-staked-ustx`. This is the identical arithmetic shape flagged in the external report: a value is scaled up by a fixed precision constant, divided down, and later multiplied back down per-staker share — the truncated remainder is systematically lost every single reward cycle.

Downstream, each bond holder's actual claimable reward is derived by multiplying their staked amount by `cumulative-rewards-per-ustx` and dividing by `PRECISION` again (per-bond distribution, analogous to `AgentToken.initialize()`'s `supplyParams.lpSupply * (10 ** decimals())` step in the C4 report). Because `stx-staker-rewards` was already fully removed from `remaining-rewards` (i.e., `gross-accrued-rewards - reserve-deposit`), the truncated fraction of `stx-staker-rewards` is neither claimable by any staker (since the per-token rate was rounded down) nor deposited back to `reserve-balance` — the `reserve-deposit` only includes `reserve-cut` and, only in the `no-stx-stakers` edge case, the entire `stx-staker-rewards`. In the normal case (stakers do exist), the rounding dust from `accrued-rewards-per-ustx` truncation is dropped entirely: it is subtracted out of `gross-accrued-rewards` accounting via `total-bond-rewards: (- gross-accrued-rewards remaining-rewards)`, but never reappears in `reserve-balance`, in `cumulative-rewards-per-ustx`, or in any staker's claim.

This breaks the core equality the contract must maintain: `sum(claimable rewards across all stakers) + reserve-balance == total rewards collected for the cycle`. Instead, `sum(claimable rewards) + reserve-balance < total rewards collected`, with the difference permanently and unrecoverably lost — precisely mirroring the C4 finding's "dust `AgentTokens` getting locked in `FPair`" outcome, except here it's sBTC/STX bond reward value that is permanently frozen with no mechanism (no `unwrapToken`-equivalent) to reclaim it.

### Impact Explanation
This is a permanent freezing of a portion of the reward pool every single reward-distribution cycle. While each individual truncation is bounded by `cycle-staked-ustx / PRECISION` in relative terms (extremely small per cycle, since `PRECISION = 1e18` is enormous relative to realistic `cycle-staked-ustx`), the truncation is systematic and compounds every cycle across the contract's lifetime, and — more importantly — establishes a structural discrepancy between rewards collected (removed from `remaining-rewards`/`gross-accrued-rewards`) and rewards that are actually redeemable by any staker or the reserve. This satisfies the High-impact class: "permanent freezing of ... sBTC rewards" / value unlocked/frozen that no unprivileged account can recover, since no staker, signer, or reserve-management function can claim the truncated remainder.

### Likelihood Explanation
This triggers automatically on essentially every reward-distribution call where `stx-staker-rewards * PRECISION` is not an exact multiple of `cycle-staked-ustx` — i.e., almost every cycle in practice, since `cycle-staked-ustx` will rarely divide `stx-staker-rewards * PRECISION` evenly. No attacker action or special permission is required; it is a deterministic consequence of normal, unprivileged reward accrual and claiming. Likelihood is high/certain given the arithmetic.

### Recommendation
Track the truncation remainder explicitly (e.g., `remainder = (stx-staker-rewards * PRECISION) mod cycle-staked-ustx`) and fold it back into `reserve-balance` (or carry it forward into the next cycle's `stx-staker-rewards` calculation) rather than silently discarding it. Alternatively, use a rounding scheme (e.g., round up on the final claim, keeping a running "owed" ledger) so that the sum of all individual claims plus reserve deposits reconciles exactly with `gross-accrued-rewards` for every cycle, eliminating any silently vanishing dust.

### Proof of Concept
Given (illustrative, using the same style as the referenced PoC): `stx-staker-rewards = 100`, `PRECISION = 1_000_000_000_000_000_000`, `cycle-staked-ustx = 3` (not a divisor of `100 * PRECISION`):

```
accrued-rewards-per-ustx = (100 * 1e18) / 3  ; truncates, drops the remainder of 100e18 mod 3
```

When every staker's share is later computed as `staked_amount * cumulative-rewards-per-ustx / PRECISION` and summed across all stakers holding `cycle-staked-ustx` total, the sum will be strictly less than `stx-staker-rewards` by the truncated remainder (up to `cycle-staked-ustx - 1` units in the `PRECISION`-scaled numerator, translating to sub-uSTX/sat-level, but nonzero and unrecoverable) each cycle, and `reserve-balance` is never credited with this difference in the normal (staked > 0) branch, as shown in the `reserve-deposit` computation at [2](#0-1) .
