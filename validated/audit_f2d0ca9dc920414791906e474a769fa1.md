This confirms `here_come_the_walrus` is a real-world fixture example of a `stack`-scoped `ApiClient` (`stack: shipit`, `read:stack` only), demonstrating that this scoping mechanism is a deliberate security boundary in the engine (also exercised by the passing test `"an api client scoped to a stack will only see that one stack"` against `Api::StacksController`). `Api::CCMenuController` breaks exactly this boundary.

### Title
Stack-scoped API client tokens bypass their stack authorization in `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The `deposit_for()` bug is a case where a state-dependent field (`perpetuallyLocked`) is not accounted for by a check, so a value is used ("what the lock is entitled to") differently from what was actually validated ("`locked.end`"). In `Api::CCMenuController` the analog is a scope binding: an `ApiClient` token's authorized stack (`ApiClient#stack_id`) is not accounted for by the action that resolves *which* stack the request actually touches.

### Finding Description
`Shipit::Api::BaseController` implements per-token stack scoping: [1](#0-0) . `stacks` restricts the client to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves the requested `params[:stack_id]` only within that scoped relation — this is the enforced binding: `token.stack_id == stack acted upon`.

`Shipit::Api::CCMenuController` overrides `stack` to bypass this relation entirely: [2](#0-1) . It resolves `Stack.from_param!(params[:stack_id])` against **all** stacks, ignoring `current_api_client.stack_id`. The only authorization gate left is `require_permission :read, :stack` [3](#0-2) , which only checks that `read:stack` is present in the token's `permissions` list via `check_permissions!` [4](#0-3)  — it never checks `stack_id`.

The token that is normally handed out for this exact endpoint is created by `CCMenuUrlController#client`, which is stack-scoped in intent (it's minted per `/ccmenu_url` request for one stack) but is **not actually bound** to that stack in the database — `stack:` is never set on the created `ApiClient`: [5](#0-4) . Combined with `CCMenuController`'s bypass, any holder of such a token (or any other `read:stack` scoped token, like `here_come_the_walrus` in fixtures which *is* explicitly scoped to `stack: shipit`) can pass a different `stack_id` and read another stack's build/deploy status via `/api/stacks/:stack_id/ccmenu.xml`, defeating the `belongs_to :stack` scoping that the rest of the API (`DeploysController`, `StacksController`, `CommitsController`, etc., which use `BaseController#stack`) correctly enforces.

The binding that should hold and is broken: `ApiClient#stack_id` (the stack a token authorizes) `== Stack` resolved by `CCMenuController#stack` (the stack the request actually touches). Before the exploit, this equality holds for every other API endpoint sharing `BaseController#stack`; only `CCMenuController` defines its own `stack` and drops the equality.

### Impact Explanation
This is an unauthenticated-scope escalation matching the "unauthorized read of stack state" High-severity category: a `read:stack`-scoped token minted (or leaked, e.g. via URL/query string, browser history, proxy/CDN logs — the token is transmitted in the query string by design, `uri.query = { 'token' => ... }`) for one stack grants read access to the build/deploy status (`stack.deploys_and_rollbacks.last`, rendered in `shipit/ccmenu/project`) of every stack in the Shipit installation, including stacks belonging to different repositories/teams that the token holder was never authorized to see.

### Likelihood Explanation
High. No privileged access is required beyond possessing any valid stack-scoped, `read:stack`-permission API token — including the low-privilege CCMenu token that Shipit itself hands to any logged-in user for any stack they can view via `CCMenuUrlController#fetch` [6](#0-5) , and which is designed to be embedded in third-party CCMenu client URLs (i.e., intentionally exposed outside the browser session). The exploit is a single parameter substitution (`stack_id`) against `/api/stacks/:stack_id/ccmenu.xml`.

### Recommendation
Remove `Api::CCMenuController#stack`'s override and use the inherited, scope-respecting `BaseController#stack`/`stacks` methods (i.e., resolve `params[:stack_id]` through `stacks.from_param!`, not `Stack.from_param!`), so a stack-scoped token can only ever resolve to its own `stack_id`. Additionally, have `CCMenuUrlController#client` set `stack:` on the created `ApiClient` so tokens minted for CCMenu URLs are actually persisted as scoped, matching their intended, single-stack purpose.

### Proof of Concept
1. As user "walrus", visit `/stacks/acme/repoA/production/ccmenu_url` (`CCMenuUrlController#fetch`), which creates (or reuses) an `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and **no** `stack` set, then returns a URL like `https://shipit.example.com/api/stacks/acme/repoA/production/ccmenu.xml?token=42--abcdef...`.
2. Take the leaked/observed `token` value (e.g. captured from a CI dashboard log, browser history, or shared CCMenu config) and issue: `GET /api/stacks/acme/repoB/staging/ccmenu.xml?token=42--abcdef...` where `repoB/staging` is a different, unrelated stack.
3. `Api::CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`; `require_permission :read, :stack` passes because the token has `read:stack` in its permission list; `stack` resolves `Stack.from_param!('acme/repoB/staging')` with no scoping check.
4. The response renders `repoB/staging`'s latest deploy/build status (`stack.deploys_and_rollbacks.last`) in the XML — data the token was never intended to expose, confirming the cross-stack read.
