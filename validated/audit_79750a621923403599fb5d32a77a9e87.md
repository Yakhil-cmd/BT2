### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` for `prevent_with_label`/`allow_with_label` repos, letting an attacker's PR provision a real `ReviewStack` on their own branch - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` is intended to require `repository.review_stacks_enabled` before any review stack is created, but Ruby's `&&`/`||` precedence makes that flag apply only to the `allow_all` branch of the boolean expression. On a repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, opening a PR without the provisioning label still evaluates `provision?` to `true`, causing `ReviewStackAdapter#create!` to provision a real, attacker-controlled `ReviewStack` whose `branch` is the attacker's PR head ref. Deploy tasks on that stack then run the attacker's `shipit.yml` steps inside an environment that contains `GITHUB_TOKEN` (and any other stack/GitHub App secrets), via `TaskCommands#env` → `Command#start` → `PTY.spawn`.

### Finding Description
The broken binding: the code intends
`stack_gets_provisioned_for_PR == (review_stacks_enabled AND provisioning_policy_allows(PR))`
but actually implements
`stack_gets_provisioned_for_PR == (review_stacks_enabled AND allow_all) OR (allow_with_label AND has_label) OR (prevent_with_label AND !has_label)`.

The offending code: [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, `review_stacks_enabled` only gates the `provisioning_behavior_allow_all?` disjunct. It is never ANDed with the `allow_with_label?`/`prevent_with_label?` disjuncts. So for a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (both legitimate, non-default settings a maintainer might pick specifically to keep review stacks off while still tracking labels), any PR without the provisioning label makes the third clause `true && true == true`, and `provision?` returns `true` even though review stacks are supposed to be disabled entirely.

Attacker's exact request: open a pull request against the target repo (no special access needed - PRs from forks trigger the `pull_request` `opened` webhook) with no provisioning label, on a branch containing a `shipit.yml` with a deploy/CI step such as `echo $GITHUB_TOKEN` or a step that HTTP-POSTs environment variables to an attacker-controlled endpoint.

Exploit flow:
1. `OpenedHandler#process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` because `provision?` wrongly returns `true` [2](#0-1) .
2. `ReviewStackAdapter#create!` builds `stack_attributes` with `branch: params.pull_request.head.ref` - the attacker's own branch - and persists a new `ReviewStack`, then enqueues it for provisioning [3](#0-2) .
3. Once provisioned, Shipit deploys the review stack; `DeploySpec::FileSystem` reads `shipit.yml` from the checked-out attacker branch, and `TaskCommands#perform`/`#install_dependencies` build `Command.new(command_line, env:, chdir:)` for each attacker-authored step [4](#0-3) .
4. `TaskCommands#env` merges `super` (base `Commands#env`, which includes the GitHub App's `GITHUB_TOKEN` for the org - confirmed by `test "#env uses the correct Github token for a stack"`) with `@stack.env` and `deploy_spec.machine_env` [5](#0-4) [6](#0-5) .
5. `Command#start` spawns the attacker's step text (e.g. `echo $GITHUB_TOKEN`) via `PTY.spawn` inside that merged environment, and the token is written to the task's captured output, which is visible to the attacker via the deploy log / PR check, or actively exfiltrated if the step curls it to an attacker server.

Why guards fail: `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?`; there is no separate re-check of `repository.review_stacks_enabled` before calling `provision?`, and `provision?` itself is the only gate, which is broken by the precedence bug. `require_permission!`, `verify_signature`, and `User#authorized?` are irrelevant here because webhook delivery/signature verification is orthogonal to this authorization decision, and this is exploitable purely by opening an unprivileged PR that emits a legitimately-signed `pull_request.opened` webhook from the attacker's own fork/PR against the target repo.

### Impact Explanation
The attacker obtains execution of arbitrary shell commands (via their own `shipit.yml`) inside a process whose environment contains `GITHUB_TOKEN` and any other secrets in `Stack#env`/`deploy_spec.machine_env`, on a repository whose owner explicitly disabled review stacks (`review_stacks_enabled: false`). This is a Critical impact: exfiltration of `GITHUB_TOKEN`/deploy secrets, and effectively RCE on the deploy host via attacker-controlled `shipit.yml` content executed through `Command`/`PTY.spawn`. It is repeatable against any repository configured with `review_stacks_enabled: false` + `provisioning_behavior: prevent_with_label` (or `allow_with_label`, which has a related but slightly different exposure since it additionally requires the attacker's own label) - i.e., any tenant using this "review stacks disabled, but still gate labeled PRs" configuration.

### Likelihood Explanation
Preconditions are a plausible, legitimate repository configuration: `review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`, and the attacker simply does not apply the provisioning label to their own PR (label application is also attacker-controlled if not locked down, but not even required here since "no label" is the natural default). Attacker cost is trivial: open a PR from a fork with a crafted `shipit.yml`. No secrets, sessions, or privileged roles are required. This is fully repeatable.

### Recommendation
Fix the operator precedence in `provision?` so `review_stacks_enabled` gates all three provisioning behaviors, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to any other handler with the identical expression (e.g. `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler` if they duplicate this logic).

### Proof of Concept
minitest plan (model/controller test, no live GitHub):
1. Create a `Shipit::Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: "prevent_with_label"`.
2. Build a `pull_request.opened` webhook payload/params for that repo with no labels and `head.ref` set to an attacker branch name.
3. Call `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process` (or invoke `respond_to_pull_request_opened?`/`provision?` directly).
4. Assert on both sides of the intended binding:
   - `assert_equal false, repository.review_stacks_enabled`
   - `assert_equal true, handler.send(:provision?)` (demonstrates the bypass - should be `false`)
   - `assert_difference('Shipit::ReviewStack.count', 1) { handler.process }` (demonstrates an unwanted stack is created)
5. For the downstream secret exposure, stub `DeploySpec::FileSystem#steps` to return `['echo $GITHUB_TOKEN']` for the created review stack's `TaskCommands`, stub `Shipit.github(organization:).token` to a known fixture value, run `TaskCommands#perform`, and assert the resulting `Command`'s `env["GITHUB_TOKEN"]` equals the fixture token while `command_line` is the attacker-authored string - showing the attacker-controlled step executes inside an environment containing the secret.
