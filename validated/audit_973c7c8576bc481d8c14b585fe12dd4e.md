### Title
Webhook signature authenticates the payload's `repository`/`organization` owner, but every handler acts on a different, unverified repository selector (`repository.full_name` or bare commit `sha`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to check the HMAC signature against using `repository_owner` (`repository.owner.login` or `organization.login`), but the handlers that subsequently execute never re-check that field. They instead trust `repository.full_name` (or, in the case of statuses, nothing at all) taken from the very same unauthenticated JSON body. This is the same class of bug as the report: one field is verified/covered by the trust check, while a sibling field in the same payload is the one actually acted upon.

### Finding Description
`verify_signature` picks the GitHub App config with:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This only proves the request was signed with *some organization's* webhook secret - it says nothing about which repository the rest of the payload claims to describe. Shipit explicitly supports multiple, independently configured GitHub Apps/organizations sharing one instance (`docs/setup.md`, "Using Multiple Github Applications"), each with its own `webhook_secret`.

Once signature verification passes, `create` dispatches the raw, still-unauthenticated body to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

`Handler` resolves the acted-upon repository from a *different* field, `repository.full_name`, never cross-checked against `repository_owner`/`organization.login`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` uses that unchecked `repository_name` (via `stacks`) to queue syncs: [5](#0-4) 

`StatusHandler` is worse: it does not consult the repository field at all and matches purely by `sha` across the entire instance's `Commit` table:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

The equality that the report's bug class maps to here is: `repository_owner` (verified against the signature) ≠ `repository.full_name`/bare `sha` (the value acted upon). Before the attacker's request, both would naturally match for a genuine GitHub-originated webhook; after a crafted request signed with one org's secret but carrying another org's/repo's identifiers, they diverge, and the divergent field is the one that drives all side effects.

### Impact Explanation
Any actor who legitimately controls (or has been granted, e.g. as an org admin) a GitHub App installation and its `webhook_secret` for **one** organization tracked by a multi-org Shipit deployment can forge a signed webhook whose `repository.owner.login`/`organization.login` names their own org (to pass `verify_signature`) while `repository.full_name` or `sha` names a repository/commit belonging to a **different** tracked organization/stack. This lets them:
- Inject `push` events for a victim stack's tracked branch, forcing `GithubSyncJob` reconciliation on demand.
- Inject fabricated commit statuses via `StatusHandler` for any commit `sha` in the whole instance, regardless of repository, which feeds `Commit#status`/`deployable?` and `Stack#blocking_statuses`/`ignore_ci?` logic used to gate continuous delivery (`schedule_continuous_delivery`), potentially causing an unauthorized/unexpected deploy trigger on a stack the attacker has no legitimate access to.

This crosses a repository/organization trust boundary using only a webhook secret for an unrelated, less-privileged organization - not push access to the victim repo, not a Shipit session, and not the victim's own GitHub credentials.

### Likelihood Explanation
Requires the attacker to already possess a valid `webhook_secret` for at least one organization configured in the multi-tenant `github:` section of `secrets.yml` (a legitimate but low-privilege tenant), which is a realistic scenario for shared/self-hosted Shipit instances serving several GitHub orgs. No other credential, session, or GitHub write access is needed; the mismatch is exploitable purely by crafting the raw JSON POST to `/webhooks` with mismatched `repository.owner.login` vs `repository.full_name`/`sha` fields.

### Recommendation
In `Handler`/`WebhooksController`, resolve the repository/organization consistently: after `verify_signature` succeeds, derive the effective organization from `repository.full_name`'s owner segment (or reject payloads where it differs from `repository_owner`/`organization.login`), and scope `StatusHandler`'s `Commit` lookup by the stack's repository rather than a bare, globally-unscoped `sha`.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.yml`: `attacker-org` (attacker is an org owner and knows/controls its `webhook_secret`) and `victim-org` (hosts a tracked stack with commit `abc123` whose CI is currently failing/pending).
2. Attacker computes `sha1=HMAC(attacker-org secret, body)` over a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "organization": { "login": "attacker-org" },
  "sha": "abc123",
  "state": "success"
}
```
3. POST to `/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates the signature successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` finds `Commit` with `sha: "abc123"` (belongs to `victim-org`'s stack, unrelated to the signing org) and calls `create_status_from_github!`, injecting a fabricated `success` status not scoped to any repository check (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), which can flip `deployable?`/unblock continuous delivery on the victim stack.
