### Title
Caller-controlled swap routes can invoke malicious code that drains wallet assets - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
The controller accepts opaque `swap` route bytes on account strategy entrypoints and forwards them to the configured router without decoding or constraining the contracts that the route may invoke. [1](#0-0) [2](#0-1) 

If a routed contract calls a token transfer from the caller, Soroban records that invocation as a child of the caller’s strategy authorization; signing the simulated tree executes the transfer. [3](#0-2) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` is the strongest path because it operates directly on the caller’s collateral and requires only owner or delegate authorization. [4](#0-3) 

The strategy withdraws the selected collateral and passes the caller-provided `swap` bytes into `withdraw_and_swap_from_supply`. [5](#0-4) 

`swap_tokens` treats those bytes as an opaque router payload, grants the router one exact transfer of controller-held input, invokes `execute_strategy`, and afterward checks only the controller’s measured input spend and positive output receipt. [6](#0-5) 

Those checks bound the controller’s own input grant, but they do not prevent route-selected code below the caller’s root authorization from requesting an additional caller-signed token transfer. [7](#0-6) [8](#0-7) 

The same pattern is reachable through `multiply`, `swap_debt`, and `repay_debt_with_collateral`, which all accept caller-supplied route bytes. [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation
A malicious route can steal assets from the caller’s wallet that are unrelated to the lending position and were never supplied as collateral. [12](#0-11) 

The proof-of-concept drains the victim’s entire `77_770_000_000` wallet-token balance to an attacker while still returning a valid swap output that satisfies the controller’s post-swap checks. [13](#0-12) 

This is theft of user funds rather than a bounded bad-route loss because the stolen amount is not limited by `amount_in`, route output, collateral value, or final account risk checks. [14](#0-13) 

### Likelihood Explanation
Any unprivileged account owner or delegate can reach the vulnerable boundary by submitting a strategy call containing crafted route bytes. [4](#0-3) 

Execution requires the caller to sign the authorization tree containing the malicious child transfer, so practical exploitation depends on an attacker supplying a poisoned route or on a client that does not clearly reject unexpected child invocations. [15](#0-14) 

That precondition does not eliminate the issue because an honest strategy requires no caller child invocation, and the controller provides no structural distinction between a normal route and one that adds an unrelated wallet transfer. [16](#0-15) 

### Recommendation
Do not pass opaque caller-selected route destinations through an authorization context belonging to the user.

Constrain routes to governance-approved venue identifiers resolved by the router or controller, rather than arbitrary contract addresses embedded in caller-controlled bytes. [2](#0-1) 

Until route destinations are constrained, wallets and integrating clients should simulate account strategies, decode the complete authorization tree, and reject any strategy containing child invocations for the caller. [17](#0-16) 

### Proof of Concept
1. The victim supplies USDC and owns a debt-free lending account; the victim also holds an unrelated token in their wallet. [18](#0-17) 

2. An attacker deploys a hop contract configured with the victim address, the unrelated wallet token, the attacker recipient, and the victim’s full wallet balance. [19](#0-18) 

3. The crafted route names that contract as a swap hop while specifying normal USDC input and fair ETH output. [20](#0-19) 

4. The victim submits `swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)`. [21](#0-20) 

5. During simulation, the malicious contract’s `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` appears as a child under the victim’s `swap_collateral` authorization. [17](#0-16) 

6. When the victim signs that recorded tree, the transaction succeeds, the attacker receives the entire wallet balance, and the victim still receives the fair ETH collateral output, so the controller’s measured-output check does not detect the theft. [15](#0-14)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    s.t.env.mock_all_auths();

        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
