### Title
Webhook signature verification keys on `repository.owner.login`, but handlers act on `repository.full_name` — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate the HMAC signature against based on `repository.owner.login` (or `organization.login`) in the JSON payload. Once the signature check passes, every registered event handler determines *which* `Repository`/`Stack` to mutate using a different payload field, `repository.full_name` (`Handler#repository_name`). Because these two fields are never cross-checked against each other, a payload can be legitimately signed for org A while acting on a repository belonging to org B.

### Finding Description
`verify_signature` picks the GitHub App config with: [1](#0-0) 

and [2](#0-1) 

using `params.dig('repository', 'owner', 'login')`. This determines the `webhook_secret` used to verify `X-Hub-Signature` via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Shipit explicitly supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`). This is a documented, supported multi-tenant configuration, not a misconfiguration.

Once the signature check passes, `create` dispatches the raw payload to handlers: [4](#0-3) 

Every handler resolves the target repository/stack via a completely different field: [5](#0-4) 

`Repository.from_github_repo_name(repository_name)` looks up by `full_name`, independent of `owner.login`. `PushHandler` then calls `stack.sync_github` on whichever stack that lookup returns: [6](#0-5) 

`StatusHandler` similarly writes a `Status` (i.e., a fake CI status) to any commit matching a `sha`, regardless of which organization the commit belongs to: [7](#0-6) 

**Binding broken:** `organization authenticated by signature == organization whose repository is written`. Before the attack, the app implicitly assumes `repository.owner.login` (the field the signature check is scoped to) determines the same repository that handlers touch. After an attacker's crafted payload, `repository.owner.login = "attacker-org"` (verified with attacker-org's own valid `webhook_secret`) while `repository.full_name = "victim-org/victim-repo"` (the field handlers actually use) — breaking the equality and letting the signature for one org authorize writes to another org's stacks.

### Impact Explanation
An attacker who controls (or has been granted) their own GitHub App installation/org in a multi-org Shipit deployment — and therefore legitimately knows their own org's `webhook_secret` — can POST a signed `status` event to `/webhooks` with `repository.owner.login` set to their own org (so `verify_signature` validates against their known secret) but `repository.full_name` set to a victim org/repo. `StatusHandler` will then create a fabricated commit status (e.g., a fake "success" CI status) on an arbitrary commit belonging to an unrelated organization's stack, which can be used to satisfy Shipit's deploy safety checks and enable an **unauthorized deploy** of unreviewed code. The same forged-signature technique also lets `PushHandler`/`CheckSuiteHandler`/`MembershipHandler` act on victim-org stacks/teams they have no legitimate access to — i.e., **cross-repository/cross-organization writes**, matching the Critical impact bar defined in scope.

### Likelihood Explanation
Requires only: (a) the Shipit deployment to be configured for multiple GitHub organizations (an explicitly documented, supported configuration), and (b) the attacker to control one of those configured orgs' GitHub App webhook secret — which they legitimately possess as the owner/admin of their own org's App. No compromise of the victim org, no `ApiClient` token, no GitHub App private key theft, and no session is required — only crafting an arbitrary JSON payload signed with a secret the attacker is entitled to know. This is a purely unprivileged-attacker path relative to the victim organization.

### Recommendation
Bind signature-verification scoping to the same field used for repository resolution. Concretely, `verify_signature` and `Handler#repository_name`/`stacks` should both derive the organization/repo from a single, consistently-verified source — e.g., verify the signature per-organization using `repository.full_name`'s owner segment (not a separate `owner.login`/`organization.login` field), and/or have handlers reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs, `AttackerOrg` and `VictimOrg`, each with its own GitHub App and distinct `webhook_secret` (per `config/secrets.development.shopify.yml` pattern).
2. Attacker is the admin of the `AttackerOrg` GitHub App installation and therefore knows `AttackerOrg`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "VictimOrg/victim-repo", "owner": { "login": "AttackerOrg" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(AttackerOrg_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` looks up the GitHub App for `repository_owner == "AttackerOrg"`, validates successfully against the attacker's own secret.
6. `StatusHandler#process` resolves `Commit.where(sha: ...)` for the victim commit (unrelated to `AttackerOrg`) and creates a forged success status, which can unblock a deploy safety check in `VictimOrg`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
