### Title
Webhook signature check selects the verifying GitHub App/secret from unverified payload fields, decoupling "organization authenticated" from "repository written" - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) is used to validate the inbound HMAC by reading `repository_owner` straight out of the request body, before that body has been authenticated by any signature. In a multi-organization deployment, an attacker can pick which org's (possibly blank) secret is used to "authenticate" a forged delivery, while the rest of the payload (`repository.full_name`, branch, sha, etc.) that the downstream handler actually acts on is not required to belong to that same organization.

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), which is populated from the raw JSON body Rails parses for the request - i.e., fully attacker-controlled and not yet checked against any signature: [1](#0-0) 

That value is used to select the `GitHubApp` instance whose secret is used for the HMAC check: [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever the selected org has no `webhook_secret` configured: [3](#0-2) 

Shipit explicitly supports per-organization app configs, each with its own (optional) `webhook_secret`, as documented for multi-org setups: [4](#0-3) 

This creates the binding break described in the rules: "an organization that authenticated versus the repository that is written." The org used to select the verification secret (`repository.owner.login`) is not cryptographically tied to the rest of the payload (e.g. `repository.full_name`, `sha`, `branches`) that the event handler (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) subsequently uses to locate and mutate a `Stack`/`Repository`/`Commit`: [5](#0-4) 

Because no field of the signed payload is checked for internal consistency (i.e., that `repository.owner.login` matches `repository.full_name`'s owner), an attacker who knows (or can find) one organization in the multi-org config with a blank `webhook_secret` can set `repository.owner.login`/`organization.login` to that org to force `verify_webhook_signature` to short-circuit to `true`, while crafting the remainder of the JSON body (full_name, sha, branch, statuses, etc.) to target a *different*, secret-protected organization's stack.

### Impact Explanation
If this precondition holds (one configured org without a secret, alongside another with a secret protecting the target stacks), an unauthenticated attacker gains the ability to inject arbitrary, unsigned GitHub webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that are processed as if they came from GitHub for the targeted repository. Depending on the handler, this can be used to fabricate commit statuses, drive `GithubSyncJob` to sync arbitrary refs, or manipulate team membership - all without holding any Shipit session, `ApiClient` token, or the real `webhook_secret` for the targeted org. This lands in the "authentication bypass" impact bucket since the intended per-org signature control is defeated for that org's inbound events.

### Likelihood Explanation
This is only exploitable in a specific configuration: a host application using the multi-organization `secrets.github` schema where at least one configured organization has no `webhook_secret` set while another configured organization (the actual target) does have one. Single-org configurations without a secret are already fully open by design (`verify_webhook_signature` returns `true` unconditionally when there is only one org, since `webhook_secret` is either set or not for everyone), so that case is not new. This analog is a real, exploitable configuration-dependent gap rather than a purely theoretical one, but it requires the operator to have provisioned an organization with a blank secret in a multi-org install - a state visibly permitted and documented by Shipit's own example config files.

### Recommendation
Do not choose the verifying `GitHubApp` from unauthenticated payload content. Either:
1. Verify the HMAC against every configured organization's secret and accept if any one matches (rather than selecting the org first), or
2. Require every organization in a multi-org config to have a non-blank `webhook_secret`, and fail closed (422) if the resolved org has none, or
3. After successful signature verification, re-derive the acting organization strictly from the same trusted config used for verification, and reject/short-circuit if `repository.full_name`'s owner does not match the organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `OrgA` (target, has a real Stack, `webhook_secret: <real-secret>`) and `OrgB` (`webhook_secret:` blank/nil), mirroring the documented multi-org schema: [6](#0-5) 
2. POST to `/github/webhooks` with header `X-Github-Event: push` and a JSON body where:
   - `repository.owner.login` = `"OrgB"` (or `organization.login` = `"OrgB"`)
   - `repository.full_name` = `"OrgA/target-repo"`, `after` = attacker-chosen SHA, `ref` matching a tracked branch.
3. `verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header value/absence: [3](#0-2) 
4. `create` proceeds to dispatch the unsigned payload to the `push` handler using `repository.full_name = "OrgA/target-repo"`, causing Shipit to act on OrgA's stack despite the request never being authenticated against OrgA's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
