Based on my investigation, I found a valid analog to the reported bug class. The Docker "runs as root by default" bug is about a trust boundary that is *optional to enforce* and silently defaults to the insecure state. The same pattern exists in Shipit's webhook authentication: signature verification is *optional* and silently no-ops when unconfigured, breaking the "organization authenticated" vs. "action performed on its behalf" binding.

### Title
Webhook signature verification silently no-ops when `webhook_secret` is unset, allowing unauthenticated forgery of GitHub webhooks and escalation into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController` verifies inbound GitHub webhooks by delegating to `GitHubApp#verify_webhook_signature`. That method treats a missing `webhook_secret` as automatic success, meaning any organization configured without a webhook secret (an explicitly documented, supported configuration) accepts **any** payload with **no signature check at all**. This lets an unauthenticated attacker forge `membership` webhook events that mutate `Shipit::Team` membership, which directly feeds the application's authorization check.

### Finding Description
`WebhooksController#verify_signature` picks a GitHub App config keyed by the organization named in the payload and asks it to verify the signature: [1](#0-0) [1](#0-0) 

The actual verification logic is: [2](#0-1) 

`return true unless webhook_secret` means that for any organization whose `config/secrets.yml` entry omits `webhook_secret` (documented as optional, e.g. `webhook_secret: # nil` in every shipped example), **all webhook requests bypass authentication entirely**, regardless of the `X-Hub-Signature` header contents.

Once "verified", the controller dispatches to handlers purely based on payload content: [3](#0-2) 

The `membership` event handler trusts the payload's `team.id` (the GitHub team ID) and `organization.login` completely, and uses `find_or_create_by!` on that ID to either create or, critically, **find an already-existing, legitimate `Team` record**, then adds the attacker-chosen `member.login` to it: [4](#0-3) 

`Shipit::User.find_or_create_by_login!` will create a bare `User` row for any login string supplied in the payload: [5](#0-4) 

Authorization to use the Shipit UI is gated on team membership: [6](#0-5) [7](#0-6) 

**The broken binding**: the code assumes "this request was verified as coming from GitHub for organization X" implies "this membership change is authentic." When `webhook_secret` is unset for that org, the left side of that equality is never actually checked, yet the right side (a real, DB-persisted team-membership mutation that later gates `authorized?`) still executes.

### Impact Explanation
An attacker who owns any GitHub account can:
1. Discover (or guess) the numeric `github_id` of a `Shipit::Team` that is included in `Shipit.github_teams` (team IDs are visible via the GitHub API to org members, and often leak through other channels).
2. POST a forged `membership` webhook to `/webhooks` with `X-Github-Event: membership`, `action: added`, `team.id` = that team's GitHub ID, and `member.login` = the attacker's own GitHub login — with no valid `X-Hub-Signature` needed if the org's `webhook_secret` is unset.
3. Log in normally via the real GitHub OAuth flow using their own GitHub account. `User#authorized?` now returns `true` because the forged `Membership` record ties their `User` to a `Team` present in `Shipit.github_teams`, even though they were never actually added to that team on GitHub.

This is a full authentication-bypass / authorization-escalation path into `Shipit.github_teams`, matching the "High" impact tier defined by the rules, achieved with zero credentials beyond owning any GitHub account.

### Likelihood Explanation
Likelihood depends entirely on whether the target Shipit deployment configured a `webhook_secret`. Every shipped configuration template and the setup docs present it as optional: [8](#0-7) [9](#0-8) 

Because this is a documented, supported configuration path (not a deviation from how the engine is meant to be mounted), any installation that follows the docs literally and skips the "(optional)" webhook secret is exposed. I could not confirm from the index how commonly real deployments leave it unset — that is an operational fact outside the code I can verify.

### Recommendation
- Make `webhook_secret` mandatory: fail closed (reject all webhooks, or refuse to boot) if it is not configured, rather than treating an absent secret as "signature verified."
- In `MembershipHandler`, do not trust the numeric `team.id` alone to resolve to an existing team without also validating `organization.login` matches the team's stored `organization`, to reduce the blast radius of any forged payload.
- Update `docs/setup.md` and all `config/secrets*.yml` examples to mark `webhook_secret` as required, not optional.

### Proof of Concept
1. Deploy Shipit with a GitHub App config that omits `webhook_secret` (as shown in the shipped example configs).
2. Identify the `github_id` of a `Shipit::Team` referenced by `Shipit.github_teams` (e.g., via the GitHub API using any account, since team IDs are visible to org members, or via other reconnaissance).
3. Send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <target_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "target-org"},
  "member": {"login": "attacker-github-login"}
}
```
No `X-Hub-Signature` header is required to pass verification because `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `MembershipHandler#process` creates a `User` for `attacker-github-login` and adds it to the existing `Team` matching `github_id` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`).
5. The attacker logs in through the normal GitHub OAuth callback with their real `attacker-github-login` account; `User#authorized?` now returns `true`, granting them access to the Shipit UI as if they were a genuine member of the privileged team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
