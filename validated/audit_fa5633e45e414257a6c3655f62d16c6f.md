### Title
AAs that receive fixed-denomination (indivisible) assets can never pay them back out - ([File: aa_composer.js])

### Summary
An Autonomous Agent (AA) can be triggered with a payment in any asset, including "fixed-denomination" (indivisible) assets, and the received amount is credited to `trigger.outputs[asset]` just like any other asset. However, when the AA composes its response unit, any `payment` message that targets a fixed-denomination asset is silently dropped before the unit is built, so the AA can never forward, refund, or otherwise pay out indivisible-asset funds it received. This mirrors the reported OpenQ bug: a fund type the contract can receive but has no code path to pay back out to the counterparty.

### Finding Description
When a unit triggers an AA, `getTrigger()` sums up all `payment` outputs sent to the AA address into `trigger.outputs[asset]` regardless of the asset's type (divisible or fixed-denomination/indivisible): [1](#0-0) 

Later, when the AA's oscript template produces response `messages`, each `payment` message referencing a non-base asset is checked against its asset properties, and messages for assets with `fixed_denominations` are explicitly marked to be "skipped later" rather than completed: [2](#0-1) 

Immediately after this loop, the code performs a second-pass filter that unconditionally removes any payment message whose asset has `fixed_denominations`, and if that empties the message list, the AA silently finishes with an empty response (no error, no bounce): [3](#0-2) 

The same `sendUnit()` path (and its message filtering) is also used by `bounce()`, which builds the same kind of asset-keyed payment messages from `trigger.outputs` to refund the sender on error: [4](#0-3) 

Since `bounce()`'s messages go through the identical `sendUnit()` pipeline, any indivisible asset included in the bounce is also filtered out before the response unit is composed - it is not returned to the sender even on failure/bounce. There is no other mechanism in `aa_composer.js` (e.g. `pickIndivisibleCoinsForAmount`) invoked for AA-authored payments; that logic exists only in `indivisible_asset.js` for wallet-composed indivisible-asset transfers, not for AA response units.

### Impact Explanation
Once an indivisible/fixed-denomination asset is sent to an AA address as part of a trigger, the AA's balance for that asset increases, but the AA has no way to move it back out: any oscript-authored payment message for that asset is dropped both in normal responses and in bounce responses. The funds become permanently stuck in the AA's balance with no oscript-level mechanism to release them, i.e., a form of AA fund freezing/loss for the depositor. This is a Medium severity issue: it does not corrupt DAG state or double-spend value, but it permanently locks funds sent by an unprivileged unit poster into an AA that can never disburse them, matching the "AA fund loss or freezing" category.

### Likelihood Explanation
Any address (an ordinary unprivileged unit poster) can issue a fixed-denomination asset and send it to any AA as part of a trigger unit — this requires no special privilege, hub cooperation, or malicious actor. AA authors have no visibility into this restriction from oscript itself (the filtering happens purely at the JS composer level after formula evaluation), so an AA that is naively written to forward "any asset it receives" back to the trigger address (a common bounce/echo pattern, as seen in `test/samples/just_a_bouncer.oscript`) will silently fail to return indivisible assets while still consuming them from its balance.

### Recommendation
Either:
1. Reject fixed-denomination asset payments to AAs at the trigger/validation stage (so such transfers cannot reach the AA balance at all), or
2. Implement proper handling for fixed-denomination assets in the AA response composer (`aa_composer.js`), reusing the indivisible-asset payload/coin-selection logic (as in `indivisible_asset.js`) so AA-authored payment messages for such assets can actually be composed and sent, or
3. At minimum, make the silent filtering in `aa_composer.js` (lines 1327-1328 and 1356) cause an explicit bounce with a clear error message when a template attempts to pay out a fixed-denomination asset, so senders/authors are aware such funds cannot be returned, instead of the AA giving `emptyResponse` and quietly keeping the funds.

### Proof of Concept
1. Define an AA whose template contains a bounce-style response (like `test/samples/just_a_bouncer.oscript`) that sends back whatever asset it received to `trigger.address`.
2. Issue a new fixed-denomination (`fixed_denominations: true`) asset and send a payment of that asset to the AA address as the trigger.
3. `getTrigger()` records the indivisible asset amount in `trigger.outputs[asset]`.
4. The AA template composes a `payment` message with that asset targeting `trigger.address`.
5. In `sendUnit()`, the message is marked "will skip it later" (`aa_composer.js:1327-1328`) and then removed entirely in the fixed-denomination filter (`aa_composer.js:1356`); if it was the only message, `handleSuccessfulEmptyResponseUnit` is invoked and no bytes of the indivisible asset are ever returned to `trigger.address`, even though the AA's balance was credited with it.
