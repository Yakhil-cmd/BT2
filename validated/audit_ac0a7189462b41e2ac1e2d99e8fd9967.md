### Title
Unauthenticated webhook `organization`/`repository.owner.login` field selects the signing secret while the `membership` handler mutates a `Team` chosen by an unrelated `github_id`, allowing cross-organization `Shipit.github_teams` escalation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/secret to use for HMAC verification from an unauthenticated field of the request body itself, before the body has been proven authentic. `MembershipHandler` then mutates a `Team` record looked up purely by the numeric `github_id` embedded in the same unauthenticated body, independent of the field used for signature selection. The binding "organization that authenticated the request" == "team/organization actually written" is not enforced, so a crafted payload can be authenticated under one (weakly-configured) organization while granting Shipit-local team membership tied to a completely different, real organization's team — feeding directly into `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to select the verifying GitHub App config directly from the JSON body, before that body's authenticity has been established: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `organization.login` — exactly the field `membership` events use. `Shipit.github(organization:)` then resolves a per-org config (multi-org schema), and signature verification is delegated to that org's `GitHubApp`: [3](#0-2) 

Critically, `verify_webhook_signature` unconditionally passes when that specific organization's `webhook_secret` is not configured — a state the project's own setup docs explicitly describe as optional: [4](#0-3) [5](#0-4) 

Once the request is accepted, `MembershipHandler#process` resolves the target `Team` purely by the attacker-supplied `team.id` (GitHub's numeric team id), independent of the `organization.login` value used moments earlier to pick the verifying secret: [6](#0-5) 

If a `Team` with that `github_id` already exists in Shipit's database (created earlier via any legitimate sync), `find_or_create_by!` simply returns the existing record — the `organization` field is only assigned inside the creation block, so it is never re-validated against the (attacker-controlled) `organization.login` in this request. The handler then unconditionally adds the attacker-chosen `member.login` (auto-vivified via `User.find_or_create_by_login!`) to that team: [7](#0-6) 

This breaks the equality: **organization authenticated by `verify_signature` == organization/team actually written by `MembershipHandler`.** The org used to select (and potentially bypass, if unsecreted) the signing key has no relationship enforced with the `team.id` being mutated — a numeric ID that can reference a team belonging to a completely different, security-relevant organization.

The resulting local `Membership` record matters because `Shipit.github_teams` — the set of teams whose membership gates access to the entire Shipit instance — is backed by these same `Team`/`Membership` records: [8](#0-7) 

and `Authentication#force_github_authentication` gates all engine access on `current_user.authorized?`, which is defined in terms of this local team membership: [9](#0-8) 

### Impact Explanation
Successfully injecting a `Membership` row for a restricted `Shipit.github_teams` team grants the (attacker-controlled or attacker-named) `User` full access to the Shipit instance — deploy, rollback, settings, and API-token creation surfaces — matching the "High - escalation into `Shipit.github_teams` authorization" impact category. Because signature selection is keyed off an unauthenticated field that is decoupled from the field the handler actually mutates on, an attacker only needs one configured organization in the deployment to have an unset `webhook_secret` (an explicitly optional/documented configuration) to authenticate a forged payload targeting an unrelated organization's real team `github_id`.

### Likelihood Explanation
Exploitability depends on deployment specifics that could not be fully confirmed from the engine code alone:
- The engine must be running the multi-org `github:` config schema (`github_default_organization` non-nil) with at least one configured organization lacking a `webhook_secret`.
- The attacker must know (or guess/brute-force) the numeric GitHub `team.id` of a `Shipit.github_teams`-listed team, and that a `Shipit::Team` row for that `github_id` already exists locally (created via prior legitimate sync).

These preconditions are plausible given the project's own documentation calls `webhook_secret` optional, but they are configuration-dependent rather than universally present, so likelihood is moderate rather than certain. Full verification of `Shipit::User#authorized?` implementation details (not retrieved in this pass) is recommended before final triage.

### Recommendation
- Do not use an unauthenticated field of the request body to select the verification secret before the signature is validated. Verify webhook signatures against every configured organization's secret and only proceed once one raw-body verification succeeds; only then trust any organization/team fields inside the body.
- In `MembershipHandler`, re-validate that `params.organization.login` matches the `organization` stored on any pre-existing `Team` record matched by `github_id`, rejecting mismatches rather than silently reusing the existing record.
- Treat a blank `webhook_secret` as a hard configuration error for any organization capable of feeding privileged handlers (e.g., `membership`), rather than silently disabling signature verification for that organization.

### Proof of Concept
Preconditions: multi-org `github:` config with an organization `weak-org` configured without `webhook_secret`, and a `Shipit::Team` already persisted locally with `github_id: 4242` belonging to a genuinely restricted organization referenced in `Shipit.github_teams`.

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything-or-absent

{
  "action": "added",
  "team": { "id": 4242, "name": "x", "slug": "y", "url": "z" },
  "organization": { "login": "weak-org" },
  "member": { "login": "attacker-github-login" }
}
```

1. `WebhooksController#verify_signature` resolves `repository_owner` to `"weak-org"` and calls `Shipit.github(organization: "weak-org").verify_webhook_signature(...)`, which returns `true` unconditionally because `weak-org` has no `webhook_secret` configured.
2. `MembershipHandler.process` looks up `Team.find_or_create_by!(github_id: 4242)`, finding the pre-existing restricted team (its `organization` attribute is untouched since the block does not run for an existing record).
3. `team.add_member(User.find_or_create_by_login!("attacker-github-login"))` persists a `Membership` row.
4. `attacker-github-login`, once they complete GitHub OAuth login to Shipit, passes `current_user.authorized?` because they are now a member of a `Shipit.github_teams` team — despite never having been added to that team on GitHub itself.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```

```ruby
      end
```
