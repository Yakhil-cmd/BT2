### Title
Escrow/arbiter shared-address funds can be permanently frozen if the counterparty's attestation for a `spender_attested` asset is revoked after funding - ([File: arbiter_contract.js], [File: validation.js])

### Summary
Arbiter (and similarly other shared-address escrow) contracts lock a fixed payment amount into a shared address whose spending definition requires sending the exact contract amount to a specific counterparty address (`peer_address`/`offeror_address`) to release funds [1](#0-0) . If the contract's `asset` is a `spender_attested` asset, every payment output of that asset must go to an address currently on the attestor-approved list, checked at validation time via `filterAttestedAddresses` [2](#0-1) . Because the attestor list for an asset can be freely and unilaterally rewritten at any time by the asset's definer through an `asset_attestors` message [3](#0-2) , a counterparty who was attested when the contract/shared address was funded can be de-attested afterward, causing all subsequent attempts to release the escrowed funds to that address to fail permanently with "some output addresses are not attested" [2](#0-1) .

### Finding Description
The shared address definition generated for arbiter contracts requires an exact-amount "has output" spending condition targeting the counterparty's fixed address in order to release funds, whether completing normally or via arbiter dispute resolution [4](#0-3) . This spending-condition check is independent from, and layered underneath, the asset-level payment validation performed in `validatePaymentInputsAndOutputs`, which enforces that for `spender_attested` assets, all output addresses must be attested by the asset's currently-active attestor list, evaluated with `storage.filterAttestedAddresses` [2](#0-1) [5](#0-4) .

The attestor list itself is not immutable at asset creation — the asset definer can post an `asset_attestors` message at any later main-chain index to completely replace the trusted attestor set for the asset, and only the most recent stable list is used for attestation checks [6](#0-5) [3](#0-2) . There is no protection preventing the definer (or an attestor colluding with the definer) from revoking a specific address's attestation after that address has already become the intended, contractually fixed recipient of an escrowed payment.

This exactly parallels the reported Cooler vulnerability: a fixed-recipient "push" transfer (there, `repayLoan()` sending debt tokens back to `lender`; here, the arbiter-contract shared address sending the asset to `peer_address`/`offeror_address`) becomes permanently un-executable if that recipient loses eligibility to receive the asset (there, ERC20 blocklist; here, revoked attestation), because there is no alternate "pull" or bypass mechanism for that asset's transfer condition.

### Impact Explanation
Funds locked into a shared/escrow address for a `spender_attested` asset can become permanently unspendable if the intended recipient's attestation is revoked after the address was already funded. Since the shared-address definition hardcodes the required recipient address for both the "peaceful" completion path and the arbiter-adjudicated path, and the asset-level validation independently requires that address to remain attested, there is no way to redirect or release the funds once attestation is pulled. This results in a permanent freeze/loss of the escrowed asset for the party legitimately entitled to receive it, matching the "AA/contract fund loss or freezing" impact class.

### Likelihood Explanation
The precondition — using a `spender_attested` asset in an arbiter contract, and the definer/attestors revoking an already-funded counterparty's attestation — is entirely within the control of the asset issuer (a single unprivileged actor who created the asset), requiring no special network position, no malicious peer/hub behavior, and no leaked keys. It is directly reachable by any user who chooses to issue a `spender_attested` asset and enter into a contract using it, then update the attestor list via `asset_attestors` at any time, satisfying the "unprivileged asset issuer" reachability requirement.

### Recommendation
Consider snapshotting attestation status at the time funds are locked into the shared address (e.g., recording whether the payee was attested as of the funding unit) rather than re-checking attestation at spend time, or documenting clearly that `spender_attested` assets are unsuitable for use in arbiter/prosaic contracts and other escrow constructs with a fixed hardcoded recipient, since revocation after funding can permanently freeze the escrowed balance. Alternatively, add a fallback unlocking path (e.g., time-locked refund-to-payer branch) in `deriveSharedAddress` that does not depend on the counterparty remaining attested.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and an initial attestor list including attestor `X`.
2. Attestor `X` attests address `B` (the future `peer_address`/`offeror_address` in an arbiter contract).
3. Two parties create an arbiter contract using asset `A`, deriving a shared address whose spending definition requires sending the contract amount to address `B` to complete [1](#0-0) .
4. Party pays into the shared address (`pay()` in `arbiter_contract.js`) [7](#0-6) .
5. Before `complete()` is called, the asset definer posts a new `asset_attestors` message removing `X` or revoking `B`'s eligibility, updating the attestor list [3](#0-2) .
6. Any subsequent attempt to `complete()` the contract (either party-initiated completion or arbiter-resolved release) fails validation with "some output addresses are not attested" because `B` is no longer on the current attested list [2](#0-1) , permanently freezing the funds in the shared address.
