## Analysis Summary

I traced the full path from `Shipit::WebhooksController#create` through `verify_signature` and into `LabelCapturingHandler`/`ReviewStackAdapter`. The finding is real, but it is not really about "sha1 vs sha256" — HMAC‑SHA1 with an unknown secret is not forgeable by an unprivileged attacker, so that framing is a red herring. The actual break is a **key mismatch between the field used to select/authenticate the webhook's secret and the field used to locate the mutated stack**.

### Title
Webhook signature is scoped by `repository.owner.login` while the affected `Stack`/`PullRequest` is resolved by the independent, unchecked `repository.full_name` field, letting a payload authenticated for one (secret-less) org mutate another org's review stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` derives the HMAC secret to check from `params.dig('repository','owner','login')` (`repository_owner`), but every `pull_request` handler (including `LabelCapturingHandler`, `ReopenedHandler`) resolves the actual `Shipit::Repository`/`Stack` to mutate from the unrelated `params.repository.full_name` field. Nothing binds these two values together, so a request that authenticates as one (unsecured) GitHub org can still mutate a `Stack` belonging to a different, properly secured org, as long as that other org's repo/stack already exists in Shipit.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`repository_owner` (used in `Shipit::WebhooksController#verify_signature`, `app/controllers/shipit/webhooks_controller.rb:25,59-62`, to pick `Shipit.github(organization: repository_owner)` and thus the webhook secret) is assumed to equal the owner embedded in `params.repository.full_name` (used in `LabelCapturingHandler#repository`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:110-114`, and in every other `pull_request` handler, to run `Shipit::Repository.from_github_repo_name(...)` and locate the target `Stack`). These are two independently attacker-controlled JSON fields; no code path checks `repository_owner == full_name.split('/').first`. [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only validates the `sha1` algorithm and, critically, `return true unless webhook_secret` — if the org resolved via `repository_owner` has no `webhook_secret` configured, the signature check is a no-op: [3](#0-2) 

Exploit flow:
1. Attacker (unprivileged, no session, no secrets) finds — or in single-org mode, always has — an org whose `webhook_secret` is blank/unset (this is a legitimate, documented deployment style; see `config/secrets.development.example.yml` and `test/dummy/config/secrets.test.json` both shipping `webhook_secret: null`). In single-org configurations, `Shipit.github(organization:)` ignores the `organization:` argument entirely and always returns the single configured app (`lib/shipit.rb:170-181`), meaning `repository_owner` doesn't even need to correspond to anything real to pass `verify_signature` if that single app has no secret. [4](#0-3) 
2. Attacker crafts a `pull_request` webhook body with `action: "reopened"`, sets `repository.owner.login` (or `organization.login`) to the secret-less org, but sets `repository.full_name` to `"<victim-org>/<victim-repo>"` where `<victim-org>` has a `bot_login` configured and a real archived `ReviewStack`.
3. `verify_signature` passes trivially (`return true unless webhook_secret`).
4. `Shipit::Webhooks.for_event('pull_request')` dispatches to `ReopenedHandler` and `LabelCapturingHandler`, both of which resolve the repository purely from `params.repository.full_name`, unarchive the victim's `ReviewStack` (`ReviewStackAdapter#unarchive!`, `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:37-50`) and overwrite `PullRequest#labels` with attacker-chosen values (`label_capturing_handler.rb:98-102`). [5](#0-4) [6](#0-5) 
5. Those labels become uppercased env vars merged into `ReviewStack#env`, which feeds `deploy`/task commands (`app/models/shipit/review_stack.rb:84-93`), and unarchiving re-enqueues the stack for provisioning/continuous delivery, run under the bot identity returned by `Shipit.user` when `bot_login` is configured (`lib/shipit.rb:208-214`). [7](#0-6) [8](#0-7) 

Existing guards do not catch this: `ExplicitParameters` (`params do ... end` in the handlers) only validates types/presence of `repository.full_name`, `pull_request.labels`, etc.; it never cross-checks that value against `repository.owner.login` or against the org used in `verify_signature`. `drop_unhandled_event` and `check_if_ping` are unrelated. No `Repository`/`Stack` validation ties a repository's `full_name` back to the org that authenticated the request.

### Impact Explanation
An attacker who controls (or picks) any Shipit-configured GitHub org lacking a `webhook_secret` can forge `pull_request` events that mutate a **different** org's `ReviewStack`/`PullRequest` records — unarchiving stacks, rewriting labels that become deploy-time environment variables, and re-triggering provisioning/continuous-delivery flows that run under the configured bot identity. This is a cross-tenant write ("a payload for one repository mutating another's stack"), matching the Critical impact category. It is repeatable against any repository/stack that exists in the Shipit instance, for every `pull_request` action handled by label-capturing/open/reopen/labeled/unlabeled handlers, not just `reopened`.

### Likelihood Explanation
Requires: (a) the Shipit instance to have at least one GitHub org/app entry with no `webhook_secret` set (a shipped default in example configs, and in single-org config mode the `organization:` argument is ignored entirely, so this reduces to "no secret configured at all," a common minimal setup), and (b) a victim stack already provisioned for a different repo with `bot_login` set. Attacker cost is a single unauthenticated `POST /webhooks` request with a crafted JSON body — no GitHub credentials, no Shipit session, fully repeatable.

### Recommendation
Bind the two identifiers: after resolving `repository_owner` for secret lookup, verify that `params.repository.full_name` (and/or `params.organization.login`) actually belongs to that same owner before dispatching to handlers, or resolve the target repository/stack using the same `repository_owner` value used for signature verification instead of trusting `repository.full_name` independently. Additionally, treat "no `webhook_secret` configured" as fail-closed (or at minimum log/alert loudly) rather than silently accepting all payloads.

### Proof of Concept
minitest plan (under `test/controllers/webhooks_controller_test.rb`):
```ruby
test "pull_request reopened with mismatched owner/full_name mutates a different org's stack" do
  # Org A ("attacker-org") is configured with no webhook_secret (matches secrets.test.json default)
  victim_stack = shipit_stacks(:review_stack) # belongs to victim repo/org, bot_login configured
  victim_stack.archive!(shipit_users(:walrus))
  victim_stack.pull_request.update!(labels: [])

  payload = {
    action: "reopened",
    number: victim_stack.pull_request.number,
    pull_request: pull_request_payload_for(victim_stack, labels: [{ name: "EVIL_ENV" }]),
    repository: { owner: { login: "attacker-org" }, full_name: victim_stack.github_repo_name },
    sender: { login: "attacker" }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'irrelevant', payload)}"

  post :create, body: payload, as: :json

  assert_response :ok
  victim_stack.reload
  assert_not victim_stack.archived?, "victim stack was unarchived by a forged, mismatched-owner payload"
  assert_equal ["EVIL_ENV"], victim_stack.pull_request.labels
  assert_equal "true", victim_stack.env["EVIL_ENV"]
end
```
Both sides of the equality (`repository_owner` used for auth vs. owner implied by `repository.full_name` used for mutation) diverge and the request still succeeds, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
