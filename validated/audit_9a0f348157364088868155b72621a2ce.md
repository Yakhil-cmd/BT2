### Title
Malicious route can add concealed token transfers to a user's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept attacker-controlled route bytes and execute them through the configured swap router. A route can name an attacker-controlled contract as a venue pool. During execution, that contract can invoke an unrelated token's `transfer(victim, attacker, amount)`, causing Soroban authorization recording to append the theft as a child of the victim's authorization for the top-level lending operation.

The vulnerability is analogous to navigation spoofing: the victim believes they are authorizing a lending operation and its expected swap, while the authorization tree contains an additional token movement unrelated to the displayed action.

### Finding Description
`process_swap_collateral` authenticates `caller` with `require_authorized_caller`, verifies account ownership or delegation, and passes caller-supplied `swap` bytes to `withdraw_and_swap_from_supply`. [1](#0-0) 

The shared router helper authorizes only one exact input-token transfer from the controller to the configured router, then invokes `router.execute_strategy(&controller, &amount_in, swap)`. It measures router spending and output, but it does not decode the route or restrict which pool contracts the route can call. [2](#0-1) 

For a direct router call, `execute_strategy` calls `sender.require_auth()` and performs `token_in.transfer(sender, router, total_in)` under that authorization. [3](#0-2)  Route instructions carry a caller-controlled pool address index, and the dispatcher calls the selected venue adapter. [4](#0-3) [5](#0-4)  For example, the Soroswap adapter invokes `swap` on the pool address supplied by the route. [6](#0-5) 

Because that pool executes below the caller-authorized operation, malicious pool code can call `token.transfer(victim, attacker, amount)` for any token held by the victim. Simulation records that token transfer as a sub-invocation of the victim's top-level authorization; if the wallet or client presents the operation only as a normal swap and the victim signs the generated tree, the host executes the unrelated transfer.

### Impact Explanation
This enables theft of user funds beyond the swap input. The malicious venue can drain any token balance for which the victim's address can authorize `transfer`, provided the victim signs the poisoned authorization tree produced by simulation.

The loss is not bounded by `total_in`, `min_out`, measured router input/output, or the controller's final account-risk checks. Those checks can all pass while an unrelated child transfer sends the victim's wallet tokens to the attacker.

### Likelihood Explanation
Exploitation requires convincing a user to execute a crafted route and sign the resulting authorization tree. An attacker can reach the path without privileges by supplying a malicious route through a caller-authorized strategy such as `swap_collateral` or through a direct `execute_strategy` call.

The attack depends on client-side authorization presentation being incomplete or misleading, matching the security-UI/navigation-spoofing class. Soroban correctly enforces the signed tree; the weakness is that arbitrary route-selected code can add sensitive sub-invocations under an operation the user believes is only a swap.

### Recommendation
Restrict route execution to governance-approved venue contracts, or dispatch by a fixed registry rather than caller-supplied pool addresses.

At minimum, clients must decode and display the complete authorization tree before signing, highlight every token transfer, and reject any `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or `execute_strategy` authorization containing children beyond the exact expected input transfer. Long-term, the router should prevent venue code from adding sender-scoped invocations or isolate routes so venue contracts cannot request the user's authorization.

### Proof of Concept
1. Attacker deploys `RoguePool`.
2. `RoguePool.swap` calls `UnrelatedToken.transfer(victim, attacker, victim_balance)`.
3. Attacker crafts a route whose `pool` address is `RoguePool` and whose quoted input/output behavior is otherwise sufficient to satisfy router checks.
4. The victim calls `controller.swap_collateral(caller=victim, account_id, current, amount, new, crafted_swap)` or calls the router's `execute_strategy(victim, total_in, crafted_swap)` directly.
5. During route execution, the router invokes `RoguePool.swap`.
6. `RoguePool` invokes `UnrelatedToken.transfer(victim, attacker, victim_balance)`.
7. Simulation adds that token transfer as a child invocation under the victim's authorization for the top-level operation.
8. If the victim signs the generated tree without noticing the additional transfer, the unrelated token balance is transferred to the attacker while the swap can still complete normally.
