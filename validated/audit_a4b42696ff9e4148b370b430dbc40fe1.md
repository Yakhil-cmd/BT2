### Title
Missing-vote-account commission lamports are silently dropped from burned/incinerator accounting in `load_and_reward_commission_accounts` - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
In the legacy (`custom_commission_collector` inactive) branch of `load_and_reward_commission_accounts`, when the commission account cannot be loaded (`maybe_commission_account` is `None`), the function silently `return None`s without adding `*commission_lamports` to `total_non_incinerator_burned_lamports`, unlike the two other failure branches in the same closure that do add the dropped lamports to that counter. This creates an accounting asymmetry: commission lamports already counted in `point_value.rewards` for that epoch vanish from both the distributed and burned totals when an eligible commission-account (vote account) is missing at distribution time.

### Finding Description
`load_and_reward_commission_accounts` iterates `reward_commissions` and, for the legacy (pre-SIMD-0232) path, expects `maybe_commission_account` to always be `Some` because "commission accounts were always vote accounts, which cannot be closed unless the account hasn't voted for at least a full epoch": [1](#0-0) 

When that assumption fails and the account is actually missing, the code does:
```rust
let Some(commission_account) = maybe_commission_account else {
    debug!("commission account {commission_pubkey} missing at distribution time");
    return None;
};
``` [2](#0-1) 

This is inconsistent with the other two failure paths in the same `filter_map` closure — the `checked_add_lamports` overflow failure and the `collector_type_checked` error — both of which explicitly add the dropped `*commission_lamports` to `total_non_incinerator_burned_lamports` before returning `None`: [3](#0-2) [4](#0-3) 

The commission's vote account can, per the code's own comment, be closed if it "hasn't voted for at least a full epoch" — this is achievable by an unprivileged owner of a vote account using the standard `Withdraw` vote instruction (draining the account) any time their vote account is not actively voting, which requires no special privilege. If an attacker's own vote account accrues commission eligibility for an epoch (via `calculate_stake_rewards_and_commissions`) and the attacker then withdraws/closes it before the commission-distribution block runs `load_and_reward_commission_accounts`, the account load returns `None`, and the commission_lamports amount for that pubkey is dropped from `total_non_incinerator_burned_lamports`, `distributed_lamports`, and `distributed_to_incinerator_lamports` alike — it is not tracked anywhere in `RewardCommissionLamportAmounts`.

### Impact Explanation
This is an accounting/capitalization bookkeeping bug: `point_value.rewards`/total epoch reward budget included this commission amount, but the amount is neither delivered to any account nor reflected as burned. This falls under capitalization/inflation accounting drift as the prompt's scoped impact — silently missing lamports from the accounting counters used to reconcile the reward budget, inconsistent with the two adjacent failure branches that correctly attribute dropped commission to `burned_lamports`. This is a genuine logic inconsistency reachable by an unprivileged, self-controlled vote account owner, not a theft-of-others'-funds primitive, but it breaks the intended invariant that `point_value.rewards` is fully reconciled across distributed + incinerator + burned totals.

### Likelihood Explanation
Feasible: any user can create/own a vote account (unprivileged), have it become the "commission collector" (default legacy behavior with `custom_commission_collector` inactive means the vote account itself is the collector), accrue commission for an epoch, refrain from voting for a full epoch (satisfying the vote-program's close-eligibility condition), and issue a `Withdraw` instruction that empties/closes the account before the reward-commission distribution block executes. This requires only standard vote-program instructions the attacker is authorized to send against their own account — no elevated privilege, leaked key, or validator control needed.

### Recommendation
In the legacy `else` branch of `load_and_reward_commission_accounts`, when `maybe_commission_account` is `None`, add `*commission_lamports` to `total_non_incinerator_burned_lamports` (mirroring the other two failure paths) before returning `None`, so the dropped commission is consistently and explicitly tracked as burned rather than silently disappearing from the `RewardCommissionLamportAmounts` totals used to reconcile `point_value.rewards`.

### Proof of Concept
Rust integration test plan (in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` test module):
1. Build a reward bank (`create_reward_bank`/`create_default_reward_bank` helpers already used in this file's tests) with `custom_commission_collector` feature deactivated and a vote account eligible for commission this epoch.
2. Run `calculate_stake_rewards_and_commissions` to obtain `RewardCommissions` including this vote account's `commission_lamports` and confirm `point_value.rewards` includes that amount.
3. Between calculation and calling `load_and_reward_commission_accounts`, simulate closing the vote account (zero its lamports / remove it from the accounts store, mimicking a `Withdraw` that drains it).
4. Call `load_and_reward_commission_accounts` and assert:
   - The returned `RewardCommissionAccounts.amounts.burned_lamports` does **not** include the missing account's `commission_lamports` (demonstrating the bug), whereas a comparable overflow/collector-type failure case (existing tests in this file) does add to `burned_lamports`.
   - Sum of `distributed_lamports + distributed_to_incinerator_lamports + burned_lamports` does not equal the original `point_value.rewards` contribution for that commission, proving the reconciliation invariant (`point_value.rewards >= distributed + incinerator + burned + total_stake_rewards`, with all consumed rewards accounted for) is violated by an untracked gap equal to the dropped commission.
