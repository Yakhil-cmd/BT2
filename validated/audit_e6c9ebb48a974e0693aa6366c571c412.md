### Title
Webhook signature verification org is not bound to `MembershipHandler`'s written `Team#organization`, allowing a cross-organization team spoof - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to authenticate a webhook from `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. [1](#0-0)  `MembershipHandler#find_or_create_team!` instead trusts `params.organization.login` verbatim to stamp `Team#organization`, with no check that it matches the organization whose secret actually verified the request. [2](#0-1)  Because the attacker fully controls the raw JSON body (including a `repository` object that a real GitHub `membership` event would never contain), they can decouple the two fields and get a request signed by "their" org's secret to write/mutate a `Team` row tagged with a victim org's login.

### Finding Description
The binding the code implicitly assumes is:
`organization_that_signed_request (repository_owner used in verify_signature) == params.organization.login (written into Team#organization by find_or_create_team!)`

This does not hold. `repository_owner` is computed as:
```
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
``` [3](#0-2) 

and is the sole input to `Shipit.github(organization: repository_owner)`, which selects the `webhook_secret` used for HMAC verification. [4](#0-3) 

`MembershipHandler`'s `params` schema requires only `action`, `team`, `organization.login`, and `member.login` — it does not forbid extra top-level keys, and `ExplicitParameters` does not strip/reject the raw payload keys used by the controller (`repository`) before the handler is instantiated with the full parsed body. [5](#0-4)  `Handler#initialize` parses `params` from the full `payload` but `payload` itself (the raw hash) is retained and it's `payload`, not the filtered `params`, that the controller's `repository_owner` lookup uses at the controller level (before handler dispatch). [6](#0-5) 

Exploit flow:
1. Attacker legitimately controls a GitHub organization ("Org A") that is registered as a distinct `Shipit.github(organization:)` source (multi-tenant Shipit installations configure per-organization GitHub Apps/`webhook_secret`s, as shown by the `OrgOne`/`OrgTwo` config test). [7](#0-6) 
2. Attacker crafts a `membership` webhook body that includes a synthetic `repository.owner.login: "org-a"` (a key real GitHub `membership` events do not send) alongside `organization.login: "org-b"` (the victim org) and a `team.id` chosen to collide with — or newly create — a team record.
3. `verify_signature` resolves `repository_owner` to `"org-a"`, fetches Org A's `webhook_secret`, and validates the HMAC the attacker legitimately computed with their own secret — the signature check passes. [4](#0-3) 
4. `MembershipHandler#find_or_create_team!` then creates/updates a `Team` keyed by `github_id: params.team.id` and sets `team.organization = params.organization.login`, i.e. `"org-b"` — never checked against the `"org-a"` secret that authenticated the request. [2](#0-1) 
5. `process` then adds/removes the attacker-chosen `member.login` on that team via `team.add_member`/`team.members.delete`. [8](#0-7) 

None of the existing guards catch this: `verify_signature` only checks the HMAC against whichever org key it derives from the attacker-supplied `repository`/`organization` object — it never cross-checks that value against the handler's own `organization.login` field. `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of required fields, not cross-field consistency or extraneous `repository` keys. There is no separate authorization step in `Team`/`Membership` models. [9](#0-8) 

### Impact Explanation
An attacker who controls a webhook-registered organization in the same multi-tenant Shipit install can forge signed `membership` events that are attributed to a different organization string. This lets them add or remove members from a `Team` row belonging (by name) to another org, and — because `User#authorized?` gates login/access on `teams.where(id: Shipit.github_teams.map(&:id))` [10](#0-9)  — potentially grant themselves membership in a team used for `Shipit.github_teams` authorization, escalating access to the Shipit application. This matches "escalation into `Shipit.github_teams` authorization" (High) and, given `team.organization` mutation is a data write attributable to the wrong tenant, borders on "a payload for one repository mutating another's ... team" (Critical), depending on whether the affected team is used for authorization.

### Likelihood Explanation
Requires the Shipit deployment to be multi-tenant (multiple orgs each with configured `webhook_secret`s under `Shipit.github`), and the attacker must control one such registered org and know/guess or collide a `team.id` that maps to (or can shadow) a target team used for access control. This is a non-trivial but plausible configuration for larger Shipit installs (as evidenced by the dedicated `secrets_double_github_app.yml` multi-org test fixture). The attacker cost is a single crafted HTTP POST with a correctly computed HMAC using their own legitimately-owned secret — no secret theft is required.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any other org-scoped webhook handler), assert that `params.organization.login` matches the `repository_owner`/verifying organization that `WebhooksController#verify_signature` resolved (e.g., pass the verified organization down to handlers, or re-derive and compare it inside the handler) and reject the event (422/ignore) on mismatch. Additionally, `WebhooksController#repository_owner` should not silently fall back across attacker-controlled top-level keys without validating that all organization-identifying fields in the payload agree.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb`, add a test that:
1. Configures two orgs, `org-a` and `org-b`, each with their own `Shipit.github(organization:)`/`webhook_secret` (mirroring the `secrets_double_github_app.yml` fixture).
2. Builds a membership payload: `{ action: 'added', team: { id: <id>, ... }, organization: { login: 'org-b' }, member: { login: 'mallory' }, repository: { owner: { login: 'org-a' } } }`.
3. Computes the `X-Hub-Signature` using `org-a`'s `webhook_secret` over the exact raw body.
4. POSTs to `/webhooks` with `X-Github-Event: membership`.
5. Asserts `response.status == 200` (signature accepted) — proving `Shipit.github(organization: 'org-a')` authenticated the request — **and** asserts `Team.find_by(github_id: <id>).organization == 'org-b'`, demonstrating the org that authenticated (`org-a`) differs from the org recorded on the mutated `Team` (`org-b`).

# frozen_string_literal: true

module Shipit
  class Team < Record
    REQUIRED_HOOKS = %i[membership].freeze

    has_many :memberships
    has_many :members, class_name: :User, through: :memberships, source: :user

    has_many :github_hooks,
             -> { where(event: REQUIRED_HOOKS) },
             foreign_key: :organization,
             primary_key: :organization,
             class_name: 'GithubHook::Organization',
             inverse_of: false

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
    end

    def refresh_members!
      github_api = Shipit.github(organization:).api
      github_members = Shipit::OctokitIterator.new(github_api.get(api_url).rels[:members])
      members = github_members.map { |u| User.find_or_create_from_github(u) }
      self.members = members
      save!
    end

    def github_team=(github_team)
      self.name = github_team.name
      self.slug = github_team.slug
      self.api_url = github_team.url
      self.github_id = github_team.id
    end
  end
