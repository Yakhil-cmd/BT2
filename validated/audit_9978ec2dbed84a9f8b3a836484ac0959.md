### Title
Task-trigger endpoint omits the stack-lock check enforced by deploy/rollback endpoints, allowing arbitrary task execution on a locked stack - (File: app/controllers/shipit/api/tasks_controller.rb)

### Summary
`Shipit::Api::DeploysController#create` and `Shipit::Api::RollbacksController#create` both check `stack.locked?` and reject the request unless `force` is set, but the sibling `Shipit::Api::TasksController#trigger` action never checks `stack.locked?`/`lock_reason` before calling `stack.trigger_task`, letting any user with only the `deploy` permission on the stack run arbitrary `shipit.yml` tasks while the stack is locked.

### Finding Description
Shipit's `Stack#lock_reason` mechanism is the primary "pause" control an operator uses to freeze all deployment activity on a stack (e.g. during an incident). The deploy and rollback API endpoints both honor it explicitly: [1](#0-0) [2](#0-1) [3](#0-2) 

Both explicitly call `param_error!(..., "Can't deploy/rollback a locked stack") if !params.force && stack.locked?` before invoking the underlying trigger method.

`Stack#trigger_task`, however, contains no such check anywhere in its body — it builds and enqueues the task unconditionally: [4](#0-3) 

And `Shipit::Api::TasksController#trigger` calls it directly with no lock guard, only the `deploy` permission check applied uniformly at the controller/action level: [5](#0-4) 

This breaks the equality that should hold between "stack lock a deploy-permitted user is bound by" and "stack lock a deploy-permitted user's action actually enforces": for deploys and rollbacks, `lock_reason present → action blocked (unless force)`; for tasks, `lock_reason present → action still proceeds` regardless of `force`. An operator or admin who locks a stack (e.g., because CI is red, a bad release needs investigation, or a `shipit.yml` script is known to be dangerous mid-incident) has no way to actually stop task execution — only deploys/rollbacks are paused, exactly mirroring the reported bug class where `undelegateFromPool` skipped the `undelegatePaused` check that `undelegate` enforced.

### Impact Explanation
Any caller holding `deploy` permission on the stack (the same minimum privilege required to trigger a deploy) can bypass the operator's explicit lock/pause intent and execute arbitrary custom tasks defined in `shipit.yml` against the stack's environment while it is locked. Since tasks run shell commands via `Shipit::Command` with the stack's environment, this is effectively "unauthorized execution" against a stack an operator believed was frozen — matching the "unauthorized deploy" class of impact in this engine's threat model, since `trigger_task` and `trigger_deploy`/`trigger_rollback` are functionally equivalent code-execution primitives gated by the same lock semantics.

### Likelihood Explanation
High: no special access beyond the already-granted `deploy` permission is required, and the only precondition is that the stack has an active `lock_reason` — a state operators intentionally set to prevent exactly this kind of action.

### Recommendation
Add the same `stack.locked?` guard to `Shipit::Api::TasksController#trigger` (and/or centrally in `Stack#trigger_task`) that `DeploysController#create` and `RollbacksController#create` already enforce, rejecting task triggers on locked stacks unless an explicit `force` parameter is supplied, consistent with the deploy/rollback endpoints.

### Proof of Concept
1. Operator locks the stack: `stack.lock('Investigating incident', operator)`, setting `lock_reason`.
2. Attacker (holding only `deploy` permission on the stack, no admin/operator role) calls `POST /stacks/:owner/:repo/:env/tasks/:task_name` via `Shipit::Api::TasksController#trigger`.
3. `TasksController#trigger` calls `stack.trigger_task(params[:task_name], current_user, env: params.env)` with no lock check, per [6](#0-5) .
4. `Stack#trigger_task` builds and enqueues the task unconditionally, per [4](#0-3) , in contrast to `DeploysController#create`'s explicit `param_error!` guard at [7](#0-6) .
5. The task executes despite the stack being locked, proving the pause/lock binding that holds for deploys/rollbacks does not hold for tasks.

        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

    def trigger_task(definition_id, user, env: nil, force: false)
      definition = find_task_definition(definition_id)
      env = env.to_h

      definition.variables_with_defaults.each do |variable|
        env[variable.name] ||= variable.default
      end

      commit = last_deployed_commit.presence || commits.first
      task = tasks.create(
        user_id: user.id,
        definition:,
        until_commit_id: commit.id,
        since_commit_id: commit.id,
        env: definition.filter_envs(env),
        allow_concurrency: definition.allow_concurrency? || force,
        ignored_safeties: force
      )
      task.enqueue
      task
    end
