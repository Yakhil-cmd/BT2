### Title
Independent per-recipient rounding when splitting `headers_commission` can mint or destroy bytes, causing supply inflation - (File: headers_commission.js)

### Summary
`headers_commission.js` splits a parent unit's `headers_commission` among the recipients declared in the winning child unit's `earned_headers_commission_recipients` list by rounding each recipient's share independently with `Math.round(full_amount * share / 100.0)`. Because `validateHeadersCommissionRecipients` only enforces that the declared *percentages* sum to exactly 100, and never re-checks that the resulting rounded *amounts* sum to `full_amount`, the actual byte amounts credited to `headers_commission_outputs` can end up larger or smaller than the commission that was actually destroyed by the payer unit. This is the same root cause as the referenced report: splitting a fixed total via per-part percentage rounding without reconciling the sum back to the total.

### Finding Description
Any unpriviledged unit author who has more than one author (or who simply wants to redirect commission earnings) can attach `earned_headers_commission_recipients` to a unit, as validated in: [1](#0-0) [1](#0-0) 

This validator only checks that `earned_headers_commission_share` values are positive integers and sum to exactly 100 — it never checks how the resulting `amount = round(full_amount * share / 100)` values will sum up once actually applied.

The actual split-and-credit logic is in `calcHeadersCommissions`, which for every recipient independently rounds its cut of the parent's `headers_commission`: [2](#0-1) 

and, for the SQL/MySQL path, does the same per-row rounding: [3](#0-2) 

These per-recipient rounded amounts are inserted directly into `headers_commission_contributions` and then summed into `headers_commission_outputs`, which become spendable MC (main-chain) inputs later validated only for double-spend / range checks in `validatePaymentInputsAndOutputs`: [4](#0-3) 

There is no reconciliation step (as recommended in the referenced report, e.g. summing computed amounts and forcing the total to equal `full_amount`), so the total credited to recipients of a single parent's commission can differ from `full_amount`, the actual headers_commission that was originally deducted from the payer as part of `total_input !== total_output + objUnit.headers_commission + ...` in unit validation.

### Impact Explanation
Because `Math.round` always rounds `.5` up, an attacker who controls the `earned_headers_commission_recipients` split (e.g. two recipients at 50%/50%) can deterministically cause the sum of rounded per-recipient amounts to exceed the actual `full_amount` whenever `full_amount` is odd (e.g. `full_amount=101` → `round(50.5)+round(50.5) = 51+51 = 102`), creating one extra byte that was never destroyed anywhere. With more recipients (up to 100, since each share must be a positive integer and their sum is 100) the achievable overcount per settlement grows (up to roughly half the recipient count). Since this computation is fully deterministic and performed identically by every full node, all nodes agree on the inflated payout — so it does not cause a fork/disagreement, but it does systematically mint extra bytes into `headers_commission_outputs`, which is real, spendable base-asset supply. Repeated over many self-authored units this constitutes ongoing base-asset supply inflation. The reverse case (rounding down) permanently destroys a few bytes, and doesn't need to be maliciously triggered to occur, but the "round up" side is directly attacker-steerable.

### Likelihood Explanation
Any unit author can populate `earned_headers_commission_recipients` on units they compose and repeat this cheaply and continuously — no special privilege, hub cooperation, or catchup/network condition is needed. Winning the "who gets header commission" race for a given parent unit is common for an author who is the sole/likely candidate child (e.g., regular self-chained postings), making the exploit practically repeatable across many main-chain indices.

### Recommendation
After computing each recipient's rounded share in `headers_commission.js`, reconcile the total: compute the sum of the rounded per-recipient amounts and adjust the last recipient's (or the largest share's) amount so the sum exactly equals `full_amount`, mirroring the "compute rounded parts, then correct the last part to match the total" pattern recommended in the referenced report. Apply the same fix to the MySQL `ROUND(...)`-based SQL path (e.g. by rounding all but the last recipient and setting the last recipient's amount to `full_amount - sum_of_others`).

### Proof of Concept
1. Attacker composes unit `A` with two authors/addresses `X` and `Y` and sets:
   ```
   earned_headers_commission_recipients: [
     { address: X, earned_headers_commission_share: 50 },
     { address: Y, earned_headers_commission_share: 50 }
   ]
   ```
   This passes `validateHeadersCommissionRecipients` since the shares sum to 100.
2. Attacker ensures unit `A` becomes the winning child for a parent unit `P` whose `headers_commission` is odd, e.g. `101` (headers_commission is derived from `objectLength.getHeadersSize`, and attacker controls unit content/size to hit an odd byte count).
3. When `calcHeadersCommissions` runs, for each recipient:
   `amount = Math.round(101 * 50 / 100) = Math.round(50.5) = 51`
   Both `X` and `Y` are each credited `51`, totalling `102`, one byte more than the `101` bytes actually paid by `P`.
4. This extra byte is inserted into `headers_commission_outputs` and becomes spendable, i.e., minted from nothing. Repeating this pattern across many self-authored units accumulates net positive supply inflation over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
