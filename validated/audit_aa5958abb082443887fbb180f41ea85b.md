### Title
Unbounded scan over all currently-unstable units in `dataFeedExists`/`readDataFeedValue` allows unprivileged unit posting to degrade AA data-feed lookups - (File: `data_feeds.js`)

### Summary
`dataFeedExists` and `readDataFeedValue` in `data_feeds.js` iterate over the entire in-memory `storage.assocUnstableMessages` collection — i.e. every currently-unstable unit in the whole DAG — whenever an AA formula performs an `in data feed` check or reads an unstable data-feed value. This scan is not scoped to the queried oracle address(es); it inspects every unstable unit's messages before filtering by author address. [1](#0-0) [2](#0-1) 

### Finding Description
Both functions loop `for (var unit in storage.assocUnstableMessages)`, and for every unstable unit check `objUnit.author_addresses` against the target oracle list and then iterate `storage.assocUnstableMessages[unit].forEach(...)` over its messages, before any filtering by the requested `feed_name` narrows the cost: [3](#0-2) 

`storage.assocUnstableMessages` holds messages for all units that have not yet stabilized, network-wide — this set is populated by any unprivileged unit posted to the DAG (any user can author units that remain unstable while the main chain does not advance past them). Because there is no cap on the number of unstable units that can accumulate before stabilization, and no restriction requiring the caller's oracle addresses to actually be represented, the cost of this loop scales with total network unstable-unit count, not with anything the AA author or trigger sender controls.

This code path is reachable by any AA trigger sender: an AA definition using the `in data feed` op in an address/asset definition [4](#0-3)  or the `data_feed[...]`/`in data feed` formula construct calls into `dataFeeds.dataFeedExists` / `readDataFeedValue` during AA response computation via `formula/evaluation.js`. Anyone can define such an AA and anyone can trigger it; every trigger causes the full unstable-unit set to be scanned.

### Impact Explanation
As with the reported analog (unbounded loop over a grow-able list causing an owner-facing operation to become gas/DoS-prohibitive), here an unprivileged actor can inflate the cost of every AA trigger evaluation that uses data-feed conditions by increasing the number of concurrently unstable units in the DAG (e.g., by posting many units quickly, or during periods of network congestion when main-chain stabilization lags). Because the scan happens synchronously during unit/AA validation on every full node, this can slow down or stall processing of AA triggers relying on data feeds, potentially causing nodes to diverge in how long validation takes or causing AA execution to time out/fail inconsistently, which risks fund-lock/bounce behavior for AAs that depend on `in data feed`/data-feed reads for critical decisions (e.g., oracle-price-gated payments).

### Likelihood Explanation
The precondition (a large number of concurrently unstable units) requires either organic network congestion or deliberate unit-flooding by an attacker; the attacker does not need any privileged role — any address can post ordinary units to inflate `storage.assocUnstableMessages` while any user can craft or trigger AAs that use `in data feed`. This makes the growth of the iterated set fully attacker-influenceable via unprivileged unit-posting, satisfying the "unbounded loop growth via unprivileged data" root cause identified in the analog report.

### Recommendation
Scope the in-memory unstable scan by indexing `storage.assocUnstableMessages` (or a derived structure) by author address and `app === 'data_feed'` so that lookups are O(matching units) rather than O(all unstable units). Alternatively, maintain a secondary index keyed by oracle address of unstable data-feed messages, updated incrementally as units are added/stabilized, so `dataFeedExists`/`readDataFeedValue` never need to walk the full unstable set.

### Proof of Concept
1. An attacker (or organic network conditions) causes a large number of units to remain unstable simultaneously (post many units faster than the main chain advances/stabilizes them).
2. Any user defines (or reuses an existing) AA whose logic uses `in data feed` (as in `definition.js` lines 933-940) or reads an unstable data-feed value via the formula `data_feed[...]` construct.
3. Any user sends a trigger to that AA.
4. During AA response computation, `dataFeeds.dataFeedExists`/`readDataFeedValue` iterates `for (var unit in storage.assocUnstableMessages)` over the entire inflated unstable-unit set [1](#0-0) , causing processing time to scale with the number of unstable units network-wide rather than with data specific to the queried oracle, degrading AA trigger processing for all nodes.
