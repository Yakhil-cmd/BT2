### Title
`ReopenedHandler#unarchive?` inherits the broken operator precedence from `provision?`, allowing re-provisioning on `review_stacks_enabled: false` repositories - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses the same flawed boolean expression as `OpenedHandler#provision?`: `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...) || (...)`. Because `&&` binds tighter than `||` in Ruby, `review_stacks_enabled` only gates the `allow_all?` branch, not the `allow_with_label?`/`prevent_with_label?` branches, so an attacker's own PR can be repeatedly closed/reopened to trigger `Shipit::ReviewStackProvisioningQueue.add(stack)` even when the repository has review stacks disabled.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` before any provisioning-related action occurs. The actual code in `unarchive?` [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby's operator precedence (`&&` binds tighter than `||`), this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. If `review_stacks_enabled == false` and `provisioning_behavior == prevent_with_label`, the third disjunct is independent of `review_stacks_enabled` and evaluates to `true` whenever the PR lacks the configured provisioning label — the default state for a freshly created PR the attacker controls.

`respond_to_pull_request_reopened?` gates on `params.action == "reopened" && unarchive?` [2](#0-1) , and when true, `process` calls `stack.unarchive!` [3](#0-2) , which is `ReviewStackAdapter#unarchive!`. If no stack exists it calls `create!` (which calls `Shipit::ReviewStackProvisioningQueue.add(stack)` unconditionally) [4](#0-3) ; if an archived stack exists, `unarchive!` also calls `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.unarchive!` [5](#0-4) . `ClosedHandler#respond_to_pull_request_closed?` has no `review_stacks_enabled` check at all and archives unconditionally [6](#0-5) , so an attacker can alternate close/reopen to repeatedly re-enqueue provisioning.

This mirrors the identical defect already present in `OpenedHandler#provision?` [7](#0-6) , confirming a copy-pasted bug rather than an isolated typo. By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` against the whole `(archive? || unarchive?)` expression [8](#0-7) , showing the correct pattern that `ReopenedHandler`/`OpenedHandler` fail to follow.

Nothing else in the request path (`ExplicitParameters` schema, webhook signature verification, `Repository.from_github_repo_name`) validates or blocks this — the payload only needs a valid `repository.full_name`, `pull_request`, and `sender.login`, all attacker-controlled fields in their own repo's webhook payload.

### Impact Explanation
Once enqueued via `Shipit::ReviewStackProvisioningQueue.add(stack)`, the periodic `ReviewStackProvisioningQueue.work` (invoked from `lib/tasks/cron.rake`) will call `stack.provision` on the queued stack, which (per the base finding this question references) leads to execution of the current `shipit.yml` for that stack/branch — i.e., attacker-controlled repeated triggering of the provisioning/build pipeline that would otherwise require `review_stacks_enabled: true`. This is scoped to the attacker's own repository (misconfigured with `review_stacks_enabled: false` + `prevent_with_label`), matching the Critical impact category of an unauthorized deploy/provisioning trigger via command execution driven by repo-controlled configuration (`shipit.yml`).

### Likelihood Explanation
Requires the specific misconfiguration `review_stacks_enabled: false` with `provisioning_behavior: prevent_with_label` (as stated in preconditions) — a real, documented, and plausible configuration for repository owners who intend to disable review stacks by default but still specify a `provisioning_behavior`. Given that precondition, the attack costs nothing: the attacker only needs to open a PR without the provisioning label, then close/reopen it via the GitHub UI or API — actions available to any PR author on their own PR, fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression, matching the pattern used in `LabeledHandler`:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `OpenedHandler#provision?`, and add a `repository.review_stacks_enabled` guard to `ClosedHandler#respond_to_pull_request_closed?` for defense-in-depth/consistency.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` add:
```ruby
test "does NOT unarchive/re-provision stacks when review_stacks_enabled is false, even under prevent_with_label with no label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  assert_no_enqueued_jobs # or stub Shipit::ReviewStackProvisioningQueue.expects(:add).never

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived when review_stacks_enabled is false"
end
```
Assert both sides of the binding: before the call, `repository.review_stacks_enabled` is `false`; after `process`, the stack must remain archived and `Shipit::ReviewStackProvisioningQueue.add` must not have been invoked. With the current code, this assertion fails because `unarchive?` returns `true` and the stack is unarchived/re-queued despite `review_stacks_enabled == false`.
