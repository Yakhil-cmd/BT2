### Title
Webhook signing organization is not bound to the repository the payload writes to, allowing cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, which is read from the unauthenticated JSON body (`repository.owner.login` or `organization.login`). The event handlers, however, resolve which `Repository`/`Stack` to mutate using a *different* field from the same body: `repository.full_name` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together, so in a multi-organization Shipit deployment (`Shipit.github(organization:)` / `Shipit.github_app_config`, which supports one distinct `webhook_secret` per configured GitHub organization) an attacker who controls (or is a member of) one onboarded organization can sign a payload with *their own org's* secret while setting `repository.full_name` to point at a *victim* organization's repository/stack.

### Finding Description
`verify_signature` picks the verifying identity from attacker-controlled JSON, not from any GitHub-provided/authenticated channel: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` supports a per-organization configuration (including a distinct `webhook_secret`) when multiple GitHub organizations are configured under `secrets.github`: [3](#0-2) 

The actual event handler resolves the acted-upon repository from a *different* field of the same unauthenticated JSON body: [4](#0-3) 

Because `verify_webhook_signature` only proves that *some* raw body was HMAC-signed with the secret belonging to whatever organization `repository_owner` names, and never checks that this organization actually owns the repository named in `repository.full_name`, the equality the system implicitly assumes — `organization that authenticated == repository that is written` — does not hold. Any attacker who is a legitimate member/admin of an org registered in Shipit's multi-org config (and can thus configure that org's real webhook secret against their own GitHub org, which is normal self-service GitHub App/webhook setup) can forge a `full_name` for a completely unrelated tracked repository/stack and have it processed as an authentic event.

### Impact Explanation
Handlers keyed on `repository_name` include, among others, the push handler (enqueues `GithubSyncJob` to sync commits for the target stack), the status handler (creates a `Status` record for a specific commit — which feeds into CI gating for deploy eligibility), and the pull-request closed/reopened handlers (archive/unarchive review stacks). By forging `repository.full_name` for a victim stack while signing with a different, attacker-controlled organization's secret, an attacker can inject falsified GitHub state (e.g., a fabricated successful CI status) into a Shipit-tracked stack they do not otherwise have write access to, influencing deploy-gating decisions and stack lifecycle (archive/unarchive) without any Shipit credentials — an unauthorized-deploy-adjacent authorization bypass across repository boundaries.

### Likelihood Explanation
This requires: (1) Shipit configured for multiple GitHub organizations (a documented, supported configuration via `Shipit.github_app_config`), and (2) the attacker controlling at least one such organization's webhook delivery (e.g., being an org owner able to configure a webhook to Shipit, which is a normal, low-privilege GitHub-side action, not a Shipit credential). Given that, forging the JSON body is trivial. Likelihood is moderate — it depends on the multi-org feature being used and on the attacker having admin rights to at least one org Shipit trusts, but no Shipit session, API token, or app private key is needed.

### Recommendation
After signature verification succeeds, verify that the organization used to select the webhook secret (`repository_owner`) matches the owner segment of `repository.full_name` (and of `organization.login` when present) before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two GitHub organizations in `secrets.github`, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `Shipit.github_app_config`).
2. As an administrator of `attacker-org` (no Shipit access needed), create/receive a webhook payload where the JSON body is:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  ...
}
```
3. Sign the raw body with `attacker-org`'s known `webhook_secret` and send it to Shipit's `/github/webhooks` endpoint with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully against the attacker's own secret.
5. `Shipit::Webhooks::Handlers::Handler#repository_name` resolves `"victim-org/victim-repo"` from `repository.full_name`, and the status handler creates a `Status` on the victim's commit — with no verification tying `attacker-org` to `victim-org`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
