### Title
Webhook `status` events are applied by commit SHA with no repository/organization binding, allowing cross-stack CI status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the payload, via `repository_owner`. [1](#0-0) [2](#0-1)  Shipit explicitly supports configuring multiple independent GitHub Apps/organizations, each with its own `webhook_secret`. [3](#0-2) [4](#0-3)  Once the signature is verified against the org named in the payload, the `status` event is processed by `Shipit::Webhooks::Handlers::StatusHandler#process`, which looks up commits **globally by SHA only** (`Commit.where(sha: params.sha)`), with no filtering by `repository.full_name`/organization at all, unlike the base `Handler` class's `stacks`/`repository_name` scoping used by other handlers (e.g. `PushHandler`). [5](#0-4) [6](#0-5) [7](#0-6) 

### Finding Description
The binding that should hold is: *the organization whose secret signed the webhook == the organization whose data is written by the webhook*. This binding is broken by `StatusHandler`.

- `verify_signature` picks the `GitHubApp` (and therefore the secret used for HMAC verification) via `repository_owner`, which is read straight from the JSON payload the sender controls: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) 
- `Commit`/`Status` writes triggered by the `status` event are **not** scoped to that same organization/repository. `StatusHandler#process` fetches `Commit.where(sha: params.sha)` across the entire Shipit installation and calls `commit.create_status_from_github!(params)` on every match. [8](#0-7) 
- Compare this to `PushHandler`, which correctly derives the affected stacks through `Handler#stacks`, which filters by `Repository.from_github_repo_name(repository_name)` (i.e. `repository.full_name`), keeping the org used for verification and the org whose data changes bound together. [6](#0-5) [9](#0-8) 
- `create_status_from_github!` creates a `Status` record directly from attacker-controlled `state`/`description`/`context`, which then recomputes the commit's overall CI status and, on success/pending transitions, invokes `stack.schedule_merges` (merge-queue processing) and fires deployable-status webhooks. [10](#0-9) [11](#0-10) 

Because HMAC verification only proves the sender knows *some* configured org's `webhook_secret`, and the payload's `repository`/`organization` fields used to pick that secret are independent of anything used to scope the actual database mutation in `StatusHandler`, an attacker who legitimately controls one Shipit-configured GitHub organization (org A, with a valid `webhook_secret`) can forge a `status` webhook: sign it so `repository_owner` == "OrgA" (satisfying `verify_signature`), while setting `sha` to a commit SHA that exists in a stack belonging to a completely different tracked organization/repository (org B). `StatusHandler` will happily create a `success` (or any) `Status` for that commit, since it never checks which organization or repository the SHA belongs to.

### Impact Explanation
This breaks the "an organization that authenticated versus the repository whose data is written" trust boundary described in scope. An attacker who is a legitimate admin/webhook holder for one org configured in a multi-org Shipit deployment can:
- Forge CI status ("success") for arbitrary commits belonging to a different org/repo's stack, satisfying `ci.require` gating and `deployable?` checks that other parts of the codebase (deploy triggers, merge queue via `schedule_merges`) rely on. [12](#0-11) 
- Indirectly enable an unauthorized deploy or automated merge of a commit that never actually passed CI on GitHub, for a repository the attacker does not control, by exploiting cross-organization state.

This matches the impact tier "an unauthorized deploy, rollback or merge" via escalation across a trust boundary that should be scoped per-repository/organization.

### Likelihood Explanation
Exploitation requires the attacker to possess a valid `webhook_secret` for at least one organization configured in the Shipit instance (i.e., be a legitimate installer/admin of a GitHub App pointed at this Shipit deployment for org A) — this is a normal, low-privilege position for someone running their own org's CI/CD via a shared Shipit instance, not a Shipit application-level credential. They additionally need to guess or observe a target commit SHA in another tracked repository (SHAs are not secret; they're visible via GitHub history, PRs, or the Shipit UI itself). No `ApiClient` token, GitHub App private key, or Shipit session is required — only knowledge of one org's `webhook_secret`, which is explicitly a documented, distinct-per-organization credential in multi-org setups. [4](#0-3) 

### Recommendation
Scope `StatusHandler#process` (and ideally the generic `Handler` webhook dispatch) so that commit lookups/writes are restricted to the stacks/repositories belonging to the same repository/organization that the webhook signature was verified against — i.e., use `stacks`/`repository_name` (as `PushHandler` does) to filter `Commit` records instead of a bare global `Commit.where(sha: params.sha)`. Additionally, consider binding the verified webhook organization identity into the handler pipeline explicitly (e.g., pass the verified organization to `Webhooks.for_event(event).each { |handler| handler.call(params, organization: verified_organization) }`) so handlers cannot process data for organizations other than the one whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section). Shipit tracks a stack for `OrgB/target-repo`, with a known commit SHA `abcdef123456` that is currently CI-pending/failing.
2. As the legitimate holder of `OrgA`'s `webhook_secret` (e.g., an admin of `OrgA`'s GitHub App installation), craft a `status` event JSON body:
   ```json
   {
     "sha": "abcdef123456",
     "state": "success",
     "context": "ci/forced",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature verifies successfully. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "abcdef123456")`, finds the commit belonging to `OrgB/target-repo`'s stack (unrelated to `OrgA`), and calls `create_status_from_github!`, marking it `success` regardless of actual GitHub CI state. [5](#0-4) 
6. The commit's status flips, `schedule_merges`/deployable-status hooks fire for `OrgB`'s stack. [12](#0-11) 

Note: I was unable to fully trace every downstream consumer of `Commit#deployable?`/`ci.require` gating in this pass (e.g. exact deploy-trigger code paths) to confirm an end-to-end automatic deploy without further review of `app/models/shipit/stack.rb`'s merge/deploy trigger logic; the PoC above is verified through `StatusHandler` and `Commit#create_status_from_github!`/`add_status`, which is sufficient to demonstrate the cross-organization binding break itself.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
