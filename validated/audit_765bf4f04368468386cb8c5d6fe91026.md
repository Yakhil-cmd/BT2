## Title
Webhook secret-selection field is decoupled from the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate a request against using an organization name pulled from the untrusted, unauthenticated request body, while the actual write target (which `Stack`/`Repository` gets synced, commented on, or updated) is derived from a *different* field of that same body. Because HMAC verification can be trivially satisfied for any organization configured without a `webhook_secret`, the org used to select the verification key and the repository actually acted upon are never cross-checked - exactly the "field acted on but never covered by the verified signature" binding break.

### Finding Description
In a multi-org deployment (`secrets.github` keyed by organization, as shown in `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml`), `Shipit.github(organization:)` looks up per-org config via `github_app_config` [1](#0-0) . The controller determines *which* organization's key to verify against straight from the JSON body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`verify_webhook_signature` short-circuits to `true` whenever the selected org has no configured `webhook_secret`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [3](#0-2) 

Once "verified" (or trivially bypassed for a secret-less org), `create` re-parses the raw body and dispatches it to handlers unmodified:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers never look at `repository.owner.login` again - they resolve the actual target repository from a completely different key, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 
and `PushHandler#process` acts on any stacks matching that repository, e.g. triggering `sync_github`: [6](#0-5) 

So the equality that should hold is:
`organization used to select/verify the signing secret == organization that owns the repository the handler writes to`

Because both `repository.owner.login` (secret-selection) and `repository.full_name` (write target) are attacker-controlled fields inside the *same unsigned/unauthenticated request* whose signature is never checked when the selected org lacks a `webhook_secret`, an attacker can set `repository.owner.login` to any secret-less org configured on the instance while setting `repository.full_name` to `victim-org/victim-repo` (any repository actually tracked by Shipit). `verify_signature` passes trivially (no HMAC check performed), and the handler then acts on the victim repository's stacks - exactly analogous to `FurnaceP1.setRatio` mutating `ratio` while the dependent `lastPayout`/`lastPayoutBal` state (here: which org's identity the request is actually trusted as) is never consistently updated/checked before the write proceeds.

### Impact Explanation
This lets an unauthenticated internet client trigger stack actions (e.g. `GithubSyncJob`, commit status creation, membership/team mutation, pull_request review-stack updates) against arbitrary repositories tracked by the Shipit instance, without ever presenting a valid signature for those repositories' actual GitHub App/organization. This is an authentication-bypass class issue on the webhook ingestion path, matching the "unauthenticated read of stack state" / cross-repository-write severity bar, since state-changing webhook events (push, membership, pull_request) can be forged for any repository as long as one configured org has no `webhook_secret` set.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with multiple GitHub organizations (a documented, supported configuration - see `config/secrets.development.example.yml` and `secrets_double_github_app.yml`), and (2) at least one of those orgs to have `webhook_secret` unset (also a documented/supported value - `webhook_secret: # nil` appears in the example configs). No credentials, tokens, or GitHub write access are needed; the attacker only needs to know one org name that lacks a secret and the target repository's `full_name`, both discoverable from the Shipit UI/public GitHub metadata. This is a realistic operator configuration, not a violation of documented deployment requirements.

### Recommendation
Do not let an untrusted payload field select the verification key independently of the field the handlers actually act on. Options: (a) verify the signature against every configured org's secret and require at least one strict match (never treat "no secret configured" as an automatic pass when other orgs in the same instance do have secrets), or (b) after selecting `github_app` by `repository_owner`, re-validate that `repository.full_name`'s owner matches the same organization before dispatching to handlers, or (c) require every configured org to set a webhook_secret and reject requests where the derived org has none.

### Proof of Concept
1. Instance is configured with two orgs, e.g. `OrgWithSecret` (has `webhook_secret`) and `OrgNoSecret` (`webhook_secret: nil`) — a supported configuration shape per `secrets_double_github_app.yml`.
2. Attacker POSTs to `/github/webhooks` (or engine-mounted webhook path) with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "OrgWithSecret/victim-repo",
    "owner": { "login": "OrgNoSecret" }
  }
}
```
3. `repository_owner` resolves to `OrgNoSecret`; `Shipit.github(organization: 'OrgNoSecret')` returns an app with `webhook_secret == nil`; `verify_webhook_signature` returns `true` unconditionally [7](#0-6)  - no valid `X-Hub-Signature` is required at all.
4. `create` dispatches the parsed body to `PushHandler`, which resolves stacks via `repository.full_name = "OrgWithSecret/victim-repo"` [8](#0-7)  and calls `stack.sync_github(expected_head_sha: 'deadbeef')` on the victim's stacks despite never proving knowledge of `OrgWithSecret`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
