### Title
Bridge Operator Can Arbitrarily Set Uncapped KAIA/ERC20 Transfer Fees to Steal User Fee Budgets — (`contracts/service_chain/bridge/BridgeFee.sol`, `BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge stores transfer fees (`feeOfKLAY`, `feeOfERC20`) with no upper-bound cap and no timelock. The bridge deployer is simultaneously the `owner` and the sole initial operator (threshold = 1). A malicious bridge operator can frontrun a user's `requestKLAYTransfer` or `requestERC20Transfer` call by atomically raising the fee to the user's entire `feeLimit`, redirecting it to a fee receiver they control, then lowering the fee back — an exact structural analog to the FERC1155 royalty-manipulation attack.

---

### Finding Description

**Role duality at deployment.** `BridgeOperator` registers `msg.sender` as both `owner` and the first operator, with both `operatorThresholds` initialised to `1`. [1](#0-0) 

This means the deployer can unilaterally execute every privileged action without any co-signer.

**Uncapped fee storage.** `_setKLAYFee` and `_setERC20Fee` write the caller-supplied value directly with no maximum check. [2](#0-1) 

**Fee-change functions are `onlyOperators`, not `onlyOwner`.** Any registered operator (including the deployer who never deregistered themselves) can call `setKLAYFee` / `setERC20Fee` in a single transaction. [3](#0-2) [4](#0-3) 

**Fee receiver is `onlyOwner` with no restriction.** The deployer (who is also the operator) can point `feeReceiver` at any address, including their own. [5](#0-4) 

**Fee is consumed at the moment of the request, using the current on-chain value.** The fee read inside `_payKLAYFeeAndRefundChange` is the live storage value, not the value the user observed when they signed the transaction. [6](#0-5) 

**Fallback path amplifies the impact.** When a user calls the fallback, `_feeLimit` is set to the current `feeOfKLAY`. If the operator raises `feeOfKLAY` to `msg.value - 1 wei`, the user loses almost their entire KAIA amount to fees while only 1 wei is bridged. [7](#0-6) 

---

### Impact Explanation

A malicious bridge operator can steal the entire `feeLimit` portion of every KAIA transfer and the entire `_feeLimit` portion of every ERC20 transfer. Via the fallback path, the loss approaches `msg.value`. The stolen KAIA/ERC20 is transferred to the operator-controlled `feeReceiver` address. This is an unauthorized fee charge affecting KAIA and bridged assets.

---

### Likelihood Explanation

The default deployment configuration (threshold = 1, deployer is sole operator and owner) requires no additional setup for the attack. Any service-chain bridge operator who has not explicitly deregistered themselves and raised the threshold can execute this attack. The attack is invisible to users until the fee-change transaction is mined.

---

### Recommendation

1. **Cap the fee.** Add a `MAX_FEE` constant (e.g., a percentage of a reasonable transfer amount) and enforce it in `_setKLAYFee` / `_setERC20Fee`.
2. **Separate owner and operator roles.** Require the deployer to explicitly register operators and deregister themselves, or enforce that `setFeeReceiver` cannot point to an address that is also an operator.
3. **Add a timelock or minimum notice period** before a fee change takes effect, so users can observe the pending change and withdraw.
4. **Require threshold > 1 for configuration votes** in production deployments, preventing a single operator from unilaterally changing fees.

---

### Proof of Concept

```
// Attacker is bridge deployer: both owner and sole operator (threshold=1)

// Step 1 – set fee receiver to attacker's address (onlyOwner, no restriction)
bridge.setFeeReceiver(attacker);

// Step 2 – advertise a low fee to attract users
bridge.setKLAYFee(0.01 ether, configNonce++);   // threshold=1, executes immediately

// Step 3 – user submits requestKLAYTransfer with msg.value=1.5 KAIA, _value=1.0 KAIA
//           feeLimit = 0.5 KAIA (user's entire fee budget)

// Step 4 – attacker frontruns: raise fee to exactly feeLimit
bridge.setKLAYFee(0.5 ether, configNonce++);    // single-operator, instant

// Step 5 – user's tx mines:
//   _payKLAYFeeAndRefundChange(0.5 ether):
//     fee = feeOfKLAY = 0.5 ether
//     require(0.5 ether >= 0.5 ether) ✓
//     feeReceiver.call{value: 0.5 ether}("") → attacker receives 0.5 KAIA
//     feeRefund = 0 → no refund to user
//   RequestValueTransfer emitted with valueOrTokenId = 1.0 KAIA

// Step 6 – attacker backruns: restore low fee
bridge.setKLAYFee(0.01 ether, configNonce++);

// Result: attacker stole 0.5 KAIA (user's entire feeLimit).
// Via fallback, attacker can steal msg.value - 1 wei.

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
```
