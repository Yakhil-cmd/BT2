### Title
`Shipit::Team#add_member` grants cross-organization team membership because team lookup keys only on `github_id`, ignoring the webhook's authenticated organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely via `Team.find_or_create_by!(github_id: params.team.id)`, never comparing `params.organization.login` against the team's already-persisted `organization`. In a multi-tenant Shipit deployment (`Shipit.github` supports per-organization `webhook_secret` configs, see `lib/shipit.rb#github_app_config`), any tenant org whose own webhook is correctly HMAC-verified with **its own** `webhook_secret` can submit a `membership`/`added` event carrying a `team.id` belonging to a *different* tenant's team, causing `Team#add_member` (`app/models/shipit/team.rb:41`) to insert an attacker-chosen member into that foreign team.

### Finding Description
The binding that should hold is:
`Team.find_by(github_id: X).organization == params['organization']['login']` for every webhook accepted by `verify_signature`.

Trace:
- `WebhooksController#verify_signature` selects the HMAC secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization','login')` for membership events. [1](#0-0) [2](#0-1) 
- `Shipit.github` picks a per-organization config/secret from `secrets.github`, confirming this engine supports multiple independently-configured GitHub org tenants sharing one Shipit instance. [3](#0-2) 
- Once the signature is verified against *that org's own secret*, `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... team.organization = params.organization.login }` — the `organization` assignment only runs in the creation block, i.e., only the first time that `github_id` is seen. [4](#0-3) 
- `Team#add_member` performs no organization check at all before appending the member. [5](#0-4) 

Exploit flow: a legitimate team `Team A` (`organization: 'org-a'`, `github_id: 100`) already exists (created from a real `org-a` membership event). A second tenant, `org-b`, onboarded to the same Shipit instance with its own `webhook_secret`, is controlled by the attacker. The attacker POSTs `/webhooks` with header `X-Github-Event: membership`, a body `{"action":"added","team":{"id":100,...},"organization":{"login":"org-b"},"member":{"login":"attacker"}}`, signed with `org-b`'s real, attacker-known `webhook_secret`. `verify_signature` picks `org-b`'s config (because `repository_owner` resolves to `org-b`) and the signature checks out — it is a genuinely valid signature for `org-b`. `find_or_create_team!` then does `Team.find_or_create_by!(github_id: 100)`, finds the **existing** `Team A` row (owned by `org-a`), and the creation block (which would have set `organization`) never runs. `team.add_member(attacker_user)` appends the attacker to `Team A`'s memberships despite the request never being authenticated by `org-a`.

None of the existing guards catch this: `verify_signature` only proves the request came from *some* configured org, not that it matches the team's owning org; `ExplicitParameters` schema in `MembershipHandler` only requires the presence/types of `team.id`, `organization.login`, `member.login`, not their consistency with stored records; there is no `Team` validation tying `github_id` to a fixed `organization`, and no uniqueness constraint spans both columns together for this purpose (the schema only has a unique index on `[organization, slug]`, not on `github_id`, and `github_id` uniqueness across tenants is never enforced or checked). [6](#0-5) [7](#0-6) 

### Impact Explanation
`Shipit::User#authorized?` gates access on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` — i.e., authorization is directly derived from `Membership` rows. [8](#0-7)  An attacker-controlled tenant org can therefore inject arbitrary GitHub logins into another tenant's authorization-relevant team without that tenant's org ever authenticating the request, escalating into `Shipit.github_teams` authorization across tenants (matches the High-severity category in scope: "escalation into `Shipit.github_teams` authorization"). This is repeatable for any `github_id` the attacker can guess or observe (team IDs are small sequential integers) and works for as many memberships/removals as desired (the same asymmetry allows unauthorized removal of a foreign org's real members too, since `'removed'` also has no org check).

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (`secrets.github` keyed by org, each with its own `webhook_secret` — a supported, documented configuration path in this engine, not a hypothetical), (2) the attacker controls one of those tenant orgs (its own webhook secret is legitimately theirs), and (3) knowledge or a good guess of a target team's numeric `github_id` (small integers, often enumerable/observable). Given those preconditions — which are realistic for any shared/multi-tenant Shipit install — the attack costs only two HTTP POSTs with a body the attacker fully controls and a signature they can legitimately compute.

### Recommendation
In `MembershipHandler#find_or_create_team!`, look up the team by `[github_id, organization]` (or verify `existing_team.organization == params.organization.login` and reject/raise otherwise) instead of `github_id` alone. Additionally, add a uniqueness validation/index ensuring a `github_id` cannot be silently reused across two different `organization` values, and reject membership webhooks whose `organization.login` doesn't match the previously recorded organization for that `github_id`.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` style, no live GitHub — signature verification stubbed like the existing `"verifies webhook signature"` test):

```ruby
test "membership webhook from a different verified org cannot add members to a foreign team" do
  team_a = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X

  # Attacker's own tenant org, independently verified with its own webhook_secret
  Shipit.github(organization: 'attacker-org').expects(:verify_webhook_signature).returns(true)

  @request.headers['X-Github-Event'] = 'membership'
  post :create, body: {
    action: 'added',
    team: { id: team_a.github_id, name: team_a.name, slug: team_a.slug, url: team_a.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-controlled-login' }
  }.to_json, as: :json

  assert_response :ok

  team_a.reload
  # Binding under test: only shopify's real webhook may add members to team_a
  assert_not_includes team_a.members.map(&:login), 'attacker-controlled-login',
    "team belonging to organization=#{team_a.organization} was mutated by a webhook verified under a different organization's secret"
end
```

Both sides of the equality to assert: `team_a.organization` (== `'shopify'`) vs. the `organization.login` that successfully authenticated the request (`'attacker-org'`). Currently they diverge and the membership is still written; after the fix, the handler must refuse to apply `add_member` when they diverge.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
