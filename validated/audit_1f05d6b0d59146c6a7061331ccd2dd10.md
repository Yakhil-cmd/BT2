This confirms the mechanism: `composeDivisibleAssetPaymentJoint` builds `arrAssetPayments` from `params.outputs_by_asset` for every asset key present (`divisible_asset.js:217-220`), and each asset gets individually funded/spent from the textcoin address's unspent outputs regardless of what asset it is, as long as the ephemeral textcoin address holds it.

### Title
Textcoin claim sweeps attacker-planted assets sent to the public ephemeral address into the claimer's transaction - (File: wallet.js)

### Summary
`receiveTextCoin`'s `checkStability()` builds `opts.outputs_by_asset` from **every** asset found in unspent outputs at the textcoin's ephemeral address, using only the first alphabetically-ordered asset's properties (`is_private`/`fixed_denominations`) to decide the claim path, then sweeps all of them to the recipient in one payment.

### Finding Description
When a textcoin is created, a payment is broadcast on the DAG to a freshly-derived, one-time address (`addrInfo.address`, derived from the mnemonic). This address, and the fact that funds are sitting there, becomes publicly visible on the DAG as soon as the sending unit is broadcast — well before the recipient actually redeems the mnemonic. Because the DAG allows any unprivileged unit poster to send a payment message with an arbitrary `asset` to any address, an attacker can post a unit sending a junk/malicious asset to that same textcoin address before the legitimate recipient claims it.

When the recipient calls `receiveTextCoin`, `checkStability()` queries **all** unspent outputs at the address grouped by asset [1](#0-0) , then builds the outbound payment by iterating over every distinct asset found there:
```
let outputs_by_asset = { };
for (let { asset, amount } of rows)
    if (asset)
        outputs_by_asset[asset] = [{ amount, address: addressTo }];
outputs_by_asset.base = [{ amount: 0, address: addressTo }];
opts.outputs_by_asset = outputs_by_asset;
``` [2](#0-1) 

The decision of whether this branch is even entered (vs. the private-asset-only branch) is based solely on `asset_infos[0]`, i.e., the properties of whichever asset happens to sort first — not the asset the sender actually intended to send [3](#0-2) . `opts.outputs_by_asset` is then handed to `divisibleAsset.composeAndSaveDivisibleAssetPaymentJoint(opts)` [4](#0-3) , whose `composeDivisibleAssetPaymentJoint` unconditionally creates a payment message for every key in `outputs_by_asset` [5](#0-4) . There is no whitelist or origin check tying the swept assets to the original textcoin sender.

This is directly analogous to the reported `BountyCore.sol` issue: an unprivileged third party plants a token/asset at a location the victim is expected to trust and claim from, the victim's claim transaction indiscriminately iterates over and includes that attacker-supplied asset alongside the legitimate one, and the recipient ends up holding/interacting with tokens they never intended to receive, potentially believing they came from the trusted sender.

### Impact Explanation
A claimer's wallet automatically composes and broadcasts a transaction receiving arbitrary attacker-chosen assets bundled with their legitimate textcoin claim. This can be used to plant malicious/spam or deceptive assets into a victim's wallet without consent, and — since the multi-asset payment is validated per-asset by `storage.loadAssetWithListOfAttestedAuthors` inside `retrieveMessages` — a mismatch between the "representative" asset used to pick the code path (`asset_infos[0]`) and the actual mixed set of assets present can also cause the private/non-private branch decision to be wrong for one of the assets actually being swept, undermining the privacy or fixed-denomination handling expectations for that asset type.

### Likelihood Explanation
Likelihood is high: sending a payment with an arbitrary asset to any known address requires no special privilege, and the textcoin's destination address becomes publicly known the moment the original sending unit is broadcast on the DAG (it's a full 32-byte address embedded in a public payment output before the recipient claims). Any network participant monitoring the DAG for textcoin outputs can front-run the redemption with a junk-asset payment.

### Recommendation
When claiming a textcoin, `checkStability()` should only build `outputs_by_asset`/claim payments for the asset(s) that legitimately correspond to the textcoin as originally sent (e.g., recorded/expected asset from `sent_mnemonics`, or restricting to a single asset chosen deterministically at send time), rather than sweeping every asset currently sitting at the address. At minimum, do not derive `is_private`/`fixed_denominations` handling from an arbitrary `asset_infos[0]`; validate each discovered asset independently and reject/skip unexpected assets that weren't part of the original textcoin payment instead of silently including them in the swept claim.

### Proof of Concept
1. Wallet A creates a textcoin: composes a unit sending `amount` of `bytes` (or of `assetX`) to the derived one-time address `T` and shares the mnemonic with recipient B out-of-band. This unit is broadcast publicly, so `T` is now visible on the DAG as an output address.
2. Attacker C, watching the DAG for outputs credited to freshly appearing addresses that match the textcoin output pattern (single unspent output, freshly created address with no unit_authors), posts a new unit sending some amount of an attacker-issued asset `assetY` to `T`.
3. Recipient B redeems the mnemonic via `receiveTextCoin`. `checkStability()` finds two assets at `T` — the legitimate `assetX` (or `base`) and attacker's `assetY` — and builds `outputs_by_asset` containing both [2](#0-1) .
4. `divisibleAsset.composeAndSaveDivisibleAssetPaymentJoint` composes and saves/broadcasts a single joint moving both `assetX` and `assetY` to B's `addressTo` [5](#0-4) , so B's wallet now holds `assetY`, an asset B never requested and has no relationship to the original sender.
