### Title
Cross-organization webhook forgery via unprotected multi-org GitHub App bypasses signature verification for a different organization's repository - (File: lib/shipit/github_app.rb, app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify a webhook against based on `repository.owner.login` taken from the still-unverified JSON payload, while the actual event handler resolves the repository to write to from `repository.full_name` in the same payload. In a multi-organization Shipit deployment, an attacker can set `repository.owner.login` to an organization whose `GitHubApp` has no `webhook_secret` configured — which causes `verify_webhook_signature` to short-circuit and return `true` unconditionally — while setting `repository.full_name` to a *different*, protected organization's repository that Shipit actually tracks. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` used to verify the request using a payload-derived field, before the payload's signature has been validated: [1](#0-0) [2](#0-1) 

The verification itself is performed by `GitHubApp#verify_webhook_signature`, which unconditionally passes when the selected org has no configured `webhook_secret`: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations, each with its own independent config block (including its own, possibly blank, `webhook_secret`): [4](#0-3) [5](#0-4) 

Meanwhile, the actual event handler that mutates state (`PushHandler`, and the base `Handler#repository_name`) resolves the target repository from a *different* payload field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) matches the owner portion of `repository.full_name` (used to pick the repository actually acted upon). An attacker who knows (or guesses) that any one organization configured in Shipit's multi-org `secrets.github` block has a blank/missing `webhook_secret` (the setup docs and example templates literally show `webhook_secret: # nil` as an acceptable default) can craft a single JSON payload where these two fields diverge, causing the request to pass verification for the "no-secret" org while acting on a completely different, protected org's repository/stack.

### Impact Explanation
This is an authentication-bypass class issue: it lets an unauthenticated, external attacker forge trusted GitHub webhook events (push, pull_request, status, check_suite, membership) for a target repository they do not control, as long as *any* other org configured on the same Shipit instance lacks a webhook secret. Concretely, a forged `push` event drives `PushHandler#process` → `Stack#sync_github(expected_head_sha: params.after)` → `GithubSyncJob`, which fetches and ingests commits up to an attacker-chosen `after` SHA into the tracked stack. On stacks with continuous delivery enabled, syncing new commits can trigger automatic deployment of that (attacker-influenceable) head, i.e., an unauthorized deploy — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Requires only an operator to have configured Shipit for more than one GitHub organization with at least one of the organizations left without a `webhook_secret` — a configuration explicitly documented and shown with blank secrets in `config/secrets.development.shopify.yml` and `docs/setup.md`. The attacker needs no credentials, no repository access, and no Shipit session — only the ability to POST to the public `/webhooks` endpoint with a crafted JSON body and an `X-Github-Event` header.

### Recommendation
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank for a resolved organization when other organizations on the same instance do have secrets configured; require every configured org to have a secret, or fail closed.
- After selecting `repository_owner` for verification, revalidate that the same payload's `repository.full_name` owner segment matches `repository_owner` before dispatching to handlers, rejecting mismatches with 422.
- Consider deriving the verifying organization deterministically from routing/target repository rather than trusting an unverified payload field.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `unprotected-org` (no `webhook_secret`) and `victim-org` (has stacks tracked, `webhook_secret` set).
2. POST to `/webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unprotected-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "unprotected-org")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (invalid/absent) signature.
4. `Webhooks::Handlers::PushHandler` resolves `repository_name` from `repository.full_name` = `victim-org/victim-repo`, finds the real `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, ingesting attacker-influenced commit history into `victim-org`'s tracked stack without any valid signature from `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
