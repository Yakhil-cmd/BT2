### Title
Split interest-rate-curve setters allow a front-run that yields the wrong borrow rate, socializing a loss onto suppliers - (File: mainnet/contracts/vault/v0-vault-stx.clar)

### Summary
`v0-vault-stx.clar` (and its sibling vaults `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) expose two independent, individually DAO-authorized setters, `set-points-util` and `set-points-rate`, that together define a single logical object: the Aave-style kink interest-rate curve [1](#0-0) . Because these are two separate public functions instead of one atomic setter, if the DAO ever changes the curve by issuing them as two separate transactions (exactly the "EOA calling two functions in two txs" pattern described in the external report), any user can interleave a `borrow`/`repay` between them and lock in interest computed from a mismatched (old-util/new-rate or new-util/old-rate) curve.

### Finding Description
`set-points-util` only rewrites the `util` field of `points-ir`, leaving `rate` untouched, and vice-versa for `set-points-rate`: [1](#0-0) 

Both are guarded only by `check-dao-auth`, i.e. `tx-sender == dao-executor`, with no mechanism forcing them to be applied together in one transaction. Every existing on-chain usage in this repo (e.g. `proposal-set-stx-interest-rates.clar`, `proposal-set-usdc-interest-rates.clar`, `v0-init.clar`) happens to call `set-points-util` immediately followed by `set-points-rate` inside a single proposal `execute` function [2](#0-1) , which is atomic. However, nothing in the vault contract itself enforces that these two state components can only be updated together — the DAO (via `dao-executor`) can call them as two separate top-level transactions, and between those two transactions the utilization/rate mapping is transiently inconsistent (mismatched breakpoints paired to the wrong rates). Any unprivileged borrower who observes the first transaction in the mempool/block can submit a `borrow` in between and have their interest computed against this inconsistent curve, potentially locking in a below-intended rate.

Any interest under-charged this way is not paid by the attacker — it is a lender-side (supplier) shortfall, since supplier yield in this Aave-style model is a share of interest actually collected from borrowers, i.e. a socialization of the loss onto all suppliers of that vault. This maps to the report's core defect: “to change [a config] the owner will generally have to call two separate functions… If the owner calls them in two separate transactions… a third party can act in between, leading to an unintended value.”

### Impact Explanation
The affected component is the DAO-facing interest-rate curve of a lending vault, which is shared state consumed by every borrow/repay/accrue call. A borrower who sandwiches the two-call curve update effectively obtains a rate lower than what the DAO intended for either the old or the new curve, and that discrepancy is a real cost socialized across all current suppliers of the vault (reduced yield), which the report's classification treats as "High – theft of unclaimed yield" for the suppliers who share the pool. The magnitude is limited to the compounding effect during the brief mismatch window and any position opened in it, so it is not comparable in severity to a direct drain, but it is a genuine loss transferred from one unprivileged class (suppliers) to another (the front-running borrower).

### Likelihood Explanation
This requires the DAO to actually submit `set-points-util` and `set-points-rate` as two separate transactions rather than bundling them in one `execute` proposal call, as every current proposal script in this repo does. Given that all existing tooling (proposal scripts) already bundles the two calls atomically, the likelihood of this occurring in practice is low, and would represent an operational deviation by governance rather than an inherent code path reachable by an attacker alone. This significantly reduces exploitability relative to the original UMA finding, where an EOA owner naturally makes two separate calls without any bundling convention.

### Recommendation
Merge `set-points-util` and `set-points-rate` into a single `set-points-curve` (or similarly named) function that atomically updates both `util` and `rate` fields of `points-ir` in one call, mirroring the UMA fix of merging `setBond`/`setCollateral` into `setCollateralAndBond`. If backward compatibility requires keeping the two setters, add a `curve-generation` nonce/version check or a pause flag around curve mutation so that borrow/repay transactions cannot execute against a partially-updated curve within the same block.

### Proof of Concept
1. DAO calls `set-points-util` on `v0-vault-stx` in transaction T1 to install a new utilization breakpoint set (e.g., raising the optimal utilization point from 80% to 90%), while the existing `rate` points (tuned for the old 80% optimal curve) remain unchanged.
2. Before the DAO submits T2 (`set-points-rate` with the matching new rate points), an attacker observes T1 in the mempool and submits `borrow` on the same asset in the same block/immediately after T1 lands.
3. The attacker's borrow is priced using the new (higher) utilization breakpoints paired with the old (lower) rates tuned for a different curve shape, resulting in an interest rate lower than the DAO intended for either the old or the new configuration.
4. T2 lands, restoring curve consistency, but the attacker's borrow — and the accrued index state during the mismatch window — already reflects the discounted rate, permanently reducing yield realized by suppliers of `v0-vault-stx` for that period. [1](#0-0)
