### Title
Cross-Organization Webhook Signature Confusion Allows Forged Status/Push Events for Repositories Under a Different, Properly-Secured GitHub Org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an incoming webhook against using the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), while every event handler that actually decides *which* `Stack`/`Repository` to act on reads a *different* attacker-controlled field, `repository.full_name`. In Shipit's documented multi-organization deployment mode, these two fields are not required to be consistent, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected org has no `webhook_secret` configured. An attacker can therefore pick an onboarded-but-unsecured org to pass signature verification, then embed a `repository.full_name` pointing at a fully-secured org's tracked repository, causing Shipit to process a forged event as if it legitimately came from that secured org.

### Finding Description
`verify_signature` picks the org whose secret is checked *before* any authenticity of the payload is established: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the unverified JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`). That value is used to fetch a `Shipit::GitHubApp` instance and check the signature against *that org's* secret: [3](#0-2) 

Critically, if the selected org has no `webhook_secret` configured, `verify_webhook_signature` returns `true` with no HMAC check at all (`return true unless webhook_secret`). Shipit explicitly supports and documents running multiple independent GitHub App configurations, keyed by organization, in a single deployment: [4](#0-3) [5](#0-4) 

and the example/dummy configs ship with `webhook_secret` left blank by default for each org entry: [6](#0-5) 

Once signature verification passes (because it validated against Org A's blank-secret config), the full raw payload is handed to the matching event handler, which resolves the actual repository/stack using the *unrelated* `repository.full_name` field: [7](#0-6) 

For example, the push handler queues a real sync job against whatever stack matches `repository.full_name`: [8](#0-7) 

and the status handler creates a `Commit::Status` for whatever commit/repo `repository.full_name` resolves to, which feeds directly into deploy-eligibility decisions elsewhere in the app.

**Binding broken:** the organization whose credential (webhook secret) authenticated the request ≠ the organization/repository whose `Stack` state the handler actually mutates.

### Impact Explanation
An attacker who knows (or can guess) the login of any organization onboarded to a shared Shipit instance without a `webhook_secret` configured can forge webhook deliveries that are processed as authentic for a *different*, properly-secured organization's tracked repositories. Depending on the event, this allows:
- Forcing `GithubSyncJob` runs / branch state changes on another org's stacks (`push`).
- Writing forged commit statuses (`status`) for another org's commits, which can influence whether a commit is considered deployable, i.e. an unauthorized-deploy-adjacent write into deploy-gating state.
- Creating/removing team memberships and users cross-org via the `membership` event (though this is scoped by `organization.login`, not `repository`, reducing exposure there).

This satisfies the "Critical/High" bar of an unauthorized write into deploy state / cross-repository writes across organizations, without needing an `ApiClient` token, session, or GitHub App credential for the target org — only knowledge that *some* org on the instance lacks a webhook secret.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (explicitly documented and supported), and (2) at least one onboarded org whose `webhook_secret` was left unset — which the example configs actually ship as the default value, making misconfiguration plausible in real deployments that follow the documented setup literally. No authentication, session, or token is needed to send the crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind org selection and target-repository resolution together and require consistency: verify the webhook against the org derived from `repository.full_name`'s owner (not a separately-controlled `owner.login`/`organization.login` field), and reject payloads where they diverge. Additionally, do not allow `verify_webhook_signature` to silently succeed when `webhook_secret` is blank for a configured multi-org entry — require an explicit opt-in (e.g., only skip verification for the single-app legacy schema, not per-org entries), and log/alert on any org config missing a secret.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `OrgA` configured with no `webhook_secret` and `OrgB` configured with a real secret and a tracked repository/stack `OrgB/secured-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/secured-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `PushHandler` resolves the target stack via `repository.full_name` = `OrgB/secured-repo` and enqueues `GithubSyncJob` for that stack — a forged event accepted and acted on for `OrgB`'s repository despite never satisfying `OrgB`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
