### Title
Lack of a token-burn primitive for AA-managed assets lets repaid "debt" tokens accumulate as spendable AA balance instead of being destroyed, causing unbacked oversupply - (File: aa_composer.js, validation.js)

### Summary
Obyte's asset model has no general-purpose "burn" operation. The only mechanism that permanently removes tokens from circulation is the static, asset-wide `auto_destroy` flag, which is enforced only at the base-layer input-selection/validation level. An Autonomous Agent (AA) that implements a lending/stablecoin pattern (issue a debt-backed asset, later accept it back as "repayment") has no way to actually reduce the asset's circulating supply on repayment — the repaid tokens are simply credited to the AA's own spendable `aa_balances`, exactly mirroring the `JUSDBank.repay()` bug where repaid JUSD sits in the bank contract instead of being burned.

### Finding Description
When an AA trigger sender sends its own previously issued asset back to the AA (a natural "repay debt" pattern), the composer's `updateFinalAABalances()` unconditionally adds the amount to the AA's balance for that asset, based only on `output.address === address`, with no notion of destroying/burning the tokens: [1](#0-0) 

This is the *only* accounting update path for self-addressed asset payments; there is no corresponding decrement of a "circulating supply" concept, because ocore has none for uncapped assets — `cap` freezes supply forever at issuance and cannot be reduced afterward. Contrast this with the base (bytes) asset, which does support a real per-unit burn via `burn_fee`, deducted directly in the balance-check formula: [2](#0-1) 

No such `burn_fee`/burn concept exists for custom assets. The single asset-level "destroy" feature that does exist, `auto_destroy`, only works when tokens are sent to the asset's `definer_address`, and it permanently excludes those outputs from ever being spent again — it is enforced in both the divisible/indivisible coin-picking logic: [3](#0-2) [4](#0-3) 
and in unit validation, which rejects any attempt to spend an output that was sent to the definer of an `auto_destroy` asset: [5](#0-4) 

Because `auto_destroy` makes the definer's own received funds permanently unspendable, it is unusable for the common design where the AA is *both* the asset's `definer_address` and the active manager of collateral/backing (it would never be able to spend or re-balance the very tokens it needs to manage). Every debt/stablecoin-style sample AA in the codebase (e.g., `futures_contract.oscript`, `create_an_asset.oscript`, `uniswap_like_market_maker.oscript`) therefore defines its asset with `auto_destroy: false`, meaning any "repayment" pattern built on ocore's primitives necessarily leaves repaid tokens as normal spendable AA balance rather than destroying them: [6](#0-5) 

As a result, an AA author implementing a JUSD-like lending contract on ocore has no base-layer facility to actually shrink the token supply when debt is repaid; the AA's internal debt-tracking state var can be decremented, but the physical tokens keep existing and keep counting toward `balance[asset]`, from which the AA (or any code path relying on that balance, e.g. re-issuing collateral, paying out yield, or servicing new loans) can redistribute them — producing tokens that are counted as circulating/available but are no longer backed by the collateral that originally backed the discharged debt.

### Impact Explanation
Any AA acting as a collateral-backed asset issuer (lending/stablecoin pattern) that relies on ocore's native asset/AA balance primitives inherits an oversupply risk identical to the JUSD case: after a wave of repayments (e.g., during a market downturn triggering liquidations), the AA accumulates a growing pool of its own "repaid" debt asset that is not actually removed from the asset's total issued supply. If any AA logic path treats `balance[asset]` as spendable/redistributable funds (a very common oscript pattern, as seen across the sample AAs), those un-backed tokens can be paid out again to users, permanently decoupling total token supply from real collateral and enabling value extraction/insolvency of the represented stable-value asset — a Medium/High severity supply-integrity issue reachable by ordinary, unprivileged AA trigger senders performing normal "repay" interactions.

### Likelihood Explanation
This is not a hypothetical edge case: it is the default and unavoidable outcome of building any lending/repay/burn pattern on top of ocore's asset system, since (1) `cap` cannot be reduced after issuance, (2) there is no generic burn instruction for AA-managed assets, and (3) the only destroy primitive (`auto_destroy`) is structurally incompatible with an AA that must also manage/spend the same asset as its collateral-controller. Any AA author who models "repay debt" as "send the debt token back to me" — the most natural implementation given available primitives — reproduces this bug automatically, with no attacker action needed beyond normal trigger interactions.

### Recommendation
Since ocore itself provides no generic burn opcode for custom assets, AA designers must be warned (and ideally the platform should provide a primitive) that repaid/collateral-backing tokens sent back to an issuing AA are not automatically removed from supply. A safe pattern requires either: (a) using a *separate* `auto_destroy` asset dedicated purely to being burned to the AA's definer address for debt extinguishment (decoupled from the AA's own operational collateral asset), or (b) the AA continuously tracking "total_supply outstanding" as state and enforcing all payouts strictly against `total_supply - repaid_and_held_amount` rather than trusting `balance[asset]`, ensuring repaid tokens held in the AA's balance are never re-distributed as if newly backed.

### Proof of Concept
1. AA `L` (a lending/stablecoin manager) defines asset `D` with `issued_by_definer_only: true`, `auto_destroy: false` (as in every debt/stablecoin sample in this repo, e.g. `futures_contract.oscript` lines 12-24) since `auto_destroy: true` would make `L` unable to ever manage its own collateral.
2. User `U` borrows: `L` issues/sends `D` tokens to `U` against posted collateral, and increments `var['total_borrowed']`.
3. User `U` "repays" by sending the same `D` tokens back to `L` in a trigger payment. `handleTrigger` → `updateFinalAABalances` credits `L`'s `aa_balances` for asset `D` by the full repaid amount, with no burn: [1](#0-0) 
4. `L`'s oscript decrements `var['total_borrowed']` but the `D` tokens physically still exist and are now simply part of `balance[D]` at `L`, indistinguishable from freshly-collateralized tokens.
5. Because `D` was never `auto_destroy`, nothing in `validation.js` or the coin-picking logic in `inputs.js`/`indivisible_asset.js` prevents `L` from later re-sending these same "repaid" `D` tokens to another borrower or in a payout — inflating usable/circulating `D` beyond the amount actually backed by outstanding collateral, reproducing the JUSD-oversupply scenario at the AA layer.
