### Title
Webhook Signature Verification Selected by Unverified Payload Field Allows Signature Bypass and Forged Team-Membership Escalation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against, using a field taken directly from the *unverified* JSON body, before any signature has been checked. In a multi-organization Shipit deployment where any configured organization has no `webhook_secret` set — which is the documented/default configuration shape (`webhook_secret: # nil`) — an attacker can pick that organization to make `verify_webhook_signature` short-circuit to `true`, bypassing HMAC verification entirely, while the very same untrusted payload is subsequently used by event handlers (e.g. the membership handler) to mutate `Team`/`Membership` records that feed into `Shipit.github_teams` authorization.

### Finding Description
The controller determines the organization used for signature verification purely from request body content that has not yet been authenticated: [1](#0-0) [2](#0-1) 

`repository_owner` is read via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both of which are attacker-controlled fields inside the raw, unauthenticated POST body. This value is fed into `Shipit.github(organization: repository_owner)` to pick a per-organization `GithubApp` instance, whose `webhook_secret` is then used to verify `X-Hub-Signature`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank (line 77: `return true unless webhook_secret`). The documented multi-org configuration format explicitly allows some organizations to have no webhook secret configured, as shown in the shipped templates: [4](#0-3) 

This breaks the intended binding: `organization used to authenticate the request == organization whose repository/team data is subsequently written`. An attacker who knows (or brute-forces) that any org in the deployment's `secrets.yml` has no `webhook_secret` can set `repository.owner.login` (or `organization.login`) to that org's name to force `verify_signature` to pass, then rely on the exact same forged payload being processed by event handlers — which re-derive the actual entities to mutate (team, membership, repository) from that same untrusted body. The `membership` event handler, for instance, creates `Team` and `Membership` records directly from webhook parameters with no further authentication, as demonstrated by: [5](#0-4) 

Those `Team`/`Membership` records are exactly what backs `User#authorized?`: [6](#0-5) 

so a forged, unsigned `membership` webhook can add an arbitrary GitHub-login-controlled user to a team present in `Shipit.github_teams`, escalating that user into application authorization.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization, one of the defined High-severity outcomes: an unprivileged, unauthenticated actor can forge a `membership` webhook event, choose an unconfigured-secret organization to bypass `verify_webhook_signature`, and cause Shipit to record that an arbitrary GitHub login belongs to a `Team` used for access control. Once granted, that GitHub identity passes `force_github_authentication`'s `current_user.authorized?` check and gains full application access (creating stacks, triggering deploys, managing API clients), constituting an authorization bypass beyond mere read access.

### Likelihood Explanation
Exploitability depends on the deployment running with multiple GitHub organizations configured (`config/secrets.yml` supporting the `github: <org>: {...}` multi-org shape) where at least one configured organization omits `webhook_secret`. This is a documented, supported configuration pattern (see the shipped `secrets.development.shopify.yml` and `secrets.development.example.yml` templates showing `webhook_secret: # nil` as an accepted value), making this a realistic operational configuration rather than a purely theoretical one, though it does require that specific multi-org setup to be reachable.

### Recommendation
- Do not select the signature-verification secret based on unverified request-body content. Verify the webhook signature using a fixed/central secret (or verify against all configured organizations' secrets and require a match) before trusting any field extracted from `params` to route or process the event.
- Reject webhooks outright when no `webhook_secret` is configured, rather than treating a missing secret as automatic verification success (change `return true unless webhook_secret` to fail closed, or require secrets to be mandatory for all configured organizations).
- Ensure the organization/repository identity used to authorize the write (e.g., which `Team`/`Stack` a handler mutates) is derived only after successful signature verification tied to that exact organization.

### Proof of Concept
1. Deploy Shipit with a multi-org GitHub config in `secrets.yml`, e.g. `github: { org-a: { webhook_secret: "s3cr3t", ... }, org-b: { webhook_secret: nil, ... } }` (a supported configuration shape per `config/secrets.development.shopify.yml`).
2. POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, body:
   ```json
   {
     "action": "added",
     "organization": { "login": "org-b" },
     "team": { "id": 1, "name": "Admins", "slug": "admins", "url": "https://example.com" },
     "member": { "login": "attacker-controlled-login" }
   }
   ```
3. `repository_owner` resolves to `"org-b"`, `Shipit.github(organization: "org-b")` returns the app config with `webhook_secret: nil`, so `verify_webhook_signature` returns `true` regardless of the (absent/invalid) signature header.
4. The membership handler processes the payload and creates/attaches `attacker-controlled-login` as a member of team `admins` (per behavior shown in `test/controllers/webhooks_controller_test.rb:129-149`).
5. If `admins`/`Admins` matches a team listed in `Shipit.github_teams`, the attacker's GitHub account is now authorized by `User#authorized?`, bypassing the intended team-membership gate without ever presenting a valid webhook signature for a properly secured organization.

*(Note: I was unable to directly view the full source of `app/models/shipit/webhooks/handlers/membership_handler.rb` in this session due to tool limitations in the final iteration; the handler's behavior is inferred from the corresponding controller test which exercises it end-to-end.)*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
