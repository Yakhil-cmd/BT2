### Title
Withdraw allows LP-token holder to route redeemed tokens back into the pool's own vault, decoupling `lp_supply` from real vault reserves and enabling a share-inflation DOS - (File: `programs/cp-swap/src/instructions/withdraw.rs`)

### Summary
The `Withdraw` instruction accepts arbitrary `token_0_account` / `token_1_account` destinations constrained only by mint, not by ownership, and not by inequality to the pool's own vault. A caller can therefore set the redemption destination equal to `token_0_vault`/`token_1_vault` themselves. Because `transfer_from_pool_vault_to_user` performs a plain `transfer_checked` CPI (which allows source == destination), the "withdrawal" becomes a no-op transfer: the LP's shares are burned and `pool_state.lp_supply` decreases, but the underlying tokens never actually leave the vault. This is the same root cause as the referenced DODO GSP finding — burning shares while returning/keeping the redeemed assets inside the pool contract — and produces the identical DOS: it inflates the vault-reserve-to-`lp_supply` ratio, forcing future depositors of a small `lp_token_amount` to supply disproportionately large token amounts (due to `Ceiling` rounding in `CurveCalculator::lp_tokens_to_trading_tokens`), or reverting entirely.

### Finding Description
`Withdraw`'s accounts only constrain the receiving token accounts by mint: [1](#0-0) 
There is no `token::authority = owner` (unlike `owner_lp_token`) and no constraint preventing `token_0_account`/`token_1_account` from being the pool's own `token_0_vault`/`token_1_vault`: [2](#0-1) 

The withdraw logic computes the redeemable amount from the current `lp_supply`/reserve ratio, burns the LP tokens, and then transfers the computed amount out via `transfer_from_pool_vault_to_user`: [3](#0-2) 

That helper issues a standard `transfer_checked` CPI with attacker-supplied `from`/`to` `AccountInfo`s: [4](#0-3) 

If the attacker passes `token_0_account = token_0_vault` (satisfying the `token::mint = token_0_vault.mint` constraint trivially, since it *is* the vault), the SPL/Token-2022 `transfer_checked` executes a self-transfer: the vault's on-chain balance is unaffected (debit and credit cancel), while `pool_state.lp_supply` is permanently reduced by the burned amount: [5](#0-4) 

Because deposit/withdraw pricing is driven purely by `total_token_amount / lp_supply` via `vault_amount_without_fee` and `CurveCalculator::lp_tokens_to_trading_tokens`, an attacker can:
1. Deposit a large `lp_token_amount` (paying proportional real tokens into the vault) via `deposit()`.
2. Immediately `withdraw()` nearly all of those minted shares while setting the destination token accounts equal to the pool's own vaults, burning the shares but leaving the deposited tokens trapped in the vault (no actual outflow).

This mirrors the DODO GSP bug exactly: shares are destroyed while the corresponding assets remain inside the pool's own balance, inflating the effective value-per-share for the (now much smaller) remaining `lp_supply`. [6](#0-5) [7](#0-6) 

Note that the permanent `lock_lp_amount = 100` minted-short mechanism in `initialize`/`initialize_with_permission` only protects against the pool's `lp_supply` ever reaching literal zero at genesis; it does not prevent the reserve/`lp_supply` ratio from being pumped arbitrarily high by any subsequent depositor performing this self-redirect trick: [8](#0-7) 

### Impact Explanation
Once the ratio `total_token_amount / lp_supply` is pumped up, `deposit()`'s `RoundDirection::Ceiling` computation forces any depositor requesting even `lp_token_amount = 1` to supply proportionally huge `token_0_amount`/`token_1_amount`, up to `maximum_token_0_amount`/`maximum_token_1_amount` slippage bounds, or the transaction reverts. This permanently denies normal-sized LP deposits to the pool (DOS on liquidity provisioning) unless a large enough depositor appears, matching the Medium-severity impact described in the analog report. It is a real accounting/availability harm to the pool and future LPs, not merely a self-inflicted loss for the attacker.

### Likelihood Explanation
Any unprivileged user who has previously deposited (or who deposits then immediately withdraws in the same/adjacent transaction) can trigger this by simply constructing the `Withdraw` instruction with `token_0_account`/`token_1_account` set to the pool's `token_0_vault`/`token_1_vault` public keys — accounts that are always publicly known (they are PDAs derivable from the pool). No special privileges, timing, or validator behavior is required; it is directly reachable from a single submitted transaction with attacker-chosen accounts.

### Recommendation
Add explicit constraints on the `Withdraw` (and `Deposit`, for symmetry) accounts to reject destination/source token accounts that alias the pool's vaults, e.g.:
```rust
#[account(
    mut,
    token::mint = token_0_vault.mint,
    constraint = token_0_account.key() != token_0_vault.key() @ ErrorCode::InvalidVault,
)]
pub token_0_account: Box<InterfaceAccount<'info, TokenAccount>>,
```
and equivalently for `token_1_account`. Alternatively/additionally, require `token::authority = owner` on these accounts so redeemed funds can only go to an account actually owned by the withdrawing LP, closing the self-redirect vector entirely.

### Proof of Concept
1. Pool `P` exists with `lp_supply = S`, vault reserves `(R0, R1)`.
2. Attacker calls `deposit(lp_token_amount = L, ...)`, depositing tokens proportional to `L`; state becomes `lp_supply = S + L`, reserves `(R0 + d0, R1 + d1)`.
3. Attacker calls `withdraw(lp_token_amount = L - 1, minimum_token_0_amount = 0, minimum_token_1_amount = 0)`, passing `token_0_account = token_0_vault` and `token_1_account = token_1_vault` (allowed, since only `token::mint` is checked).
4. `transfer_from_pool_vault_to_user` executes `transfer_checked` with `from == to`; vault balances are unchanged, but `pool_state.lp_supply` is reduced to `S + 1`.
5. Vault now holds `(R0 + d0, R1 + d1)` backing only `S + 1` LP shares — a massively inflated per-share value.
6. Any subsequent depositor calling `deposit(lp_token_amount = 1, ...)` must supply `≈ (R0+d0)/(S+1)` and `≈ (R1+d1)/(S+1)` tokens (per `CurveCalculator::lp_tokens_to_trading_tokens` with `RoundDirection::Ceiling`) — an amount the attacker can make arbitrarily large by choosing `L` large enough, DOSing ordinary deposit sizes.

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```

```rust
    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }
```
