### Title
`Shipit::ReviewStack#env` lets a PR label overwrite `ENVIRONMENT`/`GITHUB_REPO_OWNER`/etc., causing capistrano to run against an unauthorized target - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::ReviewStack#env` merges the pull request's GitHub labels *on top of* the trusted env hash returned by `Shipit::Stack#env`, using the upcased label name as the key and the literal string `"true"` as the value. Because label names are attacker-controlled free text captured verbatim from the webhook payload, an unprivileged PR author can name a label `ENVIRONMENT` (or `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `LAST_DEPLOYED_SHA`, `BRANCH`) to clobber that reserved key before it reaches `TaskCommands#env`/`DeployCommands#env` and ultimately `Command#unbundled_env`/`PTY.spawn`.

### Finding Description
The binding that should hold is: **the `ENVIRONMENT` value interpolated into the executed command line == `stack.environment`** (the value assigned at review-stack creation time by `ReviewStackAdapter`).

Trace:
1. `Shipit::Stack#env` builds the authoritative hash: `'ENVIRONMENT' => environment, 'GITHUB_REPO_OWNER' => repository.owner, ...` [1](#0-0) .
2. `Shipit::ReviewStack#env` overrides this via `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [2](#0-1) . Any label whose upcased name matches a reserved key wins the merge and replaces the real value with the string `"true"`.
3. Labels are populated straight from the webhook payload with no allow-list or format validation: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` in `LabelCapturingHandler#capture_labels` [3](#0-2) , triggered on `opened`, `labeled`, `unlabeled`, `reopened` for any `stack.present? && !stack.archived?` review stack [4](#0-3) .
4. `TaskCommands#env` calls `.merge(@stack.env)` where `@stack` is the polymorphic `task.stack`, i.e. the `ReviewStack` instance, so the corrupted hash flows straight through [5](#0-4) . `DeployCommands#env` further merges on top but never restores `ENVIRONMENT` [6](#0-5) .
5. `Command#interpolate_environment_variables` interpolates `$ENVIRONMENT` from this env at execution time via `EnvironmentVariables#interpolate` [7](#0-6) , and capistrano-based deploy steps are literally generated as `bundle_exec("cap $ENVIRONMENT #{command}")` [8](#0-7) . `Command#start` spawns this interpolated command line via `PTY.spawn` [9](#0-8) .

**Why existing guards don't stop it**: `EnvironmentVariables#permit`/`sanitize_env_vars` is only invoked for `filter_deploy_envs`/`filter_task_envs`, which apply to *user-supplied custom deploy variables* passed into `trigger_deploy`/`trigger_task`, not to the internal env hash built by `TaskCommands#env`/`ReviewStack#env` [10](#0-9) . There is no allow-list check on label names in `LabelCapturingHandler` or `ReviewStack#env`, and the `ExplicitParameters` schema for the webhook only validates types (`String` for label name), not content [11](#0-10) .

**Exploit flow**: attacker opens/owns a PR against a repo with an active Shipit review stack, adds a GitHub label literally named `ENVIRONMENT` (case-insensitive) via the GitHub UI/API on their own PR, GitHub fires a signed `labeled` webhook for their own repo, `LabelCapturingHandler` (a legitimately-authenticated webhook for that repository) stores the label, and the next deploy/rollback/task on that review stack executes `cap true deploy` instead of `cap pr123 deploy`.

### Impact Explanation
Before: `stack.environment == "pr123"`, `env['ENVIRONMENT'] == "pr123"`; the executed line is `cap pr123 deploy`, matching the review-stack authorized target. After labeling: `env['ENVIRONMENT'] == "true"` while `stack.environment` is unchanged, so the executed line becomes `cap true deploy` — the binding is broken. Because the merge is a plain `Hash#merge` over any upcased label name, the same mechanism also clobbers `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `LAST_DEPLOYED_SHA`, and `BRANCH` if the attacker names a label accordingly, corrupting whatever deploy/rollback scripts rely on those variables. This causes an unauthorized/incorrect deploy or rollback command to execute for a review stack that a webhook payload (fully controlled by the PR author) never should have been able to redirect — matching the "unauthorized deploy or rollback" Critical category. The blast radius is scoped to the affected review stack's own capistrano invocation (the value is always the fixed literal `"true"`, not attacker-chosen text), so cross-tenant targeting depends on `"true"` happening to be a valid stage in that project's capistrano config; absent that it manifests as a broken/failed deploy rather than a controlled cross-tenant compromise.

### Likelihood Explanation
Preconditions are low-cost and fully within an unprivileged attacker's reach: the repository must already have Shipit review stacks enabled (an existing feature, not attacker-controlled) and the attacker must be able to open a PR and label it — which any GitHub contributor (or a fork's owner submitting a PR against the integrated repo) can do. No Shipit session, API token, or secret is required; the webhook is a normal, correctly-signed GitHub event for that repository. The attack is trivially repeatable (label/unlabel any number of times) against any repo/stack combination the attacker can open PRs on.

### Recommendation
In `Shipit::ReviewStack#env`, do not let label-derived keys collide with reserved Stack env keys. Merge labels first, then re-apply/lock the trusted `super` values on top (e.g. `pull_request.labels...merge(super)`), or explicitly filter out/blocklist keys like `ENVIRONMENT`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `LAST_DEPLOYED_SHA`, `BRANCH` before merging label-derived entries, or prefix label-derived variables (e.g. `LABEL_<NAME>`) so they can never collide with system-reserved keys.

### Proof of Concept
Add to `test/models/shipit/review_stack_test.rb` (or similar):
```ruby
test "#env: a PR label named ENVIRONMENT overwrites the real ENVIRONMENT value" do
  stack = shipit_stacks(:shipit) # a Shipit::ReviewStack fixture with environment "pr123"
  stack.pull_request.update!(labels: ['ENVIRONMENT'])

  assert_equal 'pr123', Shipit::Stack.find(stack.id).environment # unchanged binding side A
  assert_equal 'true', stack.env['ENVIRONMENT']                   # broken binding side B
  refute_equal stack.environment, stack.env['ENVIRONMENT']
end

test "DeployCommands#env carries the label-overwritten ENVIRONMENT into the executed command" do
  deploy = shipit_deploys(:review_stack_deploy)
  deploy.stack.pull_request.update!(labels: ['ENVIRONMENT'])

  command = Shipit::DeployCommands.new(deploy)
  assert_equal 'true', command.env['ENVIRONMENT']

  cmd = Shipit::Command.new('cap $ENVIRONMENT deploy', chdir: '.', env: command.env)
  assert_equal 'cap true deploy', cmd.interpolate_environment_variables('cap $ENVIRONMENT deploy')
end
```
