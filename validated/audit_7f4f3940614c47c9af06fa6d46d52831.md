### Title
`provision?` operator-precedence bug lets `allow_with_label`/`prevent_with_label` bypass `review_stacks_enabled` - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` (and the identical `ReopenedHandler#unarchive?`) intends `review_stacks_enabled` to gate every provisioning branch, but Ruby's `&&`/`||` precedence only ANDs it with the `allow_all` branch. Any repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (or `allow_with_label`) will still auto-provision a review stack from an attacker-controlled pull request.

### Finding Description
Intended binding: `provision? == true` requires `repository.review_stacks_enabled == true` regardless of which `provisioning_behavior` branch matches.

Actual code: [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. If `provisioning_behavior` is `prevent_with_label` and `review_stacks_enabled` is `false`, opening a PR **without** the provisioning label makes `!pull_request_has_provisioning_label?` true and `provisioning_behavior_prevent_with_label?` true, so `provision?` returns `true` even though review stacks are disabled for that repository. Symmetrically, with `allow_with_label` and `review_stacks_enabled: false`, labeling the PR with `provisioning_label_name` also returns `true`.

`process` then unconditionally provisions: [2](#0-1) 

The identical flaw exists in `ReopenedHandler#unarchive?`: [3](#0-2) 

Attacker path: attacker opens (or pushes to) a pull request against a repository they can PR into (their own fork targeting the tracked repo, or any repo tracked by this Shipit instance that accepts external PRs), triggering a `pull_request` `opened`/`reopened` webhook. No secret, session, or maintainer privilege is required to open a PR or label it if the attacker owns the PR (GitHub label permissions aside — the `prevent_with_label`-without-label path requires no labeling action at all, only opening the PR). Existing guards (`ExplicitParameters` schema, `drop_unhandled_event`, webhook signature verification) validate payload shape and authenticity of the webhook itself but do not touch the `provision?` boolean logic, so they do not prevent this divergence. The repository-scoping (`Repository.from_github_repo_name`) correctly ensures the stack is created only for the targeted repository — the bug is not cross-tenant, but it does defeat that repository owner's explicit choice to disable review stacks.

### Impact Explanation
When triggered, `ReviewStackAdapter#find_or_create!` creates a `Shipit::Stack`/review stack for the targeted repository, entering the provisioning queue despite the repository owner explicitly setting `review_stacks_enabled: false`. Provisioning subsequently runs the repository's configured provisioning tasks (which shell out via `Command`/`PTY.spawn` in the deploy/task pipeline), meaning an attacker can force an unauthorized deploy/task execution for that repository's environment by simply opening a PR. This matches "an unauthorized deploy... " for a repository whose operator disabled the feature. It is repeatable per-PR/per-branch against any repository misconfigured in this way (i.e., `review_stacks_enabled: false` combined with `allow_with_label` or `prevent_with_label`), though it does not cross repository boundaries.

### Likelihood Explanation
Requires a repository configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — a plausible transitional/misconfiguration state (e.g., an operator disabling review stacks but leaving the behavior enum at a non-`allow_all` value, expecting it to be inert). No attacker secrets are needed: opening a PR (and, for the `allow_with_label` case, adding a label to their own PR) is enough. This is low-cost and fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three disjuncts, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
Table-driven minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style (outside the OUT-OF-SCOPE list is fine to *propose*, though `test/**` itself is excluded from remediation scope):
```ruby
[
  { review_stacks_enabled: false, behavior: :allow_all,          labeled: false, expected: false },
  { review_stacks_enabled: false, behavior: :allow_all,          labeled: true,  expected: false },
  { review_stacks_enabled: false, behavior: :allow_with_label,   labeled: true,  expected: false }, # currently true - BUG
  { review_stacks_enabled: false, behavior: :allow_with_label,   labeled: false, expected: false },
  { review_stacks_enabled: false, behavior: :prevent_with_label, labeled: false, expected: false }, # currently true - BUG
  { review_stacks_enabled: false, behavior: :prevent_with_label, labeled: true,  expected: false },
].each do |c|
  repository.update!(review_stacks_enabled: c[:review_stacks_enabled], provisioning_behavior: c[:behavior], provisioning_label_name: "deploy-me")
  payload["pull_request"]["labels"] = c[:labeled] ? [{ "name" => "deploy-me" }] : []
  if c[:expected]
    assert_difference(-> { Shipit::Stack.count }) { OpenedHandler.new(payload).process }
  else
    assert_no_difference(-> { Shipit::Stack.count }) { OpenedHandler.new(payload).process }
  end
end
```
Running this against current code fails for the two marked rows, proving `review_stacks_enabled: false` does not block provisioning under `allow_with_label`/`prevent_with_label`.
