### Title
Uncaught `throw Error` in address-definition-template evaluation crashes the validating node - ([File: definition.js])

### Summary
CVE-2022-3724 is a crash (DoS) in Wireshark's HID dissector caused by malformed, attacker-controlled input reaching a code path that throws instead of gracefully handling an error condition. The analogous bug class in `ocore` is an unhandled `throw Error(...)` inside asynchronous DB-callback code that is reachable during **normal unit/address-definition validation** of an attacker-crafted unit. Because these throws occur inside `async`/DB-callback continuations rather than inside the outer `try{...}catch(e)` block that wraps `validation.validate()`, they are not converted into a validation error and instead propagate as an uncaught exception, crashing the node process (denial of service for the whole network node, not just one connection).

### Finding Description
In `definition.js`, the function `validateAuthentifiers()` (used to check spending-condition authentifiers/signatures) evaluates the `'definition template'` operator like this: [1](#0-0) 
```
case 'definition template':
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            ...
```
Note that the sibling function `validateDefinition()` (used only when *defining* a new address definition, not while verifying authentifiers) handles the exact same "template not found" condition safely by returning a callback error string: [2](#0-1) 
```
conn.query(
    "SELECT payload FROM messages JOIN units USING(unit) \n\
    WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
    [unit, objValidationState.last_ball_mci],
    function(rows){
        if (rows.length !== 1)
            return cb("template not found or too many");
```
But `validateAuthentifiers()`'s copy of this logic uses `throw Error("not 1 template")` instead of `cb2(false)`/`cb(err)`. This throw happens inside a `db.query` callback, deep inside nested `async` control flow (`evaluate()` → `async.eachSeries` → DB callback), so it is **not** caught by the top-level `try { ... } catch(e) { return callbacks.ifJointError(...) }` block that wraps synchronous validation logic in `validation.js`'s `validate()`: [3](#0-2) 
```
try{
    if (objectHash.getUnitHash(objUnit) !== objUnit.unit)
        return callbacks.ifJointError(...);
}
catch(e){
    return callbacks.ifJointError("failed to calc unit hash: "+e);
}
```
Because the exception is thrown asynchronously (inside a MySQL/SQLite result callback, invoked after the synchronous `try/catch` scope has already returned), it becomes an uncaught exception in the Node.js event loop.

An attacker (any unit poster) can trigger this by:
1. Defining an address whose definition uses `['definition template', [unit, params]]` referencing a `definition_template` unit hash that does not correspond to exactly one stable, good-sequence `definition_template` message (e.g., a unit hash that was never posted as a `definition_template`, or one that was voided/non-serial so it doesn't satisfy `is_stable=1 AND +sequence='good'`).
2. Posting a unit that is signed by (or otherwise exercises the authentifier-checking path for) that address, so that `validateAuthentifiers()` — not the "define new definition" path `validateDefinition()` — evaluates this branch.

`validateAuthentifiers()` is reached from `validation.js`'s author validation whenever any unit signed by an address using such a definition is processed by any node (author, forwarding node, or hub), i.e., it is on the mainline, unprivileged unit-validation path.

### Impact Explanation
An uncaught exception thrown from inside a database-callback during unit validation will terminate the Node.js process unless something at the process level catches it (`process.on('uncaughtException', ...)`). If it is not safely caught, the effect is a full node crash triggered by a single unprivileged, network-visible unit — a "network unable to confirm new units" condition if repeated against multiple/critical nodes (witnesses, hubs), matching the CVE's DoS bug class. Even in the more benign case where the process happens to survive (e.g. a global handler swallows it), the mutex lock taken in `handleJoint`/`validateAuthentifiers` around unit validation is never released, since none of `cb`/`cb2`/`unlock()` are called on the throwing path — this stalls that node's unit-validation pipeline (denial of service against that node).

### Likelihood Explanation
Reaching this code requires only that the attacker control an address definition (their own) that references a `definition template` with a bad/non-existent/duplicate template unit, then post one signed unit from that address. No privileged role, hub cooperation, or malicious peer behavior is needed — this is exactly the class of "unprivileged unit poster" analog allowed by the rules. The inconsistency between `validateDefinition()` (safe `cb` path) and `validateAuthentifiers()` (unsafe `throw`) for the identical query strongly suggests this is an overlooked code path rather than an intentional invariant, increasing confidence that the condition (`rows.length !== 1`) is genuinely reachable with attacker-supplied data.

### Recommendation
In `definition.js`, change the `'definition template'` case inside `validateAuthentifiers()`'s `evaluate()` to fail safely instead of throwing:
```
function(rows){
    if (rows.length !== 1)
        return cb2(false); // or bubble a fatal_error like other cases do
    ...
```
Audit all other `throw Error(...)` statements inside DB-query callbacks in `definition.js` (there are 13 total) to ensure none of them can be triggered by attacker-controlled unit/definition content; convert any reachable ones to return validation errors via their callback instead of throwing.

### Proof of Concept
1. Post a unit `T` with a message of `app: "definition_template"` and get it stabilized normally, OR simply pick any hash that will never correspond to a stable `definition_template` message.
2. Create/broadcast an address whose definition is `['definition template', ['<hash-of-T-or-nonexistent-unit>', {"$foo": "bar"}]]` such that when validated it does NOT satisfy `is_stable=1 AND sequence='good' AND main_chain_index<=last_ball_mci` (e.g., reference a unit that was voided, or one still unstable relative to `last_ball_mci`, or a completely bogus hash).
3. Post a second unit signed by that address so that `validateAuthentifiers()` is invoked for it.
4. When `conn.query(...)` in `definition.js`'s `validateAuthentifiers()` returns `rows.length !== 1`, `throw Error("not 1 template")` executes inside the async DB callback, outside the protective `try/catch` in `validation.js`, causing an uncaught exception on the receiving node. [4](#0-3)
