## Confirmed root cause

`Shipit` supports a multi-org config schema keyed by GitHub org name, each with its own independent `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects **which** org's `GitHubApp` (and therefore which `webhook_secret`) to verify the inbound signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a field taken straight from the **unauthenticated, attacker-controlled** JSON body, before any signature check has succeeded [2](#0-1) .

Separately, every event handler resolves the **repository actually acted upon** using a *different* field from the same untrusted body: `payload.dig('repository', 'full_name')`, via `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . `PushHandler#process` then directly calls `stack.sync_github` for whatever stacks match that resolved repository [5](#0-4) .

Nothing in the code enforces that `repository.owner.login` (used to pick the verifying secret) is the same as the owner encoded in `repository.full_name` (used to pick the target Stack). Because `verify_webhook_signature` explicitly returns `true` whenever the selected org has no `webhook_secret` configured — `return true unless webhook_secret` [6](#0-5)  — an attacker only needs the Shipit deployment to have **one** configured org without a webhook secret (a documented, "optional" setting per `docs/setup.md`, and shown as `webhook_secret: # nil` in the multi-org example config) to defeat verification entirely for pushes/PR events aimed at a **different, secret-protected** org's repositories.

## Break-the-binding trace

`repository_owner` (org whose secret verifies the signature) `≠` `full_name`'s owner (org/repo actually written to) is possible because both are independently attacker-supplied strings in the same unsigned JSON body:

1. Shipit is configured with two orgs, e.g. `OrgWithSecret` (has `webhook_secret` set, and owns a tracked `Repository`/`Stack`) and `OrgWithoutSecret` (has `webhook_secret: nil`, e.g. a legacy/staging entry) — this is a supported, documented multi-org config shape (`test/dummy/config/secrets_double_github_app.yml`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a crafted body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "OrgWithoutSecret" },
       "full_name": "OrgWithSecret/some-tracked-repo"
     }
   }
   ```
3. `verify_signature` computes `repository_owner = "OrgWithoutSecret"`, calls `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is `nil` → `verify_webhook_signature` returns `true` unconditionally, with **no signature header required at all**.
4. `WebhooksController#create` proceeds and dispatches to `PushHandler`, which resolves the target repo/stack via `full_name = "OrgWithSecret/some-tracked-repo"` — a stack that legitimately belongs to the **secret-protected** org — and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob` for that org's stack, exactly as a genuine, correctly-signed GitHub webhook would.

This lets an unprivileged network attacker force `Shipit` to sync/refresh (and, for `pull_request` events, archive/unarchive review stacks, capture labels, or trigger provisioning) against repositories belonging to an org whose webhook secret was never presented or validated — a full authentication bypass on the webhook ingestion boundary for any Shipit instance with more than one configured GitHub org where at least one lacks a secret.

### Title
Webhook signature verification is keyed by an attacker-controlled `repository.owner.login` distinct from the `repository.full_name` actually acted upon, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and thus the `webhook_secret`) used to validate `X-Hub-Signature` based on the unauthenticated payload's `repository.owner.login`, while every webhook handler resolves the repository/stack it actually mutates from the unauthenticated payload's `repository.full_name`. In a multi-org Shipit deployment, if any configured org has no `webhook_secret`, an attacker can set `owner.login` to that unprotected org while setting `full_name` to a different, secret-protected org's tracked repository, bypassing signature verification for events acted on the protected org's stacks.

### Finding Description
- Signature verification org selection: [2](#0-1) 
- Unconditional bypass when `webhook_secret` is absent: [6](#0-5) 
- Target repository resolution used by all handlers, from a different payload field: [3](#0-2) 
- Concrete state-mutating handler using that resolution to trigger a sync: [5](#0-4) 
- Multi-org config with per-org, optionally-nil `webhook_secret`: [7](#0-6) 

The two lookups (`repository.owner.login` for authentication, `repository.full_name` for authorization/action target) are never cross-checked for consistency, and both come from the same untrusted, unsigned-at-that-point request body.

### Impact Explanation
This is an authentication bypass on the webhook ingestion trust boundary: an unprivileged network attacker who knows (or guesses) that any org in a multi-org Shipit config lacks a `webhook_secret` can forge push/pull_request/membership/check_suite events against a *different* org's tracked repositories without ever presenting a valid signature. Concretely this can force spurious `GithubSyncJob`s, archive/unarchive review stacks, or manipulate PR label-driven provisioning for stacks that belong to organizations whose webhook secret is otherwise properly protected — undermining the entire purpose of per-org webhook secrets.

### Likelihood Explanation
Requires only that the deployment configures more than one GitHub organization and that at least one has no `webhook_secret` set (an explicitly supported, documented configuration state, as shown by the shipped example secrets files). No credentials, session, or prior access are needed — a single unauthenticated HTTP POST to the public `/webhooks` endpoint suffices.

### Recommendation
Bind organization/secret selection to the same value used for authorization: derive both the verifying org and the target repository from a single canonical field (e.g., always use `repository.full_name`'s owner segment for secret lookup, or vice versa), and reject the request if the two ever disagree. Additionally, consider refusing to boot/serve a configured org with a blank `webhook_secret` in any multi-org deployment (or require secrets uniformly once more than one org is configured), so that a mis-configured or intentionally-open org cannot be leveraged to bypass protection for sibling orgs.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (`webhook_secret: nil`) and `OrgB` (`webhook_secret: <secret>`), with a `Repository`/`Stack` tracked for `OrgB/target-repo`.
2. Without any `X-Hub-Signature` header (or with an arbitrary/invalid one), POST to `/webhooks` with `X-Github-Event: push` and body:
   ```json
   { "ref": "refs/heads/master", "after": "deadbeef...",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" } }
   ```
3. `verify_signature` resolves `repository_owner = "OrgA"`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` and the request proceeds.
4. `PushHandler` resolves the target via `full_name = "OrgB/target-repo"`, finds the real `Stack` under `OrgB`, and enqueues `GithubSyncJob` for it — despite `OrgB`'s webhook secret never having been checked.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
