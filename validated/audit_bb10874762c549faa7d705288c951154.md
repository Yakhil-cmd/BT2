### Title
Security-review "oracle" (api.anthropic.com reachability) has no fallback and fails open, silently skipping all LLM-based vulnerability review - ([File: plugins/security-guidance/hooks/llm.py])

### Summary
The `security-guidance` plugin uses `api.anthropic.com` (or an `ANTHROPIC_BASE_URL` gateway) as the sole "oracle" that powers its commit/session security review. Reachability and API-call success are checked with `ensure_anthropic_reachable()` and `_call_claude()`; when either fails (network blackhole, proxy misconfiguration, rate-limit exhaustion, HTTP 5xx after retries, or schema-retry exhaustion), the review is simply skipped — there is no fallback reviewer (local static rules, alternate provider, or hard-fail/block) and no user-visible signal that a security check silently did not occur.

### Finding Description
`ensure_anthropic_reachable()` in `plugins/security-guidance/hooks/llm.py` probes `api.anthropic.com` once per process and caches the boolean result [1](#0-0) . Both the PostToolUse commit-review handler and the Stop-hook handler gate the entire LLM security review on this single boolean and exit early (`sys.exit(0)`) when it returns `False`, without running any alternative check: [2](#0-1) [3](#0-2) 

Even when the endpoint is reachable, `_call_claude()` gives up and returns `None` after HTTP errors (retryable 5xx/429 exhausted, or any other status) or network/timeout errors, again with no fallback path — the caller only records `_last_call_claude_http_error` for telemetry and otherwise proceeds as if no findings exist [4](#0-3) . The agentic investigate stage likewise treats an unavailable/failed model call as "fall back," i.e., skip review, rather than blocking or degrading to a secondary check [5](#0-4) .

This mirrors the reported bug class exactly: a single external "oracle" (Chainlink price feed / here, the Anthropic API reachability+response) is trusted with no fallback provider and no fail-safe default; when it becomes unavailable, the dependent security control (liquidation / here, vulnerability detection on commits) simply stops functioning.

### Impact Explanation
The security-guidance plugin's commit/session review is the mechanism intended to catch newly introduced vulnerabilities (secrets in logs, SSRF, command injection, auth bypass, etc.) before/after a commit. If `api.anthropic.com` is unreachable (e.g., corporate proxy issue, transient outage, NO_PROXY misconfiguration) or the API call otherwise fails, this review is silently disabled for the rest of the session (`_anthropic_reachable` is cached as `False`) — insecure commits proceed with no review and no explicit warning surfaced to the user in the normal workflow (only `debug_log`/metrics, which most users never see). This is a "fail open" control-availability issue: an attacker or unlucky network condition that denies the oracle effectively disables the security guardrail with zero visible degradation.

### Likelihood Explanation
Moderate. The reachability probe is only active under `CLAUDE_CODE_REMOTE` environments (comment: "Gated on CLAUDE_CODE_REMOTE so local installs never pay the probe cost") [6](#0-5) , so this specific fail-open path is scoped to remote/managed environments where network blackholing behind proxies is a documented, real occurrence per the code comments themselves. The `_call_claude` retry-exhaustion fail-open path applies more broadly to any environment using the direct API path.

### Recommendation
- Surface a clear, session-visible warning (not just `debug_log`) whenever the security review is skipped due to oracle unavailability, so users know no automated review occurred.
- Consider a fail-closed or "degrade to local heuristic" alternative — e.g., run the existing pattern/regex-based warnings (`sweep_pending_warnings`) as a fallback layer when the LLM oracle is unavailable, rather than skipping review entirely.
- Avoid permanently caching `_anthropic_reachable=False` for the whole process lifetime; periodically re-probe so a transient outage does not disable review for the rest of a long session.
- Emit a persistent, user-facing indicator (e.g., status line or transcript note) summarizing "N commits were not security-reviewed because the review service was unreachable."

### Proof of Concept
1. In a `CLAUDE_CODE_REMOTE=1` environment, configure the network so `api.anthropic.com` is unreachable/blackholed (e.g., firewall drop, misconfigured `NO_PROXY`).
2. Make a commit containing an obviously vulnerable pattern (e.g., hardcoded secret, `pickle.load` on untrusted input).
3. Observe that `ensure_anthropic_reachable()` returns `False`; `handle_commit_review_posttooluse` and `handle_stop_hook` both exit at `_skip(24)`/`_skip(10, restore=True)` respectively [7](#0-6) [8](#0-7) .
4. No security finding is reported to the user for the vulnerable commit, and no user-facing message indicates the review did not run — only an internal metrics record (`skip_reason`) that ordinary users never inspect.

def ensure_anthropic_reachable() -> bool:
    """Run once. Under a remote/proxied environment, probe api.anthropic.com;
    if blackholed, scrub NO_PROXY and re-probe. Returns True if reachable
    (or not in a remote env), False if still dead. Gated on
    CLAUDE_CODE_REMOTE so local installs never pay the probe cost."""
    global _anthropic_reachable
    if _anthropic_reachable is not None:
        return _anthropic_reachable
    if os.environ.get("CLAUDE_CODE_REMOTE", "").lower() not in ("1", "true", "yes", "on"):
        _anthropic_reachable = True
        return True
    if _probe_anthropic():
        _anthropic_reachable = True
        return True
    debug_log("Remote env: api.anthropic.com unreachable, stripping anthropic.com from NO_PROXY")
    _strip_anthropic_from_no_proxy()
    _anthropic_reachable = _probe_anthropic()
    if not _anthropic_reachable:
        debug_log("Remote env: api.anthropic.com still unreachable after NO_PROXY scrub")
    return _anthropic_reachable
