## Analysis

The C4 finding describes a generic integer-division rounding bug: dividing a reward numerator by a large denominator before scaling causes the result to round to zero, while a "last updated" state field is nevertheless advanced, permanently losing that period's reward. Agave's Alpenglow reward-calculation path contains a direct structural analog of this exact bug class in stake reward accounting.

### Root cause

`calculate_alpenglow_points` computes a stake account's Alpenglow reward by dividing the vote account's earned lamports by the *total* delegated stake to that vote account, per stake account, before any aggregation: [1](#0-0) [2](#0-1) 

`earned_credits` here is documented as "the lamports paid to the vote account," so `earned_points = earned_credits * stake_amount / total_stake` is a plain integer division with no fixed-point scale-up, computed independently for every stake account (unlike the Tower path, which defers division until after summing global points).

This is corroborated by `calculate_reward_points_partitioned`, which explicitly skips computing a shared `PointValue::points` for Alpenglow because each stake account's reward is already the final lamport amount from the per-account division above: [3](#0-2) 

### The "lastUpdated advances anyway" analog

In `calculate_stake_rewards`, when the Alpenglow-computed `ag_points` truncates to `0`, the code calls `skip_reward(SkippedReason::ZeroPoints)`: [4](#0-3) 

`skip_reward` decides whether to still advance `credits_observed` based on `advance_credits_for_skipped_reward`, which is `true` for Alpenglow whenever the vote account's credits changed this epoch — i.e., essentially always: [5](#0-4) 

The returned `skipped_reward()` sets `staker_rewards: 0, voter_rewards: 0` but a *new* `new_credits_observed`, which `redeem_stake_rewards` then unconditionally writes back into the stake account: [6](#0-5) 

This mirrors the reported bug precisely: `credits_observed` plays the role of `rewardsPerToken_.lastUpdated`, and `ag_points` plays the role of `rewardsPerToken_.accumulated`. Since Alpenglow rewards are computed strictly per-epoch (not as a running/cumulative balance — "In alpenglow, `points` represents the actual reward that this stake earned"), once `credits_observed` is advanced past a period whose reward rounded to zero, that reward is unrecoverable in any subsequent epoch.

### Realistic trigger, no attacker required

Minimum stake delegation is 1 SOL (1e9 lamports): [7](#0-6) 

For any large validator whose total Alpenglow-delegated stake is large relative to a small delegator's stake, and whose per-epoch vote-account earnings are modest, `earned_credits * stake_amount / total_stake` can integer-truncate to `0` for that delegator every single epoch — exactly the "no attacker needed, naturally occurs" scenario called out in the original report, since ordinary delegation and normal per-epoch reward distribution (not any privileged/validator-only action) trigger it.

### Title
Per-stake premature integer division in Alpenglow reward calculation permanently truncates small delegators' rewards to zero while `credits_observed` still advances - (File: `runtime/src/inflation_rewards/points.rs`, `runtime/src/inflation_rewards/mod.rs`)

### Summary
In the Alpenglow reward path, `calculate_alpenglow_points` computes each stake account's epoch reward via the unscaled integer division `earned_credits * stake_amount / total_stake` (`runtime/src/inflation_rewards/points.rs:300`), performed independently per stake account rather than deferred until after global aggregation (as Tower does). When this division truncates to zero for a stake account with small relative stake, `calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs:278-285`) still advances `stake.credits_observed` to the vote account's latest value via `skip_reward`/`skipped_reward()`, because `advance_credits_for_skipped_reward` is unconditionally `true` for non-Tower epochs whenever the vote account earned any credits.

### Finding Description
Because Alpenglow rewards are calculated per-epoch from the *latest* vote-account credit entry rather than as a cumulative running balance, any epoch whose reward rounds down to zero for a given delegator is permanently lost: there is no later "catch-up" redemption, since `credits_observed` has already been moved past that period. This is structurally identical to the reported `rewardsPerToken_.accumulated` staying at zero while `rewardsPerToken_.lastUpdated` keeps advancing — the accounting "clock" (`credits_observed`) advances even though the reward accumulator (`ag_points`) computed zero.

### Impact Explanation
Small-stake delegators (as low as the 1 SOL minimum delegation) to validators with large total delegated stake systematically and silently receive zero rewards for affected epochs, with no mechanism to recover the truncated amount later. This is a misattribution of intended inflation rewards — lamports allocated to a specific stake account's share are computed as due but never paid to anyone, while the account's reward-eligibility bookkeeping (`credits_observed`) is advanced as if it had been paid. This occurs through the ordinary, unprivileged stake delegation and epoch-reward-distribution path, not through any validator/operator-privileged action.

### Likelihood Explanation
No attacker action is required — the same natural conditions cited in the original report apply: a delegator's stake being a very small fraction of a vote account's total delegated stake relative to that vote account's per-epoch earned lamports causes deterministic truncation on every affected epoch. The larger a validator's total stake and the smaller an individual delegation, the more likely and more persistent this becomes.

### Recommendation
Rework `calculate_alpenglow_points` to avoid premature per-stake-account division: either scale `earned_credits`/`stake_amount` up (fixed-point, mirroring the `1e18` scale-up in the original ERC20 report's suggested mitigation) before dividing by `total_stake`, or defer the division until rewards are aggregated across all stake accounts for a vote account (as done for Tower's `PointValue::points`), so that rounding error is bounded to at most one lamport in total rather than being independently truncated to zero for every small-stake delegator.

### Proof of Concept
1. Delegate the minimum stake (1 SOL / 1e9 lamports, per `stake_utils::get_minimum_delegation`) to a validator whose total Alpenglow-delegated stake and per-epoch vote-account earnings make `earned_credits * stake_amount < total_stake` in `calculate_alpenglow_points` (`runtime/src/inflation_rewards/points.rs:300`).
2. Observe that `earned_points` computes to `0` for that stake account each epoch.
3. In `calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs:278-285`), `ag_points == 0` triggers `skip_reward(SkippedReason::ZeroPoints)`, which nonetheless returns `skipped_reward()` because `advance_credits_for_skipped_reward` is true (vote account credits changed) — advancing `new_credits_observed`.
4. `redeem_stake_rewards` (`runtime/src/inflation_rewards/mod.rs:139`) writes this new `credits_observed` back to the stake account with `staker_rewards = 0`.
5. Repeat over subsequent epochs: the delegator never accumulates any reward for the affected epochs, and there is no mechanism to retroactively redeem the truncated amounts since Alpenglow rewards are calculated per-epoch from the latest credit entry, not cumulatively.
