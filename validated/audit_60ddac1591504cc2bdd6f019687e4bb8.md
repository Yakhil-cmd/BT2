### Title
Membership webhook signed by org-x mutates a Team bound to org-y - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates the request bytes against the organization named in the payload (`repository_owner`), but `MembershipHandler#find_or_create_team!` looks up the `Team` purely by `github_id`, never checking that the found team's `organization` matches the org that signed the request. An attacker who controls a GitHub organization (and thus its webhook secret) can send a validly-signed `membership` event whose `team.id` collides with a real team belonging to a different, sensitive organization, causing `team.add_member` to grant the attacker membership in that other org's team.

### Finding Description
The broken binding: `organization whose webhook_secret verified request bytes (repository_owner == org-x)` must equal `team.organization` (`org-y`) for the mutation to be authorized — it does not.

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the HMAC using `Shipit.github(organization: repository_owner)`'s secret [2](#0-1) . For a `membership` event there is no `repository` key, so `repository_owner` resolves to `params['organization']['login']`, i.e. org-x — the attacker's own organization, whose secret they legitimately possess.
- `MembershipHandler#process` calls `find_or_create_team!`, then `team.add_member(member)` for action `added` [3](#0-2) .
- `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [4](#0-3) . The `organization=` assignment only runs inside the block passed to `find_or_create_by!`, which Rails only executes on **create**, not when an existing record with `github_id` = N is found. So if a `Team` row already exists with `github_id` N and `organization` = "org-y", the lookup returns that record untouched, regardless of the signing organization.
- `Team#add_member` simply appends the member to `members` [5](#0-4) , with no re-check of which organization signed the webhook.

Exploit flow: attacker owns org-x with its own valid `webhook_secret`. They configure/send a `membership` webhook to `POST /webhooks` with `X-Github-Event: membership`, `organization.login = "org-x"`, `team.id = N` (the real github team ID of a team already bound to `org-y` in Shipit's DB), `member.login = attacker's own GitHub login`, `action = "added"`. The signature is computed and verified correctly against org-x's secret (`verify_signature` only checks org-x, since that's what `repository_owner` resolves to). `MembershipHandler` then finds the pre-existing org-y team by `github_id` and adds the attacker as a member of it.

None of the listed guards catch this: `verify_signature` authenticates only that org-x sent bytes for org-x, never that the payload's `team.id` belongs to org-x; `drop_unhandled_event`/`ExplicitParameters` schema only check event type and payload shape, not cross-org ownership; `Team.find_or_create_by!` is keyed solely on the GitHub-global `github_id`, which is attacker-influenceable content inside a payload authenticated by a different, unrelated organization's secret.

### Impact Explanation
The attacker becomes a member of a `Shipit::Team` bound to org-y, an organization they never authenticated against. If that team is used (directly or via `Shipit.github_teams`/`User#authorized?`/`require_permission!`) to gate deploy, rollback, or stack-management authorization for org-y's stacks, the attacker gains that authorization — enabling unauthorized deploys/rollbacks on a repository/organization they do not control. This is a cross-tenant authorization escalation: a payload authenticated by org-x's secret mutates state belonging to org-y. Repeatable for any team github_id known/guessable by the attacker (team IDs are visible via GitHub's API/UI for teams the attacker can see, or via reconnaissance), and repeatable against any number of teams across tenants.

### Likelihood Explanation
Preconditions: attacker must own/control at least one GitHub organization (trivial, orgs are free to create) so they legitimately possess a valid `webhook_secret` for org-x, and Shipit's `Team` table must already contain a team with `github_id` = N for the target org-y (created by prior legitimate `membership` webhook traffic — the typical steady state for any org using Shipit). The attacker only needs to know or guess a real team's numeric GitHub `github_id` for org-y — these are often discoverable (e.g., via GitHub API for teams within the attacker's visibility, or brute-forced). Attacker cost is a single crafted HTTP POST with a valid signature they can legitimately compute. No Shipit credentials, session, or GitHub App private key are needed.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found team's `organization` matches `params.organization.login` before mutating membership (e.g., `Team.find_by(github_id: ..., organization: params.organization.login)` for lookup, and raise/no-op on organization mismatch instead of silently reusing a cross-org record). Additionally, `WebhooksController#verify_signature` should not solely trust `params.dig('organization','login')` as the sole authorization scope for handlers that mutate org-scoped resources — handlers should independently assert that any org-scoped record they touch belongs to the verified organization.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Seed `Shipit::Team.create!(github_id: 42, organization: 'org-y', name: 'sensitive-team', slug: 'sensitive-team', api_url: 'https://api.github.com/teams/42')`.
2. Configure `Shipit.github(organization: 'org-x')` with a known test secret (as existing fixtures do for org-x).
3. Build a `membership` payload: `{ action: 'added', team: { id: 42, name: 'sensitive-team', slug: 'sensitive-team', url: '...' }, organization: { login: 'org-x' }, member: { login: 'attacker' } }`.
4. Compute `X-Hub-Signature` using org-x's secret and POST to `/webhooks` with `X-Github-Event: membership`.
5. Assert response is `200 OK` (signature verified for org-x).
6. Assert `Shipit::Team.find_by(github_id: 42).organization == 'org-y'` (unchanged — binding equality `org-x == org-y` is false).
7. Assert `Shipit::Team.find_by(github_id: 42).members.map(&:login)` now includes `'attacker'`, proving org-y's team was mutated by a payload authenticated only against org-x's secret.
