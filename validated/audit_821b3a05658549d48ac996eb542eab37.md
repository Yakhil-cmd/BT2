### Title
Forged `status` webhook lets any onboarded GitHub organization mark commits in an unrelated stack/repo as CI-green, bypassing deploy gating - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using the organization identified by `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) , but the event handlers act on completely different, attacker-controlled fields of the same unsigned JSON body rather than on the value that was actually verified.

### Finding Description
The equality that should hold is:

`organization whose webhook_secret authenticated the request == organization that owns the entity the handler mutates`

`verify_signature` picks the HMAC key using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')` [2](#0-1) . Everything else in the JSON body, including `repository.full_name` and any commit `sha`, is attacker-controlled and is never covered by this check beyond the raw HMAC of the whole body — an attacker only needs to know the `webhook_secret` for *their own* onboarded organization (Shipit supports multiple organizations, each with an independent `webhook_secret`, see `config/secrets.development.shopify.yml`) to produce a validly-signed request whose other fields point at a totally different organization/repository.

`Shipit::Webhooks::Handlers::StatusHandler#process` is the most severe instance of this: it resolves the target purely by commit SHA, with no scoping to the repository/organization that authenticated the request at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit.where(sha: ...)` is a global, unscoped lookup across all stacks/organizations in the Shipit instance [4](#0-3) . `create_status_from_github!` then records the forged state directly into `commit.statuses`, and that state feeds `Commit#deployable?`, which is exactly the gate used to decide if a commit can be deployed:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [5](#0-4) 

The other default handlers share the same weakness in a milder form: `Handler#stacks`/`#repository_name` derive the target repository from `payload.dig('repository', 'full_name')` [6](#0-5) , a field never cross-checked against the `repository.owner.login` used for signature verification.

### Impact Explanation
An attacker who legitimately controls a GitHub organization onboarded to a shared Shipit instance (and therefore legitimately knows only *their own* org's `webhook_secret`) can forge a `status` webhook whose `sha` matches a commit belonging to a *different* organization's stack, and set `state: "success"`. Since `Commit#deployable?` relies on `success?` derived from these forged statuses, this can flip a commit that never actually passed CI in the victim's real GitHub repo into a deployable state in Shipit, enabling an unauthorized deploy of that commit for a repository/organization the attacker has no legitimate access to. This is a cross-organization/cross-repository write achieved purely through the low-privilege credential the attacker is entitled to (their own org's webhook secret), which the rules explicitly recognize as an in-scope analog binding ("an organization that authenticated versus the repository that is written").

### Likelihood Explanation
Exploitation requires: (1) the attacker's own organization being configured in the Shipit multi-tenant `github` config (a legitimate, low-privilege setup already supported and documented), and (2) knowledge of a target commit SHA in the victim stack, which is generally discoverable since these SHAs originate from the victim's (often public) GitHub repository and are also visible via Shipit's own UI/API for that stack (`Commit#sha`). No access to the victim's webhook secret, GitHub token, or Shipit session is needed. The `StatusHandler` has zero scoping logic, making this the most directly reachable and lowest-effort path.

### Recommendation
- In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, resolve and pass down the authenticated organization, and require every handler that mutates a `Commit`/`Stack` to verify that the target's `repository.owner` (or `stack.repository.owner`) matches the organization whose `webhook_secret` verified the request, rejecting the event otherwise.
- Specifically fix `StatusHandler#process` to scope the `Commit` lookup by `stack`/`repository`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, rather than a global `Commit.where(sha:)`.
- Consider deriving `repository_owner` and the handler's repository resolution from the same single, validated field, and reject payloads where `repository.full_name`'s owner segment does not match `repository.owner.login`.

### Proof of Concept
1. Attacker's organization `evil-org` is a legitimately configured Shipit tenant with its own `webhook_secret`, `S_evil`.
2. Attacker identifies a real commit SHA `deadbeef...` tracked by a victim stack belonging to `victim-org/victim-repo` (visible on GitHub or via Shipit's public commit views).
3. Attacker crafts a `status` event payload:
```json
{
  "repository": {"owner": {"login": "evil-org"}},
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_evil, body)` using their own known `S_evil`, and sets `X-Github-Event: status`.
5. `verify_signature` looks up `repository_owner == "evil-org"`, fetches `evil-org`'s `webhook_secret`, and the signature validates successfully [7](#0-6) .
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — unscoped — finds the victim's commit, and calls `create_status_from_github!`, recording a fabricated "success" status against the victim's commit [3](#0-2) .
7. If that commit's other statuses/checks otherwise satisfy `deployable?`, the victim's stack can now deploy a commit whose CI status was forged by an unrelated organization.
