## Title
`"r of set"` / `"weighted and"` Address Definitions Do Not Enforce Uniqueness of Set Members, Allowing Threshold Bypass - (File: `definition.js`)

## Summary
Ocore's `Definition.validateDefinition()` and `Definition.validateAuthentifiers()` implement threshold spending conditions (`"r of set"` and `"weighted and"`) that count how many members of a `set` array are satisfied and compare that count to a `required` value. Neither function checks whether the elements of `set` are distinct. This is the same bug class as the reported TSS issue: an array of "participants" (here, sub-conditions/co-signers in a multisig-like construct) is used to enforce a threshold without verifying uniqueness, so a single key can be listed multiple times and silently obtain more "voting power" than the threshold was intended to grant.

## Finding Description
`"r of set"` is validated in `evaluate()` inside `validateDefinition` at [1](#0-0) . It only checks `args.required`, `args.set` is an array, has ≥2 options, and `required <= set.length` — it never checks that the elements of `args.set` are distinct sub-definitions.

At authentication time, `validateAuthentifiers()`'s `evaluate()` independently evaluates each `set` element at its own path (`path+'.'+index`) and simply counts how many evaluate true against `args.required`: [2](#0-1) .

The same lack of uniqueness checking exists for `"weighted and"`, both at definition-validation time [3](#0-2)  and at authentication time [4](#0-3) .

Because each `set` member is assigned its own independent authentifier path (`r.0`, `r.1`, …), a single private key can satisfy multiple "distinct" slots of the threshold simply by being referenced (directly via `["sig", {pubkey: X}]` or indirectly via `["address", addr]`) more than once in `set`, and signing at each of the duplicated paths. This is structurally identical to the reported bug: the array element that is supposed to represent one independent participant is not checked for uniqueness, so one actor can occupy multiple slots and inflate their effective share of the threshold.

This mirrors the exact remediation the external report describes for `tss-lib` player arrays — verify uniqueness of each participant during initialization — except here the "players" are entries of an on-chain address/AA spending-condition definition.

## Impact Explanation
Address definitions in ocore are the trust root for shared/multisig addresses (see `wallet_defined_by_addresses.js`, `wallet_defined_by_keys.js` `createMultisigWallet`, which builds exactly `["r of set", {required: N, set: [...]}]` templates [5](#0-4) ). Co-signers agree to fund a shared address believing that spending requires cooperation of `required` distinct parties out of `set.length`. If the address (or one dishonest co-signer who controls the definition composition) duplicates their own key/sub-address within `set`, that party alone can satisfy `required` by signing under multiple duplicated paths, without the cooperation of the other, distinct co-signers. This directly enables unauthorized spending from funds that other participants believe are protected by a genuine N-of-M threshold — a concrete loss-of-funds/unauthorized-spending scenario reachable by any unprivileged address/AA definition author.

## Likelihood Explanation
Any unprivileged unit poster can construct and register an address definition (or asset spending condition attached to a self-issued asset, or an AA-controlled address) containing a `"r of set"`/`"weighted and"` clause with duplicated set members; `validateDefinition` will accept it since it never checks for duplicates. Convincing counterparties to trust in an apparent "2-of-3" security guarantee (e.g., in a shared wallet flow via `wallet_defined_by_addresses.js`) requires only social engineering, not any privileged network position, making this fully reachable from the threat model in scope (address definitions/authentifiers).

## Recommendation
In `validateDefinition()`'s handling of `"r of set"` and `"weighted and"` (definition.js, evaluate cases at lines 147 and 187), reject definitions where two or more elements of `set` are structurally identical (e.g., by comparing `JSON.stringify`/canonical hash of each sub-definition, or specifically disallowing duplicate `["sig", {pubkey}]` / `["address", addr]` leaves within the same set), analogous to how `checkAttestorList` and `validateWitnesses` already enforce sorted/unique member lists elsewhere in the codebase [6](#0-5) [7](#0-6) .

## Proof of Concept
1. Attacker who controls key `A` and wants a 2-of-3-looking address that they can spend alone builds:
```
["r of set", {
  required: 2,
  set: [
    ["sig", {pubkey: A}],
    ["sig", {pubkey: A}],   // duplicate of the same key
    ["sig", {pubkey: B}]
  ]
}]
```
2. `validateDefinition` accepts this (lines 147-185 only check array length/required bound, not uniqueness).
3. Co-signer `B` is invited into what looks like a genuine 2-of-3 shared address (per `createMultisigWallet` flow in `wallet_defined_by_keys.js`) and funds it, believing spending requires both `A` and `B` (or any 2 of 3 distinct keys).
4. To spend, `A` signs the unit twice, supplying identical/independent valid signatures at authentifier paths `r.0` and `r.1`. `validateAuthentifiers`'s `"r of set"` handler (lines 692-711) counts 2 satisfied set members (both attributable to `A`) and returns `count >= args.required` = true, authorizing the spend without `B`'s cooperation.

#### Analog Note
This maps to the report's bug class: an array meant to represent distinct independent participants (`players` in tss-lib / `set` members in ocore's `"r of set"`) is used to compute a threshold without verifying that each entry is unique, letting one actor occupy multiple slots and exceed the intended limit of authority.
