### Title
AA bounce logic forfeits all received assets (including bytes) when a single asset's amount is below its configured bounce fee - (File: aa_composer.js)

### Summary
The Sherlock report describes a class of bug where a protocol accepts a deposit of a token/asset into a contract but the corresponding return/redeem path is disabled or broken, permanently locking user funds inside the contract. The closest reachable analog in `ocore` is in the Autonomous Agent (AA) trigger-bounce mechanism in `aa_composer.js`, where an AA trigger sender's funds sent alongside multiple assets can become permanently stuck at the AA address because a failure in refunding just one asset aborts the refund of every other asset (including bytes) that was otherwise fully refundable.

### Finding Description
When an AA response fails (throws an error or the AA logic decides to reject the trigger), `bounce()` is invoked to try to refund the trigger sender [1](#0-0) . The refund attempt iterates over every asset the trigger sent to the AA and computes `fee = bounce_fees[asset] || 0` and `bounced_amount = amount - fee`, building one `payment` message per asset for the leftover amount [2](#0-1) :
```
var messages = [];
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee > amount)
        return finish(null);
    if (fee === amount)
        continue;
    var bounced_amount = amount - fee;
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
if (messages.length === 0)
    return finish(null);
sendUnit(messages);
```
If **any single asset** sent in the trigger has `amount < bounce_fees[asset]`, the function immediately returns `finish(null)` — aborting the whole loop — instead of simply skipping the refund for that one under-funded asset. This means bytes and any other asset(s) that were fully sufficient to be refunded (base bytes bounce fee check already passed at line 928 `if ((trigger.outputs.base || 0) < bounce_fees.base) return finish(null);`) are also silently forfeited and never sent back, because the loop terminates early on encountering the problematic asset.

This directly contradicts the documented intent elsewhere in the same file, where the *pre-check* before executing the AA explicitly states insufficient asset for its bounce fee should be handled by "ignoring silently" (i.e., not blocking other refunds) [3](#0-2) :
```
for (var asset in trigger.outputs) { // if not enough asset received to pay for bounce fees, ignore silently
    if (bounce_fees[asset] && trigger.outputs[asset] < bounce_fees[asset]) {
        return bounce('received ' + asset + ' is not enough to cover bounce fees');
    }
}
```
That check itself calls `bounce()`, which then re-executes the very same faulty asset-iteration logic and aborts the entire refund instead of ignoring just the deficient asset.

Since `finish(null)` sends no response unit, the trigger's coins (which were already recorded as spent to the AA address by the trigger unit itself, and already credited into the AA's `aa_balances` via `updateInitialAABalances`) remain permanently owned by the AA address [4](#0-3) . Unless the AA's own oscript logic happens to have another code path that can access and forward those exact funds, an ordinary trigger sender has no way to reclaim bytes/assets that were fully eligible for a bounce refund.

### Impact Explanation
This is a real, unauthorized-style loss/freezing of user funds reachable by any unprivileged AA trigger sender: any user who sends a payment with multiple assets (e.g., bytes + a token) to any AA that defines per-asset `bounce_fees`, and where the trigger causes a bounce (error condition in the AA), can permanently lose bytes and/or other assets that were otherwise fully sufficient to be refunded, simply because one of the other assets sent didn't cover its bounce fee. Given AAs are widely used for exchanges, and DeFi-style contracts (e.g., accepting arbitrary token deposits alongside bytes), this is a systemic freezing-of-funds bug matching the class of the reported issue (funds deposited into a contract without a working path back out).

### Likelihood Explanation
Likelihood is dependent on AA authors defining `bounce_fees` for more than one asset and users' triggers accidentally under-funding one of the assets relative to its configured fee while sending sufficient bytes/other assets. This is a plausible and common scenario for AAs handling multi-asset triggers (e.g., swap/DEX-style AAs), and requires no special privilege — any user composing a payment unit that triggers the AA can hit this path.

### Recommendation
In the `bounce()` loop in `aa_composer.js`, do not abort the entire refund when a single asset's `amount < fee`. Instead, `continue` to skip only that asset's refund message (consistent with the "ignore silently" comment used elsewhere) and still send back all other assets (including bytes) that are fully refundable via `sendUnit(messages)`.

### Proof of Concept
1. Deploy an AA with `bounce_fees: { base: 10000, asset1: 5000 }`.
2. Send a trigger unit containing `trigger.outputs.base = 20000` (sufficient to cover `bounce_fees.base`) and `trigger.outputs.asset1 = 3000` (insufficient to cover `bounce_fees.asset1 = 5000`).
3. Cause the AA to bounce (e.g., by having its oscript logic call `bounce(...)` or throw an error during evaluation).
4. In `bounce()` at [5](#0-4) , the pre-check at line 928 passes (base is sufficient), the loop reaches `asset1`, finds `fee (5000) > amount (3000)`, and calls `return finish(null)` — aborting the loop before the `base` refund message (which was fully eligible) is added to `messages`.
5. Result: no response unit is sent, `messages` never includes the base refund, and the sender's 20000 bytes (fully eligible for refund) plus the 3000 of `asset1` remain permanently credited to the AA's `aa_balances` and are unrecoverable by the trigger sender.
