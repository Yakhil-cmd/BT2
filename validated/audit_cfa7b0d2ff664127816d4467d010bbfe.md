### Title
Signature Verified Against One Organization's Secret While Handlers Act on a Different Organization's Repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The webhook signature verification binds trust to the GitHub organization named in `repository.owner.login` (or `organization.login`), which selects the per-organization `webhook_secret` used to validate the HMAC signature. However, every event handler that actually mutates state (`PushHandler`, status/check-suite handlers, pull-request handlers, etc.) resolves its target `Stack`/`Repository` independently, using only `repository.full_name` from the same JSON body. Because the field that authorizes the request (`repository.owner.login`) and the field that is acted upon (`repository.full_name`) are never checked for consistency, a party who legitimately knows the `webhook_secret` for *any* organization configured in a multi-tenant Shipit instance can forge a validly-signed payload whose `repository.full_name` points at a stack belonging to a *different* organization, causing Shipit to write state for a repository it never authenticated against.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/secret to validate against solely from the requester-supplied JSON body: [1](#0-0) [2](#0-1) 

`Shipit::GitHubApp#verify_webhook_signature` then simply HMACs the raw body with that organization's own `webhook_secret`: [3](#0-2) 

Shipit explicitly supports configuring a distinct `webhook_secret` per organization/tenant in a single instance: [4](#0-3) 

Once the signature check passes, every handler resolves the actual `Stack`s to operate on purely from `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used above: [5](#0-4) [6](#0-5) 

`PushHandler`, for example, triggers a sync for whatever stacks match `repository.full_name`: [7](#0-6) 

The `status` handler creates a `Status` record (state/description/target_url/context all attacker-controlled) on the commit resolved from the same untrusted `repository.full_name`/`sha`, as exercised by the existing test: [8](#0-7) 

This is structurally identical to the `Vault.adjustTicketInfo` bug: the counter/condition that is supposed to gate a sensitive state transition (`trader.startEpoch > _epochOfClosure`, satisfiable by unrelated past closures) is decoupled from the closure that actually needs to be adjusted. Here, the condition that gates the sensitive write (signature check keyed to `repository.owner.login`) is decoupled from the repository that is actually written (`repository.full_name`), letting an attacker satisfy the "authorization" using their own organization's binding while the write lands on someone else's.

### Impact Explanation
An attacker who is a legitimate operator of one organization/tenant registered in a multi-org Shipit deployment (and therefore knows that organization's `webhook_secret`) can sign an arbitrary JSON payload with their own secret while setting `repository.full_name` (and `sha`) to reference a stack under an unrelated organization. Via the `status` handler this injects forged commit statuses (e.g. `state: success`) for a victim stack's commit; if that status is one of the stack's `required_statuses`, it can make an otherwise-unqualified commit `deployable?` and trigger an unauthorized/automatic deploy under continuous deployment — matching the "Critical: unauthorized deploy" impact bucket. `PushHandler` similarly lets the attacker force `sync_github` calls against a victim stack. This breaks the trust binding "organization that authenticated == repository that is written," which is explicitly listed as an acceptable analog boundary.

### Likelihood Explanation
Requires only the ability to know one tenant's `webhook_secret` in a Shipit deployment configured for multiple GitHub organizations (an explicitly supported and documented configuration, see `secrets_double_github_app.yml` / `docs/setup.md`), and the ability to send an arbitrary HTTP POST to `/webhooks` with a correctly-computed `X-Hub-Signature` — no GitHub App private key, session, or `ApiClient` token is needed. This is a realistic scenario for any Shipit instance serving more than one organization/team, each with its own GitHub App and webhook secret.

### Recommendation
After verifying the signature, re-derive the organization from the actual `repository.full_name` (or `Repository#owner`) that handlers will act on, and require it to match the `repository.owner.login`/`organization.login` used to select the verifying secret; reject the request otherwise. Alternatively, verify the signature using the `webhook_secret` associated with the `Repository` record resolved from `full_name`, not from an independently-controlled field in the same untrusted payload.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgOne` (attacker-controlled) and `OrgTwo` (victim), each with its own GitHub App and `webhook_secret`, per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com",
  "repository": { "full_name": "OrgTwo/victim-repo", "owner": { "login": "OrgOne" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `OrgOne`'s known `webhook_secret` over the raw body.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `OrgOne` [2](#0-1)  and validates successfully against `OrgOne`'s secret.
5. `StatusHandler` (invoked via `Shipit::Webhooks.for_event(event)`) resolves the target commit/stack via `repository.full_name` = `OrgTwo/victim-repo` [5](#0-4)  and creates a forged `success` status on the victim's commit, as demonstrated by the existing passing test for this code path.
6. If `ci/required-check` was a missing/failing required status blocking deploy, the victim stack's commit becomes `deployable?`, and with continuous deployment enabled, an unauthorized deploy is triggered for `OrgTwo/victim-repo` using credentials the attacker never had access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
