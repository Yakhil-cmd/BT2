### Title
Webhook signature is verified against `repository.owner.login`, but events are applied against `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to verify an inbound webhook's HMAC against using `repository_owner`, a value read directly from the untrusted JSON payload. `Handler#stacks`/`#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. to decide which `Stack`/`Commit` to mutate, reads a *different* payload field (`repository.full_name`). Because these two fields are never cross-validated, a party who can produce a validly-signed webhook for one configured GitHub organization can forge the `repository.full_name` field to target a stack belonging to a completely different organization configured in the same Shipit instance, in a multi-org setup (`docs/setup.md` "Using Multiple Github Applications").

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The HMAC secret used to authenticate the request body is selected from the *body itself*, via `repository.owner.login`. This binds "which organization's `webhook_secret` is used to verify" to a field fully controlled by whoever is crafting the HTTP request body.

Separately, all event handlers determine *which* `Stack`/`Repository`/`Commit` the event applies to using a different field, `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` uses `stacks` (i.e. `repository.full_name`) to call `stack.sync_github` for every non-archived stack on the matching branch: [4](#0-3)  `StatusHandler#process` uses `Commit.where(sha: params.sha)` (no repository scoping at all) to attach arbitrary CI status to any commit sharing that SHA across the whole instance: [5](#0-4) 

There is no code path anywhere that checks `repository.owner.login == repository.full_name.split('/').first` (or equivalent) before dispatching the event. The equality that the trust boundary is supposed to enforce - "organization whose secret authenticated this request" == "repository/stack the request is allowed to mutate" - is never checked.

In a single-organization deployment this is not exploitable because only one `webhook_secret` exists and every repository is implicitly scoped to it. It becomes exploitable specifically in the documented multi-organization configuration [6](#0-5) , where distinct GitHub organizations (potentially controlled by mutually untrusting parties, e.g. different customers/teams onboarded to a shared Shipit instance) each have their own `webhook_secret` configured in `Shipit.github(organization:)`.

### Impact Explanation
An attacker who administers (or is a maintainer/owner of) one GitHub organization/App installation that is configured in Shipit's `github:` multi-org secrets, and therefore legitimately knows that organization's `webhook_secret` (it's a value the org's own admin sets when creating the GitHub App, or obtains from a real, GitHub-delivered webhook they can replay/redeliver), can:
- Sign an arbitrary JSON body with their own org's `webhook_secret`.
- Set `repository.owner.login` to their own org's login (so `Shipit.github(organization: repository_owner)` fetches the secret they know, and `verify_webhook_signature` succeeds).
- Set `repository.full_name` to `"victim-org/victim-repo"` to target any other organization's stack managed by the same Shipit instance.

With this they can, for example: trigger `stack.sync_github` for a victim stack via a forged `push` event, or inject a fake commit `status`/`check_suite` outcome onto a victim's commit via `StatusHandler`/`CheckSuiteHandler` (no repository scoping check at all on the commit lookup), potentially influencing which commits become "deployable" and get shipped by the merge-queue / continuous-deployment pipeline for a repository they do not own. This crosses the "cross-repository writes" / "unauthorized deploy" bar (Critical), since it lets an attacker who is authorized for org A silently corrupt or manipulate deploy-readiness state for org B's repository, without any repository write access or Shipit session on org B's side.

### Likelihood Explanation
Requires the target Shipit instance to be configured for multiple GitHub organizations (a supported and documented configuration) and requires the attacker to control at least one of those organizations' GitHub App installations - a bar far lower than compromising the victim's org or obtaining `GITHUB_TOKEN`/`api_clients_secret`. No Shipit session, `ApiClient` token, or victim-side credential is needed; only the ability to author a legitimate GitHub App/webhook_secret for one tenant of the shared instance.

### Recommendation
After signature verification succeeds, cross-check that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` (and, ideally, resolve the target `Repository`/`Stack` strictly by full name scoped under that verified organization) before dispatching to any handler. Reject the webhook (422) if they disagree. `StatusHandler` and other commit/SHA based handlers should additionally scope commit lookups to repositories owned by the verified organization rather than performing an unscoped `Commit.where(sha:)`.

### Proof of Concept
Given a Shipit instance configured with two organizations, `AttackerOrg` (webhook_secret known to the attacker because they administer that GitHub App installation) and `VictimOrg` (hosting stack `VictimOrg/victim-repo`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of body using AttackerOrg's known webhook_secret>

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-already-known-to-exist-on-victim-repo>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```

`verify_signature` computes `Shipit.github(organization: "AttackerOrg")` and validates the signature successfully (attacker knows this secret). `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `sync_github` on that stack — an event nominally scoped/authenticated for `AttackerOrg` mutates `VictimOrg`'s stack state.

Note: I could not execute this against a live instance; the analysis is based on static code review of `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/*.rb`, and confirmation would require a running multi-org Shipit deployment to fully validate handler-side effects (e.g. `sync_github`, `create_status_from_github!`) end-to-end.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
