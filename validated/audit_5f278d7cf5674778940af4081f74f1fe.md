### Title
Fee-on-Transfer ERC20 Token Causes Bridge Insolvency via Unverified Received Amount — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `BridgeTransferERC20.onERC20Received` both accept a caller-supplied `_value` and emit a `RequestValueTransfer` event for that exact amount without verifying the actual token balance increase in the bridge contract. When a registered ERC20 token charges a fee on transfer, the bridge receives fewer tokens than `_value + _feeLimit`, yet the counterpart bridge is instructed to release the full `_value` to the recipient. Repeated transfers drain the bridge's token reserves, causing insolvency for all users of that token pair.

---

### Finding Description

**2-step path — `requestERC20Transfer`:**

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

`safeTransferFrom` is called for `_value + _feeLimit`, but no balance snapshot is taken before or after the call. If the token deducts a fee during transfer, the bridge receives `(_value + _feeLimit) × (1 − fee_rate)`. The function then calls `_requestERC20Transfer` with the original, unverified `_value`. [1](#0-0) 

**1-step path — `onERC20Received`:**

```solidity
// BridgeTransferERC20.sol L111-121
function onERC20Received(address _from, address _to, uint256 _value, uint256 _feeLimit, bytes memory _extraData) public {
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
```

`onERC20Received` is `public` with no access control beyond `onlyRegisteredToken(msg.sender)` inside `_requestERC20Transfer`. The token contract calls `transfer(bridge, _amount + _feeLimit)` first, then calls `onERC20Received` with the original `_amount`. If the token's own `transfer` deducts a fee, the bridge holds less than `_amount + _feeLimit`, but the event is emitted for the full `_amount`. [2](#0-1) 

**`_requestERC20Transfer` — no balance check:**

```solidity
// BridgeTransferERC20.sol L76-108
function _requestERC20Transfer(...) internal onlyRegisteredToken(_tokenAddress) onlyUnlockedToken(_tokenAddress) {
    ...
    uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
    if (modeMintBurn) { ERC20Burnable(_tokenAddress).burn(_value); }
    emit RequestValueTransfer(..., _value, ...);
    requestNonce++;
}
```

No `balanceOf` snapshot is taken before or after the incoming transfer. The function trusts `_value` entirely. [3](#0-2) 

**`_payERC20FeeAndRefundChange` — spends from bridge balance:**

```solidity
// BridgeFee.sol L68-88
function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
    ...
    IERC20(_token).safeTransfer(feeReceiver, fee);
    ...
    IERC20(_token).safeTransfer(from, feeRefund);
    ...
}
```

This function spends tokens from the bridge's balance. If the bridge received fewer tokens than expected due to a transfer fee, these outgoing transfers further reduce the bridge's actual holdings below what the event claims. [4](#0-3) 

**Counterpart bridge releases full `_value`:**

The Go relay layer reads the `RequestValueTransfer` event and calls `HandleERC20Transfer` on the counterpart bridge with the event's `valueOrTokenId` (the full `_value`):

```go
// node/sc/bridge_manager.go L338-343
case ERC20:
    handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, ...)
``` [5](#0-4) 

The counterpart bridge then releases the full `_value` to the recipient:

```solidity
// BridgeTransferERC20.sol L71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [6](#0-5) 

---

### Impact Explanation

**Lock/unlock mode (`modeMintBurn = false`):** The source-chain bridge holds tokens as collateral. Each transfer with a fee-on-transfer token leaves the bridge short by `(_value + _feeLimit) × fee_rate` tokens. The counterpart bridge releases the full `_value`. After N transfers, the bridge's actual balance is `N × _value × (1 − fee_rate)` but it owes `N × _value`. The shortfall grows linearly until the bridge cannot fulfill withdrawals — a direct unauthorized drain of bridged assets.

**Mint/burn mode (`modeMintBurn = true`):** `_requestERC20Transfer` calls `ERC20Burnable(_tokenAddress).burn(_value)` after the fee-reduced deposit. If the bridge received less than `_value` (after fee payment), the `burn` call will revert (insufficient balance), causing the transaction to fail. However, `_payERC20FeeAndRefundChange` runs before the burn and may successfully transfer tokens to `feeReceiver` and refund to `from`, leaving the bridge in an inconsistent state if the burn then reverts. [7](#0-6) 

---

### Likelihood Explanation

- Any ERC20 token registered with the bridge that charges a transfer fee (or that is later upgraded to charge one, as USDT reserves the right to do) triggers this path.
- The bridge owner registers tokens in good faith; there is no on-chain enforcement preventing fee-on-transfer tokens from being registered.
- The trigger is a normal user calling `requestERC20Transfer` or `requestValueTransfer` on the token — no privileged access required beyond the token being registered.
- The `onlyRegisteredToken` guard is the only barrier, and it is satisfied by design for any legitimately registered token.

---

### Recommendation

1. **Balance snapshot check:** Record `balanceOf(address(this))` before and after the incoming `safeTransferFrom`, and use the delta as the actual received amount instead of the caller-supplied `_value`:

```solidity
uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
require(actualReceived >= _value.add(_feeLimit), "fee-on-transfer token not supported");
```

2. **Apply the same check in `onERC20Received`:** Verify the bridge's balance increased by at least `_value + _feeLimit` before accepting the request.

3. **Document the restriction:** Explicitly state in `registerToken` that fee-on-transfer tokens are not supported, and consider adding an on-chain check or allowlist mechanism.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` that deducts 10% on every `transfer`/`transferFrom`.
2. Register `FeeToken` with the bridge (owner action, legitimate).
3. Alice calls `requestERC20Transfer(feeToken, bob, 100, 0, "")` after approving 100 tokens.
4. Bridge calls `safeTransferFrom(alice, bridge, 100)` → bridge receives 90 (10 taken as fee).
5. `_requestERC20Transfer` emits `RequestValueTransfer(..., value=100, ...)`.
6. Go relay reads the event, calls `HandleERC20Transfer(..., value=100)` on the counterpart bridge.
7. Counterpart bridge calls `safeTransfer(bob, 100)` → Bob receives 90 (another 10% fee), but the counterpart bridge spent 100 from its reserves.
8. Source bridge holds 90 tokens but has committed to releasing 100 on the counterpart side.
9. After 10 such transfers, the counterpart bridge is insolvent: it has released 1000 tokens but only received 900 (net of fees on the counterpart side), and the source bridge holds 900 instead of 1000.

The exact corrupted value is the bridge's token balance, which decreases by `_value × fee_rate` per transfer, while the bridge's accounting (via nonces and events) records the full `_value` as settled.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
