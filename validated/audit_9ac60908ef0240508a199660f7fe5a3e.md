This confirms the multi-tenant configuration model. Now I have sufficient evidence to write up the finding.

Key facts confirmed:
- `Shipit.github(organization:)` supports multiple independent GitHub Apps per organization, each with its own `webhook_secret`, configured in `secrets.github` keyed by org login [1](#0-0) .
- `WebhooksController#verify_signature` selects which org's secret to verify the HMAC signature with, based on `repository_owner`, which is read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`) [2](#0-1) .
- Once verified, `WebhooksController#create` dispatches the raw parsed `params` (the entire attacker-authored JSON body) to handlers [3](#0-2) .
- Handlers resolve the target `Repository`/`Stack` using a *different* field from that same body: `payload.dig('repository', 'full_name')` [4](#0-3) , and identically in `PushHandler`, `MembershipHandler`, and every `PullRequest::*Handler` [5](#0-4) [6](#0-5) [7](#0-6) .
- Nothing cross-checks that `repository.owner.login` (used to pick the verifying secret) matches the owner embedded in `repository.full_name` / `organization.login` (used to act). Both fields are inside the same attacker-controlled JSON body that the attacker signs themselves with their own known secret.

### Title
Cross-organization write via webhook signature/target field mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (one `Shipit.github` config entry per GitHub organization, each with its own `webhook_secret`), `WebhooksController#verify_signature` selects which organization's secret to verify a webhook against using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the JSON body. Once verification succeeds, the entire raw body — including a completely independent `repository.full_name` field — is handed to event handlers that resolve the `Repository`/`Stack`/`Team` to act on purely from `full_name` (or `organization.login` for membership). Because the field used to select/verify the secret and the field used to select the target are never cross-checked, an org whose webhook secret is known to its own operator (as is normal — they set/received it during onboarding) can forge a payload that verifies as "from OrgA" but targets a repository/stack belonging to OrgB.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to obtain the webhook secret used for HMAC verification: [8](#0-7) [9](#0-8) 

`Shipit.github` looks up per-organization configs from `secrets.github`, each with an independently-configured `webhook_secret`, as shown by the multi-org secrets template: [1](#0-0) [10](#0-9) 

After verification succeeds, `create` parses and forwards the *entire raw body* to every registered handler for the event, unmodified: [3](#0-2) 

Handlers never re-derive or validate the organization from the field that was actually verified (`repository.owner.login`). Instead they resolve their target purely from `repository.full_name`: [4](#0-3) 

`PushHandler` uses this to trigger a GitHub sync (which can update `head_sha`/trigger a deploy pipeline) on any stack matching that repo/branch: [5](#0-4) 

`MembershipHandler` similarly trusts `organization.login` from the body to attach/detach a GitHub user from a `Team` used for authorization (`Shipit.github_teams`): [11](#0-10) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository/team being written to.** Because `repository.owner.login` (verification key selector) and `repository.full_name`/`organization.login` (mutation target) are two independently-controlled fields of the same attacker-authored JSON body, and the HMAC only proves "this exact byte string was signed by someone who knows OrgA's secret" — not "the actions inside this byte string are scoped to OrgA" — an operator of OrgA (who legitimately possesses OrgA's own `webhook_secret`, set during their own GitHub App onboarding) can freely set `repository.full_name` to `OrgB/some-repo` while keeping `repository.owner.login`/`organization.login` = `OrgA` so the signature check passes, then have the handler act on OrgB's stack/team.

### Impact Explanation
- Via `PushHandler`, an attacker can trigger `stack.sync_github` on a victim stack owned by a different organization, forcing an unauthorized sync to an attacker-chosen `expected_head_sha`, which can cascade into deploy pipeline actions on repositories the attacker does not control — matching the "unauthorized deploy" criterion.
- Via `MembershipHandler`, an attacker can add themselves (or any GitHub login) to a `Team` object that other parts of the app use for `Shipit.github_teams` authorization checks, since `Team#organization` is set purely from the forged `organization.login` and membership add/remove is unconditional — matching the "escalation into `Shipit.github_teams` authorization" criterion.
- This only manifests in the multi-tenant configuration where multiple organizations, each with a distinct, separately-known `webhook_secret`, are configured on one Shipit instance — a supported and documented configuration [10](#0-9) .

### Likelihood Explanation
Exploitability requires only knowledge of one legitimately-configured organization's own `webhook_secret` — something that org's operator necessarily has, since they configure it during their own GitHub App setup — plus the ability to send an HTTP POST to the shared `/webhooks` endpoint (unauthenticated, internet-reachable, standard GitHub webhook delivery target). No repository write access, Shipit session, or `ApiClient` token is required. The likelihood is limited to deployments explicitly using the multi-organization config style, which the engine documents and supports as a first-class feature.

### Recommendation
After `verify_signature` succeeds, do not trust unrelated fields of the payload for org/target resolution. Either:
1. Bind the verified organization to the request (e.g., store `repository_owner` used for verification) and have `Handler#repository_name`/`MembershipHandler` require that the resolved `Repository#owner` or `organization.login` match the verified organization exactly before acting, or
2. Verify against every configured organization's secret and only trust the secret that matches the org actually referenced by `full_name`, rejecting the event if `repository.owner.login` and the owner segment of `repository.full_name` diverge.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `orga` and `orgb`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` layout), and stacks tracked for both `orga/repo1` and `orgb/repo2`.
2. As the legitimate operator/owner of `orga`'s GitHub App, craft a `push` payload body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker chosen sha>",
     "repository": { "full_name": "orgb/repo2", "owner": { "login": "orga" } }
   }
   ```
3. Sign the raw body with `orga`'s known `webhook_secret` using the same HMAC-SHA1 scheme Shipit expects, and set it as `X-Hub-Signature`. Set `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` resolves `repository_owner` = `"orga"` from `repository.owner.login`, fetches `orga`'s app/secret, and the signature verifies successfully [8](#0-7) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/repo2")` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: params.after)` on `orgb`'s stack [5](#0-4)  — an unauthorized cross-organization write triggered entirely by an operator of a different, unrelated organization.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
