## Title
Webhook signature verified against the organization named in `repository.owner.login`, but the handler acts on the unrelated repository named in `repository.full_name` — cross-organization write via a single valid webhook secret - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-tenant Shipit deployments (multiple GitHub Apps/organizations configured under `secrets.github`), `WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using the `repository.owner.login` field taken from the *same untrusted request body* it is trying to authenticate, while the event handlers act on the repository identified by the unrelated `repository.full_name` field. An attacker who controls (or has learned the webhook secret of) one configured organization can craft a payload whose `repository.owner.login` points at their own org (so the signature validates) but whose `repository.full_name` points at a stack belonging to a completely different organization, causing Shipit to execute actions (git sync, commit statuses, PR handling) against a repository the attacker never authenticated for.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/secret to use purely from payload content: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization webhook secret from `secrets.github`, supporting multiple organizations in a single install: [3](#0-2) 

`GitHubApp#verify_webhook_signature` only proves the request was HMAC-signed with *that organization's* secret — it says nothing about which repository the payload actually names: [4](#0-3) 

Meanwhile every webhook `Handler` resolves the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`, not from `repository.owner.login`: [5](#0-4) 

and, for pushes, uses that repository/stack to trigger a live sync of GitHub state: [6](#0-5) 

This is exactly the bug class from the report: the check that is supposed to gate an action (`isBLSPublicKeyPartOfLSDNetwork` vs. `isBLSPublicKeyBanned`) validates a narrower/wrong condition than what is actually relied upon. Here, the signature check validates "this body was signed by organization X's secret" but the code that follows trusts a *different, unverified* field (`repository.full_name`) from that same body to select what gets written to. The binding that should hold is:

`organization whose secret validated the HMAC == organization owning the repository/stack acted upon`

but the code never enforces that `repository.owner.login` (used to pick the secret) matches the owner of `repository.full_name` (used to pick the stack).

### Impact Explanation
An attacker who knows the webhook secret for *any one* organization configured in a shared Shipit instance (e.g., because they administer that org's GitHub App installation, or because a secret leaked for one tenant) can forge a signed payload that is validated as "from Org A" but is processed as an event for a repository belonging to Org B. Depending on event type this can trigger `stack.sync_github` (push), commit status updates (`status`), check-run refreshes (`check_suite`), or PR-related state changes (`pull_request`) for a stack/repository the attacker has no legitimate relationship to — an unauthorized cross-repository/cross-organization write into another tenant's deployment pipeline, satisfying the "cross-repository writes" / "unauthorized deploy" high-impact bar.

### Likelihood Explanation
This requires a Shipit installation configured with more than one GitHub organization under `secrets.github` (the multi-org mode explicitly supported by `Shipit.github_organizations`/`github_app_config`), and requires the attacker to know one organization's webhook secret — which is plausible for any of the tenant admins in a shared install, none of whom should be trusted with other tenants' repositories. The webhook endpoint itself requires no session, `ApiClient` token, or GitHub App private key — only the raw HTTP POST and the HMAC secret for the tenant the attacker legitimately controls.

### Recommendation
After locating the repository/stack via `repository.full_name`, verify that its owning organization matches the organization whose secret validated the signature (i.e., cross-check `repository_owner` against the resolved `Repository`'s actual owner) before dispatching to any handler, rather than trusting `repository.full_name` unconditionally once *any* valid-for-some-org signature is found.

### Proof of Concept
1. Deploy Shipit with two organizations configured, e.g. `secrets.github: { orga: {...webhook_secret: S_A...}, orgb: {...webhook_secret: S_B...} }` (as exercised by `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls Org A's GitHub App installation and therefore knows `S_A`.
3. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC(S_A, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orga")`, whose `verify_webhook_signature` succeeds because the attacker signed with `S_A`.
6. `PushHandler#process` resolves `repository_name` as `"orgb/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on Org B's stack, even though the request was never signed by Org B's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
