### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit's webhook signature verification authenticates the *organization* that sent a webhook, but the `status` event handler writes commit status data keyed only on a global commit SHA, with no check that the SHA actually belongs to a repository owned by that authenticated organization. In a multi-organization Shipit deployment (the supported `github: {org1: {...}, org2: {...}}` configuration), an attacker who legitimately controls one onboarded organization can forge a passing CI status for a commit belonging to a completely different organization's stack, as long as they know (or guess) the target's commit SHA — which is public information on GitHub.

### Finding Description
Webhook authentication in `WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check against using an org name taken directly out of the untrusted payload itself (`repository.owner.login` or `organization.login`), and only verifies that the HMAC signature matches for *that* org: [1](#0-0) [2](#0-1) 

This is by design intended to support multiple GitHub Apps/organizations, each with its own secret, as documented in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`: [3](#0-2) 

Once the signature is verified against the *sender's own organization*, the payload is dispatched to handlers with no further binding back to that organization. `StatusHandler#process` looks up commits **globally by SHA only**, without any repository or organization scoping: [4](#0-3) 

By contrast, `PushHandler` at least scopes writes to stacks matching a `branch`, but still doesn't verify the sending organization owns the affected stack's repository: [5](#0-4) 

`CheckSuiteHandler` has the identical unscoped-lookup pattern (`stacks.where(branch:)` then `commits.where(sha:)`, with no repository filter tying it to the sending org): [6](#0-5) 

The equality that should hold is:
`organization that authenticated the webhook (repository_owner in payload, verified against that org's webhook_secret)` == `organization owning the repository/stack whose Commit/CheckRun row is mutated`.

In `StatusHandler`/`CheckSuiteHandler` this equality is never checked — `Commit.where(sha: params.sha)` (and `stacks.where(branch:)`) matches across **all stacks in the Shipit instance**, regardless of which organization the signature was verified for. The `repository` field required for signature verification is not the same field consulted when deciding what to write.

The pushed value written to the commit (`state`, `context`, `target_url`, `description`) is consumed by `StatusChecker` (used by `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?`) to decide whether required CI checks have passed for merging and deploying: [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate administrator of *any one* GitHub organization onboarded to a shared, multi-org Shipit instance can:
1. Discover the target stack's pending commit SHA (public on GitHub, or visible from the target's public/stack page).
2. Send a `status` (or `check_suite`) webhook, signed with their **own** organization's webhook secret (which they legitimately possess), containing that target SHA with `state: success` and the exact `context` name the target's `shipit.yml` requires (`ci.require` / `merge.require`).
3. `WebhooksController#verify_signature` succeeds because the org derived from the payload matches the attacker's own valid org/secret.
4. `StatusHandler#process` writes the forged "success" status onto the victim's `Commit` row anyway, since the lookup is not scoped to the attacker's repositories.
5. This can flip `StatusChecker#success?` to true for the victim's commit, unblocking `merge_request.merge!` or a stack's deploy checklist for `ci.require`d checks — enabling an unauthorized merge/deploy on a repository the attacker never had write access to.

This satisfies the Critical/High bar: cross-repository writes and an unauthorized deploy/merge, achieved purely through possessing valid credentials to an unrelated onboarded organization.

### Likelihood Explanation
This requires a Shipit instance configured for multiple GitHub organizations (explicitly documented and supported: `docs/setup.md` "Using Multiple GitHub Applications", `test/dummy/config/secrets_double_github_app.yml`). In such shared/multi-tenant deployments, this is straightforward and reliably exploitable — no race conditions, no rate-limit dependence, only knowledge of a target commit SHA (which is typically discoverable) and valid credentials for one organization's own GitHub App, which the attacker legitimately controls.

### Recommendation
In `StatusHandler`, `CheckSuiteHandler`, and any other webhook handler that mutates `Commit`/`CheckRun`/`Stack` state by SHA/branch only, scope the lookup to stacks whose `Repository#owner` matches the authenticated `repository_owner` (the same value used in `WebhooksController#verify_signature`) — e.g. join through `Stack -> Repository` and filter `owner: repository_owner` before applying `sha`/`branch` filters. Alternatively, pass the authenticated organization down from the controller into every handler's `process` call and assert repository ownership before creating/updating any commit state.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `victim-org` and `attacker-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org format).
2. `victim-org/app` has a stack tracking commit `abc123...` with `ci.require: ["ci/checks"]`, and CI hasn't reported success yet, so the merge/deploy is blocked.
3. Attacker (a legitimate admin of `attacker-org`) crafts and signs (using `attacker-org`'s own `webhook_secret`) a `status` event payload:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/checks",
  "repository": {"owner": {"login": "attacker-org"}}
}
```
4. POST it to `/github/webhooks` with header `X-Github-Event: status` and a valid `X-Hub-Signature` computed with `attacker-org`'s secret.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (it is valid for that org).
6. `StatusHandler#process` executes `Commit.where(sha: "abc123...")` — matching the victim's commit regardless of org — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto the victim's commit.
7. `StatusChecker` on the victim's stack now reports `ci/checks` as passing, potentially unblocking a merge or deploy the attacker had no authorization to trigger.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

module Shipit
  module Webhooks
    module Handlers
      class CheckSuiteHandler < Handler
        params do
          requires :check_suite do
            requires :head_sha, String
            requires :head_branch, String
          end
        end
        def process
          stacks.where(branch: params.check_suite.head_branch).each do |stack|
            stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
          end
        end
      end
    end
  end
end
