### Title
On-chain system-vote counting uses live current balance instead of a per-vote/per-count snapshot, allowing voting-weight reuse across recounts - (File: main_chain.js)

### Summary
The external report flags removal of `ERC20VotesUpgradeable`, which tracks *historical* balance snapshots so voting weight can't be reused simply by moving tokens between addresses. In ocore's own on-chain governance analog — `system_vote` / `system_vote_count` messages that steer consensus-critical parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) — the vote tally in `countVotes()` [1](#0-0)  never snapshots a voter's balance at the moment each vote was cast. It always looks up the address's *live, current* stable-good balance at whatever moment counting happens [2](#0-1) .

### Finding Description
`system_votes` is an append-only log of every vote ever cast by every address, retained forever [3](#0-2) , and vote counting can be re-triggered at will by anyone posting a `system_vote_count` message, which is queued and processed at the end of the MCI [4](#0-3) [5](#0-4) .

When `countVotes()` runs, it does not use the balance the voter held at the time their `system_vote` unit was posted. Instead it queries the addresses' *current* unspent, stable-good, base-asset balance at the moment the count executes, and stores that into a temporary `voter_balances` table [6](#0-5) . This balance is then joined against the *latest* vote per address (`op_votes`/`numerical_votes`, each keyed by `address` alone) inside a rolling time window that expands until enough weighted share has "voted" [7](#0-6) [8](#0-7) [9](#0-8) .

Because there is no snapshot tying a vote's weight to the balance held *when the vote was submitted* (or to a single canonical proposal/round), an unprivileged unit poster can:
1. Cast a `system_vote` from address A while holding a large balance, establishing an entry in `system_votes`/`op_votes`/`numerical_votes` for A.
2. Freely move the same coins to address B and cast a second `system_vote` from B (a different opinion, or the same one recorded at a different time).
3. Trigger `system_vote_count` (anyone can post this message) repeatedly. Each recount re-reads whichever address currently controls the coins and counts it as "supporting" its stored (possibly stale) vote row, even though that address's vote may have been cast under completely different economic conditions, or the same underlying value has already contributed to a prior counted outcome.

Because votes are never expired or tied to a specific proposal/round with a fixed balance snapshot (unlike OpenZeppelin's `ERC20VotesUpgradeable`, which locks voting power to a specific historical block), the same set of coins can effectively be recycled to influence multiple independent vote counts over time, or be shuffled among addresses to keep "renewing" apparent support without any real, simultaneous majority ever existing. This directly parallels the reported bug class: absence of point-in-time balance snapshotting for a voting mechanism enables reuse of the same funds for double/duplicate voting influence.

### Impact Explanation
The subjects controlled by this vote-counting mechanism are consensus-critical: `op_list` (the set of order-providers used for main-chain stability) and network parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) [10](#0-9) . Manipulating `op_list` can change which units are recognized as stable, causing the network to disagree on validity/stability or altering how new units get confirmed — a direct violation of network-wide consensus safety. Manipulating fee/TPS parameters can distort economic assumptions relied on elsewhere in validation (e.g., `storage.getOversizeFee`, used in input-selection and fee calculation) [11](#0-10) , potentially enabling free-riding or fee-based denial of service.

### Likelihood Explanation
Anyone can post a `system_vote` or `system_vote_count` unit — this is not restricted to privileged operators; it's a normal application message processed for any stable unit [12](#0-11) . The only friction is the expanding time-window / minimum-share threshold, which is intended to require broad economic support but, due to the lack of a balance snapshot, can be gamed by moving/re-voting the same funds across addresses and re-triggering counts, rather than needing genuinely broad, simultaneous holder support.

### Recommendation
Introduce a fixed-point balance snapshot per vote (e.g., record the voter's confirmed balance at the `system_vote` unit's own MCI/timestamp, analogous to `ERC20Votes` checkpoints) instead of re-reading live balance at arbitrary future recount times. Alternatively, invalidate/expire a vote's counted weight once the underlying coins move, and ensure a given output/balance can contribute to at most one canonical, time-bounded voting round per subject.

### Proof of Concept
Conceptual sequence (cannot be executed without a live network, but demonstrates the reachable path):
1. Address A (holder of large balance) posts a unit with a `system_vote` message for subject `op_list`, recorded in `system_votes`/`op_votes` [13](#0-12) .
2. A posts a `system_vote_count` message; when its MCI stabilizes, `countVotes()` tallies A's then-current balance towards A's chosen OP list [14](#0-13) .
3. A transfers the same coins to address B via an ordinary payment (no restriction tying spent coins to a "locked" vote).
4. B posts a differing `system_vote` for the same subject.
5. A new `system_vote_count` message triggers another `countVotes()` run; because balance lookup is always "current," B's balance (the same economic value as A's earlier vote) is now counted again, effectively letting the same funds influence the outcome repeatedly across rounds without ever requiring simultaneous, non-overlapping ownership.

	console.log('countVotes', mci, subject, is_emergency, emergency_count_command_timestamp);

		throw Error("emergency vote count supported for op_list only, got " + subject);
	const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
	let addresses = address_rows.map(r => r.address);
	const unstable_votes = (is_emergency && mci >= constants.pemCurvesFixMci) ? getUnstableVotes(emergency_count_command_timestamp) : null;
	if (unstable_votes) {
		for (let { author_addresses } of unstable_votes) {
			for (let address of author_addresses)
				addresses.push(address);
		}
		addresses = _.uniq(addresses);
	}
	const strAddresses = addresses.map(db.escape).join(', ');
	let balances = {};

	// This correctly handles outputs whose only spending unit was propagated to final-bad
	// (leaving is_spent=1 in the DB while no good unit claims the output), which the
	// previous two-query approach (bal_rows + spent_rows) silently undercounted.
	const bal_rows = await conn.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);
	console.log('bal rows', bal_rows)

		balances[address] = balance;
	}
