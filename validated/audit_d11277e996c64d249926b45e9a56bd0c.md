## Finding

### Title
Interrupted `git reset --hard` checkout is not detected by `sanityCheckWorktree`, allowing a partially-checked-out worktree to be treated as valid and published as complete — ([File: main.go])

### Summary
`git-sync`'s sync loop bounds every sync attempt with `context.WithTimeout(context.Background(), *flSyncTimeout)` [1](#0-0) . All git commands, including the working-tree checkout performed by `configureWorktree` via `git reset --hard <hash>`, run under this same context and can be killed mid-operation when the timeout (or a large/slow checkout of attacker-supplied content) is hit [2](#0-1) . This is directly analogous to the Upkeep.sol bug: a resource budget (gas there, wall-clock/context time here) can run out in the middle of a mandatory step, yet the surrounding logic still records the operation as "good enough" and moves on, instead of treating it as failed/needing retry.

### Finding Description
The function that is supposed to catch an incomplete/interrupted checkout is `sanityCheckWorktree`, whose own doc comment admits the gap:

```go
// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
``` [3](#0-2) 

It only verifies: (1) the worktree directory isn't empty, (2) `git rev-parse HEAD` matches the expected hash, and (3) `git fsck --no-progress --connectivity-only` succeeds — none of which detect a partially-written working tree, since `git reset --hard` updates `HEAD`/the index before it finishes writing out every blob to disk.

In `SyncRepo`, this check is only invoked in the "nothing changed" fast path:

```go
if currentHash == remoteHash {
    git.log.V(3).Info("current hash is same as remote", "hash", currentHash)
    if !git.sanityCheckWorktree(ctx, currentWorktree) {
        ...
    }
}
changed := (currentHash != remoteHash) || (currentWorktree != git.worktreeFor(currentHash))
...
if changed || git.syncCount == 0 {
    ... configureWorktree(ctx, newWorktree) ...
} else {
    git.log.V(2).Info("update not required", ...)
}
``` [4](#0-3) 

Because `currentWorktree.Hash()` is derived from the worktree's directory name (which is created for the target hash before checkout completes, in `createWorktree`) rather than from verified file contents, `currentHash` already equals `remoteHash` even if the previous `configureWorktree` call was interrupted partway through `reset --hard`. If that interrupted run is followed by a run where the remote hasn't moved on, `sanityCheckWorktree` passes (HEAD matches, fsck is only a connectivity check), `changed` evaluates to `false`, and the "update not required" branch is taken — `configureWorktree` (and therefore the checkout) is never re-run. The already-published symlink (or the one published on this interrupted run before the crash, if `publishSymlink` had already fired for the prior hash) is left pointing at a permanently incomplete worktree, with no future sync attempt to repair it because the remote ref never changes to force a full re-checkout.

### Impact Explanation
This produces a persistent partial-content publication: consumers of the `--link` symlink can permanently see a worktree missing files or with truncated blobs, with no self-healing, mirroring the accepted class of "publishing wrong or partial content." Unlike a transient failure (which increments `failCount` and retries), this failure mode is silently accepted as a successful, up-to-date sync because `sanityCheckWorktree`'s checks are insufficient to detect an interrupted checkout.

### Likelihood Explanation
Triggering this requires a repo whose checkout is large/slow enough (e.g. large blobs, many submodules, or the process being killed at exactly the wrong moment via `--sync-timeout`, OOM, or SIGKILL) to interrupt `git reset --hard`/submodule update mid-flight, followed by a subsequent sync attempt at the same target ref/hash. Since `--repo`/ref content is attacker-influenced (the untrusted upstream repo drives object size and checkout time), an attacker who controls the source repository can intentionally craft content (huge files, resource-intensive smudge filters, or slow submodule fetches) to make an interrupted checkout likely within the configured `--sync-timeout`, making this a plausible, repo-content-driven denial of a *correct* sync rather than a purely operational accident.

### Recommendation
`sanityCheckWorktree` should not rely solely on `HEAD` and `fsck --connectivity-only`. Recommendations:
- Use a completion marker: after `configureWorktree` fully succeeds (including submodules), write a sentinel file into the worktree's `.git/worktrees/<hash>` metadata; `sanityCheckWorktree` should require this marker to be present before considering the worktree valid.
- Alternatively, run `git status --porcelain` (or a full `git diff --quiet HEAD`) that compares the index/working tree with the tree object of `HEAD`, which would detect files that git never got around to writing.
- On any context cancellation/error from `configureWorktree`, explicitly remove or mark the worktree unusable rather than leaving a same-named directory that a later run may misclassify as complete via directory-name-derived hash matching.

### Proof of Concept
1. Configure `git-sync` with a `--sync-timeout` short enough relative to checkout time of a large object (or push a very large blob/many submodules as the attacker-controlled upstream content).
2. Let a sync begin: `reset --soft` succeeds, `createWorktree` creates `.../<hash>` via `worktree add --no-checkout`, then `configureWorktree`'s `git reset --hard <hash>` begins writing files.
3. Have the context timeout fire (or kill git-sync) partway through the checkout — `HEAD` in the worktree is already at `<hash>`, but many files are missing/truncated on disk. This iteration returns an error and is logged as a failure [2](#0-1) .
4. On the next sync attempt (remote ref unchanged), `currentWorktree.Hash()` reports `<hash>` (matches `remoteHash`), `sanityCheckWorktree` passes (`rev-parse HEAD` matches, `fsck --connectivity-only` doesn't inspect working-tree completeness) [5](#0-4) , `changed` is `false`, and the "update not required" branch is taken, permanently skipping re-checkout [6](#0-5) .
5. The symlink continues to serve (or gets published pointing to) the incomplete worktree indefinitely.

// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}

	// Consistency-check the worktree.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, worktree.Path(), "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "worktree fsck failed", "path", worktree.Path())
		return false
	}

	return true
}
```
