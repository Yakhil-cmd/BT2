### Title
Cross-tenant Status mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository/stack scoping, unlike every other handler in the same directory (e.g. `CheckSuiteHandler`, the `PullRequest` handlers) which first resolve the payload's `repository.full_name` to a `Repository`/`stacks` scope before touching any records. This lets a verified webhook for one repository create `Status` rows on commits belonging to unrelated stacks/repositories whenever a commit sha is shared across them.

### Finding Description
The intended binding is: `{Commit rows mutated by a 'status' webhook} == {commits belonging to Stack(s) of the repository named in payload['repository']['full_name']}`. The actual code enforces only: `{Commit rows mutated} == {all Commit rows across every Stack in the DB with sha == params.sha}`.

`StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

The `params` schema for this handler does not even `require :repository`, and the handler never calls the base class `stacks`/`repository_name` helpers (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers use for scoping: [2](#0-1)  and [3](#0-2) .

By contrast, `CheckSuiteHandler#process` first scopes to `stacks.where(branch: ...)` derived from the payload's repository, then only touches `stack.commits` — i.e., it enforces exactly the binding that `StatusHandler` is missing: [4](#0-3) .

`Status.replicate_from_github!` is called with `commit.stack_id`, so a `Status` row is written against whatever stack the matching `Commit` row actually belongs to, regardless of which repository sent the webhook: [5](#0-4)  and [6](#0-5) .

`WebhooksController#verify_signature` only authenticates that the payload matches the webhook secret configured for the *organization* named in the payload (`repository_owner`) — it says nothing about which specific commits within Shipit's whole dataset the event is allowed to touch: [7](#0-6) . That signature check does not, and cannot, prevent `Commit.where(sha:)` from matching rows belonging to a different repository/org whose commit happens to share the same sha (e.g., identical empty commits, shared cherry-picked commits, or vendored history reused across onboarded repos). None of `drop_unhandled_event`, `ExplicitParameters` schema validation, `force_github_authentication`, or model validations constrain the sha lookup to the calling repository's stacks — the divergence is real and unmitigated.

Exploit flow: attacker controls/administers a repository that is legitimately onboarded into Shipit (so their own org's webhook signature is valid). They send (or their onboarded repo's real GitHub triggers) a `status` event whose `sha` value happens to equal a commit sha that also exists in a stack belonging to a different repository/tenant (a legitimately shared/duplicate sha, not spoofed). Shipit's `StatusHandler` will iterate over every `Commit` row with that sha across all stacks and write a `Status` for each of them.

### Impact Explanation
A single validly-signed webhook write for one repository can mutate `Status`/`Commit` state belonging to N unrelated tenants (Stacks) simultaneously. Because `Status#after_create` triggers `enable_ci_on_stack` and `schedule_continuous_delivery`, and `Commit#create_status_from_github!` state changes can enqueue `ProcessMergeRequestsJob` and flip `deployable_status` (as shown by the state-machine tests around `add_status`) [8](#0-7) , this can influence deploy eligibility/merge-request processing on stacks the attacker does not own or administer. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team," blast radius across all stacks sharing a colliding commit sha.

### Likelihood Explanation
Requires: (1) attacker administers/owns a repository already onboarded into Shipit (so a legitimately-signed `status` webhook can be produced for their org), and (2) at least one commit sha collision exists between their repository's history and another onboarded repository's commit history (e.g., identical empty/no-op commits with the same author/committer/timestamp/message and tree, or shared cherry-picked/vendored commits — a realistic occurrence in monorepo-derived or template-derived repositories). No secrets, no privileged Shipit role, and no signature forgery are needed — only a legitimate webhook for a repository the attacker controls. This is directly repeatable against any repository pair sharing a commit sha for as long as the sha remains shared.

### Recommendation
Scope the lookup to the webhook's own repository before creating statuses, mirroring `CheckSuiteHandler`: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(...)`, restrict to that repository's `stacks`, and only call `create_status_from_github!` on `stack.commits.where(sha: params.sha)` instead of a global `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (controller or handler-level test, no live GitHub):
1. Create 3 fixture `Stack`/`Repository` records for 3 distinct repositories/orgs (`repo_a`, `repo_b`, `repo_c`).
2. Create 3 `Commit` fixtures, one per stack, all sharing the exact same `sha` value (simulating an empty/shared commit).
3. Stub/allow `verify_webhook_signature` to succeed for `repo_a`'s organization only (as in existing tests, e.g. `GithubHook.any_instance.stubs(:verify_signature).returns(true)` pattern from `test/controllers/webhooks_controller_test.rb`).
4. POST a `status` webhook (`X-Github-Event: status`) with `sha` set to the shared value and `repository.full_name` set to `repo_a` only.
5. Assert: `commit_a.statuses.count == 1` (expected, same-tenant write) AND, contrary to the intended binding, also assert `commit_b.statuses.count == 1` and `commit_c.statuses.count == 1` — i.e. `Stack B`/`Stack C`, which never authenticated this payload, received new `Status` rows.
6. This demonstrates `{mutated commits} != {commits of repo_a's stacks}`, confirming the vulnerability; a fixed implementation should assert `commit_b.statuses.count == 0` and `commit_c.statuses.count == 0` after the same POST.
