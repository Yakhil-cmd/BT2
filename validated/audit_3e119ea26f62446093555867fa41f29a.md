### Title
Webhook multi-organization signature scoping trusts `repository.owner.login` while payload handlers dispatch on `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), while every webhook `Handler` (e.g. `PushHandler`) resolves the actual repository/stack to act on using a *different* field of the same payload: `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`Handler#stacks`. [1](#0-0) [2](#0-1) 

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single engine instance, each with its own `webhook_secret` (`Shipit.github(organization:)` looks up per-organization app config, see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml` which define e.g. `somegithuborg` / `someothergithuborg` as separate tenants with distinct secrets). [3](#0-2) 

For an inbound webhook, `verify_signature` computes `repository_owner` from the JSON body itself (`repository.owner.login` or `organization.login`) and uses it to pick which organization's `webhook_secret` should validate the HMAC signature:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

Once the signature check passes (i.e., the HMAC matches the secret configured for the org named in `repository.owner.login`), the actual event dispatch never re-checks that org binding. Instead, `Handler#stacks`/`repository_name` derives the target repository purely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler#process` then walks every not-archived stack whose branch matches and enqueues a real GitHub sync for it:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The binding the engine implicitly relies on is:
`organization whose secret authenticated the request (repository.owner.login)` == `organization/repository the handler writes to (repository.full_name)`

Because the webhook body is attacker-supplied JSON (the whole point of signature verification is to establish trust in *some* of its fields), and both `repository.owner.login` and `repository.full_name` are independent, unauthenticated-until-verified keys inside that same body, an operator who is a legitimate GitHub App owner/admin for **their own** tenant organization (Org A, whose `webhook_secret` they legitimately possess because they created that GitHub App per `docs/setup.md`) can craft a raw POST directly to `/webhooks` with:
- `repository.owner.login = "OrgA"` (so the HMAC computed with Org A's real secret validates)
- `repository.full_name = "OrgB/some-repo"` (a different tenant's repository configured on the same Shipit instance)

`verify_signature` accepts the request because the HMAC is correct for Org A. `PushHandler` (or `status_handler.rb`'s `Commit.where(sha: params.sha)` which is not even scoped to an organization at all) then acts on Org B's stack, triggering `stack.sync_github` for a repository the attacker's credentials never authorized.

### Impact Explanation
This breaks a cross-tenant isolation boundary that the multi-org configuration model advertises (`docs/setup.md`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`): each org's webhook secret should only ever affect that org's own repositories/stacks. An attacker who legitimately controls one tenant org's GitHub App/webhook secret can force GitHub-sync events (and, via `status_handler.rb`, arbitrary commit-status writes matched purely by `sha` with no org scoping at all) against stacks belonging to a different, unrelated organization hosted on the same Shipit instance. Depending on downstream effects of `Stack#sync_github` (spec cache refresh, merge status, CI gating), this can influence merge/deploy readiness signals for a repository the attacker has no authorization over — a cross-repository write across a trust boundary the engine is supposed to enforce per-organization.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations sharing one engine instance (a documented, supported configuration), and (2) the attacker being a legitimate app owner/admin for one of those organizations (not a privileged Shipit user, not holding any `ApiClient` token, GITHUB_TOKEN, or `api_clients_secret` — this is exactly the "unprivileged attacker" class specified: GitHub identity trusted for Org A only). No Shipit session or API token is needed; only an HTTP POST to the public `/webhooks` endpoint with a self-signed payload is required.

### Recommendation
In `Shipit::WebhooksController#verify_signature` / `Handler`, ensure the organization used to select and validate the webhook secret is the same organization used to resolve the target repository/stack. Concretely, `Handler#stacks` should scope `Repository.from_github_repo_name` results (or `Commit.where(sha:)` lookups in `status_handler.rb`) to repositories belonging to the verified `repository_owner`, or reject the payload if `repository.full_name`'s owner segment does not case-insensitively match the verified `repository_owner`/`organization.login` used for signature selection.

### Proof of Concept
1. Configure Shipit with two tenant orgs, `OrgA` (secret `secretA`) and `OrgB` (secret `secretB`), each with stacks tracking their own repos, per `config/secrets.development.shopify.yml`.
2. As the legitimate owner of `OrgA`'s GitHub App (who knows `secretA` but has no access to `OrgB`), craft:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/private-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` and `X-Github-Event: push`, then POST to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature validates successfully against `secretA`.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/private-repo")` and calls `stack.sync_github(expected_head_sha: ...)` for Org B's stack — an action the attacker's Org A credentials never authorized.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
