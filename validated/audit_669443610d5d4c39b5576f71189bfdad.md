### Title
Cross-organization commit status forgery via webhook allows bypassing CI checks required for merge/deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit verifies inbound GitHub webhooks by looking up the signing key for the *organization* named in the payload, but for `status` events the actual write target (which `Commit`/`Stack` gets a new CI status) is selected purely by matching `sha` across the entire database, with no check that the sha belongs to a repository owned by the organization that produced the valid signature.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App's webhook secret to verify the HMAC against using `repository_owner`, derived from the payload itself: [1](#0-0) [2](#0-1) 

This proves only that the request was signed with the webhook secret configured for *some* organization/GitHub App recognized by this Shipit instance (Shipit explicitly supports "multiple GitHub applications for different GitHub organizations", each with its own `webhook_secret`, per `docs/setup.md`). It does not prove anything about which repository or stack the payload's other fields should be allowed to affect.

Once the signature is accepted, `WebhooksController#create` dispatches the raw parsed payload to the registered handler with no further scoping: [3](#0-2) 

Most handlers at least scope their side effects to the repository named in the payload via `Handler#stacks`/`Handler#repository_name` (`payload.dig('repository', 'full_name')`): [4](#0-3) 

But `StatusHandler#process` does not use `repository`/`stacks` scoping at all. It looks up commits **globally by sha** and writes a status to every match: [5](#0-4) 

Git commit SHAs are public (visible on GitHub, in PRs, CI logs, etc.), so an attacker only needs a webhook secret valid for *any* organization configured on the shared Shipit instance (i.e., their own org, if they administer a GitHub App that also happens to be registered with this Shipit deployment) to forge a `status` webhook naming: (a) `repository.owner.login` = their own organization (so `verify_signature` picks their own valid secret and passes), and (b) `sha` = a commit hash belonging to a *different* organization's tracked repository/stack. `StatusHandler` will happily create a `success`/`failure` status on that unrelated commit.

This directly breaks the binding: *the organization that authenticated the webhook* ≠ *the repository/stack whose commit status is written*.

### Impact Explanation
Commit CI status is load-bearing for both the merge queue and deploy gating:
- `MergeRequest#reject_unless_mergeable!` rejects PRs unless CI passed, based on `StatusChecker` reading `head.statuses_and_check_runs`: [6](#0-5) [7](#0-6) 
- `Stack#branch_status`/`#deployable?`/`#allows_merges?` similarly depend on commit status state to allow deploys and auto-merges: [8](#0-7) 

By forging a `success` status for a target commit in a stack belonging to a different organization/repository than the one whose secret they hold, an attacker can flip a required CI context to green for that unrelated repository, unblocking an automatic merge via the merge queue, or clearing the way for an otherwise-gated deploy. This is a cross-repository/cross-organization write and can lead to an unauthorized merge or deploy on a repository the attacker does not administer — matching the Critical impact bar (cross-repository writes / unauthorized deploy or merge).

### Likelihood Explanation
Requires only: (1) administering a GitHub App/organization already configured as a tenant on the target multi-org Shipit instance (a legitimate, low-privilege position relative to the *victim* organization), and (2) knowledge of a target commit SHA in the victim repository, which is public information. No access to the victim's webhook secret, GitHub token, or Shipit session is needed. This is realistic wherever a single Shipit deployment serves multiple organizations/tenants, which is an explicitly documented and supported configuration.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository named in the payload, and cross-check that the resolved repository's owner matches the organization whose secret verified the signature, before looking up or mutating any `Commit`/`Stack`. Concretely, replace `Commit.where(sha: params.sha)` with a lookup scoped through `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`'s commits, and reject the webhook if that repository's owner does not equal the `repository_owner` used to select the verification secret.

### Proof of Concept
1. Attacker registers/administers "Org-Attacker" as a GitHub App tenant on the shared Shipit instance, obtaining `webhook_secret_A` (legitimately, for their own org).
2. Attacker finds a public commit SHA `deadbeef...` belonging to `victim-org/victim-repo`, tracked as a Shipit stack requiring a `ci/required` status context.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "Org-Attacker" }, "full_name": "Org-Attacker/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"Org-Attacker"`, fetches `Shipit.github(organization: "Org-Attacker")`, and the signature verifies successfully.
6. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, finds the commit under `victim-org/victim-repo`, and creates a `success` status for context `ci/required` on it — with no check that `victim-org` matches `Org-Attacker`.
7. This can flip `MergeRequest#any_status_checks_missing?`/`#any_status_checks_failed?` to false for a pending PR against `victim-org/victim-repo`, allowing it to be auto-merged by Shipit's merge queue, or clear `Stack#deployable?`/`#branch_status` gating for an unauthorized deploy.

    def lock_reverted_commits!
      backlog = undeployed_commits.to_a
      affected_rows = 0

      until backlog.empty?
        backlog = backlog.drop_while { |c| !c.revert? }
        revert = backlog.shift
        next if revert.nil?

        commits_to_lock = backlog.reverse.drop_while { |c| !revert.revert_of?(c) }
        next if commits_to_lock.empty?

        affected_rows += commits
                         .where(id: commits_to_lock.map(&:id).uniq)
                         .lock_all(revert.author)
      end

      touch if affected_rows > 1
    end

    def next_expected_commit_to_deploy(commits: nil)
