### Title
Fork-controlled `shipit.yml` `machine.environment` and PR-label keys bypass the env whitelist and reach `PTY.spawn` unfiltered - (File: `lib/shipit/task_commands.rb`, `app/models/shipit/review_stack.rb`, `lib/shipit/command.rb`)

### Summary
`Shipit::EnvironmentVariables.permit` whitelists only the user-supplied `env` for deploys, rollbacks and tasks (`deploy_variables`/`rollback_variables`/task `variables`), but `TaskCommands#env` merges `deploy_spec.machine_env` and `Stack#env`/`ReviewStack#env` (PR label names) into the environment **without any whitelist check**. Because a Review Stack's working directory is checked out from the PR's own (fork) branch, an unprivileged contributor fully controls `shipit.yml`'s `machine.environment` block and thus can inject arbitrary keys — including `IFS` — into the environment handed to `Command#unbundled_env` and ultimately to `PTY.spawn`.

### Finding Description
The intended binding is: *the set of keys that reach the spawned process's environment == the whitelist enforced by `EnvironmentVariables.permit(variable_definitions)`*. This holds for `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` [1](#0-0) [2](#0-1) , which route through `EnvironmentVariables#permit` and raise `NotPermitted` for any non-whitelisted key [3](#0-2) .

That binding is broken for two other env sources that feed the same `Command`:

1. `TaskCommands#env` merges `deploy_spec.machine_env` (the `shipit.yml` `machine.environment` key) directly, with no call to `permit`: [4](#0-3) 
2. `ReviewStack#env` merges every PR label name (uppercased) into the environment, again unfiltered: [5](#0-4) 

Both paths feed into `Command#env`/`Command#unbundled_env`, which places `@env` **last** in the merge chain — so it overrides `PATH` and any base variable, and no key (including `IFS`) is stripped: [6](#0-5) 

That hash is passed straight to `PTY.spawn`: [7](#0-6) 

Reachability by an unprivileged fork PR: under `provisioning_behavior = prevent_with_label`, a Review Stack is provisioned by default and only archived if the PR carries the opt-out label — i.e., provisioning requires no privilege or label at all, as confirmed by the handler logic and tests ("creates and provisions a new review stack when the repository creates ReviewStacks with prevent_with_label and the label is absent") [8](#0-7) [9](#0-8) . The Review Stack's deploy spec is read from the working directory checked out for that stack's branch (the PR's head ref), via `DeploySpec::FileSystem.new(@task.working_directory, @stack)` [10](#0-9) , so the fork author fully controls the `machine.environment` block that is merged unfiltered into `env`.

Existing guards that fail to close this gap: `EnvironmentVariables.permit` exists and is enforced for `deploy`/`rollback`/`task` params supplied via the API/UI (see the controller tests rejecting `DANGEROUS_VARIABLE`) [11](#0-10) , but it is never invoked on `deploy_spec.machine_env` or on `Stack#env`/`ReviewStack#env`'s label-derived keys, so the same protection is absent exactly where the attacker-controlled input (fork `shipit.yml`, fork-added PR label) is merged.

### Impact Explanation
Any key placed in `machine.environment` in the fork's `shipit.yml`, or the exact uppercased name of a label the PR author adds to their own PR, reaches the spawned deploy/task process's environment unfiltered, overriding base variables including `PATH`. If any deploy/task step string relies on unquoted shell-level expansion (a common pattern for interpolated variables like `$ENVIRONMENT`/`$BRANCH` in `cap`-style deploy commands), setting `IFS` changes shell word-splitting behavior for that step, letting the attacker reshape the resulting argv. This is a fork-triggerable environment-poisoning primitive into the process eventually exec'd by `PTY.spawn` on the Shipit deploy host, matching the Critical RCE class described (`Command`/`PTY.spawn`), though actual code execution additionally depends on the specific deploy script containing an unquoted shell expansion — a very common but not universal condition.

### Likelihood Explanation
Preconditions: review stacks enabled with `provisioning_behavior = prevent_with_label` (a supported, documented opt-out configuration) [12](#0-11) . Attacker cost is minimal: open a PR from a fork with a `shipit.yml` containing `machine: { environment: { IFS: ... } }`, or add a label to their own PR — both fully within an unprivileged contributor's normal GitHub permissions. No secrets, tokens, or maintainer approval are required for provisioning to occur under this mode, and the behavior is repeatable per PR/stack.

### Recommendation
Route `deploy_spec.machine_env` and any PR-label-derived environment additions through `EnvironmentVariables.permit` against an explicit, maintainer-controlled whitelist (or reject reserved/security-sensitive names such as `IFS`, `PATH`, `LD_PRELOAD`, `BASH_ENV`, etc.) before merging into `Command#env`. At minimum, `Command#unbundled_env` should scrub such dangerous shell-influencing variables unconditionally, regardless of source.

### Proof of Concept
Minitest plan (models/unit, no live GitHub):
1. Create a `ReviewStack` under a repository with `provisioning_behavior: prevent_with_label`.
2. Attach a `PullRequest` with `labels = ["IFS"]` to the stack, and/or stub `deploy_spec.machine_env` to return `{ 'IFS' => 'z' }`.
3. Build a `TaskCommands`/`DeployCommands` for a task on that stack and call `.env`.
4. Assert `commands.env['IFS'] == 'true'` (label path) or `== 'z'` (machine_env path) — i.e., that the whitelist equality `commands.env.keys.subset?(deploy_variables.map(&:name))` is FALSE because `IFS` is present without being in `deploy_variables`.
5. Construct `Command.new('...', env: commands.env, chdir: tmp).unbundled_env` and assert `unbundled_env['IFS']` equals the attacker-supplied value, demonstrating it reaches the hash passed to `PTY.spawn`.

**File:** docs/review_stacks.md (L17-21)
```markdown
shipit-engine support three distinct behaviors for determining which Pull Requests should be considered for Review Stack creation.

1. "Allow All" - shipit-engine will create a Review Stack for every new Pull Requests.
1. "Allow With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisioning_label" attribute in order for shipit-engine to dynamically create/manage a Review Stack - an opt-in strategy.
1. "Prevent With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisoining_label" attribute in order to **prevent** shipit-engine from dynamically creating/managing a Review Stack - an opt-out strategy.
```
