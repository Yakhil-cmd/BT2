### Title
KAIA Bridge Nonce Permanently Stuck and Funds Locked When Recipient Contract Rejects KAIA in `handleKLAYTransfer` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge pushes KAIA directly to the user-supplied `_to` address via a low-level `call.value()`. If `_to` is a contract that has no payable fallback (or explicitly reverts on receive), the call returns `ok = false`, the `require` reverts the entire transaction, and every state mutation in that call — including the nonce registration in `handleNoncesToBlockNums` and the `_updateHandleNonce` advance — is rolled back. Because the bridge has no mechanism to skip or override a stuck nonce, `lowerHandleNonce` is permanently frozen at that position, the bridged KAIA is permanently locked inside the bridge contract, and the `recoveryBlockNumber` never advances past the stuck block.

---

### Finding Description

`handleKLAYTransfer` executes the following sequence:

```solidity
// BridgeTransferKLAY.sol lines 75–99
_lowerHandleNonceCheck(_requestedNonce);
if (!_voteValueTransfer(_requestedNonce)) { return; }

_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

The KAIA push to `_to` is the very last step. If it fails, the EVM reverts the entire transaction frame, undoing:
- `_setHandledRequestTxHash` (tx hash not marked handled)
- `handleNoncesToBlockNums[_requestedNonce]` (block number not recorded)
- `_updateHandleNonce` (nonce not advanced)
- The operator vote cast inside `_voteValueTransfer`

`_updateHandleNonce` advances `lowerHandleNonce` only by scanning a contiguous run of filled `handleNoncesToBlockNums` entries:

```solidity
// BridgeTransfer.sol lines 149–155
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    delete handleNoncesToBlockNums[i];
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;
``` [2](#0-1) 

Because the stuck nonce's entry is never written, the loop halts at that nonce on every subsequent call, and `lowerHandleNonce` never advances past it.

The `_to` address originates from the user's `requestKLAYTransfer` call on the source chain:

```solidity
// BridgeTransferKLAY.sol lines 132–134
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [3](#0-2) 

Any user can supply an arbitrary `_to`, including a contract with no payable fallback.

There is no owner-callable function to skip a nonce, force-write `handleNoncesToBlockNums`, or override `lowerHandleNonce`. The bridge contract exposes no escape hatch for this condition.

---

### Impact Explanation

1. **Permanent KAIA loss for the user.** The source-chain bridge has already consumed the user's KAIA (it was deposited when `requestKLAYTransfer` was called). The destination-chain bridge holds the corresponding KAIA but can never deliver it. The funds are permanently locked.

2. **Bridge nonce corruption.** `lowerHandleNonce` is frozen at the stuck nonce. `recoveryBlockNumber` is frozen at the block before it. The bridge recovery daemon will re-scan from that block indefinitely, wasting resources and potentially causing confusion about which events have been processed.

3. **No administrative remedy.** The bridge owner can change `feeReceiver`, lock/unlock tokens, and stop the bridge, but cannot advance `lowerHandleNonce` or skip a nonce. The only fix is a contract upgrade.

---

### Likelihood Explanation

- The `_to` address is fully user-controlled and is not validated on-chain.
- Many common patterns produce non-payable contract addresses: multisigs that lack a payable fallback, proxy contracts, DAO treasuries, and smart-contract wallets that explicitly revert on plain KAIA receives.
- A user can trigger this accidentally (e.g., bridging to a multisig) or intentionally (deploying a rejector contract and using it as `_to`).
- Once triggered, the condition is permanent and requires no further attacker action.

---

### Recommendation

Apply the same fix recommended in the original report: separate the nonce-advance from the asset delivery. Specifically:

1. Record `handleNoncesToBlockNums[_requestedNonce]` and call `_updateHandleNonce` **before** attempting the KAIA transfer, so the nonce is always advanced regardless of delivery outcome.
2. If the `call.value()` fails, store the owed amount in an internal escrow mapping keyed by `_to` and nonce, and emit a distinct event.
3. Add a permissionless `claimKLAY(uint64 nonce)` function that lets the recipient (or anyone on their behalf) pull the escrowed KAIA later.

This mirrors the pull-payment pattern already present in the OpenZeppelin `PullPayment` contract included in the repository: [4](#0-3)

### Proof of Concept

1. **Deploy a rejector contract** on the destination chain:
   ```solidity
   contract Rejector {
       // No payable fallback — all KAIA sends revert
   }
   ```

2. **On the source chain**, call:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(
       address(rejector), // _to
       0.9 ether,         // _value
       ""
   );
   ```
   This emits `RequestValueTransfer` with nonce N and deposits 1 ETH into the source bridge.

3. **Bridge operators** observe the event and call on the destination chain:
   ```solidity
   bridge.handleKLAYTransfer(txHash, from, address(rejector), 0.9 ether, N, blockNum, "");
   ```
   The `_to.call.value(0.9 ether)("")` call returns `ok = false` because `Rejector` has no payable fallback. The `require` reverts the transaction. All state changes (nonce registration, vote) are rolled back.

4. **Every subsequent operator attempt** for nonce N reverts identically.

5. **Verify the stuck state:**
   ```solidity
   bridge.lowerHandleNonce() // returns N, never advances
   bridge.recoveryBlockNumber() // returns block before N, never advances
   ```
   The 0.9 KAIA is permanently locked in the destination bridge. The user's 1 ETH on the source chain is gone. [5](#0-4) [6](#0-5)

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

/**

contract PullPayment {
    Escrow private _escrow;

    constructor () internal {

    }

    /**
     * @dev Withdraw accumulated balance.
     * @param payee Whose balance will be withdrawn.
     */
    function withdrawPayments(address payable payee) public {

    }

    /**
     * @dev Returns the credit owed to an address.
     * @param dest The creditor's address.
     */
    function payments(address dest) public view returns (uint256) {
        return _escrow.depositsOf(dest);

    /**
     * @dev Called by the payer to store the sent amount as credit to be pulled.

     * @param amount The amount to transfer.

    function _asyncTransfer(address dest, uint256 amount) internal {
