### Title
Webhook signature verification uses `repository.owner.login`, but every event handler acts on `repository.full_name` — cross-organization commit-status forgery enabling an unauthorized merge - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check the HMAC signature using `repository_owner`, which is read from `params.dig('repository','owner','login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1)  Every downstream handler, however, resolves the target repository/stack independently from a different field in the *same* payload: `repository.full_name`, via `Handler#repository_name`/`#stacks`. [3](#0-2)  Nothing enforces that `repository.full_name`'s organization equals `repository.owner.login`. This breaks the intended binding "organization that authenticated == organization/repository being written," letting a webhook that is validly signed for organization A act on a stack belonging to organization B.

### Finding Description
Shipit is multi-tenant: each configured GitHub organization has its own GitHub App / webhook secret (see `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne`/`OrgTwo` each with independent `webhook_secret`s). [4](#0-3)  `verify_webhook_signature` HMACs the raw request body against the secret belonging to whichever organization `repository_owner` names: [5](#0-4) 

Once the signature check passes, `WebhooksController#create` dispatches `params` — the full parsed JSON — to the registered handlers for the event type: [6](#0-5) 

Handlers such as `StatusHandler`, `PushHandler`, and the `PullRequest` handlers never re-check `repository.owner.login`; they locate the target `Repository`/`Stack` purely from `repository.full_name`: [7](#0-6) [8](#0-7) [3](#0-2) 

So the field that gates *which secret authenticates the request* (`repository.owner.login`) and the field that determines *which repository's state is mutated* (`repository.full_name`) are independent, attacker-controlled JSON fields inside the same signed blob. Anyone who legitimately controls a repository/organization onboarded onto the same Shipit instance (and therefore knows or can compute a valid signature for their own org's webhook secret — e.g. because they configured that GitHub App/webhook themselves, or that org's `webhook_secret` is unset, in which case `verify_webhook_signature` returns `true` unconditionally: [9](#0-8) ) can send a correctly-signed `status` (or `check_suite`/`push`) webhook whose `repository.full_name` names a *different*, victim organization's repository that is also configured on the same Shipit instance.

### Impact Explanation
The most direct exploitable consequence is forging a commit `status`: `StatusHandler#process` looks up `Commit.where(sha: params.sha)` across **all stacks in the database** (not scoped to the authenticating organization) and calls `commit.create_status_from_github!(params)`. [10](#0-9)  A forged `success` status on a victim commit satisfies `MergeRequest#all_status_checks_passed?`/`reject_unless_mergeable!`, which are the CI gates checked by `ProcessMergeRequestsJob`: [11](#0-10) [12](#0-11) . If a pull request is already queued in the victim's merge queue awaiting CI, injecting a fake passing status for its head commit lets `MergeRequest#merge!` call GitHub's merge API on the victim's repository using the app's own `github_token`, achieving an unauthorized merge on a repository the attacker's organization was never authorized to touch — matching the "unauthorized deploy, rollback or merge" / cross-repository-writes impact bar.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment with more than one GitHub organization configured (documented, supported configuration — see the double-app fixture), (2) the attacker controls at least one onboarded organization/repository (or webhook secret is unset for some org) so they can produce a valid signature, and (3) a victim stack has a merge-queue PR pending on CI at the time the forged status lands. This is a realistic scenario for a shared/internal multi-tenant Shipit instance but not for a single-tenant deployment with one organization, so likelihood is medium rather than trivial.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, cross-validate that the organization implied by `repository.full_name` (and `organization.login` for org-scoped events) matches the `repository_owner` used to select the signing secret before dispatching to handlers, and scope `StatusHandler`/`Handler#stacks` lookups by repository/organization rather than trusting `full_name` as the sole selector once verified against a possibly-unrelated org's key.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim), both onboarded, per `secrets_double_github_app.yml`.
2. Victim `OrgB/victim-repo` has an open PR in the merge queue, `pending`, waiting on CI for commit `SHA_V`.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, `X-Hub-Signature` computed with `OrgA`'s webhook secret, and body:
```json
{ "sha": "SHA_V", "state": "success", "context": "ci/required",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } } }
```
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies against `OrgA`'s secret — succeeds. [1](#0-0) 
5. `StatusHandler` finds `Commit` by `sha` (global lookup, not org-scoped) and records the forged `success` status on the victim's commit. [10](#0-9) 
6. `ProcessMergeRequestsJob` next run sees `all_status_checks_passed?` true and calls `MergeRequest#merge!`, merging the victim PR via the app's GitHub credentials. [13](#0-12)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      merge_requests = stack.merge_requests.to_be_merged.to_a

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
