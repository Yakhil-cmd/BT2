### Title
Vote account `pending_delegator_rewards` is never decremented after block rewards are distributed to stakers - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
This is a structural analog to the DODO M-14 bug: a value that tracks an outstanding, in-progress obligation (DODO's `liquidationTarget` / agave's `pending_delegator_rewards`) is set/incremented at one step of a multi-step accounting process, consumed to compute a distribution at a second step, but never reconciled (decremented) back into the record that future steps rely on. Just as DODO's `removeD3Pool()` puts the pool into liquidation without setting `liquidationTarget`, leaving `finishLiquidation()` unable to balance the vault's borrow bookkeeping, agave's block-reward accounting reads `pending_delegator_rewards` from the vote account to compute and pay out `block_reward` to each delegator's stake account, but does not appear to write back a reduced value to the vote account's own `pending_delegator_rewards` field once that reward has actually been paid out.

### Finding Description
`deposit_delegator_rewards` (SIMD-0123) is the only place shown to increment the vote account's tracked liability: [1](#0-0) [2](#0-1) 

During partitioned epoch reward calculation, `calculate_block_reward` reads the vote account's current `pending_delegator_rewards` to compute each delegator's pro-rata share of the block reward for the epoch: [3](#0-2) 

That computed `block_reward` is then folded into `PartitionedStakeReward` and, at distribution time, minted directly into stake accounts and tallied into bank capitalization and the epoch-rewards sysvar: [4](#0-3) [5](#0-4) 

Across every function inspected in the reward calculation and distribution paths (`calculate_block_reward`, `calculate_stake_rewards_and_commissions`, `store_stake_accounts_in_partition`, `distribute_epoch_rewards_in_partition`), the only mutation performed is against the *stake* accounts and bank-level bookkeeping (capitalization, epoch rewards sysvar). No code path was found that subsequently mutates the *vote* account's `pending_delegator_rewards` field to subtract the amount that was just paid out as `block_reward`. The only setter found for this field besides tests is the increment-only `add_pending_delegator_rewards`.

Separately, `withdraw()` in the vote program treats `pending_delegator_rewards` as a hard reserve that cannot be withdrawn and blocks closing the vote account while it is nonzero: [6](#0-5) 

This mirrors the DODO bug class precisely: an intermediate accounting step (block-reward distribution) consumes a "pending obligation" value to actually pay out funds, but the authoritative record of that obligation is never updated to reflect the payout, so downstream logic (withdraw/close, and the next epoch's block-reward calculation) continues operating on a stale, unreconciled value.

### Impact Explanation
If `pending_delegator_rewards` is genuinely never decremented on distribution:
- **Misattributed/duplicated rewards**: the same `pending_delegator_rewards` balance is reused as the numerator in `calculate_block_reward` every epoch, so delegators would be paid out overlapping/duplicate shares of a reward pool that has already been distributed, minting stake rewards not backed by an actual reduction in the vote account's tracked liability.
- **Permanently frozen vote account funds**: because `withdraw()` treats `pending_delegator_rewards` as an un-withdrawable, ever-growing reserve, lamports that have already been paid out to delegators remain permanently locked behind this stale reserve amount, and the vote account can never be closed via `Withdraw` to zero as long as the stale balance is nonzero.

Both outcomes fall within the accepted impact categories (misattributed/duplicated rewards, permanently frozen accounts).

### Likelihood Explanation
The path is reachable by any validator/authorized withdrawer performing a normal `DepositDelegatorRewards` (SIMD-0123, gated behind `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` features) followed by ordinary epoch-boundary partitioned reward distribution — no privileged or validator-only action beyond the unprivileged/authorized-signer-gated `DepositDelegatorRewards` instruction is required, and reward distribution runs automatically for every epoch once the relevant features are active.

### Recommendation
At the point where `block_reward_lamports_distributed` is computed and paid out per stake account in `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition`, the corresponding vote account's `pending_delegator_rewards` must be decremented by the total amount actually distributed for that vote account in the same distribution step (analogous to DODO's recommendation to calculate/settle `liquidationTarget` before finalizing). This keeps the "pending" liability figure synchronized with what has actually left the reserve, preventing double-payment across epochs and preventing indefinite freezing of already-distributed lamports behind a stale reserve check in `withdraw()`.

### Proof of Concept
Not independently reproduced with a running validator; this analysis is based on static tracing of the code paths above (`deposit_delegator_rewards` → `calculate_block_reward` → `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` → `withdraw`) and did not locate a decrement of `pending_delegator_rewards` at distribution time within the code retrievable via search. Given index size limits, it is possible a decrement exists elsewhere in the vote/reward distribution code that was not surfaced by these searches; a Devin session with full repository access should verify by grep-ing for every write site of `pending_delegator_rewards` (not just `add_pending_delegator_rewards`) and confirming whether any function reduces it in response to `block_reward` distribution, before treating this as confirmed rather than a strong analog candidate.

    fn distribute_epoch_rewards_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) {
        let pre_capitalization = self.capitalization();
        let (
            DistributionResults {
                stake_reward_lamports_minted,
                stake_reward_lamports_burned,
                block_reward_lamports_distributed,
                block_reward_lamports_burned,
                updated_stake_rewards,
            },
            store_stake_accounts_us,
        ) = measure_us!(self.store_stake_accounts_in_partition(partition_rewards, partition_index));

        // increase total capitalization by the distributed rewards
        self.capitalization
            .fetch_add(stake_reward_lamports_minted, Relaxed);

        // decrease total capitalization by burned block rewards
        self.capitalization
            .fetch_sub(block_reward_lamports_burned, Relaxed);

        // decrease distributed capital from epoch rewards sysvar
        self.update_epoch_rewards_sysvar(
            stake_reward_lamports_minted + stake_reward_lamports_burned,
            block_reward_lamports_distributed + block_reward_lamports_burned,
        );

        // update reward history for this partitioned distribution
        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),
            partition_index,
            store_stake_accounts_us,
            store_stake_accounts_count: updated_stake_rewards.len(),
            distributed_rewards: stake_reward_lamports_minted,
            burned_rewards: stake_reward_lamports_burned,
            distributed_block_rewards: block_reward_lamports_distributed,
            burned_block_rewards: block_reward_lamports_burned,
        };

        report_partitioned_reward_metrics(self, metrics);
    }
