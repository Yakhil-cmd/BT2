### Title
Cross-organization webhook forgery via mismatched signature-org lookup vs. repository-action lookup - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate an inbound webhook against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). The actual event handlers, however, resolve the `Stack`/`Repository` to act on using a completely different field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Because these two lookups use independent JSON fields, an attacker who legitimately knows (or controls) the webhook secret for one organization configured in this Shipit instance can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes with a secret they know) while `repository.full_name` names a victim stack belonging to a completely different, unrelated organization/repository.

### Finding Description
`verify_signature` computes trust based on one identity (`repository.owner.login`/`organization.login`) while the code that is actually driven by the payload (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`, etc.) is bound to a different identity (`repository.full_name`) inside the same signed blob. [1](#0-0) [2](#0-1) [3](#0-2) 

The HMAC signature (`X-Hub-Signature`) is verified against the full raw body using the webhook secret configured for whichever organization the attacker names in `repository.owner.login`: [4](#0-3) 

This satisfies "the signature is valid" from the perspective of `verify_webhook_signature`, but it only proves the payload was signed with *that org's* secret — it says nothing about which repository the payload is actually going to act upon, because `repository.full_name` is an independently attacker-controlled string in the same body. The trust binding "organization that authenticated" (used to pick the secret) is not equal to "the repository that is written" (used by the handler to find the `Stack`), which is exactly the disallowed pseudo-state/authority-mismatch pattern the report warns about — verification looks like it covers the whole payload but the two decisions (which secret to check, which repository to mutate) are keyed off different, independently forgeable fields.

Concretely, `PushHandler` finds stacks solely from `repository.full_name` and calls `sync_github`: [5](#0-4) 

`StatusHandler` looks up commits purely by `sha` (no org check at all) and creates a `Status`, which can trigger continuous delivery for any stack that already has a matching commit: [6](#0-5) [7](#0-6) 

Creating a `success` status is exactly what triggers `ContinuousDeliveryJob`, which will `trigger_deploy` for the stack if it is configured for continuous deployment: [8](#0-7) [9](#0-8) 

### Impact Explanation
In a multi-tenant Shipit deployment (multiple GitHub orgs each configured with their own `webhook_secret` in `secrets.yml`), an attacker who is entitled to send webhooks for one org (i.e., knows that org's `webhook_secret`, which is the normal, low-privilege trust boundary for that org's own repos) can forge `X-Github-Event: status` or `push` requests whose `repository.owner.login` is their own org but whose `repository.full_name`/`sha` targets a victim stack in a different, unrelated organization. This can:
- Force `GithubSyncJob`/`sync_github` on arbitrary tracked stacks (`push` handler), and
- Inject forged commit statuses (`success`/`failure`) for arbitrary commits (`status` handler), which is capable of automatically triggering an **unauthorized deploy** via `ContinuousDeliveryJob#perform` → `Stack#trigger_continuous_delivery` on a stack the attacker has no authorization over.

This matches the required "Critical: unauthorized deploy" impact bar, contingent on the target Shipit instance hosting more than one GitHub organization's webhook secret (a supported, documented multi-org configuration, per `config/secrets.development.shopify.yml`). [10](#0-9) 

### Likelihood Explanation
Likelihood is limited to deployments where Shipit is configured with multiple GitHub organizations/webhook secrets and the attacker legitimately controls (or has access to) at least one org's `webhook_secret` for a repo they administer, while a victim stack with `continuous_deployment: true` exists in another org tracked by the same Shipit instance. This is a realistic scenario for shared/hosted Shipit deployments serving multiple teams/orgs, which is the exact configuration `Shipit.github(organization:)`/multi-org secrets support.

### Recommendation
Bind the signature-verification identity to the same field used for repository resolution. Either:
1. Verify the signature using the org/secret derived from `repository.full_name` (the same field `Handler#repository_name` uses), not from `repository.owner.login`/`organization.login`, or
2. After verifying the signature, re-check that `repository.owner.login` (the org whose secret was used) matches the owner of `repository.full_name` before dispatching to handlers, rejecting the request otherwise.

More generally, avoid deriving the "authenticated identity" (which secret to check) and the "acted-upon identity" (which repo/stack the code mutates) from two different fields of the same attacker-controlled payload.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with a distinct `webhook_secret` (per `config/secrets.*.yml`).
2. Attacker knows `attacker-org`'s webhook secret (e.g., they administer that org's GitHub App/webhook, as intended).
3. Attacker crafts a `status` (or `push`) event body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<known sha of victim's tracked commit>",
  "state": "success",
  "context": "ci/forged"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), successfully verifies the signature using the secret the attacker knows. [11](#0-10) 
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — belonging to `victim-org/victim-repo` — with no organization check, and creates a forged `success` `Status`. [12](#0-11) 
7. If the victim stack has `continuous_deployment: true`, the new `success` status enqueues `ContinuousDeliveryJob`, which deploys the commit without any authorization from `victim-org`. [7](#0-6) [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
