### Title
Webhook signature verification is bound to `repository.owner.login`, but `StatusHandler` writes commit statuses using only `sha`, with no repository/organization scoping — allowing cross-repository/cross-organization CI status forgery and unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using the `repository.owner.login` (or `organization.login`) field taken from the *same* unauthenticated JSON body it is about to verify. [1](#0-0)  Once the signature check passes, the generic `Webhooks::Handlers::Handler` base class exposes a `repository_name` helper based on `payload.dig('repository', 'full_name')` for scoping, [2](#0-1)  but `StatusHandler#process` never uses this scoping at all — it looks up commits globally by `sha` across the entire Shipit installation and attaches the attacker-supplied CI state to them. [3](#0-2) 

### Finding Description
The binding that should hold is: **organization whose secret authenticated the webhook == repository/stack whose data is written**. In this engine that binding is broken for the `status` event:

1. `verify_signature` fetches `Shipit.github(organization: repository_owner)` and verifies the raw HMAC signature against that org's configured `webhook_secret`. [1](#0-0)  `repository_owner` is read straight out of the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`). [4](#0-3) 
2. Shipit explicitly supports configuring **multiple independent GitHub Apps/organizations**, each with its own `webhook_secret`. [5](#0-4) 
3. Because the attacker fully controls the raw JSON body being signed, they can pick `repository.owner.login = "OrgA"` (an org they legitimately have/administer the webhook for) so the signature check succeeds using OrgA's secret, while filling in a completely unrelated `sha` value belonging to a commit on a stack owned by a different organization/repository (`OrgB`) that is also configured on this same Shipit instance.
4. `StatusHandler` does no repository/organization scoping whatsoever: it queries `Commit.where(sha: params.sha)` globally, without ever checking `payload['repository']['full_name']`, and calls `commit.create_status_from_github!(params)` on every match. [3](#0-2)  This is unlike other handlers (e.g. `PushHandler`, `CheckSuiteHandler`) which correctly restrict processing to `stacks` derived from `repository.full_name`. [6](#0-5) [7](#0-6) 

The net effect: the "field acted on" (`sha`, used to select which commit's CI status is written) is never bound to the "field covered by the trust decision" (the organization whose secret validated the request). An attacker who legitimately controls the webhook secret for one configured organization can forge CI statuses for commits belonging to any other organization/repository hosted on the same Shipit instance.

### Impact Explanation
Shipit gates deploys on commit CI statuses via `ci.require` / `ci.blocking` configuration in `shipit.yml`. [8](#0-7)  By forging a successful status for an arbitrary commit sha belonging to a different organization's stack, an attacker can satisfy that stack's CI requirements and enable an unauthorized deploy of code they do not control — this falls squarely under the "Critical: unauthorized deploy" impact category. This also crosses an authorization boundary equivalent to "cross-repository writes," since the write (a `Status` record tied to a `Commit`) is performed on data belonging to a different repository/organization than the one whose credential (`webhook_secret`) authenticated the request.

### Likelihood Explanation
Exploitation only requires: (a) the target Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration), [5](#0-4)  and (b) the attacker legitimately controls (or has obtained) the `webhook_secret` for any one of those organizations — which is a much lower bar than compromising the target organization's own credentials. No GitHub App private key, `api_clients_secret`, or `ApiClient` token is required; only knowledge of a sibling organization's webhook secret and the target's commit `sha` (which is public information visible via GitHub or the Shipit deploy UI). No prior Shipit session or privileged account is needed to hit `WebhooksController`.

### Recommendation
In `Webhooks::Handlers::Handler`/`StatusHandler`, require and enforce that `payload.dig('repository', 'full_name')` (or `owner.login`) matches the organization that was used to verify the webhook signature, and scope the `Commit` lookup through `stacks`/`repository` exactly as `PushHandler` and `CheckSuiteHandler` already do, rather than querying `Commit.where(sha: ...)` globally.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-app instructions).
2. As someone who controls `OrgA`'s webhook secret (e.g., an org owner who installed the app for `OrgA`), craft a `status` event payload:
   ```json
   {
     "sha": "<sha-of-a-commit-belonging-to-OrgB/some-repo-stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/decoy-repo" }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` and send it to `POST /webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and successfully verifies the signature. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `OrgB` commit — and creates a successful status on it, with no check that this commit belongs to `OrgB`, not `OrgA`. [3](#0-2) 
6. If `OrgB`'s stack requires that CI context to deploy, the forged status can now satisfy the deploy gate, enabling an unauthorized deploy of `OrgB`'s stack.

<h3 id="ci">CI</h3>

**<code>ci.require</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to disallow deploys if any of them is missing on the commit being deployed.

For example:
```yml
ci:
  require:
    - ci/circleci
```

**<code>ci.hide</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to ignore.

For example:
```yml
ci:
  hide:
    - ci/circleci
```

**<code>ci.allow_failures</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to be visible but not to required for deploy.

For example:
```yml
ci:
  allow_failures:
    - ci/circleci
```

**<code>ci.blocking</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to disallow deploys if any of them is missing or failing on any of the commits being deployed.

For example:
```yml
ci:
  blocking:
    - soc/compliance
```
