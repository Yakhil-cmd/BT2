Confirmed root cause: the webhook signature-verification key is selected using `repository.owner.login` (`WebhooksController#repository_owner`), while the actual `Stack`/`Repository` that the event is applied against is looked up using `repository.full_name` (`Handler#repository_name`, `Repository.from_github_repo_name`). These are two independently-attacker-settable strings inside the same JSON body.

### Title
Webhook organization used for HMAC verification does not bind to the repository whose stack is mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate a webhook against using `repository.owner.login` (falling back to `organization.login`), [1](#0-0) [2](#0-1)  while every event handler resolves the target `Stack`/`Repository` using a *different* field of the same payload, `repository.full_name` [3](#0-2) [4](#0-3) . Both fields are attacker-controllable in the raw JSON body that is HMAC-signed as a whole, so nothing forces `repository.owner.login == repository.full_name.split('/').first`.

### Finding Description
An organization owner who legitimately configures Shipit on their own GitHub org (`OrgA`, with a real, known `webhook_secret`/GitHub App installation for `OrgA`) can compute a valid `X-Hub-Signature`/`X-Hub-Signature-256` over an arbitrary JSON body of their own choosing, because they know their own webhook secret. `verify_signature` only checks that the signature matches the secret belonging to `repository_owner`, which is read from the payload's `repository.owner.login` field [2](#0-1) . If the attacker sets `repository.owner.login = "OrgA"` (so the correct secret is selected and the signature validates) but sets `repository.full_name = "OrgB/target-repo"` (an org they don't own), the signature check passes, yet the handler that actually mutates state resolves the affected repository from `repository.full_name`, i.e. `OrgB/target-repo` [3](#0-2) [4](#0-3) . The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository/stack being written`. This binding is never enforced anywhere in `WebhooksController` or `Handler`.

For example, `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the branch under the repository resolved purely from `full_name` [5](#0-4) , and `GithubSyncJob` subsequently performs a real GitHub sync/deploy-trigger flow using the engine's own installation-scoped credentials for that stack's actual configured organization — not the attacker's org. Pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` the same way and can archive/unarchive/create review stacks belonging to `OrgB` [6](#0-5) .

### Impact Explanation
This lets an attacker who only controls their own onboarded organization's webhook secret spoof GitHub events (push/pull_request/status/etc.) that are attributed to and acted upon a *different* organization's repository/stack inside the same Shipit instance, without ever holding credentials for `OrgB`. Depending on which handler is triggered this can force an unscheduled `GithubSyncJob` run, archive/unarchive a review stack, or otherwise mutate state for a repository the attacker has no legitimate relationship with — a cross-repository/cross-organization write triggered purely by a forged-but-"validly signed" webhook body.

### Likelihood Explanation
Requires the attacker to already have set up Shipit for at least one organization they control (so they know a valid `webhook_secret`), which is the normal, low-privilege "unprivileged w.r.t. other tenants" onboarding path for a multi-tenant Shipit install. No GitHub push access, no Shipit session, and no knowledge of `OrgB`'s secret are needed — only the ability to send an HTTP POST to `/webhooks` with a body they sign themselves.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive `repository_owner` from the exact same field the handler will use (`repository.full_name`'s owner segment) and reject the request (or re-verify with that owner's secret) if it disagrees with the owner used to select the signing secret. Equivalently, always verify the signature against the app config for `repository.full_name`'s owner rather than `repository.owner.login`/`organization.login`, so the two lookups are provably the same key.

### Proof of Concept
1. Attacker sets up Shipit stacks for their own org `OrgA` and is given (or knows) `Shipit.github(organization: 'OrgA').webhook_secret`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature-256` using `OrgA`'s known `webhook_secret` over the exact raw body and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` reads `"OrgA"` from `repository.owner.login`, `Shipit.github(organization: 'OrgA')` is fetched, and `verify_webhook_signature` succeeds [1](#0-0) .
5. `PushHandler#process` (and `Handler#stacks`) resolve the target repository from `repository.full_name = "OrgB/target-repo"` [3](#0-2) , and `stack.sync_github(expected_head_sha: ...)` is invoked for `OrgB`'s stack even though the signature only ever proved knowledge of `OrgA`'s secret.
