### Title
Webhook signature verification keys off `repository.owner.login`, while pull-request handlers resolve the target repository/stack from the independent `repository.full_name` field, allowing a payload signed with one organization's secret to mutate another organization's `PullRequest` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `params.dig('repository','owner','login')`, but `LabelCapturingHandler#repository` resolves the actual `Shipit::Repository` (and its stacks/pull request) using `params.repository.full_name`. Because these are two independently attacker-controlled JSON fields in a raw POST body, an attacker who owns "attacker-org" (and thus its `webhook_secret`) can set `repository.owner.login = "attacker-org"` for signature verification while setting `repository.full_name = "victim-org/prod-repo"` for actual repository resolution, causing `capture_labels` to call `pull_request.update!(labels: ...)` on a PullRequest belonging to `victim-org`.

### Finding Description
The broken binding: the organization whose secret verifies the signature (`repository_owner` = `params.dig('repository','owner','login')`) must equal the organization owning the stack/PullRequest that gets mutated (`params.repository.full_name`'s owner segment) — but nothing enforces this equality.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)`. [1](#0-0) 
2. If the attacker sets `repository.owner.login` to `"attacker-org"`, the signature is checked against attacker-org's own `webhook_secret` — which the attacker legitimately possesses (it's their own GitHub App). The signature check passes.
3. `Shipit::Webhooks.for_event('pull_request')` dispatches to `LabelCapturingHandler`, whose `ExplicitParameters` schema only `requires :repository do requires :full_name, String end` — it never validates or cross-checks `repository.owner.login`. [2](#0-1) 
4. `LabelCapturingHandler#repository` resolves the actual Shipit `Repository` record via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which just splits the string on `/` into `owner`/`name` and does a DB lookup — completely independent of the `repository.owner.login` field used for signing. [3](#0-2) [4](#0-3) 
5. `#opened_active_stack?` finds `stack` via `review_stack.stack` scoped to that resolved (victim) repository's `review_stacks`, and `#capture_labels` executes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` on victim-org's `PullRequest`. [5](#0-4) 

No existing guard catches this: `verify_signature` never compares the "owner" it used against the eventual `full_name` the handlers use, `drop_unhandled_event`/`check_if_ping` are unrelated, and the `ExplicitParameters` schema for this handler doesn't require or validate `repository.owner.login` at all.

### Impact Explanation
An attacker who legitimately controls their own GitHub App/webhook secret ("attacker-org") can forge a `pull_request` `opened` webhook where `repository.owner.login = "attacker-org"` (used only to pick the signing secret) but `repository.full_name = "victim-org/prod-repo"` (used to resolve the actual stack/PullRequest). This lets them overwrite `PullRequest#labels` on any victim tenant's repository that has an active `ReviewStack`, using only credentials they legitimately hold for their own tenant. This is a cross-tenant write into another organization's data via a payload authenticated only for the attacker's own organization — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is trivially repeatable against any victim repository/stack whose `owner/name` the attacker knows, with no rate limiting on the endpoint itself blocking repeated exploitation.

### Likelihood Explanation
Preconditions are modest: Shipit must be configured with (at least) two distinct GitHub App entries under `Shipit.github` (multi-org setup, as documented) — one is the attacker's own onboarded organization, and the victim's repository must have an active non-archived `ReviewStack`/`PullRequest`. The attacker needs no special access beyond controlling their own org's webhook secret (which they legitimately have) and knowing the victim repo's `owner/name`. Crafting the payload and HMAC signature requires only standard tooling. This is realistically exploitable in any Shipit deployment supporting multiple GitHub organizations/tenants.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler's `repository` resolution), enforce that the organization used to verify the signature is the same organization implied by `repository.full_name` — e.g., derive `repository_owner` from `repository.full_name.split('/').first` (or, conversely, validate that `full_name`'s owner segment equals `repository.owner.login`) before doing any lookup/mutation, rejecting mismatched payloads with a 422.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test "signature from attacker-org cannot mutate victim-org's PullRequest via mismatched owner/full_name" do
  # Setup: two GitHubApp configs, 'attacker-org' and 'victim-org', each with distinct webhook_secret
  # (stub Shipit.github_config or similar to register both orgs' secrets)

  victim_stack = shipit_stacks(:review_stack_for_victim_org) # active, non-archived ReviewStack owned by victim-org/prod-repo
  original_labels = victim_stack.pull_request.labels.dup

  payload = JSON.parse(payload(:pull_request_opened))
  payload["repository"]["owner"]["login"] = "attacker-org"       # used by verify_signature
  payload["repository"]["full_name"] = "victim-org/prod-repo"    # used by LabelCapturingHandler#repository
  payload["pull_request"]["labels"] = [{ "name" => "attacker-injected-label" }]
  body = payload.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_org_webhook_secret, body)

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  post :create, body: body, as: :json

  # Assert both sides of the binding: signature verified for attacker-org,
  # but PullRequest mutated belongs to victim-org
  assert_response :ok
  assert_not_equal original_labels, victim_stack.pull_request.reload.labels
  assert_includes victim_stack.pull_request.labels, "attacker-injected-label"
end
```
This demonstrates that `repository_owner` (attacker-org, verified side) != the actual owning organization of the mutated `PullRequest` (victim-org, resolved via `full_name`), yet the write succeeds.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
