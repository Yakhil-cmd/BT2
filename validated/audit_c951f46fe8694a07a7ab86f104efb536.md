### Title
Terminal escape-sequence filter in `gh repo read-file` misses 8-bit C1 control codes (CSI/OSC), allowing raw output to a TTY - ([File: pkg/iostreams/content.go], [File: pkg/cmd/repo/read-file/read_file.go])

### Summary
`iostreams.ContainsEscapeSequence` only searches for the 7-bit `ESC` byte (`0x1B`), while `iostreams.BinaryContentType` (built on `http.DetectContentType`) does not treat bytes `0x80`–`0x9F` as binary indicators. A file that embeds raw 8-bit C1 control bytes such as `0x9B` (CSI) or `0x9D` (OSC) alongside mostly-printable ASCII text passes both checks in `readFileRun` and is written verbatim to `opts.IO.ContentOut` even in TTY mode.

### Finding Description
In `pkg/cmd/repo/read-file/read_file.go`, `readFileRun` guards direct terminal output with two checks before calling `opts.IO.ContentOut.Write(file.Content)`: [1](#0-0) 

1. `iostreams.BinaryContentType(file.Content)` — wraps `http.DetectContentType`, which classifies content as binary only via known magic-number signatures or the WHATWG mimesniff control-byte heuristic that flags `0x00-0x08, 0x0B, 0x0E-0x1A, 0x1C-0x1F` as non-text. Bytes `0x80-0x9F` are not part of that heuristic, so a mostly-ASCII file containing them is classified `text/plain` and is not treated as binary: [2](#0-1) 
2. `iostreams.ContainsEscapeSequence(file.Content)` — searches only for the single byte `0x1B`: [3](#0-2) 

Because the classic 7-bit escape sequence is `0x1B` + a following byte (e.g. `0x1B [`), many terminal emulators also implement the ISO 6429/ECMA-48 8-bit single-byte equivalents (C1 control set), notably `0x9B` (CSI, equivalent to `ESC [`) and `0x9D` (OSC, equivalent to `ESC ]`). A file containing these raw single bytes never contains `0x1B` and is not flagged as binary, so it satisfies both guards and reaches `opts.IO.ContentOut.Write(file.Content)` in TTY mode at line 209, bypassing the intended escape-sequence protection entirely without needing `--allow-escape-sequences`.

Note: the other bypass ideas in the question do not hold up under inspection of this codebase:
- The "chunked/multi-byte splitting" concern does not apply here because `readFileRun` checks the entire `file.Content` buffer in one call, not a stream in chunks.
- A `BinaryContentType` misclassification that flags a text file with `0x1B` as binary in TTY mode causes a refusal (an error is returned before any write), not an exploit — that path is safe by construction: [4](#0-3) 

### Impact Explanation
An attacker who controls a repository file (public repo, fork, or any ref the victim points `gh repo read-file` at) can craft content that, when read interactively (TTY mode, default flags), is written raw to the victim's terminal and can trigger C1-based CSI/OSC sequences on terminals/configurations that process 8-bit controls (e.g. some `xterm`-derived terminals with 8-bit control processing enabled, or non-UTF-8 locale sessions). This matches the "OUTPUT_SAFETY" / forged-trusted-output impact class: terminal state manipulation, cursor/title manipulation, or misleading prompt injection on the victim's terminal.

### Likelihood Explanation
This requires: (1) the victim to run `gh repo read-file` interactively without `--allow-escape-sequences` (the default and documented usage), and (2) the victim's terminal emulator/locale to interpret 8-bit C1 control bytes as escape introducers, which is not universal (many modern UTF-8-locale terminals disable 8-bit control interpretation by default). This makes the bypass reproducible and code-confirmed, but its terminal-side trigger is environment-dependent, so real-world impact varies by terminal configuration.

### Recommendation
Broaden `ContainsEscapeSequence` (and any equivalent checks used for terminal-bound output) to also flag the C1 control range (`0x80`–`0x9F`), particularly `0x90` (DCS), `0x9B` (CSI), `0x9D` (OSC), `0x9E` (PM), and `0x9F` (APC), not just `0x1B`. Consider reusing `asciisanitizer`-based sanitization (already used in `pkg/iostreams/untrusted.go`) instead of a hand-rolled single-byte check, since that library is purpose-built to neutralize this class of sequence.

### Proof of Concept
Add to `pkg/iostreams/content_test.go`:
```go
func TestContainsEscapeSequence_MissesC1Codes(t *testing.T) {
    // Raw C1 CSI byte (0x9B), no 0x1B present anywhere.
    content := append([]byte("hello "), 0x9B)
    content = append(content, []byte("[31mdanger")...)

    // Not classified as binary because 0x9B is outside the mimesniff control range.
    _, isBinary := BinaryContentType(content)
    assert.False(t, isBinary)

    // Escape-sequence check misses the C1 introducer entirely.
    assert.False(t, ContainsEscapeSequence(content))
}
```
Combined with an integration test on `readFileRun` (using the existing `read_file_test.go` httpmock harness) that serves this content as `file.Content` with `IsStdoutTTY() == true` and no `--allow-escape-sequences`, asserting that `opts.IO.ContentOut.Write` is still called instead of an error being returned, demonstrates the bypass end-to-end.

// BinaryContentType reports whether content appears to be binary and, if so,
// returns its detected MIME type. Textual content returns ("", false).
func BinaryContentType(content []byte) (string, bool) {
	if len(content) == 0 {
		return "", false
	}
	ct := http.DetectContentType(content)
	if i := strings.IndexByte(ct, ';'); i >= 0 {
		ct = strings.TrimSpace(ct[:i])
	}
	if strings.HasPrefix(ct, "text/") {
		return "", false
	}
	return ct, true
}
