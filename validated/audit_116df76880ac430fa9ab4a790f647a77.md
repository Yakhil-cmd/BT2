### Title
KLAY Permanently Locked in Service-Chain Bridge via Recipient-Controlled ETH Rejection in `handleKLAYTransfer` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` pushes KLAY to `_to` using a low-level `.call.value()` and then hard-reverts the entire transaction if the call fails. Because the revert unwinds all state changes — including the nonce bookkeeping — the nonce is never consumed. If `_to` is a contract that unconditionally rejects ETH, the delivery can never succeed, the nonce can never advance past that slot, and the KLAY earmarked for that transfer is permanently irrecoverable from the bridge. There is no admin escape-hatch to skip a stuck nonce or rescue the locked funds.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

```
_lowerHandleNonceCheck(_requestedNonce)          // guard
_voteValueTransfer(_requestedNonce)              // sets closedValueTransferVotes[N] = true
_setHandledRequestTxHash(_requestTxHash)         // marks tx hash handled
handleNoncesToBlockNums[N] = _requestedBlockNumber
_updateHandleNonce(N)                            // advances lowerHandleNonce
emit HandleValueTransfer(...)

(bool ok, ) = _to.call.value(_value)("");        // ← push payment
require(ok, "handleKLAYTransfer: transfer failed"); // ← hard revert on failure
``` [1](#0-0) 

If `_to` is a contract whose fallback reverts, the `require` at line 99 causes the entire transaction to revert. Because Solidity reverts are atomic, every state mutation above — `closedValueTransferVotes[N]`, `handleNoncesToBlockNums[N]`, `lowerHandleNonce`, `handledRequestTx[hash]` — is rolled back to its pre-call value. [2](#0-1) 

The nonce slot `N` is therefore never durably consumed. `_updateHandleNonce` scans forward from `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0`; since slot `N` is always reverted before it can be written, `lowerHandleNonce` never advances past `N`. [3](#0-2) 

`_lowerHandleNonceCheck` only enforces `lowerHandleNonce <= _requestedNonce`, so higher nonces can still be processed, but the KLAY for nonce `N` is permanently stranded: the bridge holds it, no delivery path exists, and no recovery function is present in the contract. [4](#0-3) 

A second, owner-gated variant of the same class exists in `_payKLAYFeeAndRefundChange`: if `feeReceiver` is set to a contract that rejects ETH, every `requestKLAYTransfer` call reverts, completely halting inbound KLAY bridging. [5](#0-4) 

---

### Impact Explanation

- **Bridged KLAY permanently locked.** The bridge contract holds the KLAY but can never deliver it. No admin function (`setRunningStatus`, `lockKLAY`, operator management) provides a path to recover or redirect the stuck funds.
- **`recoveryBlockNumber` stalls.** `recoveryBlockNumber` is only advanced inside the `handleNoncesToBlockNums[i] > 0` loop. With slot `N` permanently unset, the recovery pointer never moves past `N`, potentially causing the off-chain relayer to re-scan and re-submit old events indefinitely. [6](#0-5) 

---

### Likelihood Explanation

The `_to` address is freely chosen by the caller of `requestKLAYTransfer` on the source chain. Any user — without any privilege — can supply a contract address whose fallback reverts. This can happen accidentally (sending to a contract without a `payable` fallback) or deliberately (deploying a purpose-built rejector). The bridge has no validation of `_to` before accepting the source-chain deposit. [7](#0-6) 

---

### Recommendation

Replace the push-payment pattern with a pull-payment (withdraw) pattern: record the failed delivery in a `pendingWithdrawals` mapping and let `_to` claim the KLAY separately. Alternatively, on delivery failure, emit an event and allow the bridge owner to redirect the stuck KLAY to a recovery address, rather than hard-reverting the entire handle transaction.

---

### Proof of Concept

1. Deploy `Rejector` on the destination chain:
   ```solidity
   contract Rejector { receive() external payable { revert(); } }
   ```
2. On the source chain, call `requestKLAYTransfer(address(rejector), value, "")` with `value` KLAY.
3. Bridge operators call `handleKLAYTransfer(txHash, from, address(rejector), value, nonce, blockNum, "")` on the destination chain.
4. The `.call.value(value)("")` to `Rejector` reverts → `require(ok, ...)` reverts the entire transaction.
5. Repeat step 3 indefinitely: every attempt reverts; `lowerHandleNonce` never advances past `nonce`; `value` KLAY remains in the bridge with no delivery or recovery path. [8](#0-7)
