### Title
Cross-org `Team` hijack via `Team.find_or_create_by!` skipping `organization` overwrite on existing rows - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id) { ... team.organization = params.organization.login }`, so `organization` is only set inside the create block, never on the find path. `WebhooksController#verify_signature` selects the verifying `GitHubApp` (and thus the webhook secret) from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) , meaning an attacker who controls their own configured GitHub org can sign a `membership` webhook that supplies an arbitrary `team.id`, colliding with a pre-existing victim team's `github_id`, and mutate that victim `Team`'s membership without ever holding the victim org's secret.

### Finding Description
The broken binding is: `Team#organization` (the value recorded on the row that gates `find_or_create_by!`'s lookup/mutation) should equal the organization whose `webhook_secret` verified the request that mutated the row. Concretely: `team.organization == params.organization.login` (the org that signed the request) must hold for every write to that row; instead, once a `Team` row exists, `find_or_create_by!` returns it unchanged (the block that sets `team.organization = params.organization.login` at [3](#0-2)  only executes on the create path), while `process` still calls `team.add_member(member)` / `team.members.delete(member)` at [4](#0-3) .

Exploit flow:
1. Attacker administers `attacker-org`, a GitHub org that is configured in Shipit's `github` app config (multi-org config is a supported feature, e.g. `test/dummy/config/secrets_double_github_app.yml`), and therefore knows `attacker-org`'s `webhook_secret`.
2. Victim `Team` row already exists (`github_id: 123, organization: "victim-org"`), e.g. from `Shipit.github_teams` setup used for `User#authorized?` at [5](#0-4) .
3. Attacker crafts a raw JSON body: `{"action":"added","team":{"id":123,"name":"x","slug":"x","url":"https://x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-controlled-user"}}` and signs it with `attacker-org`'s webhook secret (`sha1=HMAC(webhook_secret, raw_body)`), sending `X-Github-Event: membership`.
4. `verify_signature` resolves `repository_owner` from `organization.login` (no `repository` key in a real `membership` payload), calls `Shipit.github(organization: 'attacker-org').verify_webhook_signature(...)`, which succeeds since it was signed with `attacker-org`'s own secret [6](#0-5) .
5. `MembershipHandler#find_or_create_team!` finds the existing victim `Team` (`github_id: 123`); the create block does not run, so `organization` remains `"victim-org"`, but `process` still calls `team.add_member(member)`, inserting a `Membership` linking the attacker-controlled `User` to the victim's `Team` [7](#0-6) .

No existing guard prevents this: `verify_signature` only checks HMAC validity for whichever org is named in the payload — it never checks that the named org actually owns the `team.id`/`Team` row being mutated; `find_or_create_by!`'s block-based initialization is a known Rails idiom that silently skips attribute updates for already-existing records; the `params do ... end` schema (`ExplicitParameters`) validates types/presence only, not cross-org consistency.

### Impact Explanation
This is a cross-tenant authorization write: an attacker's own (correctly configured but otherwise unprivileged, low-trust) GitHub org can add arbitrary GitHub logins as members of a `Team` belonging to a *different* org, including teams listed in `Shipit.github_teams`. Since `User#authorized?` grants Shipit access to any user who is a member of any team in `Shipit.github_teams` [5](#0-4) , this is an escalation into `Shipit.github_teams` authorization — matching the "High" impact category (escalation into `Shipit.github_teams` authorization). It is repeatable against any `Team` row whose `github_id` the attacker can guess or observe, and requires no interaction from the victim org.

### Likelihood Explanation
Requires: (a) Shipit configured with more than one GitHub organization/app (each with its own `webhook_secret` known to that org's admins) — a supported, documented configuration; (b) attacker controls one such configured org and thus its `webhook_secret`; (c) a pre-existing `Team` row for the victim org (created via `teams:fetch` rake task or a prior legitimate `membership` webhook) whose `github_id` the attacker knows or can enumerate. Given these, the attack is a single crafted HTTP POST to `/webhooks` with a correctly computed HMAC — cheap and fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify the found/created team's `organization` matches `params.organization.login` before proceeding (raise/drop the event on mismatch), and/or scope the lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), so that a payload signed by `attacker-org` can never touch a `Team` row owned by `victim-org`.

### Proof of Concept
minitest plan (webhooks controller / integration level, no live GitHub):
1. Fixture: `shipit_teams(:shopify_developers)` with `organization: 'shopify'`, `github_id: 1` (already exists, per `test/fixtures/shipit/teams.yml`).
2. Configure a second org `evil` in test secrets/config with its own `webhook_secret` (mirroring `test/dummy/config/secrets_double_github_app.yml` pattern).
3. Build payload: `{ action: 'added', team: { id: 1, name: 'x', slug: 'x', url: 'http://x' }, organization: { login: 'evil' }, member: { login: 'attacker_user' } }.to_json`.
4. Compute `X-Hub-Signature` using `evil`'s `webhook_secret`.
5. POST to `/webhooks` with `X-Github-Event: membership` and that signature.
6. Assert `response` is `:ok` (signature accepted for `evil`).
7. Assert `Membership.count` increased by 1 and the new membership's `team` is `shipit_teams(:shopify_developers)`.
8. Assert `shipit_teams(:shopify_developers).reload.organization == 'shopify'` (unchanged) — proving the write was accepted under `evil`'s webhook secret while the team record still claims ownership by `shopify`, demonstrating the broken binding `team.organization == params.organization.login`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end
