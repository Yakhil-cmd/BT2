### Title
Attacker-controlled pool address in the swap route lets arbitrary contract code run inside the victim's strategy transaction and join the caller's signed auth tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The strategy swap path (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) accepts a fully caller-supplied `swap` payload. The router decodes pool and token addresses straight from that payload and invokes them via `env.invoke_contract`, with no allowlist or identity check. An attacker's contract therefore executes inside the victim's transaction, in the frame of the caller's `require_auth`, and can issue `token.transfer(victim, attacker, ...)` calls that Soroban records under the victim's signed authorization tree — draining any wallet token of the victim that simulation surfaced, not just the protocol positions. This is the on-chain analogue of the CVE's "attacker-controlled endpoint string reaches a dangerous sink": an attacker-controlled *address* reaches `invoke_contract`.

### Finding Description
`contracts/controller/src/strategies/swap.rs:36-38` hands the raw `StrategySwap` to the router inside a flash guard:

```rust
storage::with_flash_guard(env, || {
    let _ = router.execute_strategy(&controller, &amount_in, swap);
});
```

The flash guard blocks re-entry into the controller, but it does nothing about *what* the router invokes. In `contracts/swap-aggregator/src/venues/mod.rs:34-40` the venue is dispatched purely from the payload's opcode, and the `pool` address comes from the payload's `assets` registry:

```rust
match hop.venue {
    SwapVenue::Soroswap => soroswap::swap(&ctx),
    ...
};
```

Every adapter then calls `env.invoke_contract(&ctx.hop.pool, ...)`, e.g. `contracts/swap-aggregator/src/venues/soroswap.rs:55-88` (`get_reserves`, `swap`) and `contracts/swap-aggregator/src/venues/comet.rs:30-34`. There is no check that `hop.pool` is a genuine Soroswap/Aquarius/Comet contract — the venue byte and the pool address are both attacker-chosen and unrelated.

Crucially, `execute_strategy` opens with `sender.require_auth()`. For a direct user call that is the user's auth; for a controller strategy call the *user's* signature is on the outer `swap_collateral` invocation, and any `require_auth` the rogue pool triggers is recorded as a sub-invocation of the tree the user signs. The test at `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:195-227` demonstrates exactly this: a `RogueHopPool` whose `swap()` calls `token::Client::transfer(victim, attacker, amount)` succeeds in recording mode, the simulated auth tree contains the stolen transfer under the caller's `swap_collateral` entry, and in enforcing mode the move succeeds once the victim signs the simulation-produced tree (lines 259-268).

### Impact Explanation
Theft of user funds beyond the protocol position: the rogue pool can move any SEP-41 token the victim holds in their wallet (the test steals `WALLET_BALANCE` of an unrelated stellar-asset token, lines 68-70, 224-225), or trigger any other victim-authorized action simulation surfaces (NFT transfers, account operations). The protocol's own balances are protected by the measured `RouterOverspend`/`NoSwapOutput` deltas and the min-out check, so the damage is concentrated on the caller's wallet — matching "theft of user funds".

### Likelihood Explanation
Reachable by any unprivileged address: the victim only needs to submit `swap_collateral`/`swap_debt`/`repay_debt_with_collateral` with a route XDR built by the attacker — the same trust pattern as the CVE (a user connecting to an attacker-controlled endpoint/UI that provisions a malicious payload). The attacker's pool contract needs no privileges; `dispatch_hop` will invoke it as long as it implements the venue's function names. The only mitigation is that enforcing-mode auth rejects the transfer unless the victim signs the poisoned tree — but wallets commonly sign the exact tree simulation returns, and simulation records the rogue transfer under the legitimate-looking root (test lines 199-222). User interaction is required, consistent with the CVE's `UI:A`.

### Recommendation
Constrain which contracts a route can invoke: maintain an owner-curated allowlist of pool addresses per venue (or validate `pool` against a factory/registry read in the adapter before `invoke_contract`), and reject hops whose `token_in`/`token_out` are not the strategy's declared input/output tokens where the venue permits it. Additionally, routers could invoke venue pools through a dedicated sub-contract so that stray `require_auth` calls cannot attach to the caller's auth tree.

### Proof of Concept
Already encoded in the repo's own test harness:

1. Victim Alice has supplied USDC and holds an unrelated `wallet_token`.
2. Attacker deploys `RogueHopPool` (test file lines 51-72) whose `swap()` executes `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`, which calls `alice.require_auth()`.
3. Attacker hands Alice a route XDR naming that pool as `hop_pool` (`route_through_pool_stealing`, lines 111-125).
4. Alice calls `controller.swap_collateral(alice, account, USDC, amount, ETH, route)`; the controller authorizes its input transfer and calls `router.execute_strategy`; `dispatch_hop` invokes the attacker pool mid-transaction.
5. Simulation records the theft under Alice's `swap_collateral` auth entry; once she signs that tree, `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows Alice's wallet balance drops to 0 and the attacker receives `WALLET_BALANCE` (lines 259-268) — while the swap itself still completes normally with a fair output.
