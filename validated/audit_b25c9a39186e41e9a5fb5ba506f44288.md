### Title
CCMenu API token authorization bypasses stack scoping, allowing cross-stack deploy status disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-resolution method in a way that removes the `ApiClient`'s `stack_id` scoping check. An `ApiClient` token created for a single stack (e.g. via the CCMenu URL flow) can be replayed against any other stack ID to read that stack's deploy/CI status, breaking the binding between "the stack a token authorizes" and "the stack it actually touches."

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true`. In `app/controllers/shipit/api/base_controller.rb`, this scoping is enforced through the `stacks` helper: [1](#0-0) 

Any controller resolving `stack` via `stacks.from_param!(params[:stack_id])` correctly restricts lookups to the client's authorized stack when `current_api_client.stack_id?` is true.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoped helper entirely and query `Stack` directly: [2](#0-1) 

Permission enforcement for this controller is only `require_permission :read, :stack`, which is implemented purely as a permission-string check with no stack identity comparison: [3](#0-2) [4](#0-3) 

Since `check_permissions!` only checks whether `"read:stack"` is in the token's `permissions` array — it never compares `current_api_client.stack_id` to the stack being accessed — and `CCMenuController#stack` never applies the `stacks` scope, a token minted for stack A (via `ccmenu_url_controller.rb`, which explicitly creates a single-stack-scoped client) can be used with an arbitrary `stack_id` in the URL to fetch any other stack's CCMenu status. [5](#0-4) 

Before/after the equality the binding claims:
- Intended: `stack authorized by token == stack touched by request` (token.stack_id == requested stack_id, when stack_id? is true).
- Actual: `stack touched by request = Stack.from_param!(params[:stack_id])` regardless of `token.stack_id`.

### Impact Explanation
This grants unauthenticated (relative to the target stack) read access to another stack's deploy state, including latest deploy status, build label and last build time, rendered in the CCMenu XML response. Per the severity classification, "unauthenticated read of stack state, task streams or deploy output" is explicitly High severity. Any holder of a CCMenu URL/token for one stack can enumerate and monitor deploy status of every other stack in the Shipit instance.

### Likelihood Explanation
Likelihood is high: CCMenu tokens are distributed as plain query-string parameters (see `ccmenu_url_controller.rb`, which embeds `token` in a URL meant for CI-status-monitor tools), so they are commonly shared/exposed in less-trusted contexts (build dashboards, browser extensions). Exploitation only requires changing the `stack_id` segment of an otherwise valid, legitimately obtained CCMenu URL — no additional privilege or secret is required.

### Recommendation
Make `CCMenuController#stack` respect the `ApiClient` stack scope, e.g. reuse the base `stacks` helper (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id` before rendering.

### Proof of Concept
1. Create a stack-scoped API client for Stack A: `POST /ccmenu_url` (or via `CCMenuUrlController#fetch`) while authenticated to Stack A, obtaining a `token` and URL `.../api/<stack_A>/ccmenu.xml?token=<token>`.
2. Note the client created has `stack_id = StackA.id` and `permissions = ['read:stack']` (see `app/controllers/shipit/ccmenu_url_controller.rb:15-18`).
3. Send `GET /api/<stack_B>/ccmenu.xml?token=<token>` where `stack_B` is any other stack in the instance.
4. `authenticate_api_client` succeeds (token is valid). `require_permission :read, :stack` succeeds (`check_permissions!` only checks the permission string). `stack` resolves via `Stack.from_param!(params[:stack_id])` to Stack B, unrelated to the token's `stack_id`.
5. Response renders Stack B's deploy status/XML, despite the token only being authorized for Stack A.
