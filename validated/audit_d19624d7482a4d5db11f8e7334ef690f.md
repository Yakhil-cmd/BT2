This confirms the binding break: signature verification selects the GitHub App config using `repository.owner.login` (fallback `organization.login`), extracted from the same unauthenticated JSON body, while the actual repository acted upon by event handlers is resolved from a separate field, `repository.full_name` [1](#0-0) [2](#0-1) . Nothing ties `repository.owner.login` to `repository.full_name`'s owner segment.

### Title
Webhook signature verification authenticates the payload's `repository.owner.login` while handlers act on the independent `repository.full_name` field, enabling cross-organization forged webhook delivery when any onboarded org has no `webhook_secret` configured - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which HMAC secret) to verify against based on `repository_owner`, itself read from the untrusted request body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) [3](#0-2) . Downstream, `Handler#stacks` resolves the target repository/stack from a *different* payload field, `repository.full_name` [2](#0-1) . There is no engine-side check that these two fields are consistent (i.e., that `repository.full_name` actually belongs to the organization named in `repository.owner.login`).

`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's `webhook_secret` is blank/unset: `return true unless webhook_secret` [4](#0-3) . Shipit explicitly supports multiple organizations configured simultaneously, each with its own independent `webhook_secret` [5](#0-4) , and setup docs/examples routinely show `webhook_secret:` left blank [6](#0-5) , [7](#0-6) .

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature == organization owning the repository the handler writes to`. This engine breaks that equality:

- Verification org: `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository','owner','login')` [3](#0-2) .
- Acted-upon repository: `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [2](#0-1) .

An unprivileged attacker who can send an HTTP POST to the public `/github/webhooks` endpoint (no session, no `ApiClient` token required — this is exactly the endpoint the GitHub webhook is meant to hit, so it is unauthenticated by design until signature verification) can set `repository.owner.login` to any organization name onboarded to the Shipit instance whose `webhook_secret` happens to be blank, while setting `repository.full_name` to the fully-qualified name of a stack belonging to a *different*, secured organization. Because `verify_webhook_signature` short-circuits to `true` for the blank-secret organization regardless of the `X-Hub-Signature` header value, the request passes verification entirely, and the handler then acts on the victim stack named by `repository.full_name`, e.g. queueing `GithubSyncJob` for a `push` event [8](#0-7) .

### Impact Explanation
This crosses the "GitHub organization authenticated versus repository written" boundary explicitly called out as in-scope. Practical consequences depend on the handler invoked but include forging `push` events to trigger `GithubSyncJob` against a stack the attacker does not control, forging `status`/`check_suite` events to manipulate `Status` records used for merge-gating, or forging `membership` events to add/remove `Team`/`Membership` records (as exercised in `WebhooksControllerTest`'s `:membership` tests) [9](#0-8) . Membership manipulation can escalate into `Shipit.github_teams`-based authorization, and forged sync/status events can influence merge/deploy decisions — both map to the defined High-severity impact categories.

### Likelihood Explanation
Exploitability is conditional: it requires the Shipit instance to be configured with more than one GitHub organization (a documented, supported configuration, see `test/dummy/config/secrets_double_github_app.yml`) and for at least one of those organizations to have an unset `webhook_secret` — a state the project's own example configs show as a normal/default value. Given that omitting `webhook_secret` is presented in setup docs as an acceptable/no-op case rather than a hard requirement, this is a realistic misconfiguration, not a purely theoretical one.

### Recommendation
Do not let untrusted payload fields decide which secret authenticates the request without cross-validating them: after selecting `repository_owner` and its `GitHubApp`, verify that `payload.dig('repository','full_name')` actually starts with `"#{repository_owner}/"` before dispatching to handlers, or resolve the app/secret from the locally-stored `Repository`/`Stack` record rather than from attacker-supplied JSON. Additionally, treat a blank/missing `webhook_secret` as "reject all webhooks for this organization" rather than "accept any signature," removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (no `webhook_secret`, per the documented default) and `OrgB` (has a `webhook_secret` and an active stack `OrgB/victim-repo`).
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: push`, an arbitrary/garbage `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` unconditionally because `OrgA`'s `webhook_secret` is blank [4](#0-3) .
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [2](#0-1) , [10](#0-9) , and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha` for `OrgB`'s stack — despite the request never being signed by `OrgB`'s secret.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
