### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the event is processed using unrelated payload fields (`repository.full_name`, or nothing at all) — allowing a webhook signed with one organization's secret to write commit statuses / trigger syncs for a different organization's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`). Once the signature check passes, the handler that actually performs the write (`PushHandler`, `StatusHandler`, PR handlers, `MembershipHandler`) reads a *different* field from the same untrusted JSON body to decide what to act on: `repository.full_name` (owner/name pair, re-parsed independently) or, in `StatusHandler`, nothing scoping the repository at all. Nothing enforces that the field used for signature verification and the field(s) used for the write are the same repository/organization. This is the exact bug class from the report: a value acted upon is never actually covered/bound by what the signature verified.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signing/HMAC secret used to authenticate the webhook is chosen solely from `repository.owner.login` (or `organization.login`). This value establishes only "this payload is signed by organization X's registered GitHub App secret" — it says nothing about which repository the event content actually refers to.

After signature verification succeeds, `create` dispatches to handlers with the full, attacker-controlled JSON body: [3](#0-2) 

The handlers then determine *which repository/stack to mutate* using a completely independent field, `repository.full_name`, parsed again from the same body with no cross-check against `repository.owner.login`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` uses `stacks` (i.e., `repository.full_name`) to sync arbitrary stacks: [5](#0-4) 

Even more directly exploitable, `StatusHandler#process` doesn't scope by repository at all — it looks up commits **globally by SHA**: [6](#0-5) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

The PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) similarly derive the acted-upon repository from `params.repository.full_name`, independent of the org used for signature verification: [7](#0-6) 

**The broken binding, stated as an equality that the code assumes but never enforces:**
`organization used to select webhook_secret for HMAC verification (repository.owner.login)` == `organization/repository whose Stack/Commit state is mutated (repository.full_name)`

Before the attack: these two fields naturally match because GitHub always sends a consistent, single-repository payload.
After the attack (forged payload): an attacker who is a legitimate GitHub App admin/owner for *any* organization onboarded to this Shipit instance (their own tenant `attacker-org`, which is a normal, supported multi-org configuration per `docs/setup.md` and `secrets_double_github_app.yml`) knows that org's `webhook_secret`. They can POST a `status` (or `push`, or PR) webhook where:
- `repository.owner.login` = `attacker-org` (so `Shipit.github(organization: repository_owner)` picks the attacker's own app/secret, and the HMAC verifies successfully), and
- `repository.full_name` / `sha` refer to a victim stack/commit belonging to a completely different organization also hosted on the same Shipit instance.

The signature check passes because it is checking a secret the attacker legitimately controls; the write, however, executes against a resource that the signature never covered.

### Impact Explanation
This breaks a deployment-trust binding for an unauthenticated remote attacker (with respect to the *target* organization) and produces a cross-tenant write:
- Via `StatusHandler`, an attacker can inject arbitrary CI status (`success`/`failure`, `context`, `description`, `target_url`) onto any commit in the system whose SHA they know (SHAs are visible on the public GitHub PR/commit or the Shipit UI), regardless of which repo/org owns that commit. Shipit's continuous-deployment gating relies on commit statuses (see `README.md` `review.checks` / CI status references), so a forged "success" status can be used to make a stack appear deployable/pass safety checks it should not — this is a path to an **unauthorized deploy**, one of the explicitly accepted impacts.
- Via `PushHandler`, a forged payload can trigger `GithubSyncJob` for arbitrary victim stacks (still a cross-org action executed on behalf of an unrelated tenant using another tenant's credentials).
- Via PR handlers, arbitrary victim `ReviewStack`s can be archived/unarchived/created based on forged `pull_request`/`repository.full_name` data signed by an unrelated org's secret.

### Likelihood Explanation
Likelihood is Medium-to-High in any multi-tenant Shipit deployment (explicitly supported, see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`'s multi-org guidance): any organization admin who can create/configure their own GitHub App on the shared Shipit instance (a standard, low-privilege, self-service action — not an admin of Shipit itself) automatically obtains a valid `webhook_secret` usable to sign requests, and can then target any other tenant's repositories/commits by simply changing the `repository.full_name` / `sha` fields in the JSON body while keeping `repository.owner.login` set to their own org.

### Recommendation
Bind the identity used for signature verification to the identity used for the write. Concretely, after verifying the signature, re-derive `repository_owner`/`organization` from the exact same struct used to resolve the target repository (`repository.full_name`), and reject the request if they don't match — i.e., require `repository.full_name.split('/').first == repository.owner.login` (or `organization.login`) before dispatching to handlers. Additionally, `StatusHandler` should scope `Commit.where(sha: params.sha)` by the verified repository/stack rather than doing a global, unscoped lookup.

### Proof of Concept
1. Attacker registers/administers their own GitHub organization `attacker-org` on the shared Shipit instance (a supported multi-org config, see `test/dummy/config/secrets_double_github_app.yml`), obtaining `webhook_secret_A`.
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<victim commit sha, publicly known>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` using their own known secret.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and `verify_webhook_signature` succeeds because the attacker knows that org's secret: [1](#0-0) 
5. `StatusHandler#process` then executes `Commit.where(sha: params.sha)` — matching the victim's commit belonging to an entirely different org/stack — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto the victim's commit: [6](#0-5)
