### Title
`handleKLAYTransfer()`, `handleERC20Transfer()`, and `handleERC721Transfer()` Execute Asset Transfers When Token/KLAY Lock Is Active — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The bridge contracts define per-asset lock flags (`isLockedKLAY`, `lockedTokens[token]`) and enforce them only on the *request* (inbound) path. The *handle* (settlement/outbound) functions — `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — carry no lock-state check, so a bridge operator can settle transfers and move assets out of the bridge even while the owner has activated the lock.

---

### Finding Description

`BridgeTransferKLAY` exposes two modifiers:

```solidity
modifier lockedKLAY   { require( isLockedKLAY, "unlocked"); _; }
modifier unlockedKLAY { require(!isLockedKLAY, "locked");   _; }
```

`_requestKLAYTransfer` (the user-facing deposit path) correctly carries `unlockedKLAY`, so new cross-chain requests revert when the flag is set. However, `handleKLAYTransfer` — the operator-facing settlement function that actually sends KLAY to the recipient — has no such guard:

```solidity
function handleKLAYTransfer(…)
    public
    onlyOperators   // ← only access control
    nonReentrant
{
    …
    (bool ok, ) = _to.call.value(_value)("");   // KLAY leaves the bridge
    require(ok, "handleKLAYTransfer: transfer failed");
}
```

The same asymmetry exists for ERC-20 and ERC-721 tokens. `_requestERC20Transfer` carries `onlyUnlockedToken(_tokenAddress)` and `_requestERC721Transfer` carries `onlyUnlockedToken(_tokenAddress)`, but neither `handleERC20Transfer` nor `handleERC721Transfer` checks `lockedTokens[_tokenAddress]` before minting or transferring tokens to the recipient.

---

### Impact Explanation

When the bridge owner calls `lockKLAY()` or `lockToken()` — typically as an emergency pause to stop all asset movement — any bridge operator can still call `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` and cause the bridge to:

- Send native KLAY to an arbitrary `_to` address (`_to.call.value(_value)("")`), or
- Mint ERC-20 / ERC-721 tokens to an arbitrary `_to` address (`ERC20Mintable.mint`, `ERC721MetadataMintable.mintWithTokenURI`), or
- Transfer held ERC-20 / ERC-721 tokens out of the bridge (`IERC20.safeTransfer`, `IERC721.transferFrom`).

This constitutes an **unauthorized transfer of KLAY and bridged assets** from system-managed bridge funds, directly matching the allowed-impact gate.

---

### Likelihood Explanation

Bridge operators are a semi-trusted role set by the owner. The lock mechanism exists precisely for emergencies (e.g., a bridge exploit in progress). During such an event, a compromised or malicious operator can exploit the missing guard to drain the bridge of KLAY or tokens before the owner can react further. The call requires only the `onlyOperators` check, which any registered operator satisfies.

---

### Recommendation

Add the appropriate lock guard to each handle function:

**`BridgeTransferKLAY.sol` — `handleKLAYTransfer`:**
```solidity
function handleKLAYTransfer(…)
    public
    onlyOperators
    unlockedKLAY      // ← add this
    nonReentrant
{ … }
```

**`BridgeTransferERC20.sol` — `handleERC20Transfer`:**
```solidity
function handleERC20Transfer(…, address _tokenAddress, …)
    public
    onlyOperators
    onlyUnlockedToken(_tokenAddress)   // ← add this
{ … }
```

**`BridgeTransferERC721.sol` — `handleERC721Transfer`:**
```solidity
function handleERC721Transfer(…, address _tokenAddress, …)
    public
    onlyOperators
    onlyUnlockedToken(_tokenAddress)   // ← add this
{ … }
```

---

### Proof of Concept

1. Owner calls `lockKLAY()` → `isLockedKLAY = true`. Any subsequent call to `_requestKLAYTransfer` reverts with `"locked"`.
2. A bridge operator calls `handleKLAYTransfer(txHash, from, victimAddr, 1 ether, nonce, blockNum, "")` directly.
3. `handleKLAYTransfer` checks only `onlyOperators` (passes) and `nonReentrant` (passes). It never reads `isLockedKLAY`.
4. `_to.call.value(1 ether)("")` executes — 1 KLAY leaves the bridge to `victimAddr` despite the lock being active.
5. The same sequence applies to `handleERC20Transfer` (mints or transfers ERC-20) and `handleERC721Transfer` (mints or transfers ERC-721) for any token whose `lockedTokens[token] == true`.
