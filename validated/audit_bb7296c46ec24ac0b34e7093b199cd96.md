## Analysis

The report's bug class is: a value computed/derived diverges from the binding that's supposed to constrain it — specifically here, "a stack a token authorises versus a stack it touches."

In `Shipit::Api::BaseController`, the authoritative pattern for stack-scoped API tokens is: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the `ApiClient` is stack-scoped, and `stack` resolves the requested stack only from within that authorized set.

However, `Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It resolves the stack directly via `Stack.from_param!(params[:stack_id])` — never consulting `current_api_client.stack_id`. The `require_permission :read, :stack` check only verifies the token's `permissions` array contains `read:stack` (see `ApiClient#check_permissions!`): [3](#0-2) 

It does not verify that the requested `stack_id` matches the token's authorized stack. So a stack-scoped `ApiClient` (e.g. fixture `here_come_the_walrus`, which is scoped to the `shipit` stack — [4](#0-3) ) can be used to fetch CCMenu status (deploy state, last build status/label, activity) for **any other stack in the installation**, not just the one it was authorized for, simply by changing `stack_id` in the URL.

### Title
Stack-scoped API tokens can read CCMenu status of any stack, bypassing `ApiClient#stack_id` authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single `stack` via `belongs_to :stack, optional: true`, and `Api::BaseController#stacks`/`#stack` enforce this scope for every other stack-nested API endpoint (deploys, rollbacks, tasks, locks, merge requests). `Api::CCMenuController` however defines its own `stack` private method that calls `Stack.from_param!(params[:stack_id])` directly, ignoring `current_api_client.stack_id`. The only authorization check performed, `require_permission :read, :stack`, validates solely that the permission string `read:stack` is present on the token — it is stack-agnostic. This breaks the equality that should hold for every stack-nested API endpoint: `stack_touched == stack_authorized_by_token`.

### Impact Explanation
An attacker holding any valid stack-scoped API token with `read:stack` (a low-privilege, narrowly-issued credential, e.g. the one self-serviced through `CCMenuUrlController`) can enumerate and read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status) of every stack in the Shipit installation, including stacks they were never granted access to. This is an unauthorized read of stack state through a scope/authorization binding that the rest of the API correctly enforces everywhere else.

### Likelihood Explanation
High. No special privileges beyond possessing any one valid, stack-scoped API token are required, and the endpoint is a standard unauthenticated-by-session, always-mounted route (`/api/stacks/*stack_id/ccmenu`). The only "attack" is substituting the `stack_id` route segment.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` collection inherited from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the stack actually served is always constrained to the stack(s) the authenticated `ApiClient` is authorized for.

### Proof of Concept
1. Create/obtain a stack-scoped token, e.g. fixture `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`), analogous to a token generated by `CCMenuUrlController#client` for a specific stack.
2. Send `GET /api/stacks/<other-owner>/<other-repo>/<other-env>/ccmenu?token=<here_come_the_walrus token>` for a stack the token was never scoped to.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (permission array contains `read:stack`), and `stack` resolves `Stack.from_param!` against the attacker-supplied `stack_id` rather than the token's own `stack_id`, returning that other stack's CCMenu XML (build status, activity, lock state) — data outside the token's authorized scope.
