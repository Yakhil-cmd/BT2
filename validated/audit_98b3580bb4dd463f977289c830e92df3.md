### Title
Unauthenticated cross-organization webhook forgery via org-keyed signature verification — forged CI status can trigger deploy scheduling on an unrelated stack - (lib/shipit/github_app.rb, app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for verifying an incoming webhook based on an **unverified field taken from the same request body** it is about to authenticate. Because a per-organization `webhook_secret` can legitimately be left unset (the shipped example configs default to `webhook_secret: # nil`), and `GitHubApp#verify_webhook_signature` treats a blank secret as "always valid", an attacker can pick any configured organization that has no secret, and the request is accepted regardless of its actual content. The event is then dispatched to handlers that pick their target `Stack`/`Commit` from *other, independent* fields of that same forged body — breaking the binding between "the organization whose credential authenticated the request" and "the repository/commit that gets written to".

### Finding Description
`WebhooksController#verify_signature` computes the signing organization purely from JSON supplied by the caller, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GitHubApp` instance configured from `secrets.github[organization]` [3](#0-2) . Multi-organization deployments are an explicitly supported, documented configuration (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), each org with its own independent `webhook_secret`.

`GitHubApp#verify_webhook_signature` intentionally short-circuits when that org's secret is not configured: [4](#0-3) 

The shipped example secrets file documents `webhook_secret:` as commented `# nil` by default for every organization block [5](#0-4) , meaning it is normal/expected for some configured organizations in a multi-org Shipit deployment to have no secret set (e.g. because that org doesn't use webhooks yet, or was left at the default while another org's secret was configured).

Once `verify_signature` passes — either because the impersonated org genuinely has no secret, or trivially, if it does have one, because the attacker (a legitimate member/webhook admin of that lower-trust org) can sign with that org's own real secret — `WebhooksController#create` dispatches the **entire attacker-supplied body** to the matching handler: [6](#0-5) 

Handlers, however, locate the record to mutate using unrelated fields of that same body, with no re-check that they belong to the organization that was used for signature verification. `Handler#stacks`/`#repository_name` resolve the target `Stack` from `payload.dig('repository','full_name')` [7](#0-6) , a completely independent value from `repository.owner.login`/`organization.login` used for verification. Worse, `StatusHandler` doesn't even scope by repository — it matches purely on commit SHA across the entire instance: [8](#0-7) 

This creates a `Status` record from fully attacker-controlled `state`/`description`/`target_url`/`context` on any commit sharing that SHA, which triggers CI-gating and continuous-delivery scheduling logic: [9](#0-8) 

The broken binding is exactly "an organization that authenticated versus the repository that is written": the signature check authenticates against organization X's (possibly absent) secret, but the mutation is applied to a stack/commit belonging to organization Y, chosen independently by the same untrusted payload.

### Impact Explanation
An attacker who can reach the public `/github/webhooks` endpoint and knows (a) any organization name configured in `Shipit.secrets.github` that has no `webhook_secret` set, and (b) the SHA of a commit tracked by a target stack (public information for public repos, or visible in the Shipit UI), can forge a `status` (or `push`/`check_suite`) event that is accepted without any valid GitHub signature, and have it applied to a stack outside the impersonated organization. For `status` events this can flip a commit's CI status to `success`, satisfying `ci.require` gating and triggering `schedule_continuous_delivery`, i.e. causing an unauthorized deploy to be scheduled for a commit that never actually passed CI. This matches the "unauthorized deploy" High-impact category.

### Likelihood Explanation
Requires no `ApiClient` token, no GitHub App private key, and no legitimate write access to the target repository — only knowledge of an organization name configured in this Shipit instance with an unset `webhook_secret` (a state the project's own example configuration ships as the default), plus a commit SHA. This is a purely unprivileged, network-reachable path with no attacker-side secret needed against the target org.

### Recommendation
Verify the webhook signature using the secret associated with the actual target repository/organization derived from a trusted source (e.g. re-resolve and cross-check `repository.full_name`'s owner against the same key used for verification), and refuse to accept any webhook when the resolved organization has no `webhook_secret` configured (fail closed rather than fail open). Additionally, scope `StatusHandler`'s commit lookup by the payload's repository, not just SHA, to remove the cross-repository ambiguity.

### Proof of Concept
1. Shipit is configured with two organizations, `LowTrustOrg` (no `webhook_secret` set) and `HighTrustOrg` (deploys production, tracked in a stack with a known commit `abc123...`).
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "LowTrustOrg"}, "full_name": "LowTrustOrg/whatever"},
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "LowTrustOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of any (missing) `X-Hub-Signature` header.
4. `StatusHandler#process` finds `Commit.where(sha: "abc123...")` — the commit actually belonging to `HighTrustOrg`'s stack — and creates a `Status` with `state: "success"` for it, potentially satisfying `ci.require` and triggering continuous-delivery scheduling for that stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
