Confirmed: `WebhooksController#verify_signature` selects the HMAC secret using `repository_owner`, which is read from the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) . The actual event handling, however, resolves the target `Repository`/`Stack` from a completely different, independently attacker-controlled payload field: `payload.dig('repository', 'full_name')` [2](#0-1) , which is then split on `/` and looked up directly with no ownership cross-check against `repository_owner` [3](#0-2) .

### Title
Webhook signature verified against attacker's own organization while the payload's `repository.full_name` field is used unchecked to select the victim stack that is mutated - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` in `config/secrets.yml` (`docs/setup.md`, `config/secrets.development.example.yml`) [4](#0-3) . `Shipit.github(organization: ...)` picks the `GitHubApp` instance (and thus the secret used for HMAC verification) purely from the string found at `repository.owner.login` in the JSON body the requester supplies [5](#0-4) . Because this "owner" field and the `repository.full_name` field used later to select which `Stack` gets acted upon are two independent, attacker-supplied strings in the same JSON body, an org administrator who legitimately knows their own org's `webhook_secret` (they configure/receive it when the GitHub App is set up for their org) can forge a signed payload where `repository.owner.login` = their own org (so the signature check passes with a secret they know) but `repository.full_name` = a victim org/repo pair, causing the event to be dispatched against the victim's `Stack`.

### Finding Description
The binding that should hold is: **the organization whose secret authenticated the webhook == the organization that owns the repository being written to**. Concretely:
- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it solely to select which per-organization `webhook_secret` to verify the HMAC against [6](#0-5) .
- Once verification passes, `create` hands the *entire raw JSON* (`params = JSON.parse(request.raw_post)`) to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) .
- Every handler (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolves the target repository via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a *different* JSON path than the one used for signature-org selection [2](#0-1) .
- `Repository.from_github_repo_name` splits this string on `/` and does a direct `find_by(owner:, name:)` lookup, with no verification that this owner matches `repository_owner` used earlier for signing, and no check that the org that owns the webhook secret is the org that owns this repository [3](#0-2) .

Just like the NFTPool bug — where a state-changing operation (`safeTransferFrom`) was permitted by the contract's public API, but a second piece of state (`ownerToId`) that other logic implicitly trusted to reflect true ownership was never re-validated — here the webhook endpoint permits any organization it recognizes to submit a signed request, but the code implicitly trusts that `repository.full_name` inside that same signed body belongs to the authenticating organization, without ever checking that invariant.

### Impact Explanation
An attacker who administers (or is a member with knowledge of the webhook configuration for) one org onboarded to a multi-org Shipit deployment can forge webhook deliveries (push, status, check_suite, membership, pull_request, etc.) that are accepted as authentic for a *different* org's repository/stack. Depending on the handler this can:
- Trigger `GithubSyncJob`/`sync_github` on a victim's stack with a forged `after` SHA, causing Shipit to fetch and treat an attacker-chosen commit as the head of the victim's branch (`PushHandler#process`) [8](#0-7) .
- Inject forged commit statuses/check-runs against a victim's commits, manipulating CI/merge-gating decisions used by `MergeRequest#reject_unless_mergeable!` and deploy safety checks.
- Manipulate merge-queue/pull-request state machines for a repository the attacker does not own.

This crosses the "unauthorized deploy/rollback" / "cross-repository writes" bar defined in scope, since it lets an entity authenticated for org A cause state changes on org B's stack purely by controlling unrelated fields of a self-signed JSON payload.

### Likelihood Explanation
Requires the deployment to be configured with multiple GitHub organizations (a documented, supported configuration) and requires the attacker to be a legitimate administrator of at least one onboarded org (i.e., they know that org's `webhook_secret`, which they configure/receive when their org's GitHub App is set up). No compromise of Shipit's session, `ApiClient` tokens, or `api_clients_secret` is needed — only knowledge of one's own org's webhook secret and the ability to POST directly to the `/webhooks` endpoint (webhooks are plain HTTP POSTs, not restricted to GitHub's IP ranges by this engine's code).

### Recommendation
After computing `repository_owner` and selecting the `GitHubApp`, re-derive the target repository/organization strictly from the same trusted field used for signature selection (or verify that `repository.full_name`'s owner segment equals `repository_owner`) before dispatching to any handler. Reject the webhook if these two organization identifiers diverge.

### Proof of Concept
Conceptual scenario (cannot be executed without a live multi-org deployment and a real second org's webhook secret, so this is presented as a reasoning-level PoC consistent with the codebase logic found):
1. Deployment configured with two orgs, `orgA` (attacker-administered, secret known to attacker) and `orgB` (victim), per `test/dummy/config/secrets_double_github_app.yml` [9](#0-8) .
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeef..."
}
```
3. Attacker computes `X-Hub-Signature` using `orgA`'s known `webhook_secret` over the exact body.
4. `verify_signature` calls `Shipit.github(organization: 'orgA')` and successfully verifies the signature [10](#0-9) .
5. `create` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name('orgB/victim-repo')` — org B's stack — and calls `stack.sync_github(expected_head_sha: 'deadbeef...')` on it [8](#0-7) , [2](#0-1) .

Note: I was not able to find any code in the reviewed paths that cross-checks `repository.owner.login` against `repository.full_name`'s owner segment, confirming the gap. I could not execute this against a live instance since I have no filesystem/terminal access; a Devin session with the actual multi-org test fixtures (`test/dummy/config/secrets_double_github_app.yml`) would be needed to run a concrete Rails test proving cross-org dispatch.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
