## Title
Cross-Stack CI-Status Disclosure via `ApiClient` stack-scope bypass in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The bug-class hint (an `initializer()`/state binding that isn't re-verified after being established once) maps here to an authorization binding that is created once (an `ApiClient`'s `stack_id`) but never re-checked at the point where the stack is actually resolved for a request. `Api::BaseController` establishes the "stack a token authorizes" via the `stacks` helper, which restricts the queryable set to `current_api_client.stack_id` when that scope is set. `Api::CCMenuController` overrides the `stack` accessor and resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping helper, so the equality "stack authorized == stack touched" is broken.

### Finding Description
`Shipit::Api::BaseController` defines the scoping primitive that all other stack-scoped API controllers rely on: [1](#0-0) 

`Api::StacksController#stack` (and other stack-scoped API resources) resolve the target `Stack` through this `stacks` method, so a client with `stack_id` set can only ever resolve to its own stack; any other stack ID raises `RecordNotFound`.

`Api::CCMenuController`, however, defines its own `stack` method that does not go through `stacks`: [2](#0-1) 

It only enforces the coarse `require_permission :read, :stack` permission check: [3](#0-2) [4](#0-3) 

`check_permissions!` only validates that the permission string (`read:stack`) is present in the client's `permissions` array — it never inspects `stack_id`. The `stack_id` binding is enforced solely by the `stacks` helper in `BaseController`, which `CCMenuController` does not use.

This matters because `ApiClient` records are explicitly designed to be scope-limited to a single stack, as shown by `CCMenuUrlController`, which is the normal/expected way such tokens are minted (scoped to the stack whose CI badge is being embedded): [5](#0-4) 
and by the `here_come_the_walrus` API-client fixture, which is stack-scoped with `read:stack` permission and is asserted elsewhere in the codebase (`Api::StacksController` tests) to be restricted to its own stack: [6](#0-5) [7](#0-6) 

The route is public/unauthenticated at the session level (only bearer-token/basic-auth via the token itself), reachable at: [8](#0-7) 

**Binding broken (equality):**
`stack authorized by ApiClient.stack_id` == `stack resolved by CCMenuController#stack` — the right-hand side ignores the left-hand side entirely, unlike every other stack-scoped API endpoint that goes through `stacks`.

### Impact Explanation
An attacker who legitimately holds *any* `read:stack`-scoped `ApiClient` token — even one deliberately minted for a single, low-sensitivity stack via the CCMenu embed feature (`CCMenuUrlController`) — can use that same token to query `GET /api/1.0/stacks/:owner/:repo/:environment/ccmenu` for **any other stack** in the installation, including private/internal ones the token was never meant to see. The CCMenu XML response discloses stack activity/build status and deploy metadata (`activity`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), which is an unauthenticated read of stack/task state for repositories the caller has no authorization for. This matches the "High" impact category: escalation into unauthorized read of stack state via a broken token-to-stack scoping boundary, without needing a Shipit session, GitHub credentials, or repository write access — only possession of a legitimately-scoped, low-privilege `ApiClient` token.

### Likelihood Explanation
Likelihood is high for any installation using the CCMenu integration feature (a supported, documented feature for exposing build status to CI dashboard tools like CCMenu clients). Any user who can create a stack-scoped API client (which is a normal, low-privilege self-service action any authenticated Shipit user can trigger via `CCMenuUrlController#fetch`) automatically obtains a token they can then replay against arbitrary `stack_id` values in the URL, with no additional exploitation complexity beyond changing the path segment.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the same scoped `stacks` helper used by `BaseController` and other API controllers, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that `current_api_client.stack_id` is honored exactly as it is for `Api::StacksController`, `Api::TasksController`, etc. Add a regression test asserting that a stack-scoped client cannot read another stack's `ccmenu` output.

### Proof of Concept
1. As any authenticated Shipit user, visit a stack you have access to and load `GET /ccmenu/<owner>/<repo>/<env>` (`CCMenuUrlController#fetch`); this creates/returns a `read:stack`-permission `ApiClient` scoped to that one stack (`stack_id` set) and returns its `authentication_token`.
2. Take that token and issue: `GET /api/1.0/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu` using HTTP Basic Auth with the token as password (per `Api::BaseController#authenticate_api_client`).
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks` helper, the request succeeds and returns the *other* stack's CI/build-status XML, even though the token's `stack_id` only authorizes the original stack — contrast this with the same token used against `GET /api/1.0/stacks/<other_owner>/<other_repo>/<other_env>` (the regular `Api::StacksController#show`), which correctly 404s because it goes through `stacks.from_param!`.
