### Title
`Api::CCMenuController` lets an `ApiClient` token scoped to one stack read the CCMenu build status of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` scopes every resource lookup to the stacks an `ApiClient` is authorized for via `stacks`/`stack`, but `Api::CCMenuController` overrides `stack` with an unscoped lookup, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
`Api::BaseController` defines the trust boundary for every other API endpoint: a request is only allowed to touch a stack if that stack is included in `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `stack` looks the requested `params[:stack_id]` up through that scoped relation: [1](#0-0) 

`Api::CCMenuController` reuses the same `require_permission :read, :stack` before_action (which only checks that `"read:stack"` is present in `current_api_client.permissions`, without any reference to which stack), but it overrides `stack` with a direct, unscoped lookup by the URL parameter: [2](#0-1) 

`ApiClient#check_permissions!` only validates the permission string, never the stack scope: [3](#0-2) 

So the equality that should hold is:
`stack a token authorizes (current_api_client.stack_id, enforced via BaseController#stacks/#stack)` == `stack the request actually touches (Api::CCMenuController#stack)`.

Before the attacker's request: an `ApiClient` created and scoped to `stack_id = A` (e.g. via the `here_come_the_walrus` fixture / `ApiClientsController`) can only read/write stack A through every other endpoint that relies on `BaseController#stack`, per the fixture and tests: [4](#0-3) [5](#0-4) 

After the attacker's request: using that same scoped token (which only holds `read:stack`), a request to `Api::CCMenuController#show` with `stack_id: B` (any other stack) succeeds and returns stack B's build status, because `CCMenuController#stack` never consults `current_api_client.stack_id`: [6](#0-5) 

The controller also accepts the token via a plain query-string parameter (`params[:token]`) rather than only via Basic Auth, widening the credential's exposure surface, which is how it's designed to be embedded in a CCMenu URL: [7](#0-6)  and confirmed by the test asserting query-string authentication works: [8](#0-7) .

### Impact Explanation
This is an authorization-scope escalation: a token that is only supposed to authorize read access to one stack (or is otherwise permission-limited) can be replayed to read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) of any other stack in the Shipit instance, without ever holding a token scoped to that stack. This matches the "unauthorized read of stack state" category — an api_client credential leaked or intended for one stack's CCMenu widget becomes a cross-stack read oracle.

### Likelihood Explanation
Likelihood is high given normal usage: `CCMenuUrlController` actively mints and hands out these tokens (e.g. `here_come_the_walrus`-style scoped clients or unscoped "CCMenu Client" tokens) for embedding in CI dashboards/IRC bots, and the token is transmitted in a URL query string, which is a lower-security channel (browser history, referrer headers, proxy/CDN logs) than an Authorization header. Any leak of one such URL/token, or any legitimately-scoped client credential, is directly usable against `stack_id` values for every other stack.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` scoping is enforced consistently with every other API controller.

### Proof of Concept
1. As an admin, create (or use the fixture) an `ApiClient` scoped to `stack_id = A` with only `permissions: ["read:stack"]` (e.g. `here_come_the_walrus`), and obtain its `authentication_token`.
2. Send `GET /api/stacks/:B/ccmenu.xml?token=<token>` where `B` is a different stack's identifier.
3. Observe the response returns stack `B`'s build status (HTTP 200 with `Project` XML for stack B), even though the token is only authorized for stack `A`; compare with `Api::StacksController#index`, which correctly restricts the same client to only stack `A`'s data (per `test/controllers/api/stacks_controller_test.rb:217-223`).

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```

```ruby
# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
```
