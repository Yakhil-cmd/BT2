The `Handler#stacks` method resolves which repository/stacks to act on using `payload.dig('repository', 'full_name')`, which is a **different field** than the one `WebhooksController#verify_signature` uses to select the signing key that authenticates the webhook — `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). These two fields are never cross-checked against each other, and neither is bound by the HMAC signature to the same value that later drives repository selection.

### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while repository/stack resolution trusts the independent `repository.full_name` field, allowing cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. Every event handler (`Shipit::Webhooks::Handlers::Handler#stacks`) instead resolves the actual `Repository`/`Stack` to mutate using a completely separate field, `payload.dig('repository', 'full_name')`. Both fields live in the same attacker-controlled JSON body and are covered by the same signature bytes, but the code never asserts that `full_name`'s owner segment matches the `repository.owner.login`/`organization.login` used for key selection.

In a single-GitHub-App deployment (the default/documented setup, one `github.webhook_secret` for the whole installation) this is not exploitable, because the same secret is valid for any repository under that installation and the org field would legitimately match. However, `test/dummy/config/secrets_double_github_app.yml` demonstrates that Shipit explicitly supports **multiple, independently configured GitHub Apps/organizations, each with its own `webhook_secret`**, selected per-request via `Shipit.github(organization: ...)`. In that supported multi-org configuration, an attacker who has legitimate delivery access to Org A's webhook secret (e.g., is a member/integrator able to see Org A's webhook secret, or Org A's app is misconfigured with `webhook_secret: nil` as shown in the fixture) can craft a payload where:
- `repository.owner.login` / `organization.login` = `"OrgA"` (used only for signature verification)
- `repository.full_name` = `"OrgB/some-other-repo"` (used to pick the actual `Repository`/`Stack`)

The HMAC signature is computed over the raw JSON body and will validate successfully against Org A's secret because `verify_webhook_signature` only checks byte-for-byte integrity of the body against whichever secret was selected — it does not tie the *result* of verification to the specific `full_name` field the handler later trusts. The handler (e.g., `push` → `GithubSyncJob`, `pull_request` → `OpenedHandler`, `status`, `check_suite`, `membership`) will then act on Org B's repository/stack even though the request was only ever authenticated as belonging to Org A.

### Impact Explanation
This breaks the intended binding "organization that authenticated == repository that is written." A successfully signature-verified webhook for Org A can drive stack synchronization (`GithubSyncJob`), auto-provisioning/deprovisioning of review stacks, PR/commit status writes, and team/membership mutations for a stack belonging to a completely different, unrelated repository/organization configured in the same Shipit instance. This is a cross-repository write achieved without ever possessing the victim organization's own webhook secret, satisfying the Critical impact bar ("cross-repository writes").

### Likelihood Explanation
Requires a Shipit instance configured with multiple GitHub Apps/organizations (a supported, documented configuration pattern per `secrets_double_github_app.yml`) and requires the attacker to control (or have leaked) the webhook secret of at least one configured organization — a realistic scenario for a compromised/malicious low-trust org onboarded to a shared Shipit instance. No repository write access, session, or `ApiClient` token is needed; only webhook delivery capability to `/webhooks`.

### Recommendation
After signature verification, assert that the organization/owner used to select the verification key is the same owner segment present in `repository.full_name` (and `organization.login` if present) before allowing any handler to resolve or mutate a `Repository`/`Stack`. Reject the webhook (422) if these fields diverge.

### Proof of Concept
1. Configure Shipit with two organizations, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As a party who knows/controls OrgA's `webhook_secret` (or where OrgA's app has `webhook_secret: nil`, bypassing verification entirely per `lib/shipit/github_app.rb`'s `return true unless webhook_secret`), craft a `push` payload:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "after": "<sha>"
}
```
3. Sign the raw body with OrgA's `webhook_secret` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against OrgA's secret.
5. The registered `push` handler calls `stacks` → `Repository.from_github_repo_name("OrgB/victim-repo")`, enqueuing `GithubSyncJob` for OrgB's stack — a write to a repository the request was never authenticated for.
