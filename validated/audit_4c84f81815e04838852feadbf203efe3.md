### Title
Membership webhook handler grants team membership without verifying the signing organization owns the target team - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves the target `Team` solely by the numeric `params.team.id` via `Team.find_or_create_by!(github_id:)`, and only assigns `team.organization` inside the create block, which is skipped when the team record already exists. `WebhooksController#verify_signature` only checks that the payload was signed with the webhook secret belonging to `params.organization.login`, never that this organization equals the `organization` field stored on the already-persisted target `Team`. An attacker who controls (or has a `GithubHook::Organization`/webhook secret configured for) any organization can therefore add themselves to an unrelated, already-existing, privileged team.

### Finding Description
The broken binding is: **verified_org (`params.organization.login`, used to select the HMAC secret in `Shipit.github(organization: repository_owner)`) must equal `team.organization` (the org that legitimately owns the numeric `team.id` being mutated)**. This equality is enforced only once, at row-creation time, and never again.

Path:
1. `WebhooksController#create` -> `before_action :verify_signature` computes `repository_owner = params.dig('organization', 'login')` (membership events carry no `repository` key) [1](#0-0) [2](#0-1) . It then verifies the signature using `Shipit.github(organization: repository_owner)`'s configured `webhook_secret` -- i.e. whichever secret belongs to the org named in the attacker's own payload.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The block that sets `organization` only runs when a **new** record is created; if a `Team` with that `github_id` already exists (created earlier by a legitimate sync/webhook from the real owning org), `find_or_create_by!` returns the existing row untouched, keeping its true `organization`.
3. `process` then unconditionally calls `team.add_member(member)` (or removes a member), creating a `Membership` row [4](#0-3) [5](#0-4) . Nothing here checks that the signature-verifying org (step 1) matches the resolved team's stored `organization`.

Exploit: the attacker signs a `membership`/`action: added` webhook with a secret valid for an organization they control (or for which a `GithubHook::Organization` webhook secret is configured), sets `organization.login` to that org (satisfying `verify_signature`), sets `team.id` to the numeric GitHub team id of an existing, privileged `Shipit::Team` (public via `GET /orgs/:org/teams`), and sets `member.login` to their own GitHub login. Because the target `Team` row already exists, `find_or_create_by!` skips the org-assignment block, and `team.add_member(User.find_or_create_by_login!(attacker_login))` runs, creating the `Membership`.

Existing guards do not catch this: `drop_unhandled_event` and `check_if_ping` only gate on event type; `verify_signature` validates only that *some* configured org's secret matches, not that it's the *correct* org for the referenced team; the `ExplicitParameters` schema in `MembershipHandler` validates shapes/types only, not organization identity; there is no `require_permission!`/ownership check anywhere in this path.

### Impact Explanation
A successful request creates a `Membership` linking the attacker's `User` to a team the attacker does not belong to. If that team is included in `Shipit.github_teams`, `User#authorized?` becomes `true` [6](#0-5) , granting the attacker full Shipit UI/session authorization without ever completing GitHub OAuth as a member of that org. This is repeatable against any `Shipit::Team` row whose `github_id` the attacker can guess/enumerate (public GitHub API), regardless of which org created the row, and constitutes escalation into `Shipit.github_teams` authorization -- matching the **High** severity category (unauthorized privilege escalation across tenants/orgs) defined in the rules.

### Likelihood Explanation
Preconditions: (1) `Shipit.github_teams` non-empty and includes the targeted team; (2) the target `Team` row must already exist in the DB with `github_id` equal to the value the attacker names (true for any team previously synced/observed via a legitimate webhook or `refresh_members!`/rake sync); (3) the attacker needs a webhook secret valid for *some* organization known to the Shipit config/`GithubHook::Organization` — this can be their own org if the deployment supports multiple GitHub orgs/apps (multi-tenant `secrets.github` keyed by org, as implied by `Shipit.github_app_config`/`github_organizations`). No Shipit session, API token, or the target org's own webhook secret is required. This is a single crafted HTTP POST to `/webhooks`, fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after resolving (finding or creating) the team, explicitly assert `team.organization == params.organization.login` (i.e., that the org verified during signature checking matches the team's stored owning org) and raise/drop the webhook if they differ, rather than only setting `organization` inside the create block.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative — not to be placed in violation of scope, for review only):
```ruby
test "membership webhook cannot add member to a team owned by a different verified organization" do
  privileged_team = shipit_teams(:some_privileged_team) # organization: "org-b", github_id: 4242
  Shipit.stubs(:github_teams).returns([privileged_team])

  attacker = users(:walrus) # not a member of org-b

  payload = {
    action: "added",
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: "org-a" }, # attacker's own org, whose secret they hold
    member: { login: attacker.login }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", secret_for("org-a"), payload)

  before_count = Membership.count
  post shipit.webhooks_path, params: payload, headers: {
    "X-Github-Event" => "membership", "X-Hub-Signature" => signature, "CONTENT_TYPE" => "application/json"
  }

  assert_equal before_count, Membership.count, "membership must not be created cross-organization"
  refute attacker.reload.authorized?
end
```
Assertions before/after directly test the equality `verified_org("org-a") == team.organization("org-b")` -> false, and confirm no `Membership` row is written and `authorized?` stays `false` under a fixed implementation, versus the current code where `Membership.count` increases and `authorized?` flips to `true`.
