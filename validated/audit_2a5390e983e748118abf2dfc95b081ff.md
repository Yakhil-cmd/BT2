### Title
AAs can consume unstable, attacker-controlled oracle prices before consensus finality, enabling flash-loan-style oracle manipulation - ([File: data_feeds.js])

### Summary
The Cheese Bank incident exploited an AMM spot-price oracle that could be manipulated and consumed atomically within a single Ethereum transaction/block, before the market could correct the price. In ocore, the analogous primitive is the `data_feed[[...]]` oscript operator used by Autonomous Agents (AAs) to read oracle values. When evaluated inside an AA, it does not restrict itself to finalized (stable) data-feed messages — it actively prefers not-yet-stable data-feed messages authored by other AAs within the current, unconfirmed DAG window, giving an attacker the same "manipulate-then-consume-before-settlement" window that enabled the Cheese Bank exploit.

### Finding Description
`readDataFeedValue()` in `data_feeds.js` is the backing implementation for the `data_feed` oscript operator. When called from within AA evaluation (`bAA`/`unstable_opts` truthy), it first scans `storage.assocUnstableMessages` for `data_feed` messages authored by *any currently unstable AA-authored unit* whose `latest_included_mc_index` falls in the requested `[min_mci, max_mci]` window, and — if such a candidate exists — returns it as the value, in preference to the durable, already-committed value in the key-value store: [1](#0-0) 

The only safety check applied to these candidates is `objUnit.sequence !== 'good'` — there is no requirement that the unit (or the `min_mci`-satisfying unit) is stable/finalized: [2](#0-1) 

The oscript `data_feed` case in the formula evaluator passes the AA context flag (`bAA`) straight through as `unstable_opts`, so any AA whose logic depends on `data_feed[[oracles=..., feed_name=...]]` will, by default, pick up the most recent *unconfirmed* value from a matching oracle/AA address rather than a settled one: [3](#0-2) 

This mirrors the Cheese Bank bug class: a price provider (in Cheese Bank, an AMM reserve ratio; in ocore, a data-feed-posting AA/oracle address) can be made to emit a value reflecting a transient, still-reversible state, and a dependent AA (e.g., a lending/vault/AMM-consumer AA) will act on that transient value in the same unconfirmed DAG round, before the network has reached consensus on whether the underlying state (and even the data-feed-posting unit itself) will remain valid. Because AA trigger processing (`aa_composer.js`, `handleTrigger`) executes deterministically based on whatever `storage.assocUnstableMessages`/`assocUnstableUnits` currently contain at trigger time, an attacker who controls or influences the timing/content of an oracle-posting unit can chain: (1) post a unit that shifts a self-referential state (e.g., an AMM-style AA's own balance-derived "price" via a deposit/withdraw), (2) post/trigger a `data_feed` message reflecting that instantaneous, unconfirmed state, and (3) immediately trigger a second AA that reads this feed via `data_feed[[...]]` and pays out funds — all before any of these units are stable.

### Impact Explanation
A dependent AA (lending, synthetic-asset, or AMM-consumer AA) that prices collateral, loans, or swaps using `data_feed[[...]]` can be tricked into releasing more funds (base or issued asset) than it should, because it is valuing a position against a transient, attacker-influenced, not-yet-final value rather than a settled one. This constitutes concrete AA fund loss, directly analogous to the $3.3M loss caused by consuming a manipulated within-transaction price in Cheese Bank.

### Likelihood Explanation
Any unprivileged address can author units, including AA-triggering units and data-feed-posting units, and any AA author is free to write oscript that calls `data_feed[[...]]` without pinning `min_mci` to a stability boundary. Because the unstable-data-feed lookup path is the *default* behavior of `data_feed` inside AAs (not an opt-in "unsafe" mode), any AA design that relies on an oracle/companion AA for pricing is exposed by default, unless the AA author explicitly avoids reading anything but long-stable feeds — which is not how the primitive is documented/used in practice (see tests referencing `readDataFeedValue`/`data_feed` unstable inclusion).

### Recommendation
- Require `data_feed[[...]]` reads used for financial decisions (pricing, collateral valuation, payout sizing) to only consider stable/finalized data-feed messages by default, or require an explicit stability threshold (e.g., `min_mci` tied to `last_stable_mci`) rather than defaulting to “most recent unstable value.”
- At minimum, document and strongly discourage using unstable-scoped `data_feed` reads for irreversible fund transfers, and add a formula-level flag/warning when `data_feed` is combined with payment/asset-transfer messages in the same AA response without a stability guard.
- Consider disallowing an oracle/AA address's own not-yet-stable data feed value from being consumed by an AA response that moves funds in the same MC round in which the feed was posted.

### Proof of Concept
1. Oracle/companion AA `O` posts a `data_feed` message with feed value `V` computed from its own currently-mutable state (e.g., `balance[asset]/balance[base]`), inside a still-unstable unit `U1`.
2. Attacker immediately posts a trigger unit `U2` to a consumer AA `C` whose oscript uses `data_feed[[oracles="O", feed_name="price"]]` to compute a payout/collateral release.
3. Because `readDataFeedValue` (data_feeds.js:211-249) scans `assocUnstableMessages` for AA-authored units with `sequence === 'good'` regardless of stability, `C`'s evaluation of `data_feed[[...]]` returns `V` from `U1` even though `U1` (and the state that produced `V`) is not yet final.
4. `C` sends a response payment sized against `V`, transferring more value than it would under the settled price, before `U1`/`U2` are confirmed stable — reproducing the flash-loan oracle-manipulation pattern from the Cheese Bank incident within ocore's DAG-and-AA execution model.
