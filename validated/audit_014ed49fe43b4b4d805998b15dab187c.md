### Title
Uncaught exception on malformed base32 c-hash crashes node - denial of service on address validation (`chash.js:isChashValid`)

### Summary
`isChashValid()` decodes a 32-character address string with `base32.decode()` and then immediately assumes the resulting buffer, once expanded to bits, is exactly 160 bits long. If the caller-supplied string decodes to a buffer whose bit-length isn't 160/288, `separateIntoCleanDataAndChecksum()` throws, and that throw happens **outside** the `try/catch` that only wraps the decode call itself, so the exception propagates uncaught.

### Finding Description
`isChashValid` only guards the decode step: [1](#0-0) 

```
function isChashValid(encoded){
	...
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);
		return false;
	}
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);
```

`separateIntoCleanDataAndChecksum` explicitly throws for any bit-length other than 160 or 288: [2](#0-1) 

`base32.decode()` from the `thirty-two` package does not guarantee the output is exactly 20 bytes for a 32-character input if the input contains characters/padding that don't perfectly correspond to a clean 32×5=160-bit block (e.g. malformed padding characters accepted by the decoder but yielding a truncated/extended byte buffer). In that case `buffer2bin(chash)` produces a bit string whose length is not 160, and the subsequent call throws `Error("bad length=...")`, which is unhandled by `isChashValid`.

`isChashValid` is reached through `isValidChash` / `isValidAddress` / `isValidAddressAnyCase`, which are the core address-format validators used throughout unit/address validation (definitions, authors, outputs, AA addresses, device addresses): [3](#0-2) 

Any unprivileged unit poster who crafts a unit containing a 32-character string in an address-checked field (author address, output address, definition address reference, etc.) that decodes via base32 to a buffer whose bit length deviates from 160 can trigger the unhandled throw during validation.

### Impact Explanation
An uncaught exception thrown synchronously inside the core address-validation routine (called on every unit that carries address strings) can crash the validating node process, since JS exceptions thrown outside of any try/catch in a synchronous call chain propagate up and, if not intercepted by an outer handler, terminate the Node.js process. This matches the impact category "a network unable to confirm new units" — if the crash occurs during normal unit/joint validation on many nodes simultaneously (because the same malicious unit is broadcast to all nodes), it can degrade or halt network validation availability, analogous to the Mutt uudecoder crash triggered by reading past declared/actual buffer boundaries during decoding.

### Likelihood Explanation
Reachability requires only posting a unit containing an address-like 32-char string that decodes cleanly through `base32.decode` (no decode-level exception) yet yields a bit-length different from 160. This is plausible because `thirty-two`'s decoder is lenient about padding/case and does not strictly enforce that input length maps to exactly 160 bits of output; constructing such an input does not require any privileged access — any address field validated with `isValidAddress`/`isValidChash` is a candidate trigger point reachable from ordinary unit posting.

### Recommendation
Wrap the entire body of `isChashValid` (including `buffer2bin`/`separateIntoCleanDataAndChecksum`) in the existing `try/catch`, or add explicit length validation on `chash.length` immediately after decode (rejecting any buffer whose length isn't 20 or 36 bytes) before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, so malformed encodings are turned into `return false` instead of an uncaught exception.

### Proof of Concept
1. Construct a 32-character string that is accepted by `base32.decode()` (passes without throwing) but whose decoded byte buffer length is not exactly 20 bytes (achievable by using non-standard padding/casing patterns that `thirty-two` tolerates while producing a shorter/longer output than a strict 160-bit decode).
2. Submit a unit whose author address (or other address-validated field) is set to this crafted string.
3. When the receiving node calls `validation_utils.isValidAddress()` → `isValidChash()` → `chash.isChashValid()` during unit validation, `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")` outside of the try/catch, propagating as an uncaught exception in the validation call stack and crashing the node process.
