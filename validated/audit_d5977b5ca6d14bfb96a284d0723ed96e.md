### Title
Delimiter-less field concatenation in arbiter contract hashing enables cross-field boundary-shifting collisions - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` exposes exactly the same class of bug flagged in the report for `abi.encodePacked`: variable-length fields are concatenated without a separator before hashing, so different sets of field values can produce an identical hash. Unlike Solidity's forward-looking deprecation concern, here the unsafe path is the currently active one, because the switch-over date to the safe, delimited hashing scheme is set in the future.

### Finding Description
`getHashSrc()` builds the source string used to compute an arbiter contract's identifying hash. For any contract whose `creation_date` is not after `exports.NEW_HASH_DATE`, it concatenates `title`, `text`, `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, and `asset` with `join("")` — i.e. no delimiter at all: [1](#0-0) 

`exports.NEW_HASH_DATE` is set to `'2026-11-01'`, a date in the future relative to today, and `exports.DELIMITER` (`"[|#|]"`) is only used for contracts created after that date: [2](#0-1) 

This means every arbiter contract created today still goes through the unsafe, delimiter-less branch. `getHash()` feeds this ambiguous string directly into SHA-256 to produce the contract's canonical hash: [3](#0-2) 

This hash is then used as the authoritative identifier for the contract throughout the entire arbiter-contract flow — it is what gets stored, sent to the peer device, checked against status transitions, shared with cosigners, and used to look up/verify the contract when responding, revoking, or sharing: [4](#0-3) [5](#0-4) [6](#0-5) 

Notably, the codebase is otherwise aware of this exact hazard: `string_utils.getSourceString()`, used pervasively for unit/definition/device-message hashing elsewhere in ocore, explicitly inserts a `STRING_JOIN_CHAR` (`\x00`) between every component and rejects any field containing that byte to prevent ambiguity: [7](#0-6) [8](#0-7) 

`arbiter_contract.js`'s legacy path (currently the live path due to the future `NEW_HASH_DATE`) does not follow this pattern and is therefore vulnerable to the same class of ambiguity that plain `abi.encodePacked` concatenation causes with dynamic-length inputs.

### Impact Explanation
Because `amount` and `asset` (both attacker/offeror-controlled financial terms of a payer/payee agreement) sit adjacent to each other in the un-delimited concatenation, an offeror can shift the boundary between numeric and string fields to produce two different (amount, asset) — or (payer_name, arbiter_address, payee_name) — combinations that hash identically. This breaks the integrity guarantee the hash is supposed to provide across the whole flow (peer acceptance, cosigner sharing, arbstore submission, dispute resolution), letting a party present contract content with different financial terms than what another party or the arbiter believes they agreed to, while it still verifies against the same `hash`. This directly enables unauthorized/fraudulent alteration of a private-payment counterparty agreement's financial terms without invalidating its supposed cryptographic identity, which is a concrete integrity/fund-related risk for the reachable actors (contract counterparty, arbiter, cosigners).

### Likelihood Explanation
The offeror of the contract fully controls `title`, `text`, `payer_name`/`payee_name`, `amount`, and `asset` when calling `createAndSend()`, so crafting a colliding pair of field-value sets requires no special privilege — just careful construction of boundary-shifted strings/numbers, which is straightforward given `amount` is serialized via implicit string conversion in the array join. Because `NEW_HASH_DATE` is still in the future, this is not a theoretical, to-be-deprecated concern — it is the hashing scheme in effect for every arbiter contract created today.

### Recommendation
Use the already-existing delimiter-based scheme (or `string_utils.getSourceString`) unconditionally, rather than gating it behind a future `NEW_HASH_DATE`. At minimum, move the effective date to the past (or remove the legacy branch entirely) so all arbiter contracts use `[contract.title, ..., contract.asset || 'null'].join(exports.DELIMITER)`, and ensure the delimiter cannot occur inside any of the joined fields (as `getSourceString` does by rejecting the join character within field values).

### Proof of Concept
1. Offeror A creates an arbiter contract with `amount = 50`, `asset = "0EUR"` (i.e. an unusual/likely-rejected asset id/placeholder, or any string starting with digits).
2. The pre-delimiter concatenation for the tail of the string is `... + "50" + "0EUR"` → `"500EUR"`.
3. A different, legitimate-looking contract with `amount = 500`, `asset = "EUR"` produces the same tail `"500" + "EUR"` → `"500EUR"`.
4. With all other fields (`title`, `text`, `creation_date`, `payer_name`, `arbiter_address`, `payee_name`) identical, `getHashSrc()` returns the identical string for both contracts, so `getHash()` returns the same SHA-256 digest for two contracts with a 10x difference in `amount`, via `arbiter_contract.js:194-207`.
5. This hash collision can be leveraged to present one version of the contract to the counterparty/arbiter while the stored/verifiable hash matches a different, more favorable-to-the-attacker version, undermining dispute resolution and fund expectations tied to the contract.
