### Title
`checkZeroedsApproved()` Re-reads Live External-Contract State at the Fork Block, Allowing a Zeroed-Contract Admin to Abort the KIP-160 Treasury Rebalance After `finalizeApproval()` — (`blockchain/system/rebalance.go` / `contracts/testing/system_contracts/TreasuryRebalanceV2.sol`)

---

### Summary

`RebalanceTreasury()` in `blockchain/system/rebalance.go` re-validates `CheckZeroedsApproved()` at the KIP-160 fork block by reading the **current** admin list and quorum from every registered zeroed contract. Because this live re-read occurs after `finalizeApproval()` has already advanced the contract status to `Approved`, any admin of a registered zeroed contract can raise the quorum (or remove themselves from the admin list) in the window between `finalizeApproval()` and the fork block. The re-validation then fails, `RebalanceTreasury()` returns an error, and all zeroed-address KAIA balances remain untouched while the allocated addresses receive nothing.

---

### Finding Description

**Step 1 — Normal approval flow**

`TreasuryRebalanceV2.finalizeApproval()` calls `checkZeroedsApproved()`, which iterates over every registered zeroed address and, for contract-type zeroed addresses, calls `_getState(zeroed.addr)` to obtain the **current** admin list and quorum from the external contract:

```solidity
// TreasuryRebalanceV2.sol lines 292-313
function checkZeroedsApproved() public view {
    uint256 numZeroeds = zeroeds.length;
    for (uint256 i = 0; i < numZeroeds; i++) {
        Zeroed memory zeroed = zeroeds[i];
        bool isContract = isContractAddr(zeroed.addr);
        if (isContract) {
            (address[] memory adminList, uint256 req) = _getState(zeroed.addr);
            require(zeroed.approvers.length >= req, "min required admins should approve");
            ...
            require(validApprovals >= req, "min required admins should approve");
        } else {
            require(zeroed.approvers.length == 1, "EOA should approve");
        }
    }
}
``` [1](#0-0) 

If the check passes, `finalizeApproval()` sets `status = Status.Approved`. [2](#0-1) 

**Step 2 — Core re-validates at the fork block**

`RebalanceTreasury()` in the Go core is invoked at the exact KIP-160 fork block. It performs four sequential validations, the third of which calls `CheckZeroedsApproved()` again against the **live** contract state at that block:

```go
// blockchain/system/rebalance.go lines 290-298
// Validation 2) Check whether status is approved. It should be 2 meaning approved
if status, err := caller.Status(nil); err != nil || status != 2 {
    return result, ErrRebalanceBadStatus
}

// Validation 3) Check approvals from zeroeds
if err = caller.CheckZeroedsApproved(nil); err != nil {
    return result, err
}
``` [3](#0-2) 

**Step 3 — The attack window**

Between the block where `finalizeApproval()` is mined and the fork block, any admin of a registered zeroed contract can call `changeMinReq(newHigherQuorum)` (or remove themselves from the admin list) on their own multisig contract. When `RebalanceTreasury()` subsequently calls `CheckZeroedsApproved()`, `_getState(zeroed.addr)` returns the new, higher quorum. The stored `zeroed.approvers` array no longer satisfies `validApprovals >= req`, so the function reverts with `"min required admins should approve"`. `RebalanceTreasury()` propagates this error and returns without executing any balance changes. [4](#0-3) 

**Step 4 — Consequence**

Because `RebalanceTreasury()` returns an error before reaching the execution section, no balances are modified:

```go
// Execution 1) Clear all balances of zeroeds
for addr := range result.Before.Zeroed {
    state.SetBalance(addr, big.NewInt(0))
    ...
}
// Execution 2) Distribute KAIA to all allocateds
for addr, balance := range result.After.Allocated {
    state.SetBalance(addr, balance)
}
``` [5](#0-4) 

The zeroed addresses keep their full KAIA balances; the allocated addresses receive nothing. Because `updateRebalanceBlocknumber` requires `block.number < rebalanceBlockNumber`, the block number cannot be pushed forward once the fork block has passed, making the failure permanent without a new contract deployment and chain-config update. [6](#0-5) 

---

### Impact Explanation

The treasury rebalance is a one-time, hard-fork-level operation that redistributes system-managed KAIA from old treasury addresses to new ones. A successful abort means:

- All zeroed-address KAIA balances remain intact (the "burn" never happens).
- All allocated addresses receive zero KAIA (the "mint/transfer" never happens).
- The discrepancy between the intended post-fork state and the actual state is permanent unless the Kaia Foundation deploys a new contract and issues a new hard fork.

This directly affects system-managed KAIA funds and constitutes a failure of a system-contract operation that changes protected asset ownership.

---

### Likelihood Explanation

The trigger requires an admin of a registered zeroed contract to deliberately raise the quorum (or remove themselves) after `finalizeApproval()` succeeds. The zeroed contracts are trusted parties chosen by the Kaia Foundation, so the probability of a malicious insider is low. However:

- No on-chain mechanism prevents the action.
- The attack requires no special privilege beyond being an admin of one's own multisig.
- The window between `finalizeApproval()` and the fork block can span many blocks (days or weeks), giving ample time.
- The attacker has no financial cost beyond gas.

---

### Recommendation

Remove the redundant `CheckZeroedsApproved()` call from `RebalanceTreasury()`. The `Status == Approved` check (Validation 2) already guarantees that `finalizeApproval()` ran successfully and that `checkZeroedsApproved()` passed at that time. Re-reading live external contract state at the fork block introduces an unnecessary dependency on the current state of third-party contracts.

```go
// Validation 2) Check whether status is approved. It should be 2 meaning approved
if status, err := caller.Status(nil); err != nil || status != 2 {
    return result, ErrRebalanceBadStatus
}

// Remove Validation 3 — status == Approved already implies checkZeroedsApproved passed.
// if err = caller.CheckZeroedsApproved(nil); err != nil { ... }
```

Alternatively, if the re-check is intentional, snapshot the quorum and admin list at `finalizeApproval()` time inside the `TreasuryRebalanceV2` contract itself (rather than re-reading from the external contract), so the stored snapshot cannot be invalidated after approval.

### Proof of Concept

```
Setup:
  - Deploy a multisig contract M with admin = Alice, minReq = 1.
  - Register M as a zeroed address in TreasuryRebalanceV2.
  - Call finalizeRegistration().

Attack:
  1. Alice calls approve(M) → zeroed[M].approvers = [Alice], quorum = 1 → passes.
  2. Owner calls finalizeApproval() → checkZeroedsApproved() passes (1 >= 1) → status = Approved.
  3. Alice calls M.changeMinReq(2) → M's quorum is now 2.
  4. Fork block N arrives. Core calls RebalanceTreasury().
     - Validation 2: status == 2 ✓
     - Validation 3: CheckZeroedsApproved() → _getState(M) returns req=2,
       zeroed[M].approvers.length == 1, validApprovals == 1 < 2 → REVERT
       "min required admins should approve"
  5. RebalanceTreasury() returns error. No balances are changed.
     All KAIA in zeroed addresses is preserved; allocated addresses receive nothing.
```
