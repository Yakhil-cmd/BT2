## Title
Webhook signature verification keyed on `repository.owner.login` while event handlers act on the untied `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against using a value it derives itself from the untrusted, unsigned JSON body — `repository.owner.login` (falling back to `organization.login`). The event handlers (e.g. `PushHandler`, via `Handler#repository_name`) then resolve the actual `Repository`/`Stack` to act on using a *different* payload field, `repository.full_name`. Nothing enforces that these two fields refer to the same owner. This mirrors the reported `ProxyLOB._claimOrder` bug class: a field used to select/validate against one binding (the bid trie / here, the signing organization's secret) is not the same field, nor properly tied, to the field that is actually used downstream to identify and act on the resource (the claimed order / here, the target repository).

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` computes the signing organization purely from attacker-suppliable JSON: [1](#0-0) [2](#0-1) 

`repository_owner` is used solely to pick which `GitHubApp`/`webhook_secret` the HMAC is checked against: [3](#0-2) 

But the actual event handlers never consult `repository.owner.login`. They resolve the target `Repository` from a separate field, `repository.full_name`: [4](#0-3) [5](#0-4) 

In a multi-GitHub-App deployment (documented and supported via `Shipit.github(organization:)`), each organization has its own `webhook_secret`: [6](#0-5) 

An attacker who legitimately controls/administers their own small organization "attacker-org" (and therefore knows or can set that org's `webhook_secret` in its GitHub App settings) can POST directly to the shared, unauthenticated `/webhooks` endpoint with a JSON body where:
- `repository.owner.login` = `"attacker-org"` (used only for HMAC secret lookup and passes verification because the attacker computed the HMAC with their own known secret), while
- `repository.full_name` = `"victim-org/victim-repo"` (used by `Handler#repository_name` / `Repository.from_github_repo_name` to pick the actually-affected `Repository` and its `Stack`s).

Before-state: `verify_signature` binds *"the organization whose secret validated this signature"* == *"the organization actually targeted by the event"*, i.e. `repository_owner_for_verification == repository_owner_for_target`. After the attacker's crafted payload, this equality is broken: the signature is valid for `attacker-org`, but the handler operates on a `Repository` belonging to `victim-org`.

### Impact Explanation
This breaks the authentication boundary that the webhook signature is supposed to enforce per organization: `WebhooksController` treats the raw, unauthenticated `X-Hub-Signature`-validated payload as globally trusted GitHub input once *any* configured org's secret matches, then hands the whole payload (including the mismatched `repository.full_name`) to handlers that operate cross-organization. Depending on which webhook event is forged, an attacker with no privileges over the victim's org/repo can:
- Trigger `PushHandler#process` → `stack.sync_github(expected_head_sha: ...)` for the victim's stacks, forcing arbitrary GitHub sync activity on a victim repository.
- Forge `status` or `check_suite` events for a victim commit, influencing CI-status caching used to gate deploys/merges on stacks with `continuous_deployment` enabled.
- Forge `membership` events that create/delete `Team`/`Membership`/`User` records globally (not scoped by organization at all in `MembershipHandler`), since these models are shared across the whole Shipit instance.

This crosses the "an organization that authenticated versus the repository that is written" trust boundary named in scope and can result in unauthorized cross-repository state changes / potentially an unauthorized deploy path (continuous deployment gated by forged CI status), which maps to the Critical impact bucket (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Exploitability requires:
1. The Shipit instance to be configured for multiple GitHub organizations (`Shipit.github(organization:)` multi-app config), which is a documented, supported configuration (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`).
2. The attacker to control (as an unprivileged party relative to the victim) at least one of the configured organizations' `webhook_secret` — plausible if Shipit is used as a shared multi-tenant instance across orgs with differing trust levels, or if any org's `webhook_secret` is leaked/weak/unset.
3. No session, `ApiClient` token, or repository write access on the victim org is needed — only the ability to POST to the public `/webhooks` endpoint, which is unauthenticated by design.

This is a real but conditional (multi-org, cross-tenant) exploitation path; single-organization deployments are not affected because there is only one secret to check against and `repository.owner.login`/`organization.login` will always resolve to the same tenant.

### Recommendation
In `WebhooksController#verify_signature` (and/or in `Handler#repository_name`), cross-check that the organization used to select/verify the webhook secret is the same organization that the event handler will act upon (e.g., re-derive and compare `repository.owner.login` against the owner segment of `repository.full_name`, and reject if they diverge). More robustly, have handlers resolve the target repository using the *same* verified field that selected the signing secret, rather than trusting a second, independently-supplied field from the same unauthenticated payload.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `attacker-org` (secret known to attacker) and `victim-org` (holds a real `Repository`/`Stack` for `victim-org/victim-repo`).
2. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using the `webhook_secret` configured for `attacker-org` (which they control) over the exact raw JSON body.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own secret. [1](#0-0) 
6. `PushHandler.new(params).process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the real victim `Repository`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on victim stacks — a cross-organization action triggered with a signature that never belonged to `victim-org`. [7](#0-6) [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
