This confirms a critical binding break: the `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) writes CI status directly from webhook payload fields (`state`, `context`) onto `Commit` records purely by matching `sha` globally — with no scoping to the repository/organization that the signature was actually verified against — and that status feeds directly into `required?`/`blocking?` checks (`app/models/shipit/status/common.rb:46-52`) used to gate merges and deploys.

### Title
Cross-organization webhook confused deputy allows forging CI status / repository events for any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on a value read out of the **unverified** JSON body (`repository.owner.login`, falling back to `organization.login`), before the signature has been checked. Once verification passes, every downstream handler locates the target `Stack`/`Commit`/`Repository` using a *different* attacker-controlled field from the same body (`repository.full_name`, or a global `sha` lookup with no owner scoping). Nothing ties the organization whose secret validated the payload to the repository/commit the handler actually mutates.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit` supports hosting several independent GitHub Apps (one per organization) in a single instance, each with its own `webhook_secret`, exactly as documented in `docs/setup.md` ("Using Multiple Github Applications") [3](#0-2) . Each organization's administrators create and control their own App, and therefore know their own `webhook_secret` — this is a credential legitimately held by an "unprivileged" (relative to *other* tenants) party.

Once the signature check passes using OrgA's secret, the handlers never re-check that the payload's `repository`/`sha` actually belongs to OrgA:
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — a **global** lookup across all stacks/repositories in the Shipit instance, with no owner/repository filter at all [4](#0-3) .
- `PushHandler`, `PullRequestClosedHandler`, `PullRequestOpenedHandler`, etc. resolve the target via `Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , a value taken from the same untrusted body used to choose the verifying secret, with no requirement that its owner match `repository_owner`.

So the equality the app relies on — "organization whose secret authenticated this request" == "organization/repository the handler is about to mutate" — is never enforced. An attacker who legitimately controls OrgA's GitHub App (and thus knows OrgA's `webhook_secret`) can sign an arbitrary payload with `repository.owner.login = "OrgA"` (to pick the secret Shipit will verify against) while setting `sha`/`repository.full_name` to values belonging to OrgB, a completely unrelated tenant tracked by the same Shipit instance.

### Impact Explanation
Forged `status` events written by `Commit#create_status_from_github!` feed directly into `required?` and `blocking?` [6](#0-5) , which gate the merge queue and deploy safety checks (`Stack#required_statuses`, `blocking_statuses`, delegated from `DeploySpec`) [7](#0-6) . Forging a `success` status for a commit belonging to OrgB's repository can satisfy required CI checks and unblock an unauthorized merge or deploy on a repository the attacker has no legitimate access to — this is the "unauthorized deploy, rollback or merge" impact class. Other handlers (`push`, `pull_request` opened/closed) similarly let the OrgA-authenticated attacker archive/create review stacks or trigger sync jobs against OrgB's tracked repositories, a cross-tenant write.

### Likelihood Explanation
Requires the attacker to control (own/administer) at least one GitHub organization/App that this specific Shipit instance already trusts (a realistic scenario for the documented multi-organization deployment mode), but no Shipit session, API token, or access to the victim organization/repository is needed — matching the "unprivileged attacker" threat model. This is directly analogous to the reported bug class: a credential/authentication scope (the organization whose secret validated the request) is not bound to the resource actually acted upon (the repository/commit written).

### Recommendation
After signature verification, re-derive the organization strictly from the verified GitHub App context (not from body fields), and require that `repository.owner.login`/`organization.login` and `repository.full_name`'s owner match the organization whose secret validated the signature before dispatching to any handler. `StatusHandler` should scope its `Commit` lookup to commits belonging to stacks under that verified organization instead of a global `sha` match.

### Proof of Concept
1. Configure Shipit with two GitHub Apps per `docs/setup.md`'s multi-org setup: `OrgA` (attacker-controlled, secret known to attacker) and `OrgB` (victim, tracks a stack with `required_statuses` including e.g. `ci/tests`).
2. Attacker crafts a `status` webhook body: `{"repository": {"owner": {"login": "OrgA"}}, "sha": "<OrgB commit sha awaiting CI>", "state": "success", "context": "ci/tests"}` and signs it with OrgA's known `webhook_secret` (`X-Hub-Signature: sha1=...`).
3. `WebhooksController#verify_signature` picks `Shipit.github(organization: "OrgA")` and successfully verifies the signature.
4. `StatusHandler#process` runs `Commit.where(sha: <OrgB sha>)` — matches OrgB's commit regardless of the verified organization — and calls `create_status_from_github!`, marking the required check as `success` for OrgB's commit, potentially unblocking an unauthorized merge/deploy on OrgB's stack.
