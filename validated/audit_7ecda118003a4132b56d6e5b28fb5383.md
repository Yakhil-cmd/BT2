### Title
Skipped `git worktree prune`/reflog-expire/GC when no worktrees are considered stale leads to unbounded repository growth and persistent sync denial - (File: main.go)

### Summary
The `cleanup` function in `git-sync` short-circuits and skips `git worktree prune`, `reflog expire`, and `git gc` entirely whenever `removeStaleWorktrees()` reports that zero worktrees were removed, mirroring the reported bug class where a critical follow-up accounting/cleanup call is conditionally skipped based on a count being zero, leaving resources unreclaimed.

### Finding Description
`git.cleanup(ctx)` is invoked on every iteration of the main sync loop after a successful `SyncRepo` call. [1](#0-0) 
Inside `cleanup`, the function calls `removeStaleWorktrees()` and, if the returned count `n` is `0`, immediately returns without running `worktree prune`, `reflog expire --expire-unreachable=all`, or `git gc`: [2](#0-1) 

This is structurally the same defect pattern as the reported Solidity issue: a necessary maintenance/accounting step (`onSettleBondEscalation` in the original report; here, `worktree prune` / `reflog expire` / `gc`) is gated on an unrelated zero-count condition (`_pledgesAgainstDispute > 0` in the original; here, `n == 0` from stale-worktree removal), causing the step to be silently skipped in states where it is still needed.

In `SyncRepo`, worktrees can also be removed directly via `os.RemoveAll` (bypassing `removeStaleWorktrees`, e.g. sanity-check failures at [3](#0-2)  or stale in-place-upgrade cleanup at [4](#0-3) ). These removals do not increment the count returned to `cleanup`, so `n` can be `0` even though the on-disk `.git/worktrees/<name>` administrative metadata is now stale and needs `git worktree prune`. Because `--stale-worktree-timeout` (default `0`, meaning worktrees become eligible for removal almost immediately after superseded) governs whether `removeStaleWorktrees()` finds anything to delete on a given pass, on many sync iterations `n` will legitimately be `0` (e.g., no new commit was fetched, so nothing is stale yet), and in those iterations `reflog expire` and `git gc` never run — even though every changed sync creates new commit objects and blobs from `git fetch`/`git reset --soft` that accumulate in the object database at [5](#0-4) .

Because `--repo` points at an attacker-influenced remote (untrusted content pushed by anyone with write access to the tracked ref), an attacker can repeatedly push small commits at a rate that keeps worktrees from going stale between pushes (or push once and never push again after the initial sync, so `removeStaleWorktrees()` always returns `0` after the first cleanup), ensuring GC and reflog expiry are perpetually skipped while `git fetch` continues to pull new objects into `--root/.git/objects` on every period.

### Impact Explanation
Skipping GC and reflog expiration indefinitely allows the object database and reflogs inside `--root` to grow without bound as an attacker pushes new commits over time. Left unresolved, this leads to unbounded disk consumption inside the git-sync working directory, eventually exhausting available disk space on the host/pod. Once disk space is exhausted, all subsequent git operations (`fetch`, `reset`, `worktree add`) fail, and the sync loop enters a persistent failure state — satisfying the "persistent sync denial" impact category. This is a resource-exhaustion / denial-of-service class issue reachable purely from attacker-pushed commits to the tracked ref, with no privileged or malicious-operator/leaked-key precondition required.

### Likelihood Explanation
Likelihood is moderate-to-low: it depends on operational conditions (period vs. commit cadence and `--stale-worktree-timeout` value) causing `removeStaleWorktrees()` to return `0` on most cleanup passes over an extended period. It is entirely plausible in common deployments where a repository receives infrequent updates or the stale timeout is tuned high, since `cleanup` is the *only* place `git gc`/`reflog expire` are triggered, and it is gated behind an unrelated worktree-removal count rather than being run unconditionally or based on repository size/age.

### Recommendation
- **Short term**: Decouple `git worktree prune`, `reflog expire`, and `git gc` from the `removeStaleWorktrees()` count. Run `worktree prune` whenever any worktree was removed by any code path (including the direct `os.RemoveAll` calls in `SyncRepo`), and run `reflog expire`/`gc` unconditionally on a periodic cadence (e.g., every N syncs or based on elapsed time/repo size), rather than only when stale worktrees happen to be found in the same pass.
- **Long term**: Add unit/e2e tests that simulate a long-running sync against a repository that receives many small commits without ever triggering `removeStaleWorktrees() > 0` (e.g., single worktree throughout), and assert that `git gc`/`reflog expire` still execute periodically and that `.git` object count/size stays bounded.

### Proof of Concept
1. Start `git-sync` with `--repo=<attacker-controlled-remote>`, `--root=/root`, `--stale-worktree-timeout=1h`, `--period=10s`.
2. Attacker (with push access to the tracked branch) pushes a new small commit every ~10s, faster than the stale-worktree-timeout, so `removeStaleWorktrees()` in `cleanup` at [6](#0-5)  always returns `n == 0` because the current worktree is younger than 1h and is excluded, and there is only ever at most one prior worktree that hasn't aged out.
3. Because `n == 0` every cycle, `cleanup` returns early and never executes `worktree prune`, `reflog expire`, or `git gc` at [7](#0-6) , while `git fetch`/`git reset --soft` continue pulling new objects into `/root/.git/objects` on every sync at [5](#0-4) .
4. Over time, `/root/.git` grows unbounded; eventually the underlying volume fills, causing subsequent `git fetch`/`worktree add` calls to fail and the sync loop to persistently error out, matching the "persistent sync denial" impact criterion.

Note: I was not able to independently verify the exact default value of `--stale-worktree-timeout` or its flag-parsing code within the available index (the `grep_search` for its definition returned only match counts, not the default value line), so the precise timing conditions under which `n` stays `0` indefinitely could not be fully confirmed from the indexed content alone.

```go
// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Expire old refs.
	git.log.V(3).Info("expiring unreachable refs")
	if _, _, err := git.Run(ctx, git.root, "reflog", "expire", "--expire-unreachable=all", "--all"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Run GC if needed.
	if git.gc != gcOff {
		args := []string{"gc"}
		switch git.gc {
		case gcAuto:
			args = append(args, "--auto")
		case gcAlways:
			// no extra flags
		case gcAggressive:
			args = append(args, "--aggressive")
		}
		git.log.V(3).Info("running git garbage collection")
		if _, _, err := git.Run(ctx, git.root, args...); err != nil {
			cleanupErrs = append(cleanupErrs, err)
		}
	}

	if len(cleanupErrs) > 0 {
		return cleanupErrs
	}
	return nil
}
```
