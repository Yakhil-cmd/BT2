### Title
Cross-organization team-membership forgery via unscoped `github_id` lookup in `MembershipHandler`/`Team.find_or_create_by!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up (or creates) a `Team` solely by `params.team.id`, without ever confirming — via `Team.find_team_on_github` or any other live check — that this team id actually belongs to `params.organization.login`. Because webhook signature verification is performed per-organization using that organization's own `webhook_secret`, an attacker who owns/administers *any* GitHub organization with a registered `webhook_secret` can sign a `membership` webhook where `organization.login` is their own org but `team.id` is the numeric GitHub team id of a **different** organization's team already known to Shipit, causing `add_member`/`members.delete` to mutate that unrelated team's membership.

### Finding Description
Binding that should hold: `params.team.id == Team.find_team_on_github(params.organization.login, params.team.slug).id` for the team record ultimately mutated. This is never checked.

Code path:
- `WebhooksController#verify_signature` selects the GitHub App config to verify against based on `repository_owner`, which for a `membership` event falls back to `params.dig('organization', 'login')` [1](#0-0) . This means the HMAC signature is checked against the `webhook_secret` configured for the organization *named in the attacker-controlled payload*, not the organization that actually owns `team.id`.
- If Shipit is configured multi-tenant (one `webhook_secret` per organization, per `Shipit.github(organization:)`), any org owner who has a registered webhook (e.g. their own org `A`) can produce a validly-signed `membership` payload with `organization.login: "A"` and an arbitrary `team.id` (e.g. a team id known to belong to victim org `B`), since the signature only proves knowledge of org `A`'s secret, not anything about `team.id`.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [2](#0-1) 
If a `Team` row with that `github_id` already exists (e.g. it was legitimately created earlier for org `B` via `Team.find_or_create_by_handle` or a prior genuine webhook), `find_or_create_by!` simply **finds** that existing record — the block (which sets `organization`) only runs on creation — and returns org `B`'s real `Team`. `add_member`/`members.delete` [3](#0-2)  is then invoked on that unrelated org's team.
- `Team.find_team_on_github`, the class's own verification helper that would call `gh_api.org_teams(organization, per_page: 100)` and filter by slug to confirm the team belongs to the claimed organization [4](#0-3) , exists in the same file but is **never invoked** from `MembershipHandler`.

Why guards don't catch this: `verify_signature` only proves the payload was signed by *some* org's secret matching the claimed `organization.login` field — it says nothing about whether `team.id` belongs to that org. The `ExplicitParameters` schema only enforces types (`Integer`, `String`) [5](#0-4) , not cross-field/cross-org integrity.

Downstream impact: `User#authorized?` grants Shipit access based on local `teams` membership intersected with `Shipit.github_teams` (locally-cached `Team` records for the configured `oauth.teams`) [6](#0-5) . If the victim team happens to be one of the org's configured authorization teams, this bug lets an attacker who controls an unrelated organization's webhook secret add an arbitrary existing Shipit `User` (identified only by GitHub login, via `User.find_or_create_by_login!(params.member.login)`) into that authorization team's local membership record, without any live GitHub check confirming true team membership.

### Impact Explanation
An attacker who administers any GitHub organization with a Shipit webhook configured (their own secret) can forge signed `membership` events that write to `Membership`/`Team` records belonging to a completely different organization's team, whose `github_id` they know or can guess/enumerate. Where that target team is used for OAuth authorization (`Shipit.github_teams`), this becomes an authorization-escalation path: an attacker-known or attacker-created Shipit user can be granted "member of an authorized team" status locally without ever actually being added to that team on GitHub. This matches the High-severity category "escalation into `Shipit.github_teams` authorization." It is repeatable per team id and does not require any Shipit session or API token — only ownership of one legitimately webhook-registered organization.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations/apps each with their own `webhook_secret`, and (2) the attacker being an administrator of at least one such registered organization (unprivileged relative to the victim org). Learning a victim team's numeric GitHub `id` may require some reconnaissance (team ids are visible via various GitHub API endpoints/UI depending on permissions), but the check that's missing is entirely absent — there is zero enforcement, so once the id is known the exploit is a single crafted, correctly-signed POST to `/webhooks`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify team-organization ownership before trusting or mutating any `Team` record: call `Team.find_team_on_github(params.organization.login, params.team.slug)` (or equivalent live Octokit `org_teams` lookup) and confirm the returned team's `id` matches `params.team.id`, rejecting the webhook if it doesn't. Additionally, scope `find_or_create_by!` by both `github_id:` and `organization:` so a payload cannot resolve to a team belonging to a different organization even without the live check.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "MembershipHandler rejects team id belonging to a different organization" do
  victim_team = shipit_teams(:cyclimse_cooks) # organization: "cyclimse", github_id: 2
  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => 'Cooks', 'slug' => 'cooks', 'url' => 'https://example.com' },
    'organization' => { 'login' => 'shopify' }, # attacker's own org, signed with shopify's secret
    'member' => { 'login' => 'attacker-controlled-user' },
    'repository' => { 'full_name' => 'shopify/some-repo' }
  }

  Team.expects(:find_team_on_github).with('shopify', 'cooks').returns(nil)
  # Current code never calls find_team_on_github, so this expectation fails,
  # and the handler proceeds to mutate cyclimse's team membership instead of rejecting it:
  assert_no_difference -> { victim_team.reload.members.count } do
    Shipit::Webhooks::Handlers::MembershipHandler.call(payload)
  end
end
```
Running this against the current code shows `Team.find_team_on_github` is never called and `victim_team.members.count` increases by one, proving the org-scoping binding does not hold.
