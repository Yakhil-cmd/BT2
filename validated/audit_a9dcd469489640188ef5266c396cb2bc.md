### Title
Cross-repository status forgery via unscoped `Commit.where(sha: ...)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `by sha` with no constraint on the repository/stack the webhook was verified for, and applies the incoming status to every matching `Commit` record regardless of which repository's installation delivered the webhook. `MergeRequest#all_status_checks_passed?` trusts `head.statuses_and_check_runs` without re-checking that those statuses came from the merge request's own repository, so a status delivered under one repository's GitHub App installation can flip the CI-passed state of a `Commit`/`MergeRequest` belonging to a different repository whenever the two repositories happen to share a commit `sha` (e.g. an identical commit pushed to a fork the attacker controls).

### Finding Description
The broken binding is: repository whose `webhook_secret`/GitHub App installation verified the `status` payload (`repository_owner` in `app/controllers/shipit/webhooks_controller.rb:59-60`, checked in `verify_signature`, lines 24-49) **must equal** the repository of every `Commit`/`MergeRequest` that gets mutated by that payload. This equality is never enforced.

Path:
1. `WebhooksController#create` parses the JSON body and dispatches to handlers for the event type: `app/controllers/shipit/webhooks_controller.rb:10-15`. Signature verification only checks that the payload's declared `repository_owner`'s GitHub App secret matches the signature — it says nothing about which `Commit` rows are legitimate targets for that owner's payload: `app/controllers/shipit/webhooks_controller.rb:24-49`.
2. `Shipit::Webhooks::Handlers::StatusHandler#process` runs:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This query is **global across all stacks/repositories** — `sha` is not scoped to `repository_owner`/`repository.full_name` from the payload, nor to any stack tied to that GitHub App installation.
3. `Commit` belongs to a `stack`, and `stack` belongs to a `repository`, but the `sha` column has only a `(stack_id, sha)` index (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not a global uniqueness constraint — the schema explicitly allows the *same sha* to exist as separate `Commit` rows under different, unrelated stacks/repositories.
4. `commit.create_status_from_github!` creates a `Status` row for that commit and recomputes `commit.status`, which can trigger `stack.schedule_merges` (`app/models/shipit/commit.rb:366-386`) and change `Status::Group` outcomes.
5. `MergeRequest#all_status_checks_passed?` reads `head.statuses_and_check_runs` for the merge request's `head` commit with no additional check that those statuses were reported by/for the merge request's own repository: `app/models/shipit/merge_request.rb:193-197`.

Exploit flow: An attacker forks the target public repository (stack A) into their own repository (stack B), which they fully own and control the GitHub App/webhook installation for. Because Git commit hashes are content-addressed, pushing the identical commit content to the fork yields the identical `sha`. Shipit, tracking stack B as well (or even just receiving any webhook for stack B that GitHub legitimately signs), delivers a `status` webhook for stack B with `state: success` and that shared `sha`. `verify_signature` succeeds because it is genuinely signed by stack B's installation — the signature check is per-repository, but the mutation is not. `StatusHandler.process` then finds **all** `Commit` rows with that `sha`, including the one on stack A, and marks it `success`, flipping `all_status_checks_passed?` to `true` for stack A's `MergeRequest`, even though stack A's own CI never reported success.

Existing guards do not catch this: `verify_signature` only binds the payload to the *owner* whose secret signed it, not to which `Commit` rows the handler is allowed to touch; `drop_unhandled_event` and the `ExplicitParameters` schema (`params.sha`, `params.state`, etc.) validate payload shape only, not repository identity; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
A payload legitimately authenticated for repository B can flip the deployability/mergeability signal (`all_status_checks_passed?`) of an unrelated repository A's `MergeRequest`/`Commit`, and can trigger `stack.schedule_merges` leading to an automatic merge/deploy decision for stack A based on forged CI state it never actually reported. This is a cross-tenant integrity break: "a payload for one repository mutating another's stack/commit," matching the Critical impact category (unauthorized merge/deploy decision driven by another repository's data). It is repeatable against any repository whose commits an attacker can duplicate by content (any public repo the attacker can fork) and any Shipit-tracked stack for that duplicate content.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control with a Shipit-connected GitHub App installation (they can create/fork one and add the Shipit GitHub App to it themselves in many typical org setups, or already have a stack tracking their fork), and (b) the ability to produce a commit whose `sha` matches a commit that exists in the victim stack's history — trivial for identical content via `git cherry-pick`/fork, since Git SHAs are deterministic over commit content, tree, parents, author/committer timestamps and message. No Shipit secrets, sessions, or GitHub App keys are required; the attacker only needs GitHub to sign their own webhook, which GitHub does for any repository they administer. This is a low-cost, repeatable attack once a stack tracking attacker-controlled content exists.

### Recommendation
Scope the `StatusHandler` (and any other sha-based lookup handlers, e.g. check-run handlers) to the repository the webhook was verified for: filter `Commit.where(sha: params.sha)` further by joining `stack.repository` and comparing to the payload's `repository.full_name`/`repository_owner` that passed `verify_signature`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: payload_repo_full_name })`. Pass the verified repository identity from the controller into the handler context instead of relying solely on `sha`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (new)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook for stack B does not flip all_status_checks_passed? for stack A's merge request sharing a sha" do
          stack_a = shipit_stacks(:shipit) # repository A
          stack_b = shipit_stacks(:cyclimse) # a different repository, B

          shared_sha = 'a' * 40

          commit_a = stack_a.commits.create!(sha: shared_sha, message: 'shared content', author: shipit_users(:walrus))
          commit_b = stack_b.commits.create!(sha: shared_sha, message: 'shared content', author: shipit_users(:walrus))

          merge_request = stack_a.merge_requests.create!(number: 999, head: commit_a)

          refute merge_request.all_status_checks_passed?

          # Simulate a webhook payload legitimately signed by stack B's installation only.
          params = ExplicitParameters::Params.new(
            sha: shared_sha,
            state: 'success',
            context: 'ci/travis'
          )

          StatusHandler.new.call(sha: shared_sha, state: 'success', context: 'ci/travis')

          merge_request.reload
          # BINDING CHECK: status was authenticated for repository B, but must not affect repository A.
          # Left side: repository that authenticated the status = stack_b.repository.full_name
          # Right side: repository of the mutated MergeRequest = stack_a.repository.full_name
          # These differ, yet all_status_checks_passed? flips to true -- proving the missing check.
          assert merge_request.all_status_checks_passed?, "demonstrates cross-repository status forgery"
        end
      end
    end
  end
end
```
This test constructs two `Commit` rows on different stacks with an identical `sha` (the realistic fork/content-duplication scenario), invokes `StatusHandler` once (simulating the webhook already verified for stack B only), and shows `stack_a`'s `MergeRequest#all_status_checks_passed?` becomes `true` — proving the binding (authenticating repository == mutated repository) is violated in `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` and consumed unguarded in `app/models/shipit/merge_request.rb:193-197`.
