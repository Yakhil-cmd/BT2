### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook signature is verified against the webhook secret belonging to the organization named in the payload's own `repository.owner.login` (or `organization.login`) field [1](#0-0) , but the handler that applies the payload's data never re-checks that the acted-upon `Commit` actually belongs to that same repository. `StatusHandler#process` looks up commits by `sha` across the *entire* database, with no scoping to `payload.dig('repository', 'full_name')` [2](#0-1) . This breaks the binding `organization that authenticated == repository that is written`, analogous to the Wildcat report's broken invariant where an action executed for one context (a batch/user) was allowed to affect global state it was never scoped to.

### Finding Description
Every other handler that mutates data scoped to a repository explicitly filters by the `stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` from the same payload used for verification, e.g. `PushHandler#process` (`stacks.not_archived.where(branch:)`) and `CheckSuiteHandler#process` (`stacks.where(branch: ...).commits.where(sha: ...)`) [3](#0-2) [4](#0-3) . The base `Handler` class even provides this exact scoping utility via `stacks`/`repository_name` [5](#0-4) .

`StatusHandler`, however, ignores this utility entirely and queries `Commit.where(sha: params.sha)` globally [2](#0-1) . `Commit` rows are not globally unique by `sha` across all tracked repositories — the same SHA can legitimately exist in more than one `Stack`'s commit history if repositories share commit history (forks, mirrors, or two Shipit stacks tracking the same upstream repo under different owners). The controller's `verify_signature` binds trust to "whichever org's webhook_secret matches `repository.owner.login`/`organization.login` in this payload" [6](#0-5) , and `Shipit.github(organization: ...)` explicitly supports separate secrets per organization [7](#0-6) . Nothing in `StatusHandler` re-validates that the commit it mutates belongs to the same `repository.full_name` that was authenticated.

Concretely: an attacker who owns/administers Org A (and thus can legitimately trigger and correctly sign a `status` webhook event for their own repo, e.g. via the GitHub Statuses API on their own token) can fork or otherwise obtain a repository that shares commit SHAs with a repository Shipit tracks under Org B. A `status` event fired for Org A's repo, correctly signed with Org A's webhook secret, will pass `verify_signature` (which only checks Org A's secret because `repository_owner` resolves to Org A) and will then be dispatched to `StatusHandler`, which writes a forged `Status` (`state`, `context`, `description`, `target_url`) onto any `Commit` row anywhere in the database matching that SHA — including Org B's tracked commit.

### Impact Explanation
Commit statuses drive Shipit's CI-gating logic (`ci.require`) and merge/deploy readiness checks. Forging a `success` status for a required CI `context` on a victim stack's commit lets an unprivileged attacker (who only controls their own, unrelated repository/organization) manipulate whether a commit is considered deployable/mergeable in a repository they have no legitimate access to — an escalation into cross-repository writes and a path to an unauthorized deploy/merge decision, consistent with the required High/Critical impact categories (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
The attacker only needs control of any GitHub repository/organization that a Shipit deployment is willing to accept webhooks from (their own, or one they can install the same GitHub App on), plus a commit SHA collision with a targeted stack (trivially obtainable by forking a tracked open-source repository, since forks preserve upstream SHAs for unmodified commits). No privileged Shipit credential, `ApiClient` token, or access to the target organization is required — only the ability to receive/sign a legitimate webhook for a repository they control, satisfying the "unprivileged attacker" constraint.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `CheckSuiteHandler`/`PushHandler`: resolve commits only through `stacks.commits.where(sha: params.sha)` (i.e., via `Repository.from_github_repo_name(repository_name)`) instead of an unscoped `Commit.where(sha: ...)`, so a status update can only ever affect commits that belong to the repository whose webhook secret authenticated the request.

### Proof of Concept
1. Attacker controls `attacker-org/forked-repo`, a fork of `victim-org/tracked-repo`, sharing an unmodified upstream commit `SHA_X` that Shipit already tracks as a `Commit` under `victim-org/tracked-repo`'s stack.
2. Attacker (with normal repo-owner privileges, e.g. via GitHub Actions or the Statuses API on their own repo) creates a `status` event for `SHA_X` with `state: "success"`, `context: "ci/required-check"` on `attacker-org/forked-repo`.
3. GitHub signs and delivers this webhook with `attacker-org`'s webhook secret; `repository_owner` resolves to `attacker-org`, and `verify_signature` passes because it validates against `attacker-org`'s own secret [6](#0-5) .
4. `StatusHandler#process` runs `Commit.where(sha: "SHA_X")`, which also returns the `Commit` belonging to `victim-org/tracked-repo`, and calls `commit.create_status_from_github!(params)` on it — writing an attacker-controlled CI status onto a commit in a repository the attacker never authenticated for [2](#0-1) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
