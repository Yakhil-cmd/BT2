### Title
Cross-repository CI status forgery via unscoped `StatusHandler` commit lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's multi-organization webhook signature verification selects the verifying `webhook_secret` based on an attacker-supplied field of the same unverified payload (`repository.owner.login`), and once a request passes verification, `StatusHandler` applies the `state` update to *any* `Commit` row in the whole database matching the given `sha`, without checking that the commit's repository matches the repository/organization whose secret validated the webhook. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
Webhook signature verification is dispatched per-organization: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the still-unverified JSON body (`params.dig('repository','owner','login')` or `organization.login`), and is used to pick which configured GitHub App/organization's secret validates the signature: [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly returns `true` (i.e. skips verification) whenever that organization has no `webhook_secret` configured: [4](#0-3) 

Once the request is accepted, the actual event handler is invoked with the full payload, and `StatusHandler` updates CI status by looking up commits **only by SHA, globally, with no repository/organization scoping at all**: [5](#0-4) 

Contrast this with every other handler (`PushHandler`, pull-request handlers), which correctly scope by `repository.full_name` via `Handler#stacks`/`Repository.from_github_repo_name`: [6](#0-5) [7](#0-6) 

**Binding broken (as equality):**
`organization_whose_secret_verified_signature == organization_of_repository_being_written`

In `StatusHandler` this equality is never checked — the handler writes a commit status for *whatever repository happens to contain a commit with the given SHA*, independent of which organization's key validated the delivery.

**Before attacker PR/request:** Only GitHub, holding the real `webhook_secret` for a given org/repo, can produce a valid `status` event for that repository's commits.

**After attacker request sequence:** An attacker who controls (or is a member of) *any* organization onboarded to this Shipit instance — including one with no `webhook_secret` configured, which is explicitly supported as valid config (`return true unless webhook_secret`) — can send a forged `status` webhook whose `repository.owner.login` matches their own (weakly- or un-secured) org, but whose `sha` is the public, well-known commit SHA of a commit belonging to a *different*, victim stack/repository tracked by the same Shipit instance. `StatusHandler` will apply that forged `state` (e.g. `success`) to the victim commit, because the lookup is `Commit.where(sha: params.sha)` with no repository filter.

### Impact Explanation
A forged "success" CI status on a victim's commit can satisfy `ci.require` checks defined in that stack's `shipit.yml`, which gate whether a commit is eligible to be shipped. This can lead to an **unauthorized deploy** of a commit that never actually passed the real CI pipeline — exactly the impact class ("unauthorized deploy") called out as acceptable in this exercise's rules. The severity is amplified by the fact that git commit SHAs are public/derivable (visible on GitHub, in PRs, commit emails, etc.), so the attacker does not need any secret information about the victim repository to target it — only the ability to send one legitimately-signed webhook from an organization they control.

### Likelihood Explanation
Likelihood depends on operational configuration: it requires (a) the Shipit instance being configured for multiple GitHub organizations (`Shipit.github_organizations`, explicitly supported per `lib/shipit.rb#github_app_config`), and (b) at least one onboarded organization having no `webhook_secret` set, or the attacker otherwise being able to produce a validly-signed delivery for any one org (e.g., a low-security demo/staging org, or one where the operator hasn't yet completed secret configuration). This is a plausible real-world misconfiguration in a system explicitly designed to host many independent organizations/teams on one instance, and requires no privileged Shipit account, API token, or session — only the ability to author one webhook HTTP request, which is unprivileged and within scope.

### Recommendation
- **Short term:** In `StatusHandler#process` (and any other handler relying on unscoped `Commit`/`Stack` lookups), scope the lookup to the repository/organization identified in `payload['repository']['full_name']`, and verify that repository's owner matches the organization whose key validated the signature (`repository_owner` used in `verify_signature`). Reject or ignore status/commit updates where these do not match.
- **Long term:** Enforce webhook secrets as mandatory (non-optional) for every configured organization, removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`, so that a misconfigured/secret-less organization can never be used to smuggle events into other organizations' stacks.

### Proof of Concept
1. Shipit instance is configured with two organizations in `secrets.github`: `victim-org` (has `webhook_secret` set, tracks stack for `victim-org/app`) and `attacker-org` (onboarded but `webhook_secret` left blank/unset).
2. Attacker identifies a public commit SHA `S` belonging to `victim-org/app` that is currently pending/failing a required CI check referenced by that stack's `shipit.yml` `ci.require`.
3. Attacker sends `POST /webhooks` with header `X-Github-Event: status`, and JSON body:
   ```json
   {
     "sha": "S",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" }
   }
   ```
   No `X-Hub-Signature` header is required to pass, because `repository_owner` resolves to `attacker-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` short-circuits to `true` (`app/controllers/shipit/webhooks_controller.rb#verify_signature`, `lib/shipit/github_app.rb#verify_webhook_signature`).
4. `StatusHandler#process` runs `Commit.where(sha: "S").each { |commit| commit.create_status_from_github!(params) }`, which finds and updates the commit belonging to `victim-org/app`, regardless of the payload's claimed (and unrelated) `repository.full_name`.
5. `victim-org/app`'s required CI status is now forged as `success`, potentially allowing the corresponding commit to be shipped/deployed without having passed real CI.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
