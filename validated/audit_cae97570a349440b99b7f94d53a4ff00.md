### Title
API clients can spoof `current_user` attribution via the unauthenticated `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The Shipit API authenticates the *caller* via an `ApiClient` bearer token (`authenticate_api_client`), but attributes the *actor* of privileged operations (deploys, rollbacks, locks, merges) via a separate, completely unauthenticated `X-Shipit-User` HTTP header. Any request that carries a valid `ApiClient` token can set this header to an arbitrary GitHub login already known to Shipit, causing the engine to bind the resulting `Task`/`Deploy`/`Lock`/`MergeRequest` record to a `User` the caller never authenticated as.

### Finding Description
`authenticate_api_client` verifies the request's bearer token against `ApiClient.authenticate`, which proves only that the caller possesses a valid `ApiClient` token: [1](#0-0) 

Separately, `current_user` — used throughout the API to record who performed an action — is derived from `identify_user`, which trusts the client-supplied `X-Shipit-User` header with no cryptographic binding to the authenticated `ApiClient`: [2](#0-1) 

This breaks the intended binding: **`ApiClient` identity (the credential that is actually verified) ≠ `User` identity (the actor bound to the resulting record)**. The `ApiClient` model only enforces coarse `permissions` (e.g. `deploy:stack`, `lock:stack`) and, optionally, a `stack_id` scope — it has no notion of "acting as user X": [3](#0-2) 

Because `current_user` is trusted at face value, this attacker-controlled identity flows directly into consequential model calls:
- `stack.trigger_deploy(commit, current_user, ...)` in `Api::DeploysController#create` [4](#0-3) 
- `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` in `Api::RollbacksController#create` [5](#0-4) 
- `stack.lock(params.reason, current_user)` in `Api::LocksController#create`/`#update` [6](#0-5) 
- `MergeRequest.request_merge!(stack, params[:id], current_user)` in `Api::MergeRequestsController#update` [7](#0-6) 

Most notably, `User#github_api` falls back to a per-user GitHub client using that user's own stored `github_access_token`: [8](#0-7) 

If any downstream code path uses the attributed `merge_requested_by`/`aborted_by`/task-creator user's `github_api` (rather than `stack.github_api`) to perform GitHub actions, an attacker who only holds a low-privilege `ApiClient` token (e.g., scoped to `deploy:stack` on one stack) could cause GitHub API calls to be made using a **different, more privileged user's stored `github_access_token`**, purely by spoofing the `X-Shipit-User` header value to that victim's login. At minimum, it allows falsifying the audit trail of who triggered a deploy/rollback/lock/merge for any Shipit user account, and can be leveraged to bypass any authorization logic elsewhere in the app that trusts `current_user` identity (e.g. team-membership-based checks) rather than the `ApiClient`'s own scoped permissions.

### Impact Explanation
This crosses the "GitHub identity vs. the `User` bound to the session" boundary called out in scope: the request is authenticated as an `ApiClient`, but the `User` record acted upon/attributed is chosen unilaterally by the client via a plain header, with no verification that the two are the same principal or that the `ApiClient`'s creator is authorized to act as that `User`. This can result in an unauthorized deploy/rollback/lock/merge being attributed to (and, if `github_access_token`-based code paths are hit, executed as) an arbitrary victim user, which matches the High-severity impact category: "escalation into `Shipit.github_teams` authorization" / unauthorized deploy or merge attribution.

### Likelihood Explanation
Any holder of a legitimate `ApiClient` token — even one scoped with minimal permissions to a single stack — can trivially set the `X-Shipit-User` header to any known GitHub login in the Shipit database (e.g., a login harvested from the stack's commit history or team member list) without needing to know that user's password, GitHub token, or session. No additional credential is required beyond the API token the caller already legitimately possesses for other operations.

### Recommendation
Do not allow the caller to freely choose the attributed `User` via a request header. Either (a) bind `current_user` to the `ApiClient`'s own `creator` association, or (b) require a `X-Shipit-User` claim to be cryptographically signed/verified the same way `ApiClient` tokens are (e.g., via `SimpleMessageVerifier`), and reject any value that isn't independently authenticated. Any Human-attributable action should require verifying that the acting identity is genuinely tied to the credential presented, not a bare, attacker-suppliable header.

### Proof of Concept
1. Attacker obtains a valid `ApiClient` bearer token scoped only to `deploy:stack` for `stack A` (e.g., a CI integration token).
2. Attacker sends `POST /api/stacks/:id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: victim_admin_login` (a login known to exist in Shipit, e.g. seen in commit authorship).
3. `identify_user` resolves `current_user` to the `User` record for `victim_admin_login` purely from the header, per `app/controllers/shipit/api/base_controller.rb:69-72`.
4. `stack.trigger_deploy(commit, current_user, ...)` records the deploy as triggered by `victim_admin_login`, and any downstream logic keyed off that `User` (audit trail, `merge_requested_by`, or `github_api`-based GitHub calls) operates as that victim, without the victim's knowledge or the caller ever proving control of that identity.

# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
