### Title
Permissionless `pallet-assets` asset creators can permanently freeze `pallet-asset-conversion` liquidity pools built on their own asset, DoS-ing and locking other users' liquidity - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
The Solana report's root cause is: an AMM pool trusts an externally-controlled token mint that can carry a "freeze authority," and the pool never validates the absence of that authority before accepting the mint as tradable collateral, so the freeze authority can later freeze the pool's vault and permanently DoS withdrawals. The Polkadot SDK analog is structurally identical: `pallet-assets` lets any signed account permissionlessly create an asset and become that asset's **Freezer** (the role-based equivalent of a "freeze authority"), and `pallet-asset-conversion` permissionlessly creates pools and accepts *any* `AssetKind` as a pairing asset without validating who controls its Freezer role. Once other users deposit liquidity that includes the attacker-created asset, the attacker (acting purely in their normal, non-privileged Freezer capacity over their own asset) can call `Assets::freeze`/`Assets::block` on the pool's account, which sets `Account::status = Frozen`, causing all subsequent transfers *out of* the pool account for that asset to fail with `Error::<T,I>::Frozen`.

### Finding Description
- `pallet-assets`'s `create` dispatchable is reachable via a plain signed extrinsic; on AssetHub runtimes, `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` [1](#0-0) , so anyone can create a `TrustBackedAssets` asset and, per standard `pallet-assets` semantics, control the roles (owner/issuer/admin/freezer) for that asset.
- The `Freezer` role can call `freeze`/`block` on any account holding that asset; this is exercised in tests: freezing account `2` blocks all outgoing transfers from `2` while transfers *into* `2` still succeed [2](#0-1) , and `freeze_asset`/`AssetNotLive` similarly blocks transfers for the whole asset [3](#0-2) .
- The freeze check is enforced directly in the balance/transfer path: `reducible_balance` returns an error and `do_transfer`-style code paths check `ensure!(!account.status.is_frozen(), Error::<T, I>::Frozen)` [4](#0-3) .
- `pallet-asset-conversion`'s `create_pool`/`add_liquidity` accept `T::AssetKind` (any asset satisfying the runtime's `AssetKind` bound, including arbitrary `TrustBackedAssets`/`ForeignAssets`) without any validation of who administers the Freezer/Admin role for that asset kind, as shown by the emulated test flow: a user mints/creates an asset, then calls `AssetConversion::create_pool` and `add_liquidity` for the native/asset pair, all with a plain signed origin and no permission checks tying pool creation to asset governance [5](#0-4) .
- Liquidity removal transfers the pooled assets *from the pool account* to the withdrawer: `T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)` and the analogous `asset2` transfer [6](#0-5) , and this whole `do_remove_liquidity` operation is executed through the `#[transactional]` `MutateLiquidity::remove_liquidity` wrapper [7](#0-6) , meaning if the transfer for the frozen asset fails, the entire extrinsic (including the transfer of the *other*, non-frozen asset) reverts — freezing out withdrawal of both legs of the pool.

Attack path (no privileged role, no governance, no malicious node/collator required):
1. Attacker calls `Assets::create` (permissionless, signed) to create asset `X`, becoming its Freezer/Admin/Issuer/Owner.
2. Attacker (or anyone) calls `AssetConversion::create_pool(Native, X)` (permissionless).
3. Victims call `AssetConversion::add_liquidity(Native, X, ...)`, depositing native tokens and `X` into the pool account.
4. Attacker, using their ordinary (non-privileged) Freezer role over asset `X`, calls `Assets::freeze(origin=attacker, id=X, who=pool_account)` or `Assets::block`.
5. Every subsequent `remove_liquidity` and `swap_*` call that needs to transfer `X` *out of* the pool account now fails with `Error::<Assets>::Frozen`, and because the operation is transactional, the victim's native-token leg is rolled back too — the victims' liquidity (both assets) becomes permanently unwithdrawable as long as the freeze stands, which the attacker (as Freezer) can maintain indefinitely.

### Impact Explanation
This is a direct structural analog of the reported bug: an externally/attacker-controlled "freeze authority" over the asset backing a liquidity pool's vault can be exercised post-deposit to permanently DoS withdrawals and lock other users' funds. As in the original report, the loss is not immediate theft but indefinite freezing of user funds in the pool (both the malicious asset and the paired native/other asset, due to the transactional remove-liquidity path), which the original researchers and the affected team classified as Medium risk with an accepted recommendation to validate absence of such freeze control before trusting a token as pool collateral.

### Likelihood Explanation
High reachability, low cost: creating an asset and a pool are both ordinary permissionless signed extrinsics with no special origin, and the Freezer role is a completely standard, intended capability of any asset creator over their own asset — no theft of keys, no governance capture, and no malicious infrastructure component is required. The only precondition is that a victim chooses to add liquidity against an asset whose Freezer is not otherwise trusted, which is exactly the scenario the original report's recommended mitigation targets (validating the absence of unilateral freeze control before accepting a token into the pool).

### Recommendation
- In `pallet-asset-conversion`'s `create_pool` (and/or `add_liquidity`), add an explicit check equivalent to the report's `mint::freeze_authority = COption::None` recommendation: reject (or clearly flag as unsafe) any `AssetKind` whose `pallet-assets` `Freezer`/`Admin` is not a trusted/none entity, or provide a governance-curated allow-list for assets eligible for AMM pools (mirroring how `PoolAssetsInstance`/`ForeignAssets` are already gated more tightly than arbitrary `TrustBackedAssets`).
- Alternatively/additionally, ensure `remove_liquidity` degrades gracefully (partial/emergency withdrawal path) instead of fully reverting when one leg's asset is frozen, so a malicious Freezer on one side of a pair cannot also trap the healthy asset leg.

### Proof of Concept
Not independently executed in this session — the reachability of `Assets::create`, `AssetConversion::create_pool`/`add_liquidity`, and the transfer/`Frozen` enforcement path were each confirmed via existing repository tests/integration tests cited above (`swap_locally_on_chain_using_local_assets`, `transferring_from_frozen_account_should_not_work`, `reducible_balance`/`do_transfer` frozen checks, and the `#[transactional]` `remove_liquidity` wrapper). A concrete local FRAME integration reproduction (mock runtime combining `pallet-assets` + `pallet-assets-freezer` + `pallet-asset-conversion`, asserting: attacker creates asset → pool created → victim adds liquidity → attacker calls `freeze`/`block` on pool account → victim's `remove_liquidity` fails with `Error::<Assets>::Frozen` and pool balances are unchanged) has **not** been written or run; this should be produced and executed to fully validate the exact error surfaced and whether any existing runtime-level allow-list (e.g., restricting AMM asset pairing to `Sufficient`/curated `ForeignAssets`) already mitigates this in production AssetHub configurations before treating this as bounty-eligible.
