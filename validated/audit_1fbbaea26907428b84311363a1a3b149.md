### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while the write target is bound to `repository.full_name` — cross-organization forgery of stack and team-membership events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a Shipit deployment configured with multiple GitHub organizations (multi-tenant mode), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using a field read directly out of the still-unverified JSON body (`repository.owner.login` or `organization.login`). Every downstream `Handlers::Handler` subclass, however, decides which `Repository`/`Stack` (or, for `MembershipHandler`, which `Team`) to mutate using a *different* field of the same body: `repository.full_name` (or `organization.login` again for teams), with no cross-check that this target actually belongs to the organization whose secret validated the request. An attacker who legitimately controls one organization's webhook secret in a shared Shipit instance can therefore forge a signed payload whose "owner" fields point at their own org (so the signature check passes) while its `repository.full_name`/team fields point at a completely different organization's stack or team, causing Shipit to act on that unrelated target.

### Finding Description
`verify_signature` computes the verification organization from the raw, unauthenticated payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `webhook_secret` from `secrets.github`, which is a supported multi-tenant configuration mode: [3](#0-2) 

Once the signature is accepted, every handler resolves its target repository from a *different* payload field (`repository.full_name`), independent of the field used to pick the verification secret: [4](#0-3) [5](#0-4) 

The same disconnect exists for team membership: the team's `organization` is taken from `params.organization.login` and used to create/attribute the team and add members, with no check that this organization matches the one whose secret validated the signature: [6](#0-5) 

`Shipit.github_teams` (used for authorization) is built from `github.oauth_teams`, i.e. teams that `MembershipHandler` populates via forged `membership` events: [7](#0-6) 

**Binding broken:** *organization that authenticated the request* (secret selected via `repository.owner.login` / `organization.login`) ≠ *repository/team that is written* (`repository.full_name` / `organization.login` reused for the actual mutation), with the only invariant relied upon being that GitHub itself always keeps these fields consistent for legitimately delivered webhooks. Since the endpoint accepts arbitrary POSTed JSON as long as the HMAC matches, an attacker who knows any one organization's `webhook_secret` configured on the instance can break this invariant deliberately.

- Before the attacker's request: for any real webhook, `repository.owner.login == organization that owns full_name`, and the secret used for verification is that same organization's secret — the two are always equal.
- After the attacker's forged request: the attacker sets `repository.owner.login`/`organization.login` to their own known-secret organization (so `verify_signature` passes), but sets `repository.full_name` (or the `organization` embedded in a `membership` payload) to a different organization/repository entirely. The equality is broken, and the handler still executes against that unrelated target.

### Impact Explanation
Two concrete exploitation paths follow this pattern, both in the required High/Critical impact set:
1. **Cross-repository/cross-organization writes and unauthorized actions**: a forged `push` (or other) event with a spoofed `full_name` causes `PushHandler#process` to call `stack.sync_github` on stacks belonging to a repository the attacker does not control, and other handlers (`pull_request`, `status`, etc.) similarly act on `Repository.from_github_repo_name(payload full_name)` for arbitrary repositories present on the instance.
2. **Escalation into `Shipit.github_teams` authorization**: a forged `membership` event whose `organization.login`/`team` fields target the org backing `Shipit.github_teams` lets the attacker add themselves (`team.add_member(member)`) to a team used for Shipit's own access control, escalating their authenticated privileges within the app.

### Likelihood Explanation
Exploitability requires that the Shipit instance be configured in the documented multi-organization mode (`secrets.github` keyed by organization, each with its own `webhook_secret`), and that the attacker legitimately possesses/administers at least one such organization's webhook secret on that shared instance (e.g. as an admin of their own GitHub App installation configured on the shared Shipit deployment) — a realistic scenario for any Shipit-as-a-service / shared multi-tenant setup, which the codebase explicitly supports (`github_default_organization`, `github_organizations`, `github_app_config`). No GitHub App private key, `GITHUB_TOKEN`, Shipit session, or `ApiClient` token is needed — only knowledge of one tenant's webhook secret, which that tenant is expected to know by design.

### Recommendation
- After signature verification succeeds, re-derive and enforce that the organization used to select the verification secret matches the organization implied by every payload field the handler will act on (`repository.full_name`'s owner, or the `organization.login` used to create/attribute a `Team`), rejecting the request otherwise.
- Alternatively, scope webhook secret lookup by the same field used for the write (`repository.full_name`'s owner) rather than a separately-trusted `repository.owner.login`/`organization.login`, so the two can never diverge.
- For `MembershipHandler`, validate that `params.organization.login` matches the verified webhook organization before creating/updating `Team` records or team membership.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `secrets.github` containing at least `org-a` (attacker-controlled, secret known to attacker) and `org-b` (victim, has a stack `org-b/victim-repo`).
2. Attacker builds a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "org-b/victim-repo",
    "owner": { "login": "org-a" }
  }
}
```
3. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over this exact raw body and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which succeeds because the attacker used `org-a`'s real secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, and triggers `stack.sync_github(expected_head_sha: ...)` on the victim org's stack — an action the attacker was never authorized to trigger, using only credentials belonging to `org-a`.
6. An analogous forged `membership` payload (`organization.login` pointed at the org backing `Shipit.github_teams`) lets the attacker add themselves to a privileged team via `MembershipHandler#process`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
