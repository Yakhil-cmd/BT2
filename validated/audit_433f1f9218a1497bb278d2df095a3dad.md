### Title
Non-atomic dual persistence between kvstore batch and SQL commit during AA trigger processing can permanently corrupt AA state after a crash - ([File: aa_composer.js])

### Summary
`handlePrimaryAATrigger` writes AA response-unit data and state-variable changes to the kvstore (`batch.write`) and only afterwards commits the corresponding SQL transaction. If the node process is killed/crashes in the window between the durable kvstore write and the SQL `COMMIT`, the kvstore already reflects the AA's new state while the SQL database (which drives trigger-completion bookkeeping via the `aa_triggers` table) still shows the trigger as unprocessed. On restart, `handleAATriggers` re-selects the still-present row from `aa_triggers` and reprocesses the same trigger against state variables that were already advanced by the crashed run, effectively double-applying state changes. This mirrors the root cause pattern in CVE-2025-46733: two persistence domains that are supposed to be updated atomically together (secure-storage responses vs. TA in-memory/keepAlive state in OP-TEE; kvstore vs. SQL DB here) can be desynchronized by an untimely crash, letting an attacker-influenced execution path corrupt state that is meant to be tamper-resistant/monotonic (AA "keepAlive"-style persistent state, analogous to fTPM PCRs).

### Finding Description
`handlePrimaryAATrigger` in `aa_composer.js` processes a trigger inside one SQL transaction (`conn.query("BEGIN")` ... `conn.query("COMMIT")`) and one shared kvstore `batch`: [1](#0-0) 

The ordering is: run `handleTrigger` (which internally calls `writer.saveJoint` for the AA response unit and `saveStateVars()` which writes updated state variables into the shared `batch`), then `batch.write({ sync: true }, ...)` to durably persist the kvstore changes, and only *after* that succeeds does it issue `conn.query("COMMIT")` for the SQL transaction: [2](#0-1) 

`writer.saveJoint` defers its own kvstore write when running "in a larger tx" (i.e., when called from AA processing) precisely so the outer `handlePrimaryAATrigger` batch write covers everything: [3](#0-2) 

State variables are read from and written to the kvstore independently of the SQL transaction/rollback semantics: [4](#0-3) [5](#0-4) 

Whether a trigger still needs processing is determined purely from the SQL `aa_triggers` table, which is only cleared inside the same transaction that is committed *after* the kvstore batch write: [6](#0-5) [7](#0-6) 

If the process crashes (or is killed) after the kvstore `batch.write` callback fires but before the SQL `COMMIT` completes, the kvstore-side changes (new AA state var values, the response-unit joint blob, storage-size updates, etc.) are durably on disk, but the SQL transaction is rolled back on restart by the database engine (uncommitted transactions do not survive a crash). Consequently, on restart:
- The `aa_triggers` row for that trigger is still present (never deleted).
- The response unit's row was never inserted into `units`.
- `handleAATriggers` will select and reprocess the same trigger from scratch, calling `handlePrimaryAATrigger` again.
- Inside this second run, `readVar`/`readAAStateVar` (`formula/evaluation.js:2807-2835`, `storage.js:1013-1022`) will read the *already-updated* values from the kvstore left behind by the crashed run, not the pre-trigger values, because kvstore reads have no relation to SQL transaction boundaries.

This means the AA's oscript formulas execute a second time on top of state that already includes the first (uncommitted-in-SQL) execution's effects — i.e., the same trigger effectively runs twice against monotonically-updated state (e.g., `var['balance'] -= amount` applied twice, `var['count'] += 1` incremented twice, a payment computed from `balance` output twice), while the SQL side will now finally commit a *second* response unit for the same original trigger. The forced-crash-on-uncaught-exception design in `network.js` makes any uncaught exception thrown deep inside AA/oscript trigger handling turn into exactly this kind of hard process crash: [8](#0-7) 

There are numerous `throw Error(...)` statements reachable synchronously from trigger processing and formula evaluation that would trigger this crash path if hit unexpectedly, for example unexpected validation outcomes while saving the AA's own generated response unit: [9](#0-8) 
or unrecognized/invalid intermediate values deep in the oscript evaluator (`formula/evaluation.js:2757`, `formula/evaluation.js:3050-3097`, `formula/evaluation.js:3136-3166`). Any of these being hit unexpectedly for a trigger sent by an ordinary unit poster or AA author (who fully controls the AA definition and the trigger payload/data) converts a purely local logic bug into a full node crash at an attacker-influenceable moment, which combined with the non-atomic kvstore/SQL persistence above can desynchronize and corrupt AA-controlled fund/state accounting analogous to how OP-TEE's TA panic/reload desynchronized fTPM's PCR state from its supposed non-resettable guarantee.

### Impact Explanation
If exploited, replaying the same trigger against already-advanced kvstore state can cause an AA to double-apply balance/state mutations (loss or duplication of AA-held funds, i.e., AA fund loss/inflation) or to emit an extra, unintended response unit for the same trigger, causing nodes that crashed at that exact point to diverge from nodes that did not — a node disagreement on AA-derived unit/state validity. This falls under the accepted impact categories ("AA fund loss or freezing", "supply inflation", "node disagreement on validity or stability").

### Likelihood Explanation
Exploitation requires the attacker to (a) craft an AA/trigger whose processing reaches an unguarded `throw Error(...)` inside the trigger-processing pipeline (multiple such paths exist and are reachable via ordinary AA definitions/getters/remote_func_call complexity metadata) and (b) have that exception land in the narrow window between the kvstore `batch.write` completing and the SQL `COMMIT` completing. Precisely timing (b) from a remote, unprivileged attacker is difficult without additional information (e.g., ability to induce resource exhaustion or crash timing), so likelihood is moderate rather than trivial — the root-cause design flaw (non-atomic dual persistence keyed on two independent stores) is concretely present in the code, but reliable weaponization needs a reachable crash trigger correlated with the specific write ordering.

### Recommendation
Make the kvstore batch write and the SQL commit atomic with respect to trigger-completion bookkeeping: either (1) write the kvstore batch only after the SQL transaction has durably committed (reversing the current order), or (2) record a persisted "checkpoint"/idempotency marker (e.g., a monotonically increasing sequence tied to the batch) in the same kvstore write so that on restart the code can detect a batch that was written but whose SQL counterpart never committed, and roll forward (finish the SQL commit) instead of reprocessing the trigger from scratch. Additionally, audit all `throw Error(...)` calls reachable from AA trigger/oscript evaluation that currently cause a full process crash via `network.js`'s `uncaughtException` handler, and convert those that stem from externally influenceable AA data into recoverable error paths (bounce the trigger) instead of crashing the process.

### Proof of Concept
1. Deploy an AA with `keepAlive`-like persistent state (e.g., a running balance/state var updated on each trigger) and post a trigger to it.
2. Kill the node process (`kill -9`) precisely after the console log "AA batch write took …ms" is printed in `handlePrimaryAATrigger` (aa_composer.js:112) but before "committed unit …" is printed by the subsequent SQL commit — this is deterministically reproducible in a controlled/test environment by inserting a `process.exit()` between the two calls at aa_composer.js:111-115 for demonstration purposes.
3. Restart the node. Observe that `aa_triggers` still contains the trigger row (SQL not committed) while `storage.readAAStateVars(address, ...)` already shows the updated post-trigger values (kvstore committed).
4. Observe `handleAATriggers` reprocess the same trigger, causing the AA's state-mutating formulas to execute a second time on top of already-updated values, producing incorrect (duplicated) balance/state changes and a duplicate response unit for the original trigger.
