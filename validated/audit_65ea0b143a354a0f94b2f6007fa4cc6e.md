### Title
Multi-tenant webhook signature does not bind to `repository.full_name`, allowing any trusted org to forge webhooks that create/mutate Stacks under a different org's Repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
In multi-org Shipit deployments, `WebhooksController#verify_signature` selects the HMAC secret using `repository_owner`, a value read straight out of the untrusted, attacker-supplied JSON body (`params.dig('repository','owner','login')`), and never cross-checks it against `repository.full_name`, which is the value handlers actually use to resolve the `Shipit::Repository`. An attacker who legitimately owns/administers one trusted org in the Shipit installation (and therefore knows that org's `webhook_secret`) can sign an arbitrary payload whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` names a victim org's repository. `OpenedHandler#process` then resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to the victim's `Repository` and, if that repository has `review_stacks_enabled` with `allow_all`, creates a live `ReviewStack` in the victim's namespace via `ReviewStackAdapter#find_or_create!`.

### Finding Description
The claimed binding is: `verifying_org == repository.full_name owner` (the org whose secret validated the signature must equal the owner segment of `repository.full_name` used downstream). Tracing the code shows this binding is never enforced:

- `WebhooksController#verify_signature` derives the signing org solely from the payload: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [1](#0-0) .
- `GitHubApp#verify_webhook_signature` only proves the raw body was HMAC-signed with the secret registered for that specific `repository_owner`/org — it makes no assertion about `repository.full_name` at all [2](#0-1) .
- `Shipit.github(organization:)` looks up a per-org config only when the installation is running in multi-org mode (`github_default_organization` non-nil); each configured org has its own independent `webhook_secret` [3](#0-2) .
- `OpenedHandler#repository` then resolves the repository purely from `params.repository.full_name`, a field with no relationship enforced to `repository_owner` used for signature validation: `Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new` [4](#0-3) .
- If that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all?`, `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates a `ReviewStack` scoped to the resolved (victim) repository, with `branch`/`environment` taken from attacker-controlled `params.pull_request.head.ref` and `params.number` [5](#0-4) [6](#0-5) .

Exploit flow: attacker administers/owns "org-attacker", one of the orgs configured/onboarded into this Shipit instance's `secrets.github` (multi-org schema), and therefore knows `org-attacker`'s `webhook_secret` (set when they created their GitHub App, per `docs/setup.md`'s "Webhook secret" step). They POST to `/webhooks` with `X-Github-Event: pull_request`, a body where `repository.owner.login = "org-attacker"` and `repository.full_name = "org-victim/app"`, and `X-Hub-Signature` computed with `org-attacker`'s own webhook secret. `verify_signature` looks up and validates against `org-attacker`'s secret — which succeeds because the attacker legitimately controls it — and the request proceeds. The handler then acts on `org-victim/app`.

No other guard intercepts this: `drop_unhandled_event` only checks the event type, `ExplicitParameters` schema only checks types/presence of fields (not cross-field relationships), and there is no model validation tying `repository.owner.login` to `repository.full_name`.

Caveat on the ContinuousDeliveryJob leg specifically: `ReviewStackAdapter#stack_attributes` hard-codes `continuous_deployment: false` for newly created review stacks [7](#0-6) , and `ContinuousDeliveryJob#perform` immediately returns unless `stack.continuous_deployment?` [8](#0-7) . So the automatic "deploy via ContinuousDeliveryJob" leg of the question does not hold for freshly-created review stacks without a further privileged action (a maintainer toggling `continuous_deployment`); the unauthorized-stack-creation-under-victim's-namespace leg, however, is confirmed.

### Impact Explanation
An attacker who controls one legitimately onboarded org in a multi-tenant Shipit installation can, using only their own org's webhook secret, forge a webhook that Shipit will process as if it came from any other onboarded org's repository. For any victim repository with `review_stacks_enabled` and `provisioning_behavior_allow_all?`, this creates a `Shipit::ReviewStack` row (a real `Stack`) in the victim org's namespace, with an attacker-chosen `branch`/head ref and environment name, and enqueues it for provisioning (`ReviewStackProvisioningQueue.add(stack)`). This is a cross-tenant write: "a payload for one repository mutating another's stack," matching the Critical category. The attack is repeatable against any repository in any onboarded org for as long as the attacker's own org credentials remain valid, and it also applies to sibling handlers (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `AssignedHandler`, `EditedHandler`) that resolve `repository` the same way, enabling forged archive/unarchive/label-driven state changes on victim stacks as well.

### Likelihood Explanation
This requires the Shipit instance to be configured in the multi-org schema (`secrets.github` keyed by organization, per `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml`) with at least two onboarded orgs, and requires the victim repository to have `review_stacks_enabled` with `provisioning_behavior_allow_all` (or an equivalent label-driven behavior an attacker can trivially satisfy by labeling their own forged PR payload). The attacker's cost is minimal: they only need to be an administrator/owner of any one org already onboarded to the Shipit instance (which they may legitimately be, e.g., a different team's org in the same enterprise) and craft a raw HTTP POST with a correctly computed HMAC using their own known secret — no GitHub-side interaction, no Shipit session, and no victim secrets are needed. This is fully repeatable and scriptable.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (or in the shared `Handler` base class), after resolving `repository_owner` for signature verification, require that it matches the owner segment of `params.dig('repository','full_name')` (and/or `params.dig('organization','login')`) before dispatching to any handler; reject the request (422) on mismatch. More robustly, derive the org used to look up the webhook secret and the org used to resolve the `Repository` from the same, single trusted field, and validate that every event references only repositories belonging to the org whose secret verified the signature.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (multi-org variant)
test "org-attacker signed webhook cannot create a Stack under org-victim's Repository" do
  # Setup: multi-org secrets fixture with OrgAttacker and OrgVictim, each with distinct webhook_secret
  victim_repo = Shipit::Repository.create!(owner: "org-victim", name: "app",
                                            review_stacks_enabled: true,
                                            provisioning_behavior: :allow_all)

  payload = payload_parsed(:pull_request_opened)
  payload["repository"]["owner"]["login"] = "org-attacker" # binds signing org
  payload["repository"]["full_name"] = "org-victim/app"    # diverges from signing org
  raw = payload.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest(
    "sha1",
    ORG_ATTACKER_WEBHOOK_SECRET, # known to the attacker, admin of org-attacker
    raw
  )

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  # Equality under audit: verifying_org ("org-attacker") == repository.full_name owner ("org-victim")?
  assert_not_equal "org-attacker", "org-victim" # binding is broken before the request even lands

  assert_no_difference -> { victim_repo.stacks.count } do
    post :create, body: raw, as: :json
  end
  # Currently FAILS: a ReviewStack row is created under victim_repo despite the signature
  # having been verified only against org-attacker's secret.
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
