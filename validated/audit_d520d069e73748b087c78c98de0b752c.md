### Title
Cross-repository CI status forgery via organization/repository binding break in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the incoming payload's HMAC signature against based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

Shipit natively supports configuring multiple independent GitHub organizations, each with its own `webhook_secret`, `app_id`, and `oauth` credentials, all served through the same `/webhooks` endpoint: [3](#0-2) 

Once the signature verifies (using the secret belonging to whichever org is named in `repository.owner.login`), the raw JSON body is dispatched unmodified to event handlers: [4](#0-3) 

`StatusHandler`, which processes GitHub `status` events, resolves the target commit purely by `sha`, with **no repository scoping whatsoever** — it does not call the `Handler#stacks`/`repository_name` helper that other handlers use to scope by `repository.full_name`: [5](#0-4) 

Compare this to `Handler#stacks`, which other handlers (push, pull_request, etc.) use to scope to the repository named in the payload: [6](#0-5) 

This breaks the binding: `organization authenticated by verify_signature (repository.owner.login)` == `repository whose Commit/Status gets written (params.sha, unscoped)`. The org whose webhook_secret is used to authenticate the request has no relationship at all to which stack's commit receives the forged status, because `StatusHandler` queries `Commit.where(sha: params.sha)` across the entire Shipit instance database, not scoped to any repository or organization.

### Impact Explanation
In a multi-org deployment, an attacker who legitimately controls one configured GitHub organization/App (e.g., "attacker-org", with its own valid `webhook_secret` that the attacker knows because it is their own App's secret) can send a POST to the shared `/webhooks` endpoint with:
- `repository.owner.login` = `"attacker-org"` (or `organization.login`) so `verify_signature` picks attacker-org's secret and the HMAC verifies successfully, and
- `X-Github-Event: status`, `sha` = an arbitrary/guessed commit SHA belonging to a victim organization's stack tracked by the same Shipit instance.

`StatusHandler#process` will create a forged `Status` (e.g. `state: "success"`) on `Commit.where(sha: params.sha)` regardless of which org/repository that commit actually belongs to: [7](#0-6) 

Status creation triggers `commit.schedule_continuous_delivery`, and if the victim stack has continuous deployment enabled and the forged status makes the commit `deployable?`, this queues `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `trigger_deploy`, resulting in an **unauthorized deploy** on a repository the attacker has no access to: [8](#0-7) [9](#0-8) 

This satisfies the "cross-repository writes" and "unauthorized deploy" Critical impact categories: the attacker breaks the "organization authenticated" vs. "repository written" binding using only credentials belonging to a repository/org they legitimately control.

### Likelihood Explanation
This requires the host application to configure Shipit for multiple GitHub organizations sharing the same instance (a documented, supported configuration), and the attacker must legitimately control at least one such configured organization/App (thus its `webhook_secret`) while targeting a different organization's stack on the same instance. This is not "no privilege" in the absolute sense, but it crosses the trust boundary the rules define: the attacker holds no privilege over the victim repository/org, only over their own, unrelated one — yet is still able to write to the victim's data. Additionally, guessing/knowing a target commit SHA of a public GitHub repo tracked by the victim's stack is trivial (SHAs of commits pushed to a public repo are public via the GitHub API/UI).

### Recommendation
- In `StatusHandler#process`, scope the `Commit` lookup by the resolved `Repository`/`Stack` derived from `payload.dig('repository', 'full_name')` (via the existing `stacks`/`repository_name` helper in `Handler`), instead of matching globally by `sha` alone.
- More generally, after signature verification selects an organization, enforce that `repository.owner.login` (used for auth) matches the owner embedded in `repository.full_name` (used for the write) before any handler processes the payload, in `WebhooksController#verify_signature` or in `Handler#initialize`.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with their own `webhook_secret` (per the documented multi-org `secrets.yml` format).
2. Attacker, who administers `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a JSON payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and creates a forged `success` `Status` on the victim's commit, irrespective of the fact that the authenticated organization was `attacker-org`, not `victim-org`.
7. If `victim-org`'s stack has continuous deployment enabled and this status makes the commit deployable, an unauthorized deploy is triggered on the victim's stack.
