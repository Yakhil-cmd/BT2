### Title
Unreverted in-memory DAG cache mutations from AA dry-run trigger evaluation cause node-wide cache/DB desynchronization - ([File: aa_composer.js])

### Summary
`aa_composer.dryRunPrimaryAATrigger()` is automatically invoked for every incoming unit that pays into an AA address (when `conf.bDryRunNewTriggers` is enabled) before the real unit is committed. This dry run wraps a real DB transaction (`BEGIN…ROLLBACK`) but the code path it exercises (`handleTrigger` → `sendUnit` → `writer.saveJoint` → `main_chain.updateMainChain`) mutates *global, non-transactional* in-memory caches (`storage.assocUnstableUnits`, `storage.assocStableUnits`, `storage.assocStableUnitsByMci`, `storage.assocBestChildren`) directly by reference. Only `revertResponsesInCaches()` is called afterward, and it only forgets the newly created AA-response units — it does not undo mutations that `main_chain.updateMainChain()`/`markMcIndexStable()` may have applied to pre-existing, real ancestor units (e.g. `is_on_main_chain`, `main_chain_index`, or even full unstable→stable promotion). This is conceptually the same bug class as CVE-2024-35869: a shared parent/ancestor structure is mutated by a transient, rolled-back child operation without guaranteeing the parent's cached state stays consistent for all other consumers, leaving stale/incorrect references in memory that diverge from the (rolled-back) database.

### Finding Description
`dryRunPrimaryAATrigger` is reachable from any unprivileged unit poster: `network.js` calls it inline while still holding the `handleJoint` mutex whenever a freshly submitted unit contains a primary AA trigger: [1](#0-0) 

The dry run itself performs a full trigger evaluation, including composing and "writing" AA response units inside a rolled-back SQL transaction: [2](#0-1) 

`writer.saveJoint`, called from inside `handleTrigger`/`sendUnit` for these fake response units, unconditionally updates the shared, process-global caches synchronously (not through the DB transaction, so a `ROLLBACK` does not undo them): [3](#0-2) 

It also triggers `main_chain.updateMainChain`, which walks up the DAG and rewrites `main_chain_index`/`is_on_main_chain` directly on `storage.assocUnstableUnits` entries of already-existing (real) units — not just the fake dry-run response unit: [4](#0-3) [5](#0-4) 

If MC stabilization advances far enough, `markMcIndexStable` permanently moves real units from `assocUnstableUnits` to `assocStableUnits`/`assocStableUnitsByMci`, and even flips `sequence` on real, previously-unstable units: [6](#0-5) [7](#0-6) 

After `onDone` fires, `dryRunPrimaryAATrigger` only calls `revertResponsesInCaches`, which forgets the fake response units and fixes `is_free` on their immediate parents — it never restores any `main_chain_index`, `is_on_main_chain`, `sequence`, or unstable→stable promotions that were applied to real ancestor units during the dry run's (rolled-back) DB transaction: [8](#0-7) 

The existing test suite is aware of exactly this defect class: it contains an explicit `fixCache()` hack acknowledging that "an AA-response unit can rebuild the MC to itself" and manually patches `is_on_main_chain`/`main_chain_index` back after a dry run in the 1-witness test setup, because production code does not do this reversion itself: [9](#0-8) 

Underlying cache primitives such as `forgetUnit`/`fixIsFreeAfterForgettingUnit` operate on the same shared parent/children associative caches (`assocUnstableUnits`, `assocBestChildren`) with no isolation between the dry-run "child" objects and the real objects they reference: [10](#0-9) 

Because the dry run is a normal, expected part of processing any inbound unit sent to an AA address, an attacker (any user posting a unit) can shape a trigger/DAG situation where the dry run's rolled-back evaluation touches and rewrites the cached `main_chain_index`/`is_on_main_chain`/`is_stable` state of real DAG ancestor units, leaving the in-memory cache permanently diverged from the database truth (which was rolled back). Later reads (`readUnitProps`, `getFinalTps`) contain hard `_.isEqual`/assertion checks precisely against this kind of divergence and `throw Error(...)` on mismatch, crashing the node process; short of a crash, stale/incorrect cached MC state can also feed into subsequent stability/validity decisions for new units.

### Impact Explanation
This corresponds to "node disagreement on validity or stability" and "a network unable to confirm new units": nodes running with `conf.bDryRunNewTriggers` enabled can have their core DAG-state caches silently or catastrophically corrupted by processing entirely ordinary, attacker-supplied units that trigger AAs, without any malicious peer/network component — purely from the unit's payload/DAG shape reaching this code path. Depending on exactly which cache fields diverge, effects range from immediate crashes (`throw Error` in `readUnitProps`/`getFinalTps` consistency checks) to silently wrong stability computations affecting subsequent unit validation on that node.

### Likelihood Explanation
The dry-run path is reachable from any unprivileged unit poster whose unit pays to an AA address; there is no special access needed beyond composing/broadcasting a normal payment+trigger unit, contingent on the node operator having enabled `conf.bDryRunNewTriggers` (an opt-in but documented/available full-node setting). The precise conditions to force `main_chain.updateMainChain`/`markMcIndexStable` to actually rewrite real ancestor entries during the dry run (rather than a no-op) require some DAG/witness-list crafting, which I could not fully verify end-to-end within the available tooling — this is a plausible but not experimentally confirmed trigger condition, and full confirmation would require running the exact witness/DAG scenario against a live/test node.

### Recommendation
Ensure `dryRunPrimaryAATrigger` performs all in-memory cache mutations against isolated/cloned structures (or snapshots the affected cache entries beforehand and fully restores them in `revertResponsesInCaches`/`onDone`), rather than mutating the shared global `storage.assocUnstableUnits`/`assocStableUnits`/`assocStableUnitsByMci`/`assocBestChildren` caches directly. At minimum, capture a deep copy of every real ancestor unit's cache entry touched during the trial `handleTrigger`/`main_chain.updateMainChain` call and restore it verbatim after rollback, mirroring what `fixCache()` does ad hoc in the test suite, but generalized to cover `is_stable`, `sequence`, and stable/unstable map membership, not just `is_on_main_chain`/`main_chain_index`.

### Proof of Concept
Not independently reproduced end-to-end; the code path and the corroborating in-repo test hack (`fixCache()` in `test/aa_composer.test.js`) demonstrate the mechanism, but crafting the exact DAG/witness-list conditions that force `main_chain.updateMainChain` to rewrite a *real, previously cached* ancestor unit's `main_chain_index`/`is_on_main_chain`/`is_stable` during a dry run — and confirming resultant divergence assertions fire — was not verified against a running node within the scope of this analysis.

function fixCache() {

		var objUnit = storage.assocUnstableUnits[unit];

function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
