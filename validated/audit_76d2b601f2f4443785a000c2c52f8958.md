### Title
Cross-repository CI status forgery via global SHA lookup bypasses the authenticating repository, enabling unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` looks up commits to update purely by `sha`, with no scoping to the repository/organization that authenticated the webhook request. This breaks the trust binding `{organization/repository that authenticated the webhook} == {repository/stack whose data is mutated}`, mirroring the reported bug class where a value acted upon (the rollover bid price) is disconnected from what was actually verified/submitted.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC secret) to verify the incoming payload against based on `repository_owner`, derived from the payload's own `repository.owner.login`/`organization.login` field: [1](#0-0) [2](#0-1) 

This correctly proves the request came from GitHub for *some* organization's installed app. However, once verified, `StatusHandler#process` does not use the repository at all to scope which records are mutated — it matches purely on the globally-unique-looking but not necessarily repository-scoped `sha` field: [3](#0-2) 

Compare this with the base `Handler` class and every other handler (`PushHandler`, `PullRequest::*Handler`), which properly scope lookups through `Repository.from_github_repo_name(repository_name)`: [4](#0-3) [5](#0-4) 

`StatusHandler` is the outlier: it queries `Commit.where(sha: params.sha)` across the entire Shipit instance, not `stacks.where(...)`. Because git commit SHAs are content-addressed, any repository sharing history with a target repository (e.g. a public fork) will contain identical SHAs for shared commits. An attacker who owns a fork of a targeted, Shipit-tracked repository — and who has the Shipit GitHub App legitimately installed on their own account/org for that fork — can create a real GitHub commit status (`state: success`) on a commit SHA that is shared with the target's tracked history. GitHub will sign and deliver this event using the attacker's own org's webhook secret, which `verify_signature` correctly validates against `repository_owner = attacker-org`. The binding broken is: **the organization that authenticated (attacker's own org) ≠ the repository/stack whose `Commit`/`Status` records are written (the victim's stack)**, because `StatusHandler` never checks `repository.full_name` against the commit's owning stack.

Once created, the forged `Status` triggers `Status#schedule_continuous_delivery` and `enable_ci_on_stack`: [6](#0-5) [7](#0-6) 

which feeds into `ContinuousDeliveryJob`, which deploys automatically once the stack's required CI checks are satisfied and `continuous_deployment?` is true: [8](#0-7) 

### Impact Explanation
An unprivileged attacker (no access to the target repository, its GitHub App, its webhook secret, or its API tokens — only write access to their own public fork) can inject a fabricated "success" CI status onto a commit belonging to a victim stack they do not control. If that stack has continuous deployment enabled and depends on the forged status/context to satisfy its deploy criteria, this can trigger an **unauthorized deploy** — matching the Critical severity bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (1) the target repository is public or otherwise forkable by the attacker so shared commit history/SHAs exist, (2) the attacker's own account/org has the Shipit GitHub App installed (a normal, unprivileged setup step available to any GitHub org owner who wants Shipit for their own repos), and (3) the target stack has `continuous_deployment` enabled and its deploy-eligibility logic keys off the forged status context. This is plausible in multi-tenant Shipit deployments serving many orgs/teams, but is conditioned on shared git history and continuous-deployment configuration, so likelihood is moderate rather than trivial.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) lookups by the authenticated `repository.full_name`/owning `Repository`, not solely by `sha`, so that a status/commit update can only affect commits belonging to stacks under the repository that was actually authenticated for the webhook delivery — consistent with how `Handler#stacks`/`#repository_name` is used elsewhere.

### Proof of Concept
1. Fork a public repository that is tracked as a Shipit stack (`victim/repo`) into `attacker/repo`; the fork shares commit SHA `abc123` with `victim/repo`'s tracked branch.
2. Install/enable the Shipit GitHub App on `attacker` (a normal, unprivileged action for an account's own repos), configuring a legitimate webhook secret for `attacker`.
3. Using the GitHub API with attacker's own token (no access to `victim` needed), create a commit status on `attacker/repo@abc123` with `state: success` and the `context` that `victim/repo`'s deploy checks require.
4. GitHub delivers a `status` webhook signed with `attacker`'s webhook secret; `WebhooksController#verify_signature` verifies it correctly against `repository_owner = attacker`.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123")`, which matches the `Commit` row belonging to `victim`'s stack, creating a forged `Status` for it and calling `schedule_continuous_delivery`, potentially triggering an unauthorized deploy on `victim`'s stack.
