Important finding: `StatusHandler#process` matches commits **only by SHA globally** (`Commit.where(sha: params.sha)`), with no scoping to the repository resolved from the payload at all — not even the loosely-checked `repository.full_name` binding that other handlers use.

### Title
Unauthenticated cross-repository CI status forgery via organization/repository binding mismatch in webhook signature verification - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  That value is never cross-checked against the field actually used later to decide what data gets written: `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` [3](#0-2) , and `StatusHandler#process`, which matches commits purely by `sha` with **no repository scoping at all** [4](#0-3) .

### Finding Description
This is the same accumulator/checkpoint bug class as the original report, generalized to an authentication binding: the field checked to authenticate the payload (`repository.owner.login` → selects the org whose `webhook_secret` gates the HMAC check) is not the same field, nor scoped consistently with, the field that determines what gets mutated (`repository.full_name` for stack resolution, and *nothing at all* for `StatusHandler`, since it filters commits only by `sha`).

`Shipit.github(organization:).verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unconfigured: `return true unless webhook_secret` [5](#0-4) . Shipit explicitly supports multi-org configurations where some orgs have `webhook_secret: nil` (seen in fixtures/docs configs) [6](#0-5) [7](#0-6) .

An unauthenticated network attacker can POST directly to the public `/webhooks` endpoint (no session, API token, or GitHub write access required) [8](#0-7) , with:
- `repository.owner.login` set to any organization configured in Shipit with no `webhook_secret` (bypassing HMAC verification entirely), and
- a `sha` belonging to a commit tracked by a completely different, victim organization's stack.

Because `StatusHandler` never checks `repository.full_name` or `repository.owner` at all before writing the status, `commit.create_status_from_github!(params)` is invoked for the victim's real commit row, letting the attacker set the CI status to `success` for an arbitrary target repository/commit they don't control and never authenticated against, breaking the equality: `organization whose signature was verified == repository/commit whose state is written`.

### Impact Explanation
Setting a fabricated `success` status on a victim commit via `Commit#create_status_from_github!` can make that commit `deployable?`/pass CI gating checks that `Stack#deployable?` and `branch_status` rely on [9](#0-8) , enabling an unauthorized deploy on a repository the attacker has no relationship to — this falls under the "unauthorized deploy" Critical-impact category, achieved purely by exploiting the binding mismatch between the authenticated organization and the written repository/commit state, without any session, token, or GitHub write access.

### Likelihood Explanation
Likelihood is high in any Shipit deployment that has at least one configured organization without a `webhook_secret` (a supported and documented configuration state) alongside at least one victim organization whose stacks the attacker wants to target — no privileged credentials of any kind are needed, only knowledge of a target commit `sha` and the low-secret org's name, both of which are often observable (org names are public, commit SHAs are visible on GitHub).

### Recommendation
Bind the value used to authenticate the payload to the value used to act on it: derive the acting repository/organization exclusively from a field validated as part of the HMAC computation (or re-derive `repository_owner` for handler dispatch from the same object used in signature verification), and reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, `StatusHandler#process` should scope `Commit.where(sha: ...)` to commits belonging to the repository identified in the verified payload, not merely by raw `sha` globally. Do not allow webhook signature verification to silently pass (`return true`) when `webhook_secret` is unset for the organization resolved from attacker-controlled JSON fields.

### Proof of Concept
1. Configure Shipit with two orgs: `orgA` (no `webhook_secret`) and `orgB` (victim, with stacks tracking commit `abc123...` on a monitored branch).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/whatever" },
  "sha": "abc123...",
  "state": "success",
  "context": "ci/attacker"
}
```
without any valid `X-Hub-Signature` (or an arbitrary one).
3. `verify_signature` resolves `Shipit.github(organization: 'orgA')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the header/body [5](#0-4) .
4. `StatusHandler#process` matches `Commit.where(sha: 'abc123...')` — the victim org's real commit — and calls `create_status_from_github!`, forging a passing CI status on `orgB`'s commit despite the request never having been authenticated by anything related to `orgB`. [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
