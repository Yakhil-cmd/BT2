### Title
Unauthenticated asset-metadata `decimals`/`name` spoofing via any address acting as an asset "registry" — misleads wallet balance/amount display and payment decisions - ([File: wallet.js])

### Summary
`fetchAssetMetadata()` in `wallet.js` derives an asset's displayed `name` and `decimals` from a `data` message authored by whatever address is embedded as `registry_address` in the hub-served metadata pointer, and stores/uses it with essentially no restriction on which address may act as a "registry" for a given asset the wallet holds.

### Finding Description
When the wallet needs to show a human-readable name/decimal-scaling for an asset, it calls `fetchAssetMetadata()`, which:
1. Takes `registry_address` from the hub response (`hub/get_asset_metadata`), only checking it `isValidAddress` [1](#0-0) .
2. Reads the `metadata_unit` joint and accepts the `data` message's `payload.name` / `payload.decimals` as long as the message author is that same `registry_address` and `payload.asset` matches [2](#0-1) .
3. Persists this into `asset_metadata` and returns it to be used to format the asset's displayed name and to scale raw integer amounts into human-readable units via `decimals` [3](#0-2) .

There is no check that `registry_address` is a trusted/whitelisted registry for that asset, nor that it is the asset's definer, an attestor, or any other privileged party — any address can author a `data` unit claiming to be the "registry" for an arbitrary `asset` hash and assign it any `name` and `decimals` value, and `readAssetMetadata()`/`fetchAssetMetadata()` will happily cache and surface it for display [4](#0-3) . The only restriction (`isUpdatableRegistry`) governs whether *existing* metadata may later be *replaced* by the *same* registry address, not whether an arbitrary attacker-controlled address may register metadata for an asset in the first place [5](#0-4) .

This is directly analogous to the CoinDash incident: the attacker doesn't need to compromise any node or steal keys — they simply post an ordinary, unprivileged `data` unit (reachable by any unprivileged unit poster) that gets picked up and displayed to victims as authoritative asset information (decimals/name), the same way CoinDash's front end displayed a wallet address string that the attacker silently swapped.

### Impact Explanation
Since wallet UIs use `decimals` to convert raw base-unit amounts into the human-readable quantity a user sees and enters when composing a payment, a spoofed `decimals` value can cause the wallet to display, e.g., 1,000,000× more or fewer "tokens" than are actually held/being sent. A user relying on the displayed amount when confirming a transfer (of that asset, or when entering an amount in "asset units" that the UI converts to raw units for the transaction) can be induced to send far more raw units than intended, resulting in direct, unrecoverable fund loss — the same "trusted-looking but attacker-controlled displayed value" pattern as the CoinDash address-swap, just applied to amount/decimals instead of an address string. This is a Medium/High severity UI-trust issue with concrete fund-loss potential for any user of an asset whose metadata registry has not yet been established/cached.

### Likelihood Explanation
Likelihood is high for any newly-encountered or lesser-known asset: the attacker only needs to broadcast a normal `data` unit (no special privileges, keys, or AA access needed — just being any unprivileged unit poster) naming themselves as the `registry_address` for a target `asset` hash before the legitimate registry's metadata is fetched/cached by the victim's wallet. Since `asset_metadata` is keyed by `(name, registry_address)` and populated on first fetch, an attacker can race to be first, or exploit assets that don't have exercise metadata cached yet.

### Recommendation
Only accept/display asset metadata where `registry_address` is verified to be an actually trusted source for that asset (e.g., the asset's definer, an address the user has explicitly configured as their registry, or metadata is signed/attested through a mechanism cryptographically bound to the asset definition). At minimum, the wallet UI should clearly flag unverified/unconfigured registries and never use unverified `decimals`/`name` to silently rescale amounts used in payment composition; require explicit user confirmation of raw base-unit amounts for such assets.

### Proof of Concept
1. Attacker picks a target `asset` (asset unit hash) that a victim wallet holds or is about to receive.
2. Attacker composes and broadcasts an ordinary `data` message unit from their own address `A` with payload `{asset: <target_asset>, name: "USDT", decimals: 2}` (or any deceptive combination).
3. Attacker gets this unit indexed as a candidate metadata unit for the asset (e.g., via a hub they control returning `{metadata_unit, registry_address: A, suffix}` for `hub/get_asset_metadata`, or by being first to publish before the legitimate registry).
4. Victim wallet calls `fetchAssetMetadata(asset, cb)` → `readJoint` finds the attacker's unit, verifies only that `objJoint.unit.authors[0].address === registry_address (A)` and `payload.asset === asset` [6](#0-5) , then stores/returns the attacker-chosen `name`/`decimals`.
5. Victim's UI now displays the asset using the attacker's `decimals`, misrepresenting the real quantity being held/sent, leading the victim to authorize a transaction moving far more raw units than intended.
