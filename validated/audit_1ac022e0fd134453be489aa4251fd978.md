### Title
Webhook signature verified against `repository.owner.login`, but handlers act on `repository.full_name` from the same unauthenticated field set - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to verify the HMAC against using `repository.owner.login` (or `organization.login`) from the incoming JSON payload, but every event handler (`PushHandler`, all `PullRequest::*Handler`s, etc.) resolves the target `Repository`/`Stack` using a *different* field of the same payload: `repository.full_name`. Nothing ties these two fields together, so a signature that is valid for organization A can be replayed with a `repository.full_name` claiming organization B, causing Shipit to act on a stack that has nothing to do with the authenticated organization.

Every webhook handler, however, resolves the affected `Repository`/`Stack` from a **different** field in the same body: [3](#0-2) 

and acts on it, e.g.: [4](#0-3) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up any repo by owner/name, independent of which organization's secret validated the request: [5](#0-4) 

Nothing in `verify_signature` or in `Handler#repository_name` asserts that `repository.full_name.split('/').first == repository.owner.login`. Because both fields live inside the same HMAC-signed body, the signature is technically "valid," but it only proves the sender knows organization A's secret — it does not prove anything about the `full_name` value the handlers actually use to pick the target stack. In a multi-org Shipit deployment (`Shipit.github(organization: ...)` per-org secrets, as documented in `docs/setup.md`), anyone who can obtain org A's `webhook_secret` (e.g. a low-privileged GitHub org member who can see/replay webhook deliveries for org A, or who leaked that one secret) can forge a payload where `repository.owner.login = "orgA"` (so verification passes with orgA's secret) but `repository.full_name = "victim-org/victim-repo"`. This lets `PushHandler` invoke `stack.sync_github(expected_head_sha:)` on a completely unrelated stack belonging to `victim-org`, which — for stacks with `continuous_deployment: true` — can trigger an unauthorized/unexpected deploy pipeline run, or an unwarranted `GithubSyncJob`/`CacheDeploySpecJob` execution against a stack the attacker was never authorized to touch.

### Impact Explanation
This breaks the binding "an organization that authenticated == the repository that is written." An attacker holding only one organization's webhook secret can cause Shipit to act (sync/cache-spec/potentially auto-deploy via `continuous_deployment`) on stacks belonging to a different, unrelated GitHub organization configured in the same Shipit instance — an unauthorized cross-repository/cross-organization action, matching the Critical bucket ("cross-repository writes" / "an unauthorized deploy").

### Likelihood Explanation
Requires the attacker to know the webhook secret of at least one organization already onboarded to the shared Shipit instance (a realistic scenario for multi-tenant Shipit deployments where many orgs share one instance and any org member with webhook admin visibility can see that org's secret). No Shipit session, ApiClient token, or GitHub App private key is needed — only a valid HMAC computed with an org secret they legitimately possess for their own org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), validate that `repository.full_name`'s owner segment matches the `repository.owner.login`/`organization.login` value that was used to select the verifying secret, and reject the webhook otherwise. Alternatively, derive the acting organization exclusively from the value used for verification and pass it explicitly into handlers instead of re-deriving it from `full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md`), and a stack for `orgB/victim-repo` with `continuous_deployment: true`.
2. As someone who knows `orgA`'s webhook secret (e.g., an `orgA` member with access to that org's GitHub App webhook config), craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<some sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=...` using `orgA`'s webhook secret over the raw body.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner = "orgA"`, verifies successfully with `orgA`'s secret.
5. `PushHandler#process` resolves the stack via `repository.full_name = "orgB/victim-repo"` [3](#0-2)  and calls `stack.sync_github(expected_head_sha:)` on the `orgB` stack the attacker never authenticated against.

  module Webhooks
