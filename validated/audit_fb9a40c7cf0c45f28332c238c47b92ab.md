## Title
Webhook signature is verified against the organization named in `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross‑organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports a multi-tenant GitHub App configuration where each organization has its own `webhook_secret` [1](#0-0) . When a webhook is delivered, `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using `repository_owner`, which is read directly from the untrusted JSON body (`repository.owner.login`, or `organization.login`) [2](#0-1) [3](#0-2) . However, every event handler determines which repository/stack to act on using a completely different field of the same payload: `repository.full_name` [4](#0-3) . Nothing ties `repository.full_name` back to the `repository.owner.login`/`organization.login` value that was used to pick the verification secret.

### Finding Description
The binding that should hold is:

`organization whose secret authenticated the request == organization that owns the repository the handlers act on`

Concretely:
1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` to get that organization's `webhook_secret`, then verifies `X-Hub-Signature` against the raw body with that secret [5](#0-4) .
2. If verification succeeds, `Shipit::Webhooks.for_event(event)` handlers are invoked with the full, attacker-supplied JSON `params` [6](#0-5) .
3. Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the target repository/stacks from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks` [4](#0-3) , e.g. `PushHandler#process` calls `stack.sync_github` for any stack whose repository matches that `full_name` [7](#0-6) , and `StatusHandler#process` creates a commit status from attacker-controlled `state`/`context`/`description` for any commit matching `params.sha`, with no repository check at all [8](#0-7) .

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target stack/commit) are two independent, attacker-supplied fields inside the same JSON body, an attacker who legitimately knows one organization's `webhook_secret` (e.g. their own org configured in the same multi-tenant Shipit instance, or a leaked/low-value org secret) can forge a payload where `repository.owner.login` = their known org (so the correct secret is used and the HMAC check passes) while `repository.full_name` = `victim-org/victim-repo` (so the handler operates on a totally different, unrelated organization/repository). The `verify_signature` step in `app/controllers/shipit/webhooks_controller.rb` never checks that `full_name`'s owner segment matches `repository_owner`.

### Impact Explanation
This breaks the intended per-organization trust boundary of the multi-tenant GitHub App configuration: possession of any one organization's `webhook_secret` allows forging webhook events for any other organization/repository/stack tracked by the same Shipit instance. Depending on the handler abused:
- `StatusHandler` lets an attacker inject arbitrary commit statuses (`state`, `context`, `target_url`) for arbitrary commits in a different org's stacks [9](#0-8) . Since Shipit gates deploys on required CI statuses (`ci.require`) described in the deploy documentation, forging a passing status for a commit that never actually passed CI can enable an unauthorized deploy.
- `PushHandler`/`CheckSuiteHandler` can trigger sync/refresh jobs against arbitrary tracked stacks belonging to a different organization, polluting or manipulating another team's stack state.

This matches the "cross-repository writes" / "unauthorized deploy" impact category because the write/side effect crosses an organizational trust boundary that the signature check was supposed to enforce.

### Likelihood Explanation
Exploitation requires the attacker to know/control at least one organization's `webhook_secret` configured on the same Shipit instance — realistic in any deployment that follows the documented multi-tenant `secrets.github` schema keyed by organization (e.g. a Shipit instance shared across several orgs/teams, where one org's GitHub App admin is less trusted than another's). No repository write access, GitHub App private key, or Shipit session/API token is needed — only the ability to send an HTTP POST to `/webhooks` with a correctly-signed body using a secret the attacker legitimately possesses for a different, low-trust organization.

### Recommendation
In `WebhooksController#verify_signature` (and/or `Handler#repository_name`), require that the organization derived from `repository.full_name` (or `repository.owner.login`) matches the `repository_owner`/organization value that was actually used to select the verification secret, rejecting the request (422) on mismatch. Alternatively, verify the signature using the secret for the organization actually referenced by `repository.full_name`, not a separately-controllable field, so the two can never diverge.

### Proof of Concept
Given a Shipit instance configured with two organizations in `secrets.github`, `org-a` (attacker-known secret `S_A`) and `org-b` (victim, secret `S_B` unknown to attacker):

1. Attacker builds payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_A, raw_body)` using the known `org-a` secret.
3. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, fetches `Shipit.github(organization: "org-a")`, and successfully verifies the signature with `S_A` [2](#0-1) .
4. `PushHandler` is invoked with the full payload and resolves `stacks` via `repository.full_name = "org-b/victim-repo"` [4](#0-3) , triggering `stack.sync_github` for `org-b`'s stack even though the request was authenticated only with `org-a`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
