Based on my review, there is a legitimate deployment-trust-binding break in the webhook signature verification: when `webhook_secret` is left blank (a state the docs explicitly present as a supported, optional configuration), the "verified signature" binding degenerates to unconditionally trusting the entire payload, allowing an unauthenticated actor to drive privileged internal actions like team-membership authorization.

### Title
Webhook signature verification is a no-op when `webhook_secret` is blank, allowing unauthenticated forgery of `membership` events to grant `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`Shipit::GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically valid, meaning the entire trust binding "payload was produced by GitHub, as proven by HMAC signature" collapses to "no proof at all." [1](#0-0)  Because `WebhooksController#verify_signature` is the only gate in front of `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, an attacker who knows nothing more than the app's public `/webhooks` URL can submit arbitrary, unsigned JSON and have it processed as if GitHub sent it. [2](#0-1) 

### Finding Description
The equality this binding is supposed to enforce is:
`payload processed by handlers == payload whose HMAC-SHA1 signature was verified against webhook_secret`

When `webhook_secret` is unset/blank (an explicitly documented, supported configuration — see the shipped example configs which set `webhook_secret: # nil`) [3](#0-2) [4](#0-3) , `verify_webhook_signature` short-circuits to `true` without inspecting `signature` or `message` at all:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

The controller only decides which `github_app`/secret to check against based on `repository_owner`, itself parsed straight out of the unauthenticated request body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Once past `verify_signature`, `create` blindly parses the raw body and dispatches every field to the registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

The most impactful consumer of this trust is `MembershipHandler`, which mutates `Team` membership directly from the (potentially unverified) payload:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
``` [7](#0-6) 

`User#authorized?` — the check gating access to the entire application — is defined purely in terms of team membership:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [8](#0-7) 

So, if `webhook_secret` is blank for the organization matching a target's `Shipit.github_teams`, any unauthenticated actor can POST a forged `membership` event naming an authorized team and their own GitHub login, causing `Team#add_member` to run and their `User` record to become `authorized?`.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes. Once authorized, the attacker gains full access to the Shipit UI/API (stacks, deploys, rollbacks, merges) as a logged-in, "authorized" user, which is a stepping stone toward unauthorized deploys/rollbacks/merges (Critical).

### Likelihood Explanation
Likelihood depends entirely on whether an organization's `webhook_secret` is blank. The engine's own documentation and shipped example secrets files present `webhook_secret` as optional/nilable in multiple places [3](#0-2) [9](#0-8) , so this is not a hypothetical misconfiguration outside the documented deployment model — it's a state the code and docs actively allow. The `webhooks_controller_test.rb` test suite even stubs `verify_signature` away entirely rather than exercising this specific blank-secret trust boundary [10](#0-9) , indicating it's not well covered/considered.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization at boot time (fail fast/raise instead of silently allowing unauthenticated webhooks), rather than defaulting to "verified" when absent.
- If a "no verification" mode is intentionally desired for local development, make it explicit (e.g. a separate `Rails.env.development?`-gated flag) instead of an implicit consequence of a blank secret.
- Add controller/model tests asserting that a blank `webhook_secret` does **not** allow `membership`/other privileged webhook events to mutate `Team`/`User` state.

### Proof of Concept
1. Deploy Shipit with an organization configured per the documented optional-secret example: `webhook_secret: # nil`.
2. As an unauthenticated network client, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Trusted Team", "slug": "trusted-team", "url": "https://example.com" },
  "organization": { "login": "target-org" },
  "member": { "login": "attacker-github-login" }
}
```
3. `verify_webhook_signature` returns `true` unconditionally (no `X-Hub-Signature` header needed since the check is skipped before ever using it). [1](#0-0) 
4. `MembershipHandler#process` creates/updates `Team` "Trusted Team" and adds a `User` with login `attacker-github-login` as a member. [7](#0-6) 
5. Attacker completes normal GitHub OAuth login with `attacker-github-login`; `find_or_create_from_github` matches the existing `User` by `github_id` [11](#0-10) , and `authorized?` now returns `true` because the user belongs to a team in `Shipit.github_teams`, granting full application access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
