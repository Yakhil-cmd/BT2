## Confirmed Vulnerability

### Title
Unscoped API token minted by CCMenu link grants read access to every stack, not just the requested one - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
The gnark advisory describes a validator that checks a *narrower* representation of a value (its bit decomposition) while the value actually used afterward can carry more information (`a` vs `a+r`), letting the checked and used values diverge. The equivalent binding in shipit-engine is: **the stack a token is generated for** (the `stack_id` route param used to build the CCMenu URL) **versus the stack(s) the resulting `ApiClient` record actually authorizes**. `CCMenuUrlController#client` mints a `read:stack` `ApiClient` but never binds it to `stack.id`, so the token silently authorizes every stack in the installation, not the one the user was viewing.

### Finding Description
`CCMenuUrlController#fetch` builds a URL containing an authentication token intended to let a specific stack's CI status be polled anonymously (no session) via `Api::CCMenuController#show`: [1](#0-0) 

The token is produced by `client`, which creates/finds an `ApiClient` scoped only by `creator` and `name`, with `permissions: %w[read:stack]` — **the `stack:` attribute is never set**:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

`ApiClient#stack_id` therefore remains `nil`. Scoping is enforced downstream in `Api::BaseController#stacks`: [2](#0-1) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
```

Because `stack_id?` is false, `stacks` resolves to `Stack.all` — every stack in the Shipit instance, including private/internal ones the requesting user may have access to via the UI but that were never intended to be exposed through this unauthenticated, long-lived token. `Api::CCMenuController` authenticates purely from the `token` query parameter (no session, no team/authorization check): [3](#0-2) 

and looks up the target stack independently from `params[:stack_id]`: [4](#0-3) 

So the equality that should hold — "stack the token was generated for" == "stack(s) the token authorizes" — is broken: the UI/URL narrows the token to one stack (`stack.to_param` in the generated URL), but the underlying `ApiClient` grants `read:stack` globally. Any holder of one CCMenu URL (these tokens are un-expiring, persisted `ApiClient` records, and the URL/token is exposed in plaintext query strings, browser history, proxies, and CI dashboards) can call `GET /api/:other_stack_id/ccmenu.xml?token=...` for **any other stack**, retrieving stack/deploy status information for stacks they were never granted this token for.

This is corroborated by `Api::BaseController#stack`, which is the standard multi-tenant boundary every other API controller relies on (`stacks.from_param!(params[:stack_id])`), confirming that `stack_id` scoping on the `ApiClient` is the intended enforcement mechanism that this controller bypasses by omission: [5](#0-4) 

### Impact Explanation
This grants **unauthenticated read of stack state** for arbitrary stacks (deploy/rollback status, `stack.to_param`, lock state, last build info) to anyone holding a single, unscoped CCMenu token — exactly the "High: unauthenticated read of stack state" bucket. It is not merely a design choice: the intent (visible from `stack.to_param` embedded in the generated URL and from the sibling `CCMenuController` always resolving `stack` by the `:stack_id` route segment) is clearly per-stack; the missing `stack:` binding on `ApiClient.create_with` is the root cause of the widened blast radius.

### Likelihood Explanation
Every logged-in user who visits a stack's settings page and fetches the "CCMenu URL" (a documented, UI-exposed feature — see `app/views/shipit/stacks/settings.html.erb`) receives one of these tokens. No special privilege is required beyond normal Shipit login; the resulting token/URL is meant to be pasted into external CI dashboard tools (unauthenticated context) and is trivially reusable against any other stack endpoint.

### Recommendation
Set `stack:` when creating the `ApiClient` in `CCMenuUrlController#client` (e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(...)`), and add a uniqueness/lookup key that includes `stack_id` so a distinct, stack-scoped token is minted per stack rather than one global-by-default client shared across all "CCMenu Client" requests.

### Proof of Concept
1. As any authenticated Shipit user with access to `stack-A`, visit its settings page and fetch the CCMenu URL, e.g. `GET /stack-owner/stack-A/production/ccmenu` → returns `{ "ccmenu_url": ".../api/stack-owner/stack-A/production/ccmenu.xml?token=<TOKEN>" }`.
2. Inspect the created `ApiClient` record: `stack_id` is `nil`, `permissions` is `['read:stack']`.
3. Using the same `<TOKEN>`, request a *different, unrelated* stack's CI status: `GET /api/other-owner/stack-B/production/ccmenu.xml?token=<TOKEN>`.
4. Because `Api::BaseController#stacks` returns `Stack.all` when `stack_id?` is false, `stacks.from_param!` successfully resolves `stack-B`, and `Api::CCMenuController#show` renders `stack-B`'s deploy/build status to the token holder, who was never granted access to `stack-B`.
