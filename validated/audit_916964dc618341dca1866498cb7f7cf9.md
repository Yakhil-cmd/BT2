## Title
`provision?` operator precedence makes `review_stacks_enabled` gate only the `allow_all` disjunct, not `allow_with_label`/`prevent_with_label` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`PullRequest::OpenedHandler#provision?` (and the identical `ReopenedHandler#unarchive?`) is written as `a && b || c || d`. Due to Ruby's `&&`/`||` precedence, `repository.review_stacks_enabled` is only ANDed with `provisioning_behavior_allow_all?`; it is never combined with the `allow_with_label` or `prevent_with_label` disjuncts. An operator who sets `review_stacks_enabled = false` while `provisioning_behavior` is `allow_with_label` or `prevent_with_label` gets automatic `Shipit::Stack` provisioning anyway, contrary to the intent that `review_stacks_enabled` is the master switch.

### Finding Description
The claimed binding is: `review_stacks_enabled == false` should imply `provision? == false` for **all** values of `provisioning_behavior`. Tracing `provision?`: [1](#0-0) 

parses as `(review_stacks_enabled && provisioning_behavior_allow_all?) || (provisioning_behavior_allow_with_label? && label_present?) || (provisioning_behavior_prevent_with_label? && !label_present?)`. So when `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` and the PR carries the configured label, `provision?` evaluates to `true` and a `Shipit::ReviewStack` is created via `ReviewStackAdapter#find_or_create!` on `process`. [2](#0-1) 

The same pattern exists in `ReopenedHandler#unarchive?`: [3](#0-2) 

By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole label-driven decision: [4](#0-3) 

confirming the intended design (a single authoritative `review_stacks_enabled` flag) is present elsewhere but was not correctly implemented in `OpenedHandler`/`ReopenedHandler`.

Repository's schema-level default of `provisioning_behavior` is `allow_all` [5](#0-4) , so a freshly tracked repo with the default `allow_all` behavior is unaffected by this bug (the `&&` correctly applies). The divergence only manifests once an operator has explicitly moved `provisioning_behavior` to `allow_with_label` or `prevent_with_label` — at that point, disabling `review_stacks_enabled` no longer suppresses provisioning for PRs matching (or not matching) the label. Existing test coverage in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` only ever tests `review_stacks_enabled: false` together with `provisioning_behavior: allow_all` [6](#0-5) ; the `allow_with_label`/`prevent_with_label` tests always leave `review_stacks_enabled` at its default `true` [7](#0-6) , so no test currently exercises (and no guard currently catches) the `review_stacks_enabled=false` + non-`allow_all` combination.

Nothing in `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema mitigates this — those govern webhook authenticity/shape, not the provisioning-behavior authorization logic itself, which is a pure boolean-logic bug in the handler.

### Impact Explanation
An unprivileged GitHub PR author (on a repo already configured by its own maintainer with `provisioning_behavior = allow_with_label` or `prevent_with_label`, and `review_stacks_enabled = false`) can still trigger creation/unarchiving of a `Shipit::ReviewStack` (backed by `Shipit::Stack`) by opening or reopening a PR with (or without) the provisioning label, even though the operator believed disabling `review_stacks_enabled` fully suppressed auto-provisioning. This is a write to `Shipit::Stack`/`Shipit::ReviewStack` records for a repository, driven purely by attacker-controlled PR labels/branch names, against the operator's expressed intent. It does not by itself grant RCE, secret exfiltration, or cross-tenant writes — it's confined to the same repository whose operator mis-set the flag, and only affects the stack-creation state, not deploy authorization. This is best characterized as a logic/authorization-consistency bug within a single repository's own review-stack provisioning, rather than a cross-tenant or credential-exposure issue matching the Critical/High categories defined (RCE, forged webhook/session/token auth bypass, secret exfiltration, cross-repo mutation, unauthorized deploy/rollback/merge, escalation into `Shipit.github_teams`, unauthenticated read, SSRF, session fixation).

### Likelihood Explanation
Requires a specific, non-default repository configuration (`provisioning_behavior` set away from `allow_all`, combined with `review_stacks_enabled = false`) that must be deliberately (if mistakenly) chosen by the repository operator; on a fresh/default repository (`provisioning_behavior = allow_all`), the bug does not manifest. Given that configuration, the attack is trivial and repeatable: any PR author can add/remove the configured label and open/reopen the PR to force stack creation.

### Recommendation
Fix operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` by explicitly parenthesizing `review_stacks_enabled` across the whole expression, mirroring `LabeledHandler#respond_to_label_change?`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add a matrix test:
```ruby
[:allow_all, :allow_with_label, :prevent_with_label].each do |behavior|
  test "does not create stacks when review_stacks_enabled is false, behavior=#{behavior}" do
    repository = shipit_repositories(:shipit)
    configure_provisioning_behavior(
      repository:, provisioning_enabled: false, behavior:, label: "pull-requests-label"
    )
    payload = payload_parsed(:pull_request_opened)
    payload["pull_request"]["labels"] << { "name" => "pull-requests-label" } if behavior == :allow_with_label

    assert_no_difference -> { Shipit::Stack.count } do
      OpenedHandler.new(payload).process
    end
  end
end
```
Currently, for `behavior: :allow_with_label` (label present) and `behavior: :prevent_with_label` (label absent, default payload), `Shipit::Stack.count` changes despite `review_stacks_enabled == false`, while for `:allow_all` it correctly does not — demonstrating the inconsistency described in the question.
