### Title
Stack-scoped API tokens can read the CCMenu status of any stack, bypassing token scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces token-to-stack binding by scoping the `stack` accessor through `stacks`, which filters by `current_api_client.stack_id` when the `ApiClient` is stack-scoped. `Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping entirely, resolving the stack directly from the unauthenticated `params[:stack_id]`. This breaks the binding *"a stack a token authorises == a stack it touches"*, allowing any valid API token — even one deliberately scoped to a single stack (as is the normal case for CCMenu URLs) — to read the CI/deploy status of every other stack in the installation.

### Finding Description
`BaseController` defines the canonical, scoped resource resolution: [1](#0-0) 

`stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set, and every other resource controller (`DeploysController`, `RollbacksController`, `TasksController`, `OutputsController`, `LocksController`, `MergeRequestsController`, `ReleaseStatusesController`, `CommitsController`, `HooksController`) relies on this same `stack`/`stacks` method inherited from `BaseController`, so a stack-scoped token can never touch another stack's data.

`CCMenuController`, however, redefines `stack` independently of `stacks`: [2](#0-1) 

`Stack.from_param!(params[:stack_id])` resolves against **all** stacks, ignoring `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the token's `permissions` array contains the string `"read:stack"` — it never checks *which* stack the permission applies to: [3](#0-2) 

So the only place stack-instance authorization is supposed to be enforced is the `stack`/`stacks` method — and `CCMenuController` deliberately (or accidentally) opts out of it. `CCMenuController` also supports authenticating via a bare query-string token, which is exactly the pattern used to generate long-lived, narrowly-scoped, unauthenticated-context CI badge URLs: [4](#0-3) [5](#0-4) 

The verified side of the binding is "the stack the `ApiClient.stack_id` authorizes"; the acted-upon side is "the stack named by `params[:stack_id]`" in `CCMenuController#stack`. These two are never checked for equality in this controller, unlike everywhere else in the API surface.

### Impact Explanation
Any holder of a valid `ApiClient` token — including a token intentionally scoped to a single stack via the `stack:` association (the exact model used by `CCMenuUrlController` to mint per-stack CCMenu URLs, and by the `here_come_the_walrus` fixture) — can query `/api/*/stack_id*/ccmenu.xml` (or whatever path resolves to `CCMenuController#show`) with an arbitrary `stack_id` and obtain that other stack's build/deploy status, lock state, and last build label. This is an unauthenticated-context (or minimally-scoped) read of stack state across stack/tenant boundaries, matching the "High - unauthenticated read of stack state, task streams or deploy output" impact bucket in scope for this exercise, since it escalates a single-stack read-only credential into an all-stacks read-only credential.

### Likelihood Explanation
Likelihood is high for any deployment where CCMenu URLs (or other stack-scoped tokens) are shared outside a fully trusted circle — CCMenu/CI-status URLs are explicitly designed to be embeddable in third-party dashboards/build-status widgets and are not treated as highly sensitive, since they're believed to only expose one stack's status. No additional privilege beyond possessing *any* valid API token (even a minimally scoped one obtained via the normal `CCMenuUrlController#fetch` flow available to any authenticated Shipit user) is required to pivot to reading all stacks' status.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that the `current_api_client.stack_id` restriction enforced elsewhere in the API is also applied here.

### Proof of Concept
1. As an authenticated Shipit user, visit any stack and let `CCMenuUrlController#fetch` mint a stack-scoped `ApiClient` (`permissions: %w[read:stack]`, `stack: <stack A>`), yielding a CCMenu URL with `token=<tokenA>`.
2. Using `tokenA`, issue: `GET /api/<stack_B_id>/ccmenu.xml?token=<tokenA>` where `stack_B_id` refers to a different stack the token was never scoped to.
3. `CCMenuController#authenticate_api_client` authenticates `tokenA` successfully (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`).
4. `require_permission :read, :stack` passes because `tokenA` does have `"read:stack"` in its permissions list, regardless of stack (`app/models/shipit/api_client.rb:38-45`).
5. `CCMenuController#stack` resolves `stack B` directly via `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` filter that `BaseController#stacks` would have applied (`app/controllers/shipit/api/ccmenu_controller.rb:29-31` vs `app/controllers/shipit/api/base_controller.rb:74-80`).
6. The response renders stack B's CCMenu status (`show` action), leaking build/deploy state for a stack `tokenA` was never authorized to read.
