### Title
Unauthenticated P2P `ServiceChainResponse` Injection Enables Unauthorized KAIA/ERC20/ERC721 Transfer via VT Recovery — (`node/sc/sub_bridge_handler.go`)

### Summary

The SubBridge's `HandleMainMsg` writes any `ServiceChainResponse` P2P message directly to the local `rpcConn` pipe without authenticating the sender or validating the content. Because `RemoteBackend.FilterLogs` sources its `kaia_getLogs` responses through this same pipe, a malicious P2P peer that connects to the SubBridge can inject crafted log responses during VT recovery, causing the child chain bridge operator to call `HandleKLAYTransfer` / `HandleERC20Transfer` / `HandleERC721Transfer` with attacker-controlled parameters.

### Finding Description

`NewRpcClientP2P` creates a `net.Pipe` `(p1, p2)`. The `rpc.Client` uses `p2`; `p1` is stored as `sb.rpcConn`. [1](#0-0) 

When the `rpc.Client` issues a `kaia_getLogs` call, the JSON-RPC request travels: `p2` → `p1` → `SetRPCConn` goroutine → `rpcSendCh` → `SendRPCData` → `peer.SendRequestRPC` (P2P `ServiceChainCall` message). [2](#0-1) 

The response path is the reverse: the peer sends a `ServiceChainResponse` P2P message, and `HandleMainMsg` writes it verbatim to `rpcConn`: [3](#0-2) 

There is no check that the writing peer is the same peer that received the request, no cryptographic binding to the parent chain state, and no content validation. Any connected P2P peer can send a `ServiceChainResponse` at any time.

`RemoteBackend.FilterLogs` blindly deserialises whatever bytes arrive: [4](#0-3) 

`retrievePendingEventsFrom` calls `from.bridge.FilterRequestValueTransfer` (which calls `FilterLogs` on the `RemoteBackend`) and accepts the returned events as canonical parent-chain events: [5](#0-4) 

The only guard, `isHandledEvent`, queries the **local** child chain bridge contract — it cannot detect fabricated events for nonces that are genuinely unhandled: [6](#0-5) 

`recoverPendingEvents` then feeds the crafted events into `cBridgeInfo.AddRequestValueTransferEvents`, which triggers `handleRequestValueTransferEvent`: [7](#0-6) 

`handleRequestValueTransferEvent` calls the child chain bridge contract with attacker-supplied `to`, `value`, `tokenAddress`, `requestNonce`, and `txHash`: [8](#0-7) 

The bridge contract's `handleKLAYTransfer` has `onlyOperators` (the SubBridge operator is the caller — passes), `_lowerHandleNonceCheck` (passes for any unhandled nonce), and `_setHandledRequestTxHash` (passes for any fresh attacker-chosen bytes32). It then executes the transfer: [9](#0-8) 

### Impact Explanation

An attacker who connects as a P2P peer to the SubBridge and injects a crafted `ServiceChainResponse` during VT recovery can cause the child chain bridge operator to call `HandleKLAYTransfer`, `HandleERC20Transfer`, or `HandleERC721Transfer` with arbitrary `to` and `value` fields. The child chain bridge contract will transfer KAIA, mint ERC20 tokens, or transfer ERC721 NFTs to the attacker's address. This is an unauthorized transfer of bridged assets from the child chain bridge.

### Likelihood Explanation

The SubBridge accepts incoming P2P connections from any node that passes the handshake (network ID + chain ID check only): [10](#0-9) 

Network ID and chain ID are public. VT recovery triggers automatically whenever `requestNonce > handleNonce` persists across two consecutive recovery intervals — a normal operational condition. `SendRPCData` sends to the first peer in the map, so a single connected attacker peer is sufficient.

### Recommendation

1. **Authenticate the RPC response source**: Track which peer received the `ServiceChainCall` request and only accept a `ServiceChainResponse` from that same peer within the same request context.
2. **Verify recovered events against canonical parent chain state**: After `retrievePendingEventsFrom`, re-verify each event's `txHash` and log index against a trusted parent chain source (e.g., a receipt query) before submitting `HandleValueTransfer` transactions.
3. **Restrict P2P peer acceptance**: Require the SubBridge to only accept connections from a configured allowlist of parent chain node IDs, rejecting all others at the handshake stage.

### Proof of Concept

1. Run a SubBridge node with VT recovery enabled (`VTRecovery: true`) and at least one pending unhandled request nonce.
2. Connect a malicious node to the SubBridge's P2P port, passing the handshake with the correct network ID and chain ID.
3. When the SubBridge sends a `ServiceChainCall` (JSON-RPC `kaia_getLogs` request), respond with a `ServiceChainResponse` containing a crafted JSON-RPC result: a `RequestValueTransfer` log with `to = <attacker address>`, `value = <bridge balance>`, `requestNonce = <any unhandled nonce>`, `txHash = <fresh bytes32>`, `tokenType = KAIA`.
4. Observe that `retrievePendingEventsFrom` accepts the crafted event (passes `isHandledEvent` since the nonce is genuinely unhandled on the child chain).
5. Observe that `recoverPendingEvents` submits a `HandleKLAYTransfer` transaction to the child chain bridge contract.
6. Confirm that the child chain bridge contract transfers KAIA to the attacker's address.

					time.Sleep(100 * time.Millisecond)

	}()

func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:

	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
