## Title
Block-reward distribution shares a stale, un-debited `pending_delegator_rewards` pool across stakers, misattributing reward amounts - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

## Summary
This finding parallels the external report's bug class: an amount owed to multiple claimants is computed from a shared pool balance that can change (or is never reconciled) between the "calculation" and "distribution" phases, causing unfair/incorrect payouts. In Agave's block-revenue-sharing feature (SIMD-0123), each stake account's `block_reward` is computed as a proportional share of the vote account's `pending_delegator_rewards` field, but that field is never decremented as it is paid out to individual stakers, and the per-epoch snapshot used for the proportional split can diverge from the vote account's actual state at distribution time.

## Finding Description
`calculate_block_reward` reads `pending_delegator_rewards` from a cached, calculation-time view of the vote account and computes each stake account's share as `pending_delegator_rewards * stake / total_active_stake`, clamped to `pending_delegator_rewards`: [1](#0-0) 

This value is computed once per stake delegation, independently, all against the *same* un-mutated `pending_delegator_rewards` snapshot held in `distribution_epoch_vote_accounts`. Nothing in this calculation subtracts amounts already paid out to other stakers of the same vote account, so the sum of all `block_reward` shares for a given vote account is only guaranteed correct as a mathematical partition of `stake / total_active_stake`, not as a running deduction from an actually-shrinking balance. During recalculation (fork-switch/reorg), stale, already-rewarded stake weight can make `stake > total_active_stake`, which the code comments acknowledge can cause individual shares to look greater than the pending pool — handled only by a `min()` clamp, not by joint conservation: [2](#0-1) 

Separately, `pending_delegator_rewards` in the vote account itself is only ever incremented via `DepositDelegatorRewards` (an unprivileged, permissionless instruction any signer can call) and is never decremented after a partitioned block-reward distribution actually pays lamports out of the pool: [3](#0-2) [4](#0-3) 

The `withdraw` instruction handler treats `pending_delegator_rewards` as an untouchable reserve that must remain in the vote account's lamport balance (`lamports - pending_delegator_rewards - rent_exempt`), which confirms the field is meant to represent lamports still owed to delegators: [5](#0-4) 

But `store_stake_accounts_in_partition` / `build_updated_stake_reward`, which actually mints/credits `block_reward` lamports into each stake account, never debits the source vote account's lamports or its `pending_delegator_rewards` field to match: [6](#0-5) [7](#0-6) 

The capitalization/sysvar accounting only tracks `block_reward_lamports_distributed`/`burned` in aggregate against the epoch-rewards sysvar, not against the originating vote account's `pending_delegator_rewards` balance: [8](#0-7) 

This mirrors the report's root cause exactly: a "finalize" step (partitioned stake-reward distribution) pays out an `amountOwed` computed from a shared pool balance (`pending_delegator_rewards`) that is never actually reconciled/decremented against real disbursements, and can additionally be manipulated in between calculation and distribution — the pool can be topped up via `DepositDelegatorRewards` by anyone (including the vote account's own delegators) at any point, since that instruction has no timing restriction relative to the reward-calculation/distribution window (`REWARD_CALCULATION_NUM_BLOCKS` gap): [9](#0-8) 

## Impact Explanation
Because `pending_delegator_rewards` is never debited when it is actually distributed to stakers as `block_reward`, each epoch's block-reward computation effectively double-counts or misattributes an outstanding pool: it is possible for the same lamports in `pending_delegator_rewards` to be proportionally "promised" to stakers across multiple recalculation epochs (via the fork-recalculation path noted in the code comments) or for the withdraw-authority-enforced reserve to no longer match what stakers are actually owed, since the pool value used at calculation time is a stale, un-reconciled snapshot. This can result in misattributed/duplicated rewards being minted into stake accounts (`checked_add_lamports` in `build_updated_stake_reward`), directly affecting lamport accounting and total capitalization tracked by the bank.

## Likelihood Explanation
Medium: block revenue sharing (SIMD-0123) is a currently-shipping feature gated behind `block_revenue_sharing`/`custom_commission_collector`/`commission_rate_in_basis_points` feature flags, and `DepositDelegatorRewards` is a fully permissionless, unprivileged instruction reachable by any signer at any time relative to the epoch reward calculation/distribution window, so the race between deposit/calculation/distribution phases is trivially triggerable in normal operation, not merely a theoretical edge case.

## Recommendation
Debit `pending_delegator_rewards` (and the corresponding vote-account lamports) at distribution time by the exact `block_reward` amount actually paid to each stake account, rather than relying solely on a calculation-time proportional snapshot; ensure the aggregate `block_reward` paid out across all stakers of a vote account can never exceed the vote account's *current* `pending_delegator_rewards` value at the moment of distribution (analogous to adding a `minAmountOut`/conservation check in the report's `finalizeUnstake`), and reconcile/re-clamp `pending_delegator_rewards` against actual vote-account lamports at recalculation time to eliminate the stale-snapshot double-counting scenario called out in the code comments.

## Proof of Concept
Not independently reproducible from static review alone; the code comments themselves acknowledge the exact failure mode ("if `pending_delegator_rewards` is a huge number, we could potentially overflow... individual rewards look greater than the pending rewards... clamp it just to be safe") without demonstrating end-to-end conservation across the full deposit → calculate → distribute → recalculate lifecycle. Confirming actual lamport double-payment would require constructing a fork-switch/recalculation scenario combined with an interleaved `DepositDelegatorRewards` call, which is beyond what can be validated via static code reading and would need to be exercised in a local test-validator/bank-forks integration test.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    fn store_stake_accounts_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) -> DistributionResults {
        let feature_snapshot = self.feature_set.snapshot();
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;

        let mut stake_reward_lamports_minted = 0;
        let mut stake_reward_lamports_burned = 0;
        let mut block_reward_lamports_distributed = 0;
        let mut block_reward_lamports_burned = 0;
        let indices = partition_rewards
            .partition_indices
            .get(partition_index as usize)
            .unwrap_or_else(|| {
                panic!(
                    "partition index out of bound: {partition_index} >= {}",
                    partition_rewards.partition_indices.len()
                )
            });
        let mut updated_stake_rewards = Vec::with_capacity(indices.len());
        let stakes_cache = self.stakes_cache.stakes();
        let stakes_cache_accounts = stakes_cache.stake_delegations();
        let stake_history = stakes_cache.history();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let rent = &self.rent_collector.rent;
        for index in indices {
            let partitioned_stake_reward = partition_rewards
                .all_stake_rewards
                .get(*index)
                .unwrap_or_else(|| {
                    panic!(
                        "partition reward out of bound: {index} >= {}",
                        partition_rewards.all_stake_rewards.total_len()
                    )
                })
                .as_ref()
                .unwrap_or_else(|| {
                    panic!("partition reward {index} is empty");
                });
            let stake_pubkey = partitioned_stake_reward.stake_pubkey;
            let stake_reward_amount = partitioned_stake_reward.inflation.stake_reward;
            let block_reward_amount = partitioned_stake_reward.block_reward;

            match Self::build_updated_stake_reward(
                self.epoch,
                stake_history,
                new_warmup_cooldown_rate_epoch,
                stakes_cache_accounts,
                partitioned_stake_reward,
                rent,
                adjust_delegations_for_rent,
                use_fixed_point_stake_math,
            ) {
                Ok(stake_reward) => {
                    stake_reward_lamports_minted += stake_reward_amount;
                    block_reward_lamports_distributed += block_reward_amount;
                    updated_stake_rewards.push(stake_reward);
                }
                Err(err) => {
                    error!(
                        "bank::distribution::store_stake_accounts_in_partition() failed for \
                         {stake_pubkey}, {stake_reward_amount} lamports burned: {err:?}"
                    );
                    stake_reward_lamports_burned += stake_reward_amount;
                    block_reward_lamports_burned += block_reward_amount;
                }
            }
        }
        drop(stakes_cache);
        self.store_accounts(
            (self.slot(), &updated_stake_rewards[..]),
            // Reuse the rewards calculation thread pool to parallelize
            // loading the previous versions of the stake accounts.
            Some(crate::bank::rewards_calculation_thread_pool()),
        );
        DistributionResults {
            stake_reward_lamports_minted,
            stake_reward_lamports_burned,
            block_reward_lamports_distributed,
            block_reward_lamports_burned,
            updated_stake_rewards,
        }
    }
