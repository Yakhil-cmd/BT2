### Title
Cross-organization Team/Membership forgery via `MembershipHandler#find_or_create_team!` ignoring the webhook-verified organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the `webhook_secret` of the organization named in the payload itself (`repository_owner`), which the attacker fully controls when the `repository` key is omitted. `MembershipHandler#find_or_create_team!` then looks up `Team` purely by the attacker-supplied `params.team.id` (`github_id`), with no check that this team's `organization` matches the organization whose secret actually verified the request, so an attacker who owns their own onboarded GitHub App in the same Shipit instance can bind their own login to any pre-existing `Team` belonging to a different organization.

### Finding Description
The security invariant that should hold is:

`verified_organization` (the org whose `webhook_secret` produced a matching `X-Hub-Signature`, i.e. `repository_owner` used in `Shipit.github(organization: repository_owner)`) **==** `team.organization` (the org that owns the `Team` row being mutated).

In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
`repository_owner` is derived from the request body itself: [2](#0-1) 
Since `Handlers::MembershipHandler`'s schema never requires a `repository` key, the attacker can send a payload with only `organization: {login: 'attacker-org'}`, making `repository_owner == 'attacker-org'` and causing `Shipit.github(organization: 'attacker-org')` to verify with attacker-org's own genuine `webhook_secret` — which the attacker legitimately knows, since they configured that GitHub App entry themselves.

Once signature verification succeeds, `MembershipHandler#process` calls `find_or_create_team!`: [3](#0-2) 
`Team.find_or_create_by!(github_id: params.team.id)` looks the team up **only by `github_id`**. If the attacker supplies a `team.id` equal to the `github_id` of an already-existing `Team` (e.g. `shipit_teams(:shopify_developers)`, created earlier from a genuine shopify webhook), the record is found and the creation block (which would set `team.organization = params.organization.login`) never runs. The pre-existing `team.organization` ("shopify") is left untouched, but `team.add_member(User.find_or_create_by_login!(params.member.login))` still executes, adding the attacker's GitHub login as a member of shopify's team — despite the request being authenticated only via attacker-org's secret.

No code anywhere re-checks `team.organization` against `repository_owner`/`params.organization.login` before calling `add_member`. `verify_signature` only proves "this body was sent by someone with the attacker-org secret"; it does not prove "this body is authoritative for team X."

### Impact Explanation
If the resulting `Team` is one of `Shipit.github_teams` (the teams gating login), the attacker's login now satisfies `User#authorized?`: [4](#0-3) 
This is a full authentication bypass into the shared Shipit instance for the victim organization's authorization boundary — the attacker's GitHub account becomes a recognized member of a privileged team without ever being invited to the victim's real GitHub team, and can now log in and act with that team's privileges across all stacks in the instance. The attack is repeatable for any team `github_id` the attacker can learn (team IDs are often discoverable via GitHub's API) and requires only one HTTP POST per target team.

### Likelihood Explanation
Preconditions: the Shipit deployment must be multi-tenant, i.e., configure more than one organization entry under `Shipit.github` (`github_app_config`), and the attacker must control one such legitimate organization entry (own its GitHub App and thus its `webhook_secret`) as stipulated by the question. Given that, the attacker needs no Shipit session, no victim secrets, and only the numeric `github_id` of a target `Team` already present in the `teams` table (created by any prior genuine event) — a modest, realistic precondition. The forged request is a single POST to `/webhooks` with a self-computed valid signature.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved organization for the current webhook request (`repository_owner`/the org whose secret validated the signature) matches the found or newly created `Team#organization` before performing any mutation; reject (or no-op) the event if they diverge. More generally, scope the `Team.find_or_create_by!` lookup by `(github_id, organization)` rather than `github_id` alone, and have `WebhooksController` pass the verified organization down to handlers so per-handler logic can enforce tenant isolation instead of trusting attacker-controlled `params.organization.login`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "membership webhook cannot bind an attacker to another organization's team" do
  victim_team = shipit_teams(:shopify_developers)
  assert_equal 'shopify', victim_team.organization

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' }, # no `repository` key -> repository_owner == 'attacker-org'
    member: { login: 'attacker-login' }
  }.to_json

  assert_difference -> { Membership.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  membership = Membership.last
  assert_equal victim_team.id, membership.team_id
  assert_equal 'attacker-login', membership.user.login
  # Broken binding demonstrated: verified organization ('attacker-org') != team.organization ('shopify')
  refute_equal 'attacker-org', victim_team.organization
end
```
