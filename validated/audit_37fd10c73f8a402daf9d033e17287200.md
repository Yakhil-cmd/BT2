### Title
`StatusHandler#process` mutates commits across repositories via unscoped `Commit.where(sha:)` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with a bare `Commit.where(sha: params.sha)`, with no repository/stack scoping, unlike `PushHandler` and `CheckSuiteHandler` which restrict all writes to `stacks` (derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`). Because the schema's uniqueness constraint on commits is `(sha, stack_id)` and not `sha` alone, two different repositories/stacks can legitimately hold rows with the identical `sha` (e.g. via forks, which share full git history), and a validly-signed status webhook for one repository will write a forged status onto the other repository's commit.

### Finding Description
**Broken binding:** for every `Handler` subclass, the set of mutated records must equal `stacks`-scoped records for the payload's own `repository.full_name`. `PushHandler#process` and `CheckSuiteHandler#process` satisfy this: `stacks.not_archived.where(branch:)...` [1](#0-0)  and `stacks.where(branch: ...)` [2](#0-1) , where `stacks` is `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) .

`StatusHandler#process`, however, mutates `Commit.where(sha: params.sha)` with no reference to `stacks`, `repository_name`, or the payload's repository at all: [4](#0-3) . This equality fails: `StatusHandler`'s write set can include commits belonging to any stack in the database, not just the ones owned by the repository that sent the webhook.

This is exploitable because the `commits` table's uniqueness constraint is `(sha, stack_id)`, not `sha` alone: [5](#0-4) , confirming the schema was designed to permit identical shas across different stacks/repositories — exactly what happens when two Shipit-tracked repositories share git ancestry (e.g. a fork and its upstream, or two repos importing the same commit).

**Exploit path:** An attacker owns/forks a repository (fork B) whose git history overlaps with a target repository (upstream A) that is a genuine Shipit stack. Because forks copy commit objects byte-for-byte, commits shared with the upstream have identical SHA-1 in both repos. The attacker adds their own fork as a Shipit-managed repository (or otherwise has a legitimately signed webhook channel for it) and creates a commit status via the GitHub API/UI on the shared commit in their own fork with an arbitrary `context`, `state` (e.g. `success`), `description`, and `target_url`. GitHub delivers a `status` webhook for repository B, which passes `verify_signature` (`GithubApp#verify_webhook_signature`) because it is genuinely signed for organization/repo B — the signature check only proves who sent the webhook, not which commit rows may be touched. `StatusHandler#process` then finds `Commit.where(sha: <shared sha>)`, which returns the row belonging to stack A, and calls `commit.create_status_from_github!(params)` on it, writing the attacker-controlled status onto repository A's commit.

None of the existing guards close this gap: `verify_signature`/`GithubApp#verify_webhook_signature` [6](#0-5)  only authenticates the sending repository, not the sha's ownership; `ExplicitParameters` in `StatusHandler` only validates shape (`sha`, `state`, etc.), not tenant scope [7](#0-6) ; and `Repository.from_github_repo_name` is never consulted by `StatusHandler` at all.

### Impact Explanation
An attacker can write an arbitrary, attacker-chosen commit-status (`context`, `state=success/failure/error`, `description`, `target_url`) onto a commit belonging to a repository/stack they do not own, as long as that commit's SHA is shared (via fork ancestry) with a commit in their own repository. `Commit#create_status_from_github!` triggers `commit_status`/`deployable_status` hooks and can flip a commit's aggregate `state`, which feeds into deploy-readiness decisions and `ProcessMergeRequestsJob` (auto-merge) for the victim stack. This is a genuine cross-tenant write ("a payload for one repository mutating another's stack, commit... state") matching the Critical impact category. The attack is repeatable against any pair of repositories that share commit history, and blast radius scales to every Shipit-managed repository that has been forked (a common, unprivileged GitHub action).

### Likelihood Explanation
Preconditions: the attacker needs (a) a fork or history-sharing relationship with a real Shipit-tracked repository, and (b) that fork itself must be onboarded to send status webhooks to Shipit (either because they added it as a repository/stack, or Shipit is broadly subscribed to org-wide webhooks). Given Shipit's webhook signature check is per-repository-owner and not tied to specific SHAs, and the schema explicitly tolerates duplicate SHAs across stacks, this requires no secrets, no privileged role, and only standard, low-cost GitHub actions (fork + create a commit status via API) — well within the stated unprivileged attacker capability. It is fully repeatable.

### Recommendation
Scope `StatusHandler#process` to only mutate commits belonging to the requesting repository's stacks, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the invariant that every handler's mutation set is bounded by `Repository.from_github_repo_name(repository_name).stacks`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_scope_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerScopeTest < ActiveSupport::TestCase
        test "StatusHandler mutates a commit belonging to an unrelated repository sharing the same sha" do
          repo_a = shipit_repositories(:shipit) # victim
          repo_b = create_repository(owner: 'attacker', name: 'fork') # attacker-owned, unrelated repo

          shared_sha = 'a' * 40
          stack_a = repo_a.stacks.first
          stack_b = repo_b.stacks.create!(environment: 'production', repository: repo_b)

          commit_a = stack_a.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), message: 'shared')
          commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), message: 'shared')

          payload = {
            'repository' => { 'full_name' => repo_b.full_name, 'owner' => { 'login' => 'attacker' } },
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'forged/ci',
          }

          # Sibling handler respects repository scope: no effect on repo A
          PushHandler.new(payload.merge('ref' => 'refs/heads/master', 'after' => shared_sha)).process
          assert_equal 0, commit_a.statuses.reload.count

          # StatusHandler mutates repo A's commit despite payload claiming repo B
          StatusHandler.new(payload).process
          assert_equal 1, commit_a.statuses.reload.count, "victim repository's commit was mutated by attacker-owned repository's webhook"
          assert_equal 'forged/ci', commit_a.statuses.last.context
        end
      end
    end
  end
end
```
This demonstrates the equality violation directly: `PushHandler`'s effect on repo A is empty (scoped via `stacks`), while `StatusHandler`'s effect on repo A is non-empty (unscoped `Commit.where(sha:)`), for the identical cross-repo payload.
