## Finding

### Title
Autonomous Agents silently drop outgoing payments of fixed-denomination (indivisible/NFT-like) assets, permanently freezing any such asset sent to an AA - (File: aa_composer.js)

### Summary
The reported bug is that `transferFrom` (unsafe ERC721 transfer) can leave an NFT stuck in a contract that can't handle it, because the sender never checks whether the destination can properly receive/forward the asset. In `ocore`, autonomous agents (AAs) are the closest analog to smart contracts that receive and later spend assets. When an AA is triggered with a fixed-denomination ("indivisible", NFT-like) asset, or when an oscript author writes AA logic intended to forward such an asset onward, `aa_composer.js` silently filters out any `payment` message for a `fixed_denominations` asset instead of failing loudly or bouncing. The asset thus remains permanently locked at the AA address with no way for the AA or its logic to ever move it again.

### Finding Description
In the message-composition pipeline of `handleTrigger`/`sendUnit`, each `payment` message payload is inspected and asset info is loaded: [1](#0-0) 

If the asset has `fixed_denominations` set, the code explicitly notes "will skip it later" and just calls `cb()`, doing nothing further with the message (no output addresses added, no completion, no error).

Later, after the first pass, the messages array is filtered a second time: [2](#0-1) 

Any payment message referencing a `fixed_denominations` asset is removed from the outgoing unit entirely. If this was the only message, the AA silently produces an "empty response" (`handleSuccessfulEmptyResponseUnit`) as if nothing needed to be sent — no error, no bounce, no state indicating failure.

Critically, this same `sendUnit` path is also used by the automatic bounce mechanism: [3](#0-2) 

`bounce()` builds `payment` messages for every asset in `trigger.outputs` (including fixed-denomination/indivisible assets) and passes them into `sendUnit(messages)`, which will silently drop the fixed-denomination payment message via the same filtering logic. So even the "refund the triggering payment" safety mechanism cannot return an indivisible asset back to the sender.

Because AA addresses are defined by the `['autonomous agent', ...]` definition (no private key/signature can ever spend from them — only AA-composed response units can), once a fixed-denomination asset output lands at an AA address, there is no mechanism — neither the AA's own oscript payment messages nor the automatic bounce logic — capable of moving it out again. This is architecturally analogous to an ERC721 token sent via unsafe `transferFrom` into a contract lacking `onERC721Received` handling: the asset is received but the receiving "contract" (the AA) has no functioning code path to transfer it onward, so it is stuck forever.

### Impact Explanation
Any unprivileged unit poster (or an AA responding to another AA) can send a fixed-denomination asset to any AA address, either accidentally or as part of normal use of an AA that is supposed to accept and re-issue/forward NFT-like assets (a common pattern for auction/marketplace/collectible-style AAs). The asset becomes permanently and irrecoverably locked at the AA address: no AA logic and no bounce path can ever release it. This is a direct, unconditional AA fund freezing/loss of value for any asset class that uses `fixed_denominations: true`, impacting any AA design that intends to custody or relay indivisible assets. This matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is high for any AA that is designed to accept indivisible/NFT-like assets (a legitimate, documented asset type in ocore, validated in `aa_validation.js` and `validation.js`), since the freezing occurs deterministically and silently — there is no error surfaced to the AA author or the sender indicating the payment was dropped, making it easy to trigger unintentionally by any ordinary unit sender, and impossible to detect/prevent from within oscript.

### Recommendation
Either:
1. Reject/bounce triggers that include `fixed_denominations` (indivisible) asset outputs to AAs at validation time (in `validateAATrigger` / `aa_addresses.checkAAOutputs`) so senders are informed the AA cannot handle such assets, preventing silent loss, or
2. Implement proper support for AAs to compose outgoing `payment` messages for `fixed_denominations` assets (picking/forwarding indivisible coin outputs) instead of silently filtering these messages out of `sendUnit`, including in the `bounce()` path.

### Proof of Concept
1. Define/register an asset with `fixed_denominations: true` (an indivisible, NFT-like asset).
2. Deploy an AA whose `messages` include a `payment` message that, upon receiving this asset, is intended to forward it to another address (or simply relies on `bounce()` to refund it if conditions aren't met).
3. Post a unit that sends units of the fixed-denomination asset to the AA as the trigger payment (a standard, unprivileged payment output, validated by `validatePaymentInputsAndOutputs` in `validation.js`).
4. Observe in `aa_composer.js` (`handleTrigger` → `sendUnit`) that the `payment` message referencing this asset is filtered out at line 1327-1328 (first pass, "will skip it later") and again at line 1356 (second pass, `!assetInfos[...].fixed_denominations`), producing either an empty successful response or dropping just that message — the asset value is never returned or forwarded.
5. Confirm there is no other code path (bounce or otherwise) by which the AA can ever spend/move this asset — it remains at the AA address indefinitely.
