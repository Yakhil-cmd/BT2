### Title
Cross-organization webhook forgery: signature verified against `repository.owner.login`, but handlers act on `repository.full_name` and unscoped commit SHAs - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate against using the attacker-controlled `repository.owner.login` field of the JSON body, but the event handlers that subsequently execute writes key off a *different* attacker-controlled field, `repository.full_name`, and in the `status` handler don't scope by repository at all. In a multi-GitHub-App Shipit deployment, an attacker who legitimately controls (and therefore knows the webhook secret of) one configured GitHub organization can forge a signature that passes verification while making the payload's `repository.full_name`/commit `sha` point at a *different* organization's repository/commit that Shipit tracks.

### Finding Description
`verify_signature` derives the signing organization purely from the unverified request body: [1](#0-0) [2](#0-1) 

It looks up `Shipit.github(organization: repository_owner)` and checks the request's `X-Hub-Signature` against *that* organization's `webhook_secret`. In the documented multi-org configuration, each organization has its own independent secret, so this only proves the request was signed by whoever administers `repository_owner`'s GitHub App — it says nothing about the rest of the payload. [3](#0-2) 

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the *entire* raw JSON, and `Handler#stacks`/`#repository_name` re-derive the target repository from a **different** field, `repository.full_name`, which was never checked against `repository_owner`: [4](#0-3) 

`PushHandler` uses this mismatched lookup to trigger a sync with an attacker-chosen `expected_head_sha` for whatever stacks match `full_name`: [5](#0-4) 

`StatusHandler` is worse: it doesn't even use `repository_name`/`stacks` — it looks up commits **globally by SHA** and writes a status to them: [6](#0-5) 

This breaks the trust binding: `organization that authenticated the request` (verified via `repository_owner` → that org's `webhook_secret`) ≠ `repository/commit that is actually written` (taken from `repository.full_name` / `sha`, never covered by that same verification).

### Impact Explanation
An attacker who operates one GitHub organization configured in a multi-org Shipit instance (a legitimate, documented setup) can forge webhook events whose signature is valid for their own org, but whose `repository.full_name`/`sha` target a stack/commit belonging to a completely different tracked repository. Via the `status` event this lets the attacker inject an arbitrary `commit_status` (e.g., a fabricated "success" state for a required check context) onto any commit SHA already known to Shipit, regardless of which repository it belongs to. If Shipit's merge queue or deploy pipeline gates merges/deploys on `deployable_status`/commit status, this can produce an unauthorized deploy or merge of a commit that never actually passed CI — matching the Critical impact bucket ("an unauthorized deploy, rollback or merge"). The `push` event similarly lets the attacker trigger syncs on unrelated stacks with an attacker-chosen expected head SHA.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub App/organization (a documented, supported configuration) and that the attacker controls (or is a member with webhook-secret knowledge of) at least one of those organizations — no privileged Shipit account, API token, or session is needed, satisfying the "unprivileged attacker" constraint. This is a realistic multi-tenant configuration for shared Shipit deployments.

### Recommendation
Bind the field used for signature-secret selection to the field used for the actual write: after verifying the signature, re-derive/validate that `repository.full_name`'s owner matches the `repository_owner` used to select the secret (i.e., reject if `full_name.split('/').first != repository_owner`), and scope `StatusHandler`'s `Commit.where(sha:)` lookup by the verified repository rather than a global SHA search.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with GitHub Apps for `AttackerOrg` and `victim-org`, each with its own `webhook_secret`.
2. Attacker knows `AttackerOrg`'s webhook secret (it's their own org's App).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and body:
```json
{
  "repository": { "full_name": "attacker-anything", "owner": { "login": "AttackerOrg" } },
  "sha": "<sha of a commit tracked under victim-org/victim-repo>",
  "state": "success",
  "context": "required-ci-check"
}
```
signed with `AttackerOrg`'s secret as `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "AttackerOrg")` and validates successfully against `AttackerOrg`'s secret [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of the `AttackerOrg` owner field — and calls `create_status_from_github!`, writing the forged "success" status onto a commit the attacker never actually controls [6](#0-5) .
