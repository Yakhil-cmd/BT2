### Title
Webhook signature verification authenticates the payload against the organization derived from `repository.owner.login`, but every event handler dispatches to the repository/stack derived from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the webhook secret used for HMAC verification) using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

Every downstream `Handler` subclass (push, status, check_suite, pull_request, etc.), however, resolves the *target* repository/stack using a completely different field, `payload.dig('repository', 'full_name')`: [3](#0-2) 

`verify_webhook_signature` only proves that the raw HTTP body was HMAC-signed with the secret configured for the organization named in `repository.owner.login`; it never checks that this organization actually owns the repository named in `repository.full_name` used later for routing. [4](#0-3) 
In Shipit's multi-tenant configuration, each GitHub organization gets its own independently configured `webhook_secret`. [5](#0-4) 

### Finding Description
The trust binding that should hold is: `organization whose secret authenticated the HMAC == organization/repository the event is applied to`. Instead the code enforces two unrelated equalities:

1. `HMAC(secret[repository.owner.login], raw_body) == X-Hub-Signature` — proves only that whoever set `repository.owner.login`'s webhook secret produced this exact byte string.
2. `stack = Repository.from_github_repo_name(repository.full_name).stacks` — determines what gets acted on, using `full_name`, a sibling field inside the very same JSON body that the attacker fully controls once they know any one organization's secret.

Because `repository.owner.login` and `repository.full_name` are independent strings inside the same attacker-crafted JSON body, and Shipit trusts the signer to have supplied a self-consistent payload, an operator who is a legitimate administrator of Org A (and therefore knows Org A's `webhook_secret`, since they configured GitHub's webhook themselves) can HMAC-sign an arbitrary payload where `repository.owner.login = "org-a"` (to pass signature verification with the secret they know) but `repository.full_name = "org-b/victim-repo"` (to target any stack in the entire Shipit instance, including repositories belonging to Org B, which they have no authorization over).

This directly breaks the "GitHub organization authenticated" vs "repository written" trust boundary called out in the analog rules: the value the signature covers structurally (the raw body) is not what actually gates access — only one unrelated substring of that body (`owner.login`) is used to pick the verification key, while a different substring (`full_name`) is used to pick the victim.

### Impact Explanation
With a forged `push` event (owner=org-a, full_name=org-b/victim-repo, `after`=attacker-chosen SHA), `PushHandler` enqueues `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on branch matching `ref` belonging to `org-b/victim-repo`. [6](#0-5) 
This forces Shipit to sync/deploy state for the victim's stack based entirely on attacker-controlled input, using the tokens/credentials Shipit already holds for `org-b` (since actual GitHub API access continues to be performed with `org-b`'s own installation token when acting on `org-b`'s repository) — this can trigger unauthorized deploy/rollback pipelines or corrupt `Commit`/`Status` state (via the analogous `StatusHandler`, which blindly attaches attacker-chosen `state`/`target_url`/`context` to any `Commit` row matching an attacker-chosen `sha`). [7](#0-6) 
This is a cross-tenant/cross-repository forgery of deploy-affecting GitHub events, satisfying the "cross-repository writes / unauthorized deploy or rollback" High/Critical impact bar.

### Likelihood Explanation
Requires only that the attacker be a legitimate administrator of *any one* GitHub organization configured in the same Shipit instance under the "multiple GitHub Applications" scheme (a normal, documented, unprivileged-relative-to-other-tenants setup) so they know that organization's own `webhook_secret`. [5](#0-4)  No access to any other tenant's secret, `ApiClient` token, or GitHub credentials is needed — they simply POST a self-crafted, self-signed payload to the shared `/webhooks` endpoint with a mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
After selecting the webhook secret via `repository_owner`, re-validate that `repository.full_name` (and `organization.login` for org-scoped events) is actually owned by that same organization before dispatching to handlers — e.g., assert `params.dig('repository', 'full_name')&.split('/')&.first&.casecmp?(repository_owner)` in `verify_signature`, rejecting the request with 422 on mismatch, rather than trusting the two fields independently.

### Proof of Concept
1. Deploy Shipit with the multi-org config from `test/dummy/config/secrets_double_github_app.yml`, with `OrgOne` and `OrgTwo` each having distinct `webhook_secret`s, and `OrgTwo/victim-repo` having a tracked `Stack` on branch `master`. [8](#0-7) 
2. Attacker is a legitimate GitHub org admin of `OrgOne` and therefore knows `OrgOne`'s `webhook_secret`.
3. Attacker crafts a `push` payload body:
```json
{"ref": "refs/heads/master", "after": "deadbeef...", "repository": {"owner": {"login": "OrgOne"}, "full_name": "OrgTwo/victim-repo"}}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(OrgOne_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")` (from `repository.owner.login`), verifies successfully since the attacker used OrgOne's real secret. [1](#0-0) 
6. `PushHandler#process` resolves stacks via `payload.dig('repository', 'full_name')` = `"OrgTwo/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` for OrgTwo's stack, despite the signature only proving OrgOne's involvement. [3](#0-2) [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
