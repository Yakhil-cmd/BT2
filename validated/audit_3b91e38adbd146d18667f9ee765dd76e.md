### Title
Unbounded in-memory buffering of git command output allows attacker-controlled remote content to trigger excessive memory allocation (DoS) - (File: pkg/cmd/cmd.go)

### Summary
git-sync's command runner buffers the entire stdout and stderr of every invoked `git` subprocess into unbounded `bytes.Buffer` objects before any size check, size limit, or streaming is applied. Since several of these git invocations (most notably `fetch`) process content that is entirely controlled by the remote/attacker-supplied repository, an attacker who controls the `--repo` target (or a compromised/malicious upstream that a legitimate sync is pointed at) can cause `git` to emit extremely large amounts of output, which is fully materialized in the git-sync process' heap with no cap, analogous in effect to the "onion bomb" class of DoS (uncontrolled allocation driven by parsing/handling attacker-influenced data).

### Finding Description
All git subprocess invocations flow through `runWithStdin` in `pkg/cmd/cmd.go`, which sets `cmd.Stdout` and `cmd.Stderr` to freshly allocated, unbounded buffers: [1](#0-0) 

There is no `io.LimitReader`, `http.MaxBytesReader`-equivalent, or any output-size cap anywhere in the runner, and a repo-wide search confirms no such bounding primitive exists in git-sync's own code (only in vendored, unrelated dependencies). This function is invoked for operations that directly execute against attacker/remote-influenced content, most importantly `fetch`, which retrieves a ref from a remote whose content and metadata are attacker-controlled when git-sync targets (or is redirected to, e.g. via `--repo` override or a compromised upstream) a malicious repository: [2](#0-1) 

`git fetch` is run with `--verbose`, and git's fetch/verbose output size (as well as error/warning text emitted to stderr, e.g. ref name lists, conflicting-ref warnings, or object-count/negotiation diagnostics) scales with content the remote determines — number of refs, branch/tag names, and error conditions the attacker's git server chooses to report. All of that text is fully buffered in memory before `runWithStdin` returns, with no bound: [3](#0-2) 

A second, independent instance of the same bug class exists in the webhook hook, which reads an entire HTTP response body via `io.ReadAll` with no `http.MaxBytesReader` or streaming size limit, even though the response comes from a URL that is typically configured by the operator but whose backend behavior is not otherwise bounded by git-sync: [4](#0-3) 

This mirrors the root cause of CVE-2024-38359: parsing/handling of externally-supplied data without an upper bound on the amount of memory allocated to hold it, enabling a remote party to force excessive allocation in the victim process.

### Impact Explanation
An attacker who controls the upstream git remote (or can redirect git-sync's fetch target, e.g. through configuration injection or a supply-chain compromise of the configured `--repo` URL) can cause the git-sync sidecar to allocate unbounded memory while capturing `git fetch` output, leading to memory exhaustion / OOM-kill of the sidecar container. Because git-sync runs as a long-lived sync loop and the sync loop is the sole mechanism keeping the published symlink content fresh, an OOM-driven crash-loop constitutes persistent sync denial for the consuming application, matching the "persistent sync denial" impact class called out in scope.

### Likelihood Explanation
Likelihood depends on an attacker's ability to control or substitute the remote git server that git-sync is configured to fetch from — this is a realistic condition for git-sync's core threat model (it is designed to sync from a remote repo that is, by definition, less trusted than the local root/environment). No special flags are required beyond the default `fetch` invocation already used by the sync loop; the `--verbose --no-progress` flags are already fixed in the code path. The bound to trigger this is however constrained by how much output `git` itself is willing to produce for a given ref/error condition, so it is somewhat weaker than the original lnd onion-bomb (which allowed a single small packet to trigger gigabytes of allocation); here the attacker-controlled server needs to actually emit large volumes of text (e.g., via extremely long ref names, huge numbers of refs, or verbose diagnostic spam), which is achievable but requires a cooperating/malicious git server rather than a single crafted message.

### Recommendation
Wrap `cmd.Stdout`/`cmd.Stderr` in `pkg/cmd/cmd.go`'s `runWithStdin` with a bounded writer (e.g., an `io.Writer` that stops accepting bytes after a configurable cap, or use `io.LimitReader`/a bounded ring buffer) so that git subprocess output capture cannot grow unbounded regardless of what the remote returns. Similarly, wrap `resp.Body` in `pkg/hook/webhook.go`'s `Do` with `io.LimitReader(resp.Body, maxWebhookBodyBytes)` before calling `io.ReadAll`.

### Proof of Concept
1. Configure git-sync with `--repo` pointing at an attacker-controlled git server (or compromise/redirect an existing remote).
2. Have the malicious server respond to the `git fetch <repo> <ref> --verbose --no-progress --prune --no-auto-gc` invocation with an extremely large amount of protocol-level diagnostic/error text (e.g., via a very large number of refs advertised, oversized ref names, or crafted error responses that `git` relays to stdout/stderr).
3. `runWithStdin` in `pkg/cmd/cmd.go` accumulates all of this into `outbuf`/`errbuf` (`bytes.NewBuffer(nil)`) with no size limit, causing the git-sync process' memory usage to grow proportionally to the attacker-supplied output volume, eventually resulting in OOM and denial of the sync loop.

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
}

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}
