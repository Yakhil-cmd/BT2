### Title
Unscoped `Commit.where(sha:)` lookup lets any status webhook mutate every stack sharing that SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes an incoming GitHub `status` webhook to **every** `Commit` record matching the payload's `sha`, with no scoping to the repository/stack that actually emitted the webhook. Because a Git SHA is a content hash shared across forks/mirrors, an attacker who can get any single repo integrated with the Shipit instance to fire a webhook (owning a fork, or a repo under an org already connected) can inject a status for a SHA that also exists in a victim stack, rewriting that victim commit's required-context status and its `deployable?`/merge eligibility.

### Finding Description
The broken binding: the code assumes `commit.stack == webhook.originating_repository`, but the actual invariant enforced is only `commit.sha == payload.sha` — repository/stack identity is never checked.

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`WebhooksController#verify_signature` only authenticates that the payload was signed with the secret belonging to `repository_owner` (an organization-level GitHub App/webhook secret), via `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`: [2](#0-1) 

This check proves the request came from *some* repository under that organization/app installation — it does not prove the SHA in the payload belongs to a commit tracked by that repository's stack. Since SHA-1 is a pure function of commit content (tree, parents, author/committer, message, timestamps), the exact same SHA can legitimately exist in multiple repositories (a fork of a public repo shares the identical commit objects with the upstream repo). An attacker who owns/controls any repository already connected to Shipit's GitHub App (e.g. a fork of the victim's repo, or another repo in an org where the app is installed) can:
1. Ensure a commit with the target SHA exists in their own repo (trivially true if it's a fork containing the victim's commit).
2. Trigger a real, validly-signed `status` webhook from their repo (e.g. by setting a commit status via the GitHub API on their own repo, or via their own CI configuration) with `context: continuous-integration/travis-ci`, `state: failure` for that SHA.
3. Shipit's `verify_signature` passes because the signature is valid for the attacker's own repo/org.
4. `StatusHandler#process` then finds **all** `Commit` rows with that SHA across all stacks — including the victim's — and calls `commit.create_status_from_github!(params)` on each one [3](#0-2) , writing a new `Status` row for the victim's stack.

This changed status feeds `Commit#deployable?`, which depends on `success?` (delegated to `status`) and `blocked?` (which checks `stack.blocking_statuses`): [4](#0-3) 

If `continuous-integration/travis-ci` is a required/blocking context for the victim stack, the forged `failure` state flips `deployable?` to false (or, in reverse, a forged `success` could make a commit falsely deployable/mergeable), directly manipulating merge/deploy eligibility for a repository that never authenticated the request.

None of the existing guards catch this: `verify_signature` authenticates the org/app, not the specific repo-to-SHA binding; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema in `StatusHandler` only validates payload shape (`sha`, `state`, `context`, etc.), not ownership; there is no `stack_id`/`repository` filter anywhere in `StatusHandler#process` or `Commit.where`.

### Impact Explanation
A payload authenticated for one repository writes state (a `Status` row) into another repository's commit/stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The immediate effect is corruption of the victim's `Status` group and `Commit#deployable?`, which gates auto-deploys (`schedule_continuous_delivery`) and merge queue processing (`ProcessMergeRequestsJob`, enqueued from `add_status` transitions per `test/models/commits_test.rb`). This is repeatable against any stack that happens to share a commit SHA with a repository the attacker can trigger events from (most easily: any fork of the victim's public repo), and can be used to block legitimate deploys/merges (DoS via forged `failure`) or, more seriously, to force a commit to appear `success`/deployable when it should not be, undermining CI-gated merge/deploy decisions cross-tenant.

### Likelihood Explanation
Preconditions: Shipit's GitHub App/webhook integration must be enabled for at least one repository the attacker controls (a fork of the victim's public repo, trivially obtainable on GitHub since forks share commit objects with upstream), and the victim stack must require the spoofed context (`ci.require` containing `continuous-integration/travis-ci`) or otherwise treat it as blocking. No Shipit secrets, sessions, or GitHub App keys are needed — the attacker relies on genuinely valid webhooks from their own repo. This is realistic and repeatable: fork sharing means colliding SHAs occur naturally for any commit that hasn't been rewritten, and the attacker can pick any upstream commit (e.g. one currently pending review/merge) to target.

### Recommendation
Scope the status update to the stack/repository that authenticated the webhook. `StatusHandler#process` should resolve the target repository from the webhook payload (`params.repository` / `repository_owner`+`name`) and filter `Commit` by the matching `stack_id`(s) for that repository, e.g. `Commit.where(sha: params.sha, stack_id: Stack.where(repository: repo).select(:id))`, instead of an unscoped `sha`-only lookup. Apply the same repository-binding fix to any other handler that resolves records purely by `sha` without checking `stack`/`repository` ownership (e.g. `check_suite`/check-run handling paths, if they share this pattern).

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status for a SHA shared across stacks only affects the authenticating repository" do
  shared_sha = 'deadbeef' * 5

  victim_stack = shipit_stacks(:shipit) # configured with ci.require including 'continuous-integration/travis-ci'
  attacker_stack = shipit_stacks(:cyclimse) # different repository

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)

  assert_predicate victim_commit.reload, :deployable? # baseline: BEFORE == equality holds (victim commit unaffected by attacker repo)

  # Attacker's repo emits a validly-signed status webhook (simulating verify_signature passing for attacker's org/app)
  params = ExplicitParameters::Params.new(sha: shared_sha, state: 'failure', context: 'continuous-integration/travis-ci')
  Shipit::Webhooks::Handlers::StatusHandler.new(attacker_repo_payload_context, params).process

  # Assert the binding is now broken: victim commit mutated by a payload the victim repo never sent
  assert_not victim_commit.reload.deployable?
  assert_equal 'failure', victim_commit.status.state
end
```
This demonstrates that `commit.sha == payload.sha` is treated as sufficient authorization, while the intended invariant `commit.stack.repository == authenticating_repository` is never checked, allowing cross-repository status/deployability manipulation.
