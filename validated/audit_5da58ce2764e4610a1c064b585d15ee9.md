### Title
Cross-repository status forgery bypasses `ci.blocking` gate - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit purely by SHA (`Commit.where(sha: params.sha)`) with no repository scoping, unlike every other webhook handler (e.g. `PushHandler`, `PullRequest::OpenedHandler`) which resolve their scope via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any records. A webhook whose signature is verified against organization A can therefore write a `Status` onto a `Commit` belonging to a completely unrelated stack/repository B, as long as the `sha` value collides with a commit id in B's table.

### Finding Description
The broken binding: the question states the intended invariant should be `organization authenticating the webhook == organization owning the blocking_statuses configuration being satisfied`. Tracing the code shows this is **not enforced at all** for the `status` event.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the payload's `repository.owner.login` (attacker-controlled field, used to select which org's `webhook_secret` to check against) matches the HMAC signature. This proves the payload was signed by *some* org's secret — but that org's identity is taken from the payload itself, not cross-checked against anything downstream.
- `Shipit::Webhooks::Handlers::Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) is the standard mechanism other handlers use to scope operations to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does **not** use `stacks`/`repository_name` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is a global, unscoped lookup across every stack/repository in the Shipit instance.
- `Commit#create_status_from_github!` → `add_status` → `Status.replicate_from_github!` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) then creates the `Status` on whatever commit was matched, using `stack_id` derived from the matched commit's own `stack`, not from the org that authenticated the request.
- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) and `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) then evaluate purely from that commit's stack state, so once the forged success `Status` lands with the correct `blocking?`-satisfying context, `blocked?` flips from `true` to `false` for all later commits in that stack, and `deployable?`/`schedule_continuous_delivery`/`Stack#trigger_continuous_delivery` can proceed.

**Attacker's exact request**: An attacker who owns Repo A (in org "attacker-org", correctly configured in Shipit with its own `webhook_secret`) triggers or crafts a `status` event on Repo A (e.g. by using their own repo's API/CI to post a commit status) whose `sha` field is set to the SHA of the blocking commit in victim Repo B's stack, and whose `context`/`state` matches Repo B's `ci.blocking` requirement (e.g. `context: 'soc/compliance', state: 'success'`). GitHub signs this webhook with attacker-org's real secret and delivers it to the shared Shipit `/webhooks` endpoint (single endpoint for all configured orgs). `verify_signature` succeeds because it only checks attacker-org's secret against attacker-org's own payload — a fully legitimate, self-consistent signature. `StatusHandler#process` then ignores `repository.full_name` entirely and updates any `Commit` row anywhere in the database whose `sha` equals the attacker-chosen value, including one that belongs to Repo B's stack (SHA collision across repos is trivially achievable if forks/shared history exist, or if the attacker can otherwise learn/guess a target SHA — SHAs are not secrets, they are visible in Shipit's own UI/API for any repository).

Existing guards fail because: `verify_signature` authenticates "the org that signed this payload," not "the org that owns the resource being mutated"; `drop_unhandled_event` doesn't inspect payload contents; there is no `ExplicitParameters` validation tying `repository.full_name` to the mutated commit for the `status` event (the params schema for `StatusHandler` doesn't even require `repository`); and `Commit#blocked?`/`#deployable?` have no cross-check against which org submitted the underlying `Status`.

### Impact Explanation
An attacker who controls only their own repository/org (Repo A, org A) can create/mutate a `Status` record attached to a `Commit` in an entirely different tenant's stack (Repo B, org B), bypassing the `ci.blocking` safety gate that is supposed to prevent commits from being considered deployable until a specific status context succeeds. This satisfies the "Critical" category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy". The blast radius is instance-wide: any repository/organization configured in the same Shipit deployment is a potential victim, since the lookup is global across all `Commit` rows regardless of stack or repository. This is repeatable per target SHA and does not require any Shipit credentials, session, or API token — only ownership of one repository already onboarded to Shipit with legitimate webhook delivery.

### Likelihood Explanation
Preconditions: attacker owns/controls a repository already registered with the Shipit instance (or any org with a working webhook secret relationship to Shipit — which is a low bar, since Shipit is often used company/org-wide with many teams having their own repos), and the target stack B has `ci.blocking` configured with a commit currently blocked. The only nontrivial requirement is causing the `sha` in the forged payload to match a real commit id in B's table — trivial if repos share history (forks, monorepo mirrors, vendored branches) or if the SHA is otherwise discoverable (Shipit exposes commit SHAs in its stack UI/API). Attacker cost is low: no secrets needed, just control of one legitimate repo's ability to emit a `status` webhook with an arbitrary `sha`/`context`/`state` (via GitHub's status API on their own repo, which does not require the sha to be reachable from their repo's history in all GitHub configurations). Fully repeatable against any exposed stack.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through `stacks` (as `PushHandler` and the `PullRequest` handlers do), e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
and add `requires :repository do requires :full_name, String end` to the `params` schema so `repository_name` is guaranteed present, matching the pattern used by other handlers.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, minitest, no live GitHub)
test "status webhook from one repository must not mutate a commit belonging to another repository's stack" do
  soc_second = shipit_commits(:soc_second) # belongs to repo B's stack, blocking commit
  soc_third  = shipit_commits(:soc_third)  # later commit in repo B's stack, currently blocked

  assert soc_third.blocked?
  refute soc_third.deployable?

  # Forge a status payload whose repository.full_name is Repo A (NOT soc_second's stack's repo),
  # but whose sha targets soc_second (repo B's blocking commit).
  payload = {
    'sha' => soc_second.sha,
    'state' => 'success',
    'context' => 'soc/compliance', # matches repo B's ci.blocking context
    'repository' => { 'full_name' => 'attacker-org/repo-a', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  soc_third.reload
  refute soc_third.blocked?, "commit must remain blocked: payload only authenticated for attacker-org, not repo B's org"
  refute soc_third.deployable?
end
```
Given the current implementation (`Commit.where(sha: params.sha)` with no repo scoping), this assertion **fails** — `soc_third.blocked?` flips to `false` and `deployable?` to `true` after processing the cross-repository payload, confirming the vulnerability. After applying the recommended fix (scoping via `stacks`), the assertion passes because the payload's `repository.full_name` ("attacker-org/repo-a") does not resolve to Repo B's stack, so `soc_second`'s status is never touched.
