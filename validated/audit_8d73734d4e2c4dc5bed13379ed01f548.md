### Title
Unbounded relay-chain trie proof size with fixed benchmark weight in `remote_proxy` / `do_remote_proxy` - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, block }` places no explicit bound on the number/size of trie nodes, yet the `#[pallet::weight]` for `remote_proxy` and `remote_proxy_with_registered_proof` only charges a fixed benchmarked `WeightInfoOf::<T,I>::remote_proxy()` value plus the inner call's `di.call_weight`, with no scaling term for `proof.len()` or byte-size before `sp_trie::read_trie_value` is executed on it.

### Finding Description
`Pallet::remote_proxy` accepts `proof: RemoteProxyProof<...>` directly from an unprivileged signed extrinsic [1](#0-0) . The weight annotation for this call is computed purely from the constant benchmark result and the inner `call`'s declared weight — it never inspects or bounds `proof` [2](#0-1) . Inside `do_remote_proxy`, the caller-supplied `proof: Vec<Vec<u8>>` is fed directly into `sp_trie::StorageProof::new(proof).into_memory_db(...)` and then `sp_trie::read_trie_value` [3](#0-2) . The `RemoteProxyProof` enum itself carries no `MaxEncodedLen`/`BoundedVec` restriction on the number of proof nodes or their sizes [4](#0-3) .

`read_trie_value` walks/validates the supplied proof nodes against the memory DB and root; its CPU/PoV cost scales with the number and size of nodes actually provided (attacker-supplied), not with the benchmark's proof (which was generated by `create_remote_proxy_proof` for a "typical" honest proof) [5](#0-4) . Because the weight charged is a fixed constant unrelated to `proof`'s actual size, a caller can pass a `proof` with as many/large `Vec<u8>` node blobs as fit inside the extrinsic length limit, all of which will be hashed/processed by `read_trie_value` before ultimately failing to resolve the real key and returning `Error::InvalidProof`. No check in the pallet (no explicit proof-length/size limit, no early-reject on oversized proof) stops this from happening — the only gating checks (`UnknownProofAnchorBlock`, i.e., checking the anchor block exists in `BlockToRoot`) happen before the trie read, but do not limit the number/size of nodes in `proof` itself, and `read_trie_value` itself has no early-exit relative to `proof` size beyond normal trie traversal cost.

The impact is bounded, however, by the runtime's outer extrinsic-length limits (`frame_system::Config::BlockLength`/`BlockWeights` extrinsic length caps and the transaction length fee), which cap how large `proof` can be per single extrinsic; this materially limits — but does not eliminate — the per-extrinsic PoV/CPU cost skew, since even within that length cap the number of small-but-many trie nodes processed by `read_trie_value` is not reflected in the charged weight at all.

### Impact Explanation
If actual `read_trie_value` execution time for a maximal-size garbage `proof` significantly exceeds the fixed weight charged (`WeightInfoOf::<T,I>::remote_proxy()`), an attacker can submit multiple such extrinsics per block, each under-charged relative to real CPU/PoV cost, causing block authoring to spend disproportionate time processing trie traversal relative to the weight meter's accounting. This could degrade block-production timing for the parachain (a DoS/liveness-adjacent issue) even though the extrinsic itself ultimately reverts with `Error::InvalidProof` and the caller pays only the (mis-priced) fixed fee.

### Likelihood Explanation
Feasibility depends on unverified real-world benchmarking data: whether `sp_trie::read_trie_value`'s cost for a maximal-length garbage `Vec<Vec<u8>>` (bounded by the runtime's max extrinsic length) meaningfully exceeds the benchmarked weight, and whether the outer extrinsic length limit already keeps this difference within tolerable bounds. I could not verify the concrete `BlockLength`/max extrinsic length values or run actual weight-vs-execution-time benchmarks in this environment, so I cannot conclusively confirm the magnitude of the discrepancy or that it is severe enough to threaten block-authoring slot budgets network-wide.

### Recommendation
Not applicable without confirmed benchmarking data — investigate empirically whether the weight charged for `remote_proxy`/`remote_proxy_with_registered_proof` is under-priced relative to worst-case `proof` size within the extrinsic length limit; if so, add a proof-size-dependent weight term (e.g., scale with `proof.iter().map(|n| n.len()).sum()`) or enforce an explicit maximum node count/size bound on `RemoteProxyProof::RelayChain.proof` before decoding/trie-reading.

### Proof of Concept
Benchmark test plan (not executed here): construct a `RemoteProxyProof::RelayChain { proof, block }` where `proof` is filled with the maximum number/size of garbage `Vec<u8>` blobs that still fit within the runtime's max extrinsic length; register a valid `block`/`storage_root` pair via `BlockToRoot`; call `do_remote_proxy` directly in a benchmark harness and measure wall-clock time of `sp_trie::read_trie_value`; compare against `WeightInfoOf::<T,I>::remote_proxy()`. Assert whether measured execution time exceeds the weight-implied time budget by a material margin — this is the empirical evidence needed to confirm or refute the underlying claim, which I was unable to run in this session.
