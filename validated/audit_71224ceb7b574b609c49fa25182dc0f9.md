### Title
Persistent Sync Denial from Premature `appTokenExpiry` Update Before Credential Store Succeeds - (File: main.go)

### Summary
`RefreshGitHubAppToken` updates the `repoSync.appTokenExpiry` field to reflect the *newly fetched* token's expiry **before** the corresponding credential is durably persisted via `git.StoreCredentials`. If the credential-store step fails after the token has been minted, the in-memory expiry has already advanced, so the next sync loop's staleness check thinks the credential is fresh and skips refreshing it—reproducing the same class of bug as the reported issue: a piece of state (`rewardPerTokenStored`/`appTokenExpiry`) is updated to reflect a not-yet-fully-applied change, and later consumers rely on that stale-but-optimistic state instead of the true persisted state.

### Finding Description
In the GitHub App auth flow, `refreshCreds` decides whether to mint a new installation token purely by comparing `git.appTokenExpiry` to `time.Now().Add(30 * time.Second)`: [1](#0-0) 

`RefreshGitHubAppToken` is the function responsible both for minting the token and for updating `appTokenExpiry`. Critically, it writes the new expiry to `git.appTokenExpiry` *before* it verifies that `StoreCredentials` (which runs `git credential approve` to actually persist the token so `git fetch` can use it) succeeds: [2](#0-1) 

If `StoreCredentials` returns an error (e.g. transient I/O error, disk pressure, or the surrounding `ctx` from `SyncRepo`'s `--sync-timeout` expiring mid-call via `RunWithStdin`), `RefreshGitHubAppToken` returns an error and `SyncRepo`/`refreshCreds` correctly propagate the failure for *that* sync attempt. However, `git.appTokenExpiry` has already been permanently mutated to the newly-fetched token's future expiry timestamp (`tokenResponse.ExpiresAt`, typically ~1 hour out) even though the actual git credential store still has the old (soon-to-expire or already-expired) token. This is analogous to the `_updateReward` bug: `rewardPerTokenPaid` (a "we processed this" marker) is written before `state.rewards = earned(account)` (the actual value that depends on the pre-update state) is computed, letting later reads see an inconsistent world. Here `appTokenExpiry` (a "we refreshed this" marker) is written before `StoreCredentials` (the action that makes the refresh actually effective) completes.

On the next sync loop iteration, `refreshCreds` evaluates `git.appTokenExpiry.Before(time.Now().Add(30 * time.Second))` and now finds it false, so it will *not* attempt `RefreshGitHubAppToken` again — permanently, until process restart — because the field was already advanced by the failed attempt. Meanwhile the actual stored git credential is stale/expired, so subsequent `git fetch` calls will start failing with authentication errors, and there is no code path to re-trigger the refresh since the guarding condition is now permanently false.

### Impact Explanation
This causes a persistent sync denial: once a single `StoreCredentials` call fails during GitHub App token refresh, the repoSync instance will never again attempt to refresh the token (the freshness check is fooled by the already-advanced `appTokenExpiry`), while the git credential helper still holds the old/expiring token. All subsequent fetches will fail with authentication errors until git-sync is restarted, which for a long-running sidecar (its primary deployment mode) means it silently stops syncing new content indefinitely while consumers keep seeing stale data at `--link`.

### Likelihood Explanation
This does not require a malicious operator, leaked key, or any adversarial repo content — it is reachable through ordinary operational conditions: a transient failure in `git credential approve` (disk pressure, filesystem errors, or the request being cut short by `--sync-timeout` since `RunWithStdin`/`StoreCredentials` shares the same per-sync `ctx` as the rest of `SyncRepo`) is sufficient to trigger it, and GitHub App auth is a documented, supported configuration.

### Recommendation
Only update `git.appTokenExpiry` after `StoreCredentials` has succeeded, e.g.:
```go
if err := git.StoreCredentials(ctx, git.repo, username, password); err != nil {
    return err
}
git.appTokenExpiry = tokenResponse.ExpiresAt
return nil
```
This mirrors the recommended fix in the reported bug (update the paid/stored marker only after the dependent state has actually been applied), ensuring the freshness check is only satisfied once the credential is truly usable.

### Proof of Concept
1. Configure git-sync with `--github-app-*` flags.
2. Inject a failure into `StoreCredentials` on the first refresh (e.g. simulate `git credential approve` failing, or set `--sync-timeout` low enough that the context deadline fires between the HTTP token fetch and the `git credential approve` call).
3. Observe `RefreshGitHubAppToken` returns an error, but `git.appTokenExpiry` is already set to the new token's expiry (~1 hour from now).
4. On the next sync loop iteration, observe `refreshCreds`'s check at [3](#0-2)  evaluates false, so no refresh is attempted, and `git fetch` subsequently fails with authentication errors on every following sync attempt until the process is restarted.
