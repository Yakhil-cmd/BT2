### Title
`PATH` env-var override via pull-request label name lets a fork PR redirect binary resolution for `tasks.<name>.steps` - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased, value `"true"`) into the stack env with no key allowlist, and `LabelCapturingHandler#capture_labels` persists these labels straight from an unauthenticated PR webhook payload. `TaskCommands#env` folds `@stack.env` into the env passed to `Command.new`, and `Command#unbundled_env` merges `@env` (task/step env) *after* the safe `Shipit.shell_paths`-based `PATH`, so a label literally named `path` clobbers `PATH` with the fixed string `"true"` for every step run for that review stack's tasks.

### Finding Description
The broken binding is: `Command#unbundled_env` should guarantee `PATH == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for every spawned step, but instead `PATH == @env['PATH']` whenever the merged task/stack env contains a `PATH` key, because [1](#0-0) 
merges the safe path first and the caller-supplied `@env` last, letting `@env` override it unconditionally.

The path to attacker control: `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` from the raw webhook body onto `PullRequest#labels` with no filtering [2](#0-1) 
and `ReviewStack#env` merges `labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into the stack env with no key allowlist [3](#0-2) 
`TaskCommands#env` then merges `@stack.env` into the env ultimately handed to `Command.new(command_line, env:, chdir: steps_directory)` for every `steps`/`dependencies_steps` command [4](#0-3) 
Because `deploy_spec.machine_env` and `@task.env` are merged after `@stack.env` (line 46-47), the label-derived `PATH` survives unless the deploy spec or task env itself defines a `PATH` key, which they normally do not.

The attacker's exact request: open (or already have) a fork pull request against a repo whose `provisioning_behavior` is `prevent_with_label`, and add a label named `path` (any case; GitHub lets any repo collaborator/owner define/apply labels on their own fork's PR before or via API). No Shipit session, token, or secret is required — the label is captured via the `pull_request` webhook, whose signature check (`GitHubApp#verify_webhook_signature`) only authenticates that GitHub sent it, not that the label content is safe.

Exploit flow: attacker's fork branch is checked out into `@task.working_directory` (the review-stack's working tree, entirely attacker-controlled content); attacker also commits an executable file at a relative path such as `true/<bare-command-name>` matching whatever bare command name is invoked in a `tasks.<name>.steps` entry in `shipit.yml` (e.g. `bundle`, `make`, or a custom step). When the task runs, `PATH` is now the literal string `"true"` instead of the real system paths, so the shell resolving that bare command searches the relative directory `./true` under `chdir` (which is inside the attacker's checked-out working directory) and executes the attacker's binary instead of the intended system binary.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only checks the webhook came from GitHub for a real event, not that label names are safe; `ExplicitParameters` on `LabelCapturingHandler` only validates types (`String`) for `labels[].name`, not content; there is no `EnvironmentVariables#permit`-style allowlist applied at `ReviewStack#env` or `Command#unbundled_env` to prevent a `PATH` (or other sensitive) key from being injected/overridden by attacker-controlled label data.

### Impact Explanation
This is a Critical finding: it allows arbitrary code execution on the Shipit deploy host as the deploy user, matching the "RCE on the deploy host via `Command`/`PTY.spawn`" category. Any fork PR author who can control `provisioning_behavior=prevent_with_label` review-stack labels and their own PR branch content can hijack binary resolution for that stack's task steps, running attacker-supplied binaries with the deploy host's privileges (potentially exfiltrating `GITHUB_TOKEN`, deploy secrets, or pivoting further). The blast radius is scoped to the given review stack/repository (each `ReviewStack` runs its own tasks against its own checked-out working directory), but is repeatable on any repo using `prevent_with_label` provisioning by any unprivileged fork contributor able to open/label PRs.

### Likelihood Explanation
Preconditions: the target repository must use `provisioning_behavior: prevent_with_label` (a documented, non-default option) so its review stack/task pipeline is reachable through PR labels; the attacker needs only permission to open a PR from their own fork and label it — no maintainer approval, no Shipit credentials. Feasibility is moderate: the attacker must know (or guess) a bare command name used in the target's `shipit.yml` `tasks.<name>.steps`/`dependencies_steps`, and must be able to place an executable at the correct relative path under the task's `chdir`; both are visible/controllable to a fork owner who can read the target's committed `shipit.yml`. The exploit is fully repeatable — the attacker can relabel/re-push and retrigger the run at will.

### Recommendation
Do not let arbitrary pull-request label names become raw environment variable keys: prefix them (e.g. `SHIPIT_LABEL_<NAME>`) or maintain an explicit allowlist of permitted label-derived keys in `ReviewStack#env`. Independently, harden `Command#unbundled_env` so that reserved/security-sensitive keys such as `PATH` (and similarly `BUNDLE_*`, `RUBYOPT`, `LD_PRELOAD`, etc.) cannot be overridden by caller-supplied `env`, e.g. compute `PATH` last and unconditionally, or reject any external env hash entry named `PATH`.

### Proof of Concept
minitest test plan (`test/lib/shipit/command_test.rb` style, no live GitHub needed):
1. Build a `Shipit::ReviewStack` fixture with an associated `pull_request` whose `labels` includes `"path"`.
2. Assert `review_stack.env["PATH"] == "true"` (label→env binding).
3. Build a `Shipit::TaskCommands` for a task on that stack and assert `task_commands.env["PATH"] == "true"` (propagation through stack env merge).
4. Instantiate `Shipit::Command.new("some_command", env: task_commands.env, chdir: some_dir)` and assert `command.unbundled_env["PATH"] == "true"`, i.e. it differs from the expected safe value `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`.
5. Optionally spawn a fake `chdir/true/some_command` executable and confirm (via `Command#run`) that it executes instead of the real system binary, proving redirected binary resolution.
