### Title
Bridge Value Transfer Queue Permanently Frozen by Reverting KLAY Recipient or Blacklisted ERC20 Recipient — (`node/sc/bridge_manager.go`, `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge processes cross-chain value transfer requests through a sequential nonce-ordered queue in `BridgeInfo.processingPendingRequestEvents()`. When any single event fails, the entire queue halts and retries that same event indefinitely. Because the asset-delivery call (`_to.call.value(_value)("")` for KLAY, `safeTransfer` for ERC20) is placed **after** all state-advancing operations inside the Solidity `handleKLAYTransfer`/`handleERC20Transfer` functions, a recipient address that permanently reverts on receipt causes the Go-level gas estimation to fail, which propagates as an error that re-queues the failing event at the front. All subsequent bridge transfers — belonging to other users — are permanently blocked until operator manual intervention.

---

### Finding Description

**Queue processing loop** (`node/sc/bridge_manager.go`):

```go
func (bi *BridgeInfo) processingPendingRequestEvents() {
    ReadyEvent := bi.GetReadyRequestValueTransferEvents()
    ...
    for idx, ev := range ReadyEvent {
        if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
            continue
        }
        if err := bi.handleRequestValueTransferEvent(ev); err != nil {
            bi.AddRequestValueTransferEvents(ReadyEvent[idx:])   // re-queues stuck event
            return                                                // stops processing
        }
    }
}
``` [1](#0-0) 

This loop is called every second from `bi.loop()`: [2](#0-1) 

**KLAY delivery in Solidity** (`BridgeTransferKLAY.sol`):

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");   // ← reverts entire tx if _to reverts
``` [3](#0-2) 

The KLAY transfer to `_to` happens **after** all nonce-advancing state writes. If `_to` is a contract that reverts on receiving KLAY, the `require` causes the entire transaction to revert, rolling back all state changes. The Go binding's `HandleKLAYTransfer` call performs gas estimation (which simulates the transaction) before submitting; the simulation fails and returns an error to `handleRequestValueTransferEvent`.

**ERC20 delivery** (`BridgeTransferERC20.sol`) has the identical structure:

```solidity
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);
IERC20(_tokenAddress).safeTransfer(_to, _value);   // ← reverts if _to is blacklisted
``` [4](#0-3) 

**Skip guard is ineffective for stuck events.** The only skip condition is:

```go
if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
    continue
}
``` [5](#0-4) 

`lowerHandleNonce` advances only when `_updateHandleNonce` succeeds on-chain, which never happens for the stuck event. `handledEvent` is populated only by `MarkHandledNonce`, called from `ProcessHandleEvent` upon observing a successful on-chain `HandleValueTransfer` event — which also never fires. So the stuck event is never skipped.

**Recovery mechanism does not help.** `valueTransferRecovery.recoverPendingEvents()` simply re-adds the same unhandled events back into the queue via `AddRequestValueTransferEvents`, which will again fail at the same point. [6](#0-5) 

---

### Impact Explanation

Any user who initiates a KLAY bridge transfer specifying `_to` as a contract that reverts on receiving KLAY (or, for ERC20 bridges using lock/unlock mode, gets the destination address blacklisted by the token after initiating the transfer) causes the bridge operator's entire pending-event queue to freeze. All other users' cross-chain transfers — regardless of token type or nonce — are permanently blocked. Bridged assets locked in the source-chain bridge contract cannot be released on the destination chain until an operator manually intervenes (e.g., by restarting with a patched binary or manually advancing `lowerHandleNonce` via a privileged contract call).

This matches the allowed impact: **persistent disruption of bridged-asset transfers** and **bridge state corruption** (the `lowerHandleNonce` / `handleNonce` accounting diverges from the true processed state).

---

### Likelihood Explanation

- **KLAY path**: Any user can call `requestKLAYTransfer(_to, ...)` on the source bridge with `_to` set to a contract they control that has a reverting fallback. This is a single, permissionless transaction.
- **ERC20 path**: Requires the destination token to support blacklisting (e.g., USDC, USDT). The attacker initiates a transfer, then gets `_to` blacklisted before the operator processes it.
- No special privileges are required. The attacker only needs to be a normal bridge user.

---

### Recommendation

1. **Decouple asset delivery from nonce advancement.** Move the `_to.call.value(_value)("")` and `safeTransfer` calls to a separate, skippable step, or credit the recipient a withdrawable balance instead of pushing assets directly (pull-over-push pattern).

2. **Add a skip-and-continue mechanism in the Go queue.** When `handleRequestValueTransferEvent` returns a permanent error (e.g., gas estimation failure), log the event, mark it as undeliverable, and advance past it rather than re-queuing it at the front. A separate "failed transfers" list can be maintained for operator review.

3. **Cap gas on the KLAY delivery call.** Use a fixed gas stipend for `_to.call.value(_value)("")` so a reverting recipient cannot cause unbounded failure.

---

### Proof of Concept

1. Deploy a contract `Rejecter` on the destination chain with a reverting fallback:
   ```solidity
   contract Rejecter { receive() external payable { revert("no KLAY"); } }
   ```

2. On the source chain, call:
   ```solidity
   bridge.requestKLAYTransfer(address(rejecter), value, extraData);
   ```
   This emits a `RequestValueTransfer` event with `requestNonce = N`.

3. The bridge operator's Go node picks up the event, adds it to `pendingRequestEvent`, and calls `processingPendingRequestEvents()`.

4. `handleRequestValueTransferEvent` calls `bi.bridge.HandleKLAYTransfer(auth, txHash, from, rejecter, value, N, blkNum, extraData)`. The Go binding estimates gas, which simulates the transaction. The simulation reaches `_to.call.value(_value)("")` → `Rejecter.receive()` → revert → `require(ok, ...)` fails → gas estimation returns error.

5. `handleRequestValueTransferEvent` returns the error. `processingPendingRequestEvents` calls `bi.AddRequestValueTransferEvents(ReadyEvent[idx:])`, re-queuing event `N` and all events after it, then returns.

6. One second later, the loop retries. Step 4–5 repeat indefinitely.

7. All events with nonce > N (other users' transfers) are never processed. The bridge queue is frozen. [7](#0-6) [8](#0-7)

func (bi *BridgeInfo) loop() {
	ticker := time.NewTicker(time.Second)
	defer ticker.Stop()

	logger.Info("start bridge loop", "addr", bi.address.String(), "onChildChain", bi.onChildChain)

	for {
		select {
		case <-bi.newEvent:
			bi.processingPendingRequestEvents()

		case <-ticker.C:
			bi.processingPendingRequestEvents()

		case <-bi.closed:
			logger.Info("stop bridge loop", "addr", bi.address.String(), "onChildChain", bi.onChildChain)
			return
		}
	}
}

// processingPendingRequestEvents handles pending request value transfer events of the bridge.
func (bi *BridgeInfo) processingPendingRequestEvents() {
	ReadyEvent := bi.GetReadyRequestValueTransferEvents()
	if ReadyEvent == nil {
		return
	}

	logger.Trace("Get ready request value transfer event", "len(readyEvent)", len(ReadyEvent), "len(pendingEvent)", bi.pendingRequestEvent.Len())

	for idx, ev := range ReadyEvent {
		if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
			logger.Trace("handled requests can be ignored", "RequestNonce", ev.GetRequestNonce(), "lowerHandleNonce", bi.lowerHandleNonce)
			continue
		}

		if err := bi.handleRequestValueTransferEvent(ev); err != nil {
			bi.AddRequestValueTransferEvents(ReadyEvent[idx:])
			logger.Error("Failed handle request value transfer event", "err", err, "len(RePutEvent)", len(ReadyEvent[idx:]))
			return
		}
	}

func (vtr *valueTransferRecovery) recoverPendingEvents() error {
	defer func() {
		vtr.childEvents = []IRequestValueTransferEvent{}
		vtr.parentEvents = []IRequestValueTransferEvent{}
	}()

	if len(vtr.childEvents) > 0 {
		logger.Warn("VT Recovery : Child -> Parent Chain", "cBridge", vtr.cBridgeInfo.address.String(), "events", len(vtr.childEvents))
	}

	vtRequestEventMeter.Mark(int64(len(vtr.childEvents)))
	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))
	for i, event := range vtr.childEvents {
		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))
	}

	vtHandleEventMeter.Mark(int64(len(vtr.parentEvents)))
	events = make([]IRequestValueTransferEvent, len(vtr.parentEvents))
	for i, event := range vtr.parentEvents {
		events[i] = event
	}
	vtr.cBridgeInfo.AddRequestValueTransferEvents(events)

	return nil
