### Title
Signature verification is keyed to an attacker-chosen `repository.owner.login`/`organization.login` field while the write target is keyed to a different, unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken straight from the unauthenticated request body. If that organization has no `webhook_secret` configured, `GithubApp#verify_webhook_signature` short-circuits and returns `true` for **any** payload, regardless of the actual repository the event claims to be about. The actual write target used by every webhook handler (`Handler#repository_name` / `Repository.from_github_repo_name`) is resolved from a completely independent field, `repository.full_name`. This breaks the intended binding "organization authenticated == repository written": the org used to authenticate and the repo that is actually mutated are decoupled, and can be different when Shipit is configured with more than one GitHub App/org (as explicitly supported, see `test/dummy/config/secrets_double_github_app.yml`).

### Finding Description
`verify_signature` resolves the org purely from body content: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally trusts the request when no secret is configured for that organization: [3](#0-2) 

Once the filter passes, `WebhooksController#create` dispatches the raw JSON payload to every registered handler for the event: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` from a *different* payload field, `repository.full_name`, with no cross-check against the organization used to authenticate the request: [5](#0-4) [6](#0-5) 

Because Shipit explicitly supports multiple GitHub Apps/organizations configured side by side (documented and tested via `test/dummy/config/secrets_double_github_app.yml`), an org that has no `webhook_secret` set effectively becomes a universal bypass key: an attacker can set `repository.owner.login`/`organization.login` to that org (to make `verify_webhook_signature` return `true` unconditionally) while setting `repository.full_name` to any other stack's real repository (the one whose secret is actually configured and never gets checked). The equality the engine relies on - "the org whose secret authenticated the request" == "the repository that gets written to" - does not hold: the two are read from unrelated JSON fields and there is no code path enforcing that `repository.owner.login == repository.full_name.split('/').first`.

### Impact Explanation
This is an authentication bypass on the webhook ingestion path for any stack whose owning organization is configured without a `webhook_secret` in a multi-org Shipit instance, and it lets the attacker forge events for *other, unrelated, secret-protected* repositories by simply putting the victim's `full_name` in the payload. Concretely, an unauthenticated attacker can:
- Forge `push` events (`PushHandler`) causing `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` to run against a victim stack, enqueuing `GithubSyncJob` with an attacker-controlled `expected_head_sha`, which fetches/creates commits and can trigger `ContinuousDeliveryJob`-driven automatic deploys for stacks with `continuous_deployment` enabled.
- Forge `status`/`check_suite`/`membership`/`pull_request` events for the victim repo, forging CI status, team/user membership, or pull-request metadata that other Shipit logic (deploy gating, merge automation) trusts.

This satisfies the "unauthorized deploy" / "cross-repository writes" impact bar because state belonging to a repository the attacker never authenticated for gets mutated as a side effect of a signature check keyed to a different, attacker-chosen organization.

### Likelihood Explanation
Requires only that a multi-organization Shipit deployment exist and that at least one configured organization omit `webhook_secret` (explicitly documented as optional: `docs/setup.md` "Webhook secret (optional)"). No credentials, tokens, or privileged access are needed - the attacker just POSTs to the public `/webhooks` endpoint. This is a realistic misconfiguration scenario in exactly the multi-org support the engine ships and tests (`secrets_double_github_app.yml`), not a theoretical one.

### Recommendation
Bind the identity used for signature verification to the identity of the repository actually acted upon:
- After signature verification (or in `verify_signature`), also derive the repository from `repository.full_name`, look up its `Repository`/`Stack` record, and require `repository.owner.login`/`organization.login` used for the HMAC check to match that repository's stored `owner`.
- Do not allow `verify_webhook_signature` to return `true` unconditionally for orgs without a secret; instead, either require a webhook secret when more than one org/App is configured, or reject events whose repository doesn't belong to the same org that produced a valid signature.

### Proof of Concept
1. Configure Shipit with two orgs (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgOne` (has `webhook_secret` set) hosting the victim stack `OrgOne/victim-repo`, and `OrgAttacker` configured with `webhook_secret: nil`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgOne/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
No `X-Hub-Signature` header is required to be valid.
3. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of header content.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("orgone/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")`, enqueuing `GithubSyncJob` for the real victim stack - an event the attacker was never authenticated to send.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
