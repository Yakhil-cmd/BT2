## Finding

Based on my investigation, the exploit hypothesis in the question is corroborated by the actual code, and it's arguably worse than stated: for secondary signers, `allow_missing_txn_authentication_key` performs a **global feature-flag check with no binding to the specific secondary account**, and the Rust-side VM code that actually invokes `dispatchable_authenticate` (the only place a Move-based signature is cryptographically checked for Abstract/derivable-AA authenticators) appears to run **only for the primary sender(s) and fee payer — not for secondary signers**.

### Title
Multi-agent secondary-signer authentication bypass via unbound `allow_missing_txn_authentication_key` and missing per-secondary-signer dispatch verification - (File: aptos-move/framework/aptos-framework/sources/transaction_validation.move)

### Summary
`multi_agent_common_prologue` accepts a `None` (empty) public-key hash for a secondary signer whenever `allow_missing_txn_authentication_key(secondary_address)` returns `true`. That helper checks `features::is_derivable_account_abstraction_enabled()` as a **network-wide** condition, with no verification that `secondary_address` itself is an actual DAA/dispatchable-authenticator account. Combined with the fact that `dispatchable_authenticate` (the code path that cryptographically verifies Abstract/DerivableV1 signing data) is only invoked in `aptos_vm.rs` for `transaction_data.senders()` and the fee payer — not for secondary signers whose proofs live in the separate `secondary_authentication_proofs` field — a secondary signer whose account authenticator is submitted as `Abstract`/`DerivableV1` can be admitted with an unverified/garbage signature once the DAA feature is enabled, even though that account never opted into account abstraction.

### Finding Description
- `allow_missing_txn_authentication_key` [1](#0-0)  is defined as:
```
inline fun allow_missing_txn_authentication_key(transaction_sender: address): bool {
    features::is_derivable_account_abstraction_enabled()
        || (features::is_account_abstraction_enabled() && account_abstraction::using_dispatchable_authenticator(transaction_sender))
}
```
Note that the derivable-AA branch is a *pure global feature check* — it does not consult any per-account state for `transaction_sender`. This is architecturally different from the classic-AA branch, which does check `using_dispatchable_authenticator(transaction_sender)` per account.

- `multi_agent_common_prologue` calls this helper per secondary signer whenever the secondary signer's supplied auth-key hash is `None`: [2](#0-1) . If it returns `true`, the loop simply moves on — no comparison against `account::get_authentication_key(secondary_address)` is ever performed for that signer.

- The `None` value for a secondary signer's proof is produced solely by `AuthenticationProof::optional_auth_key()` returning `None` for the `Abstract` variant [3](#0-2) , and these secondary proofs feed into the prologue call via `txn_data.secondary_authentication_proofs` [4](#0-3) .

- Critically, the actual cryptographic verification of an `Abstract`/`DerivableV1` proof (`dispatchable_authenticate`, which runs the account's registered Move authentication function against the transaction digest) is only performed for `transaction_data.senders()` (the primary signer(s)) and the fee payer in `aptos_vm.rs` [5](#0-4)  and [6](#0-5) . I found no corresponding dispatch call over `secondary_authentication_proofs` in this file, meaning a secondary signer's Abstract authenticator payload is never run through `dispatchable_authenticate` (nor through a classic signature check, since Abstract-type `AccountAuthenticator`s defer verification entirely to Move dispatch by design).

- The net effect: if the network has `is_derivable_account_abstraction_enabled()` turned on (a network-wide feature, not an account-specific opt-in), an attacker can name any existing account as a secondary signer, attach an `Abstract`/`DerivableV1` authenticator with arbitrary/garbage `auth_data`, and the multi-agent prologue will accept it as "no auth key needed" — bypassing `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY` entirely for that secondary signer, without ever validating any signature tied to that account.

### Impact Explanation
This breaks the "secondary signer" authentication guarantee described in the Admission Pivots: the actual signer set bound to the transaction no longer matches the address the transaction claims to be co-signed by. A transaction that appears to require an actual secondary co-signature/approval (e.g. for multi-agent flows used by DeFi protocols, escrow, or approval-gated entry functions) can be admitted and executed with a signer object for the secondary account materializing without any cryptographic proof of control, purely because a network-wide feature flag is on and the caller chose the `Abstract` authenticator encoding for that slot. This is a signer-binding/authentication bypass at the admission boundary.

### Likelihood Explanation
Likelihood is high on any network where `derivable_account_abstraction` is enabled (which the code base treats as a normal, expected feature state, not experimental), since the check is unconditional once that global flag is on — no attacker-controlled account setup is required (unlike classic AA, which requires `using_dispatchable_authenticator` to be true for that specific address). The only gating factor is that the abstraction dispatch for secondary signers appears to be entirely skipped in the Rust VM entry path I examined.

### Recommendation
- Scope `allow_missing_txn_authentication_key`'s derivable-AA branch to the specific account being checked (analogous to the classic-AA branch), e.g. require some account-level marker/derivation proof that `secondary_address` corresponds to the presented `DerivableV1` `abstract_public_key`/`function_info`, not just a global flag.
- Ensure `aptos_vm.rs` runs `dispatchable_authenticate` (or an equivalent verification) over every entry in `secondary_authentication_proofs` (and the fee-payer authenticator, if not already fully covered) before their `None` auth keys are allowed to satisfy `multi_agent_common_prologue`, mirroring exactly what is done for `senders` and `fee_payer`.

### Proof of Concept
1. On a network/testnet with `derivable_account_abstraction` feature enabled.
2. Construct a multi-agent (or fee-payer) transaction where the secondary signer address is a normal, pre-existing Ed25519 account that has never registered any dispatchable/derivable authenticator.
3. Encode that secondary signer's `AccountAuthenticator` as `Abstract` with `AbstractAuthenticationData::DerivableV1` and arbitrary/garbage `auth_data` (no valid signature over the transaction digest).
4. Submit the transaction via the standard BCS submission path (mempool → vm-validator → VM prologue).
5. Expected/secure behavior: `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY` (1001) should be raised because this account does not actually use dispatchable/derivable AA.
6. Observed (per the code): `multi_agent_common_prologue` calls `allow_missing_txn_authentication_key(secondary_address)`, which returns `true` purely because `is_derivable_account_abstraction_enabled()` is a global flag, so the check is skipped and the secondary signer is accepted without any real authentication — because `dispatchable_authenticate` was never invoked for that secondary proof in `aptos_vm.rs`.

**Note on confidence**: I was not able to fully trace, within available tool budget, every code path that constructs/verifies `SerializedSigners`/`secondary_authentication_proofs` beyond `aptos-move/aptos-vm/src/aptos_vm.rs:1950-2107`, so I cannot rule out an additional verification step elsewhere in the codebase that specifically dispatches secondary-signer Abstract proofs. If such a step exists, this finding's severity is reduced to "the feature-flag scoping in `allow_missing_txn_authentication_key` is architecturally inconsistent between classic-AA and derivable-AA" rather than a full bypass. I recommend a Devin session with full repository access to confirm whether `secondary_authentication_proofs` ever get routed through `dispatchable_authenticate`.
