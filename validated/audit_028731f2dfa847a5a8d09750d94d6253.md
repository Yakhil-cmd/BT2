### Title
Global `http.cookiefile` and GitHub App bearer token are sent to any host reached via submodules, including attacker-controlled foreign hosts - ([File: main.go])

### Summary
`SetupCookieFile` configures `http.cookiefile` with `git config --global`, which applies to every HTTPS connection git makes, not just the operator's `--repo` host. [1](#0-0)  When submodules are enabled and a submodule's `.gitmodules` points to a different (attacker-controlled) HTTPS host, `git submodule update` will present the same cookie file to that foreign host, because git's `http.cookiefile` config has no host restriction unless scoped with `http.<url>.cookiefile`.

### Finding Description
`SetupCookieFile` runs `git config --global http.cookiefile /etc/git-secret/cookie_file` with no URL/host qualifier. [2](#0-1)  git-sync's submodule handling in `configureWorktree` simply invokes `git submodule update --init [--recursive] [--depth N]` on the checked-out worktree, without any code that restricts submodule URLs to the same host as `--repo` or that scopes cookie/credential config per remote. [3](#0-2)  Because `.gitmodules` content and submodule URLs come from the fetched repo content (attacker-controlled per the threat model), an attacker who controls a submodule entry can point it at an arbitrary HTTPS host, and git will still attach the globally configured cookie file when fetching that submodule, since git's `http.cookiefile` is a global config value applied to all HTTP(S) transports unless narrowed with per-URL config (`http.<url>.*`), which git-sync does not use.

For GitHub App auth, the derived short-lived token is stored via `git.StoreCredentials(ctx, git.repo, username, password)`, scoped to `git.repo` (the operator's `--repo` URL) using git's native `credential.helper cache`. [4](#0-3)  Git's credential helper cache is genuinely scoped by URL/host at the git level (as demonstrated in `e2e::submodule_sync_over_http_different_passwords`, which relies on per-URL `git credential approve` and per-submodule `--credential` entries to avoid cross-host leakage). [5](#0-4)  This means the GitHub App token path is not vulnerable to cross-host leakage the same way, because git's credential subsystem only offers stored credentials for URLs matching the same protocol/host/path prefix — an attacker-controlled submodule host would not match and would not receive the token.

The cookie-file path is different: `http.cookiefile` is not credential-helper mediated and is not host-matched by git itself; it is sent for every HTTPS request unless the operator explicitly uses `http.<url>.cookiefile` scoping, which git-sync's `SetupCookieFile` does not do.

### Impact Explanation
This is a genuine secret/credential confinement violation (SECRET_CONFINEMENT): an attacker who controls repo content (a `.gitmodules` file with a foreign-host submodule URL) can cause the operator's cookie-file secret to be sent to a server they control, without needing any elevated privilege, flag, or misconfiguration beyond the documented, supported combination of `--cookie-file` + submodules enabled (which is a default-allowed, non-exotic configuration). This matches a credential/secret exfiltration impact class — the leaked cookie could grant read/write access to the operator's real, intended git host if the cookie is a generic auth cookie (e.g., a GitHub/GitLab session cookie), or otherwise disclose sensitive data.

### Likelihood Explanation
Preconditions: `--cookie-file` (or `GITSYNC_COOKIE_FILE`) enabled, submodules not disabled (`--submodules` default is `recursive`, so no non-default flag is required for this to be reachable), and attacker control of `.gitmodules`/submodule refs in the synced repo (already assumed attacker capability per the threat model). No non-default or exotic flags are required beyond the documented `--cookie-file` feature. This is fully deterministic and repeatable: every submodule fetch to a foreign host during a normal sync cycle will carry the cookie file.

### Recommendation
Scope the cookie file (and any other globally-applied secret-bearing git config) to the operator's configured `--repo` host instead of using `--global`. Concretely, use `git config --global http.<scheme>://<host>/.cookiefile <path>` (per-URL config keyed to the parsed host of `--repo`) rather than the unscoped `http.cookiefile`. If submodules are allowed to reference different hosts, either: (a) restrict submodule URLs to the same host as `--repo` by default (with an explicit opt-in flag to allow foreign-host submodules), or (b) ensure that authentication material (cookie file, bearer tokens) is only applied per-URL scope matching `--repo`'s host, mirroring the already-correct per-URL scoping used for `--credential`/`git credential approve`.

### Proof of Concept
Integration test outline (extending the existing e2e submodule/cookie infrastructure):
1. Stand up two local HTTP servers: `server-primary` (the `--repo` host) and `server-attacker` (a second host never referenced by `--repo` or `--credential`).
2. Configure `git-sync` with `--repo=http://server-primary/repo --cookie-file=true` and mount a cookie file that contains a marker cookie value for `server-primary`.
3. In the primary repo, add a submodule via `.gitmodules` pointing to `http://server-attacker/repo`.
4. Run git-sync once (`--one-time`) and capture the HTTP requests received by `server-attacker`.
5. Assert: `server-attacker` receives a `Cookie` header containing the same secret value configured for `server-primary` — proving the cookie was sent to a host the operator never configured. (Contrast: repeat with `--credential` username/password instead of `--cookie-file`, and assert `server-attacker` does NOT receive the primary repo's credentials, confirming the credential-helper path is correctly scoped while `http.cookiefile` is not.)

```go
func (git *repoSync) SetupCookieFile(ctx context.Context) error {
	git.log.V(1).Info("configuring git cookie file")

	var pathToCookieFile = "/etc/git-secret/cookie_file"

	_, err := os.Stat(pathToCookieFile)
	if err != nil {
		return fmt.Errorf("can't access git cookiefile: %w", err)
	}

	if _, _, err = git.Run(ctx, "", "config", "--global", "http.cookiefile", pathToCookieFile); err != nil {
		return fmt.Errorf("can't configure git cookiefile: %w", err)
	}

	return nil
}
```
