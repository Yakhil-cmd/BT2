### Title
KAIA Permanently Lost When Account Abstraction Wallet Users Trigger the Bridge Fallback Function — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

The `BridgeTransferKLAY` contract's fallback function unconditionally uses `msg.sender` as the recipient address (`_to`) on the counterpart chain. For account abstraction (AA) wallets (e.g., Safe/Gnosis Safe), the wallet address is determined by deployment parameters and factory address, meaning the same logical user controls **different addresses** on the source chain and the destination chain. Any KAIA sent via the fallback is irrecoverably delivered to an address the user does not control on the destination chain.

### Finding Description

The fallback function in `BridgeTransferKLAY.sol`:

```solidity
// () requests transfer KLAY to msg.sender address on relative chain.
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
```

passes `msg.sender` directly as `_to` — the recipient on the counterpart chain — with no mechanism for the caller to override it. [1](#0-0) 

`_requestKLAYTransfer` then emits a `RequestValueTransfer` event carrying that `_to` value: [2](#0-1) 

The bridge operator's Go relay picks up the event and calls `HandleKLAYTransfer` on the counterpart bridge with the same `_to`, which executes the native transfer:

```go
handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, ...)
``` [3](#0-2) 

On the counterpart bridge, the KAIA is sent unconditionally to `_to`:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [4](#0-3) 

There is no recovery path: no `rescueTokens`, no admin override, and no re-routing mechanism once the handle transaction is mined.

The explicit `requestKLAYTransfer` function does accept a caller-supplied `_to`, so users who are aware of the AA address-divergence problem can avoid it. However, the fallback — the most natural way to bridge KAIA (simply sending ETH/KAIA to the bridge contract) — provides no such escape hatch and no warning. [5](#0-4) 

### Impact Explanation

An AA wallet user who sends KAIA directly to the bridge contract triggers the fallback. The `RequestValueTransfer` event records `to = <AA address on source chain>`. The relay delivers KAIA to that same address on the destination chain, where the AA wallet is either not deployed or controlled by a different set of signers. The KAIA is permanently inaccessible to the user. The corrupted value is the exact KAIA amount transferred minus the bridge fee.

### Likelihood Explanation

- The fallback is the most intuitive interaction path (send ETH/KAIA to a bridge contract).
- Safe and other AA wallets are widely used across EVM chains, including Kaia service chains.
- No on-chain or off-chain warning exists in the contract or the bridge relay code.
- The trigger requires no privilege — any unprivileged user can hit this path.

### Recommendation

1. Remove or disable the fallback function, forcing all callers to use `requestKLAYTransfer(address _to, ...)` where the destination address is explicit.
2. If the fallback is retained for UX reasons, revert with a descriptive error message instructing callers to use `requestKLAYTransfer` with an explicit `_to`.
3. Add NatSpec documentation warning that AA wallet users must supply a different `_to` address corresponding to their wallet on the destination chain.

### Proof of Concept

1. Alice holds a Safe multisig at address `0xAA...` on the Kaia service chain. Her Safe on the Kaia mainnet is deployed at `0xBB...` (different CREATE2 salt or factory).
2. Alice sends 100 KAIA directly to the service-chain bridge contract, triggering the fallback:
   ```
   function () external payable {
       _requestKLAYTransfer(msg.sender /*= 0xAA*/, feeOfKLAY, new bytes(0));
   }
   ```
3. The `RequestValueTransfer` event is emitted with `to = 0xAA`.
4. The bridge relay calls `handleKLAYTransfer(..., _to = 0xAA, ...)` on the mainnet bridge.
5. The mainnet bridge executes `(bool ok,) = 0xAA.call{value: 100 KAIA}("")`.
6. `0xAA` on mainnet is either an EOA controlled by a stranger, an undeployed contract, or a Safe with different signers. Alice's 100 KAIA is permanently lost.
