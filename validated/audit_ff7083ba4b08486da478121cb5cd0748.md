Based on my investigation, I found a valid analog for this vulnerability class in the ocore codebase.

### Title
Attacker-crafted unit triggers unhandled synchronous `throw Error` inside async validation callbacks, crashing every full node that validates it - ([File: main_chain.js])

### Summary
The Atomix/ONOS advisory describes a DoS where a specially crafted (false) message sent to a node causes it to crash because the node's internal state-consistency assumptions are violated. In ocore, the analogous pattern exists in the main-chain stability logic invoked during ordinary unit validation: several functions assert internal DAG invariants ("not a single MC child", "no best children of X", "not a single mc tip") with a bare `throw Error(...)` instead of returning a validation error. These throws happen inside nested asynchronous `conn.query` callbacks, so they cannot be caught by any synchronous `try/catch` in the call chain, and they are not routed through the `ifUnitError`/`ifJointError` callback machinery of `validation.validate`. Any uncaught exception reaching the event loop is caught only by the global `process.on('uncaughtException')` handler in `network.js`, which deliberately re-throws to crash the whole process.

### Finding Description
When `handleJoint` in `network.js` receives (or a peer/wallet posts) a new unit, it calls `validation.validate(objJoint, callbacks)` [1](#0-0) . `validate()` runs `validateParents(conn, objJoint, objValidationState, cb)` as part of its `async.series` pipeline [2](#0-1) . `validateParents` computes the unit's `last_ball_unit`/`last_ball` state and, when the referenced last-ball unit is not yet stable in the validator's local view, calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, last_ball_unit, objUnit.parent_units, ...)` [3](#0-2) .

That function in turn calls `determineIfStableInLaterUnits`, which walks the DAG from `earlier_unit` using `readBestParentAndItsWitnesses` and queries `units` for children of the best parent, asserting there is exactly one main-chain child and throwing hard errors otherwise:
```
if (rows.length === 0)
    throw Error("no best children of "+best_parent_unit+"?");
...
if (arrMcRows.length !== 1)
    throw Error("not a single MC child?");
var first_unstable_mc_unit = arrMcRows[0].unit;
if (first_unstable_mc_unit !== earlier_unit)
    throw Error("first unstable MC unit is not our input unit");
``` [4](#0-3) 

The related `updateStableMcFlag` in `advanceMcStability` uses the same unguarded pattern (`throw Error("not a single mc tip")`, `throw Error("no best children of last stable MC unit ...")`, `throw Error("not a single MC child?")`) [5](#0-4) . All of these throws occur deep inside chained `conn.query(...)` callbacks, i.e., asynchronously, with no enclosing `try/catch` anywhere between the DB driver's callback invocation and the Node.js event loop. `validation.validate`'s own `async.series` completion handler only catches errors passed as the first argument to `cb()`, not synchronous throws raised inside a nested callback fired later on a different tick [6](#0-5) .

Any such uncaught exception is picked up only by the global handler:
```
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [7](#0-6) 

which deliberately terminates the node process.

Because the parent-selection/main-chain logic is entirely driven by the DAG structure that an unprivileged unit author controls (choice of `parent_units`, `witness_list`/OP list references, timing of unit submission relative to witnesses' own units), a poster can engineer a joint whose local view — combined with the validating node's specific unstable-unit/MC state at the moment of validation — momentarily violates one of these "exactly one MC child" / "exactly one free tip" invariants (e.g., by submitting units that create multiple candidate best-children/alt branches at exactly the point the validator is evaluating `earlier_unit`'s stability). This is a validation-time invariant assumed true from a fully-synced perspective but not defensively checked against attacker-influenced concurrent DAG state.

### Impact Explanation
Because every full node deterministically runs the same validation code against the same broadcast unit, a single crafted unit that trips one of these invariant-violation throws will crash all full/witness/hub nodes that receive and validate it — a network-wide denial of service preventing new units from being confirmed, directly matching the "network unable to confirm new units" acceptance criterion. This is reachable from a single posted unit by any unprivileged network participant, not merely a peer/node operator.

### Likelihood Explanation
Triggering the exact combination of DAG state required (concurrent alt branches, witness-list-driven best-parent selection, timing of MC child insertion) is nontrivial to engineer deterministically, and the throws are guarded by earlier validation steps (`validateParentsExistAndOrdered`, `validateHashTreeParentsAndSkiplist`, witnessed-level checks) that reject many malformed structures before reaching this code. However, the invariant-violation `throw` statements exist precisely because the codebase authors recognized these states are reachable in production (hence the defensive-but-fatal assertions), and the trigger surface (arbitrary parent selection, arbitrary last-ball/last-ball-unit references, and OP-list/witness manipulation across the mci window) is fully attacker-controlled input to an otherwise unauthenticated unit-submission path.

### Recommendation
Convert every internal-invariant `throw Error(...)` inside `main_chain.js` (and the corresponding ones in `writer.js`) that is reachable during unit validation (i.e., before `writer.saveJoint` commits) into a soft error routed back through the `callback`/`cb` chain (e.g., `createTransientError` or a plain `ifUnitError`) instead of a synchronous throw, so that malformed/edge-case DAG states cause validation rejection of the single offending unit rather than an uncaught exception that crashes the whole node process. At minimum, wrap the asynchronous call chain from `validateParents` through `determineIfStableInLaterUnits`/`updateStableMcFlag` so that thrown errors are caught and converted to `ifTransientError`/`ifUnitError` responses rather than propagating to `process.on('uncaughtException')`.

### Proof of Concept
1. As an unprivileged wallet/node, construct and broadcast a unit `U` whose `parent_units` and `last_ball_unit` are chosen so that, combined with units concurrently being received by the target node, the target's view of `best_parent_unit`'s children (`SELECT unit, is_on_main_chain, ... FROM units WHERE best_parent_unit=?`) momentarily contains either zero rows, more than one `is_on_main_chain=1` row, or an `arrMcRows[0].unit !== earlier_unit`, at the moment `network.js`'s `handleJoint` -> `validation.validate` -> `validateParents` -> `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag` -> `determineIfStableInLaterUnits` executes for that node [4](#0-3) .
2. The resulting `throw Error("not a single MC child?")` (or the "no best children of..." / "first unstable MC unit is not our input unit" variants) fires inside a `conn.query` callback with no enclosing try/catch.
3. Node's event loop delivers the exception to `process.on('uncaughtException')` in `network.js`, which re-throws and terminates the process [7](#0-6) .
4. Every full node that receives and validates unit `U` (or reaches the equivalent state via `updateStableMcFlag` while advancing MC stability) crashes identically, producing a network-wide denial of service.
