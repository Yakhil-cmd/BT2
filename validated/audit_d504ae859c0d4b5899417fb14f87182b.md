### Title
Unbounded multiplication of `count_coins` and `denomination` in asset definitions causes floating-point precision loss, enabling cap/supply mismatch for indivisible assets - (File: validation.js, indivisible_asset.js)

### Summary
`validateAssetDefinition()` in `validation.js` sums `denomInfo.count_coins * denomInfo.denomination` for each declared denomination to verify it matches the asset's declared `cap`. This multiplication is done with plain JS numbers, and while `denomination` is checked against `constants.MAX_CAP` (conditionally), `count_coins` has no upper bound at all — only `isPositiveInteger()` is enforced. An attacker can therefore choose `count_coins` and `denomination` values whose product, when computed in IEEE-754 double precision, silently loses precision and coincidentally rounds to match an arbitrary, much smaller declared `cap`. The same unbounded multiplication (`count_coins_to_issue * denomination`) is later used in `indivisible_asset.js` when actually issuing coins, so the real issuable supply can differ from the value validated against `cap`.

### Finding Description
In `validation.js`, `validateAssetDefinition()` validates fixed-denomination asset definitions: [1](#0-0) 

Each `denomInfo.denomination` is bounded by `constants.MAX_CAP` (and even that check is gated behind an MCI upgrade flag), but `denomInfo.count_coins` is only checked with `isPositiveInteger()`, with no upper bound: [2](#0-1) 

`total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` is computed with plain JS numbers. Because `count_coins` is unbounded, this product can be arbitrarily larger than `Number.MAX_SAFE_INTEGER` (`constants.MAX_CAP` is `9e15`, close to but still under `2^53-1`), causing double-precision multiplication to lose precision silently (JS never throws on overflow — it just returns an imprecise but "valid" double). The comparison `total_cap_from_denominations !== payload.cap` at the end of the function can pass even though the true mathematical product is vastly different, because the attacker fully controls both operands and can search for values whose IEEE-754 rounded product happens to equal any small, chosen `cap` (which itself must be `<= constants.MAX_CAP`).

Once the asset definition (and its `asset_denominations` rows, which store `denomination` and `count_coins`) is written, `indivisible_asset.js`'s `issueNextCoin()` performs the exact same kind of multiplication when actually issuing coins: [3](#0-2) 

Since the stored `count_coins` for a capped denomination row is exactly what the attacker declared, the network will accept issuance up to `count_coins * denomination` real units — the same unbounded product — regardless of the validated `cap`, because the cap-consistency check at definition time was itself corrupted by the precision-loss bug.

### Impact Explanation
This breaks the integrity of the `cap` guarantee for fixed-denomination (indivisible) assets: a malicious asset issuer can define an asset whose declared, publicly-verifiable `cap` is small, while the actual denomination table allows issuing (and therefore transferring/spending) far more units than the cap implies. Any wallet, exchange, or AA that trusts the validated `cap` value as an upper bound on total supply of the asset is exposed to supply-inflation-style deception — a direct analog to the referenced overflow bug where the value used for a critical calculation is allowed to be attacker-controlled and unbounded before a bounds-check/round-trip happens in fixed-precision (or fixed-precision-like, i.e., IEEE-754 double) arithmetic.

### Likelihood Explanation
Reachable directly by any unprivileged asset issuer via a single "asset" message defining `denominations` with `fixed_denominations: true` and `cap` set. No special network position or privileged role is required — only the ability to author a unit, which is the same reachability class as the referenced Astaria finding (an unprivileged caller supplying attacker-controlled "amount"-like values that get multiplied without a pre-multiplication bound). Finding a `count_coins`/`denomination` pair whose double-precision product exactly matches an arbitrary target `cap` is an offline computational search (bounded search space for a 15-16 significant-digit collision), which is feasible without any privileged access.

### Recommendation
- Enforce an explicit upper bound on `denomInfo.count_coins` (e.g., `count_coins <= constants.MAX_CAP`, or better, require `count_coins * denomination <= constants.MAX_CAP` using arbitrary-precision arithmetic, e.g. BigInt) before summing, both in `validateAssetDefinition()` (`validation.js`) and the analogous formula-based validation in `aa_validation.js`.
- Compute `total_cap_from_denominations` using BigInt (or a decimal library with sufficient precision, as already used elsewhere in the codebase for AA formulas) rather than native JS number multiplication, and only convert back to Number after confirming the value is representable exactly and does not exceed `constants.MAX_CAP`.
- Apply the same fix to `issueNextCoin()` in `indivisible_asset.js` where `count_coins_to_issue * denomination` is computed, ensuring it can never diverge from the validated total.

### Proof of Concept
1. An attacker crafts an asset-definition unit with `fixed_denominations: true`, a small `cap` (e.g. `1000000`), and a `denominations` array containing one entry `{ denomination: D, count_coins: C }` where `D` and `C` are large integers (each individually `<= constants.MAX_CAP = 9e15`, satisfying all existing checks) chosen such that the double-precision product `C * D` rounds in IEEE-754 to exactly `1000000` (or any value equal to the declared `cap`), even though the true integer product is astronomically larger.
2. `validateAssetDefinition()` (`validation.js:2778` `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination`) computes this lossy product, and the subsequent check `total_cap_from_denominations !== payload.cap` (`validation.js:2790`) passes because the rounded double matches.
3. The asset is accepted onto the DAG with `asset_denominations` rows storing the attacker's full, huge `count_coins` and `denomination`.
4. Later, `indivisible_asset.js`'s `issueNextCoin()` (`indivisible_asset.js:533-536`) issues coins using `count_coins_to_issue * denomination` directly from those stored values, allowing issuance far beyond what the validated `cap` implies.
