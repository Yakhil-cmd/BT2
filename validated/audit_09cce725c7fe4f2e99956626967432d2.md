### Title
Webhook signature verification authenticates the GitHub organization but the event handlers act on an unverified `repository.full_name`, allowing a legitimate tenant of one configured GitHub App to forge webhooks targeting another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC validation based on `repository.owner.login` (or `organization.login`) taken from the JSON body, but the event handlers that actually mutate state (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, …) resolve the `Repository`/`Stack` to act on using a *different* field of the same body, `repository.full_name`. Because the two fields are never cross-checked, an attacker who legitimately administers one configured GitHub organization (and therefore knows that org's `webhook_secret`) can sign a payload that authenticates as their own org while pointing `repository.full_name` at a stack belonging to a different, victim organization configured on the same Shipit instance.

### Finding Description
`verify_signature` derives the authentication key purely from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app config (including a distinct `webhook_secret`) in a documented multi-tenant configuration where each GitHub organization has its own App/secret: [3](#0-2) 

This "Using Multiple Github Applications" setup is an officially documented supported deployment mode, not a misconfiguration: [4](#0-3) 

`GitHubApp#verify_webhook_signature` HMACs the raw body against that org's own secret: [5](#0-4) 

Once the signature is accepted, `WebhooksController#create` dispatches the *entire* payload to handlers without re-deriving or re-checking the organization: [6](#0-5) 

Every handler resolves the target `Stack` via `Repository.from_github_repo_name`, keyed off `payload.dig('repository', 'full_name')` - a field that was never part of the signature-selection logic and is never checked against `repository.owner.login`: [7](#0-6) [8](#0-7) 

`PushHandler` (and analogously `StatusHandler`/`CheckSuiteHandler`) inherits this lookup and acts on whatever stacks match that `full_name`: [9](#0-8) 

This is the same bug class as the analog report: `verify_webhook_signature`/`verify_signature` is analogous to `SwapperCallbackValidation.verifyCallback` - it validates one narrow property (the sender is *a* recognized org) but the field actually consumed to decide *what gets mutated* (`repository.full_name`) is a completely different, unchecked value inside the same attacker-supplied message, exactly like `execCalls()` accepting arbitrary calldata after only checking "is this a Swapper." The broken equality is:

`organization authenticated by HMAC (repository.owner.login / organization.login)` ≠ `repository.owner actually written to (repository.full_name)`.

### Impact Explanation
On a Shipit instance configured with multiple GitHub organizations (each with their own App and `webhook_secret`, as explicitly documented and supported), any org admin who is legitimately included in that multi-tenant configuration can forge a raw webhook body: sign it (or have GitHub sign it) as their own org (`repository.owner.login = "OrgB"`, satisfying the HMAC check with `OrgB`'s known/configurable secret) while setting `repository.full_name = "OrgA/victim-repo"`. This is dispatched, unmodified, to handlers that will act on `OrgA`'s stacks — e.g. `PushHandler` enqueuing `GithubSyncJob` for a victim stack, or `StatusHandler`/`CheckSuiteHandler` writing forged commit statuses/check results for a victim's commit. Because commit statuses/checks gate whether a commit is eligible to be merged/deployed by Shipit's automation, this can be used to inject false "green" CI signal for a victim repository the attacker does not control, contributing to an unauthorized deploy/merge on that victim stack — crossing an authentication boundary between tenants that the per-organization webhook design was meant to enforce.

### Likelihood Explanation
Requires a Shipit deployment using the documented multi-organization GitHub App configuration (multiple tenants sharing one Shipit instance), and requires the attacker to be an administrator of one of those configured (even low-privilege/less-trusted) organizations — no GitHub App private key, `api_clients_secret`, or Shipit session/API token is needed, only knowledge of their own org's webhook secret, which they control by definition since they configure their own GitHub App. This is a realistic scenario for shared/SaaS-style Shipit deployments explicitly documented in `docs/setup.md`.

### Recommendation
After verifying the HMAC signature, re-derive `repository_owner` strictly from the *same* field the HMAC was validated against, and require that the `repository.full_name` (or `organization.login`) used by handlers to resolve a `Stack`/`Repository` matches the organization that was cryptographically authenticated for this request. Reject (422) any webhook where `repository.owner.login`/`organization.login` used for signature selection does not match the owner segment of `repository.full_name` before dispatching to `Shipit::Webhooks.for_event`.

### Proof of Concept
1. Shipit is configured with two tenants, `OrgA` (victim) and `OrgB` (attacker-administered), per `docs/setup.md`'s multi-app schema, each with its own `webhook_secret`.
2. Attacker, as an admin of `OrgB`, knows/controls `OrgB`'s `webhook_secret`.
3. Attacker crafts a `push` (or `status`/`check_suite`) JSON body with:
   - `repository.owner.login = "OrgB"` (or `organization.login = "OrgB"`)
   - `repository.full_name = "OrgA/victim-repo"`
4. Attacker computes `X-Hub-Signature` using `OrgB`'s webhook secret over the raw body and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgB")` and successfully validates the signature (`lib/shipit/github_app.rb#verify_webhook_signature`).
6. `WebhooksController#create` dispatches the payload; `PushHandler`/`StatusHandler` resolve the target via `Repository.from_github_repo_name("OrgA/victim-repo")` and mutate `OrgA`'s stack/commit state (`app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/repository.rb`), even though only `OrgB` was authenticated.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
