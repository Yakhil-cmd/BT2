### Title
Hookify block rules for file operations are silently bypassed for tools not enumerated in `_extract_field`/`_matches_tool` (e.g. `NotebookEdit`) - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._check_condition` (via `_extract_field`) only knows how to pull field values (`file_path`, `content`, `new_text`, `old_text`) for the tool names `Bash`, `Write`, `Edit`, and `MultiEdit`. Any other tool that can also read/write file content under a different field naming convention — most notably `NotebookEdit`, which uses `notebook_path`/cell source fields instead of `file_path`/`new_string` — causes `_extract_field` to return `None`, which makes every condition evaluate to `False` regardless of its pattern, silently letting the operation through even when a `block` rule targets exactly that kind of content or path.

### Finding Description
`RuleEngine._rule_matches` first optionally checks `rule.tool_matcher` (an exact-match allowlist split on `|`, `plugins/hookify/core/rule_engine.py` lines 127-142), but most rules documented in the skill (`plugins/hookify/skills/writing-rules/SKILL.md`) don't set `tool_matcher` at all — they rely purely on `event: file` plus `conditions`. When `tool_matcher` is unset, `_rule_matches` skips tool filtering entirely and defers solely to `_check_condition`/`_extract_field` ( [1](#0-0) ).

`_extract_field` first checks if the literal condition `field` name (e.g. `file_path`) is a key present verbatim in `tool_input`; if not, it falls through to a hardcoded `if/elif` chain keyed on `tool_name` that only recognizes `Bash`, `Write`/`Edit`, and `MultiEdit` ( [2](#0-1) ). `NotebookEdit` (and any other file-mutating tool such as future MCP filesystem tools) is not covered by any branch, so for a rule with `field: file_path` or `field: new_text`, `_extract_field` returns `None`. Back in `_check_condition`, `if field_value is None: return False` ( [3](#0-2) ) unconditionally fails the condition — independent of the actual pattern — so the rule can never match for that tool, even though the underlying dangerous action (writing content to a sensitive file path) is the same operation the rule was written to block.

Additionally, the `PreToolUse` hook driver (`plugins/hookify/hooks/pretooluse.py`) computes the `event` filter only for `Bash` → `bash` and `Edit|Write|MultiEdit` → `file` (lines 45-49); any other tool name leaves `event = None`, which causes `load_rules(event=None)` to load **all** rules (the `if event:` guard in `config_loader.load_rules` skips event filtering when `event` is falsy) — so `file`-scoped block rules are still handed to the engine for a `NotebookEdit` call, but then fail silently for the reasons above.

An attacker does not need to exploit the plugin machinery directly: because Claude Code's tool selection is influenced by repository content and prompt context, a malicious repo (e.g. via prompt injection in a README, issue text, or code comments) can induce the agent to use `NotebookEdit` to write attacker-controlled content into/adjacent to files instead of `Write`/`Edit`, causing a user-configured `block` rule (e.g. "don't touch `.env`", "don't write outside `/workspace`") to never fire.

### Impact Explanation
A security control the user relies on ("hookify" `action: block` rules meant to prevent sensitive file writes/edits) can be reliably and deterministically bypassed simply by performing the equivalent write through `NotebookEdit` instead of `Write`/`Edit`/`MultiEdit`. This maps to unauthorized file write outside the user-approved scope — the exact impact category called out in the question — because the engine's design creates a false sense of security: the block rule is present and enabled, yet the "invariant that a matching block rule must reliably deny the protected operation" does not hold for any tool outside the four hardcoded names.

### Likelihood Explanation
This is fully deterministic and requires no special privilege: any workflow where the agent is directed (by legitimate task, or by attacker-controlled repo/prompt content) to use `NotebookEdit` against a path/content pattern that a `file`-event rule intends to block will bypass that rule 100% of the time. The only precondition is that the user has hookify block rules relying on the common `event: file` / `field: file_path|new_text|content` pattern (the documented default usage pattern in `SKILL.md`) without an explicit `tool_matcher` enumerating every possible tool — which is the normal, recommended usage shown in the plugin's own documentation.

### Recommendation
- In `_extract_field`, replace the hardcoded per-tool `if/elif` chain with a generalized field-alias map that covers all file-mutating built-in tools (including `NotebookEdit`'s `notebook_path`, cell `new_source`, etc.) and any MCP filesystem-like tools, or better, canonicalize tool_input fields into common keys before rule evaluation.
- Make `_matches_tool`/rule evaluation fail-safe rather than fail-open: if a `file`-scoped rule's target tool is unrecognized, either treat it as a match candidate and require explicit rule authors to opt out, or emit a warning/log so silent bypasses aren't invisible.
- Fix `pretooluse.py` so unrecognized tool names don't cause `event=None` to load an unfiltered rule set that then silently no-ops; instead, map any tool with file-path/content-like fields into the `file` event bucket.

### Proof of Concept
Unit test added to `plugins/hookify/core/rule_engine.py` test harness:
```python
def test_notebookedit_bypasses_file_block_rule():
    rule = Rule(
        name="block-env-write",
        enabled=True,
        event="file",
        action="block",
        conditions=[Condition(field="file_path", operator="regex_match", pattern=r"\.env$")],
        message="Blocked write to .env"
    )
    engine = RuleEngine()

    # Equivalent dangerous write via Write tool -> correctly blocked
    write_input = {"tool_name": "Write", "tool_input": {"file_path": ".env", "content": "SECRET=1"}}
    assert engine.evaluate_rules([rule], write_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

    # Equivalent dangerous write via NotebookEdit -> should also be blocked but is NOT
    notebook_input = {
        "tool_name": "NotebookEdit",
        "tool_input": {"notebook_path": ".env", "new_source": "SECRET=1"}
    }
    result = engine.evaluate_rules([rule], notebook_input)
    assert result == {}  # demonstrates bypass: block rule silently did not fire
```
Expected: the `Write` case is denied, while the `NotebookEdit` case returns `{}` (allowed), proving the block rule is bypassed purely by choosing a different, unhandled tool representation for the same file-write operation.
