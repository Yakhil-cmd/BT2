### Title
`recapitalize` refunds un-deposited tokens: an unprivileged caller drains pool custody by declaring a payment that never happened - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The kernel bug class is "missing error-path unwind: a resource is acquired/assumed but never verified or released correctly, leaking resources." In `Pool::recapitalize`, the pool *assumes* the caller pre-transferred `amount` tokens ("The controller transfers `amount` into the pool before this call"), credits only the backing shortfall, and unconditionally transfers the `refund = amount - applied` back to `payer` — without ever measuring the actual balance delta or verifying any inbound payment. A caller who sends nothing is refunded tokens it never deposited.

### Finding Description
`recapitalize::apply` splits the work into `accounting` (bookkeeping) and a payout leg: [1](#0-0) 

`accounting` caps the credited amount at `backing_shortfall`, commits `cache.credit_cash(applied)`, and returns `refund = amount - applied`: [2](#0-1) 

The only inbound-funds check is a comment trusting that "The controller transfers `amount` into the pool before this call" (line 4). There is no `balance_before`/`balance_after` measurement, no receipt check, and the refund leg `transfer_out(&payer, outcome.refund)` pays out of real custody regardless. When the market has no shortfall (or the caller simply sends zero), `applied = 0` and `refund = amount` — the entire declared amount is paid out for free. Because `applied` was 0, the `cash` book is not even debited: the pool's accounting still reports the stolen funds as present, so `Cache::require_reserves` keeps admitting exits that then fail inside the SAC transfer.

The protocol's own regression test demonstrates exactly this: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` mints a deposit, then calls `pool.recapitalize(hub, payer, custody)` from a freshly generated address and drains the pool's entire token balance to `payer`: [3](#0-2) 

The test then shows the book still claims the cash exists and supplier withdrawals pass the liquidity guard but fail inside the SAC transfer with `BalanceError` — i.e., the market reports itself solvent and cannot pay.

### Impact Explanation
Theft of user funds / protocol insolvency. With `applied` capped by `backing_shortfall`, calling `recapitalize(payer = attacker, amount = pool_balance)` when the shortfall is smaller than `amount` pays `amount - shortfall` of real supplier custody to the attacker for zero cost. In the worst case (no shortfall) the attacker can drain the full pool balance in one call while the `cash` ledger still overstates custody, leaving suppliers permanently unable to withdraw.

### Likelihood Explanation
The entrypoint takes `payer` as a free parameter and the test exercises it from an arbitrary generated address, indicating the pool does not gate the refund destination. Whether the pool restricts `recapitalize` callers to the controller is a caveat I could not fully confirm from `contracts/pool/src/lib.rs` within the iteration budget — but even if only the controller calls it, the missing measured-receipt check means any path that invokes `recapitalize` without actually pre-funding (a router/strategy leg, or a direct call if the entrypoint is exposed) triggers the leak. The attack requires no privileged role at the pool layer and no price manipulation.

### Recommendation
Measure the actual inbound transfer instead of trusting the declared `amount`: snapshot the token balance before, require `balance_after - balance_before >= amount` (or pull the funds via `transfer_from` inside `recapitalize`), and compute `refund` only from tokens actually received. Alternatively, restrict `refund` to `min(refund, actual_inbound)` so an unfunded call can never pay out custody it did not receive.

### Proof of Concept
```rust
// Attacker calls the pool directly (no tokens sent beforehand).
// Assume market has no backing shortfall: applied = 0, refund = amount.
let pool_balance = token.balance(&pool);
pool_client.recapitalize(&hub_asset, &attacker, &pool_balance);
// Pool transfers `pool_balance` to `attacker`; cash book unchanged.
assert_eq!(token.balance(&pool), 0);
assert_eq!(token.balance(&attacker), pool_balance);
// Supplier withdraw passes require_reserves (book still shows cash)
// but fails inside the SAC transfer -> funds permanently frozen/stolen.
```
This mirrors the existing test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs`, which already executes the drain and observes the stranded `cash` book.
