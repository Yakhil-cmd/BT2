### Title
Quadratic-Complexity DoS via Linear `arrInputKeys` Scan in Payment Input Validation - ([File: validation.js])

### Summary
`validation.js` maintains a single flat array, `objValidationState.arrInputKeys`, that accumulates a key for **every** input (issue/transfer/headers_commission/witnessing) and every spend-proof across **all** messages of a unit. For each new input, the code does `objValidationState.arrInputKeys.indexOf(input_key)` before pushing the new key onto the array. This is the same bug class as the Expat `storeAtts()` CVE: a linear scan of an ever-growing list performed once per item, producing O(N²) total work for N attacker-controlled items in a single object.

### Finding Description
`arrInputKeys` is initialized once per unit validation at [1](#0-0) , and is never reset per message — it is threaded through `validateMessages` → `validateMessage` → `validatePaymentInputsAndOutputs` for every message in the unit.

Each input/spend-proof triggers a full linear scan of the array to check for duplicates, then appends to it:
- Issue inputs: [2](#0-1) 
- Transfer inputs: [3](#0-2) 
- Headers-commission/witnessing inputs: [4](#0-3) 
- Spend proofs (private payments): [5](#0-4) 

Because the array is shared across every message in the unit rather than being a `Set`/hash-map, the cost of validating the i-th input is O(i), and the total cost for a unit with N inputs spread across its messages is O(N²) — exactly analogous to Expat's `storeAtts()` scanning `elementType->defaultAtts` once per non-normalized attribute.

A unit can carry multiple payment messages (bounded by `constants.MAX_MESSAGES_PER_UNIT`), each with multiple inputs (bounded by `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`), so a single well-formed unit that is otherwise valid up to the point of duplicate-detection can be crafted with many distinct inputs (e.g., many small "transfer" inputs referencing distinct, non-existent or self-referential sources) to maximize N before validation fails. I was not able to confirm the exact numeric values of `MAX_MESSAGES_PER_UNIT` / `MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_UNIT_LENGTH` in this session (the constants.js content did not come back in the final tool call), so the precise practical N achievable within `MAX_UNIT_LENGTH` bytes is unverified — this should be checked before treating the finding as fully proven at Medium+ severity.

### Impact Explanation
`validation.js`'s `validate()` is invoked by any node validating a newly received/posted unit, reachable from an unprivileged unit poster (any wallet/hub client can broadcast a unit). If the quadratic cost is large enough relative to `MAX_UNIT_LENGTH`, an attacker can submit a single unit whose validation consumes disproportionate CPU on every full node that processes it (each node independently validates incoming units), potentially delaying or stalling processing of other units — a network-wide effect similar to the reported "node unable to confirm new units" DoS class.

### Likelihood Explanation
Likely low-to-medium in practice: the attack requires only crafting a unit with many payment messages/inputs, which is achievable by any unprivileged poster without needing witnesses' cooperation, entity resolution, or special permissions. However, the achievable N is capped by `MAX_UNIT_LENGTH` (unit size limit) and per-message input/output caps, and other O(N) validation costs (e.g., DB queries per input) already dominate real-world cost, potentially diluting the CPU-bound quadratic effect relative to the expat case (pure in-memory C parsing). Without confirming the actual constant values, I cannot assert the quadratic term dominates enough to produce a severity-worthy CPU spike — this is the key unresolved uncertainty.

### Recommendation
Replace `arrInputKeys` (a plain array with `.indexOf()`) with a `Set` (or plain object/hash map) for O(1) average-case duplicate lookups, eliminating the O(N²) behavior regardless of how many inputs/spend-proofs a unit contains. Apply this fix at all four call sites: [5](#0-4) [2](#0-1) [3](#0-2) [4](#0-3) 

### Proof of Concept
Construct a unit with the maximum allowed number of payment messages, each containing the maximum allowed number of transfer inputs (all with distinct, syntactically-valid but ultimately-invalid `unit`/`message_index`/`output_index` triples so they reach the duplicate-key check before failing on "output not found"). As validation proceeds message-by-message and input-by-input, each subsequent input triggers a linear scan of the accumulated `arrInputKeys` array, producing O(N²) key-comparison operations for N total inputs in the unit before the unit is ultimately rejected. Because exact `MAX_MESSAGES_PER_UNIT` / `MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_UNIT_LENGTH` values were not confirmed in this session, the concrete N (and thus CPU-time impact) achievable under the size cap needs to be measured directly in the repository (e.g., via a Devin session) to validate real-world severity.
