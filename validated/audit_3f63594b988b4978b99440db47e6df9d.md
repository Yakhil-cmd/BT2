### Title
Malicious swap route executes attacker-selected pool code under the caller’s authorization tree and drains unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept an opaque `swap` payload and pass it to the configured router while the original caller’s `require_auth` authorization remains active on the invocation stack. A route can therefore name attacker-controlled pool code that records or injects an unrelated `token.transfer(caller, attacker, amount)` as a child of the caller’s signed `swap_collateral` authorization, letting the route steal wallet assets outside the lent collateral if the victim signs that generated authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates the position owner, then carries the caller-supplied `swap` bytes through the withdrawal path into `swap_tokens`. [3](#0-2) 

`swap_tokens` validates only that the payload is nonempty, invokes `router.execute_strategy(controller, amount_in, swap)`, and afterward checks the controller’s input spend and positive output delta. [4](#0-3) [5](#0-4) 

Those controller-side accounting checks do not constrain which contracts the route payload causes the router to call. [1](#0-0) 

This is the analog of indexed dispatch in the external report: the attacker controls a route operand that selects executable code, while validation focuses on numeric settlement rather than the selected callee’s behavior. [6](#0-5) 

The repository’s regression test deploys a rogue hop whose `swap` implementation calls `wallet_token.transfer(victim, attacker, amount)`, then records that transfer as a child invocation beneath the victim’s `swap_collateral` authorization. [7](#0-6) [8](#0-7) 

After the signed route executes, the victim’s unrelated wallet balance is zero and the attacker receives the full stolen amount, while the lending swap itself still returns a fair output and passes the controller’s measured settlement checks. [9](#0-8) 

The same opaque `swap` argument is accepted by `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, so the pattern is shared across the account-strategy surface rather than isolated to one wrapper. [10](#0-9) [11](#0-10) [12](#0-11) 

### Impact Explanation
The impact is theft of user funds outside the collateral amount supplied to the strategy. [9](#0-8) 

The malicious route can produce a legitimate `token_out` receipt, so `RouterOverspend`, `NoSwapOutput`, and the final account-risk checks do not prevent or detect the unrelated wallet transfer. [5](#0-4) 

The attacker does not need a protocol role, liquidity position, leaked key, or privileged governance operation; the required condition is getting the victim to sign a transaction whose simulation-derived authorization tree contains the malicious child transfer. [13](#0-12) [8](#0-7) 

### Likelihood Explanation
An attacker can deploy the malicious hop contract, construct a valid-looking quote route that selects it, and have a UI or quoting path present only the intended swap economics to the victim. [14](#0-13) [15](#0-14) 

Because the controller forwards opaque bytes and validates only settlement deltas, the exploit does not depend on favorable market movement or on the router returning an incorrect amount. [16](#0-15) [5](#0-4) 

Execution does require the victim to authorize the poisoned invocation tree, which lowers the likelihood relative to a fully signature-free exploit but still permits wallet-draining phishing through a normal `swap_collateral` signature flow. [17](#0-16) 

### Recommendation
Do not treat an opaque route payload as merely an economic parameter: decode and validate every route-selected contract before the user signs, and reject any transaction whose simulated authorization tree contains children beyond the exact transfer or invocation expected for that strategy. [17](#0-16) [8](#0-7) 

At the protocol boundary, prefer constraining route venues and pool addresses to an explicit allowlist or a decoded route format that the controller can inspect before invoking the router, rather than forwarding unbounded opaque bytes under the caller’s authenticated invocation. [4](#0-3) 

Wallets and SDKs should display the full nested authorization tree, flag child calls that transfer assets from the signer to a third party, and refuse poisoned trees even when the displayed swap output meets the quoted minimum. [18](#0-17) 

### Proof of Concept
The repository test constructs the complete exploit with an unprivileged malicious pool and a normal `swap_collateral` call. [19](#0-18) 

1. Alice supplies `10_000 USDC` as collateral and also holds `WALLET_BALANCE` of an unrelated token in her wallet. [20](#0-19) 
2. The attacker deploys a pool whose `swap` function reads a stored `(victim, token, attacker, amount)` plan and invokes `token.transfer(victim, attacker, amount)`. [21](#0-20) 
3. The attacker constructs `swap` bytes naming that rogue pool while advertising a fair `USDC → ETH` output. [15](#0-14) 
4. Alice submits or signs `Controller::swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, malicious_route)`. [22](#0-21) 
5. The rogue token transfer is recorded beneath Alice’s `swap_collateral` authorization, not as an independent attacker authorization. [8](#0-7) 
6. Once Alice signs that tree, the transaction succeeds: Alice’s unrelated wallet token balance becomes `0`, the attacker receives `WALLET_BALANCE`, and Alice still receives the advertised `FAIR_OUT_ETH` collateral. [9](#0-8)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
