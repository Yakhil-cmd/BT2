### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while all event handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to validate the inbound webhook based on one field of the JSON body (`repository.owner.login`, falling back to `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Repository`/`Stack` to act on using a *different*, independently attacker-controlled field of the same body: `repository.full_name`. Because HMAC verification only proves "this byte string was signed with organization X's secret," not "the organization named inside this byte string is X," an attacker who legitimately controls the webhook secret for *any one* GitHub organization configured in Shipit's multi-org setup can forge a payload whose `repository.owner.login` matches their own org (so the correct, real secret validates it) but whose `repository.full_name` points at a Stack belonging to a completely different organization/repository tracked by the same Shipit instance.

### Finding Description
The signature check binds trust to the wrong entity:

```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Meanwhile the base handler class - used by every registered webhook handler (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) - resolves the target repository/stack from a *separate* field:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler` then directly triggers a GitHub sync for any stack matching that (attacker-chosen) `repository.full_name`:

```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

Shipit explicitly supports configuring multiple independent GitHub organizations, each with its own `webhook_secret`, in a single instance (`docs/setup.md`, "Using Multiple Github Applications") [4](#0-3) , and `Shipit.github(organization:)` looks the app config up purely by the organization name string passed in [5](#0-4) .

**Equality that should hold but doesn't:** `organization used to select/verify webhook_secret` == `organization that owns the repository the handler subsequently mutates`. Before the attack, for a legitimately delivered GitHub webhook these two are always the same (GitHub always signs with, and reports, its own org/repo). After the attack, an attacker who owns org `attacker-org` (and thus its real `webhook_secret`) submits a self-signed payload with `repository.owner.login = "attacker-org"` (satisfies `verify_signature`) but `repository.full_name = "victim-org/victim-repo"` (drives `PushHandler`/`StatusHandler`/etc.), breaking the equality and letting `attacker-org`'s credentials authorize actions against `victim-org`'s stack.

### Impact Explanation
By forging a `push` event this way, the attacker forces `stack.sync_github(expected_head_sha:)` → `GithubSyncJob` to run against the victim's stack [6](#0-5) , which fetches commits via the *victim org's own* installation token (since `Stack#github_api`/`Repository#github_app` are derived from the stack's real owner) and appends them, updates deploy spec caches, and — if continuous deployment is enabled on that stack — can trigger an unauthorized deploy through the stack's `after_commit` hooks (`sync_github_if_necessary`, `trigger_continuous_delivery`) [7](#0-6) . The same field-mismatch lets an attacker forge `status`/`check_suite` events to inject fabricated CI status for arbitrary commits on a victim's stack via `StatusHandler` [8](#0-7) , corrupting merge/deploy gating decisions. This crosses the organization/repository trust boundary the webhook signature is meant to enforce, matching the Critical bucket for cross-repository writes / unauthorized deploys.

### Likelihood Explanation
Exploitation requires the attacker to control the `webhook_secret` of at least one GitHub organization configured in the same multi-org Shipit deployment as the victim — a realistic scenario for any Shipit instance shared across multiple teams/orgs (the documented multi-org configuration exists precisely to let independent teams self-onboard their own GitHub App/org). No access to the victim's secret, session, or API token is required; only the ability to install/configure one's own GitHub App against the shared Shipit instance and send a POST to `/webhooks`.

### Recommendation
Bind signature verification to the same identity the handlers act on. At minimum:
- Verify the signature using the organization/app derived from `repository.full_name`'s owner segment (or `Repository.from_github_repo_name`), not a separate top-level `repository.owner.login`/`organization.login` field.
- After verifying the signature, cross-check that the resolved `GitHubApp`'s organization actually matches the owner of `repository.full_name` before any handler runs, rejecting the request if they diverge.

### Proof of Concept
1. Deploy Shipit configured with two organizations in `secrets.yml`: `attacker-org` (attacker controls the GitHub App / knows its `webhook_secret`) and `victim-org` (hosts a tracked Stack, e.g. `victim-org/victim-repo`).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-or-real-victim-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s real, legitimately-known `webhook_secret` over this exact JSON body (`Hook::DeliverySigner`/`verify_webhook_signature` logic: `sha1=` + HMAC-SHA1) [9](#0-8) .
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully validates the signature against the attacker's own secret.
5. `WebhooksController#create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — an action the attacker was never authorized to trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
