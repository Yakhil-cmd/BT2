### Title
Incomplete permission check allows any paired correspondent device to trigger signing requests for local wallet addresses - (File: wallet.js)

### Summary
The `sign` message handler in `wallet.js` is supposed to verify that the sender device is actually a registered cosigner of the wallet that owns the requested `body.address` before triggering a local signing flow. This check is present in the code but has been commented out, so it is never executed.

### Finding Description
In `handleMessageFromHub` → `doHandle()` → case `"sign"`, once `findAddress()` resolves the requested address to a locally-owned key (`ifLocal` callback), the code is supposed to confirm that the message's sender (`from_address`) is actually one of the cosigning devices registered for that wallet (`SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?`). That check exists in the source but is entirely commented out: [1](#0-0)

Because the permission check is disabled, `handleMessageFromHub()` accepts and processes a `"sign"` request from *any* known correspondent device (i.e., any device that is simply paired with the wallet owner, which requires no special trust relationship beyond exchanging a pairing code) for *any* address that is locally controlled — not just addresses that are genuinely part of a multi-device/multisig wallet shared with that sender. On success, the message is passed straight through to `network.handleOnlineJoint(ws, objJoint)` and the `"signing_request"` event is emitted ( [2](#0-1) ), which is the event UI clients use to display the sign confirmation dialog to the user.

This is directly analogous to CVE-2020-25284: the Linux `rbd` driver was supposed to gate a sensitive device operation (map/unmap) behind a permission check, but the check was incomplete, letting any local, unprivileged actor reach an operation meant to be restricted to a specific set of authorized principals. Here, the analogous "device operation" is signing-request handling for a wallet address, and the "authorized principals" are the cosigner devices of that address's wallet — but the check restricting access to that set is commented out, so any correspondent device can invoke the flow.

### Impact Explanation
Any paired correspondent device (not necessarily an actual cosigner of the target wallet/address) can send a forged `sign` message for one of the victim's controlled addresses. Because the cosigner check is disabled, the request is accepted and:
- The victim's node runs full validation (`network.handleOnlineJoint`) on an attacker-crafted unsigned unit and emits the `signing_request` event that drives the wallet UI's confirmation prompt ( [3](#0-2) ).
- An attacker who is merely paired with the victim (e.g. via a chat/support-bot pairing code) can repeatedly present fabricated transactions for the victim to "confirm," including transactions that pay out from the victim's own address to attacker-controlled destinations, exploiting user confusion about whether the request legitimately originated from a genuine wallet cosigner.
- This breaks the intended access boundary described by the existing comment ("sender is not cosigner of this address"), turning what should be a cosigner-only capability into one reachable by any correspondent device, directly matching the "incomplete permission checking for access" bug class of the CVE and creating a path toward unauthorized spending if the user is tricked into approving the presented unit.

### Likelihood Explanation
Exploitation only requires establishing a device pairing with the victim (a routine, low-friction action explicitly supported by the wallet's pairing flow, see `device.js` `handlePairingMessage`), then sending a crafted `"sign"` message referencing one of the victim's own addresses. No cosigner relationship, shared wallet, or additional secret is required, making this readily reachable by any paired device/AA-adjacent counterparty in scope.

### Recommendation
Re-enable the sender-is-cosigner check before invoking `callbacks.ifOk()` / emitting `signing_request` in the `ifLocal` branch of the `"sign"` case in `wallet.js`, i.e. verify `from_address` is registered as a signing device for the target wallet (via `extended_pubkeys` or `wallet_signing_paths`) before proceeding, instead of unconditionally trusting any correspondent device.

### Proof of Concept
1. Attacker device pairs with the victim's wallet device using a normal pairing code (no cosigner relationship established).
2. Attacker sends a device message with `subject: "sign"` and `body = { address: <victim's own address>, signing_path: "r", unsigned_unit: <crafted unit paying out from victim's address> }`.
3. On the victim's node, `handleMessageFromHub` resolves the address via `findAddress` to `ifLocal` (since it is one of the victim's own addresses) and, because the cosigner check is commented out, immediately calls `callbacks.ifOk()` and proceeds to validate/emit `signing_request` for the attacker-supplied unit — despite the attacker never having been authorized as a cosigner of that address.
