### Title
Webhook signature verification is keyed on `repository.owner.login`, but stack mutation is keyed on the unrelated `repository.full_name` field — cross-organization spoofing of webhook events (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (with a fallback to `params.dig('organization', 'login')`) [1](#0-0) [2](#0-1) . However, once the signature check passes, every `Shipit::Webhooks::Handlers::Handler` resolves the target `Repository`/`Stack` from a completely separate JSON field, `payload.dig('repository', 'full_name')` [3](#0-2) . Since the entire JSON body is attacker-controlled prior to verification, an attacker can submit a payload where `repository.owner.login` names an organization whose `webhook_secret` is blank/unset (a supported, documented configuration for multi-org Shipit installs) while `repository.full_name` names a victim repository belonging to a different, secured organization. The signature check will pass trivially (or with a secret the attacker knows for their own org) while the handler logic mutates the victim repository's stacks.

### Finding Description
`Shipit.github(organization:)` looks up per-organization GitHub App configuration from `secrets.github` and explicitly supports multiple organizations configured side by side [4](#0-3) . Each organization's config independently sets `webhook_secret`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's secret is blank: `return true unless webhook_secret` [5](#0-4) . Shipit's own setup docs and fixtures confirm `webhook_secret` is optional per-organization in multi-org setups [6](#0-5) [7](#0-6) .

The controller's `verify_signature` before_action picks the GitHub App to check against solely from `repository_owner`:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
and `repository_owner` is read straight from the untrusted, unverified request body:
```
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
``` [2](#0-1) 

Once `create` runs, the payload is dispatched to handlers (`PushHandler`, `PullRequest::*Handler`, etc.) which independently resolve the affected repository/stack from `payload.dig('repository', 'full_name')`, with no re-validation that this value matches the organization whose secret was just checked [3](#0-2) [8](#0-7) . `Repository.from_github_repo_name` splits `full_name` on `/` and looks the repo up purely by `owner`/`name` columns, with no relation back to the verified organization [9](#0-8) .

**Binding broken:** organization authenticated (`repository_owner` used to select the `webhook_secret`/GitHub App) ≠ repository actually written (`repository.full_name` used by handlers to locate and mutate `Stack`/`Repository` records). In a genuine GitHub webhook these two values always agree because GitHub itself populates both fields from the same source repository. But because Shipit trusts the raw, unauthenticated JSON body to pick both values independently before any cryptographic check ties them together, an attacker forging the body can decouple them.

### Impact Explanation
This allows an unauthenticated network attacker to trigger the `push`, `pull_request`, `status`, `check_suite`, `membership`, etc. webhook handlers against **any repository/stack tracked by the Shipit instance**, as long as the attacker can name (in `repository.owner.login`) some organization configured in the same Shipit instance with no `webhook_secret`, while pointing `repository.full_name` at the victim's tracked repository. Concretely this can:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha:)` on an arbitrary victim stack, influencing which commit is considered "head" and eligible for deploy [10](#0-9) .
- Forge `status`/`check_suite` events to fabricate commit statuses that gate merges/deploys for a victim's stack.
- Manipulate `pull_request` label/open/close/reopen handlers to archive or unarchive victim review stacks.

This crosses the "cross-repository writes" / "unauthorized deploy or rollback" impact bar defined in scope, because the write/mutation target (victim stack) is decoupled from the credential boundary (the org whose secret was actually checked).

### Likelihood Explanation
Requires only that the Shipit deployment (a) tracks more than one GitHub organization (a documented, supported feature — see `docs/setup.md` "Using Multiple Github Applications" and the `secrets_double_github_app.yml` fixture), and (b) at least one of those configured organizations has no `webhook_secret` set (also documented as optional, and shown as the default/example in `config/secrets.development.shopify.yml` and the double-app fixture where both orgs have `webhook_secret: # nil`). Under this common configuration, no secret, token, or privileged account is needed at all — the attacker only needs network access to `POST /webhooks` with a crafted `X-Github-Event` header and JSON body.

### Recommendation
Bind the field used for signature-organization selection to the same field used for repository resolution. Concretely:
- Have `verify_signature` also require that `params.dig('repository', 'full_name')`'s owner segment matches `repository_owner` before accepting the payload, or
- Have `Handler#repository_name` (and all handler `repository`/`stacks` lookups) derive the repository strictly from the already-authenticated organization context instead of trusting `repository.full_name` independently, or
- Reject/require `webhook_secret` for every configured organization in multi-org installs so `verify_webhook_signature` can never short-circuit to `true`.

### Proof of Concept
Precondition: Shipit configured with two organizations, e.g. `AttackerOrg` (no `webhook_secret`) and `VictimOrg` (tracked, has stacks), per `docs/setup.md`'s multi-org example.

1. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything
Body:
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
2. `WebhooksController#verify_signature` computes `repository_owner == "AttackerOrg"`, calls `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature` header [5](#0-4) .
3. `create` parses the body and dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim stack [10](#0-9)  — despite the attacker never having proven knowledge of `VictimOrg`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
