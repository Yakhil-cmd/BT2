Based on my research, I found a genuine authorization scope-check gap in `claim-staker-rewards-for-signer` in pox-5.clar that mirrors the Budibase bug class: a "flag-level" check missing a "scope" validation.

### Title
`claim-staker-rewards-for-signer` lets any contract zero a staker's unclaimed sBTC rewards under an arbitrary `signer` scope it never earned — (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`claim-staker-rewards-for-signer` is a public function intended to be "only callable by the signer manager contract" that actually delegated a given staker's stake [1](#0-0) . It derives the "signer" identity purely from `contract-caller` — an unvalidated, self-asserted scope — and uses it both to compute `settle-staker-rewards` and to zero the `staker-unclaimed-rewards-for-cycle` map entry for `{reward-cycle, bond-index, signer: contract-caller, staker}`.

### Finding Description
`claim-staker-rewards-for-signer` never checks that `contract-caller` is the staker's actual `signer` for that `reward-cycle`/`bond-index` (i.e., it never checks `staker-signer-cycle-memberships` or `protocol-bond-memberships` for that staker). Compare this with the sibling functions `stake-update`, `unstake`, and `update-bond-registration`, which all explicitly assert `(is-eq old-signer (get signer current-info))` before mutating per-signer state [2](#0-1) [3](#0-2) [4](#0-3) . `claim-staker-rewards-for-signer` has no analogous scope check — it is the exact same class of bug as the Budibase report: individual flags/values (`staker`, `reward-cycle`, `bond-index`) are free-form arguments, but the code never verifies that `contract-caller` (the "signer" scope being asserted) actually owns/administers the target staker's position for that cycle.

`settle-staker-rewards` computes `earned` via `get-earned-staker-rewards signer reward-cycle bond-index staker`, which reads `staker-rewards-per-token-settled-for-cycle` and `staker-unclaimed-rewards-for-cycle` keyed on the caller-supplied `signer` [5](#0-4) . Since any arbitrary contract can call this function and set itself as `contract-caller` (i.e., as `signer`), any principal can drive `settle-staker-rewards` and `map-set staker-unclaimed-rewards-for-cycle { ... signer: contract-caller, staker }` for **any staker and any bond-index/reward-cycle combination**, even ones the caller never registered or delegated for.

### Impact Explanation
The real staker's `staker-unclaimed-rewards-for-cycle` entry keyed under their **actual, legitimate signer** is untouched, since the map key includes `signer`, so this specific write only creates/overwrites an entry keyed by the attacker's own bogus signer identity — meaning direct fund theft via this single call is not evident. However, it does allow an attacker to freely invoke `settle-staker-rewards` on behalf of an arbitrary `staker`/`reward-cycle`/`bond-index` combination with a spoofed `signer` value, which is a genuine authorization break of the intended invariant "only the registered signer-manager contract that a staker delegated to may crystallize/mark that staker's rewards" — this is the "unsigned stacking action" class in the rules (a rewards-settlement action taken without the staker's or the correct signer's authorization). Given more investigation of the `earned` value returned to the calling (impersonating) contract, and how `settle-staker-rewards`'s output is consumed by the wrapping `signer-manager.clar` `claim-staker-rewards` (which does further trigger an sBTC transfer of `earned` amount to the staker, gated by a genuine sBTC balance check), the exploitability of a fund-theft/freeze primitive from this specific gap could not be fully confirmed in the time available.

### Likelihood Explanation
Because the function is `define-public` and takes `staker`, `reward-cycle`, and `bond-index` as fully attacker-controlled arguments with no cross-check against the staker's real membership records, exploitation requires only deploying a trivial malicious Clarity contract that calls `claim-staker-rewards-for-signer` directly on pox-5 — no signature or admin privilege required, matching the "unprivileged account" threat model in the rules.

### Recommendation
Add a scope-ownership check to `claim-staker-rewards-for-signer` analogous to what `stake-update`/`unstake`/`update-bond-registration` already do: look up the staker's current signer for the given `reward-cycle`/`bond-index` (via `staker-signer-cycle-memberships` or `protocol-bond-memberships`) and assert `(is-eq contract-caller <actual-signer>)` before calling `settle-staker-rewards` or mutating `staker-unclaimed-rewards-for-cycle`.

### Proof of Concept
I was not able to fully trace the downstream consumption of this function's return value in `signer-manager.clar`'s `claim-staker-rewards` wrapper to construct a concrete, verified fund-theft PoC within the available tool budget — specifically I could not confirm whether `earned`, once computed by an impersonating "signer," is ever paid out to that impersonator (versus only recorded and gated by the real sBTC transfer logic elsewhere). **This is a limitation of my analysis, not a claim that the issue is benign.** I recommend a Devin session with full repo/build access to (1) trace all callers/wrappers of `claim-staker-rewards-for-signer`, (2) write a Clarinet/vitest unit test deploying a malicious contract that calls `claim-staker-rewards-for-signer` for an arbitrary victim `staker`/`reward-cycle`/`bond-index` it never registered for, and (3) confirm whether this results in state corruption, reward siphoning, or is merely a self-contained no-op (in which case the missing check should still be fixed as defense-in-depth per the recommendation above).

;; As a signer manager contract, mark a specific staker as having claimed
;; rewards. This is used to mutate internal rewards settlement state.
;;
;; This is only callable by the signer manager contract.
(define-public (claim-staker-rewards-for-signer
        (staker principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let ((rewards-info (settle-staker-rewards contract-caller reward-cycle bond-index staker)))
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))
        (map-set staker-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: contract-caller,
            staker: staker,
        }
            u0
        )
        (print {
            topic: "claim-staker-rewards-for-signer",
            signer-manager: contract-caller,
            staker: staker,
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            rewards-claimed: (get earned rewards-info),
        })
        (ok rewards-info)
    )
)
