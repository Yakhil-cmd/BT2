### Title
Threshold signature schemes (`r of set` / `weighted and`) do not verify uniqueness of signing keys, allowing a single key to satisfy a multi-signer threshold - (File: `definition.js`)

### Summary
`ocore`'s address-definition language supports `r of set` and `weighted and` operators to express "N-of-M" multi-signature conditions, analogous to TUF/`tough`'s signature-threshold model. Just like the `tough` flaw (CVE-2020-15093/GHSA-5q2r-92f9-4m49), the ocore implementation counts satisfied branches toward the required threshold without ever verifying that the branches (and therefore the underlying keys) are distinct. A single private key can be embedded multiple times in the `set`, letting its holder single-handedly satisfy a threshold that is represented (and trusted by other parties) as requiring cooperation of several independent signers.

### Finding Description
`validateDefinition`'s handling of `r of set` only checks structural constraints — that `required` is a positive integer, `set` is an array of length ≥ 2, and `required <= set.length` — but never checks that the elements of `set` are distinct or reference distinct keys/addresses: [1](#0-0) 

The same gap exists for `weighted and`, which sums `weight` for options that provide a signature without any uniqueness check on the underlying `sig`/`address` conditions: [2](#0-1) 

At authentication time, `validateAuthentifiers` simply verifies the ECDSA signature supplied at each path independently: [3](#0-2) 

and only requires that every entry in `assocAuthentifiers` be "used" by some path in the tree — it does not require that the paths correspond to distinct keys: [4](#0-3) 

Because ECDSA `sig` verification is keyed purely by `(hash, signature, pubkey)` per path, an address owner can construct a definition such as:
```
["r of set", {required: 2, set: [
  ["sig", {pubkey: "PUBKEY_A"}],
  ["sig", {pubkey: "PUBKEY_A"}]
]}]
```
This passes `validateDefinition` unmodified, and the sole holder of `PUBKEY_A` can supply the identical valid signature at both authentifier paths (`r.0` and `r.1`), satisfying `required: 2` while controlling only one real key. The same technique applies to nested `address` branches that resolve (directly or transitively) to the same underlying signer, and to `weighted and` where duplicated weighted branches can be used to reach `required` weight with fewer unique keys than represented.

This mirrors the `tough`/TUF root cause exactly: a threshold-signature verifier that counts *valid signatures* rather than *valid signatures from distinct required keys*, letting one keyholder impersonate the required quorum.

### Impact Explanation
Any protocol participant that relies on an `r of set`/`weighted and` address as a genuine multi-party custody mechanism — shared wallets created via `wallet_defined_by_addresses.js`/`wallet_defined_by_keys.js` (`createMultisigWallet`, `handleNewSharedAddress`), asset issuer/definer addresses, AA definer/trigger conditions, or private-payment counterparty addresses — can be misled into believing that spending requires cooperation of N independent signers, when in fact the address creator embedded duplicate key references and can authorize spends alone. This results in unauthorized spending of funds that other parties funded under the assumption of joint (M-of-N) custody, undermining the core security guarantee of the multisig primitive. Because `sig` validation and `r of set`/`weighted and` evaluation are core, universally-reachable primitives used across payments, assets, and AAs, the blast radius covers any use case that depends on threshold-of-unique-keys semantics.

### Likelihood Explanation
Any unprivileged unit poster who is also the definer of a shared/multisig-style address can trivially construct such a definition — no special privilege, race condition, or network position is required. The only prerequisite is that a counterparty (co-owner, depositor, asset holder) trusts the represented "N distinct signers" semantics without independently auditing the definition tree for duplicate keys, which is exactly the operational assumption `r of set`/`weighted and` are designed to satisfy for users.

### Recommendation
In `validateDefinition`'s `r of set` and `weighted and` branches (`definition.js:147-233`), enforce that all `set` elements are structurally/cryptographically distinct — e.g., reject duplicate `pubkey` values across `sig` leaves in the same set, and, where branches are `address` references, ensure they resolve to distinct underlying signing keys (recursively). At minimum, warn/reject when two leaves in the same threshold set share an identical `pubkey`/hash condition, since this can never legitimately increase security and only serves to misrepresent the threshold to third parties.

### Proof of Concept
1. Attacker creates an address with definition:
```json
["r of set", {"required": 2, "set": [
  ["sig", {"pubkey": "A...same_pubkey_base64...="}],
  ["sig", {"pubkey": "A...same_pubkey_base64...="}]
]}]
```
2. This passes `Definition.validateDefinition` unchanged (`definition.js:147-185`), and the address hash is computed normally via `objectHash.getChash160`.
3. Attacker presents the address to a victim as a genuine "2 independent signer" address (e.g., in a shared-wallet setup or as an asset/AA authorization condition), and the victim deposits/authorizes funds to it.
4. To spend, the attacker signs the unit hash once with the single private key, and places the identical base64 signature string at both authentifier paths `r.0` and `r.1` in `assocAuthentifiers`.
5. `validateAuthentifiers`' `sig` case (`definition.js:734-754`) independently verifies each path successfully (same pubkey, same valid signature), `arrUsedPaths` contains both paths, and the final check at `definition.js:1461-1462` passes since both supplied authentifiers were "used" — the unit validates as fully authorized despite only one real key being involved, contradicting the "2 required signers" guarantee.
