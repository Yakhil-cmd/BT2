Confirmed operator-precedence bug in `provision?`. Ruby `&&` binds tighter than `||`, so the method actually evaluates as:

```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [1](#0-0) 

The second and third disjuncts never check `review_stacks_enabled` at all, unlike the sibling `labeled_handler.rb`/`unlabeled_handler.rb`, whose `respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` across the whole condition. [2](#0-1)  This means a repository with `review_stacks_enabled == false` but `provisioning_behavior == "prevent_with_label"` will still auto-create a `ReviewStack` for any opened, unlabeled PR — including one opened by an unprivileged/external contributor with `params.pull_request.head.ref` pointing at their own fork branch.

### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` uses `&&`/`||` without parentheses, so Ruby's operator precedence makes the `allow_with_label` and `prevent_with_label` branches ignore `repository.review_stacks_enabled` entirely. Any GitHub user who can open a PR against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` can force Shipit to create and enqueue-for-provisioning a live `ReviewStack` bound to their own PR branch.

### Finding Description
The broken binding: `repository.review_stacks_enabled == false` should imply `stack_created_for_pr == false` for every `provisioning_behavior` value. In `OpenedHandler#provision?` [1](#0-0) , Ruby parses the expression as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present?) || (prevent_with_label? && !label_present?)`. If an operator has `review_stacks_enabled == false` and `provisioning_behavior == "prevent_with_label"`, the third disjunct `repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?` evaluates independently of `review_stacks_enabled`, so `provision?` returns `true` for any unlabeled PR.

Exploit flow: attacker opens a PR (`params.action == "opened"`) against the target repository from a branch they control (`params.pull_request.head.ref`). `process` calls `ReviewStackAdapter#find_or_create!` unconditionally once `respond_to_pull_request_opened?` is true [3](#0-2) , which creates a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` and adds it to `ReviewStackProvisioningQueue` [4](#0-3) . The cron-run queue then calls the configured `ProvisioningHandler#up` [5](#0-4)  and the stack becomes a normal, deployable/task-runnable stack scoped to the attacker's branch. Any subsequent task/deploy execution against this stack resolves `TaskDefinition#steps`/deploy steps from `DeploySpec::FileSystem`, which reads `shipit.yml` off the checked-out branch — i.e., the attacker's own ref — and those steps are ultimately spawned via `Command`/`PTY.spawn` with the merged environment used for `TaskCommands#perform` [6](#0-5) .

Existing guards fail here specifically because `review_stacks_enabled` — the master switch operators use to disable this whole feature — is silently bypassed by the precedence bug; no other check (label state, PR state, webhook signature) constrains stack creation once this branch is reached. The sibling handlers (`LabeledHandler`, `UnlabeledHandler`) correctly gate every branch behind `review_stacks_enabled &&`, confirming this is a bug specific to `OpenedHandler`, not by design. [7](#0-6) 

### Impact Explanation
An operator who explicitly disabled review stacks for a repository (`review_stacks_enabled = false`) still gets an unauthorized `Shipit::ReviewStack` record created and provisioned for arbitrary attacker-controlled PR branches whenever `provisioning_behavior` happens to be `prevent_with_label` (a default-looking, opt-out configuration). This is an authorization-bypass write: a stack is created/mutated for a repository's provisioning state without the consent the `review_stacks_enabled` flag was meant to enforce. Depending on the host's `ProvisioningHandler` and whether a Shipit user later triggers a task/deploy on that stack, this can escalate to execution of attacker-supplied `shipit.yml` steps via `Command`/`PTY.spawn`, with `GITHUB_TOKEN` and other deploy-time secrets present in the spawned process environment — matching the Critical impact category (RCE on the deploy host / secret exposure) once a task is run against the attacker's branch. It is repeatable against every repository sharing this specific, plausible configuration combination.

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled == false` and `provisioning_behavior == "prevent_with_label"` (a legitimate, documented configuration choice, not a misconfiguration of "allow all"). Attacker cost is minimal: open a PR without the provisioning label, which any external contributor able to open a PR can do; no Shipit session, API token, or secret needed. The bug fires on every "opened" webhook that satisfies this configuration.

### Recommendation
Parenthesize the condition so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Add a regression test asserting `provision?`/stack creation returns false whenever `review_stacks_enabled` is false, for all three `provisioning_behavior` values.

### Proof of Concept
Minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create a review stack when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :prevent_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before the fix, `Shipit::Stack.count` changes (stack created) despite `repository.review_stacks_enabled == false`; after applying the recommended parenthesization, `assert_no_difference` passes, restoring `repository.review_stacks_enabled == false` → `stack_created_for_pr == false`.
