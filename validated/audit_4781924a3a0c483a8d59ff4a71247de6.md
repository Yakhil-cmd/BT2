### Title
Pool overpayment refund pays out of real token custody without debiting the `cash` book or proving the inbound payment — ([File: contracts/pool/src/ops/repay.rs](contracts/pool/src/ops/repay.rs))

### Summary
The pool's repay and recapitalize legs refund a "declared" excess by executing a real token transfer out of pool custody, while only the *net* amount is credited to the `cash` accounting book. The refund amount is derived from the caller-declared `action.amount`, not from a measured balance delta. This is the same bug class as the OpenSSL double-free: the same pool funds are effectively released twice — once they remain booked as `cash` backing supplier shares, and once they physically leave the contract as an unfunded refund — leaving the book permanently overstating custody.

### Finding Description
`ops::repay::apply` resolves the repay into `(burned, overpayment)` via `cache.resolve_repay(amount, position)`, where `amount` is `action.amount` — a declared parameter. It credits only `net_repay = amount - overpayment` to cash, commits the market state, and then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` to send real tokens back to the payer. [1](#0-0) 

Critically:

1. `credit_cash(net_repay)` is the only book movement; the refund path does not debit `cash` or pass `require_reserves`. [2](#0-1) 
2. `overpayment` is computed from `action.amount` vs. current debt — the pool never measures `token.balance(this)` before/after to confirm the inbound transfer actually happened or covered the declared amount. `resolve_repay`'s full-close branch sets `net_repay = 0` and `overpayment = amount` whenever the market carries no debt.

The repo's own test suite proves the primitive end-to-end: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` repays `custody_before` against a zero-debt market, receives the entire pool custody back as "refund", and the `cash` book is untouched — the pool still reports the paid-out funds as present. [3](#0-2)  The shared assertion documents the resulting state: "the cash book is untouched, so the pool still reports the paid-out funds as present." [4](#0-3) 

The same pattern exists in `ops::recapitalize::apply`, which refunds the excess over the shortfall computed from a declared inbound amount — again with no `cash` debit and no reserve check on the refund. [5](#0-4) 

Both pool entrypoints are `#[only_owner]` (controller-gated). [6](#0-5)  Reachability for an unprivileged address therefore depends on the controller path: `repay` is normally funded because "the controller transfers the repay amount into the pool before this call" [7](#0-6) , but `recapitalize` is a permissionless controller entrypoint whose declared amount the pool trusts. I was unable to fully verify (within available iterations) whether controller `recapitalize` enforces a measured receipt before forwarding `amount`; if it does not — consistent with the test comment that the refund is "derived from a declared inbound amount, not from the cash book" for "a payment that never happened" — an attacker declares a large recapitalization on a market with no shortfall and receives the entire declared amount (up to real custody) as a refund from the pool, having paid nothing.

Even where the inbound is funded, the missing `cash` debit on the refund path is itself defective: any discrepancy between declared and delivered amount (rounding in the controller's multi-leg repayment aggregation, fee-on-transfer debt tokens, or under-delivery on a hub leg) is paid out of supplier custody with the book unchanged.

### Impact Explanation
Theft of user funds up to the pool's entire token custody in a single call, plus permanent insolvency: `cash` continues to report drained funds as present, so `Cache::require_reserves` admits withdrawals and borrows that then fail inside the SAC transfer — the market reports itself solvent and cannot pay, permanently freezing remaining supplier funds. [8](#0-7) 

### Likelihood Explanation
An unprivileged caller reaches `recapitalize` on the controller (it is a permissionless bad-debt backstop) with a chosen `amount`. The trigger requires a market where declared amount exceeds the shortfall — trivially satisfiable on any healthy market where the shortfall is zero, making the whole declared amount "excess". No price manipulation, timing, or privileged role is needed.

### Recommendation
- Measure the refund against reality: snapshot `token.balance(pool)` before and after the inbound leg, and cap `overpayment` at the measured received delta rather than `action.amount - debt`.
- Debit the refund from `cash` (or never book it): the refund leg should route through the same `require_reserves`/cash-debit path as `withdraw`, so a refund can never exceed what the book admits.
- Treat a zero-debt or zero-shortfall leg with positive `amount` as `InvalidPayments` instead of manufacturing a refund from custody.

### Proof of Concept
Mirroring the in-repo test [3](#0-2) :

1. Pick any pool market holding supplier custody `C` with no outstanding shortfall/debt.
2. Call controller `recapitalize(hub_asset, amount = C)` (or `repay` on a zero-debt market via the path that forwards `action.amount` unmeasured).
3. Pool resolves `overpayment = C`, `net = 0`, commits the state with `cash` unchanged, and `transfer_out(payer, C)` sends the entire custody to the attacker.
4. `get_reserves` still reports the pre-attack `cash`; subsequent supplier withdraws/borrows pass the reserve check and revert inside the token transfer — funds are gone and the book is insolvent.

pub(crate) fn apply(
    env: &Env,
    payer: &Address,
    action: &PoolAction,
) -> (PoolPositionMutation, MarketStateSnapshot) {
    let outcome = accounting(env, action);

    outcome.cache.transfer_out(payer, outcome.overpayment);
    (outcome.mutation, outcome.snapshot)
}

/// Accrues interest, resolves the repay amount into burned debt shares and
/// overpayment, burns the shares, and credits the net repay to cash without
/// transferring the overpayment refund. Panics if a positive net repay would
/// burn zero scaled shares.
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
    let mutation = cache.position_mutation(position, net_repay);
    RepayOutcome {
        cache,
        mutation,
        snapshot,
        overpayment,
    }
}

#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
