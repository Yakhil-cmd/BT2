### Title
Cross-repository commit-status write via unscoped sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table and writes a GitHub status to every match, without checking that the commit's owning stack/repository matches the repository named (and authenticated) in the webhook payload. Since `sha` is only unique per `(sha, stack_id)` pair and not globally, an attacker who controls repository B can produce/replay a commit whose sha collides with a commit already tracked by stack A, sign the payload with B's own valid `webhook_secret`, and cause a `Status` to be written onto stack A's commit.

### Finding Description
The broken binding: `payload.repository.full_name` (verified as `attacker/B`) == `repository owning the Commit row mutated` (stack A's repo) — this is **false** in the exploit, yet the write still occurs.

`WebhooksController#verify_signature` only validates that the HMAC signature matches the `webhook_secret` configured for `repository_owner` (`params.dig('repository','owner','login')`) via `Shipit.github(organization: repository_owner)` [1](#0-0) . This proves the payload was signed by *some* organization's secret (here, B's), but never binds the verified organization to which `Commit` rows may be mutated downstream.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query is global — it is not scoped by `stack_id`, `repository`, or any relationship to `repository_owner`/`repository.full_name` from the verified payload. The `commits` table's uniqueness constraint is `add_index :commits, %i(sha stack_id), unique: true` [3](#0-2) , i.e. sha is unique **per stack**, not globally. Any two stacks/repos can have Commit rows with the same sha (e.g., the empty-tree sha, or any commit with identical tree+parents+timestamps, or simply two forks sharing history).

`Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [4](#0-3) , using the target commit's own `stack_id` — i.e., stack A's — to create the `Status` record, regardless of which repository the verified payload claims to be.

Exploit flow: attacker owns repo B, configures Shipit webhook secret for B (a normal, unprivileged setup step available to any repo owner who can install the webhook). Attacker crafts/pushes a commit to B whose sha matches a sha already present in stack A (trivial with the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee491`, or by matching tree+parents+timestamps). Attacker POSTs `/webhooks` with header `X-Github-Event: status`, body `{sha: <shared sha>, state: 'success', repository: {full_name: 'attacker/B', owner: {login: 'attacker'}}}`, signed with B's real `webhook_secret`. `verify_signature` passes because the signature is valid for organization `attacker`. `StatusHandler#process` finds stack A's `Commit` row (same sha) and writes a status onto it, even though the verified payload names `attacker/B`.

No existing guard closes this gap: `verify_signature` validates the signer, not the target of the mutation; `drop_unhandled_event` only checks the handler exists for the event type; the `ExplicitParameters` schema (`params do ... end`) validates only field types/presence, not repository identity; there is no `require_permission!`/`stacks` scope check in this webhook path since it is unauthenticated by design (relies purely on signature-to-repo binding, which this handler ignores).

### Impact Explanation
An attacker can inject arbitrary CI status states (`success`, `failure`, `error`, `pending`, arbitrary `description`/`target_url`/`context`) onto another tenant's commit in stack A, without ever authenticating against A's repository or webhook secret. Since Shipit's deployability/merge/continuous-delivery gating depends on commit status (`Commit#deployable?`, `schedule_continuous_delivery`) [5](#0-4) [6](#0-5) , forging a `success` status can trigger continuous deployment for a commit the attacker does not own and never had CI actually run on it. This is a payload-for-one-repository mutating another's commit/stack state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

Repeatable indefinitely against any stack whose repo the attacker can produce a sha collision with, since the attacker fully controls timing and content of commits pushed to their own repo B.

### Likelihood Explanation
Preconditions: attacker needs (1) any repository B connected to the same Shipit instance with a valid webhook configured (a normal, low-privilege onboarding action, or even a public/shared org triggers via mirrored orgs), and (2) a sha collision with a target stack A's commit. The empty-tree sha collision requires zero effort — any repo's initial/empty commits can trivially reference the fixed empty-tree hash, or an attacker can deliberately construct a commit with identical tree, parent list, author/committer, and timestamps to match a known target sha (feasible if the target commit's metadata is public, e.g., via GitHub's API/commit page). Attacker cost is low: crafting a webhook POST with correct HMAC using their own known secret is trivial scripting. No Shipit session, secrets, or elevated roles are required.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous `CheckRunHandler`/`PushHandler` type of code, if similarly affected) by the repository named in the verified payload, e.g., restrict to `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { name: ..., owner: ... })`, or otherwise verify `commit.stack.repository.full_name == payload.repository.full_name` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
class StatusHandlerTest < ActiveSupport::TestCase
  test "status payload for repository B must not mutate a commit belonging to stack A" do
    stack_a = shipit_stacks(:shipit)
    stack_b = create_stack(repository: create_repository(owner: 'attacker', name: 'B'))

    shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee491'
    commit_a = stack_a.commits.create!(sha: shared_sha, message: 'a')
    stack_b.commits.create!(sha: shared_sha, message: 'b')

    payload = Shipit::Webhooks::Handlers::StatusHandler.new(
      'sha' => shared_sha,
      'state' => 'success',
      'repository' => { 'full_name' => 'attacker/B', 'owner' => { 'login' => 'attacker' } }
    )

    assert_no_difference -> { commit_a.reload.statuses.count } do
      # Currently FAILS: statuses.count increases even though payload names attacker/B, not stack_a's repo.
      payload.process
    end
  end
end
```
This test demonstrates that `commit_a.statuses.count` changes despite the verified payload identifying `attacker/B` as the source repository, proving `repository named in payload == repository owning mutated commit` is false while the write still succeeds.
