The CVE-2018-10911 root cause is a C-language flaw where `dic_unserialize` reads a signed key-length field without checking for negative values, causing an out-of-bounds/negative-offset memory read when that length is later used for allocation or copying.

This bug class does not map onto the Polkadot SDK's actual decoding paths for several structural reasons:

- All length-prefixed decoding in the SCALE codec uses `Compact<u32>` (an unsigned type), so there is no signed/negative-length representation to smuggle through, unlike C's signed length field. [1](#0-0) 
- Extrinsic decoding explicitly cross-checks the declared length prefix against the actual consumed bytes and rejects mismatches, rather than trusting an attacker-supplied length for allocation. [2](#0-1) 
- Storage length decoding (`decode_len`/`decode_non_dedup_len`) reads a bounded fixed-size buffer (`[0u8; 5]`) and clamps the read length via `data.len().min(len as usize)` before interpreting it as a `Compact<u32>`, so it cannot produce an out-of-bounds read. [3](#0-2) 
- Wasm/contracts host-function memory reads explicitly bound-check the pointer/length against the accessible memory range before any copy or decode occurs. [4](#0-3) [5](#0-4) 
- Compressed-blob and trie node-size decoding also apply explicit upper bounds (`bomb_limit`, 16-bit max) rather than trusting a raw signed/attacker length. [6](#0-5) [7](#0-6) 

Rust's type system (unsigned `u32`/`usize` for all length fields) combined with the consistent presence of explicit remaining-length/bounds checks throughout the codec, extrinsic, storage, contracts and trie layers eliminates the specific "negative length bypasses bounds check" invariant violation that CVE-2018-10911 exploits. No user-reachable entry point (signed extrinsic, contract call, or XCM message) was found where an attacker-controlled length value skips a bounds/sign check before being used for allocation or memory copy.
