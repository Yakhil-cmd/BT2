### Title
Webhook signature verification selects the GitHub App by an unauthenticated field, decoupling the org that signs the payload from the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to verify a payload against using `repository_owner`, which is read straight out of the still-unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`). Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the target `Stack`/`Repository` to act on using a *different* field from the same body: `payload.dig('repository', 'full_name')`. In a multi-org Shipit deployment (`Shipit.github(organization:)` / `github_app_config`), this means the signature only proves "some configured organization's secret signed this exact byte stream" — it never proves that *that* organization owns the repository the handler is about to mutate.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is [2](#0-1) , taken from the JSON body before any signature check has occurred. `Shipit.github(organization:)` looks up per-organization config (secret, app id, etc.) via `github_app_config` [3](#0-2) , which is exactly the "Using Multiple GitHub Applications" feature documented for hosting several orgs behind one Shipit instance.

Once `verify_webhook_signature` returns true (HMAC computed with *that org's* `webhook_secret` over the raw body) [4](#0-3) , `WebhooksController#create` dispatches the same raw body to handlers [5](#0-4) . Every handler resolves its target repository/stack independently via `Handler#repository_name`/`#stacks`, which reads `payload.dig('repository', 'full_name')` [6](#0-5) , then looks the `Repository` up by `owner`/`name` parsed out of that string via `Repository.from_github_repo_name` [7](#0-6) . `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack [8](#0-7) , and pull-request handlers create/archive/unarchive review stacks the same way, all keyed off `repository.full_name` rather than `repository.owner.login`.

Nothing ties `repository.owner.login` (used to pick the verifying secret) to `repository.full_name` (used to pick the acted-upon repository). An org onboarded into Shipit's multi-org config — an otherwise unprivileged party with respect to any other tenant's repo — knows its own `webhook_secret` (it configured it, or it is delivered to it by GitHub for its own installation) and can therefore forge a payload with:
- `repository.owner.login` = its own org (so `verify_signature` selects its own known secret and passes),
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler resolves and acts on the victim's `Stack`).

This breaks the binding: `organization that authenticated == repository that is written` is assumed true by the controller/handler split but is never actually enforced.

### Impact Explanation
This allows one onboarded (low-privilege, webhook-only) GitHub organization to trigger unauthorized actions against another tenant's stacks hosted on the same Shipit instance — e.g. forcing `GithubSyncJob` (`stack.sync_github`) with an attacker-chosen `expected_head_sha`, or forging `pull_request`/`check_suite`/`membership` events to create, archive, or unarchive review stacks and manipulate `PullRequest`/`Membership` records tied to a repository the attacker does not control. This is a cross-repository/cross-tenant write achieved purely by crafting a JSON body and an HMAC computed with credentials the attacker legitimately possesses for their *own* tenant — satisfying the "cross-repository writes" / "unauthorized deploy" impact bar without needing any Shipit session, API token, or the victim's GitHub credentials.

### Likelihood Explanation
Requires the deployment to use the documented multi-org GitHub App configuration (`docs/setup.md` "Using Multiple GitHub Applications", `github_app_config`) so that more than one distinct `webhook_secret` exists and the attacker is a legitimate tenant of at least one of them. Given that setup, the attack is trivial: no signature forgery is needed for the org the attacker legitimately owns, only substitution of the `repository.full_name` field in the outgoing webhook payload (or a crafted POST to `/webhooks` with a valid signature computed locally).

### Recommendation
In `verify_signature`, after resolving `github_app` and verifying the signature, also verify that the selected `repository_owner` matches the owner encoded in `repository.full_name` (or `organization.login` for org-scoped events) before dispatching to handlers; reject the request (422) on mismatch. More robustly, `Handler#stacks`/`#repository_name` should validate that the resolved `Repository#owner` equals the organization whose secret verified the request, rather than trusting `full_name` unconditionally.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub App config containing at least `AttackerOrg` (attacker controls/knows `webhook_secret`) and `VictimOrg/victim-repo` (an existing `Stack`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and successfully verifies the signature against `AttackerOrg`'s secret [9](#0-8) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` [6](#0-5)  and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on VictimOrg's stack [8](#0-7) , without AttackerOrg ever having write access to `VictimOrg/victim-repo`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
