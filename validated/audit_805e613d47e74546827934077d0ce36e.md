### Title
`extract_frontmatter` misclassifies an `action: block` key as a nested list-item continuation, silently downgrading enforcement to `warn` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` is a hand-rolled YAML-subset parser that decides whether a line is a "top-level key" purely by checking `indent == 0`, and treats any line with `indent > 2` while `in_dict_item` is true as a continuation field of the *current list item's dict*, regardless of the key name. A rule author (or an attacker who can influence the checked-in `.claude/hookify.*.local.md` file) can place `action: block` at indent > 2 directly under a `conditions:` list item; the parser then stores it inside `frontmatter['conditions'][i]['action']` instead of the top-level `frontmatter['action']`. `Rule.from_dict` then falls back to the default `action = frontmatter.get('action', 'warn')`, so the rule silently becomes a warn-only rule even though the file visibly reads `action: block`.

### Finding Description
The parsing loop in `extract_frontmatter` (`plugins/hookify/core/config_loader.py:115-188`) has three branches:
- top-level key: `indent == 0 and ':' in line` (line 125)
- new list item: `stripped.startswith('-') and in_list` (line 155)
- dict-item continuation: `elif indent > 2 and in_dict_item and ':' in line` (line 184)

The continuation branch has no key-name allowlist and no dedent/list-termination detection other than encountering a subsequent `indent == 0` line. Therefore, if `action: block` (or `enabled: false`, etc.) is written with indentation greater than 2 while a list (`conditions:`) is still open (`in_dict_item == True`), it is absorbed into `current_dict` as a field of the current condition item, not as the rule's top-level `action`.

Concretely, for:
```
---
name: block-rm-rf
enabled: true
event: bash
conditions:
  - field: command
    operator: regex_match
    pattern: "rm -rf"
    action: block
---
Dangerous command blocked!
```
`extract_frontmatter` returns `frontmatter = {'name': 'block-rm-rf', 'enabled': True, 'event': 'bash', 'conditions': [{'field': 'command', 'operator': 'regex_match', 'pattern': 'rm -rf', 'action': 'block'}]}` — there is no top-level `'action'` key at all. `Rule.from_dict` (`config_loader.py:81`) then evaluates `frontmatter.get('action', 'warn')`, producing `action = 'warn'`.

`RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py:53-58`) branches purely on `rule.action == 'block'`; anything else goes to `warning_rules`, which only emits a `systemMessage` and does **not** set `permissionDecision: "deny"` (lines 86-91 vs 72-79). So a rule intended to hard-block a dangerous `Bash`/file operation instead only prints a warning while the operation proceeds — the "deny means deny" invariant is violated, and the discrepancy between the visible YAML text (`action: block`) and actual enforced behavior (`warn`) is invisible to anyone reviewing the file text without understanding this specific parser quirk.

No existing validation catches this: `load_rule_file` only checks that `frontmatter` is non-empty (`config_loader.py:256-258`) and swallows `ValueError/KeyError/AttributeError/TypeError` as generic parse warnings — there is no schema validation confirming that an `action` key was actually parsed at the top level, and no round-trip/consistency check between the raw file text and the resulting `Rule.action`.

### Impact Explanation
This is a config-integrity / enforcement-bypass bug: a rule file that appears (and is intended) to `block` a dangerous Bash command or file write instead is silently treated as `warn`, so the dangerous operation proceeds with just a message shown to the user, which the user may dismiss or not notice before continuing. This matches "approval/enforcement bypass allowing an operation that should be blocked" — a security-relevant logic flaw in the hook enforcement path (`load_rule_file -> extract_frontmatter -> Rule.from_dict -> RuleEngine.evaluate_rules`).

### Likelihood Explanation
Preconditions: hookify hooks enabled and a `.claude/hookify.*.local.md` rule file present whose `conditions:` block places `action:` (or other top-level keys) at indentation greater than 2, which is a plausible and easy-to-produce YAML-formatting mistake or a deliberately crafted misdirection since it is not obviously "wrong" YAML to a human skimming it (it visually reads as `action: block`). Reproducing requires no special tooling — it's a pure parsing/data flow issue, deterministic and 100% reproducible with the exact PoC below.

### Recommendation
Replace the custom indentation-based mini-parser with a real YAML parser (e.g. Python's `yaml.safe_load` on `frontmatter_text`) to eliminate this whole class of misparsing bugs. If the custom parser must be kept, at minimum: track list/dict nesting with an explicit stack rather than a single `in_dict_item`/`current_dict` pair, terminate the current list on any line with `indent == 0` before processing it as a top-level key, and add a post-parse validation step (e.g., assert `frontmatter.get('action') in ('warn', 'block')` matches the raw text's top-level occurrence) that fails closed (i.e., treats unparseable/ambiguous `action` as `block`, not `warn`), matching a fail-safe default rather than a fail-open default.

### Proof of Concept
Unit test to add to a differential test suite for `extract_frontmatter`/`Rule.from_dict`:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-rm-rf
enabled: true
event: bash
conditions:
  - field: command
    operator: regex_match
    pattern: "rm -rf"
    action: block
---
Dangerous command blocked!
"""

fm, msg = extract_frontmatter(content)

# Bug: top-level 'action' key is missing/misplaced
assert 'action' not in fm, f"expected 'action' absorbed into conditions, got {fm}"
assert fm['conditions'][0]['action'] == 'block'

rule = Rule.from_dict(fm, msg)
# Expected (intended) semantics: rule.action == 'block'
# Actual (buggy) behavior:
assert rule.action == 'warn'  # demonstrates silent downgrade from intended 'block'
```
Expected assertion if fixed: `rule.action == 'block'` and `fm['action'] == 'block'` at the top level, matching the YAML author's intent. Currently the test demonstrates `rule.action == 'warn'`, confirming `RuleEngine.evaluate_rules` would route this rule into `warning_rules` instead of `blocking_rules`, allowing the dangerous `Bash` command through with only a warning.
