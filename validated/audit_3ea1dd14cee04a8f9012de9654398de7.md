### Title
Membership webhook team lookup by `github_id` alone allows cross-organization team hijack, granting authorization bypass into `Shipit.github_teams` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves the target `Team` via `Team.find_or_create_by!(github_id: params.team.id)`, matching only on the numeric GitHub team id with no check that the payload's `organization.login` matches the team's stored `organization` [2](#0-1) . The webhook signature is verified per-organization using `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization', 'login')` for membership events [3](#0-2) , so in a multi-org Shipit deployment an attacker who controls their own onboarded GitHub organization can sign a membership payload with their own `webhook_secret`, but declare an arbitrary victim team's `github_id` inside it. Because the lookup ignores organization/slug, `team.add_member(member)` attaches the attacker's own user to the victim (privileged) `Team` row, and `User#authorized?` (`app/models/shipit/user.rb:81`) becomes true for that user.

### Finding Description
The intended binding is: `Membership(team_id: T, user_id: U)` should exist only if GitHub itself reports that `U` is a member of team `T`, where `T` belongs to the organization that GitHub attributes the event to. The actual binding enforced by the code is only: `Team.find_or_create_by!(github_id: params.team.id)` — a global, cross-tenant lookup with no clause tying it to `params.organization.login` [2](#0-1) .

Path: `POST /webhooks` with `X-Github-Event: membership` → `WebhooksController#create` → `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)`, and for membership payloads (no `repository` key) `repository_owner` resolves from `params.dig('organization', 'login')` [3](#0-2) . Each configured GitHub organization has its own `webhook_secret` (`GitHubApp#initialize`, `verify_webhook_signature`) [4](#0-3) . This means an attacker onboarded as an org in Shipit's `github:` config (a legitimate, unprivileged tenant in a multi-org install, per `docs/setup.md`'s "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) can compute a valid HMAC over a payload using only their own org's secret, while setting `organization.login` to their own org (to pass signature verification) and `team.id` to the numeric `github_id` of an existing privileged `Shipit::Team` (e.g. one in `Shipit.github_teams`, resolved via `Shipit.github_teams` / `Team.find_or_create_by_handle`) [5](#0-4) .

`MembershipHandler#process` then calls `find_or_create_team!`, which finds the pre-existing victim `Team` by `github_id` alone (the `organization:` assignment inside the block only runs on creation, never on the find branch) [6](#0-5) . It then resolves/creates the attacker's own `User` via `member.login` and calls `team.add_member(member)`, which appends the attacker's user to `team.members` unconditionally when action is `'added'` [7](#0-6) . This writes a `Membership` row that GitHub never actually reported for that team.

None of the documented guards prevent this: `verify_signature` only proves the request was signed by *some* configured organization's secret, not that the *referenced team* belongs to that organization [8](#0-7) ; `drop_unhandled_event` and the `ExplicitParameters` schema in `MembershipHandler.params` only validate shape/presence, not org/team consistency [9](#0-8) ; there is no `require_permission!`/`force_github_authentication` check in this webhook path at all.

### Impact Explanation
Once `Membership.exists?(team_id: victim_team.id, user_id: attacker_user.id)` is true and that team is included in `Shipit.github_teams`, `User#authorized?` returns true for the attacker's user for the entire Shipit instance [1](#0-0) , since `Shipit.github_teams` gates instance-wide authorization independent of any single stack/repository. This matches "escalation into `Shipit.github_teams` authorization" (High severity per the rubric), and is repeatable against any team whose `github_id` the attacker can learn/guess (GitHub team ids are small sequential integers), for as long as the attacker's own org remains a configured, signature-verifiable tenant.

### Likelihood Explanation
This requires Shipit to be configured for multiple GitHub organizations (per-org `github:` config block, as documented and covered by `test/dummy/config/secrets_double_github_app.yml`) and for the attacker to control (own/administer) one of those onboarded organizations — a legitimate but unprivileged tenant, matching the "unprivileged attacker" scope since they hold no Shipit secrets and are not in `Shipit.github_teams`. The attacker also needs the numeric `github_id` of the target team, which is not secret-equivalent but also not typically publicly enumerable without some GitHub access. Cost is low: one crafted, self-signed HTTP POST to `/webhooks`; no live GitHub call is needed since `find_or_create_by!` short-circuits when the team already exists.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (i.e. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally reject the event if an existing `Team` with that `github_id` has a different `organization` than the payload's — treating it as a mismatched/forged event rather than silently accepting it.

### Proof of Concept
```ruby
test ":membership from a different org cannot add members to another org's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: "shopify"
  Shipit.stubs(:github_teams).returns([victim_team])

  # Attacker controls "attacker-org", whose signature check passes independently.
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # or stub GitHubApp#verify_webhook_signature true for attacker-org

  attacker_login = 'attacker'
  @request.headers['X-Github-Event'] = 'membership'
  post :create, as: :json, body: {
    action: 'added',
    team: { id: victim_team.github_id, slug: victim_team.slug, name: victim_team.name, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: attacker_login },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json
  assert_response :ok

  attacker_user = User.find_by!(login: attacker_login)
  assert Membership.exists?(team_id: victim_team.id, user_id: attacker_user.id)
  assert attacker_user.authorized?
end
```
This demonstrates both sides of the binding diverge: no GitHub-side membership report ties `attacker` to `shopify/developers`, yet the `Membership` row and `authorized?` result assert it did.
