### Title
CCMenu endpoint bypasses ApiClient stack scoping, allowing a stack-restricted token to read state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token that is scoped to a single stack (`ApiClient#stack_id`) is meant to be restricted to reading/writing only that stack. `Shipit::Api::CCMenuController` overrides the shared `stack` lookup helper in a way that drops this scoping, so any client holding a token with the `read:stack` permission can retrieve build/status information for an arbitrary stack by supplying its `stack_id`, not just the stack the token was issued for.

### Finding Description
`Shipit::Api::BaseController` establishes the binding "token authorizes stack X" via: [1](#0-0) 

`stacks` filters to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that filtered relation, i.e. `stacks.from_param!(...)`. This is the mechanism that makes `ApiClient.stack` scoping meaningful for controllers like `TasksController` and `StacksController`.

`CCMenuController`, however, redefines `stack` to bypass this filter entirely and resolve directly against the full `Stack` table: [2](#0-1) 

It only declares `require_permission :read, :stack`, which is checked via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` only verifies the flat `permissions` list (e.g. `read:stack`) — it never checks `stack_id` against the requested resource. That check is entirely delegated to (and only implemented in) `BaseController#stacks`/`#stack`, which `CCMenuController` does not use for its `stack` lookup.

The result is a broken equality: **"stack the token authorizes" (`ApiClient#stack_id`) ≠ "stack the request actually touches" (`params[:stack_id]` resolved unscoped in `CCMenuController#stack`)**.

The fixture `here_come_the_walrus` demonstrates the intended restriction — a token scoped to the `shipit` stack with only `read:stack`: [4](#0-3) 

Existing tests confirm this scoping is enforced for `StacksController#index` (`"an api client scoped to a stack will only see that one stack"`): [5](#0-4) 

But no equivalent scoping/test exists for `CCMenuController`, and the code path structurally cannot enforce it since `stack` is redefined to ignore `stacks`.

### Impact Explanation
This is an unauthorized/unauthenticated-scope read of stack state: a token deliberately restricted by its owner (or the token issuer) to a single stack can be used to read the CI/build status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of **any** other stack managed by the Shipit instance, including stacks belonging to unrelated repositories/teams that the token was never meant to see. This falls under the defined High-impact bucket: "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
The attacker only needs a valid, minimally-scoped `read:stack` API token (which is the normal, least-privileged credential a Shipit admin would hand out for CI badge/status integrations) and knowledge or a guess of another stack's `stack_id`/`to_param`. No signature forgery, GitHub credentials, or elevated privileges are required — only the standard authenticated API client flow that CCMenu already supports (`params[:token]`), matching the rules' bounded threat model of an already-authenticated-but-under-scoped `ApiClient`.

### Recommendation
Remove `CCMenuController`'s private `stack` override, or make it delegate to the scoped `stacks` collection (`stacks.from_param!(params[:stack_id])`) exactly as `BaseController` does, so the `ApiClient#stack_id` scoping is honored consistently for every controller/action.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to stack `shipit` (`stack_id` set) with only `permissions: ['read:stack']`, mirroring the `here_come_the_walrus` fixture.
2. Using that client's `authentication_token`, call:
   `GET /shopify/other-repo/production/ccmenu.xml?stack_id=<other_stack_id>&token=<token>`
   (or via HTTP Basic auth as in `authenticate_api_client`).
3. `authenticate_api_client` in `CCMenuController` accepts the token via `params[:token]` and sets `@current_api_client` to the scoped client.
4. `require_permission :read, :stack` passes because the client has `read:stack` in its permission list — `check_permissions!` never looks at `stack_id`.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` against the entire `Stack` table (not `stacks`, which would have been filtered to the client's own `stack_id`), returning the unrelated stack.
6. The response renders that unrelated stack's build status/name/webUrl, even though the token was only ever authorized for the `shipit` stack.
