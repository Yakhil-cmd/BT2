### Title
Membership webhook trusts an unverified `organization` field, letting any configured org's signing key add users to another org's team-based authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a request against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')` only when no `repository` key is present). `MembershipHandler`, however, blindly trusts a *different* field of the same JSON body - `params.organization.login` - to decide which `Team#organization` a membership change applies to, with no cross-check that it matches the organization whose secret authenticated the request. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the SizeSealed bug class: one actor (the seller/holder-of-the-key) controls information/fields the protocol never actually binds together, letting them steer an outcome that other parties assume is honest. Here, the "signed" side of the request is only the raw HTTP body checked against the HMAC produced with `Shipit.github(organization: repository_owner).verify_webhook_signature` - i.e., it proves the payload came from the GitHub App installation for *whatever org `repository_owner` resolves to*. It does **not** prove anything about the separate `organization.login` field inside the same JSON body.

`MembershipHandler#find_or_create_team!` uses `params.organization.login` (not `repository_owner`) to set `team.organization`: [3](#0-2) 

Real GitHub `membership` events do not include a `repository` object, so in production `repository_owner` normally falls back to `params.dig('organization', 'login')`, keeping the two values naturally in sync. But nothing in `WebhooksController` or `MembershipHandler` enforces that equality. An attacker who legitimately controls a GitHub App installation for **any** organization configured in Shipit's multi-org `github:` secrets (able to compute a valid `X-Hub-Signature` with that org's `webhook_secret`) can craft a `membership` webhook payload that includes a `repository.owner.login` matching the org they control (so `verify_webhook_signature` passes with their own secret), while setting `organization.login` and `member.login` to reference a *different, victim* organization/team. `MembershipHandler` will then create/update a `Team` record scoped to the victim organization and add the attacker-chosen user (which can be the attacker's own GitHub identity) to it.

Team membership is exactly what governs Shipit's access-control boundary: [4](#0-3) 

So a `Team` whose `organization`/`slug` matches an entry in `Shipit.github_teams` grants login access when the attacker (or an account they control) is added as a member - despite the signature only proving trust for a completely unrelated organization.

### Impact Explanation
This breaks the binding "organization that authenticated" == "organization that is written," letting an attacker who controls a legitimately-configured but unrelated GitHub App forge team-membership state for a victim organization. Because `User#authorized?` gates all application access on `Shipit.github_teams` membership, this is a direct escalation into `Shipit.github_teams` authorization - one of the explicitly listed High-impact categories - potentially enabling unauthorized login/access to stacks, deploys, and task output for organizations the attacker was never granted access to.

### Likelihood Explanation
Exploitability requires only that Shipit is configured with more than one GitHub organization (the documented multi-org `github:` secrets layout) and that the attacker controls (or is an admin of) any one of those configured orgs' GitHub App installations - no Shipit session, `ApiClient` token, or access to the victim org's repository/webhook secret is required. This is a realistic deployment pattern documented in `docs/setup.md`'s "Using Multiple GitHub Applications" section.

### Recommendation
In `WebhooksController#verify_signature`, do not let the payload freely choose which secret authenticates it against unrelated payload fields; instead, derive `repository_owner` consistently and pass the *authenticated organization* into each handler (e.g., attach `verified_organization` to the params/request) so `MembershipHandler#find_or_create_team!` can assert `params.organization.login == verified_organization` before creating/mutating any `Team`, rejecting mismatches with a 422.

### Proof of Concept
1. Shipit is configured with two orgs in `config/secrets.yml`: `attacker-org` (attacker controls the installed GitHub App and knows its `webhook_secret`) and `victim-org` (has a `Team` referenced in `Shipit.github_teams`).
2. Attacker crafts a `membership` event JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Victim Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature` (`sha1=...`) over the raw body using `attacker-org`'s webhook secret and POSTs to `/github_hooks` (or the Shipit webhooks endpoint) with `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org` (via `params.dig('repository','owner','login')`) and verifies successfully against `attacker-org`'s secret.
5. `MembershipHandler#process` runs, creating/finding `Team` with `organization: "victim-org", slug: "admins"` and adds `attacker-github-login` as a member via `team.add_member(member)`.
6. If `victim-org/admins` is listed in `Shipit.github_teams`, the attacker's GitHub account now passes `User#authorized?` and gains access to Shipit as if they were a real member of the victim org's team.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

            requires :login, String

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
