### Title
Membership webhook `team.id` lookup lets any tenant org with a valid `webhook_secret` graft a forged `Membership` onto another tenant's `Team`, crossing the webhook-provenance boundary - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` resolves the target `Team` solely by the attacker-supplied `params.team.id` (an integer GitHub team id), independent of which organization's `webhook_secret` verified the request. Because `Team.find_or_create_by!(github_id: ...)`'s block (which sets `team.organization`) only executes on record creation and never on lookup, a webhook correctly signed with Org A's real `webhook_secret` can still mutate a pre-existing `Team` belonging to Org B, adding an attacker-chosen `User` to that team's `memberships` and flipping `User#authorized?` for `Shipit.github_teams`.

### Finding Description
The broken binding: `organization whose webhook_secret verified request body (repository_owner from params) == organization owning the Team the handler mutates`.

Path:
1. `WebhooksController#verify_signature` derives `repository_owner` purely from the JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then fetches `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against that org's `webhook_secret` [2](#0-1) . This only proves the request was signed by *some* configured org's secret — the org named in `organization.login`/`repository.owner.login` is attacker-controlled body content, not a cryptographically bound value.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end` [3](#0-2) . `find_or_create_by!`'s block only runs when a *new* record is created; if a `Team` with that `github_id` already exists (e.g., pre-synced via `Shipit.github_teams`/`Team.find_or_create_by_handle` for a legitimate different organization), the existing record — bound to its real organization — is returned untouched.
3. `team.add_member(member)` / `team.members.delete(member)` is then executed unconditionally on that resolved `Team` [4](#0-3) , [5](#0-4) .
4. `User#authorized?` grants Shipit access based on membership in `Shipit.github_teams` teams: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) .

Exploit: attacker legitimately controls GitHub Org A, which is one tenant configured in Shipit's multi-org `secrets.github` map (each org has its own `webhook_secret`, as shown by the two-org fixture `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml` pattern) [7](#0-6) . Attacker knows Org A's real `webhook_secret` (they configured/own that GitHub App). They send `POST /webhooks` with header `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "team": { "id": <OrgB's real Team github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "OrgA" },
  "member": { "login": "attacker-controlled-login" }
}
```
signed with `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)`. `verify_signature` looks up Org A by `organization.login` and succeeds. `MembershipHandler` then finds the *existing* `Team` row for Org B by `github_id` and adds the attacker's chosen member to it — a write to Org B's tenant data authenticated only by Org A's credential. `drop_unhandled_event`, `ExplicitParameters` schema, and model validations do not check that `params.organization.login` matches the `Team#organization` actually mutated, so none of the existing guards catch this divergence.

### Impact Explanation
An attacker who is a legitimate operator of one tenant org (Org A) in a multi-org Shipit deployment can add an arbitrary `User` record (any GitHub login they choose, including their own) as a member of any pre-existing `Shipit::Team` whose numeric `github_id` they can learn (GitHub team ids are visible via the GitHub API/UI to org members and are not secret), even if that `Team` belongs to a completely different organization (Org B) they have no relationship with. Since `Shipit.github_teams` membership drives `User#authorized?`, this is a direct escalation into the `Shipit.github_teams` authorization gate for Org B's tenant — matching the High severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any `Team` record whose `github_id` is known, for as many memberships as desired, from Org A's webhook endpoint alone.

### Likelihood Explanation
Preconditions: (1) Shipit configured for multiple GitHub organizations, each with its own `webhook_secret` (a documented, supported multi-tenant configuration) [8](#0-7) ; (2) attacker legitimately controls/administers at least one of those orgs and thus knows its real `webhook_secret`; (3) target `Team` row for a different org already exists in the DB (populated via `Shipit.github_teams`/`oauth.teams` sync) [9](#0-8) ; (4) the target team's numeric `github_id` is discoverable. All are realistic in a shared, multi-tenant Shipit install serving several orgs with a restricted `oauth.teams` allowlist — exactly the scenario the `github_teams` feature is designed for. Attacker cost is a single crafted, self-signed HTTP POST; no GitHub-side action or live GitHub API access is required.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the org that signed the webhook (the org resolved in `verify_signature`, e.g. by passing it through to the handler) matches the `Team#organization` of any *existing* record before mutating it, and reject/no-op when they diverge. At minimum, `find_or_create_by!` should also validate `existing_team.organization == params.organization.login` (case-insensitively) and raise/skip if not, rather than silently mutating a team whose organization doesn't match the webhook's own claimed organization/signing org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test, two-tenant setup)
test ":membership from Org A's verified webhook cannot mutate Org B's team" do
  org_a_secret = "org-a-secret"
  org_b_team = shipit_teams(:shopify_developers) # belongs to organization "shopify" (Org B)

  # Configure two distinct tenants with distinct webhook secrets
  Shipit.stubs(:github).with(organization: "org-a").returns(
    Shipit::GitHubApp.new("org-a", webhook_secret: org_a_secret)
  )

  body = {
    action: "added",
    team: { id: org_b_team.github_id, name: org_b_team.name, slug: org_b_team.slug, url: org_b_team.api_url },
    organization: { login: "org-a" },       # signed org == Org A
    member: { login: "attacker-controlled" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_secret, body)

  @request.headers["X-Github-Event"] = "membership"
  @request.headers["X-Hub-Signature"] = signature

  assert_no_difference -> { org_b_team.reload.organization } do
    assert_difference -> { org_b_team.members.count }, 0 do # EXPECTED after fix: no change
      post :create, body: body, as: :json
      assert_response :ok
    end
  end

  # Binding check: organization that signed (org-a) must equal organization owning mutated team
  refute_equal "org-a", org_b_team.reload.organization
  # Before fix: org_b_team.members now includes "attacker-controlled" despite org-a's signature -> vulnerability
end
```
This test asserts the WEBHOOK PROVENANCE equality (`"org-a" == org_b_team.organization`) is false, and shows the current handler still writes the membership despite the mismatch — demonstrating the cross-tenant authorization escalation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
