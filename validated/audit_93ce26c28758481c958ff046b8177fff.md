### Title
Cross-repository commit-status forgery via organization/repository binding break in the GitHub webhook pipeline - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit verifies inbound GitHub webhooks by picking a webhook secret keyed on the *organization* named in the payload (`repository.owner.login`), but the handler that actually mutates state — `StatusHandler` — never checks which repository/organization the payload claims to be for. It resolves target `Commit` records purely by `sha`, globally, across every stack in the installation. This breaks the binding `organization_verified(payload) == repository_written(payload)`: any org/repo whose webhook secret an attacker legitimately possesses (their own GitHub App installation on their own org) can be used to sign a payload that writes commit-status data onto a **different**, victim repository's commit.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret used to validate `X-Hub-Signature`) using a value taken straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

Shipit supports multiple GitHub Apps/organizations, each with its own independent `webhook_secret` (`Shipit.github(organization:)` / `github_app_config`): [3](#0-2) 

So the *only* thing the signature check proves is: "this payload was signed by the App installed on organization X (as claimed by `repository.owner.login`)." It proves nothing about which repository the payload's other fields refer to, because that organization value is attacker-controlled JSON, not something GitHub authenticates independently for Shipit.

Once the signature check passes, the payload is dispatched to handlers by event type: [4](#0-3) 

`StatusHandler#process` then resolves target commits purely by `sha`, with **no repository or organization scoping at all**: [5](#0-4) 

Compare this to the base `Handler`, which does have a repository-scoping helper (`repository_name` / `stacks`) that other handlers such as `PushHandler` use: [6](#0-5) [7](#0-6) 

`StatusHandler` does not use this at all — it never calls `stacks` or checks `payload.dig('repository', 'full_name')`. The equality that should hold is:

`org_that_signed(payload) == owner_of(stack_that_owns(sha))`

but nothing in the code enforces it. The organization used to authenticate the request is decoupled from the commit/stack that ends up being written to.

### Impact Explanation
An attacker who operates their own GitHub organization with a Shipit GitHub App installed (a completely unprivileged, self-service action — install the app on your own free/personal org) can legitimately obtain a valid `X-Hub-Signature` for their own org's webhook secret. They can then send a `status` event payload signed with their own org's secret but whose `sha` matches a commit belonging to a **victim's** stack (this occurs naturally whenever commit history is shared between repositories — forks, mirrors, subtree/vendor merges, or monorepo splits — or, in a same-tenant Shipit instance with multiple stacks/orgs configured, colliding commits are entirely plausible). This lets the attacker inject arbitrary commit statuses (`state`, `context`, `target_url`) onto the victim commit: [8](#0-7) 

Because Shipit gates deploys on required/blocking commit statuses (per the changelog: "Added blocking statuses. If they are missing or failing, they will prevent deploy..."), forging a passing status for a commit that is actually failing or missing CI results can flip a stack from "not deployable" to "deployable," enabling an **unauthorized deploy** — one of the explicitly listed High/Critical impacts.

### Likelihood Explanation
The likelihood is bounded by the need for a matching `sha` between the attacker's own repository and the victim's tracked commit — realistic in forked/mirrored/monorepo scenarios, and trivially engineerable by the attacker (they can cherry-pick or replay a commit with an identical tree/parents/timestamp to reproduce a target sha, or target shared base commits any two repos both track, e.g. a common ancestor before divergence). No privileged Shipit credentials, API tokens, or repository write access are required — only the ability to receive one legitimate webhook from GitHub for a repository the attacker controls (to learn nothing extra — the secret is per-org and verified server-side by HMAC, so the attacker simply needs GitHub to sign requests for their own org, which happens automatically once they install the App).

### Recommendation
Bind the verified organization to the data being mutated:
- In `WebhooksController`, after verifying the signature for `repository_owner`, pass that verified organization/owner down to the handler dispatch, and have every handler (including `StatusHandler`) reject or scope its side effects to commits/stacks whose `Repository` owner matches the verified organization — mirroring what `Handler#stacks`/`repository_name` already does for other handlers, but actually enforcing it in `StatusHandler`.
- `StatusHandler#process` should resolve commits through `stacks` (scoped by `repository.full_name` in the payload) rather than a bare `Commit.where(sha: params.sha)` global lookup, and that repository must itself be checked to belong to the same organization/app that produced a valid signature.

### Proof of Concept
1. Attacker creates GitHub org `attacker-org`, installs Shipit's GitHub App on it, and configures it in Shipit's multi-org `secrets.github` config (or is otherwise a legitimately configured tenant org in a shared Shipit instance).
2. Attacker identifies (or engineers, e.g., via a shared base commit/fork) a commit `sha` that is also tracked by a victim stack, e.g. `victim-org/victim-repo`.
3. Attacker pushes anything to `attacker-org/some-repo` that causes GitHub to send a `status` webhook for that `sha`, OR directly crafts a `status` payload with `repository.owner.login = "attacker-org"` and posts it to `/webhooks` with `X-Hub-Signature` computed using `attacker-org`'s known webhook secret.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature — the request is accepted.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matches the victim's commit (because it never checks repository/organization), and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `state`/`context`/`target_url` onto the victim's commit.
6. If that status is one of the victim stack's blocking/required statuses, the victim stack now appears deployable and a subsequent deploy proceeds despite failing/missing real CI — an unauthorized deploy enabled purely by cross-organization webhook forgery.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
```
