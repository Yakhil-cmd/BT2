### Title
Webhook signature verified against attacker-selectable organization but subsequent processing acts on an unrelated `repository.full_name` from the same unauthenticated JSON body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to HMAC-verify the webhook against using a value read directly out of the untrusted, still-unverified request body (`repository_owner`), then, once verification against *that org's* secret succeeds, `Handler#stacks`/`#repository_name` acts on a completely independent field of the same body (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. Nothing binds the organization whose secret validated the signature to the repository that the handler subsequently writes to.

### Finding Description
`verify_signature` derives the signing org from the payload itself, before the signature has been checked: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: ...)` looks up per-org config (`app_id`, `webhook_secret`, etc.) as documented for multi-tenant setups where each GitHub organization has its own App and its own `webhook_secret`: [3](#0-2) 

The HMAC check itself is correct in isolation: [4](#0-3) 

However, once verification succeeds, `create` hands the raw parsed JSON to every registered handler: [5](#0-4) 

Handlers resolve the target `Repository`/`Stack` using a *different* field of the same body, `repository.full_name`, with no re-check that it belongs to the organization whose secret validated the signature: [6](#0-5) [7](#0-6) 

`repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target `Stack`) are two independently attacker-controlled JSON fields inside a single request body that the attacker fully controls (they only need a secret for *some* org configured on the instance, not the target org). Concretely, `PushHandler#process` will call `stack.sync_github(expected_head_sha:)` and `StatusHandler#process` will call `commit.create_status_from_github!(params)` on whatever `Stack`/`Commit` is found via `full_name`, regardless of which org's secret was used to authenticate the request: [8](#0-7) [9](#0-8) 

This breaks the intended binding: `organization whose webhook_secret authenticated the request == organization owning the repository the handler mutates`. In a single-organization deployment this is unreachable because there is only one secret. It becomes reachable specifically in the documented "Using Multiple GitHub Applications" configuration, where several independent GitHub organizations are configured on one Shipit instance, each with its own `webhook_secret`: [3](#0-2) [10](#0-9) 

An operator/admin of `OrgTwo` (who legitimately knows `OrgTwo`'s `webhook_secret` because they administer that GitHub App installation) can send a forged webhook whose `repository.owner.login`/`organization.login` is `"OrgTwo"` (so `verify_signature` selects and validates against `OrgTwo`'s secret) but whose `repository.full_name` is `"OrgOne/victim-repo"` (a repository belonging to an entirely different tenant, `OrgOne`, tracked by the same Shipit instance). The signature check passes because it is only checking "was this raw body HMAC-signed by *a* secret configured for the org named in the body," not "does the org that signed this match the repo being acted upon."

### Impact Explanation
This lets a party who only controls one tenant/organization's webhook secret forge `push`, `status`, and `check_suite` events that are acted on for another tenant's stacks:
- Forged `push` events force `Stack#sync_github` to run against arbitrary `expected_head_sha` for a victim stack, effectively steering deploy state.
- Forged `status` events call `Commit#create_status_from_github!`, letting the attacker fabricate a passing/failing CI status on a victim's commit. Since Shipit stacks commonly gate/allow deploys based on required CI statuses, this can be used to make an unmerged/unvetted commit appear CI-green to influence the deploy pipeline of a repository the attacker does not control.
- Forged `check_suite` events trigger `RefreshCheckRunsJob` against a victim stack's commits.

This crosses a repository/authentication trust boundary between tenants of the same Shipit instance without any repository write access or session on the victim org, matching the "unauthorized deploy" / cross-repository-write impact class. It only applies to multi-org installations (the documented "Using Multiple GitHub Applications" configuration); in a single-org deployment there is no other org's secret to abuse, so this is not exploitable there.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (b) the attacker to be a legitimate holder of at least one configured org's `webhook_secret` (e.g., an admin of one tenant org's GitHub App) targeting another tenant's repositories on the same instance. This is a realistic scenario for shared/managed Shipit deployments serving multiple business units or customers, but it is not exploitable by a fully anonymous, unprivileged attacker with zero relationship to the platform - it requires possession of *some* valid org's webhook secret, which the report-provided rules permit as "unprivileged" relative to the *target* organization.

### Recommendation
After signature verification succeeds, re-derive the organization from the verified request and cross-check it against `repository.full_name`'s owner before dispatching to handlers - e.g., reject the request if `repository_owner` (the value the secret was selected on) does not case-insensitively match the owner segment of `repository.full_name`/`organization.login`. Alternatively, have handlers resolve `Repository`/`Stack` scoped by the already-verified organization rather than trusting `repository.full_name` from the unauthenticated body.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows `OrgTwo`'s `webhook_secret` (e.g., an admin of the `OrgTwo` GitHub App installation), craft a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=` HMAC-SHA1 of the raw body using `OrgTwo`'s `webhook_secret`.
4. POST to `Shipit::WebhooksController#create` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'OrgTwo')` and validates successfully against `OrgTwo`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('OrgOne/victim-repo')` (unrelated to `OrgTwo`) and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on the victim `OrgOne` stack, despite the attacker never holding `OrgOne`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
