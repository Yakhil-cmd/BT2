### Title
Stale/Freed Cache-Entry Dereference in AA Secondary-Trigger Revert Path Can Crash Node or Desync Unstable-Unit Cache - (File: aa_composer.js)

### Summary
`revertResponsesInCaches()` is invoked from `revert()` whenever a chain of secondary AA triggers bounces or fails after one or more response units have already been posted and cached in `storage.assocUnstableUnits` [3](#0-2) . It grabs `parent_units` off the cache entry for only the *first* unit in `arrResponseUnits` and then calls `storage.forgetUnit` on every unit in the array in a single pass, without re-validating that each entry is still present in `assocUnstableUnits` at the time it is dereferenced [4](#0-3) . `forgetUnit` unconditionally reads `assocUnstableUnits[unit].parent_units` for every unit passed to it [5](#0-4) , so if any response unit in the chain has already been forgotten/removed from the cache (e.g., a duplicate unit reference, a secondary trigger revert nested inside another revert, or a race where `main_chain.updateMainChain`/stabilization concurrently removed the entry from `assocUnstableUnits` for that mci), the lookup returns `undefined` and the subsequent `.parent_units` access throws a TypeError from inside the AA-trigger execution pipeline that runs under the `handleJoint`/`aa_triggers` mutex, crashing that codepath. This mirrors the CVE's use-after-free class of bug: a data structure (here, an in-memory unit-cache entry that is functionally "freed" by `forgetUnit`/deleted from `assocUnstableUnits`) is dereferenced again after being invalidated during a normal multi-step lifecycle (secondary-trigger cascade revert), reachable by any address that can trigger an AA with nested secondary triggers that end up bouncing.

### Impact Explanation
A crash in the AA-trigger execution path (which runs while holding the `['aa_triggers']` and `['handleJoint']` mutexes and inside the transaction that stabilizes an MCI) halts unit processing for the whole node, preventing it from confirming any new units until restarted — this is a network-availability impact consistent with the "Medium" severity of the reference CVE, whose worst case is escalated impact from a bad pointer dereference inside process memory. Because the revert logic is fired only when previously-added responses/units must be discarded from the AA-response chain, an attacker who can shape a trigger chain to hit this stale-cache situation can repeatedly stall stabilization and DoS the node's ability to make progress on new units.

### Likelihood Explanation
Exploitability requires shaping an AA (or chain of AAs invoked via secondary triggers) so that the revert path in `revert()`/`handleSecondaryTriggers()` is exercised after some response units for the trigger have already been recorded in `arrResponses` and their `objAAResponse.response_unit` fields populated, then causing the overall trigger evaluation to fail (e.g., a downstream secondary AA bouncing with an error) — any address is free to post units triggering AAs, so the surface is broadly reachable, but hitting the exact ordering where a response unit is no longer present in `assocUnstableUnits` at the moment `revertResponsesInCaches` runs (rather than being cleanly rolled back) requires a specific interleaving of secondary-trigger chains and cache state, making this a real but non-trivial-to-trigger condition, consistent with the CVSS AC:H rating of the referenced CVE.

### Recommendation
In `revertResponsesInCaches` (`aa_composer.js`), guard every dereference of `storage.assocUnstableUnits[unit]` before use: skip or short-circuit when the lookup for `first_unit` (or any subsequent unit in `arrResponseUnits`) is `undefined`, and change `storage.forgetUnit` (`storage.js`) to be defensive by checking `assocUnstableUnits[unit]` exists before accessing `.parent_units`, rather than assuming the cache entry is always present for every unit it's asked to forget. Add a regression test that triggers a secondary-AA revert after a mixed sequence of already-cached and already-forgotten response units to ensure the revert path is idempotent and does not throw.

### Proof of Concept
1. Deploy a primary AA that, on success, invokes two chained secondary AAs where the first one successfully posts a response unit (adding it to `storage.assocUnstableUnits` and to `arrResponses`) and the second one bounces with an error, causing `handleSecondaryTriggers`'s `async.eachSeries` callback to call `revert()` on the primary trigger [6](#0-5) .
2. In `revert()`, `revertResponsesInCaches(arrResponses)` is called, which reads `storage.assocUnstableUnits[first_unit].parent_units` and then calls `forgetUnit` on all response units [7](#0-6) .
3. Craft the trigger chain so a response unit referenced in `arrResponses` (e.g., a duplicate secondary bounce target that produced an earlier response with the same `response_unit`, or one whose cache entry was concurrently evicted by a stabilization pass running in `markMcIndexStable`) is no longer present in `assocUnstableUnits` when `revertResponsesInCaches` executes.
4. The `.parent_units` access on `undefined` throws, propagating out of the mutex-held AA trigger handling code in `handlePrimaryAATrigger`/`handleAATriggers` [8](#0-7) , crashing/halting the node's unit-processing loop.
