### Title
Cross-repository CI status injection via unscoped SHA lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The webhook signature verification in `WebhooksController` binds a request to a single GitHub organization (`Shipit.github(organization: repository_owner)`), but the `status` event handler, `Shipit::Webhooks::Handlers::StatusHandler`, does not re-apply that organization/repository binding when looking up which `Commit` records to mutate. It matches purely on the git SHA across the entire `commits` table, globally, regardless of which stack/repository/organization that SHA actually belongs to.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization used to check the HMAC signature purely from the untrusted-until-verified-body field `repository.owner.login` (or `organization.login`) via `repository_owner`: [1](#0-0) [2](#0-1) 

Once the signature check passes for that organization, the controller dispatches to handlers purely keyed on the `X-Github-Event` header, passing the raw parsed JSON body: [3](#0-2) 

Compare how `PushHandler` (a correctly-scoped handler) resolves target stacks: it goes through a `stacks` relation (scoped to the repository the webhook was signed for) before acting: [4](#0-3) 

`StatusHandler`, however, looks up commits **by SHA only**, with no repository/stack/organization scoping at all: [5](#0-4) 

`Commit.where(sha: params.sha)` searches the entire `commits` table across every stack managed by this single Shipit instance (which can span multiple repositories and multiple GitHub organizations, as documented in the "Using Multiple GitHub Applications" configuration). Because a 40-character git SHA is unique per-content but is public information (visible on GitHub for any repo), an operator holding a legitimately signed webhook for **their own** organization/repo (Org A) can submit a `status` event whose `sha` field is copied from a **different** repository/stack (Org B, e.g. some other Github org/repository also hosted on the same Shipit instance) that they have no authorization to write to. `create_status_from_github!` will then be invoked on Org B's commit: [6](#0-5) 

### Impact Explanation
`Commit#create_status_from_github!` → `add_status` triggers stack-level side effects that can advance continuous delivery / the merge queue for the *victim* stack: [7](#0-6) 

Specifically, injecting a fake "success" status for a target commit calls `stack.schedule_merges if new_status.pending? || new_status.success?`, and also fires `deployable_status`/`commit_status` webhooks. In stacks that gate continuous deployment or the merge queue on CI status (`StatusChecker`, `MergeRequest#all_status_checks_passed?`), an attacker who only controls a webhook signed for Org A can forge a passing status for an already-known commit SHA belonging to Org B's stack, unblocking that stack's automatic merge/deploy pipeline. This breaks the binding "the organization that authenticated the webhook" versus "the repository whose commit status is written," resulting in cross-repository writes and potential unauthorized deploys/merges — matching the Critical impact bar in scope.

### Likelihood Explanation
Exploitation requires the attacker to control (or be authorized to trigger) a webhook for *some* organization/repository configured on the Shipit instance — i.e., they need a legitimately signed delivery from their own installed GitHub App/org, which is a realistic scenario for any multi-tenant Shipit deployment (the "Using Multiple GitHub Applications" setup documented in `docs/setup.md`, and used by e.g. `test/dummy/config/secrets_double_github_app.yml`). No secret of the victim organization is required, and the target SHA is public knowledge (any commit hash visible via `git log`/GitHub UI on the victim repo). This is not privileged beyond having installed the app for any one org on the shared instance.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up `Commit`/`Stack` records) to the repository/organization the webhook was actually verified for. Concretely, restrict the lookup to `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: params.repository_name })`, mirroring the scoping already used by `PushHandler`'s `stacks` relation, instead of a global `Commit.where(sha:)`.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple GitHub Applications").
2. Attacker controls (or is the admin of) `OrgA`'s installation and can therefore produce validly-signed webhook deliveries for `OrgA`.
3. Attacker looks up a pending/unmerged commit SHA belonging to `OrgB`'s stack (public information, e.g. from GitHub's UI/API).
4. Attacker sends a `status` webhook event, signed with `OrgA`'s `webhook_secret`, with body:
```json
{
  "sha": "<victim OrgB commit sha>",
  "state": "success",
  "context": "ci/whatever",
  "repository": { "owner": { "login": "OrgA" } }
}
```
5. `WebhooksController#verify_signature` verifies the signature against `OrgA`'s secret and passes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgB` commit, and calls `create_status_from_github!`, marking it "success" and potentially unblocking `OrgB`'s merge queue/continuous deployment — despite the attacker having no access to `OrgB`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      end
