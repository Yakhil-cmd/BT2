### Title
Webhook signature is verified against the GitHub App config selected by the untrusted `repository.owner.login` field, while the event is processed against the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body. The event handlers that actually mutate state (`PushHandler`, `StatusHandler`, etc.) instead resolve the target `Stack`/`Commit` using `repository.full_name`, a completely independent field from the same untrusted body. Because these two fields are never checked against each other, and `GitHubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as automatic success, an attacker can pick an `owner.login` value that maps to an organization with no `webhook_secret` configured (or no config at all is not enough - it must be a *configured* org with a blank secret) while pointing `repository.full_name` at a real, different, and secret-protected stack.

### Finding Description
- `WebhooksController#verify_signature` resolves the app purely from `repository_owner`, read from the JSON payload itself: [1](#0-0)  and [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved app's `webhook_secret` is blank: [3](#0-2) .
- The engine explicitly supports multi-organization configuration where each org has its own (optionally blank) `webhook_secret`, resolved case-insensitively via `Shipit.github_app_config`: [4](#0-3) , exactly as documented and tested for `OrgOne`/`OrgTwo` setups: [5](#0-4) [6](#0-5) .
- Once `verify_signature` passes (or is bypassed), `Handler#stacks`/`#repository_name` resolves the target repository/stack from a **different** payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [7](#0-6) .
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack/branch found via that resolved repository: [8](#0-7) . `StatusHandler` similarly writes a `Status` onto any `Commit` matching an attacker-supplied `sha`, independent of organization: [9](#0-8) .

This is the exact analog of the audited bug class: a value used to authenticate the request (`repository.owner.login`, which selects the verifying secret) is never bound to the value the write path actually acts on (`repository.full_name`). The binding that should hold — "organization whose secret authenticated the request" == "organization owning the repository being written to" — is broken because both are attacker-controlled fields inside the same unsigned-selection JSON body, and the controller trusts the former for auth while the handlers trust the latter for the write.

### Impact Explanation
If any organization is configured in `secrets.github` (multi-org schema) with `webhook_secret` unset/blank — a state the shipped example config explicitly ships as the default (`webhook_secret: # nil`) in `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml` — an unauthenticated attacker can craft a webhook `POST` with:
- `X-Github-Event: push` (or `status`)
- payload `repository.owner.login` = the blank-secret organization
- payload `repository.full_name` = the real full name of a stack belonging to a different, secret-protected organization

`verify_signature` will resolve `Shipit.github(organization: <blank-secret org>)`, whose `verify_webhook_signature` short-circuits to `true` regardless of the `X-Hub-Signature` header, and the request is then dispatched to `PushHandler`/`StatusHandler`, which act on the real target stack using `repository.full_name`. This lets an attacker trigger `Stack#sync_github` (forcing a GitHub resync to an attacker-chosen `expected_head_sha`) or forge a commit `Status`, without possessing any of the org's webhook secret — an unauthorized action on a stack the attacker never authenticated against, corresponding to "an organization that authenticated versus the repository that is written" binding failure listed in scope.

### Likelihood Explanation
This requires the instance to run the multi-organization GitHub App configuration with at least one org left without a `webhook_secret` (this is the documented/shipped default in the example configs, so operators following the setup docs without setting every org's secret are exposed). Given that precondition, exploitation needs no credentials, no repository access and no prior authentication — only knowledge of a target stack's `repository.full_name`, which is public information visible in the Shipit UI/API.

### Recommendation
Bind the value used to select the verifying `webhook_secret` to the same repository the handlers act on: derive/require the organization from `repository.full_name` (or verify `repository.owner.login` equals the owner segment of `repository.full_name`) before selecting the `GitHubApp`, and reject requests whose owner/full_name fields disagree. Additionally, do not treat a blank `webhook_secret` as automatic verification success for organizations that are explicitly configured (only fall back like this for the single-app "no config" schema), or require `webhook_secret` to be present for every org entry.

### Proof of Concept
1. Configure `secrets.github` with two orgs: `OrgOne` (has a real `webhook_secret`, owns Stack `OrgOne/prod-repo`) and `OrgTwo` (no `webhook_secret` set, per the shipped example config).
2. Send: `POST /github/webhooks` with header `X-Github-Event: push`, an arbitrary/absent `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/prod-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`; since `OrgTwo.webhook_secret` is blank, `verify_webhook_signature` returns `true` for any/no signature (`lib/shipit/github_app.rb` lines 76-83).
4. `PushHandler#stacks` resolves via `repository.full_name` = `"OrgOne/prod-repo"` (`handler.rb` lines 32-38), and `sync_github(expected_head_sha: ...)` is invoked on the real `OrgOne` stack, entirely bypassing `OrgOne`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
