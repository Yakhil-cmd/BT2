## Analysis

The Tezos report's root issue — a UI blindly signs attacker-supplied opaque data (`req.prompt`) and returns the signature to an attacker-supplied endpoint (`req.callback`), with no domain separation preventing reuse of the signature for spending funds — has a direct structural analog in `ocore`.

### Root cause chain

**1. Wallets sign arbitrary attacker-controlled payloads on request from a paired device**

The `"sign"` message handler in `wallet.js` lets *any already-paired correspondent device* ask the local wallet to sign a `signed_message`, which can be **any JSON object** — its only structural check is that the unit contains nothing but `["signed_message", "authors", "version"]`: [1](#0-0) [2](#0-1) 

No validation of *what* is inside `signed_message` is performed by `ocore` — it is passed straight to the GUI's `signing_request` event for user approval, exactly like the Tezos dialog that just forwards `req.prompt` to be signed.

**2. The signature carries no domain separation / purpose tag**

`objectHash.getSignedPackageHashToSign()` hashes only `signed_message`, `authors`, `last_ball_unit`, and `version` — nothing that binds the signature to a specific AA, application, or purpose: [3](#0-2) 

**3. `is_valid_signed_package()` lets any AA accept such a blindly-signed message as authorization**

`formula/evaluation.js`'s `is_valid_signed_package` opcode only checks that the object was validly signed by the claimed address — it enforces no binding to the specific AA instance or purpose: [4](#0-3) 

**4. Official example AAs demonstrate inconsistent domain separation, proving the gap is real and exploitable**

`payment_channels.oscript` *manually* adds a `channel` field and checks it against `this_address` to stop replay across channels: [5](#0-4) 

But `order_book_exchange.oscript`, the other official reference implementation, uses `is_valid_signed_package` on an "order" object (`address`, `sell_asset`, `buy_asset`, `sell_amount`, `price`) with **no domain/application identifier at all**: [6](#0-5) 

This shows that `ocore` provides no protocol-level protection or even a convention against reusing a "blind" signature across different AA instances or applications — it is left entirely to each oscript author's discipline, and the framework's own sample code is inconsistent about it.

### Title
Blind-signing of arbitrary `signed_message` payloads via paired-device "sign" requests enables cross-AA signature replay and unauthorized fund movement - (File: wallet.js, signed_message.js, formula/evaluation.js)

### Summary
`ocore`'s device-to-device `"sign"` protocol lets any paired correspondent device request the wallet to sign an arbitrary, unstructured `signed_message` object. The resulting signature (`is_valid_signed_package` in oscript) carries no protocol-enforced domain separation (no AA address, app id, or purpose tag baked into the hash), so a signature obtained by a malicious counterparty under an innocuous pretext can be replayed into any AA that accepts `is_valid_signed_package` for a matching field-shape, moving funds the user never knowingly authorized.

### Finding Description
The `"sign"` case in `wallet.js` accepts a `signed_message` unit from a paired device with only a shallow structural check (`hasFieldsExcept`) and forwards it to the UI's `signing_request` event without validating or displaying what the object semantically represents. `objectHash.getSignedPackageHashToSign()` hashes only the message content, authors, and `last_ball_unit` — it never binds the signature to the specific AA/application that will later consume it via `is_valid_signed_package`. Consequently, whether a given signed message is safe to reuse depends entirely on each oscript author remembering to add their own domain tag (as `payment_channels.oscript` does with its `channel` field) — a discipline that the framework does not enforce and that the officially shipped `order_book_exchange.oscript` sample does not follow.

### Impact Explanation
A user who is paired with an attacker's device (e.g., a "trading partner," support bot, or textcoin/chat contact) can be induced to sign a message they believe serves one purpose. If that same address also participates in another AA that calls `is_valid_signed_package` on an object with an overlapping/compatible shape (or the same AA is instantiated multiple times without per-instance domain tags, as `order_book_exchange.oscript` illustrates), the attacker can submit the harvested signature as a trigger to withdraw or reallocate the victim's AA-held balance — resulting in unauthorized fund loss from an AA, matching the "AA fund loss" impact category.

### Likelihood Explanation
Requires the attacker to first become a confirmed correspondent ("paired device") of the victim — a normal, low-friction interaction pattern (adding a trading contact, exchange bot, or chat partner) that a legitimate-looking AA-based service would routinely ask for. Once paired, sending a `"sign"` request with a crafted `signed_message` is trivial and requires no special privileges beyond the existing pairing.

### Recommendation
- Bind `getSignedPackageHashToSign()` (or `is_valid_signed_package`) to an explicit, protocol-mandated domain separator (e.g., the AA address invoking it, plus an app-defined context string) so a signature cannot be verified as valid outside its intended context.
- Require wallets to clearly render the *type/purpose* of a `signed_message` before requesting user approval, and warn when a signing request originates from a `"sign"` device message rather than a local, self-composed transaction.
- Update `is_valid_signed_package` documentation/interface to strongly recommend (or enforce) an application/channel identifier field, and audit shipped oscript examples (e.g., `order_book_exchange.oscript`) to include one.

### Proof of Concept
1. Attacker device pairs with victim (`device.handlePairingMessage`, standard flow).
2. Attacker's device sends victim a `"sign"` message: `{address: victimAddress, signing_path: "r", unsigned_unit: {version, signed_message: {address: victimAddress, sell_asset: "X", buy_asset: "base", sell_amount: 1000000, price: 0.0000001}, authors: [{address: victimAddress, authentifiers: {r: "-------------"}}]}}` (see `wallet.js:251-349`).
3. Victim's wallet, seeing only a generic "sign this message" prompt (no context that it authorizes a below-market trade), approves; wallet signs via `signed_message.signMessage`/`getSignedPackageHashToSign` (`object_hash.js:97-103`).
4. Wallet returns the `signature` message to the attacker device (`wallet.js` `"signature"` case, `sendSignature`).
5. Attacker assembles `{signed_message, authors:[{address: victimAddress, authentifiers:{r: signature}}], last_ball_unit}` and posts it as `trigger.data.order1` to the `order_book_exchange` AA.
6. `is_valid_signed_package(trigger.data.order1, $order1.address)` passes (`formula/evaluation.js:1653-1699`), and the AA executes the unfavorable trade against the victim's balance held in the AA, without the victim ever knowingly agreeing to that specific trade.

function getSignedPackageHashToSign(signedPackage) {

	for (var i=0; i<unsignedPackage.authors.length; i++)
