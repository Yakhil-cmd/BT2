### Title
Webhook signature verification keyed by attacker-controlled `repository_owner` allows cross-organization forgery of CI status and team membership - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using a field read directly out of the *unauthenticated* JSON body, before the signature has been checked. In a multi-organization Shipit deployment, any org configured without a `webhook_secret` causes `verify_webhook_signature` to short-circuit to `true`. Because the org used to "authenticate" the request is decoupled from the org/repo/commit actually acted upon by the event handler, an attacker can pick that unsecured org to pass verification, then supply arbitrary `sha`/`organization.login` values in the same payload that get applied against any stack or team in the whole installation.

### Finding Description
`repository_owner` is computed straight from the parsed, unverified request body: [1](#0-0) 

It's then used to pick the app config *before* any signature check occurs: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization secrets via `github_app_config`, a documented, supported multi-app configuration: [3](#0-2) 

Signature verification is a no-op whenever that organization's `webhook_secret` is blank: [4](#0-3) 

The binding the platform relies on is: *the organization whose secret authenticated the request* `==` *the organization/repository/commit the handler subsequently writes to*. That equality is never enforced. Handlers act on payload fields that are entirely independent of `repository_owner`:

- `StatusHandler#process` matches **any** commit in the entire database by `sha`, with no org/stack scoping tied to the verified organization: [5](#0-4) 

- `MembershipHandler#process` creates/updates team membership using `params.organization.login` and `params.team`/`params.member`, again independent of which org's secret verified the request: [6](#0-5) 

So: an attacker sets `repository.owner.login` (or `organization.login`) in the JSON body to an org that has no `webhook_secret` configured (a supported configuration shown in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`), which makes `verify_webhook_signature` return `true` unconditionally. The rest of the payload (the real `sha`, the real target `organization.login`/`team`) is then processed as if fully trusted, even though it was never covered by any HMAC check.

### Impact Explanation
This breaks two of the explicitly in-scope High-impact bindings:
- **Unauthorized merge**: A forged `status` event can mark any commit's CI as `success` for any stack tracked by this Shipit instance. `Commit#create_status_from_github!` feeds `ProcessMergeRequestsJob`/`MergeRequest#all_status_checks_passed?`, which will merge a pull request via `stack.github_api.merge_pull_request` even though CI never actually passed — an unauthorized merge using the app's real GitHub credentials.
- **Escalation into `Shipit.github_teams` authorization**: A forged `membership` event with `organization.login` set to the *real, secured* org and a `team`/`member` matching `Shipit.github_teams` adds an attacker-chosen GitHub login to that team. Since `User#authorized?` grants full UI/session access based on team membership, this is a path to unauthenticated login/authorization bypass into the Shipit UI.

Both outcomes require zero credentials — only that the operator has configured more than one GitHub organization and at least one of them (which need not be the "real" target org at all) has no webhook secret set, a state the engine's own documentation and example configs actively encourage (`webhook_secret: # nil`).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the "Using Multiple Github Applications" configuration (documented in `docs/setup.md`) and at least one configured organization with an empty `webhook_secret`. This is realistic because:
- The example/dummy configs shipped with the engine itself (`config/secrets.development.example.yml`, `secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) all show `webhook_secret: # nil` as the default/example value.
- `webhook_secret` is documented as "optional" everywhere, so operators following the docs for a secondary/low-value org can inadvertently open this hole for every org in the same installation.

### Recommendation
- Never let an attacker-supplied payload field select which secret is used to verify that same payload. Require signature verification against **every** configured organization's secret (or fail closed) rather than trusting `repository_owner`/`organization.login` from the unauthenticated body to pick a single verifier.
- Do not treat a missing `webhook_secret` as automatic verification success; require an explicit `Shipit.disable_webhook_signature_verification`-style opt-in rather than defaulting silently to `true`.
- Scope handler side effects (status, membership, push) to the organization that actually authenticated the request, not to org/repo/commit fields taken from the unverified payload.

### Proof of Concept
1. Configure Shipit with two organizations: `SecureOrg` (real target, has `Shipit.github_teams` and active stacks) and `EmptyOrg` (no `webhook_secret` set — matches the shipped example configs).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "EmptyOrg" } },
  "sha": "<sha of any commit belonging to a SecureOrg stack, pending on CI>",
  "state": "success",
  "context": "ci/required"
}
```
No valid `X-Hub-Signature` is required because `EmptyOrg` has no secret, so `verify_webhook_signature` returns `true` (`lib/shipit/github_app.rb:76-83`). `WebhooksController#create` dispatches to `StatusHandler`, which updates the status on the targeted commit regardless of organization, potentially unblocking a merge in `SecureOrg`.
3. Similarly, POST a `membership` event with `repository.owner.login: "EmptyOrg"` but `organization.login: "SecureOrg"` and a `team` matching one of `Shipit.github_teams`, and `member.login` set to an attacker-controlled GitHub account — this adds that account to the authorizing team.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
