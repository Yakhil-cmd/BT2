### Title
`StatusHandler#process` writes CI status to any stack sharing a commit SHA, regardless of which repository authenticated the webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) with a bare, repository‑unscoped query `Commit.where(sha: params.sha)` and writes the incoming GitHub status to every matching commit across the entire database, unlike every other handler in this engine, which resolves its target through the base `Handler#stacks` helper that filters by `payload.dig('repository', 'full_name')`. Any webhook whose HMAC signature validates for its own `repository_owner` can therefore mutate CI state on a completely different stack if the `sha` in the payload happens to match a commit already ingested for that other stack.

### Finding Description
The invariant that should hold is:
`commit.stack.repo_name == payload.dig('repository', 'full_name')` for every `commit` mutated by a webhook.

Trace of the code:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches the raw JSON payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC against `Shipit.github(organization: repository_owner)` — this only proves the request was legitimately signed for *some* organization/app installation that the attacker controls (their own repository under their own GitHub org), not that it is authorized for the victim's repository.
- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) is the intended scoping mechanism used by other handlers (e.g. `push_handler.rb`, `pull_request/*_handler.rb`): it resolves `Repository.from_github_repo_name(repository_name)&.stacks`, i.e., restricts effects to stacks belonging to the repository named in `payload['repository']['full_name']`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does **not** use `stacks` or `repository_name` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries the global `commits` table by bare SHA with no `stack_id`/repository filter, then calls `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`), which appends the status and re-evaluates `deployable?`/`blocked?`/`schedule_continuous_delivery` (`app/models/shipit/commit.rb:227-237, 281-287, 366-386`), potentially triggering `stack.schedule_merges` or continuous deployment on the victim stack.

Exploit flow: the attacker owns a repository (or org) legitimately connected to Shipit (satisfying `verify_signature`), obtains/produces a commit whose SHA is shared with a commit already recorded on a victim's stack (e.g., via shared git history, forked/mirrored repos, or common upstream commits ingested by both stacks), and sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own repo, and body `{ "sha": "<shared sha>", "context": "ci/build", "state": "success", "repository": {...attacker repo...} }`. `StatusHandler` finds the victim's `Commit` row by bare SHA and writes a passing `ci/build` status to it, flipping `deployable?`/`blocked?` for the victim stack even though the victim repository never authenticated this status.

Existing guards do not prevent this: `verify_signature` only authenticates that the sender controls *a* valid webhook secret for the org named in their own payload; it never checks that the resolved `Commit`/`Stack` belongs to that same repository. `ExplicitParameters` schema only validates types (`sha`, `state`, etc.), not ownership. No repository-scoping check exists between signature verification and the `Commit.where(sha:)` lookup.

### Impact Explanation
An attacker who legitimately controls a Shipit-connected repository (their own, or one under an org they can install the app on) can, for any commit SHA shared with a victim stack, forge a CI status (`ci/build` or any other context) that the victim repository never sent. This can flip a commit from blocked to deployable (or vice-versa), triggering `stack.schedule_merges` and continuous deployment (`ContinuousDeliveryJob`) on a stack that is not the attacker's — a payload for one repository mutating another repository's commit/task/stack state. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository/org connected to Shipit so that `verify_signature` succeeds for their own webhook, and (b) a commit SHA that coincides with a commit already stored for the victim's stack. This second precondition is nontrivial in the general case (finding an arbitrary SHA collision is infeasible), but it is realistic whenever repositories share history — forks, mirrors, monorepo splits, vendored/subtree commits, or commits cherry-picked/rebased with identical hashes across multiple Shipit-tracked repositories, all of which are common in real deployment setups. Given that precondition, exploitation is trivial and repeatable: a single unauthenticated `POST /webhooks` request per target commit, with no rate limiting bypass required.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the affected stacks via `Repository.from_github_repo_name(repository_name)` (or filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) so that a status webhook can only mutate commits belonging to the repository that authenticated the request, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical):
```ruby
test "status webhook does not affect commits belonging to a different repository sharing the same SHA" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repository_full_name = "attacker/other-repo"
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/build',
    'repository' => { 'full_name' => attacker_repository_full_name },
  }

  # Binding under test:
  # commit.stack.repo_name == payload.dig('repository', 'full_name')
  assert_not_equal victim_stack.repo_name, attacker_repository_full_name

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_empty victim_commit.statuses, "status from an unrelated repository must not be recorded on the victim commit"
end
```
Before the fix, `victim_commit.statuses` is non-empty (the assertion fails), demonstrating the cross-repository write; after scoping by `repository_name`/`stacks`, the assertion passes.
