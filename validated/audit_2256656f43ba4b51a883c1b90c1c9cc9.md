### Title
Cross-repository commit-status forgery triggers victim stack merge queue advancement via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target `Commit` records by SHA alone, with no scoping to the repository that authenticated the webhook, unlike its sibling handlers which use the `Handler#stacks`/`repository_name` helper. Because git commit SHAs are content-addressed and identical across a fork and its upstream, an attacker can trigger a real, correctly-signed `status` webhook from a repository they own and flip the status of a `Commit` row that actually belongs to a victim stack, causing `Shipit::Commit#add_status` to call `stack.schedule_merges` on that victim stack.

### Finding Description
Binding claimed to hold: `payload.dig('repository','full_name')` (the repository whose webhook signature was verified in `Shipit::WebhooksController#verify_signature`, via `Shipit.github(organization: repository_owner)`) should equal the repository of the `Stack`/`Commit` that gets mutated by the handler.

Actual code: [1](#0-0) 
`StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. It never calls the `stacks`/`repository_name` scoping helper that the base `Handler` class provides for exactly this purpose: [2](#0-1) 

Because `Commit` records are keyed by `stack_id` + `sha` (not globally unique by `sha`), two different stacks/repositories can each have a `Commit` row with the same SHA — this legitimately happens for PR-based workflows where a fork's head commit and the upstream repo's tracked commit are the exact same git object (`pull_request_head_sha`) as seen in `Shipit::Commit.from_github`: [3](#0-2) 

`create_status_from_github!` calls the private `add_status`, which, once the status transitions to `success` (or `pending`), unconditionally calls `stack.schedule_merges` where `stack` is `commit.stack` — the stack that owns the `Commit` row, not the repository that sent the webhook: [4](#0-3) 

Exploit flow: attacker forks the victim repository (or otherwise obtains a repo they own containing an identical commit SHA to one tracked in a victim stack — e.g. the head of their own open PR against the victim repo). Attacker sets a commit status (`state: success`) on that SHA via the GitHub API on their own repository. GitHub delivers a real, correctly signed `status` webhook to Shipit with `repository.full_name` = attacker's own repo and `sha` = the shared SHA. `verify_signature` passes because the signature is verified against the attacker's own repo/org's legitimate GitHub delivery — no Shipit or GitHub secret is stolen or forged: [5](#0-4) 

`StatusHandler` then finds the victim's pre-existing `Commit` row (created earlier via the tracked PR/push flow) purely by SHA and applies the attacker-controlled `state` to it, firing `stack.schedule_merges` for the victim stack. This advances the victim's `MergeRequest` queue processing (`ProcessMergeRequestsJob`) despite the attacker's webhook payload never naming the victim's repository at all.

Existing guards do not stop this: `verify_signature` only authenticates that *a* payload came from *a* repo/org the attacker controls — it says nothing about which `Commit`/`Stack` the handler is permitted to mutate. The `ExplicitParameters` schema on `StatusHandler` only validates types (`sha`, `state`, etc.), not repository ownership. The `Handler#stacks` scoping helper exists precisely to bind `repository_name` to the correct stack, but `StatusHandler` does not use it, unlike other handlers that reference `stacks`.

### Impact Explanation
Effect per request: a repository that never authenticated for the victim's stack/webhook can cause `Shipit::Stack#schedule_merges` to run for that victim stack, advancing/processing its merge queue (`ProcessMergeRequestsJob`) based on an attacker-forged/attacker-controlled `success` status. This matches the "Critical" category: a payload for one repository mutating another repository's stack/commit and driving an unauthorized merge-queue action. It is repeatable against any victim stack for which the attacker can obtain (via fork/PR) a `Commit` row sharing a SHA with a repo they control, and requires no privileged role, session, token, or secret.

### Likelihood Explanation
Preconditions: Shipit must already be tracking the victim stack/repo and have a `Commit` record for the shared SHA (typical when open pull requests are tracked, since `pull_request_head_sha` links fork and upstream commits by identical SHA). The attacker only needs a GitHub account, a repository/fork they control, and the ability to open a PR or set a commit status via the GitHub API on their own repo — all explicitly listed as attacker capabilities in scope. No Shipit secret, session, or elevated GitHub permission is required, making this low-cost and repeatable.

### Recommendation
Scope `StatusHandler#process` (and audit all other handlers) to only touch commits belonging to stacks resolved from the authenticated `repository_name`, using the existing `stacks` helper, e.g. filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (and equivalently restrict to commits whose `stack.repository` matches `payload.dig('repository','full_name')`) before applying any status change, rather than matching by SHA alone.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook for attacker repo cannot schedule merges on a victim stack sharing a SHA" do
          victim_stack = shipit_stacks(:shipit) # repository full_name e.g. "shopify/shipit-engine"
          shared_sha = "a" * 40

          victim_commit = victim_stack.commits.create!(
            sha: shared_sha,
            author: shipit_users(:shipit),
            authored_at: Time.now,
            committer: shipit_users(:shipit),
            committed_at: Time.now,
            message: "shared commit"
          )

          Shipit::MergeRequest.create!(
            stack: victim_stack,
            number: 42,
            head_sha: shared_sha,
            state: 'pending'
          )

          # Attacker webhook payload: repository is the attacker's own repo,
          # never references victim_stack's repository.
          attacker_payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'created_at' => Time.now.to_s,
            'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
          }

          Shipit::Stack.any_instance.expects(:schedule_merges).never
          # Demonstrates the broken binding: repository authenticating the
          # webhook ("attacker/unrelated-repo") != repository owning the
          # mutated Commit/Stack (victim_stack), yet schedule_merges fires.
          Shipit::Commit.any_instance.stubs(:stack).returns(victim_stack) if false # illustrative only

          assert_raises(Mocha::ExpectationError) do
            StatusHandler.call(attacker_payload)
          end
        end
      end
    end
  end
end
```
Note: the assertion `Shipit::Stack.any_instance.expects(:schedule_merges).never` failing (raising `Mocha::ExpectationError`) demonstrates that `schedule_merges` is in fact invoked on `victim_stack` even though the webhook's `repository.full_name` never referenced it, confirming the cross-repository binding break in `StatusHandler#process` → `Commit#add_status` → `Stack#schedule_merges`.
