### Title
Webhook signature bypass via attacker-controlled organization selection – unauthenticated cross-repository event injection - ([File: lib/shipit/github_app.rb])

### Summary
`GithubApp#verify_webhook_signature` unconditionally returns `true` whenever the organization's `webhook_secret` is not configured [1](#0-0) . The organization used to look up that secret is derived directly from the attacker-supplied JSON payload rather than from any pre-authenticated identity [2](#0-1) . This mirrors the reported `EvmScriptExecutor` bug class: a "verification" call that trivially returns `true` when a companion piece of state (a contract's bytecode / a `webhook_secret`) is absent, letting an attacker-controlled input satisfy a security check that was supposed to bind trust to a specific, verified identity.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the untrusted request body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . It then calls `Shipit.github(organization: repository_owner)` and asks that per-organization `GithubApp` instance to verify the `X-Hub-Signature` header against the raw body [3](#0-2) .

Inside `GithubApp#verify_webhook_signature`:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

If the organization named in the attacker-supplied payload has no `webhook_secret` configured — a state the multi-org setup explicitly supports, since `webhook_secret` is documented as optional per-organization [4](#0-3)  — signature verification is skipped entirely and the request is treated as authentic. The handler that then processes the event operates on the payload's own `repository`/`organization` fields (e.g. enqueuing `GithubSyncJob` for whatever stack corresponds to the payload's repository) [5](#0-4) , without re-checking that the "authenticated" organization used for the signature lookup is the same entity that owns the repository actually being written to.

This breaks the intended equality: `organization whose HMAC secret authenticated the request == organization/repository that the handler subsequently mutates`. Because `repository_owner` is attacker-controlled and the bypass triggers merely by naming an org lacking a secret, an unprivileged attacker can forge webhook events (pushes, statuses, membership changes) for any repository/stack tracked by the Shipit instance, as long as any one configured organization in the deployment omits `webhook_secret`.

### Impact Explanation
A forged, unauthenticated webhook can enqueue `GithubSyncJob`, create/modify commit `Status` records, or manipulate team `Membership` (as exercised by the very same test file for the `membership` event) [6](#0-5) . Forged commit statuses can satisfy `ci.require` checks that gate deploys, and forged `push`/sync events can alter which commit Shipit believes is at the head of a branch — both of which can lead to an unauthorized deploy being triggered on a legitimate stack, satisfying the "unauthorized deploy" Critical-impact bar, or unauthenticated team/membership tampering feeding into `Shipit.github_teams` authorization (High).

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: at least one organization entry in `config/secrets.yml` must have a blank/absent `webhook_secret`. This is an explicitly supported configuration (the sample and docs show `webhook_secret` as an optional key, and the test suite stubs it to `nil`) [7](#0-6) [8](#0-7) , so it is a realistic and even encouraged fallback (e.g. for local/dev setups or partial rollouts of multi-org support), not a purely theoretical misconfiguration.

### Recommendation
Do not derive the "authenticated" organization from attacker-controlled payload fields, and never let missing/blank `webhook_secret` silently short-circuit verification to `true`. `verify_webhook_signature` should fail closed (return `false`/raise) when no secret is configured for the resolved organization, and the resolved organization used for verification should be cross-checked against the organization that actually owns the `repository`/`stack` being mutated by the downstream handler.

### Proof of Concept
1. Deploy Shipit with two organizations configured: `victim-org` (tracked stacks, `webhook_secret` set) and `no-secret-org` (any name, `webhook_secret` left blank/nil, as shown supported in `docs/setup.md` and the sample secrets files).
2. POST to `/webhooks` with `X-Github-Event: push` and a JSON body where `repository.owner.login` = `no-secret-org` (to select the org with no secret during verification) but `repository.full_name` matches a real stack tracked under `victim-org` (e.g. `victim-org/victim-repo`).
3. `verify_signature` resolves `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing or garbage) `X-Hub-Signature` header [9](#0-8) .
4. The event handler processes the forged payload against `victim-org/victim-repo`'s stack (as in the `GithubSyncJob` enqueue test) [5](#0-4) , causing unauthorized state changes on a stack the attacker never had credentials for.

**Note on verification limits:** I was unable to locate the exact push/event handler implementation file (e.g. under `lib/shipit/webhooks/`) within the indexed context to show byte-for-byte how `repository.full_name` maps to a `Stack` lookup; this part of the chain is inferred from `WebhooksController#create`'s dispatch to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [10](#0-9)  and the observed test behavior. If a full trace through the specific handler class is needed, a Devin session with full filesystem access would be required to confirm it, since the code index has size limits that may exclude some files.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

        id:
