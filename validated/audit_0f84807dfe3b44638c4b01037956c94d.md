### Title
Boolean-precedence bug in `provision?`/`unarchive?` causes ReviewStack creation to bypass `review_stacks_enabled=false` - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` and the identical `ReopenedHandler#unarchive?` predicate use `&&`/`||` in a way that only gates the `allow_all` branch behind `repository.review_stacks_enabled`; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of that flag. An attacker who opens (or reopens) a pull request against a tracked repository whose operator set `review_stacks_enabled = false` but left `provisioning_behavior` at `prevent_with_label` (or `allow_with_label`) can still trigger `ReviewStackAdapter#create!`, writing a `ReviewStack` + `PullRequest` row and enqueuing provisioning, contrary to the operator's opt-out.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == false` should imply `stack_created_for(repository) == false`. Due to Ruby operator precedence (`&&` binds tighter than `||`), the guard actually evaluates as:

```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
``` [1](#0-0) 

instead of the intended `review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`. The identical pattern exists in `ReopenedHandler#unarchive?` [2](#0-1) . `LabeledHandler#respond_to_label_change?`, by contrast, correctly ANDs `review_stacks_enabled` across the whole expression [3](#0-2) , confirming the other two handlers deviate from the intended semantics.

Call path: `OpenedHandler#process` → `respond_to_pull_request_opened?` (`action == "opened" && provision?`) → if true, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` → `create!` → `scope.create!(stack_attributes)` (branch/environment derived from `params.pull_request.head.ref` and `params.number`) → `stack.build_pull_request.update!(github_pull_request: params.pull_request)` → `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) .

Exploit: attacker forks a Shipit-tracked repository whose operator has `review_stacks_enabled = false` and `provisioning_behavior = "prevent_with_label"` (the default label-based state, not requiring the attacker to add a label), and opens a pull request. `provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?` evaluates true, so `provision?` returns true even though `review_stacks_enabled` is false, and a `ReviewStack` row is created and queued for provisioning. This is the "boolean-precedence bypass" referenced in the prompt.

Existing guards do not close this: `verify_signature`/webhook-secret checks only authenticate that the payload came from GitHub, not the intended repository policy; the `ExplicitParameters` schema only validates payload shape, not business rules; there is no model validation preventing `ReviewStack` creation when `review_stacks_enabled` is false — that check lives entirely in the handler predicate, which is broken by precedence. The existing test suite covers `provisioning_enabled: false` only with `behavior: :allow_all` [5](#0-4)  and covers `prevent_with_label`/`allow_with_label` only with the default `provisioning_enabled: true` [6](#0-5) , so the combination that exposes the bug (`review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label`) is untested.

### Impact Explanation
An unprivileged GitHub user who can open/reopen a pull request against a tracked repository can force creation of a `ReviewStack`/`PullRequest` database row and enqueue provisioning even though the repository owner explicitly disabled review-stack provisioning (`review_stacks_enabled = false`). This is repeatable for any tracked repository whose operator uses `allow_with_label` or `prevent_with_label` alongside `review_stacks_enabled = false` — a plausible and not-unusual misconfiguration, since operators may toggle `review_stacks_enabled` as a global kill switch without also resetting `provisioning_behavior` back to `allow_all`. Depending on how `ReviewStackProvisioningQueue` is consumed downstream, this can lead to actual infrastructure provisioning against attacker-controlled branch/environment values, which is an unauthorized state-mutating action taken on behalf of a repository/tenant that opted out.

### Likelihood Explanation
Preconditions: the target repository must already be tracked in Shipit (`Shipit::Repository` row exists), have `review_stacks_enabled = false`, and have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (not the schema default `allow_all`) [7](#0-6) . No secrets, sessions, or API tokens are required — only the ability to open/reopen a pull request, which any GitHub user can do against a public repo or their own fork's PR to an upstream repo. Attacker cost is a single webhook-triggering PR action, fully repeatable per PR/PR-reopen.

### Recommendation
Fix the operator precedence in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` to explicitly AND `repository.review_stacks_enabled` across the entire expression, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the equivalent fix to `unarchive?` in `reopened_handler.rb`, and add regression tests covering `review_stacks_enabled: false` combined with each `provisioning_behavior` value.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` add:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label default state" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::ReviewStack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: `repository.review_stacks_enabled` is `false` (left side), and `Shipit::ReviewStack.find_by(environment: "pr#{payload['number']}")&.repository_id` should be `nil` (right side) — currently the test fails because a `ReviewStack` row IS created, proving the bypass.
