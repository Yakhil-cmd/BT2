### Title
Position NFT `transfer`/`transfer_from` have no receiver-safety check — transferring to an address that cannot authorize permanently freezes the entire lending account - (File: contracts/position-nft/src/contract.rs)

### Summary
The analog to "unsafe ERC721 transfer" is the position NFT's stock `transfer`/`transfer_from`. A lending account is exactly one NFT (`account_id == token_id`), and the token carries both collateral and debt. The OpenZeppelin `NonFungibleToken` implementation exported by `PositionNft` performs no receiver-capability check — there is no `safeTransferFrom`/`onReceived` equivalent on Soroban — so `transfer` blindly rewrites `Owner(token_id)` to whatever `to` address is passed. [1](#0-0) [2](#0-1) 

### Finding Description
`PositionNft` exports the stock OpenZeppelin `NonFungibleToken` trait (`type ContractType = Enumerable`), which provides `transfer`, `transfer_from`, `approve`, and `approve_for_all` unchanged. `transfer(from, to, token_id)` only requires `from.require_auth()` and a check that `from` is the current owner; it then reassigns ownership to `to` with no validation of whether `to` can ever authorize a subsequent controller call. [3](#0-2) 

The controller stores no owner address; every account action resolves the holder live via `owner_of(account_id)` and requires that address's authorization. A `to` that is a contract address without `require_auth` support, or a keyless/derived address, can never produce the auth the controller needs. There is no recovery path: the contract address cannot call `transfer` to send the token back, `burn` is controller-only and only invoked on account deletion, and no holder-facing admin or rescue entrypoint exists. [4](#0-3) [5](#0-4) 

### Impact Explanation
Permanent freezing of user funds. All supplied collateral in the account becomes unreachable: `withdraw`, `borrow`, `supply` slot changes, and `transfer` all gate on the resolved owner authorizing. The debt side is still serviceable by anyone (`repay`, `liquidate`), but the collateral can only exit through a liquidation that burns value to the frozen holder. A user holding a large collateralized position who sends the NFT to a contract that cannot sign loses access to the entire position forever. [6](#0-5) 

### Likelihood Explanation
This requires a holder (or their approved operator via `approve`/`approve_for_all`/`transfer_from`) to pass a `to` address that cannot authorize — e.g., an EOA-style contract wallet, an intermediary contract in a marketplace/sale flow that never implemented a position-forwarding path, or an address typo. It is self-inflicted rather than attacker-driven, but the protocol amplifies it: unlike a plain NFT, the token encapsulates all collateral and debt, and DeFi integrations (marketplaces, escrow-like contracts, account-abstraction wallets) that move position NFTs routinely will pass contract addresses as `to`. The common real-world trigger is a contract that buys/receives the NFT expecting to manage it but lacking the auth surface the controller demands. [7](#0-6) 

### Recommendation
Add a receiver-confirmation mechanism for transfers to contract addresses, mirroring `safeTransferFrom` semantics:
- Expose `safe_transfer`/`safe_transfer_from` (or override `transfer`/`transfer_from`) so that when `to` is a contract, it must implement a receiver hook (e.g., `on_position_received(operator, from, token_id)` via a defined interface) before `Base::update` runs; revert otherwise.
- Alternatively, implement a two-step `claim` pattern: `transfer` to a contract marks a pending transfer that the recipient contract must explicitly `accept` before `Owner` changes, with the sender able to `cancel` while pending — this keeps keyless-address mistakes recoverable.
- At minimum, document that `transfer`/`transfer_from` to contract `Address`es is irreversible and that integrators must verify recipient auth capability before moving a position.

### Proof of Concept
1. Alice calls `controller::supply` with `account_id 0`; the controller mints token id `1` to `ALICE_ADDR` and her account holds USDC collateral. [8](#0-7) 
2. Alice calls `position-nft::transfer(from=ALICE_ADDR, to=MARKET_CONTRACT, token_id=1)` where `MARKET_CONTRACT` is any contract (or keyless address) that cannot satisfy `require_auth` for the controller. The stock OZ update succeeds unconditionally — no receiver check is executed. [1](#0-0) 
3. `owner_of(1)` now returns `MARKET_CONTRACT`. Every subsequent controller call for account `1` — `withdraw`, `supply`, `borrow`, `transfer` of the NFT — resolves the owner and demands authorization from `MARKET_CONTRACT`, which can never provide it. [9](#0-8) 
4. No admin path helps: `mint`/`burn` are controller-only and `burn` only runs on account deletion; the account cannot be deleted because deletion requires emptying the position, which requires owner auth. The collateral is permanently frozen inside account `1`. [10](#0-9)

    pub fn mint(e: &Env, to: Address) -> u32 {
        controller(e).require_auth();
        renew_instance(e);
        let token_id = Enumerable::sequential_mint(e, &to);
        // sequential_mint writes Owner/Balance at the network minimum TTL; lift
        // them to the user window so a new position does not archive early.
        extend_user_persistent_ttl(e, &to, token_id);
        token_id
    }

    /// Burns `token_id` without the holder's authorization. Controller-only.
    ///
    /// Not the OZ `Burnable` extension: `Base::burn` calls
    /// `from.require_auth()`, and the controller must burn when liquidation
    /// empties an account without the owner's signature. This replicates
    /// `Enumerable::burn` (v0.7.1) without that auth: `Base::update` removes the
    /// owner and approval and decrements the holder's balance. The enumeration
    /// helper updates owner enumeration, total supply and global enumeration.
    ///
    /// Renews the instance TTL on every account deletion.
    pub fn burn(e: &Env, token_id: u32) {
        controller(e).require_auth();
        renew_instance(e);
        let owner = Base::owner_of(e, token_id);
        Base::update(e, Some(&owner), None, token_id);
        emit_burn(e, &owner, token_id);
        Enumerable::remove_from_enumerations(e, &owner, token_id);
    }
