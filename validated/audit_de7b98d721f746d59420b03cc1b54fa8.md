### Title
Inline frontmatter parser truncates comma-containing `pattern` values, silently weakening `block` rule conditions - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter`'s ad-hoc inline-dict parser splits list-item text on `,` before splitting on `:`, so any `pattern:` value containing a literal comma is silently truncated to the substring before the first comma. Because `Condition.from_dict` and `RuleEngine._check_condition`/`_regex_match` use this truncated pattern verbatim with no validation or warning, a `block` rule authored with a comma-containing regex pattern will compile and run, but will not actually match the intended (fuller) payload space, violating the "deny means deny" invariant for that rule.

### Finding Description
In `extract_frontmatter`, when a YAML list item is written as an inline dict (`- field: command, operator: regex_match, pattern: a,b,c`), the code path is: [1](#0-0) 

```
if ':' in item_text and ',' in item_text:
    item_dict = {}
    for part in item_text.split(','):
        if ':' in part:
            k, v = part.split(':', 1)
            item_dict[k.strip()] = v.strip().strip('"').strip("'")
    current_list.append(item_dict)
```

The parser first splits the whole inline item on every `,`, regardless of whether the comma is a field separator or part of a value (e.g., inside a regex pattern like `a,b,c` or `(cmd1|cmd2),foo`). For `pattern: a,b,c`, `item_text.split(',')` yields `["field: command", " operator: regex_match", " pattern: a", "b", "c"]`. Only fragments containing `:` are kept (`"b"` and `"c"` are dropped because `':' in part` is false), so `item_dict['pattern']` ends up as `"a"` instead of the intended `"a,b,c"`.

This truncated dict is passed straight into `Condition.from_dict`, which does no validation: [2](#0-1) . The resulting `Condition.pattern` is then compiled and evaluated as a regex in `RuleEngine._regex_match`: [3](#0-2) , and used directly by `block` rules in `evaluate_rules`, which denies the tool call only if the (corrupted) condition matches: [4](#0-3) .

No part of the pipeline (`extract_frontmatter`, `Rule.from_dict`, `load_rule_file`, `RuleEngine`) detects or warns about this truncation — the rule loads successfully, is marked enabled, and silently enforces a weaker (or differently-scoped) pattern than the rule author intended. A rule file introduced or modified via ordinary repository content (e.g., a `.claude/hookify.*.local.md` file added/edited in a PR) that expresses its condition using the inline comma-separated shorthand with a comma-bearing pattern will have its enforcement silently weakened, letting real attacker payloads that were supposed to be blocked pass through as allowed Bash/Write/Edit operations.

### Impact Explanation
This is a hook/guard bypass: a `block` rule that is supposed to deny disallowed `Bash`/`Write`/`Edit` operations can end up matching a truncated/incorrect pattern instead of the intended one, so payloads that should be denied are allowed through. This directly violates the stated "deny means deny" invariant and matches the "unauthorized command or file action" / "trust-boundary bypass" impact category, since the mismatch is silent — no error, warning, or rule-load failure signals the corruption to whoever maintains the rule set.

### Likelihood Explanation
Feasibility is high and fully deterministic — it does not depend on race conditions or environment; any `pattern` value containing a comma written in the single-line inline-dict shorthand form is corrupted the same way every time. The only precondition is that a rule file uses the inline shorthand syntax (`- field: ..., operator: ..., pattern: ...`) with a comma inside the pattern (common for regex alternations/lists like `rm -rf,dd if=,mkfs`), which is a natural and undocumented-as-unsafe way to author rules. Because rule files live in the repository (`.claude/hookify.*.local.md`) and can be introduced via normal PR/content flow, an attacker who can influence repo content (e.g., a plausible-looking "security-hardening" PR) can introduce or modify such a rule, and the person accepting it would have no indication the rule is broken.

### Recommendation
Do not use naive `str.split(',')` for inline dict parsing. Instead:
- Require inline dict items to use a real YAML/structured parser (or a regex that only splits on `, ` sequences immediately followed by a `key:` token, e.g., `re.split(r',\s*(?=\w+\s*:)', item_text)`).
- Alternatively, deprecate the inline comma-shorthand entirely in favor of the already-supported multi-line dict item format, and validate at load time that reserialized `Condition` fields round-trip against the original text.
- Add a load-time sanity check that warns/fails loudly (not just silently) when a `pattern` looks suspiciously truncated (e.g., compare against the raw line for consistency), so broken rules cannot be silently deployed as if they were correct.

### Proof of Concept
```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-dangerous-commands
enabled: true
event: bash
action: block
conditions:
  - field: command, operator: regex_match, pattern: a,b,c
---

Blocked!
"""

frontmatter, message = extract_frontmatter(content)
rule = Rule.from_dict(frontmatter, message)

# Expected (correct) behavior: pattern preserved in full
assert rule.conditions[0].pattern == "a,b,c", (
    f"Pattern was corrupted: got {rule.conditions[0].pattern!r}"
)
```
Running this against the current implementation fails: `rule.conditions[0].pattern` is `"a"` instead of `"a,b,c"`, proving the inline parser truncates comma-containing patterns and silently weakens the `block` rule's enforcement.
