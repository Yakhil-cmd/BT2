### Title
Webhook signature verification key is selected from an untrusted field that is decoupled from the field used to target the repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to check the HMAC signature against using one field of the untrusted JSON body (`repository.owner.login` / `organization.login`), while every event `Handler` locates the `Stack`/`Repository` to act on using a *different* field of the same untrusted body (`repository.full_name`). These two fields are never cross-validated, so the "organization that authenticated" and the "repository that is written" are not the same binding.

### Finding Description
`verify_signature` computes the verifying key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the unauthenticated raw POST body before any signature check occurs. `Shipit.github(organization: repository_owner)` picks a distinct `GitHubApp` instance/config (potentially with its own, independently-configured `webhook_secret`) per organization, as shown by the multi-org config schema: [3](#0-2) 

Signature verification itself is a no-op when that organization has no secret configured: [4](#0-3) 

and the docs explicitly document `webhook_secret` as optional ("If you've set a webhook secret during the App creating, you should copy it here"), meaning a legitimately deployed multi-org Shipit instance can have some organizations configured without any secret while others are protected.

Once `verify_signature` passes (trivially, for the secret-less org), the same raw, unauthenticated body is dispatched to handlers, all of which resolve the target `Stack` via a completely different field: [5](#0-4) 

and e.g. `PushHandler` calls `stack.sync_github` against whatever `Stack`s match that `full_name`: [6](#0-5) 

The `status` event handler similarly persists a `Status`/`CommitStatus` for whatever `sha`/`repository.full_name` is embedded in the body (verified in the controller test: a `status` payload merged with arbitrary `repository_params` creates a `Status` record): [7](#0-6) 

**The broken equality:** `authenticated_org = payload.dig('repository','owner','login')` (used to pick the verification secret) is never required to equal `target_repo_owner = payload.dig('repository','full_name').split('/').first` (used to pick the `Stack`/`Repository` that is actually mutated). An attacker can therefore set the "owner" fields to an organization that has no `webhook_secret` configured (satisfying `verify_webhook_signature`'s `return true unless webhook_secret` short-circuit) while setting `repository.full_name` to a repository belonging to a *different*, secured organization tracked by the same Shipit instance.

### Impact Explanation
This lets an unauthenticated, unprivileged attacker forge GitHub events (push, status, check_suite, pull_request) for any repository/stack tracked by the Shipit instance, as long as at least one configured organization on that instance lacks a `webhook_secret` (an explicitly optional, documented configuration). Concretely:
- A forged `status` event can mark a commit as passing required CI checks on a protected repository, enabling an unauthorized deploy through Shipit's normal UI/CI-gating flow.
- A forged `push`/`check_suite` event can trigger `GithubSyncJob`/`RefreshCheckRunsJob` against arbitrary tracked stacks, corrupting commit history/state used to decide what gets deployed.

This crosses the "unauthorized deploy" / cross-repository-write impact bar defined in scope.

### Likelihood Explanation
Requires only that the Shipit instance track more than one GitHub organization and that at least one of them has no `webhook_secret` set — a configuration explicitly presented as optional in `docs/setup.md` and in the multi-org example (`config/secrets.development.shopify.yml`). No credentials, tokens, or prior access are needed; the attacker only needs to POST to the public `/webhooks` endpoint, which explicitly skips CSRF protection.

### Recommendation
Bind the field used for signature-key selection to the field used for repository resolution: after selecting `github_app` via `repository_owner`, require that `payload.dig('repository','full_name')` (and `organization.login`, if present) belong to the same organization before dispatching to handlers, or reject events where these fields disagree. Alternatively, make `webhook_secret` mandatory for every configured organization so `verify_webhook_signature` can never short-circuit to `true`.

### Proof of Concept
1. Configure Shipit with two orgs: `orgA` (no `webhook_secret`) and `orgB` (has `webhook_secret`, tracks a real `Stack`).
2. POST to `/webhooks` with `X-Github-Event: status` and a body:
```json
{
  "sha": "<commit-sha-of-orgB-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/protected-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`, whose `verify_webhook_secret` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`) regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `Handlers::StatusHandler` (via `Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) resolves the `Stack` from `orgB/protected-repo` and records the forged `success` status, potentially satisfying deploy gating for `orgB`'s stack despite the attacker never possessing `orgB`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
