### Title
CCMenu API endpoint bypasses per-token stack scoping, letting a stack-scoped API token read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController#stack` scopes stack lookups through `stacks.from_param!`, where `stacks` is filtered by the authenticated `ApiClient`'s `stack_id` (`Stack.where(id: current_api_client.stack_id)` when set). `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping that scoping entirely, while still relying on the generic `require_permission :read, :stack` permission check that only validates the `read:stack` permission string, not which specific stack the token is bound to.

### Finding Description
`app/controllers/shipit/api/base_controller.rb` defines the authorization binding: an `ApiClient` token that has a `stack_id` set is only supposed to authorize access to that one stack. [1](#0-0) 

`Shipit::Api::CCMenuController` inherits `BaseController` and reuses `require_permission :read, :stack`, but redefines `stack` to bypass the client-scoped `stacks` collection and look the stack up globally: [2](#0-1) 

`require_permission!` only checks that the token carries the `read:stack` permission string; it never checks that the token's `stack_id` matches the stack being accessed: [3](#0-2) 

Because `CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the equality that should hold — `token.stack_id == stack_id being served` — is broken: any token carrying `read:stack` (regardless of its `stack_id` binding) can be replayed against the CCMenu endpoint with an arbitrary `stack_id` in the URL, and the controller will happily return that other stack's build/deploy status. `CCMenuController` also supports Basic-Auth fallback (`super unless @current_api_client`) so a normally-issued, stack-scoped `ApiClient` credential (created via `ApiClientsController`, which lets any Shipit user with `write:hook`/etc. create an `ApiClient` and later assign a `stack_id`) is affected, not just the auto-generated CCMenu URL token.

### Impact Explanation
This is an authorization-boundary break where a credential explicitly scoped by its issuer to one stack can be used to read deploy/build state (`stack`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of any other stack in the Shipit instance. Per the impact taxonomy this matches "High — unauthenticated read of stack state, task streams or deploy output" relative to the intended per-stack scoping (the token is not unauthenticated overall, but it is unauthorized for the stack it ends up reading).

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token with `read:stack` permission (a routine, low-privilege credential intentionally scoped to a single stack by its creator) and knowledge/guessing of another stack's `to_param` (its repository/env slug, which is often predictable or discoverable). No signature forgery, GitHub credentials, or additional privilege is needed beyond a token that is expected to be stack-scoped.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the scoped `stacks` collection (`stacks.from_param!(params[:stack_id])`) exactly as `BaseController#stack` does, so a token's `stack_id` binding is enforced consistently across all API controllers, including CCMenu.

### Proof of Concept
1. An operator creates an `ApiClient` with permission `read:stack` and later restricts it via `stack_id` to `StackA` (intended to be embedded in a CI status badge for `StackA` only).
2. An attacker who obtains this token (e.g., from a leaked CCMenu badge URL/config) sends: `GET /api/<StackB-slug>/ccmenu.xml` using HTTP Basic auth with the token.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because the token has `read:stack`.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` — resolving `StackB` directly, ignoring that the token's `stack_id` is `StackA`.
5. The response discloses `StackB`'s build/deploy status, an unauthorized read across the token's stack-scope boundary.
