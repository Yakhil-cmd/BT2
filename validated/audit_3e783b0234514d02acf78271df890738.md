### Title
Webhook signature verification keys off `repository.owner.login` while all event handlers dispatch on `repository.full_name` — cross-organization forgery in multi-tenant GitHub App configs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the webhook secret to validate an inbound webhook's HMAC using `repository_owner`, extracted from the JSON body itself (`params.dig('repository', 'owner', 'login')`), and looks up the per-organization `GitHubApp` config accordingly. Every event handler, however, resolves the target `Repository`/`Stack` using a **different** field of the same body: `payload.dig('repository', 'full_name')`. Because Shipit supports configuring multiple GitHub organizations, each with its own `webhook_secret` [1](#0-0) , the field used to pick the *verifying* secret is decoupled from the field used to pick the *acted-upon* repository.

### Finding Description
`verify_signature` computes `repository_owner` purely from attacker-supplied JSON, then asks `Shipit.github(organization: repository_owner)` for the app whose `webhook_secret` will validate the `X-Hub-Signature` header: [2](#0-1) 

`Shipit.github` resolves this organization key against `secrets.github`, which in the documented multi-org schema maps distinct orgs to distinct `app_id`/`webhook_secret` pairs: [3](#0-2) 

Meanwhile, `Handler#repository_name`/`#stacks`, used by every concrete handler (`PushHandler`, pull-request handlers, etc.) to find the `Repository` and its `Stack`s that the event will act on, reads `payload.dig('repository', 'full_name')` — a **separate JSON key** from `repository.owner.login`: [4](#0-3) [5](#0-4) 

The binding the system implicitly relies on is: *organization whose secret validated the signature* == *organization/repository the handler will act on*. Nothing in the code enforces that `repository.owner.login` and the owner segment of `repository.full_name` are the same value; they are two independently attacker-controlled fields inside a single JSON payload that is signed as one opaque blob. In a multi-tenant deployment (one Shipit instance serving several GitHub orgs, each with its own App and `webhook_secret`, as documented in `docs/setup.md`/`config/secrets.development.example.yml`), an attacker who legitimately controls one configured org ("org-B", knows its `webhook_secret` because they installed/administer that GitHub App) can craft a payload with `repository.owner.login = "org-B"` (so `verify_signature` picks org-B's secret, which the attacker can correctly HMAC-sign) but `repository.full_name = "org-A/victim-repo"` (a different, victim organization's repository that also has a Shipit stack configured). The signature check passes because it is validated against the correct secret for the *owner* field, while every downstream handler acts on the unrelated `full_name` field pointing at a foreign repository.

### Impact Explanation
This breaks the "organization that authenticated" vs "repository that is written" binding explicitly called out as an in-scope analog class. Concretely, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4)  against stacks resolved from the forged `full_name`; if `continuous_deployment` is enabled on the victim stack, this can trigger unsynchronized/forged deploy pipelines against a repository the attacker does not control, and other handlers (pull request opened/closed/labeled, membership, etc.) similarly key off `full_name`-resolved repositories/stacks while trusting the wrong-org signature check. This satisfies the "unauthorized deploy" / cross-repository write bar for High/Critical impact defined in scope, without requiring any Shipit session, API token, or the target org's own webhook secret — only administrative control of one org already configured on the same multi-tenant instance.

### Likelihood Explanation
Requires the deployment to use Shipit's documented multi-organization GitHub config (`secrets.github` keyed by organization, each with its own `webhook_secret`) and requires the attacker to legitimately control at least one such configured organization (i.e., they can install/administer a GitHub App there and thus know that org's `webhook_secret`). Given multi-org support is a first-class, documented feature [1](#0-0) , this is a realistic deployment shape, but the attack is limited to instances actually hosting multiple mutually-untrusted organizations — not the common single-org case.

### Recommendation
After signature verification succeeds, re-derive `repository_owner` from the same field used by handlers (`repository.full_name`'s owner segment, or `organization.login`) and assert it matches the organization whose secret validated the signature; reject the webhook otherwise. Alternatively, verify the signature against a webhook secret bound to the `Repository`/`Stack` actually resolved by the handler rather than to an unauthenticated field read before dispatch.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (per multi-org schema in `config/secrets.development.example.yml`).
2. Attacker administers the GitHub App installed on `org-b` and thus knows `org-b`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a JSON body: `{"repository": {"owner": {"login": "org-b"}, "full_name": "org-a/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>", ...}`, signing the raw body with `org-b`'s `webhook_secret` in `X-Hub-Signature`.
4. `WebhooksController#verify_signature` computes `repository_owner = "org-b"`, fetches org-b's `GitHubApp`, and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-49`).
5. `Shipit::Webhooks::Handlers::PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-a/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:30-38`) and calls `stack.sync_github` on `org-a`'s stack — a repository/org the attacker does not control and never proved knowledge of that org's secret for.

*Note: I could not fully trace every downstream handler's exact side effects (e.g., whether `sync_github` alone can force an unauthorized deploy without additional CI-status conditions) within the available index; this would need to be confirmed against `Shipit::Stack#sync_github` and `continuous_deployment` logic in a full checkout.*

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
