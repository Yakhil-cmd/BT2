### Title
Uncaught exception in `chash.isChashValid` on malformed base32 address input crashes the node process - (File: `chash.js`)

### Summary
`chash.js` uses the `thirty-two` base32 library to decode an attacker-supplied 32-character address/chash string, then processes the decoded buffer without validating its byte length before feeding it into `separateIntoCleanDataAndChecksum`, which throws a hard `Error` on any length other than 160 or 288 bits. This throw is not caught anywhere in the call chain, and `network.js` installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the whole node process. This is the same bug class as CVE-2018-10360 (malformed input reaches a length-sensitive parsing routine without bounds/length validation, causing a crash), except here the "crash" is a Node.js process death instead of a native OOB memory read.

### Finding Description
`isValidAddress`/`isValidChash` in `validation_utils.js` call into `chash.isChashValid`: [1](#0-0) 

```js
function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48)
		throw Error("wrong encoded length: "+encoded_len);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);
		return false;
	}
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);
	...
``` [2](#0-1) 

The `try/catch` here only guards the *decode* step (`base32.decode` / `Buffer.from`). It only validates the *string* length (32 or 48 chars) before decoding — it never validates that the **decoded byte buffer** actually has the expected length (20 bytes for 160-bit chash, 36 bytes for 288-bit chash) before it is handed to `buffer2bin` and then `separateIntoCleanDataAndChecksum`:

```js
function separateIntoCleanDataAndChecksum(bin){
	var len = bin.length;
	var arrOffsets;
	if (len === 160)
		arrOffsets = arrOffsets160;
	else if (len === 288)
		arrOffsets = arrOffsets288;
	else
		throw Error("bad length="+len+", bin = "+bin);
	...
``` [3](#0-2) 

The `thirty-two` package is a permissive base32 codec that decodes arbitrary 32-character strings composed of the RFC4648 base32 alphabet into a byte buffer whose length depends on padding/garbage characters in the input, not strictly guaranteed to be exactly 20 bytes for every syntactically-valid 32-character string. When the decoded buffer's bit-length is anything other than 160 or 288, `separateIntoCleanDataAndChecksum` throws an `Error` that is **not wrapped in any try/catch** by its caller (`isChashValid`), and propagates synchronously up through `isValidChash` → `isValidAddress`/`isValidAddressAnyCase` into every code path that validates an address string supplied inside an untrusted, unsigned unit (author addresses, payment output addresses, definition template params, AA trigger addresses, etc.), all evaluated during `validation.js`'s `validate()` pipeline.

Because `network.js` explicitly turns any uncaught exception into a fatal process crash by design:
```js
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [4](#0-3) 

...a single malformed address string, submitted by any unprivileged unit poster as part of a normal unit (or private/AA context), can synchronously throw out of the entire async `validate()` call chain and bring down the full/hub node processing that unit.

### Impact Explanation
This maps to the "node unable to confirm new units" / DoS-on-validity impact class permitted by the scope rules: a crafted but syntactically valid 32-character address string (used, e.g., as a unit author address, a payment output address, or in a definition-template parameter) causes `isChashValid` to throw uncaught during validation. Since witnesses/hubs/full nodes all run the same validation code on every incoming unit, an attacker can repeatedly crash any node that attempts to validate the poisoned unit, disrupting network-wide consensus/availability — analogous to the DoS impact of CVE-2018-10360 where malformed input crashes the parser process.

### Likelihood Explanation
Likelihood is high for triggering the crash mechanically (any single unprivileged unit poster can submit such a unit without needing keys, funds, or privileged access), but I was **not able to fully verify** — due to index/tool limitations on inspecting the `thirty-two` npm dependency's exact decode behavior — whether a 32-character string using only valid base32 alphabet characters can actually decode to a byte length other than exactly 20 bytes. If `thirty-two.decode()` always emits exactly `Math.floor(len*5/8)` bytes for any 32-character input (32*5/8 = 20 bytes exactly, with no variable padding), then `binChash.length` would always be 160 for the 32-character path and the throw would be unreachable in practice for this specific input length. This needs confirmation directly against the `thirty-two` package source (not fully available in the indexed context) before treating this as a certain, exploitable crash.

### Recommendation
- Wrap the entire body of `isChashValid` (not just the decode call) in try/catch, and return `false` on any error instead of letting `separateIntoCleanDataAndChecksum`'s `Error` propagate.
- Explicitly validate `chash.length` (byte length of the decoded buffer) against the expected 20/36 bytes before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, returning `false` for any mismatch rather than throwing.
- More broadly, review the global `uncaughtException` handler in `network.js`: while crashing on truly unexpected internal errors is a reasonable safety measure, it means every unhandled `throw` reachable from untrusted unit content is a network-wide DoS primitive, so all length/format validation helpers reachable from unit validation should fail closed (return `false`/error) rather than throw.

### Proof of Concept
Not able to construct a concrete verified PoC input without confirming the exact byte-length behavior of `thirty-two.decode()` for a 32-character input (see Likelihood Explanation). Conceptually: submit a unit whose author `address` field (or any other field validated via `isValidAddress`) is a 32-character string composed of valid RFC4648 base32 characters that decodes to a buffer whose bit length is not exactly 160; feed the unit to a node via normal unit posting, and observe `chash.js`'s `separateIntoCleanDataAndChecksum` throw uncaught, triggering `network.js`'s `uncaughtException` handler and crashing the process.
