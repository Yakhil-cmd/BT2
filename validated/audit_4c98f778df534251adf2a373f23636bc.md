### Title
Webhook signature verification is scoped to an attacker-chosen organization while the event handlers act on unscoped, cross-repository data — allows unauthenticated status/commit forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook signature check in `WebhooksController#verify_signature` selects the GitHub App/secret to validate against using an organization name taken directly from the attacker-controlled JSON body, and `GitHubApp#verify_webhook_signature` silently treats "no secret configured for that org" as "verified." Meanwhile, the actual event processing (e.g. `StatusHandler`) never re-checks that the data it acts on belongs to the organization that was "authenticated." This breaks the binding: `organization that authenticated == repository/commit that is written`.

### Finding Description
`verify_signature` resolves the app used to check `X-Hub-Signature` purely from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (multi-org installs are an officially supported configuration, shown with a `webhook_secret` that can be left `nil`): [3](#0-2) [4](#0-3) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the resolved org has no `webhook_secret` set: [5](#0-4) 

Because `repository_owner` (the org used to pick the verifying secret) is read straight out of the same untrusted JSON body that is later reparsed and dispatched to handlers, an attacker can set `repository.owner.login`/`organization.login` to any organization configured in Shipit that has `webhook_secret` unset (or simply omit any known "safe" org that has no secret), causing signature verification to trivially pass, while the rest of the payload — used by the actual handler — references a totally different target. The `create` action re-parses the raw body and dispatches it unmodified: [6](#0-5) 

`StatusHandler` then acts on the payload's `sha` field with **no repository/organization scoping whatsoever** — it looks up `Commit` by SHA across the entire Shipit database: [7](#0-6) 

So the "organization that authenticated" (the org whose config happened to allow bypassing/passing signature check) and "the repository/commit that is written" (any commit in any stack, chosen by raw SHA string) are never checked to be the same entity — exactly the equality-breaking pattern described in the reference report (payer vs. sender in `createStream`).

### Impact Explanation
An attacker who knows (or guesses) that any organization configured in a multi-org Shipit deployment has no `webhook_secret` set can forge a `status` webhook event that is accepted as "verified," and inject an arbitrary commit status (e.g., `state: "success"`) onto any commit belonging to any other repository/stack tracked by that Shipit instance, regardless of which org owns it. Commit statuses are used by Shipit to determine mergeability/deployability of PRs in the merge queue, so this can be used to force a commit to appear "green" and unlock merges/deploys for a victim repository the attacker has no access to — this is a cross-repository write and can enable an unauthorized merge, matching the Critical impact bucket (cross-repository writes / unauthorized merge).

### Likelihood Explanation
Requires the host to have configured at least two GitHub organizations in `secrets.github`, with at least one lacking a `webhook_secret` — the documented multi-org configuration example explicitly shows `webhook_secret: # nil` as valid. Given this documented setup pattern, it is plausible for a real deployment. No authentication, GitHub App credentials, or repository write access is required from the attacker — only knowledge that a webhook-secret-less org exists.

### Recommendation
- Require `verify_webhook_signature` to fail closed when no secret is configured, rather than returning `true`.
- Cross-check that the org/repository derived from the payload used for signature verification matches the repository the handler actually mutates (e.g., scope `StatusHandler`'s `Commit.where(sha:)` lookup to the verified repository/stack, not a bare SHA match).
- Avoid keying webhook trust decisions on attacker-supplied fields in the same unverified payload used for the actual write.

### Proof of Concept
1. Configure Shipit with two orgs: `VictimOrg` (has `webhook_secret` set, hosts the target stack/commit) and `AttackerOrg` (no `webhook_secret`, e.g. left blank per the documented example config).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha in VictimOrg's stack>",
  "state": "success",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
No valid `X-Hub-Signature` is needed because `Shipit.github(organization: "AttackerOrg")` resolves to a `GitHubApp` with `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
3. `WebhooksController#create` dispatches the raw parsed body to `StatusHandler`, which finds the commit purely `Commit.where(sha: params.sha)` with no ownership check (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) and creates a forged "success" status on the victim's commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
