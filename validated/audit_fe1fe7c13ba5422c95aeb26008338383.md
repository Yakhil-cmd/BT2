### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` writes GitHub status webhook payloads to *every* `Commit` row that shares the reported SHA, without checking that the SHA belongs to the repository that authenticated the webhook. Because git SHAs are content-addressed and identical across forks/clones of the same commit, an attacker who owns a repository configured in Shipit (or a fork containing a commit shared with a victim's tracked history) can send a legitimately-signed `status` webhook that mutates a completely unrelated stack's commit status, flipping deployability/blocking for a `review_stacks_enabled true, allow_all` stack.

### Finding Description
The broken binding is: **a status update should only be applied to `Commit` rows belonging to the repository/stack that generated and signed the webhook**, i.e. `commit.stack.repository == payload.repository`. That binding is never checked.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This queries across the entire `commits` table by bare `sha` with no `stack_id`/repository filter, unlike other webhook handlers (e.g. the `pull_request` handlers) which explicitly resolve and scope to a `Repository`/`Stack` object before acting.

`Commit#create_status_from_github!` then delegates straight into `add_status`, which recomputes `status`, emits `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` — i.e. it directly affects deployability/merge decisions for whichever stack the matched `Commit` row belongs to: [2](#0-1) [3](#0-2) 

The webhook-level signature check (`WebhooksController#verify_signature`) is scoped per-**organization**, not per-repository-and-commit:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
``` [4](#0-3) 

This proves the payload came from *some* organization registered with Shipit, but it says nothing about which `Commit`/`Stack` the `sha` in the body is allowed to affect. Since git SHAs are content hashes, the same SHA legitimately exists in multiple repositories that share history (forks, mirrors, or a commit later merged upstream). An attacker who legitimately controls a repository onboarded to Shipit (their own fork/org) can push a commit, let CI run, and have GitHub emit a fully-signed `status` webhook for that SHA from their own repo/org. `StatusHandler` then applies that status to **every** `Commit` row in the database with the same SHA — including one belonging to a victim's stack that has `review_stacks_enabled: true, allow_all` — flipping the victim commit's `ci/circleci` status to `failure`, which alters `deployable?`, `blocked?`, and `stack.schedule_merges` behavior for the victim's auto-provisioned review stack (which executes `shipit.yml`).

None of the listed guards prevent this: `verify_signature` only authenticates the organization of the sender, not the target commit/repository being mutated; `drop_unhandled_event` and `ExplicitParameters` (`params do ... end`) only validate the shape of the payload, not repository ownership; there is no `require_permission!`/`stacks` scope check inside `StatusHandler`; and `Repository`/`Stack` model validations don't constrain which `Commit` a status can attach to.

### Impact Explanation
This is a payload for one (attacker-controlled) repository mutating another (victim) repository's stack/commit state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." A `failure` status on a required context can block deploys, and (per the question's scenario) a review stack with `allow_all` will auto-provision and execute `shipit.yml` for externally-opened PRs, so forcing status flips on shared-SHA commits can force ship/block decisions on infrastructure the attacker never authenticated against. The blast radius extends to any Shipit-tracked repository/stack that ever contains a commit whose SHA is reproducible by the attacker (forks, mirrors, cherry-picked/rebased-identical commits, or commits later merged upstream) — this is repeatable per SHA collision the attacker can arrange.

### Likelihood Explanation
Preconditions: (1) the attacker needs at least one repository/organization onboarded to Shipit that they control (to obtain a validly-signed webhook), and (2) a `Commit` row must exist in the victim stack with a SHA the attacker can reproduce (achievable via forking, sharing history, or waiting for a PR's commits to be merged upstream while Shipit already recorded that SHA under a different stack). The victim configuration required (`review_stacks_enabled true, allow_all`, required `ci/circleci` context) is explicitly named in the question. Attacker cost is low — no secrets, tokens, or privileged roles are needed, just ownership of any Shipit-registered repo and the ability to reproduce/share a target SHA, both of which are attainable by an unprivileged GitHub user via forking/PR workflows.

### Recommendation
Scope `StatusHandler#process` (and `Commit.where(sha:)` lookups generally) by the repository identified in the webhook payload, e.g. resolve `Stack`s via the payload's `repository.full_name` and restrict the `Commit` query to `stack_id`s belonging to that repository, mirroring the pattern used by the `pull_request` handlers.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or wherever handler tests live):
1. Create two `Stack`s, `victim_stack` (`review_stacks_enabled: true`, `allow_all` review config, requiring `ci/circleci`) and `attacker_stack`, backed by *different* `Repository` records.
2. Create a `Commit` with `sha: "deadbeef..."` under `victim_stack`, with an existing `success` status for `ci/circleci`. Assert `commit.deployable?` is `true` (or whatever the pre-condition equality is, e.g. `victim_commit.status.success? == true` and `victim_commit.blocked? == false`).
3. Create a second `Commit` row with the **same** `sha` under `attacker_stack` (simulating the shared/forked SHA).
4. Build a `status` webhook payload: `{ sha: "deadbeef...", state: "failure", context: "ci/circleci", repository: { full_name: attacker_stack.repository.full_name, owner: { login: attacker's org } } }`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(...).call(payload)` (or invoke via the controller with a signature valid for the attacker's own org).
6. Assert that `victim_commit.reload.status.state == "failure"` and `victim_commit.deployable? == false`, even though the webhook's `repository` field named only `attacker_stack.repository.full_name` — proving the write crossed repository boundaries and the pre/post binding (`commit.stack.repository == payload.repository`) diverged.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
