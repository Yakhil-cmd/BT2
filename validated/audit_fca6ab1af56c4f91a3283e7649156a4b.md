### Title
Bridge ERC20 Handle Nonce Permanently Stuck When Recipient Is Blacklisted — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`handleERC20Transfer` in the Kaia service-chain bridge updates nonce state and then calls `safeTransfer` to the recipient. If the recipient address is blacklisted by the ERC20 token (e.g., USDC), the `safeTransfer` reverts, rolling back all state changes including the vote closure. Because the operator vote key is bound to `keccak256(msg.data)`, operators cannot change `_to` to bypass the blacklist. The request nonce is permanently unhandleable, `lowerHandleNonce` is stuck forever, and the user's bridged assets are permanently lost.

### Finding Description

In `handleERC20Transfer`, the execution order is:

1. Nonce/state updates: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, `_updateHandleNonce`, and inside `_voteValueTransfer` → `closedValueTransferVotes[_requestedNonce] = true`
2. Token delivery: `IERC20(_tokenAddress).safeTransfer(_to, _value)` [1](#0-0) 

If `safeTransfer` reverts (e.g., USDC blacklist), the entire transaction reverts, including all state changes from step 1. The vote is not permanently closed (`closedValueTransferVotes` is reverted), so operators can retry — but they cannot change `_to` because the vote key is `keccak256(msg.data)`: [2](#0-1) 

All operators must submit identical calldata to reach quorum. Submitting a different `_to` creates a different vote key and leaves the original nonce permanently unhandled.

`_updateHandleNonce` advances `lowerHandleNonce` only when consecutive nonces starting from `lowerHandleNonce` are all filled: [3](#0-2) 

With nonce N permanently stuck, `lowerHandleNonce` never advances past N, and `recoveryBlockNumber` never advances past the block before N.

### Impact Explanation

- **Asset loss**: The user burned/locked tokens on the source chain via `requestERC20Transfer`. The destination bridge can never deliver the counterpart tokens. The assets are permanently lost.
- **Bridge nonce corruption**: `lowerHandleNonce` is stuck at N forever. `recoveryBlockNumber` is frozen at the pre-N block, causing the recovery system to perpetually re-scan from that old block.
- **No admin escape hatch**: There is no function to skip, redirect, or force-close a stuck nonce. The bridge owner can only lock/unlock tokens or stop the bridge entirely. [4](#0-3) 

### Likelihood Explanation

USDC is a commonly bridged token and maintains an on-chain blacklist. A user whose address is blacklisted after initiating a bridge request (or who is blacklisted on the destination chain but not the source chain) triggers this condition. The trigger requires only a valid bridge request from a subsequently-blacklisted address — no privileged access needed.

### Recommendation

Separate the nonce settlement from the token delivery. After quorum is reached and nonce state is committed, if the `safeTransfer` fails, store the funds in a claimable mapping keyed by `(_requestedNonce, _to)` rather than reverting. Alternatively, allow the bridge owner to redirect a stuck nonce's delivery to a different address (with appropriate governance controls).

### Proof of Concept

1. Alice holds USDC on the parent chain and calls `requestERC20Transfer` to bridge 1000 USDC to her address on the service chain. The `RequestValueTransfer` event is emitted with `requestNonce = N`.
2. Alice's address is added to the USDC blacklist on the service chain (or was already blacklisted there).
3. Bridge operators observe the event and call `handleERC20Transfer(..., _to=Alice, ..., _requestedNonce=N, ...)` on the service-chain bridge.
4. Quorum is reached; `closedValueTransferVotes[N] = true`, `handleNoncesToBlockNums[N]` is set, `_updateHandleNonce(N)` runs — then `IERC20(usdc).safeTransfer(Alice, 1000e6)` reverts because Alice is blacklisted.
5. The entire transaction reverts. All state changes are undone.
6. Operators retry with the same parameters — same result. They cannot change `_to` without breaking quorum (different `keccak256(msg.data)`).
7. `lowerHandleNonce` remains at N. `recoveryBlockNumber` is frozen. Alice's 1000 USDC on the parent chain is permanently lost. [5](#0-4) [6](#0-5)

    function _voteValueTransfer(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(!closedValueTransferVotes[_requestNonce], "closed vote");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
            closedValueTransferVotes[_requestNonce] = true;
            return true;
        }

        return false;
    }

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }
