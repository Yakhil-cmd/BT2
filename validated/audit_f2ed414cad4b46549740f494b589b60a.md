### Title
Webhook Signature Verification Uses `repository.owner.login` to Select the Trust Anchor While the Actual Write Target Is `repository.full_name`, Allowing Cross-Organization Payload Forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound payload against using `repository.owner.login` (or `organization.login`), but the handlers that actually mutate state (create commits, statuses, trigger syncs) resolve their target purely from `repository.full_name`, a separate, unrelated field in the same JSON body. These two identities are never cross-checked against each other, and if the App selected for verification has no `webhook_secret` configured, signature verification is skipped entirely (`return true unless webhook_secret`), letting an attacker author an arbitrary `repository.full_name` in the same forged request.

### Finding Description
`verify_signature` picks the GitHub App used to validate the HMAC based on `repository_owner`: [1](#0-0) [2](#0-1) 

That app's `verify_webhook_signature` unconditionally trusts the request if the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, every event handler resolves the actual write target — the `Repository`/`Stack` whose commits, statuses, or sync state get mutated — from a completely different field of the same payload, `repository.full_name`, with no linkage back to `repository.owner.login`: [4](#0-3) [5](#0-4) 

The binding that should hold is: `organization used to authenticate the payload == organization that owns the repository being written`. Before an attack, GitHub always sends these consistently, so the invariant holds implicitly. After an attacker-crafted request, the attacker can set `repository.owner.login` (or `organization.login`) to any onboarded organization whose GitHub App has no `webhook_secret` set — a state explicitly supported by the multi-org config schema (`config/secrets.yml` per-org `webhook_secret` is optional) — causing `verify_webhook_signature` to short-circuit to `true`, while setting `repository.full_name` to a target stack belonging to an entirely different (and properly secured) organization. The controller never checks that the app used for verification corresponds to the owner of the repository the handler is about to act on.

### Impact Explanation
This breaks a deployment-trust binding equivalent to the VRT Vault analog (a payload field acted upon — `full_name` — is never covered by the identity actually verified). Concretely, an attacker can:
- Forge `push` events that call `stack.sync_github(expected_head_sha: ...)` for an arbitrary target stack.
- Forge `status`/`check_suite` events that create fake successful CI statuses/check runs for a target repo's commits.

If the target stack has `continuous_deployment` enabled, injecting fake green statuses can drive `trigger_continuous_delivery` to deploy a commit whose CI checks were never actually run, resulting in an unauthorized deploy — matching the "High/Critical: unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires no privileged access, no token, and no repository write access — only that some organization/GitHub App instance registered on the Shipit deployment lacks a `webhook_secret` (a state the configuration schema explicitly permits, per-org, per `TOP_LEVEL_GH_KEYS`/`github_app_config` in `lib/shipit.rb`). Any operator with multiple orgs who leaves one App's secret blank (e.g., during onboarding, or for an internal/test org) unknowingly opens all other orgs' repositories on the same instance to forged webhook events.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub App/organization; refuse to boot or reject all webhooks for an org missing a secret rather than defaulting to "verified".
- Cross-validate that `repository.owner.login` (the identity used to select/verify the signing app) matches the owner segment of `repository.full_name` before dispatching to any handler, rejecting mismatches.

### Proof of Concept
1. Deploy Shipit with two organizations configured: `trusted-org` (has repos with continuous deployment enabled) and `throwaway-org` (onboarded without a `webhook_secret`, e.g. for convenience).
2. Attacker crafts a `status` (or `push`) webhook payload:
   ```json
   {
     "sha": "<head sha of trusted-org/app>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "trusted-org/app", "owner": { "login": "throwaway-org" } }
   }
   ```
3. Attacker sends `POST /webhooks` with `X-Github-Event: status` and any bogus `X-Hub-Signature` value.
4. `verify_signature` resolves `repository_owner` = `throwaway-org`, fetches its `GitHubApp`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
5. `StatusHandler` (via `Handler#repository_name` = `repository.full_name` = `trusted-org/app`) creates a forged successful status for `trusted-org`'s commit, potentially unblocking continuous deployment for a repo the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
