### Title
Unbounded chunked interest-accrual loop permanently bricks a stale market - (File: contracts/pool/src/interest.rs)

### Summary
The Kiwi TCMS report is a missing-rate-limit DoS: an unauthenticated endpoint consumes unbounded server resources per call. The on-chain analog in XOXNO Lending is `global_sync` in `contracts/pool/src/interest.rs`: interest is accrued in fixed `MAX_COMPOUND_DELTA_MS` chunks in an unbounded `while` loop whose iteration count is proportional to elapsed wall-clock time. Every state-changing pool entrypoint routes through this accrual, and the controller's permissionless `update_indexes` exposes it directly. Because the iteration count grows without bound and Soroban transactions have a hard CPU budget, any market whose `last_timestamp` falls far enough behind becomes impossible to sync — freezing all supply, borrow, withdraw, repay, liquidation, and revenue flows for that market permanently.

### Finding Description
`global_sync` splits the accrual gap `elapsed_ms = now - last_timestamp` into chunks of at most `MAX_COMPOUND_DELTA_MS` and iterates until `remaining == 0` (`contracts/pool/src/interest.rs:20-33`). There is no cap on the number of iterations and no way to accrue only part of the gap — the function either completes the entire catch-up or the transaction traps.

This loop executes inside `Cache` synchronization, which every pool operation performs before touching state, so it sits on the critical path of `supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `flash_loan`, `claim_revenue`, `recapitalize`, and `update_indexes`. The controller exposes a permissionless entrypoint `update_indexes(caller, assets)` that forwards an arbitrary caller-supplied `Vec<HubAssetKey>` to `pool_update_indexes_call` (`contracts/controller/src/markets.rs:119-125`), so any unprivileged address can invoke the accrual path for any listed market at will.

Two compounding properties make this a real DoS rather than a non-issue:

1. The cost is cumulative and monotonic. `last_timestamp` only advances when a sync succeeds; each real-world day that passes adds a fixed number of mandatory iterations to the *next* call. Once `elapsed_ms / MAX_COMPOUND_DELTA_MS` iterations exceed the per-transaction CPU budget, no transaction touching that market can ever complete, because every one of them must first run `global_sync` to completion.
2. There is no escape hatch. The protocol cannot skip accrual, cap the catch-up to a bounded window, or process it across multiple transactions — `accrue_chunk` only mutates in-memory cache state and `cache.mark_accrued()` (which stamps `last_timestamp`) runs only after the whole `while` loop finishes. A partial-catch-up transaction that traps mid-loop rolls back entirely, so even splitting the work manually is impossible.

The Certora documentation in the repo itself acknowledges this surface is unproven: "Long unbounded batch processing and arbitrary multi-year accrual loops remain outside the current proof model" (`certora/README.md`) and pool spec README lists "Unbounded multi-year accrual or arbitrary-length batch-loop induction" among what the proofs do not establish (`certora/pool/spec/README.md`).

### Impact Explanation
Permanent freezing of funds. Once the required chunk count for a market crosses the budget threshold, every entrypoint that syncs that market reverts — suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and governance cannot `claim_revenue` or `recapitalize` the market. Since `last_timestamp` can never be advanced (advancing it *is* the failing operation), the freeze is not temporary: absent a contract upgrade, the market's collateral and debt are locked forever. For a hub/spoke pool sharing one physical balance, a bricked market also blocks operations that touch the same cached pool state.

### Likelihood Explanation
No attacker action is needed to arm the condition — wall-clock time alone grows the iteration count, so an illiquid or abandoned market drifts toward the threshold on its own. An unprivileged attacker can additionally probe/trigger the failure at zero position risk via the permissionless `update_indexes`, and can hasten real-world onset on low-activity markets by ensuring no successful sync lands (e.g., griefing the sync transaction window is not needed — mere inactivity suffices). The exact threshold depends on `MAX_COMPOUND_DELTA_MS` (defined in `common::rates`) versus the Soroban CPU limit per transaction; with a chunk size measured in milliseconds-to-seconds, a gap on the order of days-to-months is enough to produce thousands of mandatory `accrue_step` invocations in a single transaction. Likelihood is moderate: it requires a market to go unsynced for an extended period, which is plausible for long-tail listed assets, and there is no mechanism bounding the growth.

### Recommendation
Bound the work per transaction and make catch-up resumable:

- Cap the number of `accrue_chunk` iterations per call (e.g., `MAX_ACCRUAL_STEPS`), persisting the intermediate `last_timestamp` after each chunk so partial catch-up commits and subsequent transactions resume where the last one left off; or
- Collapse long gaps mathematically: for `elapsed_ms > MAX_COMPOUND_DELTA_MS`, compute the compounded index directly (rate^k via exponentiation-by-squaring on `RAY` fixed-point) instead of iterating, turning O(gap) work into O(log gap); or
- As a defense-in-depth measure, clamp `elapsed_ms` to a maximum accrual window so a stale market accrues at most that window and resumes normally afterward (accepting the bounded interest shortfall as preferable to a permanent freeze).

Any of these must be paired with a regression test that seeds `last_timestamp` far in the past and asserts `update_indexes`/supply on that market still completes within budget.

### Proof of Concept
Conceptual reproduction (Soroban test env):

```rust
// Pool with one market created and synced at T0.
pool.create_market(&hub_id, &params);
pool.supply(&vec![&env, supply_entry(market, 0, amount)]);

// Advance ledger time by a gap G >> MAX_COMPOUND_DELTA_MS,
// e.g. one year: env.ledger().set_timestamp(T0 + 365*86_400);
env.ledger().set_timestamp(t0 + BIG_GAP);

// Any subsequent call must run global_sync over
// BIG_GAP_ms / MAX_COMPOUND_DELTA_MS iterations in ONE transaction.
// Each accrue_chunk performs several RAY mul/div ops, so CPU budget
// is exhausted well before the loop finishes -> tx traps, state rolls back.
pool.update_indexes(&vec![&env, market.clone()]); // exceeds budget
pool.withdraw(&vec![&env, withdraw_entry(market, 0, amount)]); // also trapped
```

After the trap, `last_timestamp` is unchanged, the gap remains, and no path exists to reduce it — the market is frozen. Root cause: `contracts/pool/src/interest.rs:26-30` iterates `while remaining > 0` with `chunk = min(remaining, MAX_COMPOUND_DELTA_MS)` and no iteration bound, and `cache.mark_accrued()` at line 32 only commits after full catch-up; the permissionless trigger path is `update_indexes` at `contracts/controller/src/markets.rs:119-125` calling `pool_update_indexes_call`.
