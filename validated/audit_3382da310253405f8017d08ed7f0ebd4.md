### Title
Cross-organization webhook forgery via `repository.owner.login`-selected signing key vs. `repository.full_name`-processed target - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (one `GitHubApp`/`webhook_secret` per GitHub organization), the field used to select which HMAC secret verifies a webhook (`repository.owner.login`) is not the same field used to determine which repository/stack the event is applied to (`repository.full_name`). An operator who controls a legitimate GitHub App installation (and its `webhook_secret`) for *their own* organization can forge a signed payload whose `repository.owner.login` matches their own org (so verification passes with a secret they legitimately possess) while `repository.full_name` is set to point at a repository belonging to a *different* tenant organization managed by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects the verifying `GitHubApp` using an organization value pulled straight out of the untrusted, attacker-suppliable payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization config (`secrets.github[org]`) and instantiates/caches a `GitHubApp` scoped to that org's own `webhook_secret`: [3](#0-2) 

Once the signature check passes, the same raw payload is dispatched to handlers, all of which derive the *actual* target repository/stack from a **different** field, `repository.full_name`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because verification binds trust to `repository.owner.login` while every downstream handler binds action to `repository.full_name`, these two fields are never required to be consistent. An attacker who legitimately controls the GitHub App/webhook secret for organization A can produce a validly-signed request where `repository.owner.login == "orgA"` (so `Shipit.github(organization: "orgA")`'s secret verifies it) but `repository.full_name == "orgB/some-repo"` — a stack belonging to a completely different, unrelated tenant organization B on the same Shipit instance. The equality that should hold — `verifying_org == acted_on_repository_owner` — is broken.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," letting a tenant with only their own org's webhook secret inject forged, validly-signed GitHub events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that Shipit will process as if they originated from another tenant's repository:
- `StatusHandler`/`CheckSuiteHandler` can inject forged CI/check statuses onto arbitrary commits of another org's stacks, which the merge queue and deploy safety checks rely on to gate merges/deploys — enabling an unauthorized merge or deploy for a repository the attacker does not control.
- `PushHandler` can trigger `GithubSyncJob` for another org's stack.
- `MembershipHandler` can create/delete `Team`/`Membership` records tied to another organization's teams, corrupting authorization data used elsewhere (`Shipit.github_teams`, `User#authorized?`).

This crosses a tenant/authorization boundary using only a credential (webhook secret) the attacker legitimately owns for their own org, satisfying the required "cross-repository writes"/"unauthorized merge or deploy" impact class.

### Likelihood Explanation
Requires the multi-organization GitHub App configuration (`TOP_LEVEL_GH_KEYS`/per-org `secrets.github[org]`), which is a supported, documented deployment mode, not a misconfiguration outside the engine's design. Any tenant admin who has a legitimate GitHub App installation (and therefore its webhook secret) for their own organization can exploit this without any additional access, session, or GitHub identity for the victim org. In single-organization deployments (the common case) this is not exploitable because there is only one webhook secret in the first place.

### Recommendation
Verify the webhook signature using the key selected by `repository.owner.login`, then additionally assert that `repository.full_name`'s owner segment matches the organization whose key was used to verify (or, more robustly, verify using the key derived from the actual repository being acted upon, not a separate `owner.login`/`organization.login` lookup performed pre-verification). Reject the webhook if the two disagree.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `secrets.github`: `orgA` (webhook secret known to the attacker, who administers orgA's GitHub App) and `orgB` (a stack/repository the attacker does not control, managed by the same Shipit instance).
2. Craft a `status` (or `push`) webhook JSON body with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/victim-repo"`
   - `sha`, `state`, etc. pointing at a real commit in an `orgB` stack.
3. Sign the raw body with `orgA`'s `webhook_secret` (`sha1=` HMAC as done in `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature`) and POST to `/github/webhooks` with `X-Hub-Signature` set accordingly and `X-Github-Event: status`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "orgA")` (from `repository.owner.login`) and successfully verifies the signature using the attacker-known `orgA` secret.
5. `StatusHandler` (via `Handler#repository_name` = `payload.dig('repository','full_name')` = `"orgB/victim-repo"`) applies the forged status to the commit in `orgB`'s stack, even though the attacker has no credentials for `orgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
