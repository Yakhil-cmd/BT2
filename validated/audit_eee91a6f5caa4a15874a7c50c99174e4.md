### Title
Webhook signature is verified against the organization named in `repository.owner.login`, while every event handler resolves the target `Stack`/`Commit` using the independently-attacker-controllable `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using `repository_owner` (`repository.owner.login`, falling back to `organization.login`), then verifies the *entire* raw POST body against that org's `webhook_secret`. [1](#0-0)  Once verification succeeds, the parsed payload is dispatched to handlers, but the handlers resolve which `Stack`/`Repository` to act on using a *different* field of the same payload: `repository.full_name`. [2](#0-1)  Because Shipit supports multiple configured GitHub organizations, each with its own independent `webhook_secret` (see the multi-org example in `config/secrets.development.example.yml`), the binding "organization whose secret authenticated the request" == "repository that gets written to" is never enforced - both values are attacker-chosen fields inside a single JSON body that the party holding *any one* configured org's `webhook_secret` can freely construct and sign.

### Finding Description
`verify_signature` picks the app/secret via:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

The HMAC check confirms only that *some* previously-configured organization's secret was used to sign *this exact byte string* - it says nothing about which repository the payload claims to describe. `Handler#stacks` / `#repository_name` then trust `repository.full_name` verbatim to look up the `Repository` and its `Stack`s:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler`, `CheckSuiteHandler` and other handlers use this `stacks` scope (or `Commit.where(sha:)` in `StatusHandler`, which is even less scoped) to trigger `sync_github`, `schedule_refresh_check_runs!`, or write commit statuses. [4](#0-3) [5](#0-4) [6](#0-5) 

**Before/after binding check**
- Equality the system relies on: `signing_org(repository.owner.login) == target_repo_owner(repository.full_name)`.
- Before the attack: for genuine GitHub-originated webhooks, `repository.owner.login` and the owner segment of `repository.full_name` are always identical because GitHub itself populates both from the same repository object.
- After the attack: an attacker who is a legitimate admin/owner of *any one* GitHub organization onboarded into this Shipit instance (and therefore knows that org's `webhook_secret`, which they themselves provisioned when creating their GitHub App) can POST an arbitrary JSON body directly to `/github/webhooks` (bypassing GitHub) with `repository.owner.login = "their-org"` (so `Shipit.github(organization: "their-org")` picks the secret they know) but `repository.full_name = "victim-org/victim-repo"` (any other repository tracked by the same Shipit instance). The HMAC is computed over their own crafted body with their own known secret, so `verify_signature` passes, and the handler acts on `victim-org/victim-repo` regardless of who "authenticated."

This exactly matches the requested binding class: "an organization that authenticated versus the repository that is written."

### Impact Explanation
This allows a party who administers only their own (possibly low-value/throwaway) GitHub organization/App integration to forge `push`, `status`, and `check_suite` webhook events for any *other* organization/repository tracked by the same Shipit installation:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for arbitrary branches/stacks of the victim repository, on demand. [4](#0-3) 
- `StatusHandler` writes arbitrary CI/commit statuses (`state`, `context`, `target_url`, `description`) onto any commit matched purely by `sha` across the whole install, with no repository scoping check at all - this can flip a victim commit's CI status to `success`, which downstream `continuous_deployment`/merge-queue logic in Shipit uses to decide whether to deploy or merge. [6](#0-5) 
- `CheckSuiteHandler` can trigger check-run refresh workflows against a victim stack's commits. [5](#0-4) 

Forging a "green" commit status for an unreviewed commit can lead to an unauthorized deploy being kicked off by Shipit's own deploy-triggering logic, which is one of the explicitly accepted Critical/High impacts.

### Likelihood Explanation
Requires the attacker to control one legitimate GitHub App/webhook integration already configured in Shipit's multi-org config (i.e., they know that org's `webhook_secret`) but does **not** require compromising the victim organization's secret, a Shipit session/user account, or any `ApiClient` token - the request goes straight to the public `WebhooksController` endpoint. This is realistic in any Shipit deployment onboarding multiple independent GitHub organizations (the exact scenario `config/secrets.development.example.yml` documents as supported), where different orgs are mutually untrusted tenants of one Shipit instance.

### Recommendation
After signature verification, cross-check that the authenticated organization actually owns the repository the payload claims to describe, e.g., derive the repository owner strictly from the same trusted `repository_owner` used for signature selection and reject/ignore the event if `repository.full_name.split('/').first` does not case-insensitively match `repository_owner` (and, for `membership`/`organization` events with no `repository` key, ensure handlers never fall back to trusting attacker-suppliable identifiers outside what was verified).

### Proof of Concept
1. Configure (or have access to) Shipit's multi-org secrets, where `attacker-org` and `victim-org` are both onboarded with distinct `webhook_secret`s (per the documented multi-org config format).
2. As the admin of `attacker-org`'s GitHub App, compute `sha1=<hmac>` over a crafted JSON body using `attacker-org`'s known `webhook_secret`:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-tracked-in-victim-stack>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `POST /github/webhooks` with header `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and verifies successfully because the attacker signed with the correct secret for that org. [7](#0-6) 
5. `PushHandler` resolves `stacks` via `repository.full_name = "victim-org/victim-repo"`, triggering `sync_github` on the victim's stacks despite the attacker never having proven any relationship to `victim-org`. [2](#0-1)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
