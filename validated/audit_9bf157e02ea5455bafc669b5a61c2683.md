### Title
Cross-tenant PR label/env injection via signature bypass on a no-secret configured org - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` config to authenticate against solely from the attacker-controlled `repository.owner.login` field, while the handler that actually mutates state (`LabelCapturingHandler`) resolves the target `Repository`/`ReviewStack` from a *different* attacker-controlled field, `repository.full_name`. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org's `webhook_secret` is blank, an attacker can pick an org configured in Shipit with no secret to satisfy `verify_signature`, then set `repository.full_name` to point at an unrelated victim repository whose review stack has `blocking_statuses` configured.

### Finding Description
The broken binding is: the org used to authenticate the webhook (`params.dig('repository','owner','login')`) is claimed to be the same org that owns the repository being mutated (`params.repository.full_name`)'s owner — but nothing in the code enforces `repository.owner.login == repository.full_name.split('/').first`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner)` [1](#0-0) , then `Shipit.github(organization:)` looks up that org's config via `github_app_config(organization)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/nil, regardless of the actual `X-Hub-Signature` header or body content [3](#0-2) . Multi-org configuration explicitly supports per-org optional `webhook_secret` (shown blank in `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), so a Shipit deployment can legitimately have one org configured without a secret while other orgs (including the victim's) have one.
- Once `verify_signature` passes, `WebhooksController#create` dispatches the entire attacker-controlled JSON body to the registered `pull_request` handlers, `LabelCapturingHandler` among them [4](#0-3) .
- `LabelCapturingHandler` resolves the target `repository`/`stack` from `params.repository.full_name` — a field entirely independent of `repository.owner.login` used for signature selection [5](#0-4) . On `action == "opened"` and `stack.present?`, it calls `capture_labels`, which persists `params.pull_request.labels.map(&:name)` onto the victim stack's `PullRequest` record [6](#0-5) .
- `ReviewStack#env` uppercases each persisted label name into an environment variable set to `"true"` and merges it into the deploy environment [7](#0-6) . If the victim stack's `blocking_statuses`/CI gating logic keys off such env-derived flags or an accompanying forced status (a separate but stacked primitive), the attacker-controlled labels can influence `blocked?` and downstream deploy gating for a repository the attacker never authenticated against.

Existing guards fail because: `drop_unhandled_event`/`check_if_ping` don't validate repository consistency; `ExplicitParameters` schema only validates types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; and `verify_signature` never re-derives or checks the owner implied by `full_name` against the one used to pick the HMAC key.

### Impact Explanation
An attacker who controls (or can name) a GitHub organization/app installation configured in the target Shipit instance with no `webhook_secret` can forge `pull_request` events attributed to a completely unrelated victim repository (`repository.full_name`), causing `LabelCapturingHandler` to write to that victim's `PullRequest.labels`, which become environment variables (`ReviewStack#env`) merged into the victim's review-stack deploy/task environment. This is a payload for one repository mutating another's stack/task state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any repository/stack as long as its full name is known, and is not limited to the attacker's own repositories.

### Likelihood Explanation
Requires a real precondition: the Shipit instance must be running the multi-org config schema (`secrets.github.<org>: {...}`) with at least one configured org whose `webhook_secret` is blank — a configuration explicitly documented and shown in example/dummy config files as acceptable (`webhook_secret: # nil`). If every configured org has a properly set `webhook_secret`, this path is closed for all orgs. Given that precondition, attacker cost is trivial: no credentials, no session, just an HTTP POST with a crafted JSON body and a `X-Github-Event: pull_request` header (the signature header value itself doesn't even matter). Fully repeatable and automatable.

### Recommendation
In `WebhooksController#verify_signature`, derive the authenticating organization from a single canonical, cross-checked field, and reject the request if `repository.owner.login` doesn't match the actual owner of `repository.full_name`. Additionally, do not allow `verify_webhook_signature` to trivially return `true` for blank secrets in a multi-org config unless that org has zero registered repositories in Shipit, or require `webhook_secret` to be mandatory for any org that has stacks/repositories configured.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure `Shipit.stubs(:secrets)` (or use `secrets_double_github_app.yml`-style fixture) with two orgs: `NoSecretOrg` (webhook_secret nil) and `VictimOrg` (webhook_secret set).
2. Create `victim_stack = shipit_stacks(:review_stack_fixture)` under `VictimOrg/victim-repo` with `blocking_statuses` configured and an associated `PullRequest`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature`, and body:
```json
{
  "action": "opened",
  "number": 2,
  "pull_request": { ... , "labels": [{"name": "malicious_flag"}] },
  "repository": { "owner": { "login": "NoSecretOrg" }, "full_name": "VictimOrg/victim-repo" },
  "sender": { "login": "attacker" }
}
```
4. Assert response is `:ok` (signature check passed despite no secret matching).
5. Assert `victim_stack.pull_request.reload.labels == ["malicious_flag"]` — i.e., `victim_stack.env["MALICIOUS_FLAG"] == "true"` — proving a payload authenticated under `NoSecretOrg` mutated `VictimOrg`'s stack state, violating the invariant that "a `pull_request` event only affects the repository/stack whose secret authenticated it."

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
