### Title
Uncaught exception in `evaluate` for `definition template` inside `validateAuthentifiers` crashes validation and blocks address usage - (File: definition.js)

### Summary
`Definition.validateAuthentifiers()` is called from `validateAuthor()` in `validation.js` without any surrounding `try/catch` for the async DB-query path, and the `'definition template'` branch of its internal `evaluate()` function throws a raw JS `Error` instead of returning an error via `cb2`/`fatal_error` when the referenced `definition_template` message cannot be found (or is ambiguous).

### Finding Description
In `definition.js` inside `validateAuthentifiers`'s inner `evaluate()`, the `'definition template'` case queries for the `definition_template` message referenced by an address definition: [1](#0-0) 

If the query returns anything other than exactly one row, the code does `throw Error("not 1 template")` instead of calling `cb2(false)`/setting `fatal_error` the way the sibling error paths in the same function do (e.g. `'sig'`/`'hash'` branches use `fatal_error = ...; cb2(false)`), and the way the analogous, non-authentifier validation path (`validateDefinition`) handles the exact same condition gracefully: [2](#0-1) 

Crucially, this `throw` executes inside the asynchronous callback of `conn.query(...)` — i.e., after the call stack that invoked `validateAuthentifiers` has already unwound. `validateAuthor()` in `validation.js` calls `Definition.validateAuthentifiers` with no `try/catch` around it at all: [3](#0-2) 

Because the throw happens inside a DB callback executed on a fresh stack, no enclosing `try/catch` (even if one existed higher up in the synchronous call chain) can catch it — it becomes an uncaught exception. The global handler in `network.js` explicitly re-throws uncaught exceptions to crash the process: [4](#0-3) 

This is functionally the same bug class as the Lybra report: a code path meant to check/evaluate something (there: an interface staticcall to a vault; here: a DB lookup for a `definition_template`) reverts/throws unconditionally instead of returning a controlled error, and that failure is unrecoverable by the caller, permanently blocking a legitimate operation (there: changing `safeCollateralRatio`; here: validating/using any address whose definition depends on `'definition template'` inside the signing path).

Only `validateDefinition()` (used for authors that supply their `definition` inline, and for asset conditions) contains the defensive `try { ... } catch(e) { if (e instanceof NoVarException) return cb(...) else throw e; }` handling around `replaceInTemplate`, and gracefully returns `"template not found or too many"` when the row count is wrong. The `validateAuthentifiers` copy of this logic (used to actually verify signatures against an existing address definition) omits both protections.

### Impact Explanation
If an address's on-chain definition (already established, i.e., not supplied inline in the unit) uses the `'definition template'` operator inside a signing/authentifier path, and by the time a later unit signed by that address is validated the referenced `definition_template` unit is no longer found with exactly one matching row before `last_ball_mci` (e.g., it was posted by a non-serial/losing unit, got reorganized, is not yet stable, or - in rarer cases - a duplicate/definition-template collision produced 2 matching rows), then `validateAuthentifiers` throws an uncaught exception during ordinary unit validation:
- Full nodes validating that unit crash (process termination via the `uncaughtException` handler), a "network unable to confirm new units" condition for any node that receives such a unit while relaying/validating it.
- Even absent a crash in some deployment contexts, the address becomes permanently unable to have any of its units validated/confirmed as long as this condition holds, i.e., unauthorized freezing/lock-out of the address's funds/AA triggers analogous to the "impossibility to change `safeCollateralRatio`" DoS — a legitimate poster is prevented from spending or triggering AAs from that address.

### Likelihood Explanation
The `'definition template'` op is a documented, supported primitive of the oscript address-definition language (also used by `wallet_defined_by_addresses.js`/shared address definitions and by asset conditions), reachable by any user who defines an address (or asset spend condition) using it. Triggering the exact race (template unit not yet stable/serial at validation time, later becoming unstable/replaced, or template being non-serial while the referencing unit's `last_ball_mci` moves past it) is a timing-dependent condition that is not part of normal happy-path usage but is fully reachable through ordinary protocol operations (posting a `definition_template` message and then relying on it in an address definition) without requiring any compromised node/peer, matching the Medium+ analog bar since it can be triggered by a single unprivileged unit poster.

### Recommendation
In `definition.js`, in the `'definition template'` branch of `validateAuthentifiers`'s `evaluate()` (around line 802-819), replace the `throw Error("not 1 template")` with a graceful failure via the same mechanism used elsewhere in this function (e.g., `fatal_error = "template not found or too many"; return cb2(false);`), mirroring the handling already present in `validateDefinition` (lines 306-343), and wrap `replaceInTemplate` in the same `try { } catch (e) { ... }` used there to avoid throwing on `NoVarException` or unexpected template shapes. Additionally, add a defensive `try/catch` around the call to `Definition.validateAuthentifiers` in `validateAuthor()` (`validation.js`) that converts any unexpected synchronous throw into a `callback(err)`, for consistency with how `signed_message.js` already wraps the same call.

### Proof of Concept
Conceptual reproduction (cannot be executed without live DB/test harness access, but the code path is deterministic):
1. Post unit U1 containing a `definition_template` message with payload `arrDefinitionTemplate` from address A.
2. Define address B with definition `['definition template', [U1, {param1: 'value'}]]` used inside a signing path, and get this definition accepted/stored for B (e.g., via an initial unit).
3. Ensure U1 becomes non-serial/loses the "good" sequence (e.g., a conflicting `definition_template` unit from the same address wins the race, or U1 remains unstable while another unit sets `main_chain_index`), such that the query in `validateAuthentifiers`'s `'definition template'` case:
   ```
   SELECT payload FROM messages JOIN units USING(unit)
   WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1
   ```
   returns 0 rows for `unit = U1` at the `last_ball_mci` used for validating B's next unit.
4. Post a new unit U2 signed by address B (using its definition template-based signing path).
5. Any node validating U2 calls `validateAuthor` → `Definition.validateAuthentifiers` → hits the `'definition template'` case, gets `rows.length === 0`, and executes `throw Error("not 1 template")` inside the `conn.query` callback, producing an uncaught exception that (per `network.js`'s `uncaughtException` handler) crashes the validating node process, while address B remains unable to get any unit validated until the condition resolves.
