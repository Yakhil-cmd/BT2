### Title
Membership webhook signature is verified against `repository.owner.login` while team scoping trusts the unbound `organization.login` field, allowing cross-organization `Shipit.github_teams` escalation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate the HMAC signature against based on `repository.owner.login`, falling back to `organization.login` only when no `repository` key is present. [1](#0-0) [2](#0-1) 

But `Shipit::Webhooks::Handlers::MembershipHandler`, which actually mutates authorization-relevant `Team` state, reads the organization to bind from a *different* field: `params.organization.login`, completely independent of whatever field (`repository.owner.login`) was used to select the verifying secret. [3](#0-2) [4](#0-3) 

### Finding Description
When Shipit is deployed with the documented multi-organization configuration (`docs/setup.md`, "Using Multiple GitHub Applications"), each organization has its own GitHub App and its own `webhook_secret`. [5](#0-4) 

`Shipit.github(organization:)` resolves per-organization config, and `verify_webhook_signature` compares the `X-Hub-Signature` against the HMAC computed with *that organization's* secret. [6](#0-5) [7](#0-6) 

The equality the engine is supposed to preserve is:
`organization whose secret verified the signature == organization whose Team/membership state is written`

The controller derives "the organization that authenticated" from `params.dig('repository','owner','login') || params.dig('organization','login')`, i.e. it prefers a `repository.owner.login` if the payload contains one at all. [2](#0-1) 

However, `membership` events are organization-level events; GitHub's real payloads for them do not naturally include a `repository` key. Nothing in `WebhooksController` or `MembershipHandler` enforces that `repository.owner.login` (used to select the verifying secret) must equal `organization.login` (used by the handler to write `Team#organization` and to add members). An attacker who controls one organization onboarded to this Shipit instance (i.e. who legitimately knows *that org's* `webhook_secret`, set when that org's GitHub App was configured) can craft a raw JSON body for a `membership` event where:
- `repository.owner.login` = their own (weakly-privileged) organization "OrgA" — used only to pick which secret verifies the signature,
- `organization.login` = the victim/target organization "OrgB" that is actually referenced in `Shipit.github_teams`,
- `team` = the id/slug/url of a real team in OrgB (guessable/observable, e.g. `shopify/developers`),
- `member.login` = the attacker's own Shipit user login.

They sign the raw body with OrgA's known `webhook_secret`. `verify_signature` selects OrgA's `GitHubApp` (because `repository.owner.login == "OrgA"`), verifies successfully, and the request proceeds to `MembershipHandler`, which binds/creates the `Team` using `organization.login == "OrgB"` and adds the attacker as a member. [8](#0-7) 

### Impact Explanation
`Team` membership drives Shipit's own authorization gate: `User#authorized?` checks whether the current user belongs to any team returned by `Shipit.github_teams`, which resolves teams by `organization/slug` handle from `secrets.github.oauth.teams`. [9](#0-8) [10](#0-9) [11](#0-10) 

Because the handler's `Team.find_or_create_by!(github_id:)` will create (or coerce) a `Team` row with `organization: "OrgB"` and the target `slug`, and `Team.find_or_create_by_handle` (used by `Shipit.github_teams`) simply looks the team up by `organization`/`slug`, an attacker able to forge a `membership` webhook that verifies under any onboarded organization's secret can add themselves (or anyone) as a member of a team that gates access into another organization's Shipit deployment — this is exactly the "escalation into `Shipit.github_teams` authorization" impact category, granting unauthorized access to trigger deploys/rollbacks scoped to that organization's stacks.

### Likelihood Explanation
This requires the multi-organization GitHub App deployment mode explicitly documented for Shipit, and requires the attacker to know the `webhook_secret` of at least one organization already onboarded to the shared Shipit instance — a realistic scenario in any Shipit deployment serving more than one team/organization, since each org's own administrators configure and know their own `webhook_secret`. No Shipit session, `ApiClient` token, or GitHub App private key is needed; the attacker only needs to POST a crafted request to the shared `/webhooks` endpoint with a signature computed from a secret they legitimately possess.

### Recommendation
In `WebhooksController#verify_signature`, do not let the payload choose which organization's secret validates the signature independent of which organization the event's handler will act on. At minimum, for events without a `repository` object, cross-check that the resolved verifying organization (`repository_owner`) is consistent with the organization the handler is going to use (`organization.login`) before dispatching, or bind the `Webhooks::Handlers::MembershipHandler` to only trust `organization.login` when it matches the organization key that successfully validated the signature. More robustly, associate each parsed webhook with the specific `GitHubApp`/organization instance that verified it, and pass that verified organization identity into every handler so the handler can never read a different, attacker-controlled organization field to decide what it writes.

### Proof of Concept
1. Deploy Shipit with two onboarded GitHub organizations, `OrgA` (attacker-administered) and `OrgB` (victim, referenced in `Shipit.github_teams` via `oauth.teams: ["orgb/developers"]`), each with its own `webhook_secret` per `docs/setup.md`'s multi-org config. [5](#0-4) 
2. Attacker builds a JSON body:
```json
{
  "action": "added",
  "team": { "id": 123, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/123" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-shipit-login" },
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and posts to `/webhooks` with `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as `"OrgA"`, looks up `Shipit.github(organization: "OrgA")`, and verifies successfully using OrgA's known secret. [1](#0-0) 
5. `MembershipHandler#process` runs, calling `find_or_create_team!`, which sets/reuses `team.organization = "OrgB"`, then adds `attacker-shipit-login` as a member. [12](#0-11) 
6. `Shipit.github_teams` resolves `"orgb/developers"` to this same `Team` row; `current_user.authorized?` now returns `true` for the attacker's Shipit user, granting access despite having no real membership in `OrgB`. [9](#0-8) 

Note: I was not able to inspect the `teams` table's DDL (uniqueness constraints on `organization`/`slug`) within the tool's read limits, so I cannot fully confirm whether a *brand-new* forged `Team` row (mismatched `github_id`) would collide with or shadow a pre-existing legitimate `OrgB/developers` team versus creating a duplicate that `Team.find_or_create_by_handle` would still resolve to (it looks up by `organization`+`slug`, not `github_id`, so either scenario appears to reach the same authorization bypass, but this should be verified against the actual schema/migrations in a full session).

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    # Backward compatibility

      config = secrets.github

    @github[organization] ||= GitHubApp.new(organization, config)
