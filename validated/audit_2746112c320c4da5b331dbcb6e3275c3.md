### Title
Caller-selected flash-loan receiver can lose funds through an existing pool allowance - (File: `contracts/pool/src/ops/flash.rs`)

### Summary
`controller::flash_loan` is permissionless and accepts an arbitrary `receiver`, while the pool sends principal to that receiver and then repays itself with `transfer_from(pool, receiver, pool, amount + fee)` using the receiver’s standing token allowance. Because `receiver` is never required to authorize the outer call, an attacker can select a compatible receiver contract that already approved the pool and cause it to lose the flash-loan fee. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The controller exposes `flash_loan(caller, asset, amount, receiver, data)` to any authenticated caller, but only `caller` is authenticated; `receiver` is caller-supplied. [1](#0-0)  The pool verifies that `receiver` is a Wasm contract, transfers `amount` to it, invokes its `execute_flash_loan` callback, and then pulls `amount + fee` from `receiver`. [4](#0-3)  Repayment is performed solely by checking `asset.allowance(receiver, pool) >= amount + fee` and calling `asset.transfer_from(pool, receiver, pool, amount + fee)`, so the receiver never has to authorize `flash_loan` itself. [3](#0-2)  This is the same bug class as a user-controlled `from`: the allowance owner is selected by an unprivileged caller rather than authenticated by the protocol.

### Impact Explanation
A selected receiver receives `amount` and then has `amount + fee` pulled back, so each successful invocation causes a net loss of `fee`. [5](#0-4)  If the receiver granted a large or reusable allowance, the attacker can repeat the call until the receiver’s available balance is insufficient to cover another fee or the allowance is exhausted. This constitutes theft of user or contract funds.

### Likelihood Explanation
The attacker only needs their own authorization for `caller`, plus a victim Wasm contract that implements `execute_flash_loan` and has at least `amount + fee` of allowance to the pool. [1](#0-0) [3](#0-2)  This is more conditional than the original finding because the victim must be a compatible contract with a live allowance, but no victim signature, owner privilege, or leaked key is required.

### Recommendation
Do not use the caller-selected `receiver` as the `transfer_from` source. Require `receiver.require_auth()` before using its allowance, or make the authenticated `initiator` responsible for repayment and use `transfer_from(pool, initiator, pool, total_repayment)` only after validating the initiator’s allowance. If the callback contract must remain distinct from the initiator, explicitly authorize the repayment source separately from the callback recipient.

### Proof of Concept
1. Victim deploys or operates a Wasm contract exposing `execute_flash_loan` and leaves `amount + fee` allowance to the pool.
2. Attacker calls `Controller::flash_loan(caller = attacker, asset, amount, receiver = victim_contract, data = attacker_controlled_bytes)`. [1](#0-0) 
3. The pool transfers `amount` to the victim and invokes `execute_flash_loan` on it. [6](#0-5) 
4. After the callback, the pool checks `allowance(victim_contract, pool) >= amount + fee` and executes `transfer_from(pool, victim_contract, pool, amount + fee)` without requiring victim authorization for the flash-loan invocation. [7](#0-6) [3](#0-2) 
5. The victim’s balance changes by `+amount - (amount + fee) = -fee`; repeating the call while allowance and prior balance remain drains additional fees.
