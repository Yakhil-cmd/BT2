### Title
Cross-repository Status forgery via `StatusHandler#process` unscoped `Commit.where(sha:)` lookup leading to unauthorized PR merge - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a forged CI status to using `Commit.where(sha: params.sha)` with no repository scoping, unlike every other handler (`PushHandler`, `PullRequest::*Handler`) which use the `stacks` helper scoped via `Repository.from_github_repo_name(repository_name)`. A validly-signed `status` webhook from an attacker-controlled repository can therefore write a `Status` row onto a `Commit` belonging to an unrelated stack whenever the sha values collide, which then defeats `MergeRequest#any_status_checks_missing?` and lets `ProcessMergeRequestsJob` auto-merge the victim's PR.

### Finding Description
The broken binding: for a `status` webhook to legitimately affect stack `S`, it must hold that `payload.dig('repository', 'full_name') == S.repository.full_name`. `StatusHandler#process` never enforces this equality: [1](#0-0) 

Compare to `PushHandler`, which correctly resolves the target stacks from the webhook's own `repository.full_name` via the shared `Handler#stacks` helper before acting: [2](#0-1) [3](#0-2) 

`verify_signature` in `WebhooksController` only proves that the payload's `repository.owner.login` legitimately signed *its own* webhook (`Shipit.github(organization: repository_owner)`); it never restricts which shas or commits that webhook is permitted to touch: [4](#0-3) 

Because `Commit` rows are only unique on `(sha, stack_id)` (not on `sha` alone), the same sha can legitimately exist as separate `Commit` rows in multiple stacks (e.g. a PR opened from a fork shares the exact same git commit object/sha as it would if that commit existed in the upstream repo): [5](#0-4) 

Attack flow: attacker opens PR #N from `attacker/evil` (a fork) against `victim/prod`. Shipit creates/refreshes a `MergeRequest` whose `head` commit is looked up/created for the victim's stack with `sha = X` via `find_or_create_commit_from_github_by_sha!`: [6](#0-5) 

Before real CI reports on commit `X`, the attacker sends a `status` event whose `repository.full_name` is `attacker/evil` (validly signed for that repository/organization) claiming `sha: X, state: success`. `StatusHandler#process` runs `Commit.where(sha: X)`, which matches the victim's `Commit` row (stack = victim) purely because the sha is identical, with zero check that the webhook's repository matches that commit's stack repository. It then calls: [7](#0-6) 
which writes a `Status` using the *found commit's own* `stack_id` (the victim's), not the attacker's: [8](#0-7) 

This flips `any_status_checks_missing?` to `false` and `all_status_checks_passed?` to `true` for the victim's PR, so `reject_unless_mergeable!` no longer rejects it: [9](#0-8) [10](#0-9) 
and `ProcessMergeRequestsJob#perform` proceeds to `merge_request.merge!`, invoking `stack.github_api.merge_pull_request` with the app's own `GITHUB_TOKEN`: [11](#0-10) [12](#0-11) 

No existing guard catches this: `verify_signature` authenticates the *sender* repository, not the *target* commit's repository; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository identity; `reject_unless_mergeable!` trusts whatever `Status` rows exist for the head commit without checking their provenance.

### Impact Explanation
An unprivileged GitHub user who controls any repository where the Shipit GitHub App/webhook is validly configured (e.g. their own fork, if the app is installable per-repo/org) can inject fabricated `success`/`failure` CI statuses onto commits belonging to a completely different stack/repository, as long as the sha values coincide (trivially true for fork-derived PR commits sharing git history with upstream). This directly enables bypassing CI-gating on `victim/prod`'s merge queue and causes `Shipit::MergeRequest#merge!` to call GitHub's merge API using the app's privileged `GITHUB_TOKEN`, merging attacker-controlled code into the victim's default branch — an unauthorized merge (Critical, "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge"). The same primitive can also forge `failure` statuses to block legitimate merges, or manipulate `continuous_delivery` scheduling on unrelated stacks (`Status#schedule_continuous_delivery`), broadening the blast radius across any tenant/stack sharing the Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs a repository where a `status` webhook they send will pass `verify_signature` for *some* `Shipit.github(organization:)` configuration — most plausible when the Shipit GitHub App/webhook is installable on the attacker's own account/org, or when attacker forks live under the same monitored GitHub organization as the victim. They also need the target victim commit's sha to be discoverable/reproducible — trivial for fork-based PRs since git commit objects (and thus shas) are shared verbatim between fork and upstream. No Shipit credentials, sessions, or team membership are required, matching the stated unprivileged threat model. This is repeatable per-PR and per-stack.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the webhook's own repository, mirroring `PushHandler`/`PullRequest` handlers, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently filter through `Repository.from_github_repo_name(repository_name)`'s stacks/commits association before calling `create_status_from_github!`, so a webhook can never write a `Status` for a commit belonging to a different repository's stack.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`):
1. Create `stack_victim` for repository `victim/prod` and `stack_attacker` for repository `attacker/evil`.
2. Create a `Commit` for `stack_victim` with `sha: "sharedsha123"` and no `Status` rows (so `any_status_checks_missing?` is true).
3. Create a `MergeRequest` on `stack_victim` with `head` = that commit, `merge_status: 'pending'`, `mergeable: true`.
4. POST to `/webhooks` with header `X-Github-Event: status`, signature stubbed valid for `attacker/evil`, and body `{ "sha": "sharedsha123", "state": "success", "repository": { "full_name": "attacker/evil", "owner": { "login": "attacker" } } }`.
5. Assert `stack_victim.commits.find_by(sha: "sharedsha123").statuses.count == 1` and `state == 'success'` — proving the write for the victim repository was authenticated only by the attacker's repository's signature (binding `payload.repository.full_name ("attacker/evil") == commit.stack.repository.full_name ("victim/prod")` is false yet the write succeeds).
6. Run `ProcessMergeRequestsJob.perform_now(stack_victim)` with `Shipit.github.api.expects(:merge_pull_request)` set, and assert it is called — proving the forged cross-repo status caused an unauthorized merge.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
