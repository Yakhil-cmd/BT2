### Title
Cross-organization webhook forgery: HMAC signature is verified against the org derived from `repository.owner.login`, but handlers act on the org derived from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App Shipit deployment, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the inbound HMAC against using the payload's `repository.owner.login` field, while the webhook handlers (e.g. `PushHandler`) resolve the target `Stack`/`Repository` to act on using the payload's `repository.full_name` field. These are two different fields of the same JSON body, and nothing cross-checks that they refer to the same organization. An admin/insider of one legitimately-configured GitHub organization ("OrgA") who possesses OrgA's real `webhook_secret` can therefore forge a request whose `repository.owner.login` is `OrgA` (so it authenticates against OrgA's secret) but whose `repository.full_name` is `OrgB/some-repo` (a completely different tenant's stack), causing Shipit to process a push/sync event for a repository that OrgA has no legitimate relationship to.

### Finding Description
`Shipit.github` supports configuring multiple, independent GitHub Apps keyed by organization name for multi-tenant installs [1](#0-0) . The webhook signature check picks the app/secret to verify with as follows:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the signature check passes, the raw parsed payload is dispatched unchanged to event handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers, however, resolve their target repository/stack from a *different* field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

```ruby
class Repository < ApplicationRecord
  def self.from_github_repo_name(github_repo_name)
    repo_owner, repo_name = github_repo_name.downcase.split('/')
    find_by(owner: repo_owner, name: repo_name)
  end
``` [5](#0-4) 

`PushHandler` then triggers a resync against whatever stack `full_name` resolves to:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

Because `verify_signature`'s org-selection key (`repository.owner.login`) and the handlers' target-selection key (`repository.full_name`) are independent, un-cross-validated fields inside the same attacker-suppliable JSON body, the equality that should hold — "the organization whose secret authenticated the request == the organization owning the repository being acted upon" — is never enforced. In a single-GitHub-App configuration this is moot because there is only one secret/org; the exposure is specific to the documented "Using Multiple Github Applications" mode [7](#0-6) .

### Impact Explanation
Any actor with legitimate knowledge of one tenant's GitHub App `webhook_secret` (e.g., an org owner of OrgA who configured the GitHub App per the documented setup) can craft and sign an arbitrary webhook payload, then substitute `repository.full_name` to point at a stack belonging to a different, unrelated organization (OrgB) tracked by the same Shipit instance. This lets OrgA force `GithubSyncJob`/`stack.sync_github` to run for OrgB's stack on demand [6](#0-5) , which can advance OrgB's undeployed-commit queue state and, combined with continuous deployment being enabled on OrgB's stack, trigger deploys earlier/differently than OrgB intended — an unauthorized cross-organization side effect the requesting party is not entitled to cause. The severity is bounded because `sync_github`/`github_api` calls still use the *stored* repository owner to fetch the real GitHub App token (`Shipit.github(organization: repository.owner)`), so OrgA cannot fabricate fake commit content; the impact is limited to unauthorized triggering/timing manipulation of sync and downstream continuous-delivery behavior for a repository outside the caller's authority, not arbitrary code injection or credential theft.

### Likelihood Explanation
Requires a Shipit instance configured with the multi-organization GitHub App schema (an explicitly documented and supported configuration) and requires the attacker to be an administrator of at least one of the configured organizations (with access to that org's own webhook secret) — this is a materially lower bar than needing the target organization's own secret, GitHub App private key, or a Shipit API token, and it does not require any Shipit session, ApiClient token, or repository write access on GitHub itself.

### Recommendation
When processing a webhook, verify that the organization owning `repository.full_name` (or `params.dig('organization','login')`) matches the organization (`repository_owner`) whose secret validated the signature before dispatching to handlers, and reject (422) any payload where these disagree.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgA` (secret `S_A`) and `OrgB` (secret `S_B`), each with its own tracked repository/stack, per `docs/setup.md`'s multi-org schema.
2. An OrgA administrator, who legitimately knows `S_A`, crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<some sha reachable in OrgB/target-repo>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
   }
   ```
3. Computes `X-Hub-Signature: sha1=HMAC(S_A, body)` and POSTs it to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully against `S_A` [8](#0-7) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on OrgB's stack [6](#0-5) , despite the request never being authenticated as belonging to OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
