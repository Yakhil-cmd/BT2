### Title
Unsynchronized access to global unit-cache state (`storage.assocUnstableUnits` / `assocBestChildren`) via unlocked `light/dry_run_aa` AA-trigger simulation racing with real unit validation/stabilization - (File: aa_composer.js)

### Summary
The `light/dry_run_aa` network command lets any peer (no authentication, no wallet ownership required) ask the node to simulate an AA trigger via `aa_composer.dryRunPrimaryAATrigger()`. Unlike every other code path that mutates the shared in-memory DAG caches (`storage.assocUnstableUnits`, `storage.assocBestChildren`, `storage.assocStableUnits`), this dry-run path takes **no mutex** at all before reading and mutating those same global objects. Real unit processing (`validation.validate`, `writer.saveJoint`, `main_chain.updateMainChain`, AA trigger execution via `handleAATriggers`) all serialize their cache mutations behind `mutex.lock([...])`. The dry-run path can interleave with these through Node's event loop (multiple pending async DB/kvstore callbacks), corrupting the shared caches — the same “unsynchronized shared-state access during a state-machine-critical operation” bug class as the EVerest phase-switch CVE, translated to ocore's cooperative-concurrency (event-loop) model.

### Finding Description
`dryRunPrimaryAATrigger` (aa_composer.js:272-306) is invoked directly from the network handler for `light/dry_run_aa` (network.js:3939-3963) with **zero locking**: [1](#0-0) [2](#0-1) 

Contrast this with every legitimate mutator of the same caches, which explicitly takes a mutex before touching `storage.assocUnstableUnits`/`assocBestChildren`/`assocStableUnits`:
- Real AA trigger execution is serialized under `mutex.lock(['aa_triggers'])`: [3](#0-2) 
- Unit validation/write is serialized under `mutex.lock(arrAuthorAddresses, ...)` and later `mutex.lock(["handleJoint"|"write"])` in various write/stabilization paths: [4](#0-3) [5](#0-4) 

`dryRunPrimaryAATrigger` internally calls `handleTrigger`, and on completion calls `revertResponsesInCaches`, which directly deletes entries from `storage.assocUnstableUnits` and mutates `storage.assocBestChildren` (via `_.pull`) with no synchronization: [6](#0-5) [7](#0-6) 

These exact caches are read by concurrent legitimate operations that assume they are internally consistent, e.g. `readBestChildrenProps` (used during main-chain/stability computation) and `readUnitProps` (used pervasively during validation and stabilization), both of which cross-check the in-memory cache against the DB and `throw Error(...)` on any mismatch: [8](#0-7) [9](#0-8) 

Because `dryRunPrimaryAATrigger` runs unlocked, an attacker-triggered dry run can be interleaved (via Node's async callback scheduling across `db.takeConnectionFromPool`, `conn.query`, `kvstore` operations) with a concurrently-processing real unit that is being validated or whose stability is being advanced. The dry run's `forgetUnit`/`fixIsFreeAfterForgettingUnit`/`_.pull` mutations on `assocUnstableUnits`/`assocBestChildren` can remove or alter cache entries mid-flight of the real operation's read of the same structures, producing either:
- A thrown consistency-check error (`storage.js:1547-1550`, `main_chain.js:720-721`) that crashes the node process handling the unit, or
- Silent corruption of the `is_free`/best-children bookkeeping used by main-chain/stability calculations, which can cause this node to diverge from other nodes on which unit is free/best-parent/stable — i.e., node disagreement on validity/stability.

This mirrors the EVerest bug class precisely: an externally-triggerable operation (`ac_switch_three_phases_while_charging` / here `light/dry_run_aa`) mutates shared state that the core execution loop (state-machine loop / here unit validation + AA trigger + stabilization loop) also mutates, without a common lock protecting both paths.

### Impact Explanation
If the race causes the in-memory DAG caches to diverge from the database (or from other nodes' caches), the node can:
- Crash on the internal consistency assertions in `storage.js`/`main_chain.js` (denial of confirmation ability for that node), or
- Silently compute an incorrect `is_free`/best-parent/stability state, which feeds into stability determination and unit validation for subsequent units — potentially causing this node to accept/reject units differently than honest peers (node disagreement on validity or stability), which is a prerequisite for stable-output double-spend disputes.

This satisfies the "network unable to confirm new units" / "node disagreement on validity or stability" bar required by the analog rules.

### Likelihood Explanation
`light/dry_run_aa` is an unauthenticated, publicly reachable network command available to any peer/light client (per the CVSS vector AC:H/PR:N/UI:N — access complexity high because precise timing of the interleave is required, but no privileges or user interaction needed). An attacker who also posts/triggers real AA-related units to the same node can deliberately time repeated `light/dry_run_aa` calls to increase the chance of an unlucky interleave with the node's own concurrent unit processing, similar to how the EVerest bug required a timed concurrent phase-switch request.

### Recommendation
Wrap `dryRunPrimaryAATrigger` (and `estimatePrimaryAATrigger`) in the same mutex domain used by real trigger execution and unit writes (e.g., `mutex.lock(['aa_triggers', 'write'])` or a dedicated read-lock that excludes concurrent cache mutation), so dry-run simulations cannot interleave their cache mutations/reads with genuine validation/stabilization. Alternatively, make dry-run code operate strictly on deep-cloned snapshots of `storage.assocUnstableUnits`/`assocBestChildren` rather than the live shared objects, and ensure `revertResponsesInCaches` never touches the shared caches for units created purely for simulation purposes.

### Proof of Concept
1. Deploy an AA definition on a full node.
2. From an unauthenticated peer connection, repeatedly send `light/dry_run_aa` requests referencing that AA address while concurrently posting real units that trigger the same AA (or units on which the target node is computing stability, e.g., near a main-chain index boundary).
3. Observe interleaving: `dryRunPrimaryAATrigger`'s `revertResponsesInCaches` (aa_composer.js:1900-1916) may run its `storage.forgetUnit`/`fixIsFreeAfterForgettingUnit` calls in between the point where the real validation/stabilization code (e.g., `readBestChildrenProps`, `readUnitProps`) has read `assocUnstableUnits`/`assocBestChildren` but not yet finished its own dependent DB writes.
4. This triggers either the `throwError("different props...")`/`throwError("different best children...")` assertions in `storage.js`/`main_chain.js`, crashing the node, or leaves inconsistent `is_free`/best-child state that diverges from the database and from peers.
