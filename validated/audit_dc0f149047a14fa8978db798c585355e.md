### Title
Webhook secret selection field is decoupled from the repository field acted upon, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate a request against based on `repository_owner`, a value read straight out of the untrusted JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Every event `Handler` then determines *which repository/stack to act on* using a different payload field, `payload.dig('repository', 'full_name')`. Because the HMAC signature only proves "this raw body was signed with the secret belonging to whatever organization `repository_owner` names," and does not bind that organization to `repository.full_name`, an attacker who legitimately controls one onboarded GitHub organization (and therefore knows its `webhook_secret`) can forge a payload where `repository.owner.login` names their own org (to pick the secret they know) while `repository.full_name` names a completely different, victim organization's repository. [1](#0-0) [2](#0-1) 

### Finding Description
The binding that should hold is:
`organization whose webhook_secret authenticated the request == owner of the repository the handler acts on`

`verify_signature` computes the verifying `GitHubApp` from `repository_owner`:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

Every registered `Handler` subclass (e.g. `PushHandler`, `CheckSuiteHandler`) resolves the target `Stack`/`Repository` via a *different* field of the same attacker-controlled JSON body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Because Shipit supports multiple GitHub Apps/organizations sharing one instance (`config/secrets.yml` → `github.<org>.webhook_secret`), each organization gets its own secret [5](#0-4) . Any org owner who legitimately installs the app on their own org obtains a valid `webhook_secret` for that org. GitHub's HMAC signature only certifies "the party holding this secret produced this exact byte string" — it says nothing about which repository name is *semantically* allowed to appear inside that byte string. The controller uses one field (`repository.owner.login`) to pick which secret to trust, but the code paths that actually mutate state use a completely independent field (`repository.full_name`) taken from the same trusted-because-signed blob. Nothing re-validates that `full_name`'s owner equals the `repository_owner` used for verification, nor that the repository is actually associated with that organization/installation on GitHub's side.

`StatusHandler` compounds this further: it does not use `repository_name`/`stacks` scoping at all, and instead updates *any* `Commit` matching the given `sha` across the entire Shipit instance regardless of repository [6](#0-5) .

### Impact Explanation
An attacker who administers a GitHub organization/app configuration that is legitimately onboarded onto the shared Shipit instance (and thus knows that org's `webhook_secret`) can forge a `push` (or `check_suite`/`status`) webhook whose `repository.owner.login` matches their own org (so it passes signature verification with their own known secret) but whose `repository.full_name` names a victim organization's repository also configured on the same instance. This causes:
- `PushHandler` to enqueue `stack.sync_github(expected_head_sha: ...)` against a victim stack the attacker does not control, forcing a GitHub sync to an attacker-chosen SHA [7](#0-6) .
- `CheckSuiteHandler`/`StatusHandler` to inject fabricated CI/check-run/commit-status data for a victim's commits, which downstream deploy-safety logic (`deployable?`, CI gating) relies on to decide whether a commit can be deployed [6](#0-5) .

This is a cross-repository/cross-organization write reachable without any Shipit session, API token, or GitHub write access to the victim repository — only knowledge of a webhook secret for *any* organization configured on the same multi-tenant Shipit instance. Forged CI/status data feeding deploy-safety checks can enable an unauthorized deploy of an attacker-chosen commit in the victim stack, satisfying the "unauthorized deploy" / cross-repository-writes impact bar.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration, see `docs/setup.md`), and requires the attacker to legitimately control one such onboarded organization. This is a real, unprivileged-relative-to-the-victim attack path (the attacker has zero rights on the victim org/repo) reachable purely by crafting and POSTing an HTTP request to `/webhooks`; no session, API token, or private key of Shipit's own GitHub App is needed for the victim side.

### Recommendation
After verifying the signature with the secret selected by `repository_owner`, re-validate that every subsequent handler operates only on repositories that actually belong to that same, signature-verified organization — e.g., have `Handler` reject processing (or re-derive the target repository) if `payload.dig('repository','owner','login')` does not match the organization whose secret validated the request, and additionally scope `StatusHandler`'s `Commit` lookup by repository instead of a bare `sha`.

### Proof of Concept
1. Attacker legitimately administers `attacker-org` and it is configured in `config/secrets.yml` under `github.attacker-org.webhook_secret = S`.
2. Attacker crafts a payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker knows `S`.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing an unauthorized sync/action on a stack the attacker has no rights to.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
