### Title
Cross-organization webhook forgery via unscoped `StatusHandler`/repository-field mismatch enables unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, then validates the signature using that organization's specific `webhook_secret`. Once verified, event handlers act on a *different* field of the same attacker-controlled payload — `repository.full_name` (via `Handler#repository_name`) or, worse, nothing at all in `StatusHandler`, which looks up commits globally by `sha` with no organization/repository scoping whatsoever.

### Finding Description
`verify_signature` picks the GitHub App/secret to verify against using: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple, independently-secreted GitHub organizations on one instance: [3](#0-2) [4](#0-3) 

An attacker who legitimately administers (or has push/webhook-configuring rights on) **one** onboarded organization, `attacker-org`, knows that organization's `webhook_secret`. Because the entire raw POST body is attacker-supplied, they can craft an arbitrary JSON payload, set `repository.owner.login` (or `organization.login`) to `attacker-org` to pass `verify_signature`, and sign it themselves with `attacker-org`'s secret — this satisfies the HMAC check exactly as the real code expects, since `verify_webhook_signature` only checks the signature against the secret indicated by the payload itself: [5](#0-4) 

The handlers then never re-validate that the organization which produced a valid signature actually owns the target resource:
- `Handler#repository_name`/`#stacks` derives the acted-upon repository from `repository.full_name`, a field completely independent from the `repository.owner.login`/`organization.login` used for signature routing: [6](#0-5) 
- `StatusHandler#process` is even more permissive: it never touches `repository` at all, and updates the CI status of **any** commit anywhere in the database purely by `sha`: [7](#0-6) 

So the equality that should hold — `organization authenticated by the signature == organization/repository the handler is permitted to mutate` — is not enforced anywhere. The attacker's payload lets them satisfy the left side using their own org's credentials while controlling the right side (target `sha`/`full_name`) to point at a victim's stack.

### Impact Explanation
Setting a fabricated commit status (e.g., a required CI context set to `success`) on a victim's commit is consumed directly by deploy-gating logic: [8](#0-7) [9](#0-8) 

`deployable?` and `schedule_continuous_delivery` are driven purely by the (forged) `status`/`check_run` records, and for stacks with `continuous_deployment?` enabled this can trigger an actual unauthorized deploy of a victim's stack purely from a spoofed webhook signed with a completely unrelated organization's secret. Even without continuous deployment, an operator could be tricked into manually deploying a commit whose CI/checks were spoofed to "green." `PushHandler`/`CheckSuiteHandler` similarly select the target stack via the independently-controlled `repository.full_name` field rather than the organization verified by the signature, allowing an attacker to trigger `GithubSyncJob`/`RefreshCheckRunsJob` against a victim repository they don't administer. This satisfies the "unauthorized deploy" / cross-repository-write class of Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate administrator of (or have webhook-secret access to) **any single** organization already onboarded to the shared Shipit instance — a normal, low-privilege, documented multi-tenant configuration (`docs/setup.md`). No access to the victim organization, no GitHub App private key, and no Shipit session/API token are required; the attacker directly POSTs a crafted, self-signed request to `/webhooks`. This is a realistic scenario for any Shipit deployment shared across multiple orgs/teams.

### Recommendation
After signature verification succeeds for organization `X`, enforce that every resource-identifying field used by the handler (`repository.full_name`, `repository.owner.login`, commit `sha` scoping, etc.) actually belongs to organization `X`. Concretely:
- In `WebhooksController`, derive the organization once, verify the signature, and pass the verified organization into the handler dispatch so handlers can reject payloads whose `repository.full_name`'s owner differs from the verified organization.
- Fix `StatusHandler` (and any other handler that doesn't scope by repository) to scope `Commit` lookups to stacks whose `Repository#owner` matches the verified organization, mirroring the `stacks`/`repository_name` pattern already used elsewhere, rather than an unscoped global `Commit.where(sha:)`.
- Reject any webhook whose `repository.owner.login` does not match `repository.full_name`'s owner segment.

### Proof of Concept
1. Attacker administers `attacker-org`, which is onboarded to the shared Shipit instance and has a known `webhook_secret` (`attacker-org`'s own GitHub App webhook secret, which the attacker legitimately possesses).
2. Attacker identifies a public commit `sha` belonging to `victim-org/victim-repo`, a stack hosted on the same Shipit instance with `ci.require` including a status context (e.g., `"ci/tests"`) and `continuous_deployment: true`.
3. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "description": "spoofed",
  "created_at": "2026-09-01T00:00:00Z"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (since it was signed with that org's real secret).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, setting a fake "success" status.
7. If `victim-org/victim-repo`'s stack has continuous deployment enabled and this was the last blocking status, `Commit#schedule_continuous_delivery` triggers `ContinuousDeliveryJob`, resulting in an unauthorized deploy of the victim's stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
