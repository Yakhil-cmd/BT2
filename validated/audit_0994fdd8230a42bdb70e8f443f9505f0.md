### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the affected stack/repository is resolved from the separate, unchecked `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository.owner.login` from the JSON body, while every event handler (`PushHandler`, `CheckSuiteHandler`, pull-request handlers) resolves the *actual* repository/stack to mutate using the sibling field `repository.full_name` via `Handler#repository_name`/`Handler#stacks`. Because these two fields are never cross-validated against each other, a valid signature for organization A does not guarantee the payload's `full_name` also belongs to organization A.

### Finding Description
`verify_signature` computes the org used for signature verification as: [1](#0-0) [2](#0-1) 

with `repository_owner` sourced only from `repository.owner.login` (or `organization.login`). This determines which `Shipit.github(organization:)` config, i.e. which per-org `webhook_secret`, verifies `X-Hub-Signature` in `lib/shipit/github_app.rb`: [3](#0-2) 

Once the signature is accepted, the full raw JSON `params` (attacker-authored, since HMAC only proves *which secret* signed it, not that GitHub generated the content) is dispatched to handlers unchanged: [4](#0-3) 

Every handler resolves the target stack(s) purely from `repository.full_name`, completely independent of `repository.owner.login`: [5](#0-4) 

This is used directly by `PushHandler` (triggers `stack.sync_github`), `CheckSuiteHandler` (schedules check-run refresh, which can gate continuous deployment), and the pull-request handlers: [6](#0-5) [7](#0-6) 

`StatusHandler` doesn't even use `repository` at all - it matches purely by commit `sha`, which is even weaker cross-tenant isolation: [8](#0-7) 

**The broken binding, stated as an equality that must hold but doesn't:**
`org(secret that validated signature) == org(repository.full_name that the handler writes to)`

Shipit explicitly supports multi-org configuration, each with its own independent `webhook_secret`, as documented in `docs/setup.md` and `config/secrets.development.example.yml`: [9](#0-8) 

So in any Shipit instance onboarding more than one organization (the documented, intended use case), a person who legitimately knows one org's `webhook_secret` (e.g. an org owner who configured their own GitHub App's webhook secret, or anyone who obtained it through that org's own GitHub App settings) can sign an arbitrary payload with `repository.owner.login` set to *their own* org (so `verify_signature` picks and successfully validates against their own secret) but set `repository.full_name` to `victim-org/victim-repo` (a completely different tenant's stack in the same Shipit install). Nothing re-checks that `full_name`'s owner segment matches `repository.owner.login`.

### Impact Explanation
This crosses a repository-write trust boundary without requiring the victim org's credentials: an attacker who controls only their own tenant's webhook secret can inject fabricated GitHub events (`push`, `status`, `check_suite`, `pull_request`) that are attributed to and acted upon another organization's stack:
- Forged `push` events trigger `stack.sync_github` (`GithubSyncJob`) against a victim stack using attacker-chosen `after` SHA.
- Forged `check_suite` events can mark commits' check runs for refresh, which factors into whether continuous deployment auto-ships a commit.
- Forged `status` events create fabricated CI statuses on arbitrary commits by SHA, which likewise gates whether Shipit's continuous delivery considers a commit deployable.

This is a cross-repository/cross-tenant write achieved purely by exploiting the mismatch between the authentication field (`repository.owner.login`) and the write-target field (`repository.full_name`), matching the "unauthorized deploy/rollback" and "cross-repository writes" impact class.

### Likelihood Explanation
This requires a multi-org Shipit deployment (explicitly documented and supported) and requires the attacker to legitimately possess one organization's own `webhook_secret` — something any org admin configuring their own GitHub App integration would have, without any need for GitHub org membership, repository write access, or a Shipit session/API token. No privileged Shipit access is needed at all; only knowledge of one tenant's webhook secret, which is by design distributed to that tenant's own admins.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, after verifying the HMAC, validate that `repository.full_name`'s owner segment matches the `repository_owner` (or `organization.login`) that selected the signing secret, and reject the webhook otherwise. Alternatively, derive the target repository/stack lookup from the same authenticated org field used for signature verification rather than the independent `full_name` field.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` (secret `S_A`, known to the attacker) and `victim-org` (secret `S_V`, unknown to the attacker), per the multi-org config in `docs/setup.md`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully against `S_A`.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack — despite the request never being signed by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
