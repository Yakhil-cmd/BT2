### Title
Webhook authentication binds to the payload's `organization`, but repository writes trust an unverified `repository.full_name` field, allowing cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook by looking up a GitHub App/secret using `repository.owner.login` (or `organization.login`) from the JSON body, then HMAC-verifies the *entire* raw body against that org's secret. Once verification passes, `create` re-parses the same body and dispatches it to handlers that resolve the target `Stack`/`Repository` using a *different* field of the same body: `repository.full_name`. Nothing ties these two fields together, so a payload signed with Org A's webhook secret can freely claim `repository.full_name = "OrgB/victim-repo"`, letting an attacker who legitimately controls Org A's own GitHub App/webhook forge push, status, check_suite, and pull_request events against any other repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` selects the signing secret based on the org named in the payload, not the repository actually referenced by the payload: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only checks that the HMAC over the raw body matches the secret for whichever organization was selected; it does not (and cannot) validate that the `repository` object embedded in that same body actually belongs to that organization's installation: [3](#0-2) 

After the signature check succeeds, the base `Handler` class and every push/status/check_suite/pull_request handler resolve the `Stack`/`Repository` to operate on using `repository.full_name` from the very same attacker-controlled body, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Shipit explicitly supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret`, which is exactly the scenario that makes this binding mismatch exploitable: [7](#0-6) 

**Binding broken:** *organization that authenticated the request* (`repository.owner.login`, used to pick the verifying secret) is treated as equal to *the repository that is written* (`repository.full_name`, used to look up the `Stack`/`Repository` a handler mutates), but the code never enforces this equality. An attacker who legitimately operates their own org/app registered in the same Shipit instance can sign a payload with their own secret while setting `repository.full_name` to point at an unrelated victim repository tracked by the same instance.

This is the same class of bug as the referenced Audius report: two semantically distinct concepts (here, "which secret verified this request" vs. "which repository this request is authorized to act on") are conflated into a single unchecked payload field, opening the door to a real security regression rather than a merely cosmetic ambiguity.

### Impact Explanation
Once a forged, signature-valid webhook can target an arbitrary tracked repository:
- A forged `status` event can mark an arbitrary commit SHA on the victim stack as `state: success` for any context, including contexts required by `ci.require`/blocking statuses. `MergeRequest#all_status_checks_passed?`/`#reject_unless_mergeable!` consult exactly these `Status` records, so this can make `MergeRequest#merge!` treat a malicious/unreviewed commit as mergeable, resulting in an **unauthorized merge**: [8](#0-7) [9](#0-8) 
- A forged `push` event queues `GithubSyncJob` for the victim stack, and forged `pull_request` `opened`/`closed` events can create or archive Review Stacks on repositories the attacker does not control: [10](#0-9) 

This satisfies the Critical bar ("unauthorized deploy, rollback or merge") since forged CI status can drive an unauthorized merge through the merge queue.

### Likelihood Explanation
The attacker needs only: (a) their own repository/organization already tracked by the target Shipit instance with its own configured GitHub App/webhook secret (a legitimate, non-privileged setup step available to any onboarded org in multi-org deployments), and (b) the ability to craft/replay an HTTP POST to the shared `/webhooks` endpoint with a body they sign themselves. No access to the victim's credentials, `GITHUB_TOKEN`, or webhook secret is required, and no Shipit session or `ApiClient` token is needed. This is realistic wherever a single Shipit deployment services more than one GitHub organization, which the engine explicitly documents and supports.

### Recommendation
After signature verification succeeds, verify that the `repository.full_name`'s owner segment (and/or `repository.owner.login`) used to route the event to a `Stack`/`Repository` matches the `repository_owner` value that was used to select the verifying GitHub App/secret. Reject the webhook (422) if they differ, e.g. in `WebhooksController#verify_signature`/`create`, or centrally in `Handler#repository_name`, so that the org bound to the signature is provably the same org that owns the repository being mutated.

### Proof of Concept
1. Operate Org A, install your own GitHub App on it, and register it in the target Shipit instance's `config/secrets.yml` (multi-org setup) so you legitimately know Org A's `webhook_secret`.
2. Build a `status` webhook JSON body: set `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"` (a repository tracked by the same Shipit instance but unrelated to Org A), with `sha` set to a commit you want to fast-track, and `state: "success"`.
3. Compute `X-Hub-Signature: sha1=<hmac>` over the raw JSON body using Org A's known `webhook_secret`, and POST it to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` selects Org A's app via `repository_owner` ("OrgA") and successfully verifies the signature; `create` then dispatches to the status handler, which creates/updates a `Status` for the victim commit in `OrgB/victim-repo`.
5. If that status context is part of `ci.require`/blocking statuses for the victim stack's pending `MergeRequest`, subsequent merge-queue processing calls `MergeRequest#merge!`, resulting in an unauthorized merge driven entirely by forged CI evidence the attacker manufactured using only their own org's credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(

        number,
        merge_message,

      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end

        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
