## Title
Cross-repository commit status forgery due to unscoped `sha` lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the GitHub organization named in `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) , but `StatusHandler#process` never checks that field, or any repository-scoping field, before writing data — it looks commits up **globally by SHA alone** and creates a status on every matching commit across the whole Shipit instance [3](#0-2) . This breaks the binding "organization authenticated == repository that is written," since a Shipit instance can host multiple independently-authenticated GitHub organizations (as shown by the multi-org secrets layout in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`).

### Finding Description
Every other webhook handler derives the target repository/stack from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks` [4](#0-3) , e.g. `PushHandler`, `OpenedHandler`, `ClosedHandler`, `ReopenedHandler` all call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting [5](#0-4) .

`StatusHandler`, however, only declares `sha`, `state`, `description`, `target_url`, `context`, `created_at`, and `branches` in its params block — it never declares or uses `repository` at all — and its `process` method resolves the target purely by SHA:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

Meanwhile `verify_signature` in the controller authenticates the request only against the org derived from `repository.owner.login` in the same payload the attacker fully controls [1](#0-0) . Because the HMAC signature only proves "this payload came from someone who knows organization A's `webhook_secret`" — it says nothing about which commit/repository the payload's data should be allowed to touch — an attacker who legitimately controls (or compromises) one org's GitHub App installation configured on a shared Shipit instance can sign an arbitrary `status` webhook body naming their own org (so `verify_signature` succeeds using their own known secret) while setting `sha` to a commit SHA that belongs to a completely different, victim organization/repository tracked by the same Shipit instance. Commit SHAs are not secret (they are visible on GitHub, in PR URLs, etc.), so obtaining a target SHA is trivial.

This exactly matches the reported bug class: a primitive (the commit-status write) acts on a field (`sha`) that is never covered by the trust boundary the signature check actually establishes (the organization named in `repository.owner.login`).

### Impact Explanation
This allows an org that is authenticated to a shared Shipit instance to write forged CI/commit statuses (`state`, `description`, `target_url`, `context`) onto commits belonging to a different organization's stack, without ever authenticating as that organization. Since Shipit's deploy/merge gating logic consumes `Commit#statuses` to determine mergeability/deployability, this is a cross-repository write that can be used to spoof a passing CI status on a victim's commit, potentially enabling an unauthorized deploy/merge decision on that commit. This satisfies the "cross-repository writes / unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Requires the attacker to control or compromise one legitimate, already-configured GitHub organization's webhook credentials on a Shipit deployment that hosts multiple organizations (a supported and documented configuration, per `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`). It requires no privileged Shipit account, API token, or victim credentials — only knowledge of a target commit's SHA, which is public information. Given a multi-tenant Shipit deployment, this is straightforward to exploit.

### Recommendation
In `StatusHandler`, require and validate the `repository.full_name` field (as all other handlers do) and scope the `Commit.where(sha: ...)` lookup to commits belonging to stacks of that specific repository (e.g., via `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join), rather than performing a global, cross-tenant SHA lookup.

### Proof of Concept
1. Shipit instance is configured with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (as supported by `config/secrets.development.shopify.yml`).
2. Attacker learns a commit SHA `abc123...` that exists in a stack belonging to `victim-org/victim-repo` (public information, e.g. from a PR link).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and a body:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
signed with `attacker-org`'s own `webhook_secret` via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully, since the attacker legitimately knows that org's secret [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the commit belonging to `victim-org/victim-repo`, and calls `create_status_from_github!` on it, writing the attacker-supplied `state`/`context`/`target_url` onto a commit the attacker never had access to [3](#0-2) .
