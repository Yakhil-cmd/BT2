### Title
Webhook signature is verified against the organization named in the untrusted payload, not the organization whose repository is actually acted upon, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting multiple GitHub Apps, one per GitHub organization, each with its own `webhook_secret` [1](#0-0) [2](#0-1) . When a webhook arrives, `WebhooksController#verify_signature` picks which app/secret to check the signature against by reading `repository_owner`, which is derived straight from the untrusted, unauthenticated JSON body (`params.dig('repository','owner','login')`), before any signature has been validated: [3](#0-2) [4](#0-3) 

The signature check itself is a plain HMAC comparison against that organization's `webhook_secret`: [5](#0-4) 

This is the equality that is supposed to hold: `organization whose secret authenticated the request == organization of the repository the payload subsequently mutates`. Because `repository_owner` (used only to *select the key*) and the rest of the payload (`repository.full_name`, used by the event handlers to resolve the actual `Stack`/`Repository` to act on) are both attacker-controlled fields inside the same forged JSON body, nothing enforces that they refer to the same organization.

### Finding Description
`verify_signature` never authenticates the request before extracting `repository_owner`; it uses that unauthenticated value only to look up which secret to check the signature with [3](#0-2) . Handlers that process the event body (e.g. `push`, `status`, `check_suite`, pull_request handlers) resolve the target repository/stack from `repository.full_name` in the same JSON body, which is a field never covered or cross-checked against the value used for key selection [6](#0-5) .

An attacker who administers their own GitHub organization/App installed on a Shipit instance that hosts multiple orgs (a documented, supported configuration [1](#0-0) ) legitimately knows their own org's `webhook_secret`. They can:
1. Set `repository.owner.login` (and/or `organization.login`) to their own org name, so `verify_signature` selects and validates against a secret they control.
2. Set `repository.full_name` (and other repo-identifying fields consumed by the handler) to point at a *different*, victim organization's repository that is tracked by the same Shipit instance.
3. POST the forged, self-signed JSON body directly to `/webhooks`.

`verify_signature` passes because the HMAC matches the attacker's own known secret; the handler then acts on the victim repository's stack because it trusts `full_name` unconditionally.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. Depending on which webhook event is forged, this can enable cross-repository writes: e.g., forging `push` events to trigger `GithubSyncJob` against a victim's stack, forging `status`/`check_suite` events to fabricate commit statuses/check results the merge and deploy safety logic relies on, or forging `membership`/`pull_request` events to alter team or PR-derived state for a repository the attacker does not own. This matches the Critical-tier "cross-repository writes" impact category.

### Likelihood Explanation
Requires only that the deployment be configured with multiple GitHub organizations (a documented, supported feature) and that the attacker control one of those organizations' own GitHub App (which they can create themselves, since anyone can register a GitHub App and have Shipit's operator install it for their own org). No Shipit credentials, session, or privileged account are needed — only knowledge of a secret the attacker legitimately owns for their own org.

### Recommendation
Do not use an attacker-controlled payload field to select which secret validates that same payload. Verify webhook signatures against every configured organization's secret (or otherwise authenticate the delivery, e.g., via a per-installation identifier from a trusted GitHub App context) before trusting any field in the body, and then additionally assert that the organization that successfully verified the signature matches the owner of the repository/stack the handler is about to mutate.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgOne` and `OrgTwo`, each with distinct `webhook_secret` values, as in the supported multi-app configuration [2](#0-1) .
2. Attacker administers `OrgOne`'s GitHub App and thus knows `OrgOne`'s `webhook_secret`.
3. Attacker crafts a JSON body: `{"repository": {"owner": {"login": "OrgOne"}, "full_name": "OrgTwo/victim-repo"}, ...}` and computes `X-Hub-Signature` using `OrgOne`'s secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully verifies the signature [3](#0-2) .
5. The relevant handler resolves the target `Repository`/`Stack` from `repository.full_name = "OrgTwo/victim-repo"` and acts on it, even though the request was never validated against `OrgTwo`'s secret.

      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
