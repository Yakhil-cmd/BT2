### Title
Hand-rolled frontmatter parser silently drops indented `enabled`/`action` keys, causing enforced rule state to diverge from displayed state - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`extract_frontmatter()` classifies every non-empty, non-comment line into exactly one of three buckets based on indentation: top-level key (`indent == 0`), list item (`stripped.startswith('-')`), or dict-item continuation (`indent > 2 and in_dict_item`) [1](#0-0) . Any line whose indentation is `1` or `2` and that is not a list item and not inside a multi-line dict item (e.g. a stray leading space before `enabled: false`) matches none of these branches and is silently discarded — no warning, no exception. Because `Rule.from_dict()` reads `frontmatter.get('enabled', True)` [2](#0-1) , a dropped `enabled` key silently defaults the rule to **enabled=True** regardless of what value the file actually stated. The same silent-drop applies to `action`, which falls back to `frontmatter.get('action', 'warn')`, but for `enabled` the failure mode is directly security-relevant: a rule file whose raw text visibly reads `enabled: false` (with a 1–2 space indent artifact) is actually loaded as active.

This diverges from what a reference YAML parser (`yaml.safe_load`) would do: real YAML requires consistent mapping indentation, so an inconsistently indented key at the top level would raise a `ScannerError`, causing `load_rule_file()`'s `except Exception` handler to reject the whole file (fail closed, rule not loaded) [3](#0-2) . Instead, the custom parser fails open, keeps the rest of the frontmatter, and silently reinstates the default `enabled=True`.

Critically, `/hookify:list` and `/hookify:configure` never call `extract_frontmatter()` at all — they are markdown command files that instruct the LLM to `Read` the file and "Extract `enabled` field from frontmatter" directly from raw text [4](#0-3) [5](#0-4) . A human or the LLM visually scanning the raw markdown will read the literal `enabled: false` text and report the rule as disabled, while the actual enforcement path — `pretooluse.py` → `load_rules()` → `extract_frontmatter()` → `RuleEngine.evaluate_rules()` [6](#0-5)  — treats it as enabled. If such a rule also sets `action: block`, this produces a genuinely hidden, persistent PreToolUse/Stop blocking rule that silently intercepts tool calls without appearing active in any user-facing review surface.

### Impact Explanation
An unprivileged party who can get a crafted `.claude/hookify.*.local.md` file into a victim's workspace (e.g. via a repository contribution/PR containing such a file, or content that gets turned into a rule via the `/hookify` generation flow) can plant a covert `action: block` rule that appears disabled under `/hookify:list`/`/hookify:configure` review but is actually active, silently interfering with the victim's tool calls (blocking legitimate commands/edits or, in Stop-event rules, stalling session termination) — a trust-boundary/approval-bypass style issue matching "hidden persistent behavior invisible to user review."

### Likelihood Explanation
Exploitation requires only the ability to place or influence the content of one `.claude/hookify.*.local.md` file with a one/two-space indentation artifact before the `enabled:` (or `action:`) line — a trivial, deterministic, and repeatable text manipulation. No parser confirmation or admin privilege is needed; the bug is a pure control-flow gap in the three-way indentation branch of `extract_frontmatter()`.

### Recommendation
Rewrite `extract_frontmatter()` to either (a) delegate to `yaml.safe_load()` with a strict schema/type check for `enabled`/`action`/`event`, failing closed on any parse error, or (b) make the hand-rolled parser raise an explicit error for any line that doesn't match a recognized indentation pattern instead of silently ignoring it, so malformed rule files are rejected (as already happens for other parse failures in `load_rule_file()`) rather than silently defaulting to `enabled=True`.

### Proof of Concept
Unit/differential test in `config_loader` tests:
```python
content = """---
name: sneaky-block
 enabled: false
event: bash
action: block
pattern: rm -rf
---
blocked!
"""
fm, _ = extract_frontmatter(content)
assert 'enabled' not in fm  # key silently dropped
rule = Rule.from_dict(fm, "blocked!")
assert rule.enabled is True  # defaults True despite raw text saying "false"
assert rule.action == 'block'
```
Fuzz/invariant test: generate randomized frontmatter blocks with 0/1/2/3+ space indentation prefixes on `enabled:`/`action:` lines, feed each into `extract_frontmatter()`, and compare `enabled`/`action` against `yaml.safe_load` (or an explicit error) — assert either semantic equivalence or that malformed indentation causes `load_rule_file()` to reject the file, never silently defaulting to an active/blocking state.

```python
def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
    except UnicodeDecodeError as e:
        print(f"Error: Invalid encoding in {file_path}: {e}", file=sys.stderr)
        return None
    except Exception as e:
        print(f"Error: Unexpected error parsing {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
        return None
```
