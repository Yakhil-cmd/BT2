### Title
Cross-org webhook confusion via mismatched `repository.owner.login` vs `repository.full_name` allows attacker to write to victim's `PullRequest` labels - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, which is parsed from the attacker-controlled JSON field `params.dig('repository', 'owner', 'login')`. The handler that actually performs the database write, `LabelCapturingHandler`, resolves the target `Repository`/`Stack` using a *different* field from the same payload: `params.repository.full_name`. Because these two fields are independently attacker-controlled and never checked for consistency, an attacker can sign a webhook that is valid for their own org (`repository.owner.login = "attacker-org"`) while pointing `repository.full_name` at a victim repo (`"victim-org/victim-repo"`), causing `capture_labels` to `update!` a victim's `PullRequest` row with attacker-chosen label strings.

### Finding Description
The broken binding is: `org that authenticated the webhook (repository_owner = params.repository.owner.login) == org owning the Repository/Stack acted upon (derived from params.repository.full_name)`. This equality is assumed by the code but never enforced.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` purely from JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to pick the GitHub App/secret: `Shipit.github(organization: repository_owner)` then calls `verify_webhook_signature` [2](#0-1) . An attacker who owns "attacker-org" and has configured a GitHub App/webhook pointed at the Shipit host can produce a validly-signed payload for that org.
2. Nothing ties `repository.owner.login` to `repository.full_name` in the same payload — they are independent JSON fields the attacker fully controls in the raw POST body.
3. `LabelCapturingHandler#repository` resolves the actual target repo using `params.repository.full_name`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , which can be set to the victim's `"victim-org/victim-repo"` even though the signature was verified against `attacker-org`.
4. `stack` is derived from that repository's `review_stacks` via `ReviewStackAdapter`, and matched to an existing PR by `params.pull_request.number` [4](#0-3) .
5. `capture_labels` then writes attacker-supplied label names onto that victim `PullRequest` row: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [5](#0-4) .

Existing guards do not prevent this: `verify_signature` only proves the request was signed by *some* org's registered secret — it never confirms that org matches the org implied by `repository.full_name` used later in the handler. `drop_unhandled_event` and the `ExplicitParameters` schema only validate event routing/type shape, not cross-field consistency. `check_if_ping` is irrelevant. No model validation on `Repository`/`Stack`/`PullRequest` enforces owner-vs-full_name consistency at write time, since the write path never re-derives or checks the org that authenticated the request.

### Impact Explanation
An attacker who legitimately owns any GitHub org onboarded to this Shipit instance (i.e., can generate validly-signed webhooks for their own org) can overwrite the `labels` column of any victim `PullRequest` row in any other org's repository, as long as `review_stacks_enabled` is set and a PR with a matching number exists. This is a cross-repository/cross-tenant database write of attacker-controlled data using another tenant's identity/PR record, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Since labels can influence merge-queue/provisioning logic elsewhere in the app, this could cascade into further unauthorized behavior (e.g., forcing a merge-queue label onto a PR that shouldn't be there). The attack is repeatable against any repository/PR number combination and is not limited to a single victim.

### Likelihood Explanation
Preconditions: attacker must control at least one GitHub org/app installation registered with this Shipit instance (a normal, low-privilege onboarding step, not a Shipit operator role), victim repo must have `review_stacks_enabled` and an existing tracked `PullRequest` for the guessed/known PR number. The attacker needs no Shipit session, no API token, and no victim secrets — only their own legitimate webhook secret. Constructing the payload requires only crafting JSON with mismatched `repository.owner.login` and `repository.full_name`, which is straightforward and requires no privileged access. This is a low-cost, easily repeatable attack.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after in `create`), validate that `repository_owner` (used to select the signing org) matches the owner segment parsed from `repository.full_name` in the same payload, and reject (422) on mismatch. Alternatively, in `Handler#repository`/`LabelCapturingHandler#repository`, re-derive the repository strictly from the org that authenticated the webhook rather than trusting `params.repository.full_name` independently, ensuring the acted-upon repository's owner equals the verified `repository_owner`.

### Proof of Concept
Minitest plan (webhooks controller / integration test, no live GitHub — use existing test helpers for signature stubbing as done in `test/controllers/webhooks_controller_test.rb`):

1. Create `attacker_org` "attacker-org" with a configured/stubbed GitHub App secret (as tests already stub `Shipit.github`).
2. Create victim `Repository` `"victim-org/victim-repo"` with `review_stacks_enabled: true`, a `Stack`, and a `PullRequest` with `number: 42`, `labels: ["safe-label"]`.
3. Build a `pull_request` webhook JSON payload:
   - `action: "labeled"`
   - `repository.owner.login: "attacker-org"` (so `repository_owner == "attacker-org"`)
   - `repository.full_name: "victim-org/victim-repo"` (so the handler targets the victim repo)
   - `pull_request.number: 42`
   - `pull_request.labels: [{name: "attacker-label"}]`
4. Sign the payload's `X-Hub-Signature` using attacker-org's known/stubbed secret.
5. POST to `/webhooks` with `X-Github-Event: pull_request`.
6. Assert response is `200 OK` (signature accepted for attacker-org: `repository_owner == "attacker-org"` on both verification sides — equality holds and diverges from the acted-upon repo's real owner `"victim-org"`).
7. Reload victim `PullRequest`; assert `pull_request.labels == ["attacker-label"]`, proving that `repository_owner ("attacker-org") != actual repo owner ("victim-org")` yet the write succeeded — the binding claimed in the question is indeed broken.
