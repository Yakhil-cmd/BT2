## Analog Found: Unbacked XCM asset credit when using non-standard/fee-on-transfer ERC20 contracts with `ERC20Transactor`

The audit report describes `Allo._fundPool` trusting the *requested* transfer amount instead of the *actually received* balance delta when crediting `strategy.poolAmount`, which desyncs internal accounting from real backing when the token skims a fee on transfer. The Polkadot SDK analog is the ERC20 `TransactAsset` implementation used by AssetHub's XCM executor, which credits the XCM holding register with the *nominal* `amount` argument passed to an arbitrary `IERC20::transfer` call, never checking the actual balance delta of the checking (reserve) account.

### Title
Unbacked XCM asset credit in `ERC20Transactor::withdraw_asset_with_surplus` for non-standard/fee-on-transfer ERC20 contracts - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` withdraws an ERC20-based XCM asset by calling `IERC20::transfer(checking_account, amount)` on an arbitrary pallet-revive contract matched purely by address pattern, and then unconditionally credits the XCM holding register with the requested `amount` as soon as the call returns `true`/does not revert. [1](#0-0)  Because the matcher `ERC20Matcher` accepts any local `AccountKey20` location without an allowlist, an attacker can register/target their own contract implementing `IERC20`, which is exactly the class of "fee-on-transfer"/non-standard token referenced in the report. [2](#0-1) 

### Finding Description
`withdraw_asset_with_surplus` performs a `bare_call` into the ERC20 contract identified by the asset location, transferring the requested `amount` to `TransfersCheckingAccount` (the pallet's reserve/checking account for ERC20-backed XCM assets): [3](#0-2) 

If the call does not revert and the decoded ERC20 return value is `true`, the function creates an `AssetsInHolding` credit of the full nominal `amount`: [4](#0-3) 

There is no verification that the checking account's actual token balance increased by `amount`. Any contract that:
- implements a transfer fee / deflationary burn on transfer, or
- otherwise returns `true` while moving less than `value` (a non-standard but common real-world ERC20 pattern),

will cause the checking account to receive `amount - fee` tokens while the XCM executor's holding register is credited with the full `amount`. The `Erc20Credit` imbalance type used to represent this credit performs no runtime-level balance enforcement, by its own doc comment: "This type implements the necessary imbalance accounting traits but does not perform runtime-level balance enforcement... actual balance constraints are enforced by the ERC20 smart contract itself" — which is precisely false here, since the withdraw path never re-checks the contract's `balanceOf`. [5](#0-4) 

The asset matcher used to select this transactor, `ERC20Matcher`, matches any local `Location` of the shape `(0, [AccountKey20 { .. }])` with no allowlist of trusted contract addresses: [2](#0-1)  This transactor is wired into the real `asset-hub-westend` runtime's XCM `AssetTransactors` tuple, reachable through normal, permissionless XCM execution: [6](#0-5) 

This is a genuine "assume transferred amount == actual balance delta" bug, structurally identical to the reported Allo issue: the pool/reserve accounting (`AssetsInHolding` credit) is inflated relative to the actual backing held by the `TransfersCheckingAccount`.

### Impact Explanation
The XCM holding register is the authoritative in-flight accounting used by the XCM executor for the remainder of the program (e.g., `DepositAsset`, `InitiateTeleport`, `InitiateReserveWithdraw`, `BuyExecution`). If a phantom-inflated credit for an ERC20-backed asset is produced during `WithdrawAsset`, it can be spent within the same XCM program for more real value than was ever actually escrowed in `TransfersCheckingAccount`, i.e., the checking account acting as reserve backing for the (locally represented) ERC20 asset becomes systematically under-collateralized relative to what the executor believes it holds. Repeated use compounds the discrepancy, and subsequent legitimate withdrawals/deposits for the same asset can fail (checking account has less than credited) or, depending on downstream logic that trusts holding-register amounts rather than re-querying `balanceOf`, be used to move/deposit value the checking account never actually received. This maps to the report's "Impact: Any logic in strategies relying on `poolAmount`" — here the analog is any XCM logic relying on the holding-register credit reflecting real reserve backing.

### Likelihood Explanation
The attacker needs no privileged role: any account can deploy a pallet-revive contract implementing the `IERC20` interface (matching only requires an `AccountKey20` location and a successful `transfer` call returning `true`), and then submit an `pallet-xcm::execute` (or otherwise trigger local XCM execution) that references that contract as the withdrawn asset. This is entirely within the capability of an ordinary signed user; no governance, relayer, or validator privilege is required.

### Recommendation
In `withdraw_asset_with_surplus` (and symmetrically in `deposit_asset_with_surplus`), record `TransfersCheckingAccount`'s (or beneficiary's) `balanceOf` before and after the `bare_call`, and credit/decrement the XCM holding register using the *actual* observed delta rather than the caller-requested nominal `amount`:
```rust
let balance_before = /* balanceOf(checking_account) via bare_call */;
// ... perform transfer bare_call ...
let balance_after = /* balanceOf(checking_account) via bare_call */;
let actual = balance_after.saturating_sub(balance_before);
Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(actual))), surplus))
```
Alternatively, restrict `ERC20Matcher`/asset registration to an allowlist of vetted, standards-compliant ERC20 contracts so arbitrary user-deployed non-standard tokens cannot be used as XCM-transactable assets at all.

### Proof of Concept
I was not able to execute a runtime integration test in this environment (ask-only mode, no filesystem/terminal access). The reasoning above is derived from direct code inspection: `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` trust the ERC20 `transfer` return value and never diff `balanceOf` before/after [7](#0-6) , `ERC20Matcher` has no address allowlist [8](#0-7) , and `ERC20Transactor` is live in `asset-hub-westend`'s `AssetTransactors` [6](#0-5) . A concrete reproduction would require: (1) deploying a pallet-revive contract implementing `IERC20` with a transfer function that moves `value * 99 / 100` to `to` but returns `true` for `value`; (2) submitting `pallet_xcm::execute` with a program `WithdrawAsset(Asset{ id: contract_location, fun: Fungible(amount) })` followed by `DepositAsset` to a second account, then asserting `IERC20::balanceOf` sums to less than the credited/deposited XCM amount. This PoC was not run; the finding is based on static code inspection and should be validated with an actual `pallet-revive` + `pallet-xcm` integration test in a Devin session with full repo/tooling access before filing.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
