This confirms the vulnerability. Shipit explicitly supports multi-organization configuration where each organization has its own independent `webhook_secret` [1](#0-0) , and `Shipit.github(organization:)` looks up config keyed purely by the organization name string [2](#0-1) .

### Title
Webhook signature validated against the organization key derived from `repository.owner.login`, while stack resolution uses the independently-controlled `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` from the **unverified** JSON body itself [3](#0-2) . Once the signature check passes, every registered `Handler` resolves the target `Stack`/`Repository` using a **different** field, `repository.full_name` [4](#0-3) . Because these are two independent, attacker-controlled strings inside the same JSON payload, an attacker who legitimately knows the `webhook_secret` for one configured GitHub organization can forge a payload that authenticates as that organization while writing to a stack that belongs to a different organization.

### Finding Description
This is directly analogous to the reported Move issue: a verification/decision step (`set_pair_jump_interest_rate_model` deciding on stale vs new interest parameters) is performed against one piece of state while the actual effect is applied using a different, out-of-sync piece of state. Here the binding that should hold is:

`organization that authenticated the webhook == organization whose repository/stack is written`

Before the attacker's request: `repository_owner` (used to select `webhook_secret`) and `repository.full_name`'s owner (used to resolve the `Stack`) are always the same for legitimate GitHub-originated webhooks, since GitHub populates both fields consistently from the actual originating repository.

After the attacker's crafted request: the attacker sets `repository.owner.login = "OrgA"` (an org whose `webhook_secret` they know, e.g. because they administer a repository in `OrgA` that is also connected to this Shipit instance and thus received the real secret in a previous delivery, or the secret was configured public/weak for that org) but sets `repository.full_name = "OrgB/target-repo"`. `verify_signature` computes `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds because the attacker signs with `OrgA`'s known secret over the full raw body [5](#0-4) . `Shipit::WebhooksController#create` then dispatches the parsed body to handlers such as `PushHandler`, `StatusHandler`, etc., all of which resolve `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from `repository.full_name` — i.e. `OrgB/target-repo` [4](#0-3) . This lets an attacker who only controls/knows one organization's webhook secret push forged events (e.g. `push`, `status`, `check_suite`) for stacks belonging to a completely different, unrelated GitHub organization configured on the same Shipit instance.

### Impact Explanation
This breaks the credential/repository binding equivalent to "an organization that authenticated versus the repository that is written," explicitly called out in scope. A forged `push` event triggers `GithubSyncJob` for the victim organization's stack [6](#0-5) , and a forged `status` event can flip commit CI state to `success`, which can unblock and trigger automatic deploys/merges for a stack the attacker's organization has no legitimate control over — an unauthorized deploy/merge crossing organizational boundaries, satisfying the Critical bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires the Shipit instance to be configured with the multi-organization GitHub App schema (explicitly documented and supported: `docs/setup.md` "Using Multiple Github Applications") and requires the attacker to know/control at least one configured organization's `webhook_secret` — a scenario the codebase treats as a normal, unprivileged trust boundary (each org owner only trusts Shipit with their own secret, not with write access to other orgs' stacks). No GitHub App private key, `GITHUB_TOKEN`, or Shipit session is needed.

### Recommendation
In `verify_signature`, after successfully validating the signature for the organization derived from `repository_owner`, re-derive the organization from `repository.full_name` (the field actually used by `Handler#repository_name`) and reject the request (422) if the two do not match. Alternatively, unify both lookups to use the exact same field (`repository.full_name`'s owner segment) before selecting the `webhook_secret`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows `OrgA`'s `webhook_secret` (e.g. because you administer a repo in `OrgA` connected to this Shipit instance), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, raw_body)>` and send it to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds [7](#0-6) .
5. `PushHandler` (subclass of `Handler`) resolves `stacks` from `repository.full_name` = `"OrgB/victim-repo"` and enqueues `GithubSyncJob` for that stack, even though the request never authenticated with `OrgB`'s secret [4](#0-3) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
