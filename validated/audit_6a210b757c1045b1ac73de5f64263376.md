### Title
CCMenu API endpoint bypasses per-token stack scoping, allowing a stack-scoped `ApiClient` token to read the build/deploy status of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and `Shipit::Api::BaseController#stacks`/`#stack` enforce that scope for every other API controller. `Shipit::Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, resolving the stack directly from the URL parameter instead of from the token-restricted collection, so a token authorised for stack A can read CCMenu status for any stack B.

### Finding Description
`ApiClient#check_permissions!` only checks that the caller's `permissions` array contains `"#{operation}:#{scope}"` (e.g. `read:stack`); it never checks *which* stack the permission applies to: [1](#0-0) 

The actual per-stack restriction is implemented separately, in `BaseController#stacks`, which narrows the visible stack set to `current_api_client.stack_id` when the client is scoped, and `#stack`, which resolves the requested stack only from that restricted collection: [2](#0-1) 

Every other API controller (e.g. `LocksController`, `DeploysController`) inherits this `#stack` method unmodified, so a client scoped to stack A cannot address stack B even with `write:stack`/`deploy:stack` permission, because `stacks.from_param!` will raise `RecordNotFound` for any stack outside the client's scope.

`CCMenuController`, however, overrides `#stack` to resolve the stack directly via the unscoped class method, ignoring `current_api_client.stack_id` entirely: [3](#0-2) 

`require_permission :read, :stack` still passes for any token holding the generic `read:stack` permission, regardless of its `stack_id` scope, because `check_permissions!` never inspects the target stack. The fixture `here_come_the_walrus` demonstrates the intended contract: a token scoped to `stack: shipit` with only `read:stack`, meant to see nothing else: [4](#0-3) 

and `StacksController` tests confirm that scoping is enforced there via the `stacks` collection: [5](#0-4) 

No equivalent test exists for `CCMenuController`, and the code path shows the scoping is skipped: the binding broken is "the stack a token authorises" (the single stack recorded on `ApiClient#stack_id`) versus "the stack it touches" (any stack addressable via `Stack.from_param!(params[:stack_id])`).

### Impact Explanation
An `ApiClient` token deliberately scoped to a single stack (a common integration pattern for exposing a stack's CI status badge/CCMenu feed to a specific external tool) can be used to read the build/deploy status - last build status, build label (deploy id), build time, and `webUrl` - of every other stack in the Shipit instance, including private/internal stacks the token was never meant to access. This is an authorization-scope bypass giving unauthenticated-for-that-resource read access to arbitrary stack state, matching the High-impact class "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state ... or deploy output".

### Likelihood Explanation
High. Exploitation requires only a single valid, stack-scoped API token with `read:stack` (the minimal, lowest-privilege permission Shipit supports issuing) and knowledge/guessing of another stack's `owner/name/environment` triple, which is often predictable or discoverable (e.g., from the Shipit UI, repo names). No additional secrets, write access, or session are required beyond the one legitimately-issued scoped token.

### Recommendation
Make `CCMenuController#stack` resolve through the scoped `stacks` collection (as `BaseController#stack` does) instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot address stacks outside its `stack_id`. Consider additionally hardening `ApiClient#check_permissions!` to accept and validate the target stack when the client is scoped, so future controllers cannot silently reintroduce the same bypass.

### Proof of Concept
1. Create an `ApiClient` scoped to stack `A` (`stack_id` set) with permission `read:stack` (mirrors the `here_come_the_walrus` fixture).
2. Authenticate as that client (e.g. via `?token=<authentication_token>` as supported by `CCMenuController#authenticate_api_client`).
3. Request `GET /ccmenu/<owner_B>/<name_B>/<environment_B>?token=<token>` for an unrelated stack `B` that the client is not scoped to.
4. Observe `200 OK` with `B`'s CCMenu XML (last build status/label/time/webUrl), even though `require_permission :read, :stack` only checks the generic permission list and `#stack` never restricts to the client's `stack_id`, unlike every other endpoint under `Shipit::Api::BaseController`.
