**Rationale:** `guid::create_id` is explicitly documented as producing "a non-privileged identifier that can be freely created by anyone" [1](#0-0) . Unlike `create`, which is `public(friend)` and restricted to trusted modules (`account`, `object`) that increment a real per-account counter [2](#0-1) , `create_id` is intentionally `public` and produces a plain comparable value struct `ID { creation_num, addr }` with no capability or authenticity guarantee attached [3](#0-2) . `eq_id` merely does structural equality on this value type [4](#0-3) , so any code that trusts `ID` equality alone as a proof of "this GUID was legitimately created by/for this address" is itself misusing the type — the module's own doc comment warns of this by calling it "non-privileged." This is a documented design property of a Move framework library type, not an admission-boundary defect: it has no interaction with REST parsing, authenticator/signature validation, mempool, vm-validator, or VM prologue checks, and does not affect sender binding, sequence numbers, chain-id, expiry, or replay protection for transactions. Per the boundary conditions, the review is scoped to transaction-admission code reachable from unprivileged transaction/authenticator/API/proof input; this Move utility function does not sit on that path.
