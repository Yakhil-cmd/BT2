### Title
Unauthenticated subscription to `/events` SSE channels leaks stack/task/deploy state to any internet user - ([File: config/routes.rb])

### Summary
`Pubsubstub::StreamAction` is mounted directly as a plain Rack endpoint at `/events`, completely outside the `Shipit::Engine::ApplicationController` controller hierarchy that carries the `Shipit::Authentication` concern. Because Rack-level `mount` calls never run controller `before_action` callbacks, `force_github_authentication` and `current_user.authorized?` are never invoked for this route, letting anyone who knows or guesses a `stack.<id>` / `repository.<id>` channel name subscribe to live stack/task/deploy event streams without a session, token, or team membership.

### Finding Description
The broken binding: the app assumes `GET /events?channels[]=<channel>` is only reachable by a request that has already passed `force_github_authentication` (i.e., `current_user.authorized? == true`), the same guard applied to every other Shipit page. In reality:

`AUTH(request to /events) != AUTH(request to any Shipit::Engine controller action)`

`config/routes.rb` mounts the stream handler as a raw Rack app: [1](#0-0) 

`Shipit::Authentication` is a `before_action` concern included in Shipit's `ApplicationController` and only fires for controller actions dispatched through that base class: [2](#0-1) [3](#0-2) 

`Pubsubstub::StreamAction` is a third-party Rack endpoint object (`.new`), not a subclass of `Shipit::Engine::ApplicationController`, so Rails' `mount` dispatches straight to its `call(env)` method — no controller instantiation, no `before_action` chain, no `current_user` check ever runs. Grepping the engine confirms there is no authentication concern, no `before_action`, and no channel-ownership check anywhere near the mount point or in `app/controllers/shipit` that wraps this route.

Channel names handed to the `subscribe` view helper are just `"stack.#{id}"` / `"repository.#{id}"` built from sequential integers and embedded as plain `<meta>` tags in HTML: [4](#0-3) 

An attacker with zero Shipit privileges can:
1. Observe or guess any `stack.<id>` / `repository.<id>` value (sequential integers, visible in any page source, browser history, referrer headers, or shared link, or simply brute-forced since they are small integers).
2. Send `GET /events?channels[]=stack.<id>&channels[]=repository.<id>` directly, with no cookies, no `Authorization` header, no API token.
3. Receive the live SSE stream of events published to that channel — task/deploy lifecycle events, status changes, and other stack activity — for a stack/repository the attacker has no relationship to.

None of the existing guards apply here: `force_github_authentication`, `User#authorized?`, and `Shipit.github_teams` gating are controller-level concerns that this mounted Rack app never touches; there's no `ExplicitParameters` schema, no `require_permission!`, and no per-channel authorization callback registered on `Pubsubstub::StreamAction.new`.

### Impact Explanation
Any unauthenticated internet user can continuously read live stack/task/deploy state (task start/completion, deploy status, rollback events, etc.) for any stack or repository configured in the Shipit instance, purely by iterating small integer IDs. This is an unauthenticated read of stack state / task streams, matching the High severity bucket ("unauthenticated read of stack state, task streams or deploy output"). It is fully repeatable against every stack/repository hosted on the instance since IDs are sequential and there is no rate limiting or authorization check gating the subscription. It does not by itself allow writes, RCE, or credential exfiltration, so it does not rise to Critical, but it is a real cross-tenant information disclosure for any multi-team Shipit deployment.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs network access to the Shipit host and any observed or guessed `stack.<id>`/`repository.<id>` value — no GitHub account, no Shipit session, no secrets. Cost is a single unauthenticated HTTP GET request; IDs are sequential integers so enumeration across the entire ID space is trivial. This requires no special Shipit configuration beyond the default engine mount shown in `config/routes.rb`, which every deployment following the documented mounting instructions will have.

### Recommendation
Wrap the `/events` mount in an authorization layer before dispatch — either (a) replace the direct `mount Pubsubstub::StreamAction.new` with a thin Shipit controller action that runs `Shipit::Authentication`'s `force_github_authentication` and validates that `current_user` is authorized for each requested channel's underlying `stack`/`repository` before delegating to `Pubsubstub::StreamAction`, or (b) configure `Pubsubstub::StreamAction` with its supported authorization callback (if available in the gem) to reject subscriptions to `stack.<id>`/`repository.<id>` channels the current session/user is not authorized to view, consistent with the authorization already enforced on every other Shipit view/controller.

### Proof of Concept
```ruby
# test/controllers/shipit/events_stream_authorization_test.rb
require 'test_helper'

module Shipit
  class EventsStreamAuthorizationTest < ActionDispatch::IntegrationTest
    test "streaming action carries no per-channel authorization callback" do
      # Binding under test: mounted app should equal an authenticated, authorized dispatcher
      mounted_app = Shipit::Engine.routes.routes.find { |r| r.name == 'events' }.app.app
      assert_instance_of Pubsubstub::StreamAction, mounted_app
      # No Shipit::Authentication concern anywhere near the mount
      refute Pubsubstub::StreamAction.ancestors.include?(Shipit::Authentication)
    end

    test "GET /events?channels[]=repository.<id> is served without authentication" do
      repository = shipit_repositories(:shipit)
      # no session set, no api token, no login
      get "/events", params: { 'channels[]' => "repository.#{repository.id}" }
      # attacker receives a stream response instead of a redirect to github_authentication or 403
      refute_equal 302, response.status
      refute_equal 403, response.status
    end
  end
end
```
This demonstrates both halves of the broken equality: no authorization callback is attached to the mounted `Pubsubstub::StreamAction`, and an unauthenticated request against a real channel name is not redirected/rejected the way every other Shipit route is via `force_github_authentication`.

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
