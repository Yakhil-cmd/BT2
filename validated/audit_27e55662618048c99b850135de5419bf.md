### Title
Item Attribute Delegate Approvals (`ItemAttributesApprovalsOf`) Persist After NFT Transfer, Letting the Old Delegate Keep Writing Attributes on a Transferred Item - ([File: substrate/frame/nfts/src/features/transfer.rs])

### Summary
`pallet-nfts`' `do_transfer` clears the *transfer* approvals (`details.approvals.clear()`) but never touches `ItemAttributesApprovalsOf`, the separate approval list created by `approve_item_attributes`. Because the `Account(delegate)` attribute-namespace check only verifies `account_id == origin && approvals.contains(&origin)` — with no check that `origin` is (or was) the current item owner — a delegate approved before a sale/transfer keeps the ability to `set_attribute`/`clear_attribute` on the item in that namespace after the item has a brand-new owner, until the new owner discovers and calls `cancel_item_attributes_approval`.

### Finding Description
`do_approve_item_attributes` lets the *current* item owner add an account to `ItemAttributesApprovalsOf::<T, I>` for a given `(collection, item)`: [1](#0-0) 

`is_valid_namespace` is the only permission gate used by `do_set_attribute`/`do_clear_attribute` for the `Account(account_id)` namespace, and it purely checks membership in `ItemAttributesApprovalsOf`, independent of who currently owns the item: [2](#0-1) 

When the item is transferred (via the permissionless `transfer` extrinsic, `buy_item`, or `claim_swap`, all of which route through `do_transfer`), only the transfer-approval map is cleared; the attribute-approval map is left untouched: [3](#0-2) 

Removing an attribute-approval delegate is a separate, owner-gated action (`do_cancel_item_attributes_approval`) that must be *explicitly* invoked by the current owner: [4](#0-3) 

This is the same missing-cleanup pattern described in the Convergence report: a delegation tied to an NFT/position is not revoked when the underlying asset's ownership changes, so the stale delegate can keep exercising delegated rights over an asset whose new owner never consented to them.

### Impact Explanation
Any account previously approved by a *former* owner in the `Account(delegate)` namespace can continue to call `set_attribute` / `clear_attribute` on the item after it has been sold/transferred/swapped to someone else, without the new owner's knowledge or consent, until the new owner proactively calls `cancel_item_attributes_approval` (which requires them to know the identity of the stale delegate). This breaks the invariant that item state should be fully under the control of its current owner once transferred, and can be used to write/alter attribute data (metadata, game state, marketplace-consumed flags, etc.) on an NFT the attacker no longer has any legitimate relationship with. Severity is Medium, matching the referenced audit finding's rating and impact class — persistent unauthorized asset-level delegation, not direct fund theft.

### Likelihood Explanation
Every step is reachable with an ordinary signed extrinsic and no privileged role:
1. The item owner (or an account colluding with a future seller) calls `approve_item_attributes` on their own item — a fully permissionless, owner-gated call.
2. The item is transferred normally (`transfer`, `buy_item`, `claim_swap`) — no special conditions required beyond the collection/item being transferable, which is the default and required for any sale market flow.
3. The stale delegate (still present in `ItemAttributesApprovalsOf`) calls `set_attribute`/`clear_attribute` with `namespace = Account(delegate)` — accepted because `is_valid_namespace` never re-checks current ownership.

No governance, no forged inherent, no privileged origin is needed; the "attacker" is simply an account that was legitimately approved once and exploits the missing cleanup on transfer. Likelihood is High for reachability, though real-world exploitation depends on how much economic/functional weight downstream code places on `Account`-namespace attributes for a given collection.

### Recommendation
In `do_transfer` (substrate/frame/nfts/src/features/transfer.rs), in addition to clearing `details.approvals`, also drain/clear `ItemAttributesApprovalsOf::<T, I>::take(&collection, &item)` (and unreserve any outstanding attribute deposits tied to removed delegates, mirroring the cleanup already done in `do_cancel_item_attributes_approval`), so attribute-setting delegation does not survive a change of ownership unless the new owner re-approves it.

### Proof of Concept
Not executed against a live network; this is a static-code trace demonstrating the missing state cleanup and the unguarded permission check. It can be reproduced deterministically in `pallet-nfts`' existing unit-test harness (`substrate/frame/nfts/src/tests.rs`) with the following sequence, which the code above shows is *not* blocked:
1. `Nfts::create`/`force_mint` an item owned by account `2`.
2. `Nfts::approve_item_attributes(signed(2), collection, item, delegate=3)` — succeeds, inserts `3` into `ItemAttributesApprovalsOf`.
3. `Nfts::transfer(signed(2), collection, item, dest=4)` — succeeds via `do_transfer`; `details.approvals` is cleared, but `ItemAttributesApprovalsOf` still contains `3` (verifiable by reading storage directly, since no test/dispatch call removes it).
4. `Nfts::set_attribute(signed(3), collection, Some(item), AttributeNamespace::Account(3), key, value)` — per `is_valid_namespace`'s `Account` branch, this succeeds because `account_id == origin (3) && approvals.contains(&3)` is still true, with **no check that `3` has any relationship to the new owner `4`**.

No existing regression test in `substrate/frame/nfts/src/tests.rs` exercises "transfer then attribute-delegate still active," and the code inspected in `transfer.rs`/`attributes.rs` confirms the storage item is never cleared on transfer — the guard that would block step 4 (an ownership/current-owner check in `is_valid_namespace`'s `Account` branch, or a clear of `ItemAttributesApprovalsOf` in `do_transfer`) does not exist.

	pub(crate) fn do_approve_item_attributes(
		check_origin: T::AccountId,
		collection: T::CollectionId,
		item: T::ItemId,
		delegate: T::AccountId,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Attributes),
			Error::<T, I>::MethodDisabled
		);

		let details = Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);

		ItemAttributesApprovalsOf::<T, I>::try_mutate(collection, item, |approvals| {
			approvals
				.try_insert(delegate.clone())
				.map_err(|_| Error::<T, I>::ReachedApprovalLimit)?;

			Self::deposit_event(Event::ItemAttributesApprovalAdded { collection, item, delegate });
			Ok(())
		})
	}

	pub(crate) fn do_cancel_item_attributes_approval(
		check_origin: T::AccountId,
		collection: T::CollectionId,
		item: T::ItemId,
		delegate: T::AccountId,
		witness: CancelAttributesApprovalWitness,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Attributes),
			Error::<T, I>::MethodDisabled
		);

		let details = Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);

		ItemAttributesApprovalsOf::<T, I>::try_mutate(collection, item, |approvals| {
			approvals.remove(&delegate);

			let mut attributes: u32 = 0;
			let mut deposited: DepositBalanceOf<T, I> = Zero::zero();
			for (_, (_, deposit)) in Attribute::<T, I>::drain_prefix((
				&collection,
				Some(item),
				AttributeNamespace::Account(delegate.clone()),
			)) {
				attributes.saturating_inc();
				deposited = deposited.saturating_add(deposit.amount);
			}
			ensure!(attributes <= witness.account_attributes, Error::<T, I>::BadWitness);

			if !deposited.is_zero() {
				T::Currency::unreserve(&delegate, deposited);
			}

			Self::deposit_event(Event::ItemAttributesApprovalRemoved {
				collection,
				item,
				delegate,
			});
			Ok(())
		})
	}
