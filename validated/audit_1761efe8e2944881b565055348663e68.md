### Title
Webhook signature is verified against the organization named in the payload, not the repository the handler actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using `repository_owner`, a value taken from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`). The handlers that actually act on the webhook (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a *different* field from the same body: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb`). Because the field used to pick the verification key and the field used to pick the mutated resource are independent strings inside the same unauthenticated JSON blob, a party who legitimately controls one organization's webhook secret on a multi-tenant Shipit install can forge a signature for that organization while pointing `repository.full_name` at a completely different organization's stack.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to select the `GitHubApp`/secret to verify the signature against:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
``` [2](#0-1) 

`Shipit.github` supports a multi-tenant configuration where each GitHub organization has its own independent `webhook_secret` (`lib/shipit.rb`, `github_app_config`), meaning a person who administers one onboarded organization on a shared Shipit deployment legitimately knows that organization's webhook secret.

Once the signature check passes, `WebhooksController#create` dispatches the *entire, attacker-supplied* JSON body to handlers unmodified:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [3](#0-2) 

Handlers such as `PushHandler` resolve the affected repository/stack from a *different* field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

For genuine GitHub-generated webhooks, `repository.owner.login` and `repository.full_name` always agree (they come from the same GitHub repository object), so this never mismatches. But because the controller does not verify a GitHub-generated request — it verifies an HMAC over a raw body that the caller fully controls — nothing forces `repository.owner.login` (used for key selection) and `repository.full_name` (used for the actual DB lookup/mutation) to refer to the same repository. This is exactly the pattern in the reference report: a field trusted for identity/authorization (`token_id`/sender in the Everscale report; `repository.owner.login`/`organization.login` here) is decoupled from the field that determines what resource gets acted upon (`pair_id` in the report; `repository.full_name` here), and nothing in the signature-verification path ties them together beyond "same JSON blob, same HMAC" — which does not imply "same repository."

### Impact Explanation
On a multi-tenant Shipit deployment (`docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`) where multiple unrelated organizations are configured with independent `webhook_secret`s, an attacker who is a legitimate administrator of Organization A (and therefore knows Organization A's `webhook_secret`) can craft a POST to `/webhooks` with:
- `X-Github-Event: push`
- Body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen-sha>"}`
- `X-Hub-Signature` computed with OrgA's secret over that exact body.

`verify_signature` will select OrgA's `GitHubApp`, verify successfully, and `PushHandler` will then look up and act on `OrgB/victim-repo`'s stacks — enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha` for a repository/organization the attacker has no legitimate access to. This is a cross-repository/cross-tenant write triggered purely by a cross-tenant credential the attacker legitimately possesses for a *different* resource, which matches the "cross-repository writes" / unauthorized state-mutation criteria for a High/Critical finding. The same organization/full_name mismatch pattern (`payload.dig('repository', 'full_name')`) is reused by every PullRequest handler (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`, `edited_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`), broadening the blast radius beyond `push` to review-stack provisioning/archival and PR metadata across organizations.

### Likelihood Explanation
Exploitability strictly requires access to a valid `webhook_secret` for at least one organization configured on the shared Shipit instance — this is not a "privileged Shipit user" credential (session, `ApiClient` token) but an ordinary GitHub organization-owner-level secret that many independent teams legitimately hold on a shared/multi-tenant deployment. Given that `docs/setup.md` explicitly documents and encourages this multi-organization configuration, the scenario of mutually-distrusting tenants sharing one Shipit instance is a supported deployment topology, making this a realistic threat model rather than a contrived one.

### Recommendation
- Short term: After verifying the webhook signature, re-derive the acting-repository identity strictly from the same field used for signature-key selection (`repository.owner.login`/`organization.login`), and reject the webhook if `repository.full_name`'s owner segment does not match `repository_owner`.
- Long term: Bind each configured GitHub App/organization to an explicit allow-list of repositories/owners it is permitted to affect, and validate that binding for every field consumed downstream by handlers, not just the field used to pick the HMAC secret.

### Proof of Concept
1. Deploy Shipit with multi-tenant `github` config containing `OrgA` (attacker-administered, webhook secret known to attacker) and `OrgB` (victim, tracks `OrgB/victim-repo`).
2. Attacker builds JSON body:
```json
{"ref":"refs/heads/master","after":"<attacker_chosen_sha>","repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/victim-repo"}}
```
3. Attacker computes `sha1=<hmac>` using OrgA's `webhook_secret` over the exact raw body (`Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` logic, `lib/shipit/github_app.rb` lines 76-83) [6](#0-5) .
4. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<hmac>`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature check passes.
6. `PushHandler.process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for OrgB's stack with the attacker-supplied `expected_head_sha`, despite the attacker never having demonstrated any access to OrgB.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
