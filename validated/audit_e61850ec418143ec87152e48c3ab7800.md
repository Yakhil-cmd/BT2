### Title
Global `outputs.output_id` counter is a fixed-size `INT` (32-bit) shared by every payment on the network, so it can be exhausted to permanently block all future units - ([File: initial-db/byteball-mysql.sql], [File: initial-db/byteball-myrocks.sql])

### Summary
The MySQL/RocksDB storage schemas used by ocore full/hub nodes define the `outputs` table with a single, network-wide `AUTO_INCREMENT` primary key of type `INT` (32-bit, max `2^31-1`), shared by every output of every payment message ever posted by any user. This mirrors the Morph `L2ToL1MessagePasser` bug: a single bounded structure (there, a Merkle tree capped at `2**32-1` leaves; here, an `INT` counter capped at `2**31-1` rows) that is fed by unprivileged, ordinary user activity and, once exhausted, blocks all further insertions into the shared structure — i.e., all future payments.

### Finding Description
The schema declares: [1](#0-0) 
```
CREATE TABLE outputs (
	output_id INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
```
and identically in the RocksDB-backed schema: [2](#0-1) 

Every payment message in every unit posted by any address inserts one or more rows into this single `outputs` table via `writer.js`'s `INSERT INTO outputs` logic when a joint is saved (`saveJoint`) [3](#0-2) . There is no per-asset or per-address partitioning of `output_id` — it is one global sequence for the entire ledger, analogous to Morph's single Merkle tree shared by all L2→L1 withdrawals.

Validation only bounds the number of outputs *per message* (`MAX_OUTPUTS_PER_PAYMENT_MESSAGE = 128`) and messages *per unit* (`MAX_MESSAGES_PER_UNIT = 128`) [4](#0-3) , but places no limit on the total number of outputs a node will ever accumulate over the life of the network. Any regular user can create arbitrarily many payment units (self-payments splitting into many outputs, exactly as the Morph attacker looped `sendMessage` 200 times per tx), continuously incrementing the shared `output_id` counter.

Once the counter reaches `2^31-1`, the next `AUTO_INCREMENT` allocation on this `INT` column overflows the column's range. In MySQL/InnoDB-style engines this produces an `Out of range value for column 'output_id'` error on `INSERT`, causing every subsequent attempt to save a unit containing a payment message (which is mandatory — `validateMessages` requires `bHasBasePayment` [5](#0-4) ) to fail at the storage layer. Because essentially all units on the network carry a base payment message, this halts the node's ability to persist any new unit, i.e., a permanent denial of service for that node's processing of the DAG — the same end effect as the Morph withdrawal Merkle tree being permanently filled.

### Impact Explanation
Filling the global `outputs.output_id` counter would make the affected node (any full node or hub running the MySQL/RocksDB backend) unable to write any new unit containing payment outputs — which is virtually all units, including ordinary payments and AA responses. This is a "network unable to confirm new units" outcome matching the acceptance bar: nodes running on this schema become permanently unable to process new transactions once the counter overflows, with no remediation short of a schema migration (widening the column) — directly analogous to the acknowledged Morph finding.

### Likelihood Explanation
Reaching `2^31-1` (~2.147 billion) output rows requires sustained, cheap spam over a long period (similar order of magnitude to the Morph attack, which required ~21 million transactions of 200 messages each to fill `2^32-1`). It is unprivileged — any address can post ordinary payment units and self-split outputs — and requires no special permission, matching the "unprivileged unit poster" reachability requirement. The main mitigating factor is that this affects only deployments using the MySQL/RocksDB schema (full/hub nodes); SQLite-based light/full nodes use `INTEGER PRIMARY KEY` rowids which are 64-bit and not practically exhaustible. Where the MySQL/RocksDB schema is used in production, the class of bug — an unprivileged, monotonically-growing global counter with an undersized fixed-width type — is directly analogous to the reported issue.

### Recommendation
Widen `outputs.output_id` (and audit other `AUTO_INCREMENT INT` primary keys shared globally across the ledger, if any) to `BIGINT` in `initial-db/byteball-mysql.sql` and `initial-db/byteball-myrocks.sql`, matching the sizing already used for `amount`, `serial_number`, and other ledger-wide counters in the same schemas, to remove the practical possibility of overflow.

### Proof of Concept
Conceptual PoC (schema-level, not exploited in this analysis):
1. Deploy a node using `initial-db/byteball-mysql.sql` or `initial-db/byteball-myrocks.sql`.
2. Repeatedly post payment units, each splitting funds into the maximum allowed outputs per message/unit (`MAX_OUTPUTS_PER_PAYMENT_MESSAGE=128`, `MAX_MESSAGES_PER_UNIT=128`) to maximize `output_id` consumption per unit, as the Morph PoC did with 200 `sendMessage` calls per transaction.
3. Continue until the global `output_id` AUTO_INCREMENT counter approaches `2^31-1`.
4. The next `INSERT INTO outputs` (from any user's payment) fails with a range/duplicate-key error in `writer.js`'s `saveJoint`, preventing that and all subsequent units with payment messages from being saved — a permanent, network-wide denial of service on that storage backend.
