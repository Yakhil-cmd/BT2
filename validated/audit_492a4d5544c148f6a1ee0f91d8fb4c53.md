### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read any other stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's `stack` accessor with a version that resolves the stack directly from `params[:stack_id]`, bypassing the scoping enforced by `Shipit::Api::BaseController#stacks`. Any `ApiClient` restricted to a single stack via `ApiClient#stack_id` can therefore read the CCMenu status (name, last build status/time, web URL) of any stack in the installation simply by changing the `stack_id` in the request path/query, exactly the kind of "stack a token authorises versus a stack it touches" mismatch flagged in the report's bug class (a check performed on one binding while a different, unguarded value is actually used).

### Finding Description
`Shipit::Api::BaseController` implements per-token stack scoping: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client has one, and `stack` resolves `params[:stack_id]` only within that restricted scope — this is what enforces that a token scoped to stack A can never touch stack B.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves directly from the global `Stack` relation: [2](#0-1) 

It only enforces `require_permission :read, :stack` (a permission-string check via `ApiClient#check_permissions!`), which has nothing to do with *which* stack the token is entitled to see: [3](#0-2) 

Because `check_permissions!` only validates the `read:stack` permission flag and never consults `stack_id`, and because `CCMenuController#stack` never calls the scoped `stacks` helper, the `stack_id` scoping binding is checked in `BaseController` but never enforced on the actual code path used by this controller.

Test coverage confirms stack-scoped tokens are a supported/expected feature elsewhere in the API surface: [4](#0-3) 

but `CCMenuControllerTest` never exercises a stack-scoped client against a *different* stack's `stack_id`, so the gap is untested: [5](#0-4) 

The equality that should hold is:
`stack the token is authorized for (ApiClient#stack_id)` == `stack whose data is returned (params[:stack_id] resolved via CCMenuController#stack)`

After the token is minted, an attacker holding *any* valid stack-scoped `read:stack` token can set the second side of the equation to an arbitrary stack id, breaking the equality and reading data belonging to a stack the token was never granted.

### Impact Explanation
This grants unauthorized read access to another stack's build/deploy state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock status, `webUrl`) across the whole installation — including stacks belonging to other repositories/teams that the token holder should have no visibility into. CCMenu tokens are specifically designed to be embedded in external tools/URLs (see `CCMenuUrlController`, which mints a `read:stack`-scoped token for embedding in a public build-status widget URL), so the operational assumption is that such a token is safe to expose narrowly for one stack; this bug defeats that assumption. This matches the "High - unauthenticated/unauthorized read of stack state" impact category.

### Likelihood Explanation
Exploitation requires only a valid stack-scoped `read:stack` API token (which is by design meant to be handed out narrowly, e.g. embedded in a CI status badge URL) and knowledge or guessing of another stack's `stack_id`/`to_param` (stack identifiers are predictable, following `owner/repo/environment` naming, and are visible throughout the UI/API for authenticated users). No further privilege or write access is needed, making this a straightforward, low-effort escalation once any single CCMenu-style token is obtained.

### Recommendation
Remove the `stack` override in `CCMenuController`, or reimplement it using the scoped `stacks` collection from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) so that `current_api_client.stack_id` scoping is honored consistently across all API controllers.

### Proof of Concept
1. Create (or via console) an `ApiClient` scoped to `stack_id: A.id` with `permissions: ['read:stack']` (as the `here_come_the_walrus` fixture demonstrates is a supported configuration in `test/controllers/api/stacks_controller_test.rb:188-198`).
2. Using that client's `authentication_token`, issue: `GET /api/stacks/:B_owner/:B_repo/:B_env/ccmenu.xml?token=<token>` where `B` is a different stack than `A`.
3. Observe the response returns stack `B`'s CCMenu XML (name, lastBuildStatus, etc.) even though the token is only authorized for stack `A`, because `CCMenuController#stack` resolves `params[:stack_id]` via unscoped `Stack.from_param!` rather than the scoped `stacks.from_param!` used everywhere else in the API (`app/controllers/shipit/api/ccmenu_controller.rb:29-31` vs `app/controllers/shipit/api/base_controller.rb:78-80`).
