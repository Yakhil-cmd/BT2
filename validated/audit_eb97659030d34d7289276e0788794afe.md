### Title
Rounding-up bias in headers commission split across multiple recipients causes double-counted/inflated commission payouts - (File: `headers_commission.js`)

### Summary
When a stable unit that wins headers commission has multiple authors (or a custom `earned_headers_commission_recipients` list), the commission `full_amount` is split among recipients by percentage share using `Math.round(full_amount * share / 100.0)` for each recipient independently. Because JavaScript's `Math.round` always rounds `.5` up, and each recipient's fractional share is rounded independently rather than distributing a single indivisible remainder, the sum of the rounded per-recipient amounts can exceed `full_amount`. This mirrors the reported bug class where a proportional split via integer arithmetic silently mishandles "dust," except here it is actually manufactured (extra commission bytes appear) rather than lost.

### Finding Description
In `headers_commission.js`, `calcHeadersCommissions()` computes, for each winning child unit, the commission amount owed to each recipient address based on `earned_headers_commission_share` (an integer percentage): [1](#0-0) 

and, in the SQL/row-driven branch, the same independent per-recipient rounding: [2](#0-1) 

Each recipient's payout is calculated independently as `round(full_amount * share / 100)`, with no adjustment to make the sum equal `full_amount`. `earned_headers_commission_recipients` is validated only to have integer shares that sum to exactly 100 — there is no check that the resulting rounded amounts also sum to `full_amount`: [3](#0-2) 

Because `Math.round` breaks ties by rounding up (`ROUND_HALF_UP` semantics), a set of recipient shares that split `full_amount` into exact `.5`-boundary fractions causes every recipient sharing that boundary to round up simultaneously, inflating the total paid beyond `full_amount`.

### Impact Explanation
This results in bytes being credited to `headers_commission_contributions` in excess of the actual commission earned by the payer unit, which increases the recipients' spendable balance without a corresponding reduction anywhere else — a form of currency (bytes) supply inflation. Since headers commission accrues continuously as units are stabilized, and any user can create a multi-authored unit and assign `earned_headers_commission_recipients` shares of their choosing (as long as they sum to 100 and are sorted, per `validateHeadersCommissionRecipients`), this is directly reachable and repeatable by an ordinary unit poster who controls all the recipient addresses, allowing them to systematically extract extra bytes over many rounds.

### Likelihood Explanation
The condition needed (an odd `full_amount` split evenly, e.g., two recipients at 50%/50%, or similar boundary cases with other share combinations) is easy to engineer deterministically because the attacker fully controls both the number of authors/recipients and their `earned_headers_commission_share` values, and headers commission amounts for many small/normal units are frequently odd numbers of bytes. This is not a probabilistic or rare edge case — it is a mechanical consequence of `Math.round`'s tie-breaking and can be triggered on demand each time the attacker's unit wins headers commission.

### Recommendation
Do not round each recipient's share independently. Instead, compute recipient amounts sequentially, rounding down (or using largest-remainder distribution) for all but the last recipient, and assign the last recipient `full_amount - sum(previous amounts)` so the total always reconciles exactly to `full_amount`. Alternatively, use `Math.floor` for all recipients and distribute the residual bytes deterministically (e.g., to the first recipient by address order) rather than rounding each recipient independently with `Math.round`.

### Proof of Concept
1. Attacker creates a 2-author unit, setting `earned_headers_commission_recipients` to `[{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` (validation only requires the shares to sum to 100 and be sorted by address — both satisfied).
2. This unit becomes the winning child (`getWinnerInfo`) for a parent unit whose `headers_commission` (`full_amount`) is an odd number, e.g. `full_amount = 1` (or any odd amount).
3. In `calcHeadersCommissions()`, for each of A and B: `amount = Math.round(1 * 50 / 100.0) = Math.round(0.5) = 1`.
4. Both A and B are inserted into `headers_commission_contributions` with `amount = 1` each, totaling `2`, while the payer unit's actual `headers_commission` was only `1`. Repeating this across many stabilized units under attacker's control accumulates inflated byte balances credited to attacker-controlled addresses that were never actually paid by anyone.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
