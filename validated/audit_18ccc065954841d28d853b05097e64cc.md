### Title
Permanent market freeze from `i128` overflow during interest accrual - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
An unprivileged caller can permanently freeze an oversized, high-utilization market by advancing its indexes until `scaled_amount * index` no longer fits in `i128`. Once that happens, `update_indexes`, repayments, withdrawals, liquidations, and other market mutations all revert during their mandatory accrual step. The repository's own regression test demonstrates this condition freezing repayment and withdrawal. [1](#0-0) 

### Finding Description
Every pool mutation loads market state and runs `interest::global_sync`, which repeatedly calls `accrue_step`. [2](#0-1) 

`accrue_step` calculates total debt and total supply by multiplying stored scaled shares by their live indexes through `scaled_to_original`. [3](#0-2)  `scaled_to_original` delegates to checked `Ray::mul`, and unrepresentable results raise `MathOverflow`. [4](#0-3) [5](#0-4) 

The borrow-index cap is applied only after this total-value multiplication. [6](#0-5)  Therefore, a market can cross the representable-value boundary before `update_borrow_index` reaches `MAX_BORROW_INDEX_RAY`. [7](#0-6) 

The permissionless path is to create or use a high-decimal market with caps allowing enough shares, supply the asset, collateralize a separate account, borrow enough to keep utilization high, and repeatedly invoke `Controller::update_indexes` or wait for another market operation. `Pool::update_indexes` performs the accrual for every supplied `HubAssetKey`. [8](#0-7)  Public controller entrypoints for `supply`, `borrow`, `repay`, `withdraw`, and `liquidate` then route into pool operations that must accrue first. [9](#0-8) [10](#0-9) 

### Impact Explanation
Once either `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128::MAX`, the market cannot accrue. Because accrual is the first operation in the mutation flow, users cannot repay debt, withdraw collateral, supply additional assets, borrow, or liquidate unhealthy positions; protocol revenue and bad-debt handling on that market are likewise blocked. The test confirms withdrawal and repayment revert with `MathOverflow` after the cliff is reached. [11](#0-10) 

This is permanent absent a privileged contract upgrade: indexes are monotone during ordinary accrual, `update_params` itself accrues before changing the rate model, and there is no non-accruing escape path that reduces the stored scaled balances. [12](#0-11) 

### Likelihood Explanation
The attack requires an extremely large market and enough collateral to maintain high utilization, so it is not reachable in a normally capped market whose configured limits keep `shares * index` below the `i128` domain. However, for a listed high-decimal asset whose caps permit the required scale, every step after market creation is permissionless and the public accrual path can be driven by any address. The test uses a billion-token, eighteen-decimal market at sustained high utilization and reaches the overflow before the configured borrow-index cap. [13](#0-12) 

### Recommendation
Bound market state against the arithmetic domain, not only the index domain.

- Enforce per-market scaled-share ceilings derived from `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`, such that all supported indexes satisfy `scaled * index / RAY <= i128::MAX`.
- Alternatively, compute utilization totals through a saturating or `I256`-based path so accrual can continue and the existing index caps can engage.
- Add equivalent saturation or domain guards to `calculate_supplier_rewards`, `update_supply_index`, and `supply_index_reward_shortfall`, which also multiply scaled shares by indexes. [14](#0-13) [15](#0-14) [16](#0-15) 
- Add a non-accruing emergency write-down or recovery path only if it cannot be abused to alter user balances; otherwise rely on domain-safe accrual and listing caps.

### Proof of Concept
The repository already contains a regression PoC:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
```

Advancing the market and calling `update_indexes` eventually returns `MathOverflow`; afterward both `withdraw` and `repay` return the same error. [17](#0-16)

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
