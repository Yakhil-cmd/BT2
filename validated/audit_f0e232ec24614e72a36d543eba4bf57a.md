### Title
Cross-repository status-poisoning via organization-scoped webhook signature but globally-scoped commit lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a GitHub `status` webhook by looking up the `webhook_secret` tied to the *organization* named in the payload (`repository.owner.login` / `organization.login`) and validating the HMAC over the whole payload. [1](#0-0)  Once the signature check passes, `StatusHandler#process` never re-derives or checks the repository at all — it looks up commits by SHA alone, across the **entire `commits` table**, and writes a GitHub-supplied status onto every matching row: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1)  The base `Handler` class does provide a `repository_name`/`stacks` scoping helper based on `payload.dig('repository', 'full_name')`, [3](#0-2)  but `StatusHandler` is the one handler that does not use it, breaking the binding: *organization authenticated (signature verified for OrgA) ≠ repository actually written (any commit sharing that SHA, in any stack under any organization)*.

### Finding Description
1. `WebhooksController#verify_signature` selects `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')`), and validates only that the request was signed by *that org's* configured `webhook_secret`. [4](#0-3) 
2. Multi-organization Shipit deployments are explicitly supported, each org having its own independent `webhook_secret`/GitHub App. [5](#0-4) 
3. For every other webhook handler (`PushHandler`, the `PullRequest::*Handler` family, `CheckSuiteHandler`), the write is scoped through `Repository.from_github_repo_name(params.repository.full_name)` and then to that repository's own `stacks`. [6](#0-5) [7](#0-6) 
4. `StatusHandler` breaks this pattern: it queries `Commit.where(sha: params.sha)` with **no repository/stack scoping whatsoever**, then calls `commit.create_status_from_github!(params)`, which persists a `Status` record and re-evaluates the commit's deployability/CI-blocking state via `add_status` → `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`. [2](#0-1) [8](#0-7) [9](#0-8) 
5. `Commit#deployable?` and `#blocked?` — the gates checked before continuous deployment or manual deploy is allowed — depend entirely on the `statuses`/`checks` state that `create_status_from_github!` mutates: `deployable?` returns `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. [10](#0-9) 

Because git commit SHAs are content-addressed, it is realistic for the *same* SHA to exist in two different repositories/stacks tracked by the same Shipit instance (e.g., a fork, a mirrored/rebased history, an internal repo whose history was seeded from a public one, or simply an org that mirrors an upstream repo into an internal fork before deploying). An attacker who can legitimately trigger a signed `status` event for *their own* organization/repo (e.g., they are an admin of a low-trust org that also has a GitHub App registered on this Shipit instance, or they control a CI integration that posts commit statuses for their own repo) can set `state: success` for a SHA value they choose. If that SHA also matches a commit belonging to a *different, higher-trust* stack, `StatusHandler` will happily write a "success" status onto that foreign commit, potentially unblocking `ci.require`/`ci.blocking` gates and enabling `stack.schedule_merges` / continuous-delivery to proceed on a stack the attacker has no authorization over.

### Impact Explanation
This crosses the "unauthorized deploy" boundary called out in scope: a payload field (`sha`) that is *not* re-validated against the repository/org whose signature was actually checked is used to write CI status onto commits belonging to an arbitrary stack, which the `deployable?`/`blocked?`/continuous-delivery logic trusts to gate ships. This matches the "High" impact bucket ("unauthenticated... escalation" is closest analog: an attacker escalates their legitimately-signed-but-unrelated-org webhook into writing state that affects another stack's deploy authorization) and, in the SHA-collision scenario, "unauthorized deploy."

### Likelihood Explanation
Likelihood is moderate-to-low in practice: it requires (a) a multi-org Shipit deployment where the attacker legitimately controls a GitHub App/webhook_secret for at least one lower-trust organization tracked by the instance, and (b) a SHA collision (shared commit) between that org's repo and the target stack's repo — which is plausible for forks/mirrors but not universal. No signature forgery, token theft, or GitHub credential compromise is required beyond what the attacker already legitimately possesses for their own org.

### Recommendation
Scope `StatusHandler#process` the same way every other handler is scoped: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (already provided by the base `Handler` class) and restrict the `Commit.where(sha: params.sha)` lookup to `stacks.commits` (or `Commit.where(sha: params.sha, stack_id: stacks.ids)`) instead of querying the global `Commit` table unscoped.

### Proof of Concept
1. Operate (or compromise credentials for) Organization `LowTrust`, which has its own GitHub App/`webhook_secret` registered on the shared Shipit instance (multi-org config as documented in `config/secrets.development.example.yml`).
2. Identify a commit SHA `X` that exists both in a repository under `LowTrust` and in a repository under a higher-trust organization `HighTrust` tracked by the same Shipit instance (e.g., because `HighTrust/app` was forked from or shares history with `LowTrust/app`).
3. Send (or have GitHub deliver, e.g. by pushing to a status-producing CI hook on the `LowTrust` repo) a `status` webhook event with `repository.owner.login = "LowTrust"`, `sha: "X"`, `state: "success"`. This is signed with `LowTrust`'s legitimate `webhook_secret`, so `verify_signature` passes.
4. `StatusHandler#process` executes `Commit.where(sha: "X")`, which returns the `HighTrust` commit as well, and calls `create_status_from_github!` on it — writing a "success" status onto a commit the attacker has no relationship to, potentially satisfying `ci.require`/unblocking `blocked?` and triggering `stack.schedule_merges`/continuous delivery for `HighTrust`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
