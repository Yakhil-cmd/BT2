### Title
Webhook signature is verified against the organization named in the payload while handlers act on a different `repository.full_name` in the same payload — cross-repository status/deploy forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a webhook's HMAC against by reading `repository.owner.login` (or `organization.login`) from the **same untrusted JSON body** whose raw bytes are being verified. The handlers that subsequently act on the payload (`Handler#stacks`/`#repository_name`) instead key off `repository.full_name` from that same body. Since these are two independently attacker-controlled fields inside one payload, an attacker who legitimately controls (and therefore knows the `webhook_secret` for) any organization configured in a multi-tenant Shipit instance can craft a payload that authenticates as their own org but whose `repository.full_name` targets a completely different, victim-owned repository/stack.

### Finding Description
`verify_signature` computes the expected organization from the request body itself: [1](#0-0) [2](#0-1) 

The signature is verified with `Shipit.github(organization: repository_owner).verify_webhook_signature`, which retrieves the `webhook_secret` configured for that organization and HMACs the raw body: [3](#0-2) 

Crucially, `webhook_secret` is a per-organization value read from `Shipit.github` config (see `config/secrets.development.shopify.yml`, which shows multiple orgs each with their own `webhook_secret`). Because the attacker can compute a valid HMAC for their own org's secret over an arbitrary payload they construct, they fully control every field of that payload, including `repository.full_name`, `repository.owner.login`/`organization.login`, `sha`, `state`, etc.

Once the signature check passes, the actual event handlers key their target `Stack`/`Repository` off `repository.full_name`, not off the organization that was used for signature verification: [4](#0-3) 

For the `status` event, the handler creates a GitHub-equivalent commit status purely from attacker-supplied fields, with no re-validation that the authenticated organization actually owns that commit/repository: [5](#0-4) 

This breaks the trust binding: `organization that authenticated the request` should equal `repository/stack the handlers write to`, but the engine never enforces that equality — it only checks that *some* org's secret matches the raw body, and separately trusts `repository.full_name` from that same, fully attacker-authored body.

### Impact Explanation
An attacker who is a legitimate owner/admin of **any** GitHub organization/App that has been configured in a shared, multi-tenant Shipit instance (a supported and documented configuration — see `docs/setup.md` and `config/secrets.development.shopify.yml`, which show multiple orgs each with independent `webhook_secret`s) can forge webhook events for **any other tracked repository's stack**, because the signature only proves the payload was signed with *an* org's secret, not with the secret of the org actually referenced by `repository.full_name`.

Concretely, using the `status` handler, the attacker can inject fabricated "success" statuses for an existing commit belonging to a victim stack that they do not control. If that stack has CI/status requirements gating continuous delivery (`ci.require`, `review.checks`, etc.), this can unblock/trigger an **unauthorized deploy** — satisfying the Critical impact bar ("an unauthorized deploy") without ever touching the victim's actual GitHub repository, Shipit session, or `ApiClient` token.

### Likelihood Explanation
Likelihood is moderate-to-high in any Shipit deployment that serves more than one GitHub organization (a documented, supported topology). The attacker only needs to be a trusted party for their *own* org (i.e., know their own org's `webhook_secret`, which they legitimately possess since they configured the GitHub App/webhook for their org) — no access to the victim org, no Shipit account, and no `ApiClient` token is required. The only prerequisite is that Shipit is multi-tenant with more than one configured organization, which is the engine's normal supported use.

### Recommendation
After verifying the HMAC signature, re-derive the organization strictly from `repository.full_name` (or `organization.login`) and confirm it is consistent with, and authorized for, the org whose secret was used to compute the signature — i.e., verify `repository_owner == organization_owning(repository.full_name)` before dispatching to handlers. Alternatively, look up the target `Repository`/`Stack` by `repository.full_name` first, resolve *that* repository's own configured organization/webhook secret, and verify the signature against that secret rather than against whatever organization the attacker put in the payload.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with independent `webhook_secret`s (as documented in `docs/setup.md`), both having stacks tracked by the same Shipit instance.
2. Attacker legitimately owns `attacker-org` and its GitHub App, so they know `attacker-org`'s `webhook_secret`.
3. Attacker builds a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` computes `repository_owner` = `"attacker-org"` (from `repository.owner.login`), fetches `attacker-org`'s `webhook_secret`, and the signature matches → request passes.
6. `Webhooks::Handlers::StatusHandler#process` uses `Commit.where(sha: params.sha)` — resolved via `victim-org/victim-repo`'s commit — and calls `create_status_from_github!`, injecting a forged "success" status onto the victim's commit, potentially unblocking that stack's continuous delivery/deploy gating despite the attacker having no relationship to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
