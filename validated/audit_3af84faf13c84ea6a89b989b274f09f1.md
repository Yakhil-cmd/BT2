### Title
Webhook signature verification binds to attacker-chosen `repository.owner.login`/`organization.login`, not to the `repository.full_name` actually acted on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook against using values read directly out of the *unverified* JSON body, while the code that actually mutates state (`Webhooks::Handlers::Handler#repository_name` / `Repository.from_github_repo_name`) reads a *different* field from the same unverified body. These two fields are never cross-checked, so the "organization that authenticated" and the "repository that is written" are not the same equality the code assumes.

### Finding Description
`verify_signature` picks the signing organization from the request body itself, before any signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `organization.login` when `repository.owner.login` is absent — both attacker-controlled JSON fields.

`GithubApp#verify_webhook_signature` unconditionally treats the request as valid when the selected organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, the handler that performs the actual write (e.g. `PushHandler`) derives the target repository from a *different* JSON field, `repository.full_name`, with no re-validation that it matches the organization used for signature verification: [4](#0-3) [5](#0-4) 

Because `repository_owner` (used only to pick the secret) and `repository.full_name` (used to resolve the `Stack`/`Repository` that gets mutated) are independent, attacker-controlled fields in the same unauthenticated payload, an attacker can:
1. Set `organization.login`/`repository.owner.login` to any GitHub org configured in this Shipit instance that has **no `webhook_secret` set** (a valid, non-privileged default configuration state, not a secret the attacker needs to know).
2. Set `repository.full_name` to a *different*, secured organization's repository/stack.

`verify_webhook_signature` returns `true` for step 1's org regardless of the actual `X-Hub-Signature` header, so the request passes `verify_signature` entirely without needing any secret. The push handler then acts on the victim stack named in `repository.full_name`, invoking `stack.sync_github(expected_head_sha:)` for a stack the attacker never authenticated against.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," one of the trust equalities this engine is expected to enforce for webhook processing. If the targeted stack has `continuous_deployment` enabled, the forced `sync_github` can pull in new upstream commits and cause `ContinuousDeliveryJob` to deploy them immediately, i.e., an attacker with no credentials at all can trigger an out-of-band deploy on another organization's stack by exploiting a sibling org's missing `webhook_secret`. This falls under the Critical bucket ("an unauthorized deploy").

### Likelihood Explanation
Requires only that the Shipit instance manages more than one GitHub organization and that at least one of them has not configured a `webhook_secret` (a default/no-op configuration state, not a secret value the attacker must obtain), plus a target stack with `continuous_deployment: true`. No session, token, or repository write access is needed.

### Recommendation
Bind the organization used for verification to the same field used for resolving the mutation target, and reject a request when they diverge. Concretely: derive `repository_owner` and the handler's `repository_name` from the same trusted source, and after signature verification, assert `payload.dig('repository','full_name')` belongs to the organization that was actually verified before dispatching to any handler. Also consider making `verify_webhook_signature` fail closed (require a configured secret) rather than defaulting to `true` when `webhook_secret` is blank.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/main",
  "after": "<current head sha of victim repo on GitHub>",
  "repository": {
    "owner": { "login": "org-without-webhook-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`repository_owner` resolves to `org-without-webhook-secret`; `Shipit.github(organization: "org-without-webhook-secret")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally. `PushHandler#repository_name` then reads `repository.full_name` = `victim-org/victim-repo`, resolves its `Stack`, and calls `sync_github`, potentially cascading into an unauthorized deploy if continuous deployment is enabled on that stack.

**Uncertainty**: I could not fully trace `Stack#sync_github`/`ContinuousDeliveryJob` in this session to confirm exactly how quickly a deploy would be triggered end-to-end, nor verify how `Shipit.github_apps`/multi-org configuration is set up in a typical deployment (whether operators commonly leave `webhook_secret` blank for any org). These would need to be checked in the full codebase to fully confirm exploitability preconditions.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
