## Title
Webhook signature verification key is selected from an unauthenticated payload field decoupled from the repository the handler actually writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects **which** organization's webhook secret to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted JSON body, *before* the signature has been validated. The event handlers that subsequently act on the request (`PushHandler`, `CheckSuiteHandler`, `MembershipHandler`, etc.) look up the target `Repository`/`Stack` using a *different* payload field — `repository.full_name` — via `Handler#repository_name` / `Repository.from_github_repo_name`. Nothing ties these two fields together beyond "both happen to appear in the same JSON blob."

### Finding Description
`verify_signature` computes the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks a `GithubApp` instance whose `webhook_secret` is configured per-organization (Shipit explicitly supports multiple GitHub Apps/orgs, each with its own `webhook_secret`, as documented in `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml`). Verification only proves the raw body was HMAC-signed with **that org's** secret; it says nothing about which *repository* the payload's `repository` object refers to.

Once verification succeeds, `Handler#repository_name` resolves the target repository from a **separate** field of the same payload: [3](#0-2) 

and `Repository.from_github_repo_name` splits `owner/name` straight from that string with no cross-check against `repository.owner.login` used earlier for signature-key selection: [4](#0-3) 

Because the HMAC covers the raw body as a whole, an attacker who legitimately controls (or has compromised) the webhook secret for **one** configured organization (e.g. their own org "OrgA", onboarded onto the same Shipit instance) can craft an arbitrary JSON payload where `repository.owner.login = "OrgA"` (selecting OrgA's secret for verification) but `repository.full_name = "OrgB/important-repo"` (the actual repo the handler acts on), sign the whole body with OrgA's known secret, and pass `verify_signature`. `PushHandler`/`CheckSuiteHandler` will then act on stacks belonging to `OrgB/important-repo` — an org whose credentials the attacker never had.

This breaks the binding: *organization that authenticated (via `repository_owner` → webhook secret) ≠ repository that is written (via `repository.full_name` → `Stack`)*.

### Impact Explanation
For `PushHandler`, this lets the attacker trigger `stack.sync_github(expected_head_sha:)` against another organization's stacks, forcing sync operations and, depending on stack state, kicking off deploy-adjacent flows against `SHA`s the attacker chooses for a repository they don't own. For `CheckSuiteHandler`, it lets the attacker forge `schedule_refresh_check_runs!` for arbitrary commits on stacks outside their org. Since Shipit deploys/merges gate on commit/check statuses, forging cross-organization check-run refresh or push-sync signals is an escalation path toward unauthorized deploy behavior on repositories the attacker does not control — this matches the in-scope High/Critical impact bucket of "escalation into authorization... unauthorized deploy."

### Likelihood Explanation
Requires the Shipit instance be configured with multiple GitHub Apps/organizations (an explicitly supported and documented configuration — `docs/setup.md`, `secrets_double_github_app.yml`) and that the attacker controls a legitimate webhook secret for at least one onboarded organization (e.g. their own org onboarded to the shared Shipit instance). This is a realistic multi-tenant deployment pattern for Shipit, and the attacker needs no session, API token, or repository write access to the victim org — only the webhook secret for their own, unrelated, already-onboarded org.

### Recommendation
After signature verification, validate that `repository.owner.login` (the field used to pick the verifying secret) matches the owner segment of `repository.full_name` (the field used to resolve the target `Repository`), and reject the webhook if they diverge. Alternatively, resolve the target repository/stack using the same field that was used for signature key selection, not an independent nested field.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, has a Stack for `OrgB/important-repo`), per the multi-org config format in `config/secrets.development.example.yml`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/important-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` using OrgA's secret, which they legitimately possess.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` computes `repository_owner == "OrgA"`, fetches OrgA's `GithubApp`, and the signature verifies successfully. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Handler#repository_name` = `"OrgB/important-repo"`, and calls `sync_github` on OrgB's stacks — despite the request only being authenticated against OrgA's secret. [5](#0-4)
