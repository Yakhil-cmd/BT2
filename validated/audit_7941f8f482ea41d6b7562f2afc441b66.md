### Title
Attacker-controlled diff padding causes `build_refute_prompt` to silently truncate away the vulnerable diff hunk, making the self-refute stage falsely dismiss real findings - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` hard-truncates the diff shown to the adversarial "refute" model to the first 8000 characters via `diff_text[:8000]`, with no truncation marker and no per-file fairness, unlike `cap_diff_for_prompt` used in stage 1. An attacker who controls the diff content (e.g. via a PR) can pad or order the diff so the actually-vulnerable hunk falls past byte 8000, causing the refute stage to conclude the flagged `vulnerableCode` is "PRE-EXISTING" / not present in the diff and REFUTE a genuine finding that stage 1 correctly surfaced.

### Finding Description
`build_refute_prompt` is defined at [1](#0-0)  and truncates the full diff text unconditionally to 8000 characters before embedding it in the prompt sent to the model: `+ "\n\nDIFF:\n" + diff_text[:8000]`. This truncation has no marker (contrast with `cap_diff_for_prompt`, which appends explicit `"... [truncated by security-guidance...]"` markers and caps per-file/total with `DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES` set to 80000/400000) as seen at [2](#0-1) .

Separately, `tag_diff_anchor` classifies candidates as `in_diff`/`off_diff` using the FULL, untruncated `diff_text` [3](#0-2) . The refute prompt's instructions then tell the model to REFUTE any candidate whose `vulnerableCode` "does NOT appear on any + line in the DIFF block above" [4](#0-3) , and to REFUTE `off_diff` candidates unless it can cite the exact enabling diff line, which it cannot do if that line was chopped off by the 8000-char cutoff [5](#0-4) .

Because the anchor classification (correct, full-diff-based) and the actual text shown to the LLM (truncated, first-8000-chars-only) are inconsistent, an attacker who controls diff content — e.g., by padding an early file with large benign/noise content, or ordering commits/files so the vulnerable hunk lands after byte 8000 — can push the genuinely dangerous `+` lines out of the refute-stage model's view. The model, following its own explicit instructions, will then legitimately REFUTE a correctly-flagged, in-diff finding as "PRE-EXISTING" or unsupported, causing the automated security-guidance review to silently drop a real vulnerability from its output.

### Impact Explanation
This breaks the security review's core invariant that high-risk diff lines must remain visible through truncation. A malicious/careless PR author can defeat the security-guidance plugin's stage-2 adversarial check purely by controlling ordinary diff size/ordering, causing real vulnerable code changes to pass through the review pipeline unflagged (findings dropped from `survived`, silently discarded by `filter_by_severity`/`format_findings` downstream). This is a review/export logic weakness that lets attacker-controlled repository content (a crafted diff) suppress its own security review, matching "review/export logic" bypass and effectively a wrong-outcome/mutation-acceptance impact (insecure code silently accepted instead of flagged).

### Likelihood Explanation
Fully attacker-controlled and requires no privilege beyond submitting a normal diff/PR that the plugin reviews — an ordinary unprivileged content-only path. The 8000-character cutoff is small relative to the stage-1 cap (`DIFF_TOTAL_BYTES` = 400000), so padding a diff past 8000 characters (e.g., one moderately sized unrelated file change) is trivial and highly repeatable; the attacker only needs to know their vulnerable hunk should not be among the first ~8000 characters of the assembled diff text.

### Recommendation
Make `build_refute_prompt`'s truncation consistent with `tag_diff_anchor`'s view of the diff: either (a) do not additionally truncate `diff_text` beyond what `cap_diff_for_prompt` already caps (400000 bytes is the intended budget), or (b) if a hard prompt-size cap is required, prioritize/preserve the hunks corresponding to the candidates' `vulnerableCode`/`filePath` (e.g., extract only the relevant per-candidate diff hunks) rather than naively slicing the first N characters, and always add an explicit truncation marker so the model knows content was cut and should not default to REFUTE for that reason.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/`:
1. Construct `diff_files` with a first dummy file whose diff content is >8000 characters of benign padding, followed by a second file containing a clearly dangerous `+` line (e.g., `subprocess.run(user_input, shell=True)`).
2. Run stage 1 (`cap_diff_for_prompt` + assemble `diff_text`) to get the full concatenated `diff_text`, and produce a `candidates` list with one entry whose `vulnerableCode` is the dangerous line, from the second file.
3. Call `tag_diff_anchor(candidates, diff_text)` — assert it tags the candidate `in_diff` (it is a real `+` line).
4. Call `build_refute_prompt(candidates, diff_text)` — assert that the dangerous line/file string does NOT appear in the returned prompt string (proving `diff_text[:8000]` dropped it), while `tag_diff_anchor` claims `in_diff`. This demonstrates the anchoring/prompt inconsistency: expected assertion `dangerous_line not in build_refute_prompt(candidates, diff_text)` while `candidates[0]["_diff_anchor"] == "in_diff"` — showing the model is denied the exact evidence it's instructed to require, driving a false REFUTE.

```python
def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```

```python
def tag_diff_anchor(
    candidates: list[dict[str, Any]], diff_text: str
) -> list[dict[str, Any]]:
    """SOFT diff-intersect: tag each candidate ``_diff_anchor: "in_diff" |
    "off_diff"`` and sort in_diff first; do NOT drop.

    Investigate reads full files and often cites pre-existing patterns in
    unchanged context (the largest false-positive source).  Hard-dropping
    those also discards correct findings whose sink is off-diff but
    enabled by an in-diff change.  The refute pass's DIFF-ANCHOR block
    keys on the ``_diff_anchor`` tag to apply stricter evidence to
    off_diff candidates instead of dropping them.

    Mutates ``candidates`` in place; returns it for chaining.
    """
    added = [
        ln[1:]
        for ln in diff_text.splitlines()
        if ln.startswith("+") and not ln.startswith("+++")
    ]
    removed = [
        ln[1:]
        for ln in diff_text.splitlines()
        if ln.startswith("-") and not ln.startswith("---")
    ]

    def _norm(s: str) -> str:
        return " ".join(t for t in " ".join(s.split()).split() if len(t) > 2)

    added_norm = _norm("\n".join(added))
    removed_norm = _norm("\n".join(removed))

    def _intersects(cand: dict[str, Any]) -> bool:
        vc = _norm(" ".join(str(cand.get("vulnerableCode") or "").split()))
        if len(vc) < 8:
            return True
        toks = vc.split()
        for i in range(max(1, len(toks) - 2)):
            if " ".join(toks[i : i + 3]) in added_norm:
                return True
        for ln in added:
            ln_n = _norm(ln)
            if len(ln_n) >= 8 and ln_n in vc:
                return True
        if len(added) < len(removed):
            for i in range(max(1, len(toks) - 2)):
                if " ".join(toks[i : i + 3]) in removed_norm:
                    return True
        return False

    for c in candidates:
        c["_diff_anchor"] = "in_diff" if _intersects(c) else "off_diff"
    candidates.sort(key=lambda c: c.get("_diff_anchor") != "in_diff")
    return candidates
```
