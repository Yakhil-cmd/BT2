### Title
CCMenu API scope binding broken: `ApiClient` scoped to stack A can read stack B's build XML - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides `#stack` to use `Stack.from_param!(params[:stack_id])` directly instead of the base `BaseController#stacks`/`#stack` scoping that restricts lookups to `current_api_client.stack_id` when the client is stack-scoped. `check_permissions!` only validates the operation/scope string (`"read:stack"`), never the specific stack, so any authenticated `ApiClient` — whether authenticated via `?token=` or via HTTP Basic auth fallback (`super`) — can fetch CCMenu XML for any stack ID, not just the one it was issued for.

### Finding Description
The broken binding: `current_api_client.stack_id == stack.id` is expected but never enforced in this controller, whereas it is normally is enforced through `BaseController#stacks` at `app/controllers/shipit/api/base_controller.rb:74-80`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
`CCMenuController` overrides `#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) to bypass this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
`require_permission :read, :stack` (ccmenu_controller.rb:6) only calls `ApiClient#check_permissions!(operation, scope)` (app/models/shipit/api_client.rb:38-45), which checks the literal string `"read:stack"` is in the client's `permissions` array — it has no notion of *which* stack, so it passes regardless of `stack_id`.

Attack flow: attacker holds a Basic-auth-capable `ApiClient` token scoped to stack A (`stack_id` set to A). They send `GET /api/stacks/:stack_id/ccmenu.xml` with `stack_id` = B and no `token` param. `authenticate_api_client` (ccmenu_controller.rb:33-36) calls `ApiClient.authenticate(nil)` which returns `nil`, so it falls to `super`, which is `BaseController#authenticate_api_client` (base_controller.rb:48-61) and successfully authenticates via HTTP Basic auth using the stack-A token. `check_permissions!` passes because the token has `read:stack`. `#show` then calls the overridden `#stack`, which does an unscoped `Stack.from_param!(params[:stack_id])` for stack B, and renders stack B's build status/deploy XML.

Existing guards fail because: `verify_signature`/webhook checks are irrelevant here (this is the API path, not webhooks); `require_permission!` only checks the operation string, not stack identity; and the only place stack-scoping is implemented (`BaseController#stacks`) is shadowed by the subclass override in `CCMenuController`.

### Impact Explanation
An attacker with one legitimately-issued `ApiClient` token scoped to stack A can read CI/deploy build status (`lastBuildStatus`, `lastBuildLabel`, activity, lock status, etc.) for any other stack B in the same Shipit installation, including private/internal projects they have no authorization for. This is repeatable for every stack ID (stack IDs/slugs are guessable/enumerable via `to_param`, typically `owner/repo/branch`), so the blast radius covers all stacks hosted by the instance. This matches "High - unauthorized read of stack state" (cross-tenant confidentiality violation via unauthenticated/unauthorized read of stack state).

### Likelihood Explanation
Preconditions: attacker needs one valid `ApiClient` record with any permission set that includes `read:stack` and Basic-auth capability, scoped to some stack (a very ordinary CI-integration credential, e.g. a CCMenu URL token given to a legitimate stack owner). No GitHub secrets, no Shipit operator role, and no elevated privileges are required — this is fully within the reach of an "unprivileged" holder of a single legitimate scoped API token. The request is a simple unauthenticated (from Shipit's perspective, aside from the attacker's own valid Basic-auth credentials) GET request; it is trivially repeatable against any `stack_id`.

### Recommendation
Remove the `#stack` override in `CCMenuController` (or have it call `stacks.from_param!(params[:stack_id])` using the inherited scoped `#stacks` method) so that stack-scoped `ApiClient` tokens can only resolve stacks within their own `stack_id`, consistent with the rest of the API controllers.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (illustrative; actual test file is out-of-scope per rules but shown for reproducibility guidance):
```ruby
test "a token scoped to stack A cannot read stack B via Basic auth fallback" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  client_a = ApiClient.create!(creator: @user, name: 'client-a', stack: stack_a, permissions: ['read:stack'])
  request.headers['Authorization'] = ActionController::HttpAuthentication::Basic.encode_credentials(client_a.authentication_token, '')

  get :show, params: { stack_id: stack_b.to_param }

  # Expected (secure) behavior: 403/404 because client_a.stack_id (stack_a.id) != stack_b.id
  assert_response :forbidden # or :not_found
  # Actual (vulnerable) behavior observed: 200 OK with stack B's XML
end
```
Assert both sides of the binding explicitly: `client_a.stack_id` (= `stack_a.id`) must equal the `id` of the stack rendered in the response before granting access; currently `CCMenuController#stack` renders `stack_b.id` regardless, proving the divergence.
