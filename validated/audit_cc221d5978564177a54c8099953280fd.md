## Title
Cross-repository status forgery unblocks a victim stack's undeployed commit queue - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` with a globally unscoped `Commit.where(sha: params.sha)`, never checking that `params.sha` belongs to the repository the webhook signature was actually verified for. `Commit#blocked?` then walks `stack.commits.reachable...any?(&:blocking?)`, so any status webhook that matches an existing commit `sha` anywhere in the database — regardless of which repository/stack it belongs to — can flip `blocking?` to false for that commit, which unblocks every later commit in that (different) stack's undeployed queue.

### Finding Description
The claimed binding is: `webhook.repository.full_name == commit.stack.repository.full_name` for every commit that `StatusHandler` mutates. Tracing the code shows this binding is **not enforced**.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` only validates that the webhook truly came from GitHub for the organization named in the payload (`repository_owner`), via `Shipit.github(organization: repository_owner).verify_webhook_signature`. It authenticates *who sent the webhook* (a real GitHub org), not *which commit/stack the sha belongs to*. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This queries `Commit` globally with no `repository`/`stack` filter tying it back to the webhook's own repository. [2](#0-1) 
- `create_status_from_github!` → `add_status` creates a `Status` row and updates the commit's derived `state`/`blocking?` (`Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)`). [3](#0-2) 
- `Commit#blocked?` scans the stack's own undeployed range for any blocking commit:
```ruby
stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
```
If a status pushes an intermediate commit's state to `success` (or any non-blocking context) from an unrelated repository's webhook, `blocking?` becomes false for that commit and every later `Commit#blocked?`/`UndeployedCommit#blocked?` check in the *victim's* stack loses that blocker. [4](#0-3) 

Exploit path: GitHub's "create commit status" API does not require the `sha` parameter to correspond to a real commit object already present in the calling repository — it stores the status keyed by the literal `sha` string. An attacker who owns/controls any GitHub repository that is registered as a legitimate Shipit stack (satisfying the org-level `verify_webhook_signature` check) can POST a commit status against their own repo using an arbitrary `sha` value equal to a victim stack's known commit SHA (SHAs are public on GitHub commit pages) and `state: success`. GitHub emits a genuinely signed `status` webhook to Shipit's `/webhooks` endpoint with that forged `sha`. `verify_signature` passes because the webhook truly came from GitHub for the attacker's own organization. `StatusHandler` then finds the victim's `Commit` row by that shared `sha` value and writes a new `Status` onto it, exactly as if the victim's own CI had reported it.

None of the existing guards address this: `verify_signature` checks org-level HMAC only, `drop_unhandled_event` only checks the event type is registered, and there is no `ExplicitParameters` field or model validation that ties the resolved `Commit`/`stack` back to the webhook's `repository.full_name`. The commit's own repository name is never compared against the incoming payload's repository at all in `StatusHandler`.

### Impact Explanation
A single forged webhook mutates a `Status` record belonging to a different tenant's stack, clearing a blocking condition (`blocking?` → false) that in turn flips `Commit#blocked?`/`UndeployedCommit#blocked?` for one or more downstream, undeployed commits in that victim stack. Because `deployable?` depends on `!blocked?`, this can make previously-blocked commits eligible for deploy, and combined with continuous delivery (`schedule_continuous_delivery`), can trigger an unauthorized deploy of commits the victim's own CI never approved. This is a payload for one repository mutating another repository's commit/stack state and enabling an unauthorized deploy — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy"). The attack is repeatable against any stack/commit whose SHA the attacker can learn (which is public GitHub data), and is not limited to a single victim — it works across arbitrary tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) the attacker controls at least one repository that is already onboarded as a legitimate Shipit stack under an organization for which Shipit has a valid webhook/App configuration (satisfying `verify_webhook_signature`); (2) the victim stack has an undeployed commit queue with an earlier commit in a `pending`/blocking CI state; (3) the attacker knows the victim commit's SHA (trivially obtainable — SHAs are public on GitHub, PRs, commit pages). No Shipit session, API token, or GitHub secret is required — only ordinary GitHub API/webhook access to a repo the attacker already owns. This is low-cost and fully repeatable.

### Recommendation
Scope the `StatusHandler` (and analogous handlers) commit lookup by the webhook's own repository, e.g. resolve `stacks` via the existing `stacks`/`repository_owner` scoping mechanism used elsewhere, and filter `Commit.where(sha: params.sha, stack: repository.stacks)` (or equivalent join through `Stack#repository`) instead of a bare `Commit.where(sha: params.sha)`. Reject/ignore status webhooks whose payload repository does not match the commit's own stack repository.

### Proof of Concept
Minitest plan (models/webhooks layer, no live GitHub):
```ruby
test "a status webhook from repo A must not clear blocked? for a commit in repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  attacker_owned_repo_name = "attacker/unrelated-repo"

  soc_second = victim_stack.commits.create!(sha: "s" * 40, ...)
  soc_third  = victim_stack.commits.create!(sha: "t" * 40, ...)
  soc_second.statuses.create!(stack: victim_stack, state: "pending", context: "ci/travis")

  assert_predicate soc_third, :blocked? # blocked by soc_second pending

  # Forged webhook: real GitHub signature for attacker's own org, but sha == soc_second.sha
  forged_payload = {
    "sha" => soc_second.sha,
    "state" => "success",
    "context" => "ci/travis",
    "repository" => { "full_name" => attacker_owned_repo_name, "owner" => { "login" => "attacker" } },
    "branches" => []
  }
  Shipit::Webhooks::Handlers::StatusHandler.new.call(forged_payload)

  soc_second.reload
  soc_third.reload
  refute_predicate soc_second.status, :blocking? # now flipped
  refute_predicate soc_third, :blocked?           # BEFORE fix: incorrectly false; should remain true
end
```
Binding checked before/after: `webhook.repository.full_name ("attacker/unrelated-repo") == soc_second.stack.repository.full_name ("shopify/shipit-engine")` is `false` both before and after the status write — yet the mutation still occurs, proving the missing binding check.
