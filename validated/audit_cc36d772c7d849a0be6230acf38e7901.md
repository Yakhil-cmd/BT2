### Title
Webhook signature verification keys off `repository.owner.login` while every event handler acts on `repository.full_name` — cross-organization/cross-repository forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret` used to validate the HMAC) using `repository.owner.login` (or `organization.login`), but every webhook handler resolves the actual `Repository`/`Stack` to write to using the completely different `repository.full_name` field. These two fields are never checked for consistency, so a payload whose `owner.login` matches an organization configured **without** a `webhook_secret` (an explicitly documented, supported configuration) passes signature verification unconditionally, while its `full_name` can point at a repository belonging to any other configured organization.

### Finding Description
`verify_signature` computes the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')`. That value is used to look up the org-scoped `GitHubApp` via `Shipit.github(organization: repository_owner)`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that org has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret` is explicitly documented as optional per-organization in a multi-org deployment: [4](#0-3) 

Once the request passes `verify_signature`, the full raw JSON `params` (fully attacker controlled) is dispatched to every registered handler for the event: [5](#0-4) 

But every handler determines *which* `Repository`/`Stack` to act on using a different field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization authenticated via repository.owner.login (or organization.login)` == `organization implied by repository.full_name used to select the Stack that is written to`

This equality is never enforced. An attacker can supply a payload where `repository.owner.login` = an organization with no configured `webhook_secret` (satisfying signature verification trivially), while `repository.full_name` = `"<victim-org>/<victim-repo>"`, causing handlers to operate on the victim organization's `Repository`/`Stack` records.

Concretely, `PushHandler` uses this to select stacks by branch and trigger a GitHub sync with an attacker-chosen `after` sha: [8](#0-7) 

`StatusHandler` similarly creates a commit status (which factors into deployability/CI checks) purely from the attacker-supplied `sha`/`state`, independent of which "authenticated" organization the request nominally came from: [9](#0-8) 

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose webhook secret authenticated this request" and "the repository/stack that is actually mutated." In a multi-org Shipit installation (the pattern explicitly documented in `docs/setup.md`), if any one configured organization has no `webhook_secret` set (an accepted, documented configuration — "Webhook secret (optional)"), an unauthenticated attacker can spoof the signature-checked organization while writing events into a completely unrelated organization's stacks: forcing `GithubSyncJob` to treat an attacker-chosen commit as HEAD, or forging a `status` (CI) event that marks an existing commit "success," which feeds directly into `deployable?`/continuous-delivery logic and can enable an unauthorized deploy of a specific pre-existing commit on a victim stack. This satisfies the "unauthorized deploy" Critical/High impact bucket.

### Likelihood Explanation
Requires: (1) a Shipit installation configured for multiple GitHub organizations (documented, supported feature), and (2) at least one of the configured organizations having no `webhook_secret` — also documented as an accepted, optional configuration, not a misconfiguration of engine mounting. Given those two documented conditions, exploitation requires no credentials at all: the `/webhooks` endpoint is unauthenticated by design and accepts arbitrary JSON bodies from any unprivileged network client.

### Recommendation
Enforce that the field used to select the signing key is the same field used to resolve the target repository/stack. Concretely: verify the signature using the organization derived from `repository.full_name`'s owner segment (not `repository.owner.login`/`organization.login`), or, after verification, re-check that `repository.owner.login == repository.full_name.split('/').first` and reject (422) on mismatch before dispatching to handlers. Additionally, consider treating a missing `webhook_secret` for one org in a multi-org config as "trusted only for that org's own repositories," never as a blanket bypass usable to authenticate payloads targeting other orgs' repositories.

### Proof of Concept
Given a Shipit config with two organizations, `OrgA` (no `webhook_secret` configured) and `OrgB` (victim, has a stack tracking `OrgB/victim-repo`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-existing-sha-in-OrgB/victim-repo>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```

- `WebhooksController#repository_owner` resolves to `"OrgA"`.
- `Shipit.github(organization: "OrgA").verify_webhook_signature(...)` returns `true` immediately because `OrgA` has no `webhook_secret` (`lib/shipit/github_app.rb:76-77`), regardless of the (absent/garbage) `X-Hub-Signature` header.
- Request proceeds to `Shipit::Webhooks.for_event('push')`, invoking `PushHandler`, whose `repository_name` resolves via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), loading `OrgB`'s actual `Repository`/`Stack`.
- `stack.sync_github(expected_head_sha: params.after)` is invoked on the victim's stack with an attacker-chosen sha, and a subsequent forged `status` webhook (same `owner.login`/`full_name` split trick) can mark that commit's CI status as green, enabling deployability on `OrgB`'s stack without any credential belonging to `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
