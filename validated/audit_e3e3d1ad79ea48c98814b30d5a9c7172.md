### Title
JSON-RPC Memory Amplification Before Any Rate/Concurrency Limiting - (File: `chain/jsonrpc/src/lib.rs`)

### Summary
nearcore's JSON-RPC server (`chain/jsonrpc/src/lib.rs`) has the same structural weakness described in the report: the only protection on the `/` POST endpoint is a byte-size cap on the raw request body (`RequestBodyLimitLayer::new(limits_config.json_payload_max_size)`, default 10MB), and full `serde_json` deserialization into `Message`/`Value` structures happens unconditionally for every request before any per-IP or global concurrency control exists.

### Finding Description
The router is built in `create_jsonrpc_app()`: [1](#0-0) 
The only middleware layers applied are CORS and `RequestBodyLimitLayer` — there is no `tower::limit::ConcurrencyLimitLayer`, no semaphore, and no per-IP rate limiter anywhere in the JSON-RPC stack. My search for `Semaphore|ConcurrencyLimit|rate_limit` across the repo found matches only in the P2P/network layer (`chain/network/src/rate_limits/*`, `chain/network/src/peer/*`), never in `chain/jsonrpc/*`. That means every accepted HTTP request up to the 10MB body limit is fully parsed with no throttling at all — nearcore is actually *less* protected than the monad-bft server described in the report, which at least had a global 1,000-concurrent-request semaphore.

The `rpc_handler` route handler takes `Json<Message>` as an Axum extractor: [2](#0-1) 
Axum's `Json<T>` extractor performs full `serde_json` deserialization of the entire body into the `Message` type before the handler body even executes. `Message` is an `untagged` enum that includes a `Batch(Vec<Message>)` variant: [3](#0-2) 
and each `Request`'s `params` field is deserialized into an untyped `serde_json::Value`: [4](#0-3) 
This produces exactly the amplification mechanism the report describes: JSON arrays/objects become `Vec<Value>`/`HashMap<String,Value>` with heap allocation and per-element enum overhead, and this happens for the whole 10MB body — and for every request in a `Batch`, unboundedly, since there is no batch-size cap comparable to the report's "5,000 requests per batch" limit. If the body doesn't even amount to a valid `Request` (e.g., a `Batch` or `Notification`), `process()` only rejects it *after* the full parse has already completed and the memory has already been allocated: [5](#0-4) 

Unlike the monad-bft report, however, nearcore performs only a single `serde_json` deserialization pass per request (into `Message` directly, via `axum::Json`), not the reported "double parsing penalty," and query/parameter-specific parsing (`R::parse(request.params)`) operates on the already-materialized `Value`, which is comparatively cheap relative to the initial parse.

### Impact Explanation
Because there is no per-IP or global concurrency/semaphore control on the JSON-RPC HTTP endpoint, an attacker can send many concurrent 10MB requests (the max configured body size) from one or more source IPs. Each such request forces the node to allocate several times the wire size in heap memory for the `serde_json::Value` tree (and again for any nested arrays/objects inside `params`, or nested `Batch` elements) before the handler can reject or process it. With enough concurrent connections this can exhaust process memory and crash or stall the validator/RPC node — a node-level resource-exhaustion condition reachable purely from unauthenticated RPC/HTTP requests, matching the "node panic or unbounded resource use" acceptance criterion. This affects availability of the RPC endpoint (and, if run on a validator node, potentially the validator's chain participation), not consensus-level state or balance correctness.

### Likelihood Explanation
High likelihood of triggerability: the JSON-RPC endpoint is intentionally public-facing (default `0.0.0.0:3030`), requires no authentication, and the vulnerable code path (`Json<Message>` extraction) is hit by every single POST to `/` before any method-specific logic or validation runs. No special account, contract, or validator status is required — this is reachable by any external caller sending crafted large/batched JSON bodies within the configured 10MB body limit.

### Recommendation
1. Add a `tower::limit::ConcurrencyLimitLayer` (or an equivalent global semaphore) around the `/` route in `create_jsonrpc_app()` to bound the number of simultaneous body-parsing operations.
2. Add per-IP or per-connection rate limiting ahead of the `Json<Message>` extractor (e.g., a custom Axum middleware/extractor that inspects `Content-Length` and enforces limits before calling into `serde_json`), rather than relying solely on `RequestBodyLimitLayer`.
3. Cap the number of elements permitted in a `Message::Batch` (or reject batches outright if unsupported) to prevent unbounded nested allocation within a single request body.
4. Consider streaming/limits-aware JSON parsing or a lower default `json_payload_max_size` for public-facing deployments, and document the amplification risk of the current 10MB default in `RpcLimitsConfig`.

### Proof of Concept
1. Start a nearcore node with default RPC config (`json_payload_max_size` = 10MB, no other RPC limits configured), as seen in `nearcore/res/example-config-no-gc.json`.
2. From an attacking client, open many concurrent HTTP connections to `POST http://<node>:3030/` and send bodies close to the 10MB limit, each containing either:
   - A `Message::Batch` array (`[{"jsonrpc":"2.0","method":"x","params":[...]}, ...]`) with as many entries as fit under 10MB, or
   - A single request whose `params` contains a deeply nested/large JSON array/object.
3. Because `axum::extract::Json<Message>` fully deserializes the payload into `serde_json::Value` trees before `rpc_handler` runs any logic, and because no concurrency/rate limiting layer exists on this route (`create_jsonrpc_app()` in `chain/jsonrpc/src/lib.rs`), each concurrent connection consumes several times its wire size in heap memory concurrently, with no cap on the number of simultaneous in-flight parses. Sustained concurrent connections from one or more IPs can drive the node's memory usage far beyond the sum of the wire-level payload sizes, exhausting available memory.

#[derive(Debug, Clone, PartialEq, serde::Serialize, serde::Deserialize)]
#[serde(untagged)]
pub enum Message {
    /// An RPC request.
    Request(Request),
    /// A response to a Request.
    Response(Response),
    /// A notification.
    Notification(Notification),
    /// A batch of more requests or responses.
    ///
    /// The protocol allows bundling multiple requests, notifications or responses to a single
    /// message.
    ///
    /// This variant has no direct constructor and is expected to be constructed manually.
    Batch(Vec<Message>),
    /// An unmatched sub entry in a `Batch`.
    ///
    /// When there's a `Batch` and an element doesn't conform to the JSONRPC 2.0 format, that one
    /// is represented by this. This is never produced as a top-level value when parsing, the
    /// `Err(Broken::Unmatched)` is used instead. It is not possible to serialize.
    #[serde(skip_serializing)]
    UnmatchedSub(Value),
}
