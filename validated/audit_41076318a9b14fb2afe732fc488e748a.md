### Title
Share-minting formula in the Uniswap-like AA example can be forced into its "initial deposit" branch to mint shares far exceeding the depositor's real contribution - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The AA-based market-maker pattern shipped in ocore's oscript samples uses a state variable (`var['mm_asset_outstanding']`) to track the total supply of a liquidity ("mm_asset") share token, exactly like Spartan's Pool tracked `totalSupply` (`P`). The share-issuance formula treats any state where one side of the reserves is `0` as a fresh "initial deposit" and mints shares equal to the *entire current balance* rather than a value proportional to the actual new contribution. An unprivileged AA trigger sender can drive one side of the reserves to `0` through ordinary swap operations that never touch `mm_asset_outstanding`, then deposit a trivial amount and receive shares equal to the whole pool balance, degenerately re-pricing the share token exactly as in the original report (where `P` collapsing to `1` broke the share formula for everyone else).

### Finding Description
The AA in [1](#0-0)  computes new shares as:
```
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
...
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```
`$asset_balance` and `$bytes_balance` are simply the AA's current reserves minus the amounts in the current trigger, i.e. they reflect the reserve state at execution time, not a genesis-only condition. Two independent, unprivileged case branches can drive either side to zero without ever adjusting `var['mm_asset_outstanding']`:
- `exchange asset to bytes` [2](#0-1) 
- `exchange bytes to asset` [3](#0-2) 

Both only move value between `balance[base]` and `balance[$asset]` using the constant-product formula and never touch `var['mm_asset_outstanding']`. This mirrors the root cause of the original finding: a state variable meant to represent total share supply (`P`/`mm_asset_outstanding`) can be desynchronized from the reserve amounts it is supposed to track, because the code that guards against divide/zero conditions is reused as an "initial deposit" trigger instead of being restricted to genesis-only state.

Once one side of the reserves (say `$asset_balance`) is pushed to `0` via a normal swap, the very next "invest" trigger — even one funding a trivial `1` unit of base and `1` unit of the paired asset — is classified as an "initial deposit," and `$issue_amount` is set to `balance[base]` (the AA's *entire current bytes balance*, which still holds essentially all previously-invested capital from other, honest depositors). This amount is added on top of the pre-existing `var['mm_asset_outstanding']` at [4](#0-3) , so the attacker is minted a number of mm_asset shares disproportionate to their real contribution while old shareholders' balances are untouched but massively diluted.

### Impact Explanation
The attacker can then divest via [5](#0-4) , redeeming a share of `balance[$asset]` and `balance[base]` far larger than what they contributed, at the direct expense of prior depositors. This is a concrete AA fund-loss/theft scenario reachable by any ordinary AA trigger sender, equivalent in class to the original Spartan Pool exploit where manipulating the share-supply accounting variable let an attacker capture value contributed by other users.

### Likelihood Explanation
Every step (swap-to-drain one reserve side, then deposit a minimal amount, then divest) uses only the AA's normal, publicly documented case branches and requires no special privilege — any address can send triggers to a deployed instance of this pattern. The only requirement is that the pool's non-attacker-controlled side of the reserve can be temporarily driven to exactly `0`, which is achievable by a well-funded attacker performing a large enough swap (constant-product AMMs can reach a zero balance on one side only in the limiting case, but the underlying design flaw — reusing a "balance == 0" check as a supply-reset condition rather than gating strictly on genesis — is a structural error independent of how close to zero the balance must get in any given deployment).

### Recommendation
Do not derive "is this an initial deposit" from a runtime reserve check. Track genesis explicitly (e.g., a dedicated `var['initialized']` flag set once and never re-enterable), and always compute new share issuance strictly proportional to `var['mm_asset_outstanding']` and the pre-trigger reserves, bouncing instead of falling back to an "initial deposit" mint whenever `mm_asset_outstanding` is already nonzero. More generally, any AA sample distributed with ocore that manages a share/LP-token-like state variable should decouple that variable's initialization path from reserve-based edge cases that can be re-triggered post-genesis by ordinary swap/divest activity.

### Proof of Concept
1. Attacker (or any user) performs normal deposits/swaps until the pool has real reserves, e.g. `balance[base] = 5,000,000`, `balance[$asset] = 50` and `var['mm_asset_outstanding'] = 1,000,000` (representing prior honest investors' shares).
2. Attacker repeatedly triggers the `exchange asset to bytes` case [2](#0-1)  until `balance[$asset]` reaches `0` (the constant-product math pushes `$asset_balance` asymptotically toward the entire asset supply moved out; with a supply large enough relative to the pool, this is achievable).
3. Attacker sends a new "invest" trigger with a nominal `1` unit of `base` and `1` unit of `$asset`. Because `$asset_balance == 0` at read time, the AA takes the `// initial deposit` branch at [6](#0-5)  and sets `$issue_amount = balance[base]` (≈5,000,001, essentially all of the pool's bytes, most of which came from other users).
4. `var['mm_asset_outstanding']` becomes `1,000,000 + 5,000,001 = 6,000,001`, with the attacker now owning `5,000,001` of it versus the original investors' `1,000,000`.
5. Attacker divests via the `divest MM shares` case [5](#0-4) , redeeming roughly `5,000,001 / 6,000,001 ≈ 83%` of the pool's `base` and `$asset` reserves — far more than the `1` unit they actually contributed — at the expense of the original depositors.
