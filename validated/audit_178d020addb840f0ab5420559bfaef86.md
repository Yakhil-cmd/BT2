### Title
Asset definer can unilaterally rewrite the attestor list to freeze all holders' ability to spend a `spender_attested` asset - (File: validation.js)

### Summary
For any asset created with `spender_attested: true`, the sole `definer_address` can post an `asset_attestors` message at any time, with no timelock and no consent from existing holders, to replace the entire list of trusted attestors. Because every subsequent `payment`/transfer of that asset is validated against the *current* attestor list rather than the list in effect when the tokens were issued or held, the definer can retroactively de-attest all existing holders and permanently block them from moving their already-issued balances — the same "privileged single key halts core user operations with no timelock" pattern as the reported `Option.kill()` DoS.

### Finding Description
An asset's `spender_attested` flag requires that every author of a payment be on the asset's attestor list, checked in `validatePayment`: [1](#0-0) 

The attestor list itself can be freely rewritten after asset creation via an `asset_attestors` message, validated by `validateAttestorListUpdate`, whose only real gate is that the message be single-authored by the asset's `definer_address`: [2](#0-1) 

`checkAttestorList` only enforces that the new list is non-empty, sorted, and made of valid addresses — it does not require inclusion of previously-attested addresses, nor any minimum overlap with the old list: [3](#0-2) 

At read time, `storage.readAsset` always resolves the *latest* attestor-list unit for the asset (most recent by level/rowid), so once a new `asset_attestors` unit becomes stable, it fully supersedes the prior list for all future validations — nothing is issuance/holding-time pinned: [4](#0-3) 

`filterAttestedAddresses` then computes `arrAttestedAddresses` by intersecting the *current* attestor list with the `attestations` table: [5](#0-4) 

Consequently, a holder who received/held the asset while attested under the old list can be excluded going forward the moment the definer swaps the list, and `validatePayment` will reject any transfer they author with "none of the authors is attested" or "issuer is not attested": [1](#0-0) 

This mirrors the reported class exactly: a single privileged actor (here, the asset `definer_address`, analogous to the `Option` contract's `factory`/`owner`) can, with a single self-authored message and no timelock, indefinitely halt normal user operations (here, spending/transferring an already-issued asset instead of `mint`/`exercise`) for arbitrary sets of existing holders.

### Impact Explanation
Any holder of a `spender_attested` asset — public or private — can have their entire balance permanently frozen (unable to be transferred to anyone, since the check applies to `bIssue` issuers and to any input author) by a single unilateral action of the asset definer. There is no way for holders to opt out, no grace period, and no on-chain recourse; the freeze persists until/unless the definer chooses to re-add them. For assets with real economic value (e.g., regulated/attested tokens), this is a direct, indefinite freezing of user funds triggerable by one compromised or malicious key, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is high for any deployed `spender_attested` asset: the attack requires only that the definer key sign one `asset_attestors` message — no special network conditions, no cooperation from other parties, and it is indistinguishable from a legitimate attestor-list update (e.g., attestor rotation) until holders are actually locked out. Because `spender_attested` assets are an explicit, supported feature (used to gate spending to attested/whitelisted addresses, e.g. for compliance), this code path is reachable in normal operation, not a corner case.

### Recommendation
- Pin the attestor list used to validate a spend to the list that was current when the holder acquired the coins (or otherwise grandfather previously-attested holders), rather than always using the most-recently-published list.
- Alternatively/additionally, introduce a timelock or grace period (delay before a new attestor list becomes effective) so holders have advance notice and an opportunity to move funds before losing attested status.
- Document clearly, at asset-definition time, that `spender_attested` gives the definer unilateral, uncollateralized power to retroactively freeze any holder's ability to spend, so wallets/users can make informed risk decisions before acquiring such assets.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and an initial attestor list `[X]` via the `asset` message (handled in `writer.js` `case "asset":`).
2. Attestor `X` attests holder `H`'s address via an `attestation` message; `H` receives/holds units of asset `A`.
3. `H` can freely transfer `A` today because `filterAttestedAddresses` finds `H` in `attestations` under attestor `X` (`storage.js:1959-1974`).
4. `D` posts a new single-authored `asset_attestors` message for asset `A` replacing the list with `[Y]` (a different attestor who has never attested `H`). This passes `validateAttestorListUpdate` since `D` is still `definer_address` and the new list is non-empty/sorted/valid (`validation.js:2829-2864`).
5. Once this unit stabilizes, `storage.readAsset` resolves `[Y]` as the current attestor list for all future asset reads (`storage.js:1898-1946`).
6. `H` attempts to spend/transfer their existing holdings of `A`. `validatePayment` computes `arrAttestedAddresses` against `[Y]` only; since `H` was never attested by `Y`, the check `objAsset.arrAttestedAddresses.length === 0` (or `indexOf(issuer_address) === -1` for reissue) fails, and the unit is rejected with "none of the authors is attested" (`validation.js:2115-2122`).
7. `H`'s balance of asset `A` is now permanently unspendable unless `D` chooses to restore attestation — a definer-triggered, indefinite DoS/freeze on already-issued funds.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
