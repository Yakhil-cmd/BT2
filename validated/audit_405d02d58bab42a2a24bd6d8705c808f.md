### Title
Owner/full_name decoupling in webhook signature verification lets a forged `pull_request` payload write labels onto a different repository's `PullRequest` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify against using `repository.owner.login`, while every `pull_request` handler (including `LabelCapturingHandler`) resolves the actual `Repository`/`Stack` to mutate using `repository.full_name` independently. Because these two payload fields are never cross-checked against each other, and because `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected organization has no `webhook_secret` configured, an attacker who can get a payload verified under a no-secret organization can still target any other tracked repository by full_name, causing `LabelCapturingHandler` to persist attacker-chosen data onto that unrelated stack's `PullRequest`.

### Finding Description
The broken binding is:
`org_used_for_signature_check = params.dig('repository','owner','login')` should equal `owner_of(params.dig('repository','full_name'))` — the org whose secret authenticates the request must be the org that owns the repository the handler subsequently mutates.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` purely from `repository.owner.login` [1](#0-0)  and uses it to pick the GitHub App config: `Shipit.github(organization: repository_owner)` then calls `verify_webhook_signature` [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's config has no `webhook_secret` set: `return true unless webhook_secret` [3](#0-2) . This means any payload claiming to originate from a no-secret-configured org passes verification with an arbitrary/absent signature.
3. Once verification passes, `LabelCapturingHandler#repository` resolves the *actual* repository to mutate from a completely different, attacker-controlled field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) , and `Repository.from_github_repo_name` simply splits `full_name` on `/` to find the record by owner/name [5](#0-4) . Nothing re-checks that this owner matches `repository_owner` used in step 1.
4. `capture_labels` then persists attacker-supplied label names onto the resolved victim stack's existing `PullRequest` record: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [6](#0-5) .
5. Those persisted labels are later surfaced as uppercased shell-environment variables via `ReviewStack#env`, which merges `pull_request.labels` into the stack's environment: `labels[label_name.upcase] = "true"` [7](#0-6) , exposing attacker-controlled values to whatever deploy/provisioning commands read that environment.

Exploit request: attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature` arbitrary/blank, and a JSON body where `repository.owner.login` = a Shipit-configured organization that has no `webhook_secret` set, and `repository.full_name` = `"victim-org/victim-repo"` (an existing, unrelated, tracked repository with an active review stack and PR). `action` = `"labeled"`, with attacker-chosen `pull_request.labels[].name` values.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered, not payload consistency [8](#0-7) ; the `ExplicitParameters` schema on `LabelCapturingHandler` only enforces types/presence of fields, not cross-field consistency between `repository.owner.login` (used upstream for auth) and `repository.full_name` (used for the DB lookup) [9](#0-8) ; there is no code anywhere that compares the two.

Note: the claim in the question that this can flip `blocked?` via `blocking_statuses` was investigated but not conclusively confirmed within the traced files — `ReviewStack#env` only injects label-derived variables into the stack's shell environment used by deploy/provisioning commands; I did not find code wiring these env vars into `Stack#blocked?`/`blocking_statuses` gating logic directly. That amplification path remains unverified/speculative; the confirmed, demonstrable impact is the cross-repository write into another tenant's `PullRequest#labels`.

### Impact Explanation
An attacker authenticated under a misconfigured (secret-less) organization can cause writes to the `PullRequest` record of an entirely unrelated, victim-owned Shipit stack, and can inject attacker-chosen values into that stack's `ReviewStack#env`, which is consumed by deploy/provisioning `Command`/`PTY.spawn` executions for that victim stack [7](#0-6) . This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." The action is repeatable against any repository tracked by Shipit, as long as the attacker can get a request routed through a no-secret-configured org. Blast radius spans all repositories/orgs hosted on the same Shipit instance, not just the org used to bypass signature verification.

### Likelihood Explanation
This requires a specific server-side misconfiguration: at least one organization in `Shipit.github_apps`/config must be defined without a `webhook_secret` (so `verify_webhook_signature` trivially returns `true`) [3](#0-2) . Given that precondition, the attacker cost is a single unauthenticated HTTP POST with no valid signature required, and the attack is fully repeatable/scriptable against any tracked repository by simply varying `repository.full_name`. Without a no-secret org configured, the attacker would need the real `webhook_secret` for the org named in `repository.owner.login`, which unprivileged attackers do not have.

### Recommendation
After resolving the target `Repository`/`Stack` from `repository.full_name`, verify that its `owner` matches the organization (`repository_owner`) whose secret was used to authenticate the request, and reject the webhook (422) on mismatch. Additionally, treat organizations configured without a `webhook_secret` as unverifiable/untrusted — either require `webhook_secret` for every configured organization or refuse to process `pull_request`/mutating events for organizations lacking one.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.github_apps` (or stub `Shipit.github`) with two orgs: `"no-secret-org"` (no `webhook_secret`) and `"victim-org"` (with a real `webhook_secret`).
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")` with an existing `ReviewStack` and associated `Shipit::PullRequest` (`labels: []`), and a `Stack` with `blocking_statuses` configured.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or a garbage one), and body:
   ```json
   {
     "action": "labeled",
     "number": <pr_number>,
     "pull_request": { ..., "labels": [{"name": "MALICIOUS_FLAG"}] },
     "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
4. Assert response is `200 OK` (not `422`), i.e. `verify_signature` (equality: `repository_owner == "no-secret-org"`) passed trivially.
5. Reload `victim_pull_request` and assert `victim_pull_request.labels == ["MALICIOUS_FLAG"]`, proving the record owned by `"victim-org"` (never authenticated) was mutated by a request authenticated as `"no-secret-org"`.
6. Assert `review_stack.env["MALICIOUS_FLAG"] == "true"`, demonstrating the cross-tenant environment injection.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
