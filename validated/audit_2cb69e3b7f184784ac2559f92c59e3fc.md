### Title
`liquidate` accepts caller-supplied Pyth price updates with no deviation/outlier check, letting a liquidator push the shared oracle price to seize another user's collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate` (and `collateral-add`, `collateral-remove`, `borrow`, `collateral-remove-redeem`, `liquidate-redeem`) accepts an optional `price-feeds` parameter that is written into the shared Pyth storage contract via `write-feeds`/`write-feed` before the borrower's health and liquidation amounts are computed in the same transaction. The only validations applied to the pushed price are staleness and a fixed confidence-interval check; there is no bound on how far the new price can move relative to the recently observed price (no outlier/median check), exactly the gap identified in the referenced BadgerDAO report for `WrappedIbbtc`/`WrappedIbbtcEth`.

### Finding Description
`liquidate` first calls `write-feeds` on the attacker-supplied `price-feeds` argument, which forwards each buffer to `pyth-oracle-v4.verify-and-update-price-feeds`, updating the globally shared `pyth-storage-v4` price used by every borrower in the market: [1](#0-0) 

`write-feed`/`write-feeds` do not add any market-side validation beyond forwarding the update, and any legitimate but stale-within-window Pyth publish (e.g. a brief price spike/crash that Pyth itself published seconds earlier) can be selected and injected by the caller: [2](#0-1) 

Once written, the same transaction immediately calls `price-resolve`, which validates only `oracle-price-legal` (price > 0) and `oracle-timestamp-fresh` (staleness + monotonicity) - there is no bound on the price's deviation from a recent median/EMA, matching the exact gap flagged in the external report: [3](#0-2) 

The confidence check in `resolve-pyth`/`check-confidence` only bounds the Pyth confidence interval relative to the *same* published price point (default 10% of price), it does not bound how far that price point itself has moved from the previously effective price: [4](#0-3) 

The freshly-written price is then used directly to compute the borrower's collateral/debt USD values, health/LTV, and the amount of collateral seized, all in `liquidate`: [5](#0-4) 

Attacker (liquidator) and victim (borrower) are different, unprivileged principals; the shared state is the Pyth price feed (`pyth-storage-v4`) and the market's `last-update` monotonic timestamp map, both read by every account's position evaluation. A liquidator who is otherwise unable to profitably liquidate a borrower at the last settled price can supply a genuinely signed but momentarily extreme Pyth update (any valid VAA within the staleness window and confidence bound) to push the collateral price down / debt price up just before evaluating the borrower's LTV, causing a position that was healthy moments before to appear liquidatable, or increasing the liquidation penalty/collateral seized beyond what a smoothed price would justify. Because there is no per-update movement cap, this genuinely-signed-but-extreme value passes both checks in `price-resolve` and is accepted as-is.

### Impact Explanation
This lets one unprivileged party (a liquidator) unilaterally move the shared price oracle that another unprivileged party's (borrower's) collateral is valued against, within the very transaction that seizes that collateral. The result is over-liquidation / premature liquidation driven by a transient price update the borrower had no opportunity to react to, i.e. theft of the borrower's collateral beyond what a manipulation-resistant price would allow - this is a direct-theft-of-user-funds scenario (Critical), matching the confirmed BadgerDAO issue's impact class of unmitigated price-outlier exposure.

### Likelihood Explanation
Likelihood is bounded by the practical difficulty of obtaining a legitimately-signed Pyth update that is both extreme enough to flip health status and still within `max-staleness`/confidence bounds, and by the same-block borrow/liquidate guard (`ERR-LIQUIDATION-BORROW-SAME-BLOCK`) which prevents flash-loan-in-block self setups. However, during real market volatility (which Pyth publishes frequently), a liquidator monitoring the Pyth network can pick up a genuine transient tick and race it into `liquidate` before the borrower or a keeper can react/repay, making exploitation plausible during ordinary volatility rather than requiring an artificial attack.

### Recommendation
Add a bounded-deviation/outlier check in `price-resolve` (or specifically before using a caller-supplied `price-feeds` update in `liquidate`/`borrow`/`collateral-*`): track a short rolling window of recently accepted prices per feed and reject/flag updates whose deviation from the median of that window exceeds a configurable threshold, similar to the mitigation recommended in the referenced report. Alternatively, disallow caller-supplied `price-feeds` specifically inside `liquidate`, forcing liquidations to use only prices that have already settled via a separate, non-atomic update path (as is already done for `liquidate-multi`, which passes `none` for `price-feeds`).

### Proof of Concept
1. Borrower has a position with LTV below `ltv-liq-partial` at the last settled Pyth price (healthy).
2. Pyth network publishes a transient price tick (still within `max-staleness` and within the 10% confidence bound) that momentarily depresses the borrower's collateral price or raises the debt price.
3. Attacker calls `market.liquidate(borrower, collateral-ft, debt-ft, debt-amount, min-collateral-expected, none, (some (list <pyth-update-buffer>)))`.
4. `write-feeds` pushes this transient price into `pyth-storage-v4`; `price-resolve` accepts it (positive price, fresh timestamp, confidence within bound) since no outlier/median check exists.
5. `current-ltv` computed against the transient price now exceeds `ltv-liq-partial`, `health-check` passes, and the attacker seizes `coll-actual` collateral from the borrower at a penalty, even though the borrower was healthy moments earlier and will be healthy again once Pyth's next tick reverts. (define-private (write-feed (feed (buff 8192)) (status (response bool uint)))
  (match status
    success-status
      (match (contract-call? 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-oracle-v4 verify-and-update-price-feeds
          feed
          {
            pyth-storage-contract: 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4,
            pyth-decoder-contract: 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-pnau-decoder-v3,
            wormhole-core-contract: 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.wormhole-core-v4,
          }
        )
        update-success (ok true)
        update-failed ERR-PRICE-FEED-UPDATE-FAILED)
    error-status status
  )
)

;; Process optional list of price feed updates
;; If list is provided, folds over it and updates all feeds
;; If list is none, does nothing (allows for backward compatibility)
(define-private (write-feeds (feeds (optional (list 3 (buff 8192)))))
  (match feeds
    entries (fold write-feed entries (ok true))
    (ok true)))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-public (liquidate
                (borrower principal)
                (collateral-ft <ft-trait>)
                (debt-ft <ft-trait>)
                (debt-amount uint)
                (min-collateral-expected uint)
                (collateral-receiver (optional principal))
                (price-feeds (optional (list 3 (buff 8192)))))
  (let (
    (feeds-check (try! (write-feeds price-feeds)))
    (liquidator contract-caller)
    (position (try! (get-liquidation-position borrower)))
    (pos-full (try! (get-full-position borrower)))
    (mask (get mask position))
    (group (try! (get-egroup mask)))

    (coll-address (contract-of collateral-ft))
    (debt-address (contract-of debt-ft))
    (coll-asset (try! (get-asset coll-address)))
    (debt-asset (try! (get-asset debt-address)))
    (coll-aid (get id coll-asset))
    (debt-aid (get id debt-asset))

    ;; accrue FIRST - populates cache for zToken price resolution
    (u-debt (accrue-user-debts (get debt pos-full)))
    (u-coll (accrue-user-collateral (get collateral pos-full)))

    ;; NOW safe to resolve prices (cache is populated)
    (assets (get-assets mask))
    (notional-valued-assets (get-notional-evaluation { position: position, assets: assets }))
    (total-collateral-usd (get collateral notional-valued-assets))
    (total-debt-usd (get debt notional-valued-assets))

    ;; LTC thresholds, liq params, health
    (ltv-liq-partial (buff-to-uint-be (get LTV-LIQ-PARTIAL group)))
    (ltv-liq-full (buff-to-uint-be (get LTV-LIQ-FULL group)))
    (liq-penalty-min (buff-to-uint-be (get LIQ-PENALTY-MIN group)))
    (liq-penalty-max (buff-to-uint-be (get LIQ-PENALTY-MAX group)))
    (curve-exponent (buff-to-uint-be (get LIQ-CURVE-EXP group)))

    ;; LTV = (debt x 10,000) / collateral
    ;; handle edge case: If collateral = 0, return max LTV (BPS) or 0 if debt also 0
    (current-ltv   (if (is-eq total-collateral-usd u0)
                       (if (is-eq total-debt-usd u0) u0 BPS)
                       (mul-div-down total-debt-usd BPS total-collateral-usd)))
    
    ;; Oracle frontrunning protection: prevent same-block liquidation
    ;; This blocks flash-loan based attacks where user borrows + gets liquidated in same block
    (last-borrow-block (get last-borrow-block position))
    (same-block-check (asserts! (not (is-eq last-borrow-block stacks-block-height)) ERR-LIQUIDATION-BORROW-SAME-BLOCK))

    ;; health check (FAIL-FAST) 
    ;; Check position is liquidatable BEFORE calling calc-liq-factor
    (health-check  (asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY))

    ;; liquidation parameters (graduated liquidation calculation)
    (liq-params (calc-liquidation-params 
                  current-ltv ltv-liq-partial ltv-liq-full
                  liq-penalty-min liq-penalty-max 
                  curve-exponent total-debt-usd))
    (liq-pct-scaled (get liq-pct-scaled liq-params))
    (liq-penalty (get liq-penalty liq-params))
    (max-debt-usd (get max-debt-usd liq-params))

    ;; debt processing
    (debt-info (process-debt-asset debt-amount debt-aid max-debt-usd assets))
    (debt-actual-usd (get debt-actual-usd debt-info))
    (debt-actual (get debt-actual debt-info))
    (debt-price (get debt-price debt-info))
    (debt-decimals (get debt-decimals debt-info))

                                         user-coll-balance assets coll-asset))

    (coll-price (get coll-price coll-info))
