### Title
Webhook signature verification is bound to the wrong identity, letting an attacker forge push/status/check_suite events for repositories outside the authenticating organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives the *organization used to authenticate the request* from the same untrusted JSON body it is about to verify, and that organization is never re-checked against the *repository the event handler subsequently writes to*. This breaks the binding: `organization authenticated == repository written`.

### Finding Description
`verify_signature` picks the `GithubApp` (and therefore the HMAC secret) to check against using a value taken straight out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` — fully attacker-controlled content of the raw POST body, read *before* the signature has been validated.

`GithubApp#verify_webhook_signature` intentionally no-ops when the selected organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile every event handler determines *which repository/stack to act on* independently, by re-reading `repository.full_name` from that same unauthenticated body: [4](#0-3) 

`PushHandler` and `StatusHandler` use that value (via `stacks`/`Repository.from_github_repo_name`) to trigger real side effects — `sync_github` and commit `Status` creation: [5](#0-4) [6](#0-5) 

Nothing ties `repository_owner` (used to select the verifying `GithubApp`) to `repository.full_name` (used to select the repository actually mutated). Because sample/legitimate Shipit configs support an organization entry with `webhook_secret: nil` (seen in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets.test.json`), any org onboarded to a multi-org Shipit instance without a webhook secret configured makes `verify_webhook_signature` return `true` unconditionally for that org — while the JSON body's `repository.full_name` can name any other repository tracked by the instance.

### Impact Explanation
An attacker who knows (or guesses) that some organization on the shared Shipit instance has no `webhook_secret` set can send an unsigned/arbitrarily-signed POST to `/github/webhooks` with:
- `repository.owner.login` (or `organization.login`) = the org with no secret (satisfies `verify_signature`, since `verify_webhook_signature` short-circuits to `true`)
- `repository.full_name` = any other tracked repo/stack in the instance (the actual target)

This lets the attacker:
- Force `GithubSyncJob` on an arbitrary stack via `PushHandler`.
- Forge a commit `Status` (`state`, `target_url`, `context`) via `StatusHandler` for an arbitrary commit SHA, which can satisfy `ci.require` checks that gate deploys, leading to an unauthorized deploy.

This crosses a credential/organization boundary without requiring any Shipit session, API token, or knowledge of a real `webhook_secret` — only the absence of one on some org in the shared instance.

### Likelihood Explanation
Requires no credentials, no repository write access, and no valid HMAC secret — only that at least one organization configured in the Shipit deployment has an empty `webhook_secret` (a state explicitly supported by the code path and present in the shipped sample configs). Multi-tenant/multi-org Shipit installs where onboarding of a new org precedes webhook-secret configuration are a realistic operational scenario.

### Recommendation
- After successfully verifying the signature for `repository_owner`'s `GithubApp`, cross-check that the `repository.full_name`'s owner matches `repository_owner` (or otherwise scope handler processing to repositories owned by the authenticated organization) before dispatching to handlers.
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank in a shared, multi-organization instance; require an explicit "unauthenticated webhooks intentionally allowed" opt-in per organization, not an implicit bypass.

### Proof of Concept
1. Shipit instance is configured with two orgs: `weak-org` (no `webhook_secret` set) and `victim-org` (repo `victim-org/prod-app`, tracked stack `victim-org/prod-app/production`).
2. Attacker sends:
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "sha": "<target-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "victim-org/prod-app", "owner": { "login": "weak-org" } }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature`.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` and creates a forged "success" status for `victim-org`'s commit, potentially satisfying `shipit.yml`'s `ci.require` gate and enabling deployment of that commit — without ever touching `weak-org`'s repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
