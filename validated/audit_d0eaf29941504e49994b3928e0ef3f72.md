### Title
Private-Payment Counterparty Can Be Tricked by Sender Double-Spending an Unstable Private Asset Transfer After Signaling Acceptance - (File: indivisible_asset.js, divisible_asset.js, network.js, validation.js)

### Summary
Similar to the NFV report, where a vault's underlying state can still be manipulated by the seller after the buyer has evaluated it but before the NFT sale is atomically finalized, `ocore`'s private-payment (private asset) protocol lets a recipient treat a payment as "accepted" while the underlying spend is still unstable and can later be invalidated by a double-spend performed by the very sender who handed it over. A counterparty relying on `ifAccepted`/`ifOk` as a signal that a private-asset transfer is final can hand over consideration (goods, fiat, another asset) for a transfer that the payer can still nullify.

### Finding Description
Private asset payments (divisible and indivisible) are exchanged directly between peers over device/network messages, not by broadcasting the full DAG unit contents. When a chain of private elements is received, it is validated and, if it passes, the callback fires `ifAccepted`/`ifOk` even when the transfer is not yet stable:

- `indivisible_asset.js` `validatePrivatePayment` returns `callbacks.ifOk(bStable, input_address)` where `bStable` can be `false` [1](#0-0) , and this propagates to `validateAndSavePrivatePaymentChain`, which persists `is_unique = objPrivateElement.bStable ? 1 : null; // unstable still have chances to become nonserial therefore nonunique` [2](#0-1) .
- The same pattern exists for divisible private assets in `divisible_asset.js`, where `is_unique` is likewise left `null` for unstable inputs, explicitly noting they "still have chances to become nonserial" [3](#0-2) .
- The network layer surfaces this straight to the application/wallet as a positive acceptance: `network.js`'s `handleOnlinePrivatePayment` calls `callbacks.ifAccepted(unit)` as soon as `privatePayment.validateAndSavePrivatePaymentChain` succeeds, with no distinction communicated to the caller about `bStable` [4](#0-3) .
- `wallet.js`'s `handlePrivatePaymentChains` treats this the same way: once `ifAccepted` fires it marks the chain `assocValidatedByKey[key] = true` and eventually calls `callbacks.ifOk()`, again with no exposed stability guarantee to the consumer of the API [5](#0-4) .

The root enabler is `validation.js`'s double-spend handling: an unstable input can still be double-spent, and the validator's own comment states inputs of a private asset used from an unstable output are provisionally accepted and later "ununique[d]" if a conflicting spend appears (`checkInputDoubleSpend`/`checkForDoublespends`, marking `is_unique=NULL` for conflicting/losing entries) [6](#0-5) . `initPrivatePaymentValidationState` itself documents that "it's ok if the unit is not stable yet" [7](#0-6) .

Because private asset transfers are shared off-DAG (peer-to-peer device messages) rather than broadcast, a payer (the "seller" analog to the NFV case) retains full DAG-level control over the source output until it is buried under stable, `sequence='good'` units. Nothing structurally prevents the payer from:
1. Sending the private element chain to the counterparty (who validates it and treats it as accepted/received), then
2. Composing and posting a conflicting unit that spends the very same source output to a different address before the original unit becomes stable, causing the originally shared chain's input to be marked non-serial (`is_unique=NULL`, eventually `sequence != 'good'`) once resolved.

This is the direct analog of "the state of the vault can change during the sale": the recipient's belief that they now own value is contingent on unstable DAG state the sender still controls, and the protocol communicates "accepted" well before that state is irreversible.

### Impact Explanation
If a wallet, marketplace, or any application built on `ocore` interprets `ifAccepted`/`ifOk` from `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` as final receipt of value (a natural read of the API, since it is literally named "Accepted"/"Ok"), a malicious payer can:
- Hand over a chain apparently transferring a private asset (e.g., a payment for goods/services or a swap counter-leg), inducing the counterparty to release their side of the exchange.
- Then double-spend the source output to reclaim the funds for themselves before the transaction stabilizes.

This is a concrete double-spend against a counterparty who released value based on an as-yet-non-final private-payment chain, resulting in unauthorized fund loss for the honest party — the same "buyer pays, doesn't get what they thought" outcome as the NFV report, but expressed in `ocore`'s asset-transfer/private-payment machinery rather than an ERC721 marketplace.

### Likelihood Explanation
Any unprivileged asset issuer/holder acting as payer in a private payment can attempt this; it requires no special privileges, only control of the funding address and normal ability to post conflicting units before finality (a well-known but narrow window, matching the referenced audit note OD-9 about time-delay windows being insufficient). The likelihood is moderated by the fact that many careful counterparties may wait for stability, but the API's naming (`ifAccepted`/`ifOk`) and lack of an explicit "final" vs "provisional" surface at the network/wallet layer make premature reliance a realistic integration mistake.

### Recommendation
- Surface the `bStable`/finality status explicitly and prominently through `ifAccepted`/`ifOk` callbacks in `network.js` and `wallet.js`, rather than only threading it internally through `divisible_asset.js`/`indivisible_asset.js`.
- Document clearly (analogous to the NFV recommendation) that private-payment recipients, exchanges, and any application composing conditional exchanges around private asset transfers must wait for MC stability (and `sequence==='good'`) before treating a private asset transfer as irrevocable, and should not release counter-value on the basis of `ifAccepted` alone.
- Consider adding a distinct callback name/state (e.g., `ifAcceptedButUnstable`) so downstream integrators cannot conflate "syntactically valid and saved" with "final and unspendable elsewhere."

### Proof of Concept
1. Payer A creates a private asset (indivisible or divisible) output O and sends payer/asset info off-chain to counterparty B along with the private element chain referencing O, expecting consideration (e.g., another asset transfer) in return.
2. B calls into `handleOnlinePrivatePayment` (network.js:2376) / `handlePrivatePaymentChains` (wallet.js), which invokes `privatePayment.validateAndSavePrivatePaymentChain` → `indivisible_asset.js`/`divisible_asset.js` `validateAndSavePrivatePaymentChain`. Validation succeeds while the source unit for O is not yet stable, so `ifOk`/`ifAccepted` fires with `bStable=false`, `is_unique=null` recorded for the corresponding `inputs` row.
3. B, seeing "accepted", releases consideration to A.
4. Before O's containing unit stabilizes, A posts a second, conflicting unit spending the same source output to A's own address.
5. `validation.js` `checkInputDoubleSpend`/`checkForDoublespends` marks the losing side's `is_unique=NULL`; once the DAG resolves finality, the original chain B received turns out to be non-serial/void, while A has already been paid — B ends up with nothing corresponding to what they paid for.
