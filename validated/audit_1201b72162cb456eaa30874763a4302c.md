### Title
Cross-repository Status forgery in `StatusHandler#process` poisons `Shipit::Stack#ci_enabled?` cache and writes forged statuses onto a victim stack's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by SHA (`Commit.where(sha: params.sha)`) with no check that the webhook's `repository.full_name` matches the repository owning that commit's stack. Any GitHub `status` event whose `sha` collides with a commit SHA already recorded on a victim stack (trivially achieved by forking the victim repo, since forks retain identical commit SHAs) will create a real `Shipit::Status` row on the victim stack's commit and immediately flip `ci_enabled?` to `true` via `Status#enable_ci_on_stack`.

### Finding Description
The broken binding: `commit.stack_id == repository_that_authenticated_the_webhook.stacks.map(&:id)` should hold for every `Status` created from a webhook, but the code only enforces `commit.sha == params.sha`.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) verifies the HMAC signature using the GitHub App config selected by `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates that "some repo owned by `repository_owner`" sent this event — it does **not** authenticate which specific commit/stack the event may touch.
2. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `StatusHandler`.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ignores `payload.dig('repository','full_name')` entirely, even though the base `Webhooks::Handlers::Handler` class already provides a `stacks`/`repository_name` scoping helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that other handlers are expected to use — `StatusHandler` does not use it.
4. `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` (`app/models/shipit/commit.rb:165-169`) creates the `Status` using `commit.stack_id` (the **victim's** stack), not any stack derived from the incoming webhook's repository.
5. `Status` model's `after_create :enable_ci_on_stack` (`app/models/shipit/status.rb:18,38-40`) immediately calls `commit.stack.enable_ci!`, which does `Rails.cache.write(ci_enabled_cache_key, true)` (`app/models/shipit/stack.rb:579-581`) — poisoning the cache to `true` synchronously, without even needing a subsequent `ci_enabled?` read to trigger the `commits.joins(:statuses).any?` fetch block (`app/models/shipit/stack.rb:573-577`).

Exploit flow: attacker forks the victim's public repository (identical commit SHAs preserved), owns that fork, and installs/configures a GitHub webhook/App on it so it emits a legitimately-signed `status` event to Shipit's `/webhooks` endpoint for a SHA that is shared with the victim's fork history. GitHub computes a valid signature for the attacker's own repo/org, so `verify_signature` passes. `StatusHandler` then matches the SHA against **any** `Commit` row across the entire database, including the victim's tracked commit, and writes a `Shipit::Status` scoped to the victim's `stack_id`.

Existing guards do not stop this: `verify_signature` authenticates the sending organization, not the object being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; no model validation ties a `Status`'s `stack_id` to the repository that originated the webhook.

### Impact Explanation
A forged event from a repository the attacker owns causes a write (`Shipit::Status`) against a completely different, victim-owned stack's commit, and immediately mutates stack-wide state (`ci_enabled?` cache) that gates CI-enforcement UI/logic for that victim stack. This matches "a payload for one repository mutating another's stack, commit ... " (Critical). It is repeatable against any victim stack whose commit history overlaps (via forks/shared history) with a repository the attacker controls, and does not require any Shipit credentials, session, or API token — only ordinary GitHub repo ownership plus the ability to configure/trigger a webhook from that repo.

### Likelihood Explanation
Preconditions: victim stack has a commit whose SHA also exists in a repository the attacker owns (easily satisfied via forking, a common and low-cost action), and the attacker's owning organization must be one Shipit already recognizes for signature verification (i.e., the attacker's org/repo must be onboarded to the same Shipit GitHub App/org configuration used for signing). Given that, the attack costs nothing beyond forking a public repo and posting a commit status via the standard GitHub API/UI on their own fork — no Shipit secrets, tokens, or elevated GitHub permissions are required. This is fully repeatable per victim stack/commit pair.

### Recommendation
In `StatusHandler#process` (and analogous handlers, e.g. check-run handler), scope commit lookup to the repository that authenticated the webhook, mirroring the `stacks`/`repository_name` helper already defined on the base `Handler` class, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `commit.stack.repository.full_name == payload['repository']['full_name']` before any `Status` is created.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub calls):
```ruby
test "#process does not create a status for a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to victim_stack
  Rails.cache.clear
  assert_equal false, victim_stack.ci_enabled? # baseline: commits.joins(:statuses).any? == false

  forged_payload = ExplicitParameters::Parameters.new(
    sha: victim_commit.sha,
    state: 'success',
    context: 'ci/attacker',
    repository: { full_name: 'attacker/unrelated-fork' } # different repo than victim_stack.github_repo_name
  )

  Shipit::Webhooks::Handlers::StatusHandler.new(forged_payload).process

  refute victim_commit.reload.statuses.exists?, "status must not be attached to a commit from a different repo"
  Rails.cache.clear
  assert_equal false, victim_stack.reload.ci_enabled?, "ci_enabled? must remain false without genuine CI activity"
end
```
Before the fix, this test fails: `victim_commit.statuses` gains a row and `victim_stack.ci_enabled?` becomes `true` and is cached, because `Commit.where(sha: params.sha)` matches the victim's commit purely by SHA, with `repository.full_name` never checked.
