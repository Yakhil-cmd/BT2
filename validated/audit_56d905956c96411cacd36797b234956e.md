### Title
Unvalidated swap-route venues can execute attacker contracts under the caller’s signed authorization tree and steal unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
High severity. `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept caller-supplied opaque `swap` bytes and forward them to the configured router after authenticating the caller. [1](#0-0)  The controller only constrains its own router input transfer and measured balances; it does not decode the route or restrict which venue contracts the route invokes. [2](#0-1)  Because route payloads can name arbitrary pool/token addresses and the router has no venue allowlist, an attacker-supplied route can place malicious contract code inside a victim-signed controller transaction. [3](#0-2) 

### Finding Description
The vulnerable pattern is the SSRF analog: a user-controlled route reaches an attacker-controlled external contract during a privileged-looking protocol operation. `swap_collateral` authenticates `caller` and verifies account ownership or delegation before routing withdrawn collateral through `withdraw_and_swap_from_supply`. [4](#0-3)  `swap_tokens` then forwards the unmodified `swap` payload to `execute_strategy`; it checks only that the controller did not overspend and received positive `token_out`. [5](#0-4)  The controller’s own contract authorization is narrow—one exact `transfer(controller, router, amount_in)` with no nested authorization—but that bound does not constrain separate token calls initiated by route-selected code against the human caller’s authorization. [6](#0-5) 

A malicious venue can call `token.transfer(victim, attacker, amount)` for any unrelated token held by the victim. Simulation records that transfer as a child of the victim’s `swap_collateral` authorization, and enforcing mode executes it when the victim signs the prepared authorization tree. [7](#0-6)  The malicious venue can simultaneously return a legitimate-looking swap output, so the controller’s balance-delta and final risk checks pass.

### Impact Explanation
A successful route drains tokens outside the collateral being swapped, causing direct theft of user funds beyond the amount intentionally routed. The transaction can still deliver a valid output and leave the lending position healthy, so neither the route minimum nor the controller’s measured-output and solvency checks bound the stolen amount. [8](#0-7) [3](#0-2) 

### Likelihood Explanation
Exploitation requires an unprivileged attacker to cause a victim to submit attacker-constructed route bytes and sign a simulated authorization tree containing the malicious child transfer. This is feasible when route bytes are treated as opaque quote output or when wallet/auth displays obscure nested token transfers, but a victim who decodes the route and rejects unexpected authorization children prevents execution. [9](#0-8) 

### Recommendation
Add a governance-managed allowlist of executable venue contracts and make the router reject routes whose pool/token addresses are not approved for the requested adapter and pair. Prefer registry-derived venue addresses over payload-supplied addresses, and bind each venue to its expected ABI and token metadata before invocation. Until venues are constrained, clients must treat route bytes as executable code, decode every hop, simulate the exact transaction, and refuse any authorization tree containing children beyond the expected input pull.

### Proof of Concept
1. Victim owns a lending account with `USDC` collateral and also holds an unrelated `WALLET` token.
2. Attacker deploys a `RogueVenue` contract whose swap entrypoint calls `WALLET.transfer(victim, attacker, victim_balance)` and then sends enough `ETH` to the router for the swap to satisfy its declared output.
3. Attacker encodes a `swap` payload whose venue/pool address is `RogueVenue`, with `token_in = USDC`, `token_out = ETH`, and a normal-looking `min_out`.
4. Victim submits `swap_collateral(caller=victim, account_id, current=hub(USDC), amount, new=hub(ETH), swap=malicious_route)`.
5. Controller authenticates the victim, withdraws the collateral, invokes the configured router with the opaque route, and later observes positive measured `ETH` output. [10](#0-9) [11](#0-10) 
6. Simulation adds `WALLET.transfer(victim, attacker, victim_balance)` as a child of the victim’s controller authorization; if the victim signs that tree, the rogue venue steals the unrelated wallet tokens while the collateral swap succeeds. [12](#0-11)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();

    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");

    s.t.env.mock_all_auths_allowing_non_root_auth();

    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
