### Title
`Team.find_or_create_by!(github_id:)` in `MembershipHandler#find_or_create_team!` is not scoped to the verifying organization, allowing cross-organization team hijack that grants `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by the GitHub-global `github_id`, with no check that the record's stored `organization` matches the organization whose webhook signature was just verified. Because `find_or_create_by!`'s block only runs on creation, an existing `Team` row (e.g. one of the teams referenced by `Shipit.github_teams`, used for application authorization) is returned unchanged whenever any verified organization sends a `membership` event whose `team.id` matches that row's `github_id`, and `add_member` is then invoked on it unconditionally.

### Finding Description
The broken binding: `Team#organization` recorded for a team **should equal** the organization that GitHub reports as actually owning that `github_id`. Instead: [1](#0-0) 

`process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The `organization:` assignment only executes inside the `create` block — it never runs for a record that already exists. So if a `Team` row with `github_id == params.team.id` already exists (created earlier for a *different* organization, e.g. one of the teams pre-populated via `Shipit.github_teams`/`Team.find_or_create_by_handle`), the lookup returns that pre-existing row untouched, and `team.add_member(member)` (where `member` comes straight from attacker-controlled `params.member.login`) creates a `Membership` for that team.

Path/guards checked:
- `WebhooksController#verify_signature` picks the `GitHubApp`/secret to verify against based on `repository_owner`, which for a `membership` event falls back to `params.dig('organization','login')` [2](#0-1) . This only proves the payload was signed by *some* configured organization's webhook secret — it does not bind `params.team.id` to that organization.
- `ExplicitParameters` schema only requires types (`Integer`/`String`), performing no cross-check between `team.id` and `organization.login` [3](#0-2) .
- Authorization uses exactly this un-scoped `Team` table: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [4](#0-3) , and `Shipit.github_teams` resolves configured team handles (e.g. `shopify/developers`) to `Team` rows once [5](#0-4) . Any `Membership` added to that specific `Team` row — regardless of which organization's webhook created it — flips `authorized?` to true for that user.
- `User.find_or_create_by_login!` will happily reuse an existing `User` row for a login the attacker already controls (e.g. their own previously-registered, unprivileged Shipit account) without any further check [6](#0-5) .

Exploit flow: an unprivileged attacker who has a Shipit account (created via a normal, unauthorized OAuth login when `Shipit.authentication_disabled?` is false but before the team check, or via any prior interaction that creates a `User`) and who controls an organization that is legitimately configured as one of Shipit's (possibly multiple) trusted GitHub orgs, sends/triggers a `membership` `added` event where `organization.login` is their own org (so `verify_signature` passes using their own known webhook secret) but `team.id` equals the `github_id` of the privileged team referenced in `Shipit.github_teams` (e.g. `shopify/developers`) and `member.login` is the attacker's own GitHub login. `find_or_create_team!` finds the existing privileged `Team` row (organization stays `"shopify"`), `add_member` adds the attacker, and `User#authorized?` now returns true for them.

### Impact Explanation
This is an authorization bypass/escalation into `Shipit.github_teams` (matches the High-severity category "escalation into `Shipit.github_teams` authorization"). Any user with an unprivileged Shipit account can grant themselves (or any other Shipit user by login) membership in a team that gates access to the entire application (`force_github_authentication`), without ever actually being a GitHub member of that team. It's repeatable per attacker-controlled org for any `github_id` they can determine belongs to a privileged `Team` row, and affects the whole instance (not scoped to one repository), since `Shipit.github_teams` gates access application-wide.

### Likelihood Explanation
Requires: (1) the Shipit deployment to configure more than one trusted GitHub organization (multi-org support exists per `docs/setup.md` and `Shipit.github(organization:)`), one of which the attacker legitimately administers and thus knows that org's own `webhook_secret`; (2) the attacker knowing/guessing the numeric `github_id` of the target privileged `Team` (not trivially public, but discoverable via GitHub API responses the attacker may have access to, or via brute force over a bounded range); (3) the attacker already possessing (or being able to create) a Shipit `User` record. For a single-organization deployment where the attacker has no relationship to the sole trusted org, this is not exploitable, since they cannot produce a valid signature. Given the stated threat model excludes attacker possession of `webhook_secret`, the practical likelihood is confined to the multi-tenant configuration case described above; the code defect itself is real and directly reachable once that precondition holds.

### Recommendation
Scope the lookup to the verifying organization instead of `github_id` alone, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally validate/update `team.organization` even on the found branch, rejecting or logging when an existing team's stored `organization` disagrees with the organization that verified the webhook.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition, no live GitHub)
test ":membership does not let another org hijack an existing team by colliding github_id" do
  team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: e.g. 999
  original_org = team.organization

  @request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature already verified for 'attacker-org'

  assert_difference -> { Membership.count }, 1 do
    post :create, as: :json, body: {
      action: 'added',
      team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
      organization: { login: 'attacker-org' },
      member: { login: 'attacker' }
    }.to_json
    assert_response :ok
  end

  team.reload
  assert_equal original_org, team.organization # organization field silently preserved
  assert team.members.exists?(login: 'attacker') # attacker membership created under the privileged team
end
```
This demonstrates: `team.organization` stays `"shopify"` (binding claims to hold) while a `Membership` for `attacker` is created against that same `Team` id, granting them `Shipit.github_teams` authorization.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
