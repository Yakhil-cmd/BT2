### Title
Webhook signature check binds the wrong organization to the repository being acted on, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an incoming payload against based on `repository.owner.login` (or `organization.login`), while the downstream `Webhooks::Handlers::Handler` (and every concrete handler) resolves the target `Stack`/`Repository` from a *different* field of the same payload: `repository.full_name`. Because both fields live inside the same signed request body and are both attacker-controlled once the attacker knows *any* configured organization's `webhook_secret`, the signature check does not actually bind "the organization whose secret validated the request" to "the repository the handler subsequently writes to."

### Finding Description
The signature verification flow is: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON payload (`params.dig('repository', 'owner', 'login')`) and used to pick which multi-tenant GitHub App config (and therefore which `webhook_secret`) to validate the HMAC against via `Shipit.github(organization: repository_owner)`. This is a multi-org lookup (each org keyed to its own `webhook_secret`): [3](#0-2) 

The HMAC itself is computed over the whole raw body: [4](#0-3) 

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same parsed payload to handlers. Every handler resolves the acted-upon repository from `repository.full_name`, a field entirely independent of `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `webhook_secret` is a per-organization value that must be disclosed to whoever configures a GitHub webhook against Shipit for that org's own repositories, an actor with legitimate ability to add a webhook for **Org A** (an unprivileged actor with respect to any other org hosted on the same multi-tenant Shipit instance) knows Org A's `webhook_secret`. Nothing stops that actor from crafting an arbitrary raw POST body where `repository.owner.login = "org-a"` (so `verify_signature` selects Org A's app/secret and the HMAC computed with the known secret validates) while `repository.full_name = "org-b/some-repo"` (so the handler acts on Org B's stack). The equality the code should enforce but does not is:

`organization whose webhook_secret authenticated the request == owner of repository.full_name acted on by the handler`

This is exactly the "organization that authenticated versus the repository that is written" trust-binding class called out in the task rules.

### Impact Explanation
This lets a user who only controls webhook configuration for one organization on a shared Shipit instance forge webhook events (`push`, `pull_request`, `status`, `membership`, etc.) for any other organization/repository hosted on the same instance, without ever having credentials or write access there. Depending on the event, this can:
- Trigger `GithubSyncJob` for an unrelated stack via a forged `push` event (`params.after`/`expected_head_sha` are attacker-supplied), feeding an attacker-chosen `expected_head_sha` into a victim stack's sync/deploy pipeline.
- Create/archive Review Stacks or manipulate `PullRequest` records for a foreign repository via the `pull_request` handlers.
- Create/delete `Team`/`Membership` records tied to an arbitrary GitHub organization.

Given Shipit's deploy pipeline treats synced commits/statuses as trusted inputs for deploy eligibility, this is a cross-tenant authentication-binding break that can cascade into unauthorized state changes on a stack the attacker does not own. This aligns with the "unauthorized deploy" / cross-repository-write impact class defined in scope.

### Likelihood Explanation
Requires the attacker to already control webhook configuration for at least one organization onboarded to the same multi-tenant Shipit deployment (i.e., they legitimately know that org's `webhook_secret`) — this is a realistic scenario for any Shipit instance shared across multiple business units/teams/orgs, each independently configuring their own GitHub webhooks pointed at the shared instance. No GitHub App private key, `ApiClient` token, or Shipit session is needed — only knowledge of one org's webhook secret, which is inherently disclosed to whoever sets up that org's webhook.

### Recommendation
After signature verification, require that `repository.owner.login` (or `organization.login`, whichever determined `repository_owner`) matches the owner segment of `repository.full_name` used by the handlers, and reject the request (422) on mismatch. Alternatively, derive the org used for both secret selection and repository resolution from a single, consistently-verified field, and have `Handler#repository_name` re-derive/validate against the same organization value used in `verify_signature` rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Shipit instance is configured with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (multi-tenant `secrets.github` config, see `github_app_config` in `lib/shipit.rb`).
2. Attacker legitimately manages a GitHub webhook for `org-a`'s repository pointing at the shared Shipit instance, and thus knows `org-a`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(org_a_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s GitHub App, and the HMAC validates successfully against the attacker-supplied body.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `GithubSyncJob` for `org-b`'s stack with the attacker-controlled `expected_head_sha`, even though the attacker never had any credential or webhook relationship with `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
