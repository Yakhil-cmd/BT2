### Title
Stack-scoped ApiClient tokens can read build status of any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` created with a `stack_id` is intended to be authorized only for that single stack (e.g., a CCMenu URL token generated by `CCMenuUrlController` at [5](#0-4) ). However, `Api::CCMenuController` resolves the target stack independently of that scope, allowing the token to read the CI/deploy status of any stack in the installation.

### Finding Description
Every other API controller resolves the requested stack through `BaseController#stack`, which delegates to `#stacks`, and `#stacks` restricts the result set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped: [2](#0-1) .

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [6](#0-5) 

The only permission gate applied is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!(operation, scope)`. That method only verifies that the string `"read:stack"` is present in the client's `permissions` array — it never consults `stack_id`: [4](#0-3) .

The route accepts an arbitrary `stack_id` segment for any stack in the install: [1](#0-0) .

The binding that should hold is: `stack a token authorizes == stack it touches` (i.e., `current_api_client.stack_id == requested stack.id` whenever `stack_id?` is true). For `CCMenuController#show`, this equality is never checked — any valid `read:stack` token, no matter which stack it was minted for, can be used to fetch `GET /api/stacks/*stack_id/ccmenu` for a completely unrelated stack.

### Impact Explanation
The response rendered by `shipit/ccmenu/project.xml.builder` discloses `lastBuildStatus`, `activity` (building/sleeping), `lastBuildTime`, `lastBuildLabel` (deploy id), and `webUrl` for the target stack: [7](#0-6) . This is a cross-stack disclosure of deploy/task state using a token that was only supposed to be authorized for one specific stack — matching the "unauthenticated read of stack state" class of impact for a party that has not been granted access to that stack.

### Likelihood Explanation
Every CCMenu token generated by the built-in `CCMenuUrlController` is stack-scoped (`permissions: %w[read:stack]`, bound via `stack_id`) and is commonly embedded in third-party CI dashboard tools (CCTray clients), which increases the chance such tokens circulate outside the originally intended stack's trust boundary. Exploitation requires only changing the `stack_id` segment of the URL; no additional privilege or secret is needed once a legitimate scoped token is obtained.

### Recommendation
Make `CCMenuController#stack` use the inherited, scope-aware `stack`/`stacks` helper from `BaseController` (i.e., remove the private override and rely on `stacks.from_param!(params[:stack_id])`), so a stack-scoped `ApiClient` can only ever resolve the stack it was issued for.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for stack `org/repo/production` via `CCMenuUrlController#fetch`, obtaining a token scoped to that stack with `read:stack` permission.
2. Send `GET /api/stacks/org/repo/production/ccmenu?token=<token>` — succeeds as expected.
3. Send `GET /api/stacks/other-org/other-repo/staging/ccmenu?token=<token>` using the same token.
4. Observe that the request succeeds (200 OK) and returns build/deploy status XML for `other-org/other-repo/staging`, a stack the token was never authorized to access, because `CCMenuController#stack` resolves via unscoped `Stack.from_param!` instead of the scoped `stacks` helper.
