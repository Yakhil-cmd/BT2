## Analog Found [1](#0-0) 

### Title
`reward_per_token_stored` can be permanently stalled via integer-division rounding while `last_update_block` keeps advancing - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards` computes reward accrual per token with a fixed-point scaling factor of only `4096` (`PRECISION_SCALING_FACTOR`), far lower than the `1e18`-style precision typically used in similar staking-rewards designs. When `reward_rate_per_block * elapsed_blocks * 4096 < total_tokens_staked`, the reward-per-token increment computed in `reward_per_token()` truncates to `0` due to integer division, yet `update_pool_rewards()` unconditionally advances `last_update_block` to the current block. Any staker can call the permissionless `harvest_rewards` extrinsic every single block to keep `elapsed_blocks == 1` forever, which — for pools with a reasonably large staked supply relative to the reward rate — causes `reward_per_token_stored` to never increase, permanently starving all stakers of rewards while pool time (and admin-visible "distribution period") keeps ticking away.

### Finding Description
`reward_per_token()` computes:
```
reward_per_token_stored + reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked
``` [2](#0-1) 

`PRECISION_SCALING_FACTOR` is a `u16` constant fixed at `4096` [1](#0-0) , which is dramatically lower precision than the `1e18` scaling used by comparable Synthetix-style staking-rewards contracts that this pallet's own doc comment says it is modeled after [3](#0-2) .

`update_pool_rewards()` is called on every `stake`, `unstake`, and `harvest_rewards` invocation via `update_pool_and_staker_rewards()`, and it unconditionally sets `last_update_block` to the current block regardless of whether `reward_per_token` actually increased:
```rust
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
``` [4](#0-3) 

This is the exact bug-class from the reported ERC20 staking finding: with an "arbitrarily small" elapsed interval and a relatively low `reward_rate_per_block` versus a large `total_tokens_staked`, the numerator `reward_rate_per_block * elapsed * PRECISION_SCALING_FACTOR` can be smaller than `total_tokens_staked`, causing the division to floor to `0`. Because `rewardable_blocks_elapsed` is bound by block granularity, `elapsed = 1` is the natural minimum any signed account can force just by calling any of `stake`/`unstake`/`harvest_rewards` in every block.

`harvest_rewards` is a fully permissionless, self-serviceable extrinsic — any staker can call it on their own account without special origin, and it internally invokes `update_pool_and_staker_rewards` -> `reward_per_token` -> `update_pool_rewards` on every call: [5](#0-4) 

Because `rewardable_blocks_elapsed` resets to 1 (or a similarly tiny value) on every call and `PRECISION_SCALING_FACTOR` is only `4096`, any pool where `reward_rate_per_block * 4096 < total_tokens_staked` will have its `reward_per_token_stored` permanently frozen once someone (attacker or a normal user acting frequently) calls `harvest_rewards` every block, while `last_update_block` keeps moving forward and consuming the pool's `expiry_block` window with zero payout.

### Impact Explanation
This directly parallels the "[H] Rewards accumulated can stay constant and often not increment" finding: the pool's advertised reward stream (`reward_rate_per_block`) is silently voided for the whole distribution duration for any pool with realistic token-supply/rate ratios (e.g., an 18-decimal asset with billions of total supply and a modest per-block reward rate). Since `expiry_block` cannot be extended past dilution loss and rewards already "spent" (time-wise) cannot be recovered, this is a real, unbacked loss of intended reward distribution to all pool stakers, not merely a Low-severity precision quirk — matching the High severity of the original report.

### Likelihood Explanation
No privileged role is required. Any staker in a pool (even one holding a tiny stake) can call the permissionless `harvest_rewards` (or `stake`/`unstake`) extrinsic once per block indefinitely at ordinary transaction-fee cost. Given `PRECISION_SCALING_FACTOR = 4096` is small, many realistic reward-rate/total-staked-supply configurations will satisfy the rounds-to-zero condition, making this both easy to trigger and likely to occur unintentionally in normal usage (any staker "farming" harvest calls, or automated bots interacting every block).

### Recommendation
Do not advance `last_update_block` when the computed reward-per-token increment rounds to zero, or track/accumulate remainder dust across updates so no rewards are silently lost to truncation (mirroring the original report's suggested mitigation). Additionally, consider raising `PRECISION_SCALING_FACTOR` substantially (e.g., to `1e18`-scale) to reduce the likelihood of rounding to zero for realistic pool configurations, and add a defensive check/test ensuring `reward_per_token_stored` cannot stagnate indefinitely while `total_tokens_staked` and `reward_rate_per_block` remain nonzero.

### Proof of Concept
Program/scope: `substrate/frame/asset-rewards` is part of the polkadot-sdk (Substrate FRAME) production pallet set within the scanned scope.

Failed guard: `update_pool_rewards()` has no check comparing old vs. new `reward_per_token_stored` before persisting `last_update_block` [4](#0-3) ; `reward_per_token()` performs a floor-division with no minimum-increment guard [6](#0-5) .

Deployment/PoC execution status: Not executed against a live network or test harness in this analysis; this is a static code-path analysis based on the pallet's existing unit tests (`substrate/frame/asset-rewards/src/tests.rs`) which explicitly acknowledge "off by 1 errors due to rounding" as expected behavior [7](#0-6) , but do not test the worst-case scenario of `total_tokens_staked` large enough relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR` to floor every single-block increment to zero. A concrete reproduction would require a FRAME integration test constructing a pool with e.g. `total_tokens_staked = 10^21`, `reward_rate_per_block < 10^21 / 4096`, and looping `harvest_rewards` once per block to confirm `reward_per_token_stored` never changes while `last_update_block` advances — this reproduction was not run as part of this analysis.

			// Transfer unclaimed rewards from the pool to the staker.

				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
