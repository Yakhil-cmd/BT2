### Title
Unchecked invariant between VAT-account filtering and VAT burn causes a validator-crashing panic - ([File: runtime/src/bank.rs])

### Summary
`Bank::maybe_burn_vat_from_staked_accounts` (`runtime/src/bank.rs:2648-2694`) debits a fixed `vat_to_burn_per_epoch` amount from every vote account returned by the epoch's VAT-filtered vote-account set, and does so with an `.expect()` rather than a graceful error path: [1](#0-0) 

The function's own doc comment states this call "must ONLY be called after the vote accounts have been filtered (`clone_and_filter_for_vat`) to the top `MAX_ALPENGLOW_VOTE_ACCOUNTS` that contain enough balance for admission" [2](#0-1) , i.e. the code relies on an invariant established by a *separate* computation (`clone_and_filter_for_vat` in `vote/src/vote_account.rs:212-271`) rather than re-validating the balance at the point of debit. This is structurally identical to the reported bug class: a value (the "amount to burn") is computed and applied against an account balance that was validated against a *different, potentially stale* snapshot/parameter, and the debit path uses an unchecked assumption (`voteFactor`/burn ratio there, VAT-eligibility filter here) instead of a checked, fail-soft operation.

### Finding Description
`compute_new_epoch_caches_and_rewards` (`runtime/src/bank.rs:1752-1813`) produces `filtered_distribution_vote_accounts` by calling `clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, self.minimum_vote_account_balance_for_vat())` [3](#0-2) . This filtered snapshot (or, in the fallback branch, a freshly-recomputed one from `get_top_epoch_stakes()`) is later fed into `update_epoch_stakes`, which calls `self.maybe_burn_vat_from_staked_accounts(&new_epoch_stakes)` [4](#0-3) .

Inside `maybe_burn_vat_from_staked_accounts`, for every vote account in that filtered set, the code re-loads the account live via `self.get_account(vote_pubkey).unwrap()` and then does:
```
account.lamports().checked_sub(vat_to_burn_per_epoch).expect(
    "Vote accounts should have already been filtered to contain enough balance for the VAT",
)
``` [5](#0-4) 

The correctness of this `.expect()` depends entirely on the assumption that the account's *live* balance at burn time is still `>= minimum_vote_account_balance_for_vat()` (rent-exempt minimum + `vat_to_burn_per_epoch()`, computed in `minimum_vote_account_balance_for_vat` at `runtime/src/bank.rs:6607-6620`). That threshold check is only performed inside `clone_and_filter_for_vat` (`vote/src/vote_account.rs:212-244`), a function that is *not* called again at the debit site — exactly the "mint-time check, burn-time debit, no re-validation" pattern in the reported bug. Any divergence between the balance/parameters used for filtering and the balance/parameters used for the actual burn (e.g. a vote-account withdrawal transaction landing between the snapshot used to build `filtered_distribution_vote_accounts` and the moment `maybe_burn_vat_from_staked_accounts` re-reads the account with `self.get_account`, or a slot-time/VAT-burn-amount parameter change taking effect between the two calls) turns the `.expect()` into a live panic instead of a `TransactionError`.

### Impact Explanation
Unlike the original report (a revert that just blocks a single claim), an `.expect()` panic inside `Bank` processing is executed identically by every validator processing that slot, because `maybe_burn_vat_from_staked_accounts` runs as part of deterministic, feature-gated epoch-boundary bank state transition (`update_epoch_stakes`), not as leader-only or RPC-only code. A panic there terminates the validator process on every node that processes the offending block, producing a cluster-wide halt rather than a rejected transaction — this satisfies the "transaction-triggered cluster halt" impact bar, and is strictly worse than the DoS in the original report.

### Likelihood Explanation
This is a low-to-moderate likelihood, timing-dependent bug. In the code as currently structured, `compute_new_epoch_caches_and_rewards` and `maybe_burn_vat_from_staked_accounts` are invoked within the same `Bank::new_from_parent`/`update_epoch_stakes` control flow for the newly-created epoch-boundary bank, and both read from the same `stakes_cache`/`get_account` snapshot at that instant, which should normally keep the filter and the burn consistent. I was not able to fully trace, within the remaining tool budget, whether any intermediate step (feature activation processing, the `prefiltered_distribution_vote_accounts = None` fallback re-filter path with `get_top_epoch_stakes()`, or partitioned/multi-slot reward distribution reusing a stale `NewEpochBundle`) can introduce a live gap where a vote-account withdrawal transaction (`VoteInstruction::Withdraw`, callable by any authorized withdrawer as an ordinary signed transaction) executes after the filtering snapshot is taken but before the corresponding burn read. This uncertainty should be resolved by a Devin session with full repo access before treating this as a confirmed, exploitable race rather than a defense-in-depth gap.

### Recommendation
Re-validate the balance at the exact point of debit instead of relying on the invariant established by an earlier, separately-computed filter: replace the `.expect()` in `maybe_burn_vat_from_staked_accounts` with a checked/saturating operation (e.g. `checked_sub` returning `None` → skip or clamp the burn for that account and log/metric it) so that any divergence between the VAT-eligibility snapshot and the live account state at burn time degrades gracefully instead of panicking the bank/validator process. Additionally, ensure `filtered_distribution_vote_accounts` and the account state read by `get_account` in the burn loop are guaranteed to originate from the same consistent snapshot (e.g., pass account data through explicitly rather than re-fetching via `get_account`) to eliminate the TOCTOU window entirely.

### Proof of Concept
1. On a cluster with `alpenglow` active, a validator's vote account is exactly at `minimum_vote_account_balance_for_vat()` and is selected into the top `MAX_ALPENGLOW_VOTE_ACCOUNTS` by `clone_and_filter_for_vat` for the upcoming epoch's `filtered_distribution_vote_accounts` snapshot (`vote/src/vote_account.rs:212-244`, `runtime/src/bank.rs:1783-1790`).
2. Before `maybe_burn_vat_from_staked_accounts` re-reads that same account via `self.get_account(vote_pubkey)` (`runtime/src/bank.rs:2665`), the vote account's authorized withdrawer submits a `Withdraw` transaction (`programs/vote/src/vote_state/mod.rs:1062-1128`) that drains the account below `vat_to_burn_per_epoch`, exploiting whatever gap exists between snapshot-time filtering and debit-time re-read (or a slot-params/feature change altering `vat_to_burn_per_epoch()` between the two calls).
3. `checked_sub(vat_to_burn_per_epoch)` on the now-insufficient balance returns `None`, and `.expect(...)` panics inside `maybe_burn_vat_from_staked_accounts`, which every validator executes deterministically while processing the same block, crashing the process cluster-wide.
