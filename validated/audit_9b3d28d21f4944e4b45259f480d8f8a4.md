### Title
Webhook signature verification is keyed to an unauthenticated payload field decoupled from the repository actually mutated by handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to verify the HMAC signature against using `repository_owner`, a value read directly out of the untrusted, unverified JSON body, *before* the signature has been checked. Every webhook `Handler` subclass, however, resolves the `Repository`/`Stack` to actually mutate using a *different* field from the same untrusted body: `payload.dig('repository', 'full_name')`. These two fields are never cryptographically bound together, so an attacker can pick which organization's secret is used for verification independently of which repository's stacks get acted upon.

### Finding Description
`verify_signature` computes the verification key as: [1](#0-0) [2](#0-1) 

`repository_owner` is taken straight from `params.dig('repository', 'owner', 'login')` (or `organization.login`) with no prior authentication. It is then used to fetch a `GitHubApp` config via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Signature verification itself is org-scoped and **short-circuits to `true` whenever that org's `webhook_secret` is blank**: [4](#0-3) 

Meanwhile, every `Shipit::Webhooks::Handlers::Handler` subclass finds the `Repository`/`Stack` to operate on using a *separate* field of the same untrusted body: [5](#0-4) 

and concrete handlers (e.g. `PullRequest::OpenedHandler`, `PullRequest::LabeledHandler`, `PullRequest::ClosedHandler`) all call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to look up the target repository, independent of `repository.owner.login`: [6](#0-5) [7](#0-6) 

**Broken binding:** `organization used to select the verification secret == organization/repository whose stacks are mutated`. Because `repository.owner.login` (verification key selector) and `repository.full_name` (mutation target) are independent, unverified fields inside the same JSON body, an attacker who knows any single Shipit-configured organization with no `webhook_secret` set (a supported, legal configuration per `docs/setup.md`'s optional `github.webhook_secret` field) can craft a payload where:
- `repository.owner.login` = the org with no secret configured → `verify_webhook_signature` returns `true` unconditionally, regardless of the (attacker-supplied, arbitrary/garbage) `X-Hub-Signature` header.
- `repository.full_name` = any *other*, fully-secured repository/organization actually tracked by that Shipit instance.

The request passes `verify_signature` and is dispatched to `Shipit::Webhooks.for_event(event)` handlers unmodified, which then act on the victim repository resolved from `repository.full_name`, e.g. archiving/unarchiving review stacks (`PullRequest::LabeledHandler#handle`), creating review stacks (`PullRequest::OpenedHandler#process`), or injecting fabricated commit statuses (`StatusHandler#process`, which is keyed only by `sha` with no repository binding at all).

### Impact Explanation
This lets an unprivileged, unauthenticated attacker forge GitHub webhook events for repositories/stacks they have no access to and no valid secret for, as long as any one org on the Shipit instance is configured without a `webhook_secret`. Concretely this allows: archiving/creating review stacks for arbitrary tracked repos, mutating pull-request state tracking, and forging commit statuses via `StatusHandler`, which are consumed to gate continuous-delivery/deploy decisions elsewhere in the app. This crosses an authentication boundary the design intends to enforce (signature-verified webhooks bound to the correct repository owner) and can influence deploy-gating state, aligning with the required "escalation" / "unauthorized" impact class, though it does not directly grant RCE, token exfiltration, or a merge/deploy execution by itself — it is a High-severity authentication/binding bypass rather than a Critical direct RCE.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment where at least one configured GitHub App organization intentionally or accidentally omits `webhook_secret` (the field is documented as optional in `docs/setup.md`). No credentials, tokens, or prior access are required — only knowledge that such an org exists (discoverable from public GitHub org names Shipit tracks) and the ability to craft an arbitrary JSON payload with mismatched `repository.owner.login` / `repository.full_name` fields.

### Recommendation
Bind the verification key deterministically to the same repository field the handlers use for mutation (`repository.full_name`'s owner), not `repository.owner.login`/`organization.login` read ad hoc. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for *any* configured organization — require a secret for every organization when running in multi-org mode, or reject/short-circuit unsigned requests for organizations without a secret instead of trusting them implicitly.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `orgA` (no `webhook_secret` set) and `orgB` (proper `webhook_secret`, with a real tracked stack `orgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: pull_request`, an arbitrary/garbage `X-Hub-Signature`, and body:
```json
{
  "action": "labeled",
  "number": 1,
  "pull_request": { "...": "..." },
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. `repository_owner` resolves to `orgA`; `Shipit.github(organization: "orgA").verify_webhook_signature` returns `true` unconditionally because `orgA` has no `webhook_secret` [8](#0-7) .
4. `PullRequest::LabeledHandler` resolves `repository` via `params.repository.full_name` = `"orgB/victim-repo"` [9](#0-8)  and archives/unarchives the corresponding review stack under `orgB`, despite the attacker never possessing `orgB`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
