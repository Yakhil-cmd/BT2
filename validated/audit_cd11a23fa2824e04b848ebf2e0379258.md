### Title
Raw, unsanitized repo entry names are written to the TTY/pager output - (File: pkg/cmd/repo/read-dir/read_dir.go)

### Summary
`writeTable` in `pkg/cmd/repo/read-dir/read_dir.go` writes `dirEntry.Name`—a value taken verbatim from the GraphQL `Tree.Entries[].Name` field—directly to the table printer, which in turn writes to `opts.IO.Out` behind an active pager (`opts.IO.StartPager()` at `read_dir.go:134`) [1](#0-0) . Unlike other untrusted-content sinks in this codebase, the name is a plain `string`, never wrapped in `iostreams.Untrusted`, so none of the ANSI/control-sequence sanitization that codebase already implements is applied before the bytes reach the terminal or pager.

### Finding Description
`fetchTree` in `pkg/cmd/repo/read-dir/http.go` populates `dirEntry.Name` directly from the GraphQL response with no sanitization: `Name: e.Name` [2](#0-1) . Git tree/blob entry names can contain arbitrary bytes other than NUL and `/`, including the ESC control character (U+001B) and other C0 control codes, so a crafted repo can create a file or directory whose name embeds ANSI/OSC escape sequences.

`writeTable` then feeds this raw value straight into the table printer: `tp.AddField(e.Name, tableprinter.WithColor(...))` [3](#0-2) . This happens in the TTY code path, which explicitly starts a pager before rendering: `opts.IO.StartPager()` ... `return writeTable(opts.IO, dir)` [4](#0-3) .

The codebase has an established mechanism for exactly this class of risk: `iostreams.Untrusted`, whose doc comment states it exists to wrap "HTTP response bodies, file contents fetched from a remote, anything that originates outside the CLI" so that `String()` neutralizes ANSI escape sequences before any `fmt` print path renders it [5](#0-4) . `dirEntry.Name` is precisely this kind of value (attacker-controlled, network-fetched), yet `read_dir.go`/`http.go` never wrap it in `Untrusted` or otherwise strip control bytes — it is a bare `string` field the whole way from the GraphQL decode to `tp.AddField`. This differs from the pattern used in other commands in this repo (e.g. `pkg/cmd/skills/list`, `pkg/cmd/skills/preview`, `pkg/cmd/run/view/logs.go`) that reference sanitization/`Untrusted` explicitly for remote-controlled text.

I was not able to fully inspect `internal/tableprinter/table_printer.go` to confirm it performs no independent escape-stripping of field content (tool budget exhausted), so it's possible the table printer itself does some sanitization; that would need to be checked before treating this as fully confirmed.

### Impact Explanation
If the table printer does not itself sanitize field text (unconfirmed due to tooling limits), a malicious file/directory name containing terminal escape sequences would reach the victim's pager (`less`, `more`, etc.) via `opts.IO.StartPager()`. Terminal escape sequences interpreted by the pager (which handles escapes differently from gh's own sanitized rendering) can be used for screen manipulation, hidden text, or spoofed prompts — potentially tricking a user into confirming a destructive action or revealing credentials, matching the "Terminal output/prompt spoofing" impact class cited in the question.

### Likelihood Explanation
An unprivileged GitHub user can create a public repo (or fork/branch) containing a file or directory whose name embeds control/escape bytes (git permits arbitrary bytes in tree entry names apart from NUL and `/`). Any victim running `gh repo read-dir` interactively (TTY) against that repo would trigger the vulnerable path automatically — no special privileges or victim actions beyond running the ordinary command are required. Feasibility depends on: (1) GitHub's GraphQL API not stripping/escaping control bytes in the `name` field, and (2) the table printer not independently sanitizing field values — both of which I could not fully verify with available tools.

### Recommendation
Wrap `dirEntry.Name` (and `Path`) in `iostreams.Untrusted` when populated in `fetchTree`, and render via `Untrusted.String()` (or otherwise sanitize with the existing `asciisanitizer`/`stripControl` helpers in `pkg/iostreams/untrusted.go`) before passing to `tp.AddField` in `writeTable`, consistent with the pattern already established elsewhere in the codebase for remote-origin text.

### Proof of Concept
Add a test in `pkg/cmd/repo/read-dir/read_dir_test.go` that stubs a GraphQL response with an entry name containing an ANSI escape sequence, e.g. `"name":"\u001b[31mFAKE PROMPT\u001b[0m"`, run `readDirRun` with `tty: true`, and assert that `stdout.String()` does **not** contain the raw `\x1b` byte / `\u001b` escape — i.e., assert the printed name is sanitized/stripped rather than passed through verbatim. Failing this assertion (the raw escape bytes appear in `stdout`) confirms the vulnerability.

// Untrusted wraps string content the application did not author: HTTP response
// bodies, file contents fetched from a remote, anything that originates outside
// the CLI. The raw bytes are unexported so the only ways out are the methods
// below.
//
// Untrusted satisfies fmt.Stringer, and String sanitizes, so any fmt print path
// (Fprint, Fprintf with %s or %v, Sprint) renders the content with ANSI escape
// sequences neutralized. The only way to reach the raw bytes is Raw, which is
// deliberately easy to grep for and is intended for non-terminal uses such as
// hashing, writing to a file, or piping to another program.
type Untrusted struct {
	raw string
}

// NewUntrusted labels a string as untrusted external content.
func NewUntrusted(s string) Untrusted {
	return Untrusted{raw: s}
}

// NewUntrustedBytes labels a byte slice as untrusted external content.
func NewUntrustedBytes(b []byte) Untrusted {
	return Untrusted{raw: string(b)}
}

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
