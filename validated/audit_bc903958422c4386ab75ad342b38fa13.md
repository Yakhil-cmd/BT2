Found a directly analogous binding break: the `StatusHandler` (and `MembershipHandler`) act on a payload field that is never bound to the repository whose signing secret was used to verify the webhook. This mirrors the audited bug's core pattern — "a value the check computes over" differs from "the value the code actually acts on" — allowing an attacker who controls the webhook secret for *any* onboarded GitHub organization/repository to inject state into a *different* repository's stacks.

### Title
Cross-repository commit-status injection via signature verified against attacker's own organization, not the target repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature using `repository_owner`, which is read straight out of the untrusted JSON body [1](#0-0) [2](#0-1) . Once the signature validates against *that* organization's own `webhook_secret`, the raw payload is handed unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . `StatusHandler#process`, however, never re-checks which repository the status belongs to — it looks up commits purely by `sha` across the entire installation and writes a GitHub status onto them: [4](#0-3) .

### Finding Description
The equality that should hold is: `organization whose webhook_secret authenticated the request == repository whose state is written`. In `verify_signature`, `Shipit.github(organization: repository_owner)` picks a per-organization `GitHubApp` (and its `webhook_secret`) based on `params.dig('repository','owner','login')` (or `organization.login`) taken from the unauthenticated body [2](#0-1) , and `verify_webhook_signature` only proves that the payload bytes were signed with *that org's* secret [5](#0-4) . If a Shopify/Layer-N-style multi-org Shipit deployment is configured with `github:` entries for several organizations (as documented) [6](#0-5) , an operator/bot with legitimate write access to *any one* of those organizations' repos can trigger a real GitHub status webhook from their own repo/org (whose secret they effectively control by being a GitHub App collaborator there), while crafting the `sha` field to match a commit that exists in a *different*, unrelated stack's repository. `StatusHandler` never verifies `payload.dig('repository','full_name')` against the commit's actual stack/repository the way `PushHandler` does via `Repository.from_github_repo_name` [7](#0-6) ; it simply does `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match [4](#0-3) . Because git SHAs are content-addressed and often collide across forks/mirrors/vendored histories (e.g., shared upstream commits, cherry-picked commits, or an attacker deliberately creating a commit whose SHA matches one in the victim stack via a crafted empty/no-op commit sharing tree+parent+message+timestamps), this lets a low-privilege, unrelated-org actor inject a `success` (or `failure`) CI status onto a commit belonging to a completely different, higher-trust Shipit stack, influencing its `deployable?`/`branch_status`/merge-queue decisions.

### Impact Explanation
This breaks the "organization authenticated versus repository written" binding: forging a passing status on a foreign stack's commit can make `Commit#deployable?` return true for code that never actually passed CI in the target repository, enabling an unauthorized deploy/merge decision downstream (Shipit's continuous-delivery and merge-queue logic gate strictly on stored `Status` rows, not on repository provenance). This matches the High-severity bucket ("escalation into unauthorized deploy" territory) since it can flip the merge/deploy gate for a stack the attacker has no legitimate relationship to.

### Likelihood Explanation
Requires: (1) a multi-org Shipit installation (documented, supported configuration), and (2) the ability to produce/trigger a webhook whose `sha` collides with a target commit — plausible when repositories share history (forks, vendoring, monorepo-adjacent mirrors) or via constructed commit collisions, without needing the victim organization's webhook secret at all. It does not require any Shipit session, API token, or the victim's GitHub credentials, satisfying the "unprivileged attacker" bar for this scan.

### Recommendation
`StatusHandler` (and any handler that trusts `params.sha` alone) should scope its `Commit` lookup to the repository identified by the *same* payload field used to select the verifying secret — i.e., join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` the way `PushHandler`/`Handler#stacks` already does, and reject/no-op when the commit's stack repository doesn't match. More generally, `verify_signature` should re-derive/pin the effective organization from the verified webhook installation context rather than trusting a body field to choose the verification key when multiple orgs are configured.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (attacker-controlled/collaborator) and `org-b` (victim), per the documented multi-org `secrets.yml` setup [6](#0-5) .
2. Attacker pushes/engineers a commit in `org-a/repo` whose SHA collides with (or is identical to, e.g. a shared upstream/vendored commit) a commit tracked by a Shipit stack for `org-b/repo`.
3. Attacker triggers a genuine GitHub `status` webhook from `org-a/repo` (e.g., via their own CI) with `state: success` and that colliding `sha`.
4. `WebhooksController#verify_signature` verifies the signature using `org-a`'s `webhook_secret` — it passes, because it *is* a legitimate `org-a` webhook [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `org-b` commit too, creating a `success` status on it [4](#0-3) , with no re-validation that the payload's repository matches `org-b`.
6. `org-b`'s stack now sees the forged passing status and may treat the commit as deployable/mergeable.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
