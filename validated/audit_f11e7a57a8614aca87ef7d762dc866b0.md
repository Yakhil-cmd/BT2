### Title
Fork PR author can hijack `PATH` via `machine.environment` in `shipit.yml`, causing arbitrary binary execution during `npm ci` and any other step - ([File: lib/shipit/command.rb])

### Summary
`DeploySpec#machine_env` returns the raw `machine.environment` map from the deploy-target branch's `shipit.yml` with no key filtering, and `TaskCommands#env`/`Command#unbundled_env` merge that map into the environment passed to `PTY.spawn` after the safe `PATH` has already been set, so a `PATH` entry in `machine.environment` silently overrides Shipit's constructed `PATH`. Since a `ReviewStack`'s branch is the fork PR's `head.ref`, and Shipit checks out and reads `shipit.yml` from that exact branch/commit, an unprivileged fork PR author fully controls the file that is merged into the subprocess environment for every task step, including `npm ci` and `dependencies`/`deploy` steps.

### Finding Description
The broken binding is: `Command#unbundled_env` is expected to always compute `PATH = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, but in fact:

```ruby
# lib/shipit/command.rb
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end
``` [1](#0-0) 

`@env.stringify_keys` is merged last, so any `'PATH'` key inside `@env` overrides the safe value.

`@env` is built by `Command.new(command_line, env:, chdir:)` in `TaskCommands#perform`/`#install_dependencies`, using the hash returned by `TaskCommands#env`:

```ruby
def env
  super
    .merge(@stack.env)
    .merge(... SHIPIT_USER, EMAIL, BUNDLE_PATH, SHIPIT_LINK, TASK_ID, IGNORED_SAFETIES, GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL ...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
``` [2](#0-1) 

`deploy_spec.machine_env` comes straight from the parsed YAML with no key allow-list or blocklist:

```ruby
def machine_env
  config('machine', 'environment') || {}
end
``` [3](#0-2) 

`deploy_spec` for a task is `DeploySpec::FileSystem.new(@task.working_directory, @stack)`, i.e., the checked-out working copy of the stack's own `branch` at the commit being deployed:

```ruby
def deploy_spec
  @deploy_spec ||= DeploySpec::FileSystem.new(@task.working_directory, @stack)
end
``` [4](#0-3) 

For a `ReviewStack`, that `branch` is set directly from the incoming pull_request webhook payload's `head.ref`, which is fully attacker-controlled (the PR author owns the fork branch and its `shipit.yml`):

```ruby
def stack_attributes
  {
    branch: params.pull_request.head.ref,
    environment:,
    ignore_ci: false,
    continuous_deployment: false
  }
end
``` [5](#0-4) 

There is no signature/permission check that filters the *content* of `machine.environment` — `EnvironmentVariables#permit` (used for `deploy_variables`/`rollback_variables` interpolation, not for `machine_env`) is never invoked on `machine_env`, and no code strips reserved keys like `PATH`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc. from `machine_env` before it is merged into the subprocess environment.

Exploit flow:
1. Attacker forks the tracked repository, opens a PR from a branch they control, with a `shipit.yml` at the repo root containing:
   ```yaml
   machine:
     environment:
       PATH: "/tmp/attacker-bin:$PATH"
   dependencies:
     override:
       - "npm ci"
   ```
   and places a malicious executable named `npm` at `/tmp/attacker-bin/npm` on... — actually the attacker cannot pre-place a file on the Shipit host filesystem directly, but they *can* have their `shipit.yml`'s earlier steps (or the repo's checked-out files, which they fully control since it's their own fork branch) write the malicious `npm` binary into the working directory during an earlier step, then set `PATH` to include that directory (e.g., `machine.directory`'s working copy) for a later step such as `npm ci`.
2. Once the review stack is created (assuming `provisioning_behavior` is `allow_all`, or after the attacker satisfies the label requirement on their own PR — a self-service action), Shipit clones the fork branch and runs `TaskCommands#perform`/`#install_dependencies`, spawning `npm ci` via `Command#start` → `PTY.spawn(unbundled_env, ...)`.
3. Because `unbundled_env` merges `@env` (containing attacker's `PATH`) after the safe default `PATH`, the bare command `npm` resolves through the attacker-controlled directory first, executing attacker code with the privileges of the Shipit deploy host process — arbitrary RCE.

### Impact Explanation
This is Remote Code Execution on the Shipit deploy host, matching the "Critical - RCE on the deploy host via `Command`/`PTY.spawn`" category. The attacker gains code execution as the Shipit worker process, which typically has GitHub App/deploy credentials (`GITHUB_TOKEN`), access to the git cache/working directories of all stacks on the host, and the ability to affect any subsequent deploy. This is repeatable per PR/per push to the fork branch (each new task run re-executes the poisoned `shipit.yml`), and if review stacks are enabled with `allow_all` provisioning, no repository maintainer approval is required to trigger it.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`repository.provisioning_behavior` allowing the PR to provision, e.g. `allow_all`, or the attacker adding their own label if `allow_with_label`). This is a common/documented configuration [6](#0-5) . No Shipit credentials, session, or API token are required — only the ability to open a PR against the tracked repo from a fork, which is available to any GitHub user for public repos. Cost is a single PR; the vulnerability is deterministic and does not depend on race conditions or timing.

### Recommendation
In `Command#unbundled_env`, do not allow `@env` to override `PATH` (and other security-sensitive variables like `LD_PRELOAD`, `LD_LIBRARY_PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, `IFS`): compute the safe `PATH` last, or explicitly delete `'PATH'` from `@env` before merging. Additionally, filter/deny listed keys in `DeploySpec#machine_env` (or `TaskCommands#env`) so that fork-controlled `shipit.yml` cannot set environment variables that affect binary resolution or interpreter behavior.

### Proof of Concept
```ruby
# test/unit/command_test.rb (new test)
test "#unbundled_env does not allow the task-provided env to override PATH" do
  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  command = Shipit::Command.new('npm', 'ci', chdir: Dir.tmpdir, env: { 'PATH' => '/tmp/attacker-bin:/usr/bin' })

  resulting_path = command.unbundled_env['PATH']

  # Binding under test: resulting_path must equal the Shipit-constructed safe_path,
  # not the attacker-supplied value.
  assert_equal safe_path, resulting_path
  refute_equal '/tmp/attacker-bin:/usr/bin', resulting_path
end
```
And at the integration level (`test/unit/deploy_commands_test.rb` style), simulate a `machine_env` containing `'PATH' => '/tmp/attacker-bin'` via the stubbed `@deploy_spec`, run `@commands.install_dependencies.first`, and assert `command.env['PATH']` (and ultimately `command.unbundled_env['PATH']`) still starts with `Shipit.shell_paths` rather than `/tmp/attacker-bin`. Currently, both assertions fail against the code shown above, confirming the divergence.
