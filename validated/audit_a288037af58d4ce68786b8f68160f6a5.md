### Title
Unhandled exception on race in `'definition template'` re-evaluation causes node crash - (File: definition.js)

### Summary
The HDF5 report describes a null-pointer dereference in `H5O__cache_chk_serialize` that occurs because the code assumes a cached chunk object is always present and dereferences it without a null check, crashing the process on a locally reachable path. The analogous bug class in ocore is an unguarded assumption ("this DB lookup will always return exactly one row") that is dereferenced/`throw`n without recovery inside `definition.js`'s `'definition template'` opcode handling, reachable by any address/asset that a user defines and any unit an unprivileged author can post referencing that address.

### Finding Description
`validateDefinition()` (used only during structural/complexity validation of a definition) checks the referenced `definition_template` unit and gracefully returns `cb("template not found or too many")` if the row count is not exactly 1: [1](#0-0) 

However, the *evaluation* path used every time signatures/authentifiers are actually checked — `validateAuthentifiers()`'s inner `evaluate()` — re-runs essentially the same query independently and, instead of returning an error to the callback, throws an uncaught `Error`: [2](#0-1) 

```js
case 'definition template':
    ...
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");   // <-- unguarded throw inside async DB callback
            ...
        }
    );
```

This throw happens inside an asynchronous SQLite/MySQL callback with no surrounding `try/catch` in this call path (`evaluate` here is a plain function, not wrapped like the caller in `signed_message.js` which does wrap `validateAuthentifiers` in `try/catch`, but ordinary unit validation via `validateAuthor()` → `Definition.validateAuthentifiers()` in `validation.js` does **not** wrap the call in `try/catch`): [3](#0-2) 

Because `validateAuthentifiers`'s `evaluate()` is invoked from deep inside `async.eachSeries`/`async.series` callback chains that are not exception-safe, a `throw` here escapes as an uncaught exception in the event loop, which by default behavior for Node.js processes not running with a global uncaught-exception handler around this call stack results in the process crashing (or, if caught by a top-level handler, aborts the currently open DB transaction/mutex-held validation flow, leaving state undefined) — this is the same class of “the code assumed a resource always exists and dereferences/uses it unconditionally” defect as `H5O__cache_chk_serialize`'s null-pointer dereference. The trigger condition ("not exactly 1 row") is reachable whenever:
1. The referenced `definition_template` unit's message becomes non-stable/non-`good`/is voided between the time `validateDefinition` (structural check) and `validateAuthentifiers`'s `evaluate` (actual signature verification) run for the *same* incoming unit, or
2. Two authors/units concurrently reference the same template unit while its stability point advances in `main_chain.js`, or the template-defining unit is later found to be non-serial ('good'→'bad'), changing the row's `sequence='good'` predicate between the two evaluations of the *same* signed unit (validateDefinition and validateAuthentifiers are two separate DB round-trips, not covered by a single atomic read).

### Impact Explanation
An uncaught exception thrown from inside a DB callback during unit validation is a process-crashing condition equivalent in effect to a null-pointer-dereference DoS: it halts the validating node's unit-processing pipeline entirely, matching the "network unable to confirm new units" / node-availability impact category in scope. Any node that validates a unit whose address definition uses `'definition template'` referencing a template unit whose stability/state changes between the two lookups can be crashed, and because address definitions are attached to ordinary payment/AA-trigger units, this is reachable by any unprivileged unit poster who defines (or gets someone else to reuse) an address with a `'definition template'` clause.

### Likelihood Explanation
Likelihood is Medium: the race window between `validateDefinition`'s structural check and `validateAuthentifiers`'s evaluation check is narrow but real, since they are two independent, non-atomic SQL queries executed at different points in the validation pipeline (potentially even against different `last_ball_mci` if timing shifts main-chain stability advancement in between, or if a competing "final-bad" determination is applied to the template-defining unit concurrently). This does not require a malicious peer/hub — it only requires a normal user's address definition containing `'definition template'` and ordinary main-chain progression, satisfying the "unprivileged unit poster" reachability requirement in the rules.

### Recommendation
Replace the unguarded `throw Error("not 1 template")` in the `evaluate()` branch of `validateAuthentifiers` (definition.js line ~811-812) with a graceful failure through `cb2(false)`/`fatal_error` propagation consistent with how `validateDefinition`'s analogous branch handles the same condition (`cb("template not found or too many")`), and wrap the whole `evaluate()` call chain (or at minimum this DB callback) in a `try/catch` boundary so any unexpected zero/multiple-row result is treated as "authentication failed" rather than crashing the process. Ideally, make the template lookup deterministic/idempotent between the validation and evaluation phases (e.g., cache the resolved template payload from `validateDefinition` and reuse it in `evaluate` rather than re-querying).

### Proof of Concept
1. Register an address A whose definition includes `['definition template', ['TEMPLATE_UNIT', {param1: 'v'}]]`, where `TEMPLATE_UNIT` carries an `app='definition_template'` message.
2. Post a unit signed by address A (any payment/AA trigger) that requires authentifier verification through this branch.
3. Arrange (or wait) for the stability/sequence status of `TEMPLATE_UNIT`'s defining unit to change between the moment `validateDefinition` performs its "template found" check and the moment `validateAuthentifiers`'s `evaluate()` re-queries the same condition for the actual signature check (e.g., a concurrent main-chain stabilization batch changes `is_stable`/`sequence` for that unit, or the template row count becomes 0 or >1 due to a race in stability advancement).
4. When `evaluate()`'s query returns `rows.length !== 1`, the uncaught `throw Error("not 1 template")` propagates out of the async DB callback, crashing/aborting the validating node process — full reproduction requires timing control over main-chain stabilization concurrency, which is not independently confirmed in this review; the root-cause code path (unguarded `throw` vs. graceful `cb` in the parallel `validateDefinition` check) is directly confirmed by the cited lines.
