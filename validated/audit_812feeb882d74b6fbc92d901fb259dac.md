**Step 1: `PostInsertBlock` is called for ALL blocks, including `SideStatTy`**

In `insertChain`, after `writeBlockWithState` resolves the canonical status, the `switch` on `writeResult.Status` handles events differently for `CanonStatTy` vs `SideStatTy` — but `PostInsertBlock` is invoked unconditionally for every block in the loop, after the switch: [1](#0-0) 

There is no guard like `if writeResult.Status == CanonStatTy` before the `PostInsertBlock` call.

**Step 2: `PostInsertBlock` unconditionally overwrites `currentState`** [2](#0-1) 

It calls `g.Chain.StateAt(block.Header().Root)` — the root of whatever block was passed in — and unconditionally calls `g.setCurrentState(currentState)`. There is no check that the block is the canonical head.

**Step 3: `currentState` is used for nonce checks in `VerifyExecutable`** [3](#0-2) 

Both the approve-tx path (line 250) and the swap-only path (line 255) call `g.getCurrentStateNonce(...)` to validate that the tx nonce matches the current on-chain nonce. If `currentState` points to a side-chain state, these nonce values are wrong.

**Step 4: The side-chain scenario**

During sync or a reorg, `insertChain` can receive a batch like `[B1, B2]` where B1 is initially `SideStatTy` (lower total difficulty than the current head) and B2 triggers a reorg to `CanonStatTy`. After `PostInsertBlock(B1)`, `currentState` is set to B1's side-chain state. If any concurrent bundle evaluation happens in this window, it uses wrong nonces.

More critically: if a single side-chain block is inserted (e.g., a competing block at the same height with lower score), `PostInsertBlock` is called for it, `currentState` is permanently set to the side-chain state, and it stays there until the next canonical block arrives. [4](#0-3) 

**Step 5: Financial impact path**

A lend tx is generated by `GetLendTxGenerator` and prepended to the bundle. If the bundle is promoted based on a stale nonce from the side-chain state, the approve/swap txs will fail on-chain (nonce mismatch or wrong balance), but the lend tx (a plain KAIA transfer) may still execute, causing the CN lender to lose the lent KAIA with no repayment. Kaia uses Istanbul BFT, and the code itself notes this: [6](#0-5)

### Title
`PostInsertBlock` called for side-chain blocks corrupts `currentState` in gasless module, enabling lend-tx issuance against stale nonces — (`kaiax/gasless/impl/execution.go`)

### Summary
`GaslessModule.PostInsertBlock` unconditionally sets `currentState` to the state at the inserted block's root. Because `blockchain.insertChain` calls `PostInsertBlock` for every block regardless of canonical status (`CanonStatTy` vs `SideStatTy`), a side-chain block insertion permanently corrupts `currentState` until the next canonical block arrives. Nonce checks in `VerifyExecutable` then use wrong state, potentially causing the gasless module to promote bundles whose approve/swap txs will fail, while the lend tx executes and the CN lender loses KAIA.

### Finding Description
`blockchain/blockchain.go` `insertChain` calls `module.PostInsertBlock(block)` after the `switch writeResult.Status` block, with no guard on canonical status. `GaslessModule.PostInsertBlock` calls `g.Chain.StateAt(block.Header().Root)` and `g.setCurrentState(currentState)` unconditionally. A side-chain block (status `SideStatTy`) thus replaces `currentState` with a non-canonical state. `VerifyExecutable` reads `getCurrentStateNonce` from this corrupted state for both the approve-tx path and the swap-only path, producing wrong nonce comparisons.

### Impact Explanation
The CN lender node issues a lend tx (plain KAIA transfer) as the first tx in a gasless bundle. If the bundle is assembled using a stale nonce from a side-chain state, the approve/swap txs fail on-chain, but the lend tx may still be included and executed, causing the lender to lose the lent KAIA with no repayment from the swap.

### Likelihood Explanation
Kaia's IBFT consensus makes reorgs rare in normal operation, but the downloader/fetcher path (P2P, permissionless) can insert side-chain blocks during sync or when receiving competing blocks. The window of corruption persists until the next canonical block's `PostInsertBlock` call corrects `currentState`.

### Recommendation
In `PostInsertBlock`, compare the inserted block's hash against `g.Chain.CurrentBlock().Hash()` before calling `setCurrentState`. Only update `currentState` when the block is the canonical head:

```go
func (g *GaslessModule) PostInsertBlock(block *types.Block) error {
    if block.Hash() != g.Chain.CurrentBlock().Hash() {
        return nil // skip side-chain blocks
    }
    currentState, err := g.Chain.StateAt(block.Header().Root)
    if err != nil {
        return err
    }
    g.setCurrentState(currentState)
    return g.updateAddresses(block.Header())
}
```

### Proof of Concept
1. Set up a node with the gasless module enabled.
2. Insert a side-chain block (lower total difficulty than current head) via `InsertChain`.
3. Observe that `PostInsertBlock` is called for the side-chain block and `currentState` is updated to the side-chain state.
4. Call `VerifyExecutable` with a gasless bundle whose nonces are valid on the canonical chain but not on the side-chain.
5. Observe that the bundle is incorrectly rejected or accepted based on the wrong nonce, and that a lend tx is issued for a bundle that will fail on the canonical chain.

func (g *GaslessModule) GetLendTxGenerator(approveTxOrNil, swapTx *types.Transaction) *builder.TxOrGen {
	var src []byte
	if approveTxOrNil != nil {
		src = append(src, approveTxOrNil.Hash().Bytes()...)
	}
	src = append(src, swapTx.Hash().Bytes()...)
	bundleHash := crypto.Keccak256Hash(src)

	gen := func(nonce uint64) (*types.Transaction, error) {
		var (
			chainId = g.InitOpts.ChainConfig.ChainID
			signer  = types.LatestSignerForChainID(chainId)
			key     = g.InitOpts.NodeKey
		)

		to, err := types.Sender(signer, swapTx)
		if err != nil {
			return nil, err
		}

		tx, err := types.NewTransactionWithMap(types.TxTypeEthereumDynamicFee, map[types.TxValueKeyType]interface{}{
			types.TxValueKeyNonce:      nonce,
			types.TxValueKeyTo:         &to,
			types.TxValueKeyAmount:     lendAmount(approveTxOrNil, swapTx),
			types.TxValueKeyData:       common.Hex2Bytes("0x"),
			types.TxValueKeyGasLimit:   params.TxGas,
			types.TxValueKeyGasFeeCap:  swapTx.GasFeeCap(),
			types.TxValueKeyGasTipCap:  swapTx.GasTipCap(),
			types.TxValueKeyAccessList: types.AccessList{},
			types.TxValueKeyChainID:    chainId,
		})
		if err != nil {
			return nil, err
		}

		err = tx.Sign(signer, key)
		return tx, err
	}

	return builder.NewTxOrGenFromGen(gen, bundleHash)
}
