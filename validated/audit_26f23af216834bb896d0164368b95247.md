### Title
Forged cross-repo `Commit` status is fully trusted by `Commit#deployable?`, allowing unauthorized deploy-gate bypass - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely `Commit.where(sha: params.sha)` with no check that `params.sha`'s repository matches the webhook's authenticated repository/organization, so any attacker who owns a signed org (or a fork sharing a commit sha) can write an attacker-chosen `state`/`context` `Status` row onto a victim's commit. That forged row is persisted with the victim commit's own `stack_id` and is then consumed unmodified by `Commit#status`, `Commit#success?`, and `Commit#deployable?` with no provenance check, so it can flip a victim stack's deploy gate to "deployable" for a commit that never actually passed CI in the victim's own pipeline.

### Finding Description
Binding claimed: `deployable? == true` should require `status.owning_repository == stack.repository` (i.e., every `Status` row backing `Commit#deployable?` must have been written by a webhook whose signature was verified for the victim's own org/repo). Actual code:

- `StatusHandler#process` looks up commits solely by sha, globally: [1](#0-0) . There is no comparison between `payload.dig('repository','full_name')` and `commit.stack.repository`.
- `verify_signature` in `WebhooksController` only checks that the payload was signed by *some* org derived from the payload's own `repository.owner.login`/`organization.login` — i.e., it authenticates "this payload came from the org named in the payload," not "this payload is authorized to mutate this specific commit/stack": [2](#0-1)  and [3](#0-2) . An attacker owning their own org can produce a validly-signed status payload for a `sha` that happens to also exist in a victim's repo's commit table (shared/guessed via public fork lineage), and the signature check passes because it only validates against the attacker's own org.
- `Commit#create_status_from_github!` writes the forged status using the **victim commit's own** `stack_id` (not the attacker's), because it calls `statuses.replicate_from_github!(stack_id, github_status)` on the already-resolved victim `Commit` instance: [4](#0-3) . This makes the forged row indistinguishable from a legitimate one — there is no field recording which webhook/org produced it.
- Downstream, `Commit#deployable?` and `Commit#status` consume all `Status` rows for the commit with zero provenance filtering: [5](#0-4)  and [6](#0-5) . `Status::Group` only filters by `context` (hidden/required/blocking), never by origin: [7](#0-6)  and [8](#0-7) .
- `Stack#deployable?` and the deploy controller's `require_ci` gate ultimately trust `Commit#deployable?`: [9](#0-8) , and the API tests confirm `require_ci: true` deploy requests are rejected/accepted purely based on `Commit#deployable?`: [10](#0-9) .

No existing guard (`verify_signature`, `ExplicitParameters` schema on `StatusHandler`, `Status::Group`/`Status::Common` context filters) checks that the status's origin repository matches the commit's own stack/repository. The equality the binding requires (`status.provenance_repo == stack.repository`) is never evaluated anywhere in this path.

### Impact Explanation
An attacker who owns any GitHub org connected to Shipit (or any repo whose webhooks reach the instance) can, for a commit sha that also exists in a victim stack (e.g., via a shared history/fork or a guessed short sha collision), post a `status` webhook with `state: 'success'` and `context` matching the victim's required CI context. This flips `Commit#deployable?` to true for the victim's commit despite CI never having run/passed in the victim's own repository, letting an operator's subsequent (possibly `require_ci: true`-gated) deploy proceed and reach `Command#start` on the deploy host for code that was never validated — an unauthorized deploy of a cross-tenant/cross-repo nature. This matches the "Critical: a payload for one repository mutating another's stack/commit… unauthorized deploy" category.

### Likelihood Explanation
Preconditions match the prompt's stated preconditions (attacker owns a legitimately signed org/repo; a commit sha collision/sharing with the victim stack is required, e.g. via public fork lineage or a short/guessable sha). No Shipit secrets, sessions, or privileged roles are needed — only a self-owned, correctly-configured GitHub webhook. The main constraint is finding/producing a matching `sha` between attacker and victim, which is realistic for forked repositories that share commit history (forks retain identical shas for unmodified upstream commits). This is repeatable against any victim stack whose commits derive from a public/forkable repository.

### Recommendation
In `StatusHandler#process` (and the analogous `CheckSuiteHandler`/`RefreshCheckRunsJob` paths), scope commit lookup to the repository authenticated by the webhook, e.g. restrict to `Repository.from_github_repo_name(repository_name)&.stacks`'s commits (as `Handler#stacks` already does elsewhere) rather than a global `Commit.where(sha:)`, so a status can only be attached to a commit whose owning stack's repository matches the payload's authenticated repository/organization.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "cross-repo forged status must not satisfy deployable?" do
  victim_commit = shipit_commits(:cyclimse_first) # belongs to victim stack
  victim_commit.statuses.destroy_all
  refute victim_commit.reload.deployable?

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => victim_commit.stack.required_statuses.first || 'ci/required',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' } # attacker's own, correctly signed repo
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  # Binding under test: status.provenance_repo == stack.repository
  # left side: 'attacker/unrelated-repo' ; right side: victim_commit.stack.repository.full_name
  refute_equal 'attacker/unrelated-repo', victim_commit.stack.repository.full_name

  victim_commit.reload
  refute victim_commit.deployable?, "forged cross-repo status must not make commit deployable"
end
```
This asserts that a status forged via a payload whose `repository.full_name` differs from the victim stack's own repository must not be able to flip `deployable?` — with the current code, this assertion fails because `StatusHandler` never checks `repository.full_name` against the resolved commit's stack.
