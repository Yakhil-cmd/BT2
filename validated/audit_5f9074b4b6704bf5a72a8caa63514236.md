### Title
Uniswap-like Market Maker AA template mints first LP shares using only the base-currency balance, letting a depositor capture pre-existing paired-asset dust for free - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The ocore repository ships an official AA template, `uniswap_like_market_maker.oscript`, demonstrating how to build a constant-product liquidity pool as an Autonomous Agent. Its "initial deposit" branch mints the first LP shares (`mm_asset`) using only the AA's base-currency (`bytes`) balance, while ignoring any pre-existing balance of the paired asset (`$asset`) that may already sit at the AA's address. This mirrors the root cause of the Thetanuts vault exploit: minting shares against zero prior supply while the contract/AA already holds real collateral, letting the depositor who triggers minting appropriate that pre-existing collateral when they subsequently withdraw.

### Finding Description
In the "invest in MM" case: [1](#0-0) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
```

`$asset_balance` and `$bytes_balance` are the AA's balances *before* the current trigger's payment is applied. The "initial deposit" branch fires as soon as **either** balance is zero. If `$bytes_balance` is zero (no bytes ever received before) but `$asset_balance` is non-zero (because someone previously sent the paired `$asset` token directly to the AA address as a plain, unmatched payment - a normal, unprivileged coin transfer to any Obyte address), the branch still treats this as the very first deposit and sets:

```
$issue_amount = balance[base];
```

i.e., it prices the newly minted `mm_asset` shares using only the just-deposited base amount, completely disregarding the `$asset` value already held by the AA. `var['mm_asset_outstanding']` is then set to that issue amount via the state update at line 62.

Because an AA address is an ordinary address, any unprivileged unit poster can pre-fund it with a small amount of `$asset` (e.g. dust from a bounced/failed prior interaction, or intentional seed liquidity sent before the "invest" trigger is ever used) without matching any `case`. The first party to actually call the "invest" case with `base > 1e5` and any `asset > 0` becomes the sole holder of all `mm_asset` shares valued only against the bytes they sent, yet the AA's real balance also contains the pre-existing `$asset` dust.

On divesting: [2](#0-1) 

```
$investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
...
{address: "{trigger.address}", amount: "{ round($investor_share * balance[$asset]) }"}
...
{address: "{trigger.address}", amount: "{ round($investor_share * balance[base]) }"}
```

The sole shareholder's `$investor_share` equals 1 (they own 100% of `mm_asset_outstanding`), so `balance[$asset]` - which includes the pre-existing dust never priced into `mm_asset_outstanding` - is paid out in full to them, in addition to their own bytes deposit.

### Impact Explanation
Any account that can send a plain (unmatched) payment of the paired asset to the AA's address before the pool's first real "invest" call can later trigger the "invest" then "divest" pattern to drain that pre-existing asset balance without having paid for it, at the expense of the pool's actual liquidity or of whoever donated the dust. This is a direct AA-fund-loss primitive reachable purely through unprivileged trigger units - no privileged role, sync manipulation, or peer compromise is needed. Any project deploying this exact ocore-documented template inherits the vulnerability.

### Likelihood Explanation
The attack requires only two ordinary triggers (an "invest" trigger and a "divest" trigger) sent by any address, plus one plain payment of the paired asset sent beforehand. All conditions are on the attacker's own controlled inputs (`trigger.output[[asset=base]]`, `trigger.output[[asset=$asset]]`) and can be satisfied deterministically, making exploitation straightforward whenever the pool's paired-asset balance can accumulate dust before the first genuine liquidity deposit (e.g., failed prior swap attempts, bounced messages that still deliver coin outputs, or intentional pre-funding by the pool operator).

### Recommendation
When detecting the "initial deposit" condition, price the minted `mm_asset` shares against the *combined* value of both balances (or require both `$asset_balance` and `$bytes_balance` to be exactly zero, and separately account for/refund any pre-existing balances before minting), e.g.:
```
if ($asset_balance == 0 AND $bytes_balance == 0){
    $issue_amount = balance[base];
}
```
and additionally handle the case where one of the balances is non-zero (there is unclaimed dust) by either bouncing until an authorized "seed" trigger clears it, or by including its value in the share-pricing formula so the first depositor cannot capture unpriced pre-existing collateral.

### Proof of Concept
1. Attacker (or any unprivileged unit poster) sends a plain payment of `$asset` (e.g. 100 units) directly to the AA address with no matching trigger data - this is accepted as an ordinary payment and simply becomes part of `balance[$asset]` at the AA.
2. Attacker sends the "invest in MM" trigger: `base > 1e5` and `asset > 0` (can be the smallest allowed positive amount, e.g. 1 unit of `$asset`).
   - At evaluation time, `$bytes_balance` (prior base balance) is `0`, so the "initial deposit" branch fires: `$issue_amount = balance[base]` (only the bytes just sent). `mm_asset_outstanding` is set to this amount, and the attacker receives 100% of `mm_asset`.
3. Attacker sends the "divest MM shares" trigger with all of their `mm_asset`.
   - `$investor_share = mm_asset_amount / mm_asset_outstanding = 1`.
   - Attacker receives `round(1 * balance[$asset])`, which includes the 100 units of `$asset` dust seeded in step 1 that was never priced into `mm_asset_outstanding`, plus `round(1 * balance[base])`.
4. Net result: the attacker recovers their own bytes deposit and additionally extracts the pre-existing `$asset` dust for free - exactly analogous to the Thetanuts vault exploit where a depositor minted shares while the vault's pre-existing WBTC balance was unaccounted for, then withdrew it via `initWithdraw`.
