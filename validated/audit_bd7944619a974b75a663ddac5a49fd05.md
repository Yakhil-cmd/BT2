### Title
Webhook signature verification is scoped to an attacker-chosen organization while status/commit mutations are scoped to an unrelated, unverified repository/SHA — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which HMAC secret) to validate a webhook against using an **organization name taken from the untrusted JSON payload itself** (`repository.owner.login` or `organization.login`). The event handlers that actually mutate data, however, act on a **completely different field** — `repository.full_name` for most handlers, or in `StatusHandler`, nothing at all (it matches by commit SHA across the whole install). Because a multi-org Shipit deployment can legitimately have `webhook_secret` unset for one organization (this is a documented, supported configuration, e.g. `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md` mark it "optional"), an attacker can pick that unsecured organization to trivially pass signature verification, then supply arbitrary `repository`/`sha` values that target a totally unrelated, secured organization's stacks.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
`verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`, where `repository_owner` is read straight from the unauthenticated JSON body: [2](#0-1) 

The signature check itself, in `lib/shipit/github_app.rb`, unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

This is not a hypothetical misconfiguration — it is a documented and tested deployment shape. `docs/setup.md` explicitly labels `webhook_secret` as "(optional)", and the multi-org fixture used in tests sets it to `nil` for both orgs: [4](#0-3) [5](#0-4) 

Once "verified" (trivially, because the chosen org has no secret), the request body is dispatched to handlers by event type. Critically, `StatusHandler` performs **no repository scoping whatsoever** — it looks up commits purely by SHA across the entire instance and writes attacker-supplied `state`, `description`, `context`, and `target_url` directly onto them: [6](#0-5) 

The base `Handler` class shows the general pattern of resolving the *acted-upon* repository from `repository.full_name`, a field never covered by the organization used in `verify_signature`: [7](#0-6) 

The broken trust binding, stated as an equality that the code fails to enforce:
`organization authenticated by verify_signature (payload.repository.owner.login) == repository/commit actually mutated by the handler (payload.repository.full_name / payload.sha)`.

`Status.create_status_from_github!` / the model layer treats these injected statuses as authoritative CI signal: a `success` state makes a commit deployable and can trigger continuous deployment or merge processing: [8](#0-7) [9](#0-8) 

### Impact Explanation
An unauthenticated, unprivileged external attacker (no Shipit session, no API token, no GitHub App key) can send a single crafted HTTP POST to `/webhooks`:
1. Set `X-Github-Event: status`.
2. Set the JSON body's `repository.owner.login` (or top-level `organization.login`) to an organization configured in this Shipit instance's `github` secrets section with no `webhook_secret` (a supported, documented configuration for multi-org installs).
3. Set `sha` to the SHA of any commit tracked by any stack in the instance (commit SHAs are public, visible on GitHub) and `state: "success"`, along with a fabricated `context` matching a required/blocking CI check.

Because `verify_webhook_signature` short-circuits to `true` for that organization, the request is accepted with no valid HMAC at all, and `StatusHandler` writes a fake "success" CI status onto that commit regardless of which organization/repository it actually belongs to. This can flip `Commit#deployable?` to true and trigger continuous delivery or unblock a manual deploy of unreviewed code — an unauthorized deploy, which falls under the required "Critical" impact bucket in scope.

### Likelihood Explanation
Likelihood is high for any Shipit deployment that manages multiple GitHub organizations (a supported and documented feature) where at least one configured organization omits `webhook_secret`. The `/webhooks` endpoint is unauthenticated by design (it must accept unauthenticated GitHub deliveries), so no credentials, session, or GitHub write access are needed — only knowledge of a target commit SHA, which is public GitHub information.

### Recommendation
- In `WebhooksController#verify_signature`, after resolving the organization and its secret, cross-check that the organization actually owns the `repository.full_name` referenced by the payload (e.g., via `Repository.from_github_repo_name` → verify its configured GitHub org matches `repository_owner`) before invoking handlers.
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is unset in a multi-organization configuration; require an explicit, obviously-dangerous opt-in flag if operators truly want unsigned webhooks for a specific org, and warn loudly.
- Fix `Shipit::Webhooks::Handlers::StatusHandler#process` to scope `Commit.where(sha: ...)` by the repository/stack derived from `params.repository.full_name` (consistent with other handlers) instead of matching SHA globally across all repositories.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` (no `webhook_secret`) and `OrgB` (real, secured, with active stacks):

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/irrelevant" },
  "sha": "<sha of a real commit in an OrgB-tracked stack>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "http://attacker.example"
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` without checking `X-Hub-Signature` at all. `StatusHandler#process` then matches the commit purely by `sha` (no repository/org check) and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `success` status onto a commit that belongs to `OrgB`, independent of the "verified" `OrgA` context.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
