### Title
Missing validation of `creator` account in `initialize_with_permission` permanently freezes creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` accepts a `creator` account with no constraints whatsoever and stores it verbatim as `PoolState.pool_creator`. Since this field is later relied upon as the sole authorization anchor for withdrawing accumulated creator fees, an attacker-chosen invalid value (e.g. `Pubkey::default()` / the System Program address, which has no corresponding private key) makes those fees permanently unclaimable — the same "unchecked/zero-address privileged field" bug class as the reported `defaultAdmin` issue, but here applied to `pool_creator`.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as a completely unchecked account: [1](#0-0) 

Unlike the plain `initialize` instruction, where `creator` is a `Signer<'info>` and therefore must be a real, signable ed25519 key [2](#0-1) , here `creator` has no `address`, no `owner`, and no signer requirement — it is fully attacker-controlled data supplied in the instruction's account list.

The handler then persists this arbitrary value directly into the pool's permanent state: [3](#0-2) [4](#0-3) 

`pool_creator` subsequently becomes the sole authorization gate for the creator fee-collection instructions: [5](#0-4) 

Here `creator` must be a `Signer` whose address equals `pool_state.pool_creator`. If `pool_creator` was initialized to `Pubkey::default()` (or any other address with no known private key, e.g. the System Program ID), no valid signature can ever be produced for that address, so this path becomes permanently uncallable.

The "permissionless" variant does not require a signature, but still routes the funds into an ATA whose authority equals the unusable `pool_creator` address: [6](#0-5) [7](#0-6) 

Even here, tokens end up controlled by an authority pubkey with no private key, so they are still permanently frozen — merely relocated from the pool vault into an ATA nobody can ever spend from.

This is directly analogous to the reported bug class: a privileged/authoritative address field (`defaultAdmin` in the report, `pool_creator` here) is written from caller-supplied input into permanent on-chain state without any validation that it is a usable, non-degenerate address, and that state is later used as an authorization anchor.

### Impact Explanation
Once a pool is created via `initialize_with_permission` with `creator` set to a key with no private key, all `creator_fees_token_0` / `creator_fees_token_1` accrued for that pool (tracked in `PoolState`, see `states/pool.rs` fields `creator_fees_token_0/1`) become permanently frozen: `collect_creator_fee` can never be authorized (no one can sign as the zero/degenerate address), and `collect_creator_fee_permissionless` merely moves the funds into an unspendable ATA. These are real economic funds (a fee split carved out of every swap that would otherwise accrue to the creator, and separately tracked from LP-redeemable liquidity via `vault_amount_without_fee`, see `programs/cp-swap/src/states/pool.rs` lines 200-220), so this constitutes permanent freezing of pool funds. Impact is bounded to the creator-fee share of a given pool (not principal/LP liquidity), so severity is Medium.

### Likelihood Explanation
The `creator` account requires no signature and no ownership/address constraint, so any account permitted to call `initialize_with_permission` (i.e., holding a valid `Permission` PDA per `PERMISSION_SEED`) can trivially pass `Pubkey::default()` or the System Program ID as `creator` in a single transaction — this is a simple, always-reachable misconfiguration rather than a complex exploit chain, making likelihood high once the instruction is reachable.

### Recommendation
Add a validation check in `InitializeWithPermission` (or in `initialize_with_permission`) rejecting `creator.key() == Pubkey::default()` and other known-unusable system addresses before calling `pool_state.initialize(...)`, mirroring the recommended fix for `defaultAdmin` in the referenced report. Consider also requiring `creator` to at least be distinct from the System Program ID and other program-owned singleton addresses.

### Proof of Concept
1. Obtain (or already hold) a valid `Permission` PDA account for `payer` via `create_permission_pda` (pre-condition for calling `initialize_with_permission`).
2. Call `initialize_with_permission` with:
   - `payer` = attacker's funded signer
   - `creator` = `Pubkey::default()` (System Program ID) — no signer required for this account, no on-chain constraint rejects it
   - valid `token_0_mint`/`token_1_mint`, correct vault/lp_mint/observation PDAs, valid `amm_config`
3. Pool is created successfully; `PoolState.pool_creator` is now `11111111111111111111111111111111111111` (System Program address).
4. As swaps occur against this pool, `creator_fees_token_0`/`creator_fees_token_1` accumulate in `PoolState` (per the normal fee-split logic in `swap_base_input`/`swap_base_output`, not shown here but gated by `CreatorFeeOn`/`enable_creator_fee`).
5. Attempt `collect_creator_fee`: fails permanently — no key exists that can sign as `Pubkey::default()` to satisfy the `Signer` + `address = pool_state.load()?.pool_creator` constraint.
6. Attempt `collect_creator_fee_permissionless`: succeeds in moving tokens into an ATA whose `authority` is `Pubkey::default()`, but no private key exists to ever move those tokens further — funds are permanently locked. [1](#0-0)
