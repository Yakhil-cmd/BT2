### Title
Webhook signature is verified against the payload's own `organization`/`repository.owner`, but handlers write to whatever `repository.full_name` is in the payload, with no cross-check that the two belong together - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` picks the `GithubApp`/`webhook_secret` used to validate `X-Hub-Signature` by reading `repository_owner` straight out of the untrusted, attacker-influenced JSON body being verified (`params.dig('repository','owner','login')` or, for org-level events, `params.dig('organization','login')`). Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, which each resolve the affected `Stack`s via `Handler#stacks`, itself derived independently from `payload.dig('repository', 'full_name')`. Nothing ties the org whose secret validated the HMAC to the repository whose `Stack` is subsequently modified. [4](#0-3) [5](#0-4) 

### Finding Description
In a single-organization deployment this is harmless because there is only one webhook secret. But Shipit explicitly supports multiple GitHub organizations configured with independent `webhook_secret`s, each mapped to its own installation (`lib/shipit/github_app.rb`, `test/dummy/config/secrets_double_github_app.yml`). `Shipit.github(organization: repository_owner)` looks up the `GithubApp` config keyed by whatever organization name appears in the payload, and `verify_webhook_signature` simply HMACs the raw body against *that* organization's secret: [6](#0-5) 

The equality that should hold is: `organization whose secret authenticated the signature == organization owning repository.full_name that the handler writes to`. Nothing enforces this. A holder of the webhook secret for `OrgA` (any legitimate person who received/leaked `OrgA`'s webhook secret, or any GitHub webhook delivered honestly by `OrgA`) can craft (or GitHub, if compromised/misdelivered, could deliver) a payload whose `repository.owner.login` is `OrgA` (so the signature check passes using `OrgA`'s secret) but whose `repository.full_name` is `OrgB/some-repo` — a repository actually owned by a different configured organization. `Handler#stacks` will resolve `OrgB/some-repo`'s `Stack` and the handler will act on it (queue a `GithubSyncJob`, create commit `Status`es, run `RefreshCheckRunsJob`, etc.), even though the signature only proves the request came from someone who knows `OrgA`'s secret, not `OrgB`'s.

This mirrors the report's bug class exactly: the field the code *acts on* (here, `repository.full_name`, driving which `Stack`/deploy state is mutated) is disjoint from the field actually *covered by the verified credential* (here, the HMAC, checked against `repository.owner.login`/`organization.login`). Just as the Buyout contract verified nothing about the `proposer` field re-entering `start`, this controller verifies nothing tying the authenticated organization to the repository ultimately written.

### Impact Explanation
This allows cross-repository/cross-organization writes to `Stack` state: an attacker who legitimately controls (or has leaked) one configured organization's webhook secret can inject events (pushes, commit statuses, check-suite completions) that get attributed to a *different* organization's repository/stack, causing spurious `GithubSyncJob`, status/check-run records, and continuous-deployment triggers on stacks they do not control. That is a cross-repository write via a credential-authentication mismatch, matching the Critical bucket ("cross-repository writes").

### Likelihood Explanation
This only manifests in the documented multi-organization configuration (which the engine explicitly supports and ships example config for), and requires the attacker to possess a legitimate webhook secret for at least one configured organization (not privileged Shipit access, an `ApiClient` token, or a GitHub App private key — those are different credentials). Given that the secret only needs to match the *declared* org in the payload, not the org that actually owns the target repository, likelihood is moderate: it requires a specific deployment topology (multiple orgs sharing one Shipit instance) but no additional Shipit-side privilege.

### Recommendation
After verifying the HMAC, re-derive `repository_owner` from the same trusted context used for verification, and require that every handler's resolved `Stack`/`Repository` actually belongs to the organization whose secret was used to validate the signature (e.g., compare `Repository#owner` to the verified `repository_owner` before invoking handlers, or scope `Handler#stacks` to `Stack.where(repository: Repository.from_github_repo_name(repository_name)).where(...owner: verified_org)`).

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As a holder of `OrgA`'s webhook secret, POST to `/github_webhooks` a `push` event body where `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against `OrgA`'s secret) but `repository.full_name = "OrgB/target-repo"`.
3. Sign the raw body with `OrgA`'s `webhook_secret` and set `X-Hub-Signature` accordingly.
4. `WebhooksController#verify_signature` passes (organization `OrgA` matched, signature valid).
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github` on `OrgB`'s stack, even though `OrgA`'s secret was used to authenticate the request.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
