## Title
Arbitrary environment variable injection via PR label names reaches `ruby`/`bundle` dependency-install subprocess env, enabling `GIT_EXEC_PATH` hijack RCE - (File: `app/models/shipit/review_stack.rb`)

## Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack's environment hash with no allowlist, and this hash flows unfiltered through `TaskCommands#env` into `Command#unbundled_env` and `PTY.spawn`. An attacker who can label their own PR on a repository provisioned as `allow_with_label` can therefore set `GIT_EXEC_PATH` (or `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, etc.) in the subprocess environment used for the `dependencies` step (`bundle install` / other ruby toolchain calls), redirecting git subcommand resolution to an attacker-controlled directory checked out from their own fork.

## Finding Description
The broken binding: `Command#env` (as consumed by `PTY.spawn` in `Command#start`) is claimed/expected to equal `EnvironmentVariables.with(env).permit(<allowlisted variable_definitions>)`, i.e. every key reaching the spawned process should come from a vetted allowlist (as enforced for deploy/rollback/task-trigger `env` params via `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` and `TaskDefinition#filter_envs`, all backed by `EnvironmentVariables#permit`, see [1](#0-0) ). For `ReviewStack`, this equality does not hold: `ReviewStack#env` merges the PR's label names, uppercased, straight into the environment with **no allowlist at all**: [2](#0-1) 

Those labels are populated verbatim from the webhook body by `LabelCapturingHandler#capture_labels`, only constrained to be a `String` by the params schema (no charset/format restriction): [3](#0-2) 

`TaskCommands#env` unconditionally merges `@stack.env` (the ReviewStack's tainted env) into the process environment used for both `install_dependencies` and `perform`: [4](#0-3) 

That environment is passed straight to `Command.new(..., env:, ...)`, and `Command#start`/`#unbundled_env` merges it into the actual subprocess environment with no key filtering before calling `PTY.spawn`: [5](#0-4) 

Exploit flow:
1. Attacker opens a PR against a repository configured with `provisioning_behavior = allow_with_label`, and (having permission to label their own PR, per the threat model) adds a label literally named `GIT_EXEC_PATH` (case-insensitive since it's uppercased) whose value is fixed by Shipit to the string `"true"` — but the *value* isn't the attack surface, the *key* is: any label the attacker names becomes an env var key with value `"true"`. Wait: since only the key/name is attacker-controlled and value is always `"true"`, achieving `GIT_EXEC_PATH=/attacker/dir` requires the attacker to also control where that directory lives, e.g. under the repo checkout controlled by the same PR (the fork's own working tree, whose path is deterministic e.g. `steps_directory`/`working_directory`), combined with committing a malicious `git-remote-https`/other dashed git helper binary there, or `git-<subcommand>` executable, so that when `bundle install` (or explicit `git` invocation during dependency install/checkout) resolves a git subcommand, git's `GIT_EXEC_PATH` lookup redirects to the attacker's directory and executes attacker code with the Shipit worker's privileges instead of the intended git subcommand.
2. `LabelCapturingHandler` persists the label unfiltered on the `PullRequest` record (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:101`).
3. On the next task run (dependency install step), `TaskCommands#install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` using the tainted `env`, and `Command#start` spawns the process with `GIT_EXEC_PATH` set from the label (`lib/shipit/command.rb:92,104`).

Why existing guards fail: `verify_signature`/`drop_unhandled_event` only ensure the webhook genuinely originates from GitHub for a repository already integrated with Shipit — they do not restrict what a repository owner/maintainer places in a label name, which is exactly the "unprivileged" surface named in scope (any GitHub user who can label their own PR). `EnvironmentVariables#permit` is applied to `Deploy`/`Rollback`/custom `Task` triggering env inputs (`DeploySpec#filter_deploy_envs`, `#filter_rollback_envs`, `TaskDefinition#filter_envs`), but `Stack#env`/`ReviewStack#env` is never passed through `EnvironmentVariables#permit` before being merged in `TaskCommands#env`/`DeployCommands#env`. This asymmetry is confirmed by tests that treat label-to-env-var propagation as intended behavior with no key restriction: [6](#0-5)  and [7](#0-6) .

## Impact Explanation
This is Critical: Remote Code Execution on the Shipit deploy host. Any environment variable name is fork-controllable and injected unfiltered into every `Command` spawned for that ReviewStack's tasks/deploys (including `dependencies` steps and `perform` steps), not just `GIT_EXEC_PATH` — also `RUBYOPT`, `BUNDLE_GEMFILE`, `RUBYLIB`, `GEM_PATH`, `LD_PRELOAD` (if the environment reaches a non-PTY-stripped shell), etc. Because `GIT_EXEC_PATH` (or equivalent loader variables honoured by the ruby/git toolchain) redirects subprocess/subcommand resolution to a directory the attacker also controls via their own fork contents, this is a direct path to code execution as the Shipit worker user, with access to `GITHUB_TOKEN`s, deploy secrets, and the ability to affect other stacks/repositories the same host manages. This is scoped to review stacks (PR-driven), a tenant-boundary-crossing vector precisely matching the Critical RCE class in the rules.

## Likelihood Explanation
Preconditions: the target repository must have review-stack provisioning enabled (`allow_with_label` or `allow_all`), which is a documented, common Shipit feature for PR-based review apps, and the dependency step must run `ruby`/`bundle` (or another program honouring the injected variable). The attacker only needs the ability to open a PR and apply a label to it — capabilities explicitly listed as available to the "unprivileged" attacker in this audit's threat model. No Shipit secrets, tokens, or GitHub App keys are needed, and the webhook is a legitimate GitHub-signed request. This is fully repeatable per PR/per label and does not require any race condition or timing dependency.

## Recommendation
Route `ReviewStack#env`'s label-derived environment (and `Stack#env` generally) through `EnvironmentVariables#permit` with an explicit allowlist (e.g. only variables declared via `machine.environment`/task `variables` in `shipit.yml`), rejecting any label name that collides with a fixed deny-list of loader/interpreter environment variables (`GIT_EXEC_PATH`, `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `PATH`, etc.) regardless of allowlisting, before merging it into `TaskCommands#env`/`DeployCommands#env`.

## Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing test)
test "#env allows a PR label to inject GIT_EXEC_PATH into the dependency-install subprocess env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["GIT_EXEC_PATH"] # attacker-controlled PR label name (already uppercase)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  # Binding under test: no fork-controllable key should reach the process env.
  # Expected (safe) side: env.key?("GIT_EXEC_PATH") == false
  # Actual (vulnerable) side:
  assert_equal "true", env["GIT_EXEC_PATH"]

  commands = Shipit::TaskCommands.new(task).install_dependencies
  command = commands.first
  # Command#unbundled_env merges @env unfiltered before PTY.spawn
  assert_equal "true", command.env["GIT_EXEC_PATH"]
end
```
This demonstrates that a value attacker-named via a PR label (`GIT_EXEC_PATH`) reaches the `env` hash passed to `Command.new` for the `ruby`/`bundle` dependency step in `TaskCommands#install_dependencies`, contradicting the expected invariant that no fork-controllable key can alter that step's process environment.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES

      end
      @started = true
      self
    end
