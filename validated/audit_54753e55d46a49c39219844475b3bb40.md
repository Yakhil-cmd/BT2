### Title
Cross-repository commit-status writes via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by bare SHA with no repository or stack scoping, then writes the incoming GitHub status to every matching `Commit` record. Because Git SHAs are content-addressed and identical across forks/mirrors of a repository, a status delivered and authenticated for one repository can be applied to a `Commit` belonging to a completely different repository/stack, altering that victim stack's CI state and, when `blocking_statuses` is configured, its `blocked?`/deploy-gating outcome.

### Finding Description
The broken binding is: `status.repository == commit.stack.repository` is assumed to be true for every `commit` returned by `Commit.where(sha: params.sha)`, but nothing in the code enforces it.

Trace:
- `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to handlers for the event type [1](#0-0) .
- `verify_signature` authenticates the *sender*, not the *target commit*: it looks up the `GitHubApp` config keyed by `repository_owner`, taken straight from the payload's own `repository.owner.login`, and HMAC-verifies the raw body against that org's `webhook_secret` [2](#0-1) [3](#0-2) . This only proves the payload genuinely came from GitHub for the org that owns the repo named in the payload — it says nothing about which `Commit` rows should be touched.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . There is no filter on repository, stack, or the payload's `repository.full_name` — every `Commit` record in the database sharing that SHA (across any stack/repository) gets the status applied.

Exploit flow: an attacker who legitimately owns/administers a repository already integrated with this Shipit instance (a normal, unprivileged self-service user of the tool) forks or otherwise shares git history with a victim's repository, so that a victim's commit SHA also exists in the attacker's own repo. The attacker triggers (via their own CI, or directly via the GitHub Status API on a repo they control) a `status` webhook with `context: sonarqube` for that shared SHA. GitHub signs and delivers this webhook correctly for the attacker's own org, so `verify_signature` passes legitimately — the signature check is org-scoped to the sender, not repo-scoped to the target commit. `StatusHandler` then matches and mutates the victim's `Commit` row for the same SHA in a different repository/stack, because the query has no repository predicate at all.

Existing guards do not stop this: `verify_signature` validates the sender's organization/secret, `drop_unhandled_event`/`check_if_ping` only filter event types, and `ExplicitParameters` only validates the shape of the payload (`sha`, `state`, `context`, etc.) — none of them constrain which `Commit` rows the handler is allowed to update.

### Impact Explanation
A payload authenticated for repository A can write CI status directly onto a `Commit` belonging to repository B's stack, without B's authentication ever being involved. If the victim stack has `blocking_statuses` configured to require the `sonarqube` context, this forced status write can flip the aggregate commit state and thus `blocked?`, which gates deploy eligibility — enabling either a forced ship (attacker posts `success`) or a forced block/DoS-of-deploys (attacker posts `failure`/`pending`) on a stack the attacker never authenticated against. This is a cross-tenant state-mutation issue matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions: attacker must control (or trigger status posts on) a repository that already passes `verify_signature` for some org configured in this Shipit instance, and that repository must share a commit SHA with the victim's tracked stack (trivially true for forks, mirrors, or repos with common ancestor commits/empty-tree/initial commits), and the victim stack must have `blocking_statuses` requiring the same context. These are realistic, low-cost preconditions for anyone who can fork a tracked repo and post their own commit statuses — no Shipit session, API token, or secret is required beyond what GitHub already grants a repo owner. The attack is repeatable against any repository sharing a SHA with a Shipit-tracked stack.

### Recommendation
Scope the lookup in `StatusHandler#process` (and analogous handlers) to commits belonging to the repository identified in the payload (e.g., join through `stack.repository` and filter by `params.dig('repository','full_name')` / `repository_owner`+`repository_name`) instead of matching on bare `sha` alone, so a status can only ever be applied to commits of the repository that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Repository`/`Stack` pairs, `repo_a` (attacker-owned, org `attacker-org`) and `repo_b` (victim, org `victim-org`), with `repo_b`'s stack configured with `blocking_statuses` requiring `sonarqube`.
2. Create a `Commit` on `repo_a`'s stack and a `Commit` on `repo_b`'s stack sharing the same `sha` value.
3. Build a `status` webhook payload with `repository.owner.login = 'attacker-org'`, `context: 'sonarqube'`, `state: 'success'`, and the shared `sha`.
4. Call `StatusHandler.new(...).call(payload)` (or invoke through the controller with a valid signature for `attacker-org` only).
5. Assert: `repo_b`'s `Commit#state`/`blocked?` (before) != (after) — i.e., the victim commit picked up the `sonarqube` status and its `blocked?`/ship eligibility changed — even though the request was only ever authenticated for `attacker-org`/`repo_a`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
