### Title
Permanent freezing of accrued creator fees when the pool creator's token account is blacklisted/frozen - (File: programs/cp-swap/src/instructions/collect_creator_fee.rs, programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs)

### Summary
Both `collect_creator_fee` and `collect_creator_fee_permissionless` push accrued creator-fee amounts directly to a fixed destination token account owned by the pool's `creator` field via `transfer_from_pool_vault_to_user`, mirroring the reported push-payment pattern (`PredictDotLoan.repay` transferring `LOAN_TOKEN` directly to a fixed lender) that fails when the recipient is blacklisted by the token (e.g., USDC).

### Finding Description
`collect_creator_fee_permissionless` allows anyone to trigger a transfer of the pool's accumulated `creator_fees_token_0`/`creator_fees_token_1` from the pool vaults to `creator_token_0`/`creator_token_1`, which are ATAs whose `authority` is hard-constrained to `pool_state.load()?.pool_creator` [1](#0-0) . Likewise, `collect_creator_fee` requires the `creator` signer to equal `pool_state.pool_creator` and transfers to the same fixed ATA [2](#0-1) .

The actual transfer is a direct push via `transfer_from_pool_vault_to_user`, which performs `token_2022::transfer_checked` from the vault to the recipient token account using the pool authority PDA as signer [3](#0-2) . If the mint is USDC (or any token with a freeze/blacklist authority) and the creator's wallet/ATA has been frozen or blacklisted, the `transfer_checked` CPI will fail and revert the entire instruction, exactly as in the reported `PredictDotLoan.repay` case where `LOAN_TOKEN.safeTransferFrom` reverts against a blacklisted lender.

Because `pool_state.creator_fees_token_0`/`creator_fees_token_1` are only zeroed after a successful transfer [4](#0-3) , a permanently blacklisted creator means these fee counters can never be decremented and the corresponding tokens sitting in the vaults can never be withdrawn by anyone — there is no alternate "pull" mechanism, no way to redirect the recipient, and no admin override to reset `pool_creator` or the fee counters.

### Impact Explanation
This causes a permanent, protocol-level freezing of funds: the accrued creator-fee token balance becomes permanently unclaimable once the creator's token account is blacklisted. Unlike `withdraw()`, where a user could only freeze their own funds by having their own account blacklisted (self-inflicted, not a protocol bug), here the frozen fee amount is a portion of pool assets tracked separately (`creator_fees_token_0/1`) that no other party — not LPs, not protocol, not the creator themselves — can ever recover, since the destination is immutably tied to `pool_state.pool_creator` and both the permissioned and permissionless entry points use the same fixed recipient.

### Likelihood Explanation
Requires the pool's token mint to have a blacklist/freeze capability (e.g., USDC) and requires the creator's address to become blacklisted by the token issuer — an external condition outside the program's control, matching the same precondition structure as the original report. Given USDC and similar centralized stablecoins are extremely commonly paired against in AMM pools, and pool creators are typically permissionless/unprivileged addresses (not vetted), this is a realistic external trigger.

### Recommendation
Replace the direct push-transfer model for creator fees with a pull-based claim model: credit the fee amount in a per-creator ledger and let the creator (or, if blacklisted, a rescue/redirect path) withdraw to an account of their choosing, or allow an admin-gated mechanism to redirect frozen creator fees to a different destination if the original ATA/authority becomes permanently unusable.

### Proof of Concept
1. Deploy a pool with `token_0`/`token_1` where one mint is USDC-like (freezable/blacklistable) and `pool_creator` = address `C`.
2. Accumulate `creator_fees_token_0`/`creator_fees_token_1` > 0 via normal swap activity (fee accrual logic in `states/pool.rs`, not fully verified line-by-line due to index limits).
3. USDC issuer blacklists address `C` (or `C`'s ATA is frozen).
4. Call `collect_creator_fee_permissionless` (or `collect_creator_fee` signed by `C`) — the `transfer_checked` CPI to `creator_token_0`/`creator_token_1` reverts because the recipient is blacklisted/frozen, so the whole instruction fails.
5. Because the fee counters are only zeroed after a successful transfer, the accrued fee amount remains permanently stuck in the vault, unrecoverable by any caller, indefinitely.

Note: The exact accrual and rounding logic for `creator_fees_token_0/1` in `programs/cp-swap/src/states/pool.rs` was not fully inspected due to search/read budget limits; readers should verify there against the actual field definitions and update logic before treating this as final.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
