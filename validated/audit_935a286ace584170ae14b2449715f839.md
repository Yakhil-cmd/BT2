### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while `LabeledHandler` (and all handlers) act on the independent `repository.full_name` field, letting a payload "verified" under a secret‑less/attacker‑controlled organization mutate a victim repository's label‑driven state - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC against using `repository_owner`, computed independently from `params.dig('repository','owner','login')` or `params.dig('organization','login')` [1](#0-0) . Nothing ties that value to `repository.full_name`, which is what `PullRequestLabeledHandler#repository` actually uses to resolve the target `Shipit::Repository` and mutate its review-stack state [2](#0-1) . Combined with `GitHubApp#verify_webhook_signature` returning `true` unconditionally when no `webhook_secret` is configured for the org being checked [3](#0-2) , an attacker who controls (or names) any organization lacking a configured secret can forge a payload whose `repository.owner.login`/`organization.login` point at that secret-less org (satisfying `verify_signature`) while `repository.full_name` and all pull-request/label fields point at an unrelated victim repository.

### Finding Description
The claimed binding is: `organization used to verify the webhook signature (repository_owner)` == `organization owning the repository whose state is mutated (owner segment of repository.full_name)`.

Trace:
- `WebhooksController#create` parses the raw JSON body directly from the attacker-controlled POST and dispatches it to handlers without re-deriving or cross-checking any field against the org used for verification [4](#0-3) .
- `verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(header, raw_post)` [5](#0-4) . `repository_owner` is read from the same JSON body via `repository.owner.login`, falling back to `organization.login` [1](#0-0) .
- `verify_webhook_signature` short-circuits to `true` when the resolved app has no `webhook_secret` configured [6](#0-5) . This is the "secret-less org" referenced in the question: any Shipit-configured GitHub App/organization entry without a `webhook_secret` accepts arbitrary signatures for payloads claiming that org.
- Once past `verify_signature`, `LabeledHandler#repository` looks up the target purely from `params.repository.full_name`, with no re-check against `repository_owner` [2](#0-1) , then drives `archive!`/`unarchive!` on that repository's `review_stacks` based on attacker-supplied `pull_request.labels` [7](#0-6) .

Exploit flow: attacker crafts a raw JSON body with `repository.owner.login` (or `organization.login`) set to an org Shipit has configured without a `webhook_secret`, and `repository.full_name` set to `"victim-org/victim-repo"`, with a `pull_request.labels` array containing the label the victim's `provisioning_label_name` is configured to react to. POST it (with any `X-Hub-Signature` value, since it's ignored when no secret is set) to `/webhooks` with `X-Github-Event: pull_request`. `verify_signature` passes because the resolved org has no secret; `LabeledHandler` resolves and mutates the victim repository's review-stack `Stack`/`PullRequest` archive state, entirely independent of anything the victim's real GitHub repo emitted.

Existing guards do not stop this: `verify_signature` only checks the HMAC for whichever org the payload itself claims — it never asserts that org matches `repository.full_name`'s owner segment. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not cross-field consistency. `Repository` model validations constrain the stored repository's own name format but do nothing to bind an incoming webhook's claimed owner to its target repository field.

### Impact Explanation
An attacker with no Shipit credentials can force archive/unarchive (provisioning) state changes on a victim's review-stack-enabled repository — a write to a repository record the attacker never authenticated for — purely by exploiting the disjoint fields used for authentication vs. targeting. This is repeatable against any repository as long as one org in Shipit's configuration lacks a `webhook_secret`, and is not limited to `LabeledHandler`; any handler that resolves its target from `repository.full_name` (the general handler design) is equally exposed. This matches "a payload for one repository mutating another's stack" — Critical.

### Likelihood Explanation
Requires that at least one organization configured in Shipit's GitHub Apps config omit `webhook_secret` (plausible for internal/dev/default entries, and the code explicitly supports and treats this as valid via the `return true unless webhook_secret` branch, rather than treating it as "deny"). The attacker needs no Shipit session, API token, or GitHub secret — only knowledge of a secret-less org's login (which they may register themselves as an org owner) and the victim's `owner/repo` full name. This is exploitable with plain HTTP POSTs.

### Recommendation
Bind signature verification to the same identity used for repository resolution: require `repository.full_name`'s owner segment to match the org whose secret verified the request (reject on mismatch), and/or refuse to treat an org with no configured `webhook_secret` as automatically verified — require an explicit opt-in/allow-list instead of `return true`.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` style, without live GitHub:
1. Configure Shipit test secrets with two orgs: `"attacker-org"` (no `webhook_secret`) and `"victim-org"` (has `webhook_secret`).
2. Create `Shipit::Repository` for `victim-org/victim-repo` with `provisioning_behavior` requiring the label, and a `PullRequest`/review `Stack` in the non-archived state.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, body JSON: `{"action":"labeled","number":1,"pull_request":{...,"state":"open","labels":[{"name":"<provisioning_label_name>"}]},"repository":{"full_name":"victim-org/victim-repo","owner":{"login":"attacker-org"}},"sender":{"login":"attacker"}}`, with any/garbage `X-Hub-Signature`.
4. Assert response is `200 OK` (not `422`) and that `victim-org/victim-repo`'s `PullRequest`/`Stack` archive state changed — proving `repository_owner` ("attacker-org", verified) diverged from `repository.full_name`'s owner ("victim-org", mutated) yet the mutation succeeded.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
