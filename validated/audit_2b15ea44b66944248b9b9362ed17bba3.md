Based on my investigation, the closest genuine Polkadot SDK analog to the reported "missing CEI pattern in `netAtPrice`" is a CEI-ordering issue in the new `pallet-psm` (Peg Stability Module) pallet, which is wired into `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`. ### Title
`pallet-psm::mint`/`redeem` mutate `PsmDebt` accounting only *after* invoking generic `T::Fungibles` transfer/mint/burn calls, violating CEI - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`Pallet::mint` and `Pallet::redeem` in `pallet-psm` perform all token-moving interactions (`T::Fungibles::transfer`, `mint_into`, `burn_from`) before writing the pallet's own accounting state (`PsmDebt`), mirroring the exact bug class described in the report (interactions before effects).

### Finding Description
In `mint()`, the debt-ceiling checks are computed from `PsmDebt::<T>::get` and `Self::total_psm_debt` read *before* any external calls [1](#0-0) , then the pallet performs the external asset transfer and mints the internal asset [2](#0-1) , and only afterwards commits the updated debt to storage [3](#0-2) . The same ordering exists in `redeem()`: the internal asset is burned and the external asset transferred out of the reserve [4](#0-3)  before `PsmDebt` is decremented [5](#0-4) .

`T::Fungibles` is only bound to the generic `FungiblesMutate`/`FungiblesMetadataInspect`/`FungiblesRolesInspect` traits [6](#0-5) , and the repository itself ships a contract-execution-backed implementation of these fungibles traits in `pallet-revive` (`substrate/frame/revive/src/impl_fungibles.rs`), which routes `transfer`/`mint_into` calls through actual EVM/PVM contract execution for the corresponding asset. If a PSM instance's approved `external_asset` (added via the permissioned but ordinary `add_external_asset` admin call) is backed by such a contract, that contract's `transfer` logic can itself dispatch back into the runtime (e.g., via a `call_runtime`-style precompile) and re-enter `Psm::mint`/`Psm::redeem` while the outer call's `PsmDebt` entry is still stale — because the debt write happens last. `pallet-revive` itself uses a fine-grained `ReentrancyProtection` mechanism, but that guard only prevents re-entering the contracts/revive pallet's own call stack; it does not protect other pallets such as `pallet-psm` from being re-entered through a nested `RuntimeCall` dispatch triggered from contract code.

### Impact Explanation
If reachable, a reentrant `mint` call could read the not-yet-updated `PsmDebt`/`AssetCeilingWeight` figures on each nested invocation and pass the `ExceedsMaxPsmDebt` check multiple times, minting internal stablecoin beyond the configured debt ceiling (unbacked issuance) — a Critical/High-class outcome if reachable. A reentrant `redeem` could similarly drain more of the PSM reserve than the caller's actual internal-asset backing justifies.

### Likelihood Explanation
Medium-to-speculative. The CEI-violation code pattern is confirmed and unambiguous (interactions strictly precede the `PsmDebt` write in both dispatchables). However, exploitability is conditioned on a PSM instance's approved external (or internal) asset being backed by a `Fungibles` implementation that actually executes attacker-influenceable code during `transfer`/`mint_into`/`burn_from` (e.g. a `pallet-revive`-backed ERC20). I could not confirm within the available investigation whether Asset Hub Westend's live `pallet_psm::Config::Fungibles` wiring uses such a contract-backed implementation versus plain `pallet-assets` (which has no such hooks and would make this unreachable). This is a genuine unresolved gap in my analysis, not a claim of confirmed exploitability.

### Recommendation
Reorder both `mint` and `redeem` to follow strict checks-effects-interactions: write `PsmDebt::insert`/`mutate` (and any other pallet-owned accounting state) before invoking `T::Fungibles::transfer`/`mint_into`/`burn_from`, or add an explicit reentrancy guard (e.g. a per-instance in-storage lock, or `frame_support::storage::with_transaction`-based rollback-safe ordering) around the swap logic so nested re-entry into `mint`/`redeem` for the same PSM instance is rejected regardless of what `T::Fungibles` implementation a runtime configures.

### Proof of Concept
Not executed. I identified the vulnerable code ordering via static analysis of `substrate/frame/psm/src/lib.rs` and confirmed (a) the pallet is wired into a real runtime (`asset-hub-westend`), and (b) the repository ships a contract-execution-capable `Fungibles` implementation in `pallet-revive` (`impl_fungibles.rs`) that could in principle back a PSM external asset. I was not able to, within the remaining tool budget, (1) confirm the actual `Fungibles` type used for `pallet_psm::Config` on a live/production runtime, or (2) construct and run a concrete Rust/FRAME integration test demonstrating a nested re-entrant `mint`/`redeem` call bypassing the debt ceiling. This finding is reported as a code-pattern match with a plausible but unverified reachability path, not a confirmed, reproduced exploit.
