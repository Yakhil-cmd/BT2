### Title
`pool_creator` identity binding is fully attacker-controlled and unverified in `initialize_with_permission`, allowing an unrelated address to be granted exclusive creator-fee-collection rights - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The authentik CVE describes an identity-binding field (`UserSourceConnection.user` / `GroupSourceConnection.group`) that is settable by an actor without proving they control the linked identity, letting them redirect a privileged capability (account login) to an arbitrary target. The Solana analog is the `creator` field in `InitializeWithPermission`, which becomes `PoolState.pool_creator` and is later used as the sole authorization check for collecting accumulated creator fees, yet it is never validated to be a signer, to match the `payer`, or to relate to the `permission` PDA that authorized pool creation.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as an `UncheckedAccount` with only a `CHECK: creator of pool` comment, no signer requirement, and no constraint tying it to `payer` or to the `permission` PDA: [1](#0-0) 

That raw, attacker-supplied pubkey is written directly into `PoolState.pool_creator` via `pool_state.initialize(...)`: [2](#0-1) 

`PoolState.pool_creator` is subsequently the only authorization check for who may collect accumulated creator fees, both in the signer-gated and permissionless collection paths: [3](#0-2) [4](#0-3) 

Because `creator` is never checked to be `payer`, to be a signer, or to be associated with the `permission` PDA (which is seeded only by `payer.key()`), any account holding a `Permission` grant can initialize a pool while binding `pool_creator` to an address it does not control and did not obtain consent for, or conversely to an address it does control while pretending the pool was created on behalf of someone else. This mirrors the authentik bug class: an identity-binding field that gates a privileged capability is attacker-settable without proof of ownership of the identity being bound.

By contrast, the permissionless `Initialize` instruction correctly requires `creator` to be a `Signer`: [5](#0-4) 

No later instruction updates `pool_creator` after pool creation (confirmed by searching for `pool_creator` across the codebase, which only appears in `pool.rs`, `collect_creator_fee.rs`, and `collect_creator_fee_permissionless.rs`), so the binding is fixed for the pool's lifetime once created this way.

### Impact Explanation
`PoolState.creator_fees_token_0` / `creator_fees_token_1` accumulate a real share of every swap's trading fee (see `pool_state.update_fees` calls in `swap_base_input.rs`/`swap_base_output.rs`), and are only claimable by whichever pubkey is stored in `pool_creator`. Since that field is unauthenticated at creation time in the permissioned path, the accounting for "who legitimately earned these fees" can be permanently misattributed to an address that never proved control of the intended creator identity — a fee-ledger/privileged-effect issue consistent with the required impact bar (unauthorized privileged effect over fee accounting), though the value at risk is limited to future creator-fee accrual on that specific pool rather than existing LP/user principal.

### Likelihood Explanation
Exploitation requires the attacker to hold (or collude with) a `Permission` grant that authorizes calling `initialize_with_permission`; it is not reachable by a fully anonymous swapper. Within that permissioned class of actor, the exploit is trivial — a single crafted transaction with an arbitrary `creator` pubkey and no additional signature requirement.

### Recommendation
Require `creator` to either be a `Signer`, or add an explicit constraint tying it to `payer`/the `permission` account (e.g., require `creator == payer.key()` unless a separate signed consent/PDA scheme is introduced to prove the designated creator authorized the binding).

### Proof of Concept
1. Attacker A obtains a `Permission` PDA (via `create_permission_pda`, assuming they are eligible for or otherwise hold such a grant).
2. Attacker A calls `initialize_with_permission`, funding the pool with `payer = A`, but sets `creator = B` (or `creator = A` when it was supposed to be a different pool sponsor), where `B` never signed and has no relation to `A` or the `permission` account.
3. `pool_state.initialize(...)` stores `pool_creator = B` unconditionally.
4. All subsequent creator fees generated by swaps against this pool can only be withdrawn by `B` via `collect_creator_fee`/`collect_creator_fee_permissionless`, regardless of who actually funded/operated the pool or was intended to receive those fees, since both instructions gate solely on `pool_state.pool_creator`.

**Note on confidence:** I was not able to find any post-creation "update creator" instruction, so the binding is set-once at creation rather than mutable afterward like the authentik `UserSourceConnection`. This makes the analogy directionally correct (unauthenticated identity-binding field gating a privileged capability) but weaker than the original "changeable after establishment" bug class — flagging this uncertainty explicitly since severity depends on how `initialize_with_permission`'s permissioned-actor trust model is intended to work, which is not fully documented in the code I could inspect.
