### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every handler acts on the independently-controlled `repository.full_name` field - allowing a webhook authenticated for one tenant organization to provision/deploy against another organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the inbound HMAC against based on `repository.owner.login` (or `organization.login`) taken straight out of the untrusted JSON body. Every webhook handler, however, resolves the actual `Repository`/`Stack` it operates on using a *different* field of that same body, `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing ties the organization whose secret validated the signature to the organization actually named in `repository.full_name`, so in a multi-tenant Shipit deployment (explicitly documented and supported via per-organization `webhook_secret`s) a party holding a valid secret for *their own* organization can forge a payload naming a *different* organization's repository in `full_name`, and have Shipit act on it as if GitHub had sent it.

### Finding Description
`verify_signature` picks the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to the `GithubApp` (and its `webhook_secret`) configured for whatever organization string appears in the payload's `repository.owner.login`/`organization.login`. Shipit explicitly supports configuring one distinct `webhook_secret` per organization for multi-org installs, as documented: [3](#0-2) 

Once the signature check passes, the raw JSON is dispatched to handlers `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [4](#0-3) 

Every handler determines the target `Repository`/`Stack` from a *separate* field, `repository.full_name`, with no re-check that its owner segment matches the organization used to validate the signature: [5](#0-4) 

This pattern repeats in every concrete handler (`PushHandler`, `OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `EditedHandler`, `AssignedHandler`): [6](#0-5) [7](#0-6) 

**Broken binding:** the engine implicitly assumes `organization-that-authenticated == organization-that-owns(repository.full_name)`, but never enforces this equality. Since `repository.owner.login` and `repository.full_name` are two independent JSON keys inside the same attacker-composed body, a party who legitimately possesses a `webhook_secret` for organization B (e.g., a tenant with their own GitHub App configured in this shared Shipit instance, per the multi-org setup docs) can HMAC-sign a body where `repository.owner.login = "OrgB"` (so `verify_signature` succeeds using OrgB's secret) while `repository.full_name = "OrgA/some-repo"` (so the handler acts on OrgA's tracked stacks/repositories). This is exactly the class of bug described in the report: two logically-linked values are treated as independently valid instead of being bound together, letting the "authenticated" identity diverge from the "acted-upon" resource.

Note: I was not able to fully trace `Shipit.github`'s organization-resolution/fallback logic in `lib/shipit.rb` in the time available (ran out of tool budget before reading it directly), so I cannot rule out an additional safeguard there; the analysis above is based on the webhook controller, handler base class, and the documented multi-org secrets configuration.

### Impact Explanation
For `PullRequest::OpenedHandler`, a successfully-authenticated-but-wrong-tenant payload drives `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, i.e., provisioning of a new review stack (and subsequent deploy) keyed off attacker-supplied `pull_request.head.sha` / `head.ref` for a repository the forging party does not own. `LabelCapturingHandler`/`UnlabeledHandler`/`ReopenedHandler` can archive/unarchive review stacks belonging to the other organization. `PushHandler` can force `GithubSyncJob`/deploy-spec resynchronization for another org's stack. This maps to the "Critical - unauthorized deploy" and "High - unauthenticated read/state manipulation of stack state" impact categories in scope, since the acting party never held credentials for the target organization/repository, only for their own.

### Likelihood Explanation
Exploitation requires the attacker to control one legitimate, distinct `webhook_secret` in a multi-organization Shipit deployment (a configuration Shipit's own docs describe as supported) — this is not privileged access to the *target* organization, matching the rules' definition of an unprivileged attacker relative to the victim org/repository. Single-organization deployments are not affected since there is only one secret to match against, but any deployment onboarding multiple GitHub organizations (as documented) is exposed.

### Recommendation
After signature verification succeeds, re-derive the organization from `repository.full_name` (the field actually used to select the target `Repository`/`Stack`) and reject the request (or re-verify) unless it equals the organization whose secret validated the signature. Equivalently, bind `repository_owner` used for `verify_signature` to be computed from the same `repository.full_name` field the handlers use, rather than from the independent `repository.owner.login`/`organization.login` fields, so the authenticated identity and the acted-upon resource can never diverge.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. As the operator/holder of `OrgB`'s `webhook_secret` (not privileged for `OrgA`), craft a `pull_request` "opened" webhook JSON body with:
   - `repository.owner.login = "OrgB"`
   - `repository.full_name = "OrgA/target-repo"`
   - `pull_request.head.sha` / `head.ref` pointing at an attacker-chosen ref/commit.
3. Compute `X-Hub-Signature` as `HMAC-SHA1(OrgB_webhook_secret, raw_body)` and POST to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgB")` and the signature validates successfully.
5. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler` resolves `repository` from `params.repository.full_name` ("OrgA/target-repo") and calls `ReviewStackAdapter#find_or_create!`, provisioning/deploying a review stack for `OrgA`'s repository at the attacker-chosen `head.sha`, despite the requester never authenticating as `OrgA`.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

          stacks
            .not_archived

        end

        private

          params.ref.gsub('refs/heads/', '')
        end
      end
