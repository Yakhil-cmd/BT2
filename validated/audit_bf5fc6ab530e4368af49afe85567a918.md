## Analysis

The Iron Bank bug class is: a security gate is enforced on one "leg" of a composite operation (the collateral market) but not on the semantically-equivalent other leg (the borrow market), because the code derives a single boolean flag from only part of the operation and uses it to decide which check to run, omitting the other.

Ocore has a structurally identical flaw in asset spend-condition enforcement.

### Root cause

In `validation.js`, `validatePayment()` determines whether a payment message is an "issue" message purely from its **first** input: [1](#0-0) 

Ocore's payment format explicitly allows a single payment message to combine **one issue input followed by transfer inputs** that spend previously-received/existing coins, as documented directly in the input-processing loop: [2](#0-1) 

At the end of `validatePaymentInputsAndOutputs()`, only one of the two conditions is ever evaluated, selected by that same message-level `bIssue` flag: [3](#0-2) 

Because `bIssue` reflects only whether the *first* input is an issue, a message that bundles an issue input (leg 1) with transfer inputs (leg 2) will have `issue_condition` evaluated for the whole message while `transfer_condition` is **never evaluated at all**, even though real value transfer of existing (potentially restricted) coins is happening in the same message. This exactly mirrors the Iron Bank pattern: check applied to one leg (`isMarketSeizable(mCollateral)`), omitted for the other (`mBorrow`), because a single flag governs an operation composed of two independently-restrictable legs.

### Exploitability

Asset definitions allow `transfer_condition` to be a strict, KYC/attestation-style gate while issuance is left open. `issued_by_definer_only` is only mandatory for capped assets: [4](#0-3) 

For an uncapped asset, `issued_by_definer_only` may be `false`, allowing **any** address to issue further units, and `issue_condition` can be entirely absent (in which case it's skipped with `if (!arrCondition) return cb();`): [5](#0-4) 

An attacker holding transfer-restricted coins of such an asset can therefore compose a single payment message with (a) a trivial self-issue input of 1 unit of the same asset and (b) transfer inputs spending their restricted held coins, sending outputs to any address they like. Since `bIssue` is true, only the (absent/trivial) `issue_condition` is checked, and the restrictive `transfer_condition` is never evaluated — unauthorized transfer of a spend-restricted asset.

### Title
Transfer Condition Bypass via Combined Issue+Transfer Inputs in a Single Payment Message - (File: `validation.js`)

### Summary
`validatePaymentInputsAndOutputs()` picks between evaluating `issue_condition` or `transfer_condition` using a single message-level flag `bIssue` derived only from the first input's type. Because ocore legally permits mixing one issue input with subsequent transfer inputs in the same payment message, this design lets an attacker skip the enforcement of `transfer_condition` on the transfer inputs entirely by attaching a trivial issue input to the message, as long as issuance for that asset is unrestricted or has no `issue_condition`.

### Finding Description
`validatePayment()` sets `var bIssue = (payload.inputs[0].type === "issue");` [1](#0-0)  based purely on the first input. The input-processing comment confirms multiple input "legs" (issue, then transfers, then hc/witnessing) are permitted within one message [2](#0-1) . At the end of the same function, only one condition — `bIssue ? objAsset.issue_condition : objAsset.transfer_condition` — is evaluated against the whole message [3](#0-2) . There is no per-input enforcement that checks `transfer_condition` for the transfer-type inputs when the message also happens to contain an issue input. This is analogous to `IronBank.liquidate()` checking `isMarketSeizable(mCollateral)` but never validating an equivalent pause condition for the debt leg — a single derived flag substitutes for independent validation of each leg of a composite operation.

### Impact Explanation
Any asset definer can (intentionally or not) create an asset with a restrictive `transfer_condition` (e.g., requiring attestor sign-off, whitelisting recipients, blocking certain senders) while leaving issuance open (`issued_by_definer_only:false`, uncapped, no `issue_condition`). Any holder of that asset's coins can bypass the transfer restriction entirely by attaching a self-issue input to the same payment message as their transfer inputs. This is concrete unauthorized spending / bypass of an intended asset-level spending restriction — value moves to addresses that the `transfer_condition` was designed to forbid, and it is reachable by any unprivileged unit poster holding the asset.

### Likelihood Explanation
This does not require any special privilege beyond being a normal holder of the asset. Issuing a token amount of an uncapped asset (with distinct `serial_number`) is a normal, always-available capability for anyone if `issued_by_definer_only` is `false`. Combining it with a transfer input in the same message is explicitly supported by the payment format's ordering rules ("issue must come first, then transfers"), so no unusual or unstable code path is required — this is a straightforward, low-cost bypass for any asset configured with open issuance plus a restrictive `transfer_condition`.

### Recommendation
Do not select a single condition for the whole message based on the first input's type. Instead:
- Evaluate `issue_condition` specifically against the issue input (if present), and independently evaluate `transfer_condition` against the transfer inputs whenever any transfer-type input exists in the message, regardless of whether an issue input is also present, or
- Disallow mixing issue and transfer inputs in the same message for any asset that defines a `transfer_condition` different in effect from its `issue_condition`.

### Proof of Concept
1. Definer creates asset `A`: `is_transferrable:true`, `issued_by_definer_only:false`, `cap` unset (uncapped), no `issue_condition`, and a strict `transfer_condition` (e.g., requiring the recipient to be attested).
2. Attacker holds coins of asset `A` obtained legitimately (or via an earlier compliant issue/transfer).
3. Attacker composes a single `payment` message for asset `A` with:
   - `inputs[0] = {type:"issue", amount:1, serial_number:<unused>}` (self-issue, legal since `issued_by_definer_only:false`)
   - `inputs[1..n]` = transfer inputs spending the attacker's existing restricted coins
   - outputs sending the combined amount to an arbitrary, non-attested address
4. In `validatePayment()`, `bIssue = true` (input[0] is issue). In `validatePaymentInputsAndOutputs()`, `arrCondition = objAsset.issue_condition` = `undefined`, so the condition check is skipped entirely (`if (!arrCondition) return cb();`), and `transfer_condition` is never evaluated for the transfer inputs.
5. The unit validates and is accepted, transferring the previously transfer-restricted coins to an address that `transfer_condition` was meant to block.
