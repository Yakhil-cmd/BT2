### Title
Pools can be created with freeze-authority-controlled ("blacklistable") mints, allowing permanent freezing of pool vaults and LP/swapper funds - (File: programs/cp-swap/src/utils/token.rs)

### Summary
`is_supported_mint` in `programs/cp-swap/src/utils/token.rs` (lines 335-360) is the sole gatekeeper used by `initialize` and `initialize_with_permission` to decide whether a mint is allowed to be used to create a pool. It unconditionally accepts any mint owned by the legacy `Token` program, and for Token-2022 mints it only inspects the extension list, checking against an allow-list of `TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, and `ScaledUiAmount`. It never inspects the base `Mint.freeze_authority` field, which exists in both the legacy SPL Token and Token-2022 mint layouts independent of any extension.

### Finding Description
A mint's `freeze_authority`, if set, allows that authority to call `FreezeAccount` on **any** token account for that mint — including the pool's own `token_0_vault`/`token_1_vault` accounts created in `create_token_account` ( [1](#0-0) ), and any user's associated token account used in `deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, `collect_creator_fee`, and `collect_creator_fee_permissionless`. This is exactly analogous to the referenced report's "weird ERC20" blacklist concern (e.g. USDT), except on Solana the mechanism is the SPL `freeze_authority`.

Because `is_supported_mint` never rejects mints with a non-null `freeze_authority`: [2](#0-1) 

Any pool creator (an unprivileged, permissionless actor calling `initialize` / `initialize_with_permission`) can create a pool using such a mint, and the mint's freeze authority (which could even be the pool creator itself, or a colluding party) can subsequently freeze the pool's vault token account at will.

### Impact Explanation
Once a vault token account for `token_0_vault` or `token_1_vault` is frozen:
- All `swap_base_input`/`swap_base_output` calls touching that vault fail permanently, since `transfer_from_user_to_pool_vault`/`transfer_from_pool_vault_to_user` ( [3](#0-2) ) invoke `transfer_checked`, which the SPL token program rejects on frozen accounts.
- `withdraw` calls that need to move tokens out of that vault fail permanently, permanently locking all LPs' underlying funds in the pool.
- `deposit` calls fail as well, though this mainly affects new depositors rather than existing fund safety.
- `collect_creator_fee` / `collect_creator_fee_permissionless` fail if the creator's own receiving token account (or a vault, indirectly) is frozen.

This results in permanent freezing of LP funds for any pool created with a freeze-authority-bearing mint, which is a concrete, high-impact accounting/freezing bug rather than a mere inconvenience — funds cannot be recovered through any code path in the program.

### Likelihood Explanation
Likelihood is realistic: pool creation via `initialize`/`initialize_with_permission` is permissionless and reachable by any user in a single transaction; nothing prevents a malicious or compromised token issuer (or a pool creator deliberately pairing their own token with a freeze authority they control) from later freezing the vault. This mirrors real-world tokens (e.g., many project tokens retain freeze authority for compliance reasons, similar to USDT's blacklist) that would be silently accepted by `is_supported_mint`.

### Recommendation
Extend `is_supported_mint` to unpack the base `Mint` state (via `StateWithExtensions::<spl_token_2022::state::Mint>::unpack` for Token-2022, and the analogous legacy `spl_token::state::Mint::unpack` for the legacy `Token` program) and reject any mint where `freeze_authority.is_some()`, in addition to the existing extension allow-list check.

### Proof of Concept
1. Create a legacy SPL Token mint `M` with a non-null `freeze_authority` set to attacker-controlled keypair `F`.
2. Call `initialize` (or `initialize_with_permission`) to create a pool with `token_0_mint = M`; `is_supported_mint` returns `Ok(true)` immediately because `*mint_info.owner == Token::id()` short-circuits the check ( [4](#0-3) ), and `token_0_vault` is created and funded normally ( [5](#0-4) , [6](#0-5) ).
3. From `F`, submit `FreezeAccount` (legacy SPL Token instruction) targeting `token_0_vault`.
4. Any subsequent `swap_base_input`, `swap_base_output`, `deposit`, or `withdraw` call touching `token_0_vault` fails at the `transfer_checked` CPI ( [7](#0-6) ), permanently locking all liquidity in that pool.

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
