### Title
Cross-organization webhook forgery via mismatched signature-verification key and repository-write target - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the same trust-binding-break pattern as the SwapUtils `withdrawAdminFees` bug: a value that governs the sensitive action (which `adminFees[i]` gets paid) is decoupled from the value that was actually validated/reset. In `shipit-engine`, the analogous binding is: **the GitHub organization whose secret authenticates the webhook** must equal **the repository the webhook payload is allowed to write to**. `WebhooksController` breaks this binding by selecting the verification key from an attacker-controlled field and then dispatching to handlers keyed off a *different* attacker-controlled field.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the webhook secret) using `repository_owner`, which is read straight out of the unverified JSON body: [1](#0-0) [2](#0-1) 

The actual repository/stack that gets written to, however, is derived independently in `Handler#repository_name`, from `payload.dig('repository', 'full_name')`: [3](#0-2) 

These are two separate JSON paths (`repository.owner.login` vs `repository.full_name`) that an attacker fully controls in the raw POST body. Signature verification is per-organization and, critically, is a no-op when that organization's `webhook_secret` is not configured: [4](#0-3) 

Multi-organization deployments are an explicitly supported and documented configuration shape (`test/dummy/config/secrets_double_github_app.yml` configures `OrgOne` and `OrgTwo` under one Shipit instance, with `OrgTwo`'s `webhook_secret` left `nil`). In that shape, `verify_webhook_signature` for `OrgTwo` always returns `true` regardless of the `X-Hub-Signature` header. An attacker can send a payload where `repository.owner.login = "OrgTwo"` (selects the always-passing verifier) but `repository.full_name = "OrgOne/some-protected-repo"` (the actual write target used by `PushHandler`/`stacks` lookup): [5](#0-4) 

`create` then dispatches the *same raw body* to handlers using the mismatched field, so the push is accepted and processed as if it came from `OrgOne`, even though only `OrgTwo`'s (non-)secret was checked: [6](#0-5) 

The equality that should hold is:
`organization authenticated (repository_owner used to select webhook_secret) == organization owning the repository actually written (repository.full_name used by Handler#stacks)`

Before the attacker's request, this equality holds only because in a single-org setup there's one webhook secret and `repository.owner.login`/`repository.full_name` describe the same repo. After the attacker's crafted request in a multi-org setup, the equality is broken: the org selected for signature-checking is not the org whose repository is mutated.

### Impact Explanation
This allows an unauthenticated remote attacker (no Shipit session, no `ApiClient` token, no knowledge of any real webhook secret) to forge `push`, `pull_request`, `status`, `check_suite`, or `membership` events for any repository/stack belonging to a *different, properly-secured* organization on the same Shipit instance, as long as at least one configured organization has no `webhook_secret` set (a state the docs/config templates explicitly show as a supported default — `webhook_secret: # nil`). Consequences include:
- Forged `push` events triggering `GithubSyncJob`/`sync_github` and thus deploy pipeline state changes for the target stack.
- Forged `status`/`check_suite` events manipulating commit deployability/merge status used to gate deploys.
- Forged `membership` events creating/removing `Team`/`Membership`/`User` records, which feed into `Shipit.github_teams` authorization checks.

This crosses the "unauthorized deploy/rollback" and "escalation into `Shipit.github_teams` authorization" impact bars defined in the rules, without requiring any credential the attacker doesn't already have (public knowledge that some org in the shared instance has no webhook secret, or simply guessing `organization`/`repository.owner.login` values that don't match a configured org — see `GithubOrganizationUnknown` handling for the negative case).

### Likelihood Explanation
Requires: (1) the operator to run Shipit with multiple GitHub organizations configured (a documented, supported configuration), and (2) at least one of those organizations to omit `webhook_secret` (also a documented default, `webhook_secret: # nil`, shown in `config/secrets.development.example.yml` and the multi-org fixture). Given both conditions, exploitation needs no privileged access at all — just a single unauthenticated HTTP POST to `/webhooks` (or engine-mounted equivalent) with a crafted JSON body and no valid `X-Hub-Signature`.

### Recommendation
Verify the webhook signature using the same field that determines which repository/stack the handlers will act on (`repository.full_name`'s owning organization), not a separately-read `repository.owner.login`/`organization.login` fallback. Concretely, derive `repository_owner` from the parsed, single source of truth for the target repository (e.g., split `repository.full_name`) so the org used to select the `webhook_secret` is provably the org whose repository is written, closing the gap the same way `withdrawAdminFees` was fixed by making the "amount charged" and "amount reset" operate on the same state.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. mirroring `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (has `webhook_secret`) and `OrgTwo` (`webhook_secret: nil`), both installed on the same Shipit instance, with a stack tracking `OrgOne/protected-repo`.
2. As an unauthenticated attacker, POST to the webhooks endpoint with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/protected-repo"
  }
}
```
No valid `X-Hub-Signature` header is needed.
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb` line 77).
4. `create` re-parses the same body and dispatches to `PushHandler`, which resolves `stacks` via `payload.dig('repository', 'full_name')` = `"OrgOne/protected-repo"`, triggering `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for a stack the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
