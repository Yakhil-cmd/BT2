### Title
Webhook signature verification binds the wrong organization to the acted-upon repository, allowing cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on `repository_owner`, but every webhook `Handler` resolves the actual target `Repository`/`Stack` to mutate from a *different* field in the same JSON body (`repository.full_name`). Because the signature only proves the request bytes were signed with *some* configured organization's secret — not that the organization matches the repository the handler will act on — a party who legitimately controls one onboarded organization's webhook secret can forge a payload that authenticates as their own org while acting on a repository belonging to a different organization.

### Finding Description
`verify_signature` computes the signing organization like this: [1](#0-0) 

and [2](#0-1) 

`repository_owner` is used solely to pick the `github_app`/secret via `Shipit.github(organization: repository_owner)`, which resolves a per-organization webhook secret configured on `Shipit::GithubApp`: [3](#0-2) [4](#0-3) 

Once the HMAC passes, `params` (the entire attacker-controlled JSON body) is dispatched unchanged to every registered handler: [5](#0-4) 

Every handler, however, resolves the repository/stack to act on from a *different* field of the same payload — `repository.full_name` — never re-checked against `repository_owner`: [6](#0-5) 

For example `PushHandler` uses that resolved stack set directly to trigger a GitHub sync: [7](#0-6) 

and `Repository.from_github_repo_name` does a straight DB lookup on the owner/name parsed out of `full_name`, with no relation back to which organization's secret validated the request: [8](#0-7) 

The broken trust binding is:
`organization whose secret authenticated the signature == organization that owns the repository the handler mutates`

This equality is never enforced. `repository_owner` (`repository.owner.login` / `organization.login`) and `repository.full_name` are independent, attacker-controlled JSON fields inside the same HMAC-signed body; nothing prevents them from referring to different repositories/organizations. A payload only needs to be internally self-consistent enough to pass each handler's `ExplicitParameters` schema — it does not need `repository.owner.login` and `repository.full_name`'s owner segment to match.

### Impact Explanation
Any organization already onboarded to a given Shipit instance (i.e., one entry in the multi-organization GitHub App/secret configuration resolved by `Shipit.github(organization:)`) can forge events that are processed as if they originated from a *different* onboarded organization's repository. Depending on which handler is targeted (e.g. `PushHandler` forcing `stack.sync_github(expected_head_sha:)` on another org's stack, or the `PullRequest::*Handler`s archiving/unarchiving/updating another org's review stacks and pull request state), this crosses the "cross-repository writes" / "unauthorized deploy or rollback" boundary called out as Critical impact, because state belonging to one repository's Shipit stack is mutated using credentials that were only ever proven valid for a different, unrelated organization.

### Likelihood Explanation
Exploitation requires the attacker to already hold a legitimate webhook secret for at least one organization configured in this Shipit instance — a realistic scenario in any multi-tenant/multi-org Shipit deployment, since that secret is provisioned per organization specifically so that organization's own webhook deliveries validate. No additional Shipit session, `ApiClient` token, or GitHub App private key is needed; the attacker only needs to be able to compute a valid HMAC over an arbitrary payload using their own org's secret, which by design they can do (they may even self-host a duplicate delivery or replay/tamper before it reaches Shipit if they control the origin).

### Recommendation
After signature verification, re-derive the owning organization from the same field the handlers actually act on (`repository.full_name` / `repository.owner.login`) and require it to match the organization whose secret validated the signature (`repository_owner` used in `verify_signature`). Reject the request (422) if they diverge, e.g. by moving the “owner” extraction into a single canonical method shared between `WebhooksController#verify_signature` and `Handler#repository_name`, and asserting equality before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two organizations, `org-attacker` and `org-victim`, each with its own onboarding entry and webhook secret registered via `Shipit.github(organization:)`.
2. Attacker (an admin of `org-attacker`, who legitimately knows `org-attacker`'s webhook secret) crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "org-attacker" },
       "full_name": "org-victim/target-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(org-attacker_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-attacker")`, verifies successfully against `org-attacker`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-victim/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim organization's stack — despite the request never being authenticated by anything belonging to `org-victim`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
