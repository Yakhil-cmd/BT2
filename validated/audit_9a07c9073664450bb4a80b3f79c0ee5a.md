### Title
Webhook signing-organization selected from unsigned payload field lets an attacker's own GitHub App forge sync events for a victim repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC `webhook_secret`) to validate the incoming delivery against by reading `repository_owner` straight out of the still-unauthenticated JSON body, then verifies the signature against that org's secret [1](#0-0) . Downstream event handlers separately re-read `repository.full_name` from the same unauthenticated body to decide which `Repository`/`Stack` to act on [2](#0-1) . Because the field used to pick the verification key (`repository.owner.login`) and the field used to pick the target repository (`repository.full_name`) are independent, unsigned fields in the same payload, a signature that is valid for one organization's secret can be replayed with a `repository.full_name` pointing at a stack belonging to a completely different organization.

### Finding Description
Shipit supports hosting multiple GitHub Apps, one per organization, each with its own `webhook_secret`, selected by `Shipit.github(organization: repository_owner)` per the documented "Using Multiple GitHub Applications" setup [3](#0-2) . The webhook signature check looks like this:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

The HMAC verification (`verify_webhook_signature`) checks that `X-Hub-Signature` matches `HMAC(webhook_secret_of_org_X, raw_post)` [5](#0-4) , which does mean the full raw body content is covered by the signature *for the org whose secret is used* — but the org itself is *chosen* by an unauthenticated field inside that same body. If an attacker controls their own GitHub organization/App (e.g., "OrgAttacker", legitimately configured in Shipit alongside a victim "OrgVictim" per the multi-app setup) they know OrgAttacker's `webhook_secret` and can compute a valid `X-Hub-Signature` for any payload they choose. They can then craft a payload where:
- `repository.owner.login` = `OrgAttacker` (so `verify_signature` selects OrgAttacker's app/secret, which the attacker signs correctly and verification passes), while
- `repository.full_name` = `OrgVictim/victim-repo` (so the event handler, which independently reads `repository.full_name`, resolves and acts on the victim's `Stack`).

The event dispatch in `WebhooksController#create` runs the same JSON body through the registered handler for `event` [6](#0-5) . `Handler#stacks` resolves the target purely from `payload.dig('repository', 'full_name')` [2](#0-1) , with no cross-check against `repository_owner` (the field actually used for authentication). For example `PushHandler#process` enqueues `stack.sync_github(expected_head_sha: params.after)` for every not-archived stack on the matching branch of that resolved repository [7](#0-6) , which in turn triggers `GithubSyncJob`, fetching commits from GitHub for the victim's stack and appending them, and can also trigger continuous delivery / merge-queue processing off the back of it.

This is the exact pattern called out in scope: "an organization that authenticated versus the repository that is written" — the binding `repository_owner (authenticated org) == repository.full_name (target of write)` is never enforced.

### Impact Explanation
This lets an attacker who controls only their own GitHub organization/App configured on the same Shipit instance (a normal, low-privilege scenario for any Shipit deployment supporting multiple orgs) force a `GithubSyncJob`/`RefreshCheckRunsJob`/`Hook.emit` style webhook-driven side effect to run against a victim organization's stack whose webhook secret they never possessed. Depending on which handler is targeted (`push`, `status`, `check_suite`, `membership`, `pull_request`), this can desynchronize commit history caching, spuriously advance/queue continuous delivery for a repo the attacker doesn't control, create bogus commit statuses/check-runs on a victim's commits, or manipulate `Team`/`Membership` records — an unauthorized write against a repository/stack the attacker's credentials were never authorized for. This qualifies as High: escalation into cross-organization/cross-repository state changes bypassing the per-organization webhook trust boundary.

### Likelihood Explanation
Requires only that Shipit is configured with more than one GitHub App/organization (a documented, supported configuration) and that the attacker has a legitimate but unrelated org/app registered on the same instance — no session, no `ApiClient` token, no repository write access to the victim repo, and no compromise of the victim's `webhook_secret` is needed. The attacker only needs to be able to POST to the public `/webhooks` endpoint, which is unauthenticated by design (it's how GitHub delivers webhooks).

### Recommendation
After selecting `github_app` from `repository_owner` and verifying the signature, re-derive the acted-upon repository/organization strictly from the same trusted `repository_owner` value (or explicitly assert `repository.full_name`'s owner segment matches `repository_owner`) before dispatching to handlers, e.g. in `WebhooksController#verify_signature` or in `Handler#repository_name`, reject the request if `payload.dig('repository','full_name')&.split('/')&.first != repository_owner`.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgVictim` (installed on the victim's real repo, secret unknown to attacker) and `OrgAttacker` (attacker's own org/app, secret known to attacker), per the documented multi-org config [3](#0-2) .
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC(OrgAttacker secret, raw_post)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner == "OrgAttacker"`, loads OrgAttacker's `github_app`, and the signature verifies successfully [8](#0-7) .
5. `Shipit::Webhooks.for_event('push')` runs `PushHandler` with the same payload; `Handler#stacks` resolves `Repository.from_github_repo_name("OrgVictim/victim-repo")` and finds the real victim `Stack` [2](#0-1) [7](#0-6) .
6. `stack.sync_github` enqueues `GithubSyncJob` for the victim stack with attacker-supplied `expected_head_sha`, even though the attacker never possessed OrgVictim's webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
