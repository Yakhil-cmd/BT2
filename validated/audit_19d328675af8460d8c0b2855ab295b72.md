### Title
Unbounded growth of per-address `aa_balances` rows enables DOS of an Autonomous Agent's trigger processing - (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `updateInitialAABalances` loads *every* asset ever credited to an AA address on *every* trigger invocation, and computes a diff against the newly-arriving assets. Because any unprivileged user can cheaply define a new asset and send a minimal amount of it to any AA address, the number of distinct `(address, asset)` rows in `aa_balances` for that address can be inflated without bound, making this per-trigger read/diff step grow linearly (or worse) with attacker-controlled state, mirroring the "any ERC20 token can be pushed into an unbounded array that is later iterated in critical paths" pattern from the referenced DODO V3 report.

### Finding Description
When a trigger unit is processed for a non-air (real) invocation, `handleTrigger` calls `updateInitialAABalances`: [1](#0-0) 
This function issues `SELECT asset, balance FROM aa_balances WHERE address=?` (no limit), iterates `rows.forEach` over **all** assets ever held by the address, and then computes `arrNewAssets = _.difference(arrAssets, arrExistingAssets)` against the full existing-assets list, for every single trigger — including tiny, unrelated triggers.

`aa_balances` uses `(address, asset)` as primary key and a new row is inserted whenever a payment of a previously-unseen asset arrives at that address: [2](#0-1) 

Crucially, nothing prevents an attacker from creating and sending new custom assets to a target AA:
- Defining a new asset via an `asset` message is cheap and unrestricted, gated only by generic complexity/format checks in `aa_validation.js` (`validatePayload` for `case 'asset'`), not by any cap on distinct-assets-per-address: [3](#0-2) 
- A single output of a tiny amount of the new asset sent to the victim AA address is enough to create a permanent row in `aa_balances` for that address the first time the AA is triggered while holding that output (via `insertAADefinitions`'s bulk insert, or via `updateInitialAABalances`'s `arrNewAssets` insert path shown above).

There is no cap analogous to `MAX_MESSAGES_PER_UNIT` or `MAX_PARENTS_PER_UNIT` on the number of distinct assets that can accumulate against a single address in `aa_balances`; each new asset costs the attacker only the price of an asset-definition unit plus a negligible payment output, both of which are far cheaper than the cumulative cost imposed on every subsequent trigger of the victim AA.

### Impact Explanation
Every future trigger of the targeted AA (not just those sent by the attacker) pays the cost of reading and diffing the entire, attacker-inflated asset list in `updateInitialAABalances`. As this list grows, the AA's response processing (which occurs synchronously as part of unit/DAG stabilization work) becomes progressively slower and more resource-intensive, which can lead to the AA becoming practically unusable or unable to respond in a timely fashion — a denial-of-service against the AA that freezes legitimate users' interactions with, and funds held in, that AA. This matches the "AA fund loss/freezing" and "network unable to confirm new units in a timely manner for that AA" criteria, since node operators processing that AA's triggers bear an ever-increasing per-trigger cost that legitimate senders did not create and cannot avoid.

### Likelihood Explanation
Likelihood is high in principle for any publicly known/valuable AA: the attack requires only the ability to (1) define new assets (unrestricted, cheap) and (2) send a minimal payment of each to the victim AA address — both are standard, permissionless actions available to any unit poster. No coordination with the AA owner or any privileged capability is required.

### Recommendation
- Cap the number of distinct assets a single address may hold in `aa_balances` (e.g., reject/ignore payments of new assets beyond a configurable limit, or require the AA to explicitly opt-in to accepting a given asset).
- Avoid loading the *entire* balance row set for the address on every trigger; instead look up only the balances relevant to `trigger.outputs`' assets (`SELECT asset, balance FROM aa_balances WHERE address=? AND asset IN (?)`), falling back to `INSERT ... ON CONFLICT/DUPLICATE` semantics rather than diffing full lists with `_.difference`.
- Consider charging a storage/rent fee proportional to the number of distinct assets held by an address, similar to `storage_size`, to disincentivize spamming new assets into `aa_balances`.

### Proof of Concept
1. Attacker composes and posts many `asset` messages (each defining a distinct new asset) — cheap, unrestricted per `aa_validation.js` asset-payload validation.
2. For each new asset, attacker sends a minimal-amount payment output to the target AA address; this is processed and inserted into `aa_balances` as shown in `aa_composer.js` (`arrNewAssets` insertion path, `aa_composer.js:515-524`) or `storage.js`'s `insertAADefinitions` bulk-insert query.
3. Repeat at scale (thousands of distinct assets) — the marginal cost per attacker-created asset is a small, fixed unit fee, independent of the growing burden imposed on the victim.
4. Any subsequent legitimate trigger to the victim AA now forces `updateInitialAABalances` (`aa_composer.js:491-524`) to `SELECT` and iterate the entire, attacker-inflated `aa_balances` row set for that address on every single invocation, degrading throughput/latency of that AA's processing over time.

Note: I was not able to fully verify within the available searches whether any global or per-address limit on distinct assets in `aa_balances` exists elsewhere in the codebase (e.g., enforced at the payment-validation layer rather than in `aa_composer.js`); if such a limit exists it would mitigate this finding, and a full repository read (beyond the indexed excerpts available here) would be needed to rule this out conclusively.
