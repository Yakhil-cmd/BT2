## Confirmed Analog

Found a valid analog: the webhook signature verification binds the HMAC secret to the `repository.owner.login` field, but every event handler (`StatusHandler`, `PushHandler`, etc.) routes and mutates state using the `repository.full_name` field — a separate, independently-controlled field inside the *same signed payload*. The Sherlock bug is "a validation check trivially passes because the check covers a smaller/wrong scope than what's acted upon"; here the analog is "the signature covers the raw body, but which secret validates it is selected by an attacker-influenced field (`owner.login`), while the actually-acted-upon field (`full_name`) is never cross-checked against that owner."

### Title
Webhook signature is validated against the organization named in the payload, not the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) read from the untrusted, attacker-supplied JSON body itself, then verifies the signature against the full raw body using that secret. Downstream handlers (e.g. `StatusHandler`, `PushHandler`) act on `repository.full_name`, a different field in that same body, with no re-validation that it belongs to the organization whose secret validated the signature.

### Finding Description
`verify_signature` does: [1](#0-0) 
using [2](#0-1) 
to pick the `github_app`/secret. `Shipit.github(organization:)` resolves per-organization secrets when the engine is configured for multiple GitHub organizations (documented in `config/secrets.development.example.yml`): [3](#0-2) 

Once verified, every handler derives the target repository/stack from `repository.full_name`, a wholly separate field in the same payload, not from `repository.owner.login`: [4](#0-3) 

`StatusHandler` then writes a commit status directly from attacker-controlled payload fields for any commit sha matching across the whole install: [5](#0-4) 

`PushHandler` similarly triggers a `GithubSyncJob` using `params.after` sha and the repository resolved from `full_name`: [6](#0-5) 

Because HMAC verification only proves "this body was signed with the secret belonging to whatever organization the body itself claims to be from," and no code ever checks that `full_name`'s owner matches `repository_owner`/the org whose secret validated, an operator of a multi-org Shipit deployment who legitimately controls their own org's GitHub App (and therefore knows their own `webhook_secret`) can forge a POST to `/webhooks` with `repository.owner.login` = their own org (so their own secret validates the signature) but `repository.full_name` = any other org/repo tracked by the same Shipit instance. The verified-signature binding ("this signature belongs to org A") is broken against the acted-upon binding ("this payload governs repo in org B").

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. An attacker with a legitimate but unrelated org's webhook secret can inject forged `status`/`check_suite`/`push` events for a stack belonging to a different, victim organization on the same Shipit instance: forging passing CI statuses (`StatusHandler#process` calls `commit.create_status_from_github!` unconditionally) can satisfy `required_statuses`/`ci.require` checks and unblock an otherwise-gated deploy or merge-queue merge — an unauthorized deploy/merge, matching the Critical impact bucket.

### Likelihood Explanation
Requires the engine to be configured for multiple GitHub organizations sharing one Shipit instance (a documented, supported configuration) and requires the attacker to control (own the webhook secret of) at least one of those organizations while targeting a stack belonging to another organization in the same instance. This is a realistic deployment pattern for shared/multi-tenant Shipit installs, and the request itself needs no authentication beyond knowing one's own configured secret.

### Recommendation
After verifying the HMAC signature, cross-check that the organization used to select the verifying secret (`repository_owner`) matches the owner encoded in `repository.full_name` (and in `organization.login` for org-scoped events) before dispatching to handlers; reject the webhook with 422 on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, `org-a` (attacker-controlled, secret known to attacker) and `org-b` (victim, tracks stack `org-b/app`).
2. Attacker builds a `status` webhook JSON body: `{"sha": "<victim commit sha>", "state": "success", "context": "ci/required", "repository": {"full_name": "org-b/app", "owner": {"login": "org-a"}}}`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and validates successfully since the attacker signed with `org-a`'s real secret.
5. `StatusHandler#process` finds the commit by `sha` (belonging to `org-b/app`) and creates a fabricated `success` status, independent of `org-a` at all — satisfying CI requirements for `org-b`'s deploy/merge pipeline.
