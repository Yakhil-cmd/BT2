### Title
Stack-scoped API token can read build/deploy status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates a caller-supplied `token` query-string parameter into an `ApiClient` and checks only the generic `read:stack` permission, but resolves the target stack directly from the URL parameter instead of through the client's stack scope, allowing a token that is authorized for exactly one stack to read status information for any stack in the installation.

### Finding Description
Shipit's `ApiClient` model supports scoping a token to a single stack via the `stack_id` column [1](#0-0) . `Shipit::Api::BaseController` enforces this scope by restricting the queryable stack collection whenever `current_api_client.stack_id?` is true, and every normal controller resolves the target stack through this scoped collection: [2](#0-1) 

`Shipit::CCMenuUrlController#client` creates exactly this kind of scoped, read-only token intended for a single stack's status feed (used by external CI-status tools such as CCMenu clients) and hands the token out embedded in a public URL: [3](#0-2) 

However, `Shipit::Api::CCMenuController` does not use the scoped `stacks`/`stack` helper from `BaseController`. It overrides `stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` restriction entirely, and it overrides `authenticate_api_client` to accept a bare `token` query parameter: [4](#0-3) 

The only permission check performed is `require_permission :read, :stack`, which merely checks that the string `"read:stack"` is present in `ApiClient#permissions` — it never compares the client's `stack_id` to the requested `stack_id`: [5](#0-4) 

The equality that should hold is:
`stack authorised by token (ApiClient#stack_id)` == `stack actually touched (params[:stack_id] resolved via Stack.from_param!)`

In `CCMenuController`, this equality is never enforced — any valid token with `read:stack` permission, regardless of its `stack_id`, can be replayed with a different `stack_id` in the URL to read another stack's data.

### Impact Explanation
This breaks the trust boundary between "stack a token authorises" and "stack it touches," one of the explicitly recognized binding classes for this engine. Because CCMenu tokens are specifically designed to be embedded in plaintext, externally-shared URLs (RSS/CI-status widgets), an attacker who obtains or is handed one such link (their own, legitimately-issued, single-stack, read-only token) can pivot it to read `deploys_and_rollbacks`, lock status, and stack name/state for every other stack hosted on the same Shipit instance — an unauthorized read of stack state across the deployment's full stack inventory, matching the High-impact category "unauthenticated/unauthorized read of stack state, task streams or deploy output."

### Likelihood Explanation
Likelihood is high for anyone who already has a legitimate, low-privilege CCMenu URL (a routine, intentionally-distributed artifact for any Shipit user watching any single stack). Exploitation requires no additional secrets, no elevated permissions, and no interaction with GitHub credentials — only changing the `stack_id` in an otherwise valid, already-possessed URL.

### Recommendation
Have `CCMenuController#stack` resolve through the same stack-scoping mechanism as `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) rather than `Stack.from_param!(params[:stack_id])` directly, so a stack-scoped `ApiClient` cannot address any stack other than the one it was issued for.

### Proof of Concept
1. As a normal user, visit `CCMenuUrlController#fetch` for `stack_id=stackA`; Shipit returns a URL containing `token=<T>`, where `T` is an `ApiClient` with `stack_id = stackA.id` and `permissions = ["read:stack"]` [6](#0-5) .
2. Call `GET /api/stacks/stackB/ccmenu.xml?token=<T>` (any other stack the token was never scoped to).
3. `authenticate_api_client` accepts `T` via `ApiClient.authenticate(params[:token])` [7](#0-6) ; `require_permission :read, :stack` passes because `T.permissions` includes `"read:stack"`; `stack` resolves `stackB` via unscoped `Stack.from_param!` [8](#0-7) .
4. The response renders `stackB`'s build/deploy status even though `T` was only ever authorised for `stackA`.
