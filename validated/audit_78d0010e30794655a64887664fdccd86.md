### Title
Stale oracle snapshot survives a flash-position callback governance transition - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary

`flash_position` resolves and caches the prices used by its final solvency gate before invoking the caller-selected receiver. The receiver can execute a ready governance operation that changes a price-aggregator configuration, after which the controller continues using the pre-callback oracle result rather than revalidating the position under the new oracle configuration.

### Finding Description

`process_flash_position` validates the requested collateral markets and calls `prefetch_strategy_prices` before minting debt and invoking `execute_flash_position`. [1](#0-0)  The price aggregator performs freshness, source-tolerance, and sanity-band validation when the prices are fetched. [2](#0-1) 

After the debt is minted and forwarded, the controller calls arbitrary code at the selected `receiver`. [3](#0-2)  A ready governance operation can be executed without privileged executor authorization, so receiver code can execute a scheduled price-aggregator operation while the flash-position callback is active. [4](#0-3) 

The controller context deliberately retains already-fetched prices, and `cached_price` later returns that old feed instead of querying the aggregator again. [5](#0-4)  Collateral and debt totals are calculated from these cached prices, including the health-factor decision. [6](#0-5) 

Consequently, a callback can change the oracle basis after the initial valid read but before the collateral deposit and final solvency gate at lines 145–154. [7](#0-6)  This is the same check-time/use-time separation as the reported destination-path race: the validated external condition is replaced before the dependent write is finalized. [8](#0-7) 

### Impact Explanation

An attacker can leave an account with debt that passed the final health-factor gate under the pre-callback oracle configuration but is undercollateralized under the oracle configuration activated during the callback. [9](#0-8)  Because `flash_position` mints debt before the callback and does not require that debt to be repaid within the callback, the receiver can retain the borrowed asset while the account remains responsible for the new debt. [10](#0-9) 

For example, if a scheduled governance operation reprices collateral `C` from 100 to 50, an attacker can receive collateral valued at 100 during the stale gate, borrow 70 units of dollar-valued debt, and leave an account whose post-transition LTV-weighted collateral is far below its debt. [11](#0-10)  Liquidators may seize the collateral, but the residual shortfall becomes bad debt, causing protocol insolvency or socialized supplier losses. [12](#0-11) 

### Likelihood Explanation

The attacker cannot create the governance change, but they only need to observe a ready oracle or sanity-band operation and invoke `flash_position` with a receiver that calls `execute` during the callback. [4](#0-3)  The receiver is explicitly caller-selected, and the only requirement is that it be a WASM contract distinct from the controller and pool. [13](#0-12) 

The attack window exists whenever a ready governance operation changes any price relevant to the caller's collateral or debt book and the resulting post-transition valuation would fail the normal solvency gate. [5](#0-4)  Since governance execution is permissionless when ready, this is an opportunistic but practical single-transaction path rather than a privileged parameter abuse. [4](#0-3) 

### Recommendation

Re-resolve all account and extra-asset prices after `invoke_receiver` returns, and run `strategy_finalize` against that fresh oracle snapshot rather than prices fetched before the callback. [7](#0-6)  This can be implemented by constructing a fresh pricing context for the final risk calculation or by versioning oracle configuration and requiring the version observed before the callback to remain unchanged.

More generally, do not reuse `Context::token_prices`, `market_indexes`, or spoke configuration across an arbitrary receiver callback unless the code proves that callback cannot alter the corresponding external state. [5](#0-4)  Equivalent post-callback refresh should be considered for other strategy paths that invoke the router before final risk checks. [14](#0-13) 

### Proof of Concept

1. Governance schedules an operation that will reduce collateral token `C`'s accepted oracle price from `P0` to `P1`; the operation enters its executable ready window. [4](#0-3) 
2. Attacker deploys a receiver implementing `execute_flash_position` that delivers `C` to the controller and, before returning, calls `governance.execute` for the ready operation. [15](#0-14) 
3. Attacker calls `controller.flash_position` with `account_id = 0`, the account's spoke, `mode = Multiply`, debt asset `D`, a nonzero `amount`, the malicious `receiver`, collateral list containing `(C, min)`, and an empty or valid refund list. [16](#0-15) 
4. Before the callback, `prefetch_strategy_prices` accepts `C = P0`, while `D` remains priced at one dollar. [17](#0-16) 
5. The controller mints `amount` of `D` to the account and forwards the measured tokens to the receiver. [10](#0-9) 
6. Inside `execute_flash_position`, the receiver executes the ready governance operation, changing `C`'s aggregator result to `P1`, then transfers enough `C` to satisfy the declared minimum. [3](#0-2) 
7. The controller deposits the measured `C`, but `Context::cached_price` still returns `P0`, so LTV coverage and health factor are evaluated under the stale oracle value. [5](#0-4) 
8. Choose `amount` so that `D < LTV(C) × C_amount × P0` but `D > LT(C) × C_amount × P1`; the transaction persists an apparently solvent account that is liquidatable or insolvent under the new oracle configuration. [11](#0-10) 
9. The receiver keeps the borrowed `D`; repayment or collateral delivery is limited to the declared collateral/refund deltas, and flash-position debt intentionally remains open after settlement. [18](#0-17)

```markdown
### INV-RISK-01 — Risk-increasing actions re-prove solvency

Ordinary borrowing, withdrawal and account strategies apply final solvency gates
after pool mutations. With debt remaining, LTV-weighted collateral must cover
debt, health factor must be at least one, and LTV-weighted collateral must meet
any nonzero configured floor. Debt-free accounts skip these numerical gates.

Listed LTV snapshots refresh before the shared gate. Listing and count checks
precede entry; spoke caps use returned pool deltas and revert the whole
transaction on failure. Supply, repayment and liquidation do not universally
apply this final gate.
```

```markdown
### INV-STRAT-04 — Flash position retains debt and supply

Flash position mints debt without an origination fee and never automatically
repays returned debt tokens. Every declared collateral minimum must be
non-negative, with at least one positive minimum. The controller measures
callback receipts against those minima, deposits positive receipts and
remeasures the pool's receipt.

Before and after account finalization, the borrowed market must retain positive
scaled debt and the account must retain supply. Returned debt becomes
collateral if declared, returns to the caller if refund-listed, or remains
uncredited if in neither list. Refunds cover only positive callback balance
changes.
```
