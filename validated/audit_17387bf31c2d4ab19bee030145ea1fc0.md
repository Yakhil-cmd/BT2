### Title
`StatusHandler` writes commit statuses without checking that the authenticated webhook organization owns the target commit's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate an inbound webhook based on `repository_owner`, taken from the payload's `repository.owner.login` (falling back to `organization.login`). This establishes an "authenticated organization" for the request. However, `Shipit::Webhooks::Handlers::StatusHandler`, which processes `status` events, never re-derives or checks that organization against the repository that owns the commit it mutates - it looks up commits globally by `sha` alone and writes a status to every matching `Commit` row in the database, regardless of which stack/repository that commit belongs to.

### Finding Description
The webhook entrypoint authenticates per-organization: [1](#0-0) 

`repository_owner` is read straight from attacker-influenced JSON: [2](#0-1) 

Once `verify_signature` succeeds for organization X (validated with X's own `webhook_secret`, see `Shipit::GitHubApp#verify_webhook_signature`), the full raw payload is handed to every handler registered for the event: [3](#0-2) 

Most handlers scope their side effects to the repository named in the payload via `Handler#stacks`/`Repository.from_github_repo_name`, e.g. `PushHandler`: [4](#0-3) [5](#0-4) 

`StatusHandler`, by contrast, performs **no repository/stack scoping at all** - it queries `Commit` globally by SHA and mutates whatever it finds: [6](#0-5) 

This breaks the intended binding: *"organization that authenticated" == "repository that is written."* The signature check proves the sender controls organization X's webhook secret, but `StatusHandler` writes to `Commit`/`Status` rows belonging to *any* stack whose commit history happens to contain a matching SHA - there is no check that the commit's `stack.repository` corresponds to `repository_owner`/`repository.full_name` from the same payload.

Writing a `Status` has real side effects beyond bookkeeping: it flips CI state, can enable CI on the stack, and can trigger continuous deployment/merge scheduling: [7](#0-6) [8](#0-7) 

### Impact Explanation
Because git commit SHAs are content-addressed, the same commit (and therefore the same SHA) commonly exists in more than one repository known to Shipit - forks, mirrors, or a staging/testing copy of a production repo, or simply repos that share history (e.g., a vendored subtree, monorepo split, or a repo an attacker forks specifically to obtain a shared ancestor commit). If Shipit's GitHub App is installed for multiple organizations (the codebase explicitly supports and tests a multi-org configuration, see `Shipit.github(organization:)` and `test/unit/shipit_test.rb`), an attacker who controls (or has push access to) any one such organization's repository can:
1. Trigger a legitimate, correctly-signed `status` webhook from their own organization (`repository_owner` = attacker's org, which correctly passes `verify_signature`).
2. Set `sha` in the payload to a commit SHA that is shared with, or otherwise present in, a victim stack's commit history.
3. Have `StatusHandler` write an attacker-chosen `state`/`context`/`description`/`target_url` onto the victim's `Commit`, because the lookup is `Commit.where(sha: params.sha)` with no organization/repository filter.

This can flip a victim stack's CI status to `success`, which (per `Commit#add_status`) can enable CI, mark the commit deployable, and — if the victim stack has `continuous_deployment` enabled — trigger an **unauthorized deploy** via `stack.schedule_merges`/continuous delivery scheduling. This satisfies the required High/Critical impact bar of "an unauthorized deploy" or "escalation into" stack state that should be repository-scoped, achieved purely by authenticating as an unrelated, unprivileged organization.

### Likelihood Explanation
Exploitation requires: (a) the attacker to have write/webhook-trigger capability on some GitHub organization/repository that Shipit's GitHub App is configured for (which can be as low-privilege as owning a personal fork/org that installs the same App, depending on deployment), and (b) a commit SHA that is present in both the attacker's repo and the victim stack's commit history. Shared history is realistic in fork-based/mirrored workflows, which are common in the kind of continuous-delivery setups Shipit targets. No secret material for the victim's organization is required at any point - only the attacker's own legitimately-obtained webhook credentials.

### Recommendation
`StatusHandler` (and any other handler that does not scope through `Handler#stacks`) must verify that the `sha` being updated belongs to a commit whose `stack.repository` matches the `repository.full_name`/`repository_owner` asserted (and cryptographically authenticated) in the same payload, e.g. by joining through `stacks` (as `PushHandler` does) instead of doing an unscoped `Commit.where(sha: ...)`. More generally, the webhook layer should carry the authenticated organization/repository forward and have every handler assert equality between "organization that authenticated" and "repository whose data is mutated" before writing.

### Proof of Concept
1. Configure/attacker controls GitHub organization `attacker-org`, which has Shipit's GitHub App installed with its own valid `webhook_secret` (multi-org configuration is explicitly supported: `test/unit/shipit_test.rb` lines 11-22 show `Shipit.github(organization: ...)` resolving distinct apps/secrets per org).
2. Attacker identifies (or engineers, e.g. via a fork sharing history) a commit SHA `S` that is also present in `victim-org/victim-repo`'s Shipit-tracked stack, where `continuous_deployment: true`.
3. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<valid HMAC computed with attacker-org's webhook_secret>
{
  "sha": "S",
  "state": "success",
  "context": "ci/attacker",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates the signature successfully (it is a genuine signature from a genuine, but unrelated, org).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which executes `Commit.where(sha: 'S').each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-23`) - matching and mutating the victim stack's `Commit` record with no check against `attacker-org`.
6. Per `Commit#add_status` (`app/models/shipit/commit.rb:366-386`), the new `success` status can mark the commit deployable and invoke `stack.schedule_merges`, potentially triggering deployment of `victim-org/victim-repo` on the strength of a forged status the attacker fully controls.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
