### Title
Cross-organization webhook forgery via organization/repository binding confusion - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload against using only the top-level `repository.owner.login` (or `organization.login`) field, then HMAC-verifies the *entire* raw body against that secret. Every downstream webhook handler, however, resolves the target `Repository`/`Stack` from a different, independently-parsed field: `repository.full_name`. Nothing ties the organization used to pick/verify the secret to the organization embedded in `full_name`. In a multi-organization Shipit deployment (each org configured with its own `webhook_secret`, as documented), an attacker who legitimately administers one onboarded organization can craft a payload whose `owner.login` names their own org (so their own known secret passes verification) while `full_name` names a stack belonging to a different, victim organization — forging events (pushes, statuses, pull-request actions) against a repository they do not control.

### Finding Description
`verify_signature` picks the app/secret purely from the owner login: [1](#0-0) [2](#0-1) 

It verifies the signature via `Shipit.github(organization: repository_owner).verify_webhook_signature`, which performs a straightforward HMAC compare of the raw body against that organization's configured `webhook_secret`: [3](#0-2) 

Shipit explicitly supports per-organization GitHub Apps, each with its own independent `webhook_secret`: [4](#0-3) 

Once the signature check passes, every handler ignores `repository_owner` entirely and instead re-derives the target repository from `repository.full_name`, a sibling JSON field inside the same signed payload: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` independently to find owner/name, with no cross-check against the organization that was used to authenticate the request: [7](#0-6) 

Because the HMAC covers the raw bytes and not a structured/bound claim ("this signature is only valid for events where owner == full_name's owner"), the only real security guarantee is "whoever crafted this exact byte string knows organization X's secret." Nothing enforces that the repository/stack being mutated by the handler must belong to organization X. This is the same class of bug as the Frankencoin finding: a value used to satisfy a check (the organization used to authenticate) is decoupled from the value actually acted upon (the repository the handler resolves and mutates), and an attacker who legitimately controls one side of the binding (their own org's secret) can steer the other side (an arbitrary `full_name`) to a resource outside their authorization.

### Impact Explanation
An attacker who administers or controls webhook delivery for one org onboarded into a multi-tenant Shipit instance (i.e., knows that org's `webhook_secret`) can forge signed webhook deliveries whose `repository.full_name` points at a *different* org/repo's stack. This lets them:
- Trigger `GithubSyncJob` for a victim stack with an attacker-chosen `stack_id`/`expected_head_sha`.
- Fabricate CI `status` payloads against a victim's commits.
- Trigger PR-lifecycle handlers (`opened`, `labeled`, etc.) that create/manipulate review stacks for a victim repository.

This crosses a repository boundary using credentials scoped to a different organization, matching the "cross-repository writes" / stack-state-manipulation impact class called out as in-scope.

### Likelihood Explanation
Requires the deployment to be configured with multiple GitHub organizations/Apps (a documented, supported configuration) and requires the attacker to control webhook delivery/secret for at least one onboarded org — a realistic scenario for a shared, multi-tenant Shipit instance where different teams/orgs each maintain their own GitHub App registration. No privileged Shipit session, `ApiClient` token, or GitHub App private key is needed — only knowledge of one org's `webhook_secret`, which that org's own admins legitimately possess.

### Recommendation
Bind the two identity checks together: after computing `repository_owner` for secret selection, require that `repository.full_name` (and `organization.login`, if present) start with that same owner before dispatching to any handler, rejecting (422) on mismatch. This closes the gap between "who authenticated" and "what gets written," analogous to the recommended slippage/expected-price check in the referenced report.

### Proof of Concept
1. Shipit is configured with two orgs, `org-a` (attacker-administered, secret known to attacker) and `org-b` (victim, has a Shipit stack `org-b/app`).
2. Attacker crafts a `push` webhook JSON body with `repository.owner.login = "org-a"` but `repository.full_name = "org-b/app"` and `ref = "refs/heads/master"`.
3. Attacker signs the raw body with `org-a`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, then POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the HMAC against `org-a`'s secret — passes.
5. The push handler resolves `stacks` via `Repository.from_github_repo_name("org-b/app")`, locating the victim's real stack, and enqueues sync/deploy-relevant jobs for it — despite the request only being authenticated for `org-a`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
