### Title
`StatusHandler#process` mutates `Commit` records across repositories using only `params.sha`, without verifying `repository.full_name` ownership - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits globally by `sha` and calls `commit.create_status_from_github!(params)` on every match, without ever consulting `Handler#stacks` (which scopes by `repository.full_name`). `verify_signature` only proves the payload was signed by the `webhook_secret` of the repository *named* in the payload, not that the `sha` field actually belongs to that repository, so any repo owner can push a status update for a commit sha belonging to a different stack.

### Finding Description
The broken binding: the code requires `repository.full_name (payload) == Repository owning Commit.stack (mutated)`, but no code enforces this equality.

`app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Compare with sibling handlers, which correctly scope through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` (i.e. `payload.dig('repository', 'full_name')`) before touching any commit:

`app/models/shipit/webhooks/handlers/handler.rb`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`app/models/shipit/webhooks/handlers/check_suite_handler.rb`:
```ruby
def process
  stacks.where(branch: params.check_suite.head_branch).each do |stack|
    stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
  end
end
``` [3](#0-2) 

`app/models/shipit/webhooks/handlers/push_handler.rb`:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

Both siblings call `stacks`, restricting the query to the stacks belonging to the repository actually named (and cryptographically verified) in the payload. `StatusHandler` skips this entirely and queries `Commit` unscoped by repository or stack.

Signature verification only authenticates that the request was signed with the `webhook_secret` of the repository named in `payload['repository']['full_name']` / `payload['repository']['owner']['login']`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [5](#0-4) 

This proves the request genuinely came from the named repository owner — it does **not** prove anything about the `sha` field's ownership. `sha` is attacker-controlled free text in the JSON body; `ExplicitParameters` only requires it to be a `String`:
```ruby
params do
  requires :sha, String
  requires :state, String
  ...
end
``` [6](#0-5) 

Exploit flow: attacker owns Repo A and controls its `webhook_secret`. Attacker copies a commit `sha` from Victim's public Repo B (already tracked as a `Commit` row in Shipit because Repo B is a monitored stack). Attacker sends `POST /webhooks` with `X-Github-Event: status`, `repository.full_name = "attacker/repoA"`, correctly signed with Repo A's secret, and `sha` set to the victim commit's sha. `verify_signature` passes because the signature matches Repo A's secret. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, finds the victim's `Commit` row (belonging to Repo B's stack), and calls `create_status_from_github!(params)` on it, which calls `add_status` and can flip `previous_status`/`new_status`, trigger `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` — i.e., influence deploy-gating CI status for Victim's stack.

None of the existing guards catch this: `verify_signature` authenticates the claimed repo, not the sha's owner; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema only checks types/presence, not cross-record ownership; `stacks`/`repository_name` scoping exists in `Handler` but `StatusHandler#process` never calls it.

### Impact Explanation
An attacker who owns any GitHub repository configured in Shipit (and thus its own legitimate `webhook_secret`) can write a fabricated CI status onto any `Commit` record in the database whose `sha` they can observe (e.g., from a victim's public repository history), regardless of which stack/repository that commit belongs to. This can flip a commit from failing to "success," triggering `stack.schedule_merges` and continuous-delivery evaluation (`schedule_continuous_delivery`) for a stack the attacker never authenticated against — a cross-tenant record write for a repository that did not authenticate the request, matching the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable per known sha and scales to any repository/commit already tracked by Shipit.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (a) any Shipit-registered repository they own (to get a valid `webhook_secret` and pass `verify_signature`), and (b) a `sha` that already exists as a `Commit` row for some other stack (trivially obtainable from any public repo history already synced into Shipit via push events). No GitHub App private key, no `api_clients_secret`, no session, and no team membership are required. This is inexpensive and fully repeatable via direct HTTP POST to `/webhooks`.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through `stacks` (as `CheckSuiteHandler` and `PushHandler` do) instead of a bare `Commit.where(sha: ...)`, e.g. `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }`, so that only commits belonging to the repository verified in the payload can be mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process never scopes via Handler#stacks, mutating a commit from a different repository/stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  Shipit::Webhooks::Handlers::Handler.any_instance.expects(:stacks).never

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/repoA' } # repo the attacker owns/signed with
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_equal 'success', victim_commit.status.state,
    "Attacker-signed webhook for their own repo mutated a Commit belonging to a different repository's stack"
end
```
This proves both sides of the equality diverge: `payload['repository']['full_name']` (`attacker/repoA`) never equals the repository owning `victim_commit.stack` (`shipit/shipit`), yet the mutation still succeeds without `stacks` ever being consulted.
