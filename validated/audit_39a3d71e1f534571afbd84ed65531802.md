### Title
Cross-organization team-membership write via unsigned `Team#organization` binding in `find_or_create_by!` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)` and only sets `team.organization` inside the create block, so when a row with that `github_id` already exists, the existing team's `organization` is left untouched while the handler still calls `team.add_member(member)` on it. Because `WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to verify against using `organization.login` from the payload (not `Team#organization` on the DB row), an attacker who owns any org enrolled in Shipit can sign a `membership` webhook with their own org's secret, set `organization.login` to their own org, but set `team.id` to the `github_id` of a victim org's existing `Team` row, and thereby add an arbitrary attacker-controlled user to that victim team's membership.

### Finding Description
Binding claimed: `Team#organization` (the value recorded on the mutated row) == the organization whose `webhook_secret` verified the webhook that performed the mutation.

Code path:
- `WebhooksController#verify_signature` derives `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then verifies the signature using `Shipit.github(organization: repository_owner)` [2](#0-1) . For a `membership` event there is no `repository` key, so this becomes `params.organization.login` — fully attacker-controlled and equal to the attacker's own org, whose `webhook_secret` they legitimately know.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; ... }` [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g., a victim org's team previously synced into Shipit), the block does not execute, so `organization` stays as the victim org's value.
- `#process` still calls `team.add_member(member)` [4](#0-3) , and `Team#add_member` unconditionally appends the membership [5](#0-4) .
- `member` is derived from `User.find_or_create_by_login!(params.member.login)`, an attacker-supplied login string that the handler never checks for membership in the claimed organization [6](#0-5) .

None of the existing guards prevent this: `verify_signature` validates that a signature matches *an* org's secret, not that the org matches the `Team` row being mutated; the `ExplicitParameters` schema only checks types/presence, not cross-record consistency; `drop_unhandled_event` and `check_if_ping` are irrelevant.

### Impact Explanation
An attacker who controls one org enrolled in `Shipit.github_teams`' backing config (i.e., has a valid `GitHubApp` webhook_secret configured for their own org) can inject membership rows into a `Team` belonging to a *different, unrelated* org, provided they know or guess that team's GitHub team `github_id` (an integer, often enumerable/predictable and not secret). If that target team is one of the teams listed in `Shipit.github_teams`, the attacker gains the ability to grant `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [7](#0-6)  to an arbitrary GitHub login, i.e., escalation into a privileged Shipit authorization group belonging to an org they do not control. This matches "escalation into `Shipit.github_teams` authorization" (High), and could reach Critical if that authorization directly gates deploys/merges in the target org's stacks.

### Likelihood Explanation
Preconditions required: (1) the attacker controls at least one org already configured in Shipit's `github` app config (so they know a valid `webhook_secret`), (2) a `Team` row for the victim org already exists in Shipit's DB with a known/guessable `github_id`, and (3) that team is part of `Shipit.github_teams`. Given these, the exploit is a single crafted HTTP POST to `/webhooks` with a valid HMAC signature computed with the attacker's own secret — no privileged credentials of the victim are needed. This is repeatable per victim team (`removed`/`added` both work) and does not require live GitHub access to reproduce in tests, since `verify_webhook_signature` only checks the HMAC against the configured `webhook_secret` for the resolved org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, do not blindly trust an existing `Team` row matched by `github_id` alone; verify/enforce that `params.organization.login` matches the row's `organization` for both create and update paths (e.g., use `find_or_initialize_by(github_id:, organization: params.organization.login)` and raise/reject on mismatch, or explicitly check `team.organization == params.organization.login` before calling `add_member`/`members.delete`). More generally, `github_id` should be scoped/unique per organization rather than global, since GitHub team IDs from different verified orgs must not be conflated into the same row when they collide or are spoofed.

### Proof of Concept
Minitest plan (webhooks controller/handler level, no live GitHub):
1. Configure two orgs in test secrets, `victim-org` and `attacker-org`, each with a distinct `webhook_secret` (already supported per `test/dummy/config/secrets_double_github_app.yml`).
2. Seed `team = Shipit::Team.create!(github_id: 42, organization: 'victim-org', slug: 'core', name: 'Core')`.
3. Build a `membership` webhook payload: `{ action: 'added', team: { id: 42, name: 'Core', slug: 'core', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'evil-user' } }`.
4. Sign the raw JSON body with `attacker-org`'s `webhook_secret` and POST to `/webhooks` with header `X-Github-Event: membership` and correct `X-Hub-Signature`.
5. Assert response is `200 OK` (signature accepted).
6. Reload `team` and assert `team.organization == 'victim-org'` (unchanged — binding still broken).
7. Assert `Shipit::Membership.count` increased by 1 and `team.members.pluck(:login)` includes `'evil-user'`, proving a webhook verified under `attacker-org`'s secret mutated a team scoped to `victim-org`.
