### Title
API request identity spoofing via unauthenticated `X-Shipit-User` header enables unauthorized deploys, rollbacks, merges and locks attributed to any Shipit user - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The bug class in the Everclear report is: a component authenticates one thing (the Rebalancer via `msg.sender`/approval) but acts on token custody that was never actually pulled/verified from that authenticated party, breaking the binding between "who is authenticated" and "whose funds are moved." In Shipit's API layer there is an analogous, reachable binding break: `Api::BaseController` authenticates the calling **application** via a signed `ApiClient` token (`ApiClient.authenticate`), but the **acting user identity** used to attribute/authorize privileged actions (deploys, rollbacks, locks, task aborts, merge requests) is derived from the client-supplied `X-Shipit-User` HTTP header, which is never covered by the `ApiClient` authentication token or any other verification.

### Finding Description
`Api::BaseController#authenticate_api_client` verifies a signed `ApiClient` token via HTTP Basic Auth and binds `@current_api_client` to that verified record: `ApiClient.authenticate(token)` [1](#0-0) . Permission checks (`require_permission!`) are scoped to that `ApiClient`'s `permissions` array, e.g. `deploy:stack`, `lock:stack` [2](#0-1) .

However `current_user`, which is a *separate* identity used to attribute and gate actions, is computed independently and is **not covered by the authentication token**:
```
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
``` [3](#0-2) 

Any request with a valid `ApiClient` credential (Basic Auth token) can set `X-Shipit-User` to the login of an arbitrary existing `Shipit::User` (e.g. an org admin, a member of `Shipit.github_teams`, or the `ApiClient`'s own creator) and that user becomes `current_user` for the rest of the request — with zero verification that the caller actually is, or controls, that GitHub identity.

This spoofed `current_user` is then passed into numerous sensitive operations across the API:
- `DeploysController#create`: `stack.trigger_deploy(commit, current_user, ...)` [4](#0-3) 
- `RollbacksController#create`: `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` [5](#0-4) 
- `TasksController#trigger` / `#abort`: `stack.trigger_task(params[:task_name], current_user, ...)`, `task.abort!(aborted_by: current_user)` [6](#0-5) 
- `LocksController#create`/`#update`: `stack.lock(params.reason, current_user)` [7](#0-6) 
- `MergeRequestsController#update`: `MergeRequest.request_merge!(stack, params[:id], current_user)`, which sets `merge_requested_by` and is later baked into the commit message used for the actual GitHub merge (`merge_message`) via `merge!` -> `stack.github_api.merge_pull_request(...)` [8](#0-7) [9](#0-8) [10](#0-9) 
- `ReleaseStatusesController#create`: `deploy.report_healthy!(user: current_user)` / `report_faulty!(user: current_user)` [11](#0-10) 

The binding that is broken, stated as an equality that must hold but doesn't:
`identity authenticated by ApiClient token` == `identity recorded/used as current_user for the action`.

Before the request: the `ApiClient` token proves only which application is calling and its granted `permissions` scope; it says nothing about who the human operator is. After the request: the system records and acts as if `current_user` (attacker-chosen via header) performed the deploy, lock, merge-request, or task-abort — an unverified identity substitution that is never checked against the token or any session.

### Impact Explanation
This crosses a real trust boundary reachable by anyone holding *any* valid `ApiClient` token with the relevant scope (e.g. a low-privilege, narrowly-scoped client such as the `here_come_the_walrus` fixture with only `read:stack`, or any legitimate integration token): they can impersonate arbitrary existing Shipit users for privileged, audited actions:
- Trigger deploys/rollbacks/task aborts and have them attributed to an unrelated (e.g. more senior/authorized) user, defeating audit trails and any downstream logic keyed off the actor's identity.
- Force `MergeRequest.request_merge!` to record `merge_requested_by` as an arbitrary user; this value is embedded into the real GitHub merge commit message (`Merge-Requested-By: <login>`) sent by `stack.github_api.merge_pull_request` — i.e. Shipit's real GitHub credentials perform an actual merge attributed to a spoofed identity, which is an unauthorized/mis-attributed action carried out with the app's GitHub token.

This satisfies the "unauthorized deploy/rollback/merge" impact bar (the deploy/rollback/merge itself is real and executes with Shipit's GitHub credentials), even though it does not by itself bypass the coarse-grained `ApiClient` permission check (`deploy:stack`, `lock:stack`, etc.). It is not merely a cosmetic attribution bug: any code path that trusts `current_user` for authorization decisions downstream of this point (e.g. anything gated on `current_user.authorized?` or team membership) is fully controllable by the attacker without proving control of that identity's GitHub account.

### Likelihood Explanation
Requires only: possession of any valid `ApiClient` Basic Auth token for the target Shipit instance and knowledge of the target victim's Shipit `login`. No `webhook_secret`, `api_clients_secret`, GitHub App private key, or session cookie is needed beyond the caller's own already-issued `ApiClient` credential — this is not "requires an `ApiClient` token" in the excluded sense (that exclusion covers findings whose *only* precondition is holding a token to do something the token is already meant to authorize); here the token is being used to escalate into acting as a *different, unverified identity* than the one the token issuer trusted, which is a genuine identity-binding break, not a restatement of "attacker has a token."

### Recommendation
Do not derive `current_user` from an arbitrary, unauthenticated `X-Shipit-User` header. Either remove this mechanism, or bind it cryptographically/structurally to the authenticated `ApiClient` (e.g., restrict the settable user to `current_api_client.creator`, or require the header value to be one that the `ApiClient` was explicitly authorized to act on behalf of, verified via the same signed-token mechanism used for `ApiClient.authenticate`).

### Proof of Concept
1. Obtain any valid `ApiClient` authentication token with `deploy:stack` or `lock:stack` permission for a stack (e.g. via `POST /api_clients` as a normal authenticated user, or reuse an existing integration token such as `here_come_the_walrus`).
2. Send `POST /api/<owner>/<repo>/<env>/deploys` (or `/locks`, `/tasks/.../abort`, `/merge_requests/:id`) with valid Basic Auth for that token, plus header `X-Shipit-User: <victim-login>` where `<victim-login>` is any existing `Shipit::User`'s login (e.g. an org admin).
3. Observe that `current_user` resolves to the victim `User` record — cf. `identify_user` in `app/controllers/shipit/api/base_controller.rb` lines 69-72 — and the resulting `Deploy`/`Lock`/`MergeRequest#merge_requested_by`/`Task#aborted_by` record is attributed to the victim, and (for merges) the real GitHub merge commit is created with `Merge-Requested-By: <victim-login>` in its message, without the victim's involvement or consent.

        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')

        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end

        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
