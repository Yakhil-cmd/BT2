### Title
Missing CPI permission-check case for the Loader-v4 program allows unprivileged cross-program invocation into loader management instructions - (File: program-runtime/src/cpi.rs)

### Summary
`check_authorized_program()` in `program-runtime/src/cpi.rs` is the CPI permission gate that blocks a program from invoking privileged loader/precompile programs via `sol_invoke_signed`. It explicitly denies CPI to `native_loader`, `bpf_loader`, `bpf_loader_deprecated`, and (conditionally) `bpf_loader_upgradeable`, and to precompiles, but it has no case at all for `loader_v4` (`solana_sdk_ids::loader_v4`). [1](#0-0) 

### Finding Description
`check_authorized_program` is called on every CPI (`invoke`/`invoke_signed`) before the callee instruction is dispatched: [2](#0-1) 

Its allow/deny logic only special-cases four program IDs plus precompiles:
```
native_loader::check_id(program_id)
|| bpf_loader::check_id(program_id)
|| bpf_loader_deprecated::check_id(program_id)
|| (bpf_loader_upgradeable::check_id(program_id) && !(...allowed sub-instructions...))
|| invoke_context.is_precompile(program_id)
``` [3](#0-2) 

`loader_v4` is a fully active, independent loader in this codebase — it is recognized as a valid executable-account owner in `process_executable_chain` alongside the other three loaders, and the program loader (`svm/src/program_loader.rs`) has first-class handling for `ProgramOfLoaderV4` accounts (state, status, deployment slot, etc.): [4](#0-3) [5](#0-4) 

Because `check_authorized_program` has no `loader_v4::check_id(program_id)` branch, any unprivileged BPF program can CPI directly into the `loader_v4` program ID and invoke its management instructions (deploy/retract/finalize/transfer-authority/set-program-length) as a nested instruction, something the other three loaders are explicitly barred from (with only narrow, deliberate exceptions carved out for `bpf_loader_upgradeable`). This is a missing-case bug in a permission/allow-list check — structurally the same bug class as CVE-2019-5778, where a scheme/case was omitted from an extension permission check, letting an attacker-controlled caller reach a privileged code path that the check was meant to block.

The other loaders are blocked from CPI specifically because mutating a program's own executable state (upgrade, close, set authority) while that program is present on the current call stack is dangerous: it can change code/state backing an account that's mid-execution, invalidate cached program entries, or violate invariants the program cache relies on (the `ProgramCacheEntry` state machine has `debug_assert!`s that panic on "unexpected replacement of an entry" for illegal state transitions, as seen in program-cache tests for Loader-v4/v3 tombstone transitions). [6](#0-5) [7](#0-6) 

Because `loader_v4` is missing from `check_authorized_program`, a malicious program can trivially reach these same illegal-transition paths via CPI (e.g., retracting/redeploying/finalizing a Loader-v4 program while it is present on the instruction stack), something that top-level-instruction-only loaders were designed to prevent.

### Impact Explanation
If Loader-v4 program-management instructions (deploy/retract/finalize/set-authority) are reachable via CPI while the target program is on the call stack, this can:
- Drive the program cache/state machine into transitions it assumes are impossible (the debug-mode `debug_assert!("Unexpected replacement of an entry")` panics demonstrate the invariant exists and is relied upon), which in release builds risks corrupting `ProgramCacheEntry` bookkeeping used identically by every validator — a potential consensus-divergence or transaction-triggered node panic depending on build config and downstream handling.
- Allow a program to alter/retract its own (or another's) executable definition mid-instruction, undermining the "closed for reentrant mutation" guarantee that the CPI allow-list is designed to enforce for every other loader.

This qualifies as a transaction-triggered path toward CPI privilege/invariant violation and possible cluster-wide non-determinism, matching the accepted analog classes (CPI privilege escalation / consensus divergence / transaction-triggered halt).

### Likelihood Explanation
Likelihood is High for reachability: `loader_v4::id()` is a well-known, unauthenticated program ID; any BPF program can construct an `Instruction` targeting it and call `invoke`/`invoke_signed` — no elevated privileges are required, and the omission is a simple, unconditional missing branch (not gated by a feature flag). I was not able to locate the Loader-v4 instruction-processor source in this index (the `programs/loader-v4/**` search returned no results, and `svm/src/program_loader.rs` contains a comment noting the "now-removed Loader V4 program library"), so I could not fully confirm the exact runtime consequence (panic vs. `InstructionError`) of calling each Loader-v4 sub-instruction via CPI in this specific snapshot of the repo. This is a genuine gap in my verification — a full assessment requires reading the Loader-v4 builtin's `process_instruction` entrypoint, which is not present/indexed in this codebase view.

### Recommendation
Add a `loader_v4::check_id(program_id)` arm to `check_authorized_program` in `program-runtime/src/cpi.rs`, mirroring the treatment of `bpf_loader`/`bpf_loader_deprecated` (deny outright) or `bpf_loader_upgradeable` (deny by default, with only deliberately-reviewed sub-instructions allowed), so Loader-v4 management instructions cannot be triggered via CPI by an arbitrary unprivileged program.

### Proof of Concept
1. Deploy an attacker-controlled BPF program `A` under Loader-v4 (or targeting any Loader-v4-owned program account).
2. From within `A`'s instruction handler (or from a second attacker program `B` that CPIs into `A`), construct an `Instruction` with `program_id = loader_v4::id()` and a Loader-v4 management opcode (e.g., Retract/Deploy/Finalize) targeting a program account that is part of the current call stack.
3. Call `invoke_signed`/`invoke` with that instruction. `cpi_common` → `check_authorized_program` is invoked and — because `loader_v4::check_id` is absent from the allow-list — returns `Ok(())` instead of `CpiError::ProgramNotSupported`, allowing the nested call to reach the Loader-v4 processor while the target program is still executing. [8](#0-7) 

Verification limitation: I could not execute or trace the Loader-v4 processor's handling of this nested call in this index to observe the concrete runtime error/panic, since its source was not found under `programs/loader-v4/**`. Confirming full weaponization (panic vs. graceful `InstructionError`) requires locating/reading that processor directly (e.g., via a Devin session with full repo access) or reproducing this with a local validator build.

/// Check whether a program is authorized for CPI
fn check_authorized_program(
    program_id: &Pubkey,
    instruction_data: &[u8],
    invoke_context: &InvokeContext,
) -> Result<(), Error> {
    if native_loader::check_id(program_id)
        || bpf_loader::check_id(program_id)
        || bpf_loader_deprecated::check_id(program_id)
        || (solana_sdk_ids::bpf_loader_upgradeable::check_id(program_id)
            && !(bpf_loader_upgradeable::is_upgrade_instruction(instruction_data)
                || bpf_loader_upgradeable::is_set_authority_instruction(instruction_data)
                || (invoke_context
                    .get_feature_set()
                    .enable_bpf_loader_set_authority_checked_ix
                    && bpf_loader_upgradeable::is_set_authority_checked_instruction(
                        instruction_data,
                    ))
                || bpf_loader_upgradeable::is_close_instruction(instruction_data)))
        || invoke_context.is_precompile(program_id)
    {
        return Err(Box::new(CpiError::ProgramNotSupported(*program_id)));
    }
    Ok(())
}
