### Title
Webhook organization selected for signature verification differs from the repository the payload actually writes to, allowing signature-check bypass across GitHub App configurations - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and therefore which `webhook_secret`) to validate the request against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1)  The handlers that actually act on the webhook (e.g. `push`) resolve the target Stack/repository from a *different* field in the same JSON body, `repository.full_name`. `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured: `return true unless webhook_secret`. [3](#0-2)  Because Shipit explicitly supports multiple GitHub Apps for multiple organizations, each with its own optional `webhook_secret`, [4](#0-3) [5](#0-4)  and the webhook secret is documented as optional, [6](#0-5)  an attacker can pick an organization slug that has no `webhook_secret` configured, place it in `repository.owner.login` (used only for verification/App selection), while leaving `repository.full_name` pointing at a real, protected repository belonging to a different, secured organization. `verify_signature` trivially passes because it authenticates against the unsecured organization, but the actual create action processes the full, attacker-controlled JSON body — including the victim's `full_name` — dispatching real jobs (e.g. `GithubSyncJob`) against the victim stack. [7](#0-6) 

### Finding Description
The binding that should hold is: *organization authenticated (`repository_owner` used in `verify_signature`) == organization actually written to (owner encoded in `repository.full_name` consumed by `Shipit::Webhooks` handlers)*. These are two independently attacker-controlled JSON fields inside the same unauthenticated (pre-signature) payload, and only the first is covered by the "verification" step — which itself degenerates to `true` for any organization lacking a `webhook_secret`. [3](#0-2)  Nothing in `WebhooksController` cross-checks that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same organization/App before dispatching to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [7](#0-6)  This is directly analogous to the report's root cause: a value is trusted and acted upon without validating that it corresponds to the value that was actually authenticated/verified.

### Impact Explanation
In any deployment where at least one configured GitHub organization has no `webhook_secret` (explicitly supported/optional per the setup docs and example config files), an external, unprivileged attacker can forge webhook events (e.g., `push`) targeting a different, secured organization's stacks, bypassing the entire HMAC signature protection for that stack. This can trigger unauthorized `GithubSyncJob` runs and other webhook-driven side effects (statuses, check runs, membership changes) against a repository/stack the attacker does not control, without needing the real `webhook_secret`, `ApiClient` token, or any GitHub write access — an authentication bypass on the webhook trust boundary.

### Likelihood Explanation
Exploitability only requires knowledge of Shipit's public multi-org configuration convention (documented) and identification of any organization slug in the deployment without a configured secret — no credentials or repository access needed. The example/default configs ship with `webhook_secret: # nil`, indicating this is a realistic and even encouraged (optional) configuration state. [8](#0-7) 

### Recommendation
Bind the organization used for signature verification to the same organization that owns the repository being mutated: derive both from the same canonical field (e.g., always parse `repository.full_name`'s owner segment, or explicitly reject requests where `repository.owner.login` does not match the owner encoded in `repository.full_name`). Additionally, do not allow `verify_webhook_signature` to silently return `true` for organizations without a `webhook_secret`; either require a `webhook_secret` for every configured organization or reject/flag unsigned webhooks for repositories belonging to organizations that do have a secret configured.

### Proof of Concept
1. Deploy Shipit with two configured organizations: `secure-org` (has `webhook_secret` set) owning the tracked stack `secure-org/app`, and `open-org` (no `webhook_secret` configured), per the documented multi-org config format. [4](#0-3) 
2. Attacker crafts a `push` webhook payload where `repository.owner.login = "open-org"` but `repository.full_name = "secure-org/app"` (and `after` pointing at an attacker-chosen ref).
3. Attacker sends `POST /webhooks` with `X-Github-Event: push` and any/garbage `X-Hub-Signature` header (or omitted).
4. `verify_signature` calls `Shipit.github(organization: "open-org")` and `verify_webhook_signature` returns `true` unconditionally since `open-org` has no `webhook_secret`. [1](#0-0) [3](#0-2) 
5. `create` proceeds to parse the full body and dispatches to `Shipit::Webhooks.for_event('push')` handlers using `repository.full_name = "secure-org/app"`, enqueuing a `GithubSyncJob` for the victim stack without ever having a valid signature for `secure-org`. [7](#0-6)

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
