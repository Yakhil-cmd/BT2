### Title
Attacker-controlled PR label names inject arbitrary env-var keys (e.g. `BASH_ENV`) into shell-interpreted `shipit.yml` task/deploy steps - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges PR label names, uppercased, as environment variable *keys* into every task/deploy command with no allowlist, and `LabelCapturingHandler` persists arbitrary label names straight from unauthenticated webhook payloads. Since `TaskCommands#env` merges `@stack.env` unfiltered before building `Command.new(command_line, env:, chdir:)`, and `Command#unbundled_env` applies `@env` last (overriding even `PATH`), a PR opened from any fork can inject security-relevant variable names such as `BASH_ENV`, `PATH`, `IFS`, or `ENV` into the process environment of shell-interpreted steps run with `chdir` set to the checked-out PR content.

### Finding Description
The broken binding: the set of keys entering `Command#unbundled_env` should equal the intersection of `{ENVIRONMENT, LAST_DEPLOYED_SHA, GITHUB_REPO_OWNER, GITHUB_REPO_NAME, DEPLOY_URL, BRANCH}` (defined in `Stack#env`, [1](#0-0) ) plus operator/maintainer-defined `shipit.yml` variables — but in practice it equals that set **union with `pull_request.labels.map(&:upcase)`**, entirely attacker-chosen key names, because:

- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` with no key allowlist: [2](#0-1) 
- `LabelCapturingHandler#capture_labels` writes `params.pull_request.labels.map(&:name)` straight from the webhook body onto `pull_request.labels`, with only a String type check in the params schema (no character restriction): [3](#0-2) , and this handler fires simply for `opened_active_stack?`/`labeled_active_stack?` on an unarchived stack — no maintainer approval needed: [4](#0-3) 
- `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes the label-derived keys) with no call to `EnvironmentVariables#permit` anywhere in the merge chain: [5](#0-4) . The only place `EnvironmentVariables#permit` (the allowlist mechanism, see `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` and `TaskDefinition#filter_envs`) is invoked is on the API-supplied `env` param of an explicit deploy/task trigger request — never on `stack.env`.
- `Command#unbundled_env` applies `@env.stringify_keys` **last**, after `PATH` is set, so any label-derived key (including `PATH` itself) silently overrides prior values: [6](#0-5) 
- `Command#start` passes this env hash directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and `parse_arguments` leaves a `shipit.yml` step as a single string when written that way, so Ruby's `Process.spawn` semantics route it through `/bin/sh -c` whenever the interpolated command contains shell metacharacters (e.g. `$ENVIRONMENT`): [7](#0-6) 
- The task's `chdir` (`steps_directory`) is the checked-out PR branch content itself (`@task.working_directory`), which the attacker fully controls via their fork's PR head: [8](#0-7) 

**Exploit flow**: An attacker opens a PR (or applies a label to their own already-open PR) on a repository with `provisioning_behavior: allow_all` and `review_stacks_enabled: true`, naming a label `bash_env` (case-insensitive, becomes `BASH_ENV` after `.upcase`). They also commit a file literally named `true` in their PR branch (in `steps_directory`) containing malicious shell commands. `LabelCapturingHandler` persists `["bash_env"]` into `pull_request.labels` from the raw webhook payload — no signature bypass needed since this only requires normal, valid webhook delivery for an attacker-owned repository/PR. When any subsequent task (e.g. `restart`, or a deploy) is triggered for that review stack, `ReviewStack#env` injects `BASH_ENV=true` into the command's env; if that step (or any script it execs with a `#!/bin/bash` shebang) is later invoked as `bash` (not posix-mode `sh`), bash sources `./true` relative to `chdir` before running anything else — the attacker's payload executes on the Shipit deploy host.

Existing guards do not stop this: `EnvironmentVariables#permit` is never applied to `@stack.env`/`ReviewStack#env`; `LabelCapturingHandler`'s `ExplicitParameters` schema only validates types, not content; and `provisioning_behavior: allow_all` is an explicit, documented mode intended to let any PR trigger review-stack provisioning — none of these checks constrain the *variable names* derived from labels.

### Impact Explanation
If realized, this yields arbitrary command execution on the Shipit deploy host under the identity that runs task/deploy steps, for the specific repository/stack that has `review_stacks_enabled` and `provisioning_behavior: allow_all` (or `allow_with_label`, since the attacker also controls whether the label they choose satisfies the provisioning label). It also independently permits overriding `PATH` and other operationally sensitive variables in every shell-interpreted step for that stack, since `@env` is merged last in `unbundled_env`. This matches the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category, but is scoped to review-stack-enabled repositories in `allow_all`/`allow_with_label` mode, and its actual triggering (whether `BASH_ENV` is honored) is contingent on how a given `shipit.yml`'s steps or their scripts invoke `bash` versus `sh` on the host — this is host/config dependent, not universal, but the env-key-injection primitive itself is unconditional and repeatable against any repository configured this way.

### Likelihood Explanation
Preconditions: repository must have `review_stacks_enabled: true` and `provisioning_behavior` of `allow_all` or `allow_with_label` (a documented, intentional feature for auto-provisioning review stacks from PRs) — this is by design attacker-reachable since the whole point is unprivileged forks/PRs can trigger it. Attacker cost is low: opening a PR and adding a label are actions any GitHub user with fork access can perform. The env-key-injection (arbitrary key names entering the process env) is reliably reproducible with a plain minitest as shown in existing tests (`ReviewStackTest#env includes the stack's pull request labels`, `TaskCommandsTest`, `DeployCommandsTest`), it is only the downstream shell/bash-invocation behavior that is environment-dependent.

### Recommendation
Apply an explicit allowlist to keys derived from `ReviewStack#env`'s PR-label merge (e.g., require label names to match a safe env-var-name pattern and/or route them through `EnvironmentVariables#permit` against a maintainer-defined allowlist, analogous to `deploy_variables`/`rollback_variables`/`TaskDefinition#variables`), reject or filter label names that collide with reserved/sensitive variable names (`PATH`, `BASH_ENV`, `IFS`, `ENV`, `LD_PRELOAD`, etc.), and ensure `Command#unbundled_env` cannot let caller-supplied `@env` override `PATH` (compute `PATH` after merging `@env`, not before).

require "test_helper"

module Shipit
  class ReviewStackBashEnvTest < ActiveSupport::TestCase
    test "[allow_all] a PR label name injects an arbitrary env key (e.g. BASH_ENV) into shell-interpreted steps" do
      stack = shipit_stacks(:review_stack)
      # Attacker-controlled PR label name (as captured verbatim from an
      # unauthenticated webhook payload by LabelCapturingHandler#capture_labels)
      stack.pull_request.labels = ["bash_env"]

      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env

      # Binding under test: no fork-controllable key should reach the
      # process env of a shell-interpreted shipit.yml step.
      # LHS: attacker-chosen label-derived key   RHS: keys allowed by TaskDefinition#variables
      assert_not_includes task.definition.variables.map(&:name), "BASH_ENV"
      assert_equal "true", env["BASH_ENV"] # demonstrates the divergence: it is present anyway

      command = Shipit::Command.new("echo hi", env:, chdir: Dir.tmpdir)
      assert_equal "true", command.unbundled_env["BASH_ENV"]
    end
  end
end

    def interpolated_arguments
      interpolate_environment_variables(@args)

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
