### Title
CCMenuController bypasses ApiClient stack-scoping, letting a stack-scoped token read status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` can be scoped to a single stack via its `stack_id` column, and `Api::BaseController` is supposed to enforce `token.stack_id == requested stack.id` for every API action that resolves a stack. `Api::CCMenuController` re-defines the `stack` lookup method and, in doing so, drops that scoping check entirely, so a token whose authority is limited to one stack can be used to read CCTray/CI status for any other stack in the installation.

### Finding Description
`Api::BaseController` defines the trust binding between an API token and the stack it may act on: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the request's `:stack_id` param only within that restricted set. This is the equality that must hold: `current_api_client.stack_id == resolved_stack.id` (or the client is unscoped).

`ApiClient` supports this scoping — it `belongs_to :stack, optional: true` and grants `read:stack` (and other) permissions independently of scope: [2](#0-1) 

`check_permissions!` only checks that the permission string (e.g. `read:stack`) is present in the client's permission list; it never checks `stack_id`. Scope enforcement therefore depends entirely on the `stack`/`stacks` helper in `BaseController` being used consistently by every controller.

`Api::CCMenuController` overrides that helper: [3](#0-2) 

Instead of calling the scoped `stacks.from_param!(params[:stack_id])`, it calls `Stack.from_param!(params[:stack_id])` directly against the entire `Stack` table, bypassing the `current_api_client.stack_id` restriction. `require_permission :read, :stack` (checked via `check_permissions!`) still passes because the token does have `read:stack` — it just isn't supposed to have it for stacks other than the one it's bound to.

This is the same bug class as the reported `setFee` issue: a value that is supposed to bound/limit an action (`stack_id` scope on the token) is accepted by an authorization check (`read:stack` permission present) but never actually enforced against the resource being acted on (`params[:stack_id]`), because the enforcement point (`stack` method) was overridden without the guard.

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token (an intentionally low-privilege, single-stack credential) can call the CCMenu endpoint for a different `stack_id` and read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state, etc.) for every stack in the Shipit instance, not just the one the token was scoped to. This is an authorization-scope escalation: an unauthenticated-for-that-resource read of stack state, matching the "High - escalation into `Shipit.github_teams` authorization ... unauthenticated read of stack state" impact category (here, escalation past the token's intended stack scope rather than past team authorization, but the same class of authorization-boundary break).

### Likelihood Explanation
Stack-scoped API clients are a first-class, documented, tested feature of the engine (used e.g. to hand out narrowly-scoped CCTray tokens), and `params[:stack_id]` is an ordinary, attacker-controlled URL parameter. Exploitation requires only possessing any valid stack-scoped token with `read:stack` — no privileged account, no GitHub credentials, and no additional exploitation steps beyond changing the `stack_id` in the URL.

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` and use the inherited, scope-enforcing `stack` (and `stacks`) method from `Api::BaseController`, or explicitly re-check `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering. More generally, audit all API controllers for private overrides of `stack`/`stacks` to ensure the `current_api_client.stack_id` binding can never be silently bypassed.

### Proof of Concept
1. As an authorized user, create (or have created) an `ApiClient` with `permissions: ["read:stack"]` and `stack: StackA` (this is exactly the scoping the model supports, exercised by the engine's own test suite, e.g. "an api client scoped to a stack will only see that one stack").
2. Using that token's Basic-Auth credentials, request `GET /api/stacks/StackB_id/ccmenu.xml` where `StackB` is any other stack in the instance.
3. `require_permission :read, :stack` passes because the token has `read:stack`. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`, so `StackB`'s build/deploy status is returned even though the token is only supposed to authorize `StackA`.
