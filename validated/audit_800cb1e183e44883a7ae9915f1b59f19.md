### Title
Cross-tenant/cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The Aptos bug is a TOCTOU-style violation of an invariant equality (`merged_state`'s layer must remain compatible with `persisted_snapshot`'s layer) that is checked lazily instead of being enforced at the point where a security/consistency-critical action is taken. The structurally identical class of bug in this engine is: the GitHub webhook signature is verified against the **organization derived from the `repository` object in the payload** (`WebhooksController#repository_owner`, `app/controllers/shipit/webhooks_controller.rb:59-62`), but `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that binding — it looks up `Commit` records globally by SHA with no repository/organization scoping at all, breaking the equality: `authenticated_org(repository_owner) == owner(repository_of_commit_being_written)`.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the signature against based on the payload's own `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

Every other default handler re-derives the target repository the same way and scopes its side effects to that repository, e.g. the base `Handler#stacks` helper: [3](#0-2) 
and `PushHandler#process`, which restricts to `stacks.not_archived.where(branch:)`: [4](#0-3) 

`StatusHandler`, however, breaks this pattern entirely. It never calls `stacks`/`repository_name`; it queries every `Commit` in the entire installation purely by SHA, with no repository or organization filter: [5](#0-4) 

This means the organization whose webhook secret validated the request (`repository_owner` in the request payload) is never checked against the organization that actually owns the commit/stack being mutated by `commit.create_status_from_github!(params)`. In a multi-tenant Shipit deployment — explicitly documented and supported, see `docs/setup.md:181-216` (multiple GitHub Applications, one per organization, each with its own `webhook_secret`) — any organization/App configured on the instance can forge a `status` event, sign it with *its own* legitimate `webhook_secret`, and have `repository.owner.login` in the payload point to itself (so `verify_signature` passes), while the `sha` field references a commit belonging to a completely different tenant's stack/repository. `StatusHandler` will happily update that foreign commit's status.

### Impact Explanation
`Commit#add_status`/status creation feeds directly into deploy automation: a transition to `pending` or `success` triggers `stack.schedule_merges`, which can queue and execute unauthorized merges/deploys for a victim stack that the forging tenant has no legitimate authorization over: [6](#0-5) 
Because the check that "the org that authenticated this webhook" must equal "the org whose repository is being written" is present in every other handler but silently dropped in `StatusHandler`, an attacker who legitimately controls one tenant/organization on a shared Shipit instance can trigger commit-status-driven automatic merges/deploys for another tenant's repository/stack — an unauthorized deploy/merge, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires the attacker to be an authenticated tenant on a multi-tenant Shipit install (i.e., to control a legitimate GitHub App/organization already configured in `secrets.github`), which is a normal, documented deployment configuration, not a privileged Shipit admin account or GITHUB_TOKEN compromise. The attacker only needs to know a victim commit SHA (commonly public/knowable via GitHub) to target it. This is a realistic scenario for any organization running Shipit for multiple GitHub orgs/customers.

### Recommendation
Have `StatusHandler` (and any other handler that mutates data) scope its `Commit` lookup through the same repository resolution used for signature verification — i.e., restrict to commits whose `stack.repository` matches `payload.dig('repository', 'full_name')`/`repository_name`, consistent with the `Handler#stacks` helper used elsewhere, so the authenticated organization always equals the organization of the repository being written.

### Proof of Concept
1. Configure Shipit with two organizations, `tenant-a` and `tenant-b`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org setup).
2. As `tenant-a`, know/guess a commit SHA that exists in a `tenant-b` stack (e.g. from a public repo or CI logs).
3. Send a `status` webhook to `/github/webhooks` with:
   - `X-Github-Event: status`
   - Payload: `{"sha": "<tenant-b-commit-sha>", "state": "success", "repository": {"owner": {"login": "tenant-a"}, "full_name": "tenant-a/some-repo"}}`
   - `X-Hub-Signature` computed with `tenant-a`'s own `webhook_secret` over the raw body.
4. `verify_signature` resolves `repository_owner` = `tenant-a`, validates successfully against `tenant-a`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the `tenant-b` commit despite the payload/authenticated org being `tenant-a`, and calls `create_status_from_github!`, potentially flipping the commit to `success` and invoking `stack.schedule_merges` on `tenant-b`'s stack.
