### Title
Reachable `throw Error` in AA response validation crashes full nodes processing an attacker-crafted AA trigger - (File: `aa_composer.js`)

### Summary
CVE-2021-28905 is a reachable assertion (CWE-617) in libyang: attacker-influenced input reaches a code path where `node->module` is null, but the code unconditionally asserts it is non-null, crashing the process. The analogous pattern in ocore is in the Autonomous Agent (AA) trigger-processing pipeline: `aa_composer.js` builds and internally re-validates the AA's response unit, and treats several `validation.validate()` outcomes as "impossible," `throw`-ing an uncaught `Error` if they ever occur. Because the response payload is derived from an oscript/AA formula that is fully controlled by an unprivileged AA definition author (via arbitrary triggers sent by any user), a payload can be constructed that reaches one of these "impossible" branches, crashing every full node that executes the trigger.

### Finding Description
When a trigger unit is processed, `aa_composer.js` builds `objUnit` for the AA's response and re-validates it as a joint with `aa: true`: [1](#0-0) 

Every branch except `ifUnitError` is treated as unreachable and immediately throws:
- `ifJointError` → `throw Error("AA validation joint error: " + err)`
- `ifTransientError` → `throw Error("AA validation transient error: " + err)`
- `ifNeedHashTree` / `ifNeedParentUnits` / `ifOkUnsigned` → likewise throw.

However, `validation.js`'s central dispatcher routes *any* error carrying `error_code: "invalid_joint"` to `ifJointError`, independent of whether the unit is an AA unit (`bAA`): [2](#0-1) 

Several validation checks call `createJointError(...)` (which sets `error_code: "invalid_joint"`) without excluding the AA case, e.g. the oversize-fee mismatch check inside `validateParents`: [3](#0-2) 

Contrast this with the `temp_data` handler, which explicitly recognizes that AA-authored payloads must not raise `ifJointError` and deliberately downgrades the error when `objValidationState.bAA` is true: [4](#0-3) 

This shows the codebase is aware that AA-composed units can legitimately hit "joint-error-shaped" conditions and must be routed to `ifUnitError` instead — but this downgrade was not applied uniformly to every `createJointError`/`ifJointError` call site reachable from AA-composed payloads (e.g. the oversize-fee check, and other `createJointError(...)` calls in the general message/payload validators). If an AA-composed response payload ever causes one of these un-downgraded joint-error paths to fire, `aa_composer.js`'s `ifJointError` handler treats it as an "impossible" case and throws an uncaught `Error`, matching CVE-2021-28905's reachable-assertion pattern: a value the code assumes can never occur (a joint-level structural error on an internally-composed, self-consistent unit) turns out to be attacker-reachable through a specific payload shape.

### Impact Explanation
The trigger — and thus the shape of the AA's response messages/payload — is fully attacker-controlled: any unprivileged user can define an AA and any unprivileged user can send it a trigger. If the response payload can be steered into one of the un-guarded `createJointError`/joint-error conditions, every full node that processes the trigger executes `aa_composer.js`'s `validateAndSaveUnit` and hits the `throw Error("AA validation joint error: ...")` with no surrounding try/catch at that call depth, crashing the node process. Because trigger/AA execution is deterministic and identical across all full nodes, this is not a single-node fluke — it is a network-wide DoS: no node can advance past that trigger, and units depending on it can never be confirmed, satisfying the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Likelihood is High because:
- No special privileges are needed — defining an AA and sending it a trigger are both open, permissionless actions.
- The oscript formula language gives an AA author fine-grained control over output payload sizes/shapes, which is exactly the class of input that feeds fee/size-derived joint-error checks like the oversize-fee mismatch.
- The bug class (an assumed-impossible branch reachable via attacker-shaped structured input) is exactly CVE-2021-28905's root cause, and the code's own defensive fix for `temp_data` (explicitly avoiding `ifJointError` for AA payloads) demonstrates this exact scenario has already manifested at least once and was only patched for one specific message type.

### Recommendation
- Audit every `createJointError(...)` / joint-error-producing check reachable from AA-composed payload validation (not just `temp_data`) and downgrade them to unit-errors (`createError = objValidationState.bAA ? err => err : createJointError`) whenever `objValidationState.bAA` is true, consistent with the existing `temp_data` handling.
- In `aa_composer.js`, replace the blind `throw Error(...)` in `ifJointError`/`ifTransientError`/etc. with safe handling (log, mark the trigger/response as failed, bounce, or skip) rather than crashing the process, since these branches are demonstrably reachable via attacker-controlled trigger data.
- Add fuzz/property tests that generate AA definitions producing edge-case response payloads (oversized/borderline-size payloads, boundary values for `oversize_fee`, `tps_fee`, etc.) and assert that trigger processing never throws an uncaught exception.

### Proof of Concept
A network-observable PoC requires crafting a specific AA response payload that trips one of the un-guarded `createJointError` paths (e.g., an oversize-fee boundary mismatch produced by `storage.getOversizeFee` vs. the composer's computed `oversize_fee` for a particular payload size/version combination). Precisely pinpointing the exact byte-level trigger requires deeper inspection of `storage.getOversizeFee` and the AA composer's fee-computation code, which was not available within the indexed context; a Devin session with full repository access would be needed to construct and test the exact AA definition/trigger pair that reaches the throw.
