### Title
Cross-tenant Membership deletion via unbound `team.id` in MembershipHandler#process 'removed' branch - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process`'s `'removed'` branch resolves the `Team` solely by `github_id` via `find_or_create_team!`, then calls `team.members.delete(member)` without ever checking that the resolved team's `organization` matches the webhook's verified `params.organization.login`. An attacker who controls a genuinely configured org can forge a `removed` membership event naming a victim org's team ID and a real user's login to deauthorize that user cross-tenant.

### Finding Description
The broken binding, as an equality that is never checked: `team.organization == params.organization.login` is required for the operation to be scoped correctly, but the code never asserts it.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and picks the GitHub App/secret for that org via `Shipit.github(organization: repository_owner)`, then validates the HMAC signature against that org's own `webhook_secret` [2](#0-1) . For a membership event there is no `repository` key, so `repository_owner` falls back to `params.organization.login` — i.e. the *attacker's own org's* login, which the attacker fully controls, and `verify_signature` legitimately passes using the attacker's own org secret.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . Because a Team with that `github_id` already exists (the victim org's real team, part of `Shipit.github_teams`), `find_or_create_by!` returns the existing record and the block — which would set `organization`  — never runs. There is no verification that the found team's `organization` equals the attacker-controlled `params.organization.login`.
- `User.find_or_create_by_login!(params.member.login)` resolves the real victim user by login [4](#0-3) .
- In the `'removed'` branch, `team.members.delete(member)` [5](#0-4)  destroys the `Membership` row linking the victim user to the victim team — a record that belongs entirely to org B, mutated by a webhook whose only verified identity is org A.

No other guard intervenes: `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema only validates shape, not organization ownership; `Team#add_member`/`members.delete` perform no organization check either [6](#0-5) .

Attacker request: attacker's own genuinely-registered GitHub org emits (or the attacker crafts, since they control that org's webhook delivery) a `membership` event with `action: 'removed'`, `team.id` = the victim's real (discoverable) team `github_id`, `organization.login` = attacker's own org, `member.login` = victim's real login. The event is signed with the attacker org's own webhook secret, which the attacker legitimately possesses since it is their own org.

### Impact Explanation
The attacker can silently strip an arbitrary, targeted user's membership from a specific team belonging to a different, victim organization — including a team enumerated in `Shipit.github_teams`, which gates `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [7](#0-6) . This deauthorizes a legitimate Shipit user (revoking their ability to deploy/approve/merge) without any privilege on the victim org, using only the attacker's own org credentials. This is a cross-tenant write vector: a payload verified as coming from org A mutates a `Membership` record scoped to org B's team, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"), mirroring the `'added'` case escalation bug but in the deauthorization direction.

### Likelihood Explanation
Preconditions are modest: the attacker needs their own genuinely configured org (webhook_secret, App/OAuth config) registered with the host — which is presented in the rules as available to "any internet user" sending HTTP requests, though practically it requires being an operator's registered org partner; the victim's team `github_id` must be discoverable, which the audit states is feasible via GitHub's public team APIs; and the victim user's login must be known (public GitHub info). Given that, the attack is a single crafted HTTP POST to `/webhooks`, fully repeatable against any team github_id and any user login, at negligible cost.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and in `process` before performing the mutation), verify that the resolved team's `organization` equals the webhook's verified `params.organization.login` (case-insensitively), and raise/reject (e.g. via `drop_unhandled_event`-style 422/head) if they diverge, instead of trusting `github_id` lookup alone across organizations.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`):
1. Setup: `victim_team = shipit_teams(:shopify_developers)` with `organization: 'shopify'`, `github_id: 4242`; `member = shipit_users(:walrus)` (or similar existing authorized user) with an existing `Membership` row to `victim_team`.
2. Build payload: `{ action: 'removed', team: { id: 4242, name: 'x', slug: 'x', url: 'https://x' }, organization: { login: 'attacker-org' }, member: { login: member.login } }`.
3. Invoke `Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call` (or `.process`) directly, simulating that `verify_signature` already passed for `organization.login == 'attacker-org'`.
4. Assert before: `assert victim_team.members.include?(member)`.
5. Assert after: `refute victim_team.reload.members.include?(member)` — proving org A's payload (`organization.login == 'attacker-org'`) destroyed org B's (`shopify`) `Membership` row, i.e. `team.organization ('shopify') != params.organization.login ('attacker-org')` yet the deletion still succeeded.
