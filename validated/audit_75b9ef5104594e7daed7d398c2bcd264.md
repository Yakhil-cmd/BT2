### Title
CCMenu API tokens are never scoped to a single stack, letting a leaked token read deploy status for every stack in the instance - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token intended to authorize CI tooling (CCTray/CCMenu) to read a single stack's build status, but the created client is never bound to that stack. `Api::CCMenuController` then resolves the target stack without consulting the client's stack scope at all, so the token is treated as globally valid for `read:stack` across every stack in the Shipit installation.

### Finding Description
`CCMenuUrlController#client` creates the `ApiClient` with only a permission set, no `stack:` binding: [1](#0-0) 

Contrast this with `ApiClient`, whose `belongs_to :stack, optional: true` field is exactly what `Api::BaseController` uses to scope which stacks a client may see: [2](#0-1) [3](#0-2) 

`stacks` returns `Stack.where(id: current_api_client.stack_id)` only when `stack_id` is set, otherwise it defaults to `Stack.all`. Because the CCMenu client never gets `stack_id` set, `current_api_client.stack_id?` is false for it, so the scoping guard is already defeated at the model level.

On top of that, `Api::CCMenuController` doesn't even use the shared `stacks`/`stack` scoping helper — it defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` directly, bypassing the scoping mechanism entirely regardless of whether `stack_id` was set: [4](#0-3) 

The only authorization check performed is `require_permission :read, :stack`, which only verifies the permission *name* `read:stack` is present on the token — it never checks that the requested `stack_id` matches the client's authorized stack: [5](#0-4) 

This breaks the binding: **stack a token authorizes == stack it touches**. Before the attacker's request: the token is presented to the user as scoped to one stack (`api_stack_ccmenu_url(stack_id: stack.to_param)`): [6](#0-5) 
After the request: the same token, presented against `Api::CCMenuController#show`, resolves any `stack_id` param — including stacks unrelated to the one it was minted for — because neither `ApiClient#stack_id` nor the `stacks` allow-list is consulted.

### Impact Explanation
Any holder of a single CCMenu URL/token (these are routinely pasted into third-party CI dashboards, CCTray-compatible clients, status widgets, or shared with limited-access collaborators) can use that one token to read the latest deploy/rollback status, SHA, and environment name of **every stack** managed by the Shipit instance via `GET /api/stacks/:owner/:repo/:env/ccmenu.xml?token=...`, not just the stack it was generated for. This is an unauthenticated (from the app's authentication-checkpoint perspective — no GitHub team membership or session is verified, only the bearer token) cross-stack read of stack/deploy state, which matches the High-impact bucket for "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Likelihood is high for any environment running multiple stacks: CCMenu tokens are designed to be embedded in external polling tools and are inherently exposed outside the Shipit web session (unlike normal `X-Shipit-User`/session-based access). No special privilege is required beyond having once been given (or having intercepted) a single stack's CCMenu URL — the same reusable token created via `find_or_create_by!(creator:, name: 'CCMenu Client')` is also shared across all stacks a given user requests it for, further widening exposure.

### Recommendation
Bind the CCMenu `ApiClient` to the target stack when it is created (`stack: stack` in `ApiClient.create_with(...)`), and make `Api::CCMenuController#stack` use the shared `stacks.from_param!(params[:stack_id])` helper (or otherwise verify `current_api_client.stack_id == stack.id`) instead of querying `Stack.from_param!` directly, so a CCMenu token can only ever resolve the stack it was scoped to.

### Proof of Concept
1. As an authenticated Shipit user with access to stack `A`, request `GET /stacks/:owner/:repoA/:envA/ccmenu_url`. This calls `CCMenuUrlController#fetch`, which creates an `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and no `stack_id`, and returns a URL such as `https://shipit/api/stacks/owner/repoA/envA/ccmenu.xml?token=TOKEN`.
2. `TOKEN` is copied into a third-party CI status tool (its normal intended use) and is subsequently leaked/observed by a party who only has legitimate access to stack `A` (or none at all beyond having seen the widget).
3. That party sends `GET /api/stacks/:owner/:repoB/:envB/ccmenu.xml?token=TOKEN` for an unrelated stack `B`. `Api::CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`, `require_permission :read, :stack` passes because the permission list contains `read:stack`, and `stack` resolves `Stack.from_param!(params[:stack_id])` for stack `B` directly — returning `B`'s latest deploy/rollback status and SHA even though the token was only ever meant to authorize reading stack `A`.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
