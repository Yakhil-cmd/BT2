### Title
Signature validation selects the GitHub App by `repository.owner.login` while event handlers act on `repository.full_name` - cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App's `webhook_secret` to validate the HMAC signature against using the `repository.owner.login` field of the attacker-supplied JSON body, but every `Handler` subclass resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`. Since Shipit supports multiple independent GitHub Apps (one per organization) with independent `webhook_secret`s, an actor who legitimately controls the GitHub App for organization A can forge a raw webhook payload whose signature is valid for org A but whose `repository.full_name` points at an unrelated org B's stack, causing Shipit to process attacker-controlled push/status/pull_request events against org B's repository.

### Finding Description
`verify_signature` computes `repository_owner` from the untrusted body and uses it purely to pick the `GitHubApp` instance (and thus the `webhook_secret`) used to validate `X-Hub-Signature`: [1](#0-0) 

That `repository_owner` value is never cross-checked against the actual data acted upon. Every handler that processes the payload resolves the affected repository independently, via `repository_name = payload.dig('repository', 'full_name')`: [2](#0-1) 

`PushHandler`, for example, uses that resolved repository's stacks and forces a GitHub resync using an attacker-chosen `after` sha: [3](#0-2) 

The `StatusHandler`-driven flow writes attacker-controlled fields (`target_url`, `state`, `description`, `context`, `created_at`) directly onto a `Status` for a commit in whatever repository `repository.full_name` names, entirely independent of which org's secret validated the request, as confirmed by the fixture-driven expectations in the test suite: [4](#0-3) 

Shipit's multi-organization support means each org's GitHub App has its own, independently-known `webhook_secret` — it is configured per-organization, and an operator of one org's App (e.g. as its GitHub App admin) legitimately knows that org's secret: [5](#0-4) [6](#0-5) 

**The broken binding, as an equality that should hold but does not:**
`organization whose secret authenticated the request == organization that owns the repository the handler subsequently writes to`

Before the attack: for any legitimate GitHub-originated webhook, `repository.owner.login` (used to pick the app/secret) and `repository.full_name`'s owner segment (used by handlers) are always the same value, because GitHub itself constructs the payload from one true repository object.

After the attacker's forged request: the attacker crafts a JSON body where `repository.owner.login = "OrgA"` (an org they administer, so the HMAC validates against `OrgA`'s `webhook_secret`) but `repository.full_name = "OrgB/victim-repo"` (a different, unrelated stack). `verify_signature` passes because it only checked the byte-signature against `OrgA`'s secret; the handler then acts on `OrgB/victim-repo` using data entirely chosen by the attacker.

### Impact Explanation
This crosses an authentication boundary that the engine treats as its foundational trust guarantee — "a webhook whose signature validates for org X may only affect org X's resources." Concretely, an attacker who controls (or is an admin of) any single GitHub App configured in a multi-org Shipit deployment can inject synthetic `push`, `status`, `pull_request`, or `check_suite` events against every other configured organization's stacks. Depending on downstream state (continuous deployment enabled, deploy gating on CI status), this can inject fabricated successful CI statuses onto a real commit of a repository the attacker has no access to, which can influence deployability checks and stack synchronization for `OrgB`'s stacks — a cross-organization (cross-repository) integrity violation reachable without any credentials belonging to the victim organization.

### Likelihood Explanation
Likelihood is limited to installations that configure more than one GitHub organization (the multi-app configuration documented in `docs/setup.md` and exercised by `secrets_double_github_app.yml`), and requires the attacker to control the GitHub App/`webhook_secret` for at least one configured org. In single-org deployments the two fields always agree, so there's no divergence to exploit. Where multi-org configuration is used, no other privilege is required beyond that org-level webhook secret, which the rules classify as an unprivileged-attacker credential relative to the victim organization's resources.

### Recommendation
- Short term: after signature verification, re-validate that `repository.owner.login` (the value used to select the verifying `GitHubApp`/secret) matches the `repository.full_name` owner segment that handlers subsequently use, rejecting the request (422) on mismatch.
- Long term: bind webhook signature verification directly to the specific `Repository`/`Stack` being mutated (e.g., verify against the secret owned by the actual target repository's org, derived from the same field the handler will use), rather than using a caller-suppliable field purely to select which secret to check against.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`).
2. As an attacker who administers `OrgA`'s GitHub App, craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Sign this raw body with `OrgA`'s `webhook_secret` using HMAC-SHA1 and send it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully validates the signature.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves `repository_name` from `repository.full_name` = `"OrgB/victim-repo"` and forces a resync/expected-head-sha update on `OrgB`'s stack — despite the request never being authenticated by anything belonging to `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
