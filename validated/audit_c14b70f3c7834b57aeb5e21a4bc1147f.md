## Title
Permanent DOS of AA asset issuance via front-run issue by an unprivileged unit ([File: aa_composer.js])

### Summary
An Autonomous Agent (AA) that defines a capped, non-fixed-denomination asset with `issued_by_definer_only=false` can be permanently blocked from ever issuing that asset. Any unprivileged user can post a normal (non-AA) payment unit that issues the asset from their own address up to its cap. The AA's own issuance logic checks only whether *any* issue input for the asset exists—regardless of issuer address—so this outside issuance permanently makes the AA's `issueAsset()` fail with `'already issued'`, freezing any AA logic that depends on being able to issue the asset.

### Finding Description
When an AA needs to issue a capped asset it owns, `aa_composer.js` runs: [1](#0-0) 

The comment `// only our AA can issue, no unstable consensus-breaking issues possible` reflects an assumption that is only true when the asset is `issued_by_definer_only`. However, the query itself (`SELECT 1 FROM inputs WHERE type='issue' AND asset=?`) does not filter by `address` or `definer_address`—it treats the asset as "already issued" as soon as *any* issue input exists, from *any* address.

Whether an outside address can create that issue input depends on `issued_by_definer_only`. `validation.js` enforces the definer restriction only when this flag is set: [2](#0-1) 

For a capped asset, `serial_number` must simply be `1` and `input.amount` must equal `objAsset.cap`—there is no `issued_by_definer_only` requirement unless the asset explicitly sets it. If the AA defines the asset with `issued_by_definer_only=false` (a legitimate configuration allowed by the asset-definition validator), then any address is permitted to post a standalone payment unit with an `issue` input for that asset, consuming the sole allowed capped issuance before the AA ever gets a chance to issue it itself.

Because the double-spend uniqueness key for issue inputs includes `address` only when `!issued_by_definer_only` (`validation.js` line ~2370), a foreign address's issuance does not conflict at the DB-uniqueness layer with a hypothetical AA issuance from a different address—yet the AA's own pre-check (`aa_composer.js` line 1196) unconditionally treats the asset as issued the moment any row exists, regardless of address.

This mirrors the reported pattern in `MeritDutchAuction.mint()`: a privileged/central minting flow that tracks "already minted" state internally, while an out-of-band actor can create the same state externally, permanently colliding with and blocking the intended contract's own logic — with no corresponding "burn"/reset capability, since AA bytecode is immutable and stateVars/asset definitions cannot be redefined after the fact.

### Impact Explanation
Any AA logic that relies on issuing its own capped asset (e.g., token distribution, LP-share minting, reward tokens) is permanently and irrecoverably frozen once a single unprivileged unit issues the asset out-of-band. Since AA definitions and asset definitions are immutable on-chain, there is no way to reset `max_issued_serial_number`-style state or to force the "already issued" check to re-open. Any bytes/assets sent to the AA in anticipation of triggering this issuance path will be bounced/refunded per AA semantics, but the intended functionality (issuing its token) is dead forever — a permanent freezing of AA functionality, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Any user with the ability to post a normal unit (no special privileges) can issue a capped, `issued_by_definer_only=false` asset up to its cap in one message, as long as they know the asset id (visible on-chain from the AA's `asset` definition message). This requires no cooperation from the AA operator and no race condition beyond simply issuing before the AA's own trigger does — it's a single, straightforward transaction.

### Recommendation
In `aa_composer.js`'s `issueAsset()`, when checking whether a capped asset has "already" been issued, restrict the check to issuances from the AA's own address (or definer address), consistent with how uncapped issuance is already scoped by `address` (line 1204). Alternatively, require `issued_by_definer_only=true` to be enforced (or defaulted) whenever an AA is the asset's definer, so that only the AA itself can ever issue the capped supply, eliminating the front-running window entirely.

### Proof of Concept
1. An AA defines an asset with `cap: 1000000`, `fixed_denominations: false`, `issued_by_definer_only: false`, with `definer_address` = the AA's own address.
2. Before the AA's trigger logic issues the asset, an unprivileged user crafts and posts a normal payment unit containing a payment message for this `asset` with an `issue` input: `{type: "issue", amount: 1000000, serial_number: 1, address: <attacker_address>}`. This passes validation per `validation.js` lines 2321-2346 (capped asset, `serial_number=1`, `amount === cap`) since `issued_by_definer_only` is false.
3. Once this unit is stable, the AA is triggered and attempts to issue: `aa_composer.js` runs `SELECT 1 FROM inputs WHERE type='issue' AND asset=?`, finds the attacker's row, and returns `cb2('already issued')` (line 1195-1200), causing the AA's response to bounce.
4. This condition is permanent: the asset's cap and definition are immutable, and no unit can ever again satisfy the AA's issuance path, freezing any AA functionality dependent on issuing that asset. [1](#0-0) [2](#0-1) [3](#0-2)
