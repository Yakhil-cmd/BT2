### Title
Cross-repository commit-status injection reaches `Stack#trigger_continuous_delivery`, causing unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely `Commit.where(sha: params.sha)` with no scoping to the repository/organization whose webhook signature was actually verified. Because Git commit SHAs are content-addressed and public information, and GitHub's Statuses API will accept and re-broadcast a status for *any* SHA string on a repository regardless of whether that commit actually exists there, an attacker who owns/controls their own GitHub repo (with the Shipit GitHub App installed on it) can send a genuinely-signed `status` webhook for their own org that references a victim stack's `next_commit_to_deploy` SHA. Shipit applies that status to the victim's `Commit` row, which can make the commit pass deployability checks and cause `Stack#trigger_continuous_delivery` to call `trigger_deploy` as `Shipit.user` for a repository the attacker never authenticated against.

### Finding Description
The claimed binding is:
`repository_owner_verified_by_signature == repository.owner_of(commit.stack)`

Trace:
- `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from the payload's own `repository.owner.login`/`organization.login`, and verifies the HMAC signature against that org's app config [1](#0-0) . This only proves the payload really came from GitHub for the org named *inside the payload itself*—the attacker's own org, if the attacker owns a repo with the Shipit GitHub App installed.
- `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which does:
  `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
  There is no filter on `commit.stack.repository` matching `repository_owner`/`repository.full_name` from the payload. Any `Commit` row in the entire Shipit installation sharing that SHA is updated, regardless of which repository/stack it belongs to.
- Because git commit hashes are pure functions of commit content (tree, parent(s), author/committer lines, message) and GitHub's `POST /repos/:owner/:repo/statuses/:sha` endpoint accepts arbitrary 40-hex SHA strings without verifying the commit exists in that repo, an attacker can request a status for the victim's known, public commit SHA (e.g., copied from the victim's public PR/commit page) on their own repository. GitHub will emit a validly-signed `status` webhook to Shipit for the attacker's own org/repo, referencing that SHA.
- `ContinuousDeliveryJob#perform` → `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`) computes `next_commit_to_deploy` from `deployable_commits`, which depends on the commit's `statuses` [3](#0-2) . If the injected status flips the required check(s) to success, the victim commit becomes deployable and `trigger_deploy(commit, Shipit.user, env: ...)` is invoked, producing a real `Deploy` for the victim stack.

Existing guards fail here because:
- `verify_signature` only proves authenticity for the *attacker's own* org, not for the victim stack's repository — the code never checks that the org verified in the signature matches the repository owner of the `Commit`/`Stack` being mutated.
- No model-level scoping (`Repository` association, `full_name` check) is enforced in `StatusHandler#process` before calling `create_status_from_github!`.
- `force_github_authentication`, `require_permission!`, and the ExplicitParameters schema for `StatusHandler` (`sha`, `state`, etc.) do not constrain which stack's commits can be targeted — they only validate payload shape, not repository ownership.

### Impact Explanation
An attacker who owns any GitHub repository with the Shipit GitHub App installed (a normal, unprivileged onboarding action, not requiring any Shipit secret) can inject fabricated commit statuses onto any `Commit` row in the Shipit database that happens to share a SHA they can learn (any public commit SHA on GitHub). This can push a victim stack's `next_commit_to_deploy` into a deployable state and, combined with `continuous_deployment: true`, cause `Shipit::Stack#trigger_continuous_delivery` to create a `Deploy` for that stack as `Shipit.user` — an unauthorized deploy triggered against a repository/stack the attacker never authenticated against. This is repeatable against any stack/commit whose SHA the attacker can discover, and the blast radius spans every tenant/stack hosted by the same Shipit instance. This matches "an unauthorized deploy... triggered" / "a payload for one repository mutating another's stack, commit... " in the Critical impact category.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`, no restrictive `continuous_delivery_schedule`, `cached_deploy_spec` present, and is not `occupied?` — all normal, common configurations. The attacker needs: (1) a GitHub repo they control with the Shipit App installed (self-service, no privilege), and (2) knowledge of the victim commit's SHA (trivially public for open-source stacks, or observable via Shipit's own UI/API for many deployments). No Shipit secret, session, or GitHub team membership is required. Cost is low and the attack is fully repeatable/scriptable via GitHub's public Statuses API.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository that was actually verified by the webhook signature, e.g. join through `commit.stack.repository` and require `repository.full_name == payload.dig('repository', 'full_name')` (or `owner/name`) before calling `create_status_from_github!`. More generally, every webhook handler that mutates a `Commit`/`Stack`/`Task` by attacker-supplied identifiers (SHA, branch name, etc.) must additionally assert that the record's owning `Repository` matches the `repository_owner`/`repository.full_name` that `WebhooksController#verify_signature` actually authenticated.

### Proof of Concept
Minitest plan (no live GitHub, using existing webhook test helpers/fixtures):
1. Create two stacks/repositories: `victim/repo` (with `continuous_deployment: true`, no schedule) and `attacker/repo`.
2. Create a `Commit` on `victim/repo`'s stack with a known `sha` (e.g., `"a" * 40`) and no passing status yet, such that `next_commit_to_deploy` currently returns nil/not-deployable.
3. POST to `/webhooks` a `status` event payload where `repository.owner.login == "attacker"` and `repository.full_name == "attacker/repo"`, but `sha == "a" * 40` (the victim's commit sha), `state == "success"`, `context` matching the check the victim stack requires — signed with `attacker`'s webhook secret (i.e., signature verifiable for `Shipit.github(organization: "attacker")`).
4. Assert: `Commit.find_by(sha: "a"*40, stack: victim_stack).statuses.last.state == "success"` even though the verified organization was `attacker`, proving `repository_owner_verified_by_signature ("attacker") != commit.stack.repository.owner ("victim")` yet the status was still written — the binding is broken.
5. Call `ContinuousDeliveryJob.new.perform(victim_stack)` and assert a `Deploy` row is created for `victim_stack` with `user_id == Shipit.user.id` and `until_commit_id` equal to the injected commit's id, confirming the unauthorized deploy.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
      head(422) unless verified

      Rails.logger.info([

    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",

      ].join(' '))
    end

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
