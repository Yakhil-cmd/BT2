### Title
`extract_frontmatter`'s naive `str.split('---', 2)` delimiter parsing silently downgrades `action: block` rules to `warn` (or drops them entirely) - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` locates the YAML frontmatter boundaries using a plain `content.split('---', 2)` on the raw file text instead of a line-anchored delimiter check. Any frontmatter field value (e.g. `pattern:`) that contains the literal substring `---` before the `action: block` line causes the split to truncate the parsed frontmatter early, pushing the real `action: block` line into the message body. Because `Rule.from_dict` uses `frontmatter.get('action', 'warn')`, the resulting `Rule` silently becomes `action='warn'` even though the on-disk file visibly shows `action: block`.

### Finding Description
`extract_frontmatter` splits the whole file content on the substring `---` with `maxsplit=2`: [1](#0-0) 

This split operates on the raw text, not on lines beginning with `---`, so any `---` sequence embedded inside a field value (e.g. a `pattern:` regex meant to match markdown horizontal rules, YAML separators, or git-conflict-like markers) is treated as a frontmatter-closing delimiter. If such a field appears **before** the `action: block` line in the file, the second "occurrence" of `---` is consumed inside that field value, and everything after it — including the real `action: block` line and the true closing `---` — is shoved into `parts[2]` (the message body), never entering the parsed `frontmatter` dict.

Downstream, `Rule.from_dict` computes the action purely from the dict: [2](#0-1) 

Since `action` is now absent from `frontmatter`, `frontmatter.get('action', 'warn')` defaults to `'warn'`. `RuleEngine.evaluate_rules` treats non-`'block'` rules purely as warnings that do not stop the tool call: [3](#0-2) [4](#0-3) 

`load_rules` globs every `.claude/hookify.*.local.md` in the current working directory and loads it automatically on every `PreToolUse`/`PostToolUse`/`Stop` hook invocation, with no signature/integrity check on file content: [5](#0-4) [6](#0-5) 

Any parsing failure or malformed input is swallowed and logged only to stderr (which is not surfaced by the hook's stdout-only JSON protocol), so the downgrade happens with no visible warning to the operator: [7](#0-6) 

A rule file such as:
```
---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm\s+-rf.*---.*
action: block
---
Blocked!
```
is displayed to any reviewer as a `block` rule, but `extract_frontmatter` parses it into `{'name': ..., 'enabled': True, 'event': 'bash', 'pattern': 'rm\\s+-rf.*'}` with **no `action` key**, so `Rule.action` resolves to `'warn'`. The dangerous `Bash` command is then only warned about, not blocked, breaking the invariant that a deny rule must never be parsed into a non-blocking configuration.

This is reachable without maintainer/admin privileges because: (1) `.claude/hookify.*.local.md` files can be introduced through ordinary repository content (e.g. a contributed file in a PR that gets merged and later cloned/pulled by a victim, matching the described fast-validation scenario of "place a crafted `.claude/hookify.*.local.md` in a cloned repo"), and (2) rule content/patterns are frequently authored via the `/hookify` slash command from natural-language instructions or conversation analysis (`plugins/hookify/commands/hookify.md`), so a pattern containing `---` (e.g. meant to detect markdown/YAML separators, diff markers, or merge-conflict markers) can be produced without any adversarial intent, yet still silently defeats the intended blocking rule.

### Impact Explanation
This is a Security-control bypass: a rule explicitly configured to `action: block` for a dangerous tool invocation (e.g. destructive `Bash` commands or edits to sensitive files) is silently re-interpreted by `extract_frontmatter`/`Rule.from_dict` as `action: warn`, so `RuleEngine.evaluate_rules` allows the operation to proceed instead of denying it. Since the file on disk still visibly reads `action: block`, a human reviewer inspecting the rule would believe protection is active while it is not — a classic "config says deny, engine says allow" trust-boundary bypass that silently routes around the blocking/permission boundary hookify is meant to provide.

### Likelihood Explanation
The only precondition is that a `.claude/hookify.*.local.md` rule file contains a frontmatter field value with an embedded `---` positioned before the `action:` line — a condition easily met unintentionally (e.g. a regex intended to catch markdown horizontal rules, diff hunks, or YAML documents) or deliberately by anyone able to influence the content of such a file (via `/hookify` argument text, conversation-analyzer-derived patterns, or a contributed rule file in the repository). No credentials, social engineering, or elevated privileges are required, and the bug is 100% deterministic given the crafted input — every load of the file with such content reproduces the downgrade.

### Recommendation
Replace the raw substring `split('---', 2)` with a line-anchored frontmatter delimiter parser: scan `content` split by `\n`, and only treat a line that is exactly `---` (optionally with trailing whitespace) as a delimiter, exactly as standard YAML frontmatter parsers (and most static site generators) do. Additionally, treat an `action` value that cannot be confidently parsed as `'block'` or `'warn'`, or a frontmatter block that fails to close before EOF, as a hard load failure (reject the rule / fail closed for `block`-intended rules) rather than silently defaulting to `warn`. Consider also failing loudly (non-silent) when `load_rule_file` cannot parse a file that appears to declare `action: block` anywhere in its raw text, to catch this specific corruption pattern.

### Proof of Concept
Unit test to add near `plugins/hookify/core/config_loader.py`:
```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

def test_embedded_delimiter_does_not_downgrade_block_rule():
    content = (
        "---\n"
        "name: block-dangerous-rm\n"
        "enabled: true\n"
        "event: bash\n"
        "pattern: rm\\s+-rf.*---.*\n"
        "action: block\n"
        "---\n"
        "Blocked!\n"
    )
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Expected (correct) behavior: the visible action:block must survive parsing
    assert rule.action == 'block', (
        f"Rule visibly declares action: block but parsed as {rule.action!r} "
        "due to naive '---' splitting in extract_frontmatter"
    )
```
Running this against the current implementation fails: `frontmatter` lacks the `action` key (it was pushed into the message body), so `rule.action == 'warn'`, demonstrating the parsed `Rule` object differs from the visible file content and that a declared `block` rule is enforced as a non-blocking `warn`.
