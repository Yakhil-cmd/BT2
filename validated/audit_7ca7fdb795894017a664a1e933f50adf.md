### Title
Unscoped `Commit` lookup by SHA in `StatusHandler` allows cross-repository/cross-organization commit-status writes - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload against the GitHub App/organization derived from `repository.owner.login` [1](#0-0) . Every other event handler that needs to touch a `Stack`/`Repository` scopes its side effects to the repository named in that same signed payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [2](#0-1) . `StatusHandler`, however, never calls `stacks`; it looks up commits globally by SHA alone: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This breaks the binding "organization/repository whose webhook secret verified this request == repository whose state is mutated," letting a webhook legitimately signed for one organization's repository write commit-status data belonging to any other repository/stack tracked by the Shipit instance whose commits table happens to contain the same SHA.

### Finding Description
The binding that should hold, expressed as an equality:

`organization/repository authenticated by verify_webhook_signature` == `repository whose Commit/Stack state is mutated by the handler`.

- `PushHandler` and `CheckSuiteHandler` both call `stacks`, which filters strictly to the `Repository` matching `payload['repository']['full_name']` — the same object whose `owner.login` was used to pick the webhook secret for verification [4](#0-3) [5](#0-4) .
- `StatusHandler` instead accepts `sha`, `state`, `context`, etc., and resolves the target purely as `Commit.where(sha: params.sha)`, with no repository/stack scoping at all [6](#0-5) .

Because `Commit` records across all stacks share one table and SHAs are only unique within Git history (not enforced unique per Shipit instance across repositories), a `status` webhook that is validly signed for organization/repository A can update the status of a `Commit` belonging to an unrelated repository/organization B, as long as a `Commit` row with a matching SHA exists for B. Git commit SHAs are content-addressed and fully attacker-reproducible when the target commit's tree/parents/author/committer/message/timestamps are known (e.g. from B's public history), so an attacker who only controls repository A can engineer such a collision and drive B's commit state via a webhook GitHub will happily deliver and sign for A.

### Impact Explanation
Commit statuses gate `deployable?`/safety checks used before a `Stack` can build/trigger a deploy (`release_status_context`, `Stack#trigger_deploy`, etc., all consuming `Commit` status state) [7](#0-6) . An attacker who only has push/webhook-triggering rights on their own registered repository (organization A) can flip the CI/status state of a specific commit in a completely different, unrelated stack (organization B) to `"success"`, turning an otherwise-undeployable commit into a deployable one — i.e. an unauthorized deploy path, and in general a cross-repository write, both of which are explicitly listed as Critical impacts.

### Likelihood Explanation
Requires: (1) the attacker administers/pushes to at least one repository already registered as a Shipit stack (so GitHub will sign `status` webhooks for it with a secret Shipit trusts), and (2) the attacker can produce or has produced a Git commit whose SHA collides with a commit already present in the victim stack's history (straightforward via forks/template repos/shared-history monorepos, or by crafting a byte-identical commit object once the victim commit's git object fields are known/public). No access to the victim organization's webhook secret, GitHub token, or Shipit session is required — only the ordinary, unprivileged ability to trigger a `status` event (e.g. push/commit-status API) on one's own configured repository. This matches the report's "simple input abuse on every request" likelihood pattern from the ANALOG source (`feeOn` accepting an out-of-range value that silently defeats the intended binary check).

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the `Commit` lookup to commits belonging to `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), for example `stacks.flat_map(&:commits).where(sha: params.sha)`, so a webhook can only ever mutate state for the repository whose ownership was actually verified against the signing secret.

### Proof of Concept
1. Attacker registers/administers `attacker-org/repo-a` as a Shipit stack (a normal, unprivileged onboarding action many Shipit instances allow for any GitHub org member).
2. Attacker crafts (or finds) a commit `C` with SHA `deadbeef...` that is also present in `victim-org/repo-b`'s tracked commit history (feasible via forks, template repos, or reconstructing an identical commit object from public victim history).
3. Attacker pushes `C` to `repo-a` and triggers/receives a legitimate `status` webhook event from GitHub for `repo-a` (e.g., via any CI integration or the Statuses API), with body `{"sha":"deadbeef...","state":"success","context":"ci/required-check", "repository": {"full_name":"attacker-org/repo-a","owner":{"login":"attacker-org"}}}`.
4. GitHub signs this payload with `attacker-org`'s real webhook secret; `WebhooksController#verify_signature` succeeds because it only checks the org derived from the payload, which correctly matches `attacker-org` [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, which matches the `Commit` row belonging to `victim-org/repo-b`, and calls `create_status_from_github!` on it — setting `victim-org/repo-b`'s commit status to `"success"` [3](#0-2) , without ever validating that `repo-b` was the repository whose signature was verified.
