### Title
Cross-repository `Status` webhook injection reclassifies another stack's commit as non-blocking, unblocking deploy/rollback target selection - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` with no scoping to the repository that sent the webhook, unlike every other handler in the same directory which uses the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`). A `status` webhook whose signature is valid for *any* GitHub organization known to Shipit can therefore write a `Status` row onto a commit belonging to a completely different stack/repository, as long as the sha string matches (e.g. a shared-history commit between a fork and its upstream, or any other coincidental sha match already present in the `commits` table).

### Finding Description
The broken binding: `repository owner that authenticated the webhook == repository owner of the stack whose commit/status is mutated`. This is asserted nowhere in the code path.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) validates the HMAC only against `Shipit.github(organization: repository_owner)`, i.e. it proves "this payload came from GitHub for organization X," not "this payload's `sha`/`repository` belongs to the stack being mutated."
- `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, whose `process` is:
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ``` [1](#0-0) 
  This is a global, unscoped `Commit.where(sha: ...)` query across **all** stacks/repositories in the installation. Contrast with the base class helper every other handler (`push_handler.rb`, `check_suite_handler.rb`, `membership_handler.rb`, the `pull_request/*` handlers) uses to restrict work to the originating repository:
  ```ruby
  def stacks
    @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
  end
  ``` [2](#0-1) 
  `StatusHandler` never calls `stacks` and never compares `params.dig('repository','full_name')` (or `payload['name']`) against `commit.stack.github_repo_name`.
- `Commit#create_status_from_github!` -> `add_status` -> `statuses.replicate_from_github!` persists the row unconditionally on whatever `commit` was matched by sha.
- `commit.status` is memoized via `Status::Group.compact(self, statuses_and_check_runs)` (`app/models/shipit/commit.rb:304-306`) [3](#0-2) , and `Status::Common#blocking?` re-derives from the current set of statuses each time: `!success? && commit.blocking_statuses.include?(context)` (`app/models/shipit/status/common.rb:46-48`) [4](#0-3) . So injecting a `success` status for the same `context` that was previously `failure`/`pending` on that commit changes `Status::Group#significant_status` and thus `blocking?` from true to false without any write authorized by the target stack's repository.
- `Commit#blocked?` (used by `deployable?`) scans `stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?)` (`app/models/shipit/commit.rb:231-237`) [5](#0-4) . Flipping the intermediate commit's `blocking?` to false unblocks every later commit in `stack_a`, so `Stack#next_commit_to_deploy` / `#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-243`) [6](#0-5)  can now select a later, attacker-favored commit as the deploy target. Rollback target selection (`previous_successful_deploy_commit`, `last_deployed_commit`) depends on completed `Deploy`/`Rollback` tasks rather than `blocking?`, so the "unblock a rollback" framing is not directly supported by this code path — the concrete, provable effect is on **forward** continuous-delivery target selection (`next_commit_to_deploy`/`trigger_continuous_delivery`), not on rollback target resolution, which is derived from `deploys_and_rollbacks` history and `until_commit`, unaffected by `blocking?`.

Why guards don't stop it: `verify_signature` authenticates the org, not the repo-to-commit binding; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates types (`sha`, `state`, etc.), not repository identity; there is no `force_github_authentication`/`require_permission!`/`stacks` scope check in this controller at all (webhooks are unauthenticated except by signature).

Precondition/limitation: exploitation requires the attacker's webhook-emitting repository to belong to a GitHub organization/App installation already known to and trusted by Shipit's `Shipit.github(organization:)` configuration (otherwise `GithubOrganizationUnknown` yields HTTP 422), and requires the injected `sha` to exactly match a real commit sha already recorded in `stack_a`'s `commits` table (feasible for forks that share unmodified upstream commits, or for any other legitimately-known sha, but not an arbitrary sha of the attacker's choosing).

### Impact Explanation
A payload sent as if from one repository can flip the deploy-blocking classification of a commit that belongs to a stack tracking a different repository, letting `trigger_continuous_delivery` pick and deploy a commit that the intended blocking gate should have prevented — this is "a payload for one repository mutating another's stack/commit" and produces an unauthorized deploy target selection, matching the Critical impact category. Blast radius: any two stacks in the installation that happen to share a commit sha (forks are the common real-world case) are cross-contaminated; repeatable per matching sha, and each successful injection permanently alters `commit.status`/`blocking?` for the victim stack until a legitimate status is replayed.

### Likelihood Explanation
Requires (a) the target commit's sha to also exist verbatim on a repository whose org is already configured in Shipit (realistic for forks/mirrors within the same GitHub org or App installation), and (b) the attacker being able to trigger a genuine, signed `status` webhook from that repository (e.g. by pushing a commit that reuses the shared sha and letting a CI system or the attacker's own status API call report `success` for that context). No Shipit credentials, sessions, or GitHub secrets are needed — only ordinary write/push access to a repo whose org is trusted by Shipit's webhook signature check.

### Recommendation
In `StatusHandler#process`, scope the lookup to the stacks that belong to the originating repository, mirroring the base `Handler#stacks` helper used elsewhere, e.g. restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` (or join through `stack_id: stacks.select(:id)`), rejecting/ignoring commits whose `stack.repository` does not match `payload.dig('repository','full_name')`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not update commits belonging to a different repository" do
  stack_a = shipit_stacks(:shipit)                 # repo: shopify/shipit-engine
  commit  = stack_a.commits.create!(sha: 'deadbeef' * 5, ... , stack_id: stack_a.id)
  commit.statuses.create!(stack_id: stack_a.id, state: 'failure', context: 'ci/required')
  assert_predicate commit, :blocking?

  # Binding under test:
  # payload_repository_full_name == commit.stack.repository.full_name  -> should hold, currently doesn't
  payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/required',
    'repository' => { 'full_name' => 'attacker/unrelated-fork' }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit.reload
  refute_equal 'attacker/unrelated-fork', commit.stack.repository.full_name
  # Current (vulnerable) behavior: commit.blocking? is now false
  # Expected (fixed) behavior: assert_predicate commit, :blocking?  # status from unrelated repo must not apply
end
```

      return if cached_deploy_spec.blank?

      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
