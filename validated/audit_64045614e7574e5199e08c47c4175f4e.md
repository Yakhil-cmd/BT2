Stack-scoped ApiClient token can read deploy status of any stack via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-lookup helper with a version that does not enforce the `ApiClient`'s stack scope, allowing a token that is authorized (and intended to be restricted) to a single stack to read the build/deploy status of any stack in the installation.

### Finding Description
The base API controller enforces per-token stack scoping through the `stacks` helper, which restricts the queryable set to the client's own `stack_id` when the client is scoped: [1](#0-0) 
This is the binding the protocol relies on: `stack a token authorizes == stack it touches`. Every other API controller that resolves a stack from `params[:stack_id]` goes through this `stacks`/`stack` helper (e.g. `Api::StacksController`, `Api::TasksController`, etc.), so a token scoped via `belongs_to :stack, optional: true` on `ApiClient` is confined to that one stack.

`Api::CCMenuController` breaks this binding. It overrides `stack` to bypass the scoping entirely: [2](#0-1) 
It resolves `Stack.from_param!(params[:stack_id])` directly against the global `Stack` relation instead of `stacks.from_param!(...)`. The only check performed is `require_permission :read, :stack`, which validates that the `permissions` array on the `ApiClient` includes `read:stack` — it says nothing about *which* stack: [3](#0-2) [4](#0-3) 

The controller also supports authenticating via a `?token=` query-string parameter (for CCMenu/CI-status clients), independent of the standard Basic-Auth header flow: [5](#0-4) 

An `ApiClient` created with `stack_id` set (e.g. as seen in the `here_come_the_walrus` fixture, scoped to the `shipit` stack, with only `read:stack` permission) is elsewhere correctly confined to its own stack: [6](#0-5) [7](#0-6) 

But nothing in `CCMenuController` re-checks `current_api_client.stack_id`. Any holder of a valid, stack-scoped token can supply a different `stack_id` in the URL/route (`GET /api/stacks/:stack_id/ccmenu`) and receive that other stack's latest deploy/rollback status, lock state, and build label — data belonging to a repository/stack the token was never granted access to.

### Impact Explanation
This is an authorization-scope bypass: an intentionally stack-scoped credential (an `ApiClient` with `stack_id` set, meant to expose deploy status only for one project to something like a CI dashboard integration) can be used to enumerate and read the deploy/rollback status, lock reason, and build metadata of *any* stack in the Shipit installation. This matches the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-impact category, since the scoping mechanism that is supposed to bind the token to a specific stack is silently ignored for this endpoint.

### Likelihood Explanation
Any legitimate holder of a stack-scoped `ApiClient` token (which by design is meant to be handed to lower-trust integrations, e.g. a CI status badge/dashboard for one project) can trivially exploit this by changing the `stack_id` segment of the URL — no privilege escalation, secret guessing, or race condition is required, only a token that already exists for one stack. The `Api::CCMenuController` route is public/reachable (`/api/stacks/:stack_id/ccmenu`) and requires nothing beyond a valid token string.

### Recommendation
Have `Api::CCMenuController#stack` resolve the stack through the scoped `stacks` collection (as `Api::BaseController#stack` does) instead of `Stack.from_param!` directly, e.g. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot resolve a stack outside its `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <stack A>` with permission `read:stack` (as in the `here_come_the_walrus` fixture).
2. Using that client's `authentication_token`, issue `GET /api/stacks/<repo-B>/<env-B>/ccmenu?token=<token>` where stack B is a different stack the client is not scoped to.
3. `CCMenuController#authenticate_api_client` succeeds (the token itself is valid), `require_permission :read, :stack` passes (the client has `read:stack`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` to stack B regardless of the client's `stack_id`.
4. The response renders stack B's latest deploy/rollback status, lock state, and build label — data outside the token's intended scope, confirmed by contrast with `Api::StacksController`/`Api::BaseController#stacks`, which correctly restrict a scoped client to `Stack.where(id: current_api_client.stack_id)`.
