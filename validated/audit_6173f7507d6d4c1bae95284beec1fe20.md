### Title
Webhook signature verification uses a different repository field than the one the handler acts on, allowing cross-organization spoofed pushes when any configured GitHub org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate the HMAC signature based on `repository_owner` (derived from `repository.owner.login` or the fallback `organization.login`). But the handler that actually acts on the payload (`Handlers::Handler#repository_name`, used by `PushHandler`) resolves the target repository from a *different* JSON field, `repository.full_name`. Because these two fields are read independently and Shipit explicitly supports a documented multi-organization configuration where any given org's `webhook_secret` can be left blank, an attacker can pick an org with no configured secret for the "authenticating" field while pointing the "acted upon" field at a completely different, victim stack.

**The binding that is broken:** the organization whose credential (webhook secret) authenticated the request must equal the repository whose Stack is written to. Before the attacker's request, `repository_owner` (used for signature lookup) and `repository.full_name` (used for the actual sync target) are assumed to belong to the same GitHub repository/org for legitimate GitHub-originated webhooks. After a crafted request, these two values can diverge: `repository.owner.login`/`organization.login` = an org with no `webhook_secret` configured (so `verify_webhook_signature` returns `true` unconditionally, without any real HMAC check), while `repository.full_name` = `victim-org/victim-repo`, whose stacks then get processed as if the push were authentic.

### Impact Explanation
An unauthenticated attacker who only needs to know (a) that Shipit is configured for multiple GitHub organizations and (b) that at least one configured organization has no `webhook_secret` set (a supported and documented setting, not requiring any secret disclosure) can forge a `push` webhook that:
- Passes signature verification trivially (`return true unless webhook_secret`), and
- Targets any other org/repo's Stack via `repository.full_name`, triggering `GithubSyncJob` with an attacker-chosen `expected_head_sha`.

This lets the attacker force Shipit to fetch and register attacker-influenced commit history/SHAs into a victim stack's commit graph without ever holding real GitHub push access or a real webhook secret for that victim org, undermining the "an organization that authenticated versus the repository that is written" trust binding. Downstream, this can influence continuous-delivery/eligible-commit selection (`trigger_continuous_delivery`) for the victim stack, which can lead to deploys against attacker-influenced state — meeting the "unauthorized deploy" bar for High/Critical impact. I was not able to fully trace, within remaining budget, whether `GithubSyncJob#append_commit` performs additional server-side validation against the real GitHub API response (it does call `stack.github_commits`, which uses `stack.github_api`, itself scoped by the Stack's real `owner`/org, not the spoofed one) — this partially mitigates the worst-case (commit content is still fetched from the real GitHub API for the *targeted* stack's actual org), so the primary confirmed impact is an unauthorized trigger of sync/build activity against a targeted stack using attacker-chosen `expected_head_sha` and timing, bypassing the intended per-organization webhook authentication boundary.

### Likelihood Explanation
Requires only that the Shipit instance is configured with the documented multi-org GitHub App layout and that at least one configured organization intentionally or accidentally has no `webhook_secret` set — both explicitly supported/shown in `docs/setup.md` and example secrets files. No GitHub credentials, session, or `ApiClient` token are needed; the request is a plain unauthenticated HTTP POST to `WebhooksController#create`.

### Recommendation
Bind the signature-verifying organization to the same repository actually processed by the handlers: derive `repository_owner` for signature verification from the exact same field the handlers use (`repository.full_name`'s owner segment), and/or reject/require a non-blank `webhook_secret` for every configured organization, and/or have handlers verify that `payload.dig('repository','owner','login')` matches `repository.full_name`'s owner before acting.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (no `webhook_secret`) and `victim-org` (real stacks, real secret) — matching the documented pattern in `config/secrets.development.shopify.yml`/`docs/setup.md`.
2. POST to `/webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgOne")` → `verify_webhook_signature` returns `true` (no secret configured), regardless of `X-Hub-Signature`.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for that victim stack with the attacker-chosen `expected_head_sha`, without ever validating anything against `victim-org`'s real webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
