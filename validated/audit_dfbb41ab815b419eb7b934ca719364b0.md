### Title
Stale `DelegateGrant` resurrects when a transferred position NFT returns to its original owner — (`contracts/controller/src/storage/account.rs`)

### Summary
When a position NFT is transferred, the controller leaves the `Delegates(account_id)` entry untouched. Grants are stamped with `granted_by`, so reads filter them out for the new owner — but the entry is never deleted. If the token ever returns to the original owner, the previous owner's delegate list silently becomes live again. This is the same bug class as the Visor `transferERC721` finding: an auxiliary per-token record is not cleaned up on transfer and later reactivates.

### Finding Description
`get_delegates` filters the stored `DelegateGrant` by `granted_by == owner`, so an ownership change only *invalidates* reads, it does not remove the entry (`contracts/controller/src/storage/account.rs:174-181`). The only paths that delete a stale grant are `remove_delegate` (called explicitly by the owner, `storage/account.rs:226-247`) and `remove_account_entry` (account deletion). There is no hook on `PositionNft::transfer`/`transfer_from` — the controller cannot observe transfers, and `burn` is the only lifecycle coupling (`position-nft/src/contract.rs:88-95`, `account.rs:159-163`).

The test `remove_delegate_purges_stale_grant_preventing_resurrection` (`controller/tests/storage/account.rs:179-225`) confirms the intended invariant — a stale grant "must not resurrect when the NFT returns to its original owner" — but that purge only happens when the *new* owner happens to call `remove_delegate`. If nobody calls it, the stale grant persists indefinitely:

1. Alice calls `add_delegate(account_id, M)` — grant stored as `{granted_by: Alice, delegates: [M]}`.
2. Alice transfers the position NFT to Bob (e.g., sells the position). The `Delegates(account_id)` entry still says `granted_by: Alice`.
3. Bob never touches delegates; the position is transferred back to Alice (buyback, cancelled sale, OTC return, or Alice controlling both addresses).
4. `get_delegates(account_id, Alice)` now returns `[M]` again — `is_owner_or_delegate` (`account.rs:115-127`) accepts M, provided M is a registered active position manager.

M then regains every delegate-gated power over Alice's account without any fresh authorization: `multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `migrate_from_blend` (all reach `require_owner_or_delegate`, `account.rs:99-110`). Because router strategies accept caller-supplied swap routes on unallowlisted venues, a resurrected delegate can route the account's collateral through a self-serving trade and extract value — theft of user funds.

### Impact Explanation
Permanent unauthorized control, not just a stale-record issue: a delegate that the owner reasonably believed was severed by transferring the position regains the ability to move collateral and debt through arbitrary swap routes. This enables theft of user funds via value-extracting routes (e.g., `swap_collateral` into a pool the delegate trades against), satisfying the theft-of-funds impact criterion.

### Likelihood Explanation
Medium. Requires: (a) the victim to have granted a delegate that is a registered active position manager, (b) an NFT transfer away and back to the same address, and (c) no intervening `remove_delegate`/`add_delegate` call that would overwrite or purge the entry. Round-trip ownership is realistic — marketplace sales that fall through, collateralized NFT lending, or transferring between a user's own wallets. Note the NFT's own `transfer` path gives the controller no opportunity to purge, so no user action on transfer can prevent it; only the new owner explicitly calling `remove_delegate` (which returns `false` and is non-obvious) cleans up.

### Recommendation
Make stale-grant cleanup unconditional rather than dependent on an explicit `remove_delegate` call. Options: (a) treat any `Delegates(account_id)` entry whose `granted_by != current owner` as garbage and delete it lazily inside `get_delegates`/`is_owner_or_delegate` whenever a mismatched grant is observed (mirroring `remove_delegate`'s purge); (b) version grants with an epoch bumped on every observed ownership change. At minimum, document that transferring a position NFT does not revoke delegates and that grants can resurrect on return — though the lazy-purge fix is cheap and eliminates the footgun entirely.

### Proof of Concept
```rust
// contracts/controller/tests — scenario sketch
let account_id = mint_and_supply(alice);          // Alice owns account
add_delegate(&env, account_id, &alice, &manager); // Alice delegates to active manager M
nft.transfer(&alice, &bob, &token_id);            // Alice sells/transfers position
// Bob never calls remove_delegate; Delegates(account_id) still {granted_by: alice}
nft.transfer(&bob, &alice, &token_id);            // Position returns to Alice
// BUG: get_delegates(account_id, alice) == [M]; M can call swap_collateral /
// multiply / migrate_from_blend on Alice's account with no fresh authorization.
assert!(is_owner_or_delegate(&env, account_id, &manager, &alice)); // unexpectedly true
```
Supporting code: `get_delegates` filter at `storage/account.rs:174-181`; resurrection behavior demonstrated by `controller/tests/storage/account.rs:219-225` (which passes only because `remove_delegate` was invoked in between); owner/delegate gate at `account.rs:115-139`.
