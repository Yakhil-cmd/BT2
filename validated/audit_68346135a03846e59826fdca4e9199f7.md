### Title
Webhook signature verification is scoped to the payload's `repository.owner.login` while event handlers act on the independently-attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, which is read straight out of the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` or the `organization.login` field). But every event `Handler` (push, status, pull_request, membership, etc.) determines the actual Shipit `Repository`/`Stack` it mutates using a different field from that same attacker-controlled body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so the "organization whose secret authenticated the request" and "the repository the handler actually writes to" are never checked for equality.

### Finding Description [1](#0-0) 
`verify_signature` computes `repository_owner` from the raw JSON body and uses it purely to look up which `GitHubApp` config's `webhook_secret` to check the signature against: [2](#0-1) 

Meanwhile `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`, and every subclass (`PushHandler`, `ClosedHandler`, `LabeledHandler`, etc.), resolve the target repository from `payload.dig('repository', 'full_name')`: [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` and `github_app_config` do a case-insensitive, per-key lookup among configured organizations, each with its own independently-set `webhook_secret` (documented as optional/nilable): [5](#0-4) 
and `verify_webhook_signature` explicitly treats an unset secret as "verification passes": [6](#0-5) 

Because `repository.owner.login` and `repository.full_name` are two independent, attacker-supplied fields in the same unauthenticated POST body, an attacker can pick `repository.owner.login` to be any organization configured in `secrets.github` that has no `webhook_secret` set (or one whose secret they know/guess), while setting `repository.full_name` to `"other-org/tracked-repo"` — the actual full name of a Shipit-tracked stack belonging to a *different, unrelated* organization. `verify_signature` will pass (secret-less org, or correct secret for that org), but every downstream handler will act on `other-org/tracked-repo` with no relation whatsoever to the organization that "authenticated" the request.

### Impact Explanation
This breaks the deployment-trust binding "the organization whose signature/secret authenticated the request == the repository the handler is permitted to write to." Concretely reachable, unauthenticated-attacker actions once one org lacks/leaks a `webhook_secret`:
- Forge `status` events to create fabricated `CommitStatus` rows for arbitrary commits of a victim stack tracked under a completely different organization (seen directly in `WebhooksControllerTest` — the status handler persists payload fields like `state`/`target_url`/`description` verbatim), which can flip CI gating used by continuous deployment/auto-merge.
- Forge `push` events to enqueue `GithubSyncJob` for arbitrary tracked stacks regardless of which org's secret was actually verified.
- Forge `pull_request` events (`labeled`/`unlabeled`/`closed`/`reopened`) to archive/unarchive review stacks or otherwise manipulate PR-linked resources of a repository that has nothing to do with the "authenticated" organization.

This matches the report's cross-repository-write class: a value verified (the signing organization) is not the value acted upon (the target repository), letting an attacker who controls/knows a weak or absent org secret write into any other configured organization's tracked stacks — an unauthorized cross-repository state change.

### Likelihood Explanation
Exploitability requires that the Shipit deployment be configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" setup) and that at least one configured organization has no `webhook_secret` set (explicitly supported/optional per `docs/setup.md` and `config/secrets.development.example.yml`, both show `webhook_secret: # nil`) or has a secret the attacker can obtain. This is a realistic deployment shape the engine itself documents and supports, not a contrived one, and requires no session, no `ApiClient` token, and no GitHub write access — only knowledge of the target's `full_name` and the ability to send a POST to `/webhooks`.

### Recommendation
Bind the two identities together explicitly instead of trusting them independently: after selecting the `GitHubApp` via `repository_owner` and verifying the signature, assert that `repository.full_name` actually starts with `"#{repository_owner}/"` before dispatching to any handler (reject with 422 otherwise). Alternatively, derive `repository_owner` strictly from `repository.full_name.split('/').first` so there is only one attacker-controlled source of truth for organization selection, eliminating the possibility of divergence between the two fields.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org-a` (no `webhook_secret`) and `org-b` (has a tracked stack `org-b/prod-app`, `webhook_secret` set and unknown to the attacker).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/prod-app" },
  "sha": "<victim commit sha>",
  "state": "success",
  "target_url": "http://attacker.example",
  "description": "forged",
  "context": "ci/attacker"
}
```
No `X-Hub-Signature` (or any garbage value) is required, since `Shipit.github(organization: "org-a")` resolves to a `webhook_secret`-less config and `verify_webhook_signature` returns `true` unconditionally.
3. `WebhooksController#verify_signature` passes; the `status` handler creates a `CommitStatus` on the real `org-b/prod-app` commit using attacker-supplied values, even though the signature check never touched `org-b`'s secret at all.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
