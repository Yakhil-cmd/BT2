### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while status/push/check-suite handlers act on unauthenticated `repository.full_name` or global `sha` lookups - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Once the signature checks out for that organization, the request body is handed unchanged to the event handler. Several handlers then key off a *different* field of the same attacker-controlled JSON body — `repository.full_name` (for `PushHandler`/`CheckSuiteHandler`) or, worse, a bare commit `sha` with no repository scoping at all (`StatusHandler`) — to decide which `Stack`/`Commit` records to mutate. Nothing in the engine enforces that `repository.owner.login` (the field the signature was checked against) matches `repository.full_name` (the field used to select the target repository/stack), or that the signing organization has any relationship to the commit being altered.

### Finding Description
`verify_signature` picks the app/secret to validate against: [1](#0-0) [2](#0-1) 

Downstream, `Handler#stacks`/`#repository_name` resolve the target repository from a *different* JSON field: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` use that repository-scoped `stacks` helper: [4](#0-3) [5](#0-4) 

`StatusHandler` doesn't even scope by repository — it matches purely on a global commit `sha` across the entire database: [6](#0-5) 
That status is persisted via `Commit#create_status_from_github!`, which can flip a commit from pending/unknown to `success`, which in turn triggers merge/deploy evaluation: [7](#0-6) [8](#0-7) 

Shipit explicitly supports multiple independently-configured GitHub organizations, each with its own `app_id`/`webhook_secret`, sharing a single Shipit deployment: [9](#0-8) 

**Binding broken:** the organization whose webhook secret authenticated the request (`repository_owner` used in `verify_signature`) ≠ the repository/commit that the handler actually writes to (`repository.full_name` in `PushHandler`/`CheckSuiteHandler`, or an unscoped global `sha` in `StatusHandler`).

**Attack path:** In a multi-org Shipit instance, an attacker who legitimately controls a GitHub App installation for their own organization "OrgA" (and therefore knows OrgA's `webhook_secret`, since they set it when creating their own App) can POST directly to `/webhooks` with:
- `X-Github-Event: push` (or `status`/`check_suite`)
- A JSON body where `repository.owner.login` (or top-level `organization.login`) = `"OrgA"` — so `verify_signature` selects and validates against OrgA's known secret
- But `repository.full_name` = `"OrgB/victim-repo"` (for push/check_suite), or, for `status`, simply any known commit `sha` belonging to a completely unrelated stack in OrgB
- `X-Hub-Signature` computed with OrgA's own webhook secret over that exact body

Because `verify_signature` only checks the HMAC against the secret selected by `repository_owner`, and never cross-checks that value against `repository.full_name` or against the commit's actual owning stack, the signature validates successfully even though the payload targets OrgB's data.

### Impact Explanation
This crosses an authentication boundary: identity authenticated (OrgA's webhook secret) is not the same as the resource written (OrgB's stack/commit). Concretely:
- `StatusHandler` lets the OrgA-authenticated attacker write CI statuses (including `success`) onto **any** commit in the database matching a chosen `sha`, regardless of which org/repo/stack owns it. Since flipping a commit to `success` triggers `schedule_continuous_delivery` and `stack.schedule_merges`, this can bypass CI-gating for an unrelated stack's continuous-deployment or merge-queue logic — an unauthorized deploy/merge trigger, which is explicitly listed as Critical impact.
- `PushHandler`/`CheckSuiteHandler` allow forcing a `GithubSyncJob`/check-run refresh against an arbitrary victim stack picked purely from the unauthenticated `repository.full_name` field, again despite having authenticated as a different organization.

### Likelihood Explanation
Requires: (1) the Shipit deployment configured for more than one GitHub organization (a documented, supported configuration), and (2) the attacker controls a legitimate GitHub App installation/webhook secret for at least one of those organizations — i.e., they are a normal, authorized tenant of the shared Shipit instance, not a privileged Shipit user, and needs no GitHub write access to the victim org. This satisfies "unprivileged attacker" while still crossing an authentication boundary.

### Recommendation
In `WebhooksController#verify_signature`, or centrally in `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to select/verify the webhook secret is the same organization embedded in `repository.full_name` (and reject if they diverge). Additionally, `StatusHandler#process` should scope `Commit.where(sha: params.sha)` to commits belonging to stacks whose repository owner matches the verified `repository_owner`, rather than matching `sha` globally.

### Proof of Concept
Not independently executable from static analysis alone — the index does not include a live GitHub App/webhook_secret pair to demonstrate signature generation end-to-end. Conceptually verified via code reading:
1. Configure Shipit with two orgs, `OrgA` (attacker-controlled webhook secret `secretA`) and `OrgB` (victim, has stack `orgb/victim`, with a commit of known `sha`).
2. POST to `/webhooks` with header `X-Github-Event: status`, body `{"sha": "<victim sha>", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "OrgA"}}}`, and `X-Hub-Signature: sha1=<hmac(secretA, body)>`.
3. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against `secretA`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, setting `success` on the victim's commit in `OrgB`'s stack — triggering `schedule_continuous_delivery`/`schedule_merges` for a stack the attacker never authenticated against.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
