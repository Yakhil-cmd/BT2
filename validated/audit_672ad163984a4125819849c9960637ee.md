### Title
Commission-update timing rule removed for `UpdateCommissionBps` (SIMD-0291) reintroduces the reward-sandwiching bug class the legacy rate limit was built to prevent - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote program has two mechanisms to update a vote account's commission split between the validator and its delegators/stakers: the legacy `UpdateCommission` instruction and the newer basis-points `UpdateCommissionBps` instruction (SIMD-0291). The legacy path enforces a timing rule that prevents commission increases too close to reward distribution — precisely the class of "commission sandwich" fix that cLabs implemented for Celo's `Validators.updateCommission`. The new bps-based path explicitly removes this rule by design, per an in-code comment referencing SIMD-0249/SIMD-0291.

### Finding Description
`update_commission()` enforces `is_commission_update_allowed(clock.slot, epoch_schedule)` for commission *increases*, returning `VoteError::CommissionUpdateTooLate` if the update happens too late in the epoch [1](#0-0) . This is the direct analog of the fix cLabs shipped for the Celo H02 report (queue/delay commission changes so members have time to react).

`update_commission_bps()`, used by the newer `UpdateCommissionBps` instruction that sets `inflation_rewards_commission_bps` / `block_revenue_commission_bps` on `VoteStateV4`, contains no such check — only a signer check on the authorized withdrawer — with the comment "No commission update rule, per SIMD-0249 and SIMD-0291" [2](#0-1) . This is confirmed as an intentional design choice, not an oversight, by the corresponding test's docstring: "Unlike test_update_commission, SIMD-0291 has no timing restrictions... Updates are always allowed regardless of epoch position." [3](#0-2) 

For the `InflationRewards` commission kind, this is mitigated one layer up: `redeem_delegation_rewards()` reads the commission used for payout from a **prior-epoch snapshot** of the vote account when `delay_commission_updates` is active, whether the value is legacy-percentage or bps-based [4](#0-3) . So a validator flipping `inflation_rewards_commission_bps` to 100% right before distribution should not actually change what gets paid out for the *current* epoch's inflation rewards — the runtime uses the value in effect as of the prior epoch's cached vote account.

For the `BlockRevenue` commission kind (`block_revenue_commission_bps`, SIMD-0123/SIMD-0232), I could not locate and verify, within available tool calls, the exact code that applies this commission to split per-block revenue deposits (this logic appears to live near `DepositDelegatorRewards` handling in `programs/vote/src/vote_processor.rs`, referenced but not fully inspected). `calculate_block_reward()` only distributes an already-computed `pending_delegator_rewards` pool proportionally to stake; it does not show where/when the commission cut is taken from gross block revenue [5](#0-4) . If that deposit path applies the *live* `block_revenue_commission_bps` at time of deposit (which appears likely, since the instruction has explicitly "no timing restriction"), a validator could raise its block-revenue commission to 100% immediately before a block's revenue is deposited/distributed and set it back afterward, taking the entire block-revenue share of delegator rewards for a given block/epoch with no time-lock protection — exactly the Celo H02 pattern, but I cannot confirm this with certainty since I was unable to inspect that deposit function.

### Impact Explanation
If block-revenue commission changes are applied live (unconfirmed), a vote-account/withdraw authority could unilaterally redirect delegator-earned block revenue to itself for one or more blocks by toggling `block_revenue_commission_bps` to its maximum immediately before revenue deposit, then reverting it — a stake/reward corruption scenario matching the "Validate" criteria (stake or reward corruption). For `InflationRewards`, the identified snapshot-based delay in `redeem_delegation_rewards` appears to already prevent this specific attack, reducing confirmed impact to the `BlockRevenue` commission kind only, which remains unverified.

### Likelihood Explanation
The instruction is reachable from any vote account's authorized withdrawer via a normal signed transaction (`UpdateCommissionBps`), requiring only that account's own signature — no special network or leader privilege — matching the "unprivileged transaction sender" scope of this review, gated behind the relevant feature flags (`commission_rate_in_basis_points`, `delay_commission_updates`, `block_revenue_sharing`) [6](#0-5) .

### Recommendation
Confirm whether the block-revenue-sharing deposit path (`DepositDelegatorRewards` and related handler code) reads `block_revenue_commission_bps` live or via a delayed/snapshotted value analogous to the inflation-rewards path. If it reads the live value, apply the same epoch-delay mechanism used for inflation rewards (reading commission from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) to block-revenue commission before it is used to compute delegator payouts, or reinstate an `is_commission_update_allowed`-style timing gate inside `update_commission_bps()` for the `BlockRevenue` kind.

### Proof of Concept
Not confirmable as a concrete PoC within the current investigation — the decisive missing piece is the block-revenue commission deposit/application code path, which was not located in this session. The confirmed, provable part of this finding is limited to: (1) `update_commission_bps()` lacking any timing restriction by design [2](#0-1) , and (2) the fact that the timing restriction exists specifically to prevent this bug class for the legacy commission field [1](#0-0) . Full exploitability for `block_revenue_commission_bps` requires verifying the deposit-time application logic, which should be examined with full filesystem access (e.g., a Devin session) rather than the indexed snippets available here.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
