### Title
Caller-chosen flash loan receiver lets anyone drain fee from any contract with a pool allowance - (File: contracts/pool/src/ops/flash.rs)

### Summary
`controller.flash_loan` accepts an arbitrary `receiver` address chosen by the caller, and the pool settles the loan by pulling `amount + fee` from that receiver via `token.transfer_from`, relying solely on the receiver's pre-existing allowance to the pool. An unprivileged attacker can name any contract that (a) implements `execute_flash_loan` without gating the initiator and (b) holds a token allowance to the pool, and each call burns `fee` of the victim's balance, repeatable until the allowance or balance is exhausted. This is the same bug class as the Yield `Join.flashLoan` griefing finding.

### Finding Description
The controller entrypoint `flash_loan(caller, hub_asset, amount, receiver, data)` only requires `require_authorized_caller(caller)` — the `receiver` is a free parameter validated only as a WASM contract (`require_wasm_receiver`), not as the caller or an authorized party (`contracts/controller/src/strategies/flash_loan.rs:22-32`). In the pool, `apply` transfers `amount` to `receiver`, invokes `execute_flash_loan` on it, then `collect_repayment` requires `asset.allowance(receiver, pool) >= amount + fee` and executes `asset.transfer_from(pool, receiver, pool, &terms.total_repayment)` (`contracts/pool/src/ops/flash.rs:60-67`, `166-179`). The repayment is pulled from the victim's balance using the victim's allowance — there is no check that the initiator controls the receiver or that the receiver consented to this specific loan. The excess allowance is explicitly permitted by design (INV-FLASH-01 / ADR-0010: "extra allowance is allowed"), so a receiver that ever approved the pool for more than one loan's repayment, or with a non-trivial `expiration_ledger`, is exposed. The fee pulled each round is booked as protocol revenue (`finalize`/`book_fee`), so the victim's funds are consumed rather than recoverable.

### Impact Explanation
For every invocation, the victim receives `amount` and then has `amount + fee` pulled from its balance — a net loss of exactly `fee` per call, with zero cost to the attacker beyond transaction fees. Repeating the call drains the victim's balance in `fee` increments for as long as its allowance to the pool covers `amount + fee`. This is theft/burning of user funds caused purely by protocol-side authorization structure: the pool pulls repayment from a caller-designated third party.

### Likelihood Explanation
Exploitation requires a victim contract that implements a permissive `execute_flash_loan` callback (returns without reverting) and holds a live allowance to the pool ≥ `amount + fee`. The documented receiver pattern approves exactly `amount + fee` with next-ledger expiration inside the callback, and `transfer_from` consumes it, so protocol-generated approvals leave no residue; however nothing prevents a contract from granting the pool a larger or longer-lived allowance (the design deliberately tolerates excess allowance), and the published mock receiver demonstrates an ungated callback. Because the preconditions are not created by in-scope protocol flows — no other code path asks a contract to approve the pool — realization depends on a third-party contract's own approval/callback choices rather than purely protocol-driven state, which lowers likelihood.

### Recommendation
Bind the loan to the initiator: require `receiver == initiator` (or have the receiver `require_auth()`/`authorize_as_current_contract` inside the callback for a pre-registered plan, as the skill docs already recommend gating `initiator` to `cfg.operator`), so a caller cannot force repayment from an unrelated contract. Alternatively, switch to push-based settlement — have the receiver transfer `amount + fee` to the pool inside the callback and check the balance delta — so no standing allowance can be consumed by a third party's call. At minimum, drop the pull-via-allowance model's tolerance for third-party receivers.

### Proof of Concept
1. Victim contract `V` implements `execute_flash_loan` permissively and has previously called `token.approve(V, pool, A, expiration)` with `A >= amount + fee` and `expiration` still in the future (e.g., an over-approval or a long-lived grant).
2. Attacker calls `controller.flash_loan(attacker, hub_asset, amount, V, data)` with `amount + fee <= A`.
3. Pool transfers `amount` to `V`, invokes `V.execute_flash_loan` (returns normally), checks `allowance(V, pool) >= amount + fee`, then `transfer_from`s `amount + fee` from `V` to the pool (`contracts/pool/src/ops/flash.rs:173-179`).
4. `V`'s net balance decreases by `fee`; `fee` is booked as protocol revenue. Attacker repeats until `A` or `V`'s balance is drained.

Note: whether any real deployed contract would satisfy the victim preconditions is unverifiable from in-scope code alone — the protocol's own receivers never leave residual allowance — so this analog sits at the boundary of the "third-party contract" exclusion. The pull-from-arbitrary-receiver structure is nonetheless identical to the Yield finding.
