In `arbiter_contract.js`, the shared-address definition (`deriveSharedAddress`) embeds the ArbStore's cut-payout address using `arbstoreInfo.address` obtained fresh via `arbiters.getArbstoreInfo()` at the moment the shared address is created [1](#0-0) , and this address is baked into the smart-contract definition's `"has"` output condition [2](#0-1) . However, when the contract is later completed, `complete()` does not use that address from the (immutable, already-hashed) shared-address definition — instead it separately re-fetches/caches `objContract.arbstore_address` via `fillArbstoreAddresses()` and pays out to that value [3](#0-2) [4](#0-3) . `fillArbstoreAddresses()` only fetches once and caches the result permanently in `objContract.arbstore_address`/DB, short-circuiting on any subsequent call even if the ArbStore's registered address changes [5](#0-4) . The authoritative arbstore address for an arbiter is resolved from the hub via `hub/get_arbstore_address`, which simply looks up the current `arbiter_locations.arbstore_address` row for that arbiter [6](#0-5) , i.e. the value can legitimately be updated later, but the payer's cached `objContract.arbstore_address` will not follow it.

This exactly mirrors the M-3 bug class: the payout in `complete()` uses a locally cached/immutable address (`objContract.arbstore_address`, fetched once via `fillArbstoreAddresses`) instead of re-deriving it from the value that was actually authorized/committed in the shared-address `arrDefinition` at contract-creation time (`arbstoreInfo.address` baked into the `"has"` condition in `deriveSharedAddress`). If the ArbStore's registered address is rotated between contract creation and `complete()`, the peer-signed shared address definition (created via `wallet_defined_by_addresses.js`, checked by `oscript`/definition evaluation in `definition.js`) requires the fee output to go to the **address embedded at contract creation**, while `complete()`'s `opts.asset_outputs`/`opts.base_outputs` will construct a payment to the **currently cached** `objContract.arbstore_address` [7](#0-6) . Because these two are read from two different, uncoordinated sources, a mismatch produces a transaction that fails the address definition's `"has"` condition, and thus the finalizing payment cannot be composed/broadcast successfully — a payer is unable to release the contract's fee cut to the correct (or any) valid arbstore address, effectively freezing the shared-address funds mid-payout.

### Title
Arbiter contract completion pays to a stale cached ArbStore address instead of the address committed in the shared-address definition - (File: arbiter_contract.js)

### Summary
`deriveSharedAddress()` bakes the ArbStore payout address (fetched live via `arbiters.getArbstoreInfo`) into the shared address's `oscript` definition at contract-creation time. `complete()`, which actually executes the payout, ignores this committed address and instead uses a separately cached value `objContract.arbstore_address`, populated once by `fillArbstoreAddresses()` and never refreshed thereafter.

### Finding Description
When a contract with an ArbStore cut is created, `deriveSharedAddress` requests `arbiters.getArbstoreInfo(contract.arbiter_address)` and embeds the returned `arbstoreInfo.address` directly into the definition's `"has"` output condition, requiring any spending transaction from the shared address to send the ArbStore's cut to that specific address [8](#0-7) [2](#0-1) . This value is not persisted on the contract at creation time in a way that is reused later; instead, `complete()` calls `fillArbstoreAddresses(objContract)`, which independently queries the hub/ArbStore for the address and caches it, short-circuiting on any subsequent invocation once `objContract.arbstore_address` is set [5](#0-4) [3](#0-2) . It then builds the payout outputs using this separately-sourced, potentially stale value [4](#0-3) . Because `arbiter_locations.arbstore_address` for a given `arbiter_address` is a mutable row on the hub that can change over time [6](#0-5) , and because the two code paths (`deriveSharedAddress` at creation vs. `fillArbstoreAddresses`/`complete` at payout) each independently resolve "the arbstore address" without cross-checking against what was actually committed in the on-chain address definition, they can diverge.

### Impact Explanation
If the value diverges, the composed multi-payment in `complete()` will not satisfy the `"has"` output condition of the shared address's `oscript` definition (which demands the fee go to the address that was frozen into the definition at creation), so the unit will be rejected/invalid, or the payer will unknowingly build a transaction that cannot spend from the shared address at all. This can permanently strand the contract's escrowed funds in the shared address (AA-analogous fund freezing), since neither party can compose a valid payment matching the hardened condition. This matches the "AA fund loss or freezing" acceptance category for this exercise.

### Likelihood Explanation
This requires the ArbStore's registered address for a given arbiter to be rotated (a normal administrative/config-update operation on the hub, not a malicious actor) between contract creation and its `complete()` call — plausible for long-running or delayed contracts (`ttl` defaults to a week) [9](#0-8) . No malicious peer, hub or network behavior is needed; it's a straightforward reachable path for any legitimate contract counterparty (payer) calling `complete()` normally.

### Recommendation
`complete()` should not re-resolve or rely on a separately cached `arbstore_address`; instead it should read the exact address that was committed into the shared address's on-chain `arrDefinition` (i.e., parse `arbstoreInfo.address`/the `"has"` condition's `address` field from `wallet_defined_by_addresses.readSharedAddressDefinition`, the same source already used to derive `peer_amount`/`arbstore_amount` at lines 753-756) rather than `objContract.arbstore_address` populated by `fillArbstoreAddresses`. This guarantees the payout always targets the address actually authorized in the spending condition, regardless of any later ArbStore address rotation.

### Proof of Concept
1. Party A and Party B create an arbiter contract with `arbiter_address` X; `deriveSharedAddress` calls `arbiters.getArbstoreInfo(X)` returning ArbStore address `ADDR1`, which gets embedded in the shared address's `"has"` condition and the resulting shared address is derived/shared between A and B [10](#0-9) .
2. Funds are paid into the shared address; contract status becomes `"paid"`.
3. Before `complete()` is called, the hub operator updates `arbiter_locations.arbstore_address` for arbiter X from `ADDR1` to `ADDR2` (a legitimate administrative update reflected via `hub/get_arbstore_address`) [6](#0-5) .
4. Party A calls `complete(hash, ...)`. Since `objContract.arbstore_address` was not set before, `fillArbstoreAddresses` fetches and caches `ADDR2` [5](#0-4) .
5. `complete()` builds `asset_outputs`/`base_outputs` sending the ArbStore cut to `ADDR2` [4](#0-3) , but the shared address's `oscript` definition (embedded at step 1) requires the cut go to `ADDR1`. The composed unit fails the spending condition and cannot be validly signed/broadcast, leaving the escrowed funds stuck in the shared address.
