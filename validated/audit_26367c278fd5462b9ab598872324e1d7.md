### Title
Webhook authentication organization is not bound to the repository being written, allowing cross-org triggering of stack syncs/deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using the organization login taken from the payload's `repository.owner.login` (falling back to `organization.login`), but the event handlers that act on the payload (e.g. `Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`) resolve the target repository from the independent `repository.full_name` field of the *same attacker-controlled JSON body*. Because these two fields are never checked for consistency, an entity that legitimately possesses the webhook secret for one onboarded organization can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` names a stack belonging to a completely different organization hosted on the same Shipit instance.

### Finding Description
The binding that should hold is:
`authenticated_org (used to pick/verify the HMAC secret) == owning_org (of the repository whose stacks are mutated)`

`verify_signature` computes the org to authenticate against like this: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` returns the `GithubApp`/secret configured for *that* organization; `verify_webhook_signature` then HMACs the raw body against that secret.

Once the signature is accepted, `create` dispatches the same raw payload to the registered handlers: [3](#0-2) 

Handlers such as `PushHandler` resolve which `Stack`s to act on via `Handler#stacks`/`#repository_name`, which reads a *different* JSON field of the same payload — `repository.full_name` — with no cross-check against the organization used for signature verification: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` and `repository.full_name` are two independently-controlled strings inside the same unsigned-at-the-field-level JSON body (only the raw byte string is HMAC'd, not any semantic binding between these two fields), an attacker who is a legitimate GitHub App/organization administrator for **Org A** (and therefore knows or can trigger delivery of a validly-signed payload for Org A) can set:
- `repository.owner.login = "org-a"` (so `repository_owner` picks Org A's secret and the signature verifies)
- `repository.full_name = "org-b/victim-repo"` (so `PushHandler` operates on Org B's `Stack`s)

This lets the request pass authentication for Org A while its side effects are applied to Org B's stacks — i.e., the organization that authenticated is not the organization whose repository is written, which is exactly the deployment-trust binding the report's bug class targets (analogous to the `bountyPullerTo_`/`account_` mismatch in the reference report, where the entity credited/verified differs from the entity actually affected).

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every not-archived stack on the branch of the spoofed repository. If continuous deployment/deployment is configured on the targeted (Org B) stack, this can force an out-of-band resync/deploy cycle on a stack the attacker has no legitimate relationship to, without ever needing Org B's webhook secret, a Shipit session, or repository write access on Org B — satisfying the "unauthorized deploy" High/Critical criterion. Other handlers keyed the same way (`StatusHandler` via `Commit.where(sha: ...)`, `CheckSuiteHandler`, etc.) are similarly reachable cross-org, since none of them cross-validate the authenticating organization against the repository fields they act on.

### Likelihood Explanation
Exploitation requires only possession of a validly configured webhook secret/GitHub App for *any one* organization onboarded to the shared Shipit instance — a realistic bar for a multi-tenant Shipit deployment where separate teams/orgs each control their own GitHub App installation and secret, but should not be able to affect each other's stacks. No Shipit session, `ApiClient` token, or GitHub repository write permission to the victim org is needed, only control over the raw payload sent to the shared webhook endpoint signed with one's own org's secret.

### Recommendation
After `verify_signature` succeeds, require that the organization/owner derived from every payload field actually consumed by a handler (`repository.full_name`, `repository.owner.login`, etc.) matches the organization that was used to select and verify the HMAC secret. Reject the webhook (422) if they diverge, rather than trusting the `repository.full_name` field independently of the authenticated organization.

### Proof of Concept
1. Attacker administers a GitHub App/organization "org-a" that is legitimately configured in this Shipit instance with `webhook_secret_a`.
2. Attacker crafts a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_a, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"org-a"`; `Shipit.github(organization: "org-a")` returns Org A's app; `verify_webhook_signature` succeeds because the attacker used Org A's real secret.
5. `PushHandler#repository_name` reads `repository.full_name == "org-b/victim-repo"`, looks up `Repository.from_github_repo_name("org-b/victim-repo")`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Org B's stacks — an org the attacker never authenticated as and has no access to.
