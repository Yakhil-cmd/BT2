I have sufficient evidence to conclude the analysis. The core mechanism (branch is checked out and `shipit.yml` executed for review stacks) is documented behavior of the feature itself; the actual bug is the bypass of the `review_stacks_enabled` gate.### Title
`OpenedHandler#provision?` operator-precedence bug lets `review_stacks_enabled` be bypassed for `allow_with_label`/`prevent_with_label` repos, letting an attacker-controlled PR branch become a `ReviewStack#branch` and be queued for provisioning - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with three provisioning-behavior disjuncts using `&&`/`||` without grouping parentheses, so Ruby's operator precedence (`&&` binds tighter than `||`) makes `review_stacks_enabled` gate only the `allow_all` branch, not `allow_with_label`/`prevent_with_label`. Consequently, on any repository configured with `provisioning_behavior: prevent_with_label` (with or without `review_stacks_enabled` truly enabled), an attacker who opens a PR with no labels (the default state of any freshly opened PR) reaches `ReviewStackAdapter#create!`, which persists `params.pull_request.head.ref` — a string the attacker fully controls — verbatim into `ReviewStack#branch`, then enqueues the stack via `Shipit::ReviewStackProvisioningQueue.add`.

### Finding Description
Intended binding: `stack_created ⟹ repository.review_stacks_enabled == true`, for every `provisioning_behavior` value.

Actual code, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` is only ANDed into the first disjunct. For a repository with `provisioning_behavior == prevent_with_label`, the third disjunct fires whenever the PR has no matching label — which is the default state of any newly opened PR — completely independent of `review_stacks_enabled`.

Call path: `OpenedHandler#process` → `provision?` returns `true` → `ReviewStackAdapter#find_or_create!` → `create!` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:72-94`) builds `stack_attributes` with `branch: params.pull_request.head.ref` taken directly from the webhook payload with no allow-list/maintainer check, then calls `scope.create!(stack_attributes)` and `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

`ReviewStackProvisioningQueue#provision` (`app/models/shipit/review_stack_provisioning_queue.rb:29-37`) subsequently calls `stack.provision`, which is documented to check out `ReviewStack#branch` and run its `shipit.yml` provisioning tasks: [3](#0-2) 

No signature check, `ExplicitParameters` schema, or model validation intervenes to restrict `branch` to an approved value: the `PullRequest` schema only requires `head.ref` to be a `String`, and `Repository`/`Stack` validations constrain `owner`/`name` format, not `branch` content. [4](#0-3) 

The test suite confirms the gap is untested: `opened_handler_test.rb`'s only `provisioning_enabled: false` test uses `behavior: :allow_all`; there is no test asserting that `review_stacks_enabled: false` combined with `:allow_with_label` or `:prevent_with_label` prevents stack creation. [5](#0-4) 

### Impact Explanation
Any repository whose `provisioning_behavior` has ever been set to `prevent_with_label` (or `allow_with_label`, in the label-present case) will provision review stacks for arbitrary forked PRs even if a maintainer has separately disabled `review_stacks_enabled`, believing that toggle fully controls provisioning. Since `ReviewStack#branch` is set verbatim to the attacker's fork branch ref with no maintainer-approval or allow-list gate, this results in a `Shipit`-managed task execution pipeline being triggered against attacker-controlled repository content, matching the "unauthorized deploy" / stack mutation impact category. This is repeatable against every repository sharing this misconfiguration, and each PR the attacker opens produces one new `ReviewStack` bound to an unapproved branch.

### Likelihood Explanation
Requires a repository owner to have configured `provisioning_behavior` to `allow_with_label` or `prevent_with_label` (a supported, documented setting) at some point, and to also have `review_stacks_enabled` in a state that does not match the operator's actual intent for that behavior branch — e.g., toggling `review_stacks_enabled` off later while a non-`allow_all` behavior is still set, or simply never realizing `review_stacks_enabled` doesn't gate `prevent_with_label`. No secrets or elevated privileges are needed by the attacker: opening a PR from a fork with no label is the default action any GitHub user can perform.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three disjuncts:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to the structurally identical `unarchive?`/`archive?` logic in `reopened_handler.rb`, `labeled_handler.rb`, and `unlabeled_handler.rb` if they share this pattern (`reopened_handler.rb:70-75` has the identical unparenthesized precedence bug).

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does NOT create stacks when review_stacks_enabled is false, even for prevent_with_label with no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix this assertion fails: a `ReviewStack` is created with `stack.branch == payload["pull_request"]["head"]["ref"]` (the attacker's fork branch) even though `repository.review_stacks_enabled == false`, demonstrating the broken binding `review_stacks_enabled == true ⟹ no stack created` for the `prevent_with_label`/`allow_with_label` branches.
