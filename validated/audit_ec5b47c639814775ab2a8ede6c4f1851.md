### Title
`get_reserves()` infers pool existence from raw account balances instead of validated `Pools` storage - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet_asset_conversion::Pallet::get_reserves()` [1](#0-0)  determines whether a pool has "liquidity" purely by reading the raw token balances held at the deterministically-computed pool account (`T::PoolLocator::pool_address(&asset1, &asset2)`), the same class of bug as the reported `_existsPairPool()` issue that used `ERC20.balanceOf()` on a computed UniswapV2 pair address without checking whether the pair contract actually exists. Here, the FRAME analog never consults the `Pools` storage map (`Pools::<T>::get(&pool_id)`) [2](#0-1)  that records whether a pool was actually created via the `create_pool` extrinsic. Instead, it treats any non-zero token balance sitting at the computed pool address as proof of a real, tradable pool.

### Finding Description
The pool account address for an asset pair is a deterministic, publicly-computable function of the two asset identifiers (via `PoolLocator`), analogous to a CREATE2-style deterministic pair address in the EVM report. Because it is deterministic and requires no special permission to derive or to send tokens to, any signed account can transfer small ("dust") amounts of both `asset1` and `asset2` directly to that address using ordinary `transfer`/`transfer_keep_alive` extrinsics — no privileged role, governance, or malicious validator/collator is required.

`get_reserves()` is the single source of truth used by:
- `quote_price_exact_tokens_for_tokens` / `quote_price_tokens_for_exact_tokens` [3](#0-2) , exposed via the `QuotePrice` trait [4](#0-3) .
- The XCM `SingleAssetExchangeAdapter::quote_exchange_price` used by `xcm_executor::traits::AssetExchange` to price cross-chain asset exchanges [5](#0-4) .
- `pallet-asset-conversion-tx-payment`, which relies on these quote functions to convert transaction fees into arbitrary assets.

All of these callers only check `get_reserves()`/quote success or failure — they never independently verify that the pool pair is registered in `Pools::<T>`. This mirrors the report's root cause exactly: "This logic never verifies that `pool` has deployed contract code, nor does it read real reserves … it thus treats any stray token balances at that address as liquidity." The FRAME equivalent never verifies the pool was registered via `create_pool` (the `Pools` map), and instead treats any stray balance at the pool address as reserves.

By contrast, other pool-mutating entry points such as `do_add_liquidity` and `do_remove_liquidity` correctly gate on the `Pools` map first (`Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?`) [6](#0-5) [7](#0-6) , which shows the intended invariant (a pool "exists" iff it is in `Pools` storage) is inconsistently enforced across the pallet — `get_reserves()`/the quote path is the outlier.

### Impact Explanation
Because quoting logic can be fooled into believing a non-existent (never `create_pool`'d) pair has real reserves, downstream consumers that rely on a `Some`/`Ok` quote as a signal of a usable pool (XCM asset-exchange quoting, transaction-fee-in-asset quoting) can be led into initiating swaps or fee conversions against a pool that was never actually set up with proper LP accounting. When an actual swap is attempted, it will operate against attacker-seeded dust balances rather than genuine liquidity, and — since real swap paths are executed transactionally (`#[transactional]`) — the swap will most likely fail/revert once it attempts to move an output amount the dust reserves cannot support, producing the same "broken swap path / denial of service" outcome described in the original report, rather than fund loss.

### Likelihood Explanation
Reachability requires only an ordinary signed transfer to a publicly-computable account — no elevated privilege. However, I was unable to fully verify within the available search budget whether `do_swap_exact_tokens_for_tokens`/`SwapCredit::swap_exact_tokens_for_tokens` (in `substrate/frame/asset-conversion/src/lib.rs`) perform an independent `Pools::<T>::get` existence check before relying on `get_reserves()`-derived amounts, which would materially change whether the end-to-end impact is a hard revert (DoS on quote-driven decision paths, consistent with the report) or something more benign that is simply rejected earlier. This uncertainty, combined with the fact that the concrete consequence here is bounded to reverted transactions/false quotes rather than theft or unbacked issuance, places this at low/medium severity rather than Critical/High, and I could not confirm a matching live Parity bounty scope classification for this exact code path within the time available.

### Recommendation
`get_reserves()` should first confirm `Pools::<T>::get(&pool_id)` returns `Some(_)` (i.e., the pool was actually created) before treating balances at the derived pool account as reserves, mirroring the pattern already used in `do_add_liquidity`/`do_remove_liquidity`. This closes the "false pool exists" gap and ensures `QuotePrice`/`AssetExchange` consumers only receive quotes backed by pools with committed on-chain existence, not incidental dust balances.

### Proof of Concept
Not executed. I identified the guard gap by code inspection: `get_reserves()` [1](#0-0)  omits the `Pools::<T>::get(&pool_id)` check present in `do_add_liquidity`/`do_remove_liquidity`. A full local FRAME integration reproduction (deriving `PoolLocator::pool_address` for an unregistered pair, transferring dust `asset1`/`asset2` to it, then calling `quote_price_exact_tokens_for_tokens`/`get_reserves` to observe a non-`PoolEmpty`/`PoolNotFound` result) was not run due to tool/iteration limits, and the downstream `do_swap` gating behavior was not conclusively traced — these are flagged above as open verification items rather than asserted as proven.

		pub fn get_reserves(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
		) -> Result<(T::Balance, T::Balance), Error<T>> {
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			let balance1 = Self::get_balance(&pool_account, asset1);
			let balance2 = Self::get_balance(&pool_account, asset2);

			if balance1.is_zero() || balance2.is_zero() {
				Err(Error::<T>::PoolEmpty)?;
			}

			Ok((balance1, balance2))
		}

		/// If `include_fee` is true, the quote will include the liquidity provider fee.
		/// If the pool does not exist or has no liquidity, `None` is returned.
		/// Note that the price may have changed by the time the transaction is executed.
		/// (Use `amount_out_min` to control slippage.)
		/// Returns `Some(quoted_amount)` on success.
		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
		}
