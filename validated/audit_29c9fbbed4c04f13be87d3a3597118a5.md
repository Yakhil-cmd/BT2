### Title
Unauthenticated Bridge Peer Can Forge `ServiceChainReceiptResponseMsg` to Prematurely Advance `latestAnchoredBlockNumber` Without On-Chain Confirmation — (`node/sc/sub_bridge_handler.go`)

### Summary

`writeServiceChainTxReceipts` processes receipt messages from bridge peers without verifying the receipt against the parent chain state and without checking `receipt.Status`. Any connected bridge peer can send a crafted `ServiceChainReceiptResponseMsg` whose `TxHash` matches a pending anchoring tx in the `BridgeTxPool`, causing the sub-bridge to unconditionally call `WriteAnchoredBlockNumber` and permanently remove the tx from the pool — all without the anchoring tx ever being confirmed on-chain.

### Finding Description

The entry point is `HandleMainMsg` dispatching to `handleParentChainReceiptResponseMsg`: [1](#0-0) 

That handler decodes the peer-supplied receipt slice and immediately passes it to `writeServiceChainTxReceipts` with no further gate: [2](#0-1) 

Inside `writeServiceChainTxReceipts`, the only guard is a BridgeTxPool lookup by `receipt.TxHash`. If the hash matches a pending anchoring tx, the code:

1. Decodes `AnchoringData` **from the pool tx** (not from the receipt — so the block hash/number are real, belonging to a block whose anchoring is still unconfirmed).
2. Calls `WriteAnchoredBlockNumber` unconditionally.
3. Calls `RemoveTx` unconditionally. [3](#0-2) 

There is **no `receipt.Status` check** anywhere in this path (confirmed: no match for `receipt.Status` or `ReceiptStatusSuccessful` in any production `node/sc/*.go` file). A receipt with `Status = 0` (failed) triggers the exact same state mutation as a successful one.

`WriteAnchoredBlockNumber` then persists the corrupted value to `chainDB`: [4](#0-3) 

### Impact Explanation

- `latestAnchoredBlockNumber` in `chainDB` is advanced to a block whose anchoring tx was never confirmed on the parent chain.
- The anchoring tx is permanently removed from `BridgeTxPool` with no retry path (the comment at line 399 explicitly notes "there is no automatic retry mechanism" for anchoring txs).
- The sub-bridge's `GetLatestAnchoredBlockNumber()` and any consumer of `ReadAnchoredBlockNumber` (APIs, monitoring, cross-chain proofs) will report a false anchored height.
- This is persistent corruption of chainDB state that breaks the anchoring settlement invariant: the sub-chain falsely asserts a state-root commitment to the parent chain that was never actually recorded there.

### Likelihood Explanation

The attacker must be a connected bridge peer. Bridge peer authentication is limited to a chainID equality check (`RegisterNewPeer`, line 466); there is no cryptographic identity verification. Any parent-chain node the sub-bridge operator connects to — including via P2P discovery — can send this message. The `broadcastServiceChainReceiptRequest` call (line 477) actively advertises pending tx hashes to all peers, giving the attacker the exact `TxHash` values needed to craft the forged receipt. [5](#0-4) 

### Recommendation

1. **Check `receipt.Status`**: reject any receipt where `receipt.Status != types.ReceiptStatusSuccessful` before calling `WriteAnchoredBlockNumber` or `RemoveTx`.
2. **Verify receipt on-chain**: before trusting a peer-supplied receipt, confirm the tx hash and block hash against the parent chain via `remoteBackend` (e.g., `TransactionReceipt` RPC call).
3. **Authenticate bridge peers**: use TLS or a shared-secret handshake so only the operator-designated parent-chain node can send receipt responses.

### Proof of Concept

1. Sub-bridge creates an anchoring tx for block N; it sits in `BridgeTxPool` with hash `H`.
2. `broadcastServiceChainReceiptRequest` sends `H` to all peers.
3. Malicious peer constructs a `ServiceChainReceiptResponseMsg` containing a single `ReceiptForStorage{TxHash: H, Status: 1}` (or even `Status: 0`).
4. Sub-bridge receives it, finds the tx in the pool, decodes the real block-N anchoring data, calls `WriteAnchoredBlockNumber(N)`, and calls `RemoveTx`.
5. Assert `chainDB.ReadAnchoredBlockNumber() == N` — confirmed without any parent-chain transaction inclusion.
6. The anchoring tx is gone from the pool; block N is never actually anchored on the parent chain.

func (sbh *SubBridgeHandler) writeServiceChainTxReceipts(bc *blockchain.BlockChain, receipts []*types.ReceiptForStorage) {
	for _, receipt := range receipts {
		txHash := receipt.TxHash
		if tx := sbh.subbridge.GetBridgeTxPool().Get(txHash); tx != nil {
			if tx.Type().IsChainDataAnchoring() {
				data, err := tx.AnchoredData()
				if err != nil {
					logger.Error("failed to get anchoring data", "txHash", txHash.String(), "err", err)
					continue
				}
				decodedData, err := types.DecodeAnchoringData(data)
				if err != nil {
					logger.Warn("failed to decode anchoring tx", "txHash", txHash.String(), "err", err)
					continue
				}
				sbh.WriteReceiptFromParentChain(decodedData.GetBlockHash(), (*types.Receipt)(receipt))
				sbh.WriteAnchoredBlockNumber(decodedData.GetBlockNumber().Uint64())
			}
			// TODO-Kaia-ServiceChain: support other tx types if needed.
			sbh.subbridge.GetBridgeTxPool().RemoveTx(tx)
		} else {
			logger.Trace("received service chain transaction receipt does not exist in sentServiceChainTxs", "txHash", txHash.String())
		}
		logger.Trace("received service chain transaction receipt", "anchoring txHash", txHash.String())
	}
}
