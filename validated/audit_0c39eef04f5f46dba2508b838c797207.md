### Title
Race in private-payment duplicate/spend-proof check allows unserialized double processing of the same private-asset output - (File: private_payment.js)

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` performs a classic check-then-act sequence — `SELECT` for a pre-existing duplicate output, and only if absent proceeds to validate and insert — without ever taking a per-unit/per-output mutex, and it is reachable concurrently from multiple untrusted paths (hub-forwarded chains, direct peer sends, and re-processing of `unhandled_private_payments`). This mirrors the kernel bug class: a check ("is this already being/been processed?") is not atomic with the action that follows, so two concurrent callers can both pass the check and both proceed to act on stale state.

### Finding Description
`validateAndSavePrivatePaymentChain` in [1](#0-0)  opens its own DB connection/transaction, `SELECT`s existing `outputs` rows to detect a duplicate private payment, and — if none is found — calls into `indivisibleAsset`/`divisibleAsset`'s `validateAndSavePrivatePaymentChain`, which internally re-checks spend proofs and double-spends via `validation.checkForDoublespends` [2](#0-1)  before writing `inputs`/`outputs` rows with `INSERT IGNORE` [3](#0-2) .

Crucially, none of this per-unit “duplicate?” check plus subsequent validate-and-save sequence is protected by any mutex keyed on the unit/message_index/output_index (or on the source output being spent). The only lock in this code path, `mutex.lock(["private_write"])`, is taken transiently and only inside the doublespend-acceptance branch to run a single `UPDATE ... SET is_unique=NULL` [4](#0-3) ; it does not serialize the surrounding `SELECT`-then-write sequence for competing spends of the same private output. As a result, two concurrent invocations of `validateAndSavePrivatePaymentChain` for the same asset/output (e.g., the same private chain resent by the hub and independently forwarded by a peer, or two competing spends of the same private coin sent to different recipients) can each open their own transaction, each pass the "duplicate" `SELECT` check while the other's write is still uncommitted, and each proceed to validate spend proofs against not-yet-committed state.

This function is reachable directly and repeatedly by any correspondent/hub without a unit-level "in progress" lock: `network.handleOnlinePrivatePayment`'s `ifKnown` branch calls `privatePayment.validateAndSavePrivatePaymentChain` directly, with the `assocUnitsInWork[unit] = true` guard explicitly commented out [5](#0-4) , and `handleSavedPrivatePayments` processes rows from `unhandled_private_payments` in parallel via `async.each` [6](#0-5) . `wallet.js`'s `handlePrivatePaymentChains` only deduplicates via a cache keyed on a hash of the whole chain array, and that cache is populated only after processing completes [7](#0-6) , leaving a window where identical or overlapping requests race through unguarded.

### Impact Explanation
If two competing spends of the same private (indivisible/divisible) asset output are submitted concurrently by a malicious sender/AA-adjacent counterparty (e.g., to two different recipients, or resent via hub and peer paths simultaneously), the lack of serialization around the duplicate/spend-proof check means both branches can pass validation before either commits, since `checkForDoublespends`'s `SELECT` against the `inputs` table and the final `INSERT IGNORE`/`UPDATE ... is_spent` writes are not mutually exclusive across the two transactions. This can let a private-payment counterparty accept two conflicting private payment chains built from the same source output, leading to unauthorized/double spending of private funds credited to two payees, which the wallet accepts as valid transactions (`callbacks.ifOk()` fires for both).

### Likelihood Explanation
This requires a concurrent race window between two calls processing overlapping private-payment data, which is a rare but realistic timing condition for a paired device or hub-relayed private payment flow — similar to the kernel bug's real-world rarity noted in the report ("about once every 5 minutes" under artificial reproduction). It does not require a malicious peer/hub/node in the excluded sense; it can be triggered by a normal (if hostile) private-payment counterparty deliberately sending the same/competing private chain through two channels (hub + direct peer) at once, which is within the reachable "private-payment counterparty" surface.

### Recommendation
Serialize `validateAndSavePrivatePaymentChain` (and by extension `indivisibleAsset`/`divisibleAsset`'s per-asset save routines) with a mutex keyed on the private output being consumed (e.g., `asset:src_unit:src_message_index:src_output_index`) or at minimum on `unit:message_index:output_index`, held for the full duration of the duplicate-check-and-save transaction, not just the narrow `is_unique=NULL` update. Re-enable/restore the `assocUnitsInWork` (or an equivalent) guard in `network.js`'s `handleOnlinePrivatePayment` `ifKnown` branch so concurrent deliveries of the same private payment are queued rather than processed in parallel.

### Proof of Concept
Not independently reproducible from static analysis alone; the described race requires precise timing of two concurrent private-payment submissions referencing the same source output through the hub/peer channels described above, analogous to the kernel PoC's multi-thread reproducer targeting the same swap entry. Confirming exploitability would require instrumenting concurrent calls to `private_payment.js`'s `validateAndSavePrivatePaymentChain` with an injected delay between its duplicate `SELECT` and the downstream `INSERT`, mirroring the kernel reproducer's delayed `swap_read_folio`.

function handleSavedPrivatePayments(unit){
	//if (unit && assocUnitsInWork[unit])
	//    return;
	if (!my_device_address) return; // skip if we don't have a wallet
	if (!unit && mutex.isAnyOfKeysLocked(["private_chains"])) // we are still downloading the history (light)
		return console.log("skipping handleSavedPrivatePayments because history download is still under way");
	var lock = unit ? mutex.lock : mutex.lockOrSkip;
	lock(["saved_private"], function(unlock){
		var sql = unit
			? "SELECT json, peer, unit, message_index, output_index, linked FROM unhandled_private_payments WHERE unit="+db.escape(unit)
			: "SELECT json, peer, unit, message_index, output_index, linked FROM unhandled_private_payments CROSS JOIN units USING(unit)";
		db.query(sql, function(rows){
			if (rows.length === 0)
				return unlock();
			var assocNewUnits = {};
			async.each( // handle different chains in parallel
				rows,
				function(row, cb){
					var arrPrivateElements = JSON.parse(row.json);
					var ws = getPeerWebSocket(row.peer);
					if (ws && ws.readyState !== ws.OPEN)
						ws = null;
					
					var validateAndSave = function(){
						var objHeadPrivateElement = arrPrivateElements[0];
						try {
							var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
						}
						catch (e) {
							console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
							if (ws)
								sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
							deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
						}
						var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
						privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
							ifOk: function(){
								if (ws)
									sendResult(ws, {private_payment_in_unit: row.unit, result: 'accepted'});

									eventBus.emit("new_direct_private_chains", [arrPrivateElements]);

								deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
