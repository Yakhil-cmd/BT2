### Title
Dust collateral leg with an attacker-killable price source makes an account permanently unliquidatable — (`contracts/price-aggregator/src/providers/aquarius.rs`)

### Summary
The Contour bug class is an unauthenticated "shutdown switch": a single unprivileged request disables a safety-critical function for everyone. XOXNO Lending has the same shape. Because `supply` accepts a dust collateral leg without a usable price while every valuation-dependent exit (`liquidate`, `clean_bad_debt`, `force_socialize_bad_debt`, `withdraw`, `repay_debt_with_collateral`) fail-closes on any missing or invalid required price, an attacker can attach a dust leg of an asset whose price they can kill on demand — an Aquarius LP token whose underlying pool the attacker can drain below `min_pool_value_wad`. From that moment the account's debt cannot be liquidated or socialized by anyone, including governance's forced cleanup, while the debt keeps accruing: a permissionless, self-serve liquidation kill-switch that converts a bad position into protocol bad debt.

### Finding Description
`supply` requires only `caller.require_auth()` and does not require the supplied asset's price to be readable (`scripts/permissionless_entrypoints.txt:69`; controller README notes a failed price read reverts state-changing calls, yet supply admission succeeds with a stale feed — `tests/test-harness/tests/controller/audit_supply_stale_shield.rs:26-31`).

Every risk-taking exit path computes `calculate_account_risk_totals` over **all** supply and borrow legs (`contracts/controller/src/positions/liquidation/mod.rs:222-227`), and INV-LIQ-04 confirms both `clean_bad_debt` and owner-only `force_socialize_bad_debt` require "valid required prices" (`docs/reference/invariants.md:463-469`). A single unpriceable collateral leg therefore reverts `liquidate`, `clean_bad_debt`, `force_socialize_bad_debt`, and `withdraw` — proven by the audit tests where a stale WBTC dust leg blocks liquidation, cleanup, and even the borrower's own withdrawal (`tests/test-harness/tests/controller/audit_supply_stale_shield.rs:51-58`, `audit_liquidate_and_clean_stale_leg.rs:36-40`).

For an Aquarius LP collateral asset, `providers::aquarius::read` returns `Err(InsufficientAquariusLiquidity)` whenever `pool_value_wad < lp.min_pool_value_wad`, i.e. `price_wad * total_shares / share_unit < min_pool_value_wad` (`contracts/price-aggregator/src/providers/aquarius.rs:118-122`). `pool_value_wad` scales with live reserves: an attacker who is a liquidity provider in that pool — or who performs large sells ("own trades on Aquarius/Soroswap" are in-scope) — can drive the computed pool value under the floor at will. Unlike a stale Reflector timestamp, which can recover, draining a thin pool below the floor is fully attacker-controlled and can be sustained indefinitely. The attacker holds a large LP position in the pool anyway to supply the dust leg, so this is their own liquidity being withdrawn, not third-party oracle dishonesty.

The threat model names this exact exposure: "an indebted borrower can add a dust leg of any listed collateral and choose which feed outage shields the account. For an Aquarius LP leg, liquidity providers can cause that outage by withdrawing pool value below `min_pool_value_wad`. The same leg blocks bad-debt cleanup and force-socialization" (`docs/explanation/threat-model.md:364`).

### Impact Explanation
Once the leg is planted and the pool is drained:

- `liquidate` reverts for every liquidator → the account is immune while its debt accrues at the borrow index.
- `clean_bad_debt` (permissionless) and `force_socialize_bad_debt` (governance) both revert on the missing price → no path removes the account.
- The attacker keeps full collateral while debt compounds; eventual effective insolvency of the account is borne by suppliers via index write-downs that can never be triggered while the price is dead — permanent freezing of the protocol's loss-realization path and, in aggregate across many such accounts or one large one, protocol insolvency.

This matches the acceptable impacts: theft of user funds (suppliers absorb the unresolvable bad debt), permanent freezing of funds (the account's debt and collateral are locked from all resolution paths), and protocol insolvency.

### Likelihood Explanation
Fully permissionless and attacker-controlled: `supply` needs only the attacker's auth, the dust leg cost is negligible (sub-3-decimal or minimal units), and triggering the outage requires only withdrawing the attacker's own LP liquidity or trading the attacker's own funds in a pool they chose precisely because it is thin relative to `min_pool_value_wad`. The attacker would first build maximum borrowable debt against ordinary collateral, then plant the LP dust leg before going underwater. Timing, magnitude, and duration of the outage are all under the attacker's control, and the outage persists as long as the pool stays below the floor — the attacker can re-deepen and re-drain it at will to dodge transient liquidations. Requirements: a listed Aquarius-LP collateral asset with pool value near `min_pool_value_wad` (a plausible configuration for newly admitted pools). Severity: High.

### Recommendation
Treat per-leg price failures non-fatally on risk exits: skip or price-at-zero an unpriceable *collateral* leg in `calculate_account_risk_totals` rather than reverting (a collateral leg priced at zero only hurts its owner, never the liquidator or suppliers), while keeping fail-closed behavior for *debt* legs. Alternatively/additionally: (a) require a readable price at `supply` admission for collateral-enabled assets; (b) exclude zero-value or unpriceable dust legs from the "required prices" set in `liquidate`/`clean_bad_debt`/`force_socialize_bad_debt`; (c) enforce a minimum USD value on new supply legs so the shield leg costs real money. Raising `min_pool_value_wad` alone does not fix the issue — a larger pool attacker still controls the threshold crossing.

### Proof of Concept
1. Attacker creates account via `supply(caller=attacker, account_id=0, assets=[ordinary collateral])`, then `borrow(...)` up to the limit.
2. Attacker holds LP shares in the thin Aquarius pool `P` whose LP token `LPT` is listed as collateral with `min_pool_value_wad` floor; attacker calls `supply(account_id=acct, assets=[(hub, LPT, dust)])` — succeeds even if `LPT`'s price is already unusable (`audit_supply_stale_shield.rs:26-31` shows a stale-feed leg is admitted).
3. Collateral price drops; account HF < 1.
4. Attacker withdraws their liquidity from `P` (or dumps into it) so `price_wad * total_shares / share_unit < min_pool_value_wad`; `aquarius::read` now returns `InsufficientAquariusLiquidity` (`aquarius.rs:118-122`), making `LPT` permanently unpriceable while the pool stays thin.
5. Any `liquidate(liquidator, acct, ...)`, `clean_bad_debt(caller, acct)`, or governance `force_socialize_bad_debt(acct)` reverts on the missing price — directly demonstrated by the stale-leg variants returning `PRICE_FEED_STALE` for `liquidate`, `clean_bad_debt`, and `withdraw` (`audit_liquidate_and_clean_stale_leg.rs:36-40`).
6. Attacker optionally re-adds liquidity briefly if needed to keep monitoring, then drains again; the account can never be liquidated or socialized, and suppliers eventually eat the compounded bad debt through a supply-index write-down that cannot execute while the price is dead.

Uncertainty note: I verified the fail-closed revert behavior via the audit tests and the Aquarius floor check in source, but did not trace every individual call site inside `risk::calculate_account_risk_totals` to confirm no per-leg price-failure tolerance exists — the tests' `PRICE_FEED_STALE` reverts on liquidation/cleanup establish the behavior empirically for stale feeds, and `InsufficientAquariusLiquidity` propagates through the same `OracleError` path (`aquarius.rs:120-122`, engine resolution), so the conclusion stands.
