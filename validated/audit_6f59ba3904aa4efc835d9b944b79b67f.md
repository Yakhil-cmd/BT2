### Title
Cross-organization webhook forgery via decoupled owner-for-authentication and repository-for-action fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-tenant Shipit deployment (multiple GitHub Apps configured under `secrets.github`, one per organization), the webhook signature verification selects which organization's `webhook_secret` to validate against using one field of the untrusted JSON payload, while the event handlers that actually act on the payload use a *different* field to resolve the target repository/stack. These two fields are never cross-checked, so a party who legitimately controls one onboarded organization's webhook secret can forge webhook deliveries that are "authenticated" as their own organization but act on a completely different organization's repository/stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to verify against using `repository_owner`, which is read straight from the unverified JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github_app_config` looks the org up case-insensitively in `secrets.github` (multi-org config schema): [3](#0-2) 

Once the signature check passes, `Handler#stacks`/`Handler#repository_name` resolve the actual target repository from an entirely different key of the *same* payload — `repository.full_name` — with no comparison back to `repository.owner.login`: [4](#0-3) 

`PushHandler` then uses that repository lookup to enqueue a sync for any matching, non-archived stack with the attacker-supplied `after` SHA: [5](#0-4) 

The binding that should hold is: `organization used to select/verify the signing secret == organization that owns the repository/stack being acted upon`. The controller only ever establishes the left side (`repository_owner` → `webhook_secret`) and the handlers only ever consume the right side (`repository.full_name` → `Stack`), with no equality enforced between them.

### Impact Explanation
On a shared multi-organization Shipit instance, an attacker who administers one onboarded organization (call it Org-B, whose webhook secret they legitimately know because they configured/received it for their own GitHub App) can craft a raw JSON payload where `repository.owner.login = "Org-B"` (to select and pass verification with Org-B's key) but `repository.full_name = "Org-A/target-repo"` (a different tenant's repository). Signing the whole raw body with Org-B's real secret produces a header that `verify_webhook_signature` accepts, yet `PushHandler` (and other handlers relying on `Handler#repository_name`, e.g. `status`, `check_suite`, `pull_request` handlers) act on Org-A's stack. This is a cross-repository/cross-organization write of trust: a webhook "authenticated" for one tenant drives job enqueuing (`GithubSyncJob`) and other event processing for a different tenant's stack — exactly the "organization that authenticated versus the repository that is written" binding called out as in-scope, and lands in the Critical "cross-repository writes" bucket if it reaches state-changing handlers.

### Likelihood Explanation
This requires: (1) the instance running in multi-organization config (`secrets.github` keyed by org), and (2) the attacker controlling a legitimately onboarded organization's own webhook secret — no compromise of Shipit's own secrets or of the target organization is needed. This is a realistic multi-tenant SaaS deployment shape for Shipit; the attack payload is a single crafted HTTP POST to `/webhooks` with a valid `X-Hub-Signature` computed offline.

### Recommendation
After signature verification, cross-check that the organization used to select/verify the webhook secret (`repository_owner`) matches the organization implied by `repository.full_name` (or `organization.login`) before dispatching to handlers, and reject the request (422) on mismatch. Alternatively, resolve the target repository/stack strictly from the same identity that was cryptographically verified rather than from an independent field of the untrusted payload.

### Proof of Concept
1. Instance configured with `secrets.github` containing at least two orgs: `org-a` (target, victim) and `org-b` (attacker-administered), each with distinct `webhook_secret`s, per the multi-org schema in `config/secrets.development.shopify.yml` [6](#0-5) .
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(org-b's webhook_secret, raw_body)>` and sends `POST /webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-b")`, verifies with Org-B's secret — succeeds [1](#0-0) .
5. `PushHandler` resolves `repository_name` as `"org-a/target-repo"` from the same payload and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for Org-A's stack [4](#0-3) [5](#0-4) .

Note: I could not verify within this session whether `Stack#sync_github`'s downstream GitHub API calls (which would use Org-A's own installation token to actually fetch commits) fully neutralize the attacker-supplied `expected_head_sha`, or whether other handlers (status/check_suite/pull_request) produce a more directly writable effect (e.g., commit statuses) once cross-tenant dispatch occurs — this would need further tracing of `Stack#sync_github` and the other handler classes to fully bound severity.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
