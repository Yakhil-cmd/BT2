### Title
AA payment responses are exempt from the input-count cap, so an AA that accumulates many small unspent outputs cannot compose a valid payout - ([File: validation.js], [File: aa_composer.js])

### Summary
`validatePaymentInputsAndOutputs` in `validation.js` explicitly waives the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check for AA-generated payments: [1](#0-0) 
Meanwhile, when an AA composes a response payment, `aa_composer.js`'s `completePaymentPayload`/`iterateUnspentOutputs` loop simply keeps consuming the AA's unspent outputs (ordered by `main_chain_index, unit, output_index`) one at a time, pushing each into `payload.inputs`, until `total_amount` reaches the target amount — with no cap on how many outputs/inputs it accumulates: [2](#0-1) 
This is directly analogous to the reported bug class: an unbounded, ever-growing per-address collection (here, the AA's accumulated unspent outputs from many prior small deposits/triggers) that a later withdrawal/payout action must iterate over in full, with no defensive cap matching real-world usage patterns.

### Finding Description
Any unprivileged party can send many small payments (each above the dust threshold `FULL_TRANSFER_INPUT_SIZE`, currently just tens of bytes) to an AA over time — e.g. by repeatedly triggering it with small deposit calls, or simply sending base/asset outputs to the AA address directly (any AA can receive "silent" outputs, as shown in the `a_bank_without_percent.oscript` deposit pattern). Each such payment creates a new spendable output owned by the AA.

When the AA logic later needs to compose a payment whose target amount can only be met by summing many of these small outputs (e.g., a "send all" response, a large single-user withdrawal, or a refund), `completePaymentPayload`/`iterateUnspentOutputs` in `aa_composer.js` walks the full ordered list of unspent outputs and appends one input per output until the target is reached, without limiting the resulting `payload.inputs.length`: [3](#0-2) 

Because `validatePaymentInputsAndOutputs` deliberately skips the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap when `objValidationState.bAA` is true, this large-input payment is not rejected purely for input count: [1](#0-0) 
However, the resulting unit is still subject to global object-size/oversize-fee limits computed via `objectLength.getTotalPayloadSize` and the oversize fee logic seen throughout `completePaymentPayload` (`net_target_amount`, `getOversizeFee`, etc.): [4](#0-3) 
As the number of required inputs grows (driven purely by how many small outputs an attacker chooses to send the AA), the added per-input size (`FULL_TRANSFER_INPUT_SIZE`) increases `size`/`net_target_amount`/`target_amount`, which can make the payload commission and oversize fee balloon, potentially exceeding the AA's actual balance or unit size limits before the loop can terminate with the target reached. This mirrors the CrabNetting bug: the number of state entries a single user (or attacker) can force into a per-address collection is attacker-controlled and unbounded, and the code that must consume that collection to fulfil a withdrawal has no bound reflecting realistic usage, only reflecting the SQL-limited row set and success/failure of accumulating enough value.

### Impact Explanation
If an attacker (or normal heavy usage) causes an AA address to accumulate a very large number of small unspent outputs, a legitimate future payout that needs to sum many of them (including "send-all" responses, which are common in bank/DAO/AA vault patterns as seen in `a_bank_without_percent.oscript`) may fail to compose as a valid, sufficiently small unit, or may spend an excessive/dust-losing amount on the oversize fee to include enough tiny inputs, effectively freezing part of the AA's funds or making them uneconomical to withdraw. This is an AA fund freezing scenario, which the task explicitly lists as an acceptable high/medium impact category.

### Likelihood Explanation
Triggering many small payments to a public AA address is achievable at low cost by any unprivileged unit poster, since deposits of small amounts are a normal part of many AA designs (as illustrated by the bank/uniswap/fundraising sample AAs). Because the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap is explicitly disabled for AA payments, this class of accumulation is not defended against at validation time, and the composer's greedy consumption of unspent outputs has no independent cap.

### Recommendation
Introduce a bound on the number of inputs an AA-issued payment payload can accumulate in `iterateUnspentOutputs`/`completePaymentPayload` (e.g., cap iteration at a fixed number of outputs per payment message even for AAs, similar to the `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` bound already used in `inputs.js`'s wallet-side coin-selection). If more funds remain, either issue multiple response messages/units across the `max_aa_responses`/secondary-trigger mechanism, or otherwise ensure the AA has a periodic consolidation mechanism (e.g., merging dust outputs) so that a single withdrawal is never forced to enumerate an unbounded number of historical deposits.

### Proof of Concept
1. Deploy (or use) an AA that accepts deposits and supports a withdrawal/send-all response (pattern shown in `test/samples/a_bank_without_percent.oscript`).
2. Repeatedly send many small trigger payments (just above dust size) to the AA address from many different low-cost units, so the AA accumulates hundreds/thousands of tiny unspent outputs.
3. Trigger the AA's withdrawal/refund logic that must gather enough of these outputs to satisfy a target amount (or a send-all response).
4. Observe that `completePaymentPayload`/`iterateUnspentOutputs` in `aa_composer.js` [2](#0-1)  keeps adding inputs without a cap (since `validatePaymentInputsAndOutputs` skips `MAX_INPUTS_PER_PAYMENT_MESSAGE` for AA responses [1](#0-0) ), causing the resulting unit's size/oversize fee to grow with the number of prior small deposits, up to the point where the AA cannot economically or successfully complete the payout, freezing the affected funds.

*Note: I was not able to fully trace the exact numeric thresholds (e.g., the practical object/unit size limit enforced elsewhere in the codebase) that would definitively show the payment fails outright versus merely becoming very expensive; this would require deeper tracing of `objectLength.js` and unit size constants, which is not fully covered in the indexed context available to me.*
