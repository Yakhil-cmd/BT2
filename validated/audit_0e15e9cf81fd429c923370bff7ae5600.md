This looks very promising — the webhook signature verification uses `repository_owner` (from the *unverified* JSON body) to select which GitHub organization's secret verifies the signature, while the actual event processing later uses `repository.full_name` from the same unverified body to determine which repository/stack to act on. Let me examine the handlers and how organizations are configured to confirm the exploitable path.### Title
Webhook signature is verified against an organization derived from unverified payload fields that differ from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a GitHub webhook by reading `repository_owner`, which is computed **from the unverified request body itself**, before any signature has been checked. Downstream event handlers then act on a *different* field of that same unverified body — `repository.full_name` — to decide which `Repository`/`Stack` to mutate. Because these two fields are never required to reference the same organization, an attacker can make the signature check pass using the secret of an organization they control (or one with no `webhook_secret` configured) while the actual write target is any other repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the signing organization straight from the JSON body before trust is established: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects the `GithubApp` config (and thus the `webhook_secret`) for whatever organization name is present in `repository.owner.login` / `organization.login` of the **as-yet unverified** payload. The signature is then checked with that org's secret via `verify_webhook_signature`, which explicitly treats a blank secret as automatically valid: [3](#0-2) 

Once the (org-scoped) signature check passes, the controller dispatches to handlers using the **same raw, attacker-supplied JSON**: [4](#0-3) 

Handlers resolve the target repository from a *different* field of that body — `repository.full_name` — with no re-validation that it belongs to the organization whose secret authenticated the request: [5](#0-4) [6](#0-5) 

For example, `PushHandler` finds all stacks for `repository_name` (from `payload['repository']['full_name']`) and immediately schedules a GitHub sync using the attacker-supplied `after` SHA, entirely independent of `repository_owner`: [7](#0-6) 

This is the exact analog of the reported bug class: the value that is validated (`repository_owner`, gating which secret authenticates the request) is not the value that is subsequently acted upon (`repository.full_name`, which selects the repository/stack that gets written to). A Shipit deployment that configures multiple GitHub organizations (as the shipped example `config/secrets.development.shopify.yml` demonstrates is a supported configuration) is exposed: any organization in that config with a blank `webhook_secret`, or whose secret the attacker knows, can be used to authenticate a forged webhook whose `repository.full_name` names a completely different, unrelated organization's repository/stack tracked by the same instance.

### Impact Explanation
An attacker who can produce a valid signature for *any one* configured organization (including exploiting a blank `webhook_secret` for that org, which is treated as auto-verified) can forge `push`, `status`, `check_suite`, `membership`, or `pull_request` events for **any other repository** tracked by the same Shipit instance, by simply setting `repository.full_name` (used by handlers) to a target unrelated to `repository.owner.login` (used for authentication). For `push`, this triggers `Stack#sync_github` → `GithubSyncJob` with an attacker-chosen `expected_head_sha`, causing the stack to ingest and cache attacker-influenced commit/ref state for a repository outside the authenticating organization — a cross-repository write achieved without possessing the correct organization's actual webhook secret. This matches the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope.

### Likelihood Explanation
This requires: (1) the target Shipit instance to configure more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml`), and (2) at least one of those organizations to have a blank/unset `webhook_secret`, or its secret otherwise known to the attacker. Given multi-org Shipit deployments and the fact that `webhook_secret` is described as optional (`presence` not enforced, `.presence` used defensively), this is a realistic misconfiguration rather than a purely theoretical scenario, and requires no privileged credentials — only the ability to send an unauthenticated HTTP POST to `/webhooks`.

### Recommendation
Verify the webhook signature using the secret bound to the organization that actually owns the repository the handler will act on — i.e., derive `repository_owner` from the same field (`repository.full_name`) used later by `Handler#repository_name`/`Repository.from_github_repo_name`, and re-check that the two never diverge. Alternatively, once a repository/stack is resolved, assert that its persisted `owner` matches the organization whose secret validated the signature before invoking any handler logic. Do not treat a missing `webhook_secret` for one organization as an implicit bypass usable to authenticate events for a differently-owned repository.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `org-a` (no `webhook_secret` set) and `org-b` (has stacks tracked, real secret configured), as in `config/secrets.development.shopify.yml`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` computes `repository_owner = "org-a"`, loads `org-a`'s (blank) `webhook_secret`, and `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77` — no valid signature is required at all.
4. `PushHandler#process` resolves stacks via `payload['repository']['full_name'] == "org-b/target-repo"`, and schedules `GithubSyncJob` for `org-b`'s real stack with the attacker-supplied `after` SHA, even though the request was never authenticated for `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
