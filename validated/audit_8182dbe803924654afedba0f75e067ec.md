### Title
CCMenu API tokens are unscoped to any stack, granting cross-stack `read:stack` access - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` creates the user's `ApiClient` via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without ever setting `stack:`, so `ApiClient#stack_id` is `nil` for this client. Because `Api::BaseController#stacks` treats a `nil` `stack_id` as "unscoped" (`current_api_client.stack_id? ? Stack.where(id: ...) : Stack.all`), the token minted for one stack's CCMenu URL is valid, via `Api::CCMenuController`, for every stack in the Shipit instance the user has ever requested a CCMenu URL for — not just the stack named in that URL.

### Finding Description
Binding claimed vs. actual: the URL generated for stack A embeds a token that should satisfy `token.stack_id == A.id`; instead `client.stack_id == nil`, so `Api::BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`) resolves to `Stack.all`, and `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) uses `Stack.from_param!(params[:stack_id])` directly (not `stacks.from_param!`), meaning the stack lookup for `show` is not filtered by the client's stack at all in this controller regardless.

Path: `CCMenuUrlController#fetch` (`app/controllers/shipit/ccmenu_url_controller.rb:7-18`) calls `client`, which does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — keyed only by `(creator, name)`, never by stack. The resulting `authentication_token` (`app/models/shipit/api_client.rb:34-36`) is a signed client `id`, verifiable by `ApiClient.authenticate` (`app/models/shipit/api_client.rb:24-27`) with no stack constraint baked in beyond the (unset) `stack_id` column. `Api::CCMenuController#authenticate_api_client` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) accepts any valid token and only enforces `require_permission :read, :stack`, which checks the `permissions` array (`read:stack`), not stack identity. Since `stack_id` is nil, no stack binding exists at all — the token is a blanket `read:stack` credential across all stacks for that user's session.

Existing guards checked and found insufficient: `require_permission` only checks the permission string, not stack scoping. The `stacks` scoping helper in `BaseController` would restrict to `current_api_client.stack_id` if it were set, but it is never set here, and `CCMenuController#stack` doesn't even use the `stacks` helper. No model validation ties `ApiClient#stack` to the requested stack at creation time.

Attacker/exploit flow: a legitimate low-privilege user calls `GET /ccmenu/stackA`, receives a token; the same underlying `ApiClient` (memoized by creator+name) is reused for `GET /ccmenu/stackB`, and that identical token, embedded in a CCMenu URL meant only for stack A, also authenticates `GET /api/stacks/stackB/ccmenu.xml` and, in fact, any stack in the instance (since `stack_id` is nil and `Stack.from_param!` is used unscoped in `CCMenuController#stack`) — leaking deploy status of stacks the user was never granted CCMenu URLs for.

### Impact Explanation
The finding matches the "unauthenticated/unauthorized read of stack state" High-severity category: a token minted and scoped in intent to a single stack's build status instead discloses build/deploy status (`deploys_and_rollbacks.last`, running state) for arbitrary stacks in the Shipit instance to whoever holds that one leaked CCMenu URL (e.g., pasted into a CI dashboard, README badge, or a public CCTray monitor). This is a confidentiality leak of stack state across tenants/repositories, not RCE or credential exfiltration, so it does not reach Critical, but it is a genuine authorization-boundary defect exploitable by any authenticated low-privilege user without further secrets.

### Likelihood Explanation
Preconditions are minimal: any logged-in Shipit user with access to at least one stack can trigger `GET /ccmenu/:stack_id` twice for two different stacks and obtain a single shared token good for both (and, further, for stacks they were never shown a URL for, since the token is stack-unbound). No GitHub secrets, webhook secrets, or admin roles are required — only a normal browser session. This is trivially repeatable and requires no special configuration.

### Recommendation
Scope the `ApiClient` per stack: change `find_or_create_by!` to include `stack: stack` (and adjust uniqueness so name+creator+stack identifies the CCMenu client), set `permissions: %w[read:stack]` with `stack_id` populated, and make `Api::CCMenuController#stack` use the `stacks` helper (scoped by `current_api_client.stack_id`) instead of unscoped `Stack.from_param!`, so a token minted for stack A can never resolve stack B.

### Proof of Concept
```ruby
# test/controllers/ccmenu_controller_test.rb (extended)
test ":fetch reuses one unscoped token across different stacks" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a second stack fixture the user can access

  get :fetch, params: { stack_id: stack_a.to_param }
  token_a = JSON.parse(response.body)['ccmenu_url']

  assert_no_difference 'ApiClient.count' do
    get :fetch, params: { stack_id: stack_b.to_param }
  end
  token_b = JSON.parse(response.body)['ccmenu_url']

  assert_equal URI(token_a).query, URI(token_b).query # same token param

  client = ApiClient.last
  assert_nil client.stack_id # token is not bound to any single stack

  # Confirm the token authorizes an unrelated third stack via the API controller
  stack_c = shipit_stacks(:some_other_stack)
  token = Rack::Utils.parse_nested_query(URI(token_a).query)['token']
  get :show, params: { stack_id: stack_c.to_param, token: token } # Api::CCMenuController
  assert_response :ok
end
```
This demonstrates `ApiClient.count` does not increase on the second call for a different stack, the same token is embedded in both URLs, and that token authenticates against a third, unrelated stack.
