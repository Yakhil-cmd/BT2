### Title
Unscoped `Commit.where(sha:)` in `StatusHandler` lets a webhook from any onboarded repository write forged CI status into another repository's commit/stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits purely by `sha`, with no scoping to the repository that emitted the webhook. If two commits in different stacks (e.g., a review stack of repo A and a review stack of repo B) share the same `sha` — achievable when both PRs cherry-pick/import an identical upstream commit — a genuine, correctly-signed `status` webhook from repo A will also create a `Status` row on repo B's commit, polluting a stack the attacker never controls.

### Finding Description
The binding the question implies should hold is: `Status written to commit C` `⇒` `commit C.stack ∈ {stacks belonging to the repository named in the payload's repository.full_name}`. Tracing the code shows this binding does not hold.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does: [1](#0-0) 
which iterates over `Commit.where(sha: params.sha)` — an unscoped, engine-wide query — and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository owns that commit's stack. The `params.repository` field required by the schema (`requires :sha`, `:state`, etc.) is never consulted to constrain the query, unlike the `pull_request` handlers which explicitly build a `repository.review_stacks` scope before resolving a `ReviewStack` via `ReviewStackAdapter#stack` (`scope.find_by(environment:)` in `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:15-17`). No such repo-scoping exists for statuses.

`Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) unconditionally calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) creates the `Status` row keyed to that commit's own `stack_id` — i.e., whichever stack happens to own the colliding-sha commit, not the stack tied to the webhook's originating repository.

Preconditions for exploitation: the attacker must control (own/administer) a repository that is legitimately onboarded to the target Shipit instance (so a real, correctly-signed GitHub `status` webhook can be delivered — no signature forgery required, since `GithubHook#verify_signature`/`GitHubApp#verify_webhook_signature` validate authenticity, not repository authorization for the target sha). The attacker engineers a commit whose sha matches a commit already present in a victim review stack (e.g., both PRs cherry-pick the exact same upstream commit, yielding identical author/committer/tree/parent/timestamps and thus identical sha), then triggers (or has GitHub trigger) a `status` event for that sha from their own repository.

Existing guards do not catch this: `verify_signature`/`verify_webhook_signature` only prove the payload came from GitHub for *some* configured organization/app — they say nothing about which repository's data may be written. `drop_unhandled_event` and the `ExplicitParameters` schema validate shape, not repository ownership of the target commit. There is no repository-scoping check anywhere in `StatusHandler`.

I could not fully verify whether `Commit#schedule_continuous_delivery` (referenced from `Status#schedule_continuous_delivery` at `app/models/shipit/status.rb:42-44`) gates on `stack.continuous_deployment?` the same way `Deploy#schedule_continuous_delivery` does (`app/models/shipit/deploy.rb:327-331`, which checks `return unless stack.continuous_deployment?`); I was unable to retrieve its full body before running out of tool calls. Based on the analogous `Deploy` implementation and the fact that `continuous_deployment` is a persisted `Stack` attribute only ever set via `stack_attributes` at creation (`continuous_deployment: false`, `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:87-93`) or explicit settings updates, there is no code path by which receiving a `Status` flips `continuous_deployment` from `false` to `true`. So the specific "re-enabling continuous deployment" framing in the question is not substantiated — that flag is not toggled by this path.

What *is* substantiated is cross-tenant state pollution: the forged `Status` is persisted against the victim's commit/stack, `after_create :enable_ci_on_stack` runs `commit.stack.enable_ci!` on the victim's stack (`app/models/shipit/status.rb:18,38-40`), and `Commit#create_status_from_github!`/`#add_status` can enqueue `ProcessMergeRequestsJob` for the victim's stack on a `pending`/`success` transition (demonstrated in `test/models/commits_test.rb:763-777`), and updates the commit/stack dashboard state visible to the victim.

### Impact Explanation
An attacker who legitimately controls one Shipit-onboarded repository can write a `Status` record (state/description/context/target_url of their choosing) onto a commit belonging to a completely different repository/stack, provided a sha collision exists. This can flip the victim commit's CI state, enable CI on the victim stack, and enqueue `ProcessMergeRequestsJob` against the victim's stack, polluting review-stack dashboards and merge-queue processing with attacker-controlled data. This matches the listed Critical category "a payload for one repository mutating another's stack, commit, task or team." It does not, however, demonstrate flipping `continuous_deployment` itself or causing an unauthorized deploy — that specific escalation path is not shown to exist.

### Likelihood Explanation
Requires: (1) attacker's own repository already onboarded/webhook-connected to the target Shipit instance (a normal, low-privilege precondition per the rules), and (2) an actual sha collision — i.e., a genuinely identical git commit (same tree, parents, author/committer identity and timestamps, and message) landing in both the attacker's and victim's history, which requires either coincidence (near-impossible) or a shared upstream commit both parties cherry-pick/merge verbatim (feasible in monorepo/fork ecosystems, but not attacker-arbitrary — the attacker cannot forge an arbitrary sha into the victim's repo). This constrains real-world exploitability to specific multi-repo workflows sharing upstream history, not a fully generic "attacker picks any target."

### Recommendation
Scope `StatusHandler#process` to commits belonging to the repository named in the webhook payload, mirroring the pull-request handlers: resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and restrict the `Commit` lookup to `repository.stacks.commits.where(sha: params.sha)` (or equivalent join) instead of the engine-wide `Commit.where(sha:)`.

### Proof of Concept
minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or via `WebhooksControllerTest`):
1. Create two stacks/repos, `repo_a` and `repo_b`, each with a `Commit` sharing the identical `sha` (`same_sha = "deadbeef..."`).
2. Assert precondition: `Commit.where(sha: same_sha).pluck(:stack_id)` includes both `stack_a.id` and `stack_b.id`.
3. POST a `status` webhook (`X-Github-Event: status`) whose `repository.full_name` is `repo_a`'s full name and `sha: same_sha`, `state: "success"`.
4. Assert `commit_b.statuses.reload.count` increased by 1 and the created `Status.stack_id == stack_b.id`, even though the payload only named `repo_a` — proving `Status written to commit_b ⇒ commit_b.stack belongs to repo_a` is false.
5. Optionally assert `stack_b.reload.ignore_ci` unaffected/`enable_ci!` invoked, and `ProcessMergeRequestsJob` enqueued with `stack_b` if the transition qualifies.
