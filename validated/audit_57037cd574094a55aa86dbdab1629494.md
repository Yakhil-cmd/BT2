### Title
Cross-organization webhook confusion lets an org-B admin trigger sync/deploy actions and forge CI status for org-A repositories tracked by Shipit - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against using one field of the JSON payload (`repository.owner.login`, falling back to `organization.login`), while every event handler downstream (`PushHandler`, `StatusHandler`, the `PullRequest::*Handler`s) resolves the *target* repository/stack using an entirely different field, `repository.full_name`, via `Shipit::Repository.from_github_repo_name` [1](#0-0) . Nothing in the request pipeline checks that the owner encoded in `full_name` matches the organization whose secret validated the signature. In Shipit's documented multi-organization mode, each tracked GitHub organization has its own independent `webhook_secret` looked up via `Shipit.github(organization:)` [2](#0-1) , so knowing one organization's secret is not supposed to authorize action on another organization's repositories.

### Finding Description
`verify_signature` picks the app/secret purely off `repository_owner`: [3](#0-2) 

That is a single JSON field extracted from the attacker-controlled raw body before the HMAC has been checked against anything else; the signature only proves the *entire byte string* was signed with the secret belonging to whichever organization `repository_owner` names — it does not prove that `repository.full_name` (used later) is consistent with that owner.

Every consumer of the payload trusts `repository.full_name` independently to resolve the actual target:
- `Handler#repository_name` / `#stacks`: [1](#0-0) 
- `PushHandler#process`, which syncs and can trigger `stack.sync_github`: [4](#0-3) 
- `StatusHandler#process`, which writes a CI status for any commit matching `sha` regardless of repo/org: [5](#0-4) 
- The pull-request handlers, which look up the repo via `params.repository.full_name` for archiving/unarchiving/provisioning review stacks, e.g. `ClosedHandler#repository`: [6](#0-5) 

`Shipit::Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)` with no relation to the verified organization at all: [7](#0-6) 

**Equality that should hold but doesn't**: `organization_that_authenticated(repository_owner used for HMAC lookup) == owner(repository.full_name used by handlers)`. Because the controller never enforces this equality, an attacker who can compute a valid signature for *organization A's* `webhook_secret` (e.g. because Shipit is configured in multi-org mode and org A's own operator legitimately knows/controls that secret) can send a self-crafted (not necessarily GitHub-originated) POST to `/webhooks` where `repository.owner.login` = `"org-a"` but `repository.full_name` = `"org-b/victim-repo"`. `verify_signature` authenticates against org A's app and passes; the handler then acts on org B's stack.

### Impact Explanation
This crosses exactly the trust boundary the ruleset calls out — "an organization that authenticated versus the repository that is written" — and manifests as unauthorized cross-organization state changes without ever needing org B's secret:
- `push` events can force `GithubSyncJob`/`stack.sync_github` on an arbitrary org's stack, which is used elsewhere in the deploy pipeline as the trigger for pulling new commits and can feed into continuous-deployment flows.
- `status` events let the attacker forge a commit status (`state`, `context`, `description`) for any commit whose SHA happens to be tracked in Shipit's `Commit` table for another org's stack, via `commit.create_status_from_github!`. Since Shipit uses commit statuses to gate CI-based deployability, this is a path to marking a victim commit as passing/deployable — i.e., contributing to an unauthorized deploy.
- `pull_request` events can archive/unarchive/provision review stacks belonging to a different tracked organization.

This satisfies the Critical/High bar of "cross-repository writes" / contribution to "an unauthorized deploy," matching the M-6 report's pattern of a signed/authorized scope (organization secret) being used to act outside that scope (a different repository's data), analogous to the locker owner manipulating a pool it doesn't own to bypass a control tied to a different, unverified quantity.

### Likelihood Explanation
Requires that the attacker legitimately possesses (or can derive) the `webhook_secret` for *some* organization configured in Shipit's multi-org GitHub config — this is realistic in any Shipit deployment where multiple GitHub organizations each manage/rotate their own webhook secret (a documented supported configuration, `github_app_config`), rather than requiring compromise of the victim organization's secret. No `ApiClient` token, session, or GitHub App private key of the victim org is needed, only knowledge of one's own org's webhook secret plus the ability to send an arbitrary HTTP POST — well within "unprivileged attacker with respect to the victim organization."

### Recommendation
In `WebhooksController#verify_signature`, after resolving `repository_owner` and validating the signature, also assert that the owner segment of `repository.full_name` (and of `organization.login`, if present) matches `repository_owner` before dispatching to any handler; reject the payload (422) on mismatch. Alternatively, have handlers derive the organization strictly from the same field used for signature verification and refuse to resolve stacks/repos whose owner differs from it.

### Proof of Concept
1. Configure Shipit in multi-org mode with organizations `org-a` and `org-b`, each with its own `webhook_secret` (`secrets.github[:org_a][:webhook_secret]`, `secrets.github[:org_b][:webhook_secret]`).
2. As an operator/holder of `org-a`'s webhook secret (no access to `org-b`'s secret or GitHub credentials), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC_SHA1(org_a_webhook_secret, raw_body)` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully against the attacker's own secret [8](#0-7) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/victim-repo")` and invokes `stack.sync_github` on org B's stack, entirely unrelated to the authenticated org [4](#0-3) , [7](#0-6) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
