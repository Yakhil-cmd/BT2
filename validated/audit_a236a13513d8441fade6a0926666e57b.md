### Title
`calculate_fee` can silently produce a zero remote fee for a validated `PricingParameters`, and callers use it unchecked - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
The TOKE-16 report describes a caller (`updateDebtReporting`) that receives a safety flag (`pricesWereSafe`) from a lower-level function but never validates it before using the (potentially unsafe) computed value downstream. Searching polkadot-sdk--013 for an analogous pattern — a computed economic value that can be degenerate/unsafe despite passing an input-level validation, and that is consumed by a caller without a follow-up safety check — surfaces `snowbridge_core::PricingParameters::validate()` and `Pallet::<T>::calculate_fee` in the Snowbridge outbound queue.

### Finding Description
`PricingParameters::validate()` checks that each individual input field (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) is non-zero: [1](#0-0) 

This `validate()` is enforced only at the point governance sets pricing parameters via `set_pricing_parameters`, as shown by the test asserting `InvalidPricingParameters` for each zero field: [2](#0-1) 

However, the *derived* fee actually used to price a message, `Pallet::<T>::calculate_fee`, performs its own arithmetic (multiply by gas, add reward, multiply by `multiplier`, divide by `exchange_rate`, then integer-truncate/convert decimals) that can round the remote fee down to zero even though every individual `PricingParameters` field passed `validate()` and is non-zero: [3](#0-2) 

This exact scenario is demonstrated by an existing unit test, whose own comment states the result is "invalid" and "should be avoided", i.e., the code and its authors recognize a "safe/unsafe" boundary similar to the `pricesWereSafe` flag in the report, but no code path actually rejects the unsafe value: [4](#0-3) 

The caller that actually uses this fee to price and enqueue a real user message, `SendMessage::validate` in `send_message_impl.rs`, takes whatever `calculate_fee` returns and forwards it as the `Fee` to be charged, with **no check that `fee.remote` (or the overall fee) is non-zero / "safe"**: [5](#0-4) 

This mirrors the TOKE-16 root cause precisely: a lower-level computation exposes (via test/comment, not via a returned boolean) that its result can be "unsafe" (degenerate/zero), and the calling code path that consumes that result for real, user-triggered dispatch (any XCM `Transact`/token transfer routed to Ethereum through this outbound queue) does not validate it before using it to determine the actual fee charged.

### Impact Explanation
If `fee.remote` degenerates to zero for a real message (e.g., due to a governance-set combination of `exchange_rate`, `fee_per_gas`, `multiplier`, and `rewards.remote` that is individually valid but produces underflow/truncation in the fixed-point math), a message can be queued and eventually delivered to Ethereum while the relayer's reimbursement/reward accounting on the remote side is undercharged or zero, breaking the fee-settlement invariant documented in the pallet's own module doc (`RemoteFee(Message) = MaxGasRequired(Message) * Params.MaxFeePerGas + Params.Reward`). This is an accounting/economic-safety violation analogous to using an unsafe/degenerate price in vault debt accounting — value is computed and then used without validating that it is within a "safe" (non-degenerate) range.

### Likelihood Explanation
Likelihood depends entirely on governance choosing a combination of `exchange_rate`/`fee_per_gas`/`multiplier`/`rewards.remote` values that individually pass `validate()`'s non-zero checks yet produce a truncated-to-zero `fee.remote` for the specific `gas_used_at_most` of a given `Command`. This requires a privileged parameter-setting action (governance/root sets `PricingParameters`) rather than a purely permissionless attacker-controlled input — the "attacker" here would need pricing parameters to already be in a degenerate regime, which is a configuration/governance risk, not a directly attacker-triggerable exploit from an unprivileged signed extrinsic alone.

### Recommendation
In `Pallet::<T>::calculate_fee` (or in the `SendMessage::validate` caller in `send_message_impl.rs`), explicitly assert/ensure that the computed `Fee.remote` (and `Fee.local`) is non-zero before returning it for use in message enqueueing, mirroring the caller-side validation recommended for `pricesWereSafe` in the original report. Alternatively, extend `PricingParameters::validate()` (or add a dedicated post-computation check) so that degenerate derived-fee outcomes are rejected rather than silently accepted.

### Proof of Concept
No new PoC was executed. The unsafe/degenerate-output scenario is already reproduced by the existing repository test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, which sets `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local: 1, remote: 1}`, `multiplier = 1/1` — all individually non-zero and therefore `PricingParameters::validate()`-passing — and asserts `fee.remote == 0`: [4](#0-3) 
This test's own comment ("the remote fee calculated here is invalid which should be avoided") confirms the code path produces an unsafe/degenerate value that downstream callers (`send_message_impl.rs::validate`) accept without any additional safety check, satisfying the structural analog to TOKE-16's ignored `pricesWereSafe` flag. I was unable to fully trace, within the available tool budget, whether any higher-level XCM router/exporter (e.g., in `bridges/snowbridge/primitives/router`) adds an additional non-zero/safety check on top of this `Fee` before final dispatch to Ethereum; this remains unverified and should be checked in a full session before treating this as a conclusively unguarded path.

		}

			return Err(InvalidPricingParameters);
		}

	}

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
