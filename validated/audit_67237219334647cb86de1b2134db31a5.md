### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler acts on the repository derived from the independent `repository.full_name` field, allowing cross-organization webhook forgery in multi-tenant GitHub App configurations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same unvalidated `params` hash to handlers. Every handler resolves the repository/stack to act on via `Shipit::Webhooks::Handlers::Handler#repository_name`, which reads a *different* JSON field: `payload.dig('repository', 'full_name')`. Nothing ties `repository.owner.login` (used to pick the trust boundary/secret) to `repository.full_name` (used to pick the target of the write). This is analogous to the Sherlock M-18 pattern: a value used to satisfy a check (Chainlink feed keyed on `TOKEN/USD`) doesn't cover the actual value acted upon (the real token pair queried) — here, the field used to authenticate the sender's organization doesn't cover the actual field used to select the repository being mutated. ### Finding Description
Shipit supports a multi-tenant GitHub App configuration where `Shipit.github(organization:)` looks up a distinct `GitHubApp` (with its own `webhook_secret`) per organization key in `secrets.github`, keyed by whatever string is passed as `organization`. [5](#0-4) 

`WebhooksController#verify_signature` uses the `repository_owner` helper to select which per-organization secret to verify the `X-Hub-Signature` against:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

The HMAC check itself is a standard `secure_compare` against `OpenSSL::HMAC.hexdigest`, so it is cryptographically sound *for the organization it is checked against*: [7](#0-6) 

The problem is that `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON fields in the same raw POST body used to compute the HMAC. The signature only proves the payload bytes were signed with the secret belonging to whatever organization `repository.owner.login` names — it says nothing about consistency between that field and `repository.full_name`, which every handler actually uses to resolve the target `Repository`/`Stack`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

The same divergent field is used identically in `PushHandler#process` (drives `stack.sync_github`), `StatusHandler#process` (creates a commit status from arbitrary `sha`/`state`), the `pull_request/*` handlers (drive review-stack provisioning via `params.repository.full_name`), etc.: [8](#0-7) [9](#0-8) [10](#0-9) 

**Equality that should hold, but doesn't:**
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository the handler mutates (repository.full_name)`

Before the attack: for legitimate GitHub-originated webhooks, GitHub itself guarantees `repository.owner.login` and the owner segment of `repository.full_name` refer to the same repository, so the equality holds implicitly. After the attack: an attacker who is onboarded to the same Shipit instance as one tenant organization (and thus knows or controls that organization's `webhook_secret`) can send a POST to `/github/webhooks` with `repository.owner.login = "attacker-org"` (to select their own valid secret) but `repository.full_name = "victim-org/victim-repo"` (to select the actual target). `verify_signature` passes because the HMAC matches attacker-org's secret over the full raw body (which the attacker controls and can freely craft), and then `Repository.from_github_repo_name("victim-org/victim-repo")` resolves the real, unrelated stack.

### Impact Explanation
This breaks the binding between "the organization whose credential authorized this request" and "the repository/stack that is written," which the report's rules explicitly list as a target class of trust-boundary break for this engine. Concretely, an attacker who controls (or is onboarded with) one tenant organization on a shared multi-tenant Shipit install can forge events attributed to any other tenant's repository:
- Forge `push` events to trigger `Stack#sync_github`/continuous delivery evaluation for a victim stack.
- Forge `status` events to inject arbitrary CI status (`state`, `context`, `target_url`) for arbitrary commit SHAs on a victim repository, potentially satisfying `ci.require` gates that continuous delivery relies on to auto-deploy.
- Forge `pull_request` events (opened/labeled/reopened) to provision/archive/unarchive review stacks belonging to a victim repository.

Because commit-status forgery can feed into automatic (continuous) deploy triggers, this can escalate to an unauthorized deploy on a stack the attacker does not own — matching the report's "Critical: unauthorized deploy" bucket, contingent on the target using continuous delivery gated on `ci.require` statuses. At minimum it is a cross-repository/cross-organization write of state (statuses, review-stack lifecycle), matching the "High: cross-repository writes" bucket.

### Likelihood Explanation
Exploitability depends entirely on the deployment being configured for **multi-tenant GitHub Apps** (i.e., `secrets.github` keyed by multiple organizations rather than the single top-level GitHub App schema), and on the attacker having legitimate standing (or knowledge of the webhook secret) for at least one of the onboarded organizations — this is a lower bar than compromising the victim organization directly, since webhook secrets are typically shared with/settable by each onboarded org's own GitHub App admins, not restricted to Shipit's core operators. In the common single-tenant deployment (`github_default_organization.nil?`), `Shipit.github(organization: repository_owner)` collapses to the single configured app regardless of `repository_owner`, so the specific cross-tenant angle does not apply there — but the underlying design flaw (verifying against one field while acting on another) still exists structurally.

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`) is consistent with the owner segment of `repository.full_name` before dispatching to handlers, and/or verify the signature using the same repository-derived key that handlers use to resolve write targets. Reject webhooks where these fields disagree.

### Proof of Concept
1. Deploy Shipit with a multi-tenant `secrets.github` config containing at least `attacker-org` (attacker-known `webhook_secret`) and `victim-org` (hosting stack `victim-org/victim-repo`).
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check succeeds (attacker signed with the correct secret for that org).
5. `Shipit::Webhooks::Handlers::StatusHandler#process` runs using `params.sha`/`params.state`/`params.context`, writing a forged commit status onto the victim's commit (`Commit.where(sha: params.sha)` is not scoped to `attacker-org`), independent of the `repository.owner.login` used above.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
