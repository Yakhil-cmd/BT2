### Title
Webhook organization used for signature verification is decoupled from the repository the handler actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  Once the signature is accepted, every event `Handler` resolves the target `Repository`/`Stack` from a *different* JSON field in the same body, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3)  Nothing checks that the owner encoded in `full_name` matches `repository_owner` used to select the trusted secret.

### Finding Description
Shipit supports multiple GitHub organizations behind one instance, each with its own webhook secret, selected via `Shipit.github(organization:)` → `github_app_config(organization)`. [5](#0-4)  `verify_signature` looks up the app/secret for the org named in `repository.owner.login` (or `organization.login`) and only checks that the raw POST body is HMAC-signed by *that org's* secret:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

This proves only "some configured org's secret signed this exact byte string" — it says nothing about which repository the payload's other fields describe. Every handler (`PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::ReopenedHandler`, etc.) instead trusts `payload.dig('repository', 'full_name')` to decide which `Repository`/`Stack` to act on:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 
```
def repository
  Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new
end
``` [7](#0-6) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the acted-upon repository) are independent, attacker-controlled strings inside the same JSON body, an attacker who legitimately controls the webhook secret for **one** organization onboarded to the Shipit instance (e.g. their own tenant org in a multi-org deployment) can craft a payload where:
- `repository.owner.login` = their own org (so `verify_signature` selects their own known secret and the HMAC check passes), and
- `repository.full_name` = `"victim-org/victim-repo"` (an entirely different, unrelated tenant's repository already registered in Shipit).

The signature check succeeds because it is checking the correct secret for the *claimed* owner field, while the handlers dispatch on the *unrelated* `full_name` field. This breaks the equality that should hold: `organization authenticated by verify_signature == repository written to by the handler`.

### Impact Explanation
For `pull_request` "opened"/"reopened" events, `ReviewStackAdapter` provisions/unarchives a `ReviewStack` for the resolved `repository`, using attacker-controlled `pull_request.head.ref` as the stack's `branch`. [8](#0-7) [9](#0-8)  That review stack is then deployed by Shipit's normal task pipeline, which checks out the given branch/ref of the *victim* repository and executes its `shipit.yml` on the deploy host using the instance's real GitHub credentials. For `push` events, `PushHandler` similarly triggers `stack.sync_github(expected_head_sha:)` against whatever `Stack`s belong to the spoofed `full_name`, forcing an out-of-band sync of a repository the attacker's org has no relationship to. [10](#0-9) 

In a multi-tenant Shipit deployment this is a cross-repository-write / unauthorized-deploy primitive: a low-privilege tenant with only their own org's webhook secret can force actions (stack provisioning, deploy triggers, sync) against a different tenant's repository, without ever possessing that tenant's webhook secret, `github_access_token`, or a Shipit session.

### Likelihood Explanation
Exploitability requires only knowledge of the webhook secret for **any one** organization configured on the shared Shipit instance — this is exactly the credential every legitimate multi-tenant onboarding grants, not a privileged Shipit account, API token, or GitHub App private key. No repository write access to the victim's repository is needed; only the raw HTTP webhook endpoint (`/github/webhooks`, unauthenticated by design) and a correctly-signed body using the attacker's own secret. Given Shipit's explicit multi-org secret architecture (`github_app_config`), this is a realistic configuration, not a hypothetical one.

### Recommendation
Bind the signature-verification identity to the repository actually acted upon: after resolving `repository_owner` for secret selection, also require that `payload.dig('repository','full_name')&.split('/')&.first` (case-insensitively) equals `repository_owner` before dispatching to handlers, rejecting the request (422) on mismatch. Alternatively, resolve the target `Repository` first (via `full_name`), look up its owning organization/app config independent of the `owner.login` claim, and use that association (not attacker-suppliable payload fields) to select the verification secret.

### Proof of Concept
1. Configure/observe that the Shipit instance hosts two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret` values under `secrets.github` (per `github_app_config`). [11](#0-10) 
2. As the owner of `attacker-org` (who legitimately knows `attacker-org`'s webhook secret), craft a `pull_request` "opened" webhook payload:
   ```json
   {
     "action": "opened",
     "number": 999,
     "pull_request": { ... "head": { "ref": "malicious-branch", "sha": "..." } ... },
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
     "sender": { "login": "attacker" }
   }
   ```
3. Compute `X-Hub-Signature` using `attacker-org`'s own webhook secret over the raw JSON body.
4. POST to `/webhooks/github` with `X-Github-Event: pull_request`. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, and successfully verifies the signature. [1](#0-0) 
5. `OpenedHandler#repository` resolves `victim-org/victim-repo` from `params.repository.full_name` and provisions/unarchives a review stack on `malicious-branch` for the victim repository, all without ever presenting `victim-org`'s webhook secret. [12](#0-11)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
