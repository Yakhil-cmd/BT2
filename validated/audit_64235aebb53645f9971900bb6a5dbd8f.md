### Title
Cross-organization webhook signature bypass leads to global forged commit statuses that trigger unauthorized auto-deploys/merges - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to verify a GitHub webhook against based on `repository_owner`, a field read directly from the unverified JSON body [1](#0-0) . That org-selection field is never itself covered by any signature check, and it is never cross-checked against the field that downstream handlers actually act on. `Shipit::Webhooks::Handlers::StatusHandler` looks up commits purely by `sha`, with **no repository scoping at all** [2](#0-1) . Combined, these two facts break the binding "organization that authenticated == repository that is written": an attacker can pick, as `repository.owner.login`, any org configured in `Shipit.secrets.github` whose `webhook_secret` is blank (an explicitly documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and the shipped example `config/secrets.development.shopify.yml` where `webhook_secret: # nil`), which makes `verify_webhook_signature` return `true` unconditionally [3](#0-2) . The attacker can then send a forged `status` event whose `sha` belongs to a commit in a *completely different, properly-secured* repository/org, and Shipit will accept it as authentic because the org used for cryptographic verification is never the org whose commit is mutated.

### Finding Description
1. `verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login')` (or `organization.login`) of the raw, still-unverified payload, and uses it to fetch the corresponding `GitHubApp` via `Shipit.github(organization: repository_owner)` [1](#0-0) [4](#0-3) .
2. `GitHubApp#verify_webhook_signature` explicitly trusts any signature (even a missing/garbage one) when that particular org's `webhook_secret` is not configured: `return true unless webhook_secret` [3](#0-2) . This is a first-class, documented configuration path for multi-org Shipit installs [5](#0-4) .
3. Once the request body passes this owner-scoped check, `WebhooksController#create` dispatches the **entire raw payload** to all registered handlers for the event, with no re-validation tying the payload to the org that was used for verification [6](#0-5) .
4. `StatusHandler#process` resolves target commits by `Commit.where(sha: params.sha)` — a global, instance-wide lookup with zero relationship to `repository.owner.login` (the field that was actually verified) or even `repository.full_name` [2](#0-1) . `Commit#create_status_from_github!` then persists the forged status into that commit's real stack [7](#0-6) .
5. `Commit#add_status` reacts to the new status: if it flips the commit's simple state to success it calls `stack.schedule_merges` and (via `deployable?`/`schedule_continuous_delivery`) can trigger `ContinuousDeliveryJob` for stacks with continuous deployment enabled [8](#0-7) [9](#0-8) [10](#0-9) .

Equality broken: `organization used to select/verify the webhook signature (repository.owner.login)` ≠ `repository/commit whose state is actually mutated (identified only by sha, with no owner check)`.

Before the attacker's request: only genuine, signed GitHub events from the correct org's GitHub App can create/update a `Status` for a given commit. After: an unauthenticated attacker, knowing only that *some* org in the Shipit instance's multi-org config has no `webhook_secret` set (visible from public repo settings pages, or simply the documented default of leaving it blank), can forge a `success` status for any commit belonging to any repository/stack in the whole Shipit installation, including ones owned by a different, fully-secured GitHub organization.

### Impact Explanation
This crosses the "unauthenticated write into a repository/stack the attacker was never authorized for" boundary. A forged `success`/passing status on a commit can satisfy `stack.required_statuses`/`Commit#deployable?`, causing `Commit#schedule_continuous_delivery` to enqueue `ContinuousDeliveryJob` and `stack.schedule_merges` to proceed with merge-queue processing for a stack the attacker does not control and never authenticated against — an unauthorized deploy/merge trigger, which matches the Critical bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured with more than one GitHub org (a documented, supported setup), (b) at least one of those orgs to have no `webhook_secret` configured (also a documented, explicitly optional setting — shown blank in the shipped example config), and (c) a target stack with continuous deployment/merge queue enabled and a fetched commit sha (which is largely public information for public repos, or leaked via other endpoints). All are realistic, admin-supported configurations rather than exotic edge cases, and no credentials, session, or GitHub App keys are needed by the attacker.

### Recommendation
- Never use unverified payload fields to select the verification key; instead, iterate/attempt verification across all configured orgs' secrets (or bind webhook delivery URLs per-org) rather than trusting `repository.owner.login` from the request body.
- Do not allow "no secret configured" to universally bypass signature verification when other orgs in the same instance do have secrets configured; at minimum, warn/reject when a wildcard-trust org coexists with a repository-scoped lookup.
- Scope `StatusHandler` (and any other sha-only lookups) to the verified organization/repository rather than a global `Commit.where(sha: ...)` search — enforce that the org verified in `verify_signature` matches the repository referenced by the payload before any handler processes it.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `SecureOrg` (has `webhook_secret` set) owning stack `SecureOrg/victim-repo`, and `OpenOrg` (no `webhook_secret`, per the documented optional setting).
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything
{
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "OpenOrg/whatever" },
  "sha": "<sha of a real commit in SecureOrg/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OpenOrg")`; `verify_webhook_signature` returns `true` unconditionally because `OpenOrg`'s `webhook_secret` is blank [3](#0-2) .
4. `StatusHandler#process` finds the commit by `sha` alone (matches the `SecureOrg/victim-repo` commit) and calls `create_status_from_github!`, writing a forged `success` status into `SecureOrg`'s stack [2](#0-1) .
5. If that status satisfies the stack's required checks, `Commit#add_status` triggers `stack.schedule_merges` / continuous delivery for `SecureOrg/victim-repo`, an unauthorized action on a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
