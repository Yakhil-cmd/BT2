### Title
`pull_request` webhook `repository.owner.login` vs `repository.full_name` split lets one org's signature authorize mutation of another org's stack - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the signing secret using `params.dig('repository','owner','login')`, but `LabeledHandler` (and every other `pull_request` handler) resolves the mutated `Shipit::Repository`/stack using the independent, attacker-controlled field `params.repository.full_name`. Since these two JSON fields are never cross-checked, an attacker who forges a raw `POST /webhooks` body can pick an org for `repository.owner.login` whose webhook secret is unset or known to them, while pointing `repository.full_name` at a victim's repository, causing `LabeledHandler` to archive/unarchive that victim's review stack.

### Finding Description
The broken binding: the invariant should be `verified_org(repository_owner) == owner_segment(repository.full_name)`, i.e. the org whose secret authenticated the webhook must be the same org that owns the repository the handler mutates. In the code these are two independently-read, attacker-controlled JSON fields with no equality check between them:

- Signature/org selection: [1](#0-0)  uses [2](#0-1)  (`params.dig('repository','owner','login')`) to pick the `GitHubApp` config via `Shipit.github(organization: repository_owner)`, and `verify_webhook_signature` trivially returns `true` when that org's `webhook_secret` is blank [3](#0-2) .
- Repository resolution used to mutate state: `LabeledHandler#repository` resolves the actual `Shipit::Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, a completely separate JSON field [4](#0-3) , and then archives/unarchives the matching `ReviewStack` via `ReviewStackAdapter` scoped to `repository.review_stacks` [5](#0-4) . `ReviewStackAdapter#unarchive!`/`archive!` directly call `stack.unarchive!`/`stack.archive!` on the resolved review stack, enqueuing a `GithubSyncJob` and re-adding it to the provisioning queue [6](#0-5) .

Exploit flow: the attacker (any internet user, no Shipit credentials) sends a raw JSON `POST /webhooks` with header `X-Github-Event: pull_request`, body `action: "labeled"`, `repository.owner.login` = an org configured in Shipit with no `webhook_secret` (or one they know), and `repository.full_name` = `"victim-org/victim-repo"` (a real, unrelated repository with `review_stacks_enabled`). `verify_signature` authenticates against the harmless org and passes; `drop_unhandled_event`/`ExplicitParameters` schema checks do not compare the two fields. `LabeledHandler` then resolves `victim-org/victim-repo`'s `Repository` and, depending on the attacker-chosen PR number/labels, archives or unarchives one of that repository's `ReviewStack`s. If that review stack has `continuous_deployment: true` (settable independently through the normal stacks API/UI by whoever owns it), unarchiving it re-enables `ContinuousDeliveryJob` (`Stack.schedule_continuous_delivery` picks up `not_archived` stacks with `continuous_deployment: true` [7](#0-6) ), which will then auto-deploy the next green commit on that stack via `trigger_continuous_delivery` [8](#0-7)  and `ContinuousDeliveryJob#perform` [9](#0-8) .

Existing guards do not close this gap: `verify_signature` only checks the signature against the org derived from `repository.owner.login`, never against `repository.full_name`'s owner segment [10](#0-9) ; the `ExplicitParameters` schema in `LabeledHandler.params` only requires `repository.full_name` to be a `String`, with no relationship enforced to `repository.owner.login` [11](#0-10) ; and `Repository.from_github_repo_name` performs no ownership/secret check, just a DB lookup [12](#0-11) .

### Impact Explanation
An unauthenticated attacker can cause a state mutation (archive/unarchive of a `ReviewStack`, deprovision/reprovision, resumption of `ContinuousDeliveryJob`, and downstream unauthorized deploy of the next green commit) on a repository/stack that did not authenticate the request — the request was signed (or trivially passed with no signature) for a completely different, unrelated organization. This matches the "payload for one repository mutating another's stack" and "unauthorized deploy" Critical-severity categories: the attacker never needed the victim's `webhook_secret`, GitHub App private key, or any Shipit credential. The action is repeatable against any target repository whose owner+name the attacker can reference in `repository.full_name`, for as long as at least one org in the deployment's multi-org GitHub config has no `webhook_secret` set (or one the attacker knows, e.g. because they installed a Shipit GitHub App on their own org).

### Likelihood Explanation
Requires: (1) the Shipit deployment uses the multi-org `github:` config schema (`Shipit.github_organizations` > 1) since single-org deployments always verify against the sole configured org, which — if that config also lacks a secret — is a broader unauthenticated-webhook issue rather than this cross-org split; (2) at least one configured org has no `webhook_secret` or one known to the attacker; (3) the victim repository has `review_stacks_enabled`; (4) a review stack exists (or is created) with `continuous_deployment: true`. Given these fairly common multi-tenant/config conditions, the attacker's cost is a single crafted HTTP POST with no GitHub or Shipit secret required, and it is trivially repeatable.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, and in every `pull_request`/push handler, enforce that the organization used to select the signing secret is the same organization referenced by `repository.full_name` (and reject the request if they diverge) before dispatching to handlers. Alternatively, derive `repository_owner` exclusively from `repository.full_name`'s owner segment rather than from the separate `repository.owner.login` field, and require `full_name.split('/').first == repository.owner.login` as a precondition for verification.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a request test), no live GitHub:
1. Configure `Shipit.secrets.github` with two orgs: `"harmless-org"` (no `webhook_secret`) and `"victim-org"` (with `webhook_secret: "victim-secret"`).
2. Create `Shipit::Repository` with `owner: "victim-org", name: "victim-repo"`, `review_stacks_enabled: true`, `provisioning_behavior: allow_with_label`. Create an existing archived `ReviewStack` for a PR (e.g. `pr1`) with `continuous_deployment: true`.
3. Assert the binding before the request: `assert_equal "harmless-org", repository_owner_from_payload` and `assert_equal "victim-org", full_name_owner_from_payload` (i.e. they diverge) — this is the equality the invariant demands be equal but the code allows to differ.
4. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature` (or a signature computed with no secret), and JSON body: `action: "labeled"`, `repository.owner.login: "harmless-org"`, `repository.full_name: "victim-org/victim-repo"`, `pull_request.number/head/labels` matching the archived review stack's PR, `pull_request.state: "open"`.
5. Assert response is `200 OK` (not `422`), then assert `stack.reload.archived? == false` (unarchived) and `enqueued_jobs` contains `GithubSyncJob` for that stack — proving a repository that never signed with `victim-secret` had its stack mutated.
6. Optionally run `Stack.schedule_continuous_delivery` / `ContinuousDeliveryJob.perform_now(stack)` and assert a `Deploy` was created, demonstrating amplification into an unauthorized deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do
              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end
