### Title
Multisig transaction payload substitution bypasses approval binding when `abort_if_multisig_payload_mismatch_enabled` is off - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the VM-invoked prologue for multisig transaction execution, only unconditionally checks the caller-supplied `payload` against the on-chain record when the transaction was created with a `payload_hash` (i.e., `create_transaction_with_hash`). When the full `payload` is stored on-chain instead (`create_transaction`), the match between the caller-supplied `payload` argument and the approved, stored `transaction.payload` is enforced **only if** the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on.

### Finding Description [1](#0-0) 

The prologue performs, in order:
1. `assert_is_owner` — any owner (not necessarily the one who created the proposal) can trigger execution.
2. Quorum check (`can_execute`/`can_be_executed`) and timelock check — these are computed against the *stored* transaction record at `sequence_number`, which was approved via `create_transaction`/`vote_transaction` calls referencing either a `payload_hash` or a full `payload`.
3. If `transaction.payload_hash.is_some()`, the caller-provided `payload` is hashed and compared — this path is unconditional.
4. If `transaction.payload.is_some()` **and** the feature `abort_if_multisig_payload_mismatch_enabled` is enabled, the caller-provided `payload` is compared byte-for-byte against the stored `payload`.

Step 4 is the only check binding the caller-supplied `payload` (the bytes that will actually be decoded and executed by the VM as the multisig's entry-function call) to what owners actually voted to approve, for transactions created via the "full payload stored on-chain" path. If that feature flag is disabled, an executing owner can pass an arbitrary `payload` argument to the transaction that satisfies quorum/timelock (which were computed against the sequence number of the *approved* transaction, not against the actual bytes to be executed), while the code that actually runs is different from what other owners approved.

### Impact Explanation
This breaks the core multisig invariant that only a payload explicitly approved by a quorum of owners can execute. An owner with only enough authority for one vote (or the sole executor slot) could submit a k-of-n approved multisig transaction ID but substitute a different, unapproved payload (e.g., transferring funds to an attacker-controlled address instead of the approved recipient), and have it execute as if it were approved — an admission-boundary "approval set" confusion that lets an unprivileged/single-approval actor execute state transitions that should have required full quorum re-approval of the *actual* payload.

### Likelihood Explanation
Exploitability is gated entirely by whether `abort_if_multisig_payload_mismatch_enabled` is turned on for the target network. I was not able to verify from the available code/index whether this flag defaults to enabled in current mainnet/testnet feature sets, nor could I fully trace how the VM sources the `payload` argument passed into `validate_multisig_transaction` at the call site (`aptos-move/aptos-vm/src/transaction_validation.rs` invokes prologues by MoveValue but I did not confirm whether it always forwards the raw transaction's payload bytes verbatim). This uncertainty limits confidence in a definitive "high/critical, unprivileged, currently exploitable" verdict.

### Recommendation
Make the full-payload match check (currently gated by `abort_if_multisig_payload_mismatch_enabled`) unconditional, matching the treatment already given to the `payload_hash` case, so that a stored full payload is always byte-compared against the caller-supplied payload regardless of feature-flag state.

### Proof of Concept
Not constructed — a full PoC would require confirming (a) the default/rollout state of `abort_if_multisig_payload_mismatch_enabled` on a live network, and (b) that the AptosVM's multisig execution path forwards a caller/attacker-controlled `payload` (rather than always substituting the on-chain stored payload) into `validate_multisig_transaction` and into the actual executed entry function. I could not complete this trace within the available tool budget.

**Note on confidence:** Given the feature-flag dependency and the incomplete trace of the VM call site, I am not fully certain this holds as a currently exploitable, unprivileged, high/critical bug in the shipped configuration — flagging this explicitly rather than asserting definitive impact.

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
