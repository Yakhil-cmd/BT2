## Analysis

The forceRepay bug class is about an obligated party being able to satisfy only the minimal, cheap, on-chain requirement of a transfer while withholding the extra off-chain/auxiliary step the counterparty actually needs to realize their funds — shifting cost (or, in ocore's case, total loss) onto the counterparty with no way for the counterparty to compel delivery.

ocore's private (hidden) asset payments have exactly this structural split between "on-chain settlement" and "off-chain delivery of the secret data needed to use the funds," reachable by an ordinary **private-payment counterparty** (the sender).

### Title
Malicious private-payment sender can post a fully valid unit while withholding the private-elements chain, permanently freezing the recipient's funds - (File: `indivisible_asset.js`, `wallet_general.js`, `network.js`)

### Summary
For private assets, on-chain payment messages only carry a `payload_hash` referencing a hidden payload; the actual `address`/`blinding` values that let a recipient later prove and spend their output are never placed on the DAG. They exist only in an off-chain "private elements chain" that the sender must separately push to the recipient's device via `sendPrivatePayments`/the `private_payments` hub message.

### Finding Description
When a private asset payment is composed, the outputs are hashed and stripped of `address`/`blinding` before being placed on-chain [1](#0-0) , so the ledger only stores an opaque `output_hash`. The recipient's ability to ever spend that output depends entirely on receiving the matching private-elements chain (containing `address`, `blinding`, `amount`, `denomination`, and the input reference used to compute the `spend_proof`), which is built via `buildPrivateElementsChain` [2](#0-1)  and validated with `validatePrivatePayment`/`validateSpendProof` [3](#0-2) .

Delivery of this chain is a purely off-chain, sender-controlled step performed in `sendMultiPayment`'s `preCommitCb`, which calls `walletGeneral.sendPrivatePayments` to the recipient's device (or `forwardPrivateChainsToOtherMembersOfOutputAddresses` for local wallets) [4](#0-3) . The underlying primitive `sendPrivatePayments` is a fire-and-forget device message [5](#0-4) .

Ledger-level validation (`validatePayment`/`validatePaymentInputsAndOutputs`) only checks that inputs and outputs balance and that asset rules are respected [6](#0-5) [7](#0-6) ; it has no way to verify, and does not require, that the sender actually delivered the corresponding private elements to the recipient. Once the unit is broadcast and stabilizes, the transfer is final at the consensus layer regardless of whether delivery happened.

This is structurally identical to the `forceRepay` pattern: the obligated party (sender) can satisfy the mandatory, cheap, on-chain leg of the transaction (post the hidden payment) while skipping the considerate off-chain step the counterparty needs (forwarding the private chain), and the counterparty has no on-chain mechanism (no analogue of `redeemNote`) to compel or reconstruct that missing data themselves, because for private assets the address/blinding are never published anywhere else.

### Impact Explanation
Unlike the original report where the lender can still recover funds by paying an extra fee via `redeemNote`, here the outcome is strictly worse: the recipient's coins are consensus-final and unrecoverable by them, because the address/blinding needed to construct a valid future `spend_proof` for the output was never revealed by any channel other than the withheld device message. This is a concrete freezing of counterparty funds, reachable by any ordinary private-payment counterparty (the sender) with no elevated privileges — matching the "AA fund loss or freezing"-style impact bar, generalized to the private-payment domain explicitly called out as an in-scope actor.

### Likelihood Explanation
No special conditions are required beyond acting as the sender in a private-asset payment: compose and broadcast the on-chain unit normally, then simply omit or fail to complete the `sendPrivatePayments` device-message step in the client. Since the hub/device-message delivery layer is entirely separate from and unenforced by unit validation, nothing in the validated protocol prevents this asymmetry, and it can be triggered deterministically by the sender at will.

### Recommendation
Consider making the recipient's ability to spend independent of trusting the sender to forward off-chain data — e.g., by requiring senders to escrow/publish a retrievable, verifiable commitment sufficient for recipients to eventually reconstruct their private chain (with a compensation/penalty mechanism if the sender fails to deliver), analogous to forcing the "cheap path" to also carry the recipient-recovery guarantee, rather than leaving the recipient with no recourse at all.

### Proof of Concept
1. Sender (private-payment counterparty) constructs a private-asset payment to Recipient using `composeAndSaveMinimalIndivisibleAssetPaymentJoint`/`sendMultiPayment`, producing an on-chain unit whose payment message has `payload_location: "none"` and only a `payload_hash` [8](#0-7) .
2. Sender broadcasts the unit; it is validated and stabilizes normally via `validatePayment`, since only balance/asset-rule checks are performed [9](#0-8) .
3. Sender deliberately skips or lets fail the `preCommitCb` step that would call `walletGeneral.sendPrivatePayments(recipient_device_address, arrChainsOfRecipientPrivateElements, ...)` [10](#0-9) .
4. Recipient sees (at best) that some output_hash targets an address they might control but has no `address`/`blinding`/`amount` data reachable from the DAG to construct a valid `spend_proof` per `validateSpendProof` [11](#0-10) , so the funds remain permanently unspendable by them while the sender's coins are already consumed and finalized.

// used for both public and private payments
function validatePayment(conn, payload, message_index, objUnit, objValidationState, callback){

	if (!isNonemptyObject(payload))
		return callback("payment must be a non-empty object");
	if (!isNonemptyArray(payload.inputs))
		return callback("no inputs");
	if (!isNonemptyArray(payload.outputs))
		return callback("no outputs");

	if (!("asset" in payload)){ // base currency
		if (hasFieldsExcept(payload, ["inputs", "outputs"]))
			return callback("unknown fields in payment message");
		if (objValidationState.bHasBasePayment)
			return callback("can have only one base payment");
		objValidationState.bHasBasePayment = true;
		return validatePaymentInputsAndOutputs(conn, payload, null, message_index, objUnit, objValidationState, callback);
	}
