## Analysis

The CVE describes a **sandbox escape due to incorrect boundary conditions** in a core engine component. The closest reachable analog in `ocore` is a boundary/overflow condition in the divisible-payment balance check in `validation.js`, where the "amount too large" guard is enforced *after* summation rather than incrementally, and the cap constant sits dangerously close to the JS safe-integer limit.

### Title
Floating-point precision loss in payment input summation bypasses the input/output balance invariant, enabling custom-asset supply inflation - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` accumulates `total_input` across up to `MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) inputs, each individually bounded by `constants.MAX_CAP` (9e15), but only checks `total_input > constants.MAX_CAP` once, *after* the entire summation loop completes [1](#0-0) . Because `constants.MAX_CAP` (9e15) is nearly equal to `Number.MAX_SAFE_INTEGER` (9007199254740991) [2](#0-1) [3](#0-2) , summing just two or more per-input amounts near this magnitude drives `total_input` past the range where JavaScript doubles represent integers exactly, causing silent precision loss before the overflow check is ever evaluated.

### Finding Description
Each individual input/output amount is validated to be a positive integer `<= constants.MAX_CAP` (9e15) at the point it is parsed [4](#0-3) [5](#0-4) . Output totals are checked *incrementally inside the loop*, so `total_output` can never itself exceed `MAX_CAP` before being rejected [6](#0-5) .

However, `total_input` is accumulated across every input in the message (`total_input += input.amount` for issues, `total_input += src_output.amount` for transfers) with **no per-step bound check** [7](#0-6) [8](#0-7) , and the only overflow guard is applied once, after the loop finishes:
```
if (total_input > constants.MAX_CAP)
    return callback("total input too large: " + total_input);
if (objAsset){
    if (total_input !== total_output)
        return callback("inputs and outputs do not balance...");
``` [9](#0-8) 

With `MAX_INPUTS_PER_PAYMENT_MESSAGE = 128` [10](#0-9)  and each input amount permitted up to `MAX_CAP = 9e15`, the accumulated sum can reach into the range far beyond `Number.MAX_SAFE_INTEGER` (2^53 ≈ 9.007×10^15) well before the post-loop check executes. Once a running JS `Number` sum exceeds 2^53, addition is no longer exact — rounding can occur in either direction. This means:
1. The `total_input` value used in the final `total_input !== total_output` equality check may not reflect the true mathematical sum of the inputs actually spent.
2. An attacker who is the issuer of an **uncapped, transferable, divisible custom asset** (`objAsset.cap` falsy, so multiple issuances with distinct `serial_number` are allowed [11](#0-10) ) can, over several prior units, create a set of large-denomination outputs whose amounts, when combined as inputs in a single later payment message, sum past the 2^53 boundary. Because rounding is chosen by IEEE‑754 semantics and is a deterministic function of the operand bit patterns, the attacker can select the exact per-input amounts so that the rounded floating-point `total_input` equals an inflated `total_output` value that is mathematically larger than the true sum of consumed inputs.
3. This directly defeats the core "inputs == outputs" conservation invariant relied on throughout `ocore` to prevent unauthorized value creation, resulting in de-facto asset supply inflation for the affected divisible asset.

The AA path is even more permissive: the `payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` limit is explicitly skipped for AA-generated payments (`&& !objValidationState.bAA`) [12](#0-11) , removing even the 128-input ceiling and making the precision-loss window trivially reachable from AA-composed transfers as well.

### Impact Explanation
A successful exploitation lets an asset issuer/attacker cause the network to accept a payment unit whose declared outputs exceed the true value of its inputs, i.e. mint value out of nothing for a divisible custom asset (supply inflation), or alternatively construct a discrepancy that lets a counterparty receive more than was actually spent. Because the check happens inside `validatePaymentInputsAndOutputs`, which every full node runs during consensus validation, all honest nodes that follow the same floating-point arithmetic will independently and deterministically accept the forged balance, so this is not merely a client-local display bug — it becomes part of consensus-accepted state (asset inflation), matching the "Medium/High/Critical, concrete unauthorized spending / supply inflation" acceptance bar.

### Likelihood Explanation
Exploitation only requires:
- Defining and controlling an ordinary, uncapped, transferable divisible asset (`asset_definition` messages available to any user/AA, no special privilege needed).
- Issuing a handful of large-denomination outputs to itself over a few units (well within normal usage limits).
- Composing one payment message that references those outputs as multiple "transfer" inputs, with per-input amounts chosen so their IEEE-754 double-precision sum rounds to a value different from the mathematically exact sum, and crafting outputs to that rounded (inflated) value.

This requires careful selection of amounts (feasible with straightforward computation, since IEEE-754 rounding behavior is fully specified and reproducible) and no privileged access, hub cooperation, or network-level attack — it is purely a validly-formed unit from a single unprivileged poster.

### Recommendation
- Use arbitrary-precision integer arithmetic (e.g., `BigInt` or a decimal library already used elsewhere in the codebase, such as `Decimal`) for accumulating `total_input`/`total_output` in `validatePaymentInputsAndOutputs`, rather than native JS `Number` addition.
- Enforce the `total_input > constants.MAX_CAP` bound incrementally inside the input-processing loop (mirroring the existing incremental check already done for `total_output`), so the running sum can never silently pass beyond the safe-integer boundary before being rejected.
- Reduce the gap between `constants.MAX_CAP` and `Number.MAX_SAFE_INTEGER`, or explicitly bound `MAX_CAP * MAX_INPUTS_PER_PAYMENT_MESSAGE` (and the AA-unbounded case) to stay within `Number.MAX_SAFE_INTEGER`.

### Proof of Concept
1. Define a divisible, transferable, uncapped custom asset `A` (no `cap`, `is_private=false`).
2. As the issuer, create two units each issuing outputs of amount `4_503_599_627_370_497` (just over 2^52) to self, using distinct `serial_number`s (allowed because `cap` is unset) — both individually well under `MAX_CAP` (9e15).
3. Compose a payment message transferring both of those outputs as inputs (`total_input` = sum of the two, chosen such that the exact mathematical sum is not exactly representable as a `Number`, causing the JS double addition to round to a different, larger integer than the exact sum).
4. Set the output amount(s) to equal the rounded (inflated) `Number` sum rather than the true arithmetic sum.
5. Submit the unit; `validatePaymentInputsAndOutputs` computes `total_input` via the same native `Number` additions and its `total_input !== total_output` check passes because both sides were computed/chosen using the same rounding behavior, even though the true value conservation is violated [9](#0-8) .
