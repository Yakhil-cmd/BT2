### Title
Custom inflation-rewards commission collector accounts can permanently lose earned commission with no re-register/re-assign option - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
SIMD-0232 lets a vote account's authorized withdrawer point its inflation-rewards (and block-revenue) commission to an arbitrary external system account via `UpdateCommissionCollector`, validated once at set-time by `NewCommissionCollector::validate_and_resolve_key` [1](#0-0) . Unlike the classic behavior where the vote account itself is always the commission recipient, this collector is not re-validated or re-anchored to the vote account, and if the target account's ownership/state changes by the time rewards are distributed (potentially an epoch or more later), the already-earned commission is silently burned in `load_and_reward_commission_accounts`, with no mechanism to re-register the collector retroactively or recover the burned lamports — directly analogous to the Turnstile `register`/`assign` bug where fee accrual is bound to an NFT owner that can change with no re-assign path.

### Finding Description
`update_commission_collector` only checks the collector account's validity (system-owned, rent-exempt, or the Incinerator/vote-account special cases) at the moment the instruction executes [1](#0-0) . This resolved pubkey is stored in vote state (`inflation_rewards_collector`) and is *not* re-verified until distribution time, which can be an arbitrary number of slots/epochs later.

At distribution time, `load_and_reward_commission_accounts` re-fetches the account and re-checks its validity via `collector_type_checked`; if the account is missing, or no longer a valid `SystemAccount`/`Incinerator`, the accrued commission lamports for that vote account are added to `total_non_incinerator_burned_lamports` instead of being paid out [2](#0-1) . The code comments explicitly acknowledge this class of loss:

- "In that situation, the rewards for vote account A will get burned... if vote account B sets a system account as its inflation collector... commission lamports for vote account A will NOT get burned here, but will get burned during `load_and_reward_commission_accounts`" [3](#0-2) 
- "If the account doesn't exist, the vote commission may be enough lamports to cover rent-exemption... otherwise... always vote accounts... `maybe_commission_account` should always exist" (pre-SIMD-0232 invariant that no longer holds once a custom, non-vote-account collector is allowed) [4](#0-3) 

Unlike the legacy vote-account-is-always-the-collector model — where a vote account cannot be closed while it has pending, un-distributed commission or has voted recently (see the SIMD-0123 checks in `withdraw`) [5](#0-4)  — a custom collector set via SIMD-0232 has no such protection: any unprivileged actor who fully controls the designated collector account (or the account itself, if reassigned by its owner) can close it, reassign its owner away from the System Program, or drain it below rent-exemption at any point after `UpdateCommissionCollector` runs and before the next distribution. There is no "re-register"/"re-assign" recovery path analogous to Turnstile's missing re-register: the withdrawer can call `UpdateCommissionCollector` again to fix the pointer for *future* commission, but the commission already accrued for the epoch(s) in between is unconditionally burned at distribution time with no way to recover it.

### Impact Explanation
This causes legitimate, already-earned vote-account commission (part of protocol inflation rewards) to be permanently destroyed (burned) rather than distributed, purely because of the state of an external, less-trusted account chosen by the validator operator. This is a loss/misattribution of rewards at the protocol level — lamports that should have been paid to the commission collector are instead removed from circulation — matching the "misattributed or duplicated rewards" / unintended lamport-burning class explicitly in scope. The root cause (irrevocable accrual bound to a mutable external account with no re-registration option for the already-accrued amount) is structurally identical to the Turnstile finding: fees/rewards generated before a change in the receiving account's status are lost forever.

### Likelihood Explanation
Likelihood is moderate: it requires a validator operator to have configured a custom (non-vote-account) inflation-rewards collector via `UpdateCommissionCollector` (a supported, intended feature of SIMD-0232), and for that account's ownership/rent-exemption state to change between commission accrual and the (up to one epoch later) partitioned distribution. This can happen accidentally (operator repurposes or drains the account) or could be induced by any party who controls the designated collector account, since nothing in the protocol prevents that account's owner from reassigning/closing it after being nominated as a collector.

### Recommendation
Either (a) re-validate the collector at accrual/snapshot time and lock in its state for that reward period so later changes can't retroactively burn already-earned commission, or (b) instead of burning unpayable commission at distribution time, redirect it to the vote account itself (which is always guaranteed to exist and be valid) as a fallback recipient, or hold it in an escrow/re-claimable pool the withdrawer can pull from after fixing the collector — eliminating the unconditional, unrecoverable burn.

### Proof of Concept
1. Vote account V's authorized withdrawer calls `UpdateCommissionCollector(CommissionKind::InflationRewards)` with a valid, rent-exempt, system-owned account C as the new collector; `validate_and_resolve_key` passes and `inflation_rewards_collector` is set to C [1](#0-0) .
2. During the current epoch, V earns inflation commission; `redeem_delegation_rewards` records `commission_pubkey = C` with `is_vote_account = false` [6](#0-5) .
3. Before the epoch-boundary partitioned distribution runs, C's owner (the party controlling C, which need not be V's operator) reassigns C's owner away from the System Program (or closes/drains it below rent-exemption) — an ordinary, unprivileged system-program operation on an account C fully controls.
4. At distribution time, `load_and_reward_commission_accounts` loads C, and `collector_type_checked` fails the `SystemAccount`/`Incinerator` check, so V's entire accrued commission for that epoch is added to `total_non_incinerator_burned_lamports` and never paid [7](#0-6) .
5. V's withdrawer can call `UpdateCommissionCollector` again to point at a fresh valid account, but the commission already burned in step 4 is gone with no re-register/recovery mechanism — mirroring exactly the Turnstile `register`/`assign` limitation where fees accrued before an NFT transfer/burn are permanently lost.

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
