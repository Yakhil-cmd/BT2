### Title
Webhook signature is scoped to `repository.owner.login`/`organization.login`, but every event handler trusts unrelated, unvalidated fields (`repository.full_name`, `sha`) to select the target repository/commit — allowing cross-organization webhook forgery in multi-tenant Shipit deployments ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using only `repository.owner.login` (or `organization.login`) from the JSON body itself. [1](#0-0) [2](#0-1) 
Every downstream event handler, however, resolves the target `Stack`/`Repository` (or `Commit`) using a *different, unvalidated* field of the same attacker-controlled JSON body: `repository.full_name` in the generic `Handler#repository_name`/`stacks` helper used by `PushHandler`, and by every `PullRequest::*Handler`, and by raw `sha` lookup with **no repository scoping at all** in `StatusHandler`. [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Because Shipit explicitly supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` (documented in `docs/setup.md` "Using Multiple Github Applications"), this is a real deployment mode, not a hypothetical misconfiguration. [7](#0-6) 

### Finding Description
This is the same root-cause pattern as the reported reserve-reinitialization bug: a "reserve" (here, a `Stack`/`Commit`'s trusted state) is keyed by one identifier (`aTokenID`/`variableDebtTokenID` in the report; `repository.full_name` / `sha` here) while the *authorization/initialization check* is performed against a different identifier (`asset` in the report; `repository.owner.login` here) that is not cross-validated against the first. Anyone who can satisfy the narrower check can then supply an arbitrary value for the wider, unchecked field and corrupt state that belongs to someone else.

Concretely:
1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` directly from the untrusted, attacker-supplied JSON body, and picks `Shipit.github(organization: repository_owner)` to obtain the webhook secret to HMAC-check against.
2. The HMAC only proves "whoever sent this owns the secret for `repository_owner`" — it does **not** constrain any other field of the JSON body, including `repository.full_name` or `sha`.
3. `Handler#repository_name` (used by `PushHandler`, `CheckSuiteHandler`, and effectively every stack-resolving handler) and each `PullRequest::*Handler#repository` independently read `payload.dig('repository','full_name')` to look up the `Repository`/`Stack` to act on — a value that can freely diverge from `repository.owner.login` used in step 1.
4. `StatusHandler#process` is worse: it doesn't even use the repository at all. It does `Commit.where(sha: params.sha)` globally across the whole Shipit instance and calls `commit.create_status_from_github!(params)`. [8](#0-7) 

So an administrator of GitHub organization **A**, who has legitimately installed the Shipit GitHub App on org A (and therefore legitimately possesses org A's `webhook_secret` — no privileged access to org **B**, no Shipit session, no `ApiClient` token, no repository write access on org B is needed), can POST a hand-crafted webhook to `/webhooks`, sign it with org A's secret, and set:
- `repository.owner.login = "org-A"` (to pass `verify_signature`), and
- `repository.full_name = "org-B/private-repo"` (or an arbitrary `sha` belonging to org B), to act on org B's stacks/commits.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written," which is one of the explicitly in-scope binding classes. Consequences depend on which handler is abused:
- `StatusHandler`: fabricate a CI "success" status on any known commit `sha` belonging to a *different organization's* repository, with no ownership check at all. Because commit deployability and required-status gating (`DeploySpec#required_statuses`) are evaluated against `Commit#statuses`, this can be used to make an otherwise CI-failing/unverified commit appear deployable, enabling an **unauthorized deploy** of an untrusted commit in a foreign organization's stack — a Critical-tier impact per the rubric ("unauthorized deploy"). [9](#0-8) 
- `PushHandler`/`PullRequest::*Handler`: trigger `stack.sync_github`, archive/unarchive review stacks, or provision/deprovision review stacks belonging to a different org's repository — a cross-organization/cross-repository write and disruption of another tenant's stack state without any credential belonging to that tenant.

### Likelihood Explanation
Any organization admin who is allowed to install the Shipit GitHub App on their own org (a normal, low-privilege, self-service action explicitly supported by the multi-org configuration documented in `docs/setup.md`) automatically obtains a valid webhook secret usable to forge these cross-tenant payloads. No secret belonging to the victim org, no `ApiClient` token, and no GitHub write access to the victim repository is required — only knowledge of the target `repository.full_name` (typically public) or a target commit `sha` (often publicly visible via the victim's public commit history/PRs).

### Recommendation
Cross-validate the field used for authentication against the field(s) used for authorization/target resolution within every handler:
1. In `WebhooksController`, after verifying the signature, ensure the resolved `repository_owner` matches the owner-prefix of `repository.full_name` (and of any `organization.login` present) before dispatching to handlers, rejecting payloads with mismatched values.
2. In `Shipit::Webhooks::Handlers::Handler`, thread the authenticated `repository_owner`/`organization` through to `repository_name`/`stacks` resolution and assert it matches, rather than trusting `payload.dig('repository', 'full_name')` unconditionally.
3. Fix `StatusHandler` specifically to scope `Commit.where(sha: params.sha)` to commits belonging to the authenticated organization/repository, not globally across the whole Shipit instance.

### Proof of Concept
Assume a Shipit instance configured with two orgs in `secrets.yml`, `org-A` (secret `sA`) and `org-B` (secret `sB`), and org B has stack `org-B/private-repo` with `shipit.yml` requiring CI context `ci-required`.

1. Attacker is a legitimate admin of `org-A` (has installed the Shipit GitHub app there, thus knows `sA`) but has no access whatsoever to `org-B`.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<sha of a commit on org-B/private-repo the attacker wants to deploy>",
  "state": "success",
  "context": "ci-required",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-A/decoy" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(sA, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "org-A"`, fetches `Shipit.github(organization: "org-A")`, and the signature verifies successfully (attacker legitimately knows `sA`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the commit by `sha` alone, globally, regardless of which org/repo it belongs to — and calls `create_status_from_github!`, marking org B's commit's `ci-required` context as `success`.
6. If `org-B`'s `shipit.yml` lists `ci-required` in `ci.require`, the commit is now considered deployable by `DeploySpec#required_statuses`/deployability checks, even though org B's real CI never reported success — an unauthorized state change performed by an entity with no credentials for org B.

(Verification note: I was unable to load `app/models/shipit/commit.rb` in this session due to a tool error on the final iteration, so the exact wiring from `Commit#statuses` → `deployable?` could not be re-confirmed line-by-line; the gating relationship is inferred from `DeploySpec#required_statuses`/`hidden_statuses`/`soft_failing_statuses` in `app/models/shipit/deploy_spec.rb:190-200` and should be double-checked in `Commit`/`Stack` before relying on the exact deploy-gating mechanics.)
