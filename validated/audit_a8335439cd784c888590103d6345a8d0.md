### Title
StatusHandler#process writes GitHub commit statuses to any Commit row matching a SHA, regardless of which repository the webhook authenticated for - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` with `Commit.where(sha: params.sha).each`, then calls `commit.create_status_from_github!(params)` on every match, without ever checking that `payload['repository']['full_name']` matches the repository that owns the matched `Commit`/`Stack`. Since GitHub SHAs are content hashes and are not unique per repository (e.g., the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any commit an attacker's fork shares with a victim's fork/mirrored history), an attacker who legitimately owns a GitHub org/app registered with Shipit can send a validly-signed `status` webhook for their own repository and have it overwrite the `Status` of a same-SHA `Commit` belonging to an unrelated victim stack.

### Finding Description
The broken binding is: `payload['repository']['full_name']` (the repository the webhook signature authenticates, e.g. `attacker/repo`) **should equal** the repository owning the `Commit` row whose `statuses` get mutated, but the code never enforces this equality.

Code path:
1. `Shipit::WebhooksController#create` parses the raw body and dispatches to handlers after `verify_signature` [1](#0-0) .
2. `verify_signature` only checks that the HMAC signature is valid for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload itself (`params.dig('repository','owner','login')`) [2](#0-1) . This proves the request was signed by *some* organization/app registered with Shipit that the attacker legitimately controls — it says nothing about which `Commit`/`Stack` rows may be touched.
3. `StatusHandler#process` ignores `payload['repository']` entirely and does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
4. Contrast with `PushHandler`, which correctly scopes to the repository named in the payload via the base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) before acting [4](#0-3) [5](#0-4) . `StatusHandler` never calls `stacks` or filters by `repository_name` at all.
5. `Commit#create_status_from_github!` unconditionally writes a `Status` scoped to `self.stack_id` (`statuses.replicate_from_github!(stack_id, github_status)`) and triggers `add_status`, which fires `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` and can call `stack.schedule_merges` [6](#0-5) [7](#0-6)  — i.e. this can directly influence the victim stack's merge/deploy decisions (`deployable?` gates on CI state).

**Existing test coverage confirms the design**: `test/controllers/webhooks_controller_test.rb` (":state create a Status for the specific commit") only checks a single-commit, single-repository scenario using `shipit_commits(:first)` and never exercises the multi-repository-same-SHA case, so nothing catches this divergence [8](#0-7) .

None of the listed guards prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` only validates the sender owns the org named in the payload, not that they own the repository of the target `Commit`; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate shape (`sha`, `state`, etc.), not repository binding; there is no `force_github_authentication`, `User#authorized?`, or `stacks`-scope check anywhere in `StatusHandler`.

### Impact Explanation
An attacker who owns any GitHub organization/app configured in Shipit (a low bar — anyone who registers their own org's Shipit GitHub App/webhook) can forge a `status` event for a commit SHA that also exists in a victim stack's `Commit` table, causing Shipit to write/overwrite that victim commit's `Status` row. Because `deployable?`, `blocked?`, and continuous-delivery scheduling are all derived from `Commit#status`, this is a "payload for one repository mutating another's commit/stack" — matching the Critical impact category (cross-repository write causing potentially unauthorized deploy gating changes). The practical blast radius depends on SHA collisions occurring between the attacker-controlled repo and a targeted victim repo (trivially true for the empty-tree SHA, or for any commit shared via fork/rebase history), but is not universally exploitable against arbitrary unrelated repositories with unrelated histories.

### Likelihood Explanation
Requires: (1) attacker controls a GitHub org/app already registered with Shipit (so `Shipit.github(organization: 'attacker-org')` succeeds) — this is a real precondition that limits attackers to Shipit-onboarded orgs, not literally the entire internet; (2) a target `Commit` row exists with the same SHA (guaranteed for well-known SHAs like the empty tree, or achievable by forking/rebasing against the victim repo history). Given those, the attack is a single unauthenticated-cost, repeatable HTTP POST with no rate limiting evident in the handler.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `PushHandler`'s use of `stacks`/`Repository.from_github_repo_name`, e.g. restrict the `Commit.where(sha: params.sha)` lookup to `stacks.map(&:commits)` (or join through `Stack`/`Repository` on `payload['repository']['full_name']`) before calling `create_status_from_github!`.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` or a new `test/models/shipit/webhooks/handlers/status_handler_test.rb` (both currently absent for this exact scenario):
1. Create two stacks/repositories, e.g. `victim/repo` (fixture stack `shipit`) and `attacker/repo` (a second fixture repository/stack).
2. Create `Commit` rows with the identical `sha` (e.g. `4b825dc642cb6eb9a060e54bf8d69288fbee4904`) in both stacks.
3. POST to `/webhooks` with `X-Github-Event: status`, a signature valid for `attacker-org` (stubbed via `Shipit.github(organization: 'attacker-org')`/`GithubHook.any_instance.stubs(:verify_signature).returns(true)` as in existing tests), and body `{ sha: SHA_X, state: 'success', context: 'ci/travis', repository: { full_name: 'attacker/repo', owner: { login: 'attacker-org' } } }`.
4. Assert: `victim_commit.statuses.reload.count` changed (currently it does, proving the bug) even though the payload's `repository.full_name` (`attacker/repo`) does not equal the victim stack's repository (`victim/repo`) — i.e. assert `payload_repo_full_name != victim_commit.stack.repository.full_name` while `victim_commit.statuses.count` increased, demonstrating the equality claimed as a required invariant is violated in the current code.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
