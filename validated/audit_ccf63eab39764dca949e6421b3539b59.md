### Title
Stack-scoped `ApiClient` tokens can read the build/deploy status of any stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` restricts a stack-scoped `ApiClient` (one with `stack_id` set) to only the single `Stack` it was issued for, by resolving the requested stack through the `stacks` scope: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. `Api::CCMenuController`, however, overrides `#stack` to resolve directly against `Stack.from_param!(params[:stack_id])`, bypassing that scoping entirely. Any valid `ApiClient` token with `read:stack` permission — even one that is supposed to be locked to a single stack — can therefore read the CI/build status ("CCMenu" XML feed, which includes last build status/label/time and web URL) of any stack in the installation, not just the one it was issued for.

### Finding Description
`Stack` has a `belongs_to`-style scoping mechanism for `ApiClient`: `app/models/shipit/stack.rb` declares `has_many :api_clients`, and tokens can be bound to a specific stack via the `stack_id` column on `ApiClient`. [1](#0-0) 

The generic API base controller enforces this binding for every endpoint that resolves `stack` through it: [2](#0-1) 

`Api::CCMenuController` is mounted under the same `Api::BaseController` authentication/permission stack (`before_action :authenticate_api_client`, `require_permission :read, :stack`), but redefines `stack` to ignore the scoping entirely: [3](#0-2) 

Because `require_permission :read, :stack` only checks that the token has the `read:stack` permission string (`ApiClient#check_permissions!`, which is scope-name based, not stack-instance based), and the actual `Stack` record used for rendering is looked up via the un-scoped `Stack.from_param!(params[:stack_id])`, the equality the system is supposed to preserve —

`stack(s) authorized for token == stack(s) the token can touch`

— is broken specifically in this controller. The token's authorization is checked at the permission-string level (`read:stack`), while the object actually acted upon is chosen from the full `Stack` table via a caller-supplied `params[:stack_id]`.

### Impact Explanation
Any holder of a stack-scoped, `read:stack`-only `ApiClient` token (a credential intentionally issued with reduced trust, limited to one stack, e.g. handed to a low-privilege consumer or third-party monitoring integration) can supply an arbitrary `stack_id` to `Api::CCMenuController#show` and receive that other stack's CI/build status information — `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` — for stacks it was never authorized to see. This is an unauthenticated-relative-to-scope read of stack state across a trust boundary that the engine explicitly models (`ApiClient#stack_id`), matching the "High" impact bucket for escalation into unauthorized read of stack state.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` authentication token that has `read:stack` permission and is stack-scoped — no elevated privilege, admin access, or additional secret is needed beyond a token that is explicitly meant to be narrowly scoped. The only "attacker" action is changing the `stack_id` query/path parameter to a different stack's slug. This is a straightforward, deterministic bypass, not a race condition or timing issue.

### Recommendation
Make `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `Api::BaseController` instead of querying `Stack` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so a stack-scoped token can never resolve to a stack outside its `stack_id`. Audit other controllers that override `stack`/`stacks` in the `Api` namespace for the same pattern.

### Proof of Concept
1. As a stack admin, create/imagine an `ApiClient` scoped to `stack_id = A` with permission `read:stack` (e.g., via the `has_many :api_clients` association on `Stack` A).
2. Using that token's `authentication_token` for HTTP Basic auth (or the `token` query param, which `CCMenuController#authenticate_api_client` also accepts), issue:
   `GET /api/stacks/<OTHER_STACK_B_slug>/ccmenu.xml?token=<TOKEN_FOR_A>`
3. `Api::BaseController#authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (`read:stack` is in the token's `permissions`), and `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against stack B directly — bypassing the `current_api_client.stack_id` check entirely.
4. The response renders stack B's build/deploy status XML, even though the token was only meant to authorize stack A. [4](#0-3) [2](#0-1)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
