### Title
Webhook signature check keyed on attacker-supplied `repository_owner`, decoupled from the stack/commit actually written — forged `status` events with a secret-less organization trigger unauthorized continuous-delivery deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization config to validate a webhook signature against solely from the unverified JSON body (`repository.owner.login` / `organization.login`), and `GitHubApp#verify_webhook_signature` fully skips verification whenever that organization's `webhook_secret` is unset. The handler that actually mutates state on behalf of the webhook (`StatusHandler`) never re-checks that the payload's claimed repository/organization matches the stack owning the commit it writes to — it matches purely by commit `sha` across the whole database. This breaks the binding: *"organization authenticated" ≠ "repository/stack written"*, letting an unprivileged attacker forge a CI status event that pushes any tracked commit into a `success` state and, if `continuous_deployment` is enabled on that stack, triggers an unauthorized deploy.

### Finding Description
`verify_signature` resolves the GitHub App config to use for signature verification directly from the untrusted payload: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally accepts the request when that organization has no `webhook_secret` configured: [3](#0-2) 

Because `webhook_secret` is an optional per-organization key (`@webhook_secret = @config[:webhook_secret].presence`, see `lib/shipit/github_app.rb` lines 44-51), any organization onboarded onto the Shipit instance without a configured `webhook_secret` becomes a signature-check bypass: an attacker simply sets `repository.owner.login` (or `organization.login`) in the forged payload to that organization's name, and `verify_signature` treats the request as verified — no `X-Hub-Signature` needs to be valid at all.

Once past `verify_signature`, `WebhooksController#create` dispatches the raw JSON body to the registered handler for `X-Github-Event: status`, `StatusHandler`: [4](#0-3) 

This handler locates commits purely by `sha` — with **no scoping to the organization/repository named in the payload** — and calls `commit.create_status_from_github!(params)` on every matching commit across every stack in the instance. Creating a `Status` record fires: [5](#0-4) 

which calls `commit.schedule_continuous_delivery`: [6](#0-5) 

If the target stack has `continuous_deployment` enabled and is otherwise deployable, `ContinuousDeliveryJob` runs `Stack#trigger_continuous_delivery`, which calls `trigger_deploy(commit, Shipit.user, ...)`: [7](#0-6) 

`Shipit.user` here is the bot/service account (`GithubApp#bot_login`), meaning the deploy is not attributed to (or gated by) any real, authenticated human or `ApiClient` — the forged webhook alone is sufficient to cause the deploy host to check out and execute the stack's deploy steps for that commit.

**The broken binding, as an equality:**
- Before: `organization used to select webhook_secret for signature check` (attacker-controlled payload field) MUST equal `organization/repository owning the stack whose commit is being written` (the actual trust boundary that should gate the write).
- After the attacker's forged request: these are two independent values — the attacker picks an arbitrary secret-less organization for the signature check, while `StatusHandler` writes to any commit matching the given `sha`, regardless of which stack/repository/organization it belongs to.

### Impact Explanation
This is a **Critical** severity finding: an unauthenticated, unprivileged attacker (no Shipit session, no `ApiClient` token, no `webhook_secret`, no GitHub repository write access) can cause an **unauthorized deploy** on any stack that has `continuous_deployment` enabled, provided at least one organization configured on the Shipit instance lacks a `webhook_secret` (an optional, easily-overlooked setting per `lib/shipit/github_app.rb` lines 44-51). The attacker does not need to control the target repository at all — they only need to guess/know a commit SHA already tracked by Shipit (visible on the stack's public commit list/UI) and the name of any secret-less organization on the same instance. This can cause execution of deploy scripts (arbitrary shell commands defined in `shipit.yml`) on the deploy host using the app's stored GitHub credentials, satisfying the "unauthorized deploy" and potentially GITHUB_TOKEN-adjacent impact bar.

### Likelihood Explanation
Likelihood is moderate-to-high in multi-organization Shipit deployments: `webhook_secret` is optional per organization config, and it is plausible that not every onboarded organization sets one (e.g., internal/low-risk repos, or repos onboarded before secrets were mandated). Any single such organization on a shared Shipit instance undermines the signature guarantee for every other stack, because `StatusHandler` does not scope by repository/organization — it is a systemic gap, not an isolated per-repo weakness.

### Recommendation
1. Have `StatusHandler` (and other handlers that key off `sha`/`ref` alone) verify that the commit's owning stack/repository actually matches the `repository.owner.login`/`repository.full_name` present in the (verified) payload before writing any state.
2. Do not silently bypass signature verification when `webhook_secret` is blank; either require a `webhook_secret` for every configured organization, or reject requests for organizations that were resolved from unverified payload fields when no secret is present, rather than treating "no secret configured" as "verification passed."
3. Consider deriving `repository_owner`/organization from a securely re-parsed and already-signature-verified body rather than trusting the pre-verification `params` dig for routing which secret to check.

### Proof of Concept
1. Configure (or find) a Shipit instance with at least two GitHub organizations, where organization `no-secret-org` has no `webhook_secret` in `secrets.github`, and organization `victim-org` owns a stack `victim-org/app` with `continuous_deployment: true`.
2. Attacker sends, without any valid `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status
{
  "repository": { "owner": { "login": "no-secret-org" } },
  "sha": "<sha of latest undeployed commit on victim-org/app>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the forged request is accepted.
4. `StatusHandler#process` finds the commit by `sha` (belonging to `victim-org/app`, unrelated to `no-secret-org`) and creates a `success` `Status` for it.
5. `Status#enable_ci_on_stack`/`schedule_continuous_delivery` fires; if the commit becomes `deployable?` and `victim-org/app` has `continuous_deployment` enabled, `ContinuousDeliveryJob` deploys the commit via `Shipit.user`, with no human or API-authenticated actor involved.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
