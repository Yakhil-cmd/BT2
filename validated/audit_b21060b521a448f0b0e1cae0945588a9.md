### Title
`OpenedHandler#provision?` operator-precedence bug lets attackers auto-provision Review Stacks (and later execute attacker-controlled `shipit.yml`, including `machine.environment` overrides of `GIT_ASKPASS`/`GITHUB_TOKEN`) on repositories where review stacks are explicitly disabled - (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` (and identically `ReopenedHandler#unarchive?`) only applies the `repository.review_stacks_enabled` gate to the `allow_all` branch of its boolean expression due to Ruby `&&`/`||` precedence, not to the `allow_with_label`/`prevent_with_label` branches. If a tracked repository has `review_stacks_enabled: false` but `provisioning_behavior: "prevent_with_label"` (a state reachable simply by toggling the checkbox off after selecting that behavior), any unauthenticated PR opener whose PR lacks the exclusion label auto-provisions a `ReviewStack` whose `branch` is `params.pull_request.head.ref` - fully attacker controlled. Once provisioned, `TaskCommands` (`lib/shipit/task_commands.rb`) reads `shipit.yml` straight from that attacker branch via `DeploySpec::FileSystem.new(@task.working_directory, @stack)`, and its `env` merge chain lets the attacker's `machine.environment` config land in `Command#unbundled_env`, which can override host-managed keys such as `GITHUB_TOKEN`/`GIT_ASKPASS`.

### Finding Description
The binding that should hold is: `respond_to_pull_request_opened? == true` only if `repository.review_stacks_enabled == true` AND (one of the three provisioning-behavior predicates matches). Instead, the code is: [1](#0-0) 

which Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is only ANDed into the first disjunct, so with `review_stacks_enabled: false` and `provisioning_behavior: "prevent_with_label"`, `provision?` still evaluates true whenever the PR lacks the exclusion label. Contrast this with `LabeledHandler#respond_to_label_change?`, which correctly places `repository.review_stacks_enabled &&` as a top-level gate over the whole `(archive? || unarchive?)` expression: [2](#0-1)  - confirming the intended invariant and that `OpenedHandler`/`ReopenedHandler` diverge from it.

`ReviewStackAdapter#create!` then builds the stack with `branch: params.pull_request.head.ref` taken directly from the webhook payload, with no ownership check beyond "PR was opened against this repository": [3](#0-2) , and immediately enqueues it: `Shipit::ReviewStackProvisioningQueue.add(stack)` at line 82.

Once provisioned, `TaskCommands#steps` and `#env` execute that branch's `shipit.yml`: [4](#0-3) [5](#0-4) 

`deploy_spec.machine_env` is populated solely from `config('machine', 'environment')` of the checked-out `shipit.yml`: [6](#0-5) . It is merged after the `super` (`Commands#env`/`base_env`, which sets `GITHUB_TOKEN` and `GIT_ASKPASS`): [7](#0-6) , and later merges win, so `machine_env` overrides those keys. The final env then flows unchanged into `Command#unbundled_env`: [8](#0-7) , which is passed to `PTY.spawn` at line 92. This override behavior itself is intentional/tested functionality (`test/unit/deploy_commands_test.rb:330-332,346-349`), meaning the trust boundary for "who is allowed to set `machine.environment`" is entirely delegated to "who controls the branch behind a provisioned stack" - which is exactly what the `provision?` precedence bug lets an attacker forge.

Existing guards do not catch this: `ExplicitParameters` only validates payload shape, not authorization; there is no signature/label re-check between `provision?` returning true and `ReviewStackProvisioningQueue.work` actually calling `stack.provision`; and the only test covering the "disabled" case uses `behavior: :allow_all` (`test/models/.../opened_handler_test.rb:96-107`), leaving the `review_stacks_enabled: false` + `provisioning_behavior: "prevent_with_label"` combination completely untested.

### Impact Explanation
An attacker who can merely open a pull request against a tracked repository can force Shipit to auto-provision and run a `ReviewStack` even though the repository owner turned review-stack auto-provisioning off, executing arbitrary commands from the attacker's own `shipit.yml` (`deploy_steps`, `tasks`, `dependencies_steps`) with the deploy host's environment, including the ability to override `GITHUB_TOKEN`/`GIT_ASKPASS` via `machine.environment`. This is Critical: RCE on the deploy host, and exposure/redirection of `GITHUB_TOKEN` credential flows for that repository/organization. The blast radius is scoped to repositories that are tracked in Shipit and have this specific misconfiguration (`review_stacks_enabled=false`, `provisioning_behavior="prevent_with_label"`), which is a realistic transient/operational state (e.g., an operator disabling the feature via checkbox without resetting the behavior dropdown).

### Likelihood Explanation
Preconditions: the target repository must already be tracked by Shipit, and must have `provisioning_behavior` set to `prevent_with_label` while `review_stacks_enabled` is `false`. This requires no attacker privilege - only ordinary repository-owner UI use elsewhere in time (enabling review stacks with prevent_with_label, then disabling the checkbox later without changing the dropdown) produces this state, which is plausible given the two settings are independent form fields (`app/views/shipit/repositories/settings.html.erb:9-41`). Once that state exists, exploitation is trivial and repeatable: any GitHub user can open a PR without the exclusion label and repeatedly trigger this for the same or different repositories in this state.

### Recommendation
Add explicit parentheses in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` so `review_stacks_enabled` gates all three behavior branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Add regression tests for `review_stacks_enabled: false` combined with `allow_with_label` and `prevent_with_label` behaviors.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no exclusion label

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
This currently fails (a `Stack` IS created) because `provision?` evaluates true despite `review_stacks_enabled == false`, demonstrating the broken binding.

A follow-on test in `test/lib/shipit/task_commands_test.rb` demonstrates the downstream env-override consequence:
```ruby
test "#env allows shipit.yml machine_env to override GIT_ASKPASS/GITHUB_TOKEN" do
  stack = shipit_stacks(:review_stack)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  commands = Shipit::TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(stub(machine_env: { 'GIT_ASKPASS' => '/tmp/evil' }))

  assert_equal '/tmp/evil', commands.env['GIT_ASKPASS']
end
```
