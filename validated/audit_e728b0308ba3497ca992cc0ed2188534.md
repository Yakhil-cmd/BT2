### Title
Hardcoded bypass of unresolved inner-address-definition guard allows unauthorized `["address", ...]` spending conditions to validate without any signature check - (File: definition.js)

### Summary
In `definition.js`, `validateDefinition()`'s handling of the `'address'` operator contains a safety check that was effectively disabled: the real guard (`objValidationState.bAllowUnresolvedInnerDefinitions`) is commented out and replaced with a hardcoded `var bAllowUnresolvedInnerDefinitions = true;`, unconditionally accepting an unresolved inner address reference as valid. This mirrors the Keras `Lambda` bug class: a safe/unsafe decision that should be driven by an explicit per-call context flag is instead collapsed to a constant "allow" value, silently disabling the intended default-deny behavior.

### Finding Description
`validateDefinition()` recursively validates address/asset spending-condition definitions such as `['and', [...]]`, `['sig', ...]`, and `['address', other_address]`. For the `'address'` case: [1](#0-0) 

```js

        return cb("no references allowed in address definition");
    ...
    storage.readDefinitionByAddress(conn, other_address, objValidationState.last_ball_mci, {
        ifFound: function(arrInnerAddressDefinition){
            ...

        ifDefinitionNotFound: function(definition_chash){
        //	if (objValidationState.bAllowUnresolvedInnerDefinitions)
        //		return cb(null, true);
            var bAllowUnresolvedInnerDefinitions = true;

            if (arrDefiningAuthors.length === 0) // no address definition in the current unit
```

The original, correct logic (visible in the commented-out lines) is: only accept an unresolved inner-address reference as valid when the *caller explicitly opted in* via `objValidationState.bAllowUnresolvedInnerDefinitions`. That flag is deliberately set to `true` only in an offline/local pre-validation helper used by the wallet UI: [2](#0-1) 

For all real on-chain validation paths (units posted to the network, AA triggers, asset issue/transfer condition checks, authentifier checks), `objValidationState` is never given `bAllowUnresolvedInnerDefinitions = true`, so before this change an `['address', X]` definition that references an address `X` whose actual definition cannot be found on-chain (`ifDefinitionNotFound`) and is not co-supplied by the current unit's authors would correctly fail: `"definition of inner address X not found"`.

With the hardcoded `var bAllowUnresolvedInnerDefinitions = true;` inside the callback, this default-deny behavior is unconditionally overridden for every caller, including real consensus-critical unit/authentifier validation. Any unit or address/asset condition that includes `['address', X]` referencing an address `X` with no known/matching definition will now have that branch of the definition tree treated as satisfied (`cb(null, true)`) regardless of `objValidationState.bAllowUnresolvedInnerDefinitions`'s real value.

This is structurally identical to the Keras bug class: a nullable/absent authorization flag (`bAllowUnresolvedInnerDefinitions === undefined` in real network validation, meaning "not explicitly allowed" i.e. default-deny) is conflated with an explicit `true`, permanently disabling the security guard that the comment shows was intended.

### Impact Explanation
`validateDefinition()` gates whether a *structural* branch of an address/asset spending-condition definition is well-formed and resolvable; `validateAuthentifiers()` (the actual authorization check that walks the same tree and demands real signatures at authentifier paths) is a separate pass, but the bypass also affects the analogous `evaluate()` for the `'address'` op in `validateAuthentifiers`. If an attacker crafts a definition using `['and', [['sig', {...pubkey_they_control...}], ['address', X]]]` or similar composite conditions where a branch nested under `'address'` references an address `X` that has no findable/matching definition, `validateDefinition` will accept the overall definition as structurally valid even though the referenced sub-definition can never be authenticated on its own. Depending on how the branch composes with `'and'`/`'or'`/`'r of set'` semantics in `validateAuthentifiers`, this can let an attacker construct address definitions or asset issue/transfer conditions that pass structural validation but whose real authorization requirements are effectively unresolvable/never-checked, undermining node agreement on validity of units, address definitions, and asset conditions (an unprivileged unit poster can post such a definition as part of a new address or address-definition-change message). This is a consensus-integrity bug: nodes intending to enforce "definition of inner address not found" as a hard validation failure will instead silently accept, creating potential node disagreement on validity/spendability and paths toward unauthorized-looking definitions being accepted into the network.

### Likelihood Explanation
Any unpriviledged actor who can post a unit (posting a new address definition, an address-definition-change message, or an asset issue/transfer condition referencing `['address', X]`) reaches this code path directly through `validateDefinition()`, which is invoked from unit/message validation flows (`validation.js` for address definitions, asset definitions, and authentifier checks). No special keys or privileged role is needed — merely crafting a unit whose definition includes a nested `['address', X]` op where `X`'s definition is absent from storage and not co-supplied by an author in the same unit. This is a normal, low-cost, always-reachable operation for any wallet user or script capable of composing raw unit definitions.

### Recommendation
Restore the intended guard: replace the hardcoded `var bAllowUnresolvedInnerDefinitions = true;` with the commented-out check `if (objValidationState.bAllowUnresolvedInnerDefinitions) return cb(null, true);` followed by the original `"definition of inner address ... not found"` failure path for callers that do not explicitly set the flag. Audit all callers of `validateDefinition`/`validateAuthentifiers` to confirm the flag is only ever set for the intentional offline/local pre-check use case (`wallet_defined_by_addresses.js`) and never for real consensus validation.

### Proof of Concept
Conceptual PoC (cannot be executed without live node/test harness access, but the code path is deterministic):
1. Choose an address `X` for which no `definitions`/`addresses` row exists in storage (i.e., never used before, and not present as a co-author in the target unit).
2. Compose an address definition/asset condition containing `['address', X]` as a term (e.g. combined with a real `sig` clause the attacker controls via `and`/`or`).
3. Post a unit that defines a new address using this composite definition (or an asset with `issue_condition`/`transfer_condition` containing this term), without including any author whose `address === X`.
4. In `validateDefinition`, `storage.readDefinitionByAddress` calls `ifDefinitionNotFound`; `arrDefiningAuthors.length === 0` (no matching co-author supplies `X`'s definition), yet the branch is now unconditionally treated as valid (`cb(null, true)`) because of the hardcoded `bAllowUnresolvedInnerDefinitions = true`, rather than failing with `"definition of inner address X not found"` as intended for real network validation.
