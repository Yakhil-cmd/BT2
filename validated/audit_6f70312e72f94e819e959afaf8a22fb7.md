### Title
Validator Node Private Key Written World-Readable (`os.ModePerm` / 0o777) by `kgen` Tool — (File: cmd/kgen/main.go)

### Summary
`cmd/kgen/main.go`'s `writeNodeKeyInfoToFile` writes the raw ECDSA validator node private key to disk with `os.ModePerm` (0o777) permissions. The same function also serialises the key into `node_info.json` (via the `validatorInfo.Nodekey` field) and writes that file with identical world-readable/writable permissions. Any unprivileged local OS user on the machine where key generation was performed can read the unencrypted private key and then sign `onlyNodeId`-gated AddressBookV2 system-contract calls (`readyCandidate`, `unreadyCandidate`, `readyValidator`, `unreadyValidator`, `pause`, `resume`, `exit`, `offboard`) on behalf of the victim validator, constituting validator-set privilege escalation.

### Finding Description

`writeNodeKeyInfoToFile` in `cmd/kgen/main.go`:

```go
// line 104
if err = os.WriteFile(nodeKeyFilePath, []byte(nodekey), os.ModePerm); err != nil {
    return err
}
// line 114
if err = os.WriteFile(validatorInfoFilePath, []byte(str), os.ModePerm); err != nil {
    return err
}
```

`os.ModePerm` equals `0o777`. Both the `nodekey` file (raw 32-byte ECDSA private key in hex) and `node_info.json` (a JSON object whose `Nodekey` field is the same raw hex) are created world-readable and world-writable. [1](#0-0) 

The `validatorInfo` struct that is marshalled into `node_info.json` explicitly carries the private key:

```go
type validatorInfo struct {
    Address  common.Address
    Nodekey  string   // raw hex private key
    NodeInfo string
}
``` [2](#0-1) 

The same pattern is repeated in `cmd/homi/setup/cmd.go` `writeValidatorsAndNodesToFile`, which writes `nodekey<i>` and `validator<i>` files (the latter containing the raw key in JSON) with `os.ModePerm`: [3](#0-2) 

By contrast, the rest of the codebase correctly uses `0o600` for secret files. `crypto.SaveECDSA` writes with `0o600`: [4](#0-3) 

And `cmd/kcn/genkeys.go` `writeFile` also uses `0o600` for all secret material: [5](#0-4) [6](#0-5) 

### Impact Explanation

The `nodekey` is the validator's P2P identity key and the signing key for all `onlyNodeId`-gated AddressBookV2 system-contract operations. The `kcn` README states explicitly:

> `nodekey` — node identity (p2p) + createNode `nodeId`; **signs state transitions (onlyNodeId)**
> These commands require `msg.sender == node-id` (the private key **is** the node key). [7](#0-6) 

An attacker who reads the `nodekey` file can:
1. Submit `readyCandidate` / `unreadyCandidate` / `readyValidator` / `unreadyValidator` / `pause` / `resume` / `exit` / `offboard` transactions signed with the stolen key, directly manipulating the victim validator's lifecycle state in AddressBookV2. [8](#0-7) 

2. Force the validator out of the active set (`exit` / `offboard`), reducing the active validator count and potentially disrupting BFT consensus liveness.

This is a validator-set privilege escalation that changes protected on-chain state (node lifecycle state in AddressBookV2, which drives `applyTransition` and `writeTransitionToABv2`). [9](#0-8) 

### Likelihood Explanation

Medium. The attacker requires local OS access to the machine where `kgen --file` was executed. In practice, validator key generation is often performed on shared cloud VMs, CI/CD runners, or jump hosts with multiple OS users. Because the files persist on disk after generation and carry `0o777` permissions, any co-tenant user can read them at any time after the fact — no race condition is required.

### Recommendation

Replace `os.ModePerm` with `0o600` in both `os.WriteFile` calls inside `writeNodeKeyInfoToFile` (`cmd/kgen/main.go` lines 104 and 114) and in `writeValidatorsAndNodesToFile` (`cmd/homi/setup/cmd.go` lines 1361 and 1366). Additionally, remove the `Nodekey` field from the `validatorInfo` struct (or omit it from the JSON output) so that the raw private key is never written to `node_info.json` in plaintext.

### Proof of Concept

```bash
# 1. Generate keys with kgen
kgen --file --ip 127.0.0.1 --port 32323

# 2. Observe world-readable permissions
ls -la keys/
# -rwxrwxrwx  nodekey        ← 0o777
# -rwxrwxrwx  node_info.json ← 0o777

# 3. Any local user reads the raw private key
cat keys/nodekey
# e.g. a1b2c3d4...  (64 hex chars = 32-byte ECDSA private key)

# 4. node_info.json also leaks it in plaintext
jq .Nodekey keys/node_info.json
# "a1b2c3d4..."

# 5. Attacker uses the stolen key to call onlyNodeId-gated ABv2 functions
# e.g. kcn valops exit --private-key 0xa1b2c3d4... --endpoint <rpc>
# → validator is forcibly exited from the active set
```

func writeValidatorsAndNodesToFile(validators []*ValidatorInfo, parentDir string, nodekeys []string) {
	parentPath := path.Join(outputPath, parentDir)

	for i, v := range validators {
