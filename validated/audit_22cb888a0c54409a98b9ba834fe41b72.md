### Title
Webhook signature verified against `repository.owner.login`'s GitHub App, but handlers act on the (attacker-controlled) `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` derives which GitHub App/organization config to use for HMAC verification from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), while every event handler resolves the actual `Stack`/`Repository` to mutate from a *separate* field, `payload.dig('repository', 'full_name')`. These two fields are never checked for consistency, so the organization whose secret authenticated the request is not bound to the repository the handler subsequently writes to.

### Finding Description
`verify_signature` picks the GitHub App config by `repository_owner`: [1](#0-0)  and [2](#0-1) . It uses `github_app.verify_webhook_signature` to HMAC-check `X-Hub-Signature` against `webhook_secret` configured for that specific organization: [3](#0-2) .

Once verified, `create` fans the parsed JSON body out to every registered handler for the event unmodified: [4](#0-3) . Handlers however key off `repository.full_name`, not `repository.owner.login`, to find the target `Repository`/`Stack`: [5](#0-4) [6](#0-5) 

Because Shipit supports multiple organizations, each with its own GitHub App config and `webhook_secret` (`config/secrets.*.yml`), an operator of *any one* configured organization knows their own `webhook_secret`. That operator can sign an arbitrary JSON payload where `repository.owner.login` is their own org (so `verify_signature` picks their own app and the signature validates), but `repository.full_name` is set to `victim-org/victim-repo`, a repository belonging to a *different* configured organization on the same Shipit instance. `Repository.from_github_repo_name` and the handlers will happily act on that victim repository/stack.

This is the exact class of bug described in the report: a value that is trusted and acted upon (`repository.full_name`) is never bound to the value that was actually authenticated (`repository.owner.login`/the signing secret) — an organization-authenticated-vs-repository-written mismatch.

### Impact Explanation
`PushHandler` calls `stack.sync_github(expected_head_sha:)` for every matching, non-archived stack under the spoofed `full_name` [7](#0-6) , and `PullRequest::ClosedHandler` calls `review_stack.archive!` based purely on `params.repository.full_name` [8](#0-7) . `CheckSuiteHandler` and `StatusHandler` similarly let an attacker post fabricated commit statuses / check-run refresh triggers for a victim's commits [9](#0-8) . These are read/state-changing operations on stacks the attacker's organization does not own, but they are bounded to sync/status/archive actions rather than a direct unauthorized deploy, merge, RCE, or credential exfiltration — the concrete high-severity outcomes the rules require (unauthorized deploy/rollback/merge, RCE, auth bypass, credential exfiltration, or cross-repo writes) are not clearly reached by any single in-scope handler observed. `StatusHandler` writing fabricated commit statuses onto a victim's commits could influence deploy-readiness checks (`Commit#create_status_from_github!`), which is the closest path toward an unauthorized-deploy outcome, but confirming that requires tracing how commit statuses gate deploy eligibility, which was not fully verified within the available context.

### Likelihood Explanation
Exploitation requires the attacker to control (or register) a legitimate organization on the same Shipit instance — i.e., they need their own configured `github` entry with a known `webhook_secret`, and knowledge that another organization's repository (`owner/name`) is also configured as a `Stack` on the same instance. `/webhooks` is publicly reachable and unauthenticated by design (rules explicitly exclude requiring a Shipit session/API token as an "attack cost", and this crosses no such boundary — it only requires a webhook secret the attacker's own org already possesses).

### Recommendation
In `WebhooksController#verify_signature`, ensure `repository.owner.login` matches the organization actually implied elsewhere in the payload, or better, require handlers to re-derive/re-validate that `repository.full_name`'s owner segment equals `repository_owner` (the organization whose secret validated the signature) before performing any lookup/mutation in `Handler#stacks` and in each handler's `repository` resolution.

### Proof of Concept
1. Operate (or be granted) organization `attacker-org` configured in Shipit with a known `webhook_secret`.
2. Craft a `push` (or `pull_request`, `status`, `check_suite`) webhook JSON body where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"` (a real `Stack` configured on the same Shipit instance)
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org's webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` selects `Shipit.github(organization: "attacker-org")` and the signature validates. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `sync_github` on the victim's stack, despite the request never being signed by (or originating from) victim-org's GitHub App. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
