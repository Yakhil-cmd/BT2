### Title
Webhook signature verification binds trust to `repository.owner.login`, but repository-writing handlers act on the unverified `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while the handlers that actually act on the payload to look up and mutate a `Stack`/`Repository` resolve the target repository from a different field, `payload.dig('repository', 'full_name')`. The equality the signature is supposed to guarantee — "the organization whose secret authenticated this request" == "the repository being written to" — is broken because these are two independent, attacker-controlled fields inside the same signed body, and only one of them is used to pick which secret validates the signature.

### Finding Description
`verify_signature` looks up the app config via `repository_owner` and calls `github_app.verify_webhook_signature`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance configured per-organization (see `config/secrets.development.shopify.yml`, which shows multiple orgs each with their own `webhook_secret`) [3](#0-2) , and `verify_webhook_signature` performs an HMAC-SHA1 comparison against that org's `webhook_secret` and the raw request body [4](#0-3) .

Once the HMAC check passes, `create` dispatches the entire parsed payload to the registered handlers for the event, unmodified: [5](#0-4) 

However, the base `Handler` class (used by pull_request handlers and others) determines the target `Repository`/`Stack` from a *different* JSON path than the one used for signature-org selection: [6](#0-5) 

Concretely: signature selection uses `repository.owner.login`; repository resolution for writes uses `repository.full_name`. Both fields live in the same HMAC-signed JSON body, so the signature does cover their literal byte values — but the *decision of which secret to check against* is keyed off `owner.login`, not `full_name`. In a multi-organization Shipit deployment (explicitly supported, as shown by the secrets file listing `somegithuborg` and `someothergithuborg` each with independent `webhook_secret`s), a party that legitimately controls (or has leaked) the webhook secret for Org A can craft a raw POST body where `repository.owner.login = "OrgA"` (so the signature validates against Org A's secret) while `repository.full_name = "OrgB/some-other-repo"`. The request passes `verify_signature` because HMAC(OrgA_secret, body) is valid, then `Handler#repository_name`/`Repository.from_github_repo_name` resolves and mutates the `Stack`/`Repository` belonging to Org B, e.g. via `PullRequest::OpenedHandler`, which calls `ReviewStackAdapter#find_or_create!` scoped to `repository.review_stacks` for whatever repo the crafted `full_name` names: [7](#0-6) 

This is the direct structural analog of the Snaps issue: the report's `hello`/`togglepopup` RPC calls were accepted from any connected origin without checking that the origin matched the address/config being mutated. Here, the *cryptographic authentication* is anchored to one payload field (`repository.owner.login`), but the *authorization decision* (which repository's stacks get created/mutated) is made from a sibling field (`repository.full_name`) that was never used to select the verifying key. The binding "org that authenticated" == "repo that is written" is not enforced.

### Impact Explanation
This breaks a cross-organization/cross-repository trust boundary explicitly called out in scope: an entity holding only Org A's webhook secret can cause Shipit to create or mutate review stacks (and potentially other stack state driven by pull_request/push webhook handlers) for a repository under a completely different, unrelated GitHub organization also configured on the same Shipit instance. This matches the "Critical - cross-repository writes" impact bucket, since the write target is decoupled from the credential that authorized the request.

### Likelihood Explanation
Exploitability requires: (1) a Shipit instance configured with more than one GitHub organization (explicitly supported and documented in `config/secrets.development.shopify.yml`), and (2) possession of the webhook secret for at least one of those organizations (which is a lower bar than full repository write access or an API token — webhook secrets are often distributed to CI/webhook relay infrastructure and are not "privileged account" credentials in the same sense as `api_clients_secret` or a GitHub App private key). Given that, crafting the payload is trivial — it's just picking two different string values for `owner.login` and `full_name` in a JSON body.

### Recommendation
Derive the organization used for signature verification from the same field that handlers use for authorization decisions (`repository.full_name`'s owner segment, or better, verify against every configured org whose derived owner could plausibly match, and reject if `owner.login` disagrees with the owner segment of `full_name`). At minimum, add a consistency check in `WebhooksController#verify_signature` (or in `Handler`) asserting that `params.dig('repository','owner','login')` matches the owner extracted from `params.dig('repository','full_name')` before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Shipit configured with two orgs, `OrgA` (attacker has webhook secret) and `OrgB` (victim org, has a repo `OrgB/victim-repo` with `review_stacks_enabled` and a permissive provisioning behavior).
2. Attacker crafts a `pull_request` webhook JSON body:
```json
{
  "action": "opened",
  "number": 1,
  "pull_request": { ... valid pull_request shape ..., "head": {"sha": "...", "ref": "attacker-branch"} },
  "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo" },
  "sender": {"login": "attacker"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` computes `repository_owner = "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the HMAC matches — request passes. [8](#0-7) 
5. `PullRequest::OpenedHandler` resolves `repository = Shipit::Repository.from_github_repo_name("OrgB/victim-repo")` and, if provisioning conditions are met, creates/mutates a review stack for `OrgB/victim-repo` — despite the request only ever having been authenticated against `OrgA`'s secret. [9](#0-8)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
