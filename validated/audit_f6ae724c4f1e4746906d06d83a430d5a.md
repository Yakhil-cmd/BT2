### Title
Missing membership/authorization check in `addDeviceXPubKey` allows any paired device to inject itself into an existing multisig wallet's cosigner list and permanently brick that wallet - (File: `wallet_defined_by_keys.js`)

### Summary
`addDeviceXPubKey`, exported and invoked from the network/device-message layer as `// called from network, without user interaction`, blindly inserts a row into `extended_pubkeys` for any `(wallet, device_address)` pair supplied in an incoming `my_xpubkey` message, then marks it approved and re-checks completion of the wallet setup, with no verification that `device_address` is actually one of the cosigners defined in the wallet's `wallet_definition_template`. [1](#0-0) 

### Finding Description
`addWallet` derives the authoritative set of cosigner device addresses from the wallet's signing-path template (`getDeviceAddressesBySigningPaths`) and only that fixed set of addresses is expected to ever appear in `extended_pubkeys` for a given wallet. [2](#0-1) 

However, `addDeviceXPubKey` (reachable when a peer device sends a `my_xpubkey` message) performs an unconditional `INSERT ... IGNORE INTO extended_pubkeys (wallet, device_address)` followed by an `UPDATE ... SET extended_pubkey=?, approval_date=NOW()` for whatever `wallet` and `device_address` values are contained in the attacker-controlled message, without first checking that this `device_address` belongs to the wallet's member set defined by `wallet_definition_template`. [3](#0-2) 

This is inconsistent with the sibling function `deleteWallet`, which explicitly checks membership (`SELECT approval_date FROM extended_pubkeys WHERE wallet=? AND device_address=?` and bails out if `rows.length === 0`, i.e., "you are not a member device") before mutating any wallet state. [4](#0-3) 

Because wallet ids (the sha256 hash of the initiator's `xPubKey`) and the fact that a wallet-creation offer is in progress are known to any device that received (or eavesdropped/replayed) the `create_new_wallet`/`my_xpubkey` handshake, an unrelated paired device can craft a `my_xpubkey` message naming any pending `wallet` id and its own `device_address`/xPubKey. This adds an extra, illegitimate row to `extended_pubkeys` for that wallet. `checkAndFullyApproveWallet` and `checkAndFinalizeWallet` subsequently poll `extended_pubkeys` joined on `wallet` and require every row to have `approval_date`/`member_ready_date` set before the wallet can be marked `full_approval_date`/`ready_date`. [5](#0-4) 

Since the injected row's `device_address` is not among the addresses actually derivable from the definition template, no legitimate device will ever send the corresponding `wallet_fully_approved`/ready acknowledgment for it, so `checkAndFinalizeWallet`'s condition `rows.some(row => !row.member_ready_date)` remains permanently true. The multisig wallet setup can never complete (`ready_date` never gets set), bricking the shared wallet for all its real cosigners — directly analogous to the reported `setPoolActive` issue where an unauthorized caller flips a state flag that other legitimate flows depend on, permanently denying the intended functionality.

### Impact Explanation
A multisig/shared wallet that legitimate cosigners are trying to jointly set up can be permanently prevented from reaching `full_approval_date`/`ready_date` by an unrelated device that is merely paired with one of the participants (no wallet membership required), because `addDeviceXPubKey` performs no authorization check before mutating `extended_pubkeys` and re-triggering the approval/finalization state machine. This is a denial-of-service against the wallet-creation/finalization flow — the analog of "bricking" described in the source report — potentially preventing funds from ever being spendable/manageable through that address setup path.

### Likelihood Explanation
Reaching this code only requires being a paired device able to send a `my_xpubkey` network message with an attacker-chosen `wallet` (a hash the attacker can learn from the handshake it is targeting) and its own real `device_address`/xPubKey — no signature over the wallet's authoritative definition template is required and no check ties the message to a device actually named in that template. This fits the allowed category of "paired device"/"wallet message handling" reachable by an unprivileged counterparty.

### Recommendation
In `addDeviceXPubKey` (and `handleNotificationThatWalletFullyApproved`), before inserting/updating `extended_pubkeys`, verify that `device_address` is actually one of the addresses derived from the wallet's stored `definition_template` (i.e., mirror the membership check already present in `deleteWallet`), rejecting/no-op'ing the message otherwise.

### Proof of Concept
1. Device A and Device B start creating a multisig wallet; Device A sends `create_new_wallet`/`my_xpubkey` messages, exposing `wallet` (hash of A's xPubKey) to any device that can see the handshake, e.g. via `sendOfferToCreateNewWallet`/`sendMyXPubKey`. [6](#0-5) 
2. Attacker device C, which is not part of the `wallet_definition_template`, sends a `my_xpubkey` message to Device A (or B) with the same `wallet` id and C's own `device_address`/xPubKey.
3. On the receiving side, `addDeviceXPubKey(wallet, "C's device_address", xPubKey, onDone)` is invoked with no membership check, inserting a new `extended_pubkeys` row for `(wallet, C)` and setting `approval_date`. [3](#0-2) 
4. `checkAndFullyApproveWallet` and `checkAndFinalizeWallet` now require a `member_ready_date` from C's illegitimate row that will never legitimately arrive, so the wallet never reaches `ready_date`, bricking the setup for A and B. [5](#0-4)

function checkAndFinalizeWallet(wallet, onDone){
	db.query("SELECT member_ready_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0){ // wallet not created yet or already deleted
		//	throw Error("no wallet in checkAndFinalizeWallet");
			console.log("no wallet in checkAndFinalizeWallet");
			return onDone ? onDone() : null;
		}
		if (rows.some(function(row){ return !row.member_ready_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET ready_date="+db.getNow()+" WHERE wallet=? AND ready_date IS NULL", [wallet], function(){
			if (onDone)
				onDone();
			eventBus.emit('wallet_completed', wallet);
		});
	});
}

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}

function addDeviceXPubKey(wallet, device_address, xPubKey, onDone){
	db.query(
		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",

				"UPDATE extended_pubkeys SET extended_pubkey=?, approval_date="+db.getNow()+" WHERE wallet=? AND device_address=?",

					eventBus.emit('wallet_approved', wallet, device_address);
					checkAndFullyApproveWallet(wallet, onDone);
				}

	);
