### Title
Cross-stack authorization bypass in CCMenu API endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug-class hint (unenforced binding between an authorized scope and the resource actually acted upon) maps onto Shipit's `ApiClient` stack-scoping mechanism. `Shipit::Api::BaseController` establishes the security invariant that a stack-scoped `ApiClient` token can only see the single `Stack` it is bound to, but `Shipit::Api::CCMenuController` re-implements its `stack` lookup in a way that ignores this scoping entirely, breaking the equality: `stack a token authorizes == stack it touches`.

### Finding Description
`Shipit::Api::BaseController` defines the authorization-scoping primitive used by every other API controller: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is bound to a specific stack, and `StacksController` correctly builds its resource lookup on top of that scoped relation: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass the scoped relation entirely and query the global `Stack` model directly by the caller-supplied `stack_id` param: [3](#0-2) 

Because `Stack.from_param!` is called instead of `stacks.from_param!`, the `current_api_client.stack_id` binding is never consulted for this action. `ApiClient` tokens that are intentionally created scoped to a single stack (confirmed by the `stack_id` column and the `stacks` scoping logic in `BaseController`, and exercised by `CCMenuUrlController`'s `:fetch` action, which creates a read-only, stack-scoped `ApiClient` for embedding in CCTray-style monitoring URLs) therefore only enforce their permission bit (`read:stack`, via `require_permission :read, :stack`) but not their stack binding, on this endpoint.

### Impact Explanation
An `ApiClient` token that was minted/leaked for a single stack (e.g., the read-only token generated by the "fetch CCMenu URL" feature, meant to be embedded in a possibly-exposed CI-status widget URL for one project) can be replayed with an arbitrary `stack_id` parameter to read the deploy/build status (`deploys_and_rollbacks.last`, lock state, last build label/status) of any other stack tracked by the same Shipit instance — including stacks the token holder was never authorized to see. This is a scope-escalation read of stack/deploy state across stack boundaries, matching the accepted "unauthorized/escalated read of stack state or deploy output" impact category.

### Likelihood Explanation
Exploitation only requires possession of any valid stack-scoped `ApiClient` token (such as a leaked CCMenu URL, which by design is meant to be embeddable in external dashboards/tools and therefore has a materially weaker secrecy expectation than a full API credential) and knowledge/enumeration of another stack's `to_param` (slug), which is not itself secret. No privileged access, GitHub credentials, or webhook secrets are required — only the read-only CCMenu token itself.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (as `StacksController` does: `stacks.from_param!(params[:stack_id])`) so the `ApiClient#stack_id` binding is enforced consistently across all API controllers, rather than only the permission bit.

### Proof of Concept
1. Use the "fetch CCMenu URL" feature on Stack A (`CCMenuUrlController#fetch`) to obtain a read-only `ApiClient` token whose `stack_id` is bound to Stack A.
2. Send `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` where `:stack_id` is replaced with Stack B's slug (a stack the token was never scoped to).
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (it is a valid `ApiClient`), `require_permission :read, :stack` passes (the token has `read:stack`), and `stack` resolves Stack B via the unscoped `Stack.from_param!` lookup at [4](#0-3) , returning Stack B's latest deploy/build status despite the token being scoped only to Stack A.
