### Title
Webhook signature verification is keyed on `repository.owner.login` while the synced repository is selected from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against based on `repository.owner.login` (falling back to `organization.login`), but the code that actually determines *which* `Repository`/`Stack` gets acted on uses a different field from the same payload: `repository.full_name`. In a multi-organization Shipit deployment, these two fields are not required to agree, and if the organization used to pick the secret has no `webhook_secret` configured, signature verification is skipped entirely, letting an attacker point `full_name` at a completely different, secret-protected organization's repository.

### Finding Description
Signature verification happens in `verify_signature`: [1](#0-0) [2](#0-1) 

The organization used to select `github_app` (and therefore the `webhook_secret` used for HMAC validation) is derived purely from the payload itself: [3](#0-2) 

`Shipit::GithubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as "always verified": [4](#0-3) 

Shipit explicitly supports multiple GitHub Apps/organizations, each with its own (optional) `webhook_secret`, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section, and the webhook secret is described as optional at App-creation time.

Once signature verification passes, `WebhooksController#create` dispatches the entire JSON payload to handlers, and the actual repository/stack acted upon is resolved from a *different* field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

The trust binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written to`. Because the controller derives the authenticating organization from `repository.owner.login`/`organization.login` while the handler layer derives the acted-upon repository from `repository.full_name`, these two are never cross-checked against each other, and both are attacker-controlled fields inside the same JSON body. If any organization configured in `Shipit.github` has a blank/unset `webhook_secret` (an explicitly supported, documented configuration), an unauthenticated attacker can submit a webhook where `repository.owner.login` names that unsecured organization (bypassing the signature check entirely per line 77 of `github_app.rb`) while `repository.full_name` names a repository belonging to a *different*, secret-protected organization. `PushHandler` will then look up and sync/deploy that unrelated stack.

### Impact Explanation
This breaks the equality "organization that authenticated the webhook == repository that is written/synced," letting an external, unauthenticated attacker trigger `GithubSyncJob`/`stack.sync_github` (and by extension deploy/rollback pipelines gated on branch HEAD state) for a stack belonging to an organization whose webhook secret they do not know, as long as any other configured organization lacks a webhook secret. This is a cross-repository/cross-organization forgery of GitHub events and can lead to unauthorized deploy triggers, satisfying the "cross-repository writes / unauthorized deploy" Critical impact bar.

### Likelihood Explanation
Requires: (a) the deployment to host multiple GitHub Apps/organizations (a supported and documented configuration), and (b) at least one of those organizations configured with no `webhook_secret` (also documented as "optional"). Given both conditions, exploitation requires no credentials, only the ability to send an unauthenticated POST to the public `/webhooks` endpoint with a crafted JSON body.

### Recommendation
- Bind the "organization used for signature verification" strictly to the resolved `Repository`'s owner (looked up in Shipit's own DB), not to attacker-controlled `repository.owner.login`/`organization.login` payload fields.
- Reject payloads where `repository.full_name`'s owner does not match the organization whose secret validated the signature.
- Do not allow `webhook_secret` to be optional/blank for any organization in production, or fail closed (reject) instead of `return true` when `webhook_secret` is unset.

### Proof of Concept
1. Deploy Shipit configured with two organizations per `docs/setup.md`'s multi-app example: `OrgA` (no `webhook_secret` set) and `OrgB` (has `webhook_secret` set, hosts a real deployable stack `OrgB/critical-app`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/critical-app"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` → `verify_webhook_signature` returns `true` immediately because `OrgA`'s `webhook_secret` is blank (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
4. `PushHandler#process` resolves the stack via `repository.full_name` = `OrgB/critical-app` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and invokes `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack, despite the attacker never possessing `OrgB`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
