### Title
Unauthenticated peer can crash a node via null-pointer/TypeError dereference in `handleOnlinePrivatePayment` when processing a malformed `private_payment` network message - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment()` is invoked directly on a `private_payment` message received from any network peer (or forwarded via hub) before the private-element structure is fully validated. It dereferences `arrPrivateElements[0].payload.denomination` immediately after checking only that `arrPrivateElements` is a non-empty array, with no check that `arrPrivateElements[0].payload` exists or is an object. This mirrors the Firebird `op_slice` bug class: an unprepared/unvalidated wire structure containing a possibly-null or missing nested field is passed straight into code that dereferences it, causing an unhandled exception that can crash the node process.

### Finding Description
`handleOnlinePrivatePayment` starts with: [1](#0-0) 

Only `ValidationUtils.isNonemptyArray(arrPrivateElements)` is checked before `arrPrivateElements[0].payload.denomination` is accessed on line 2382. If the attacker-supplied JSON for `arrPrivateElements[0]` omits `payload` (or sets it to `null`/a primitive), `arrPrivateElements[0].payload.denomination` throws a `TypeError: Cannot read properties of null/undefined (reading 'denomination')`.

This handler is reached by two code paths that accept peer-controlled data:
- Directly from the `private_payment` justsaying message handled in `network.js` (sent by any connected peer, unauthenticated).
- Via the hub-forwarded flow in `wallet.js`'s `handlePrivatePaymentChains`, which does perform some structural checks on `body.chains` elements (`isNonemptyObject(e.payload)`, etc.) at [2](#0-1)  before calling `network.handleOnlinePrivatePayment`. However, the direct peer-to-peer `private_payment` justsaying path (peer sends `arrPrivateElements` straight to `handleOnlinePrivatePayment`) does not perform this pre-check, so a directly connected peer can supply an `arrPrivateElements[0]` object lacking a `payload` field entirely, triggering the crash on the very first line that touches `.payload.denomination`.

By contrast, deeper validators such as `indivisible_asset.js`'s `validatePrivatePayment` and `private_payment.js`'s `validateAndSavePrivatePaymentChain` ( [3](#0-2) ) do check `headElement.payload` for existence before using it — but those checks occur *after* `handleOnlinePrivatePayment` has already dereferenced `.payload.denomination` unguarded.

### Impact Explanation
An uncaught `TypeError` thrown synchronously inside a network message handler is not caught by any `try/catch` in this call chain, so it propagates up as an unhandled exception. In a Node.js process without a top-level domain/handler for this specific call stack, this can crash the node process, matching the "network unable to confirm new units" / node crash impact criteria (analogous to the Firebird server crash via null-pointer dereference from an unauthenticated request). Any peer that opens a websocket connection to a full node can trigger this by sending a single crafted `private_payment` justsaying message.

### Likelihood Explanation
The trigger requires no authentication, no valid unit, and no prior state — just a malformed `private_payment` message sent by any connected peer. This makes the likelihood high: it is a trivial, repeatable, remotely triggerable crash from an "AA trigger sender"/"private-payment counterparty"-equivalent unprivileged actor, exactly the class of attacker the rules allow.

### Recommendation
Add strict structural validation of `arrPrivateElements[0]` at the very top of `handleOnlinePrivatePayment` (and ideally for every element in the chain) before accessing any nested fields: verify `arrPrivateElements[0]` is a non-empty object, `arrPrivateElements[0].payload` is a non-empty object, and `unit`/`message_index`/`output_index`/`denomination` fields have the expected types, mirroring the checks already performed in `wallet.js:959-972` and `private_payment.js:23-34`. Apply the same guard uniformly across all entry points that can receive raw `private_payment` data from peers.

### Proof of Concept
A peer connects to a full node's websocket interface and sends:
```json
["justsaying", {
  "subject": "private_payment",
  "body": [ { "unit": "SOME_BASE64_UNIT_HASH_OF_LENGTH_44" } ]
}]
```
i.e., an `arrPrivateElements` array whose single element has a `unit` field but no `payload` field. This satisfies `ValidationUtils.isNonemptyArray(arrPrivateElements)` and reaches line 2382 of `network.js`, `arrPrivateElements[0].payload.denomination`, throwing an unhandled `TypeError` because `payload` is `undefined`.
