### Title
`_has_redos_structure` heuristic evades bounded-quantifier ReDoS patterns, allowing a committed `security-patterns.yaml` regex to hang the PostToolUse hook - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_has_redos_structure` only detects catastrophic-backtracking shapes that are spelled with literal `*`/`+` characters (nested quantifiers, `(.*)*`, or textually-prefix-overlapping alternation). Because the check is purely syntactic and does not normalize `{m,}`/`{0,}` bounded-repetition syntax to its `+`/`*` equivalent, an attacker can write a functionally identical catastrophic-backtracking regex using `{n,}` counts that never matches `_REDOS_SHAPES` or `_ALT_UNDER_REP`, sail through `_validate_pattern`, and reach `re.search` in the PostToolUse pattern-check path unguarded by any execution timeout.

### Finding Description
`_load_user_patterns` (plugins/security-guidance/hooks/extensibility.py:147) reads `.claude/security-patterns.yaml` from the project directory (a normal, committed repo file — "Project (committed)" in the precedence list at lines 92-102) and passes each entry's `regex` field to `_validate_pattern` (line 199). The only gate against catastrophic backtracking is `_has_redos_structure` (line 272), called before `re.compile`: [1](#0-0) 

The detector's own docstring admits it is "Not a proof" and only "catches the common shapes." Concretely:
- `_REDOS_SHAPES` requires the nested quantifier to be written with a literal `+`/`*`/`?` character inside/after a `(...)` group.
- `_ALT_UNDER_REP` only flags alternation under a literal `[+*]` repetition suffix with a simple substring-prefix overlap test on a single, non-nested group.

Neither regex accounts for classic-ReDoS patterns expressed with counted/bounded repetition (`{m,}`, `{0,}`, `{1,50}` etc.), which are semantically equivalent to `+`/`*` for backtracking purposes. For example `(a{1,50}){1,50}` is exactly as catastrophic as `(a+)+` but contains no `+`, `*`, or alternation characters at all, so it passes `_has_redos_structure` cleanly and only fails if `re.compile` itself rejects it (it won't — it's syntactically valid).

That regex is then stored in the rule dict (line 228) and returned by `user_patterns()` (line 84). The per-question precondition states `check_patterns` runs `re.search(pattern['regex'], content)` for every pattern (built-in and user-supplied) on each Write/Edit tool call, with no per-regex timeout, process isolation, or length/complexity cap on the untrusted regex itself. `re.search` in CPython's `re` module has no built-in backtracking budget, so a matching (or near-matching, non-matching-at-the-end) input causes exponential-time evaluation, blocking the hook process.

### Impact Explanation
Once such a rule is loaded, every subsequent `Write`/`Edit` PostToolUse invocation in the session re-evaluates the malicious regex against the new file content via `check_patterns`. Ordinary content that contains a long run of the targeted character class followed by a non-matching terminator (e.g., a long string of `a`s, base64/hex blobs, repeated indentation, or any moderately long homogeneous run) is enough to trigger the exponential blowup — the attacker does not need to control the edited file's content, only the regex, because many normal editing operations will incidentally supply an adversarial-shaped string. This causes the hook to hang or time out on every future edit, effectively disabling all security-pattern reminders (and possibly the LLM review triggered from the same hook path) for the remainder of the session — a session-scoped denial-of-service against a security control, reachable purely from a committed repo file with no elevated privileges.

### Likelihood Explanation
Highly feasible and repeatable. The only precondition is the ability to commit `.claude/security-patterns.yaml` to the project (or land it via a PR that gets checked out), which is exactly the "unprivileged, ordinary repository content" scenario in scope. No YAML/JSON schema restricts regex complexity or length, `PATTERN_MAX_RULES` (50) does not bound single-pattern cost, and the bypass technique (using `{n,}` instead of `+`/`*`) is a single well-known, mechanical regex-writing choice — not a fragile fuzzing result.

### Recommendation
- Normalize quantifiers before applying `_has_redos_structure`: treat `{0,}`, `{1,}`, and any `{m,}`/`{m,n}` with `n - m` large as equivalent to `*`/`+` when checking `_REDOS_SHAPES`/`_ALT_UNDER_REP`, or reject any user regex containing nested repetition groups regardless of quantifier spelling.
- Do not rely solely on a static shape check; enforce a runtime bound on `re.search` for user-supplied regexes, e.g. run pattern matching in a subprocess/thread with a hard wall-clock timeout (or use the `regex` module's backtracking-limit support, or `re2`-style linear-time matching) and drop/disable a rule that exceeds it.
- Cap regex length/complexity (e.g. max nested groups, max quantifiers) for `security-patterns.yaml` entries in addition to the existing shape heuristic.

# Catastrophic backtracking: nested quantifiers, overlapping alternations
# under repetition, and wildcard groups under repetition. Static check, not a
# proof — catches the common shapes that hang the hook on every edit.
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")
