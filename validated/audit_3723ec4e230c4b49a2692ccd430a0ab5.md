**Analysis:**

The `VestingAdminStore` struct in `types/src/vesting.rs` is a passive deserialization type used only by client-side tooling (e.g., `crates/aptos/src/node/mod.rs` `get_stake_pools` and `crates/aptos/src/stake/mod.rs` `RequestCommission`) to read the on-chain `0x1::vesting::AdminStore` resource for display/convenience purposes. [1](#0-0) [2](#0-1) 

This resource content plays no role whatsoever in the actual fee-payer/sponsored-transaction admission path. Fee-payer eligibility in the real transaction admission stack is determined exclusively by cryptographic signature verification in `TransactionAuthenticator::verify` for the `FeePayer` variant, which requires a valid signature from the fee payer's private key over the raw transaction (or the zero-address variant) — not by any on-chain resource content. [3](#0-2) 

On the VM side, the `fee_payer_script_prologue`/`unified_prologue_fee_payer_v2` Move prologue functions independently verify that the fee payer's authentication key matches the one associated with the signed authenticator, again purely from signature/key material — never from `vesting_contracts` or any other arbitrary resource field. [4](#0-3) 

The premise of the question — an "off-chain signing service" that "trusts resource-derived address lists for eligibility" and treats a matching `vesting_contracts` entry as authorization to co-sign as fee payer — describes a hypothetical external system that does not exist anywhere in this codebase. There is no code path in mempool, vm-validator, or the AptosVM that reads `VestingAdminStore.vesting_contracts` (or any vesting-module resource) to determine fee-payer eligibility, construct a `FeePayer` authenticator, or bind a gas payer. Since the admission boundary itself never consumes this resource for that purpose, there is no broken invariant within the reviewed production admission code — the described exploit lives entirely outside the codebase's actual authentication/authorization logic.
