### Title
Cross-Function Reentrancy in `handleERC20Transfer` Enables Unauthorized `RequestValueTransfer` Emission via Missing `nonReentrant` Guard — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`handleERC20Transfer` in `BridgeTransferERC20.sol` lacks the `nonReentrant` modifier that its KLAY counterpart (`handleKLAYTransfer`) carries. It makes an external call to the token contract (`mint` or `safeTransfer`) after all handle-side state updates. Because `onERC20Received` and `requestERC20Transfer` also carry no reentrancy guard, and because `_requestERC20Transfer` increments `requestNonce` only after its own external calls, a malicious token with a transfer hook (ERC777-style `tokensReceived`) can reenter the bridge during the handle-side token delivery, emit a spurious `RequestValueTransfer` event with the current `requestNonce`, and cause the counterpart bridge to execute an unauthorized asset transfer.

---

### Finding Description

`BridgeTransferKLAY` explicitly inherits `ReentrancyGuard` and marks both `handleKLAYTransfer` and `_requestKLAYTransfer` with `nonReentrant`: [1](#0-0) [2](#0-1) 

`BridgeTransferERC20` inherits no `ReentrancyGuard` and `handleERC20Transfer` carries only `onlyOperators`: [3](#0-2) 

After completing all handle-side state updates (`_setHandledRequestTxHash`, `handleNoncesToBlockNums`, `_updateHandleNonce`) and emitting `HandleValueTransfer`, the function makes an external call to the token contract as its final step: [4](#0-3) 

`onERC20Received` and `requestERC20Transfer` carry no reentrancy guard either: [5](#0-4) 

Inside `_requestERC20Transfer`, `requestNonce++` is the last statement, placed after external calls to `_payERC20FeeAndRefundChange` and `ERC20Burnable.burn`: [6](#0-5) 

`_payERC20FeeAndRefundChange` itself issues `safeTransfer` calls to `feeReceiver` and `from`: [7](#0-6) 

The comment in `BridgeFee.sol` explicitly acknowledges that callers of `_payKLAYFeeAndRefundChange` must be `nonReentrant`, but no equivalent protection is applied to the ERC20 path: [8](#0-7) 

---

### Impact Explanation

During `handleERC20Transfer`'s external call to `mint(_to, _value)` or `safeTransfer(_to, _value)`, a token contract implementing ERC777-style `tokensReceived` hooks (backward-compatible with the `IERC20` interface the bridge accepts) can invoke `bridge.onERC20Received(...)` or `bridge.requestERC20Transfer(...)` on the same bridge. Because neither function has a reentrancy guard, `_requestERC20Transfer` executes fully: it emits `RequestValueTransfer` with the current `requestNonce` and then increments it. The counterpart bridge's off-chain relayer observes this event and calls the corresponding `handleERC20Transfer` (or `handleKLAYTransfer`) on the source chain, transferring assets to the attacker-controlled address without any legitimate source-chain deposit. This constitutes an **unauthorized mint/transfer of bridged assets**.

---

### Likelihood Explanation

The trigger requires a registered ERC20 token that fires a callback during `mint` or `transfer` (e.g., ERC777, or any custom token with a `tokensReceived`/`afterTokenTransfer` hook). Such tokens are explicitly supported by the bridge's `onERC20Received` 1-step deposit path. The attacker only needs to:
1. Make a legitimate bridge request with their malicious contract as `_to`.
2. Wait for an operator to call `handleERC20Transfer`.
3. Have the token's hook call `onERC20Received` during delivery.

No privileged role is required beyond the attacker controlling `_to` on the destination chain, which is determined by their own source-chain request.

---

### Recommendation

1. Add `ReentrancyGuard` inheritance to `BridgeTransferERC20` and `BridgeTransferERC721`, mirroring `BridgeTransferKLAY`.
2. Apply `nonReentrant` to `handleERC20Transfer`, `handleERC721Transfer`, `requestERC20Transfer`, `onERC20Received`, `requestERC721Transfer`, and `onERC721Received`.
3. Move `requestNonce++` to before any external call in `_requestERC20Transfer` and `_requestERC721Transfer`, following the Checks-Effects-Interactions pattern already partially applied in the handle path.

---

### Proof of Concept

```
Attacker deploys MaliciousToken T (ERC777-compatible, registered in bridge).
T.mint() calls tokensReceived(recipient) on recipient.

Step 1: Attacker calls requestERC20Transfer(T, attackerContract, value, 0, data)
        on source bridge → RequestValueTransfer(nonce=N) emitted.

Step 2: Operator calls handleERC20Transfer(txHash, from, attackerContract, T,
        value, N, blockNum, data) on destination bridge.
        → _setHandledRequestTxHash, handleNoncesToBlockNums[N], _updateHandleNonce(N)
        → emit HandleValueTransfer(...)
        → ERC20Mintable(T).mint(attackerContract, value)   ← external call, no nonReentrant

Step 3: T.mint() triggers tokensReceived on attackerContract.
        attackerContract calls bridge.onERC20Received(attackerAddr, victimAddr,
        value2, 0, data2).
        msg.sender = T (registered token) → onlyRegisteredToken passes.
        _requestERC20Transfer executes:
          → _payERC20FeeAndRefundChange (no fee → no-op)
          → emit RequestValueTransfer(ERC20, attackerAddr, victimAddr, T,
                                      value2, requestNonce=M, 0, data2)
          → requestNonce++ (M → M+1)

Step 4: Relayer observes RequestValueTransfer(nonce=M) on destination chain.
        Calls handleERC20Transfer(..., victimAddr, T, value2, M, ...) on source bridge.
        Source bridge transfers value2 tokens of T to victimAddr (attacker-controlled).

Result: Attacker receives value2 tokens on source chain with no corresponding deposit.
        requestNonce on destination bridge is now M+1 (consumed by spurious request).

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
