### Title
Signature Replay Across AAs and Over Time via `is_valid_signed_package`/`signed_message` Primitive Lacking Built-in Domain/Expiration Binding - (File: `signed_message.js`, `object_hash.js`, `formula/evaluation.js`)

### Summary
The oscript primitives `is_valid_signed_package` (evaluated in `formula/evaluation.js`) and the underlying `signed_message.validateSignedMessage` (`signed_message.js`) let an AA verify an externally signed message from a user. The hash that is actually signed, produced by `objectHash.getSignedPackageHashToSign`, only commits to the `signed_message` payload, `authors`, `last_ball_unit` and `version` — it never binds the signature to the specific AA (`this_address`) that is meant to consume it, nor does it enforce any expiration. Any domain separation or expiry must be manually embedded by the AA author inside the free-form `signed_message` object. If an AA author omits this (a very plausible oversight, exactly the class of bug flagged in the external report for Primex), a signature produced for one context can be replayed against a different AA or reused indefinitely by any unprivileged trigger sender.

### Finding Description
`getSignedPackageHashToSign` computes the hash to sign strictly from the `signed_message`/`authors`/`last_ball_unit`/`version` fields of the package, with authentifiers stripped out: [1](#0-0) 

`validateSignedMessage` in `signed_message.js` only checks that the authentifiers verify against this hash and, optionally, that `last_ball_unit` is a stable known unit; it performs no check that the message is bound to a particular target address (e.g., `this_address` of the AA validating it) and no expiration/timestamp enforcement: [2](#0-1) [3](#0-2) 

The oscript `is_valid_signed_package` operator in `evaluation.js` simply calls `validateSignedMessage` for a caller-supplied address and, if `last_ball_unit` is provided, only verifies it corresponds to a stable unit — again with no default expiration or per-AA binding: [4](#0-3) 

Because the signature is over arbitrary free-form JSON, the only way to prevent replay across AAs or over time is for the AA author to manually embed a domain-separating value (such as `this_address`) and an expiration/nonce inside `signed_message` and check them in oscript — exactly the mitigation pattern demonstrated ad hoc in the sample payment-channel contract, which manually checks `signed_message.channel != this_address` and a period counter: [5](#0-4) 

This confirms the primitive itself provides no built-in protection — it is entirely opt-in and easy to omit, mirroring the exact root cause described in the external report (EIP-712-style domain separation and expiration are absent from the base signing mechanism, and must be added ad hoc by each consumer).

### Impact Explanation
Any AA that uses `is_valid_signed_package`/`is_valid_sig` to authorize a privileged, fund-affecting action (e.g., an off-chain-approved withdrawal, price attestation, permission grant, "channel close" cooperative message, oracle-style attestation) but fails to embed `this_address` and an expiration/nonce inside the signed payload is vulnerable to:
- Cross-AA replay: the exact same signed package (and signature) can be submitted as trigger data to a different AA instance sharing the same signer/schema, causing that AA to treat it as valid authorization it was never intended to receive.
- Unbounded temporal replay: since there is no expiration enforcement in the base primitive, a once-valid signed authorization remains usable forever, enabling repeated invocation of the same one-time authorization (e.g., repeated withdrawal or repeated favorable state transition), leading to unauthorized spending or fund loss from AA balances.

This matches the "Accept only concrete unauthorized spending... AA fund loss" bar, reachable purely by any unprivileged party crafting and posting a trigger unit containing a previously observed `signed_package`.

### Likelihood Explanation
Exploitability depends on an AA author's oscript failing to add the manual `this_address`/expiration checks that the platform does not provide by default. This is a design footgun rather than a guaranteed-exploitable bug in every AA, similar to how the Primex report rated the underlying issue only "medium" because it depends on how consuming code uses the signature. Given `is_valid_signed_package`/`is_valid_sig` are general-purpose primitives intended for third-party AA authors (as shown by the documented example needing to hand-roll the anti-replay checks), and the base API gives no compile-time or runtime warning about missing domain/expiration binding, it is reasonably likely that some deployed AAs omit one or both checks.

### Recommendation
- Consider extending `getSignedPackageHashToSign` (or adding a distinct oscript operator) to optionally bind the signed message to a specific `this_address`/AA and to a validity window (e.g., an explicit `expiry_mci`/`expiry_ts` field checked automatically in `validateSignedMessage`), analogous to EIP-712's domain separator and an expiration parameter.
- At minimum, update `is_valid_signed_package` documentation/guidance to explicitly require AA authors to include `this_address` and an expiration or one-time nonce inside `signed_message`, and consider adding a lint/validation warning when neither is present in the fields being checked by the AA's oscript.

### Proof of Concept
1. AA `X` is written to accept a `trigger.data.signed_package` where `signed_message = {action: "withdraw", amount: 100}` signed by a trusted off-chain approver, checked via `is_valid_signed_package(trigger.data.signed_package, approver_address)`, without the AA embedding `this_address` or any expiration inside `signed_message`.
2. The approver signs this message once, intending it to authorize a single withdrawal from AA `X`.
3. Because `getSignedPackageHashToSign` only hashes `signed_message`/`authors`/`last_ball_unit`/`version` (`object_hash.js:97-103`) and `validateSignedMessage` performs no target-address or expiration check (`signed_message.js:117-137`, `255-303`), any user can resubmit the identical `signed_package` as `trigger.data` in a new trigger unit to AA `X` repeatedly, or to a second, structurally similar AA `Y` deployed from the same base code that also checks `is_valid_signed_package(..., approver_address)`.
4. `is_valid_signed_package` in `formula/evaluation.js:1653-1702` returns `true` again each time, causing AA `X` (and/or `Y`) to execute the withdrawal logic repeatedly/unintentionally, draining AA funds beyond what the approver authorized.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
