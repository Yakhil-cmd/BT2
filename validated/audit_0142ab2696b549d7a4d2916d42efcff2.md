### Title
Double-truncating integer division in `min-ustx-for-sats-amount` lets a bond staker zero out the STX collateral floor for a large sBTC bond position - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` gates the amount of STX a bond member must lock relative to the sBTC they custody using `min-ustx-for-sats-amount`, which performs two sequential integer (floor) divisions [4](#0-3) . Because the intermediate `(* stx-value-ratio sats-amount) / 100` term truncates to zero whenever `stx-value-ratio * sats-amount < 100`, the whole floor collapses to `0`, exactly mirroring the referenced report's root cause: a protective quantity computed as a fraction of an attacker-chosen value can be driven to zero by choosing that value near a rounding boundary, decoupling the "fee"/floor from the actual value it is meant to secure.

### Finding Description
`register-for-bond` requires `amount-ustx >= (min-ustx-for-sats-amount sats-total stx-value-ratio min-ustx-ratio)` before accepting a staker into a bond [5](#0-4) . The helper computes this floor as:
```
(/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
``` [4](#0-3) 
Clarity `/` on `uint` is integer (floor) division. The inner term `(* stx-value-ratio sats-amount) / 100` is computed and truncated to an integer *before* being multiplied by `min-ustx-ratio` and divided by `10000`. If `stx-value-ratio * sats-amount < 100`, this inner term truncates to `0` regardless of `min-ustx-ratio`, so the final floor is `0` no matter how the bond admin configured `min-ustx-ratio`. The accepted `amount-ustx` then only needs to satisfy the node-level nonzero-lock invariant in `pox_lock_v5`/`pox_rollover_v5` (which only requires `> 0`, not any minimum tied to `sats-total`) [6](#0-5) . Once accepted, the bond membership records the (possibly minimal) `amount-ustx` and the full `sats-total` [7](#0-6) , and `amount-ustx` is what is added to `signer-delegated-per-cycle` via `add-staker-to-signer-cycles`, which is precisely the input to `pox_5_make_signer_set`'s stake-weighted reward-slot apportionment [2](#0-1) .

### Impact Explanation
The `min-ustx-ratio` floor exists to enforce that a signer's STX-denominated weight (used for reward-slot apportionment and the security budget backing block-signing) remains proportionate to the sBTC/bond exposure it is fronting. Because the floor can be driven to `0` by choosing `sats-amount` such that `stx-value-ratio * sats-amount < 100` (a boundary that depends only on the admin-chosen `stx-value-ratio`, not on `min-ustx-ratio`), a staker can register a bond position whose intended collateralization ratio is bypassed entirely. This falls into "signing weight or reward slots exceeding locked value" — the equality the contract is meant to enforce (STX collateral commensurate with the bond's `sats`) is broken because the floor no longer reflects `min-ustx-ratio` at all for such inputs.

### Likelihood Explanation
Exploitability is bounded: because the truncation-to-zero window is `stx-value-ratio * sats-amount < 100`, it is only reachable for `sats-amount` values that are small in absolute terms relative to `stx-value-ratio` (analogous to the "zero/near-zero strike" case in the source report, where the manipulable quantity itself has to be economically small to trigger the bypass). Whether this is exploitable for material value depends entirely on the `stx-value-ratio`/`min-ustx-ratio` values the bond admin (a privileged party, out of scope per the rules) chooses for a given bond, and the sBTC decimal scale (sats) actually being staked. I could not fully verify from the available code whether any admin-set/realistic `stx-value-ratio` combined with an otherwise-meaningful `sats-amount` produces this bypass for economically significant amounts, or whether it only manifests for dust-level `sats-amount` (in which case, like the cited report's own conclusion for zero-strike options, the practical impact is low since the bypassed collateral would also be near-zero in value).

### Recommendation
Perform the multiplication before any division in `min-ustx-for-sats-amount` (e.g. `(/ (* stx-value-ratio sats-amount min-ustx-ratio) (* 100 10000))`) so that only a single, final truncation occurs, eliminating the compounding/zeroing effect of the intermediate division. Additionally, consider enforcing an absolute minimum `amount-ustx` for any bond membership independent of the ratio-derived floor, so that the STX floor cannot collapse to a value near/at the network's minimum lock amount regardless of the chosen `sats-amount`.

### Proof of Concept
1. Bond admin calls `setup-bond` with some `stx-value-ratio` (e.g. `50`) and `min-ustx-ratio` (e.g. `10000`, i.e. 100%), allow-listing an attacker for up to `N` sats [8](#0-7) .
2. Attacker calls `register-for-bond` with `sats-total = 1` (or any value with `stx-value-ratio * sats-total < 100`, e.g. `sats-total < 2` for `stx-value-ratio = 50`).
3. `min-ustx-for-sats-amount(1, 50, 10000)` evaluates `(50*1)/100 = 0`, then `(0*10000)/10000 = 0`, so the required `amount-ustx` floor is `0`, even though `min-ustx-ratio` was configured at 100%.
4. Attacker supplies `amount-ustx = 1` (minimal nonzero value to satisfy `pox_lock_v5`'s `> 0` check) and passes the `ERR_INSUFFICIENT_STX` assertion at line 713-719 despite the admin intending a 1:1 STX:sats floor [5](#0-4) .
5. The registration succeeds, recording `amount-sats = 1` and `amount-ustx = 1`, and `amount-ustx` (not the intended collateral) is what is added into the signer's per-cycle delegated total used for reward-slot weight [1](#0-0) .

Given the bounded/small-value nature of the exploitable window (mirroring the source report's own caveat that "zero strike" abuse only matters when the manipulated quantity is itself economically negligible), I flag this with lower confidence that it clears the "material value" bar required for a High/Critical finding, but it is a genuine equality-breaking rounding defect matching the requested bug class.
