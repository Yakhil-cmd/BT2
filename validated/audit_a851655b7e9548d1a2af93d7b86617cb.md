## Title
Race condition allows concurrent processing of the same private-payment chain, bypassing the duplicate-detection check and enabling private-output double-spend / crash - (File: `network.js`, `private_payment.js`)

### Summary
The Narayana advisory describes a race where a second `Join` request is processed on the same LRA identifier while the effects of a prior `Cancel` are still in flight (a multi-second asynchronous window), because the two operations on the same resource are not mutually exclusive. In `ocore`, the analogous pattern exists in the private-payment handling path: the mutex/in-work guard that used to serialize processing of the *same* incoming private-payment unit was removed (left commented out), and the downstream duplicate check in `private_payment.js` races against its own asynchronous write, allowing two concurrent submissions of the same private-payment chain to both pass validation.

The same removed guard exists in `handleSavedPrivatePayments`, which processes queued unhandled private payments "in parallel" (`async.each`) with no per-unit exclusivity: [2](#0-1) 

Once inside, `private_payment.js#validateAndSavePrivatePaymentChain` opens its own DB connection, begins a transaction, and only *then* performs a duplicate check by `SELECT`ing the `outputs` row for `(unit, asset, message_index[, output_index])` before deciding whether to write: [3](#0-2) 

Because the actual `INSERT`/`UPDATE` of the `outputs` row happens several asynchronous steps later — after `parsePrivatePaymentChain` walks the whole chain and calls `validatePrivatePayment` for every element, which itself does further async spend-proof and inclusion checks (`indivisible_asset.js` `validatePrivatePayment`, lines 20-182) — there is a multi-step asynchronous window, analogous to the ~2 second gap in the LRA bug, during which a second identical (or conflicting) submission of the same private-payment chain can enter the same code path. Since Node.js callbacks interleave at each async I/O boundary, two concurrent invocations for the same `(unit, message_index, output_index)` can both execute the "check if duplicate" `SELECT` before either one's `UPDATE ... SET is_serial=?, is_spent=?, address=?, blinding=? WHERE ... AND is_spent=0` in `indivisible_asset.js#validateAndSavePrivatePaymentChain` (lines 239-297) commits, so both see `rows.length === 0` (or a still-hidden output) and both proceed to write.

This is reachable purely by any private-payment counterparty (or a paired device / hub relaying such messages) sending the same private-payment chain (or two chains that both try to reveal/spend the same otherwise-hidden output) twice in quick succession, exactly mirroring the "duplicate protocol message sent within the race window" pattern of the reported CVE.

### Impact Explanation
Two interleaved writers touching the same `outputs.unit/message_index/output_index` row can: (1) both pass the "is this a duplicate?" check and independently attempt to reveal/spend the private output, risking data corruption or an unhandled exception when they both try to satisfy `WHERE ... AND is_spent=0` (the second `UPDATE` may silently no-op if the first already flips `is_spent`, or produce inconsistent state such as a private output ending up attributed to two different addresses/blindings depending on write ordering) — undermining spend uniqueness guarantees for private assets, which is exactly the invariant `is_unique`/`is_spent` is meant to protect against double-spend. In the worst case this can crash the node process (the code contains a `throw Error("more than one output ...")` a few lines above, and other paths in this file `throw` on unexpected states), which matches the "application may crash or hang indefinitely" impact of the referenced CVE, causing denial of service for a full/light wallet node processing private payments.

### Likelihood Explanation
The guard against concurrent processing of the same unit was explicitly disabled (visible as commented-out code), and no other mutex protects the specific `(unit, message_index, output_index)` tuple across the async gap between the duplicate check and the eventual write, so the race is directly triggerable by any counterparty capable of sending (or replaying/relaying) the same private-payment JSON twice, which requires no special privilege.

### Recommendation
Restore per-unit (or better, per `(unit, message_index, output_index)`) serialization for `handleOnlinePrivatePayment` / `handleSavedPrivatePayments`, e.g. re-enable an `assocUnitsInWork`-style guard or use `mutex.lock` keyed by `unit+message_index+output_index` around the entire validate-and-save path in `private_payment.js`, so that a second identical submission is queued or rejected instead of racing the first one's write.

### Proof of Concept
1. As a counterparty/paired device, send the same `private_payment` chain (same `unit`, `message_index`, `output_index`, `payload`) to the victim node twice in rapid succession (e.g., two WebSocket `justsaying` messages a few milliseconds apart, or once directly and once via `handleSavedPrivatePayments`'s reprocessing of `unhandled_private_payments`).
2. Both calls reach `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`, each opening its own DB connection/transaction.
3. Both run the "check if duplicate" `SELECT` in `private_payment.js` before either has committed its `UPDATE` to `outputs`, so both see no existing revealed output and proceed to `indivisible_asset.js`/`divisible_asset.js` `validateAndSavePrivatePaymentChain`, racing to write conflicting `is_spent`/`address`/`blinding` values or triggering the `throw Error("more than one output ...")` guard, crashing the node.
