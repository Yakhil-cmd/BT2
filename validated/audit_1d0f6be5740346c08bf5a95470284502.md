### Title
`recapitalize` refunds tokens that were never deposited, draining pool custody - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The kernel bug is a release-without-acquire on the error path: `imsttfb` probe cleans up resources even when the corresponding acquisition (`init_imstt` / `ioremap` of `cmap_regs`) failed or never completed. The analog in XOXNO Lending is `recapitalize`: the pool unconditionally refunds `payer` for the portion of `amount` it does not credit, without verifying that any funds were actually received — releasing custody (a refund) against an acquisition (a prefunding transfer) that never happened.

### Finding Description
`pool_recapitalize_call` is documented as "Applies prefunded cash up to the backing shortfall and refunds excess to `payer` … does not pull funds from `payer`" [1](#0-0) . Because the pool never pulls the funds, the refund leg is only sound if the controller first performed a measured transfer into the pool and passed the *received* amount as `amount`. The pool itself, however, exposes `recapitalize(hub_asset, payer, amount)` directly and computes the refund as `amount − credited` unconditionally. A caller who invokes the pool's `recapitalize` with `amount` equal to the pool's entire token balance and without sending anything receives the full `amount` as an "excess refund".

The committed regression test proves the exact leak shape — the resource (token custody) is released on a path where the matching acquisition (the payer's transfer) never occurred:

- `t.client().recapitalize(&hub(&t.asset), &payer, &custody)` with no transfer drains `token.balance(&t.pool)` to 0 while `cash` still reports `>= deposit` [2](#0-1) .
- Afterward a legitimate supplier's `withdraw` passes `Cache::require_reserves` (the cash book says solvent) and fails inside the SAC transfer with `BalanceError = 10` [3](#0-2) .

### Impact Explanation
Theft of user funds followed by permanent freezing of remaining funds. The unfunded refund pays `payer` real tokens out of supplier custody; the `cash` accounting book is not reduced for the "refund", so the market reports solvency it does not have. Subsequent withdrawals clear the pool's own liquidity guards and revert inside the token transfer — a fail-open accounting state where remaining suppliers can never exit [4](#0-3) .

### Likelihood Explanation
Reachability hinges on whether the pool's `recapitalize` is auth-gated to the controller. The pool's own test client invokes it directly with an arbitrary `payer` and no prefunding, indicating no such gate on the pool endpoint [5](#0-4) . If the deployed pool restricts the endpoint to the controller (the controller recapitalize path does `transfer_amount_measured` before the call [6](#0-5) ), the same defect is still exploitable whenever the measured receipt is smaller than the credited basis — e.g., a fee-on-transfer or re-entrant token where `received < amount` still triggers a refund computed against the un-measured figure. I was unable to verify the pool's authorization check on `recapitalize` within the available iterations, which is the deciding factor between Medium and High.

### Recommendation
In `contracts/pool/src/ops/recapitalize.rs`, compute the refundable excess only against funds actually received in the same transaction (balance-delta measurement or an explicit credited amount passed by the controller), never against the caller-declared `amount`; and/or restrict `recapitalize` to the controller address so the refund basis is always the measured prefund. Additionally decrement `cash` for any refund paid so the book cannot overstate custody.

### Proof of Concept
```rust
// contracts/pool/tests/flows.rs — already-committed reproduction
let custody = token.balance(&t.pool);
// No token transfer occurs; payer is refunded "excess" anyway.
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);            // custody gone
assert!(t.state_snapshot().cash >= deposit);      // book still claims funds
// Supplier withdraw now passes liquidity guards and fails in the SAC transfer.
```
