Confirmed: `revert()` at [1](#0-0) , triggered from `handleSecondaryTriggers` when any of the secondary AAs invoked from a primary AA's output addresses bounces, causes a full `ROLLBACK TO SAVEPOINT initial_balances` that undoes every balance change, response, and payment output made by the primary AA — including any legitimate outputs already sent to other payees in the same response unit.

### Title
Malicious secondary-AA recipient can block payments to all other payees of a multi-output AA response - (File: aa_composer.js)

### Summary
An AA that distributes funds to multiple destination addresses in one response (e.g. a withdrawal/distribution AA analogous to `approveWithdraw` sending to several payees) is vulnerable to a single malicious recipient blocking payment to *everyone* in that batch, if any of the destination addresses is itself an AA. This mirrors the reported Solidity issue where a single reverting payee in a `send()` loop causes the whole transaction — and all other payees' funds — to fail.

### Finding Description
When a primary AA's response unit pays multiple output addresses and one of those addresses is another AA, `handleSecondaryTriggers` fires a secondary trigger for that AA [2](#0-1) . If that secondary AA's own logic decides to `bounce` (the AA analog of "throwing"), its `child_trigger_opts.onDone` callback passes a `bounce_message` error back to the `async.eachSeries` completion handler [3](#0-2) . For a primary trigger, this error is *not* just ignored for that one payee — it triggers `revert(err)` on the entire primary AA invocation [4](#0-3) .

`revert()` performs a full rollback of the primary trigger's effects: it removes all recorded AA responses, clears state-variable caches, calls `batch.clear()`, and issues `ROLLBACK TO SAVEPOINT initial_balances` on the DB connection, then calls `bounce(err)` [5](#0-4) . This undoes *every* output, balance update, and state change made by the primary AA in that invocation — not just the failed leg to the malicious AA — before the primary AA itself bounces and (if funds allow) returns the trigger amount to the original sender.

Consequently, if a distribution/withdrawal-style AA sends outputs to N addresses and any one of them is a secondary AA controlled by an attacker that always bounces (e.g., it always contains `bounce('deny')` in its `init`/`state` code), that single malicious address can unconditionally cause the whole distribution to fail every time it's attempted — denying funds to all the other, honest payees in the same batch, exactly as described in the reported `send()`-based push-payment issue.

### Impact Explanation
This is a fund-freezing / denial-of-service vulnerability reachable by any unprivileged party who can get their own AA address included as one of the destinations in a multi-payee AA (e.g., a shared/distribution AA, a DAO-like payout AA, or any AA whose payee list is influenced by user input such as `trigger.data`). By deploying a "poison" AA that always bounces and arranging to be one of the recipients, the attacker can permanently block legitimate payees from receiving their share whenever the distribution AA is invoked, causing AA fund loss/freezing and node-visible failed responses for all parties, not just the attacker.

### Likelihood Explanation
Likelihood is high for any AA design pattern that: (1) pays multiple addresses in a single response unit, and (2) allows those addresses to be influenced by an external/untrusted party (e.g., a payee list supplied via `trigger.data`, a shared multi-party settlement AA, or a marketplace/distribution AA). No special privilege is needed — deploying an AA and getting listed as one recipient is sufficient. This matches common AA patterns for withdrawal/distribution logic (see `test/samples/payment_channels.oscript` multi-output payment pattern [6](#0-5) ) and the chain-of-AAs mechanics already exercised in `test/aa_composer.test.js` [7](#0-6) .

### Recommendation
- Do not let a secondary AA's bounce cascade into a full rollback of the primary trigger's unrelated payments. Consider isolating each secondary-trigger invocation so a bounce by one recipient AA only affects funds sent to that recipient (e.g., treat it like a failed/returned payment rather than reverting the whole batch), analogous to favoring "pull payments" over "push payments" in the original report.
- Alternatively, document and strongly discourage AA payout patterns that pay multiple addresses—especially externally influenced ones—in a single response, recommending a pull-based claim pattern (recipients trigger their own AA to claim/withdraw their share) instead of push-based multi-output distribution.
- If push-based multi-output distribution must be supported, evaluate sending each payee's funds via independent response units/triggers so that one payee's AA logic bouncing cannot roll back payments already computed for others.

### Proof of Concept
1. Deploy AA `Poison` whose `init` unconditionally executes `bounce('deny')`.
2. Deploy AA `Distributor` whose messages pay out to a list of addresses including one legitimate payee `X` and `Poison`'s address, e.g.:
   ```
   messages: [{
     app: 'payment',
     payload: { asset: 'base', outputs: [
       { address: '{X}', amount: 1000 },
       { address: '{Poison_address}', amount: 1000 }
     ]}
   }]
   ```
3. Trigger `Distributor`. `handleTrigger` builds the response unit, then `handleSecondaryTriggers` fires a secondary trigger into `Poison` [2](#0-1) .
4. `Poison` bounces; `handleSecondaryTriggers`'s `async.eachSeries` completion callback receives the error and, because this is the primary trigger, calls `revert(...)` [1](#0-0) .
5. `revert()` rolls back the entire `Distributor` invocation via `ROLLBACK TO SAVEPOINT initial_balances`, meaning payee `X` never receives the 1000 bytes that were already computed for them, and `Distributor` itself bounces [5](#0-4) .
6. Every subsequent trigger of `Distributor` that includes `Poison` as an output address repeats this failure, permanently denying `X` (and any other payees) their funds as long as `Poison` remains a target address.
