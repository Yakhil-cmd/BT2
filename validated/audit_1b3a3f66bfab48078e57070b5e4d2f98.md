I found a genuine local analog: `SignerCapabilityOfferProofChallengeV2` lacks `chain_id` domain-binding, unlike its sibling `RotationCapabilityOfferProofChallengeV2`.

### Title
`offer_signer_capability` signed proof-challenge omits `chain_id`, enabling cross-network replay of capability delegation - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`offer_signer_capability` verifies a message signed by the account owner over `SignerCapabilityOfferProofChallengeV2`, which contains only `sequence_number`, `source_address`, and `recipient_address` [1](#0-0) . In contrast, the closely related `RotationCapabilityOfferProofChallengeV2` explicitly adds a `chain_id` field "which prevents replaying the challenge message" [2](#0-1) . The signer-capability variant has no such binding.

### Finding Description
`offer_signer_capability` constructs the challenge purely from the sequence number and two addresses, then verifies the owner's signature over it and stores the recipient as authorized to obtain a signer for the account via `create_authorized_signer`: [3](#0-2) 

Compare this to `offer_rotation_capability`, which explicitly includes `chain_id: chain_id::get()` in its proof challenge to domain-separate signatures across networks: [4](#0-3) 

Because the signer-capability proof omits `chain_id`, a signature produced by an account owner authorizing a `recipient_address` to obtain their signer capability on one Aptos chain (e.g., devnet, testnet, or a fork/L2 sharing the same address derivation) is valid BCS-identical input on any other chain where the same account address and sequence number exist. This mirrors the external NodeRegistry bug class: the signed payload does not bind to the specific "registry"/chain instance, so it can be resubmitted elsewhere without the signer's consent for that instance.

### Impact Explanation
If replayed on another chain/network where the signer's account exists at the same address with the same sequence number (a realistic scenario for pre-funded genesis/faucet accounts, devnet/testnet resets, or private forks that mirror mainnet state), an attacker who intercepts or otherwise obtains this signed proof (e.g. from a public mempool/API on the origin chain) could submit `offer_signer_capability` on the target chain to grant themselves (as `recipient_address`) the account's signer capability there, subsequently calling `create_authorized_signer` to fully impersonate the account on the second chain. This is an authenticator/approval-binding failure at the admission boundary: the signed material does not bind the intended execution domain, allowing wrong-signer-set acceptance.

### Likelihood Explanation
Exploitation requires: (1) two Aptos chains/networks sharing account address derivation and matching sequence numbers for the target account (common for testnets/devnets that are periodically reset from a snapshot, or private forks/replicas), and (2) the attacker being the `recipient_address` party or colluding with them since `recipient_address` is fixed in the signed message (so the attacker cannot arbitrarily redirect capability to themselves without being the originally-designated recipient). This constrains real-world exploitability to scenarios where the same owner signs delegation intending it for one specific chain instance but it also is valid on another — a genuine but narrower "cross-chain confusion" bug rather than a fully unrestricted replay.

### Recommendation
Add a `chain_id` (and consider a module/struct identifier already present via BCS type discrimination) field to `SignerCapabilityOfferProofChallengeV2`, mirroring `RotationCapabilityOfferProofChallengeV2`, and update `offer_signer_capability` to populate it from `chain_id::get()`. This requires a struct/version bump and corresponding CLI/SDK signing helper updates.

### Proof of Concept
1. On Chain A (chain_id = 4), Alice signs a `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: alice_addr, recipient_address: bob_addr }` and submits `offer_signer_capability` intending to delegate only for Chain A.
2. If Chain B (chain_id = 1, e.g., a periodically-reset devnet or private fork) has an account at `alice_addr` with `sequence_number == 0` (plausible after a network reset restoring genesis state), Bob (or anyone possessing the signature) submits the identical `signer_capability_sig_bytes`/`account_public_key_bytes`/`recipient_address` to Chain B's `offer_signer_capability`.
3. Verification succeeds because the challenge struct contains no chain-binding field, granting Bob signer capability over Alice's account on Chain B without her consent for that chain.

**Caveat:** I could not find evidence within this repository of an unprivileged, fully self-contained same-chain exploitation path (the `recipient_address` is fixed in the signed data, so an attacker cannot redirect capability to an arbitrary address of their choosing on the *same* chain). The impact is scoped to cross-network/cross-fork replay, which is a real domain-binding gap analogous to the external report, but is narrower than a universal replay bug.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
