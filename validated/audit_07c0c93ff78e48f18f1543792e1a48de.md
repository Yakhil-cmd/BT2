## Title
Unchecked property access on previous private-payment chain element causes crash - (`indivisible_asset.js`)

### Summary
CVE-2025-55780 describes a null-pointer dereference in MuPDF's `break_word_for_overflow_wrap()`, which calls `fz_html_split_flow()` to split a linked-list node and then dereferences `node->next->overflow_wrap` without checking that `node->next` is non-null. The root cause pattern — consuming an adjacent/previously-linked structure element and dereferencing a nested field without validating that the field (or the whole structure) exists — has a direct analog in ocore's private-payment chain validation, where a chain element supplied by a counterparty is dereferenced before its own structural validity has been checked.

### Finding Description
In `indivisible_asset.js`, `parsePrivatePaymentChain()` iterates the private-element chain `arrPrivateElements` sequentially with `async.forEachOfSeries`. For every element `i` it grabs the *next* array element as `prevElement` (the private payment chain is stored in reverse order) and passes it straight into `validatePrivatePayment()`: [1](#0-0) 

Inside `validatePrivatePayment()`, `validateSpendProof()` dereferences `objPrevPrivateElement.output.address` guarded only by a truthiness check on `objPrevPrivateElement` itself — not on its nested `.output` field: [2](#0-1) 

The structural check that an element actually has an `.output` field (`if (!objPrivateElement.output) return cb("no output in private element");`) is only performed on the *current* element being iterated, at line 203, not on the *next* element that is passed in as `prevElement`/`objPrevPrivateElement`: [3](#0-2) 

Because `async.forEachOfSeries` processes elements strictly in order, when element `i` is processed, element `i+1`'s own `.output` field has not yet been validated (that validation only happens when the loop reaches index `i+1`). If a malicious private-payment counterparty crafts a chain where an element used as `prevElement` is missing its `output` object (e.g. `{unit, payload}` with no `output` key), `objPrevPrivateElement.output.address` throws an uncaught `TypeError: Cannot read properties of undefined (reading 'address')` — precisely analogous to MuPDF dereferencing `node->next->overflow_wrap` without validating `node->next` first.

### Impact Explanation
This code path is reachable by any private-payment counterparty sending a crafted private-payment chain over the wallet-to-wallet/hub protocol (`network.js`'s `handleOnlinePrivatePayment`/`handleSavedPrivatePayments`, or `wallet.js`'s `handlePrivatePaymentChains`), which ultimately calls into `private_payment.js` → `indivisible_asset.js`'s `validateAndSavePrivatePaymentChain`/`parsePrivatePaymentChain`. An uncaught `TypeError` thrown synchronously inside a callback executed outside of a try/catch boundary can crash the Node.js process, denying the recipient wallet/hub the ability to process further private payments or units — a network/node availability impact matching CVSS `A:H` with no confidentiality/integrity impact, consistent with the reference CVE's severity profile.

### Likelihood Explanation
The attack requires only sending a malformed JSON private-payment chain as a private-payment counterparty — no privileged access, no consensus/network position, and no cryptographic material is needed beyond crafting the payload. This satisfies the reachability requirement (single posted trigger/message from an allowed unprivileged actor: a private-payment counterparty).

### Recommendation
In `validatePrivatePayment()` (and `parsePrivatePaymentChain()`), validate that `objPrevPrivateElement.output` is a non-empty object before dereferencing `.address`/`.blinding`, mirroring the existing checks already applied to the *current* element (e.g., `!objPrevPrivateElement.output` check similar to line 203's `!objPrivateElement.output`). Additionally, wrap chain validation logic in defensive error handling so a malformed private element results in `callbacks.ifError(...)` rather than an uncaught exception.

### Proof of Concept
1. As a private-payment counterparty, construct a 2-element `arrPrivateElements` chain where the tail (issue) element is well-formed, but the intermediate transfer element that would become `prevElement` for index 0 lacks an `output` field (e.g., strip `output` from the JSON while keeping `payload`/`unit`/`message_index`).
2. Send this chain via the wallet private-payment message flow (`handlePrivatePaymentChains` in `wallet.js` or `handleOnlinePrivatePayment` in `network.js`) to a victim wallet/hub.
3. When `parsePrivatePaymentChain` reaches index 0 and calls `validatePrivatePayment` with `prevElement` (the tail element missing `.output`), `validateSpendProof`'s check `objPrevPrivateElement.output.address` throws a `TypeError`, crashing the process if uncaught.
