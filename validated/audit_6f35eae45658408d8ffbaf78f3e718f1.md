### Title
Disabled origin check lets an indirectly-introduced device impersonate a trusted correspondent - (File: wallet.js)

### Summary
`ocore`'s device-messaging layer distinguishes between fully-paired correspondents and "indirect" correspondents that are silently added to `correspondent_devices` (with `is_indirect=1`) whenever a peer names them as a co-signer during multisig wallet setup (`device.addIndirectCorrespondents`, called from `wallet_defined_by_keys.js` `approveWallet`). A restriction that limited what subjects an indirect correspondent could send was removed (commented out) in `wallet.js`, so once a device is known — even only "indirectly" through a third party's claim — it is trusted for every message subject, including `sign`, `removed_paired_device`, private-payment chains, and shared-address flows.

### Finding Description
When a user approves a multisig wallet creation offered by another device, `approveWallet` in `wallet_defined_by_keys.js` calls: [1](#0-0) 
which invokes `device.addIndirectCorrespondents(arrOtherCosigners, ...)`. This list of "other cosigners" — including each one's `device_address`, `pubkey`, `hub`, and `name` — originates entirely from the initiating peer's proposal message and is inserted into `correspondent_devices` without any pairing-secret exchange, cryptographic proof of control, or user confirmation of that specific device: [2](#0-1) 

Once a device address exists in `correspondent_devices` (even `is_indirect=1`), `handleJustsaying` in `device.js` treats it as "known" and dispatches every subsequent signed message from it to the application layer: [3](#0-2) 

The application-layer dispatcher (`wallet.js`) was previously supposed to restrict indirect correspondents to a narrow, safe whitelist of subjects, but this check is commented out: [4](#0-3) 

As a result, an attacker who gets merely *named* as a co-signer in someone else's wallet-creation proposal (a message the attacker's confederate, or the attacker acting as the wallet initiator, fully controls) becomes a trusted correspondent for the honest user's device. That attacker device address can then send arbitrary subjects that are normally reserved for verified, directly-paired peers, e.g.:
- `sign` — request the local wallet to co-sign a caller-supplied unit (used for multisig/multilateral signing), potentially tricking a human cosigner into approving an attacker-crafted spend from a shared address.
- `removed_paired_device` — trigger unpairing logic.
- Private-payment chain messages / shared-address messages that assume the sender is a genuine, vetted correspondent.

This is directly analogous to the CardGate issue: a message from an unauthenticated/unauthorized origin (never actually verified as a legitimate counterparty by the wallet's own trust model) is processed with full privileges because the origin-restriction check was removed, letting an attacker who merely appears in someone else's payload masquerade as a trusted party.

### Impact Explanation
This lets an attacker who is included (by anyone, including themselves) in a wallet-creation cosigner list obtain the same message-processing trust as a properly paired correspondent, without ever completing a real pairing handshake. Combined with the disabled indirect-correspondent whitelist, this reaches “wallet and contract message handling” — the attacker can push `sign` requests for arbitrary shared-address units to a legitimate cosigner's device, increasing the chance of tricking them into cosigning a malicious multisig transaction, or send other subjects that manipulate correspondent state (e.g., unpairing) — a Medium/High severity trust-boundary bypass affecting shared/multisig wallet safety.

### Likelihood Explanation
Reachable by any unprivileged peer: to become an "indirect correspondent" of a victim, the attacker only needs the victim to receive and approve a wallet-creation proposal (`create_new_wallet`/`approveWallet`) that lists the attacker's device as one of the co-signers — controlled entirely by the message the attacker (or their confederate acting as the wallet initiator) sends. No cryptographic pairing secret or additional user confirmation of the specific device is required for the entry to be added to `correspondent_devices`.

### Recommendation
Restore and enforce an explicit restriction on what message subjects are accepted from `is_indirect=1` correspondents (the commented-out check in `wallet.js`), limiting indirect correspondents to the minimal safe whitelist necessary for wallet setup (e.g., `cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`). Any sensitive subject (`sign`, `removed_paired_device`, private payment forwarding, shared-address creation, etc.) should require a fully-confirmed, directly-paired correspondent, or additional verification that ties the indirect correspondent's claimed identity to a specific wallet/shared-address context before granting elevated trust.

### Proof of Concept
1. Attacker (or a confederate) initiates a multisig wallet-creation proposal (`create_new_wallet`) to the victim, listing `arrOtherCosigners` that includes the attacker's own device address/pubkey/hub as a purported co-signer.
2. Victim calls `approveWallet`, which calls `device.addIndirectCorrespondents(arrOtherCosigners, ...)`, inserting the attacker's device into `correspondent_devices` with `is_indirect=1` — no pairing secret was ever exchanged with this device.
3. Attacker's device now passes the "known correspondent" check in `device.js` `handleJustsaying` (`hub/message` case) for any subject.
4. Because the indirect-correspondent subject whitelist in `wallet.js` (`doHandle`) is commented out, the attacker sends a `sign` message (or other sensitive subject) which is processed by `handleMessageFromHub` exactly as if it came from a legitimately paired correspondent, e.g.: [5](#0-4)
