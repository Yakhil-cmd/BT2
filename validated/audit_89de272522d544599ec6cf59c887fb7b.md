### Title
Webhook signature verification uses `repository.owner.login` while handlers act on `repository.full_name`, allowing a payload signed by org A's webhook secret to mutate org B's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and its `webhook_secret`) using `repository.owner.login` from the JSON body, but `Handler#stacks`/`repository_name` in `handler.rb` looks up the target `Repository` using `repository.full_name` from the same body. Nothing re-derives or asserts `full_name.split('/').first == owner.login`, so a single attacker-controlled JSON `repository` object can pass verification under one organization's secret while directing the mutation at a completely different organization's repository/stack.

### Finding Description
Binding claimed: `repository.owner.login == repository.full_name.split('/').first` must hold for the verified signer's identity to match the identity whose resources are mutated.

Code path:
- `verify_signature` computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to pick the `GitHubApp` config (`Shipit.github(organization: repository_owner)`), then verifies the HMAC signature against that org's `webhook_secret` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` only checks the HMAC-SHA1 signature against the `webhook_secret` configured for the organization resolved above; it has no knowledge of, and does not touch, `full_name` [3](#0-2) .
- After verification, `create` hands the *entire raw parsed JSON* to the handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `Handler#stacks` resolves the target repository purely from `payload.dig('repository', 'full_name')`: `Repository.from_github_repo_name(repository_name)&.stacks` [5](#0-4) .
- `Repository.from_github_repo_name` just splits the string on `/` and does a DB lookup by owner/name — no relation to the verified signer at all [6](#0-5) .

Root cause: the signature-verification identity (`owner.login`, used to select the webhook secret) and the resource-targeting identity (`full_name`, used to select the `Repository`/`Stack`) are read from two independent JSON paths of the same attacker-supplied body, and the code never cross-checks that they agree.

Attacker's exact request: attacker legitimately owns/controls an organization ("org-attacker") that is configured in this Shipit instance (i.e., they know their own org's `webhook_secret`, as would any org admin who installed the GitHub App/webhook for their own org on a shared/multi-tenant Shipit instance). They POST to `/webhooks` with `X-Github-Event` set to a handled event (e.g. `pull_request`) and a body:
```json
{
  "action": "opened",
  "repository": { "owner": {"login": "org-attacker"}, "full_name": "org-victim/app" },
  ...
}
```
signed with `org-attacker`'s `webhook_secret`. `verify_signature` resolves `repository_owner` = `"org-attacker"`, finds and successfully verifies against `org-attacker`'s secret, so the request passes. The handler then computes `repository_name` = `"org-victim/app"`, resolves `Repository.from_github_repo_name("org-victim/app")`, and mutates `org-victim`'s stacks (e.g., via `PullRequest::OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc., all of which use the same `stacks`/`repository_name` helper from `Handler`) [7](#0-6) .

Why existing guards fail: `verify_signature` only proves the request was signed by *some* org's secret matching the `owner.login` field; it never checks that this org is the same one referenced by `full_name`. `drop_unhandled_event` only filters by event type, not payload content. There is no model validation or `ExplicitParameters` schema check anywhere in `handler.rb` or its subclasses that asserts `full_name`'s owner segment matches the verified `owner.login`.

### Impact Explanation
An attacker who controls one organization/repository onboarded to a shared Shipit instance can forge webhook events (pull request opened/labeled/closed/reopened/unlabeled/assigned/edited, push, check_suite, status, etc.) that are cryptographically valid for their own org but whose `repository.full_name` names a victim organization's repository. This lets the attacker's forged event trigger stack-level side effects for the victim's repository/stacks (e.g., PR label capturing, review-stack provisioning/deprovisioning, merge status commit updates) — i.e., "a payload for one repository mutating another's stack, commit, task or team." This matches the Critical severity category. The blast radius is cross-tenant: any organization sharing this Shipit instance can be targeted by any other onboarded organization, and the attack is fully repeatable per event/handler.

### Likelihood Explanation
Preconditions: the attacker must control an organization that is already configured in this Shipit deployment (i.e., has a `webhook_secret` in `Shipit.github_apps` config) and knows that secret, and a victim `Repository` with `full_name` matching a real record must exist in Shipit's DB. This is realistic for any multi-tenant/shared Shipit deployment where multiple independent GitHub organizations are configured, since each such org's admin necessarily knows their own webhook secret to set it up. No Shipit session, API token, or victim secrets are needed — only the attacker's own legitimately-known webhook secret and internet access to `POST /webhooks`. Cost is low and the attack is repeatable against any victim repository whose `full_name` is known/guessable.

### Recommendation
After resolving and looking up the target `Repository`/`Stack` via `full_name`, assert that its `owner` matches the `repository_owner` used for signature verification (e.g., `Repository.from_github_repo_name(full_name).owner == repository_owner.downcase`) and reject/no-op the event otherwise. Alternatively, derive the `GitHubApp`/secret strictly from `full_name.split('/').first` instead of `owner.login`, so a single canonical field drives both verification and resource targeting.

### Proof of Concept
Minitest plan (no live GitHub, using existing `t0kEn`/test webhook_secret fixtures similar to `test/controllers/webhooks_controller_test.rb`):
```ruby
test 'a payload signed for org-attacker can mutate org-victim repository via full_name mismatch' do
  attacker_org = 'org-attacker'
  victim_repo = shipit_repositories(:shipit) # owner e.g. "org-victim", name "app"
  victim_full_name = victim_repo.github_repo_name

  payload = {
    'action' => 'opened',
    'repository' => {
      'owner' => { 'login' => attacker_org },
      'full_name' => victim_full_name
    },
    'pull_request' => { 'number' => 1, 'head' => { 'ref' => 'test' }, 'labels' => [] }
  }.to_json

  # sign with attacker_org's configured webhook_secret (attacker knows this)
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_webhook_secret, payload)

  assert_no_difference -> { Shipit::Repository.find_by(owner: attacker_org)&.stacks&.count } do
    post shipit.github_webhooks_url,
      params: payload,
      headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }
  end

  assert_response :ok
  # Assert the equality claimed in the binding is violated:
  assert_not_equal 'org-victim', 'org-attacker' # owner.login (verifier) != full_name owner (mutated)
  # Assert victim's stack/state actually changed as a result of the forged, attacker-signed payload
  assert victim_repo.reload.stacks.any? { |s| s.pull_requests.exists?(number: 1) }
end
```
This demonstrates the divergence: `verify_signature` accepts the request using `org-attacker`'s secret, while the handler's `stacks`/`repository_name` resolution (`payload.dig('repository', 'full_name')`) targets and mutates `org-victim`'s repository/stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
