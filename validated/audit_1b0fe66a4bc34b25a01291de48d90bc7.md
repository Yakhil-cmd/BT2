### Title
Arbitrary route hop can spend unrelated caller tokens through the signed `swap_collateral` authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller accepts opaque route bytes and invokes the configured router under the caller’s `require_auth` context. A malicious route can name an attacker-controlled hop that performs `token.transfer(victim, attacker, amount)`. Soroban records that transfer as a child of the victim’s authorization, and it executes when the victim signs the simulated tree. This is analogous to forwarding an authentication credential across an untrusted redirect: authorization granted for a swap can be consumed for an unrelated token transfer.

### Finding Description
`swap_collateral` accepts caller-supplied `swap` bytes and requires only caller authentication before execution. `process_swap_collateral` authenticates the caller, authorizes the account owner or delegate, withdraws collateral, and passes the opaque route into `swap_tokens_or_passthrough`. [1](#0-0) 

The shared router wrapper grants the controller only one exact input-token transfer authorization, but it does not decode or constrain the contracts reachable through the supplied route. It invokes `router.execute_strategy` inside the guarded call and subsequently checks only controller balance deltas and account risk. [2](#0-1) 

The authorization helper is narrowly scoped to `token_in.transfer(controller, router, amount_in)` and has no sub-invocations, but that protects only the controller’s invoker authorization. It does not prevent route-selected code beneath the router from requesting a separate transfer from the human caller. [3](#0-2) 

The same exposure exists for every route-taking user operation:

- `multiply(caller, account_id, spoke_id, collateral, debt_to_flash_loan, debt, mode, swap, initial_payment, convert_swap)`
- `swap_debt(caller, account_id, existing_debt, amount, new_debt, swap)`
- `swap_collateral(caller, account_id, current, amount, new, swap)`
- `repay_debt_with_collateral(caller, account_id, collateral, collateral_amount, debt, swap, close_position)`

These public entrypoints forward attacker-influenced route bytes after owner/delegate authentication. [4](#0-3) 

### Impact Explanation
An unprivileged attacker can craft a route whose hop invokes `transfer(victim, attacker, victim_balance)` on an arbitrary token. If the victim signs the authorization tree produced by simulation, the route can drain tokens unrelated to the supplied collateral, including assets never listed by the protocol. The executed transfer is not bounded by `amount_in`, route minimum output, measured router output, or final health-factor checks.

This is direct theft of user funds. The protocol’s post-swap checks can remain successful because the malicious hop may still permit a valid-looking swap while performing an additional victim-token transfer.

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-influenced route and sign the resulting authorization tree. Transaction simulation exposes the malicious child transfer, so a wallet or client that decodes and rejects unexpected children prevents the theft. However, nothing in the controller rejects the route, the authorization is rooted in an ordinary strategy call, and route bytes are opaque to users unless their client performs authorization-tree validation.

The repository’s threat model explicitly states that route-selected pool and token addresses are not allowlisted and that a signed child transfer can consume the caller’s wallet balance. [5](#0-4) 

### Recommendation
Do not treat route bytes as opaque at the authorization boundary. Decode the route before simulation and reject routes containing pool, token, callback, or recipient addresses outside an explicitly approved venue/registry set. If arbitrary venue contracts are intentionally supported, constrain execution to a router mode that cannot place additional caller-authorized token transfers beneath the strategy authorization, or require a separate explicit authorization scope for every caller-funded transfer.

Clients must also display the complete simulated authorization tree and reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or direct `execute_strategy` authorization containing children other than the expected protocol input transfer. On-chain venue allowlisting is still necessary because wallet-side checks are not a protocol invariant.

### Proof of Concept
The test harness demonstrates the exact behavior with `swap_collateral`:

1. Alice supplies USDC and holds `77_770_000_000` units of an unrelated token.
2. The route names an attacker-deployed hop pool.
3. The hop executes `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)`. [6](#0-5) 
4. Transaction simulation records that transfer as a child of Alice’s `swap_collateral` authorization. [7](#0-6) 
5. Signing the simulated tree executes the malicious transfer, leaving Alice’s unrelated-token balance at zero and crediting the attacker. [8](#0-7)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

        sub_invocations: std::vec![],
```
