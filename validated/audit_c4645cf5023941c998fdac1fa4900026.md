### Title
Forged `pull_request` edited webhook via no-secret organization reaches `EditedHandler` and mutates cross-tenant records - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` only checks the HMAC using the `webhook_secret` configured for the organization named in `repository.owner.login`, and `Shipit::GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org has no configured `webhook_secret`. Because `Shipit::Webhooks::Handlers::PullRequest::EditedHandler` resolves the target `Repository`/`PullRequest` from the separate, attacker-controlled `params.repository.full_name` field rather than from the field used for authentication, an org configured with no secret can be used to "authenticate" a forged payload that actually names and mutates a repository belonging to a different, secured organization.

### Finding Description
The broken binding is: *the organization whose `webhook_secret` verified the request* (`repository.owner.login`, used in `verify_signature`) **must equal** *the organization/repository whose record is mutated* (`repository.full_name`, used in `EditedHandler#repository`/`#pull_request`). These two values are read from two different, independently attacker-controlled JSON fields in the same payload, and nothing enforces they refer to the same organization.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` immediately if that org's config has no `webhook_secret` set: `return true unless webhook_secret`. [3](#0-2) 
- Once verification passes, `WebhooksController#create` dispatches the raw parsed JSON to all handlers for the event, with no re-check of which org "owns" the payload. [4](#0-3) 
- `EditedHandler` locates the repository/stack/pull_request purely from `params.repository.full_name` (independent of `repository.owner.login`) and calls `pull_request.update(github_pull_request: params.pull_request)`. [5](#0-4) 

Exploit flow: an attacker crafts a `pull_request` webhook body where `repository.owner.login = "org-with-no-secret"` (an org configured in Shipit but without `webhook_secret`) while `repository.full_name = "org-with-secret/protected-repo"` (a different, secured org/repo actually tracked in Shipit). `verify_signature` looks up the GitHubApp for `"org-with-no-secret"`, finds no secret, and accepts the request unconditionally regardless of the `X-Hub-Signature` header content. `EditedHandler` then resolves the `Repository` via `Repository.from_github_repo_name("org-with-secret/protected-repo")` and updates the persisted `PullRequest` belonging to that unrelated, secured stack. Existing guards do not prevent this: `verify_signature` never compares `repository.owner.login` against `repository.full_name`'s owner segment; the `ExplicitParameters` schema on `EditedHandler` only requires `repository.full_name` to be a `String`, with no format/ownership constraint tying it back to the authenticating org. [6](#0-5) 

### Impact Explanation
An unauthenticated internet actor can forge a state mutation (`pull_request.update`) against any `Shipit::PullRequest` belonging to any repository/org configured in Shipit, as long as at least one *other* configured org has no `webhook_secret`. This is a cross-tenant/cross-repository state manipulation: one org's (lack of) credential is used to legitimize a payload naming a completely different org's repository and pull request, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). This is repeatable per-request and scales to every `PullRequest`/stack in the installation, and the same authentication decoupling (owner-login vs full_name) generically affects other handlers relying on `params.repository.full_name`, not just `EditedHandler`.

### Likelihood Explanation
The only precondition is that the Shipit deployment has configured at least one GitHub organization without a `webhook_secret` — a realistic and low-friction misconfiguration since `webhook_secret` is optional per-org in `GitHubApp#initialize` (`@webhook_secret = @config[:webhook_secret].presence`). [7](#0-6)  Given that, the attacker needs no session, token, or secret at all — just knowledge of one such org's login and a target repo's `full_name` that is tracked in Shipit, both of which are typically public/discoverable information. The attack costs a single unauthenticated HTTP POST and is fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, derive and enforce a single canonical "authenticating organization" per request and require every organization-scoped field in the payload (`repository.full_name`'s owner segment, `organization.login`, etc.) to match it before dispatching to handlers. Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank in production; require every configured org to have a `webhook_secret`, or reject/flag payloads from secret-less orgs at the controller level instead of treating them as fully verified.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "forged pull_request edited event via no-secret org mutates unrelated org's pull request" do
  # Setup: shipit.yml/config has org "no-secret-org" (no webhook_secret) and
  # org "secured-org" (has webhook_secret), with a Stack/Repository "secured-org/protected-repo"
  # containing an existing Shipit::PullRequest with number 42.

  pr = shipit_pull_requests(:protected_repo_pr_42) # belongs to secured-org/protected-repo
  original_title = pr.github_pull_request['title']

  forged_body = {
    action: 'edited',
    number: 42,
    pull_request: {
      id: 999, number: 42, url: 'https://x', title: 'HIJACKED TITLE',
      state: 'open', additions: 1, deletions: 0,
      head: { sha: 'deadbeef', ref: 'attacker-branch' },
      user: { login: 'attacker' }, assignees: [], labels: []
    },
    repository: {
      full_name: 'secured-org/protected-repo',   # the real target
      owner: { login: 'no-secret-org' }          # org with no webhook_secret, used only for auth
    },
    sender: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=totally-invalid'

  post :create, body: forged_body, as: :json

  assert_response :ok
  pr.reload
  assert_equal 'HIJACKED TITLE', pr.github_pull_request['title']
  refute_equal original_title, pr.github_pull_request['title']
end
```
This demonstrates that `repository.owner.login` (used by `verify_signature` for the HMAC/secret lookup) and `repository.full_name` (used by `EditedHandler` to resolve and mutate the actual `PullRequest`) diverge, and that divergence is never checked — allowing the org with no `webhook_secret` to "authenticate" a forged mutation of a different, secured org's data.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
