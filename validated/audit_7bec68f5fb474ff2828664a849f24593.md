### Title
Cross-tenant webhook confusion: signature-verified organization is never bound to the resolved `repository.full_name`, allowing an attacker's own signed webhook to trigger `RefreshCheckRunsJob` against a victim's stack/commit - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub organization taken from `payload.dig('repository','owner','login')` (falling back to `payload.dig('organization','login')`), while `Handlers::Handler#stacks` independently resolves the target repository from `payload.dig('repository','full_name')`. These two fields live in the same attacker-controlled JSON body and are never checked for consistency, so an attacker who owns a legitimate (but unrelated) GitHub org/webhook secret registered with Shipit can sign a request as themselves while pointing `repository.full_name` at a victim's repository.

### Finding Description
The claimed broken binding, made explicit: `payload.dig('repository','owner','login')` (used by `verify_signature` to pick the HMAC secret via `Shipit.github(organization: repository_owner)`) should equal the organization that owns `payload.dig('repository','full_name')` (used by `Handler#stacks` to resolve `Repository.from_github_repo_name`). In the code, these are read independently: [1](#0-0) [2](#0-1) [3](#0-2) 

Nothing in `verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, or `CheckSuiteHandler` cross-checks that `repository.owner.login` matches the owner encoded in `repository.full_name`: [4](#0-3) 

`Repository.from_github_repo_name` performs a plain lookup on the attacker-supplied string with no ownership check tying it back to the verified signer: [5](#0-4) 

Exploit flow: the attacker crafts a raw HTTP POST to `/webhooks` with `X-Github-Event: check_suite`, sets `repository.owner.login` (or `organization.login`) to their own org (for which they legitimately know the configured `webhook_secret` from their own GitHub App/webhook setup), computes a correct `X-Hub-Signature` for that secret over the raw body, but sets `repository.full_name` to `"victim-org/victim-repo"` and `check_suite.head_branch`/`check_suite.head_sha` to values matching a real victim commit. `verify_signature` succeeds because the signature is valid for the attacker's own org/secret pair. `CheckSuiteHandler#process` then calls `stacks` (resolved from the victim's `full_name`, not the attacker's verified org) and enqueues `RefreshCheckRunsJob` for a real victim commit: [6](#0-5) 

That job ultimately calls `Commit#refresh_check_runs!`, which uses the repository's real owner to select GitHub credentials via `Shipit.github(organization: owner)` (through `Repository#github_app`), i.e. the app's legitimate credentials for the *victim's* org, not the attacker's: [7](#0-6) 

Existing guards do not stop this: `verify_signature` only validates that *some* known organization's secret matches the raw body - it never validates that the same organization also owns the repository referenced by `full_name` used downstream by handlers.

### Impact Explanation
An attacker who legitimately controls a Shipit-registered org/webhook (their own repo/org) can force Shipit to enqueue `RefreshCheckRunsJob` (and, by the same `repository_name` confusion pattern, any other handler keyed off `payload.dig('repository','full_name')`, e.g. push/status handlers) against an arbitrary victim stack/commit that Shipit tracks. The job runs with Shipit's own GitHub credentials for the victim org, hits the victim's real GitHub check-run/status data, and writes `CheckRun` records tied to the victim's commit based on attacker-chosen branch/sha - a payload authenticated for one repository mutating another repository's stack/commit records. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
The attacker must control/administer at least one GitHub organization/repository that is already configured in Shipit with its own webhook secret (a plausible precondition in any multi-tenant Shipit deployment supporting multiple orgs) - they need no privilege on the victim's repository, session, or API token. Crafting the JSON body with mismatched `repository.owner.login` vs `repository.full_name` and signing it with their own known secret is trivial and fully repeatable against any victim repository/stack tracked by the same Shipit instance.

### Recommendation
Bind the verified organization to the resolved repository: after `verify_signature`, derive `repository_name`/`stacks` resolution strictly from the same `repository_owner` used for signature verification (e.g., require `Repository.from_github_repo_name(payload.dig('repository','full_name'))` to belong to `repository_owner`, or better, resolve the owner solely from `repository_owner` and reject if it doesn't match the owner segment of `full_name`) in `Webhooks::Handlers::Handler#stacks`.

### Proof of Concept
Add a minitest in `test/controllers/webhooks_controller_test.rb` style (integration, no live GitHub, uses the existing stubbed `verify_webhook_signature`):
1. Create a victim stack/commit fixture (`victim-org/victim-repo`, branch `master`, known sha).
2. Configure Shipit with a second org `attacker-org` with its own webhook secret (or stub `Shipit.github(organization: 'attacker-org')`).
3. POST a `check_suite` payload where `repository.owner.login == 'attacker-org'` and `repository.full_name == 'victim-org/victim-repo'`, `check_suite.head_branch == 'master'`, `check_suite.head_sha == victim_commit.sha`.
4. Stub/mock `Shipit.github(organization: 'attacker-org')#verify_webhook_signature` to return `true` (simulating attacker's valid signature for their own org).
5. Assert: `assert_equal 'attacker-org', repository_owner_used_for_verification` and `assert_equal 'victim-org', Repository.from_github_repo_name(payload.dig('repository','full_name')).owner` - showing the two differ - then `assert_enqueued_with(job: RefreshCheckRunsJob, args: [commit_id: victim_commit.id])` after `post :create`.

# frozen_string_literal: true

module Shipit
  class RefreshCheckRunsJob < BackgroundJob
    queue_as :default

    def perform(params)
      if params[:commit_id]
        Commit.find(params[:commit_id]).refresh_check_runs!
      else
        stack = Stack.find(params[:stack_id])
        stack.commits.order(id: :desc).limit(30).each(&:refresh_check_runs!)
      end
    end
  end
end
