### Title
Cross-tenant deploy-gate forgery via unscoped commit lookup in the `status` webhook handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` writes a GitHub commit status to Shipit's database by matching **only the commit SHA**, with no check that the SHA belongs to a repository owned by the GitHub organization/App installation whose webhook secret was used to authenticate the request. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` selects the HMAC secret to validate the incoming payload based on `repository_owner`, i.e. it only proves *which organization's App installation* sent the event: [1](#0-0) 

Every other default handler (`PushHandler`, `CheckSuiteHandler`, `pull_request/*` handlers) re-derives the target `Repository`/`stacks` from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`Repository.from_github_repo_name`, scoping the write to repositories the authenticated organization actually owns: [2](#0-1) [3](#0-2) [4](#0-3) 

`StatusHandler`, however, does not require or use a `repository` field at all, and instead looks up commits **globally by SHA** across the entire `commits` table, regardless of which stack/repository/organization they belong to: [5](#0-4) 

Because `Commit.where(sha: params.sha)` is unscoped, any signed `status` event — signed with the webhook secret of *any* organization/repository Shipit trusts — can write a `Status` record onto a commit that belongs to a completely different stack/repository, as long as the attacker knows (or can predict/collide) that commit's SHA. Git commit SHAs for tracked repositories are ordinarily discoverable through the GitHub UI/API (they are not secrets), so an attacker who merely has the ability to trigger a `status` webhook for one repository the App is installed on (e.g., a low-value sandbox repo in the same org, or any repo if the App/secret is shared) can forge a passing (or failing) CI status for a commit belonging to a different, unrelated, higher-value stack.

This directly undermines `ci.require`/CI-gating logic (`Shipit::CommitChecks`, `Status::Group`) that stacks use to decide whether a commit is safe to deploy — Shipit trusts `Status` rows created from these webhooks when evaluating whether a commit has satisfied its required checks. [6](#0-5) 

### Impact Explanation
This crosses a repository/authentication boundary equivalent to the analog described in the rules: "an organization that authenticated versus the repository that is written." An attacker with the ability to fire a `status` event for one repository can forge CI-passing statuses on commits in a different repository/stack, potentially causing Shipit to consider a commit "green" and mergeable/deployable when it is not — an unauthorized-deploy-adjacent condition (High), since it escalates into stack deploy-gating logic that is supposed to be scoped per-repository.

### Likelihood Explanation
Moderate-to-high: it requires the attacker to control (or trigger events from) at least one repository under a GitHub App installation Shipit trusts, and to know a target commit's SHA (public information for any repository visible on GitHub). No Shipit session, API token, or webhook secret compromise is needed — only the ability to cause a legitimate, correctly-signed `status` webhook to fire, which is native GitHub behavior (e.g., any CI system, GitHub Action, or collaborator posting a commit status on a repo covered by the same organization-level webhook secret).

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: require and validate the payload's `repository.full_name`, resolve it to a `Shipit::Repository`, and restrict the `Commit` lookup to commits belonging to that repository's stacks (mirroring `Handler#stacks`) rather than a bare `Commit.where(sha: params.sha)` across the whole database.

### Proof of Concept
1. Shipit tracks `stack_a` (repository `org/private-app`) and `stack_b` (repository `org/sandbox`), both under the same GitHub organization/App installation with webhook secret `S`.
2. An attacker with only write/CI access to `org/sandbox` learns the SHA `abc123` of a commit on `org/private-app` (visible via GitHub UI/API).
3. Attacker causes a `status` event to be sent to Shipit's webhook endpoint, correctly signed with `S`, containing `{"sha": "abc123", "state": "success", "context": "ci/required-check"}` — no `repository` field is required by `StatusHandler`.
4. `WebhooksController#verify_signature` validates the signature against org `org`'s secret and passes it through.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123").each { |c| c.create_status_from_github!(params) }`, creating a "success" status on the `org/private-app` commit even though the event never referenced that repository, potentially satisfying `ci.require` for `stack_a` and enabling an unauthorized deploy/merge decision.
