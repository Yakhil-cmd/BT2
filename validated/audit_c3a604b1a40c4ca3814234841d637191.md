### Title
AA payment `issueAsset` auto-mints uncapped assets to cover any output shortfall, ignoring available AA balance - ([File: aa_composer.js])

### Summary
This mirrors the reported class: a spend/limit path that doesn't validate a spend amount against the actual available balance, letting the operation consume/create more than intended. In `AuctionRebalanceModuleV1`, `_quoteQuantityLimit` wasn't checked against the real quote-asset balance. In `ocore`, when an AA's `payment` message tries to send an uncapped asset it doesn't have enough of, `completePaymentPayload` doesn't fail — it silently mints the shortfall via `issueAsset`, inflating supply beyond what the AA (or anyone) actually deposited.

### Finding Description
In `aa_composer.js`, `completePaymentPayload` builds payment payloads for AA-generated messages. It first tries to gather unspent stable/unstable outputs to cover `target_amount` [1](#0-0) . If insufficient funds are found for a non-base asset, instead of bouncing the message it calls `issueAsset` [2](#0-1) .

`issueAsset` checks only whether the AA is allowed to issue (`issued_by_definer_only`) — not whether issuing is economically sound or whether the AA actually intended to mint new supply. For uncapped assets, it computes `issue_amount = target_amount - total_amount` (i.e., exactly the shortfall) and unconditionally prepends an `issue` input covering the gap [3](#0-2) . There is no check that the AA's own bookkeeping/state variables actually tracked or authorized this issuance amount — the formula author only specifies output amounts (e.g. `trigger.data.amount`) in the AA formula language, with no visibility into or control over whether the underlying transfer will be satisfied from existing balance or from freshly minted supply.

This is analogous to the reported bug: a value specified through user/AA-facing logic (`output.amount`, akin to `_quoteQuantityLimit`) is not validated against the actually available balance (`quote asset balance` / AA's real asset holdings) before the module proceeds, and the fallback behavior (spend more than available / mint the difference) silently violates the implicit invariant that payments come from real backing.

### Impact Explanation
Any AA that issues a non-capped, non-`issued_by_definer_only`-restricted custom asset and later attempts to pay out more of that asset than it currently holds (e.g., due to a state-variable/accounting bug, a bounced complementary transfer, or an attacker crafting a trigger that causes the AA to compute an output larger than its tracked balance) will have the module auto-mint the missing supply rather than fail the operation. This is uncontrolled supply inflation of the asset — units are created without any deposit or backing — undermining any economic assumptions counterparties have about the asset's total supply, which is the "asset issuance/supply inflation" impact class explicitly in scope.

### Likelihood Explanation
Likelihood depends on an AA's own logic ever attempting to pay out more of a self-issued asset than it currently holds — this can happen from an AA definition bug, a mis-accounted state variable, or crafted trigger data driving a formula-computed `output.amount` above the AA's real balance. Since `issueAsset` is reached automatically as a fallback with no explicit opt-in flag distinguishing "pay from balance" vs. "mint new supply", any AA author relying on the assumption that payments only draw from existing balance is exposed. The condition is a state/logic condition, not an attacker directly forging an issue input, so likelihood is moderate rather than trivial, but it's realistically reachable via a single crafted AA trigger under an AA definition with imperfect accounting.

### Recommendation
Require explicit intent for issuance in AA payment messages (e.g. a distinct message field / instruction) rather than treating "insufficient output-covering inputs" as an implicit signal to mint. At minimum, `completePaymentPayload` should bounce the AA response when the requested payment for a non-base asset cannot be covered by the AA's tracked balance, unless the AA definition/state explicitly authorized an issuance for exactly the needed amount, closing the gap where a balance shortfall silently becomes new supply.

### Proof of Concept
1. Deploy an AA that defines a custom uncapped asset (`is_transferrable`, not `cap`, issuable by anyone or by the AA itself) and tracks a state variable representing its "balance" of that asset for accounting.
2. Through normal operation (e.g., due to a rounding/accounting discrepancy in the AA's oscript, or a crafted sequence of triggers) get the AA to construct a `payment` message with `payload.asset = <custom asset>` and `outputs` totaling more than the AA's actual on-chain holdings of that asset.
3. `completePaymentPayload` runs `readStableOutputs`/`readUnstableOutputsSentByAAs`, finds insufficient inputs, and calls `issueAsset`, which mints exactly the shortfall as a new `issue` input [2](#0-1) [4](#0-3) .
4. The response unit is produced with newly minted asset supply that was never deposited, inflating total circulating supply of the custom asset beyond what any depositor contributed.
