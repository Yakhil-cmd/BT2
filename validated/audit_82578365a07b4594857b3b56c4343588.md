### Title
Membership webhook trusts unsigned `organization.login` field for `Team#organization` while signature verification is keyed on a different, attacker-controlled field (`repository.owner.login`) - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the webhook secret to validate against using `repository_owner`, which reads `repository.owner.login` first and only falls back to `organization.login` if `repository` is absent. `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` to populate `team.organization` when creating a new `Team`. Because both fields live in the same attacker-controlled JSON body and are never cross-checked, an attacker who legitimately owns `attacker-org` (and thus its real `webhook_secret`) can forge a body whose `repository.owner.login` is `attacker-org` (so signature verification passes) but whose `organization.login` is an arbitrary different org name, causing a `Team` to be created and attributed to that arbitrary org.

### Finding Description
The broken binding: `repository_owner` (used in `verify_signature` to pick `Shipit.github(organization: repository_owner)`) is assumed to equal `params.organization.login` (used in `MembershipHandler#find_or_create_team!` to set `team.organization`). These are two independent JSON paths with no cross-validation: [1](#0-0) [2](#0-1) [3](#0-2) 

Exploit flow: the attacker crafts a `membership` event payload with a synthetic `repository: { owner: { login: "attacker-org" } }` object (this key is not required by GitHub's real membership payload schema, but nothing in `WebhooksController` or `MembershipHandler`'s `ExplicitParameters` schema rejects extra keys) so that `repository_owner` resolves to `attacker-org`. The attacker signs the raw JSON body with `attacker-org`'s real, legitimately-provisioned `webhook_secret` via `X-Hub-Signature`. `verify_signature` calls `Shipit.github(organization: 'attacker-org').verify_webhook_signature(...)`, which succeeds because the HMAC is computed over raw bytes only — it has no notion of which fields are "trusted" for which purpose. The same body's `organization.login` field is set to `real-org`. `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`, creating (or if `github_id` doesn't collide, always creating) a `Team` row with `organization == 'real-org'`, despite `real-org`'s own webhook secret never having been used or verified.

Existing guards do not catch this: `drop_unhandled_event` only checks the event name exists in the handler map, not payload internal consistency; the `ExplicitParameters` schema in `MembershipHandler` only validates presence/type of `organization.login`, `team.*`, `member.login` — it has no rule tying `organization.login` to `repository.owner.login`; `force_github_authentication` and `require_permission!` are unrelated to webhook ingestion. Nothing in `Shipit::GithubApp#verify_webhook_signature` binds the verified secret's organization identity back into the parsed payload used by handlers.

### Impact Explanation
The attacker can plant a fabricated `Team` row attributed to any organization name of their choosing (`real-org`), including choosing the `slug`/`name`/`github_id` to match a team handle referenced in this Shipit instance's `Shipit.github_teams` configuration (`organization/slug` pairs used for OAuth-team-based authorization, per `Team.find_or_create_by_handle`) — see [4](#0-3)  and [5](#0-4) . Once the fake team exists with `organization == 'real-org'` and a slug matching a privileged team, the same forged `membership` payload's `action: 'added'` / `member.login` lets `MembershipHandler#process` add an arbitrary Shipit `User` (looked up/created purely by login string, with no cross-org verification) to that team: [6](#0-5) . This is a repeatable, cross-tenant escalation: any request that impersonates a `real-org` team membership can be repeated against arbitrary target organization names, matching the "escalation into `Shipit.github_teams` authorization" / cross-tenant record mutation impact category.

### Likelihood Explanation
Preconditions are exactly as stated: the attacker must be a legitimate tenant of a multi-org Shipit deployment (owns `attacker-org` with its own genuine `webhook_secret` configured by the Shipit operator) — this is a normal, low-cost precondition for any customer/org onboarded onto a shared Shipit instance. No GitHub-side or Shipit-side secret belonging to `real-org` is required. The attacker only needs to control the raw JSON body they POST to `/webhooks` and compute a valid HMAC-SHA1 with their own known secret, which is trivial and fully repeatable against any organization name.

### Recommendation
In `MembershipHandler` (and any other org-scoped webhook handler), derive the trusted organization from the same value used for signature verification (`repository_owner` semantics) rather than trusting `params.organization.login` independently, or explicitly assert `params.organization.login == request-verified organization` before using it to set `team.organization`. Alternatively, have `WebhooksController` pass the verified organization identity into the handler context and require handlers to use it instead of re-reading `organization.login` from the untrusted body.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` patterns):
```ruby
test ":membership binds team.organization to signature-verified org, not organization.login" do
  request.headers['X-Github-Event'] = 'membership'

  forged_payload = {
    action: 'added',
    team: { id: 999, name: 'Fake Team', slug: 'fake-team', url: 'https://example.com' },
    organization: { login: 'real-org' },          # attacker-controlled, used by MembershipHandler
    repository: { owner: { login: 'attacker-org' } }, # attacker-controlled, used for signature selection
    member: { login: 'walrus' }
  }.to_json

  Shipit.github(organization: 'attacker-org').expects(:verify_webhook_signature).returns(true)

  assert_difference -> { Team.count }, 1 do
    post :create, body: forged_payload, as: :json
    assert_response :ok
  end

  team = Team.find_by(github_id: 999)
  # Binding check: signature was verified for 'attacker-org', but the created record claims 'real-org'
  assert_equal 'real-org', team.organization
  refute_equal 'real-org', 'attacker-org' # demonstrates mismatch between verified org and attributed org
end
```
This proves that a payload whose signature only verifies for `attacker-org` results in a `Team` record persisted with `organization == 'real-org'`, which `real-org` never authenticated.
