## Analysis

**Claimed binding:** `status.context == 'ci/circleci'` for `sha == S` should only mutate `Commit` rows where `commit.stack.repository == repository_owner(params)` (the org/repo that authenticated the webhook). Actual code: `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no join or scope on stack/repository at all**. [1](#0-0) 

Signature verification is scoped only to the GitHub **organization** in the payload, not to the specific repository/stack: `Shipit.github(organization: repository_owner)` then `verify_webhook_signature`. [2](#0-1) 

So a genuinely GitHub-signed `status` event for a repository the attacker legitimately owns/controls (e.g. a fork that still shares commit history/objects with the victim's repository, so the git commit SHA is byte-identical) will pass `verify_signature`, then `StatusHandler` will match and mutate **every** `Commit` row across **every stack in the installation** that shares that SHA — including a victim's unrelated stack — regardless of which repository/organization actually authenticated the request. `create_status_from_github!` → `add_status` can flip `simple_state`, fire `deployable_status`/`commit_status` hooks, and call `stack.schedule_merges`. [3](#0-2) [4](#0-3) 

This is a genuine cross-tenant write: a status authenticated for repo/org A mutates a `Commit`/`Status` belonging to stack of repo/org B, satisfying the "payload for one repository mutating another's stack/commit" Critical impact class.

**However, the question's specific causal chain is not supported by the code.** The `review_stacks_enabled` precedence bug is real — in `OpenedHandler#provision?`, `ReopenedHandler#unarchive?`, and the equivalent methods in `LabeledHandler`/`UnlabeledHandler`, Ruby's `&&`/`||` precedence means `review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches: [5](#0-4) [6](#0-5) 

But this bug is only reachable via **`pull_request`** webhook events (`opened`, `reopened`, `labeled`, `unlabeled`), which govern `ReviewStack` create/archive/unarchive through `ReviewStackAdapter`. `StatusHandler` never touches `Repository#review_stacks_enabled`, `provisioning_behavior`, or the `ReviewStackAdapter` at all — it only queries the existing `commits` table by bare `sha` and writes a `Status`/triggers `schedule_merges` on the pre-existing `Stack` the `Commit` already belongs to. The two bugs do not compose: a status webhook cannot "provision" anything, and `review_stacks_enabled` has no bearing on whether `StatusHandler`'s unscoped `Commit.where(sha:)` lookup crosses repository boundaries.

### Title
Cross-repository status pollution via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/organization scoping, so a legitimately-signed `status` webhook from one repository can mutate `Status`/trigger `schedule_merges` on a `Commit` belonging to an unrelated stack whenever the SHA is shared (e.g., un-diverged forks, mirrors, or duplicated history). This is a real, independently-exploitable cross-tenant write, but it is **not** amplified or gated by `review_stacks_enabled` or the provisioning-behavior precedence bug as the question claims — those two mechanisms are on separate, non-interacting code paths.

### Finding Description
The broken binding: for a `status` webhook, `commit.stack.repository` should `==` the `repository_owner` that authenticated the webhook via `Shipit.github(organization: repository_owner)` in `verify_signature`. Instead, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no `stack_id`/`repository` filter, so any `Commit` record in the whole installation sharing that SHA is updated. `verify_signature` only checks that the payload was signed by *some* verified GitHub organization, not that the SHA/commit actually belongs to that organization's repository. An attacker who controls (or forks) a repository that is itself onboarded to Shipit can cause a real, correctly-signed `status` webhook (e.g., from their own CircleCI build) whose SHA coincides with a commit that also exists in a victim's stack (typical for un-diverged forks or mirrored history), and that status will be applied to the victim's `Commit`, potentially flipping `deployable_status`/`commit_status` and calling `stack.schedule_merges`.

### Impact Explanation
An attacker triggers a write (`Status` record + hook emission + `Stack#schedule_merges`) against a `Commit`/`Stack` that never authenticated the event, which matches the "payload for one repository mutating another's stack/commit" Critical category. Repeatable for any SHA collision the attacker can arrange (any repo they legitimately control that shares git history/objects with a target).

### Likelihood Explanation
Requires the attacker to have a repository already onboarded into Shipit (so a real GitHub-signed webhook reaches `/webhooks`) and a SHA collision with a victim `Commit` row — realistically limited to forks/mirrors that share unmodified history. This is a meaningful precondition that reduces likelihood versus a fully unauthenticated exploit, but the code contains no defense-in-depth once that precondition is met.

### Recommendation
Scope `StatusHandler#process` to commits whose `stack.repository` matches the authenticated `repository_owner`/`repository.full_name` from the payload (join `Commit` → `Stack` → `Repository` and filter), instead of a bare `Commit.where(sha:)`.

### Proof of Concept
Not applicable as combined with `review_stacks_enabled` — that part of the claimed chain is unsupported by the code (`StatusHandler` never reads `review_stacks_enabled` or provisioning behavior). A minitest for the standalone cross-repo `Commit.where(sha:)` issue would create two stacks under different repositories with a `Commit` sharing one `sha`, POST a `status` payload for one repository's `full_name`, and assert that only the commit belonging to that repository received a new `Status`.

      reload # to get the statuses into the right order (since sorted :desc)

      end

      end
      new_status
    end
