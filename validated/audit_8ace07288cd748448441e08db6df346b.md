### Title
Revoked proposer's already-scheduled timelock operations remain executable by anyone - (File: contracts/governance/src/timelock/lifecycle.rs)

### Summary
In the governance timelock, a caller holding `PROPOSER_ROLE` can schedule operations via `propose()`. If that proposer is later removed (via `RevokeGovRole`/`apply_revoke_role`), their pending operations are not invalidated: `execute()`/`execute_self()` only verify that the operation is scheduled, non-expired, and past its delay — they never re-check that the original proposer still holds `PROPOSER_ROLE`. Worse, execution with `executor = None` is fully permissionless, so any unprivileged address can drive a revoked proposer's queued operations to completion. This is the same bug class as "removed allocator's votes still count": revocation strips future privileges but leaves the revoked party's already-committed influence intact.

### Finding Description
`propose()` checks the caller's role at schedule time only (`begin_immediate(env, proposer, PROPOSER_ROLE)`) and stores no proposer identity alongside the operation — `operation_for_admin_op` builds an `Operation` of `(target, function, args, predecessor, salt)` and `schedule_operation` records only a ready ledger [1](#0-0) . The only sidecar state recorded is for `RevokeGovRole` targets (to stop them cancelling their own revocation), not for proposers [2](#0-1) . At execution time, `prepare_execute` authorizes the executor and checks expiry, but performs no proposer-role check because none is stored [3](#0-2) . `authorize_executor` explicitly permits `executor == None`, meaning anyone may execute a ready operation [4](#0-3) . Role revocation in `apply_revoke_role` removes the role but does not enumerate or cancel that account's scheduled operations [5](#0-4) .

### Impact Explanation
If a proposer acts maliciously — e.g., schedules a harmful `AdminOperation` and is then revoked precisely because of it — revocation does not neutralize the queued operation. Unless a `CANCELLER_ROLE` holder individually cancels each pending operation within its grace window, the malicious proposer's "votes" still count: any unprivileged address can call `execute`/`execute_self` with `executor = None` once the delay elapses and the operation takes effect. Note that owner-gated operations (upgrades, ownership transfers, oracle/swap-aggregator config, role grants) additionally required `proposer == owner` at schedule time, but all non-owner-gated admin operations (e.g., market/spoke configuration ops that fall into the `_ => {}` branch) can be queued by any proposer and survive their revocation.

### Likelihood Explanation
Requires a proposer to schedule an operation and later have their role revoked — the exact scenario `RevokeGovRole` exists for. Mitigations exist (cancellers can cancel non-recovery ops, sensitive ops have a longer delay giving more reaction time), but cancellation is per-operation and opt-in; nothing automatically invalidates a revoked proposer's queue, so any operation that slips past canceller review executes. Impact is bounded by which ops non-owner proposers can schedule, keeping this Medium.

### Recommendation
Record the proposer's address as sidecar state at `propose()` time (analogous to `mark_role_revocation_target`), and in `prepare_execute`/`execute_self` assert that the recorded proposer still holds `PROPOSER_ROLE` before allowing execution. Alternatively, provide a bulk-cancel path in `apply_revoke_role` that iterates and clears all pending operations scheduled by the revoked account.

### Proof of Concept
```rust
// 1. Owner grants PROPOSER_ROLE to `mallory` via timelock.
// 2. mallory proposes a non-owner-gated AdminOperation `op` with salt `s`.
//    -> propose() stores only (target, function, args, predecessor, salt);
//       no record that mallory scheduled it.
// 3. Owner schedules + executes RevokeGovRole { account: mallory, role: PROPOSER }.
//    -> mallory no longer holds PROPOSER_ROLE; the pending op is untouched.
// 4. Wait delay ledgers. Any unprivileged address calls:
//    gov.execute(&None, &op.target, &op.function, &op.args, &zero_pred, &s);
//    -> authorize_executor(None) does nothing;
//    -> prepare_execute finds the ready ledger, not expired;
//    -> execute_operation runs mallory's operation despite revocation.
```
The missing link is that `schedule_operation`'s ledger entry and the operation hash contain no proposer binding, so revocation has no hook to invalidate the queue.

pub(crate) fn apply_revoke_role(env: &Env, account: &Address, role: &Symbol) {
    renew_instance(env);
    assert_with_error!(
        env,
        access_control::has_role(env, account, role).is_some(),
        GenericError::InvalidRole
    );
    let owner = owner_or_panic(env);
    assert_with_error!(env, account != &owner, GenericError::NotAuthorized);
    if *role == Symbol::new(env, PROPOSER_ROLE) {
        assert_with_error!(
            env,
            access_control::get_role_member_count(env, role) > 1,
            GenericError::CannotRemoveLastProposer
        );
    }
    access_control::revoke_role_no_auth(env, account, role, &owner);
}
