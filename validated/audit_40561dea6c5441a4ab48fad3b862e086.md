### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare `sha` with no repository/stack scoping, and applies the incoming `status` payload to every matching commit across all stacks. Because `verify_signature` in `Shipit::WebhooksController` only checks that the request was validly signed *for the repository named in the payload* (attacker's own repo/org), an attacker who controls a repository can forge a `security/scan` `failure` status for a SHA that also exists on a victim's stack, flipping that victim commit's `blocked?`/`deployable?` state.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.github_repo_name == params.dig('repository','full_name')` (the repo that authenticated the webhook), but `StatusHandler#process` never enforces this equality.

Path:
1. `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the JSON body and dispatches to handlers for the `status` event.
2. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) derives `repository_owner` from `params.dig('repository','owner','login')` — a value taken from the attacker's own payload — and validates the signature using `Shipit.github(organization: repository_owner)`. This proves only that the attacker legitimately owns/controls that org/repo webhook secret; it says nothing about which commit SHA the payload may reference.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
   ```ruby
   def process
     Commit.where(sha: params.sha).each do |commit|
       commit.create_status_from_github!(params)
     end
   end
   ```
   This queries `Commit` globally by `sha`, with no `stack_id`/`repository` filter, then calls `commit.create_status_from_github!(params)` for **every** matching row, regardless of which stack/repo owns it.
4. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes the status via `statuses.replicate_from_github!(stack_id, github_status)` and `add_status` (`app/models/shipit/commit.rb:366-386`) recomputes `status`, potentially firing `Hook.emit(:commit_status/:deployable_status, ...)` and calling `stack.schedule_merges`.
5. `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) and `#deployable?` (`app/models/shipit/commit.rb:227-229`) are driven by `stack.blocking_statuses` and the presence of a `blocking?` status among reachable commits — exactly the state the forged status mutates.

Exploit: an attacker creates/controls a repository (or fork) whose commit history contains, or is engineered to share, the same SHA as a commit already tracked on a victim's Shipit stack (e.g., via a common upstream commit, a rebase-preserving fork, or a cherry-pick with identical tree/parents/timestamps producing the same SHA1). The attacker pushes a commit with that SHA to their own repo (satisfying GitHub's requirement that the SHA be known to that repo for the API/webhook to be considered valid by their own CI), then sends a `status` webhook, signed with their own repo's secret, with `context: security/scan`, `state: failure`, `sha: <shared-sha>`. `verify_signature` passes because the signature matches the attacker's own org. `StatusHandler#process` then finds the victim's `Commit` row with the same `sha` value in a completely different stack/repo and applies the failure status to it, flipping `blocked?` on the victim stack if `security/scan` is in `stack.blocking_statuses`.

No existing guard prevents this: `verify_signature` only authenticates the org/repo named in the *attacker's own* payload; there is no cross-check that the `sha` in the status payload belongs to a commit fetched from that same repository. `drop_unhandled_event`, `ExplicitParameters` (`params` schema only validates types, not repo ownership), and the `Handler` base class do not scope by repository either.

### Impact Explanation
An attacker can, without any Shipit credentials, cause an arbitrary status write against a victim's `Commit` row belonging to a repository the attacker does not control, and this status can flip `blocked?`/`deployable?` for the victim stack when `blocking_statuses` is configured for that context — gating or unblocking deploys/merges for a tenant the attacker has no relationship with. This is a cross-repository/cross-tenant state mutation via a webhook authenticated for a different repository, matching the "Critical — payload for one repository mutating another's stack/commit" category.

The practical constraint is that the attacker needs a `Commit` row to exist with the *same SHA1* as the victim's commit under a different stack, and needs to control a repository/webhook whose signature is accepted for some org known to `Shipit.github(organization:)`. SHA1 collision across unrelated repos is not attacker-controlled at will (git SHA1 depends on tree/parents/metadata), but shared history (shared upstream repos, mirrors, forks tracked as separate Shipit stacks, or CI relays which import commits from multiple sources into shared tables) makes duplicate rows for the same SHA plausible and is exactly the scenario the question's invariant is meant to guard against.

### Likelihood Explanation
Preconditions: victim stack must have `blocking_statuses` configured requiring `security/scan` (or the manipulated context must matter to `deployable?`); a `Commit` record with the target SHA must exist in the victim's stack (Shipit stores commits per stack, ingested from that stack's repo's own push/PR history); attacker needs any repository/org whose signature verification will pass (their own GitHub org). Attacker cost is low — one webhook POST with a valid signature for their own repo. It is repeatable against any SHA shared across stacks, and is not blocked by rate limiting concerns (which are out of scope, but not the vulnerability here). The realistic exploitation surface is bounded by needing a real matching SHA in the victim's commit table, which is the main uncertainty in this write-up (not independently verified with a live reproduction against two arbitrarily-chosen distinct repos in this audit).

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and the analogous `CheckRunHandler`, if present) by the repository that authenticated the webhook, not just by `sha`. Concretely, join through `Stack` and filter by `stack.repository_owner`/`repository_name` matching `params.dig('repository','owner','login')` / `params.dig('repository','name')` (or `full_name`) before applying `create_status_from_github!`, e.g.:
```ruby
Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: owner, repository_name: name }).each { ... }
```
so a status can only ever affect commits belonging to the repository that generated and signed it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status for a SHA is applied to commits in ANY stack sharing that SHA, not just the authenticating repo" do
          shared_sha = 'a' * 40

          victim_stack = shipit_stacks(:shipit)
          victim_stack.update!(deploy_spec_cache: { review: { checklist: nil } }) # ensure blocking_statuses can be set
          victim_stack.cached_deploy_spec.stubs(:blocking_statuses).returns(['security/scan'])

          attacker_stack = create_stack(repository: create_repository(owner: 'attacker-org', name: 'attacker-repo'))

          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')
          attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit')

          # BEFORE: binding under test — victim commit state is independent of attacker repo's payload
          assert_equal false, victim_commit.reload.blocked?

          params = ExplicitParameters::Parameters.new(
            sha: shared_sha,
            state: 'failure',
            context: 'security/scan'
          )

          # simulate a request signed for attacker-org/attacker-repo only
          StatusHandler.new(params).process

          # AFTER: assert cross-repo mutation occurred (proves the bug)
          assert victim_commit.reload.blocked?, "victim commit's blocked? state was mutated by a status signed for a different repository"
        end
      end
    end
  end
end
```
Assertion pair: `victim_commit.blocked? == false` before the forged webhook is processed, versus `victim_commit.blocked? == true` after — with the webhook signed and scoped only to `attacker-org/attacker-repo`, demonstrating that `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup lets one repository's status payload mutate another repository's commit/stack state.
