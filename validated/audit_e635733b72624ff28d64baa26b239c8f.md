### Title
Membership webhook `Team` lookup keyed only on attacker-controllable `github_id`, allowing cross-organization team membership injection - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` record solely by `params.team.id` (`github_id`), with no check that this `github_id` actually belongs to the organization that authenticated the webhook (`params.organization.login`). In a multi-organization Shipit deployment, an attacker who legitimately administers one onboarded GitHub organization (and thus possesses that organization's real `webhook_secret`) can forge a `membership`/`added` event naming another organization's team `github_id`, causing themselves to be added as a member of that pre-existing `Team` row.

### Finding Description
The binding the code is supposed to enforce is: `Team.find_or_create_by!(github_id: params.team.id)` should only resolve/create a team scoped to the organization identified by `Shipit.github(organization: params.organization.login)` that authenticated the request. In code: [1](#0-0) 

`process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` — a global lookup keyed only on the numeric `github_id`, with `organization: params.organization.login` only ever set as a default on first creation, never validated on subsequent lookups.

Signature verification in `WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to check against using `repository_owner`, which for a `membership` event (no `repository` key) falls back to `params.dig('organization', 'login')`: [2](#0-1) [3](#0-2) 

This means the signature check only proves that the payload was signed by the organization *named in the payload's own `organization.login` field* — it does not, and cannot, prove anything about the `team.id` embedded elsewhere in that same payload. An organization admin who owns org B (with org B's real, legitimately-possessed `webhook_secret` configured via `Shipit.github_app_config`) can construct a payload where `organization.login = "org-b"` (so the signature check against org B's secret succeeds) but `team.id` is the `github_id` of a team that actually belongs to org A. Because `find_or_create_team!` never cross-checks that `team.id` belongs to org B, it will find the existing org-A `Team` row and add the attacker's own login as a member via `team.add_member(member)`.

`Shipit.github_teams` builds the authorization team list independently via `Team.find_or_create_by_handle`, but if the `github_id` on that authorized `Team` row matches the one the attacker names, this membership write directly affects the team object used by `User#authorized?`: [4](#0-3) [5](#0-4) 

No other guard intervenes: `drop_unhandled_event` only checks that a handler exists for the event type, `ExplicitParameters` only validates shape/type of `team.id`, `organization.login`, `member.login`, not their mutual consistency, and there is no `require_permission!`/`force_github_authentication` check inside webhook handlers (webhooks are server-to-server, authenticated only by HMAC signature, which — as shown — only authenticates the organization field, not the team-id-to-organization binding).

### Impact Explanation
A successful forged event causes `Team#add_member` to add the attacker's GitHub login to a `Team` record they do not actually belong to on GitHub. If that `Team` row is one of the entries resolved into `Shipit.github_teams` (the authorization allow-list consumed by `User#authorized?`), the attacker gains membership in Shipit's authorization group without ever being a real member of the corresponding GitHub team — an escalation into `Shipit.github_teams` authorization, matching the High severity category defined in the rules. The write is silently accepted (webhook handlers return `head(:ok)` regardless), is repeatable for any team `github_id` the attacker can learn or guess, and crosses tenant boundaries in any Shipit instance configured with multiple GitHub organizations (`secrets.github` keyed by org).

### Likelihood Explanation
This requires: (1) a Shipit deployment configured with more than one onboarded GitHub organization (multi-tenant `secrets.github` config), (2) the attacker legitimately administering/owning one of those onboarded organizations (giving them that org's real `webhook_secret`, obtained through legitimate onboarding rather than theft), and (3) knowledge of the target team's numeric `github_id` (learnable via public GitHub API responses, prior webhook deliveries, or sequential guessing, per the question's premise). Given those preconditions, the attack is a single crafted HTTP POST to `/webhooks` and is fully repeatable and deterministic — `Team.find_or_create_by!` will always resolve to the same existing row for a given `github_id` regardless of which organization's secret signed the request.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and the authenticated organization (e.g., require `team.organization == params.organization.login` on an existing record, raising/dropping the event on mismatch, rather than blindly reusing the found row). More generally, webhook handlers that mutate shared records keyed by GitHub numeric IDs should validate that the authenticated organization (derived from the verified `webhook_secret`) actually owns the referenced entity before applying membership/state changes.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership event signed by org B cannot mutate org A's team" do
  org_a_team = Shipit::Team.create!(github_id: 4242, handle: 'org-a/core', organization: 'org-a')
  attacker = Shipit::User.find_or_create_by_login!('attacker-login')

  # Simulate a 'membership' webhook whose signature is valid for org-b's
  # real webhook_secret, but names org-a's team github_id.
  payload = {
    action: 'added',
    team: { id: org_a_team.github_id, name: 'Core', slug: 'core', url: '...' },
    organization: { login: 'org-b' },
    member: { login: 'attacker-login' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  # BROKEN BINDING: Team.find_or_create_by!(github_id:) should only resolve
  # within the organization that authenticated the call (org-b), i.e.
  # org_a_team.organization == 'org-b' should hold if the write is legitimate.
  # Instead:
  assert_includes org_a_team.reload.members, attacker
  refute_equal 'org-b', org_a_team.organization # org actually authenticating the call
end
```
This demonstrates the write succeeds against org A's team even though the request was authenticated only for org B, confirming the cross-tenant membership injection.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
