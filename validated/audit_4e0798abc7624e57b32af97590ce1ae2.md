### Title
Unsanitized route payload lets a venue address execute arbitrary contract calls under the signer's auth tree, draining the caller's wallet — (File: contracts/swap-aggregator/src/execute/mod.rs, venues dispatch; mirrored test tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs)

### Summary
CVE-2025-1015 is an unsanitized-data bug: a malicious payload is embedded in a field the victim later imports, and the importing context executes it with the victim's privileges. The on-chain analog is the router's `swap_xdr` route payload: `assets` entries are attacker-craftable addresses, every instruction dispatches to the named pool contract with no venue allowlist, and any `require_auth` that code performs is recorded under the *caller's* authorization tree. A crafted route can therefore place a contract on the stack that calls `token.transfer(victim, attacker, amount)` — if the victim signs the tree simulation produced, arbitrary wallet funds move, far beyond the routed `total_in`. The project reproduces exactly this in `rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, where a rogue hop pool steals the caller's entire `WALLET_BALANCE` while still paying a fair swap output that passes every router and controller check.

### Finding Description
`execute_strategy` decodes `StrategyPayload` (`assets`, `amounts`, `ops`) and the execute loop calls `venues::dispatch_hop` against `assets[idx_a]` — the pool address is taken straight from the payload with no registry or allowlist check (README: "Venues … unallowlisted"; threat-model: "the router calls the pool and token addresses its payload names and keeps no allowlist of them"). [1](#0-0) 

The dispatcher measures only the router's own token deltas around the venue call, so a pool that returns an honest-looking balance delta passes `ZeroOutput`/`InvalidAmount`/`SlippageExceeded` while also executing an unrelated `token::transfer(victim → attacker)` inside the same invocation. Because the venue call sits below the caller's `require_auth`, simulation records that transfer as a child of the caller's auth entry, and it executes if the caller signs the tree.

Reachable paths for a single unprivileged caller signing a crafted payload:

- Direct `Router::execute_strategy(sender, total_in, swap_xdr)` — `contracts/swap-aggregator/src/lib.rs:250`.
- Composed via controller strategies (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`), which forward the caller-supplied `swap_xdr` untouched; the harness test drives it through `ctrl.try_swap_collateral`. [2](#0-1) 

### Impact Explanation
Theft of user funds beyond the swapped amount. In the pinned test, a route naming `RogueHopPool` moves the victim's full unrelated-token wallet balance to the attacker inside a `swap_collateral` call that still delivers a fair output and leaves the account healthy — no min-out, residual, or risk gate bounds the loss, since the stolen transfer is not a routed amount. [3](#0-2)  The threat model itself states "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it."

### Likelihood Explanation
Medium, matching the CVE's shape: exploitation needs the victim to submit/sign a route whose `assets` registry contains the attacker's contract — i.e., a malicious quote server response, phishing frontend, or social-engineered `routeXdr` — analogous to the victim importing the poisoned address book. It requires no privileges, no leaked keys, and no protocol admin; it works against the production router as deployed because venue addresses are unvalidated. The defense is off-loaded to clients ("a client must decode the route it signs"), so any wallet/SDK that signs the simulated auth tree without inspecting children exposes its users. Whether this is accepted-as-documented is a judgment call; mechanically the contract provides no on-chain bound, which is why it maps to the CVE rather than to a rejected route-quality class.

### Recommendation
On-chain options: maintain an owner-managed venue allowlist keyed by pool/WASM hash checked in `dispatch_hop`, or restrict payload `assets` to tokens plus venues registered by the owner. If the permissionless-route design is retained, the mitigation must be enforced in the signing path: wallets/SDK must decode `swap_xdr` (per `payload.md`'s `verifyRouteBytes`) and reject any simulated authorization tree whose children contain anything other than the single expected `token_in.transfer(sender → router)` (standalone) or the controller's grant (composed). Documenting the requirement does not enforce it; an allowlist or auth-tree linter in `sdk-js` is the actionable fix.

### Proof of Concept
Already pinned in-repo: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Deploy `RogueHopPool` whose `swap()` executes `token.transfer(alice → attacker, WALLET_BALANCE)` on an unrelated wallet token. [4](#0-3) 
2. Build a route (`RoutedSwap`/payload `assets`) naming that pool as the hop venue with a fair `min_out`. [5](#0-4) 
3. Alice calls `swap_collateral` (or `execute_strategy` directly). Simulation records the stolen transfer as a child of her `swap_collateral` auth entry; signing that tree executes it. [6](#0-5) 
4. Result: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and Alice still received `FAIR_OUT_ETH` supply — all contract-side checks passed.
