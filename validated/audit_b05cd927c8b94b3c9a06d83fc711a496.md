### Title
Webhook organization used for signature verification is never bound to the repository/commit acted on by event handlers, enabling unauthenticated forged CI-status injection into unrelated tracked stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks a GitHub App/secret to validate the HMAC signature purely from the attacker-supplied `repository.owner.login` field, then `create` dispatches the entire, still-untrusted-with-respect-to-repository payload to event handlers that act on a *different* field (`repository.full_name`, or for `StatusHandler`, no repository scoping at all). The binding "organization whose signature was verified == repository that is written to" is never enforced, exactly analogous to the CNote report where the amount that was computed/verified (`repayAmountFinal`) differs from the amount actually transferred (`repayAmount`).

### Finding Description
`verify_signature` resolves the signing secret using an attacker-controlled field before any authentication has occurred: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` unconditionally passes when that resolved organization's `webhook_secret` is blank - a configuration explicitly documented as optional: [3](#0-2) [4](#0-3) 

Multi-organization Shipit installs are a documented, supported configuration where each organization has its own independent `webhook_secret`: [5](#0-4) 

After (or without) real verification, `create` re-parses the same raw body and hands it to handlers unchanged: [6](#0-5) 

Handlers select the repository/stack to mutate from `repository.full_name` in that same payload - a field that has no relationship to `repository.owner.login`, the field that was used to select the verification secret: [7](#0-6) 

`StatusHandler` is worse: it does not scope by repository/stack at all, only by raw commit `sha`, globally across every tracked stack in the instance: [8](#0-7) 

`CheckSuiteHandler` similarly resolves its target stacks from the same forgeable `full_name`/branch fields: [9](#0-8) 

**The broken equality:** `organization_authenticated (repository.owner.login → GithubApp secret check)` should equal `repository_written_to (repository.full_name / commit sha acted on by handlers)`. Nothing in `WebhooksController` or `Webhooks::Handlers::Handler` enforces this equality.

### Impact Explanation
Any organization configured in `config/secrets.yml` without a `webhook_secret` (an explicitly optional, documented setting) becomes a skeleton key for the entire Shipit instance's webhook endpoint. An unauthenticated attacker who only knows that one organization's login name can:
- Forge a `status` event with an arbitrary `sha` belonging to a completely unrelated, victim-owned stack tracked by the same Shipit instance and set `state: success`, injecting a fake passing CI status via `Commit#create_status_from_github!`. If the victim stack's `shipit.yml` gates deploys/merges on required statuses, this can unblock an otherwise-blocked deploy or merge queue entry - an unauthorized deploy.
- Forge a `check_suite` event to trigger `schedule_refresh_check_runs!` against arbitrary victim commits, or a `push` event to force `sync_github` on arbitrary stacks, none of which are bound to the organization whose (non-existent) secret satisfied `verify_signature`.

This requires no Shipit session, no `ApiClient` token, no valid webhook secret for the targeted victim organization, and no repository write access - it only requires the existence of one loosely-configured (secret-less) organization entry, a configuration the project's own setup docs describe as normal/optional.

### Likelihood Explanation
Multi-organization Shipit deployments are explicitly documented and supported, and the webhook secret is explicitly marked optional in the setup guide. Any installation that onboards a low-trust or convenience organization without a webhook secret (or where an attacker can get a GitHub App installed on their own org name known to the Shipit config) exposes every other tracked repository's commit statuses and check-run refresh triggers to unauthenticated forgery, since the handlers never re-check that the acted-upon repository matches the organization whose secret satisfied the signature check.

### Recommendation
After `verify_signature` succeeds, re-derive the authenticated organization and pass it into the handler dispatch; every handler must assert that `repository.full_name`'s owner (or, for `StatusHandler`, the owning stack's repository owner) equals the organization whose secret validated the request, rejecting the event otherwise. Additionally, reconsider allowing `webhook_secret` to be blank at all in multi-organization configurations, since it currently makes `verify_webhook_signature` an unconditional pass-through for that organization.

### Proof of Concept
1. Configure Shipit with two organizations per the documented multi-org format: `victim-org` (real `webhook_secret`) hosting tracked `Repository` `victim-org/victim-repo`, and `attacker-org` (no `webhook_secret`, i.e. blank/omitted, per `docs/setup.md`'s "optional" note).
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<victim's head commit sha>",
  "state": "success",
  "context": "ci/tests"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any `X-Hub-Signature` value [10](#0-9) .
4. `create` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha)` with no repository check and calls `create_status_from_github!`, injecting a forged "success" status onto the victim's commit [11](#0-10) .
5. If `victim-org/victim-repo`'s deploy/merge pipeline treats this status as a required check, the attacker has enabled an unauthorized deploy/merge on a repository they have no relationship to, using zero valid credentials for that repository or its organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
