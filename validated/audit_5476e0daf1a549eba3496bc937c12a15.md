## Analysis

The Dopex bug is a redemption/withdraw function that reverts with a hard-coded "zero" check even though the user is still owed value in a different asset, causing total loss of the position. The closest reachable analog in `ocore` is in the **AA (Autonomous Agent) message-composition engine** itself, not in a specific oscript sample: `aa_composer.js` silently drops any `payment` message whose output rounds down to zero, while `state` messages (which mutate AA vars, e.g. burning share/asset balances) are still executed and committed. Any AA author who implements a standard share/LP-redemption pattern (present as an official example in `test/samples/uniswap_like_market_maker.oscript`) is exposed to fund loss: a trigger sender who redeems a small number of shares against a much larger pool can end up with a computed payout of `0` for one or both assets, the payment message is dropped, but the burn of shares (state var update) still executes — the sent asset is consumed by the AA and nothing is returned.

### Root cause

`aa_composer.js` builds `messages` from the AA template, then: [1](#0-0) 

filters out any payment output that computed to exactly zero, and drops the whole payment message if all its outputs became zero. If **all** messages end up empty this way, the code explicitly treats it as a no-op response and still performs state changes: [2](#0-1) 

The comment `// eat the received coins and send no response, state changes are still performed` documents the exact hazard: the framework provides no atomicity guarantee tying a `payment` message's actual (non-zero) delivery to the `state` message's variable mutations that logically depend on that delivery. This is functionally identical to the Dopex root cause, where `assets = shares.mulDivDown(totalCollateral(), supply)` truncated to zero and the transaction reverted after already being economically owed — here, the AA does not even revert; it accepts the deposit/redemption and mutates state, but the payout silently vanishes.

The framework-level unit test confirms this exact mechanic is intended/expected behavior of the engine, not a corner-case oversight: [3](#0-2) 

### Concrete exploitable pattern

The bundled reference AA template for share-based redemption issues a *payment* message computed from a ratio and a separate *state* message that decrements the outstanding-shares counter in the same trigger response: [4](#0-3) 

If `round($investor_share * balance[$asset])` (or the paired bytes payout) evaluates to `0` — which happens whenever a small number of shares are redeemed against a large asset balance, or after balance[$asset]/balance[base] has been mostly depleted, e.g. by the counterpart asset losing effectively all its value (directly mirroring the Dopex RDPX-price-collapse scenario) — the corresponding `payment` message is silently removed by the `aa_composer.js` filter at lines 1274-1281, while `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]` still executes, permanently burning the depositor's/redeemer's share tokens with zero compensation, and the bytes/asset sent in the triggering unit remain trapped inside the AA.

### Impact

An unprivileged AA trigger sender following any of ocore's own documented redemption/LP patterns can lose their entire deposited asset with no recourse: the AA accepts the funds, burns the internal accounting entry that represents the sender's claim, and returns nothing, because the payment output rounded to zero and was dropped by the message-filtering logic rather than causing the whole response to fail atomically. This is AA fund loss/freezing for the depositor, directly analogous to the confirmed Medium-severity Dopex finding.

### Recommendation

The AA engine should either (a) treat a zero-computed payment output inside a message that is logically paired with irreversible state mutations as a bounce condition rather than silently dropping the message and continuing, or (at minimum) document prominently that `state` and `payment` messages in the same response are not atomic with respect to zero-output filtering, and provide oscript authors a built-in guard (e.g., a `require`-equivalent) to bounce when a computed payout output would round to zero, mirroring the recommended fix in the Dopex report (bounce unless the total payout across all denominations is non-zero).
