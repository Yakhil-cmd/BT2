### Title
Webhook signature verified against `repository.owner.login`/`organization.login` but the event is applied to whatever `repository.full_name` the payload claims - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which configured GitHub App/organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, taken from `params.dig('repository','owner','login')` (or `organization.login` as fallback). Once the signature check passes, the raw payload is dispatched unmodified to the event handlers, which independently resolve the target repository/stack from `payload.dig('repository','full_name')`. Nothing ties these two fields together, so a payload can be crafted where the "owner" used for signature verification and the "full_name" used to locate the stack that gets acted upon refer to two different organizations. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This engine supports being configured with multiple independent GitHub organizations, each with its own `webhook_secret`, via `Shipit.github_app_config`/`Shipit.github(organization:)`. [4](#0-3) 

`verify_signature` looks up which org's secret to verify against purely from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`), not from any authenticated channel:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

After the signature is accepted, `create` hands the same raw, attacker-supplied JSON to the registered handler for the event type:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

Every handler resolves the repository/stack it acts on from a *different* JSON field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses this to call `stack.sync_github(expected_head_sha: params.after)` on every matching stack, and `StatusHandler` uses `Commit.where(sha: params.sha)` (no repository scoping at all) to attach an arbitrary CI status to any commit sha in the database. [7](#0-6) [8](#0-7) 

The binding that should hold is: **organization whose secret authenticated the request == organization/repository the event is applied to**. Because `repository_owner` (verification key) and `repository.full_name` (action key) are read from two independent, unauthenticated fields of the same JSON body, an attacker who legitimately controls one configured organization's webhook secret (e.g., their own GitHub App installation registered in Shipit's `secrets.github`) can forge a payload where `repository.owner.login` names *their own* org (so the signature check passes with their own secret) while `repository.full_name` names a *victim* organization's repository that is actually tracked by Shipit. The signature check has no way to detect this mismatch, since it never looks at `repository.full_name`.

- Before the attacker's crafted request: HMAC verification org == acted-upon repository org, by construction of genuine GitHub webhooks (GitHub always signs the payload it generated, and `owner.login` and `full_name`'s owner segment are consistent).
- After the attacker's crafted request: HMAC verification org (attacker's own org, whose secret they know) != acted-upon repository org (victim org named in `full_name`), yet the request is accepted and processed as if it were a legitimate GitHub-originated event for the victim repository.

### Impact Explanation
This lets an unprivileged attacker (someone who merely controls their own configured GitHub App/webhook secret in a multi-org Shipit deployment, with no access to the victim org, no `ApiClient` token, and no repository write access to the victim) inject forged CI status and push events for a victim's tracked stack:
- Via `StatusHandler`, they can post an arbitrary `success` status for any commit sha already known to Shipit, on any repository, unscoped by owner, satisfying required CI checks and enabling continuous-delivery/merge-queue flows to proceed on unreviewed commits — an unauthorized deploy/merge path.
- Via `PushHandler`, they can force `sync_github(expected_head_sha:)` with an attacker-chosen sha for any branch on any tracked stack, influencing what Shipit considers the deployable head.

This crosses the "organization that authenticated versus the repository that is written" trust boundary called out as an acceptable analog, and its consequence (bypassing CI/status gating to enable deploys/merges on a repository the attacker does not control) matches the Critical/High impact bar for an unauthorized deploy or merge.

### Likelihood Explanation
Requires only that the deployment configure more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml` showing two orgs each with independent `webhook_secret`s) and that the attacker legitimately controls one of them. [9](#0-8)  No GitHub App private key, TLS interception, or session/token theft is needed — only knowledge of the attacker's own webhook secret and the ability to POST directly to the public `/webhooks` endpoint, which is exactly what `WebhooksController` exposes. [10](#0-9) 

### Recommendation
Verify the signature using the same field the handlers use to locate the target repository (`repository.full_name`'s owner segment, or equivalently ensure `repository.owner.login` and `repository.full_name` are consistent) before dispatch, and reject the request if they diverge. Alternatively, resolve the target `Stack`/`Repository` first and use its known organization to select the webhook secret and to authorize the handler, rather than trusting two independently-read fields from an unauthenticated payload.

### Proof of Concept
1. Deploy Shipit configured with two orgs in `secrets.github`: `attacker-org` (attacker controls/knows its `webhook_secret`) and `victim-org` (has a tracked `Stack` for `victim-org/victim-repo`).
2. Attacker crafts a JSON payload for the `status` event:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim-commit-sha>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and the signature matches, so verification succeeds. [11](#0-10) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, attaching a forged `success` status to the victim's commit, unscoped by organization. [8](#0-7) 
6. If `victim-org/victim-repo`'s stack has continuous delivery/merge queue enabled and gated on that CI context, the forged status can unblock an automatic deploy/merge the attacker does not have access to trigger legitimately.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
