### Title
Unauthenticated webhook signature bypass lets an attacker forge `membership` events to grant themselves `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit.github(organization:).verify_webhook_signature` is a no-op whenever no `webhook_secret` is configured for that organization, and `webhook_secret` is explicitly documented as *optional*. When it is unset, `WebhooksController#verify_signature` accepts any payload with any (or no) `X-Hub-Signature`, so an unauthenticated network attacker can POST directly to `/webhooks` and have Shipit treat the payload as an authentic GitHub event.

### Finding Description
`WebhooksController#verify_signature` derives the org from the untrusted payload and asks the corresponding `GithubApp` to verify the signature: [1](#0-0) 

The verification itself is a pass-through when no secret is configured: [2](#0-1) 

`webhook_secret` is documented in `docs/setup.md` as **optional** (`- Webhook secret (optional): Fill it with some randomly generated string...`), and the shipped `template.rb` / example secrets files leave it blank by default — i.e., running with no secret is a supported, documented configuration, not a deviation from documented deployment.

With no secret configured, `create` dispatches attacker-supplied JSON straight to the registered handlers, no credential of any kind required: [3](#0-2) 

One of the default handlers is `MembershipHandler`, which creates/updates `Team` and `Membership` records purely from payload fields (`team.id`, `organization.login`, `member.login`) with no additional validation against real GitHub state: [4](#0-3) 

`Team#add_member` blindly appends the resolved `User` to the team: [5](#0-4) 

This directly feeds `User#authorized?`, which is the single gate that `Shipit::Authentication#force_github_authentication` uses to allow access to the whole application: [6](#0-5) [7](#0-6) 

**The broken binding:** the organization Shipit believes it "authenticated" the webhook against (via `verify_webhook_signature`) is supposed to equal the organization whose team membership is written to the database. When `webhook_secret` is absent (a documented, supported configuration), that equality collapses to "any unauthenticated sender = any organization," so the org-authentication step provides zero assurance for the `membership` event's side effects.

### Impact Explanation
An attacker who already has (or creates) a Shipit `User` record (e.g., by visiting `/github/auth/github` once and completing OAuth login, which requires no team membership by itself) can forge a `membership` `added` event naming their own GitHub login as `member` and any configured `Shipit.github_teams` team as `team`. This adds a `Membership` row that satisfies `User#authorized?`, escalating an ordinary logged-in user into the `Shipit.github_teams` authorization gate without ever actually belonging to that GitHub team. This matches the explicitly listed High-severity impact: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
The `webhooks` endpoint is unauthenticated by design (it must accept unsolicited POSTs from GitHub) and reachable by anyone who can send an HTTP request to the host. The only thing preventing forgery is `webhook_secret`, which the project's own setup documentation marks as optional. Any Shipit deployment run per the documented "optional" setting (or one where the secret leaked/rotated without matching the payload) is exposed. The attacker only needs a valid Shipit `User` (obtained by a single OAuth login, which itself doesn't require team membership) to benefit from the escalation.

### Recommendation
- Make `webhook_secret` mandatory (fail to boot / refuse to process webhooks if absent) rather than silently trusting unsigned payloads.
- Do not let the `membership` webhook resolve `organization`/`team` purely from client-controlled payload; cross-check against `GithubHook`-registered organizations and, ideally, verify team membership via the GitHub API rather than trusting the webhook body outright.
- Log/alert loudly (not just at `info`) whenever webhook processing occurs without a configured secret, since it is effectively unauthenticated ingestion of privileged state changes (team membership, review-stack lifecycle, etc.).

### Proof of Concept
1. Deploy Shipit per the documented example configuration with `github.webhook_secret` left blank (as shown in `config/secrets.development.example.yml` / `template.rb`).
2. Log in once via `/github/auth/github` as attacker's own GitHub account to create a Shipit `User` record (no team membership required for the OAuth flow itself).
3. POST directly to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Required Team", "slug": "required-team", "url": "https://example.com" },
  "organization": { "login": "the-configured-org" },
  "member": { "login": "attacker-login" }
}
```
No valid `X-Hub-Signature` is required because `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank.
4. `MembershipHandler#process` creates the `Team` (if unknown) and appends the attacker's `User` as a member via `Team#add_member`.
5. `User#authorized?` now returns `true` for the attacker for any controller gated by `Shipit.github_teams`, granting full application access despite the attacker never having real GitHub membership in that team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
