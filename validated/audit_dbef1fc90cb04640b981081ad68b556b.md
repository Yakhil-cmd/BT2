### Title
Unbounded oscript/ojson formula parsing enables CPU-exhaustion DoS during AA definition/unit validation - (File: formula/validation.js, formula/evaluation.js, formula/grammars/oscript.js)

### Summary
CVE-2025-21500 is a MySQL Optimizer bug where a low-privileged, network-reachable request causes the server to hang or crash (pure availability impact, no confidentiality/integrity loss). The analogous weakness in ocore is that any unprivileged unit poster can embed an attacker-crafted `oscript`/`ojson` formula string (in an AA definition, an AA trigger's `if`/output formulas, or asset condition) that is fed into the `nearley` Earley parser with no cost/size accounting prior to parsing, and no execution-time limit on the parse itself. Because all `MAX_OPS`/`MAX_COMPLEXITY`/depth guards in `formula/validation.js` and `formula/evaluation.js` are only enforced while walking the already-produced AST, a pathologically ambiguous or deeply-nested formula can make the underlying Earley parser itself consume excessive CPU/memory before any of those protections ever run, causing every full node that validates the posted unit to hang or crash.

### Finding Description
When a unit containing an AA definition or trigger with an oscript formula is validated, the formula text is parsed with `nearley.Parser` before any op/complexity accounting takes place:

<cite repo="Jaredbentat/ocore--019" path="formula/validation.js" start="249="266"/> [1](#0-0) 

The same unmetered pattern occurs in the evaluator used at AA-trigger time: [2](#0-1) 

All existing safety limits (`MAX_OPS`, `MAX_COMPLEXITY`, call-stack-depth interruption via `setImmediate`, `MAX_AA_STRING_LENGTH` for string values) are applied only to nodes of the **already parsed** AST during `evaluate()`: [3](#0-2) [4](#0-3) 

None of them bound the cost of the `nearley.Parser.feed()` call itself, and the oscript grammar (`formula/grammars/oscript.js`, generated from `formula/grammars/oscript.ne`) contains many overlapping alternative productions (e.g. the `N` non-terminal, `local_var_assignment` selector loop, array/dictionary/pair ambiguities) that are exactly the conditions under which Earley parsing degrades from its typical near-linear behavior toward worst-case cubic time and, if the grammar admits multiple parses for a crafted prefix, toward exponential result-set construction — the parser explicitly checks for and rejects `parser.results.length > 1` only *after* parsing completes: [5](#0-4) [6](#0-5) 

There is no upstream bound on the formula string's length or structure before it reaches the parser — `getFormula()` only strips the surrounding braces and performs no size/complexity pre-check: [7](#0-6) 

The only global size constraint an attacker is subject to is the overall unit size cap (`MAX_UNIT_LENGTH`, 5,000,000 bytes) and the generic nesting/node-count guard `isTooDeeplyNestedOrHasTooManyNodes` (100 depth / 10,000 nodes) applied to the *joint JSON structure*, not to the length or shape of any individual formula string: [8](#0-7) [9](#0-8) 

Neither of these limits prevents a single string field up to megabytes in size from containing a pathological expression (e.g., deeply right/left-nested arithmetic, chained ternaries, or ambiguity-inducing token sequences) that is expensive for the Earley parser to process, since the guard only counts JSON object/array nodes, not characters inside string leaves.

### Impact Explanation
Any unprivileged party able to post a unit (register an AA definition, or send a trigger to an existing AA whose definition evaluates a formula supplied via trigger data, e.g. `local_var_expr`, `if` conditions in AA definitions, or asset-definition formulas) can force every full node that receives and validates that unit to spend excessive CPU time — or exhaust memory building an ambiguous parse forest — while parsing the formula, before the interpreter-level `MAX_OPS`/`MAX_COMPLEXITY` guards ever engage. Because unit validation runs under a mutex per author address and blocks the validation pipeline (`validation.js`'s `validate()`), a hang here can stall a node's ability to validate and gossip new units, which is the availability-impact analog of "hang or frequently repeatable crash" described in the CVE: nodes become unable to keep confirming/propagating units while stuck parsing the malicious formula, and the same crafted unit will similarly stall every other honest node that later validates it, giving a network-wide, repeatable denial of confirmation.

### Likelihood Explanation
Posting a unit (including one defining a new AA or invoking an oscript formula path) is a normal, permissionless operation available to any address holding a small amount of bytes to pay for unit size — matching the CVE's "low privileged attacker with network access." No special role (hub, witness, operator) is required, and the trigger path is reachable purely through consensus validation of user-submitted content, which happens automatically for every node.

### Recommendation
- Add a hard length/complexity pre-check on formula strings (similar in spirit to `MAX_AA_STRING_LENGTH`) before handing them to `nearley.Parser.feed()`, rejecting formulas above a safe size threshold.
- Wrap `parser.feed()` calls in `formula/validation.js` and `formula/evaluation.js` with a wall-clock or step budget (e.g., abort/measure via `nearley`'s incremental `feed` API) so pathological/ambiguous inputs cannot consume unbounded parse time.
- Audit `formula/grammars/oscript.ne` for rules that permit genuine ambiguity (multiple derivations for the same token sequence) and tighten them to remove ambiguity at the grammar level, reducing worst-case Earley blowup.
- Consider bounding raw formula-string length independent of overall unit size and depth/node counters, since `isTooDeeplyNestedOrHasTooManyNodes` does not inspect the internal structure of string leaves.

### Proof of Concept
Construct an AA definition (or trigger `if`/output formula) whose formula text is a long chain of arithmetic/ternary/concatenation operators crafted to maximize shared-prefix ambiguity for the oscript grammar, e.g. deeply nested combinations of `otherwise`/ternary/or/and operators up to the multi-hundred-KB range permitted by `MAX_UNIT_LENGTH`. Post this as a unit; every full node that calls `aa_validation.js`'s `validateAADefinition` → `validateFormula` → `formula/validation.js`'s `nearley.Parser.feed(formula)` will spend disproportionate CPU/memory before validation's `MAX_OPS`/`MAX_COMPLEXITY` checks ever run, stalling that node's validation pipeline for the duration of the parse.

function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
