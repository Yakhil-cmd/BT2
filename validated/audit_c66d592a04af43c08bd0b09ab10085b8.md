### Title
Sybil-splitting a stacker's bond across two `signer_key`s wins two largest-remainder slots instead of one in `pox_5_make_signer_set` - (File: stackslib/src/chainstate/nakamoto/signer_set.rs)

### Summary
`pox_5_make_signer_set` aggregates `amount_ustx` per `signer_key` (not per staker) and runs a largest-remainder ("Hare") round that hands +1 weight to at most one slot per distinct key. Because the aggregation key is the signer key rather than staker identity, a staker who registers two signer keys for the same locked stake can capture two leftover slots instead of the single slot a lone key would receive, as long as the split remainders don't overflow the threshold when recombined.

### Finding Description
The equality that should hold is: for a staker whose total locked `amount_ustx` is `S`, `sum(weight over that staker's signer key(s)) == floor(S / threshold) + at most 1` (one leftover unit, per the invariant already encoded in `check_make_signer_set`, see `stackslib/src/chainstate/nakamoto/tests/signer_set.rs` lines 118-139 and 141-158).

The implementation in `pox_5_make_signer_set` (`stackslib/src/chainstate/nakamoto/signer_set.rs` lines 822-937) builds a `HashMap` keyed by `signer_key` (lines 829-856), computes per-key `weight = stacked_amt / threshold` and `remainder = stacked_amt % threshold` (lines 882-890), then sorts *all* entries (across every distinct signer key in the whole reward cycle) by descending remainder and hands `+1` to the top `leftover` entries, unconditionally, even to zero-remainder entries once positive-remainder candidates are exhausted (lines 896-911).

Because `floor(a/T) + floor(b/T) <= floor((a+b)/T)`, a staker can pick a split `A = S1`, `B = S2` such that `r1 = S1 mod T` and `r2 = S2 mod T` satisfy `r1 + r2 < T` — which guarantees the base-weight sum for the split equals the base weight of a single combined key (no loss from splitting), while both `r1` and `r2` are individually large enough to outrank other entries' remainders in the global leftover round. If the whole cycle's global `leftover >= 2` (which happens whenever `reward_slots - sum(floor(amt/T))` over all cycle participants is `>= 2` — routine, since it is exactly the mechanism the comment at lines 858-871 says exists to avoid degenerate all-zero rounding), the attacker's two split entries can each win one of those slots, taking weight `floor(S/T) + 2` versus the `floor(S/T) + 1` maximum a single key could ever get.

Concrete reproduction (mirroring the harness in `stackslib/src/chainstate/nakamoto/tests/signer_set.rs`): with `reward_slots = 10`, `threshold = 100`, 8 filler signers each staking exactly `100` (`base=8`, zero remainder), and the attacker staking `Y = 99` (`< threshold`, so `base = 0`):
- Single key: `weight = floor(99/100) = 0`, `remainder = 99` — wins the sole highest-remainder slot in a `leftover = 2` round → final weight `1`.
- Split into `A = 50` (`remainder 50`) and `B = 49` (`remainder 49`), same total `99` and same combined base `0` (`50 + 49 = 99 < 100`, no floor loss): both `A` and `B` outrank the filler's zero-remainder entries and each independently win one of the two leftover slots → `A.weight = 1`, `B.weight = 1`, combined attacker weight `2`.

The attacker doubles their signing weight for the same locked stake. Nothing in the code checks staker identity when apportioning the leftover round; only `signer_key` uniqueness is deduplicated (line 852-855), so two keys belonging to the same staker are treated as independent apportionment candidates. The existing per-entry test invariant (`weight in {base, base+1}`, lines 150-158 of the test file) is satisfied for *each individual key*, which is why this slips past `check_make_signer_set`'s current assertions — none of them sum weight across keys known to belong to the same underlying staker.

### Impact Explanation
This grants a staker signing weight (and implicitly reward-slot allocation, since `.signers` weight drives block-signing thresholds) that exceeds what their actually-locked uSTX would earn under a single signer key — "signing weight or reward slots exceeding locked value," matching the High-severity category in scope. Because weights sum to a fixed budget (`reward_slots`), the extra unit an attacker gains is stolen from the fair share of other honest signers in the same cycle (someone who would otherwise have won that leftover slot loses it). This is repeatable every reward cycle in which the attacker restakes with two (or more) keys and the global leftover count in that cycle is `>= 2`, which is a common, attacker-observable condition (attacker can simply not exploit in cycles where it's unfavorable, and exploit only when advantageous).

### Likelihood Explanation
Preconditions: the attacker needs (1) the ability to register/stake under two distinct signer keys for the same underlying locked value — ordinary stacking/delegation flexibility already allows choosing an arbitrary signer key per stacking action, so this needs no privileged access; (2) the ability to choose the exact split amounts, which the attacker fully controls since it's their own stake; (3) a reward cycle where the global leftover (`reward_slots - sum of floors`) is `>= 2`, which the attacker can observe from public on-chain `.signers`/pox-5 state before submitting their stacking transactions each cycle, and either wait for or engineer by staking a specific amount into the pool. No privileged role, no cross-account interaction, and no protocol violation is required — only splitting one's own locked stake across two owned keys and choosing amounts precisely, which is fully within an unprivileged staker's control.

### Recommendation
Aggregate for the largest-remainder round by the underlying staker/committer identity (or cap total leftover slots awarded per staker/principal to 1) rather than purely by `signer_key`, or alternatively track and reconcile per-stacker locked totals against the sum of weights awarded across all signer keys registered by that stacker, rejecting/adjusting apportionments where the same staker's combined weight would exceed `floor(combined_stacked/threshold) + 1`.

### Proof of Concept
Extend `check_make_signer_set` in `stackslib/src/chainstate/nakamoto/tests/signer_set.rs` with a fixed unit test:
```rust
#[test]
fn splitting_stake_across_two_keys_wins_extra_leftover_slot() {
    let pox_constants = test_pox_constants(?); // configured so reward_slots() == 10
    // 8 fillers @ 100 each => base 8, zero remainder
    let mut entries: Vec<_> = (0..8u8)
        .map(|i| RawPox5Entry { signer_key: signer_key(i), amount_ustx: 100 })
        .collect();

    // Baseline: single attacker key with 99
    let mut single = entries.clone();
    single.push(RawPox5Entry { signer_key: signer_key(200), amount_ustx: 99 });
    let mut it = single.into_iter().map(Ok);
    let baseline = NakamotoSigners::pox_5_make_signer_set(&mut it, &pox_constants).unwrap();
    let baseline_weight: u128 = baseline.signer_set.iter()
        .filter(|e| e.signing_key == signer_key(200))
        .map(|e| u128::from(e.weight)).sum();
    assert_eq!(baseline_weight, 1);

    // Split: same 99 total across two attacker-controlled keys
    let mut split = entries.clone();
    split.push(RawPox5Entry { signer_key: signer_key(201), amount_ustx: 50 });
    split.push(RawPox5Entry { signer_key: signer_key(202), amount_ustx: 49 });
    let mut it2 = split.into_iter().map(Ok);
    let split_out = NakamotoSigners::pox_5_make_signer_set(&mut it2, &pox_constants).unwrap();
    let split_weight: u128 = split_out.signer_set.iter()
        .filter(|e| e.signing_key == signer_key(201) || e.signing_key == signer_key(202))
        .map(|e| u128::from(e.weight)).sum();

    // Violates: sum(weight of attacker's keys) == floor(99/threshold) + at most 1
    assert!(split_weight > baseline_weight + 0, "attacker gained {} vs baseline {}", split_weight, baseline_weight);
    assert_eq!(split_weight, 2); // demonstrates doubling vs. baseline's 1
}
```

    pub(crate) fn pox_5_make_signer_set<I>(
        entries: &mut I,
        pox_constants: &PoxConstants,
    ) -> Result<Pox5SignerSetOutput, ChainstateError>
    where
        I: Iterator<Item = Result<RawPox5Entry, PoxEntryParsingError>>,
    {
        let mut signer_set = HashMap::new();
        let mut total_ustx_locked = 0u128;
        for entry_res in entries {
            let entry = match entry_res {
                Ok(x) => x,
                Err(PoxEntryParsingError::Skip(err_str)) => {
                    warn!(
                        "Error while iterating PoX-5 entries, impacting a single entry. Dropping entry from signer set";
                        "error" => err_str
                    );
                    continue;
                }
                Err(PoxEntryParsingError::Abort(err_str)) => {
                    error!(
                        "Abort-triggering error while iterating PoX-5 entries";
                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
        }
