### Title
Webhook signature verification keys off an attacker-controlled organization field that is disjoint from the repository actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate a delivery against based on `repository_owner`, which is read straight out of the untrusted, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit's documented, supported configuration format lets an operator register several GitHub organizations at once, each with its own independent `webhook_secret` (which is explicitly optional / may be `nil`): [4](#0-3) 

Once the request clears `verify_signature`, `WebhooksController#create` dispatches the *entire* JSON body to the registered handlers, all of which resolve the target `Stack`/`Repository` using a **different** field of the same body — `repository.full_name` — completely independent of the `repository.owner.login` value used to pick the verification secret: [5](#0-4) [6](#0-5) 

This breaks the binding: `organization whose config authorized the request == organization that owns the repository being written to`. In a multi-org Shipit deployment, if even one configured organization has no `webhook_secret` set (a documented, supported state), signature verification for that organization is a no-op. An unprivileged, unauthenticated attacker can then POST directly to the public `/webhooks` endpoint (no session, no `ApiClient` token, no GitHub credentials required — `WebhooksController` does not include the `Authentication` concern used elsewhere, and `verify_authenticity_token` is explicitly skipped) with a forged JSON payload that sets `repository.owner.login` to the org lacking a secret (satisfying `verify_signature`) while setting `repository.full_name` to any *other* organization's repository/stack tracked by the same Shipit instance.

### Impact Explanation
Because `PushHandler`, `StatusHandler` and `CheckSuiteHandler` all resolve their target via `repository.full_name` with no cross-check against the organization used for authentication, the attacker can, for a completely unrelated victim repository/stack:
- Fire `push` events that make Shipit believe new commits landed and enqueue `GithubSyncJob` for the victim stack, or
- Fire `status` events that call `Commit#create_status_from_github!`, letting the attacker fabricate CI/status records that Shipit's deploy-safety checks rely on, or
- Fire `check_suite` events to trigger check-run refreshes for the victim stack.

Depending on how the victim stack's `shipit.yml` CI requirements are satisfied via these forged statuses/commits, this can contribute to bypassing deploy-safety gating on a stack the attacker has no legitimate relationship with, i.e., a step toward an unauthorized deploy — which matches the "unauthorized deploy" Critical impact category. I was not able to fully trace, within the remaining budget, whether forged `status` events alone are sufficient to flip a stack's `deployable?` state to green (that logic lives in `Shipit::Stack`/`Shipit::DeploySpec`/`Shipit::Status::Group`, which I located but did not have iterations left to read in full) — this final link should be verified before treating this as a confirmed "unauthorized deploy," but the authentication/authorization confusion itself (organization used to authenticate vs. repository being mutated) is concretely demonstrated in the code above.

### Likelihood Explanation
The precondition (one org among several configured without a `webhook_secret`) is explicitly documented as an acceptable/optional configuration, not a misconfiguration outside the engine's documented deployment model, so it is realistic for a legitimate multi-tenant Shipit instance. Once that precondition holds, exploitation requires only a single unauthenticated HTTP POST with a crafted JSON body — no secrets, tokens, or GitHub access of any kind.

### Recommendation
`verify_signature` should not use attacker-supplied data to select which secret proves the attacker's authority; and regardless, handlers must verify that the organization used to authenticate the webhook matches the owner segment of `repository.full_name` (or better, resolve the target `Stack`/`Repository` first and check that its owning organization equals the one whose secret validated the request) before allowing any handler to mutate state for that repository.

### Proof of Concept
Given a Shipit instance configured with two organizations, e.g.:
```yaml
github:
  loose-org:
    app_id: ...
    installation_id: ...
    webhook_secret: # nil, none configured
  victim-org:
    app_id: ...
    installation_id: ...
    webhook_secret: "s3cr3t"
```
and `victim-org/victim-repo` tracked as a Shipit stack, an unauthenticated attacker sends:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "loose-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` calls `Shipit.github(organization: "loose-org")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) `X-Hub-Signature` header [7](#0-6) . The request then reaches `PushHandler#process`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` [8](#0-7)  and enqueues a sync for that stack, entirely outside of any credential belonging to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
