### Title
Ranked-collective `remove_member`/`demote_member` don't purge or reweight prior `vote()` records, letting a demoted/removed member's stale voting power keep influencing an ongoing poll's `Tally` - ([File: substrate/frame/ranked-collective/src/lib.rs])

### Summary
`pallet-ranked-collective` records a member's vote weight into `Voting<T,I>` and into the poll's `Tally` at the time `vote()` is called, using the member's *rank at that moment* [1](#0-0) . When that same member is later demoted or removed from the collective via `demote_member`/`remove_member`, neither call touches the `Voting` storage map or recomputes the affected `Tally` entries; `do_remove_member_from_rank` only prunes `Members`, `MemberCount`, `IdToIndex`, and `IndexToId` [2](#0-1) . This is directly analogous to the reported Gitcoin `QVSimpleStrategy` bug: flipping an actor's "allowed" status (rank/membership) does not revoke the influence of allocations (votes) they already cast.

### Finding Description
- Any account with at least the class's minimum rank can call `vote(origin, poll, aye)` on an ongoing poll; this is a normal, unprivileged, signed-extrinsic entry point available to every ranked member [3](#0-2) .
- Inside `vote`, the member's current rank is converted into vote weight via `Self::rank_to_votes(record.rank, min_rank)`, and that weight is folded into `tally.ayes`/`tally.nays`/`bare_ayes`, then the `VoteRecord` (weight) is persisted in `Voting::<T, I>::insert(&poll, &who, &vote)` [4](#0-3) .
- If the same member votes again, the *previous* recorded weight (from `Voting::<T,I>::get`) is subtracted before the new weight is added — but this reconciliation only happens on a fresh `vote()` call by that member, never automatically [5](#0-4) .
- `remove_member` (governance-gated by `RemoveOrigin`) calls `do_remove_member_from_rank`, which removes the account from `Members`/`IdToIndex`/`IndexToId` for each rank down to 0, but never iterates `Voting` for ongoing polls and never mutates any `Tally` to strip out the member's prior contribution [6](#0-5) [2](#0-1) .
- The only pruning mechanism that touches `Voting` is `cleanup_poll`, which is explicitly gated on the poll having already ended (`T::Polls::as_ongoing(poll_index).is_none()`) — it cannot and does not run against ongoing polls, so it offers no remedy while a poll (and its stale vote) is still active [7](#0-6) .
- By contrast, `pallet-collective` explicitly designed and tested for this exact class of bug: `ChangeMembers::change_members_sorted` walks every open `Proposals` entry and filters `outgoing` accounts out of `ayes`/`nays` the moment membership changes [8](#0-7) , with a dedicated regression test `removal_of_old_voters_votes_works` proving stale votes are purged [9](#0-8) . `pallet-ranked-collective` has no equivalent hook for `Voting`/`Tally` on rank change or removal, despite `prdoc/1.5.0/pr_2591.prdoc` showing that "Ensure to cleanup state in `remove_member`" was previously addressed only for the membership index maps, not for in-flight poll votes.

### Impact Explanation
Because `Tally` values (bare_ayes/ayes/nays) computed from stale, higher-rank vote weights are used directly to decide whether a poll (referendum) passes — e.g., FellowshipCollective/AmbassadorCollective tallies feeding OpenGov-style referenda tracks in the runtimes that configure this pallet — a member who is demoted or removed mid-poll continues to exert their pre-demotion voting weight on that poll's outcome until the poll concludes. This breaks the intended invariant that voting power should track current rank/membership, and can let disproportionate, no-longer-authorized influence swing an in-flight decision (e.g., approving/rejecting a promotion, demotion, or other fellowship-governed action) in a way current membership rules were supposed to prevent.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a member voting on an active poll, and (b) governance (via `RemoveOrigin`/`DemoteOrigin`) or an automated mechanism such as `pallet-core-fellowship`'s inactivity-based demotion to change that member's rank/membership before the poll ends. Both are realistic, expected chain operations (fellowship polls commonly run for extended periods while membership churn/demotions also occur), so the window for this to matter is not contrived; however it needs a specific race between an open poll and a rank change to manifest as a visible integrity break.

### Recommendation
On `demote_member`/`remove_member` (and any rank change), iterate the caller's outstanding `Voting` entries for currently-ongoing polls and either remove the vote or reduce the `Tally` by the delta between the old and new weight, mirroring what `pallet-collective::change_members_sorted` already does for `Proposals`/`Voting`. Alternatively, disallow rank reduction/removal while the account holds unresolved votes on ongoing polls, or expose a permissionless "reconcile vote weight" extrinsic that can be called against any member whose rank has changed, similar in spirit to `cleanup_poll` but usable while the poll is still ongoing.

### Proof of Concept
No executable PoC was run; this is a static-analysis finding derived from code inspection under ask-only mode. The reasoning trail establishing the gap:
1. `vote()` persists rank-derived weight into `Tally` and `Voting` [4](#0-3) .
2. `remove_member`/`do_remove_member_from_rank` never touch `Voting`/`Tally` [6](#0-5) [2](#0-1) .
3. `cleanup_poll` cannot run on an ongoing poll [10](#0-9) .
4. The sibling pallet-collective explicitly guards against exactly this scenario, confirming the absence of an analogous guard in ranked-collective is a real gap rather than intended behavior [8](#0-7) .

I was not able to fully verify within the available search scope whether any downstream runtime configuration (e.g., `pallet-core-fellowship` or `pallet-referenda`'s `Polls` implementation) independently recomputes tallies from current membership at decision time, which would neutralize this gap; a Devin session with full repository/build access would be needed to trace `T::Polls` implementations (e.g., `pallet-referenda`'s `ReferendumInfoFor`) end-to-end and confirm no such reconciliation exists before treating this as bounty-eligible.

		pub fn vote(
			origin: OriginFor<T>,
			poll: PollIndexOf<T, I>,
			aye: bool,
		) -> DispatchResultWithPostInfo {
			let who = ensure_signed(origin)?;
			let record = Self::ensure_member(&who)?;
			use VoteRecord::*;
			let mut pays = Pays::Yes;

			let (tally, vote) = T::Polls::try_access_poll(
				poll,
				|mut status| -> Result<(TallyOf<T, I>, VoteRecord), DispatchError> {
					match status {
						PollStatus::None | PollStatus::Completed(..) => {
							Err(Error::<T, I>::NotPolling)?
						},
						PollStatus::Ongoing(ref mut tally, class) => {
							match Voting::<T, I>::get(&poll, &who) {
								Some(Aye(votes)) => {
									tally.bare_ayes.saturating_dec();
									tally.ayes.saturating_reduce(votes);
								},
								Some(Nay(votes)) => tally.nays.saturating_reduce(votes),
								None => pays = Pays::No,
							}
							let min_rank = T::MinRankOfClass::convert(class);
							let votes = Self::rank_to_votes(record.rank, min_rank)?;
							let vote = VoteRecord::from((aye, votes));
							match aye {
								true => {
									tally.bare_ayes.saturating_inc();
									tally.ayes.saturating_accrue(votes);
								},
								false => tally.nays.saturating_accrue(votes),
							}
							Voting::<T, I>::insert(&poll, &who, &vote);
							Ok((tally.clone(), vote))
						},
					}
				},
			)?;
			Self::deposit_event(Event::Voted { who, poll, vote, tally });
