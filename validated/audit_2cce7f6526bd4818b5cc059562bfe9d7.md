### Title
`provision?` ignores `review_stacks_enabled` for `prevent_with_label` repositories due to Ruby operator precedence - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` in `opened_handler.rb` intends every provisioning path to require `review_stacks_enabled`, but Ruby's `&&`/`||` precedence causes the `prevent_with_label` branch to be evaluated independently of that flag. Any repository configured with `provisioning_behavior: prevent_with_label` — even with `review_stacks_enabled: false` — will provision a `ReviewStack` (and trigger `provisioner.up`) for every PR that carries no labels, which is the default state of a freshly opened PR.

### Finding Description
The intended binding is: `review_stacks_enabled == necessary_precondition_for_any_provisioning`. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

In Ruby, `&&` has higher precedence than `||`, so this parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

The third disjunct — `prevent_with_label? && !has_label` — has no dependency on `review_stacks_enabled` at all. It is parenthesized only relative to its own two operands, not against the first clause. So for any `Repository` with `provisioning_behavior_prevent_with_label?` true, `provision?` returns `true` whenever the PR has no matching label, regardless of `review_stacks_enabled`.

An unprivileged attacker only needs to open a PR from a fork (or any repo they control) against a repository configured this way, with default (no) labels — which is the normal unlabeled state, not a privileged action. The webhook flows through `respond_to_pull_request_opened?` → `provision?` → `true`, and `process` calls `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates a `ReviewStack` and immediately enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

The `ReviewStack` state machine then triggers `stack.provisioner.up` on the `deprovisioned -> provisioning` transition: [3](#0-2) 

No existing guard intercepts this: `verify_signature`/webhook signature checks only authenticate that the payload came from GitHub for *that* repository (an attacker who owns the repository can legitimately trigger real webhooks for their own repo), the `ExplicitParameters` schema only validates payload shape, and there is no additional check anywhere in `provision?`, `respond_to_pull_request_opened?`, or `ReviewStackAdapter` that re-verifies `review_stacks_enabled` before creating and provisioning the stack.

### Impact Explanation
Provisioning a `ReviewStack` invokes `stack.provisioner.up`, which runs the configured provisioning handler (e.g., Terraform or shell-based infrastructure automation) via `Command`/`PTY.spawn`-based execution for that repository. This means an attacker who merely opens an unlabeled PR against a repository that an operator believed was safe (because `review_stacks_enabled` is `false`) triggers real infrastructure provisioning and command execution on the Shipit host, matching the Critical category (execution triggered without proper authorization gate). The attack is repeatable per PR/branch on any repository configured with `prevent_with_label`, and is fully within the reach of an unprivileged repository owner or contributor opening PRs.

### Likelihood Explanation
Preconditions: the repository must use `provisioning_behavior: prevent_with_label` (one of three selectable behaviors, not the default `allow_all`/`allow_with_label`) — no other Shipit secret or role is needed. Given that configuration, exploitation cost is zero: an attacker opens a PR with no labels, which is the default, unprivileged state of a new PR. This is trivially repeatable and requires no elevated access, only reliance on operators believing `review_stacks_enabled: false` fully disables provisioning for that behavior — which the code does not honor.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three behavior clauses, e.g.:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
