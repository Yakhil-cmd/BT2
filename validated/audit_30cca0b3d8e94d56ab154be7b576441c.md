## Title
Webhook Signature Verified Against the `repository.owner.login` Field While Event Handlers Act on the Unverified `repository.full_name` Field, Enabling Cross-Organization Writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the strongest analog to the report's core bug class: a value that determines *which credential is trusted* (the GitHub App/organization whose `webhook_secret` is used to accept a payload) is not the same value that downstream code actually *acts on* (which repository/stack gets mutated). Just as the API3Market report describes a mismatch between "funds transferred" and "entity trusted to use them safely," here the "organization whose secret authenticated the request" and "the repository the payload claims to describe" are two independent, attacker-influenceable fields.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config (and therefore the HMAC `webhook_secret` used to validate `X-Hub-Signature`) using: [1](#0-0) [2](#0-1) 

i.e. `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

However, once the signature check passes, `Shipit::Webhooks::Handlers::Handler` (the base class used by `PushHandler`, `StatusHandler` (via `Commit.where(sha:)`), and all `PullRequest::*Handler`s) resolves the repository/stack to mutate using a **different** payload field: [3](#0-2) 

`repository_name = payload.dig('repository', 'full_name')`, fed into `Repository.from_github_repo_name`, which splits on `/` and does a case-insensitive lookup: [4](#0-3) 

`repository.owner.login` (used to pick the trusted signing key) and `repository.full_name` (used to pick the repository/stack acted on) are two independent JSON fields in the same payload. In a genuine GitHub-generated webhook they are always consistent, but nothing in `WebhooksController` or `Handler` enforces that `full_name`'s owner segment matches `repository.owner.login`. Since Shipit explicitly supports hosting multiple GitHub organizations behind one instance (see `docs/setup.md`, "Using Multiple Github Applications", and `lib/shipit.rb#github`), anyone who knows (or controls) the `webhook_secret` for **any one** of those configured organizations can sign an arbitrary raw JSON body with that organization's secret while setting `repository.full_name` to point at a stack belonging to a **completely different** organization/repository hosted on the same Shipit instance.

This breaks the binding: `organization whose secret authenticated the request == repository the handler writes to`. Concretely:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` on stacks matched by the forged `full_name` [5](#0-4) 
- `PullRequest::OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, etc. create/archive/unarchive review stacks belonging to the forged repository, using the org boundary only for signature acceptance, not for authorizing the mutation [6](#0-5) [7](#0-6) 
- `StatusHandler#process` writes commit statuses for any commit matching the forged `sha`, independent of which org's secret validated the payload [8](#0-7) 

### Impact Explanation
This is a cross-repository/cross-organization write from an attacker who only controls one tenant organization's webhook configuration on a shared Shipit instance — matching the report's theme that a trust boundary (secret A) is being relied upon to gate actions on assets belonging to a different party (org/repo B). It can archive/unarchive review stacks, force `GithubSyncJob` execution, and forge commit statuses on a victim organization's stacks, none of which the attacker's own GitHub App installation permissions should allow. It does not, by itself, exfiltrate `GITHUB_TOKEN`/`api_clients_secret`, achieve RCE, or bypass Shipit login/session auth — the concrete effects are limited to state mutation of `Repository`/`Stack`/`Commit`/`ReviewStack` records reachable via existing webhook handlers.

### Likelihood Explanation
Requires the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to know one tenant's `webhook_secret` — typically someone who configured that org's GitHub App, not a random unauthenticated internet user. This is a real but narrower precondition than a fully unauthenticated exploit, and the `webhook_secret` is explicitly marked optional/nil in Shipit's own example configs, meaning some deployments could disable signature checking entirely for one org and open the same cross-repo write path to any anonymous caller (`verify_webhook_signature` returns `true` unless a `webhook_secret` is set) [9](#0-8) .

### Recommendation
Enforce that the field used to select the verifying secret and the field(s) used by downstream handlers to identify the target repository are the same, and cross-check them explicitly: after selecting `github_app` from `repository_owner`, require that `repository.full_name`'s owner segment (case-insensitively) equals `repository_owner`/`organization.login` before dispatching to handlers, rejecting (422) any payload where they diverge.

### Proof of Concept
1. Shipit instance is configured with two GitHub Apps, one for org `attacker-org` (attacker knows/controls `webhook_secret_A`) and one for victim org `victim-org` hosting stack `victim-org/victim-repo`.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(webhook_secret_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and validates the signature against `webhook_secret_A` — it passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, matching real victim stacks, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on them — a write triggered on `victim-org`'s stack using only `attacker-org`'s secret.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
