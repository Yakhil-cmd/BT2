### Title
Stack-scoped API tokens can read task/deploy status of any stack via the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by `Shipit::Api::BaseController` and, in doing so, drops the `ApiClient#stack_id` scoping that every other API resource controller relies on to keep a token confined to the single stack it was issued for.

### Finding Description
`ApiClient` records can optionally be scoped to a single `stack` (`belongs_to :stack, optional: true`) [1](#0-0) . `BaseController#stacks` enforces this scope for every controller that inherits from it: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` resolves the requested `stack_id` param only within that scoped relation (`stacks.from_param!(params[:stack_id])`) [2](#0-1) . This is the binding the token is supposed to authorize: *the stack a token authorizes == the stack it can touch*.

`CCMenuController`, however, redefines `stack` to bypass this relation entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

This queries `Stack.from_param!` directly against the full `Stack` table, with no filtering by `current_api_client.stack_id`. `require_permission :read, :stack` [4](#0-3)  only checks that the token carries the `read:stack` permission string; it never checks which stack the token was created for (`ApiClient#check_permissions!` only compares operation/scope, not the object) [5](#0-4) .

Every other stack-nested API controller (`StacksController`, `TasksController`, `HooksController` via `stack_id`, etc.) uses the inherited, correctly-scoped `stack`/`stacks` methods [6](#0-5) , confirming CCMenuController's override is the outlier, not an intentional design choice. The existing test suite for `CCMenuController` only exercises the client that is unscoped (`authenticate!` uses the globally-permissioned `spy` fixture) [7](#0-6) , and never exercises the `here_come_the_walrus` fixture that is scoped to a single stack [8](#0-7)  against this endpoint, unlike `StacksController`'s test suite which explicitly verifies that "an api client scoped to a stack will only see that one stack" [9](#0-8) . This confirms the scoping gap is untested and unnoticed for this specific endpoint.

The CCMenu endpoint is also reachable via query-string token authentication (`?token=...`), a mechanism specifically designed for embedding in third-party CI dashboard tools, widening the practical exposure of any leaked/observed token [10](#0-9) ; the URL containing this token is even generated and stored via `CCMenuUrlController` for users to copy/paste into external tools [11](#0-10) .

### Impact Explanation
A token that was deliberately scoped to a single stack (e.g. handed out to embed in an external CI status dashboard for one project) can be replayed against `GET /api/stacks/:stack_id/ccmenu` for any other stack's `stack_id` in the installation, disclosing that stack's name, lock state, and latest deploy/rollback status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) [12](#0-11) . This is an unauthenticated-for-that-resource read of stack/deploy state belonging to repositories the token holder was never granted access to — matching the "High" bucket (unauthenticated read of stack state / deploy output) defined in scope.

### Likelihood Explanation
Exploitation requires only possession of any valid scoped `ApiClient` token with `read:stack` permission (the default/minimal permission set) and knowledge or guessing of another stack's `owner/name/environment` path — no privileged account, GitHub write access, or additional secret is needed beyond the token itself, which is exactly the class of credential this endpoint's own `token` query-param mechanism is designed to expose in third-party tools.

### Recommendation
Remove the `stack` override in `CCMenuController` (and its bespoke `Stack.from_param!` call) so it inherits `BaseController#stack`/`#stacks`, restoring the `current_api_client.stack_id` scoping used everywhere else:
```diff
- def stack
-   @stack ||= Stack.from_param!(params[:stack_id])
- end
```
Add a regression test using the `here_come_the_walrus` (stack-scoped) fixture requesting a *different* stack's `ccmenu` URL and asserting a `404`/`403`, mirroring the equivalent test already present for `StacksController`.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack: shipit` with only `read:stack` permission (fixture `here_come_the_walrus`).
2. As that client, request `GET /api/stacks/some-other-org/some-other-repo/production/ccmenu` (a stack the client was never scoped to), authenticating with Basic Auth or `?token=<here_come_the_walrus token>`.
3. Observe that `BaseController#stacks`/`#stack` would normally raise `ActiveRecord::RecordNotFound` (via `stacks.from_param!`) for a stack outside `current_api_client.stack_id`, but because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly, the request succeeds with `200 OK` and returns that other stack's CCMenu XML (`name`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`), as confirmed by the passing behavior of the existing `#show renders the xml` test pattern [13](#0-12)  when swapped to a stack outside the token's scope.

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
