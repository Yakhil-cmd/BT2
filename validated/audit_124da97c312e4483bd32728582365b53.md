### Title
Unbounded recursion depth in address/asset definition evaluation causes stack overflow - (File: `definition.js`)

### Summary
`definition.js`'s `evaluate()` functions used by `validateDefinition()` and `validateAuthentifiers()` — the code paths that validate address definitions, asset issue/transfer conditions, and authentifiers for every posted unit — recurse into nested boolean expressions (`and`, `or`, `not`, `r of set`, `weighted and`, `address`) with no explicit recursion-depth guard, unlike the sibling interpreters in the same codebase.

### Finding Description
`definition.js` implements two structurally similar recursive evaluators:
- `evaluate()` inside `validateDefinition()` [1](#0-0) , which recurses through `or`/`and`/`r of set`/`weighted and`/`not`/`address` nodes [2](#0-1) [3](#0-2) .
- `evaluate()` inside `validateAuthentifiers()`, which recurses the same way, including recursively re-evaluating nested/other-address definitions and definition templates [4](#0-3) [5](#0-4) .

Both functions only bound recursion via cumulative `complexity`/`count_ops` counters checked against `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` [6](#0-5) , and via `evaluate(arrDefinition, 'r', false, ...)` at the top level [7](#0-6) . There is no explicit `depth` counter or stack-unwinding interrupt (e.g. `setImmediate`) anywhere in this file.

This is in stark contrast to the two other recursive interpreters in the same codebase that process comparable untrusted, attacker-supplied nested structures:
- `formula/validation.js`'s `evaluate()` explicitly tracks `depth`, rejects formulas once `depth > 100`, and periodically defers via `setImmediate` every 100 recursive calls specifically "to avoid extra long call stacks to prevent Maximum call stack size exceeded" [8](#0-7) .
- `aa_validation.js`'s `validate()` enforces `MAX_DEPTH = 100` and also periodically yields via `setImmediate` [9](#0-8) [10](#0-9) .
- `formula/evaluation.js`'s runtime `evaluate()` also periodically yields via `setImmediate` [11](#0-10) .

The presence of `MAX_DEPTH`/`depth`-based guards with explicit "prevent Maximum call stack size exceeded" comments in the sibling formula and AA validators, but their total absence in `definition.js`, indicates the missing guard here is an oversight rather than an intentional design choice, and is the direct root cause analog to CWA-2024-005's "stack overflow via unbounded recursion" bug class.

Because JS's `async.eachSeries` executes its iteratee synchronously when the iteratee itself completes synchronously (as `evaluate()` does for pure boolean-tree cases with no DB round trip, e.g. deeply nested `not`/`and`/`or` chains), a definition composed of many nested boolean operators can drive the native JS call stack arbitrarily deep, bounded only by `MAX_COMPLEXITY`/`MAX_OPS`, not by an explicit stack-safety depth check.

### Impact Explanation
An attacker who controls the address definition of a co-author, the definition of an asset's `issue_condition`/`transfer_condition`, or a definition change referenced by a unit can craft a deeply nested boolean expression that is parsed and recursively evaluated by every full node validating that unit (via `validateDefinition`/`validateAuthentifiers`). If the recursion depth reachable before `MAX_COMPLEXITY`/`MAX_OPS` is exceeded is large enough to exceed V8's default call-stack limit, the validating node process crashes with "Maximum call stack size exceeded" while processing an ordinary, unprivileged unit. This is a Denial-of-Service against every node that attempts to validate/relay the unit, potentially causing network-wide disagreement or inability to confirm/relay new units containing the malicious definition — matching the "node unable to confirm new units" / "node disagreement on validity" impact classes.

### Likelihood Explanation
Likely: composing a valid unit with a deeply nested address definition (`and`/`or`/`not` chains) or asset condition is entirely within reach of any unprivileged unit poster or asset issuer, requires no special privileges, no consensus/quorum, and no p2p/node compromise — it is a pure single-unit crafting exercise that is validated by every peer as part of normal unit/asset processing.

### Recommendation
Add an explicit depth counter (mirroring `aa_validation.js`'s `MAX_DEPTH`/`depth` check and `formula/validation.js`'s `depth > 100` + periodic `setImmediate` yield) to both `evaluate()` functions in `definition.js` (`validateDefinition` and `validateAuthentifiers`), rejecting definitions whose evaluation nesting exceeds a safe bound and/or periodically unwinding the call stack via `setImmediate`, independent of the `MAX_COMPLEXITY`/`MAX_OPS` counters.

### Proof of Concept
Construct an address/asset definition consisting of deeply nested `['not', ['not', ['not', ... ['sig', {...}] ...]]]` (or nested `and`/`or` with the minimum 2 branches, one trivial) so that each nesting level costs only 1 unit of `complexity`/`count_ops` (well under `MAX_COMPLEXITY`/`MAX_OPS`) while nesting depth grows into the thousands. Use this as: (a) the definition of a co-author address referenced in a unit, or (b) the `issue_condition`/`transfer_condition` of a newly issued asset. When any node calls `validateDefinition`/`validateAuthentifiers` on this unit (`definition.js` lines 103-234, 646-820), the synchronous recursive `evaluate()` calls exhaust the JS call stack before the complexity/ops limits are reached, crashing the node process.
