### Title
Unhandled `throw Error` on malformed `seen` filter in address/AA definitions can crash node during unit validation - (File: definition.js)

### Summary
CVE-2021-2088 is a MySQL Server DML bug where a logged-in but otherwise unprivileged-for-crash-purposes user can send a crafted DML statement that causes the server process to hang or crash (availability-only impact, no confidentiality/integrity loss). The reachable analog in ocore is a synchronous `throw Error(...)` inside the address/AA-condition evaluator (`evaluate()` in `validateAuthentifiers`) that is invoked directly from unit-validation code, outside of any `try/catch`, so a single attacker-crafted address definition can crash the node process that evaluates it.

### Finding Description
In `definition.js`, the `'seen'` authentifier operator implementation checks the `what` field of the filter object and, if it is anything other than `'input'`/`'output'`, executes: [1](#0-0) 
This is a plain synchronous `throw`, not a callback error (`cb2(err)` / `cb(err)`) like every other validation failure in the same `evaluate()` switch statement. `evaluate()` is called recursively from `validateAuthentifiers`, which in turn is called from unit-validation flows such as `validateAuthor` in `validation.js`: [2](#0-1) 
Because the throw happens synchronously in the call stack that is triggered from `mutex.lock(...)`/`async.series(...)` callbacks in `validation.js`'s `validate()`, and not through the normal error-propagation callback (`cb`/`cb2`), it is not guaranteed to be caught by the surrounding `async` control flow the way a passed `err` argument would be. An uncaught exception thrown from deep inside a nested callback chain in Node.js normally propagates up as an unhandled exception and terminates the process (unless a top-level domain/`process.on('uncaughtException')` handler exists and swallows it, which I could not confirm is present for this exact call path).

An address definition (or AA base/child definition) containing `['seen', {what: 'anything-but-input-or-output', ...}]` is valid JSON and is only rejected at evaluation time (when `evaluate()` walks the definition tree while checking authentifiers for a spending unit or an AA trigger), not necessarily at definition-creation time — I was unable to confirm within available searches whether `validateDefinition()` (the separate structural-validation function referenced at the top of `definition.js`) performs a pre-check of `filter.what` before the address/definition is accepted onto the DAG. If it does not, then any address using such a definition — created by an ordinary unprivileged unit author — becomes a "poison" address: any node (this includes light and full nodes, but critically also normal full nodes performing routine unit validation) that processes a unit spending from, or signed by, that address will hit the `throw` and crash.

### Impact Explanation
If reachable without prior structural rejection, this becomes a repeatable full-node crash triggered by an unprivileged unit poster defining an address/AA with a malformed `'seen'` filter and then getting any unit to reference it (spending unit, AA trigger, or authentifier check). Every node that validates that unit crashes, which can be broadcast network-wide, causing multiple full nodes to repeatedly crash on the same poisoned unit — directly analogous to the CVE's "hang or frequently repeatable crash (complete DOS)" impact, but affecting the confirmation/validation availability of the whole network rather than a single MySQL server.

### Likelihood Explanation
Likelihood depends entirely on whether `validateDefinition()` already validates the `'seen'` filter shape (including `what`) before the definition is accepted. I could not verify this with certainty in the available searches, so I present this with medium confidence: the code pattern (bare `throw` instead of `cb2(err)`) is a genuine code-quality/robustness anomaly regardless, and if it is reachable, the likelihood of a successful DoS is high because it requires only crafting a plain JSON definition, no privileged access, and no race conditions.

### Recommendation
1. Replace the bare `throw Error("invalid what: ...")` in the `'seen'` case (and audit for any other bare `throw` inside `evaluate()`/`validateAuthentifiers` reachable from attacker-controlled definitions) with `return cb2(false)` or an explicit error propagated through the callback chain, consistent with every other validation failure in that function.
2. Confirm and, if missing, add a structural check in `validateDefinition()` that rejects `'seen'` operators with any `what` value other than `'input'`/`'output'` at definition-creation time, so malformed definitions can never reach the DAG in the first place.
3. Add a top-level safety net (e.g., wrapping unit validation in `try/catch` and converting to a validation failure) so a single malformed unit cannot crash the whole node process regardless of where a stray `throw` occurs in the validator internals.

### Proof of Concept
Not independently executed. Conceptually: author an address (or AA base definition) whose spending condition is `['seen', {what: 'bogus', asset: 'base'}]` (or embed it in an `'or'`/`'and'` combinator to satisfy "must have a signature" checks), define the address on-chain, then have any unit reference that address in its authors or as an AA trigger author. When any node calls `validateAuthentifiers` → `evaluate()` on that definition, `filter.what !== 'input' && filter.what !== 'output'` is true, and the bare `throw Error("invalid what: ...")` at `definition.js:859` fires outside of the errback chain, propagating as an unhandled exception in that node's process. I was not able to run this against a live ocore instance to confirm whether the process actually crashes or whether an upstream handler catches it — this is the key unresolved uncertainty for this finding.
