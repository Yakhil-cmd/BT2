### Title
Exechook timeout can be silently bypassed because `runWithStdin` never sets `cmd.WaitDelay`, allowing `cmd.Run()` to block forever past `h.timeout` - ([File: pkg/cmd/cmd.go])

### Summary
`Exechook.Do` wraps the hook execution in `context.WithTimeout(ctx, h.timeout)` and relies on `exec.CommandContext` plus `cmd.Run()` in `runWithStdin` to enforce that timeout. Because `cmd.Stdout`/`cmd.Stderr` are set to in-process `bytes.Buffer`s (not `*os.File`), Go's `os/exec` package internally creates OS pipes and spawns goroutines that copy from the read end until EOF; `cmd.Wait()` (invoked by `cmd.Run()`) blocks until those goroutines finish, not merely until the direct child exits. If the hook command forks a detached/backgrounded grandchild that inherits fd 1/2 and doesn't close them, `cmd.Wait()` can hang indefinitely even after context cancellation kills the direct child, because `WaitDelay` (the Go 1.20+ mitigation for exactly this scenario) is never set.

### Finding Description
`Exechook.Do` (`pkg/hook/exechook.go:65-80`) calls `h.cmdrunner.Run(ctx, worktreePath, env, h.command, h.args...)` inside a `context.WithTimeout(ctx, h.timeout)`. `Runner.Run` forwards into `runWithStdin` (`pkg/cmd/cmd.go:63-94`): [1](#0-0) 

`exec.CommandContext` arranges for the process to be killed when the context is done, but `cmd.Stdout`/`cmd.Stderr` are assigned `bytes.Buffer` objects rather than `*os.File`. Per Go's documented `os/exec` semantics, when `Stdout`/`Stderr` are not `*os.File`, the package creates an `os.Pipe()` and a background goroutine to copy pipe output into the buffer; `cmd.Wait()` blocks until that goroutine observes EOF on the pipe — i.e., until **every** process holding the pipe's write end (fd 1/2) has closed it, not just the direct child. If the hook command (running in the worktree, potentially invoking build/test tooling that processes attacker-controlled repository content) spawns a detached/backgrounded child that inherits fd 1/2 (e.g., via a shell `&`, `setsid`, `nohup`, or a double-fork daemonize pattern) without redirecting/closing those descriptors, that grandchild keeps the pipe open even after the immediate child is SIGKILLed by the expired context. `cmd.Run()` therefore never returns, `Do()` never returns, and the deferred `cancel()` is never reached to reset resources for the next invocation. This is the standard, Go-documented `os/exec` "Wait may hang on inherited pipes" gotcha, and its intended mitigation, `cmd.WaitDelay` (available since Go 1.20), is not set anywhere in `runWithStdin`.

### Impact Explanation
This causes a **permanent stall of the exec-hook path**: `Exechook.Do` never returns, so `h.timeout` provides no actual upper bound on hook execution time. Depending on how the sync loop serializes hook invocations after a successful sync, this can wedge subsequent hook-triggering syncs and leak goroutines/file descriptors/processes indefinitely — a liveness/resource-exhaustion issue, matching the Kubernetes bounty "resource exhaustion / permanent stall" impact class. It does not grant code execution, secret disclosure, or writes outside `--root` by itself.

### Likelihood Explanation
Requires `--exec-hook-command` (a supported, documented feature) to be configured with a command whose behavior over repository content can spawn a background/detached subprocess that leaves stdout/stderr inherited and open (e.g., a build tool invoked on repo content that backgrounds a job). This is a plausible but non-trivial precondition — it depends on the specific hook script's behavior, which is operator-configured, not directly attacker-controlled; the attacker can only influence *what data* the hook processes, not the hook's own forking logic. This somewhat weakens direct attacker feasibility, but the underlying code defect (missing `WaitDelay`) is real and independent of any specific hook script.

### Recommendation
Set `cmd.WaitDelay` (Go 1.20+) on the `exec.Cmd` in `runWithStdin` to bound how long `Wait()` will wait for I/O copy goroutines after the context is canceled/process exits, and/or set `cmd.Cancel`/`SysProcAttr.Setpgid` plus kill the whole process group on timeout so orphaned descendants are also terminated.

### Proof of Concept
```go
// pkg/cmd/cmd_test.go (new test)
func TestRunWithStdin_HangsOnDetachedGrandchild(t *testing.T) {
    ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
    defer cancel()
    // shell script: forks a detached grandchild holding stdout/stderr open,
    // then the direct child exits immediately.
    script := `(sleep 10 & disown); exit 0`
    done := make(chan struct{})
    go func() {
        _, _, _ = runWithStdin(ctx, testLogger, "", nil, "", "/bin/sh", "-c", script)
        close(done)
    }()
    select {
    case <-done:
        // expected: returns within h.timeout once WaitDelay is set
    case <-time.After(2 * time.Second):
        t.Fatal("runWithStdin did not return after context timeout — Wait() hung on inherited pipe from detached grandchild")
    }
}
```
Before adding `cmd.WaitDelay`, this test fails/hangs, demonstrating that the timeout does not reliably bound `Exechook.Do`'s execution time.
