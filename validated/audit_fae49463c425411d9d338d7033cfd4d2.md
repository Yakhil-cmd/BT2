### Title
Cross-repository/cross-tenant commit status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook only against the GitHub App/organization identified by `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), which is itself attacker-supplied content inside the very payload being verified. [1](#0-0) [2](#0-1) 

Once the signature check passes for that (attacker-controlled) organization, the `status` event is dispatched to `Shipit::Webhooks::Handlers::StatusHandler#process`, which never re-checks that the `sha` in the payload belongs to a commit/repository owned by the organization that authenticated the request. It performs a completely global lookup: [3](#0-2) 

This breaks exactly the binding class described in the reference bug: **the organization that authenticated the webhook ≠ the repository/commit that is actually written to.**

### Finding Description
Every other event handler in this engine derives the target `Repository`/`Stack` from `payload.dig('repository','full_name')` before touching any record (see `Handler#stacks`/`Handler#repository_name`, and the `PullRequest::*` handlers which all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting). [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does not use `repository_name`/`stacks` at all — it queries `Commit` by `sha` only, across the entire instance: [6](#0-5) 

Because `verify_signature` authenticates the request based on the `repository.owner.login`/`organization.login` field embedded in the same JSON body (used purely to pick which configured `Shipit::GitHubApp`'s `webhook_secret` to check the HMAC against), a Shipit deployment configured to serve multiple GitHub organizations/apps (explicitly supported — see `Shipit.github(organization:)` and `test/dummy/config/secrets_double_github_app.yml`) allows any one onboarded, unprivileged organization to legitimately compute a valid `X-Hub-Signature` for its **own** webhook secret while putting an arbitrary `sha` value in the body. Since git SHA-1s are content-addressed, an attacker can reproduce (e.g., via a fork or by simply knowing) a commit SHA that exists in a victim organization's tracked repository, and send a `status` event authenticated as their own organization. `StatusHandler` will match that `sha` against `Commit` records belonging to the **victim's** stack (not the attacker's), and call `commit.create_status_from_github!(params)`, injecting an attacker-controlled `state`/`context`/`description`/`target_url` status onto the victim commit. [7](#0-6) 

### Impact Explanation
Commit statuses gate both deploys and PR merges in this engine: `required_statuses`/`ci.require`/`merge.require` from `shipit.yml` are checked via `StatusChecker` against `statuses_and_check_runs` when deciding `deployable?` and whether a `MergeRequest` can be merged. [8](#0-7) [9](#0-8) 

By forging a `success` status context that satisfies `ci.require`/`merge.require` for a commit in an organization the attacker does not control, the attacker can make a normally CI-blocked commit `deployable?`, unblocking an unauthorized deploy, or make a merge-queue PR pass its status checks and get auto-merged (`MergeRequest#merge!` calling `stack.github_api.merge_pull_request`). This crosses the explicitly in-scope "unauthorized deploy, rollback or merge" impact bar.

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one GitHub organization/app (a documented, supported configuration — `secrets_double_github_app.yml`, `Shipit.github(organization:)`), and that the attacker controls one of those onboarded organizations (their own legitimate webhook secret, no privileged Shipit account, no `webhook_secret`/`api_clients_secret` of the victim needed). Obtaining a target commit `sha` in a victim repo is trivial for public repos or via forks (identical history/SHAs). No GitHub App private key, `ApiClient` token, or Shipit session is required — only the attacker's own organization's webhook secret, which they legitimately possess.

### Recommendation
In `StatusHandler#process` (and any other handler that does not currently do so), scope the `Commit` lookup to the repository identified by the authenticated webhook (`payload.dig('repository','full_name')`/the `stacks` helper already defined on `Handler`), e.g. `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })`, instead of a bare `Commit.where(sha: params.sha)`. More generally, `WebhooksController#verify_signature` should not let the authenticated organization be picked purely from unauthenticated payload content without then enforcing that every write performed by the handler is confined to repositories belonging to that same organization.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/organizations, e.g. `OrgOne` (attacker-controlled) and `OrgTwo` (victim), each with its own `webhook_secret`, per the documented multi-org configuration format. [10](#0-9) 
2. Attacker identifies a commit `sha` present in a `Shipit::Stack` tracking a `OrgTwo` repository (public commit, or a forked repo sharing the same SHA).
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgOne_webhook_secret, body)` for a `status` event payload:
```json
{ "sha": "<victim_commit_sha>", "state": "success", "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgOne/attacker-repo" } }
```
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and validates the signature successfully (it is a legitimate signature for OrgOne's own secret). [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — since `sha` matches a commit belonging to `OrgTwo`'s stack, `commit.create_status_from_github!(params)` creates a forged `success` status on the victim's commit, satisfying `ci.require`/`merge.require` for that commit and enabling deploy/merge. [3](#0-2)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end

      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(

        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',

      true

    rescue Octokit::Conflict # shas didn't match, PR was updated.

    end
