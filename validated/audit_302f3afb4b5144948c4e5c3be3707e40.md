This scenario describes a bypass that does not exist in the codebase — the check is explicitly implemented and tested.

## No vulnerability found for this question.

**Reasoning:**

Transaction admission via `AptosVM::validate_transaction` (used by vm-validator) performs two independent checks, neither of which trusts the caller's claimed public key/address binding:

1. **Cryptographic signature check**: `transaction.check_signature()` verifies the submitted signature against the *declared* public key in the authenticator (e.g., a `SingleKeyAuthenticator` for secp256k1) via `AccountAuthenticator::verify`/`AnySignature::verify`. [1](#0-0) [2](#0-1) 

2. **On-chain authentication-key binding check** (in the Move prologue, `prologue_common`): the auth key derived from the declared public key (via `AuthenticationKey::any_key`/`to_authentication_key`, scheme `SingleKey`) is compared against `account::get_authentication_key(sender_address)`, which is read from the sender's actual on-chain `Account` resource — not from anything the attacker supplies. [3](#0-2) [4](#0-3) 

An attacker who submits a transaction for account X's address but signs it with an unrelated keypair Y would produce an authenticator whose public key hashes (via `any_key`) to Y's derived address, not X's stored authentication key. `txn_authentication_key.destroy_some() == authentication_key` fails, and the prologue aborts with `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY`, which vm-validator surfaces as `StatusCode::INVALID_AUTH_KEY`.

This exact scenario is already covered by an existing unit test that proves the rejection behavior: [5](#0-4) 

`native_ecdsa_recover` (the Move native used to recover a public key from a secp256k1 signature) is not part of the core transaction-admission authentication path at all — the `AnyPublicKey`/authenticator scheme requires the *declared* public key up front, and both the signature check and the on-chain auth-key comparison are performed against that declared key, not against anything an attacker can spoof via a "valid-looking" recovered key for a different address. There is no code path where a mismatched recovered/declared key can be admitted by vm-validator or mempool while binding to a different sender's authentication key.
