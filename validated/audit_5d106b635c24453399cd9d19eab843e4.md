### Title
Signer-key grant revocation is not durable in `revoke-signer-grant`, allowing an attacker holding a revoked/rotated-away signer key to re-fixate control of a signer-manager identity - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`revoke-signer-grant` only deletes the current `signer-key-grants` row for a `(signer-key, signer-manager)` pair. It does not record that the key has ever been revoked, and `grant-signer-key` places no restriction on re-granting a key other than requiring a fresh, unused `auth-id`. Consequently, the holder of the private key that was just revoked (or rotated away from) can immediately re-mint a valid grant for that same key and re-register it as the manager's current signer, completely undoing the operator's revocation — the pox-5 analogue of a fixation attack where invalidating a credential does not actually invalidate it.

### Finding Description
`signer-key-grants` is the durable state that gates whether a `signer-key` may be bound to a `signer-manager` (used by `register-signer`, `stake-update`, `update-bond-registration` via `verify-signer-key-grant`) [1](#0-0) .

`grant-signer-key` inserts into this map after checking only that the specific `(signer-key, signer-manager, auth-id)` triple hasn't been used before — it does not check whether the `(signer-key, signer-manager)` pair was ever revoked: [2](#0-1) 

`revoke-signer-grant` only performs a `map-delete` on `signer-key-grants`; it does not blacklist the key, and it leaves `used-signer-key-grants` (keyed by `auth-id`, not by key) as the only anti-replay mechanism: [3](#0-2) 

Because the *only* thing single-use-checked is the specific `auth-id`, the key holder can trivially produce a new SIP-018 signature over a fresh `auth-id` and call `grant-signer-key` again, re-inserting `signer-key-grants{signer-key, signer-manager} = true` — with no operator or admin action required. Once re-granted, `register-signer` (invoked via the manager's own self-registration wrapper, e.g. `register-self` in the reference signer contract) will happily overwrite `signers[signer-manager]` back to the "revoked" key: [4](#0-3) [5](#0-4) 

The test-suite itself documents that rotation intentionally does not revoke the previous grant ("rotation does not revoke it; only the recorded key moves") [6](#0-5) , and that `revoke-signer-grant`'s entire stated purpose is to permanently block a "buggy or deprecated" manager key from accumulating new stake [7](#0-6) . Neither guarantee actually holds against the key holder themselves, because nothing stops them from self-issuing a brand-new grant.

This mirrors the report's bug class exactly: a privileged transition (revocation / key rotation, analogous to a post-privilege-change session renewal) is expected to invalidate an old credential, but the underlying state (`signer-key-grants`) can be silently re-established by the same unprivileged party using only their already-known private key, with no new authorization from the operator.

### Impact Explanation
`register-signer`, `stake-update`, and `update-bond-registration` all gate on `verify-signer-key-grant signer (get-signer-info signer)` before routing new stake/bond delegation to a signer-manager identity [8](#0-7) [9](#0-8) . By resurrecting a revoked/rotated-away key and re-registering it, an attacker can cause the `signers` map entry for a manager to point back at a key the operator no longer controls/trusts, letting new STX stakes and sBTC bond shares continue to be routed to — and claimable rewards continue to accrue under — a signer identity backed by a key the legitimate operator explicitly tried to remove. This is a stacking/registration action that the current, intended key holder never re-authorized, which falls under the "unsigned stacking action" category. I could not fully verify within this session whether this pox-5 `signer-manager`/bond abstraction feeds directly into Nakamoto's actual block-signing weight (`signer_set.rs`) or is a self-contained reward-pool layer; that linkage would materially change the severity and should be confirmed before treating this as consensus-critical.

### Likelihood Explanation
Exploitation requires only that the attacker previously possessed (and still possesses) the private key for a `signer-key` that was later revoked or rotated away from — a realistic scenario when pool operators rotate keys after suspected compromise or offboard a co-signer. No admin, bond-admin, pause-admin, or other privileged principal is needed; the attacker acts entirely through their own key and permissionless public entry points (`grant-signer-key` requires only `contract-caller == signer-manager`, which the manager's own public self-registration wrapper satisfies for anyone presenting a valid signature).

### Recommendation
Make revocation durable: add a permanent `revoked-signer-key-grants` (or similar) map set by `revoke-signer-grant`, and have `grant-signer-key` reject re-granting any `(signer-key, signer-manager)` pair that appears in it (independent of `auth-id`). Alternatively, require operators to change to a genuinely new key on rotation and have `register-signer`/`update-bond-registration` reject re-use of any key that was ever associated with that manager and subsequently replaced.

### Proof of Concept
1. Operator registers `signer-manager` with `signer-key = K1` via `grant-signer-key(K1, signer-manager, auth-id=1, sig1)` then `register-signer(signer-manager, K1)` [4](#0-3) .
2. Operator suspects `K1` is compromised and calls `revoke-signer-grant(signer-manager, K1)` as the `K1`-derived principal, which deletes the `signer-key-grants` row [10](#0-9) ; operator separately registers a fresh key `K2` for the manager.
3. Attacker, still holding `K1`'s private key, signs a fresh message with a new `auth-id=2` and calls `grant-signer-key(K1, signer-manager, 2, sig2)` — this succeeds because `used-signer-key-grants` only tracked `auth-id=1` [11](#0-10) .
4. Attacker then calls the manager's self-registration wrapper (`register-self`/`register-signer`) with `K1`, overwriting `signers[signer-manager]` back to `K1` [5](#0-4) , fully reversing the operator's revocation/rotation without their consent.

```text
;; Revoke a signer key grant for a staker. Only the Stacks principal
;; associated with `signer-key` can call this function.
;;
;; Revoking has two effects: it prevents future `register-signer` calls for
;; this (signer-key, signer-manager) pair, and, because every new-stake
;; entry point re-checks the grant via `verify-signer-key-grant`, it also
;; disables an already-registered manager from accepting any new stake. The
;; manager's `signers` entry is left intact so its outstanding obligations can
;; still be settled; those positions wind down as their bonds/stakes expire.
;;
;; Returns a boolean indicating whether the signer key grant existed.
(define-public (revoke-signer-grant
        (signer-manager principal)
        (signer-key (buff 33))
    )
    (begin
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))

        ;; Validate that `contract-caller` has the same pubkey hash as `signer-key`
        (asserts!
            (is-eq
                (unwrap-panic (principal-construct?
                    (if is-in-mainnet
                        STACKS_ADDR_VERSION_MAINNET
                        STACKS_ADDR_VERSION_TESTNET
                    )
                    (hash160 signer-key)
                ))
                contract-caller
            )
            ERR_UNAUTHORIZED
        )
        (print {
            topic: "revoke-signer-grant",
            signer-key: signer-key,
            signer-manager: signer-manager,
        })
        (ok {
            signer-key: signer-key,
            signer-manager: signer-manager,
            existed: (map-delete signer-key-grants {
                signer-key: signer-key,
                signer-manager: signer-manager,
            }),
        })
    )
)
```
