### Title
Unprivileged PR against a repository with `review_stacks_enabled == false` and `provisioning_behavior == 'prevent_with_label'` bypasses the enablement gate and creates a ReviewStack - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses Ruby operator precedence (`&&` binds tighter than `||`) so `repository.review_stacks_enabled` only gates the `provisioning_behavior_allow_all?` branch, not the `provisioning_behavior_allow_with_label?` or `provisioning_behavior_prevent_with_label?` branches. An attacker who opens a labelless PR against a repository configured with `provisioning_behavior: 'prevent_with_label'` but `review_stacks_enabled: false` still triggers `ReviewStackAdapter#find_or_create!`, creating a real `Shipit::ReviewStack` record and enqueuing it in `ReviewStackProvisioningQueue`.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` must precede any `ReviewStackAdapter#create!` call. The actual code in `provision?` is: [1](#0-0) 
Due to Ruby precedence, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`.

The `review_stacks_enabled` check is scoped only to the first disjunct. For a repository with `provisioning_behavior_prevent_with_label? == true` and `review_stacks_enabled == false`, the third disjunct `(prevent_with_label? && !has_label)` evaluates independently of `review_stacks_enabled`. An attacker who opens a pull request with `params.pull_request.labels == []` satisfies `!pull_request_has_provisioning_label?`, making `provision?` return `true` even though review stacks were never enabled for the repository.

`process` then unconditionally calls: [2](#0-1) 
`ReviewStackAdapter` itself performs no independent `review_stacks_enabled` check — it just does `scope.find_by` / `scope.create!` against `repository.review_stacks`, an ordinary `has_many` association with no additional scoping tied to the flag: [3](#0-2) [4](#0-3) 
No model-level validation on `Repository` or `Stack` enforces `review_stacks_enabled` as a precondition for `review_stacks.create!`, and `webhooks_controller` signature verification only authenticates that the payload came from GitHub for that repo — it does not gate on this business-logic flag. The attacker's own repo webhook payload (labels array empty) is sufficient; no privileged token or secret is required.

### Impact Explanation
This results in a `Shipit::ReviewStack` record and provisioning-queue entry being created for a repository whose owner explicitly disabled review stacks (`review_stacks_enabled == false`). This is a record written for a repository configuration that should have prevented it, and the created stack is subsequently subject to provisioning (branch/environment build), effectively an unauthorized ReviewStack creation and provisioning trigger. This is repeatable against any repository configured with `provisioning_behavior: 'prevent_with_label'` and `review_stacks_enabled: false`, by any user able to open a PR (or, since this is webhook-driven `params`, by any actor who can cause a GitHub webhook for that repository, e.g. an outside contributor opening a PR with no labels).

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior == 'prevent_with_label'` (a valid, supported configuration per `Repository::PROVISIONING_BEHAVIORS`) while `review_stacks_enabled == false`. This is a plausible/likely misconfiguration since these are two independently-set fields on the `repositories_controller` settings form, and an operator may set a `provisioning_behavior` in preparation for later enabling review stacks. Attacker cost is zero: opening a PR with no labels is trivial and requires no special access; the vulnerable code path fires on the standard `pull_request.opened` webhook, and label absence is the default state (no explicit label needs to be added).

### Recommendation
Add explicit parentheses/refactor `provision?` so `review_stacks_enabled` gates all three branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same audit/fix to `reopened_handler.rb`, `labeled_handler.rb`, and `unlabeled_handler.rb`, which share this pattern per the earlier grep results.

### Proof of Concept
In a minitest (e.g. `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Stub/build a repository with `review_stacks_enabled: false`, `provisioning_behavior: 'prevent_with_label'` (so `provisioning_behavior_prevent_with_label?` returns `true`).
2. Build `params` via the handler's `params` schema with `action: "opened"`, `pull_request.labels: []`, and a `head.ref`/`number` etc.
3. Instantiate `OpenedHandler.new(params)` and call `process`.
4. Assert binding before: `repository.review_stacks_enabled == false` (should have implied no `ReviewStackAdapter#create!`/`find_or_create!` call).
5. Assert binding after: `Shipit::ReviewStackAdapter` instance's `find_or_create!` was in fact invoked (e.g. via mocking `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.any_instance.expects(:find_or_create!)`, or asserting `Shipit::ReviewStack.count` changed) — demonstrating the two sides of the equality diverge, i.e. `review_stacks_enabled == false` did NOT prevent stack creation.
