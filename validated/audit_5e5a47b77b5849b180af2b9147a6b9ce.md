Based on my analysis, I found a concrete analog matching the report's bug class: a binding-breaking mismatch between the field used for authentication/authorization and the field used to determine what gets written.

### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while the target repository is selected from `repository.full_name` in the same forgeable payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's secret to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. But the handlers that actually act on the payload (e.g. `Handler#stacks`, used by `PushHandler`, `CheckSuiteHandler`, etc.) resolve the target `Repository`/`Stack` using a completely different field: `payload.dig('repository', 'full_name')`. Additionally, `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever `webhook_secret` is blank/unset for that organization, which the setup docs describe as "optional".

### Finding Description
<cite repo="Ellentat/shipit-engine--017" path="app/controllers/shipit/webhooks_controller.rb" start="24,59" end="30,62" />
`verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `repository_owner`: [1](#0-0) 

Meanwhile, `Handler#stacks`/`#repository_name` — the base class used by `PushHandler`, `CheckSuiteHandler`, `StatusHandler`, and all `PullRequest::*Handler`s — resolves the actual repository/stack acted upon from a different key, `repository.full_name`: [2](#0-1) 

And `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically verified: [3](#0-2) 

This is documented as an explicitly optional setting for multi-organization deployments in `docs/setup.md` ("Webhook secret (optional)"), so it's a legitimate, foreseeable configuration state rather than a hypothetical.

The equality that should hold, but doesn't, is:
```
organization used to select/verify the signing secret (repository.owner.login / organization.login)
    ==
organization implied by the repository actually mutated (repository.full_name's owner)
```
Nothing in `WebhooksController` or `Webhooks::Handlers::Handler` cross-checks these two values. In a multi-organization Shipit deployment (`config/secrets.yml` keyed per-org, as documented in `docs/setup.md:182-209`), if even one configured organization has no `webhook_secret` set, an unauthenticated attacker can POST an arbitrary JSON body to `/webhooks` with `X-Github-Event` set to any handled event, `repository.owner.login` (or `organization.login`) set to that unsecured org, and `repository.full_name` set to any *other* tracked repository belonging to a *different* organization in the same Shipit instance. `verify_signature` will pass unconditionally for the unsecured org, while the handler dispatches the event against the unrelated repository/stack chosen by the attacker via `full_name`.

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding called out in the rules. Concretely reachable handlers that mutate cross-organization state without any real GitHub-issued signature:
- `PushHandler` triggers `stack.sync_github` / `GithubSyncJob` for a stack belonging to an unrelated organization: [4](#0-3) [5](#0-4) 
- `MembershipHandler` creates/mutates `Team`/`Membership` records keyed by `organization.login`/`team.id`, again decoupled from the org used for signature verification: [6](#0-5) 
- `PullRequest` handlers can archive/unarchive review stacks belonging to a different repository entirely (`stack.archive!` / `stack.unarchive!`) based on the forged `full_name`.

This can reach "unauthorized deploy"/cross-repository writes and, via `MembershipHandler`, escalation of `Team`/`Membership` records used for `Shipit.github_teams` authorization — both explicitly in-scope impact categories.

### Likelihood Explanation
Exploitability depends entirely on one condition that is realistic and even encouraged by the docs: at least one configured GitHub organization in a multi-org Shipit deployment has no `webhook_secret` set (explicitly labeled "optional" in `docs/setup.md`). Once that condition holds, the attack requires no secrets, no GitHub App credentials, and no prior authentication — a bare, unauthenticated HTTP POST to `/webhooks` suffices, and `repository_owner` (used for auth) and `full_name` (used for target resolution) are both attacker-supplied fields in the same request body.

### Recommendation
1. Always require a `webhook_secret` for every configured GitHub organization; refuse to boot (or refuse to accept webhooks for that org) if it's absent, rather than treating a missing secret as automatically verified in `GitHubApp#verify_webhook_signature`.
2. After signature verification, assert that the organization inferred from `repository.full_name` (or `organization.login`) used by the handler matches the `repository_owner` that was actually used to select and verify the signing secret, rejecting the request otherwise.

### Proof of Concept
Given a Shipit deployment configured for two organizations, `org-a` (no `webhook_secret` set) and `org-b` (repository `org-b/prod-app` tracked as a Stack with `continuous_deployment` enabled):
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/prod-app"
  }
}
```
- `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, loads the `org-a` `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no `X-Hub-Signature` header is even required.
- `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-b/prod-app")`, unrelated to `org-a`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")`, enqueuing `GithubSyncJob` against `org-b`'s stack — a cross-organization action triggered without any credential belonging to `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
