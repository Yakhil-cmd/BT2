Confirmed impact analysis: `GithubSyncJob#perform` fetches commits via `stack.github_commits`/`stack.github_api`, which uses the *real* `Repository`'s stored `owner` (via `Shipit.github(organization: owner)` in `Shipit::Repository#github_app`), so the actual git data comes from GitHub with legitimate app credentials — the forged `expected_head_sha` is only used as a hint/retry-trigger, not trusted as fact. This mitigates a "commit forgery" impact, but the core trust-binding break remains: the organization whose secret validates the webhook signature is decoupled from the repository the handler acts on.

### Title
Webhook signature is verified against the organization named in the unverified payload while handlers act on an unrelated `repository.full_name` from the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read directly out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')`), before the signature itself has been checked. Once verified, the actual event handlers (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a *different* field from the same attacker-controlled body: `payload.dig('repository', 'full_name')`. Nothing enforces that `repository.owner.login` (used to pick the verification secret) is consistent with `repository.full_name` (used to pick the affected Stack).

In a multi-organization Shipit deployment (explicitly supported, one `webhook_secret` per organization), the equality the code implicitly relies on is:
`organization that signed the payload == organization owning repository.full_name`.
This equality is never checked. An attacker who controls (or has been issued) the webhook secret for **one** onboarded, low-trust organization "OrgA" can sign an arbitrary JSON body with OrgA's secret while setting `repository.full_name` to `"OrgB/some-other-stack"` — a repository/Stack belonging to a completely different, unrelated organization "OrgB" configured in the same Shipit instance. `verify_signature` passes because it only checks `repository.owner.login == "OrgA"` against OrgA's secret; the push handler then acts on `"OrgB/some-other-stack"`.

### Impact Explanation
The practical effect (given `GithubSyncJob` fetches actual commit data via `stack.github_api`, which is scoped to the real stored `Repository#owner`) is that the forged webhook cannot inject fake commit content, but it can force enqueuing sync/status/pull-request-state jobs (`GithubSyncJob`, `CacheDeploySpecJob`, review-stack archive/unarchive, PR label capture, etc.) against **any Stack configured in the Shipit instance**, regardless of which organization's secret the attacker actually possesses. This is a cross-tenant control-plane confusion: the organization boundary that is supposed to scope which webhook secret authorizes which repository's automation is not enforced, allowing an attacker who only controls one tenant's webhook secret to trigger sync/state-changing jobs for stacks belonging to other tenants they have no relationship with.

### Likelihood Explanation
Exploitation requires the attacker to already possess a valid `webhook_secret` for at least one organization onboarded to the same multi-tenant Shipit instance — this is the normal, documented "Using Multiple GitHub Applications" configuration (`docs/setup.md`), not a privileged Shipit account. Given that, forging the JSON body and computing the correct HMAC is trivial; there is no additional secret or credential needed for the target organization/repository.

### Recommendation
After determining which `github_app`/secret validated the signature, re-derive `repository_owner` from the *authenticated* organization context (or explicitly assert `params.dig('repository', 'owner', 'login') == authenticated_organization` and reject otherwise) before dispatching to any handler, mirroring the pattern the external report recommends (add an explicit equality check binding the verified identity to the acted-upon resource, analogous to `require(_operator != msg.sender)`-style checks added for `authorizeOperatorByPartition`/`revokeOperatorByPartition`).

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple GitHub Applications").
2. As an attacker who legitimately administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/some-other-stack"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac using OrgA's webhook_secret over the raw body>`.
4. POST to `/github/webhooks` (Shipit webhook endpoint) with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates successfully since the attacker signed with OrgA's real secret.
6. `PushHandler#process` then resolves `Repository.from_github_repo_name("OrgB/some-other-stack")` and enqueues `GithubSyncJob`/`stack.sync_github` for a Stack the attacker has no relationship with, demonstrating the organization-that-signed vs. repository-that-is-acted-upon binding break.
