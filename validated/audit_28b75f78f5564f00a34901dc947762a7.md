### Title
Unsettled reward checkpoint on bond-share mutation in `add-staker-to-bond-for-cycle` / `remove-staker-from-bond-for-cycle` leads to double-counted or lost sBTC bond rewards - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar` maintains, per signer/cycle/bond, a reward "checkpoint" (`signer-rewards-per-token-settled-for-cycle`) that must be refreshed via `settle-rewards` *before* `signer-shares-staked-for-cycle` / `total-shares-staked-for-cycle` is mutated, exactly as documented at the definition of `settle-rewards` itself. This checkpoint discipline is followed by the STX-only staking path (`add-staker-to-signer-for-cycle`) and by the bond-unstake path (`unstake-sats-from-bond-cycle`), but is missing from the bond-join and bond-leave helpers, `add-staker-to-bond-for-cycle` and `remove-staker-from-bond-for-cycle`.

### Finding Description
`settle-rewards` explicitly documents the invariant it relies on: [1](#0-0) 

and the mirrored per-staker function repeats the same rule: [2](#0-1) 

The STX-only staking add path honors this: it calls `settle-rewards` (and, if the staker already has shares, `settle-staker-rewards`) *before* touching `signer-shares-staked-for-cycle` / `total-shares-staked-for-cycle`: [3](#0-2) 

The bond-unstake path also honors it: [4](#0-3) 

However, `add-staker-to-bond-for-cycle` — invoked when a staker joins a bond for a given cycle (via `add-staker-to-bond-cycles`) — mutates `total-shares-staked-for-cycle` and `signer-shares-staked-for-cycle` directly, with **no call to `settle-rewards`** beforehand: [5](#0-4) 

It does correctly checkpoint the *staker's own* settled snapshot (`staker-rewards-per-token-settled-for-cycle`) to the current `rewards-per-token`, which prevents the new staker from personally back-claiming pre-join rewards: [6](#0-5) 

But it never checkpoints `signer-rewards-per-token-settled-for-cycle` for the signer, and it increases `signer-shares-staked-for-cycle` and `total-shares-staked-for-cycle` in place. Because `settle-rewards`/`compute-earned-rewards` compute earned amounts as `shares * (current_rpt - last_settled_rpt)` using whatever the *current* share balance is at settlement time, any later call to `settle-rewards` for that signer/cycle/bond (triggered by a subsequent claim, unstake, or `calculate-rewards`-driven flow) will apply the full accumulated `rpt` delta — which includes reward-per-token growth that happened *before* the new shares were added — to the now-larger share count. The symmetric bug exists in `remove-staker-from-bond-for-cycle`, which reduces shares without settling first, causing an equal-and-opposite understatement of rewards owed for the shares that departed.

The mirror-image function pair (`unstake-sats-from-bond-cycle` calling `settle-rewards`, `add-staker-to-bond-for-cycle` not calling it) is precisely the same bug class described in the external report: a "recalculate before use" invariant that is enforced in some code paths that mutate the underlying accounted quantity but is silently skipped in others, letting the accounted value drift from the true state until a path that does perform the recalculation (e.g. a claim or `calculate-rewards`) is eventually triggered — at which point the drift is baked into an incorrect payout rather than merely a stale intermediate read.

### Impact Explanation
This breaks the equality between rewards actually accrued/deposited into the bond's `rewards-per-token-for-cycle` pool and rewards paid out to signers/stakers of that bond. When a staker joins a bond in a cycle where `rewards-per-token-for-cycle` has already advanced (i.e., `calculate-rewards` ran at least once this cycle before the join), the signer's next settlement will retroactively apply that accrued `rpt` delta to the enlarged share balance, crediting rewards for sBTC that was never staked during the period those rewards were earned — a double-count of a reward commitment paid from the shared sBTC reward pool (`get-rewards`/`reserve-balance`), at the expense of the pool/other stakers or the protocol reserve. This matches the in-scope impact category "sBTC rewards paid that were not earned or counted twice" (Critical: double-counting a commitment or reward).

### Likelihood Explanation
Reachable by any ordinary staker calling the public bond-registration flow (`add-staker-to-bond-cycles`) in any cycle after `calculate-rewards` has already been invoked once for that cycle — a routine, expected sequence of events requiring no privileged role, and it will occur naturally any time new stakers/bonds are added mid-cycle after a reward calculation.

### Recommendation
Add `settle-rewards` (and, when the staker already has a nonzero prior balance, `settle-staker-rewards`) calls in `add-staker-to-bond-for-cycle` and `remove-staker-from-bond-for-cycle`, mirroring the pattern already used in `add-staker-to-signer-for-cycle` and `unstake-sats-from-bond-cycle`, so that `signer-rewards-per-token-settled-for-cycle` is checkpointed to the current `rewards-per-token-for-cycle` *before* `signer-shares-staked-for-cycle` / `total-shares-staked-for-cycle` is mutated for the bond.

### Proof of Concept
1. Bond `B` cycle `C` starts with signer `S` holding `1000` sats staked, `signer-rewards-per-token-settled-for-cycle(S,C,B) = 0`.
2. `calculate-rewards` runs, distributing rewards for bond `B`, advancing `rewards-per-token-for-cycle(C,B)` to `RPT1` (computed against the pre-join `1000` sats).
3. Staker `A` calls the public bond-registration entrypoint, which invokes `add-staker-to-bond-cycles` → `add-staker-to-bond-for-cycle` for cycle `C`, adding `500` sats. `signer-shares-staked-for-cycle(S,C,B)` becomes `1500`; `signer-rewards-per-token-settled-for-cycle(S,C,B)` is **not** updated and remains `0`.
4. Any subsequent trigger of `settle-rewards(S,C,B)` (e.g. a claim, or the next `unstake`) computes `earned = compute-earned-rewards(1500, RPT1_or_later, settled=0, prevUnclaimed=0)`, i.e. `1500 * RPT1` instead of the correct `1000 * RPT1`, crediting the signer for `500` shares that were not staked when `RPT1` accrued — sBTC reward double-counted against the pool/reserve.
