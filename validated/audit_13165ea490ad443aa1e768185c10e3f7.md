### Title
Cross-tenant webhook forgery via organization/repository field mismatch between signature verification and event dispatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using `payload.dig('repository','owner','login')` (or `organization.login`), but every event handler (`Handler#stacks`, `PushHandler`, `CheckSuiteHandler`) resolves the target `Repository`/`Stack` using a different field, `payload.dig('repository','full_name')`. Because these two JSON fields are independently attacker-controlled inside the same signed body, an attacker who legitimately controls the webhook secret for *any* one GitHub organization configured on a multi-tenant Shipit instance can forge a validly-signed webhook whose `repository.owner.login` matches their own org (so their own secret verifies it) while `repository.full_name` names a completely different organization's repository, causing Shipit to act on that victim repository/stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

`repository_owner` is derived from: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `GitHubApp` config (each org can have its own `webhook_secret`, per `config/secrets.development.example.yml` and `docs/setup.md`), and `verify_webhook_signature` HMACs the *entire raw body* against that org's secret: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the same raw JSON payload to the registered handler for the event type: [4](#0-3) 

All handlers resolve which `Stack`/`Repository` to mutate via `Handler#stacks`, which reads a *different* field of the payload than the one used for signature-key selection: [5](#0-4) 

`PushHandler` then syncs the resolved stacks to an attacker-supplied SHA: [6](#0-5) 

and `CheckSuiteHandler` schedules check-run refreshes against arbitrary stacks by branch/SHA: [7](#0-6) 

The security binding that should hold is: `organization whose secret authenticated the request == organization owning the repository being written`. Instead, the code enforces: `repository.owner.login (key selection) verified` while acting on `repository.full_name (arbitrary org/repo)`. Nothing in `verify_signature`, `create`, or `Handler` cross-checks that `repository.owner.login` is a prefix of / consistent with `repository.full_name`.

- Before the attack: only GitHub itself (holding the real per-org webhook secret) can produce events that Shipit accepts for a given org's repositories, and those events only affect that org's own `Stack`s.
- After the attacker's forged request: an entity that legitimately owns/administers one tenant organization's GitHub App (and therefore knows that org's `webhook_secret`, since the org admin who created the App originally chose/shared that secret per `docs/setup.md`) can produce a signature valid for `Shipit.github(organization: their_org)`, while directing the effect of the event (via `full_name`) at a `Stack` belonging to any other tenant organization hosted on the same Shipit instance.

This is exploitable specifically in the documented multi-organization Shipit configuration (`config/secrets.development.example.yml` shows the `github: { org1: {...}, org2: {...} }` schema), which is an explicitly supported, in-scope deployment mode, not a misconfiguration.

### Impact Explanation
Using `push` events, the attacker can force `stack.sync_github(expected_head_sha:)` on a victim organization's stack for any SHA that exists in that victim repository's history (or that GitHub will resolve), effectively triggering out-of-band GitHub sync/build-eligibility processing for a repository the attacker does not own — a cross-organization/cross-repository write triggered purely by a forged, differently-scoped signature. Using `check_suite` events, the attacker can force check-run refresh scheduling against arbitrary victim stacks/commits. This matches the "cross-repository writes" / "unauthorized ...rollback" Critical impact bucket: an attacker with no privileges on the victim organization can cause the engine to process privileged webhook events as if they originated from GitHub for that victim repository.

### Likelihood Explanation
Requires the Shipit instance to be configured for more than one GitHub organization (the documented, supported multi-tenant configuration) and requires the attacker to control (or be an admin of) at least one of the onboarded organizations — a low/unprivileged trust level relative to the victim organization, and no GitHub App private key, `api_clients_secret`, or Shipit session is needed. This is a realistic scenario for any shared/multi-tenant Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), require that `payload.dig('repository','owner','login')` (the value used to select the verifying secret) matches the owner portion of `payload.dig('repository','full_name')` before dispatching to handlers, rejecting (422) any event where they diverge. Alternatively, have `Handler#stacks`/`repository_name` derive the target strictly from `repository.owner.login` rather than trusting the independently-controlled `full_name` field.

### Proof of Concept
1. Configure Shipit with two tenant organizations, `attacker-org` (attacker is the org's GitHub App admin, knows `webhook_secret_A`) and `victim-org` (hosts `Stack` for `victim-org/victim-repo`).
2. Attacker computes `sig = HMAC-SHA1(webhook_secret_A, body)` where:
```json
{
  "ref": "refs/heads/master",
  "after": "<existing sha in victim-org/victim-repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. POST to `/webhooks` with headers `X-Github-Event: push`, `X-Hub-Signature: sha1=<sig>`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, verifies with `webhook_secret_A`, succeeds.
5. `PushHandler#process` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `sync_github(expected_head_sha: '<attacker-chosen sha>')` on the victim's `Stack`, even though the request was never authenticated for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
