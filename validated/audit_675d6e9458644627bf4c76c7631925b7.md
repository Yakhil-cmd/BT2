### Title
Double integer truncation in `min-ustx-for-sats-amount` lets a bond's STX floor be rounded down to zero, letting sBTC-backed reward shares exceed locked STX collateral - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`min-ustx-for-sats-amount` computes the minimum uSTX a staker must lock when joining an sBTC-backed protocol bond, so that BTC-collateralized reward shares are always backed by a configured minimum ratio of STX. The function performs two sequential integer divisions, each of which truncates towards zero, so the result can be `0` even when the bond's admin-configured `min-ustx-ratio` is very high (near 100%). Because `register-for-bond` only checks `amount-ustx >= (min-ustx-for-sats-amount ...)`, a staker can join a bond and be credited `sats-total` sBTC shares while contributing `0` (or near-zero) STX, breaking the intended equality between sats-backed reward weight and STX collateral.

### Finding Description
`min-ustx-for-sats-amount` is defined as: [1](#0-0) 

```
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
)
```

This performs the division `(/ (* stx-value-ratio sats-amount) u100)` *before* multiplying by `min-ustx-ratio`. Clarity's `/` is integer division, so any fractional remainder from the first division is discarded before the second multiplication/division is even applied. For values of `sats-amount` and `stx-value-ratio` where `(stx-value-ratio * sats-amount) / 100` truncates to a small integer, the second stage can still shrink the already-truncated intermediate result all the way to `0`, even when `min-ustx-ratio` is close to `10000` (100%).

Concretely: with `stx-value-ratio = 1`, `min-ustx-ratio = 9999` (99.99% STX backing required), and `sats-amount = 150`:
- Inner: `(1 * 150) / 100 = 1` (150/100 truncated)
- Outer: `(1 * 9999) / 10000 = 0` (9999/10000 truncated)
- Result: `0`

`register-for-bond` uses this value as the *sole* floor for the STX a staker must contribute relative to the sBTC they lock: [2](#0-1) 

```
;; Verify that they're sending enough STX
(asserts!
    (>= amount-ustx
        (min-ustx-for-sats-amount sats-total (get stx-value-ratio bond)
            (get min-ustx-ratio bond)
        ))
    ERR_INSUFFICIENT_STX
)
```

If `min-ustx-for-sats-amount` returns `0`, this check is satisfied by `amount-ustx = 0`. There is no other floor enforced for sBTC-backed bonds at this call site (`SIGNER_SET_MIN_USTX` only gates whether the *signer* crosses the delegation threshold for reward eligibility purposes at the signer level, not a per-staker STX-to-sats minimum) — see `add-staker-to-signer-for-cycle`, which applies `SIGNER_SET_MIN_USTX` to the signer's aggregate delegated total, not to this staker's ratio requirement: [3](#0-2) 

Meanwhile, the staker's full `sats-total` is credited toward bond shares/rewards regardless of the truncated STX amount: [4](#0-3) 

This breaks the intended equality: `locked STX collateral ≥ min-ustx-ratio × (STX-value of locked sats)`. An attacker can lock real (small but nonzero) sBTC and be credited full sBTC-bond reward shares while contributing effectively 0 STX, defeating the STX-collateral requirement that the bond admin configured via `min-ustx-ratio`.

### Impact Explanation
This matches the "High" bucket in scope: "signing weight or reward slots exceeding locked value." A staker's bond reward shares (driven by `amount-sats`) are not actually backed by the STX ratio the bond administrator configured, because the floor computation can silently round to zero. This lets a staker obtain sBTC-bond reward shares while posting far less STX collateral than intended — up to a full bypass of the STX floor for small `sats-amount`/`stx-value-ratio` combinations, or in cases involving multiple such registrations, for larger totals. This does not require any privileged role — any unprivileged staker registering for a bond that meets these ratio/amount conditions can trigger it via `register-for-bond`.

### Likelihood Explanation
The truncation is deterministic and depends only on parameters chosen by the bond admin (`stx-value-ratio`, `min-ustx-ratio`) and the sats amount the staker chooses to lock (bounded by their allowlist `max-sats`). A staker fully controls their own `sats-total` (via `btc-lockup`/`sbtc-amount`), so they can search for/select an amount that makes `min-ustx-for-sats-amount` evaluate to zero (or minimal), especially for smaller `sats-amount` values relative to the ratio denominators (100 and 10000). This is a straightforward, staker-triggerable computation with no dependency on race conditions or privileged actors, making it readily exploitable whenever a bond's parameters and the staker's allowed `max-sats` combine to produce a small enough intermediate product.

### Recommendation
Restructure `min-ustx-for-sats-amount` to avoid discarding precision in an intermediate division step, e.g. combine both scaling factors before dividing:
```
(/ (* stx-value-ratio sats-amount min-ustx-ratio) (* u100 u10000))
```
This performs the multiplication in full before the single division, minimizing truncation loss. Additionally, consider rounding up (ceiling division) for a *minimum* required amount, so the floor is never permissive of less STX than the configured ratio strictly requires, and add an explicit non-zero floor check when `sats-total > 0` and `min-ustx-ratio > 0`, so that computed minimums do not silently allow `amount-ustx = 0` for nonzero sats collateral.

### Proof of Concept
Given a bond with:
- `stx-value-ratio = 1`
- `min-ustx-ratio = 9999` (99.99%)
- Staker allowlisted for `max-sats >= 150`

1. Staker calls `register-for-bond` with `btc-lockup = (err sbtc-amount)` where `sbtc-amount = 150` sats, and `amount-ustx = 0`.
2. `min-ustx-for-sats-amount(150, 1, 9999)` evaluates to `0` (per the double-truncation shown above) at [5](#0-4) 
3. The `ERR_INSUFFICIENT_STX` assertion at [2](#0-1) 
passes since `0 >= 0`.
4. The staker's full `150` sats are custodied and registered as bond shares via `add-staker-to-bond-cycles`, while `amount-ustx = 0` is recorded as their STX contribution — bypassing the intended ~100% STX-backing requirement.

Note: I was not able to fully trace every downstream reward-distribution path (e.g., exact interplay with `settle-rewards`/`get-total-shares-staked-for-cycle` weighting) within the available index snippets, so the precise magnitude of reward-share exploitation in aggregate (across many stakers/bonds) is not fully quantified here; a Devin session with full repository access could verify the end-to-end reward math to confirm the exact scale of impact.
