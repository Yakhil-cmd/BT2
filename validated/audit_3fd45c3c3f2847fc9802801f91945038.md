### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler resolves its target via `repository.full_name` or `sha`, letting a valid signature for one GitHub organization authorize writes against a different organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the inbound signature against based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

Every actual event handler, however, resolves the record it acts on from a *different* field of the same JSON body — `payload.dig('repository', 'full_name')` in the base `Handler` class and all `PullRequest::*Handler`s, or bare `sha`/`state` in `StatusHandler` — with no re-check that this repository/commit belongs to the organization whose secret validated the signature. [3](#0-2) [4](#0-3) 

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` with a top-level `github:` key per organization, as documented), each organization has an independent GitHub App configuration and `webhook_secret`. [5](#0-4) 

The equality the engine implicitly relies on is:
`organization authenticated by HMAC (repository.owner.login / organization.login)` == `repository/commit actually written (repository.full_name in Handler#repository_name, or bare sha in StatusHandler)`

Before the PR/attack: for a genuine GitHub-delivered webhook, both fields are always populated consistently by GitHub itself, so the equality holds implicitly, and no explicit cross-check exists in the code.

After the attack: an attacker who is a legitimate member/owner of **any** organization configured in this Shipit instance (or who otherwise knows a valid `webhook_secret` for any one configured org — e.g., their own org's app) can POST an arbitrary raw JSON body directly to `/webhooks` and compute a correct `X-Hub-Signature` themselves using that org's known secret. They can set `repository.owner.login` to their own (attacker-controlled) org so that `verify_signature` picks their org's `GitHubApp`/secret and the HMAC check passes, while independently setting `repository.full_name` (used by `Handler#repository_name`/`Repository.from_github_repo_name`) to point at a **victim** organization's tracked repository/stack, or setting an arbitrary `sha` in a `status` event payload to match any commit tracked by any stack in the instance. [3](#0-2) [4](#0-3) 

Since the signature is computed over the raw body the attacker crafted (not a body GitHub validated), and the field used for key selection (`repository.owner.login`) is decoupled from the field used for target resolution (`repository.full_name`/`sha`), the HMAC check does not actually bind "this payload was authorized for this repository" — only "this payload was authorized for *some* configured organization, whichever one the attacker names in `repository.owner.login`."

Concretely for `StatusHandler`, this allows an attacker with any single org's webhook secret to inject fabricated commit statuses (`state`, `description`, `target_url`, `context`) for arbitrary commits/stacks across the entire Shipit instance, regardless of which organization owns them. [6](#0-5) 

For `PushHandler`/`PullRequest::*Handler`, the attacker can trigger `sync_github`/provisioning actions against a victim organization's stacks by supplying a mismatched `repository.full_name`. [7](#0-6) [3](#0-2) 

### Impact Explanation
This escalates a credential valid for one organization's webhook trust boundary into write/state-changing actions against stacks belonging to a different, unrelated GitHub organization tracked by the same Shipit instance — a cross-organization write that the per-organization webhook secret model is specifically meant to prevent. Fabricated commit statuses can influence deploy-gating decisions (`deployable?` checks rely on commit status), and forged push/PR events can trigger unwanted syncs/provisioning against victim stacks, i.e., unauthorized state changes outside the attacker's authorized organization.

### Likelihood Explanation
Requires the attacker to control (or know) a valid `webhook_secret` for at least one organization configured on the shared Shipit instance — realistic in any deployment that follows the documented "Using Multiple GitHub Applications" multi-tenant configuration, since each org's own webhook secret is intentionally exposed to that org's GitHub App settings. No privileged Shipit session, `ApiClient` token, or GitHub write access to the victim repo is needed — only the ability to POST directly to the Shipit `/webhooks` endpoint with a self-computed signature.

### Recommendation
Bind the verified organization to the resolved repository/stack: after computing `repository_owner` and verifying the signature, re-derive the repository from `repository.full_name` and assert its owner matches `repository_owner` before dispatching to any handler; reject the request (422) on mismatch. Apply the same invariant inside `Handler#stacks`/`Handler#repository_name` and `StatusHandler#process` so a signature validated for organization A can never resolve or mutate resources scoped to organization B.

### Proof of Concept
1. Deployment configured with multiple GitHub organizations, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker (owner of `attacker-org`, knows `attacker-org`'s `webhook_secret`) crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim-org tracked commit sha>",
     "state": "success",
     "description": "forged",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC check passes because the attacker used the correct (their own) secret. [1](#0-0) 
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — a commit belonging to `victim-org`'s stack — and calls `commit.create_status_from_github!(params)`, injecting a forged status onto a victim commit despite the signature only ever proving knowledge of `attacker-org`'s secret. [4](#0-3)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
