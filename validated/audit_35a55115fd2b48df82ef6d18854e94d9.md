This confirms the bug. `StatusHandler#process` queries `Commit.where(sha: params.sha)` globally with **no repository/stack scoping at all**, unlike `Handler#stacks` (used by `PushHandler`) which properly resolves `Repository.from_github_repo_name(repository_name)&.stacks`. `StatusHandler` never calls `stacks` or checks `repository_name` — it applies the incoming status to every `Commit` row across the entire database that happens to share that `sha`. ### Title
Cross-repository Status webhook poisons unrelated commits' deployability - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone with no repository scoping, so a `status` webhook signed for a repository the attacker controls can write a `success` `Status` onto a `Commit` row belonging to a completely different repository/stack, as long as the SHA values match. Since git commit hashes are deterministic and reproducible by anyone who knows a public commit's exact metadata (tree, parent, author/committer, timestamps, message), an attacker can replicate a victim's commit SHA in their own repo and drive its CI to `success`, then flip `Commit#deployable?` on the victim stack from `false` to `true`.

### Finding Description
The broken binding is: **the repository that authenticated/produced the CI status == `commit.stack.repository`**. In `StatusHandler#process`, this equality is not enforced:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Contrast this with `PushHandler`, which correctly resolves the target stacks via `Handler#stacks`, itself derived from `Repository.from_github_repo_name(repository_name)`: [2](#0-1) [3](#0-2) 

`StatusHandler` never calls `stacks` or reads `repository_name` at all — the `payload['repository']` field is completely unused for scoping, even though it is present in real GitHub `status` payloads (see `test/fixtures/payloads/status_master.json` `name: "baxterthehacker/public-repo"`).

The write then reaches `Commit#create_status_from_github!` → `statuses.replicate_from_github!` unconditionally, and `Commit#deployable?` is later re-evaluated purely from `success?`: [4](#0-3) [5](#0-4) 

**Why `verify_signature` doesn't stop this**: `WebhooksController#verify_signature` resolves the GitHub App/organization purely from `params.dig('repository','owner','login')` in the *incoming* payload and checks the HMAC against that org's own webhook secret: [6](#0-5) 
This only proves the webhook genuinely came from GitHub for *some* repository the attacker controls (e.g. their own public fork/repo with the GitHub App installed) — it proves nothing about which `Commit`/`Stack` the payload should be applied to. `StatusHandler` then ignores the repository field entirely and matches on `sha` across the whole `commits` table.

**Exploit flow**:
1. Attacker identifies a public victim commit (sha, tree, parent, author/committer name+email+dates, message) — all of this is public information for any open-source repo tracked by Shipit.
2. Attacker reproduces the identical commit object (same SHA) in a repository they own (git commit hashing is fully deterministic and content-addressed; `git commit-tree`/replay of an existing commit object trivially reproduces the same SHA in another repo).
3. Attacker's own repo (with a legitimately installed GitHub App/webhook) reports a `status` event with `state: success` for that SHA — a completely normal, self-signed webhook from GitHub for the attacker's own repo.
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` and finds the victim's `Commit` row (in the victim's unrelated `Stack`), writing a `success` `Status` onto it.
5. `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) flips from `false` to `true` on the victim stack without the victim repository ever reporting success.

### Impact Explanation
This is a "payload for one repository mutating another's stack/commit" case explicitly listed as Critical impact. A previously un-deployable (pending/failing CI) commit on a victim's Shipit stack becomes `deployable?` solely due to an attacker-controlled repository's webhook, enabling an unauthorized deploy of code that never actually passed the victim repository's CI. This is repeatable against any commit whose SHA the attacker can reproduce (which includes any commit shared via forks/rebases/cherry-picks, or any commit whose full metadata is public), and works across arbitrary tenants/stacks tracked by the same Shipit instance since the lookup is global (`Commit.where(sha: ...)`, unscoped by stack or repository).

### Likelihood Explanation
Preconditions are modest: the attacker needs (a) a repository they control with the GitHub App/webhook installed (trivially satisfiable — public GitHub Apps can usually be installed on any repo the attacker owns), and (b) the ability to reproduce a target SHA, which is deterministic and achievable for any commit whose full git metadata is known (very common for public/open-source victim repos, and for PR-based commits which are inherently public before merge). No Shipit secret, session, or API token is needed at any step. The attack is repeatable and low-cost per target commit.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks whose repository matches the webhook's `repository.full_name`, mirroring the pattern already used in `Handler#stacks`/`PushHandler`, e.g. restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Stack` filtered by `Repository.from_github_repo_name(repository_name)`, rejecting/ignoring statuses whose payload repository doesn't correspond to the commit's owning stack.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook from an unrelated repository must not change deployable? of a commit belonging to a different stack/repository" do
          victim_stack = shipit_stacks(:shipit) # stack.ignore_ci? == false
          commit = shipit_commits(:first)
          commit.update!(stack: victim_stack)

          refute commit.success?
          refute commit.deployable?, "precondition: commit must start un-deployable"

          # Payload whose repository differs from commit.stack.repository
          spoofed_payload = {
            'sha' => commit.sha,
            'state' => 'success',
            'context' => 'ci/travis',
            'repository' => { 'full_name' => 'attacker/unrelated-repo' },
          }

          StatusHandler.call(spoofed_payload)
          commit.reload

          assert_not_equal victim_stack.repository.full_name, spoofed_payload['repository']['full_name']
          refute commit.success?, "deployable? must not flip true from an unrelated repository's status"
          refute commit.deployable?
        end
      end
    end
  end
end
```
This asserts the binding `commit.stack.repository.full_name == payload['repository']['full_name']` must hold before any state mutation; currently it does not, and `deployable?` flips `false → true` regardless.
