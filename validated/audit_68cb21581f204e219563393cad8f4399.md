### Title
Webhook signature verification authenticates the payload's `repository.owner.login` (or `organization.login`), but handlers act on an unrelated `repository.full_name` (or, for status events, no repository scope at all) — breaking the binding "organization authenticated == repository written" - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) taken from the raw JSON body. [1](#0-0) [2](#0-1) 

Once the signature is accepted, the event is dispatched to a handler that determines *which repository/stack/commit to mutate* using a **different, independently-controlled field** of the same payload: `repository.full_name` (`Handler#repository_name`), or — for `status` events — no repository scope at all. [3](#0-2) [4](#0-3) 

Nothing enforces that the owner segment of `repository.full_name` matches `repository.owner.login`. GitHub always populates both consistently in genuine webhooks, but Shipit never re-derives or cross-checks this at the code level — the two fields are simply two independently attacker-suppliable keys inside the one HMAC-signed JSON blob.

### Finding Description
The trust chain is:
1. `verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then HMACs the whole raw body against that organization's `webhook_secret`. [5](#0-4) 
2. If valid, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs with the raw parsed JSON. [6](#0-5) 
3. `Handler#stacks` resolves the target repository via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, a field wholly independent of `repository.owner.login`. [3](#0-2) 
`Repository.from_github_repo_name` just splits this string on `/` and does a DB lookup — no comparison back to the verified owner. [7](#0-6) 

For `push` events, `PushHandler` uses `stacks` (i.e. the repo derived from `full_name`) to call `stack.sync_github(expected_head_sha: params.after)` for every not-archived stack on that branch. [8](#0-7) 

For `status` events it is worse: `StatusHandler` does not scope by repository at all — it looks up `Commit.where(sha: params.sha)` across the *entire* Shipit instance and applies the payload's status/state to every matching commit, regardless of which repository/organization that commit belongs to. [4](#0-3) 

Root cause, expressed as the broken equality: the binding the security check is supposed to guarantee is `signing_organization (repository.owner.login) == repository_actually_mutated`. The code instead verifies `signing_organization == repository.owner.login` (trivially true, it's the same field) and separately uses `repository.full_name` / bare commit SHA to decide what to mutate, with no code path re-checking that `full_name`'s owner matches `repository.owner.login`, nor that the affected commit's stack belongs to the authenticated organization at all.

### Impact Explanation
An attacker who is a legitimate administrator of *any* GitHub organization/repository tracked by this multi-tenant Shipit instance (and therefore possesses that organization's `webhook_secret` — an entirely unprivileged, ordinary credential for their own org, not for the victim's) can forge a webhook whose HMAC is computed over their own secret, but whose JSON body sets `repository.full_name` (push events) or `sha` (status events) to reference a completely different, victim-owned repository/commit that they have no access to.

- Via `status`: the attacker forges a CI status ("success") for an arbitrary commit SHA belonging to a repository they don't control. `Commit#create_status_from_github!` writes this status, and `Commit#deployable?`/`Stack#deployable?` gate continuous delivery and manual deploys on exactly this status data — enabling an unauthorized deploy of a commit that never actually passed the victim's real CI requirements (`ci.require`).
- Via `push`: the attacker triggers `GithubSyncJob`/`sync_github` on a victim's stack with an attacker-chosen `expected_head_sha`, letting them influence what Shipit believes is the latest reachable commit for a repository they do not own.

This satisfies the Critical impact bar of "an unauthorized deploy" via a credential/repository binding that was never actually checked, using only a legitimate-but-unrelated organization's webhook secret — no `ApiClient` token, no GitHub App private key, and no access to the victim organization required.

### Likelihood Explanation
This requires: (a) the Shipit deployment to track more than one GitHub organization/webhook secret (an explicitly supported, documented configuration via `Shipit.github(organization:)` and `Shipit::GithubHook::Organization`/`Repo` records), and (b) the attacker to be a legitimate admin of at least one tracked organization/repo (able to view/set its `webhook_secret`). Both are realistic in any shared/multi-tenant Shipit install, and crafting the payload requires no special tooling — just a standard signed HTTP POST with mismatched `repository.owner.login` vs `repository.full_name` (or an arbitrary `sha` for `status`).

### Recommendation
- In `Handler#stacks` / `Handler#repository_name`, require that the owner segment of `repository.full_name` match the verified `repository.owner.login` (or `organization.login`) used to select the webhook secret; reject the event otherwise.
- In `StatusHandler#process`, scope the `Commit` lookup to the authenticated organization/repository (e.g. join through `stacks.repository` and filter by owner) instead of matching bare SHA globally.
- More generally, pass the authenticated organization down from `WebhooksController` into every handler and have each handler assert equality against every repository-identifying field it consumes from the payload, not just the one used for signature selection.

### Proof of Concept
1. Shipit tracks two orgs, `attacker-org` (attacker is a legitimate admin, knows its `webhook_secret`) and `victim-org` (has a stack tracked in Shipit, e.g. `victim-org/app`).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha, guessable/known/forked-history sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s legitimate `webhook_secret` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own secret. [5](#0-4) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit in `victim-org/app` — and calls `create_status_from_github!`, marking it CI-passing regardless of the actual owner/organization used for authentication. [4](#0-3) 
6. If `victim-org/app` has continuous delivery enabled, this forged status can make `deployable?` return true and trigger an unauthorized deploy.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
