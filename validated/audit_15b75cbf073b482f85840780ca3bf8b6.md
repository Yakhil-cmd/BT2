### Title
Unlocked, snapshot-less coin-weighted `system_vote` allows voting power to be rented/bribed to skew OP-list and consensus-parameter elections - (File: main_chain.js)

### Summary
Ocore's `system_vote` mechanism lets any address cast a coin-weighted vote to change the Order Provider (OP/witness) list or core consensus parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`). Because voting weight is the voter's *current* spendable byte balance measured at the moment votes are tallied (not a balance locked or snapshotted at the moment of casting the vote), the exact "buy/bribe temporary voting power" pattern described in the Nouns Builder report (M-20) is directly reachable by an unprivileged unit poster.

### Finding Description
Any address can post a `system_vote` message (`validation.js` case `"system_vote"`) choosing a `subject` such as `op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, or `tps_fee_multiplier`: [1](#0-0) 

Once a `system_vote_count` command triggers tallying, `countVotes()` computes each voter's weight by summing that address's *currently* unspent, stable, good outputs — i.e., its live spendable balance at counting time, not the balance held when the vote was cast: [2](#0-1) 

The temporary voting window can also be expanded ("if too small a share voted in the previous year, expand to 2 years, etc."), but the weight applied to every recorded vote is still the voter's balance at count time: [3](#0-2) 

Votes for `op_list` are tallied purely by summed balance and directly become the new Order Provider/witness set, which drives DAG stability and finality determination: [4](#0-3) [5](#0-4) 

There is no lock-up, vesting, or minimum-holding-duration requirement between casting a vote and the balance being counted — an address only needs to hold a large balance at the point `countVotes` runs. This is architecturally identical to the report's "increase voting power by incentivizing" bug class: a briber can rent, borrow, or temporarily concentrate bytes into voter addresses just long enough for a counting event, cast (or already have cast) a vote, then redistribute the funds — no persistent economic stake is required to swing the outcome of an `op_list` or system-parameter election.

### Impact Explanation
`op_list` votes determine which addresses become Order Providers; the resulting OP set is used by every node to determine main-chain stability and unit finality (`storage.getOpList`, `onSystemVarUpdated`). An adversary who can transiently concentrate enough coin balance (via bribery, rented custody, exchange deposits, or coordinated temporary transfers) into voting addresses can force an `op_list` change to attacker-influenced/malicious Order Providers, or push consensus-critical numeric parameters (`threshold_size`, TPS fee parameters) to attacker-favorable values. A compromised OP set is a path to network-wide disagreement on unit validity/stability and can facilitate double-spend or censorship scenarios, since the whole DAG-stability algorithm is anchored on the OP list.

### Likelihood Explanation
Exploitation requires only posting ordinary `system_vote` units from addresses holding (even temporarily) large byte balances — no special privilege, contract interaction, or network position is needed, matching the "unprivileged unit poster" threat model. The cost is bounded by how long the attacker needs to hold coins across the (multi-day-to-multi-year) counting window and the size of `SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES` needed to dominate turnout, which for a low-participation vote can be modest relative to total supply. This mirrors the C4 finding's core critique: whenever the benefit from swinging governance/consensus outcome exceeds the cost of temporarily acquiring voting weight, the vote is corruptible.

### Recommendation
Snapshot each voter's balance at the time the `system_vote` unit is posted/stabilizes (rather than at count time), and/or require a minimum continuous holding period (time-lock) before a balance counts toward voting weight, similar to snapshot-block voting in token-based DAO governance. Consider requiring votes to be weighted by balances that have remained undisturbed for the full voting window, and/or introducing decay/eligibility rules so freshly-acquired balances cannot immediately dominate a tally, mitigating the rent-a-vote/bribery vector for `op_list` and system-parameter elections.

### Proof of Concept
1. Attacker (or a coalition paid via bribery) accumulates/borrows a large byte balance across several addresses.
2. Each address posts a `system_vote` unit with `subject: "op_list"` (or a numeric subject) choosing the attacker-preferred value, validated per `validation.js` lines 1844-1883.
3. Shortly before/at the moment a `system_vote_count` unit stabilizes and triggers `countVotes()`, the addresses hold their large balances so that `bal_rows` (main_chain.js lines 1757-1773) attributes maximal weight to the attacker's votes.
4. `countVotes()` tallies `op_votes`/`numerical_votes` weighted by these balances (lines 1850-1902) and writes the new `system_vars` value, which is broadcast and applied network-wide via `onSystemVarUpdated` (network.js lines 2157-2182), changing the live OP list or consensus parameter.
5. After the count is finalized, the attacker redistributes/returns the borrowed/bribed funds — no lasting economic stake was required to have swung the vote.
