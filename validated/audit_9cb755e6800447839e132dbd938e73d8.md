### Title
Membership webhook trust bypass grants Shipit team-authorization membership when `webhook_secret` is unset - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
This is a structural analog of H-11: a downstream authorization decision (`User#authorized?`) trusts a value (`Team#members`, sourced from GitHub) whose *provenance guarantee* — the webhook signature — is optional and silently skipped, exactly like the missing "slippage/deadline" guard in the Uniswap fork let stale/attacker-favorable state be acted upon. Here the binding that should hold is: "GitHub organization team membership" == "`Shipit::Team#members` used by `User#authorized?`". That binding is enforced only by HMAC verification of the `membership` webhook, and that verification is unconditionally bypassable when no `webhook_secret` is configured for the organization.

### Finding Description
`GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb`:
```ruby

  return true unless webhook_secret
  ...

``` [1](#0-0) 

If `webhook_secret` is blank (a state explicitly documented as "optional" in `docs/setup.md`), every webhook is treated as verified regardless of its actual signature header or the absence of one.

**Before the attacker's request sequence:** `GITHUB_ID_X` team is genuinely gated to real GitHub org members; attacker's GitHub login has no membership on GitHub and no Shipit session.
**After the attacker's request sequence:** attacker POSTs a forged `membership` `added` event (no valid `X-Hub-Signature` needed, since `webhook_secret` is blank) naming `team.id = GITHUB_ID_X` (learned from GitHub's public team-listing API) and `member.login = <attacker's own GitHub login>`. `Team#members` now contains the attacker's `User` row. Attacker then completes normal GitHub OAuth login (which they are fully entitled to do with their own GitHub account) and `current_user.authorized?` now returns true, granting them a fully authenticated Shipit session with deploy/rollback/lock privileges — despite never having been a member of the real, gating GitHub team.

### Impact Explanation
This breaks the binding "GitHub identity's real team membership == the `User`/`Team` state that `force_github_authentication` trusts to grant a session." The result is authentication-bypass-grade privilege escalation into `Shipit.github_teams` authorization (explicitly listed High-severity impact), and in practice leads to a fully authenticated attacker who can trigger unauthorized deploys/rollbacks (Critical-severity impact) once inside the app.

### Likelihood Explanation
Exploitability is gated entirely on one condition: the target Shipit instance has `github.webhook_secret` unset for the relevant organization — a state the project's own `docs/setup.md` documents as "(optional)". Numeric GitHub team IDs are not secrets (retrievable via the GitHub REST API or web UI for any team in an org the attacker can view), so the only real precondition is the missing webhook secret. Given the code path is entirely unauthenticated (`WebhooksController` has no session/token requirement, and `verify_webhook_signature` returns `true` outright when the secret is blank), likelihood is high for any deployment that has not configured a webhook secret.

### Recommendation
- Make `Shipit.github(...).webhook_secret` mandatory (fail closed) instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`.
- Do not derive the "organization to verify against" (`repository_owner`) from the same unverified payload used later for authorization-affecting side effects; require it to also match the delivering App installation.
- In `MembershipHandler`, cross-check `params.team.id` / `params.organization.login` against a known/expected authorization-relevant team list before mutating `Team#members`, and/or re-validate membership via the GitHub API instead of trusting the webhook body outright for state that feeds `User#authorized?`.

### Proof of Concept
Given a Shipit instance with `Shipit.github_teams` including a team whose GitHub numeric ID is `48` (discoverable via `GET https://api.github.com/orgs/<org>/teams`) and `github.webhook_secret` left blank (per `docs/setup.md` "optional"):

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com"},
  "organization": {"login": "acme-org"},
  "member": {"login": "attacker-github-login"}
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is `nil`/blank. This matches the exact flow exercised in `test ":membership creates the mentioned user on the fly"` in `test/controllers/webhooks_controller_test.rb`, minus a valid signature. [8](#0-7)  After this request, the attacker completes GitHub OAuth as `attacker-github-login` via `GithubAuthenticationController#callback`, and `User#authorized?` now returns `true` due to the injected `Team` membership, granting a fully authenticated Shipit session. [9](#0-8)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
