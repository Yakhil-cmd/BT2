### Title
`StatusHandler#process` matches commits by `sha` alone with no repository/stack scoping, letting a status event for a foreign commit trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` on an unrelated victim stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on the webhook's `repository.full_name`/`repository.owner.login`, so a correctly-signed `status` event referencing any commit SHA present anywhere in the `commits` table gets applied to every matching row, regardless of which stack or organization it belongs to. Since `Commit#add_status` (via `create_status_from_github!`) unconditionally fires `Hook.emit(:deployable_status, stack, ...)` and `stack.schedule_merges` on state transitions, this can enqueue `ProcessMergeRequestsJob` for a stack the webhook's origin repository has nothing to do with.

### Finding Description
Binding claimed broken: `webhook_verified_organization(payload) == stack.repository.owner_login_of(matched_commit)`. Tracing the code:

- `WebhooksController#verify_signature` resolves the signing organization solely from the attacker-controlled payload field: `params.dig('repository','owner','login')` [1](#0-0)  and checks the signature via `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
- `Shipit.github` only differentiates secrets per organization when the multi-app config schema is used; in the default/single-app schema (`github_default_organization` returns `nil`), `config = secrets.github` is used **regardless of the `organization` argument passed in**, so one shared `webhook_secret` authenticates events for every org/repo the App is installed on [3](#0-2) .
- Once signature verification passes, `WebhooksController#create` dispatches to `StatusHandler.call(params)` with no further repository binding [4](#0-3) .
- `StatusHandler#process` looks up commits **purely by `sha`**, with no join/filter on the webhook's repository, org, or stack: [5](#0-4) .
- `Commit#create_status_from_github!` → `Commit#add_status` then fires `Hook.emit(:deployable_status, stack, ...)` and calls `stack.schedule_merges` on qualifying state transitions [6](#0-5) .

Root cause: signature verification authenticates only "this request came from GitHub for organization X's app secret," never "this status event actually originates from the specific repository/stack whose commit is about to be mutated." `StatusHandler` conflates any matching `sha` row anywhere in the database with the sender's actual repository.

Exploit flow: attacker owns (or has push/status access to) a repository serviced by the same GitHub App installation/secret as the victim's stack — a capability explicitly permitted by the rules ("emit webhooks from a repository they own"). Attacker crafts a git commit whose content (tree, parent, author/committer identity and timestamps, message) is byte-identical to a known, public victim commit, producing an identical SHA-1 by construction (not a cryptographic collision — simply identical content). Attacker pushes/triggers a CI status on that SHA in their own repo. GitHub delivers a genuinely signed `status` webhook to Shipit. `verify_signature` passes (correct secret for that org/app). `StatusHandler` then matches the *victim's* `Commit` row by `sha` and fires the victim stack's hooks and `schedule_merges`.

### Impact Explanation
An attacker who never authenticated to, nor holds any secret for, the victim's specific stack can force `Hook.emit(:deployable_status, victim_stack, ...)` (webhook delivery to victim's configured hook URL with attacker-influenced status payload) and enqueue `ProcessMergeRequestsJob` for the victim stack, which drives merge-queue processing (`MergeRequest#merge!` reachable via `schedule_merges`). This is a cross-tenant write triggered by a payload that authenticated only for a different repository/org, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." It is repeatable against any stack whose commit SHA the attacker can reproduce and is not limited to a single victim.

### Likelihood Explanation
Preconditions: (1) the attacker's own repository must be serviced by the same Shipit GitHub App/webhook secret as the victim's stack (true by default when a single GitHub App is installed across many repos/orgs, the documented default configuration, since `github_default_organization` collapses to one shared secret); (2) the attacker must reproduce a victim commit's exact SHA by replicating its full git object content, which is feasible when the victim commit and its metadata are public (a common case for open-source PRs). No Shipit session, API token, or `webhook_secret` value is ever needed by the attacker. This makes the attack cheap and repeatable once the attacker has any repository under the shared App installation.

### Recommendation
Scope `StatusHandler#process` (and analogously any other sha-keyed handler) to the repository identified in the webhook payload, e.g., join through `Stack`/`Repository` on `full_name`/`github_repo_name` before mutating a `Commit`, so a status event can only affect commits that belong to the stack whose repository actually sent it. Additionally, consider binding webhook signature verification to a per-repository/per-stack secret rather than one shared organization/app-wide secret, to reduce blast radius when multiple repositories share a single GitHub App installation.

            StatusHandler.call(attacker_payload)
          end
        end
