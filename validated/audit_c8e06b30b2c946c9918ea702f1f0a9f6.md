Found a clear analog: the `Api::BaseController#identify_user` binding breaks the "GitHub identity vs. `User` bound to the session/request" equality that the rules call out explicitly.

### Title
API requests authenticate as an arbitrary `User` via unverified `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
Shipit's API authenticates the *client* via a signed `ApiClient` token (`Authorization: Basic <token>`), but the *acting user* attributed to the resulting deploy/task/rollback is taken from the unauthenticated `X-Shipit-User` request header, which is resolved to a `Shipit::User` record purely by matching `login` case-insensitively.

### Finding Description
`Api::BaseController#authenticate_api_client` validates the bearer of the request is a legitimate `ApiClient` by verifying a signed token: `ApiClient.authenticate(token)` in [1](#0-0) . That signature only proves *which* `ApiClient` credential is being used and what `permissions`/`stack_id` scope it has (`app/models/shipit/api_client.rb`) [2](#0-1) .

Separately, `current_user` — the identity that gets recorded as the author of a `Deploy`/`Task`/`Rollback` — is derived from `identify_user`, which simply looks up any `User` row whose `login` matches the client-supplied `X-Shipit-User` header, with no cryptographic binding to the authenticated `ApiClient` or any GitHub session at all: [3](#0-2) 

This is exactly the bug-class in the report: two different things are supposed to represent the same principal — the credential that was verified (the `ApiClient`, an application/service credential) and the identity that is bound to and recorded for the action (the human `User` claimed via `X-Shipit-User`) — but only one of them is actually authenticated. The "signature"/verification covers the `ApiClient` token; it never covers the `X-Shipit-User` field. Test coverage confirms the header is trusted at face value and even case-normalized without any additional check: `request.headers['X-Shipit-User'] = @user.login.swapcase` still resolves to that exact user [4](#0-3) .

Contrast this with the browser/session-based flow, where identity is derived only from a server-side session created after GitHub OAuth (`session[:user_id]`) and is never client-suppliable: [5](#0-4)  and [6](#0-5) . The API path has no equivalent binding between the verified credential and the acting identity.

### Impact Explanation
Any caller possessing a valid `ApiClient` token (e.g. a CI system or partner integration issued a low-trust token scoped only to `deploy:stack`) can impersonate *any* `Shipit::User` in the database — including members of privileged `Shipit.github_teams` — simply by setting `X-Shipit-User` to that user's GitHub login. This falsely attributes deploys, rollbacks, and tasks to a different person, defeats audit trails used for approvals/attribution, and can be leveraged to make an unauthorized deploy/rollback appear as though it was performed by an authorized team member, which is squarely in the report's "authentication bypass" / "unauthorized deploy or rollback" impact bucket. It breaks the equality: `identity of verified credential == identity recorded/acted-upon`.

### Likelihood Explanation
Likelihood is High: exploitation requires nothing beyond a single valid `ApiClient` token (which is intentionally distributed to CI/service accounts, i.e., lower-trust callers than full org members) and knowledge of a target user's GitHub login (public information). No additional secrets, sessions, or race conditions are needed — a single crafted HTTP header on an otherwise legitimate API call is sufficient.

### Recommendation
Do not let API callers set the acting user via a client-supplied header. Either derive `current_user` solely from the `ApiClient`'s own `creator`, or require that `X-Shipit-User` be part of the signed/verified token payload (e.g. sign `{api_client_id, user_id}` together) rather than a separate unauthenticated header. At minimum, restrict which `ApiClient`s are permitted to specify `X-Shipit-User` at all, and log/alert when the header is used to assume an identity different from the token's creator.

### Proof of Concept
1. Obtain (or be issued) any valid low-privilege `ApiClient` token, e.g. one scoped only to `deploy:stack` for a low-trust integration.
2. `POST /api/stacks/:owner/:repo/:env/deploys` with:
   - `Authorization: Basic base64(<api_client_token>)`
   - `X-Shipit-User: <login-of-a-privileged-org-member>`
   - body `{ "sha": "<sha>" }`
3. The resulting `Deploy` record's `user` is set to the impersonated privileged user (as shown by the existing test asserting `deploy.user == @user` purely from the header) [7](#0-6) , even though that user never authenticated the request.
