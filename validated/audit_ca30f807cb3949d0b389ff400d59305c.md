### Title
Signature verification keyed on `organization.login` fallback is decoupled from the `repository.full_name` used to select the stack to sync - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate against using `repository_owner`, which falls back to `params.dig('organization', 'login')` when `repository.owner.login` is absent from the payload. `Webhooks::Handlers::Handler#stacks` (used by `PushHandler`) independently resolves the target repository from `payload.dig('repository', 'full_name')`. Because these two fields are never cross-checked, a webhook validly signed for one organization's secret can carry an unrelated `repository.full_name` pointing at a victim stack in a different organization, letting `PushHandler` call `stack.sync_github(expected_head_sha: params.after)` against a repository that never authenticated the request.

### Finding Description
The broken binding the code implicitly assumes is:
`repository_owner` (used to select the verifying secret) == owner of `repository.full_name` (used to select the affected stack).

Trace:
- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that org's `webhook_secret` [1](#0-0) .
- `repository_owner` is defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — an explicit fallback to a wholly separate top-level `organization` object in the payload [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is blank: `return true unless webhook_secret` [3](#0-2) .
- Once past `verify_signature`, `PushHandler#process` (via the shared `Handler#stacks`) resolves the *actual* affected repository from `payload.dig('repository', 'full_name')`, completely independent of `repository_owner` [4](#0-3) .
- `PushHandler#process` then syncs every non-archived stack on the branch and calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4) .

Exploit request: attacker crafts a JSON body with `organization.login` set to an org whose Shipit-configured `webhook_secret` is blank/unset (or one the attacker legitimately administers and thus knows the secret for), and `repository.full_name` set to the victim's repository (omitting or diverging `repository.owner.login`). `X-Github-Event: push` is set, `X-Hub-Signature` is either absent or trivially accepted (blank-secret case). `verify_signature` authenticates the request against the attacker-chosen organization, then `Handler#stacks`/`PushHandler` acts on the victim repository's stacks regardless.

Existing guards do not close this: `drop_unhandled_event` only checks the event type is handled, not the payload's internal consistency; there is no validation anywhere in `WebhooksController`, `Handler`, or `PushHandler` that `repository.full_name`'s owner equals `repository_owner`; `ExplicitParameters` on `PushHandler` only requires `ref` and `after`, not `repository`.

Compounding effect via `ignore_ci`: once `sync_github` appends the attacker-influenced commit(s), the stack's continuous delivery pipeline is triggered on commit creation (`after_create :schedule_continuous_delivery`) in `Commit` [6](#0-5) . On a stack configured with `ignore_ci: true`, CI status checks are bypassed in the deployability logic, so the newly synced commit is immediately considered shippable and can be deployed without any CI gate — turning an authentication mismatch into an unauthorized deploy trigger.

### Impact Explanation
An attacker who can obtain a validly-signed (or trivially-accepted, in the blank-secret case) webhook for *any* organization configured in Shipit can drive `sync_github` on stacks belonging to a completely different, victim repository, by simply setting `repository.full_name` to the victim repo while keeping `organization.login`/`repository.owner.login` pointed at the org whose secret is being used for verification. This is a payload for one repository mutating another's stack/commit — matching the Critical impact category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". On an `ignore_ci: true` stack, the injected commits become immediately deployable, enabling unauthorized deploys of attacker-influenced commit history without any CI gate. The blast radius spans every stack tracked in Shipit, since `PushHandler` has no coupling between the field used for authentication and the field used for target selection.

### Likelihood Explanation
This requires: (1) Shipit deployed in a multi-organization configuration where at least one organization's `webhook_secret` is unset/blank, or the attacker controls a legitimate GitHub org already registered with Shipit (and thus knows/can produce a valid signature for that org); and (2) a victim stack exists with `ignore_ci: true` and continuous delivery configured. Given these preconditions, the attack is a single unauthenticated `POST /webhooks` request, trivially repeatable against any target repository name known to the attacker, with no privileged Shipit role, session, or secret required for the victim side.

### Recommendation
Cross-validate that the owner embedded in `repository.full_name` (the field the handlers actually act on) matches `repository_owner` used for signature verification before any handler processes the payload; alternatively, always resolve the verifying organization strictly from `repository.owner.login` and reject payloads that lack it rather than silently falling back to `organization.login`. Additionally, enforce a non-blank `webhook_secret` requirement for every configured organization so `verify_webhook_signature` can never return `true` unconditionally.

### Proof of Concept
Minitest plan under `test/controllers/webhooks_controller_test.rb`:
1. Configure two orgs in test `Shipit.github`: `org-a` with no `webhook_secret` (or a known test secret) and `org-b` (the victim) with a stack `stacks(:shipit)` where `ignore_ci: true`.
2. Assert the binding before: `repository_owner` (`org-a`) != owner of `stacks(:shipit).repository.full_name` (`org-b`).
3. POST to `/webhooks` with `X-Github-Event: push`, body: `{"organization":{"login":"org-a"},"repository":{"full_name":"org-b/victim-repo"},"ref":"refs/heads/master","after":"<attacker_sha>"}`, no/blank signature matching `org-a`'s blank secret.
4. Assert response is `200`/`:ok` (not `422`), proving verification passed using `org-a`.
5. Assert `stacks(:shipit).commits.exists?(sha: "<attacker_sha>")` or that `Stack#sync_github` was invoked with `expected_head_sha: "<attacker_sha>"` on the `org-b` stack — proving a payload authenticated for `org-a` mutated `org-b`'s stack.
6. Assert the resulting commit's `deployable?` returns `true` on the `ignore_ci: true` stack without any CI status recorded, confirming the amplification.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
