### Title
Webhook signature verification binds only to the claimed organization, not the repository actually mutated, enabling cross-repository writes via a shared GitHub App secret - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the HMAC secret associated with the organization named in `repository.owner.login` (or `organization.login`), but the handlers that actually mutate application state key off a separate, independently-forgeable field in the same JSON body — `repository.full_name` — without ever checking that it belongs to the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

It looks up `Shipit.github(organization: repository_owner)` and verifies the raw body against that organization's `webhook_secret` via HMAC. Once verified, the entire raw body — including the `repository.full_name` field — is handed unchanged to the handlers: [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` from a *different* field of the same body, `repository.full_name`, with no cross-check against `repository.owner.login`/the organization that was actually used for signature verification: [4](#0-3) 

For example, `PushHandler` uses that repository lookup to trigger a real sync/deploy pipeline action, driven entirely by attacker-controlled `ref`/`after` parameters, on whatever stack the resolved `Repository` owns: [5](#0-4) 

Because GitHub Apps have exactly one webhook secret per App (not per installation/organization), any organization that installs the same Shipit GitHub App shares an identical `webhook_secret`. An attacker who controls (or merely installs the app on) their own throwaway organization/repository can therefore:
1. Compute a valid `X-Hub-Signature` over an arbitrary JSON body using the shared secret.
2. Set `repository.owner.login` (and/or `organization.login`) to their own org, so `verify_signature` resolves `Shipit.github(organization: ...)` successfully and passes.
3. Set `repository.full_name` to `victim-org/victim-repo`, a repository they have no access to.

The equality the engine implicitly relies on — *organization authenticated by the HMAC == organization of the repository whose Stack state is mutated* — does not hold. `verify_signature` binds trust to `repository.owner.login`; the handlers bind side effects to `repository.full_name`. Nothing in the request pipeline enforces `repository.owner.login == repository.full_name.split('/').first`, and the two are populated independently in the JSON, so an attacker who knows the App-wide secret can decouple them.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out in scope. Concretely, an attacker with a valid signature for their own organization can:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha: params.after)` on a `Stack` belonging to a repository they do not own [5](#0-4) , triggering out-of-band sync/deploy-pipeline behavior against the victim's stack.
- Drive `StatusHandler`/`CheckSuiteHandler` to write arbitrary commit status/check data against the victim repository's commits.
- Trigger `PullRequest` handlers (opened/closed/labeled/etc.) to mutate `PullRequest`/`ReviewStack` records tied to the victim repository.

This is a cross-repository write: state belonging to a repository the attacker does not control is mutated using only a signature the attacker legitimately possesses for an unrelated organization.

### Likelihood Explanation
Requires only: (a) the ability to install/configure a GitHub App webhook for an organization the attacker controls (or otherwise learn one organization's webhook secret) — no special privilege on the victim's repository, no `ApiClient` token, no session. Because GitHub App webhook secrets are App-scoped rather than per-installation, this is realistic whenever the same Shipit GitHub App is shared across multiple orgs/tenants, which is the deployment model the engine's own multi-organization `Shipit.github(organization:)` lookup is built to support.

### Recommendation
After verifying the HMAC signature, cross-check that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` before dispatching to handlers; reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same verified organization identity used for signature lookup, rather than trusting a second, unverified field from the same payload.

### Proof of Concept
1. Attacker creates organization `attacker-org` and installs the shared Shipit GitHub App on a throwaway repo, obtaining (or already knowing, since it is App-wide) the webhook secret used by `Shipit.github(organization: 'attacker-org')`.
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_for_attacker-org, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, verifies the signature successfully (secret matches, since it's App-wide), and calls `PushHandler.call(params)`.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, despite the attacker having no relationship to `victim-org/victim-repo`.
