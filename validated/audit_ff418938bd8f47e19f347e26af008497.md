### Title
Front-Runnable Deterministic Pool PDA Allows Squatting of `pool_creator` and Permanent Theft of Creator Fees - (File: `programs/cp-swap/src/instructions/initialize.rs`)

### Summary
The `initialize` instruction lets *any* signer become the permanent `pool_creator` of a `(amm_config, token_0_mint, token_1_mint)` pair, because the pool's address is a fully deterministic PDA and the `creator` field is populated with `msg.sender` at creation time with no allow-list or reservation mechanism. An attacker who observes an intended `initialize` transaction in the mempool (e.g. from a token team about to launch and collect creator fees on their own token pair) can front-run it, deploy the pool first, and permanently capture the `pool_creator` role and the future stream of creator fees, blocking the legitimate deployer from ever occupying that identity for that token pair/config combination — the same "squat a scarce identifier via front-run" pattern described in the Aloe `enrollCourier` report.

### Finding Description
`Initialize` is documented as callable by anyone: `/// Address paying to create the pool. Can be anyone` [1](#0-0) . The pool account address is derived deterministically from `POOL_SEED`, `amm_config`, `token_0_mint`, and `token_1_mint` inside `create_pool`, and this exact PDA is what's expected/allocated on-chain: [2](#0-1) .

Because the PDA seeds contain no per-caller or per-attempt nonce, the tuple `(amm_config, token_0_mint, token_1_mint)` can only ever be initialized once — whoever's `initialize` transaction lands first wins that PDA forever, exactly like the fixed `id` in `enrollCourier` that a front-runner can occupy first.

At the end of `initialize`, `pool_state.initialize(...)` stores `ctx.accounts.creator.key()` as the pool's permanent `pool_creator`: [3](#0-2) .

This `pool_creator` field is later used as the sole authority entitled to withdraw accumulated creator fees, both in the signer-gated and permissionless collection paths: [4](#0-3) [5](#0-4) 

Creator fees accrue continuously as swaps occur on the pool (`update_fees` credits `creator_fees_token_0`/`creator_fees_token_1` on every trade): [6](#0-5) .

Since a legitimate token deployer typically wants to be the one who creates the canonical pool for their own token (to receive the ongoing creator-fee revenue), an attacker only needs to observe the mempool for the deployer's `initialize` transaction (mint addresses, and `amm_config_index` which is almost always `0`, both public/predictable — see the client's use of `amm_config_index = 0u16` [7](#0-6) ), then submit their own `initialize` transaction referencing the same mints/config with higher priority fee, permanently seizing `pool_creator` for that pair before the legitimate deployer's transaction executes.

### Impact Explanation
The attacker permanently diverts all future creator-fee revenue from the legitimate token/pool creator to themselves for that specific `(config, mint0, mint1)` tuple — an unauthorized privileged effect and an ongoing theft of value that the pool's fee-accounting explicitly earmarks for "the creator." The legitimate party can never reclaim the `pool_creator` role for that exact deterministic pool because the PDA is already occupied and `pool_state` is already initialized. This is a direct, sustained loss of fee income for the rightful party, and there is no recourse other than abandoning that canonical pool.

### Likelihood Explanation
The attack is cheap (a single `initialize` transaction, requiring only knowledge of the two mint addresses and default `amm_config` index, both of which are public before the target's transaction confirms) and can be executed by any observer of pending transactions/mempool activity. Because `initialize` requires no special permission and the PDA is fully deterministic and reusable seeds contain no anti-squatting nonce, the vulnerability is reliably and repeatedly exploitable against any anticipated pool launch.

### Recommendation
Decouple "who created the pool_state PDA transaction" from "who is entitled to be `pool_creator`." Options:
- Require an explicit authorization/allow-list check (e.g., mint authority signature or a permissioned creator registration step) before crediting `pool_creator` fee rights, rather than trusting `msg.sender` at `initialize` time.
- Alternatively, make the fee-recipient assignable/transferable after creation only by the mint authority, so a front-run pool creation does not permanently lock out the legitimate token issuer from the creator-fee stream.

### Proof of Concept
1. Alice (token deployer) prepares and broadcasts `initialize(token_0_mint = X, token_1_mint = Y, amm_config = default(0))`, intending to become `pool_creator` and later collect creator fees via `collect_creator_fee`.
2. Bob observes this pending transaction, and submits his own `initialize` call with identical `amm_config`, `token_0_mint`, `token_1_mint` accounts but a higher priority fee, so it lands first.
3. `create_pool` allocates the deterministic PDA `[POOL_SEED, amm_config, X, Y]` for Bob's transaction [8](#0-7) ; `pool_state.initialize` records Bob as `pool_creator` [3](#0-2) .
4. Alice's identical transaction now fails (`pool_account_info.owner != &system_program::ID` check fails since the account is already allocated), permanently preventing her from being the pool's fee recipient for that token pair.
5. As swaps occur, creator fees accrue and only Bob can withdraw them via `collect_creator_fee`/`collect_creator_fee_permissionless` [9](#0-8) .

```rust
pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);
    }

    token::create_or_allocate_account(
        &crate::id(),
        payer.to_account_info(),
        system_program.to_account_info(),
        pool_account_info.clone(),
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
            &[bump],
        ],
        PoolState::LEN,
    )?;
```

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;
```
