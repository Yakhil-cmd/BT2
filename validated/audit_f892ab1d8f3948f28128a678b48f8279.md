### Title
Webhook signature is verified against a secret selected by `repository.owner.login`, but the handler acts on an unrelated `repository.full_name` in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to HMAC-verify the raw request body against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . Once the signature is accepted, every registered handler for the event is invoked with the *entire* JSON body [3](#0-2) , and those handlers resolve the target `Stack`/`Repository` from a *different* field of the same payload: `payload.dig('repository', 'full_name')` [4](#0-3) . Nothing in the engine enforces that `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon Stack/Repository) refer to the same repository. This is the same class of bug as the Nayms Diamond report: the value that is authenticated/authorized (the org whose secret validated the signature) is not cryptographically bound to the value that is actually acted upon (the repository being mutated).

### Finding Description
In a Shipit deployment configured for multiple GitHub organizations (a normal multi-tenant setup - `Shipit.github(organization:)` looks up per-org config, and unknown organizations raise `GithubOrganizationUnknown`) [5](#0-4) , each organization has its own `webhook_secret`, known to whoever administers that organization's GitHub App integration in Shipit's config [6](#0-5) .

The controller only checks that the raw body's HMAC matches the secret belonging to the organization named in the payload's `repository.owner.login` field:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

Because an attacker constructs the raw POST body themselves (this is not GitHub relaying a webhook - it is a direct HTTP request to Shipit's `/webhooks` endpoint), they can set `repository.owner.login` to an organization whose secret they legitimately know (their own org administered in the same Shipit instance) while setting `repository.full_name` to `victim-org/victim-repo`. The controller will select and verify against the attacker's own known secret, and the signature check passes since the attacker signed the exact bytes they are sending.

After verification, handlers such as `Shipit::Webhooks::Handlers::Handler#stacks` and `#repository_name` use only `payload.dig('repository','full_name')` to resolve which `Repository`/`Stack` to act on [4](#0-3) , completely ignoring the owner field that was used for authentication. For example, `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` on any stack under the repository named in `repository.full_name` [8](#0-7) ; pull-request handlers use `Repository.from_github_repo_name(params.repository.full_name)` to archive/unarchive/provision review stacks [9](#0-8) [10](#0-9) .

The broken binding, stated as an equality that the engine fails to enforce:
`organization authenticated (secret selected via repository.owner.login) == repository/stack actually written (resolved via repository.full_name)`

### Impact Explanation
An attacker who administers (or has compromised) any single GitHub organization configured in a shared/multi-tenant Shipit instance can forge webhook events against any *other* organization's repositories/stacks tracked by the same instance, without ever needing that victim organization's webhook secret. Depending on which event/handler is targeted this allows:
- Forcing arbitrary `GithubSyncJob` runs on a victim stack (`push`).
- Archiving/unarchiving or force-provisioning review stacks on a victim repository (`pull_request` opened/closed/reopened/labeled handlers).
- Creating team/user memberships (`membership` handler).
- Injecting/forging commit statuses for a victim's commits (`status` handler), which the deploy pipeline may use to gate safety checks (`deploy_spec`'s `ci.require`/`ci.blocking`/`ci.allow_failures` configuration) - this is the path with the most severe consequence, since forged "green" CI status could be used to defeat merge/deploy safety gating and contribute to an unauthorized deploy.

This satisfies the "unauthorized deploy" / cross-repository writes bar in the rubric, since a party authenticated for organization A is able to write state belonging to organization B's stacks/repositories.

### Likelihood Explanation
This requires the Shipit instance to serve multiple GitHub organizations with distinct `webhook_secret`s (the multi-org config shown in `config/secrets.development.shopify.yml` is a supported, documented configuration, not a misconfiguration) and the attacker to control or administer at least one of those organizations - a much weaker requirement than repository write access or an `ApiClient` token on the victim's stack. No cryptographic secret belonging to the victim is required at all; only the ability to craft an arbitrary JSON body with mismatched `repository.owner.login` vs `repository.full_name` fields and sign it with a secret the attacker legitimately possesses.

### Recommendation
Bind the field used for authentication to the field used for authorization/action:
- After selecting the GitHub App/secret via `repository_owner`, verify that `repository.owner.login` matches the owner segment of `repository.full_name` (and reject the request if they diverge) in `WebhooksController#verify_signature`.
- Alternatively, have handlers resolve the target `Repository`/`Stack` using the *same* `repository_owner` value that was used to select the verification secret, rather than independently re-parsing `repository.full_name`.
- Consider signing/validating the whole payload including the "identity" fields as one hash the way the fix for the analogous Diamond Pattern issue did (hash all fields relied upon before trusting any one of them).

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known to attacker, who administers it) and `victim-org` (tracks stack `victim-org/victim-repo`), as in `config/secrets.development.shopify.yml`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (through `Handler#stacks`/`#repository_name`) and triggers `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [8](#0-7) [4](#0-3) , all without the victim organization's webhook secret ever being involved.
