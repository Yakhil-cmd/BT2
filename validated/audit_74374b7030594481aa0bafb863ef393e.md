### Title
`CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, allowing any `read:stack` token to read ccmenu deploy status for any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])` used by `BaseController` and `StacksController`. This means the per-token stack restriction enforced by `BaseController#stacks` is never applied in this controller, so any API client holding the `read:stack` permission can fetch ccmenu XML (deploy id, timestamps, running state) for a stack it was never scoped to.

### Finding Description
The broken binding: `current_api_client.stacks` (the set of stacks a token is authorized to touch, defined as `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) should equal the set of stacks `CCMenuController#show` can actually load. It does not.

- `BaseController#stacks` [1](#0-0)  restricts lookup to `Stack.where(id: current_api_client.stack_id)` when the token is pinned to a specific stack, and `StacksController#stack` correctly uses this scoped relation: `stacks.from_param!(params[:id])` [2](#0-1) .
- `CCMenuController#stack`, however, overrides the method and calls `Stack.from_param!(params[:stack_id])` directly on the model class, never touching `stacks` or `current_api_client.stack_id` at all: [3](#0-2) .
- `require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks that the string `"read:stack"` is present in the token's `permissions` array — it has no notion of *which* stack is being accessed [4](#0-3) . The actual per-stack restriction lives entirely in `stacks`/`stack_id`, which `CCMenuController` doesn't consult.

Attacker flow: attacker holds a legitimate `ApiClient` token scoped via `stack_id` to Stack A (`read:stack` permission granted, e.g. issued for a CI system deploying stack A). They send `GET /stacks/:stack_id/ccmenu.xml?token=...` (or however the route is nested) with `stack_id` pointing to Stack B, a stack they were never granted access to. `require_permission!` passes because the token has `read:stack` generally. `CCMenuController#stack` then loads Stack B via `Stack.from_param!`, completely ignoring that the token is pinned to Stack A only. The response renders `shipit/ccmenu/project` with Stack B's deploy id, timestamps, and running state.

None of the listed guards catch this: `verify_signature`/webhook checks are irrelevant (this is an authenticated API GET), `ExplicitParameters` doesn't validate stack ownership, and `require_permission!`/`check_permissions!` never inspects the target stack — the only place that ever would have caught it is `stacks` scoping in `BaseController`, which this controller's override skips.

### Impact Explanation
Any `ApiClient` token with `read:stack` permission — even one deliberately scoped to a single stack via `stack_id` — can enumerate/read ccmenu status (deploy id, timestamps, running/success state) for every other stack in the installation, not just its own. This is an authorization-scope escalation: a token meant to be confined to one tenant's stack gains read access across all stacks. This matches the "High - unauthenticated/unauthorized read of stack state" impact category (here it's a token-scope bypass rather than fully unauthenticated, but it grants read access far beyond the token's granted scope).

### Likelihood Explanation
Preconditions are minimal and realistic: an operator must have issued at least one `ApiClient` with `read:stack` permission scoped to a specific stack via `stack_id` (a common, intended-safe pattern for giving CI/CD systems narrow access, e.g. to a monitoring dashboard's ccmenu feed). No GitHub secrets, webhook forgery, or special repository configuration is needed — only a valid, narrowly-scoped API token and knowledge/guessing of another stack's `stack_id`/param. The attack is trivially repeatable against every stack in the instance with a single HTTP GET per stack.

### Recommendation
Change `CCMenuController#stack` to use the inherited scoped lookup, consistent with the rest of the API controllers:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This reuses `BaseController#stacks`, which already applies `current_api_client.stack_id?` scoping, and removes the redundant override entirely if no other special-casing is needed.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb` conceptually):
1. Create `stack_a = Shipit::Stack.create!(...)` and `stack_b = Shipit::Stack.create!(...)` under different repositories or environments.
2. Create `api_client = Shipit::ApiClient.create!(creator: user, name: 'scoped', permissions: ['read:stack'], stack: stack_a)` — i.e. `stack_id` pinned to `stack_a.id`.
3. Assert the binding before tracing: `current_api_client.stacks` (via `Stack.where(id: api_client.stack_id)`) == `[stack_a]`, i.e. `stack_b` is NOT in scope.
4. `get "/stacks/#{stack_b.to_param}/ccmenu.xml", params: { token: api_client.authentication_token }` (adjust to actual mounted route for `CCMenuController#show`).
5. Assert response is `403 Forbidden` (expected, matching `stacks` scoping) — but current code returns `200 OK` with `stack_b`'s deploy XML, proving `Stack.from_param!` bypassed `current_api_client.stack_id` scoping.
6. As a control, repeat step 4 for `stack_a.to_param` and confirm `200 OK` is returned (legitimate access still works), isolating the bug to cross-stack access rather than a total auth failure.
