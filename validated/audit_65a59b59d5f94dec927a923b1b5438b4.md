### Title
BLS12-381 host functions charge gas based on the untrusted `value_len` argument instead of the actual bytes processed, allowing underpriced compute when reading input from a register - (File: runtime/near-vm-runner/src/logic/bls12381.rs)

### Finding Description
The `bls12381_impl!` macro computes the per-element gas cost *before* the actual input bytes are fetched: [1](#0-0) 

```rust
self.result_state.gas_counter.pay_base($bls12381_base)?;
let elements_count = value_len / $ITEM_SIZE;
self.result_state.gas_counter.pay_per($bls12381_element, elements_count as u64)?;
let data = get_memory_or_register!(self, value_ptr, value_len)?;
```

`elements_count` (and thus the compute gas charged via `pay_per`) is derived purely from the caller-supplied `value_len` parameter, and is charged *before* `get_memory_or_register!` resolves the real byte slice `data` that is actually parsed/decoded and processed in `p1_sum`/`g1_multiexp`/etc (`data.chunks_exact(ITEM_SIZE)` loops in the `bls12381_fn!` macro, e.g. lines 143 and 176 of the same file). This differs from the pattern used elsewhere in the runtime (e.g. `sha256`) where the per-byte cost is charged using the length of the data actually obtained (`data.len()`), after the read, so the value passed in cannot desynchronize cost from work.

Under NEAR's documented `get_memory_or_register!`/`get_vec_from_memory_or_register` convention, when `value_ptr` equals the sentinel `u64::MAX`, the function does not read `value_len` bytes at `value_ptr` from guest memory; instead it treats `value_len` as a *register id* and returns the full contents of that register regardless of what `value_len`'s numeric value is. This means an attacker fully controls both parameters independently: they can set `value_len` to a tiny value (e.g. `0` or `1`, so `elements_count` computed from it is `0` or negligible) while pointing (via the sentinel) at a register that was previously populated with a large payload (e.g. via `input`, `read_register`, or the output register of a prior host call, up to the configured max register size). The gas metering step (`pay_per`) then charges for essentially zero elements, while the subsequent `$impl_fn_name(&data, version)` call performs elliptic-curve point parsing, subgroup checks, additions/multiplications proportional to the *real* register length via `data.chunks_exact(ITEM_SIZE)`.

No later re-charge based on `data.len()` exists in this macro, so the mismatch between the priced cost and the performed work is never reconciled.

### Impact Explanation
This is a gas-metering completeness violation: the attacker can make the runtime perform elliptic-curve-heavy BLS12-381 operations (`p1_sum`, `g1_multiexp`, `p2_sum`, `g2_multiexp`, decompress/map-to-curve variants) at a cost far below the actual CPU work, by decoupling the charged `elements_count` (derived from the spoofable `value_len` argument) from the real number of `ITEM_SIZE` chunks processed from the register contents. This falls into the gas/metering-bypass impact class: it allows underpriced compute execution reachable by any unprivileged account through a normal `FunctionCall` action, which can be used to cheaply consume validator/chunk-producer compute resources relative to the gas paid, indirectly degrading throughput/availability for other transactions competing for block gas.

### Likelihood Explanation
Exploitation only requires an ordinary contract that: (1) populates a register with a large buffer via a normal host call (e.g. `input`, or the output register of a preceding call), and (2) invokes one of the `bls12381_*` host functions passing `value_ptr = u64::MAX` and `value_len` set to the register id containing that buffer. No special privileges, validator access, or bugs in dependencies are required; the flow is entirely within the standard WASM host-function calling convention available to any deployed contract, making it directly and repeatably reachable via public RPC `FunctionCall` transactions.

### Recommendation
Charge the `$bls12381_element` per-element cost using the length of the actually-resolved `data` buffer (i.e. `data.len() / $ITEM_SIZE`) computed *after* `get_memory_or_register!` returns, instead of `value_len / $ITEM_SIZE` computed before the register/memory read — mirroring the pattern already used by other byte-length-priced host functions (e.g. `sha256`) that charge based on the realized data length rather than the caller-declared length.

### Proof of Concept
Unit test plan in `runtime/near-vm-runner/src/logic/tests/` (or a new test module for `bls12381.rs`):
1. Populate a register (e.g. register `1`) with a buffer encoding `N` valid `(sign_byte || P1 point)` items (`N * ITEM_SIZE` bytes), where `N` is large (e.g. 64).
2. Call `bls12381_p1_sum(value_len = 1 /* register id */, value_ptr = u64::MAX, register_id = 0 /* output */)`.
3. Instrument/inspect `gas_counter` before and after the call: assert that the `pay_per($bls12381_element, elements_count)` call was invoked with `elements_count == 0` (since `1 / ITEM_SIZE == 0`), while the actual work performed in `p1_sum` iterates `data.chunks_exact(ITEM_SIZE).count() == N`.
4. Assert the mismatch: `elements_count_charged (0) != data.chunks_exact(ITEM_SIZE).count() (N)`, demonstrating gas charged does not scale with real compute performed.
5. Expected fix validation: after moving the `pay_per` call to use `data.len() / ITEM_SIZE` post-read, the same test should assert `elements_count_charged == N`.
