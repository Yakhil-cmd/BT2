### Title
Webhook signature verified against attacker-controlled `repository.owner.login`, while handlers act on the independently attacker-controlled `repository.full_name` — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which organization's webhook secret* to validate a request against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body itself. All downstream `Webhooks::Handlers` (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) then resolve the target `Stack`/`Repository` using a *different* field from the same body: `repository.full_name`. Nothing enforces that these two fields refer to the same organization. An attacker who legitimately controls a GitHub App installation/webhook secret for one organization tracked by Shipit can therefore forge webhook deliveries that pass signature verification (using their own valid secret) while acting on a completely unrelated organization's stack.

### Finding Description
`verify_signature` computes the org used to look up the verification secret purely from payload content: [1](#0-0) [2](#0-1) 

Every event handler, however, resolves the `Stack`(s) it acts on from a *different* payload field, `repository.full_name`, via the shared `Handler#stacks`/`#repository_name` helpers: [3](#0-2) 

`Shipit.github(organization:)` is a first-class multi-tenant mechanism (confirmed by the `GithubOrganizationUnknown` rescue path in the controller), meaning a single Shipit deployment can be configured with distinct webhook secrets per GitHub organization. Nothing checks that the organization used to select/verify the secret (`repository.owner.login`) is the same organization referenced by `repository.full_name` used to pick the target repository/stack.

This breaks the equality that should hold: `organization authenticated by verify_signature (repository.owner.login)` == `repository the handler writes to (repository.full_name)`.

Concretely:
1. Attacker legitimately owns/controls the GitHub App/webhook secret configured for `OrgA` (their own onboarded org in this Shipit instance).
2. Attacker crafts a raw JSON body with `repository.owner.login = "OrgA"` (so `verify_signature` looks up and validates against OrgA's real secret, which the attacker knows and can correctly HMAC-sign) but `repository.full_name = "OrgB/victim-repo"` (a totally different, unrelated stack tracked by the same Shipit instance).
3. The signature check passes because it only validates that the body was signed with OrgA's secret — it never checks that `owner.login` is consistent with `full_name`.
4. The dispatched handler (e.g. `StatusHandler`, `PushHandler`, `CheckSuiteHandler`) then resolves stacks via `full_name`/`sha`, operating on `OrgB`'s stack despite the request only being authorized for `OrgA`.

`StatusHandler` is especially exposed since it doesn't even scope by repository — it matches purely on `sha` globally: [4](#0-3) 
so a forged status delivery, authenticated only against OrgA's secret, can flip the CI status of any commit belonging to any tracked stack across the whole instance to `success`.

### Impact Explanation
A forged `status` event lets the attacker mark an arbitrary commit as CI-`success` for a stack they have no legitimate access to. Combined with `Commit#deployable?`/`Stack#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`), this can make a malicious or unreviewed commit eligible for deployment: an operator later clicking "Deploy" (or continuous deployment being enabled) can push the forged-status commit to production — resulting in an unauthorized deploy of a commit that never passed real CI, for an organization/repository the attacker was never authorized to interact with. This maps to the in-scope Critical impact category "an unauthorized deploy" and is a cross-organization/cross-repository write of protocol state (commit statuses, sync triggers) achieved purely with credentials scoped to a different, unrelated organization. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
Requires the attacker to already control a valid webhook secret for at least one organization onboarded to the Shipit instance (a plausible, low-privilege position for a self-service multi-tenant Shipit deployment where many orgs/teams configure their own GitHub App/webhook credentials). No repository write access, session, or `ApiClient` token is needed — only the ability to send an HTTP POST with a correctly HMAC-signed body to the public `webhooks` endpoint, which is by design unauthenticated except for this signature check.

### Recommendation
After verifying the HMAC signature, cross-check that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` (and any other repository identifiers used later, e.g. in `Handler#repository_name`), rejecting the payload if they diverge. Alternatively, resolve the target `Repository`/`Stack` using the same already-authenticated organization value rather than re-deriving it from a second, independently-forgeable field in the same payload.

### Proof of Concept
1. Attacker has legitimate GitHub App/webhook installation and secret for `orga` on the shared Shipit instance.
2. Attacker builds JSON body:
```json
{
  "repository": {"owner": {"login": "orga"}, "full_name": "orgb/victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orga_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orga")` and validates successfully (attacker knows `orga`'s secret) — [1](#0-0) .
5. `StatusHandler#process` runs unscoped by organization, matching `Commit.where(sha: params.sha)` and creating a `success` status on the victim commit belonging to `orgb`'s stack — [4](#0-3) .
