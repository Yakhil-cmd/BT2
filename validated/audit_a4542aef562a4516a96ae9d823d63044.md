### Title
Cross-repository commit-status mutation via unscoped `Commit.where(sha:)` lookup using a well-known degenerate sha - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository/stack constraint, then calls `commit.create_status_from_github!(params)` on every match. Because git shas are content-addressed and not repository-scoped, any attacker who controls a repository can emit a `status` webhook naming a sha that happens to also exist as a `Commit` row on a completely unrelated victim stack — including the universally reproducible empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904` — and mutate that victim's commit status with zero information about the victim beyond it running Shipit at all.

### Finding Description
The intended binding is: **the sha named in a `status` webhook payload belongs to the same repository (`payload.repository.full_name`) that GitHub-signed the delivery** — i.e. `commit.stack.repository.full_name == payload.dig('repository', 'full_name')`. This binding is never checked.

Code path:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the HMAC signature matches the secret registered for `repository_owner` (the org named in the payload itself). It proves "this payload was really sent by GitHub for org X," not "sha S belongs to a commit that was ever pushed to org X's repo." An attacker who owns/controls any repo under any GitHub org can generate a validly-signed webhook for that org.
- The base `Handler` class (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) does provide a `stacks`/`repository_name` scoping helper (`Repository.from_github_repo_name(repository_name)&.stacks`), but `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not use it at all:
  ```
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ```
- This queries `Commit` globally across every stack/repository in the Shipit instance, matching solely on the 40-hex-char `sha` string.

Exploit flow:
1. Victim stack (any repo) has, at some point, a `Commit` row whose sha is `4b825dc642cb6eb9a060e54bf8d69288fbee4904` (the git empty-tree object) or any other attacker-predictable degenerate sha (e.g., a no-op merge/rebase commit with fully attacker-controlled tree/parent/author/committer/date fields that an attacker can also construct in their own throwaway repo to get the identical sha).
2. Attacker pushes/creates a commit with that identical sha in their own controlled repository and configures a webhook (or lets GitHub's app deliver it) for the `status` event on that repo.
3. GitHub signs and delivers the `status` payload to Shipit for the attacker's own repo/org — `verify_signature` passes because it only validates against the attacker's own org's secret.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim's pre-existing `Commit` row (and any other stack in the whole install sharing that sha) purely on sha equality, and calls `create_status_from_github!(params)` on it — writing a `Status` record with attacker-chosen `state`, `description`, `target_url`, and `context` onto the victim stack's commit.
5. `Commit#add_status` (`app/models/shipit/commit.rb:366-386`) then fires `Hook.emit(:commit_status/...)` and, critically, calls `stack.schedule_merges if new_status.pending? || new_status.success?` — meaning an attacker-forged `success` status can trigger the victim stack's continuous-merge/deploy pipeline.

No other guard intervenes: `drop_unhandled_event` only checks the handler exists for the event type; `ExplicitParameters` only validates the shape of `sha`/`state` strings, not ownership; there is no `require_permission!`/`stacks` scoping call inside `StatusHandler`.

### Impact Explanation
An unauthenticated-relative-to-the-victim attacker (only needing to control any single repo wired to the same Shipit instance) can write arbitrary `Status` rows — including forged `success` statuses — onto a victim stack's commit that they do not control. Since commit status can gate `deployable?`/`blocking?` and trigger `schedule_merges`/`ContinuousDeliveryJob`, this is a cross-repository payload mutating another repo's stack/commit, which can enable an unauthorized deploy. This matches the **Critical** category: "a payload for one repository mutating another's stack, commit, task or team... or an unauthorized deploy". Blast radius spans every stack/tenant hosted by the same Shipit instance sharing sha space, and the degenerate-sha variant requires no reconnaissance of the victim at all.

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository/org they control that is registered as a webhook source Shipit will accept a signed delivery from (any repo with Shipit's GitHub App/webhook installed satisfies `verify_signature`, since it only checks against that repo's own org secret). The empty-tree sha is universal and requires zero interaction with the victim; alternatively, ordinary no-op merge commits GitHub itself creates can coincidentally collide across independent histories. Attacker cost is minimal — one crafted commit and a naturally-triggered `status` webhook (e.g., from a CI check on the attacker's own repo). This is fully repeatable and requires no elevated privilege.

### Recommendation
Scope the commit lookup to the reporting repository, analogous to the `stacks`/`repository_name` helper already present in the base `Handler` class:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently, join through `Stack`/`Repository`:
```ruby
Commit.joins(:stack).merge(stacks).where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
ensuring only commits belonging to stacks whose `Repository.from_github_repo_name` matches `payload.dig('repository','full_name')` can be updated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status webhook from an unrelated repository does not mutate a victim commit sharing a well-known sha" do
  victim_stack = shipit_stacks(:shipit)
  degenerate_sha = "4b825dc642cb6eb9a060e54bf8d69288fbee4904"
  victim_commit = victim_stack.commits.create!(sha: degenerate_sha, message: "empty tree", author: shipit_users(:walrus))

  attacker_payload = {
    'sha' => degenerate_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  victim_commit.reload
  assert_not_equal 'success', victim_commit.status.state
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `attacker_payload['repository']`, so the assertion fails, demonstrating the equality `commit.stack.repository.full_name == payload['repository']['full_name']` is not enforced.
