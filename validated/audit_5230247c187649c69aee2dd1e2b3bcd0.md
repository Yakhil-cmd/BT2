## Confirmed root cause

`Shipit::WebhooksController#verify_signature` selects the HMAC secret used to authenticate a webhook based on **one** field of the untrusted, unparsed JSON body — `repository.owner.login` (or `organization.login`) — and then verifies the signature over the raw body: [1](#0-0) [2](#0-1) 

Once verification passes, the event is handed unfiltered to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) , and every handler resolves **which repository/stack to mutate** from a *different* field of the same body — `repository.full_name` — via `Handler#repository_name`/`#stacks`: [4](#0-3) 

and identically in the pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`) via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`.

Nowhere is `repository.full_name`'s owner segment cross-checked against `repository.owner.login`/`organization.login`, the field that was actually used to pick the trust anchor (the per-organization `webhook_secret`, see `Shipit.github(organization:)` and `github_app_config` in `lib/shipit.rb` lines 170–200, and `GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb` lines 76–83).

**Equality that should hold but doesn't:** `organization_that_authenticated(repository.owner.login) == organization_of(repository.full_name)`.

## Why this is the same bug class as the report

In the `Checkpoint.sol` bug, `validSignersCount` (used to compute the trust threshold) is decremented by a subset of the same submission the check is meant to validate, so the entity that ultimately gets trusted is not the one the check was nominally protecting. Here, the trust anchor (which organization's secret authenticates the request) is likewise derived from a field inside the very payload whose *other* field (`full_name`) determines what gets written — and these two fields are never bound to each other. Under Shipit's documented multi-tenant "Using Multiple GitHub Applications" mode (`docs/setup.md`, `github_app_config`), each organization has its own independently-configured `webhook_secret`. Whoever legitimately controls organization A's GitHub App (and therefore genuinely knows/can produce validly-signed deliveries for org A, since they configured that App's secret when installing it) can compose a webhook body where `repository.owner.login = "orgA"` (so `verify_signature` picks org A's secret and it matches) while `repository.full_name = "orgB/victim-repo"` (so the handler acts on org B's stack). This is a forgeable cross-organization request because the signature check and the object-selection logic key off different, uncorrelated fields of attacker-influenced JSON.

## Impact

This breaks the repository/organization write boundary: a party who legitimately administers one onboarded GitHub App/organization in a multi-org Shipit deployment can trigger `push`/`pull_request`/`status`/`check_suite` handling against a stack belonging to a **different** repository or organization they do not control — e.g. forcing `GithubSyncJob`, archiving/unarchiving review stacks, or feeding fabricated commit statuses into the merge queue for another org's repository, which can influence unauthorized merges. This matches the "cross-repository writes" / "unauthorized deploy, rollback or merge" impact tier.

## Uncertainty / limits of this analysis

I could not fully trace whether every consumer of `params` (in particular the `status_handler`, `check_suite` handler, and `membership_handler`) performs any additional owner/full_name consistency check, since the index does not surface their full source; I only confirmed the pattern in `handler.rb` (base class, inherited by `PushHandler`) and the `pull_request/*_handler.rb` files. I also could not verify from the index whether Shipit's operators, in practice, always configure a single shared GitHub App (single-org mode) — in which case this analog would not be exploitable, since there'd be only one webhook secret shared by all repos and `repository_owner` would always resolve to the same trust anchor regardless of value. The multi-app support is real and documented, but I have no visibility into deployment-specific configuration, so likelihood depends on that operational choice. Given this, I present the finding but flag this precondition explicitly.

### Title
Cross-organization webhook forgery via inconsistent trust binding between `repository.owner.login` and `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`) from the untrusted payload, while every `Webhooks::Handlers::Handler` subclass resolves the repository/stack to mutate using a different payload field, `repository.full_name`. These two fields are never cross-validated, so in multi-organization deployments (`Shipit.github_organizations`/`github_app_config`), a party controlling one organization's webhook secret can forge a payload whose `owner.login` matches their own org (passing signature verification) but whose `full_name` names a stack belonging to a different organization/repository, causing Shipit to process the event against that unrelated stack.

### Finding Description
Signature verification: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, request.raw_post)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [5](#0-4) . `Shipit.github(organization:)` looks up a per-organization config, including a distinct `webhook_secret`, via `github_app_config` [6](#0-5) , and `verify_webhook_signature` HMACs the raw request body with that org's secret [7](#0-6) .

Object resolution: every handler independently derives the target repository from `payload.dig('repository','full_name')` via `Handler#repository_name`/`#stacks` [4](#0-3) , or the equivalent in PR handlers (`Shipit::Repository.from_github_repo_name(params.repository.full_name)`), e.g. [8](#0-7) .

No code path checks that the owner segment of `full_name` matches `repository.owner.login`/`organization.login`. Because the whole raw body is HMAC'd by whichever secret corresponds to the *claimed* owner field, anyone who knows that org's secret can self-sign an entirely self-consistent-looking payload whose `full_name` field targets an unrelated org/repo.

### Impact Explanation
In a multi-org Shipit configuration, this allows a legitimately-onboarded organization (or anyone who has obtained that organization's `webhook_secret`) to trigger stack mutations for another organization's repositories without holding write access to them — cross-repository/cross-organization writes, e.g. forcing sync jobs, provisioning/archiving review stacks, or injecting forged commit statuses that feed the merge queue, potentially enabling an unauthorized merge.

### Likelihood Explanation
Requires the deployment to run in multi-GitHub-App mode with per-organization secrets (a supported, documented configuration) and requires the attacker to know or control one organization's registered webhook secret — a realistic scenario for any org onboarded to a shared/multi-tenant Shipit instance. In single-app deployments (`github_default_organization` is `nil`), the same secret is used for all payloads, so this specific analog is not exploitable; likelihood is therefore configuration-dependent, which I could not verify against a specific production deployment.

### Recommendation
After signature verification succeeds, validate that the owner segment of `repository.full_name` (or `organization.login`) is consistent with the `repository_owner`/organization used to select the verifying secret, and reject the webhook (422) if they diverge, mirroring how `Checkpoint.sol` was fixed by anchoring the consensus check to a single authoritative value (`originalValidSignersCount`) rather than one derived independently from attacker-influenced state.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub Apps: `secrets.github` contains `orgA: { webhook_secret: S_A, ... }` and `orgB: { webhook_secret: S_B, ... }`, with `orgB` having a real repository/stack, e.g. `orgB/victim-repo`.
2. As the operator/holder of `S_A` (legitimately onboarded org A), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "orgA")` and successfully verifies the signature against `S_A`.
5. `PushHandler#process` resolves `stacks` from `payload.dig('repository','full_name') == "orgB/victim-repo"` [4](#0-3)  and enqueues `stack.sync_github(expected_head_sha: params.after)` against org B's stack, even though the request was authenticated only against org A's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      return true unless webhook_secret
