### Title
Cross-organization CI status forgery bypasses per-organization webhook signature binding, enabling unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the GitHub organization derived from the payload's `repository.owner.login` (or `organization.login`) field, using that organization's configured `webhook_secret`. [1](#0-0)  However, the handler that actually performs the write — `Shipit::Webhooks::Handlers::StatusHandler#process` — never checks that the target `Commit` belongs to a repository/stack owned by the organization that was verified; it looks up `Commit.where(sha: params.sha)` globally across every tracked repository and creates a status on whatever commits match. [2](#0-1)  This is the same class of trust-binding break as the Centrifuge finding: the entity that is cryptographically verified (the organization whose secret validated the signature) is not the entity that the subsequent state-changing operation actually operates on (an arbitrary commit belonging to any repository/organization tracked by the same Shipit instance).

### Finding Description
Shipit explicitly supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret`/app credentials, keyed by organization name in `secrets.yml`. [3](#0-2)  The webhooks controller resolves which organization's app/secret to validate the signature against purely from attacker-controlled payload fields:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

`verify_signature` then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. it only proves the request was signed by *some org's* secret that matches the `repository.owner.login` claimed in the same untrusted payload — it never binds that verification to the object the handler will subsequently mutate. [5](#0-4) 

Once past that gate, dispatch is entirely payload-driven: `Handler#stacks` normally scopes lookups by `payload.dig('repository', 'full_name')`, [6](#0-5)  but `StatusHandler` doesn't even use that scoping — it queries commits by SHA alone, with no repository/organization constraint whatsoever:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

The equality that should hold but doesn't:
`organization verified by signature (repository_owner in payload)` == `organization owning the repository/commit actually written to (Commit.where(sha:))`.

Before the attack: signature verification for org A only allows forging events "as org A." After: because the target of the write (`Commit.where(sha:)`) is completely decoupled from the verified org, an attacker who controls org A's webhook secret (their own legitimate, unrelated GitHub org integrated with the same Shipit instance) can set `repository.owner.login = "OrgA"` to pass signature verification, while setting `sha` to a commit SHA that actually belongs to a stack under a victim organization "OrgB" tracked by the same Shipit instance. `StatusHandler` will happily create/overwrite a commit status on that victim commit.

### Impact Explanation
Commit statuses gate deployability in Shipit (`ci.require` in `shipit.yml`, `deployable?`) — forging a `success` status for a required CI context on a victim commit that has not actually passed CI lets an attacker satisfy deploy safety checks for a stack/repository they have no legitimate relationship with, and thereby trigger an unauthorized deploy of that commit through Shipit's normal deploy flow. This falls under the accepted High-impact category "unauthorized deploy," since the attacker never needs a Shipit session, `ApiClient` token, or GitHub write access to the victim's repository — only a valid webhook secret (or none, since `verify_webhook_signature` trivially returns `true` when an org has no secret configured) for any one organization hosted on the shared Shipit instance. [7](#0-6) 

### Likelihood Explanation
This requires the deployment to be running Shipit's documented multi-organization configuration (multiple GitHub orgs on one Shipit instance), which is an explicitly supported and documented setup. [3](#0-2)  Given that configuration, the attack needs only knowledge of one organization's own webhook secret (which the attacker, as an admin of their own org, legitimately possesses) — no compromise of the victim organization or Shipit credentials is required. Likelihood is Medium-High in multi-org deployments and not applicable to single-org deployments.

### Recommendation
`StatusHandler` (and any other handler) must scope its lookups by the repository derived from `payload.dig('repository', 'full_name')` and cross-check that this repository's `owner` matches the organization that was cryptographically verified in `verify_signature`, rejecting the webhook otherwise. More generally, `WebhooksController` should pass the verified organization into each handler and have `Handler#stacks`/any commit lookups filter by `Repository.owner == verified_organization`, not merely by attacker-supplied `full_name`/`sha` fields.

### Proof of Concept
1. Deploy Shipit configured with two GitHub organizations, `OrgA` (attacker-controlled) and `OrgB` (victim, hosting the tracked stack), per the documented multi-org `secrets.yml` schema. [3](#0-2) 
2. Attacker knows/owns `OrgA`'s webhook secret (or `OrgA` has no `webhook_secret` configured, in which case signature verification is a no-op). [7](#0-6) 
3. Attacker crafts a `status` event payload:
   - `repository.owner.login = "OrgA"` (used only to select which secret validates the HMAC)
   - `sha = <victim commit sha under OrgB's tracked stack>`
   - `state = "success"`, `context = "<required CI context for OrgB stack>"`
4. Attacker signs the payload with `OrgA`'s webhook secret (or sends unsigned if `OrgA` has none) and POSTs to `/github/webhooks`.
5. `verify_signature` passes because it only validates against `OrgA`'s secret. [5](#0-4) 
6. `StatusHandler#process` finds the commit purely by `sha` (no org/repo check) and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto the victim's commit. [2](#0-1) 
7. If that context is in `OrgB`'s stack's `ci.require` list, the forged status now satisfies the deploy safety check, letting the attacker (or anyone) trigger a deploy of that commit that would otherwise have been blocked.

Note: I was unable to fully trace `Commit#create_status_from_github!` and the exact `ci.require`/`deployable?` gating logic within this iteration's tool budget; a Devin session with full repo access should confirm the precise code path from forged `Status` record to `Commit#deployable?`/`ci.require` enforcement in `app/models/shipit/commit.rb` and `app/models/shipit/deploy_spec.rb` to finalize the PoC end-to-end.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
