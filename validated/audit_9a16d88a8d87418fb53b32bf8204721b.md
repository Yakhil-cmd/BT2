Confirmed: there is no rule in `validateAssetDefinition` (validation.js:2725-2800) requiring `cap` to imply `issued_by_definer_only`. An asset can legally be defined with `cap: N` and `issued_by_definer_only: false`. This makes the double-issuance bug reachable.

### Title
Capped assets with `issued_by_definer_only=false` can be issued multiple times by different addresses, inflating supply beyond the declared cap - (File: validation.js)

### Summary
Similar to the reported bug where the zero address bypassed the "already registered"/"already refunded" dedup guard because the guard's uniqueness scope didn't cover that special case, ocore's issue-input double-spend check for asset issuance narrows its uniqueness scope to `(asset, serial_number, address)` instead of `(asset, serial_number)` whenever the asset is not `issued_by_definer_only`. For capped assets this collapses the intended global "one-time issuance up to cap" guarantee into a per-address guarantee, letting every distinct address independently issue the full `cap` amount once.

### Finding Description
In `validatePaymentInputsAndOutputs` (validation.js), the "issue" input case builds the double-spend detection query: [1](#0-0) 
```
doubleSpendWhere = "type='issue'";
doubleSpendVars = [];
doubleSpendWhere += " AND denomination=?";
doubleSpendVars.push(denomination);
if (objAsset){
    doubleSpendWhere += " AND serial_number=?";
    doubleSpendVars.push(input.serial_number);
}
if (objAsset && !objAsset.issued_by_definer_only){
    doubleSpendWhere += " AND address=?";
    doubleSpendVars.push(address);
}
``` [2](#0-1) 

For a capped asset, `serial_number` is forced to `1` for every issuer: [3](#0-2) 

and the issue amount must equal the cap: [4](#0-3) 

The underlying storage-level uniqueness constraint mirrors this scoping — it includes `address` in the key: [5](#0-4) 

So, when `issued_by_definer_only` is `false` (which `validateAssetDefinition` never forbids in combination with `cap`, see validation.js:2725-2800), the double-spend/uniqueness check is scoped **per issuing address**, not globally per asset. Every distinct address can therefore submit its own single-authored unit with an `issue` input of `serial_number=1, amount=cap` for the same capped asset, and each such unit passes validation independently because none of them collides on the `(asset, denomination, serial_number, address)` key.

This is the direct analog of the `PolicyProposals` bug: a guard meant to enforce a single, canonical action ("only one issuance of the capped supply" / "only one registration of a proposal") is scoped by an extra dimension (issuer address / zero address) that a caller fully controls, letting the caller manufacture new "eligible" instances of the guarded action and bypass the intended global limit.

The composer-side helper that is supposed to prevent this (`SELECT 1 FROM inputs WHERE type='issue' AND asset=?` in `aa_composer.js:1195-1200` and `inputs.js:264-269`) only protects a well-behaved wallet/AA composing its own transaction — it is not a consensus rule. The actual consensus-level check enforced by `validatePaymentInputsAndOutputs`/`checkForDoublespends` is the one shown above, and it is the one that is scoped incorrectly for non-definer-restricted capped assets.

### Impact Explanation
This is a direct **supply inflation** vulnerability for any capped asset defined without `issued_by_definer_only: true`. An attacker (any unpriviledged unit poster, or any AA acting as multiple addresses) can post issue transactions from N different addresses, each minting the full `cap` amount, producing up to N× the declared total supply of the asset. Any application, exchange, or AA (e.g. an AMM/market maker or ICO contract in `test/samples/*.oscript`) that trusts `asset[...].cap` as a hard supply ceiling would be misled, and downstream token holders/liquidity pools could suffer fund loss once the market discovers the real (inflated) supply.

### Likelihood Explanation
High. No special privileges, hub cooperation, or protocol upgrade timing window is required — an attacker only needs to define the asset (or find an existing capped asset defined by someone else with `issued_by_definer_only:false`) and post ordinary `asset`/`payment` (issue) messages from multiple addresses they control. All of the involved code paths (`validateAssetDefinition`, `validatePaymentInputsAndOutputs`) are on the hot path for any unit posted to the DAG.

### Recommendation
Scope the issue double-spend/uniqueness check for capped assets by `(asset, denomination, serial_number)` only, regardless of `issued_by_definer_only`, i.e. remove the address-scoping exception when `objAsset.cap` is set. Alternatively, require in `validateAssetDefinition` that `cap` can only be combined with `issued_by_definer_only: true`, closing the combination that makes the mis-scoped guard reachable.

### Proof of Concept
1. Author A posts an `asset` definition message with `cap: 1000000, issued_by_definer_only: false, is_private:false, is_transferrable:true, fixed_denominations:false, auto_destroy:false, cosigned_by_definer:false, spender_attested:false`. This is accepted because `validateAssetDefinition` (validation.js:2725-2800) does not forbid `cap` + `issued_by_definer_only:false`.
2. Address A posts a `payment` message for this asset with an `issue` input: `{type:"issue", amount:1000000, serial_number:1}`. It validates: `serial_number===1` (required for capped assets, validation.js:2321-2324), `amount===cap` (validation.js:2345-2346), and the double-spend key is `asset|denomination|serial_number|address=A` (validation.js:2366-2373) — first occurrence, so it passes.
3. Address B (different keypair, no relationship to A) posts its own single-authored unit with the same `issue` input `{type:"issue", amount:1000000, serial_number:1}` for the same asset. Because `issued_by_definer_only` is `false`, the double-spend key now differs only in `address=B`, so this unit does **not** collide with A's issuance and is also accepted.
4. Repeat for addresses C, D, … Each additional address can mint another full `cap` (1,000,000) units of the asset, so total circulating supply becomes `N × cap` instead of the intended `cap`, violating the asset's declared supply ceiling — the ocore analog of the reported "guard bypass leading to fund/state corruption" bug.
