### Title
Unbounded loop over all unstable messages in `readDataFeedValue`/`dataFeedExists` can degrade AA/unit validation throughput - (File: data_feeds.js)

### Summary
The bug class described in the TWAP oracle report is an unbounded loop that walks an ever-growing collection on every operation, with no cap and no way to shrink or skip entries, eventually making the operation too expensive to complete reliably. In `ocore`, the "unstable" branch of the data-feed lookup functions exhibits the same pattern: every time an unprivileged unit poster or AA trigger sender references an oracle's not-yet-stable data feed (via the `data_feed`/`in_data_feed` oscript opcodes or the `"in data feed"` address-definition condition), the code performs a full, unbounded `for...in` scan of `storage.assocUnstableMessages`, i.e. every message of every currently-unstable unit in the whole DAG, rather than a scan limited to the relevant oracle address(es).

### Finding Description
`readDataFeedValue()` and `dataFeedExists()` in `data_feeds.js` both branch on `bIncludeUnstableAAs`/`bAA` and, in that branch, iterate the entire in-memory dictionary of unstable messages: [1](#0-0) 

```
if (bIncludeUnstableAAs) {
    var arrCandidates = [];
    for (var unit in storage.assocUnstableMessages) {
        ...
        storage.assocUnstableMessages[unit].forEach(function (message) { ... });
    }
    ...
}
```

and the analogous loop in `dataFeedExists`: [2](#0-1) 

Both loops walk **every** unstable unit's messages in the whole network (filtering only after entering the loop body), regardless of how many oracle addresses are of interest. This code path is reachable by an unprivileged trigger sender through the `data_feed[[...]]`/`in_data_feed[[...]]` oscript expressions evaluated during AA execution: [3](#0-2) [4](#0-3) 

and by any unprivileged unit poster whose address definition uses the `"in data feed"` authentifier condition, which is evaluated during ordinary unit validation: [5](#0-4) 

Unlike the array-literal/dictionary/foreach evaluation paths in the same formula engine, which are explicitly capped (100-element array/dictionary literals, `foreach`/`map`/`filter`/`reduce` counts bounded and checked against the actual element count, delete-selectors capped at 30, statement count capped at 1000): [6](#0-5) [7](#0-6) 

there is **no** corresponding bound on the size of `storage.assocUnstableMessages` that is scanned when resolving an unstable data feed. `assocUnstableMessages` accumulates one entry per unstable unit network-wide and is only cleaned up as units become stable in `main_chain.js`'s `saveUnstablePayloads()`: [8](#0-7) 

Because stabilization itself depends on continued unit posting and witnessing, and because any user can post units (including many "unstable" units in quick succession), the size of `assocUnstableMessages` that must be scanned per data-feed lookup is effectively attacker-influenceable and not bounded by AA formula complexity/gas accounting, unlike the rest of the formula evaluator.

### Impact Explanation
Every AA that uses `data_feed()`/`in_data_feed()` with `unstable_opts` (or any address definition using `"in data feed"`) forces every full node validating that unit/trigger to perform an O(number of currently unstable units) scan. As the count of unstable units grows (e.g., during periods of high transaction volume or if an attacker deliberately posts many units that remain unstable for longer), every single such lookup becomes progressively more expensive. Since this validation work must be repeated by every node in the network for every unit/trigger that touches this code path, a sustained increase in unstable-unit count degrades validation throughput network-wide, which can push nodes toward being unable to keep up with confirming new units in a timely manner — the same "network unable to confirm new units" class of impact called out for the TWAP oracle bug, rather than a one-shot out-of-gas failure.

### Likelihood Explanation
This requires no special privilege: any unit poster or AA trigger sender can invoke `data_feed`/`in_data_feed` with unstable options, or use `"in data feed"` in their address definition, and the size of the scanned collection grows naturally with network activity (and can be inflated by anyone flooding the network with units). The relevant contributor already disagreed with high severity for the original TWAP finding on the grounds that it required unusual/ill owner behavior; here the trigger condition (posting units) requires no privileged action at all, but the growth of `assocUnstableMessages` is still bounded in practice by the DAG's ongoing stabilization, making sustained, severe degradation harder to achieve than a permanent lock — this is a resource-degradation issue tied to network load rather than a guaranteed permanent denial of service.

### Recommendation
- Index `assocUnstableMessages` by author address (or maintain a secondary per-address index) so unstable data-feed lookups only scan messages authored by the requested oracle address(es), instead of the entire unstable-unit set.
- Alternatively, apply an explicit cap (mirroring the caps already used elsewhere in the formula engine, e.g. the 100-element array/dictionary or foreach-count limits) on the number of unstable units/messages inspected per lookup, and fail fast or fall back to stable-only lookup once the cap is exceeded.
- Factor the size of `storage.assocUnstableMessages` into AA formula complexity/op-count accounting so the cost is reflected in the fees charged, discouraging abuse.

### Proof of Concept
1. Deploy an AA whose formula calls `data_feed[[oracles=..., feed_name=..., ...]]` (or `in_data_feed[[...]]`) with the unstable-inclusion option, or post a unit whose address definition contains `["in data feed", [...]]`.
2. Have many units posted network-wide in a short window so that `storage.assocUnstableMessages` (visible via `main_chain.js`'s bookkeeping, populated for every unstable unit) grows large before those units stabilize.
3. Trigger the AA (or post/validate a unit using the `"in data feed"` condition) repeatedly while the unstable set is large; observe that `dataFeedExists`/`readDataFeedValue` (`data_feeds.js` lines 34-94 and 211-241) must scan the full, unbounded `for...in storage.assocUnstableMessages` loop on every single invocation, with cost scaling linearly with total network unstable-unit count rather than with the number of oracles actually queried.
