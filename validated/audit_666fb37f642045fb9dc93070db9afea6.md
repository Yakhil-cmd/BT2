### Title
Missing `return` after payload-hash exception causes duplicate mutex unlock and process crash on malformed private payment - ([File: network.js])

### Summary
A private-payment counterparty can send a private payment chain whose head element has a malformed `payload` (any value that `objectHash.getBase64Hash()` cannot serialize/hash, e.g. a value that throws inside `getBase64Hash`, such as unsupported types or excessively deep/foreign structures). When this chain reaches `handleSavedPrivatePayments()`, the resulting exception is caught but the code fails to `return` from the handler, causing the payment to be processed twice and the completion callback to be invoked twice for the same queued item. This double-invocation eventually calls `unlock()` twice on the same mutex key, hitting a deliberate `throw Error("double unlock?")` guard, which is an uncaught exception that the process intentionally rethrows to crash the node.

### Finding Description
In `handleSavedPrivatePayments()` the per-chain handler computes a payload hash inside a `try/catch`: [1](#0-0) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (attacker controls `payload` fully, since it originates unvalidated from network-received `arrPrivateElements` stored in the `unhandled_private_payments` table via `handleOnlinePrivatePayment`/`savePrivatePayment`), the `catch` block calls `deleteHandledPrivateChain(..., cb)` — which already invokes the `async.each` per-item completion callback `cb` — but the function does **not** `return` after this. Execution falls through to the un-guarded lines below the `try/catch` and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` a second time on the same malformed data: [2](#0-1) 

That second call will again resolve via one of `ifOk`/`ifError`/`ifWaitingForChain`, each of which also calls the same `cb` (directly or through `deleteHandledPrivateChain`). `cb` is thus invoked twice for the same `async.each` item, causing the group's final callback (which calls `unlock()` on the `"saved_private"` mutex key) to fire more than once: [3](#0-2) [4](#0-3) 

`mutex.js`'s `exec()` guards against exactly this with an explicit crash-on-purpose check: [5](#0-4) 

The resulting `Error("double unlock?")` is an uncaught exception. `network.js` installs a handler that deliberately rethrows any uncaught exception to terminate the process rather than continue in an inconsistent state: [6](#0-5) 

The input path is reachable by any private-payment counterparty: private payment chains are accepted from peers/hub messages without validating that `payload` is hashable before it is persisted into `unhandled_private_payments` and later replayed through `handleSavedPrivatePayments()`: [7](#0-6) [8](#0-7) 

### Impact Explanation
Any node that has a wallet and receives private payment chains (a normal function of `ocore`-based wallets) can be crashed remotely by any private-payment counterparty by sending one malformed private-payment chain whose head payload cannot be hashed. This is a direct, reproducible denial-of-service against a full/light wallet node — the same class of impact as the CVE-2017-6464 NTP crash-via-malformed-directive bug: a small malformed input drives an unhandled error path that terminates the daemon.

### Likelihood Explanation
High reachability: no special privileges, hub cooperation, or race condition needed beyond being a paired/known correspondent (or, depending on `arrSubjectsAllowedFromNoncorrespondents` whitelisting for the "chat" delivery path, potentially even before pairing completes for specific subjects). The attacker fully controls the shape of `arrPrivateElements[0].payload`, so triggering an exception inside `objectHash.getBase64Hash` is straightforward (the function is defined to throw on certain malformed/incompatible structures). The missing `return` is a simple, deterministic control-flow bug, not a race — it fires on every occurrence of the hash failure.

### Recommendation
Add a `return` immediately after `deleteHandledPrivateChain(...)` inside the `catch` block in `handleSavedPrivatePayments()` (network.js line ~2476) so the function does not fall through to a duplicate `validateAndSavePrivatePaymentChain` call. Additionally, harden `mutex.exec`'s unlock guard to log-and-ignore (or safely no-op) a double-unlock instead of throwing/crashing the whole process, and validate `payload` shape/hashability before persisting to `unhandled_private_payments`.

### Proof of Concept
1. As a paired correspondent device (or via a whitelisted "chat" subject before pairing, if applicable), construct a private-payment chain whose head element's `payload` is a value that causes `objectHash.getBase64Hash()` to throw (e.g., a payload containing a type not supported by the hashing/serialization logic, or crafted to exceed internal invariants checked by `objectHash`).
2. Send this chain to the victim node as a private payment (through chat/device message flow that leads to `handleOnlinePrivatePayment` → `savePrivatePayment` → `unhandled_private_payments`, or directly if `conf.bLight` chain-length conditions apply).
3. Once `handleSavedPrivatePayments()` processes the row, `getBase64Hash` throws, the `catch` block runs `deleteHandledPrivateChain(..., cb)` without returning, and control falls through to a second `validateAndSavePrivatePaymentChain` call, causing `cb` to fire twice for the same item.
4. `async.each`'s final callback executes `unlock()` more than once on the `"saved_private"` mutex key, triggering `mutex.js`'s `throw Error("double unlock?")`.
5. `network.js`'s `process.on('uncaughtException', ...)` handler rethrows the error, crashing the node process.

Note: I was unable to fully trace the exact internal exception conditions of `objectHash.getBase64Hash` (its source was not retrieved in this session) or the complete wallet.js chat-message code path that stores incoming private chains for unpaired/whitelisted subjects; a Devin session with full file access would be needed to confirm the precise payload shape that triggers the hash exception and to fully enumerate all reachable entry points into `handleSavedPrivatePayments`.
