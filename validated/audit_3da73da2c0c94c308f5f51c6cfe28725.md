## Title
CCMenu API endpoint lets a stack-scoped `ApiClient` token read the build status of any stack, not just the stack it was authorized for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup helper from `BaseController` and drops the scoping that binds an `ApiClient` token to the single stack it was issued for. Any `ApiClient` holding the `read:stack` permission can therefore read deploy/build status for every stack in the installation by simply changing the `stack_id` parameter, regardless of the `stack_id` column stored on that client.

### Finding Description
`Shipit::Api::BaseController` establishes the trust binding between an authenticated `ApiClient` and the stack(s) it is allowed to touch: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped (`current_api_client.stack_id?`), and `stack` resolves `params[:stack_id]` only from within that restricted relation. Every other API controller (`DeploysController`, `StacksController`, `TasksController`, etc.) inherits this `stack` method and is therefore correctly bound: `Stack an ApiClient authorises == Stack it can act on`.

`CCMenuController`, however, redefines `stack` to bypass this scope entirely: [2](#0-1) 

It resolves `params[:stack_id]` directly against `Stack.from_param!`, with no reference to `current_api_client.stack_id`. The permission check performed by `require_permission :read, :stack` only verifies that the client's `permissions` array contains `read:stack` (via `ApiClient#check_permissions!`), it does not verify which stack that permission applies to: [3](#0-2) 

So the equality the rest of the API enforces - `stack authorised by token == stack acted on` - is broken specifically in `CCMenuController`. A token created with `stack_id` set to Stack A (as `ApiClientsController` allows an admin to configure per stack, mirroring how `CCMenuUrlController` issues a `read:stack` client) can be replayed against Stack B, C, ... simply by changing the `stack_id` request parameter. This is architecturally analogous to the reported bug: a value that is properly bound/validated in one code path (`BaseController#stack`, the "chain id"/scope check) is silently unvalidated in a sibling code path (`CCMenuController#stack`) that consumes the same credential.

### Impact Explanation
This lets a holder of a stack-scoped, `read:stack`-only API token obtain unauthorized read access to the state (last deploy status, lock status, activity) of arbitrary other stacks in the same Shipit installation - stacks the token was never meant to authorize. This matches the "High" impact category defined for this analysis: unauthenticated/unauthorized **read of stack state or deploy output** via a broken authorization scope, without needing any additional credential beyond the low-privilege token itself.

### Likelihood Explanation
Any party holding a legitimately-issued, narrowly-scoped `ApiClient` credential (e.g., a CI badge/CCMenu integration token meant for one stack) can exploit this by making a single additional HTTP request with a different `stack_id`; no other privilege, secret, or session is required. The bypass is deterministic and requires no timing or race conditions.

### Recommendation
`CCMenuController#stack` should reuse the `stacks`/`stack` scoping logic from `BaseController` (i.e., resolve `params[:stack_id]` through `current_api_client.stack_id?`-scoped `Stack.where(...)`) instead of querying `Stack.from_param!` unscoped, so that a client's `stack_id` binding is enforced consistently across every API controller.

### Proof of Concept
1. As an admin, create (or have `CCMenuUrlController` create) an `ApiClient` scoped to Stack A: `permissions: ['read:stack']`, `stack_id: <Stack A id>`.
2. Obtain that client's `authentication_token`.
3. Send `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b_id` refers to an unrelated Stack B.
4. Observe that the request succeeds (200 OK) and returns Stack B's build/deploy status, even though the token's `stack_id` column only authorizes Stack A - confirming `stack_authorised != stack_touched`. [4](#0-3)
