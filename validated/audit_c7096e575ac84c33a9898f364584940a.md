### Title
Bridge ERC20 Handle Nonce Permanently Stuck When Recipient Is Blacklisted — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`handleERC20Transfer` in the Kaia service-chain bridge performs the ERC20 `safeTransfer` to the recipient **after** updating the handle nonce in the same atomic transaction. If the recipient address is blacklisted by the token contract (e.g., USDC, USDT), the `safeTransfer` reverts, rolling back the entire transaction including the nonce update. Because the bridge enforces strict sequential nonce ordering via `lowerHandleNonce`, the stuck nonce permanently corrupts the bridge's recovery pointer and the affected user's bridged tokens are irrecoverable.

---

### Finding Description

In `BridgeTransferERC20.sol`, `handleERC20Transfer` executes the following sequence atomically:

```solidity
_lowerHandleNonceCheck(_requestedNonce);          // require lowerHandleNonce <= N
if (!_voteValueTransfer(_requestedNonce)) return;  // threshold vote
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);               // advances lowerHandleNonce
// ...
IERC20(_tokenAddress).safeTransfer(_to, _value);  // ← REVERTS if _to is blacklisted
``` [1](#0-0) 

If `safeTransfer` reverts (because `_to` is blacklisted by the token), the entire transaction is rolled back — including `handleNoncesToBlockNums[N]` and `_updateHandleNonce`. The `lowerHandleNonce` therefore never advances past N.

`_updateHandleNonce` advances `lowerHandleNonce` only when `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting from `lowerHandleNonce`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

Since `handleNoncesToBlockNums[N]` is always zero (every attempt reverts), `lowerHandleNonce` is permanently frozen at N. Subsequent nonces N+1, N+2, … pass `_lowerHandleNonceCheck` (which only requires `lowerHandleNonce <= _requestedNonce`) and their transfers succeed on-chain, but `lowerHandleNonce` and `recoveryBlockNumber` never advance past N. [3](#0-2) 

There is no `skipNonce`, `redirectTransfer`, or any other operator-callable escape hatch in the bridge contract set.

---

### Impact Explanation

- **Bridged ERC20 assets permanently lost**: The user's tokens are locked in the bridge (lock/unlock mode) or burned on the source chain (mint/burn mode) with no delivery on the destination chain.
- **`recoveryBlockNumber` permanently frozen**: The off-chain recovery daemon (`recoveryBlockNumber`) never advances past the stuck nonce's block, causing it to re-scan and re-attempt the same failing nonce indefinitely.
- **`lowerHandleNonce` corruption**: The bridge's sequential nonce accounting is permanently broken for the affected token/bridge pair.

This matches the allowed impact gate: *unauthorized loss of bridged assets* and *persistent corruption of bridge nonce/state that breaks settlement*.

---

### Likelihood Explanation

- USDC and USDT — both of which have on-chain blacklists — are commonly bridged assets in service-chain deployments.
- A user's address can be blacklisted by the token issuer (regulatory action, sanctions) at any time after the `RequestValueTransfer` event is emitted on the source chain but before operators call `handleERC20Transfer` on the destination chain.
- A malicious user could also intentionally get their own address blacklisted to permanently corrupt the bridge's nonce state.
- No privileged access is required to trigger this; the blacklisting is performed by the token issuer, not by any Kaia operator.

---

### Recommendation

1. **Wrap the transfer in a try/catch and emit a `FailedTransfer` event** rather than reverting the entire transaction. This allows the nonce to advance even when delivery fails.
2. **Add an operator-callable `recoverFailedTransfer(uint64 nonce, address newRecipient)`** that allows redirecting a stuck transfer to an alternate address, callable only after a failed delivery is recorded.
3. **Alternatively, separate nonce advancement from token delivery**: record the nonce as handled unconditionally, and store failed deliveries in a separate claimable mapping so the recipient (or a substitute address) can pull funds later.

---

### Proof of Concept

1. User on service chain calls `requestERC20Transfer` with a USDC amount, specifying `_to = 0xVictim`. The bridge emits `RequestValueTransfer` with nonce N.
2. Before operators handle nonce N on the main chain, Circle blacklists `0xVictim` on USDC.
3. Operators call `handleERC20Transfer(..., _to=0xVictim, ..., _requestedNonce=N, ...)`.
4. `_voteValueTransfer(N)` reaches threshold → proceeds.
5. `handleNoncesToBlockNums[N]` is set, `_updateHandleNonce(N)` runs, `lowerHandleNonce` advances.
6. `IERC20(usdc).safeTransfer(0xVictim, value)` reverts (blacklisted recipient).
7. Entire transaction reverts → `handleNoncesToBlockNums[N]` reset to 0, `lowerHandleNonce` reset.
8. Every subsequent operator attempt to handle nonce N repeats steps 3–7 and always reverts.
9. `lowerHandleNonce` is permanently stuck at N; `recoveryBlockNumber` never advances; the user's USDC is irrecoverable. [4](#0-3) [5](#0-4)

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
