### Title
CCMenu API endpoint bypasses per-token stack scoping, allowing a stack-scoped `ApiClient` token to read the CI/CD status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Api::BaseController` is supposed to enforce that scope on every lookup through its `stacks`/`stack` helpers. `Api::CCMenuController` overrides `stack` with an unscoped lookup, so any token that merely has the `read:stack` permission — including one deliberately scoped to a single stack — can read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, lock state, etc.) of every other stack in the installation simply by changing the `stack_id` request parameter. This is the analog of the audited `getVotingPower` flaw: an authorization decision is made against one binding (the permission flag), while the actual resource acted upon (an arbitrary stack) is never re-checked against the binding that was supposed to constrain it (the token's `stack_id` scope).

### Finding Description
`Api::BaseController` defines the intended authorization binding between a token and the stacks it may touch: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the client is scoped, and `stack` performs `stacks.from_param!(params[:stack_id])`, i.e. it looks the requested stack up only within the authorized set — if the requested `stack_id` doesn't belong to the client's authorized stack, `from_param!` raises `ActiveRecord::RecordNotFound`.

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves the parameter against **all** stacks: [2](#0-1) 

The only authorization check performed before `show` runs is the permission check: [3](#0-2) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which validates the client's `permissions` array, not its `stack_id` scope: [4](#0-3) 

So the binding `current_api_client.stack_id == stack.id` (enforced everywhere else in the API via `stacks.from_param!`) is never checked in `CCMenuController#show`. Any bearer of a token with `read:stack` permission — even one explicitly created and distributed for a single stack, e.g. the `here_come_the_walrus` fixture — can pass a different `stack_id` and read another stack's status: [5](#0-4) 

Authentication for this endpoint additionally accepts the token as a plain query-string parameter (not just Basic Auth), which is how CCMenu URLs are meant to be used and is also how the leaked/scoped token would typically be shared: [6](#0-5) [7](#0-6) 

### Impact Explanation
This is an unauthenticated-scope read: a token that the operator restricted to a specific stack (e.g. handed out for one team/project's CCMenu integration) can be used to enumerate/read the build and deploy status of any other stack in the Shipit instance — including private, unrelated repositories' stacks — because the `stack_id` scope binding is silently dropped for this one controller action. This matches the High-impact criterion of "unauthenticated read of stack state... via a token whose authorized stack differs from the stack it actually touches."

### Likelihood Explanation
Any holder of a `read:stack`-scoped `ApiClient` token (which is routinely created and distributed via `CCMenuUrlController`/`ApiClientsController` for exactly this endpoint) can trigger this by changing one URL parameter. No special privileges, secrets, or additional access are required beyond possessing any valid CCMenu-permission token, which is the expected, lowest-privilege way to consume this endpoint.

### Recommendation
Make `Api::CCMenuController#stack` respect the same scoping as the rest of the API by reusing the inherited `stacks` collection (or explicitly re-validating `current_api_client.stack_id` against the resolved stack) instead of calling `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and remove the unscoped override entirely, matching `BaseController`'s enforcement.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and `stack_id: A.id` (as in fixture `here_come_the_walrus`).
2. As this client, call `GET /api/stacks/B/ccmenu.xml?token=<A's token>` where `B` is a stack the client is not authorized for.
3. Observe that `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against all stacks (bypassing `stacks.from_param!`'s `stack_id` filter used everywhere else in the API), returning stack B's build/deploy status even though the token's authorized scope is limited to stack A.
