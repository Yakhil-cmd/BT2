## Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while event processing trusts the unrelated `repository.full_name` field, allowing cross-organization webhook forgery in multi-GitHub-App Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report's bug class is "a value the code trusts for one purpose is never the value that's actually verified for another purpose" (decimal amount computed for one context but consumed for another without re-validation). The engine analog is `WebhooksController#verify_signature`, which selects the signing `GitHubApp`/`webhook_secret` using `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, while every event `Handler` (`Handler#repository_name`, used transitively by `PushHandler`, `StatusHandler`, etc.) resolves the target `Stack`/`Repository` using the sibling but independently-controlled `repository.full_name` field from the same body. Nothing ties these two fields together, so the organization whose secret authenticated the request is not guaranteed to be the organization whose repository is actually mutated.

### Finding Description
`WebhooksController#verify_signature` picks the app/secret to validate the HMAC against solely from the payload itself: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the request passes verification, event handlers derive which `Stack`/`Repository` to act on from a **different** payload field, `repository.full_name`, with no cross-check against `repository_owner`: [3](#0-2) 

`Shipit.github` supports installing one GitHub App per organization ("Using Multiple Github Applications"), each with its own `webhook_secret`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the affected repository/stack) are two independently-attacker-controlled strings inside the same unauthenticated-until-verified JSON body, a payload can be crafted where the two fields disagree: the signature is computed and verified against Org A's secret, but the event content (repo/commit/SHA) targets Org B's stack.

`PushHandler` and `StatusHandler` both act purely on the payload-derived `Repository`: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who legitimately controls one GitHub organization/App configured in the same multi-tenant Shipit instance (e.g. their own org's install, with their own known `webhook_secret`) can forge webhook deliveries whose HMAC is valid for their own org, but whose `repository.full_name` names a stack belonging to a completely different, unrelated organization served by the same Shipit instance. This breaks the binding "organization that authenticated == repository that is written," one of the deployment-trust bindings explicitly called out as in-scope.

Concretely:
- Via `PushHandler`, the attacker can force `GithubSyncJob` to run against a victim org's stack with an attacker-chosen `expected_head_sha`, corrupting which commit Shipit believes is the branch head for that unrelated stack.
- Via `StatusHandler`, the attacker can inject a forged `success`/`failure` CI status for an arbitrary commit SHA on the victim stack (`Commit#create_status_from_github!`), which feeds directly into `ci.require` deploy-safety gating (`README.md` `ci.require`), potentially satisfying CI requirements to enable an unauthorized deploy of a repository the attacker does not control.

This is a cross-repository write achieved purely by crafting a JSON payload against your own org's already-valid signature — no possession of the victim org's secret, private key, or session is required, satisfying the "cross-repository writes / unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Exploitability requires only that the Shipit instance be configured to serve more than one GitHub organization (a documented, supported configuration) and that the attacker controls (or has push access enabling webhook delivery to) at least one of those organizations. Given that, forging the divergent `repository.owner.login` vs `repository.full_name` fields is trivial JSON manipulation, and the `X-Hub-Signature` header simply needs to be a valid HMAC over the raw body using the attacker's own known secret. No secret of the target org is ever needed.

### Recommendation
After selecting the signing `GitHubApp` via `repository_owner`, validate that this same organization/login is consistent with the owner portion of `repository.full_name` (and `organization.login` when present) before dispatching to handlers; reject the webhook otherwise. Alternatively, resolve the target `Repository`/`Stack` using the same trusted identifier that selected the verifying secret, rather than a second, independently-controlled field.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` (attacker-controlled, secret known to attacker) and `OrgB` (victim), as in `docs/setup.md` "Using Multiple Github Applications".
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s known `webhook_secret` over the raw body, matching `GitHubApp#verify_webhook_signature` [8](#0-7) .
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: 'OrgA')` and succeeds because the signature matches `OrgA`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('OrgB/victim-repo')` [3](#0-2)  and enqueues `GithubSyncJob` for `OrgB`'s stack with the attacker-supplied `expected_head_sha`, even though the request was never signed by `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
