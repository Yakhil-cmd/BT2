### Title
`ERC20Transactor` credits the nominal `amount` into XCM holding instead of the actual balance received by the checking account, breaking on fee-on-transfer/deflationary ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` moves ERC20 tokens from a user to a shared `TransfersCheckingAccount` by calling the token's `transfer()` function and, if the call returns `true` (success), unconditionally records the *requested* `amount` as `Erc20Credit(amount)` in the XCM holding register, rather than checking the checking account's actual balance delta. `deposit_asset_with_surplus` performs the symmetric operation, transferring the nominal holding `amount` back out of the checking account. Any ERC20 contract registered via the `AccountKey20` asset-id convention (any deployed contract address, fully permissionless per the PR description) that charges a transfer fee, is deflationary/rebasing, or otherwise delivers less than `value` to the recipient will cause the XCM-tracked "amount" to diverge from the real balance actually held by `TransfersCheckingAccount`. This is the same root-cause class as the referenced Sublime `NoYield.sol` finding: assuming `received == amount` on an ERC20 `transfer()`/`transferFrom()` without measuring the actual balance change.

### Finding Description
`ERC20Transactor` is a `TransactAsset` implementation wired into `AssetTransactors` on Asset Hub Westiend: [1](#0-0) 

Per its own introducing PR-doc, any asset id of the shape `{ parents: 0, interior: X1(AccountKey20 { key, network }) }` is matched, and `key` is treated as an arbitrary ERC20 contract address to call - this is not restricted to an admin-curated allow-list, it is derived directly from the asset id supplied in the XCM message: [2](#0-1) 

In `withdraw_asset_with_surplus`, the user's own tokens are moved to the checking account via a `transfer` call executed with the *user's* origin, and the code only checks whether the ABI-decoded boolean return value is `true`: [3](#0-2) 

If `is_success` is `true`, the full requested `amount` (not the checking account's actual balance delta) is wrapped into `Erc20Credit(amount)` and placed into the `AssetsInHolding` register: [4](#0-3) 

Symmetrically, `deposit_asset_with_surplus` transfers the nominal holding `amount` out of the checking account to the beneficiary, again relying only on the boolean return value of `transfer()`, not on the checking account's actual balance: [5](#0-4) 

`Erc20Credit`/`ImbalanceAccounting` explicitly documents that it performs no runtime-level balance enforcement and relies entirely on the ERC20 contract to be well-behaved 1:1 with the requested `value`: [6](#0-5) 

None of `transfer()`'s success paths compare `IERC20::balanceOf(checking_account)` before/after (for withdraw) or `IERC20::balanceOf(beneficiary)` before/after (for deposit) - exactly the missing check flagged in the referenced report ("Consider comparing before and after balance to get the actual transferred amount"). A user (any signed account, no privileged role required) can deploy an ordinary ERC20 contract via `pallet-revive` that charges a transfer fee, is deflationary, rebases, or has any non-standard transfer semantics, then reference that contract's address as an XCM asset id and drive it through a normal `pallet_xcm::execute`/local XCM program (`WithdrawAsset` -> `DepositAsset`), which is the real, non-privileged user entry point that reaches this transactor.

### Impact Explanation
Because the holding register believes it holds the full nominal `amount` while `TransfersCheckingAccount` actually holds `amount - fee`, any subsequent instruction operating on the holding (partial `PayFees`/fee deduction, further `DepositAsset`, or multi-step XCM programs that split the holding) can request the checking account to pay out more than it actually received. Concretely:
- The `deposit_asset_with_surplus` transfer call from the checking account can revert (insufficient real balance), causing `XcmError::FailedToTransactAsset("ERC20 contract reverted")` mid-way through the XCM program, after the checking account has already absorbed the withdrawn amount from the user - trapping value in the checking account or causing the executor to trap/burn the un-deposited holding.
- Legitimate/innocent users transacting the same registered ERC20 token later can have their deposit fail for the same reason, mirroring the original report's core impact: "later users may not be able to successfully withdraw their tokens" due to the checking account's real balance being smaller than the nominal amount the protocol believes is backed.

This is a real integrity/availability break for the XCM asset-transfer machinery on any chain enabling `ERC20Transactor` (Asset Hub Westend today), though the blast radius is currently limited to ERC20s users choose to reference via XCM against this transactor - it does not, by itself, forge fungible-token issuance recorded in FRAME pallet storage (since `pallet-revive`'s `fungibles::Inspect::balance`/`total_issuance` always live-query the contract rather than caching a divergent ledger), so I classify this as Medium rather than Critical.

### Likelihood Explanation
Likelihood is Medium: it requires (a) an ERC20 contract with fee-on-transfer/deflationary/rebasing semantics to be deployed via `pallet-revive` (fully permissionless, anyone can deploy such a contract) and (b) that contract's address referenced as an `AccountKey20` XCM asset id in a `WithdrawAsset`/`DepositAsset` XCM program executed through `pallet_xcm::execute` or an XCM message. Both steps are ordinary, unprivileged user actions. No governance, validator, or collator compromise is required. The condition is a well-known ERC20 pattern (many real-world tokens implement transfer fees), and does not depend on any race condition or timing assumption.

### Recommendation
In `withdraw_asset_with_surplus`, measure `IERC20::balanceOf(checking_address)` before and after the `transfer` call (or use `transferFrom`/pull semantics with a pre/post balance diff) and use that delta - not the requested `amount` - to construct `Erc20Credit`. Symmetrically, in `deposit_asset_with_surplus`, measure the beneficiary's balance delta (or the checking account's balance delta) and reconcile the holding with the actually-moved amount, failing/returning the unspent remainder rather than assuming full success from the boolean return value alone.

### Proof of Concept
- Program/severity rationale: analog of the referenced `NoYield.sol` fee-on-transfer finding (Medium), mapped onto `ERC20Transactor`'s `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, reachable from a genuine unprivileged user entry point (`pallet_xcm::execute` with a `WithdrawAsset`/`DepositAsset` program against an `AccountKey20`-addressed ERC20 asset id) on Asset Hub Westend (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`).
- Failed guard identified: `is_success` only checks the ABI-decoded boolean return of `IERC20::transfer`, never a before/after balance comparison on the checking account or beneficiary (lines 185-216 and 270-298 of `erc20_transactor.rs`).

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
