### Title
Cross-repository commit status forgery via unscoped `StatusHandler` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler`, unlike the other GitHub webhook handlers, does not scope its database lookup to the repository that the webhook payload (and its verified signature) belongs to. This lets a party who controls any repository configured as a Shipit stack write CI status records onto commits that belong to a *different* stack/repository, breaking the binding between "the repository whose webhook signature was verified" and "the repository whose data is written."

### Finding Description
Every webhook request is authenticated in `WebhooksController#verify_signature` by looking up the GitHub App config for the organization named in the payload (`repository.owner.login` or `organization.login`) and checking the HMAC signature with that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

This only proves the request came from *some* organization/repository whose secret matches the payload — it says nothing about which `Commit`/`Stack` records the handler is allowed to touch. Handlers are expected to enforce that scoping themselves, and the base `Handler` class provides a `stacks` helper for exactly this purpose, which resolves the target stacks strictly from the `repository.full_name` in the same signed payload: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` correctly use this `stacks` scope before touching any commit: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, looks up commits globally by SHA with no repository scoping at all, then writes a status onto every matching commit across the entire Shipit instance: [6](#0-5) 

Because Git commit SHAs are content-addressed (derived from tree, parents, author, message, timestamps), the same SHA can legitimately exist in more than one repository — e.g. forks, mirrors, or repositories sharing common history/rebased branches. If an attacker controls (or can push signed webhooks from) *any* repository that is configured as a Shipit stack, and can get a commit with an identical SHA to a targeted commit in a *different*, more sensitive stack, they can trigger a real `status` webhook from their own repository. That webhook is legitimately signed with their own organization's `webhook_secret`, so `verify_signature` passes — but `StatusHandler#process` then applies the status to the victim's commit as well, since it only filters by `sha` and never checks that the commit's stack/repository matches the webhook's `repository.full_name`.

**Binding broken:** `organization/repository that authenticated the webhook == organization/repository whose Commit record is written` is assumed but not enforced; `StatusHandler` allows the left side (attacker's own low-privilege repo) to diverge from the right side (a different, high-privilege repo's tracked commit).

### Impact Explanation
Commit CI status directly feeds Shipit's deployability logic (`blocking_statuses`, `required_statuses`, `soft_failing_statuses` in `app/models/shipit/deploy_spec.rb`, consumed by `Commit#deployable?`). An attacker who forges a passing status (e.g. a required `ci/foo` context set to `success`) onto a commit in a stack they do not control can make that commit appear deployable, potentially enabling an unauthorized deploy of code that never actually passed the required checks in the correct repository — this falls under "unauthorized deploy" / cross-repository writes, a Critical-tier impact per the engine's threat model.

### Likelihood Explanation
Exploitation requires the attacker to control a repository that is itself onboarded into the same Shipit instance as a stack (so they can generate a validly-signed `status` webhook), and to produce a commit whose SHA collides with a commit tracked by the victim stack. This is realistic in fork/mirror/shared-history scenarios (common in monorepo splits, vendored branches, or forks of the same upstream) but not a trivial SHA collision attack — likelihood is moderate and depends on the deployment's repository topology, not on breaking SHA-1/SHA-256 collision resistance.

### Recommendation
Scope `StatusHandler#process` to the stacks/commits belonging to the webhook's own repository, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This ensures a webhook can only affect commits within the repository it was actually signed for.

### Proof of Concept
1. Attacker owns/administers `attacker/repo`, which is added as a Shipit stack (`webhook_secret` known to attacker via their own GitHub App/organization config).
2. Victim stack `victim/repo` tracks a commit `abc123...` (e.g., because both repos share history via a fork or mirrored branch).
3. Attacker pushes/creates the same commit object (or otherwise causes GitHub to fire a `status` event with `sha: abc123...`) on `attacker/repo`, setting `state: success`, `context: "ci/required-check"`.
4. GitHub signs the webhook with `attacker/repo`'s org secret; `WebhooksController#verify_signature` validates it successfully because it looks up the secret for the org named in the (attacker-controlled) payload.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, which matches the commit belonging to `victim/repo`'s stack, and calls `create_status_from_github!`, marking that commit's `ci/required-check` as passing — even though `victim/repo` never ran or reported that check.
6. If this status is one of `victim/repo`'s `required_statuses`, the commit now appears deployable and can be deployed via the normal Shipit UI/API without ever having passed the real check.
