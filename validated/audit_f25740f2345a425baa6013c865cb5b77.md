### Title
Unvalidated strategy routes can inject caller-authorized token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept caller-supplied route bytes and forward them to the configured router. [1](#0-0) [2](#0-1)  The controller narrowly authorizes only its own exact input-token transfer, but it does not constrain which venue contracts the router invokes from the opaque route payload. [3](#0-2) [4](#0-3)  A malicious route can therefore place third-party code below the caller’s `require_auth` context and request an unrelated `token.transfer(caller, attacker, amount)` as a signed child invocation. [5](#0-4) [6](#0-5) 

### Finding Description
`process_swap_collateral` authenticates the caller, verifies that the caller owns or delegates the account, withdraws collateral, and forwards the caller-controlled `swap` payload to `withdraw_and_swap_from_supply`. [7](#0-6)  `swap_tokens` forwards that opaque payload to `SwapAggregatorClient::execute_strategy` after authorizing only `token_in.transfer(controller, router, amount_in)`. [8](#0-7) [9](#0-8)  The post-swap checks measure only the controller’s input spend and positive output receipt; they do not detect or reject unrelated caller-authorized calls performed by code reached through the route. [10](#0-9) [11](#0-10)  The protocol’s own threat model confirms that route-selected pool and token addresses are not allowlisted and that a downstream token transfer from the caller executes when the caller signs the recorded authorization tree. [6](#0-5) 

### Impact Explanation
A malicious route can steal assets held in the caller’s wallet that are unrelated to the lending position, rather than merely consuming the routed collateral. [12](#0-11)  The demonstrated authorization tree records `token.transfer(victim, attacker, balance)` as a child of `swap_collateral`, drains the victim’s unrelated wallet token, and still deposits a fair swap output. [13](#0-12)  Because the injected call is included in the signed authorization tree, the balance checks and final account-risk checks do not bound the stolen amount. [10](#0-9) [14](#0-13)  This is theft of user funds and warrants High severity despite requiring the victim to sign the poisoned authorization tree.

### Likelihood Explanation
Any unprivileged user can reach `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` for an account that user controls. [2](#0-1) [15](#0-14)  The exploitable condition is a route supplied by a malicious quote provider, router response, or trading interface that causes simulation to add an unauthorized-looking transfer beneath the strategy invocation. [6](#0-5)  The attack requires the victim to sign the expanded authorization tree, so wallets or clients that clearly display and reject unexpected child calls reduce the likelihood, but the contract itself provides no venue allowlist or authorization-manifest check. [16](#0-15) [6](#0-5) 

### Recommendation
Do not pass opaque routes that can name arbitrary executable venues without an authorization boundary. [8](#0-7)  Change the router/controller interface to enumerate every venue call in the route and require those venues to come from a governance-managed allowlist, or make the router execute only fixed, audited venue adapters rather than route-selected contract addresses. [17](#0-16)  Clients should additionally simulate the complete transaction, decode the returned authorization tree, and reject any child invocation other than the expected controller input transfer or explicitly expected route calls. [18](#0-17) 

### Proof of Concept
1. Victim owns an account with USDC collateral and also holds an unrelated token in their wallet; `swap_collateral` is reachable because the victim owns the account. [19](#0-18) 
2. An attacker supplies a route whose payload names an attacker-controlled venue while still promising a valid output token amount. [17](#0-16) 
3. The victim calls `swap_collateral(caller, account_id, USDC, amount, ETH, malicious_route)`, and the controller forwards `malicious_route` to the configured router. [20](#0-19) [16](#0-15) 
4. The attacker-controlled venue invokes `unrelated_token.transfer(victim, attacker, wallet_balance)`, causing simulation to attach that transfer as a child of the victim’s `swap_collateral` authorization. [21](#0-20) 
5. If the victim signs that generated tree, the unrelated token is transferred to the attacker while the swap still returns a positive output and satisfies the controller’s measured-output check. [22](#0-21) [11](#0-10)

**File:** docs/explanation/threat-model.md (L144-165)
```markdown
Router swaps settle measured input/output changes. The controller grants
one exact input-transfer invocation, not a token allowance, and refunds
unspent input still held by the controller. The router checks its payload
minimum against output after fees but before payout; its own residuals
follow a capped admin-revenue policy. The controller requires positive
measured output and final account risk, not an independent slippage bound.
A compromised router may consume authorized input for dust output while the
final account passes its risk gates. Exposure is bounded by routed funds and
those gates, not by an independent controller slippage limit.

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
