### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire database, with no scoping to the repository/organization that the webhook's signature was verified against. Because the webhook signature is verified only against the organization named in the attacker's own payload (`repository.owner.login`), an attacker who owns a Shipit-connected org/repo can sign an arbitrary JSON body with their own valid `webhook_secret` and set `sha` to any 40-hex value they choose, mutating the `Status` of a commit that belongs to a completely different repository/stack.

### Finding Description
The broken binding, stated explicitly: the question assumes `organization(webhook_secret used to verify payload) == organization(Commit/Stack mutated by the handler)`. Tracing the code shows this equality is never enforced.

- `Shipit::WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and validates the HMAC using `Shipit.github(organization: repository_owner)`'s `webhook_secret` [1](#0-0) [2](#0-1) . This only proves the JSON body was signed by *some* organization's secret that matches the `repository.owner.login` field the attacker themselves supplied in the JSON — it does not prove that the `sha`, `branches`, or any other top-level field actually pertains to that organization's repository. Since the attacker owns that organization/repo and legitimately receives GitHub webhooks configured with that org's `webhook_secret`, they can freely author the raw JSON body (GitHub does not constrain webhook payload contents to “your own commits” beyond what GitHub itself would normally send — but nothing in Shipit forces the attacker's forged payload to match reality once it's their own signed request).
- The generic `Handler` base class does provide a repository-scoped `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) [3](#0-2) , which other handlers are expected to use to scope their side effects to the correct repository.
- `StatusHandler#process`, however, ignores this scoping entirely and does a bare, global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . `sha` is not unique per repository in the schema — it is a plain column with no uniqueness/foreign-key constraint tying it to the requesting repository — so any commit row anywhere in the database sharing that sha string is mutated.
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` [5](#0-4) , writing a real `Status` row against the victim commit, which feeds into `Commit#status`, `#deployable?`, `#blocked?`, and can trigger `stack.schedule_merges` for autodeploy/merge pipelines [6](#0-5) .

**Exploit flow:** Attacker owns GitHub org/repo "A" registered in Shipit with a known-to-them `webhook_secret` (standard GitHub App/webhook config for their own repo). They discover (via public GitHub) the commit SHA of a commit belonging to victim org "B"'s stack. They POST to `/webhooks` with header `X-Github-Event: status`, a body whose `repository.owner.login` = "A" (so `verify_signature` uses A's secret) but whose top-level `sha` field is set to B's commit SHA, and sign the raw body with A's `webhook_secret`. `verify_signature` passes because the HMAC matches org A's secret over the attacker-chosen bytes. `StatusHandler#process` then finds the commit row belonging to stack B (matched purely by `sha`) and creates a forged `Status` on it.

None of the listed guards prevent this: `drop_unhandled_event` only filters unregistered event types; `ExplicitParameters` schema only validates types/shape, not repository ownership; there is no `force_github_authentication`/session/API-client check on this unauthenticated webhook endpoint; and `verify_signature` checks only that *a* valid signature exists for the org named in the (attacker-controlled) payload, not that the mutated records belong to that org.

### Impact Explanation
An attacker with control of any Shipit-registered repository/org can forge a commit `Status` (state, context, description, target_url) on any commit belonging to any other tenant's stack, provided they can guess/observe that commit's SHA (SHAs of public commits are trivially obtainable). This is a genuine "payload for one repository mutating another's stack/commit" — matching the Critical category explicitly listed in scope. Depending on the victim stack's configuration (`required_statuses`, `ignore_ci?`, continuous deployment/merge queue settings), a forged "success" status can make a commit `deployable?` and trigger `schedule_merges`/`ContinuousDeliveryJob`, potentially causing an unauthorized deploy or merge on the victim's stack. It is repeatable against arbitrary commits/stacks at will, and blast radius spans all tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one legitimate Shipit-registered repository/org of their own (a normal, low-privilege setup — any org admin can register a repo/app with Shipit) and knowledge of a target commit SHA (obtainable from any public GitHub repository's commit history, or from a public/forked PR). No Shipit session, API token, or victim secrets are required. Crafting and signing the payload is cheap (compute one HMAC-SHA1 over attacker-controlled JSON) and fully repeatable/scriptable against any number of target commits.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook was verified for, mirroring the base `Handler#stacks` pattern, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more directly, join `Commit` through `Stack`/`Repository` filtered by `repository_name`/`repository_owner` derived from the same payload used for signature verification, so a commit is only mutated if it belongs to a stack whose repository matches the authenticated organization/repository. Apply the same audit to any other handler that queries `Commit`/`Stack` by attacker-supplied identifiers without going through the `stacks` scoping helper.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub required):
1. Create `stack_a` for `Repository` "orgA/repo-a" with `webhook_secret` "secretA", and `stack_b` for `Repository` "orgB/repo-b" with `webhook_secret` "secretB".
2. Create `commit_b` under `stack_b` with a known `sha` (e.g. `"deadbeef" * 5`), asserting `commit_b.statuses.count == 0` beforehand.
3. Build a JSON payload with `repository.owner.login = "orgA"`, `repository.full_name = "orgA/repo-a"`, `sha = commit_b.sha`, `state = "success"`, `context = "ci/forged"`.
4. Sign the raw JSON with `secretA` (org A's real, attacker-known secret) as `X-Hub-Signature`.
5. POST to `/webhooks` with `X-Github-Event: status` and the signed payload.
6. Assert the response is `200 OK` (signature accepted, since it was verified against orgA, matching the payload's own `repository.owner.login`).
7. Assert equality-violation: `commit_b.reload.statuses.count == 1` and `commit_b.status.context == "ci/forged"` even though `commit_b.stack.repository.owner_login == "orgB" != "orgA"` — i.e., assert explicitly that `organization_that_signed ("orgA") != organization_owning_mutated_commit ("orgB")`, proving the binding claimed by the question is indeed broken.
