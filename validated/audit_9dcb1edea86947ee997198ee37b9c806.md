### Title
`StatusHandler#process` matches commits by raw SHA across all repos, letting a forged status from one repository mark another stack's commit `deployable?` and trigger an unauthorized deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Stack#trigger_continuous_delivery` itself does not need to re-verify commit ownership because `next_commit_to_deploy` only queries `commits` scoped by the `stack_id` foreign key [1](#0-0) . However, the upstream data feeding that scoped query can be poisoned: `StatusHandler#process` looks up commits by `sha` alone, with no repository/stack check, so a validly-signed webhook from an attacker-owned repository can write a `success` status onto a `Commit` row that actually belongs to a victim's stack, as long as the two repos happen to share that git SHA (e.g. shared history via a fork).

### Finding Description
The claimed binding is: `commit.stack.repository.full_name == payload['repository']['full_name']` (the repository whose CI produced the status webhook must equal the repository owning the commit being marked deployable).

Trace:
1. `WebhooksController#verify_signature` verifies the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the payload's `repository.owner.login` [2](#0-1) . This proves the request came from *some* org/app that Shipit trusts, but it never checks that this org/repo is the one owning the target `Commit`.
2. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This query is scoped by `sha` only - it is **not** filtered by `repository_owner`, `repository.full_name`, or any `stack_id` derived from the payload. Any `Commit` row anywhere in the database with a matching `sha` is updated, regardless of which repository the webhook actually came from.
3. `create_status_from_github!` -> `add_status` writes the new `Status` using the commit's own `stack_id` (i.e. the victim's real stack), and if the state transition is meaningful it emits `:deployable_status` and, critically, calls `stack.schedule_merges` and (via `Commit#schedule_continuous_delivery`, invoked as an `after_commit` callback on creation, or via periodic refresh) triggers `ContinuousDeliveryJob.perform_later(stack)` [4](#0-3) [5](#0-4) .
4. `ContinuousDeliveryJob#perform` and `Stack#trigger_continuous_delivery` execute against the victim stack correctly scoped by `stack_id` [6](#0-5) [7](#0-6) , but by this point the corrupted `deployable?` state has already been written onto the victim's `Commit`/`Status` records, so the scoping at this layer does not help - the poisoned data is exactly what gets deployed.

Root cause: the binding between "which repository's CI produced this status" and "which stack/commit it may affect" is enforced nowhere in the webhook-processing path; `StatusHandler` trusts SHA equality alone as proof of repository identity, which is false whenever the same commit object exists in more than one tracked repository (forks, mirrors, shared upstream history, or a colliding SHA).

Existing guards checked and found insufficient: `verify_signature` only proves the payload was signed by *a* trusted org, not that it is signed by the org owning the specific commit being touched [8](#0-7) ; the `ExplicitParameters` schema in `StatusHandler` validates shape (`sha`, `state`, etc.) but not repository identity [9](#0-8) ; `Stack#trigger_continuous_delivery`/`next_commit_to_deploy` correctly scope by `stack_id` but that only protects against cross-stack *selection*, not against cross-repo *pollution* of the commit's own status state.

### Impact Explanation
An attacker who controls a repository whose GitHub App/webhook secret Shipit trusts (their own repo/org, a precondition already granted per the org-A/org-B multi-tenant scenario) can cause a real `Status` row with state `success` to be written onto a victim stack's `Commit`, potentially flipping `deployable?` to true and driving `ContinuousDeliveryJob` -> `Stack#trigger_continuous_delivery` -> `trigger_deploy` -> real deploy task execution with the victim stack's `GITHUB_TOKEN` and deploy commands via `Command#start`/`PTY.spawn`. This is an unauthorized deploy triggered by a payload that authenticated for a *different* repository, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy."

### Likelihood Explanation
This requires: (a) a Shipit instance configured for multiple GitHub orgs/repos (multi-tenant), (b) the victim's newest undeployed commit having the same `sha` value as a commit reachable in a repository the attacker controls (realistic for forks/mirrors sharing git history, not merely a cryptographic collision requirement), and (c) the victim stack being `continuous_deployment?` enabled with an otherwise-passing/absent CI status so the forged `success` completes the deployable determination. Given those preconditions (which the question grants), the attacker's cost is a single legitimate webhook POST from their own repo - no secrets, sessions, or elevated privileges are needed. It is repeatable against any stack whose tracked commit SHA is shared with an attacker-accessible repo.

### Recommendation
In `StatusHandler#process` (and any other SHA-keyed webhook handler), scope the `Commit` lookup by the webhook's `repository.full_name`/`repository_owner` in addition to `sha`, e.g. join through `stack.repository` and only update commits belonging to stacks whose repository matches the payload's `repository` object, rejecting/ignoring matches for other repositories.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create two stacks in fixtures for two different repositories (`org_a/repo` and `org_b/repo`), each with a `Commit` sharing the identical `sha` value (simulate shared history).
2. Set `continuous_deployment?` true and stub `deployment_checks_passed?`/related predicates so `org_b`'s commit is otherwise pending/deployable-once-status-arrives.
3. Build a status webhook payload naming `org_a/repo` with `state: 'success'`, `sha: <shared_sha>`, run it through `StatusHandler.new(payload).process` (bypassing signature verification, since that layer is already proven to authenticate only the sender's own org).
4. Assert a `Status` row was created for `org_b`'s `Commit` (`commit_b.statuses.last.state == 'success'`) even though the payload only authenticated `org_a`.
5. Stub/mock `Command.start` (or `PerformTaskJob`/task spawning) and assert it gets invoked for `org_b`'s stack as a side effect of `ContinuousDeliveryJob.perform_now(stack_b)`, proving deploy execution triggered purely by `org_a`'s webhook.
6. Assert on both sides of the binding: `payload['repository']['full_name'] == 'org_a/repo'` while `commit_b.stack.repository.full_name == 'org_b/repo'` - showing they differ yet the deploy proceeded.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
