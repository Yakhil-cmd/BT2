### Title
`Api::CCMenuController#stack` bypasses `ApiClient` stack scoping, allowing single-stack tokens to read CI status of every stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController#stack` enforces tenant isolation by scoping through `stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) before calling `from_param!`. `Api::CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, never consulting `current_api_client.stack_id`, so a token scoped to one stack can read the CCMenu (CI status) XML for any stack in the installation.

### Finding Description
The binding that should hold for every request is:
`stack requested ∈ Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true.

In `Api::BaseController`:
```
app/controllers/shipit/api/base_controller.rb:74-80
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
this binding is evaluated: `from_param!` is called on the scoped relation, so a stack outside `current_api_client.stack_id` raises `ActiveRecord::RecordNotFound` before any data is rendered.

`Api::CCMenuController` overrides `stack` and never calls `stacks`:
```
app/controllers/shipit/api/ccmenu_controller.rb:29-31
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
Here `Stack.from_param!` is invoked on the unscoped `Stack` class itself, so the binding is never evaluated — any `stack_id` (or slug, per `from_param!`) resolves regardless of `current_api_client.stack_id`.

`authenticate_api_client` is also overridden to accept a `token` query parameter (`ApiClient.authenticate(params[:token])`) rather than only Basic Auth, which is intentional for CCMenu clients, but the permission check `require_permission :read, :stack` (via `Api::BaseController.require_permission`) only checks `permissions.include?("read:stack")` — it never checks `stack_id` because `require_permission!` calls `current_api_client.check_permissions!(operation, scope)`, which has no notion of which stack is being accessed:
```
app/models/shipit/api_client.rb:38-45
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
```
So an attacker holding one `ApiClient` token scoped to stack A with `read:stack` permission can send `GET /api/ccmenu/:stack_id?token=<token>` with any other stack's id/slug and receive a `200` with that stack's `deploys_and_rollbacks.last` status rendered via the `shipit/ccmenu/project` XML view, instead of a `403`/`404`.

None of the existing guards catch this: `require_permission!` checks permission name only, not stack ownership; `authenticate_api_client` only validates the token signature; and the `stacks` scoping method that would enforce the binding is simply never invoked by this controller.

### Impact Explanation
Any holder of a legitimately-issued, single-stack-scoped `ApiClient` token with `read:stack` permission can enumerate and read the CI/build status (latest deploy/rollback id and finished state) of every stack across every tenant/repository managed by the Shipit instance, by iterating `stack_id` values. This is a cross-tenant unauthorized read of stack state, matching the High-severity category "unauthenticated/unauthorized read of stack state ... across all tenants using a single-stack-scoped token." It does not grant write, deploy, or code-execution capability, but it does break the tenant-isolation guarantee that scoped tokens are supposed to provide.

### Likelihood Explanation
The attacker only needs one legitimately issued `ApiClient` with `read:stack` permission scoped to a single stack (a normal, low-privilege credential many integrators are given, e.g. for CI status badges). No GitHub secrets, session, or additional privilege is required. The exploit is a single repeated GET request with varying `stack_id`, trivially scriptable, fully repeatable, and requires no race conditions or timing.

### Recommendation
Remove the overridden `stack` method in `Api::CCMenuController` (or reimplement it to call the inherited scoping) so it uses the same `stacks.from_param!(params[:stack_id])` logic defined in `Api::BaseController#stack`, ensuring `current_api_client.stack_id` scoping is enforced identically to every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual, no live GitHub required)
test "ccmenu leaks other stacks status to a single-stack scoped token" do
  scoped_stack = shipit_stacks(:shipit)
  other_stack  = shipit_stacks(:cocaine) # any stack != scoped_stack

  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack: scoped_stack,
    permissions: ['read:stack']
  )
  token = client.authentication_token

  # Binding under test: other_stack.id ∈ Stack.where(id: client.stack_id) must be false
  refute Stack.where(id: client.stack_id).exists?(other_stack.id)

  get "/api/ccmenu/#{other_stack.id}?token=#{token}"

  # Expected per binding: 403/404. Actual (bug): 200 with other_stack's CI data rendered.
  assert_response :forbidden # or :not_found — currently fails, response is 200
end
```
