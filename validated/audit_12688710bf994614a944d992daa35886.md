Based on my research into `pox-5.clar`, I found a highly relevant analog to the reported bug class. The report describes value being credited on a receiving side based on an insufficiently-verified/insufficiently-scoped cross-chain event, allowing the same underlying value to be exploited multiple times. `pox-5.clar`'s Bitcoin-lockup verification (`verify-l1-lockups` / `validate-l1-lockup`) has the analogous "L1 proof credits sats" pattern, and its outpoint de-duplication is scoped only to a single call.

### Title
Missing global outpoint tracking allows the same Bitcoin lockup UTXO to be credited to multiple protocol bonds/stakes, double-counting sats commitment - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`validate-l1-lockup` in `pox-5.clar` verifies a Bitcoin SPV proof (header, merkle proof, script, amount) for a locked UTXO and credits its `amount` in sats toward a staker's committed bond amount [1](#0-0) . Deduplication of outpoints (`seen-outpoints`) is only tracked as an accumulator local to the single `fold` invocation inside `verify-l1-lockups`, and is reset to `(list)` at the start of every call [2](#0-1) . There is no persistent, contract-wide map that records which Bitcoin outpoints have already been credited toward a bond across different calls or bond-indexes.

### Finding Description
The comment on `seen-outpoints` explicitly states its scope: "tracks every (txid, output-index) pair already credited *in this call*" [3](#0-2) . This means the same real-world Bitcoin lockup transaction output — which corresponds to one specific locked amount of BTC — can be supplied again as SPV proof in a second, independent `register-for-bond` (or equivalent) call, since the proof-of-lock check (`verify-block-header`, `verify-merkle-proof`, script hash equality, amount equality) will pass identically every time; only the intra-call list prevents re-use, not the ledger of previously credited outpoints.

This is directly analogous to the H-6 Tapioca bug: there, a cross-chain "receive" event (ETH landing on the destination chain) was not properly gated/consumed by the intended one-time state transition (`sgReceive`), so the same transferred value could be later swept out through an unrelated legitimate function. Here, a Bitcoin-side lock event (verified purely by SPV/merkle proof) is not permanently marked as "consumed," so the same BTC lock event can be replayed as proof to mint additional pox-5 stacking/bond credit (`sum`) without any additional BTC ever being locked — an unprivileged staker can bond/stake with more Bitcoin-backed shares than they actually locked.

### Impact Explanation
This breaks the core equality that pox-5's Bitcoin-backed bond/stake mechanism depends on: `sats credited via L1 proof == sats actually locked on Bitcoin`. A staker could reuse one Bitcoin lockup output across multiple bond registrations (or in future cycles once state permits reuse) to inflate their `amount-sats` / signing-weight / reward-share entries beyond what is actually backed by locked BTC, resulting in signing weight or reward slots exceeding the locked value — matching the "High" impact category (signing weight or reward slots exceeding locked value) or potentially "Critical" if it leads to unbacked reward payouts from `calculate-rewards`.

### Likelihood Explanation
Exploitability depends on whether any other layer of the protocol (outside `verify-l1-lockups`/`validate-l1-lockup`) maintains a persistent outpoint registry across separate calls. I was not able to locate such a persistent map in the portions of `pox-5.clar` reviewed (`total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`, `staker-shares-staked-for-cycle` track staked totals, not consumed outpoints) [4](#0-3) . This is a significant caveat: it's possible a persistent outpoint map exists elsewhere in the ~2000+ line `pox-5.clar` file that I did not view in full, given the index/tool-call limits reached during this investigation.

### Recommendation
Introduce a persistent, contract-level map (e.g., `used-lockup-outpoints: {txid, output-index} -> bool`) that is checked and updated (via `map-insert`, failing on duplicate) inside `validate-l1-lockup`, so that any given Bitcoin outpoint can only ever be credited toward stacking/bond weight exactly once across the lifetime of the contract, not merely within a single call's fold.

### Proof of Concept
Not able to be fully constructed/confirmed with certainty — this requires verifying (in a live/full read of `pox-5.clar` and its integration tests, e.g. `stacks-node/src/tests/pox_5_integrations.rs`) whether a cross-call persistent outpoint ledger exists elsewhere in the contract that I did not view due to tool-call/context limits reached in this session. If no such map exists, the PoC would be: (1) lock BTC in a valid pox-5 timelock output, (2) call `register-for-bond` once with SPV proof of that output to receive bond credit `X` sats, (3) call `register-for-bond` again (new bond-index or new staker context) supplying the *same* SPV proof of the *same* Bitcoin output; since `seen-outpoints` resets per-call, the same amount is credited a second time with no new BTC ever locked.

**Caveat**: Given the remaining tool-call budget was exhausted before I could read the surrounding `register-for-bond`/`stake` logic and the full map declarations at the top of `pox-5.clar`, I recommend a Devin session be used to fully verify (a) whether a persistent outpoint-consumption map exists elsewhere in the file, and (b) whether `register-for-bond` calls `verify-l1-lockups` per-registration without cross-referencing prior registrations' outpoints, before treating this finding as fully confirmed.
