### Title
Pre-fix binary-field (GF(2^m)) PEM curves in `is_valid_sig`/`vrf_verify` still reachable for units dated before `pemCurvesFixMci`, allowing an attacker-supplied malformed EC public key to reach OpenSSL's curve-point parser - ([File: signature.js])

### Summary
The Crypto++ advisory describes a crash in `gf2n.cpp` when parsing a DER-encoded public key for a binary-field (F(2^m)) elliptic curve whose polynomial terms are not strictly decreasing in degree. `ocore`'s oscript functions `is_valid_sig` and `vrf_verify` accept an attacker-supplied PEM public key string from AA trigger data and hand it directly to native EC/DSA key parsing in `signature.js`, historically supporting a long list of binary-field curves (`sect113r1`, `sect113r2`, `sect131r1`, `sect131r2`, `wap-wsg-idm-ecid-wtls*`, etc.).

### Finding Description
`signature.validateAndFormatPemPubKey()` maintains `objSupportedPemTypes`, a large table of OIDs including several GF(2^m) binary curves, and only restricts to `objSafePemTypes` (`prime256v1`, `secp224r1`, `secp384r1`, `secp256k1`, RSA) when `bPostPemCurvesFix` is true [1](#0-0) . The actual signature verification for any type other than the newly-added `secp256k1` npm path falls through to Node's built-in `crypto.createVerify('SHA256').verify({key: pem_key}, ...)`, which parses the DER/PEM key with OpenSSL [2](#0-1) . Both `is_valid_sig` and `vrf_verify` in the oscript evaluator take `pem_key` directly from evaluated (attacker-controlled) trigger expressions and pass it into this validation/verification pipeline [3](#0-2) .

`bPostPemCurvesFix` is computed from the *unit's own mci relative to `constants.pemCurvesFixMci`* (`3975000` testnet / `12185000` mainnet) [4](#0-3) , meaning any code path that evaluates a unit/trigger whose relevant mci is below this fix point still exercises the full unrestricted `objSupportedPemTypes` table, including binary-field curves — exactly the curve family implicated in the Crypto++ `gf2n.cpp` advisory. This is a "grandfather" branch retained for old AA definitions/units, not a full removal of the vulnerable code path.

### Impact Explanation
If OpenSSL's EC key parsing for a legacy/rare binary curve (GF(2^m)) is vulnerable to a malformed-DER crash analogous to the Crypto++ report, an attacker who can get any unit/trigger evaluated with `bPostPemCurvesFix === false` (i.e., referencing an mci prior to the fix point, which is always true for historical replay/catchup of old blocks, or for any AA whose validation state still resolves to a pre-fix mci) could pass a crafted PEM key into `is_valid_sig`/`vrf_verify` and crash the Node.js process evaluating it. Because AA evaluation and unit validation happen on every full node that processes the DAG, a reliable crash here is a network-wide denial-of-service vector — nodes repeatedly crash while trying to validate/replay the same unit, preventing confirmation of new units.

### Likelihood Explanation
Likelihood is **uncertain** and could not be fully confirmed with the available tooling:
- It is confirmed that the vulnerable code path (broad `objSupportedPemTypes`, including GF(2^m) curves) still exists and is reachable from unprivileged AA trigger data via `is_valid_sig`/`vrf_verify` for units below `pemCurvesFixMci` [5](#0-4) .
- What is **not confirmed**: (1) whether Node's OpenSSL binding actually recognizes/parses these obscure binary-curve OIDs at all (if OpenSSL rejects the OID outright, the `try/catch` around `verify.verify()` would simply catch a normal error, not crash) [6](#0-5) ; (2) whether the specific Crypto++ `gf2n.cpp` defect (a C++ library bug) has any counterpart in OpenSSL's own binary-curve point parser — the advisory is Crypto++-specific and Node does not use Crypto++, so this is a bug-class analogy rather than a proven shared vulnerability; (3) whether a native OpenSSL crash, if triggered, would escape the JS `try/catch` (native segfaults are not catchable by JS `try/catch`, so if such a bug exists in OpenSSL it would indeed crash the process, but its existence is unverified here).
- The presence of `pemCurvesFixMci` and the explicit `objSafePemTypes` restriction strongly suggests the developers already identified and mitigated a security concern with parsing several of these legacy curves via OpenSSL, which raises the plausibility that a real (if different) issue was found in this exact area previously — but the specifics of that historical fix could not be retrieved (no prior commit history was available in this repo snapshot).

### Recommendation
- Confirm with the current OpenSSL version bundled with the Node runtime whether any of the retained legacy binary-field curve OIDs in `objSupportedPemTypes` can trigger a native crash on malformed points, and if so, remove them from the pre-fix table entirely rather than only gating them post-fix.
- Consider making the safe-curve restriction unconditional (not mci-gated) for any new evaluation, and only allow the unsafe legacy table strictly for re-validating already-stable historical units (never for new AA trigger evaluation), to shrink the attack surface.
- Wrap native crypto verification calls with additional defense in depth (e.g., worker-process isolation or a native-crash-tolerant sandbox) so that any native library defect cannot crash the main validation/consensus process.

### Proof of Concept
Not runnable without confirming that Node's OpenSSL binding will actually parse one of the retained GF(2^m) OIDs (e.g. `sect113r1`, OID `06072a8648ce3d020106052b81040004`) — conceptually: craft an AA trigger whose `data.pem_key` is a DER/PEM-encoded EC public key using one of the binary-field OIDs from `objSupportedPemTypes` with a corrupted point encoding (polynomial terms not strictly decreasing in the underlying representation), and invoke `is_valid_sig(trigger.data.message, trigger.data.pem_key, trigger.data.signature)` on a trigger/unit whose associated mci resolves to `bPostPemCurvesFix === false`, forcing evaluation through `crypto.createVerify('SHA256').verify({key: pem_key}, ...)` [2](#0-1) [7](#0-6) .

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}
