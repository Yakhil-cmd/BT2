### Title
Unallowlisted route venues let an attacker-named "pool" contract ride the caller's signed auth tree to transfer arbitrary wallet tokens - (File: contracts/swap-aggregator/src/execute/mod.rs — dispatch path; demonstrated by tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs)

### Summary
Analogous to GHSA-55v3-xh23-96gh (a credential meant for GitHub hosts being usable toward a non-GitHub host), the controller's router-integration keeps no venue allowlist: `StrategySwap` payload bytes name arbitrary pool addresses that `execute_strategy` invokes below the caller's authorization. Any contract placed on that call stack can call `token.transfer(victim, attacker, amount)`, which the host records as a sub-invocation of the *victim's* auth root. An honest simulation therefore returns a poisoned tree; if the victim signs it (the same UI:R interaction as the advisory), the transfer executes — an authorization meant to scope one swap input leaks spending authority for an unrelated token to an unintended recipient.

### Finding Description
- `swap_tokens` grants the router one exact `token_in.transfer(controller, router, amount_in)` invoker-auth entry and then calls `router.execute_strategy` inside the flash guard; it does not constrain which pool/token contracts the payload names (`contracts/controller/src/strategies/swap.rs:33-38`).
- The router authenticates the sender once (`sender.require_auth()`), pulls `total_in`, and dispatches hops to pool addresses taken verbatim from the XDR route; venue adapters self-authorize via `env.authorize_as_current_contract`, so nothing distinguishes a real pool from attacker-deployed code (`skills/xoxno-swap-aggregator/payload.md:109-115`, `contracts/swap-aggregator/src/venues/auth.rs:72-77`).
- `docs/explanation/threat-model.md:154-165` states the resulting exposure: "a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount."
- The harness test proves enforceability: a `RogueHopPool` whose `swap()` calls `token::Client::transfer(victim, attacker, WALLET_BALANCE)` is recorded under Alice's `swap_collateral` root by simulation; enforcing host auth rejects the unsigned transfer but executes it once the poisoned tree is signed (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-72, 194-269`).

### Impact Explanation
Theft of user funds: any token balance in the victim's wallet (not just the routed input) can be moved to the attacker in the same transaction, for every `execute_strategy` caller and every controller strategy that routes a swap (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`).

### Likelihood Explanation
Medium, matching the advisory's UI:R profile: exploitation requires the victim to submit a route whose payload names the attacker's contract and to sign the simulation-produced tree containing the extra transfer. There is no on-chain allowlist or structural check that prevents naming an arbitrary pool, so the only barrier is client-side inspection of the signed auth tree — the same class of boundary failure as trusting `GITHUB_TOKEN` for a non-GitHub host.

### Recommendation
Maintain a governance-managed venue/pool allowlist consulted before `dispatch_hop` invokes a payload-named address, or constrain hops to addresses resolved from registered venue metadata rather than raw payload indices. Short-term, enforce in the SDK/quote path that a signed auth tree for `execute_strategy` or controller swap entrypoints contains exactly the single expected input-transfer child, and surface any extra sub-invocation as a hard refusal.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. Deploy `RogueHopPool` initialized with `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)`; its `swap()` performs `token.transfer(alice, attacker, amount)`.
2. Craft a route whose hop pool is the rogue contract and call `swap_collateral` under `mock_all_auths()` (recording mode): the recorded tree shows Alice's root carrying a sub-invocation `transfer(alice → attacker, WALLET_BALANCE)`; Alice's wallet is drained.
3. Enforcing mode: signing the honest root-only tree makes the host reject the rogue transfer (`Unauthorized function call`); signing the simulation-produced poisoned tree authorizes it and the wallet balance moves to the attacker.
