### Title
Broken tenant isolation in CCMenu API - stack-scoped `ApiClient` token can read any stack's status via `Stack.from_param!` bypass - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides both `authenticate_api_client` and `stack` from `Shipit::Api::BaseController`, but the overridden `#stack` method calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])` used by the base class. This drops the `current_api_client.stack_id` restriction entirely, letting any valid `ApiClient` token read the CCMenu status of any stack, not just the one it was issued for.

### Finding Description
The intended binding is `current_api_client.stack_id == stack.id` (or `stack.id ∈ stacks` when unscoped), enforced in the base controller via: [1](#0-0) 

`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `#stack` resolves through that scoped relation. `CCMenuController`, however, redefines `#stack` to bypass this scoping entirely: [2](#0-1) 

`ApiClient.authenticate(params[:token])` only verifies the signed token identifies a valid `ApiClient` row; it performs no scope check on `stack_id`: [3](#0-2) 

The only authorization check applied by `require_permission :read, :stack` is `check_permissions!`, which verifies the client's `permissions` array contains `"read:stack"` — it never compares `current_api_client.stack_id` to the requested `stack_id`: [4](#0-3) 

Attack flow: attacker legitimately obtains a CCMenu URL for stack 1 (token for `ApiClient` A scoped to `stack_id: 1`, permission `read:stack`). Attacker sends `GET /api/stacks/2/cc.xml?token=<A's token>`. `authenticate_api_client` succeeds because the token is valid. `require_permission!(:read, :stack)` passes because A holds `read:stack`. `#show` calls `#stack`, which resolves `Stack.from_param!(params[:stack_id])` = stack 2, with no cross-check against `current_api_client.stack_id == 1`. The controller renders stack 2's CCMenu XML (deploy status) to the attacker.

### Impact Explanation
An attacker with legitimate, narrowly-scoped access to one stack's CCMenu endpoint can read deploy/rollback status for any other stack in the installation by simply changing the `stack_id` path segment while reusing their own valid token — no additional secrets or privileges needed. This is repeatable against every stack id in the system (enumerable via sequential integer ids) and crosses tenant boundaries, matching the "High - unauthenticated read of stack state" impact category (the token was authenticated for a different resource, so this is effectively unauthenticated read relative to the target stack).

### Likelihood Explanation
Preconditions are minimal and realistic: two or more stacks exist, and the attacker has ever been issued a CCMenu URL for a stack they legitimately manage (a very common, low-privilege API client type). No secrets need to be guessed — the attacker already possesses their own valid token via `CCMenuUrlController#fetch`. The only action required is changing the `stack_id` in the URL. This is trivially and repeatably exploitable.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to reuse the scoped lookup from the base controller instead of overriding it:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
or simply remove the override so the inherited `BaseController#stack` (which uses `stacks.from_param!`) is used.

### Proof of Concept
```ruby
# minitest ActionDispatch::IntegrationTest
stack1 = shipit_stacks(:shipit)
stack2 = Shipit::Stack.create!(repository: stack1.repository, environment: 'staging2')

client = Shipit::ApiClient.create!(
  creator: shipit_users(:walrus),
  name: 'scoped-client',
  stack: stack1,
  permissions: ['read:stack'],
)

get api_stack_ccmenu_url(stack_id: stack2.to_param, token: client.authentication_token)

# Broken binding check: client.stack_id (== stack1.id) must equal the stack actually served.
assert_not_equal client.stack_id, stack2.id # precondition: client is NOT authorized for stack2
assert_response :success        # currently 200 — should be :not_found or :forbidden
assert_match stack2.repository.full_name, response.body # confirms stack2 data leaked to a stack1-scoped token
```
This test currently passes (returns 200 with stack2's CCMenu XML) on the vulnerable code, demonstrating the cross-tenant read.
