### Title
`CCMenuController` bypasses stack-scoped `ApiClient` authorization, allowing a stack-scoped token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController#stack` restricts stack access to the set of stacks a given `ApiClient` is authorised for via `stacks`, which filters by `current_api_client.stack_id` when the client is scoped to a single stack. `Shipit::Api::CCMenuController` overrides `#stack` and looks the stack up directly with `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping. This breaks the binding "the stack(s) an `ApiClient` token authorises == the stack the request actually touches," which is exactly the class of bug flagged in the external report (a value acted upon that isn't covered by the authorisation/verification check that was supposed to gate it).

### Finding Description
`BaseController` defines the "authorised stacks" set and the stack lookup as: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id`, otherwise `Stack.all`. `stack` is supposed to always go through this scoped relation via `stacks.from_param!(...)`.

`CCMenuController`, however, defines its own `stack` method that ignores the `stacks` scoping entirely: [2](#0-1) 

It only requires the generic `:read, :stack` permission, not that the requested `stack_id` matches the client's `stack_id`: [3](#0-2) 

`#show` then renders build/deploy state for whatever `stack` this bypassed lookup resolves to: [4](#0-3) 

The `ApiClient` model supports creating tokens scoped to a single stack (`belongs_to :stack, optional: true`), and this is an intended, in-scope use case — the fixture `here_come_the_walrus` demonstrates a real client scoped to one stack with only `read:stack` permission, and the `stacks_controller_test.rb` confirms that scoping is enforced elsewhere ("an api client scoped to a stack will only see that one stack"): [5](#0-4) [6](#0-5) 

Because `CCMenuController#stack` does not use the `stacks` scoping helper that `StacksController` (and `BaseController` by default) rely on, a token that is supposed to be restricted to a single stack can be used against the CCMenu endpoint to read the deploy/build status of **any** stack in the installation by simply supplying a different `stack_id` in the URL, since `require_permission :read, :stack` only checks the generic permission string and never checks `stack_id` equality.

### Impact Explanation
This is an unauthenticated-read escalation: an attacker holding a legitimately-issued, narrowly-scoped `ApiClient` token (e.g. a CCMenu token created for one specific stack via `CCMenuUrlController`, or any other single-stack-scoped client) can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.) for stacks outside the scope they were granted — an authorization-scope escalation matching the impact bar "escalation into Shipit... authorization" / "unauthenticated read of stack state, task streams or deploy output" for stacks the token was never meant to see.

### Likelihood Explanation
Any holder of a stack-scoped API token/CCMenu URL (which is explicitly designed to be handed out to less-trusted consumers, e.g. embedded in CI dashboards) can trivially exploit this by changing the `stack_id` path parameter of the CCMenu request — no additional privilege or secret is required beyond having one legitimately scoped token.

### Recommendation
Remove the `stack` override in `CCMenuController` and let it inherit `BaseController#stack`, which correctly scopes lookups through `stacks` (i.e. `current_api_client.stack_id`-restricted). If overriding is required for parameter naming reasons, ensure the override still filters through the `stacks` scoping method instead of calling `Stack.from_param!` directly.

### Proof of Concept
1. As an authenticated user, request a CCMenu URL for `stack_A` via `CCMenuUrlController#fetch`; this creates/returns an `ApiClient` token (in general, any single-stack-scoped `ApiClient` with `read:stack` works, e.g. the `here_come_the_walrus` pattern).
2. Use that token to call `GET /api/stacks/:stack_id/ccmenu.xml` (the CCMenu controller's route) but substitute `stack_id` with `stack_B`'s id/param, a stack the token was never scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of going through `stacks.from_param!`, the request succeeds and returns `stack_B`'s deploy/build status, even though the token is scoped to `stack_A` only.
