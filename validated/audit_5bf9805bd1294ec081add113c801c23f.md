### Title
Kiosk owner can close a Kiosk while extension dynamic fields hold user deposits, permanently locking funds - (File: crates/sui-framework/packages/sui-framework/sources/kiosk/kiosk.move)

### Summary
The `sui::kiosk::close_and_withdraw` function allows a Kiosk owner to destroy a Kiosk after verifying only that `item_count == 0`, without checking whether the Kiosk's UID still owns dynamic fields added by extensions. [1](#0-0)  Because Sui's `object::delete` primitive removes the UID but leaves attached dynamic fields orphaned and inaccessible, any user deposits stored in extension dynamic fields are permanently locked. [2](#0-1) [3](#0-2)  This is the native Sui analog of burning a token that still has active rental deposits.

### Finding Description
`close_and_withdraw` takes the `Kiosk` by value together with its `KioskOwnerCap`, asserts ownership via `id.to_inner() == for`, and asserts `item_count == 0` before calling `id.delete()`. [1](#0-0)  The `allow_extensions` flag and any extension-added dynamic fields are ignored on the destruction path. [4](#0-3)  Kiosk extensions obtain mutable access to the Kiosk UID through the extension framework and can attach dynamic object fields or dynamic fields that hold user assets. [5](#0-4)  The `item_count` counter only tracks items placed via `place_internal` and does not account for extension state. [6](#0-5)  When `id.delete()` is invoked, the framework's `delete` implementation emits a deletion event and consumes the UID without traversing or removing child dynamic fields. [2](#0-1)  Dynamic field child objects are addressed by hashes of the parent address, name, and type, so once the parent UID is gone the child object IDs cannot be recomputed and the objects become unreachable. [3](#0-2) 

### Impact Explanation
This leads to permanent fund lock (High impact) for users whose assets are held in Kiosk extension dynamic fields. [7](#0-6)  The owner does not steal the funds; instead the funds become irrecoverable because the only access path to the dynamic fields was the Kiosk UID. [8](#0-7)  The scenario mirrors the external report: a privileged owner destroys the parent object while unprivileged users still have active deposits recorded in child state.

```text
public fun close_and_withdraw(self: Kiosk, cap: KioskOwnerCap, ctx: &mut TxContext): Coin<SUI> {
    let Kiosk { id, profits, owner: _, item_count, allow_extensions: _ } = self;
    let KioskOwnerCap { id: cap_id, `for` } = cap;

    cap_id.delete();
    id.delete();
```

```text
## Deleting an object with dynamic fields

It is possible to delete an object that has (potentially non-`drop`) dynamic fields still defined on it. Because field values can be accessed only through the dynamic field's associated object and field name, deleting an object that has dynamic fields still defined on it renders them all inaccessible to future transactions. This is true regardless of whether the field's value has the `drop` ability. This might not be a concern when adding a small number of statically known additional fields to an object, but is particularly undesirable for onchain collection types that could be holding unboundedly many key-value pairs as dynamic fields.
```
