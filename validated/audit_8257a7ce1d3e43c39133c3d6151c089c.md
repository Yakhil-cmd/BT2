### Title
Tokens transferred directly to the pool or controller are permanently locked with no recovery path - (File: contracts/pool/src/ops/withdraw.rs, contracts/controller/src/payments.rs)

### Summary

The original report describes a contract that accepts ETH from anyone via `receive` but can only pay out through a WETH balance, so a user who tops it up directly can never recover the funds. XOXNO Lending has the same shape: anyone can `token.transfer` arbitrary assets directly to the pool or controller contract addresses, yet neither contract exposes any entrypoint that can pay out those stray balances. The pool deliberately does not book unsolicited deposits into `cash` (they are unbooked donations), and every outbound path is keyed to booked claims only — `withdraw` pays out `net_transfer` computed from burned supply shares, `claim_revenue` only burns booked revenue shares, `repay`/`recapitalize` refunds are bounded by the owner's measured amount, and `refund_controller_balance_delta` explicitly preserves any pre-existing controller balance. There is no `sweep`/`rescue` function on either contract (only the out-of-scope swap-aggregator has `sweep_balance`).

### Finding Description

- `controllers/controller/src/markets.rs:129-137` and `contracts/pool/src/lib.rs:182-194`: all inbound accounting (`supply`, `repay`, `recapitalize`) credits only measured receipts; a raw SAC `transfer` to the pool raises `token.balance(pool)` above every market's `cash` book forever.
- `contracts/pool/src/ops/withdraw.rs:30-50`: outbound transfers are driven solely by `net_transfer` derived from share accounting; nothing can send the unbooked surplus anywhere.
- `contracts/pool/README.md` surface table: the pool's only `out` paths are `borrow`, `withdraw`, `claim_revenue`, `flash_loan`/`create_strategy` — all of them gated by booked state, none able to touch surplus.
- `contracts/controller/src/payments.rs:41-52`: `refund_controller_balance_delta` refunds only the balance *increase* since `balance_before`, deliberately preserving (and thus permanently parking) whatever stray balance already sat on the controller.
- `docs/explanation/threat-model.md:172-179` confirms "Neither category sweeps prior balances" and the DeFindex adapter "has no recovery path for arbitrary stranded assets"; `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs` documents that "the controller holds funds no balance-delta measurement can ever claim."
- The GH-17 guard rejects `to = pool/controller` on `borrow`/`withdraw`, which acknowledges the stranding hazard — but it only stops *protocol-initiated* transfers into those addresses; any user (or any third-party contract's callback) can still send tokens directly to either address via the token contract, bypassing the guard.

### Impact Explanation

Tokens sent to the pool or controller outside the measured deposit flows are permanently frozen: no user, keeper, owner, or governance action can move them. For the pool this also means `token.balance(pool)` can diverge arbitrarily far above the sum of all `cash` books with no reconciliation path, and flash-loan balance assertions bake the surplus into `pre_balance` forever without ever releasing it. A user who tops up either contract directly — exactly the action class the original report flagged — loses those funds permanently.

### Likelihood Explanation

Direct SAC transfers to contract addresses are a routine occurrence (mistyped recipients, integrators prefunding instead of going through `supply`/`recapitalize`, refund-style pushes from other protocols). Each occurrence deterministically strands the transferred amount. The loss is limited to whoever sends funds, so this is a fund-freezing/usability defect rather than protocol insolvency — consistent with the Medium severity of the analog report.

### Recommendation

Add a `sweep`-style recovery (e.g., an owner-gated `sweep_excess` on the pool that transfers `balance - Σ cash` to the accumulator, and an equivalent controller sweep for refund-asset leftovers), mirroring the swap-aggregator's `sweep_balance`. Alternatively, keep the no-sweep design but document prominently that any token balance exceeding booked `cash` is permanently burned.

### Proof of Concept

1. Alice calls `token.transfer(alice, pool_addr, X)` for a listed asset (or for an unlisted token).
2. `get_reserves` / `get_sync_data` for every `(hub, asset)` market is unchanged; `token.balance(pool)` exceeds total booked cash by `X`.
3. No entrypoint (`supply`, `withdraw`, `repay`, `recapitalize`, `claim_revenue`, `seize_positions`, `flash_loan`, owner calls) can transfer out more than booked claims; `X` is unrecoverable.
4. The same holds for `token.transfer(alice, controller_addr, X)`: `refund_controller_balance_delta` only refunds the delta above `balance_before`, so pre-existing `X` is preserved in place indefinitely.
